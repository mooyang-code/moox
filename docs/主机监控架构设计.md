# 主机监控架构设计

本文描述 MooX 当前主机监控链路、模块边界和关键设计决策。它是主机监控的架构基线；执行计划只记录实施过程，不作为现状说明。

## 目标与边界

主机监控面向不超过 10 台 Linux 服务器，只支持 `amd64` 和 `arm64`。系统采集 CPU、内存、文件系统、磁盘 I/O 和网络指标，允许短时丢样，不追求审计级可靠性。

明确不做：

- 不在 Admin 中采集或保存主机指标。
- 不依赖 Node Exporter，也不复制其 collector 实现。
- Host Agent 不使用 SQLite、outbox 或离线补发队列。
- 不提供 Host Agent 直连 Monitor HTTP 上报路径。
- 前端不直接查询 Storage，也不读取 Monitor SQLite。
- 不按 Agent 或使用场景拆分 EventBus 凭据。

## 总体架构

```text
Linux kernel interfaces
  /proc + /sys + statfs
          |
          v
  moox-host-agent
          |
          | HostMetric / MooxMessage
          | moox.metrics.host.reported.v1
          v
  NATS JetStream (moox-eventbus)
          |
          | durable consumer, at-least-once
          v
     moox-monitor
       |       |
       |       +--> 内存 latest registry
       |       +--> 内存规则快照 -> 告警状态/事件
       v
    Storage PrimaryStore
       |
       +--> host_resource_v1
       +--> host_fs_v1
       +--> host_disk_v1
       +--> host_net_v1

Web -> Admin 控制面 -> moox-monitor -> latest registry / Storage history
```

链路只有一个事实入口：Host Agent 发布 EventBus 消息，Monitor 消费后直接写 Storage。Admin 仅负责登录鉴权、浏览器控制面和节点/服务部署注册；机器服务请求由每台服务器的独立 Gateway 转发。

主机指标的四个 Dataset 在 Schema v5 中直接绑定部署注册的 DataNode，并以 disabled
状态导入。部署先注册 `node_id/service_target`，Doctor 通过只读激活检查确认 DataNode
身份、Schema 和运行就绪，再显式激活 Dataset；激活后绑定锁定，Monitor 写入路径只使用
Metadata Snapshot，不在每条消息上访问 SQLite。DataNode 页面展示节点下的 Dataset 标签。

## 模块职责

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| `modules/hostagent` | 读取 Linux 内核接口、计算瞬时值和计数器、发布 `HostMetric` | 历史保存、补发、告警、HTTP 上报 |
| `modules/eventbus` | 独占 NATS JetStream Broker，声明 Stream、Topic、Consumer 和 ACL | 业务消息转换、发布代理、指标存储 |
| `packages/messagepb` | 定义统一 `MooxMessage` 外层协议 | 业务处理 |
| `packages/jetstream` | 封装 NATS 连接、发布、消费、凭据和投递语义 | 内嵌 Broker、业务重试策略 |
| `modules/monitor` | 校验并消费消息、写 Storage、维护当前快照、计算告警、提供查询 API | Host 原始样本 SQLite 历史 |
| `modules/storage` | 保存分钟级时序数据；默认保留 48 小时 | 告警计算、页面聚合 |
| `modules/admin` | JWT 鉴权、浏览器控制面、网关节点和 SysDeploy 路由编译 | 主机采集、历史保存、机器服务代理 |
| `modules/gateway` | 校验机器请求并把 Monitor API 转发到节点本机 | 指标采集、历史保存、跨节点转发 |
| `web` | 主机卡片墙、选中主机明细和趋势 | 直连 EventBus 或 Storage |

## 采集与消息语义

Host Agent 由 `trpc.moox.hostagent.sample.timer` 每 15 秒采集一次，并通过 `startAtOnce=1` 在服务启动时同步采集。初次采集或发布失败会阻止 Timer service 成功启动。CPU 和速率指标需要相邻样本才能计算；首次启动、计数器回绕或间隔异常时必须标记 unavailable，不能用 `0` 代替缺失。

Agent 使用普通用户目录中的 `0600` identity 文件保存稳定 `agent_id`。这个标识不依赖 hostname、IP 或进程生命周期，是主机卡片选择、Storage subject 和历史查询的统一身份。

每次采集构造 `HostMetric`，再包装为 `MooxMessage` 发布到 `moox.metrics.host.reported.v1`。发布是 best effort：成功获得 PubAck 即结束；失败只记录错误，下一周期发布新样本，不补发旧数据。

## EventBus 与鉴权

`moox-eventbus` 是唯一 Broker 所有者，业务服务通过 `packages/jetstream` 直接连接 NATS。管理面只读，不提供 tRPC/HTTP 发布代理。

公网部署使用 NATS 用户名和一个共享 `eventbus_token`。部署发布流程生成凭据并写入目标用户可读的 `0600` 文件；Host Agent、Monitor 等进程从文件加载。凭据永久有效，不设置自动过期和自动轮换；需要轮换时由发布流程提醒用户并重新部署相关进程。

二进制 Protobuf 只是传输格式，不承担安全边界。真正的身份校验由 NATS 用户、共享 token、ACL 和连接权限完成。

## Monitor 消费顺序

Monitor 使用 durable consumer，处理顺序固定为：

```text
Validate -> Write Storage -> Update latest -> Evaluate alerts -> Ack
```

- 校验失败的毒消息进入 DLQ 并终止重投。
- Storage 暂时失败时 NAK，由 JetStream 有界重投。
- Storage 成功后才更新内存 current registry，避免页面展示未落盘的样本。
- 告警错误不回滚已成功的 Storage 写入，也不阻塞 ACK。
- 同一分钟的重复消息使用确定性时序 key 幂等覆盖。

Monitor 不保留 HostMetric inbox、latest、history 或 outbox 表。当前快照只在内存中，进程重启后等待 Agent 下一次上报恢复；这是接受丢样以换取简单实现的明确取舍。

## Storage 模型与保留策略

所有系统主机指标使用 `space_id=moox_system`。该 Space 是系统级命名空间，不受管理台业务 Space 筛选影响，任何业务 Space 都能查看系统监控数据。

Monitor 将 15 秒样本投影到 `freq=1m` 的四个 Dataset：

| Dataset | 内容 |
| --- | --- |
| `host_resource_v1` | CPU、内存和逻辑核心数 |
| `host_fs_v1` | 挂载点、容量、使用率和只读状态 |
| `host_disk_v1` | 磁盘累计计数、吞吐、IOPS 和利用率 |
| `host_net_v1` | 网卡状态、累计计数、吞吐、错误和丢包 |

Storage 是历史数据的唯一事实源。`trpc.moox.storage.host_metrics_cleanup.timer` 每小时删除严格早于 48 小时的数据；每个数据集单次最多清理 10 批，每批每 target 最多 1000 行，并设置 60 秒超时、防重入、部分失败继续和结果指标。Monitor API 允许请求最近 72 小时，但默认部署中 48 小时之前的数据已被 Storage 清理；Monitor 自身不删除 Storage 事实。历史数据允许存在缺口，前端必须展示 `data_gap`，不能插值伪造完整曲线。全系统容量边界见[数据保留与磁盘空间](运维/数据保留与磁盘空间.md)。

## 告警设计

告警在 Monitor 消费链路中直接计算，不依赖 Storage 变更通知，避免“写入后再订阅自己消息”的环路。

规则仍保存在 Monitor SQLite，但通过 `snapshotcache` 周期性加载成不可变内存快照。消费路径只读缓存，不逐消息查询数据库；规则新增、修改或删除后不主动刷新，统一等待下一次定时加载。刷新失败保留上一份可用快照；首次尚无快照时跳过告警，不影响落盘与 ACK。

主机规则统一属于 `moox_system`，支持 CPU、内存、文件系统、磁盘和网络条件。unavailable 的值不参与阈值判断。

## 查询与前端

管理台调用路径为：

```text
/ops/hosts?tab=monitor
  -> Admin 浏览器控制面
  -> Monitor 服务实例
  -> trpc.moox.monitor.MonitorMgr
```

`ListHostAgents` 读取 Monitor 内存 current registry；`QueryHostMetricHistory` 从 Storage 合并四个 Dataset。前端使用稳定 `agent_id` 选择主机，并显示：

- 一至三列响应式主机卡片墙。
- CPU、内存、最大文件系统使用率和聚合网络速率。
- 选中主机的文件系统、磁盘、网卡明细。
- 1 小时、24 小时或 3 天趋势。
- 离线、指标不可用、Storage 不可用和历史缺口状态。

实时值为合法 `0%` 时必须显示为零；只有 availability 为 false 或字段缺失时显示 `--`。自动刷新只更新当前卡片，避免周期性重置用户正在查看的历史范围。

## 部署与故障语义

启动顺序是 EventBus、Storage、DataNode 注册、Host metadata、Doctor 只读检查、Dataset
显式激活、Monitor、Host Agent、Admin/Web。Monitor 启动前不应用独立拓扑 seed；每个 Host
Dataset 的 `data_node_id` 必须已注册且通过激活检查。

| 故障 | 行为 |
| --- | --- |
| Host Agent 无法连接 EventBus | 丢弃本周期样本，下周期重试新样本 |
| EventBus 暂时不可用 | 发布失败或消费暂停，恢复后继续 |
| Storage 未就绪 | Monitor 暂停 fetch 或 NAK，不更新 current registry |
| Monitor 重启 | current registry 清空，等待下一次 Agent 上报 |
| 规则缓存刷新失败 | 保留旧快照继续计算 |
| 历史被清理或丢样 | API 返回 gap 状态，前端不补零 |

部署命令、凭据文件和 user systemd 说明见 [监控配置](监控配置.md)；EventBus 运维见 [MooX EventBus 运维](运维/MooX-EventBus运维.md)。
