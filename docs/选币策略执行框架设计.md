# MooX 选币策略执行框架设计

## 文档状态

本文是 Strategy 模块的目标架构。当前代码仍是 Python `run-once + quantity` 契约，
见 [策略模块架构设计](策略模块架构设计.md)。项目不保留旧契约兼容分支；实施时直接
替换为本文的声明式选币与权重输出。

旧实施计划
[MooX 选币策略执行框架实施计划](superpowers/plans/2026-08-29-moox-coin-selection-strategy.md)
已作废，不再作为施工依据。新的实施计划在本文确认后再写。

本文固定以下决策：

- Strategy 输出目标权重，不输出交易数量。
- 选币候选集合称为标的池（`InstrumentPool`）。规则称为 `InstrumentPoolRule`。
- 标准流水线为：解析标的池 → 截面打分 → 前置过滤 → 选币 → 后置过滤 → 方向内等权。
- 因子继续使用现有 `factor_id`（FactorDef + Binding 两层），不引入 FactorInstance。
- 一个 Runner 一个日程、一份标的池规则。不做多组件、多 Slot、权重合成器。
- 运行时查询 View，不落盘输入快照制品。
- 一期不做 Python 策略入口，不做回测引擎。

## 目标

Strategy 把一份不可变的选币配置应用到某个周期已经算好的行情和因子上，生成可追溯的
目标权重，并交给 Trade。

一期能力：

- 按 `InstrumentPoolRule` 解析当期标的池，在池内做横截面排名和选币。
- 前置过滤、选币、后置过滤，顺序固定。
- 多头与空头可写在同一份配置里；现货不允许负权重。
- 选币数量支持固定数量和比例。
- 多因子横截面排名后加权求和。
- Live 与 Paper 共用同一套求值语义。
- 每次运行可解释、可幂等恢复。

## 非目标

- Strategy 不读取交易凭据，不提交订单，不管理成交和持仓。
- Strategy 不根据固定资金数额生成数量。
- Strategy 不直接访问交易所、网络或账户余额。
- 不拆分 FactorDef / FactorInstance / FactorBinding。同一算法不同参数继续使用不同
  `factor_id`。
- 不做横截面派生指标（如 rank_diff）。需要时先做成普通时序因子。
- 不保存内容寻址的 MarketFrame 制品，不维护逐周期 point-in-time 成员时间线。
- 不做多 `StrategyComponent`、多 `RebalanceSlot`、`WeightMerger`。
- 不建设 Python 自定义策略、回测引擎、分布式工作流。

## 术语

| 术语 | 含义 |
| --- | --- |
| `InstrumentPoolRule` | 标的池规则。交易所、市场、报价资产、包含/排除名单、最短历史等过滤条件 |
| `InstrumentPool` | 某周期用规则解析出的候选 `instrument_id` 列表。打分和过滤都在这个集合上进行 |
| `StrategyDef` | 不可变选币配置：原始 YAML、编译 JSON、hash |
| `StrategyRunner` | 一份配置的可调度实例：空间、频率、账户 |
| `StrategyResult` | 某周期已接受的权重快照 |
| `InstrumentTarget` | `instrument_id` + `target_weight` |

「解析标的池」指：用 `InstrumentPoolRule` 查询当期标的目录和 View 数据，得到
`InstrumentPool`。规则不是列表；列表要到运行时才能确定。

标的池不是 Storage 的 Subject 目录，也不是 Trade 账户的可交易品种。`markets`
只限制选币候选，不决定用哪个执行账户。

## 模块边界

```text
Collector
  -> 采集闭合，Source View 可读
Factor
  -> 逐标的时序因子
  -> ViewFactorPeriodReady（结果 View 可查询）
Strategy
  -> 解析标的池
  -> 查询当期行情与因子列
  -> 打分 / 前置过滤 / 选币 / 后置过滤 / 等权
  -> StrategyResult + outbox
Trade
  -> 按当时权益和参考价格把权重换成 quantity
  -> 现有 TargetExecutor
```

Strategy 只消费 Storage 已发布的可读事件。因子结果以 `ViewFactorPeriodReady` 为准，
因为只有它保证 Result View 可查询。Factor 模块本身不改协议。

## 领域模型

### StrategyDef

不可变制品。配置变化时创建新的 `strategy_id`，不原地修改。

```text
strategy_id
name
kind = coin_selection
manifest_yaml
compiled_json
source_hash
created_at
```

`compiled_json` 在发布时生成：校验 schema、解析 `factor_id`、归一化多空
`side_weight`、冻结依赖的 Source View 与因子 Result View。运行只读编译结果。

### StrategyRunner

```text
runner_id
strategy_id
space_id
source_view_id
frequency
logical_account_id
status
current_targets_json
command_sequence
last_result_id
last_error
```

一个 Strategy 可创建多个 Runner。一个执行型 Runner 最多控制一个 LogicalAccount；
观察型 Runner 不关联账户。一个启用的 LogicalAccount 只能有一个 owner Runner。

切换 Strategy 或账户前必须先停用 Runner。

### 调度

数据粒度与调仓间隔分开，但一期只允许单一间隔，没有多个 offset。

```yaml
input:
  source_view_id: crypto_spot_kline_1h
  data_frequency: 1h
schedule:
  every: 24h
```

`every` 默认等于 `data_frequency`，即每个闭合周期都调仓。若 `every` 更大，只在
`period_time` 对齐该间隔时运行（UTC 锚点）。收到未对齐周期的 ready 事件时忽略。

## 标的池

### InstrumentPoolRule

```yaml
instrument_pool:
  exchanges: [binance]
  markets: [spot]
  quote_assets: [USDT]
  include: []
  exclude: [BTC-USDT-SPOT, ETH-USDT-SPOT]
  min_history_periods: 168
```

| 字段 | 含义 |
| --- | --- |
| `exchanges` | 数据来源，对应 `series_tag` / venue，如 `binance` |
| `markets` | 候选市场，如 `spot`、`perpetual` |
| `quote_assets` | 报价资产，如 `USDT` |
| `include` | 非空时，候选只能来自该名单（仍须满足其余条件） |
| `exclude` | 从候选中去掉 |
| `min_history_periods` | 不同 `data_time` 数量下限；不足则不进入标的池 |

`include` / `exclude` 使用完整 `instrument_id`，例如 `BTC-USDT-SPOT`。

多头和空头共用这一份规则。需要现货多头与合约空头分池时，用两个 Runner、两个
LogicalAccount，不在一期做侧边覆盖。

### 解析

```text
候选 = 标的目录中满足 exchanges/markets/quote_assets/include/exclude 的 instrument
适格 = 候选中历史长度 >= min_history_periods 的 instrument
InstrumentPool = 适格集合（按 instrument_id 升序）
```

适格只看历史长度。历史不足的新上市标的正常排除，不构成失败，记入 `debug_info`。

当期数据是否齐全不改变池的成员：池内标的缺少当期行或必需列，属于数据链路异常。
默认 `readiness.policy = strict`：存在缺数据标的或必需 View 未齐时跳过本期，只更新
Runner `last_error`（含缺失标的列表），不写 `StrategyResult`，不发事件。横截面排名
对样本变化敏感，不能默认静默缩小样本。

`exclude` 策略可在后续版本增加；一期只实现 `strict`。

标的池列表随当次 `StrategyResult` 的 `debug_info` 落库，不单独建
`t_universe_snapshots` 一类表。下次运行再解析一遍。

## 数据输入

截面选币只使用**当期**每个标的一行：行情列加已计算的因子列。Strategy 不在模块内
做 rolling 窗口；lookback 由 Factor 完成。

```text
instrument_id       close    bias_20    quote_volume_mean_w288
SOL-USDT-SPOT       ...      ...        ...
DOGE-USDT-SPOT      ...      ...        ...
```

唯一键为 `instrument_id`。列必须能对应到编译后的 Field 或 `factor_id` 输出。
不允许未来数据。查询失败或列缺失按 `strict` 跳过本期。

输入 hash 包含：Strategy hash、compiled hash、标的池列表、当期面板内容。
上游事件 ID 只做来源记录，不参与 hash。

## 标准选币流水线

```text
InstrumentPoolRule
  -> ResolveInstrumentPool
  -> 查询当期面板
  -> CrossSectionScore
  -> PreFilter
  -> Select
  -> PostFilter
  -> SideWeight
  -> StrategyResult
  -> Outbox
```

### 打分

每个因子先在**未做前置过滤**的标的池上做横截面排名，再乘归一化权重求和。过滤改变
可选集合，不改变本周期已经算好的名次。

```text
score = sum(rank(metric_i, direction_i) * normalized_weight_i)
```

排名使用 `method=min`：相同值共享最小 rank。最终选币按 `(score, instrument_id)`
稳定排序后截取，既保留并列含义，也不会因并列超选。

`direction: ascending` 表示因子值越小 rank 越靠前（多头常见于「超卖」类）；
`descending` 相反。

### 过滤

```yaml
filters:
  - phase: pre
    factor_id: quote_volume_mean_w288
    value_type: percentile
    op: gte
    value: "0.2"
```

| 字段 | 取值 |
| --- | --- |
| `phase` | `pre` 或 `post` |
| `value_type` | `value` / `percentile` |
| `op` | `lt` / `lte` / `gt` / `gte` / `eq` |

过滤规则写在 `long:` / `short:` 块内，天然作用于所在方向，没有独立的 `side` 字段。
`percentile` 是标的池内的横截面分位（0 到 1）；按名次筛选用 `selection.mode: count`
表达，不提供 `value_type: rank`。

同阶段多条规则 AND。未知字段、NaN 比较、类型不匹配在编译或运行时失败，不静默忽略。

### 选币

```text
count       固定数量
fraction    标的池（经过前置过滤后）的比例
```

比例向下取整；比例大于零且候选非空时至少选 1 个。不实现 `rank_range`、`all`、
`match_long`。

后置过滤可能使入选数量少于 selection 请求值。这是允许的：先按规则截取，再剔除
不满足后置条件的标的，不回补。

### 方向权重

入选标的在方向内等权：

```text
instrument weight = 归一化后的 side_weight / 该方向最终入选数量
```

多头为正，空头为负。只有 long 时，多头权重和为 1。多空都启用时，按 `side_weight`
归一化后分配，例如 long 0.5 / short 0.5 则多头和为 +0.5、空头和为 -0.5。
`side_weight` 为 0 或省略该侧，表示该方向不选。

Spot 标的不允许负权重；`instrument_pool.markets` 仅含 `spot` 时，编译期拒绝空头。
未出现在 FULL 目标中的旧标的表示零权重。

方向内等权意味着同方向所有权重相等，不会产生需要清理的尘埃权重，因此没有
`dust_weight` 配置。

`gross = sum(abs(weight))`，`net = sum(weight)`。gross 不必等于 1；未分配部分视为
现金。杠杆与保证金上限由 Trade 的 LogicalAccount 风控判断。

## 配置示例

```yaml
api_version: moox.strategy/v2
kind: coin_selection

input:
  source_view_id: crypto_spot_kline_1h
  data_frequency: 1h
  factors:
    - factor_id: min_max_w288
    - factor_id: quote_volume_mean_w288
    - factor_id: zf_mean_q_w288

instrument_pool:
  exchanges: [binance]
  markets: [spot]
  quote_assets: [USDT]
  include: []
  exclude: [BTC-USDT-SPOT, ETH-USDT-SPOT]
  min_history_periods: 168

schedule:
  every: 24h

readiness:
  policy: strict

long:
  side_weight: "1"
  scores:
    - factor_id: min_max_w288
      direction: ascending
      weight: "1"
  filters:
    - phase: pre
      factor_id: quote_volume_mean_w288
      value_type: percentile
      op: gte
      value: "0.2"
    - phase: post
      factor_id: zf_mean_q_w288
      value_type: value
      op: gt
      value: "0.5"
  selection:
    mode: fraction
    value: "0.05"

# 省略 short，或显式 side_weight: "0"
```

发布时保存原始 YAML 和编译 JSON。编译 JSON 中的 `factor_id` 必须指向已启用的
Factor 及其在该 `source_view_id` / frequency 上的 enabled Binding。

## 触发

Runner 编译依赖为：Source View + 配置引用的每个因子 Result View。

收到相关 `ViewFactorPeriodReady`（必要时同时确认 Source View 已就绪）后：

1. 若 `period_time` 未对齐 `schedule.every`，忽略。
2. 若该周期所需 View 未齐，等待后续事件；不阻塞下一周期。
3. 齐备则求值：input hash 与已有 Result 相同则幂等返回；不同则覆盖并再发目标。
4. 某周期始终不齐则永不跑该期，只在 Runner 上保留最近错误；新周期独立。

不单独记录就绪进度。「ready」的含义就是 View 可查询，因此收到任意相关事件后直接
查询当期面板：列齐了就运行，缺行缺列就放弃、等下一个事件再试。个人系统事件量小，
重复查询的成本可以忽略。`t_strategy_inbox` 只做 `message_id` 去重。

不引入 `recalc_revision`、worker lease、owner token。进程内按 Runner 串行即可。
同一周期因子重算导致面板变化时，按 latest-wins 覆盖，与 Factor 一致。

## 输出与 Trade

策略输出：

```text
StrategyEvaluation
  action = hold | rebalance
  weights[]
    instrument_id
    target_weight
  debug_info
```

`debug_info` 是 JSON object，记录本次运行的解释信息：当期标的池、历史不足被排除的
标的（新上市）、各阶段过滤剔除数量等。它只用于事后解释和前端展示，不参与 hash、
hold 判断或任何下游决策。缺少当期数据的标的在 `strict` 下直接跳过本期、不产生
输出，因此不出现在这里，只记入 Runner `last_error` 和日志。

- `rebalance` 用本周期权重完整替换理论目标。空列表表示全部归零。
- 规范权重字符串与当前 `current_targets_json` 完全相同则视为 `hold`：不增加
  sequence，不发事件。
- 一次运行一个 FULL 快照，没有 Slot 中间组合。

发给 Trade 的事件沿用 `LogicalAccountTargetRequested`，字段改为权重：

```text
LogicalAccountTargetRequested
  target_id
  runner_id
  logical_account_id
  command_sequence
  signal_time
  targets[]
    instrument_id
    target_weight
```

权重使用规范十进制定点字符串。项目不保留 `quantity` 字段兼容。

Trade 在消费时按当时权威权益和参考价格换算：

```text
target_notional = equity * target_weight
raw_quantity    = target_notional / reference_price
```

同一 `target_id` 重投必须返回第一次换算结果，不得用新价格或新权益重算。换算在现有
事件消费者内完成，不引入独立 PENDING resolver、CAS 或 SUPERSEDED 状态机。量化、
合约乘数和容量检查仍由现有 TargetExecutor 在选好执行账户之后处理。

LogicalAccount 成员必须能交易目标中的市场与结算资产。选币池包含某市场，不自动
意味着账户能执行该市场。

## 持久化

```text
t_strategies
  不可变 StrategyDef、YAML、编译 JSON、hash

t_strategy_runners
  Runner 配置、状态、当前权重、账户、sequence

t_strategy_results
  运行幂等键、action、权重、debug_info、input hash

t_strategy_outbox
  待发布 LogicalAccountTargetRequested

t_strategy_inbox
  已处理的 View Ready message_id
```

业务事实仍是前四张表；inbox 只做事件去重。

`current_targets_json` 保存最新已接受的 FULL 权重，用于 hold 判断、展示和下游事件，
不回传给求值器，也不是账户实际持仓。

StrategyResult 逻辑键：

```text
(runner_id, strategy_id, period_time)
```

Runner 已绑定具体 LogicalAccount（自身是 live 或 paper），不需要 V1 的 `namespace`
维度。

相同键且相同 input hash 返回已有结果。相同键但 hash 不同视为当期数据已更新（与
Factor 的 latest-wins 一致）：写入新 Result、增加 sequence、再发 outbox。失败或
输入不齐不写 Result，只更新 `last_error`。

一次成功 `rebalance` 在同一 SQLite 事务中：插入 Result、更新 Runner 目标与
sequence、写 outbox。任一步失败全部回滚。

## 状态

Runner：`DISABLED` / `ENABLED`。启用前校验 Strategy 存在、引用的 Factor 与 Binding
已启用、View 与频率可用、标的池规则可解析、账户归属双向一致。

求值器是无状态纯函数：输入为编译配置、标的池、当期面板；输出为权重。Live 与 Paper
只是账户与执行环境不同。

## 可观测性

最少指标：`strategy_runs_total{status}`、`strategy_run_duration_seconds`、
`strategy_pool_instruments`、`strategy_selected_instruments{side}`、
`strategy_target_gross_weight`、`strategy_outbox_pending`。

日志字段：`space_id`、`runner_id`、`period_time`、`result_id`、`trace_id`。

## 安全与确定性

- 配置拒绝未知字段。
- decimal、时间、`instrument_id` 在 Go 边界规范化。
- 排序始终带 `instrument_id` 次级键。
- 不使用进程内随机数决定选币。
- 不从源码推断数据依赖；列和因子在发布时声明并编译。

## 交付顺序

1. 配置 schema、编译与校验（`InstrumentPoolRule`、因子引用、过滤、选币）。
2. 解析标的池，查询当期面板。
3. 求值器：打分、前置过滤、选币、后置过滤、等权。
4. 消费 `ViewFactorPeriodReady`，inbox 去重，对齐 `schedule.every`。
5. Result / outbox 改为权重；Trade 消费时换算 quantity。
6. 管理台与文档。
