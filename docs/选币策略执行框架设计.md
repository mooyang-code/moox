# MooX 选币策略执行框架设计

## 文档状态

本文是 Strategy 模块的声明式运行架构与实施基线。本文只定义目标契约和边界；旧版
Python `run-once + quantity` 文档仅作历史迁移参考，不再作为新实现的线上契约。实施
是否完成，必须以配套计划中的测试、协议检查和运行验收为准，不能以文档或工作树状态
推断。

配套施工步骤见
[MooX 选币策略执行框架实施计划](superpowers/plans/2026-08-29-moox-coin-selection-strategy.md)。

本文固定以下决策：

- Strategy 输出目标权重，不输出交易数量。
- 选币候选集合称为标的池（`InstrumentPool`）。规则称为 `InstrumentPoolRule`。
- 标准流水线为：解析标的池 → 标的池评分（`PoolScoring`）→ 前置过滤 → 选币 → 后置过滤 → 方向内等权。
- 因子继续使用现有 `factor_id`（FactorDef + Binding 两层），不引入 FactorInstance。
- XBX 迁移中的 12 个因子文件直接采用 MooX 因子格式；`Bias`、`Cci` 在本项目尚未正式
  上线前按 XBX 计算逻辑覆盖当前实现，沿用原 `factor_id`，不建立兼容双版本。上线后
  任何公式变化必须创建新的 `factor_id`，并重新编译/启用引用它的 StrategyDef。
- 一个 Runner 一个日程、一份标的池规则。不做多组件、多 Slot、权重合成器。
- 运行时查询 View，不落盘输入快照制品。
- 一期不做 Python 策略入口，不做回测引擎。
- Strategy/Trade 启动时执行可证明安全的增量 schema 迁移；V1 Strategy 表不做语义兼容，
  而是先归档到 `legacy_strategy_v1_*` 表，再由 V2 schema 建立现役表。无法识别的旧表
  继续 fail-closed，禁止静默清库。

命名和周期信号也在本文中固定：

- 用户 YAML 的 Go 类型使用 `config.Manifest`，不使用含义不明确的 `config.Config`。
- 启用前的依赖复核使用 `Compiler.VerifyDependencies`。
- 当期输入类型使用 `EvaluationInput`，不使用 `Panel`。
- 评分阶段使用 `PoolScoring`，不使用带有横截面术语色彩的 `CrossSection`。
- 不引入持久化的 `InputBarrier`；需要时使用无状态的 `ReadinessChecker` 检查当期输入是否齐备。
- 方向预算分配使用 `WeightAllocator`；不引入 `PortfolioComposer` 或跨策略合成器。
- Trade 的不可变换算回执表统一命名为 `t_logical_account_target_receipts`，不使用
  `t_logical_account_target_conversions` 或 `t_logical_account_target_resolutions`。
- 权重换算的资金分母固定为 LogicalAccount 当前启用且 Ready 成员的权益合计；不使用
  available funds、固定示例资金或单个账户权益替代它。Trade 在回执中同时保存权益来源
  时间、逐标报价时间和实际选中的成员，freshness 取全部必要输入的最老时间。

本轮文档修订统一术语、职责边界，并补充实现与验收约束：

| 原称 | 统一称呼 | 采用原因 |
| --- | --- | --- |
| `config.Config` / `Spec` | `config.Manifest` | 明确表示用户提交的版本化声明，而不是运行时服务配置 |
| `ValidateFrozenDependencies` | `Compiler.VerifyDependencies` | 表明它是在启用前验证已编译依赖，不会重新发现依赖 |
| `Panel` | `EvaluationInput` | 表达一次求值的输入，不绑定 DataFrame 或通用量化表格概念 |
| `CrossSection` | `PoolScoring` | 强调评分发生在已解析标的池内，避免把实现绑定到某种数学术语 |
| `InputBarrier` | `ReadinessChecker` | 输入完整性是无状态检查，不维护持久化屏障进度 |
| `PortfolioComposer` | `WeightAllocator` | 一期只负责方向内权重分配，不合成多个策略组合 |
| `target_conversions` / `target_resolutions` | `TargetReceipt` | 回执记录首次换算事实，不是异步解析队列或可重算结果 |

## 目标

Strategy 把一份不可变的选币配置应用到某个周期已经算好的行情和因子上，生成可追溯的
目标权重，并交给 Trade。

一期能力：

- 按 `InstrumentPoolRule` 解析当期标的池，在池内做排名和选币。
- 前置过滤、选币、后置过滤，顺序固定。
- 多头与空头可写在同一份配置里；现货不允许负权重。
- 选币数量支持固定数量和比例。
- 多因子标的池排名后加权求和。
- Live 与 Paper 共用同一套求值语义。
- 每次运行可解释、可幂等恢复。

## 非目标

- Strategy 不读取交易凭据，不提交订单，不管理成交和持仓。
- Strategy 不根据固定资金数额生成数量。
- Strategy 不直接访问交易所、网络或账户余额。
- 不拆分 FactorDef / FactorInstance / FactorBinding。同一算法不同参数继续使用不同
  `factor_id`。
- 不做跨标的派生指标（如 rank_diff）。需要时先做成普通时序因子。
- `circulating_supply` 不属于框架输入、标的池规则或内置因子字段；需要类似数据时，先
  作为独立 Factor 发布，再由 Manifest 通过 `factor_id` 引用。
- 不保存内容寻址的 MarketFrame 制品，不维护逐周期 point-in-time 成员时间线。
- 不做多 `StrategyComponent`、多 `RebalanceSlot`、`WeightMerger`。
- 不建设 Python 自定义策略、回测引擎、分布式工作流。

## 术语

| 术语 | 含义 |
| --- | --- |
| `InstrumentPoolRule` | 标的池规则。交易所、市场、报价资产、包含/排除名单、最短历史等过滤条件 |
| `InstrumentPool` | 某周期用规则解析出的候选 `instrument_id` 列表。打分和过滤都在这个集合上进行 |
| `Manifest` | 用户提交的版本化声明式 YAML 配置 |
| `EvaluationInput` | 某周期供求值器使用的完整输入：标的池成员、行情列和因子列 |
| `PoolScoring` | 在完整 `InstrumentPool` 上计算各标的的排名和加权分数 |
| `WeightAllocator` | 选币完成后，在 long/short 方向内分配目标权重的无状态步骤 |
| `ReadinessChecker` | 对单个周期检查 View、行和列是否齐备的无状态检查器 |
| `StrategyDef` | 不可变选币配置：原始 YAML、编译 JSON、hash |
| `StrategyRunner` | 一份配置的可调度实例：空间、频率、账户 |
| `StrategyResult` | 某周期已接受的权重快照 |
| `InstrumentTarget` | `instrument_id` + `target_weight` |
| `TargetReceipt` | Trade 首次接受某个目标后保存的不可变处理回执 |

`Panel` 是量化库中常见的二维或三维表格抽象，通常以时间、标的和字段作为索引。它
不是本框架的领域对象：Strategy 只在一个周期读取一行/标的，并把结果组织为
`EvaluationInput`，因此不会暴露 `Panel`、DataFrame 或类似持久化快照 API。

「解析标的池」指：用 `InstrumentPoolRule` 查询当期标的目录和 View 数据，得到
`InstrumentPool`。规则不是列表；列表要到运行时才能确定。

标的池不是 Storage 的 Subject 目录，也不是 Trade 账户的可交易品种。`markets`
只限制选币候选，不决定用哪个执行账户。

## 模块边界

```text
Collector
  -> 向 Storage 上报 DatasetPeriodCollected marker
Storage DataNode
  -> 通过同一 outbox 发布 DatasetPeriodCollected（Source View 可读）
Factor
  -> 消费 DatasetPeriodCollected
  -> 逐标的时序因子
  -> 向 Storage 上报 FactorPeriodComputed marker
Storage DataNode/View
  -> 通过 outbox 发布 ViewFactorPeriodReady（结果 View 可查询）
Strategy
  -> 解析标的池
  -> 查询当期行情与因子列
  -> 打分 / 前置过滤 / 选币 / 后置过滤 / 等权
  -> StrategyResult + outbox
Trade
  -> 按启用成员合计权益和参考价格把权重换成 quantity
  -> 现有 TargetExecutor
```

Strategy 只消费 Storage 已发布的可读事件。因子结果以 `ViewFactorPeriodReady` 为准，
因为只有它保证 Result View 可查询。Factor 模块本身不改协议。

这里要区分“谁判定完成”和“谁负责发布”：Collector/Factor 是 marker 的业务判定者和
上报者；Storage DataNode 将 marker 与结果行按同一持久化顺序提交，再由 outbox relay
实际发布 EventBus 消息。Collector/Factor 不各自维护独立事件 outbox，避免完成事件先于
结果行可读，或在重试时出现两套幂等语义。

Strategy 访问 Storage 时使用两套进程内身份：Metadata/Primary 使用
`MOOX_STORAGE_PRIMARY_AUTH_SECRET` 派生的 `storage.app_key`，DataView 使用
`MOOX_STORAGE_VIEW_AUTH_SECRET` 派生的 `storage.view_app_key`。两者不能混用，也不写入
编译产物、日志或前端响应。

SQLite 数据库升级遵循“先迁移、后严格校验、再应用 schema”的顺序。Trade 对已知的
`t_logical_accounts.c_owner_claimed_at` 缺列只执行一次 additive `ALTER TABLE`，已有行
无 owner 的代际为 `0`，已有 owner 的代际初始化为 `1`；其余列、索引、外键和检查约束仍必须与当前 schema 一致。Strategy V1
的 `source_code/view_id/trigger_bar_time` 等字段没有 V2 语义，启动时将整组旧表重命名为
`legacy_strategy_v1_*`（保留数据但不参与运行），随后由 `ApplySchema` 创建 V2 五表。
启动后的后台协调器会按 runner 锁重读归档 owner：同一 space/account 的 ENABLED V2
Runner 通过 Trade 的 Rebind owner 生命周期接口推进 `owner_generation`、清理旧 target，
但不释放 ownership 或暂停 automation，然后在归档表写入完成标记；其余（不同 account、
DISABLED 或已不存在的 Runner）均向 Trade 幂等释放旧 owner，并在归档表写入完成标记，避免每个周期重复调用 Trade。未知或
部分损坏的表不会被归档，服务保持启动失败并要求人工处理。Rebind 请求携带持久化
`rebind_key`，Trade 对同一 key 只推进一次代次；Strategy 只有在本地生命周期缓存清理
完成后才写归档完成标记。启动顺序为先完成 owner 协调，再启动 EventBus relay/ready
consumer；部署脚本先启动 Trade 并等待 `/readyz`，再启动 Strategy。

Strategy 的一次评估先为 Source View 和一个因子 Result View 建立统一的读取快照；同一
Strategy 的多个因子必须写入同一个 Result View，编译器拒绝跨多个 Result View 的组合，避免
单个 ready 事件无法携带完整的代际信息。快照记录 `View.active_index_id` 与 subject selector；
随后每次历史/当期 DataView 请求都携带对应的 `expected_active_index_id`。Storage 同时为每次
成功写入递增 `active_index_revision`；首个响应返回该 revision，后续分页请求携带
`expected_active_index_revision`，并在单次查询前后复核 revision。任一 View 在读取期间发生
A/B 索引切换或同一索引原地修订，Storage 返回 `VIEW_NOT_READY`；该 ready 消息被视为已被
更新代际 supersede，Strategy 记录失败并 ACK，等待更新代际的 ready 或显式 recalc，不能让
无限重试队列被旧 revision 永久占满。若当期返回行数超过 selector 基数则拒绝该周期，禁止
分页拼接或静默截断多个序列。

## 领域模型

### StrategyDef

不可变制品。配置变化时创建新的 `strategy_id`，不原地修改。

```text
strategy_id
name
kind = coin_selection
manifest_yaml
compiled_json
source_hash
created_at
```

`compiled_json` 在发布时生成：校验 schema、解析 `factor_id`、归一化多空
`side_weight`、冻结依赖的 Source View 与因子 Result View。运行只读编译结果。

用户 YAML 的 Go 类型统一命名为 `Manifest`，编译产物命名为 `CompiledStrategy`。
Runner 启用时调用 `Compiler.VerifyDependencies`，只核验编译产物中已经固定的 ID、状态
和 schema，不重新寻找或替换 Binding。

Factor 的 `source_hash`、输出定义和 Binding 参数属于已发布依赖的一部分。被启用 Runner
引用的 Factor 不允许原地改变公式或输出；XBX 的 Bias/Cci 仅在本期上线前按约定覆盖，
上线后任何公式修订都必须发布新的 `factor_id`，再重新编译并启用 Strategy。这样
`VerifyDependencies` 发现的仍是同一个已冻结制品，而不是“同名因子已换公式”。

运行期的 `ViewFactorPeriodReady` 同时携带每个 Binding 的 `source_hash`，并携带 Factor 计算所用的
`source_index_id/source_index_revision` 与结果 View 的 `result_index_id/result_index_revision`。
Strategy 只接受与这两个代际及 revision 一致的读取快照。
Factor 输出行的
`factor.source_hash.<factor_id>` 会随 View 行属性保存，DataView 查询返回该属性，Strategy
在读取因子值时再次核对 compiled hash；因此就绪事件、当前 View 行与已发布因子版本必须
属于同一版本，旧事件或旧行不会被误算为当前信号。

新发布的 `FactorPeriodComputed` 与 `ViewFactorPeriodReady` 中每个 Binding 必须带
`source_hash`；Storage/Strategy 对带有新代际字段的消息 fail-closed。升级兼容窗口仍允许
发布历史 v1 outbox 中没有 provenance 的 marker，避免旧队首错误阻塞整个 DataNode outbox；
这类旧消息不带 index provenance，Strategy 不会据此执行新的权重计算，需由 Factor/View
按当前制品补发一次 ready marker。

### StrategyRunner

```text
runner_id
strategy_id
space_id
source_view_id
frequency
logical_account_id
status
current_targets_json
command_sequence
last_result_id
last_error
```

一个 Strategy 可创建多个 Runner。一个执行型 Runner 最多控制一个 LogicalAccount；
观察型 Runner 不关联账户。一个启用的 LogicalAccount 只能有一个 owner Runner。

切换 Strategy 或账户前必须先停用 Runner。

### 调度

数据粒度与调仓间隔分开，但一期只允许单一间隔，没有多个 offset。

```yaml
input:
  source_view_id: crypto_spot_kline_1h
  data_frequency: 1h
schedule:
  every: 24h
```

`every` 默认等于 `data_frequency`，即每个闭合周期都调仓。若 `every` 更大，只在
`period_time` 对齐该间隔时运行（UTC 锚点）。收到未对齐周期的 ready 事件时忽略。

## 标的池

### InstrumentPoolRule

```yaml
instrument_pool:
  exchanges: [binance]
  markets: [spot]
  quote_assets: [USDT]
  include: []
  exclude: [BTC-USDT-SPOT, ETH-USDT-SPOT]
  min_history_periods: 168
```

| 字段 | 含义 |
| --- | --- |
| `exchanges` | 数据来源，对应 `series_tag` / venue，如 `binance` |
| `markets` | 候选市场，如 `spot`、`perpetual` |
| `quote_assets` | 报价资产，如 `USDT` |
| `include` | 非空时，候选只能来自该名单（仍须满足其余条件） |
| `exclude` | 从候选中去掉 |
| `min_history_periods` | 不同 `data_time` 数量下限；不足则不进入标的池 |

`exchanges` 的配置顺序也是行情路由优先级；同一 instrument 多 venue 可用时选择第一个
历史适格 venue，并写入 `debug_info`。Subject metadata 必须提供 `series_tag`；历史
Binance 元数据缺失时可由 `exchange` 推导 `venue:<exchange>`。DataView selector 和
当期行读取必须带上该 tag，不能把同一 instrument 的多 provider 序列混读。

`include` / `exclude` 使用完整 `instrument_id`，例如 `BTC-USDT-SPOT`。

多头和空头共用这一份规则。需要现货多头与合约空头分池时，用两个 Runner、两个
LogicalAccount，不在一期做侧边覆盖。

### 解析

```text
候选 = 标的目录中满足 exchanges/markets/quote_assets/include/exclude 的 instrument
适格 = 候选中历史长度 >= min_history_periods 的 instrument
InstrumentPool = 适格集合（按 instrument_id 升序）
```

适格只看历史长度。历史不足的新上市标的正常排除，不构成失败，记入 `debug_info`。

当期数据是否齐全不改变池的成员：池内标的缺少当期行或必需列，属于数据链路异常。
默认 `readiness.policy = strict`：存在缺数据标的或必需 View 未齐时跳过本期，只更新
Runner `last_error`（含缺失标的列表），不写 `StrategyResult`，不发事件。View 已可读但
当前池缺行/缺列属于本次事件的终态 skip（ACK），后续 View ready 事件仍可再次尝试该周期；
View 尚未完成或 Storage 暂时不可用则 RETRY，避免把同一 broker 消息无限保活。标的池排名
对样本变化敏感，不能默认静默缩小样本。

`exclude` 策略可在后续版本增加；一期只实现 `strict`。

标的池列表随当次 `StrategyResult` 的 `debug_info` 落库，不单独建
`t_universe_snapshots` 一类表。下次运行再解析一遍。

## 数据输入

标的池选币只使用**当期**每个标的一行：行情列加已计算的因子列。Strategy 不在模块内
做 rolling 窗口；lookback 由 Factor 完成。

运行时把这些数据组织为 `EvaluationInput`。它表达“供一次策略求值使用的输入”，不把
类型绑定到表格库或持久化快照概念：

```text
EvaluationInput
  period
  instruments[]
    instrument
    values[field_or_factor_id]
```

```text
instrument_id       close    bias_20    quote_volume_mean_w288
SOL-USDT-SPOT       ...      ...        ...
DOGE-USDT-SPOT      ...      ...        ...
```

唯一键为 `instrument_id`。列必须能对应到编译后的 Field 或 `factor_id` 输出。
不允许未来数据。查询失败或列缺失按 `strict` 跳过本期。

输入 hash 包含：Strategy hash、compiled hash、标的池列表、当期 `EvaluationInput` 内容。
上游事件 ID 只做来源记录，不参与 hash。

## 标准选币流水线

```text
InstrumentPoolRule
  -> ResolveInstrumentPool
  -> LoadEvaluationInput
  -> PoolScoring
  -> PreFilter
  -> Select
  -> PostFilter
  -> SideWeight
  -> StrategyResult
  -> Outbox
```

### 打分

每个因子先在**未做前置过滤**的标的池上做排名，再乘归一化权重求和。过滤改变
可选集合，不改变本周期已经算好的名次。

```text
score = sum(rank(metric_i, direction_i) * normalized_weight_i)
```

排名使用 `method=min`：相同值共享最小 rank。最终选币按 `(score, instrument_id)`
稳定排序后截取，既保留并列含义，也不会因并列超选。

`direction: ascending` 表示因子值越小 rank 越靠前（多头常见于「超卖」类）；
`descending` 相反。

### 过滤

```yaml
filters:
  - phase: pre
    factor_id: quote_volume_mean_w288
    value_type: percentile
    op: gte
    value: "0.2"
```

| 字段 | 取值 |
| --- | --- |
| `phase` | `pre` 或 `post` |
| `value_type` | `value` / `percentile` |
| `op` | `lt` / `lte` / `gt` / `gte` / `eq` |

过滤规则写在 `long:` / `short:` 块内，天然作用于所在方向，没有独立的 `side` 字段。
`percentile` 是标的池内的分位（0 到 1）；按名次筛选用 `selection.mode: count`
表达，不提供 `value_type: rank`。

同阶段多条规则 AND。未知字段、NaN 比较、类型不匹配在编译或运行时失败，不静默忽略。

### 选币

```text
count       固定数量
fraction    标的池（经过前置过滤后）的比例
```

比例向下取整；比例大于零且候选非空时至少选 1 个。不实现 `rank_range`、`all`、
`match_long`。

后置过滤可能使入选数量少于 selection 请求值。这是允许的：先按规则截取，再剔除
不满足后置条件的标的，不回补。

### 方向权重

入选标的在方向内等权：

```text
instrument weight = 归一化后的 side_weight / 该方向最终入选数量
```

多头为正，空头为负。只有 long 时，多头权重和为 1。多空都启用时，按 `side_weight`
归一化后分配，例如 long 0.5 / short 0.5 则多头和为 +0.5、空头和为 -0.5。
`side_weight` 为 0 或省略该侧，表示该方向不选。

Spot 标的不允许负权重；`instrument_pool.markets` 仅含 `spot` 时，编译期拒绝空头。
未出现在 FULL 目标中的旧标的表示零权重。

方向内等权意味着同方向所有权重相等，不会产生需要清理的尘埃权重，因此没有
`dust_weight` 配置。

`gross = sum(abs(weight))`，`net = sum(weight)`。gross 不必等于 1；未分配部分视为
现金。杠杆与保证金上限由 Trade 的 LogicalAccount 风控判断。

```yaml
api_version: moox.strategy/v2
kind: coin_selection

input:

  data_frequency: 1h
  factors:
    - factor_id: min_max_w288
    - factor_id: quote_volume_mean_w288
    - factor_id: zf_mean_q_w288
      output: value

instrument_pool:
  exchanges: [binance]
  markets: [spot]
  quote_assets: [USDT]
  include: []
  exclude: [BTC-USDT-SPOT, ETH-USDT-SPOT]
  min_history_periods: 168

  every: 24h

readiness:
  policy: strict

long:
  side_weight: "1"
  scores:
    - factor_id: min_max_w288
      direction: ascending
      weight: "1"
  filters:

    - phase: post

```

发布时保存原始 YAML 和编译 JSON。编译 JSON 中的 `factor_id` 必须指向已启用的
Factor 及其在该 `source_view_id` / frequency 上的 enabled Binding。

`input.factors[]` 可以只写 `factor_id`，此时被引用 Factor 必须恰好声明一个 output；
多 output Factor 必须显式写 `output`，编译器会冻结该 output 对应的 Result View 列，
运行时不会猜列名。这样同一个 FactorDef 可以通过不同的 FactorBinding/参数输出被多个
策略复用，而不把输出选择隐含在策略排序规则里。

## 周期完成与全市场输入

全市场选币不等待一个由 Strategy 自己维护的“全市场 K 线完成”计数器，也不把部分
标的静默缩小后继续排名。周期完成由数据链路按 View 发布，Strategy 在读取时执行
严格的完整性检查：

| 事件 | 完成判定/上报者 | Storage 实际发布时机 | 消费者 |
| --- | --- | --- | --- |
| `DatasetPeriodCollected` | Collector -> Storage marker | Source View 对应周期的行情行、元数据和完成标记已提交且可查询 | Factor |
| `ViewFactorPeriodReady` | Factor -> Storage marker | Factor 已完成该周期计算，Result View 的所有结果行已提交且可查询 | Strategy |

两类事件都必须携带 `space_id`、`dataset_id/view_id`、`frequency`、`period_time`、
`message_id` 和可追溯的 `source_event_id`。`ViewFactorPeriodReady` 还要携带结果 View
标识以及每个 binding 的 `complete/degraded/error` 状态；它表达“这个 View 可读”，不
表达“所有 Strategy 依赖都已齐备”。

Strategy 使用固定 pull durable 消费 ready 事件。处理结果遵循以下协议：

| 结果 | Broker 动作 | inbox |
| --- | --- | --- |
| View 未完成、依赖暂缺、Storage/SQLite 暂时错误 | `NAK`/延迟重试 | 不写入 processed |
| View 可读但池内缺行、缺列、非数值等本期终态异常 | 记录 `last_error` 后 `ACK` | 写入 processed |
| 求值成功、hold、rebalance、无匹配 Runner | `ACK` | 写入 processed |
| 非法协议、不可恢复配置或 owner 冲突 | `TERM` | 写入 processed 或 quarantine |

同一 `message_id` 的 inbox 记录只在该消息对应的全部 Runner 得到终态后写入；任一
Runner 需要重试时，不能提前标记整条消息已处理。

`VerifyDependencies` 只在 ready 事件与 Runner 的 Source/Result View 匹配后执行。
Factor/Binding/View 的明确业务错误（例如已删除对象、非法 schema 或权限拒绝）标记为
永久依赖不匹配并 ACK；RPC 传输错误、`INNER_ERR`、View 尚未生成 active index 等暂态
错误返回 NAK/延迟重试，避免无关 View 的事件被错误阻塞。

`DatasetPeriodCollected` 是上游“行情周期已收齐”信号，粒度为 dataset/view +
`period_time`，不是全市场单独的全局状态。Factor 收到后按自己的历史窗口计算各标的
时序因子，只有在结果 View 可读之后才发布 `ViewFactorPeriodReady`。因此不再额外引入
一个语义重复的 `FactorPeriodCollected` 作为 Strategy 的触发协议；如果 Factor 内部
需要记录计算完成日志，可以使用同一事件的内部观测字段，但不得早于 Result View 可读
时机。

Strategy 收到任意相关 `ViewFactorPeriodReady` 后，按 Manifest 解析完整
`InstrumentPool`，一次性加载所有标的的当期行情和因子列。`readiness.policy: strict`
就是全市场完整性检查：View 未完成或依赖暂缺时重试；View 已可读但缺少任一池内标的、
必需列或出现非数值时，整期终态跳过并记录错误，不产生部分样本的排名结果。事件由
Storage DataNode outbox 通过 NATS JetStream 发布，允许
重复投递；`t_strategy_inbox` 以 `message_id` 去重，输入内容 hash 决定同周期是否需要
latest-wins 重算。

## 触发

Runner 编译依赖为：Source View + 一个承载全部因子输出的 Result View。

收到相关 `ViewFactorPeriodReady`（必要时同时确认 Source View 已就绪）后：

1. 若 `period_time` 未对齐 `schedule.every`，忽略。
2. 若该周期所需 View 未齐，等待后续事件；不阻塞下一周期。
3. 齐备则求值：input hash 与已有 Result 相同则幂等返回；不同则覆盖并再发目标。
4. 某周期始终不齐则永不跑该期，只在 Runner 上保留最近错误；新周期独立。

不单独记录就绪进度。「ready」的含义就是 View 可查询，因此收到相关事件后直接
通过无状态 `ReadinessChecker` 加载当期 `EvaluationInput`：View 未完成返回 RETRY；代际
已被更新的 ready 返回 superseded 并 ACK，
View 已可读但缺行缺列返回终态 skip 并 ACK。这里的 checker 只返回本次检查结果，不持有跨周期 barrier
状态，也不对应一张 readiness 表。
个人系统事件量小，
重复查询的成本可以忽略。`t_strategy_inbox` 只做 `message_id` 去重。因子结果 View 的
`degraded` 状态还会携带 binding 的失败/跳过 subject 列表；Strategy 在加载出本期实际
池后，同时按 `subject_id` 和 `instrument_id` 判断这些 subject 是否落入池内。池外
subject 的终态异常不阻断本期，池内 subject 仍严格跳过；没有可用于映射的当期池时
保持保守阻断，避免把 subject ID 与 instrument ID 的偶然同名当作完整性证明。

不引入 `recalc_revision` 或 worker lease；Runner 进程内按 Runner 串行即可。Trade
使用由 LogicalAccount 持久化的单调 `owner_generation` 生命周期代次作为跨进程
目标事件栅栏，不使用 wall-clock 比较。
同一周期因子重算导致 `EvaluationInput` 变化时，按 latest-wins 覆盖，与 Factor 一致。

## 输出与 Trade

策略输出：

```text
StrategyEvaluation
  action = hold | rebalance
  weights[]
    instrument_id
    target_weight
  debug_info
```

`debug_info` 是 JSON object，记录本次运行的解释信息：当期标的池、历史不足被排除的
标的（新上市）、各阶段过滤剔除数量等。它只用于事后解释和前端展示，不参与 hash、
hold 判断或任何下游决策。缺少当期数据的标的在 `strict` 下直接跳过本期、不产生
输出，因此不出现在这里，只记入 Runner `last_error` 和日志。

- `rebalance` 用本周期权重完整替换理论目标。空列表表示全部归零。
- 规范权重字符串与当前 `current_targets_json` 完全相同则视为 `hold`：不增加
  sequence，不发事件。
- 一次运行一个 FULL 快照，没有 Slot 中间组合。

Runner 从停用重新启用时视为新的活动生命周期：Trade 在重新 Claim owner 时清理 live
target，Strategy 同时清理缓存目标，下一次成功周期必须重新发出 `rebalance`。历史
`StrategyResult` 和 Trade 的 `TargetReceipt` 不删除；这样既不会恢复旧策略目标，也不会
因清理 Trade target 后把首个新周期误判为 `hold`。
Trade 还持久化 owner lifecycle 的 `owner_generation`，Strategy 在目标事件中携带
同一代次；Trade 只接受当前代次，防止 broker 延迟投递把上一生命周期的目标重新写回，
且不受各服务系统时钟偏差影响。Strategy 读取 generation 时同时校验当前
`owner_runner_id` 仍是本 Runner；在提交评估后再次执行同样校验。若计算期间发生
disable/enable、owner rebind 或外部转移，则原子清空本地 live target、删除尚未发布的
outbox 并让 ready 消息重试。即使失效操作暂时失败，重投也会比较结果 generation，强制
生成新的 `rebalance`，避免记录一次无法被 Trade 接受的 `hold`。

发给 Trade 的事件使用独立的 `LogicalAccountTargetWeightRequested`（subject
`moox.trade.target.weight_requested.v1`），不复用旧数量事件的消息类型或字段号：

```text
LogicalAccountTargetWeightRequested
  target_id
  runner_id
  logical_account_id
  command_sequence
  owner_generation
  signal_time
  targets[]
    instrument_id
    target_weight
```

权重使用规范十进制定点字符串。Trade 的新 durable 只消费该权重 subject；旧的
`LogicalAccountTargetRequested` 数量事件即使继续注册，也不进入新的 Strategy→Trade
链路，避免未确认的旧消息被按权重解释。

Trade 在消费时按当时权威权益和参考价格换算：

```text
target_notional = equity * target_weight
raw_quantity    = target_notional / reference_price
```

同一 `target_id` 重投必须返回第一次换算结果，不得用新价格或新权益重算。换算在现有
事件消费者内完成，不引入独立 PENDING resolver、CAS 或 SUPERSEDED 状态机。量化、
合约乘数和容量检查仍由现有 TargetExecutor 在选好执行账户之后处理。

LogicalAccount 的权益聚合以实际资金源为去重边界：LIVE 成员使用
`exchange + environment + credential_secret_id` 识别同一资金源，Spot/Swap 账户即使
建模为不同成员也只计入一次；PAPER 成员按账户独立计入。成员必须 enabled、ready 且
权益来源在 freshness 窗口内，否则本次换算失败并等待下一次目标重试。

Trade 为每个首次接受的 `target_id` 写一条不可变 `TargetReceipt`，保存规范请求 hash、
首次采用的权益与参考价格，以及换算后的 raw quantity。对应表为
`t_logical_account_target_receipts`。同一 `target_id` 且请求 hash 相同的重投直接复用
回执；hash 不同视为冲突。已经被更新目标覆盖的旧 target 重投时只返回原回执，不把
旧目标重新写回当前目标。

这张表的职责是“已接受目标的第一次换算事实”审计和幂等重放，不是异步解析器队列：
不增加 `PENDING`、`RESOLVED`、`SUPERSEDED` 状态，也不承担当前账户持仓。名称中的
`receipt` 强调它是不可变回执，避免与容易被误解为可重算结果的 conversion/resolution
概念混用。

```text
TargetReceipt
  target_id
  logical_account_id
  runner_id
  command_sequence
  request_hash
  receipt
    signal_time
    weights[]
    equity + equity_source_time
    reference_prices[]
    quantity_targets[]
    accepted_at
```

LogicalAccount 成员必须能交易目标中的市场与结算资产。选币池包含某市场，不自动
意味着账户能执行该市场。

停用 Runner 时 Strategy 先提交本地 `DISABLED`，再调用 Trade 释放 owner。Trade release
会暂停自动化并留下 release-time fence；Strategy 在启动和周期任务中重复调用 release，
使崩溃或短暂网络故障最终收敛到“无 owner、无活动自动化”。

## 持久化

```text
t_strategies
  不可变 StrategyDef、YAML、编译 JSON、hash

t_strategy_runners
  Runner 配置、状态、当前权重、账户、sequence

t_strategy_results
  每次运行的 action、权重、debug_info、input hash；同周期 latest-wins 仍保留历史行，
  用 Runner.last_result_id 指向当前活动结果

t_strategy_outbox
  待发布 LogicalAccountTargetWeightRequested

t_strategy_inbox
  已处理的 View Ready message_id

t_logical_account_target_receipts（Trade）
  已接受 target 的不可变 TargetReceipt，用于重投幂等和换算审计
```

Strategy 业务事实仍是前四张表；inbox 只做事件去重。`TargetReceipt` 属于 Trade，
不增加 Strategy 的持久化职责。

`current_targets_json` 保存最新已接受的 FULL 权重，用于 hold 判断、展示和下游事件，
不回传给求值器，也不是账户实际持仓。

`command_sequence` 是 Runner 的持久单调序列。停用后重新启用、切换 StrategyDef 或重新
绑定 LogicalAccount 都不能把它重置为已经使用过的值；否则 Trade 会把新目标误判为旧
目标，TargetReceipt 也可能发生唯一键冲突。若未来确实需要从 1 开始，必须增加持久化
`runner_generation` 并将其贯穿目标事件、当前目标和回执；一期不引入 generation。

ready 处理器不依赖一个覆盖所有存储能力的大 `Repository`。它按调用方拆成两个窄接口：

```text
InboxStore
  IsProcessed
  MarkProcessed

EvaluationStore
  ListTriggeredRunners
  CommitEvaluation
  RecordFailure
```

`ListTriggeredRunners` 一次返回 Runner 及其最近成功周期；`CommitEvaluation` 在事务内
再次执行旧周期检查，并原子维护 Result、Runner 和 outbox。

StrategyResult 逻辑键：

```text
(runner_id, strategy_id, period_time)
```

Runner 已绑定具体 LogicalAccount（自身是 live 或 paper），不需要 V1 的 `namespace`
维度。

相同键且相同 input hash 返回已有结果。相同键但 hash 不同视为当期数据已更新（与
Factor 的 latest-wins 一致）：写入新 Result、增加 sequence、再发 outbox。失败或
输入不齐不写 Result，只更新 `last_error`。

一次成功 `rebalance` 在同一 SQLite 事务中：插入 Result、更新 Runner 目标与
sequence、写 outbox。任一步失败全部回滚。

## 状态

Runner：`DISABLED` / `ENABLED`。启用前校验 Strategy 存在、引用的 Factor 与 Binding
已启用、View 与频率可用、标的池规则可解析、账户归属双向一致。

求值器是无状态纯函数：输入为编译配置和当期 `EvaluationInput`；输出为权重。Live 与 Paper
只是账户与执行环境不同。

## 可观测性

最少指标：`strategy_runs_total{status}`、`strategy_run_duration_seconds`、
`strategy_pool_instruments`、`strategy_selected_instruments{side}`、
`strategy_target_gross_weight`、`strategy_outbox_pending`。

日志字段：`space_id`、`runner_id`、`period_time`、`result_id`、`trace_id`。

## 安全与确定性

- 配置拒绝未知字段。
- decimal、时间、`instrument_id` 在 Go 边界规范化。
- 排序始终带 `instrument_id` 次级键。
- 不使用进程内随机数决定选币。
- 不从源码推断数据依赖；列和因子在发布时声明并编译。

## 交付顺序

1. 配置 schema、编译与校验（`InstrumentPoolRule`、因子引用、过滤、选币）。
2. 解析标的池，加载当期 `EvaluationInput`。
3. 求值器：打分、前置过滤、选币、后置过滤、等权。
4. 消费 `ViewFactorPeriodReady`，inbox 去重，对齐 `schedule.every`。
5. Result / outbox 改为权重；Trade 消费时换算 quantity。
6. 管理台与文档。
