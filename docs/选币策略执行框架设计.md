# MooX 选币策略执行框架设计

## 文档状态

本文描述 Strategy 模块的目标架构，不代表当前代码已经具备全部能力。实施完成前，
`策略模块架构设计` 和 `Strategy Python 策略接入手册` 继续说明当前
`run-once + quantity` 契约；本文是后续重构的设计基线。

本文固定以下已确认决策：

- Strategy 最终输出目标权重，不输出交易数量。
- Trade 首次幂等接受权重目标后，由异步 resolver 按账户权益和参考价格冻结换算为完整 raw quantity 目标。
- Strategy 支持多标的横截面计算、多因子组合、过滤、多空分离、选币、多个调仓轮次和多个子策略合并。
- 用户选币范围由显式 `UniverseSpec` 表达，不使用含糊的 `is_use_spot` 布尔值。
- Factor 拆分为 `FactorDef`、`FactorInstance` 和 `FactorBinding`。
- `bias`、`cci` 等导入因子不增加来源前缀。本次尚未投产的初始 schema 迁移直接清理旧定义、绑定和结果，以新公式创建 revision 1；此后公式变化一律创建新 revision。
- `circulating_supply` 不是框架概念。框架只处理普通输入列和因子依赖。
- Collector/Factor 判定周期终态，Storage 负责持久化 Marker 并通过 outbox 发布事件。

## 目标

Strategy 模块负责把一个不可变策略定义应用到指定周期的完整、多标的数据快照，生成可追溯的目标权重，并将其可靠交给 Trade。

目标能力包括：

- 同一时点跨多个标的排名、过滤和选币。
- 多头与空头分别配置因子、过滤、选币数量和权重。
- 支持固定数量、比例、排名区间、全选和空头跟随多头数量。
- 支持多因子横截面排名后加权求和。
- 支持前置过滤、选币、后置过滤的明确执行顺序。
- 支持多个 `StrategyComponent` 和多个 `RebalanceSlot` 的权重合并。
- 支持现货、永续等用户选币范围，但不把市场范围与交易路由混为一谈。
- Live、Paper 和 Backtest 复用相同输入快照、策略求值和权重合并语义。
- 每次运行可解释、可重放、可幂等恢复。

## 非目标

- Strategy 不读取交易凭据，不提交订单，不管理成交和持仓事实。
- Strategy 不根据固定资金数额生成数量，框架中不存在“2000U 模式”。
- Strategy 不直接访问交易所、网络、账户余额或本地任意文件。
- Factor 不承担跨标的横截面计算，也不建立 Factor DAG。
- 不复制参考项目的源码、动态模块装载方式、tuple 配置或本地完成标记文件。
- 不建设分布式工作流、全局 exactly-once 或跨集群协调系统。

## 术语

| 术语 | 含义 |
| --- | --- |
| `MarketFrame` | `StrategyInputSnapshot` 内的规范化二维数据载荷，唯一键为 `(time, instrument_id)` |
| `StrategyInputSnapshot` | 某次 StrategyRun 实际使用的不可变输入信封，包含 manifest、可用性时间线和 MarketFrame 制品引用 |
| `StrategyTrigger` | 消费 View Ready 事件并决定是否创建运行的组件 |
| `DataReadyCheck` | StrategyTrigger 内部的数据齐备判断 |
| `StrategyComponent` | Runner 内一个独立的选币子策略 |
| `RebalanceSlot` | 按固定周期和 offset 独立更新的一份子目标 |
| `WeightMerger` | 合并组件和调仓轮次目标权重的纯计算组件 |
| `StrategyWeightTarget` | Strategy 最终接受并交给 Trade 的完整权重快照 |

`Panel` 是统计分析中的常见概念，表示多标的、多时间的数据。本文仅在解释外部概念时使用 Panel，代码和协议统一使用 `MarketFrame`。

## 模块边界

```text
Collector
  -> Report DatasetPeriodCollected marker
Storage
  -> DatasetPeriodCollected
  -> ViewSourcePeriodReady
Factor
  -> 逐标的时序因子计算
  -> Report FactorPeriodComputed marker
Storage
  -> FactorPeriodComputed
  -> ViewFactorPeriodReady
Strategy
  -> StrategyTrigger
  -> UniverseSnapshot
  -> MarketFrame
  -> StrategyInputSnapshot
  -> Filter / Score / Select / Weight
  -> RebalanceSlot
  -> WeightMerger
  -> StrategyWeightTarget
Trade
  -> 权益和价格冻结估值
  -> FULL raw quantity target
  -> TargetExecutor
```

Strategy 只消费 Storage 发布的可读事件。`FactorPeriodComputed` 表示结果行已写入结果 Dataset，但 Strategy 等待 `ViewFactorPeriodReady`，因为只有后者保证结果 View 已经可查询。

## Factor 依赖模型

### 三层模型

```text
FactorDef 1 -> N FactorInstance 1 -> N FactorBinding
算法定义          参数实例               数据绑定
```

`FactorDef` 是不可变算法版本：

```text
factor_def_id
revision
display_name
source_code
source_hash
entrypoint
input_columns
output_schema
param_schema
lookback_spec
state = draft | published | retired
```

这里的 `state` 只表示制品发布生命周期，不表示是否参与执行。发布后的 revision 不可修改；是否运行由 FactorInstance 和 FactorBinding 控制。

`FactorInstance` 是一组确定参数：

```text
factor_instance_id
factor_def_id
factor_def_revision
params_json
params_hash
lookback_periods
state = disabled | enabled | cleanup_pending
```

`factor_instance_id` 使用显式、业务可读的 ID，并包含定义 revision，例如
`bias_r1_w20`。这样算法升级后可以创建 `bias_r2_w20`，不会覆盖旧实例。实例唯一约束为：

```text
(factor_def_id, factor_def_revision, params_hash)
```

`FactorBinding` 负责将实例绑定到输入 View 和运行频率：

```text
binding_id
factor_instance_id
space_id
source_view_id
frequency
subject_scope
result_dataset_id
result_view_id
state
```

Binding 的自然唯一约束为：

```text
(factor_instance_id, space_id, source_view_id, frequency)
```

物理结果列由实例 ID 生成，例如 `bias_r1_w20__value`。FactorDef 不能直接生成结果列，否则同一算法的不同参数或不同算法 revision 会发生列冲突。

### 参数与 Lookback

Lookback 只支持受限规则，不执行任意公式字符串：

```text
constant(periods)
affine(param, multiplier, offset)
```

首批 12 个 FactorDef 的规则为：

| FactorDef | Lookback |
| --- | --- |
| `bias`、`min_max`、`quote_volume_mean` | `w` |
| `bias_q`、`cci`、`quote_volume_mean_q`、`volume_mean_q`、`zf_mean_q` | `2w - 1` |
| `zf_std` | `w + 1` |
| `zf_abs_mean` | `2w` |
| `zscore_abs_mean_q` | `3w - 2` |
| `circulating_mcap` | `1` |

12 个文件导入为 12 个 FactorDef。示例策略配置只决定需要解析哪些 FactorInstance，不能反向决定框架固定创建多少实例。

Factor worker 收到包含多个 `series_tag` 的 Frame 时，必须先按 `series_tag` 分组、组内按时间排序，再分别执行 rolling 计算；任何窗口都不得跨 instrument 串联。

### 实例解析

策略作者使用逻辑引用：

```yaml
factor:
  factor_def_id: bias
  params:
    window: 20
```

策略发布流程负责：

1. 查询已发布 FactorDef revision。
2. 应用参数默认值并严格校验 schema。
3. 规范化参数 JSON 并计算 hash。
4. 查找或幂等创建 `bias_r1_w20`。
5. 将编译后的策略配置固定到 FactorInstance ID、Def revision 和 source hash。

运行时不创建或修改 FactorInstance。

## Strategy 领域模型

### StrategyDef

`StrategyDef` 是不可变执行制品：

```text
strategy_id
revision
kind = coin_selection | python
manifest_yaml
source_code
source_hash
state = draft | published | retired
created_at
```

`state` 同样只表示 StrategyDef 制品生命周期。Runner 只能引用 `published` revision；发布后的 manifest、源码和 hash 不可原地修改。

标准选币策略使用内置 `coin_selection` evaluator 和强类型配置。高级策略可使用 Python evaluator，但必须接收相同的 `StrategyInputSnapshot` 并输出相同的权重契约。

### StrategyRunner

Runner 是一个可调度、可执行实例：

```text
runner_id
strategy_id
strategy_revision
space_id
logical_account_id
universe_spec
input_spec
components
readiness_policy
status
compiled_config_hash
command_sequence
```

一个 Runner 可以包含多个 StrategyComponent。一个启用的 LogicalAccount 只能由一个 Runner 控制，避免多个 Runner 同时覆盖 FULL 权重目标。

### UniverseSpec

用户选币范围使用显式结构：

```yaml
universe:
  exchanges: [binance]
  markets: [spot, perpetual]
  quote_assets: [USDT]
  include: []
  exclude: [BTC-USDT-SPOT, ETH-USDT-SPOT]
  min_history_periods: 168
  require_trading_status: true
```

`markets` 只决定候选标的范围，不决定 Trade 使用哪个执行账户。选中结果包含完整规范化 `instrument_id`，Trade 再校验 LogicalAccount 是否具备对应执行能力。

### StrategyComponent

```text
component_id
component_weight
universe_override
schedule
derived_metrics
long_side
short_side
```

组件权重是相对权重。配置编译时对所有启用组件做确定性归一化，并将归一化结果写入 compiled config，运行时不重复解释原始值。

### 调度

调度必须分开表达数据粒度、触发周期和 offset：

```yaml
input:
  data_frequency: 1h
schedule:
  every: 24h
  offsets: [9h, 21h]
  anchor_time: "1970-01-01T00:00:00Z"
```

每个 offset 对应一个 RebalanceSlot。Slot 到点时只更新自己的权重快照，其他 Slot 保留上次已接受目标，随后由 WeightMerger 合并全部 Slot。Slot 不自动过期；它只会在下一次到期求值时被替换，或由显式 `clear` 清空。这样 `hold` 不会因后台 TTL 删除而偷偷改变组合。

## 数据齐备与触发

### 不等待抽象的“全市场”

完整性由本次 `UniverseSnapshot` 定义，而不是由交易所全部 symbol 的绝对集合定义。

```text
candidate instruments = UniverseSpec 在 period_time 的解析结果
required views       = compiled input dependencies
ready views          = 已收到并持久化的 View Ready 事件
```

`StrategyTrigger` 以如下 key 收敛状态：

```text
(runner_id, strategy_revision, compiled_dependency_hash, frequency, period_time)
```

`compiled_dependency_hash` 固定本 revision 的 View、Dataset、Field、FactorInstance 和 lookback 集合，防止同一周期切换策略版本后误用旧 readiness。就绪记录只收敛上游事件；达到条件后，异步协调器解析并冻结 UniverseSnapshot，再创建 StrategyRun。

当所有 required views 对 candidate instruments 达到终态后，协调器加载 MarketFrame。历史长度小于 `min_history_periods` 的标的归类为 `ineligible_instruments`，正常排除且不触发 strict 失败；本应具备历史但缺少当前周期或必需列的标的才归类为 `missing_instruments`。随后创建不可变 `StrategyInputSnapshot` 和 StrategyRun。

### 上游事件

事件含义固定为：

| 事件 | 判定者 | 实际发布者 | 含义 |
| --- | --- | --- | --- |
| `DatasetPeriodCollected` | Collector | Storage outbox | 外部数据采集进入终态 |
| `ViewSourcePeriodReady` | Storage View | Storage outbox | 原始数据 View 可查询 |
| `FactorPeriodComputed` | Factor | Storage outbox | 因子结果 Dataset 写入完成 |
| `ViewFactorPeriodReady` | Storage View | Storage outbox | 因子结果 View 可查询 |

不新增 `FactorPeriodCollected`。Factor 是计算者，不是采集者。

FactorDef/Instance 拆分后，`FactorBindingPeriodState` 使用：

```text
binding_id
factor_def_id
factor_instance_id
status
skipped_subjects
failed_subjects
```

### 缺失数据策略

Runner 显式配置：

```text
strict        任一必需 View 或适格标的缺失时跳过本次运行
exclude       排除缺失标的，但记录缺失集合后继续
```

默认使用 `strict`。横截面排名对 universe 变化敏感，不能默认静默缩小样本。

达到 deadline 仍未齐备时，运行记录为 `SKIPPED_INCOMPLETE_INPUT`，不得继续等待并阻塞后续周期。

## MarketFrame

MarketFrame 是规范化多标的时序表：

```text
time                  instrument_id       close    bias_r1_w20__value
2026-08-29T10:00:00Z  BTC-USDT-SPOT       ...      ...
2026-08-29T10:00:00Z  ETH-USDT-SPOT       ...      ...
2026-08-29T11:00:00Z  BTC-USDT-SPOT       ...      ...
2026-08-29T11:00:00Z  ETH-USDT-SPOT       ...      ...
```

约束：

- 唯一键为 `(time, instrument_id)`。
- `time` 按周期递增，同一周期内按 `instrument_id` 升序。
- `history_periods` 表示不同时间点数量，不等于总行数。
- 每个输入列必须对应编译后的 Field 或 FactorInstance。
- 不允许重复键、未来数据或超出快照 watermark 的值。
- 不足 `min_history_periods` 的新上市标的属于不适格，不属于数据故障。

### StrategyInputSnapshot

```text
snapshot_id
runner_id
period_time
frequency
universe_snapshot_id
expected_instruments
included_instruments
ineligible_instruments
missing_instruments
columns
history_start
history_end
data_watermark
source_event_ids
factor_revisions
frame_hash
artifact_uri
artifact_size
artifact_encoding
availability_timeline
status
```

`StrategyInputSnapshot` 是正式领域契约，`MarketFrame` 是其中的数据载荷。Frame 以规范列顺序、规范 decimal 和稳定行序编码为 NDJSON，再使用 gzip 写入受控、内容寻址的不可变快照目录；文件名含 `frame_hash`，写入使用临时文件加原子 rename。SQLite 保存 manifest、URI、hash、字节数、编码和保留期。普通可变 View 引用不能代替快照制品，否则只能发现数据变化，无法重放原输入。

`availability_timeline` 记录历史窗口内每个 period 的 point-in-time subject membership 和列可用性。历史横截面排名必须使用该时点实际存在且适格的标的，不能用当前 Universe 回填历史，以免产生幸存者偏差。

## 标准选币流水线

固定执行顺序：

```text
Universe
  -> PointInTimeAvailability
  -> DerivedMetricAndMetricRank
  -> CrossSectionScore
  -> PreFilter
  -> Select
  -> PostFilter
  -> SideWeight
  -> RebalanceSlot
  -> WeightMerger
  -> StrategyWeightTarget
```

### DerivedMetric

逐标的滚动因子由 Factor 模块计算。跨标的派生指标留在 Strategy：

```yaml
derived_metrics:
  - metric_id: qvm_rank_diff
    operator: cross_section_rank_diff
    input:
      factor_def_id: quote_volume_mean
      params: {window: 1608}
    window: 1608
    market_scope: spot
```

第一版注册以下确定性 operator：

- `cross_section_rank`
- `cross_section_rank_diff`
- `cross_section_rank_bias`
- `cross_section_rank_pct_change`

这些 operator 先按 `availability_timeline` 在每个历史时点的适格 universe 上做横截面排名，再沿每个 instrument 的时间序列进行 diff、rolling mean 比值或 pct change。它们是 Strategy 的横截面特征，不注册成 FactorDef。

### FilterRule

```yaml
filters:
  - phase: pre
    side: short
    metric: quote_volume_mean_w288
    value_type: percentile
    op: lt
    value: "0.2"
```

支持：

- `value_type`: `value | rank | percentile`
- `op`: `lt | lte | gt | gte | eq`
- `phase`: `pre | post`
- `side`: `long | short | both`

同阶段多条规则使用 AND。未知 operator、NaN 比较和类型不匹配必须在编译或运行校验中失败，不能静默忽略。

### ScoreRule

每个因子先在未执行 pre-filter 的适格 universe 上做横截面排名，再乘归一化权重求和；完成 score 后才执行 pre-filter。这与参考选币框架的排名语义一致：过滤改变可选集合，但不改变本周期已经计算好的因子名次。

```text
score = sum(rank(metric_i, direction_i) * normalized_weight_i)
```

因子和过滤指标的排名使用 `method=min` 等价语义，相同值共享最小 rank。最终选币另按 `(score, instrument_id)` 稳定排序并截取精确数量，因此既保留指标并列含义，也不会因并列而超选。

### SelectionRule

```text
count       固定数量
fraction    候选集合比例
rank_range  排名区间
all         全部候选
match_long  空头数量等于本组件最终多头数量
```

区间统一使用左闭右开 `[start, end)`。比例转换数量时使用向下取整，但只要比例大于零且候选非空，至少选择一个标的。

### SideWeight

入选标的在方向内默认等权：

```text
instrument weight
  = side weight
  / selected instrument count
```

这里产出的是 Slot 内部归一权重，不包含 component 或 slot 权重。多头为正，空头为负。Spot 标的不允许负权重。遗漏标的在 FULL 目标中表示零权重。

## WeightMerger

WeightMerger 是纯函数，输入全部 RebalanceSlot 的内部归一权重，输出按 instrument_id 聚合的最终权重。

处理顺序：

1. 读取每个 Slot 最近一次已接受目标；未运行过或显式清空的 Slot 贡献为零。
2. 按 component 的编译归一权重和静态 slot share 各应用一次。`slot share = 1 / configured slot count`，不随当前有结果的 Slot 数变化。
3. 对相同 instrument_id 求和。
4. 删除绝对值低于配置阈值的尘埃权重。
5. 校验 decimal 有限、instrument 不重复和 Spot 非负等结构约束。
6. 按 instrument_id 排序并生成规范十进制字符串。

```text
gross = sum(abs(weight))
net   = sum(weight)
```

`gross` 不强制等于 1。未分配部分自然表示现金，gross 也可以大于 1。Strategy 计算并记录 gross/net，但不拥有账户风险上限；杠杆、gross、可用保证金和执行容量统一由 Trade 的 LogicalAccount 风控策略判断，避免两套配置漂移。

## Strategy 输出契约

策略算法输出：

```text
StrategyEvaluation
  due_slots[]
    component_id
    slot_id
    action = hold | rebalance | clear
    weights[]
      instrument_id
      target_weight
  debug_info
```

语义：

- 一次 Run 包含本周期全部 `due_slots`，并在一个事务中原子应用，不能为同一周期的多个 Slot 分别发出中间组合。
- `hold` 保留该 Slot 上次目标；若全部 due slots 都是 hold，则不增加 sequence、不发布事件。
- `rebalance` 完整替换对应 Slot 的权重。
- `clear` 显式清空对应 Slot；不以 TTL 或空值暗示清空。
- WeightMerger 生成 Runner 的完整权重目标，未出现的旧标的权重归零。

Strategy 到 Trade 的事件：

```text
LogicalAccountWeightTargetRequested
  weight_target_id
  runner_id
  logical_account_id
  command_sequence
  signal_time
  input_snapshot_id
  targets[]
    instrument_id
    target_weight
```

权重使用规范十进制定点字符串，不使用 float。

## 完整配置示例

下面的示例只展示框架能力，不代表固定资金或推荐交易参数：

```yaml
api_version: moox.strategy/v2
kind: coin_selection

input:
  source_view_id: crypto_market_with_factors
  data_frequency: 1h

universe:
  exchanges: [binance]
  markets: [spot, perpetual]
  quote_assets: [USDT]
  include: []
  exclude: [BTC-USDT-SPOT, ETH-USDT-SPOT]
  min_history_periods: 168
  require_trading_status: true

readiness:
  policy: strict
  deadline: 5m

weight_output:
  dust_weight: "0.0001"

components:
  - component_id: spot_long
    component_weight: "0.4"
    universe_override:
      markets: [spot]
    schedule:
      every: 24h
      offsets: [10h, 21h]
      anchor_time: "1970-01-01T00:00:00Z"
    long:
      side_weight: "1"
      scores:
        - metric:
            factor_def_id: min_max
            params: {window: 288}
          direction: ascending
          weight: "1"
      filters:
        - phase: pre
          metric:
            factor_def_id: quote_volume_mean
            params: {window: 288}
          value_type: percentile
          op: gte
          value: "0.2"
        - phase: post
          metric:
            factor_def_id: zf_mean_q
            params: {window: 288}
          value_type: value
          op: gt
```

## Trade 权重换算

Trade 第一次接受 `LogicalAccountWeightTargetRequested` 时执行冻结式换算：

1. 校验 LogicalAccount owner、sequence 和支持的 instruments。
2. 将权重请求以 `PENDING` 原子保存，允许 EventBus 消息被 ACK。
3. 按 `capital_source_id` 读取当前、权威且满足新鲜度要求的权益快照。
4. 每个 capital source 只计一次，以统一结算资产汇总 `frozen_equity`；available funds 只供容量和风险判断，不作为权重分母。
5. 为每个 instrument 取得带时间戳的参考价格。
6. 计算 `target_notional = frozen_equity * target_weight`。
7. 计算未量化的 canonical base quantity，并保存 equity source time、逐标的 price time 和 FULL raw quantity target。
8. 提交结果前以 CAS 核验该 LogicalAccount 的最新 `weight_target_id/command_sequence`；已被更新目标超过的解析标记为 `SUPERSEDED`，不得写 quantity target。
9. TargetExecutor 选择实际执行 member 后，才按该 member 的 step、minimum quantity、contract value 和 venue 规则量化并做容量检查。
10. 交给现有 TargetExecutor 收敛。

同一 `weight_target_id` 重投必须返回第一次保存的换算结果，不能用新价格或新权益重新估值。只有下一次 Strategy command 才重新换算。

LogicalAccount 的成员必须共享 execution mode 和 settlement asset。是否支持多市场由成员能力决定，不再由 `is_use_spot` 推断。Trade 解除 LogicalAccount 的单一 market type 限制，但每个 TradingAccount 必须声明稳定的 `capital_source_id`。多个 Spot/Perpetual execution member 可以共享一个 capital source；权益聚合按该字段去重，并要求同一 capital source 只有一个权威权益快照。重复或冲突来源使 LogicalAccount 不可执行。

Strategy 目标表：

```text
t_strategies

  某周期期望、包含和排除的 instruments 及 hash

t_strategy_period_readiness
  每个 Runner/周期收到的 View Ready 事件和 deadline 状态

  输入 manifest、watermark、来源事件、可用性时间线和不可变制品引用

  运行幂等键、状态、输入输出 hash、错误和耗时

  component + slot 最近一次已接受的内部归一权重
```

## 幂等与原子性

运行逻辑键：

```text
(runner_id, strategy_revision, compiled_dependency_hash, namespace, period_time, recalc_revision)
```

自动运行固定使用 `recalc_revision = 0`。人工修复通过显式 `RecalcStrategy` 请求分配稳定且递增的 revision；普通消息重投不能自行产生新 Run。

输入 hash 至少包含：

- Strategy revision 和 source hash。
- compiled config hash。
- UniverseSnapshot hash。
- StrategyInputSnapshot frame hash。
- point-in-time availability timeline hash。
- FactorInstance ID、Def revision 和 source hash。

上游 source event IDs 仅作为 provenance 保存，不参与内容 hash，避免相同数据因传输事件 ID 变化产生假冲突。

一次成功 rebalance 在同一 SQLite 事务中：

1. 插入 StrategyRun。
2. 原子应用全部 due SlotTarget 的 `hold/rebalance/clear`。
3. 执行 WeightMerger 并保存 StrategyWeightTarget。
4. 增加 Runner command sequence。
5. 写入 outbox。

任一步失败全部回滚。相同逻辑键和相同 input hash 返回已有结果；相同逻辑键但 input hash 不同返回 conflict。

## 状态与恢复

Runner 状态：

```text
DISABLED -> ENABLED -> DISABLED
                  \-> ERROR
```

StrategyRun 状态：

```text
PENDING -> RUNNING -> SUCCEEDED
                   -> SKIPPED_INCOMPLETE_INPUT
                   -> FAILED
                   -> SUPERSEDED
```

worker 通过 owner token 和 lease 从 `PENDING` claim；超时 `RUNNING` 可恢复为 `PENDING`。终态不可原地重开，数据修复使用新的 `recalc_revision`。

启用前必须验证：

- StrategyDef 已发布。
- 所有 FactorInstance 和 FactorBinding 已 enabled。
- 输入 View、frequency 和 retention 满足最大 history periods。
- UniverseSpec 可以解析且不为空。
- LogicalAccount owner 双向一致。
- LogicalAccount 支持所有允许输出的 market/settlement asset。

恢复原则：

- inbox 防止重复消费 View Ready 事件。
- readiness 状态和 SlotTarget 持久化，重启后无需重放隐藏 Python 状态。
- outbox 未发送消息重启后继续发布。
- 已存在 StrategyRun 时按 input hash 幂等返回。
- 过期周期不会阻塞新周期；旧事件只完成 inbox 记录。

## Live、Paper 与 Backtest

三种模式共用以下纯计算核心：

```text
UniverseResolver
MarketFrameLoader
DerivedMetricEvaluator
FilterEvaluator
ScoreEvaluator
Selector
SlotEvaluator
WeightMerger
```

差异仅在驱动和执行端：

| 模式 | 驱动 | 输出去向 |
| --- | --- | --- |
| Live | View Ready 事件 | Trade live LogicalAccount |
| Paper | View Ready 事件 | Trade paper LogicalAccount |
| Backtest | 历史 period iterator | Backtest portfolio simulator |

Backtest 不调用真实账户权益，也不复用 Trade 的 live 账户快照。它使用显式初始权益和同一权重到数量换算公式，由独立模拟执行器处理手续费、滑点和成交。

## 安全与确定性

- Python 只接收快照、上下文和参数，不访问网络、Secret 或账户 API。
- Strategy 配置拒绝未知字段和位置 tuple。
- 所有 decimal、时间、factor params 和 instrument ID 在 Go 边界规范化。
- 排序始终带 `instrument_id` 次级键。
- 不使用进程内随机数决定选币；需要随机策略时必须由输入 seed 显式控制。
- 不从 Python 源码推断数据依赖，所有列和 lookback 在发布时声明并编译。
- 外部数据只是普通 Field/Factor 输入，不在框架中增加专用业务对象。
