## 导言：整体质量判断与已拍板决策总览

经历前期重构后，系统**核心主干扎实且自洽**：
- **数据流主干清晰**：“采集 → Storage Pebble 事实与周期完成唯一权威 → Factor 本地连续序列计算 → Storage View 派生索引 → Strategy 纯函数求值与会话/试运行防呆 → Trade 无状态 6 阶段目标收敛”整条链路靠因果顺序协作，无分布式锁。
- **前期收敛到位**：单 MooX CA、ed25519 网关签名、网关快照 v2 自算路由、View 与 Dataset 1:1 自动建删、统一策略回放执行器、下架并入 Trade、`setup wipe` 取代复杂在线 `reset`、全仓 `.proto` 清零 `reserved` 声明等均已落地。

本次审查识别出 **10 余处高优逻辑/安全缺陷与热路径无效重扫**，并定稿以下 **9 项跨模块架构决策**：

| 编号 | 决策主题 | 定稿结论 |

| **D1** | **归档内置 `SeaweedFS`** | **删除内置 `SeaweedFS` 组件**及 `servicecatalog` 中唯一为其存在的 `third_party` 机制。对象存储改为真正可选：未配 `[archive_object_store]` 时仅保留本地带 SHA-256 的 `.csv.gz` 目录，后端 `dataapi.go` 与前端 `archive-model.ts` 同步放开无对象存储时的本地文件校验下载；配了外部 S3（COS / R2）时才启用远端上传、恢复与每日抽查。 |

### 1. `Admin`（管理后台：`modules/admin`）

**合理保留的主干**：单端口 `:9527` 内嵌静态页面（启动预压 gzip + 内容 ETag）+ 根证书下载 + `HttpOnly/SameSite=Strict` Cookie 会话与 `Origin` 强校验（`modules/admin/internal/webserver/server.go:169-201`、`modules/admin/internal/console/request_auth.go:54-112`）；`SysDeploy` 按 `moox.toml` 整份覆盖登记拓扑；`gorilla/mux` 单路由严格 404 方法约束稳定简洁，保持不动。

**问题与已定改造项**：
- **表设计与安全缺陷（高优）**：
  1. **`c_extra_config`（含 OKX `passphrase`）全入口加密**：`modules/admin/internal/service/secret/dao/secret.go:167-184` 原先只加密 `c_secret_value`，导致 `c_extra_config` 中的 OKX 交易口令明文落库；同时 `Setup`（`modules/admin/internal/service/setup/exchange_keys.go:84-95`、`impl.go:214`）、`modules/admin/cmd/cli/eventbus_credentials.go:176` 与 `modules/admin/internal/service/secret/dao/system.go:17-52` 直接用 GORM 读写 `t_secrets`。定稿：抽取统一的 `t_secrets` 字段加解密辅助函数覆盖全部读写入口，对 `c_secret_value` 与 `c_extra_config` 一并做 AES-GCM 加密。
  2. **软删除改为物理硬删除 + 初始密钥防复活保护**：原 `modules/admin/schema/admin.sql:127-134` 的 `UNIQUE (c_secret_id, c_is_deleted)` 导致固定 ID 密钥（`tencent-default` 或迁移导入同 ID 密钥）第二次删除必撞唯一索引报 `INNER_ERR`。定稿：`t_secrets` 去掉 `c_is_deleted` 列（及 `internal/softdelete` 包）改为物理硬删除（`UNIQUE (c_secret_id)`）；同时用极简的已删初始密钥 ID 记录表承接 `Setup`“管理台已删的作废初始 `[[exchange_keys]]` 不被 `setup init` 静默重建”（`exchange_keys.go:51-67`）的墓碑语义（手工新建或重新导入同 ID 时自动清除墓碑）。
  3. **移除二次脱敏冲突 + 修复 UTF-8 按字节截断**：`modules/admin/internal/service/secret/rpc/service.go:380-444` 先用 `•` 脱敏且按字节 `len(value)` 切片（多字节字符会切坏编码），随后 tRPC `masking` 过滤器调用 `modules/admin/proto/admingen/security.go:6-23` 覆盖为 `*` 使 `isMaskedSecret` 失效。定稿分两步落地：**批次 1** 仅删 `modules/admin/proto/admingen/security.go`（`Secret.Masking()`）并修复 `service.go:380-444` 为单点 `[]rune` + `•` 脱敏（保持批次 1 零 `go.mod` 变更）；**批次 2B** 随单根 `go.mod` 一并摘除 `admin` 与 `trade`（无任何 `Masking()` 实现）的 `trpc-filter/masking` 依赖、YAML `- masking` 配置及 `scripts/test/contract/test-trpc-plugin-config.sh:108-111` 断言。
  4. **Schema 规范与 `t_activity_logs` 毫秒化**：修复 `modules/admin/schema/admin.sql:21-25, 140-144` 触发器缺失的 `FOR EACH ROW WHEN NEW.c_mtime = OLD.c_mtime` 与行尾对齐注释；删掉只写不读的 `t_host_gateway_status.c_expected_hash`（`modules/admin/schema/admin.sql:99`），补外键 `ON DELETE CASCADE`；将 `t_activity_logs.c_ctime` 改为 Unix 毫秒 `INTEGER NOT NULL`（修复 `modules/admin/internal/service/activitylog/dao.go:152-157` 秒级截断漏查）。

## 第二部分：总体架构核心决策依据记录

### 1. 为什么删掉内置 `SeaweedFS`（决策 D1 完整记录）

- **原有 4 项作用**：① 通过无删除权限的 `s3.json` 策略与内容哈希键保留同盘历史版本；② 本地 `.csv.gz` 误删或校验失败时同机拉回自愈；③ 作为 `dataapi.go` `/v1/partition` 网页下载的唯一读取源；④ 未配云存储时常驻跑通 S3 代码路径。
- **核心弊端与删除理由**：
  1. **不防硬件故障却制造“已复制”假象**：与归档目录位于同一因子机、同一块盘、同一 `<部署根>` 下（`setup wipe` 一并清空，换机需拷两份），坏盘时两份同丢，但界面显示“已复制”。
  2. **超过 2 倍磁盘空间与双倍写入 I/O**：每分区本地写一份 `.csv.gz` 后又回环 HTTP 写一份进同盘 `SeaweedFS` volume，且重导出旧版本永不清理。
  3. **全仓唯一的第三方重型组件运维负担**：为单机存 `.csv.gz` 引入 `master+volume+filer+s3` 占 8 个端口的 `weed` 进程，牵出外部二进制拉取脚本、密钥派生、systemd 编排、`servicecatalog` 专属 `third_party` 机制与监控豁免特判。
- **替代方案**：异地防坏盘直接配外部腾讯云 COS / Cloudflare R2；未配外部 S3 时退回诚实的**纯本地单份 `.csv.gz` 归档**，后端 `dataapi.go` 与前端 `archive-model.ts` 同步放开无对象存储时的本地文件流式校验下载。

### 2. 为什么拆分 `Collector` 补采来源 `c_source`（决策 D5 完整记录）

- **原阻塞链**：`t_collector_kline_backfill_jobs` 仅允许 `'manual' | 'auto'`，迫使数小时的 `HistorySeed`、`CloseRefetch`、`Catchup` 全部填为 `'manual'`。`system resume` 追赶期间实时采集保持关闭、下游全部停在栅栏前等待，而 `Catchup`（`modules/collector/internal/klinecheck/catchup.go:33-61`）要求整空间 `ActiveJobs == 0` 才提交追赶并判定追平——结果同空间只要有一个慢速 `HistorySeed` 在跑，全系统实时采集与实盘交易就会陪着停摆数小时。
- **定稿方案**：将 `c_source` 正交扩展为 `'manual' | 'auto' | 'seed' | 'close_refetch' | 'catchup'`，`Catchup` 只跟踪 `'catchup'` 作业（补完暂停窗口立即放行全系统恢复实时运行），`AutoScan` 收窄到 `(dataset_id, frequency)` 粒度。

### 3. 全仓单根 `go.mod` 合一与工程护栏（决策 D8 / 6B 完整记录）

- **动机**：消除 26 个子 `go.mod`（含 11 个 `proto/*gen/go.mod`）与 `go.work` 带来的跨模块伪版本同步噪音，模块引用边界继续由 `scripts/check/check-module-boundaries.sh` 静态门禁强制守护。与前端恢复 `vue-tsc`（批次 2A）拆为两个独立 PR，避免 Go 工具链改造与存量 `.vue` 类型清错互相阻塞。
- **复核识别的 3 条硬护栏（落地必守）**：
  1. **防 SQLite 引擎退版本**：原各子模块 `go.mod` 写的是 `modernc.org/sqlite v1.45.0`，靠 `go.work` 的 `replace` 升到 `v1.49.1`。建根 `go.mod` 时必须直接 `require` 锁定 `modernc.org/sqlite v1.49.1`（`libc v1.72.0`、`memory v1.11.0`）及 `google.golang.org/genproto`。
  2. **保留按模块差异化的 `goom` 编译标志与全量 CGO 测试覆盖**：`admin`、`hostagent`、`trade` 单测使用 `goom` 桩拦截，必须带 `-gcflags=all=-l -ldflags=-s=false`，而全仓一刀切加该标志会拖慢 `pebble` 与纯 Go `sqlite` 数倍。`scripts/test/contract/test-go-workspace.sh` 须改为按显式模块目录清单分片，仅对这 3 个目录附加 `goom` 标志，并**继续全量执行全部模块（含 `modules/storage` 的 CGO DuckDB 单元测试与 E2E，切勿排除）**；纯 Go 交叉编译与无 CGO 环境由 `modules/storage` 既有的 `//go:build cgo` / `index_manager_nocgo.go`（`//go:build !cgo`）编译隔离自然兜底。
  3. **同步更新 6 个门禁与分片契约脚本**：`scripts/ci/check-go-version.sh`、`scripts/check/check-module-boundaries.sh`（删 `modules/*/go.mod` 与 `packages/go.mod` 扫描段，保留 `.go` import 边界检查）、`scripts/test/contract/test-build-factor.sh`、`scripts/test/contract/test-docs-architecture.sh`、`scripts/test/contract/test-go-workspace.sh`（并确保 `scripts/test/contract/test-go-workspace-shard-contract.sh` 继续通过）、`scripts/test/contract/test-trpc-plugin-config.sh`。

### 4. 为什么将 K 线重采样重构为市场无感的通用数据集变换（决策 D9 完整记录）

- **原有市场耦合症结**：`kline_resample` 的分桶接口（`barclock.Clock`）与三路无锁执行（`Engine.RunBucket`）骨架本身通用，但具体实现把市场假设写死在四处：
  1. **列与算子二元硬编码**：全链路调 `markets.HasTradeCount(spaceID, "")` 将列形状一刀切为 `crypto`（强制要求 `quote_volume` + `trade_num`）与 A 股（强制要求 `amount`），导致标准 5 列 OHLCV 外部导入数据集无法合成、同空间多品种列差异被忽略，且新增任意可聚合字段都需改动校验/存储/聚合全链路；
  2. **`space_id == market_id` 静态绑死**：重采样按 `spaceID` 查静态 `barclock.MarketFor`，并在 `packages/events` 中单独发明 `perSpace: true` 为固定的 4 个空间名建消费者，导致新建任何自定义空间（如沙盒/回测空间或新市场空间）均无法使用重采样；
  3. **参数背负外部采集路由残留**：无需联网的纯存储内变换反而强制要求 `provider`、`market_type`（前端未知市场静默强转为 `"spot"`，`definition.go` 残留 `binance` 选项）；
  4. **`session` `1d` 截止时间偏差**：`00:00 UTC` 桶键套用 `+24h` 算截止时间，使 A 股 `1d` 缺数降级完结比 `15:00` 真实收盘晚了 17 小时。
- **定稿方案与边界**：不引入复杂的通用 SQL/流计算表达式引擎，而是采用**“标准字段归约规则表 ∩ 源数据集实际列 + 源数据集 `alignment/calendar` 继承 + 跨空间通配消费者 + 真实收盘截止时间”**做减法解耦（代码量比原二元分支更少，对任意自定义空间、新市场与外部导入 K 线开箱即用）。对于跨午夜交易时段（如期货夜盘归属下一交易日），当前股票与 crypto 无需过度预留，待未来实际接入夜盘品种时再扩充 `barclock` 的时段日偏移表达。

### 附：无迁移 SQL 原则下的库与索引重建清单

项目遵循 `AGENTS.md` 不编写 `ALTER TABLE` 兼容迁移，SQLite 的 `CREATE TABLE IF NOT EXISTS` 不会更新旧表约束或列定义。为避免线上反复清空数据，**批次 1、2A、2B、5 均支持原地滚动发布，批次 3 与批次 4 的所有表结构变更合并在单次线上重建窗口统一执行**。

> **推荐操作方式**：合并窗口直接执行 `moox-cli setup wipe` + 全新 `setup install` / `setup deploy` 最干净彻底（注意 `wipe.py` 会清空整个 `<部署根>` 含 `<部署根>/archive/`，执行前须先在管理台导出密钥迁移包、备份因子/策略定义，如需保留既有历史归档 `.csv.gz` 请先拷出异地备份）。若选择逐文件定向清理而不跑整机 `wipe`，须完整清理下表全部状态文件：

| 批次 | 需重建的本地状态/数据库文件 | 原因说明 |
| --- | --- | --- |
| **批次 1、2A、2B** | **无需重建任何库文件** | 纯逻辑修复与构建/类型系统收敛，磁盘数据结构不变，可直接滚动发布。 |
| **批次 3 + 批次 4（合并单次窗口）** | **控制机**：`admin.db`、`collector.db`、`factor.db`、`strategy.db`、`monitor.db`、`archive.db`<br>**存储机**：`storage_metadata.db`、`storage-primary` Pebble 目录、`storage-view` 的 `.duckdb` 索引文件、EventBus JetStream 卷（或手工删除旧 `collector_resample_*_<space>_v1` durable consumers）<br>**海外机**：`trade.db`<br>**因子机**：`factor-engine` 本地状态（`data/seriesstore`、`data/engine/watermarks.json`、`gapledger`）、`archive-worker` `.state`（同时停用移除旧 `moox-seaweedfs.service`） | `t_secrets` 启用 `c_extra_config` 加密（旧库明文 `{}` 解密会报错）与硬删索引变更、`t_activity_logs` 毫秒化；`t_tags` 移除全局唯一索引，Pebble 需与 `storage_metadata.db` 同步重建并生效新 `session` `1d` 周期截止时间；DuckDB 移除 `__moox_attributes` 列；归档时间列精度统一且下线内置 `SeaweedFS`；`t_collector_kline_backfill_jobs` 扩展 `CHECK (c_source ...)` 约束与时间列毫秒化、合成任务剥离旧路由字段且重采样消费者切为跨空间通配（`setup deploy` 仅刷新 EventBus ACL 凭据，不会自动删旧 durable consumer，须清 JetStream 卷或手工删旧消费者防永久积压告警）；`factor.sql` 外键/约束更新且因子引擎本地状态须与新数据集重建对齐；`t_operator_actions` 毫秒化与显式状态列更新；`strategy.db`（本身无 DDL 变更，因上游 `storage`/`factor`/`trade` 重建后存量实例/会话引用的 `factor_task_id`/`logical_account_id`/`index_id` 全部失效）与 `monitor.db`（清旧 `seaweedfs` 拓扑、`subject_first_seen` 及单调水位防倒退告警）随全链路一并重建。 |
