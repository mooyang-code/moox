# Storage 读写路径审查

日期：2026-10-16（S-8～S-13 于 2026-10-17 由两轮 Codex 评审补充，Claude 逐条回到代码核实）　基线：`feature/mooyang`　方式：读代码，没有做 profile 或压测；文中的量级是按代码推算的，落地前要用 benchmark 或线上 profile 确认。

范围：DataNode 的 Pebble 读写（`internal/service/datanode/pebble`）、Outbox 中继（`internal/service/datanode/outbox`）、
Primary 的写入校验与元数据快照（`internal/service/primarystore`、`internal/service/metadata/cache`）。
没有覆盖：View 的 DuckDB / Bleve 细节、过期清理与 compaction 调度、CLI。

## 1. 发现

| 编号 | 级别 | 位置 | 问题 | 建议 |
| --- | --- | --- | --- | --- |
| S-1 | 正确性（潜在） | `pebble/history.go:127`、`pebble/store.go:604` | 读取结果的字段补全只按「键数 × 字段数 ≤ 10 万」分块，没有按「键数 ≤ 1 万」分块。一次返回超过 1 万行、且请求的列少于 10 个时，`ReadFieldsWithPresence` 报 `read request exceeds key/field limit`，整个读取失败。单个 selector 有多个 `series_tag` 的最近 N 根（如 View 重建 5000 根 × 3 个 tag）就会触发；归档的批量最近 N 根（单次 2 万行）一定触发 | 分块大小取 `min(10000, 100000 / 字段数)`；补一个「1 万行以上、少量列」的用例 |
| S-2 | 高：读放大 | `pebble/store.go:594` `ReadFieldsWithPresence`、`:689` `rowExists` | 每一行先新建两个迭代器判断这一行是否存在（字段、属性命名空间各一个），再对每个字段各做一次 `Get`。而同一行的字段在物理上是连续的（`0x01 + 行前缀 + field_id`，见 `pebble/key.go`），一次前缀扫描就能取全 | 整个请求共用一个快照迭代器：把键按物理编码排序，对每一行 `SeekGE` 行前缀后顺序 `Next` 取字段，同时得到是否存在；只有请求了属性、或这一行没有字段时才查属性命名空间；最后按原顺序返回。每行从「2 次建迭代器 + F 次点查」降到「1 次定位 + F 次顺序读」。因子窗口读取、View 重建、Collector 读行、归档都受益 |
| S-3 | 高：CPU 与内存分配 | `metadata/cache/store.go:92` `Snapshot`、`:571` `snapshotList`；`primarystore/service.go:114` `requestContext`；`primarystore/metadata_validator.go:91` | Primary 的每个请求（读和写都是）都通过 `RequestSnapshot` 复制一份完整的元数据缓存：`snapshotcache` 复制一次条目切片，`Store.Snapshot` 再深拷贝所有条目的 payload。之后 `GetDataset`、`ListDatasetColumns` 都是对全部条目的线性扫描加反序列化，不用缓存已有的索引；写入校验对**每一行**都重复一次数据集查找和列清单扫描，并重建列映射。开销约为「元数据条目总数 × 请求数（写入再 × 行数）」 | 快照直接引用缓存当前那一代不可变的数据和索引，不复制；解码结果按代缓存；校验在一次请求内按 `(space, dataset)` 只取一次数据集和列映射。先写 benchmark（按线上的标的、标签成员、列数量构造元数据），并抓一次 storage-primary 的 alloc profile 确认量级 |
| S-4 | 中 | `pebble/store.go:822` `PublishOutboxPublication`、`outbox/relay.go:181` `flush` | 每条出站事件被读 3 次（`ListOutbox` 一次，`PrepareOutboxPublication` 两次），信封反序列化 6 次，载荷完整解码校验 2 次；写入时已经校验过一次。因子结果事件约 300KB，积压时浪费明显 | 用 `ListOutbox` 拿到的数据确定数据集范围；加锁后只确认这一条还在（一次 `Get` 比较字节），去掉重复的完整校验 |
| S-5 | 中：需压测后决定 | `pebble/store.go:122` `Open` | Pebble 除 `Merger` 和块缓存外全部用默认值（v1.1.5）：没有布隆过滤器，MemTable 4MB，L0 文件 2MB。点查在每一层都要读索引块，与 2026-10-14 profile 中「解压索引块」占比高的现象一致 | 各层配置 `bloom.FilterPolicy(10)`（只对新写的 SST 生效，随 compaction 逐步覆盖）；MemTable 调到 64MB，并相应调整 L0 阈值和目标文件大小。S-2 落地后点查会大幅减少，收益随之变小，建议在 S-2 之后用同样的回填场景复测再决定 |
| S-7 | 高：接口设计 | `primarystore/rows_read.go` `ReadTimeSeriesRows`、`CountTimeSeriesRows`、`ListHistorySubjects` | `ReadTimeSeriesRows` 按调用方身份分流：`storage-view` 和因子身份读 DataNode，其余调用方读 View；`CountTimeSeriesRows` 由 View 回答；`ListHistorySubjects` 只给 `storage-view`。同一个请求，不同调用方读到的数据范围不同，超出 View 覆盖范围（每个序列最近 5000 根）时结果残缺。Collector 的历史缺口扫描统计「最早生效点之前 500 根」，计数为 0 时被当作没有历史，读行也走 View，扫描区间早于 View 覆盖范围时什么都看不见。2026-10-17 线上核查：目前扫描区间在 Pebble 里本来就没有数据（Storage 10-14 清空过），尚未表现；约 10-18 起 1m 数据超出 View 保留根数后会出现。同一接口两条路由的 `data_time` 格式、`complete` 取值也不一致 | PrimaryStore 对所有调用方都读事实、数事实，看板类查询改用 DataView；删除按身份分流、`ListHistorySubjects` 与自定义游标。见 Storage 读接口收敛设计 |
| S-8 | 中 | `pebble/cleanup.go:35` `CleanupExpiredBuckets`、`pebble/store.go:172` `compactAsync`、`cmd/server/main.go:183` | 过期清理持有节点级的 `datasetWriteMu` 独占锁，并在锁内逐个遍历数据集的序列，期间同一节点上所有数据集的写入（周期提交、因子写入）都被阻塞；清理每小时运行，截止桶通常一天才推进一次，但每次都提交删除并发起 compaction，`compactAsync` 每次直接起 goroutine | 改为数据集级互斥；截止桶未推进时跳过；compaction 串行执行 |
| S-9 | 高 | `packages/gatewayclient/trpc.go:125` | 配置 gzip 后，请求体不足 1KB 时仍不压缩，而响应的压缩方式跟随请求。「小请求、大响应」的读取（单标的区间读取、不带 selector 的最近 N 根）在公网上不压缩 | 配置 gzip 时总是压缩；补小请求、大响应的链路测试 |
| S-10 | 中 | `pebble/history.go:244` `pageHistory` | 只要带时间范围就扫描整个数据集的时间索引，再逐行过滤 selector；Collector 每批 50 个标的，5000 个标的的数据集检查一轮要把同一时间范围的索引遍历约 100 遍。S-2 只降低选中行的字段读取，解决不了这部分 | 带 selector 时在序列索引上逐个序列定位、归并输出；不带 selector 时用时间索引 |
| S-11 | 高 | `pebble/history.go:140`、`rows.proto:91`、`view/build.go:847` | 历史读取补字段时不读属性；`TimeSeriesRow.attributes` 是字符串映射，丢失类型。View 重建靠第二步 `ReadFields` 补回因子来源属性 | 2026-10-17 第三轮评审核实后调整：因子结果写入拒绝行属性（`primarystore/factor_rows.go:64`），View 补读的 `factor.*` 键没有写入方，DataView 的行属性也没有读取方。改为区间读取与 View 都不处理行属性、删除 `factorAttributeKeys`；行属性只由 `ReadRows` 返回 |
| S-12 | 低 | `monitor/internal/metrics/query.go:62` `QueryService.History`、`metrics/storage.go:257` | 没有生产调用方的读取链 | 删除 |
| S-13 | 中 | `primarystore/rows_read.go:137` `ReadRecordRows` | 记录数据的第三个读取入口：版本为空、未指定列或按版本范围读取时转给 View，又是一个 Primary 读 View 的旁路；仓库里没有生产调用方，只有实现和测试 | 删除；精确读取用 `ReadRows`，搜索用 `DataView.SearchRecordRows` |
| S-6 | 低 | `outbox/relay.go` | 中继单线程、每条事件同步等待确认。EventBus 积压时，排空速度受 Storage 主机到 EventBus 的往返时延限制 | 可改为有界流水线发布（保持顺序、只删除连续确认的前缀），但要处理数据集级发布锁与清除的串行化；收益只在积压时体现，暂不建议做 |

不建议改动：

- 写入时每行额外写两条历史索引键（`0x03` 时间优先、`0x04` 标的优先）。前者用于游标翻页，后者用于按标的取最近 N 根，都在用。
- View 的 DuckDB 写入已经是批量多值 upsert，没有逐行写入的问题。

## 2. 建议顺序

已确定（2026-10-16，2026-10-17 补充）：S-1～S-4、S-7～S-13（Storage 读接口收敛）放在同一次改动里，
整套 Storage 一起发布：storage-node → storage-primary → 至少等 30 秒 → storage-view（storage-primary 与 storage-view 是同一个程序）。

1. **S-1、S-2、S-4**：都在 DataNode 上，与批量最近 N 根改的是同一段读取路径。
2. **S-3**：在 storage-primary 上，做法见设计第 5.3 节；先写 benchmark 确认量级。
3. **S-5**：S-2 上线后复测回填场景，再决定是否调整 Pebble 参数。
4. **S-6**：暂缓。

详细改动见 Storage 读接口收敛设计。
