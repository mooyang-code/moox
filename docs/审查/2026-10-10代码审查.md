# MooX 代码审查与优化建议

审查基线：`feature/mooyang@2aabfaeb`，收尾核对至 `f283eb1a`，日期 2026-10-10。范围为架构与关键路径：主机网关和鉴权、
原生部署与配置发布、Storage 就绪事件、采集/因子/策略链路、Monitor 与前端，以及 docs 中对应契约。
本次交付修改文档，不改变业务代码或运行环境的部署状态。以下优先级表示后续修复顺序；性能建议尚无压测收益结论。

## 1. 优先修复的问题

### P1 View 行 ACK 与写入围栏落盘之间有崩溃窗口

`NoteAppliedPosition` 只更新内存，后台每秒保存 `applied.json`；行事件此前可以已经 ACK。
若进程在此间退出，重启会恢复持久就绪队列，却缺少证明对应行已经应用的来源位置。
`FlushViewDataReady` 因 `positionsApplied` 不满足而跳过这些事件，重试发布本身不能恢复缺失的围栏。
日线可能等待下一交易日的写入；停更的数据集可能一直等待，下游策略便无法及时触发。

依据：[data_ready.go](https://github.com/mooyang-code/moox/blob/2aabfaeb/modules/storage/internal/service/view/data_ready.go#L28)、
[ready_fence.go](https://github.com/mooyang-code/moox/blob/2aabfaeb/modules/storage/internal/service/view/ready_fence.go#L71)、
[消费后台持久化](https://github.com/mooyang-code/moox/blob/2aabfaeb/modules/storage/internal/service/view/consume.go#L253)。

本地临时探针复用了已有的 View 测试设施：保存待发事件、只推进内存围栏后丢弃服务实例，从同一目录重载；
不追加来源位置时发布数为 0、队列仍有积压，再追加更高来源位置后才发布成功。这验证了恢复状态逻辑，
不是实际进程 SIGKILL/JetStream 集成验收。

建议将“该批次可 ACK”的条件绑定到已持久化的进度。可选择按数据集批量提交水位后 ACK，或把来源水位与索引写入
放在同一可恢复事务中；仍保留批量落盘以降低 fsync 成本。应补实际强杀场景：最后一批行后停止上游、重启 View，
无需新行也能发布该周期的就绪事件。

### P1 部署与配置发布仍使用两套不相容的布局和锁

原生 `setup bootstrap/deploy-unit` 安装到 `<单元根>/releases/<ID>`，通过 `current` 定位，配置位于角色内，
维护锁是 `<部署根>/run/maintenance.lock`。但 `configTargets` 仍指向 `<storage_root>/config/storage-policy.json`、
`<control_root>/collector/config/app.yaml`，发布脚本锁 `<root>.maintenance.lock` 并调用根目录 `restart.sh`。
因此更新原生安装时会看到缺失配置、重启入口不存在；若旧目录也存在，还可能修改旧副本，且没有与原生安装器互斥。

旧 `setup deploy-control/deploy-storage` 也仍注册并进入 `deploy-moox.sh`。脚本把新的 hostgateway 模板复制到 `gateway/config`，
随后替换旧 `hmac_key_file/base_url/native_addr` 字段；新配置需要的是 `host/server/tls/control`、主机证书和独立 KeyID。
仅替换二进制名称不足以让这条旧路径部署新架构。

依据：[配置目标](https://github.com/mooyang-code/moox/blob/2aabfaeb/modules/cli/internal/command/config_publish.go#L174)、
[旧维护锁与重启](https://github.com/mooyang-code/moox/blob/2aabfaeb/modules/cli/internal/command/config_publish.go#L354)、
[旧部署模板复制](https://github.com/mooyang-code/moox/blob/2aabfaeb/scripts/deploy/deploy-moox.sh#L4125)、
[原生运行锁](https://github.com/mooyang-code/moox/blob/2aabfaeb/modules/cli/internal/setup/unitruntime/maintenance.go)。

建议先让旧命令检测到新布局时在写文件/停服务前明确拒绝，再把配置更新接入原生发布准备、摘要校验及同一维护锁。
原生升级能力完整后删除旧部署器与外置 Caddy 路径。验证应从原生安装开始发布策略，确认实际进程加载新配置、失败恢复原配置，
并与部署、pause/resume 并发执行来验证互斥。本次已修正文档与根 README 的默认部署指引。

### P2 前端 Node 版本声明低于测试依赖要求

`web/package.json` 声明 Node `>=18.12.0`，但锁定的 jsdom 29 声明 `^20.19.0 || ^22.13.0 || >=24.0.0`。
本机 Node 22.11 满足项目声明，却在 `pnpm --dir web test` 初始化环境时遇到 `ERR_REQUIRE_ESM`：97 个环境错误，0 个测试执行。
切换 Node 24.19 后，同一份代码与依赖运行 97 个测试文件、541 个测试，全部通过。

依据：[项目 engines](https://github.com/mooyang-code/moox/blob/2aabfaeb/web/package.json#L122)、
[依赖锁文件](https://github.com/mooyang-code/moox/blob/2aabfaeb/web/pnpm-lock.yaml)及本地安装的 jsdom `package.json`。

建议统一项目 engines、开发版本文件和 CI 运行版本，并在启动测试前检查依赖所需的 Node 范围。
若仍需支持更旧的 Node，则选择满足该版本的依赖组合并重新运行测试；仅放宽 engine 检查不会解决加载错误。

## 2. 性能与维护优化

| 优先级 | 现状与影响 | 建议和验证方式 |
| --- | --- | --- |
| P2 | Access 的 nonce 库只有一个连接；每次请求都开启事务、删除全部已过期记录、插入并提交。请求在这条持久化路径串行，突发流量或一批 nonce 同时过期时可能增加延迟 | 将过期清理移到有界批次/周期任务；保留唯一约束、过期 nonce 可安全复用、提交成功后才能放行和数据库故障时拒绝请求。评估 WAL 与批量提交，先测冷盘及并发请求的 p95/p99，再决定实现 |
| P2 | 调用方 gatewayclient、Access 内部 gatewayclient、HostGateway 的只读转发都各有重试。在快速连接失败时，多层重试可能扩大上游请求量；总期限虽有界，次数未共用预算 | 明确一层负责业务重试，其余层只处理必要的连接恢复，或传播剩余尝试预算。用故障注入统计每个逻辑 RPC 的实际尝试次数；继续保持写调用单发及新 nonce |
| P2 | 原生部署有 Linux 专项门禁，但 `make verify` 没有自动执行全部 `test-unit-*-linux`；普通 Go 测试在 macOS 不编译 Linux 测试，一些真实制品场景缺少输入会跳过 | 在可信 Linux CI 中准备明确的制品并执行无跳过 gate，先覆盖 unit-core、unit-bootstrap、unit-install、unit-runtime 和真实 HostGateway 控制面联调；保留多主机独立验收 |

## 3. 文档已修正的契约

- 明确 core、host、业务单元与 control 都有实际入口，以及它们与全系统验收的区别。
- 将旧计划与当前设计分开导航，补齐策略、数据保留和压测记录的索引；保留历史证据原文及时间语境。
- Storage schema 更新为 13，补充三个角色同机限制、固定节点 ID、原生策略路径和 View 崩溃恢复边界。
- Access 外部身份统一为 `scf-collector`、`factor-engine`、`moox-skill`；标签管理仍属于内部 Collector。
- FactorEngine 管理协议统一为 tRPC；HostAgent 用 host_id 关联部署，host_name 只展示。
- Monitor 服务指标事实默认 48 小时，区分 EventBus Stream 的 24 小时；Strategy 明细/回放与 Admin 登录记录各有清理策略。
- 修正配置发布目标为 egress-policy、跨主机选路主体、生成健康监听、事件命名示例及不透明 series_tag。
