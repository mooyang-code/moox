# 因子计算模块设计

> 本文描述 Factor 当前时序契约及其有意保留的简洁边界；scalar `series_tag`、
> 单任务单 Factor 和 `lookback_periods` 已在代码中实现，本地真实跨模块 E2E 已
> 覆盖 Storage、View、Python、Archive/Parquet 与 Monitor；生产发布和远端验收见
> [Time-Series `series_tag` 统一设计](superpowers/specs/2026-07-29-time-series-series-tag-design.md)
> 和
> [Time-Series Series Tag 与 Factor 正确性改造实施计划](superpowers/plans/2026-07-29-factor-runtime-correctness-hardening.md)。

## 定位

Factor 服务用于个人量化的通用时序数值因子计算，只支持单实例、timeseries
Dataset 和 Python 执行器。设计目标是可理解、可维护和足够扩展，不追求高可用、
跨进程任务恢复或任意计算平台能力。

核心层不假定输入是 K 线，不隐式读取 OHLCV，也不把整数 period 固化为框架字段。
Bias、CCI 等 K 线算法只是普通示例，与净值、基准收益率、资金费率等时序因子使用
同一套运行时。

## 数据边界

SQLite 只保存：

- `t_factor_defs`：源码、源码哈希、输入列、输出列、静态参数、回看周期数与状态。
- `t_factor_bindings`：source/target Dataset、频率、subject 选择与状态。

不保存 FactorRun、事件 inbox、replay task、补算进度或调度租约。Storage 是行情输入与
因子结果的事实源。

## Factor 定义契约

```proto
message FactorDef {
  string factor_id = 1;
  string name = 2;
  string source_code = 3;
  string source_hash = 4;
  repeated string input_columns = 5;
  repeated string outputs = 6;
  string params_json = 7;
  int32 lookback_periods = 8;
  string status = 9;
  string created_at = 10;
  string updated_at = 11;
}
```

- `input_columns` 是需要从 source Dataset 读取的完整业务字段集合。
- `name` 是 Python 模块名，`outputs` 是写入 target Dataset 的最终列名；两者创建后均
  不可修改，改名或调整输出需要创建新的 `factor_id`。
- `params_json` 是静态 JSON object。算法可自行使用 `window`、`periods` 等 key，
  但框架不解释这些业务参数。
- `lookback_periods` 是计算第一个目标时间点所需的最大不同 `data_time` 数，必须
  大于等于 1；同一时间点有多少 tag 都只算一个 period。
- `data_time` 和 `series_tag` 是运行时注入的保留系统列，不出现在
  `input_columns` 或 `outputs` 中。

同一算法需要不同参数时创建不同的 `factor_id`。模块改名、输出重命名或删除也创建
新的 Factor 定义，不为个人项目引入列迁移状态机。

`DeleteFactor` 只允许删除已经没有 Binding 的定义，并同时移除 SQLite 记录、
`factors/<name>.py`、`.versions/factor/<name>` 与
`factors/__pycache__/<name>.*.pyc`；文件先暂存，数据库删除失败时恢复，避免 RPC
失败后留下定义与源码不一致的半删除状态。数据库删除后若暂存文件清理失败，RPC
返回 `INNER_ERR`，不把带磁盘残留的删除报告为成功。

Factor 从 `disabled` 启用时先同步 Storage Factor metadata 和所有 enabled Binding
的 target Dataset，全部成功后才持久化 `enabled`；同步失败时仍保持本地 disabled，
因此不会被实时刷新加载。禁用仍先落本地状态，再向 Storage 对齐。

新建 Factor 和 CLI import 一律以 `disabled` 落库；UpdateFactor 和再次 import 只能
在 Factor 为 `disabled` 时修改定义。enabled Factor 的源码、输入列、参数和
`lookback_periods` 均不可原地更新；变更流程固定为
`disable -> update -> enable -> 全范围补算`。`SetFactorStatus` 是唯一状态写入口，
避免其他写路径绕过上述启用前 reconciliation。

Binding 启用前一次性校验 source Dataset 是 active TimeSeries、存在 active View、
`input_columns` 均可读取且 frequency 合法。禁止 `source_dataset == target_dataset`，
也禁止 `dataset_role=factor_result` 再作为 Factor source；当前模块不支持 Factor
链或 Dataset 环。

### 为什么删除 Depends

删除的是旧的 `Depends` 字段，不是删除输入依赖信息。旧模型实际采用：

```text
实际输入列 = 框架固定的 OHLCV + Depends
```

因此 `Depends` 只表示 OHLCV 之外的额外列，并不是完整依赖。例如只读取 `close`
的 Bias 即使 `Depends` 为空，也仍然依赖 `close`。这种隐式基线使非 K 线因子被迫
读取无关字段，也无法从定义本身判断真实输入。

旧设计还通过解析特定 Python 源码中的 `extra_data_dict` 推导 `Depends`。源码格式
变化、直接访问 `df["column"]` 或采用其他编码方式时都可能漏报，因此不适合作为
运行时契约。

新模型把完整依赖显式写入 `input_columns`：

```text
Bias:          ["close"]
ExcessReturn:  ["nav", "benchmark_return"]
```

TaskRunner 将相同 subject、period、lookback 和 trigger 的任务合并为一次 View 读取，
读取这些 Factor `input_columns` 的去重并集；Python 执行单个 Factor 时再投影，只看到
`data_time`、`series_tag` 和该 Factor 声明的输入列。系统不再维护
`KLineColumns`、`DependsFromSource` 或“默认 OHLCV + 额外字段”两套来源。

`Depends` 还容易被误解为依赖其他 Factor。当前模块明确不支持 Factor DAG，所以
`input_columns` 能更准确地表达“依赖 source Dataset 的哪些列”。

## 实时链路

```text
ViewSourcePeriodReady
  -> Factor durable Consumer
  -> ViewReadyRunner builds subject x binding tasks
  -> TaskRunner groups exact period reads
  -> View read sliding window
  -> bounded prepared-task queue
  -> PythonWorkerPool next available process
  -> Storage field patch
  -> FactorPeriodComputed
  -> ACK source-ready event
```

同一周期所有 Source View 输入可读后才触发计算。`ViewReadyRunner` 按稳定排序构造
`subject_id x enabled binding` 笛卡尔积；每个任务仍只包含一个 subject 和一个 Factor。
TaskRunner 使用 `engine.view_read_workers` 个读取槽位维护滑动窗口；任意 subject 读取
完成后立即把成员任务投递到有界 prepared queue，并补入下一个 subject，不存在批次
屏障。相同读取身份的多个因子共享一个 Frame，队列只保存 Frame 引用，因子取得 Python
执行机会时才做列投影，不会预复制全部 `subject x factor` DataFrame。

`engine.python_workers` 独立控制 Python 计算和写回任务并发。同一标的的不同因子在批量
模式下共享一次 Python 调用，不同标的仍可并行；Python 进程只预热一个，其余槽位在首次
领取任务时按需启动。prepared queue
容量固定为 `max(1, 2 * python_workers)`；队列满时读取生产者自然背压，内存不会随组合
数量无界增长。

单次读取使用 `engine.view_read_timeout_ms`。timeout 或临时 RPC 错误释放 read slot，
分组移动到待读取队尾重试一次；第二次失败只降级该 subject。不可重试的字段、协议或
校验错误直接失败。父 context 取消时停止新读取并取消在途 RPC。

Python 进程池不按 subject 固定分片；每个新任务领取下一个空闲进程。单任务失败只把
对应 binding/subject 标记为 degraded 并清理陈旧输出，其他组合继续执行。所有组合
终态后才追加一个 `FactorPeriodComputed` 并 ACK source-ready。系统不保存另一套 Factor
业务队列、DLQ 或 exactly-once 状态；中断由 durable consumer 重投，历史修复使用 Recalc。

历史时间点修正会向后扩展 `lookback_periods - 1` 个实际 `data_time`。无限窗口或
递归状态因子不做自动实时修正，必须显式补算到最新时间。

## 范围计算

RPC `RecalcFactor` 复用线上 TaskRunner 与全局 Python 进程池；多周期之间串行，每个
周期内部并行执行组合任务。CLI `run-once` 使用独立的单 worker TaskRunner。时间范围
统一采用 `[start_time, end_time)`。

每次最多处理 2000 个目标 period：

1. 范围 selector 不设置 `series_tag`，读取 scope 下的全部 tag。
2. 按 `data_time, series_tag` 升序聚合最多 2000 个不同目标时间点；不能在同一
   时间点的 tag cohort 中间截断。
3. 在第一个目标时间点前读取最多 `lookback_periods - 1` 个完整时间点。
4. 合并成一个输入 DataFrame，执行一个 Factor。
5. 校验返回的 `(data_time, series_tag)` 唯一，并只保留目标半开范围内的结果。
6. 按返回身份对 target Dataset 执行一次字段 patch。

一个 chunk 对应一次逻辑读取、一次 Python 调用和一次写回。后续 chunk 失败时已完成
chunk 不回滚；调用方可以重跑整个范围。内部读页使用包含 `series_tag` 的稳定全序，
chunk 只在完整 cohort 之后推进到下一个 `data_time`，不会跳过同一时间点的后续 tag。

## Python 契约

唯一执行器是 `PythonWorkerPool`，内部使用常驻本地进程池，但公共协议只使用 JSON。
Factor 源码统一提供：

```python
import pandas

def compute(df, params):
    return pandas.DataFrame({
        "data_time": output_times,
        "series_tag": output_tags,
        "output_name": values,
    })
```

- `df` 按 `data_time, series_tag` 升序，只包含两个系统列和声明的
  `input_columns`。
- `params` 一定是 dict。
- 返回值必须是 pandas DataFrame。
- 返回列必须恰好是 `data_time`、`series_tag` 和声明的 `outputs`。
- `(data_time, series_tag)` 必须唯一；输出 tag 可以与输入 tag 不同。
- 空 DataFrame 是合法结果，但表示不写任何行，不清除旧结果；目标身份已知但输入
  tag 缺失时，算法应返回该身份的 `null`。

Python 在完整的“历史上下文 + 目标范围”上计算，worker 再按 `data_time` 切出目标
范围。算法通过 `params_json` 选择所需完整 tag，并可 pivot 后输出
`venue_pair:binance-okx` 等新序列；Factor 核心不解释 tag，也不跨 Dataset join。
结果元素只能是有限数值或 `null`。`NaN` 和正负无穷在 Python 边界归一化为
`null`；写回时 `null` 转成 Storage 显式 null marker，用于清除旧值。请求中省略
字段才表示保留旧值。

不保留 `signal`、`signal_multi_params`、`candle_begin_time` 或旧 Factor 文件兼容分支。

## 模板示例

`examples/factors/timeseries` 中的 Bias、CCI 和 ExcessReturn 只用于展示如何实现
`compute(df, params)`。Bias/CCI 选择 `close` 等 K 线字段是算法自身的输入声明，
不是 Factor 运行时的固定协议；净值、组合收益率、资金费率或其他数值时序使用完全
相同的定义、绑定、范围读取和写回路径。

## Python 进程运行时

```text
Factor TaskRunner
  -> View read sliding window
  -> bounded prepared-task queue
  -> PythonWorkerPool
  -> pyruntime Pool
  -> one Supervisor per pool slot
  -> one resident StdioWorker
  -> Python process
```

各层职责：

- ViewReadyRunner 决定计算对象和周期；TaskRunner 合并严格相同的 period read identity，
  用独立 read workers 准备数据，再把数据就绪任务交给 Python workers。
- Pool 把任务交给下一个空闲 worker 槽位，不按 subject 建立固定亲和关系。
- Supervisor 管理一个常驻 worker 的创建、串行使用、状态、关闭和失败替换。
- StdioWorker 启动 Python 子进程，执行 HELLO/LOAD/RUN 帧读写和超时终止；
  同一个 `TaskTimeout` 覆盖握手、写帧和等待响应。

Python 进程启动不扫描或 import factors 目录。每个任务只按 immutable
`SourcePath + SourceHash` 执行 LOAD；LOAD 阶段捕获 stdout/stderr，普通 `print()`
不能污染二进制帧协议。disabled 草稿因此不会阻塞 worker 启动或执行副作用。

Supervisor 不是 Factor TaskRunner，也不保存业务任务。它只保证一个 pool 槽位中的
Python 进程处于可使用状态：

1. `Ensure` 复用 ready worker；非 ready worker 先完整关闭，再通过 factory 创建。
2. `runMu` 将同一 worker 上的 LOAD 与 RUN 串行化，避免模块被并发请求替换。
3. HELLO、LOAD、RUN、协议、读写或超时失败后，旧进程必须 `Kill + Wait`，然后
   清空引用；即使子进程停止读取 stdin，阻塞中的写帧也必须能被超时终止。
4. 后续请求按 backoff 创建新 worker；连续创建失败超过阈值时进入 crash-loop failure。
5. Pool 关闭时尝试关闭全部 Supervisor，并汇总错误，不能因第一个错误遗留其他进程。

Factor 不在 Supervisor 中额外重放业务任务；TaskRunner 内部固定有限重试，不暴露
`max_retry` 调优项，避免两层重试相乘。

## 明确不做

- Arrow/mmap、截面因子、多实例分片。
- Dimensions Map、多 tag、tag registry 或跨 Dataset join。
- 持久化调度、运行历史、异步进度、自动 replay。
- 通用因子 DAG、参数 Schema Registry、任意输出类型。
- 分布式锁、DLQ、exactly-once。
- 旧 SQLite、Proto、`lookback_rows`、`Depends` 或 Python `signal` 兼容。

若 profiling 证明 JSON 或单实例成为真实瓶颈，再针对测得的问题单独立项。
