# 因子计算模块设计

## 定位

Factor 服务用于个人量化的时序因子计算。当前只支持单实例、timeseries 因子和 Python
执行器。设计目标是可理解、可维护和足够扩展，不追求高可用或跨进程任务恢复。

## 数据边界

SQLite 只保存：

- `t_factor_defs`：源码、源码哈希、`periods`、`lookback_bars`、`depends` 与状态。
- `t_factor_bindings`：source/target Dataset、频率、subject 选择与状态。

不保存 FactorRun、事件 inbox、replay task、补算进度或调度租约。Storage 是行情输入与
因子结果的事实源。

`Depends` 表示源码所需的额外 Storage 列，与标准 OHLCV 列合并读取；它不是因子依赖
DAG。`LookbackBars` 表示目标范围前需要读取的输入上下文 bar 数，不表示输出长度。

## 实时链路

```text
DatasetRowsUpserted
  -> Factor JetStream Consumer
  -> decode and validate
  -> EventBatcher.Add
  -> ACK
  -> fixed-window Flush
  -> refresh executable bindings
  -> bounded scheduler queue
  -> range runner
  -> PythonExecutor
  -> Storage field patch
```

ACK 发生在事件进入内存 batcher 后。ACK 后进程退出可能漏算；系统不提供 durable
scheduler、Factor inbox、DLQ 或 exactly-once。通过手动范围补算恢复即可。

EventBatcher 按
`(space, source_dataset, target_dataset, subject, freq)` 聚合，deadline 固定为首事件
时间加窗口。实时任务把最新事件转换为 `[bar_time, bar_time + 1ns)`。

Scheduler 使用有界队列。新 scope 在队列满时返回 `ErrQueueFull` 并增加
`queue_overflow_count`；相同 scope 的更新原位替换，不增加队列深度。

## 范围计算

RPC `RecalcFactor` 和 CLI `run-once` 都同步调用同一个 `scheduler.BuildTask` 与
`Service.Run`，不占用实时队列容量。时间范围统一采用 `[start_time, end_time)`。

每次最多处理 2000 个目标 bar：

1. 升序读取最多 2000 条目标数据。
2. 在第一条目标数据前读取最多 `lookback_bars - 1` 条历史上下文。
3. 合并成一个输入 DataFrame。
4. 调用一次 Python。
5. 校验每个结果列恰好有 `target row count` 个元素。
6. 对该 chunk 写回一次。

一个 chunk 对应一次逻辑读取、一次 Python 调用和一次写回。后续 chunk 失败时已完成
chunk 不回滚；调用方可以重跑整个范围。

## Python 契约

唯一执行器是 `PythonExecutor`，内部可使用本地 worker pool，但公共协议只使用 JSON。
Python 在完整的“历史上下文 + 目标范围”上计算，只返回目标范围数组：

```json
{
  "id": "task-id",
  "ok": true,
  "encoding": "json",
  "results": {
    "Bias_20": [null, 1.01]
  }
}
```

结果元素只能是有限数值或 `null`。`NaN` 和正负无穷在 Python 边界归一化为 `null`；
写回时只跳过对应单元格。

## 明确不做

- Arrow/mmap、截面因子、多实例分片。
- 持久化调度、运行历史、异步进度、自动 replay。
- 通用因子 DAG、分布式锁、exactly-once。

若 profiling 证明 JSON 或单实例成为真实瓶颈，再针对测得的问题单独立项。
