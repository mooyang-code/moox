# 因子计算模块设计

> 本文描述 Factor 当前的通用时序契约及其有意保留的简洁边界。改造和验收步骤见
> [Factor Generic Time-Series Review Remediation Implementation Plan](superpowers/plans/2026-07-28-factor-generic-timeseries-review-remediation.md)。

## 定位

Factor 服务用于个人量化的通用时序数值因子计算，只支持单实例、timeseries
Dataset 和 Python 执行器。设计目标是可理解、可维护和足够扩展，不追求高可用、
跨进程任务恢复或任意计算平台能力。

核心层不假定输入是 K 线，不隐式读取 OHLCV，也不把整数 period 固化为框架字段。
Bias、CCI 等 K 线算法只是普通示例，与净值、基准收益率、资金费率等时序因子使用
同一套运行时。

## 数据边界

SQLite 只保存：

- `t_factor_defs`：源码、源码哈希、输入列、输出列、静态参数、回看行数与状态。
- `t_factor_bindings`：source/target Dataset、频率、subject 选择与状态。

不保存 FactorRun、事件 inbox、replay task、补算进度或调度租约。Storage 是行情输入与
因子结果的事实源。

## Factor 定义契约

```proto
message FactorDef {
  string factor_id = 1;
  string name = 2;
  string source_code = 3;
  string source_hash = 4;
  repeated string input_columns = 5;
  repeated string outputs = 6;
  string params_json = 7;
  int32 lookback_rows = 8;
  string status = 9;
  string created_at = 10;
  string updated_at = 11;
}
```

- `input_columns` 是需要从 source Dataset 读取的完整业务字段集合。
- `name` 是 Python 模块名，`outputs` 是写入 target Dataset 的最终列名；两者创建后均
  不可修改，改名或调整输出需要创建新的 `factor_id`。
- `params_json` 是静态 JSON object。算法可自行使用 `window`、`periods` 等 key，
  但框架不解释这些业务参数。
- `lookback_rows` 是计算第一个目标行所需的最大输入行数，必须大于等于 1。
- `data_time` 是运行时注入的保留系统列，不出现在 `input_columns` 或 `outputs` 中。

同一算法需要不同参数时创建不同的 `factor_id`。模块改名、输出重命名或删除也创建
新的 Factor 定义，不为个人项目引入列迁移状态机。

`DeleteFactor` 只允许删除已经没有 Binding 的定义，并同时移除 SQLite 记录、
`factors/<name>.py`、`.versions/factor/<name>` 与
`factors/__pycache__/<name>.*.pyc`；文件先暂存，数据库删除失败时恢复，避免 RPC
失败后留下定义与源码不一致的半删除状态。数据库删除后若暂存文件清理失败，RPC
返回 `INNER_ERR`，不把带磁盘残留的删除报告为成功。

Factor 从 `disabled` 启用时先同步 Storage Factor metadata 和所有 enabled Binding
的 target Dataset，全部成功后才持久化 `enabled`；同步失败时仍保持本地 disabled，
因此不会被实时刷新加载。禁用仍先落本地状态，再向 Storage 对齐。

新建 Factor 和 CLI import 一律以 `disabled` 落库；UpdateFactor 和再次 import 只能
修改定义内容并保留当前状态。`SetFactorStatus` 是唯一状态写入口，避免其他写路径绕过
上述启用前 reconciliation。

### 为什么删除 Depends

删除的是旧的 `Depends` 字段，不是删除输入依赖信息。旧模型实际采用：

```text
实际输入列 = 框架固定的 OHLCV + Depends
```

因此 `Depends` 只表示 OHLCV 之外的额外列，并不是完整依赖。例如只读取 `close`
的 Bias 即使 `Depends` 为空，也仍然依赖 `close`。这种隐式基线使非 K 线因子被迫
读取无关字段，也无法从定义本身判断真实输入。

旧设计还通过解析特定 Python 源码中的 `extra_data_dict` 推导 `Depends`。源码格式
变化、直接访问 `df["column"]` 或采用其他编码方式时都可能漏报，因此不适合作为
运行时契约。

新模型把完整依赖显式写入 `input_columns`：

```text
Bias:          ["close"]
ExcessReturn:  ["nav", "benchmark_return"]
```

Scheduler 只读取所有待算 Factor 的 `input_columns` 去重并集；Python 执行单个 Factor
时只看到 `data_time` 和该 Factor 声明的输入列。系统不再维护 `KLineColumns`、
`DependsFromSource` 或“默认 OHLCV + 额外字段”两套来源。

`Depends` 还容易被误解为依赖其他 Factor。当前模块明确不支持 Factor DAG，所以
`input_columns` 能更准确地表达“依赖 source Dataset 的哪些列”。

## 实时链路

```text
DatasetRowsUpserted
  -> Factor JetStream Consumer
  -> decode and validate
  -> EventBatcher.Add
  -> ACK
  -> fixed-window Flush
  -> refresh executable bindings
  -> bounded scheduler queue
  -> range runner
  -> PythonExecutor
  -> Storage field patch
```

ACK 发生在事件进入内存 batcher 后。ACK 后进程退出可能漏算；系统不提供 durable
scheduler、Factor inbox、DLQ 或 exactly-once。通过手动范围补算恢复即可。

EventBatcher 按
`(space, source_dataset, target_dataset, subject, freq)` 聚合，deadline 固定为首事件
时间加窗口。同一窗口内的多行事件合并为
`[min(data_time), max(data_time) + 1ns)`，不能只保留最新时间。

Scheduler 使用有界队列。新 scope 在队列满时返回 `ErrQueueFull` 并增加
`queue_overflow_count`；相同 scope 的 pending task 合并时间范围，不增加队列深度，
也不丢弃较早的数据行。

## 范围计算

RPC `RecalcFactor` 和 CLI `run-once` 都同步调用同一个 `scheduler.BuildTask` 与
`Service.Run`，不占用实时队列容量。时间范围统一采用 `[start_time, end_time)`。

每次最多处理 2000 个目标行：

1. 升序读取最多 2000 条目标数据。
2. 在第一条目标数据前读取最多 `lookback_rows - 1` 条历史上下文。
3. 合并成一个输入 DataFrame。
4. 调用一次 Python。
5. 校验每个结果列恰好有 `target row count` 个元素。
6. 对该 chunk 写回一次。

一个 chunk 对应一次逻辑读取、一次 Python 调用和一次写回。后续 chunk 失败时已完成
chunk 不回滚；调用方可以重跑整个范围。

## Python 契约

唯一执行器是 `PythonExecutor`，内部可使用本地 worker pool，但公共协议只使用 JSON。
Factor 源码统一提供：

```python
def compute(df, params):
    return {
        "output_name": series,
    }
```

- `df` 按 `data_time` 升序，只包含系统列和声明的 `input_columns`。
- `params` 一定是 dict。
- 返回值必须是 `dict[str, pandas.Series]`。
- 返回 key 必须与 `outputs` 完全一致。
- 每个 Series 必须与输入 DataFrame 等长且 index 一致。

Python 在完整的“历史上下文 + 目标范围”上计算，worker 再切出目标范围。结果元素只能
是有限数值或 `null`。`NaN` 和正负无穷在 Python 边界归一化为 `null`；写回时
`null` 转成 Storage 显式 null marker，用于清除旧值。请求中省略字段才表示保留旧值。

不保留 `signal`、`signal_multi_params`、`candle_begin_time` 或旧 Factor 文件兼容分支。

## 模板示例

`examples/factors/timeseries` 中的 Bias、CCI 和 ExcessReturn 只用于展示如何实现
`compute(df, params)`。Bias/CCI 选择 `close` 等 K 线字段是算法自身的输入声明，
不是 Factor 运行时的固定协议；净值、组合收益率、资金费率或其他数值时序使用完全
相同的定义、绑定、范围读取和写回路径。

## Python 进程运行时

```text
Factor Scheduler
  -> pyruntime Pool
  -> one Supervisor per pool slot
  -> one resident StdioWorker
  -> Python process
```

各层职责：

- Factor Scheduler 决定计算对象、时间范围和任务级重试。
- Pool 根据 shard key 或轮询选择 worker 槽位，本身不管理进程恢复。
- Supervisor 管理一个常驻 worker 的创建、串行使用、状态、关闭和失败替换。
- StdioWorker 启动 Python 子进程，执行 HELLO/LOAD/RUN 帧读写和超时终止。

Supervisor 不是 Factor scheduler，也不保存业务任务。它只保证一个 pool 槽位中的
Python 进程处于可使用状态：

1. `Ensure` 复用 ready worker；非 ready worker 先完整关闭，再通过 factory 创建。
2. `runMu` 将同一 worker 上的 LOAD 与 RUN 串行化，避免模块被并发请求替换。
3. LOAD、RUN、协议、读写或超时失败后，旧进程必须 `Kill + Wait`，然后清空引用。
4. 后续请求按 backoff 创建新 worker；连续创建失败超过阈值时进入 crash-loop failure。
5. Pool 关闭时尝试关闭全部 Supervisor，并汇总错误，不能因第一个错误遗留其他进程。

Factor 不在 Supervisor 中额外重放业务任务；任务级 `max_retry` 仍由 Scheduler 统一
控制，避免两层重试相乘。进程恢复不改变 realtime best-effort 边界。

## 明确不做

- Arrow/mmap、截面因子、多实例分片。
- 持久化调度、运行历史、异步进度、自动 replay。
- 通用因子 DAG、参数 Schema Registry、任意输出类型。
- 分布式锁、DLQ、exactly-once。
- 旧 SQLite、Proto、`Depends` 或 Python `signal` 兼容。

若 profiling 证明 JSON 或单实例成为真实瓶颈，再针对测得的问题单独立项。
