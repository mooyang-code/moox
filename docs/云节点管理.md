# 云节点管理

云节点能力由 `modules/cloudnode` 提供，Admin 只负责网关、登录态、SecretMgr 和服务目录。

## 云账户

先在 SecretMgr 创建 active 的 Tencent cloud secret，再创建 CloudAccount 并保存其
`credential_secret_id`。CloudAccount 保存 AppID、COS region/bucket 等业务配置，不保存
SecretID/SecretKey。禁用或删除 secret 后，SCF/COS 操作会明确失败。

## 作业路由

CloudNode 在发布或部署 SCF 节点时，根据节点声明的 workloads 按
`space_id + job_type` 提前 ensure Job Execution Queue；提交 JobItem 时也会幂等校准。
Collector SCF 直接 bind 和消费该队列。代码包只描述部署产物，不参与 durable identity。
Kline 和 Symbol 队列彼此独立，一个缺失不影响另一个。

每个 SCF 进程只有一个 NATS 连接和一个常驻 taskrunner，内部绑定多个受支持 durable。
新增 SCF 实例会通过相同 durable 自动参与竞争消费，执行完全由 JetStream delivery 驱动。
`execute_at` 缺失或已到期表示立即执行，未来任务的 NAK delay 严格等于
`execute_at - now`。系统允许少量重复执行，不提供任务级去重承诺。

状态从 `pending` 直接进入 `success` 或 `failed`；发布失败为 `enqueue_failed`，允许重复
提交重新发布。没有 attempt、running、cancel、Poll fallback 或 ack token。终态记录
`duration_ms` 和 `execution_node`，first-terminal-wins。
每次 JobItem 的获取、延期、执行、状态上报、完成和 delivery action 都可按
`job_item_id` 在 CLS 检索。

## SCF 发布

`collector function publish submit` 读取部署机上的 0600
`~/.config/moox/eventbus/cloudnode-worker.yaml`，将 URL、用户名、密码、Base64 CA 与本次
PackageID 注入 SCF Environment。`--env` 不能覆盖这些托管键，loopback URL 不能发布到
SCF，函数包中不得包含凭据。

提交示例：

```bash
moox-cli collector function publish submit \
  --cloud-account-id tencent-prod \
  --region ap-guangzhou \
  --package-name moox-collector \
  --version 20260728 \
  --node-count 50 \
  --function-name-prefix moox-collector
```

上传 COS 完成后，命令提交一个后台发布 Job 并返回 `job_id`，不会等待腾讯云创建或部署
完成。使用以下命令查询真实 Job 和 Item 结果：

```bash
moox-cli collector function publish status --job-id node-batch-...
```

`PENDING/RUNNING` 可继续查询；`SUCCESS` 表示全部成功；`FAILED/PARTIAL` 时应检查失败
Item 的 `node_id` 和 `error_message`。CLI 退出不影响后台 Job。

已有函数也可使用前端批量/单节点部署或 `collector function deploy`；这些入口同样只提交
异步 Job，并通过上述 status 命令查询。部署保留现有 Environment，只更新代码和
`MOOX_CODE_PACKAGE_ID`。凭据轮换需删除函数后重新 publish。
