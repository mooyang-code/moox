# 云节点管理

> **实时行情节点说明**：`node_type=scf-event` 表示腾讯云事件函数，
> `trigger_type=timer` 表示由 Timer Trigger 触发实时 K 线，`trigger_type=invoke` 表示
> Collector 按需调用 Symbol 快照、补采、探针或人工 E2E。Timer 节点的任务和 Collector
> 维护的公共 DNS 通过 CloudNode 受管 Environment Patch 更新；腾讯云没有跨函数共享的全局
> Environment，每个函数都有自己的分片。完整背景见
> [SCF 短时行情采集架构](architecture/scf-short-lived-market-fetch.md)。

云节点能力由 `modules/cloudnode` 提供，Admin 只负责网关、登录态、SecretMgr 和服务目录。

## 云账户

先在 SecretMgr 创建 active 的 Tencent cloud secret，再创建 CloudAccount 并保存其
`credential_secret_id`。CloudAccount 保存 AppID、COS region/bucket 等业务配置，不保存
SecretID/SecretKey。禁用或删除 secret 后，SCF/COS 操作会明确失败。

## 作业路由

提交 JobItem 时，CloudNode 按 `space_id + job_type` 幂等创建执行队列。实时
`market_data` 行情 SCF 不消费 JobItem，也不由 Collector 每分钟逐节点 Invoke：Timer
直接触发函数，函数完成单次请求、Storage 聚合写入和 CLS 上报后立即返回。

状态从 `pending` 直接进入 `success` 或 `failed`；发布失败为 `enqueue_failed`，允许重复
提交重新发布。没有 attempt、running、cancel、Poll fallback 或 ack token。终态记录
`duration_ms` 和 `execution_node`，first-terminal-wins。
每次 JobItem 的获取、延期、执行、状态上报、完成和 delivery action 都可按
`job_item_id` 在 CLS 检索。

## SCF 发布

实时 Timer 发布不把 EventBus、Collector 控制面凭据写入函数。配置驱动的
`collector function publish submit --file custom.toml --space-id crypto` 会按地域创建
`trigger_type=timer` 的实时函数，并额外创建 1 个 `trigger_type=invoke` 辅助函数；后者才读取
按需 Completion 所需的 EventBus 材料。Timer 函数只接收 64MB/15s、Storage/CLS、任务和 DNS
环境变量。

每个 Space 可在 `custom.toml` 的 `timer_function_count` 配置 Timer 函数总数；启用地域的
`function_count` 之和必须与该值一致。将某个启用地域的 `function_count` 设为 `0`，表示由
CLI 按总数自动均分（每地域最多 50 个）。未设置地域数量时，`crypto` 默认 60 个，
`stock_cn` 默认 300 个；后者至少需要 6 个启用地域。Invoke 辅助函数不计入该总数。

### 两类行情云节点

- `trigger_type=timer`（名称通常含 `-timer-`）：由腾讯 Timer Trigger 直接触发实时 K 线，
  每个函数保存自己的标的分片和 DNS Environment。
- `trigger_type=invoke`（名称通常含 `-invoke-`）：没有 Timer Trigger，由 Collector 或 CLI
  通过 `InvokeFunction` 按需调用，负责 Symbol 全量快照、缺口补采、出口探针和人工 E2E。

标准发布在每个启用地域保留 1 个 Invoke 辅助函数，是为了保留该地域的 SCF 公网出口，且不
让按需任务污染实时 Timer 的任务 Environment。Invoke 函数不参与每分钟实时采集，也不计入
`function_count`；删除它不会影响 Timer K 线，但会关闭这些按需能力。

手工 `--trigger-type=invoke` 发布时，命令才读取部署机上的 0600
`~/.config/moox/eventbus/market-fetch-publisher.yaml`，将 URL、用户名、密码、Base64 CA 与本次
PackageID 注入 SCF Environment。`--env` 不能覆盖这些托管键，loopback URL 不能发布到
SCF，函数包中不得包含凭据。

提交示例：

```bash
moox-cli collector function publish submit \
  --cloud-account-id tencent-prod \
  --region ap-guangzhou \
  --package-name moox-collector \
  --version 20260728 \
  --node-count 50 \
  --function-name-prefix moox-collector
```

上传 COS 完成后，命令提交一个后台发布 Job 并返回 `job_id`，不会等待腾讯云创建或部署
完成。使用以下命令查询真实 Job 和 Item 结果：

```bash
moox-cli collector function publish status --job-id node-batch-...
```

`PENDING/RUNNING` 可继续查询；`SUCCESS` 表示全部成功；`FAILED/PARTIAL` 时应检查失败
Item 的 `node_id` 和 `error_message`。CLI 退出不影响后台 Job。

已有函数也可使用前端批量/单节点部署或 `collector function deploy`；这些入口同样只提交
异步 Job，并通过上述 status 命令查询。部署保留现有 Environment，只更新代码和
`MOOX_CODE_PACKAGE_ID`。凭据轮换需删除函数后重新 publish。
