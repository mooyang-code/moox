# 采集（Collector）

Collector 负责行情采集：管理采集任务，规划每个周期要抓取的标的，把工作分派给执行端（腾讯云 SCF 函数，
或香港机上 `collector-stream` 的 WS 推送接收与本地执行端），跟踪每个周期在 Storage 中的完成情况，并维护标的与标签。

代码位置：`modules/collector`。

## 1. 组成

| 组件 | 入口 | 职责 |
| --- | --- | --- |
| `moox-collector` | `cmd/server` | 采集任务管理、采集计划对账与部署、K 线检查与补采、K 线重采样、DNS 快照、标签与标的属性同步 |
| SCF 采集函数 | `cmd/scf/market_data` | 在腾讯云由 Timer 触发，按环境变量里的采集计划抓取行情并写入 Storage；也接受手动与补采调用 |
| `moox-collector-stream` | `cmd/stream` | 部署在海外机（单元档案 `collector-stream`）：订阅交易所 WS 收盘 K 线，按周期提交 Storage；同进程提供本地执行端 `MarketFetchExecutor`（补采与本地定时拉取） |
| `moox-collector-cli` | `cmd/cli` | 初始化 Collector 数据库 |

实时采集不依赖 Collector：函数与 `collector-stream` 按计划自行触发或接收、自行写入，Collector 停机不影响 K 线入库，只影响计划变更与补采。

`moox-collector` 的服务与定时器：

| 名称 | 端口 / 周期 | 说明 |
| --- | --- | --- |
| `CollectMgr` | tRPC `11402` | 任务管理与采集计划、K 线检查与补采接口，经主机网关供控制台、CLI 与 Monitor 调用 |
| `StreamCollector` | tRPC `11422` | `collector-stream` 的心跳、拉计划与周期统计上报（只放行 `collector-stream`） |
| 健康检查 | `11412` | `/healthz`、`/readyz`、`/metrics` |
| `kline_resample` 定时器 | 每分钟第 5 秒 | 准备合成目标数据集、兜底检查、发布补写通知、推进历史合成作业，见第 7 节 |
| `dns` 定时器 | 每 30 秒 | 刷新行情域名的 DNS 快照 |
| `metrics` 定时器 | 每 30 秒 | 上报指标 |
| `subject_tags` 定时器 | 每分钟第 30 秒 | 检查到期标签并同步成员 |
| `subject_attributes` 定时器 | 每分钟第 45 秒 | 按任务时区检查属性维护计划 |

采集计划对账（每个空间一个协程，每分钟一次）与自动补采在进程内常驻运行，不经过 tRPC 定时器。

## 2. 领域模型

| 对象 | 表 | 说明 |
| --- | --- | --- |
| CollectionTask | `t_collector_tasks`、`t_collector_task_tags` | 采集任务：数据类型（`kline` / `kline_resample`）、采集参数、绑定的标签、结果数据集与 View |
| TaskSeries | `t_collector_task_series` | 任务当前要采的序列（标的 × 数据源 × 市场 × series_tag） |
| FetchPlan | `t_collector_fetch_plans` | 采集计划：每个空间同一时间最多一份未生效的计划，最近一份已生效的计划即“已生效状态” |
| BackfillJob / Chunk | `t_collector_kline_backfill_jobs`、`t_collector_kline_backfill_chunks` | K 线补采作业（范围、来源、类型按列保存）与分块 |
| Watermark | `t_collector_backfill_watermarks` | 自动补采的扫描水位 |
| SourceAbsence | `t_collector_source_absences` | 已确认“行情源没有”的 K 线区间，检查与补采都扣除 |
| HistoryScan | `t_collector_history_scans` | 每个数据集最近一次历史缺口扫描的结果与缺口分组 |
| ResampleSnapshot | `t_collector_resample_snapshots` | 合成目标数据集登记过的标的快照（按生效点追加），决定一个目标桶用周期提交还是普通写入 |
| ResampleJob | `t_collector_resample_jobs` | 历史合成作业（范围、游标、进度、跳过样例） |
| BackfillNotice / EventOutbox | `t_collector_backfill_notices`、`t_collector_event_outbox` | 补写通知（补采分块确认、合成补写）与本地事件发件箱，发布 `event.collector.kline.backfilled` |
| IngestMode | `t_collector_ingest_modes` | 每个数据集的采集方式（`stream` / `pull`）与拉取、补采的执行端（`scf` / `local`），见第 3a 节 |
| StreamWorker | `t_collector_stream_workers` | `collector-stream` 的心跳、已应用的计划与连接状态（一空间一行） |
| SubjectExclusion | `t_collector_subject_exclusions` | 采集名单排除：叠加在标签成员之上、只作用于采集计划，可设到期时间，见第 6 节 |
| TagSyncRun | `t_collector_tag_sync_runs` | 标签的标的同步运行状态（上次运行时间、结果、错误，按空间与标签）：调度判断读它，Monitor 与管理台经 `ListTagSyncStatus` 读取；重置 data 范围时清空，见第 6 节 |

**一任务一结果。** 每个采集任务独占一个结果数据集和默认 View，ID 由任务 ID 派生
（`dataset_<task>`、`view_<task>_<类型>_<频率>`）。用户只面对“采集任务”和“采集结果”，
不需要管理数据集。删除任务时由用户选择保留结果，或物理删除结果 View、数据集及其数据。
内置任务定义在 `config/setup/collection-tasks.yaml`，首次启动时导入。

**标签与来源。** `kline` 任务的 Provider 与市场由所选标签固定绑定，同一任务的标签必须来自同一数据源（`sync.source`），
市场（`market_type`）要么全部相同，要么正好是现货加永续（统一数据集，见下）；创建时校验，否则计划生成会拒绝整个空间。
结果数据集的 `market_type` 属性取自这些标签，重采样据此校验源数据集。

**统一数据集。** 一个任务同时挂同一数据源的现货、永续两个标签，两条序列写进同一个数据集，用行键里已有的 `series_tag` 区分，
只要一个因子任务、一个 View。想按市场分开就建两个任务、各挂一个标签（管理台在同时选了两个市场时让用户在“合并为一个数据集”与“按市场拆成两个任务”之间选，选后者一次建两个任务，第二个失败就保留第一个并提示补建）。
不另存“组织方式”字段，数据集属性 `market_type=multi` 就是统一数据集的标记，`data_source_id` 保留数据源。
- **tag 取值**沿用采集写行的约定：现货 `venue:binance|market:spot|source:spot_http`，永续 `venue:binance|market:swap|source:swap_http`。
  tag 到市场用 `packages/seriesset` 的 `SeriesTagMarket(tag)`（按 `market:` 段解析，没有这一段视为现货，返回小写 `spot`、`swap`），生成 tag 的正向逻辑（`PlanSeriesTag`）留在 Collector。
- **已有任务不能在单市场与统一数据集之间切换**：更新任务不允许增删标签（含跨市场增删），后端的 `UpdateTask` 拦截，要换就新建任务。统一数据集一律新建，不改造已有的分开数据集。
- **每个市场的标的与活跃状态**来自数据集挂的标签：现货标签下的标的属于现货序列，永续标签下的属于永续序列；一个市场的标的缺失、失败、延迟不连累另一个市场。
- **升级已有的 Collector 库**：启动时只执行 `CREATE TABLE IF NOT EXISTS`，不会给旧表补列或重建表。新版本启动时检查表结构（`store.ApplySchema` 之后的 `verifySchemaUpgrade`），
  没升级就**拒绝启动**并提示迁移脚本，不会带着旧库启动后让补采、合成、已确认缺失的读写逐个失败。迁移脚本随发布包提供，在安装出来的 Collector 单元里是
  `collector/schema/migrations/20261105-unified-dataset.sql`（仓库里是 `modules/collector/schema/migrations/`，打包时随 `collector/schema` 整个目录一起带上）。升级步骤：
  停 Collector → 备份 Collector 库 → `sqlite3 -bail <库路径> < <发布包>/collector/schema/migrations/20261105-unified-dataset.sql` → 换二进制并启动。库在控制机的 `<ControlRoot>/current/collector/data/moox_collector.db`（默认 `/data/moox/prod/current/collector/data/moox_collector.db`：组件的工作目录是 `<ControlRoot>/current/<组件>`，Collector 的默认相对路径是 `./data/moox_collector.db`；先 `ls` 确认文件存在再操作。清理命令 `moox-cli collector task purge` 的默认库路径取同一位置，可用 `--db-path` 覆盖）。
  **必须带 `-bail`**（遇到第一个错误就停）：脚本只能对未升级的库执行一次，对已升级的库重跑时第一条 `ALTER` 会失败，不带 `-bail` 的 sqlite3 会接着重建表并提交，
  把已有记录的 `c_series_tag` 全部丢成空串（统一数据集的记录主键冲突时整张表被清空）；带 `-bail` 时事务未提交，库保持原样。脚本做的事：
  给 `t_collector_resample_snapshots.c_members`（`'{}'`）、`t_collector_resample_jobs.c_series_tags`（`'[]'`）、`t_collector_backfill_notices.c_series_tag`（`''`）加列；
  `t_collector_kline_backfill_chunks` 与 `t_collector_source_absences` 的 `c_series_tag`（`''`）进了唯一键、主键，所以重建这两张表并拷贝已有数据。
  升级后的旧表里新增的列排在末尾，列顺序与全新建库不同，不影响读写（代码都按列名访问）。全新部署直接用 `collector.sql`，不需要迁移脚本（`migrations/` 目录不会被当成启动 schema 载入）。
- 单市场任务的行为与输出不受影响。统一数据集上只用一个市场的消费者也会受另一个市场拖慢（两个市场共用一份快照，周期要等两边都提交或到截止时间），只用一个市场的用户应选“分开”。
加密货币的采集请求固定用标签的来源；A 股股票的计划仍按标签来源分组，但实时采集与补采请求不写死来源，由 `config/markets/stockcn/route.yaml` 按频率给每个标的固定分配一个 primary（按路由 ID 与标的哈希，不随调用变化），失败或限流再按候选链回落，分摊各家的频率限制；序列标签固定为 `default`，写入行的 `source_provider`、`provider_id`、`source_id` 记实际取到数据的来源。

各行情源在函数进程内的并发与每秒上限写在 `configs/scf/stockcn/sources/market/*.yaml`，计划里 A 股的函数内并发（`concurrency`）与熔断并发（`feed_concurrency`）由它们推导，每函数标的数与函数个数由它们和权重、标的数估算（`auto_size`）。
补采、追赶、缺口修复这类持续几分钟到几小时的请求还会按压力信号自适应调速（控制方式参考 [agilelimiter](https://github.com/Yiming1997/agilelimiter)，按统计周期而不是按单次请求）：每秒上限是最大值，速率从它开始；行情源返回限流、繁忙立即减半；每秒汇总一次，超时、断连、5xx 的占比超过 5% 加 3 倍标准误差（一个周期至少 5 个请求）就降 20%；连续 2 个健康周期、降速后已过 3 秒、并且流量确实用到了当前速率的一半以上才升 10%；下限是上限的 10%。速率在本进程内按行情源共享。实时采集每 5 分钟只有 1～2 秒的突发，不使用。
交易时段市场的时序结果数据集还写分桶属性，取自 `packages/barclock` 的市场登记：stockcn 为 `alignment=session`、`calendar=cn_stock`；crypto 不写，策略按缺省的 `crypto_24x7` 处理。策略按 `calendar` 选交易日历（`internal/planner/taskresult/result.go`）。
创建校验按实际行情源能力判断：Binance 现货/合约支持 1m～1mo；东方财富 A 股（`eastmoney/equity`）支持 1m、5m。
腾讯源缺成交额时按 `close × volume` 估算写入 `amount`，`amount_quality=estimated_close_x_volume` 标明是估算值（其余来源为 `reported`）。
采集只从计划生效的周期起实时采集；历史数据用 `SubmitKlineBackfill` 补采。检查与自动补采只看采集计划覆盖的时间（每个数据集从时间线起点起：最早一次生效的周期，重新登记之后是重新登记选出的生效周期，见第 3 节“重新登记”），更早的数据只能由 `force` 补采：`force` 的范围可以早于最早的生效点，更早时间的标的集合沿用最早一段的标的，分块完成后同样读回确认（任务参数里已删除的 `history_policy` 在存量任务里解析时忽略，启动对账时会改写存量任务并重算定义哈希）。
`CheckKline` / `SubmitKlineBackfill` 是同步操作，服务端业务预算 300 秒（网关路由 310 秒，tRPC 超时 320 秒），浏览器超时 330 秒。

## 3. 实时采集链路

“拉取 + 云函数”方式（`pull` + `scf`，非 crypto 空间默认）是：腾讯云定时器触发函数，函数按环境变量里的采集计划自行采集并提交 Storage；crypto 默认走 WS 推送（`stream` + `local`，见第 3a 节），同样经 Access 提交 Storage、缺口同样由检查与补采修复。下面按云函数路径说明：

```text
Collector 对账协程（每个空间，每分钟）
  ├─ 读任务与标签成员，算出每个数据集的标的集合 hash 与函数分配
  ├─ 无变化：什么都不做
  └─ 有变化：选生效周期 P → Storage 登记序列快照 → 更新函数环境变量（新旧两份都带生效起点）
     统一数据集：两个市场各有自己的函数，两边的计划都包含这个数据集，序列是（标的、各市场的 series_tag）的并集，
     共用同一份快照哈希，各自只提交自己 tag 的序号；`Plan` 结构不变（SCF 严格解码，tag 由 `PlanSeriesTag(plan.Market)` 推出）。
     允许迟到取两个市场里较大的；一个市场的标的变化会让两个市场的函数一起重新下发
SCF 函数（Timer 触发）
  ├─ 按计划与事件时间确定本周期要采的（数据集、标的）
  ├─ 并发请求行情源，只保留已收盘的 K 线
  └─ 经 Access（11004）调用 CommitTimeSeriesBatch 写入 Storage；调用内按预算尝试或切换端点，最终失败项上报 CLS
Collector 自动补采（每个空间）
  └─ 扫描 Storage 里缺失的 K 线，分块调用补采函数写回
```

- 函数调用结束后的失败不由 Collector 即时重投；行情请求在调用内部仍可重试或切换候选源。剩余缺口由检查与补采统一修复：`moox-cli collector kline check` 比对
  Storage 与采集计划，`kline backfill` 补采；自动补采按水位扫描最近的缺口。自动补采只在发现缺口时建作业，
  所以近 24 小时的自动作业就是实时采集漏掉的 K 线，运行状态页据此统计“实时缺口”。
- **行情源缺失**：补采后复查仍缺的 K 线可能是行情源本来没有（停牌、无成交的分钟）。单根分块直接确认；多根分块第一次
  记下仍缺的区间并退回重跑，连续两次缺的完全一样才确认，不一样就继续重跑，超过最大尝试次数才失败。确认的区间永久写入
  `t_collector_source_absences`，检查、自动补采与历史扫描都扣除它们（整段重拉不扣除），不再算缺口、不影响健康等级。
  行情源后来补上数据时用 `ClearSourceAbsences`（页面“清除并重新检查”）按数据集清空，并让历史扫描重新进行。
- **统一数据集的检查与补采按序列（标的、series_tag）**：数据集的一段计划里出现两个以上 `series_tag` 才进入按序列模式（单 tag 的数据集读法不变，读取不带 tag）。
  期望点数、缺口（`KlineGap.series_tag`）、`MaxCheckPoints`、`MaxGaps` 都按序列计；计数接口会把同一标的的不同 tag 合并，所以按 tag 分请求，
  读行的 selector 也带 tag。只缺永续的一段时间会被查出，补采按（标的、市场）找计划：缺口 tag 经 `SeriesTagMarket` 得到市场，只用市场类型相同的计划，
  写出的行 tag 与缺口一致，不会写出现货行；补采分块、已确认缺失（`t_collector_kline_backfill_chunks`、`t_collector_source_absences`）带 `c_series_tag`，
  并放进唯一键、主键（单序列为空串）。补采确认后发布的 `event.collector.kline.backfilled` 在按序列模式下带 `series_tags`，单序列的事件不变。
- 补采作业的失败分块可以 `RetryKlineBackfill` 重试；已结束的作业由每分钟的维护任务清理：自动作业保留 7 天，手动作业保留 30 天。
- 自动补采每 5 分钟一个槽、槽内偏移 2 分 30 秒后才扫（避开整点与每分钟开头的采集高峰），每次只检查水位向前重叠 5 分钟起、
  最多 1 小时的窗口，落后时分多次追赶。
- **先计数、再读行**：检查（自动补采、手动检查、历史扫描）先用 `PrimaryStore.CountTimeSeriesRows` 按标的统计区间内已有的根数
  （每批 500 个标的、只回传计数），根数正好等于“应有 - 已确认缺失”的标的没有缺口；只有其余标的才读行（每批 50 个）定位缺口，
  历史扫描中一根都没有的标的（没有历史）也不读行。读取量随缺口而不是随标的数增长。深度检查要校验字段、强制重拉不读数据，二者不计数；
  计数失败（例如 Storage 未升级）时退回逐行比对。读行时行响应约 200 字节一行，跨主机调用的压缩（恒定开启）
  不能去掉，否则缺口多时公网链路会被占满、读超时，水位无法推进并拖慢同时段的策略读取与事件投递（曾导致每小时约 9 分钟的整体变慢）。
  已知局限：计数只比对数量，若某根已确认缺失的 K 线后来补上、同时另一根缺失，数量恰好相等时会漏报这一根；A 股的应有时间点只取交易时段内的桶（按 barclock），
  区间内非交易时段若有写入同样会抵消一根缺失。
- **历史缺口发现**：检查与自动补采只看采集计划覆盖的时间，早于数据集最早生效点的数据（旧的采集方式或历史导入留下的）里的孔洞，
  它们看不到。Collector 在自动补采之后按数据集定期读回最早生效点之前的 500 根 K 线（同一空间每 5 分钟最多扫一个数据集，
  同一数据集每 24 小时扫一次，读取失败 1 小时后重试），只报告每个标的第一根 K 线之后的缺口（新上市的标的前面没有数据，不算），
  **不自动补采**：结果（扣除已确认缺失后的缺口根数、标的数与至多 200 组缺口）写入 `t_collector_history_scans`，扫描节奏也以它为准，
  重启不丢；日志里 `collector history scan` 是每个数据集的汇总，`collector_history_gap` 是范围相同的缺口合并后的一组。
  操作员在运行状态页点“补采确认”（`ConfirmHistoryGaps`，CLI `kline history-confirm`）按记下的缺口精确补采，
  行情源本来没有的部分在补采时被确认，以后不再报告；
  还没被确认的（尚未上市、没有成交的缺口）会每天重复提示，可以忽略，或点“补采确认”让补采把它们确认下来。
- 周期是否完成以 Storage DataNode 为准（见[存储](存储.md)第 4 节）。
- 采集计划由 Collector 生成并保存在 `t_collector_fetch_plans`；`moox-cli collector fetch-plan` 查看函数分配与变更进度，
  `moox-cli collector status` 与控制台“采集任务 → 运行状态”查看总体健康与各数据集的自动巡检进度、缺口和补采情况（见第 11 节）。
- **重新登记**：序列快照登记在 Storage 的 DataNode 里。Storage 数据被整体清空后快照没了，函数的周期提交会因“快照缺失”被拒绝，
  而对账只在数据集标的集合 hash 变化时才登记。`moox-cli collector fetch-plan reregister --space-id <空间> --yes`
  （RPC `ReregisterFetchPlan`）把最近一份已生效计划里全部数据集的 hash 清空，下一轮对账会把它们都当作变化：生成新计划、重新登记快照、
  选新的生效周期，函数沿用不动。被清空的 hash 同时是时间线的重置标记：该空间此前的全部计划段作废（包括已退役的数据集，
  它们以后重新启用时同样从新的生效周期开始），每个数据集的时间线从新计划的生效周期重新开始。
  新快照登记之前（通常 1～2 分钟）这些数据集不检查、不补采、不扫历史，运行状态页暂不列出，超过 30 分钟仍没有新计划接手时
  运行状态报异常；登记之后检查与自动补采从新的生效周期起，历史扫描读回它之前的 500 根，清库前计划覆盖的时间不再当作缺口。同一个调用清掉该空间的补采作业、自动补采水位与历史扫描记录
  （水位留空时自动补采从时间线起点扫起，也就是新的生效周期）。空间里有未生效的计划时拒绝。这个 RPC 是新增的网关路由（只允许 `moox-cli` 调用），服务目录变化需要 Admin、Monitor 与各主机 host-gateway 一起发布后 `moox-cli` 才调得通，见[部署与运维](../部署与运维.md#_8-常见故障与处理)。完整的清库顺序见[部署与运维](../部署与运维.md#清空全部数据重新积累)。
- 函数的 Storage 入口固定为同地域的一个 Access 实例，地址和实例身份（`access@<主机ID>`）由部署清单派生；
  函数的运行参数（计划、Storage 入口、DNS 路由、CLS 配置）只写在 SCF 环境变量里，SCF 代码包本身不带任何凭据。
- 函数日志不会自动投递：每次调用把失败项（`market_fetch_item_failure`）、批次摘要（`market_fetch_batch`）、
  偏慢或重试过的单项（`market_fetch_item_slow`）与写入 Storage 的耗时（`market_fetch_commit`）上报到 CLS，
  字段与索引见[部署与运维](../部署与运维.md)。整点前后行情源响应变慢时，用这些阶段耗时区分慢在排队、DNS、建连、
  TLS 握手、行情源首字节还是重试（见部署与运维的“上报内容”）。

## 3a. 采集方式与执行端（WS 推送）

采集方式按数据集绑定，存在 `t_collector_ingest_modes`：`stream` 由 `collector-stream` 接收交易所 WS 推送的收盘 K 线，`pull` 定时拉取 REST；
`executor` 是拉取与补采的执行端，`scf`（云函数）或 `local`（`collector-stream` 同进程的本地执行端）。新数据集按空间配置 `scf_plan.spaces.<空间>.default_ingest` /
`default_executor` 初始化（setup 渲染：crypto 为 `stream` + `local`，其余 `pull` + `scf`）；已在已生效计划里的数据集第一次落库时按现有执行端。之后以库为准，
只由 `moox-cli collector ingest-mode set` 切换。

- **计划项**：对账器把期望状态分给三类执行端：SCF 函数（`moox-fetch-plan-…`）、`stream-<空间>-<市场>`、`local-<空间>-<市场>`。SCF 专属步骤（建函数、改环境、定时器、发布租约）
  只作用于 SCF 项；推送与本地项由 `collector-stream` 经 `StreamCollector.PullStreamPlan` 拉取，10 秒一次心跳上报已应用的计划与阶段，Collector 以心跳确认代替云端读回。
  条目上限：SCF 每函数 200，推送与本地 4000。
- **截止跟随采集方式**：`stream` 的 `allowed_lateness_seconds` 默认 1m 5 秒、1h 8 秒（`stream.lateness_s`，任务参数显式指定的以任务为准），`pull` 沿用 SCF 的值（合约 20 秒，见第 10 节）。
  `collector-stream` 的周期闸门在全部标的到齐时立即提交，否则在 `收盘 + 截止 − commit_reserve_ms`（默认 1000）提交已到的部分，缺的标的由补采补齐。
- **交接**：`ingest-mode set` 之后下一轮对账生成交接计划，按频率选生效周期 P（至少提前 3 分钟）：P 之前旧执行端写，P 起新执行端写；截止在 drain 阶段（旧截止的窗口结束后、最后一次下发之前）
  改为新值（只看时间，不等过渡阶段的确认：旧端失联或云端作业慢时也按时改，否则新执行端的周期会因截止还是旧值而整期被拒）。交接与标的变更分开（同时发生时先完成标的变更），Collector 重启后按库里的计划续跑。`--force` 用于旧执行端失联：交接计划不等失联端确认，已打开的计划也不再等。
  drain 结束后 SCF 函数去掉切走的数据集，函数里全部数据集都切走后停用定时器（函数保留作为备用）。
- **补采**：补采按数据集的 `executor` 调用 SCF 补采函数或本地执行端 `MarketFetchExecutor.Invoke`（`collector-stream` 的 11450 端口，独立并发上限 4）。
- **下架**：`collector-stream` 在合约上下架推送或连续 3 个 1m 周期没有收盘推送时上报疑似下架标的，Collector 立即同步对应市场的自动标签（快照取数重试 3 次，失败时保持成员）。
- **运行状态**：周期统计（到达、截止时仍缺、是否提交）进 Collector 指标，不落库；运行状态页“函数”区列出推送与本地项、连接与最近周期。
  Monitor 在心跳中断超过 3 分钟、某数据集连续 3 个周期有失败标的（疑似下架不计）时告警，见[监控](监控.md)。
- **下游**：因子引擎按连续水位逐期计算，零提交或缺失超过阈值的周期会阻塞，补采成功后 Collector 调 `FactorMgr.NotifyPeriodsFilled` 通知补齐，见[因子](因子.md)。

全部数据源登记在行情源目录（`internal/sources/catalog`，类型 `marketdata.Catalog`）：一个（市场, 品种, provider, source_id）对应一个工厂。
标的同步、SCF 与本地取数、`collector-stream` 接收都从目录按能力取用：实现了 `InstrumentFetcher` 的用于标的同步，`KlineFetcher` 用于取数与补采，
`stream.Provider` 用于 WS 接收。新增交易所只需实现这些接口并在目录里加一项登记。

数据源的地址、限流等配置在 `configs/sources/market/*.yaml`（SCF 包内为 `sources/market/`）；
A 股的市场与数据源路由在 `config/markets/stockcn/`（`market.yaml`、`route.yaml`）。每个数据源按出口 IP 维护独立的限流与
熔断，单个数据源失败时在本次调用内切换到备用数据源。

**A 股 K 线。** stockcn 走 SCF 定时直采（`pull` + `scf`），内置任务“A 股 K 线 5m”“A 股 K 线 1d”采沪深 300 成分股（标签 `cn_hs300`），默认停用。
`route.yaml` 按频率分候选链，路由 ID 是 `stockcn_equity_kline_<频率>`：

| 频率 | 主 | 备 |
| --- | --- | --- |
| 5m | 通达信（权重 4）、东方财富（`push2his` K 线接口，`klt=5`，权重 2），按权重对股票固定分配 | 按通达信、东方财富、新浪、腾讯的顺序回落；每家最多试 3 次再换下一家；新浪、腾讯只做备源（收盘后头几秒给的是未定稿值，见下文） |
| 1m | 新浪、腾讯 | 通达信、东方财富 |
| 1d | 通达信 | 东方财富（`push2his` K 线接口，`klt=101`） |

- 都存不复权 OHLCV：东方财富请求 `fqt=0`，通达信请求固定为不复权，主备切换时口径一致；除权日前后跨越除权的窗口会有一次跳变。
- 腾讯没有成交额，按收盘价 × 成交量估算并标 `amount_quality=estimated_close_x_volume`；通达信的成交额是 float32，末位有误差。
- 东方财富与通达信日内 K 线的时间标签都是收盘时刻，归一化时减去一个周期作为行键（开盘时刻）。通达信把上午最后一根标成 13:00，
  按同一交易日的前一根（上午最后一根，5m 是 11:25）处理。成交量统一为股（东方财富的“手”乘 100）。
- 回看能力按频率声明：东方财富 1m 为 24 小时、5m 为 30 天，通达信 365 天；超出东方财富回看窗口的补采落到通达信。
  日线：通达信 10 年（按交易日偏移取），东方财富任意区间（按日期取，能取到上市首日）。
- **日线的行键是日期键**：交易日期的 UTC 零点（10-09 的日线是 `2026-10-09T00:00:00Z`），与 `packages/barclock` 的 1d 键、统一校验、
  完整性检查和策略一致；只有交易日有桶。`close_time` 是键加 24 小时，不是 15:00；`trade_date` 与日内行一样是交易日的上海零点。
  交易日 D 的日线在 D+1 日 00:00 UTC（北京时间 08:00）到期并采集。东方财富日线的成交量以手为单位，乘 100 后与通达信差在 100 股以内。
  完整性检查里日线的连续缺失不按周末、节假日拆段，一个标的一年的日线是一个补采分块。通达信按市场的交易日序号算偏移，
  标的在补采区间之后停过牌时取回的窗口偏旧，可能缺末尾几根（补到今天的整段补采不受影响）。
- 函数每 5 分钟触发一次，只采交易时段内的桶：午休、收盘后、非交易日直接返回 `no_work`。

**A 股 5m 为什么用通达信和东方财富做主源，新浪和腾讯做备源。** 选源看的是“收盘后尽快拿到定稿值”，不是谁先返回：

- **四个来源的返回里都没有“这根 K 线已完成”的标记。** 东方财富（`push2his`）每根只有时间、开收高低、成交量、成交额和涨跌幅、换手率等派生字段；新浪是 `day/open/high/low/close/volume/amount`；
  腾讯是按位置排列的数组；通达信是二进制的时间、开收高低、成交量、成交额。进行中的那一根和已收盘的那一根格式完全一样，只能靠本机时间判断收盘，
  再靠“等到值稳定”保证取到的是定稿。所以必须实测各家在收盘后多久给出定稿值，不能凭返回字段判断。
- **实测方法与结果**（2026-11-06 盘中，南京 SCF 同 VPC 子网，14:35～14:55 连续 5 个 5 分钟边界，每个来源每次 60 只标的、共 300 个样本，
  收盘后每 200 毫秒轮询目标 K 线，记下第一次出现的时刻与数值，8 秒后再取一次看数值有没有变）：

  | 来源 | 首次出现（中位 / 99 分位） | 首次出现之后 8 秒数值又变了的比例 |
  | --- | --- | --- |
  | 东方财富 | 183 / 271 毫秒 | 0 |
  | 通达信 | 120 / 354 毫秒 | 0 |
  | 新浪 | 135 / 242 毫秒 | 69%（约一半收盘价差 0.01～0.04，成交量中位差 1.5%～5.8%，最大 32%） |
  | 腾讯 | 142 / 250 毫秒 | 85% |

  四家出现得都很快，区别在于新浪、腾讯一开始给的是未定稿值，之后还会更新；通达信、东方财富第一次给的就是最终值。
  Storage 的周期一旦全部提交就锁定，早取到的未定稿值改不回来，所以不能让它们做主源。
- **限频与稳定性。** 同一实测里四家都扛得住 64 并发突发、每秒 80 次持续，没有触发频控；通达信是 TCP 直连，延迟最低且不随并发上升。
  各源在函数进程内的并发与每秒上限写在 `configs/scf/stockcn/sources/market/*.yaml`，取值都小于各家的频控值，不需要留很大余量。
- **只剩两个主源，要避免单个出口 IP 触发频控，所以把函数拆细并让出口 IP 尽量分开。** 沪深 300 约 200 只落在通达信、100 只落在东方财富。
  函数按标的数估算个数（`auto_size`），并设了下限（`min_functions`，现为 8）：每个函数分到的标的少，同一时刻每个出口 IP 对单个来源发出的请求就少。
  但函数个数不等于出口 IP 个数：SCF 的公网出口来自云上共享的地址池，不同函数可能用同一个 IP。2026-11-06 实测线上 15 个函数连续探测两次，
  只有 9～10 个不同 IP，个别 IP 被 3～4 个函数共用，同一个函数的出口 IP 基本稳定、实例回收后可能变。
  所以 Collector 在**计划新建了函数之后（包括云端函数被删后按已生效计划重建）只做一次**出口 IP 去重。这是与市场无关的公共能力，封装在 `modules/collector/internal/egressbalance` 包里，
  任何空间都能在 `scf_plan.spaces.<空间>.egress_balance` 里开启（A 股默认开启）：核对云端没有其他问题时，调用每个函数的 `egress_probe` 取公网出口 IP，
  把共用同一个 IP 的函数（每个 IP 只留 `max_per_ip` 个，默认 1）交给已有的“云端缺失重建”流程删掉重建，新实例会重新分到地址；
  每轮相隔几分钟，最多 `rounds`（默认 5）轮，连续两轮不同 IP 数没有增加就说明地址池里的 IP 不够，停止并保持现状。
  删除重建期间这些函数没有数据，所以用 `idle_start`、`idle_end`、`timezone` 限定允许重建的时段（A 股是北京时间 15:10 到次日 09:00，不写表示任何时候）；
  做完（或停止）之后不再探测，也不做每小时的检查。这只能降低重叠的概率，不是保证：实例回收后出口 IP 可能又变；要复查随时用
  `moox-cli collector function probe-egress --space-id stockcn`。
- **备源的作用。** 通达信、东方财富失败（连续 3 次）才会换到新浪，再不行换腾讯。备源取到的值可能是未定稿的，但总比这一根缺失好，缺口以后可由补采或完整性检查修复。
- **成交量与成交额的小误差不作为选源依据。** 各源成交量约差万分之几，腾讯没有成交额只能估算（`amount_quality=estimated_close_x_volume`），通达信成交额是 float32 末位有误差，
  这些在允许范围内，不影响双均线等因子结果。
- **重新评估。** 来源的行为会变，换主源或调权重前要在盘中至少连续测几个 5 分钟边界，按上面的方法（首次出现时刻、之后数值是否变化、限频）重新对比。

**交易日历只有一份。** A 股交易日历内嵌在 `packages/marketcalendar`（`cn_stock`），交易时段登记在 `packages/barclock`（`Asia/Shanghai`，
`09:30-11:30`、`13:00-15:00`）。Collector 判断“某根是不是交易桶”、取最近收盘的桶、检查日历覆盖期统一经过 `internal/markets/trading.go`，
采集过滤、完整性检查、补采与通达信的时间标签换算共用它（K 线合成直接按 barclock 的市场登记取时钟）；SCF 包里不再带日历文件。日历每年更新一次，步骤见 skill 的 `references/fresh-deploy.md`。

## 4a. 资金费率（可选输出字段）

资金费率是行情源的一项可选能力（`marketdata.FundingRateSource`），目前只有币安 U 本位永续实现。K 线采集任务可以在输出字段里选 `funding_rate`，**默认不选**；不选时采集、写入、建列与原来完全一致。

**字段口径。**

- 值是结算时刻落在 `[bar_start, bar_end)` 内的资金费率之和，本根没有结算写 0；取币安返回的小数原值（0.0001 即 0.01%），字段目录的单位是 `ratio`。
- 结算可能比整点晚 1 毫秒，归属按原始毫秒判断；结算间隔有 8 小时、4 小时、1 小时三种，所以按区间求和。
- 第 k 根的值是第 k 根开盘时刻那次结算，这一刻持有的是第 k 根开盘调仓之前的仓位。按资金费结算的账本要用第 k−1 根期间的持仓结算第 k 根的费率。
- 数据集列的属性写 `fill=zero`：因子引擎读列时没有 `fill` 属性就沿用上一根，会重复计费。

**适用条件**（建任务、改任务都在 `validateCollectionTaskTagRoutes` 里校验，不满足直接拒绝）：

- 频率只能是 1h、1d。1m～30m 收盘时结算记录可能还没公布；1w、1M 推送不支持，一次要取的数据也太多。
- 标签必须全部是永续，不能是统一数据集；行情源要具备资金费率能力（按行情源目录判断，由 marketwiring 注入）。
- 重采样不合成这一列：源数据集带 `funding_rate` 也可以重采样，结果里没有这一列；只有重采样的输出字段显式要它时才拒绝（`resample.ValidateTaskParams`）。
- 管理台只在以上条件满足时显示这个选项，条件不再满足时去掉已选的这一项。

**取数。**

- **限速**：资金费接口和 fundingInfo 共用“每 5 分钟 500 次”的配额。进程内只有一个限速器，每秒最多 1 次，实时请求排在补采请求前面；收到 429、418 时暂停全部资金费请求，连续触发时退避翻倍（5 秒起，最长 5 分钟），成功一次复位。请求在客户端只发一次，不在请求内重试。
- **查询方式**：区间左闭右开。不带 symbol 时按 4 小时分段查全部合约，某段满页（1000 条）就对半拆开重查；带 symbol 时按时间往后翻页，满页总要再翻一页确认。全市场查询里格式不对的记录跳过并记日志，指定合约的记录格式不对报错。
- **进程内小时缓存**：实际运行拉取管线的进程（collector-stream、SCF）各有一份按小时的全市场结算缓存，键是（小时, 合约）。控制机上的 collector 不建。
  - 只有当前计划（推送或本地拉取）里有数据集选了 `funding_rate` 时，collector-stream 才启用整点取数：每个整点后约 2 分钟取上一个整点开始的这一小时，收盘前约 5 分钟再取一次覆盖，避免个别晚公布的记录被写成 0。启用时补取上一根与当前这一根已经过去的小时。
  - 没就绪的小时槽按需补取，走同一个限速器；取数失败按退避重试。SCF 没有常驻缓存，同样按需补取。
  - 1d 取本根覆盖的 24 个小时槽，全部就绪才算就绪。
- **推送**：周期提交前只读缓存，不调 REST。缓存没就绪时这一期先挂起，取到后回到这个数据集的协程再提交；到最晚提交时刻仍没有，这一期不提交，交给缺口补采（这一期的标的全部记为缺失）。
- **拉取与补采**：资金费在批次开始时与 K 线并行取。实时批次读缓存；补采、追赶、缺口修复按合约查本块区间。取不到资金费时，只让选了这一列的写入目标的这一项失败，错误归为可重试的 `provider_error`，其他目标照常写入。不能把缺的几根丢掉照常报成功，否则补采复查连续两次缺同样的根就会登记成“行情源没有”，之后不再补。
- **失败可见**：指标 `moox_collector_funding_fetch_failures_total{reason}`（`rate_limited`、`http_status`、`network`、`protocol`、`malformed_record`、`canceled`），日志带合约与区间。

**补采与字段。** 补采沿用当时计划里的输出字段：任务后来加上 `funding_rate`，老区间不会自动补上这一列。需要这一列的任务从创建起就选上它；历史用公开数据导入或 `kline backfill --force` 补。

**执行端。** 选了 `funding_rate` 的数据集要用 collector-stream（推送加本地拉取）。SCF 函数包要重发带这项能力的版本后才能执行这类数据集；SCF 里 1d 一次要补取 24 个小时槽，每秒 1 次的限速下超出函数时限，不适合 1d。

## 5. DNS 快照

SCF 函数需要快速、稳定地连接行情域名。Collector 维护一份 DNS 快照写入函数环境：

- `egress_proxy.dns.domains` 非空时，每 5 分钟经进程级共享网关向独立出口代理请求经过 TCP 探测、按延迟排序的公网 IPv4；
- 请求失败或某个域名未解析时保留上一次成功的结果，并回退到本地 DNS；
- 最近一次成功的快照会持久化，进程重启后先恢复再刷新。

SCF 仍以原域名作为 Host/SNI，IP 只用于拨号；所有 IP 都失败时直接连接域名。

常驻采集的 HTTP 客户端对 `egress_proxy.domains` 中的域名调用出口代理 `Do`，HTTP 与 DNS 复用同一 `collector` 身份和目录。代理保留目标状态码，过滤认证/Cookie 头并返回正文（传输压缩由 tRPC 帧层统一完成；该客户端整体超时 60 秒，仅用于控制面标的同步）；请求失败不会回退本机直连，DNS 快照的 IP 也不能绕过代理。其他域名继续本机连接，短生命周期 SCF 使用自己的直接行情出口。

## 6. 标的与标签同步

Storage 的标签只是一组标的，标的同步的业务配置写在标签属性里，由 Collector 解释：`market_type`（市场类型）、`sync.source`（数据来源）、`sync.cron`、`sync.timezone`（同步周期与时区）。
种子（`config/setup/metadata.yaml`）里标签只定义一处。是否支持某个（来源，市场类型）由 Collector 的行情源目录里的标的 lister 决定，Storage 不登记也不校验这类能力。标的同步复用进程级网关客户端与出口代理 HTTP 客户端：

定时同步只处理 `sync.cron` 到期的标签（没有运行记录、标签在上次运行后被改过也算到期）。首次部署、交易所接口恢复或标签配置变更后，可用 `moox-cli collector subjects sync` 立即同步：它调用 `CollectMgr.SyncSubjects`，无视 cron 窗口，只处理 `mode=auto` 且配置了 `sync.source`、`market_type` 的标签，返回每个标签的状态、标的数和失败原因。手动同步与定时任务共用一把互斥锁，同步正在运行时返回冲突；调用预算 180 秒，服务端 170 秒后以失败结果返回。网关只向 `moox-cli` 开放这个方法。

- **指数成分标签**：标签配置了 `sync.index`（指数代码）时，同步该指数的成分股，而不是数据源的全部标的。目前只登记了东方财富的沪深 300
  （`000300`，成分板块 `BK0500`）：内置自动标签 `cn_hs300` 每天北京时间 08:40 同步。取到的条数必须等于接口给出的总数，翻页不完整就报错、
  不应用快照，保留上一次的成员。成分 lister 按（来源，指数）单独登记（`subjectsync.IndexListers`），不出现在 `ListSubjectListers` 的来源选项里。
- **自动标签**：每分钟第 30 秒检查是否到期，按标签属性声明的数据源（`sync.source`）拉取完整成员快照并调用 `ApplyTagSnapshot`（只表示“把成员设成这份快照”，被移出成员的 `inactive_at` 取 Storage 收到快照的时间）。运行状态写进 Collector 自己的库（`t_collector_tag_sync_runs`）；失败记在这张表里并打日志、出指标，不再上报给 Storage。手动标签成员由用户维护。
- **标的属性**：快照里新出现的标的由快照新建（`subject_id`、名称、时区与属性），已有标的的属性由属性维护任务更新；两条路径写出同一组属性键：crypto 是 `subject_type=crypto_pair`、`market=CRYPTO`、`currency`、`base`、`quote`、`pair`，stockcn 是 `subject_type=stock`、`market=交易所`、`currency=CNY`、`exchange`。
- **同步状态与可选来源**：`ListTagSyncStatus(space_id)` 只读返回上述运行状态，Monitor 的标签检查（`failed` / `stale`，`stale` 的周期按 `sync.cron`、`sync.timezone` 算，没有运行记录的按 `stale`）与管理台标签页读它；`ListSubjectListers` 只读返回能提供标的快照的（来源，市场类型）组合，管理台新建自动标签的来源与市场类型选项来自它。
- **属性维护**：每分钟第 45 秒检查 `app.yaml` 中的 `subject_sync.attributes`；按任务时区判断 `(触发时间 - 1 分钟, 触发时间]` 内是否有计划时间。默认在北京时间 08:10:45 刷新 A 股与加密货币的名称和属性，首次启动也遵循该规则。

**采集名单排除**：需要在交易所快照之外临时去掉某些标的（公告下架、数据异常）时，用 `moox-cli collector subjects exclude --space-id <空间> --subjects A,B [--market swap] --reason <原因> [--expires-in 72h]`
（RPC `SetSubjectExclusions` / `ClearSubjectExclusions` / `ListSubjectExclusions`）。排除只作用于采集计划，标签成员与标的属性照常同步；对账在计算期望状态前去掉排除的标的，
名单一变下一轮（≤1 分钟）生成新计划、按提前量生效，SCF 与推送一样生效；已打开的计划（包括进行中的交接）先推进完再生效。到期后标的自动回到计划（期间的历史需要时用补采）。
调用方为控制台、`moox-cli`，以及经 Access 用外部身份 `collector-operator` 调用的旁路程序（只放行这三个方法与 `SyncSubjects`；签名密钥在控制机上用 `moox-admin-cli keys export --caller collector-operator` 导出，请求的 `operator` 字段写设置人）；每次变更写活动日志 `collector.subject_change`。排除全部标的时数据集按“数据集消失”的去抖（5 轮）后退出计划，到期后作为新数据集回到计划。

两个定时器各自通过 `timerjob` 防止重叠，运行上限为 10 分钟。标签同步失败不会阻塞周期规划；退出时先取消并等待同步任务，再关闭 HTTP、网关客户端和数据库。

## 7. K 线重采样

`kline_resample` 类型的任务在 Collector 进程内执行：读取源数据集的 K 线，生成更长的周期（如 5m → 45m、1m → 1h）
并写入任务的结果数据集。该功能默认关闭，在 `config/app.yaml` 的
`kline_resample.enabled` 中开启。

**创建**：新建合成任务时选一个**源采集任务**（`kline` 任务，或另一个合成任务，可逐级合成），再填目标频率。源数据集、
源周期、序列标签由 Collector 从源任务推导并保存（任务参数 `source_task_id`），不需要手填；`PreviewKlineResampleSource`
给出推导结果并按下面的规则校验目标频率，控制台据此即时提示。合成任务继承源数据集的标的范围，不能单独选择标签；创建后参数不可修改。

**合成规则**（创建、更新、种子导入、启动清单都走 `resample.ValidateTaskParams`，不满足的直接拒绝）：

- 源、目标都是 1m～1d 的定长周期，目标必须是源的整数倍；日内周期写成 `<N>m` / `<N>h` 且整除一天（45m 一天 32 根）。
- 市场必须登记了分桶方式（`packages/barclock`）。24 小时连续市场（crypto）按 `epoch_utc` 从 Unix 零点切分；
  交易时段市场（A 股）按 `session`，每个交易时段从开盘起切分，不跨午休、不截短，休市日没有桶，`1d` 为交易日一根。
  交易时段市场的日内源、目标周期必须整除每个交易时段（A 股两段各 120 分钟，目标只能是 120 的约数，45m、4h 拒绝并列出可选周期）。
  没有在 barclock 登记的市场不能合成；交易时段市场的交易日历取 `packages/marketcalendar`（目前只有 A 股 `cn_stock`）。

**统一数据集作源**：源任务挂了现货、永续两个标签时，推导出的合成任务 `market_type=multi`，源序列写在 `source_series_tags`（每个市场一条；
单序列的源仍是 `source_series_tag`，两者不能同时给出），`PreviewKlineResampleSource` 同样返回 `source_series_tags`。
合成按 tag 分别进行：源标的按 tag 各取自己标签的成员（用标签的 `market_type` 与 `SeriesTagMarket(tag)` 对应，不取并集），
目标数据集的快照按（标的、tag）生成，某个 tag 下没有的标的不进快照，不会生成不存在的序列；周期完成事件带 `universe_series`、`failed_series` 时，
失败的序列不合成、其他序列照常。补写通知与 `event.collector.kline.backfilled` 在统一数据集上带 `series_tag(s)`，合成订阅它时只对涉及的序列建作业。
目标数据集同样是统一数据集（`market_type=multi`）。

**触发与执行**（按“数据集 × 桶”批量：一次读出全部标的的源窗口，逐标的聚合，再批量写入）：

- **事件主路径**：配置了顶层 `event_bus` 时，订阅 `DatasetPeriodCompleted`（`event.storage.dataset.period.completed`），按源数据集与频率筛选；收到桶内最后一个源周期的完成事件，
  就合成该桶（`degraded` 事件里失败的标的先跳过）。45m 收盘后约 1～3 秒写入。
- **兜底检查**：每分钟第 5 秒，检查每个任务最近 `fallback_lookback_bars` 根已收盘的目标 K 线（收盘已过 `fallback_grace`），
  按目标数据集里缺的行补齐；不保存状态。没有事件总线时它是唯一的实时路径，延迟约 1 分钟。
- **补采完成事件**：补采分块读回确认成功时，在同一事务记补写通知；发布协程按（空间、数据集、频率、来源、作业）合并，先对源数据集追加
  同步点，再经本地 outbox 发布 `event.collector.kline.backfilled`（只带元数据，`sync_request_id` 是同步点 ID，读 View 的消费者要先等它）。
  合成订阅它，对依赖该数据集的合成任务提交 `source_backfill` 历史作业（最早开始时间 = 确认时刻 + 2×`exec_timeout`，保证不被读到旧源数据的执行覆盖）。
- **历史合成**：`SubmitKlineResampleJob` / `GetKlineResampleJob` / `ListKlineResampleJobs` / `CancelKlineResampleJob`，
  CLI 为 `moox-cli collector resample backfill / jobs / cancel`。范围按 UTC 解析并向外对齐到目标桶，最多 10080 个桶，按游标推进、
  进程重启后继续；源数据不完整的标的跳过并计数（记录样例）；作业结束前对目标数据集追加同步点并等 View 追上。同步点成功表示 View 已处理前面的事件；超过 `[storage_view.max_age]` 的历史行会被过滤，不能据此保证整个合成区间都在 View 可读。

**写入目标**：落在已登记快照内且周期未截止（收盘后 2 分钟）的标的用周期提交（`CommitTimeSeriesBatch`），由 Storage 判断是否到齐并发出目标数据集的
`DatasetPeriodCompleted`（`source=ledger`）；首次生效点之前的桶、截止之后的补写、快照之外的标的用普通写入，并记为补写通知。快照在兜底检查里随源数据集的标的集合登记，
生效点是当前时间之后的第一个目标桶边界。

**不加锁**：事件、兜底、历史作业可能同时处理同一个桶——读到同一份源数据时写出同一个值；源数据只会被补采改写，补采确认后一定触发重算，结果最终一致。

## 7a. 下架检测

Collector 把交易所的下架信息变成事件 `event.collector.instrument.delist_scheduled`（交易所、市场 SPOT/SWAP、交易所代码、下架时间、来源、首次发现时间、范围 ALL / PAPER_ONLY），
由[事件中心](事件中心.md)按规则处理（通知你的接口，或禁止买入并在下架前平仓）。检测放在 Collector 而不是 collector-stream：Collector 有数据库、EventBus 发布身份和发件箱，也已经经出口代理访问币安。
它只检测下架**发生之前**的信息；`collector-stream` 发现的“疑似下架”（见 3a）是下架之后的检测，两者不重叠。

每 10 分钟轮询一次，只保留 USDT 计价的现货和 U 本位永续，接口来源忽略下架时间已过的条目：

| 来源 | 接口 | 说明 |
| --- | --- | --- |
| 币安现货 | `GET /sapi/v1/spot/delist-schedule` | 行情数据类：请求头带 `X-MBX-APIKEY`，不签名。用专用只读 Key，经 SecretMgr 的 `GetReadonlyExchangeKey`（只返回 `exchange-binance-production-readonly` 的 `key_id`，Collector 拿不到任何 Secret 明文，也拿不到 Trade 的交易密钥） |
| 币安 U 本位合约 | `GET /fapi/v1/exchangeInfo` | 单独解码：永续合约的 `deliveryDate` 正常是占位的远期值（官方样例 4133404800000），出现近期的真实时间才算下架；季度合约、非 USDT 计价忽略 |
| OKX 永续 | `GET /api/v5/public/instruments?instType=SWAP`（`openapi.okx.com`） | 永续合约的 `expTime` 正常为空，有值才算计划下架 |
| 手工登记 | RPC `RegisterDelistNotice`、`moox-cli collector delist register`、管理台「事件中心」“事件”页签的“手工登记” | 补漏报和演练；可以补录过去的下架时间（仍写下架名单、只核对不下单）；`paper_only` 时范围是 PAPER_ONLY。登记后到 T−24h（已不足 24 小时的立即）会自动卖出策略持有的实盘仓位，命令行加 `--yes` 之前先和用户确认标的与下架时间；演练用 `--paper-only`，只平模拟盘，但同样全局禁止买入这个标的，直到演练记录结束 |

- **去重与发布**：新表 `t_collector_delist_notices`，（交易所、市场、代码、范围、下架时间）唯一；同一条再次被报告只更新最后报告时间，不再发布。新条目在同一事务里写进发件箱 `t_collector_event_outbox`，由 Collector 级的中继发布（不丢）。
  事件 ID 由（交易所、市场、代码、范围、下架时间）确定性生成，信封空间固定为系统空间 `mooxsys`，subject 是“交易所:市场:代码”。下架时间变了就是新条目、发布新事件，事件中心按同一标的合并。
  同一来源一轮里同一（交易所、市场、代码、范围）出现多条（币安现货计划里同一个代码可能在两个下架时间组）时，只取最早的下架时间，免得每轮在两个时间之间来回发布。
  **手工登记与接口的优先级**：以接口为准。范围 ALL 的手工登记时间和接口报的不同，下一轮轮询（10 分钟内）就会按接口时间重新发布一次（事件中心的执行记录跟着改回接口时间）；
  想自己定下架时间做演练，请用 `paper_only`（范围 PAPER_ONLY，和真实的 ALL 互不影响）。
- **发件箱的积压与死信**：事件先写进发件箱 `t_collector_event_outbox`（`c_published`：0 待发布、1 已发布、2 死信），中继每 10 秒发布一轮。
  最老的待发布事件超过 10 分钟没发出去，上报关注项 `event_outbox_stuck`（EventBus 连不上或发布被拒）；无法解码的事件标成死信，不再堵住后面的事件，同样上报 `event_outbox_stuck`，需要人工查看。
  连上 EventBus 后 K 线合成消费者启动失败不影响下架事件的发布，连续 3 次失败上报 `eventbus_consumer_failed`。
- **不做自动撤销**：条目从接口里消失，可能是下架时间改了，也可能是下架已经完成，没法可靠判断交易所是否撤销了下架。误报靠提前量、事件中心的 `delist_detected` 通知和手工取消兜底。
- **没有只读 Key**：读不到 `exchange-binance-production-readonly` 时，币安现货来源本轮跳过，上报关注项 `delist_readonly_key_missing`，下一轮继续尝试，补上 Key 即自动恢复。
  读不到有三种情况，关注项分不出是哪一种（`GetReadonlyExchangeKey` 都回 NOT_FOUND），管理台监控页一次列全：
  - 已有这把 Key 但被禁用：到密钥管理页启用；
  - 还没有：用户在 moox.toml 的 `[[exchange_keys]]` 里加一把币安正式环境的密钥（`exchange = "binance"`、`environment = "production"`、`name = "readonly"`、`readonly = true`，用 `moox-cli config edit` 修改），经 `setup apply` 写进 SecretMgr；
  - 在管理台删除过：`setup apply` 不重建删除过的密钥，换名称也不行（Collector 只读这个固定 ID），目前补不回来，见[已知限制](#已知限制)。
  关注项的 detail 里也简短写了这三种情况。这一项只算 warning（业务检查显示“需关注”），不挡安装验收；缺 Key 期间现货下架只能手工登记。
- **自动检测开关**：配置 `delist.auto_detect`（默认 true）。安装时按拓扑渲染：有出口代理（配了海外机）为 true，没有时为 false——三个来源都要经出口代理访问，没有出口代理时只会一直失败。
  关闭时不轮询来源、不建出口 HTTP 客户端，手工登记照常可用。
  渲染只替换配置里已有的 `delist` 段、不新增（新版模板自带这一段）：旧版 Collector 不认识这个键、读到会启动失败，所以发布时先换 Collector 二进制，再渲染或手改，回滚到旧版本前删掉这一段，见 skill 的 `references/native-release.md`。
- **来源失败**：某个来源连续 3 次失败，上报 `delist_source_failed`；某个来源这一轮返回的条目被校验拒绝（交易所、市场不对，代码带冒号等）、没有发布时同样上报（等于漏报，请手工登记并检查来源返回），下一轮不再被拒就恢复。交易所代码在登记时统一成大写再校验（来源返回小写或大小写混用也照常发布），与手工登记一致。两个关注项都走指标 `moox_collector_attention_active{kind,detail}`，Monitor 汇总成 `collector_attention:*` 检查，见[监控](监控.md)。
- **出口代理**：币安现货接口需要 `X-MBX-APIKEY`，OKX 域名要在出口代理白名单里，见[出口代理](出口代理.md)。

### Collector 级的 EventBus 接入

EventBus 连接和发件箱中继属于 Collector 整体（`internal/eventbus`），不再挂在 K 线合成下面：配置是顶层 `event_bus`（`urls`、`credential_file`；原先的 `kline_resample.event_bus` 已删除，
Collector 的配置是严格解码，包里的 `app.yaml`、`unitinstall` 写配置的分支和二进制必须同一版本发布）。`Hub` 维护一条共享连接，连不上每分钟重试，EventBus 晚于 Collector 启动也能自动连上；
连上后才创建 K 线合成的消费者。`Relay` 是独立的发布循环（10 秒一轮，封存出新事件会立即唤醒），不依赖 K 线合成是否开启。
`NoticePublisher` 只负责把补写通知封存进发件箱。没有配置 `event_bus` 时不发布任何事件，下架检测不启动，手工登记返回明确的错误。

## 9. 数据保留

Collector 的 SQLite 只保存运行状态：采集计划、补采作业、任务与合成状态。每分钟的维护任务按
`collector_retention.max_rows_per_pass` 的预算清理已结束的补采作业；补写通知与已发布事件保留 7 天、已结束的历史合成作业保留 30 天。
行情数据本身在 Storage 中，按 Storage 保留策略（结果数据集的空间与频率）清理，采集任务不设置保留期。

SQLite 使用显式选择的纯 Go modernc 驱动，Collector 服务、CLI、标的同步及 SCF 程序在本机关闭 CGO 构建。连接显式设置 `_time_format=sqlite`，保持时间可被 SQLite 日期函数解析，范围查询与绑定参数使用相同格式。

进程内 Storage Metadata/Primary 调用共用 `gatewayclient`；计划对账、结果管理、重采样和周期上报从同一客户端注入，标的同步读取同一份 Collector 主配置。`gateway_client` 记录固定 caller `collector`、Admin 分配的 KeyID 与签名文件，主机 ID、loopback 地址及私有 CA 来自同级 hostgateway 配置。只读刷新重试交给共享层，内部写调用只发送一次。退出或初始化失败时先取消并等待定时任务、维护和对账协程，再关闭客户端和数据库。SCF 使用外部 Access 客户端；DNS/HTTP 出口复用 EgressProxy，拓扑来自 SysDeploy v2。

## 10. 发布 SCF 函数

SCF 采集函数由 Collector 的采集计划对账器创建与升级，不需要手工发布：

- `moox-cli setup init`按清单的 `[scf_plan]` 段渲染 Collector 的 `scf_regions`、`scf_markets`、`scf_plan`，
  并保证每个空间已上传代码包；
- 代码包按包名取最新（`scf_plan.package_name`），在每轮对账或补采准备时按需解析，成功结果缓存至少 30 秒；对账默认每分钟一轮，上传新版本后逐轮滚动升级各函数；
- 函数基础环境（`MOOX_SPACE_ID`、Storage 应用密钥等）由 Collector 生成，CloudFunction 在创建函数时补齐 CLS 环境。

**备援请求（默认关闭）**：整点前后行情源响应变慢时，约一半的 1m 请求第一次尝试停住 2～5 秒后才换端点成功。Collector 配置 `scf_plan.fetch`
（或 `scf_plan.spaces.<空间>.fetch`）的 `standby_ms` 大于 0 时，函数在行情请求超过这么多毫秒还没有结果时并发再发一个备援请求（有下一个端点用下一个，
只有一个端点就再发一次同一个），先成功的为准，另一个被取消；第一次请求在延迟之前就失败时仍是普通的顺序换端点，不发备援。取值 200～5000，
太短会让大多数请求都发出备援、白白加倍请求权重；多出的请求权重只发生在发出备援的那部分请求上。`standby_hour_only: true` 只在整点那一分钟触发的调用里启用。
批次摘要总是带 `standby_ms`（0 表示这批没有启用），启用的批次另有 `standby_fired`（发出备援请求的次数）与 `standby_won`（备援请求先成功的次数）。
这些字段随采集计划下发，旧版本函数遇到未知字段会拒绝计划，所以必须先把函数代码包升级到新版本，再在 Collector 配置里打开。
2026-10-20 在单端点上限 1.2 秒时试过一次（`standby_ms=800`），没有改善（备援请求同样被截断）；现在随 3 秒的单端点上限重新提供，效果待再试。

**连接复用（默认关闭）**：函数进程会连续服务多次调用，但默认每次调用都新建 HTTP 客户端，上一分钟建好的连接全部丢弃，每个标的每分钟都要重新握手。
整点实测里新建连接上的第一个请求常停住数秒，而复用连接上的请求都正常返回。`scf_plan.fetch` 的 `conn_reuse: true` 让函数在调用之间共用一个进程内的 HTTP 客户端（空闲连接最长保留 90 秒，每个函数最多 64 条空闲连接），
下一分钟的请求直接用上一分钟留下的连接。
批次摘要总是带 `conn_reuse`（0/1），启用后批次里的 `conn_reused` 应明显增加、`conn_new` 与握手耗时 `tls_*` 下降。

**币安端点**：现货只配 3 个出口各不相同的官方端点（`api.binance.com` 走 CloudFront、`api-gcp.binance.com` 走 Google Cloud、`data-api.binance.vision` 走 AWS 东京直连），
合约只有 `fapi.binance.com` 一个可用端点（`fapi1`～`fapi4` 只是重定向到 www.binance.com 的通配域名）。配置在 `configs/scf/market_data/sources/market/binance.yaml`。

**REST 取到的不一定是定稿值**：币安 K 线接口没有"已闭合"标志（返回里的收盘时间是固定值），函数只按本机时间判断收盘。2026-10-20 实测：合约 REST 要到收盘后约 8 秒、现货约 3 秒才与最终值一致，更早取到的成交量、成交额、笔数偏少；而 Storage 的周期一旦全部提交就锁定，早取的值改不回来。线上合约 1m 因此有 26%～55% 的 K 线不是定稿值。现已按市场推迟取数：`scf_plan.spaces.<空间>.markets.<市场>.fetch.not_before_ms` 让函数等到收盘后这么多毫秒再取数（crypto 现货 3000、合约 8000，
合约的 `allowed_lateness_seconds` 放宽到 20 秒），并为 crypto 改用 WS 推送（第 3a 节）。`not_before_ms` 随计划下发，必须先升函数包再改配置。

云函数实例页只保留列表、详情、同步和删除；采集函数的新增与部署一律由对账器完成，页面不再提供手工批量新增/部署入口（采集函数的变更需要发布租约，手工入口无法满足）。

构建与上传代码包：`moox-cli collector function upload --package-name <包名> --version <版本> --collector-root modules/collector`。
`moox-cli collector function delete --space-id <空间> [--instance-prefix <前缀>] [--namespace <命名空间>] [--region <地域>]` 可按条件删除一批函数（持发布租约；不带 `--yes` 只列出目标，确认后加 `--yes`）。
详见[命令行工具](命令行工具.md)、[云函数管理](云函数管理.md)和[部署与运维](../部署与运维.md)。

### 采集计划协调的失败原因

对账器每轮向 Monitor 上报「协调是否健康」和当前失败原因（`moox_collector_market_fetch_coordination_failure{reason}`，同一时刻只有一个原因为 1）。
原因白名单与含义（白名单之外的一律按 `cloudfunction` 上报；单测保证每个 `fail` 调用点用到的原因都在名单里，Monitor 为每个原因给出专属告警文案）：

| 原因 | 含义 |
| --- | --- |
| `cloudfunction` | 调用 CloudFunction 失败：列函数、提交作业、读取作业结果、作业到终态但失败，以及 Admin 不可达、无权限等租约错误 |
| `publish_lease_held` | Admin 明确答复（`CONFLICT`）发布租约或在途操作占用仍被持有，见下 |
| `environment` | 生成函数运行环境失败（Access 入口、环境变量） |
| `rules` | 读取或解析采集规则、任务、标的失败 |
| `store` | Collector 本地 SQLite 读写失败（读取、保存采集计划与进度） |
| `storage` | 向 Storage 登记标的快照失败，或 Collector 与 Storage 计算的快照哈希不一致 |
| `package` | 解析最新代码包失败（包名未上传或 CloudFunction 不可达） |
| `dataset` | 设置数据集允许迟到失败 |
| `activity` | 活动日志没有写入成功，计划保持未生效 |
| `preflight` | 创建新计划前的检查未通过，例如 A 股内嵌交易日历的覆盖期不足 14 天（不足 60 天只打告警日志） |
| `capacity` | 计划放不进函数：每函数标的数过多、环境变量超过 4KB 上限 |

- **`publish_lease_held`**：Admin 明确答复（`CONFLICT`）发布租约或在途操作占用仍被他人持有。租约在正常工作，不是 CloudFunction 故障。
  典型场景是 Collector 重启：旧进程提交的批次作业还在 CloudFunction 里执行，它的操作占用（每次续期到当前时间加 6 分钟）挡住新进程，新进程的持有者 ID 与旧进程不同，必须等占用结束。
  冲突持续的时间取决于旧作业还要跑多久，没有固定上界；线上实测约 6 分钟。Admin 不可达、无权限、响应异常不属于它，仍按 `cloudfunction` 告警。
- **失败起始时间**：`moox_collector_market_fetch_coordination_failure_since_timestamp_seconds` 记录当前失败原因首次出现的时间，同一原因连续出现时不重置，原因变化或恢复时清零。
  Monitor 用它判断「被占用」是否超过宽限期，见[监控](监控.md)。
- **作业未结束不是失败**：提交云端作业后，对账等待的上限是 `min(JobWait, 本轮剩余时间 − 余量)`（余量取 5 秒与剩余时间四分之一的较小者；`JobWait` 默认 90 秒，而单轮时限只有 55 秒）。
  到上限作业仍在运行就记入在途集合（计划作业进 `pending`，漂移修复、升级、清理等进 `aux`），下一轮继续，不再把「慢」记成 `cloudfunction` 失败。
  只有读取作业结果本身出错、或父 ctx 被取消或超时，才记失败。补采函数的创建、升级、删除、清理遗留预留走 `runBackfillJob`：作业在等待上限内结束就释放补采租约；没有结束（或读取结果出错）时作业仍可能在云端运行，
  此时**保留租约并登记在途作业**（`backfillJobs`，函数名 → 作业），返回 `errBackfillJobRunning`，不释放租约——租约一释放就立即过期，排队中的作业开始执行时会因租约已过期而失败，
  下一次调用还会对同一函数重复提交。下一次 `EnsureBackfillFunction` 先结算在途作业：仍在运行就只续租并返回“仍在进行”，不重复提交；到终态就移出并在没有其他在途作业时释放租约，
  再按云端实际状态判断下一步（函数缺失就重建）。补采租约已持有时复用并续租：只有明确得知租约已过期或被取代（`ErrCollectorPublishLeaseStale`）才丢弃重新申请，通信错误时保留句柄（租约可能仍然有效，丢掉后 Admin 会拒绝重新申请），把错误交给调用方；
  读取作业结果失败时同样续租。租约不会在没人调用时被后台续期，没有后续调用时按 2 分钟 TTL 自行过期（作业一旦开始执行，操作占用会接管）。
  在途作业超过 30 分钟（`backfillJobGiveUpAge`，大于 CloudFunction 单项 16 分钟的预算）仍无法确认终态（作业记录丢失、状态一直读不到）就放弃：移除在途记录并释放租约，再按云端实际状态判断
  （函数已在就绪，缺失才重建），旧作业即使还活着也会被新租约的围栏令牌隔离。
- **每轮收尾**：本轮及自上一轮结束以来没有任何失败时，协调恢复为健康并清除遗留的失败原因与起始时间（计划仍在进行也一样）；
  这不会刷新「最近一次对账成功」时间——计划未生效时该时间保持不动。有在途云端作业时，最老的作业未超过 10 分钟（`pendingJobWarnAge`）照常刷新
  （大批量升级可能连续跑十几分钟，期间一直有正常推进的作业）；超龄说明卡住了，才停止刷新，由 Monitor 的对账陈旧判定（默认 15 分钟）发现。
  有在途作业时 `coordination_pending_since` 取最早在途作业的提交时间。

## 11. 运行状态

控制台“采集任务 → 运行状态”（`/collector/tasks?tab=status`）回答“采集有没有问题”，数据来自 `GetCollectorStatus`：

- **总体等级**取计划层面与各数据集中最严重的一级：计划下发失败为异常，未生效计划超过 30 分钟为需关注，
  重新登记 30 分钟后仍没有新计划接手为异常（这期间数据集没有时间线、数据集健康里看不到，实时提交仍因快照缺失被拒绝）。
- **数据集健康**（只列正在采集的数据集，异常排前）：

  | 条件 | 等级 |
  | --- | --- |
  | 自动巡检超出预期 1 小时（已停） | 异常 |
  | 自动巡检超出预期 15 分钟（落后） | 需关注 |
  | 24 小时内有失败分块 | 需关注 |
  | 历史扫描发现未确认的缺口，或扫描失败 | 需关注 |

  “自动巡检”列说的是自动补漏有没有跟上，不是数据延迟：正常时只显示“已查至 HH:mm”（水位），超出预期时才带上
  “落后 N 分钟”或“已停 N 小时”，原因文案说明“期间的缺口暂未（不会被）自动补上”。超出预期的口径
  （`inspect_lag_seconds`）：自动补采只扫到 `alignDown(now - 迟到容忍 - 一个周期)`（不含），水位之后第一根未检查的 K 线
  从 `alignUp(水位)` 开始，到 `它 + 两个周期 + 迟到容忍` 才进入巡检范围，从那一刻起算；1h 等低频数据集整点刚过、
  下一个扫描槽到来前的正常等待不算落后。数据是否齐全看“24h 实时缺口”和“历史缺口”。
  24 小时实时缺口与已确认的行情源缺失只展示，不影响等级。
- 数据集与函数服务的数据集都显示展示名（所属采集任务名），悬停可看数据集 ID。
- **函数**：上百个函数可按名称、数据集或展示名搜索，按地域、市场筛选，只看下发中与退役中的函数；普通分页，每页行数按可视高度自动适配（至少 8 行，不出现表格滚动条）；“触发”列把 cron 翻译成中文（如“每 5 分钟”“工作日 09:30”，翻译不了时原样显示，悬停看原文）；点击函数名弹窗展示详情：地域、触发、市场，以及按数据集分组、可搜索的标的列表与生效时间（`CollectorFunctionStatus.dataset_subjects`）。

## 生命周期、暂停与恢复追赶

> 状态：已实现（暂停恢复与重置设计阶段 2）。Collector 有模块级生命周期（健康端口 `/v1/lifecycle/status|command|catchup`，状态文件 `lifecycle.json` 在数据库旁），没有对象。

- **暂停**：全部采集计划空间的暂停开关置为暂停（与 `collector fetch-plan` 的空间暂停是同一个开关）：SCF 定时器停用、collector-stream 停止订阅、不再认领补采分块。
  暂停要等所有空间的 SCF 定时器停用确认、在途的补采分块结束才算真正停下（等待上限 5 分钟，超时返回「已暂停，但在途操作没有结束」，门禁已经关闭）。
- **恢复追赶**：进入**恢复模式**——暂停开关仍在（实时定时器与订阅保持关闭），但补采调度运行：对暂停区间 `[暂停时间, 现在)` 的全部数据集检查缺口，有缺口且没有未结束的作业时提交一个补采作业，
  缺口太多时缩成最早的一个窗口逐窗口推进。追平：区间内没有缺口（已确认行情源缺失的周期扣除并单独统计为「不可补」）且没有未结束的补采作业。
  **追赶目标是固定的**：恢复开始的时刻 T0，补采只补 `[暂停时间, T0)`。恢复模式下实时采集仍然关闭，如果目标跟着当前时间走，补采速度（每个标的至少一个分块）赶不上缺口增长的速度，永远追不平
  （2026-10-22 线上演练遇到：40 分钟没有收敛）。T0 之后到放行之间的缺口由放行后的自动补采填。
  恢复模式只在进程内存里：追赶中重启会回到暂停，再 resume 即可。
- **放行**：暂停区间补齐后清除暂停开关，对账协程重新启用定时器，恢复实时采集。采集只拉取和写入行情，没有下单、发目标这类副作用，所以**追平后自行放行，不等系统恢复的栅栏**
  （`moox-cli system resume` 里只有因子、Trade、策略等有副作用的模块等栅栏）；等栅栏期间采集一直关着，这段行情又成了新缺口。

## 已知限制

- **在管理台删除过的币安只读 Key 用 `setup apply` 不能重建**：`setup apply` 不重建在管理台删除过的密钥（见 `modules/admin/internal/service/setup/exchange_keys.go`），
  密钥管理页新增的密钥 ID 是随机的，Collector 只读固定 ID `exchange-binance-production-readonly`，换名称也补不上。删除过之后币安现货下架检测一直跳过（关注项 `delist_readonly_key_missing`），
  现货下架只能用 `moox-cli collector delist register` 或管理台「事件中心」“事件”页签里“标的即将下架”一行的“手工登记”登记。
