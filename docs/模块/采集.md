# 采集（Collector）

Collector 负责行情采集：管理采集任务，规划每个周期要抓取的标的，把工作分派给腾讯云 SCF 函数，
跟踪每个周期在 Storage 中的完成情况，并维护标的与标签。

代码位置：`modules/collector`。

## 1. 组成

| 组件 | 入口 | 职责 |
| --- | --- | --- |
| `moox-collector` | `cmd/server` | 采集任务管理、周期批次规划、SCF 运行配置协调、完成事件处理、重试、K 线重采样、DNS 快照 |
| `moox-collector-subject` | `cmd/subject` | 按数据源同步自动标签的成员，并定时刷新标的属性 |
| SCF 采集函数 | `cmd/scf/market_data` | 在腾讯云执行一批行情抓取并写入 Storage：crypto 由调度器异步调用，stockcn 由 Timer 触发后领取批次 |
| `moox-collector-cli` | `cmd/cli` | 初始化 Collector 数据库 |
| `providerprobe` | `cmd/providerprobe` | 开发工具：直接探测各行情源的可用性和数据格式 |

`moox-collector` 的服务与定时器：

| 名称 | 端口 / 周期 | 说明 |
| --- | --- | --- |
| `CollectMgr` | tRPC `11402` | 任务管理接口，经主机网关供控制台、CLI 与 Monitor 调用 |
| `MarketFetchRuntime` | tRPC `11422` | `ClaimTimerBatch`，供 Timer 模式的 SCF 函数领取批次（经节点网关） |
| 健康检查 | `11412` | `/healthz`、`/readyz`、`/metrics` |
| `schedule` 定时器 | 每分钟 | 规划周期、生成批次、调度重试与补采 |
| `kline_resample` 定时器 | 每分钟 | 本地 K 线重采样 |
| `dns` 定时器 | 每 30 秒 | 刷新行情域名的 DNS 快照 |
| `metrics` 定时器 | 每 30 秒 | 上报指标 |

## 2. 领域模型

| 对象 | 表 | 说明 |
| --- | --- | --- |
| CollectionTask | `t_collector_tasks`、`t_collector_task_tags` | 采集任务：数据类型（`kline` / `kline_resample`）、采集参数、绑定的标签、结果数据集与 View |
| TaskSeries | `t_collector_task_series` | 任务当前要采的序列（标的 × 数据源 × 市场 × series_tag） |
| PeriodSeriesSnapshot | `t_collector_task_period_series` | 某数据集某频率某周期冻结下来的序列清单，周期中途标签变化只影响后续周期 |
| TaskInstance | `t_collector_task_instances` | 一个标的、一个频率的执行身份，多个任务可共享 |
| WriteTarget | `t_collector_instance_write_targets` | 执行实例写往哪个任务的结果数据集；写入与重试状态记录在这里 |
| Run | `t_collector_runs` | 一次按分钟的调度运行 |
| TimerPeriodBatch | `t_collector_timer_period_batches` | 一个周期、一个函数分片的可领取批次 |
| FetchBatch / Item | `t_collector_fetch_batches`、`t_collector_fetch_batch_items` | 一次调用的批次与逐项结果 |
| RetryItem | `t_collector_fetch_retry_items` | 待重试的序列，以及向 Storage 上报失败的状态 |
| PeriodStorageState | `t_collector_period_storage_states` | Collector 对 Storage 周期状态的本地跟踪 |
| PeriodReadiness | `t_period_readiness`、`t_period_readiness_items` | 本地重采样等工作的周期就绪跟踪 |

**一任务一结果。** 每个采集任务独占一个结果数据集和默认 View，ID 由任务 ID 派生
（`dataset_<task>`、`view_<task>_<类型>_<频率>`）。用户只面对“采集任务”和“采集结果”，
不需要管理数据集。删除任务时由用户选择保留结果，或物理删除结果 View、数据集及其数据。
内置任务定义在 `config/setup/collection-tasks.yaml`，首次启动时导入。

## 3. 实时采集链路

函数有两种执行模式，由空间决定：

| 模式 | 空间 | 方式 |
| --- | --- | --- |
| Invoke 函数池 | crypto | 调度器每分钟把批次通过 CloudNode `InvokeFunction` 以异步方式交给函数池中的节点，调用失败时换节点重试 |
| Timer fleet | stockcn | 函数按 Timer 自行触发，通过 `ClaimTimerBatch` 领取本分片本周期的持久批次 |

```text
schedule 定时器（每分钟）
  ├─ 冻结本周期各数据集的序列快照（PeriodSeriesSnapshot）
  ├─ 生成本周期批次（Invoke 模式直接调用函数，Timer 模式写成 TimerPeriodBatch 等待领取）
  └─ 必要时通过 CloudNode 更新函数环境（分片、binding hash、DNS 路由、服务入口）
SCF 函数执行
  ├─ 得到本周期批次（Invoke 事件携带，或 ClaimTimerBatch 领取）
  ├─ 并发请求行情源，只保留已收盘的 K 线
  ├─ 经 storage-access（或 storage 主机网关 11003）调用 EnsureDatasetPeriod / CommitTimeSeriesBatch / RecordDatasetPeriodFailures
  └─ 发布 MarketFetchBatchCompleted
Collector 完成事件消费者（MOOX_MARKET_FETCH，按空间）
  └─ 更新批次与执行实例，生成重试项
Storage 写入事件消费者（MOOX_STORAGE rows.upserted）
  └─ 记录每个标的的数据实际写入 Storage 的时间（任务实例新鲜度）
```

- 失败的序列进入 RetryItem，由调度器在后续周期通过 CloudNode `InvokeFunction` 补采；
  Timer 模式的每个启用地域会自动保留一个 Invoke 辅助函数，它不计入 Timer 函数数量。
- 周期是否完成以 Storage DataNode 为准（见[存储](存储.md)第 4 节）。Collector 只有在 Storage
  返回逐序列回执后才认为失败上报已被接受，之前一直保持待上报并重放。
- Storage 入口按地域选择：`moox.toml` 的 `storage_access_targets` 为该地域配置了 storage-access 时使用它；
  否则同地域走 storage 主机私网的网关 `11003`，跨地域走公网 `11003`。
- 函数的运行参数（分片、Storage 入口、DNS 路由等）只写在 SCF 环境变量里，
  SCF 代码包本身不带任何凭据。

## 4. 数据源

| 市场 | 数据源 |
| --- | --- |
| 加密货币 | Binance（现货、永续） |
| A 股 | 新浪、腾讯、东方财富、百度、通达信 |
| 港股、美股 | 东方财富、新浪 |
| 指数 | 中证指数、国证指数、申万、东方财富、新浪、腾讯 |
| 可转债 | 东方财富、新浪、通达信 |

数据源的地址、限流等配置在 `configs/sources/market/*.yaml`（SCF 包内为 `sources/market/`）；
A 股的交易日历和数据源路由在 `config/markets/stockcn/`。每个数据源按出口 IP 维护独立的限流与
熔断，单个数据源失败时在本次调用内切换到备用数据源。

## 5. DNS 快照

SCF 函数需要快速、稳定地连接行情域名。Collector 维护一份 DNS 快照写入函数环境：

- 启用 Trade DNS Resolver 时，每 5 分钟批量向 Trade 节点请求经过 TCP 探测、按延迟排序的 IPv4；
- 请求失败或某个域名未解析时保留上一次成功的结果，并回退到本地 DNS；
- 最近一次成功的快照会持久化，进程重启后先恢复再刷新。

SCF 仍以原域名作为 Host/SNI，IP 只用于拨号；所有 IP 都失败时直接连接域名。

## 6. 标的与标签同步

`moox-collector-subject` 每分钟轮询一次：

- **自动标签**：按标签声明的数据源拉取完整成员快照，写回 Storage（`ApplyTagSnapshot`）；手动标签的
  成员由用户维护，不被覆盖。
- **属性维护**：按 `config/subject.yaml` 中的计划（例如 A 股每天 08:00、加密货币每天 00:00）
  刷新标的的名称、上市状态等属性。

## 7. K 线重采样

`kline_resample` 类型的任务在 Collector 进程内由本地 worker 执行：读取源数据集的低频 K 线，
生成高频周期（如 1m → 5m、1h → 4h）并写入任务的结果数据集。支持按时间范围发起历史回填
（`StartKlineResampleBackfill` / `CancelKlineResampleBackfill` / `GetKlineResampleBackfill`）。
该功能默认关闭，在 `config/app.yaml` 的 `kline_resample.enabled` 中开启。

## 8. 管理接口

`CollectMgr`（管理台路径 `/api/admin/collectmgr/<方法>`）：

| 方法 | 作用 |
| --- | --- |
| `GetTaskList` / `GetTaskDetail` | 任务列表与详情 |
| `CreateTask` / `UpdateTask` / `DisableTask` / `DeleteTask` | 任务增删改，删除时指定是否删除结果数据 |
| `GetTaskResultInventory` | 任务结果清单（供 Monitor 和前端使用） |
| `GetTaskInstanceList` | 执行实例列表 |

| `StartKlineResampleBackfill` 等 | 重采样回填 |

## 9. 数据保留

Collector 的 SQLite 只保存运行状态，由每分钟的维护任务按 `collector_retention` 清理：
执行明细保留 6 小时，调度运行汇总 30 天，终态重试项 7 天，周期快照 30 天。行情数据本身在
Storage 中，按 Storage 保留策略（结果数据集的空间与频率）清理，采集任务不设置保留期。

SQLite 使用显式选择的纯 Go modernc 驱动，Collector 服务、CLI、标的同步及 SCF 程序在本机关闭 CGO 构建。连接显式设置 `_time_format=sqlite`，保持时间可被 SQLite 日期函数解析，范围查询与绑定参数使用相同格式。批次完成把终态 CAS、范围校验和所有效果放在同一事务；每次事务读取一次批次成员，复用连接池持有的有界预编译语句分组写入重试，数据库关闭时释放语句。待派发查询使用 pending 部分索引，失败上报使用 permanent_failed 部分索引；已知重试键的派发更新按唯一键查询，避免扫描整个 pending 队列。恢复和派发分别受 15 秒、30 秒预算限制。

进程内 Storage Metadata/Primary 调用共用 `gatewayclient`；计划器、结果管理、重采样和周期上报从同一客户端注入，标的同步读取同一份 Collector 主配置。`gateway_client` 记录固定 caller `collector`、Admin 分配的 KeyID 与签名文件，主机 ID、loopback 地址及私有 CA 来自同级 hostgateway 配置。原 Storage 请求体中的角色认证保留；只读刷新重试交给共享层，内部写调用只发送一次，Ensure 的未知结果允许只读查询状态。退出或初始化失败时先取消并等待定时任务、维护、派发及消费者，再关闭客户端和数据库。SCF 外部工厂及其目标配置留待 E2，DNS 与 SysDeploy 分别随 E4、D2c 迁移。

## 10. 发布 SCF 函数

SCF 代码包由 `scripts/build/build-collector-scf-package.sh` 构建，包含 `main`、`sources/`、
EventBus 公开 CA 证书，A 股包还包含交易日历和路由。函数的创建、发布、Timer 管理通过
`moox-cli collector function ...` 完成，CLI 通过 Admin 的采集发布租约避免并发发布同一组函数。
详见[命令行工具](命令行工具.md)和[云节点](云节点.md)。

按 fleet 发布使用 `moox-cli collector function publish submit --file ./moox.toml --control-url https://<控制机>:11001 --space-id <空间>`，
CLI 通过 SSH 从控制机读取发布所需的信任材料并自行打包。发布前需要在 `moox.toml` 的对应
`[[scf_fetcher.spaces]]` 中配置：

- `canary_task_id`：一个专用、停用、只含一个序列的采集任务。发布器先用它独占一个未使用的周期，
  调用候选函数完成一次真实抓取、写入和读回，验证通过后才更新生产函数。任务的序列由调度器冻结，
  所以新建后需要短暂启用、待序列冻结后再停用。
- `collector_rpc_gateway_target` / `collector_gateway_target_node`：Collector 的服务入口与网关节点。
