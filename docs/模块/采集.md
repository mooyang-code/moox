# 采集（Collector）

Collector 负责行情采集：管理采集任务，规划每个周期要抓取的标的，把工作分派给腾讯云 SCF 函数，
跟踪每个周期在 Storage 中的完成情况，并维护标的与标签。

代码位置：`modules/collector`。

## 1. 组成

| 组件 | 入口 | 职责 |
| --- | --- | --- |
| `moox-collector` | `cmd/server` | 采集任务管理、采集计划对账与部署、K 线检查与补采、K 线重采样、DNS 快照、标签与标的属性同步 |
| SCF 采集函数 | `cmd/scf/market_data` | 在腾讯云由 Timer 触发，按环境变量里的采集计划抓取行情并写入 Storage；也接受手动与补采调用 |
| `moox-collector-cli` | `cmd/cli` | 初始化 Collector 数据库 |
| `providerprobe` | `cmd/providerprobe` | 开发工具：直接探测各行情源的可用性和数据格式 |

实时采集不依赖 Collector：函数按计划自行触发、自行写入，Collector 停机不影响 K 线入库，只影响计划变更与补采。

`moox-collector` 的服务与定时器：

| 名称 | 端口 / 周期 | 说明 |
| --- | --- | --- |
| `CollectMgr` | tRPC `11402` | 任务管理与采集计划、K 线检查与补采接口，经主机网关供控制台、CLI 与 Monitor 调用 |
| 健康检查 | `11412` | `/healthz`、`/readyz`、`/metrics` |
| `kline_resample` 定时器 | 每分钟 | 本地 K 线重采样 |
| `dns` 定时器 | 每 30 秒 | 刷新行情域名的 DNS 快照 |
| `metrics` 定时器 | 每 30 秒 | 上报指标 |
| `subject_tags` 定时器 | 每分钟第 30 秒 | 检查到期标签并同步成员 |
| `subject_attributes` 定时器 | 每分钟第 45 秒 | 按任务时区检查属性维护计划 |

采集计划对账（每个空间一个协程，每分钟一次）与自动补采在进程内常驻运行，不经过 tRPC 定时器。

## 2. 领域模型

| 对象 | 表 | 说明 |
| --- | --- | --- |
| CollectionTask | `t_collector_tasks`、`t_collector_task_tags` | 采集任务：数据类型（`kline` / `kline_resample`）、采集参数、绑定的标签、结果数据集与 View |
| TaskSeries | `t_collector_task_series` | 任务当前要采的序列（标的 × 数据源 × 市场 × series_tag） |
| FetchPlan | `t_collector_fetch_plans` | 采集计划：每个空间同一时间最多一份未生效的计划，最近一份已生效的计划即“已生效状态” |
| BackfillJob / Chunk / Watermark | `t_collector_backfill_*` | K 线补采作业、分块与自动补采的扫描水位 |
| TaskInstance / WriteTarget | `t_collector_task_instances`、`t_collector_instance_write_targets` | 本地重采样任务的执行身份与写入目标 |
| PeriodReadiness | `t_period_readiness`、`t_period_readiness_items` | 本地重采样等工作的周期就绪跟踪 |

**一任务一结果。** 每个采集任务独占一个结果数据集和默认 View，ID 由任务 ID 派生
（`dataset_<task>`、`view_<task>_<类型>_<频率>`）。用户只面对“采集任务”和“采集结果”，
不需要管理数据集。删除任务时由用户选择保留结果，或物理删除结果 View、数据集及其数据。
内置任务定义在 `config/setup/collection-tasks.yaml`，首次启动时导入。

## 3. 实时采集链路

所有空间统一为“腾讯云定时器触发函数，函数按环境变量里的采集计划自行采集并提交 Storage”：

```text
Collector 对账协程（每个空间，每分钟）
  ├─ 读任务与标签成员，算出每个数据集的标的集合 hash 与函数分配
  ├─ 无变化：什么都不做
  └─ 有变化：选生效周期 P → Storage 登记序列快照 → 更新函数环境变量（新旧两份都带生效起点）
SCF 函数（Timer 触发）
  ├─ 按计划与事件时间确定本周期要采的（数据集、标的）
  ├─ 并发请求行情源，只保留已收盘的 K 线
  └─ 经 Access（11004）调用 CommitTimeSeriesBatch 写入 Storage；失败项上报 CLS，不在线重试
Collector 自动补采（每个空间）
  └─ 扫描 Storage 里缺失的 K 线，分块调用补采函数写回
```

- 函数失败不由 Collector 即时重试，缺口由检查与补采统一修复：`moox-cli collector kline check` 比对
  Storage 与采集计划，`kline backfill` 补采；自动补采按水位扫描最近的缺口。
- 周期是否完成以 Storage DataNode 为准（见[存储](存储.md)第 4 节）。
- 采集计划由 Collector 生成并保存在 `t_collector_fetch_plans`；`moox-cli collector fetch-plan` 查看函数分配、
  数据集 hash 与变更进度。
- 函数的 Storage 入口固定为同地域的一个 Access 实例，地址和实例身份（`access@<主机ID>`）由放置清单派生；
  函数的运行参数（计划、Storage 入口、DNS 路由、CLS 配置）只写在 SCF 环境变量里，SCF 代码包本身不带任何凭据。
- 函数日志不会自动投递：每次调用把失败项（`market_fetch_item_failure`）与批次摘要（`market_fetch_batch`）
  上报到 CLS，字段与索引见[部署与运维](../部署与运维.md)。

## 5. DNS 快照

SCF 函数需要快速、稳定地连接行情域名。Collector 维护一份 DNS 快照写入函数环境：

- `egress_proxy.dns.domains` 非空时，每 5 分钟经进程级共享网关向独立出口代理请求经过 TCP 探测、按延迟排序的公网 IPv4；
- 请求失败或某个域名未解析时保留上一次成功的结果，并回退到本地 DNS；
- 最近一次成功的快照会持久化，进程重启后先恢复再刷新。

SCF 仍以原域名作为 Host/SNI，IP 只用于拨号；所有 IP 都失败时直接连接域名。

常驻采集的 HTTP 客户端对 `egress_proxy.domains` 中的域名调用出口代理 `Do`，HTTP 与 DNS 复用同一 `collector` 身份和目录。代理保留目标状态码，过滤认证/Cookie 头并返回正文（传输中 gzip 压缩，由 Collector 解压；该客户端整体超时 60 秒，仅用于控制面标的同步）；请求失败不会回退本机直连，DNS 快照的 IP 也不能绕过代理。其他域名继续本机连接，短生命周期 SCF 使用自己的直接行情出口。

## 6. 标的与标签同步

Collector 启动时向 Storage 注册行情源的标的查询能力，标的同步复用进程级网关客户端与出口代理 HTTP 客户端：

定时同步只处理 cron 到期的标签。首次部署、交易所接口恢复或标签配置变更后，可用 `moox-cli collector subjects sync` 立即同步：它调用 `CollectMgr.SyncSubjects`，无视 cron 窗口，只处理 `mode=auto` 且配置了数据源的标签，返回每个标签的状态、标的数和失败原因。手动同步与定时任务共用一把互斥锁，同步正在运行时返回冲突；调用预算 180 秒，服务端 170 秒后以失败结果返回。网关只向 `moox-cli` 开放这个方法。

- **自动标签**：每分钟第 30 秒检查是否到期，按标签声明的数据源拉取完整成员快照并调用 `ApplyTagSnapshot`；失败通过 `ReportTagRunFailure` 上报。手动标签成员由用户维护。
- **属性维护**：每分钟第 45 秒检查 `app.yaml` 中的 `subject_sync.attributes`；按任务时区判断 `(触发时间 - 1 分钟, 触发时间]` 内是否有计划时间。默认在北京时间 08:10:45 刷新 A 股与加密货币的名称和属性，首次启动也遵循该规则。

两个定时器各自通过 `timerjob` 防止重叠，运行上限为 10 分钟。标签同步失败不会阻塞周期规划；退出时先取消并等待同步任务，再关闭 HTTP、网关客户端和数据库。

## 7. K 线重采样

`kline_resample` 类型的任务在 Collector 进程内由本地 worker 执行：读取源数据集的低频 K 线，
生成高频周期（如 1m → 5m、1h → 4h）并写入任务的结果数据集。支持按时间范围发起历史回填
（`StartKlineResampleBackfill` / `CancelKlineResampleBackfill` / `GetKlineResampleBackfill`）。
该功能默认关闭，在 `config/app.yaml` 的 `kline_resample.enabled` 中开启。

| `StartKlineResampleBackfill` 等 | 重采样回填 |

## 9. 数据保留

Collector 的 SQLite 只保存运行状态：采集计划、补采作业、任务与重采样状态。每分钟的维护任务按
`collector_retention.max_rows_per_pass` 的预算清理已上报的周期就绪记录（保留期见 `period_readiness`）。
行情数据本身在 Storage 中，按 Storage 保留策略（结果数据集的空间与频率）清理，采集任务不设置保留期。

SQLite 使用显式选择的纯 Go modernc 驱动，Collector 服务、CLI、标的同步及 SCF 程序在本机关闭 CGO 构建。连接显式设置 `_time_format=sqlite`，保持时间可被 SQLite 日期函数解析，范围查询与绑定参数使用相同格式。

进程内 Storage Metadata/Primary 调用共用 `gatewayclient`；计划对账、结果管理、重采样和周期上报从同一客户端注入，标的同步读取同一份 Collector 主配置。`gateway_client` 记录固定 caller `collector`、Admin 分配的 KeyID 与签名文件，主机 ID、loopback 地址及私有 CA 来自同级 hostgateway 配置。只读刷新重试交给共享层，内部写调用只发送一次。退出或初始化失败时先取消并等待定时任务、维护和对账协程，再关闭客户端和数据库。SCF 使用外部 Access 客户端；DNS/HTTP 出口复用 EgressProxy，拓扑来自 SysDeploy v2。

## 10. 发布 SCF 函数

SCF 采集函数由 Collector 的采集计划对账器创建与升级，不需要手工发布：

- `moox setup init`（或 `setup deploy`）按清单的 `[scf_plan]` 段渲染 Collector 的 `scf_regions`、`scf_markets`、`scf_plan`，
  并保证每个空间已上传代码包；
- 代码包按包名取最新（`scf_plan.package_name`），Collector 每 30 秒解析一次，上传新版本即自动滚动升级各函数；
- 函数基础环境（`MOOX_SPACE_ID`、Storage 应用密钥等）由 Collector 生成，CloudNode 在创建函数时补齐 CLS 环境。

构建与上传代码包：`moox-cli collector function upload --package-name <包名> --version <版本> --collector-root modules/collector`。
`moox-cli collector function delete --node-prefix <前缀> ...` 可按节点前缀删除一批函数（持发布租约，先 `--dry-run`）。
详见[命令行工具](命令行工具.md)、[云节点](云节点.md)和[部署与运维](../部署与运维.md)。
