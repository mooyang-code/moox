# 采集（Collector）

Collector 负责行情采集：管理采集任务，规划每个周期要抓取的标的，把工作分派给执行端（腾讯云 SCF 函数，
或香港机上 `collector-stream` 的 WS 推送接收与本地执行端），跟踪每个周期在 Storage 中的完成情况，并维护标的与标签。

代码位置：`modules/collector`。

## 1. 组成

| 组件 | 入口 | 职责 |
| --- | --- | --- |
| `moox-collector` | `cmd/server` | 采集任务管理、采集计划对账、云账号与代码包、云函数的创建与升级（进程内直接调腾讯云，见第 10a 节）、K 线检查与补采、K 线重采样、标签与标的属性同步 |
| SCF 采集函数 | `cmd/scf/market_data` | 在腾讯云由 Timer 触发，按环境变量里的采集计划抓取行情并写入 Storage；也接受手动与补采调用 |
| `moox-collector-stream` | `cmd/stream` | 部署在海外机（组件 `collector-stream`）：订阅交易所 WS 收盘 K 线，按周期提交 Storage；同进程提供本地执行端 `MarketFetchExecutor`（补采与本地定时拉取） |
| `moox-collector-cli` | `cmd/cli` | 初始化 Collector 数据库 |

实时采集不依赖 Collector：函数与 `collector-stream` 按计划自行触发或接收、自行写入，Collector 停机不影响 K 线入库，只影响计划变更与补采。

`moox-collector` 的服务与定时器：

| 名称 | 端口 / 周期 | 说明 |
| --- | --- | --- |
| `CollectMgr` | tRPC `11402` | 任务管理与采集计划、K 线检查与补采、云账号、代码包与云函数接口，经主机网关供控制台、CLI 与 Monitor 调用 |
| `StreamCollector` | tRPC `11422` | `collector-stream` 的心跳、拉计划与周期统计上报（只放行 `collector-stream`） |
| 健康检查 | `11412` | `/healthz`、`/readyz`、`/metrics` |
| `kline_resample` 定时器 | 每分钟第 5 秒 | 准备合成目标数据集、兜底检查、发布补写通知、推进历史合成作业，见第 7 节 |
| `metrics` 定时器 | 每 30 秒 | 上报指标 |
| `subject_tags` 定时器 | 每分钟第 30 秒 | 检查到期标签并同步成员 |
| `subject_attributes` 定时器 | 每分钟第 45 秒 | 按任务时区检查属性维护计划 |

采集计划对账（每个空间一个协程，每分钟一次）、自动补采与代码包清理（每天一次，启动 10 分钟后第一次）在进程内常驻运行，不经过 tRPC 定时器。
改云上状态的操作（建函数、改环境、换代码、设定时器、删函数）都在进程内的操作表里由后台协程执行，同一个函数同一时刻只有一个操作，见第 10 节。

## 2. 领域模型

| 对象 | 表 | 说明 |
| --- | --- | --- |
| CollectionTask | `t_collector_tasks`、`t_collector_task_tags` | 采集任务：数据类型（`kline` / `kline_resample`）、采集方式（K 线任务的 `c_ingest`，见第 3a 节）、采集参数、绑定的标签、结果数据集与 View |
| FetchPlan | `t_collector_fetch_plans` | 采集计划：每个空间同一时间最多一份未生效的计划，最近一份已生效的计划即“已生效状态”。记录全部保留，补采按历史计划找当时负责某个标的的函数与交易所符号映射 |
| SeriesTimeline | `t_collector_series_timeline` | 标的时间线：每个采集数据集的每个频率从某个生效周期起应有的序列（空序列表示从这一刻起不再采集），按写入先后重放；同一生效点后写的覆盖先写的；重新登记时整空间删除。检查、自动补采、历史扫描、收盘重取、健康度都读它；合成目标数据集不在里面 |
| BackfillJob / Chunk | `t_collector_kline_backfill_jobs`、`t_collector_kline_backfill_chunks` | K 线补采作业（范围、来源、类型按列保存）与分块 |
| Watermark | `t_collector_backfill_watermarks` | 自动补采的扫描水位 |
| SourceAbsence | `t_collector_source_absences` | 已确认“行情源没有”的 K 线区间，检查与补采都扣除 |
| HistoryScan | `t_collector_history_scans` | 每个数据集最近一次历史缺口扫描的结果与缺口分组 |
| ResampleSnapshot | `t_collector_resample_snapshots` | 合成目标数据集登记过的标的快照（按生效点追加），决定一个目标桶用周期提交还是普通写入 |
| ResampleJob | `t_collector_resample_jobs` | 历史合成作业（范围、游标、进度、跳过样例） |
| BackfillNotice / EventOutbox | `t_collector_backfill_notices`、`t_collector_event_outbox` | 补写通知（补采分块确认、合成补写）与本地事件发件箱，发布 `event.collector.kline.backfilled` |
| StreamWorker | `t_collector_stream_workers` | `collector-stream` 的心跳、已应用的计划与连接状态（一空间一行） |
| SubjectExclusion | `t_collector_subject_exclusions` | 采集名单排除：叠加在标签成员之上、只作用于采集计划，可设到期时间，见第 6 节 |
| TagSyncRun | `t_collector_tag_sync_runs` | 标签的标的同步运行状态（上次运行时间、结果、错误，按空间与标签）：调度判断读它，Monitor 与管理台经 `ListTagSyncStatus` 读取；停掉 Collector 后删 `<部署根>/data/collector` 时随库清空 |
| CloudAccount | `t_collector_cloud_accounts` | 云账号：厂商（目前只有 `tencent`）、Admin 密钥 ID、COS 地域与桶；只保存密钥 ID，不保存密钥本身，见第 10a 节 |
| FunctionPackage | `t_collector_function_packages` | 云函数代码包：空间、包名、版本、COS 位置、大小与 MD5、状态（`pending` / `available`），每个（空间、包名）只留最新 3 个可用包 |

云函数本身不建表：函数名由采集计划决定，期望内容由计划算出，云上的实际状态每次现场读回，最近一次读回只放在内存里（运行状态页的“云上状态”一列读它）。

**一任务一结果。** 每个采集任务独占一个结果数据集和默认 View，ID 由任务 ID 派生
（`dataset_<task>`、`view_<task>_<类型>_<频率>`）。用户只面对“采集任务”和“采集结果”，
不需要管理数据集。删除任务时由用户选择保留结果，或物理删除结果 View、数据集及其数据。
内置任务定义在 `config/setup/collection-tasks.yaml`，首次启动时导入。

**标签与来源。** `kline` 任务的 Provider 与市场由所选标签固定绑定，同一任务的标签必须来自同一数据源（`sync.source`），
市场（`market_type`）要么全部相同，要么正好是现货加永续（统一数据集，见下）；创建时校验，否则计划生成会拒绝整个空间。
结果数据集的 `market_type` 属性取自这些标签，重采样据此校验源数据集。

**统一数据集。** 一个任务同时挂同一数据源的现货、永续两个标签，两条序列写进同一个数据集，用行键里已有的 `series_tag` 区分，
只要一个因子任务、一个 View。想按市场分开就建两个任务、各挂一个标签（管理台在同时选了两个市场时让用户在“合并为一个数据集”与“按市场拆成两个任务”之间选，选后者一次建两个任务，第二个失败就保留第一个并提示补建）。
不另存“组织方式”字段，数据集属性 `market_type=multi` 就是统一数据集的标记，`data_source_id` 保留数据源。
- **tag 取值**沿用采集写行的约定：现货 `venue:binance|market:spot|source:spot_http`，永续 `venue:binance|market:swap|source:swap_http`。
  tag 到市场用 `packages/seriesset` 的 `SeriesTagMarket(tag)`（按 `market:` 段解析，没有这一段视为现货，返回小写 `spot`、`swap`），生成 tag 的正向逻辑（`PlanSeriesTag`）留在 Collector。
- **已有任务不能在单市场与统一数据集之间切换**：更新任务不允许增删标签（含跨市场增删），后端的 `UpdateTask` 拦截，要换就新建任务。统一数据集一律新建，不改造已有的分开数据集。
- **每个市场的标的与活跃状态**来自数据集挂的标签：现货标签下的标的属于现货序列，永续标签下的属于永续序列；一个市场的标的缺失、失败、延迟不连累另一个市场。
- 单市场任务的行为与输出不受影响。统一数据集上只用一个市场的消费者也会受另一个市场拖慢（两个市场共用一份快照，周期要等两边都提交或到截止时间），只用一个市场的用户应选“分开”。
K 线来源有两种定法，看行情源目录里这个（市场，品种）的数据源有没有登记为按路由分配：没有的（加密货币，A 股的指数、可转债）采集请求固定用标签的来源；有的（A 股股票）计划仍按标签来源分组，但实时采集与补采请求不写死来源，由 `config/markets/stockcn/route.yaml` 按频率给每个标的固定分配一个 primary（按路由 ID 与标的哈希，不随调用变化），失败或限流再按候选链回落，分摊各家的频率限制；序列标签固定为 `default`，写入行的 `source_provider`、`provider_id`、`source_id` 记实际取到数据的来源。

各行情源在函数进程内的并发与每秒上限写在 `config/markets/stockcn/sources/*.yaml`（编在二进制里），计划里 A 股的函数内并发（`concurrency`）与熔断并发（`feed_concurrency`）由它们推导，每函数标的数与函数个数由它们和权重、标的数估算（`auto_size`）。
补采、追赶、缺口修复这类持续几分钟到几小时的请求还会按压力信号自适应调速（控制方式参考 [agilelimiter](https://github.com/Yiming1997/agilelimiter)，按统计周期而不是按单次请求）：每秒上限是最大值，速率从它开始；行情源返回限流、繁忙立即减半；每秒汇总一次，超时、断连、5xx 的占比超过 5% 加 3 倍标准误差（一个周期至少 5 个请求）就降 20%；连续 2 个健康周期、降速后已过 3 秒、并且流量确实用到了当前速率的一半以上才升 10%；下限是上限的 10%。速率在本进程内按行情源共享。实时采集每 5 分钟只有 1～2 秒的突发，不使用。
交易时段市场的时序结果数据集还写分桶信息，取自 `packages/barclock` 的市场登记：stockcn 为数据集字段 `alignment=session`、属性 `calendar=cn_stock`；crypto 不写，策略按缺省的 `crypto_24x7` 处理。策略按 `calendar` 选交易日历（`internal/planner/taskresult/result.go`）。
创建校验按实际行情源能力判断：Binance 现货/合约支持 1m～1mo；东方财富 A 股（`eastmoney/equity`）支持 1m、5m、1d。输出字段里选了附加字段时另按第 4a 节的规则校验。
腾讯源缺成交额时按 `close × volume` 估算写入 `amount`，`amount_quality=estimated_close_x_volume` 标明是估算值（其余来源为 `reported`）。
采集只从计划生效的周期起实时采集；历史数据用 `SubmitKlineBackfill` 补采。检查与自动补采只看采集计划覆盖的时间（每个数据集从时间线起点起：最早一次生效的周期，重新登记之后是重新登记选出的生效周期，见第 3 节“重新登记”），更早的数据只能由 `force` 补采：`force` 的范围可以早于最早的生效点，更早时间的标的集合沿用最早一段的标的，分块完成后同样读回确认（任务参数里已删除的 `history_policy` 在存量任务里解析时忽略，启动对账时会改写存量任务并重算定义哈希）。
`CheckKline` / `SubmitKlineBackfill` 是同步操作，服务端业务预算 300 秒（网关路由 310 秒，tRPC 超时 320 秒），浏览器超时 330 秒。

## 3. 实时采集链路

云函数拉取方式（采集方式 `scf`，非 crypto 空间默认）是：腾讯云定时器触发函数，函数按环境变量里的采集计划自行采集并提交 Storage；crypto 默认走 WS 推送（采集方式 `stream`，补采走 `collector-stream` 的本地执行端，见第 3a 节），同样提交到 Storage、缺口同样由检查与补采修复。下面按云函数路径说明：

```text
Collector 对账协程（每个空间，每分钟）
  ├─ 读任务与标签成员，算出每个数据集的标的集合 hash 与函数分配
  ├─ 无变化：什么都不做
  └─ 有变化：选生效周期 P → Storage 登记序列快照 → 更新函数环境变量（新旧两份都带生效起点）
     统一数据集：两个市场各有自己的函数，两边的计划都包含这个数据集，序列是（标的、各市场的 series_tag）的并集，
     共用同一份快照哈希，各自只提交自己 tag 的序号；`Plan` 结构不变（SCF 严格解码，tag 由 `PlanSeriesTag(plan.Market)` 推出）。
     允许迟到取两个市场里较大的；一个市场的标的变化会让两个市场的函数一起重新下发
SCF 函数（Timer 触发）
  ├─ 按计划与事件时间确定本周期要采的（数据集、标的）
  ├─ 并发请求行情源，只保留已收盘的 K 线
  └─ 经入口主机网关的外部入口（11004）调用 CommitTimeSeriesBatch 写入 Storage；调用内按预算尝试或切换端点，最终失败项上报 CLS
Collector 自动补采（每个空间）
  └─ 扫描 Storage 里缺失的 K 线，分块调用补采函数写回
```

- 函数调用结束后的失败不由 Collector 即时重投；行情请求在调用内部仍可重试或切换候选源。剩余缺口由检查与补采统一修复：`moox-cli collector kline check` 比对
  Storage 与采集计划，`kline backfill` 补采；自动补采按水位扫描最近的缺口。自动补采只在发现缺口时建作业，
  所以近 24 小时的自动作业就是实时采集漏掉的 K 线，运行状态页据此统计“实时缺口”。
- **行情源缺失**：补采后复查仍缺的 K 线可能是行情源本来没有（停牌、无成交的分钟），也可能是上游晚出数。分块（含单根分块）第一次
  记下仍缺的区间并退回重跑，连续两次缺的完全一样才确认，不一样就继续重跑，超过最大尝试次数才失败。确认的区间永久写入
  `t_collector_source_absences`，检查、自动补采与历史扫描都扣除它们（整段重拉不扣除），不再算缺口、不影响健康等级。
  行情源后来补上数据时用 `ClearSourceAbsences`（页面“清除并重新检查”）按数据集清空，并让历史扫描重新进行。
- **统一数据集的检查与补采按序列（标的、series_tag）**：数据集的一段计划里出现两个以上 `series_tag` 才进入按序列模式（单 tag 的数据集读法不变，读取不带 tag）。
  期望点数、缺口（`KlineGap.series_tag`）、`MaxCheckPoints`、`MaxGaps` 都按序列计；计数接口会把同一标的的不同 tag 合并，所以按 tag 分请求，
  读行的 selector 也带 tag。只缺永续的一段时间会被查出，补采按（标的、市场）找计划：缺口 tag 经 `SeriesTagMarket` 得到市场，只用市场类型相同的计划，
  写出的行 tag 与缺口一致，不会写出现货行；补采分块、已确认缺失（`t_collector_kline_backfill_chunks`、`t_collector_source_absences`）带 `c_series_tag`，
  并放进唯一键、主键（单序列为空串）。补采确认后发布的 `event.collector.kline.backfilled` 在按序列模式下带 `series_tags`，单序列的事件不变。
- 强制重拉（`force`）的分块遇到函数报失败会退回重试，一共执行 5 次都失败才记失败（行已经在库里，失败后没有缺口可让自动补采重新发现）；按缺口补采的分块失败一次就记失败。
- 补采作业的失败分块可以 `RetryKlineBackfill` 重试；已结束的作业由每分钟的维护任务清理：自动作业保留 7 天，手动作业保留 30 天。
- 自动补采每 5 分钟一个槽、槽内偏移 2 分 30 秒后才扫（避开整点与每分钟开头的采集高峰），每次只检查水位向前重叠 5 分钟起、
  最多 1 小时的窗口，落后时分多次追赶。
- 市场的 `market.yaml` 配了 `refetch_after_close_minutes` 时，收市后这么多分钟的那一轮另外提交一次当天整天的强制补采
  （港股、美股配了，见第 4c、4d 节）；没配的市场没有这一步。
- **先计数、再读行**：检查（自动补采、手动检查、历史扫描）先用 `PrimaryStore.CountTimeSeriesRows` 按标的统计区间内已有的根数
  （每批 500 个标的、只回传计数），根数正好等于“应有 - 已确认缺失”的标的没有缺口；只有其余标的才读行（每批 50 个）定位缺口，
  历史扫描中一根都没有的标的（没有历史）也不读行。读取量随缺口而不是随标的数增长。深度检查要校验字段、强制重拉不读数据，二者不计数；
  计数失败时退回逐行比对。读行时行响应约 200 字节一行，跨主机调用的压缩（恒定开启）
  不能去掉，否则缺口多时公网链路会被占满、读超时，水位无法推进并拖慢同时段的策略读取与事件投递。
  已知局限：计数只比对数量，若某根已确认缺失的 K 线后来补上、同时另一根缺失，数量恰好相等时会漏报这一根；A 股的应有时间点只取交易时段内的桶（按 barclock），
  区间内非交易时段若有写入同样会抵消一根缺失。
- **历史缺口发现**：检查与自动补采只看采集计划覆盖的时间，早于数据集最早生效点的数据（旧的采集方式或历史导入留下的）里的孔洞，
  它们看不到。Collector 在自动补采之后按数据集定期读回最早生效点之前的 500 根 K 线（同一空间每 5 分钟最多扫一个数据集，
  同一数据集每 24 小时扫一次，读取失败 1 小时后重试），只报告每个标的第一根 K 线之后的缺口（新上市的标的前面没有数据，不算），
  **不自动补采**：结果（扣除已确认缺失后的缺口根数、标的数与至多 200 组缺口）写入 `t_collector_history_scans`，扫描节奏也以它为准，
  重启不丢；日志里 `collector history scan` 是每个数据集的汇总，`collector_history_gap` 是范围相同的缺口合并后的一组。
  操作员在运行状态页点“补采确认”（`ConfirmHistoryGaps`，CLI `kline history-confirm`）按记下的缺口精确补采，
  行情源本来没有的部分在补采时被确认，以后不再报告；
  还没被确认的（尚未上市、没有成交的缺口）会每天重复提示，可以忽略，或点“补采确认”让补采把它们确认下来。
- 周期是否完成以 Storage 主服务（storage-primary）为准（见[存储](存储.md)第 4 节）。
- 采集计划由 Collector 生成并保存在 `t_collector_fetch_plans`；`moox-cli collector fetch-plan` 查看函数分配与变更进度，
  `moox-cli collector status` 与控制台“采集任务 → 运行状态”查看总体健康与各数据集的自动巡检进度、缺口和补采情况（见第 11 节）。
- **标的时间线**由对账写入，和采集计划记录在同一个事务里：建计划时，不再采集的数据集写一行空序列（从它的生效周期起停止）；
  Storage 确认登记序列快照后，标的集合变了的数据集写一行“从生效周期起是这份序列”（未生效但已登记的计划也算，生效周期只在登记之前因过期重选，登记之后不再变）。
  一个空间同时只有一份未生效的计划，它一直推进到生效，不会被新计划取代，所以时间线里不会留下没生效的行。一段的结束是同一数据集同一频率下一行的生效点。
- **重新登记**：序列快照登记在 storage-primary 的 Pebble 库里。Storage 数据被整体清空后快照没了，函数的周期提交会因“快照缺失”被拒绝，
  而对账只在数据集标的集合 hash 变化时才登记。`moox-cli collector fetch-plan reregister --space-id <空间> --yes`
  （RPC `ReregisterFetchPlan`）把最近一份已生效计划里全部数据集的 hash 清空，下一轮对账会把它们都当作变化：生成新计划、重新登记快照、
  选新的生效周期，函数沿用不动。同一个事务里删掉该空间的全部时间线行：此前的计划段作废（包括已退役的数据集，
  它们以后重新启用时同样从新的生效周期开始），每个数据集的时间线从新计划的生效周期重新写起。
  新快照登记之前（通常 1～2 分钟）这些数据集不检查、不补采、不扫历史，运行状态页暂不列出，超过 30 分钟仍没有新计划接手时
  运行状态报异常；登记之后检查与自动补采从新的生效周期起，历史扫描读回它之前的 500 根，清库前计划覆盖的时间不再当作缺口。同一个调用清掉该空间的补采作业、自动补采水位与历史扫描记录
  （水位留空时自动补采从时间线起点扫起，也就是新的生效周期）。空间里有未生效的计划时拒绝。这个 RPC 是新增的网关路由（只允许 `moox-cli` 调用），服务目录变化需要 Admin、Monitor 与各主机 host-gateway 一起发布后 `moox-cli` 才调得通，见[部署与运维](../部署与运维.md#_8-常见故障与处理)。完整的清库顺序见[部署与运维](../部署与运维.md#清空全部数据重新积累)。
- 函数的入口固定为同地域一台入口主机网关的外部入口（`11004`），地址和入口主机 ID 由部署清单派生（环境变量 `MOOX_ENTRY_ADDRESS`、`MOOX_ENTRY_HOST`）；
  函数的运行参数（计划、Storage 入口、CLS 配置）只写在 SCF 环境变量里，SCF 代码包本身不带任何凭据。
- 函数日志不会自动投递：每次调用把失败项（`market_fetch_item_failure`）、批次摘要（`market_fetch_batch`）、
  偏慢或重试过的单项（`market_fetch_item_slow`）与写入 Storage 的耗时（`market_fetch_commit`）上报到 CLS，
  字段与索引见[部署与运维](../部署与运维.md)。整点前后行情源响应变慢时，用这些阶段耗时区分慢在排队、DNS、建连、
  TLS 握手、行情源首字节还是重试（见部署与运维的“上报内容”）。

## 3a. 采集方式（WS 推送、云函数拉取、本地拉取）

采集方式记在 K 线任务上，是任务表的一列 `c_ingest`，只有三个取值；合成任务没有采集方式：

| 取值 | 实时采集 | 补采 |
| --- | --- | --- |
| `stream` | `collector-stream` 接收交易所 WS 推送的收盘 K 线 | `collector-stream` 同进程的本地执行端 |
| `scf` | 云函数定时拉取 REST | 云函数（补采函数） |
| `local` | `collector-stream` 本地定时拉取 REST | 本地执行端 |

- **默认值**：建任务不写采集方式时，取任务所在空间的市场默认值，即 `config/markets/<市场>/market.yaml` 顶层的 `ingest`（crypto 是 `stream`，stockcn、stockhk、stockus 是 `scf`）。
  默认值在任务仓库写入这一层填上，管理台与命令行建任务、内置任务种子走的是同一处；空间不是登记的市场时必须写明。`moox.toml`、渲染出的配置、任务参数里都没有采集方式。
- **切换**：只由 `moox-cli collector ingest-mode set --ingest stream|scf|local` 切换；带 `--dataset-id` 改写这个数据集的任务，不带改空间的全部 K 线任务。切到 `stream` 或 `local` 要求 `collector-stream` 在线。
  采集方式不进任务的定义哈希，切换不改变任务身份。
- **一个数据集一个取值**：一个结果数据集只由一个任务写（现货加永续的统一数据集也是一个任务带两个标签），建任务时拒绝第二个任务写同一个数据集，所以数据集的采集方式不会出现两个值；对账器算期望状态时再兜底检查一次。

- **计划项**：对账器把期望状态分给三类执行端：SCF 函数（`moox-fetch-plan-…`）、`stream-<空间>-<市场>`、`local-<空间>-<市场>`。SCF 专属步骤（建函数、改环境、换代码、定时器）
  只作用于 SCF 项；推送与本地项由 `collector-stream` 经 `StreamCollector.PullStreamPlan` 拉取，10 秒一次心跳上报已应用的计划与阶段，Collector 以心跳确认代替云端读回。
  条目上限：SCF 每函数 200，推送与本地 4000。
- **截止跟随采集方式**：`stream` 的 `allowed_lateness_seconds` 默认 1m 5 秒、1h 8 秒（`stream.lateness_s`，任务参数显式指定的以任务为准），`scf`、`local` 沿用拉取的值（合约 20 秒，见第 10 节）。
  `collector-stream` 在一个周期的全部标的到齐时立即提交，否则在 `收盘 + 截止 − commit_reserve_ms`（默认 1000）提交已到的部分，缺的标的由补采补齐。
- **交接**：`ingest-mode set` 之后下一轮对账生成交接计划，按频率选生效周期 P（至少提前 3 分钟）：P 之前旧执行端写，P 起新执行端写；截止在 drain 阶段（旧截止的窗口结束后、最后一次下发之前）
  改为新值（只看时间，不等过渡阶段的确认：旧端失联或云端操作慢时也按时改，否则新执行端的周期会因截止还是旧值而整期被拒）。交接与标的变更分开（同时发生时先完成标的变更），Collector 重启后按库里的计划续跑。
  drain 结束后 SCF 函数去掉切走的数据集，函数里全部数据集都切走后停用定时器（函数保留作为备用）。
- **旧执行端失联时的固定规则**（没有强制开关）：计划里没有数据集正切到 `stream` 或 `local`，并且 `collector-stream` 的心跳已超时（180 秒）时，这份计划不等它确认。
  它只是旧执行端的交接计划（`stream` 或 `local` 切到 `scf`）会放行；数据集留在它上面、只是标的变了的计划也会放行；有数据集正切到它上面的计划仍然要等它确认。
  Collector 进程启动不满 180 秒时不按离线放行：重启后心跳表里的时间是旧的，要先给它一次上报的机会。
  “正切到它上面”只指交接（数据集原来由别的执行端写）。新增推送或本地拉取数据集的计划（新建任务、数据集退出后回来）不算：`collector-stream` 离线超过心跳超时后，
  这份计划同样不等它确认就生效，它恢复之前新数据集开头的周期没有人写，由补采补上。
  后果：`collector-stream` 连控制机和连 Storage 是两条路，它可能心跳超时但仍在写 Storage，这时生效周期附近两个执行端可能各提交一次同一个周期。Storage 对同一份快照的两次提交是接受并合并，不是拒绝：
  周期还在等待时成功位图取并集、行按字段后写覆盖先写；周期已到终态或已过截止时不写行，返回终态；只有哈希或标的数不一致才拒绝。所以周期不会写错、完成判定不会错，
  只是同一根 K 线可能混着两个来源的字段值（crypto 的两个来源取的是同一份交易所数据）。证据是 Storage 的 `modules/storage/internal/service/datanode/pebble/period_golden_test.go`：`TestGoldenLedgerJudgement` 与并发提交用例。
- **补采**：补采按任务的采集方式选执行端：`scf` 调 SCF 补采函数，`stream`、`local` 调本地执行端 `MarketFetchExecutor.Invoke`（`collector-stream` 的 11450 端口，独立并发上限 4）。
- **下架**：`collector-stream` 在合约上下架推送或连续 3 个 1m 周期没有收盘推送时上报疑似下架标的，Collector 立即同步对应市场的自动标签（快照取数重试 3 次，失败时保持成员）。
- **运行状态**：周期统计（到达、截止时仍缺、是否提交）进 Collector 指标，不落库；运行状态页“函数”区列出推送与本地项、连接与最近周期。
  Monitor 在心跳中断超过 3 分钟、某数据集连续 3 个周期有失败标的（疑似下架不计）时告警，见[监控](监控.md)。
- **下游**：因子引擎按连续水位逐期计算，零提交或缺失超过阈值的周期会阻塞，补采确认后 Collector 发布 `event.collector.kline.backfilled`（带确认行情源没有的 K 线），因子引擎订阅它推进水位，见[因子](因子.md)。

标的同步、SCF 与本地取数、`collector-stream` 接收都从目录按能力取用：实现了 `InstrumentFetcher` 的用于标的同步，`KlineFetcher` 用于取数与补采，

只提供附加字段的来源（A 股的复权因子、申万行业、财务）也登记在目录里，但不取 K 线，不出现在上表和 `route.yaml` 里；管理台数据源页下方的“附加字段来源”列出它们。

数据源的地址、限流等配置在 `configs/sources/market/*.yaml`（SCF 包内为 `sources/market/`）；
各市场的参数、路由与数据源运行参数在 `config/markets/<市场>/`（`market.yaml`、`route.yaml`、`sources/*.yaml`），编在 Collector 与云函数的二进制里，发布不用带这些文件；各市场的标的规则（标的 ID 的写法、默认品种、标的属性）在 `internal/markets/<市场>`。每个数据源按出口 IP 维护独立的限流与
熔断，单个数据源失败时在本次调用内切换到备用数据源。

**A 股 K 线。** stockcn 走 SCF 定时直采（采集方式 `scf`），内置任务“A 股 K 线 5m”、“A 股 K 线 1d”和“A 股日线（复权、行业、财务、换手率、股本）”采沪深 300 成分股（标签 `cn_hs300`），默认停用；两条日线任务要用户显式启用，附加字段见第 4b 节。
`route.yaml` 写明它管的品种（`instrument_type: equity`）和结算延迟（`settle_delay_ms: 800`），按频率分候选链，路由 ID 是 `stockcn_equity_kline_<频率>`：

| 频率 | 主 | 备 |
| --- | --- | --- |
| 5m | 通达信（权重 4）、东方财富（`push2his` K 线接口，`klt=5`，权重 2），按权重对股票固定分配 | 按通达信、东方财富、新浪、腾讯的顺序回落；每家最多试 3 次再换下一家；新浪、腾讯只做备源（收盘后头几秒给的是未定稿值，见下文） |
| 1m | 新浪、腾讯 | 通达信、东方财富 |
| 1d | 通达信 | 东方财富（`push2his` K 线接口，`klt=101`） |

- 都存不复权 OHLCV：东方财富请求 `fqt=0`，通达信请求固定为不复权，主备切换时口径一致；除权日前后跨越除权的窗口会有一次跳变。
- 腾讯没有成交额，按收盘价 × 成交量估算并标 `amount_quality=estimated_close_x_volume`；通达信的成交额是 float32，末位有误差。
- 东方财富与通达信日内 K 线的时间标签都是收盘时刻，归一化时减去一个周期作为行键（开盘时刻）。通达信把上午最后一根标成 13:00，
  按同一交易日的前一根（上午最后一根，5m 是 11:25）处理。成交量统一为股（东方财富的“手”乘 100）。
- 回看能力按频率声明：东方财富 1m 为 24 小时、5m 为 30 天，通达信 365 天；超出东方财富回看窗口的补采落到通达信。
  日线：通达信 10 年（从最新一根往回取），东方财富任意区间（按日期取，能取到上市首日）。
- **日线的行键是日期键**：交易日期的 UTC 零点（10-09 的日线是 `2026-10-09T00:00:00Z`），与 `packages/barclock` 的 1d 键、统一校验、
  完整性检查和策略一致；只有交易日有桶。`close_time` 是键加 24 小时，不是 15:00；`trade_date` 与日内行一样是交易日的上海零点。
  交易日 D 的日线在 D+1 日 00:00 UTC（北京时间 08:00）到期并采集。东方财富日线的成交量以手为单位，乘 100 后与通达信差在 100 股以内。
  完整性检查里日线的连续缺失不按周末、节假日拆段，一个标的一年的日线是一个补采分块。通达信补日线固定从最新一根取到区间起点
  （停牌的标的根数只会比市场交易日少，窗口一定覆盖到起点），区间之后多取的部分由采集管线截掉。
- 函数每 5 分钟触发一次，只采交易时段内的桶：午休、收盘后、非交易日直接返回 `no_work`。

**A 股 5m 为什么用通达信和东方财富做主源，新浪和腾讯做备源。** 选源看的是“收盘后尽快拿到定稿值”，不是谁先返回：

- **四个来源的返回里都没有“这根 K 线已完成”的标记。** 东方财富（`push2his`）每根只有时间、开收高低、成交量、成交额和涨跌幅、换手率等派生字段；新浪是 `day/open/high/low/close/volume/amount`；
  腾讯是按位置排列的数组；通达信是二进制的时间、开收高低、成交量、成交额。进行中的那一根和已收盘的那一根格式完全一样，只能靠本机时间判断收盘，
  再靠“等到值稳定”保证取到的是定稿。所以必须实测各家在收盘后多久给出定稿值，不能凭返回字段判断。
- **实测方法与结果**（2026-11-06 盘中，南京 SCF 同 VPC 子网，14:35～14:55 连续 5 个 5 分钟边界，每个来源每次 60 只标的、共 300 个样本，
  收盘后每 200 毫秒轮询目标 K 线，记下第一次出现的时刻与数值，8 秒后再取一次看数值有没有变）：

  | 来源 | 首次出现（中位 / 99 分位） | 首次出现之后 8 秒数值又变了的比例 |
  | --- | --- | --- |
  | 东方财富 | 183 / 271 毫秒 | 0 |
  | 通达信 | 120 / 354 毫秒 | 0 |
  | 新浪 | 135 / 242 毫秒 | 69%（约一半收盘价差 0.01～0.04，成交量中位差 1.5%～5.8%，最大 32%） |
  | 腾讯 | 142 / 250 毫秒 | 85% |

  四家出现得都很快，区别在于新浪、腾讯一开始给的是未定稿值，之后还会更新；通达信、东方财富第一次给的就是最终值。
  Storage 的周期一旦全部提交就锁定，早取到的未定稿值改不回来，所以不能让它们做主源。
- **限频与稳定性。** 同一实测里四家都扛得住 64 并发突发、每秒 80 次持续，没有触发频控；通达信是 TCP 直连，延迟最低且不随并发上升。
  各源在函数进程内的并发与每秒上限写在 `config/markets/stockcn/sources/*.yaml`（编在二进制里），取值都小于各家的频控值，不需要留很大余量。
- **只剩两个主源，要避免单个出口 IP 触发频控，所以把函数拆细并让出口 IP 尽量分开。** 沪深 300 约 200 只落在通达信、100 只落在东方财富。
  函数按标的数估算个数（`auto_size`），并设了下限（`min_functions`，现为 8）：每个函数分到的标的少，同一时刻每个出口 IP 对单个来源发出的请求就少。
  但函数个数不等于出口 IP 个数：SCF 的公网出口来自云上共享的地址池，不同函数可能用同一个 IP。2026-11-06 实测线上 15 个函数连续探测两次，
  只有 9～10 个不同 IP，个别 IP 被 3～4 个函数共用，同一个函数的出口 IP 基本稳定、实例回收后可能变。
  所以 Collector 在**计划新建了函数之后（包括云端函数被删后按已生效计划重建）只做一次**出口 IP 去重。这是与市场无关的公共能力，封装在 `modules/collector/internal/egressbalance` 包里，
  任何空间都能在 `scf_plan.spaces.<空间>.egress_balance` 里开启（A 股默认开启）：核对云端没有其他问题时，调用每个函数的 `egress_probe` 取公网出口 IP，
  把共用同一个 IP 的函数（每个 IP 只留 `max_per_ip` 个，默认 1）交给已有的“云端缺失重建”流程删掉重建，新实例会重新分到地址；
  每轮相隔几分钟，最多 `rounds`（默认 5）轮，连续两轮不同 IP 数没有增加就说明地址池里的 IP 不够，停止并保持现状。
  删除重建期间这些函数没有数据，所以用 `idle_start`、`idle_end`、`timezone` 限定允许重建的时段（A 股是北京时间 15:10 到次日 07:50，避开日内交易时段和 08:00 的日线采集；不写表示任何时候）；
  做完（或停止）之后不再探测，也不做每小时的检查。这只能降低重叠的概率，不是保证：实例回收后出口 IP 可能又变；要复查随时用
  `moox-cli collector function probe-egress --space-id stockcn`。
- **备源的作用。** 通达信、东方财富失败（连续 3 次）才会换到新浪，再不行换腾讯。备源取到的值可能是未定稿的，但总比这一根缺失好，缺口以后可由补采或完整性检查修复。
- **成交量与成交额的小误差不作为选源依据。** 各源成交量约差万分之几，腾讯没有成交额只能估算（`amount_quality=estimated_close_x_volume`），通达信成交额是 float32 末位有误差，
  这些在允许范围内，不影响双均线等因子结果。
- **重新评估。** 来源的行为会变，换主源或调权重前要在盘中至少连续测几个 5 分钟边界，按上面的方法（首次出现时刻、之后数值是否变化、限频）重新对比。

**交易日历只有一份。** A 股交易日历内嵌在 `packages/marketcalendar`（`cn_stock`），交易时段登记在 `packages/barclock`（`Asia/Shanghai`，
`09:30-11:30`、`13:00-15:00`）。Collector 判断“某根是不是交易桶”、取最近收盘的桶、检查日历覆盖期统一经过 `internal/markets/trading.go`，
采集过滤、完整性检查、补采与通达信的时间标签换算共用它（K 线合成直接按 barclock 的市场登记取时钟）；SCF 包里不再带日历文件。日历每年更新一次，步骤见 skill 的 `references/fresh-deploy.md`。

## 4a. 附加字段

附加字段是 K 线行情（开高低收、成交量等）之外、按根写进同一行的可选列，例如币安永续的资金费率、A 股日线的复权因子、行业和财务数据。
它们做成 K 线数据集里的列，而不是单独的数据集：因子引擎会把源数据集的全部业务列带进因子结果数据集，策略用 `来源名.列名`（例如 `daily.sw_l1`）就能读到，因子和策略的读取都不用改。

K 线采集任务在输出字段里选它们，**默认都不选**；不选时采集、写入、建列与没有这项能力时完全一致。

**来源怎样登记。**

- 提供附加字段的来源实现 `marketdata.FieldSource`（`internal/marketdata/fields.go`）：`FieldSpecs()` 列出它提供的字段，`FetchFields()` 按“一个标的、一段时间”返回各根 K 线上的值。
  每个字段的定义（`FieldSpec`）有四项：字段名（同一市场内唯一）、值类型（`double` 或 `int`）、缺行时的补法 `fill`（`prev` 沿用上一根，`zero` 补 0，写进数据集列的属性供因子引擎使用）、适用的 K 线频率。
- 来源登记在行情源目录（第 4 节）。有两种形态：
  - K 线适配器自己兼任，例如币安永续适配器提供 `funding_rate`。字段清单按实例返回：币安现货与永续是同一个适配器类型，现货实例返回空清单。
  - 只提供附加字段的来源，用独立的提供方 ID 登记（A 股的 `sina_hfq`、`swsresearch`、`sina_finance`、`eastmoney_turnover`、`eastmoney_select`），不取 K 线，不写进 `route.yaml`。
    它们的并发与每秒上限写在 `config/markets/stockcn/sources/<提供方 ID>.yaml`（编在二进制里），按提供方 ID 加载，没有配置文件时用代码里的默认值。
- 采集管线按（市场, 品种）找出全部来源，再按字段名找到提供它的来源，与这根 K 线实际由哪个行情源取到无关。
- 接一类新数据的步骤：写一个实现 `FieldSource` 的来源，在目录里登记一项，在 `config/setup/metadata.yaml` 的字段目录里加上这些字段（管理台的显示名、分组、单位取自字段目录）。任务校验、结果数据集建列、任务表单、数据源页的展示都从目录生成，不用逐处添加。

**字段怎样选。**

- `GetDataTypeConfigWithFields` 的返回里有 `extra_fields`：每一项是字段名、市场、品种、适用频率、提供方 ID。管理台按它过滤任务表单里的输出字段，并在数据源页列出“附加字段来源”（见[前端](前端.md)）。
- 建任务时校验（`validateCollectionTaskTagRoutes`，不满足直接拒绝）：
  - 任务频率必须在字段的适用频率里；
  - 任务的**每个标签**对应的（市场, 品种）下都要有这个字段的来源。所以现货任务选不了资金费率，统一数据集（现货加永续）也选不了。
- 结果数据集与默认 View 只为显式选中的附加字段建列，列的类型、显示名和 `fill` 属性取自字段定义。输出字段留空（用默认字段）的任务没有附加字段的列。
- CLI 用 `moox-cli collector task create --output-field` 选择。这个参数会替换默认字段，所以要把基础字段和附加字段一起列全。
- **改任务只能减少输出字段，不能新增**（基础字段和附加字段都一样，`UpdateTask` 拒绝并提示新建任务）。原因：因子结果数据集的列在因子任务创建时确定，采集数据集后来多出的列不会出现在已有的因子结果数据集里，因子引擎带着新列写入会被 Storage 拒绝。
  要加字段就新建采集任务和对应的因子任务。原来没有显式选输出字段的任务，改成只列基础字段算减少，加附加字段算新增。

**取数与写入。**

- 拉取与补采共用同一条管线（`KlinePipeline`）。一个标的的附加字段在批次开始时与 K 线并行取；取数区间未知（只说“取最近若干根”）时，等 K 线取完按它们覆盖的时间范围再取。没有任何写入目标选中附加字段时不取数。
- 每个值的口径统一为“这根 K 线收盘时已经能知道的最新值”，由来源按自己记录的生效时间判断。实时采集和补采走同一个函数，同一根 K 线两条路径算出的值相同（财务和股本除外：财务重取会变，股本只有当日值、补采拿不到，见第 4b 节）。
- 实时批次给附加字段取数设了时间上限：批次截止前 2 秒（剩余时间不足时取剩余的一半）。超时按取数失败处理，留出时间让没选附加字段的写入目标照常写入。补采不设这个上限。
- 行里的附加字段按字段名排序写出，云函数、`collector-stream` 和补采写出的行一致。

**缺值与失败。** 这两种情况处理不同：

| 情况 | 处理 |
| --- | --- |
| 来源正常返回，但某根的某个字段没有值（没有申万记录的新股、没有上年数据的滚动值、金融类公司没有的科目、来源里没有这只股票） | 照常写行，这一列留空。来源以后补上也不会回填 |
| 来源报错（超时、限频、非 2xx、响应解析失败） | 选了这个来源字段的写入目标，这个标的这一项失败，错误归为可重试的 `provider_error`；没选这些字段的写入目标照常写入。失败的标的由缺口检查和补采补上 |
| 任务选了某个字段，但这条管线的（市场, 品种）下没有来源 | 配置错误，这一项按 `invalid` 失败，不重试。建任务的校验正常会拦住这种情况 |

- 不把没取到值的几根丢掉后照常报成功：补采复查连续两次缺同样的根会登记成“行情源没有”，之后不再补。
- 一个来源报错只影响它提供的字段。但一个任务如果同时选了几个来源的字段，任何一个来源报错都会让这个任务里这个标的的整行写不进去。想让行情不受附加来源影响，就另建一个不带附加字段的任务。
- **深度检查不含附加字段**：`kline check --deep` 要求每根都有值的字段，是任务选中的输出字段去掉附加字段（一个都不剩时是开高低收）。附加字段允许为空，不能据此判断缺口。
- **重采样不合成附加字段**：源数据集带附加字段也可以重采样，结果里没有这些列；重采样任务的输出字段里写了附加字段会被拒绝。

**发布顺序。** 新增附加字段时，Collector、云函数代码包、`collector-stream` 和内嵌管理台的 `admin` 要是同一版（逐台 `setup deploy`，并上传新的代码包），再建带这些字段的任务。

### 来源：币安永续资金费率

提供方 `binance`（永续实例），字段 `funding_rate`，`double`，`fill=zero`，适用频率 1h、1d。

**字段口径。**

- 值是结算时刻落在 `[bar_start, bar_end)` 内的资金费率之和，本根没有结算写 0；取币安返回的小数原值（0.0001 即 0.01%），字段目录的单位是 `ratio`。
- 结算可能比整点晚 1 毫秒，归属按原始毫秒判断；结算间隔有 8 小时、4 小时、1 小时三种，所以按区间求和。
- 第 k 根的值是第 k 根开盘时刻那次结算，这一刻持有的是第 k 根开盘调仓之前的仓位。按资金费结算的账本要用第 k−1 根期间的持仓结算第 k 根的费率。
- `fill=zero` 的原因：因子引擎读列时没有 `fill` 属性就沿用上一根，会重复计费。

**适用条件**（都由上面的通用校验得到，没有单独的判断）：

- 频率只能是 1h、1d。1m～30m 收盘时结算记录可能还没公布；1w、1M 推送不支持，一次要取的数据也太多。
- 标签必须全部是永续：现货下没有这个字段的来源，统一数据集因此也不能选。

**取数。**

- **限速**：资金费接口和 fundingInfo 共用“每 5 分钟 500 次”的配额。进程内只有一个限速器，每秒最多 1 次，实时请求排在补采请求前面；收到 429、418 时暂停全部资金费请求，连续触发时退避翻倍（5 秒起，最长 5 分钟），成功一次复位。请求在客户端只发一次，不在请求内重试。
- **查询方式**：区间左闭右开。不带 symbol 时按 4 小时分段查全部合约，某段满页（1000 条）就对半拆开重查；带 symbol 时按时间往后翻页，满页总要再翻一页确认。全市场查询里格式不对的记录跳过并记日志，指定合约的记录格式不对报错。
- **进程内小时缓存**：实际运行拉取管线的进程（`collector-stream`、SCF）各有一份按小时的全市场结算缓存，键是（小时, 合约），推送与拉取共用。控制机上的 Collector 不建。
  - 只有当前计划（推送或本地拉取）里有数据集选了 `funding_rate` 时，`collector-stream` 才启用整点取数：每个整点后约 2 分钟取上一个整点开始的这一小时，收盘前约 5 分钟再取一次覆盖，避免个别晚公布的记录被写成 0。启用时补取上一根与当前这一根已经过去的小时。
  - 没就绪的小时槽按需补取，走同一个限速器；取数失败按退避重试。SCF 没有常驻缓存，同样按需补取。
  - 1d 取本根覆盖的 24 个小时槽，全部就绪才算就绪。
- **推送**：周期提交前只读缓存，不调 REST。缓存没就绪时这一期先挂起，取到后回到这个数据集的协程再提交；到最晚提交时刻仍没有，这一期不提交，交给缺口补采（这一期的标的全部记为缺失）。推送路径不经过上面的通用取数，只是把值写进同一处。
- **拉取与补采**：实时批次读缓存，小时槽没就绪就等，等不到按来源报错处理；补采、追赶、缺口修复按合约查本块区间。查询区间里放不下完整一根的 K 线按报错处理，不当成“没有值”写成空列。
- **失败可见**：指标 `moox_collector_funding_fetch_failures_total{reason}`（`rate_limited`、`http_status`、`network`、`protocol`、`malformed_record`、`canceled`），日志带合约与区间。

**历史。** 需要这一列的任务从创建起就选上它；创建之前的历史用公开数据导入或 `kline backfill --force` 补。

**执行端。** 选了 `funding_rate` 的数据集要用 `collector-stream`（推送加本地拉取）。SCF 里 1d 一次要补取 24 个小时槽，每秒 1 次的限速下超出函数时限，不适合 1d。

## 4b. A 股日线与日线附加数据

A 股日线和 5m 一样走云函数定时采集，路由见第 4 节。日线上可以选五个来源的附加字段：后复权因子、申万行业、财务数据、换手率、股本，共 27 个字段，全部只适用于 `1d`、只适用于股票（指数、可转债没有）。`fill` 除换手率是 `zero`（停牌日补出的行换手率为 0）外都是 `prev`。

**内置任务。** `config/setup/collection-tasks.yaml` 里有两条日线任务，标签都是 `cn_hs300`、频率 `1d`，默认停用：

| 任务 | 任务 ID | 输出字段 |
| --- | --- | --- |
| A 股 K 线 1d | `dasftksvjhj2jom4vhi0` | 默认的 22 个基础字段，不带附加字段，行情不受附加来源影响 |
| A 股日线（复权、行业、财务、换手率、股本） | `dasftksvjhj2jom4vhj0` | 22 个基础字段加全部 27 个附加字段（输出字段只能在建任务时选全，所以一次带齐） |

- **两条都要用户显式启用。** 种子里它们带 `start: manual`，`moox-cli setup start --space-id stockcn` 不启用它们，只在输出的 `notes` 里提示“需手动启用”；
  启用用 `moox-cli collector task update --space-id stockcn --task-id <ID> --enabled=true`。`start` 只在种子文件和 `setup start` 之间起作用，不进任务表。
- **Skill 读数据用纯日线任务。** `setup skill-config` 按“标签 + 频率”找 K 线数据集，同一标签同一频率有两条内置任务时取没有指定 `output_fields` 的那条。
- **已有部署怎样得到它们。** Collector 启动时只在任务表为空（全新安装）时写入内置任务。已有部署在控制机上用
  `moox-collector-cli init --db-path <Collector 库> --seed-file <collection-tasks.yaml>` 补写：它只新建库里没有的（空间, 任务 ID），已有的任务不动，
  输出 `tasks_created`、`tasks_unchanged`。种子里的其他内置任务如果以前删过，也会被一起补回来（停用状态）。补写后重启 Collector，
  启动时才给新任务建结果数据集和 View。完整步骤见 skill 的 `references/ashare-daily.md`。

**采集时刻与对策略的影响。**

- 日线的行键是交易日期的 UTC 零点，周期按“键 + 24 小时”算收盘。所以交易日 D 的日线在 D+1 日 00:00 UTC、也就是**北京时间 D+1 日 08:00** 才到期并采集，不是 D 日 15:00 收盘后。
- 用日线做附加来源的日内策略（例如 5m 主帧加 `sources: {daily: {bar: 1d}}`）：D 日 15:00 收盘的那一根主帧要读 D 日的日线，会等到 D+1 日 08:00 之后日线和日线因子都到齐才求值，结果在次日开盘前给出。
  D 日盘中的其他各根读的是 D−1 日的日线，它在 D 日 08:00 已经到齐，不受影响。
- **实时失败要隔一天才自动补**。自动补采的扫描终点比当前时间晚“允许迟到 + 一个周期”，D 日的日线要到 D+2 日 08:00 之后才会被扫到，期间策略按缺数处理。急用时手工 `moox-cli collector kline backfill`。

### 来源：后复权因子

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `adj_factor` | double | 后复权因子。不复权收盘价 × 它 = 后复权价 |

- 提供方 `sina_hfq`。地址 `https://finance.sina.com.cn/realstock/company/<sh|sz><代码>/hfq.js`，一次返回这只股票上市以来的全部除权记录（除权日期、因子），不需要密钥。每只股票一次请求。
- 取值：除权日期不晚于这个交易日的最后一条记录的因子。第一条除权记录之前的交易日没有值。
- 存后复权而不是前复权：后复权因子写下之后不再变；前复权因子每次除权都会改写全部历史。K 线本身仍是不复权价（第 4 节）。
  前复权价在因子表达式里算：以当前这一根为基准，k 根之前的前复权收盘价是 `delay(close, k) * delay(adj_factor, k) / adj_factor`；只关心涨跌幅时直接用后复权价 `close * adj_factor`，比值相同。
- 来源返回 404（没有这只股票）时这一列留空。

| `sw_l2` | int | 申万二级行业代码：保留前 4 位，其余补零 | `480300` |
| `sw_l3` | int | 申万三级行业代码：完整 6 位 | `480301` |

- 提供方 `swsresearch`。地址 `https://www.swsresearch.com/swindex/pdf/SwClass2021/StockClassifyUse_stock.xls`：一个旧版 `.xls` 文件，约 1.1MB，每次行业调整一行（股票代码、计入日期、行业代码、更新日期），包含历史变迁。
- 取值：计入日期不晚于这个交易日的最后一条记录。文件里没有这只股票、或第一条记录之前的交易日没有值。
- 一次函数调用内文件只下载一次，供这次调用的全部标的使用；下载或解析失败也只记一次，这次调用里选了行业字段的标的全部按来源报错处理。文件有任何一行格式不对都整体报错，不给出部分结果。
- 这个网站的服务器握手时不发中间证书，Linux 上只凭系统根证书拼不出完整的证书链。来源把这张中间证书（GeoTrust G2 TLS CN RSA4096 SHA256 2022 CA1，有效期到 2032-12-14）内嵌进校验用的证书池，仍然校验整条链和主机名，没有关闭校验。证书到期或网站更换证书链后要更新内嵌的证书。
- 限制：申万只发布代码，不发布中文名，策略里按代码分组；文件里 2021 版分类之前的旧行业代码原样写出，不做新旧代码的换算，跨越分类改版的历史区间里同一行业可能有两个代码。

### 来源：财务

提供方 `sina_finance`。地址 `https://quotes.sina.cn/cn/api/openapi.php/CompanyFinanceService.getFinanceReport2022`，参数 `paperCode=<sh|sz><代码>`、`source=lrb|fzb|llb`（利润表、资产负债表、现金流量表）、`num=<期数>`。每只股票三次请求，三张表任何一张取不到都按来源报错处理。

| --- | --- | --- | --- | --- |

| `fin_operating_cash_flow` | 经营活动现金流量净额 | 现金流量表 | `MANANETR` | `fin_operating_cash_flow_ttm` |

`fin_report_period` 是 int，其余都是 double，金额单位是元。

- **累计值与滚动值。** 利润表、现金流量表的科目原值是年初至今的累计值（三季报是前三个季度之和）。带 `_ttm` 后缀的字段是滚动十二个月的值：本期累计 + 上年年报 − 上年同期累计；本期是年报时就是年报值。
  三项里任何一项还没生效或没有这个科目，滚动值留空。资产负债表的科目是期末时点值，没有滚动值。
- **不同行业的报表模板不同。** 同一科目在一般工商业、银行、保险、券商的报表里代码不同，所以一个字段登记了几个代码。金融类公司没有“营业总收入”等科目，这些列留空。
- **生效时间。** 一期财务数据从披露日的下一个交易日起可用（披露当天的日线仍用上一期）。披露日取“三张表的 `publish_date` 里最早的一个”与“法定披露截止日”中较早的那个。
  法定截止日：一季报 4 月 30 日，半年报 8 月 31 日，三季报 10 月 31 日，年报次年 4 月 30 日。
  这样取的原因是接口的 `publish_date` 只对最近几期是首次披露日：更早的报告期被后来的报告当作对比数重新列示时，`publish_date` 会变成那一次的日期，而且三张表不同步（利润表、现金流量表的对比数是上年同期，资产负债表的是上年年末）。
- **取哪一期。** 在这个交易日已生效的报告期里取报告期最大的一期。年报与一季报常在同一天披露，按报告期取可以保证用的是一季报。
- **请求期数。** 接口只能从最新一期往回取。每次请求的期数是“取数区间的起点到现在跨的季度数 + 6”：实时采集是 6 期（滚动值最远用到往前第 5 期），补最近一年约 10 期。一次请求返回，不翻页。
- 来源里没有这只股票、或这个交易日之前没有已生效的报告期时，财务字段全部留空。

| `turnover_rate` | DOUBLE | 当日换手率，单位是百分比（`0.90` 表示 0.90%），分母是流通股本 |

提供方 `eastmoney_turnover`。地址 `https://push2his.eastmoney.com/api/qt/stock/kline/get`（`klt=101`、`fqt=0`、`beg`、`end` 是区间的起止日期），取每行的第 11 列。每只股票一次请求，补一年也是一次。

### 来源：股本、每股股利、是否 ST

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `total_shares` | DOUBLE | 总股本（股） |
| `float_shares` | DOUBLE | 流通股本（股） |
| `dividend_per_share` | DOUBLE | 每股股利（元）：接口的最新股息率 × 最新价 ÷ 100 |
| `is_st` | INT | 名称里含 `ST` 为 1，否则为 0 |

提供方 `eastmoney_select`。地址 `https://data.eastmoney.com/dataapi/xuangu/list`（东方财富选股器），按 `filter=(SECURITY_CODE="<代码>")` 每只股票一次请求。

- **只有当前这一天的值，没有历史。** 每条记录带标注的交易日 `MAX_TRADE_DATE`，按它与取数区间的关系处理：落在区间内，写到那一个交易日的行上；晚于区间（补历史、隔天补采），这几列留空；早于区间的起点，说明接口还没更新到这一天，按取数失败处理（错误里写“选股器的数据还停在某天”），这次不写出这一行。实时采集没有当天的重试：下一次是 D+2 日的自动补采，那时接口已经标注为 D+1 日，这一行会写出来，但这 4 列为空。
  所以开通之前的日线行这 4 列是空的；平日某天实时采集失败，隔天补采时接口已经是下一个交易日的值，那一天的这 4 列也补不回来（那一天是周五或长假前最后一个交易日时还能补上）。
- **只取和价格无关的量。** 接口里的最新价、市值、市盈率、股息率都按盘中实时价计算，而标注的交易日在盘中还是上一个交易日（2026-11-12 盘中实测：标注 11-11，价格是 11-12 的盘中价），直接存下来会随采集时刻变化。股本不随价格变；每股股利由同一条响应里的股息率和最新价相乘得到，价格的影响相互抵消。
  市值和估值由内置日线因子用“当日收盘价 × 股本”计算（`total_mv`、`float_mv`、`pe_ttm`、`pb`、`ps_ttm`、`dv_ratio`，见 [因子](因子.md) 第 6 节的内置因子库）。
- 查不到这只股票（`success` 为 true、`data` 为空）时这几列留空；单个字段为空或不是有限的数字时只有那一个字段留空。HTTP 失败（包括 404）、响应解析失败、`success` 不为 true、返回的不是请求的这只股票、标注的交易日期无效按取数失败处理。
- 沪深 300 的样本里没有 ST 股，`is_st` 在内置任务的股票池里基本恒为 0；历史上某天是不是 ST 查不到。
- 接口在除权日的哪一天更新股本没有验证：提前更新时除权前一天算出的市值偏大，晚于除权日才更新时除权日起的几天偏小。

**实测**（2026-11-11，国内腾讯云主机）：复权因子单次 0.08 秒；财务每张表取 6 期 0.17～0.24 秒；一个函数 40 只标的（并发 8，每只 4 次请求）3.6 秒；八个函数共用一个出口、并发 64、共 1280 次请求 15.1 秒，全部成功，没有被限频；申万文件下载 0.3 秒。
换手率与股本（2026-11-12，同一台主机）：换手率单次 0.10 秒、取一年 0.2 秒；选股器单次 0.24 秒；八个函数共用一个出口、并发 64 时换手率 320 次 2.4 秒、选股器 320 次 6～7 秒（最慢一次 6.5 秒），全部成功，没有被限频。
五组字段都在云函数里取，60 秒的函数时限内余量充足。云函数实际出口上的表现没有单独测，上面按“全部函数共用一个出口”的最坏情况估计。北京时间 08:00 选股器标注的交易日是不是上一个交易日还没有实测到（只实测到 11:08 时是）。不是的话后果很重，发布前必须先确认：带股本字段的任务每天 08:00 的实时采集都会失败，整行（包括开高低收）要晚一天、等自动补采才写出；补采时接口已是下一个交易日，平日的股本列全部为空，只有周五和长假前最后一个交易日能写上，内置的估值因子只能沿用那一天的股本。

**限制**（另见文末“已知限制”）：只支持沪深股票，北交所、基金、可转债、指数没有这些字段；股本这一组没有历史，市值和估值只能从开通日起算。

## 4c. 港股 5m K 线

stockhk 和 A 股一样走 SCF 定时直采（采集方式 `scf`），只有 5m 一个周期；东方财富是主源，腾讯是备源（当天分时合成，见下文“腾讯备源”）。内置标签 `hk_hsi`（恒生指数成分股，写法见第 6 节）和内置任务“港股 K 线 5m”默认停用；任务不写输出字段，与 A 股 5m 一样输出股票行的全部字段。标的 ID 是五位代码加交易所，例如 `00700.XHKG`。交易时段 09:30～12:00、13:00～16:00（香港时间），每个交易日 66 根，半日市只有上午 30 根，时钟与日历登记在 `packages/barclock`。

**市场参数**（`modules/collector/config/markets/stockhk/market.yaml`，编在 Collector 与云函数的二进制里；产物包根目录的 `config/` 只有初始化种子 `config/setup/`，没有这个文件）：

| 项 | 取值 | 说明 |
| --- | --- | --- |
| `currency` | `HKD` | 成交额单位港元 |
| `allowed_lateness_seconds` | 90 | 与 A 股相同 |
| `egress_probe` | `public_ip` | 云函数出口探测只取出口公网 IP，与 A 股相同（两边共用南京出口） |
| `scf_plan.symbols_per_function` | 25 | 固定每函数 25 只，恒指 95 只共 4 个函数；不估算函数个数，不做出口 IP 去重 |
| `scf_plan.fetch.not_before_ms` | 5000 | 收盘后等 5 秒再取数；必须不小于 `route.yaml` 的 `settle_delay_ms`（5000），生成采集计划时按实际生效的值校验 |
| `refetch_after_close_minutes` | 15 | 收市后 15 分钟把当天整天强制重取一遍，见下文；A 股、crypto 不配这一项 |

部署时在 `moox.toml` 的 `[scf_plan]` 里加一段 `space_id = "stockhk"`，写上 `equity = [<地域>]`（示例见 `moox.toml.example`）。命名空间默认 `moox-stockhk-plan`，代码包默认 `moox-collector-stockhk-plan`。2026-11-23 起线上的定时函数在香港（`ap-hongkong`）、补采在南京（`backfill_region = "ap-nanjing"`），不与 A 股共用南京的出口 IP。

`equity` 可以写多个地域，函数按顺序轮流分到各地域，函数名里带地域。没有 MooX 主机的地域用公网方式（`[scf_plan.regions.<地域>]` 写 `network = "public"`、`entry_host = "storage"`，见 `skills/moox/references/private-network.md`），这样东方财富的请求可以分散到更多出口 IP 上。加地域后，原地域里分给新地域的函数只停定时器、不删，要用 `collector function delete --name` 手工删。代码包的存储访问配置在 `configs/scf/stockhk/sources/market/binance.yaml`（只有函数写 Storage 用的应用身份这一项）。

**连接与域名**（`sources/eastmoneykline`，A 股、港股、美股的东方财富 K 线共用）：

- 东方财富从南京出口对**新建连接**成片断开（EOF）：2026-11-12 实测新建连接断开 40%～70%、复用连接 2%～4%；2026-11-17 上午、2026-11-23 上午都出现过港股整期取不到，A 股同一时刻东方财富也大量重试，只是有备源兜住。所以三处一起做：
  - 独立连接池，每个域名留 32 条空闲连接（不小于各市场 `rate_limit.max_concurrent`），一波并发结束后连接留给后面的请求和重试复用；Go 默认只留 2 条。
  - 港股 `rate_limit.max_concurrent` 取 4（A 股、美股仍是 16）：每个函数每期只新建 4 条连接；25 只 4 路并发 3～4 秒取完。
  - 没配 `kline.endpoint` 的绝对地址时，在 `push2his`、`33.push2his`、`72.push2his` 三个域名间轮换：当前域名**连续** 6 次网络错误（含超时，中间没有一次成功）才换下一个，之后的请求留在新域名上；收到响应（含状态码错误）清零，调用方取消不计。只有部分请求被断开时成功与失败交替、不换，已建好的连接继续复用（换域名就得在新域名上重新建连接，而被断开的正是新建连接）；整个域名不通时两只标的各试 3 次就换。三者是同一个接口，经 trafficmanager 调度到不同后端。
- 请求记进流水线的逐项跟踪：CLS 的 `market_fetch_item_slow` 带 `attempt_trace`（每次停在哪个阶段、新建还是复用连接、对端地址）、`endpoint`（最后用的域名），批次摘要的 `conn_new`、`conn_reused` 也包含东方财富。

**腾讯备源**（`sources/stockhk/tencent/kline.go`，路由里 `role: fallback`，source_id `stockhk_minute_http`）：

- 只在东方财富对这只标的试满 3 次都失败后使用；写入的行 `source_provider=tencent`、`route_rank=2`、`quality_status=fallback`。
- 腾讯没有港股分钟 K 线（A 股用的 `mkline` 对港股代码报 `param error`），只有当天实时分时 `ifzq.gtimg.cn/appstock/app/hkMinute/query?code=hk00700`：每分钟一行“时刻 价格 累计成交量 累计成交额”，时刻是这一分钟的结束时刻（0930 是开盘那一刻，13:00 那一行的累计值与 12:00 相同），一次只能请求一只，约 14KB。2026-11-23 15:53 请求时最后一行就是正在走的那一分钟，是实时的。
- 合成规则：一行属于“这一分钟开始时刻”所在的桶，开始时刻不在交易时段内（09:30、13:00 那一行）就属于结束时刻所在的桶，16:00 之后的行并进 15:55 那根。开盘价取这一根开始那一刻的价格（上一根最后一行；09:30 那根取开盘那一行），收盘价取最后一行，最高、最低取开盘价与各行价格的极值；成交量、成交额是累计值的增量。只返回已收盘、且分时已经走到收盘时刻的根。
- 与东方财富比对（2026-11-23，6 只、223 根）：收盘价 222 根一致；成交量、成交额偏大 3%～7%（各只中位数，最多 22%），推断是东方财富的 5m 不含碎股；开盘价 124 根一致、最高 92 根、最低 97 根，最高价中位数低 0.06%、最差低 0.68%（分钟内的极值取不到）。
- **没有成交的根不返回**，与东方财富一致：腾讯对没有成交的分钟照样按上一价格给一行，停牌的标的当天也给满 332 行、成交量全是 0（2026-11-23 实测 00204）。请求的区间在当天、分时已经走过区间终点、区间里却没有有成交的根时，报“没有已收盘的根”（与东方财富对没有成交的根的结论一致），补采据此记“行情源确认没有”；否则东方财富断连时这类根每轮失败，自动补采的水位停住（2026-11-23 00002 的 13:10 那根）。
- 只能取当天：回看按 24 小时声明。返回的是别的交易日时（长期停牌的标的返回最后交易日的分时，实测 00232 返回 10-12；开盘前补上一交易日时已经换成当天）报覆盖不到，不报“没有已收盘的根”。候选链上“取不了这个区间”的错误（覆盖不到、超出回看、没有这个源）不盖掉前面来源的错误，所以东方财富确认没有的根（停牌）补采照样记“行情源确认没有”，水位不会停住。
- **强制补采不用腾讯**：收市后整天重取和手工 `--force` 重写的是已经写好的行，请求带 `complete_only`，只用开高低收完整的来源（`KlineSpec.CompleteOHLCV`），腾讯分时声明为不完整、被去掉；东方财富失败时分块退回重试，保留原来的行。补缺口的自动补采、普通手工补采照常回落；A 股的备源都是完整的，强制补采照常回落。
- 限速沿用 A 股腾讯（每秒 5 次、并发 1）：东方财富整期失败时每个函数约 25 只，5 秒左右取完。
- 其他候选都不可用（2026-11-23 实测）：新浪港股分钟 K 线接口报 `Service not valid`；百度连发几次就触发验证码风控；雪球要登录；雅虎对腾讯云 IP 第一次请求就 429；通达信扩展行情没有测（免费港股行情通常延迟 15 分钟）。

**数据源的实测结论**（2026-11-12 交易时段，从南京的云函数取东方财富，10 只标的）：

- **请求方式与 A 股相同**：带起止日期时返回区间内的全部根，一次请求不限根数。
- **只能回看约 23 个交易日**（5m 共约 1500 根），再早的取不到；数据源按 28 个自然日声明回看能力。缺口超过这个范围就补不回来。
- **时间标签是收盘时刻**，首根 09:35、末根 16:00，上午最后一根 12:00、下午第一根 13:05；写入时换成开盘时刻做行键。
- **成交量单位是股**，不用换算；成交额单位港元。
- **5m 不含开盘竞价（09:00～09:20）和碎股的成交**，一天的 5m 成交量合计比日线少 4%～17%（按标的不同）。09:35 那根的开盘价等于竞价成交价。
- **普通边界收盘后最晚 0.5 秒定稿**；取样有空档时看到的上限是 5.8 秒，所以起跑等待和结算延迟都定为 5 秒。
- **新一根要等新时段里第一笔成交才出现**，冷门股可能一分多钟不出新一根；取数只按时间挑目标那根，不等下一根出现。
- **16:00 这根分三段**：16:00:00 起是连续交易时段的成交，值合法但不是最终值；中间一段（开始于 16:00:28～16:01:20 之间，结束于 16:07:53～16:09:28 之间）成交量不变而收盘价被换成收市竞价的参考价，经常超出这一根的最高价、最低价，这段时间取到的值不能用；最后收市竞价的成交并进这一根，成交量大增（例如 09988 从 284.8 万股到 1853.4 万股），这才是最终值。港交所的收市竞价在 16:10 前随机收市。
- **偶尔返回异常值**：实测看到 09988 的 15:55 那根两回返回过成交量 1.6 亿股的值，开高低收合法，校验拦不住。

**收市后整天重取。** 16:00:05 照常取一次，写入连续交易时段的值，因子和策略照常用这一期。自动补采只补缺的根，不会重取已有的根，所以 Collector 在每个空间的对账循环里另加一步（`klinecheck.Backfiller.RefetchAfterClose`）：

- 时刻是当天实际的收市时刻（`packages/barclock`，半日市是 12:00）加 `refetch_after_close_minutes`。和自动补采一样按 5 分钟分轮，这个时刻落在“上一轮起点之后、这一轮起点及之前”的那一轮提交，港股是 16:15（半日市 12:15）那一轮的第一次对账，约 16:15:10。
- 提交的是强制补采作业（`force`，来源记为 `manual`），范围是按市场时区的当天零点到次日零点（K 线开始时刻，左闭右开）。对空间里仍在采集、周期在 `route.yaml` 里有路由的数据集各提交一个。分块按标的、按上下午拆开，港股每只标的两块；东方财富按日期整天返回，一块一次请求。
- 重取同时覆盖 16:00 这根、上面说的异常值，以及自动补采在收市竞价期间写进去的参考价（16:00 这一期第一次取失败时，自动补采约 16:07:30 才扫到，正落在收市竞价期间）。
- 重取之后 Storage 和 View 按新值更新，因子引擎发现内容不同会替换并重算；补采发的是 `event.collector.kline.backfilled`，不发新的就绪事件，策略不订阅它，**已经发出的策略信号不会重算**。
- 不存状态：非交易日、没配这一项的市场什么都不做；Collector 在那 5 分钟里重启会再提交一次（重复重取一遍，结果相同），那 5 分钟整段没在运行就不重取，要手工 `moox-cli collector kline backfill --force` 补当天。

- 强制补采的分块遇到函数报失败（例如东方财富按整天返回、其中一根不合法，这只标的上午、下午两块都失败）会退回重试，一共执行 5 次都失败才记失败。重试没有固定间隔：失败的分块不自己接着重试，要等同一空间别的分块执行完，或下一次每分钟的对账才再被认领；作业里还有别的分块在跑时间隔只有一两秒，只剩它自己时最长约一分钟。手工 `kline backfill --force` 同样会这样重试；不带 `--force` 的补采和自动补采不变，失败一次就记失败（自动补采下一轮会重新发现缺口）。

**上线。** 已有数据的环境不会再导入种子，标签和任务用命令建。顺序和要点：

1. 确认各主机都是带港股的版本（`moox-cli setup status`），crypto、A 股的采集和告警正常。
2. 在 `moox.toml` 的 `[scf_plan]` 里加上 stockhk 一段（见上文，`setup start` 要检查它），再重新部署 Collector。Collector 的配置每次部署都从模板和 `moox.toml` 重新渲染，不要上机手工改；渲染出来多的是下面两段（`ap-nanjing` 的 `scf_regions` 和 `scf_plan.entry_routes` A 股已经有）：

   ```yaml
   scf_markets:
     # 已有的 crypto、stockcn 不动
     stockhk:
       equity:
         - ap-nanjing
   scf_plan:
     spaces:
       # 已有的 crypto、stockcn 不动
       stockhk:
         package_name: moox-collector-stockhk-plan
         namespace: moox-stockhk-plan
   ```

   `moox.toml` 那一段由用户用 `moox-cli config edit` 加（数组表，Agent 不代填），加在已有的 stockcn 那段之后：

   ```toml
   [[scf_plan.spaces]]
   space_id = "stockhk"
   [scf_plan.spaces.markets]
   equity = ["ap-nanjing"]
   ```

   然后 `moox-cli setup deploy --host <控制机> --component collector`，确认 crypto、A 股照常采集。
3. 构建并上传港股代码包，**要在 `setup start` 之前**：`setup start` 会生成采集计划并创建函数，那时找不到代码包会失败。`--space-id`、`--cloud-account-id` 必填；`--package-name` 的默认值是 `moox-collector`，必须显式写成这个空间的包名；`--version` 不写是 `dev`；在仓库根目录执行时不用写 `--collector-root`。云账号 ID 是 `moox.toml` 里 `[scf_plan.cloud_account]` 的 `account_id`。

   ```bash
   ./bin/moox-cli collector function upload --space-id stockhk --package-name moox-collector-stockhk-plan --cloud-account-id <云账号 ID> --version <版本>
   ```

4. 建标签。`metadata tag upsert` 的参数里没有属性，用 `--data` 给完整请求；请求带 `"seed":true` 和 `"builtin":true`，按种子标签建成内置标签，Monitor 才会巡检它。标签一建好，Collector 下一次检查（每分钟第 30 秒）就会同步，立即请求腾讯的成分接口，不等 08:40：

   ```bash
   ./bin/moox-cli metadata tag upsert --space-id stockhk --tag-id hk_hsi --data '{"seed":true,"tag":{"space_id":"stockhk","tag_id":"hk_hsi","tag_name":"恒生指数","description":"恒生指数成分股，每天开盘前按腾讯的指数成分接口同步","mode":"auto","builtin":true,"attributes":{"market_type":"equity","sync.source":"eastmoney","sync.index_source":"tencent","sync.index":"HSI","sync.cron":"40 8 * * *","sync.timezone":"Asia/Hong_Kong"}}}'
   ```

5. 建任务。**必须带 `--all-output-fields`**：`--output-field` 的默认值是现货、永续行的 7 个字段，不带这个开关建出来的数据集没有 `amount`、`trade_date` 等股票行的字段；命令会打一句提示，但任务照样建出来。

   ```bash
   ./bin/moox-cli collector task create --space-id stockhk --name "港股 K 线 5m" --tag-id hk_hsi --frequency 5m --all-output-fields --disabled
   ```

   带上它时请求里不含 `output_fields`，与种子里不写 `output_fields` 的任务（A 股 5m、港股 5m）相同：两条路径都把解析出的空输出字段交给同一个 `taskresult.Manager.Ensure`（种子在 `bootstrap/bootstrap.go`，命令在 `rpc/service.go` 的 `CreateTask`），空表示数据集带全部基础列、View 不单独建列。只有任务 ID 不同：命令建的是新生成的 ID，结果数据集是 `dataset_<任务 ID>`，以后港股因子任务的源数据集 ID 要用实际值。
6. 开盘前执行 `./bin/moox-cli setup start --space-id stockhk`（`--space-id` 必填；`[scf_plan]` 里没有这个空间时直接报 `start_prerequisite_missing`）：同步标签、启用任务、生成采集计划。确认成员数等于腾讯接口报的总数，4 个函数建好。
7. 开盘后在 Monitor 看港股的 K 线新鲜度检查（`kline_freshness:stockhk:<View ID>:5m`）通过。Monitor 没有按数据源的健康检查，不用等它。
8. 第一个交易日 16:15 之后看补采作业列表（`./bin/moox-cli collector kline backfill-status --space-id stockhk --source manual`，看某个作业的分块再加 `--job-id <作业 ID>`）：应有一个来源 `manual`、类型 `force` 的作业，190 个分块（95 只 × 上午、下午）全部成功；再抽查几只标的 16:00 收盘那根（行键 15:55）的成交量，应明显大于 16:00:05 写入时的值，说明已含收市竞价的成交。
9. 因子、策略与模拟盘（Strategy 支持港股日内周期、Trade 有港股模拟盘之后）：再执行一次 `./bin/moox-cli setup start --space-id stockhk`——它会导入种子里的港股因子任务 `ftask_hk_5m`（只有 `ma__5`、`ma__10`；线上已有同 ID 且内容相同算已存在），并创建观察实例 `default_dual_ma_hk_5m`（[`examples/strategies/dual_ma_hk_5m.yaml`](../../examples/strategies/dual_ma_hk_5m.yaml)，不挂账户）。只要因子任务、不要默认策略时用 `./bin/moox-cli factor task apply --file config/setup/factor-tasks.yaml`。
   新建的因子任务的结果数据集 `dataset_factor_hk_5m` 没有归档任务，装了数据归档时 Monitor 会报“未归档的数据集”：命令结束时会给出 `moox-cli archive tasks create --space-id stockhk --dataset-id dataset_factor_hk_5m`，要归档就执行它。
   港股模拟账户在管理台“交易 › 交易账户 › 新建账户”里建：模拟盘、场所“港股”、市场“股票”、按港元结算；规则、费用和已知差别见 [交易](交易.md) 的“港股模拟盘”一节。要让默认策略下单，再建一个挂这个组合账户的实例。

**已知差别：**

- **备源是近似值**：东方财富失败时由腾讯分时合成的 5m 顶上，收盘价可靠；成交量、成交额偏大 3%～7%，开盘、最高、最低是近似值，同一条序列里两个源的行混在一起（看 `source_provider` 区分）。用到最高、最低、成交量的因子会受影响。腾讯只能取当天，更早的缺口仍只靠东方财富，只能回看约 23 个交易日。
- **备源的定稿时刻与收市竞价没有实测**：分钟结束后多久那一行才不再变、16:00 之后收市竞价怎么出，都还没在盘中测过；16:00 这根由收市后整天重取（先试东方财富）改正。
- **重试不拉开间隔**：每只标的 3 次尝试一个接一个发出，几百毫秒内用完，窗口还剩约 50 秒；断连常是间歇的（11-23 10:00 起每期 20%～40%），拉开间隔有机会多补回一些，但要改流水线的公共重试，没有做。
- **数据源连续断开时自动补采每 5 分钟原样重发**：补采函数访问东方财富 `push2his` 被断开连接（EOF）时，这一轮自动补采作业记失败、扫描水位不推进，下一轮（5 分钟后）对同一批缺口再建一个作业、再发一遍同样的分块；
  没有失败计数，也不退避。2026-11-17 上午 09:48～11:19 连续 19 个自动作业、628 个分块失败，11:28 数据源恢复后一次补齐。期间不用处理；不想让它继续请求时停用这个空间的采集任务。
  补采没有现成的失败计数或退避可以接，这里没有为它加状态。
- **16:00 这根先写后改**、**5m 不含开盘竞价和碎股的成交**、**偶尔返回异常值**：见上面“数据源的实测结论”和“收市后整天重取”。
- **只支持 5m**：1m、1d 的采集任务能建成功，但运行时会失败（港股数据源只声明了 5m）。

## 4d. 美股 5m K 线

stockus 和港股一样走 SCF 定时直采（采集方式 `scf`），只有 5m 一个周期、东方财富一个数据源，没有备源。内置两个标签：标普 500（`us_spx`，成分来自开源数据集 datahub）和纳斯达克 100（`us_ndx`，成分来自纳斯达克官网接口）；内置任务“美股 K 线 5m”绑 `us_spx`，默认停用，要采纳斯达克 100 就建任务时写 `--tag-id us_ndx`。任务不写输出字段，与 A 股 5m 一样输出股票行的全部字段。标的 ID 是代码加交易所的 MIC，例如 `AAPL.XNAS`、`JPM.XNYS`、`SPY.XASE`，带类别的代码保留点（`BRK.B.XNYS`）。交易时段 09:30～16:00（纽约时间），每个交易日 78 根，半日市（13:00 收市）42 根，不采盘前盘后；时钟与日历（`us_stock`）登记在 `packages/barclock`、`packages/marketcalendar`。美股的因子、策略、Trade、管理台不在这一套里。

**市场参数**（`modules/collector/config/markets/stockus/market.yaml`，同样编在二进制里）：

| 项 | 取值 | 说明 |
| --- | --- | --- |
| `currency` | `USD` | 成交额单位美元 |
| `allowed_lateness_seconds` | 90 | 与 A 股、港股相同 |
| `egress_probe` | `public_ip` | 云函数出口探测只取出口公网 IP（三个股票市场共用南京出口） |
| `scf_plan.symbols_per_function` | 50 | 固定每函数 50 只，标普 500 共 11 个函数、纳斯达克 100 共 3 个；不估算函数个数，不做出口 IP 去重。美股只有一个数据源，每只每期一个请求，函数内并发 16 下 1 秒内取完 |
| `scf_plan.fetch.not_before_ms` | 5000 | 收盘后等 5 秒再取数；必须不小于 `route.yaml` 的 `settle_delay_ms`（5000），生成采集计划时按实际生效的值校验 |
| `refetch_after_close_minutes` | 20 | 收市后 20 分钟把当天整天强制重取一遍，见下文。2026-11-13 冬令时实测：纽约 16:00 那一根的收盘竞价在 16:16:19～16:16:54 之间并入，所以取 16:20；并入后这根的量仍会缓慢增长（见“已知差别”） |

部署时在 `moox.toml` 的 `[scf_plan]` 里加一段 `space_id = "stockus"`、`equity = ["ap-nanjing"]`（示例见 `moox.toml.example`）。命名空间默认 `moox-stockus-plan`，代码包默认 `moox-collector-stockus-plan`；函数与 A 股、港股同在南京，共用一个出口 IP 池。代码包的存储访问配置在 `configs/scf/stockus/sources/market/binance.yaml`（只有函数写 Storage 用的应用身份这一项）。CLI 按空间 ID 选 `configs/scf/<空间>/`，不需要为美股另加分支。

**数据源的实测结论**（2026-11-12 纽约 09:39～10:20，从南京的临时云函数取东方财富，原始返回在 `docs/计划/美股实测数据/`）：

- **请求写法**：`secid` 前缀 105 是纳斯达克、106 是纽交所、107 是其他（含 ETF 和 Cboe 上市的证券）；代码里的点要换成下划线（`106.BRK_B`、`106.BF_B`），写成点返回空。标的 ID 里的 MIC 对应：`XNAS`→105、`XNYS`→106、`XASE`→107。
- **时间标签是收盘时刻，北京时间**：冬令时首根 22:35、末根次日 05:00，夏令时首根 21:35、末根次日 04:00；写入时换成开盘时刻做行键。返回里包含进行中的那一根，实时请求只取目标那一根。
- **日期区间的规则和 A 股、港股不同**（共用代码按各市场提供的“日期区间”函数拼 `beg`、`end`，美股的实现在 `sources/stockus/eastmoney/daterange.go`）：东方财富对美股的 `beg`、`end` 不按 UTC 日期、也不按纽约交易日过滤，而是返回**收盘标签（北京时间）不早于 `beg` 日 22:30**、且不晚于 `end` 日某个时刻（在 05:00 之后、21:35 之前）的根；`beg` 与 `end` 同一天一定是空的。要取收盘标签在 `[L1, L2]` 的根：`beg` 取 L1 减 22:30 之后的日期（冬令时首根 22:35 落在当天，夏令时首根 21:35 落在前一天），`end` 取 L2 的日期加一天；`end` 一侧最多多带回一天的根，由流水线按请求区间裁掉。实时请求、补采、收市后整天重取都走这一个函数。区间内一根都没有时（标的全天停牌、已退市）美股数据源返回“没有已收盘的 K 线”，补采把它当成行情源确认没有，不会卡住。
- **实时性**：22:50、22:55 两个边界、10 只标的，边界后 0.5～1.4 秒看到新一根、目标那根定稿，之后不再变。样本只有这两个边界，所以起跑等待和结算延迟留余量定为 5 秒；实时批次的截止是收盘后 90 秒，多等没有代价。
- **收盘那一根的实测**（2026-11-13 北京时间 04:52～06:00，冬令时，纽约 16:00 = 北京 05:00；10 只标的约每 0.7 秒轮询，05:30、05:45、06:00 各取一次快照）：04:55 那一根在 04:59:09 开始轮询时已是定稿值，到 06:00 不再变。05:00（纽约 16:00）那一根在 16:00:09 前后只有连续交易时段的成交，**收盘竞价的成交在纽约 16:16:19～16:16:54 之间一次并进来**（10 只同一窗口，成交量变成原来的 1.6～7.6 倍，AAPL 1,294,294→6,987,067、NVDA 11,283,145→35,544,212），并入前的三次取样（北京 05:00:09、05:14:36、05:16:19）值相同；并入后量仍缓慢增长到 06:00，没有真正定稿的时刻（推断是盘后成交被加进来，未证实）；收盘价在并入时小幅变化（AAPL 354.920→354.880），10 只在整个观察期内没有一根收盘价超出最高、最低价。所以 16:00:05 首次写入的量被低估，整天重取要在 16:17 之后，定为 16:20。半日市（13:00 收市）并入时刻没有实测。
- **回看按交易日滚动**：全量 1412 根 = 18 个交易日 × 78 + 当天 8 根；数据源按 21 个自然日声明回看能力。缺口超过这个范围就补不回来。
- **单位**：成交量单位是股，成交额是美元。5m 含开盘、收盘竞价的成交（与港股不同）：AAPL 纽约 11-11 的 78 根成交量合计 3446.15 万股，日线 3445.35 万股，多 0.023%（只核对了这一只一天）。
- **没有一根开盘价超出最高、最低价**，不会被校验拒掉；但盘中多数根的开盘价等于上一根的收盘价（见“已知差别”）。
- **东方财富美股列表 `clist`**：每页最多 100 行，105 有 6061 只、106 有 2967 只、107 有 4880 只，其中大量是 ETF 和杂项代码，所以不当作标的来源，只用来给标普 500 的成分对交易所。从南京云函数每次新建连接时约 40% 的请求被断开，所以成分同步放在控制机的 Collector 里直连。

**成分来源**（只取成分，不取 K 线，也不是采集数据源，不用在空间里登记）：

| 标签 | 来源 | 内容与校验 |
| --- | --- | --- |
| `us_ndx` 纳斯达克 100 | `api.nasdaq.com/api/quote/list-type/nasdaq100`（纳斯达克官网网页自己用的接口） | 101 行（谷歌 A、C 各一行），行数必须等于自报的 `totalrecords` 且在 95～110 之间、无重复；交易所一律写 `XNAS`（按编制规则全部是纳斯达克上市，实测都在东方财富 105），不翻东方财富列表 |
| `us_spx` 标普 500 | `datasets/s-and-p-500-companies` 的 `constituents.csv`，经 jsdelivr 读取 | 503 行，与道富 SPY 持仓的代码集合一致；CSV 不报总数，校验行数在 495～515 之间、无重复、代码合法；交易所由东方财富美股列表对上（把代码里的点换成下划线到 105、106、107 里按顺序查，同一代码在两个市场时取靠前的），每只成分都必须对上，有一只对不上就整次同步失败、标签保留旧成员，日志列出全部对不上的代码 |

控制机连不上 `raw.githubusercontent.com`，所以走 jsdelivr；jsdelivr 对分支引用最多缓存 12 小时，数据集又每天 UTC 00:00 才从维基百科更新一次，调样后可能晚一两天生效。

两个标签写法相同，只有成分来源和指数代码不同：`market_type: equity`、`sync.source: eastmoney`、`sync.index_source: datahub`（纳斯达克 100 是 `nasdaq`）、`sync.index: SPX`（`NDX`）、`sync.cron: "0 8 * * 1-5"`、`sync.timezone: America/New_York`。**`sync.cron` 和 `sync.timezone` 必须写**：不写时是每小时一次（UTC），标普 500 每次要翻东方财富列表约 140 页（限流后每页至少 0.5 秒，至少约 70 秒；请求耗时 0.5 秒时约 70 秒，0.8 秒时约 112 秒），每小时翻一遍既浪费又容易被限流。

**标签同步的超时。** 标普 500 一次成分同步要翻约 140 页，同一次同步的三次重试共用一个 `fetch_timeout`（`config/app.yaml` 的 `subject_sync.fetch_timeout`，代码兜底默认 2 分钟、全新安装的模板里是 150 秒，`TagRunner` 取这一个值，所有标签、所有市场共用，不能按空间配）。一遍限流后至少约 70 秒（请求耗时 0.5 秒时约 70 秒，0.8 秒时约 112 秒），代码兜底的 2 分钟留给失败后重试的余量不大，所以模板取 150 秒；配置每次部署都从模板渲染，不需要手工改。手工同步（`setup start`、`collector subjects sync`）经网关调 `SyncSubjects`，服务端 170 秒后以失败结果返回，所以这个值要留出余量：取 170 秒时重试用满、取到快照也来不及写进 Storage（`ApplyTagSnapshot` 拿到的是已到期的 ctx）。定时同步不受网关限制；同一个值也用在属性维护任务上，改大只是放宽上限，不影响 A 股、港股、crypto 的同步耗时。

**收市后整天重取。** 沿用港股的机制（第 4c 节，`klinecheck.Backfiller.RefetchAfterClose`），美股的差别只有范围：

- 时刻是当天实际的收市时刻加 `refetch_after_close_minutes`（半日市按 13:00 算，所以是 13:20 那一轮，北京时间冬令时 02:20），和港股一样按 5 分钟分轮，约纽约 16:20:10（北京时间冬令时 05:20、夏令时 04:20）。
- 范围是**纽约当天 00:00～次日 00:00 换算成 UTC**（冬令时 05:00Z～次日 05:00Z，夏令时 04:00Z～次日 04:00Z），K 线开始时刻，左闭右开。美股没有午休，每只标的整天 1 个分块，标普 500 约 503 块、纳斯达克 100 约 101 块；一个分块一次请求，按上面的日期区间规则提前一天或多带前后一天的根，多带的由流水线裁掉。冬令时、夏令时、半日市（13:00 收市，42 根）各一天的整天重取都能取全 78 根（42 根），有端到端测试（`marketwiring/stockus_refetch_e2e_test.go`，上游按日期区间规则的模型返回，`end` 日的切点取两个极端各跑一遍）。
- 当天全天停牌的标的：区间内一根都没有，函数报“没有已收盘的 K 线”，强制作业的这个分块先退回复查一次，连续两次缺的一样就记成行情源没有、分块成功结束，不会卡住同一作业里别的标的。
- 其余（不存状态、来源记为 `manual`、强制分块失败最多执行 5 次）与港股相同。

**上线。** 已有数据的环境不会再导入种子，标签和任务用命令建。顺序和要点：

0. 发布前只读核对：管理台里 stockus 空间是启用状态；`metadata source list --space-id stockus` 里有 `eastmoney`；线上没有 stockus 的采集任务；线上 Monitor 配置里没有 `kline_freshness.space_ids`（有的话 K 线新鲜度检查只查列出的空间，不覆盖 stockus）。

   **限流门槛**：控制机出口 IP 曾因 2026-11-13 凌晨一次没有页数上限的实测脚本被东方财富限流（push2、push2his 被断开，push2test 备用域名可用）。启用前先看 `./bin/moox-cli collector subjects status --space-id stockcn` 最近一轮是否成功（A 股的标的同步走同一套 `FetchClist` 主备回退，能反映出口现在的状态）。`us_spx` 同步要翻约 140 页，限流不恢复时每个交易日失败一次、成员为空；这时**先只上 `us_ndx`**（只调纳斯达克接口、不翻东方财富列表，不受影响）：第 4 步只建 `us_ndx` 标签，第 5 步的任务写 `--tag-id us_ndx`。任务的标签建好后改不了（`collector task update` 只改名称、说明、启用），所以建任务时就要选定；以后限流恢复要加标普 500，是建好 `us_spx` 标签、确认同步成功后再新建一个绑 `us_spx` 的任务。
1. 确认各主机都是带美股的版本（`moox-cli setup status`），crypto、A 股、港股的采集和告警正常。要重新部署时避开美股交易时段（北京时间 21:30／22:30～次日 05:00）和 08:00～08:10 的 A 股日线与标的同步；`collector-stream` 没有变化时不会被重启（重启会让 crypto 的 WS 重连，美股不走 WS）。
2. 在 `moox.toml` 的 `[scf_plan]` 里加上 stockus 一段（`setup start` 要检查它），再重新部署 Collector（配置由部署渲染，不要上机手工改，见 4c 上线第 2 步）。渲染出来多的是下面两段；`subject_sync.fetch_timeout` 模板默认就是 `150s`（见上文）：

   ```yaml
   scf_markets:
     # 已有的 crypto、stockcn、stockhk 不动
     stockus:
       equity:
         - ap-nanjing
   scf_plan:
     spaces:
       # 已有的 crypto、stockcn、stockhk 不动
       stockus:
         package_name: moox-collector-stockus-plan
         namespace: moox-stockus-plan
   ```

   `moox.toml` 那一段由用户用 `moox-cli config edit` 加（数组表，Agent 不代填），加在已有的 stockhk 那段之后：

   ```toml
   [[scf_plan.spaces]]
   space_id = "stockus"
   [scf_plan.spaces.markets]
   equity = ["ap-nanjing"]
   ```

   然后 `moox-cli setup deploy --host <控制机> --component collector`，确认 crypto、A 股、港股照常采集。
3. 构建并上传美股代码包，**要在 `setup start` 之前**。**只传 stockus 的新包，不要重传 stockcn、stockhk 的代码包**：上传后 Collector 约 2 分钟内会自动升级所有落后的函数，会带上线上包版本之后 main 上所有函数端的改动，而 A 股、港股的行为已证明不变，没有必要。年度更新交易日历时才需要三个包都重传（见 `skills/moox/references/fresh-deploy.md`）：

   ```bash
   ./bin/moox-cli collector function upload --space-id stockus --package-name moox-collector-stockus-plan --cloud-account-id <云账号 ID> --version <版本>
   ```

4. 建标签。`metadata tag upsert` 的参数里没有属性，用 `--data` 给完整请求。标签一建好，Collector 下一次检查（每分钟第 30 秒）就会同步，立即请求成分来源，不等纽约 08:00；标普 500 要翻约 140 页，同步要几十秒到两分钟：

   ```bash
   ./bin/moox-cli metadata tag upsert --space-id stockus --tag-id us_spx --data '{"tag":{"space_id":"stockus","tag_id":"us_spx","tag_name":"标普500","description":"标普 500 成分股，每个交易日开盘前按 datahub 的开源成分名单同步","mode":"auto","attributes":{"market_type":"equity","sync.source":"eastmoney","sync.index_source":"datahub","sync.index":"SPX","sync.cron":"0 8 * * 1-5","sync.timezone":"America/New_York"}}}'
   ./bin/moox-cli metadata tag upsert --space-id stockus --tag-id us_ndx --data '{"tag":{"space_id":"stockus","tag_id":"us_ndx","tag_name":"纳斯达克100","description":"纳斯达克 100 成分股，每个交易日开盘前按纳斯达克官网的成分接口同步","mode":"auto","attributes":{"market_type":"equity","sync.source":"eastmoney","sync.index_source":"nasdaq","sync.index":"NDX","sync.cron":"0 8 * * 1-5","sync.timezone":"America/New_York"}}}'
   ```

   用命令建出来的标签内置标记是否保留，以种子/命令的实际行为为准，参见 #200。

   **建完标签后不要马上手工同步，也不要直接 `setup start`**：标签只要被改过就算到期，建好后一分钟内定时器就会同步一遍（两个标签依次跑，期间持有同步锁）；再手工同步就是第二遍翻约 140 页，出口被限流时等于风险加倍。做法是建完等 5 分钟（两个标签依次同步，各自最多用满 150 秒），等两个标签都出现在 `subjects status` 里再判断；建标签的时刻避开每小时第 23 分（A 股全部标的的同步）：

   ```bash
   ./bin/moox-cli collector subjects status --space-id stockus
   ./bin/moox-cli metadata tag show --space-id stockus --tag-id us_spx
   ./bin/moox-cli metadata tag show --space-id stockus --tag-id us_ndx
   ```

   `subjects status` 只读 Collector 的库，不发请求，也不返回成员数，没有运行记录的标签不会列出（所以要等两个标签都出现）；看每个标签最近一次的 `last_status`（`success` 或 `failed`）和 `last_error`。成员数用 `metadata tag show` 的 `active_count` 看：`us_spx` 要等于 CSV 的行数（约 503），`us_ndx` 等于纳斯达克接口的 `totalrecords`（101），再抽查几只的交易所。

   **只有 `last_status` 是 `failed` 时才手工同步**：`last_error` 是网络错误（连接被断开、超时）或被限流（429）时，等出口恢复再说，不要马上重来；其余原因（例如有成分对不上交易所）按错误里的提示处理后再逐个同步，不带 `--tag-id` 会把两个标签放进同一份预算，所以分开跑：

   ```bash
   ./bin/moox-cli collector subjects sync --space-id stockus --tag-id us_spx
   ./bin/moox-cli collector subjects sync --space-id stockus --tag-id us_ndx
   ```
5. 建任务（标签在这一步选定，建好后改不了，见第 0 步的限流门槛）。**必须带 `--all-output-fields`**（原因同 4c 上线第 5 步）。只上纳指 100 时把 `--tag-id` 换成 `us_ndx`、任务名改成“美股 K 线 5m（纳指 100）”；以后要加标普 500 的任务时两个任务会重叠采集 100 多只标的，是否删掉纳指 100 的任务到时再定。不想采某个标签的话就不建它的任务，标签本身只有成员、没有采集：

   ```bash
   ./bin/moox-cli collector task create --space-id stockus --name "美股 K 线 5m" --tag-id us_spx --frequency 5m --all-output-fields --disabled
   ```

   结果数据集是 `dataset_<任务 ID>`，以后美股因子任务的源数据集 ID 要用实际值。
6. 第 4 步确认任务绑定的标签同步成功之后，开盘前执行 `./bin/moox-cli setup start --space-id stockus`：启用任务、生成采集计划，确认函数建好（标普 500 是 11 个函数，只上纳指 100 是 3 个）。
7. 开盘后在 Monitor 看美股的 K 线新鲜度检查（`kline_freshness:stockus:<View ID>:5m`）通过：`./bin/moox-cli monitor health --space-id stockus`。
8. 第一个交易日收盘 20 分钟之后看补采作业列表（`./bin/moox-cli collector kline backfill-status --space-id stockus --source manual`，看某个作业的分块再加 `--job-id <作业 ID>`）：应有一个来源 `manual`、类型 `force` 的作业，每只标的 1 个分块（标普 500 约 503 块，只上纳指 100 约 101 块），**正常应全部成功，个别延迟开盘的标的是例外**（见已知差别），用 `backfill-status` 加 `--job-id` 看失败分块是哪几只；抽查几只标的收盘那根（行键纽约 15:55）的成交量与收盘价，对比 16:00:05 写入时的值；重取后的值应与纽约 16:20 之后的快照一致（20 分钟已按实测定下，见第 4d 节“数据源的实测结论”，不用再确认够不够；之后几个小时这根的量还会略涨，见已知差别）。

**撤掉美股。** 先停用并删除 stockus 的任务（`collector task delete --space-id stockus --task-id <任务 ID> --yes`）：空间没有启用的任务、也没有计划之后，Collector 会把它的函数定时器停用并读回确认。再用 `moox-cli collector function delete --space-id stockus --prefix <函数名前缀>` 删掉云上的函数（先不带 `--yes` 预览），最后从 `moox.toml` 的 `[scf_plan]` 删掉 stockus 一段并重新部署 Collector。顺序不能反：空间配置去掉之后，它在云上的函数不在 Collector 的识别范围内，只能到腾讯云控制台处理。

**已知差别：**

- **没有备源**：东方财富失败时这一期缺数，等自动补采；回看约 18 个交易日，超过就补不回来。
- **盘中开盘价**：东方财富盘中多数根的开盘价等于上一根的收盘价，不是本根第一笔成交价（实测轮询的 10 只标的、两个边界全部如此；AAPL 全量 1393 根里有 243 根不等，只差几厘）；当天第一根是真实开盘价。用到开盘价的因子（如跳空）会有偏差，已接受。
- **107 对应 `XASE` 不准确**：东方财富的 107 是纽交所、纳斯达克以外的交易所合在一起，含 Cboe 上市的 CBOE 和各种 ETF，标的 ID 一律写成 `XASE`。
- **标的换交易所会换标的 ID**：标普 500 的交易所对照每次同步重算，某只从纽交所转到纳斯达克后会以新 ID 出现，旧 ID 的数据不接上。
- **一只成分对不上交易所，整次同步失败**：新上市的成分在东方财富列表里出现之前，`us_spx` 保持旧成员；同步失败时同一次同步会整遍重跑 3 次（每遍翻约 140 页），请求量与失败原因无关。
- **成分名单是第三方来源**：标普 500 来自开源数据集，经 jsdelivr 再滞后最多 12 小时；纳斯达克接口是网页用的接口，格式变了同步会失败并保留旧名单。成分里的名称不会刷新（标的由标签同步创建，没有全市场标的同步）。
- **日期区间规则是实测推出来的**：东方财富没有文档，规则变了美股会取到 0 根或缺开头几根，由 Monitor 的 K 线新鲜度告警发现。
- **“区间内无根报没有已收盘的 K 线”写在美股数据源里**：这段判断在 `sources/stockus/eastmoney`，没有下沉到共用代码；下一个市场要用日期区间（`DateRange`）时要照抄这段判断，否则全天停牌的标的会让补采和整天重取记失败。
- **东方财富个别服务器 4～5 秒才给出新一根**：设计文档 1.4 记过，离收盘后 5 秒的等待很近；实测的两个边界都在 1.4 秒内，样本少。偶尔取到的还是旧的一根时，由自动补采和收市后整天重取兜底。
- **16:00 这根先写后改**：16:00:05 写入的是连续交易时段的值，收盘竞价的成交约在纽约 16:16～16:17 才并进来（2026-11-13 实测，见第 4d 节“数据源的实测结论”），成交量被低估 1.6～7.6 倍、收盘价也有小幅变化；16:20 的整天重取之后才含收盘竞价。因子会重算，中间已经发出的策略信号不重算。实测没有出现收盘价超出最高、最低价。
- **16:00 这根的成交量收市后还会缓慢增长**：并入收盘竞价之后量仍在涨，实测 06:00（纽约 17:00）比刚并入时多 0.3%～81%（视标的，SPY 多 81%、NVDA 多 11%、多数 1%～7%，NWSA 只多 0.3%），没有真正定稿的时刻；推断是盘后成交被加进这根最后的 K 线，没有证实。收市后重取只能取到 16:20 当时的值，之后几个小时这根的量还可能再涨，用这根量的下游（因子、策略）要知道这一点。
- **半日市未实测**：2026-11-27 的 13:00 收市（42 根、末根标签北京时间 11-28 02:00）还没有真实返回，现在的测试用构造的 42 根；收盘竞价并入 13:00 这根的时刻也没有实测，按同样的 16 分钟推断是 13:16，重取在 13:20。
- **5m 成交量合计略大于日线**：只核对了 AAPL 一只一天，多 0.023%（5m 含收盘、开盘竞价的成交）；成交额合计反而少 0.10%。
- **标普 500 同步的耗时**：约 140 页，限流后至少约 70 秒，和 A 股每天 08:10 的全部标的同步共用控制机出口 IP（A 股同步在北京时间，美股同步在纽约 08:00，时刻不重叠）；`fetch_timeout` 要按上文改成 150 秒。
- **建完标签后紧接着 `setup start` 可能报“没有有效标的”**：`setup start` 只对任务绑定的标签（种子任务和上线步骤里的任务只绑 `us_spx`，`us_ndx` 不会被它同步）逐个单独调一次 `SyncSubjects`，各有自己的预算，而且只在启用任务报“没有有效标的”时才同步。问题在于标签一建好，定时器一分钟内就开始同步并持有同步锁，两个标签依次跑完才释放；这期间 `setup start` 只拿到“正忙”，最多等 60 秒，标普 500 要几十秒到两分钟，所以紧接着的 `setup start` 可能失败。因此上线步骤要求建完标签后等 3 分钟，用 `collector subjects status` 确认这一轮成功再 `setup start`；失败才手工同步。两个标签共用同一份 170 秒预算的是不带 `--tag-id` 的 `collector subjects sync --space-id stockus`，所以要分开跑。
- **延迟开盘的标的，整天重取可能整个作业记失败**：当天 09:30 那一根缺失的标的（延迟开盘），整天重取在冬令时、半日市因回看覆盖核对（`ValidateCoverage`）失败，这只标的的分块重试 5 次都失败，整个作业记 failed；夏令时 `beg` 提前一天，前一天是交易日时覆盖核对能过，缺的那一根记成行情源没有，作业成功，但周一和节后（`beg` 落在非交易日）同样会失败。别的标的不受影响，已经写入的照常。看到失败分块时先用 `backfill-status --job-id` 确认是不是这类标的。
- **控制机到东方财富的出口 IP 曾被限流**：2026-11-13 凌晨一次没有页数上限的实测脚本翻列表所致；备用域名 `push2test` 可用。翻全量美股列表必须走限流器与页数上限（`FetchClist` 已接好限流器，`exchangelist` 的 `MaxPages`），不要另写无节制的翻页。启用前的检查和只上 `us_ndx` 的做法见上线第 0 步“限流门槛”。交易所对照的主备地址选择会带到后面的市场：第一个市场换到 push2test 之后，后两个市场直接用它，起点是 push2test 时中途不再回退 push2。
- **美股只支持 5m**：1m、1d 的采集任务能建成功，但运行时会失败（美股数据源只声明了 5m）。
- **整天重取的作业与手工作业混在一起**、**不存状态**、**交易日历过期后每分钟报一次警告**：与港股相同（第 4c 节和“已知限制”）。

## 5. 出口代理

SCF 函数用系统解析直接连接行情域名。

常驻采集的 HTTP 客户端对 `egress_proxy.domains` 中的域名调用出口代理 `Do`，使用 `collector` 身份和目录。代理保留目标状态码，过滤认证/Cookie 头并返回正文（传输压缩由 tRPC 帧层统一完成；该客户端整体超时 60 秒，仅用于控制面标的同步）；请求失败不会回退本机直连。其他域名继续本机连接，短生命周期 SCF 使用自己的直接行情出口。

## 6. 标的与标签同步

Storage 的标签只是一组标的，标的同步的业务配置写在标签属性里，由 Collector 解释：`market_type`（市场类型）、`sync.source`（该标签采集用的行情源，也是标的同步的数据来源）、`sync.index`（指数代码，可选）、`sync.index_source`（指数成分的来源，可选，不写时等于 `sync.source`）、`sync.cron`、`sync.timezone`（同步周期与时区）。
种子（`config/setup/metadata.yaml`）里标签只定义一处。是否支持某个（来源，市场类型）由 Collector 的行情源目录里的标的 lister 决定，Storage 不登记也不校验这类能力。标的同步复用进程级网关客户端与出口代理 HTTP 客户端：

定时同步只处理 `sync.cron` 到期的标签（没有运行记录、标签在上次运行后被改过也算到期）。首次部署、交易所接口恢复或标签配置变更后，可用 `moox-cli collector subjects sync` 立即同步：它调用 `CollectMgr.SyncSubjects`，无视 cron 窗口，只处理 `mode=auto` 且配置了 `sync.source`、`market_type` 的标签，返回每个标签的状态、标的数和失败原因。手动同步与定时任务共用一把互斥锁，同步正在运行时返回冲突；调用预算 180 秒，服务端 170 秒后以失败结果返回。网关只向 `moox-cli` 开放这个方法。

- **指数成分标签**：标签配置了 `sync.index`（指数代码）时，同步该指数的成分股，而不是数据源的全部标的。登记了四个：东方财富的沪深 300
  （stockcn，`000300`，成分板块 `BK0500`）、腾讯的恒生指数（stockhk，`HSI`）、纳斯达克官网的纳斯达克 100（stockus，`NDX`）和
  datahub 的标普 500（stockus，`SPX`，写法与耗时见第 4d 节）。内置自动标签 `cn_hs300` 每天北京时间 08:40 同步，`us_spx`、`us_ndx` 每个交易日纽约时间 08:00 同步。
  取到的条数必须等于接口给出的总数，翻页不完整就报错、不应用快照，保留上一次的成员。成分 lister 按（市场，来源，指数）单独登记
  （`subjectsync.IndexListers`），不出现在 `ListSubjectListers` 的来源选项里。
  - **成分来源与行情源不是同一家时**写 `sync.index_source`：`sync.source` 始终表示采集用的行情源（建任务时匹配任务能力表、
    结果数据集的数据源、采集计划的 Provider 都取它），成分名单按 `sync.index_source` 查，不写时等于 `sync.source`（`cn_hs300` 不写）。
    没有 `sync.index` 的标签写了 `sync.index_source` 不起作用。
  - **港股恒指标签的写法**：`market_type: equity`、`sync.source: eastmoney`、`sync.index_source: tencent`、`sync.index: HSI`、
    `sync.cron: "40 8 * * *"`、`sync.timezone: Asia/Hong_Kong`。港股没有全市场标的同步，成分快照里还不存在的标的由 Storage 在应用快照时创建。
    腾讯的成分接口每页固定 20 条、按价格排序：盘中翻页时排序会变，可能取到重复或漏掉一只，校验不通过就报错并在本次同步内重试，
    所以同步时间配在开盘前。除条数等于 `total` 外，还要求 `total` 大于一页（等于 20 说明翻页参数没生效）、没有重复、中途没有空页。
  - 市场 `market.yaml` 的 `subject_egress` 只对使用传入 HTTP 客户端的数据源起作用（币安）；自己建 HTTP 客户端的数据源
    （A 股各源、港股的腾讯成分来源、美股的纳斯达克与 datahub 成分来源和东方财富列表）都是直连，这一项对它们不起作用。
- **自动标签**：每分钟第 30 秒检查是否到期，按标签属性声明的数据源（`sync.source`；指数成分标签按 `sync.index_source`）拉取完整成员快照并调用 `ApplyTagSnapshot`（只表示“把成员设成这份快照”，被移出成员的 `inactive_at` 取 Storage 收到快照的时间）。运行状态写进 Collector 自己的库（`t_collector_tag_sync_runs`）；失败记在这张表里并打日志、出指标，不再上报给 Storage。手动标签成员由用户维护。
- **标的属性**：快照里新出现的标的由快照新建（`subject_id`、名称、时区与属性），已有标的的属性由属性维护任务更新；两条路径写出同一组属性键：crypto 是 `subject_type=crypto_pair`、`market=CRYPTO`、`currency`、`base`、`quote`、`pair`，stockcn 是 `subject_type=stock`、`market=交易所`、`currency=CNY`、`exchange`。
- **备用来源**（`sync.fallback_source`，可选，只对全部标的的标签有效）：主来源重试后仍失败（断连、超时、两个域名都在冷却）时，改用备用来源再取一次，超时预算单独算；成功按成功记录，日志有 `falling back to`、`used fallback` 两行 WARN。备用来源须与主来源同一口径；结果**只加不减**：当前全部 active 成员留着，再加上备用来源里的新标的。备用来源也失败时成员不变、记失败。内置的 `cn_a_share` 配的是 `sina`（新浪 hs_a 含沪深主板、创业板、科创板、北交所，与东方财富全部 A 股的筛选同一口径；2026-11-24 实测 57 页、5580 只）。2026-11-24 起控制机请求东方财富 clist 频繁断开（EOF、reset），`cn_a_share` 连续几轮同步失败，因此加了这一路。
- **同步状态与可选来源**：`ListTagSyncStatus(space_id)` 只读返回上述运行状态，Monitor 的标签检查（`failed` / `stale`，`stale` 的周期按 `sync.cron`、`sync.timezone` 算，没有运行记录的按 `stale`）与管理台标签页读它；`ListSubjectListers` 只读返回能提供标的快照的（来源，市场类型）组合，管理台新建自动标签的来源与市场类型选项来自它。
- **属性维护**：每分钟第 45 秒检查 `app.yaml` 中的 `subject_sync.attributes`；按任务时区判断 `(触发时间 - 1 分钟, 触发时间]` 内是否有计划时间。默认在北京时间 08:10:45 刷新 A 股与加密货币的名称和属性，首次启动也遵循该规则。

**采集名单排除**：需要在交易所快照之外临时去掉某些标的（公告下架、数据异常）时，用 `moox-cli collector subjects exclude --space-id <空间> --subjects A,B [--market swap] --reason <原因> [--expires-in 72h]`
（RPC `SetSubjectExclusions` / `ClearSubjectExclusions` / `ListSubjectExclusions`）。排除只作用于采集计划，标签成员与标的属性照常同步；对账在计算期望状态前去掉排除的标的，
名单一变下一轮（≤1 分钟）生成新计划、按提前量生效，SCF 与推送一样生效；已打开的计划（包括进行中的交接）先推进完再生效。到期后标的自动回到计划（期间的历史需要时用补采）。
调用方为控制台、`moox-cli`，以及经主机网关的外部入口用外部身份 `collector-operator` 调用的旁路程序（只放行这三个方法与 `SyncSubjects`；签名私钥在使用它的电脑上生成、公钥登记到控制机：`moox-cli setup register-identity --identity collector-operator --key-file <文件>`；请求的 `operator` 字段写设置人）；每次变更写活动日志 `collector.subject_change`。排除全部标的时数据集按“数据集消失”的去抖（5 轮）后退出计划，到期后作为新数据集回到计划。

两个定时器各自通过 `timerjob` 防止重叠，运行上限为 10 分钟。标签同步失败不会阻塞周期规划；退出时先取消并等待同步任务，再关闭 HTTP、网关客户端和数据库。

## 6a. 东方财富限流

2026-11-13 凌晨，一个没有页数上限的临时脚本在控制机上翻东方财富美股列表（`push2.eastmoney.com/api/qt/clist/get`），失败页不计入总数、页码一直往上加，
连续请求约 40 分钟（估计每秒十几次）。之后控制机出口 IP 被限流：对 `push2`、`push2his` 的请求立即被断开（`RemoteDisconnected`，约 0.1 秒），
`push2test` 仍可用，8 小时以上没有恢复。Collector 自己没有出事，但它每小时、每天 08:10 也在控制机上翻 A 股约 55 页、美股约 140 页的列表（页间没有节奏），
所以由程序自己保证打不到那个程度，并在发现被限流后主动停手。

**限流（默认开启，不写配置也生效）**：控制机进程内所有发往 `*.eastmoney.com` 的请求，即 `packages/cnstock` 的 `FetchClist` 的每一次请求
（A 股全部标的、沪深 300 成分、美股交易所对照；含页内重试和回退到 `push2test` 的请求），先过进程内唯一的限流器 `cnstock.RequestLimiter`：

- 一个全局令牌桶（各东方财富主机合计）：默认每秒 2 个请求、突发 2；一个并发上限：默认 1（顺序请求）。等待时尊重 `ctx`，取消或到期立即返回。
- `PageInterval`（页间隔）、`PageRetries`（页内重试）仍然保留，限流器是更底层的保证：重试和回退请求也要取令牌，所以两者叠加只会变慢，不会互相放大。
  页间隔与令牌等待重叠、不相加：每页的间隔约等于 max(0.5 秒, 页间隔 + 请求耗时)。
- 主机名不是 `*.eastmoney.com` 的请求（本地测试服务等）不受限流。云函数里取 K 线与附加字段的请求不经过这里，它们由各数据源的 `rate_limit` 控制（`config/markets/*/sources/eastmoney.yaml`）。
- 限流器只许让请求变慢：请求序列、重试条件、回退域名条件、返回结果与错误类别都不变（`packages/cnstock/testdata/clist_scenarios.golden` 是在接入限流器之前的代码上生成的 30 个场景金样，改动后逐字比对）。
  前提是同一页在同一主机上连续失败不到 5 次（冷却阈值）：线上 A 股 `PageRetries` 为 0、美股为 2，单页最多 3 次，到不了。
  唯一允许的差别是 `PageRetries` 达到 5 且同一页一直失败：第 6 次请求不再发出，错误由“重试 5 次后仍失败”（超时类）变成 `ErrCoolingDown`（场景 31，`testdata/clist_scenarios_diff.golden`）。

**冷却（按主机，`push2`、`push2his`、`push2test` 各自独立；令牌桶仍合计）**：

- 触发：连续 5 次传输层失败（连接被断开、EOF、重置、拨号失败、超时、读响应体失败），或一次 HTTP 429，或一次 HTTP 403；成功一次清零计数。
  ctx 取消或到期不算失败；5xx 没有结论，不计入失败也不清零计数。
- 冷却期间对该主机的请求不发出去，立即返回 `cnstock.ErrCoolingDown`（`*CoolingDownError`，带主机和剩余冷却时间，`errors.Is` 可识别），不占令牌与并发名额。
  这个错误不可重试：`FetchClist` 对 `push2` 报冷却时直接回退 `push2test`；`push2test` 也在冷却时整次失败；标签同步（`TagRunner`）遇到它不再在同一次同步内重跑 3 遍，等下一轮调度；
  触发冷却的那次请求自己仍返回原来的错误（429、403、超时），从下一次请求起才报冷却。
- 冷却时长：首次 10 分钟，之后每次再触发翻倍，最长 60 分钟；429 带 `Retry-After`（秒数或日期）时取较大者，同样不超过最长冷却。
  冷却结束后放过一个探测请求（其余请求继续被拒绝）：成功就恢复并清零，失败（传输失败、429、403）立即按翻倍后的时长重新冷却，不用再累计 5 次；探测被取消或遇到 5xx 没有结论，则释放探测名额，下一个请求再探测。

**配置**（`app.yaml` 的 `egress_limits.eastmoney`，整段可选，每项都有代码默认值；线上旧配置没有这一段也照常启动，默认值生效）：

| 键 | 默认 | 范围 | 含义 |
| --- | --- | --- | --- |
| `requests_per_second` | 2 | (0, 20] | 全局令牌桶每秒请求数 |
| `burst` | 2 | 1～50 | 突发数 |
| `max_concurrent` | 1 | 1～8 | 同时在途的请求数 |
| `cooldown_failures` | 5 | 1～50 | 连续传输层失败多少次进入冷却（429、403 一次就进入） |
| `cooldown_initial` | 10m | 1s～1h | 首次冷却时长 |
| `cooldown_max` | 1h | `cooldown_initial`～24h | 翻倍后的最长冷却时长 |

默认值的依据：2026-11-13 事故里每秒十几次连续 40 分钟触发了限流；每秒 2 个、顺序请求比它低一个数量级，A 股约 55 页约 30 秒、美股约 140 页约 70 秒读完。
冷却 10 分钟起步、翻倍到 1 小时，是为了让对方的限流有时间过去，同时不让一次误判长时间挡住标的同步。Trade 进程里的 `ListAllStocks` 也走同一个限流器，但不读这一段配置，使用代码默认值；每个进程各有自己的令牌桶，不跨进程合计。

**日志、指标与关注项**：

- 日志（Collector 日志里搜“东方财富限流”）：进入冷却、冷却结束放出探测、探测成功恢复各一行，带主机、时长、第几次冷却与原因（由连续失败触发的冷却还带失败次数；探测失败和 429 没有这个数）。
- 指标（标签只有 `host`，取值是 `push2.eastmoney.com`、`push2his.eastmoney.com`、`push2test.eastmoney.com`，其他一律记为 `other`；这些指标在 Collector 的 `/metrics` 里，不在 Monitor 的上报白名单里）：
  `moox_collector_eastmoney_requests_total`（通过限流器发出的请求数）、`moox_collector_eastmoney_rejected_total`（因冷却被拒绝、没有发出的请求数）、
  `moox_collector_eastmoney_wait_seconds`（请求在限流器里等令牌的时间，直方图；不含等并发名额的时间）、`moox_collector_eastmoney_cooling`（1 表示冷却中，探测成功才回到 0）、
  `moox_collector_eastmoney_cooldowns_total`（进入冷却的次数）。
- 关注项 `collector_attention:eastmoney_cooling_down`：**只在 `push2` 和 `push2test` 都在冷却（标的列表同步真的做不了）时为 1**，任一主机探测成功后回到 0；detail 是固定文字，不含时长与次数。
  `push2` 单独冷却时 `FetchClist` 回退 `push2test`，同步照常，只记日志和指标，不告警；`push2his` 不是标的列表同步用的主机，它的冷却也不触发关注项。
  Monitor 把它记为 warning（需关注）：只是标的列表同步暂缓，云函数采集不受影响；但 warning 仍会走告警通知，两个主机都在冷却期间会持续提醒，此时同步确实失败，不是误报。
  已知差别：冷却结束后如果一直没有新请求（`cn_a_share` 每小时的第 23 分钟同步一次，所以通常最多晚一个小时），值会保持 1，直到下一次探测成功。

**被限流后怎么恢复**：什么都不用做，等冷却结束，下一次标的同步会自动探测并恢复；同一时间 `push2test`（备用域名）已由 `FetchClist` 自动换用，不用手工切换（只有 `push2` 在冷却时同步照常、不告警）。
不要手工狂打：不要在冷却期间反复 `collector subjects sync`（它会被限流器直接拒绝，也不会缩短冷却），也不要重启 Collector 来“重置”冷却（重启只是丢掉本进程的记忆，对方的限流仍在，下一次请求照样被断开）。
急需同步时，先确认对方已经恢复，再手工同步一次。

**运维约定：禁止在生产主机上跑没有上限的临时脚本访问东方财富。** 做实测只有两条路：

1. 用临时云函数（南京出口）做，并设请求总数上限；
2. 写在 Collector 的代码里，复用 `cnstock.RequestLimiter`（`FetchClist` 已经接好），不要另起一套请求。

确实要在本机做一次性探测时，按“安全探测”的做法：

- **总请求数硬上限**：写死一个不大的数（例如 50），循环用“已发出的请求数”做上限，而不是“翻到没数据为止”；失败的请求、失败页也计入请求数，页码循环必须有上限。
- **速率**：每秒不超过 1～2 个（相邻请求间隔不小于 0.5 秒），不开并发。
- **失败就停**：连续失败 3 次立即停止；遇到 429、403 或连接被断开立即停止，不重试、不换域名继续打。
- 开始前先写下预计的请求数，结束后核对实际请求数。

**标签同步的时间预算**（`subject_sync.fetch_timeout` 现在是 150 秒，网关调用 170 秒后返回失败，不要再加大；估算按每页 0.5 秒的令牌间隔、请求耗时不超过 0.3 秒）：

| 场景 | 页数 | 限流后的耗时 | 说明 |
| --- | --- | --- | --- |
| A 股全部标的（`cn_a_share` 每小时 :23；08:10 的属性维护再读一次） | 约 55 | 约 28 秒 | 没有页间隔，每页就是 0.5 秒 |
| 沪深 300 成分（`cn_hs300`） | 3 | 约 1.5 秒 | |
| 标普 500 的交易所对照（`us_spx`，m:105、m:106、m:107 三个市场） | 约 140 | 约 70 秒 | 交易所对照不再额外加页间隔（默认 0，节奏全由限流器管）；请求耗时 0.5 秒时约 70 秒，0.8 秒时约 112 秒（请求耗时超过 0.5 秒后节奏由请求本身决定，限流器不再拖慢） |
| 最坏一轮同时到期的几个标签 | 约 200 | 约 100 秒以上 | 内置标签的 cron 错开（`cn_a_share` 每小时 :23、`cn_hs300` 北京 08:40、`us_spx` 纽约 08:00），标签同步与属性维护共用一把互斥锁、按顺序执行，不会同时抢令牌；每个标签各有 150 秒预算，定时器总上限 10 分钟 |

结论：150 秒够每个标签完整读一遍，不改，也不要加大 `fetch_timeout`；但美股那一次读完需要 70～112 秒，同一次同步里整次重跑一遍（失败后 2 秒、4 秒再试）基本来不及，
页内重试（每页最多 2 次）才是主要的容错，整次失败后要等下一次 cron。
手工 `collector subjects sync` 一次同步 A 股与美股全部标签约 100 秒，请求耗时 0.8 秒时约 160 秒，逼近 170 秒的网关上限，请按标签分开同步。

**已知差别**：

- 翻页已固定在 `push2` 之后，如果中途 `push2` 进入冷却（只会出现在别的调用同时触发冷却时），本次读列表直接失败，不会半路换 `push2test`，下一次同步从头开始会直接用 `push2test`。
- `Retry-After` 超过 `cooldown_max` 时按 `cooldown_max` 算。
- 遇到冷却不在本次同步内重跑：日频标签（`us_spx`、`cn_hs300`、08:10 的属性维护）碰上两个主机都在冷却，要等到下一次 cron（第二天）；`cn_a_share` 每小时一次，下一小时再试。
- 限流器的观察者在归还并发名额之前被调用：“在锁之外”只对互斥锁成立。生产的观察者只写日志、指标和关注项，不回调限流器，所以没有影响。
- 限流只覆盖 `FetchClist`；以后新增的、在控制机上直连东方财富的代码必须也走 `RequestLimiter`。控制机上的其他脚本不经过限流器（例如 `~/t0probe/probe.py watch` 每 10 分钟取几只 A 股的数据，量很小）；新增脚本要自己遵守上面“安全探测”的做法。

## 7. K 线重采样

`kline_resample` 类型的任务在 Collector 进程内执行：读取源数据集的 K 线，生成更长的周期（如 5m → 45m、1m → 1h）
并写入任务的结果数据集。该功能默认关闭，在 `config/app.yaml` 的
`kline_resample.enabled` 中开启。

**创建**：新建合成任务时选一个**源采集任务**（`kline` 任务，或另一个合成任务，可逐级合成），再填目标频率。源数据集、
源周期、序列标签由 Collector 从源任务推导并保存（任务参数 `source_task_id`），不需要手填；`PreviewKlineResampleSource`
给出推导结果并按下面的规则校验目标频率，控制台据此即时提示。合成任务继承源数据集的标的范围，不能单独选择标签；创建后参数不可修改。

**合成规则**（创建、更新、种子导入、启动清单都走 `resample.ValidateTaskParams`，不满足的直接拒绝）：

- 源、目标都是 1m～1d 的定长周期，目标必须是源的整数倍；日内周期写成 `<N>m` / `<N>h` 且整除一天（45m 一天 32 根）。
- 市场必须登记了分桶方式（`packages/barclock`）。24 小时连续市场（crypto）按 `epoch_utc` 从 Unix 零点切分；
  交易时段市场（A 股）按 `session`，每个交易时段从开盘起切分，不跨午休、不截短，休市日没有桶，`1d` 为交易日一根。
  交易时段市场的日内源、目标周期必须整除每个交易时段（A 股两段各 120 分钟，目标只能是 120 的约数，45m、4h 拒绝并列出可选周期）。
  没有在 barclock 登记的市场不能合成；交易时段市场的交易日历取 `packages/marketcalendar`（A 股 `cn_stock`、港股 `hk_stock`、美股 `us_stock`）。

**统一数据集作源**：源任务挂了现货、永续两个标签时，推导出的合成任务 `market_type=multi`，源序列写在 `source_series_tags`（每个市场一条；
单序列的源仍是 `source_series_tag`，两者不能同时给出），`PreviewKlineResampleSource` 同样返回 `source_series_tags`。
合成按 tag 分别进行：源标的按 tag 各取自己标签的成员（用标签的 `market_type` 与 `SeriesTagMarket(tag)` 对应，不取并集），
目标数据集的快照按（标的、tag）生成，某个 tag 下没有的标的不进快照，不会生成不存在的序列；实时合成按源周期完成事件的 `universe_series`、`failed_series` 取成员（单序列的源也一样），
失败的序列不合成、其他序列照常。补写通知与 `event.collector.kline.backfilled` 在统一数据集上带 `series_tag(s)`，合成订阅它时只对涉及的序列建作业。
目标数据集同样是统一数据集（`market_type=multi`）。

**触发与执行**（按“数据集 × 桶”批量：一次读出全部标的的源窗口，逐标的聚合，再批量写入）：

- **事件主路径**：配置了顶层 `event_bus` 时，订阅 `DatasetPeriodCompleted`（`event.storage.dataset.period.completed`），按源数据集与频率筛选；收到桶内最后一个源周期的完成事件，
  就合成该桶（`degraded` 事件里失败的标的先跳过）。45m 收盘后约 1～3 秒写入。
- **兜底检查**：每分钟第 5 秒，检查每个任务最近 `fallback_lookback_bars` 根已收盘的目标 K 线（收盘已过 `fallback_grace`），
  按目标数据集里缺的行补齐；不保存状态。没有事件总线时它是唯一的实时路径，延迟约 1 分钟。
- **覆盖的空间**：事件消费者和兜底检查覆盖 barclock 登记的全部市场（现在是 `crypto`、`stockcn`、`stockhk`、`stockus`），
  不读环境变量，新建合成任务不需要重启。每个空间两个持久消费者；任一消费者创建失败（例如 EventBus 凭据没有给这个空间授权）
  就整体失败并关掉已建的，由 `Hub` 之后整体重试，连续 3 次失败上报 `eventbus_consumer_failed`。
  Admin 生成 Collector EventBus 凭据的空间名单（`collectorEventBusSpaces`）要与 barclock 登记的市场一致，新增市场时两处一起改。
- **补采完成事件**：补采分块读回确认成功时，在同一事务记补写通知；发布协程按（空间、数据集、频率、来源、作业）合并，
  经本地 outbox 发布 `event.collector.kline.backfilled`（只带元数据）。补采来源的事件另带 `absent`：范围内全部标的已确认行情源没有的 K 线
  （标的、`series_tag`、区间，最多 5000 段，超出只留最新的并告警），因子引擎据此不把它们算进缺失比例。
  补采作业结束（成功、失败）或被取消时立即封存一次，失败作业里已成功的分块同样会发；每分钟的维护轮兜底封存创建超过一小时还没封存的通知（进行中的补采作业刚写下的不动，留给作业结束时一并封存；合成关闭时只靠这两处，没封存的通知不会等到 7 天后被清理掉），合成开启时合成的定时器也封存；每次封存循环到没有未成批的通知为止。
  发布器和中继属于 Collector 的 EventBus 接入，过期通知与已发布事件的清理在维护轮里做，都不依赖 K 线合成是否开启。因子引擎和合成都只订阅这个事件，没有另外的补齐通知接口。
  合成订阅它，对依赖该数据集的合成任务提交 `source_backfill` 历史作业（最早开始时间 = 确认时刻 + 2×`exec_timeout`，保证不被读到旧源数据的执行覆盖）。
- **历史合成**：`SubmitKlineResampleJob` / `GetKlineResampleJob` / `ListKlineResampleJobs` / `CancelKlineResampleJob`，
  CLI 为 `moox-cli collector resample backfill / jobs / cancel`。范围按 UTC 解析并向外对齐到目标桶，最多 10080 个桶，按游标推进、
  进程重启后继续；源数据不完整的标的跳过并计数（记录样例）；作业结束时不等 View：作业成功只表示行已写进 Storage，View 随后跟随变更日志应用；超过 `[storage_view.max_age]` 的历史行会被 View 过滤。

**写入目标**：落在已登记快照内且周期未截止（收盘后 2 分钟）的标的用周期提交（`CommitTimeSeriesBatch`），由 Storage 判断是否到齐并发出目标数据集的
`DatasetPeriodCompleted`（`source=ledger`）；首次生效点之前的桶、截止之后的补写、快照之外的标的用普通写入，并记为补写通知。快照在兜底检查里随源数据集的标的集合登记，
生效点是当前时间之后的第一个目标桶边界。

**不加锁**：事件、兜底、历史作业可能同时处理同一个桶——读到同一份源数据时写出同一个值；源数据只会被补采改写，补采确认后一定触发重算，结果最终一致。

## 7a. 下架检测

代码在 `internal/tradingstatus/delist`，与第 7b 节的交易状态检测同属一个子模块：下架检测管“已经预告、将来不可交易”（驱动 Trade 的下架名单与清仓），交易状态管“现在不能交易、也可能恢复”。

Collector 把交易所的下架信息变成事件 `event.collector.instrument.delist_scheduled`（交易所、市场 SPOT/SWAP、交易所代码、下架时间、来源、首次发现时间、范围 ALL / PAPER_ONLY），
由[事件中心](事件中心.md)按规则处理（通知你的接口，或禁止买入并在下架前平仓）。检测放在 Collector 而不是 collector-stream：Collector 有数据库、EventBus 发布身份和发件箱，也已经经出口代理访问币安。
它只检测下架**发生之前**的信息；`collector-stream` 发现的“疑似下架”（见 3a）是下架之后的检测，两者不重叠。

每 10 分钟轮询一次，只保留 USDT 计价的现货和 U 本位永续，接口来源忽略下架时间已过的条目：

| 来源 | 接口 | 说明 |
| --- | --- | --- |
| 币安现货 | `GET /sapi/v1/spot/delist-schedule` | 行情数据类：请求头带 `X-MBX-APIKEY`，不签名。用专用只读 Key，经 SecretMgr 的 `GetReadonlyExchangeKey`（只返回 `exchange-binance-production-readonly` 的 `key_id`，Collector 拿不到任何 Secret 明文，也拿不到 Trade 的交易密钥） |
| 币安 U 本位合约 | `GET /fapi/v1/exchangeInfo` | 单独解码：永续合约的 `deliveryDate` 正常是占位的远期值（官方样例 4133404800000），出现近期的真实时间才算下架；季度合约、非 USDT 计价忽略 |
| OKX 永续 | `GET /api/v5/public/instruments?instType=SWAP`（`openapi.okx.com`） | 永续合约的 `expTime` 正常为空，有值才算计划下架 |
| 手工登记 | RPC `RegisterDelistNotice`、`moox-cli collector delist register`、管理台「事件中心」“事件”页签的“手工登记” | 补漏报和演练；可以补录过去的下架时间（仍写下架名单、只核对不下单）；`paper_only` 时范围是 PAPER_ONLY。登记后到 T−24h（已不足 24 小时的立即）会自动卖出策略持有的实盘仓位，命令行加 `--yes` 之前先和用户确认标的与下架时间；演练用 `--paper-only`，只平模拟盘，但同样全局禁止买入这个标的，直到演练记录结束 |

- **去重与发布**：新表 `t_collector_delist_notices`，（交易所、市场、代码、范围、下架时间）唯一；同一条再次被报告只更新最后报告时间，不再发布。新条目在同一事务里写进发件箱 `t_collector_event_outbox`，由 Collector 级的中继发布（不丢）。
  事件 ID 由（交易所、市场、代码、范围、下架时间）确定性生成，信封空间固定为系统空间 `mooxsys`，subject 是“交易所:市场:代码”。下架时间变了就是新条目、发布新事件，事件中心按同一标的合并。
  同一来源一轮里同一（交易所、市场、代码、范围）出现多条（币安现货计划里同一个代码可能在两个下架时间组）时，只取最早的下架时间，免得每轮在两个时间之间来回发布。
  **手工登记与接口的优先级**：以接口为准。范围 ALL 的手工登记时间和接口报的不同，下一轮轮询（10 分钟内）就会按接口时间重新发布一次（事件中心的执行记录跟着改回接口时间）；
  想自己定下架时间做演练，请用 `paper_only`（范围 PAPER_ONLY，和真实的 ALL 互不影响）。
- **发件箱的积压与死信**：事件先写进发件箱 `t_collector_event_outbox`（`c_published`：0 待发布、1 已发布、2 死信），中继每 10 秒发布一轮。
  最老的待发布事件超过 10 分钟没发出去，上报关注项 `event_outbox_stuck`（EventBus 连不上或发布被拒）；无法解码的事件标成死信，不再堵住后面的事件，同样上报 `event_outbox_stuck`，需要人工查看。
  连上 EventBus 后 K 线合成消费者启动失败不影响下架事件的发布，连续 3 次失败上报 `eventbus_consumer_failed`。
- **不做自动撤销**：条目从接口里消失，可能是下架时间改了，也可能是下架已经完成，没法可靠判断交易所是否撤销了下架。误报靠提前量、事件中心的 `delist_detected` 通知和手工取消兜底。
- **没有只读 Key**：读不到 `exchange-binance-production-readonly` 时，币安现货来源本轮跳过，上报关注项 `delist_readonly_key_missing`，下一轮继续尝试，补上 Key 即自动恢复。
  读不到有三种情况，关注项分不出是哪一种（`GetReadonlyExchangeKey` 都回 NOT_FOUND），管理台监控页一次列全：
  - 已有这把 Key 但被禁用：到密钥管理页启用；
  - 还没有：用户在秘密文件 `moox.secrets.toml` 的 `[[exchange_keys]]` 里加一把币安正式环境的密钥（`exchange = "binance"`、`environment = "production"`、`name = "readonly"`、`readonly = true`，用 `moox-cli config edit` 修改），经 `setup init` 写进 SecretMgr；
  - 在管理台删除过：`setup init` 不重建删除过的密钥，换名称也不行（Collector 只读这个固定 ID），目前补不回来，见[已知限制](#已知限制)。
  关注项的 detail 里也简短写了这三种情况。这一项只算 warning（业务检查显示“需关注”），不挡安装验收；缺 Key 期间现货下架只能手工登记。
- **自动检测开关**：配置 `delist.auto_detect`（默认 true）。安装时按拓扑渲染：有出口代理（配了海外机）为 true，没有时为 false——三个来源都要经出口代理访问，没有出口代理时只会一直失败。
  关闭时不轮询来源、不建出口 HTTP 客户端，手工登记照常可用。
- **来源失败**：某个来源连续 3 次失败，上报 `delist_source_failed`；某个来源这一轮返回的条目被校验拒绝（交易所、市场不对，代码带冒号等）、没有发布时同样上报（等于漏报，请手工登记并检查来源返回），下一轮不再被拒就恢复。交易所代码在登记时统一成大写再校验（来源返回小写或大小写混用也照常发布），与手工登记一致。两个关注项都走指标 `moox_collector_attention_active{kind,detail}`，Monitor 汇总成 `collector_attention:*` 检查，见[监控](监控.md)。
- **出口代理**：币安现货接口需要 `X-MBX-APIKEY`，OKX 域名要在出口代理白名单里，见[出口代理](出口代理.md)。

### Collector 级的 EventBus 接入

EventBus 连接和发件箱中继属于 Collector 整体（`internal/eventbus`）：配置是顶层 `event_bus`（`urls`、`credential_file`），不挂在 K 线合成下面。`Hub` 维护一条共享连接，连不上每分钟重试，EventBus 晚于 Collector 启动也能自动连上；
连上后才创建 K 线合成的消费者。`Relay` 是独立的发布循环（10 秒一轮，封存出新事件会立即唤醒），不依赖 K 线合成是否开启。
`NoticePublisher` 只负责把补写通知封存进发件箱。没有配置 `event_bus` 时不发布任何事件，下架检测不启动，手工登记返回明确的错误。

## 7b. 标的交易状态

停牌、退市的标的会让各处出问题：采集和补采每期为它失败，监控一直报“没有任何数据”，因子每期记失败，策略可能把它选进目标。所以由 Collector 的子模块 `internal/tradingstatus` 统一检测每个标的**在每个市场**的交易状态，写到 Storage 的标签成员上（`t_subject_tags.c_trading_status`：`trading` 正常、`suspended` 停牌、`delisted` 退市；见[存储](存储.md)）。状态按标签成员记而不是按标的：crypto 的现货、永续共用一个标的，常常只有一边停。

Storage 的 `ResolveSubjects` 与 `ListDatasetSubjects` 只把可交易的成员当作活跃，于是下游不用各自处理：

- **采集**：采集计划按 `ResolveSubjects` 取标的，不可交易的从函数分配里去掉，时间线新开一段、自动补采也不再为它补；复牌后回到计划，从复牌那期起照常采集（停牌期间本来就没有行情）。
- **监控**：K 线新鲜度的活跃名单不含它，不再报“没有任何数据”。
- **因子**：预载名单与实时全集里都没有它，不再每期记失败、不进空洞台账。
- **策略**：全集里没有它；已持有的停牌标的冻结持仓（`suspended_hold`，见[策略](策略.md)），退市或被移出标签的照常清零。
- **交易**：crypto 交易所列表里有、但不可交易、又不在下架名单里的持仓本轮跳过，不再阻塞整份目标（见[交易](交易.md)）。

**各市场的来源与时间**（只写在编进二进制的各市场 `market.yaml` 的 `trading_status` 段，不能被部署配置覆盖）：

| 市场 | 来源 | 时间 |
| --- | --- | --- |
| A 股 | 腾讯实时快照第 40 个字段：S 停牌，D、C（北交所旧代码换号）退市 | 交易日 9:05、12:05（上海） |
| 港股 | 腾讯港股实时快照第 40 个字段：非空即停牌（腾讯对退市的代码不返回行，退市靠成分同步移出） | 交易日 9:05、12:05（香港） |
| 美股 | 腾讯美股快照第 40 个字段：S 停牌，D 退市 | 交易日 9:05（纽约） |
| crypto 币安现货、永续 | 标的同步用的 exchangeInfo 原始状态，经出口代理 | 每小时第 25 分；推送侧疑似下架时立即再查 |

- **股票的时间**：9:05 开盘前快照的状态已是当天的，留出半小时让新计划生效；12:05 那次让上午停牌、午后复牌的股票在 13:00 前回到计划（标的离开计划后时间线新开一段，补采只看段内标的，不跑这一次当天下午的 K 线就既不采也不补）。美股没有午休，只跑一次。
- **美股的实测**（2026-11-24，用纳斯达克交易暂停列表核对）：纳斯达克上市的暂停股（IPFX、TJGC、HCHL，原因 T12）第 40 个字段是 S；AMEX 上市的（DDC、TOVX，原因 H11）为空，腾讯没有标出；NYSE 的没有样例。标不出来的照旧按缺数处理。
- **币安的判定顺序**（先命中的为准）：① 原始状态 `TRADING` 记 trading，不看下架名单也不看合约类型；② 永续处于 `PRE_DELIVERING`、`DELIVERING`、`DELIVERED`、`PRE_SETTLE`、`SETTLING`、`CLOSE` 记 delisted；③ 现货非 TRADING、而且下架记录（第 7a 节）里这个交易对最新一行（`binance`、`SPOT`、`ALL`，不含 PAPER_ONLY）的下架时间已过，记 delisted；④ 其余非 TRADING（BREAK、HALT、PENDING_TRADING……）记 suspended；列表里已经没有的保留原值，由标签同步移出。
- **crypto 的开关**：跟随部署配置的 `delist.auto_detect`（没有出口代理时渲染成 false，两者一起关掉）。关掉时标签同步的快照只留正常交易的交易对。
- **触发**：挂在属性任务的每分钟定时器上（入口先固定触发时间，先跑交易状态、不进标签同步的锁，再跑属性任务）；Collector 启动一分钟后跑一次全部；`collector-stream` 报疑似下架触发的立即同步之后，对那个市场再跑一次（同步失败或正忙也跑）；手工 `collector subjects sync` 之后顺带跑一次这个空间。
- **列哪些标的**：本空间里 `market_type` 与任务相同的标签（自动、手动都算，例如用 `tag clone` 建的手动标签）的 active 成员，用 `ListTagMembers` 列，不受停牌过滤影响，才能发现复牌。同一只股票在多个标签里时每个都写。没有 `market_type` 属性的手动标签不检测。
- **写入**：只写有变化的成员（Storage 的 `SetTagMemberTradingStatus` 也只更新值不同的行，避免白白递增标的修订号让采集计划、监控、策略缓存重算）；日志只打出有变化的，例如 `trading status stockcn cn_hs300 changed=1: 601059.XSHG trading→delisted`。
- **失败处理**：腾讯每 60 只一批单独请求，某一批失败只丢这一批；返回里没有的标的保留原值；不会因为请求失败把标的标成可交易或停牌。
- **整体维护保护**：某个市场本轮查到的成员里一个正常交易的都没有，或者本轮新变成不可交易的成员超过当前可交易成员的一半，整轮不写、保留原值、打警告。第二条只数这一轮新变的，长期停牌的成员不进比例。
- **crypto 的频率**：每次都全量拉 exchangeInfo（现货十几 MB），经海外机的出口代理，海外机带宽小，所以只每小时查一次（与整点后的标签同步错开）；停牌分钟级生效靠 `collector-stream` 的疑似下架触发（永续的 `!contractInfo` 推送、或连续 3 个 1m 缺数）。
- **查看与手工触发**：`moox-cli metadata tag list-members --space-id <空间> --tag-id <标签>` 的输出带每个成员的 `trading_status`。没有单独的检测命令：`moox-cli collector subjects sync --space-id <空间>` 同步完标签后顺带检测这个空间（A 股会连带请求东方财富的标签同步），检测结果不进命令输出，看 Collector 日志的 `trading status` 行确认。
- **已知差别**：
  - 股票盘中临时停牌不处理（照旧按缺数）；午后盘中才复牌的，当天复牌后的 K 线要等第二天 9:05 之后才回到计划，补不回来。反过来，Collector 盘中重启或手工同步时碰上腾讯已标 S 的临停，会一直停到下一次定时检测。
  - 港股退市的代码腾讯不返回，标不上，靠成分同步移出；美股只有纳斯达克上市的暂停经实测会标 S。
  - 腾讯快照或交易所不可用时，状态停在上一次的值；启动那一次失败不重试，等下一次定时检测。
  - 币安整体维护（全部或过半新变不可交易）时状态保持维护前的值，维护期间的缺数照旧走补采。某个空间同一市场类型的成员只有一两只、又正好全停时，保护会一直生效、一直不写。
  - 从停牌到被标记之间（crypto 最长约 1 小时，推送侧触发时为分钟级），策略仍可能给不可交易的标的发非保持目标，被 Trade 整份拒绝，与原来相同。
  - 没有下架预告、却长期 BREAK 的现货交易对，一直以 `suspended` 留在标签里（不采集、不进策略全集，只多一个成员）。下架检测的币安现货来源要只读 Key，缺 Key 时所有下架的现货都会这样留着。
  - 没有 `market_type` 属性的手动标签写不到；同一数据集里它会让标的保持活跃。
  - 因子补算时显式指定这类标的会报“不在源数据集”。
  - A 股每轮查的是 `cn_a_share` 全部成员（约 5400 只、90 多批腾讯请求），每天两次。

**币安标签同步的变化**：交易所长期保留已下架的交易对（2026-11-24 线上：现货 3751 个交易对里 TRADING 只有 1376 个；永续 956 个里活跃 567 个）。lister 现在带出全部 USDT 交易对和原始状态（永续合约类型包括 `PERPETUAL_DELIVERING`），同一标的出现多次时优先保留 TRADING 的那条。标签同步只保留“正常交易的 ∪（非 TRADING ∩ 现有 active 成员 ∩ 没被标成退市）”：新增和重新激活只认 TRADING，已在标签里、临时 BREAK 的留给交易状态检测标成停牌，被标成退市的下一次同步移出。一个 TRADING 都没有时这次同步按失败处理、成员不变；读成员失败同样按失败处理。股票的 lister 不带原始状态，这条过滤不适用。

## 8. 管理接口

## 9. 数据保留

Collector 的 SQLite 只保存运行状态：采集计划、补采作业、任务与合成状态。每分钟的维护任务按
`collector_retention.max_rows_per_pass` 的预算清理已结束的补采作业；补写通知与已发布事件保留 7 天、已结束的历史合成作业保留 30 天。
维护任务每轮现取管理集合（有启用任务、库里有计划、配置了云函数或处于暂停的空间，与采集计划同一份名单），逐空间清理补采作业并刷新库指标；
Collector 进程不读 `MOOX_SPACE_ID` / `MOOX_SPACE_IDS`。已知差别：一个空间的任务和计划全部删光后不在管理集合里，它剩下的已结束补采作业不再清理。
行情数据本身在 Storage 中，按 Storage 保留策略（结果数据集的空间与频率）清理，采集任务不设置保留期。

SQLite 使用显式选择的纯 Go modernc 驱动，Collector 服务、CLI、标的同步及 SCF 程序在本机关闭 CGO 构建。连接显式设置 `_time_format=sqlite`，保持时间可被 SQLite 日期函数解析，范围查询与绑定参数使用相同格式。

进程内 Storage Metadata/Primary 调用共用 `gatewayclient`；计划对账、结果管理、重采样和周期上报从同一客户端注入，标的同步读取同一份 Collector 主配置。`gateway_client` 记录固定 caller `collector`、本机的主机签名私钥文件，以及部署渲染的主机 ID、loopback 地址与私有 CA。函数用的 `scf-collector` 私钥在 `scf_entry.key_file`（控制机 `secrets/scf-collector.key`），Collector 每次生成函数环境时重读它。只读刷新重试交给共享层，内部写调用只发送一次。退出或初始化失败时先取消并等待定时任务、维护和对账协程，再关闭客户端和数据库。SCF 使用外部入口客户端；HTTP 出口复用 EgressProxy，拓扑来自 SysDeploy v2。

## 10. 发布 SCF 函数

SCF 采集函数由 Collector 的采集计划对账器创建与升级，不需要手工发布：

- `moox-cli setup deploy --host <控制机>` 按 `moox.toml` 的 `[scf_plan]` 段渲染 Collector 的 `scf_regions`、`scf_markets`、`scf_plan`，
  `setup init` 保证每个空间已上传代码包；
- 代码包按包名取最新（`scf_plan.package_name`），在每轮对账或补采准备时按需解析，成功结果缓存至少 30 秒；对账默认每分钟一轮，上传新版本后逐轮滚动升级各函数；
- 函数环境由 Collector 生成：空间（`MOOX_SPACE_ID`）、代码包 ID、外部入口地址与入口主机（`MOOX_ENTRY_ADDRESS`、`MOOX_ENTRY_HOST`）、`scf-collector` 的 ed25519 签名私钥及其指纹（`MOOX_CALLER`、`MOOX_CALLER_KEY`、`MOOX_CALLER_KEY_ID`），每次建函数或改环境时补齐 CLS 上报环境（见第 10a 节）。函数不连 EventBus，环境里出现任何 EventBus 变量都会被拒绝；Storage 没有调用方密钥，函数能调哪些方法由外部入口按 `scf-collector` 的方法名单决定。

**备援请求（默认关闭）**：整点前后行情源响应变慢时，约一半的 1m 请求第一次尝试停住 2～5 秒后才换端点成功。Collector 配置 `scf_plan.fetch`
（或 `scf_plan.spaces.<空间>.fetch`）的 `standby_ms` 大于 0 时，函数在行情请求超过这么多毫秒还没有结果时并发再发一个备援请求（有下一个端点用下一个，
只有一个端点就再发一次同一个），先成功的为准，另一个被取消；第一次请求在延迟之前就失败时仍是普通的顺序换端点，不发备援。取值 200～5000，
太短会让大多数请求都发出备援、白白加倍请求权重；多出的请求权重只发生在发出备援的那部分请求上。`standby_hour_only: true` 只在整点那一分钟触发的调用里启用。
批次摘要总是带 `standby_ms`（0 表示这批没有启用），启用的批次另有 `standby_fired`（发出备援请求的次数）与 `standby_won`（备援请求先成功的次数）。
这些字段随采集计划下发，函数遇到不认识的字段会拒绝计划，所以函数代码包要和 Collector 是同一版，再在 Collector 配置里打开。
2026-10-20 在单端点上限 1.2 秒时试过一次（`standby_ms=800`），没有改善（备援请求同样被截断）；现在随 3 秒的单端点上限重新提供，效果待再试。

**连接复用（默认关闭）**：函数进程会连续服务多次调用，但默认每次调用都新建 HTTP 客户端，上一分钟建好的连接全部丢弃，每个标的每分钟都要重新握手。
整点实测里新建连接上的第一个请求常停住数秒，而复用连接上的请求都正常返回。`scf_plan.fetch` 的 `conn_reuse: true` 让函数在调用之间共用一个进程内的 HTTP 客户端（空闲连接最长保留 90 秒，每个函数最多 64 条空闲连接），
下一分钟的请求直接用上一分钟留下的连接。
批次摘要总是带 `conn_reuse`（0/1），启用后批次里的 `conn_reused` 应明显增加、`conn_new` 与握手耗时 `tls_*` 下降。

**币安端点**：现货只配 3 个出口各不相同的官方端点（`api.binance.com` 走 CloudFront、`api-gcp.binance.com` 走 Google Cloud、`data-api.binance.vision` 走 AWS 东京直连），
合约只有 `fapi.binance.com` 一个可用端点（`fapi1`～`fapi4` 只是重定向到 www.binance.com 的通配域名）。配置在 `configs/scf/market_data/sources/market/binance.yaml`。

**REST 取到的不一定是定稿值**：币安 K 线接口没有"已闭合"标志（返回里的收盘时间是固定值），函数只按本机时间判断收盘。2026-10-20 实测：合约 REST 要到收盘后约 8 秒、现货约 3 秒才与最终值一致，更早取到的成交量、成交额、笔数偏少；而 Storage 的周期一旦全部提交就锁定，早取的值改不回来。线上合约 1m 因此有 26%～55% 的 K 线不是定稿值。现已按市场推迟取数：`scf_plan.spaces.<空间>.markets.<市场>.fetch.not_before_ms` 让函数等到收盘后这么多毫秒再取数（crypto 现货 3000、合约 8000，
合约的 `allowed_lateness_seconds` 放宽到 20 秒），并为 crypto 改用 WS 推送（第 3a 节）。`not_before_ms` 随计划下发，必须先升函数包再改配置。

### 函数的创建、升级与读回

采集函数的新建、改配置、升级、读回修复一律由对账器完成，没有手工新增或部署的入口。管理台运行状态页的函数表有“云上状态”一列（内存里最近一次读回），计划外的函数单列一组；“云账号”“代码包”两个对话框也从这里打开。

- **名字即身份**：采集函数名由计划决定（`moox-fetch-plan-<空间>-<市场>-<地域>-<三位序号>`，地域去掉 `ap-`），命名空间每 50 个函数分一片（`scf_plan` 配置的命名空间，第二片起加 `-2`、`-3`……）。
  补采函数每个市场一个（`moox-fetch-plan-backfill-<空间>-<市场>-<地域>`），放在该市场第一个地域、配置的命名空间里，不分片。云上已有同名函数就接管，不看是谁建的。
  **命名空间只按固定规则建**：只有 Collector 会建命名空间，名字是 `moox.toml` 里这个空间的 `namespace`（默认 `moox-<空间>-plan`），只建在这个空间用到的地域
  （各市场的地域，加上 `backfill_region`）。每个地域最多 5 个命名空间（含删不掉的 `default`），满了建函数报 `LimitExceeded.Namespace`、补采卡住；
  不要手工或用别的命名建命名空间。2026-11-23 清理过一次早先版本留下的随机名命名空间（`ap-<地域>-01`、`ap-<地域>-xxx`、`moox-crypto`、`moox-crypto-ns2` 等）。
  `moox.toml` 的 `[[scf_plan.spaces]]` 里写了 `backfill_region` 时补采函数改放那个地域（要有对应的 `[scf_plan.regions.<地域>]`：vpc 方式要有同地域的外部入口主机，而且必须是普通云服务器；public 方式不需要）：
  定时函数与补采函数分开地域，补采的重发不占定时函数那批出口地址（港股定时函数在香港、补采在南京）。改地域后新地域的补采函数在下一次补采时创建，
  原地域留下的那个列为计划外，用 `collector function delete` 删。
  补采的名额（每个空间同时执行的分块数）先分给补缺口的作业，强制重拉的作业（收市后整天重取、手工 `--force`）排在最后：它重写的是已有的行，
  行情源不可用时每块都失败、退回重试，排在前面会每轮占满名额（2026-11-23 港股收市后整天重取把自动补采拖慢到每分钟几块）。补缺口的分块一直排不完时强制作业会一直等。
- **期望内容只在一处算**：计划推进时由调用方指定阶段（过渡计划配过渡 cron，最终计划配最终 cron；退役的函数保留过渡那一份环境，只停定时器）；
  读回修复、恢复启用、出口 IP 去重后重建、删除后重建不指定阶段，按已确认的状态算（未生效计划里已确认收尾的用最终计划，已确认过渡的用过渡计划，其余用已生效计划）。
- **建函数与改配置（Ensure）的顺序**：读函数（没有就建命名空间、建函数；CreateFailed 先删掉、等删完再建；UpdateFailed 直接重做更新）→ 等到 Active → 代码包不同先换代码 →
  再改环境与配置（内存、超时、VPC、公网、并发 1、不让腾讯云重试异步调用、补采函数的预留并发），`MOOX_CODE_PACKAGE_ID` 跟这一步一起写，所以环境里的包 ID 只在代码换好之后才变 →
  读回校验 → 最后设定时器并读回确认。环境比对只看期望的每一项在云上都有且相等，云上多出来的项不算不一致；写入时以云上现有环境为底合并期望值，顺带删掉废弃的键。
  做完的部分读回一致就不再写，重复调用没有写请求。
- **操作表**：改云上状态的操作都在进程内的操作表里由后台协程执行，同一个函数同一时刻只有一个操作；各空间共用并发上限 `scf_plan.max_concurrent_operations`（默认 20），单个操作最长 16 分钟（含遇到瞬时错误时从头重做，最多 3 遍）。
  对账每轮起完操作后最多等到本轮剩余时间减 5 秒，改环境这类几秒的操作当轮就能确认；没结束的下一轮接着看，不算失败，也不重复起操作。
  操作只在内存里：Collector 重启后没确认的函数重新 Ensure，从读回的状态接着做，建到一半的函数被接管。
- **读回修复**：已生效计划里的函数每小时读回一次（函数、定时器的 cron、开关、可用状态、Qualifier、Message、受管环境、代码包）。不存在或不一致的按期望重做，只是代码包落后的只换代码；
  有函数没读到时 5 分钟后重试，不宣布核对完成。读回时还按本空间的命名格式列出计划外的同前缀函数，停掉它们的定时器、不删除（见“已知限制”）。
- **代码包升级**：每 2 分钟检查一次（不做完整读回，优先用内存里最近一次读回的包 ID），落后的函数每次最多 100 个起“只换代码”的操作：环境取云上读回的值，只把 `MOOX_CODE_PACKAGE_ID` 换成新包，不动定时器，
  所以升级不会把正在过渡的环境改回去。
- **暂停**：先把空间标成“正在暂停”，不再为它起可能打开定时器的操作（补采函数与删除照常），取消排队中的这类操作、等在跑的结束，作废未生效计划里的下发与收尾确认，再停用全部定时器并读回确认，
  全部是停用才算完成。Ensure 走到设定时器那一步时看到空间正在暂停，也把定时器设成停用。
  恢复（以及进程重启后的第一轮）先把落后的函数升级到最新代码包，成功之后才启用定时器。

构建与上传代码包：`moox-cli collector function upload --space-id <空间> --cloud-account-id <云账号 ID> --version <版本> --collector-root modules/collector`（`--space-id`、`--cloud-account-id` 必填；`--package-name` 默认 `moox-collector-<空间>-plan`，与 `scf_plan` 的默认包名一致）。
`moox-cli collector function list --space-id <空间> [--drift]` 现场读回函数与期望比对；`moox-cli collector function delete --space-id <空间> --name <函数名>`（可重复）或 `--prefix <本空间前缀>` 删除函数，`--namespace`、`--region` 只删这个命名空间、地域里的（不带 `--yes` 时 Collector 用与实际删除相同的匹配列出会删的函数；计划里的函数删掉后下一轮重建）。命名空间改过之后，旧命名空间里的副本与在用的函数同名，删副本一定要带 `--namespace`，否则在用的同名函数也会被删，要等下一轮对账（约 1 分钟）才重建；`collector function list` 与运行状态页给计划外函数的删除命令都已带上命名空间与地域。
详见[命令行工具](命令行工具.md)和[部署与运维](../部署与运维.md)；云账号、代码包与腾讯云接口限流见第 10a 节。

### 采集计划协调的失败原因

对账器每轮向 Monitor 上报「协调是否健康」和当前失败原因（`moox_collector_market_fetch_coordination_failure{reason}`，同一时刻只有一个原因为 1）。
原因白名单与含义（白名单之外的一律按 `cloud` 上报；单测保证每个 `fail` 调用点用到的原因都在名单里，Monitor 为每个原因给出专属告警文案）：

| 原因 | 含义 |
| --- | --- |
| `cloud` | 调腾讯云失败：读回、列函数、建函数、改环境、换代码、设定时器、删函数失败，以及取云账号密钥失败（Admin 不可达、无权限、密钥已停用） |
| `quota` | 腾讯云的函数个数、命名空间个数或账号预留并发总额超限（`LimitExceeded.Function`、`LimitExceeded.Namespace`、`LimitExceeded.FunctionReservedConcurrencyMemory`）；其他 `LimitExceeded.*` 是参数越界，按 `cloud` 报。Monitor 的文案提示清理计划外的函数 |
| `environment` | 生成函数运行环境失败（外部入口、环境变量） |
| `rules` | 读取或解析采集规则、任务、标的失败 |
| `store` | Collector 本地 SQLite 读写失败（读取、保存采集计划与进度） |
| `storage` | 向 Storage 登记标的快照失败，或 Collector 与 Storage 计算的快照哈希不一致 |
| `package` | 没有可用的代码包（`scf_plan` 的包名还没有上传过可用的包），而要建函数，或者这个空间在云上已经有采集函数要升级 |
| `dataset` | 设置数据集允许迟到失败 |
| `activity` | 活动日志没有写入成功，计划保持未生效 |
| `preflight` | 创建新计划前的检查未通过，例如 A 股内嵌交易日历的覆盖期不足 14 天（不足 60 天只打告警日志） |
| `capacity` | 计划放不进函数：每函数标的数过多、环境变量超过 4KB 上限 |

- **操作还在跑不是失败**：云端操作没在本轮结束，下一轮接着看，不记失败；操作结束且失败才按上表的原因上报，下一轮重来。
- **每轮收尾**：本轮及自上一轮结束以来没有任何失败时，协调恢复为健康并清除遗留的失败原因（计划仍在进行也一样）；
  这本身不刷新「最近一次对账成功」时间。计划未生效时分两段：过渡配置都已下发、只是在等旧周期的窗口结束（1h 最长约一小时，1d 要等到下一个 UTC 零点）的
  每一轮都按对账成功刷新，Monitor 不把正常的等待判成对账陈旧；配置还没下发完，或过了窗口结束（加 5 秒收尾余量）仍没收尾的，该时间保持不动，
  卡住的计划照样由对账陈旧判定报出来。有云端操作在跑时，最早的一个未超过 10 分钟照常刷新
  （大批量升级可能连续跑十几分钟，期间一直有正常推进的操作）；超过说明卡住了，才停止刷新，由 Monitor 的对账陈旧判定（默认 15 分钟）发现。
- **协调进行中**：有未生效的计划或有云端操作在跑时上报 `moox_collector_market_fetch_coordination_pending`，`coordination_pending_since` 取计划的创建时间或最早一个在跑操作的开始时间；
  Monitor 在它开始后的 5 分钟内按“协调进行中”处理，见[监控](监控.md)。

## 10a. 云函数管理

云账号、代码包和对腾讯云 SCF、COS 的调用都在 Collector 进程里（`internal/cloud`），没有单独的进程，也没有作业表。只有控制面（对账器、补采、`CollectMgr` 的云函数接口）引用这个包，
云函数程序与 `collector-stream` 不引用（`internal/depcheck` 检查）。同一个函数的写操作在进程内加锁排队，只经第 10 节的操作表执行。

**云账号与密钥。** 云账号登记在 `t_collector_cloud_accounts`，只保存 Admin 里的密钥 ID 与 COS 地域、桶，不保存密钥本身；`moox-cli setup init` 登记，管理台运行状态页的“云账号”对话框可以查看和修改。
腾讯云 SecretID/SecretKey 由 Admin 的 SecretMgr 加密保存。Collector 每次操作 SCF 或 COS 时经网关调 `SecretMgr.GetCloudCredential` 现取：服务端校验密钥的类别是 `cloud`、厂商是 `tencent`、处于启用状态，
任何一项不满足就拒绝，不返回密钥值。Collector 读 SecretMgr 只被放行两个专用方法：这一个，和下架检测读币安只读 Key 公开标识的 `GetReadonlyExchangeKey`（见第 7a 节），名单里没有 `GetSecretValue`。这份名单只对跨主机调用起作用：Collector 与 Admin 同在控制机，同机调用直连回环端口、不查方法名单，所以专用方法对同机的组件没有隔离作用（见[主机网关](主机网关.md)第 4 节）。密钥不缓存、不落库、不写日志，在管理台轮换后下一次操作就用新的。
删云账号时，账号还被 `scf_plan.cloud_account_id` 引用、名下还有代码包、或配置过的地域里还有它建的函数，都会被拒绝（见“已知限制”）。

**代码包。** `InitPackageUpload` 登记一条 `pending` 的代码包并返回 COS 预签名上传地址（1 小时有效，对象在 `moox/cloud-packages/<日期>/` 下），上传完成后 `CompletePackageUpload` 核对 COS 里对象的大小与 MD5，
再标成可用；`moox-cli collector function upload` 和管理台的“代码包”对话框都走这两步。代码包不包含任何凭据。对账与补采按包名（`scf_plan.package_name`）取最新的可用包，不能固定用某个包 ID。
每天清理一次（启动 10 分钟后第一次）：每个（空间、包名）只留最新 3 个可用包，更早的连同 COS 对象删除；发出上传地址超过 6 小时仍没完成上传的删除。先删 COS 对象再删记录，对象删不掉时记录保留，下次再删。

**函数调用。** 补采分块同步调用补采函数（单次最长 90 秒），`collector function probe-egress` 经 `ProbeFunctionEgress` 调用各采集函数的出口探针。实时采集由腾讯云定时器触发函数，Collector 不逐周期调用。

**日志服务（CLS）。** `config/app.yaml` 的 `cloud.cls` 打开时，Collector 每次建函数或改环境都把上报所需的 `MOOX_CLS_*` 补进函数环境，首次使用时幂等开通 CLS；
开通失败、补齐后环境超过 4KB 都只记日志，函数照常建。函数环境里已经声明 `MOOX_CLS_ENABLED` 的保持不动。上报内容见[部署与运维](../部署与运维.md)。

### 腾讯云接口限流

日常 SCF 资源变更集中在 Collector，并由本进程限流。CLI 的 `setup inspect-scf`、`attach-scf-vpc`、`invoke-scf` 等诊断入口也直接调腾讯云 API；它们、腾讯云控制台或其他使用同一云账号的程序都会占用平台配额，所以这里的令牌桶不等于账号级的全局限流。

- **腾讯云的口径**：默认按「API + 接入地域 + 子账号」限频，每个接口单独计数；另有主账号限频、IP 限频叠加（阈值未公开），超限返回 `RequestLimitExceeded`。
  同一子账号的不同密钥共用配额。几个接口的默认值：`ListTriggers`、`UpdateTrigger`、`ListNamespaces`、`CreateNamespace`、
  `UpdateFunctionEventInvokeConfig`、`PutReservedConcurrencyConfig` 是 20 次/秒，`GetFunction`、`CreateTrigger`、`DeleteTrigger`、`CreateFunction`、
  `DeleteFunction`、`UpdateFunctionConfiguration`、`UpdateFunctionCode`、`ListFunctions`、`Invoke` 是 100 次/秒。
- **令牌桶**：每个（云账号、接入点、接口）一个进程级令牌桶，速率取官方限频的 75%（20 次/秒的接口为 15，100 次/秒的为 75；未登记的接口按 15），
  **突发容量为 1**——桶初始是满的，突发容量等于速率时第一秒可放行约两倍速率，仍会超限。限流器以云账号标识为键（不是 SecretID），轮换密钥后新旧客户端共用同一组令牌桶。
  所有 SDK 调用统一走 `Client.call`，单测会扫描 `tencentscf` 包，禁止绕过它的调用。
- **配置**：Collector `config/app.yaml` 的 `cloud.tencent_scf.api_rate_limits` 可按接口名覆盖速率（次/秒），值必须大于 0 且不超过官方限频，接口名必须是登记过的 SCF 接口，否则 Collector 启动失败。
  例如 `ListTriggers: 10`。配置文件不随二进制更新，要改需手工编辑（见[部署与运维](../部署与运维.md)）。
- **限频重试**：遇到 `RequestLimitExceeded`（请求在服务端被拒、没有执行，对 Create 类接口重试也安全）最多再试 2 次，每次等待 0.5～2 秒的随机时长，并重新取令牌；
  退避会越过调用方截止时间时不再等待，直接返回限频错误。等令牌的时间超过截止时间时请求不发出，返回 `ErrRateLimitWaitExceedsDeadline`。
  这两种都算瞬时错误，由外层把整个操作从头再做（一次操作最多 3 遍）。
- **定时器确认轮询**：创建、更新定时器后，等云端读回一致的轮询按 500ms、1s、2s 退避，总预算 5 秒，预算通过局部 ctx 传给每次查询；
  最坏情况从约 25 次 `ListTriggers` 降到 4 次左右。
- **指标**（只在 Collector 本地 `/metrics` 暴露，不进 Monitor）：`moox_collector_tencent_api_wait_seconds{action}`（取令牌的等待时间直方图）、
  `moox_collector_tencent_api_throttled_total{action}`（被腾讯云限频的次数）。日志里 `被腾讯云限频` 的 WARN 带接口、尝试序号和 RequestId。
  正常情况下限频次数应接近 0；每小时仍有大量限频，说明有别的调用方在用同一个云账号，或需要调低 `api_rate_limits`。

## 11. 运行状态

控制台“采集任务 → 运行状态”（`/collector/tasks?tab=status`）回答“采集有没有问题”，数据来自 `GetCollectorStatus`：

- **总体等级**取计划层面与各数据集中最严重的一级：计划下发失败为异常，未生效计划超过 30 分钟为需关注，
  重新登记 30 分钟后仍没有新计划接手为异常（这期间数据集没有时间线、数据集健康里看不到，实时提交仍因快照缺失被拒绝）。
- **数据集健康**（只列正在采集的数据集，异常排前）：

  | 条件 | 等级 |
  | --- | --- |
  | 自动巡检超出预期 1 小时（已停） | 异常 |
  | 自动巡检超出预期 15 分钟（落后） | 需关注 |
  | 24 小时内有失败分块 | 需关注 |
  | 历史扫描发现未确认的缺口，或扫描失败 | 需关注 |

  “自动巡检”列说的是自动补漏有没有跟上，不是数据延迟：正常时只显示“已查至 HH:mm”（水位），超出预期时才带上
  “落后 N 分钟”或“已停 N 小时”，原因文案说明“期间的缺口暂未（不会被）自动补上”。超出预期的口径
  （`inspect_lag_seconds`）：自动补采只扫到 `alignDown(now - 迟到容忍 - 一个周期)`（不含），水位之后第一根未检查的 K 线
  从 `alignUp(水位)` 开始，到 `它 + 两个周期 + 迟到容忍` 才进入巡检范围，从那一刻起算；1h 等低频数据集整点刚过、
  下一个扫描槽到来前的正常等待不算落后。数据是否齐全看“24h 实时缺口”和“历史缺口”。
  24 小时实时缺口与已确认的行情源缺失只展示，不影响等级。
- 数据集与函数服务的数据集都显示展示名（所属采集任务名），悬停可看数据集 ID。
- **函数**：上百个函数可按名称、数据集或展示名搜索，按地域、市场筛选，只看下发中与退役中的函数；普通分页，每页行数按可视高度自动适配（至少 8 行，不出现表格滚动条）；“触发”列把 cron 翻译成中文（如“每 5 分钟”“工作日 09:30”，翻译不了时原样显示，悬停看原文）；点击函数名弹窗展示详情：地域、触发、市场，以及按数据集分组、可搜索的标的列表与生效时间（`CollectorFunctionStatus.dataset_subjects`）。

补采作业在独立的“补采” Tab（`/collector/tasks?tab=backfills`）：按数据集与需关注、全部、手动、自动筛选，
可检查缺口、新建补采，详情里看失败分块、取消或重试失败分块；有进行中的作业时每 5 秒刷新。筛选与打开的作业写在 URL 里
（`dataset`、`segment`、`job`），运行状态页新建的作业会带着 `job` 跳过来直接展开详情。
- 标的变更记录在右上角“变更记录”里查看（活动日志 `collector.subject_change`）。

## 生命周期、暂停与恢复追赶

Collector 有模块级生命周期（运行、暂停、恢复追赶；接口是 CollectMgr 的 `GetLifecycle`、`ControlLifecycle`（读给管理台与 moox-cli，写只给 moox-cli），状态文件 `lifecycle.json` 在数据库旁）。重启后载入的是暂停时，生命周期一开始运行就把系统暂停开关重新落到全部空间上。

- **暂停**：全部采集计划空间置为系统暂停（和 `collector fetch-plan` 的手工暂停是同一张表的两列，效果相同、互不覆盖）：SCF 定时器停用、collector-stream 停止订阅、不再认领补采分块。
  暂停要等所有空间的 SCF 定时器停用确认、在途的补采分块结束才算真正停下（等待上限 5 分钟，超时返回「已暂停，但在途操作没有结束」，这时系统暂停已经生效）。
- **恢复追赶**：进入**恢复模式**——暂停开关仍在（实时定时器与订阅保持关闭），但补采调度运行：对暂停区间 `[暂停时间, 现在)` 的全部数据集检查缺口，有缺口且没有未结束的作业时提交一个补采作业，
  缺口太多时缩成最早的一个窗口逐窗口推进。追平：区间内没有缺口（已确认行情源缺失的周期扣除并单独统计为「不可补」）且没有未结束的补采作业。
  **追赶目标是固定的**：恢复开始的时刻 T0，补采只补 `[暂停时间, T0)`。恢复模式下实时采集仍然关闭，如果目标跟着当前时间走，补采速度（每个标的至少一个分块）赶不上缺口增长的速度，永远追不平
  （2026-10-22 线上演练遇到：40 分钟没有收敛）。T0 之后到放行之间的缺口由放行后的自动补采填。
  恢复模式只在进程内存里：追赶中重启会回到暂停，再 resume 即可。
  已知差别：追赶中重启回到暂停时，`moox-cli system resume` 会把 Collector 当成“已自行放行”接着往下走（`packages/sysctl` 按自放行模块处理，暂停状态的追赶进度也报追平）。
  下游没有因此被提前放行，是因为因子引擎的追赶目标按墙上时钟算，7×24 的加密任务在 Collector 没放行时追不平；如果只剩交易时段的任务、又在休市时执行恢复，下游会被真的放行。
  遇到 Collector 在恢复期间重启，重新执行一次 `system resume`。
- **放行**：暂停区间补齐后清除系统暂停开关（之前手工暂停的空间保持暂停，要用 `collector fetch-plan resume` 单独恢复），对账协程重新启用定时器，恢复实时采集。放行时清系统暂停失败只记日志（`collector_lifecycle_release_failed`），留下的系统暂停要再走一遍 `system pause` / `system resume` 才能清掉。采集只拉取和写入行情，没有下单、发目标这类副作用，所以**追平后自行放行，不等系统恢复的栅栏**
  （`moox-cli system resume` 里只有因子、Trade、策略等有副作用的模块等栅栏）；等栅栏期间采集一直关着，这段行情又成了新缺口。

## 市场数据文件编在二进制里

各市场的 `market.yaml`、`route.yaml`、数据源运行参数编在 Collector、云函数、`collector-stream` 的二进制里，未登记的市场一律报错。
本文里写的 `config/markets/<市场>/…` 都是相对 `modules/collector/` 的路径（仓库和产物包里是 `modules/collector/config/markets/<市场>/`，由 `config/markets/embed.go` 编进二进制）；
仓库根目录的 `config/` 只有初始化种子 `config/setup/`，部署和运行都不从磁盘读这些市场文件：

- 覆盖内置路由和数据源运行参数的环境变量只有 `MOOX_MARKET_CONFIG_DIR`：它指向一个与 `config/markets` 布局相同的目录
  （`<市场>/route.yaml`、`<市场>/sources/<数据源>.yaml`），目录里有的文件优先于内置内容，没有的仍读内置内容并打一条警告日志；
  它覆盖不到 `market.yaml`，`market.yaml` 始终读内置的。
- 部署配置 `[scf_plan]` 里 stockcn 的 `fetch.not_before_ms` 不小于 800（内置默认就是 800，没有覆盖过就不用管）。生成采集计划时会校验它不小于路由文件的结算延迟
  （云函数和本地执行端都校验），小了会报错、整个空间的计划不再更新（已有的函数照旧运行）。
- stockcn 标签 `market_type` 为 `index` 或 `convertible_bond` 的采集任务采不了：这两个品种的数据源在行情源目录里都是 `catalog_only`（没有做过行情验收），
  取数时逐项报 `source is not enabled`。代码过得了 A 股标的规则的标的（例如 `399xxx.XSHE`）会进采集计划、建出云函数，然后每期失败；
  过不了的（例如 `000300.XSHG`、`113050.XSHG`，标的规则按股票代码段校验归属的交易所）在生成计划时就被跳过。有这类启用中的任务就先停用。
- 各空间都在登记的市场里（现在是 `crypto`、`stockcn`、`stockhk`、`stockus`）。其他空间下的采集任务、合成任务、标签同步、`moox-cli` 的序列导入直接报“市场未登记”。

已知差别（只影响手工拼出来的、字段不全的取数请求；采集计划和补采构造的请求这几项都是齐的，不受影响）：

- 请求没写 `provider` 时，单一来源的市场直接报“行情源目录里没有……数据源”，不默认用币安。
- 请求的 `instrument_type`、`market_type` 都没写时按市场的默认品种取（crypto 是现货），不按数据集 ID 猜品种。
- 请求没写 `market_type` 时，crypto 行的 `series_tag` 里没有 `market:<品种>` 这一段。

其他已知差别：

- **强制补采的分块失败后会退回重试**：一共执行 5 次都失败才记失败（第 3 节）。这不只对港股、美股的整天重取生效，crypto、stockcn 手工 `kline backfill --force` 的分块同样如此；原来失败一次就记失败。
- **stockcn 指数、可转债任务的 `source_id` 变了**：默认 `source_id` 改查行情源目录，指数是 `index_http`、可转债是 `convertible_bond_http`；原来写死的表给的都是股票的 `stockcn_http`。这两个品种本来就采不了（见上文）。
- **改 `market.yaml` 要重新发布**：允许迟到时间、出口探测方式、收市后整天重取、采集计划默认参数都在 `market.yaml` 里，`MOOX_MARKET_CONFIG_DIR` 覆盖不到它，改了要重新构建并发布 Collector 和云函数代码包。
- **通达信端口、币安限速预算仍写在代码里**：通达信的端口 7709（`marketfetch/route.go` 的 `providerPort`）不读数据源配置；采集计划的限速预算估算（`fetchplan/plan_ratebudget.go` 的 `EstimateRateBudget`）只算币安，其他数据源不估算。
- **余额对账检查要停报 24 小时后才收尾**：Trade 停止上报余额后，检查先按指标过期判失败并告警；序列过了 24 小时被清掉后，检查转为“不再检查”，告警随之恢复。原来会一直告警。
- **新增一个市场要登记五处**：行情源目录（`internal/sources/catalog`）、规则包的显式引用（`internal/marketwiring/handler.go`）、`packages/barclock` 的市场表、`packages/marketcalendar` 的内嵌日历（交易时段市场）、`config/markets/<市场>/market.yaml`。漏一处由 `marketwiring` 的测试 `TestEveryCatalogMarketIsFullyRegistered` 报出来。

东方财富 K 线数据源的已知差别（A 股、港股、美股共用一份取数代码，见 `sources/eastmoneykline`；美股的日期区间规则与别的市场不同，见第 4d 节）：

- **日内时间标签只认 `YYYY-MM-DD HH:MM`**：上游改了格式，这只标的整次请求报协议错误。A 股会回落到路由里的其他数据源；
  港股回落到腾讯分时合成的 5m（近似值，见第 4c 节）。
- **港股收市竞价期间补不了当天的任何一根**：约 16:00:28～16:09:28 之间，16:00 这根的收盘价是收市竞价的参考价，经常超出它的最高价、最低价，
  过不了开高低收校验。东方财富按日期整天返回，一根不合法整次请求失败，所以这段时间补当天的哪一根，这只标的都失败；
  错误归为 invalid，本次调用内不重试、也不回落到腾讯（invalid 不在可回落的错误里）。自动补采 16:02:30、16:07:30 两轮扫描落在这段里，要到 16:12:30 那轮才补上。
  失败的作业不会卡住自动补采，但当天有缺根时，状态页的“24 小时内补采分块失败”会出现。
- **只有一个主源的路由，熔断阈值不低于单一来源的口径**：单次调用内同一数据源连续失败“候选链长度 × 每源尝试次数”次就不再用它
  （A 股 1m、5m 是 12），同时在途的请求数也以此为上限。只有一个主源时（港股、A 股 1d，不论有没有备源）没有同级的来源可换，阈值取它与
  “每源尝试次数 × 并发”的较大值（港股 max(2 × 3, 3 × 4) = 12），开头几次断连不会让整批其余标的不再请求主源、全部落到备源。一只标的的请求断连后，在本次调用内立刻重试，连同第一次最多 3 次
  （`MOOX_FETCH_HTTP_MAX_ATTEMPTS`），不等待；断开的连接不再使用，重试用连接池里的空闲连接，没有就新建。
  港股一期里某只标的在东方财富 3 次都失败、或东方财富连续失败满 12 次（之后本次调用不再向它发请求）就回落到腾讯；腾讯也失败或函数的取数时间用完才算失败，由下一轮自动补采补。
- 测试样例里 00836“14:50:05 时刚收盘那根仍是最后一根”的时刻是构造的：返回内容取自 2026-11-12 14:49:57 的实测取样，
  那次实测在 14:49:57 到 14:51:09 之间没有取样。

## 已知限制

- **在管理台删除过的币安只读 Key 用 `setup init` 不能重建**：`setup init` 不重建在管理台删除过的密钥（见 `modules/admin/internal/service/setup/exchange_keys.go`），
  密钥管理页新增的密钥 ID 是随机的，Collector 只读固定 ID `exchange-binance-production-readonly`，换名称也补不上。删除过之后币安现货下架检测一直跳过（关注项 `delist_readonly_key_missing`），
  现货下架只能用 `moox-cli collector delist register` 或管理台「事件中心」“事件”页签里“标的即将下架”一行的“手工登记”登记。
- **港股的备源是近似值、只能取当天**：东方财富限流或断连时由腾讯分时合成的 5m 顶上（成交量偏大、开高低是近似值）；腾讯也失败时等补采补齐，历史缺口只靠东方财富，只能回看约 23 个交易日（第 4c 节）。
- **港股 5m 合计少于日线**：5m 不含开盘竞价和碎股的成交，成交量合计比日线少 4%～17%，用 5m 合成日线成交量会偏小。
- **港股 16:00 这根先写后改**：16:00:05 写入的是连续交易时段的值，约 16:15 的整天重取之后才是含收市竞价的最终值；因子会重算，中间已经发出的策略信号不重算。东方财富偶尔返回的异常值如果被实时那一期取到，也要到整天重取才改正。
- **港股收市后的整天重取不存状态**：Collector 在 16:15～16:20 之间重启会重复提交一次；这 5 分钟整段没在运行、或提交时出错到这一轮结束都没成功，当天就不重取，要手工 `kline backfill --force`。重取的分块遇到函数报失败会重试，5 次都失败才记失败，之后不再自动重试，要看补采作业列表并手工 `kline backfill-retry`。半日市那天收市竞价是否同样并进 12:00 这根还没有实测（最近一次是 2026-12-24）。
- **美股的已知差别**集中写在第 4d 节“已知差别”：没有备源、盘中开盘价多数等于上一根收盘价、107 记为 `XASE` 不准确、收盘那根先写后改并在收市后量还会缓慢增长（`refetch_after_close_minutes: 20` 按实测定下）、半日市的并入时刻还没实测、启用前要把线上 `subject_sync.fetch_timeout` 改成 `150s`。
- **已有标签的 `builtin` 改不了**：只有新建标签时能定下是否内置（种子导入带 `seed`，见[存储](存储.md)），之后 `UpsertTag` 不改它。不带 `seed` 用 `metadata tag upsert` 建过 `hk_hsi` 的环境（第 4c 节第 4 步对已有的 `hk_hsi` 不起作用），这个标签是非内置的（可以删除，Monitor 也不巡检），重跑 `setup init` 不会改过来，要在 Storage 元数据库里手工改 `t_tags.c_builtin`。
- **Storage 或网关短时中断会让强制重取很快记失败**：中断期间正在跑的强制重取分块每次调用都立刻失败，几秒内就把 5 次重试用完，作业记失败；恢复后用 `./bin/moox-cli collector kline backfill-retry --space-id stockhk --job-id <作业 ID>` 重跑失败的分块。
- **港股的整天重取作业与手工作业混在一起**：来源记为 `manual`、类型 `force`，在补采作业列表里和手工提交的强制补采分不开，按手工作业保留 30 天（每个交易日一个作业、190 个分块）。
- **港股交易日历过期后每分钟报一次警告**：日历覆盖期用完之后，整天重取每轮对账都算不出收市时刻，Collector 每分钟打一条 `collector close refetch failed` 的 Warn，直到更新日历并重新发布；此时采集计划本身也已经拒绝建新计划。
- **用命令建港股任务要带 `--all-output-fields`**：`collector task create` 的 `--output-field` 默认是现货、永续行的字段，不带这个开关建出的港股数据集缺 `amount` 等股票行的字段；命令只打一句提示，任务照样建出来（第 4c 节“上线”）。
- **港股只支持 5m**：1m、1d 的采集任务能建成功，但运行时会失败（港股数据源只声明了 5m）。
- **港股标的的名称和属性不会刷新**：标的由标签同步创建，没有全市场标的同步去更新；成分名单来自腾讯，不是指数公司，季度调样后人工核对一次成员数。
- **附加字段只能在建任务时选全**：改任务只能减少输出字段。要加字段就新建采集任务和对应的因子任务，旧任务的历史不会带上新列（第 4a 节）。
- **附加字段的空值不回填**：来源当时没有值的根这一列为空，来源后来补上也不会自动重写；要重写用 `kline backfill --force`。没有申万记录的股票按行业分组时计入策略的缺数占比。
- **A 股日线次日 08:00 才有**：交易日 D 的日线在北京时间 D+1 日 08:00 采集，用日线做附加来源的日内策略，收盘那一根的结果在次日开盘前给出（第 4b 节）。
- **A 股日线实时失败要隔一天才自动补**：自动补采在 D+2 日 08:00 之后才扫到 D 日的日线，期间策略按缺数处理；急用时手工 `kline backfill`。
- **附加来源报错会让整行写不进去**：内置的“A 股日线（复权、行业、财务、换手率、股本）”把五个来源的字段放在同一个任务里，任何一个来源当天报错，这只股票当天的日线行（包括开高低收）都不写，等隔天自动补采。内置的纯日线任务“A 股 K 线 1d”不带附加字段，不受影响。
- **带 `funding_rate` 的任务深度检查不再检查这一列**：`kline check --deep` 只要求基础字段每根有值，附加字段（包括 `fill=zero` 的 `funding_rate`）不在检查范围内，这一列缺值要另外抽查数据。
- **采集方式只有三个值，没有“推送加云函数补采”**：`stream` 的数据集补采只走 `collector-stream` 的本地执行端，它不在线时补采等它恢复；要用云函数补采就把任务切到 `scf`。
- **没有 `--force`**：`collector-stream` 心跳超时（180 秒）时，不往它上面切数据集的计划不等它确认（第 3a 节）。它如果其实还在写 Storage，生效周期附近同一根 K 线可能混着两个来源的字段值；
  周期不会写错，完成判定不会错。Collector 刚启动的 180 秒内不按离线处理。
- **采集方式跟着任务走**：清空重装后任务按内置种子重新写入，采集方式回到市场默认值（crypto 是 `stream`，其余是 `scf`）；不重装时切换过的任务保持当前的采集方式。
- **删任务不清时间线**：删掉任务后，到下一份计划生效、时间线写入“停止采集”之前，检查与补采仍会碰这个数据集并告警。有未生效的计划在等旧窗口结束时，这段时间可达几小时。与时间线拆表之前相同。
- **采集计划记录不清理**：每次标的变更或交接多一行（每行约几十到几百 KB，一年几十 MB）。补采每轮调度（以及每个分块完成后的补位）把全部记录读出来解码一次，本轮认领的分块共用，不跨轮缓存。
- **备用来源期间不移出成员**：`cn_a_share` 改用新浪时，退市的旧代码、新浪还没收录的新股都留在标签里，要等东方财富恢复后的下一次同步才按完整快照移出；退市代码已由交易状态检测标成 delisted，不进采集计划，不受影响。
- **东方财富把北交所记成市场 0**：clist 的 `f13` 对北交所与深交所都是 0，全部 A 股快照按代码（4、8、9 开头）把它们认成 XBSE。
- **东八区主机上部分统计窗口偏 8 小时**：Collector 的 SQLite 按本机时区写时间文本，按 `>= since` 字符串比较的统计（运行状态页的健康窗口、发件箱积压的 SQL 统计）
  在东八区主机上偏 8 小时，只影响显示；补采租约的写入和比较都用 UTC，不受影响。线上 Collector 在控制机，按 UTC 运行。
- **补采读计划记录时持着认领锁**：读出并解码全部计划记录挪进了补采的 `Tick`，在串行认领的锁（`tickMu`）里做。计划记录很长时每次 `Tick` 多持一会锁，调度节拍与分块完成后的补位要排队等它。
- **时间线读取随标的变更次数增长**：检查、自动补采、历史扫描、收盘重取、健康度每次读该空间的全部时间线行再重放，每次标的变更或交接多几行，读取量随之增长（只有重新登记会清掉）。
- **计划等窗口结束期间不校验被改动的函数**：采集计划等旧周期窗口结束的这段时间（1h 最长约一小时，日线最长约 24 小时），只对不受这份计划影响的函数做云端读回校验；被这份计划改动过的函数在计划收尾之前不读回，云端配置被改或函数被删要到收尾时才发现。
- **日线计划收尾前不能生成新计划**：采集计划要等旧周期的窗口结束才收尾，日线的窗口结束是下一个 UTC 零点（北京时间 08:00）加允许迟到时间。空间里有日线任务的计划没收尾时，停用任务、改任务、标的变化都要等到那之后才生成新计划并生效，最长约一天。等待期间对账按正常上报，Monitor 不告警。
- **延期披露的公司补采时会提前用上新一期财务**：披露日取公告日与法定披露截止日中较早的一个。最近四期里延期披露的公司，补采时从法定截止日的下一个交易日起就用上新一期，早于真实披露；实时采集时来源在真实披露前还没有这一期，不受影响。
- **少数标的没有复权因子**：新浪复权接口对少数标的返回空列表，这些标的的 `adj_factor` 一直为空。
- **日线的缺口根数与补采写入行数偏大**：完整性检查的缺口根数、补采分块的写入行数按自然日计，包含周末和节假日。
- **管理台把日线键显示成 08:00**：日线的行键是 UTC 零点，管理台数据页按 UTC+8 显示成当天 08:00；回放截断后的区间终点同样显示为 08:00。
- **A 股日线行的 `close_time` 是“行键 + 24 小时”**，不是 15:00。
- **A 股日线超过约 8 年的补采没有验证**：通达信声明的日线回看是 10 年，财务一次请求的期数随区间变长而增加（实测 40 期能一次返回），更长区间的补采没有实际跑过。
- **市值和估值没有历史**：股本（`total_shares`、`float_shares`）来自只有当日值的选股器接口，开通之前的日线行没有股本，内置的市值、估值因子在那之前为空。不用“收盘价 × 资产负债表的股本”补历史：那个股本是按面值计的金额，面值不是 1 元的股票会错；送转后股价立即下调，而它要到下一期报表才更新。
- **平日某天没采到股本就补不回来**：隔天补采时选股器已经是下一个交易日的值。内置的市值、估值因子沿用最近 20 个交易日里的股本；直接读 `total_shares`、`is_st` 这些列的策略按缺数处理。
- **财务历史用的是重新列示后的数值**：较早的报告期，接口只给后来作为对比数重新列示的值，数值可能与当时首次披露的略有不同。
- **财务重取会变**：同一根日线，实时写入的是首次披露值；一年后用 `kline backfill --force` 重取，得到的是重新列示后的值，生效日也可能变成法定截止日。复权因子和申万行业重取不变。
- **财务生效时间有偏差**：较早的报告期一律按法定截止日生效，多数比真实披露日晚；延期披露的公司反而比真实披露日早。披露当天收盘后才公告和盘中公告不区分，统一从下一个交易日起用。
- **滚动每股收益是近似值**：按“本期 + 上年年报 − 上年同期”算，期间的股本变化没有调整。
- **申万行业只有代码，没有中文名**；2021 版分类之前的旧行业代码原样写出，不换算成新代码。
- **A 股附加字段只保证沪深 300 的规模**：财务每只股票每天三次请求，沪深 300 约 900 次；全市场约 1.5 万次，没有验证。不含北交所、基金、可转债、指数。
- **云函数的云上状态只在内存里**：Collector 重启后到第一轮之前，运行状态页“云上状态”一列为空；运行中的空间第一轮启用定时器时会读回已生效计划里的全部定时函数（暂停中的空间在停用确认时读回），这一列随之有值。未生效计划里新建的函数、补采函数与计划外函数要等到下一次读回（最长 1 小时）或手工列出云函数。重启时正在执行的云端操作不续跑，下一轮从读回的状态重新开始（Ensure 先读云上状态，做完的部分不重做）。
- **计划外的同前缀函数只停定时器、不删除**：读回时按本空间的命名格式（前缀、配置里的市场与地域、三位以上序号，并排除其他已配置空间按同样规则能生成的名字）找出不在计划里的函数，只停定时器，要人工删除；它们占着函数个数与命名空间配额，配额超限时对账报 `quota`。配置里已经去掉的市场、地域下的旧函数不在识别范围内。扫描覆盖地域里的全部命名空间，“在计划里”按（地域、命名空间、函数名）判断：命名空间配置改过之后，旧命名空间里的同名副本也算计划外；补采函数另按补采前缀扫描，命名空间、市场的第一个地域或 `backfill_region` 改过之后留下的补采函数旧副本同样列为计划外（它没有定时器，不用停）。所以同一个云账号里不要有另一套部署用相同的空间 ID，否则它的函数会被当成计划外停掉，用 `collector function delete` 按前缀删时还会被删掉。定时器已经停用的计划外函数，之后的读回不再重发停用。
- **接管旧函数时有几秒是新代码配旧环境**：接管云上已有的同名函数时它的定时器还开着，换代码与改环境之间这几秒触发的调用可能报计划解码失败，缺的周期由自动补采补上。
- **代码包只按包名取最新**：不能固定用某个包 ID；每个包名只留最新 3 个可用包（每天清理一次），回退到更早的版本要重新上传。
- **恢复时有一个函数升级失败，整个空间都不启用定时器**：启用定时器之前要求全部函数都在最新代码包上（环境的编码格式随代码版本变化），升级没成功之前每轮重试，期间这个空间不采集；升级失败按 `cloud`（或 `quota`）报对账失败。解除：先看 Collector 日志里升级失败的原因；修不好就用 `moox-cli collector function delete` 删掉这个函数，下一轮其余函数照常启用，随后对账按最新代码包重建被删的函数。
- **补采函数的外部入口变了是就地改写环境**：由 Ensure 按当前身份改写环境，函数不重建。
- **`collector function list` 把还没建出来的补采函数算进 `drift_count`**：补采函数按需创建，一个市场还没做过云函数补采（或函数被删掉）时云上没有它，读回是“不存在”，就被算作与期望不一致，`--drift` 也会列出它（`kind` 是 `backfill`）。不代表采集有问题，第一次补采时自动建出来。
- **空间没启动时它在云上的定时函数被当成计划外**：空间还没有 `setup start`（没有启用的任务、没有计划）时，云上已有的同名定时函数会被 Collector 判为计划外并停掉定时器，函数本身留在云上；下次启动这个空间时 Collector 按名字接管，不用重建。
- **删云账号要先清掉它在云上的函数**：账号还被 `scf_plan.cloud_account_id` 引用、名下还有代码包、或配置过的地域里还有它建的 `moox-fetch` 函数时，删除被拒绝。账号已经不被 `scf_plan` 引用时，`collector function delete` 只删当前配置账号下的函数，删不到旧账号的：用 `moox-cli setup inspect-scf` 查出这些函数，在腾讯云控制台手工删除后再删账号。
- **未生效计划期间删掉的函数靠内存里的记录重推**：用 `collector function delete` 删掉计划里的函数后，下一轮对账去掉它在本阶段的确认、按阶段期望重建（不受计划影响的函数由下一轮读回重建）。这份记录只在内存里，删完到下一轮之间 Collector 重启的话，已确认的函数要等计划收尾（或计划生效后的读回修复，最长 1 小时）才重建。
