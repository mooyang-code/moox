# 管理后台（Admin）

Admin 是 MooX 的控制面：负责登录认证、组件目录与主机登记和部署、密钥与 PKI、控制台终端（SSH）和系统初始化，
同时是浏览器的唯一入口：Admin 自己在 `9527` 提供 HTTPS、管理台静态页面和根证书下载，并把 `/api/admin/*` 转给各后端服务（管理网关）；
还通过网关控制把登记的主机、部署与公钥作为快照下发给每台机器的[主机网关](主机网关.md)，路由由网关自己算。

代码位置：`modules/admin`。

## 1. 进程与端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| 浏览器入口 | `9527` | HTTPS（HTTP/2 与 HTTP/1.1）：管理台页面、`/ca/*` 根证书下载、浏览器 API `/api/admin/*`；Admin 自己用标准库监听，见第 3 节 |
| `Auth` | 进程内（`port: 0`） | 登录、会话、用户信息（纯控制台内部服务，仅注册到进程内 `LocalDispatcher`，无独立 TCP 端口） |
| `Ssh` | 进程内（`port: 0`） | 按登记主机建立终端会话（WebSocket）、SFTP（纯控制台内部服务，仅注册到进程内 `LocalDispatcher`，无独立 TCP 端口） |
| `SecretMgr` | `11108` | 加密保存的密钥（云账号、交易所、EventBus 等）与初始云密钥写入 |
| `SysDeploy` | `11109` | 组件目录、主机登记（中文名、可达性、控制台 SSH）、组件部署与网关路由状态 |
| `GatewayControl` | `11112` | 主机网关拉取快照（主机、部署、公钥，全部主机同一份），拉取兼作心跳（loopback 原生 tRPC，其他主机经 control 的主机网关 `11003` 到达，独立 `SerializationTypeNoop` 与 64 KiB 上限） |
| `ActivityLog` | `11113` | 内部组件追加活动日志，控制台按空间或全局查询 |
| 健康检查 | `11010` | `/healthz`、`/readyz`、`/metrics` |

配置已合并为单一 `config/app.yaml`（含数据库、会话、登录锁定、控制台来源与限流设置，由 `yaml.v3` 开启 `KnownFields(true)` 单次加载；另配 `config/trpc_go.yaml`）。主密钥仅由 `bootstrap` 读取/生成并显式传参，不再写入进程环境变量；内嵌的 `servicecatalog` 通过 `sync.Once` 缓存，避免重复解析 YAML。

定时器：`metrics`（30 秒）、`certificates`（每 10 分钟，校验 MooX CA 和各主机的主机证书（主机网关与 EventBus 都用它），到期前 90 天告警；
同时幂等检查 9527 的网页证书，有效且剩余不少于 30 天时无副作用，剩余不足 30 天就重签）。
Admin 不替其他模块清理数据：云函数代码包由 Collector 每天自己清理（见[采集](采集.md)第 10a 节），Collector、Monitor、Storage View 各自按配置保留数据。

数据：SQLite `data/admin.db`（`schema/admin.sql`）；9527 的网页证书在 `data/web-cert/`。浏览器会话和登录失败计数只放在进程内存里。

证书巡检每 10 分钟执行一次（启动时先跑一轮），读取 `MOOX_ADMIN_PKI_DIR` 中的 `ca.crt` 和 `hosts/<host-id>.crt`；默认路径与主密钥文件同目录下的 `pki/`。每轮从数据库读取全部已登记主机，包含停用主机，只检查公有证书，不读取私钥或修复主机证书。同一个定时任务还检查 9527 的网页证书：先只读 `ca.crt` 判断当前内存证书是否由当前 CA 签发、SAN 匹配且剩余不少于 30 天，满足即直接返回（幂等、无磁盘写入、不碰 `ca.key`）；仅在需要重签时才读 CA 私钥 `ca.key`，重签并写入 `data/web-cert/`。检查 CA、自签名、有效期、主机证书签名、服务端用途与登记的 SAN；缺失或异常上报关注项 `certificate_invalid`（critical），90 天内到期上报关注项 `certificate_expiring`（warning），由 Monitor 统一展示、告警与屏蔽。首次部署未签发的主机证书会报告异常，但不阻止 Admin 启动，使部署和续签可以继续，待其他主机证书签发后下一轮（10 分钟内）自动消除告警。EventBus 没有单独的 CA：它用所在主机的主机证书，已在这项巡检里。

`SecretMgr`、`SysDeploy`、`GatewayControl`、`ActivityLog` 四个机器 RPC 服务只在 loopback 提供原生 tRPC（端口 `11108`、`11109`、`11112`、`11113`）；纯控制台内部服务 `Auth` 与 `Ssh` 不监听独立 TCP 端口（服务目录 `port: 0`，拓扑校验与网关路由编译均跳过 `port == 0`），仅注册到进程内 `LocalDispatcher`。健康接口使用 HTTP。机器调用由主机网关验证各自身份，浏览器请求由生成 handler 在 Admin 进程内分派。

## 2. 认证与会话

MooX 是单用户系统，唯一用户拥有全部管理能力，但认证始终开启：

1. `Login` 收用户名和明文密码（HTTPS 保护），用 bcrypt 校验已保存的密码哈希；用户不存在时也对一个固定哈希做一次 bcrypt，
   耗时与密码错误相同，提示也相同。登录接口单独限流（`app.yaml` 的 `rate_limit`）。
2. 同一用户名加来源 IP 连续失败 5 次锁定 15 分钟（`security.max_login_attempt`、`security.lock_duration`），用户不存在也计数；
   来源 IP 取 9527 连接的对端地址，请求头里的转发地址一概不认。
3. 登录成功后生成 32 字节随机会话 ID，放进 Admin 进程内存，用 `Set-Cookie: __Host-moox_session=…; HttpOnly; Secure; SameSite=Strict; Path=/`
   下发，会话 ID 不进响应体。有效期 `session.ttl`（默认 24 小时，从登录时算起，不随使用顺延）；退出时删除服务端会话并让浏览器删掉 Cookie。
   Admin 重启后要重新登录。登录成功写一条全局活动日志（类别 `auth.login`，管理台“日志中心”的活动日志页签选“全局”查看）。
4. 之后每个请求只看 Cookie。RPC 只收 POST；非 GET 请求和终端 WebSocket 握手另外要求恰好一个 `Origin` 头，且等于 `https://<Host>`
   或 `console.allowed_origins` 里的开发来源（只给本机开发经开发服务器代理时用，生产留空，不能写 `*`）。Origin 不对返回 403，
   没有会话或会话过期返回 401，前端只把 401 当成掉线。
5. 终端 WebSocket、文件上传下载、归档下载与预览和页面同源，浏览器自己带 Cookie，鉴权与普通请求相同；SSH 的这几个通道另外要求地址栏里的
   `session_id` 是当前用户建的 SSH 会话（上传也只认地址栏这一份，表单里的同名字段不看）。

服务之间的调用使用调用方的 ed25519 签名（见[主机网关](主机网关.md)），与浏览器会话互不相干；管理台代浏览器调用各业务服务时以 `console` 的身份、用控制机的主机密钥签名；健康检查端口只听本机、不验签。
命令行里要以管理员身份登录管理台的客户端（如 `setup init` 的登录核对）和浏览器一样换取并携带会话 Cookie 与本站 Origin。

## 3. 浏览器入口与管理网关

**入口（9527）**：Admin 用标准库 `http.Server` 在 `MOOX_ADMIN_WEB_LISTEN`（默认 `0.0.0.0:9527`）上提供 HTTPS，代码在 `internal/webserver`：

- **证书**：Admin 用本机的 MooX CA（`MOOX_ADMIN_PKI_DIR`）签一张网页证书，SAN 是控制机地址 `MOOX_ADMIN_WEB_ADDRESS`，有效期 1 年，
  存在 `data/web-cert/`；启动时和每 10 分钟随证书巡检幂等检查，CA 变了、地址变了或剩余不足 30 天就重签，新连接立即用上新证书。主机网关的证书与签名密钥不受影响。
- **协议**：TLS 1.2 起，ALPN 协商 `h2` 与 `http/1.1`。终端 WebSocket 只能在 HTTP/1.1 上升级：Go 默认不开 WebSocket over HTTP/2（RFC 8441），
  服务端不宣告它，浏览器就为 WebSocket 另开一条 HTTP/1.1 连接（有测试保证不宣告）。
- **Host 与安全头**：请求的 Host（去掉端口）必须等于控制机地址，否则 404；每个响应带 `X-Content-Type-Options`、`X-Frame-Options: DENY`、
  `Referrer-Policy: no-referrer` 与 CSP。
- **时限**：读请求头 10 秒、空闲连接 2 分钟，不设读写总时限（下载、上传与终端是长连接；接口时限由下面的管理网关按服务目录控制）。
  停止时先不接新连接，等在途请求最多 30 秒。
- **路由**：`/api/admin/*` 交给管理网关；`/api/` 下其余路径与 `/healthz`、`/readyz`、`/metrics` 一律 404；`/ca/*` 是根证书下载；
  其余是内嵌的前端（`internal/webui`，构建时由 `scripts/build/build.sh admin` 把 `web/dist` 临时拷入），前端路由回退到 `index.html`，
  ETag 按文件内容算，带哈希的 `static/` 文件缓存一年，入口页不缓存。
- **压缩**：静态文件预先压好 gzip；接口的 JSON 响应（1KB 以上）由管理网关自己压缩；终端、文件与归档下载这些原始通道不压缩。

**根证书下载（登录前可用）**：`/ca/root.crt`（MooX CA 根证书，文件名 `moox-ca.crt`）、`/ca/root.sha256`（SHA-256 指纹，冒号分隔的大写十六进制）、
`/ca/moox-root-ca.zip`（安装包：根证书、指纹、各系统的安装脚本和给 Agent 阅读的 `AGENT-INSTALL.md`；`install.sh` 与
`scripts/deploy/install-moox-ca.sh` 一致，由测试保证）。只输出启动时校验过的那一张 CA 证书。入口在管理台“密钥管理”页的“HTTPS 根证书”按钮和登录页的“下载并安装根证书”链接。
安装包经由尚未被信任的连接下载，包内的指纹、说明和脚本都可能被一起替换，所以唯一的可信锚点是用户通过另一条渠道确认的指纹；
`AGENT-INSTALL.md` 要求 Agent 自己计算证书指纹、优先用系统命令安装、不要不加检查地运行包内脚本。初始化电脑上运行 `moox-cli setup trust-browser`
会经 SSH 从控制机取回 MooX CA 根证书（缓存为 `~/.moox/certs/moox-ca-<控制机地址>.crt`）并安装到本机，不经过 HTTPS。
手机同样要各装一次：iPhone 用 Safari 下载后在“VPN 与设备管理”安装，并且必须在“关于本机 → 证书信任设置”里打开完全信任；Android 在“加密与凭据 → 安装证书 → CA 证书”安装。
浏览器之外的客户端：系统自带 curl 和 Go 程序读系统信任库，Node.js 要设 `NODE_EXTRA_CA_CERTS`，Python 要设 `REQUESTS_CA_BUNDLE`，Homebrew 的 curl 用 `--cacert`；不要用 `-k` 之类关闭校验的开关。
全新部署会生成新的 MooX CA，所有设备要重新装一次。

**已知差别**：
- 定期检查网页证书时重签失败（例如 CA 目录读不到）只记一条错误日志，不推送告警；Admin 启动时签不出来则直接启动失败。
  `moox-cli doctor` 目前不检查这张证书，要看到期时间用
  `openssl s_client -connect <控制机>:9527 -servername <控制机> </dev/null 2>/dev/null | openssl x509 -noout -enddate`。证书剩余 30 天起每 10 分钟都会重试重签。
- 归档最新数据预览（`archive/RecentRows`）按原始通道转发，不压缩；接口响应的压缩只有 gzip。
- 服务端 SQLite 没有设 `_txlock=immediate`（`moox-admin-cli` 侧设了）：先读后写的事务只有 `Apply` 一个手工命令，撞上并发写时立即报库忙，重试即可。
- 离线 `moox-admin-cli bootstrap` 与在线 `SysDeploy.SyncTopology` 共用同一份 `SyncTopologyReq` 与入库写入器 `TopologyDAO.ReplaceTopology`，但离线 `bootstrap` 不接触运行中的管理台进程，因此不会主动关闭管理台已有的 SSH 终端会话。
- 网关运行态（已应用哈希、最近拉取时间、反向连接会话）保存在 Admin 进程内存中，不落 SQLite；Admin 重启后由各主机网关下一次拉取（约 5 秒）自然填回，在此之前管理台暂不显示历史心跳。
- 不按空间放行：业务空间只登记在 Storage，管理网关只核对请求头与请求体里的空间一致，不判断空间是否存在、是否停用（Admin 不依赖 Storage）。
  Trade、Strategy、Factor、Archive 也都不判断空间是否存在。页面只让选已有的启用空间；但用 CLI 写错空间 ID、或对已停用的空间调交易、策略、因子接口，
  不会被拒绝。停用空间的实际效果是 Collector 不再采它（Collector 按 Storage `ListSpaces` 的启用名单启停各空间）。
- Storage 不可用时：已经选过空间的浏览器（空间列表缓存在本地）里交易、策略页面不受影响；新浏览器首次打开要等 Storage 恢复才能选空间。

**管理网关**：路径形如 `/api/admin/<服务>/<方法>`：

- **鉴权与限流**：按会话 Cookie 与 Origin 校验（见第 2 节），按方法限流。
- **空间作用域（目录单一声明）**：三档空间策略直接声明在 `packages/servicecatalog/catalog.yaml` 的服务与方法上（省略时默认 `space_required`），管理网关（`internal/console/policy.go`）直接查目录，前端在构建时从同一份 `catalog.yaml` 生成对应策略表：
  - **`global`（纯全局）**：不要求 `X-Space-Id`，也不向下游透传空间上下文（如认证、密钥、主机与部署、云账号、下架名单与解除、生命周期查询、策略定义的 `CreateStrategy`/`UpdateStrategy`/`ListStrategies`/`DeleteStrategy`）；
  - **`space_optional`（空间可选）**：无空间时照常调用，带 `X-Space-Id` 时校验一致并透传下游（如 `GetStrategy`、`ValidateStrategy`、`ListActivityLogs`、`ListFactorTasks`、`ListFactors`、`GetFactor`）；
  - **`space_required`（默认，必须带空间）**：要求携带 `X-Space-Id` 并与请求体里的 `space_id` 一致，网关将其注入下游上下文。
  部分方法只允许机器调用方使用（例如 `EnsureInitialSecret`、密钥明文读取等），浏览器无法调用。
- **转发**：方法与权限由 servicecatalog 定义，Directory 从 Admin 拓扑表生成；自身服务通过生成 handler 在进程内调用，其他服务经共享客户端转发原始 JSON。
- **Storage**：浏览器使用目录中的 `storage` 服务名，经同一签名客户端调用原生 RPC，保留用户、空间和 trace 元数据。
- **原始通道**：SSH 终端和 SFTP、归档分区下载与最新数据预览通过专门的 raw handler 处理 WebSocket 与流式传输。

**为什么用 HTTPS 加私有 CA**：

- 不用纯 HTTP：登录提交的是明文密码，会话 Cookie 带 `Secure` 只在 HTTPS 上发送；密钥管理里新增、修改交易所或云账号的 API Key 时提交的也是明文，
  中间人还能往页面里注入脚本或改掉提交的内容（包括手动下单）。
- 不靠浏览器警告页的“继续前往”：它只放行那一次页面加载，页面里的后台请求新建连接时会在证书校验处失败；而且每次都点“继续”等于接受任何证书，
  真被冒充时分辨不出来。常用的电脑和手机都应安装根证书。前端对网络层失败只显示一条带证书指引的中文提示（`web/src/api/network-error.ts`）。
- 没有采用的替代：域名加公共证书（需要域名，未备案域名做证书校验可能被拦）；Tailscale 一类内网工具（每台设备要装客户端，手机与代理 App 冲突）；
  只在本机监听加 SSH 隧道（每次要开隧道，手机上不现实）。

## 4. 服务目录（SysDeploy）

SysDeploy 是面向少量机器的静态服务目录，不是动态注册中心：

- `t_hosts` 和 `t_deployments` 保存主机与组件部署关系，`t_hosts` 是唯一的主机登记处：除地址、可达性外还有中文名 `c_label` 与控制台终端用的 `c_ssh_port`、`c_ssh_user`、`c_ssh_fingerprint`（端口为 0 表示不开放终端；凭据存 `t_secrets` 的系统密钥 `moox:ssh-host:<主机ID>`，指纹按“地址:端口”首次连接时固定，只认当前登记的端点），servicecatalog 定义方法、端口与权限，按主机编译网关快照和 Directory。主机带可达性 `c_reachability`（`direct` / `outbound`）：出站主机的网关证书加签 `ClientAuth`，经 control 网关反向连接接入（见[主机网关](主机网关.md)第 5 节）。
- 每个服务在每台主机只有一个入口；`enabled` 表示配置启用，不代表健康，健康由 Monitor 按组件的上报判断。
- 服务不自行注册或续约，拓扑由 `SysDeploy.SyncTopology`（在线）和 `moox-admin-cli bootstrap`（离线）共用同一份协议消息 `SyncTopologyReq` 与入库写入器 `TopologyDAO.ReplaceTopology` 写入（离线文件为 `SyncTopologyReq` 的 protojson）；CLI 按主机 ID 同步完整组件部署，主机与部署的启停状态也按 `moox.toml` 整份覆盖；机器的新增、部署、启停与移除只经 `moox-cli`，管理台只读。`SysDeploy.GetCatalog` 除返回原始 `catalog_yaml` 与 `sha256` 供 Monitor/CLI 使用外，同时返回结构化 `ComponentCatalog` 供前端直接消费。EventBus 凭据工具从有效主机与 EventBus 部署派生地址。
- 主机网关通过原生 GatewayControl 获取快照，请求里带上已应用的哈希，`PullSnapshot` 以只读 SQLite 事务读取拓扑与公钥，并把各主机网关的已应用哈希、拉取时间与反向连接会话记在 Admin 进程内存中（不落库，已移除 `t_host_gateway_status` 表；Admin 重启后由约 5 秒一次的拉取自然填回，期望哈希由当前拓扑实时算出）；`SysDeploy.GetHostRoutes` 里的路由是 Admin 按同一套规则算出来给人看的，不下发，且仅返回 `t_hosts` 中仍存在的主机。GatewayControl 只听本机回环端口，不自己验签：控制机网关验签后把签名主机写在 `x-moox-verified-host` 头里转进来（它自己直连时也带），服务要求请求里的主机与它一致；见[主机网关](主机网关.md)。

| 服务 | 说明 |
| --- | --- |
| SecretMgr | 密钥表 `t_secrets` 采用**物理硬删除**（`UNIQUE (c_secret_id)`，无软删除列与墓碑表）；全部读写入口（`SecretDAO`、`eventbus_credentials`、`system.go`）统一用 AES-GCM 加密 `c_secret_value` 与 `c_extra_config`（含 OKX `passphrase` 等敏感配置）；接口返回在 RPC 层按 `[]rune` + `•` 单点脱敏（已移除 `trpc-filter/masking` 避免二次打码冲突与多字节截断）；`ListSecrets` 统一使用 `commonpb.Page` / `PageResult` 分页；`EnsureInitialSecret` 仅对机器调用方 `moox-cli` 开放，供 `setup init` 按固定 `secret_id`（如默认腾讯云密钥 `tencent-default`）幂等写入初始密钥（不存在则创建，已存在且一致返回 `unchanged`，已存在但值不同则保留现值返回 `kept`，拒绝 `moox:*` 系统环境绑定密钥）；`GetSecretValue` 仅对 `moox-cli` 开放，按 ID 读取单条明文，浏览器只能看到掩码；`GetExchangeCredential` 仅对 `trade` 开放，服务端校验 `category="exchange"` 且 `status="active"` 后返回对应交易所密钥（主机网关不再为 `SecretMgr` 传递 `X-Moox-Verified-Caller` 特例头）。`GetCloudCredential` 只放行 Collector，读一把云账号密钥：服务端校验类别 `cloud`、厂商 `tencent`、状态启用，任何一项不满足就拒绝、不返回密钥值。`GetReadonlyExchangeKey` 也只放行 Collector，按属性匹配返回只读 Key 的公开标识（`key_id`），不返回密钥值：查找 `category="exchange"`、`provider` 等于指定交易所、`status="active"` 且 `extra_config` 含 `readonly="true"`、环境为 `production`（或兼容旧导入未写 `environment` 字段）的密钥。迁移用 `ExportSecrets` / `ImportSecrets`（服务目录对控制台与 `moox-cli` 开放；操作者有登录用户记用户名，否则记 `moox-cli`）：导出把全部密钥连同明文（属于本环境的除外：主机 SSH 凭据与 EventBus 内部凭据，导入也拒收这些）用导出口令加密成迁移包（`moox.secrets/v1`，口令至少 12 个字符，PBKDF2-SHA256 60 万次派生 AES-256-GCM 密钥，格式与 KDF 参数参与认证），明文只在 Admin 进程内出现；导入用同一口令解开，按 `secret_id` 写入（保留原标识，引用它的配置迁移后仍然有效），已存在时按选择跳过或覆盖，逐个报告新增、覆盖、跳过与失败 |
| Ssh | 纯控制台进程内服务（`port: 0`），按登记主机的 SSH 端口与凭据建立 Web 终端和 SFTP（`SftpList` 强类型返回），不提供主机增删改，也不记录会话日志；只能出站或没有登记 SSH 的主机不能连接 |
| ActivityLog | `AppendActivityLogs` 仅接受内部组件写入；`ListActivityLogs` 为空间可选（`space_optional`），按指定空间或 `global=true` 查询，两者互斥，`since`/`until` 是 Unix 毫秒（0 表示不限），分页响应统一为 `page_result`；表 `t_activity_logs.c_ctime` 存 Unix 毫秒整数（`INTEGER NOT NULL`） |

各服务接口里的时刻（登录过期、用户创建与最后登录、密钥 `created_at`/`updated_at`、SFTP 条目 `modified_at`、部署登记与网关状态、反向连接会话、操作记录）都是 int64 Unix 毫秒，0 表示没有；库表里 `t_activity_logs.c_ctime` 存 Unix 毫秒整数，其余审计列保留 `DATETIME`。

## 6. 命令行

`moox-admin-cli`：

| 命令 | 作用 |
| --- | --- |
| `bootstrap` | 离线初始化：建库、MooX CA、主密钥，按拓扑文件整份覆盖全部主机与部署（含启停状态；多出的删除，签名公钥与 SSH 指纹保留）、登记操作电脑的 `moox-cli` 公钥，决定控制机的主机签名密钥并发布控制机的身份包；CA、主密钥与已登记的公钥只建不改；参数与重跑约束见 [Admin README](../../modules/admin/README.md#离线初始化与恢复) |
| `host-bundle` | 给一台已登记的主机签发身份包：主机证书（每次重签）、根证书；`--current-sign-public-key` 传入目标机上现有私钥的公钥，和登记的一致就沿用，否则（或带 `--rotate-sign-key`）生成新的主机签名私钥并登记公钥，私钥只在包里、Admin 不保留；部署了 collector 的主机另管 `scf-collector` 的私钥。不生成 CA 或主密钥，不修改启停状态 |
| `user ensure` / `user set-password` | `ensure` 创建管理员（用户名已存在时不改动），`setup deploy` 部署控制机时按秘密文件调用；`set-password` 改已有管理员的密码（都从 stdin 读密码），改完把秘密文件里的 `admin.password` 一起改掉（`moox-cli config set admin.password=… --yes`），`setup init` 用它核对登录 |
| `eventbus-credentials ensure / export / export-clients / rotate` | 生成或导出 EventBus 的角色令牌（没有证书：EventBus 用所在主机的主机证书）；`rotate` 轮换一个角色的令牌，`export-clients` 仅导出指定角色的文件（EventBus 所在主机另带 `--server`，多一份用户表） |
| `keys set / list / delete` | 登记、列出、删除不属于主机的身份（`moox-cli`、`scf-collector`）的签名公钥；`list` 同时列出各主机的公钥。Admin 不保存任何签名私钥，一个身份只有一把公钥，再登记就是替换 |

**外部身份与操作电脑**：不属于主机的身份有两个，公钥都登记在 `t_identity_keys`，Admin 不保存它们的私钥。

| 身份 | 私钥在哪 | 怎么登记 |
| --- | --- | --- |
| `moox-cli` | 操作电脑 `~/.config/moox/moox-cli.key` | 首装时由部署控制机的 `bootstrap` 登记；装好之后换电脑用 `moox-cli setup operator --register`（经 SSH 在控制机上替换） |
| `scf-collector` | 控制机 `<部署根>/secrets/scf-collector.key` | 随控制机的身份包签发，Collector 发布函数时写进函数环境 |

- `moox-cli` 的信任根是操作电脑到控制机的 SSH 私钥：能 SSH 上控制机，就能登记一把新的 `moox-cli` 公钥。一个身份只有一把公钥，再登记就是替换，两台操作电脑不能同时用。
- 换操作电脑要带的东西、秘密文件只是初始值（之后以管理台为准，清空前先导出密钥）见[命令行工具](命令行工具.md) 1.1 节与[部署与运维](../部署与运维.md)第 5 节。
- 存储机、因子机的 `secrets/` 下没有 `moox-cli`、`console` 的签名能力：`console` 用的是控制机的主机密钥。
