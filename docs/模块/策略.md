# 策略（Strategy）

Strategy 用声明式 DSL 描述截面选股与固定池择时：每当绑定的 View 有一个周期就绪，就在这一帧数据上
求值，得到组合账户相对总权益的完整目标权重，连同逐标的的解释一起保存，并异步发送给 Trade。
Strategy 不读取账户、余额、持仓和订单，也不接触交易所。

代码位置：`modules/strategy`。设计依据见[策略模块评审与设计](../计划/策略模块评审与设计.md)。

## 1. 进程与端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| `StrategyMgr` | tRPC `11430`、HTTP `11433` | 管理接口；管理台经 Admin 访问 HTTP 端口 |
| 健康检查 | `11431` | `/healthz`、`/readyz`、`/metrics` |
| 指标定时器 | `11432` | 每 30 秒刷新实例的期望数据集并上报指标快照 |

依赖：经节点网关读取 Storage（Metadata、DataView）与 Factor（`GetFactor`）；订阅 EventBus 的
`ViewDataReady`（durable `strategy_view_data_ready_v1`，投递次数不设上限）并发布目标权重事件；
状态保存在 `data/strategy/strategy.sqlite`。

## 2. 核心概念

| 概念 | 含义 |
| --- | --- |
| 定义 | 一份 DSL 文本，按内容哈希 `dsl_hash` 标识版本；出现过的每个版本永久保留 |
| 实例 | 定义 + 一个 View + 可选的组合账户。没有账户的实例是观察实例，只计算不投递 |
| 会话 | 每次显式启用产生一个会话，固化当时的 DSL 版本与绑定解析（`resolved_json`）；进程重启沿用会话，重复启用幂等 |
| 结果 | 每个处理过的周期一行：`ok` 带目标权重与规则状态，`skipped` 带原因；两者都有输入摘要 |
| 解释明细 | 各规则预期集合中每个标的的最终阶段、分数、名次、权重与原因 |
| 回放 | 在 View 的历史数据上逐期求值、用现货理论账本模拟成交的研究任务 |

策略时间统一使用 `bar_end_time`（已闭合 K 线的结束边界）。实例的周期由绑定 View 的频率决定，
DSL 的 `bar` 只是可选断言。

## 3. DSL

下面的示例只用因子库已有的列，可以直接绑定 Binance 现货分钟因子结果 View
（`view_factor_dasftksvjhj2jom4vhd0_1m`）：

```yaml
name: binance_spot_momentum
bar: 1m                       # 可选断言：与 View 周期不一致时拒绝启用

universe:                     # 策略级默认标的池，省略即全部
  min_age_bars: 240           # 标的在 240 根之前已有数据才参与
  exclude: [BTC-USDT]

rules:
  - id: long_momentum         # 稳定标识：规则状态与解释明细按 id 关联
    name: 多头动量选币         # 只用于展示
    type: rank                # 截面选股
    filter: "quote_volume_mean_20 > 20000 && close > 0"
    score: "0.6 * rank(bias_q_20) + 0.4 * rank(quote_volume_mean_q_20)"
    select: {top: 5, buffer: 2}
    weight: {total: 0.8, method: equal, cap: 0.3}

  - id: btc_trend
    name: BTC 上穿均线          # bias_20 = close / MA20，由不大于 1 变为大于 1 即上穿
    type: signal              # 固定池择时
    pool: [BTC-USDT]
    entry: "bars[-1].bias_20 <= 1 && bars[0].bias_20 > 1"
    exit: "bars[0].bias_20 < 1"
    weight: {total: 0.2}

portfolio:
  leverage: 1                 # gross 上限；现货 View 不允许大于 1
  max_weight: 0.3             # 组合级单标的上限，超出部分留现金
  min_universe: 20            # rank 规则进入 filter 的可用标的少于它则整期跳过
  max_missing: 0.2            # rank 规则缺数占（预期 − 年龄剔除）的比例超过它则整期跳过
```

| 字段 | 说明 |
| --- | --- |
| `universe` | `tags`、`exclude_tags`、`include`、`exclude`、`min_age_bars`；只作用于没有显式 `pool` 的规则 |
| `rules[].id` | `^[a-z][a-z0-9_]{0,63}$`，修改 id 等于从零开始 |
| `rules[].type` | `rank` 或 `signal` |
| `pool` | 固定列表或 `{tags: [...]}`；显式给出时不再套用 universe 的标签与黑白名单 |
| `filter` | rank：布尔表达式，淘汰的标的记为 `filtered` |
| `score` | rank：数值表达式；`rank(x)` 与 `zscore(x)` 在通过 filter 的样本上计算，可嵌套 |
| `select` | rank：`top` 与 `bottom` 二选一，`where` 用 `score` 二次筛选，`buffer` 是排名缓冲区 |
| `weight` | `total` 是规则预算；`method` 为 `equal` 或 `rank`（最优 N 份、最差 1 份）；`cap` 是规则内单标的上限 |
| `filter_after` | rank：只剔除不补位，剔除的权重留现金 |
| `holding` | rank：`{bars, offsets}` 分批换仓，与 `buffer` 互斥 |
| `side` | `long`（默认）或 `short`；现货 View 不允许做空 |
| `entry` / `exit` | signal：先对旧理论持仓判 exit，再对候选判 entry，退出优先 |

表达式用 Expr 编写，只能引用 View 的列、`bars[0].<列>`（当期）、`bars[-1].<列>`（日历上紧邻的上一根）、
`instrument_id` 与（仅 `select.where`、`filter_after`）`score`。内置函数一律禁用，只开放 `rank` 与 `zscore`
（仅在 `score` 中）。`rank` 同分取平均名次、单样本记 0.5；`zscore` 零方差记 0；排序以 `instrument_id`
打破平局。时序计算（均线、动量、分位）都写成因子，策略只在截面上过滤、打分、配权。

保存定义时只做语法与结构校验；列是否存在、因子指纹与市场类型在启用实例时解析。编辑器的"试算"与
`ValidateStrategy` 会在选定 View 的最近一期上求值一次，结果不落库。

## 4. 处理流程

```text
ViewDataReady（View, period_time, universe_subject_ids, factors[] 含 definition_hash）
  ─► 找出绑定该 View 的全部启用实例，逐个处理，错误汇总；全部终态落库后才 ACK
  ─► 乱序周期 ─► skipped(out_of_order)；已过有效期 ─► skipped(expired)
  ─► 就绪判定（见下表）
  ─► 读取输入：只读绑定的 View，分页时固定活动索引与修订号，变化即整期重读
        基础集合 U = 事件名单 ∩ 活跃标的
        规则 r 的预期集合 E(r) = U ∩（显式 pool 或 universe 配置）
        年龄剔除 G(r)：E(r) 中不满足 min_age_bars 的标的（每期一次探针查询）
        可用集合 A(r)：E(r) − G(r) 中有行、所需列都有值、且未被所引用因子标记失败的标的
        缺数集合 M(r) = E(r) − G(r) − A(r)
  ─► 纯函数引擎：守门 → rank / signal → 组合合成与约束
  ─► 一个事务写入结果、解释明细与（绑定账户时）待投递事件
  ─► 后台发布 LogicalAccountTargetWeightRequested
```

就绪判定按顺序：

| 情况 | 结果 |
| --- | --- |
| 引用的因子不在 `factors[]` 中，或 `definition_hash` 为空 | `skipped(factor_missing)` |
| `definition_hash` 与启用时固化的值不同 | `skipped(factor_changed)`，需要重新启用实例 |
| DSL 用了 `bars[-1]`，本实例对恰好上一根没有可信的处理记录 | `skipped(previous_version_unknown)`，这条记录保存本期指纹，下一期即可求值 |
| DSL 用了 `bars[-1]`，可信的上一根记录的指纹与本期不同 | `skipped(factor_changed)` |
| 因子本期 `skipped` | `skipped(factor_skipped)` |
| 因子 `degraded` | 继续；失败标的只对引用该因子的规则算缺数 |

可信的上一根记录：同一实例、同一 View、同一 bar 与日历、`bar_end` 恰好早一根、含全部所需因子的指纹；
不限会话，优先当前会话。每次启用或停机之后，用到 `bars[-1]` 的实例因此会多跳过一期。

组合合成：各规则权重相加（做空为负）→ 超过 `max_weight` 的部分留现金 → `gross` 超过 `leverage`、
现货 View 出现负权重或 Σw > 1 时整期 `skipped(config_error)` → 现金 = 1 − Σw。选择阶段合法地选出
0 个标的仍是 ok，表示转为现金；守门（`universe_too_small`、`too_many_missing`）防止池被意外清空。

持有标的缺数即清仓：rank 规则的 buffer 不保留缺数标的，signal 规则把缺数的持仓视为退出，holding
批次把缺数标的移出、份额留现金。

## 5. 失败语义

| 情况 | 处理 |
| --- | --- |
| 解码失败、事件契约错误 | TERM |
| Storage / Factor 瞬时错误 | 进程内重试；同一事件对同一实例超过 `evaluation.attempt_budget` 次后记 `skipped(infra_retry_exhausted)` 并 ACK |
| 终态记录落库失败 | 不 ACK，退避重投，直到落库成功 |
| 提交时发现更新的记录 | 重读后分类：同周期视为重复、更早视为乱序，否则重新求值一次 |
| 求值完成时已过有效期 | `skipped(expired)`，不投递 |
| 列被删除、View 周期或数据集变化、同一标的多个序列 | `skipped(config_error / ambiguous_series)`，实例标记 `degraded`，页面提示重新启用 |

`skipped` 只推进处理记录：不取消任何待投递目标，规则状态只从最近一次 ok 决策恢复，只有新的 ok
决策才替代旧目标。

## 6. 持久化

| 表 | 内容 |
| --- | --- |
| `t_strategy_defs` | 定义：名称、DSL 文本、`dsl_hash`；软删除 |
| `t_strategy_def_versions` | 出现过的每个 DSL 版本，按哈希去重，永久保留 |
| `t_strategy_instances` | 实例：定义、空间、View、可空的组合账户、启用状态、会话、`resolved_json`、健康状态；软删除 |
| `t_strategy_sessions` | 会话快照：DSL 版本与绑定解析、关闭时间 |
| `t_strategy_results` | 每个处理过的周期：状态、跳过原因、DSL 版本、输入摘要、目标、规则状态、摘要、事件数据、投递状态 |
| `t_strategy_result_items` | 解释明细，默认保留 90 天 |
| `t_strategy_replays`、`t_strategy_replay_bars` | 回放任务与每期记录，默认保留 90 天 |

实例只能在停用后删除，定义只能在没有未删除实例引用时删除；会话、DSL 版本与结果不随删除消失，
历史结果的解释始终按当时的 DSL 版本与绑定展示。投递状态只有 `none`（观察实例或 skipped）、
`pending`、`sent`（已被 broker 确认，不代表 Trade 已接受）和 `cancelled`。

## 7. 实例生命周期

- 启用：解析绑定（View → 数据集 → 源数据集的市场类型 → 列与因子 `definition_hash`）→ 编译 →
  写入会话快照 → 绑定账户时向 Trade 认领会话 → 置为启用。市场类型取源数据集属性 `market_type`，
  没有时取其标的范围标签的 `market_type`；现货 View 拒绝 `leverage > 1` 与做空。
- 重复启用不新建会话；绑定账户时会核对 Trade 的所有者仍是本会话。
- 停用：先持久化停用并关闭会话，再向 Trade 释放；释放确认前保留会话，后台每 30 秒对账重试。
  停用不会撤单或清仓。
- 进程启动时先完成未结束的停用握手，再核对每个启用实例仍持有 Trade 会话，最后开始消费事件。

## 8. Strategy 到 Trade 的契约

事件 `event.trade.target.weight_requested`（Stream `MOOX_TRADE`）是组合账户的完整目标快照：

```text
target_id = result_id
instance_id、session_id、strategy_id、logical_account_id
bar_end_time、effective_at（= bar_end_time）、valid_until（= bar_end_time 之后 2 根 bar）
targets[] { instrument_id, target_weight }
```

`target_weight` 是相对组合账户总权益的带符号权重；遗漏的旧标的目标为 0，空列表表示全部归零。
Trade 校验当前授权会话与有效期，按同一会话的 `bar_end_time` 只接受更新的目标，再独立完成数量换算、
账户选择、精度和风控。

## 10. 回放

回放是基于 View 的研究工具，用来比较策略版本，不承诺复现历史上的实时结果：

- 入参：定义、View、`[start, end)`、单边手续费（bps）。第一版只支持现货 View，合约 View 直接拒绝。
- 进程内单工作协程，同一时刻只跑一个回放；按 `replay.chunk_bars` 分段、`replay.page_size` 分页读取。
  进程重启时遗留的 `running` 任务标记为 `failed(interrupted)`，已写入的周期保留，可重新发起。
- 每期的基础集合 U 取该期有行的标的（数据集的全部标的绑定，含已停用的），再按规则得到 E / G / A / M，
  与实时共用同一个引擎；规则状态在内存中跨期传递，从空状态开始。
- 理论账本：按当期 `close` 估值，无价的持仓冻结并按最后价估值；目标金额按总权益
  `W = 现金 + 可成交持仓 + 冻结持仓` 迭代扣费后计算；先卖后买，买入受现金约束、不足时按比例缩减并记
  "目标未达成"；手续费只按实际成交额。skipped 期不成交、不清算；持有标的连续缺价达到
  `replay.missing_price_liquidate_bars` 期后，在 ok 期按最后价清算。
- 报告给出累计收益、年化、最大回撤、平均换手、平均持仓数、跳过周期，并逐项标注局限性。

## 11. 监控

- 每个启用实例登记为 Monitor 的期望数据集（`moox_strategy_dataset_*`，数据集标识
  `strategy_<instance_id>`，间隔 = bar 时长）：ok 计为成功并推进输出水位，skipped 计为未完成。
  停掉上游或连续跳过时，现有的数据集新鲜度检查会告警。
- 模块健康检查 `strategy-targets` 只在 ok 时记成功，在读取重试耗尽、配置错误或因子定义变化时记失败。
- `moox_strategy_period_total{instance_id,result,reason}` 按实例累计处理的周期。

## 12. 配置

`config/app.yaml`：

```yaml
database: ./data/strategy.sqlite
trade:
  gateway_url: ""             # Trade 节点的 HTTPS 服务网关 origin；留空表示只运行观察实例
  target_node: ""
  ca_file: ""
  timeout: 3s
instance_id: strategy-1
eventbus: {...}
factor: {target: ..., target_node: factor, app_id: strategy, timeout: 5s}
storage: {target: ..., target_node: storage-gateway, app_id: strategy, timeout: 5s}
evaluation:
  attempt_budget: 5
retention:
  result_items_days: 90
  replays_days: 90
replay:
  chunk_bars: 50
  page_size: 2000
  missing_price_liquidate_bars: 3
```

Storage 的 `app_key`、`view_app_key` 由部署注入的 `MOOX_STORAGE_PRIMARY_AUTH_SECRET`、
`MOOX_STORAGE_VIEW_AUTH_SECRET` 派生；`MOOX_TRADE_GATEWAY_URL` / `MOOX_TRADE_GATEWAY_NODE_ID` 可覆盖
Trade 接线。Strategy 经节点 HTTPS 服务网关调用 Trade，网关路由 `trade_owner` 只允许调用
`GetLogicalAccount`、`ClaimLogicalAccountOwner`、`ReleaseLogicalAccountOwner`、`RebindLogicalAccountOwner`。

数据库与旧版本不兼容：升级到本版本时停止 Strategy、删除旧的 `data/strategy/strategy.sqlite`（含
`-wal`、`-shm`），启动后自动建表；旧库会被拒绝并提示人工处理。

本地校验 DSL：

```bash
moox-strategy-cli validate strategy.yaml
```

## 附：可导入的 MA 因子

如果更习惯直接写均线，可以把仓库里的 `examples/factors/timeseries/ma.py` 导入因子库：

```json
{
  "file": "ma.py",
  "factor_type": "timeseries",
  "factor_id": "Ma",
  "input_columns": ["close"],
  "outputs": ["ma_20"],
  "params": {"windows": [20]},
  "lookback_periods": 20
}
```

把这一项与 `ma.py` 放进一个目录的 `catalog.json`，用 `moox-factor-mgr-cli import-catalog --dir <目录>` 导入。
加入计算任务并启用后，结果 View 会多出 `ma_20` 列，择时规则可以写成
`bars[-1].close <= bars[-1].ma_20 && bars[0].close > bars[0].ma_20`。成员启用会触发补算，
期间实例的 `definition_hash` 不变；修改已启用因子的参数会改变指纹，实例随之 `skipped(factor_changed)`，
需要重新启用。
