# 策略（Strategy）

Strategy 用声明式 DSL 描述截面选股与固定池择时：每当实例关联的因子任务的结果 View 有一个周期就绪，就在这一帧数据上
求值，得到组合账户相对总权益的完整目标权重，连同逐标的的解释一起保存，并异步发送给 Trade。
Strategy 的求值不读取余额、持仓和订单，也不接触交易所；绑定与会话对账会调用 Trade 的 `GetLogicalAccount` 等组合账户归属接口。

代码位置：`modules/strategy`。本文描述当前实现；策略模块评审与设计保留重建前的评审与目标，不作为当前缺陷清单。

## 1. 进程与端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| `StrategyMgr` | 原生 tRPC `11430` | 管理接口；管理台经 Admin 与主机网关访问 |
| 健康检查 | `11431` | `/healthz`、`/readyz`、`/metrics` |
| 指标定时器 | `11432` | 每 30 秒刷新实例的期望数据集并上报指标快照 |

依赖：经主机网关读取 Storage（Metadata、DataView）、调用 Factor（`GetFactor`、`GetFactorTask`、`ListFactorTasks`、`BindFactorTask`、`DeleteBoundTask`、`SubmitFactorParams`），删除实例前只读调用 archive-mgr 的 `ListArchiveTasks`；通过 EventBus
订阅 `ViewDataReady`（durable `strategy_view_data_ready_v1`，投递次数不设上限）并发布目标权重事件；
状态保存在 `data/strategy/strategy.sqlite`。

## 2. 核心概念

| 概念 | 含义 |
| --- | --- |
| 定义 | 一份 DSL 文本，按内容哈希 `dsl_hash` 标识版本；出现过的每个版本永久保留 |
| 实例 | 定义 + 一个因子任务（创建时选定，独占，不能改；只随实例一起删除）+ 可选的组合账户。读取的 View 是任务结果数据集的默认 View。没有账户的实例是观察实例，只计算不投递 |
| 会话 | 每次显式启用产生一个会话，固化当时的 DSL 版本与绑定解析（`resolved_json`）；进程重启沿用会话，重复启用幂等 |
| 结果 | 每个处理过的周期一行：`ok` 带目标权重与规则状态，`skipped` 带原因；追赶或过期周期成功求值时，`skipped` 也保存推进后的规则状态，但不带目标。两者都有输入摘要 |
| 解释明细 | 各规则预期集合中每个标的的最终阶段、分数、名次、权重与原因 |
| 回放 | 在 View 的历史数据上逐期求值、用理论账本模拟成交的研究任务（支持现货、永续与混合市场） |
| 关联因子任务 | 规则直接引用任务结果数据集的列名（成员键与列名规则见第 3 节）；`factor_params` 每期求出下一期可变成员的参数，`params()` 读取这一行实际用的参数（第 3 节末） |
| 外显设置 | 实例在结果表里隐藏的因子分类、成员（按成员键）与列，默认全部展示；只影响控制台展示与默认导出 |

策略时间统一使用 `bar_end_time`（已闭合 K 线的结束边界）。实例的周期由绑定 View 的频率决定，
DSL 的 `bar` 只是可选断言。

## 3. DSL

下面的示例假设实例关联的因子任务里有这些默认参数的单输出成员：`quote_volume_mean`、`quote_volume_mean_q`、`bias_q`、`bias`（列名就是成员键）：

```yaml
name: binance_spot_momentum
bar: 1m                       # 可选断言：与 View 周期不一致时拒绝启用

universe:                     # 策略级默认标的池，省略即全部
  min_age_bars: 240           # 标的在 240 根之前已有数据才参与
  exclude: [BTC-USDT]

rules:
  - id: long_momentum         # 稳定标识：规则状态与解释明细按 id 关联
    name: 多头动量选币         # 只用于展示
    type: rank                # 截面选股
    filter: "quote_volume_mean > 20000 && close > 0"
    score: "0.6 * rank(bias_q) + 0.4 * rank(quote_volume_mean_q)"
    select: {top: 5, buffer: 2}
    weight: {total: 0.8, method: equal, cap: 0.3}

  - id: btc_trend
    name: BTC 上穿均线          # bias = close / MA20，由不大于 1 变为大于 1 即上穿
    type: signal              # 固定池择时
    pool: [BTC-USDT]
    entry: "bars[-1].bias <= 1 && bars[0].bias > 1"
    exit: "bars[0].bias < 1"
    weight: {total: 0.2}

portfolio:
  leverage: 1                 # gross 上限；只有市场模式含永续时才允许大于 1
  max_weight: 0.3             # 组合级单币上限，同一个币的现货、永续合计；超出部分留现金
  min_universe: 20            # rank 规则进入 filter 的可用标的少于它则整期跳过
  max_missing: 0.2            # 任一规则缺数占（预期 − 年龄剔除）的比例超过它则整期跳过
```

`portfolio` 省略的字段取默认值（`leverage: 1`、`max_missing: 0.2`、`min_universe: 0`、不限 `max_weight`）；
显式写出的 0 按原值校验：`max_missing: 0` 表示不容忍任何缺数，`leverage: 0` 非法。

| 字段 | 说明 |
| --- | --- |
| `universe` | `tags`、`exclude_tags`、`include`、`exclude`、`min_age_bars`；`tags` 与 `include` 任一非空时取两者并集作为白名单，都为空表示全部 U，再减去 `exclude_tags` 成员与 `exclude`。标签与名单只作用于没有显式 `pool` 的规则；`min_age_bars` 对所有规则生效（含显式 `pool`），但不剔除规则上期已持有的标的 |
| `rules[].id` | `^[a-z][a-z0-9_]{0,63}$`，修改 id 等于从零开始 |
| `rules[].type` | `rank`、`signal` 或 `tranche`（见下方「tranche 规则」）；三者都可写 `stop`（见「止损止盈」） |
| `pool` | 固定列表或 `{tags: [...]}`；显式给出时不再套用 universe 的标签与黑白名单 |
| `filter` | rank：布尔表达式，淘汰的标的记为 `filtered` |
| `score` | rank：数值表达式；`rank(x)` 与 `zscore(x)` 在通过 filter 的样本上计算，可嵌套 |
| `select` | rank：`top` 与 `bottom` 二选一，`where` 用 `score` 二次筛选，`buffer` 是排名缓冲区（按 `select.where` 之前的全样本名次判断"前 N+B 名"，与解释明细的名次一致） |
| `weight` | `total` 是规则预算；`method` 为 `equal` 或 `rank`（最优 N 份、最差 1 份）；`cap` 是规则内单标的上限；保存时要求 `cap × 选中数量 ≥ total`（预算分得完）。holding 规则的每个批次各自按 `cap / total` 的份额上限配权、批次之间互不补足（这样同一标的叠在所有批次里也不超过 `cap`），所以校验不按批次数放宽，批次较多时实际总权重可能低于 `total` |
| `filter_after` | rank：只剔除不补位，剔除的权重留现金；holding 规则只在建仓 bar 执行 |
| `holding` | rank：`{bars, offsets}` 分批换仓，与 `buffer` 互斥。bar 序号对 `bars` 取模落在 offset 上时按本期名次重建该批次，批次延续到满 `bars` 根；延续期间只因缺数移出标的，本期被 filter 等淘汰仍按批次持有；缺数与 filter_after 剔除的份额都留现金，不重新分配。首次引擎求值成功的 bar 上按本期名次建立全部批次（不等各自的 offset、不空仓一个周期）；建仓 bar 没有产生 ok 决策（守门跳过、无数据、停机期间漏掉的事件）时，到期的批次不会被丢弃清仓，而是在之后第一根引擎求值成功的 bar 上按本期名次补建。首次建立与补建的批次，建仓序号都按各自的 offset 对齐到最近一个应建仓的 bar，之后照常在 offset 上轮换。追赶或过期周期成功求值也会推进批次状态，即使持久化结果是 `skipped(catchup / expired)`（见第 4 节）。bar 序号：crypto 是 `bar_end` 自 Unix 纪元起的根数（例如 1h 下 offset 0 落在 UTC 整点按 `bars` 对齐的时刻），A 股日线是内嵌交易日历首个交易日起的交易日序号，A 股日内是 barclock 的交易序号（午休、隔夜、休市不占根数，与因子的交易序号轴一致） |
| `side` | `long`（默认）或 `short`；现货 View 不允许做空 |
| `entry` / `exit` | signal：先对旧理论持仓判 exit，再对候选判 entry，退出优先 |

表达式用 Expr 编写，只能引用 View 的列、`bars[0].<列>`（当期）、`bars[-1].<列>`（日历上紧邻的上一根）、
`instrument_id` 与（仅 `select.where`、`filter_after`）`score`。内置函数一律禁用，只开放 `rank` 与 `zscore`
（仅在 `score` 中）。`matches` 右边只能是字符串字面量的正则表达式，保存时校验写法（用数据当正则时，标的 ID 里的括号
会让整期求值失败）；`??`、范围 `..` 与 `in` 不可用（列值不会为空，范围会为每一行分配整段数组，求值时必然出错），保存时
就拒绝；三元表达式 `a ? b : c` 的两个分支类型必须一致（都是布尔、都是数值或都是字符串），在启用与试算编译时检查；
运行错误只写中文原因，不带表达式库的英文原文。`rank` 同分取平均名次、单样本记 0.5；`zscore` 零方差记 0（样本值相同、或标准差
不超过样本量级的 1e-12 都按零方差处理）；排序以 `instrument_id` 打破平局。同一层的截面函数在同一个样本上
计算一次：先在通过 filter 的样本上求出全部参数（参数中嵌套的截面函数在下一层按同样规则计算），任一参数
无效（NaN、Inf、运行错误）的标的从这一层的名次与标准化中剔除；外层结果无效（例如 `rank(a) / rank(b)` 在
名次 0 处除零）只淘汰该标的本身，不触发重算。结果与截面函数的书写顺序无关。通过 filter 的候选全部分数
无效时整期 `skipped(config_error)`，不当作"选不出标的"清仓；holding 规则只在建仓或补建批次的 bar 检查，其余 bar
只延续批次、不使用本期分数。时序计算（均线、动量、分位）都写成因子，策略只在截面上过滤、打分、配权。

DSL 文本不超过 64 KiB；单条表达式不超过 1024 个字符（按字符计，只限制用户写下的原文）、不超过 256 个
语法节点，两者都在保存时检查；`bars[...]` 之后只能用 `.列名` 引用列。数字可以写成 YAML 接受的 `.5`、
`+0.5`、`5e-1` 等形式，精度不超过 18 位小数；数字写法不超过 64 个字符、指数绝对值不超过 30、绝对值小于 10^9。
`portfolio.leverage` 不超过 10（各规则 `weight.total` 之和不超过它）；`min_age_bars`、`min_universe`、`select` 的
`top` / `bottom` / `buffer` 与 `holding.bars` 不超过 10000，`holding.offsets` 不超过 64 个。rank 规则的固定 `pool` 列表少于 `min_universe` 个标的
时保存即拒绝（这条规则永远无法通过守门）；只写 `universe.include`、没有 `tags` 时它是白名单，去掉 `exclude` 后少于
`min_universe` 个标的，没有显式 `pool` 的 rank 规则同样保存即拒绝。标的与标签 ID 区分大小写。多个阶段同时有错时按 filter、score、
select.where、filter_after、entry、exit 的顺序报告第一个。

保存定义时只做语法与结构校验；列是否存在、成员契约与市场类型在启用实例时解析。编辑器的"试算"与
`ValidateStrategy` 会在选定因子任务的结果 View 的最近一期上求值一次，结果不落库；引用了任务里不存在的列时，报错带最接近的列名与该任务的全部列。

### tranche 规则（批次持仓）

`type: tranche` 的规则每根 K 线按本期选币新开一批仓位，每批持有 h 期，多批叠加。打分、选币、过滤、持有计数、定仓方式都是选项，
同类策略写配置即可，不用改代码。

```yaml
rules:
  - id: main
    type: tranche
    weight: {total: 1}            # 规则预算：各子策略按 stg_weight 归一化后乘以它
    candidates: {require_volume: true}   # 规则级：候选是否要求 volume > 0（默认 true）
    tranche:                      # 子策略模板；"{列名}" 取参数表这一行的值，整段占位符保留数字类型
      hold_period: "{h}"          # 必填
      hold_count: candidate_rows
      score: {method: rank_sum, missing: median}
      sizing: {method: quantity, scale: 0.5}
      long_factors: [{factor: "momentum__{n}", descending: true, weight: 1}]
      short_factors: []
      long_weight: 2
      short_weight: 0
      long_coin_num: 1            # 整数是个数；0～1 之间是百分比（按分数非空的样本排名）
      short_coin_num: 0
      long_white_list: []         # 另有 long_black_list、short_white_list、short_black_list
      filter_before: []           # 串联执行：rank / pct 在上一步留下的样本上计算，符合条件的保留
      filter_after:               # 在选中的样本上一次判断，任一条件成立就剔除，不补位
        - {direction: long, factor: "shadow__{m}", type: value, op: lte, value: "{p}"}
      stg_weight: "{w}"
      # stop: {loss: 0.08, cooldown_bars: 12}   # 止损止盈，见下一节
    params:                       # 可选：每行展开为一个子策略（一条规则最多 5000 行，全策略合计最多 10000 个）
      columns: [h, n, m, p, w]
      rows:
        - [1, 20, 24, 0.1, 0.0033333333333333335]
universe: {min_age_bars: 999}     # 需要去掉上市不久的标的时，用策略级的年龄门槛
portfolio:
  leverage: 2                     # 按数量持有会让 Σw 略大于 1，留出上限，不缩放
```

| 选项 | 取值 | 默认 |
| --- | --- | --- |
| `candidates.require_volume`（规则级） | `true`：候选要求 `volume` 非空且 > 0，`volume = 0` 记 `idle`（`volume_zero`）；`false`：不读 `volume` | `true` |
| `hold_period` | 1～2016 | 必填 |
| `hold_count` | `candidate_rows`：该标的本期是候选才计数；`bars`：每根 K 线都计数 | `bars` |
| `score.method` | `rank_sum`：各因子截面平均名次 × 权重 × 方向后求和（不除以权重和）；`raw_sum`：因子原值加权求和 | `rank_sum` |
| `score.missing` | `median`：因子空值补同期名次中位数；`drop`：空值不参与本期排名（`raw_sum` 下空值总是不参与） | `drop` |
| `sizing.method` | `quantity`：开仓时定数量，本期权重 = 份额 × 本期 close / 开仓 close；`weight`：每批份额固定 | `weight` |
| `sizing.scale` | (0, 10]，份额 = `scale × side_weight / h / 分母` | 1 |
| `long_weight`、`short_weight` | 0～20，某侧为 0 时该侧不选币 | 1、0 |
| `long_coin_num`、`short_coin_num` | 个数（分母固定为配置值，选不满也不变）或 0～1 的比例（分母为实际选中数） | 1、0 |
| `stg_weight` | > 0 | 1 |

默认值按"对新策略最不意外"来定：只做多、因子空值不靠补中位数入选、持有期等于自然时间、每批份额固定。要与外部框架逐值一致时，把它的做法逐项显式写出。

- **选币方向**：多头按分数升序取小者，空头按分数降序取大者；`descending: true` 的因子在分数里取负号。
  多空因子列表不同时分两遍排名：先排多头列表的列，再在当前值上（共用的列已经是名次）排空头列表的列。
- **过滤条件**：`direction`（`long`/`short`，默认 `long`）、`factor`（列名）、`type`（`value`/`rank`/`pct`）、
  `op`（`lt lte gt gte bt bte nbt nbte eq ne`，必填）、`value`（数字，或 `bt` 一类的 `[下限, 上限]`，必填）、`rank_ascending`。
  比较规则：`between` 的开闭（以 e 结尾为闭区间，`lt`/`gt` 一类用 ±1e100 的有限边界），`nb*` 与 `ne` 取反，所以 NaN 在 `nb*` 下为真。
  `rank` 默认从大到小、`pct` 固定从小到大，都按 `method='first'`（同分按标的 ID 去掉 `-` 后的顺序）。
  逻辑组合写成 `{logic: "1&(2|3)", items: [...]}`（`&` 优先于 `|`，1～9 号，同一组必须同一方向）。
- **持有**：开仓当期计 1，之后每期先计数、再贡献、最后清理；持有计数超过子策略的 `hold_period` 时它不再从这条记录取权重；
  标的本期不是候选时不贡献权重。组内每个子策略都不再需要的记录才删除。
- **候选与缺数**：缺数只算没有行、`close`（`require_volume` 时还有 `volume`）为空或 K 线失败，**因子列为空不算缺数**。
  `max_missing`、`min_universe` 按这个口径守门；tranche 规则不参与持仓冻结。
- **去重**：打分方式与缺值处理、多空因子、名单、前置过滤、个数、哪一侧权重大于 0、`stop.price` 都相同的子策略构成一个"排名签名"，
  每期只选一次币；后置过滤、定仓与止损逐个子策略计算。状态按签名保存开仓记录（`RuleState.tranche`），任何子策略字段变化时旧记录不再沿用。
- **明细**：每个（规则, 标的）最多一条：有权重的是 `weighted`，原因 `tranche:<持有它的子策略数>`；本期选中但被全部子策略后置过滤剔除的是 `dropped`（`tranche_filter_after`）。
- **限制**：含 tranche 规则的策略只能全部是 tranche 规则，不能写 `factor_params`；只能用在单个市场的策略（纯永续，或纯现货、A 股且按权重持有、不做空；A 股同纯现货）；双市场的 tranche（`both`、`spot/swap`）启用被拒——**S1 暂不支持双市场 tranche，原因：一个市场本期不可用时 tranche 的持仓无法冻结**；
  研究回放与闭环回放暂不支持。含参数表时 DSL 上限放宽到 1 MiB。

### 止损止盈

`rank`、`signal` 规则写在规则上，`tranche` 写在子策略模板里（可用参数表占位符）；不写时行为不变。

```yaml
stop:
  loss: 0.05            # 固定止损：相对入场价不利变动达到 5%（含等于）
  trailing: 0.08        # 跟踪止损：相对此前最有利价格回撤 8%
  profit: 0.10          # 止盈：相对入场价有利变动达到 10%
  price: close          # close（默认）| extreme：止损看本期 low（空头 high），止盈与最有利价格看 high（空头 low）
  cooldown_bars: 12     # 触发后 [T, T+12] 根内本规则不能重新入场；默认 0（只禁止触发当期）
```

- `loss`、`trailing` 取值 (0, 1)，`profit` 取值 (0, 10]，至少写一项。同期多项触发按 `stop_loss` > `trailing_stop` > `take_profit` 记。
- **按收盘判断**：每期在规则求值最前面判断，止损的目标随本期目标下发，由 Trade 执行；不是盘中触价止损。入场价是入场当期的 close，不是成交价。
- **跟踪止损**用此前的最有利价格（不含本期）判断，判断后再用本期价格更新：同一根 K 线里高低点的先后未知，这样不会用后出现的高点去判先出现的低点。
- **价格列**：`close`（`extreme` 时还有 `high`、`low`）作为可选列读取，绑定的 View 必须有这些列；缺值、非有限或 ≤ 0 时本期不判止损、
  不更新最有利价格，不算缺数。入场当期没有 close 时，入场价在下一个有价格的期次补记。冻结的标的不判止损。
- **持仓单位**：`rank`（无 `holding`）与 `signal` 是每个持有标的（入场价是进入持有集合那一期的 close，持有期间调权不改）；
  `rank` 的 `holding` 是每个批次里的每个标的（入场价是实际进入批次那一期的 close，不用回填的建仓序号）；
  `tranche` 是每条开仓记录 × 每个子策略：同组共用入场价与最有利价格，各子策略按自己的阈值判断，止损后该子策略不再从这条记录取权重。
- **触发后**：`rank` 从选币与 `buffer` 的上期持有里排除，由后面的名次补位（名次仍在完整样本上计算）；`holding` 批次里的份额留现金到下次重建；
  `signal` 等同 exit（exit 的输入缺失也照常判断），冷却中 entry 成立也不入场；`tranche` 冷却中的子策略不为这个标的的新开仓取权重，
  共用的选币不受影响。
- **明细与摘要**：失去全部权重的标的记阶段 `stopped`，原因 `stop_loss` / `trailing_stop` / `take_profit`，同一标的另有缺数等明细时合并为一条
  （例如 `stop_loss;missing:x`）；仍有权重的保持 `weighted`，原因追加 `;stopped:<n>`；冷却中的候选记 `dropped`（`cooldown`）。
  规则摘要的 `stop_loss`、`trailing_stop`、`take_profit` 是本期触发的持仓单位数。
- 状态：`RuleState.entries`（入场价、入场序号、最有利价格）、`RuleState.cooldown`（冷却截止序号，含当期）；holding 批次的 `entries`；
  tranche 开仓记录的 `peak` 与已止损子策略位图 `stopped`，以及按子策略的 `RuleState.tranche.cooldown`。追赶期与迟到周期照常推进这些状态。

### 策略模板

模板是命名的 DSL 骨架 + 变量定义 + 可选的参数表样例行，用来快速生成同类策略；生成的策略是普通策略定义，之后与模板脱钩。
内置示例模板放在 `modules/strategy/templates/tranche_example.yaml`。

```yaml
template_id: tranche_example
name: 批次持仓截面选币（示例）
description: 动量因子选币、影线因子后置过滤，参数表每行一个子策略
variables:                       # 类型 int / number / string / bool；可写 min、max；保存时要求都有 default
  - {name: leverage, type: number, min: 0, max: 10, default: "2", doc: 组合杠杆上限}
sample_row: ["1", "20", "24", "0.1", "0.5"]   # 骨架带参数表时必填：保存时用它试渲染
dsl: |
  name: "{{name}}"               # name 是内置变量（策略名），渲染时必填
  rules:
    - id: main
      type: tranche
      ...
      params:
        columns: [h, n, m, p, w]
        rows: []                 # 必须为空，渲染时填入参数表
  portfolio: {leverage: "{{leverage}}"}
```

::: v-pre
- 渲染只替换**值为完整 `"{{变量}}"`** 的 YAML 标量，按声明类型写入；键里、部分包含的占位符一律拒绝。字符串值与参数表单元格不能含花括号
  （避免被 tranche 的 `{列名}` 展开二次解释）。最多一条规则带参数表，参数表 CSV 的表头必须与 `params.columns` 一致；
  骨架带参数表时参数表不能为空，不带时不接受参数表。生成的 DSL 走完整的 DSL 校验。
:::

- 本地校验与渲染：`moox-strategy-cli template check <模板.yaml>`；
  `moox-strategy-cli template render <模板.yaml> --name demo [--var leverage=3] --params params.csv > demo.yaml`。
- 保存与删除走接口（管理台只读列表并“从模板新建”）：
  `moox-cli gateway call trpc.moox.strategy.StrategyMgr SaveStrategyTemplate --data @save.json`，`save.json` 是 `{"template_yaml": "<模板原文>"}`；
  `DeleteStrategyTemplate` 传 `{"template_id": "tranche_example"}`。管理台“策略定义 → 从模板新建”选模板、填变量、上传参数表，预览后创建策略。

### 市场模式

DSL 顶层的 `market` 决定策略从哪个市场的币里选，以及一个币在两个市场都可用时优先在哪个市场下单：

```yaml
market:
  select: spot | swap | both   # 从哪个市场的币里选
  prefer: spot | swap          # 一个币在两个市场都可用时，优先用哪个下单
```

只允许 5 种组合，每种需要绑定的因子任务不同（一个任务读一个市场的结果 View）：

| select | prefer | 含义 | 需要绑定的因子任务 |
| --- | --- | --- | --- |
| spot | spot | 纯现货 | 现货 |
| swap | swap | 纯永续 | 永续 |
| both | spot | 两边选，现货优先 | 现货、永续 |
| both | swap | 两边选，永续优先 | 现货、永续 |
| spot | swap | 现货选币，有永续就用永续下单 | 现货、永续 |

- 不写 `market` 时，按实例唯一绑定的因子任务的市场取 `{select: 该市场, prefer: 该市场}`；绑定了两个任务必须写 `market`。`select` 为 `spot` 或 `swap` 时可省略 `prefer`。
- 股票（`equity`）不允许写 `market`，目标的市场固定为 `STOCK`。
- 空头只走永续；纯现货与股票不能做空、`leverage` 不能大于 1；`portfolio.leverage` 大于 1 只有模式含永续时才允许。
- tranche 只能用在单个市场的策略：`spot/spot`、`swap/swap`。`both/spot`、`both/swap`、`spot/swap` 都可能跨市场（`spot/swap` 有永续就在永续下单），一律拒绝，原因是 tranche 不参与持仓冻结，一个市场本期不可用时持仓会被卖掉。纯现货的 tranche 不能做空且必须用 `sizing.method: weight`（按数量持有会让权重之和略大于 1），纯现货按权重持有现在可以用；纯永续的 tranche 不受影响。
- 绑定两个任务（或模式含两个市场）的策略不支持 `factor_params`。

**“可用”的定义**：某个标的在某个市场本期可用，指它在该市场的数据集里处于活跃状态，且该市场的 View 本期有它的行。

**选币池构造（每期）**：为每个标的在两个市场的行里选出一行，因子值用这一行；Frame 仍是每个标的一行，另带本行市场和两个市场的可用标记，规则内部照旧按标的计算。

1. 上期持有正权重目标的标的（所有模式，包括 `select: spot, prefer: swap` 持仓在永续时），只取它持仓所在市场的行；那一行本期不存在时按无行处理，走缺数和冻结逻辑，不退回去取另一个市场的行。
2. 其余标的：`select: both` 时两个市场都可用，只保留 `prefer` 市场那一行，只在一边可用就保留那一边；`select` 为单个市场时只用该市场的行（另一个市场只提供“可用”标记，用来决定下单市场；只在另一个市场上市的标的不进入基础集合）。
3. 空头候选只保留本期永续可用的标的（规则上期已持有的不过滤，永续本期不可用时由冻结逻辑保持）；只涉及单一市场的策略不过滤。

**定市场**：在规则贡献合成之前，给每个（规则, 标的）的权重定下市场。空头一律永续。多头按顺序：① 上期这个标的有**正权重**目标的，沿用那个目标的市场直到归零（“粘住”，避免永续偶尔缺数时在两个市场之间来回倒仓；上期在永续上的空头不会把本期多头粘到永续）；② `prefer` 市场本期可用就用它；③ 否则用另一个市场。

**已知局限（粘住只看正权重）**：`select: both, prefer: spot` 时，上期持有的是永续**空头**的币，本期不会粘在永续上，取行与定市场都先看 `prefer` 的现货行（空头本来只能下在永续，所以仍然落在永续，但用的是现货行的因子值，现货行不可用时才退回永续行）；需要空头始终用永续行时，把 `prefer` 写成 `swap`。**例外是永续对这个币的失败证据全都可冻结时**，两条都要满足：① 永续对这个币至少有一条证据，并且**每条**都是整体不可用（因子被跳过、整体失败、失败比例超限，即 `market_unavailable`）；② 永续本期有它的行，或者证据覆盖了策略引用的全部列（当期列与 `bars[-1]` 列）。这时上期在永续持有空头的币只取永续的行（行在就取它；不在就按无行），失败证据也取永续的，由冻结逻辑保持，不退回现货的行重新排名（`prefer` 取哪个都一样），空头保持不动。不满足时照常按上面的顺序取行：证据里混有逐币的 `factor_failed`（它在单市场下也不冻结），或者永续没有行、只有部分列有证据（其余列是没有证据的缺失，单市场下同样不冻结）。冻结按币，同一个币同时持有现货多头和永续空头时，满足条件就把现货多头一起冻结（保守的已知边界）。

**持有的永续空头在永续下架时平掉**（设计变化，第二轮总审查）：规则上期持有、上期在永续上是空头的币，本期永续没有它的行、也没有任何失败证据，并且永续不是整体不可用（典型是这个币的永续已下架、现货还在）时，这条空头规则按无行处理：明细 `missing(no_row)`、市场标永续，空头平掉、从规则持仓里移除，计入这条规则的缺数，也不参与冻结。以前它会借用现货行的因子值继续排名，照样输出 `Y|swap` 的空头目标，而永续上已经没有这个合约。这与上期持有的永续多头在永续无行时被平掉（粘住永续、不退回现货的行）对称。按规则处理、不按币：同一个币的现货多头和其他规则照常用现货行，对冲币只平永续空头、现货多头不动；只做空的币本期仍可以被多头规则在现货选中。永续有证据时按上一段处理，永续整体不可用时由冻结逻辑保持（见下文“一个市场整体失败也算不可用”）。

**合成与键**：从规则贡献合成开始，`State.Targets`、目标和结果明细都用（标的, 市场）作键（`State.Targets` 的键是 `标的|市场`，如 `BTC-USDT|swap`）。同一市场内多空可以相互抵消，现货与永续之间不抵消。排序先按标的，再按市场（现货在前）。

**组合约束**按固定顺序：① `max_weight` 按币合计——同一个标的现货、永续权重绝对值之和不超过它，两边都不为零时按比例缩小两边，只有一边时直接取上限（“现货多 + 永续空”这样的对冲也按绝对值之和截断）；② 给保持目标预留预算，保持目标本身不缩小；③ 现货部分（不含现货保持目标）超过 `1 − 现货保持目标` 时按比例缩小，多出的留作现金（`leverage` 大于 1 时才可能出现）；④ `gross` 超过 `leverage` 时按比例缩小（保持目标不动）；⑤ 摘要里 `net` 拆成 `spot_net`、`swap_net`，`cash` 只对单市场策略有意义，混合市场不填。**行为变化**：现货权重之和超过 1、`gross` 超过 `leverage` 以前整期 `skipped(config_error)`，现在改成按比例缩小并在摘要注明；现货出现负权重仍然报错（说明策略或定市场的逻辑有错）。

**一个市场整体失败也算不可用**（方式 A、B 一样，只对涉及多个市场的策略）：时序因子在永续整体晚到时，该市场所有序列都在失败名单里，因子侧记 `degraded` 而不是 `skipped`。逐币的 `factor_failed` 不冻结，持有的永续会被卖成现货（缺数比例没超过 `max_missing`，或没持仓的币退回现货的行、缺数分母被摊薄）。所以两种情况按这个市场不可用处理——记 `market_unavailable`、冻结持仓：① 某个因子成员在这个市场本期读取的标的**全部失败**，在年龄探针之前判断（整体失败的市场不做探针）；探针之后扣掉年龄不够的标的、再按下面的范围重判一次“全部失败”，`max_missing` 为 1 时同样成立；② 失败的标的占比**严格大于** `portfolio.max_missing`，在年龄探针之后判断（比例恰好等于上限仍可用）。
统计范围：只统计本次实际读行的标的（规则预期集合的并集 ∩ 这个市场的基础集合：策略池被收窄、`universe.exclude` 排除的标的没读行，它们的失败不计入），并且只统计有行或在失败名单里的标的；探针之后的判断还要扣掉在这个市场年龄不够的标的，**但上期在这个市场持仓的豁免**（年龄剔除只拦新进入的标的，与单市场的缺数检查、选币池构造一致；持仓来自处理器先读出的上期状态，多空都算）。失败序列在源数据行存在时写成 NULL 行；上游缺失、整体晚到的序列没有行，只在失败名单里——代码里“在失败名单里就计入”。因子没有期望的序列（方式 B 里永续标签的活跃成员、但 `universe_series` 里还没有这条序列，或已停更而标签没移除）既没有行也不在失败名单里，不参与判断。这个口径与单市场的缺数检查**近似、不完全相同**：单市场缺数检查的分母是规则的预期集合减年龄剔除，这里是读行的标的减在这个市场年龄不够的标的，两者在池被收窄等边缘情况下可能差一点。每个因子成员各自统计，只看它自己的失败名单和行，不同成员的失败不叠加。
判断在读完行之后（方式 B 一次读完两个市场，不增加读取），认定不可用的市场清掉已读的行（必须清：不清的话没持仓的标的会取到不可用市场的行，在引擎里记成 `market_unavailable` 缺数，而不是退回另一个市场的行），规则级的年龄剔除集合也按剩下的市场重算。因此在设置了 `min_age_bars`（大于 0）时，同一个只在永续上市、没持仓的币在三条不可用路径上口径一致：因子被跳过、全部失败（都不做探针）与失败比例超限（探针之后清掉不可用市场的探针结果）都按年龄剔除记，不计入缺数检查。**`min_age_bars` 为 0 时没有年龄剔除**，不可用市场独有、没持仓的币记 `market_unavailable` 缺数、计入缺数检查：同一份数据只差 `min_age_bars`，结论可能翻转（例如永续 8 个币里 B、C、D 失败：为 0 时整期 `too_many_missing`，为 24 时只在现货开仓）；而且被记成年龄剔除的币其实历史齐全，结果明细里看到 `aged_out`/`min_age_bars` 时要结合“市场不可用”判断，不要误以为是新上市。比例路径还有一个例外：要判为不可用的市场如果探针窗口里一行都没有，会先整期 `history_insufficient`，而“因子被跳过”的路径照常求值（偏保守）。选币市场这样不可用、或所有市场都不可用时整期按 `market_failed` 跳过，说明里列出每个不可用市场各自的原因（`LoadBar` 返回的数据类跳过，不计实例故障；它不是“积累中”，不进积累期，持续出现走数据集新鲜度告警）。冻结的持仓仍计入缺数比例，比例超过 `max_missing` 时本期 `too_many_missing`、持仓不动。只是一部分市场不可用不整期跳过，缺数检查有两处收窄：① 永续本期整体不可用、并且空头规则（非 tranche，rank 与 signal 都算，与空头候选过滤的范围一致）本期的**可用集合与缺数都为空**时，这条规则不做缺数检查——它的预期集合只剩上期持有、全部按市场不可用冻结的空头，检查必然得出 `universe_too_small` 或 `too_many_missing`，会把多头腿也一起整期跳过；冻结的空头照常产出保持目标，不新开空头，摘要里注明；holding 规则这一期不重建批次、沿用上期批次（否则启用后第一根 ok bar 正好碰上时会建出空批次，永续恢复后空头只配到一部分），到期没重建的批次在之后第一根 ok bar 上补建。可用或缺数不为空说明有持有的空头没被冻结（例如证据没覆盖到它、借用了现货行），这时照常做缺数检查。为了让持有的空头都有证据，输入层给不可用的市场构造 `market_unavailable` 证据时，除了这个市场本期基础集合里的标的，还补上上期在这个市场持仓（多空都算）的标的：它可能已不在本期的基础集合里（例如永续标签刚移除了它），没有证据就会借用现货行重新排名。② 多市场策略的缺数检查只排除一种冻结标的：**本规则上期没持有、并且因所在市场本期整体不可用而冻结（`market_hold`）**的标的。冻结按币，别的规则在不可用市场的持仓（例如永续空头）会让这个币在所有规则里冻结，它对没持有它的规则只是本期不参与的候选（仍留在分母里）。规则自己持有的冻结标的、以及只缺上一根而冻结（`prev_hold`）的标的照旧计入——只缺上一根与另一个市场可不可用无关，不能因为永续恰好也不可用就不计；比例超限仍整期 `too_many_missing`。单市场策略保持原来的缺数处理（纯永续大面积失败仍是整期 `too_many_missing`）。

**一个市场整体不可用**：绑定两个任务的实例里，只有一个市场的因子本期被跳过（`factor_skipped`）时，只让这个市场本期不可用，不整期跳过：这个市场里的标的记缺失原因 `market_unavailable`，可以冻结（已持仓的保持不动，不会因为一期没数据就被卖出），缺数检查把它们计入缺数（别的规则持有、因市场不可用冻结的标的不计，永续整体不可用时只剩冻结空头的空头规则不做缺数检查，见上面“一个市场整体失败也算不可用”）；新开仓可以用另一个市场。需要的市场全部不可用时仍按原来的原因整期跳过。成员契约变了、事件缺失、没有上一根的版本证据等配置、契约类原因，整期按原因处理。

**两种输入方式。** 同样的五种模式，因子数据可以来自两种组织方式，建实例时自己选；读完数据后都整理成同一种 Frame（每个标的一行，带本行市场与两个可用标记），后面的选币池构造、定市场、合成、组合约束、目标事件完全共用：

- **方式 A：现货、永续各一个因子任务**（`factor_tasks` 写 `spot=…`、`swap=…`），两个 View 汇合求值（见 4 的“汇合求值”）。
- **方式 B：统一数据集上的一个因子任务**（`factor_tasks` 写 `multi=…`）：同一个数据集里同时放同一标的的现货、永续两条序列，用 `series_tag` 区分，一个因子任务、一个 View，不需要汇合，到达即求值。

方式 B 的规则：

- **识别与登记**：任务的源数据集 `market_type` 是 `multi`（采集侧挂了现货、永续两个标签的数据集）。登记为 `multi`，只绑这一个任务，不能再绑别的；登记成 `spot`、`swap` 会被拒绝并提示写 `multi`。策略必须显式写 `market`（统一数据集没有可当默认值的市场），五种模式都可以用（纯现货、纯永续只取对应市场的序列）。
- **读取**：selector 不带 `series_tag`，一个 View 一期只读一次全部序列，再按 `packages/seriesset` 的 `SeriesTagMarket` 把行的 `series_tag` 换成市场（`market:` 段，没有这一段按现货），按市场拆成 Frame 里各市场的行。
- **活跃状态与标的全集按市场**：数据集挂的标签按标签自己的 `market_type` 归到市场，标签的活跃成员（且标的在数据集里是活跃绑定）就是这个市场的标的。永续下架而现货还在时，永续不可用、现货照常可用；只在永续上市的币不算现货缺失。事件里的标的名单是各市场标的的并集（View 就绪事件没有按序列的名单），每个市场用它与自己的活跃标的求交。
- **歧义**：现货、永续两条序列并存是正常的，只在同一个市场内判断歧义：同一标的同一周期在同一个市场里出现两个 `series_tag`，或某个 `series_tag` 换不出现货/永续（例如 `market:option`），才整期 `skipped(ambiguous_series)`。单市场数据集上同标的多序列仍是歧义。研究回放（`RangeLoader`）同样按市场过滤。
- **年龄探针按（标的、市场）**：`t_strategy_age_passed` 主键含 `c_market`，探针只认这个市场自己的序列有历史行，老的现货币新上永续时不能用现货的历史通过永续的年龄检查；内存缓存按（View、min_age_bars、市场）分槽，现货、永续每期交替探针不会互相覆盖。候选全部没通过时的“历史缺口”确认查询也只看这个市场自己的序列（读全部序列再按市场过滤，不取一行）：现货有数据、永续整段缺口时与方式 A 一样整期 `history_insufficient`，不会把永续全部判成新上市。启用时除 View 级覆盖校验外，按市场在目标根附近探针，某个市场一行都没有就拒绝启用。年龄不够的标的在这个市场的行不再被删掉，而是记进 Frame 里该市场的 `AgedOut`，选币池构造不取这些行，**但上期在该市场持仓的豁免**（年龄剔除只拦新进入的标的，持仓不能因为探针窗口里的历史缺口而无行、被卖出；这一条方式 A 同样适用）。
- **就绪判断读因子明细的按序列字段**，一份事件拆成各市场的结论（`readiness.Result.ForMarket`）：失败读 `failed_series`（先与周期级 `shared_failed_series` 合并，`seriesset.Union`），不读按标的折叠的 `failed_subjects`（一个币只在永续失败时它里面也有这个币，读了会让现货跟着失败）；`skipped_series_tags` 命中的市场本期不可用（数据类原因，记 `market_unavailable`，可冻结已持仓的标的），别的市场照常；成员 `skipped`（全部 tag 都跳过）、配置、契约类原因整期按原因处理。例外：期望快照里只剩一个 `series_tag` 的一期，Storage 不生成序列名单，因子只给出按标的的名单，事件里确定不了是哪个市场，`ForMarket` 先把按标的的失败名单带到每个市场并记下这些因子；读完行之后，本期一行也没有的市场丢掉这些名单、按无行处理（失败只可能属于有行的那个市场），有行的市场照常按失败处理，不把真实失败的标的当成可用。这样零行市场的结论不随另一个市场有没有失败而变。结论的分类与方式 A 一致，所以同样的数据在两种方式下得到同样的目标。
- **限制**：不支持 `factor_params`（参数按标的取值，现货、永续两条序列会共用同一组参数）；不能进策略池；**闭环回放显式拒绝**（因子引擎的闭环回放只取每个标的的第一条序列）；研究回放支持（回放表的任务键是 `multi`，同一段的行只读一次 Storage、两个市场再按 `series_tag` 过滤；独立的回放发起表单与试算面板不列统一数据集上的任务，试算、回放按市场给 `factor_tasks` 时写成现货会提示写 `multi`，要回放统一数据集上的实例从实例详情发起）。

### 策略池

> 状态：已实现（执行计划 S3）。研究回放与闭环回放暂不支持策略池；成员的净值与分配比例在池实例启用后的预热与运行结果里查看。

一个策略要么写 `rules`，要么写 `strategy_pool`，两者互斥。池由若干**成员**组成，成员引用已有的策略定义；每个成员独立求值，并在自己的模拟账本里维护含手续费的净值曲线，池按曲线分配资金。

```yaml
name: 双策略轮动
bar: 1h                                      # 必须写，成员的 bar（写了的话）要与它一致
strategy_pool:
  members:
    - {id: a, strategy: strategy_xxx}        # 引用已有策略；启用时固化其 DSL 与哈希
    - {id: b, strategy: strategy_yyy}
  allocation:
    method: fixed | rotation
    ratios: {a: 0.6, b: 0.4}                 # fixed：必须覆盖所有成员，可以不归一（总敞口受 portfolio.leverage 约束）
    rotation:                                # rotation
      factors: [{name: return, window: 24, weight: 1}, {name: ma_ratio, window: 72, weight: 1}]
      top: 1                                 # 取名次靠前的几个，并列的平分
  timing: {window: 24}                       # 可选：成员净值在 window 期均线之上取 1，否则取 0
  step: 0.2                                  # 可选：每期每个成员的比例变化上限
  fees: {spot_bps: 10, swap_bps: 5}          # 可选：成员账本的单边手续费，默认 10 / 5 bps
portfolio: {leverage: 1.5, max_weight: 0.1}  # 组合级约束，max_weight 仍是同一个币的现货、永续合计
```

**成员约束**：成员策略必须显式写 `market`（股票策略不能进池）、不能是池（不嵌套）、不能用 `factor_params`、写了 `bar` 的要与池一致。池本身不写 `market`、`universe`、`factor_params`。池要绑定的因子任务是**成员所需市场的并集**（最多现货、永续各一个），每个成员只读它自己市场的 View；每个绑定的 View 都要有 `close` 列（账本按收盘价估值）。启用时把每个成员的策略 ID、DSL 文本、哈希和各自的绑定解析固化进会话的 `c_members_json`，之后改成员定义不影响已启用的池。保存池定义和启用时都会检查成员存在、能进池，且数据集的保留期装得下预热（预热期数加成员最长回看）。

**每期计算顺序**：
1. 每个成员各自做就绪判断（只看它自己用到的市场与因子）并求值，得到成员目标。没通过的成员（缺因子、因子被跳过、输入配置问题、求值被跳过）沿用它上一期的目标权重，按普通权重参与合成（不用保持标记，保持会挡住其他成员在同一个标的上调仓）；池整体只有所有成员都没通过时才记 `skipped`：原因优先取需要人工处理的原因（`config_error`、`history_insufficient`、`ambiguous_series`、`factor_changed`，实例据此标 `degraded`），否则取第一个成员的原因（就绪判断阶段与求值阶段同一口径），说明里列出每个成员的原因，状态原样保留，摘要里也带各成员的状态与原因（池详情里这些期不缺）。
2. 用到**上一期末为止**的成员净值序列算本期比例：
   - `fixed`：直接用 `ratios`；
   - `rotation`：每个因子在未爆仓的成员之间排名（名次从 1 起，并列取平均名次），按因子权重加权得综合名次分，取最小的前 `top` 名（与第 `top` 名并列的一并入选）平分 1。序列不够长、算不出某个因子时这一期不排名，未爆仓的成员均分；
   - 乘择时系数：净值严格高于 `window` 期均线取 1，否则取 0（序列不足 `window` 期取 1）；
   - 按 `step` 限制每个成员相对上期比例的变化（上期没有比例时不限制）。
3. 每个成员的模拟账本按成员目标推进一期（没通过的成员只估值、不调仓），追加本期期末净值；账本复用研究回放的账本（含手续费、粉尘阈值、缺价清算，永续逐期结算，不计资金费、不模拟强平与保证金率），初始权益 1。缺的期（没被处理的周期）净值沿用上一个值补齐。
4. 池目标 = Σ 比例 × 成员目标权重，按（标的, 市场）合成；成员冻结（因市场不可用或只缺上一根保持持仓）的标的在池里保持上期池目标，其余走与普通策略相同的组合约束与 `max_weight`（超出的部分留作现金，不分给其他成员）。
5. 模拟爆仓（成员账本权益不为正）：爆仓成员的比例一律为 0——不参与轮动排名，不受步长限制，`fixed` 也归零；择时系数照常按净值与均线计算并写进明细，只是最终比例被置 0；明细里标 `bankrupt`。

**轮动因子**（作用在成员净值序列上，`order` 可选 `asc` 或 `desc`；默认 `return`、`ma_ratio` 降序，`drawdown` 升序）：`return(w)` 区间收益 = 净值 ÷ w 期之前的净值 − 1（需要 w+1 个值）；`ma_ratio(w)` = 净值 ÷ 最近 w 期均线 − 1（w 个值）；`drawdown(w)` 最近 w+1 个净值上的最大回撤，越小越好。

**预热**：启用后后台用研究回放的历史读取，从启用时刻往前按真实历史依次求值所有成员、推进账本（成员之间共享行读取），一直推进到最新已收盘的一根（收盘超过宽限一分钟、View 里已有数据；研究回放把最新一根排除在外，预热不能——它的就绪事件在启用之前就发出了，没有别的路径会处理它），再写进会话的 `c_warm_state` 与 `c_warmed_through`。期数 = max(轮动因子与择时的最长窗口, 成员最长持有期) + 1。
- 预热完成前，触发器对这个实例返回等待（事件稍后重投、到达记录照写，完成后按 bar 顺序补处理，不丢期也不乱序），不允许 `confirm` 进入运行（返回“策略池预热未完成”，没挂账户的观察实例的自动确认也等它）；
- 完成后：不晚于预热终点的事件直接去重；实例还没有带状态的结果时，第一期从预热状态起算；之后照常走试运行与运行；
- 进程在预热中途重启：启动时对没有预热结果的池会话重新预热；停用再启用产生新会话，重新预热；
- 启用时按精确的覆盖统计核对 View 实际的历史够不够预热（不只看配置的保留期），不够就拒绝启用；
- 暂时性错误（Storage 暂不可用）按退避重试，永久性错误（数据覆盖不够、配置无效）或重试用尽时，实例标 `degraded`、触发器不再让事件等待，并留下一条 `skipped(pool_warmup_failed)` 结果，原因写在输入摘要的说明里（页面的历史结果直接可见），修复后重新启用；
- 预热结束后的第一期没有相邻记录，用到 `bars[-1]` 的成员会因“上一根版本未知”没通过一期（沿用上期权重），可以接受。

**已知局限**：
- 预热终点包含最新已收盘的一根，只靠一分钟宽限判断它的数据写完了：可能读到半截数据（那一期的成员状态按缺数推进、其正式事件被去重，之后的期次不受影响），也可能这一根的数据还没到而少推进一期（净值沿用上一个值补齐）；
- 绑定现货、永续两个任务的池与普通双任务策略一样要等两个 View 的事件都到齐才求值：一个 View 长时间不来事件，整个池都停（只有缺的 View 已经到了更晚的一期、或更晚的一期已经汇合时才补记 `skipped(market_missing)`）。“只缺部分市场时只把用到该市场的成员判为没通过”没有实现；
- 实时求值时每个成员各自读一次自己的行（只有预热共享读取），处理器按整个事件持锁串行处理所有实例；成员多、标的多时这段耗时要在 V3 的模拟盘上实测。预热耗时的实测（10 成员 × 168 期 × 500 标的，1.6 秒）用的是假客户端，不含 Storage 的网络与查询开销，只是下限；
- 池状态偏大（10 成员 × 500 标的约 26 KB/期），短周期的池每天写入的结果较多。

**结果与展示**：每期把池明细写进结果摘要 `summary_json.pool`（各成员的状态与没通过的原因、期末净值、基础比例、择时系数、步长前后的比例、综合名次分、总敞口、净敞口与各（标的|市场）的贡献），解释明细的规则 id 是 `成员 id/规则 id`，`rule_states_json` 里 `members` 是各成员自己的状态、`pool` 是上期比例、净值序列与账本。池的 skipped 记录也带完整状态。成员遇到需要人工处理的原因（`config_error`、`history_insufficient`、`ambiguous_series`、`factor_changed`）时，池照常出 `ok`，但实例标 `degraded`，且只要同一期里还有这类成员就不执行 ok 周期的健康恢复。**成员净值是按收盘价成交的模拟曲线，只用来分配资金，不代表实盘收益**（不模拟调仓阈值、最小下单额与拆单，也未计资金费与强平）。

### 因子任务、成员键与列名

策略不再自己声明因子：**创建实例时选定一个因子任务**（市场模式含现货和永续时有两种选法：现货、永续各一个，或统一数据集上的一个任务，登记为 `multi`；只能选本空间里运行中、还没有被别的实例关联的任务），规则里直接写任务结果数据集的列名。
实例第一次启用时对每个任务调用 `FactorMgr.BindFactorTask` 与任务正式关联，独占：一个任务只能被一个实例关联，一个实例可以关联多个任务；创建后实例的 `factor_tasks` 不能改。关联一直保留到删除实例：删除已停用的实例时，关联的任务和任务的结果数据集一起删除（见第 7 节「删除实例」）。
策略停止不影响因子任务，它照常计算，由用户手动停止。读取的 View 就是任务结果数据集的默认 View `view_factor_<后缀>`，由任务 ID 推导。

任务里每个成员对应哪些列由规则推导（完整说明见[因子](因子.md)的「成员键与列名」一节）：

```text
成员键 = 因子ID [ "__" 参数段 ]      参数段 = "var" | 值 { "_" 值 }      值里小数点写 p、负号写 n，只写值、按定义声明的参数顺序
列名   = 成员键 [ "__" 输出名 ]       单输出因子没有输出段
```

| 成员 | 列名（规则里直接引用） |
| --- | --- |
| `ema`，参数全为默认值 | `ema` |
| `ema`，span=20、warmup=50000 | `ema__20_50000` |
| `rsi`，参数全为默认值 | `rsi` |
| `boll`，window=30（多输出：mid/up/low/pctb） | `boll__30__mid` 等 |
| `ma_fast`，可变成员 | `ma_fast__var` |

要记住两条：**参数全为默认值时省略参数段**（所以默认的 `boll` 成员列是 `boll__mid`，不是 `boll__20__mid`）；**可变成员固定以 `__var` 结尾**。
创建实例选好任务后，页面会列出这个任务的全部列名（可复制）。校验时规则引用了任务里不存在的列，报错会列出最接近的几个列名并附上这个任务的全部列，不会只说“列不存在”。

### 动态调参

任务里的**可变成员**（`<因子>__var`）由策略逐期提交下一期的参数；固定成员的参数在加成员时写定，策略不能改。策略用 `factor_params` 声明每期如何求出可变成员的参数，键是成员键：

```yaml
factor_params:                # 可选：每期求出下一期的可变成员参数；键只能是任务里的可变成员键
  ma_fast__var:
    window:
      default: "20"                               # 统一值：数值表达式，按标的求值后取中位数（不引用列的常数就是它本身）
      per_subject: "10 + 30 * rank(vol_zf_std)"   # 可选：按标的求值，与统一值不同的标的进入覆盖
  ma_slow__var:
    window: "60"                                  # 简写：只写统一值

rules:
  - id: cross
    type: signal
    pool: [BTC-USDT]
    entry: "bars[-1].ma_fast__var <= bars[-1].ma_slow__var && bars[0].ma_fast__var > bars[0].ma_slow__var"
    exit: 'bars[0].ma_fast__var < bars[0].ma_slow__var || params("ma_fast__var", "window") > 50'
    weight: {total: 1}
```

- **读取实际用的参数**：规则或参数表达式里写 `params("成员键", "参数名")`（两个都是字符串字面量，成员键必须是可变成员的），值来自结果行的系统列 `__params`，即这一行上该成员**实际用的**参数；
  这一行没有这个值时是 NaN，与缺数的处理一致。用到 `params()` 的实例，实时求值和回放都会显式读取 `__params`。
- **启用实例**：先调用 `BindFactorTask`（幂等，换一个实例会被拒绝），再检查任务在运行、DSL 引用的列都存在于任务的结果列里、`factor_params` 的键都是任务里的可变成员、参数名是该因子声明过的；
  `resolved_json` 固化任务 ID、结果 View、各列所属成员的契约哈希（定义哈希加成员类型）与可变成员的参数声明。任务先于策略运行，可以已经积累了历史，不再有“私有因子集刚建、还没有数据”的等待。
- **参数输出**：只在正常周期的决策为 `ok` 且尚未过期时求值；追赶与过期周期只推进规则状态，不保存或提交下一期参数（正常求值后在提交时才过期的，丢弃已经算出的参数）。结果按因子定义的声明整理：没写出的参数取默认值，整型四舍五入，所有取值限制在声明范围内（被限幅会记入说明）；
  某个参数在所有标的上都没有有效值时，这个成员本期不提交（因子沿用上一次提交的值，从未提交过用成员的默认参数）。
- **投递**：下一期的参数写进这一期结果的 `c_next_params_json`，与结果**在同一个事务里**落库。独立的投递循环只投当前会话里**最新一条还没送达**的结果（更早的未送达记录被覆盖，直接跳过），
  调用 `FactorMgr.SubmitFactorParams`（请求号取结果 ID，目标期是这条结果的下一期），失败按退避重试（1 秒起、上限 30 秒），送达后写 `c_params_delivered_at`；
  被因子侧明确拒绝的写 `c_params_error` 且不再重试（因子侧只接受目标期不减的提交，重试的旧请求不会让参数倒退）。实例停用时当前会话里没送达的结果不再投递，重新启用从新会话的第一条结果开始。
  模块或实例暂停时不提交，因子沿用上一次的参数；观察实例（没有账户）同样提交。
- **滞后告警**：实例在运行、任务有可变成员、最近连续 `params.stale_alert_periods`（默认 10）期结果都没有送达参数时，导出 `moox_strategy_param_delivery_stale{space_id,instance_id}=1`，实例停止后解除。
  因子引擎积压追赶时不等策略，晚到的提交从下一个还没开算的期次起生效，每期实际用的参数以 `__params` 为准（见[因子文档第 11 节](因子.md)）。
- **不支持**：声明了 `factor_params` 的策略不支持试算（`ValidateStrategy` 只校验 DSL）与 View 回放（`StartReplay`）；研究回放用第 10 节末尾的闭环回放。

## 4. 处理流程

```text
ViewDataReady（View, period_time, universe_subject_ids, detail_type + detail：因子的 PeriodDetail，各成员含 definition_hash）
  ─► 找出绑定该 View 的全部启用实例，逐个处理，错误汇总；全部终态落库后才 ACK
  ─► 重复周期忽略；乱序周期 ─► skipped(out_of_order)
  ─► 汇合（只绑定两个因子任务的实例）：先把这个 View 的原始事件幂等写入 t_strategy_ready_events 并确认，两个 View 本期都到齐才往下走；
        更早、不会再等到齐的期补记 skipped(market_missing)（见下）
  ─► 标记追赶 / 已过有效期的周期：仍尝试求值，只推进状态，不发目标
  ─► 就绪判定（见下表）
  ─► 读取输入：只读绑定的 View，分页时固定活动索引与修订号，变化即整期重读
        标的元数据（标的绑定、标的详情、标签、标签成员）跨周期缓存，LoadBar 取得 View 后先读一次
        GetDataset 的 subjects_revision，与缓存一致才复用，变化则整体重读；行数据每期现读、不缓存
        基础集合 U = 事件名单 ∩ 活跃标的
        规则 r 的预期集合 E(r) = U ∩（显式 pool 或 universe 配置）
        年龄剔除 G(r)：E(r) 中不满足 min_age_bars 的标的（探针查询在当期主查询之后、固定同一修订号；通过探针的标的按 View 活动索引与 min_age_bars 持久化在 `t_strategy_age_passed`，之后跨周期、跨重启不再探针，只探针尚未通过的标的，全部已知时不发查询）；
                       规则上期已持有的标的不剔除
        可用集合 A(r)：E(r) − G(r) 中有行、所需列都有值、且所需列未被上游标记失败的标的
                       （signal 规则的持仓只需要 exit 引用的列，未持有的候选需要 entry 与 exit 的全部列）
        保持集合 H(r)：上期已持有且只因市场不可用或只缺上一根缺数的标的（不求值、不调仓，见下）
        普通缺数集合 M(r) = E(r) − G(r) − A(r) − H(r)；max_missing 同时计算 M(r) 与 H(r)
  ─► 纯函数引擎：守门 → rank / signal / tranche → 组合合成与约束
  ─► 正常周期：一个事务写入结果、解释明细与（绑定账户时）待投递事件
        追赶 / 过期周期：成功求值后只保存规则状态与摘要，结果为 skipped(catchup / expired)
  ─► 后台发布正常 ok 结果的 LogicalAccountTargetWeightRequested
```

正常周期的就绪判定按顺序：

| 情况 | 结果 |
| --- | --- |
| 引用的列所属的成员不在事件明细（`detail_type=moox.factor.PeriodDetail.v1` 的 `PeriodDetail`）里，或 `definition_hash` 为空，或明细无法解码 | `skipped(factor_missing)` |
| `definition_hash` 与启用时固化的值不同 | `skipped(factor_changed)`，需要重新启用实例 |
| DSL 经 `bars[-1]` 读取了因子列，本实例对恰好上一根没有可信的处理记录 | `skipped(previous_version_unknown)`，这条记录保存本期指纹，下一期即可求值 |
| DSL 经 `bars[-1]` 读取了因子列，可信的上一根记录里这些因子的指纹与本期不同 | `skipped(factor_changed)` |
| 因子本期 `skipped` | `skipped(factor_skipped)` |
| 多市场策略里选币市场或所有市场整体失败（见“一个市场整体失败也算不可用”） | `skipped(market_failed)`，数据类原因，不计实例故障，不属积累中 |
| 因子 `degraded` | 继续；失败标的只对引用该因子的规则算缺数 |

追赶与过期周期的结果归类有所不同：输入就绪时调用同一引擎求值，只有引擎给出 `ok` 决策才保存推进后的状态；守门跳过时只写没有规则状态的 `skipped(catchup / expired)`。追赶期间的就绪失败通常记 `catchup` 并在输入摘要中附上就绪原因，但 `factor_changed` 仍单独记录；首次收到就已过期的周期，就绪失败统一记 `expired`。读取输入或求值产生配置、历史不足、重试耗尽等错误时，仍按相应原因记录，不能只凭 `catchup` / `expired` 或追平状态推断规则状态已推进。

可信的上一根记录：同一实例、同一 View、同一 bar 与日历、`bar_end` 恰好早一根、含经 `bars[-1]` 读取的全部因子的
指纹；不限会话，优先当前会话。首次运行或漏掉相邻周期时，经 `bars[-1]` 读取因子列的实例会先跳过一期；启用或重启本身不强制跳过，只要已有可信的相邻记录就可继续。恢复追赶会补记周期指纹，见第 7 节。`bars[-1]` 只读 K 线列（例如 `bars[-1].close`）的实例没有上一根的版本需要核对，不受影响。

守门：基础集合 U 为空（本期没有任何标的的数据，事件的空名单同样按空处理）整期 `skipped(no_data)`；
rank 规则没有可评估的候选（E(r) 为空或全部年龄剔除）、进入 filter 的可用标的少于 `min_universe` 时
`skipped(universe_too_small)`；任一规则（rank 与 signal）缺数占（预期 − 年龄剔除）的比例超过 `max_missing`
时 `skipped(too_many_missing)`，signal 规则不受 `min_universe` 约束。多市场策略只有一部分市场不可用时缺数检查有两处收窄（永续整体不可用、只剩冻结空头的空头规则不做缺数检查；别的规则持有、因市场不可用冻结的标的不计入缺数），见第 3 节“市场模式”里的“一个市场整体失败也算不可用”。守门跳过时不产生目标，规则状态沿用前序。

`min_age_bars` 应不小于规则引用的因子的回看（因子定义页与 `GetFactor` 的 `lookback_periods`）：因子按严格窗口计算，
新上市标的在回看凑满之前的因子值是 null，`min_age_bars` 更短时这些标的会进入候选、却因因子为 null 被跳过。

**年龄按任务结果 View 的覆盖判断**：因子任务可以先于策略运行积累历史，结果 View 的覆盖起点就是任务开始产出结果的时间（加成员不自动补算历史，需要更早的因子值用补算）。`min_age_bars` 大于结果 View 已有的根数时启用被拒绝，等任务积累够再启用。用到 `bars[-1]` 因子列的规则，第一期没有上一根的处理记录，整期以 `previous_version_unknown` 跳过，第二期起正常。

`min_age_bars` 的判定：以本期为 T，读取 `[T−(N+1), T−(N−1)]` 三根的 `close`，有行即满足。候选全部没有行时，
再确认这三根内整个数据集是否有数据：一行都没有是历史缺口（停机或维护），整期 `skipped(history_insufficient)`，
不会把全部标的当作新上市剔除；规则上期已持有的标的在建仓时已满足要求，不因窗口内的偶然缺数被剔除。回放与实时一致：标的在一次回放中通过年龄判定后保持通过，之后窗口缺口不再把它重新剔除；整窗为空时，只有从未通过的候选才按历史缺口跳过。
只有设置了 `min_age_bars` 的实例每期读取 View 的覆盖统计，且只用 Storage 已缓存的统计、不触发全量统计（未缓存时
由上面的确认查询兜底）；活跃序列的覆盖起点以本期 T 与索引最新一根中较早者为基准计算，索引已经写入更新的 bar
（处理滞后、重投退避）不影响对第 T 根能否追溯 N 根的判断；探针窗口的日历换算失败（例如超出内嵌日历）是确定性的，
记 `skipped(config_error)` 而不是重试。DSL 引用的标签每期核对一次：运行期被删除时整期
`skipped(config_error)` 并标记 `degraded`，不让 `exclude_tags` 悄悄失效或按标签选的池变空。

**监控口径**：因历史不足（`history_insufficient`）或上游因子这期被跳过（`factor_skipped`）而跳过的周期（`market_failed` 不在其中：它是多市场策略的整体失败，持续出现要走数据集新鲜度告警），在“积累期上限”内向 Monitor 报告为 `partial`（数据积累中）：数据集页面显示降级、不告警；模块健康检查记一次成功（模块在正常处理事件，只是无需求值），不计失败。数据重置、新建因子任务后一定会有这一段，数据攒够自动恢复。积累期从实例第一次因这类原因跳过起算，上限是 `min_age_bars` 根 K 线对应的时长与 72 小时的较大者再加一小时，出现一次 ok 就清零重算；超过上限仍然不足说明不是在积累（例如 `min_age_bars` 超过 View 保留的根数），回到原来的失败处理（模块健康失败与数据集告警）。计时只在进程内，重启后重新开始。

组合合成：各规则权重按（标的, 市场）相加（做空为负）→ `max_weight` 按币合计截断，超出部分留现金 → 现货部分超过预算、`gross` 超过
`leverage` 时按比例缩小 → 现金 = 1 − Σw（混合市场改为现货 net、永续 net）；现货出现负权重仍整期 `skipped(config_error)`。选择阶段合法地选出
0 个标的仍是 ok，表示转为现金；守门防止池被意外清空。

**已持有标的的冻结保护**：rank / signal 规则中，上期组合目标非零的标的，若所有相关规则的缺数原因都只是所在市场本期整体不可用（`market_unavailable`，只在多市场策略里出现），或当期完整、仅缺 `bars[-1]` 的值，就进入保持集合 H：不判 exit、不重新排名或配权，目标带 `hold=true`，要求 Trade 保持当前数量。signal 已持有标的只检查 exit 引用的列；tranche 不参与冻结保护。H 在明细中为 `held(prev_hold)`（只缺上一根）或 `held(market_hold)`（所在市场本期不可用），独立于普通 `missing` 计数，但仍计入 `max_missing` 的缺数比例，不能把被保护标的算成可用。

保持目标以其上期权重预留预算（冻结时按标的展开成上期所有非零的（标的, 市场）键），其余目标的总敞口超过剩余预算时按比例缩小；预算不足时其余目标归零。保持权重只是预算占用，不要求 Trade 按当前权益重新换算数量。

混有其他缺失原因（普通因子失败、K 线失败、无行或无失败证据的当期缺值）的标的不受保护：通过整期守门后，rank 的 buffer 不保留它，signal 的 exit 缺值视为退出，holding 批次把它移出、份额留现金。上期持有、本期已不在预期集合中的标的（退市、移出标签）记 `dropped(not_expected)`。

解释明细中每个（规则, 标的）只有一条，`reason` 取值：

| 原因 | 含义 |
| --- | --- |
| `min_age_bars` | 年龄不足（阶段 `aged_out`） |
| `no_row`、`missing:<列>`、`missing:bars[-1].<列>`、`factor_failed:<列>`、`source_failed:<列>` | 缺数（阶段 `missing`）；`factor_failed` 是因子对该标的失败，`source_failed` 是 K 线 View 声明该标的本期失败 |
| `prev_hold` | 已持有标的当期输入齐全、只缺上一根（`bars[-1]`）而保持数量（阶段 `held`），仍计入缺数比例 |
| `market_hold` | 多市场策略里已持有标的因所在市场本期整体不可用保持数量（阶段 `held`），计入缺数比例的口径见“一个市场整体失败也算不可用” |
| `filter` | 未通过 filter |
| `score_invalid`、`score_error:<信息>` | 分数无效或计算出错 |
| `select.where`、`not_selected` | 已打分但未入选 |
| `not_rebalanced` | holding 规则的非建仓 bar 上未被任何批次持有 |
| `filter_after` | 选中后被 filter_after 剔除 |
| `holding`、`holding:<原因>` | 只由延续批次持有；带后缀时表示本期在该阶段被淘汰但仍按批次持有 |
| `exit`、`no_entry`、`entry_and_exit` | signal 规则的退出、未触发入场、入场与退出同时成立 |
| `not_expected` | 上期持有、本期已不在预期集合 |
| `stop_loss`、`trailing_stop`、`take_profit` | 本期止损止盈失去全部权重（阶段 `stopped`）；可能附上原有原因，如 `stop_loss;missing:x` |
| `…;stopped:<n>` | 仍有权重，但本期有 n 个持仓单位止损（holding 的其他批次、tranche 的其他开仓记录还持有） |
| `cooldown` | 止损后冷却中，不能入场（阶段 `dropped`） |
| `tranche:<n>`、`tranche_filter_after`、`volume_zero` | tranche 规则：由 n 个子策略持有；被全部子策略后置过滤剔除；本期无成交不作为候选 |
| `market_unavailable:<列>` | 标的所在市场本期整体不可用（那个市场的因子本期被跳过）；可冻结已持仓的标的，计入缺数 |

### 汇合求值（绑定两个因子任务的实例）

现货、永续各有一个因子任务和结果 View，完成时间不同，所以实例等两边都到齐再求值一次：

1. 一个 View 的就绪事件到达，只把原始事件（按字节，`readiness.Check` 要用整条事件）幂等写入 `t_strategy_ready_events` 并确认，不求值。
2. 写入后检查本期所有绑定的 View 是否到齐。到齐就对每个 View 的事件各跑一次就绪判断，再合并结论：配置、契约类原因（`factor_missing`、`factor_changed`、`previous_version_unknown`）整期按该原因处理；数据类原因（某个市场的因子被跳过 `factor_skipped`）只让该市场本期不可用，需要的市场全部不可用时仍按原因整期跳过。基础集合用各 View 事件里的标的名单。同一期已求值的不重复求值。
3. 不加定时器。只在两种情况下把更早还没汇合的期补记为 `skipped(market_missing)`（另一个市场的数据未到）：缺的那个 View 本身已经到了更晚的一期（它跳过了这一期）；更晚的某一期已经汇合完成并求值。补记在提交更晚一期之前完成。两个 View 稳定相差一根以上是正常情况（永续标的多、算得慢），此时不补记；有效期本来就容许两根的延迟。`market_missing` 属于数据未到，不标记实例 `degraded`，不计入模块健康失败。
4. 迟到的那一半事件到达时，那一期如果已补记过，按乱序规则忽略。
5. 触发器的放行检查返回等待（`ModeWait`）时事件返回重投、不确认，到达记录照写；返回 `ModeOff` 时沿用直接确认、不写记录。
6. 结果的输入记录（`c_input_json`）每个 View 一份事件 ID 与因子指纹（`views`），下一期的相邻周期检查按 View 比对。

只绑一个任务的实例到达即算到齐，直接用手上这条事件，不写到达记录，行为与以前逐位一致。统一数据集（方式 B）只有一个 View，也是到达即求值；它的一份事件按序列拆成各市场的结论，再用同一套合并规则（数据类原因只让对应市场不可用，所有用到的市场都不可用时整期按原因跳过）。

补充说明与已知边界：

- 两个 View 都已记下、只是还没求值的期（例如事件被要求等待期间两期都被记下，放行后先重投了较晚的一期）不是缺数据：处理当期之前先按 bar 顺序把它们求值，不会补记 `market_missing`；补记只针对确实缺一个 View 的期。
- 补记的 `skipped(market_missing)` 记录没有因子指纹（缺的那个 View 没有事件，也没有跑就绪判断），所以下一期若经 `bars[-1]` 读取因子列，相邻周期检查找不到可信记录，会按 `previous_version_unknown` 跳过一期。
- 选币市场整体不可用时（`select` 为单个市场，如 `spot/swap` 的现货因子被跳过）没有候选池，整期按 `factor_skipped` 跳过；只有下单市场不可用时选币照常。
- 暂停（`ModeOff`）期间一个 View 的事件被直接确认、不写记录，另一个 View 若在暂停前已记下，这一期不会再凑齐：它会在更晚的一期到齐后被补记为 `market_missing`，暂停期间的周期按本来的规则不求值。
- 一个 View 长期不再到达（例如那个任务被停掉）时，另一个 View 的每一期都停在“等另一半”，补记只在缺的 View 出现更晚一期或更晚一期汇合时发生，没有定时器，也没有单独上报：靠实例的数据集新鲜度告警发现。
- 组合约束的摘要文本：单市场策略现货超过预算、`gross` 超过 `leverage` 时按比例缩小，摘要里的说明文本是“总敞口 … 超过 portfolio.leverage … 按比例缩小”或“现货部分总权重 … 超过现货预算 …”，与以前的报错文本不同。

## 5. 失败语义

| 情况 | 处理 |
| --- | --- |
| 解码失败、事件契约错误 | TERM |
| Storage / Factor 瞬时错误 | 重投重试；同一事件对同一实例超过 `evaluation.attempt_budget` 次后记 `skipped(infra_retry_exhausted)` 并 ACK。Storage 与 Factor 返回的错误只给中文概述与错误码，服务端原文（可能是英文、带内部细节）只写日志 |
| 终态记录落库失败 | 不 ACK，按投递次数指数退避（2 秒起、最长 30 秒）重投，直到落库成功；消费者逐条拉取，一个 View 的重试不拖住其他 View |
| 结果校验失败或违反表约束（确定性写入错误） | 记一条不带明细的 `skipped(config_error)` 并 ACK，实例标记 `degraded`；兜底的 skipped 也被拒绝时记错误日志、计入模块健康失败后 ACK，不无限重投 |
| EventBus 重启（拉取请求收到 Server Shutdown） | 消费循环退出后自动按退避重建消费者，期间 `/readyz` 不就绪；不需要重启 Strategy |
| 启动时 EventBus 不可用 | 进程照常启动、接口可用，消费者与出站投递在后台按退避重连，连上之前 `/readyz` 不就绪 |
| 目标事件发布得不到确认（EventBus 重启、断网导致确认丢失） | 单次发布最多等 `eventbus.publish_timeout`（默认 10 秒）；一批中遇到第一个发布失败立即断开重连，不再让同一批其余结果逐条等满超时；重连后重发，`result_id` 作为 Msg-Id，重发会被去重。连接、探针与投递异常写日志，同一条连续出现只记一次，恢复后再记一条 |
| 目标事件无法通过契约校验或超过 EventBus 最大消息长度（永久发布错误） | 该结果标为 `cancelled`、不再重试并写日志，不阻塞其后的结果 |
| 发布期间更新的 ok 结果把这一行取消，而事件已经发出 | 仍记为 `sent`，如实反映投递状态；取消计数（`superseded`）只增不减、不回退，这类结果另计 `moox_strategy_target_sent_after_cancel_total`。发出后把这一行记为 `sent` 时数据库出错，这一行可能随后被新结果取消，而事件其实已经发出（至多一次的记账缺口，Trade 以最新目标为准） |
| 周期无法按日历换算（A 股内嵌日历已过期、周期不在交易日或交易时段的桶上） | 写日志并计入模块健康失败后 ACK（同一事件因其他实例需要重投而再次投递时不重复记日志与计数）。周期的有效期要推到其后 2 个交易日，内嵌日历的最后 2 个交易日的周期已推不出有效期，实际可用截止日是“最后一个交易日往前 2 个交易日”：截止日前 30 天起 `/readyz` 给出 `calendar_warning`，过了截止日不就绪，也不能再启用 A 股实例（沿用待定会话的启用同样检查）。报错都是中文，带日历的覆盖范围与推进前的那一天。A 股日线的行键必须是交易日的上海零点：按 UTC 零点写行却声明了 `cn_stock` 的数据集换算失败，不会被静默规整成一直读不到行；A 股日内周期的行键是真实的开盘时刻（UTC）。内嵌日历的第一个交易日没有上一根，`bars[-1]` 的值都缺失。二进制内嵌时区数据，主机缺少 tzdata 也能换算 |
| 会话快照（`resolved_json`）损坏 | 退回实例上的同一份副本取日历与周期，跳过记录仍按正确的周期写；两份都无法解析时无从确定周期，只记日志并计入模块健康失败后确认（不写记录、不标记实例；同一事件因其他实例而重投时不重复计数） |
| 事件的 View 不是实例绑定的 View | 不处理：Strategy 只按绑定的 View 找实例，不再按完成来源或事件类型过滤；因子结果 View 的事件带因子明细，K 线 View（含重采样 K 线）的事件没有明细 |
| 提交时发现更新的记录 | 重读后分类：同周期视为重复、更早视为乱序，否则重新求值一次 |
| 首次收到时、求值完成时或提交时已过有效期 | 输入就绪且引擎成功求值时保存推进后的规则状态，记 `skipped(expired)`，不投递目标或下一期参数；未成功求值时不推进状态 |
| 列被删除（含只在 `bars[-1]` 中引用的列与 `min_age_bars` 探针读取的 `close`）、View 被停用或删除、View 周期或数据集变化、同一标的多个序列 | `skipped(config_error / ambiguous_series)`，实例标记 `degraded`，页面提示重新启用 |
| View 活跃序列的覆盖起点晚于 `min_age_bars` 的目标根，或探针窗口内整个数据集都没有数据（已有标的通过探针的缓存时，窗口缺口不再整期跳过） | `skipped(history_insufficient)`，实例标记 `degraded`；不会把全部标的当作新上市剔除 |
| 绑定的因子定义变化 | `skipped(factor_changed)`，实例标记 `degraded`，重新启用后恢复 |

**统一数据集（同一数据集里有现货、永续两条序列，方式 B）。** 策略侧已支持，规则见“市场模式”里的“两种输入方式”：上表的 `ambiguous_series` 在统一数据集上只在同一个市场内判断（现货、永续两条序列并存不是歧义），单市场数据集的行为不变；
因子明细的 `failed_series`、`skipped_series_tags` 拆成各市场的结论（只让对应市场不可用；全部 tag 都跳过才是 `skipped`，部分跳过是 `degraded`）。
永续整体晚到而不是被跳过时（时序因子的所有永续序列都在 `failed_series` 里），按“一个市场整体失败也算不可用”处理，持仓冻结。
已知边界（早已存在）：统一数据集上纯 `swap/swap` 策略（只涉及一个市场），永续标签里有、但因子没有期望永续序列的币（既没有行也不在失败名单里，如刚新上永续标签、`universe_series` 里还没有这条序列），方式 B 把它算缺数、方式 A 的永续数据集里没有它所以不算；`min_age_bars` 为 0、`max_missing` 很紧时，这种币会让方式 B 持续整期 `too_many_missing`。需要时把 `max_missing` 放宽，或等因子的 `universe_series` 补上这条序列。

实例健康：`degraded` 表示最近一期因配置或数据问题跳过，下一个 ok 周期自动恢复（健康标记只作用于仍以同一会话
启用的实例，对账自动停用时标记的 `degraded` 不会被并发提交的 ok 周期抹掉）；`session_unverified` 表示
Trade 会话结果未知（启动或对账时 Trade 不可达），只有再次核实成功才恢复，ok 周期不会清除它。

`skipped` 不取消任何待投递目标。普通跳过只推进处理记录，规则状态为空；追赶或过期周期成功求值后的 `skipped(catchup / expired)` 会保存规则状态与摘要，目标为空，也不保存逐标的解释明细或下一期因子参数。下一次求值从**同一会话最近一条带非空规则状态的记录**恢复（`LatestState`），包括这些只推进状态的 skipped。只有新的 ok 目标才替代旧目标。

**持仓冻结**：因子本地数据写入时保证连续，回看窗口里没有空洞，逐币的因子失败（`factor_failed`）不冻结持仓。已持有（上期组合目标非零）的标的，只要在所有引用它的规则里缺失的原因全部是所在市场本期整体不可用（`market_unavailable`，见“一个市场整体失败也算不可用”），或只缺上一根（`bars[-1]`）而当期输入齐全，就**冻结**：不判 exit、不从目标移除、持仓数量保持不动，明细阶段为 `held`（原因 `market_hold` 或 `prev_hold`）；混有其他原因（因子失败、K 线失败、无行、值缺失而没有证据）时完全按缺数处理（signal 规则 exit 输入缺失清仓，rank 规则移除）。冻结的标的在组合里预留预算（取上期组合目标权重，写回状态供下一期继续保持），其余标的在剩余预算内按比例缩小（只缩小不放大）；保持目标带 `hold` 标记发给 Trade，Trade 不换算数量也不调仓。冻结的标的仍计入 `max_missing` 的缺数比例。holding 规则里含冻结成员的批次延后重建，保持解除后补建。

| 表 | 内容 |
| --- | --- |
| `t_strategy_defs` | 定义：名称、DSL 文本、`dsl_hash`；软删除 |

| `t_strategy_result_items` | 解释明细（`c_market` 是入选的权重进入的市场，其余是所选行所在的市场；冻结标的按规则方向取上期持仓所在的市场——多头规则取正权重持仓的市场，空头规则取永续，所选行来自另一个市场时也一样；空头规则里因永续下架按无行处理的持仓标永续），带与所属结果相同的 `c_ctime`（有索引），默认保留 90 天，按批清理 |

| `t_strategy_replays`、`t_strategy_replay_bars` | 回放任务（含从实例发起时的来源实例与会话、DSL 版本哈希、按市场保存的因子任务与结果 View、提交时各 View 校验区间所用的活动索引代次、现货与永续两个费率）与每期记录（含期末现货市值与永续净名义价值）；默认保留 90 天，且每个空间只保留最近 50 个已结束的回放（只在已结束的回放里排名次，排队与运行中的不计入也不删除；每期都记录持仓账本，一个长回放可达数十 MB） |

**升级与重建**：Strategy 打开库时会校验已有表的定义与当前 schema 一致，不一致就拒绝启动，所以改了已有表的版本要重建策略库（实例沿用原来的 `instance_id` 重新创建，因子任务的绑定与长回看因子不用重算）。两处已有表的定义变了：`t_strategy_instance_tasks.c_market` 的 CHECK 加上 `multi`（S1.8），`t_strategy_age_passed` 的主键加上 `c_market`（S1.8）。S1 的重建（实例任务子表、回放表的按市场字段等）与 S1.8 的这两处如果分两次发布，库要重建两次；同一次发布则一次重建即可。

已停用的实例可以删除，删除时连同它在本库的全部记录（见第 7 节「删除实例」）；定义只能在没有实例引用时删除；实例在的时候，会话、DSL 版本与结果一直保留，
历史结果的解释始终按当时的 DSL 版本与绑定展示。投递状态只有 `none`（观察实例或 skipped）、
`pending`、`sent`（已被 broker 确认，不代表 Trade 已接受）和 `cancelled`。

## 7. 实例生命周期

> **启用后的实例自动 init、start**：每个生命周期周期（30 秒）对未初始化、就绪的启用实例自动执行 init 与 start，进入试运行（求值，只发带影子标记的目标，Trade 不下单），
> 不必逐个执行命令；**没有挂账户的观察实例随后自动 confirm 进入运行**（它不会真实下单），挂了账户的实例的 `confirm` 仍由用户执行（真实下单的实例不会自动放行）。检查没过、手动暂停、恢复追赶、重置中的实例不动。
> 因子任务由因子引擎独立推进生命周期（见[因子](因子.md)生命周期一节），与实例的阶段互不影响；任务刚建、结果 View 还没有数据时（`min_age_bars` 检查）启用可能因“还没有数据（覆盖范围未知）”被拒绝，等任务算出几个周期后再启用。

> 暂停与恢复追赶：实例暂停（手动 / 系统 / 自动）时不求值、不发新目标，持仓不动。恢复先进入**追赶**：追赶期间到达的因子完成事件记录周期与因子指纹；输入就绪且引擎成功求值时，所有规则类型都推进规则状态（包括 tranche 的开仓记录、持有计数与止损状态、rank/signal 的理论持仓），结果仍为 `skipped(catchup)`，不发目标、不提交下一期因子参数。有效期已过的迟到周期同样尝试推进状态，结果记 `skipped(expired)`；就绪检查、守门或求值失败时不会推进状态，具体分支见第 4 节。引用上一周期因子列的策略仍需要相邻周期指纹。
> 追赶目标取当前时间减去 1 分钟宽限后最近已收盘的 bar，已处理记录达到该目标即判追平，给刚收盘但因子还没送达的周期留出时间。此判定不保证每个历史周期都完成了状态推进。放行时控制器记下放行时间，BarEnd 不晚于它的周期即使放行后才到达，也走追赶分支；重复或乱序周期先按去重与乱序规则处理，不会补发交易目标。
> 状态推进使按时间顺序送达、输入就绪且成功求值的追赶周期能延续理论状态；暂停时已忽略的事件不会自动重放，漏期、跳过或实际未成交也不能据此推断实盘持仓与连续运行一致。
> 单独恢复因子引擎而策略一直在运行时，历史事件若仍在 2 根有效期内，仍可能生成交易目标；过期后只尝试推进状态。需要统一控制放行边界时用 `moox-cli system pause|resume`（先暂停策略）。

- 启用：解析绑定（因子任务 → 结果 View → 数据集 → 源数据集的市场类型 → 列与成员契约）→ 第一次启用时 `BindFactorTask` → 编译 →
  写入会话快照 → 把会话挂到停用的实例上 → 绑定账户时向 Trade 认领会话 → 置为启用。挂会话与置为启用都对
  会话做比较交换：会话必须属于该实例、未关闭，并与实例当前引用的定义版本和因子任务一致；期间实例被改定义、定义
  被修改或会话已被对账释放时拒绝，挂不上的会话立即关闭、不交给 Trade。启停与对账都在实例当前
  定义的锁内拿锁后重读，等锁期间实例被改到别的定义时换锁重试；停用对账只处理与列表快照里同一个会话。
  市场类型取源数据集属性 `market_type`，没有时取其标的范围标签的属性 `market_type`（支持 `spot`、`swap`、`equity`）；
  A 股（`equity`）按现货处理：现货与 A 股 View 都拒绝 `leverage > 1` 与做空（tranche 只许按权重持有且不做空）。A 股目前没有交易账户，绑定账户时 Strategy 的账户归属检查（`internal/tradeowner`）
  以“市场不受支持”拒绝，只能建观察实例（不发目标）。日历取 View 数据集的属性 `calendar`；数据集没有声明时，只有因子结果
  （`dataset_role=factor_result`，沿用源数据集的行键）继承源数据集的 `calendar`，重采样等按自己的对齐方式写行的派生
  数据集不继承；都没有时为 `crypto_24x7`。`cn_stock` 使用内嵌的 A 股交易日历（`packages/marketcalendar`），支持 1d 与
  barclock 允许的日内周期（能整除两个交易时段，例如 5m；45m、4h 拒绝）：日内周期由 `packages/barclock` 按交易时段切分，不跨午休
  （`input/calendar_session.go`），1d 沿用按交易日推进的实现。A 股数据集必须显式声明 `calendar: cn_stock`（Collector 建的采集结果数据集会自动写上），
  否则会按 7×24 计算周期；按 UTC 零点对齐（`alignment=epoch_utc`）的数据集不能使用 `cn_stock`。数据集保留期换算根数时，
  A 股按每年 244 个交易日 × 每个交易日的根数折算（5m 每天 48 根）。设置了 `min_age_bars` 时，View 必须提供 `close` 列，N 不超过
  View 每个序列保留的根数，且以最新一根为 T、T − (N−1) 根不早于活跃序列的覆盖起点；覆盖范围未知（索引还没有
  任何行）时拒绝启用。A 股日线实例不论是否设置 `min_age_bars`，启用时都读取覆盖统计并检查最晚一行的行键是上海
  零点：按 UTC 零点写行的数据集在启用时就被拒绝，而不是启用后每一期都读不到行。没有 `min_age_bars` 时只校验行键
  （覆盖范围不影响实时求值），新建的 View 只有未来行或当天一行也能启用。覆盖范围只在需要时向 DataView 读取该 View 活动索引的统计（`min_data_time` / `max_data_time`，两端包含，是真实存在的行键，
  View 进程至多每 5 分钟刷新一次；启用与回放要求精确统计，未缓存时现算）；索引的最早时间可能来自已停更的
  序列、只会提前不会推后，因此活跃序列的覆盖起点取它与“最新一根往前 `retained_rows_per_series`−1 根”中较晚者。
  `retained_rows_per_series` 是活动索引建立时记录的保留根数与当前配置中较小的一个（调大配置要等索引重建后才变大），
  为 0 表示未知，此时不做依赖它的检查。
  标的只按显式声明的 `series_tag` 属性过滤序列，没有声明时不过滤。DSL 引用的标签必须存在，固定写出的
  标的（`pool` 列表、`include`、`exclude`）必须在 View 的数据集中有绑定。绑定账户时，同一空间里该账户已被
  另一个启用实例持有则在写会话、认领之前拒绝，被拒绝的启用不留下待定会话。
- 重复启用不新建会话；绑定账户时会核对 Trade 的所有者仍是本会话。只有上次未完成的启用留下的待定会话
  （未关闭且定义未变）会被沿用；停用后释放未确认的旧会话必须先在 Trade 侧确认释放，然后新建会话并重新
  解析绑定，规则状态从零开始。
- 停用：先持久化停用并关闭会话，再向 Trade 释放；释放确认前保留会话，后台每 30 秒对账重试。
  停用不会撤单或清仓。
- 停用与关闭会话在同一个事务里完成；Trade 对释放返回所有权冲突或账户不存在都视为已释放。
- 进程启动时与之后每 30 秒的对账循环：完成未结束的停用握手，并核对每个启用实例的 Trade 会话。Trade 明确
  拒绝（所有者已变或账户不存在）的实例自动停用、标记 `degraded` 并计入模块健康失败；结果未知（Trade 不可达）
  的标记 `session_unverified`，核实成功后恢复。对账问题不阻止进程启动，接口始终可用于人工修复。

**删除实例**（`DeleteStrategyInstance`，CLI `strategy instance delete --instance-id <实例>`，管理台运行实例列表的“删除”）：

- 只能删已停用、没有会话的实例；挂着组合账户也能删，账户绑定随实例一起清掉。实例不存在返回成功。
- 全程持有实例锁（锁的是整个策略定义），并发的启用被挡住。不加状态列，靠每一步幂等支持重试。
- 逐个读实例登记的因子任务（`GetFactorTask`）按绑定分组：只有绑定到本实例（`bound_instance_id` 等于实例 ID）的任务随实例删除；
  没绑定或绑定到别的实例的任务（例如默认的公共任务）保留不动，只去掉本实例的引用；Factor 里已经没有的跳过。从没启用过、启用到一半的实例也能删。
  要删的任务必须与实例在同一个空间。
- 所有拒绝都在删第一个任务之前做完：
  - 有回放在排队或执行、会读到这个实例的数据时拒绝，先取消回放：从实例发起的回放，以及本空间里按定义或 DSL 发起、读取要删的任务的回放。
  - 对每个要删的任务先调一次 `DeleteBoundTask(check_only)`：Factor 做完动手前的全部检查（关联的实例、没有补算在排队或执行、结果数据集没有被默认 View 之外的 View 引用），不做修改。被拒绝时按原类别透传（参数错误）。
  - 用 archive-mgr 的 `ListArchiveTasks` 分页拉回空间内全部归档任务，在本地按要删任务的结果数据集筛选；有归档任务就拒绝，列出归档任务（按 `空间/数据集` 标识），先到归档页删掉。读不到归档任务也拒绝。没有要删的任务时不查归档。
- 逐个调用 Factor 的 `DeleteBoundTask` 删除任务、成员与结果数据集（结果数据不可恢复）。
- 最后在一个事务里删除实例在策略库的全部记录：会话、结果与解释明细、汇合到达记录、回放与回放明细、外显设置、因子任务登记和实例本身；`t_strategy_age_passed` 按删掉的任务的结果 View 删除，保留的任务不动。
- Trade 里的影子目标、目标回执、订单都留着，作为交易审计。
- 失败的响应带 `incomplete`：为真表示已经开始删（之后的失败），再删一次即可接着做完，CLI 和管理台提示“删除未完成，请稍后重试”；为假表示什么都还没删，原样提示。
  没拿到响应（超时、连接中断）按删除未完成处理。调用 Factor、archive-mgr 的截止时间比请求提前 5 秒，给最后那个事务留时间。
- 任务删完、实例记录还没删时失败，实例保持停用。停用实例上只要有引用的任务已不存在（删除没做完，或任务被另外删掉，两者不区分），列表与详情就用 `missing_factor_tasks` 标出，
  `setup verify` 在说明里标出，提示“引用的因子任务已不存在，删除实例即可清理”；启用会在写会话之前报同一句。
- 清空大数据集期间同一定义下的其他实例不能启停；删除的路由超时是 30 秒。

### 7.1 运行阶段与试运行

> 状态：已实现（设计 6）。实例是 `packages/lifecycle` 的对象（`strategy_instance`），阶段与颜色同[因子](因子.md)：未初始化、未就绪、就绪、试运行、运行、暂停、故障。

- **试运行与运行处理正常周期，追赶只推进规则状态**：就绪的实例要先 `moox-cli lifecycle start --endpoint <策略健康端口> --kind strategy_instance --id <实例>` 进入试运行，再 `confirm` 进入运行（观察实例会自动 confirm）。
  `init` 检查实例仍然启用且有会话；`degraded` 等非 `ok` 健康状态只产生 warning，继续求值，避免“暂停后无法靠成功求值恢复”的循环。按跳过原因修复数据或配置；因子定义变化需要重新启用以更新绑定指纹。
- **试运行**：正常求值，目标事件带 `shadow=true`；Trade 对影子目标只完成权重到数量的换算并记录（`t_shadow_targets`），不预留资金、不下单。
  `moox-cli lifecycle shadow --space-id <空间> --id <实例>`（按 moox.toml 自动连 Trade） 查看影子订单。确认后进入运行，之后的目标是正式目标。
- **暂停（包括手动、模块检查失败自动暂停、没有启动）= 不求值、不发新目标、持仓不动**，不能用空目标表示暂停（Trade 把空的 FULL 目标解释为清仓）。暂停期间到达的事件不留周期记录；恢复先进入追赶，期间以 `skipped(catchup)` 留下周期与指纹，输入就绪且成功求值时同时推进状态。放行后只有晚于放行时间且未过期的周期才可能发出目标；更早的周期仍走追赶分支。正常周期仅在相邻版本证据确实缺失时才记 `previous_version_unknown`。
- **模块自身暂时未就绪（刚启动、检查有失败项且没有暂停等控制意图，例如重启后出站 EventBus 还在连接）不算暂停**：到达的就绪事件不确认、不留记录，按退避（2 秒起，最长 30 秒）重投，就绪后照常求值，重启窗口里的周期不会丢；超过有效期才处理的周期照常记 `skipped(expired)`。启动后模块还没就绪时每秒检查一次（最多 1 分钟），出站连接一建立就放行，之后回到每 30 秒一次。
- **策略池实例预热期间**同样返回等待（放在放行与追赶判断之前），并拒绝 `confirm`，细节见第 3 节“策略池”。
- 阶段持久化在数据库旁的 `lifecycle.json`；重启后先跑检查，通过就回到重启前的阶段。接口挂在策略健康端口：`/v1/lifecycle/status|command|catchup` 与 `/v1/lifecycle/reset/*`，`/healthz` 的 `details.lifecycle` 带精简快照。

## 8. Strategy 到 Trade 的契约

事件 `event.trade.target.weight_requested`（Stream `MOOX_TRADE`）是组合账户的完整目标快照：

```text
target_id = result_id
instance_id、session_id、strategy_id、logical_account_id
bar_end_time、effective_at（= bar_end_time）、valid_until（= bar_end_time 之后 2 根 bar）
shadow（试运行为 true）
targets[] { instrument_id, market_type（SPOT | SWAP | STOCK）, target_weight, hold }
```

同一个 `instrument_id` 可以以 SPOT、SWAP 各出现一次（现货与永续各自独立、不互相抵消），Trade 按 `market_type` 规范化标的 ID。策略启用时要求策略要输出的每个市场都在组合账户可交易的市场里（启用成员已开通市场的并集），组合还没有启用的成员时提示“组合账户还没有启用的成员”。

`target_weight` 是相对组合账户总权益的带符号权重；遗漏的旧（标的, 市场）目标为 0，空列表表示全部归零。`hold=true` 明确要求保持该标的当前持仓数量，权重只保留策略预算占用，Trade 不为它读取参考价或换算数量。
Trade 校验当前授权会话与有效期，按同一会话的 `bar_end_time` 只接受更新的目标，再独立完成数量换算、
账户选择、精度和风控。

## 10. 回放

> 当前 View 研究回放的账本只接收目标权重，没有传递引擎的 `hold` 标记：当期价格可用但因冻结保护应保持数量时，账本仍可能按原权重再平衡。它的“缺价冻结”仅由价格缺失触发，与实时 `hold=true` 不是同一机制；涉及该分支的回放不能作为实时保持数量行为的等价验证。实现位置：`internal/replay/runner.go` 的 `Ledger.Step` 调用与 `internal/replay/ledger.go` 的 `Step`。

回放是基于 View 的研究工具，用来比较策略版本，不承诺复现历史上的实时结果：

- 入参：定义、DSL 文本（可回放未保存的草稿）或实例（三选一；实例用其当前会话、停用时最近一次会话固化的 DSL，
  回放记录同时保存来源实例与会话；重新启用实例会按定义的当前版本重新解析）、`[start, end)`（UTC，先截到
  毫秒）、`factor_tasks`（市场 → 因子任务，混合市场给 spot 与 swap 两个，统一数据集上的任务给 `multi` 一个，登记的市场要与任务的源数据集一致，多个 View 的周期与日历必须一致）、
  现货与永续各一个单边手续费 `spot_fee_bps`、`swap_fee_bps`（0～1000 bps，股票按现货费率）。A 股日内 View 的 bar_start 是真实的开盘时刻，与 crypto 一样按 UTC 区间回放；A 股日线 View 按上海日期回放：两端各取所在的上海日期零点，含起始日期、不含
  结束日期（日线的 bar_start 是上海零点、即前一日 16:00 UTC，直接按 UTC 比较会漏掉首日、多出末日），记录保存换算后的
  区间（记录同时保存日历，页面按上海日期显示区间，报错里的时间也写上海日期）。支持现货、永续、混合市场与 A 股；
  tranche 策略、声明了 `factor_params` 的策略与策略池仍然拒绝（策略池的成员净值与比例在池实例的预热与运行结果里看）。绑定两个 View 时逐个校验：起点要在每个 View 的可用范围内，终点取各 View
  中最早的，各 View 的索引换代各自跟随、各自复查剩余区间。提交时同步完成：View 覆盖范围未知时拒绝，覆盖整体超出内嵌日历、行都落在非交易日上或 A 股行键不是
  上海零点（数据集按 UTC 零点写行）时说明具体原因；起点不早于活跃序列的覆盖起点（见第 7 节）加上 `min_age_bars` 与 `bars[-1]` 所需的历史（否则给出
  可用起点），因此不会出现早期区间只剩已停更序列的情况；终点截到最新一根之前（最新一根可能还没写完，覆盖统计
  也可能滞后几分钟）；根数不超过 20000；返回实际回放的根数与首末根，并固化当时的因子定义指纹（没有引用因子时
  固化空集合）以及校验区间所用的活动索引代次。代次是索引 ID 加上建成时记录的代次（Storage 记在 View 的内部属性 `moox.index_generation` 里）：
  索引 ID 对一个 View 是固定的，View 被 `force-rebuild-view` 重新建索引时代次才变。
  同一代索引的行只会被定时删除最旧数据删掉：执行时代次没变就按精确统计复查起点；代次变了（排队期间重建过索引，新一代只保留最近的根数）才按新索引的精确统计复查起点并截断终点，
  越界时提示重建并要求重新发起，新索引的统计暂时未知时同样拒绝执行。每段读取完成后都确认代次没变；发现换了一代时，按新索引复查从当前分段起的剩余区间，通过才让行与年龄判定的读取器一起
  切换过去重读这一段，并按新索引截短终点（指标里说明截到哪一根），否则以“在回放过程中重建了索引”失败、说明剩余
  区间从哪一根起不再被覆盖，不会静默改读新索引、把丢掉的较早 bar 记成缺数据。每段读完的代次复核只读代次（不读
  列），传输失败单独重试。一次回放最多跟随 3 次换代（整个回放累计），每次跟随后立即把累计次数写进指标的局限说明，
  回放失败或取消时保存的部分指标也带着它；排队期间或回放过程中换代截短了终点时，说明写明最后一根 K 线结束于哪一刻
  （同一件事只保留最新一条）。复查时读取覆盖统计又遇到索引变化，稍等后按最新的 View 重读，最多 3 次；复查里读取覆盖统计与读取 View 遇到
  传输失败时同样按 1、2、3 倍基础间隔退避重试（最多 3 次，与分段读取一致），复查的每次退避之前与之后都确认回放没有被取消。View 被删除时
  失败原因是“View 已不存在，回放无法继续”。执行时不再做启用级
  的覆盖校验。指纹在排队期间变化（包括新引用或不再引用的因子）则拒绝执行。提交时回放的每一根之前所需的历史
  （`min_age_bars`、`bars[-1]`，连同本根在内的根数）不少于 View 每个序列保留的根数时直接拒绝（回放只到最新一根之前，
  永远没有可回放的 bar）；覆盖太短时先反向判断历史够不够，说明历史不足，不会被误报成日历需要更新。A 股日线的覆盖边界按交易日规整
  （最早一根取不早于它的交易日、最晚一根取不晚于它的交易日并夹到内嵌日历之内），回放区间枚举到内嵌日历的最后一个
  交易日为止；索引里晚于当前已闭合最后一根的行（误写的未来数据）不算覆盖，最晚一根夹到当前已闭合的最后一根，
  全部行都在未来时说明疑似误写（行在未来的交易日上与行在非交易日上是两种不同的说明）；日历之内的未来行被夹掉后，每个序列
  保留起点仍按已闭合的最后一根估算、可能偏早，多出来的 bar 回放时按 `no_data` 记录（只影响异常数据）；索引里有超出内嵌日历的数据、并且当前时间已过日历末日的收盘时，末日那一根已经写完，提交时也能回放到它。
  这时真正的最新一根在日历之外，估算每个序列保留的起点时先扣掉日历之外至多的根数（每个自然日至多一根），扣完一根
  都不剩时说明数据已超出日历、暂不能回放。每个空间同时排队
  与运行的回放不超过 20 个，排队已满时在解析绑定、读取覆盖统计之前就拒绝。
- 进程内单工作协程，同一时刻只跑一个回放；按 `replay.chunk_bars` 分段、`replay.page_size` 分页读取，分段读取
  遇到传输失败时退避重读最多 3 次。活跃 View 每个写入批次都会改变索引修订号，跨页读取常与写入冲突：代次没变、
  只是修订号变化时按指数退避（250 毫秒起、翻倍到 4 秒，再加 ±50% 抖动，单次最长约 6 秒）重读，一段最多重试
  1 分钟，仍不一致才以“读取期间持续有新的写入，请稍后重试”失败。每次退避之前与之后都确认回放没有被取消，取消后不再继续读
  Storage；确认时读取回放状态失败按错误处理（与逐期检查一致，数据库异常时不会在退避里空等）。进程重启时遗留的 `running` 任务标记为 `failed(interrupted)`，已写入的周期
  保留，可重新发起。
- 每期的基础集合 U 取该期有行的标的（数据集的全部标的绑定，含已停用的），再按规则得到 E / G / A / M，
  与实时共用同一个引擎；规则状态在内存中跨期传递，从空状态开始。整根 bar 没有任何行时记
  `skipped(no_data)`：持仓只估值、不清算，规则状态保留。年龄判定每段只读取所需的 `close` 窗口，
  内存不随 `min_age_bars` 或回放长度增长；窗口内整个数据集都没有数据时记 `skipped(history_insufficient)`。
  与实时一致，只有策略涉及的标的（∪E(r)，年龄剔除之前）同一周期出现多个序列才整期 `skipped(ambiguous_series)`，
  用到 `bars[-1]` 时上一根的歧义同样跳过；无关标的的歧义不影响本期，歧义标的的价格一律不用于估值。判定顺序与
  实时一致：当期歧义 → 年龄判定 → 上一根歧义。A 股日线年龄窗口里落在非交易日的行（例如节假日误写的一行）跳过，
  不让整个回放失败。
- 理论账本：持仓键是（标的，市场），同一个币的现货与永续是两个持仓、不互相抵消。价格表按（标的，市场）取各 View 的原始
  行（不受选币池去重影响，另一个市场的持仓也要估值）。按当期 `close` 估值，无价的持仓冻结并按最后价估值；目标金额按总权益
  `W = 现金 + 现货持仓市值（含冻结）` 迭代扣费后计算，现货、永续各用各的费率。现货数量不为负，按现金成交：先卖现货，
  再调永续，最后买现货，买入受现金约束、不足时按比例缩减并记"目标未达成"（同时给出缩减比例，现金为 0 时为 0）。
  永续可以做空，不占用现金：每期有价时把 数量 × (收盘价 − 上期价) 结算进现金，成交只改数量并扣手续费，所以永续盈利可以用来买现货，
  亏损会减少现金（现金可以为负，此时现货买入缩减为 0，现货随目标按缩小后的权益被卖出补回）；没有价格的永续持仓冻结、不结算。
  **不计资金费，不模拟强平与保证金率**，页面与指标的局限里都写明。**权益不超过 0 即模拟爆仓**：持仓期间权益降到不超过 0 的那一期记入
  指标的 `bankrupt_at` 与局限说明，可成交的持仓（现货与永续）全部平掉，此后各期忽略目标、空仓直到结束，权益保持不变（否则“目标权重 × 负权益”
  会把多头算成空头，账户靠反向持仓“复活”）；该期结果摘要的 ledger 里带 `bankrupt`。每期记录期末现货类持仓市值之和与永续持仓的净名义价值
  （多头为正、空头为负）。年龄判定（`min_age_bars`）按市场各自的历史，多个市场时年龄没通过的市场不用它的行；不超过 1e-9 × 权益的金额视为浮点残差，不交易也
  不算未达成。手续费只按实际成交额。skipped 期不成交、不清算；持有标的连续缺价达到
  `replay.missing_price_liquidate_bars` 期后，在 ok 期按最后价清算。

## 11. 监控

- 每个启用实例登记为 Monitor 的期望数据集（`moox_strategy_dataset_*`，数据集标识
  `strategy_<instance_id>`）：ok 计为成功并推进输出水位，skipped 计为未完成。停掉上游或连续跳过时，现有的数据集
  新鲜度检查会告警。期望间隔：crypto 是 bar 时长；A 股相邻 bar 之间可能隔着午休、隔夜、周末与长假，按交易日历推进折算，取“最近处理的
  一根到其后第 2 根”的间隔的一半与“最近一个 ok 的一根到其后第 3 根”的间隔的三分之一中较大者（分别对应 Monitor 的
  run_missed_intervals=2 与 success_missed_intervals=3），不因休市误报 run stale，周末后第一根跳过也不会立即报 success
  stale（还没处理过时以最近闭合一根的上一根为基准）。两个基准在进程重启或重新启用后从结果库里取（最近处理的一根、
  最近一个 ok 的一根），不会退回 24 小时。Monitor 按交易日历判断应收的最新一根是否按时到达（允许迟到见监控模块文档），
  周末、长假不会被算成落后。两个系数（2、3）写在观察器里（`bootstrap/observer.go`），与 `config/setup/dataset-health-policy.yaml`
  的默认值一致并有测试绑定；线上调整 Monitor 的 `run_missed_intervals` 或 `success_missed_intervals` 时必须同步修改，
  否则 A 股实例周末会误报。实例 ID 区分大小写，数据集标识只接受小写：含大写、非法字符或过长的 ID 用它的哈希，
  只差大小写的实例（Abc 与 abc）不会映射到同一个标识。
- 模块健康检查 `strategy-targets` 只在 ok 时记成功，在读取重试耗尽、配置错误、历史覆盖不足、同一标的
  多个序列、因子定义变化，以及实例因 Trade 拒绝会话被自动停用时记失败；第 4 节规定的积累期 `history_insufficient` / `factor_skipped` 例外按成功处理。
- `moox_strategy_period_total{instance_id,result,reason}` 按实例累计处理的周期；`moox_strategy_target_cancelled_total{reason}`
  按原因累计被取消的目标（`superseded` 被更新的结果替代、`expired` 投递前已过期、`inactive` 投递前实例已停用或换了
  会话、`rejected` 无法通过契约校验），四个原因预先登记；其中发布期间被取消、随后确认已发出的另计于
  `moox_strategy_target_sent_after_cancel_total`，两者相减才是没有送到 Trade 的目标数。这些计数只供本机采集
  （`/metrics`），不上报 Monitor。参数送达滞后由 `moox_strategy_param_delivery_stale{space_id,instance_id}` 告警（连续 `params.stale_alert_periods` 期没送达为 1，Monitor 的 `factor_params` 检查读它，见因子文档第 11 节）。
- **暂停等目标发完**：系统暂停先暂停策略，策略的暂停要等正在求值的那一期结束、并且 outbox 里已经落库的目标都发布到 EventBus 才算停下（`Quiesce`）；
  等不到会返回“已暂停，但在途操作没有结束”，系统暂停编排器在这一步拦住，不再暂停 Trade 和更上游，等目标发完后重新执行即可。
- `/readyz` 在数据库不可用、EventBus 未连接、事件消费者未就绪，或投递停滞（`outbox_stalled`：最老的待投递结果超过
  5 分钟仍未发出，或发布持续失败超过 5 分钟——新结果会替代、过期取消旧的待投递结果，1m 等短 bar 的实例最老一条的
  年龄不会超过一根 bar，只能看发布本身失败了多久，见 `outbox_publish_failing_seconds`）时不就绪，Monitor 据此告警。
  有启用实例使用 A 股日历时，内嵌日历的可用截止日前 30 天起在 `calendar_warning` 给出提醒，过了截止日不就绪。
  事件消费者处理一条事件期间按 AckWait 的三分之一向 broker 报告进行中，实例多或依赖慢时不会被判超时重投。事件消费者的连接被永久关闭（例如连续鉴权失败）时丢弃它重新
  拨号，不需要重启进程。

## 13. Storage/Factor 网关接线与构建

Strategy 的输入读取、回放与事件执行器共用一个进程级 `gatewayclient`，覆盖 Factor 的 `GetFactor`、`GetFactorTask`、`ListFactorTasks`、`BindFactorTask`、`DeleteBoundTask`、`SubmitFactorParams`，archive-mgr 的 `ListArchiveTasks`（删除实例前用，适配器在 `internal/archivetasks`），以及
Storage Metadata 的七个读方法（`GetView`、`ListViewColumns`、`GetDataset`、`GetTag`、`ListDatasetSubjects`、
`ListSubjects`、`ListTagMembers`）与 DataView 的 `QueryTimeSeriesRows`，适配器在 `internal/input/gateway.go`。`gateway_client` 显式配置 caller `strategy`、
Admin 分配的 KeyID 和签名密钥文件；主机地址与 MooX 私有 CA 由同级 hostgateway 配置提供，
目录缓存位于数据库父目录的 `gatewayclient/directory.json`，权限为 0600。只读刷新重试、签名和超时由共享层处理。

原 `factor.target`、`factor.target_node`、`storage.target`、`storage.target_node` 已删除，旧网关地址环境覆盖不再参与选路；
`factor.timeout` 与 `storage.timeout` 保留为经网关调用的单次超时。
`storage.app_key` 与 `view_app_key` 分别用于 Metadata 和 DataView，与网关签名密钥独立；
未显式配置时，继续由 `MOOX_STORAGE_PRIMARY_AUTH_SECRET` 和 `MOOX_STORAGE_VIEW_AUTH_SECRET` 派生。
配置拒绝未知字段、重复键和额外 YAML 文档。离线读取不打开私密文件，进程启动则要求完整部署身份和两类角色凭据，
并创建真实的事件消费者；关闭时等待事件 runner 与实例协调循环退出，再释放共享客户端与数据库。

Strategy 服务和 CLI 均在本机关闭 CGO 编译或交叉编译，Linux amd64 静态程序和相关测试包已通过运行验证。
Trade 已使用同一客户端；原生 control 部署已分发 Strategy 签名身份和 Storage primary/view 凭据。

数据库与旧版本不兼容：升级到本版本时停止 Strategy、删除旧的 `data/strategy/strategy.sqlite`（含
`-wal`、`-shm`），启动后自动建表；旧库会被拒绝并提示人工处理。

周期标记的 `definition_hash` 是必填字段。升级 Factor 与 Storage 时先停 Factor 引擎，等 DataNode 出站队列、
View 的就绪队列与 ViewDataReady 消费积压都清空后再替换二进制，最后启动新 Factor 引擎；仍然无法通过契约校验的
出站记录会被 Storage 隔离（记日志后删除），不会堵住其后的事件。本版本还要求 Storage 在 DataView 查询响应里
返回 `retained_rows_per_series`，策略据此计算活跃序列的覆盖起点；索引没有记录时为 0（未知），只能按索引统计的最早时间判断。
Storage 发布 ViewDataReady 用专用连接，单次最多等 10 秒；因连接问题失败后进入 5 秒退避（期间刷新直接跳过），
在串行锁之外后台重连，并由后台定时重试补发；调用方结束（进程关闭、消费者重启）不算连接故障，超过 EventBus 最大
消息长度等确定性错误隔离该条并记日志；启动时补发失败只记日志，不让 View 角色退出；行事件不因就绪事件发布失败而
失败重投；入队落盘失败时不 ACK 周期事件；所属 View 已不在目录中的事件 24 小时后隔离（目录在进程内不删除 View，
实际在重启后生效）。就绪队列每次刷新结束时落盘一次，先写唯一的临时文件并 fsync 再改名。写入围栏（每个索引已写入
到的来源位置）只在内存里更新并标脏，由后台循环每秒合并落盘一次（同样 fsync，但不在行处理的热路径上），后台循环
一直跑到消费者完全停下，停止后再落盘一次。崩溃时丢失最近一次落盘之后的更新：这些行已经 ACK、不会重投，对应的就绪
事件要等同一来源的下一次行写入才放行，日线来源会晚一个交易日。索引标识对一个 View 是固定的，
键的数量有界，不需要清理（已删除 View 的少量键会一直留着）。首次建索引的回填不走事件、不推进围栏：建索引之前写入的行对应的
就绪事件要等同一来源的下一次行写入才放行。损坏的文件在启动时改名保留后按空状态继续，崩溃留下
的临时文件在启动时清掉。就绪队列的异常日志按类别（发布、重连、围栏落盘）各自去重，只有真正发布成功或队列已空时
才记“发布已恢复”。View 健康详情给出 `ready_queue_pending`、`ready_queue_oldest_age_seconds` 与
`ready_publish_backoff`（只展示，不影响就绪判断），同名指标只供本机采集，不上报 Monitor：就绪事件积压在 Monitor 上
表现为下游策略实例的运行滞后。Storage 建成索引时在 View 上记录代次。


## 附：可导入的 MA 因子

仓库里的 `examples/factors/timeseries.yaml` 收录了 `ma`（算术移动平均，窗口 `window` 可调），可以直接导入因子库：

```bash
moox-factor-mgr-cli import --file examples/factors/timeseries.yaml --factor-id ma
```

在因子任务里加一个固定成员 `ma`（默认参数，列名 `ma`），或者一个可变成员 `ma__var`（由策略逐期提交窗口）。策略不用声明因子，规则直接写列名，
择时规则可以写成 `bars[-1].close <= bars[-1].ma && bars[0].close > bars[0].ma`；用可变成员时：

```yaml
factor_params:
  ma__var:
    window: "20"
```

声明进指纹、取值不进：策略调整 `window` 不会让实例 `skipped(factor_changed)`，修改因子定义的参数声明（范围）才会，需要重新启用。
