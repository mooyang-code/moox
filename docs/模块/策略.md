# 策略（Strategy）

Strategy 用声明式 DSL 描述选股和择时规则：在每个已闭合的 K 线周期，按规则计算出一个资金单元的
完整目标权重，保存为结果，并异步发送给 Trade 执行。Strategy 不读取账户、余额、持仓和订单，
也不接触交易所。

代码位置：`modules/strategy`。

## 1. 进程与端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| `StrategyMgr` | tRPC `11430`、HTTP `11433` | 管理接口；管理台经 Admin 访问 HTTP 端口 |
| 健康检查 | `11431` | `/healthz`、`/readyz`、`/metrics` |

依赖：经主机网关读取 Storage（行情与因子结果）和 Factor Manager（因子元数据）；通过 EventBus
订阅 `ViewDataReady`（durable `strategy_view_data_ready_v1`）并发布目标权重事件；数据保存在
`data/strategy.sqlite`。

## 2. 核心概念

| 概念 | 含义 |
| --- | --- |
| StrategyDef | 一份 DSL 定义，持久化 `strategy_id`、`strategy_name`（由 DSL 的 `name` 派生）和 `dsl_yaml` |
| StrategyInstance | 定义、空间、输入绑定、资金单元（组合账户）和启用状态的运行绑定 |
| Session | 每次显式启用实例产生新的 `session_id`；进程重启保持会话，停用后重新启用创建新会话 |
| EvaluationInput | 本周期冻结的标的池、行情、因子、时间边界和输入来源 |
| RuleState | 每条规则下一周期需要的理论状态（不是真实持仓） |
| StrategyResult | 一次成功求值的快照、目标、规则后态和投递状态 |
| PositionTargets | 一个实例一个周期的完整目标权重集合（`instrument_id` + 带符号 `target_weight`） |

策略时间统一使用 `bar_end_time`（已闭合 K 线的结束边界）。表达式中 `bars[0]` 是本次使用的已闭合
K 线，`bars[-1]` 是同一日历下紧邻的上一根；只接受这两个常量索引。缺少精确的上一根时整次求值跳过。

## 3. DSL

```yaml
name: strategy_demo

triggers:
  schedule: {cron: "5 * * * *", timezone: UTC}
  event: {name: ViewDataReady}

data: {bar: 1h, calendar: crypto_24x7}

rules:
  momentum_selection:
    pool: {udf: spot_symbols, params: {quote_asset: USDT}}
    filter_before: "turnover_20 > 1000000"
    score: "0.6 * pct_rank(return_20) + 0.4 * pct_rank(turnover_20)"
    select: {top: 10}
    weight: 0.60
    filter_after: "return_20 > 0"

  ma_signal:
    pool: [BTC-USDT-SPOT, ETH-USDT-SPOT]
    signals:
      entry: "bars[-1].ma20 <= bars[-1].close && bars[0].ma20 > bars[0].close"
      exit: "bars[-1].ma20 >= bars[-1].close && bars[0].ma20 < bars[0].close"
    weight_each: 0.10
```

- 规则名自定义；`pool`、`filter_before`、`score`、`select`、`signals`、`weight` / `weight_each`、
  `side`、`filter_after` 是框架字段。
- `pool` 可以是固定列表，也可以是按名称注册的可信 UDF（输入为 Storage 的标的目录快照）。
- `score` 是数值表达式；`pct_rank` 和 `zscore` 是两个内置截面标准化函数。`select.top` / `select.tail`
  取高分前 N / 末 N。
- `signals` 用于时序规则：先对旧理论持仓检查 `exit`，再从候选中加入 `entry`，退出优先。
- 表达式用 Expr 编写，只能访问声明的行情、因子输出、标的元信息和时间上下文，开放纯函数白名单，
  禁止网络、文件、数据库、当前时间和随机数。

## 4. 处理流程

```text
定时 / ViewDataReady
  ─► 确定 instance_id + session_id + bar_end_time，本周期已成功则跳过
  ─► 恢复本会话最近的 RuleState
  ─► 解析标的池 ─► 加载本期行情、因子和精确历史，冻结输入来源
  ─► filter_before ─► 标准化与 score ─► select ─► signals
  ─► 分配权重（weight / weight_each）─► filter_after（只剔除，不补位）
  ─► 合成完整 PositionTargets 和下一期 RuleState
  ─► 一个 SQLite 事务保存 StrategyResult 和初始投递状态
  ─► 后台发布 LogicalAccountTargetWeightRequested
```

- 各规则独立计算，任一必要规则失败则整次不提交。明确成功的空集合才表示全部目标为零；缺数、
  因子未就绪或表达式错误不能当成空持仓。
- 因子结果只在收到 `completion_kind=factor_period.computed` 的 `ViewDataReady` 后才视为就绪；
  Factor 预热中的标的会被跳过。
- 定时和事件两种触发方式可以同时配置，语义为“或”。事件只提供触发时点，不能携带买卖指令。
  定时任务每分钟根据实例配置刷新一次。

## 5. 持久化与投递

| 表 | 内容 |
| --- | --- |
| `t_strategies` | `strategy_id`、`strategy_name`、`dsl_yaml`、创建/更新时间 |
| `t_strategy_instances` | `instance_id`、`strategy_id`、`space_id`、输入绑定、可空的组合账户 ID、启用状态、可空的 `session_id` |
| `t_strategy_results` | `result_id`、实例、会话、`bar_end_time`、`valid_until`、快照、目标、规则后态、冻结的事件数据、投递状态 |

投递状态只有 `none`（观察模式）、`pending`、`sent`（已被 broker 确认，不代表 Trade 已接受）和
`cancelled`。后台发布器每秒处理一批待发结果；同一实例同一会话出现新周期结果后，更早的待发结果被取消。
确认丢失时用同一个 `result_id` 重投，Trade 按实例、会话、周期和内容幂等处理。

## 6. 实例生命周期

- 未绑定组合账户的实例为观察模式：照常计算和保存结果，但不发布交易事件。
- 一个组合账户同一时刻只能被一个启用的实例控制。
- 启用：解析 DSL、检查输入和资金单元、生成新会话，先完成 Trade 授权再开始求值。
- 停用：先持久化 `enabled=false`，停止新的求值和发布，确认 Trade 清理后再清空会话。
  停用不会撤单或清仓，交易操作由 Trade 负责。
- 进程重启时恢复 `enabled=true` 且有会话的实例；`enabled=false` 但会话未清空的实例视为未完成的
  控制操作，只清理旧授权，不自动续启。

## 7. Strategy 到 Trade 的契约

事件 `event.trade.target.weight_requested`（Stream `MOOX_TRADE`）是组合账户的完整目标快照：

```text
target_id = result_id
instance_id、session_id、strategy_id、logical_account_id
bar_end_time、effective_at（= bar_end_time）、valid_until
targets[] { instrument_id, target_weight }
```

`target_weight` 是相对组合账户权益的带符号权重；遗漏的旧标的目标为 0，空列表表示全部归零。
Trade 校验当前授权会话与有效期，按同一会话的 `bar_end_time` 只接受更新的目标，再独立完成数量换算、
账户选择、精度和风控。Trade 的执行结果不会反过来修改策略的规则状态。

## 8. 管理接口

| 分类 | 方法 |

## 9. 与 Trade 的接线

Strategy 经节点 HTTPS 服务网关（`/api/service/*`）调用 Trade，不直连 Trade 端口：

```yaml
trade:
  gateway_url: https://<trade 节点>:11001   # 只写 origin；跨主机必须 HTTPS
  target_node: <trade 节点的网关 node_id>
  ca_file: ../certs/gateway/peers.pem
  timeout: 3s
```

- 网关路由 `trade_owner` 只允许调用方 `strategy` 调用 `GetLogicalAccount`、`ClaimLogicalAccountOwner`、
  `ReleaseLogicalAccountOwner`、`RebindLogicalAccountOwner`；下单、人工接管等仍只走管理入口。
- 凭据来自 `MOOX_GATEWAY_SERVICE_KEY_ID`、`MOOX_GATEWAY_CALLER=strategy`、`MOOX_GATEWAY_SERVICE_SECRET_KEY`；
  `MOOX_TRADE_GATEWAY_URL` / `MOOX_TRADE_GATEWAY_NODE_ID` 可覆盖配置。
- 两项都留空表示尚未接入 Trade：可以创建停用的实例，但启用需要 Trade 授权，会失败。

## 10. Storage/Factor 网关接线与构建

Strategy 的编译器和事件执行器共用一个进程级 `gatewayclient`，覆盖 Factor 元数据两个方法、
Storage Metadata 四个方法与 DataView 查询方法。`gateway_client` 显式配置 caller `strategy`、
Admin 分配的 KeyID 和签名密钥文件；主机地址与 MooX 私有 CA 由同级 hostgateway 配置提供，
目录缓存位于数据库父目录的 `gatewayclient/directory.json`，权限为 0600。只读刷新重试、签名和超时由共享层处理。

原 `factor` 配置及 `storage.target`、`target_node`、`timeout` 已删除；旧网关地址环境覆盖不再参与选路。
`storage.app_key` 与 `view_app_key` 分别用于 Metadata 和 DataView，与网关签名密钥独立；
未显式配置时，继续由 `MOOX_STORAGE_PRIMARY_AUTH_SECRET` 和 `MOOX_STORAGE_VIEW_AUTH_SECRET` 派生。
配置拒绝未知字段、重复键和额外 YAML 文档。离线读取不打开私密文件，进程启动则要求完整部署身份和两类角色凭据，
并创建真实的事件消费者；关闭时等待事件 runner 与实例协调循环退出，再释放共享客户端与数据库。

Strategy 服务和 CLI 均在本机关闭 CGO 编译或交叉编译，Linux amd64 静态程序和相关测试包已通过运行验证。
上节 Trade HTTP 接线留待主计划 D2d 与服务端协议同批迁移，部署身份分发留到 G 阶段。
