# 策略（Strategy）

Strategy 用声明式 DSL 描述截面选股与固定标的择时：每当实例关联的因子任务的结果 View 有一个周期就绪，就在这一帧数据上
求值，得到组合账户相对总权益的完整目标权重，连同逐标的的解释一起保存，并异步发送给 Trade。
Strategy 的求值不读取余额、持仓和订单，也不接触交易所；实例与组合账户的归属只记在 Strategy：启用挂了组合账户的实例前读一次 Trade 的 `GetLogicalAccount` 核对控制模式与市场，停用后调一次 `CloseTargetSession` 通知 Trade 关闭会话（见第 7 节）。

代码位置：`modules/strategy`。本文描述当前实现；策略模块评审与设计保留重建前的评审与目标，不作为当前缺陷清单。

## 1. 进程与端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| `StrategyMgr` | 原生 tRPC `11430` | 管理接口；管理台经 Admin 与主机网关访问 |
| 健康检查 | `11431` | `/healthz`、`/readyz`、`/metrics` |
| 指标定时器 | `11432` | 每 30 秒刷新实例的期望数据集并上报指标快照 |

依赖：经主机网关读取 Storage（Metadata、DataView）、调用 Factor（`GetFactor`、`GetFactorTask`、`ListFactorTasks`、`BindFactorTask`、`DeleteBoundTask`、`SubmitFactorParams`），回放的“因子现算”调因子引擎的 EngineControl（`OpenReplay`、`StepReplay`、`CloseReplay`），调 Trade 的 `GetLogicalAccount`、`CloseTargetSession`，删除实例前只读调用 archive-mgr 的 `ListArchiveTasks`；通过 EventBus
订阅 `ViewDataReady`（durable `strategy_view_data_ready_v1`，投递次数不设上限）并发布目标权重事件；
状态保存在组件数据目录下的 `strategy.sqlite`（生产是 `/data/moox/data/strategy/strategy.sqlite`）。

## 2. 核心概念

| 概念 | 含义 |
| --- | --- |
| 定义 | 一份 DSL 文本，按内容哈希 `dsl_hash` 标识版本；出现过的每个版本永久保留 |
| 实例 | 定义 + 一个因子任务（创建时选定，不能改；一个任务可以被多个实例引用，声明了 `factor_params` 的实例启用时独占关联它、随实例一起删除，见第 3 节「因子任务、成员键与列名」）+ 可选的组合账户。读取的 View 是任务结果数据集的默认 View。没有账户的实例是观察实例，只计算不投递 |
| 会话 | 每次显式启用产生一个会话，固化当时的 DSL 版本与绑定解析（`resolved_json`）；进程重启沿用会话，重复启用幂等 |
| 结果 | 每个处理过的周期一行：`ok` 带目标权重，`skipped` 带原因；两者都有输入摘要。结果里不存规则状态 |
| 规则状态 | 引擎下一期求值的起点（rank 的持有集合、止损入场价与冷却、hold 的入场序号、holding 批次、组合目标；策略池另有成员状态与池账本）。每个实例只有一行，与结果在同一个事务里更新；追赶或过期周期成功求值时，结果记 `skipped`、不带目标，状态照样推进。停用再启用时，新会话固化的 DSL 版本与绑定解析和原来一致就沿用，不一致才清空；修改实例（换账户或定义）一律清空（见第 5 节“规则状态”） |
| 解释明细 | 各规则预期集合中每个标的的最终阶段、分数、名次、权重与原因 |
| 回放 | 在历史数据上逐期求值、用理论账本模拟成交（收盘价加可选滑点）的研究任务。只有一个执行器、一个入口 `StartReplay`，主帧的因子数据有两种来源：读结果 View 的历史行（支持现货、永续、混合市场、A 股与策略池），或由因子引擎按因子机本地 K 线现算（声明了 `factor_params` 的策略只能用它），见第 10 节 |
| 关联因子任务 | 规则直接引用任务结果数据集的列名（成员键与列名规则见第 3 节）；`factor_params` 每期求出下一期可变成员的参数，`params()` 读取这一行实际用的参数（第 3 节末） |
| 外显设置 | 实例在结果表里隐藏的因子分类、成员（按成员键）与列，默认全部展示；只影响控制台展示与默认导出 |

策略时间统一使用 `bar_end_time`（已闭合 K 线的结束边界）。实例的周期由绑定 View 的频率决定，
DSL 的 `bar` 只是可选断言。

## 3. DSL

> 按功能讲写法、带例子与逐步推演的使用手册见 [策略 DSL 手册](../策略DSL手册.md)；本节是完整语义与边界条件的权威说明。

下面的示例假设实例关联的因子任务里有这些默认参数的单输出成员：`quote_volume_mean`、`quote_volume_mean_q`、`bias_q`、`bias`（列名就是成员键）：

```yaml
name: binance_spot_momentum
bar: 1m                       # 可选断言：与 View 周期不一致时拒绝启用

universe:                     # 策略级默认标的池，省略即全部
  min_age_bars: 240           # 标的在 240 根之前已有数据才参与
  exclude: [BTC-USDT]

rules:
  - id: long_momentum         # 稳定标识：规则状态与解释明细按 id 关联
    name: 多头动量选币         # 只用于展示
    type: rank                # 截面选股
    filter: "quote_volume_mean > 20000 && close > 0"
    score: "0.6 * rank(bias_q) + 0.4 * rank(quote_volume_mean_q)"
    select: {top: 5, buffer: 2}
    weight: {total: 0.8, method: equal, cap: 0.3}

  - id: btc_trend
    name: BTC 上穿均线          # bias = close / MA20，由不大于 1 变为大于 1 即上穿
    type: rank                # 固定标的择时：显式 pool 加 hold
    pool: [BTC-USDT]
    allow_empty: true         # 池只有 1 个标的，少于 min_universe，必须写
    on_missing: {keep_bars: 3}   # 写了 allow_empty 后缺数不再整期跳过：BTC 偶尔缺数先冻结保持，连续超过 3 根才出场
    score: "0"                # 不排序，写常数即可
    select: {top: 10000}      # 足够大的上限：池里满足条件的都持有
    hold:
      entry: "bars[-1].bias <= 1 && bars[0].bias > 1"
      exit: "bars[0].bias < 1"
    weight: {total: 0.2}

portfolio:
  leverage: 1                 # gross 上限；只有市场模式含永续时才允许大于 1
  max_weight: 0.3             # 组合级单币上限，同一个币的现货、永续合计；超出部分留现金
  min_universe: 20            # 规则进入 filter 的可用标的少于它则整期跳过（写了 allow_empty 的规则除外）
  max_missing: 0.2            # 任一规则缺数占（预期 − 年龄剔除）的比例超过它则整期跳过
  limits:                     # 可选：单标的分方向上限与超限转移
    long_max: 0.05            # 单标的多头上限（占权益比例，不随杠杆换算）
    short_max: 0.03           # 单标的空头上限
    overflow: {to: long_momentum}   # 超出部分转给哪条规则（池里写成员 id）；不写留现金
```

`portfolio` 省略的字段取默认值（`leverage: 1`、`max_missing: 0.2`、`min_universe: 0`、不限 `max_weight`、不写 `limits`）；
显式写出的 0 按原值校验：`max_missing: 0` 表示不容忍任何缺数，`leverage: 0` 非法。

**单标的上限（`portfolio.limits`）**：在多规则相加（池里是池合成）之后、`max_weight` 与 `leverage` 之前执行。一个标的的多头敞口是它各市场正权重之和，空头敞口是负权重绝对值之和（与 `max_weight` 一样按币合计）；超出 `long_max` / `short_max` 的部分按比例从这个标的的同方向键上削掉，按方向汇总后转给 `overflow.to` 指向的规则（池里是成员）本期**同方向**的其他标的，按该来源的分组目标权重比例分配（池的分组目标 = 条件转移之后的比例 × 成员目标，比例为 0 的成员分组目标为 0，不能当去向）。分配后又超限的部分再分一轮，最多三轮，剩下的留现金；已经截到上限的标的、冻结标的不作为去向，去向本期没有同方向持仓时全部留现金。`long_max`、`short_max` 至少写一个，取值大于 0 且不超过 `portfolio.leverage`；`overflow.to` 必须是规则 id（池里是成员 id），保存时校验。结果摘要的 `limits` 记每个超限标的、方向、超出量、轮次与去向（空表示留现金）。

| 字段 | 说明 |
| --- | --- |
| `universe` | `tags`、`exclude_tags`、`include`、`exclude`、`min_age_bars`、`max_age_bars`、`age_markets`（见“规则选项”）；`tags` 与 `include` 任一非空时取两者并集作为白名单，都为空表示全部 U，再减去 `exclude_tags` 成员与 `exclude`。标签与名单只作用于没有显式 `pool` 的规则；`min_age_bars` 对所有规则生效（含显式 `pool`），但不剔除规则上期已持有的标的 |
| `rules[].id` | `^[a-z][a-z0-9_]{0,63}$`，修改 id 等于从零开始 |
| `rules[].type` | 只能是 `rank` |
| `pool` | 固定列表或 `{tags: [...]}`；显式给出时不再套用 universe 的标签与黑白名单 |
| `rules[].universe` / `allow_empty` | 规则级 universe 逐项覆盖策略级；`allow_empty: true` 的规则不参与整期守门（见“规则选项”） |
| `rules[].market` | `spot` 或 `swap`：规则级市场，策略涉及现货、永续两个市场时这条规则只从该市场的序列选择、目标也落在该市场（见“市场模式”里的“规则级市场”）；写了它的策略必须显式写 `market` |
| `filter` | rank：布尔表达式，淘汰的标的记为 `filtered` |
| `score` | rank：数值表达式；`rank(x)` 与 `zscore(x)` 在通过 filter 的样本上计算，可嵌套 |
| `select` | rank：`top`、`bottom`（整数或 (0, 1) 的比例，配 `count_round`、`count_min`）与 `range` 三选一，`group` 分组名额，`then` 二次排序（见“规则选项”）；`where` 用 `score` 二次筛选，`buffer` 是排名缓冲区（按 `select.where` 之前的全样本名次判断"前 N+B 名"，与解释明细的名次一致） |
| `weight` | `total` 是规则预算；`method` 为 `equal` 或 `rank`（最优 N 份、最差 1 份）；`cap` 是规则内单标的上限；保存时要求 `cap × 选中数量 ≥ total`（预算分得完）。holding 规则的每个批次各自按 `cap / total` 的份额上限配权、批次之间互不补足（这样同一标的叠在所有批次里也不超过 `cap`），所以校验不按批次数放宽，批次较多时实际总权重可能低于 `total` |
| `filter_after` | rank：只剔除不补位，剔除的权重留现金；holding 规则只在建仓 bar 执行 |
| `holding` | rank：`{bars, offsets}` 分批换仓，与 `buffer` 互斥；`offsets: all` 是“每根建一个批次”的简写（见“每根开一批”）；可写 `anchor` 指定相位，或改用 `calendar` 按交易日、周、月换仓（见“规则选项”）。bar 序号对 `bars` 取模落在 offset 上时按本期名次重建该批次，批次延续到满 `bars` 根；延续期间只因缺数移出标的，本期被 filter 等淘汰仍按批次持有；缺数与 filter_after 剔除的份额都留现金，不重新分配。首次引擎求值成功的 bar 上按本期名次建立全部批次（不等各自的 offset、不空仓一个周期）；建仓 bar 没有产生 ok 决策（守门跳过、无数据、停机期间漏掉的事件）时，到期的批次不会被丢弃清仓，而是在之后第一根引擎求值成功的 bar 上按本期名次补建。首次建立与补建的批次，建仓序号都按各自的 offset 对齐到最近一个应建仓的 bar，之后照常在 offset 上轮换。追赶或过期周期成功求值也会推进批次状态，即使持久化结果是 `skipped(catchup / expired)`（见第 4 节）。bar 序号：crypto 是 `bar_end` 自 Unix 纪元起的根数（例如 1h 下 offset 0 落在 UTC 整点按 `bars` 对齐的时刻），A 股日线是内嵌交易日历首个交易日起的交易日序号，A 股日内是 barclock 的交易序号（午休、隔夜、休市不占根数，与因子的交易序号轴一致） |
| `hold` | rank：进出场持有（`entry`、`exit`、`max_bars`、`cooldown_bars`、`allow_reentry`），见“规则选项” |
| `scale` / `on_missing` | 仓位系数与持有标的缺数冻结，见“规则选项” |
| `side` | `long`（默认）或 `short`；现货 View 不允许做空 |

表达式用 Expr 编写，只能引用 View 的列、`bars[0].<列>`（当期）、`bars[-1].<列>`（日历上紧邻的上一根）、
`instrument_id` 与（仅 `select.where`、`filter_after`）`score`。内置函数一律禁用，只开放 `rank` 与 `zscore`
（仅在 `score` 中）。`matches` 右边只能是字符串字面量的正则表达式，保存时校验写法（用数据当正则时，标的 ID 里的括号
会让整期求值失败）；`??`、范围 `..` 与 `in` 不可用（列值不会为空，范围会为每一行分配整段数组，求值时必然出错），保存时
就拒绝；三元表达式 `a ? b : c` 的两个分支类型必须一致（都是布尔、都是数值或都是字符串），在启用与试算编译时检查；
运行错误只写中文原因，不带表达式库的英文原文。`rank` 同分取平均名次、单样本记 0.5；`zscore` 零方差记 0（样本值相同、或标准差
不超过样本量级的 1e-12 都按零方差处理）；排序以 `instrument_id` 打破平局。同一层的截面函数在同一个样本上
计算一次：先在通过 filter 的样本上求出全部参数（参数中嵌套的截面函数在下一层按同样规则计算），任一参数
无效（NaN、Inf、运行错误）的标的从这一层的名次与标准化中剔除；外层结果无效（例如 `rank(a) / rank(b)` 在
名次 0 处除零）只淘汰该标的本身，不触发重算。结果与截面函数的书写顺序无关。通过 filter 的候选全部分数
无效时整期 `skipped(config_error)`，不当作"选不出标的"清仓；holding 规则只在建仓或补建批次的 bar 检查，其余 bar
只延续批次、不使用本期分数。时序计算（均线、动量、分位）都写成因子，策略只在截面上过滤、打分、配权。

DSL 文本不超过 64 KiB；单条表达式不超过 1024 个字符（按字符计，只限制用户写下的原文）、不超过 256 个
语法节点，两者都在保存时检查；`bars[...]` 之后只能用 `.列名` 引用列。数字可以写成 YAML 接受的 `.5`、
`+0.5`、`5e-1` 等形式，精度不超过 18 位小数；数字写法不超过 64 个字符、指数绝对值不超过 30、绝对值小于 10^9。
`portfolio.leverage` 不超过 10（各规则 `weight.total` 之和不超过它）；`min_age_bars`、`min_universe`、`select` 的
`top` / `bottom` / `buffer` 与 `holding.bars` 不超过 10000，`holding.offsets` 不超过 64 个。rank 规则的固定 `pool` 列表少于 `min_universe` 个标的
时保存即拒绝（这条规则永远无法通过守门）；只写 `universe.include`、没有 `tags` 时它是白名单，去掉 `exclude` 后少于
`min_universe` 个标的，没有显式 `pool` 的 rank 规则同样保存即拒绝。标的与标签 ID 区分大小写。多个阶段同时有错时按 filter、score、
select.where、filter_after、select.then.score、hold.entry、hold.exit、scale.expr 的顺序报告第一个。

保存定义时只做语法与结构校验；列是否存在、成员契约与市场类型在启用实例时解析。编辑器的"试算"与
`ValidateStrategy` 会在选定因子任务的结果 View 的最近一期上求值一次，结果不落库；引用了任务里不存在的列时，报错带最接近的列名与该任务的全部列。

### 规则选项（选择数量、进出场持有、规则级标的池、换仓相位与日历、仓位系数）

以下字段都可选，不写时结果与没有这些字段时逐位一致。

**选择数量（rank 的 `select`）**

```yaml
select:
  top: 0.1                 # 整数是个数；(0, 1) 是比例；bottom 同理；1 以上必须是整数
  count_round: floor       # 比例换算个数：floor（默认）| ceil | round（0.5 进位）；只能配比例写法
  count_min: 1             # 换算后的最少个数（默认 0）；只能配比例写法
  range: [10, 13]          # 名次闭区间（分数从高到低），与 top/bottom 互斥、与 buffer 互斥，只收整数
  group: {by: ind, max: 3}                          # 每组最多 3 个；by 是 View 里的数值列，或附加来源的列（来源名.列名）
  # group: {by: ind, quotas: [2, 1, 1], rest: 1}    # 按组内最优名次给组排序，第 i 组名额 quotas[i]，其余组 rest
  then: {score: "-close", top: 5}                   # 二次排序：在第一段选中的集合里按新分数再取（与 buffer、hold 互斥）
```

- 比例的分母是通过 `filter` 且分数有效的样本数（`rank()` 的样本），在 `where` 之前计数；换算用十进制精确计算（`0.1 × 30` 恰好是 3）。
- `group` 按名次从前往后逐个接受，所属组已满就跳过（明细 `group_full`），`group.by` 的列计入规则的必需列：输入层不给 NaN 值（空值不出现在行里），分组列为空的标的按缺数处理（`missing:<列>`），计入 `max_missing` 的缺数占比；行里直接出现非数（例如统一数据集以外的特殊来源）时，引擎把它当作不属于任何组、不能入选（`group_none`）；`max` 与 `quotas` 二选一，`rest` 只能配 `quotas`。`buffer` 保留的上期持仓先占各组名额。`group.by` 也可以写附加来源的列（`来源名.列名`，例如小时线主帧按日线来源的行业代码分组 `by: daily.industry`）：分组值取这一根主帧按 as-of 读到的来源值，其余口径与主帧的列完全一样，见“附加列来源与参考市场”。
- `then.score` 是数值表达式，可以用 `rank()`、`zscore()`，截面函数在第一段选中的集合上计算；第一段选中、二次排序没取到的记 `select.then`；二次排序的分数全部无效时，这条规则本期不出目标（预算留现金），不整期跳过。与 `holding` 同用时只在建仓 bar 执行。`weight.method: rank` 按最终顺序配权。
- 写比例时选中个数要到运行时才知道，保存时跳过“`cap × 选中数量 ≥ total`”的检查，分不完的预算按 cap 语义留现金，并在决策摘要的 notes 里注明。写了 `then` 且个数是整数时按 `then` 的个数检查。
- `then.top`、`then.bottom` 与第一段同口径：整数是个数，(0, 1) 是比例，可配 `count_round`、`count_min`；比例的分母是第一段选中且二次排序分数有效的个数（例如第一段选出 7 个、`then: {top: 0.5}` 取 3 个）。写比例时与第一段一样，保存时不做 cap 检查。

**进出场持有（rank 的 `hold`）**

```yaml
- id: quiet_long
  type: rank
  filter: "volume_mean > 0"     # 资格：入场和继续持有都要满足
  score: "-vol_ratio"           # 补位排序
  select: {top: 0.1, group: {by: ind, max: 3}}   # 目标持有数；可带 where、group
  hold:
    entry: "vol_pct < 0.1"      # 新入场还要满足；不写表示不限制
    exit: "vol_pct > 0.7"       # 持有中满足即出场
    max_bars: 720               # 持有满这么多根强制出场，0 表示不限
    cooldown_bars: 0            # 出场后这么多根内不能再入场（[T, T+N] 闭区间）
    # allow_reentry: true       # 候选只看 entry：出场条件为真的标的也可入场，刚出场的标的当根可补回（要求 cooldown_bars 为 0）
  weight: {total: 1}
```

每根依次：① 冻结的持有标的（市场不可用、只缺上一根、`on_missing` 保持）不判出场、照常计持有根数、占用名额；② 其余持有标的依次判出场：已不在预期集合（`not_expected`）→ 止损（`exit_stop:<原因>`，冷却按 `stop.cooldown_bars`，同根与其他原因同时成立时按止损记）→ 缺数（`exit_missing`）→ 不满足 filter（`exit_filter`）→ `exit` 为真（`exit_condition`）→ 持满 `max_bars`（`exit_max_bars`），除止损外冷却按 `hold.cooldown_bars`；③ 补位：目标数 = `select` 换算的个数，空位 = 目标数 − 留下的持有数（含冻结），不为负，持有数超过目标不裁减；候选要通过 `where`、`entry` 为真且 `exit` 不为真（同根都成立不入场，`hold_not_entered`）、不在持有中、本根没有出场、不在冷却中（`hold_cooling`），按名次受 `group` 名额约束依次补满（持有标的先占所属组的名额，冻结且本根没有行的按规则状态里记下的分组值占名额）；④ 对持有集合（含冻结）按 `weight` 配权，持有数少于目标时预算按实际持有数分满；冻结标的的份额由组合层保持。持有与新入场的明细分别是 `hold_kept`、`hold_entered`。

- **`allow_reentry: true`**：把“出场条件”只当作持有中的退出条件，不再挡入场——候选只需 `entry` 为真（以及 `where`、不在持有中、名额等），出场条件为真的标的也可以入场；本根刚出场的标的当根也可以补回，补回按新入场记（持有根数重新计、不记冷却）。与大于 0 的 `cooldown_bars` 不能同写（保存即拒绝）。用于复刻“出场只管持有中的标的、补位只看滞后排名”的写法：补位排名用滞后几根的分数时，刚触发出场的标的往往仍排在前面，会立刻补回。默认不写时仍是“出场条件为真不入场、本根出场不补回”。
- 持有标的判缺数只看 `filter`、`hold.exit`、`scale` 与 `group.by` 引用的列：`score`、`entry` 缺值时不出场，只是不能参与补位。
- 持有根数与冷却都按 bar 序号的差计算（与 holding 一致）；跳过、过期、追赶的期都算时间流逝。规则状态 `hold` 记持有标的的入场序号、冷却到期序号与（与日历同写时）上次判进出场的序号和基准权重；停用再启用时 DSL 与绑定没变就沿用（停用期间的根数照样算时间流逝），变了从零开始。
- 与 `buffer`、`holding.bars/offsets`、`then`、`range`、`filter_after` 互斥；可以与 `holding.calendar` 同写（非建仓 bar 沿用上次判定时的基准权重，出场空出的份额留现金，与 holding 批次同一口径），这时 `days` 只能有一个值：冻结、缺数与止损每根都判；`filter`、`exit`、`max_bars` 与补位只在建仓 bar 判断（`max_bars` 到了也等到之后第一个建仓 bar 才出场），其余 bar 保持上一次的持有集合，未持有的候选记 `not_rebalanced`；某个建仓 bar 没有 ok 决策时，在之后第一根 ok bar 上补判一次；`scale` 仍每根生效。
- 需要“用 k 根之前的排名补位”时，在因子里写 `delay(x, k)` 作为 `score` 与 `entry` 的输入。
- **固定标的择时**：不选股、只对固定的几个标的判断进出时，写显式 `pool`、`score: "0"`（不排序）、`select: {top: 10000}`（足够大的上限，池里满足条件的都持有），进出场条件写在 `hold` 里；持有的标的平分规则预算。它与其他 rank 规则一样参与整期守门：池里本期没有可评估的标的（全部年龄不够，或池与本期基础集合没有交集：标的停用、退市，标签池没有成员，ID 写错）时，整期 `skipped(universe_too_small)`，同策略的其他规则也不出目标；不写 `allow_empty` 时，1～4 个标的的小池按默认 `max_missing: 0.2` 缺一个就整期跳过。固定列表的 `pool` 少于 `min_universe` 个标的时保存即拒绝；`{tags}` 池保存不拒，运行时成员少于 `min_universe` 就每根整期跳过；两种都要写 `allow_empty: true`。写了之后这条规则不参与任何整期守门，持有的标的普通缺数时按 `exit_missing` 出场（所在市场不可用、只缺上一根的仍冻结保持），建议同时写 `on_missing: {keep_bars: N}` 让缺数先冻结。有冻结标的时，冻结的一份按上期权重保持，其余持有标的按含冻结的个数平分预算；冻结标的上期份额大于本期平分份额时规则合计会超过 `weight.total`（预算 0.5：上期 A 独占 0.5，本期 A 冻结、B 入场得 0.25，合计 0.75），只受 `portfolio.leverage` 封顶，冻结解除后恢复。

**规则级标的池与年龄（规则的 `universe`、`allow_empty`）**

- 规则里写 `universe`，字段与策略级相同，写了的字段逐项覆盖策略级、没写的沿用策略级；只改了年龄类字段的规则仍用策略级的默认集合。写了显式 `pool` 的规则只能写年龄类字段（`min_age_bars`、`max_age_bars`、`age_markets`）。
- `max_age_bars: N` 只保留年龄小于 N 根的新标的，判定方式是“`min_age_bars: N` 不通过”；一个标的一旦被记为通过 N（实时的年龄通过记录、回放的已通过集合都按 N 分开保存），就永远不再算新标的。与 `min_age_bars` 一样只在建仓时判断，不剔除已持有的标的。剔除原因记 `aged_out_max`。`min_age_bars` 必须小于 `max_age_bars`。
- `age_markets: each`（默认）：`min_age_bars` 在任一市场通过即算通过（现状）；`max_age_bars` 在任一市场通过 N 即不是新标的，标的列在某个本期整体不可用的市场里时无法确认它在那里的年龄，按保守口径算作不是新标的、剔除。
- `age_markets: all`：标的必须在实例绑定的每个市场都列出、且这些市场本期都可用，否则 `min_age_bars` 与 `max_age_bars` 都不通过、剔除，明细原因记 `age_markets`（只上了一个市场的老币、市场本期整体不可用时，写了 `max_age_bars` 的规则也会剔除它）；满足时年龄按最晚出现的那个市场算：`min_age_bars` 要在每个市场都通过，`max_age_bars` 在每个市场都通过 N 才不是新标的。`min_age_bars: 1` 配 `all` 就是“各市场都已上线”。支持统一数据集、现货永续两个任务的绑定，以及单市场加参考市场（`market.reference`，见“附加列来源与参考市场”）；只绑一个市场又没有参考市场时写 `all` 启用即拒绝。没写 `allow_empty` 的 `all` 规则，在某个市场本期整体不可用时候选会被全部剔除，触发 `universe_too_small` 整期跳过，所以 `all` 规则建议配 `allow_empty: true`。研究回放与实时一样，把市场的全部标的当作“列出”（本根没有行也算）；回放不模拟“市场整体不可用”，差别见第 10 节“回放与实时的已知差别”。第 3 期起，所有双市场研究回放的年龄探针都对齐了实时：候选与“列出的标的”取市场的全部标的，本根没有行的标的也照常判定。这也影响只写策略级 `min_age_bars` 的老策略：旧回放只探针本根有行的标的，一个币在一个市场是新币、在另一个市场是老币、而老的那个市场某根缺行时（例如现货新上、永续某根缺行），旧回放把它记成年龄剔除，实时与新回放按年龄足够、本根缺数处理；`max_missing` 较小时这一期会从 ok 变成 `skipped(too_many_missing)`，与逐期实时求值一致。
- 双市场选币时按市场剔除年龄不够的行，只按策略级 `universe.min_age_bars` 判断；规则级的年龄字段只影响这条规则自己的年龄剔除集合 G(r)。
- `allow_empty: true` 的规则不参与任何整期守门（`universe_too_small`、`min_universe`、`max_missing`）：候选为 0 或缺数时这条规则本期不出目标，预算留现金，缺数的只是不入选；已持有的标的按缺数口径处理。其他规则照常守门。写了（或从策略级继承了）`max_age_bars` 的规则必须写 `allow_empty: true`，否则保存即拒绝；`allow_empty` 的规则也不做“固定 pool 或 include 白名单少于 `min_universe`”的保存检查。
- 启用时的历史覆盖、回看与保留期检查按策略里最长的年龄根数（各规则上下限取大）进行。

**换仓相位与日历周期（rank 的 `holding`）**

```yaml
holding: {bars: 24, offsets: [0, 12], anchor: "2024-01-02T08:00:00Z"}   # 锚点只决定相位
holding:
  calendar: trading_days     # trading_days | week | month
  every: 5                   # 仅 trading_days：每 5 个交易日一个周期（必填）
  days: [1, 3]               # week / month：每周（月）的第几个交易日，1 起，-1 为最后一个；trading_days：周期内第几天，1～every
  at: last                   # 日内帧在该交易日的 first（第一根）或 last（最后一根，默认）建仓
  anchor: "2024-01-02"       # 仅 trading_days：周期起点；默认 A 股为内嵌日历首个交易日，加密为 1970-01-01（UTC）
```

- DSL 里的时刻都指某根 bar 的 **bar_start**；A 股写交易日期 `YYYY-MM-DD` 表示该日第一根。时刻不是 bar 起点时启用即拒绝；DSL 写了 `bar` 与 `market`（加密）时保存就检查。
- `anchor` 写在 bars/offsets 上时，批次在 `(序号 − 锚点序号) mod bars == offset` 时重建，锚点早于、晚于当前都可以；建仓序号按锚点对齐。
- 日历写法：`days` 的每个值是一个批次，预算按批次数均分，每个批次延续到它自己的下一个建仓 bar。当周（当月）交易日少于指定序号时这一期该批次不重建。输入层按日历算出每个批次“最近一个应建仓的序号”（不晚于本根），批次的建仓序号早于它就重建：本根就是建仓 bar，或建仓 bar 没有 ok 决策、在之后第一根 ok bar 上补建；到下一个建仓日仍没补上，就按下一个建仓日正常重建。首次求值按本期名次建好全部批次。加密按 UTC 自然日（每天都是交易日，周从周一开始、月从 1 日开始），A 股按内嵌交易日历；日内帧 `at: last` 是收盘那一根，A 股 15:00 那一根得到的目标由 Trade 在次日开盘执行。
- `calendar` 与 `bars`、`offsets` 互斥，与 `buffer` 互斥；`every` 只配 `trading_days`；`at` 只配 `calendar`。A 股的 `days` 要在交易日历上存在：一周最多 5 个交易日（`week` 只能写 ±1～±5），一个月最多的交易日数从内嵌日历推出，超出的序号启用即拒绝（否则批次永远不重建）。建仓日最多向前找 400 个交易日：月度序号写得接近上限（例如 `days: [23]`）时，如果最近一个有这么多交易日的月份在 400 个交易日之前，每根都会报 `config_error` 跳过，所以月度序号不要用到接近上限。

**仓位系数与缺数冻结（`scale`、`on_missing`）**

```yaml
scale: {expr: "timing_coef", max: 1}   # 数值表达式（逐行，不能用截面函数），结果截到 [0, max]；max 默认 1，上限 10
on_missing: {keep_bars: 3}             # 持有标的连续缺数不超过 3 根时冻结保持，超过后移出；1～1000
```

- 系数只乘在规则的输出权重上（规则内配权与 `cap` 之后）；乘掉的部分留现金，不重新分配。holding 批次的基准权重、持有集合等规则状态不含系数。系数为 0 的标的不出目标，明细仍是 `weighted`、权重 0。它仍记在规则的持有集合里（下期 buffer 照样给它缓冲资格），但组合目标为 0，不受冻结保护。解释明细的 `weight` 是乘系数之后的权重，`scale` 是系数本身（结果表 `c_scale`、proto `StrategyResultItem.scale`）。
- `scale.expr` 引用的列与 filter、score 引用的列一样计入缺数划分；值为 NaN、无穷或求值出错的标的按缺数处理（`scale_invalid`）。需要“缺值当 0”时在因子里用 `fill_nan`。
- `on_missing`：持有中的标的本根缺数时并入现有的冻结（明细 `held(missing_kept)`）：保持上期目标、不交易，仍留在批次或持有集合里，持有根数照常累计；连续缺数根数记在规则状态 `missing_streak`，数据恢复即清零，超过 `keep_bars` 根后按现状移出。冻结的标的照常计入缺数占比。
- `missing_streak` 只在产生 ok 决策（含追赶、过期周期成功求值）的 bar 上累计：整期守门跳过、没有数据或停机漏掉的 bar 不计数，所以 `keep_bars` 数的是“连续多少次求值都缺数”。这与 hold 的持有根数、冷却按 bar 序号的差计算（跳过的期也算时间流逝）不同。
- 只有策略里有规则写了 `on_missing` 时，冻结按以下规则合并（否则与现状完全相同）：只有持有该标的的规则参与“要不要移出”的判断，没持有它的规则只把它当作缺数的候选；持有它、但没写 `on_missing` 的规则仍阻止冻结；市场不可用、只缺上一根的冻结规则不变。空头规则里永续本根没有行、也没有失败证据的持仓按“永续已下架”平掉，写了 `on_missing` 也不冻结（对冲币的现货多头不受影响）。

### 每根开一批（`holding.offsets: all`）

每根 K 线按本期名次新建一个批次、每个批次持有固定根数、多批叠加的风格，用 `holding` 写：

```yaml
rules:
  - id: main
    type: rank
    filter: "volume > 0"
    score: "rank(momentum__20)"                # 多个因子写成加权和：0.6 * rank(a) + 0.4 * rank(-b)
    select: {top: 1}
    filter_after: "shadow__24 <= 0.1"          # 满足条件的留下；只剔除不补位
    holding: {bars: 24, offsets: all}          # 每根重建一个批次，每个批次持有 24 根
    weight: {total: 1}
    stop: {loss: 0.08, cooldown_bars: 12}      # 可选
```

- `offsets: all` 在解析时展开成 0 到 `bars − 1`，与逐个写出完全相同，引擎没有另一条路径。批次数上限仍是 64，所以“每根开一批”最长持有 64 根（`bars` 大于 64 时保存即拒绝）；要更长就把 `bars` 放大、`offsets` 取稀疏的几个。只能与 `bars` 一起写，不能配 `calendar`。
- 规则预算在批次之间均分，批次权重固定，不随价格漂移；漂移出的差额是否下单由 Trade 的调仓阈值决定。
- 多空都做的写成两条规则（一条 `side: long`，一条 `side: short`）；名单用规则级 `universe.include`、`exclude`。
- `filter_after` 是保留条件（条件为真的留下），方向与外部框架里“条件成立就剔除”的后置过滤相反，照搬时要把条件取反。
- `portfolio.min_universe` 比较的是进入 filter 之前的可用标的数：`filter: "volume > 0"` 淘汰的标的（本期成交量为 0）也计入。
- 其余行为就是 holding 的行为：规则引用的任一列为空都算缺数、计入 `max_missing`；首次求值成功的那一根按本期名次建好全部批次；延续期间只因缺数或止损把标的移出批次；持仓参与冻结，可写 `on_missing`。

**表达不了的写法（已知限制）**

| 想做的事 | 现状 |
| --- | --- |
| 一条规则带一张参数表，展开成几百上千个子策略再按权重叠加 | 没有这种写法。一份 DSL 不超过 64 KiB，策略池最多 20 个成员，只放得下几十到一百多条规则 |
| 开仓时定数量，持有期内权重随价格漂移 | 批次权重固定 |
| 标的本期不是候选时不计持有根数 | 持有期按自然根数 |
| 在留下的样本上逐步重排后再过滤（过滤条件里用名次、分位） | `filter`、`filter_after` 不能用截面函数；需要时把名次做成因子列 |
| 因子缺值补同期名次中位数、同分按先后排名 | `rank()` 是平均名次，任一参数无效的标的不参与 |
| 每根开一批且持有超过 64 根 | 批次数上限 64 |

### 止损止盈

写在规则上；不写时行为不变。

```yaml
stop:
  loss: 0.05            # 固定止损：相对入场价不利变动达到 5%（含等于）
  trailing: 0.08        # 跟踪止损：相对此前最有利价格回撤 8%
  profit: 0.10          # 止盈：相对入场价有利变动达到 10%
  price: close          # close（默认）| extreme：止损看本期 low（空头 high），止盈与最有利价格看 high（空头 low）
  cooldown_bars: 12     # 触发后 [T, T+12] 根内本规则不能重新入场；默认 0（只禁止触发当期）
```

- `loss`、`trailing` 取值 (0, 1)，`profit` 取值 (0, 10]，至少写一项。同期多项触发按 `stop_loss` > `trailing_stop` > `take_profit` 记。
- **按收盘判断**：每期在规则求值最前面判断，止损的目标随本期目标下发，由 Trade 执行；不是盘中触价止损。入场价是入场当期的 close，不是成交价。
- **跟踪止损**用此前的最有利价格（不含本期）判断，判断后再用本期价格更新：同一根 K 线里高低点的先后未知，这样不会用后出现的高点去判先出现的低点。
- **价格列**：`close`（`extreme` 时还有 `high`、`low`）作为可选列读取，绑定的 View 必须有这些列；缺值、非有限或 ≤ 0 时本期不判止损、
  不更新最有利价格，不算缺数。入场当期没有 close 时，入场价在下一个有价格的期次补记。冻结的标的不判止损。
- **持仓单位**：`rank`（无 `holding`）是每个持有标的（入场价是进入持有集合那一期的 close，持有期间调权不改）；
  `rank` 的 `holding` 是每个批次里的每个标的（入场价是实际进入批次那一期的 close，不用回填的建仓序号）。
- **触发后**：`rank` 从选币与 `buffer` 的上期持有里排除，由后面的名次补位（名次仍在完整样本上计算）；`holding` 批次里的份额留现金到下次重建；
  `hold` 规则里止损等同出场（出场条件的输入缺失也照常判断），冷却中 `entry` 成立也不入场。
- **明细与摘要**：失去全部权重的标的记阶段 `stopped`，原因 `stop_loss` / `trailing_stop` / `take_profit`（写了 `hold` 的规则是 `exit_stop:<原因>`，例如 `exit_stop:stop_loss`），同一标的另有缺数等明细时合并为一条
  （例如 `stop_loss;missing:x`）；仍有权重的保持 `weighted`，原因追加 `;stopped:<n>`；冷却中的候选记 `dropped`（`cooldown`）。
  规则摘要的 `stop_loss`、`trailing_stop`、`take_profit` 是本期触发的持仓单位数。
- 状态：`RuleState.entries`（入场价、入场序号、最有利价格）、`RuleState.cooldown`（冷却截止序号，含当期）；holding 批次的 `entries`。追赶期与迟到周期照常推进这些状态。

### 市场模式

DSL 顶层的 `market` 决定策略从哪个市场的币里选，以及一个币在两个市场都可用时优先在哪个市场下单：

```yaml
market:
  select: spot | swap | both   # 从哪个市场的币里选
  prefer: spot | swap          # 一个币在两个市场都可用时，优先用哪个下单
```

只允许 5 种组合，每种需要绑定的因子任务不同（一个任务读一个市场的结果 View）：

| select | prefer | 含义 | 需要绑定的因子任务 |
| --- | --- | --- | --- |
| spot | spot | 纯现货 | 现货 |
| swap | swap | 纯永续 | 永续 |
| both | spot | 两边选，现货优先 | 现货、永续 |
| both | swap | 两边选，永续优先 | 现货、永续 |
| spot | swap | 现货选币，有永续就用永续下单 | 现货、永续 |

- 不写 `market` 时，按实例唯一绑定的因子任务的市场取 `{select: 该市场, prefer: 该市场}`；绑定了两个任务必须写 `market`。`select` 为 `spot` 或 `swap` 时可省略 `prefer`。
- 股票（`equity`）不允许写 `market`，目标的市场固定为 `STOCK`。
- 空头只走永续；纯现货与股票不能做空、`leverage` 不能大于 1；`portfolio.leverage` 大于 1 只有模式含永续时才允许。
- 绑定两个任务（或模式含两个市场）的策略不支持 `factor_params`。

**“可用”的定义**：某个标的在某个市场本期可用，指它在该市场的数据集里处于活跃状态，且该市场的 View 本期有它的行。

**选币池构造（每期）**：为每个标的在两个市场的行里选出一行，因子值用这一行；Frame 仍是每个标的一行，另带本行市场和两个市场的可用标记，规则内部照旧按标的计算。

1. 上期持有正权重目标的标的（所有模式，包括 `select: spot, prefer: swap` 持仓在永续时），只取它持仓所在市场的行；那一行本期不存在时按无行处理，走缺数和冻结逻辑，不退回去取另一个市场的行。
2. 其余标的：`select: both` 时两个市场都可用，只保留 `prefer` 市场那一行，只在一边可用就保留那一边；`select` 为单个市场时只用该市场的行（另一个市场只提供“可用”标记，用来决定下单市场；只在另一个市场上市的标的不进入基础集合）。
3. 空头候选只保留本期永续可用的标的（规则上期已持有的不过滤，永续本期不可用时由冻结逻辑保持）；只涉及单一市场的策略不过滤。

**定市场**：在规则贡献合成之前，给每个（规则, 标的）的权重定下市场。空头一律永续。多头按顺序：① 上期这个标的有**正权重**目标的，沿用那个目标的市场直到归零（“粘住”，避免永续偶尔缺数时在两个市场之间来回倒仓；上期在永续上的空头不会把本期多头粘到永续）；② `prefer` 市场本期可用就用它；③ 否则用另一个市场。

**已知局限（粘住只看正权重）**：`select: both, prefer: spot` 时，上期持有的是永续**空头**的币，本期不会粘在永续上，取行与定市场都先看 `prefer` 的现货行（空头本来只能下在永续，所以仍然落在永续，但用的是现货行的因子值，现货行不可用时才退回永续行）；需要空头始终用永续行时，把 `prefer` 写成 `swap`。**例外是永续对这个币的失败证据全都可冻结时**，两条都要满足：① 永续对这个币至少有一条证据，并且**每条**都是整体不可用（因子被跳过、整体失败、失败比例超限，即 `market_unavailable`）；② 永续本期有它的行，或者证据覆盖了策略引用的全部列（当期列与 `bars[-1]` 列）。这时上期在永续持有空头的币只取永续的行（行在就取它；不在就按无行），失败证据也取永续的，由冻结逻辑保持，不退回现货的行重新排名（`prefer` 取哪个都一样），空头保持不动。不满足时照常按上面的顺序取行：证据里混有逐币的 `factor_failed`（它在单市场下也不冻结），或者永续没有行、只有部分列有证据（其余列是没有证据的缺失，单市场下同样不冻结）。冻结按币，同一个币同时持有现货多头和永续空头时，满足条件就把现货多头一起冻结（保守的已知边界）。

**持有的永续空头在永续下架时平掉**（设计变化，第二轮总审查）：规则上期持有、上期在永续上是空头的币，本期永续没有它的行、也没有任何失败证据，并且永续不是整体不可用（典型是这个币的永续已下架、现货还在）时，这条空头规则按无行处理：明细 `missing(no_row)`、市场标永续，空头平掉、从规则持仓里移除，计入这条规则的缺数，也不参与冻结。以前它会借用现货行的因子值继续排名，照样输出 `Y|swap` 的空头目标，而永续上已经没有这个合约。这与上期持有的永续多头在永续无行时被平掉（粘住永续、不退回现货的行）对称。按规则处理、不按币：同一个币的现货多头和其他规则照常用现货行，对冲币只平永续空头、现货多头不动；只做空的币本期仍可以被多头规则在现货选中。永续有证据时按上一段处理，永续整体不可用时由冻结逻辑保持（见下文“一个市场整体失败也算不可用”）。

**合成与键**：从规则贡献合成开始，`State.Targets`、目标和结果明细都用（标的, 市场）作键（`State.Targets` 的键是 `标的|市场`，如 `BTC-USDT|swap`）。同一市场内多空可以相互抵消，现货与永续之间不抵消。排序先按标的，再按市场（现货在前）。

**组合约束**按固定顺序：① `max_weight` 按币合计——同一个标的现货、永续权重绝对值之和不超过它，两边都不为零时按比例缩小两边，只有一边时直接取上限（“现货多 + 永续空”这样的对冲也按绝对值之和截断）；② 给保持目标预留预算，保持目标本身不缩小；③ 现货部分（不含现货保持目标）超过 `1 − 现货保持目标` 时按比例缩小，多出的留作现金（`leverage` 大于 1 时才可能出现）；④ `gross` 超过 `leverage` 时按比例缩小（保持目标不动）；⑤ 摘要里 `net` 拆成 `spot_net`、`swap_net`，`cash` 只对单市场策略有意义，混合市场不填。**行为变化**：现货权重之和超过 1、`gross` 超过 `leverage` 以前整期 `skipped(config_error)`，现在改成按比例缩小并在摘要注明；现货出现负权重仍然报错（说明策略或定市场的逻辑有错）。

**规则级市场（`rules[].market`）**：策略的模式含两个市场（`both/spot`、`both/swap`、`spot/swap`）时，规则可以写 `market: spot` 或 `market: swap`。

```yaml
market: {select: both, prefer: spot}
rules:
  - {id: cash_long, type: rank, market: spot, score: "mom", select: {top: 5}, weight: 0.5}
  - {id: perp_short, type: rank, market: swap, side: short, score: "-mom", select: {top: 5}, weight: 0.5}
```

- **保存校验**：只能写 `spot` 或 `swap`；写了它的策略必须显式写 `market`（股票策略因此不能用）；单市场模式下必须与策略的市场相同（相同时等同于没写）；现货规则不能做空。
- **只用该市场的行**：这条规则不经过上面的选币池构造，引擎给它一份只含该市场行与失败证据的视图；预期集合收窄到在该市场有行、有失败证据或本规则上期持有的标的（基础集合 U 仍由 `select` 决定，`select: spot, prefer: swap` 时永续规则只在 U 里、也在永续上的标的中选；只在另一个市场上市的币不是它的候选，不记缺数）。本规则持有、但该市场已经没有行也没有证据的标的记 `missing(no_row)` 并平掉。
- **目标落在该市场**：权重不走“定市场”，同一个币在两条规则里落在不同市场时是两个独立目标、不互相抵消（同一市场内多空照常合成）。“上期持有沿用市场”不作用于这类规则；它们的持仓也不让没写规则级市场的规则沿用（只被规则级市场的规则持有的币，其他规则选它时按 `prefer` 定市场）。同一个币同时被两类规则持有时，组合目标是合成后的，分不开，没写规则级市场的规则仍按组合目标沿用。
- **缺数与年龄按规则的市场**：缺数按视图里该市场的行与证据判断；年龄（策略级 `min_age_bars` 与规则级年龄字段）在 `age_markets: each` 下只看该市场的判定，不用另一个市场的历史，也不再受“按市场剔除行”的影响（年龄剔除集合 G(r) 已按该市场判定）。`age_markets: all` 仍要求全部绑定市场。
- **冻结按（标的, 市场）键**：只在写了同一市场的规则之间、用该市场的视图合并（合并规则与按币冻结相同，`on_missing` 照常），组合层只保持那一个键，同一个币另一个市场的目标照常调仓；`max_weight` 仍按币合计，另一个市场的目标上限先扣掉保持目标的绝对值（不低于 0；摘要会注明“扣掉保持目标后的上限”，排查时据此对账）。保持目标本身不受 `max_weight` 截断：例如调低 `max_weight` 之前就已存在的保持目标超过新上限时，另一个市场的上限压到 0，保持目标仍超出上限，直到它解除冻结。所在市场本期整体不可用时这条规则不守门：持有的键按 `market_hold` 冻结，不新开仓，摘要注明；holding 规则这一期不重建批次。
- **已知的保守边界**：没写规则级市场的规则按币冻结某个币时，仍展开到这个币的全部键，连同规则级市场规则在另一个市场的目标一起保持（那条规则对这个币的贡献本期不生效）；反过来，某个键按键冻结时，没写规则级市场的规则落到同一个键上的贡献也在组合层删掉（它的明细仍显示 `weighted`）。策略池成员按键冻结的目标，池里仍按币保持。一个币同时被两类规则持有、且两个市场都是正权重时，没写规则级市场的规则沿用 `prefer` 市场，会把它在非 `prefer` 市场的份额倒到 `prefer` 市场。某个键在同一市场内多空抵消、净权重为 0 时，上期目标里没有这个键，输入层不给它补市场不可用的证据，该市场整体不可用时这个键对应的持仓按缺数平掉而不是冻结（极少见）。

**一个市场整体失败也算不可用**（方式 A、B 一样，只对涉及多个市场的策略）：时序因子在永续整体晚到时，该市场所有序列都在失败名单里，因子侧记 `degraded` 而不是 `skipped`。逐币的 `factor_failed` 不冻结，持有的永续会被卖成现货（缺数比例没超过 `max_missing`，或没持仓的币退回现货的行、缺数分母被摊薄）。所以两种情况按这个市场不可用处理——记 `market_unavailable`、冻结持仓：① 某个因子成员在这个市场本期读取的标的**全部失败**，在年龄探针之前判断（整体失败的市场不做探针）；探针之后扣掉年龄不够的标的、再按下面的范围重判一次“全部失败”，`max_missing` 为 1 时同样成立；② 失败的标的占比**严格大于** `portfolio.max_missing`，在年龄探针之后判断（比例恰好等于上限仍可用）。
统计范围：只统计本次实际读行的标的（规则预期集合的并集 ∩ 这个市场的基础集合：策略池被收窄、`universe.exclude` 排除的标的没读行，它们的失败不计入），并且只统计有行或在失败名单里的标的；探针之后的判断还要扣掉在这个市场年龄不够的标的，**但上期在这个市场持仓的豁免**（年龄剔除只拦新进入的标的，与单市场的缺数检查、选币池构造一致；持仓来自处理器先读出的上期状态，多空都算）。失败序列在源数据行存在时写成 NULL 行；上游缺失、整体晚到的序列没有行，只在失败名单里——代码里“在失败名单里就计入”。因子没有期望的序列（方式 B 里永续标签的活跃成员、但 `universe_series` 里还没有这条序列，或已停更而标签没移除）既没有行也不在失败名单里，不参与判断。这个口径与单市场的缺数检查**近似、不完全相同**：单市场缺数检查的分母是规则的预期集合减年龄剔除，这里是读行的标的减在这个市场年龄不够的标的，两者在池被收窄等边缘情况下可能差一点。每个因子成员各自统计，只看它自己的失败名单和行，不同成员的失败不叠加。
判断在读完行之后（方式 B 一次读完两个市场，不增加读取），认定不可用的市场清掉已读的行（必须清：不清的话没持仓的标的会取到不可用市场的行，在引擎里记成 `market_unavailable` 缺数，而不是退回另一个市场的行），规则级的年龄剔除集合也按剩下的市场重算。因此在设置了 `min_age_bars`（大于 0）时，同一个只在永续上市、没持仓的币在三条不可用路径上口径一致：因子被跳过、全部失败（都不做探针）与失败比例超限（探针之后清掉不可用市场的探针结果）都按年龄剔除记，不计入缺数检查。**`min_age_bars` 为 0 时没有年龄剔除**，不可用市场独有、没持仓的币记 `market_unavailable` 缺数、计入缺数检查：同一份数据只差 `min_age_bars`，结论可能翻转（例如永续 8 个币里 B、C、D 失败：为 0 时整期 `too_many_missing`，为 24 时只在现货开仓）；而且被记成年龄剔除的币其实历史齐全，结果明细里看到 `aged_out`/`min_age_bars` 时要结合“市场不可用”判断，不要误以为是新上市。比例路径还有一个例外：要判为不可用的市场如果探针窗口里一行都没有，会先整期 `history_insufficient`，而“因子被跳过”的路径照常求值（偏保守）。选币市场这样不可用、或所有市场都不可用时整期按 `market_failed` 跳过，说明里列出每个不可用市场各自的原因（`LoadBar` 返回的数据类跳过，不计实例故障；它不是“积累中”，不进积累期，持续出现走数据集新鲜度告警）。冻结的持仓仍计入缺数比例，比例超过 `max_missing` 时本期 `too_many_missing`、持仓不动。只是一部分市场不可用不整期跳过，缺数检查有两处收窄：① 永续本期整体不可用、并且空头规则（与空头候选过滤的范围一致）本期的**可用集合与缺数都为空**时，这条规则不做缺数检查——它的预期集合只剩上期持有、全部按市场不可用冻结的空头，检查必然得出 `universe_too_small` 或 `too_many_missing`，会把多头腿也一起整期跳过；冻结的空头照常产出保持目标，不新开空头，摘要里注明；holding 规则这一期不重建批次、沿用上期批次（否则启用后第一根 ok bar 正好碰上时会建出空批次，永续恢复后空头只配到一部分），到期没重建的批次在之后第一根 ok bar 上补建。可用或缺数不为空说明有持有的空头没被冻结（例如证据没覆盖到它、借用了现货行），这时照常做缺数检查。为了让持有的空头都有证据，输入层给不可用的市场构造 `market_unavailable` 证据时，除了这个市场本期基础集合里的标的，还补上上期在这个市场持仓（多空都算）的标的：它可能已不在本期的基础集合里（例如永续标签刚移除了它），没有证据就会借用现货行重新排名。② 多市场策略的缺数检查只排除一种冻结标的：**本规则上期没持有、并且因所在市场本期整体不可用而冻结（`market_hold`）**的标的。冻结按币，别的规则在不可用市场的持仓（例如永续空头）会让这个币在所有规则里冻结，它对没持有它的规则只是本期不参与的候选（仍留在分母里）。规则自己持有的冻结标的、以及只缺上一根而冻结（`prev_hold`）的标的照旧计入——只缺上一根与另一个市场可不可用无关，不能因为永续恰好也不可用就不计；比例超限仍整期 `too_many_missing`。单市场策略保持原来的缺数处理（纯永续大面积失败仍是整期 `too_many_missing`）。

**一个市场整体不可用**：绑定两个任务的实例里，只有一个市场的因子本期被跳过（`factor_skipped`）时，只让这个市场本期不可用，不整期跳过：这个市场里的标的记缺失原因 `market_unavailable`，可以冻结（已持仓的保持不动，不会因为一期没数据就被卖出），缺数检查把它们计入缺数（别的规则持有、因市场不可用冻结的标的不计，永续整体不可用时只剩冻结空头的空头规则不做缺数检查，见上面“一个市场整体失败也算不可用”）；新开仓可以用另一个市场。需要的市场全部不可用时仍按原来的原因整期跳过。成员契约变了、事件缺失、没有上一根的版本证据等配置、契约类原因，整期按原因处理。

**两种输入方式。** 同样的五种模式，因子数据可以来自两种组织方式，建实例时自己选；读完数据后都整理成同一种 Frame（每个标的一行，带本行市场与两个可用标记），后面的选币池构造、定市场、合成、组合约束、目标事件完全共用：

- **方式 A：现货、永续各一个因子任务**（`factor_tasks` 写 `spot=…`、`swap=…`），两个 View 汇合求值（见 4 的“汇合求值”）。
- **方式 B：统一数据集上的一个因子任务**（`factor_tasks` 写 `multi=…`）：同一个数据集里同时放同一标的的现货、永续两条序列，用 `series_tag` 区分，一个因子任务、一个 View，不需要汇合，到达即求值。

方式 B 的规则：

- **识别与登记**：任务的源数据集 `market_type` 是 `multi`（采集侧挂了现货、永续两个标签的数据集）。登记为 `multi`，只绑这一个任务，不能再绑别的；登记成 `spot`、`swap` 会被拒绝并提示写 `multi`。策略必须显式写 `market`（统一数据集没有可当默认值的市场），五种模式都可以用（纯现货、纯永续只取对应市场的序列）。
- **读取**：selector 不带 `series_tag`，一个 View 一期只读一次全部序列，再按 `packages/seriesset` 的 `SeriesTagMarket` 把行的 `series_tag` 换成市场（`market:` 段，没有这一段按现货），按市场拆成 Frame 里各市场的行。
- **活跃状态与标的全集按市场**：数据集挂的标签按标签自己的 `market_type` 归到市场，标签的活跃成员（且标的在数据集里是活跃绑定）就是这个市场的标的。永续下架而现货还在时，永续不可用、现货照常可用；只在永续上市的币不算现货缺失。事件里的标的名单是各市场标的的并集（View 就绪事件没有按序列的名单），每个市场用它与自己的活跃标的求交。
- **歧义**：现货、永续两条序列并存是正常的，只在同一个市场内判断歧义：同一标的同一周期在同一个市场里出现两个 `series_tag`，或某个 `series_tag` 换不出现货/永续（例如 `market:option`），才整期 `skipped(ambiguous_series)`。单市场数据集上同标的多序列仍是歧义。研究回放（`RangeLoader`）同样按市场过滤。
- **年龄探针按（标的、市场）**：`t_strategy_age_passed` 主键含 `c_market`，探针只认这个市场自己的序列有历史行，老的现货币新上永续时不能用现货的历史通过永续的年龄检查；内存缓存按（View、min_age_bars、市场）分槽，现货、永续每期交替探针不会互相覆盖。候选全部没通过时的“历史缺口”确认查询也只看这个市场自己的序列（读全部序列再按市场过滤，不取一行）：现货有数据、永续整段缺口时与方式 A 一样整期 `history_insufficient`，不会把永续全部判成新上市。启用时除 View 级覆盖校验外，按市场在目标根附近探针，某个市场一行都没有就拒绝启用。年龄不够的标的在这个市场的行不再被删掉，而是记进 Frame 里该市场的 `AgedOut`，选币池构造不取这些行，**但上期在该市场持仓的豁免**（年龄剔除只拦新进入的标的，持仓不能因为探针窗口里的历史缺口而无行、被卖出；这一条方式 A 同样适用）。
- **就绪判断读因子明细的按序列字段**，一份事件拆成各市场的结论（`readiness.Result.ForMarket`）：失败读 `failed_series`（先与周期级 `shared_failed_series` 合并，`seriesset.Union`），不读按标的折叠的 `failed_subjects`（一个币只在永续失败时它里面也有这个币，读了会让现货跟着失败）；`skipped_series_tags` 命中的市场本期不可用（数据类原因，记 `market_unavailable`，可冻结已持仓的标的），别的市场照常；成员 `skipped`（全部 tag 都跳过）、配置、契约类原因整期按原因处理。期望快照里只剩一个 `series_tag` 的一期同样有序列名单，失败照常按序列归到对应的市场。结论的分类与方式 A 一致，所以同样的数据在两种方式下得到同样的目标。
- **限制**：不支持 `factor_params`（参数按标的取值，现货、永续两条序列会共用同一组参数）；不能进策略池；研究回放支持（回放表的任务键是 `multi`，同一段的行只读一次 Storage、两个市场再按 `series_tag` 过滤；独立的回放发起表单与试算面板不列统一数据集上的任务，试算、回放按市场给 `factor_tasks` 时写成现货会提示写 `multi`，要回放统一数据集上的实例从实例详情发起）。回放的“因子现算”来源只支持一个主帧任务：方式 B 可以用，方式 A（两个任务）不能用（见第 10 节）。

两种方式都保留。是否只留统一数据集还没定：统一数据集现在拿不到资金费率、要与分开的数据集重复采集，跨市场的策略池也只能用方式 A，取舍与可走的几条路见[实现状态](../实现状态.md)第 3 节，等用户决定。

### 附加列来源与参考市场

**附加列来源（`sources`）**：策略仍只有一个主帧，`sources` 只增加“列的来源”：实例为每个来源另外绑定一个更慢频率的因子任务，规则用 `来源名.列名` 读它的列。适合“按日（或更长周期）选择、按小时调整”这类需要日线指标的写法。

```yaml
bar: 1h                       # 主帧：触发求值、规则状态、止损、冻结、缺数都按它
sources:
  daily: {bar: 1d}            # 至多两个来源；来源名小写字母开头的 snake_case
rules:
  - id: pick
    type: rank
    filter: "daily.close > daily.ma__20"
    score: "rank(daily.mom__20)"
    select: {top: 5}
    scale: {expr: "timing_coef"}    # 主帧的列，每根取值
```

- **写法与保存校验**：每个来源要写 `bar`，周期要长于策略的 `bar`，并且至少被一个表达式或 `select.group.by` 引用（没用到的来源仍要绑定任务，对齐的那一根还会等它，保存即拒绝）；来源名不能是表达式的保留标识符（`bars`、`score`、`instrument_id`、`rank`、`zscore`、`params`），也不能与主帧 View 的列同名（启用时查）。`来源名.列名` 可以出现在所有表达式阶段（含 `rank`/`zscore` 的参数）；`bars[-1].来源名.列名`、`来源名.列名.x`、`来源名[列名]` 都拒绝。`factor_params` 的表达式不能读来源列（只作用于主帧的任务）。策略池与池成员不能写 `sources`。
- **分组列写来源列**：`select.group.by` 可以写 `来源名.列名`（例如 `group: {by: daily.industry, max: 2}`），来源名必须已在 `sources` 声明（否则保存即拒绝），列名部分按普通列名检查，不能是表达式；只有 `group.by` 引用某个来源也算这个来源被引用。它与表达式里的来源列走同一条路：计入规则的必需列与来源要读的列，启用时在来源的 View 里核对列是否存在，分组值取这一根主帧按 as-of 读到的来源值。缺数口径与主帧的分组列一致：来源读不到、缺了一期或这一列为空的标的按缺数处理（`missing:来源名.列名`），计入 `max_missing` 的缺数占比；行里直接出现非数时记 `group_none`。hold 规则的持有标的缺这一列同样按缺数出场，冻结且本根没有行的持仓仍按规则状态记下的分组值占名额。已知差别：来源比主帧慢，对齐的那一根之后来源晚就绪的几根主帧里分组列缺数，按上面的缺数口径处理，需要时配 `on_missing`。
- **绑定**：每个来源按主帧的任务键各绑一个因子任务，登记为 `来源名:市场`（`--factor-task daily:swap=…`；主帧是统一数据集时写 `daily:multi=…`）。实例任务表按（实例, 来源, 市场）登记，空来源名是主帧。来源任务只读、不关联（`factor_params` 只作用于主帧任务），可以被多个实例共用，不随实例删除。
- **启用时的校验**：来源 View 的周期必须等于来源的 `bar`，日历与主帧相同；加密（定长周期）要求来源周期是主帧周期的整数倍，A 股的来源只能是 `1d`、主帧必须是日内周期；来源 View 不能有可变成员；DSL 引用的来源列都要在来源的每个 View 里；同名成员在来源的各市场里契约一致。来源的成员契约单独固化在 `resolved_json` 的 `sources.<名>.factors`，不混进主帧的 `factors`。
- **按时间对齐读取（as-of）**：每根主帧用 `ClosedPeriod(来源日历, 来源周期, 主帧 bar_end)` 算出应读的那一根来源 bar，只读这一根（`[bar_start, +1ns)`），列以 `来源名.列名` 并进主帧的行。读不到、或读到的不是应读的那一根（来源缺了一期），这些列按缺数处理，计入缺数划分。A 股 15:00 那根小时线读当天的日线，10:30 那根读上一交易日的日线（日线时间键是交易日期的 UTC 零点，与采集写入的行键一致）。A 股当天的日线在次日北京时间 08:00 才采集（见[采集](采集.md)第 4b 节），所以 15:00 那一根要等到次日 08:00 之后日线和日线因子到齐才汇合求值，结果在次日开盘前给出；盘中各根读的上一交易日日线当天 08:00 已到齐。日线数据集的附加字段（复权因子 `adj_factor`、申万行业 `sw_l1`～`sw_l3`、财务 `fin_*`）随日线因子任务进入来源 View，可以直接写 `daily.sw_l1`，例子见[策略 DSL 手册](../策略DSL手册.md) 12.11。
- **修订号**：来源读取不固定修订号（Storage 的修订号固定只接受当前修订号，非汇合 bar 固定上一次汇合时的修订号会在来源 View 有任何写入后一直读失败），读回服务端当前的修订号，每根都写进结果输入记录的 `views.<来源 View>.revision`；汇合 bar 上同时记下来源事件的 ID 与因子指纹。
- **汇合与指纹**：见第 4 节“汇合求值”。来源的因子指纹只在汇合 bar 上按来源的就绪事件核对，变化时按 `factor_changed` 处理；汇合 bar 上来源的因子被整体跳过（`factor_skipped`）时，这一根不读来源，来源列按缺数处理。
- **不新增的东西**：规则状态、holding 计数、S2 的持有根数、止损、冻结都只按主帧算，来源没有自己的求值与状态；来源的绑定在绑定解析里，来源变了（换任务、因子契约变化）重新启用时规则状态清空。

**参考市场（`market.reference`）**：单市场策略可以额外绑定另一个市场的任务，只用于 `age_markets: all` 的年龄判定，不参与选择与下单：

```yaml
market: {select: swap, prefer: swap, reference: [spot]}
universe: {min_age_bars: 24, age_markets: all}     # 现货、永续都满 24 根才入选
```

- **保存校验**：只能写 `spot` 或 `swap`，不能是模式已涉及的市场（所以只有单市场策略能写）；必须有规则（策略级或规则级 `universe`）写 `age_markets: all`；不支持 `factor_params`；池成员不能写。
- **绑定**：参考市场的任务按市场登记（`--factor-task spot=…`），由 DSL 的 `market.reference` 区分它与主帧；统一数据集上的任务不能再写参考市场。启用时核对它的市场、周期与日历，并且和主帧一样校验年龄覆盖与 `close` 列。参考任务固化在 `resolved_json` 的 `references`，不在 `tasks` 里，所以“只绑一个主帧任务”的实例照旧到达即求值。
- **运行**：每期读参考 View 的活跃标的作为这个市场列出的标的，按年龄探针判定（修订号不固定）；它只进 `age_markets: all` 的判断（缺一个市场或任一市场没通过即剔除，原因记 `age_markets`），不进 `each` 的判断，不读行、不进帧、不出目标。参考 View 的就绪事件直接确认。

### 策略池

> 状态：已实现（执行计划 S3；组合约束、资金费与股票池见通用能力扩展第 6 期，漂移分配、波动冻结与漂移起点见第 7 期，研究回放见第 8 期与下方“研究回放”）。回放的“因子现算”来源不支持策略池，策略池只能用 View 来源回放。

一个策略要么写 `rules`，要么写 `strategy_pool`，两者互斥。池由若干**成员**组成，成员引用已有的策略定义；每个成员独立求值，并在自己的模拟账本里维护含手续费的净值曲线，池按曲线分配资金。

```yaml
name: 双策略轮动
bar: 1h                                      # 必须写，成员的 bar（写了的话）要与它一致
strategy_pool:
  members:
    - {id: a, strategy: strategy_xxx}        # 引用已有策略；启用时固化其 DSL 与哈希
    - {id: b, strategy: strategy_yyy}
  allocation:
    method: fixed | rotation | drift         # drift 见下方“漂移分配”
    ratios: {a: 0.6, b: 0.4}                 # fixed、drift：必须覆盖所有成员，可以不归一（总敞口受 portfolio.leverage 约束）
    rotation:                                # rotation
      factors: [{name: return, window: 24, weight: 1}, {name: ma_ratio, window: 72, weight: 1}]
      top: 1                                 # 取名次靠前的几个，并列的平分
  timing: {window: 24}                       # 可选：成员净值在 window 期均线之上取 1，否则取 0
  step: 0.2                                  # 可选：每期每个成员的比例变化上限
  fees: {spot_bps: 10, swap_bps: 5, equity_bps: 3, funding_column: funding_rate}  # 可选：成员账本的单边手续费（默认 10 / 5 / 3 bps）与资金费列
portfolio: {leverage: 1.5, max_weight: 0.1}  # 组合级约束，max_weight 仍是同一个币的现货、永续合计；也可写 limits（见上文）
```

**成员约束**：现货、永续成员必须显式写 `market`；股票策略本来就不写 `market`，保存时分不出股票与加密，没写 `market` 的成员一律放行，启用时按池绑定的任务判断：绑的是 `equity` 任务就按股票成员处理，否则拒绝（“现货、永续成员必须写 market”）。股票成员与现货、永续成员不能混在同一个池里（`factor_tasks` 也不允许 equity 与 spot、swap 混用），股票池只做多、`portfolio.leverage` 不超过 1。成员不能是池（不嵌套）、不能用 `factor_params`、不能写 `sources` 与 `market.reference`、写了 `bar` 的要与池一致。池本身不写 `market`、`universe`、`factor_params`。池要绑定的因子任务是**成员所需市场的并集**（最多现货、永续各一个），每个成员只读它自己市场的 View；每个绑定的 View 都要有 `close` 列（账本按收盘价估值）。启用时把每个成员的策略 ID、DSL 文本、哈希和各自的绑定解析固化进会话的 `c_members_json`，之后改成员定义不影响已启用的池。保存池定义时检查成员存在、能进池；启用（以及带任务的校验、发起池回放）时再按绑定的任务推断成员市场，并检查数据集的保留期装得下预热（预热期数加成员最长回看）。

**每期计算顺序**：
1. 每个成员各自做就绪判断（只看它自己用到的市场与因子）并求值，得到成员目标。没通过的成员（缺因子、因子被跳过、输入配置问题、求值被跳过）沿用它上一期的目标权重，按普通权重参与合成（不用保持标记，保持会挡住其他成员在同一个标的上调仓）；池整体只有所有成员都没通过时才记 `skipped`：原因优先取需要人工处理的原因（`config_error`、`history_insufficient`、`ambiguous_series`、`factor_changed`，实例据此标 `degraded`），否则取第一个成员的原因（就绪判断阶段与求值阶段同一口径），说明里列出每个成员的原因，状态原样保留，摘要里也带各成员的状态与原因（池详情里这些期不缺）。
2. 每个成员的模拟账本先按本根收盘价**估值**（不调仓；永续按价差结算、写了资金费列时结算资金费、判定爆仓）。只有 `drift` 用这次估值，`fixed`、`rotation` 不用。
3. 算本期比例。`fixed`、`rotation` 用到**上一期末为止**的成员净值序列（`drift` 见下方“漂移分配”）：
   - `fixed`：直接用 `ratios`；
   - `rotation`：每个因子在未爆仓的成员之间排名（名次从 1 起，并列取平均名次），按因子权重加权得综合名次分，取最小的前 `top` 名（与第 `top` 名并列的一并入选）平分 1。序列不够长、算不出某个因子时这一期不排名，未爆仓的成员均分；
   - 乘择时系数：净值严格高于 `window` 期均线取 1，否则取 0（序列不足 `window` 期取 1）；
   - 按 `step` 限制每个成员相对上期比例的变化（上期没有比例时不限制）。
   - 写了 `exposure`、`gross` 时再按净敞口区间与总杠杆区间修正，写了 `allocation.switch` 时再做条件转移（见下方“组合约束”）。这几步只作用于本期合成用的比例，下一期步长用的上期比例仍是步长之后、这几步之前的值。
4. 每个成员的模拟账本按成员目标调仓（没通过的成员只估值、不调仓），追加本期期末净值；账本复用研究回放的账本（含手续费、粉尘阈值，永续逐期结算，不模拟强平与保证金率），初始权益 1。加密成员缺价 3 期后清算；股票成员（池按股票市场运行时）停牌缺价按最后价格保持持仓、不清算，费率用 `fees.equity_bps`，不模拟 T+1、整手与最低佣金。写了 `fees.funding_column` 时永续持仓计资金费（见下方“资金费”）。缺的期（没被处理的周期）净值沿用上一个值补齐。
5. 池目标 = Σ 合成比例 × 成员目标权重，按（标的, 市场）合成；成员冻结（因市场不可用或只缺上一根保持持仓）的标的在池里保持上期池目标，其余走与普通策略相同的组合约束：先 `limits`（单标的上限与超限转移，分组目标是各成员的合成比例 × 成员目标），再 `leverage` 与 `max_weight`（超出的部分留作现金）。
6. 模拟爆仓（成员账本权益不为正）：爆仓成员的比例一律为 0（从爆仓那一根的下一根起）——不参与轮动排名，不受步长限制，`fixed`、`drift` 也归零；择时系数照常按净值与均线计算并写进明细，只是最终比例被置 0；明细里标 `bankrupt`。

**组合约束**（都按成员汇总的分配比例计算：多头敞口 = 多头成员的比例之和，空头敞口 = 空头成员的比例之和，不按实际持仓折算、不做同标的抵消）：

```yaml
strategy_pool:
  allocation:
    method: fixed
    ratios: {long_core: 0.5, short_core: 0.45, short_new: 0.05, probe: 0}
    switch:                                    # 条件转移，按顺序判断，第一个成立的生效
      - when: {empty: probe}                   # probe 本期的有效目标没有任何持仓
        move: {from: short_new, to: [short_core]}   # 把 from 的比例全部转给 to（同方向）
  exposure:                                    # 净敞口区间 = 多头敞口 − 空头敞口，各段按书写顺序执行
    bands:
      - {min: -0.1, max: 0.3, adjust: auto, pivot: 1.0}
      - {when_gross_below: 1.0, min: 0, max: 0, adjust: raise_smaller}
  gross: {min: 1.0, max: 1.8}                  # 总敞口 = 多头敞口 + 空头敞口
```

- **成员方向**：用了 `method: drift`，或写了 `switch`、`exposure`、`gross` 时，每个成员都必须是单方向的（规则全部做多或全部做空；规则的 `side` 默认 long），保存与启用时都校验。
- **执行顺序**：步长之后（drift 是侧内再平衡之后）依次执行 `exposure` 各段、`gross`、`switch`，再合成池目标。
- **`exposure`**：写了 `when_gross_below` / `when_gross_above` 的段只在执行到这一段时总敞口满足条件才执行。净敞口超出 `[min, max]` 时按**超出方向**修正，侧内构成不变：
  - `reduce_larger`：净敞口高于 `max` 时按比例缩小多头一侧，低于 `min` 时缩小空头一侧；
  - `raise_smaller`：净敞口高于 `max` 时按比例放大空头一侧，低于 `min` 时放大多头一侧；
  - `auto`（必须写 `pivot`）：总敞口大于 `pivot` 时同 `reduce_larger`，否则同 `raise_smaller`。

  要缩放的一侧比例为 0 时无法修正，原样保留并在明细里注明（例如只有多头成员的池净敞口高于 `max` 时写 `raise_smaller`，或 `auto` 在总敞口不大于 `pivot` 时要放大的一侧为 0）；缩小到负数时截到 0，这时净敞口仍在区间外。
  区间包含 0 时，超出方向的一侧就是较大的一侧；区间不含 0 时（例如 `[0.2, 0.5]`）也按超出方向修正，净敞口回到区间边界，而不是缩小数值较大的一侧（那样会把净敞口推得更远）。
  放大一侧后总敞口可能超过 `gross.max` 或 `portfolio.leverage`，随后被整体缩小，净敞口按同一倍数变化，可能又离开区间（区间指缩放前的口径）。
- **`gross`**：大于 `max` 时整体按比例缩小，小于 `min` 时整体按比例放大；池的第一根（还没推进过）不放大。整体按倍数 k 缩放时净敞口也按 k 变化，可能离开 `exposure` 的区间（区间指缩放前的口径）。`gross.max`、`gross.min` 不能超过 `portfolio.leverage`，`leverage` 仍是最后的硬上限。
- **数值**：`exposure`、`gross` 在比例的 float64 副本上计算，算完四舍五入到 12 位小数再换回定点数；没写时不做这次换算。
- **`switch`**：只能与 `method: fixed` 或 `drift` 一起写（rotation 不支持）。“有效目标”是成员本期参与合成的目标：成员没通过、沿用上期目标时按沿用后的目标判断。比例恒为 0 的“监控成员”照常求值、推进账本，只用于条件判断。`from` 的比例按 `to` 各成员本根的比例分给它们（都为 0 时平分，最后一个接收者取剩余，侧的总量精确不变；平分时不区分 `to` 成员是否已爆仓，爆仓成员也会分到比例）；`from` 与 `to` 必须同方向，保存时校验。
- **明细**：`summary_json.pool.adjustments` 记各段修正与杠杆缩放（段号、缩放的一侧、倍数、前后的多空敞口），`switch` 记生效的转移；成员的 `composed` 是实际用于合成的比例（与 `ratio` 不同时才有，`ratio` 仍是步长之后的比例）。

**漂移分配（`method: drift`）**：成员比例不再每根回到固定值，而是随成员持仓价值的自然变化漂移，再按两侧各自的规则拉回 `ratios` 的侧内构成。

```yaml
strategy_pool:
  allocation:
    method: drift
    ratios: {long_core: 0.3, long_majors: 0.2, short_a: 0.25, short_b: 0.05, short_c: 0.2}   # 目标比例，必须覆盖所有成员
    start: "2026-01-17T07:00:00Z"          # 可选：漂移起点；或写 initial: {at: <时刻>, ratios: {...}}，二选一
    sides:                                 # 不写的一侧不再平衡
      long: {rebalance: every_bar}
      short:
        rebalance: both                    # none（默认）| every_bar | periodic | threshold | both
        period_bars: 2160                  # periodic、both 必填
        anchor: "2026-01-17T07:00:00Z"     # 可选：periodic 的相位起点，默认漂移起点
        threshold: 0.6                     # threshold、both 必填
        spread_bars: 24                    # 可选：触发后分几根走完，默认 1
        drift_by: notional                 # notional（默认）| nav
  freeze: {watch: short, window_bars: 1, threshold: 0.10, bars: 4}   # 可选：波动冻结
```

- **前提与互斥**：每个成员必须是单方向的；不能写 `timing`、`step`、`rotation`。`start`、`initial`、`sides`、`freeze` 只能与 drift 一起写，写在 fixed、rotation 下保存即拒绝。`sides` 的字段按方式成对校验：`period_bars`、`anchor` 只能配 periodic、both，`threshold` 只能配 threshold、both，`spread_bars` 不能配 none。
- **记号**：gᵢ 是成员 i 的分配系数（池目标 = Σᵢ gᵢ·wᵢₖ，位置与 fixed 的比例相同）；vₖ 是成员账本上一次调仓后持仓 k 的带符号价值（现货市值、永续名义价值）；rₖ = 本根收盘价 ÷ 上一次估值价 − 1，缺价的持仓记 0，池跳过几根（或缺期）时就是这几根的累计收益；ρᵢ = Σ|vₖ|·rₖ ÷ Σ|vₖ|（空仓为 0）是持仓名义价值的收益率，πᵢ = Σvₖ·rₖ ÷ 成员权益是资金收益。上一次估值价就是账本里持仓的最后价格，状态里不另存。
- **每根的漂移**：gᵢ′ = gᵢ·(1 + ρᵢ) / (1 + Σⱼ gⱼ·πⱼ)。分子是成员持仓名义价值的变化（空头的名义价值随价格上涨同样变大，但这时在亏损），分母是账户权益的变化；预算没用满、`scale` 截掉的部分、`filter_after` 留下的现金都不影响 ρᵢ；成员空仓时只随权益变化。`drift_by: nav` 的一侧，侧的总量照此漂移，侧内构成改按 gᵢ·(1 + πᵢ) 分配（盈利的成员占比变大）。
- **侧内再平衡**（每侧分别配置，侧的总量保持漂移后的值，只改侧内构成；目标构成是 `ratios` 的侧内比例，爆仓成员的目标为 0）：
  - `every_bar` 每根触发；`periodic` 在 (bar 序号 − 锚点序号) ÷ `period_bars` 的整数部分比上一次求值的那一根大时触发，所以触发点落在被跳过的根（池跳过或缺期）时，在之后第一根成功求值的 bar 上补触发；相位按 (bar 序号 − 锚点序号) mod `period_bars` 计，`anchor` 晚于漂移起点时，锚点之前相位为 0 的根同样触发；`threshold` 在任一成员的 |侧内占比 ÷ 目标侧内占比 − 1| 超过阈值时触发，目标比例为 0 的成员不参与判断；`both` 两者都判断，同一根都满足时记 periodic；`none` 不再平衡；
  - `spread_bars`：触发那一根起每根移动“当前构成到目标的距离 ÷ 剩余根数”，最后一根精确到达；分步期间不重新判断触发（这期间落下的 periodic 触发点不补），走完后从下一根起照常判断。
- **波动冻结（`freeze`）**：被观察成员（`watch` 写 long、short 或成员 id 列表）的组合净值 = Σ `ratios`ᵢ × 成员净值，本根取估值后的净值，与 `window_bars` 根之前的净值比较，涨跌幅绝对值超过 `threshold` 时从这一根起冻结 `bars` 根（按 bar 序号计，池跳过的根也算；冻结中再次触发会从那一根重新计时）。冻结期间跳过侧内再平衡（分步暂停、不消耗剩余根数，也不触发新的）、`exposure` 与 `gross`，直接用漂移后的系数；`switch`、`limits`、`leverage`、`max_weight` 照常执行。净值历史不足 `window_bars` 根时不判断，漂移起点那一根（及之前的根）也不判断；被观察成员的 `ratios` 都为 0 时组合净值恒为 0，不会触发。`window_bars` 计入预热期数与净值序列的保留长度。
- **顺序与状态**：估值 → 漂移 → 冻结判断 → 侧内再平衡 → `exposure` → `gross` → `switch` → 合成。`gross` 之后（冻结时是漂移之后）的 gᵢ 写入规则状态的 `pool.drift.g`，下一根从它漂移；`switch` 的转移与 `limits` 不写回。漂移起点那一根与池的第一根一样，`gross` 不放大。
- **数值**：漂移、侧内再平衡、`exposure`、`gross` 都在 float64 上计算，合成前四舍五入到 12 位小数换成定点数（只换一次），再乘成员目标权重。
- **漂移起点**：
  - `allocation.start`：漂移从这一根开始，系数在这一根置为 `ratios`；预热也从这一根开始（成员的规则状态与账本从这里起步），推进到最新已收盘的一根；
  - `allocation.initial: {at, ratios}`：系数在 `at` 那一根置为给定的比例（例如从一次回放结果里取），之后照常漂移；预热从 `at` 往前推成员所需的预热期数开始，`at` 之前的根按 `initial.ratios` 合成、不写入漂移状态。成员的规则状态与账本是重新预热出来的，不复制回放的状态，所以与回放在这一刻之后的结果会有差别，只能做到“比例一致”；
  - 都不写：漂移从预热的第一根开始，系数置为 `ratios`，periodic 的默认锚点就是这一根；
  - 时刻都指某根 bar 的 bar_start（交易日期指该日第一根）。池不写 market，保存时分不出加密与 A 股，只检查写法；启用时按池绑定的日历与周期换成 bar 序号，不是 bar 起点就拒绝；起点晚于最新已收盘的一根、或从起点到最新一根超过 20000 根（预热与研究回放共用的上限）、或 View 的历史覆盖不到起点时，都在启用时拒绝，错误里写明需要多少根；
  - 停用再启用产生新会话：池的 DSL、绑定解析与成员都没变时沿用规则状态，从状态所在的那一根之后接着推进到最新一根，系数、分步与冻结状态连续；任何一项变了就从起点重新预热（见下方“预热”）。
- **明细**：`summary_json.pool.drift` 记本根的阶段（`pending` 还没到起点、`start` 起点那一根、`drift` 照常漂移）、有成员的每一侧的再平衡（方式、本根触发原因、`threshold` 用的最大偏离、是否移动、剩余分步根数与分步的触发原因、冻结中是否暂停）与冻结状态（窗口涨跌幅、是否触发、是否冻结、冻结截止的 bar 序号）。drift 下成员的 `base` 是目标比例，`ratio_before` 是漂移前的系数，`drifted` 是漂移后、再平衡与组合约束之前的系数，`ratio` 是写入状态的系数，`composed` 只在 `switch` 改变了它时出现。不写 drift 时这些字段都不出现。

**资金费**：写了 `fees.funding_column`（例如生产采集的 `funding_rate`，取值是本根内各次结算费率之和）时，成员账本按这一列给永续持仓结算资金费。第 k 根的费率是这一根开盘时刻的结算，那一刻持有的是第 k−1 根收盘调仓之前的仓位，所以账本每根估值后记下永续持仓的带符号名义价值（按这一根的收盘价，也就是下一根开盘时的价格），下一根按它乘本根费率结算进现金：费率为正时多头付、空头收；第 k−1 根收盘时平掉的仓位第 k 根仍要付，新开的仓位不付；费率为空时不结算。只读永续的 View，启用时要求池绑定了永续、且永续的 View 有这一列；成员都不涉及永续时写了即保存拒绝。不写时与原来一样，不计资金费，状态里也不出现快照。

**轮动因子**（作用在成员净值序列上，`order` 可选 `asc` 或 `desc`；默认 `return`、`ma_ratio` 降序，`drawdown` 升序）：`return(w)` 区间收益 = 净值 ÷ w 期之前的净值 − 1（需要 w+1 个值）；`ma_ratio(w)` = 净值 ÷ 最近 w 期均线 − 1（w 个值）；`drawdown(w)` 最近 w+1 个净值上的最大回撤，越小越好。

**预热**：启用后后台用研究回放的历史读取，从启用时刻往前按真实历史依次求值所有成员、推进账本（成员之间共享行读取），一直推进到最新已收盘的一根（收盘超过宽限一分钟、View 里已有数据；研究回放把最新一根排除在外，预热不能——它的就绪事件在启用之前就发出了，没有别的路径会处理它），再在一个事务里把最终状态写进实例的规则状态行（`t_strategy_states`）、把预热终点写进会话的 `c_warmed_through`。期数 = max(轮动因子、择时与波动冻结的最长窗口, 成员最长持有期) + 1；drift 写了 `allocation.start` 时改为从 `start` 推进到最新一根，写了 `initial` 时从 `initial.at` 往前推这么多期开始（见上方“漂移分配”）。成员最长持有期统计 `holding.bars`、`hold.max_bars`，以及日历换仓（`holding.calendar`）一个周期内最多的 bar 数：A 股的月按 23 个交易日、周按 5 个交易日，加密的月按 31 天、周按 7 天，`trading_days` 按 `every` 个交易日，再乘每日根数。
- 预热完成前，触发器对这个实例返回等待（事件稍后重投、到达记录照写，完成后按 bar 顺序补处理，不丢期也不乱序），确认实盘被拒绝（`ConfirmStrategyInstance` 返回“策略池预热未完成”）；
- 完成后：不晚于预热终点的事件直接去重；第一期从预热出的规则状态起算；之后照常求值（挂了账户、还没确认实盘的实例发影子目标）；
- 进程在预热中途重启：启动时对没有预热结果的池会话重新开始预热；
- **停用再启用**产生新会话，新会话同样要先预热，但分两种情况：
  - 池的 DSL、绑定解析与成员快照（成员的 DSL 与各自的绑定）都和规则状态所属的会话逐字节一致：状态挂到新会话沿用，预热只从状态所在的那一根之后接着推进到最新已收盘的一根（停用期间漏掉的根用历史补上，账本、净值序列、分配比例、成员的规则状态都连续）；期间没有新收盘的根时不读历史，预热立即完成；
  - 其余情况清空状态、从预热起点从头推进：上面任何一项变了；状态所在的那一根早于从头预热的起点（停用期间漏掉的根数超过一次预热要推进的根数——没写 drift 起点的池是上面的“期数”，写了 `allocation.start` / `initial` 的池起点固定，不会出现）；状态无法解析；或接着推进失败（例如 Storage 暂不可用），这时直接改为从头预热，不重试接着推进。状态之后那一根已过一分钟宽限、但 View 还没写到它时不算失败：和没有新收盘的根一样原样沿用，那一根等它的就绪事件照常处理；
  - 接着推进用的是历史读取，与实时路径的差别和预热相同（没有就绪信息：停用前因就绪判断没通过而跳过、状态没有推进的那几根，接着推进时会按历史数据求值）；
- 启用时按精确的覆盖统计核对 View 实际的历史够不够预热（不只看配置的保留期），不够就拒绝启用；预热要推进的根数超过 20000（与研究回放共用的上限）时也在启用时拒绝，不写 drift 的池同样适用（例如 1m 周期、成员按日历月换仓，期数约 44640）。这时报错里“把 allocation.start 改晚一些”的提示只对写了起点的 drift 池有意义，其他池要缩短窗口或持有期；
- 暂时性错误（Storage 暂不可用）按退避重试，永久性错误（数据覆盖不够、配置无效）或重试用尽时，实例标 `degraded`、触发器不再让事件等待，并留下一条 `skipped(pool_warmup_failed)` 结果，原因写在输入摘要的说明里（页面的历史结果直接可见），修复后重新启用；
- 预热结束后的第一期没有相邻记录，用到 `bars[-1]` 的成员会因“上一根版本未知”没通过一期（沿用上期权重），可以接受。

**已知局限**：
- 重新启用后接着推进时，年龄判定（`min_age_bars`）已通过的标的集合从空开始重新探测，而一路推进时这个集合是累积的：只有标的在探针窗口里恰好有连续 3 根以上的历史缺口时，两者对它是否满足年龄的结论才会不同；
- 预热终点包含最新已收盘的一根，只靠一分钟宽限判断它的数据写完了：可能读到半截数据（那一期的成员状态按缺数推进、其正式事件被去重，之后的期次不受影响），也可能这一根的数据还没到而少推进一期（净值沿用上一个值补齐）；
- 绑定现货、永续两个任务的池与普通双任务策略一样要等两个 View 的事件都到齐才求值：一个 View 长时间不来事件，整个池都停（只有缺的 View 已经到了更晚的一期、或更晚的一期已经汇合时才补记 `skipped(market_missing)`）。“只缺部分市场时只把用到该市场的成员判为没通过”没有实现；
- 实时求值时每个成员各自读一次自己的行（只有预热共享读取），处理器按整个事件持锁串行处理所有实例；成员多、标的多时这段耗时要在 V3 的模拟盘上实测。预热耗时的实测（10 成员 × 168 期 × 500 标的，1.6 秒）用的是假客户端，不含 Storage 的网络与查询开销，只是下限；
- 池状态偏大（10 成员 × 500 标的约 26 KB/期），短周期的池每天写入的结果较多；
- drift 的几处简化：periodic 的触发点落在分步或冻结期间时不补（只有落在被跳过的根上才补）；冻结按 bar 序号计根数，池整根跳过的根也消耗冻结；成员爆仓后从下一根起系数为 0，不再分给同侧其他成员；权益变化的分母 1 + Σgⱼ·πⱼ 不为正（池整体亏光）时所有系数归零；分步再平衡的目标构成不在触发时固定，每根按 `ratios` 去掉已爆仓成员重新计算（只在分步中途有成员爆仓时与“触发时固定”不同）；漂移起点那一根整根跳过（所有成员都没通过）时，漂移从之后第一根成功求值的 bar 开始，状态里的起点序号记这一根，periodic 的默认锚点仍是配置的起点；ρ、π 只按持仓的价格收益计算，不含手续费与资金费（写了 `fees.funding_column` 时资金费只进成员净值，影响波动冻结的判断，不进漂移公式）；
- 资金费只在账本推进的那一根结算：池整根跳过（所有成员都没通过）或事件缺失的期不推进账本，这些根的费率不结算；之后第一根结算的是它自己的费率，用的是最后一次推进那一根调仓之前的持仓与收盘价（不是之后实际持有的仓位；净值补齐期间没有估值）。

**研究回放**（`StartReplay`，第 10 节）：
- 发起：`factor_tasks` 给成员所需市场的并集（与建实例相同）。成员定义的来源：
  - 从定义或 DSL 草稿发起：取成员的当前定义，并核对都能进池；
  - 从池实例发起：取会话固化的成员快照，回放的是实例在跑（或最后在跑）的成员版本。
- 提交时：按成员各自解析绑定，按每个成员的回看要求校验起点、截断终点，把成员（策略 ID、DSL 文本与哈希、各自的绑定）写进回放记录的 `c_members_json`。
- 执行：只读这份快照，不重读成员定义，所以排队期间改了成员定义不影响结果。执行时按快照里的 DSL 重新解析绑定，核对因子指纹，指纹变了就拒绝执行。
- 逐期逻辑与预热共用同一段代码（成员之间共享读取、调用同一个 `pool.Step`），回放从空状态开始，所以与同一区间、同一起点的预热逐期一致。
  有成员用了 `params()` 时，回放与预热都读 `__params` 列，成员取到 View 里记的实际参数，与实时求值成员时一致（批 3 之前两者都取到 NaN）。
- 账本：合成后的池目标由一个池级账本承接，费率与滑点用回放任务的现货、永续费率与 `slippage_bps`，与单策略回放一致；成员账本仍用池 DSL 的 `fees`，不计滑点。资金费只看池 DSL 的 `fees.funding_column`，成员账本与池级账本都按它结算；回放任务上写 `funding_column` 即拒绝。
- 每期记录：摘要的 `decision.pool` 与 `decision.limits` 就是实时结果里的池明细与超限转移。
- drift 的起点：写了 `allocation.start`（或 `initial.at`）时，回放的起点必须等于它，否则提交即拒绝，错误里写明该填的 start_time；没写时漂移从回放区间的第一根开始。写了 `initial` 的池，回放里成员从 `at` 才开始求值，不像预热那样往前多推若干期，所以只有 `at` 那一根的比例与实时一致。
- 换代：读取期间 View 换了索引时整个池一起跟随（一次回放累计最多 3 次）。
- 页面：回放页显示每期的池明细（与实例结果里的池卡片相同，覆盖周期表当前页）。
- 比对：`skills/moox/scripts/strategy_check.py targets --replay 名称=回放ID` 导出每期目标，再用 `compare` 与参考结果比对。

回放与实时的差别见第 10 节的“回放与实时的已知差别”。

**结果与展示**：每期把池明细写进结果摘要 `summary_json.pool`（各成员的状态与没通过的原因、期末净值、基础比例、择时系数、步长前后的比例、综合名次分、总敞口、净敞口与各（标的|市场）的贡献），解释明细的规则 id 是 `成员 id/规则 id`，规则状态里 `members` 是各成员自己的状态、`pool` 是上期比例、净值序列与账本（drift 另有 `drift`：分配系数、漂移起点序号、分步与冻结状态；drift 不写上期比例）。池的 skipped 记录不动规则状态，摘要里的账本与比例取当前状态。成员遇到需要人工处理的原因（`config_error`、`history_insufficient`、`ambiguous_series`、`factor_changed`）时，池照常出 `ok`，但实例标 `degraded`，且只要同一期里还有这类成员就不执行 ok 周期的健康恢复。**成员净值是按收盘价成交的模拟曲线，只用来分配资金，不代表实盘收益**（不模拟调仓阈值、最小下单额与拆单，也不模拟强平；资金费只在写了 `fees.funding_column` 时计入）。

### 因子任务、成员键与列名

策略不再自己声明因子：**创建实例时选定一个因子任务**（市场模式含现货和永续时有两种选法：现货、永续各一个，或统一数据集上的一个任务，登记为 `multi`；只能选本空间里运行中的任务），规则里直接写任务结果数据集的列名。创建后实例的 `factor_tasks` 不能改。
一个任务可以被多个实例引用。**只有 DSL 声明了 `factor_params` 的实例**第一次启用时对主帧任务调用 `FactorMgr.BindFactorTask` 与任务正式关联，独占：一个任务只能被一个实例关联（任务里要有可变成员），之后只有它能给任务提交参数；
创建实例时不检查任务是否已关联（管理台的创建页对这样的定义不列出已关联到别的实例的任务）；任务已关联到别的实例时，启用会在解析通过后的关联这一步被拒（“关联的是实例 X，不是本实例”）。关联只在解析与市场核对都通过之后写入，启用失败的实例不会占住任务。关联一直保留到删除实例：删除已停用的实例时，关联到它的任务和任务的结果数据集一起删除；还有别的实例引用这个任务时拒绝删除，先删引用方（见第 7 节「删除实例」）。
没有声明 `factor_params` 的实例不关联任何任务，启用时只用 `GetFactorTask` 确认任务已启用；它只读任务的列（含已关联给别人的任务的可变成员列，参数由关联它的实例提交），删除实例时任务保留。
所以**只有固定成员的任务不随任何实例删除**，会一直计算，不用了要到因子页手动停用或删除；因子侧删任务时不知道有哪些实例在引用，被删后由 `missing_factor_tasks` 提示。
策略停止不影响因子任务，它照常计算，由用户手动停止。读取的 View 就是任务结果数据集的默认 View `view_factor_<后缀>`，由任务 ID 推导。

任务里每个成员对应哪些列由规则推导（完整说明见[因子](因子.md)的「成员键与列名」一节）：

```text
成员键 = 因子ID [ "__" 参数段 ]      参数段 = "var" | 值 { "_" 值 }      值里小数点写 p、负号写 n，只写值、按定义声明的参数顺序
列名   = 成员键 [ "__" 输出名 ]       单输出因子没有输出段
```

| 成员 | 列名（规则里直接引用） |
| --- | --- |
| `ema`，参数全为默认值 | `ema` |
| `ema`，span=20、warmup=50000 | `ema__20_50000` |
| `rsi`，参数全为默认值 | `rsi` |
| `boll`，window=30（多输出：mid/up/low/pctb） | `boll__30__mid` 等 |
| `ma_fast`，可变成员 | `ma_fast__var` |

要记住两条：**参数全为默认值时省略参数段**（所以默认的 `boll` 成员列是 `boll__mid`，不是 `boll__20__mid`）；**可变成员固定以 `__var` 结尾**。
创建实例选好任务后，页面会列出这个任务的全部列名（可复制）。校验时规则引用了任务里不存在的列，报错会列出最接近的几个列名并附上这个任务的全部列，不会只说“列不存在”。

### 动态调参

任务里的**可变成员**（`<因子>__var`）由策略逐期提交下一期的参数；固定成员的参数在加成员时写定，策略不能改。策略用 `factor_params` 声明每期如何求出可变成员的参数，键是成员键：

```yaml
factor_params:                # 可选：每期求出下一期的可变成员参数；键只能是任务里的可变成员键
  ma_fast__var:
    window:
      default: "20"                               # 统一值：数值表达式，按标的求值后取中位数（不引用列的常数就是它本身）
      per_subject: "10 + 30 * rank(vol_zf_std)"   # 可选：按标的求值，与统一值不同的标的进入覆盖
  ma_slow__var:
    window: "60"                                  # 简写：只写统一值

rules:
  - id: cross
    type: rank
    pool: [BTC-USDT]
    score: "0"
    select: {top: 10000}
    hold:
      entry: "bars[-1].ma_fast__var <= bars[-1].ma_slow__var && bars[0].ma_fast__var > bars[0].ma_slow__var"
      exit: 'bars[0].ma_fast__var < bars[0].ma_slow__var || params("ma_fast__var", "window") > 50'
    weight: {total: 1}
```

- **读取实际用的参数**：规则或参数表达式里写 `params("成员键", "参数名")`（两个都是字符串字面量，成员键必须是可变成员的），值来自结果行的系统列 `__params`，即这一行上该成员**实际用的**参数；
  这一行没有这个值时是 NaN，与缺数的处理一致。用到 `params()` 的实例，实时求值和回放都会显式读取 `__params`。
- **启用实例**：声明了 `factor_params` 的实例先调用 `BindFactorTask`（幂等，换一个实例会被拒绝），再检查任务在运行、DSL 引用的列都存在于任务的结果列里、`factor_params` 的键都是任务里的可变成员、任务的每个可变成员都有输出、参数名是该因子声明过的；
  `resolved_json` 固化任务 ID、结果 View、各列所属成员的契约哈希（定义哈希加成员类型）与可变成员的参数声明（`factor_params`）。
  没有声明 `factor_params` 的实例不关联任务，可以只读任务里的可变成员列与 `params()`；它的 `resolved_json` 不带参数声明，也不提交参数。关联本身不进 `resolved_json`，所以规则状态的沿用判断不受关联与否影响。任务先于策略运行，可以已经积累了历史，不再有“私有因子集刚建、还没有数据”的等待。
- **参数输出**：只在正常周期的决策为 `ok` 且尚未过期时求值；追赶与过期周期只推进规则状态，不保存或提交下一期参数（正常求值后在提交时才过期的，丢弃已经算出的参数）。结果按因子定义的声明整理：没写出的参数取默认值，整型四舍五入，所有取值限制在声明范围内（被限幅会记入说明）；
  某个参数在所有标的上都没有有效值时，这个成员本期不提交（因子沿用上一次提交的值，从未提交过用成员的默认参数）。
- **投递**：下一期的参数写进这一期结果的 `c_next_params_json`，与结果**在同一个事务里**落库。独立的投递循环只投当前会话里**最新一条还没送达**的结果（更早的未送达记录被覆盖，直接跳过），
  调用 `FactorMgr.SubmitFactorParams`（请求号取结果 ID，目标期是这条结果的下一期），失败按退避重试（1 秒起、上限 30 秒），送达后写 `c_params_delivered_at`；
  被因子侧明确拒绝的写 `c_params_error` 且不再重试（因子侧只接受目标期不减的提交，重试的旧请求不会让参数倒退）。实例停用时当前会话里没送达的结果不再投递，重新启用从新会话的第一条结果开始。
  模块或实例暂停时不提交，因子沿用上一次的参数；观察实例（没有账户）同样提交。
- **滞后告警**：实例在运行、任务有可变成员、最近连续 `params.stale_alert_periods`（默认 10）期结果都没有送达参数时，导出 `moox_strategy_param_delivery_stale{space_id,instance_id}=1`，实例停止后解除。
  因子引擎积压追赶时不等策略，晚到的提交从下一个还没开算的期次起生效，每期实际用的参数以 `__params` 为准（见[因子文档第 11 节](因子.md)）。
- **不支持**：声明了 `factor_params` 的策略不支持试算（`ValidateStrategy` 只校验 DSL）与读 View 的回放；回放只能用“因子现算”来源（`StartReplay` 的 `input=compute`，见第 10 节）。

## 4. 处理流程

```text
ViewDataReady（View, period_time, universe_subject_ids, detail_type + detail：因子的 PeriodDetail，各成员含 definition_hash）
  ─► 找出绑定该 View 的全部启用实例，逐个处理，错误汇总；全部终态落库后才 ACK
  ─► 重复周期忽略；乱序周期 ─► skipped(out_of_order)
  ─► 汇合（只绑定两个因子任务的实例）：先把这个 View 的原始事件幂等写入 t_strategy_ready_events 并确认，两个 View 本期都到齐才往下走；
        更早、不会再等到齐的期补记 skipped(market_missing)（见下）
  ─► 标记追赶 / 已过有效期的周期：仍尝试求值，只推进状态，不发目标
  ─► 就绪判定（见下表）
  ─► 读取输入：只读绑定的 View，分页时固定活动索引与修订号，变化即整期重读
        标的元数据（标的绑定、标的详情、标签、标签成员）跨周期缓存，LoadBar 取得 View 后先读一次
        GetDataset 的 subjects_revision，与缓存一致才复用，变化则整体重读；行数据每期现读、不缓存
        基础集合 U = 事件名单 ∩ 活跃标的
        规则 r 的预期集合 E(r) = U ∩（显式 pool 或 universe 配置）
        年龄剔除 G(r)：E(r) 中不满足规则的 min_age_bars、或已通过 max_age_bars（不再是新标的）的标的，每个需要的 N 各探针一次（探针查询在当期主查询之后、固定同一修订号；通过探针的标的按 View 活动索引与 min_age_bars 持久化在 `t_strategy_age_passed`，之后跨周期、跨重启不再探针，只探针尚未通过的标的，全部已知时不发查询）；
                       规则上期已持有的标的不剔除
        可用集合 A(r)：E(r) − G(r) 中有行、所需列都有值、且所需列未被上游标记失败的标的
                       （hold 规则的持仓只需要 filter、hold.exit、scale 与 group.by 的列，
                        未持有的候选需要全部列；仓位系数无效也算缺数）
        保持集合 H(r)：上期已持有且只因市场不可用或只缺上一根缺数的标的，以及写了 on_missing 的规则里连续缺数不超过 keep_bars 的持有标的（不求值、不调仓，见下）
        普通缺数集合 M(r) = E(r) − G(r) − A(r) − H(r)；max_missing 同时计算 M(r) 与 H(r)
  ─► 纯函数引擎：守门 → rank → 组合合成与约束
  ─► 正常周期：一个事务写入结果、解释明细与（绑定账户时）待投递事件
        追赶 / 过期周期：成功求值后只保存规则状态与摘要，结果为 skipped(catchup / expired)
  ─► 后台发布正常 ok 结果的 LogicalAccountTargetWeightRequested
```

正常周期的就绪判定按顺序：

| 情况 | 结果 |
| --- | --- |
| 引用的列所属的成员不在事件明细（`detail_type=moox.factor.PeriodDetail.v1` 的 `PeriodDetail`）里，或 `definition_hash` 为空，或明细无法解码 | `skipped(factor_missing)` |
| `definition_hash` 与启用时固化的值不同 | `skipped(factor_changed)`，需要重新启用实例 |
| DSL 经 `bars[-1]` 读取了因子列，本实例对恰好上一根没有可信的处理记录 | `skipped(previous_version_unknown)`，这条记录保存本期指纹，下一期即可求值 |
| DSL 经 `bars[-1]` 读取了因子列，可信的上一根记录里这些因子的指纹与本期不同 | `skipped(factor_changed)` |
| 因子本期 `skipped` | `skipped(factor_skipped)` |
| 多市场策略里选币市场或所有市场整体失败（见“一个市场整体失败也算不可用”） | `skipped(market_failed)`，数据类原因，不计实例故障，不属积累中 |
| 因子 `degraded` | 继续；失败标的只对引用该因子的规则算缺数 |

追赶与过期周期的结果归类有所不同：输入就绪时调用同一引擎求值，只有引擎给出 `ok` 决策才保存推进后的状态；守门跳过时只写 `skipped(catchup / expired)`，规则状态不动。追赶期间的就绪失败通常记 `catchup` 并在输入摘要中附上就绪原因，但 `factor_changed` 仍单独记录；首次收到就已过期的周期，就绪失败统一记 `expired`。读取输入或求值产生配置、历史不足、重试耗尽等错误时，仍按相应原因记录，不能只凭 `catchup` / `expired` 或追平状态推断规则状态已推进。

可信的上一根记录：同一实例、同一 View、同一 bar 与日历、`bar_end` 恰好早一根、含经 `bars[-1]` 读取的全部因子的
指纹；不限会话，优先当前会话。首次运行或漏掉相邻周期时，经 `bars[-1]` 读取因子列的实例会先跳过一期；启用或重启本身不强制跳过，只要已有可信的相邻记录就可继续。恢复追赶会补记周期指纹，见第 7 节。`bars[-1]` 只读 K 线列（例如 `bars[-1].close`）的实例没有上一根的版本需要核对，不受影响。

守门：基础集合 U 为空（本期没有任何标的的数据，事件的空名单同样按空处理）整期 `skipped(no_data)`；
规则没有可评估的候选（E(r) 为空或全部年龄剔除）、进入 filter 的可用标的少于 `min_universe` 时
`skipped(universe_too_small)`；任一规则缺数占（预期 − 年龄剔除）的比例超过 `max_missing`
时 `skipped(too_many_missing)`。多市场策略只有一部分市场不可用时缺数检查有两处收窄（永续整体不可用、只剩冻结空头的空头规则不做缺数检查；别的规则持有、因市场不可用冻结的标的不计入缺数），见第 3 节“市场模式”里的“一个市场整体失败也算不可用”。写了 `allow_empty: true` 的规则不参与这些守门。守门跳过时不产生目标，规则状态沿用前序。

`min_age_bars` 应不小于规则引用的因子的回看（因子定义页与 `GetFactor` 的 `lookback_periods`）：因子按严格窗口计算，
新上市标的在回看凑满之前的因子值是 null，`min_age_bars` 更短时这些标的会进入候选、却因因子为 null 被跳过。

**年龄按任务结果 View 的覆盖判断**：因子任务可以先于策略运行积累历史，结果 View 的覆盖起点就是任务开始产出结果的时间（加成员不自动补算历史，需要更早的因子值用补算）。`min_age_bars` 大于结果 View 已有的根数时启用被拒绝，等任务积累够再启用。用到 `bars[-1]` 因子列的规则，第一期没有上一根的处理记录，整期以 `previous_version_unknown` 跳过，第二期起正常。

`min_age_bars` 的判定：以本期为 T，读取 `[T−(N+1), T−(N−1)]` 三根的 `close`，有行即满足。候选全部没有行时，
再确认这三根内整个数据集是否有数据：一行都没有是历史缺口（停机或维护），整期 `skipped(history_insufficient)`，
不会把全部标的当作新上市剔除；规则上期已持有的标的在建仓时已满足要求，不因窗口内的偶然缺数被剔除。回放与实时一致：标的在一次回放中通过年龄判定后保持通过，之后窗口缺口不再把它重新剔除；整窗为空时，只有从未通过的候选才按历史缺口跳过。
只有设置了 `min_age_bars` 的实例每期读取 View 的覆盖统计，且只用 Storage 已缓存的统计、不触发全量统计（未缓存时
由上面的确认查询兜底）；活跃序列的覆盖起点以本期 T 与索引最新一根中较早者为基准计算，索引已经写入更新的 bar
（处理滞后、重投退避）不影响对第 T 根能否追溯 N 根的判断；探针窗口的日历换算失败（例如超出内嵌日历）是确定性的，
记 `skipped(config_error)` 而不是重试。DSL 引用的标签每期核对一次：运行期被删除时整期
`skipped(config_error)` 并标记 `degraded`，不让 `exclude_tags` 悄悄失效或按标签选的池变空。

**监控口径**：因历史不足（`history_insufficient`）或上游因子这期被跳过（`factor_skipped`）而跳过的周期（`market_failed` 不在其中：它是多市场策略的整体失败，持续出现要走数据集新鲜度告警），在“积累期上限”内向 Monitor 报告为 `partial`（数据积累中）：数据集页面显示降级、不告警；模块健康检查记一次成功（模块在正常处理事件，只是无需求值），不计失败。数据重置、新建因子任务后一定会有这一段，数据攒够自动恢复。积累期从实例第一次因这类原因跳过起算，上限是 `min_age_bars` 根 K 线对应的时长与 72 小时的较大者再加一小时，出现一次 ok 就清零重算；超过上限仍然不足说明不是在积累（例如 `min_age_bars` 超过 View 保留的根数），回到原来的失败处理（模块健康失败与数据集告警）。计时只在进程内，重启后重新开始。

组合合成：各规则权重按（标的, 市场）相加（做空为负）→ `max_weight` 按币合计截断，超出部分留现金 → 现货部分超过预算、`gross` 超过
`leverage` 时按比例缩小 → 现金 = 1 − Σw（混合市场改为现货 net、永续 net）；现货出现负权重仍整期 `skipped(config_error)`。选择阶段合法地选出
0 个标的仍是 ok，表示转为现金；守门防止池被意外清空。

**已持有标的的冻结保护**：rank 规则中，上期组合目标非零的标的，若所有相关规则的缺数原因都只是所在市场本期整体不可用（`market_unavailable`，只在多市场策略里出现），或当期完整、仅缺 `bars[-1]` 的值，就进入保持集合 H：不判出场、不重新排名或配权，目标带 `hold=true`，要求 Trade 保持当前数量。hold 规则已持有的标的只检查 filter、hold.exit、scale 与 group.by 引用的列。规则写了 `on_missing` 时，持有标的本根缺数、连续缺数不超过 `keep_bars` 也进入 H（`held(missing_kept)`，合并规则见“规则选项”）。H 在明细中为 `held(prev_hold)`（只缺上一根）、`held(market_hold)`（所在市场本期不可用）或 `held(missing_kept)`，独立于普通 `missing` 计数，但仍计入 `max_missing` 的缺数比例，不能把被保护标的算成可用。

保持目标以其上期权重预留预算（冻结时按标的展开成上期所有非零的（标的, 市场）键；写了规则级市场的规则按键冻结，只保持那个市场的键，见“市场模式”），其余目标的总敞口超过剩余预算时按比例缩小；预算不足时其余目标归零。保持权重只是预算占用，不要求 Trade 按当前权益重新换算数量。

混有其他缺失原因（普通因子失败、K 线失败、无行或无失败证据的当期缺值）的标的不受保护：通过整期守门后，rank 的 buffer 不保留它，hold 规则按 `exit_missing` 出场，holding 批次把它移出、份额留现金。上期持有、本期已不在预期集合中的标的（退市、移出标签）记 `dropped(not_expected)`。

解释明细中每个（规则, 标的）只有一条，`reason` 取值：

| 原因 | 含义 |
| --- | --- |
| `min_age_bars` | 年龄不足（阶段 `aged_out`） |
| `aged_out_max` | 已通过 `max_age_bars` 的判定、不再是新标的（阶段 `aged_out`） |
| `age_markets` | `age_markets: all` 的规则里，标的没在全部绑定市场列出，或某个市场本期整体不可用（阶段 `aged_out`） |
| `scale_invalid` | 仓位系数为 NaN、无穷或求值出错，按缺数处理（阶段 `missing`） |
| `missing_kept` | 写了 `on_missing` 的规则里，持有标的本根缺数、连续缺数没超过 `keep_bars` 而保持数量（阶段 `held`），仍计入缺数比例 |
| `group_full`、`group_none` | 所属组名额已满而跳过；行里的分组值是非数、不属于任何组（分组列为空时按缺数记 `missing:<列>`） |
| `select.then`、`select.then:<原因>` | 第一段选中、二次排序没取到；或二次排序的分数无效 |
| `hold_kept`、`hold_entered`、`hold_not_entered`、`hold_cooling` | hold 规则：继续持有、新入场、`entry` 不成立（或与 `exit` 同时成立）不入场、出场冷却中 |
| `exit_condition`、`exit_max_bars`、`exit_filter`、`exit_missing`、`exit_stop:<原因>` | hold 规则的出场：`exit` 为真、持满 `max_bars`、不再满足 filter、缺数、止损；`exit_missing` 会附上缺数原因，如 `exit_missing;missing:x` |
| `no_row`、`missing:<列>`、`missing:bars[-1].<列>`、`factor_failed:<列>`、`source_failed:<列>` | 缺数（阶段 `missing`）；`factor_failed` 是因子对该标的失败，`source_failed` 是 K 线 View 声明该标的本期失败 |
| `prev_hold` | 已持有标的当期输入齐全、只缺上一根（`bars[-1]`）而保持数量（阶段 `held`），仍计入缺数比例 |
| `market_hold` | 多市场策略里已持有标的因所在市场本期整体不可用保持数量（阶段 `held`），计入缺数比例的口径见“一个市场整体失败也算不可用” |
| `filter` | 未通过 filter |
| `score_invalid`、`score_error:<信息>` | 分数无效或计算出错 |
| `select.where`、`not_selected` | 已打分但未入选 |
| `not_rebalanced` | holding 规则的非建仓 bar 上未被任何批次持有 |
| `filter_after` | 选中后被 filter_after 剔除 |
| `holding`、`holding:<原因>` | 只由延续批次持有；带后缀时表示本期在该阶段被淘汰但仍按批次持有 |
| `not_expected` | 上期持有、本期已不在预期集合 |
| `stop_loss`、`trailing_stop`、`take_profit` | 本期止损止盈失去全部权重（阶段 `stopped`）；可能附上原有原因，如 `stop_loss;missing:x` |
| `…;stopped:<n>` | 仍有权重，但本期有 n 个持仓单位止损（holding 的其他批次还持有） |
| `cooldown` | 止损后冷却中，不能入场（阶段 `dropped`） |
| `market_unavailable:<列>` | 标的所在市场本期整体不可用（那个市场的因子本期被跳过）；可冻结已持仓的标的，计入缺数 |

### 汇合求值（绑定两个因子任务的实例）

现货、永续各有一个因子任务和结果 View，完成时间不同，所以实例等两边都到齐再求值一次：

1. 一个 View 的就绪事件到达，只把原始事件（按字节，`readiness.Check` 要用整条事件）幂等写入 `t_strategy_ready_events` 并确认，不求值。
2. 写入后检查本期所有绑定的 View 是否到齐。到齐就对每个 View 的事件各跑一次就绪判断，再合并结论：配置、契约类原因（`factor_missing`、`factor_changed`、`previous_version_unknown`）整期按该原因处理；数据类原因（某个市场的因子被跳过 `factor_skipped`）只让该市场本期不可用，需要的市场全部不可用时仍按原因整期跳过。基础集合用各 View 事件里的标的名单。同一期已求值的不重复求值。
3. 不加定时器。只在两种情况下把更早还没汇合的期补记为 `skipped(market_missing)`（另一个市场的数据未到）：缺的那个 View 本身已经到了更晚的一期（它跳过了这一期）；更晚的某一期已经汇合完成并求值。补记在提交更晚一期之前完成。两个 View 稳定相差一根以上是正常情况（永续标的多、算得慢），此时不补记；有效期本来就容许两根的延迟。`market_missing` 属于数据未到，不标记实例 `degraded`，不计入模块健康失败。
4. 迟到的那一半事件到达时，那一期如果已补记过，按乱序规则忽略。
5. 触发器的放行检查返回等待（`ModeWait`）时事件返回重投、不确认，到达记录照写；返回 `ModeOff` 时沿用直接确认、不写记录。
6. 结果的输入记录（`c_input_json`）每个 View 一份事件 ID 与因子指纹（`views`），下一期的相邻周期检查按 View 比对。

只绑一个任务的实例到达即算到齐，直接用手上这条事件，不写到达记录，行为与以前逐位一致。

**附加来源的汇合（逐根判断）**：写了 `sources` 的实例也写到达记录，但只在主帧收盘时刻正好也是某个来源收盘时刻的那一根（例如加密 1h 主帧的 00:00、A 股的 15:00）等主帧与该来源都到齐，其余时刻只等主帧（多市场的主帧照上面的规则汇合）。来源事件按来源的日历与周期换算出它的收盘时刻，记在 bar_end 相同的那根主帧上；主帧这一根已经到了时，用主帧的事件重新走一遍处理（这时汇合求值），否则等主帧。来源迟迟不到时不加定时器，按上面第 3 步补记 `skipped(market_missing)`（说明是“附加来源（名）的数据未到”）：下一根非汇合的主帧到达即完整，会先把它补记掉；补记之后才到的来源事件直接确认。参考市场的事件直接确认，不参与汇合。统一数据集（方式 B）只有一个 View，也是到达即求值；它的一份事件按序列拆成各市场的结论，再用同一套合并规则（数据类原因只让对应市场不可用，所有用到的市场都不可用时整期按原因跳过）。

补充说明与已知边界：

- 两个 View 都已记下、只是还没求值的期（例如事件被要求等待期间两期都被记下，放行后先重投了较晚的一期）不是缺数据：处理当期之前先按 bar 顺序把它们求值，不会补记 `market_missing`；补记只针对确实缺一个 View 的期。
- 补记的 `skipped(market_missing)` 记录没有因子指纹（缺的那个 View 没有事件，也没有跑就绪判断），所以下一期若经 `bars[-1]` 读取因子列，相邻周期检查找不到可信记录，会按 `previous_version_unknown` 跳过一期。
- 选币市场整体不可用时（`select` 为单个市场，如 `spot/swap` 的现货因子被跳过）没有候选池，整期按 `factor_skipped` 跳过；只有下单市场不可用时选币照常。
- 暂停（`ModeOff`）期间一个 View 的事件被直接确认、不写记录，另一个 View 若在暂停前已记下，这一期不会再凑齐：它会在更晚的一期到齐后被补记为 `market_missing`，暂停期间的周期按本来的规则不求值。
- 一个 View 长期不再到达（例如那个任务被停掉）时，另一个 View 的每一期都停在“等另一半”，补记只在缺的 View 出现更晚一期或更晚一期汇合时发生，没有定时器，也没有单独上报：靠实例的数据集新鲜度告警发现。
- 组合约束的摘要文本：单市场策略现货超过预算、`gross` 超过 `leverage` 时按比例缩小，摘要里的说明文本是“总敞口 … 超过 portfolio.leverage … 按比例缩小”或“现货部分总权重 … 超过现货预算 …”，与以前的报错文本不同。

## 5. 失败语义

| 情况 | 处理 |
| --- | --- |
| 解码失败、事件契约错误 | TERM |
| Storage / Factor 瞬时错误 | 重投重试；同一事件对同一实例超过 `evaluation.attempt_budget` 次后记 `skipped(infra_retry_exhausted)` 并 ACK。Storage 与 Factor 返回的错误只给中文概述与错误码，服务端原文（可能是英文、带内部细节）只写日志 |
| 终态记录落库失败 | 不 ACK，按投递次数指数退避（2 秒起、最长 30 秒）重投，直到落库成功；消费者逐条拉取，一个 View 的重试不拖住其他 View |
| 结果校验失败或违反表约束（确定性写入错误） | 记一条不带明细的 `skipped(config_error)` 并 ACK，实例标记 `degraded`；兜底的 skipped 也被拒绝时记错误日志、计入模块健康失败后 ACK，不无限重投 |
| EventBus 重启（拉取请求收到 Server Shutdown） | 消费循环退出后自动按退避重建消费者，期间 `/readyz` 不就绪；不需要重启 Strategy |
| 启动时 EventBus 不可用 | 进程照常启动、接口可用，消费者与出站投递在后台按退避重连，连上之前 `/readyz` 不就绪 |
| 目标事件发布得不到确认（EventBus 重启、断网导致确认丢失） | 单次发布最多等 `eventbus.publish_timeout`（默认 10 秒）；一批中遇到第一个发布失败立即断开重连，不再让同一批其余结果逐条等满超时；重连后重发，`result_id` 作为 Msg-Id，重发会被去重。连接、探针与投递异常写日志，同一条连续出现只记一次，恢复后再记一条 |
| 目标事件无法通过契约校验或超过 EventBus 最大消息长度（永久发布错误） | 该结果标为 `cancelled`、不再重试并写日志，不阻塞其后的结果 |
| 发布期间更新的 ok 结果把这一行取消，而事件已经发出 | 仍记为 `sent`，如实反映投递状态；取消计数（`superseded`）只增不减、不回退，这类结果另计 `moox_strategy_target_sent_after_cancel_total`。发出后把这一行记为 `sent` 时数据库出错，这一行可能随后被新结果取消，而事件其实已经发出（至多一次的记账缺口，Trade 以最新目标为准） |
| 周期无法按日历换算（A 股内嵌日历已过期、周期不在交易日或交易时段的桶上） | 写日志并计入模块健康失败后 ACK（同一事件因其他实例需要重投而再次投递时不重复记日志与计数）。周期的有效期要推到其后 2 个交易日，内嵌日历的最后 2 个交易日的周期已推不出有效期，实际可用截止日是“最后一个交易日往前 2 个交易日”：截止日前 30 天起 `/readyz` 给出 `calendar_warning`，过了截止日不就绪，也不能再启用 A 股实例。报错都是中文，带日历的覆盖范围与推进前的那一天。A 股日线的行键必须是日期键（交易日期的 UTC 零点，例如 10-09 的日线是 `2026-10-09T00:00:00Z`，与 `packages/barclock` 的 1d 键、采集写入的行键一致）：不按日期键写行（例如按上海零点，即前一日 16:00 UTC）却声明了 `cn_stock` 的数据集换算失败，不会被静默规整成一直读不到行；日期键只表示日期，`bar_end` 仍是当日上海 15:00 收盘；A 股日内周期的行键是真实的开盘时刻（UTC）。内嵌日历的第一个交易日没有上一根，`bars[-1]` 的值都缺失。二进制内嵌时区数据，主机缺少 tzdata 也能换算 |
| 会话快照（`resolved_json`）损坏 | 退回实例上的同一份副本取日历与周期，跳过记录仍按正确的周期写；两份都无法解析时无从确定周期，只记日志并计入模块健康失败后确认（不写记录、不标记实例；同一事件因其他实例而重投时不重复计数） |
| 事件的 View 不是实例绑定的 View | 不处理：Strategy 只按绑定的 View 找实例，不再按完成来源或事件类型过滤；因子结果 View 的事件带因子明细，K 线 View（含重采样 K 线）的事件没有明细 |
| 提交时发现更新的记录 | 重读后分类：同周期视为重复、更早视为乱序，否则重新求值一次 |
| 首次收到时、求值完成时或提交时已过有效期 | 输入就绪且引擎成功求值时保存推进后的规则状态，记 `skipped(expired)`，不投递目标或下一期参数；未成功求值时不推进状态 |
| 列被删除（含只在 `bars[-1]` 中引用的列与 `min_age_bars` 探针读取的 `close`）、View 被停用或删除、View 周期或数据集变化、同一标的多个序列 | `skipped(config_error / ambiguous_series)`，实例标记 `degraded`，页面提示重新启用 |
| View 活跃序列的覆盖起点晚于 `min_age_bars` 的目标根，或探针窗口内整个数据集都没有数据（已有标的通过探针的缓存时，窗口缺口不再整期跳过） | `skipped(history_insufficient)`，实例标记 `degraded`；不会把全部标的当作新上市剔除 |
| 绑定的因子定义变化 | `skipped(factor_changed)`，实例标记 `degraded`，重新启用后恢复 |

**统一数据集（同一数据集里有现货、永续两条序列，方式 B）。** 策略侧已支持，规则见“市场模式”里的“两种输入方式”：上表的 `ambiguous_series` 在统一数据集上只在同一个市场内判断（现货、永续两条序列并存不是歧义），单市场数据集的行为不变；
因子明细的 `failed_series`、`skipped_series_tags` 拆成各市场的结论（只让对应市场不可用；全部 tag 都跳过才是 `skipped`，部分跳过是 `degraded`）。
永续整体晚到而不是被跳过时（时序因子的所有永续序列都在 `failed_series` 里），按“一个市场整体失败也算不可用”处理，持仓冻结。
已知边界（早已存在）：统一数据集上纯 `swap/swap` 策略（只涉及一个市场），永续标签里有、但因子没有期望永续序列的币（既没有行也不在失败名单里，如刚新上永续标签、`universe_series` 里还没有这条序列），方式 B 把它算缺数、方式 A 的永续数据集里没有它所以不算；`min_age_bars` 为 0、`max_missing` 很紧时，这种币会让方式 B 持续整期 `too_many_missing`。需要时把 `max_missing` 放宽，或等因子的 `universe_series` 补上这条序列。

实例健康只有 `ok` 与 `degraded`：`degraded` 表示最近一期因配置或数据问题跳过，下一个 ok 周期自动恢复（健康标记只作用于仍以同一会话
启用的实例，停用之后并发提交的周期不改它）。

`skipped` 不取消任何待投递目标。普通跳过只推进处理记录，规则状态不动；追赶或过期周期成功求值后的 `skipped(catchup / expired)` 会推进规则状态并保存摘要，目标为空，也不保存逐标的解释明细或下一期因子参数。只有新的 ok 目标才替代旧目标。

**规则状态**：每个实例一行（`t_strategy_states`），记着状态内容、它推进到的那一期（bar_end）、所属会话与 DSL 版本。

- **读写**：每期求值前读这一行作为起点（没有就从零开始）；引擎给出决策后，结果、解释明细与新的状态在同一个事务里写入，状态推进到的那一期记为这条结果的 bar_end。提交失败（比较交换冲突、写入出错、实例已停用）时结果和状态都不写。没有求值的跳过记录（就绪判断没过、读取失败、乱序等）不动这一行；
- **停用再启用**：打开新会话的同一个事务里比较新会话与状态所属会话固化的内容——DSL 版本（`dsl_hash`）、绑定解析（`resolved_json`，含市场模式、因子任务与 View、列绑定、因子成员契约、View 的列清单、附加来源与参考市场）、策略池成员快照——三者逐字节一致就把状态改挂到新会话，内容与它推进到的那一期都不变；任何一项不同就删除，新会话从头开始。所以只改了 DSL 的注释或空白、绑定的因子任务加了列、因子定义改了，都会清空；
- **修改实例**：停用后修改实例（换组合账户、换策略定义，哪怕提交的内容与原来相同）在同一个事务里清空规则状态——状态是按原来的账户与定义积累的理论持仓（批次、止损入场价、冻结时的“保持”目标），不能带到新的账户或定义上；
- **想从头开始**：人工平仓、手工调过仓位之后要让策略从零开始，光停用再启用不够（状态会沿用，启用后第一期会按原来的持有记录把平掉的标的买回来）。管理台不能改实例，清空规则状态用命令行，两条路任选其一，做完再启用：
    - 原样提交一次实例修改（只清这一个实例）：
        1. 停用实例（停用的实例上没有会话，停用之后马上能修改）；
        2. `moox-cli strategy instance show --space-id <空间> --instance-id <ID>`，记下 `strategy_id` 和 `logical_account_id`；
        3. `moox-cli strategy instance update --space-id <空间> --instance-id <ID> --strategy-id <原值> --logical-account-id <原值>`。两条命令的 `--space-id` 默认是 `crypto`，别的空间的实例不写会报“实例不在当前空间”。`--logical-account-id` 是整体替换：漏写等于把实例解绑组合账户、变成观察实例，原来挂了账户的一定要带上；原来就是观察实例（`logical_account_id` 为空）的不写；
    - 改一下 DSL 文本（`strategy update`，加一行注释也行）：共用这个定义的所有实例下次启用都会清空；
- **停用期间漏掉的期**：普通策略不补，与暂停后恢复相同——状态原样接着用，持有根数、冷却、holding 批次都按 bar 序号的差计算，停用的那段算时间流逝；rank 的止损入场价、持有集合保持停用前的值。策略池用历史把漏掉的期补上，见第 3 节“预热”；
- **重复的期**：沿用状态的新会话收到状态已经推进过的期（上一个会话里求值过，例如那一期的就绪事件被重发）时记 `skipped(out_of_order)`，不再求值，状态不重复推进；
- **状态无法解析**：普通策略清掉状态、本期记 `skipped(config_error)`（两者在同一个事务里），下一期从头开始；策略池的状态要靠预热重建，每期记 `config_error`，停用再启用后从头预热。模块重置（`data` 范围）清掉规则状态后同理：普通实例从头开始，策略池实例要停用再启用；
- 回放不读写这张表：回放的规则状态在回放内部逐期传递，从空状态开始。

**持仓冻结**：因子本地数据写入时保证连续，回看窗口里没有空洞，逐币的因子失败（`factor_failed`）不冻结持仓。已持有（上期组合目标非零）的标的，只要在所有引用它的规则里缺失的原因全部是所在市场本期整体不可用（`market_unavailable`，见“一个市场整体失败也算不可用”），或只缺上一根（`bars[-1]`）而当期输入齐全，就**冻结**：不判 exit、不从目标移除、持仓数量保持不动，明细阶段为 `held`（原因 `market_hold` 或 `prev_hold`）；混有其他原因（因子失败、K 线失败、无行、值缺失而没有证据）时完全按缺数处理（从持有里移除）。冻结的标的在组合里预留预算（取上期组合目标权重，写回状态供下一期继续保持），其余标的在剩余预算内按比例缩小（只缩小不放大）；保持目标带 `hold` 标记发给 Trade，Trade 不换算数量也不调仓。冻结的标的仍计入 `max_missing` 的缺数比例。holding 规则里含冻结成员的批次延后重建，保持解除后补建。规则写了 `on_missing` 时，持有标的本根缺数（含仓位系数无效）也按冻结保持（`missing_kept`），连续缺数超过 `keep_bars` 根才按缺数处理，合并规则见“规则选项”。

| `t_strategy_replays`、`t_strategy_replay_bars` | 回放任务（含从实例发起时的来源实例与会话、DSL 版本哈希、按市场保存的因子任务与结果 View、提交时各 View 校验区间所用的活动索引代次、现货与永续两个费率、主帧的因子数据来源 `c_input`（`view` 或 `compute`）与滑点 `c_slippage_bps`）与每期记录（含期末现货市值与永续净名义价值，以及因子现算这一期生效的逐期提交参数 `c_params_json`，View 来源记 `{}`）；任务键含附加来源的 `来源名:市场`；`c_members_json`（策略池回放发起时固化的成员快照，与会话的成员快照同一格式；单策略回放为 NULL，列表不读）与 `c_funding_column`（单策略回放计资金费用的列，空串表示不计）；默认保留 90 天，且每个空间只保留最近 50 个已结束的回放（只在已结束的回放里排名次，排队与运行中的不计入也不删除；每期都记录持仓账本，一个长回放可达数十 MB） |
| `t_strategy_age_passed` | 年龄探针通过的标的（按空间、View、活动索引、年龄根数、市场、标的），通过一次后跨周期、跨重启复用；View 换了活动索引后旧行作废，删除实例时按删掉的任务的结果 View 清理 |

**升级与重建**：Strategy 打开库时逐个比对已有表与索引的定义和当前 schema（表的集合相同、定义逐字等价），有旧表或定义不一致就拒绝启动（报“使用旧 schema”）；当前 schema 新增、库里还没有的表与索引在打开时补建。不写迁移：改了已有表定义的版本要清掉策略库全新建（系统没有上线，按全新部署处理）。批 3 改了会话表（加 `c_started_at`、`c_logical_account_id`）、实例表（健康状态只剩 `ok`、`degraded`）、实例任务表（去掉任务的唯一约束）、回放表与每期记录（`c_input`、`c_slippage_bps`、`c_params_json`），并删了模板表；Trade、Factor 的库同批也改了（见[交易](交易.md)、[因子](因子.md)），三个库一起清空。

已停用的实例可以删除，删除时连同它在本库的全部记录（见第 7 节「删除实例」）；定义只能在没有实例引用时删除；实例在的时候，会话、DSL 版本与结果一直保留，
历史结果的解释始终按当时的 DSL 版本与绑定展示。投递状态只有 `none`（观察实例或 skipped）、
`pending`、`sent`（已被 broker 确认，不代表 Trade 已接受）和 `cancelled`。

## 7. 实例生命周期

> **启用的实例都求值，实盘还是影子看确认列**：实例没有自己的阶段。启用即开始求值。
> - 没有挂账户的观察实例启用时就写入确认时间，它不会真实下单。
> - 挂了账户的实例启用后是试运行：目标带影子标记，Trade 只换算记录、不下单。
> - 用户在管理台实例列表点“确认实盘”，或执行 `moox-cli strategy instance confirm --instance-id <实例> --session-id <会话>`，写入确认时间，下一期起目标是正式目标。
> - 停用再启用回到试运行。
>
> 因子任务能不能计算由因子引擎自己检查（见[因子](因子.md)生命周期一节），与实例互不影响。任务刚建、结果 View 还没有数据时（`min_age_bars` 检查），启用可能因“还没有数据（覆盖范围未知）”被拒绝，等任务算出几个周期后再启用。

> 暂停与恢复追赶：策略模块暂停（手动 / 系统）时所有实例都不求值、不发新目标，持仓不动。恢复先进入**追赶**：追赶期间到达的因子完成事件记录周期与因子指纹；输入就绪且引擎成功求值时，规则状态照样推进（持有集合、holding 批次、hold 的入场序号、止损状态），结果仍为 `skipped(catchup)`，不发目标、不提交下一期因子参数。有效期已过的迟到周期同样尝试推进状态，结果记 `skipped(expired)`；就绪检查、守门或求值失败时不会推进状态，具体分支见第 4 节。引用上一周期因子列的策略仍需要相邻周期指纹。
> 追赶目标取当前时间减去 1 分钟宽限后最近已收盘的 bar，已处理记录达到该目标即判追平，给刚收盘但因子还没送达的周期留出时间。此判定不保证每个历史周期都完成了状态推进。放行时控制器记下放行时间，BarEnd 不晚于它的周期即使放行后才到达，也走追赶分支；重复或乱序周期先按去重与乱序规则处理，不会补发交易目标。
> 状态推进使按时间顺序送达、输入就绪且成功求值的追赶周期能延续理论状态；暂停时已忽略的事件不会自动重放，漏期、跳过或实际未成交也不能据此推断实盘持仓与连续运行一致。
> 单独恢复因子引擎而策略一直在运行时，历史事件若仍在 2 根有效期内，仍可能生成交易目标；过期后只尝试推进状态。需要统一控制放行边界时用 `moox-cli system pause|resume`（先暂停策略）。

- 启用：解析绑定（因子任务 → 结果 View → 数据集 → 源数据集的市场类型 → 列与成员契约）→ 声明了 `factor_params` 的第一次启用时 `BindFactorTask`（其余 `GetFactorTask` 确认任务已启用）→ 编译 →
  核对覆盖 → 挂了组合账户时读一次 Trade 的 `GetLogicalAccount`（只读，`internal/tradeowner`），核对组合由策略控制（人工控制的组合拒绝）、
  策略要输出的每个市场都在组合可交易的市场里 → 一个事务里写会话（带开始时刻 `c_started_at` 与当时绑的组合账户）、挂到实例上并置为启用。
  事务里核对实例仍是停用的、定义当前的 DSL 版本就是会话的版本、登记的因子任务与会话固化的一致：解析期间实例被改定义或定义被修改时整体回滚，
  任何一步失败都不留下会话。启停都在实例当前定义的锁内拿锁后重读，等锁期间实例被改到别的定义时换锁重试。
  市场类型取源数据集属性 `market_type`，没有时取其标的范围标签的属性 `market_type`（支持 `spot`、`swap`、`equity`）；
  A 股（`equity`）按现货处理：现货与 A 股 View 都拒绝 `leverage > 1` 与做空。A 股实例可以绑定 A 股模拟账户（Trade 场所 `ASHARE`，市场 `STOCK`），
  启用前读账户的核对（`internal/tradeowner`）要求组合账户开通了股票市场；实盘的 QMT 执行端还没接入。日历取 View 数据集的属性 `calendar`；数据集没有声明时，只有因子结果
  （`dataset_role=factor_result`，沿用源数据集的行键）继承源数据集的 `calendar`，重采样等按自己的对齐方式写行的派生
  数据集不继承；都没有时为 `crypto_24x7`。`cn_stock` 使用内嵌的 A 股交易日历（`packages/marketcalendar`），支持 1d 与
  barclock 允许的日内周期（能整除两个交易时段，例如 5m；45m、4h 拒绝）：日内周期由 `packages/barclock` 按交易时段切分，不跨午休
  （`input/calendar_session.go`），1d 沿用按交易日推进的实现。A 股数据集必须显式声明 `calendar: cn_stock`（Collector 建的采集结果数据集会自动写上），
  否则会按 7×24 计算周期；按 UTC 零点对齐（`alignment=epoch_utc`）的数据集不能使用 `cn_stock`。数据集保留期换算根数时，
  A 股按每年 244 个交易日 × 每个交易日的根数折算（5m 每天 48 根）。设置了 `min_age_bars` 时，View 必须提供 `close` 列，N 不超过
  View 每个序列保留的根数，且以最新一根为 T、T − (N−1) 根不早于活跃序列的覆盖起点；覆盖范围未知（索引还没有
  任何行）时拒绝启用。A 股日线实例不论是否设置 `min_age_bars`，启用时都读取覆盖统计并检查最晚一行的行键是 UTC
  零点（日期键）：不按日期键写行的数据集在启用时就被拒绝，而不是启用后每一期都读不到行。没有 `min_age_bars` 时只校验行键
  （覆盖范围不影响实时求值），新建的 View 只有未来行或当天一行也能启用。覆盖范围只在需要时向 DataView 读取该 View 活动索引的统计（`min_data_time` / `max_data_time`，两端包含，是真实存在的行键，
  View 进程至多每 5 分钟刷新一次；启用与回放要求精确统计，未缓存时现算）；索引的最早时间可能来自已停更的
  序列、只会提前不会推后，因此活跃序列的覆盖起点取它与“最新一根往前 `retained_rows_per_series`−1 根”中较晚者。
  `retained_rows_per_series` 是活动索引建立时记录的保留根数与当前配置中较小的一个（调大配置要等索引重建后才变大），
  为 0 表示未知，此时不做依赖它的检查。
  标的只按显式声明的 `series_tag` 属性过滤序列，没有声明时不过滤。DSL 引用的标签必须存在，固定写出的
  标的（`pool` 列表、`include`、`exclude`）必须在 View 的数据集中有绑定。绑定账户时，同一空间里该账户已被
  另一个启用实例持有则在解析、联系 Trade 之前拒绝（唯一索引兜底）。这是“账户归哪个实例”的唯一判断：Trade 不存归属，
  管理台建实例时账户选项的置灰、交易账户详情页与列表的“关联策略”都读 Strategy 的实例列表：置灰只看绑了这个账户的启用实例；
  “关联策略”取绑了这个账户的启用实例，没有启用的就退回显示最近创建的那个停用实例（同一账户可能留着几个停用的旧实例，见[前端](前端.md)）。
- 重复启用不新建会话，也不联系 Trade。新会话的 DSL 版本与绑定解析和规则状态所属的会话一致时沿用规则状态，否则从零开始。
  停用的实例上没有会话（`c_session_id` 只在启用时非空），停用之后马上能修改、删除，没有“启用或停用尚未完成”的中间状态。
- 停用：一个事务里置为停用、关闭会话、清掉实例上的会话；提交之后调一次 Trade 的 `CloseTargetSession`（组合、实例、会话、会话开始时刻），
  组合账户取会话里记的那个，不受之后改账户影响；会话没挂账户（观察实例）时不调。Trade 把组合的“关闭到”推进到这个会话的开始时刻，
  这个会话与更早会话的目标从此都按 `superseded` 结束；当前这份目标的有效期缩到“现在”（最早 `bar_end_time` 加 1 毫秒），由 Trade 的过期路径撤掉它的挂单（见[交易](交易.md)第 3 节）。
  停用不会清仓，持仓保留。
- 不做后台重试。Trade 没确认（不可达、超时、内部错误）时接口返回错误、实例已经停用，页面弹出“实例已停用，但 Trade 未确认”。
  对已停用的实例再停用一次（运行实例列表“更多”与实例详情里的“再次停用”，或 `moox-cli strategy instance disable`）会按它最近一次挂过账户的会话
  （最近一次会话没挂账户、更早一次挂过时取更早的那次）、会话里记的账户再调一次 `CloseTargetSession`，幂等；Trade 回答账户不存在（例如 Trade 重置过）视为已关闭。
  没调成功期间，Trade 最多把最后一份目标执行到它原本的有效期结束（2 根 bar，日线策略是 2 天）。**要立刻停手，在 Trade 暂停这个组合账户**
  （暂停后执行器撤掉目标挂单）；组合的控制模式创建后不能改，不能靠改成人工控制来停。
- 重新启用不被没确认的关闭挡住：新会话的开始时刻更晚，Trade 按会话先后用新会话的目标覆盖旧会话的，旧挂单由执行器收敛的第 1 阶段撤掉。
- 有两种情况这次关闭送不到 Trade，也没有自动补发，旧目标会执行到它的有效期结束（已知情况，不为它加状态）：
  - Strategy 进程恰好在“停用落库”与“调 Trade”之间重启：再点一次停用可以补上；
  - 停用时没调成功，随后把实例改到新账户并重新启用：最近一次挂账户的会话已经是新账户的，旧账户那次关闭没有入口，要补就在 Trade 暂停旧组合。
  另外，模块重置 `all` 清掉实例与会话时同样不通知 Trade，最后一份目标执行到有效期结束。
- 已知差别：启停的路由超时是 5 秒（服务目录里 `StrategyMgr` 的默认值，只有删除实例单独放到 30 秒），停用里调 Trade 最多 3 秒。
  启停、修改与删除都在同一定义的锁里排队，同一定义下另一个实例正在启停或删除时，停用要先等锁，等锁加调 Trade 超过 5 秒就由网关先超时。
  超时的响应里没有实例，页面分不出“已停用、Trade 未确认”，只弹一条普通的错误提示并重新读取实例状态，不弹“Trade 未确认”的对话框；
  服务端仍在按自己的 30 秒期限排队，停用可能稍后才落库。看重新读到的状态：已停用的再点一次“再次停用”补发关闭（幂等），仍在启用的再点停用。不为这种情况加状态或调大超时。

**删除实例**（`DeleteStrategyInstance`，CLI `strategy instance delete --instance-id <实例>`，管理台运行实例列表的“删除”）：

- 只能删已停用的实例；挂着组合账户也能删，账户绑定随实例一起清掉。实例不存在返回成功。
- 全程持有实例锁（锁的是整个策略定义），并发的启用被挡住。不加状态列，靠每一步幂等支持重试。
- 逐个读实例登记的因子任务（`GetFactorTask`）按关联分组：只有关联到本实例（`bound_instance_id` 等于实例 ID，只有声明了 `factor_params` 的实例会关联）的任务随实例删除；
  没关联或关联到别的实例的任务（不调参的实例引用的任务、来源任务、默认的公共任务）保留不动，只去掉本实例的引用；Factor 里已经没有的跳过。从没启用过、启用到一半的实例也能删。
  要删的任务必须与实例在同一个空间。
  要删的任务还被别的实例引用时**拒绝删除**，提示“先删除引用它的实例 X、Y”：不做“保留任务、只去掉引用”，因为留下的任务仍关联着已删的实例、关联又不能改，Factor 的普通删除拒绝关联过的任务，它就再也删不掉了。
- 所有拒绝都在删第一个任务之前做完：
  - 要删的任务还被别的实例引用（见上）。
  - 有回放在排队或执行、会读到这个实例的数据时拒绝，先取消回放：从实例发起的回放，以及本空间里按定义或 DSL 发起、读取要删的任务的回放。
  - 对每个要删的任务先调一次 `DeleteBoundTask(check_only)`：Factor 做完动手前的全部检查（关联的实例、没有补算在排队或执行、结果数据集没有被默认 View 之外的 View 引用），不做修改。被拒绝时按原类别透传（参数错误）。
  - 用 archive-mgr 的 `ListArchiveTasks` 分页拉回空间内全部归档任务，在本地按要删任务的结果数据集筛选；有归档任务就拒绝，列出归档任务（按 `空间/数据集` 标识），先到归档页删掉。读不到归档任务也拒绝。没有要删的任务时不查归档。
  - 挂过组合账户的实例，对它最近一次挂过账户的会话（最近一次会话没挂账户、更早一次挂过时取更早的那次）再调一次 Trade 的 `CloseTargetSession`（幂等，账户取会话里记的那个）：会话行随实例删掉之后，停用时没确认的关闭就再也没有重试入口了。Trade 没确认就拒绝删除，提示稍后重试；从没挂过账户的实例不联系 Trade。不为“Trade 是否已确认”加状态列。
- 逐个调用 Factor 的 `DeleteBoundTask` 删除任务、成员与结果数据集（结果数据不可恢复）。
- 最后在一个事务里删除实例在策略库的全部记录：会话、结果与解释明细、汇合到达记录、回放与回放明细、外显设置、因子任务登记和实例本身；`t_strategy_age_passed` 按删掉的任务的结果 View 删除，保留的任务不动。
- Trade 里的订单留着；影子目标和目标回执由 Trade 在有效期截止 7 天后定时清理，不随实例删除。
- 失败的响应带 `incomplete`：为真表示已经开始删（之后的失败），再删一次即可接着做完，CLI 和管理台提示“删除未完成，请稍后重试”；为假表示什么都还没删，原样提示。
  没拿到响应（超时、连接中断）按删除未完成处理。调用 Factor、archive-mgr 的截止时间比请求提前 5 秒，给最后那个事务留时间。
- 任务删完、实例记录还没删时失败，实例保持停用。停用实例上只要有引用的任务已不存在（删除没做完，或任务被另外删掉，两者不区分），列表与详情就用 `missing_factor_tasks` 标出，
  `setup verify` 在说明里标出，提示“引用的因子任务已不存在，删除实例即可清理”；启用会在写会话之前报同一句。
- 清空大数据集期间同一定义下的其他实例不能启停；删除的路由超时是 30 秒。

### 7.1 运行状态与试运行

> 状态：已实现（设计 3.8）。生命周期只有模块级的运行、暂停、恢复追赶，实例没有自己的阶段。

- **运行中的模块对每个启用实例求值**。实盘还是影子看实例的确认列：
  - 挂了账户、还没确认实盘的实例是**试运行**：目标事件带 `shadow=true`。Trade 对影子目标只把权重换算成数量并记录（`t_shadow_targets`），不预留资金、不下单。
  - 在管理台“确认实盘”之前，先列出这个实例最近的影子目标，也可以用 `moox-cli trade shadow list --instance-id <实例>`（TradeConsoleService `ListShadowTargets`）查看。
  - 确认用 `moox-cli strategy instance confirm --instance-id <实例> --session-id <会话>`（StrategyMgr `ConfirmStrategyInstance`）。不给 `--session-id` 时预览里显示实例当前的会话号，执行时只确认这次启用。
  - 确认之后的目标是正式目标。
  - 实例的 `degraded` 等非 `ok` 健康状态不挡求值，避免“不求值就无法靠成功求值恢复”的循环。按跳过原因修复数据或配置；因子定义变化需要重新启用以更新绑定指纹。
- **暂停 = 不求值、不发新目标、持仓不动**，不能用空目标表示暂停（Trade 把空的 FULL 目标解释为清仓）。
  - 暂停期间到达的事件不留周期记录。
  - 恢复先进入追赶，期间以 `skipped(catchup)` 留下周期与指纹，输入就绪且成功求值时同时推进状态。
  - 每个启用、有会话的实例都处理到最新已收盘的 bar，才算模块追平；策略池预热失败的实例不参与。
  - 放行时间是模块级的，系统恢复由编排器 `release` 时同样记下。放行后只有晚于放行时间且未过期的周期才可能发出目标，更早的周期仍走追赶分支。
  - 正常周期仅在相邻版本证据确实缺失时才记 `previous_version_unknown`。
- **模块自检没通过不算暂停**。自检三项：数据库 Ping、出站 EventBus 已连、就绪事件消费者已连。
  - 刚启动、重启后出站 EventBus 还在连接、运行中连接断开，都属于这种情况。
  - 到达的就绪事件不确认、不留记录，按退避（2 秒起，最长 30 秒）重投，下一期因子参数也暂停提交。
  - 自检通过后照常求值，这段时间里的周期不会丢；超过有效期才处理的周期照常记 `skipped(expired)`。
  - 启动后自检没通过时每秒检查一次（最多 1 分钟），通过就放行，之后每 30 秒一次。
  - 模块暂停时按暂停处理，不让事件重投。
- **策略池实例预热期间**同样返回等待（放在暂停与追赶判断之前），确认实盘被拒绝，细节见第 3 节“策略池”。
- 模块状态持久化在数据库旁的 `lifecycle.json`。接口是 StrategyMgr 的 `GetLifecycle`、`ControlLifecycle`（读给管理台与 moox-cli，写只给 moox-cli），模块状态随指标上报带给 Monitor（首页的系统状态读它）。

## 8. Strategy 到 Trade 的契约

事件 `event.trade.target.weight_requested`（Stream `MOOX_TRADE`）是组合账户的完整目标快照：

```text
target_id = result_id
instance_id、session_id、strategy_id、logical_account_id
session_started_at（会话开始时刻，毫秒，取自会话行的 c_started_at）
bar_end_time、valid_until（= bar_end_time 之后 2 根 bar）
shadow（试运行为 true）
targets[] { instrument_id, market_type（SPOT | SWAP | STOCK）, target_weight, hold }
```

同一个 `instrument_id` 可以以 SPOT、SWAP 各出现一次（现货与永续各自独立、不互相抵消），Trade 按 `market_type` 规范化标的 ID。策略启用时要求策略要输出的每个市场都在组合账户可交易的市场里（启用成员已开通市场的并集），组合还没有启用的成员时提示“组合账户还没有启用的成员”。

`target_weight` 是相对组合账户总权益的带符号权重；遗漏的旧（标的, 市场）目标为 0，空列表表示全部归零。`hold=true` 明确要求保持该标的当前持仓数量，权重只保留策略预算占用，Trade 不为它读取参考价或换算数量。
Trade 校验有效期与控制模式，按 `session_started_at` 比较会话先后（已关闭的会话、比当前目标更早的会话的目标都不接受），
同一会话按 `bar_end_time` 只接受更新的目标，再独立完成数量换算、账户选择、精度和风控，规则见[交易](交易.md)第 3 节。
Trade 不存实例与组合账户的归属，也没有认领、释放的调用：Strategy 对 Trade 只有两个调用，启用前读 `GetLogicalAccount`、停用后调 `CloseTargetSession`。
停用后最后一份目标的挂单由 Trade 执行器的过期路径撤掉，连续撤不下来超过 10 分钟 Trade 记关注项 `release_orders_stuck`（见[交易](交易.md)第 2 节）。

## 10. 回放

> 当前 View 研究回放的账本只接收目标权重，没有传递引擎的 `hold` 标记：当期价格可用但因冻结保护应保持数量时，账本仍可能按原权重再平衡。它的“缺价冻结”仅由价格缺失触发，与实时 `hold=true` 不是同一机制；涉及该分支的回放不能作为实时保持数量行为的等价验证。实现位置：`internal/replay/runner.go` 的 `Ledger.Step` 调用与 `internal/ledger/ledger.go` 的 `Step`。

回放是研究工具，用来比较策略版本，不承诺复现历史上的实时结果。主帧（绑定的因子任务）的因子数据有两种来源，由 `StartReplay` 的 `input` 选定：
`view`（默认）读因子任务结果 View 的历史行；`compute`（因子现算）经主机网关调因子引擎，按因子机本地 K 线与回放中的参数现算，见下方“因子现算”。
附加来源与参考市场两种来源都读 View。下面除“因子现算”一条外说的都是 View 来源，执行器、求值、账本与报告两种来源共用：

- 入参：定义、DSL 文本（可回放未保存的草稿）或实例（三选一；实例用其当前会话、停用时最近一次会话固化的 DSL，
  回放记录同时保存来源实例与会话；重新启用实例会按定义的当前版本重新解析）、`[start, end)`（UTC，先截到
  毫秒）、`factor_tasks`（市场 → 因子任务，混合市场给 spot 与 swap 两个，统一数据集上的任务给 `multi` 一个，登记的市场要与任务的源数据集一致，多个 View 的周期与日历必须一致）、
  现货与永续各一个单边手续费 `spot_fee_bps`、`swap_fee_bps`（0～1000 bps，股票按现货费率），可选的滑点 `slippage_bps`（0～200 bps，默认 0，现货、永续相同，见下方理论账本；上限比手续费紧，是因为（手续费率 + 滑点率）× 杠杆接近 1 时目标金额的迭代不收敛、成交后权益几乎归零），可选的资金费列 `funding_column`（例如 `funding_rate`：
  永续持仓按这一列结算资金费，口径与策略池的 `fees.funding_column` 相同；必须是列名，策略要涉及永续；永续的 View 没有这一列时拒绝（只绑一个 View 时提交即检查，现货、永续两个 View 时执行时检查）；
  策略池的回放任务写了它即拒绝，资金费写在池 DSL 的 `strategy_pool.fees.funding_column`）。A 股日内 View 的 bar_start 是真实的开盘时刻，与 crypto 一样按 UTC 区间回放；A 股日线 View 按上海日期回放：两端各取所在的上海日期零点，含起始日期、不含
  结束日期（页面按上海时区选日期，区间两端是上海零点；日线的 bar_start 是交易日期 D 的 UTC 零点、即上海 D 日 08:00，落在区间内当且仅当 起始日期 ≤ D < 结束日期），记录保存换算后的
  区间（记录同时保存日历，页面按上海日期显示区间，报错里的时间也写上海日期）。支持现货、永续、混合市场与 A 股；
  写了附加来源（`sources`）的策略在回放里为每个来源另加一组读取器，按 as-of 把来源列合进每一期的输入（与实时同一套 `ClosedPeriod` 换算，每段向前多取一根来源 bar；来源不截断区间，回放过程中来源 View 换代直接失败、请重新发起），`factor_tasks` 里按 `来源名:市场` 给出；参考市场只读年龄判定的历史，参与 `age_markets: all`。
  声明了 `factor_params` 的策略只能用“因子现算”来源（View 来源提交即拒绝）；用了 `params()`、但没有声明 `factor_params` 的策略照常回放：回放读主帧 View 的 `__params` 列，
  `params()` 取到 View 里记的这一期实际参数，与实时一致（批 3 之前回放不读这一列、取到 NaN，这类策略的回放结果因此变化）；没用 `params()` 的策略不读这一列。
  策略池的回放见第 3 节“策略池”的“研究回放”。绑定两个 View 时逐个校验：起点要在每个 View 的可用范围内，终点取各 View
  中最早的，各 View 的索引换代各自跟随、各自复查剩余区间。提交时同步完成：View 覆盖范围未知时拒绝，覆盖整体超出内嵌日历、行都落在非交易日上或 A 股日线行键不是
  UTC 零点（数据集没有按日期键写行）时说明具体原因；起点不早于活跃序列的覆盖起点（见第 7 节）加上 `min_age_bars` 与 `bars[-1]` 所需的历史（否则给出
  可用起点），因此不会出现早期区间只剩已停更序列的情况；终点截到最新一根之前（最新一根可能还没写完，覆盖统计
  也可能滞后几分钟）；根数不超过 20000；返回实际回放的根数与首末根，并固化当时的因子定义指纹（没有引用因子时
  固化空集合）以及校验区间所用的活动索引代次。代次取自 DataView 的 `GetViewState`，由索引 ID、变更日志的 `store_id` 与建成那一刻的序号
  （`generation`）组成，只做相等比较：索引 ID 对一个 View 是固定的，View 被 `repair-view` 或断档重建原地重建索引时建成序号变，
  存储重建时 `store_id` 变，两种情况都算换代。`index_id` 为空（还没建好，或断档、原地重建中）时代次为空；`GetViewState` 返回
  `VIEW_NOT_FOUND`（storage-view 还没登记这个 View，例如刚重启）时同样当作还没建好，View 是否被删除以 Metadata 的 `GetView` 为准。
  同一代索引的行只会被定时删除最旧数据删掉：执行时代次没变就按精确统计复查起点；代次变了（排队期间重建过索引，新一代只保留最近的根数）才按新索引的精确统计复查起点并截断终点，
  越界时提示重建并要求重新发起，新索引的统计暂时未知时同样拒绝执行。每段读取完成后都确认代次没变；发现换了一代时，按新索引复查从当前分段起的剩余区间，通过才让行与年龄判定的读取器一起
  切换过去重读这一段，并按新索引截短终点（指标里说明截到哪一根），否则以“在回放过程中重建了索引”失败、说明剩余
  区间从哪一根起不再被覆盖，不会静默改读新索引、把丢掉的较早 bar 记成缺数据。每段读完的代次复核只读代次（不读
  列），传输失败单独重试。一次回放最多跟随 3 次换代（整个回放累计），每次跟随后立即把累计次数写进指标的局限说明，
  回放失败或取消时保存的部分指标也带着它；排队期间或回放过程中换代截短了终点时，说明写明最后一根 K 线结束于哪一刻
  （同一件事只保留最新一条）。复查时读取覆盖统计又遇到索引变化，稍等后按最新的 View 重读，最多 3 次；复查里读取覆盖统计与读取 View 遇到
  传输失败时同样按 1、2、3 倍基础间隔退避重试（最多 3 次，与分段读取一致），复查的每次退避之前与之后都确认回放没有被取消。View 被删除时
  失败原因是“View 已不存在，回放无法继续”。执行时不再做启用级
  的覆盖校验。指纹在排队期间变化（包括新引用或不再引用的因子）则拒绝执行。提交时回放的每一根之前所需的历史
  （`min_age_bars`、`bars[-1]`，连同本根在内的根数）不少于 View 每个序列保留的根数时直接拒绝（回放只到最新一根之前，
  永远没有可回放的 bar）；覆盖太短时先反向判断历史够不够，说明历史不足，不会被误报成日历需要更新。A 股日线的覆盖边界按交易日规整
  （最早一根取不早于它的交易日、最晚一根取不晚于它的交易日并夹到内嵌日历之内），回放区间枚举到内嵌日历的最后一个
  交易日为止；索引里晚于当前已闭合最后一根的行（误写的未来数据）不算覆盖，最晚一根夹到当前已闭合的最后一根，
  全部行都在未来时说明疑似误写（行在未来的交易日上与行在非交易日上是两种不同的说明）；日历之内的未来行被夹掉后，每个序列
  保留起点仍按已闭合的最后一根估算、可能偏早，多出来的 bar 回放时按 `no_data` 记录（只影响异常数据）；索引里有超出内嵌日历的数据、并且当前时间已过日历末日的收盘时，末日那一根已经写完，提交时也能回放到它。
  这时真正的最新一根在日历之外，估算每个序列保留的起点时先扣掉日历之外至多的根数（每个自然日至多一根），扣完一根
  都不剩时说明数据已超出日历、暂不能回放。每个空间同时排队
  与运行的回放不超过 20 个，排队已满时在解析绑定、读取覆盖统计之前就拒绝。
- 回放只有一个执行器（`internal/replay` 的 `Runner`），主帧的输入来源是 `barSource` 接口：每次给出一段连续 bar 的行与年龄判定的依据，按市场分，
  另给出每一根因子实际生效的逐期提交参数。View 来源（`viewSource`，`internal/replay/source.go`）：一个或两个主帧 View、统一数据集的一个 View、附加来源与参考市场的读取器、
  索引换代跟随与修订号重读都在它里面；因子现算来源是 `computeSource`（`internal/replay/compute.go`）。主循环、求值与账本不关心来源。策略池回放的每个成员各有一个 View 来源，换代由整个池一起跟随。
- **因子现算**（`input=compute`）：主帧不读 View。
  - 提交：声明了 `factor_params` 的策略必须用它；不支持策略池、绑了两个主帧任务的实例（方式 A；统一数据集是一个任务，可以）与股票市场（引擎回放的计算核心没有核对过交易日历与午休），
    都在提交时拒绝。不查主帧 View 的覆盖范围，只把终点截到最近一根已收盘的 bar 之前（它可能还没同步到因子机本地），根数上限仍是 20000；回放记录照常登记各任务键的 View 代次（附加来源与参考市场执行时仍读 View）。
    按“数据集标的数 × 市场数 × 引用的列数 × 每个值约 48 字节”（每行除了本期的值还带上一期的同名列）估算一期的大小，超过 3 MiB 时提交即拒绝、提示减少引用的列（服务的包体上限是默认的 4 MiB，不为回放调大）。
  - 通道：策略经同一个网关客户端调因子引擎的 `trpc.moox.factor.EngineControl`（因子机只出站，经控制机网关的反向中转），寻址、签名与中转由客户端按服务目录完成。
    单次超时取目录的路由超时：`OpenReplay` 10 分钟，其余 2 分钟；不套 `factor.timeout`（5 秒）。网关转发失败（引擎没起、因子机断开、超时）时回放失败，原因是“因子引擎不在线”；
    `StepReplay` 返回会话不存在（`NOT_FOUND`，引擎重启过）时回放失败，原因是“因子引擎重启，回放会话已失效，请重新发起”，都不静默重试。
  - 执行：开始时 `OpenReplay(replay_id, 任务, 区间, 列)` 建会话，可回放的各期以引擎返回的 `period_times` 为准（不按 View 的覆盖复查或截短）；请求的列与 View 来源读主帧的列相同
    （`close`、当期列、`bars[-1]` 列，用到 `params()` 时加 `__params`，计资金费时加资金费列）；`extra_periods` 只传引用上一根的深度（0 或 1）：年龄由引擎按本地数据里序列的第一根算，与快照长度无关。
    引擎目录里任务成员的定义与发起时固化的指纹不一致时拒绝执行；多数标的的本地数据晚于预热起点时引擎拒绝建会话，策略侧不提供放行短预热的选项，先回补或导入因子机本地的历史再发起。之后按期 `StepReplay`：不调参时每步期数按“标的数 × 列数 × 48 字节”控制在 3 MiB 以内、至少 1 期、不超过 `replay.chunk_bars`；
    单步响应放不下时引擎只返回前几期，策略按 `period_times` 的下标从下一期接着请求，不请求本段之外的期。结束（含失败、取消）时 `CloseReplay`，关不上只记日志，由引擎 6 小时闲置清理；
    `OpenReplay` 转发失败时结果未知（引擎可能已登记会话），同样尽力关一次。Strategy 重启时先读出运行中的因子现算回放、逐个 `CloseReplay`（失败只记日志），再把它们标成 `failed(interrupted)`。
    取消在 `OpenReplay` 期间不生效，要等它返回（最长 10 分钟）之后才停下。
  - 标的全集：引擎的候选只取源数据集当前在册（active）的标的，名单里消失的标的（不论何时下架，包括回放区间之后才下架的）不是候选、整段不参与，
    也不计入引擎返回的排除名单；候选里本地数据不覆盖回放最后一期的再被排除。所以截面因子按较小的全集算，存活标的的截面因子值也会变，结果有幸存者偏差。
  - 行与年龄：引擎按（标的, series_tag）出行，与 View 来源一样整理（统一数据集按 series_tag 分市场，同一标的同一根多个序列按歧义处理）。`bars[-1]` 读上一段最后一期的行，第一段用引擎给的上一期同名列补出。
    年龄判定用引擎给的根数（这条序列截至本根的本地根数不少于 N 即通过），通过后整次回放内不再剔除；本根没有行、此前也没通过的标的不通过。
    本地的填充行（同步补上的缺失周期，OHLC 取上一根收盘、成交量为 0）与实时一样不算本期有行：引擎不出行、也不算本期可用，策略按缺价处理。
  - 调参：声明了 `factor_params` 时每步一根；这一根 `ok` 时在同一帧上 `EvaluateParams` 求出下一期参数（整型取整、限幅，说明写进这一期摘要的 notes），作为下一步请求的参数；
    没求出（跳过、或所有标的上都没有有效值）时下一步不带参数，引擎沿用上一期生效的，第一期按成员自己的参数；引擎拒绝的参数丢弃、沿用上一期，拒绝的成员与原因写进这一期摘要的 notes 并记日志。
    每期记录的 `params_json`（表列 `c_params_json`）是引擎返回的本期生效的逐期提交参数（成员键 → 参数名 → `{default, overrides}`），`{}` 表示按成员自己的参数；View 来源的记录总是 `{}`。
  - 局限说明另写一条“因子现算”：因子按本地 K 线与回放参数重新计算、年龄按本地根数、附加来源与参考市场仍读 View，以及“数据集登记 X 个标的，参与 Y 个”（差额是不在册与本地数据不覆盖的标的，见上方“标的全集”）与预热不足的标的数。
  - 耗时（估计值，待全新部署后实测）：每步一次经中转的调用加一次计算，按 0.1～0.3 秒算。声明了 `factor_params` 的策略一期一步，2 万根约 0.5～1.5 小时；
    不调参的策略 500 个标的 10 列每步约 13 期，2 万根约 1500 步、3～8 分钟；A 股 5000 个标的 10 列每步 1 期（股票现在不能用这种来源，只作量级参考）。
- 进程内单工作协程，同一时刻只跑一个回放；按 `replay.chunk_bars` 分段、`replay.page_size` 分页读取，分段读取
  遇到传输失败时退避重读最多 3 次。活跃 View 每个写入批次都会改变索引修订号，跨页读取常与写入冲突：代次没变、
  只是修订号变化时按指数退避（250 毫秒起、翻倍到 4 秒，再加 ±50% 抖动，单次最长约 6 秒）重读，一段最多重试
  1 分钟，仍不一致才以“读取期间持续有新的写入，请稍后重试”失败。每次退避之前与之后都确认回放没有被取消，取消后不再继续读
  Storage；确认时读取回放状态失败按错误处理（与逐期检查一致，数据库异常时不会在退避里空等）。进程重启时遗留的 `running` 任务标记为 `failed(interrupted)`，已写入的周期
  保留，可重新发起。
- 每期的基础集合 U 取该期有行的标的（数据集的全部标的绑定，含已停用的），再按规则得到 E / G / A / M，
  与实时共用同一个引擎；规则状态在内存中跨期传递，从空状态开始。整根 bar 没有任何行时记
  `skipped(no_data)`：持仓只估值、不清算，规则状态保留（回放与实时的已知差别见下方“回放与实时的已知差别”）。年龄判定每段只读取所需的 `close` 窗口，
  内存不随 `min_age_bars` 或回放长度增长；窗口内整个数据集都没有数据时记 `skipped(history_insufficient)`。
  与实时一致，只有策略涉及的标的（∪E(r)，年龄剔除之前）同一周期出现多个序列才整期 `skipped(ambiguous_series)`，
  用到 `bars[-1]` 时上一根的歧义同样跳过；无关标的的歧义不影响本期，歧义标的的价格一律不用于估值。判定顺序与
  实时一致：当期歧义 → 年龄判定 → 上一根歧义。A 股日线年龄窗口里落在非交易日的行（例如节假日误写的一行）跳过，
  不让整个回放失败。
- 理论账本：持仓键是（标的，市场），同一个币的现货与永续是两个持仓、不互相抵消。价格表按（标的，市场）取各 View 的原始
  行（不受选币池去重影响，另一个市场的持仓也要估值）。按当期 `close` 估值，无价的持仓冻结并按最后价估值；目标金额按总权益
  `W = 现金 + 现货持仓市值（含冻结）` 迭代扣费后计算，现货、永续各用各的费率。现货数量不为负，按现金成交：先卖现货，
  再调永续，最后买现货，买入受现金约束、不足时按比例缩减并记"目标未达成"（同时给出缩减比例，现金为 0 时为 0）。
  永续可以做空，不占用现金：每期有价时把 数量 × (收盘价 − 上期价) 结算进现金，成交只改数量并扣手续费，所以永续盈利可以用来买现货，
  亏损会减少现金（现金可以为负，此时现货买入缩减为 0，现货随目标按缩小后的权益被卖出补回）；没有价格的永续持仓冻结、不结算。
  **默认不计资金费，不模拟强平与保证金率**，页面与指标的局限里都写明；写了 `funding_column` 时每根先按上一根估值后、调仓前的永续名义价值乘本根费率结算资金费（见第 3 节“策略池”的“资金费”），局限说明改写为按哪一列结算。
  账本每根分两步：估值（`Mark`：价差结算、缺价计数、资金费、爆仓判定）与调仓（`Rebalance`：清算、扣费、卖现货、调永续、买现货），skipped 期只估值。**权益不超过 0 即模拟爆仓**：持仓期间权益降到不超过 0 的那一期记入
  指标的 `bankrupt_at` 与局限说明，可成交的持仓（现货与永续）全部平掉，此后各期忽略目标、空仓直到结束，权益保持不变（否则“目标权重 × 负权益”
  会把多头算成空头，账户靠反向持仓“复活”）；该期结果摘要的 ledger 里带 `bankrupt`。每期记录期末现货类持仓市值之和与永续持仓的净名义价值
  （多头为正、空头为负）。年龄判定（`min_age_bars`）按市场各自的历史，多个市场时年龄没通过的市场不用它的行；不超过 1e-9 × 权益的金额视为浮点残差，不交易也
  不算未达成。手续费只按实际成交额。写了 `slippage_bps` 时成交价在收盘价上按方向加减这个比例（买入上浮、卖出下浮，永续开空、减多算卖出）：
  成交数量仍按收盘价的名义金额算、持仓仍按收盘价估值，滑点按成交的名义金额乘比例从现金里扣，与按成交价成交在现金上等价；手续费按收盘价的名义金额计
  （与按成交价计差一个二阶小量）；目标金额的迭代与现货买入的现金约束都带上滑点，缺价清算与爆仓后的平仓同样计滑点。每期摘要的 ledger 里带本期的滑点成本
  `slippage`，局限说明写明滑点；逐期的手续费列与指标的总手续费都不含滑点成本，滑点只体现在权益里；策略池的成员账本不计滑点（滑点只在回放任务的账本上，池回放的池级账本计）。滑点为 0 时结果与不带滑点完全相同。skipped 期不成交、不清算；持有标的连续缺价达到
  `replay.missing_price_liquidate_bars` 期后，在 ok 期按最后价清算。
- 报告给出累计收益、年化、最大回撤、平均单边换手（成交额 / 2 / 成交前权益；与实时的 Σ|Δw|/2 同为单边口径，
  但回放按实际成交计算，包含价格漂移后的再平衡，持仓不变时实时为 0、回放可能大于 0）、

### 回放与实时的已知差别

研究回放只有历史行，没有实时的就绪信息（事件名单、失败名单、市场是否整体可用），下面几处结论可能和逐期实时求值不同；这些差别对两种输入来源都适用（因子现算同样只给行，不接因子状态做就绪判断），场景里写了“因子现算”的几行是它特有的。处理原则：不为了对齐回放增加状态或特殊分支，在这里逐条写明，等回放能拿到历史的就绪信息时统一处理（后续单独立项）。

| 场景 | 回放 | 实时 | 处理 |
| --- | --- | --- | --- |
| 成交价 | 按当期收盘价加滑点（`slippage_bps`，默认 0）成交，手续费按收盘价的成交额计 | 按下单时的市价成交 | 已知差别；滑点只是一个固定比例，不模拟盘口冲击 |
| 持有标的某一根整行缺失（同市场其他标的有行） | 基础集合只取本根有行的标的，它不在预期集合里，按 `dropped(not_expected)` 出场；`on_missing` 与 hold 的缺数口径在这种情况下不起作用 | 事件名单里仍有它，按缺数处理：没写 `on_missing` 时同样出场（原因是 `missing:…` 或 hold 的 `exit_missing`），写了 `on_missing` 时冻结保持（`missing_kept`）；计入缺数占比，`max_missing` 较小时可能整期 `skipped(too_many_missing)` | 已知差别，继承自 main；行还在、只是列为空时两边一致 |
| 双市场单边断档（一个市场整根没有行，另一个市场有行） | 断档市场的持仓没有行、也没有失败证据，按缺数处理（多头移出，永续空头按“永续已下架”平掉），缺数占比超过 `max_missing` 时整期 `skipped(too_many_missing)` | 断档市场的事件名单仍是预期全集、全部标为失败，判为整体不可用：持仓按 `market_hold` 冻结，空头规则守门豁免 | 已知差别，继承自 main |
| 整根断档（选币市场都没有行） | `skipped(no_data)`，持仓只估值、规则状态保留 | 取决于就绪结论：可能 `skipped(market_failed)`、`factor_skipped` 等，持仓同样不动 | 持仓结论一致，跳过原因可能不同；继承自 main |
| 已停用的标的绑定 | 数据集的全部标的绑定（含已停用）都算“列出”，参与 `age_markets: all` 与 `max_age_bars` 的判断 | 只算活跃标的 | 已知差别；`all` 规则在已下架标的上两边可能不一致 |
| 某个市场本期整体不可用时的年龄判定 | 不模拟不可用，照常按年龄判定 | 写了 `max_age_bars` 或 `age_markets: all` 的规则保守剔除这个市场列出的标的（记 `aged_out_max` 或 `age_markets`） | 已知差别；只影响写了规则级年龄字段的规则 |
| 规则级市场的规则没持有的币，在规则所在市场本根没有行 | 没有失败证据，收窄出这条规则的预期集合，不计缺数 | 失败名单里有它时留在预期集合，记缺数并计入 `max_missing` 守门 | 已知差别，与第一行同源（回放没有失败名单） |
| 主帧很快、来源很慢（例如 5m 主帧配 1d 来源），日线比对齐后的一根主帧还晚就绪 | 来源行在就照常读，不出现这个现象 | 对齐的那一根补记 `market_missing`，之后几根读到的仍是上一根日线（或刚写入的新行）；写了 `allow_empty` 但没写 `on_missing` 的规则可能在这几根因来源缺数清仓、之后再买回 | 已知差别；这类规则建议配 `on_missing: {keep_bars: N}` |
| 来源里同一标的同一根有多个序列 | 只把这个标的的来源行当缺数 | 整期 `skipped(ambiguous_series)` | 已知差别 |
| 回放的因子定义与历史覆盖核对 | `factorDrift` 只核对主帧的因子定义，不核对来源的；也不检查来源在回放起点之前有没有历史（没有时来源列按缺数处理） | 启用时核对来源的成员契约，汇合 bar 上核对指纹 | 已知差别 |
| 参考市场“列出的标的” | 参考数据集的全部标的绑定（含已停用） | 参考数据集的活跃标的 | 已知差别，与“已停用的标的绑定”一行同源 |
| 统一数据集上的来源（`来源名:multi`），一个市场的来源因子被跳过 | 照常读行 | 这个来源本期整体不读，现货、永续两个市场的来源列都按缺数处理 | 已知差别；实时偏保守 |
| 汇合 bar 上附加来源的因子被整体跳过、或来源事件迟迟不到 | 没有就绪信息，照常读来源那一根的行（行在就用） | 因子被跳过时这一根不读来源、来源列按缺数处理；来源超期时这一根补记 `skipped(market_missing)` | 已知差别，与第一行同源（回放没有就绪信息） |
| 规则级市场所在的市场本期整体不可用 | 不模拟不可用：该市场有行的标的照常求值，整根没有行时规则的持仓按缺数处理（没有证据记 `no_row`） | 规则不守门，持有的键按 `market_hold` 冻结、不新开仓；有年龄要求时，该市场的标的按年龄剔除记 | 已知差别，与上面两行同源（回放不模拟“市场整体不可用”） |
| 非 drift 策略池回放的起点 | 从回放区间的第一根起，成员规则状态、净值序列、步长的上期比例都从空开始 | 从预热起点（启用时刻往前若干期）推进而来 | 已知差别：前几期的轮动、择时与步长结果不同，窗口装满后才可比；要逐期对上实时，用写了 `allocation.start` 的 drift 池，回放起点取 `start` |
| drift 池没写 `allocation.start`、`initial` | 漂移起点与 periodic 的默认锚点都是回放区间的第一根 | 漂移起点与默认锚点都是预热起点 | 已知差别：分配系数按路径逐根累积，不会随窗口装满收敛，两边始终不可比（写 `sides.*.anchor` 只能对齐 periodic 的相位）；要逐期比对就写 `start`，回放起点取它 |
| drift 池写了 `allocation.initial` | 回放起点必须是 `initial.at`，成员从这一根才开始求值，规则状态与净值从空开始 | 预热从 `at` 往前多推成员所需的期数，成员状态是重建出来的 | 已知差别（设计 P8 只保证比例一致）：只有 `at` 那一根的分配系数一致，之后成员目标与漂移可能不同 |
| 策略池回放的成员版本 | 从定义或 DSL 草稿发起时取成员的当前定义；“按此配置重新发起”只复用池 DSL 文本，成员按当前定义重新解析，不复用原回放的成员快照 | 用启用时固化在会话里的成员快照 | 已知差别：要回放实例在跑的版本，从池实例发起 |
| 策略池回放读取期间 View 换了索引 | 由后面的成员发现换代时，同一段里先读完的成员（以及估值用的价格）沿用旧索引读到的行，之后各段都读新索引 | 无此情形 | 小差别：新一代索引从同一份 Primary 重建、本段区间已按新索引复查，行的值相同 |
| 策略池成员本期的就绪判断 | 没有就绪信息：成员按本根的行照常求值，只有求值被跳过才算没通过 | 成员的因子被跳过、缺数等先在就绪判断里判为没通过，沿用上期目标 | 已知差别，与第一行同源（回放没有就绪信息） |
| 策略池的最新一根 | 和单策略回放一样不含最新一根 | 预热包含最新已收盘的一根 | 差一根，不影响逐期比对 |
| 股票池回放的池级账本 | 池级账本与单策略回放相同，连续缺价 `replay.missing_price_liquidate_bars` 期后清算 | 实盘没有池级账本；成员账本停牌不清算 | 已知差别，与下一行同源 |
| A 股的成交时点 | 日内最后一根（15:00）与日线得到的目标按当根收盘价成交，隔夜跳空不计 | 下一个交易日开盘才执行 | 已知差别：结果偏乐观，这类策略的回放收益不能直接当作实盘预期 |
| 因子现算的因子值 | 按回放中的参数、因子机本地 K 线重新算 | View 里记的是当时按实时参数算出的值 | 已知差别：两者不一定相同；要复现已发生的历史用 View 来源或补算 |
| 因子现算的年龄 | 按因子机本地数据里序列的根数 | 按 View 的历史 | 已知差别；本地数据比 View 短或长时结论不同 |
| 因子现算的附加来源与参考市场 | 仍读 View，区间与历史受它们的 View 限制 | 读 View | 两边一致；只有主帧换成现算 |
| 因子现算的标的全集 | 只取源数据集当前在册、且本地数据覆盖到回放最后一期的标的；已下架的（不论何时下架）整段不参与，截面因子按较小的全集算，存活标的的截面因子值也会变；登记数与参与数写进局限说明 | 下架前照常参与，截面按当时的全集 | 已知差别（幸存者偏差）；要包含下架标的用 View 来源 |
| 因子现算：一条序列在快照里停更到末尾 | 分不出它是已下架还是暂时没更新，从它最后一根之后的那一期起按不存在处理，不进这一期的序列全集；不允许部分全集（`allow_partial_universe: false`）的截面因子在其余序列上照常排序 | 标的还在册时完成事件的序列全集里仍有它，记为失败的序列；不允许部分全集的截面因子跳过整个分组（这个 `series_tag` 这一期） | 已知差别：回放少跳过这些期，截面按较小的全集算；多见于终点贴近当前时间、这条序列在因子机本地同步落后时，把终点往前挪几根或等同步追上 |
| 因子现算：本地填充行所在的那一期 | 填充行（同步补上的缺失周期，OHLC 取上一根收盘、成交量为 0）不算本期有行，这条序列这一期不可用；不允许部分全集的截面因子这一期整个分组为空 | 按当时的完成事件判断：完成事件也把这条序列标为失败时同样跳过整个分组 | 已知差别：只有实时的完成事件也把这条序列标为失败时两边才一致 |
| 因子现算期间取消 | `OpenReplay` 建会话期间（读整段本地快照，最长 10 分钟）取消不生效，要等它返回才停下 | 无此情形 | 小差别，不另加机制 |
| 因子现算的因子状态 | 引擎给的成员状态（部分失败、截面跳过）不参与判断，只看行 | 就绪判断按因子状态跳过或记失败 | 已知差别，与第一行同源 |
| 股票市场与因子现算 | 股票市场不能用因子现算，A 股上声明了 `factor_params` 的策略不能回放 | 照常运行 | 已知差别：引擎回放没有核对交易日历与午休，先不放开 |
| 股票策略持有的标的停牌（连续缺价） | 单策略研究回放的账本连续缺价 `replay.missing_price_liquidate_bars`（默认 3）期后在 ok 期按最后价清算，复牌后策略仍要它时再买回 | 同一策略作为股票池成员时，成员账本按最后价格保持持仓、不清算（设计 S8 只改成员账本） | 已知差别；同一股票策略单独回放与作池成员时，在停牌标的上的净值与手续费不同，单策略回放的结果只用于研究比较 |

## 11. 监控

- 每个启用实例登记为 Monitor 的期望数据集（`moox_strategy_dataset_*`，数据集标识
  `strategy_<instance_id>`）：ok 计为成功并推进输出水位，skipped 计为未完成。停掉上游或连续跳过时，现有的数据集
  新鲜度检查会告警。期望间隔：crypto 是 bar 时长；A 股相邻 bar 之间可能隔着午休、隔夜、周末与长假，按交易日历推进折算，取“最近处理的
  一根到其后第 2 根”的间隔的一半与“最近一个 ok 的一根到其后第 3 根”的间隔的三分之一中较大者（分别对应 Monitor 的
  run_missed_intervals=2 与 success_missed_intervals=3），不因休市误报 run stale，周末后第一根跳过也不会立即报 success
  stale（还没处理过时以最近闭合一根的上一根为基准）。两个基准在进程重启或重新启用后从结果库里取（最近处理的一根、
  最近一个 ok 的一根），不会退回 24 小时。Monitor 按交易日历判断应收的最新一根是否按时到达（允许迟到见监控模块文档），
  周末、长假不会被算成落后。两个系数（2、3）写在观察器里（`bootstrap/observer.go`），与 `config/setup/dataset-health-policy.yaml`
  的默认值一致并有测试绑定；线上调整 Monitor 的 `run_missed_intervals` 或 `success_missed_intervals` 时必须同步修改，
  否则 A 股实例周末会误报。实例 ID 区分大小写，数据集标识只接受小写：含大写、非法字符或过长的 ID 用它的哈希，
  只差大小写的实例（Abc 与 abc）不会映射到同一个标识。
- 模块健康检查 `strategy-targets` 只在 ok 时记成功，在读取重试耗尽、配置错误、历史覆盖不足、同一标的
  多个序列、因子定义变化时记失败；第 4 节规定的积累期 `history_insufficient` / `factor_skipped` 例外按成功处理。
- `moox_strategy_period_total{instance_id,result,reason}` 按实例累计处理的周期；`moox_strategy_target_cancelled_total{reason}`
  按原因累计被取消的目标（`superseded` 被更新的结果替代、`expired` 投递前已过期、`inactive` 投递前实例已停用或换了
  会话、`rejected` 无法通过契约校验），四个原因预先登记；其中发布期间被取消、随后确认已发出的另计于
  `moox_strategy_target_sent_after_cancel_total`，两者相减才是没有送到 Trade 的目标数。这些计数只供本机采集
  （`/metrics`），不上报 Monitor。参数送达滞后由 `moox_strategy_param_delivery_stale{space_id,instance_id}` 告警（连续 `params.stale_alert_periods` 期没送达为 1，Monitor 的 `factor_params` 检查读它，见因子文档第 11 节）。
- **暂停等目标发完**：系统暂停先暂停策略，策略的暂停要等正在求值的那一期结束、并且 outbox 里已经落库的目标都发布到 EventBus 才算停下（`Quiesce`）；
  等不到会返回“已暂停，但在途操作没有结束”，系统暂停编排器在这一步拦住，不再暂停 Trade 和更上游，等目标发完后重新执行即可。
- `/readyz` 在数据库不可用、EventBus 未连接、事件消费者未就绪，或投递停滞（`outbox_stalled`：最老的待投递结果超过
  5 分钟仍未发出，或发布持续失败超过 5 分钟——新结果会替代、过期取消旧的待投递结果，1m 等短 bar 的实例最老一条的
  年龄不会超过一根 bar，只能看发布本身失败了多久，见 `outbox_publish_failing_seconds`）时不就绪，Monitor 据此告警。
  有启用实例使用 A 股日历时，内嵌日历的可用截止日前 30 天起在 `calendar_warning` 给出提醒，过了截止日不就绪。
  事件消费者处理一条事件期间按 AckWait 的三分之一向 broker 报告进行中，实例多或依赖慢时不会被判超时重投。事件消费者的连接被永久关闭（例如连续鉴权失败）时丢弃它重新
  拨号，不需要重启进程。

database: ./data/strategy.sqlite
trade:
  timeout: 3s
instance_id: strategy-1

  key_file: ../../secrets/caller-strategy.key

evaluation:
  attempt_budget: 5

  result_items_days: 90
  replays_days: 90
  replays_max: 50             # 每个空间保留的最近已结束回放数

  chunk_bars: 50
  page_size: 2000

- `strategy` 只允许调用 `GetLogicalAccount`、`CloseTargetSession`，
  下单与资金管理仍由控制台身份访问。
- 签名复用 `gateway_client` 的 Admin 分配 KeyID 与部署密钥文件；空间标识经原生元数据传递。
- 删除专用 URL、目标节点、CA 字段及环境覆盖；业务超时保留，写调用单发，传输失败保留结果未知语义。
- 进程负责客户端的统一关闭，账户适配器不再创建连接或读取签名凭据。

## 13. Storage/Factor 网关接线与构建

Strategy 的输入读取、回放与事件执行器共用一个进程级 `gatewayclient`，覆盖 Factor 的 `GetFactor`、`GetFactorTask`、`ListFactorTasks`、`BindFactorTask`、`DeleteBoundTask`、`SubmitFactorParams`，因子引擎 EngineControl 的 `OpenReplay`、`StepReplay`、`CloseReplay`（因子现算，适配器在 `internal/input/engine.go`），Trade 的 `GetLogicalAccount`、`CloseTargetSession`（`internal/tradeowner`），archive-mgr 的 `ListArchiveTasks`（删除实例前用，适配器在 `internal/archivetasks`），以及
Storage Metadata 的七个读方法（`GetView`、`ListViewColumns`、`GetDataset`、`GetTag`、`ListDatasetSubjects`、
`ListSubjects`、`ListTagMembers`）与 DataView 的 `QueryTimeSeriesRows`、`GetViewState`，适配器在 `internal/input/gateway.go`。`gateway_client` 显式配置 caller `strategy`、
Admin 分配的 KeyID 和签名密钥文件；主机地址与 MooX 私有 CA 由同级 hostgateway 配置提供，
目录缓存位于数据库父目录的 `gatewayclient/directory.json`，权限为 0600。只读刷新重试、签名和超时由共享层处理。

原 `factor.target`、`factor.target_node`、`storage.target`、`storage.target_node` 已删除，旧网关地址环境覆盖不再参与选路；
`factor.timeout` 与 `storage.timeout` 保留为经网关调用的单次超时。
Storage 没有调用方密钥，只靠服务端口只监听本机加网关访问控制；`factor`、`storage` 两段只剩 `timeout`，写了 `app_id`、`app_key`、`view_app_key` 会被拒绝。
配置拒绝未知字段、重复键和额外 YAML 文档。离线读取不打开私密文件，进程启动则要求完整部署身份和两类角色凭据，
并创建真实的事件消费者；关闭时等待事件 runner 与后台循环（参数提交、回放执行、保留清理、生命周期）退出，再释放共享客户端与数据库。

Strategy 服务和 CLI 均在本机关闭 CGO 编译或交叉编译，Linux amd64 静态程序和相关测试包已通过运行验证。
Trade 已使用同一客户端；原生 control 部署已分发 Strategy 签名身份和 Storage primary/view 凭据。

表结构与旧版本不兼容时不迁移：停止 Strategy、删除 `data/strategy.sqlite`（含 `-wal`、`-shm`），启动后自动建表；
旧库会被拒绝启动并提示人工处理（见第 6 节“升级与重建”）。

周期标记的 `definition_hash` 是必填字段。升级 Factor 与 Storage 时先停 Factor 引擎，等 storage-primary 的完成事件转发（跟随变更日志）、
View 的跟随进度与 ViewDataReady 消费积压都追平后再替换二进制，最后启动新 Factor 引擎；仍然无法通过契约校验的
完成标记会被 Storage 跳过（记错误日志），不会堵住其后的事件。本版本还要求 Storage 在 DataView 查询响应里
返回 `retained_rows_per_series`，策略据此计算活跃序列的覆盖起点；索引没有记录时为 0（未知），只能按索引统计的最早时间判断。
View 跟随变更日志时直接发布 ViewDataReady，发布失败就停在这条完成标记上退避重试、不往后应用行（见[存储](存储.md) 6.3）；
就绪事件发不出去在 Monitor 上表现为 View 跟随落后（`moox_storage_view_follow_lag_seconds`）和下游策略实例的运行滞后。
策略经 DataView 的 `GetViewState` 读取 View 的活动索引与代次，不再从 Metadata 的 View 记录读取。

本地校验 DSL：

```bash
moox-strategy-cli validate strategy.yaml
```

## 附：可导入的 MA 因子

仓库里的 `examples/factors/timeseries.yaml` 收录了 `ma`（算术移动平均，窗口 `window` 可调），可以直接导入因子库：

```bash
moox-factor-mgr-cli import --file examples/factors/timeseries.yaml --factor-id ma
```

在因子任务里加一个固定成员 `ma`（默认参数，列名 `ma`），或者一个可变成员 `ma__var`（由策略逐期提交窗口）。策略不用声明因子，规则直接写列名，
择时规则可以写成 `bars[-1].close <= bars[-1].ma && bars[0].close > bars[0].ma`；用可变成员时：

```yaml
factor_params:
  ma__var:
    window: "20"
```

声明进指纹、取值不进：策略调整 `window` 不会让实例 `skipped(factor_changed)`，修改因子定义的参数声明（范围）才会，需要重新启用。
