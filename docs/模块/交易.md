# 交易（Trade）

Trade 是 MooX 的交易执行与交易事实来源：管理执行账户和组合账户，接收 Strategy 的目标权重，
换算成具体数量并通过交易所下单收敛，记录订单、成交和持仓，并提供人工干预和模拟盘。

代码位置：`modules/trade`。`moox.toml.example` 将 Trade 放在海外机（`overseas`）；装在哪台主机由 `[deployments]` 决定。

## 1. 进程与端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| `TradeConsoleService` | tRPC `11200` | 账户、模拟盘、组合账户、人工订单、查询与执行能力 |
| 健康检查 | `11210` | `/healthz`、`/readyz`、`/metrics`；只听 127.0.0.1、不验签 |
| `equity` 定时器 | 每 20 秒 | 记录账户与组合账户权益曲线；每分钟一个点，不清理历史点。`QueryEquityCurve` 起止为 0 时默认最近 30 天，跨度超过 2 天按 15 分钟、超过 30 天按小时取每桶最后一点（首尾点保留），最多返回 3000 点 |
| `metrics` 定时器 | 每 30 秒 | 上报指标 |
| 历史订单清理 | 每小时 | 启动时一次，之后每小时一次，不受暂停影响。删掉结束超过保留天数的订单和它们的成交，保留天数是各模拟账户自己的配置（`order_retention_days`，默认 5 天，0 表示不清理，见第 2 节），每轮按账户分别算边界；开了永续的账户边界再收紧到最近一次模拟资金费结算所在整点的前一小时（资金费补算要从那里读成交倒推持仓，订单结束时间不早于它的成交，按结束时间删就删不到这段；补算最多回看 7 天，资金费长期结算失败时边界最多停在 7 天前）。订单与成交在同一个事务里一起删，删之前把这批成交的手续费、已实现盈亏和笔数按（执行账户，整点，组合，手续费资产，结算资产）十进制累加进 `t_order_fill_hourly_summaries`，收益拆解照样算得到；每批 300 单（本地 30 万单的库上平均约 27ms）、批间让出连接。**所有模拟账户都清理**（现货、股票、合约一样）：受管判断、持仓均价和取不到价时的最近成交价读标的汇总 `t_account_instrument_summaries`（见第 4 节受管资产），不依赖成交历史。实盘账户不清理：订单与成交是账务记录，而且实盘成交按交易所成交号去重，删了会在成交游标回退时被重新入账 |

Trade 是单进程、单 SQLite（`data/moox_trade.db`）的设计：用 SQLite 事务、账户锁、组合账户锁、
幂等 ID、交易所查询恢复和定期同步覆盖个人量化需要的一致性，不引入分布式事务或任务框架。
启动时只校验已有表结构与 `schema/*.sql` 一致，不做迁移。

库上开两个句柄（`internal/infra/store/store.go`）：一条读写连接，交易执行和写接口的读写都走它；同一个库文件上另开 4 条只读连接（`query_only`，busy_timeout 同读写连接），
`Store.ReadOnly()` 返回走这些连接的只读视图，Store 的读方法经它调用就读只读连接。管理台的查询接口在处理函数开头取只读视图，整个请求的库读取都经它：
组合详情页每 5 秒轮询的 `GetLogicalAccount`（含成员、可交易市场、就绪原因）、`GetLogicalAccountTarget`、`ListTradingAccounts`、`ListPositions`、`ListHoldings`
（持币查询 `HoldingQuery` 构造时就拿只读视图），列表页的 `ListLogicalAccounts`、`QueryEquityCurve`、`ListBlockedInstruments`，订单、成交列表（含开头查账户、组合是否存在和标的换算），
操作进度跟踪轮询的 `GetOperatorAction`、`GetOrder`，人工操作记录，收益拆解（成交汇总、模拟盘资金费汇总），资金流水（模拟盘的成交与资金费、本地划转记录）。
WAL 模式下读不挡写，页面开着时这些查询不和每分钟的目标执行排同一个读写连接。只读视图看得到所有已提交的数据，看不到还没提交的事务，
所以交易执行路径（目标执行、保证金率风控、模拟盘估值等）即使调同一类查询也仍走读写连接；写接口（下单、撤单、暂停、恢复、清仓、改设置、同步等）写完读回返回结果也走读写连接。
经只读视图写库会被 SQLite 拒绝（attempt to write a readonly database）；只读视图和读写连接共用标的、账户身份缓存，账户锁、组合锁则是另一套，不能经它加锁。
不在页面轮询里的 `GetTradingAccount`、`GetExecutionCapabilities`、`ListTradableInstruments`、`ListInstrumentHolders` 仍走读写连接。
内存库（`:memory:`）每个连接是独立的库，只读视图就是读写连接本身。

成交表 `t_order_fills.c_logical_account_id` 是成交所属订单的组合账户（订单不属于任何组合时为空），写入成交时从订单带过来；
启用成员时外部单被补上组合编号，它已有的成交在同一个事务里一起补上，成交的组合编号始终跟随订单。
按组合查成交（`ListFills`）、汇总收益（`SummarizeAccountPnl`）直接按这一列取，走 `idx_order_fills_logical_time` 按成交时间倒序分页，
已移出的成员的历史成交仍算在组合下。

```text
目标权重事件 / 人工操作 RPC
          │
LogicalAccount ─ TargetExecutor ─ OrderService
          │
     ExchangeSession（Binance、OKX、Paper；A 股、港股只有 Paper）
          │
SQLite：账户、组合账户、目标、人工操作、合约、订单、成交、持仓、权益
```

## 2. 核心对象

| 对象 | 含义 |
| --- | --- |
| TradingAccount（执行账户） | 一个实际交易账户，配置为实盘（Live）或模拟盘（Paper） |
| LogicalAccount（组合账户） | 一个或多个同质执行账户组成的策略资金单元，由一个策略实例的当前会话控制 |
| LogicalAccountTarget | 组合账户当前唯一、可替换的完整目标 |
| TargetHistory | 目标历史（`t_logical_account_target_history`）：正式目标首次接受时写下的换算快照（权益、报价、实际成员和换算出的数量），与影子目标同表、用 `c_shadow` 区分；写入后不再修改，有效期截止 7 天后清理 |
| Order / Fill / Position | 订单意图、交易所成交事实、已确认持仓；目标子单记下所属的策略实例（`instance_id`），其他订单为空 |
| OperatorAction | 人工下单、撤单、逐账户清仓的幂等操作记录 |

- 一个执行账户最多属于一个组合账户（停用的成员也算）；组合账户的成员必须是相同的模拟/实盘模式、
  相同的环境（生产或测试网，模拟盘按生产算）和相同的结算资产，开通的市场可以不同（组合可交易的市场是启用成员已开通市场的并集），可以来自不同交易所，也可以是同一交易所的不同密钥（主账户、子账户）。
- 同一交易所账户不能录入两次：两个会话看到同一批订单，会互相当成外部订单。一把密钥（交易所、环境、密钥）只能有一个启用的实盘执行账户，不管开通的市场是否相同。
- 模拟盘也支持组合：创建模拟账户时可以不填组合账户名称，之后再加入成员；关闭模拟账户时移出成员，组合账户保持暂停。
- 模拟账户配置（`PaperConfig`，表 `t_paper_account_configs`）：初始资金、挂单/吃单费率、滑点创建后不能改；订单保留天数 `order_retention_days`
  创建时可填（不传取 5，0 表示不清理，1～365 天），之后用 `UpdateTradingAccount` 的同名字段随时改（这是模拟账户创建后唯一能改的配置，改它不重建会话），
  实盘账户传了返回参数错误。所有模拟账户都按这个字段清理，见第 1 节“历史订单清理”。
- 名称在空间内唯一（执行账户、组合账户各自唯一），已关闭的模拟账户也占用名称；重名时返回 `INVALID_PARAM`“名称已被使用”，其它唯一约束冲突返回 `CONFLICT` 和固定文案，不带数据库原文。
- 停用成员（或以停用状态加入）与移出成员同一口径：只看挂单、持仓和受管资产，没被 MooX 交易过的余额和卖不掉的零头不挡；凭证失效或没有会话时只看本地记录，成功时在返回的 `msg` 里提示交易所侧没有核对。账户还没同步完成时返回“执行账户还没同步完成，稍后再试”。
- 启用成员时，把这个账户还没结束、也没有组合编号的订单（加入前就挂着的外部单）归到本组合，这样组合里能看到、能撤。
- 移出成员先同步账户；凭证失效或没有会话（同步永远不会成功）时只看本地记录：本地没有挂单、持仓和受管资产就移出并提示交易所侧没有核对；
  本地还有的返回“有持仓不能移出”（`INVALID_PARAM`），同步失败的原因用中文摘要附在后面（没有会话、凭证失效、交易所错误类别和错误码，不带交易所原文），不返回“会话还没启动，请稍后重试”（那样重试多少次都不会成功）。
- 实例与组合账户的归属只记在 Strategy，Trade 不存归属，也没有认领、释放的调用：Strategy 启用挂了组合账户的实例前只读一次 `GetLogicalAccount`
  核对控制模式与市场，停用后调一次 `CloseTargetSession`（见第 3 节）。目标接收与下单前的检查只看会话先后和组合的当前目标行（规则见第 3 节）。
  策略实例重新启用会产生新会话，新会话的目标按开始时刻直接覆盖旧会话的目标行，旧目标留下的单由新目标的第 1 阶段撤掉：上一份目标、上一个实例留下的目标单
  都按第 1 阶段撤（其中结果未知的旧单批量解析，每笔在未知窗口内最多查两次），不当冲突暂停组合（只有别的组合的目标单、或同一目标号却不是本实例下的才暂停）。
- 没有新目标接替时（停用后关闭会话缩短了有效期，或策略不再发目标），最后一份目标的单由执行器的过期路径撤掉：待提交的丢弃；结果未知的不分限价 GTC、市价、IOC
  都先解析一次（逐笔解析、不限次数），退回待提交的丢弃；挂单撤掉；撤单中的等它自己结束；撤完之后每个撤过单的账户同步一次（不是每笔都同步）。
  限价 GTC 单没撤下来（撤单失败或结果解析不出来；市价、IOC 解析不出来不挡）时目标保持原状，每 5 秒重试，撤下来之后才置为过期。
  同一份过期目标的挂单连续撤不下来超过 10 分钟记关注项 `release_orders_stuck`，之后每次重试都刷新，撤下来即消除。
  已知差别：计时只在内存里，重启后从头算；这份目标被新会话的目标取代后过期路径不再重试（旧单交给新目标的第 1 阶段），关注项不再刷新，约 5 分钟后消失；
  凭证失效或执行账户处于异常（`ERROR`）状态、会话建不起来时撤单不会成功，过期路径不按本地记录放行，一直重试并报 `release_orders_stuck`。
  要恢复凭证，或让执行账户的会话建起来，由账户同步确认撤单结果后关注项才会消失；到交易所手工撤单只能防止成交，本地订单仍是挂单，关注项不会因此消失；
  交易所确认标的已不存在的单，账户同步会把它按过期结束（关注项 `orders_instrument_gone`），结束之后就不再挡住过期路径。
- 订单归属由服务端写入：`TARGET`（属于当前目标）、`OPERATOR`（属于一次人工操作）、
  `EXTERNAL`（账户同步发现、非 MooX 创建）。

## 3. 目标权重的接收

Strategy 发布的 `event.trade.target.weight_requested`（Stream `MOOX_TRADE`，durable
`trade_target_weight_v1`）是组合账户的完整快照，字段见[策略](策略.md)第 8 节。

- `target_weight` 是相对组合账户权益的带符号权重；遗漏的旧标的目标为 0，空列表表示全部归零。
- `hold=true` 的目标项表示保持该标的当前持仓数量：不读取它的参考价、不按权重换算数量，执行器不为它提交新的调仓订单。权重只供策略预留预算；全为保持项的快照可直接生成保持快照，无需估值。
- 按会话先后接受目标：事件带 `session_started_at`（会话开始时刻，毫秒，Strategy 全库严格递增），组合上记着“关闭到哪个会话为止”
  （`c_closed_through`），目标行记着所属会话的开始时刻（`c_session_started_at`）。正式目标在估值和下单之前依次判断：
  1. 已过期 → 按过期终止（最先判断：停用再启用后，旧会话还在路上的目标多半已经过期）；
  2. 组合是人工控制 → 按授权冲突（`authorization_conflict`）告警；
  3. `session_started_at` 不大于 `c_closed_through` → 会话已关闭，按被取代（`superseded`）终止、不告警；
  4. 与当前目标行比较（没有目标行则直接接受）：开始时刻更晚是新会话，直接覆盖目标行（不比 `bar_end_time`，旧挂单由执行器收敛的第 1 阶段撤）；
     相等且是同一个会话，按 `bar_end_time` 只接受更新的；更早的按被取代终止；相等但会话不同（不应出现）按授权冲突告警。
  会话先后的判断（第 3、4 步）在历史查重之前：关闭之后同一份目标的重复投递也按被取代终止；同一会话 `bar_end_time` 的先后在历史查重之后，
  被同会话更晚一根取代之后重投旧目标靠目标历史确认。通过入口检查后在等组合锁期间会话被关闭、来了别的会话的目标或改成人工控制的，落库时（组合锁和事务里）按同样的规则分类。
  影子目标只做第 1～3 步，通过后照常记进影子目标表，不与正式目标行比较，也不改它。
  尚未生效（早于 `bar_end_time` 送到）的目标照常接收，保持 PENDING 到生效时刻才执行。相同 `target_id` 和内容的重投幂等，同一会话按 `bar_end_time`
  保留最新快照。
- 关闭会话（`CloseTargetSession`，Strategy 停用实例后调用，幂等）：在组合锁内把 `c_closed_through` 推进到请求的 `session_started_at`（只增不减）；
  当前目标行属于开始时刻不大于它的会话、并且还没过期时，把有效期改成“现在”与 `bar_end_time` 加 1 毫秒中较大的一个（不能早于 `bar_end_time`，
  否则违反表约束、执行器也会当成无效目标绕开过期路径），目标行不删；提交之后唤醒一次这个组合的执行器（已收敛、已阻塞的目标不被定时扫描，
  不唤醒就要等按旧有效期算好的定时器）。之后由执行器的过期路径撤掉这份目标的挂单并把它置为过期，撤不下来由这条路径每 5 秒重试，连续超过 10 分钟记关注项 `release_orders_stuck`（见第 2 节）；关闭本身不撤单。
- 下单前的会话检查（执行器下单与提交前、目标单落库、下单服务提交前）都与组合的当前目标行比较：执行器要求当前目标行的实例、会话与正在收敛的目标一致；
  目标单落库要求当前目标行属于这笔单的实例；提交前要求当前目标行就是这笔单的目标、并在有效期内。
- 已知差别：关闭时 `bar_end_time` 还没到的目标，有效期是 `bar_end_time` 加 1 毫秒，留着一个 1 毫秒的可执行窗口。但下单要过几处检查：执行器收敛前、准备好订单提交前（`checkTargetExecutable`）
  和下单服务提交前，每处都要求当前时刻不早于 `bar_end_time`、早于有效期，几处检查得落在同一毫秒里才能真发出单，实际发不出单，到点照常过期；
  关闭后 BLOCKED 的目标在被执行器置为过期之前（几秒），“目标持续阻塞”的关注项按缩短后的有效期估算一根 K 线，可能提前上报一次；
  Trade 整体暂停（生命周期门禁关闭）期间关闭的会话，那一次唤醒被门禁丢掉；已收敛、已阻塞的目标恢复之后要等下一次全量扫描（账户事实变化的唤醒）或恢复后才到点的定时器才撤挂单（定时器在暂停期间到点的同样被丢），待执行、收敛中的目标恢复后由每秒的定时扫描接上。
  目标事件没有单独的生效时刻字段，生效时刻就是 `bar_end_time`。
  目标事件不在签名保护之内：它走 EventBus，Trade 消费时不验来源，只靠 EventBus 的角色权限（`strategy-eventbus` 能往目标事件的主题上发）。EventBus 服务端在存储机上，各角色的令牌在它的配置里是明文，所以拿到存储机就能伪造目标事件让 Trade 下单；因子机能写坏因子值，间接影响下单。四台都是自己的机器，按单用户原则接受，不做事件签名。主机网关的签名保证的是：存储机、因子机拿不到 `moox-cli`、`console` 的签名能力，不能直接调 Trade 的接口下单。
- 首次接受时按启用且就绪成员的合计权益和参考价格换算数量，结果写入目标历史（`c_shadow = 0`，写入后不再修改）；
  重投复用这一行，不重新估值。它只用于接收时的幂等检查（只在有效期内起作用）和换手告警（最近 1 小时），
  有效期截止 7 天后由定时任务分批删除（启动时一次，之后每 6 小时一次，不受暂停影响），不作长期审计。
- 目标消费者并发处理，最多同时处理 4 条，一条处理完就接着拉下一条：按批顺序处理时同批里一条重试会把其余消息不经处理一起延后，
  只拉一条时服务端又优先投递到期的重投，一个组合每次都要一秒以上才失败（等组合锁、取价超时）就会占住处理位置、拖住其他组合的目标。
  最多容忍 3 个组合同时慢失败。同一组合的处理在组合锁内串行，旧 K 线的目标由落库前的快速检查和存储层的旧目标拒绝挡住。
- 组合账户处于 PAUSED 时仍保存最新目标，但不下单；只有人工 Resume 才恢复收敛。
- SPOT 目标不能为负数；SWAP 用正负号表示方向。交易所原生代码、精度、最小量和合约张数由 Trade 解析。
- 上游标的是 `BTC-USDT`，Trade 内部是 `BTC-USDT-SPOT`、`BTC-USDT-SWAP`，由 `exchange.NormalizeInstrumentID` 按每个目标项自带的 `market_type` 转换；股票原样使用，如 `600519.XSHG`。市场不在组合可交易的市场里、标的无法识别或转换后重复，整条目标拒绝。策略启用时核对要输出的每个市场都在组合可交易的市场里。

目标事件的 `shadow` 字段为真时（试运行中的策略实例发来的影子目标）：Trade 只做权重到数量的换算（权益与参考价同正式目标）并写入目标历史表（`c_shadow = 1`；重投查重、换手检查、同会话同 K 线唯一约束都只看 `c_shadow = 0` 的行）
（按 `target_id` 幂等），**不接受为正式目标、不拿账户锁、不预留资金、不唤醒执行器**。管理台确认实盘前列出的影子目标、`moox-cli trade shadow list --instance-id <实例> [--limit 20]` 都经 TradeConsoleService `ListShadowTargets` 读取（按周期从新到旧，默认 20 条、最多 200 条，经只读视图读库）。
换算前做与正式目标相同的标的检查：没有成员能交易的标的整份拒绝（`unsupported_instrument`，告警），下架名单上的标的改成保持；
换算投递满 5 次仍失败同样记关注项。影子目标与正式目标一样，有效期截止 7 天后清理；目标历史按组合挂外键，删除组合时影子目标随之删掉。

## 4. 目标收敛

**暂不可交易的持仓**：crypto 现货余额或永续持仓对应的标的在交易所列表里、但状态不可交易（币安 BREAK 等），而且不在下架名单里时，这一项本轮跳过、不阻塞整份目标，打一行警告日志（同一组合、账户、标的每天一条，不是 Monitor 能看到的关注项）；恢复可交易后照常收敛。交易所列表里有、但长期不可交易又不在下架名单里的持仓会一直被跳过、资金一直占着，信号只有这行日志（取不到价时还有 `valuation_degraded`），属已知差别。目标接收之后才变不可交易、又没有持仓的买入项会被整项去掉，不打日志。列表里根本没有对应标的的，记 BlockedTarget、整份目标置为 BLOCKED。下架名单里的标的见 5.1。停牌状态另由采集的交易状态检测写到标签成员上，策略对停牌持仓给出保持目标（[采集](采集.md)第 7b 节、[策略](策略.md)）。

TargetExecutor 一轮下一批子单，每个标的最多一笔，批内并发发往交易所，等账户事实更新后再算下一批：

1. 有在途子单（待提交、提交中、结果未知、挂单中）时本轮只处理这些单：从未发出的残留待提交单丢弃，结果未知的批量查询（每笔在未知窗口内最多查两次），挂单中的市价单等它结束，不撤单；
2. 跨标的先减后加：减仓批的结果回来、资金释放之后才发加仓批；减仓全部下不了时才加仓；
3. 减仓优先选择可减持仓绝对值最大的账户；
4. 加仓按成员优先级、可用资金和交易所限制择优，资金用完才用下一个账户，不按比例分配；
5. 当前账户无法承接剩余数量时再换下一个合格成员；
6. 每个执行账户每批永续最多 16 单、现货 8 单，同一组合账户每秒最多一批（约为交易所下单限额的 80%）。额度用完算本轮跳过，不换成员；交易所接口限流暂停或权重用到 90% 时不发新批。

批量提交（`SubmitBatch`）持组合账户执行锁覆盖整批，逐笔持账户锁落 `SUBMITTING`，账户锁不跨请求；发送前再确认一次目标授权；私有流的订单和成交事件在整批结束后入账。

一个成员未就绪时整个组合账户暂停收敛，恢复后继续。

防重复下单：

- 防抖只合并同步请求，不下单；所有重试都按本地事实重算差额，经过同一套准入检查。
- 只丢弃确定没发出的单：未写提交时间、交易所明确未受理（限流、封禁）。未知单过了 2 分钟窗口仍被交易所明确告知查无此单（币安 -2013、OKX 51603；网关的裸 404 不算，保持结果未知）时退回待提交：差额变了（已到位、方向或成员变了、剩余量小于这笔单）或持仓没反映已成交子单就丢弃重算，没变就用原单号重发。超时、408、503 未知都按结果未知处理，只查询不重发。订单号重复（币安现货 -2010 的 Duplicate order、合约 -4116、OKX 51016）说明原单可能已被受理，同样按结果未知处理，由查单认领；-1000、-1001 也按结果未知，-1016 是确定未受理的拒单。
- 下单前持仓校验：目标子单记录下单前持仓（`c_position_before`）。持仓回退到最近 10 分钟同方向成交段里某笔子单下单前的值时，说明持仓没反映已成交子单，整条标的本轮跳过、写入 `blocked_targets`，不换成员，同步纠正后自动重算。
- 同一目标、同一执行账户、同一标的的已发出子单方向切换 1 次时放行纠正单并告警 `target_reversal`，切换 2 次后本目标内跳过这个标的。
- 调仓阈值见 4.1：默认整条标的的成员持仓都与目标同号时，差额不超过目标数量 5% 不下单；建仓、清仓、反向持仓、多成员对冲不受影响。
- 挂单与调仓阈值配合：成交后剩余差额在阈值内就视为到位，不区分挂单和吃单。挂单部分成交、差额落进阈值内时，余下的挂单会被撤、不再补，所以最终偏差最大约为阈值（默认 5%），与吃单成交后的结果口径相同。这是有意的行为，不当成缺陷。

完成判定按交易规则：剩余量在全部成员上都达不到最小数量或最小名义金额时，目标为 0 或已有同向持仓算完成（零头）；
从空仓开新仓就达不到最小量才写入 `blocked_targets`。有成员本来能下单、只是被拒单排除时不算完成。
合约全平的只减仓订单只查最小数量。持仓够但可卖量不足（如被挂单冻结）时为 `BLOCKED`，原因里带“可卖量不足”；只因 T+1 卖不出的按市场规则顺延（“当日买入，次日可卖”），不算阻塞。

拒单：交易所明确拒绝后，同一目标在这个标的上不再向该账户下单，下一轮换成员；全部被拒写入 `blocked_targets`，下一个目标重试。
待提交子单的报价过期时丢弃，下一轮按最新持仓和报价重新下单。

不同执行账户上方向相反的持仓不会被净额抵消成“已完成”。

### 4.1 下单设置与资金设置

两组设置存在组合账户上（`c_order_settings_json`、`c_fund_settings_json`），由 `UpdateLogicalAccountOrderSettings`、`UpdateLogicalAccountFundSettings` 写入，`LogicalAccount` 只读返回当前生效的值（没写的项已填默认值）。
写入时严格校验：未知键、大小写不规范的键、类型不对和越界的值都拒绝，库里只存规范 JSON。执行器每轮收敛都读最新设置，保存后对之后的收敛立即生效；设置读不出来时这个组合不下单，原因写进目标。

下单设置（键名、默认值）：

| 键 | 含义 | 默认 |
| --- | --- | --- |
| `rebalance_threshold_mode`、`rebalance_threshold_ratio` | 调仓阈值：`TARGET_RATIO`（差额不超过目标数量 × r 不调）、`POSITION_RATIO`（调仓金额低于持仓金额 × r）、`EQUITY_RATIO`（低于组合最近权益采样点 × r）、`ALWAYS`。建仓、清仓、反向持仓任何模式都不受限 | `TARGET_RATIO`，0.05 |
| `min_notional_spot`、`min_notional_swap` | 子单最小下单额，与交易所最小名义金额取大。**差额低于它视为已满足**（与调仓阈值同口径）：跳过这个标的，不阻塞，`blocked_targets` 不记，过期告警也不算持仓未到位；合约减仓、清仓例外，低于门槛也照常下 | 10、5 |
| `hourly_cap_spot`、`hourly_cap_swap` | 每个标的每个自然小时（UTC）累计下单金额上限，键是内部标的 ID 或 `*`；**只限制加仓和建仓**，减仓（包括目标改 0、受管但不在目标里按 0 卖出）不受限，金额照常计入汇总。从订单表汇总（结束的单按成交额，没结束的按全部数量，被拒绝和本地丢弃的不算），超出的部分顺延到下一个整点，顺延的标的和原因写进目标的 `blocked_targets`（带 `deferred` 标记，界面用中性色显示“顺延”），但不算阻塞（目标仍定为已收敛，不触发“目标持续阻塞”告警） | 不限 |

| `batch_interval_seconds` | 批间隔，写了就覆盖默认（实盘 1 秒、模拟盘 0.3 秒） | 不写 |
| `order_mode`、`slippage_step`、`slippage_max`、`max_attempts` | `PSEUDO_MARKET`：限价 + IOC，价格 = 参考价 ×（1 ± 滑点），买入向上、卖出向下取整到价格精度；没成交完的剩余量下一轮按新持仓补，滑点每次加一份直到上限；尝试次数按（目标，标的）统计（换成员不重新计数）= 最近连续没成交完的 IOC 子单数，一笔 IOC 全部成交即清零，非 IOC 子单、从没发到交易所的子单（结果未知、查无此单退回待提交后被丢弃：已撤销、零成交、没有交易所单号）跳过不打断；用满次数记“未到位”并告警一次，不再重试。`MARKET` 为市价单 | `PSEUDO_MARKET`，0.015、0.06、4 |
| `resting_ratio`、`resting_ttl_seconds` | 挂单：加仓、减仓、调仓按此比例（每个方向的金额预算）挑标的改成限价 GTC 挂单（买一、卖一价），建仓、清仓不挂；挂单剩余量从差额里扣除，反向或超出差额的挂单撤掉；寿命 0 表示保留到下一份目标到达或过期，否则到期撤单；同一目标里挂过单、挂单已结束（到期或超出差额被撤）的标的不再挂单，改吃单（从没发到交易所、没有交易所单号的不算挂过）；目标过期时组合里所有目标的挂单一起撤掉 | 0，0 |

资金设置（键名）：`reserve_ratio`（资金预留比例）、`bnb_discount`（只会打开交易所的 BNB 抵扣开关，不会关）、`bnb_reserve_amount`（BNB 保留金额 N：统一账户 BNB 市值低于 N 减 10 时市价补买缺口；普通账户只补现货钱包，目标是 N 的一半，市值低于 N/2 减 5 时补买，见资金维护）、
`dust_convert_enabled`、`dust_convert_interval_days`（默认 15 天，**只兑受管的零头**（MooX 成交过留下的），用户自持、MooX 从没碰过的币不动；仍排除当前目标和排除资产、低于 5 USDT；这是对“非目标、非排除”的有意收窄，时间记在账户的 `c_last_dust_convert_at`）、
`stablecoin_margin`（稳定币及目标比例，必须含组合的结算币（默认 USDT）、和为 1）、`margin_coins`（保证金币及配置的固定 U 值）、`arbitrage_base_assets`（套利底仓）。
保证金率监控的四个键放在资金设置里（口径和动作见 5.2，只对币安生产环境的实盘组合生效）：`margin_ratio_threshold`（普通账户阈值，默认 0.5，范围 (0, 10]）、`unified_mmr_threshold`（统一账户 uniMMR 阈值，默认 1.5，范围 (1, 100]）、`margin_reduce_ratio`（触发后每个持仓减掉的比例，默认 0.1，范围 (0, 1)）、`margin_monitor_disabled`（关闭监控，默认开启）；读不出来时数值取默认值，关闭开关读不出来按开启处理（监控是保护，不能因设置写坏就悄悄关掉）。

已保存的设置读不出来时（`LogicalAccount.order_settings_error`、`fund_settings_error` 非空，包括资金设置里个别数值读不出来、执行器按默认值处理的情况），界面提示并禁止保存，不按默认值显示；
修复步骤：在设置表单点“按默认值重置”确认（会丢掉原来保存的整组设置，用默认值覆盖），再重新填写；或直接重新提交一份合法的设置。

资金维护（`fundmaint` 服务 + `FundWorker`，每小时一次、设置变更后和账户第一次就绪时马上一次）：BNB 抵扣、BNB 补买、小额兑 BNB、稳定币调平（统一账户，各稳定币占比与目标的绝对差超过 5 个百分点才动，每轮只做一个方向、先卖，买单挂买一价、挂满 55 分钟没成交才撤，撤掉过期买单的同一轮在撤单全部结束后重读账户、重算并重挂（账户因撤单前的部分成交还没就绪就等下一轮），卖出用 IOC，卖单成交后的买入要等下一次检查，账户就绪唤醒每个账户每个进程只有一次；BNB 补买单刚下出时调平让路）。
只对币安生产环境的实盘账户生效：模拟盘、测试网、OKX 不做；含非币安成员的组合、模拟盘组合写入这些项时被拒绝。BNB 保留金额按**每个币安执行账户**各 N 计。币安文档确认 U 本位合约的 BNB 手续费抵扣要用合约钱包里的 BNB，而补买只下现货单、不在钱包之间划转 BNB，所以普通账户只维护现货钱包：只数现货钱包的 BNB，补买目标是 N 的一半（触发容差同样减半），归集时现货钱包留的 BNB 补买资金也按这个目标（`collectKeep`）；合约钱包里的 BNB 由用户自己放，不算、不补。合约侧的抵扣开关保持只开不关：合约钱包没有 BNB 时手续费只是照常扣 USDT，无害；要用 BNB 抵扣合约手续费，请自己把 BNB 放进合约钱包。统一账户只有一个钱包，目标是 N，口径不变。换算目标时按账户逐个计缺口再求和，扣的缺口与补买目标一致（普通账户只数现货钱包的 BNB、目标 N/2，统一账户 N；`bnbShortfall` 直接用 `fundmaint.BNBQuantity`、`BNBBounds`，不另写一份）；保留金额要大于 10。组合里有币安普通账户时，设置页在 BNB 保留金额旁写明“普通账户只补现货钱包，合约手续费用 BNB 抵扣需要在合约钱包里自行放入 BNB”。BNB 抵扣的查询和设置在组合锁外进行。
补买和调平的单归属 `SYSTEM`：不暂停组合、不算执行器的子单、成交不让资产变成受管；组合暂停或正在清仓、减仓时不下单。权益里除结算币外的目标稳定币按对结算币的现货价折算计入。

### 4.2 账户同步

- 同步分四种：轻量同步（成交、持仓、账户事件 250 毫秒防抖后触发，下单之后也用它）只读持仓和账户，补拉不一致标的的成交，永续一致时 10 权重；30 秒对账读账户、持仓、挂单，加轮转批次（全集十分之一，单次最多 20 个标的）；增量同步不推进轮转，用于撤单确认；会话启动和手动同步先拉必须的标的（挂单、未结束订单、成交缺口，不限个数），再按持仓或余额有变化的、近期已结束订单的、一批轮转的顺序补，总数到 60 个为止，其余靠轮转。轻量同步没能恢复准入时按 0.5、1、2 秒退避重排，最多 5 次。权重用到 80% 时推迟对账。
- 持仓数量只由成交投影和 REST 决定，私有流持仓事件只关闭准入。本地持仓 10 秒保护期内不删、不被更旧的 REST 覆盖，过了保护期以 REST 为准。
- 现货 REST 余额的交易所更新时间早于待确认水位时，不恢复准入。
- 成交重放只按订单、方向、数量、价格判重，手续费等字段不一致只记日志。
- 账户创建之前的成交只推进游标，不入账，也不算外部成交；创建之后的外部订单或成交暂停组合账户（自主下单的组合不暂停）；已被系统自动暂停的组合保留原有原因。
- 交易所账户里有逐仓持仓（moox 只支持全仓单向）：该标的持仓不入投影，账户所在组合暂停自动执行，暂停原因写明标的（走 `auto_paused` 关注项），同时记关注项 `isolated_position`（组合已暂停、自主下单或没加入组合时也会记）；其余持仓、私有流和快照照常运行。已经暂停的组合不改写原因；用户在逐仓持仓还在时恢复，下一次同步会再暂停。
- 币安私有流的成交判断是“有成交号（非空、不为 -1）且本次成交量大于 0”，强平、自动减仓产生的 `CALCULATED` 成交与 `TRADE` 一样入账（强平单的客户端订单号不是我们的，走外部成交路径）。
- 账户检测会测本机时钟与交易所时间的偏差（币安 `/api/v3/time` 与 `/fapi/v1/time`，OKX `/api/v5/public/time`）：超过 1 秒是提示，达到 3 秒是阻断项 `clock_skew`；下单或查询遇到币安 -1021、OKX 50102 记关注项 `clock_skew`（订单仍按结果未知处理）。
- 余额确认用本地读取时间：读取账户快照前记录时间，晚于成交时间才清除待确认水位。
- 标的已下架（交易所明确回“标的不存在”：币安 -1121、OKX 51001）不让整次同步失败：查成交（会话启动那一次和之后的账户同步都一样）、统一账户按标的查挂单遇到它就跳过这个标的；查成交遇到它时只跳过、记提示，成交游标原样保留（删掉的话标的一旦又查得到——误报或重新上市——币安会从 `fromId=0` 把历史成交全部重拉一遍），
  并在入账快照之前、同一个事务里把账户在这个标的上“观察累计成交量大于已入账成交量”的订单（含已结束的单）的观察成交量压回已入账值
  （下单回执、订单快照会抬高观察成交量，明细再也拉不到，不收掉的话账户每次同步都判有成交缺口、一直停在“成交待余额同步确认”），
  每笔记关注项 `orders_instrument_gone`（详情带单号和“标的已下架，成交明细缺失，以持仓/余额同步为准”）并写日志；
  查单遇到它时，发出过的未结束订单（结果未知、挂单中、部分成交、撤单中、撤单结果未知；提交中的要停了 5 分钟以上）按 `EXPIRED` 结束，
  原因写“标的已下架，交易所查不到这笔单，成交以持仓/余额同步为准，需人工核对”，释放剩余资金预留，记关注项 `orders_instrument_gone`；
  待提交的不动（提交时会被交易所拒绝）。持仓、余额照常以交易所同步结果为准，迟到的成交仍可入账。否则一笔下架标的的遗留单会让账户永远同步不过去、
  一直未就绪，整组清仓、减仓（含保证金风控减仓）、目标执行全被挡住。
- 现货受管资产由系统推导：结算资产、当前目标里的标的、标的汇总里受管的标的。其他资产不估值、不卖出，持仓页照常显示。
  标的汇总（`t_account_instrument_summaries`）：持仓来自余额的市场（现货、股票）里每个（执行账户，市场，代码）一行，成交入账的同一个事务里更新，行不删除（合约的均价来自持仓表，不走这里）。“受管”只由 TARGET、OPERATOR 订单的成交置位，置位后不清；数量、成本、最近成交价由每一笔成交更新、不分订单来源：买入时数量与成本都累加，卖出时减少量不超过当前数量、成本按当时均价扣减，数量为 0 时的卖出忽略，数量归零后成本归零；最近成交价取成交时间最晚（同一毫秒取成交号最大）的一笔。模拟盘持仓页的均价、已关闭模拟账户的估值价、受管现货取不到价时的“最近一笔成交价”都读它。
  受管现货取不到新鲜报价时（权益采样和模拟盘快照用同一套规则，`execution/valuation.go`）：先用不超过 90 秒（权益过期阈值）的最后已知价；
  没有时只有三种情况按 0 计——标的表里没有这个标的、交易所确认标的不存在、标的已不在交易状态又在下架名单里；其余不在交易状态的（BREAK、HALT、暂停、盘前等）
  按本账户最近一笔成交价计；仍然没有价、或标的还在交易只是暂时取价失败的（在下架名单里也一样，下架之前它仍有市价），报错。降级估值不拉低权益的来源时间。账户里只有不受管的币、没有结算资产时权益为 0，要先准备结算资产。执行账户快照里落库的 `equity`（管理台展示、`turnover_high` 的权益口径）也在每次完整同步时按这个统一公式重算，不用适配器各自的口径（币安现货没有、币安合约是 `totalMarginBalance`、统一账户是 `accountEquity`、OKX 只有结算币 `cashBal`）；交易所给的总权益只在 `exchange_equity` 里展示核对。估值失败时沿用上一次的值，不让同步失败；私有推送不改 `equity`。
- 杠杆按需设置：合约账户默认 `*` 倍杠杆，单标的配置优先；首次在某标的开仓前设置全仓和杠杆，结果记在会话内存里，改杠杆不重启会话。

## 5. 人工干预

| 操作 | 行为 |
| --- | --- |
| `PauseLogicalAccount` | 停止新的自动下单，需要填写原因 |
| `ResumeLogicalAccount` | 用已保存的最新目标恢复收敛 |
| `SubmitOrder` | 人工下单的唯一入口，只有一个动作类型 `MANUAL_ORDER`，一条流程里按组合的控制模式决定其中几步：策略驱动的组合（接管）先暂停组合账户并撤销活动的 TARGET 订单，请求里同步提交到交易所，完成后保持 PAUSED；自主下单的组合（直接下单）不暂停、不撤别的订单，只在本地受理并冻结资金，交易所提交由后台完成。两种都要求执行账户是请求里 `logical_account_id` 的启用成员，新建动作时执行账户已启用、当前在交易时段内。流程在建动作时记进动作结果（`takeover`），同一个 `action_id` 重试、后台恢复都沿用它 |
| `CancelOrder` | 策略驱动的组合账户撤单会暂停整个组合账户，自主下单账户不暂停 |
| `FlattenLogicalAccount` | 逐账户清仓：同步全部成员、撤销全部活动订单、在原账户提交平仓单，逐账户记录结果，最终保持 PAUSED（自主下单组合不暂停）且保留最新目标。每笔子单前等账户就绪（实盘每笔成交都会关闭准入），等不到就结束本轮；没有撤单时用轻量同步 |

人工下单、撤单和清仓都必须带幂等 `action_id` 和操作原因。`ListOperatorActions` 按组合分页列出这些操作记录（可按类型过滤），概览页的“人工操作记录”用它。

**持仓页的“是否到位”由 Trade 给出。** `GetLogicalAccountTarget` 的响应带 `lanes`：目标里的标的和目标之外、执行器管着的持仓各一条（整项跳过的下架标的、套利底仓的对冲腿、不受管的现货没有），状态是执行器自己的结论（`target/lane_status.go` 的 `laneStatus`，过期告警 `HasDifference` 用的是同一个函数），页面只显示、不再自己算：

| 状态 | 含义 |
| --- | --- |
| `WILL_ORDER` | 有差额，执行器在组合活动且目标有效时会为它下单（未到位） |
| `IN_PLACE` | 已到位：差额为 0、在调仓阈值之内、目标是保持当前持仓，或剩下的零头不到交易所最小数量、最小名义金额 |
| `BELOW_MIN_NOTIONAL` | 差额低于设置的最小下单额，视为已满足 |
| `MARKET_DEFERRED` | 停牌、涨停、跌停、当日买入次日可卖，`reason` 是具体原因 |
| `BELOW_LOT` | 整手交易的市场里差额不足一手，视为已满足 |
| `BLOCKED` | 有差额但下不了单：没有成员支持这个标的，或从空仓开新仓不到交易所最小数量、最小名义金额，`reason` 是原因 |
| `UNKNOWN` | 判断要用的报价不在缓存里，说不准 |

这个查询只读库、只读适配器里已有的报价缓存（5 分钟以内的），不向交易所发请求。最小下单额、按金额比较的调仓阈值、股票的停牌和涨跌停要用报价，缓存里没有时给 `UNKNOWN`；执行器在跑（目标没收敛）时缓存不到一分钟就会刷新，组合暂停、目标过期或休市时多半是 `UNKNOWN`。目标已收敛（`CONVERGED`）时不算、`lanes` 为空，页面整页按到位显示；成员或下单设置读不出来时也为空，页面按未知显示。被拒单、每小时上限顺延等只有下单时才知道的原因仍在 `blocked_targets` 里。

判断和下单时一样逐个看候选成员（`placementCandidates`），每个成员按 `candidateStatus` 的次序（检查项与下单时的 `checkCandidate` 相同）：数量取整后不到交易所最小数量 → 停牌、涨跌停、T+1 → 金额不到交易所最小名义金额（合约全平例外）→ 金额低于设置的最小下单额（合约减仓、清仓例外）。某个成员太小就换下一个，有一个成员能下就是 `WILL_ORDER`（两家交易所最小值不同、首选成员下不了而另一家能下时也是）。全部成员都太小时：有成员是低于设置的最小下单额给 `BELOW_MIN_NOTIONAL`；其余在目标为 0、已有同向持仓或整手市场里是零头，算已满足；从空仓开新仓才是 `BLOCKED`。A 股目标为 0 的零股按全部可卖数量算，不按一手取整。

过期告警（`HasDifference`）用的是同一个函数，口径相同：不到一个步长或不到交易所最小名义金额的同向残差不算“持仓未到位”；A 股目标为 0 剩零股时算未到位；从空仓开新仓不到交易所最小值也算未到位，和执行器把它记成 `BLOCKED` 一致。

已知差别：

- 本目标的拒单记录、伪市价次数和每小时上限只有下单时才知道，这里不看；下单后的结果写在 `blocked_targets` 里，页面优先显示。
- `WILL_ORDER` 只表示有差额、条件满足时会下单，不看目标此刻能不能执行：目标已过期或还没到 `bar_end_time` 时仍可能显示“还会下单”，而执行器实际不下。只影响显示，不影响下单。
- 除了“不到最小数量”和合约全平，判断都要用报价。组合暂停、目标过期或休市超过 5 分钟后缓存里没有报价，有差额的标的显示“未知”，并计入页面的未到位个数。

按比例减仓（`REDUCE`）没有对外接口，只由保证金率风控发起（见 5.2）：先暂停组合（自主下单组合不暂停）、撤全部订单，再把现货和合约同比例减掉（比例大于 0 小于 1）。每个持仓的目标数量在发起时写定并存进动作结果（`reduce_targets`、`reduce_done_accounts`），之后各轮、重试和重启恢复都收敛到这个数量，不会再减一次；减不动一个最小数量的持仓（零头）不登记，套利底仓的对冲腿不减。

清仓、减仓、下架清仓共用一套执行框架（`operator/flatten*.go`）：范围收窄到一个标的时，撤单、撤单确认、恢复子单、剩余统计和完成判断都只看这个标的；同一组合里整组清仓、减仓和下架清仓互斥（整组动作遇到运行中的这一族动作时，同类型、同比例且覆盖本次范围的返回那个动作的进度，其余返回“忙”），不同标的、不同交易所的下架清仓之间不冲突、排队执行。重启后 `ResumeOperatorAction` 与工作线程按持久化的请求继续这一族动作；它们运行期间组合不能恢复自动执行。

### 5.1 下架处理

下架检测由 Collector 负责（发现或手工登记后发布 `event.collector.instrument.delist_scheduled`），之后全部在 Trade 进程内完成：收事件、写禁止名单、按时间线清仓、核对。下架事件只有加密现货与永续；A 股、港股退市走标签成员的交易状态，不经这条时间线。
三张表在 `schema/delist.sql`：

- **禁止名单** `t_trade_blocked_instruments`：全局的，不分空间，键是（交易所、市场、交易所代码）。范围 `c_scope`：`ALL` 对所有账户生效；`PAPER_ONLY` 只对模拟盘账户生效（演练）。`c_delist_id` 是写入或把范围升级为 `ALL` 的那条下架记录。匹配视图 `store.BlockedSet` 带账户判断（`Contains(account, …)`），执行器、目标接收、清仓、估值降级都用它；同一组合的成员执行方式相同，所以不会出现同一组合一半受限。
- **下架记录** `t_trade_delists`：一条对应一个（标的、范围、下架时间），状态 `ACTIVE`、`COMPLETED`、`FAILED`、`CANCELED`、`RESCHEDULED`；`c_planned_round` 是已规划到第几轮（0 还没到 T−24h，1 已按 T−24h 规划，2 已按 T−2h 规划）。同一标的同一范围只能有一条 `ACTIVE`（部分唯一索引）；`c_source_event_id` 唯一，挡住重投。
- **各轮各组合** `t_trade_delist_flattens`：规划一轮时给每个持有的（空间、组合账户）建一行，写下确定生成的操作号（`uuid.NewSHA1`，由“记录 ID、轮次、空间、组合”生成）；动作状态不在这里存，从 `t_operator_actions` 读。

**收到下架事件**（`eventconsumer/delist.go` 的 `RunDelist`，消费者 `trade_instrument_delist_v1`，从头读起、串行处理；解码或校验失败 TERM，写库失败 5 秒后重投）：在一个事务里（`application/delist/intake.go`）

1. 交易所、市场、代码统一转大写；同一事件 ID 已有记录就是重投，不做任何事；
2. 防乱序：和这个（标的、范围）最近的一条记录（不论状态）比事件发生时间，更早的是乱序的旧事件，不做任何事；
3. 已有 `ACTIVE` 记录且下架时间相同，不做任何事；下架时间不同就是改期：旧记录记 `RESCHEDULED`（结果写“改期为 …，由记录 … 接着处理”），再新建一条；
4. 新建 `ACTIVE` 记录并写名单：没有这一行就插入（范围取事件的）；已有 `PAPER_ONLY` 行而事件是 `ALL` 就升级为 `ALL`；行指向刚改期结束的旧记录就改指新记录（范围不变）；其余不改。

提交后名单有变化就唤醒目标，并检查特殊持仓：标的是某个组合的套利底仓对冲腿或排除资产（BNB 保留、稳定币保证金、保证金币）时打一条关注项日志（固定文字），下架时没有任何动作会碰它们，要人工处理。新建了记录时查一次持有者，有非零头持有者或有账户没能判断，记 `delist_detected`。收到时已过下架时间的事件（手工补录）照常建记录、写名单，之后只等核对。
下架消费者不受暂停限制（写名单是保护动作），也不计入 Trade 的 EventBus 就绪（配错不能拖住目标执行和恢复追赶），状态只进健康详情 `delist_consumer_running`。

**推进时间线**（`application/delist/timeline.go`，定时任务“下架处理”，复用资金维护的定时任务外壳：每 30 秒一次、单次最长 5 分钟、受生命周期门禁约束）：每次读出全部 `ACTIVE` 记录，逐条按记录、步骤行、动作状态和当前时间重新推导该做什么，进程里不存状态（T 是下架时间）：

- **now ≥ T+10 分钟：核对**。查持有者（范围是 `PAPER_ONLY` 时只看模拟盘）：仍有非零头持有者或有没能判断的账户记 `FAILED`，否则 `COMPLETED`，零头和说明写进结果。状态用条件更新（只改 `ACTIVE`），`PAPER_ONLY` 的记录结束时，在同一事务里删掉范围仍是 `PAPER_ONLY` 的名单行（模拟盘恢复买入；已被真实下架升级为 `ALL` 的不删）。查持有者失败这次不动，原因写进说明，下一次重试；
- **T ≤ now < T+10 分钟**：不做任何事，已在跑的清仓按自己的截止时间 T 停下；
- **now < T：规划和发起**。按 now 算出应到的轮次（T−24h 之前 0，[T−24h, T−2h) 为 1，[T−2h, T) 为 2），比已规划的轮次大就规划这一轮：只规划应到的最新一轮，错过的不补。查持有者，按（空间、组合账户）聚合非零头持有者，在一个事务里用条件更新推进已规划轮次并插入各行；没有持有者也推进，说明里写明查到几个组合、没能判断的账户和零头。然后推进当前轮的各行（更早一轮没发起的行不再发起）：动作不存在就发起；`RUNNING` 由动作工作线程每秒恢复；`COMPLETED`、`PARTIAL` 这一轮结束；`FAILED` 的动作最后修改时间过去 10 分钟以上，就用同一个号再调一次（同号请求会重新进入运行）。发起前确认还没到 T、记录仍是 `ACTIVE`，然后进程内调用 `FlattenLogicalAccount`（`DeadlineAt` 为 T，原因只由记录 ID、轮次、标的生成）；组合正忙、组合里没有这个交易所的成员、成员标的表里解析不到时不建动作，下一次推进再试。

“步骤行已写、动作已建、进程在拿到返回前退出”这个窗口由同一个操作号挡住：重启后读到 `RUNNING` 由动作工作线程恢复，不存在就再发起。会改记录和名单的只有三处（收事件、定时任务、`UnblockInstrument`），各自用一个 SQLite 事务，不需要按标的的锁：解除和发起清仓之间被解除时，清仓第一轮开头查名单就撤单、记完成，不会卖；改期和发起之间刚好改期时，旧记录的清仓卖的就是即将下架的币，新记录对同一组合发起时拿到“忙”，等旧动作结束再发起；规划和核对都用条件更新，已结束的记录不会再插行、不会再记完成或删名单。

**解除名单**（`UnblockInstrument`，管理台）：一个事务里删掉名单行，并把这个标的所有 `ACTIVE` 记录（两种范围都算）记为 `CANCELED`（结果写“名单被手工解除”）；提交后唤醒目标。已在跑的 `DELIST_FLATTEN` 下一轮开头发现标的不在名单里，撤掉自己的单、记 `COMPLETED` 并带 `unblocked`。

**演练**：就是范围为 `PAPER_ONLY` 的下架登记（`moox-cli collector delist register --paper-only`，或下架名单页的“手工登记下架”勾选演练）。名单行只对模拟盘账户生效：实盘照常买卖；模拟盘只减不增；只查模拟盘持有者、只平模拟盘组合。即使误把实盘组合交给清仓，实盘账户不在名单里，清仓会按“已解除”立即撤单结束、不卖。演练核对结束时删掉仍是 `PAPER_ONLY` 的名单行；想提前结束就在下架名单页对这一项点“解除”。

**关注项**：`delist_detected`（收到新记录且有组合持有或有账户没能判断，约 3 分钟）；`delist_failed`（由关注项扫描推出：进行中记录的当前轮有动作 `FAILED` 或 `PARTIAL`；当前轮有行建好超过 30 分钟、动作还不存在；下架事件消费者 3 分钟以上没在运行，只在启用 EventBus 时；核对失败的记录在结束后 24 小时内）。详情都是固定文字。

接口都用（交易所、市场、交易所代码）定位标的（交易所用枚举 `EXCHANGE_BINANCE`、`EXCHANGE_OKX`，市场只收 `MARKET_TYPE_SPOT`、`MARKET_TYPE_SWAP`），由 Trade 按标的表换算内部标的 ID；都是全局方法，Trade 不检查空间头。

管理台“交易管理 › 下架名单”页上段是下架处理记录（进行中与最近结束的，展开看各轮各组合的动作），下段是名单并可逐条解除；工具栏有“手工登记下架”。moox-cli 只能查看（`trade blocked list`、`trade delist list`）。`holders` 没有持有者时是空数组（经网关的 JSON 序列化不会省略，有测试锁住）。
“策略持有”：现货必须是受管资产且余额大于 0，永续持仓不为 0（套利底仓的对冲腿不算）；标的的计价币不是账户结算币的不算（例如手工屏蔽 FOOBTC，清仓什么也不会卖，写进 `notes`）；只看该交易所、在组合里的执行账户，测试网不算。

**名单标的“只减不增”**：名单只禁止买入。执行器在 `loadMembers`（`target/executor.go`）、`constrainDesired`（`target/delist.go`）两处处理，Converge 和 `HasDifference` 共用，接收目标时（`eventconsumer/target.go`）另有一处：

- 标的还能交易：目标截到不超过当前持仓（多头不超过持仓，空头绝对值不超过持仓，反号或没有持仓截成 0），加仓和反向开仓的部分去掉并按组合、标的每天告警一次；减仓、卖出照常，受管持仓不在目标里的仍按目标 0 卖出；截断发生在挂单对账之前，名单标的的买入挂单随之撤掉。组合里只有部分成员的交易所在名单里时，目标不动，受限成员不会被选来加仓；
- 标的已经不能交易：整项跳过，不买不卖，剩下的持仓或余额不再让目标置为 `BLOCKED`；现货按基础资产且只匹配 `SPOT` 条目（永续下架不会豁免同名现货余额），永续按（交易所、`SWAP`、代码）匹配；
- 接收目标时，名单里已经不能交易的标的只跳过这一项（改成“保持”），不拒绝整份目标。截断告警只在截掉的买入量确实会下出去时才发（目标只比持仓多一点点、低于调仓阈值或最小下单额的不算）。
名单是按成员所在交易所匹配的，别家交易所的同名标的不受影响。写入或解除名单后、下架清仓结束后都会唤醒目标重新判断（已收敛、已阻塞的目标不被定时器扫描）。

**`DELIST_FLATTEN`**：伪市价单（限价 + IOC，滑点固定 3%，买入向上、卖出向下取整到价格精度），不暂停组合、只看这一个标的和这个交易所的成员；零成交的 IOC 不算终结。子单号固定 32 位（`mf` + 30 位十六进制，第几次尝试并进哈希，OKX 的 `clOrdId` 上限 32 位，有契约测试），两笔 IOC 之间至少隔 3 秒：一笔发出后下一笔最早时间直接记成现在加间隔，下一轮先睡到间隔结束再查名单、同步、下单（睡醒后留轮间等待和发单余量，预算不够就不睡、结束这一轮），中间不做账户同步，不会空转打满交易所限频；睡眠期间解除禁止，睡醒后查到就停，不会再多下一笔。每次进入运行（创建、或同一个动作号在 FAILED、PARTIAL 之后重试）在结果 JSON 里记一个起点（`attempt_started_at`），被拒和连续未成交只统计起点之后创建的子单：这一轮最近一笔被交易所拒绝，或连续 20 笔 IOC 一股都没成交（部分成交说明在推进，不计入），这一轮以 `PARTIAL` 结束，同一个动作号重试会重新来过（30 分钟期限也从这一轮的起点算，不看动作创建时间；起点取到秒，上一轮结束不到一秒就用同一个动作号重试会看到上一轮同一秒的被拒单，下架定时任务对失败的动作至少隔 10 分钟才重发，碰不到）；执行器不碰清仓中的标的；清仓一族（下架清仓、整组清仓、减仓）的子单不管动作是否还在运行都不算冲突、不暂停组合。动作要结束（完成、部分完成、失败）之前先收拾本动作还没结束的子单（指定的成员已被移出组合、组合里没有该交易所的成员、标的在成员的标的表里解析不到这三种提前失败直接记 `FAILED`，不收拾子单、不唤醒目标），尽力而为，分三步：先只读库逐个账户列出本动作的子单（每个账户另起 5 秒上下文，不受本次调用剩余预算影响；某个账户列不出来就跳过它、记为没列全，其余账户照常）；再逐笔丢弃待提交的子单（记已撤销，从没发到交易所，释放资金预留；每笔各用 5 秒时限，某个账户等账户锁超时一次就跳过它余下的待提交子单，服务关闭时跳过这一步；子单已经不是待提交，例如在控制台手动撤掉了，算已收拾）；最后逐笔同步解析提交中、结果未知的子单，本次剩余预算平均分给还要尝试的子单、每笔至少 2 秒，某个账户这一轮已失败过就跳过它余下的子单，解析后退回待提交的同样丢弃，放不下的留到下次。还有没收拾掉或没列全的就先保持运行，在结果里记下要结束成什么（`finishing_status`）和进入收尾的时间（`finishing_since`，落库，重启后照样从它算），之后每次恢复只收拾、不下单。收尾最多 30 分钟：满了仍收拾不完就照常落成记下的状态，没收拾掉的子单写进结果的 `manual_check_child_order_ids`（没列全时另列一次，其中待提交的顺手丢弃）；交易所确认标的不存在（币安 -1121、OKX 51001）的子单等多久都收拾不了，当场放行、同样写进这个列表，不阻塞收尾（记下的状态是 `COMPLETED` 时照样记 `COMPLETED`，子单号在结果里）。这两种情况都记关注项 `flatten_orders_unsettled`，要人工到交易所核对；凭证失效、取不到账户会话（重启后会话还没建好时只是暂时的）不当场放行，按 30 分钟上限处理。收拾期间遇到的任何错误（解析、丢弃失败，写库失败，预算用完，列子单失败）都只写进动作的 `last_error`，不作为调用错误返回，不影响 Trade 的整体就绪；数据库真坏了时落库进度本身会失败并返回，其他工作线程也会报出来。之后的清仓、减仓撤别的单时遇到这类遗留单（解析或撤单时交易所确认标的不存在）不算撤单失败：撤单后的账户同步按 4.2 节把它按 `EXPIRED` 结束（记关注项 `orders_instrument_gone`），撤单确认随之通过，不让它挡住后面的动作（包括保证金风控减仓）。截止时间在每笔下单（包括提交待提交的子单）之前都检查，一轮中途过了就不再下；过了截止时间先看是否已解除禁止，解除了照样走“撤单后记 `COMPLETED`”；同一个动作号在截止之后重试保留上一轮各账户的进度。限价按 3% 滑点算出后再夹进交易所的价格偏离限制（币安 PERCENT_PRICE，与目标执行器的伪市价单同一个夹价函数）。每一轮先查名单，已解除禁止就撤掉本动作自己的订单，撤单后同步并确认它们都结束了，才记 `COMPLETED` 并带 `unblocked` 标记（不记 `FAILED`、`PARTIAL`，免得下架定时任务把它当失败重发）；撤单还没确认结束就继续运行、下一轮接着确认，不记完成也不唤醒目标（没结束的 OPERATOR 单会被执行器当冲突、暂停组合）。同标的同交易所已经有另一个动作号在平（例如演练和真实下架同时平同一个模拟盘组合）时，新的动作号返回“忙”，不创建动作、也不返回别人的动作。下架的恰好是套利底仓的对冲腿时不自动平仓：以 `PARTIAL` 结束并写明原因、打关注项日志，不会静默记完成。

下架处理的已知差别：

- 演练不再验证“实盘买入被挡住”：演练的禁止只对模拟盘生效。
- 下架处理不能整体停用；不想处理某个标的就在下架名单页解除。手工解除会同时取消这个标的进行中的真实下架和演练。
- 下架时间提前时，旧记录已在跑的清仓带的是原来（更晚）的截止时间，会越过新的 T 继续下单，直到它自己的截止时间；标的下架后下单会被交易所拒绝。
- 改期后，旧记录这一轮还没发起的组合不再发起，由新记录到点重新规划；某一轮没发起完就到了下一轮，上一轮剩下的行同样不再发起。
- Trade 暂停或停机期间时间线不推进，错过的轮次不补，恢复后只做应到的最新一轮；停到 T 之后才恢复，就只做核对，持仓不会卖出。暂停期间仍会收事件、写名单；已在跑的清仓由动作工作线程继续（它不受暂停限制）。暂停即“不自动下单”，下架清仓也不例外，与保证金风控一致。
- Trade 停机超过 72 小时（`MOOX_COLLECTOR` 的保留期），这期间发布的下架事件会丢失，要手工登记补上；Collector 不会重发。
- 核对失败的关注项只在结束后 24 小时内上报，不需要“确认已处理”；24 小时到了 Monitor 会发一条“恢复”通知，但持仓可能还在，以下架记录的结论为准。核对失败（`FAILED`）是终态，没有“重新核对”的入口：人工处理完持仓后记录照样显示失败；用同一个下架时间重新登记会被 Collector 去重、不再发事件，误点“解除”取消记录后只能换一个下架时间重新登记才能重走时间线。
- 规划时有账户没能判断是否持有，只在记录的说明里显示，不立即告警；要到核对时仍判断不了才告警。零头不单独告警，只写在记录的结果里。
- 下架事件消费者停了不影响 Trade 就绪和恢复追赶，只上报关注项。
- Trade 不认识的标的（没开通对应市场）不立即结束，要到 T+10 分钟核对通过才结束。

### 5.2 保证金率监控

每分钟检查一次币安生产环境、已启用且就绪的实盘永续账户（`marginmonitor` 服务，复用资金维护的定时任务外壳）。口径（读数不全一律不触发，不会凭空减仓）：

- 币安普通账户（`BINANCE_STANDARD`）：交易所总权益 ÷ 合约持仓名义，**不高于** `margin_ratio_threshold` 触发。总权益取账户快照的 `exchange_equity`：现货快照不填这个字段、多市场合并时相加，所以普通账户上它就是合约接口的 `totalMarginBalance`（钱包余额 + 未实现盈亏 + 多资产模式下的抵押，保证金币手工划到合约钱包的部分也算在内，正是币安决定强平的口径）。换算目标用的策略权益不取交易所总权益（见 4.2 的统一公式），和这里的风控读数是两回事。持仓名义 = Σ |数量| × 标记价，没有标记价用开仓均价；没有持仓时不触发；
- 币安统一账户（`BINANCE_PORTFOLIO_MARGIN`）：直接取快照里交易所给的 `uniMMR`，**低于** `unified_mmr_threshold` 触发；`uniMMR` 为空时退回总权益 ÷ 维持保证金（总权益取 `exchange_equity`，维持保证金取快照的 `maintenance_margin`），这时两者缺一或不大于 0 不触发（口径见第 12 节）；
- 账户快照超过 3 分钟没更新不判断；
- **OKX 暂不监控**：官方样例里账户级的维持保证金在 `mmr`、`adjEq`，币种明细里的 `mmr` 和 `mgnRatio` 是空串，现有快照读不对，宁可不监控也不读错。含 OKX 账户的组合每个账户告警一次“OKX 保证金率监控未接入”，资金设置表单只在组合里没有币安生产实盘成员（全是 OKX 等不被监控的成员）、测试网、模拟盘时隐藏这一组设置（隐藏时保存提交库里已存的值，不重置）；混合组合（既有币安生产实盘成员、又有 OKX 成员）照常显示并注明：OKX 成员不参与保证金率判断，触发减仓时按设置的比例对整组减仓（含 OKX 成员）；接入账户级 `adjEq`/`mmr`（或 `mgnRatio`）后再开放；
- **依赖账户类型检测**：账户类型（`c_account_mode`）由账户检测写入；还没有写入的实盘永续账户同样不监控，并告警一次“账户类型还没有检测写入”。测试网、模拟盘不监控。

触发后：暂停组合并发起 `REDUCE`（自主下单组合不暂停、不改写暂停原因，告警口径见已知差别）（比例 `margin_reduce_ratio`，现货和合约同比例）。组合上记两列状态：暂停来源（`c_pause_source`：`USER` 人工、`SYSTEM` 系统自动、`MARGIN` 保证金率风控）和减仓状态（`c_margin_reduce_state`：`REDUCED` 已减仓、`PENDING` 减仓待执行、`UNREDUCED` 没有减仓已回安全线、`FAILED` 减仓失败、`PARTIAL` 只减了一部分，只在来源是 `MARGIN` 时非空），风控的判断、条件更新和关注项详情都只看这两列；暂停原因是按减仓状态取的固定文字“自动暂停：保证金率过低…”，只用于展示，不带比值（暂停原因会作为 `auto_paused` 告警的详情上报，带变化的数字会让每次触发产生新的指标序列），来源是 `MARGIN` 的暂停同时算系统自动暂停，进入已有的“组合账户自动暂停”告警；比值只写日志。同时只要暂停来源还是保证金风控，`margin_ratio_low` 关注项就持续上报（按库里的状态推出，不带时间窗口），详情是固定文字（带减仓状态，见下文），用户恢复后消失。减仓动作发出之后才写日志；有下架清仓在跑、减仓排不进去时先把组合暂停停住，下一轮再补减仓。减仓结束后，普通账户把现货钱包的 USDT 归集回合约钱包（用执行器的钱包划转，见第 11 节；风控划转没有目标，`target_id` 为空串，归集接口带这次风控事件的幂等键——风控减仓的动作号 `margin-<组合>-<时间>`，必须按它做幂等，不能只按（组合、空目标、方向），否则第二次风控事件的归集会被当成已做过）。是否归集只看组合最近一次风控减仓动作：动作还在跑就等，动作之后组合恢复过就不再为它归集，其余都归集；不看暂停状态（撤单、外部订单或成交、人工下单、手动暂停都会改写它）。这个动作是否已经归集完成、是否被交易所拒到放弃，由归集实现按引用号查全部划转记录得出（不限 24 小时窗口，重启不丢）；监控进程内只缓存“已处理”以省掉每分钟重复查余额，不作为判断依据。

不会重复触发：整组清仓、减仓在跑时这一轮不叠加（人工单、撤单这类动作不挡监控）；上一次风控减仓之后，组合要恢复过（用户确认安全后手动恢复）才会再触发（自主下单组合没有恢复这一步，上一次减仓结束后照常判断），用户在暂停期间人工下单、撤单、清仓会把暂停来源改成人工（`USER`）、清空减仓状态，比值仍低也不会再自动减一次。“恢复过”记在库里（`t_logical_accounts.c_resumed_at`，每次从暂停恢复自动执行时写入），Trade 重启不丢；人工暂停的组合、历史上有过风控减仓但之后已恢复的组合照样监控。风控先把组合暂停、减仓还排不进去（有下架清仓在跑）时，减仓状态记 `PENDING`（原因写“减仓待执行”而不是“已减仓”，`margin_ratio_low` 照报），下一轮（含重启之后）会把减仓补上，补上后换成 `REDUCED`；补上之前保证金率又回到安全线，减仓不会再做，换成 `UNREDUCED`（原因写“没有减仓、等待确认后恢复”，仍算保证金风控暂停）。减仓动作发起时写入 `REDUCED`（由风控把这个暂停状态随减仓动作传给清仓流程，清仓流程不解析原因文字），其余改写都是条件更新：只有组合当前的暂停来源与减仓状态仍是风控读到的那个（`MARGIN` 加 `PENDING`，或仍在自动执行）才改，用户在此期间恢复或人工暂停就不覆盖。风控减仓结束状态是 `FAILED` 或 `PARTIAL` 时，减仓状态如实改成 `FAILED`／`PARTIAL`（原因写“风控减仓失败／只完成了一部分，请检查持仓后手动处理”），`margin_ratio_low` 的详情也带上减仓状态（待执行、没有减仓、失败、部分完成），减仓失败或部分完成时同样归集（归集不看暂停原因）。普通账户的总权益填了但不大于 0 时，有合约持仓就触发；没就绪的账户这一轮不判断，但快照太久没更新的告警照发。动作号 `margin-<组合>-<时间>`。

### 5.3 收益拆解

`SummarizeAccountPnl`（按组合或单个执行账户、时间范围默认近 7 天）：手续费、已实现盈亏和成交笔数从成交表与小时汇总表（`t_order_fill_hourly_summaries`，历史订单清理删掉的成交在这里）一起汇总：区间两端先对齐到整点（起点向前取整、终点延到所在小时末，资金费也用对齐后的区间），一条 `UNION ALL` 语句读区间内的原始成交和整点落在区间内的汇总行，每笔成交只在其中一处，直接相加，清理前后结果一致（十进制累加，手续费**按手续费资产分别汇总，不折算成结算币**，已实现盈亏按结算资产，只来自合约成交，现货成交的已实现盈亏记为 0）；资金费：模拟盘直接按资产汇总本地资金费记录（见第 6 节，十进制累加、不经过流水翻页，不截断；OKX 模拟盘不结算，`funding_note` 写明），实盘从交易所流水即查（每个有永续的实盘执行账户翻页取 `FUNDING_FEE`，最多 5 页、共用 11 秒期限，按流水号去重；多个账户都没取完时，统计起点取各账户已取到的最老时间里最晚的一个）。时间范围最长 90 天（请求校验限制，成交汇总逐行读成交表，不放开）；翻页没取完、有账户流水查不了时 `funding_truncated` 为真并写明 `funding_note`；所有账户都没有永续或都查不了流水（没有流水接口、会话没建立、查询失败），又没有带永续的模拟账户时 `funding_available` 为假。

## 6. 订单与交易所

- 公共数量统一使用基础资产数量，交易所适配器负责合约换算。
- `FillPolicy` 支持 `GTC`、`IOC`、`FOK`；`ReducePositionOnly` 由服务端根据已确认持仓推导，
  调用方不能设置。
- 状态为 `SUBMITTING` / `SUBMIT_UNKNOWN` 的订单先用相同的 client order ID 查询交易所，禁止盲目重发；
  成功但非 OPEN 的下单响应立即触发轻量同步，回执里的累计成交量写入观察成交量并关闭准入。
- 退回待提交后才到的交易所证据由成交 Reducer 统一处理（私有流和 REST 同步都经过它）：待提交的订单收到它的成交，先认领成挂单（记下交易所单号）再入账；
  收到“已撤销”直接结束为已撤销（部分成交的为部分撤销）；已经结束的订单收到“交易所已不存在”不再迁移。
  对提交结果未知的订单不能直接撤单，要先解析（查到就认领，查不到退回待提交再丢弃）；资金维护（BNB 补买、稳定币调平）的系统单照同一写法处理，
  停在待提交的旧单丢弃，不会让补买一直“忙”；BNB 补买在某一轮解析过提交结果未知的旧单，这一轮不下新单（解析出的成交还没进账户快照），下一轮再算缺口。
- 交易所查不到原单（已归档）而只有成交时，同步按成交合成外部订单（订单号前缀 `synthetic:`），数量是已知成交之和；后到的成交使已入账成交量超过数量时（订单已成交、部分成交或部分撤销都一样），数量放大到已入账加本笔，状态按新数量重新推导。
  普通订单的数量是下单时定的，成交超量仍是非法迁移；单笔成交入账失败不隔离，账户保持未就绪，记关注项 `fill_ingest_failed`。
- 限流统一由 `httpclient` 处理：418、币安的 429、WAF 403 按域名暂停全部请求；OKX 的 429（按接口和用户限频）和 -1015、-1008、OKX 50011 只暂停该账户下单，而且只有下单请求被限流才暂停，查询被限流不影响下单；暂停期间本地直接拦截、不发请求，也不在请求内等待。确定未受理的下单回到待提交，不算拒单。会话重连等暂停结束；暂停期间跳过 listenKey 续期。
- 交易所适配器：Binance、OKX（client order ID 用 `xid` 生成并校验格式）；A 股、港股只有公共行情适配器（`exchange/ashare`、`exchange/hkex`，通用实现在 `exchange/stockfeed`），下单由模拟撮合执行，见下面的“A 股模拟盘”。
- 模拟盘使用公共行情做简化撮合：市价单按下单时的卖一/买一加滑点成交；限价单下单当时能立即成交的按 taker 成交，
  价格是当时的卖一/买一加滑点、但不比限价差；否则 GTC 挂单在行情穿价后按 maker 费率、以自己的限价成交
  （和真实交易所一样，挂单被对手吃掉时拿不到比限价更好的价格），IOC/FOK 无法全部立即成交则整单取消。
  不模拟盘口深度、排队和部分成交。
- 模拟账户的余额记在 `t_paper_asset_balances`（按资产一行）：建账户时在同一个事务里写入结算资产的初始资金，之后只改不删，
  所以“余额已初始化”就是“该账户有余额行”，没有单独的标记表。
- **模拟盘不拆成独立的模拟交易所**：模拟账户与实盘账户共用订单表、成交表和执行流程，只把下单、撤单换成本地撮合。
  这样模拟盘直接得到执行器、清仓与减仓、人工下单、目标收敛等全套逻辑；拆成独立交易所要再造一套订单与余额状态，还要和 Trade 同步，
  多出来的是两份状态和它们之间的对账，没有换来新的能力。
- 模拟盘永续资金费（第一版只做币安；OKX 不结算，也不做爆仓）：
  - **来源**：模拟盘绑定的币安公共行情实现可选能力 `execution.FundingRateSource`，调公共接口 `GET /fapi/v1/fundingRate`（不带 symbol、不签名），一次取回时间窗内全部合约的结算记录（`fundingTime`、`fundingRate`、`markPrice`）。按 4 小时分段请求，满 1000 条就对半拆开重查，同一毫秒就超过 1000 条时报错，不把截断的结果当完整结果。只严格解析要结算的合约，它们格式不对就报错；其他合约格式不对的记录只记日志跳过。同时开现货和永续的账户由组合适配器路由到永续。
  - **结算时刻的持仓按成交推**：模拟盘持仓只由本地撮合成交投影，成交和持仓在同一个库里（停掉 Trade 后删 `<部署根>/data/trade` 时一起清），所以结算时刻 T 的持仓 = 当前持仓减去 T 及之后（含同一毫秒）的永续成交，严格早于 T 的成交才算在持仓里。停机期间的结算点也能补算，不需要整点取持仓快照。
  - **金额与入账**：金额 = −持仓数量（多为正、空为负）× 标记价格 × 费率，记入账户的结算资产，不取整。记录写进 `t_paper_funding_fees`（账户、合约、结算时刻、费率、标记价格、持仓、金额、资产；唯一键是账户、合约、结算时刻），插记录和改余额在同一个事务里，余额改动按资产累加后每个资产只写一次；唯一键冲突就不插也不改余额，重复结算是幂等的。持仓为零的记录跳过。`markPrice` 为空的记录按时间处理：结算时刻距本轮截止时间 6 小时以内，这一段只入账不晚于缺价那一期的记录，进度停在那一期，每分钟重查，交易所补上价格后这一期结算一次；超过 6 小时仍缺，先取同一合约在本段里时间最近的有价记录（前后都算）的标记价格，没有就取交易所现在的参考价（多半是现价，和结算时刻的价格有偏差，是已知的近似），并打 Warn 日志；连参考价都取不到就跳过这一条（Warn），不让整轮失败。
  - **触发**：模拟盘会话在单独的协程里每分钟检查一次，启动时先跑一次。只结算 1 分钟前的结算点（等撮合在那之前定好时间的成交落库，也等交易所公布）；同一个整点只查完一轮，过了下一个整点从上一个整点起回看。重启后的起点是表里最大结算时刻所在整点的前一个小时（同一整点里还没结算的合约也能补上，已结算的靠唯一键去重），最早不超过 7 天前，即 Trade 停机后最多补算 7 天。没有永续持仓的时段不查。按不超过 4 小时的段依次查询、入账，每段入账后推进内存里的进度；中途失败只重做没入账的那几段，失败后退避（1 分钟起翻倍，最长 30 分钟），不影响账户就绪。
  - **流水与收益**：模拟盘的资金流水在成交推出的手续费、已实现盈亏之外，再由这张表推出 `FUNDING_FEE`（类型原文 `PAPER_FUNDING_FEE`，说明里写费率、标记价格、持仓）；查现货时没有资金费。成交和资金费各取一页再合并，哪一路没取完就按那一路已取到的最老时间截断。收益拆解不走流水，直接汇总这张表。停掉 Trade 后删 `<部署根>/data/trade` 时这张表一起清空。

### 已知差别

- OKX 查单返回空数组时，错误不带错误码，这种单会一直停在结果未知，不再自动重发（未知订单恢复只认 -2013、51603 这类明确的错误码）。
- 逐仓标的上的外部成交（含逐仓强平）会被当作全仓持仓短暂投影，下一次同步后删除，此时组合已暂停。
- 币安标的保证金模式按标的设置：逐仓持仓还在时用户恢复组合，下一轮下单可能直接加进逐仓仓位，之后同步再次暂停。
- 伪市价永续开空、加空时，下单量贴着最小名义金额，容量预检按限价算名义金额会得到 0，阻塞原因写成“成员容量不足：…没有可用资金”（实际是低于最小名义金额）；有阻塞原因，不会静默。
- 按可用资金截量后的下单量可能低于设置的最小下单额（`min_notional_*`），这一单照常下，不再回头补。
- 股票组合把 `order_mode` 设成 `MARKET` 时目标执行器直接下市价单，不经过涨跌停、价格笼子与港股价位表的对齐；默认是伪市价单（`PSEUDO_MARKET`，限价 IOC），股票只有模拟盘，不要改成 `MARKET`。
- 单笔上限可以设得低于交易所的最小名义金额；这时高于最小数量、低于最小名义金额的开仓单被校验器拒绝，阻塞原因文案只说“低于最小名义金额”，不点明是单笔上限设置过低，需要用户自己调高。
- 超过 24 小时的未结划转不再被自动对账：它是某次归集自己的记录时，这次风控归集或目标归集会一直等它，需要用 `ResolveWalletTransfer` 人工结束（见第 11 节）；别的目标、别的风控事件留下的不挡新的划转和归集。
- 风控减仓、清仓连续零成交或本地拒单最多 20 笔后终结，两笔之间间隔约 200 毫秒，持续不成交时很快用完，需要人工处理。
- 普通账户的 BNB 补买只把现货钱包补到保留金额的一半；合约侧的 BNB 抵扣要用合约钱包里的 BNB，要用就自己放进合约钱包，不会自动划转。
- 模拟盘资金费的结算记录缺标记价格时，先等（最长 6 小时，进度停在这一期，下一轮重试）；超过 6 小时仍缺，改用同合约前后最近一条有标记价格的记录，没有就取交易所现价结算并打警告日志。这个参考价多半是交易所现价而不是那一期的标记价，金额有小幅差别；连参考价都取不到时跳过这一期。
- 币安把裸 HTTP 404 归为“订单不存在”，但未知订单恢复只认明确错误码（-2013、51603），其余调用方保持现状；传输错误的文本里含带签名的请求地址，签名只能在 `recvWindow` 内重放同一个请求，日志只在本机。
- A 股快照里缺某只股票时返回旧缓存，由上层的报价时效检查兜底；停牌股票本来就不交易。
- 撤单受理后读本地账户失败时直接返回错误，订单停在“撤单中”，等同步确认；实盘撤单的正常路径本来就停在“撤单中”。
- 订单同步会对待提交的订单也查单，多耗少量权重；退回待提交的订单查到成交也会被认领。
- “持仓未反映成交”的判断用精确相等，需要外部干预才触发，失败方向是继续等待。
- 目标历史清理后 SQLite 库文件不会自动缩小：清理前已经涨上去的空间留在库里给之后的写入复用，文件不再继续增长；要收回空间需停 Trade 后做一次 VACUUM。
- 模拟账户的订单与成交明细只保留结束后若干天（模拟账户配置的 `order_retention_days`，默认 5 天，可随时改，0 表示不清理）：更早的订单列表、成交列表、人工操作和目标对应的子单都查不到了；模拟盘资金流水里成交产生的条目也只剩保留期内的（更早的只有资金费）；超过保留期再用同一个动作号重放人工下单、撤单动作会报找不到子单，而不是返回原结果。收益不受影响：收益曲线只读净值点，资金费在单独的表里，收益拆解（`SummarizeAccountPnl`）的手续费、已实现盈亏和成交笔数靠小时汇总永久保留，统计区间两端对齐到整点（比请求的区间最多宽出不足一小时）。模拟资金费补算要读的成交不会被清理（已有结算记录时清理边界不晚于补算起点；账户从没结算过资金费、保留天数又小于 7 天时，超过保留期的成交照常清理，补算回看到的这段持仓不准）。天数改大找不回已经删掉的明细。按目标查全部子单的逻辑（伪市价重试次数、反向熔断、挂单结束后改吃单）在目标活过保留期时（例如周线策略）会因旧子单被删各重置一次，多一轮重试或挂单，不影响收益记账。首次上线或长时间停机后积压很多时，一轮（最长 5 分钟）删不完，每小时会记一条“历史订单清理有失败”的关注日志直到删完，期间交易写入会多等一点。实盘账户的订单与成交不清理，单量大的话库还会涨。清理后库文件同样不缩小（见上一条）。
- 标的汇总的数量与成本按成交入账的顺序累计，不按成交时间重排：模拟盘的成交按时间顺序产生，没有差别；实盘成交乱序到达（私有流与 REST 补拉交错）或同一毫秒有多笔时，均价可能与按成交时间重放略有出入（实盘持仓页不显示均价，只影响内部记录）。数量归零时成本直接归零，不留除法的尾差。受管按（市场，代码）认标的，不再要求订单带标的 ID。
- 净值点不清理（约每分钟一个，一年约 52 万行，查询已按时间范围分桶降采样）；订单列表只按执行账户过滤时没有带 `c_ctime` 的索引（按组合列有）、`ListOrdersForLane` 没有上限，单用户订单量下无影响，实测变慢再加。
- 模拟成交价不按价格步长取整，A 股费用不取整到分，误差在分以下。
- 会话 `Run` 提前返回时不等订阅协程；成交入账幂等、订单按时间戳防回退，后果有限。
- 轮询会话的内存就绪标志只升不降，重连对账错误只记日志；持久化的准入字段会关闭，不受影响。
- 资产名大小写按原样比较：资产名原样取自交易所，交易所返回本身是大写。
- 终态判断有多余的一层、部分查询是 N+1，单用户规模下无影响，碰到相关文件时再删。
- 流水按截止时刻翻页时，同一毫秒的记录可能读不全；现货 `SettlementAsset` 的含义未改动，只在注释里说明。
- 前端操作跟踪每 1.5 秒轮询一次，不看页面是否隐藏，只在动作进行中轮询。
- 测试连接的结果可能显示到另一把密钥名下：要在检测进行中关掉弹窗再打开另一把密钥才会出现。
- 订单页签的后台轮询顶掉前台查询时，失败不提示，下一次轮询自愈。
- 加入组合弹窗里的执行账户固定取 200 条；弹窗在请求中关闭时不刷新列表，手动刷新即可。
- 权重换算读标的失败（数据库错误）会被当成该成员不支持这个标的，消息已区分为“读取标的失败”，行为不变，目标会重投。
- 风控归集：动作结束超过 24 小时且没有归集记录则不再归集；24 小时内重启可能对同一动作再归集一次（同账户内划转，把期间手动放进现货的 USDT 划回合约）；放弃归集的告警每个进程一次。
- 下架清仓和 A 股限价清仓的尝试序号按全部已结束子单计，持仓快照滞后时可能按旧数量再发一笔：永续有 reduceOnly，现货与 A 股有本地资金校验挡着，最多多一笔被拒的单；加密市场清仓、减仓只数零成交子单。
- 一笔查单一直给不出明确结论的“提交结果未知”挂单（例如 OKX 查单返回空数组），会挡住该组合后续目标的撤旧单阶段、过期释放、该账户的清仓与风控减仓。提交满 10 分钟后，在订单上人工撤单会把它强制结束（记为已过期、释放预留，不向交易所发请求）；它若其实已在交易所成交，持仓由账户同步的快照纠正。自动流程遇到这种单仍然等待，不会自行结束它。
- 持有的标的在标的表里不是可交易状态、又没进下架名单时（交易对临时暂停、维护等），这笔持仓本轮跳过、不下单，其余标的照常执行；只打一条日志（同一组合、账户、标的每天一条），不告警，资金一直占着，标的恢复交易后照常收敛（见第 4 节）。
- 下架清仓、整组清仓、风控减仓运行期间反复占用组合锁（每次最多约 8 秒），同组合其他标的和排在后面的组合收敛会变慢，不会下错单。
- 账户里本地标的表之外的合约（USDC 本位、币本位、交割合约）的全仓持仓、挂单、成交不读入，也不会因此暂停组合；它们的未实现盈亏仍随账户快照计入权益。逐仓持仓照常上报并暂停组合。
- 自主下单组合不会被风控减仓或清仓暂停：保证金率持续不高于阈值时，上一次减仓结束后每分钟再按比例减一次，每次都会先撤掉组合的全部挂单；持仓太小、按比例减不动时一小时内不再发起，只打一条日志提示手动处理。`margin_ratio_low` 只在减仓进行中或结束不到 5 分钟时上报。资金维护（BNB 补买、小额兑换、稳定币调平）不看暂停状态。
- 普通账户同时有现货和永续时，风控减仓卖现货得到的 USDT 在下一轮开头才归集，这一轮判断用的是归集前的快照，自主下单组合可能因此多减一次。
- 加入组合前就挂着的外部单在启用成员时归到本组合；这笔单加入之前已有的部分成交，会一起算进组合的成交汇总和盈亏。
- 统一账户 papi 查不存在的单是否返回 -2013 还没核对，开实盘前要在小额实盘里核对（见第 13 节冒烟清单）。
- 撤单请求刚发出、交易所还没处理时进程被强杀，这笔挂单在本地会一直停在“撤单中”，之后的目标停在撤旧单阶段；人工撤掉这笔单或清仓即可解开（只在开了挂单比例时可能出现）。

### A 股模拟盘（场所 `ASHARE`）

- **场所**：`ASHARE`（界面名“A 股”），只开股票（`STOCK`）、按 CNY 结算；建账户时按场所校验市场和结算资产（BINANCE、OKX 不开股票），模拟账户和实盘账户共用 `execution.ValidateAccount`。执行方式与环境：PAPER 由 Trade 内的模拟撮合执行；LIVE 的 TESTNET（QMT 仿真账户）、PRODUCTION（QMT 实盘账户）留给 QMT 执行端，接入前建账户和绑定都报“A 股实盘要通过 QMT 执行端下单，QMT 执行端尚未接入”。
- **行情**（`exchange/ashare`，快照缓存、标的列表刷新、只读适配器的通用实现在 `exchange/stockfeed`，抓取与解析在 `packages/cnstock`）：只用腾讯实时快照 `qt.gtimg.cn`，按需拉取（换算目标、模拟盘估值前批量预取，一次最多 60 只；撮合时取有挂单的标的），同一标的 2 秒内复用，网络类取价失败（超时、错误状态码、限流）也记 2 秒（时间按请求返回后算；这期间单只取价直接返回同一个错误，腾讯故障时不会逐只等超时）；某一只的行格式不对只跳过那一只并记日志，按取不到报价处理，整个进程共用一份缓存。快照带现价、昨收、买一卖一、涨停价、跌停价（绝对价）和停牌标记；停牌（含退市）的报价按取价时刻、以昨收计，不判过期。腾讯取不到时 A 股行情不可用，账户按现有逻辑变成未就绪。
- **标的**：东方财富全部 A 股列表（含科创板、北交所），进程启动时和每天 08:30 在后台刷新，失败沿用已有列表；列表加载完之前用库里已有的标的，库里也没有（第一次启动）时会话稍后重试。标的 ID、交易所代码、基础资产都是 `600519.XSHG` 这种写法，计价、结算 CNY。数量规则按代码前缀：科创板最少 200 股、按 1 股递增，北交所最少 100 股、按 1 股递增，其余 100 股一手；价格步长 0.01 元；没有最小名义金额。停牌不写进标的状态，只在报价上标记。
- **交易时段**：场所目录登记时段对象（`execution.TradingSession`）：市场时段 09:30-11:30、13:00-15:00（按 `packages/marketcalendar` 的交易日历，判断函数在 `packages/barclock` 的 `Hours`）给报价新鲜度、撮合、收盘撤单用；下单时段在 14:57 截止（之后是收盘集合竞价，撤不了单），开盘集合竞价不参与。交易日历不覆盖当天时一律按不在时段内处理，目标原因写“交易日历已过期”。
- **报价新鲜度**：`execution.QuoteFresh` 注入全部报价新鲜度检查点（权益服务的持仓报价、换算参考价、模拟盘估值、降级用的最后已知价、盘口、撮合）：时段内按各检查点自己的窗口；时段外只要求报价时间不早于最近一次休市（11:30 或 15:00）减 5 分钟。时段外有效的报价不拉低权益来源时间。余额、持仓的同步时间仍按 90 秒判断。所以夜间、午休、周末账户保持就绪，15:00 之后到的目标按收盘价换算、写进目标历史，进入 PENDING“当前不在交易时段”，次日 09:30 由 TargetWorker 放行。
- **下单规则**（规则按“场所 + 市场”取：`exchange.RuleFor(STOCK)` 是股票共有的整手、不能卖空、按报价里的停牌与涨跌停判断；`exchange.RuleAt(ASHARE, STOCK)` 再带上 A 股的 T+1、A 股费用、价格笼子价位数。业务代码只看规则，不判断具体场所）：
  - 伪市价 IOC 限价单：价格先截到价格笼子（基准价买入取卖一、卖出取买一，拿不到时用最新价；±2% 和 10 个最小价位取更宽的那个，都按精确值），再截到涨跌停价之间；
  - 单笔上限不足一手时按一手下单（拆单随机化后也一样），高价股一手就超过默认的 10 万元上限；
  - 整手：买入向下取整，不足一手视为已满足；卖出时要卖的不小于全部可卖数量就卖出全部可卖数量（允许零股），否则按整手取整；下单校验允许“卖出后余下的持仓为 0 或满足整手规则”的零股卖单；
  - T+1：模拟盘可卖数量 = 总额 − 冻结 − 当日（北京时间当天）买入成交，下单资金检查在写事务里同样扣掉；只因 T+1 卖不出的部分顺延，原因“当日买入，次日可卖”；
  - 涨停时买（现价在涨停价且没有卖一）、跌停时卖、停牌：顺延，原因“涨停”“跌停”“停牌”；下单校验看到停牌返回 `ErrInstrumentHalted`，执行器同样映射成顺延；委托价超出涨跌停价拒单，原因“超出涨跌停价”；
  - 顺延和视为已满足的部分，`HasDifference` 都不算未到位，和收敛同一个判断；有顺延项时目标在有效期内 60 秒后再收敛一次（停牌复牌、涨跌停打开）；
  - T+1 的数量是“总数 − 挂单冻结 − 可卖”，挂单冻结卖不出的照旧记“可卖量不足”；
  - 不做空、不加杠杆。
- **费用**：`exchange.AShareFee`（经 `RuleAt(ASHARE, STOCK).Fee` 调用）：佣金复用模拟账户的 taker 费率字段（默认 0.025%）、最低 5 元，印花税 0.05% 只收卖方，过户费 0.001% 买卖都收；下单预留（含提交前重新定价）、下单容量（最低佣金让花费和数量不成正比，按步长往下减到付得起）、成交扣费三处都调它。模拟账户配置的 proto 和表不变。
- **清仓、减仓**：和执行器同一个卖出规则（零股一次卖完，只因 T+1 卖不出的部分记“当日买入，次日可卖”并按终结处理：当天怎么重试都卖不了），发限价 IOC（3% 滑点，截到价格笼子和涨跌停价之间）。子单号和下架清仓一样带上尝试次数，零成交结束后换号再下；连续 20 笔零成交或被拒才终结，休市时被撤掉的不算。停牌、跌停（卖出时没有买一）不下单，原因写“停牌，复牌后再卖”“跌停，没有买一，打开后再卖”，按可重试处理，由清仓动作的 30 分钟期限兜底。
- **手动下单**：A 股不在下单时段时直接拒绝，提示“不在交易时段（A 股 09:30-11:30、13:00-14:57）”。
- **加密货币不受影响**：没有登记交易时段的场所，撮合、估值、盘口的报价新鲜度只按各检查点自己的窗口判断（不接受超前的报价时间）。
- **模拟撮合**：时段外不扫挂单，休市前一刻发出、还没撮合过的单整笔撤掉（原因“不在交易时段”，不算一次伪市价尝试），挂着的单留到开盘；停牌或没有对手价时 IOC 整笔撤掉、GTC 继续挂；整笔成交或整笔撤销，不按盘口量部分成交。
- **收盘撤单**（`application/order/session_close.go`，订单层，模拟盘和实盘一样）：每 30 秒扫一遍，日收盘（15:00）之后先全量同步，再把提交时间早于最近一次日收盘、已确认在途（挂单中、部分成交、撤单中）的订单按已撤结束，原因“收盘撤单”。只按日收盘判断，午间不碰上午的挂单；提交结果未知、撤单结果未知的单先走结果不明处理，由下一轮接手；按订单现状扫描、不记进度，重启后自然补做。
- **不做**：除权除息、分红送转、配股，开盘和收盘集合竞价，融资融券、ETF、可转债，A 股下架处理。

- **标的与每手股数**：港股每手股数逐只不同（腾讯 100、汇丰 400、盈富基金 500、小米 200）。数据源是上面那个腾讯实时快照的第 60 个字段——Collector 同步恒生指数成分用的腾讯成分列表接口、取 K 线用的东方财富接口都不带每手股数。
  标的表 = 恒生指数成分（与 Collector 默认采集的港股范围同一个腾讯接口）加库里已有的港股标的（被调出指数的旧成分可能还有持仓），进程启动时和每天 08:30（香港时间）刷新一次：约 5 次成分列表请求加 2 次快照请求。
  **取不到每手股数的标的不收录、不猜**：库里已有的沿用原来的规则，库里也没有的不能下单——目标里出现它时整份目标被拒，原因“没有启用的成员支持标的 xxx（港股模拟盘只收录恒生指数成分里取得到每手股数的标的）”。
  标的 ID、交易所代码、基础资产都是 `00700.XHKG`（与采集、策略一致），计价、结算 HKD；最小数量和数量步长都是每手股数；没有最小名义金额。
- **价位**：港交所价位表按价格分档（`exchange.HKPriceTick`）：0.25 及以下 0.001，0.5 及以下 0.005，10 及以下 0.005，20 及以下 0.01，50 及以下 0.02，100 及以下 0.05，200 及以下 0.1，500 及以下 0.2，1000 及以下 0.5，2000 及以下 1，5000 及以下 2，以上 5。
  0.5～10、10～20、20～50 港元三档比旧价位表细（港交所下调最小价位之后的值：第一阶段 2025-08-04 生效，10～20 港元 0.01、20～50 港元 0.02；第二阶段 2026-08-03 生效，0.5～10 港元 0.005）。各档取值是按 2026-11-17 腾讯报价里的真实价格反推核对的（1.005、8.395、18.81、29.08、68.85、138.5、376.0 等都落在对应档位上），
  没有对照交易所公告原文；交易所再调整价位表时改 `exchange/stock_hk.go` 的 `hkTickBands`。标的表里的价格步长存最小的一档 0.001；
  伪市价单、清仓单的限价按价格所在档位对齐，买入向上、卖出向下（`ExchangeRule.SnapPrice`）。手动下单填的限价不校验价位。
- **费用**（`exchange.HKFee`，常量集中在 `exchange/stock_hk.go`；**按 2026 年公开费率，模拟盘口径**，不是任何券商的实际收费）：买卖都收——
  印花税 0.1%（按成交金额算出后向上取整到元，不足 1 港元按 1 港元）、交易费 0.00565%、证监会交易征费 0.0027%、会财局交易征费 0.00015%、股份交收费 0.0042%（港交所自 2025-06-30 起的收费，没有最低、最高）、
  佣金按模拟账户的 taker 费率字段（建账户页面默认 0.03%）、每笔最低 3 港元。下单预留、下单容量、成交扣费三处都经 `RuleAt(HKEX, STOCK).Fee` 调同一个函数。除印花税外各项不取整到分。
- **交易时段**：取 `packages/barclock` 的 stockhk——09:30-12:00、13:00-16:00，半日市（圣诞前夕、新年前夕、农历新年前夕）只有上午。连续竞价时段内都能发新单（没有 A 股 14:57 那样的截止）；
  16:00 之后的收市竞价不参与。时段外（午休、收市后、半日市下午、休市日）到的目标与 A 股一样：按当时的报价换算、写进目标历史，进入 PENDING“当前不在交易时段”，下一次开盘由 TargetWorker 放行（目标还在有效期内时）。
- **已知差别**：不含开市前时段和收市竞价（腾讯收市后的现价是收市竞价之后的价格，时段外换算目标用的就是它）；碎股不能买，只在卖出全部可卖数量时一次卖完；费率是模拟口径；汇率不换算；
  除权除息、分红送转、供股不处理；退市不处理（退市后腾讯不再返回报价，持仓估值会报行情不可用，超过 90 秒后账户一直不就绪；模拟账户不能停用，要关闭这个模拟账户才能恢复，代价是清空它；
  只收录恒指成分，退市前通常先长期停牌，停牌期间按昨收估值，所以很少遇到）；标的范围只有恒生指数成分，其他港股即使采集了也不能下单；
  停牌只认状态 `S`，其他非空状态含义不明、同样按不能交易处理；市调机制（冷静期）不模拟；
  腾讯整体停更（所有标的都不再更新）时没有单独的判断：报价时间按取价时刻算，港股模拟盘会按停更前的最后价撮合和估值，不报过期（采集的 K 线来自东方财富，不受影响，因子、策略照常）；
  目标换算失败时 Trade 每秒重投一次、没有退避（换算只在拿不到报价时失败，按取价时刻算报价时间之后基本碰不到）；
  影子目标、目标历史里的数量是按权重算出的小数，整手取整在下单时才做；股票组合的持仓用 `moox-cli trade holdings` 看，`trade positions` 只列合约持仓。

### 接入新场所清单

新增交易所或券商时，`application`、`runtime` 不用改：

1. 新建适配器目录，实现 `execution.ExecutionAdapter`，并实现 `ExchangeIdentity`（`Exchange()`）。行情、参考价、标的加载、按交易所单号查询都是必须实现的方法。
2. 按需实现可选接口：有私有流实现 `AccountEventSource`，否则会话每 3 秒同步一次；有杠杆配置实现 `SymbolConfigurer`。
3. 在 `bootstrap.registerBuiltins` 注册工厂和 `execution.ExchangeDescriptor`：可用订单类型、成交策略、支持开通的市场和结算资产、交易时段对象（`execution.TradingSession`，不填表示全天）、实盘是否已接入。凭据校验放在工厂里，账号、网关地址从 `Credential.Extra` 读取。
4. 在 `trade_service.proto` 的 `Exchange` 枚举加一个值，在 `rpc/convert.go` 的 `exchangePBNames` 表加一行。
5. 新市场类型在 `exchange/market_rule.go` 的 `marketRules` 加一行，并同步 proto `MarketType`、`schema/account.sql`（`c_markets`）和 `schema/blocked_instrument.sql`（`c_market_type`）的 `CHECK`。
6. 场所在某个市场上有自己的规则（T+1、费用函数、价格笼子、按价位分档的价格步长）时，在 `exchange/market_rule.go` 的 `exchangeRules` 按“场所 + 市场”加一行；没有登记的就是市场类型共有的规则。
   场所按市场命名（`ASHARE`、`HKEX`），不按券商命名：同一个市场换一家券商不用再登记规则。
7. 股票场所只做模拟盘时不用写适配器：用 `exchange/stockfeed` 的 `Market`（给出快照来源和标的列表来源）、`Session`（给出 barclock 的市场 ID）和 `NewAdapter`，见 `exchange/hkex`。

股票沿用现货模型：持仓放进 `Balances`，`Total` 是持仓，`Available` 是可卖量（T+1 的场所当日买入的不在里面）；一手 100 股直接表示为数量步长 100，港股每手股数逐只不同、同样写成数量步长。不在交易时段时目标保持等待，不算错误，也不暂停。`test/fake_exchange_e2e_test.go` 是完整示例。

## 7. 密钥与环境

实盘默认关闭：启用 PRODUCTION 账户和提交实盘订单都需要显式配置 `live_trading_enabled=true`。
Trade 复用进程级签名网关客户端，以独立 `trade` 身份调用原生 `GetSecretValue(secret_id)` 逐条读取交易所密钥，不列出也不加载无关密钥；SecretMgr 对经网关来的组件调用方只返回类别为 `exchange` 的密钥。
TESTNET 与 PRODUCTION 使用适配器内的固定端点；Binance 分别使用测试网与生产端点，OKX REST 共用 `https://openapi.okx.com`，TESTNET 请求增加 `x-simulated-trading: 1`，私有 WebSocket 按环境区分。

交易所密钥可以在秘密文件 `moox.secrets.toml` 的 `[[exchange_keys]]` 里录入（`config init` 录入页、`config edit`），`setup init` 写进密钥管理：category=exchange，provider 为小写交易所名，固定 ID `exchange-<交易所>-<环境>-<名称>`，passphrase 放进 `extra_config`；`readonly = true` 的密钥再写 `"readonly":"true"`，`loadCredential` 据此拒绝用它建执行账户（例如 Collector 检测币安现货下架读的 `exchange-binance-production-readonly`）。写入只建不改，换密钥以管理台为准，已在管理台删除的密钥不重建。`setup init` 只写入、不检测（它排在 Trade 部署之前），Trade 部署后用 `moox-cli trade inspect-credential` 逐把检测。

## 8. 生命周期

- **生命周期**：只有模块级的运行、暂停、恢复追赶（见[总体设计](../总体设计.md) 7.5）。就绪判定（数据库、EventBus、账户会话、各工人）不改变生命周期，恢复追赶放行前要它通过。
  就绪判定不通过时 Monitor 报未就绪、系统恢复不放行 Trade，所以人工操作的工作线程按动作隔离：单个动作恢复失败、而且只关乎这个动作（账户、交易所侧的错误，`operatorapp.ActionScopedError`）时只记在 `/healthz` 的
  `operator_action_errors` 里，不让 `operator_worker_ready` 变假；列不出运行中的动作、或掺着数据库等共享故障的才不就绪。接口是 TradeConsoleService 的 `GetLifecycle`、`ControlLifecycle`（写只给 moox-cli），模块状态随指标上报带给 Monitor，同其他模块。
- **暂停与恢复**：暂停同时关闭**目标接收**（真实目标不被接收，也不被销毁：延迟重投，放开后照常接收，已过有效期的按过期终止——策略暂停前刚发布、暂停期间才送到的目标因此不会被静默终止；影子目标只是记录，照常接收）和**订单执行**（`TargetWorker` 不再收敛目标），并等在途的收敛（订单提交）结束才算停下；**不撤单、不平仓**，回报与账户对账照常。
  门禁看「是否被有意停下」（暂停、恢复追赶），不看就绪检查，所以就绪抖动不会让 Trade 丢目标。
  恢复先进入追赶：每个启用的实盘账户最近一次交易所对账在 2 分钟内、已就绪、无错误、余额已确认，并且没有目标在收敛，才算追平；暂停前未收敛的目标不强制过期，按各自的有效期自然过期。
  Strategy 对追赶或过期周期成功求值时只保存规则状态，不发布新目标；这与 Trade 已收到、随后过期的旧目标不同。策略理论状态推进不表示实际账户已成交，也不会由 Trade 补执行这些历史周期。

## 10. 告警

Trade 每 30 秒扫描一次需要人看的情况，上报关注项 `moox_attention_active`（种类、中文名与级别声明在 `internal/telemetry/attention.go`），Monitor 生成 `attention:trade:*` 检查并发告警：目标被拒绝、组合账户自动暂停、目标持续阻塞超过 1 根 K 线、执行账户持续未就绪超过 2 分钟、连续 3 个目标过期且有差额、同一目标内反向下单（`target_reversal`）、交易所接口限流（`rate_limited`）、1 小时目标单成交额超过目标变化所需成交额的 1.5 倍再加权益的 5%（`turnover_high`；组合 1 小时内暂停、恢复或改过设置时不判断）、1 分钟内结果未知超过 5 笔（`unknown_results`）、实盘账户保证金率跌破阈值（`margin_ratio_low`，风控已暂停组合并减仓，等用户确认后手动恢复；自主下单组合只在减仓进行中或结束不到 5 分钟时上报）、交易账户密钥检测发现阻断项（`inspection_blocked`）、密钥复查连续 6 次没有检测成功（`inspection_failing`）、普通账户合约钱包可划转资金不足导致现货买入被缩小或挡下（`transfer_shortfall`：每份目标的事件，加上每轮扫描从当前目标状态推出——目标 BLOCKED 且带着资金不足的项就持续上报，文字固定，不依赖时间窗口）、钱包划转或归集出问题（`transfer_failing`：连续失败、划转前的查询持续失败、未结划转超过 10 分钟）、受管资产取不到价（`valuation_degraded`：按最后已知价、最近一笔成交价或 0 计了权益，规则见第 4 节受管资产；标签只带账户、资产和降级方式的固定文字，不带数量和价格）、清仓一族动作结束时有子单没收拾掉（`flatten_orders_unsettled`：收尾满 30 分钟仍解析不出或标的已不存在，子单号在动作结果和 Trade 日志里）、过期目标（含停用策略后关闭会话缩短了有效期的目标）的挂单连续撤不下来超过 10 分钟（`release_orders_stuck`：执行器的过期路径仍在每 5 秒重试，撤下来即消除；规则见第 2 节）、成交没能记进本地账本（`fill_ingest_failed`：只记关注项，详情带订单号、成交号和原因，账户保持未就绪，不隔离这一笔）、同步发现订单的标的已下架（`orders_instrument_gone`：未结束的单按过期结束，成交缺口按已入账值收掉；要人工到交易所核对这笔单实际成交了多少，单号在关注项详情和 Trade 日志里，按过期结束的还写在订单原因里）、下架处理（`delist_detected`、`delist_failed`，见 5.1）、交易所账户里有逐仓持仓（`isolated_position`：该持仓不入投影，所在组合已暂停；约 5 分钟窗口内每次同步刷新，逐仓持仓平掉后消失）、下单或查询遇到时间戳超窗（`clock_skew`：币安 -1021、OKX 50102，本机时钟与交易所相差过大，检查 NTP；订单仍按结果未知处理，约 5 分钟后自动消失）。同步持续失败走已有的余额同步检查。

下单量指标只在本地 Prometheus：`moox_trade_orders_total{account,result}`、`moox_trade_cancels_total`、`moox_trade_order_notional_total`、`moox_trade_reversals_total`、`moox_trade_target_child_orders`、`moox_trade_rate_weight_used`、`moox_trade_rate_pauses_total`。

交易所接口说明见 `modules/trade/docs/exchange-apis.md`。

## 11. 普通账户钱包划转与归集

币安普通账户的现货、合约是两个钱包，USDT 平时放在合约钱包。执行器的第 4、6 阶段由 `application/wallet` 处理（经 `target.NewWalletTransfer` 接入）；统一账户、OKX、模拟盘不划转。划转只在同一个账户的两个钱包之间进行，没有提现和跨账户路径。

- **第 4 阶段（现货买入前）**：划转金额 = max(0, 现货买单名义总额 × 1.02 − 现货钱包可用 USDT)，不超过合约钱包可划转额度 × 0.99。可划转额度取合约资产的 `maxWithdrawAmount`（官方说明：最多可转出），不是可用余额。划转前现查两个钱包的余额。现货钱包够用就直接放行。
- **额度不足**：划转金额被合约钱包可划转额度封顶（小于需要的金额）时，记录上打“封顶”标记；封顶的划转完成后，这个目标不再追加，只把现货买单按“本轮能用的资金 ÷ 本轮需要的资金”缩小（比例和缩小后的数量都向下取到 8 位小数，每轮重算、不累计；`blocked_targets` 记缩小前的原始差额；缩小后低于最小下单额的也记 blocked，不当作已满足），告警每个目标一次。没封顶的划转完成后如果仍缺 1U 以上（比如价格上涨），再划一笔差额，不告警；缺口不到 1U 起划额时，现货钱包已经够付买单的名义金额（不含 2% 余量）就不缩小，不够只缺一点就按 1U 划转，不会为了不到 1U 的缺口把买单缩得下不了单；同一个目标往现货钱包最多划 3 次，防止余额口径异常时一直追加。划转被交易所拒绝或连续失败 3 次，这个账户的买入比例记为 0，原因写进目标的 `blocked_targets`，不影响同组合其他账户，也不会让整轮收敛报错。
- **先排除本来就不会下的买单**：调用钱包之前，先按缩小前的原始差额判断——低于设置的最小下单额，或交易规则下下不了单且已有同向持仓（零头）的现货买入，视为已满足，不下单、不计入划转需求（不为不会下的单划转资金，缺钱时也不判 BLOCKED）；因为非资金原因注定下不了的买单（交易规则、所有成员在本目标都拒过单、同目标反向次数已满、伪市价次数用满），用下单前的试算（`placeActionMode` 的 dryRun）排除，直接记非资金原因的 BLOCKED，不划转（否则先划进现货钱包、再归集回去、再划进来，钱停在现货钱包）。兜底：这个目标已经把现货钱包多出来的资金归集回合约钱包后，不再往现货钱包划，只按现有资金缩小。试算先看全部成员（下单时会换成员），再看要划转的这个账户：首选成员自己下不了单、别的成员能下，就不为首选成员划转，下单照常换成员；试算遇到目标过期、会话变化、还没生效这类目标级错误原样返回，不先划转。单币每小时上限已经用完时买单顺延到下一个整点，不为它划转（划进去这个小时也买不了），已有的现货资金也不归集；“持仓未反映已成交子单”这种暂时状态下同样不归集。剩下的买单如果缩小后太小，一律记 BLOCKED 和缩小前的原始差额，不走“已有同向持仓就算完成”的跳过；差额本身够下单只是没钱，是真实的资金缺口，记 BLOCKED。这类缺口只发 `transfer_shortfall`，不发 `target_blocked`。
- **归集只让位给在等资金的买单**：账户有现货买单被每小时上限顺延、在等划转、或因合约钱包可划转资金不足被缩小或挡下时不归集；被拒单、反向次数超限等非资金原因被挡的买单用不上资金，不拦归集。
- **软失败不阻塞**：限频、本地限流暂停（请求没有被受理）和“对账宽限期后交易所记录里没有这笔划转”不计入连续失败。限频这类软失败让这个账户按退避等待后自动重试（目标保持收敛中，`blocked_targets` 里用“顺延”显示原因，类别是中文）。
- **按账户等待**：划转、对账、等快照、失败后退避，都只挡对应账户自己的现货买单；同组合其他账户（包括 OKX、统一账户）的买单照常下。只要还有账户在等，目标保持收敛中，不归集、不定终态。
- **没有幂等键怎么防重复**：币安的万向划转接口没有客户端流水号。先写一条 PENDING 记录再请求；请求超时或进程崩溃后，按请求时间、方向、资产、金额对账交易所的划转记录，认领到就记流水号，宽限期（1 分钟）内查不到不下结论，过了才作废重试。发起新划转前先对账这个账户所有未结的记录（不论哪个目标），有未结的就等待。查不到交易所记录、查不到余额时按账户指数退避（1 秒起，最长 30 秒）：钱包服务记着每个账户“下次可以请求交易所的时间”，目标每秒收敛一次，退避期内直接返回等待，不请求交易所；连续 5 次告警。未结划转超过 10 分钟会告警（关注项标签是固定文字，划转编号、金额只写在 Trade 日志正文里），从日志里取到划转编号、核对交易所划转记录后，由用户确认，用 `ResolveWalletTransfer`（`moox-cli gateway call trpc.moox.trade.TradeConsoleService ResolveWalletTransfer --data '{"transfer_id":"…","result":"COMPLETED"}' --yes`，没到账填 `FAILED`）人工结束这条记录；只处理超过 10 分钟的未结记录，已经结束的原样返回。Agent 不代用户判断到账与否。
- **划转完成后等现货钱包快照**：现货钱包的存储快照更新时间不早于划转的完成时间（交易所记录的时间）才放行买入，等待最长 2 分钟。重启后从划转表接着走。
- **第 6 阶段（归集）**：目标执行完后，现货钱包多出来的 USDT 划回合约钱包。现货钱包留 1U，开启 BNB 保留时再留 BNB 补买所需（保留金额的一半减去现货钱包 BNB 的市值，与补买目标同一口径）；资金设置或 BNB 价格取不到时不归集并告警。多出来的低于 max(100U, 权益 × 1%) 不划，避免 1 分钟级策略每期来回划转。每个目标最多归集一次，归集是收尾动作，失败只告警、跳过。本目标里还有现货买单在等资金（被每小时上限顺延、缩小后太小、资金不足被挡、还在等划转）的账户不归集，否则刚划进现货钱包的资金又被划回合约钱包，剩下的买单再也买不了。
- **风控归集**：保证金率监控触发后的归集（`CollectForRisk`）没有目标，划转记录的 `target_id` 为空串；一次风控事件由幂等键标识（风控减仓的动作号 `margin-<组合>-<时间>`），本地引用号写成 `<幂等键>:TO_FUTURES:1`。同一个幂等键最多归集一次（重复调用不重复划转，未结的记录对账到完成）；不同幂等键各自归集，不会被上一次的记录当成已经做过，（账户、本地引用号）唯一约束也不冲突。风控归集必须做成，不沿用目标归集“收尾吞错”的语义：出错（查余额限频、划转没发出、被拒绝）返回错误，监控下一轮重试；账户上有别的未结划转时返回 pending；限频、没到账的软失败记录不算“做过”，重试的本地引用号递增（`<幂等键>:TO_FUTURES:<第几次>`）；被交易所确定拒绝连续 3 次后放弃这次风控事件的归集：告警一次（`transfer_failing`，请手动划转），之后每轮读到同样的记录直接跳过，不再尝试也不再报错。“是否已经归集”“每个目标最多归集一次”都按引用号或目标查全部记录，不限时间窗口；账户上超过 24 小时的未结划转不再被自动对账：它是这次归集自己的记录时，归集会一直等它，需要用 `ResolveWalletTransfer` 人工结束；别的目标、别的风控事件留下的不挡新的划转和归集。
- **资金流水**：`ListAccountLedger` 把已完成的划转合并进返回结果；合约收益流水里已经带的划转（流水号相同）不重复合并。

## 12. 币安统一账户的未核对项（V3 小额实测必须覆盖）

统一账户没有测试网，下面几点只能靠官方样例和用户本人小额实测核对，不能由 Agent 下真实订单：

- 统一账户同时开通合约时，现货买单的本地资金校验用账户级可用资金（含 UM 钱包）。如果交易所要求现货买单只能花杠杆钱包里的资金（需要先 `POST /papi/v1/asset-collection` 把 UM 钱包的资金归集到杠杆钱包），带 `sideEffectType=NO_SIDE_EFFECT` 的买单会被交易所拒绝；目前没有核对，也没有实现归集。
- `GET /papi/v1/margin/openOrders` 不传 symbol：官方文档说明返回全部标的，但限频权重按交易中的标的数量计；SDK 的参数校验却把 symbol 标成必填。只有会话启动、增量同步和手动全量同步按文档说明不传 symbol；30 秒一次的周期对账按“本地未结束订单、持有资产对应的交易对、当前目标里的现货标的”逐个查（传 symbol，权重 5；要查的标的超过 20 个时退回不传 symbol 的全量查询），合约照常列全部。因此没有出现在这些标的里的外部现货挂单，要等会话启动或手动全量同步才发现。实测时核对不传 symbol 的返回和权重消耗，必填的话全量路径也改成按相关标的逐个查询。
- 资金流水去重假定：合约收益流水（`/fapi/v1/income`、`/papi/v1/um/income`）里 `incomeType=TRANSFER` 那一行的 `tranId` 就是万向划转的 `tranId`；如果不是同一个编号，已完成的划转会在资金流水里出现两次（一次来自划转表、一次来自合约收益）。未核对。
- 等现货钱包快照追上划转：用现货账户 `GET /api/v3/account` 的 `updateTime` 和划转完成时间比较。如果划转不会更新现货账户的 `updateTime`，每笔划转后都要等满 2 分钟（`snapshotGrace`）才放行买入；买入前的余额是现查的，只是慢，不会多花钱。未核对。
- 保证金率监控读数（统一账户）：直接取 papi account 的 `uniMMR` 比阈值（币安常见问答：uniMMR = 调整后权益 ÷ 维持保证金，调整后权益计入抵押率、再扣掉挂单浮亏 openLoss；接口文档里 `accountEquity` 是计入抵押率的账户权益、`actualEquity` 是不计抵押率的权益，所以分子对应 `accountEquity`，不是 `actualEquity`，用 `actualEquity` 会读数偏高、漏触发）。`uniMMR` 为空时才退回自己算的 `accountEquity ÷ accountMaintMargin`，它没扣挂单浮亏，有挂单时可能略高于币安的 `uniMMR`。官方样例里几个数字彼此对不上，只是示例填充值。私有事件更新了维持保证金时清掉上一次的 `uniMMR`，监控退回自己算。未核对：V3 小额实测时日志里同时记着交易所的 `uniMMR` 和自己算的值，对照两者是否一致。
- `totalAvailableBalance` 的真实取值（官方样例是空串）。
- papi 权重：适配器按每分钟 6000 估计额度（`papiWeightLimit`，官方没有整体额度原文），只用来算用量比例。实测记录 `X-MBX-USED-WEIGHT-1M` 响应头的读数，以及触发 -1003 时的实际用量，核对 6000 是否合理；`balance`、`account` 的权重官方 SDK 给的是 20。
- 私有流心跳：适配器沿用合约流的 4 分钟超时（`pmHeartbeatTimeout`），假定服务端约每 3 分钟 ping 一次。实测记录统一账户私有流真实的 ping 间隔，确认 4 分钟不会误判断线、也不会太晚发现断线。
- 私有流地址：`POST /papi/v1/listenKey` 取 listenKey 后连 `wss://fstream.binance.com/pm/ws/<listenKey>`（官方 SDK 的默认地址，不是原文）。实测确认能连通，现货（`executionReport`、`outboundAccountPosition`）和合约（`ORDER_TRADE_UPDATE`、`ACCOUNT_UPDATE`）事件都从这一条连接收到，续期 `PUT /papi/v1/listenKey` 不带参数能成功。
- `GET /papi/v1/margin/openOrders` 不传 `symbol`：见上一条，同时记录权重消耗。
- 成交首次拉取 `fromId=0`：`GET /papi/v1/um/userTrades` 和 `GET /papi/v1/margin/myTrades` 首次不带游标时适配器传 `fromId=0` 从头取。实测确认两个接口都接受 `fromId=0`（返回从最早成交起的一页，而不是报参数错误或只回最近一页），之后按“最后成交号加 1”续取不重复。
- 查不存在的订单：`GET /papi/v1/margin/order`、`GET /papi/v1/um/order` 按 `origClientOrderId` 查一个从没下过的单号，确认返回 -2013。适配器的“订单不存在”只认 -2013（以及 OKX 51603），统一账户如果返回别的码，未知订单就一直退不回待提交，下单结果未知的订单会长期停在“结果未知”，需要改认新的错误码。

## 13. 测试网冒烟清单

`cmd/testnet-smoke` 是对接交易所测试网的冒烟工具（`modules/trade/scripts/testnet-smoke.sh`）。`--phase submit`、`recover` 会向测试网下真实订单，要设 `MOOX_TRADE_TESTNET_CONFIRM=YES` 才执行；`--phase facts` 只读核对交易所接口，不写库、不下单。`--market SPOT|SWAP` 选择要跑的市场：币安现货、合约测试网是两套域名和两把密钥，脚本里现货用 `MOOX_BINANCE_TESTNET_SECRET_ID`、合约用 `MOOX_BINANCE_TESTNET_SWAP_SECRET_ID` 各跑一遍；OKX 模拟盘一把密钥（`MOOX_OKX_TESTNET_SECRET_ID`），一个冒烟账户同时开通现货和永续，两个市场分别演练、共用一个库。币安每个市场一个独立的冒烟账户，永续固定 1 倍杠杆。清理只回收测试单自己成交的部分：现货余额和合约持仓都不能低于基线（否则拒绝清理，不去动别人的仓位），合约只减多头、不反手开空。`--phase facts` 的 `--environment` 只接受 TESTNET 或 PRODUCTION。脚本要在部署了 trade 单元的主机上跑：`MOOX_TRADE_TESTNET_CONFIG` 指向该单元的配置文件（没设就跳过）；单笔金额上限现货用 `MOOX_TRADE_TESTNET_MAX_NOTIONAL`（默认 20），合约用 `MOOX_TRADE_TESTNET_SWAP_MAX_NOTIONAL`（默认 250）。

实盘前由用户或维护者执行（配好测试网密钥后，Agent 不执行），在已有的 `cmd/testnet-smoke` 之上追加下面几项。每项都要把交易所的原始响应存下来：能替换 `exchange/binance/testdata`、`exchange/okx/testdata` 里按官方字段集整理或改写的样例就替换（同时更新各目录的 `README.md`），不能替换的在 README 里写明样例来源。
