# 因子（Factor）

Factor 负责因子定义的管理和计算：每当一个采集周期完成，就对相应的源数据集计算已启用的
因子（用表达式定义，由引擎内置的 Go 执行器计算），把结果写入因子结果数据集，供 Strategy 使用。也支持对历史区间发起补算。
表达式引擎的完整设计见[因子表达式引擎详细设计](../计划/因子表达式引擎详细设计.md)。

代码位置：`modules/factor`。同一个 Go 模块构建两个进程。

## 1. 组成与部署

| 进程 | 运行位置 | 职责 |
| --- | --- | --- |
| `moox-factor-mgr` | control 主机 | `FactorMgr` 管理接口：因子定义、计算任务（因子集）、成员、补算任务、状态；维护 SQLite 和结果数据集；通过内部服务 `FactorEngine` 给引擎提供目录、租约和补算任务 |
| `moox-factor-engine` | 操作员机器（只做出站连接） | 消费采集周期完成事件，运行周期流水线和补算任务，写入因子结果 |
| `moox-factor-mgr-cli` | control 主机 | 初始化数据库、导入因子、提交补算、查看状态 |

| 进程 | 端口 |
| --- | --- |
| manager | FactorMgr 原生 tRPC `11403`，FactorEngine 原生 tRPC `11405`，健康 `11414` |
| engine | 健康 `11417`、admin `11945`、metrics `12945`（均只监听本机） |

引擎的网络连接全部是出站的：

| 方向 | 地址 | 用途 |
| --- | --- | --- |
| 引擎 → Access | `<access>:11004`（`access@<主机>`） | 同步目录、心跳、领取和上报补算任务（FactorMgr），读源数据、写因子结果与周期标记（Storage）；两者共用同一个固定 Access 与外部身份 `factor-engine` |
| 引擎 → 控制机 | `tls://<控制机>:4222` | 订阅 `CollectorPeriodCompleted`（`factor-eventbus` 凭据） |

管理端在创建或编辑定义时编译表达式校验；`PreviewFactor` 试算时直接读 Storage、在进程内计算少量标的，不经过引擎，
不写结果。管理端不消费 EventBus。

## 2. 领域模型

Factor 的 SQLite 只有四张业务表：

| 表 | 内容 |
| --- | --- |
| `t_factor_defs` | 全局因子定义：`factor_id`、展示名、表达式定义（spec）与原文哈希、`allow_partial_universe`；类型、输入列、输出列与回看由编译推导，不落库 |
| `t_factor_sets` | 计算任务（因子集）：源数据集、空间、频率、标的范围（全部 / 指定）、结果数据集、状态 |
| `t_factor_set_members` | 定义与计算任务的成员关系，各自独立启停 |
| `t_factor_recalc_jobs` | 补算任务：范围、筛选、进度、结果摘要、执行引擎 |

- 定义指纹 `definition_hash` 覆盖完整计算契约：表达式语义版本（`expr/1`）、编译后的规范程序文本与
  `allow_partial_universe`。只改注释、格式、`let` 名不会改变它，任何影响结果的改动都会改变它。它在读取时派生、不落库，
  随 `FactorDef` 和周期标记的 `FactorPeriodState` 一起下发；Strategy 启用实例时固化它，之后据事件里的指纹判断因子版本是否变化。
  事件层要求指纹非空；升级前先排空出站队列，仍然无法通过校验的旧记录由 Storage 隔离，不会堵住其后的事件。
  `spec_hash` 只代表定义原文（周期标记里沿用 Storage 协议的 `source_hash` 字段名承载它）。
- 计算任务 ID 和结果数据集 ID 由源数据集与频率确定。输出列在 Storage 列元数据里标记为
  `origin=factor`、`origin_id=<factor_id>`。
- 输入列、输出列、类型与回看都由编译推导：表达式里引用的、不是 `let`/`params`/函数名的标识符就是输入列；
  用到截面算子（`cs_*`）的是截面因子。系统列 `subject_id`、`freq`、`data_time`、`series_tag` 不能作为输入或输出。
  回看按周期网格计数（缺失的 K 线是 NaN，严格窗口会让受影响的结果为 null）。
- 加入计算任务时校验：输入列都存在于源数据集且是数值列（int、double），`params`/`let` 不与源列重名，
  输出列不与源列、其他成员的输出或结果数据集里别的因子拥有的列重名。
- 成员加入后为停用状态；`SetFactorMemberStatus(enabled)` 会重新校验、对齐结果数据集的列，
  并原子提交一次补算。停用或移出不删除已写入的列和值，只停止后续写入。仍被引用的定义、
  仍有成员的计算任务都不能删除；成员启用期间定义不能修改。

## 3. 周期流水线

```text
CollectorPeriodCompleted
  ─► durable factor_collector_period_v1
  ─► 按计算任务进入各自的串行 lane（不同任务并行）
  ─► 冻结本周期启用的定义，规划最大回看窗口
  ─► 读取源数据（PrimaryStore.ReadTimeSeriesRows）
  ─► 集合内全部因子编译成一个程序（相同子表达式只算一次），在网格面板上执行
  ─► WriteFactorRows（携带列 + 因子列）─► ReportFactorPeriodComputed ─► ACK
  ─► Storage View 应用标记后发布 ViewDataReady
```

- 每个 (标的, `series_tag`) 是一条序列；时序算子沿序列计算，截面算子在同一 `(data_time, series_tag)` 的全部可用标的之间计算。
  结果只在有源行的目标时刻产生，行身份是源行的 `(data_time, series_tag)`。同一份输入的结果与并行度、分块、
  是否与其他因子共享节点无关，逐位相同（实时写入的提交 ID 依赖它）。
- **回看窗口缓存与预热。** 实时周期之间回看窗口只差一根 K 线，引擎缓存每个计算任务已加载的窗口，
  预热完成的标的只读新的数据。新启用或落后太多的标的在后台预热，不拖慢实时周期；预热期间的结果
  不算正式结果，按失败标的上报，持有这些标的的策略不会使用该周期。
- **主动预热。** 引擎成为活动引擎（启动、接管租约）或目录里出现新的因子集后，立即为还没有载入窗口的因子集排队预热，
  窗口读到最近一根已收盘 K 线的前一根，不等该集合的第一个实时周期到达才开始。1h 及更长周期的集合在下一期到达前早已预热完成，
  这一期照常完整计算；以前要等第一期到达才懒加载，那一期全部标的预热中，整根缺失（2026-10-16 发布重启后 1h 集合缺了 08:00Z 一根）。
- **预热跳过的周期会补算。** 来不及预热而跳过的 (因子, 标的, 周期)（1m 集合重启后的前一两期、在整点前一两分钟重启的 1h 集合、
  新上市或落后太多的标的）和空洞跳过一样记入跳过账本（`reason=warming`），由跳过恢复按「只填充」补算，历史结果不会缺一根；
  这一期实时路径一行都没写，恢复时携带列（`close` 等源字段）一并按源数据写入。marker 不改写，也不再触发策略。
  缓存落后窗口起点不超过 5 根（回看很短、或中间漏了几期）的标的在本期内直接读整窗口，不当作预热中。
- **预热完成即补算。** 集合预热就绪（全部标的窗口已载入、没有排队或在途的预热）后，因预热中跳过的待办不再等 `gap.settle`
  （5 分钟，给自动补采留的时间）：源数据在跳过时就已入库，窗口一载入就能补。一批预热完成（日志 `factor_warmup_done`）、
  或者实时周期记入预热中跳过的项时都会唤醒跳过恢复，不等下一轮轮询；集合还在预热时这些项照旧等待。空洞跳过的项仍按原节奏。
  以前重启后 1h 集合的第一期要在预热完成后再等 5～10 分钟才补齐，因子视图这段时间告警。
- **补齐的最新一期记入运行摘要。** 跳过恢复补齐的如果是某集合最新的一期，账本里这一期没有待办之后，引擎改写这一期的运行摘要：
  去掉补齐的失败标的与空洞标的、不再算预热中，余下没有失败就记为完成，完成时刻改为补齐的时刻，并立刻补发心跳（日志
  `factor_period_repaired`）。补算没覆盖的失败（上游失败、读取失败、计算出错、放弃或取消的待办）原样保留；已失败的期次不改写。
  整因子跳过的严格截面因子（实时路径一行没写）按补算重算全集的逐项结果判断，这次没写成的标的仍记为失败。
- 单个因子或标的计算失败不影响其他结果；可恢复的 Storage 基础设施错误会让消息重投，
  其他错误汇总进周期状态后照常上报完成并 ACK，避免坏因子阻塞整条 lane。
- `WriteFactorRows` 使用提交 ID 幂等去重（实时周期是内容摘要，相同内容的重投被去重；补算与含空洞失效的写入每次执行加一个唯一的盐，不会被旧回执吞掉），只有这个专用接口能写因子结果列；
  完成标记在结果行之后写入，同一数据集由 DataNode Outbox 保序。
- 当前只支持 `crypto` 空间的连续周期日历，其他空间返回 `unsupported space calendar`。

### 回看窗口与 K 线空洞

> 状态：已实现。窗口空洞检查默认关闭（引擎配置 `gap.enabled: false`），Storage、策略、Trade 都升级到支持 `gap_subjects` 与保持标记之后才打开（线上已打开）；跳过账本与恢复始终开启，预热中被跳过的周期也靠它补算。完整背景、取舍与设计见[因子窗口空洞防护执行计划](../计划/因子窗口空洞防护执行计划.md)与[详细设计](../计划/因子窗口空洞防护详细设计.md)。

因子按「最近 N 根」取回看窗口，**窗口中间缺了几根时，因子照样算出一个看似正常的数**，再一路传给策略和下单，整条链路没有任何环节会发现它错了。所以因子侧必须自己检查窗口连续性，不能只靠采集补齐。分工如下：

- **采集侧「防」和「补」**：自动补采每 5 分钟一轮（见[采集](采集.md)）；冷门币的零成交分钟币安也会返回 K 线，不构成空洞。
- **因子侧「不信、不算」**：对每个因子、每个标的、每个序列，用该因子自己的回看长度生成应有的时间点，窗口缺任何一个，该因子对该标的当期失败（字段写 NULL，已存在的结果键一并失效），按失败标的上报，并用 `gap_subjects` 与其他失败区分。窗口头部缺失只有在该标的有上市时间或首根 K 线时间的依据时才按新上市放行。补算按周期逐个检查；截面因子按 `AllowPartialUniverse` 处理，恢复时用该周期 marker 里冻结的全集，不按单标的恢复。
- **跳过而不是阻塞**：一个标的的空洞不能拖住整个周期的约 500 个标的；修复要 5～15 分钟，结果早已过期。
- **补采后恢复**：引擎本地账本（`factor-gap-YYYYMM.jsonl`，按月一个文件、永不自动删除）记录每次跳过（空洞跳过，以及预热中跳过、带 `reason=warming`）；引擎每 5 分钟检查缺口是否已补上，补上后在进程内做**只填充**的重算（只写完整窗口算出的值，从不写失效 NULL），写入确认后记 `repaired`；超过 6 小时仍补不上记 `gave_up` 并告警，由操作员手工补采和补算。时序因子按（集合, 标的）分组，恢复区间相同的分组合并成一次重算（每批最多 100 个标的），重启后一期约 500 个标的整体预热跳过只需几次运行；每轮最多运行 `gap.max_groups_per_sweep` 批，新建因子集一次积压几十万条、各标的区间又各不相同时，默认的 20 批要很久才恢复完、赶不上放弃期限，这时调大它（线上引擎设为 200）；缺口如果早于数据集最早的采集计划生效点，普通补采看不到，用 `moox-cli collector kline backfill --force` 指定范围补采。恢复只写历史因子行，不改写原 marker，也不触发策略。
- **监控口径**：一期只因回看窗口空洞（`gap_subjects`）或预热中而不完整，向 Monitor 报告为 `partial`（数据积累中），不算失败也不算成功，Monitor 显示“数据积累中”而不告警；有空洞与预热之外的失败才是意外的不完整，按失败处理。
- **配置与告警**：`gap.*` 见引擎配置示例（`config/engine.yaml`）。指标 `factor_gap_pending`、`factor_gap_skipped_total`、`factor_gap_gave_up_total`、`factor_gap_ledger_degraded`；整期大面积缺失（有空洞或上游失败的标的占预期的比例 ≥ `gap.mass_ratio`）输出 `ERROR factor_gap_mass`；`gave_up` 输出 `ERROR factor_gap_gave_up` 并提示人工补采（`moox-cli collector kline backfill`）与补算（因子管理 CLI 的 `recalc`）。
- **永久审计**：账本即审计，可用 DuckDB 的 `read_json_auto` 或 `jq` 分析空洞频率、集中的标的与时段、从发现到补齐的耗时；另有结构化日志 `factor_window_gap`。

## 4. 补算

补算任务按目标区间 `[start, end)` 执行，按 `recalc.chunk_periods` 分块（当前默认 500 个目标周期），块内不拆分同一 `data_time`
的不同 series_tag，并在块起点前读取所需回看。已完成的块不会因后续失败回滚；同一请求 ID 可
幂等提交。补算可以按因子和标的缩小范围，但不能改变定义里的输入、输出和参数。

引擎通过 `PullRecalcJob` 领取任务（带任务租约，默认 15 分钟），每完成一块用
`ReportRecalcProgress` 上报；引擎停止后租约过期，任务会被重新领取并从 `progress_time` 续跑。

**回填与补算对 Storage 的负载防护**（2026-10-14 两个 1h 因子集同时回填，把 4 核的 `storage-node` 打到 330% 以上、读窗口反复超时之后加上的）：

- **同一因子集只建一个回填任务**：启用成员时，如果同一个因子集已经有排队中、还没被引擎领取的 `factor-enable-` 回填任务，新成员并进这个任务，窗口取并集。
  逐个启用 11 个成员只会产生 1 个任务，而不是 11 个各读一遍同一窗口的任务。手工补算、已领取或已结束的任务不会被并入。
- **默认回填最近 5000 期**（`catalog.DefaultMaxBackfillPeriods`）：回填窗口取结果数据集保留期（保留期无限时取源数据最早一期）与最近 5000 期中较近的一个。
  时序 View 只保留最近 `view_rows_per_series`（默认 5000）根，更早的因子结果没有读取方。需要更长的历史时用 `moox-factor-mgr-cli recalc` 显式指定范围。
- **同时只跑一个补算任务**（所有引擎合计，`enginehub.DefaultMaxRunningJobs`）：领取任务时在同一个事务里数租约未过期的运行中任务，达到上限就不再发出新任务。
- **读窗口的并发、退避与断路**：补算和预热读窗口的并发按 `pipeline.bulk_read_workers`（默认 4）收敛，不再随引擎机器的核数增长；
  批量读取失败后先退避再重试（`pipeline.read_retry_backoff`，默认 2 秒，按 2 的幂递增、上限 30 秒、带 20% 抖动），
  连续失败 `pipeline.read_breaker_failures`（默认 3，负数关闭）个批次后，其余批次不再请求、直接失败。实时周期的读取不受影响，仍然快速失败。
  补算分块遇到基础设施错误的重试也改为指数退避（5 秒起，上限 2 分钟）。

## 5. 管理端与引擎的协作

- **目录同步。** 引擎启动时立即同步一次，之后在每分钟第 45 秒调用 `SyncEngineCatalog` 拉取带哈希的目录快照并落盘
  （`data/engine/catalog.json`）；管理端不可达时继续用最后一份快照计算。新启用的成员在引擎下一次
  同步之前的周期不会自动补算，需要时手动提交补算。引擎安装快照时编译全部定义（派生字段以编译结果为准）；
  补算任务自带完整定义，引擎领取后现场编译，不依赖目录同步。引擎侧编译失败（只在管理端与引擎的 expr 版本不一致时出现）
  只让该因子本期对全部标的失败，计入 `factor_compile_errors_total`。
- **引擎租约。** 引擎每 10 秒调用 `EngineHeartbeat`；同一时刻只有一个 `engine_id` 持有租约，
  旧引擎停止心跳 45 秒后新引擎自动接管。心跳同时上报各计算任务最近的运行摘要；平时每 10 秒一次，每算完一期立刻补发一次。
- **状态。** `FactorMgr.GetStatus` 返回引擎是否在线、最后心跳时间、目录是否与管理端一致，
  消费者、lane、计算线程数、引擎与管理端各自的 expr 语义版本（不一致时控制台标红），以及最近运行情况。
- **监控。** 管理端把引擎心跳中的运行摘要转换为因子结果数据集的数据集指标，由 Monitor 的数据集
  新鲜度检查覆盖因子计算。每收到一次被接受的心跳就立刻刷新这些指标，水位前进时补报一份快照，
  Monitor 约 1 秒内看到这一期的完成时刻（不再等 30 秒的定时上报）。同一期只记一次，除非结果变好：
  从不正式（预热中、出错，不推进产出水位）变为正式、或从不完整变为成功时再记一次（补算补齐了这一期），
  产出水位随之前进，到达时间是补齐的时刻，“数据积累中”当场消失，不用等下一期；水位已经推进过的一期升级为成功时
  水位不动、到达时间不变，管理端主动补报一次。

## 6. 表达式语言

因子定义（spec）是一份 YAML 文档：

```yaml
params: {window: [5, 20]}          # 可选：命名常量；列表会展开成多个输出
let:                               # 可选：有序的中间量，后面的可以引用前面的
  ma: ts_mean(close, window)
outputs:                           # 必填：输出列名 → 表达式
  bias_{window}: close / ma - 1     # 展开为 bias_5、bias_20
```

- 表达式支持数字、`true`/`false`、标识符、`+ - * / % **`、比较、`and`/`or`/`not`、`c ? a : b` 与已登记的函数调用；
  其余语法一律拒绝，报错带字段路径和行列。窗口、位移等参数必须是编译期常量。
- 函数分三类：逐元素（`abs`、`log`、`where`、`clip`、`fill_nan` 等）、时序（`delay`、`ts_mean`、`ts_std`、`ts_rank`、
  `ts_corr`、`ema`、`sma` 等）、截面（`cs_rank`、`cs_zscore`、`cs_demean`、`cs_scale`）。完整清单、参数范围、回看规则与说明
  由 `ListFactorFunctions` 返回，控制台编辑器的函数参考面板即来源于此。
- 空值语义：null 与网格上缺失的行读作 NaN；任一输入为 NaN 结果即为 NaN（`where` 的未选分支除外）；±Inf 一律记为 NaN；
  **严格窗口**：时序窗口内只要有一个 NaN 结果就是 NaN，没有 `min_periods`；截面算子跳过输入为 NaN 的标的。
  写入时 NaN 为 null。
- 回看由编译推导（例如 `ts_rank(ts_mean(x, 20), 20)` 是 39）；`ema`/`sma` 截断到权重低于 1e−9 的 K 根（`ema(x, 20)` 为 208）。
- 限制：spec 64 KiB、单条表达式 4096 字符、展开后最多 64 个输出、窗口 1～5000、推导出的回看不超过 5000。

因子库位于 `modules/factor/factors/`（`*.yaml`，每个文件是 `[{factor_id, name, spec}]` 列表），
用 `moox-factor-mgr-cli import-catalog --dir ./factors` 导入；单个定义用 `import --file <文件> --factor-id <ID>`。
示例见 [`examples/factors`](../../examples/factors/)。
离线检查与试算用 `packages/factorexpr/cmd/factorexpr`（`functions`、`check`、`eval`，与引擎同一个编译器和执行器）；
把旧 Python 因子转成表达式并逐值核对的完整流程见 [`skills/moox/references/factor-dsl.md`](../../skills/moox/references/factor-dsl.md)。

## 8. 运维

安装或更新引擎：

```bash
scripts/deploy/deploy-factor-engine.sh \
  --dir ~/moox/factor-engine \
  --access-address <access 主机>:11004 --access-id access@<主机ID> \
  --access-key-id <Admin 分配的 KeyID> \
  --eventbus-url tls://<控制机>:4222
```

脚本会编译引擎、渲染 `config/engine.yaml`（含 `compute:` 段），
macOS 用 launchd（`com.moox.factor-engine`）、Linux 用 systemd 用户服务托管，并等待 `/readyz`。
安装目录不要放在 `~/Documents` 等受 macOS 隐私保护的目录下，否则进程会卡在启动阶段。

引擎需要的凭据放在安装目录的 `secrets/` 下，必须是 0600 普通文件：Admin 导出的外部身份密钥
`access-factor-engine.key`（KeyID 经 `--access-key-id` 传入，独立于 caller 名）、
Storage primary 密钥 `storage-primary-auth.secret`、EventBus 凭据 `factor-eventbus.yaml`（旁边放它的 CA 文件），
以及安装时生成的 `health-auth.env`。引擎不再需要控制机 Caddy 根证书，也不直接连接 Factor Manager。

常用命令：

```bash
launchctl kickstart -k gui/$(id -u)/com.moox.factor-engine   # 重启（macOS）
~/moox/factor-engine/bin/moox-factor-engine health            # 查看 /readyz 详情
moox-factor-engine run-once --set <set_id> --period <RFC3339>  # 单周期诊断
moox-factor-engine reset-gap-ledger --config config/engine.yaml --yes  # 引擎停止后删除空洞账本（数据被整体清空之后用）
moox-factor-mgr-cli recalc --set <set_id> --start ... --end ...  # 提交补算
```

| 现象 | 处理 |
| --- | --- |
| `/readyz` 返回 503 且 `lease_conflict=true` | 另一个引擎持有租约，停掉多余的引擎 |
| 日志出现 `factor_catalog_sync_failed` | 管理端不可达；引擎继续用最后快照计算，恢复后自动追平 |
| 事件反复 `factor_period_retry` | 结果数据集未就绪或 access 不可达 |
| 补算任务 `running` 但不前进 | 执行它的引擎已停止，等任务租约过期后会被重新领取 |

引擎与管理端的 tRPC 配置里不要启用 `transinfo-blocker` 客户端过滤器：网关客户端的签名头（`X-Moox-*`）走 tRPC 透传元数据，被白名单过滤后会表现为 code 41 或 Access 认证失败。
引擎经公网读 Storage 时，补算和预热的单批读取量较大，必要时调小 `pipeline.read_batch_subjects`、调大 `pipeline.read_timeout`。

表达式执行器的资源配置在 `compute:` 段：`workers` 是一次程序执行的并行度（默认 min(4, 核数)），`max_memory` 是一个计算分块
估算峰值内存的上限（默认 1GiB，可写 `512MiB` 这样的字符串）。引擎是单个 Go 进程，没有子进程。`pipeline.read_workers`
不写时按核数自动选择（核数的四分之一，范围 4~16）。

引擎经公网访问 Access，`gateway_client.compression: gzip`（部署脚本默认开启）压缩读取与写入的请求和响应，减少公网带宽；实测稳态周期读取多在 0.3 秒左右，整周期约 1.8 秒。单个周期的结果行（约 500 个标的）本来就在一次 `WriteFactorRows` 内写完（`write_batch_rows` 默认 1000），回写耗时约 0.5 秒主要是 Access→Storage 的固定往返与提交，不随批次拆分而下降。

首次预热（以及新启用、落后太多的标的）使用独立的读取节流：`pipeline.warmup_batch_subjects`（默认 10）、`warmup_workers`（默认 1）、`warmup_batch_pause`（默认 500ms），宁可预热慢一些，也不在启动时向 Storage 同时发出大量读请求。约 500 个标的的预热，1m 集合约 45 秒、1h 集合约 80 秒，各集合依次进行。引擎接管租约后立即主动预热全部因子集（日志 `factor_prewarm_queued`），不等第一期到达；预热期间到达的周期结果按失败标的上报，策略不会使用这些周期，跳过的结果记入账本（`reason=warming`），该集合预热一就绪就由跳过恢复补算（日志 `factor_gap_repaired`，每批 100 个标的）；补齐的是最新一期时运行摘要随之改为完成。

不要通过清空消费者来恢复积压；先排查 lane 积压和 Storage 错误，历史修正用补算任务。
引擎指标：`factor_period_total`、`factor_period_duration_seconds`、`factor_period_lag_seconds`、
`factor_failures_total`、`factor_lane_backlog`、`factor_compile_errors_total`、`factor_last_period_time`。

## 9. Manager 内部网关身份与构建

Manager 和 Factor CLI 的 Storage 调用统一使用 `gatewayclient`，覆盖 PrimaryStore 与 Metadata 的 14 个方法。
`config/app.yaml` 的 `gateway_client` 配置 caller `factor-mgr`、Admin 分配的 `key_id` 和签名 `key_file`；
KeyID 与请求体内固定的 `moox-factor` 角色认证独立。主机身份、loopback 地址和 MooX 私有 CA 从部署目录中同级
hostgateway 配置读取，Directory 缓存保存在数据库父目录的 `gatewayclient/directory.json`，权限为 0600。
Manager 持有进程级客户端，CLI 在命令结束时关闭；只读刷新重试和签名由共享层处理，写操作只发送一次。

Manager 与 CLI 共用严格配置加载器，旧 `storage` 配置及 `MOOX_FACTOR_STORAGE_*` 环境覆盖已删除；
未知字段、重复键和额外 YAML 文档会被拒绝。Engine 已通过同一外部 `factor-engine` 身份调用 Access；
Manager 的签名与 Storage 凭据由原生 control 部署分发，外置 Engine 使用第 8 节的独立安装流程。

Factor Manager、CLI 和 Engine 均可关闭 CGO 构建，由本机编译或交叉编译。
实际 `scripts/build/build.sh factor-mgr` 已在本机生成 Linux amd64 的 Manager/CLI 静态程序，并完成相关 Linux 运行验证。
远端 Linux CGO 构建入口仅用于需要 CGO 的 Storage 目标。
