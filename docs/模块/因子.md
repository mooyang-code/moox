# 因子（Factor）

Factor 负责因子定义的管理和计算：每当一个采集周期完成，就对相应的源数据集计算已启用的
因子（用表达式定义，由引擎内置的 Go 执行器计算），把结果写入因子结果数据集，供 Strategy 使用。也支持对历史区间发起补算。

代码位置：`modules/factor`。同一个 Go 模块构建两个进程。

## 1. 组成与部署

| 进程 | 运行位置 | 职责 |
| --- | --- | --- |
| `moox-factor-mgr` | control 主机 | `FactorMgr` 管理接口：因子定义、因子任务、成员、补算作业、状态、策略参数提交；维护 SQLite 和结果数据集；通过内部服务 `FactorEngine` 给引擎提供目录、登记和补算作业 |
| `moox-factor-engine` | 因子机（外部程序，对外只做出站连接） | 消费数据集周期完成事件（`DatasetPeriodCompleted`），运行周期流水线和补算作业，写入因子结果；经本机网关给策略服务提供回放的“因子现算”（第 9 节） |

| 进程 | 端口 |
| --- | --- |
| manager | FactorMgr 原生 tRPC `11403`（含模块生命周期 `GetLifecycle`、`ControlLifecycle`），FactorEngine 原生 tRPC `11405`，健康 `11414` |
| engine | 健康 `11417`（只有 `/healthz`、`/readyz`、`/metrics`）、EngineControl 原生 tRPC `11423`（由本机主机网关转发：回放只给 strategy；模块生命周期、任务检查 `CheckTask`、本地写入 `WriteSeries` 等只给 moox-cli）、admin `11945`、metrics `12945`（均只监听本机） |

引擎对外的网络连接全部是出站的；入站的 EngineControl 只监听本机，由因子机的主机网关按服务目录的路由转发（因子机只能出站时，调用方经 control 的反向中转进来，见[主机网关](主机网关.md)第 5 节）：

| 方向 | 地址 | 用途 |
| --- | --- | --- |
| 引擎 → 控制机、存储机的主机网关 | `<主机>:11003`（TLS） | 同步目录、心跳、领取和上报补算作业（控制机的 FactorMgr），读源数据、写因子结果与周期标记（存储机的 Storage）；引擎是普通调用方，用因子机的主机密钥、以 `factor-engine` 的身份签名，先从本机网关 `127.0.0.1:11002` 取目录 |
| 引擎 → EventBus 所在主机（默认存储机） | `tls://<EventBus 主机>:4222` | 订阅 `DatasetPeriodCompleted` 与 K 线补写事件 `event.collector.kline.backfilled`（`factor-eventbus` 凭据） |

管理端在创建或编辑定义时编译表达式校验；`PreviewFactor` 试算时直接读 Storage、在进程内计算少量标的，不经过引擎，
不写结果。管理端不消费 EventBus。

## 2. 领域模型

分层：**采集数据集 →（因子任务）→ 因子结果数据集 → 策略实例**。因子任务关联一个源数据集和一个频率，产出一个因子结果数据集；
一个源数据集可以有多个因子任务。策略实例创建时选定一个或两个（现货、永续各一个）因子任务，一个任务可以被多个实例引用。只有 DSL 声明了 `factor_params` 的实例启用时才把主帧任务**关联**（`BindFactorTask`，独占：一个任务只关联一个实例，写入后不能改，只随实例一起删除），用来独占可变成员的参数提交；其余实例只读任务的列，不关联（见[策略](策略.md)）。只有固定成员的任务从不关联，不随任何实例删除，不用了要手动停用或删除。任务由用户创建（控制台或 `moox.toml`），可以先于策略运行以积累历史；
策略停止只影响策略层，因子任务照常计算，由用户手动停止。控制台里这一页叫「计算任务」，指的就是这里的因子任务。

Factor 的 SQLite（`factor.db`）有这些业务表：

| 表 | 内容 |
| --- | --- |
| `t_factor_defs` | 全局因子定义：`factor_id`、展示名、分类、表达式定义（spec）与原文哈希、`allow_partial_universe`；类型、输入列、输出列、回看与可调参数由编译推导，不落库 |
| `t_factor_categories` | 因子分类（动量类、波动类……）：只是元数据，用于查找与按类展示；内置“未分类”不能删除 |
| `t_factor_tasks` | 因子任务：任务 ID、空间、展示名、源数据集、频率、结果数据集、状态、`c_bound_instance_id`（关联的策略实例：只有声明了 `factor_params` 的实例关联，一个任务只关联一个实例，一个实例可以关联多个任务；写入后不能修改或清空）；任务的标的就是源数据集当前的标的，没有单独的对象范围 |
| `t_factor_task_members` | 任务的成员，主键 `(task_id, member_key)`；`kind` 是 `fixed` 或 `var`；`c_params` 是固定参数（可变成员是默认参数），加成员时写定、之后不变 |
| `t_factor_member_params` | 可变成员最近一次被接受的提交（各标的的参数、目标期、请求 ID、提交时间），主键 `(task_id, member_key)`，没提交过的成员没有行；是运行状态，不属于配置，目录同步和成员变化检测都不看；删成员时级联删除 |
| `t_factor_recalc_jobs` | 补算作业：范围、成员、进度、结果摘要 |
| `t_factor_udfs` | 自定义算子（第 12 节）：名称与当前启用的版本哈希，空串表示还没有启用 |
| `t_factor_udf_versions` | 自定义算子的版本：不可变，主键是 wasm 字节的 sha256，存元数据、wasm、源码提交号、SDK 与工具链版本、服务端一致性测试报告 |
| `t_factor_engine_heartbeat` | 最近一次引擎心跳（哪个引擎、什么时候），只有一行 |

- 定义指纹 `definition_hash` 覆盖完整计算契约：表达式语义版本、编译后的规范程序文本（含参数声明：类型、范围、
  默认值）与 `allow_partial_universe`。只改注释、格式、`let` 名不会改变它，任何影响结果的改动都会改变它；**参数取值不进指纹**。
  它在读取时派生、不落库，随 `FactorDef` 和周期明细 `PeriodDetail`（`DatasetPeriodCompleted.detail`）里的 `FactorPeriodState` 一起下发。`spec_hash` 只代表定义原文。
  **成员契约哈希** = `definition_hash` + 成员类型 + 固定参数（可变成员不含参数）：策略启用实例时固化它，之后据事件里的契约哈希判断成员是否变化。
  周期明细要求指纹非空，由因子侧上报前校验（`storageio.ValidatePeriodDetail`）；Storage 对明细是不透明字节，不解析。
- **ID 与展示名**：任务 ID 是 `ftask_<后缀>`，结果数据集 `dataset_factor_<后缀>`，默认 View `view_factor_<后缀>`（结果数据集与 View 都由 factor-mgr 自己创建、维护、删除，Storage 不托管）。后缀只含小写字母、数字、下划线，最长 35 个字符；
  控制台创建时随机生成 8 位，因子任务文件里由用户写定（这样 `factor task apply` 可重复执行）。任务展示名 `name` **直接**用作结果数据集的展示名，
  所以必须 1～10 个字、含汉字、在空间内唯一。
- 输入列、输出列、类型与回看都由编译推导：表达式里引用的、不是 `let`/`params`/函数名的标识符就是输入列；
  用到截面算子（`cs_*`）的是截面因子。系统列 `subject_id`、`freq`、`data_time`、`series_tag` 不能作为输入或输出。
  回看按周期网格计数（缺失的 K 线是 NaN，严格窗口会让受影响的结果为 null）。有可调参数的因子，回看按参数范围的最坏情况推导。
- 加入任务时校验：输入列都存在于源数据集且是数值列（int、double），`params`/`let` 不与源列重名，
  列名不与源列、其他成员的列或结果数据集里别的因子拥有的列重名。
- 成员加入后为停用状态（`AddTaskMember` 带因子 ID、成员类型与参数，成员键由服务端推导并随响应返回列名）；`SetTaskMemberStatus(enabled)` 会重新校验、对齐结果数据集的列，
  不自动补算历史。停用或移出不删除已写入的列和值，只停止后续写入；再次加入同一个成员键沿用原来的列，并核对旧列元数据里的参数与成员类型一致。
  仍有成员的任务、已关联策略实例的任务都不能用 `DeleteFactorTask` 删除；已关联的任务只随策略实例删除（`DeleteBoundTask`）。没有关联的任务可能还被不调参的实例引用，factor-mgr 不知道有哪些实例在读它，删掉后由策略侧的 `missing_factor_tasks` 提示。
- **被任务引用的定义有修改限制**：不允许增删参数，不允许改参数的类型、声明顺序和默认值，也不允许增删、改名或重排输出（列名依赖它们）；要改就新建一个定义。
  表达式本身和参数范围可以改，但新范围必须包含所有引用它的成员现有的固定参数与默认参数。成员启用期间定义不能修改。

### 成员键与列名

成员键与列名由「因子 ID + 参数 + 是否可变 + 输出」按规则推导，不存储别名。写策略规则、筛选条件或 SQL 时，列名就是这里推导出的名字；
控制台加成员时会实时预览，`AddTaskMember` 与 `factor task apply` 也会返回或打印它们。规则只有一份实现：Go 在 `packages/factorname`，前端在 `web/src/utils/factor-name.ts`，两边共用 `testdata/vectors.json`。

```text
名字（因子 ID / 输出名 / 参数名）： 小写字母开头，只含小写字母、数字、单下划线，不以下划线结尾
成员键 = 因子ID [ "__" 参数段 ]
参数段 = "var"  |  值 { "_" 值 }       值 = n?[0-9]+(p[0-9]+)?    按定义声明的参数顺序，只写值不写参数名
列名   = 成员键 [ "__" 输出名 ]          单输出因子没有输出段
```

| 成员 | 成员键 | 列名 |
| --- | --- | --- |
| `ema`，参数全为默认值 | `ema` | `ema` |
| `ema`，span=20、warmup=50000 | `ema__20_50000` | `ema__20_50000` |
| `rsi`，参数全为默认值 | `rsi` | `rsi` |
| `boll`，参数全为默认值（输出 mid/up/low/pctb） | `boll` | `boll__mid`、`boll__up`、`boll__low`、`boll__pctb` |
| `boll`，window=30 | `boll__30` | `boll__30__mid` 等 |
| `ma_fast`，可变成员 | `ma_fast__var` | `ma_fast__var` |

- **段与段之间用双下划线**，名字内部用单下划线（`ma_fast`、`bias_q`），所以只看列名就能按 `__` 切开：第一段是因子 ID；第二段是 `var` 或匹配值语法的就是参数段，否则是输出名；
  三段依次是参数段与输出名；超过三段非法。因此输出名不能是 `var`，也不能匹配值语法（如 `n5`），也不能等于因子 ID，不带因子前缀（写 `mid`，不写 `boll_mid`）。
- **参数值的写法**：十进制，小数点写 `p`、负号写 `n`（`0.5` → `0p5`，`-1` → `n1`，`-1.5` → `n1p5`）；只写值，顺序就是定义声明参数的顺序。只接受规范形式（`01`、`1p0` 非法）。
- **参数全为默认值时省略参数段**，成员键就是因子 ID；**可变成员固定以 `__var` 结尾**，一个因子在一个任务里最多一个可变成员，需要多个可变值就注册多个因子（`ma_fast`、`ma_slow`）。这两条最容易被忽略。
- **单输出与多输出**：单输出因子在规格里写 `output: <表达式>`，列名就是成员键；多输出因子写 `outputs: {输出名: 表达式, …}`（至少两个），列名是 `成员键__输出名`。
  只有确实共用同一组参数的因子才用多输出；不共用参数的输出拆成独立因子，引擎同一期合并公共子表达式，不会多算。
- 长度上限：因子 ID 24 个字符，输出名与参数名 16 个字符，成员键 44 个字符，列名 64 个字符。列名与源数据集的非因子列重名（例如因子 ID 叫 `close`）时加成员被拒绝。
- 列名只能还原「列名里有的信息」：默认成员的键 `ema` 能解析出「固定、参数全为默认值」，具体参数值要查列元数据的 `factor_params` 或定义。
- 固定成员的参数一旦写定就不能改，要换参数就加一个新成员（键随之不同）。

结果数据集的列元数据（来源 `CUSTOM`，不带 `origin_id`）记录每列的来源：`column_kind=output` 的列带 `factor_id`、`member_key`、`member_kind`、`output_name`、`category_id`、`definition_hash`，
固定成员另带 `factor_params`（完整参数的规范 JSON）；列名、类型与这些属性的契约由 factor-mgr 建列时自己保证，Storage 只校验列名唯一、值类型合法这类通用规则，不解释这些属性。

### 系统列 `__params`

每个因子结果数据集有一个系统列 `__params`（`column_kind=params`，类型 `json`，展示名「因子参数」），**只记录这一行各可变成员实际用的参数**；固定成员的参数就是它自己的 `c_params`（也写在列属性 `factor_params` 里），不记。任务里没有可变成员时这一列不写（为空）：

```json
{"ma_fast__var": {"window": 5}, "ma_slow__var": {"window": 60}}
```

- 它是可变成员参数的**唯一历史记录**，补算、回放、策略的 `params()` 和用户查询都读它；两层键按字典序、不带空白，数字用十进制写法，同一期重算时与因子值一样逐位相同。
- 补算选中的成员里有可变成员时，先读出原行的 `__params`，只替换这次重算成功的可变成员键再写回（其余可变成员的记录保留）；原行不存在时只记录这次实际计算的可变成员。
  选中的成员里没有可变成员时不读也不写这一列，原行里可变成员的记录不动。
- 结果页默认隐藏这一列，「显示参数」开关打开后按成员分组展开；筛选只按因子值（`FilterSpec` 的「列名 + 操作符 + 值」），不支持按参数值筛选。
  直接用 DuckDB 排查时可写 `json_extract("__params", '$.ma_fast__var.window')`。

## 3. 周期流水线

```text
DatasetPeriodCompleted
  ─► durable factor_collector_period_v1
  ─► 按因子任务进入各自的串行执行器（不同任务并行）
  ─► 生命周期门禁：模块没在运行、或任务检查没通过就 ACK 不计算
  ─► 取本期各成员的参数（第 11 节），规划最大回看窗口
  ─► 把本期标的从 Storage 同步到本地时序存储（只拉增量），抓取内存窗口的读租约
  ─► 任务内全部成员编译成一个程序（相同子表达式只算一次），在网格面板上执行
  ─► UpsertFields（携带列 + 因子列 + __params）─► ReportDatasetPeriodCompleted（detail 为 PeriodDetail）─► ACK
  ─► Storage View 应用标记后发布 ViewDataReady（透传 detail）
```

- 每个 (标的, `series_tag`) 是一条序列；时序算子沿序列计算，截面算子在同一 `(data_time, series_tag)` 的全部可用标的之间计算。
  结果只在有源行的目标时刻产生，行身份是源行的 `(data_time, series_tag)`。同一份输入的结果与并行度、分块、
  是否与其他因子共享节点无关，逐位相同。
- **一个数据集里每个标的一期只有一条序列。** 现货、永续分开放（各一个数据集、一个因子任务），不支持同一数据集里同时放两个市场的统一数据集。
  引擎内部的期望、可用与失败都按标的记；本期有没有数据看这个标的这一期有没有真实的源行，不看 tag（同一期一个标的至多一条序列，需要 tag 的地方都从行键取）。
  周期完成事件与因子写的周期完成标记只带按标的的全集（`universe_subject_ids`）与失败名单（`failed_subjects`）。结果值、成员状态与按标的的名单由金样固定（`pipeline/testdata/baseline`、`localdata/testdata/baseline`，实时与补算两份）。
  - **期望全集**来自源数据集周期完成事件的 `universe_subject_ids`（上游失败读 `failed_subjects`）。有冻结全集可读的路径都读它：实时计算读事件；空洞恢复读因子自己结果数据集 marker 里冻结的
    `universe_subject_ids`（读 marker 要带该期的触发事件 ID，待办条目带着它）。**截面因子和时序因子的空洞恢复都按待办周期逐期读**
    （`gapFiller.fillSubjects` / `fillCross`）：时序恢复把冻结全集相同的相邻周期合并成一次运行，各自带当期的全集（`Selection.FrozenUniverse` 为真）。冻结全集只含当时存在的标的，下架之后各期的全集里没有它，待办能收敛；
    marker 读不到、或冻结全集与本批标的没有交集的周期（以及没有触发事件的待办）退回下面的数据层兜底。
    恢复时的细节：一轮内同一（结果数据集、触发事件、周期）的 marker 只读一次；先按本批标的过滤冻结全集再比较，别的标的上下架不会切碎批次；只合并相邻周期（日线按一天算相邻），
    只处理时序成员的待办（截面成员由 `fillCross` 按周期恢复）；某一期读 marker 失败只让这一期留待下一轮，其余各期照常。待办是实时周期跳过时记下的，marker 在这一期结果写完之后才写，
    恢复可能抢在它前面：读不到 marker 且待办刚记下不足 `gap.settle` 时保留待办、下一轮再试，不退回兜底推导（截面恢复同样，不直接 `gave_up`）；超过 `gap.settle` 仍读不到才按兜底（截面记 `gave_up`）。
    **没有冻结全集可读的路径**——人工补算（窗口跨很多期、没有每期的触发事件）、失效重算（Follow 发现 Storage 修正历史后自动触发，同样没有单一触发事件）——
    `Plan.FrozenUniverse` 为假，由数据层收窄期望标的（`pipeline.SubjectExpecter`，`Runner.Run` 在补算类计划上调用；数据层不提供时补算报错），不做推测：
    只排除本地最早一根不早于计划区间终点的标的（区间结束时还没上市），这些标的不读、不算缺数、不进周期标记的全集。
    否则补算或失效重算上市前的区间时新股被当成缺数，严格截面因子整段跳过，老标的已有的值被写成 NULL。
    本地没有数据的期望标的照常保留、按缺数处理；这个数据源在本地一个标的都没有时报“没有可补的数据”（`localdata.ErrNoLocalData`）：补算只读本地，这时什么都算不出来。
    空洞恢复的确认键是（成员、标的、周期），该标的在这个周期有已写成的行才算补齐。
  - **成员状态**：截面因子没有可用标的、或严格全集（不允许部分全集）下有标的缺数时整个成员 `skipped`，结果写 NULL、`__params` 里去掉该成员；其余有标的缺数时 `degraded`。
    上游事件判为失败的标的（`failed_subjects`）即使本地已有这一期的数据，也不进计算面板（不参与截面排名），结果写 NULL、不记参数。
  - **成员失败名单与标记体积**：周期明细（`PeriodDetail`）里每个成员的 `failed_subjects` 只记周期级 `failed_subjects` 之外多出来的部分，
    成员完整的失败标的 = 周期级 `failed_subjects` ∪ 成员自己记的（读取方一律用 `packages/factorname.MemberFailedSubjects` 还原：因子自己的 `storageio.ValidatePeriodDetail`、Strategy 的就绪判断）。
    相减只在 `storageio.markerToProto` 写明细时做一次，管线内部的成员状态与心跳 `TaskRunSummary` 里都是完整名单。实时路径上成员的失败名单本来就包含周期级失败（上游失败 ∪ 本期读不到），
    所以周期有失败标的时没有 complete 的成员。
    写标记前预检体积（`storageio.MaxMarkerBytes`，6 MiB，留出 Storage 事件 8 MiB 上限的余量），超过时报中文错误，不等 Storage 拒绝。
    成员数上限（`storageio/marker_test.go` 的 `TestMarkerMemberLimitBySubjects` 用 `proto.Size` 算出）：A 股 5931 只全部失败、各成员失败相同（常见，上游整期晚到）时约 12 万个成员；
    各成员额外失败互不相同、几乎覆盖全部标的（周期级没有失败，名单无法相减）的极端情况约 95 个。加密 500 只对应约 12 万个与约 736 个。超出时写标记报上面的错误，要减少任务的成员数或标的数。
  - **导入**：EngineControl 的 `WriteSeries`（导入专用）与同步器、对账路径一样整段替换标的在 `[from, to)` 内的全部序列。
  - **改 tag**：采集写行的 tag 由任务的路由固定，备用来源回落不换 tag；人为改了任务的主来源会换 tag，等于新序列：本地存储里同一标的先后有新旧两条序列，
    同步按标的的最新一根接着拉。补算按期判断：每一期用这一期那条序列的行（旧 tag 那几期用旧 tag 的行、新 tag 那几期用新 tag 的行），都能写成。要么新建数据集，要么沿用原 tag。
  - **已知差别**（小问题，不另加机制）：
    - 空洞恢复要读完成标记。正常的待办要等过 `gap.settle`（默认 5 分钟）才恢复，那时标记早已写好，不用多等；
      可能多等的只有两类提前放行的条目——任务已就绪后的预热跳过、已收到 K 线补写事件的上游失败。这两类在正常流程里标记同样已经写好；
      万一读不到，待办刚记下不足 `gap.settle` 时保留、下一轮再试，过了 `gap.settle` 仍读不到就退回由数据层收窄期望标的，不会卡死。
    - 本地一个标的都没有时，人工补算与失效重算报 `localdata.ErrNoLocalData`（“没有可补的数据”）：补算作业记失败，失效重算的待办保留到下一轮。
    - 补算里一行结果值无效时，写 NULL 的范围是“这个标的在本块内的行”；本块跨过 tag 切换时比只写那条序列的行更大。
    - 实时周期里 `outcomeFor` 给没有状态的成员补 degraded 时失败名单为空；周期明细还原后它的失败标的是本期周期级失败的全部标的（更准确），Strategy 据此把这些标的当成该成员不可用。
    - 实时周期目标时刻那一根是本地填充行时，这个标的按缺数算。同步不会把填充行留作最后一行，平时遇不到。
  - 回放的“因子现算”（第 9 节）每个标的每期至多一行；标的全集按标的取，序列按期从本地快照取（没有完成事件，口径见第 9 节的已知差别）。
- **本地数据与窗口。** 常驻引擎的实时、补算、重算都从因子机的本地时序存储（Pebble，不按时间自动淘汰；只有 `setup wipe` 或停掉引擎后删 `<部署根>/data/factor-engine` 才会清空）读取；每个启用任务的回看窗口常驻内存
  （按序列的列式环形数组，实时周期之间只追加一根）。Storage 只在增量与修正时被读取，详见下面「本地时序存储」。
- **窗口没载入完成，本期不算。** 引擎成为活动引擎、或目录里出现新任务后，后台预载每个任务的窗口（取同步基线、补到最新已收盘的一根、载入内存）；
  载入完成之前（以及任务检查没通过期间）到达的周期事件不算，事件确认掉。算过的任务（有连续水位记录，典型是引擎重启后重新载入窗口）
  只在连续水位里记下追赶目标与这一期的标的全集，载入完成后由 10 秒一轮的追赶循环从水位下一期起依次补算，不用等下一条实时事件（日线任务不会因此晚一天）；
  从没算过的新任务不记，从就绪后的第一条实时事件算起，之前的历史用补算作业。模块暂停期间到达的事件不记目标，由恢复追赶显式建立。
- **没有任何数据的标的不拖住任务。** 预载时，任务里本地和 Storage 都没有数据的标的（停牌超过保留期、刚加入还没采到）记一条警告
  （`factor_subjects_without_data`），不进内存窗口，每期按本期不可用处理，其余标的照常计算；实时周期照常按回看范围拉取它们，
  拉到数据（复牌）的那一期就载入窗口。任务检查的“没有数据的标的”一项现算列出它们：部分没有时警告，任务的标的全部没有时不通过。
  停牌、退市的成员由采集的交易状态检测标记（[采集](采集.md)第 7b 节），不进预载名单和实时全集，所以长期停牌的股票不会走到这里。
  只有数据源上（同源各任务标的的并集）全部标的都没有数据时才算数据源未就绪：任务检查“本地数据”不通过，要导入历史或把标的从标签里移除。
  2026-11-24 停牌两个多月的 601059.XSHG 的最后一批 5m 超出保留期，原来的“任一标的没有数据就停算”让沪深 300 的因子和策略停了一上午。
- **补齐的最新一期记入运行摘要。** 跳过恢复补齐的如果是某任务最新的一期，账本里这一期没有待办之后，引擎改写这一期的运行摘要：
  去掉补齐的失败标的、不再算预热中，余下没有失败就记为完成，完成时刻改为补齐的时刻，并立刻补发心跳（日志
  `factor_period_repaired`）。补算没覆盖的失败（上游失败、读取失败、计算出错、放弃或取消的待办）原样保留；已失败的期次不改写。
  整因子跳过的严格截面因子（实时路径一行没写）按补算重算全集的逐项结果判断，这次没写成的标的仍记为失败。
- 单个因子或标的计算失败不影响其他结果；可恢复的 Storage 基础设施错误会让消息重投，
  其他错误汇总进周期状态后照常上报完成并 ACK，避免坏因子阻塞整条任务执行器。
- 结果行用通用 `UpsertFields` 写入，Storage 不去重，重投或补算时再写一次、后写覆盖先写；写入权限由网关 ACL 决定；
  完成标记在结果行之后写入：同一数据集的变更日志按提交先后排序，View 应用完之前的行之后才处理这条标记、发布就绪事件。同一事件下的多个任务并行计算、各自写出，某个任务失败只影响它自己的这一期。
- **周期日历按空间取**（`internal/periodclock`）：crypto 是 7×24 的 `Continuous`；stockcn、stockhk、stockus 是按 `packages/barclock` 实现的 `Session`，
  只有交易时段内的桶，周期必须整除每个交易时段，除不尽的在建任务时拒绝（本地存储支持的频率里，A 股可用 1m、5m、15m、30m、1h、1d；
  港股、美股的交易时段不是整小时，可用 1m、5m、15m、30m、1d）。
  没有在 barclock 登记的空间返回 `unsupported space calendar`。同一台引擎可以同时跑不同空间的任务。
- **交易序号时间轴。** 引擎内部（本地存储网格、内存窗口、填充、长缺口、连续水位、跳过账本）一律用轴上时间计算：
  轴上时间 = 纪元 + barclock 交易序号 × 周期。A 股的交易 K 线在轴上排成一条没有午休、隔夜和休市的连续序列，crypto 的轴就是真实时间。
  真实时间只在三层边界上换算：Storage 客户端（读行、写结果、周期上报、完成标记）、事件入口（周期完成事件、K 线补写事件）、
  引擎对外接口（心跳与 RecentRuns、本地写入的四个方法、重算、导入、回放、预览、CLI）。日志和告警里的周期先换回真实时间再输出。
  按根数计的阈值在 A 股上数的是交易 K 线：长缺口阈值 289 根在 5m 上约等于 6 个交易日；心跳里的滞后由引擎按落后的交易 K 线根数换算成秒，
  午休、周末不算滞后，管理端原样使用。

### 连续水位

追赶目标只往后推：补写事件和恢复追赶在水位存储的锁内推目标，追赶循环拿着开始时的副本写回时保留已存的较晚目标，互相不会盖掉。
引擎为每个因子任务保存连续水位（`watermark.state_file`，默认 `./data/engine/watermarks.json`，原子写）：`committed_through`（W）表示这一期及之前都已连续算完，
`target` 是收到的最新收盘周期。收到 T 的事件后，引擎在该任务的串行执行器 里从 W 的下一期推进到 T：

- 有事件的周期用事件里的期望标的与失败标的；没有事件的周期（零提交，或阻塞期间已经 ACK 的事件）按水位状态文件里最近一次事件的期望全集，
  先把这些标的从 Storage 增量同步到本地（新进名单、本地还没有数据的标的也同步），再看**每个标的在本地这一期有没有真实的行**（`localdata.Data.RealRowsAt`）：
  有这一行、不是填充行、至少一个数值字段非 NaN（与回放同一口径，`serieswindow.SeriesView.RealRowAt`）。不按本地最新时间判断：中间缺一根、后面已到的标的，这一期仍算没到。
  不再单独向 Storage 读回这一期。数据源窗口还没载入或同步失败时这一轮不推进，追赶循环稍后重试。
  已知差别：增量同步只从本地最新一根往后拉，本地已有的周期上晚到的行（例如先补成填充行、之后 Storage 才写入真实行）要靠变更跟进取回，
  最长约 `sync.follow_interval`（默认 30 秒）之后才算到；在那之前这一期按缺失计，超过阈值时水位暂时阻塞，跟进取回后自动推进。
- 零提交或缺失比例超过阈值（`watermark.max_missing_ratio`，默认 0.1，`watermark.task_ratios` 按任务覆盖）时**阻塞**：W 不前进、不计算，记下 `blocked_since`。
  阈值以内的缺失照常计算，缺的标的记进跳过账本（`reason=upstream_failed`），补采补齐后由跳过恢复「只填充」补算。
- 计算或报告完成标记遇到重试也不会通过的错误（例如完成标记超过 `MaxMarkerBytes`、被 Storage 判为无效请求）时同样记成阻塞（`blocked_reason=compute_failed`）：
  W 停在这一期、记下 `blocked_since`，这条事件不再重投（TERM），追赶循环照常重试，问题排除后算完这一期阻塞自动解除。基础设施错误只重投、不记阻塞。
- 没有事件、靠本地判断推进的周期用合成的触发事件 ID `catchup:<任务 ID>:<周期>`，marker 与正常周期一样，策略只会看到连续的结果。一次最多推进 `watermark.max_periods`（30）期。
- 事件处理完一律 ACK（只有基础设施错误重投），阻塞靠本地状态续推：追赶循环每 `watermark.poll_interval`（10 秒）对 `target > W` 的任务再推进一次，不占 JetStream 的待确认名额。
- **K 线补写事件**：引擎用持久消费者 `factor_kline_backfilled_v1` 直接订阅 Collector 发布的 `event.collector.kline.backfilled`（`MOOX_COLLECTOR`，
  与周期完成事件共用一个 EventBus 连接和 `factor-eventbus` 凭据）。补采分块读回确认、合成补写都发这个事件，所以以合成数据集为源的任务也收得到。
  事件带数据集、频率、范围 `[start, end)` 和 `absent`（范围内全部标的补采确认行情源没有的 K 线，不限于这批被补写的标的：标的、区间；因子按标的扣除，不读其中的 `series_tag`）。引擎收到后立即推进源数据集相同的任务、唤醒跳过恢复，范围内 `upstream_failed` 的待办不再等 `gap.settle`；
  确认没有的标的在 30 分钟内不计入缺失比例。“已补齐”按已确认的分块给出：失败或被取消的作业里已成功的分块也会发。
  有连续水位记录的任务还会把追赶目标推到范围的最后一期，但不越过当前最后一根已收盘、过了采集宽限的根（与恢复追赶同一个上限；收市后整天重取的范围到次日零点）：
  实时取数整期失败时 Storage 不发周期完成事件，目标停在最后一次有事件的那一期；不推的话，补采把后面补齐了也要等下一条实时事件才补算
  （2026-11-23 港股 15:05 之后整期失败，因子停在 15:00 那根）。只补了一只标的的分块也会推目标，其余标的没补齐时水位按缺失比例短暂阻塞，属于正常。
  事件只更新引擎内存里的状态，被补写的行本身由本地数据跟随 Storage 变更日志取回并触发失效重算，追赶循环另有定时推进保底。
  一个事件最多带 5000 段确认缺失（够全部 A 股标的各带一段，超出时只留最新的并告警），补采作业结束或被取消时立即封存发出。
  - 消费者首次创建时只收新事件；之后是持久的，引擎停机期间的事件在流的 72 小时保留期内恢复后能补收。
  - 它与周期完成事件的消费者一起创建，任一个建不起来整个消费就不启动（之后重试）：`factor-eventbus` 凭据没有按新权限重新生成时，
    实时计算也会停。全新部署会重新生成凭据；只换引擎二进制时要先重新生成并下发凭据。
- 第一次见到某个任务时 W 取 T 的前一期：只从上线起保证连续，历史用补算。重启后从状态文件恢复 W 与 target 继续追赶。
- 心跳带各任务的水位与阻塞状态；factor-mgr 导出 `moox_factor_task_watermark_blocked_since_timestamp_seconds`，阻塞超过 30 分钟 Monitor 告警（不自动跳过，交给人工手动补采或确认缺失）。



### 本地时序存储

> 状态：已实现。

因子按「最近 N 根」取回看窗口，**窗口中间缺了几根时，因子照样算出一个看似正常的数**。
所以**本地数据在写入时就保证连续**，窗口里没有空洞，也就没有逐期的空洞检查：

- **存储。** `seriesstore`（`modules/factor/internal/seriesstore`）按 `k/{空间}/{数据集}/{频率}/{标的}/{块起点}` 存列式块，
  频率支持 1m 5m 15m 30m 1h 4h 1d；块跨度因频率而异（1m 按小时、5m 按 6 小时、15m 与 30m 按天、1h 按周、4h 按月、1d 按年）。
  只有一种写入语义：**整段替换**（用一批行替换标的在 `[from, to)` 内的全部数据）。每个标的在 `[Earliest, Latest]` 上按频率网格连续，
  所以「同步到哪里」只看 `Latest`。实测导入约 102 万行/秒，一批 200 个标的的实时写入约 10ms。
- **缺失行与填充。** 交易所本身缺数据的周期，写入时按字段的 `fill` 属性填成带标记的填充行：`prev`（取上一期该字段的值，默认）、
  `prev_close`（取上一期的 close，给 open/high/low/close）、`zero`（填 0，给 volume 等量类字段）。空洞没有长度上限。
  填充行带已填充标记，表达式里可用虚拟列 `is_filled`（1 或 0）区分；之后拿到真实数据，整段替换会把填充行换成真实行，
  并重新生成它之后的填充行。`fill` 属性存在数据集字段的 `attributes` 里（Storage 原样保存、不校验，由因子解释，无效值按列名取默认规则；`moox-cli metadata apply` 的 `dataset_columns[].attributes` 可写）。
- **窗口。** `serieswindow` 为每个数据源保留回看数量 N 根（`window.lookback` 等，见第 6 节；加余量）的内存窗口，实时只追加；换代（压缩）时复制，读租约抓到的切片不受影响。
  窗口内存超出 `window.max_memory` 或进程预算 `memory.total_budget` 时拒绝启用该任务，并给出估算值。
- **进程级内存准入。** 计算、回放、重算、导入向 `memadmit` 预留内存，预留不到就排队、等不到拒绝；实时周期优先级最高。
  常驻的窗口与块缓存先从总预算里扣除。
- **与 Storage 的同步。** Storage 为数据集行写入维护持久化的**变更日志**（`__changelog/`，保留 7 天，由 storage-primary 的保留期清理循环删除；因子机只跟进其中的时间序列行条目，忽略完成标记与记录型行条目），
  新增读取接口 `ReadDatasetChanges`。同步器：`Pull` 从本地 `Latest` 之后拉增量；`Baseline` 在读数据之前先取变更日志位点；
  `Follow` 读取位点之后的变更，只在内容与本地不同时应用，并把改变的区间记入「失效重算」待办，引擎据此重算受影响的周期
  （已知差别：失效重算待办与跳过账本的待办互不销账，同一段迟到数据可能被两边各算一次、各写一次，结果相同、不会算错；不合并是为了保留跳过账本“超过 `gap.give_up_after`（6 小时）仍补不上”的告警）；
  位点已被清理（断档）时该数据源标为未就绪，由 `moox-factor-engine reconcile --task <任务 ID>` 对账（需要先停止引擎，Pebble 同一时刻只能由一个进程打开）：
  取位点、在保留期内逐标的比对、写入差异、再跟进变更。
- **导入。** `moox-cli import --target storage,factor` 把 CSV 等文件导入：先校验全部文件再写入，按时间边界切批，
  断点记在 SQLite（重跑自动续传），写因子机由 `moox-cli` 经主机网关调引擎 EngineControl 的 `WriteSeries`（因子机只能出站时经 control 中转，引擎未就绪时也能写；
  一批按 protobuf 编码不能超过 4 MiB，默认一万行、40 个数值列约 3.5 MiB，超了提示减小 `--batch-rows`）。格式解析在 `modules/cli/internal/seriesformat`
  （`Decoder` 注册表，目前有 csv）。`--allow-missing` 允许序列内部缺周期（按字段填充规则写成填充行），`--recalc` 把改变的区间记入失效重算。
  **初始数据导入**（数据源第一次接入时灌入长历史）：因子机本地写全量、Storage 只写最近窗口（`--tail-rows`），按导入包 `manifest.json` 预检（`--pack`），
  步骤见 [skill 的初始数据导入](../../skills/moox/references/initial-import.md)。写入从操作机经 control 中转到因子机，中转没有限速，会和采集写 Storage 抢 control 的出口：
  按“行数 ×（列数 × 约 9 字节 + 时间与 tag）”估体量（经 zstd 压缩，长历史仍可能到 GB 级），从 1 路并发开始，导入时盯着采集延迟再决定加不加。
- **仍保留的跳过账本。** 引擎本地账本（`factor-gap-YYYYMM.jsonl`，按月一个文件、永不自动删除）记录每次跳过（窗口没载入完成 `reason=warming`、
  上游数据没到 `reason=upstream_failed`）；引擎每 5 分钟检查缺口是否已补上，补上后在进程内做**只填充**的重算（只写完整窗口算出的值，从不写失效 NULL），
  写入确认后记 `repaired`；超过 6 小时仍补不上记 `gave_up` 并告警，由操作员手工补采和补算。恢复区间相同的分组合并成一次重算（每批最多 100 个标的），
  每轮最多运行 `gap.max_groups_per_sweep` 批。缺口如果早于数据集最早的采集计划生效点，普通补采看不到，用 `moox-cli collector kline backfill --force` 指定范围补采。
  恢复只写历史因子行，不改写原 marker，也不触发策略。
- **监控口径。** 一期只因窗口没载入完成而不完整，向 Monitor 报告为 `partial`（数据积累中），不算失败也不算成功；其他失败按失败处理。
  指标 `factor_gap_pending`、`factor_gap_skipped_total`、`factor_gap_gave_up_total`、`factor_gap_ledger_degraded`、`factor_series_change_gaps_total`（变更日志断档次数）。
- **永久审计。** 账本即审计，可用 DuckDB 的 `read_json_auto` 或 `jq` 分析。

### 生命周期

> 状态：已实现。`packages/lifecycle` 只管模块级状态：运行、暂停、恢复追赶；各模块共同的约定见[总体设计](../总体设计.md) 7.5 节。

**模块级**：引擎只有运行、暂停（手动 / 系统）、恢复追赶三种状态，持久化在 `data/engine/lifecycle.json`；
因子任务没有自己的阶段，也不需要任何生命周期命令。

**任务检查**：每个任务计算前要过一组检查，检查通过且模块在运行才计算，不通过就不计算，并在任务状态里写明哪一项没过和处理办法。检查项：
- 有启用成员；
- 本地窗口已载入完成；
- 本地数据覆盖：每个标的本地连续的根数不少于数据源的回看数量 N（`window.lookback` 等，见第 6 节），或者是新标的（本地最早一根就是 Storage 的首根，且 N 不超过数据集保留期能容纳的根数）；
- 数据源变更日志没有断档、窗口内存没有超过预算（检查项“变更同步”；失败项带处理办法，例如 `moox-factor-engine reconcile --task <任务 ID>`）；
- 任务里因子的回看没有超过回看数量 N（检查项“回看数量”）；
- 数据源上有数据（“本地数据”“没有数据的标的”两项，见上文“没有任何数据的标的不拖住任务”）；
- 引用的自定义算子模块已就绪；
- 另有长缺口一项，只警告。

检查的时机与查看：
- 引擎每 30 秒（`lifecycle.interval`）重查一次，窗口载入完成后立即重查（已知差别：载入完成的重查偶尔会被同时进行的周期重查用旧结果覆盖，任务最多晚 30 秒开始）。
- 窗口没载入时自动唤醒预载，载入后自动开始计算。
- 检查结果按任务缓存，重启后从“不通过”开始；“本地窗口”一项不看缓存，目录变化触发重新预载时，窗口一失效就停止计算，直到重新载入。
- 检查结果随心跳上报给因子管理，用 `moox-cli factor task status [--task-id <任务 ID>]` 查看；加 `--recheck`（配合 `--task-id`）让引擎经 EngineControl 的 `CheckTask` 立即重查并直接返回结果。
- 新建任务的第一个结果要等三件事：引擎同步目录（每分钟第 45 秒）、预加载完本地窗口（源数据有 5 万根历史时可达一两分钟）、下一个源数据周期收盘。

**暂停与恢复**：命令是 `moox-cli lifecycle pause|resume|release|catchup`，默认操作 factor-engine。
- `pause [--reason 原因] [--for 2h]`：暂停详情带类型、原因、操作者和时间；手动暂停只有 `resume` 才恢复。
- `resume` 先进入**恢复追赶**：不计算实时周期，只做追赶门禁放行的历史写入，追平后自动放行。
- `--manual-release` 让追平后停在待放行，等 `release`（系统级恢复用）。
- `catchup` 查看追赶进度。

**后台写结果路径也受门禁约束**：补算作业、缺口恢复、失效重算都经过补算执行器。
- 模块暂停、恢复追赶期间，以及任务检查不通过时，执行器返回 `ErrGated`，不记失败。
- 补算作业随即归还给管理端，放行后重新领取，从已上报的进度续跑。
- 因子目录还没载入时不领取补算作业。
- 实时事件用实时门禁，连续水位追赶用实时门禁或追赶门禁。

**恢复追赶**由模块级 `Catchup` 钩子逐个汇总参与追赶的任务。
- 参与者：除“本地窗口”外还有不通过检查项的任务本来就不计算，不参与追赶、不挡住引擎放行，检查通过后由连续水位从断点补算；
  只是窗口没载入的任务照常参与（例如系统暂停期间重启了引擎，载入记录只在内存里、暂停期间预载循环不运行），由下面第 1 步载入窗口并立即重查，在那之前报未追平。
- 参与者在恢复途中才出现检查不通过，会在下一次重查（每 30 秒）时被排除；变更日志断档在每次汇总追赶进度时按当时的状态直接判断，出现即排除（断档的任务不再建追赶目标、不推进水位）。其余任务照常追平、放行。

每个参与的任务依次做四步：
1. 后台同步本地数据：`Data.Prepare` = Follow 已有范围的修正 + Pull 新增尾部 + 重载内存窗口，每次恢复做一次；同步会载入窗口并立即重查任务。
2. 显式建立追赶目标：暂停区间内最新已收盘周期，扣采集宽限。恢复追赶的目标由 `Continuity.NoteTarget` 显式建立，不等下一条实时事件。
3. 唤醒连续水位追赶循环，在追赶门禁下补算暂停区间每个周期并发布历史结果。
4. 水位追到目标且没有阻塞，才算这个任务追平。

追赶的阻塞与放行：
- 参与追赶的任务全部追平、本次恢复之后目录同步成功过、参与追赶的任务引用的自定义算子模块全部就绪，模块才算追平；被排除的任务用到的算子编译失败不挡放行。
- 变更日志断档（暂停超过保留期或 Storage 身份变化）时增量同步追不上：任务检查的“变更同步”一项不通过，任务被排除出追赶、不再计算，需要人工离线维护（`moox-factor-engine reconcile` / `backfill`）。
- “检查不过的任务不挡放行”只在引擎内部成立：被排除的任务如果有启用的策略实例在读它的结果，策略等不到暂停区间的因子结果，系统恢复会卡在策略追不平。
  策略只由所绑 View 的 `ViewDataReady` 事件触发，策略追赶要求每个启用、有会话的实例都处理到最新一根，所以停用这个因子任务对策略侧没有任何影响，
  策略没追平时它的 `release` 会被拒绝。处理办法是停用读它的策略实例（`moox-cli strategy instance disable`），或把任务修好；
  停用后重新启用会清空实例的确认列，挂了账户的实例要重新确认实盘。其余模块追平后，`moox-cli system resume --release-partial --yes` 放行已追平的模块。
- 本地窗口一直载入失败时，引擎自己追不平：窗口没载入的任务仍参与追赶（与“检查不过就排除”不同），`moox-cli lifecycle release` 与 `--release-partial`
  都放不了引擎，`system resume` 的输出里会显示“同步本地数据失败：……”。处理是把数据问题修好；或 `moox-cli factor task disable` 停用该任务
  （下一次目录同步把它移出追赶），读它的策略实例也要停用（理由同上）。
- 系统恢复时由 `moox-cli system resume` 保证采集先补采完、因子才开始同步。
- 已知差别：源数据所在空间被手工暂停采集（`moox-cli collector fetch-plan pause`）时，系统恢复追赶跳过这个空间，读这个空间的任务判为 `no_rows`、水位卡住，模块追不平。这时先停用这些任务（`moox-cli factor task disable`），读它们的策略实例也要停用（`moox-cli strategy instance disable`，理由同上），放行后再启用，挂了账户的实例要重新确认实盘。

**上报与依赖链**：
- 心跳里的任务暂停标记只跟着模块：暂停、放行前的恢复追赶都算。
- 检查不通过的任务不标暂停，照常做新鲜度检查。
- 接口是 EngineControl 的 `GetLifecycle`、`ControlLifecycle`（只给 moox-cli，经网关到达）。模块状态（含暂停类型、原因与追赶进度）随心跳交给 factor-mgr，由它代报给 Monitor，首页的系统状态读它；引擎的就绪判断也一样代报。
- 依赖链向下传：数据源断档 → 因子任务检查不通过、不计算 → 它的策略实例收不到新事件，没有新目标、持仓不动。

## 4. 补算

补算作业按目标区间 `[start, end)` 执行，按 `recalc.chunk_periods` 分块（当前默认 500 个目标周期），块内不拆分同一 `data_time`
的不同 series_tag，并在块起点前读取所需回看。已完成的块不会因后续失败回滚；同一请求 ID 可
幂等提交。按成员重算时读取原行 `__params` 里可变成员的参数，写回时合并 `__params`；只重算固定成员时不读不写 `__params`（第 2 节、第 11 节）。补算可以按因子和标的缩小范围，但不能改变定义里的输入、输出和参数。

引擎通过 `PullRecalcJob` 领取任务，每完成一块用 `ReportRecalcProgress` 上报。作业没有租约：只有登记的引擎进程（`engine_id` 加 `boot_id`，心跳未过期，见下文“引擎登记”）
能领取和上报，**运行中的作业也可以领取，并且先返回运行中的那一条，没有运行中的才把一条待领取的置为运行中**，所以同时只有一条作业在跑。
引擎重启、管理端重启、引擎崩溃或上报失败放弃作业之后，下一次领取拿回的都是这条运行中的作业，从管理端记下的 `progress_time` 续跑；旧进程（被新 `boot_id` 顶替的）的上报被拒绝。
引擎放弃作业时（被生命周期门禁挡住超过 5 分钟、模块暂停、引擎正常停止）用同一个接口以 `status=accepted` 归还：作业回到待领取并保留进度；
领取按作业最近一次变动的时间从早到晚排，归还的作业排到其他待领取作业之后。运行中的作业所在任务的结果数据集暂时没就绪时，领取把它退回待领取，改发别的作业。

**启用不自动补算历史。** 启用成员只让它参与此后每期的计算，不提交回填作业；需要历史因子值时用 `moox-cli factor recalc submit` 或控制台「补算」指定范围。
原因：自动回填会按结果数据集的保留期往回算，写出几百万行因子结果，再由 Storage View 逐行消化，初始数据导入后会把 View 积压数小时（见 skill 的[初始数据导入](../../skills/moox/references/initial-import.md)）。

补算写回的结果受 Primary 自己的保留策略约束；结果 View 另有 `[storage_view.max_age]` 写入年龄上限（默认 1m 7d），超过上限的历史结果在 View 写入时被丢弃且处理仍成功。因子本地历史与计算不受该 View 限制，不能仅凭 View 没有旧结果判断补算未写入 Primary。

**补算对 Storage 的负载防护**（2026-10-14 两个 1h 因子任务同时回填，把 4 核主机上的 Storage 进程打到 330% 以上、读窗口反复超时之后加上的）：

- **同时只跑一个补算作业**：领取在同一个事务里先找运行中的作业，有就返回它，不再发出新作业（见上文）。
- **补算读本地。** 补算、只填充与失效重算都从本地时序存储读 `[回看起点, 终点)`，不向 Storage 逐批读窗口，没有读取并发、退避与断路的配置；分块大小由内存准入与 `compute.max_memory` 约束。补算分块遇到基础设施错误的重试仍是指数退避（5 秒起，上限 2 分钟）。
  **补算前先延长本地历史**：补算区间（加回看）早于本地最早数据时，那些周期所有标的都“没有行”会整段失败（作业还显示成功），例如手动补算的区间远早于只预载了回看根数的本地数据。所以领取补算作业后、读之前，引擎先把本地历史从 Storage 补到覆盖「区间起点 − 回看」（与离线 `backfill` 命令同一实现，
  Earliest 前移会登记失效重算）；补历史失败只记日志，仍用已有的本地数据计算，Storage 保留期里没有那么早的数据时有多少补多少。
  同样，Storage 里比本地最新一根更晚的数据平时留给实时计算去拉；补算区间落在这段上时（例如强制补采写入了新的周期、不发实时事件，
  或任务刚建好还没跑过实时周期），执行前先把本地往后拉到补算区间的终点（不超过最新已收盘的一根），并同步到内存窗口，否则读不到源数据、
  写出 0 行而作业仍然成功。只拉数据源登记范围内、本地已有数据的标的（没登记过的数据源、本地还没有数据的标的都不拉）。
  拉取失败（包括有标的读取失败）时记日志（`factor_recalc_catch_up_failed`），作业照常继续。
- **任务离开目录时释放窗口。** 预载循环对账目录：删除、停用的任务取消它们在数据源上的登记；
  数据源没有其他任务登记时丢弃它的内存窗口与同步状态并释放常驻内存预算，还有其他任务时下次准备按其余任务的标的并集与最大回看收缩。

## 5. 管理端与引擎的协作

- **目录同步。** 引擎启动时立即同步一次，之后在每分钟第 45 秒调用 `SyncEngineCatalog` 拉取带哈希的目录快照并落盘
  （`data/engine/catalog.json`）；管理端不可达时继续用最后一份快照计算。新启用的成员在引擎下一次
  同步之前的周期不会自动补算，需要时手动提交补算。引擎安装快照时编译全部定义（派生字段以编译结果为准）；
  补算作业自带完整定义，引擎领取后现场编译，不依赖目录同步。引擎侧编译失败（只在管理端与引擎的 expr 版本不一致时出现）
  只让该因子本期对全部标的失败，计入 `factor_compile_errors_total`。
- **引擎登记。** 系统只有一个引擎。引擎每 10 秒调用 `EngineHeartbeat`，管理端记下当前引擎进程（`engine_id` + 每次启动生成的 `boot_id`）
  和最后心跳时间，45 秒内有心跳算在线。引擎重启（同一 `engine_id`、新的 `boot_id`）立刻顶替旧进程，不用等；
  另一个 `engine_id` 在当前引擎心跳还新鲜时来心跳会被拒绝（误起了第二个引擎）。心跳同时上报各计算任务最近的运行摘要；平时每 10 秒一次，每算完一期立刻补发一次。
- **状态。** `FactorMgr.GetStatus` 返回引擎是否在线、最后心跳时间、目录是否与管理端一致，
  消费者、任务执行器、计算线程数、引擎与管理端各自的 expr 语义版本（不一致时控制台标红），以及最近运行情况。
- **监控。** 管理端把引擎心跳中的运行摘要转换为因子结果数据集的数据集指标，由 Monitor 的数据集
  新鲜度检查覆盖因子计算。每收到一次被接受的心跳就立刻刷新这些指标，水位前进时补报一份快照，
  Monitor 约 1 秒内看到这一期的完成时刻（不再等 30 秒的定时上报）。同一期只记一次，除非结果变好：
  从不正式（预热中、出错，不推进产出水位）变为正式、或从不完整变为成功时再记一次（补算补齐了这一期），
  产出水位随之前进，到达时间是补齐的时刻，“数据积累中”当场消失，不用等下一期；水位已经推进过的一期升级为成功时
  水位不动、到达时间不变，管理端主动补报一次。

## 6. 表达式语言

因子定义（spec）是一份 YAML 文档：

```yaml
params:                            # 可选：可调参数的声明（类型、范围、默认值）
  window: {type: int, min: 2, max: 120, default: 20}
let:                               # 可选：有序的中间量，后面的可以引用前面的
  ma: ts_mean(close, window)
output: close / ma - 1              # 单输出写 output（列名就是成员键）；多输出写 outputs: {输出名: 表达式, …}
cross_section_history: current     # 可选：历史截面的标的全集，current（默认）或 observed，见下文“历史截面的全集”
```

- 表达式支持数字、`true`/`false`、空值常量 `nan`、标识符、`+ - * / % **`、比较、`and`/`or`/`not`、`c ? a : b` 与已登记的函数调用；
  字符串只能写在 `cs_ref` 的标的参数位置；其余语法一律拒绝，报错带字段路径和行列。`nan` 是保留字（不能作参数名或 `let` 名），
  不能写在窗口、位移、分位数等编译期位置；常量运算算出 NaN 时报错，只有运算里写了 `nan` 时才允许。窗口、位移等位置只接受整数字面量，或一个范围落在算子允许范围内的**整数参数**；
  其余数值位置可以放字面量或任意参数。参数声明的未知键、范围不合法、默认值越界都在编译时拒绝；联合约束（如 `sma` 的 `m < n`）
  对声明范围的全部取值都要成立。
- 函数分三类：逐元素（`abs`、`log`、`where`、`clip`、`fill_nan`、`floor`、`ceil`、`round` 等）、时序（`delay`、`ts_mean`、`ts_std`、`ts_rank`、
  `ts_corr`、`ema`、`sma`、事件记忆 `ts_last_valid`/`ts_bars_since`/`ts_value_when` 等）、截面（逐行变换 `cs_rank`、`cs_zscore`、`cs_demean`、`cs_scale`、
  `gs_rank`、`gs_demean`、`gs_zscore`、`gs_cumshare`、`cs_resid`、`gs_resid`；聚合广播 `cs_mean`、`cs_sum`、`cs_count`、`cs_std`、`cs_median`、`cs_quantile`、
  `cs_min`、`cs_max`、`cs_corr`、`cs_ref`、`gs_mean`、`gs_sum`、`gs_count`、`gs_median`、`gs_wmean`、`gx_rank`、`gx_zscore`）。完整清单、参数范围、回看规则与说明
  由 `ListFactorFunctions` 返回，控制台编辑器的函数参考面板即来源于此；`factorexpr functions` 与它同源。`round` 在 0.5 处远离零取整。
- 空值语义：null 与网格上缺失的行读作 NaN；普通算子遇到 NaN 向后传播，`where` 的未选分支、`fill_nan` 与 `is_nan` 按各自契约处理；±Inf 一律记为 NaN；
  **严格窗口**：时序窗口内只要有一个 NaN 结果就是 NaN，没有 `min_periods`；截面算子跳过输入为 NaN 的标的（两类截面函数的输出规则见下文）。
  写入时 NaN 为 null。
- **宽松窗口算子**（`*_relaxed`）：底层能力，让序列开头、窗口还没攒满时也能出值：`ema_relaxed(x, n, k)`，以及 `ts_sum`、`ts_mean`、`ts_min`、
  `ts_max`、`ts_std`、`ts_var`、`ts_zscore`、`ts_rank`、`ts_median`、`ts_skew`、`ts_kurt`、`ts_argmax`、`ts_argmin`、`ts_product`、`ts_count` 的 `(x, n, m)` 版本，
  `ts_quantile_relaxed(x, n, q, m)`、`ts_corr_relaxed(x, y, n, m)`、`ts_cov_relaxed(x, y, n, m)`。
  - **含义**：严格算子（`ts_mean`、`ema` 等）要凑满窗口才出值，不足时为 NaN；宽松算子在窗口开头是 NaN（序列还没开始）时，在有效值上计算，
    有效值不少于 `m` 个就出值，相当于 pandas 的 `rolling(n, min_periods=m)`；`ema_relaxed` 从序列第一个有效值开始递推，相当于 `ewm(span=n, adjust=False)` 从首根算起。
    有效值之后再出现 NaN 时仍为 NaN（这一点和 pandas 不同，pandas 的 `min_periods` 会跳过中途的 NaN）。
  - **约束**：`m` 不能大于 `n`；m 的下限沿用严格版本对 n 的下限（`ts_std`、`ts_var`、`ts_zscore`、`ts_corr`、`ts_cov` 为 2，`ts_skew` 为 3，`ts_kurt` 为 4）。
    回看与对应的严格算子相同；宽松版与严格版共用同一个统计函数，窗口里没有 NaN 时结果逐位一致，所以只影响序列开头那一小段。
    `ts_rank_relaxed` 的百分位分母是窗口内的有效个数；两个序列参数的 `ts_corr_relaxed`、`ts_cov_relaxed` 的任一条序列在窗口里有中途 NaN（即使落在另一条序列开始之前）时为 NaN，否则从两条序列都开始的位置起取共同的有效尾段，有效对数 ≥ m 才出值。
    本地时序存储保证序列在 `[Earliest, Latest]` 上连续（缺失周期写成填充行），所以输入列的 NaN 只在序列开始之前。
  - **适用场景**：还原外部（pandas 等）因子在上市初期也出值的行为。**不要默认使用**。
  - **取舍（重要）**：宽松窗口用 1～2 根数据算出的均值、标准差噪声很大，`ema_relaxed` 的开头值带着起点偏差（通常要约 3～5 倍 span 才稳定）。
    在截面排名、选币策略里，新上市标的会因此从第一根就参与排名，更容易被噪声推到极端位置。**新写的因子优先用严格算子**，
    在策略里用 `aged_out`（年龄剔除）、`min_universe` 等机制排除历史不足的标的；只有需要与外部结果逐值对齐时才用宽松算子，并在迁移验收里单独核对序列开头。
- **截面函数的两类空值规则**：截面函数按 (data_time, series_tag) 分组，只在成员的标的范围之内计算，范围外的行为 NaN。
  - **逐行变换**（`cs_rank`、`cs_zscore`、`cs_demean`、`cs_scale`、`gs_rank`、`gs_demean`、`gs_zscore`、`gs_cumshare`、`cs_resid`、`gs_resid`）：
    输入为 NaN 的行不参与统计，该行输出 NaN。
  - **聚合广播**（`cs_mean`、`cs_sum`、`cs_count`、`cs_std`、`cs_median`、`cs_quantile`、`cs_min`、`cs_max`、`cs_corr`、`cs_ref`，分组的 `gs_mean`、`gs_sum`、
    `gs_count`、`gs_median`、`gs_wmean`、`gx_rank`、`gx_zscore`）：输入为 NaN 的行不参与统计，
    统计量写给同一截面（分组函数是同一组）的**每一行**，包括输入为 NaN 的行和这一刻没有源行的序列；没有有效样本时整个截面为 NaN（`cs_sum`、`cs_count` 也是 NaN，不是 0）。
    `cs_count` 只收布尔，`cs_std` 有效样本少于 2 时为 NaN，`cs_quantile` 的 q 只收 0～1 的字面量（不收参数，所以流入截面算子的参数仍然没有）。
  - **条件截面**写成 `cs_rank(where(c, x, nan))`：只在 c 为真的标的里排名，其余为 NaN。截面比例、个数参与比较时有 1e−16 级的浮点误差，阈值要留余量。
  - **参考序列** `cs_ref(x, "BTC-USDT")`：取同一截面里该标的的 x 广播到每一行，它本期不在截面里或 x 为 NaN 时整个截面为 NaN。
    保存定义时只检查标的 ID 的写法；加成员、启用成员、启用任务时由管理端读取源数据集的标的（`ListDatasetSubjects`），参考标的不在其中就拒绝，错误里写出标的 ID。
    用到它的因子是截面因子，建议 `allow_partial_universe: true`。
  - **截面相关** `cs_corr(x, y)`：x、y 都有效的行上的皮尔逊相关，有效对数少于 3 或任一方方差为 0 时为 NaN；秩相关写成 `cs_corr(cs_rank(x), cs_rank(y))`。
  - 时序套截面每期要重算多个历史截面；`factorexpr check` 输出 `cross_section_points`（计算一个目标时刻时各截面算子的需求区间长度之和），用来估算计算量。
- **分组截面**（`gs_*`、`gx_*`）：分组键 g 是源数据集里的数值列（例如行业代码），参数类型为 group，必须依赖输入列。每个截面内按 g 的取值分组
  （−0 与 0 同组），g 为 NaN 的行不属于任何组，逐行变换与聚合广播都输出 NaN——这一刻没有源行的序列 g 也是 NaN，所以分组聚合不像 `cs_mean` 那样写给它。
  - `gs_rank`、`gs_demean`、`gs_zscore` 与 `gs_mean`、`gs_sum`、`gs_count`（只收布尔）、`gs_median` 在每组内按对应 `cs_` 函数的口径计算；
    `gs_wmean(x, w, g)` 是 Σw·x / Σw，w ≤ 0 或 NaN 的行不参与；`gs_cumshare(x, g)` 组内按 x 降序（并列按标的 ID）累计到本行的占比，排在最后的一行恰好为 1；x 应为成交额、市值这类非负量，组内有负数或总和为 0 时整组为 NaN。
  - `gx_rank(v, g)`、`gx_zscore(v, g)`：每组取 v 的有效均值作为该组的值（v 通常是 `gs_*` 的结果，组内为常数；组内全为 NaN 的组不参与），
    在组之间按 `cs_rank`、`cs_zscore` 的口径排名或标准化，再写回组内每一行。
  - 一个截面最多 1000 个组；超出时整个截面为 NaN，并计入失败指标 `factor_failures_total`（`reason="gs_too_many_groups"`，`factor` 是成员键）。
- **截面回归残差** `cs_resid(y, x1[, x2 … x8])`、`gs_resid(y, g[, x1 … x8])`：每个截面上 y 对截距（`gs_resid` 为每组一个截距，即分组哑变量）与 1～8 个自变量
  做最小二乘，输出残差；任一变量（`gs_resid` 还有 g）为 NaN 的行不参与、输出 NaN。实现先按截面（或组）对 y 与各 x 去均值，再对去均值后的 x 做
  Householder QR、求不带截距的回归，与带截距或哑变量的完整设计矩阵结果相同；`gs_resid` 不给 x 时与 `gs_demean(y, g)` 逐位相同，例外是样本不足：有效行数不超过组数（例如每组只有 1 个样本）时 `gs_resid` 整截面为 NaN 并计告警，`gs_demean` 则给这些行 0。
  有效行数不超过参数个数（`cs_resid` 为 k+1，`gs_resid` 为 k+组数），或某个 x 与截距、哑变量、其他 x 共线时（判定：消去截距、哑变量与前面的 x 后剩下的范数
  不超过 max(n, k)·ε·去均值前的原列范数，即按各列自身的尺度判定；只差几个 ulp 的近似常数列也判为奇异），整个截面为 NaN，
  并计入 `factor_failures_total`（`reason="cs_resid_singular"`）；整个截面没有有效行时只是 NaN，不计数。
  与 numpy `lstsq` 对拍时先把各列标准化或去均值；相对误差 1e−9 只对条件好的数据成立，接近奇异时两边的判定与数值都可能不同。
  - 告警只统计目标区间内的截面（时序套截面时向前多算的历史截面在它自己作为目标的那一期统计），计数是截面个数；值照常写成 null，不改变成员状态。
- **历史截面的全集** `cross_section_history`：写在 spec 顶层，只对截面因子有效（时序因子写 `observed` 时保存即拒绝）。
  - `current`（默认，不写也是它）：每个历史时刻的截面只用本期可用的标的（期望全集 ∩ 本期可用），本期不可用、但历史上存在的标的被排除。
    “过去 N 根是否进过前 10%”“滚动秩相关”这类时序套截面的因子因此带幸存者偏差。
  - `observed`：历史时刻的截面由本地存储里在读取区间内有数据的标的组成，与本期是否可用无关；每个时刻只让这一刻在网格上有源行的
    序列参与截面（目标时刻也是：本期同步失败、迟到的在册标的这一刻不参与），所以 `cs_rank(delay(close, 1))` 这类表达式不会让
    已下架的标的带着上一根的值进入目标期截面；
    已下架或移出全集的标的仍参与它们还在交易时的历史截面，新加入并回补了历史的标的也参与加入之前的截面。
    observed 与 current 只在目标期截面上可比：对在册标的，历史截面也可能不同（例如 `ts_mean(cs_count(x), n)` 在新上架标的上架之前的时刻，current 把聚合值广播给它，observed 给 NaN）。
    额外纳入的标的只有两类（截面只在成员的标的范围内计算，历史截面也一样）：本任务范围里本期不可用的标的，以及已经没有任何任务在同步的标的
    （已下架、已移出）。**其他任务正在同步、而本任务范围不含的标的不纳入**：它们本期的数据到没到取决于那个任务先跑还是后跑，
    纳入会让结果随执行顺序变化。**“正在同步”只有一个来源**：预载最近一次从 Storage 取到的数据集在册清单（任务的标的就是在册标的）。
    实时、补算、研究回放都读这同一份清单，清单变了立即生效；预载查询失败时沿用上一次的清单。所以同一期的结果只取决于计划
    （期望全集、上游失败）、这份清单与本地存储的内容，与任务执行先后、重启时的就绪先后无关。
    清单与本地存储不变时，实时、补算全部标的、研究回放彼此逐位相同；这只对“没有源行时一定得到 NaN”的表达式成立。三种模式取历史标的的
    区间不同（实时：本期的回看窗口；补算：本块的读取区间；回放：整个快照区间），某个标的没有源行、表达式却能算出值时
    （例如 `fill_nan` 填了常数），它在这一刻不参与截面，但区间不同会让它是否算历史标的不同，结果可能不同。不同的情形见下面的已知差别表。
    内存窗口不按这份清单过滤：回看区间内、不在任何任务范围里的本地标的全部载入，过滤放到每期计算时做；万一窗口里缺了某个历史标的，
    这一期改读本地磁盘并记告警（factor_history_subject_outside_window）。
    它不与当前全集名单求交（全集只含在册标的）；对按指数成分划定的全集，它不等于“当时的成分股”。
    本期不可用的标的只在本期没有结果行；上游判为失败的标的与序列仍不进面板，**那一期它们的历史也不进历史截面**（数据不可信，整条不用）；
    `allow_partial_universe: false` 的门禁只看本期。内存预检与补算选块（按本块的区间列出）都把这些标的计入。
  - **试算是近似口径**：管理端没有本地存储与任务登记，只能直接读 Storage。它把源数据集里在册（active）的标的都当作“有任务在同步”，
    只纳入不在册（已下架、停用）且试算区间内有行的标的（每批最多 200 个标的、只读一列确认；连同本期标的不超过 2000 个，
    超过时尽早报错，候选数超过 max(余量的 4 倍, 8000) 时不读取直接报错；报错里给出处理办法：缩小任务范围，或试算时去掉
    `cross_section_history: observed`。先按本期标的数做一次内存预检，再探测历史标的）。与实时的差别见下面的已知差别表。
  - 多出来的标的只读本地历史，**不同步、也不再跟进源数据的修正**；它们的窗口照常占内存，内存预检按扩大后的序列数估算。
    有 observed 成员的任务每期会多一次本地标的边界扫描（只读边界键）；没有 observed 成员的任务不扫描。
    同一数据源上只要有 observed 任务，整个数据源的内存窗口都会多载这些历史标的，窗口内存估算也随之变大。
    窗口里缺了某个历史标的时，到下次预载之前每期都会改读本地磁盘（每期一条告警）。
    研究回放里截面回归奇异、组数超限的告警只体现为 NaN，不计入 `factor_failures_total`。
  - **实时、补算、回放、试算之间的已知差别**（不另加机制消除，按下表处理）：

    | 场景 | 差异 | 处理方式 |
    | --- | --- | --- |
    | 某个标的下架或移出（不再在册） | 之后补算、回放它在册时的旧期次，历史截面多出这个标的（当时它在当前截面里），与当时的实时值不同 | 接受；需要统一口径时补算整段 |
    | 下架、上架前后的几期 | 事件里冻结的全集与预载的在册清单本来就有先后差，这几期的历史截面可能一时多或少一个标的；清单滞后期间发起的补算或回放，整个区间都按当时的清单计算，都会受影响 | 接受；清单更新后下一期起一致，需要时重新补算受影响的区间 |
    | 预载还没取到过清单（引擎刚启动后的补算） | 这时“正在同步”为空，只按本期全集排除；本期全集就是在册标的，结果相同 | 无需处理 |
    | 本地存储清空或全新安装 | 已下架、又没有任务同步的标的不会被重新拉回本地，从历史截面里消失，observed 的值改变 | 接受；需要时先导入历史数据再补算 |
    | 指定部分标的的补算 | 没列出的在册标的不进截面，与实时不同 | 含 observed 成员时直接拒绝，请补算全部标的 |
    | 试算 | 直接读 Storage：纳入的标的与实时相同（不在册、区间内有行），数据可能不同（本地未同步的修正、保留期外的数据） | 试算只作预览；以补算结果为准 |

    以上任何一种都不改变定义哈希；旧期次需要按新口径重算时补算。
  - 同一任务里两种口径可以混用：current 成员的截面用范围掩码限制在本期可用的序列之内，结果与只有 current 成员的任务逐位相同；
    只有 current 成员的任务面板与原来完全相同。
  - 定义哈希：只有写了 `observed` 时才追加标记，不写或写 `current` 的哈希不变；从 `current` 改成 `observed` 会改变哈希，引用它的策略报 `factor_changed`。
  - 实测（Apple M4、4 个工作线程、500 个标的、回看 1000、`ts_mean(cs_rank(close), 1000)`，另加 100 个已下架标的的历史）：
    一期实时计算 current 约 11 ms、分配 13 MB，observed 约 14 ms、分配 16 MB；`compute.max_memory` 口径的估算峰值 8.3 MiB → 10.0 MiB。
- **factor-mgr 与引擎要用同一版编译器**：两边各自编译定义（共用 `packages/factorexpr`）。`GetStatus` 只比较表达式语义版本（`ExprVersion`），
  新增函数不改这个版本号，所以两边的二进制不一致时系统发现不了：引擎编译用到新函数的定义会失败，该成员按编译失败处理（第 5 节）。发布时两者一起换。
- **事件记忆的“窗口有界”**：引擎不跨点保存状态，`ts_last_valid(x, n)`、`ts_bars_since(c, n)`、`ts_value_when(c, x, n)` 只在最近 n 根（含当根）里回看最近一次事件，
  窗口里没有事件时为 NaN；c 的真值判定是“非 NaN 且不为 0”，距今根数当根记 0，回看为 L(x)+n−1。
  所以只有最近一次事件落在最近 n 根以内时，结果才等于无限期前向填充：n 要按“最长停留时长”取（上限 100000），迁移状态类因子时要统计窗口内没有事件的点数。
  执行时每条序列正向扫描一遍，不在每个点上回读 n 根，复杂度为 O(输出点数 + n)。需要严格递推的状态（以截断后的值为基准）写成自定义算子。写法示例见
  [`factor-dsl.md`](../../skills/moox/references/factor-dsl.md) 的“窗口内事件记忆”。
- 回看由编译推导（例如 `ts_rank(ts_mean(x, 20), 20)` 是 39）；`ema`/`sma` 截断到权重低于 1e−9 的 K 根（`ema(x, 20)` 为 208）；`ema(x, n, k)` 可显式指定预热总根数 K=k（含起点那一根，回看就是 k；k 不写或为 0 按通常方式；n 远大于 k 时起点权重不可忽略，是近似值）。例如 `ema(close, 20, 50000)` 是 EMA20（α = 2/21）用 5 万根预热，与逐根递推 49999 次一致。
- 限制：spec 64 KiB、单条表达式 4096 字符、最多 64 个输出、窗口 1～100000（实际受回看上限约束）、推导出的回看不超过 100000。

因子库位于 `modules/factor/factors/`（`*.yaml`，每个文件是 `[{factor_id, name, spec}]` 列表），
用 `moox-cli factor import --dir ./factors` 导入（经 `FactorMgr.ImportFactorCatalog`，任一因子已存在或编译失败时整批拒绝；已知差别：带 `category_name` 的分类在定义写入的事务之外先写，定义写入失败时分类可能已经新建或改了名，并且会把已有分类的排序覆盖成 0）；单个定义用 `moox-cli factor create`。因子 ID、输出名、参数名都是小写（语法见第 2 节「成员键与列名」）；单输出因子写 `output: <表达式>`，多输出因子写 `outputs`。
示例见 [`examples/factors`](../../examples/factors/)。

内置因子库有三个文件：`xbx.yaml`（动量、成交量、波动类，由旧 Python 因子转写）、`common.yaml`（常用技术指标）与 `stockcn_daily.yaml`（A 股日线因子：`mom_adj`、`roe_ttm` 读后复权因子与财务列；筹码类 `chip_profit_ratio`、`chip_avg_cost`、`chip_concentration` 另外要读换手率 `turnover_rate`；估值类 `total_mv`、`float_mv`、`pe_ttm`、`pb`、`ps_ttm`、`dv_ratio` 要读股本 `total_shares`、`float_shares` 和每股股利 `dividend_per_share`。只能用在带这些附加字段的日线数据集上）。

**估值类因子**：市值是“当日不复权收盘价 × 股本”，市盈率、市净率、市销率是总市值除以归母净利润（滚动十二个月）、归母股东权益、营业收入（滚动十二个月），股息率是每股股利除以收盘价。股本和每股股利来自只有当日值的接口（见 [采集](采集.md) 第 4b 节），所以先取 `ts_last_valid(列, 20)`：某天没采到时沿用最近 20 个交易日里最后一个有值的，开通之前为空。分母为 0 或为空时因子值为空；亏损股的市盈率、净资产为负的市净率是负数。

**筹码分布**（算子 `chip_profit`、`chip_cost`，三个筹码类因子基于它们）：用最近 n 根的开高低收与换手率推算持仓成本的分布，只依赖窗口，每个输出点重算一遍。

- 价格档：窗口最低价到最高价之间取 150 个等距的价格。窗口内价格没有波动时为 NaN。
- 从早到晚逐根处理：各档先乘 `1 − 换手率`（换手率是百分比，超过 100% 按 100%）；再把当根换手的筹码加到最低价与最高价之间的档上：每根加入的总量固定为 `换手率 / 档宽`，在覆盖到的档之间按三角形的高度分配，顶点在 `(开 + 高 + 低 + 收) / 4`。一字板或最高最低价都落在两档之间的根，全部加到均价所在的档；只碰到三角形端点的根，加到碰到的那一档。全程没有换手时为 NaN；价格不是正数、最高价低于最低价时也为 NaN。
- `chip_profit(open, high, low, close, turnover, n)` 是价格不高于当根收盘价的筹码占比；`chip_cost(..., n, q)` 是从低价往上累计超过全部筹码的 q 时那一档的价格，`q = 0.5` 是平均成本。n 的范围 20～500，q 的范围 0.01～0.99。
- 价格要用复权价：除权前后的成本换算到同一口径才可比。内置因子用后复权价（`价格 * adj_factor`），平均成本再除以当日的 `adj_factor`，可以直接和当日的不复权收盘价比；它在除权日与收盘价同比例跳变，`close / chip_avg_cost` 不受除权影响。
- 内置因子的换手率输入是 `fill_nan(turnover_rate, 0)`：某天没有换手率时按当天没有换手处理。停牌日本地写成填充行，`turnover_rate` 的列属性是 `fill=zero`（缺属性时按列名默认也填 0），不沿用停牌前的值。默认窗口 210，上市不满窗口长度的标的没有值。
- 与东方财富网页的筹码分布同一思路；不同之处是每根加入的总量固定（网页直接取三角形在各档上的密度，振幅不到一两档的 K 线会被放大好几倍或整根丢掉，一字板用的又是另一个固定值）、没有 0.01 元的最小档宽。所以每根加入的量都和网页略有不同，振幅越窄差得越多，一字板和振幅不到一两档的根差得最多。
- 离线对比（2026-11-11）：10 只沪深 300 成分股最近 210 根前复权日线（窗口里没有一字板），与按网页算法的步骤另写的参考实现在同一份数据上算，平均成本、90% 集中度相同，获利比例最多相差 0.0015。还没有和网页上实际显示的数值比过。

用户自己迁移的因子（例如从外部框架转写的选币因子）不放进仓库，直接用 `import` 或管理台写入系统。
`common.yaml` 的 10 个因子都是时序因子，窗口（`Ema` 为跨度 `span` 与预热根数 `warmup`）是可调参数：

| 因子 | 默认成员的列名 | 窗口（默认，范围） | 回看 |
| --- | --- | --- | --- |
| `ma` 简单移动平均 | `ma` | 20，2～120 | 120 |
| `ema` 指数移动平均 | `ema` | `span` 20，2～4825；`warmup`（预热根数，0 为按通常方式）0，0～50000 | 50000 |
| `macd` | `macd__dif`、`macd__dea`、`macd__hist` | 固定 12/26/9 | 362 |
| `rsi`（Wilder 平滑） | `rsi` | 14，2～120 | 2478 |
| `roc` 变动率 | `roc` | 12，1～120 | 121 |
| `boll` 布林带（±2 倍标准差） | `boll__mid`、`boll__up`、`boll__low`、`boll__pctb` | 20，2～120 | 120 |
| `atr` 平均真实波幅 | `atr` | 14，2～120 | 121 |
| `atr_pct` 平均真实波幅占收盘价比例 | `atr_pct` | 14，2～120 | 121 |
| `return_std` 收益率波动 | `return_std` | 20，2～120 | 121 |
| `vwap` 成交量加权均价 | `vwap` | 20，2～120 | 120 |

窗口上限一般为 120，不为控制回看而单独收紧；EMA 的 span 上限是 4825，自动预热最大回看 49995 根，结合 warmup 上限后定义的最大回看为 50000 根（1m 约 34.7 天）。EMA、MACD、RSI 带指数衰减，回看按“起点权重衰减到 1e-9 以下的根数”或显式预热根数按参数上限推导，所以比同窗口的普通均线长。
最大回看决定要保有多少历史：Storage 的保留期（默认 1m 35 天）和引擎的回看数量 N（`engine.yaml` 的 `window.lookback`，7×24 市场默认 5 万；有交易时段的市场用 `window.session_lookback`，默认 5000；`window.lookback_overrides` 可按数据源 `空间/数据集/频率` 单独指定）都要装得下它，否则 `factor task apply` 拒绝导入，或任务预载失败、整个任务都不出结果（检查项“回看数量”不通过，不参与追赶）；只影响这个任务，同一数据源上的其他任务照常计算。
实际计算按当期参数取窗口：EMA 默认 span=20、warmup=0 只需 208 根，本地历史够就有值；把窗口调大后，本地历史不足该窗口所需根数的那段时间，这个输出为空（严格窗口），同一任务的其他成员不受影响。
回看 5 万根时，500 多个标的单次计算约需 1.1GB 内存，引擎的单次计算上限 `compute.max_memory` 默认 4GiB，超过时整期放弃。哪些因子进哪个任务由因子任务文件决定（默认任务在仓库种子 `config/setup/factor-tasks.yaml`，由 `setup start` 导入；自己的任务用 `moox-cli factor task apply --file` 导入），没有默认加成员。
离线检查与试算用 `packages/factorexpr/cmd/factorexpr`（`functions`、`check`、`eval`，与引擎同一个编译器和执行器）；
把旧 Python 因子转成表达式并逐值核对的完整流程见 [`skills/moox/references/factor-dsl.md`](../../skills/moox/references/factor-dsl.md)。

## 8. 运维

安装或更新引擎（因子机，只支持 Linux）：

```bash
./bin/moox-cli setup deploy --file ./moox.toml --host factor --component factor-engine
```

`factor-engine` 是服务目录里的外部程序组件，登记在因子机的 `[deployments]` 里。部署从模板渲染 `<部署根>/config/factor-engine/engine.yaml`（调过的值写在 `moox.toml` 的 `[overrides."factor-engine"."engine.yaml"]` 里），
由 systemd 用户服务 `moox-factor-engine` 托管（目标机需开启 linger），并等本机 `/readyz` 就绪；`moox.toml` 的 `[deployments_disabled]` 里写了它时只更新文件、单元停掉。
启停与退役改 `moox.toml`（`[deployments_disabled]`，或从 `[deployments]` 删掉）后 `setup deploy --host factor`，详见[部署与运维](../部署与运维.md)。

引擎需要的凭据放在部署根的 `secrets/` 下，必须是 0600 普通文件：因子机的主机签名私钥 `host.key`（引擎和别的组件一样用它、以 `factor-engine` 的身份签名，
经本机主机网关取目录，再直连存储机与控制机的 `11003`）、MooX CA 根证书 `moox-ca.crt`、
EventBus 角色文件 `eventbus/factor-eventbus.yaml`（其中 `ca_file` 指向同一份 `moox-ca.crt`）；健康端口只听本机、不验签。Storage 没有调用方密钥，只靠服务端口只监听本机加网关访问控制。它经控制机的主机网关调 Factor Manager 的 `FactorEngine` 服务。
因子机负责写因子结果，拿到因子机就能写坏因子值、间接影响策略下单，这不在签名的保护范围内；因子机拿不到 `moox-cli`、`console` 的签名能力。因子机只能出站、SSH 只在局域网可达，它的部署与 `doctor` 只能在局域网里做。

常用命令：

```bash
systemctl --user restart moox-factor-engine                   # 重启
/data/moox/bin/moox-factor-engine health                      # 查看 /readyz 详情（默认 http://127.0.0.1:11417/readyz，可用 --url 指定）
/data/moox/bin/moox-factor-engine reset-gap-ledger --config /data/moox/config/factor-engine/engine.yaml --yes  # 引擎停止后删除空洞账本（数据被整体清空之后用）
moox-cli factor recalc submit --task-id <任务 ID> --start ... --end ...  # 提交补算（在操作机上执行）
moox-cli factor purge-dataset --space-id <空间> --dataset-id <数据集> --yes  # 删除没有任务引用的孤立结果数据集
```

已知差别：`factor purge-dataset` 先核对数据集的 `dataset_role` 是因子结果再删；Storage 删完元数据、删行之前失败时，重试会因读不到数据集而被拒，剩下的行这条命令删不掉。

| 现象 | 处理 |
| --- | --- |
| `/readyz` 返回 503 且 `lease_conflict=true` | 另一个 `engine_id` 的引擎还在心跳，停掉多余的引擎 |
| 引擎状态里的 `boot_id` 来回变、补算作业反复被放弃 | 同一个 `engine_id` 有两个进程（另一个在别的目录或机器上）：它们轮流登记、都在计算，不会出现 `lease_conflict` 提示。`engine_id` 部署时按主机名生成，不要拷贝到别处；停掉多余的那个 |
| 日志出现 `factor_catalog_sync_failed` | 管理端不可达；引擎继续用最后快照计算，恢复后自动追平 |
| 事件反复 `factor_period_retry` | 结果数据集未就绪或存储机的主机网关不可达 |
| 补算作业 `running` 但不前进 | 引擎离线或卡在别的工作上：引擎恢复后下一次领取（轮询间隔内）就拿回它续跑；引擎不再回来时用 `moox-cli factor recalc cancel` 取消 |

引擎与管理端的 tRPC 配置里不要启用 `transinfo-blocker` 客户端过滤器：网关客户端的签名头（`X-Moox-*`）走 tRPC 透传元数据，被白名单过滤后会表现为 code 41 或网关拒签。

表达式执行器的资源配置在 `compute:` 段：`workers` 是一次程序执行的并行度（默认 min(4, 核数)），`max_memory` 是一个计算分块
估算峰值内存的上限（默认 4GiB，默认因子 EMA 回看 5 万根时 500 多个标的一期约需 1.1GB，可写 `512MiB` 这样的字符串）。引擎是单个 Go 进程，没有子进程。

本地时序存储、窗口与内存的配置（`engine.yaml`）：

```yaml
seriesstore:
  dir: ./data/seriesstore       # Pebble 目录，无自动历史淘汰，纳入备份
  block_cache: 512MiB           # 块缓存，计入进程内存预算
window:
  max_memory: 4GiB              # 所有窗口常驻内存的上限；新任务会超出时拒绝启用，0 不限制
  headroom: 0                   # 每个序列数组的余量根数，0 取窗口长度的 1/4（至少 16）
memory:
  total_budget: 12GiB           # 进程内存预算，常驻窗口与块缓存先扣除；0 不限制
sync:
  workers: 4
  batch_subjects: 100           # 同步时每批标的数（Storage 单次最多 100 个）
  follow_interval: 30s          # 读取变更日志、应用修正的间隔
lifecycle:
  state_file: ./data/engine/lifecycle.json
  interval: 30s                 # 生命周期检查周期
```

`window.max_memory` 与 `memory.total_budget` 默认 0（不限制）；`compute.max_memory` 的 0 会补成默认 4GiB，不能用 0 关闭计算上限。部署不按本机内存自动校准：在因子机上执行 `moox-factor-engine tune --config <部署根>/config/factor-engine/engine.yaml` 查看建议值，它只打印、不改配置，
输出末尾是一段可以直接贴进 `moox.toml` 的 `[overrides."factor-engine"."engine.yaml"]`，贴进去后重新部署因子引擎生效。公式：总预算 = 总内存 × 60%；窗口上限 = (总预算 − 块缓存) × 40%；单次计算上限 = max(1GiB, (总预算 − 窗口 − 块缓存) × 50% ÷ 并行数)，
并行数取计划启用的任务数（`--tasks`）与核数的较小值；窗口与块缓存超过总预算的 2/3、或扣除后不足 1GiB 时给出警告。

引擎的维护子命令：`reconcile --task <任务 ID> [--subject <标的>]`（数据源变更日志断档后对账，引擎必须先停止）、`backfill --task <任务 ID> --bars <根数>`（把本地最早一根之前、Storage 保留期内的历史回补到指定根数，与本地相接，Earliest 前移会登记失效重算；引擎必须先停止）、`tune`（内存配置建议）。
`engine.yaml` 按严格解析加载，不认识的键会被拒绝；
`config/trpc_go.engine.yaml` 里健康服务的 `timeout` 是 10000；EngineControl（回放、导入的本地写入都走它）的 `timeout` 是 600000，与目录里 `OpenReplay` 的路由超时一致，其余方法由路由按 120 秒截断。

引擎经公网访问存储机与控制机的主机网关，跨主机调用恒定压缩读取与写入的请求和响应（zstd 字典），减少公网带宽。单个周期的结果行（约 500 个标的）在一次 `UpsertFields` 内写完（`write_batch_rows` 默认 1000）。

不要通过清空消费者来恢复积压；先排查任务执行器积压和 Storage 错误，历史修正用补算作业。
引擎指标：`factor_period_total`、`factor_period_duration_seconds`、`factor_period_lag_seconds`、
`factor_failures_total`、`factor_runner_backlog`、`factor_compile_errors_total`、`factor_last_period_time`、`factor_series_change_gaps_total`。

## 9. 回放的“因子现算”服务（EngineControl）

> 状态：已实现，策略回放的“因子现算”来源（`StartReplay` 的 `input=compute`，见[策略](策略.md)第 10 节）调用它。

引擎在因子机本机 `127.0.0.1:11423` 上提供 tRPC 服务 `trpc.moox.factor.EngineControl`（`modules/factor/proto/factor.proto`），由因子机的主机网关按服务目录的路由转发，
回放的三个方法只给 strategy 调用。因子机只能出站，控制机上的策略服务连本机网关 `11003` 打开到因子机网关的反向中转（`gatewayclient` 按目录自动完成）。
回放用三个方法（同一个服务上另有只给 `moox-cli` 的模块生命周期、任务检查与本地写入方法，见第 1 节）：

| 方法 | 作用 |
| --- | --- |
| `OpenReplay(replay_id, task_id, from, to, extra_periods, columns, allow_short_warmup)` | 建立会话：核对本地数据、按预热区间读快照、预留内存。返回参与的标的与被排除的标的（附原因）、各决策周期的 `period_times`（真实时间的 Unix 秒，可回放的区间就是它的首尾）、成员与输出列、源数据集的数值列、预热不足的标的数 |
| `StepReplay(replay_id, period_time, periods, params)` | 从 `period_time` 起按顺序算最多 `periods` 期。每期每个标的至多一行（行里带它这一期的 `series_tag`）：`columns` 里的列本期与上一期的值、请求了 `__params` 时各成员本期实际用的参数、这个标的在本地数据里截至本期的根数（年龄）；另附各成员状态、生效参数与被拒绝的参数 |
| `CloseReplay(replay_id)` | 结束会话，释放内存 |

- **快照与计算**：会话开始时从因子机本地存储取快照（运行中不随修正更新，向内存准入器低优先级预留），每期走实时计算路径；
  快照整段占住预留直到会话结束，所以估算超过“`memory.total_budget` − 常驻内存 − `compute.max_memory`”的会话直接拒绝并提示缩短回放区间（`memory.total_budget` 为 0 时不限制）；
  回放不写结果、不发周期完成事件、不改连续水位。会话只在引擎内存里，按 `replay_id` 区分，闲置 6 小时清理；引擎重启后会话不存在，返回 `NOT_FOUND`，调用方重新建立。
- **候选与校验**：候选只取源数据集当前在册（active）的标的，已下架的（不论何时下架）不是候选、也不在 `excluded` 里；候选里本地数据覆盖到回放的最后一期才参与，不满足的被排除并列出原因。
  本期的可用与出行都不算本地的填充行（同步补的缺失周期），与实时一致。预热起点 = `from − (因子最大回看 − 1 + extra_periods) × 周期`
  （`extra_periods` 是策略引用上一根的深度，0 或 1；年龄按本地数据里序列的第一根算、与快照长度无关，不算进来）；多数标的的本地数据晚于预热起点时（因子前段会是空值）拒绝建立会话并提示先回补或导入，`allow_short_warmup` 可放行。
- **列**：`columns` 必填，可以是成员输出列、源数据集的数值列和 `__params`，不认识的列名拒绝。行里只有请求的列，没有数据、算不出的列不出现；
  本期在快照里没有这条序列的行（还没上市、已经结束）时不出行，出不出行与请求了哪些列无关。
- **参数**：`params` 只给这一步的第一期，没给的成员沿用上一期实际用的参数，再没有就用成员自己的参数；这一步后面各期都沿用。
  引擎对每个成员的参数做与实时提交相同的校验，不合法的成员沿用上一期并在 `rejected_params` 里返回原因，整期不失败；成员键不存在时整步失败。
  参数只存在会话里，不写成员行。帧里的参数包含固定成员（固定值），实时结果行的 `__params` 只记可变成员，策略的 `params()` 只读可变成员，结果相同。
- **包体与超时**：路由用默认的包体上限 4 MiB，单步响应由引擎控制在 3 MiB 以内：放不下时只返回前面几期（至少 1 期），调用方从下一期接着请求；
  一期就放不下时拒绝，提示减少引用的列。路由超时：服务 120 秒，`OpenReplay` 要读整段本地快照，10 分钟。
- **已知差别**（小问题，不另加机制）：
  - 本期的标的全集按标的取（本地最早一根不晚于本期的候选），每个标的取它在快照里本期已经开始、还没结束（第一根不晚于本期、最后一根不早于本期）的序列；
    可用看本期有没有真实的源行（填充行不算）。
  - 标的是否参与回放按它的本地数据判断（覆盖到最后一期即可）。一个标的停更到快照末尾时，回放分不出它是已下架还是暂时没更新（例如本地同步落后、
    回放终点又贴近当前时间），从它最后一根之后起按不存在处理，不报错也不列进排除原因；实时的完成事件会把它记为失败，不允许部分全集的截面因子实时整体跳过，回放在其余标的上照常排序。
    把终点往前挪几根或等同步追上即可。
  - 本地填充行所在的那一期，这个标的不可用，不允许部分全集的截面因子这一期整体跳过；只有实时的完成事件也把它标为失败时两边才一致。
  - 这几条对策略回放结果的影响见[策略](策略.md)第 10 节“回放与实时的已知差别”。
- **源数据集停用列与少见频率**（小问题，不另加机制）：
  - 源数据集的某一列被改成非启用后，同步不再带这一列，而本地时序存储要求每次写入带齐已有的全部字段，这个数据源上的所有任务持续同步失败；把列改回启用即可恢复（只有手工改元数据会触发）。
  - 建任务时只校验频率能整除一天，本地时序存储只支持第 3 节“本地时序存储”列出的 7 种频率；`10m`、`2h` 这类任务能建出来，预载第一步就明确报错，不影响同源的其他任务。
- **要历史因子值**：回放不写结果，要历史因子值用导入加区间重算（`--recalc`）。

## 11. 动态调参

> 状态：已实现。

策略可以在运行中根据行情逐期调整因子参数：第 T 期因子写出后，策略算出第 T+1 期的参数并异步投递给因子管理端，引擎开算第 T+1 期时取用最新的提交值。
每期实际用了什么参数，记在结果行的系统列 `__params`（第 2 节）里，没有单独的冻结记录、参数列或离线补报。

**概念**

- **参数声明**在因子定义里（第 6 节）：名称、类型（`int`/`float`）、范围、默认值。声明进 `definition_hash`，取值不进。
  结构型位置（窗口、位移）只接受整数参数，回看按范围上限推导，所以参数切换时内存窗口永远够用。
- **固定成员与可变成员**：固定成员的参数在加成员时写定，不再改；可变成员（成员键以 `__var` 结尾）的 `c_params` 是**默认参数**，
  实际取值由关联的策略逐期提交。一个因子在一个任务里最多一个可变成员；需要多个可变值就注册多个因子（`ma_fast`、`ma_slow`）。
- **唯一的写入方**是任务关联的策略实例：DSL 声明了 `factor_params` 的实例第一次启用时调用 `BindFactorTask`（幂等，一个任务只能关联一个实例，写入后不能改；任务没有可变成员时拒绝），之后只有这个实例能对该任务提交参数。
  不调参的实例不关联，可以读已关联给别人的任务的可变成员列（只读）。任务没有关联实例、或某个标的从未提交过，就用默认参数。

**提交（`SubmitFactorParams`）**

请求为任务、成员键、目标期、`request_id` 与各标的的参数。factor-mgr 在一个 SQLite 事务里依次：

1. 校验：提交方是任务关联的实例；成员必须是可变成员；参数名是定义声明过的且在范围内（整型为整数、联合约束成立）；标的在源数据集当前的标的里。
2. 单调与幂等：目标期小于已接受的最后目标期的拒绝（乱序到达的旧请求）；目标期相等时 `request_id` 相同视为幂等成功，不同则拒绝。
3. 整份替换：每次提交都是完整快照，这次没带覆盖的标的用本次的默认值，不保留上一期的覆盖（与现算回放一致）。
4. 写入 `t_factor_member_params`（每个成员只有一行，不保留提交历史）。

**引擎取值（`GetTaskParams`）**

```text
开算第 t 期：
  本地缓存里有这个任务第 t 期的“进行中记录”？ ─ 有 ─► 直接用记录里的参数（失败重试、重启都复用）
                                              └ 无 ─► GetTaskParams 读各可变成员在 t_factor_member_params 里的提交（factor-mgr 连不上用最近一次读到的值）
  固定成员 → c_params；可变成员 → 这个标的的提交值，没有则 c_params（默认参数）
  把第 t 期选定的参数写入进行中记录（落盘）─► 计算 ─► 写结果行（因子值 + __params）─► 写周期标记 ─► 清掉记录
```

- 进行中记录在本地文件 `data/engine/param_cache.json`（`engine.yaml` 的 `params.cache_file`，`params.fetch_timeout` 默认 5 秒），保证**同一期重试不换参数**；
  同一个文件还保存最近一次读到的提交值，factor-mgr 暂时连不上或引擎重启后接着用，不退回默认参数。文件不是事实来源，删了只会让离线期间退回默认参数。
- 策略要提交第 t+1 期的参数，前提是第 t 期因子已经写出，所以引擎读到的提交值不会超前；读到超前值时改用本地缓存并告警。
- **晚到与积压**：第 t+1 期已经开算后，目标期为 t+1 的提交才到，新值从 t+2 起生效。引擎追赶积压时按期次依次计算、**不等策略**，所以追赶期间不保证每期都用上针对这一期算出的参数，
  只保证参数不超前、不倒退，每期实际用的都如实记在 `__params`。策略停止后不再有提交，沿用最后一次的参数。

**引擎计算**

- 周期事件分发给同一源数据集上的**每个**启用任务，各自在自己的串行任务执行器（runner）里算，不同任务并行（同一事件的多个任务同时开算，全部返回后才决定 ACK 或重投）；
  每个任务只算自己的成员，不做跨任务的公共计算，两个任务有相同成员就各算一遍。某个任务失败只影响它自己的这一期，其他任务照常写出，重投时已完成的任务靠周期标记跳过。
- 参数是运行时输入：每个参数槽是“每个序列一个值”的向量，窗口类算子逐序列取值；同一期里结构相同、参数向量相同的节点只算一次。
- 周期明细（`PeriodDetail`）以成员为单位（`member_key`、`factor_id`、`definition_hash`、`member_kind`），策略的就绪判定、失败标的映射、相邻周期记录都按成员键。
- **补算**：固定成员一律用 `c_params`，不读 `__params`；选中的成员里有可变成员时，按期读取已有行 `__params` 里这些可变成员的参数重算，连续若干期参数相同的合成一段一次算完（只按可变成员切段），写回时合并 `__params`。
  可变成员的一致性只对「原行存在、且 `__params` 里有这个成员」的期次作保证（重算结果与原值逐位相同）；原行不存在或没有这个成员时用默认参数，
  算出的是**新补的值**，补算作业的结果摘要会列出这些按默认参数补的期次（`default_filled`，只有可变成员）。

**策略侧投递**（详见[策略](策略.md)）：策略求值时同时算出下一期的参数，与结果在同一个事务里落库（`c_next_params_json`），投递循环只投当前会话里最新一条还没送达的结果，
送达后写 `c_params_delivered_at`，重试按退避。目标期不减的规则保证重试的旧请求不会让参数倒退。

**监控**：因子侧不再导出参数相关告警。策略侧导出 `moox_strategy_param_delivery_stale{space_id,instance_id}`：实例在运行、任务有可变成员、连续
`params.stale_alert_periods`（策略配置，默认 10）期结果都没有成功送达参数时为 1；实例停止后自动解除。Monitor 的 `factor_params` 检查（名称「策略参数投递」）读这个指标。

**回放**：调参策略的因子依赖上一期策略输出，不能先算完因子再跑策略。第 9 节的“因子现算”服务每步带着策略上一期产出的参数（缺值沿用），
因子帧里带上这一期各标的实际生效的参数；参数只存在回放会话的内存里，不写成员行。引擎对请求里每个成员的参数做与实时提交相同的校验，不合法的成员沿用上一期实际用的参数、整期不失败，
拒绝原因随步进响应返回（`rejected_params`），同时返回实际生效的请求参数（`applied_params`）。这样的回放是一次新的模拟，不等同于已有的实时历史，也不把结果写回结果数据集。
复现已发生的历史用补算，不需要重跑策略。

## 12. 自定义算子（wasm UDF）

DSL 表达不了的那一步算法（递归滤波、带分支与迭代的状态更新、自定义回归……），用 Rust 写成**自定义算子**，编译成 wasm，发布后在因子表达式里调用，
不用改系统代码、不用重新发布引擎。

### 写法与语义

```yaml
params:
  n: {type: int, min: 2, max: 200, default: 20}
let:
  trend: ema(close, n)                       # 内置算子，Go 原生计算
output: cs_rank(udf.kalman_trend(trend, n, 0.1))   # UDF 只做 DSL 写不出来的那一步；截面在外层组合
```

- `udf.<名称>(<序列输入>..., <参数>...)` 是**时序算子**：序列输入可以是任意数值表达式；参数必须是常量或因子参数槽，取值范围由 UDF 的元数据声明并在编译时检查。
  UDF 内部不回调系统、不使用内置算子，组合在 DSL 层完成。
- 回看由元数据的公式给出（只允许常量或 `a*<整数参数>+b`），所以空洞检查、预热、补算分块、试算、`definition_hash` 变更检测全部照常工作。
- 空值：默认严格（窗口内任一输入有 NaN 输出 NaN，不调用 UDF）；声明 `relaxed` 时各输入从同一时间偏移裁出共同有效段。输出只能是有限值或 NaN。
- 版本不可变，身份是 wasm 字节的 sha256；名称指向当前启用的版本。版本哈希写进规范程序文本（`udf.<名称>@<哈希>(...)`），所以切换版本会改变引用它的定义的
  `definition_hash`，目录指纹随之变化，引擎重新编译，策略进入 `factor_changed` 需要重新启用。

### 失败语义

UDF 失败（panic、超时、内存超限、返回错误码）只让**这一次计算**失败：本次运行的全部成员按计算失败处理（与执行器出错相同），**不写 NaN**——否则 `fill_nan`、截面排名会把失败当成空值悄悄吞掉。
引擎进程与其他任务不受影响；失败的实例被丢弃，下一次调用用新实例。指标：`factor_udf_call_seconds`、`factor_udf_failures_total{udf,reason}`、
`factor_udf_copy_bytes_total`、`factor_udf_module_state`。

### 发布与切换

```text
moox-cli udf new <名称> → 编辑 → moox-cli udf build → git commit → moox-cli udf publish <包>
→ moox-cli udf preview <名称>@<哈希> --spec … --task-id …   # 在真实数据上试算（版本还没有启用）
→ moox-cli udf activate <名称>@<哈希>                    # 默认只给影响清单与前提检查（不加 --yes 不修改）
```

`build` 在本地跑全部门禁（clippy 禁用清单、原生测试、编译、模块检查、一致性测试）并打包，`publish` 由服务端复核同一套检查并比对测试输出摘要（本地 arm64 与服务端 amd64 的摘要必须一致，
这就是跨架构的确定性检查），通过后存为不可变版本（未启用）。源码留在你的私有仓库，系统只记录提交号，`publish` 要求工作区干净。

**切换启用版本与改写定义（`UpdateFactor`）用同一组前提**，不需要暂停引擎（新 UDF 的首次启用没有引用方，前提都满足）：

1. `moox-cli udf activate <名称>@<哈希>`（不带 `--yes` 只预览）检查影响清单与前提；
2. 停用列出的已启用成员（`moox-cli factor member disable`），取消列出的已经开始的补算作业（`CancelRecalcJob`）；
   等引擎同步到停用后的目录（`moox-cli factor status` 里引擎目录一致，`catalog_in_sync` 为真）再切换；不等的话，切换之后到引擎同步之前的周期仍按旧版本算，要在第 4 步一并补算；
3. `moox-cli udf activate <名称>@<哈希> --yes`；
4. 重新启用成员，等引擎下一次同步目录并预热；停用期间没有产出的周期要用新版本补算（`moox-cli factor recalc submit`）；
5. 受影响的策略实例进入 `factor_changed`，重新启用。回滚就是 `activate` 指回旧版本，步骤相同。

前提检查：没有已启用的成员引用它（成员停用后实时计算不再用它）；受影响任务没有已经开始的补算作业：正在运行的，或领取过又归还、进度已越过起点的
（作业的定义在领取时下发，这类作业再领取会拿到新定义，前半段旧算法、后半段新算法一起写进正式结果）；用新版本重新编译并重做成员校验（参数在新范围内等）。
补算作业只算已启用的成员，成员停用后新领取的作业也用不到这个定义。
切换（或改写定义）对实时计算的生效时刻是引擎下一次成功同步目录为止，不是 `activate` 返回的时刻。
已知差别：停用成员到引擎下一次同步目录之间（最长约 1 分钟，同步失败时更久），引擎仍按缓存的目录用旧版本计算这些成员；这段结果属于旧版本，与停用前一致。
没等目录同步就切换时，切换之后到同步之前的周期同样是旧版本的结果，按上面第 2 步的说明补算。

### 引擎侧

- 模块按版本哈希存在本地（`<udf.dir>/<哈希>.wasm`，编译缓存在 `cache/`），向管理端拉取并校验 sha256，每个版本在每台机器上只编译一次。
- 目录同步时引用的模块全部就绪才应用新快照，失败不记哈希、下次同步重试；启动恢复时缺失的模块按退避拉取，未就绪的任务检查不过（不可执行）；补算领取后先备齐模块。
  恢复追赶在引用的模块全部就绪、且本次恢复之后同步过目录之前不写任何结果。
- 配置（`engine.yaml` 的可选段 `udf`，都有默认值）：`dir`（`./data/udf`）、`call_timeout`（10s，实例化与每次调用的截止时间）、`instance_memory`（512MiB）、`batch_bytes`（64MiB，单批输入输出预算）、`idle_timeout`（5m）。
  实例常驻内存计入进程内存预算（超出拒绝），每次调用拷贝的缓冲计入 `compute.max_memory` 的估算；回看很长的 UDF 每次调用要拷贝整个窗口，这部分开销第一期接受。
