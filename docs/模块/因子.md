# 因子（Factor）

Factor 负责因子定义的管理和计算：每当一个采集周期完成，就对相应的源数据集运行已启用的
Python 因子，把结果写入因子结果数据集，供 Strategy 使用。也支持对历史区间发起补算。

代码位置：`modules/factor`。同一个 Go 模块构建两个进程。

## 1. 组成与部署

| 进程 | 运行位置 | 职责 |
| --- | --- | --- |
| `moox-factor-mgr` | control 主机 | `FactorMgr` 管理接口：因子定义、计算任务（因子集）、成员、补算任务、状态；维护 SQLite 和结果数据集；通过内部服务 `FactorEngine` 给引擎提供目录、租约和补算任务 |
| `moox-factor-engine` | 操作员机器（只做出站连接） | 消费采集周期完成事件，运行周期流水线和补算任务，写入因子结果 |
| `moox-factor-mgr-cli` | control 主机 | 初始化数据库、导入因子、提交补算、查看状态 |

| 进程 | 端口 |
| --- | --- |
| manager | FactorMgr tRPC `11403`、HTTP `11404`，FactorEngine HTTP `11405`，健康 `11414` |
| engine | 健康 `11417`、admin `11945`、metrics `12945`（均只监听本机） |

引擎的网络连接全部是出站的：

| 方向 | 地址 | 用途 |
| --- | --- | --- |
| 引擎 → 控制机 | `https://<控制机>:11001/api/service/factormgr/*` | 同步目录、心跳、领取和上报补算任务（网关调用方 `factor-engine`） |
| 引擎 → 控制机 | `tls://<控制机>:4222` | 订阅 `CollectorPeriodCompleted`（`factor-eventbus` 凭据） |
| 引擎 → storage 主机 | `ip://<storage>:11004` | storage-access：读源数据、写因子结果与周期标记（主体 `factor-engine`） |

管理端只在创建或编辑定义时用 `python.bin` 试加载源码，不执行因子，也不消费 EventBus。

## 2. 领域模型

Factor 的 SQLite 只有四张业务表：

| 表 | 内容 |
| --- | --- |
| `t_factor_defs` | 全局因子定义：类型（时序 / 截面）、源码与哈希、完整输入列、输出列、静态参数、回看周期数 |
| `t_factor_sets` | 计算任务（因子集）：源数据集、空间、频率、标的范围（全部 / 指定）、结果数据集、状态 |
| `t_factor_set_members` | 定义与计算任务的成员关系，各自独立启停 |
| `t_factor_recalc_jobs` | 补算任务：范围、筛选、进度、结果摘要、执行引擎 |

- 定义指纹 `definition_hash` 覆盖完整计算契约：源码哈希、因子类型、规范化后的参数、回看周期、输入列、
  输出列与 `allow_partial_universe`。它在读取时派生、不落库，随 `FactorDef` 和周期标记的
  `FactorPeriodState` 一起下发；Strategy 启用实例时固化它，之后据事件里的指纹判断因子版本是否变化。
  `source_hash` 仍只代表源码。
- 计算任务 ID 和结果数据集 ID 由源数据集与频率确定。输出列在 Storage 列元数据里标记为
  `origin=factor`、`origin_id=<factor_id>`。
- 定义显式声明完整输入列，框架不推断依赖，也不默认注入 OHLCV；系统列 `subject_id`、`freq`、
  `data_time`、`series_tag` 不能作为输入或输出。回看周期按不同的 `data_time` 计数。
- 成员加入后为停用状态；`SetFactorMemberStatus(enabled)` 会重新校验、对齐结果数据集的列，
  并原子提交一次补算。停用或移出不删除已写入的列和值，只停止后续写入。仍被引用的定义、
  仍有成员的计算任务都不能删除；成员启用期间定义不能修改。

## 3. 周期流水线

```text
CollectorPeriodCompleted
  ─► durable factor_collector_period_v1
  ─► 按计算任务进入各自的串行 lane（不同任务并行）
  ─► 冻结本周期启用的定义，规划最大回看窗口
  ─► 读取源数据（PrimaryStore.ReadTimeSeriesRows）
  ─► Python worker 批量执行全部因子
  ─► WriteFactorRows（携带列 + 因子列）─► ReportFactorPeriodComputed ─► ACK
  ─► Storage View 应用标记后发布 ViewDataReady
```

- 时序因子逐标的执行，截面因子使用同一周期的面板；结果行以 `(data_time, series_tag)` 为身份。
- **回看窗口缓存与预热。** 实时周期之间回看窗口只差一根 K 线，引擎缓存每个计算任务已加载的窗口，
  预热完成的标的只读新的数据。新启用或落后太多的标的在后台预热，不拖慢实时周期；预热期间的结果
  不算正式结果，按失败标的上报，持有这些标的的策略不会使用该周期。
- 单个因子或标的计算失败不影响其他结果；可恢复的 Storage 基础设施错误会让消息重投，
  其他错误汇总进周期状态后照常上报完成并 ACK，避免坏因子阻塞整条 lane。
- `WriteFactorRows` 使用确定性的提交 ID 幂等去重，只有这个专用接口能写因子结果列；
  完成标记在结果行之后写入，同一数据集由 DataNode Outbox 保序。
- 当前只支持 `crypto` 空间的连续周期日历，其他空间返回 `unsupported space calendar`。

## 4. 补算

补算任务按目标区间 `[start, end)` 执行，最多 2000 个目标周期一块，块内不拆分同一 `data_time`
的不同 series_tag，并在块起点前读取所需回看。已完成的块不会因后续失败回滚；同一请求 ID 可
幂等提交。补算可以按因子和标的缩小范围，但不能改变定义里的输入、输出和参数。

引擎通过 `PullRecalcJob` 领取任务（带任务租约，默认 15 分钟），每完成一块用
`ReportRecalcProgress` 上报；引擎停止后租约过期，任务会被重新领取并从 `progress_time` 续跑。

## 5. 管理端与引擎的协作

- **目录同步。** 引擎在每分钟第 45 秒调用 `SyncEngineCatalog` 拉取带哈希的目录快照并落盘
  （`data/engine/catalog.json`）；管理端不可达时继续用最后一份快照计算。新启用的成员在引擎下一次
  同步之前的周期不会自动补算，需要时手动提交补算。
- **引擎租约。** 引擎每 10 秒调用 `EngineHeartbeat`；同一时刻只有一个 `engine_id` 持有租约，
  旧引擎停止心跳 45 秒后新引擎自动接管。心跳同时上报各计算任务最近的运行摘要。
- **状态。** `FactorMgr.GetStatus` 返回引擎是否在线、最后心跳时间、目录是否与管理端一致，
  以及消费者、lane、Python 和最近运行情况。
- **监控。** 管理端把引擎心跳中的运行摘要转换为因子结果数据集的数据集指标，由 Monitor 的数据集
  新鲜度检查覆盖因子计算。

## 6. Python 契约

因子源文件定义 `compute(df, params, context)` 并返回 pandas DataFrame：

- 输入只包含 `data_time`、`series_tag` 和声明的业务输入列，按 `(data_time, series_tag)` 升序。
- 输出必须包含系统身份列和全部声明的输出列，身份唯一；数值必须有限，NaN 和正负无穷归一为 null。
- 省略字段表示保留旧值，显式 null 表示清除。

Go 与 Python 之间使用常驻进程池和 `packages/pyruntime` 的 JSON 帧协议；同一批请求中各因子
独立返回结果或错误。因子模块源码按 `source_hash` 发布为不可变文件，供 worker 加载。

因子库位于 `modules/factor/factors/`，用 `moox-factor-mgr-cli import-catalog --dir ./factors` 导入。

## 7. 管理接口

`FactorMgr`：

| 分类 | 方法 |
| --- | --- |
| 计算任务 | `CreateFactorSet`、`UpdateFactorSet`、`SetFactorSetStatus`、`DeleteFactorSet`、`GetFactorSet`、`ListFactorSets` |
| 因子定义 | `CreateFactor`、`UpdateFactor`、`DeleteFactor`、`GetFactor`（含使用它的计算任务）、`ListFactors`（默认不返回源码） |
| 成员 | `AddFactorToSet`、`RemoveFactorFromSet`、`SetFactorMemberStatus` |
| 补算 | `RecalcFactors`、`ListRecalcJobs`、`GetRecalcJob`、`CancelRecalcJob` |
| 状态 | `GetStatus` |

`FactorEngine`（仅允许调用方 `factor-engine`）：`SyncEngineCatalog`、`EngineHeartbeat`、
`PullRecalcJob`、`ReportRecalcProgress`。

## 8. 运维

安装或更新引擎：

```bash
scripts/deploy/deploy-factor-engine.sh \
  --dir ~/moox/factor-engine \
  --manager-url https://<控制机>:11001 --manager-node-id <控制机网关节点> \
  --manager-ca /path/to/control-caddy-root.crt \
  --storage-target ip://<storage>:11004 --storage-node-id storage-access-<storage 节点> \
  --eventbus-url tls://<控制机>:4222
```

脚本会编译引擎、拷贝 Python worker、准备含 pandas/numpy 的 venv、渲染 `config/engine.yaml`，
macOS 用 launchd（`com.moox.factor-engine`）、Linux 用 systemd 用户服务托管，并等待 `/readyz`。
安装目录不要放在 `~/Documents` 等受 macOS 隐私保护的目录下，否则进程会卡在启动阶段。

引擎需要的凭据放在安装目录的 `secrets/` 下，必须是 0600 普通文件：网关密钥
`gateway-factor-engine.key`、storage-access 密钥 `storage-access-factor-engine.key`、
Storage primary 密钥 `storage-primary-auth.secret`、EventBus 凭据 `factor-eventbus.yaml`、
控制机 Caddy 根证书，以及安装时生成的 `health-auth.env`。

常用命令：

```bash
launchctl kickstart -k gui/$(id -u)/com.moox.factor-engine   # 重启（macOS）
~/moox/factor-engine/bin/moox-factor-engine health            # 查看 /readyz 详情
moox-factor-engine run-once --set <set_id> --period <RFC3339>  # 单周期诊断
moox-factor-mgr-cli recalc --set <set_id> --start ... --end ...  # 提交补算
```

| 现象 | 处理 |
| --- | --- |
| `/readyz` 返回 503 且 `lease_conflict=true` | 另一个引擎持有租约，停掉多余的引擎 |
| 日志出现 `factor_catalog_sync_failed` | 管理端不可达；引擎继续用最后快照计算，恢复后自动追平 |
| 事件反复 `factor_period_retry` | 结果数据集未就绪或 storage-access 不可达 |
| 补算任务 `running` 但不前进 | 执行它的引擎已停止，等任务租约过期后会被重新领取 |

不要通过清空消费者来恢复积压；先排查 lane 积压、Storage 错误和 Python 饱和，历史修正用补算任务。
引擎指标：`factor_period_total`、`factor_period_duration_seconds`、`factor_period_lag_seconds`、
`factor_failures_total`、`factor_lane_backlog`、`factor_python_busy`、`factor_last_period_time`。
