# 因子（Factor）

Factor 负责因子定义的管理和计算：每当一个采集周期完成，就对相应的源数据集计算已启用的
因子（用表达式定义，由引擎内置的 Go 执行器计算），把结果写入因子结果数据集，供 Strategy 使用。也支持对历史区间发起补算。
表达式引擎的完整设计见[因子表达式引擎详细设计](../计划/因子表达式引擎详细设计.md)。

代码位置：`modules/factor`。同一个 Go 模块构建两个进程。

## 1. 组成与部署

| 进程 | 运行位置 | 职责 |
| --- | --- | --- |
| `moox-factor-mgr` | control 主机 | `FactorMgr` 管理接口：因子定义、因子任务、成员、补算作业、状态、策略参数提交；维护 SQLite 和结果数据集；通过内部服务 `FactorEngine` 给引擎提供目录、租约和补算作业 |
| `moox-factor-engine` | 因子机（外部程序，只做出站连接） | 消费数据集周期完成事件（`DatasetPeriodCompleted`），运行周期流水线和补算作业，写入因子结果 |
| `moox-factor-mgr-cli` | control 主机 | 初始化数据库、导入因子、提交补算、查看状态 |
| `moox-importer` | 因子机（引擎旁） | 把历史 K 线文件导入因子机的本地时序存储，见第 3 节「本地时序存储」；同时写 Storage 用 `moox-cli import` |
| `moox-replay` | 任意能访问各模块健康端口的机器 | 逐期回放的编排，见第 9 节；`moox-cli replay` 是同一份实现 |

| 进程 | 端口 |
| --- | --- |
| manager | FactorMgr 原生 tRPC `11403`，FactorEngine 原生 tRPC `11405`，健康 `11414` |
| engine | 健康 `11417`（同时承载本地写入 `/v1/series/*`、生命周期 `/v1/lifecycle/*`、回放 `/v1/replay/*`）、admin `11945`、metrics `12945`（均只监听本机） |

引擎的网络连接全部是出站的：

| 方向 | 地址 | 用途 |
| --- | --- | --- |
| 引擎 → Access | `<access>:11004`（`access@<主机>`） | 同步目录、心跳、领取和上报补算作业（FactorMgr），读源数据、写因子结果与周期标记（Storage）；两者共用同一个固定 Access 与外部身份 `factor-engine` |
| 引擎 → EventBus 所在主机（默认存储机） | `tls://<EventBus 主机>:4222` | 订阅 `DatasetPeriodCompleted`（`factor-eventbus` 凭据） |

管理端在创建或编辑定义时编译表达式校验；`PreviewFactor` 试算时直接读 Storage、在进程内计算少量标的，不经过引擎，
不写结果。管理端不消费 EventBus。

## 2. 领域模型

分层：**采集数据集 →（因子任务）→ 因子结果数据集 →（1:1）→ 策略实例**。因子任务关联一个源数据集和一个频率，产出一个因子结果数据集；
一个源数据集可以有多个因子任务。策略实例创建时关联一个因子任务，独占且永久（见[策略](策略.md)）。任务由用户创建（控制台或 `moox.toml`），可以先于策略运行以积累历史；
策略停止只影响策略层，因子任务照常计算，由用户手动停止。控制台里这一页叫「计算任务」，指的就是这里的因子任务。

Factor 的 SQLite（`factor.db`）有这些业务表：

| 表 | 内容 |
| --- | --- |
| `t_factor_defs` | 全局因子定义：`factor_id`、展示名、分类、表达式定义（spec）与原文哈希、`allow_partial_universe`；类型、输入列、输出列、回看与可调参数由编译推导，不落库 |
| `t_factor_categories` | 因子分类（动量类、波动类……）：只是元数据，用于查找与按类展示；内置“未分类”不能删除 |
| `t_factor_tasks` | 因子任务：任务 ID、空间、展示名、源数据集、频率、结果数据集、状态、`c_bound_instance_id`（关联的策略实例，唯一，写入后不能修改或清空）；任务的标的就是源数据集当前的标的，没有单独的对象范围 |
| `t_factor_task_members` | 任务的成员，主键 `(task_id, member_key)`；`kind` 是 `fixed` 或 `var`；`c_params` 是固定参数（可变成员是默认参数），加成员时写定、之后不变；可变成员另有运行状态列 `c_last_submitted_*`（各标的最近一次提交的参数、目标期、请求 ID、提交时间），它们不属于配置，目录同步和成员变化检测都不看 |
| `t_factor_recalc_jobs` | 补算作业：范围、成员、进度、结果摘要、执行引擎 |
| `t_factor_engine_heartbeat` | 引擎心跳与租约 |

- 定义指纹 `definition_hash` 覆盖完整计算契约：表达式语义版本、编译后的规范程序文本（含参数声明：类型、范围、
  默认值）与 `allow_partial_universe`。只改注释、格式、`let` 名不会改变它，任何影响结果的改动都会改变它；**参数取值不进指纹**。
  它在读取时派生、不落库，随 `FactorDef` 和周期明细 `PeriodDetail`（`DatasetPeriodCompleted.detail`）里的 `FactorPeriodState` 一起下发。`spec_hash` 只代表定义原文。
  **成员契约哈希** = `definition_hash` + 成员类型 + 固定参数（可变成员不含参数）：策略启用实例时固化它，之后据事件里的契约哈希判断成员是否变化；任务的自动确认证据也与它绑定。
  周期明细要求指纹非空，由因子侧上报前校验（`storageio.ValidatePeriodDetail`）；Storage 对明细是不透明字节，不解析。
- **ID 与展示名**：任务 ID 是 `ftask_<后缀>`，结果数据集 `dataset_factor_<后缀>`，默认 View `view_factor_<后缀>`（结果数据集与 View 都由 factor-mgr 自己创建、维护、删除，Storage 不托管）。后缀只含小写字母、数字、下划线，最长 35 个字符；
  控制台创建时随机生成 8 位，`moox.toml` 里由用户写定（这样 `setup factors` 可重复执行）。任务展示名 `name` **直接**用作结果数据集的展示名，
  所以必须 1～10 个字、含汉字、在空间内唯一。
- 输入列、输出列、类型与回看都由编译推导：表达式里引用的、不是 `let`/`params`/函数名的标识符就是输入列；
  用到截面算子（`cs_*`）的是截面因子。系统列 `subject_id`、`freq`、`data_time`、`series_tag` 不能作为输入或输出。
  回看按周期网格计数（缺失的 K 线是 NaN，严格窗口会让受影响的结果为 null）。有可调参数的因子，回看按参数范围的最坏情况推导。
- 加入任务时校验：输入列都存在于源数据集且是数值列（int、double），`params`/`let` 不与源列重名，
  列名不与源列、其他成员的列或结果数据集里别的因子拥有的列重名。
- 成员加入后为停用状态（`AddTaskMember` 带因子 ID、成员类型与参数，成员键由服务端推导并随响应返回列名）；`SetTaskMemberStatus(enabled)` 会重新校验、对齐结果数据集的列，
  不自动补算历史。停用或移出不删除已写入的列和值，只停止后续写入；再次加入同一个成员键沿用原来的列，并核对旧列元数据里的参数与成员类型一致。
  仍有成员的任务、已关联策略实例的任务都不能删除。
- **被任务引用的定义有修改限制**：不允许增删参数，不允许改参数的类型、声明顺序和默认值，也不允许增删、改名或重排输出（列名依赖它们）；要改就新建一个定义。
  表达式本身和参数范围可以改，但新范围必须包含所有引用它的成员现有的固定参数与默认参数。成员启用期间定义不能修改。

### 成员键与列名

成员键与列名由「因子 ID + 参数 + 是否可变 + 输出」按规则推导，不存储别名。写策略规则、筛选条件或 SQL 时，列名就是这里推导出的名字；
控制台加成员时会实时预览，`AddTaskMember` 与 `setup factors` 也会返回或打印它们。规则只有一份实现：Go 在 `packages/factorname`，前端在 `web/src/utils/factor-name.ts`，两边共用 `testdata/vectors.json`。

```text
名字（因子 ID / 输出名 / 参数名）： 小写字母开头，只含小写字母、数字、单下划线，不以下划线结尾
成员键 = 因子ID [ "__" 参数段 ]
参数段 = "var"  |  值 { "_" 值 }       值 = n?[0-9]+(p[0-9]+)?    按定义声明的参数顺序，只写值不写参数名
列名   = 成员键 [ "__" 输出名 ]          单输出因子没有输出段
```

| 成员 | 成员键 | 列名 |
| --- | --- | --- |
| `ema`，参数全为默认值 | `ema` | `ema` |
| `ema`，span=20、warmup=50000 | `ema__20_50000` | `ema__20_50000` |
| `rsi`，参数全为默认值 | `rsi` | `rsi` |
| `boll`，参数全为默认值（输出 mid/up/low/pctb） | `boll` | `boll__mid`、`boll__up`、`boll__low`、`boll__pctb` |
| `boll`，window=30 | `boll__30` | `boll__30__mid` 等 |
| `ma_fast`，可变成员 | `ma_fast__var` | `ma_fast__var` |

- **段与段之间用双下划线**，名字内部用单下划线（`ma_fast`、`bias_q`），所以只看列名就能按 `__` 切开：第一段是因子 ID；第二段是 `var` 或匹配值语法的就是参数段，否则是输出名；
  三段依次是参数段与输出名；超过三段非法。因此输出名不能是 `var`，也不能匹配值语法（如 `n5`），也不能等于因子 ID，不带因子前缀（写 `mid`，不写 `boll_mid`）。
- **参数值的写法**：十进制，小数点写 `p`、负号写 `n`（`0.5` → `0p5`，`-1` → `n1`，`-1.5` → `n1p5`）；只写值，顺序就是定义声明参数的顺序。只接受规范形式（`01`、`1p0` 非法）。
- **参数全为默认值时省略参数段**，成员键就是因子 ID；**可变成员固定以 `__var` 结尾**，一个因子在一个任务里最多一个可变成员，需要多个可变值就注册多个因子（`ma_fast`、`ma_slow`）。这两条最容易被忽略。
- **单输出与多输出**：单输出因子在规格里写 `output: <表达式>`，列名就是成员键；多输出因子写 `outputs: {输出名: 表达式, …}`（至少两个），列名是 `成员键__输出名`。
  只有确实共用同一组参数的因子才用多输出；不共用参数的输出拆成独立因子，引擎同一期合并公共子表达式，不会多算。
- 长度上限：因子 ID 24 个字符，输出名与参数名 16 个字符，成员键 44 个字符，列名 64 个字符。列名与源数据集的非因子列重名（例如因子 ID 叫 `close`）时加成员被拒绝。
- 列名只能还原「列名里有的信息」：默认成员的键 `ema` 能解析出「固定、参数全为默认值」，具体参数值要查列元数据的 `factor_params` 或定义。
- 固定成员的参数一旦写定就不能改，要换参数就加一个新成员（键随之不同）。

结果数据集的列元数据（来源 `CUSTOM`，不带 `origin_id`）记录每列的来源：`column_kind=output` 的列带 `factor_id`、`member_key`、`member_kind`、`output_name`、`category_id`、`definition_hash`，
固定成员另带 `factor_params`（完整参数的规范 JSON）；列名、类型与这些属性的契约由 factor-mgr 建列时自己保证，Storage 只校验列名唯一、值类型合法这类通用规则，不解释这些属性。

### 系统列 `__params`

每个因子结果数据集有一个系统列 `__params`（`column_kind=params`，类型 `json`，展示名「因子参数」），**记录这一行所有成员实际用的参数**，包括固定成员：

```json
{"boll": {"window": 20}, "ema__20_50000": {"span": 20, "warmup": 50000}, "ma_fast__var": {"window": 5}, "rsi": {"window": 14}}
```

- 它是参数的**唯一历史记录**，补算、回放、策略的 `params()` 和用户查询都读它；两层键按字典序、不带空白，数字用十进制写法，同一期重算时与因子值一样逐位相同（提交 ID 依赖它）。
- 补算只选了部分成员时，先读出原行的 `__params`，只替换这次重算成功的成员键再写回；原行不存在时只记录这次实际计算的成员。
- 结果页默认隐藏这一列，「显示参数」开关打开后按成员分组展开；筛选只按因子值（`FilterSpec` 的「列名 + 操作符 + 值」），不支持按参数值筛选。
  直接用 DuckDB 排查时可写 `json_extract("__params", '$.ma_fast__var.window')`。

## 3. 周期流水线

```text
DatasetPeriodCompleted
  ─► durable factor_collector_period_v1
  ─► 按因子任务进入各自的串行执行器（不同任务并行）
  ─► 生命周期门禁：任务没有处于试运行或运行就 ACK 不计算
  ─► 取本期各成员的参数（第 11 节），规划最大回看窗口
  ─► 把本期标的从 Storage 同步到本地时序存储（只拉增量），抓取内存窗口的读租约
  ─► 任务内全部成员编译成一个程序（相同子表达式只算一次），在网格面板上执行
  ─► UpsertFields（commit_id；携带列 + 因子列 + __params）─► ReportDatasetPeriodCompleted（detail 为 PeriodDetail）─► ACK
  ─► Storage View 应用标记后发布 ViewDataReady（透传 detail）
```

- 每个 (标的, `series_tag`) 是一条序列；时序算子沿序列计算，截面算子在同一 `(data_time, series_tag)` 的全部可用标的之间计算。
  结果只在有源行的目标时刻产生，行身份是源行的 `(data_time, series_tag)`。同一份输入的结果与并行度、分块、
  是否与其他因子共享节点无关，逐位相同（实时写入的提交 ID 依赖它）。
- **本地数据与窗口。** 实时、补算、重算都从因子机的本地时序存储（Pebble，数据永不删除）读取；每个启用任务的回看窗口常驻内存
  （按序列的列式环形数组，实时周期之间只追加一根）。Storage 只在增量与修正时被读取，详见下面「本地时序存储」。
- **窗口没载入完成，本期不算。** 引擎成为活动引擎、或目录里出现新任务后，后台预载每个任务的窗口（取同步基线、补到最新已收盘的一根、载入内存）；
  载入完成之前该任务的标的本期都不算：结果不正式、按失败标的上报，持有它们的策略不会使用该周期，跳过的 (因子, 标的, 周期)
  记入跳过账本（`reason=warming`），载入完成后由跳过恢复「只填充」补算，历史结果不会缺一根；marker 不改写，也不再触发策略。
- **补齐的最新一期记入运行摘要。** 跳过恢复补齐的如果是某任务最新的一期，账本里这一期没有待办之后，引擎改写这一期的运行摘要：
  去掉补齐的失败标的、不再算预热中，余下没有失败就记为完成，完成时刻改为补齐的时刻，并立刻补发心跳（日志
  `factor_period_repaired`）。补算没覆盖的失败（上游失败、读取失败、计算出错、放弃或取消的待办）原样保留；已失败的期次不改写。
  整因子跳过的严格截面因子（实时路径一行没写）按补算重算全集的逐项结果判断，这次没写成的标的仍记为失败。
- 单个因子或标的计算失败不影响其他结果；可恢复的 Storage 基础设施错误会让消息重投，
  其他错误汇总进周期状态后照常上报完成并 ACK，避免坏因子阻塞整条任务执行器。
- 结果行用通用 `UpsertFields` 写入，带提交 ID 幂等（实时周期的提交 ID 是内容摘要，相同内容的重投直接返回成功；补算与含空洞失效的写入每次执行加一个唯一的盐，不会被旧标记吞掉；同一提交 ID 内容不同返回 `CONFLICT`）；写入权限由网关 ACL 决定；
  完成标记在结果行之后写入，同一数据集由 DataNode Outbox 保序。同一事件下的多个任务并行计算、各自写出，某个任务失败只影响它自己的这一期。
- 当前只支持 `crypto` 空间的连续周期日历，其他空间返回 `unsupported space calendar`。

### 连续水位

引擎为每个因子任务保存连续水位（`watermark.state_file`，默认在跳过账本旁的 `factor-watermarks.json`，原子写）：`committed_through`（W）表示这一期及之前都已连续算完，
`target` 是收到的最新收盘周期。收到 T 的事件后，引擎在该任务的串行执行器 里从 W 的下一期推进到 T：

- 有事件的周期用事件里的期望标的与失败标的；没有事件的周期（零提交，或阻塞期间已经 ACK 的事件）读回 Storage 判断哪些标的已到（读任务第一个因子的第一个输入列）。
- 零提交或缺失比例超过阈值（`watermark.max_missing_ratio`，默认 0.1，`watermark.task_ratios` 按任务覆盖）时**阻塞**：W 不前进、不计算，记下 `blocked_since`。
  阈值以内的缺失照常计算，缺的标的记进跳过账本（`reason=upstream_failed`），补采补齐后由跳过恢复「只填充」补算。
- 读回推进的周期用合成的触发事件 ID `catchup:<任务 ID>:<周期>`，marker 与正常周期一样，策略只会看到连续的结果。一次最多推进 `watermark.max_periods`（30）期。
- 事件处理完一律 ACK（只有基础设施错误重投），阻塞靠本地状态续推：追赶循环每 `watermark.poll_interval`（10 秒）对 `target > W` 的任务再推进一次，不占 JetStream 的待确认名额。
- **补齐通知**：Collector 补采作业成功后调 `FactorMgr.NotifyPeriodsFilled`（数据集、频率、范围、补采确认行情源没有的标的），factor-mgr 暂存并在引擎心跳响应里带回；
  引擎收到后立即推进相应任务、唤醒跳过恢复，范围内 `upstream_failed` 的待办不再等 `gap.settle`。确认没有的标的在 30 分钟内不计入缺失比例。
- 第一次见到某个任务时 W 取 T 的前一期：只从上线起保证连续，历史用补算。重启后从状态文件恢复 W 与 target 继续追赶。
- 心跳带各任务的水位与阻塞状态；factor-mgr 导出 `moox_factor_task_watermark_blocked_since_timestamp_seconds`，阻塞超过 30 分钟 Monitor 告警（不自动跳过，交给人工手动补采或确认缺失）。

设计见[因子连续水位详细设计](../计划/因子连续水位详细设计.md)。

### 本地时序存储

> 状态：已实现。完整设计见[因子本地K线存储设计](../计划/因子本地K线存储设计.md)。

因子按「最近 N 根」取回看窗口，**窗口中间缺了几根时，因子照样算出一个看似正常的数**。过去靠每期检查窗口连续性、缺了就跳过；
现在改为**本地数据在写入时就保证连续**，窗口里不会再有空洞，也就不再有逐期的空洞检查（`gap.enabled`、`gap.mass_ratio` 已删除）：

- **存储。** `seriesstore`（`modules/factor/internal/seriesstore`）按 `k/{空间}/{数据集}/{频率}/{标的}/{块起点}` 存列式块，
  频率支持 1m 5m 15m 30m 1h 4h 1d；块跨度因频率而异（1m 按小时、5m 按 6 小时、15m 与 30m 按天、1h 按周、4h 按月、1d 按年）。
  只有一种写入语义：**整段替换**（用一批行替换标的在 `[from, to)` 内的全部数据）。每个标的在 `[Earliest, Latest]` 上按频率网格连续，
  所以「同步到哪里」只看 `Latest`。实测导入约 102 万行/秒，一批 200 个标的的实时写入约 10ms。
- **缺失行与填充。** 交易所本身缺数据的周期，写入时按字段的 `fill` 属性填成带标记的填充行：`prev`（取上一期该字段的值，默认）、
  `prev_close`（取上一期的 close，给 open/high/low/close）、`zero`（填 0，给 volume 等量类字段）。空洞没有长度上限。
  填充行带已填充标记，表达式里可用虚拟列 `is_filled`（1 或 0）区分；之后拿到真实数据，整段替换会把填充行换成真实行，
  并重新生成它之后的填充行。`fill` 属性存在数据集字段的 `attributes` 里（Storage 注册时校验，`moox-cli metadata import` 的 `dataset_columns[].attributes` 可写）。
- **窗口。** `serieswindow` 为每个数据源保留任务内最大回看根数（加余量）的内存窗口，实时只追加；换代（压缩）时复制，读租约抓到的切片不受影响。
  窗口内存超出 `window.max_memory` 或进程预算 `memory.total_budget` 时拒绝启用该任务，并给出估算值。
- **进程级内存准入。** 计算、回放、重算、导入向 `memadmit` 预留内存，预留不到就排队、等不到拒绝；实时周期优先级最高。
  常驻的窗口与块缓存先从总预算里扣除。
- **与 Storage 的同步。** Storage 为数据集行写入维护持久化的**变更日志**（`__changelog/`，保留 7 天，由 outbox relay 顺带清理；因子结果的写入不记），
  新增读取接口 `ReadDatasetChanges`。同步器：`Pull` 从本地 `Latest` 之后拉增量；`Baseline` 在读数据之前先取变更日志位点；
  `Follow` 读取位点之后的变更，只在内容与本地不同时应用，并把改变的区间记入「失效重算」待办，引擎据此重算受影响的周期；
  位点已被清理（断档）时该数据源标为未就绪，由 `moox-factor-engine reconcile --task <任务 ID>` 对账（需要先停止引擎，Pebble 同一时刻只能由一个进程打开）：
  取位点、在保留期内逐标的比对、写入差异、再跟进变更。
- **导入。** `moox-importer run`（或 `moox-cli import --target storage,factor`）把 CSV 等文件导入：先校验全部文件再写入，按时间边界切批，
  断点记在 SQLite（重跑自动续传），写因子机经引擎的 `/v1/series/*` 接口（签名鉴权，引擎未就绪时也能写）。格式解析在 `packages/seriesformat`
  （`Decoder` 注册表，目前有 csv）。`--allow-missing` 允许序列内部缺周期（按字段填充规则写成填充行），`--recalc` 把改变的区间记入失效重算。
  **初始数据导入**（数据源第一次接入时灌入长历史）：因子机本地写全量、Storage 只写最近窗口（`--tail-rows`），按导入包 `manifest.json` 预检（`--manifest-pack`），
  步骤见 [skill 的初始数据导入](../../skills/moox/references/initial-import.md)；因子机本地写入 6 万行约 5 秒，多个标的并发几乎线性加速（6 路 4.2 秒）。
- **仍保留的跳过账本。** 引擎本地账本（`factor-gap-YYYYMM.jsonl`，按月一个文件、永不自动删除）记录每次跳过（窗口没载入完成 `reason=warming`、
  上游数据没到 `reason=upstream_failed`）；引擎每 5 分钟检查缺口是否已补上，补上后在进程内做**只填充**的重算（只写完整窗口算出的值，从不写失效 NULL），
  写入确认后记 `repaired`；超过 6 小时仍补不上记 `gave_up` 并告警，由操作员手工补采和补算。恢复区间相同的分组合并成一次重算（每批最多 100 个标的），
  每轮最多运行 `gap.max_groups_per_sweep` 批。缺口如果早于数据集最早的采集计划生效点，普通补采看不到，用 `moox-cli collector kline backfill --force` 指定范围补采。
  恢复只写历史因子行，不改写原 marker，也不触发策略。
- **监控口径。** 一期只因窗口没载入完成而不完整，向 Monitor 报告为 `partial`（数据积累中），不算失败也不算成功；其他失败按失败处理。
  指标 `factor_gap_pending`、`factor_gap_skipped_total`、`factor_gap_gave_up_total`、`factor_gap_ledger_degraded`、`factor_series_change_gaps_total`（变更日志断档次数）。
- **永久审计。** 账本即审计，可用 DuckDB 的 `read_json_auto` 或 `jq` 分析。

### 生命周期

> 状态：已实现（设计 6）。`packages/lifecycle` 是各模块共用的状态机，阶段与颜色：未初始化（灰）、未就绪（红）、就绪（蓝）、试运行（黄）、运行（绿）、暂停（橙）、恢复追赶（青）、重置中（紫）、重置失败（红）、故障（红）。

引擎的对象是目录里启用的因子任务，模块自身是基础设施（第一次检查时自动初始化）。**只有处于试运行或运行的任务才计算**。
目录里的全部因子任务都由引擎自动推进，不需要手动执行命令；排障时仍可手动：

```bash
moox-cli lifecycle init  --task <任务 ID>   # 载入本地窗口（读字段、取基线、补到最新已收盘的一根）
moox-cli lifecycle start --task <任务 ID>   # 启动：进入试运行，因子正常计算，策略对试运行实例发影子目标
moox-cli lifecycle confirm --task <任务 ID> # 确认试运行结果：进入运行
```

- **自动 init、start**：引擎每个生命周期周期（`lifecycle.interval`，默认 30 秒）对目录里的任务自动执行 init（未初始化）与 start（就绪），
  直接进入试运行开始计算；检查没过（窗口没载入、变更日志断档）的等检查通过后下一轮再推进，手动暂停、恢复追赶、重置中的不动。
  新建任务的第一个结果要等引擎同步目录（每分钟第 45 秒）并预加载完本地窗口（源数据有 5 万根历史时可达一两分钟），再等下一个源数据周期收盘。
- **自动 confirm**：任务进入试运行之后，有一期所有启用成员都完整算完（没有失败、没有预热中的标的）、写入了结果行，
  且这一期的成员清单与当前目录一致，就自动确认进入运行。证据只放在引擎内存里：成员变化、再次进入试运行、引擎重启都使证据作废，
  代价至多晚一个周期转为运行（因子计算在试运行阶段本来就是完整的，只是显示阶段不同；是否已关联策略实例不影响）。证据与成员契约哈希（成员键、定义哈希、成员类型、固定参数）绑定。
  任务启用时检查引擎本地序列是否覆盖成员里最长的「回看 + 预热」（可变成员按参数范围上限算），不够就停在试运行并提示先导入历史，不自动补算。
- 启动前检查：本地窗口已载入完成、数据源变更日志没有断档（失败项带处理办法，例如 `moox-factor-engine reconcile --task <任务 ID>`）。
  `moox-cli lifecycle status` 列出各对象阶段与未就绪原因。
- **暂停与恢复**（设计见[暂停恢复与重置设计](../计划/暂停恢复与重置设计.md)）：`pause [--reason 原因]` 在就绪、试运行、运行时都可以暂停，暂停详情带类型（手动 / 系统 / 自动）、原因、操作者和时间；
  手动暂停只有 `resume` 才恢复。`resume` 先进入**恢复追赶**（不计算、不下单，只做追赶门禁放行的历史写入），追平后自动放行回到暂停前的阶段；
  `--manual-release` 让追平后停在待放行，等 `release`（系统级恢复用）。`catchup` 查看追赶进度。
- **三条后台写结果路径并入生命周期门禁**：补算作业、缺口恢复、失效重算都经过补算执行器，任务暂停、恢复追赶（对象未参与）、重置期间执行器返回 `ErrGated`（不记失败，作业租约到期后由放行后的引擎继续）；
  实时事件用实时门禁，连续水位追赶用实时门禁或追赶门禁。恢复追赶的目标由 `Continuity.NoteTarget` 显式建立，不等下一条实时事件。
- **恢复追赶**（任务级 `Catchup` 钩子）：① 后台同步本地数据（`Data.Prepare` = Follow 已有范围的修正 + Pull 新增尾部 + 重载内存窗口，每次恢复一次）→ ② 显式建立追赶目标（暂停区间内最新已收盘周期，扣采集宽限）→ ③ 唤醒连续水位追赶循环，在追赶门禁下补算暂停区间每个周期并发布历史结果 → ④ 水位追到目标且没有阻塞才算追平。
  变更日志断档（暂停超过保留期或 Storage 身份变化）时增量同步追不上，追赶报告「变更日志断档」，需要人工离线维护（`moox-factor-engine reconcile` / `backfill`）。
  系统恢复时由 `moox-cli system resume` 保证采集先补采完、因子才开始同步。
- 试运行或运行中检查失败的任务**自动暂停**，只影响它自己，检查重新通过后自动回到暂停前的阶段；期间漏掉的周期由现有追赶机制补算。
  重启后先跑检查，通过就回到重启前的阶段（首页提示「已自动恢复」），阶段持久化在 `data/engine/lifecycle.json`。
- 接口挂在引擎健康端口：`GET /v1/lifecycle/status`、`POST /v1/lifecycle/command`；`/healthz` 的 `details.lifecycle` 带精简快照，Monitor 据此汇总首页的系统状态。
- 依赖链向下传：数据源断档 → 因子任务暂停（显式）→ 它的策略实例收不到新事件，没有新目标、持仓不动（隐式，策略侧的实例阶段单独管理，见[策略](策略.md)）。

## 4. 补算

补算作业按目标区间 `[start, end)` 执行，按 `recalc.chunk_periods` 分块（当前默认 500 个目标周期），块内不拆分同一 `data_time`
的不同 series_tag，并在块起点前读取所需回看。已完成的块不会因后续失败回滚；同一请求 ID 可
幂等提交。按成员重算时读取原行 `__params` 里该成员的参数，写回时合并 `__params`（第 2 节、第 11 节）。补算可以按因子和标的缩小范围，但不能改变定义里的输入、输出和参数。

引擎通过 `PullRecalcJob` 领取任务（带任务租约，默认 15 分钟），每完成一块用
`ReportRecalcProgress` 上报；引擎停止后租约过期，任务会被重新领取并从 `progress_time` 续跑。

**启用不自动补算历史。** 启用成员只让它参与此后每期的计算，不再提交回填作业；需要历史因子值时用 `moox-factor-mgr-cli recalc` 或控制台「补算」指定范围。
原因：自动回填会按结果数据集的保留期往回算，写出几百万行因子结果，再由 Storage View 逐行消化，初始数据导入后会把 View 积压数小时（见[初始数据导入执行计划](../计划/初始数据导入执行计划.md)）。

**补算对 Storage 的负载防护**（2026-10-14 两个 1h 因子任务同时回填，把 4 核的 `storage-node` 打到 330% 以上、读窗口反复超时之后加上的）：

- **同时只跑一个补算作业**（所有引擎合计，`enginehub.DefaultMaxRunningJobs`）：领取作业时在同一个事务里数租约未过期的运行中作业，达到上限就不再发出新作业。
- **补算读本地。** 补算、只填充与失效重算都从本地时序存储读 `[回看起点, 终点)`，不再向 Storage 逐批读窗口，也就不需要读取并发、退避与断路的配置
  （`pipeline.read_*`、`bulk_read_*`、`warmup_*` 已删除）；分块大小由内存准入与 `compute.max_memory` 约束。补算分块遇到基础设施错误的重试仍是指数退避（5 秒起，上限 2 分钟）。
  **补算前先延长本地历史**：补算区间（加回看）早于本地最早数据时，那些周期所有标的都“没有行”会整段失败（作业还显示成功），例如手动补算的区间远早于只预载了回看根数的本地数据。所以领取补算作业后、读之前，引擎先把本地历史从 Storage 补到覆盖「区间起点 − 回看」（与离线 `backfill` 命令同一实现，
  Earliest 前移会登记失效重算）；补历史失败只记日志，仍用已有的本地数据计算，Storage 保留期里没有那么早的数据时有多少补多少。
- **任务离开目录时释放窗口。** 预载循环对账目录：删除、停用的任务取消它们在数据源上的登记；
  数据源没有其他任务登记时丢弃它的内存窗口与同步状态并释放常驻内存预算，还有其他任务时下次准备按其余任务的标的并集与最大回看收缩。

## 5. 管理端与引擎的协作

- **目录同步。** 引擎启动时立即同步一次，之后在每分钟第 45 秒调用 `SyncEngineCatalog` 拉取带哈希的目录快照并落盘
  （`data/engine/catalog.json`）；管理端不可达时继续用最后一份快照计算。新启用的成员在引擎下一次
  同步之前的周期不会自动补算，需要时手动提交补算。引擎安装快照时编译全部定义（派生字段以编译结果为准）；
  补算作业自带完整定义，引擎领取后现场编译，不依赖目录同步。引擎侧编译失败（只在管理端与引擎的 expr 版本不一致时出现）
  只让该因子本期对全部标的失败，计入 `factor_compile_errors_total`。
- **引擎租约。** 引擎每 10 秒调用 `EngineHeartbeat`；同一时刻只有一个 `engine_id` 持有租约，
  旧引擎停止心跳 45 秒后新引擎自动接管。心跳同时上报各计算任务最近的运行摘要；平时每 10 秒一次，每算完一期立刻补发一次。
- **状态。** `FactorMgr.GetStatus` 返回引擎是否在线、最后心跳时间、目录是否与管理端一致，
  消费者、任务执行器、计算线程数、引擎与管理端各自的 expr 语义版本（不一致时控制台标红），以及最近运行情况。
- **监控。** 管理端把引擎心跳中的运行摘要转换为因子结果数据集的数据集指标，由 Monitor 的数据集
  新鲜度检查覆盖因子计算。每收到一次被接受的心跳就立刻刷新这些指标，水位前进时补报一份快照，
  Monitor 约 1 秒内看到这一期的完成时刻（不再等 30 秒的定时上报）。同一期只记一次，除非结果变好：
  从不正式（预热中、出错，不推进产出水位）变为正式、或从不完整变为成功时再记一次（补算补齐了这一期），
  产出水位随之前进，到达时间是补齐的时刻，“数据积累中”当场消失，不用等下一期；水位已经推进过的一期升级为成功时
  水位不动、到达时间不变，管理端主动补报一次。

## 6. 表达式语言

因子定义（spec）是一份 YAML 文档：

```yaml
params:                            # 可选：可调参数的声明（类型、范围、默认值）
  window: {type: int, min: 2, max: 120, default: 20}
let:                               # 可选：有序的中间量，后面的可以引用前面的
  ma: ts_mean(close, window)
output: close / ma - 1              # 单输出写 output（列名就是成员键）；多输出写 outputs: {输出名: 表达式, …}
```

- 表达式支持数字、`true`/`false`、标识符、`+ - * / % **`、比较、`and`/`or`/`not`、`c ? a : b` 与已登记的函数调用；
  其余语法一律拒绝，报错带字段路径和行列。窗口、位移等位置只接受整数字面量，或一个范围落在算子允许范围内的**整数参数**；
  其余数值位置可以放字面量或任意参数。参数声明的未知键、范围不合法、默认值越界都在编译时拒绝；联合约束（如 `sma` 的 `m < n`）
  对声明范围的全部取值都要成立。不再有列表参数与 `{window}` 列名模板。
- 函数分三类：逐元素（`abs`、`log`、`where`、`clip`、`fill_nan` 等）、时序（`delay`、`ts_mean`、`ts_std`、`ts_rank`、
  `ts_corr`、`ema`、`sma` 等）、截面（`cs_rank`、`cs_zscore`、`cs_demean`、`cs_scale`）。完整清单、参数范围、回看规则与说明
  由 `ListFactorFunctions` 返回，控制台编辑器的函数参考面板即来源于此。
- 空值语义：null 与网格上缺失的行读作 NaN；任一输入为 NaN 结果即为 NaN（`where` 的未选分支除外）；±Inf 一律记为 NaN；
  **严格窗口**：时序窗口内只要有一个 NaN 结果就是 NaN，没有 `min_periods`；截面算子跳过输入为 NaN 的标的。
  写入时 NaN 为 null。
- **序列开头的部分窗口**（`*_partial`）：`ema_partial(x, n, k)`、`ts_mean_partial(x, n, m)`、`ts_std_partial(x, n, m)`、
  `ts_min_partial(x, n, m)`、`ts_max_partial(x, n, m)`。窗口里的 NaN 只出现在开头（序列还没开始）时，在有效值上计算（不少于 m 个），
  相当于 pandas 的 `rolling(n, min_periods=m)` 与 `ewm(adjust=False)` 从序列首根递推；有效值之后再出现 NaN 时仍为 NaN（这一点和 pandas 不同）。
  本地时序存储保证序列在 `[Earliest, Latest]` 上连续（缺失周期写成填充行），所以输入列的 NaN 只在序列开始之前。回看与对应的严格算子相同；
  窗口里没有 NaN 时结果与严格算子逐位一致。用于还原上市初期也出值的外部因子（如 F1 迁移，见下方 `f1.yaml`）。
- 回看由编译推导（例如 `ts_rank(ts_mean(x, 20), 20)` 是 39）；`ema`/`sma` 截断到权重低于 1e−9 的 K 根（`ema(x, 20)` 为 208）；`ema(x, n, k)` 可显式指定预热总根数 K=k（含起点那一根，回看就是 k；k 不写或为 0 按通常方式；n 远大于 k 时起点权重不可忽略，是近似值）。例如 `ema(close, 20, 50000)` 是 EMA20（α = 2/21）用 5 万根预热，与逐根递推 49999 次一致。
- 限制：spec 64 KiB、单条表达式 4096 字符、最多 64 个输出、窗口 1～100000（实际受回看上限约束）、推导出的回看不超过 100000。

因子库位于 `modules/factor/factors/`（`*.yaml`，每个文件是 `[{factor_id, name, spec}]` 列表），
用 `moox-factor-mgr-cli import-catalog --dir ./factors` 导入；单个定义用 `import --file <文件> --factor-id <ID>`。因子 ID、输出名、参数名都是小写（语法见第 2 节「成员键与列名」）；单输出因子写 `output: <表达式>`，多输出因子写 `outputs`。
示例见 [`examples/factors`](../../examples/factors/)。

内置因子库有三个文件：`xbx.yaml`（动量、成交量、波动类，由旧 Python 因子转写）、`common.yaml`（常用技术指标），
以及 `f1.yaml`（F1 策略迁移的 5 个因子：`f1_po`、`f1_mtmstd`、`f1_wick_max`、`f1_upper_shadow`、`f1_min_max`，与 alphalib 原版逐值一致，
回看分别为 50000、4000、2016、2016、2016，见[F1 策略迁移设计](../计划/F1策略迁移/F1策略迁移设计.md)第 2、3 节）。
`common.yaml` 的 10 个因子都是时序因子，窗口（`Ema` 为跨度 `span` 与预热根数 `warmup`）是可调参数：

| 因子 | 默认成员的列名 | 窗口（默认，范围） | 回看 |
| --- | --- | --- | --- |
| `ma` 简单移动平均 | `ma` | 20，2～120 | 120 |
| `ema` 指数移动平均 | `ema` | `span` 20，2～4825；`warmup`（预热根数，0 为按通常方式）0，0～50000 | 50000 |
| `macd` | `macd__dif`、`macd__dea`、`macd__hist` | 固定 12/26/9 | 362 |
| `rsi`（Wilder 平滑） | `rsi` | 14，2～120 | 2478 |
| `roc` 变动率 | `roc` | 12，1～120 | 121 |
| `boll` 布林带（±2 倍标准差） | `boll__mid`、`boll__up`、`boll__low`、`boll__pctb` | 20，2～120 | 120 |
| `atr` 平均真实波幅 | `atr` | 14，2～120 | 121 |
| `atr_pct` 平均真实波幅占收盘价比例 | `atr_pct` | 14，2～120 | 121 |
| `return_std` 收益率波动 | `return_std` | 20，2～120 | 121 |
| `vwap` 成交量加权均价 | `vwap` | 20，2～120 | 120 |

窗口上限一般为 120，不为控制回看而单独收紧；EMA 的上限是 4825，最大回看 49995 根（1m 约 34.7 天）。EMA、MACD、RSI 带指数衰减，回看按“起点权重衰减到 1e-9 以下的根数”按参数上限推导，所以比同窗口的普通均线长。
最大回看决定要保有多少历史：Storage 的保留期（默认 1m 35 天）和引擎的回看数量 N（`engine.yaml` 的 `window.lookback`，默认 5 万）都要装得下它，否则 `setup factors` 拒绝导入，或任务预载失败、整个任务都不出结果。
实际计算按当期参数取窗口：EMA 默认窗口 20 只需 1243 根，本地历史够就有值；把窗口调大后，本地历史不足该窗口所需根数的那段时间，这个输出为空（严格窗口），同一任务的其他成员不受影响。
回看 5 万根时，500 多个标的单次计算约需 1.1GB 内存，引擎的单次计算上限 `compute.max_memory` 默认 4GiB，超过时整期放弃。哪些因子进哪个任务由 `moox.toml` 的 `[[factors.tasks]]` 决定，没有默认加成员。
离线检查与试算用 `packages/factorexpr/cmd/factorexpr`（`functions`、`check`、`eval`，与引擎同一个编译器和执行器）；
把旧 Python 因子转成表达式并逐值核对的完整流程见 [`skills/moox/references/factor-dsl.md`](../../skills/moox/references/factor-dsl.md)。

## 8. 运维

安装或更新引擎（因子机，只支持 Linux）：

```bash
./bin/moox-cli setup release build --release <ID> --source-dir .
./bin/moox-cli setup deploy-unit --file ./moox.toml --source-dir . --host factor --profile factor-engine --release <ID>
```

`factor-engine` 是服务目录里的外部程序组件，登记在因子机的 `[deployments]` 里。`deploy-unit` 把随 release 交付的软件包和凭据经 SSH 上传，
渲染 `config/engine.yaml`（含 `compute:` 段），由 systemd 用户服务 `moox-factor-engine` 托管（目标机需开启 linger），并经 control 网关中转等待 `/readyz`；
主机或部署在 Admin 里已停用时只安装文件、不启动。启停与退役用 `moox-cli setup deployment enable|disable --host factor --component factor-engine`
（先停服务并核对已停止，再改登记），详见[部署与运维](../部署与运维.md)的“因子机外部程序”。

引擎需要的凭据放在安装目录的 `secrets/` 下，必须是 0600 普通文件：Admin 导出的外部身份密钥
`access-factor-engine.key`（KeyID 经 `--access-key-id` 传入，独立于 caller 名）、
Storage primary 密钥 `storage-primary-auth.secret`、EventBus 凭据 `factor-eventbus.yaml`（旁边放它的 CA 文件），
以及 CLI 按运行身份渲染并上传的 `health-auth.env`。引擎不再需要控制机 Caddy 根证书，也不直接连接 Factor Manager。

常用命令：

```bash
systemctl --user restart moox-factor-engine                   # 重启
~/moox/factor-engine/bin/moox-factor-engine health            # 查看 /readyz 详情
moox-factor-engine run-once --task <任务 ID> --period <RFC3339>  # 单周期诊断（会写结果，跑在独立进程里不走任务执行器的串行锁：先暂停该任务，避免与实时写入或补算同时写同一期）
moox-factor-engine reset-gap-ledger --config config/engine.yaml --yes  # 引擎停止后删除空洞账本（数据被整体清空之后用）
moox-factor-mgr-cli recalc --task <任务 ID> --start ... --end ...  # 提交补算
```

| 现象 | 处理 |
| --- | --- |
| `/readyz` 返回 503 且 `lease_conflict=true` | 另一个引擎持有租约，停掉多余的引擎 |
| 日志出现 `factor_catalog_sync_failed` | 管理端不可达；引擎继续用最后快照计算，恢复后自动追平 |
| 事件反复 `factor_period_retry` | 结果数据集未就绪或 access 不可达 |
| 补算作业 `running` 但不前进 | 执行它的引擎已停止，等作业租约过期后会被重新领取 |

引擎与管理端的 tRPC 配置里不要启用 `transinfo-blocker` 客户端过滤器：网关客户端的签名头（`X-Moox-*`）走 tRPC 透传元数据，被白名单过滤后会表现为 code 41 或 Access 认证失败。

表达式执行器的资源配置在 `compute:` 段：`workers` 是一次程序执行的并行度（默认 min(4, 核数)），`max_memory` 是一个计算分块
估算峰值内存的上限（默认 1GiB，可写 `512MiB` 这样的字符串）。引擎是单个 Go 进程，没有子进程。

本地时序存储、窗口与内存的配置（`engine.yaml`）：

```yaml
seriesstore:
  dir: ./data/seriesstore       # Pebble 目录，数据永不删除，纳入备份
  block_cache: 512MiB           # 块缓存，计入进程内存预算
window:
  max_memory: 4GiB              # 所有窗口常驻内存的上限；新任务会超出时拒绝启用，0 不限制
  headroom: 0                   # 每个序列数组的余量根数，0 取窗口长度的 1/4（至少 16）
memory:
  total_budget: 12GiB           # 进程内存预算，常驻窗口与块缓存先扣除；0 不限制
sync:
  workers: 4
  batch_subjects: 100           # 同步时每批标的数（Storage 单次最多 100 个）
  follow_interval: 30s          # 读取变更日志、应用修正的间隔
lifecycle:
  state_file: ./data/engine/lifecycle.json
  interval: 30s                 # 生命周期检查周期
```

三项内存值不会自动设置（0 表示不限制）：安装后在引擎机器上执行 `moox-factor-engine tune --config config/engine.yaml` 查看建议值，加 `--write` 写入
（只写还没设置的项，`--force` 覆盖）。公式：总预算 = 总内存 × 60%；窗口上限 = (总预算 − 块缓存) × 40%；单次计算上限 = max(1GiB, (总预算 − 窗口 − 块缓存) × 50% ÷ 并行数)，
并行数取计划启用的任务数（`--tasks`）与核数的较小值；窗口与块缓存超过总预算的 2/3、或扣除后不足 1GiB 时给出警告。

新增的引擎子命令：`reconcile --task <任务 ID> [--subject <标的>]`（数据源变更日志断档后对账，引擎必须先停止）、`backfill --task <任务 ID> --bars <根数>`（把本地最早一根之前、Storage 保留期内的历史回补到指定根数，与本地相接，Earliest 前移会登记失效重算；引擎必须先停止）、`tune`（内存配置建议）。
旧配置里已删除的键（`pipeline.read_*`、`bulk_read_*`、`warmup_*`、`gap.enabled`、`gap.mass_ratio`）会被严格解析拒绝，升级前要从 `engine.yaml` 删掉；
健康服务的 `timeout`（`config/trpc_go.engine.yaml`）要调到 120000，导入的大批量写入与回放建立会话都比健康检查慢得多。

引擎经公网访问 Access，跨主机调用恒定压缩读取与写入的请求和响应（zstd 字典），减少公网带宽。单个周期的结果行（约 500 个标的）在一次 `UpsertFields` 内写完（`write_batch_rows` 默认 1000）。

不要通过清空消费者来恢复积压；先排查任务执行器积压和 Storage 错误，历史修正用补算作业。
引擎指标：`factor_period_total`、`factor_period_duration_seconds`、`factor_period_lag_seconds`、
`factor_failures_total`、`factor_runner_backlog`、`factor_compile_errors_total`、`factor_last_period_time`、`factor_series_change_gaps_total`。

## 9. 逐期回放

> 状态：已实现（设计 9）。

按时间顺序逐期推进历史数据，每期走实时计算路径算出因子，交给策略求值，再由 Trade 的纸面账本撮合，得到接近实盘时序的模拟结果。
**回放绝不产生实际下单**，不进入生产事件总线，不影响连续水位、监控新鲜度和实盘策略实例。

```bash
moox-cli replay start [--task <因子任务>] --instance <策略实例> \
  --from 2026-01-01T00:00:00Z --to 2026-02-01T00:00:00Z [--write-factors] [--quote next_open|close] \
  [--initial-cash 100000 --fee-rate 0.001 --slippage-bps 0]
moox-cli replay status|pause|resume|cancel|report|delete --replay <ID>
```

- `--task` 可省略，缺省取实例关联的因子任务。
- **三个模块各提供一组接口**（都挂在健康端口，签名鉴权）：因子引擎 `/v1/replay/open|step|close`——会话开始时从本地存储取快照窗口
  （运行中不随修正更新，向内存准入器低优先级预留），`step` 用实时计算路径算一期并返回因子帧、源数据列、报价与标的年龄；
  策略 `/v1/replay/bind|evaluate`——固定策略版本与因子绑定，复用实盘求值引擎，无状态（规则状态由回放服务保存），只返回本期决策；
  Trade `/v1/replay/session|advance|periods|close|delete`——纸面账本（`t_replay_*` 三张表：会话、周期记录、订单），
  每期按回放报价估值和撮合（先卖后买，买单受可用现金限制，缺价报错、不回退实时报价），按 `(replay_id, period)` 幂等，不接触实盘账户、订单、预留与执行器。
- **成交价**默认取下一根的开盘价（本期收盘决策、下期开盘成交），`--quote close` 取本期收盘价；时间语义：K 线起点是 `data_time`，决策时刻是 `data_time + 周期`。
- **校验**：本地数据覆盖回放区间，并且包含 `to` 之后的一根；不满足的标的被排除并列出原因。预热起点 = `from − (因子最大回看 − 1 + 策略引用上一根的深度) × 周期`；多数标的的本地数据晚于预热起点时（因子前段会是空值）拒绝建立会话并提示先回补或导入，`--allow-short-warmup` 可放行。
- **各模块的健康密钥可以不同**（因子引擎安装时生成自己的 `health-auth.env`）：回放命令优先读 `MOOX_FACTOR_` / `MOOX_STRATEGY_` / `MOOX_TRADE_` + `HEALTH_AUTH_ACCESS_KEY`、`_SECRET_KEY`、`_VERSION`，没有时用共用的 `MOOX_HEALTH_AUTH_*`。
- **周期记录与恢复**：回放服务自己的 SQLite（`--db`，默认 `./replay.db`）按 `(replay_id, period)` 保存本期决策、下一期策略状态、待发送的 `ReplayAdvance` 与各阶段完成标记
  （Trade 已确认、因子已写回、本期完成）。中断后用同样的参数（或只给 `--replay`）再次 `start` 即续跑：已完成的周期不重做，缺的阶段按记录补齐，
  Trade 未确认就原样重发（同一期重发返回同一条记录）；引擎重启后会话丢失（404）时自动重新建立。续跑时策略或因子定义变了会拒绝。
- `--write-factors` 每期把因子结果写回结果数据集（携带列加因子列，与区间重算相同的写法，不发周期完成事件）。
- 只要历史因子值，导入加区间重算（`--recalc`）比逐期回放快几个数量级；快速比较策略版本用策略研究回放（读取 View，区间受 View 保留根数限制）。

## 10. Manager 内部网关身份与构建

Manager 和 Factor CLI 的 Storage 调用统一使用 `gatewayclient`，覆盖 PrimaryStore 与 Metadata 的 14 个方法。
`config/app.yaml` 的 `gateway_client` 配置 caller `factor-mgr`、Admin 分配的 `key_id` 和签名 `key_file`；
KeyID 与请求体内固定的 `moox-factor` 角色认证独立。主机身份、loopback 地址和 MooX 私有 CA 从部署目录中同级
hostgateway 配置读取，Directory 缓存保存在数据库父目录的 `gatewayclient/directory.json`，权限为 0600。
Manager 持有进程级客户端，CLI 在命令结束时关闭；只读刷新重试和签名由共享层处理，写操作只发送一次。

Manager 与 CLI 共用严格配置加载器，旧 `storage` 配置及 `MOOX_FACTOR_STORAGE_*` 环境覆盖已删除；
未知字段、重复键和额外 YAML 文档会被拒绝。Engine 已通过同一外部 `factor-engine` 身份调用 Access；
Manager 的签名与 Storage 凭据由原生 control 部署分发，外置 Engine 使用第 8 节的独立安装流程。

Factor Manager、CLI 和 Engine 均可关闭 CGO 构建，由本机编译或交叉编译。
实际 `scripts/build/build.sh factor-mgr` 已在本机生成 Linux amd64 的 Manager/CLI 静态程序，并完成相关 Linux 运行验证。
远端 Linux CGO 构建入口仅用于需要 CGO 的 Storage 目标。

## 11. 动态调参

> 状态：已实现。设计与执行计划见[因子任务与参数模型重构设计](../计划/因子任务与参数模型重构设计.md)、[执行计划](../计划/因子任务与参数模型重构执行计划.md)。

策略可以在运行中根据行情逐期调整因子参数：第 T 期因子写出后，策略算出第 T+1 期的参数并异步投递给因子管理端，引擎开算第 T+1 期时取用最新的提交值。
每期实际用了什么参数，记在结果行的系统列 `__params`（第 2 节）里，没有单独的冻结记录、参数列或离线补报。

**概念**

- **参数声明**在因子定义里（第 6 节）：名称、类型（`int`/`float`）、范围、默认值。声明进 `definition_hash`，取值不进。
  结构型位置（窗口、位移）只接受整数参数，回看按范围上限推导，所以参数切换时内存窗口永远够用。
- **固定成员与可变成员**：固定成员的参数在加成员时写定，不再改；可变成员（成员键以 `__var` 结尾）的 `c_params` 是**默认参数**，
  实际取值由关联的策略逐期提交。一个因子在一个任务里最多一个可变成员；需要多个可变值就注册多个因子（`ma_fast`、`ma_slow`）。
- **唯一的写入方**是任务关联的策略实例：策略第一次启用实例时调用 `BindFactorTask`（幂等，一个任务只能关联一个实例，写入后不能改），之后只有这个实例能对该任务提交参数。
  任务没有关联实例、或某个标的从未提交过，就用默认参数。

**提交（`SubmitFactorParams`）**

请求为任务、成员键、目标期、`request_id` 与各标的的参数。factor-mgr 在一个 SQLite 事务里依次：

1. 校验：提交方是任务关联的实例；成员必须是可变成员；参数名是定义声明过的且在范围内（整型为整数、联合约束成立）；标的在源数据集当前的标的里。
2. 单调与幂等：目标期小于已接受的最后目标期的拒绝（乱序到达的旧请求）；目标期相等时 `request_id` 相同视为幂等成功，不同则拒绝。
3. 按标的合并：本次带了的标的覆盖旧值，没带的标的保留原值。
4. 写入成员行的 `c_last_submitted_*`（只有一格，不保留提交历史）。

**引擎取值（`GetTaskParams`）**

```text
开算第 t 期：
  本地缓存里有这个任务第 t 期的“进行中记录”？ ─ 有 ─► 直接用记录里的参数（失败重试、重启都复用）
                                              └ 无 ─► GetTaskParams 读各可变成员的 c_last_submitted_*（factor-mgr 连不上用最近一次读到的值）
  固定成员 → c_params；可变成员 → 这个标的的提交值，没有则 c_params（默认参数）
  把第 t 期选定的参数写入进行中记录（落盘）─► 计算 ─► 写结果行（因子值 + __params）─► 写周期标记 ─► 清掉记录
```

- 进行中记录在本地文件 `data/engine/param_cache.json`（`engine.yaml` 的 `params.cache_file`，`params.fetch_timeout` 默认 5 秒），保证**同一期重试不换参数**；
  同一个文件还保存最近一次读到的提交值，factor-mgr 暂时连不上或引擎重启后接着用，不退回默认参数。文件不是事实来源，删了只会让离线期间退回默认参数。
- 策略要提交第 t+1 期的参数，前提是第 t 期因子已经写出，所以引擎读到的提交值不会超前；读到超前值时改用本地缓存并告警。
- **晚到与积压**：第 t+1 期已经开算后，目标期为 t+1 的提交才到，新值从 t+2 起生效。引擎追赶积压时按期次依次计算、**不等策略**，所以追赶期间不保证每期都用上针对这一期算出的参数，
  只保证参数不超前、不倒退，每期实际用的都如实记在 `__params`。策略停止后不再有提交，沿用最后一次的参数。

**引擎计算**

- 周期事件分发给同一源数据集上的**每个**启用任务，各自在自己的串行任务执行器（runner）里算，不同任务并行（同一事件的多个任务同时开算，全部返回后才决定 ACK 或重投）；
  每个任务只算自己的成员，不做跨任务的公共计算，两个任务有相同成员就各算一遍。某个任务失败只影响它自己的这一期，其他任务照常写出，重投时已完成的任务靠周期标记跳过。
- 参数是运行时输入：每个参数槽是“每个序列一个值”的向量，窗口类算子逐序列取值；同一期里结构相同、参数向量相同的节点只算一次。
- 周期明细（`PeriodDetail`）以成员为单位（`member_key`、`factor_id`、`definition_hash`、`member_kind`），策略的就绪判定、失败标的映射、相邻周期记录都按成员键。
- **补算**：按期读取已有行 `__params` 里这个成员的参数重算，连续若干期参数相同的合成一段一次算完；写回时合并 `__params`。
  一致性只对「原行存在、且 `__params` 里有这个成员」的期次作保证（重算结果与原值逐位相同）；原行不存在或没有这个成员时，固定成员用 `c_params`，可变成员用默认参数，
  算出的是**新补的值**，补算作业的结果摘要会列出这些按默认参数补的期次（`default_filled`）。

**策略侧投递**（详见[策略](策略.md)）：策略求值时同时算出下一期的参数，与结果在同一个事务里落库（`c_next_params_json`），投递循环只投当前会话里最新一条还没送达的结果，
送达后写 `c_params_delivered_at`，重试按退避。目标期不减的规则保证重试的旧请求不会让参数倒退。

**监控**：因子侧不再导出参数相关告警。策略侧导出 `moox_strategy_param_delivery_stale{space_id,instance_id}`：实例在运行、任务有可变成员、连续
`params.stale_alert_periods`（策略配置，默认 10）期结果都没有成功送达参数时为 1；实例停止后自动解除。Monitor 的 `factor_params` 检查（名称「策略参数投递」）读这个指标。

**回放**：调参策略的因子依赖上一期策略输出，不能先算完因子再跑策略。第 9 节的逐期回放对关联任务里有可变成员的实例，每期因子步进带着策略上一期产出的参数（缺值沿用），
因子帧里带上这一期各标的实际生效的参数；参数只存在回放会话的内存里，不写成员行。引擎对请求里每个成员的参数做与实时提交相同的校验，不合法的成员沿用上一期实际用的参数、整期不失败，
拒绝原因随步进响应返回（`rejected_params`），同时返回实际生效的请求参数（`applied_params`）。闭环回放的结果是一次新的模拟，不等同于已有的实时历史，也不把结果写回结果数据集（`--write-factors` 对调参回放被拒绝）。
策略自己的 View 回放（`StartReplay`）不支持声明了 `factor_params` 的策略。复现已发生的历史用补算，不需要重跑策略。
