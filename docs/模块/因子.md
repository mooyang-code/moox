# 因子（Factor）

Factor 负责因子定义的管理和计算：每当一个采集周期完成，就对相应的源数据集计算已启用的
因子（用表达式定义，由引擎内置的 Go 执行器计算），把结果写入因子结果数据集，供 Strategy 使用。也支持对历史区间发起补算。
表达式引擎的完整设计见[因子表达式引擎详细设计](../计划/因子表达式引擎详细设计.md)。

代码位置：`modules/factor`。同一个 Go 模块构建两个进程。

## 1. 组成与部署

| 进程 | 运行位置 | 职责 |
| --- | --- | --- |
| `moox-factor-mgr` | control 主机 | `FactorMgr` 管理接口：因子定义、计算任务（因子集）、成员、补算任务、状态；维护 SQLite 和结果数据集；通过内部服务 `FactorEngine` 给引擎提供目录、租约和补算任务 |
| `moox-factor-engine` | 操作员机器（只做出站连接） | 消费采集周期完成事件，运行周期流水线和补算任务，写入因子结果 |
| `moox-factor-mgr-cli` | control 主机 | 初始化数据库、导入因子、提交补算、查看状态 |
| `moox-importer` | 因子机（引擎旁） | 把历史 K 线文件导入因子机的本地时序存储，见第 3 节「本地时序存储」；同时写 Storage 用 `moox-cli import` |
| `moox-replay` | 任意能访问各模块健康端口的机器 | 逐期回放的编排，见第 9 节；`moox-cli replay` 是同一份实现 |

| 进程 | 端口 |
| --- | --- |
| manager | FactorMgr 原生 tRPC `11403`，FactorEngine 原生 tRPC `11405`，健康 `11414` |
| engine | 健康 `11417`（同时承载本地写入 `/v1/series/*`、生命周期 `/v1/lifecycle/*`、回放 `/v1/replay/*`）、admin `11945`、metrics `12945`（均只监听本机） |

引擎的网络连接全部是出站的：

| 方向 | 地址 | 用途 |
| --- | --- | --- |
| 引擎 → Access | `<access>:11004`（`access@<主机>`） | 同步目录、心跳、领取和上报补算任务（FactorMgr），读源数据、写因子结果与周期标记（Storage）；两者共用同一个固定 Access 与外部身份 `factor-engine` |
| 引擎 → 控制机 | `tls://<控制机>:4222` | 订阅 `CollectorPeriodCompleted`（`factor-eventbus` 凭据） |

管理端在创建或编辑定义时编译表达式校验；`PreviewFactor` 试算时直接读 Storage、在进程内计算少量标的，不经过引擎，
不写结果。管理端不消费 EventBus。

## 2. 领域模型

Factor 的 SQLite 只有四张业务表：

| 表 | 内容 |
| --- | --- |
| `t_factor_defs` | 全局因子定义：`factor_id`、展示名、表达式定义（spec）与原文哈希、`allow_partial_universe`；类型、输入列、输出列与回看由编译推导，不落库 |
| `t_factor_sets` | 计算任务（因子集）：源数据集、空间、频率、标的范围（全部 / 指定）、结果数据集、状态 |
| `t_factor_set_members` | 定义与计算任务的成员关系，各自独立启停 |
| `t_factor_recalc_jobs` | 补算任务：范围、筛选、进度、结果摘要、执行引擎 |

- 定义指纹 `definition_hash` 覆盖完整计算契约：表达式语义版本（`expr/1`）、编译后的规范程序文本与
  `allow_partial_universe`。只改注释、格式、`let` 名不会改变它，任何影响结果的改动都会改变它。它在读取时派生、不落库，
  随 `FactorDef` 和周期标记的 `FactorPeriodState` 一起下发；Strategy 启用实例时固化它，之后据事件里的指纹判断因子版本是否变化。
  事件层要求指纹非空；升级前先排空出站队列，仍然无法通过校验的旧记录由 Storage 隔离，不会堵住其后的事件。
  `spec_hash` 只代表定义原文（周期标记里沿用 Storage 协议的 `source_hash` 字段名承载它）。
- 计算任务 ID 和结果数据集 ID 由源数据集与频率确定。输出列在 Storage 列元数据里标记为
  `origin=factor`、`origin_id=<factor_id>`。
- 输入列、输出列、类型与回看都由编译推导：表达式里引用的、不是 `let`/`params`/函数名的标识符就是输入列；
  用到截面算子（`cs_*`）的是截面因子。系统列 `subject_id`、`freq`、`data_time`、`series_tag` 不能作为输入或输出。
  回看按周期网格计数（缺失的 K 线是 NaN，严格窗口会让受影响的结果为 null）。
- 加入计算任务时校验：输入列都存在于源数据集且是数值列（int、double），`params`/`let` 不与源列重名，
  输出列不与源列、其他成员的输出或结果数据集里别的因子拥有的列重名。
- 成员加入后为停用状态；`SetFactorMemberStatus(enabled)` 会重新校验、对齐结果数据集的列，
  并原子提交一次补算。停用或移出不删除已写入的列和值，只停止后续写入。仍被引用的定义、
  仍有成员的计算任务都不能删除；成员启用期间定义不能修改。

## 3. 周期流水线

```text
CollectorPeriodCompleted
  ─► durable factor_collector_period_v1
  ─► 按计算任务进入各自的串行 lane（不同任务并行）
  ─► 生命周期门禁：集合没有处于预热或运行就 ACK 不计算
  ─► 冻结本周期启用的定义，规划最大回看窗口
  ─► 把本期标的从 Storage 同步到本地时序存储（只拉增量），抓取内存窗口的读租约
  ─► 集合内全部因子编译成一个程序（相同子表达式只算一次），在网格面板上执行
  ─► WriteFactorRows（携带列 + 因子列）─► ReportFactorPeriodComputed ─► ACK
  ─► Storage View 应用标记后发布 ViewDataReady
```

- 每个 (标的, `series_tag`) 是一条序列；时序算子沿序列计算，截面算子在同一 `(data_time, series_tag)` 的全部可用标的之间计算。
  结果只在有源行的目标时刻产生，行身份是源行的 `(data_time, series_tag)`。同一份输入的结果与并行度、分块、
  是否与其他因子共享节点无关，逐位相同（实时写入的提交 ID 依赖它）。
- **本地数据与窗口。** 实时、补算、重算都从因子机的本地时序存储（Pebble，数据永不删除）读取；每个启用集合的回看窗口常驻内存
  （按序列的列式环形数组，实时周期之间只追加一根）。Storage 只在增量与修正时被读取，详见下面「本地时序存储」。
- **窗口没载入完成，本期不算。** 引擎成为活动引擎、或目录里出现新集合后，后台预载每个集合的窗口（取同步基线、补到最新已收盘的一根、载入内存）；
  载入完成之前该集合的标的本期都不算：结果不正式、按失败标的上报，持有它们的策略不会使用该周期，跳过的 (因子, 标的, 周期)
  记入跳过账本（`reason=warming`），载入完成后由跳过恢复「只填充」补算，历史结果不会缺一根；marker 不改写，也不再触发策略。
- **补齐的最新一期记入运行摘要。** 跳过恢复补齐的如果是某集合最新的一期，账本里这一期没有待办之后，引擎改写这一期的运行摘要：
  去掉补齐的失败标的、不再算预热中，余下没有失败就记为完成，完成时刻改为补齐的时刻，并立刻补发心跳（日志
  `factor_period_repaired`）。补算没覆盖的失败（上游失败、读取失败、计算出错、放弃或取消的待办）原样保留；已失败的期次不改写。
  整因子跳过的严格截面因子（实时路径一行没写）按补算重算全集的逐项结果判断，这次没写成的标的仍记为失败。
- 单个因子或标的计算失败不影响其他结果；可恢复的 Storage 基础设施错误会让消息重投，
  其他错误汇总进周期状态后照常上报完成并 ACK，避免坏因子阻塞整条 lane。
- `WriteFactorRows` 使用提交 ID 幂等去重（实时周期是内容摘要，相同内容的重投被去重；补算与含空洞失效的写入每次执行加一个唯一的盐，不会被旧回执吞掉），只有这个专用接口能写因子结果列；
  完成标记在结果行之后写入，同一数据集由 DataNode Outbox 保序。
- 当前只支持 `crypto` 空间的连续周期日历，其他空间返回 `unsupported space calendar`。

### 连续水位

引擎为每个因子集合保存连续水位（`watermark.state_file`，默认在跳过账本旁的 `factor-watermarks.json`，原子写）：`committed_through`（W）表示这一期及之前都已连续算完，
`target` 是收到的最新收盘周期。收到 T 的事件后，引擎在该集合的串行 lane 里从 W 的下一期推进到 T：

- 有事件的周期用事件里的期望标的与失败标的；没有事件的周期（零提交，或阻塞期间已经 ACK 的事件）读回 Storage 判断哪些标的已到（读集合第一个因子的第一个输入列）。
- 零提交或缺失比例超过阈值（`watermark.max_missing_ratio`，默认 0.1，`watermark.set_ratios` 按集合覆盖）时**阻塞**：W 不前进、不计算，记下 `blocked_since`。
  阈值以内的缺失照常计算，缺的标的记进跳过账本（`reason=upstream_failed`），补采补齐后由跳过恢复「只填充」补算。
- 读回推进的周期用合成的触发事件 ID `catchup:<集合>:<周期>`，marker 与正常周期一样，策略只会看到连续的结果。一次最多推进 `watermark.max_periods`（30）期。
- 事件处理完一律 ACK（只有基础设施错误重投），阻塞靠本地状态续推：追赶循环每 `watermark.poll_interval`（10 秒）对 `target > W` 的集合再推进一次，不占 JetStream 的待确认名额。
- **补齐通知**：Collector 补采作业成功后调 `FactorMgr.NotifyPeriodsFilled`（数据集、频率、范围、补采确认行情源没有的标的），factor-mgr 暂存并在引擎心跳响应里带回；
  引擎收到后立即推进相应集合、唤醒跳过恢复，范围内 `upstream_failed` 的待办不再等 `gap.settle`。确认没有的标的在 30 分钟内不计入缺失比例。
- 第一次见到某个集合时 W 取 T 的前一期：只从上线起保证连续，历史用补算。重启后从状态文件恢复 W 与 target 继续追赶。
- 心跳带各集合的水位与阻塞状态；factor-mgr 导出 `moox_factor_set_watermark_blocked_since_timestamp_seconds`，阻塞超过 30 分钟 Monitor 告警（不自动跳过，交给人工手动补采或确认缺失）。

设计见[因子连续水位详细设计](../计划/因子连续水位详细设计.md)。

### 本地时序存储

> 状态：已实现。完整设计见[因子本地K线存储设计](../计划/因子本地K线存储设计.md)。

因子按「最近 N 根」取回看窗口，**窗口中间缺了几根时，因子照样算出一个看似正常的数**。过去靠每期检查窗口连续性、缺了就跳过；
现在改为**本地数据在写入时就保证连续**，窗口里不会再有空洞，也就不再有逐期的空洞检查（`gap.enabled`、`gap.mass_ratio` 已删除）：

- **存储。** `seriesstore`（`modules/factor/internal/seriesstore`）按 `k/{空间}/{数据集}/{频率}/{标的}/{块起点}` 存列式块，
  频率支持 1m 5m 15m 30m 1h 4h 1d；块跨度因频率而异（1m 按小时、5m 按 6 小时、15m 与 30m 按天、1h 按周、4h 按月、1d 按年）。
  只有一种写入语义：**整段替换**（用一批行替换标的在 `[from, to)` 内的全部数据）。每个标的在 `[Earliest, Latest]` 上按频率网格连续，
  所以「同步到哪里」只看 `Latest`。实测导入约 102 万行/秒，一批 200 个标的的实时写入约 10ms。
- **缺失行与填充。** 交易所本身缺数据的周期，写入时按字段的 `fill` 属性填成带标记的填充行：`prev`（取上一期该字段的值，默认）、
  `prev_close`（取上一期的 close，给 open/high/low/close）、`zero`（填 0，给 volume 等量类字段）。空洞没有长度上限。
  填充行带已填充标记，表达式里可用虚拟列 `is_filled`（1 或 0）区分；之后拿到真实数据，整段替换会把填充行换成真实行，
  并重新生成它之后的填充行。`fill` 属性存在数据集字段的 `attributes` 里（Storage 注册时校验，`moox-cli metadata import` 的 `dataset_columns[].attributes` 可写）。
- **窗口。** `serieswindow` 为每个数据源保留集合内最大回看根数（加余量）的内存窗口，实时只追加；换代（压缩）时复制，读租约抓到的切片不受影响。
  窗口内存超出 `window.max_memory` 或进程预算 `memory.total_budget` 时拒绝启用该集合，并给出估算值。
- **进程级内存准入。** 计算、回放、重算、导入向 `memadmit` 预留内存，预留不到就排队、等不到拒绝；实时周期优先级最高。
  常驻的窗口与块缓存先从总预算里扣除。
- **与 Storage 的同步。** Storage 为数据集行写入维护持久化的**变更日志**（`__changelog/`，保留 7 天，由 outbox relay 顺带清理；因子结果的写入不记），
  新增读取接口 `ReadDatasetChanges`。同步器：`Pull` 从本地 `Latest` 之后拉增量；`Baseline` 在读数据之前先取变更日志位点；
  `Follow` 读取位点之后的变更，只在内容与本地不同时应用，并把改变的区间记入「失效重算」待办，引擎据此重算受影响的周期；
  位点已被清理（断档）时该数据源标为未就绪，由 `moox-factor-engine reconcile --set <集合>` 对账（需要先停止引擎，Pebble 同一时刻只能由一个进程打开）：
  取位点、在保留期内逐标的比对、写入差异、再跟进变更。
- **导入。** `moox-importer run`（或 `moox-cli import --target storage,factor`）把 CSV 等文件导入：先校验全部文件再写入，按时间边界切批，
  断点记在 SQLite（重跑自动续传），写因子机经引擎的 `/v1/series/*` 接口（签名鉴权，引擎未就绪时也能写）。格式解析在 `packages/seriesformat`
  （`Decoder` 注册表，目前有 csv）。`--allow-missing` 允许序列内部缺周期（按字段填充规则写成填充行），`--recalc` 把改变的区间记入失效重算。
- **仍保留的跳过账本。** 引擎本地账本（`factor-gap-YYYYMM.jsonl`，按月一个文件、永不自动删除）记录每次跳过（窗口没载入完成 `reason=warming`、
  上游数据没到 `reason=upstream_failed`）；引擎每 5 分钟检查缺口是否已补上，补上后在进程内做**只填充**的重算（只写完整窗口算出的值，从不写失效 NULL），
  写入确认后记 `repaired`；超过 6 小时仍补不上记 `gave_up` 并告警，由操作员手工补采和补算。恢复区间相同的分组合并成一次重算（每批最多 100 个标的），
  每轮最多运行 `gap.max_groups_per_sweep` 批。缺口如果早于数据集最早的采集计划生效点，普通补采看不到，用 `moox-cli collector kline backfill --force` 指定范围补采。
  恢复只写历史因子行，不改写原 marker，也不触发策略。
- **监控口径。** 一期只因窗口没载入完成而不完整，向 Monitor 报告为 `partial`（数据积累中），不算失败也不算成功；其他失败按失败处理。
  指标 `factor_gap_pending`、`factor_gap_skipped_total`、`factor_gap_gave_up_total`、`factor_gap_ledger_degraded`、`factor_series_change_gaps_total`（变更日志断档次数）。
- **永久审计。** 账本即审计，可用 DuckDB 的 `read_json_auto` 或 `jq` 分析。

### 生命周期

> 状态：已实现（设计 6）。`packages/lifecycle` 是各模块共用的状态机，阶段与颜色：未初始化（灰）、未就绪（红）、就绪（蓝）、预热（黄）、运行（绿）、暂停（橙）、恢复追赶（青）、重置中（紫）、重置失败（红）、故障（红）。

引擎的对象是目录里启用的因子集合，模块自身是基础设施（第一次检查时自动初始化）。**只有处于预热或运行的集合才计算**；新集合要依次执行：

```bash
moox-cli lifecycle init  --set <集合>   # 载入本地窗口（读字段、取基线、补到最新已收盘的一根）
moox-cli lifecycle start --set <集合>   # 启动：进入预热，因子正常计算，策略对预热实例发影子目标
moox-cli lifecycle confirm --set <集合> # 确认预热结果：进入运行
```

- 启动前检查：本地窗口已载入完成、数据源变更日志没有断档（失败项带处理办法，例如 `moox-factor-engine reconcile --set <集合>`）。
  `moox-cli lifecycle status` 列出各对象阶段与未就绪原因。
- **暂停与恢复**（设计见[暂停恢复与重置设计](../计划/暂停恢复与重置设计.md)）：`pause [--reason 原因]` 在就绪、预热、运行时都可以暂停，暂停详情带类型（手动 / 系统 / 自动）、原因、操作者和时间；
  手动暂停只有 `resume` 才恢复。`resume` 先进入**恢复追赶**（不计算、不下单，只做追赶门禁放行的历史写入），追平后自动放行回到暂停前的阶段；
  `--manual-release` 让追平后停在待放行，等 `release`（系统级恢复用）。`catchup` 查看追赶进度。
- **三条后台写结果路径并入生命周期门禁**：补算作业、缺口恢复、失效重算都经过补算执行器，集合暂停、恢复追赶（对象未参与）、重置期间执行器返回 `ErrGated`（不记失败，作业租约到期后由放行后的引擎继续）；
  实时事件用实时门禁，连续水位追赶用实时门禁或追赶门禁。恢复追赶的目标由 `Continuity.NoteTarget` 显式建立，不等下一条实时事件。
- **恢复追赶**（集合级 `Catchup` 钩子）：① 后台同步本地数据（`Data.Prepare` = Follow 已有范围的修正 + Pull 新增尾部 + 重载内存窗口，每次恢复一次）→ ② 显式建立追赶目标（暂停区间内最新已收盘周期，扣采集宽限）→ ③ 唤醒连续水位追赶循环，在追赶门禁下补算暂停区间每个周期并发布历史结果 → ④ 水位追到目标且没有阻塞才算追平。
  变更日志断档（暂停超过保留期或 Storage 身份变化）时增量同步追不上，追赶报告「变更日志断档」，需要人工离线维护（`moox-factor-engine reconcile` / `backfill`）。
  系统恢复时由 `moox-cli system resume` 保证采集先补采完、因子才开始同步。
- 预热或运行中检查失败的集合**自动暂停**，只影响它自己，检查重新通过后自动回到暂停前的阶段；期间漏掉的周期由现有追赶机制补算。
  重启后先跑检查，通过就回到重启前的阶段（首页提示「已自动恢复」），阶段持久化在 `data/engine/lifecycle.json`。
- 接口挂在引擎健康端口：`GET /v1/lifecycle/status`、`POST /v1/lifecycle/command`；`/healthz` 的 `details.lifecycle` 带精简快照，Monitor 据此汇总首页的系统状态。
- 依赖链向下传：数据源断档 → 因子集合暂停（显式）→ 它的策略实例收不到新事件，没有新目标、持仓不动（隐式，策略侧的实例阶段单独管理，见[策略](策略.md)）。

## 4. 补算

补算任务按目标区间 `[start, end)` 执行，按 `recalc.chunk_periods` 分块（当前默认 500 个目标周期），块内不拆分同一 `data_time`
的不同 series_tag，并在块起点前读取所需回看。已完成的块不会因后续失败回滚；同一请求 ID 可
幂等提交。补算可以按因子和标的缩小范围，但不能改变定义里的输入、输出和参数。

引擎通过 `PullRecalcJob` 领取任务（带任务租约，默认 15 分钟），每完成一块用
`ReportRecalcProgress` 上报；引擎停止后租约过期，任务会被重新领取并从 `progress_time` 续跑。

**回填与补算对 Storage 的负载防护**（2026-10-14 两个 1h 因子集同时回填，把 4 核的 `storage-node` 打到 330% 以上、读窗口反复超时之后加上的）：

- **同一因子集只建一个回填任务**：启用成员时，如果同一个因子集已经有排队中、还没被引擎领取的 `factor-enable-` 回填任务，新成员并进这个任务，窗口取并集。
  逐个启用 11 个成员只会产生 1 个任务，而不是 11 个各读一遍同一窗口的任务。手工补算、已领取或已结束的任务不会被并入。
- **默认回填最近 5000 期**（`catalog.DefaultMaxBackfillPeriods`）：回填窗口取结果数据集保留期（保留期无限时取源数据最早一期）与最近 5000 期中较近的一个。
  时序 View 只保留最近 `view_rows_per_series`（默认 10000）根，更早的因子结果没有读取方。需要更长的历史时用 `moox-factor-mgr-cli recalc` 显式指定范围。
- **同时只跑一个补算任务**（所有引擎合计，`enginehub.DefaultMaxRunningJobs`）：领取任务时在同一个事务里数租约未过期的运行中任务，达到上限就不再发出新任务。
- **补算读本地。** 补算、只填充与失效重算都从本地时序存储读 `[回看起点, 终点)`，不再向 Storage 逐批读窗口，也就不需要读取并发、退避与断路的配置
  （`pipeline.read_*`、`bulk_read_*`、`warmup_*` 已删除）；分块大小由内存准入与 `compute.max_memory` 约束。补算分块遇到基础设施错误的重试仍是指数退避（5 秒起，上限 2 分钟）。

## 5. 管理端与引擎的协作

- **目录同步。** 引擎启动时立即同步一次，之后在每分钟第 45 秒调用 `SyncEngineCatalog` 拉取带哈希的目录快照并落盘
  （`data/engine/catalog.json`）；管理端不可达时继续用最后一份快照计算。新启用的成员在引擎下一次
  同步之前的周期不会自动补算，需要时手动提交补算。引擎安装快照时编译全部定义（派生字段以编译结果为准）；
  补算任务自带完整定义，引擎领取后现场编译，不依赖目录同步。引擎侧编译失败（只在管理端与引擎的 expr 版本不一致时出现）
  只让该因子本期对全部标的失败，计入 `factor_compile_errors_total`。
- **引擎租约。** 引擎每 10 秒调用 `EngineHeartbeat`；同一时刻只有一个 `engine_id` 持有租约，
  旧引擎停止心跳 45 秒后新引擎自动接管。心跳同时上报各计算任务最近的运行摘要；平时每 10 秒一次，每算完一期立刻补发一次。
- **状态。** `FactorMgr.GetStatus` 返回引擎是否在线、最后心跳时间、目录是否与管理端一致，
  消费者、lane、计算线程数、引擎与管理端各自的 expr 语义版本（不一致时控制台标红），以及最近运行情况。
- **监控。** 管理端把引擎心跳中的运行摘要转换为因子结果数据集的数据集指标，由 Monitor 的数据集
  新鲜度检查覆盖因子计算。每收到一次被接受的心跳就立刻刷新这些指标，水位前进时补报一份快照，
  Monitor 约 1 秒内看到这一期的完成时刻（不再等 30 秒的定时上报）。同一期只记一次，除非结果变好：
  从不正式（预热中、出错，不推进产出水位）变为正式、或从不完整变为成功时再记一次（补算补齐了这一期），
  产出水位随之前进，到达时间是补齐的时刻，“数据积累中”当场消失，不用等下一期；水位已经推进过的一期升级为成功时
  水位不动、到达时间不变，管理端主动补报一次。

## 6. 表达式语言

因子定义（spec）是一份 YAML 文档：

```yaml
params: {window: [5, 20]}          # 可选：命名常量；列表会展开成多个输出
let:                               # 可选：有序的中间量，后面的可以引用前面的
  ma: ts_mean(close, window)
outputs:                           # 必填：输出列名 → 表达式
  bias_{window}: close / ma - 1     # 展开为 bias_5、bias_20
```

- 表达式支持数字、`true`/`false`、标识符、`+ - * / % **`、比较、`and`/`or`/`not`、`c ? a : b` 与已登记的函数调用；
  其余语法一律拒绝，报错带字段路径和行列。窗口、位移等参数必须是编译期常量。
- 函数分三类：逐元素（`abs`、`log`、`where`、`clip`、`fill_nan` 等）、时序（`delay`、`ts_mean`、`ts_std`、`ts_rank`、
  `ts_corr`、`ema`、`sma` 等）、截面（`cs_rank`、`cs_zscore`、`cs_demean`、`cs_scale`）。完整清单、参数范围、回看规则与说明
  由 `ListFactorFunctions` 返回，控制台编辑器的函数参考面板即来源于此。
- 空值语义：null 与网格上缺失的行读作 NaN；任一输入为 NaN 结果即为 NaN（`where` 的未选分支除外）；±Inf 一律记为 NaN；
  **严格窗口**：时序窗口内只要有一个 NaN 结果就是 NaN，没有 `min_periods`；截面算子跳过输入为 NaN 的标的。
  写入时 NaN 为 null。
- 回看由编译推导（例如 `ts_rank(ts_mean(x, 20), 20)` 是 39）；`ema`/`sma` 截断到权重低于 1e−9 的 K 根（`ema(x, 20)` 为 208）。
- 限制：spec 64 KiB、单条表达式 4096 字符、展开后最多 64 个输出、窗口 1～5000、推导出的回看不超过 5000。

因子库位于 `modules/factor/factors/`（`*.yaml`，每个文件是 `[{factor_id, name, spec}]` 列表），
用 `moox-factor-mgr-cli import-catalog --dir ./factors` 导入；单个定义用 `import --file <文件> --factor-id <ID>`。
示例见 [`examples/factors`](../../examples/factors/)。
离线检查与试算用 `packages/factorexpr/cmd/factorexpr`（`functions`、`check`、`eval`，与引擎同一个编译器和执行器）；
把旧 Python 因子转成表达式并逐值核对的完整流程见 [`skills/moox/references/factor-dsl.md`](../../skills/moox/references/factor-dsl.md)。

## 8. 运维

安装或更新引擎：

```bash
scripts/deploy/deploy-factor-engine.sh \
  --dir ~/moox/factor-engine \
  --access-address <access 主机>:11004 --access-id access@<主机ID> \
  --access-key-id <Admin 分配的 KeyID> \
  --eventbus-url tls://<控制机>:4222
```

脚本会编译引擎、渲染 `config/engine.yaml`（含 `compute:` 段），
macOS 用 launchd（`com.moox.factor-engine`）、Linux 用 systemd 用户服务托管，并等待 `/readyz`。
安装目录不要放在 `~/Documents` 等受 macOS 隐私保护的目录下，否则进程会卡在启动阶段。

Windows 上以管理员身份运行 `scripts/deploy/deploy-factor-engine.ps1`（参数与 bash 脚本对应，`-Binary` 指定用 `TARGET_GOOS=windows TARGET_GOARCH=amd64 scripts/build/build.sh factor-engine` 构建的 `.exe`）：默认装到 `%LOCALAPPDATA%\moox\factor-engine`，注册为开机延迟自动启动、失败 10 秒后重启的系统服务（`moox-factor-engine.exe service stop|start|uninstall`），密钥要求 ACL 只允许当前用户与 SYSTEM。引擎离线约 3.5 分钟后 Monitor 推送“因子引擎在线状态”告警（factor-mgr 按最近心跳评估，见[监控](监控.md)第 12 节）。

引擎需要的凭据放在安装目录的 `secrets/` 下，必须是 0600 普通文件：Admin 导出的外部身份密钥
`access-factor-engine.key`（KeyID 经 `--access-key-id` 传入，独立于 caller 名）、
Storage primary 密钥 `storage-primary-auth.secret`、EventBus 凭据 `factor-eventbus.yaml`（旁边放它的 CA 文件），
以及安装时生成的 `health-auth.env`。引擎不再需要控制机 Caddy 根证书，也不直接连接 Factor Manager。

常用命令：

```bash
launchctl kickstart -k gui/$(id -u)/com.moox.factor-engine   # 重启（macOS）
~/moox/factor-engine/bin/moox-factor-engine health            # 查看 /readyz 详情
moox-factor-engine run-once --set <set_id> --period <RFC3339>  # 单周期诊断
moox-factor-engine reset-gap-ledger --config config/engine.yaml --yes  # 引擎停止后删除空洞账本（数据被整体清空之后用）
moox-factor-mgr-cli recalc --set <set_id> --start ... --end ...  # 提交补算
```

| 现象 | 处理 |
| --- | --- |
| `/readyz` 返回 503 且 `lease_conflict=true` | 另一个引擎持有租约，停掉多余的引擎 |
| 日志出现 `factor_catalog_sync_failed` | 管理端不可达；引擎继续用最后快照计算，恢复后自动追平 |
| 事件反复 `factor_period_retry` | 结果数据集未就绪或 access 不可达 |
| 补算任务 `running` 但不前进 | 执行它的引擎已停止，等任务租约过期后会被重新领取 |

引擎与管理端的 tRPC 配置里不要启用 `transinfo-blocker` 客户端过滤器：网关客户端的签名头（`X-Moox-*`）走 tRPC 透传元数据，被白名单过滤后会表现为 code 41 或 Access 认证失败。

表达式执行器的资源配置在 `compute:` 段：`workers` 是一次程序执行的并行度（默认 min(4, 核数)），`max_memory` 是一个计算分块
估算峰值内存的上限（默认 1GiB，可写 `512MiB` 这样的字符串）。引擎是单个 Go 进程，没有子进程。

本地时序存储、窗口与内存的配置（`engine.yaml`）：

```yaml
seriesstore:
  dir: ./data/seriesstore       # Pebble 目录，数据永不删除，纳入备份
  block_cache: 512MiB           # 块缓存，计入进程内存预算
window:
  max_memory: 4GiB              # 所有窗口常驻内存的上限；新集合会超出时拒绝启用，0 不限制
  headroom: 0                   # 每个序列数组的余量根数，0 取窗口长度的 1/4（至少 16）
memory:
  total_budget: 12GiB           # 进程内存预算，常驻窗口与块缓存先扣除；0 不限制
sync:
  workers: 4
  batch_subjects: 100           # 同步时每批标的数（Storage 单次最多 100 个）
  follow_interval: 30s          # 读取变更日志、应用修正的间隔
lifecycle:
  state_file: ./data/engine/lifecycle.json
  interval: 30s                 # 生命周期检查周期
```

三项内存值不会自动设置（0 表示不限制）：安装后在引擎机器上执行 `moox-factor-engine tune --config config/engine.yaml` 查看建议值，加 `--write` 写入
（只写还没设置的项，`--force` 覆盖）。公式：总预算 = 总内存 × 60%；窗口上限 = (总预算 − 块缓存) × 40%；单次计算上限 = max(1GiB, (总预算 − 窗口 − 块缓存) × 50% ÷ 并行数)，
并行数取计划启用的集合数（`--sets`）与核数的较小值；窗口与块缓存超过总预算的 2/3、或扣除后不足 1GiB 时给出警告。

新增的引擎子命令：`reconcile --set <集合> [--subject <标的>]`（数据源变更日志断档后对账，引擎必须先停止）、`backfill --set <集合> --bars <根数>`（把本地最早一根之前、Storage 保留期内的历史回补到指定根数，与本地相接，Earliest 前移会登记失效重算；引擎必须先停止）、`tune`（内存配置建议）。
旧配置里已删除的键（`pipeline.read_*`、`bulk_read_*`、`warmup_*`、`gap.enabled`、`gap.mass_ratio`）会被严格解析拒绝，升级前要从 `engine.yaml` 删掉；
健康服务的 `timeout`（`config/trpc_go.engine.yaml`）要调到 120000，导入的大批量写入与回放建立会话都比健康检查慢得多。

引擎经公网访问 Access，跨主机调用恒定压缩读取与写入的请求和响应（zstd 字典），减少公网带宽。单个周期的结果行（约 500 个标的）在一次 `WriteFactorRows` 内写完（`write_batch_rows` 默认 1000）。

不要通过清空消费者来恢复积压；先排查 lane 积压和 Storage 错误，历史修正用补算任务。
引擎指标：`factor_period_total`、`factor_period_duration_seconds`、`factor_period_lag_seconds`、
`factor_failures_total`、`factor_lane_backlog`、`factor_compile_errors_total`、`factor_last_period_time`、`factor_series_change_gaps_total`。

## 9. 逐期回放

> 状态：已实现（设计 9）。

按时间顺序逐期推进历史数据，每期走实时计算路径算出因子，交给策略求值，再由 Trade 的纸面账本撮合，得到接近实盘时序的模拟结果。
**回放绝不产生实际下单**，不进入生产事件总线，不影响连续水位、监控新鲜度和实盘策略实例。

```bash
moox-cli replay start --set <因子集合> --instance <策略实例> \
  --from 2026-01-01T00:00:00Z --to 2026-02-01T00:00:00Z [--write-factors] [--quote next_open|close] \
  [--initial-cash 100000 --fee-rate 0.001 --slippage-bps 0]
moox-cli replay status|pause|resume|cancel|report|delete --replay <ID>
```

- **三个模块各提供一组接口**（都挂在健康端口，签名鉴权）：因子引擎 `/v1/replay/open|step|close`——会话开始时从本地存储取快照窗口
  （运行中不随修正更新，向内存准入器低优先级预留），`step` 用实时计算路径算一期并返回因子帧、源数据列、报价与标的年龄；
  策略 `/v1/replay/bind|evaluate`——固定策略版本与因子绑定，复用实盘求值引擎，无状态（规则状态由回放服务保存），只返回本期决策；
  Trade `/v1/replay/session|advance|periods|close|delete`——纸面账本（`t_replay_*` 三张表：会话、周期记录、订单），
  每期按回放报价估值和撮合（先卖后买，买单受可用现金限制，缺价报错、不回退实时报价），按 `(replay_id, period)` 幂等，不接触实盘账户、订单、预留与执行器。
- **成交价**默认取下一根的开盘价（本期收盘决策、下期开盘成交），`--quote close` 取本期收盘价；时间语义：K 线起点是 `data_time`，决策时刻是 `data_time + 周期`。
- **校验**：本地数据覆盖回放区间，并且包含 `to` 之后的一根；不满足的标的被排除并列出原因。预热起点 = `from − (因子最大回看 − 1 + 策略引用上一根的深度) × 周期`；多数标的的本地数据晚于预热起点时（因子前段会是空值）拒绝建立会话并提示先回补或导入，`--allow-short-warmup` 可放行。
- **各模块的健康密钥可以不同**（因子引擎安装时生成自己的 `health-auth.env`）：回放命令优先读 `MOOX_FACTOR_` / `MOOX_STRATEGY_` / `MOOX_TRADE_` + `HEALTH_AUTH_ACCESS_KEY`、`_SECRET_KEY`、`_VERSION`，没有时用共用的 `MOOX_HEALTH_AUTH_*`。
- **周期记录与恢复**：回放服务自己的 SQLite（`--db`，默认 `./replay.db`）按 `(replay_id, period)` 保存本期决策、下一期策略状态、待发送的 `ReplayAdvance` 与各阶段完成标记
  （Trade 已确认、因子已写回、本期完成）。中断后用同样的参数（或只给 `--replay`）再次 `start` 即续跑：已完成的周期不重做，缺的阶段按记录补齐，
  Trade 未确认就原样重发（同一期重发返回同一条记录）；引擎重启后会话丢失（404）时自动重新建立。续跑时策略或因子定义变了会拒绝。
- `--write-factors` 每期把因子结果写回结果数据集（携带列加因子列，与区间重算相同的写法，不发周期完成事件）。
- 只要历史因子值，导入加区间重算（`--recalc`）比逐期回放快几个数量级；快速比较策略版本用策略研究回放（读取 View，区间受 View 保留根数限制）。

## 10. Manager 内部网关身份与构建

Manager 和 Factor CLI 的 Storage 调用统一使用 `gatewayclient`，覆盖 PrimaryStore 与 Metadata 的 14 个方法。
`config/app.yaml` 的 `gateway_client` 配置 caller `factor-mgr`、Admin 分配的 `key_id` 和签名 `key_file`；
KeyID 与请求体内固定的 `moox-factor` 角色认证独立。主机身份、loopback 地址和 MooX 私有 CA 从部署目录中同级
hostgateway 配置读取，Directory 缓存保存在数据库父目录的 `gatewayclient/directory.json`，权限为 0600。
Manager 持有进程级客户端，CLI 在命令结束时关闭；只读刷新重试和签名由共享层处理，写操作只发送一次。

Manager 与 CLI 共用严格配置加载器，旧 `storage` 配置及 `MOOX_FACTOR_STORAGE_*` 环境覆盖已删除；
未知字段、重复键和额外 YAML 文档会被拒绝。Engine 已通过同一外部 `factor-engine` 身份调用 Access；
Manager 的签名与 Storage 凭据由原生 control 部署分发，外置 Engine 使用第 8 节的独立安装流程。

Factor Manager、CLI 和 Engine 均可关闭 CGO 构建，由本机编译或交叉编译。
实际 `scripts/build/build.sh factor-mgr` 已在本机生成 Linux amd64 的 Manager/CLI 静态程序，并完成相关 Linux 运行验证。
远端 Linux CGO 构建入口仅用于需要 CGO 的 Storage 目标。
