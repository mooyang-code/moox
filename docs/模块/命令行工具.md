# 命令行工具

MooX 的运维入口是 `moox-cli`（`modules/cli`），各模块另有只操作本模块数据的 CLI。

## 1. moox-cli

`moox-cli` 读取 `moox.toml`（主机、云账户、Storage 主机等），负责初始化、部署、数据导入和诊断。
默认部署错误省略目标端私密输出；显式设置 `MOOX_SETUP_DEBUG_HELPER=1` 会附带截断的助手错误、stdout 和 stderr，仅用于联调，输出可能含私密信息。下面列出实际注册的命令，
部署顺序和边界见[部署与运维](../部署与运维.md)。

| 命令 | 作用 |
| --- | --- |
| `setup validate` / `status` / `hosts` / `trust-host` / `trust-browser` | 校验配置与连接、查看初始化状态、列出主机、记录 SSH 指纹、安装管理台证书信任（经 SSH 从控制机取回根证书，输出 `ca_path`、`fingerprint`、`other_machines`） |
| `setup apply` | 写入初始用户与云凭据（主机由 `deploy-host` 登记） |
| `setup init` | 导入默认空间、数据集、字段和因子，注册 `mooxsys` 元数据；控制台使用内部 CA 时先在本机安装根证书信任，并在输出的 `browser_trust`（缓存路径、指纹、换机器的做法）里记录 |
| `setup factors` / `metadata-import` | 导入本地因子；通过 SSH 隧道导入选定业务空间 |
| `setup build-linux` | 在本机 Docker 里构建需要 CGO 的 Linux 二进制（`--module storage` 或 `storage-primary`），产物写到源码目录的 `bin/`；环境准备见[构建手册](../构建手册.md) |
| `setup sync-deployments --host <主机>` | 把 `moox.toml` 里该主机的完整组件部署同步给 Admin（生成网关路由）；服务目录新增了可选组件而主机没有重新部署时使用 |
| `setup host enable\|disable --host <ID>` / `setup deployment enable\|disable --host <ID> --component <组件>` | 启用或停用已登记的主机、组件部署；默认只预览，`--yes` 执行。外部程序先经 SSH 停服务并核对已停止再改登记，停用主机先逐个停掉其上启用的外部程序，恢复主机只启动启用部署的外部程序 |
| `setup bootstrap --stage core/control` | 原生核心初始化 / 完整控制单元部署，保留原始制品、配置与身份 |
| `setup deploy-host` / `deploy-unit` | 原生 host / access、egress-proxy、trade、storage、collector-stream 业务单元部署（collector-stream 的 Storage 应用密钥在本机按 Storage 主密钥派生后注入，主密钥不上海外机）；`factor-engine`、`archive-worker` 是外部程序，软件包随 release 交付，经 SSH 以 systemd 用户服务安装（目标机需开启 linger），主机或部署已停用时只安装文件、不启动 |
| `setup release build` | 构建一个版本的全部单元制品；各部署命令用 `--release <版本>` 升级已安装单元（配置随版本更新） |
| `moox-runtime reseal --unit-root <单元> [--yes]`（目标主机） | 已安装发布被原地换过二进制或改过配置后，把发布文件清单重新封存为现状：不带 `--yes` 只列出新增、变化、删除的路径；`--yes` 在维护锁内改写 `prepared.json`（原清单留在单元根目录 `reseal-backups/`），之后单元工具才接受这个发布 |
| `setup remove-host --host <ID>` | 从 Admin 删除已不在 `moox.toml` 里的主机（下线）：清空业务组件部署与路由、删除主机（其控制台 SSH 登录信息一并失效）；默认只预览，`--yes` 执行，不碰目标机上的进程与文件 |
| `storage node update\|delete` | 修改或删除存储节点登记（管理台只读展示，写操作只在这里） |
| `activity list` | 查看活动日志，支持全局事件（如登录记录） |
| `setup host-diagnostics` / `reboot-host` | 检查主机、重启无响应的云主机 |
| `setup firewall` / `attach-scf-vpc` / `inspect-scf` / `invoke-scf` | 腾讯云防火墙（按拓扑放行所需端口）与 SCF 网络 |
| `setup render-runtime-config` / `export-skill-config` | 渲染 Collector / Trade 运行配置；导出 Skill 使用的数据访问配置 |
| `config init` | 在本机起一个只监听 `127.0.0.1` 的一次性分步表单：验证腾讯云密钥，按公网 IP 识别服务器的地域与规格（只接受当前账号下的服务器），检测因子机环境（局域网里的 Linux 机器，首次 SSH 需确认指纹），确认后生成加密保存的 `moox.toml`（0600，不覆盖已有文件）；填写内容不经过 Agent |
| `config edit` / `config encrypt` | 在本机配置页查看（秘密默认隐藏）和用表单修改常用设置（管理员、腾讯云、告警、服务器 SSH 登录、数据保留期、本地日志；按行写回，注释与其他设置原样保留，不展示配置原文），保存前校验、保存后重新加密；把明文 `moox.toml` 原样加密保存。加密用 AES-256-GCM，密钥在系统钥匙串（没有时为 `~/.config/moox/config.key`），所有命令读取时自动解密 |
| `config migrate` | 在本机解密 `moox.toml` 并改写成当前格式：因子定义改为 `factor_id` + 因子库文件、按角色补中文名 `label`、把旧的 `[placements]` 表改名为 `[deployments]` 并转换已改名的旧组件身份（`cloudnode` → `cloudfunction`）、`--rename-host 旧=新` 改主机 ID；校验通过后才可写回，默认只预览，`--yes` 写回时备份原文件并重新加密。只输出键名、因子 ID、主机 ID 与中文名 |
| `config backup` / `config restore` | 用管理员账号登录管理台（9527），把用管理员密码（Argon2id + AES-256-GCM）加密的整份配置备份到管理后台；换电脑时在本机恢复页登录管理台取回、在本机解开并用新电脑的密钥重新加密（管理台证书不受信任时先核对指纹）。配置页每次保存后自动同步 |
| `config notification` | 对比 `moox.toml` 的 `[notification]` 与 Monitor 的告警渠道（唯一来源）；`--publish --yes` 缺少时添加，`--prune` 才删除控制台添加的其他渠道（先加后删）；同时经 SSH 列出各主机主机策略缓存的版本、来源、拉取时间与渠道数。Webhook 一律脱敏显示 |
| `setup watchdog` | 在各主机安装（`--remove` 移除）每分钟一次的 `moox-runtime watch` crontab 与主机策略种子（`--host` 只处理指定主机）；`setup deploy-host` 部署后自动执行 |
| `collector function package` / `deploy` / `delete` | 构建 SCF 代码包；单节点部署；删除节点 |
| `collector function publish submit` / `status` | 按 fleet 发布 SCF 函数（先向 Admin 申请发布租约） |
| `collector function timer-inventory` / `probe-egress` / `activate-stockcn` | Timer fleet 盘点、出口探测、按门禁启用 A 股采集 |
| `collector subjects sync` | 立即同步标的标签成员（`--space-id`、`--tag-id` 过滤，`--attributes` 同时刷新标的属性）；用于首次部署和接口异常恢复，不等整点；任一标签失败则退出码非零 |
| `collector subjects exclude` / `unexclude` / `exclusions` | 采集名单排除：把标的从采集计划里临时去掉（`--space-id`、`--subjects`、可选 `--market`、必填 `--reason`、可选 `--expires-in`），解除，列出当前生效的排除；下一轮对账生成新计划，交接进行中时等交接完成 |
| `collector ingest-mode get` / `set` | 按数据集查看与切换采集方式（`--mode stream\|pull`、`--executor scf\|local`，`--dataset` 或 `--space-id` 全部数据集）：`get` 显示执行端、交接中的生效周期 P 与 `collector-stream` 状态；`set` 不带 `--yes` 只打印现状，带 `--yes` 保存并打印各数据集选用的 P。切到 stream 或本地执行端要求 `collector-stream` 在线；`--force` 用于旧执行端失联 |
| `collector status` | 查看采集运行状态：总体健康、各数据集的自动巡检进度、实时与历史缺口、补采汇总 |
| `collector kline check` / `backfill` / `backfill-status` / `backfill-cancel` / `backfill-retry` / `history-confirm` / `absences-clear` | K 线缺口检查与补采；查看、取消、重试补采作业；按历史扫描的缺口补采确认；清除数据集已确认的行情源缺失 |
| `archive overview` / `archive tasks list\|prepare\|preview\|create\|update\|delete\|run\|backfill` / `archive runs list\|get\|cancel` / `archive partitions list\|get` | 数据归档：调用 ArchiveMgr 的 14 个方法，输出按 proto 字段名的 JSON；建任务前先 `tasks prepare` 看推荐的执行计划、`tasks preview` 校验 |
| `collector fetch-plan` / `fetch-plan reregister` | 查看采集计划的函数分配与变更进度；Storage 数据被清空后让采集计划重新登记序列快照并重置补采状态（`--yes` 确认） |
| `collector period-inventory` / `task purge` | 只读盘点采集周期状态；清理采集任务（默认只输出清单） |
| `metadata apply` / `import` / `spaces` | 存储元数据 seed |
| `import` | 把历史时序数据文件（CSV 等，必须带数据集的全部字段）导入 Storage 和因子机本地时序存储（`--target storage,factor`，`--allow-missing`、`--recalc`、`--dry-run`）；断点存在 `--job-db`，重跑自动续传。因子机本地写入经因子引擎的本地接口（`--engine`）。独立的 `moox-importer` 只写因子机本地存储。写 Storage 前会按 `moox.toml` 的 `[storage_retention]` 核对：早于「现在 − 保留期」的行写进去会在下一次清理时被删，命令在 stderr 给出警告（文件、行数、最早时间、怎么改）；`setup init` / `setup factors` 会核对因子回看根数与保留期的关联（见[存储](存储.md)） |
| `setup storage-auth` | 经 SSH 从 Storage 主机读取一次 Primary 角色密钥，保存到本机操作员目录 `~/.config/moox/storage-internal-auth.env`（0600，不打印）。`setup init` 读取 Storage 主机时也会顺带保存。此后 `import`、`data rows export`、`collector` 的 Storage 盘点不用再设环境变量或指定 `--storage-auth-file`。解析顺序：环境变量 `MOOX_STORAGE_PRIMARY_AUTH_SECRET` → `--storage-auth-file`（存在时）→ 本机副本。不放进 `moox.toml`：它按设计不含秘密。`MOOX_OPERATOR_DIR` 可改目录 |
| `storage repair-view` / `force-rebuild-view` / `reconcile-view-consumers` / `reset-view-consumers` | View 修复与消费者维护 |
| `data kline get` / `data rows export` | 读取 K 线、导出数据集行 |
| `doctor bootstrap` / `diagnose` / `alerts` / `repair-view-consumers` | 新部署检查；解读 Monitor 的诊断事实；读取 Monitor 的当前告警与不健康的数据集、检查、组件、主机（默认 JSON，退出码 0/1/2/3 表示正常/降级/异常/无法判断，只读）；修复 View 消费者 |
| `ops tencent cls ...` / `ops tencent lighthouse firewall ...` | 腾讯云日志服务、轻量服务器防火墙 |

### 1.0 生命周期与逐期回放

- `moox-cli lifecycle status|check|init|start|confirm|pause|resume|release|catchup [--set <因子集合> | --kind <类型> --id <ID>] --endpoint <模块健康端口>`
  （`pause` 可带 `--reason`、`--pause-kind manual|system`、`--for 2h`（到点自动恢复：先追赶再放行，不能用于系统暂停）；`resume` 先进入恢复追赶，追平后自动放行，`--manual-release` 停在待放行等 `release`，`--pause-kind system` 只恢复系统暂停，`--force` 在模块暂停期间只放行单个对象的追赶；`catchup` 查看追赶进度）：
  查看和推进模块或其对象（因子集合、策略实例）的生命周期；不指定对象时作用于模块自身；`lifecycle shadow --space <空间> --id <实例>` 读 Trade 的影子目标。
  鉴权密钥取自环境变量 `MOOX_HEALTH_AUTH_ACCESS_KEY` / `MOOX_HEALTH_AUTH_SECRET_KEY`。
- `moox-cli lifecycle reset-plan|reset-apply|reset-status|reset-abort --endpoint <模块健康端口>`：单个模块的重置（删除运行数据，`--scope all` 再删业务配置，回到新部署状态）。
  流程：先 `lifecycle pause` 暂停模块 → `reset-plan --scope data|all` 只读查看每一步、保留项、不备份项与阻止条件，拿到 10 分钟内有效、只能用一次的令牌 →
  `reset-apply --scope <同 plan> --token <令牌> --yes` 发起（默认等到结束并逐步打印；`--wait=false` 立即返回）。失败后 `reset-apply --operation-id <ID> --yes` 续做（已完成的步骤跳过），或 `reset-abort --yes` 放弃；重置完成后模块是未初始化，要重新 `init`。
  重置用**重置专用密钥**签名：环境变量 `MOOX_HEALTH_RESET_ACCESS_KEY` / `MOOX_HEALTH_RESET_SECRET_KEY`，模块进程也要配置同一对才开放重置接口；`reset-status` 用普通健康密钥即可。
- `moox-cli system reset plan|apply|status`：系统级重置（实现在 `packages/sysctl`）。`plan --scope data|all --system-name <系统名>` 连接各模块取重置计划，汇总阻止条件（实盘持仓、未停用的 SCF 定时器、进行中的归档运行等），给出 10 分钟内有效、只能用一次的令牌；
  `apply --token <令牌> --confirm-name <系统名> --yes`（生产环境默认，`--env test` 免输系统名）先系统暂停，再按下游到上游逐个重置：策略 → Trade → 因子引擎 → 因子管理 → 采集 → 归档 →（Storage）→ Monitor →（Admin 业务部分）。模块重置前会重新取该模块的计划核对摘要，所以令牌过期不影响后面的模块。
  archive-worker 暂存库、Storage 与 Admin 业务部分要在各自主机上执行：编排器停在那一步并列出命令（停 worker 删暂存库、`storage reset-view-consumers`、`storage reset-metadata`、`moox-admin-cli reset-business`），执行完用 `--external-done archive-worker|storage|admin` 继续；失败或中断后 `apply --operation-id <ID>` 续做，已完成的步骤不重做，不自动回滚。
  各模块地址用 `--strategy/--trade/--factor/--factor-mgr/--collector/--archive/--monitor`（没指定的不参与）；每个模块用重置专用密钥签名：`MOOX_<模块>_HEALTH_RESET_ACCESS_KEY` / `_SECRET_KEY`（没设置时用 `MOOX_HEALTH_RESET_ACCESS_KEY` / `_SECRET_KEY`）。计划与系统日志默认保存在 `~/.moox/system-reset/`（0600）。
- `moox-cli system status|pause|resume [--collector <地址> --factor <地址> --strategy <地址> --trade <地址>]`：系统级暂停与恢复（实现在 `packages/sysctl`，设计见[暂停恢复与重置设计](../计划/暂停恢复与重置设计.md)）。
  `pause [--reason]` 下游到上游逐个暂停（策略 → Trade → 因子引擎 → 采集），每个模块等在途操作结束；
  `resume [--timeout] [--release-partial --yes]` 先追赶后放行：上游追平后才启动下游（采集补采完，因子才同步；因子追平，策略才记录周期；Trade 与交易所对账一开始就做），
  所有模块都追平之后按上游到下游放行（Trade 先于策略）；追赶超时只报告、不自动放行，`--release-partial --yes` 放行已追平的模块；手动暂停的模块不参与；命令幂等，中途断开再执行一次即可。
  各模块地址用 `--collector` 等参数或 `MOOX_<COLLECTOR|FACTOR|STRATEGY|TRADE>_HEALTH_ENDPOINT` 指定，密钥用 `MOOX_<模块>_HEALTH_AUTH_ACCESS_KEY` / `_SECRET_KEY`（缺省取 `MOOX_HEALTH_AUTH_*`）。
- `moox-cli replay start|status|pause|resume|cancel|report|delete`：逐期回放（同一份实现也在 `moox-replay`），详见[因子](因子.md)第 9 节。

### 1.1 K 线查询与网关身份

`data kline get` 及 Collector 金丝雀的 Storage 证明使用 `gatewayclient` 的隧道方式：从 `moox.toml` 取得可信 SSH 主机，查询 control 的本机 Directory，再转发目标主机的 `127.0.0.1:11002`。`--file` 默认 `./moox.toml`，可传绝对路径；目录返回的公网地址不作为连接目标。操作员身份位于 `~/.config/moox/gateway-client.yaml`，配置 `caller: moox-cli`、Admin 分配的 `key_id` 和独立的 `key_file`，配置与密钥均要求普通文件、0600 且禁止符号链接。Admin bootstrap bundle 已生成身份配置；自动取回安装在部署阶段完成。

K 线数据配置只包含 Storage 角色认证与数据类型映射，旧 `gateway` 字段被严格拒绝，须重新导出。网关签名与 Storage 请求角色认证分别校验。命令退出会释放目录刷新、连接池和 SSH 隧道；JSON 结果写 stdout，RPC 诊断写 stderr。

### 1.2 配置变更

`moox.toml` 派生的运行配置（`[storage_retention]`、`[storage_view]`、Collector 与出口代理策略等）在单元安装时渲染进发布目录。
修改后用 `setup release build` 构建新版本，再用对应单元的部署命令加 `--release <版本>` 安装；同一版本的重试绑定原始配置摘要。
缩短保留期会在下一次 Storage 清理时删除超出新保留期的数据，安装前先确认。

### 1.3 按组件边界打包

`setup package` 收集已编译的 Linux 制品和 Git 跟踪的配置模板，输出可复现的 `.tar.gz`。打包不读取 `moox.toml`；运行配置、证书、签名密钥由原生部署层另行注入。产物只包含软件与模板，是 `unitdeploy` 的输入，不能直接当运行目录启动。

| `--profile` | 服务进程 |
| --- | --- |
| `host` | Host Gateway、Host Agent |
| `control` | Console Proxy、Web Host、Admin、EventBus、Monitor、Collector、CloudFunction、FactorMgr、Strategy |
| `storage` | Storage Primary、Storage Node、Storage View |
| `access` | Access |
| `egress-proxy` | Egress Proxy |
| `trade` | Trade |
| `collector-stream` | Collector Stream（WS 推送接收与本地执行端，海外机） |

只有 `host` 包包含 Host Gateway；每个包同时收集本组件需要的管理 CLI、配置模板、schema 和静态资源。Web 前端由已编译的 Web Host 内嵌。编译位置与打包位置独立：纯 Go 制品在本机交叉编译，需要 CGO 的 Linux 制品在本机的 Docker 编译镜像里编译，也可在本机打包。

```bash
# 先构建本机可运行的 moox-cli，并准备 bin/linux-amd64 中的目标制品
./bin/moox-cli setup package --repo-root . --profile host \
  --binary-dir ./bin/linux-amd64 --goarch amd64 --output ./dist/host.tar.gz
./bin/moox-cli setup package inspect ./dist/host.tar.gz

# 脚本入口与 CLI 使用相同的参数；MOOX_CLI 可指定本机 CLI
./scripts/build/package-deployment.sh --profile access \
  --binary-dir ./bin/linux-amd64 --output ./dist/access.tar.gz
make test-deployment-packages
```

支持 Linux amd64/arm64。JSON 结果包含整个归档的 SHA256 和 `package-manifest.json`：记录平台、组件、共享服务目录摘要，以及逐文件的路径、权限、长度和 SHA256。`inspect` 不解压到文件系统，校验平台、组件边界、文件清单与摘要，拒绝链接、越界路径、重复条目、未知字段和多余压缩载荷。摘要用于核对制品一致性，发布来源仍须由部署流程确认。

打包、检查与软件准备共用独立的 [unitpackage](../../modules/cli/internal/setup/unitpackage/README.md)，不依赖旧部署器。远端 `moox-runtime extract` 接收生产端摘要，只按所在 Linux 主机的平台解包；校验成功后原子发布到新目录，已有目标不覆盖。它不切换 current、不注入身份或数据、不启动服务，运行配置、维护锁、激活和回滚由 `unitinstall` 与 `unitbootstrap` 完成。

身份包读取与 SSH 下载共用独立的 [unitbundle](../../modules/cli/internal/setup/unitbundle/README.md)。调用方提供当前拓扑、完整部署、已确认 CA 和期望快照；库校验清单、逐文件摘要、配置、证书/私钥和目标调用方，再发布全新私密目录，并可生成排除操作员身份的服务材料。`moox-runtime inspect-bundle` 复用同一验证，只输出公开清单。[发布准备层](../../modules/cli/internal/setup/unitinstall/README.md) 已接入按组件身份投影、KeyID/Host Agent 配置注入、私密运行计划和七个共用助手包装脚本，并在维护锁下原子发布候选目录。`moox-runtime prepare --request PATH` 读取部署器生成的 0600 规范请求，`inspect-release --directory PATH` 核对尚未启动候选的完整文件清单。`activate`、`recover`、`rollback` 已连接持锁停止、独立状态复制、current 切换、启动验证和失败恢复；持久标记保护安装器退出后的恢复窗口。`seal-state --request PATH` 封存离线状态，绑定新发布和预期旧 current；`activate --state-seed DIR --state-seed-sha256 SHA256` 在停机前及复制后核对摘要，仅导入显式可变目录，旧发布保留独立快照。实际 CLI 的 core、host、业务单元及 control 阶段已接通上述组件，含首次 CA 授权和操作员身份安装；
完整现场迁移、云资源编排与通用升级仍见[实现状态](../实现状态.md)。
