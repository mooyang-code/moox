# 命令行工具

MooX 的运维入口是 `moox-cli`（`modules/cli`），各模块另有只操作本模块数据的 CLI。

## 1. moox-cli

`moox-cli` 读取同一目录里的 `moox.toml`（主机、部署、部署参数）与 `moox.secrets.toml`（加密的初始秘密），负责初始化、部署、数据导入和诊断。下面列出实际注册的命令，
部署顺序和边界见[部署与运维](../部署与运维.md)。

### 约定

- **连接**：所有命令读取 `--file`（默认 `./moox.toml`）。调用管理接口的命令经里面登记的 SSH 配置建立隧道，进目标主机网关的本机入口 `127.0.0.1:11002`，以 `moox-cli` 的身份、用这台电脑的签名私钥（`~/.config/moox/moox-cli.key`）签名调服务目录里的 RPC；`lifecycle`、`system`、`import --target factor` 也一样（调各模块的 `GetLifecycle`、`ControlLifecycle` 与因子引擎的 `EngineControl`，只能出站的主机经 control 中转）。隧道由命令自己建立和释放，不用设置环境变量。健康端口只听本机，`doctor` 要看时经 SSH 在目标机上请求。
- **破坏性命令默认只预览**：删除、重启、改防火墙、切换线上版本、改网关路由、停用或启用线上对象（采集任务、因子任务与成员、策略实例）、暂停系统或采集这类命令不带 `--yes` 只输出将要发出的请求或影响范围（JSON，`preview: true`，退出码 0），确认后加 `--yes` 才执行。
- **修改类命令取回再合并**：服务端的修改接口是整体替换，`space update`、`collector task update`、`metadata dataset|source|field|field-group|view update`、`factor update` 先取回现有对象，只覆盖你给出的字段（只读或创建后不可变的字段不回传），不会把没给的字段清空。
- **退出码与输出**：新增的专用命令标准输出是 JSON，提示写标准错误；响应里 `ret_info.code` 非成功时先打印响应、再以非 0 退出。`gateway call` 同样如此。
- **参数命名**：`--file`、`--space-id`、`--dataset-id`、`--task-id`、`--instance-id`、`--replay-id`、`--frequency`、`--from` / `--to`（RFC3339，左闭右开）、`--seed`（元数据种子）、`--pack`（导入包）。
- **密钥不经过命令输出**：`gateway call` 拒绝返回密钥明文或完整 webhook 的方法（`SecretMgr.GetSecretValue`、`MonitorMgr.ListNotificationChannels`）以及密钥的新建、修改、启停、删除，`gateway methods` 标出；云账户凭证由专用命令在进程内使用，不打印。密钥的新建与修改、登录、交互式终端留在管理台。

### 管理台操作与命令对照

管理台页面上的操作都有对应命令（`TestEveryConsoleMethodHasACommandOrAReason` 逐个核对服务目录里管理台能调用的接口：要么有专用命令，要么在 `rpc_coverage.go` 里写明为什么留在管理台）。

| 无专用命令 | `gateway methods`、`gateway call` |

### 命令清单

| 命令 | 作用 |
| --- | --- |
| `setup validate` / `hosts` / `trust-host` / `trust-browser` | 校验两份配置与连接，只读检测各主机并报告部署情况：`deployment.route` 是 `fresh`（都没装过）或 `installed`（至少一台有 `version.json`）；`deployment.modes` 是可选的部署方式（没装过只有 `install` 新安装，装过时是 `update` 覆盖更新与 `uninstall` 卸载，由用户对整套部署选一个）；`deployment.components` 按主机列出 `moox.toml` 要求的每个组件是否已部署（`version.json` 里有记录或还有单元文件）、是否在运行，`extra` 是已不属于这台主机的组件；`notes` 提醒部分主机没装过（上次安装没做完或新加的主机）或有没有 `version.json` 的残留；`next_steps` 是接下来要运行的命令，`manual_steps` 是要用户在目标机上自己做的事（没开 linger），`warnings` 里有 journald 没持久化和磁盘提醒；`hosts` 列出候选主机；`trust-host` 确认 SSH 主机指纹；`trust-browser` 安装管理台根证书的本机信任 |
| `setup install` | 主线：一条命令装完。不带 `--yes` 只读预检（路线、步骤、`manual_steps`，装过时还有清空范围）；带 `--yes` 按顺序执行：防火墙、控制机先装 Admin 与主机级组件、带 EventBus 与 Storage 的主机、`setup init --stage storage`、控制机其余组件、其余主机（因子机最后）、统一等一次全部就绪、`setup init`、备份配置、`setup start`、`setup verify`。失败后重跑同一条命令，每一步都可以重做（装过的机器不带 `--wipe` 就是接着装完）；带 `--wipe <预检摘要>` 是卸载后重装。装好的系统换版本或改配置用 `setup update`，不重跑 `setup install`（它会再执行一次 `setup start`）。配置模板、元数据种子、云函数代码包、默认因子任务和默认策略都从 `--source-dir`（默认当前目录）取，各步用的是同一个目录 |
| `setup start` | 启动一个空间：启用采集任务、触发计划、导入这个空间的因子任务、创建默认示例策略。任务默认停用，不运行就没有采集。重复运行不重复创建 |
| `setup verify` | 验收一个空间：K 线入库、因子前进、策略运行才算通过，只读。任务全部停用时失败 |
| `setup deploy --host <主机> [--component a,b]` | 把一台主机部署成 `moox.toml` 描述的样子：放二进制（产物包目录里目标机按清单下载组件包，源码目录里用 `--binary-dir`）、取身份材料（控制机执行 `moox-admin-cli bootstrap`，其余主机先同步登记再由控制机导出）、渲染配置与单元文件并应用 `[overrides]`、按启动顺序重启有变化的组件、写 `version.json`，最后等这次装的组件就绪。重跑就是再做一遍。每台主机有一把签名私钥（本机组件共用），例行部署不换，`--rotate-host-key` 显式更换（控制机不支持）；签发了新私钥的这次部署按整台部署处理，`--component` 不起作用 |
| `setup status` / `logs` | 只读：`status` 读各主机的 `version.json` 与每个组件的用户服务状态；`logs` 先读文件日志（`logs/<组件>/`），没有再读 journald（`--journal` 只读 journald，`--grep` 过滤，`--lines` 行数） |
| `setup restart` / `stop` / `start-component` | 重启一个组件；停掉并不再开机自启（`systemctl --user disable --now`，之后的部署保持停用）；恢复（`enable --now`）。默认只预览，`--yes` 才执行 |
| `setup init` 的初始秘密 | 写入初始用户、云凭据、交易所密钥与告警渠道（主机由 `setup deploy` 登记）。`moox.secrets.toml` 的 `[[exchange_keys]]` 写成 category=exchange 的密钥，固定 ID `exchange-<交易所>-<环境>-<名称>`（小写三段，如 `exchange-binance-production-readonly`），passphrase 放进 extra_config，`readonly = true` 时再写 `"readonly":"true"`（Trade 据此拒绝用只读密钥建执行账户）；**只建不改**，已存在的以管理台为准、已在管理台删除的不重建，都不算冲突。管理员、腾讯云密钥、业务空间也一样：库里已有但和秘密文件不一致（例如在管理台改过密码、换过密钥）时以管理台为准、不改写也不报错，结果的 `kept` 列出这些项（`admin`、`tencent_cloud`、`space:<ID>`），`setup status` 同样给出 `kept`。告警渠道只在 Monitor 还没有任何渠道时写入一次。交易所密钥在 Trade 部署之后用 `trade inspect-credential` 检测，检测只有 Trade 里一份实现。Admin 回执的密钥条数和请求对不上时报 `setup_admin_outdated`（Admin 与 CLI 不是同一版，先部署控制机） |
| `setup init` | `--stage storage` 在控制机只装了 Admin、存储机装好之后运行，只写业务空间与初始秘密、导入元数据（数据集建好即为 active，不需要另外激活）；不带 `--stage` 在全部组件装好后完成全部初始化（告警渠道、云账户、日志服务、采集计划要等 Collector、Monitor 起来）。导入默认空间、数据集、字段和因子；云函数代码包从 `--source-dir`（默认当前目录）下的 `modules/collector` 构建，产物包目录里按清单下载预编译的函数程序，元数据种子默认读它下面的 `config/setup`（`--config-dir` 可另指），单独运行时要和 `setup deploy`、`setup start` 指同一个源码目录；管理台用 MooX CA 签的证书，初始化时先在本机安装根证书信任，并在输出的 `browser_trust`（缓存路径、指纹、换机器的做法）里记录 |
| `factor task apply` / `setup metadata-import` | 按因子任务文件（格式同 `config/setup/factor-tasks.yaml`）新建因子定义、因子任务与成员，只建不改：线上已有且内容不同时逐项列出差异、不写入，退出码非 0（打印成员键与列名）；通过 SSH 隧道导入选定业务空间 |
| `setup build-linux` | 在本机 Docker 里构建需要 CGO 的 Linux 二进制（`--module storage` 或 `storage-primary`），产物写到源码目录的 `bin/`；环境准备见[构建手册](../构建手册.md) |
| `setup sync-deployments --host <主机>` | 把 `moox.toml` 里该主机的完整组件部署同步给 Admin（各网关在下一次快照按它算路由）；服务目录新增了可选组件而主机没有重新部署时使用 |
| `setup host enable\|disable --host <ID>` / `setup deployment enable\|disable --host <ID> --component <组件>` | 启用或停用已登记的主机、组件部署；默认只预览，`--yes` 执行。外部程序先经 SSH 停服务并核对已停止再改登记，停用主机先逐个停掉其上启用的外部程序，恢复主机只启动启用部署的外部程序 |
| `setup remove-host --host <ID>` | 从 Admin 删除已不在 `moox.toml` 里的主机（下线）：清空业务组件部署与路由、删除主机（其控制台 SSH 登录信息一并失效）；默认只预览，`--yes` 执行，不碰目标机上的进程与文件 |
| `udf new` / `build` / `publish` / `preview` / `activate` / `list` / `show` | 自定义算子（wasm UDF）：生成 Rust 工作区骨架；本地门禁并打包 `.udfpkg`；上传由服务端复核（要求 git 工作区干净）；用未启用的版本在真实数据上试算；切换启用版本（`--dry-run` 先看影响清单与前提）；查看版本、引用关系与各引擎的模块状态。流程与切换步骤见[因子](因子.md)第 12 节 |
| `activity list` | 查看活动日志，支持全局事件（如登录记录） |
| `gateway methods [关键字]` / `gateway call <服务> <方法>` | 列出内嵌服务目录里 moox-cli 可调用的服务与方法（标出只读 / 写，不连网）；经 SSH 隧道、以 `moox-cli` 的身份调用任意内部方法（JSON，`--data @文件`；`--host` 只调用指定主机上的服务，如 `HostAgentMgr`；业务失败时退出码非 0；拒绝返回密钥明文的方法与密钥写入；写方法不带 `--yes` 只预览），用于没有专用命令的管理接口 |
| `setup host-diagnostics` / `reboot-host` | 检查主机、重启无响应的云主机（`reboot-host` 默认只预览目标实例，`--yes` 才重启） |
| `setup firewall` / `attach-scf-vpc` / `inspect-scf` / `invoke-scf` | 腾讯云防火墙（按拓扑放行所需端口：控制机 9527、11003，存储机与交易所在主机 11003，EventBus 所在主机它的端口；服务端口与健康端口只听本机，不放行）与 SCF 网络；`firewall`、`attach-scf-vpc`、`sync-deployments` 默认只预览，`--yes` 执行 |
| `setup operator` | 准备这台电脑的操作身份：生成 `moox-cli` 的签名私钥（已有就复用）；`--register` 经 SSH 把公钥登记到已经装好的控制机（换电脑，原电脑随即不能用） |
| `setup export-skill-config` | 导出 Skill 使用的数据访问配置；`moox-skill` 的签名私钥在本机生成（`~/.config/moox/moox-skill.key`，反复导出是同一把），公钥登记到控制机（随快照下发到各网关）；入口取默认的外部入口主机（存储机标了 `external_entry` 就用它，否则取第一台标了的），没有主机标 `external_entry` 时报错 |
| `setup register-identity` | 给外部身份（`collector-operator`、`moox-skill`）在 `--key-file` 准备签名私钥并登记公钥；再登记一次就是替换。公钥随快照下发，各网关最多约 5～10 秒后认到，不用再对哪台主机做什么 |
| `config init` | 在本机起一个只监听 `127.0.0.1` 的一次性分步表单：验证腾讯云密钥，按公网 IP 识别服务器的地域与规格（只接受当前账号下的服务器；每台服务器旁有「测试连接」，不需要密码即可探测 IP、端口和防火墙是否通畅），为每台服务器开通免密登录（确认主机指纹，用户输入一次 SSH 密码装上本机的 `~/.ssh/moox_ed25519` 公钥，密码不保存，填错时可以当场改用户名和密码重试；已有可用的密钥直接复用，文件损坏或带口令时先改名备份为 `moox_ed25519.bak-<时间>` 再生成新的），免密后检测因子机环境，告警 Webhook 可以不填、部署后在管理台添加，配了海外服务器时可以再录入交易所密钥（写成 `[[exchange_keys]]`，可以不填；不在本机检测，部署完成后在海外机上检测），确认后生成加密保存的 `moox.toml`（SSH 只记录私钥路径）（0600，不覆盖已有文件）；填写内容不经过 Agent |
| `config edit` / `config encrypt` | 在本机配置页查看（秘密默认隐藏）和用表单修改常用设置（管理员、腾讯云、告警、归档对象存储、服务器 SSH 登录、交易所密钥（整块替换全部 `[[exchange_keys]]`，明文只在点“显示”时按序号取）、数据保留期、本地日志；归档对象存储一组可开关，关闭后保存会删掉整个 `[archive_object_store]` 段；按行写回，注释与其他设置原样保留，不展示配置原文），保存前校验、保存后重新加密；把明文 `moox.toml` 原样加密保存。加密用 AES-256-GCM，密钥在系统钥匙串（没有时为 `~/.config/moox/config.key`），所有命令读取时自动解密 |

### 1.0 生命周期、系统暂停与回放

- `moox-cli lifecycle status|pause|resume|release|catchup [--module <模块>]`：查看和控制一个模块的生命周期。
  - 模块只有运行、暂停、恢复追赶三种状态。
  - `pause` 可带 `--reason`、`--pause-kind manual|system`、`--for 2h`。`--for` 到点自动恢复，先追赶再放行，不能用于系统暂停。
  - `resume` 先进入恢复追赶，追平后自动放行；`--manual-release` 停在待放行，等 `release`；`--pause-kind system` 只恢复系统暂停。
  - `catchup` 先让模块推进一次恢复追赶，再看进度。
  - 默认操作 `factor-engine`，`--module collector|strategy|trade|factor-mgr|archive-mgr` 换模块；经操作员网关（按 `--file` 建隧道）调模块服务的 `GetLifecycle`、`ControlLifecycle`，因子机只能出站时经 control 中转。
  - factor-mgr、archive-mgr 不参与系统暂停：factor-mgr 暂停时拒绝修改类接口，archive-mgr 暂停时跳过定时触发与维护。Monitor 的暂停就是告警屏蔽，用 `moox-cli monitor mute`。
- `moox-cli factor task status [--task-id <因子任务>] [--recheck]`：引擎计算前对因子任务的逐项检查，有不通过项的任务不计算。检查项是窗口载入、数据覆盖、变更同步、回看数量、自定义算子模块，经 FactorMgr `GetStatus` 读取（随心跳上报）；`--recheck` 配合 `--task-id`，经因子引擎 EngineControl `CheckTask` 立即重查。
- `moox-cli strategy instance confirm --instance-id <实例> --session-id <会话>`：确认试运行中的实例转为实盘。
  - 写实例的确认列，挂了账户的实例确认后才下单。
  - 默认只预览，预览里有当前会话号；`--yes` 才执行。
- `moox-cli trade shadow list --instance-id <实例>`：看试运行实例的影子目标，经 TradeConsoleService `ListShadowTargets` 读取。
- 没有重置命令：整体清空用 `moox-cli setup wipe`，只清一个组件的数据是停掉它、删 `<部署根>/data/<组件>` 再启动。
- `moox-cli system status|pause|resume`：系统级暂停与恢复（实现在 `packages/sysctl`，经操作员网关调 collector、factor-engine、strategy、trade 服务的 `GetLifecycle`、`ControlLifecycle`，服务目录里没有部署的模块跳过；
  `pause [--reason]` 下游到上游逐个暂停（策略 → Trade → 因子引擎 → 采集），每个模块等在途操作结束，默认只预览将要暂停的模块，`--yes` 才执行；
  `resume [--timeout] [--release-partial --yes]` 先追赶后放行：采集补采完，因子才同步；策略与 Trade 一开始就进入追赶（策略只记录周期、不发目标，Trade 与交易所对账），
  所有模块都追平之后按上游到下游放行（Trade 先于策略）；追赶超时只报告、不自动放行，`--release-partial --yes` 放行已追平的模块；手动暂停的模块不参与；命令幂等，中途断开再执行一次即可。
  暂停跨过新的 K 线周期时，因子引擎在追赶中补算这些周期，策略在追赶中记下它们的完成事件，两边追平后一起放行，不用等下一根实时 bar。
- `moox-cli strategy replay start`：策略服务里的研究回放，`--input` 选主帧的因子数据来源：`view`（默认，读因子任务结果 View 的历史行）或 `compute`（因子现算：经主机网关调因子引擎按因子机本地 K 线现算，
  声明了 `factor_params` 的策略必须用它，不支持策略池、绑了两个主帧任务的实例与股票市场），`--spot-fee-bps`、`--swap-fee-bps` 是现货与永续的单边手续费，
  `--slippage-bps` 是滑点（0～200 bps，不写为 0：成交价在收盘价上按方向加减这个比例），`--funding-column` 是永续结算资金费的列，详见[策略](策略.md)第 10 节。

### 1.1 K 线查询与网关身份

`data kline get` 使用 `gatewayclient` 的隧道方式：从 `moox.toml` 取得可信 SSH 主机，查询 control 的本机 Directory，再转发目标主机的 `127.0.0.1:11002`。`--file` 默认 `./moox.toml`，可传绝对路径；目录返回的公网地址不作为连接目标。操作员身份是 `~/.config/moox/moox-cli.key`：`moox-cli` 的 ed25519 签名私钥，只在这台电脑上生成（`setup operator`，已有就复用），要求普通文件、0600 且禁止符号链接；控制机只登记它的公钥（首装时由部署控制机的 bootstrap 登记，换电脑用 `setup operator --register`）。同目录下的 `moox-ca.crt` 与 `gateway-bootstrap.json` 是部署控制机时记下的根证书与指纹。

`moox-cli` 的信任根是这台电脑到控制机的 SSH 私钥：能 SSH 上控制机（并且能解开 `moox.secrets.toml`），就能登记一把新的 `moox-cli` 公钥。换操作电脑要带上两份配置文件（或用 `config restore` 加管理员密码取回）、到各主机的 SSH 私钥、解密秘密文件的密钥（钥匙串里的，或 `~/.config/moox/config.key`），然后运行 `setup operator --register`，再 `setup deploy --host <控制机>` 取回根证书；新公钥替换原来登记的那把，两台电脑不能同时用。
秘密文件里的管理员、云密钥、交易所密钥、告警渠道只是初始值，`setup init` 只建不改，之后以管理台为准；管理台里改过或新加的密钥只在线上有，`setup wipe` 之前先在管理台“设置 › 密钥”导出。浏览器要信任的根证书是 MooX CA，全新部署会生成新的 CA，所有设备要重新装一次（`setup trust-browser`）。

Skill 的数据访问配置（`setup export-skill-config` 导出）只有外部入口与 `moox-skill` 身份（`gateway_client`）和数据类型映射，未知字段被严格拒绝；Storage 没有自己的调用方凭据，访问控制由主机网关按服务目录做。命令退出会释放目录刷新、连接池和 SSH 隧道；JSON 结果写 stdout，RPC 诊断写 stderr。

### 1.2 配置变更

`moox.toml` 派生的运行配置（`[storage_retention]`、`[storage_view]`（含 `[storage_view.max_age]` 按频率的 View 最长保留天数）、Collector 与出口代理策略等）在每次部署时渲染到 `<部署根>/config/<组件>/`。
修改后对受影响的主机执行 `setup deploy --host <主机>`：配置变了的组件会重启。个别组件要调的值写在 `[overrides."<组件>"."<配置文件名>"]`，渲染之后逐项覆盖，键路径不存在就报错。
缩短保留期会在下一次 Storage 清理时删除超出新保留期的数据，部署前先确认。

### 1.3 组件包与发布清单

发布时每个组件一个包：`moox-<组件>_<版本>_linux_<架构>.tar.gz`，里面只有 `bin/` 下这个组件的二进制与配套命令行（第三方的内置对象存储另带许可证）。组件到二进制的对应只从服务目录取（`binary` 与 `tools`）。
条目按名字排序、时间戳为 0，同一输入得到逐字节相同的包。`scripts/release/build-release.sh` 用 `moox-cli setup package-components --binary-dir <目录> --output-dir <目录> --version <版本>` 打包，
再由 `scripts/release/write-bundle-manifest.py` 写出产物包清单 `moox-bundle.json`（version 2）：

```json
{"version": 2, "release": "v0.0.2", "commit": "<40 位>", "catalog_sha256": "sha256:<hex>",
 "components": {"collector": {"file": "moox-collector_v0.0.2_linux_amd64.tar.gz", "sha256": "<hex>", "size": 1, "binaries": {"moox-collector": "<hex>", "moox-collector-cli": "<hex>"}}},
 "collector_scf": {"file": "moox-collector-scf_v0.0.2_linux_amd64", "sha256": "<hex>", "size": 1},
 "files": ["<仓库快照里的全部文件>"]}
```

配置模板、单元模板与种子不在组件包里，在产物包的仓库快照里（`moox-bundle_<版本>_linux_amd64.tar.gz`），由 CLI 在部署时渲染。部署时目标机按清单下载这次要装的组件包并校验 SHA256；`catalog_sha256` 和 CLI 内嵌的服务目录不一致时拒绝使用（`bundle_version_mismatch`）。
身份包的读取与校验用 [identitybundle](../../modules/cli/internal/setup/identitybundle/README.md)：调用方提供主机 ID、地址、是否只能出站和已确认的 CA 指纹，库校验清单、逐文件摘要、证书链与 SAN、私钥和登记公钥的配对。
