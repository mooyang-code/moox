# 外部接入（Access）

`moox-access` 是外部调用方（云函数 SCF、因子引擎、Skill）进入 MooX 的唯一入口：签名 tRPC，监听 `11004`，目标身份为
`access@<主机 ID>`。它从[组件目录](共享包.md)读取 `scf-collector`、`factor-engine`、`moox-skill` 三类外部调用方的逐方法白名单，校验
Admin 分配的 caller 与 KeyID、签名和目标身份，用持久化 nonce 拒绝重放，再通过进程级 `gatewayclient` 以内部 `access` 身份把请求
转给目标服务所在主机的[主机网关](主机网关.md)。

代码位置：`modules/access`；客户端在 `packages/gatewayclient`，白名单在 `packages/servicecatalog`。

## 1. 部署与端口

| 端口 | 监听 | 说明 |
| --- | --- | --- |
| `11004` | 公网，tRPC 明文 + 签名 | 外部调用方的入口；外部调用方只携带自己的签名身份 |
| `11014` | 模板为回环；原生安装渲染为 `0.0.0.0` | `/healthz`、`/readyz`、`/metrics`，使用共享健康鉴权的 `MOOX_HEALTH_AUTH_*` |

SCF、因子引擎和 Skill 固定连接一个 Access 实例（`access_address` + `access_id`），不做目录发现。Access 用主机网关目录选择业务服务所在
主机：同机走 loopback 原生 tRPC，跨主机走私有 CA 校验的 TLS tRPC。独立部署 profile 为 `access`。

## 2. 请求处理

1. 校验外部调用方的签名：caller、KeyID、时间戳、nonce、目标身份和请求体摘要；nonce 保存在持久化 SQLite，重启后仍然有效，
   数据库故障时拒绝请求。
2. 按组件目录检查该调用方对「服务 + 方法」的白名单，逐方法超时与请求体上限也来自组件目录；不在白名单里的直接拒绝并计入
   `moox_access_denials_total`。
3. 转发原始 PB/JSON 字节及空间、trace 元数据，丢弃外部提供的用户权限元数据。Storage 请求体内的角色认证（AppID/AppKey）
   独立保留，与 Access 身份无关。

## 3. 外部调用方白名单

白名单只写在组件目录里（`packages/servicecatalog/catalog.yaml` 的 `principals`）：

| 调用方 | 能调用的服务与方法 |
| --- | --- |
| `scf-collector` | `PrimaryStore`：`CommitTimeSeriesBatch`、`UpsertFields`（补采写行） |
| `factor-engine` | `PrimaryStore`：`ReadTimeSeriesRows`、`ReadDatasetChanges`、`WriteFactorRows`、`ReportFactorPeriodComputed`、`GetFactorPeriodComputed`；`Metadata`：`GetDataset`、`ListDatasetColumns`、`ListDatasetSubjects`；`FactorEngine`：`SyncEngineCatalog`、`EngineHeartbeat`、`PullRecalcJob`、`ReportRecalcProgress` |
| `moox-skill` | `PrimaryStore`：`ReadTimeSeriesRows`（只读行情查询） |

新增或修改白名单要改组件目录并重新编译快照，Access 在目录里没有部署的服务上不会就绪。

## 4. 外部调用方怎么连

外部调用方不使用主机网关配置，也不做目录发现，只配置固定的 Access：

```yaml
gateway_client:
  access_address: access.example.test:11004
  access_id: access@storage          # 必须是 access@<主机 ID>
  caller: factor-engine              # scf-collector / factor-engine / moox-skill
  key_id: ""                         # Admin 分配的 KeyID，独立于 caller 名
  key_file: ../secrets/access-factor-engine.key
```

SCF 的 Access 地址和实例身份由部署清单派生：地域匹配先产生公网候选，私网需要在部署中核验实际 VPC、子网及函数绑定后才使用。
因子引擎的 Storage 与 Factor Manager 共用同一个 Access 和同一个外部身份。

### 传输压缩

跨主机调用恒定压缩，没有开关，覆盖经主机网关、经 control 中转、SSH 隧道和经 Access 的调用（含 SCF→Access）；本机回环从不压缩。
压缩算法是 zstd 加训练字典，由共享包 `packages/wirecompress` 实现，系统内部所有传输与编码都用它（浏览器流量与对外文件格式除外）。
请求按 tRPC 帧头的压缩类型压缩，**不设请求体大小门槛**：服务端按请求的压缩类型压缩响应，读接口请求很小、响应很大，小请求也必须标记压缩。
服务端（Access、主机网关）解压后再验签，签名始终覆盖未压缩的原始请求体。解压只接受声明了原始长度的单个 zstd 帧，按帧上限分配缓冲，框架内置的 gzip 等算法一律拒绝。
字典按空间绑定：压缩类型号对应一个字典版本，调用方按请求顶层的 `space_id`（或调用点用 `wirecompress.WithSpace` 指定）选择；没有专用字典的空间用默认字典。
Access 手里只有原始字节，把入站帧的压缩类型沿用到出站一跳，SCF 选的字典全程不变。字典与绑定见 `packages/wirecompress/dicts/registry.yaml`，维护流程见 `docs/计划/统一压缩算法（zstd字典）执行计划.md` 第 6 节。
跨境一跳的背景：2026-10-19 实测海外机出口约 3 Mbit/s，未压缩时整分钟突发约 600KB 排队丢包，压缩后没有重传（见 `docs/计划/网关跨主机连接保活与写重试方案.md` 第 12 节）。

## 5. 配置与密钥

`config/app.yaml`：

```yaml
gateway_client:                      # Access 自己以内部身份调用业务服务
  caller: access
  key_id: ""
  key_file: ../../secrets/caller-access.key
verification_file: ../../secrets/access/access-verification.json   # Admin 导出的外部调用方校验文件
nonce_path: ../../data/access/nonces.db
```

- 主机身份、loopback 地址和私有 CA 来自同一发布根目录下的 `host-gateway/config/app.yaml`，目录缓存在 `data/access/gatewayclient`。
- `verification_file` 由 `moox-admin-cli keys export-access` 导出，包含外部调用方的校验表与带版本的私密密钥；轮换或停用后都必须重新
  部署 Access。配置与密钥均为 `0600` 的普通文件。
- 密钥轮换：`keys rotate` 后新旧 KeyID 同时有效，确认替代密钥生效后用 `keys retire --confirm` 停用旧密钥；每个调用方最多同时
  保留两把有效密钥，旧密钥未停用时拒绝再次轮换。`keys info` 只显示 KeyID 与状态。

## 6. 指标

| 指标 | 含义 |
| --- | --- |
| `moox_access_denials_total` | 按原因累计被拒绝的外部请求（签名、重放、白名单、目标身份等） |
