# 外部接入（Access）

`moox-access` 是外部调用方（云函数 SCF、Skill、采集名单干预工具）进入 MooX 的入口：签名 tRPC，监听 `11004`，目标身份为
`access@<主机 ID>`。它从[组件目录](共享包.md)读取 `scf-collector`、`collector-operator`、`moox-skill` 三个外部身份的逐方法白名单，用它们登记在 Admin 的
ed25519 公钥验签、核对目标身份，用持久化 nonce 拒绝重放，再通过进程级 `gatewayclient` 以 `access` 的身份（所在主机的签名私钥）把请求
转给目标服务所在主机的[主机网关](主机网关.md)。

因子引擎与归档 worker 不再经这里进入：它们是普通组件，用因子机的主机密钥直接连存储机、控制机的主机网关（见[主机网关](主机网关.md)）。

代码位置：`modules/access`；客户端在 `packages/gatewayclient`，白名单在 `packages/servicecatalog`。

## 1. 部署与端口

| 端口 | 监听 | 说明 |
| --- | --- | --- |
| `11004` | 公网，tRPC 明文 + 签名 | 外部调用方的入口；外部调用方只携带自己的签名身份 |
| `11014` | 127.0.0.1 | `/healthz`、`/readyz`、`/metrics`，不验签 |

各外部调用方固定连接一个 Access 实例（`access_address` + `access_id`），不做目录发现。Access 用主机网关目录选择业务服务所在
主机：同机走 loopback 原生 tRPC，跨主机走私有 CA 校验的 TLS tRPC。独立部署 profile 为 `access`。

## 2. 请求处理

1. 校验外部调用方的签名：调用方、时间戳、nonce、目标身份、被调服务与方法、请求体摘要，用这个身份登记的公钥验 ed25519 签名；
   nonce 保存在持久化 SQLite，重启后仍然有效，数据库故障时拒绝请求。验签、重放、白名单不过时返回拒签专用错误码，调用方重新签名重发一次。
2. 按组件目录检查该调用方对「服务 + 方法」的白名单，逐方法超时与请求体上限也来自组件目录；不在白名单里的直接拒绝并计入
   `moox_access_denials_total`。
3. 转发原始 PB/JSON 字节及空间、trace 元数据，丢弃外部提供的用户权限元数据。Storage 只靠服务端口只监听本机加网关访问控制，
   不校验调用方密钥；谁能调用哪些方法只由这份白名单（以及网关访问控制）决定。

## 3. 外部调用方白名单

白名单只写在组件目录里（`packages/servicecatalog/catalog.yaml` 里外部身份列在 `identities`，能调的方法是 `callers` 里写了它的那些）：

| 调用方 | 能调用的服务与方法 |
| --- | --- |
| `scf-collector` | `PrimaryStore`：`CommitTimeSeriesBatch`、`UpsertFields`（补采写行） |
| `collector-operator` | `CollectMgr`：`SetSubjectExclusions`、`ClearSubjectExclusions`、`ListSubjectExclusions`、`SyncSubjects`（采集名单干预的旁路程序，不在部署拓扑里） |
| `moox-skill` | `PrimaryStore`：`ReadTimeSeriesRows`（只读行情查询） |

新增或修改白名单要改组件目录并重新编译快照，Access 在目录里没有部署的服务上不会就绪。

## 4. 外部调用方怎么连

外部调用方不使用主机网关配置，也不做目录发现，只配置固定的 Access：

```yaml
gateway_client:
  access_address: access.example.test:11004
  access_id: access@storage          # 必须是 access@<主机 ID>
  caller: moox-skill                 # scf-collector / collector-operator / moox-skill
  key_file: .moox-skill-keys/moox-skill.key   # 这个身份自己的 ed25519 私钥（base64 的 32 字节种子，0600）
```

SCF 的 Access 地址和实例身份由部署清单派生：地域匹配先产生公网候选，私网需要在部署中核验实际 VPC、子网及函数绑定后才使用。
函数没有配置文件：Collector 发布函数时把 `scf-collector` 的私钥写进环境变量 `MOOX_CALLER_KEY`（`MOOX_CALLER_KEY_ID` 是公钥的十六进制，只用来判断云上函数是不是还带着当前这把密钥）。

### 传输压缩

跨主机调用恒定压缩，没有开关，覆盖经主机网关、经 control 中转、SSH 隧道和经 Access 的调用（含 SCF→Access）；本机回环从不压缩。
压缩算法是 zstd 加训练字典，由共享包 `packages/wirecompress` 实现，系统内部所有传输与编码都用它（浏览器流量与对外文件格式除外）。
请求按 tRPC 帧头的压缩类型压缩，**不设请求体大小门槛**：服务端按请求的压缩类型压缩响应，读接口请求很小、响应很大，小请求也必须标记压缩。
服务端（Access、主机网关）解压后再验签，签名始终覆盖未压缩的原始请求体。解压只接受声明了原始长度的单个 zstd 帧，按帧上限分配缓冲，框架内置的 gzip 等算法一律拒绝。
全系统只用一个默认字典：压缩类型号对应一个字典版本，解码按帧头里的字典 ID 选字典。
Access 手里只有原始字节，把入站帧的压缩类型沿用到出站一跳。字典版本与当前使用的版本见 `packages/wirecompress/dicts/registry.yaml`，维护工具见 `tools/zstddict`。
跨境一跳的背景：2026-10-19 实测海外机出口约 3 Mbit/s，未压缩时整分钟突发约 600KB 排队丢包，压缩后没有重传。

## 5. 配置与密钥

`config/app.yaml`：

```yaml
gateway_client:                      # Access 自己以 access 的身份调用业务服务
  caller: access
  key_file: ../../secrets/host.key   # 所在主机的签名私钥，本机组件共用
  host_id: ""                        # 以下三项由部署渲染
  local_address: 127.0.0.1:11002
  ca_file: ../../secrets/moox-ca.crt
verification_file: ../../secrets/access/access-verification.json   # 外部身份的公钥表
nonce_path: ../../data/access/nonces.db
```

- `verification_file` 是外部身份的公钥表（没有秘密）：部署 access 时由 `moox-cli` 从控制机列出登记的身份公钥后生成。之后有外部身份登记或换了公钥
  （`setup export-skill-config`、`setup register-identity`，或控制机重新签发了 `scf-collector` 的密钥），命令会把新表推到各台 access 并重启它；
  推不到的主机会提示对它重新部署 access（`setup deploy --host <主机> --component access`）。
- 各外部身份的私钥在哪：`scf-collector` 在控制机 `<部署根>/secrets/scf-collector.key`（随控制机的身份包签发）；`moox-skill`、`collector-operator`
  在使用它的电脑上生成。一个身份只有一把公钥，再登记一次就是替换，旧私钥随即不能用，没有新旧并存。
- 外部入口并入主机网关之后（批 4 后续步骤），公钥随网关快照下发，这份公钥表与 access 进程一起去掉。

## 6. 指标

| 指标 | 含义 |
| --- | --- |
| `moox_access_denials_total` | 按原因累计被拒绝的外部请求（签名、重放、白名单、目标身份等） |
