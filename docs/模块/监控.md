# 监控（Monitor）

Monitor 是 MooX 唯一的健康检查与告警模块：探测各服务进程、接收服务指标和主机快照、评估实时
数据集新鲜度和行情健康，生成告警并发送到企业微信或飞书。它是单实例服务，不做跨实例选主。

代码位置：`modules/monitor`。

## 1. 进程与端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| `MonitorMgr` | tRPC `11410` | 管理接口：管理台经控制台 API（`console_name: monitor`）访问 |
| 健康检查 | `11409` | `/healthz`、`/readyz`、`/metrics`，需要 health HMAC |

| 定时器 | 周期 | 作用 |
| --- | --- | --- |
| `check_schedule.timer` | 30 秒 | 执行到期检查，并运行行情金丝雀和业务新鲜度评估 |
| `placement.timer` | 每分钟 | 按 SysDeploy 的部署同步健康检查 |
| `metrics.timer` | 30 秒 | 上报 Monitor 自身指标 |
| `host_silence.timer` | 30 秒 | 检测主机失联，补齐默认主机告警规则 |
| `data_cleanup.timer` | 启动时 + 每 6 小时 | 清理过期检查结果、告警事件、指标去重记录，以及 24 小时未上报的指标序列和服务（改名或下线的服务随之不再告警） |

数据：SQLite `data/monitor/monitor.db`（`schema/monitor.sql`）。服务指标和主机指标的时序历史写入
Storage 的 `mooxsys` 空间，Monitor 的 SQLite 只保存检查、结果、告警和指标目录。

## 2. 检查来源

| 来源 | 内容 |
| --- | --- |
| 部署 | 每条部署对应一个检查 `placement:<主机>:<组件>`，探测方式取自组件目录的 `health.kind`：`readyz` 带 health HMAC 请求健康端口的 `/readyz`（control 上走回环地址）；`https` 请求主机公网地址，2xx 或 3xx 即正常，不校验证书；`none` 不生成检查。部署或主机停用时停用检查，部署删除时连同结果和告警规则一起删除；探测时不依赖 Admin |
| 主机网关 | 读 SysDeploy 的主机列表，每台启用的主机一个检查 `host_gateway:<主机>`：超过 2 分钟没有心跳、从未上报心跳超过 2 分钟、两个网关实例交替上报（冲突），或已应用的路由哈希与期望哈希不一致超过 2 分钟时告警；实例被替换（正常重启）不告警。SysDeploy 读不到时保留上一次的判断 |
| 模块健康 | `packages/report` 注册的各模块健康检查清单 |
| 主机 | HostAgent 主机快照：CPU、内存、磁盘空间、磁盘繁忙度、网络错误包的阈值告警，以及主机失联 |
| 数据集新鲜度 | 按 `config/setup/dataset-health-policy.yaml` 评估实时时序数据集是否按时更新 |
| K 线新鲜度 | 从 Collector 拉取采集任务清单，逐个结果数据集检查最新 K 线是否超时（默认 5 分钟） |
| 行情健康 | Timer 协调是否停滞、容量余量、行情源失败率、标的快照的时效与数量 |
| 行情金丝雀 | 抽取一个流动性好的标的，检查最近闭合 K 线的新鲜度、覆盖率和异常收益 |

管理台「资源与运维 → 监控告警」展示健康概览，不提供检查项的增删改。

## 3. 指标接入

各服务的 `metrics` 定时器把有界的 Prometheus 快照发布到 `MOOX_OBSERVABILITY`，HostAgent 发布主机快照。
Monitor 用固定消费者读取两类事件：

- 服务指标去重后保存最新值，并写入 Storage 数据集 `dataset_mooxsys_service_metrics`（保留 24 小时）。
- 主机快照写入 `dataset_mooxsys_host_resource`、`_filesystem`、`_disk`、`_network` 四个数据集（保留 180 天）。快照带上
  主机 ID（主机采集器的 `MOOX_NODE_ID`），Monitor 据此把主机采集器和 SysDeploy 的主机对应起来；这个对应关系只保存在内存中，
  Monitor 重启后收到下一次快照时恢复。
- 只接受已登记的指标族，原始指标不对用户开放，也不支持自定义规则。
- 上报的服务名是组件 ID、节点是主机 ID；只接受已登记且启用的部署（有启用的 `placement:<主机>:<组件>` 检查）和 SCF 采集
  函数（`scf-collector`）的上报。
- 反向对账：被拒收的上报方在最近 10 分钟内列为「未登记」（只保存在内存中）；组件目录标明应当上报指标、已登记且启用、
  却没有上报记录的部署列为「从未上报」。

Monitor 不抓取服务的 `/metrics`，不依赖 Prometheus Server。`mooxsys` 空间的元数据由
`moox-cli setup init` 注册。

## 4. 告警

- 告警规则绑定检查，状态保存在 `t_monitor_alert_states`，每次触发和恢复记录到 `t_monitor_alert_events`。
- 通知渠道保存在 `t_monitor_notification_channels` 的固定 `global` 行，支持企业微信和飞书。
  Webhook 只返回掩码；清空后仍记录告警状态，只是不再发送。
- 告警文案由 `internal/alerttext` 统一生成，标题写明对象和问题，正文给出当前值和阈值。

## 5. 管理接口

`MonitorMgr`：

| 方法 | 说明 |
| --- | --- |
| `GetHealthOverview` | 健康概览，见第 6 节 |
| `GetNotificationChannel` / `UpdateNotificationChannel` | 通知渠道 |
| `ListHostAgents` / `QueryHostMetricHistory` | 主机列表与资源历史 |
| `GetDoctorContext` | 为诊断聚合服务目录、最新检查、指标、主机和告警事实（有界，最多 2 MiB），不执行恢复动作 |

## 6. 健康概览

`GetHealthOverview` 返回结构化数据，后端给出中文摘要并保留原始错误；状态统一为 `healthy`、`degraded`、`down`、
`unknown`、`disabled`、`unchecked`（不探测）六种，组件名称只取自组件目录。

| 字段 | 内容 |
| --- | --- |
| `summary` | 告警数，以及组件、主机、业务检查、数据集中需关注（降级或故障）、正常、未知的数量；停用和不探测的不计入 |
| `alerts` | 正在触发的告警，**包含主机告警**：级别（主机资源阈值为 `warning`，其余为 `critical`）、告警对象（组件、数据集、主机、业务检查）、所属的数据链路阶段、标题（检查名称）、中文原因、原始错误、触发时间、最近检查时间 |
| `components` | 每条部署一行（来自 SysDeploy；读不到时退回到部署检查，并在 `warnings` 中说明）：状态、原因、探测结果与最近 5 次探测、运行指标上报（实例、版本、最近上报）、当前状态的开始时间。`health.kind` 为 `none` 的组件显示为「不探测」；部署或主机停用时为 `disabled` |
| `pipeline` | 采集、存储与视图、因子、交易四个阶段：阶段状态取该阶段数据集、业务检查和告警中最严重的一个，没有数据时为 `unchecked`；明细是各数据集频率的最新水位、落后时长、最近成功和原因 |
| `business_checks` | 行情采集协调、行情探针、数据投递、账户余额同步 |
| `hosts` | SysDeploy 的每台主机一行：主机网关状态、主机采集器的资源占用和最近上报、主机资源阈值告警；在上报快照却没有登记的主机单独列出 |
| `unregistered` | 最近 10 分钟内被拒收上报的进程（未登记的部署） |
| `notification` | 告警推送渠道及其配置状态 |

## 7. 运维

```bash
./scripts/build/build.sh monitor
./bin/moox-monitor-cli init --db-path ./data/monitor/monitor.db
```

`start.sh` 启动前会用 `moox-monitor-cli` 应用 schema，所以 schema 变更时要同时发布服务和 CLI 两个二进制。
