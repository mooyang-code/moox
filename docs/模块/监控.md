# 监控（Monitor）

Monitor 是 MooX 唯一的健康检查与告警模块：探测各服务进程、接收服务指标和主机快照、评估实时
数据集新鲜度和行情健康，生成告警并发送到企业微信或飞书。它是单实例服务，不做跨实例选主。

代码位置：`modules/monitor`。

## 1. 进程与端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| `MonitorMgr` | loopback tRPC `11410` | 管理接口，经 Admin 管理网关访问 |
| 健康检查 | `11409` | `/healthz`、`/readyz`、`/metrics`；control 主机绑定公网网卡，供 SCF 哨兵用 health HMAC 访问 |

| 定时器 | 周期 | 作用 |
| --- | --- | --- |
| `check_schedule.timer` | 30 秒 | 执行到期检查，并运行行情金丝雀和业务新鲜度评估 |
| `placement.timer` | 每分钟 | 从 Admin SysDeploy v2 同步组件部署检查 |
| `metrics.timer` | 30 秒 | 上报 Monitor 自身指标 |
| `host_silence.timer` | 30 秒 | 检测主机失联，补齐默认主机告警规则 |
| `data_cleanup.timer` | 启动时 + 每 6 小时 | 清理过期检查结果、告警事件、指标去重记录，以及 24 小时未上报的序列和退役上报记录；仍登记的部署保留最后一次上报 |

数据：SQLite `data/monitor/monitor.db`（`schema/monitor.sql`）。服务指标和主机指标的时序历史写入
Storage 的 `mooxsys` 空间，Monitor 的 SQLite 只保存检查、结果、告警和指标目录。

## 2. 检查来源

告警项按"同一问题只告警一次"精简：K 线结果已由「K 线新鲜度」覆盖的数据集，不再重复生成 `dataset:storage` / `dataset:storage_view`
新鲜度检查（上一轮 K 线评估没有成功时保留它们作兜底）；每台主机的网关心跳、实例冲突、路由同步合并成一条 `gateway:<主机>:status`；
主机阈值告警只保留 CPU、内存、磁盘空间（磁盘繁忙度与网络错误包不再告警，指标仍在页面展示）。
CPU 告警取 80%（恢复线 70%）、连续 12 次采样（HostAgent 每 15 秒一次，约 3 分钟）；内存 90%、连续 20 次（约 5 分钟）；磁盘空间 85%、连续 3 次。
CPU 阈值不能放得更高：2026-10-14 回填 1h 因子集时 `storage-node` 吃掉 4 核主机 330%–380% 的 CPU（整机 82%–95%），原来的“90%、连续 5 分钟”一条告警也没出。

| 来源 | 内容 |
| --- | --- |
| 组件部署 | 按组件目录与 SysDeploy v2 的主机、部署生成 `placement:<host>:<component>`，来源为 `placement`；探测时不依赖 Admin |
| 模块健康 | `packages/report` 注册的各模块健康检查清单 |
| 主机 | HostAgent 主机快照：CPU、内存、磁盘空间的阈值告警，以及主机失联（磁盘繁忙度、网络错误包只展示不告警） |
| 数据集新鲜度 | 按 `config/setup/dataset-health-policy.yaml` 评估实时时序数据集是否按时更新；输出水位滞后阈值是 `watermark_periods` × max(周期, 上报的期望间隔)，不低于 `minimum_watermark_lag`，按交易日历上报间隔的数据集（A 股策略实例）跨周末、长假不误报 |
| 数据集检查命名 | 数据集新鲜度检查名为「对象 · 环节」，环节按生产者分为采集、写入存储、结果视图、因子计算、策略结果。对象优先取生产者随期望清单上报的展示名称（`moox_<module>_dataset_info` 的 `name` 标签；策略实例是「定义名称（实例 ID 前 8 位）」，与控制台策略页一致，例如「动量轮动（26d51f7e）· 策略结果」），其次取 Storage 登记的数据集名称，都没有时用「数据集 ID（频率）」。名称改了之后旧名称序列不再上报，Monitor 只认仍在上报、最近上报的那条；名称拿不到不影响检查和告警。告警页标题和推送标题都取这个名称 |
| 数据积累中 | 生产者（因子引擎、策略）把“只因数据还没攒够而不完整”的运行报告为 `partial`（因子：失败的标的都是回看窗口空洞或预热中；策略：因历史不足或上游因子被空洞保护跳过，且在积累期上限之内），并带上 `<module>_dataset_last_partial_timestamp_seconds`。最近一次产出是部分结果、此后没有更新的成功、而且部分结果仍按成功容忍时间内持续出现时，数据集状态是 `degraded`、原因是 `warming`（页面显示“数据积累中，结果暂不完整”），但新鲜度检查按通过记录，**不触发也不延续告警**；部分结果也断了（生产者停了或开始真正失败）就回到原来的 `run stale` / `success stale` 判断。数据重置、新建因子集、重启后的第一期都属于这种情况 |
| K 线新鲜度 | 从 Collector 拉取采集任务清单，逐个结果数据集检查最新 K 线是否超时（默认 5 分钟） |
| 行情健康 | Timer 协调是否停滞、容量余量、行情源失败率、标的快照的时效与数量 |
| 行情金丝雀 | 抽取一个流动性好的标的，检查最近闭合 K 线的新鲜度、覆盖率和异常收益 |

管理台只展示健康摘要，不提供检查项的增删改。

## 3. 指标接入

各服务的 `metrics` 定时器把有界的 Prometheus 快照发布到 `MOOX_OBSERVABILITY`，HostAgent 发布主机快照。
Monitor 用固定消费者读取两类事件：

- 服务指标去重后保存最新值，并写入 Storage 数据集 `dataset_mooxsys_service_metrics`（默认保留 48 小时，来自 Storage 的 mooxsys/30s 策略）。
- 主机快照写入 `dataset_mooxsys_host_resource`、`_filesystem`、`_disk`、`_network` 四个数据集（保留 180 天）。
- 只接受已登记的指标族，原始指标不对用户开放，也不支持自定义规则。

Monitor 不抓取服务的 `/metrics`，不依赖 Prometheus Server。`mooxsys` 空间的元数据由
`moox-cli setup init` 注册。

## 4. 告警

- 告警规则绑定检查，状态保存在 `t_monitor_alert_states`，每次触发和恢复记录到 `t_monitor_alert_events`。
- 通知渠道保存在 `t_monitor_notification_channels` 的固定 `global` 行，支持企业微信和飞书。
  `GetNotificationChannel` 返回推送平台和完整的 Webhook URL，供「消息通知设置」弹窗展示当前配置；Webhook URL
  本身就是推送凭据，控制台把这个读取接口收为仅全局管理员（`modules/admin/internal/console/policy.go`），
  其他登录用户从健康概览只能看到推送平台和是否已配置，也看不到设置入口。清空后仍记录告警状态，只是不再发送。
- **推送地址必须在初始化前配置**：`moox.toml` 的 `[notification]`（`channel_type`、`webhook_url`）在 `setup init` 和部署 Monitor 时必填，
  部署工具把它写进 Monitor 的私有运行环境（`MOOX_NOTIFICATION_*`），Monitor 首次建库时据此写入全局渠道；
  之后用 `UpdateNotificationChannel` 改的值不会被重启覆盖。没有推送地址，监控只展示不通知，等于没有告警。
- 告警文案由 `internal/alerttext` 统一生成，标题写明对象和问题，正文给出当前值和阈值。
- **外部检查有 60 秒宽限**：运行指标上报、采集计划对账、行情探针、数据集与 K 线新鲜度等外部检查每个周期评估一次，
  默认规则要求持续失败满 60 秒才告警（连续失败次数 = 1 + ⌈60 秒 ÷ 检查间隔⌉，30 秒间隔即 3 次），恢复仍是成功 1 次（K 线 2 次）。
  原来失败一次就告警，服务每重启一次就推送一对“新告警 / 已恢复”（2026-10-14～15 两天 122 次告警，大多 29 秒内自愈）。
  HTTP/TCP 部署探测仍是失败 3 次、恢复 2 次，主机阈值规则不变。
- 告警事件的 `c_payload` 记录结构化原因 `{"reason": ...}`，主机阈值告警记录指标值与阈值；概览按它展示告警经过，不解析推送正文。
  主机失联与恢复也写入事件表（`check_id` 为 `host:<agent>:presence`，事件 ID 由主机、目标状态和观察时间决定，重复投递只记一条）。
- 告警分级：服务不可用、数据中断、主机失联、网关异常为 `critical`（严重）；资源超阈值、运行指标上报中断、采集任务清单过期为 `warning`（警告）。

## 7. Storage 调用身份与生命周期

服务指标、主机快照与历史、行情金丝雀、标的标签巡检统一使用进程持有的 `gatewayclient`。配置顶层的 `gateway_client` 声明 `caller: monitor`、Admin 分配的 `key_id` 及 `key_file`；密钥路径相对模块配置文件。主机 ID、本机入口与私有 CA 来自同级 `host-gateway/config/app.yaml`，目录缓存保存在 Monitor 数据库目录的 `gatewayclient/directory.json`。启动时校验身份与私密文件，关闭时先取消后台任务，再释放客户端和数据库。

签名 KeyID 与 Storage 请求的认证身份分开；指标及主机数据请求固定使用 `monitor` 的 Storage 角色认证，行情金丝雀保留自身认证。组件目录只新增 Monitor 对 `PrimaryStore.UpsertFields` 的写权限，其他写方法继续拒绝。只读重试、nonce 与目录刷新由共享客户端控制，业务调用不再叠加 tRPC 重试过滤器或指定目标。`metrics.storage` 和 `metrics.host_storage` 仅保留业务字段，旧目标、节点、KeyID 与 HMAC 文件字段已删除；配置加载拒绝未知字段、重复键和额外 YAML 文档。

Collector 任务清单与 SysDeploy v2 调用复用同一客户端。Monitor 仅调用 `GetCatalog`、`ListHosts`、`ListPlacements` 和 `GetHostRoutes`；校验目录 SHA-256 与当前制品一致，不再调用 v1。旧 SysDeploy v1 协议、表和部署种子已删除。Doctor 的 Monitor 查询与部署查询复用命令持有的 SSH 网关客户端，删除固定 Monitor 目标与环境覆盖。原生 control 部署已注入 Monitor 签名身份与 Storage 角色凭据。

隔离主机指标集成测试使用 `MOOX_MONITOR_E2E_CONFIG` 指向含实际 Monitor 网关身份的模块配置，并保留 `MOOX_SERIES_TAG_E2E=1` 的显式运行开关；完整已部署 Storage 回环测试属于最终候选验收。

## 8. 组件部署检查与 HTTPS 页面检查

`internal/placement` 先校验完整的发现结果，再在一个事务中保存完整部署快照和同步检查。`t_monitor_topology` 保存非敏感的目录、主机、部署及观察时间，包含停用部署和无需探测的组件。启用部署创建或恢复检查；停用主机或部署保留登记、检查及历史，停用探测并移除活动告警；删除部署会删除检查、结果和活动告警。获取失败、无效记录或身份冲突不会部分覆盖快照或检查。`health.kind: none` 不创建检查，探测事实为 `unchecked`（不探测），Reporter 状态独立判断。

`readyz` 使用目录声明的健康端口与响应匹配，并携带 health HMAC。Monitor 自己所在的主机（`placement.local_host_id`，由部署工具按控制主机生成）上的组件直接连 `127.0.0.1`，因为主机没有私网地址时对外地址从本机访问常常不通；其他远端健康端口优先连接主机私网地址；目录标记 `loopback` 的控制组件保持 `127.0.0.1`，因此 console-proxy 始终探测 `127.0.0.1:19528/readyz`。没有 doctor manifest 的旧过滤或部署 `extra_config` 覆盖。

控制台页面另设 `console-page:<host>:console-proxy`，不合并到代理进程健康。`placement.https.console-proxy` 必须显式配置 `url`、`connect_address`、`server_name`、`trust_mode`。URL 的公开 Host 与 SNI 必须一致，连接地址可以是 loopback；2xx/3xx 视为成功，不跟随重定向。`internal` 还必须配置 `ca_file` 与已由部署核验的 `ca_baseline`，探测前校验根证书指纹；路径相对模块配置文件。`public` 使用系统信任，拒绝配置内部 CA。两种模式都校验证书和名称。页面请求不携带内部健康认证。原生 control 部署根据控制主机地址与 TLS 模式生成实际入口配置。

检查结果同时保存中文摘要与 `raw_error`，概览 v2 和前端均已接入。Doctor 读取 v2 部署记录及共享组件目录，保留每台主机的部署，不再按服务名覆盖多机记录，也不依据默认安装配置推测未登记的进程。

## 9. 主机网关状态

每次部署同步对启用的主机读取 `GetHostRoutes`，将非敏感状态和路由收敛时间保存到 `t_monitor_gateway_observations`。概览读取本地观测，不在页面请求时修改状态。每台主机只有一条外部检查 `gateway:<host>:status`，合并评估三项信号：两分钟无心跳、Admin 确认的实例冲突、两分钟未应用期望快照（任一项异常即告警，原因里列出异常项；三项都无法确认时保持原状态）；正常替换实例不触发冲突告警。

路由等待期跨 Monitor 重启保留，读取失败及同一期望快照内再次变化的 applied hash 不重新计时。新期望快照重新开始计时，完全同步后清除等待期。发现失败、没有可靠观测或缓存过期时，无法确认的状态保持“未知”，不会伪造成功结果来恢复既有告警。停用或删除主机后移除活动观测、停用关联检查并移除活动告警，重新启用后恢复检查。当前告警事实已接入存储和评估，并通过概览 v2 与监控告警页展示。

服务和 CLI 必须成对发布。原生安装已有候选状态复制和数据库初始化机制；旧生产 Monitor 运行库的离线重建、通知渠道保留及完整迁移仍需在切换流程中单独验收，不能仅凭新建库就绪确认迁移成功。

## 10. 部署反向对账

概览事实层按完整部署快照与指标目录对账，使用精确的主机 ID 和组件 ID。组件发布方直接使用共享目录中的 ID，SCF 指标使用 `scf-collector`；目录中的外部 principal 不作为主机部署。每条部署独立记录探测结果、原始错误、探测时间、Reporter 状态和实例；探测成功不更新指标上报时间。

已登记且目录要求 Reporter 的部署（`transport: reporter` 且 `functional_observability` 不是 `not_applicable`；不适用的组件没有上报行时不要求上报，与 doctor 的豁免一致），没有上报记录时为 `missing`，超过上报时限为 `stale`；稳定检查身份为 `reporter:<host>:<component>`，首次上报或更换实例不会创建另一条部署检查。停用部署仍保留登记和真实上报事实，但停止对应 Reporter 告警。`none` 不产生未知探测，仍能识别缺失上报。

有近期上报但没有部署记录的进程进入独立的 `Unregistered` 事实集合；过期上报不作为仍在运行的证据。指标入口保留事件与快照校验，允许未登记进程进入目录供对账。首次完整发现之前不推断未登记；成功发现的空部署列表具有权威性，后续发现失败保留旧快照。目录读取有分页和总量上限，超限明确报错。

目录清理保留每条登记部署最后一次上报，清除其多余旧 boot 和退役实例，防止离线部署被误标为“从未上报”；首次发现尚未知时不清除 Reporter 历史。历史入库沿用报告产生时间，不用重投递时间刷新在线状态。结构化概览与页面已在 F4/F5 同批接入。


## 11. 健康概览 v2

`GetHealthOverview` 返回 summary、alerts、components、pipeline、business_checks、hosts、unregistered、notification。名称取自完整部署快照中的组件目录；按明确身份分组，不再按中文名称或 ID 子串归类。对外状态为 healthy、degraded、down、unknown、disabled、unchecked。探测和 Reporter 分开，none 仍可暴露缺失的 Reporter；状态起始时间保存在 `t_monitor_component_health`，由后台采样更新，未观测到的变化不伪造时间。

当前告警包含主机资源阈值、网关信号及 Agent 静默；静默边界为最后上报加三分钟，停用主机/Agent 部署不产生静默告警。选择空间仍保留全局告警。恢复阈值期间，最新检查时间与最近失败原因分别保留，原始错误与中文摘要同时返回。组件详情仅返回探测地址和最近十次结果，不返回认证 Header。

Host Agent `host_id` 显式对应部署主机，Agent ID 继续标识物理采集实例。hostname 仅展示，不用作部署关联；未配置 host_id 的独立 Agent 单独展示。各资源项附可用标志，缺失资源不会作为 0% 展示。原生 host 单元已渲染 host_id；旧运行库切换仍需单独验收，服务/CLI/Host Agent 应按一致版本发布。

概览同时返回：

- 当前告警的 `severity`、`recovering`（最近一次检查已通过、等待确认恢复）和数据集告警对应的数据集事实 `dataset`；告警标题取检查名称，与推送标题一致，没有检查记录（主机阈值、主机失联）时用身份字段拼出。
- `incidents`：最近 48 小时（`incident_window_hours`）的告警经过，同一检查的“触发 → 恢复”归并为一条，带提醒次数与推送失败标记；触发早于窗口的从窗口外最近一次触发补齐，没有恢复记录又不在告警的标为已撤销（`active=false`）。
- 数据集的 `lag_limit_seconds`（输出水位允许落后多久，即告警判定线）、主机的 CPU/内存/磁盘告警阈值、业务检查的检查名称；已停用或移除的业务检查返回 `disabled`，不再显示为正常。

前端页面与 API 为 `web/src/views/ops/monitor/`、`web/src/api/monitor/`，按“值班排障优先”组织：顶部一句话结论（告警 / 需要关注 / 全部正常 / 数据不可用），
其下是当前告警（持续最久的在前，同一分钟内触发的合并为一组并提示可能同因），再是最近 48 小时的告警经过（1 分钟内自愈的闪断默认折叠），
最后是组件、主机、数据链路、业务检查四层健康：组件按主机显示状态点，主机资源条带告警阈值刻度，数据链路与业务检查只列出需要关注的项，可展开全部。
数据集 ID 用存储元数据翻译成名称；后端输出中文摘要，原始错误可展开；刷新失败保留旧数据并标出错误，不显示绿色正常结论。
