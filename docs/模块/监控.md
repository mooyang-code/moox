# 监控（Monitor）

Monitor 是 MooX 的集中健康检查与告警模块：探测各服务进程、接收服务指标和主机快照、评估实时
数据集新鲜度和行情健康，生成告警并推送到通知渠道（企业微信、飞书、钉钉或通用 Webhook）。它是单实例服务，不做跨实例选主；本机守护和 Admin 证书巡检另有独立推送路径（见第 12 节）。

代码位置：`modules/monitor`。

## 1. 进程与端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| `MonitorMgr` | loopback tRPC `11410` | 管理接口，经 Admin 管理网关访问 |
| 健康检查 | `11409` | `/healthz`、`/readyz`、`/metrics`；需 health HMAC。实际监听由 `trpc_go.yaml` 决定：仓库模板为 loopback，原生安装按组件目录渲染为 `0.0.0.0`；防火墙放行情况需在目标环境核实 |

| 定时器 | 周期 | 作用 |
| --- | --- | --- |
| `check_schedule.timer` | 30 秒 | 执行到期检查，并运行行情金丝雀和业务新鲜度评估 |
| `deployment.timer` | 每分钟 | 从 Admin SysDeploy v2 同步组件部署检查 |
| `metrics.timer` | 30 秒 | 上报 Monitor 自身指标 |
| `host_silence.timer` | 30 秒 | 检测主机失联，补齐默认主机告警规则 |
| `data_cleanup.timer` | 启动时 + 每 5 分钟 | 清理过期检查结果、告警事件、指标去重记录、7 天前的数据链路到达记录，24 小时未上报的序列和退役上报记录（仍登记的部署保留最后一次上报），以及失效的自动业务检查（见下） |

失效检查清理：自动生成的业务检查（来源 `observability`、分组 `business`）对应的对象被删除后，检查会一直以“已停用或移除，不再检查”的通过结果留着。
`data_cleanup.timer` 每轮清掉其中两类：持续处于该状态超过 1 小时、且没有未恢复告警的启用检查；停用超过 7 天的检查。清理时一并删除告警规则、
告警状态和检查结果，告警事件按保留期自然过期；每轮最多 100 条，清掉的检查 ID 记在日志 `monitor_stale_checks_pruned`。主机组件检查（来源
`deployment`）和控制台页面检查不清理；对象再次出现时检查按原逻辑重建。规则存在但关闭了 K 线新鲜度监控的检查（页面显示“已关闭”）每轮评估都会被补建，
也不清理：K 线评估器记下这类检查的 ID（`RuleDisabledCheckIDs`），清理时保留；还没成功评估过时保守保留所有 K 线检查。清理与默认规则补齐并发时可能留下检查已不存在的默认规则，同一轮会把存在超过 10 分钟、
没有未恢复告警的这类孤儿规则一并清掉（日志 `monitor_orphan_rules_pruned`）。

数据：SQLite `data/monitor/monitor.db`（`schema/monitor.sql`）。主机指标的时序历史写入 Storage 的 `mooxsys` 空间；
服务指标只保存每个序列的最新值，不写时序历史。Monitor 的 SQLite 保存检查、结果、告警、指标目录、服务指标最新值和数据链路逐根到达记录（见「数据链路到达曲线」）。

## 2. 检查来源

告警项按"同一问题只告警一次"精简：K 线结果已由「K 线新鲜度」覆盖的数据集，不再重复生成 `dataset:storage` / `dataset:storage_view`
新鲜度检查（上一轮 K 线评估没有成功时保留它们作兜底）；每台主机的网关心跳、实例冲突、路由同步合并成一条 `gateway:<主机>:status`；
主机阈值告警只保留 CPU、内存、磁盘空间（磁盘繁忙度与网络错误包不再告警，指标仍在页面展示）。
CPU 告警取 80%（恢复线 70%）、连续 3 次采样；内存 90%、连续 5 次；磁盘空间 85%、连续 3 次。HostAgent 每分钟采样一次（`modules/hostagent/config/trpc_go.yaml`），所以 CPU、内存、磁盘分别约 3、5、3 分钟告警。
CPU 阈值不能放得更高：2026-10-14 回填 1h 因子任务时 `storage-node` 吃掉 4 核主机 330%–380% 的 CPU（整机 82%–95%），原来的“90%、连续 5 分钟”一条告警也没出。

| 来源 | 内容 |
| --- | --- |
| 组件部署 | 按组件目录与 SysDeploy v2 的主机、部署生成 `deployment:<host>:<component>`，来源为 `deployment`；探测时不依赖 Admin |
| 模块健康 | `packages/report` 注册的各模块健康检查清单 |
| 主机 | HostAgent 主机快照：CPU、内存、磁盘空间的阈值告警，以及主机失联（磁盘繁忙度、网络错误包只展示不告警） |
| 数据集新鲜度 | 只检查业务数据集：`mooxsys` 系统监控空间（主机快照）不做新鲜度检查，也不列入数据链路，主机停报由主机失联告警覆盖。按“最新一根 K 线是否按时到达”判断，见下文「数据集新鲜度：最新一根 K 线」；允许迟到按周期分级（`config/setup/dataset-health-policy.yaml`）：分钟级（30s～30m 周期）`minute_lateness` 默认 10 秒，小时级（1h、4h）`hour_lateness` 默认 20 秒，日线及以上 1 个周期；可按数据集用 `overrides[].lateness` 覆盖。生产者上报的最近运行、最近成功时刻另按 `run_missed_intervals`（默认 2）、`success_missed_intervals`（默认 3）个间隔判运行停滞（`run stale`）与成功停滞（`success stale`）；上报的间隔是连续时间，交易所市场（A 股）在此刻没有应收而未到的 K 线时（午休、收盘后、非交易日）跳过这两项，开盘后真停了由等待中的 K 线照常判出（`internal/observability/overview.go` 的 `datasetStatus`）。告警还要连续失败满 60 秒（见「外部检查有 60 秒宽限」） |
| 任务暂停与新鲜度检查 | 生产者的期望清单决定哪些数据集要检查：数据集的 `moox_<module>_dataset_enabled` 为 0 就是“现在不期望它产出”，Monitor 对它的因子计算与写入存储检查不再期望（按「已停用或移除，不再检查」恢复既有告警），同一数据集的结果视图水位也不再检查。因子任务被有意暂停（手动、系统或自动暂停，以及放行前的恢复追赶；故障不算）时，引擎在心跳的 runner 状态里带 `paused`，管理端据此把它的结果数据集标为 enabled=0（管理端重启后第一轮清单里也有这条 0 序列，下游视图检查不会重新告警）；恢复后回到期望清单。系统暂停时所有因子任务都算暂停 |
| 数据集检查命名 | 数据集新鲜度检查名为「对象 · 环节」，环节按生产者分为采集、写入存储、结果视图、因子计算、策略结果。对象优先取生产者随期望清单上报的展示名称（`moox_<module>_dataset_info` 的 `name` 标签；策略实例是「定义名称（实例 ID 前 8 位）」，与控制台策略页一致，例如「动量轮动（26d51f7e）· 策略结果」），其次取 Storage 登记的数据集名称，都没有时用「数据集 ID（频率）」。名称改了之后旧名称序列不再上报，Monitor 只认仍在上报、最近上报的那条；名称拿不到不影响检查和告警。告警页标题和推送标题都取这个名称 |
| 数据积累中 | 生产者（因子引擎、策略）把“只因数据还没攒够而不完整”的运行报告为 `partial`（因子：失败的标的都是预热中的；策略：因历史不足或上游因子被跳过，且在积累期上限之内），并带上 `<module>_dataset_last_partial_timestamp_seconds`。最近一次产出是部分结果、此后没有更新的成功、而且部分结果仍按成功容忍时间内持续出现时，数据集状态是 `degraded`、原因是 `warming`（页面显示“数据积累中，结果暂不完整”），但新鲜度检查按通过记录，**不触发也不延续告警**；部分结果也断了（生产者停了或开始真正失败）就回到原来的 `run stale` / `success stale` 判断。数据重置、新建因子集、重启后的第一期都属于这种情况 |
| K 线新鲜度 | 从 Collector 拉取采集任务清单，逐个结果视图检查：应收的最新一根（按任务声明的交易日历算）之后缺的第一根，从收线起超过允许迟到（健康策略按周期给出的值与采集任务声明的允许迟到中较大的一个，例如加密货币采集任务声明 15 秒，1 分钟线取 15 秒、1 小时线取 20 秒，A 股采集任务默认声明 90 秒，5 分钟线取 90 秒；数据集新鲜度只用健康策略，加密货币 1 分钟线为 10 秒）仍没到就判为停止更新；逾期按 Storage View 摘要快照的时刻算（快照每 30 秒上报一次，半分的评估可能早于那次快照入库，按当前时间算会把准时写完、还没上报的 K 线误判为停止更新；快照超过 1 分钟没有更新时改按当前时间算，停更照样报出），落后标的的逾期时长同样按交易日历和快照时刻计（统一数据集里同一标的有现货、永续两条序列：Storage View 按（标的、`series_tag`）记最新时间，任一序列落后该标的就报落后、写出它最旧的一根，一个市场落后不会被另一个盖住；上报的标的名不带市场标签）。休市、午休、开盘前不需要跳过：应收的最新一根停在上一时段的最后一根。日历未覆盖、市场没有日历、周期对齐未确认时按“无法判断”报出，不推测 |
| 行情健康 | Timer 协调是否停滞、容量余量、行情源失败率（按指标的 `market_id` 分组，每个市场各出一组 `market_fetch:provider_feed:<数据源>` 检查，归在该市场的空间下；只统计窗口（`market_health.feed_failure_rate_window`，默认 5 分钟）内有观测的数据源，没上报过的市场、午休、收市后和周末不出结果，已有的检查按“不再检查”收尾，完全断流由 K 线新鲜度和云函数定时检查发现）。协调失败原因为 `publish_lease_held`（Collector 重启后旧作业仍占着发布租约）时，`market_health.timer_coordination_lease_grace`（默认 10 分钟）内按“协调进行中”处理，超过才判失败；这是告警策略，不是恢复时间的上界。Admin 不可达、无权限等其他租约错误不享受宽限；其余协调失败原因（`cloudfunction`、`environment`、`rules`、`store`、`storage`、`package`、`dataset`、`activity`、`preflight`、`capacity`）各有专属文案，Collector 本地数据库、Storage 等故障不再显示成“CloudFunction 服务调用失败”；只有“被占用”是唯一失败原因时才给宽限（多个 Collector 实例上报不同原因时，真实故障不被盖住），普通 pending 宽限也不能盖过已超期的租约失败。缺少失败起始时间指标时无法证明还在宽限期内，按已超期处理。细节见[采集](采集.md) |
| 推送采集 | `collector-stream` 上报 `moox_collector_stream_heartbeat_timestamp_seconds` 与按数据集的 `moox_collector_stream_failed_period_streak`：心跳中断超过 3 分钟（“collector-stream 心跳已中断”，原因里给出切回 SCF 的命令）、某数据集连续 3 个周期有截止时仍缺的标的（疑似下架不计）时告警。见[采集](采集.md)第 3a 节 |
| 因子连续水位 | factor-mgr 按引擎心跳导出 `moox_factor_task_watermark_blocked_since_timestamp_seconds{space_id,task_id}`（任务的连续水位从何时起阻塞，0 表示没有阻塞）；阻塞超过 30 分钟的任务告警“因子连续水位停滞”，不自动跳过，交给人工手动补采或确认行情源缺失。见[因子](因子.md) |
| 策略参数投递 | strategy 导出 `moox_strategy_param_delivery_stale{space_id,instance_id}`：实例在运行、关联的因子任务有可变成员、连续 `params.stale_alert_periods`（默认 10）期结果都没有把下一期参数送达因子侧时为 1，实例停止后解除；Monitor 的 `factor_params` 检查（名称“策略参数投递”）读它，因子侧不再导出参数相关告警。见[因子](因子.md)第 11 节 |
| 存储截止拒绝 | storage-primary 导出每个数据集最近一次“周期建立前截止已过”拒绝的时刻（`moox_storage_period_deadline_rejected_timestamp_seconds`）：写入方取数晚于数据集截止时整期提交被拒（常见于采集方式切换后截止没跟上），最近 10 分钟内出现过就告警，数据要靠补采补齐 |
| 交易关注项 | Trade 每 30 秒上报 `moox_trade_attention_active{kind,detail}`（指标在上报白名单里）。交易关注项、事件中心与采集关注项、账户余额同步这几类检查与空间无关，归在 `mooxsys` 空间下。值为 1 的种类生成失败的业务检查 `trade_attention:<kind>`，检查名取 Monitor 里的中文名对照（例如 `valuation_degraded` 是“估值降级（有持仓取不到价）”：受管资产已下架、不可交易、交易所确认标的不存在或暂时取价失败，权益按最后已知价或 0 计；`fill_ingest_failed` 是“成交没能记进账本，账户卡在同一笔”：某笔成交入账失败（订单状态不允许、数量超量等），账户保持未就绪，详情带订单号、成交号和原因，失败期间每轮同步刷新，修好后约 5 分钟消失；`flatten_orders_unsettled` 是“清仓结束时有子单没收拾掉，需人工核对”，`release_orders_unverified` 是“释放会话时没能撤单，只按本地记录释放”，`orders_instrument_gone` 是“标的已下架的订单需人工核对成交”，这三项按事件上报，约 5 分钟后自动消失，告警消失不代表已处理：`flatten_orders_unsettled` 的单号在清仓动作结果的 `manual_check_child_order_ids` 和 Trade 日志里；`release_orders_unverified` 的原因在 Trade 日志里，没撤下的单仍在本地订单记录里；`orders_instrument_gone` 的单号在 Trade 日志（搜“交易关注项”）里查；都要人工到交易所核对这些单是否还挂着、成交了多少。`release_orders_stuck` 是“释放会话持续失败，目标单没撤下”：释放策略会话连续失败超过 10 分钟，会话还没释放、策略在重试，释放成功即消失；`clock_skew` 是“本机时钟与交易所相差过大，请检查 NTP”：下单或查询遇到币安 -1021、OKX 50102，按事件上报，校时后约 5 分钟自动消失；`isolated_position` 是“交易所账户里有逐仓持仓，moox 只支持全仓单向”：该持仓不入投影、所在组合已暂停，按事件上报，逐仓持仓平掉后约 5 分钟自动消失），原因是 detail 标签；值回到 0 即恢复。对照表里没有的种类不生成检查，Trade 新增种类要同时登记中文名。种类见[交易](交易.md) |
| 事件中心与下架检测 | 事件中心每 30 秒上报 `moox_callbackdispatcher_attention_active{kind,detail}`，Collector 的下架检测上报 `moox_collector_attention_active{kind,detail}`（两个指标在上报白名单里，Monitor 保留）。值为 1 的种类生成失败的业务检查 `event_center_attention:<kind>`（`execution_failed` 事件通知失败、`delist_detected` 发现标的即将下架、`action_failed` 系统动作处理失败：核对时仍有持有、下架步骤失败或只平了一部分、连续暂时失败超过 15 分钟、取消后的善后没做成、下架后留有零头）和 `collector_attention:<kind>`（`delist_source_failed` 某个下架来源连续 3 次失败，或这一轮返回的条目被校验拒绝、没有发布（可能漏报，具体条目看 Collector 日志，用手工登记补漏）、`delist_readonly_key_missing` 读不到币安只读 Key、`event_outbox_stuck` 事件发件箱最老的事件超过 10 分钟没发布出去或有无效事件被搁置为死信、`eventbus_consumer_failed` 连上 EventBus 后 K 线合成消费者连续 3 次启动失败），原因是 detail 标签；值回到 0 即恢复。种类见[事件中心](事件中心.md)与[采集](采集.md) 7a |
| 行情金丝雀 | `market_canary.subjects` 里每个探针取一个流动性好的标的，按市场时钟（`packages/barclock`，市场默认取空间 ID）找最近已收盘的桶再读 Storage：没有在 barclock 登记的市场在启动校验时拒绝；24 小时市场（crypto）检查最新一根的新鲜度与相邻两根的收盘价波动（`return_threshold`）；交易时段市场（A 股）用内嵌交易日历，检查最近 `closed_bar_count` 根的覆盖率（`closed_bar_min_coverage`）、OHLCV 与来源（`eligible_kline_providers`），周期可以是 barclock 允许的任意周期（如 5m，45m 在启动校验时拒绝）。A 股交易时段内一直检查（收盘不满 `settle_delay` 的桶还不算已收盘）；一个时段的最后一根只在收盘后 `post_close_delay` 起的 `freshness` 内检查，午休、收盘后、开盘前与非交易日空闲（结果正常，`{"state":"idle"}`）；内嵌日历到期前 `calendar_warning_lead` 起报“即将过期”。见 `internal/watchdog/market_canary.go` |
| 内置标签巡检 | 随行情金丝雀定时运行（`market_canary.enabled` 关闭时一并退役），每轮读所有空间的标签，只看内置标签（种子导入的标签，例如 `binance_spot`、`cn_hs300`、`hk_hsi`），与探针配在哪些空间无关。每个标签一个检查 `subject_tag:<空间>:<标签>`，名为「采集对象标签 · 标签名」：同步失败、没有启用的成员、上次同步距今超过 3 个同步周期（周期取 `sync.cron`、`sync.timezone`，没有运行记录的也算）都判为失败。经接口、管理台新建的标签不是内置标签，不巡检。见 `internal/bootstrap/market_canary.go` |

管理台只展示健康摘要，不提供检查项的增删改。

### 数据集新鲜度：最新一根 K 线

- **应收的最新一根 E**：Monitor 按采集任务清单声明的市场日历（`calendar_id`、`timezone`、`sessions`；A 股是 `cn_stock`、`Asia/Shanghai`、
  `09:30-11:30` 与 `13:00-15:00`）算出此刻应已收线的最新一根（`internal/metrics/market_clock.go`）。每个空间取该空间采集任务的日历：
  有交易日历的（A 股）优先，加密货币全天交易，按周期取整（周线按周一、月线按自然月）。非交易日、未开盘、午休时 E 回溯到上一时段
  或上一交易日的最后一根，所以新时段第一根收线前 E 仍指向上一时段的最后一根，不需要“开盘预热”。
- **K 线的 data_time**：输出水位是最新一根 K 线在存储里的 `data_time`（开盘时间），策略结果也上报它所用那根 K 线的开盘时间。
  A 股日内周期按 `packages/barclock` 从每个交易时段开盘起切分，不跨午休，与 Collector 采集、合成的桶一致：1 分钟线 09:30～11:29、13:00～14:59 开盘，
  5 分钟线每个交易日 48 根（09:30～11:25、13:00～14:55 开盘）；不能整除交易时段的周期（如 45m、4h）没有这样的桶，显示“周期对齐未确认”，不判断。
  日线、周线、月线每个交易日（周、月）一根，在最后一个交易日 15:00 收线。交易日历只有一份，内嵌在 `packages/marketcalendar`。
- **延迟 = 到达时间 − 收线时间**：到达时间由生产者在写入时记录（`moox_<module>_dataset_output_arrival_timestamp_seconds`，Storage 视图是
  `moox_storage_view_output_arrival_timestamp_seconds`；因子引擎随运行摘要带上每期的完成时间），在输出水位前进的那一刻定值，之后不随当前时间增长。
  生产者没有上报到达时间时页面不推算延迟。
- **预期 K 线**：概览给出 E 的开盘时间与收线时间（`expected_bar_at`、`expected_bar_close_at`，开盘时间与输出水位同一口径），
  页面在“最新K线”旁单列“预期K线”：两者相同即应收的那根已到，不同就是还在等它。
- **已晚多久与过期判断**：还没到时，“已晚” = 当前时间 − 缺的第一根的收线时间（应到时间），持续增长、用于展示。生产者每 30 秒定时上报一次
  快照（整分与半分对齐，比收线晚几毫秒）；入库、视图、策略计算在输出水位前进时还会立刻补报一份（见「水位前进即补报」），
  因子引擎每算完一期就补发心跳，因子管理服务收到心跳立刻刷新指标并补报（见下文）。Monitor 只能看到上报那一刻的水位，所以判过期看上报：生产者最近一次上报
  （`confirmedAt`，即上报快照的时刻；同一数据集有多个实例时取仍在上报的实例里最早的那次）时，缺的第一根已晚超过允许迟到仍没有，
  才判为过期（`late_confirmed`）并走数据集新鲜度告警。例如 1 分钟线 :00 收线、允许迟到 10 秒，:10 之后那次上报（补报或 :30 的定时上报）仍没有就判过期，最多比“当前时间”口径晚一次上报，
  但不会把还没来得及上报的准时 K 线判成过期。超过 1 分钟（两次上报）没有新上报时不再按上报时刻判断，改按当前时间算
  （`ReportSnapshotGrace`，`internal/metrics/kline_freshness.go`），漏报或停止上报不会让停更一直被当作没逾期。
- **低频视图的上报静默**：Storage 视图只在每个周期的输出提交时刷新水位指标，重启后也要等到下一次提交才重新出现，1 小时视图正常会静默接近一小时。
  通用的“2 分钟无数据即停止上报”不适用于它们：周期不短于 5 分钟的视图容忍一个完整周期再加 5 分钟（1 小时视图 65 分钟），
  分钟级视图仍按 2 分钟判定；真正停止的视图静默超过这个时间，或之后的运行过期判断，仍会发现（`viewReporterStale`，`internal/observability/overview.go`）。
- **页面上的几种状态**（“到达延迟”列，“预期K线”列同色）：
  - 准时到达：显示“延迟 5 秒”，状态正常。
  - 迟到但已到：显示“延迟 40 分钟”并标橙；当前状态正常、告警恢复，这个延迟一直保留到下一根到达后被替换。
  - 还没收到、在允许迟到之内：显示“等待中，已晚 20 秒”，正文色。
  - 已晚超过允许迟到、但还没有上报确认（后端仍判正常）：显示“等待中，已晚 35 秒”并标橙，悬停说明在等生产者下次上报确认。
  - 上报确认迟到（`late_confirmed`）：显示“未到，已晚 N 分钟（缺 n 根）”并标红，状态列写原因“等待中：… 收线的那根已晚 … 仍未到”。
    数据集因别的原因降级（例如数据积累中）不按它标红。数据集还没有任何产出时，“预期K线”列只给出应收的那根，不写“已到”。
- **不推测**：日历覆盖不到当前日期时状态为未知、原因是“日历未覆盖”（会告警，需要更新交易日历）；周期对齐未确认时只在页面显示原因，
  不改变状态。没有交易日历的空间（例如 mooxsys 的主机指标，没有采集任务声明市场）不是行情 K 线，不判断到达延迟，也不提示。
  不再使用“当前时间 − 最新 K 线时间”。

## 3. 指标接入

各服务的 `metrics` 定时器把有界的 Prometheus 快照发布到 `MOOX_OBSERVABILITY`，HostAgent 发布主机快照。
Monitor 用固定消费者读取两类事件：

- 服务指标去重后只在 SQLite 保存每个序列的最新值（`t_monitor_metric_latest`）和目录，不写 Storage：概览、告警和 Doctor 都只用最新值，
  原来写入的服务指标数据集与其视图没有任何读取方，却占用 Storage 写入、View 索引（生产约 440 MB）和 EventBus 存储，
  而且 Storage 写失败会卡住整条服务指标入库。指标入库因此不依赖 Storage，Monitor 的就绪状态也不再检查这个数据集的表结构。
- 主机快照写入 `dataset_mooxsys_host_resource`、`_filesystem`、`_disk`、`_network` 四个数据集（保留 7 天，mooxsys/1m 策略）。
- 只接受已登记的指标族，原始指标不对用户开放，也不支持自定义规则。

Monitor 不抓取服务的 `/metrics`，不依赖 Prometheus Server。`mooxsys` 空间的元数据由
`moox-cli setup init` 注册。

### 新序列限额与入库诊断

指标目录（`t_monitor_metric_series`）会随新标签组合增长；24 小时未上报的序列由清理定时器删除。若上报方持续把标的、请求 ID 之类放进标签，清理前仍可能挤占目录与入库资源，因此入库另有两道保护：

- **新序列限额**：每小时、每天新建的序列数有上限（`metrics.max_new_series_per_hour` 默认 2000、`max_new_series_per_day` 默认 10000；负数表示不限）。
  已有序列照常更新，超出上限的**新序列**样本被丢弃，同一份快照里的其他样本照常入库，消息仍确认、不重投。默认值留足余量：目录约 500 条序列，
  全新启动（清空 Monitor 库）时一小时内要全部建出来，限额只拦标签失控这种成倍增长。
- **丢弃与拒收可见**：`/metrics` 输出
  `moox_monitor_metrics_series_limit_current{window}` / `_max{window}`（近 1 小时、24 小时新增数与上限）、
  `moox_monitor_metrics_series_dropped_total{service}`（被限额丢弃的新序列）、
  `moox_monitor_metrics_samples_filtered_total{service}`（不在健康指标白名单里被丢弃的样本，生产者改了指标名而白名单没跟上时靠它看出来）、
  `moox_monitor_metrics_ingest_total{result,reason}`（`rejected` 按原因分 `checksum`、`limit_exceeded`、`parse`、`space`）。
- **告警**：warning 级检查 `metrics_ingest:series_limit`「指标序列数量保护」——有服务的新序列被丢弃，或近 1 小时 / 24 小时新增数达到上限的 90%，
  文案点名被丢弃最多的服务和它最近一条被丢弃的指标名，恢复后自动解除。
- **Doctor**：`GetDoctorContext` 的 `module_observations` 里多出 `kind=metrics_ingest`、`component_id=monitor` 的诊断项：
  `metrics_ingest_series_dropped`（每个被丢弃的服务：累计丢弃数、最近的指标名）和 `metrics_ingest_snapshot_rejected`（每个服务最近一次被拒的原因、各原因次数）。
  诊断在进程内累计，Monitor 重启后清零。

### 水位前进即补报

30 秒的定时上报不变。Storage primary（写入水位）、Storage View（View 提交水位）和策略服务在注册定时上报时调用
`Handler.FlushOnOutputAdvance()`；`report.DatasetMetrics` 与 Storage View 的水位记录在输出水位前进时调用 `report.NotifyOutputAdvanced()`，
已订阅的处理器 1 秒后补报一份完整快照，1 秒内的多次前进合并成一次（同一时刻写完的多个数据集只补报一份）。补报时定时上报正在进行，
就稍后再补一次，避免漏掉在那份快照之后才前进的水位。Monitor 因此约 1 秒内看到新写完的那根，到达记录也基本做到每根一条。
因子结果的水位来自因子引擎的心跳：引擎每算完一期就唤醒心跳循环立刻补发一次（平时 10 秒一次），因子管理服务每收到一次被接受的心跳
就把运行摘要换算成数据集指标，水位前进同样补报。之前它只在 30 秒定时器里读取心跳，因子这一根约 6 秒算完，Monitor 却要到半分才知道，
页面在这段时间里会显示“等待中，已晚 N 秒”。引擎重启后预热期间到达的那一期（1h 任务是整整一根）结果不正式、不推进水位，
预热完成后由缺口补算补齐，引擎随即把这一期的摘要改为完成，因子管理服务接受同一期的升级，水位前进、补报，
因子环节的“数据积累中”当场消失，到达时间记为补齐的时刻（不再等到下一个整点）。

### 数据链路到达曲线

- **记录**：Monitor 在指标入库的同一个 SQLite 事务里，把每份快照的输出水位（`moox_<module>_dataset_output_watermark_timestamp_seconds`、
  `moox_storage_view_output_watermark_timestamp_seconds`）与入库前已提交的值比较，前进了就为新的最新一根写一行 `t_monitor_bar_arrivals`：
  环节（入库 storage、视图 storage_view、因子 factor、策略 strategy）、空间、数据集（View 为 view_id 并记主数据集）、周期、开盘时间、
  上一份快照的水位、生产者上报的写完时刻。与消息去重同一事务，重复投递不会重复记录、入库失败重试也不会漏记；同一根已有记录时保留最早那条。
  补数据时一批追了几根，只记最新那根（带上一份快照的水位，查询时算出跳过了几根）。采集环节与没有交易日历的 mooxsys 系统数据不记录。
- **存储与保留**：放在 Monitor 的 SQLite 而不是 Storage：Storage 的范围读取走 View，View 每个序列只保留最近 5000 根（1m 约 3.5 天），
  查不到 7 天。一个空间一天约 2 万行，单表按（空间、周期、开盘时间）建索引即可按天查询；`data_cleanup.timer` 删除到达早于 7 天的记录
  （按到达时间而不是开盘时间：周线、月线到达时开盘早已超过 7 天）。
- **系统数据不补报**：mooxsys 的数据集（主机指标）水位前进不触发补报——Monitor 把每份主机快照写进系统指标数据集，水位随之前进，
  再补报就会形成每秒一份快照的循环。
- **查询**：`QueryPipelineArrivalHistory` 按链路（源数据集，即入库的数据集，加周期）和日期返回一天各环节的曲线。日期按市场时区的自然日：
  加密货币 UTC、A 股北京时间（Asia/Shanghai），时间点按收线时间落在这一天内。链路成员：入库是源数据集本身；视图是主数据集为它的 View；
  因子是源数据集在该周期下的因子任务对应的结果数据集（Monitor 向 Storage 列出属性 `dataset_role=factor_result` 且 `source_dataset_id` 为该源数据集的结果数据集，
  一个源数据集可以有多个任务；请求带 `task_id` 时只看该任务，不带且有多个任务时响应列出 `tasks` 让页面选择；没有因子任务的链路没有因子环节）；因子视图是主数据集为
  因子结果的 View；策略的输入在运行时解析、Monitor 拿不到，按同空间同周期列出。每个点给出收线时间、延迟（写完时刻 − 收线时间，按交易日历算收线）
  和跳过的根数（按交易日历数，午休、隔夜、节假日不算）；超出 7 天保留期的日期标出 `retention_truncated`。查询在 SQL 里只读这条链路的成员，
  开盘时间往前多读两个周期（至少一天，覆盖小时线、日线、周线、月线在这一天收线的那根）；超过一次 5 万行的上限时标出 `truncated`。
- **页面**：数据链路卡片右上角“表格 / 曲线”切换（按钮加大、选中为实心主色）。曲线视图选链路和日期（标明时区，可选今天及之前 7 天），
  每个环节一条线，横轴是收线时间（按市场时区标注），纵轴是到达延迟（秒，上限包住允许迟到，至少 0～10 秒），虚线是允许迟到，
  超过的点标红、补数据跳过处标橙；不做动画（页面每 30 秒刷新会重画）。时间范围分“1 小时 / 3 小时 / 全天”三档：分钟级链路默认 1 小时
  （锚点前 45 分钟、后 15 分钟），小时线及以上一天至多 24 根，默认全天。锚点看今天时是当前时间，看历史日期时是当天延迟最大的那一根，
  跨天的部分以当天的界限为准截掉；可前后挪动（1 小时档每步 30 分钟、3 小时档每步 1 小时，锚点不出当天，“回到默认”恢复跟随），
  切换档位时锚点不变。刻度 1 小时档 5 分钟一格、3 小时档 15 分钟、全天 2 小时；只画范围内的点。链路这一天没有记录时也画出空的坐标；
  悬停显示收线时间（带时区）与各环节延迟；下方逐环节汇总全天的根数、中位与最大延迟、超过允许迟到与补数据跳过的根数。
  看的是今天时，页面每次刷新（30 秒轮询或点“刷新”）都重新加载曲线，跨过市场时区的 0 点自动跟到新的一天；看历史日期时不重复查询。

## 4. 告警

- 告警规则绑定检查，状态保存在 `t_monitor_alert_states`，每次触发和恢复记录到 `t_monitor_alert_events`。
- 通知渠道保存在 `t_monitor_notification_channels`，可以有多个（同一个 URL 不能重复），告警发给全部渠道。类型有四种：

  | 类型 | 地址 | 密钥（选填） | 说明 |
  | --- | --- | --- | --- |
  | `wecom` 企业微信 | `qyapi.weixin.qq.com` 的群机器人地址 | 不使用 | markdown 消息 |
  | `feishu` 飞书 | `open.feishu.cn` 等飞书域名的群机器人地址 | 机器人“签名校验”的密钥 | 文本消息 |
  | `dingtalk` 钉钉 | `oapi.dingtalk.com/robot/send?access_token=…` | 机器人“加签”的密钥 | markdown 消息；每条消息的标题和正文开头固定带“MooX”，机器人的安全设置选“自定义关键词”时把关键词设成 `MooX` |
  | `webhook` 通用 Webhook | 任意公网 HTTPS 地址 | 签名密钥 | POST 固定格式的 JSON，返回 2xx 算送达 |

- **飞书**：机器人开了“签名校验”时填它的密钥，请求体会带上秒级时间戳 `timestamp` 与签名 `sign`（以“时间戳 + 换行 + 密钥”为 HMAC-SHA256 的 key、对空内容求摘要再 base64）。飞书要求时间戳与当前时间相差不超过 1 小时，主机时钟偏差过大会验签失败（返回 `code` 19021，记为发送失败）。
  已有的飞书渠道如果事后在飞书里打开了“签名校验”，原渠道立刻发不出去；同一个地址不能重复添加，要先删掉再带密钥重新添加。
  升级时注意：带密钥的飞书渠道要等各主机的 host 单元和 Admin 都换成新版后再添加，旧版会丢掉密钥、不带签名照发，每次都被飞书拒收（只影响这一个渠道）。
- **钉钉**：启用加签时，按钉钉的规则给地址加上 `timestamp` 与 `sign`。钉钉拒收（关键词不符、签名不对、限流）时 HTTP 仍是 200，以返回体的 `errcode` 为准，不为 0 记为发送失败，`errmsg` 写进“推送失败”事件。
- **通用 Webhook**：请求体是 `{"key", "severity", "title", "body", "labels", "sent_at"}`（`severity` 取 `info`、`warning`、`critical`，`sent_at` 是 UTC 时间）。
  没有单独的“触发 / 恢复”字段，从标题和正文里看，和群里收到的内容相同。配了密钥时带两个请求头，与事件中心回调的约定相同：
  `X-MooX-Timestamp`（毫秒时间戳）和 `X-MooX-Signature`（`sha256=` 加上以密钥对“时间戳 + `.` + 请求体”做 HMAC-SHA256 的十六进制）。
  只向公网地址发送：域名解析到内网、回环、保留地址时拒绝（`packages/netguard`），所以局域网里的接收方用不了；不跟随重定向，超时 5 秒。
- **密钥只写不读**：添加渠道时提交，`ListNotificationChannels` 只返回是否设置（`has_secret`）；要改密钥就删掉渠道重加。密钥随主机策略下发到各主机（见第 12 节），主机守护和证书巡检的直推同样带签名。
  「消息通知设置」弹窗列出全部渠道（平台与完整 Webhook URL），可以添加、删除（`ListNotificationChannels` / `AddNotificationChannel` /
  `DeleteNotificationChannel`）。Webhook URL 本身就是推送凭据：列出渠道只允许全局管理员（`modules/admin/internal/console/policy.go`），
  增删是 monitor 的写方法，本来就只允许全局管理员；其他登录用户从健康概览只能看到渠道数量和平台，也看不到设置入口。
  全部删除后仍记录告警状态，只是不再发送。
- **送达规则**：至少一个渠道送达就算送达，失败的渠道记一条“推送失败”事件（写平台、域名和 URL 末 4 位），不按未送达重试，
  免得已收到的群每次重试都重复收到；全部渠道失败才按未送达在下一次评估重试（`internal/notifier`）。
- **推送地址可以稍后配置**：`moox.toml` 的 `[notification]`（`channel_type`、`webhook_url`、`secret`）里的 `webhook_url` 可以留空，
  填了的话部署工具把它写进 Monitor 的私有运行环境（`MOOX_NOTIFICATION_*`），Monitor **只在首次建库时**据此写入第一个渠道；
  没填就不写，部署后在监控页添加。渠道在监控页增删，删光了重启也不会自动加回来。没有推送渠道时监控只展示不通知，所以要提醒用户尽快补上。
- 告警文案由 `internal/alerttext` 统一生成，标题写明对象和问题，正文给出当前值和阈值。
- **外部检查有 60 秒宽限**：运行指标上报、采集计划对账、行情探针、数据集与 K 线新鲜度等外部检查每个周期评估一次，
  默认规则要求持续失败满 60 秒才告警（连续失败次数 = 1 + ⌈60 秒 ÷ 检查间隔⌉，30 秒间隔即 3 次），恢复仍是成功 1 次（K 线 2 次）。
  原来失败一次就告警，服务每重启一次就推送一对“新告警 / 已恢复”（2026-10-14～15 两天 122 次告警，大多 29 秒内自愈）。
  HTTP/TCP 部署探测仍是失败 3 次、恢复 2 次，主机阈值规则不变。
- 告警事件的 `c_payload` 记录结构化原因 `{"reason": ...}`，主机阈值告警记录指标值与阈值；概览按它展示告警经过，不解析推送正文。
- **CPU、内存告警附带进程占用**：HostAgent 随主机快照上报占用最高的进程（见[主机代理](主机代理.md)）。CPU、内存阈值告警触发和重复提醒时，推送正文多一行“占用最高（进程 CPU 按单核计）：storage-node CPU 340%、内存 5.1 GB；…”（CPU 告警按 CPU 排前 3，内存告警按内存排前 3），
  事件的 `c_payload` 里另存完整排行 `top_processes`（最多 10 个），进程事后退出或被杀掉仍能查到当时是谁占的。恢复通知和磁盘空间告警不带。主机监控详情页显示最新一次采样的排行。
  排行只保留最新一次，不能回看历史时刻；CPU 是一分钟平均，短于一分钟的尖峰会被摊平；同名的多个进程（例如几个 python）在正文里分不开，事件的完整排行里每项带 `pid`。整机使用率是全部核的百分比，进程的 CPU 按单核计，所以正文里会出现“整机 91%、某进程 340%”。
  进程名来自可执行文件名，脚本类进程只显示解释器的名字（python3.12、node），看不出跑的是哪个脚本。
  主机失联与恢复也写入事件表（`check_id` 为 `host:<agent>:presence`，事件 ID 由主机、目标状态和观察时间决定，重复投递只记一条）。
- 告警分级：服务不可用、数据中断、主机失联、网关异常为 `critical`（严重）；资源超阈值、运行指标上报中断、采集任务清单过期，以及只需提醒的关注项（目前是 `collector_attention:delist_readonly_key_missing`，业务检查显示 degraded“需关注”）为 `warning`（警告）；`moox-cli setup verify` 只把 critical 当成故障。

- **告警屏蔽**（`moox-cli monitor mute --for 3h --reason 初始数据导入`、`unmute`、`mute-status`）：给初始数据导入等会让数据链路告警暂时失真的操作用。
  屏蔽就是 Monitor 模块的生命周期暂停（`rpc/mute.go` 的 `MuteAlerts` 带 `ExpiresAt` 调生命周期，到期自动恢复），期间探测、入库、告警评估与记录、首页聚合照常，
  只是发送器返回 nil、不推送（`bootstrap/lifecycle.go` 的 `alertSender`，告警评估、主机指标告警、主机失联三处共用）。一次最长 24 小时，已在屏蔽中不能重复设置；
  系统暂停等别的暂停不算屏蔽，也不能被 `unmute` 解除。**静默结束时（到期、`unmute`、系统恢复）补发一条汇总**（`bootstrap/mute_summary.go`）：
  仍未恢复的告警逐条列出（含屏蔽前就在触发的），期间触发后又恢复的按检查项列出次数与时间范围，什么都没发生就不发。
  没有走 Monitor 的直推告警（主机守护 `moox-runtime watch`、Admin 证书巡检）不受屏蔽影响。

## 4a. 重要日志

不登机器就能看到各服务的错误。

- **哪些算重要日志**：Error 及以上级别的全部日志；以及代码里用 `logsink.Important` / `logsink.Audit` 写出的关键事件，目前是两类：
  进程启动（`process_started`，带版本和启动号）、生命周期审计（`lifecycle_pause`、`lifecycle_resume`、`lifecycle_reset_*` 等，含告警屏蔽）。
  Info、Warn 不进库，在本机文件里（启用了 CLS 上报时，Warn 也在 CLS 里）。
- **怎么到 Monitor**：各服务的 tRPC 日志多了一个输出 `moox`（`packages/report/logsink`），和配置里的 `file` 输出并存。它由代码加上，**不写在 `trpc_go.yaml` 里**：
  服务的 `main` 空白引入 `packages/clsreporter/logcls`，进程按配置装配默认日志时就自动带上这一项。线上的配置文件不随二进制更新，靠配置开启的话，换二进制不改配置不生效，
  改了配置再回滚二进制又会因为旧版不认识这个输出而起不来；所以配置文件里不能出现 `writer: moox`（契约脚本会检查）。
  重要日志先进一个最多 256 条的内存队列，后台每秒（或满 50 条）发一个事件 `event.observability.log.reported` 到 `MOOX_OBSERVABILITY`，
  用指标上报的同一份地址和凭据（`metrics-publisher` 账号），但另开一条连接。Monitor 消费后写进 `t_monitor_log_records`。
  Monitor 自己的日志不绕 EventBus，直接批量写库。写日志的调用只做一次不阻塞的入队；队列满了就丢并计数。
- **同一处反复报错**：同一个代码位置每分钟最多进库 10 条，多出来的只计数，下一分钟的第一条带上“此前另有 N 条被合并”。循环报错时库不会被刷满，完整记录在 CLS 和本机文件里。
- **去重与保留**：记录号是“实例 | 启动号 | 序号”，重复投递只留一条（必须带启动号，进程重启后序号从头开始）。`data_cleanup.timer` 删除 30 天前的记录，总行数超过 20 万时从最旧的删起。
  时间戳偏离入库时间超过 24 小时的记录按入库时间保存。
- **在哪看**：管理台“运维 › 重要日志”；`moox-cli monitor logs --component storage-node --level error --from 2026-11-12T00:00:00+08:00`。带关键字又没有给起点时只查最近 7 天（关键字要逐行匹配，不走索引）。
  页面按时间范围查（最近 24 小时、7 天、30 天），列表上方是按时间的条数分布（错误与关键事件分开计），点一根柱子只看那段时间；日志详情里可以直接看同一主机上这个组件前后 5 分钟的记录（不带级别和关键字筛选）。
  分布由 `QueryLogRecords` 的 `with_buckets` 一并返回（按小时统计，没有给起点时只统计最近 7 天）。
- **接入范围**：创建了指标上报（`report.NewHandler`）并使用 tRPC 日志的服务：admin、archive-mgr、callback-dispatcher、cloudfunction、collector、collector-stream、eventbus、factor-mgr、monitor、storage 的三个进程、strategy、trade。
- **CLS 上报**（可选）：`moox.toml` 的 `[logging.cls]` 启用后，上述服务把不低于 `min_level`（默认 `warn`）的日志和全部关键事件另外上报到 CLS 的主题 `moox-service`（后台每 2 秒或满 500 条一批，失败丢弃不重试）。
  默认不上报 Info：Storage 等服务逐条处理的 Info 日志量是其余日志的十倍左右。日志保留天数取 `[logging] retention_days`（默认 2）。费用见部署文档，每个主题每月约 1 元多。
  部署时写进各组件运行环境的是 `MOOX_LOG_CLS_*`，和云函数采集日志用的 `MOOX_CLS_*` 分开。配置步骤见[部署与运维](../部署与运维.md)。
- **进程里能看到的计数**（各服务自己的 `/metrics`）：`moox_logsink_records_total{path}`、`moox_logsink_dropped_total{path,reason}`、`moox_logsink_merged_total`；
  Monitor 另有 `moox_monitor_log_records_total{result}`（`stored`、`duplicate`、`failed`）。

已知的限制：

- **没有覆盖的进程**：主机网关、Access、出口代理、控制台代理、HostAgent、导入工具、factor-engine、archive-worker、Python 因子引擎、QMT 执行端、云函数。它们的日志仍在本机（云函数仍上报 `moox-application`）。
- **标准输出里的内容不上报**：崩溃信息（panic）、数据库（GORM）语句日志只在 `<部署根>/run/logs/<组件>.log`。
- **启动很早就失败的错误不进库**：服务在创建指标上报之前就退出时，重要日志还没有接收方，这些错误只在本机文件里。创建之后的失败走 `Fatalf`，退出前会先把队列发出去。
- **可能丢**：EventBus 不通时这一批直接丢弃、不重试；Monitor 自己的日志直接写库，最多等 30 秒（刚启动时数据库连接被启动查询占着），仍写不进去才丢弃；进程崩溃前最后一两秒的日志可能来不及发出。以本机文件为准。
- **不根据错误日志告警**：重要日志只用于查看，服务是否健康仍由现有的检查判断。
- **部署变更没有做成关键事件**：Monitor 的部署同步每分钟都会记一条“更新了 N 项检查”，分不出真正的变更，没有接入。
- **CLS 上报是明文 HTTP**（腾讯云 SDK 写死，云函数现在也是这样）：日志里不要写密钥和完整的 Webhook 地址。
- **Storage 的日志换了位置**：原来写标准输出（`run/logs/storage-*.log`），现在和别的服务一样写 `<发布目录>/<组件>/logs/trpc.log`（只留 10MB×5，突发时这个文件输出会丢）。

## 6. 运维

```bash
./scripts/build/build.sh monitor
./bin/moox-monitor-cli init --db-path ./data/monitor/monitor.db
```

Monitor 服务在 `internal/bootstrap/bootstrap.go` 启动时直接应用内嵌 schema；`moox-monitor-cli init` 是可单独执行的离线入口，当前启动链不依赖 `start.sh`。schema 变更时仍应同时发布服务和 CLI，避免两个入口使用不同的 schema。


### 已有环境升级到按市场通用的版本

- 配置是严格解析的，换二进制前先备份线上 `app.yaml`，再从里面 `app.yaml` 删掉 `market_health` 下的 `instrument_snapshot_max_age`、`instrument_minimum_count`、`instrument_required_exchanges` 三项，否则新二进制启动失败；同时删掉 `kline_freshness.space_ids`，K 线新鲜度才会按 barclock 登记的全部市场检查。
- 余额对账（`balance:*`）和关注项（`trade_attention:*`、`event_center_attention:*`、`collector_attention:*`）改归 `mooxsys` 空间，检查 ID 不变，默认告警规则自动生成。在旧检查上调过的告警规则要在 `mooxsys` 下重设。静音是全局的时间窗，不用重设。
    - 升级后：旧 `crypto` 空间下的同名检查每轮记一条“已停用或移除，不再检查”的通过结果，不会告警，原来未恢复的告警随之恢复；余额对账的旧检查在概览里显示为已停用。约 1 小时后数据清理定时器把这些旧检查连同规则、结果一起删掉，不用手工处理。
    - 回滚到旧二进制：`crypto` 空间下的检查会自动重建；`mooxsys` 下的关注项检查同样自动收尾并清理。但 `mooxsys` 下的余额对账检查（`balance:*`）旧二进制处理不了，会连续记失败并告警，而且消不掉。回滚时要在启动旧二进制之前手工停用：`sqlite3 monitor.db "UPDATE t_monitor_checks SET c_enabled = 0 WHERE c_space_id = 'mooxsys' AND c_check_id LIKE 'balance:%';"`，停用的检查 7 天后自动删除。
- 数据源健康按指标的 `market_id` 分组。新市场的云函数上线前，Collector 的指标市场白名单要先包含这个市场，否则它的数据源结果记不到自己的市场下，这里也就没有它的检查。

## 7. Storage 调用身份与生命周期

主机快照与历史、数据集元数据（有效标的、展示名称）、行情金丝雀、标的标签巡检（成员统计读 Storage；同步的上次运行时间、结果与错误读 Collector 的 `ListTagSyncStatus`，没有运行记录的按“同步过期”，周期取标签属性 `sync.cron`、`sync.timezone`）统一使用进程持有的 `gatewayclient`。配置顶层的 `gateway_client` 声明 `caller: monitor`、Admin 分配的 `key_id` 及 `key_file`；密钥路径相对模块配置文件。主机 ID、本机入口与私有 CA 来自同级 `host-gateway/config/app.yaml`，目录缓存保存在 Monitor 数据库目录的 `gatewayclient/directory.json`。启动时校验身份与私密文件，关闭时先取消后台任务，再释放客户端和数据库。

签名 KeyID 与 Storage 请求的认证身份分开；指标及主机数据请求固定使用 `monitor` 的 Storage 角色认证，行情金丝雀保留自身认证。组件目录只新增 Monitor 对 `PrimaryStore.UpsertFields` 的写权限，其他写方法继续拒绝。只读重试、nonce 与目录刷新由共享客户端控制，业务调用不再叠加 tRPC 重试过滤器或指定目标。`metrics.host_storage` 仅保留业务字段，旧目标、节点、KeyID 与 HMAC 文件字段已删除；服务指标不写 Storage，`metrics.storage` 整段已删除，配置里留着这一段会被拒绝启动；配置加载拒绝未知字段、重复键和额外 YAML 文档。

Collector 任务清单与 SysDeploy v2 调用复用同一客户端。Monitor 仅调用 `GetCatalog`、`ListHosts`、`ListDeployments` 和 `GetHostRoutes`；校验目录 SHA-256 与当前制品一致，不再调用 v1。旧 SysDeploy v1 协议、表和部署种子已删除。Doctor 的 Monitor 查询与部署查询复用命令持有的 SSH 网关客户端，删除固定 Monitor 目标与环境覆盖。原生 control 部署已注入 Monitor 签名身份与 Storage 角色凭据。

隔离主机指标集成测试使用 `MOOX_MONITOR_E2E_CONFIG` 指向含实际 Monitor 网关身份的模块配置，并保留 `MOOX_SERIES_TAG_E2E=1` 的显式运行开关；完整已部署 Storage 回环测试属于最终候选验收。

## 8. 组件部署检查与 HTTPS 页面检查

`internal/deployment` 先校验完整的发现结果，再在一个事务中保存完整部署快照和同步检查。`t_monitor_topology` 保存非敏感的目录、主机、部署及观察时间，包含停用部署和无需探测的组件。启用部署创建或恢复检查；停用主机或部署保留登记、检查及历史，停用探测并移除活动告警；删除部署会删除检查、结果和活动告警。获取失败、无效记录或身份冲突不会部分覆盖快照或检查。`health.kind: none` 不创建检查，探测事实为 `unchecked`（不探测），Reporter 状态独立判断。

`readyz` 使用目录声明的健康端口与响应匹配，并携带 health HMAC。Monitor 自己所在的主机（`deployment.local_host_id`，由部署工具按控制主机生成）上的组件直接连 `127.0.0.1`，因为主机没有私网地址时对外地址从本机访问常常不通；其他远端健康端口优先连接主机私网地址；目录标记 `loopback` 的控制组件保持 `127.0.0.1`，因此 console-proxy 始终探测 `127.0.0.1:19528/readyz`。没有 doctor manifest 的旧过滤或部署 `extra_config` 覆盖。

控制台页面另设 `console-page:<host>:console-proxy`，不合并到代理进程健康。`deployment.https.console-proxy` 必须显式配置 `url`、`connect_address`、`server_name`、`trust_mode`。URL 的公开 Host 与 SNI 必须一致，连接地址可以是 loopback；2xx/3xx 视为成功，不跟随重定向。`internal` 还必须配置 `ca_file` 与已由部署核验的 `ca_baseline`，探测前校验根证书指纹；路径相对模块配置文件。`public` 使用系统信任，拒绝配置内部 CA。两种模式都校验证书和名称。页面请求不携带内部健康认证。原生 control 部署根据控制主机地址与 TLS 模式生成实际入口配置。

检查结果同时保存中文摘要与 `raw_error`，概览 v2 和前端均已接入。Doctor 读取 v2 部署记录及共享组件目录，保留每台主机的部署，不再按服务名覆盖多机记录，也不依据默认安装配置推测未登记的进程。

## 9. 主机网关状态

每次部署同步对启用的主机读取 `GetHostRoutes`，将非敏感状态和路由收敛时间保存到 `t_monitor_gateway_observations`。概览读取本地观测，不在页面请求时修改状态。每台主机只有一条外部检查 `gateway:<host>:status`，合并评估三项信号：两分钟无心跳、Admin 确认的实例冲突、两分钟未应用期望快照（任一项异常即告警，原因里列出异常项；三项都无法确认时保持原状态）；正常替换实例不触发冲突告警。

路由等待期跨 Monitor 重启保留，读取失败及同一期望快照内再次变化的 applied hash 不重新计时。新期望快照重新开始计时，完全同步后清除等待期。发现失败、没有可靠观测或缓存过期时，无法确认的状态保持“未知”，不会伪造成功结果来恢复既有告警。停用或删除主机后移除活动观测、停用关联检查并移除活动告警，重新启用后恢复检查。当前告警事实已接入存储和评估，并通过概览 v2 与监控告警页展示。

服务和 CLI 必须成对发布。原生安装已有候选状态复制和数据库初始化机制；旧生产 Monitor 运行库的离线重建、通知渠道保留及完整迁移仍需在切换流程中单独验收，不能仅凭新建库就绪确认迁移成功。

## 10. 部署反向对账

概览事实层按完整部署快照与指标目录对账，使用精确的主机 ID 和组件 ID。组件发布方直接使用共享目录中的 ID，SCF 指标使用 `scf-collector`；目录中的外部 principal 不作为主机部署。每条部署独立记录探测结果、原始错误、探测时间、Reporter 状态和实例；探测成功不更新指标上报时间。

已登记且目录要求 Reporter 的部署（`transport: reporter` 且 `functional_observability` 不是 `not_applicable`；不适用的组件没有上报行时不要求上报，与 doctor 的豁免一致），没有上报记录时为 `missing`，超过上报时限为 `stale`；稳定检查身份为 `reporter:<host>:<component>`，首次上报或更换实例不会创建另一条部署检查。停用部署仍保留登记和真实上报事实，但停止对应 Reporter 告警。`none` 不产生未知探测，仍能识别缺失上报。

有近期上报但没有部署记录的进程进入独立的 `Unregistered` 事实集合；过期上报不作为仍在运行的证据。指标入口保留事件与快照校验，允许未登记进程进入目录供对账。首次完整发现之前不推断未登记；成功发现的空部署列表具有权威性，后续发现失败保留旧快照。目录读取有分页和总量上限，超限明确报错。

目录清理保留每条登记部署最后一次上报，清除其多余旧 boot 和退役实例，防止离线部署被误标为“从未上报”；首次发现尚未知时不清除 Reporter 历史。历史入库沿用报告产生时间，不用重投递时间刷新在线状态。结构化概览与页面已在 F4/F5 同批接入。


## 11. 健康概览 v2

`GetHealthOverview` 返回 summary、alerts、components、pipeline、business_checks、hosts、unregistered、notification。名称取自完整部署快照中的组件目录；按明确身份分组，不再按中文名称或 ID 子串归类。对外状态为 healthy、degraded、down、unknown、disabled、unchecked。探测和 Reporter 分开，none 仍可暴露缺失的 Reporter；状态起始时间保存在 `t_monitor_component_health`，由后台采样更新，未观测到的变化不伪造时间。

当前告警包含主机资源阈值、网关信号及 Agent 静默；静默边界为最后上报加三分钟，停用主机/Agent 部署不产生静默告警。选择空间仍保留全局告警。恢复阈值期间，最新检查时间与最近失败原因分别保留，原始错误与中文摘要同时返回。组件详情仅返回探测地址和最近十次结果，不返回认证 Header。

Host Agent `host_id` 显式对应登记主机，Agent ID 标识物理采集实例。主机只按登记的 `host_id` 汇总：每台登记主机只取最近上报的采集器参与汇总，同一主机重装后换了 Agent ID 的旧采集器静默退役，不再显示，超时也不产生失联事件与通知；没有 `host_id`、或 `host_id` 不在登记里的采集器不进入主机列表（页面只提示数量）。hostname 仅展示，不用作关联。各资源项附可用标志，缺失资源不会作为 0% 展示。原生 host 单元已渲染 host_id。

概览同时返回：

- 当前告警的 `severity`、`recovering`（最近一次检查已通过、等待确认恢复）和数据集告警对应的数据集事实 `dataset`；告警标题取检查名称，与推送标题一致，没有检查记录（主机阈值、主机失联）时用身份字段拼出。
- `incidents`：最近 48 小时（`incident_window_hours`）的告警经过，同一检查的“触发 → 恢复”归并为一条，带提醒次数与推送失败标记；触发早于窗口的从窗口外最近一次触发补齐，没有恢复记录又不在告警的标为已撤销（`active=false`）。主机 CPU、内存告警的经过带上触发时记下的进程排行（`processes`，内存告警按内存排、CPU 告警按 CPU 排，最多 5 个），当前告警带最近一次触发或提醒时的排行，页面直接显示：进程事后退出了也能查到当时是谁占的。
- 数据集最新一根的收线与到达时间、延迟（`delay_seconds`/`delay_known`）、预期 K 线（`expected_bar_at`/`expected_bar_close_at`）、
  还在等待的根数、最早一根的收线时间与已晚多久（`waiting_bars`/`waiting_since`/`overdue_seconds`）、是否已由上报确认迟到（`late_confirmed`）、
  允许迟到（`lateness_limit_seconds`）、无法按日历判断的原因（`clock_issue`）和市场时区（`timezone`，加密货币 UTC、A 股 Asia/Shanghai、
  没有交易日历的系统数据 UTC）；生产者上报的数据集展示名称（`display_name`，例如策略实例名）。
- 主机的 CPU/内存/磁盘告警阈值与资源总量（CPU 核数、内存总量与已用量、使用率最高的那个文件系统的总量、已用量和挂载点）、业务检查的检查名称；
  已停用或移除的业务检查返回 `disabled`，不再显示为正常。

**生命周期与系统状态**：各模块（因子引擎、策略、Trade）在 `/healthz` 的 `details.lifecycle` 里带精简的生命周期快照（阶段、颜色、降级、需要关注的对象与失败的检查项），
Monitor 从最近一次探测的响应体里解析（响应体上限放宽到 4096 字节，被截断或没有该字段时不显示），投影到组件的 `lifecycle` 字段，并汇总成概览的 `system`：
**健康面**（任何模块未就绪或故障，系统标红并列出模块与原因）与**运行阶段**（各模块里最靠前的：就绪 → 试运行 → 运行）两个维度，有对象**自动**暂停或故障时显示「运行中 · 降级」；手动、系统暂停是用户意图，不算降级，显示「已暂停」「部分暂停」；
有模块在恢复追赶时显示「恢复中 · 追赶 n/m 个模块」，全部追平后显示「已追平，待放行」，并列出各模块的进度与阻塞原因；有模块在重置时显示「重置中」；
有模块重启后自动回到原阶段时提示「已自动恢复」。`details.lifecycle` 同时带暂停详情、控制意图和恢复追赶进度。首页横幅显示这一行（`web/src/views/home/`）。

前端页面与 API 为 `web/src/views/ops/monitor/`、`web/src/api/monitor/`，按“值班排障优先”组织：顶部一句话结论（告警 / 需要关注 / 全部正常 / 数据不可用），
其下是当前告警（持续最久的在前，同一分钟内触发的合并为一组并提示可能同因），再是最近 48 小时的告警经过（1 分钟内自愈的闪断默认折叠），
最后是组件、主机、数据链路、业务检查四层健康，各占一整行：组件按主机列出名称与状态，主机卡片横向排列、资源条带告警阈值刻度并标出总量，
数据链路依次是采集 → 入库 → 视图 → 因子 → 策略计算 → 交易（入库是 Storage 写入水位，视图是 View 提交水位，分成两个环节），
表格按环节分组，每组标题写数据集数量与需要关注的个数，每个数据集显示最新K线、预期K线、到达延迟（上面的几种状态）与允许迟到，
K 线时间按市场时区显示并带时区标记（例如“18:54 UTC”“09:31 UTC+8”，告警里的数据集事实同样如此）；可切换到曲线视图看某一天逐根的到达延迟；
数据链路与业务检查只列出需要关注的项，可展开全部。首页的数据新鲜度用同一套后端字段：应收的最新一根已到写“已追平”，否则写已等待多久。
数据集 ID 用存储元数据翻译成名称；后端输出中文摘要，原始错误可展开；刷新失败保留旧数据并标出错误，不显示绿色正常结论。

## 12. 告警覆盖与高可用

这一节说明 MooX 出了哪些问题会通知到人、通知链路本身的可用性，以及仍然存在的盲区。
以下是当前代码已提供的主机守护、交叉检查和策略缓存能力；是否已在某个环境生效，需核实该环境的 host/control 制品、cron 与策略缓存。

### 12.1 覆盖的故障

| 故障 | 发现方式 | 判定条件与通知时间 |
| --- | --- | --- |
| 组件进程挂了或卡死 | 本机守护 `moox-runtime watch`（cron 每分钟）检查存活并按依赖顺序拉起；Monitor 也按部署探测健康端口 | 守护 1 分钟内拉起并推送“自动拉起”（10 分钟内合并）；10 分钟内拉起 3 次进入“持续崩溃”（严重），降频重试 |
| 组件活着但持续未就绪 | 守护读取 `/readyz` | 持续 5 分钟推送一次（30 分钟内不重复） |
| Monitor 活着但评估停滞 | Monitor 的 `/readyz` 包含“最近一次评估完成时间”（3 分钟） | control 上的守护按未就绪推送 |
| 组件不再上报运行指标 | Reporter 对账：已登记但上报缺失或过期 | 超过上报时限后，再持续失败满 60 秒（外部检查宽限） |
| 主机失联（宕机、断网） | HostAgent 每分钟上报快照，Monitor 3 分钟收不到、且该主机网关心跳也已停止 | 约 3 分钟，“主机 X · 失联”（严重），恢复后“已恢复在线” |
| 只有 HostAgent 停止上报 | 同上，但主机网关心跳仍正常 | 约 3 分钟，“主机 X · host-agent 停止上报”（警告），恢复后“host-agent 已恢复上报” |
| control 自身失联 | 存储机、海外机的守护每分钟与 control 主机网关做 TLS 握手（MooX CA 校验） | 连续约 3 分钟失败，由观测方直接推送“control 失联（由 storage 观测）”，恢复后“已恢复”；不经过 Monitor |
| 主机网关异常 | 心跳、路由同步、实例冲突合成一条检查 | 心跳或路由同步超过 2 分钟才判失败，再持续失败满 60 秒才通知，合计约 3 分钟起；实例冲突没有前面的 2 分钟 |
| 主机资源吃紧 | CPU 80%、内存 90%、磁盘 85%（HostAgent 每分钟采样） | 约 3、5、3 分钟（见第 2 节） |
| 归档对象存储不可用 | worker 每分钟 HEAD 一个不存在的键，archive-mgr 每 30 秒上报 `moox_archive_object_store_state`（“归档对象存储”） | 连续不可用超过 5 分钟；原因带最近一次失败原因 |
| 因子引擎、归档 worker 离线 | factor-mgr、archive-mgr 每 30 秒按最近心跳评估在线状态并上报（“因子引擎在线状态”“归档 worker 在线状态”） | 有启用的因子任务 / 归档任务时，2 分钟无心跳 + 上报与宽限，约 3.5 分钟；原因写明机器与最后心跳 |
| 归档任务异常 | archive-mgr 每 30 秒上报各任务健康等级（`moox_archive_task_health`），检查名“归档任务 <数据集>” | 任务为“异常”（接近线上保留期仍没成功、累积过无法补齐的区间、分区登记被拒等）时，上报与宽限后约 1.5 分钟；“需关注”不通知 |
| 有数据集没有归档任务 | Storage 数据集清单与归档任务健康指标比对，检查名“未归档的数据集” | archive-mgr 正在上报、有已激活且有限保留期的时序数据集（不含 `mooxsys`）没有归档任务时；原因列出数据集 |
| WS 推送接收停了或持续缺标的 | `collector-stream` 心跳与按数据集的失败周期连续数 | 心跳中断 3 分钟；连续 3 个周期有失败标的（疑似下架不计） |
| 因子水位卡在缺数据的周期 | factor-mgr 导出的任务阻塞起始时间 | 阻塞超过 30 分钟 |
| 数据中断：采集、入库、视图、因子、策略任何一环停更 | 数据集新鲜度与 K 线新鲜度，按交易日历判断应到的最新一根 | 允许迟到 + 持续失败满 60 秒 |
| 行情异常 | 行情金丝雀、Timer 协调、行情源失败率 | 持续失败满 60 秒 |
| 证书即将过期或无效 | Admin 证书巡检定时检查全部主机证书 | 每次巡检读取本机主机策略缓存里的渠道直接推送 |
| 主机重启 | 守护在开机后第一轮按依赖顺序拉起全部组件 | 一条“主机重启，已拉起 N 个组件”（有失败时为严重） |

**通知节奏**：普通检查与主机资源阈值的推送首次为“严重”，持续未恢复按规则的提醒间隔（默认 5 分钟）发“警告”，恢复发“提示”；概览中的问题严重程度另按故障类别判定。主机存在性通知还会依据网关心跳区分整机失联（严重）和仅 HostAgent 停报（警告）。
守护侧的告警按上表的合并与限频规则发送。设计告警量和验收预期时按这个节奏算，而不是“只通知一次”。

数据链路检查是端到端的兜底：即使某台机器或某个组件没有被直接监控，它停摆后，下游数据集按时没有新数据也会告警。

### 12.2 通知链路的可用性

- **两条独立的推送路径**：Monitor 发出数据、主机、业务类告警；每台主机的守护（以及 Admin 证书巡检）直接调用通知渠道（企业微信、飞书、钉钉、通用 Webhook），不经过 Monitor 与 EventBus——
  挂掉的可能正是 Monitor 所在的 control 或 EventBus 所在的主机。EventBus 不在本机的主机，守护每轮还会对 EventBus 端点做 TLS 握手，
  连续失败约 3 分钟推送一条“EventBus 不可达”，并抑制这一轮依赖它的组件各自的“持续未就绪”告警。
- **观测输入中断时冻结判定**：Monitor 自己的 EventBus 观测消费者没连上（或刚重新连上的 5 分钟宽限内），服务指标与主机快照的 last_seen 都是旧的，
  这时判“已停止上报”只会整批误报。依赖观测输入的检查（上报方、数据集新鲜度、业务检查、模块健康、主机失联扫描）全部冻结——既不新增告警，也不恢复已有告警——
  只留一项“观测输入”检查说明原因；网关、K 线新鲜度、行情探针这类不依赖观测输入的检查照常判定。
- **告警渠道单一来源**：渠道只在 Monitor 的通知渠道里维护（控制台“消息通知设置”，或 `moox-cli config notification --publish --yes` 把 `moox.toml` 的 `[notification]` 写进去）。
  每台主机的 HostAgent 每 5 分钟经网关调用 `GetHostPolicy`，把全部渠道与守护参数写进 `<部署根>/run/host-policy.json`（0600）；拉取失败时保留旧文件，
  部署时用 `moox.toml` 写一份种子保证首次拉取之前也能告警。`moox-cli config notification` 会列出各主机缓存的版本与拉取时间。
- **多渠道**：告警发给全部通知渠道，至少一个送达就算送达；全部失败才在下一次评估重试，单个渠道失败记一条“推送失败”事件。推送失败的报告里不带出 Webhook。
- **防闪断**：外部检查持续失败满 60 秒才告警，避免服务重启时的闪断刷屏；持续未恢复每 5 分钟提醒，恢复通知一次。
- **告警历史可追溯**：每次触发、恢复、推送失败都写入告警事件表，监控页展示最近 48 小时的告警经过；守护的每次拉起写进 `run/watchdog/<组件>.jsonl` 台账。

### 12.3 仍然存在的盲区

| 盲区 | 说明 | 兜底 |
| --- | --- | --- |
| control 主机还在，但守护（cron）与 Monitor 同时失效 | 交叉检查只能证明 control 的网关入口活着 | 可选：在腾讯云配置云拨测探测控制台，作为不依赖本系统的外部检查 |
| 所有主机同时断网，或推送服务本身不可用 | 两条推送路径都发不出去 | 恢复后告警事件表与守护台账仍可追溯 |
| 只能出站的主机（192）与 control 的反向连接断开 | “主机网关反向连接（主机）”检查断开满 3 分钟告警，该主机经中转的健康探测同时失败；HostAgent 经 EventBus 的上报不经中转，主机失联判断仍准确 | 告警正文按 host-agent 是否仍在上报区分反向连接断开与主机失联；网关自动退避重连 |

### 12.4 整体形态

```text
                 ┌──────────── control ────────────┐
 组件崩溃 ──► watch（cron，每分钟）拉起 ──► 直接推送到通知渠道（读本机缓存的渠道）
                 │                                  │
 数据/主机异常 ──► Monitor 检查 ──► 推送全部渠道     │
                 └──────────────────────────────────┘
 control 失联 ──► 存储机 / 海外机的 watch 交叉检查 ──► 直接推送
 外部程序离线 ──► factor-mgr / archive-mgr 在线状态 ──► Monitor ──► 推送
 渠道修改（控制台或 moox-cli config notification）──► Monitor ──► 各主机 HostAgent 拉取缓存（≤ 5 分钟）
```

在守护与 Monitor 正常部署、观测方及推送网络可用的前提下，上述路径覆盖主机失联、组件停摆、数据断流、Monitor 评估停滞与外部程序离线；同时失效的边界见第 12.3 节。
