# 监控（Monitor）

Monitor 是 MooX 的集中健康检查与告警模块：接收各组件的上报（服务指标、就绪判断、模块级生命周期）和主机快照、评估实时
数据集新鲜度和行情健康，生成告警并推送到通知渠道（企业微信、飞书、钉钉或通用 Webhook）。组件健康只看上报，Monitor 不探测任何组件（见第 8 节）。
它是单实例服务，不做跨实例选主；非控制机的主机采集器对控制机与 Monitor 的直推另有独立推送路径（见第 12 节）。

代码位置：`modules/monitor`。

## 1. 进程与端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| `MonitorMgr` | loopback tRPC `11410` | 管理接口，经 Admin 管理网关访问 |
| 健康检查 | `11409` | `/healthz`、`/readyz`、`/metrics`；只听 127.0.0.1、不验签（同机进程与 `moox-cli doctor` 经 SSH 使用） |

| 定时器 | 周期 | 作用 |
| --- | --- | --- |
| `check_schedule.timer` | 30 秒 | 每轮依次：主机类检查 → 行情金丝雀和业务评估（含组件的停止上报、未就绪、反复重启）（`bootstrap/schedule_timers.go` 的 `checkRound`） |
| `deployment.timer` | 每分钟 | 从 Admin 的 SysDeploy 同步部署拓扑（每台主机应该有哪些组件）与各主机网关状态，不生成检查 |
| `metrics.timer` | 30 秒 | 上报 Monitor 自身指标 |
| `data_cleanup.timer` | 启动时 + 每 5 分钟 | 清理过期告警事件（`scheduler.alert_event_retention_days`，默认 14 天）、指标去重记录、7 天前的数据链路到达记录，24 小时未上报的序列和退役上报记录（仍登记的部署保留最后一次上报） |

检查表：每项检查一行（`t_monitor_checks`），存最近一次结果、最近一次失败、连续计数与告警状态；不保存结果历史，要看经过读告警事件。
检查由每轮评估按本轮事实生成（`internal/checks`）：评估分主机、探针（行情探针与内置标签）、业务三个域，各域只推进、删除自己的检查。
本轮不再产出、也没有冻结的检查当轮删除，在告警的先写一条“已恢复”事件并推送（原因“已停用或移除，不再检查”）；对象再次出现时新建一行、计数从零开始。
产出方读不到依赖、无法判断时把它负责的检查冻结（行不动），不能省略不报：观测输入中断、K 线本轮没有评估、组件无法确认、Collector 暂停、
标签同步状态读不到，以及上报方停止上报（见第 8 节）。没有清理定时器，也没有要手工清理的残留。

数据：SQLite `data/monitor/monitor.db`（`schema/monitor.sql`）。主机快照历史存在本库的 `t_monitor_host_samples`（见第 3 节）；
服务指标只保存每个序列的最新值，不写时序历史。Monitor 的 SQLite 保存检查表、告警事件、指标目录、服务指标最新值、主机快照历史和数据链路逐根到达记录（见「数据链路到达曲线」）。Monitor 不往 Storage 写任何数据。

## 2. 检查来源

告警项按"同一问题只告警一次"精简：K 线类采集数据集只由「K 线新鲜度」（`kline_freshness:`）出检查，`dataset:` 只管因子、策略等非采集生产者，不再生成 `dataset:collector:` 检查，`storage` / `storage_view` 两类生产者按采集任务清单排除采集数据集（清单尚未取到时冻结这两类前缀，避免误建重复检查或误删已有因子检查）；主机网关不单独检查，只按组件上报判断（第 9 节）；
主机阈值告警只保留 CPU、内存、磁盘空间（磁盘繁忙度与网络错误包不再告警，指标仍在页面展示）。
CPU 告警取 80%（恢复线 70%）、连续 3 次采样；内存 90%（恢复线 80%）、连续 5 次；磁盘空间 85%（恢复线 80%）、连续 3 次。HostAgent 每分钟采样一次（`modules/hostagent/config/trpc_go.yaml`），所以 CPU、内存、磁盘分别约 3、5、3 分钟告警。
这些参数是检查自己的参数，写在代码里（`internal/hostmetrics/checks.go` 的 `metricThresholds`），不放在告警规则里。
CPU 阈值不能放得更高：实测回填 1h 因子任务时 `storage-primary` 占到 4 核主机 330%–380% 的 CPU（整机 82%–95%），按“90%、连续 5 分钟”一条告警也不出。

| 来源 | 内容 |
| --- | --- |
| 组件上报 | 每个登记了部署的组件三条检查：停止上报 `reporter:<host>:<component>`、未就绪 `ready:<host>:<component>`、反复重启 `restart:<host>:<component>`。只看组件的上报，见第 8 节 |
| 模块健康 | `packages/report` 注册的各模块健康检查清单，目前三项：策略目标生成（`strategy-targets`）、交易调仓（`trade-rebalance`）、监控指标接收（`monitor-metrics`），检查 ID 是 `module:<清单 ID>`。健康状态与级别判定口径统一收口在 `packages/doctor/health.go`（`EvaluateModuleRunHealth`、`HealthStatusSeverity`、`HealthStatusRank`），Monitor 与 `moox-cli doctor` 共用同一份规则：模块上报过运行之后才生成，最近一次运行失败并且在允许间隔内（依次为 10、5、2 分钟）没有成功过判失败，恢复成功即通过；最近一次失败之后超过 1 小时没有新的运行按闲置处理、判通过（例如组合解绑后没有调仓可做），每小时跑一次、次次失败的仍一直判失败 |
| 主机 | HostAgent 主机快照：每台登记主机六项检查 `host:<host_id>:<种类>`——`presence`（主机失联）、`agent`（只有 host-agent 停止上报）、`cpu`、`memory`、`filesystem_usage`、`disk_forecast`（磁盘写满预测；磁盘繁忙度、网络错误包只展示不告警）。见下文「主机类检查」 |
| 数据集新鲜度 | 主机快照不在 Storage 里，主机停报由主机失联告警覆盖。按“最新一根 K 线是否按时到达”判断，见下文「数据集新鲜度：最新一根 K 线」；允许迟到按周期分级（写在 Monitor `app.yaml` 的 `metrics.dataset_health`）：分钟级（30s～30m 周期）`minute_lateness` 默认 10 秒，小时级（1h、4h）`hour_lateness` 默认 20 秒，日线及以上 1 个周期；可按数据集用 `overrides[].lateness` 覆盖。生产者上报的最近运行、最近成功时刻另按 `run_missed_intervals`（默认 2）、`success_missed_intervals`（默认 3）个间隔判运行停滞（`run stale`）与成功停滞（`success stale`）；上报的间隔是连续时间，交易所市场（A 股）在此刻没有应收而未到的 K 线时（午休、收盘后、非交易日）跳过这两项，开盘后真停了由等待中的 K 线照常判出（`internal/observability/overview.go` 的 `datasetStatus`）。告警还要连续失败满 60 秒（见「外部检查有 60 秒宽限」） |
| 任务暂停与新鲜度检查 | 生产者的期望清单决定哪些数据集要检查：数据集的 `moox_<module>_dataset_enabled` 为 0 就是“现在不期望它产出”，Monitor 对它的因子计算与写入存储检查不再期望（按「已停用或移除，不再检查」恢复既有告警），同一数据集的结果视图水位也不再检查。因子引擎模块被有意停下（手动或系统暂停，以及放行前的恢复追赶）时，引擎在心跳的 runner 状态里给每个任务带 `paused`；任务检查不通过不算暂停，照常检查新鲜度。管理端据此把它的结果数据集标为 enabled=0（管理端重启后第一轮清单里也有这条 0 序列，下游视图检查不会重新告警）；恢复后回到期望清单。系统暂停时所有因子任务都算暂停。策略模块同理：暂停与放行前的恢复追赶期间，策略把每个启用实例的期望项标为暂停（`moox_strategy_dataset_enabled` 为 0），Monitor 不报“运行过期”，放行后回到期望清单 |
| 数据集检查命名 | 数据集新鲜度检查名为「对象 · 环节」，环节按生产者分为采集、写入存储、结果视图、因子计算、策略结果。对象优先取生产者随期望清单上报的展示名称（`moox_<module>_dataset_info` 的 `name` 标签；策略实例是「定义名称（实例 ID 前 8 位）」，与控制台策略页一致，例如「动量轮动（26d51f7e）· 策略结果」），其次取 Storage 登记的数据集名称，都没有时用「数据集 ID（频率）」。名称改了之后旧名称序列不再上报，Monitor 只认仍在上报、最近上报的那条；名称拿不到不影响检查和告警。告警页标题和推送标题都取这个名称 |
| 待生效（上游历史补齐中） | 首次接入的数据集（Collector 自动补历史，见[采集](采集.md)）补齐期间，下游因子任务与策略实例不生效。生产者（因子管理端、策略）把读取它的数据集置“暂停”期望，并带原因：`enabled` 指标取 `-1`（一般暂停为 `0`），其余指标不变。Monitor 把 `enabled <= 0` 一律当作“不期望产出”，小于 0 时数据集显示为状态 `disabled`、原因 `history_seeding`（页面“待生效（上游历史补齐中）”，带实例名），不算异常、不进“需关注”计数、不生成数据集新鲜度检查，已有的检查按“不再检查”收尾；补齐结束后生产者恢复 `enabled=1`，回到正常检查。首页系统状态的补齐进度由控制台读 Collector 的 `GetCollectorStatus.history_seeds`；Monitor 只从采集任务清单取各结果数据集是否在补齐中、何时补完（下面 K 线新鲜度按标的的放宽用） |
| 数据积累中 | 生产者（因子引擎、策略）把“只因数据还没攒够而不完整”的运行报告为 `partial`（因子：失败的标的都是预热中的；策略：因历史不足或上游因子被跳过，且在积累期上限之内），并带上 `<module>_dataset_last_partial_timestamp_seconds`。最近一次产出是部分结果、此后没有更新的成功、而且部分结果仍按成功容忍时间内持续出现时，数据集状态是 `degraded`、原因是 `warming`（页面显示“数据积累中，结果暂不完整”），但新鲜度检查按通过记录，**不触发也不延续告警**；部分结果也断了（生产者停了或开始真正失败）就回到原来的 `run stale` / `success stale` 判断。数据重置、新建因子集、重启后的第一期都属于这种情况 |
| K 线新鲜度 | 从 Collector 拉取采集任务清单，逐个结果视图检查（活跃标的取自 Storage 的 `ListDatasetSubjects`，停牌、退市的成员不算活跃，不会报“没有任何数据”，见[采集](采集.md)第 7b 节）：应收的最新一根（按任务声明的交易日历算）之后缺的第一根，从收线起超过允许迟到（健康策略按周期给出的值与采集任务声明的允许迟到中较大的一个，例如加密货币采集任务声明 15 秒，1 分钟线取 15 秒、1 小时线取 20 秒，A 股采集任务默认声明 90 秒，5 分钟线取 90 秒；数据集新鲜度只用健康策略，加密货币 1 分钟线为 10 秒）仍没到就判为停止更新；逾期按 Storage View 摘要快照的时刻算（快照每 30 秒上报一次，半分的评估可能早于那次快照入库，按当前时间算会把准时写完、还没上报的 K 线误判为停止更新；快照超过 1 分钟没有更新时改按当前时间算，停更照样报出），落后标的的逾期时长同样按交易日历和快照时刻计。休市、午休、开盘前不需要跳过：应收的最新一根停在上一时段的最后一根。日历未覆盖、市场没有日历、周期对齐未确认时按“无法判断”报出，不推测。已启用任务的数据准备状态（`result_status`）停在 `pending` 或 `unverified` 时，30 分钟宽限期内跳过（保持原检查状态）；连续超过 30 分钟仍未准备完成则由 K 线检查报失败（`task_result_prepare_stalled`，“任务已启用但数据准备一直未完成”，宽限计时保存在 Monitor 内存里，任务就绪、停用或删除后清零）。首次接入的历史补齐中与补齐结束后 24 小时内（空间里有数据集处于上面的“待生效”，与下面 View 跟随落后同一份记忆）：补齐写入的历史行在变更日志里排在实时写入前面，结果视图按变更日志顺序追赶，几个小时内会落后于采集已完成的一期；这时只要采集任务清单里已完成的最新一期本身没过期（按清单的观测时刻、允许迟到内），检查按通过记、原因写“结果视图在追补齐写入的历史行”，采集真的停了仍按“结果视图落后于已完成的一期”报出。只按空间判断：这段时间里同空间别的数据集的视图落后也不报；空间里没有下游因子或策略时看不到补齐，照常报（已知差别）。按标的的结论另按数据集放宽：采集任务清单标明结果数据集在首次接入的历史补齐中（`history_seeding`）或补完不到 30 分钟（`history_seed_finished_at`）时，视图整体按时更新、按标的看有落后或没有数据的，按通过记，原因写“补齐过程中的假象”，数字留在诊断里。原因是 storage-view 按标的记的最新一根只在进程内、只认本进程见过的写入，重启后补齐又按时间升序写历史行：跟踪表里先出现的标的带着几个月前的时刻，还没补到的一根都没有（11-25 A 股补齐时 197 个对象“没有数据”约 11 分钟，美股补齐中一直报到开盘）。视图整体停更照样报；只放宽补齐中的那个数据集，同空间别的数据集照常判。已知差别：这段时间里实时采集个别标的真的缺根也不在这里报，兜底只有两项：视图整体停更会报，自动巡检会补缺。Collector 的“连续 3 个周期有失败标的”检查只对推送采集（crypto）生效，云函数定时采集的市场（美股、A 股、港股）没有按标的的兜底；补完 30 分钟内下游已经生效，这一段同样没有按标的的兜底（见[采集](采集.md)）；合成任务的目标数据集没有补齐记录，源数据集补齐后合成补写目标的历史时同样可能误报；休市期间 storage-view 重启后补齐刚开始、跟踪表里还没有任何标的补到最近一根时，可能按视图整体停更报，第一只标的补到最近一根后消失（没有实测） |
| 行情健康 | 采集计划协调由 Collector 自己判断后上报关注项 `attention:collector:fetch_coordination_failing`（“采集计划协调异常”）：协调进行中（有未生效的计划或云端操作在跑）且开始不满 `plan_health.pending_grace`（默认 5 分钟）时不报；协调失败按失败原因给出处理办法；最近一次对账成功超过 `plan_health.stale_after`（默认 15 分钟）时写明最后对账成功的时刻。阈值与文案都在 Collector（`internal/fetchplan/coordination_attention.go`），见[采集](采集.md)第 10 节。行情源出问题由 K 线新鲜度和云函数定时检查发现 |
| 推送采集 | 心跳中断由 Collector 自己判断后上报关注项 `attention:collector:stream_heartbeat_lost`（“行情推送 collector-stream 心跳中断”）：空间里有启用的推送 K 线任务、而库里的心跳记录不存在或早于 `stream.heartbeat_timeout_seconds`（默认 180 秒，与切换前检查同一个值）时为 1，Collector 启动后一个超时之内不判断，detail 写空间与最后心跳时刻并给出切回 SCF 的命令。推送连续缺失也由 Collector 判断：某数据集连续 3 个周期有截止时仍缺的标的（疑似下架不计）时上报关注项 `attention:collector:stream_periods_missing`（“行情推送连续缺失”，期数在 Collector 内存里，重启后从零数）。见[采集](采集.md)第 3a 节 |
| 因子连续水位 | factor-mgr 按引擎心跳记下各任务连续水位的阻塞起点，采集指标时把阻塞超过 30 分钟的任务上报为关注项 `attention:factor-mgr:watermark_stalled`（“因子连续水位停滞”，detail 写空间、任务与起点），阈值在 factor-mgr；不自动跳过，交给人工手动补采或确认行情源缺失。见[因子](因子.md) |

### 主机类检查

主机的在线情形和资源使用率是普通检查，由 `check_schedule.timer` 每 30 秒产出结果（`internal/checks/host.go` 的 `NewHostReporter`），
写入检查表，经同一套告警推进记状态、推送，概览从同一份告警状态展示。所以同一件事在页面和推送里是同一个标题、同一个级别、同一段原因。
Monitor 里只有这一套告警处理。

主机类检查在每轮里**独立先跑**，排在行情探针和业务评估之前：它只需要采集器登记、部署拓扑和网关信号（`observability.Builder.HostFacts`），
都在 Monitor 自己的库里，并且用自己的 10 秒时限，不沿用这一轮剩下的时间。所以读 Storage 超时或业务评估整体失败时，
主机失联和其他主机的资源告警照常产出。业务评估不碰 `host:` 开头的检查（和行情探针的检查一样，各域只推进、删除自己的检查）。

| 检查 | 失败条件 | 告警所需 | 级别 |
| --- | --- | --- | --- |
| `host:<host_id>:presence`，“主机 X · 失联” | 采集器停报满 3 分钟，且主机网关的组件上报不是正常（停报、从没上报或没有部署） | 失败 1 次 | 严重 |
| `host:<host_id>:agent`，“主机 X · host-agent 停止上报” | 采集器停报满 3 分钟，但主机网关仍在上报 | 失败 1 次 | 警告 |
| `host:<host_id>:cpu` / `memory` / `filesystem_usage`，“主机 X · CPU 使用率”等 | 使用率不低于告警线；已在告警的要回落到恢复线及以下才算通过 | 连续 3 / 5 / 3 次采样 | 警告 |
| `host:<host_id>:disk_forecast`，“主机 X · 磁盘写满预测” | 按近 7 天每日最晚主机快照（至少 3 个自然日间隔）的日增长率中位数估算，任意挂载点预计不超过 **7 天**（`DiskForecastAlertDays`）耗尽安全余量（10% 且不少于 5 GiB）；已在告警的需回落到超过 **10 天**（`DiskForecastRecoveryDays`）或停止增长才恢复；历史不足 3 个自然日间隔时按正常记录、不告警 | 失败 1 次 | 警告 |

- 标题里的“X”是登记的主机 ID（与主机卡片一致）。
- 失联与 host-agent 停报两项互斥：同一时刻最多一项失败。情形变化时一项恢复、另一项告警，恢复通知的“当前”一行写明改由哪条告警跟进。
- 每台上报过的登记主机有一组主机类检查（六项都是），以主机 ID 为键，重装 HostAgent 后沿用；
  主机或其 host-agent 部署停用、主机从登记里移除后检查不再产出、当轮删除，已有告警（含资源告警与磁盘写满预测）各推一条“已恢复”。
- 失联与 host-agent 停报之间改判时（例如停报之后网关也停报了），原来那条同样推一条“已恢复”，再推新的一条。
- 网关状态某一次读取出错不改变判断：库里保留上一次读到的心跳时间，它超过 2 分钟才算心跳停止。所以 host-agent 停报后主机真的失联，最多晚 2 分钟改判。
- 资源检查只在有新采样时产出结果：每 30 秒评估一轮，同一次采样只算一次（本轮写入成功后才记为已评估），“连续 N 次采样”才成立；没有新采样、主机失联或该指标不可用时保持原状态。
- 恢复线：超过告警线之后，使用率落在恢复线与告警线之间仍按失败记录（原因写“还没有回落到恢复线”），继续提醒；没有在告警时落在这一段不算失败。
- 观测输入中断时这些检查全部冻结（见 12.2）。

管理台只展示健康摘要，不提供检查项的增删改。

### 数据集新鲜度：最新一根 K 线

- **应收的最新一根 E**：Monitor 按采集任务清单声明的市场日历（`calendar_id`、`timezone`、`sessions`；A 股是 `cn_stock`、`Asia/Shanghai`、
  `09:30-11:30` 与 `13:00-15:00`）算出此刻应已收线的最新一根（`internal/marketclock/market_clock.go`）。每个空间取该空间采集任务的日历：
  有交易日历的（A 股）优先，加密货币全天交易，按周期取整（周线按周一、月线按自然月）。非交易日、未开盘、午休时 E 回溯到上一时段
  或上一交易日的最后一根，所以新时段第一根收线前 E 仍指向上一时段的最后一根，不需要“开盘预热”。
- **K 线的 data_time**：输出水位是最新一根 K 线在存储里的 `data_time`（开盘时间），策略结果也上报它所用那根 K 线的开盘时间。
  交易所市场的日内周期（含 1m）与日线全部交给 `packages/barclock`，与 Collector 采集、合成的桶一致：日内从每个交易时段开盘起切分，不跨午休，
  1 分钟线 09:30～11:29、13:00～14:59 开盘，5 分钟线每个交易日 48 根（09:30～11:25、13:00～14:55 开盘）；不能整除交易时段的周期（如 45m、4h）
  没有这样的桶，显示“周期对齐未确认”，不判断。日线的 data_time 是交易日期的 UTC 零点（按交易日取桶，`barclock.DailyBucket`），当天最后一个时段收盘时收线。
  周线、月线每周（月）一根，在最后一个交易日 15:00 收线，开盘取第一个交易日的本地零点，这两种由 Monitor 按交易日历归并。交易日历只有一份，内嵌在 `packages/marketcalendar`。
  已知差别：周线、月线 Monitor 的开盘取首个交易日的本地零点，Collector 合成写的是周一或当月 1 日的 UTC 零点，两边对不上；
  目前没有股票周线、月线任务，启用这类任务时新鲜度可能对不上，到时再统一口径。
- **延迟 = 到达时间 − 收线时间**：到达时间由生产者在写入时记录（`moox_<module>_dataset_output_arrival_timestamp_seconds`，Storage 视图是
  `moox_storage_view_output_arrival_timestamp_seconds`；因子引擎随运行摘要带上每期的完成时间），在输出水位前进的那一刻定值，之后不随当前时间增长。
  生产者没有上报到达时间时页面不推算延迟。
- **预期 K 线**：概览给出 E 的开盘时间与收线时间（`expected_bar_at`、`expected_bar_close_at`，开盘时间与输出水位同一口径），
  页面在“最新K线”旁单列“预期K线”：两者相同即应收的那根已到，不同就是还在等它。
- **已晚多久与过期判断**：还没到时，“已晚” = 当前时间 − 缺的第一根的收线时间（应到时间），持续增长、用于展示。生产者每 30 秒定时上报一次
  快照（整分与半分对齐，比收线晚几毫秒）；入库、视图、策略计算在输出水位前进时还会立刻补报一份（见「水位前进即补报」），
  因子引擎每算完一期就补发心跳，因子管理服务收到心跳立刻刷新指标并补报（见下文）。Monitor 只能看到上报那一刻的水位，所以判过期看上报：生产者最近一次上报
  （`confirmedAt`，即上报快照的时刻；同一数据集有多个实例时取仍在上报的实例里最早的那次）时，缺的第一根已晚超过允许迟到仍没有，
  才判为过期（`late_confirmed`）并走数据集新鲜度告警。例如 1 分钟线 :00 收线、允许迟到 10 秒，:10 之后那次上报（补报或 :30 的定时上报）仍没有就判过期，最多比“当前时间”口径晚一次上报，
  但不会把还没来得及上报的准时 K 线判成过期。超过 1 分钟（两次上报）没有新上报时不再按上报时刻判断，改按当前时间算
  （`ReportSnapshotGrace`，`internal/metrics/query.go`），漏报或停止上报不会让停更一直被当作没逾期。
- **低频视图的上报静默**：Storage 视图只在每个周期的输出提交时刷新水位指标，重启后也要等到下一次提交才重新出现，1 小时视图正常会静默接近一小时。
  通用的“2 分钟无数据即停止上报”不适用于它们：周期不短于 5 分钟的视图容忍一个完整周期再加 5 分钟（1 小时视图 65 分钟），
  分钟级视图仍按 2 分钟判定；真正停止的视图静默超过这个时间，或之后的运行过期判断，仍会发现（`viewReporterStale`，`internal/observability/overview.go`）。
- **K 线新鲜度在 View 摘要缺失时的兜底**：Storage 只在进程内存里记每个 View 的最新输出（`moox_storage_view_output_latest_data_time_seconds` 等摘要），
  重启后要等这个 View 再提交写入才有；休市期间重启（股票市场周末、长假），旧采样过了回看窗口就读不到。读不到这个 View 的摘要时，“K 线结果”检查用采集结果清单里
  View 已建索引的上界（`view_last_data_time`，和摘要一样不收未来时间）当作最新一根，照常按交易日历判逾期：休市时停在上一交易日最后一根算正常，开盘后第一根收线加允许迟到
  仍没前进就判停止更新。兜底时没有对象明细，只判 View 整体，不算缺失或过期对象。有摘要但最新一根为零（例如 Storage 跟踪的序列超过上限）不兜底；
  这种情况和两个值都没有时一样，仍报“还没有收到任何结果数据”（`no_observation`）。
- **页面上的几种状态**（“到达延迟”列，“预期K线”列同色）：
  - 准时到达：显示“延迟 5 秒”，状态正常。
  - 迟到但已到：显示“延迟 40 分钟”并标橙；当前状态正常、告警恢复，这个延迟一直保留到下一根到达后被替换。
  - 还没收到、在允许迟到之内：显示“等待中，已晚 20 秒”，正文色。
  - 已晚超过允许迟到、但还没有上报确认（后端仍判正常）：显示“等待中，已晚 35 秒”并标橙，悬停说明在等生产者下次上报确认。
  - 上报确认迟到（`late_confirmed`）：显示“未到，已晚 N 分钟（缺 n 根）”并标红，状态列写原因“等待中：… 收线的那根已晚 … 仍未到”。
    数据集因别的原因降级（例如数据积累中）不按它标红。数据集还没有任何产出时，“预期K线”列只给出应收的那根，不写“已到”。
- **不推测**：日历覆盖不到当前日期时状态为未知、原因是“日历未覆盖”（会告警，需要更新交易日历）；周期对齐未确认时只在页面显示原因，
  不改变状态。没有交易日历的空间（没有采集任务声明市场）不是行情 K 线，不判断到达延迟，也不提示。

## 3. 指标接入

各服务的 `metrics` 定时器把有界的 Prometheus 快照发布到 `MOOX_OBSERVABILITY`，HostAgent 发布主机快照。
Monitor 用固定消费者读取两类事件：

- 服务指标在单次 SQLite 写事务内完成幂等去重、服务上报刷新与序列最新值更新（已移除原先额外的 `IsDuplicate` / `TouchService` 冗余写事务），只在 SQLite 保存每个序列的目录与最新值（同一张 `t_monitor_metric_series`：最近一次上报时间总是前进，最新值只前进到更新的观测、水位类指标不往小里退），不写 Storage；数据集清理时（`pruneDeletedDatasets`）同步清理孤立的 `t_monitor_subject_first_seen` 记录。概览、告警和 Doctor 都只用最新值，
  指标入库不依赖 Storage，Monitor 的就绪状态也不检查 Storage 里的表结构。
- 主机快照的处理顺序是：按主机 ID 登记最近一次上报（`t_monitor_host_agents`，每台主机一行）→ 更新内存里的最新快照 → 写本地表 `t_monitor_host_samples`（每台主机每分钟一行，同一分钟后到的覆盖先到的）。
  收快照时不评估告警：失联与资源阈值由主机类检查按登记时间和最新快照判断（见第 2 节「主机类检查」）。主机是否在线只按“距最近一次上报是否超过 3 分钟”判断，不另存状态。
  历史保留 7 天，由 `data_cleanup.timer` 删除；`QueryHostMetricHistory` 与主机磁盘写满预测检查（按 UTC 自然日只取每日最晚样本，每台主机至多 8 行）都读这张表，可查最近 7 天；行数超过请求的条数时在整段范围内等间隔抽取（页面取 500 点，1 小时到 7 天的曲线都覆盖整段）。
  进程排行与采集器状态只随当前快照展示，不写进历史。
  存储机不可达或磁盘写满时，主机在线状态和阈值告警照常：主机类检查在每轮评估里独立先跑、只读 Monitor 自己的库（见第 2 节「主机类检查」），不受后面读 Storage 的行情探针和业务评估影响；
  本地表写失败只让这条快照重投，登记时间与最新快照已经更新，检查不受影响。
- 只接受已登记的指标族，原始指标不对用户开放，也不支持自定义规则。

Monitor 不抓取服务的 `/metrics`，不依赖 Prometheus Server。

### 新序列限额与入库诊断

指标目录（`t_monitor_metric_series`）会随新标签组合增长；24 小时未上报的序列由清理定时器删除。已知差别：生产者改了指标的标签名或标签值之后，旧标签的序列还会留 24 小时，这期间依赖它的检查可能按旧序列报“停止更新”；不按服务整份替换（云函数和 `moox-cli` 这类上报方只报一部分序列，整份替换会误删），需要立刻消掉时手工删旧序列（`t_monitor_metric_series` 里对应的行）。若上报方持续把标的、请求 ID 之类放进标签，清理前仍可能挤占目录与入库资源，因此入库另有两道保护：

- **新序列限额**：每小时、每天新建的序列数有上限（`metrics.max_new_series_per_hour` 默认 2000、`max_new_series_per_day` 默认 10000；负数表示不限）。
  已有序列照常更新，超出上限的**新序列**样本被丢弃，同一份快照里的其他样本照常入库，消息仍确认、不重投。默认值留足余量：目录约 500 条序列，
  全新启动（清空 Monitor 库）时一小时内要全部建出来，限额只拦标签失控这种成倍增长。
- **丢弃与拒收可见**：`/metrics` 输出
  `moox_monitor_metrics_series_limit_current{window}` / `_max{window}`（近 1 小时、24 小时新增数与上限）、
  `moox_monitor_metrics_series_dropped_total{service}`（被限额丢弃的新序列）、
  `moox_monitor_metrics_samples_filtered_total{service}`（不在健康指标白名单里被丢弃的样本，生产者改了指标名而白名单没跟上时靠它看出来）、
  `moox_monitor_metrics_ingest_total{result,reason}`（`rejected` 按原因分 `checksum`、`limit_exceeded`、`parse`、`space`）。
- **告警**：warning 级检查 `metrics_ingest:series_limit`「指标序列数量保护」——有服务的新序列被丢弃，或近 1 小时 / 24 小时新增数达到上限的 90%，
  文案点名被丢弃最多的服务和它最近一条被丢弃的指标名，恢复后自动解除。

### 水位前进即补报

30 秒的定时上报不变。Storage primary（写入水位）、Storage View（View 提交水位）和策略服务在注册定时上报时调用
`Handler.FlushOnOutputAdvance()`；`report.DatasetMetrics` 与 Storage View 的水位记录在输出水位前进时调用 `report.NotifyOutputAdvanced()`，
已订阅的处理器 1 秒后补报一份完整快照，1 秒内的多次前进合并成一次（同一时刻写完的多个数据集只补报一份）。补报时定时上报正在进行，
就稍后再补一次，避免漏掉在那份快照之后才前进的水位。Monitor 因此约 1 秒内看到新写完的那根，到达记录也基本做到每根一条。
因子结果的水位来自因子引擎的心跳：引擎每算完一期就唤醒心跳循环立刻补发一次（平时 10 秒一次），因子管理服务每收到一次被接受的心跳
就把运行摘要换算成数据集指标，水位前进同样补报，不用等 30 秒的定时上报。引擎重启后预热期间到达的那一期（1h 任务是整整一根）结果不正式、不推进水位，
预热完成后由缺口补算补齐，引擎随即把这一期的摘要改为完成，因子管理服务接受同一期的升级，水位前进、补报，
因子环节的“数据积累中”当场消失，到达时间记为补齐的时刻（不再等到下一个整点）。

### 数据链路到达曲线

- **记录**：Monitor 在指标入库的同一个 SQLite 事务里，把每份快照的输出水位（`moox_<module>_dataset_output_watermark_timestamp_seconds`、
  `moox_storage_view_output_watermark_timestamp_seconds`）与入库前已提交的值比较，前进了就为新的最新一根写一行 `t_monitor_bar_arrivals`：
  环节（入库 storage、视图 storage_view、因子 factor、策略 strategy）、空间、数据集（View 记它所属的数据集，主数据集同为该数据集）、周期、开盘时间、
  上一份快照的水位、生产者上报的写完时刻。与消息去重同一事务，重复投递不会重复记录、入库失败重试也不会漏记；同一根已有记录时保留最早那条。
  补数据时一批追了几根，只记最新那根（带上一份快照的水位，查询时算出跳过了几根）。采集环节不记录。
- **存储与保留**：放在 Monitor 的 SQLite 而不是 Storage：Storage 的范围读取走 View，View 每个序列只保留最近 5000 根（1m 约 3.5 天），
  查不到 7 天。一个空间一天约 2 万行，单表按（空间、周期、开盘时间）建索引即可按天查询；`data_cleanup.timer` 删除到达早于 7 天的记录
  （按到达时间而不是开盘时间：周线、月线到达时开盘早已超过 7 天）。
- **查询**：`QueryPipelineArrivalHistory` 按链路（源数据集，即入库的数据集，加周期）和日期返回一天各环节的曲线。日期按市场时区的自然日：
  加密货币 UTC、A 股北京时间（Asia/Shanghai），时间点按收线时间落在这一天内。链路成员：入库是源数据集本身；视图是主数据集为它的 View；
  因子是源数据集在该周期下的因子任务对应的结果数据集（Monitor 向 Storage 列出属性 `dataset_role=factor_result` 且 `source_dataset_id` 为该源数据集的结果数据集，
  一个源数据集可以有多个任务；请求带 `task_id` 时只看该任务，不带且有多个任务时响应列出 `tasks` 让页面选择；没有因子任务的链路没有因子环节）；因子视图是主数据集为
  因子结果的 View；策略的输入在运行时解析、Monitor 拿不到，按同空间同周期列出。每个点给出收线时间、延迟（写完时刻 − 收线时间，按交易日历算收线）
  和跳过的根数（按交易日历数，午休、隔夜、节假日不算）；超出 7 天保留期的日期标出 `retention_truncated`。查询在 SQL 里只读这条链路的成员，
  开盘时间往前多读两个周期（至少一天，覆盖小时线、日线、周线、月线在这一天收线的那根）；超过一次 5 万行的上限时标出 `truncated`。
- **页面**：数据链路卡片右上角“表格 / 曲线”切换（按钮加大、选中为实心主色）。曲线视图选链路和日期（标明时区，可选今天及之前 7 天），
  每个环节一条线，横轴是收线时间（按市场时区标注），纵轴是到达延迟（秒，上限包住允许迟到，至少 0～10 秒），虚线是允许迟到，
  超过的点标红、补数据跳过处标橙；不做动画（页面每 30 秒刷新会重画）。时间范围分“1 小时 / 3 小时 / 全天”三档：分钟级链路默认 1 小时
  （锚点前 45 分钟、后 15 分钟），小时线及以上一天至多 24 根，默认全天。锚点看今天时是当前时间，看历史日期时是当天延迟最大的那一根，
  跨天的部分以当天的界限为准截掉；可前后挪动（1 小时档每步 30 分钟、3 小时档每步 1 小时，锚点不出当天，“回到默认”恢复跟随），
  切换档位时锚点不变。刻度 1 小时档 5 分钟一格、3 小时档 15 分钟、全天 2 小时；只画范围内的点。链路这一天没有记录时也画出空的坐标；
  悬停显示收线时间（带时区）与各环节延迟；下方逐环节汇总全天的根数、中位与最大延迟、超过允许迟到与补数据跳过的根数。
  看的是今天时，页面每次刷新（30 秒轮询或点“刷新”）都重新加载曲线，跨过市场时区的 0 点自动跟到新的一天；看历史日期时不重复查询。

## 4. 告警

- 没有告警规则表：失败、恢复阈值与级别都由检查 ID 在代码里推出（`internal/checks/rule.go` 的 `RuleFor`、`Severity`，关注项的级别由生产者给出），告警状态记在检查表的同一行，每次触发、提醒、恢复与推送失败记录到 `t_monitor_alert_events`（事件带标题与级别，检查删除后告警经过与静默汇总仍能显示）。
- 推进是纯函数（`checks.Step`）：失败计数达到阈值触发；告警中每 5 分钟提醒；通过（含 degraded）计数达到阈值恢复。一轮的更新、删除与事件在一个事务里写入，提交后再逐条推送。
- 通知渠道保存在 `t_monitor_notification_channels`，可以有多个（同一个 URL 不能重复），告警发给全部渠道。类型有四种：

  | 类型 | 地址 | 密钥（选填） | 说明 |
  | --- | --- | --- | --- |
  | `wecom` 企业微信 | `qyapi.weixin.qq.com` 的群机器人地址 | 不使用 | markdown 消息 |
  | `feishu` 飞书 | `open.feishu.cn` 等飞书域名的群机器人地址 | 机器人“签名校验”的密钥 | 文本消息 |
  | `dingtalk` 钉钉 | `oapi.dingtalk.com/robot/send?access_token=…` | 机器人“加签”的密钥 | markdown 消息；每条消息的标题和正文开头固定带“MooX”，机器人的安全设置选“自定义关键词”时把关键词设成 `MooX` |
  | `webhook` 通用 Webhook | 任意公网 HTTPS 地址 | 签名密钥 | POST 固定格式的 JSON，返回 2xx 算送达 |

- **飞书**：机器人开了“签名校验”时填它的密钥，请求体会带上秒级时间戳 `timestamp` 与签名 `sign`（以“时间戳 + 换行 + 密钥”为 HMAC-SHA256 的 key、对空内容求摘要再 base64）。飞书要求时间戳与当前时间相差不超过 1 小时，主机时钟偏差过大会验签失败（返回 `code` 19021，记为发送失败）。
  已有的飞书渠道如果事后在飞书里打开了“签名校验”，原渠道立刻发不出去；同一个地址不能重复添加，要先删掉再带密钥重新添加。
- **钉钉**：启用加签时，按钉钉的规则给地址加上 `timestamp` 与 `sign`。钉钉拒收（关键词不符、签名不对、限流）时 HTTP 仍是 200，以返回体的 `errcode` 为准，不为 0 记为发送失败，`errmsg` 写进“推送失败”事件。
- **通用 Webhook**：请求体是 `{"key", "severity", "title", "body", "labels", "sent_at"}`（`severity` 取 `info`、`warning`、`critical`，`sent_at` 是 UTC 时间）。
  没有单独的“触发 / 恢复”字段，从标题和正文里看，和群里收到的内容相同。配了密钥时带两个请求头：
  `X-MooX-Timestamp`（毫秒时间戳）和 `X-MooX-Signature`（`sha256=` 加上以密钥对“时间戳 + `.` + 请求体”做 HMAC-SHA256 的十六进制）。
  只向公网地址发送：域名解析到内网、回环、保留地址时拒绝（`packages/netguard`），所以局域网里的接收方用不了；不跟随重定向，超时 5 秒。
- **密钥只写不读**：添加渠道时提交，`ListNotificationChannels` 只返回是否设置（`has_secret`）；要改密钥就删掉渠道重加。密钥随主机策略下发到各主机（见第 12 节），非控制机主机采集器的直推同样带签名；卸载前备份由仅允许 `moox-cli` 调用的 `ExportNotificationChannels` 导出，重装后恢复由仅允许 `moox-cli` 调用的 `ImportNotificationChannels` 按 `webhook_url` 幂等覆盖导入（两者均在 `gateway call` 禁用，仅供备份与重装恢复流程在进程内使用）。
  「消息通知设置」弹窗列出全部渠道（平台与完整 Webhook URL），可以添加、删除（`ListNotificationChannels` / `AddNotificationChannel` /
  `DeleteNotificationChannel`）。Webhook URL 本身就是推送凭据：列出渠道只允许全局管理员（`modules/admin/internal/console/policy.go`），
  增删是 monitor 的写方法，本来就只允许全局管理员；其他登录用户从健康概览只能看到渠道数量和平台，也看不到设置入口。
  全部删除后仍记录告警状态，只是不再发送。
- **送达规则**：至少一个渠道送达就算送达，失败的渠道记一条“推送失败”事件（写平台、域名和 URL 末 4 位），不按未送达重试，
  免得已收到的群每次重试都重复收到；全部渠道失败才按未送达在下一次评估重试（`internal/notifier`）。
- **推送地址在管理台配置**：告警渠道不在秘密文件 `moox.secrets.toml` 里填写，安装完成后在管理台「资源与运维 › 监控告警」的“消息通知设置”里增删；`moox-cli setup init` 与 `setup install` 会只读检查 `ListNotificationChannels`，若尚无渠道则在结束输出中给出管理台入口与未配置提醒，监控页面也直接展示未配置状态。清空重装时通过本机 `moox.backup` 自动备份与恢复。没有推送渠道时监控只展示不通知，应尽快补上。
- 告警文案由 `internal/alerttext` 统一生成，标题写明对象和问题，正文给出当前值和阈值。
- **外部检查有 60 秒宽限**：运行指标上报、采集计划对账、行情探针、数据集与 K 线新鲜度等外部检查每个周期评估一次，
  默认规则要求持续失败满 60 秒才告警（连续失败次数 = 1 + ⌈60 秒 ÷ 检查间隔⌉，30 秒间隔即 3 次），恢复仍是成功 1 次（K 线 2 次）。
  主机类检查不另加这 60 秒：失联与 host-agent 停报在停报满 3 分钟后才产生失败结果，失败一次即告警；
  资源检查每次采样一个结果，按连续采样次数告警（见第 2 节「主机类检查」）。
- 告警事件的 `c_payload` 记录结构化原因 `{"reason": ...}`，主机 CPU、内存告警另带 `metric` 与 `top_processes`；概览按它展示告警经过，不解析推送正文。
- **CPU、内存告警附带进程占用**：HostAgent 随主机快照上报占用最高的进程（见[主机代理](主机代理.md)）。CPU、内存阈值告警触发和重复提醒时，推送正文多一行“占用最高（进程 CPU 按单核计）：storage-primary CPU 340%、内存 5.1 GB；…”（CPU 告警按 CPU 排前 3，内存告警按内存排前 3），
  事件的 `c_payload` 里另存完整排行 `top_processes`（最多 10 个），进程事后退出或被杀掉仍能查到当时是谁占的。恢复通知和磁盘空间告警不带。主机监控详情页显示最新一次采样的排行。
  排行只保留最新一次，不能回看历史时刻；CPU 是一分钟平均，短于一分钟的尖峰会被摊平；同名的多个进程（例如几个 python）在正文里分不开，事件的完整排行里每项带 `pid`。整机使用率是全部核的百分比，进程的 CPU 按单核计，所以正文里会出现“整机 91%、某进程 340%”。
  进程名来自可执行文件名，脚本类进程只显示解释器的名字（python3.12、node），看不出跑的是哪个脚本。
  排行由检查事实的诊断信息带出（不入检查表），写触发、提醒事件时原样记进事件并在正文里列出前 3 个。
- 告警分级（`internal/checks/rule.go` 的 `Severity`，按检查 ID 判定，关注项按生产者声明的级别，**页面展示和推送用同一个结果**）：服务不可用（组件停止上报、未就绪、反复重启，主机网关也按这三类判断）、数据中断、主机失联为 `critical`（严重）；资源超阈值、只有 host-agent 停止上报、采集任务清单过期，以及生产者声明为 warning 的关注项（例如 `attention:collector:delist_readonly_key_missing`、`attention:collector:eastmoney_cooling_down`、`attention:admin:certificate_expiring`，业务检查显示 degraded“需关注”）为 `warning`（警告）；`moox-cli setup verify` 只把 critical 当成故障。

- **告警屏蔽**（`moox-cli monitor mute --for 3h --reason 初始数据导入`、`unmute`、`mute-status`）：给初始数据导入等会让数据链路告警暂时失真的操作用。
  屏蔽就是 Monitor 模块的生命周期暂停（`rpc/mute.go` 的 `MuteAlerts` 带 `ExpiresAt` 调生命周期，到期自动恢复），期间入库、告警评估与记录、首页聚合照常，
  只是发送器返回 nil、不推送（`bootstrap/lifecycle.go` 的 `alertSender`；推送只有告警评估这一个出口）。一次最长 24 小时，已在屏蔽中不能重复设置；
  系统暂停等别的暂停不算屏蔽，也不能被 `unmute` 解除。**静默结束时（到期、`unmute`、系统恢复）补发一条汇总**（`internal/checks/mute_summary.go`）：
  仍未恢复的告警逐条列出（含屏蔽前就在触发的），期间触发后又恢复的按检查项列出次数与时间范围，什么都没发生就不发。
  没有走 Monitor 的直推告警（非控制机主机采集器的两条直推）不受屏蔽影响。

### 检查表的已知差别

- 对象移除（停用、删除、配置关闭）时，在告警的检查推一条“已恢复”（原因“已停用或移除，不再检查”）并删行；这条恢复推送失败只记“推送失败”，不重试（行已删）。
- 对象再次出现时从零计数：短时间内删了又建的对象会先恢复再重新计数。
- 探针读 Storage 出错时产出 `storage_unreachable` 失败事实，按普通检查连续 3 轮告警；只有 Storage 标签列表读不到时探针域整轮报错、本轮不推进，探针与标签检查全部保持原状态，既不新增告警也不恢复，直到下一轮成功。
- 关注项的 detail 只写对象与起始时刻，推送正文不再有“已中断 N 分钟”“约 N 分钟”，持续时长看正文里的“已持续”（由触发时间算出）。
- 截止拒绝、因子水位、推送心跳由按空间各一项合成每个生产者一项，detail 列出对象；多个对象先后出问题只触发一次，后来的出现在提醒正文里。
- 截止拒绝的记录在 storage-primary 内存里，重启后告警提前恢复；截止拒绝的 detail 写数据集 ID，不再是数据集名称。
- 推送心跳：切回 SCF 后不再告警；有推送数据集但 collector-stream 从没启动过的空间会告警（以前不报）。
- 页面不再显示已停用的检查；页面的业务检查是上一轮评估的结果（最多晚 30 秒）。
- 推送正文去掉了“建议”行（检查描述一直没人写，实际从未出现）。
- 检查结果历史不再保存：要看一项检查的经过只有告警事件（触发、提醒、恢复、推送失败）。
- 生产者声明为 warning 的关注项失败时照常按 warning 级别告警、推送，业务检查显示“需关注”（与改前相同）。
- 余额同步、采集计划协调、推送连续缺失、投递积压、View 索引文件、策略参数投递、外部程序在线、归档任务与对象存储都由生产者判断后上报关注项，Monitor 只读结果；生产者停报时这些关注项随组件“停止上报”冻结，不推假恢复。
- 余额同步按账户判断：还没成功过、失败不到 3 次的账户先不报（以前算“尚未上报”的失败）。采集计划协调与推送连续缺失的状态在 Collector 内存里，Collector 重启后要等第一次对账、第一期上报才重新判断。
- 关注项没有“不知道”这个值：生产者重启后先报 0（心跳判断的启动宽限、空的协调状态、清零的缺失期数、清空的截止拒绝记录），重启前在告警的会先推一条“已恢复”，再次看到问题时重新触发。
- 推送失败不让整轮评估失败：失败记成“推送失败”事件、行改成待重发，只写日志。
- Collector 启动后一个超时（默认 180 秒）内推送心跳关注项报 0：重启 Collector 时，重启前在告警的心跳中断可能先推一条“已恢复”，超时后再次判断仍中断就重新触发。
- 服务仍在上报、但某个数据集自己的指标序列过期时，这项数据集检查不再产出、当轮删除，在告警的推“已恢复”（与改前相同）；这种情况由 K 线新鲜度与 `view_follow_lagging` 覆盖。
- 关注项按（服务名, kind）分组、取最近一次上报的那条：同名服务多个实例上报同一种关注项、一个为 1 一个为 0 时，检查会随上报先后来回翻（失败、恢复交替推送）。现在每个服务只部署一个实例，碰不到；以后同名服务多实例部署时要先给关注项带上实例区分。

## 4a. 重要日志

不登机器就能看到各服务的错误。

- **哪些算重要日志**：Error 及以上级别的全部日志；以及代码里用 `logsink.Important` / `logsink.Audit` 写出的关键事件，目前是两类：
  进程启动（`process_started`，带版本和启动号）、生命周期审计（`lifecycle_pause`、`lifecycle_resume`、`lifecycle_release`，含告警屏蔽）。
  Info、Warn 不进库，在本机文件里（启用了 CLS 上报时，Warn 也在 CLS 里）。
- **怎么到 Monitor**：各服务的 tRPC 日志多了一个输出 `moox`（`packages/report/logsink`），和配置里的 `file` 输出并存。它由代码加上，**不写在 `trpc_go.yaml` 里**：
  服务的 `main` 空白引入 `packages/clsreporter/logcls`，进程按配置装配默认日志时就自动带上这一项，配置文件里不能出现 `writer: moox`（契约脚本会检查）。
  依赖 `packages/report` 的组件 `main` 漏了这个引入时，report 不接日志、这个组件的重要日志全都不进库：`scripts/check/check-report-logcls.sh`（随 `make test-quality-gates`）逐个检查，命令行与一次性工具列为例外。
  重要日志先进一个最多 256 条的内存队列，后台每秒（或满 50 条）发一个事件 `event.observability.log.reported` 到 `MOOX_OBSERVABILITY`，
  用指标上报的同一份地址和凭据（`metrics-publisher` 账号），但另开一条连接。Monitor 消费后写进 `t_monitor_log_records`。
  Monitor 自己的日志不绕 EventBus，直接批量写库。写日志的调用只做一次不阻塞的入队；队列满了就丢并计数。
- **同一处反复报错**：同一个代码位置每分钟最多进库 10 条，多出来的只计数，下一分钟的第一条带上“此前另有 N 条被合并”。循环报错时库不会被刷满，完整记录在 CLS 和本机文件里。
- **去重与保留**：记录号是“实例 | 启动号 | 序号”，重复投递只留一条（必须带启动号，进程重启后序号从头开始）。`data_cleanup.timer` 删除 30 天前的记录，总行数超过 20 万时从最旧的删起。
  时间戳偏离入库时间超过 24 小时的记录按入库时间保存。
- **在哪看**：管理台“资源与运维 › 日志中心”的“重要日志”页签；`moox-cli monitor logs --component storage-primary --level error --from 2026-11-12T00:00:00+08:00`。带关键字又没有给起点时只查最近 7 天（关键字要逐行匹配，不走索引）。
  页面按时间范围查（最近 24 小时、7 天、30 天），列表上方是按时间的条数分布（错误与关键事件分开计），点一根柱子只看那段时间；日志详情里可以直接看同一主机上这个组件前后 5 分钟的记录（不带级别和关键字筛选）。
  分布由 `QueryLogRecords` 的 `with_buckets` 一并返回（按小时统计，没有给起点时只统计最近 7 天）。
- **接入范围**：创建了指标上报（`report.NewHandler`）并使用 tRPC 日志的服务：admin、archive-mgr、collector、collector-stream、eventbus、factor-mgr、monitor、storage 的两个进程（storage-primary、storage-view）、strategy、trade。
- **CLS 上报**（可选）：`moox.toml` 的 `[logging.cls]` 启用后，上述服务把不低于 `min_level`（默认 `warn`）的日志和全部关键事件另外上报到 CLS 的主题 `moox-service`（后台每 2 秒或满 500 条一批，失败丢弃不重试）。
  默认不上报 Info：Storage 等服务逐条处理的 Info 日志量是其余日志的十倍左右。日志保留天数取 `[logging] retention_days`（默认 2）。费用见部署文档，每个主题每月约 1 元多。
  部署时写进各组件运行环境的是 `MOOX_LOG_CLS_*`，和云函数采集日志用的 `MOOX_CLS_*` 分开。配置步骤见[部署与运维](../部署与运维.md)。
- **进程里能看到的计数**（各服务自己的 `/metrics`）：`moox_logsink_records_total{path}`、`moox_logsink_dropped_total{path,reason}`、`moox_logsink_merged_total`；
  Monitor 另有 `moox_monitor_log_records_total{result}`（`stored`、`duplicate`、`failed`）。

已知的限制：

- **没有覆盖的进程**：主机网关、出口代理、HostAgent、`moox-cli`（含导入命令）、factor-engine、archive-worker、云函数。它们的日志仍在本机（云函数仍上报 `moox-application`）。
- **标准输出里的内容不上报**：崩溃信息（panic）、数据库（GORM）语句日志只在 journald 里（`moox-cli setup logs --host <主机> --component <组件> --journal`）。
- **启动很早就失败的错误不进库**：服务在创建指标上报之前就退出时，重要日志还没有接收方，这些错误只在本机文件里。创建之后的失败走 `Fatalf`，退出前会先把队列发出去。
- **可能丢**：EventBus 不通时这一批直接丢弃、不重试；Monitor 自己的日志直接写库，最多等 30 秒（刚启动时数据库连接被启动查询占着），仍写不进去才丢弃；进程崩溃前最后一两秒的日志可能来不及发出。以本机文件为准。
- **不根据错误日志告警**：重要日志只用于查看，服务是否健康仍由现有的检查判断。
- **部署变更没有做成关键事件**：Monitor 的部署同步每分钟都会记一条“更新了 N 项检查”，分不出真正的变更，没有接入。
- **CLS 上报是明文 HTTP**（腾讯云 SDK 写死，云函数现在也是这样）：日志里不要写密钥和完整的 Webhook 地址。
- **文件日志只留最近一段**：各服务的 tRPC 文件日志在 `<部署根>/logs/<组件>/trpc.log`，按大小轮转（50MiB×5）。

## 5. 管理接口

`MonitorMgr`：

| 方法 | 说明 |
| --- | --- |
| `GetHealthOverview` | 健康总览：服务、主机、数据集、告警 |
| `ListNotificationChannels` / `AddNotificationChannel` / `DeleteNotificationChannel` | 通知渠道（列出含完整 URL，不含密钥，仅全局管理员） |
| `ExportNotificationChannels` | 导出全部通知渠道（含完整 URL 与签名密钥），供卸载前备份使用；只允许 `moox-cli` 调用 |
| `ImportNotificationChannels` | 批量导入通知渠道（`channel_type`、`webhook_url`、`secret`），按 `webhook_url` 幂等覆盖，返回 `created`、`updated` 条数；只允许 `moox-cli` 调用 |
| `ListHostAgents` / `QueryHostMetricHistory` | 主机列表（含在线判定 `reachable` 与主机资源告警阈值）与资源历史 |
| `QueryPipelineArrivalHistory` | 数据链路一条链路某一天各环节逐根 K 线的到达延迟（曲线视图） |
| `QueryLogRecords` | 重要日志：各服务的 Error 及以上日志和关键事件，新的在前，可按主机、组件、级别、关键字、时间筛选，`before_id` 向更早翻页 |
| `SyncHostAgent` | 主机代理同步：各主机的 HostAgent 每分钟上报主机快照并拉取全部通知渠道缓存到本机；Monitor 评估停滞时返回失败（见第 12 节）。只允许 `host-agent` 调用 |
| `MuteAlerts` / `UnmuteAlerts` / `GetAlertMute` | 告警屏蔽（只停推送，到期自动恢复，最长 24 小时）；`MuteAlerts`、`UnmuteAlerts` 只允许 `moox-cli` |

接口里的时刻（创建、触发、恢复、上报、检查、“自从”、收线、日志时刻，以及 `QueryLogRecords`、`QueryHostMetricHistory` 请求里的 `start_at`/`end_at`）
都是 int64 Unix 毫秒，0 表示没有；JSON 里是十进制字符串。`HostReport.collected_at`、`SyncHostAgentRsp.monitor_started_at` 也是毫秒。
例外是 `HealthDataset` 的 `input_watermark_at`、`output_watermark_at`、`expected_bar_at`：它们是 K 线的 `data_time`（开盘时间）文本，
与 Storage 行键同一口径；同一个消息里的 `latest_bar_close_at`、`expected_bar_close_at`、`waiting_since` 是按交易日历算出的收线时刻，按毫秒给。
`QueryPipelineArrivalHistory` 的 `day` 是市场时区的日历日文本。已知差别：时刻截到毫秒，原来带纳秒的告警经过 ID 等在同一毫秒内不再区分先后。

```bash
./scripts/build/build.sh monitor
```

Monitor 服务在 `internal/bootstrap/bootstrap.go` 启动时直接应用内嵌 schema，没有单独的建表命令。

## 7. Storage 调用身份与生命周期

数据集元数据（有效标的、展示名称）、行情金丝雀、标的标签巡检（成员统计读 Storage；同步的上次运行时间、结果与错误读 Collector 的 `ListTagSyncStatus`，没有运行记录的按“同步过期”，周期取标签属性 `sync.cron`、`sync.timezone`）统一使用进程持有的 `gatewayclient`。配置顶层的 `gateway_client` 声明 `caller: monitor` 与本机的主机签名私钥 `key_file`；密钥路径相对模块配置文件。主机 ID、本机入口与私有 CA 由部署写进同一段，目录缓存保存在 Monitor 数据库目录的 `gatewayclient/directory.json`。启动时校验身份与私密文件，关闭时先取消后台任务，再释放客户端和数据库。

Storage 没有调用方密钥，访问控制由主机网关按服务目录做；Monitor 对 Storage 只读，服务目录不给它任何写方法。只读重试、nonce 与目录刷新由共享客户端控制，业务调用不叠加 tRPC 重试过滤器、不指定目标。主机快照与服务指标都不写 Storage；配置加载拒绝未知字段、重复键和额外 YAML 文档。

Collector 任务清单与 SysDeploy 调用复用同一客户端。Monitor 只调用 `GetCatalog`、`ListHosts`、`ListDeployments`，并校验 Admin 给的服务目录与自己内嵌的逐字节一致，不一致就不更新拓扑。`moox-cli doctor` 的 Monitor 查询与部署查询用命令自己持有的网关客户端。

## 8. 组件健康：只看上报

组件健康只有一种来源：组件自己的上报。Monitor 不探测任何组件的健康端口，也不经控制机中转去连只能出站的主机；
`internal/deployment` 只把 Admin 里登记的主机与部署（每台主机应该有哪些组件）整份校验后存进 `t_monitor_topology`，
获取失败或记录无效时保留上一份拓扑，不生成任何检查。

每个组件每 30 秒经 EventBus 上报一份快照（`packages/report`），快照里除了指标还有两组字段（`packages/metricspb` 的 `MetricReport`）：

- 就绪判断 `ready` 与未就绪原因 `not_ready_reason`：与组件自己 `/readyz` 用的是同一个判断函数（`healthz.Readiness`）。没有登记就绪判断的上报方（云函数）不带 `ready`，Monitor 不按未就绪处理。
- 模块级生命周期 `lifecycle`：三态（运行、暂停、恢复追赶）、暂停类型与原因、暂停起始时间、追赶进度（是否追平、目标、已完成多少、被什么挡住）。首页的系统状态读它（第 11 节）。
- 启动标识 `boot_id`：部署注入了 `MOOX_BOOT_ID` 就用它，否则进程启动时生成一个随机值。Monitor 按它的变化数启动次数。

各组件的上报来源：

| 组件 | 上报来源 | 说明 |
| --- | --- | --- |
| host-gateway、admin、eventbus、monitor、collector、collector-stream、factor-mgr、archive-mgr、strategy、storage-primary、storage-view、trade、egress-proxy | `packages/report` | 自己上报指标、就绪与生命周期（有生命周期的：collector、strategy、trade、monitor） |
| host-agent | 主机快照 | 它发的主机快照算作它的上报，Monitor 按这台主机最近一次快照的时间判断；停报由主机类检查（`host:<host_id>:agent`、`presence`）告警，不另起停止上报检查；快照不带启动标识，不判断反复重启 |
| factor-engine | factor-mgr 代报 | 引擎只给 factor-mgr 发心跳，心跳里带它的就绪判断与模块级生命周期（`EngineRuntimeStatus` 的 `ready`、`not_ready_reason`、`lifecycle`）；factor-mgr 在自己的上报里多带一行（`delegated`），时间取最近一次被接受的心跳。Monitor 按组件名把它对到 factor-engine 唯一的部署上。停报由“因子引擎在线状态”检查告警，不另起停止上报检查 |
| archive-worker | archive-mgr 代报 | worker 只给 archive-mgr 发心跳，心跳被接受即算就绪；停报由“归档 worker 在线状态”检查告警。心跳不带启动标识，不判断反复重启 |

组件状态（`internal/observability/services.go`）：有上报且就绪为正常；上报了未就绪为异常（原因写“未就绪：……”）；超过无数据时限没有上报为停止上报；
登记了部署却从没上报过也算停止上报，没有按 `functional_observability` 的豁免。已启用的部署停止上报或从没上报时，组件状态记为异常（`down`，与未就绪同级），
上报的新鲜度另记在上报状态里（中断、从未上报）：进程整个挂了不能比活着但未就绪显示得更轻，`setup verify` 也据此拦住没起来的组件。
`moox-cli doctor bootstrap` 的监控视角部分直接读取 `GetHealthOverview`（由 `observability.Builder.Services()` 产出），与页面、组件检查同一份结论，CLI 不再重复计算模块健康。生命周期只在上报新鲜时挂到组件上，停止上报的模块不会显示成它最后一次上报的暂停状态。
上报落在 `t_monitor_metric_services`：每个启动标识一行，`c_readiness`、`c_not_ready_reason`、`c_lifecycle_json` 取最近一次上报（重投递的旧上报不覆盖），`c_ctime` 是这个启动标识第一次上报的时间。

每个登记且启用的部署三条检查（`internal/checks/component.go`），都按外部检查的默认规则告警（持续失败满 60 秒），都是严重级别：

- 停止上报 `reporter:<host>:<component>`（“<组件>（<主机>）· 运行指标上报”）：只针对经 `packages/report` 上报的组件。无数据时限是 `metrics.no_data_intervals`（默认 2）个上报间隔，加上 60 秒告警宽限，启用后约 2 分钟没有上报就告警。
  上报方停止上报（本轮有它的这条失败事实）时，它的关注项、它上报的数据集检查保持原状态、不推假恢复，以这条“停止上报”为准；
  组件停用后这条不再产出，那些检查随之删除。关注项序列的过期截止比服务判定多放 30 秒，生产者刚停报的首轮不会先于这条把关注项删掉。
- 未就绪 `ready:<host>:<component>`（“· 就绪”）：上报新鲜时按上报里的就绪判断；停止上报期间保持原状态，由停止上报那一条说明。代报的因子引擎同样有这一条。
- 反复重启 `restart:<host>:<component>`（“· 反复重启”）：10 分钟内启动标识变了 3 次（即重启了 3 次；全新部署的第一次启动不算变化）。10 分钟内连续部署一个组件三次也会触发这一条，属于误报。

三类都依赖观测输入：Monitor 的观测消费者没连上，或刚重连 5 分钟内，它们和其他依赖观测输入的检查一起冻结（见 12.2），只由“观测输入”一项说明原因。
部署停用或删除后不再生成，已有检查当轮删除（在告警的推一条“已恢复”）；重新部署时新建、计数从零开始。

## 9. 主机网关状态

主机网关和其他组件一样只按组件上报判断（第 8 节的停止上报、未就绪、反复重启三类检查）：快照同步超过 90 秒网关就报未就绪，
所以“路由长期不同步”落在 `ready:<host>:host-gateway`。Monitor 不读 Admin 的网关状态，没有单独的网关检查。
主机在线判断（第 10 节）也取 host-gateway 的组件上报：采集代理停报时，网关仍在上报判“host-agent 停止上报”，网关也停报判“主机失联”。

已知差别：网关的组件上报经 EventBus。EventBus 不可达时四台网关的上报同时过期，页面上四台网关都显示停止上报；
组件检查与主机类检查这时都随观测输入一起冻结，只有“观测输入”一项告警，不会推四条网关停报；主机快照不经 EventBus，照常入库，
页面上的主机资源照常刷新，但这期间某台主机的采集代理也停了的话，页面会把它显示成“主机失联”而不是“host-agent 停止上报”。

Monitor 只有服务一个二进制（`moox-monitor`），没有模块自己的 CLI；schema 由服务启动时自己应用。表结构变了不写迁移：停掉 Monitor、删掉 `<部署根>/data/monitor` 下的库文件后再启动，通知渠道在管理台「监控告警」页重新添加（若走 `setup install --wipe` 会通过本机 `moox.backup` 自动备份与恢复）。

## 10. 部署反向对账

概览事实层按完整部署快照与指标目录对账，使用精确的主机 ID 和组件 ID；代报的外部程序不带主机，按组件名对到它唯一的部署上。组件发布方直接使用共享目录中的 ID，SCF 指标使用 `scf-collector`；目录中的外部 principal 不作为主机部署。

已登记的部署没有上报记录时为 `missing`，超过上报时限为 `stale`；稳定检查身份为 `reporter:<host>:<component>`，首次上报或更换实例不会创建另一条检查。停用部署仍保留登记和真实上报事实，但停止对应告警。

有近期上报但没有部署记录的进程进入独立的 `Unregistered` 事实集合；过期上报不作为仍在运行的证据。指标入口保留事件与快照校验，允许未登记进程进入目录供对账。首次完整发现之前不推断未登记；成功发现的空部署列表具有权威性，后续发现失败保留旧快照。目录读取有分页和总量上限，超限明确报错。

目录清理保留每条登记部署最后一次上报，清除其多余旧 boot 和退役实例，防止离线部署被误标为“从未上报”（代报行不带主机，引擎离线超过 24 小时后它的旧行会被清掉，之后显示为从未上报）；首次发现尚未知时不清除 Reporter 历史。历史入库沿用报告产生时间，不用重投递时间刷新在线状态。

## 11. 健康概览 v2

`GetHealthOverview` 返回 summary、alerts、components、pipeline、business_checks、hosts、unregistered、notification。名称取自完整部署快照中的组件目录，按明确身份分组。对外状态为 healthy、degraded、down、unknown、disabled。组件状态只看上报，组件另带最近一次上报的就绪判断与未就绪原因（`readiness`、`not_ready_reason`）；状态起始时间保存在 `t_monitor_component_health`，由后台采样更新，未观测到的变化不伪造时间。

当前告警全部来自检查表里在告警的行（`c_alert_status = 'firing'`），包括主机资源阈值、主机失联与 host-agent 停报；概览不从主机事实另外投影失联告警。停报的边界为最后上报加三分钟，停用主机/Agent 部署不产生这两项告警。
主机卡片的状态与原因取同一处判断（`observability.Overview.HostPresences`）：主机失联显示异常，只有 host-agent 停报（网关仍在上报）显示需关注，原因文字与告警一致。选择空间仍保留全局告警。恢复阈值期间，最新检查时间与最近失败原因分别保留，原始错误与中文摘要同时返回。

HostAgent 只用 `host_id`（Admin 登记的主机 ID，由部署渲染进 HostAgent 的配置，必填）标识自己，Monitor 的主机登记、快照历史与主机类检查都以它为键，每台登记主机一行，重装 HostAgent 沿用同一行；`host_id` 不在登记里的上报不进入主机列表。hostname 仅展示，不用作关联。各资源项附可用标志，缺失资源不会作为 0% 展示。

概览同时返回：

- 当前告警的 `severity`、`recovering`（最近一次检查已通过、等待确认恢复）和数据集告警对应的数据集事实 `dataset`；告警标题取检查名称，与推送标题一致（主机类告警也有检查记录）；告警经过的标题与级别取事件里记下的，检查删除后照样显示。
- `incidents`：最近 48 小时（`incident_window_hours`）的告警经过，同一检查的“触发 → 恢复”归并为一条，带提醒次数与推送失败标记；触发早于窗口的从窗口外最近一次触发补齐；检查不再产出时有一条恢复记录，经过随之结束（`active=false`）。主机 CPU、内存告警的经过带上触发时记下的进程排行（`processes`，内存告警按内存排、CPU 告警按 CPU 排，最多 5 个），当前告警带最近一次触发或提醒时的排行，页面直接显示：进程事后退出了也能查到当时是谁占的。
- 数据集最新一根的收线与到达时间、延迟（`delay_seconds`/`delay_known`）、预期 K 线（`expected_bar_at`/`expected_bar_close_at`）、
  还在等待的根数、最早一根的收线时间与已晚多久（`waiting_bars`/`waiting_since`/`overdue_seconds`）、是否已由上报确认迟到（`late_confirmed`）、
  允许迟到（`lateness_limit_seconds`）、无法按日历判断的原因（`clock_issue`）和市场时区（`timezone`，加密货币 UTC、A 股 Asia/Shanghai、
  没有交易日历的系统数据 UTC）；生产者上报的数据集展示名称（`display_name`，例如策略实例名）。
- 主机的 CPU/内存/磁盘告警阈值与资源总量（CPU 核数、内存总量与已用量、使用率最高的那个文件系统的总量、已用量和挂载点）、业务检查的检查名称；
  业务检查列表读检查表（上一轮评估的结果，最多晚 30 秒），不含主机、组件、数据集三类（它们在各自的栏里）；已停用或移除的检查已删除，不再显示。

**生命周期与系统状态**：各模块随上报带模块级的生命周期状态（运行、暂停、恢复追赶；暂停详情与恢复追赶进度，见第 8 节；因子引擎由 factor-mgr 代报）。
Monitor 取最近一次新鲜上报里的这一组，直接复用 `commonpb.LifecycleSnapshot` 投影到 `HealthComponent.lifecycle` 字段，并由 `healthview/system.go` 汇总成概览的 `system`（严格按上报新鲜度区分停报/崩溃与正常暂停，不会将停报或崩溃的模块误算为“已暂停”），有两个维度：
- **健康面**：计入系统健康汇总的模块（采集、因子管理、因子引擎、归档管理、策略、Trade、Monitor）停止上报（或从没上报过）、或上报了未就绪时，系统标红并列出模块与原因（「策略服务：停止上报」「策略服务：未就绪（出站 EventBus 未连接）」），
  横幅写「有模块停止上报」「有模块未就绪」（两者都有时写「有模块未就绪或停止上报」）。Strategy 自检不过但进程仍在上报时显示未就绪；`factor-mgr` 与 `archive-mgr` 不参与运行阶段汇总，仅计入健康面。
- **运行阶段**：系统暂停覆盖的模块（采集、因子引擎、策略、Trade）全部暂停时显示「已暂停」，部分暂停时显示「部分暂停」，并列出暂停的模块与原因。
  有模块在恢复追赶时显示「恢复中 · 追赶 n/m 个模块」，全部追平后显示「已追平，待放行」，并列出各模块的进度与阻塞原因。
- 首页另读策略实例的确认列：有挂了账户、还没确认实盘的启用实例时，在运行中后面标出「n 个实例试运行」。

首页横幅显示这一行（`web/src/views/home/`）。

前端页面与 API 为 `web/src/views/ops/monitor/`、`web/src/api/monitor/`，按“值班排障优先”组织：顶部一句话结论（告警 / 需要关注 / 全部正常 / 数据不可用），
其下是当前告警（持续最久的在前，同一分钟内触发的合并为一组并提示可能同因），再是最近 48 小时的告警经过（1 分钟内自愈的闪断默认折叠），
最后是组件、主机、数据链路、业务检查四层健康，各占一整行：组件按主机列出名称与状态，主机卡片横向排列、资源条带告警阈值刻度并标出总量，
数据链路依次是采集 → 入库 → 视图 → 因子 → 策略计算 → 交易（入库是 Storage 写入水位，视图是 View 提交水位，分成两个环节），
表格按环节分组，每组标题写数据集数量与需要关注的个数，每个数据集显示最新K线、预期K线、到达延迟（上面的几种状态）与允许迟到，
K 线时间按市场时区显示并带时区标记（例如“18:54 UTC”“09:31 UTC+8”，告警里的数据集事实同样如此）；可切换到曲线视图看某一天逐根的到达延迟；
数据链路与业务检查只列出需要关注的项，可展开全部。首页的数据新鲜度用同一套后端字段：应收的最新一根已到写“已追平”，否则写已等待多久。
数据集 ID 用存储元数据翻译成名称；后端输出中文摘要，原始错误可展开；刷新失败保留旧数据并标出错误，不显示绿色正常结论。

## 12. 告警覆盖与高可用

这一节说明 MooX 出了哪些问题会通知到人、通知链路本身的可用性，以及仍然存在的盲区。
进程的拉起只靠 systemd 用户服务；主机上没有另外的守护程序。

### 12.1 覆盖的故障

| 故障 | 发现方式 | 判定条件与通知时间 |
| --- | --- | --- |
| 组件进程挂了或卡死 | 进程退出时 systemd 用户服务 5 秒后拉起（`Restart=always`），主机重启后靠 linger 开机拉起；卡死不退出的不会被自动重启，要人来重启；Monitor 按组件上报判停止上报与反复重启（第 8 节） | 进程自动拉起、主机重启都不单独推送；持续起不来或卡死时报“停止上报”，启动标识频繁变化时报“反复重启” |
| 组件活着但持续未就绪 | 组件上报里的就绪判断（与它的 `/readyz` 同一个） | Monitor 的“· 就绪”检查持续失败满 60 秒告警 |
| 组件反复重启 | 组件上报的启动标识：10 分钟内变了 3 次 | “· 反复重启”检查，持续失败满 60 秒告警 |
| 组件停止上报 | 已登记的部署上报缺失（从没上报过也算）或过期 | 超过上报时限后，再持续失败满 60 秒（外部检查宽限），严重 |
| 控制机或 Monitor 不可达、Monitor 评估停滞、Monitor 反复重启 | 非控制机的主机采集器每分钟经网关调 `SyncHostAgent`：连续 3 次失败（Monitor 启动满 3 分钟后，最近 3 分钟没有一次完整成功的检查评估或业务评估时，`SyncHostAgent` 也返回失败）；或响应里 Monitor 的启动时间 10 分钟内变了 3 次（Monitor 反复崩溃时每次拉起后都能应答几次，光看连续失败发现不了） | 由观测方直接推送（读主机策略缓存里的渠道），恢复后各推一条；不经过 Monitor。10 分钟内连续部署控制机三次也会误报一条“Monitor 反复重启” |
| 主机失联（宕机、断网） | HostAgent 每分钟上报快照，Monitor 3 分钟收不到、且该主机网关的组件上报不是正常 | 约 3 分钟（下一轮 30 秒评估），“主机 X · 失联”（严重），每 5 分钟提醒，恢复后同一标题的“已恢复” |
| 只有 HostAgent 停止上报 | 同上，但主机网关仍在上报 | 约 3 分钟，“主机 X · host-agent 停止上报”（警告），每 5 分钟提醒，恢复后同一标题的“已恢复”；之后网关也停报了，这条恢复、改报“主机 X · 失联” |
| 主机网关异常 | 没有单独的网关检查，按 host-gateway 的组件上报判断（第 9 节）：停止上报、未就绪（路由快照同步超过 90 秒）、反复重启 | 与其他组件检查相同 |
| 主机资源吃紧 | CPU 80%、内存 90%、磁盘 85%（HostAgent 每分钟采样） | 约 3、5、3 分钟（见第 2 节） |
| 主机磁盘写满风险 | 主机检查 `host:<host_id>:disk_forecast`（按近 7 天每日最晚快照的日增长率中位数估算耗尽安全余量（10% 且不少于 5 GiB）的剩余天数） | 预计不超过 7 天即告警（警告级，恢复线 10 天；历史不足 3 个自然日间隔时不告警） |
| 归档对象存储不可用 | worker 每分钟 HEAD 一个不存在的键，archive-mgr 每 30 秒判断后上报关注项 `attention:archive-mgr:object_store_down`（“归档对象存储不可用”） | 连续不可用超过 5 分钟；原因带最近一次失败原因 |
| 因子引擎、归档 worker 离线 | factor-mgr、archive-mgr 每 30 秒按最近心跳评估在线状态，离线时上报关注项 `engine_offline`、`worker_offline`（“因子引擎离线”“归档 worker 离线”） | 有启用的因子任务 / 归档任务时，2 分钟无心跳 + 上报与宽限，约 3.5 分钟；原因写明机器与最后心跳 |
| 归档任务异常 | archive-mgr 每 30 秒按各任务健康等级上报关注项 `attention:archive-mgr:task_failing`（“归档任务异常”，detail 列出空间/数据集） | 任务为“异常”（接近线上保留期仍没成功、累积过无法补齐的区间、分区登记被拒等）时，上报与宽限后约 1.5 分钟；“需关注”不通知 |
| 归档任务自动补齐失败 | archive-mgr 维护定时器每分钟从 Storage 列出全部数据集并为活跃、有限保留期的时序数据集补齐任务（停用的任务不重建），补不上时上报关注项 `attention:archive-mgr:task_ensure_failed`（“归档任务自动补齐失败”） | 读取 Storage 数据集清单失败，或有数据集因目录名冲突、频率不支持等建不出任务时，上报与宽限后约 1.5 分钟；问题解决后自动恢复 |
| WS 推送接收停了或持续缺标的 | Collector 的关注项 `stream_heartbeat_lost`、`stream_periods_missing` | 心跳中断 3 分钟；连续 3 个周期有失败标的（疑似下架不计） |
| 因子水位卡在缺数据的周期 | factor-mgr 导出的任务阻塞起始时间 | 阻塞超过 30 分钟 |
| 数据中断：采集、入库、视图、因子、策略任何一环停更 | 数据集新鲜度与 K 线新鲜度，按交易日历判断应到的最新一根 | 允许迟到 + 持续失败满 60 秒 |
| 行情异常 | 行情金丝雀、Timer 协调 | 持续失败满 60 秒 |
| 证书即将过期或无效 | Admin 证书巡检定时检查全部主机证书，通过 `moox_attention_active` 上报关注项 `attention:admin:certificate_invalid`（严重）与 `attention:admin:certificate_expiring`（警告） | 走 Monitor 统一检查表、页面展示与告警屏蔽/推送流程，持续失败满 60 秒告警 |

**通知节奏**：所有告警（含主机失联、host-agent 停报、主机资源阈值）走同一条路径：首次推送“新告警”，持续未恢复按规则的提醒间隔（默认 5 分钟）推送“仍未恢复”，恢复推送“已恢复”。
新告警与提醒的级别就是这条告警自己的级别（严重或警告，与概览里显示的一致），恢复是“提示”。
设计告警量和验收预期时按这个节奏算，而不是“只通知一次”。

数据链路检查是端到端的兜底：即使某台机器或某个组件没有被直接监控，它停摆后，下游数据集按时没有新数据也会告警。

### 12.2 通知链路的可用性

- **两条独立的推送路径**：Monitor 发出数据、主机、组件、业务类告警；非控制机的主机采集器（控制机或 Monitor 不可达、Monitor 反复重启两条）直接调用通知渠道（企业微信、飞书、钉钉、通用 Webhook），不经过 Monitor 与 EventBus——
  挂掉的可能正是 Monitor 所在的 control 或 EventBus 所在的主机。
- **观测输入中断时冻结判定**：Monitor 自己的 EventBus 观测消费者没连上（含运行中连接断开、客户端还在重连的时候；或刚重新连上的 5 分钟宽限内），服务指标（含各主机网关的组件上报）的 last_seen 都是旧的，
  这时判“已停止上报”只会整批误报。依赖观测输入的检查（组件的停止上报、未就绪、反复重启，数据集新鲜度、K 线新鲜度、业务检查、模块健康、主机类检查）全部冻结——既不新增告警，也不恢复已有告警——
  只留一项“观测输入”检查说明原因。主机快照经 `SyncHostAgent` 直达、不经 EventBus，照常入库，但主机类检查要用网关的组件上报判断在线，同样冻结（第 9 节）；K 线新鲜度的视图摘要同样经 EventBus 入库，快照超过 1 分钟后会退回按当前时间判逾期，因此一并冻结；只有行情探针（直读 Storage）与标签巡检这类在探针域、不依赖观测输入的检查照常判定。
  连接断开由 EventBus 客户端的断开与重连回调得知，断开即冻结；“观测输入”这一项和其他外部检查一样有 60 秒宽限，几秒内重连的抖动不会告警，但重连后同样进入 5 分钟宽限。连接反复短断（每次短于 60 秒、间隔小于 5 分钟）时这些检查会持续冻结而“观测输入”自己不告警，这段时间只剩行情探针与标签检查照常判定。
- **Collector 暂停时不评估采集结果**：Collector 模块处于暂停或恢复追赶（按它最近一次新鲜上报带的生命周期）时，采集是有意停下的，“K 线结果”（`kline_freshness:`）与“行情探针”（`market_canary:`）两类检查本轮不评估、保持原状态；放行后恢复评估。
- **告警渠道单一来源**：渠道只在 Monitor 的通知渠道里维护（控制台“消息通知设置”，清空重装经 `moox.backup` 备份恢复）。
  每台主机的 HostAgent 每分钟经网关调用 `SyncHostAgent`，把全部渠道写进 `<部署根>/data/host-agent/host-policy.json`（0600）；拉取失败时保留旧文件。
  第一次拉取成功之前这台主机没有渠道，直推发不出去。各主机缓存的版本与拉取时间在各主机的策略缓存文件里。
- **多渠道**：告警发给全部通知渠道，至少一个送达就算送达；全部失败才在下一次评估重试，单个渠道失败记一条“推送失败”事件。推送失败的报告里不带出 Webhook。
- **防闪断**：外部检查持续失败满 60 秒才告警，避免服务重启时的闪断刷屏；持续未恢复每 5 分钟提醒，恢复通知一次。
- **告警历史可追溯**：每次触发、恢复、推送失败都写入告警事件表，监控页展示最近 48 小时的告警经过；进程被 systemd 拉起的次数看 `systemctl --user show moox-<组件> -p NRestarts`。

### 12.3 仍然存在的盲区

| 盲区 | 说明 | 兜底 |
| --- | --- | --- |
| control 主机还在，但 Monitor 失效而控制机网关还能转发 | 别的主机调 `SyncHostAgent` 连续失败会推送；评估停滞时 `SyncHostAgent` 返回失败，同样会推送；Monitor 评估在跑、但别的地方卡住且还能应答时发现不了 | 可选：在腾讯云配置云拨测探测控制台，作为不依赖本系统的外部检查 |
| 所有主机同时断网，或推送服务本身不可用 | 两条推送路径都发不出去 | 恢复后告警事件表仍可追溯 |
| Monitor 进程活着，但检查评估停住（例如检查结果写库失败、业务评估整轮失败），而且只有控制机一台主机 | 首页与告警停在最后一次评估的状态；Monitor 的 `/readyz` 因评估超过 3 分钟没完成而未就绪，`SyncHostAgent` 返回失败。有非控制机时由它们的 HostAgent 推送“控制机或 Monitor 不可达”（标题不区分不可达与评估停滞，原因在 HostAgent 日志的同步错误里）；只有控制机一台时没有观测方，这里没有告警 | 收到这条推送而控制机能连上，或页面、`doctor alerts` 的时间长时间不动时，用 `moox-cli doctor bootstrap --node control`（经 SSH 看 Monitor 的本机 `/readyz`）和 `moox-cli setup logs --host control --component monitor` 排查 |
| 只能出站的主机（192）与 control 的反向连接断开 | 中转链路没有单独的检查：因子机的实时链路（读行情、写因子、心跳、上报）全是它主动出站的，没有一条经过中转；经中转的只有人发起的操作（回放、导入、暂停恢复、归档下载、主机采集器查询），断了当场报错 | 网关自动退避重连 |

### 12.4 整体形态

```text
                 ┌──────────── control ────────────┐
 组件崩溃 ──► systemd 用户服务 5 秒后拉起（不推送；起不来由 Monitor 报停止上报）
                 │                                  │
 组件/数据/主机异常 ──► Monitor 检查（只看上报）──► 推送全部渠道
                 └──────────────────────────────────┘
 控制机或 Monitor 不可达、Monitor 反复重启 ──► 非控制机的 HostAgent ──► 直接推送
 外部程序离线 ──► factor-mgr / archive-mgr 在线状态与代报 ──► Monitor ──► 推送
 渠道修改（控制台）──► Monitor ──► 各主机 HostAgent 拉取缓存（≤ 1 分钟）
```

在 Monitor 正常运行、观测方及推送网络可用的前提下，上述路径覆盖主机失联、组件停摆、数据断流与外部程序离线；同时失效的边界见第 12.3 节。
