# 存储（Storage）

Storage 是 MooX 的事实存储与查询中心：保存行情、因子结果、系统指标等全部时序与记录数据，
维护空间、标的、标签、数据集等元数据，并为每个数据集提供可重建的查询 View。

代码位置：`modules/storage`。

## 1. 进程与端口

Storage 由同一个二进制按 `MOOX_STORAGE_ROLE` 启动为不同角色：

| 进程 | 角色 | 主要服务与端口 |
| --- | --- | --- |
| `moox-storage-primary` | Metadata + PrimaryStore | Metadata 原生 tRPC `20100`，PrimaryStore 原生 tRPC `20101`、`20102`，DataNode 管理 tRPC `20106`，健康 `20210` |
| `moox-storage-node` | DataNode | DataNodeRuntime tRPC `20107`，健康 `20212` |
| `moox-storage-view` | View | DataView 原生 tRPC `20103`，ViewIndex tRPC `20104`，健康 `20211` |

- **primary**：元数据的增删改查和校验；把写入请求按数据集路由到所属 DataNode。
- **node**：一个固定 `node_id` 的 Pebble 数据目录；负责字段写入、Outbox 事件、采集周期账本、
  过期数据清理。一个节点可以承载多个数据集，但每个数据集只属于一个节点，创建后不可更改。
- **view**：消费 Storage 事件，维护 DuckDB（时序）和 Bleve（记录）索引，提供查询。

SCF 和因子引擎通过独立的[外部接入模块](../../modules/access/README.md)访问，入口为 `moox-access`（见第 8 节）。

原生 `setup deploy-unit --profile storage` 当前要求三个角色同机，内部 RPC 走 loopback；
DataNode ID 固定为 `storage-node-0`，与默认 seed 及 Collector 一致。

系统不做数据集内分片、副本、选主或在线迁移；节点离线只影响它承载的数据集，
View 离线不阻塞写入，未消费的事件留在 JetStream 中。

## 2. 数据模型

### 2.1 元数据

元数据保存在 primary 的 SQLite（`schema/metadata.sql`，schema 版本 13），主要对象：

| 对象 | 表 | 说明 |
| --- | --- | --- |
| Space | `t_spaces` | 业务域：`crypto`、`stockcn`、`stockhk`、`stockus`、`mooxsys` |
| DataSource | `t_data_sources` | 数据来源（交易所、行情 API、内部系统等） |
| Subject | `t_subjects` | 标的（交易对、股票、主机等），带属性 |
| Tag | `t_tags`、`t_subject_tags` | 标的分组；自动标签由标的同步服务维护成员 |
| Dataset | `t_datasets` | 数据集：时序（time_series）或记录（record），绑定一个 DataNode 和保留期；时序数据集只有一个规范频率 `freq`，创建后不可修改 |
| FieldGroup / Field | `t_field_groups`、`t_fields` | 数据集字段，只增不删，类型不可改 |
| DatasetColumn | `t_dataset_columns` | 数据集的列定义（因子结果等需要的携带列） |
| View | `t_views`、`t_view_columns` | 面向查询的视图，只索引一个 Dataset；`freq` 由 Storage 按所属 Dataset 填写 |
| View 运维状态 | `t_view_index_builds`、`t_view_rebuild_logs`、`t_view_period_dataset_states`、`t_view_sync_points` | 索引构建、重建日志、周期就绪状态、同步点 |
| DataNode / Device | `t_data_nodes`、`t_storage_devices` | 节点注册与存储设备 |
| ArchiveFile | `t_archive_files` | Archive 写出的 Parquet 文件登记 |
| 标的修订号 | `t_space_revisions` | 按空间单调递增的 `subjects_revision`：标的（状态、属性、增删）、标签成员、标签市场类型、数据集（创建、删除、标的范围）变化时由触发器在同一事务内递增；`GetDataset` 响应带回，调用方用它判断缓存的标的元数据是否过期 |

`t_space_revisions` 与触发器全部 `IF NOT EXISTS`，不提升 schema 版本：已有库执行一次 `moox-storage-cli init` 即可补建。runtime 托管的 storage-primary 启动时不执行 init；整包发布由 setup 在候选目录内 init，增量换二进制用 `scripts/deploy/swap-storage-primary.sh <ssh 目标> <二进制目录>`（备份库 → 更新 schema → init → 换二进制 → 重启）。

数据集创建后为 disabled 状态，需要通过只读的激活检查后显式激活，激活后与 DataNode 的绑定锁定。
`factor_result` 角色的数据集在激活时自动维护默认 View。

命名规则见[元数据命名规范](../元数据命名规范.md)。

### 2.2 行身份

```text
时序：space_id + dataset_id + subject_id + freq + data_time(UTC) + series_tag
记录：space_id + dataset_id + record_id + version
```

- `series_tag` 是可选的不透明字符串，空字符串表示默认序列；推荐写成 `venue:binance` 这样的约定，
  Storage 不解析其内容。范围查询中“不设置”表示全部序列，“设置为空”表示只要默认序列。
- `data_time` 统一保存为 UTC、9 位纳秒精度。
- 写入是字段级 Upsert：可以新增、覆盖或补写历史行的某些字段，所有字段都允许缺失。
- 记录写入必须带 `version`；读取时不指定版本则取字节序最大的版本。

### 2.3 物理布局

DataNode 使用 Pebble，key 空间按用途分区：`0x01` 字段、`0x02` 属性、`0x03` 时序历史索引、
`0x04` 序列历史索引，另有 `__outbox/`、`__meta/` 等内部前缀。布局版本为 4，写在数据目录的
版本文件中，版本不符时拒绝启动。

时序数据的物理 key 把规范化的时间桶 `bucket_start` 放在数据集之后，过期清理可以按
`(space, dataset, bucket)` 做有界的 `DeleteRange`（不逐个读取 key），再异步 Compact 回收空间。

### 2.4 保留策略

保留期不由数据集各自声明，而是由 `moox-cli` 从 `moox.toml` 的 `[storage_retention]` 与 `[storage_view]`
渲染为策略 JSON。原生安装向各 Storage 角色的发布目录写入 `config/storage-policy.json`，
`storage.policy_file` 指向角色内副本；primary 与 view 使用同一策略内容，缺失或非法时拒绝启动。
旧平铺部署使用 `<storage_root>/config/storage-policy.json`，不能用该路径推导原生配置位置。

- 时序数据集的生效保留期按 `(space_id, freq)` 解析：空间配置优先，没有时用全局默认；全局默认覆盖
  全部规范频率，因此每个时序数据集都有确定的保留期。记录型数据集不过期。
- Metadata 的 `GetDataset`、`ListDatasets` 和 DataNode 列表返回只读的 `retention`（`<n>h` 或
  `forever`）与 `retention_source`（`default`、`space`、`record`）；写接口没有保留字段。
- primary 每小时清理一次：对每个活跃时序数据集计算 `cutoff = now - 保留期` 并按天桶截断，调用
  DataNode 的 `CleanupExpiredBuckets` 删除更早的行与历史索引。实际保留在保留期到多一天之间。
  `forever` 跳过。每次清理记录日志和指标 `moox_storage_dataset_cleanup_cutoff_timestamp_seconds`、
  `moox_storage_dataset_cleanup_duration_seconds`、`moox_storage_dataset_cleanup_failures_total`；
  DataNode 上报 Pebble 磁盘占用 `moox_storage_node_pebble_disk_bytes`。

## 3. 写入路径与事件

```text
调用方 ─► PrimaryStore（校验数据集、字段、类型）─► 按 (space, dataset) 分组 ─► DataNode
DataNode：一个 Pebble Batch 内写入 字段/属性 + __outbox/<id> + __meta/next_outbox_id
Outbox Relay：按 ID 顺序同步发布到 EventBus，失败即停止，只删除连续成功的前缀
事件压缩：信封不小于 4KB 时以 gzip 发布（content type 为 `application/vnd.moox.event+protobuf+gzip`），消费端经 `events.DecodeRaw` 透明解压。因子结果行事件每期约 300KB，Storage 与 EventBus 跨公网往返一次要近 1 秒，压缩后降到约 0.1 秒；新增消费端必须先于发布端支持解压
```

DataNode 发布的事件都在 `MOOX_STORAGE` Stream：

| 事件 | 含义 |
| --- | --- |
| `rows.upserted` v2 | 一次写入的变更行和变更字段（不是全量快照），Subject 精确到数据集 |
| `collector.period.completed` | 某数据集某频率的一个采集周期已终结（complete/degraded） |
| `dataset.factor_period.computed` | 因子结果数据集的某个周期已全部写完 |
| `dataset.sync_point` | 数据集同步点，用于等待 View 追上某个写入位置 |

## 4. 采集周期协议

DataNode 是“采集周期是否完成”的唯一权威，Collector 通过 PrimaryStore 调用：

| 方法 | 作用 |
| --- | --- |
| `EnsureDatasetPeriod` | 首次调用时固化该周期的完整序列快照（`series_snapshot`、hash、数量）和截止时间 |
| `CommitTimeSeriesBatch` | 写入行，返回被接受的序列编号；只有完整回执才算成功 |
| `RecordDatasetPeriodFailures` | 上报失败序列，逐个返回 `recorded`、`already_succeeded` 或 `missed_deadline` |
| `GetDatasetPeriodStatus` | 查询周期状态 |

到达截止时间后，DataNode 原子地把周期固化为 `complete` 或 `degraded`，并写入
`CollectorPeriodCompleted` 标记；标记里只包含截止前被接受且最终仍未成功的序列。删除或恢复
数据集时，其周期账本和索引一并清理。

## 5. 因子结果与同步点

- Factor 用 `WriteFactorRows` 一次写入一个周期的完整结果行（携带列 + 因子列），随后用
  `ReportFactorPeriodComputed` 写入 `FactorPeriodComputed` 标记；`GetFactorPeriodComputed` 用于查询。
- `AppendDatasetSyncPoint` 在数据集事件流中插入同步点，`WaitViewSyncPoint` 等待 View 消费到该点，
  供需要“写后读”的调用方使用。

## 6. View

### 6.1 索引与重建

- 一个 View 只索引一个 Dataset。View 列名就是 Dataset 列名，不带数据集前缀，`origin_id` 与列名相同；
  Metadata 写入 View 列时校验该列是所属 Dataset 的活跃列。按精确 Key 读 Primary 与按时间范围读 View
  使用同一套列名。
- 时序 View 使用 DuckDB 文件，主键为 `(subject_id, freq, data_time, series_tag)`；记录 View 使用 Bleve，
  支持全文检索。
- 每个 View 有 A/B 两份独立索引。触发重建时创建新索引并安装实时双写，从 Primary 回填历史，
  回填只填缺失值、不覆盖实时写入；完成后在 Metadata 中以 CAS 激活新 revision，DataView 原子切换，
  旧索引在宽限期后删除。新索引写入或回填失败只终止本次构建，旧索引继续服务。
- 时序 View 只按根数保留：每个序列保留最近 `view_bars` 根（默认 5000），超过 ceil(1.2 × N) = 6000 根时
  触发整理；周末和节假日不影响有效根数。根数由 `moox.toml` 的 `[storage_retention] view_bars` 统一配置。
- 重建回填先由 Primary 列出该频率下有数据的标的（`ListHistorySubjects`，在序列历史索引上逐标的跳跃），
  再对每个标的只发一次读取（`latest_per_series`）：DataNode 倒序读，每个 series_tag 读满目标根数就跳到
  下一个 tag。耗时只与「标的数 × 根数」有关、与历史长度无关，不依赖数据集是否绑定了标的标签。
  历史不足目标根数时以现有数据激活。记录型 View（Bleve）不按根数，从活跃索引整体复制。
- 文件超过 `max_view_file_bytes` 时：时序 View 触发容量重建，记录型 View 只告警不截断。
  仅由容量触发的重建要等 View 消费者积压足够小、连续空闲若干次后才开始。
- 每次实际重建或被门禁跳过都记录到 `t_view_rebuild_logs`。

### 6.2 事件消费

View 按数据集消费 `MOOX_STORAGE` 的事件：

| 消费者 | 范围 | 投递参数 |
| --- | --- | --- |
| `storage_view_metrics` | `mooxsys` 系统指标数据集（静态路由） | fetch 16，4 个 worker |
| `storage_view_misc_<hash>` | 其余每个数据集各一个（动态创建） | 来自 `misc` 分区模板 |
| `storage_view_factor_<hash>` | 每个因子结果数据集各一个（动态创建） | 来自 `factor` 分区模板：单并发、`max_ack_pending=1` |

- 静态分区和模板定义在 `config/storage.yaml` 的 `storage.view.consumer_partitions`。
- 动态消费者由 View 清单协调器根据当前数据集清单创建和回收，名称由数据集身份哈希得到，
  保持稳定。JetStream 消费者的过滤条件不可修改，因此通配分区不能跟随新数据集变化。
- 同一数据集的行、标记和同步点进入同一个有序队列，保证行先于标记应用；不同数据集并行。
  连续的行事件在不跨越标记的前提下合并为一次索引写入。
- 写入 Active 失败时保持当前投递并本地退避；Subject、Proto、负载等永久错误执行 `Term`。

### 6.3 就绪事件

View 应用 `CollectorPeriodCompleted` 或 `FactorPeriodComputed` 标记并确认该周期的数据都已进入
索引后，发布 `ViewDataReady`（携带 `completion_kind`、已提交位置和因子定义指纹）。Strategy 以此作为触发信号。

就绪事件先进入持久队列；发布失败按有界超时重试，行写入不会因发布失败而回滚。写入围栏记录每个索引
已应用的来源位置，当前按秒批量落盘。行事件可能在围栏落盘前已经 ACK，异常退出会丢失这段进度，
重启后相应就绪事件可能等待同一来源的后续写入；日线或停更数据集等待尤其明显。
该边界与建议见[代码审查](../审查/2026-10-10代码审查.md)。

### 6.4 DuckDB 资源与临时目录

每个时序 View 索引（每个 A/B 槽位）是一个独立的 DuckDB 实例，各自受 `memory_limit` 约束，所以一台主机上的总占用最多是「索引个数 × 单个上限」，不是一个全局上限。

**内存上限的默认值**：`moox-storage-view` 启动时按主机内存推算，取 1/16，下限 128MB、上限 2GB。在容器里取 cgroup 限制和物理内存中较小的一个；读不到主机内存（非 Linux 开发机）时用 256MB。
推算结果随主机规格变化，不需要在部署时手工填写：

| 主机内存 | 单个索引上限 | 说明 |
| --- | --- | --- |
| 2GB 及以下 | 128MB | 取下限；应显式配置更小的值或减少 View |
| 4GB | 256MB | |
| 8GB | 512MB | |
| 16GB | 1GB | 线上 Storage 主机（15480MB）约 967MB |
| 32GB 及以上 | 2GB | 取上限 |

- 为什么是 1/16 而不是更小：上限是天花板，不是预留。只有几 MB 的索引不会涨到天花板，主机上的实际占用约等于各索引文件大小之和再加重建时的峰值，
  不是「索引个数 × 上限」。上限应当按能装下最大索引在重建时的工作集来定。
  线上出现过一次：256MB 的上限在重建一个 211MB 的索引（历史回填、激活探测）时被顶满，报 `Out of Memory Error: failed to pin block`。
  索引文件超过 `max_view_file_bytes`（默认 1GiB）才触发容量重建，正常可以长到 1GiB，重建它需要约 1 到 1.5 倍文件大小的内存，所以上限放到 2GB。
- 线上现状作参照：Storage 主机 15.5GB，`storage-view` 进程约 550MB，最大的 4 个索引是 260 到 346MB，其余十几个各约 1MB。
- 启动日志会记录生效值和来源，例如 `storage view DuckDB 单个索引内存上限 967MB（主机内存 15480MB 的 1/16，…）`。
- 需要固定某个值时设置环境变量 `MOOX_STORAGE_VIEW_DUCKDB_MEMORY_LIMIT`（正整数加 `KB`/`MB`/`GB`/`TB`），显式配置优先于推算；留空等同未配置。原生部署不需要额外配置；`scripts/deploy/deploy-moox.sh` 的该变量留空即自动推算。
- 同时可用 `MOOX_STORAGE_VIEW_DUCKDB_THREADS`（1–8，默认 1）和 `MOOX_STORAGE_VIEW_DUCKDB_MAX_OPEN_CONNS`（1–64，默认 4）限制每个索引的线程和连接数。

**用量日志**：`moox-storage-view` 启动 30 秒后记录一次，之后每 5 分钟一次，读的是每个索引的 `duckdb_memory()`：

- 汇总行：`storage view DuckDB 资源 索引=17 内存合计=… 溢出临时文件合计=0MB 单个上限=967MB 进程常驻内存=… 内存最多：空间/View/槽位 …MB；…`，列出内存最多的 3 个索引。
- `storage view DuckDB 内存接近上限 index=…`：某个索引内存用到上限的 80% 以上，再大一点的重建或查询就会开始溢出，甚至 OOM。
- `storage view DuckDB 发生磁盘溢出 index=… 溢出=…`：该索引当前有数据写进了临时目录。
- 这两类提示行反复出现，说明上限偏小，应调大 `MOOX_STORAGE_VIEW_DUCKDB_MEMORY_LIMIT`；长期只有汇总行且内存远低于上限，说明有富余，不必调。
- 在容器或内存很小的主机上，对照“进程常驻内存”，确认索引合计加上其他部分没有逼近主机内存。

**临时目录的作用**：DuckDB 的内存超过 `memory_limit` 时不会报错，而是把暂时放不下的中间状态（排序、聚合、Join、检查点前的缓冲）写到 `temp_directory` 里的临时文件，需要时再读回。
它只是易失的工作区，已提交的数据在 `.duckdb` 主文件和 `.wal` 里；进程退出后临时文件没有用处，无人使用时可以直接删除。
临时文件名只包含块大小类别和序号（例如 `duckdb_temp_storage_S32K-0.tmp`），不含数据库名。

**每个索引用自己的临时目录**：目录固定为 `<索引文件>.tmp`（例如 `view_xxx_a.duckdb.tmp`）。
不能让多个索引共用一个目录：各实例的临时文件都从 `-0` 开始编号，同目录下会重名，一个实例清理时会删掉另一个实例正在用的文件，
那个实例的下一次提交就会失败，之后该索引一直写不进去（见下面的排障）。这个问题曾在线上出现过一次。

- 索引被删除（A/B 轮换、重建后的退役）时临时目录一并删除；新建索引的准备文件改名为正式索引后，准备阶段的临时目录也会清掉。
- 启动时清理中断遗留的准备文件及其临时目录。
- 这些目录平时是空的，只有内存吃紧时才有文件。磁盘被它占满说明某个查询或写入批次的工作集远大于单个索引上限，
  应调大上限或优化查询，不要靠清理临时文件。

**排障：View 水位停滞，日志反复出现“活动索引写入失败 … Duplicate key”**

- 现象：某个 View 的输出水位停住，监控报“数据停止更新”（`dataset:storage_view:…`）；`storage-view` 日志每秒几条
  `storage view 活动索引写入失败 … Constraint Error: Duplicate key "subject_id: …"`，涉及的标的集中在少数几个。
- 找首条：`grep -a "活动索引写入失败" storage-view.log | head -1`。如果首条是
  `Failed to commit: Failed to create checkpoint … Could not remove file … duckdb_temp_storage_…tmp: No such file or directory`，
  就是一次提交失败后索引的内存状态与磁盘不一致，后续重试永远撞主键，不会自愈。
- 处理：重启 `storage-view`（`restart.sh --components storage-view`）。数据不会丢，WAL 随启动重放，各 View 中断几秒；
  上游数据集和 Primary 不受影响。
- 确认：重启后日志里不再出现“活动索引写入失败”，该 View 的输出水位追上数据集，监控告警自动恢复。
- 预防：升级到每个索引独立临时目录的版本（含 `index_manager.go` 的 `indexTempDir`），共用目录不再出现。

### 6.5 DataNode 的 Pebble 块缓存

DataNode 用 Pebble 保存字段级事实。窗口读取（`ReadTimeSeriesRows`）先在历史索引里选出行键，再对每一行做一次存在性检查、对每一列做一次点查，所以读取成本约等于「行数 × (列数 + 1)」次 `Get`。
Pebble 的块缓存缓存的是解压后的数据块和索引块；缓存装不下热点时，每次 `Get` 都要重新读出并 snappy 解压。

- **大小**：默认取主机内存的 1/32，下限 64MB、上限 2GB，读不到主机内存时 128MB；线上 Storage 主机（15480MB）是 483MB。
  环境变量 `MOOX_STORAGE_NODE_BLOCK_CACHE`（正整数加 `KB`/`MB`/`GB`/`TB`）可显式指定，优先于推算。
- **日志**：打开时写 `storage node Pebble 块缓存 483MB（来源）`；启动 30 秒后及之后每 5 分钟写一行 `Pebble 块缓存 占用=…MB/…MB 条目=… 近期命中率=… 累计命中率=…`。
  近期命中率长期偏低、占用顶满上限，说明缓存偏小。
- **为什么不能用默认值**：2026-10-14 为两个 1h K 线因子集做回填，`storage-node` 的 CPU 被打到 330% 以上，单个窗口读取 15 秒以上并超时重试。CPU profile 里 52% 的时间在 `snappy.decode`，其中 72% 是在解压索引块。
  把块缓存从 8MiB 放大后，同一个补算的 CPU 采样总量约降到原来的十分之一。
- **仍然偏重的地方**：回填和预热读的是整个回看窗口，而且逐期重读。DataNode 的读取没有并发上限，也不区分在线计算和批量回填；新建因子集时每个成员各建一个全量回填任务。这些都会在数据量变大后重新放大负载。

## 7. 查询

| 接口 | 用途 |
| --- | --- |
| `DataView.QueryTimeSeriesRows` | 按 View 查询时序行，支持序列、时间范围、字段选择和稳定分页 |
| `DataView.SearchRecordRows` | 在记录 View 中检索 |
| `PrimaryStore.ReadTimeSeriesRows` / `ReadRecordRows` / `ReadFields` | 直接读取事实数据（回填、补算、因子源数据） |
| `PrimaryStore.CountTimeSeriesRows` / `DataView.CountTimeSeriesRows` | 按标的统计时间范围内已有的行数（同一时间点多个 series_tag 只计一次），由 active View 的 DuckDB `GROUP BY subject_id` 回答，只回传计数；一次至多 2000 个标的。Collector 完整性检查先用它比对根数 |

管理台通过 Admin 的 Storage BFF 访问 Metadata 和 DataView。

## 8. 鉴权

- primary、node、view 三个角色各有必填密钥（`MOOX_STORAGE_PRIMARY_AUTH_SECRET` 等），所有内部 RPC
  都校验 HMAC，不允许空密钥或以节点 ID 代替密钥。
- 独立[外部接入模块](外部接入.md)接受 `scf-collector`、`factor-engine`、`moox-skill` 三类外部身份；
  逐方法白名单在 `packages/servicecatalog/catalog.yaml` 的 `principals` 中声明。SCF 只可执行周期/批次协议与领取 Timer 批次，
  不能维护标签或元数据；这些管理调用由内部 `collector` 身份执行。
- Access 验证外部签名后以内部 `access` 身份重新签名转发；Storage 请求体的角色认证继续独立校验。
- access 用 SQLite 记录 nonce 防重放（`data/access/nonces.db`）。

## 9. 运维命令

`moox-storage-cli`（随 Storage 部署）：

| 命令 | 作用 |
| --- | --- |
| `init` | 初始化元数据库 |
| `import-seed` | 导入元数据种子 |
| `register-node` | 注册 DataNode |
| `activate-datasets` | 激活数据集 |
| `repair-view` | 默认备份元数据、重置消费者并提高 desired revision，触发 A/B 重建；删除索引需显式选项 |
| `force-rebuild-view` | 删除旧索引、运行时指针和消费者，从可重放事件重新创建 View |
| `reset-view-consumers` / `reconcile-view-consumers` | 重置或对账 View 消费者；`reset-view-consumers --reset-all-storage-data --yes` 还会清空全部行数据（含已登记的序列快照），之后必须让 Collector 重新登记，见[部署与运维](../部署与运维.md#清空全部数据重新积累) |
| `retain-views` | 按保留策略整理 View |
| `purge-dataset-events` | 清理数据集的积压事件 |
| `period-inventory` | 在停机或一致副本上只读盘点采集周期账本 |

`setup init` 提供业务 seed 导入，但仍包含旧部署假设；原生安装的初始化边界见[部署与运维](../部署与运维.md)。
这些维护命令（`repair-view`、`force-rebuild-view`、`reconcile-view-consumers`、`reset-view-consumers`、`retain-views`）按原生部署的接口工作：
通过包根目录的 `start.sh` / `stop.sh` / `status.sh` / `healthcheck.sh`（转给 `moox-runtime`，不接受位置参数）停启服务和检查状态，
整个 Storage 单元不带参数，单个组件用 `--components`；数据路径按所属组件解析（元数据库在 `storage-primary`、Pebble 在 `storage-node`、
View 索引在 `storage-view`），所以 `--package-root` 要指向包根目录（如 `/data/moox/storage/current`），`--storage-conf` 指向 `storage-view` 的配置
（读它的 View 消费者分区）。`status.sh` / `healthcheck.sh` 输出的是 JSON（按组件给出 `state` 与 `ready`）。
涉及 EventBus 的操作（查看消费者过滤、删除消费者、清除数据集事件）不需要 EventBus 凭据，也没有 `--credential-file`、`--eventbus-url` 参数：
命令用 `storage-view` 配置里的 `gateway_client` 身份（原生部署在 `<包根>/storage-view/config/storage.yaml`，caller 必须是 `storage-view`）
经网关调用 Admin 的 `InspectEventBus`、`DeleteEventBusConsumers`、`PurgeEventBusSubjects`，由 Admin 用数据库里的管理员令牌执行（见[管理后台](管理后台.md)）。
`--dry-run` 同样走这条路径（`repair-view`、`force-rebuild-view` 在要删消费者时也一样），网关、Admin、EventBus 任何一段不通都会在停止服务、改动本地状态之前报错；`reset-view-consumers` 还会提前检查所有要清除的主题都在 Admin 允许的范围内。网关目录缓存放在 `<组件目录>/var/storage-cli/`，与 storage-view 进程互不干扰。
`reset-view-consumers` 重启后会等所有 View 重建出活动索引；View 有历史数据时重建要几十分钟（线上 19 个 View 约 26 分钟），建议 `--timeout 60m`。等待超时时重置已经提交，命令会明确报“重置已完成、View 仍在后台重建”，不要重复执行。

## 10. 代码结构

```text
cmd/server            三个角色的进程入口（按 MOOX_STORAGE_ROLE）
cmd/cli               moox-storage-cli
internal/service/metadata      元数据服务与 SQLite 实现、缓存
internal/service/primarystore  写入校验与路由、读取
internal/service/datanode      DataNode：pebble 存储、outbox 发布、周期账本
internal/service/view          View 构建、维护、消费者与清单协调
internal/service/viewindex     DuckDB / Bleve 索引实现
schema/metadata.sql            元数据表结构
```

DuckDB 需要 CGO；正式的 Linux 版本在编译机上用 `make build-storage-linux` 构建。

## 11. View 访问 Metadata

storage-view 使用 `gatewayclient` 访问 Metadata，身份固定为 `storage-view`。公开业务配置顶层声明 `gateway_client.caller`、Admin 分配的 `key_id`、`key_file`，密钥路径相对模块配置文件；同一部署目录中的 `host-gateway/config/app.yaml` 提供主机 ID、loopback 地址与私有 CA。目录缓存保存在 Storage 数据目录的 `gatewayclient/directory.json`，客户端在进程退出时关闭。

查询、索引构建、重建日志、周期状态和同步点等全部 Metadata 能力统一经网关调用，原有请求中的 Storage 角色认证保留。只读重试、nonce、目录刷新、超时及大小限制统一来自共享客户端和组件目录，调用方不能再通过 tRPC 客户端选项指定其他目标。

Storage 内部的数据面仍使用角色认证直接调用 tRPC。View 到 PrimaryStore 的默认目标为 `127.0.0.1:20102`，历史修复读取保留五分钟超时；主进程到 DataNode、ViewIndex 等内部链路也保持直连。内部 tRPC 客户端和监听显式使用 go-net，避免 Linux SDK 自动选择 tNET。旧 Metadata 目标/协议/网络环境变量、Primary 协议/网络环境变量、`storage.view.storage_rpc` 及无用服务名配置已移除；配置加载拒绝已删除字段、未知网关字段和重复键。当前 Storage 业务监听均为原生 tRPC；原生单元部署已接入按角色分发签名身份与 Storage 凭据。
