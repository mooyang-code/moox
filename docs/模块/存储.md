# 存储（Storage）

Storage 是 MooX 的事实存储与查询中心：保存行情、因子结果等全部时序与记录数据（主机与服务指标存在 Monitor 自己的库里），
维护空间、标的、标签、数据集等元数据，并为每个数据集提供可重建的查询 View。

代码位置：`modules/storage`。

## 1. 进程与端口

Storage 由同一个二进制按 `MOOX_STORAGE_ROLE` 启动为两个角色：

| 进程 | 角色 | 主要服务与端口 |
| --- | --- | --- |
| `moox-storage-primary` | Metadata + PrimaryStore + Pebble 事实存储 | Metadata 原生 tRPC `20100`，PrimaryStore 原生 tRPC `20101`、`20102`，健康 `20210` |
| `moox-storage-view` | View | DataView 原生 tRPC `20103`，健康 `20211` |

- **primary**：元数据的增删改查和校验；在同一进程内打开 Pebble 库，负责字段写入、Outbox 事件转发、
  采集周期账本和过期数据清理。全部数据集都在这一个 Pebble 库里，库身份固定为 `storage-primary`，
  目录是 `<storage-primary 包>/var/storage/pebble/storage-primary`（代码在 `internal/service/datanode`，包名沿用）。
- **view**：每个 View 一个跟随协程读 storage-primary 的变更日志，维护 DuckDB（时序）和 Bleve（记录）索引，发布 `ViewDataReady`，提供查询。

SCF 和因子引擎通过独立的[外部接入模块](../../modules/access/README.md)访问，入口为 `moox-access`（见第 8 节）。

原生 `setup deploy-unit --profile storage` 要求两个角色同机，内部 RPC 走 loopback。

系统不做分片、副本、选主或在线迁移；storage-primary 停止时全部写入失败，
View 离线不阻塞写入，恢复后从变更日志的游标接着跟随（停机超过日志保留期 7 天才断档重建）。

## 2. 数据模型

### 2.1 元数据

元数据保存在 primary 的 SQLite（`schema/metadata.sql`，schema 版本 18，共 12 张表）。每张表只保留主键、唯一约束、外键和查询条件用到的列，整条消息放在 `c_item_json`；
状态取值只有 `active`、`disabled`、`deleted`（数据集、标的只有前两种）。主要对象：

| 对象 | 表 | 说明 |
| --- | --- | --- |
| Space | `t_spaces` | 业务域：`crypto`、`stockcn`、`stockhk`、`stockus` |
| DataSource | `t_data_sources` | 数据来源：数据集可引用的名字，只有 ID、名称、状态与属性；采集的连接配置在 Collector 的源配置里 |
| Subject | `t_subjects` | 标的（交易对、股票等）：ID、名称、时区、状态与属性；`subject_type`、`market`、`currency` 等业务含义是属性键，Storage 不解释 |
| Tag | `t_tags`、`t_subject_tags` | 标的分组：ID、名称、描述、`mode`、`builtin`、成员统计与属性；内置标签只能来自种子：`UpsertTag` 带 `seed`（`setup init`、`setup metadata-import`、`metadata import`、`metadata apply` 都带）时新建的标签保留请求里的 `builtin`，不带时新建的一律非内置，已有标签的 `builtin` 都不改；内置标签不能删除，Monitor 巡检所有空间的内置标签；市场类型、同步来源、同步周期这类业务含义写在属性里（`market_type`、`sync.source`、`sync.cron`、`sync.timezone`，由 Collector 解释），自动标签的成员由 Collector 按这些属性同步 |
| Dataset | `t_datasets` | 数据集：时序（time_series）或记录（record），有确定的保留期；时序数据集只有一个规范频率 `freq`，创建后不可修改；`alignment`（周期对齐方式，`epoch_utc` 或 `session`）与 `allowed_lateness_seconds`（周期截止前允许迟到的秒数，0 用默认值）是 Storage 会解释的正式字段，其余属性由调用方自用 |
| FieldGroup / Field | `t_field_groups`、`t_fields` | 数据集字段，只增不删，类型不可改 |
| DatasetColumn | `t_dataset_columns` | 数据集的列定义；来源分三类：`FIELD`（引用字段，身份是 `origin_id`）、`CUSTOM`（数据集自己定义的值列，身份就是列名、不带 `origin_id`，因子 ID、成员键等生产者信息由写入方放在列属性里）、`SYSTEM` |
| View | `t_views` | 面向查询的视图，只索引一个 Dataset，只存声明；列等于数据集启用的列，`freq` 由 Storage 按所属 Dataset 填写；已建好的索引状态只在 View 的索引文件里（见 6.1）；由使用方（Collector、factor-mgr）自己创建与删除 |
| 标的修订号 | `t_space_revisions` | 按空间单调递增的 `subjects_revision`：标的（状态、属性、增删）、标签成员、标签属性、数据集（创建、删除、标的范围）变化时由触发器在同一事务内递增；`GetDataset` 响应带回，调用方用它判断缓存的标的元数据是否过期 |

`t_space_revisions` 与触发器全部 `IF NOT EXISTS`：执行一次 `moox-storage-cli init` 即可补建。runtime 托管的 storage-primary 启动时不执行 init；单元安装由 setup 在候选目录内 init，只换二进制的原生发布要先备份元数据库并执行 init 再换二进制。

数据集建好即为 active，可以直接写入；`CreateDataset` 可以同时带上列定义，不需要另外激活。
`UpdateDataset` 合并已有值：`data_source_id`、`alignment` 设置后不能修改（没设置过的可以补上，要改只能删数据集重建）；请求里 `alignment` 为空、
`allowed_lateness_seconds` 为 0 时沿用已有值，所以迟到时间设过之后不能改回 0（默认值）。`data_kind`、`freq` 创建后不可变。
数据集列名必须是标识符（字母、数字、下划线，不以数字开头），不能用 `subject_id`、`freq`、`data_time`、`series_tag` 等系统列名：列名会原样成为 View 索引里的列。
Storage 不托管任何默认 View：数据集的 View 由业务模块自己建（Collector 为采集结果建浏览 View，factor-mgr 为因子结果数据集建结果 View），数据集属性（`attributes`）、列属性也全部由业务模块自己维护，Storage 不读取、不锁定、不校验业务含义；Storage 要用的信息都是消息上的正式字段。
`data_source_id` 对所有数据集都可选，填写时校验引用存在。

命名规则见[元数据命名规范](../元数据命名规范.md)。

### 2.2 行身份

```text
时序：space_id + dataset_id + subject_id + freq + data_time(UTC) + series_tag
记录：space_id + dataset_id + record_id + version
```

- `series_tag` 是可选的不透明字符串，空字符串表示默认序列；推荐写成 `venue:binance` 这样的约定，
  Storage 不解析其内容。范围查询中“不设置”表示全部序列，“设置为空”表示只要默认序列。
  **统一数据集**：同一数据集里同时放同一标的的现货、永续两条序列，靠 `series_tag` 区分、互不覆盖（采集写行的取值：
  现货 `venue:binance|market:spot|source:spot_http`，永续 `venue:binance|market:swap|source:swap_http`）。
  消费方把 tag 换成市场用 `packages/seriesset` 的 `SeriesTagMarket`（按 `market:` 段解析，没有这一段视为现货）；
  Storage 本身仍不解释 tag，行键、读取、View 主键与计数、定时删旧行本来就按（标的、频率、时间、tag）。
- `data_time` 统一保存为 UTC、9 位纳秒精度。
- 写入是字段级 Upsert：可以新增、覆盖或补写历史行的某些字段，所有字段都允许缺失。
- 记录写入必须带 `version`；读取时不指定版本则取字节序最大的版本。

### 2.3 物理布局

storage-primary 的 Pebble 库 key 空间按用途分区：`0x01` 字段、`0x02` 属性、`0x03` 时序历史索引、
`0x04` 序列历史索引，另有 `__outbox/`、`__meta/` 等内部前缀。布局版本为 5，写在数据目录的
版本文件中，版本不符时拒绝启动。

时序数据的物理 key 把规范化的时间桶 `bucket_start` 放在数据集之后，过期清理可以按
`(space, dataset, bucket)` 做有界的 `DeleteRange`（不逐个读取 key），再异步 Compact 回收空间。

### 2.4 保留策略

保留期不由数据集各自声明，而是由 `moox-cli` 从 `moox.toml` 的 `[storage_retention]` 与 `[storage_view]`
渲染为策略 JSON。原生安装向各 Storage 角色的发布目录写入 `config/storage-policy.json`，
`storage.policy_file` 指向角色内副本；primary 与 view 使用同一策略内容，缺失或非法时拒绝启动。
旧平铺部署使用 `<storage_root>/config/storage-policy.json`，不能用该路径推导原生配置位置。

- **保留期与因子回看根数是关联的配置**：因子引擎预载、补算要从 Storage 读回「任务里启用成员的最大回看根数」那么多历史，保留期装不下就读不全。`setup init` / `setup factors` 初始化因子时核对：保留期必须大于最大回看根数，crypto 等 7×24 市场装不下报错并写明至少要调到多少（`storage_retention.spaces.<空间>.<频率>`），股票等交易时段市场按日历估算只给提醒；View 的 `bars` 同理要被保留期装下（`Policy.Coverage`）。改因子表达式的窗口、改保留期、改 View 根数时要一起看。
- 时序数据集的生效保留期按 `(space_id, freq)` 解析：空间配置优先，没有时用全局默认；全局默认覆盖
  全部**标准频率**（30s、1m、5m、15m、30m、1h、4h、1d、1w、1mo）。合成出来的非标准频率（如 45m、2h）没有单独配置时，
  沿用时长不超过它的最大标准档（45m → 30m，2h → 1h，12h → 4h），先看空间覆盖再看默认；也可以在配置里为它单独写一项。
  因此每个时序数据集都有确定的保留期。记录型数据集不过期。
- Metadata 的 `GetDataset`、`ListDatasets` 返回只读的 `retention`（`<n>h` 或
  `forever`）与 `retention_source`（`default`、`space`、`record`）；写接口没有保留字段。
- primary 每小时清理一次：对每个活跃时序数据集计算 `cutoff = now - 保留期` 并按天桶截断，调用
  Pebble 库的 `CleanupExpiredBuckets` 删除更早的行与历史索引。实际保留在保留期到多一天之间。
  `forever` 跳过。每次清理记录日志和指标 `moox_storage_dataset_cleanup_cutoff_timestamp_seconds`、
  `moox_storage_dataset_cleanup_duration_seconds`、`moox_storage_dataset_cleanup_failures_total`；
  Pebble 磁盘占用上报为 `moox_storage_pebble_disk_bytes`。

## 3. 写入路径与事件

```text
调用方 ─► PrimaryStore（一次请求一个数据集；校验数据集、字段、类型）─► 同进程的 Pebble 库
Pebble 写入：锁外编码 KV；outboxMu 内查 commit 标记、分配变更日志序号，一个 Pebble Batch 写入 字段/属性 + 变更日志行条目（时序范围或记录键）+ commit 标记
完成标记：标记记录 + __outbox/<id> + 变更日志完成标记条目（内嵌整条标记消息）同批提交；提交后广播一次进程内信号，唤醒等待新变更的 ReadDatasetChanges
Outbox Relay：只承载周期完成事件，按 ID 顺序同步发布到 EventBus，失败即停止，只删除连续成功的前缀
事件压缩：发布器默认压缩，信封不小于 256B 且压缩后明显变小时以 zstd 字典压缩发布（content type 为 `application/vnd.moox.event+protobuf+zstd`），字典按事件所属空间选择，消费端经 `events.DecodeRaw` 透明解压；新增或更换字典必须分两次发布，先让所有消费端能解码
```

谁能调用哪些写方法只由网关 ACL（`packages/servicecatalog/catalog.yaml`）决定：Storage 内部没有按调用方身份（因子、采集等）的写入判断，请求体里的 AppId 只用于服务签名与日志。
代价是 ACL 管的是方法、不管数据集：有写权限的调用方能写所有数据集，模块写错数据集 ID 时 Storage 不会拦。

Storage 发布的事件都在 `MOOX_STORAGE` Stream：

| 事件 | 含义 |
| --- | --- |
| `dataset.period.completed` | storage-primary 经 Outbox 转发：某数据集某频率的一期已完成（complete/degraded），统一的周期完成事件；`source` 为 `ledger`（storage-primary 按序列快照账本判定，采集与 K 线合成）或 `producer`（写入方自己报告，因子） |
| `view.data.ready` v2 | storage-view 直接发布：View 已应用某一期的数据（见 6.3） |

## 4. 采集周期协议与周期完成

storage-primary 是“采集周期是否完成”的唯一权威。当前对外的 PrimaryStore 周期写入接口是：

| 方法 | 作用 |
| --- | --- |
| `RegisterSeriesSnapshot` | Collector 对账协程在生效周期之前登记完整序列快照，返回 hash 与数量 |
| `CommitTimeSeriesBatch` | SCF、stream 或重采样执行端提交行；首个有效批次按已登记快照懒建周期账本并固化截止时间，返回被接受的序列编号；只有完整回执才算成功 |

全部预期序列都成功时 storage-primary 提前把周期固化为 `complete`；到达截止时间仍未齐则固化为 `degraded`，两者都是原子完成，并写入
`DatasetPeriodCompleted` 标记（`source=ledger`）；标记里 `universe_subject_ids` 来自完整快照，`failed_subjects` 包括其中所有未成功提交的标的（含从未上报过失败的标的）。删除
数据集时，其周期账本、完成标记、序列快照与生效表一并清理。序列快照里的序列身份只有 `subject_id` 与 `series_tag` 两项（`packages/seriesset`，Collector 与 Storage 共用同一份实现，`series_hash` 因此一致）；`series_tag` 由写入方决定，Storage 不解释。

账本在 Pebble 里每期一条记录（`__period/{空间}/{数据集}/{频率}/{周期}`：状态、快照引用、截止时间、成功位图），storage-primary 每秒扫一遍各数据集最近一段里未完成的记录判定截止（启动后第一遍扫全部记录，补上停机期间到期的周期）。账本与完成标记随数据集保留期按同一截止时间清理；序列快照的生效条目在下一条生效点也早于截止时间时一并删除（它覆盖的周期都已清理），不再被剩余条目引用的快照随之删除，每个频率的最后一条总是保留。整个周期零提交时没有账本和完成标记；缺口由 Collector 检查补采，因子连续水位读回推进。

删除数据集只用 `Metadata.DeleteDataset`：服务端先删元数据，再删这个数据集的行与行索引、周期账本、完成标记、序列快照与生效表；元数据已不在时重试照样删行。
序列快照删掉之后，同名数据集要重新登记才能按周期提交：对仍在活跃采集的数据集，执行 `moox-cli collector fetch-plan reregister --space-id <空间> --yes`。
`DeleteSpace` 删除空间元数据后，也会逐个删掉空间内数据集的行。PrimaryStore 没有单独的删行或恢复行接口。

### 4.1 周期完成事件

不由账本判定的周期（现在只有因子结果）由写入方用 `ReportDatasetPeriodCompleted` 报告（`source=producer`），`GetDatasetPeriodCompleted` 按 `cause_event_id` 加 `period_time` 查询，同一触发事件与周期只存一条（内容不同的重报返回冲突）。两种来源的标记都存在 `__marker/{空间}/{数据集}/{频率}/{周期}/{来源}/{触发事件哈希}`（账本来源触发事件部分为空），查询直接点读；标记随数据集保留期清理，超过保留期的周期查不到、也不会再被重报。
两种来源写出的是同一个事件 `DatasetPeriodCompleted`，`source` 只说明这一期怎么判定完成的，不是业务分类；消费方按自己绑定的数据集与频率筛选，两种来源都接受。字段：

| 字段 | 说明 |
| --- | --- |
| `dataset_id`、`frequency`、`period_time` | 哪个数据集的哪一期 |
| `status` | `complete` / `degraded` |
| `source` | `ledger`（storage-primary 账本判定）/ `producer`（写入方报告） |
| `universe_subject_ids`、`failed_subjects` | 本期应有的标的与失败的标的（标的的任一序列失败，该标的就记入失败） |
| `universe_series`、`failed_series` | 按序列（标的、`series_tag`，`SeriesRef`）的期望全集与失败名单，**只有序列快照含多个 `series_tag`（统一数据集）时才填**，单序列数据集为空；失败名单是全集的子集，失败序列的标的必须在 `failed_subjects` 里（有一条序列失败的标的就是失败标的），全集包含的标的正好是 `universe_subject_ids`，`series_tag` 与行键同一套规则（不超过 128 字节、无首尾空白和控制字符），`complete` 不带失败序列（`packages/events` 校验） |
| `snapshot_ref` | `ledger` 来源时的序列快照引用 |
| `cause_event_id` | `producer` 来源时触发本次计算的事件 ID，用于幂等查询 |
| `completed_at` | 完成时间 |
| `detail_type`、`detail` | 写入方自定义的明细（不透明字节）：Storage 原样保存并透传，不解析 |

统一数据集的序列名单（标的加 `series_tag`）让事件体积随序列数增长：周期登记时的体积预检按“每条序列都失败”的最坏情况估算（全集与失败名单各一份），超过事件上限就拒绝登记。
`DatasetPeriodCompletedMarker`（producer 来源的报告）同样带 `universe_series`、`failed_series`，Storage 原样保存并带进事件，`GetDatasetPeriodCompleted` 原样返回，
因子的空洞恢复据此读回冻结的序列全集。
补采事件 `event.collector.kline.backfilled` 另带 `series_tags`（统一数据集写入的序列，空表示数据集的全部序列）。View 就绪事件不带序列字段：策略的失败名单读因子明细，不读它。

**写入幂等**：`UpsertFields` 一次只写一个数据集（请求顶层 `space_id`、`dataset_id`，每行必须一致），可选 `commit_id`：同一数据集内同一
`commit_id` 只生效一次，内容相同返回成功、内容不同返回 `CONFLICT`。commit 标记按写入日分桶（`__commit/{写入日}/{空间}/{数据集}/{commit 哈希}`），固定保留 7 天、与数据集保留期无关，查重时读今天和前 7 天共 8 个日桶；超过 7 天的同一 `commit_id` 当作新提交（最长的重投来源是 `MOOX_STORAGE` 的 72 小时）。删除数据集时一并清理。
不带 `commit_id` 的写入不去重：消息重投时会再写一次相同的行、多记一条变更日志行条目，View 重复应用无害。

## 5. 因子结果与写后读

- Factor 用 `UpsertFields`（带 `commit_id`）一次写入一个周期的完整结果行（携带列 + 因子列 + 系统列 `__params`），随后用
  `ReportDatasetPeriodCompleted`（`source=producer`）报告这一期完成；`detail_type` 是 `moox.factor.PeriodDetail.v1`，`detail` 是因子自己定义的 `PeriodDetail`
  （`modules/factor/proto/factor.proto`：每个成员的状态、`spec_hash`、`definition_hash`、失败标的与失败序列等），由因子侧校验（`storageio.ValidatePeriodDetail`），Storage 不解析。
- **因子结果列的契约不在 Storage**：结果数据集的值列用 `CUSTOM` 来源（不带 `origin_id`），`column_kind`、`factor_id`、`member_key`、`member_kind`、`output_name` 等放在列属性里，列名与类型的约定由 factor-mgr 建列时自己保证；
  Storage 只校验通用规则（列名唯一、值类型合法、字段列引用存在）。`__params` 是 `json` 类型的列，JSON 文本由调用方解析，Storage 不解析；
  结果 View 的列集合跟随数据集（含 `__params`），View 照常为它建索引，DuckDB 可用 `json_extract` 查询。
- 需要“写后读”的调用方在写入返回后调用 `DataView.WaitViewApplied`，等 View 跟上调用这一刻的变更日志头部；要确认 View 的列已建好、看覆盖范围与跟随进度用 `DataView.GetViewState`。
  这两个方法也接受由 Primary 角色密钥派生的写入身份（Collector 建合成目标、`moox-cli import --view` 用）。

## 5.1 变更日志

> 状态：已实现（因子本地K线存储设计 5.1；Storage 合并与 View 跟随变更日志执行计划 T5 扩展了条目种类与等待）。

变更日志存在 Pebble 的 `__changelog/` 键下，序号全局单调递增，每条和它记录的写入在同一个 Pebble 批里提交。条目有两种（`DatasetChange` 按 `marker` 是否为空区分）：

- **行条目**：每次行写入（`UpsertFields`、`CommitTimeSeriesBatch`）一条。时间序列行记在 `ranges`（按标的、频率合并成时间范围，两端都含，RFC3339Nano UTC），记录型行记在 `records`（被写入的记录键，去重排序）。
- **完成标记条目**：每条周期完成标记一条，`marker` 是整条 `EventMessage` 的字节，与标记本体、Outbox 条目同批提交。写入方上报（`ReportDatasetPeriodCompleted`）和账本判定（完成或截止降级）两个写入点都记；内容相同的重报不再记。

同一数据集的条目按序号先后就是提交先后：账本判定的标记在使这一期完成的那次行写入提交之后才写，所以标记条目之前的行条目都已提交。

日志保留 7 天，由 storage-primary 每小时一次的保留期清理循环按创建时间删除（记录已清理到的序号）；创建时间读不出来的条目按已过期删除。`ReadDatasetChanges`（PrimaryStore）必须带 `dataset_id`，按游标（`store_id`、序号）读取：

- `from_head` 只返回当前头部位点。
- 返回的 `next_cursor` 是已扫描到的位置，没有命中本数据集的条目也会前进。
- 一页最多扫描 `limit` 条（默认 500，上限 2000），放进响应的条目累计不超过约 4 MiB（完成标记条目内嵌整条标记，全集大的数据集一条就有几十 KB；单条超过时单独成页），截断时 `has_more` 为真、`next_cursor` 停在最后一条放进响应的条目上。
- 游标早于已清理的序号、比头部还新或 `store_id` 对不上（存储重建）时返回 `gap`（断档）。
- `wait_ms` 大于 0 时，没有本数据集的新变更就在服务端等下一次提交（写入提交后进程内广播一次信号，不轮询），最多等 `wait_ms`（上限 30 秒；请求带截止时间时截到截止前 200 毫秒）；到期返回空的 `changes`，`next_cursor` 照样前进。`from_head` 和断档不等待。头部、清理位置与条目从同一个 Pebble 快照读；游标之后的第一条不是游标加一（条目已被删除）时也返回 `gap`。

调用方是 `factor-engine`、`archive-worker`（服务目录里已授权）与 storage-view（见 6.2）；归档 worker 只用时间序列行条目的时间范围找出回看窗口之外的晚到写入（见归档文档第 9 节）。因子机只跟进时间序列行条目，在本地时序存储里跟进修正，忽略记录型行条目和完成标记条目。

数据集字段的 `attributes.fill` 声明缺失行的填充规则：`prev`（默认）、`prev_close`、`zero`；Storage 原样保存，由因子机本地存储解释，取值无效时按列名取默认规则。
View 默认保留 10000 根（`view_rows_per_series`）。Primary 默认保留期为 30s 90h、1m 35d（要装得下默认因子 EMA 的最大回看）、5m 35d、15m 105d、30m 210d、1h 420d、4h 1700d；1d、1w、1mo 永久，
单 View 文件容量阈值 `max_view_file_bytes` 默认 4GiB（1 万根的 1m K 线 View 约 1.1GB）；文件大小还取决于标的数、字段和压缩率，不能只按每序列根数确定。
View 另有按空间 × 频率的写入年龄上限 `[storage_view.max_age]`（写法同 `[storage_retention]`：省略 `defaults` 时使用推荐表，显式提供的表整体替换推荐表，`defaults` 必须覆盖全部标准频率，`spaces.<空间>` 覆盖默认；未单独配置的规范频率回落到不大于它的最大标准档，例如 45m 使用 30m 的期限）。通用默认值恰好装下 1 万根：30s 90h、1m 7d、5m 35d、15m 105d、30m 210d、1h 420d、4h 1700d，1d、1w、1mo 永久。各市场（stockcn、stockhk、stockus）的空间覆盖属于部署配置（`moox.toml` 的 `[storage_retention.spaces.*]` 与 `[storage_view.max_age.spaces.*]`，示例见 `moox.toml.example`），不写在 Storage 代码里。
`setup` 分别校验 Primary 保留期与 View 写入年龄上限是否装得下 `view_rows_per_series` 根：默认值装不下时报错，空间覆盖装不下只警告（空间可以有意少留历史）。生成的 `storage-policy.json` 必须包含完整的 `view.max_age.defaults`，运行时不会为旧 policy 文件补齐。

## 6. View

### 6.1 索引

- 一个 View 只索引一个 Dataset。**View 的列就是数据集里启用的列**（列本身启用、引用的字段也启用），由 Metadata 推出：
  按数据集列的创建顺序排列，列名与 `origin_id` 都是 Dataset 列名，属性取自数据集列；`CreateView`/`UpdateView` 传入的列被忽略，
  没有单独写 View 列的接口。给数据集加一列，View 就有了这一列，不需要任何 View 侧的调用。按精确 Key 读 Primary 与按时间范围读 View
  使用同一套列名。
  - 已知差别：种子里 stockus 日线 View 原来只声明了 6 列，现在等于数据集的 9 列，多出 `provider_id`、`source_id`、`provider_symbol` 三个文本列。
- 时序 View 使用 DuckDB 文件，主键为 `(subject_id, freq, data_time, series_tag)`；记录 View 使用 Bleve，
  支持全文检索。
- 每个 View 只有一个物理索引，标识由空间和 View 决定（`ViewIndexID`），任何时刻只写这一个索引。
  - **已建状态只在索引文件里**：索引自己记下所属数据集、已建列（含排序）、修订号、列契约哈希和跟随进度（DuckDB 在 `view_meta`，Bleve 在 `meta.json`），
    元数据不保存这些。`DataView.GetViewState` 对外提供索引标识、代次、已建列、覆盖范围与跟随进度。记下跟随进度是建索引的最后一步，**记下了跟随进度、且属于 View 当前数据集的索引文件才算建好**；
    启动时只挂接建好的索引，文件不存在、没建完（进程在建索引中途退出，含 Bleve 目录在而 `meta.json` 不在）或属于另一个数据集（删除后同名重建、旧文件还没清理）时由维护流程重新建；
    单个索引读不出来只跳过这个 View，不让进程起不来。从元数据删除的 View（停用的不算）由维护流程摘掉，`GetViewState` 返回 `VIEW_NOT_FOUND`，索引文件由退役清理回收。
  - **首次建索引**：没有建好的索引时，维护循环先取变更日志头部、准备空索引，再从 Primary 回填历史，最后记下跟随进度，View 从此可读，跟随器从建索引前取的头部接着应用（见 6.2）。建索引期间 View 不可读，查询返回“索引未就绪”，读取方等待；这期间的周期完成不发 `ViewDataReady`，建成后也不补发，就绪事件从建成后的下一期开始，所以 Strategy 的规则状态不包含建索引期间的周期。半成品不续建：回填失败或进程退出后，下一轮删掉重建。
  - **列只能追加**：不允许改列名、删列、改列类型，也不允许改数据集、引擎和主键维度，要改就新建 View。数据集加列后，每分钟的定时任务（见下面“定时删除最旧数据”）持该索引的写锁原地加列（线上 DuckDB 单次 33～41ms），加列与新的列契约在索引的同一次提交里落盘，修订号加 1。新列默认为空，不回填。
  - **列删除只是逻辑上的**：数据集列被禁用，或它引用的字段被停用、删除时，View 的列、索引里的列和已写入的值都留着，只从 `ListViewColumns`、`QueryTimeSeriesRows`、`SearchRecordRows` 的结果里隐藏。隐藏的列由元数据算好，放在 `View.hidden_columns` 下发，不落库；View 服务下一轮维护生效（约 1 分钟），重新启用后恢复。字段管理页面展示字段的停用、已删除状态，也可以批量删除；删除是逻辑上的，数据保留，批量启用即恢复。
  - **修订号**：`view_revision` 建成时为 1，每次加列加 1；`GetViewState.columns` 是已经建进索引的列。View 的列与已建列按列名比较。
  - 索引文件不见了时由维护流程重新建；索引损坏用 `repair-view` 删除后从 Primary 重新建。
- **View 的写入路径**（`viewindex/duckdb/bulk_write.go`）：一批行按携带的字段集合分组，每组两条语句——先对 `view_rows` 里还不存在的键按序列累加 `view_series_counts`，
  再整批 UPSERT；每个列绑定成一个 LIST 参数、用 `unnest` 展开（驱动不支持 LIST 里的 NULL 与 BLOB：NULL 用占位值加布尔掩码，BLOB 用十六进制文本再 `from_hex`）。
  旧实现是每 32 行一条多值 INSERT、每行两轮 SQL，本机实测导入形态 8055 → 93982 行/秒（11.7 倍），实时形态 6177 → 27686 行/秒（4.5 倍）；
  旧实现原样留在 `legacy_write_oracle_test.go` 作对照，`bulk_write_equivalence_test.go` 用同一批输入写两个索引、逐行逐列比较结果。
  **按最长保留天数过滤写入**：所有写入路径（跟随变更日志、首次回填）最后都经 `Service.writeIndex`，写进索引之前先丢弃 `data_time` 早于“当前时间 − `[storage_view.max_age]` 期限”的时序行
  （以处理该批时的时钟为准，恰好等于截止点仍保留；K 线 View 与因子结果集 View 一样；记录型行、无法解析到期限的频率、永久保留的频率不过滤）。补采、导入与因子历史重算带来的超期行因此不进 View；这不是 Primary 写入拒绝，即使整批超期，View 处理也返回成功，不因年龄过滤重试。Primary 仍受自己的保留策略约束，因子机本地存储的保留行为不变。
  丢弃行数记在指标 `moox_storage_view_expired_rows_dropped_total{space,freq}` 和 `storage view 丢弃超过最长保留期的行` 日志里。
  这条过滤只管新写入，不在查询时过滤，也不按年龄主动删除已入索引的行。已有旧行可能继续可见，直到被定时删除最旧数据删掉（按根数而不是年龄），或 View 被重新建索引时回填被年龄过滤排除；不能把上限当作现有索引的最早时间保证。
  历史导入仍建议只写最近窗口（`moox-cli import --tail-rows`），省得 Storage 读写一遍再丢弃。
- **定时删除最旧数据**：storage-view 的定时任务每分钟第 10 秒触发，先检查加列，偶数分钟再执行一轮删除，逐个时序 View 的活动索引删除每个序列里排在最新
  `view_rows_per_series` 根之前的最旧数据，每个序列最新的 N 根不动。先不持锁按快照查出每个序列的删除分界，再持该索引的写锁在一个短事务里删除并减计数，
  每批最多 64 个序列、`storage.view.delete_oldest_batch_size` 行（默认 2000，1～20000；不配置或配成 0 时取默认值），每个索引一轮最多删“每批行数 × 10”行，剩余留到下一轮。
  每批删除都更新索引的修改时间并推进修订号，分页读取期间删了行会被发现，不会静默少行；一轮删完（中途出错也一样）把覆盖起点前移到剩余行的最早时间，并把记录的保留根数改为 N；全量统计合并覆盖范围时以实际最早时间为下限，不会把起点改回去。
  指标 `moox_storage_view_oldest_rows_deleted_total{space,view}`、`moox_storage_view_oldest_delete_lock_seconds`，
  以及每轮结束都会更新的 `moox_storage_view_oldest_delete_last_round_timestamp_seconds`（没有可删的也更新，用来确认任务在跑）；启动时打一条日志；
  单批持锁超过 200ms 或一轮达到上限时打日志。序列因此保持在 N 根左右。
  因为同一代索引也会删除最旧数据，Strategy 回放开始前总是按精确覆盖统计复查起点，起点已被删掉时失败并提示重新发起（统计暂时未知且索引未换代时按提交的区间执行）。
- 时序 View 每个序列保留最近 `view_rows_per_series` 根（默认 10000）；周末和节假日不计作有效根数，但写入年龄仍按自然时间计算。根数由 `moox.toml` 的 `[storage_retention] view_rows_per_series` 统一配置。DataView 查询响应的 `retained_rows_per_series` 是活动索引建立时记录的保留根数与当前配置中较小的一个（调大配置要等 `repair-view` 重新建索引才变大），不承诺实际存在这么多行或覆盖对应时长。
- 回填不指定标的，用 `ReadTimeSeriesRows(latest_per_series = N)` 按游标逐页读取：storage-primary 在序列索引上按
  subject_id、series_tag 顺序逐个序列、从新到旧取最近 N 根，一页最多 2 万行且不超过 20 万个值，同一标的可以跨页。
  耗时只与「序列数 × 根数」有关、与历史长度无关，不依赖数据集是否绑定了标的标签。某一页失败（含超时）时丢弃半成品，
  下一轮重建，不静默跳过标的。历史不足目标根数，或最近 N 根中有行超过 View 年龄上限时，以实际留下的数据建成。派生输出（例如因子结果）在第一个周期之前 Primary 里没有行，View 从空开始。记录型 View（Bleve）没有可读的 Primary 历史，也从空开始，只跟随新写入。
- 数据集加列后，加列完成前跟随到的行按 View 当前的列投影应用，尚未建进索引的新列直接裁掉，不阻塞跟随、不回填；
  新列在 View 里晚生效一两期，需要这几期的值时加列完成后对那几期重算（行会带上新列）。主库里的值不受影响。
- View 的正式字段 `maintenance_priority` 决定维护顺序：越小越先，0（默认）最先；Collector 的浏览 View 与种子里的 View 为 0，因子结果 View 为 10。Storage 不读 View 的属性，不认业务标记。
  因子结果 View 由 factor-mgr 创建与删除（`view_role=factor_result` 只是页面用来找到它的业务标记，Storage 不读）；删除因子结果数据集时先删 View，再调用 `DeleteDataset`（由它删行）。
- View 不保存也不返回行属性（因子结果写入本来就不带行属性）；行属性只由 `PrimaryStore.ReadRows` 按 `attribute_keys` 返回。
- 文件超过 `max_view_file_bytes`（默认 4GiB）只告警，不动数据：指标 `moox_storage_view_file_over_limit` 是超限的 View 数量，Monitor 检查 `view_file:storage_view`（“View 索引文件大小”）据此告警，具体的 View 在 `storage view 索引文件超过告警线` 日志里。定时删除只删行，DuckDB 复用释放的空间，文件不会随之缩小。

### 6.2 跟随变更日志

View 按游标读取 storage-primary 的变更日志（`PrimaryStore.ReadDatasetChanges`），和因子机用的是同一个机制。

- 每个已建好索引的 View 一个跟随协程（`internal/service/view/follow`），游标、重试各自独立：一个 View 卡住（索引写入出错、就绪事件发不出去）不影响其他 View。
- 没有新变更时让 storage-primary 等到下一次提交再返回（`wait_ms` 20 秒，单次调用超时 25 秒）。
- 游标是“已扫描到的位置”，没有命中本数据集的条目也会前进，空闲数据集不会因为日志清理而断档；只有 View 停机超过日志保留期（7 天）才会断档并重建索引。
  行与游标在同一个 DuckDB 事务里提交，Bleve 把游标写在索引旁的 `meta.json`；只扫描、没有写入的前进每分钟落盘一次。
- 行条目只记“哪些行被写过”，View 按时间范围回读整行写入索引：日志区间两端都含、读取接口左闭右开，结束时间加一个频率步长；先按 View 的最长保留期截掉过期范围；
  同一页里连续的行条目合并后再读，时间窗相同的标的合成一次读取，超过 100 个标的时不带标的、按时间索引读。记录型条目按记录键回读。
- 完成标记轮到它时，数据集在它之前的行必然已经应用，直接把 `ViewDataReady` 发布到 EventBus；发布失败就停在这条标记上稍后再试，期间不往后应用行。
  发布成功只推进内存游标，崩溃后可能重复发布少量就绪事件（事件 ID 稳定，EventBus 去重窗口 2 分钟，下游按周期去重）。
- 建索引先取日志头部 `H_start`，读存量，建成时再取一次头部 `H_done` 一起记进索引；跟随器从 `H_start` 接着应用（重放的行是幂等写入），
  `(H_start, H_done]` 之间的完成标记只推进游标、不发布，建索引期间的周期完成不补发就绪事件。断档时按当前的列契约原地重建，重建期间 View 不可读；重建失败、中途停用后由跟随器接着重建，进程退出后索引没有跟随进度，由维护流程重新建；记录型 View 重建后为空。
- 就绪：恢复完活动索引、开始跟随变更日志后 `/readyz` 才就绪。
- 落后情况：指标 `moox_storage_view_follow_lag_seconds`（距离上一次追上日志头部的秒数，等待新变更时为 0）与 `moox_storage_view_follow_lag_changes`（头部序号减已扫描序号），
  按 View 打标签；Monitor 检查 `view_follow:storage_view`（“View 跟随数据变更”）在落后超过 2 分钟时告警。

### 6.3 就绪事件

View 跟随变更日志按序应用该周期的行，轮到 `DatasetPeriodCompleted` 标记时直接发布 `ViewDataReady`（v2：携带标的全集，并原样透传标记里的 `detail_type`、`detail`）。Strategy 以此作为触发信号：
`detail_type` 是 `moox.factor.PeriodDetail.v1` 时按因子的 `PeriodDetail` 解码，判断每个成员这一期是否可用；是否相关只看事件绑定的 View 与数据集，不再区分完成来源。
已处理不保证每条历史行仍能在 View 查到：超过 `max_age` 的行可以被成功过滤，根数整理也会移除旧行。

就绪事件由 View 直接发布到 EventBus；发布失败时该 View 停在这条标记上退避重试，期间不往后应用行（EventBus 故障时查询停在旧数据）。
标记解不开或事件无法通过契约校验时记日志跳过，不让一条坏标记永远卡住 View。

### 6.4 DuckDB 资源与临时目录

每个时序 View 索引是一个独立的 DuckDB 实例，各自配置 `memory_limit`。
「索引个数 × 单个上限」只是各实例受该设置管理的缓冲池预算之和，不能作为进程 RSS 的硬上界；Go 堆和其他原生分配也会占用内存。
代码**没有进程级的总预算**，应结合实际 RSS 评估多个索引及首次建索引的总需求（见下方“内存占用与硬件要求”）。

**内存上限的默认值**：`moox-storage-view` 启动时按主机内存推算，取 1/16，下限 128MB、上限 2GB。在容器里取 cgroup 限制和物理内存中较小的一个；读不到主机内存（非 Linux 开发机）时用 256MB。
推算结果随主机规格变化，不需要在部署时手工填写：

| 主机内存 | 单个索引上限 | 说明 |
| --- | --- | --- |
| 2GB 及以下 | 128MB | 取下限；应显式配置更小的值或减少 View |
| 4GB | 256MB | |
| 8GB | 512MB | |
| 16GB | 1GB | 线上 Storage 主机（15480MB）约 967MB |
| 32GB 及以上 | 2GB | 取上限 |

- 1/16 是当前代码采用的单实例预算比例，不是启动时预留的内存，也不保证所有负载都足够。应结合最大索引的查询、写入和重建工作集，以及主机剩余内存调整。
  历史运行曾记录：256MB 的上限在建一个 211MB 的索引（历史回填）时被顶满，报 `Out of Memory Error: failed to pin block`。
  索引文件超过 `max_view_file_bytes`（默认 4GiB）只告警；文件告警线和单实例内存预算分别控制不同资源。
- 历史运行记录作参照（2026-10-28，重启 1 小时后；本次文档审查未重新测量）：Storage 主机 15.5GB，`storage-view` 打开 36 个索引文件，磁盘合计约 2.7GB（最大的是 crypto 5m K 线 615MB、两个 1m K 线各约 470MB，另有 7 个因子结果集各 120～190MB），
  进程常驻内存约 7.8GB（峰值 8.5GB），其中 Go 堆约 60MB。RSS 与 Go 堆的差值还包含原生分配等，不能仅据差值精确归因。
- 启动日志会记录生效值和来源，例如 `storage view DuckDB 单个索引内存上限 967MB（主机内存 15480MB 的 1/16，…）`。
- 需要固定某个值时设置环境变量 `MOOX_STORAGE_VIEW_DUCKDB_MEMORY_LIMIT`（正整数加 `KB`/`MB`/`GB`/`TB`），显式配置优先于推算；留空等同未配置。原生部署不需要额外配置。
- 同时可用 `MOOX_STORAGE_VIEW_DUCKDB_THREADS`（1–8，默认 1）和 `MOOX_STORAGE_VIEW_DUCKDB_MAX_OPEN_CONNS`（1–64，默认 4）限制每个索引的线程和连接数。

**内存占用与硬件要求**（新建 View、给 View 加标的、新增因子结果集之前先估算）：

以下倍数和行大小来自历史运行观测，只供相近负载粗估；源码不保证内存与文件大小线性对应，也没有这些倍数构成的 RSS 上界。字段类型、压缩率、查询、写入批次和重建并发都会改变需求。

- 历史样本的稳态 RSS 约为**所有索引文件大小之和的 2.5～3 倍**；可将它用作初始估算，再对照 `duckdb_memory()` 与进程 RSS 实测。仅凭内存上涨后稳定，不能判定是否存在泄漏。
- 单个 View 的行数可按序列数 × `view_rows_per_series` 粗估，但历史不足和 `max_age` 过滤会使实际行数更少。历史样本的压缩后磁盘占用约每行 100～150 字节；500 多个标的、每标的一个序列、每序列 1 万根的 5m K 线 View 曾约为 600MB 文件、1.5～2GB 常驻，不能直接套用于所有 Dataset。
- 历史估算还为建索引时的回填预留最大索引文件大小的 1～1.5 倍额外内存，这不是峰值保证。2026-10-28 的运行记录曾在未限制历史写入年龄的重算期间达到约 13.6GB；当前 `max_age` 会过滤超期写入，但不会主动清除已有旧行，也不限制总 RSS。
- **容量粗估**：可先按「全部 View 文件之和 × 3 + 最大索引 × 1.5 + storage-primary / EventBus 等进程的实测占用」再留 20% 余量。历史样本中其他进程约 2GB，据此估算 15.5GB 主机容纳约 3GB View 文件；这不是部署保证，必须结合目标负载测量。
  余量不足时考虑升配、缩小 `view_rows_per_series`、为高频率设更短的 `[storage_view.max_age]` 或减少 View；调大单索引预算不能增加主机容量。调整 View 年龄上限不会立即回收现有索引。
  大批量历史重算和多个 View 建索引应错峰，并监控实际峰值。
- 可观测：`moox_storage_view_expired_rows_dropped_total`（被最长保留期挡掉的行）、用量日志里的“内存合计 / 进程常驻内存”、`moox_storage_view_*` 指标；监控上要给 Storage 主机的内存留告警。

**用量日志**：`moox-storage-view` 启动 30 秒后记录一次，之后每 5 分钟一次，读的是每个索引的 `duckdb_memory()`：

- 汇总行：`storage view DuckDB 资源 索引=17 内存合计=… 溢出临时文件合计=0MB 单个上限=967MB 进程常驻内存=… 内存最多：空间/View …MB；…`，列出内存最多的 3 个索引。
- `storage view DuckDB 内存接近上限 index=…`：某个索引内存用到上限的 80% 以上，再大一点的写入或查询就会开始溢出，甚至 OOM。
- `storage view DuckDB 发生磁盘溢出 index=… 溢出=…`：该索引当前有数据写进了临时目录。
- 这两类提示行反复出现时，检查查询、批次大小和建索引负载，并对照主机 RSS 余量；有足够余量时再考虑调大 `MOOX_STORAGE_VIEW_DUCKDB_MEMORY_LIMIT`，否则先减少工作集或错峰。长期只有汇总行且内存远低于上限时，无需仅为消除告警调整。
- 在容器或内存很小的主机上，对照“进程常驻内存”，确认索引合计加上其他部分没有逼近主机内存。

**临时目录的作用**：DuckDB 可把部分中间状态写到 `temp_directory` 里的临时文件，需要时再读回；这不能保证所有操作都能在 `memory_limit` 内完成，写入或重建仍可能出现 OOM。
它只是易失的工作区，已提交的数据在 `.duckdb` 主文件和 `.wal` 里；进程退出后临时文件没有用处，无人使用时可以直接删除。
临时文件名只包含块大小类别和序号（例如 `duckdb_temp_storage_S32K-0.tmp`），不含数据库名。

**每个索引用自己的临时目录**：目录固定为 `<索引文件>.tmp`（例如 `view_xxx.duckdb.tmp`）。
不能让多个索引共用一个目录：各实例的临时文件都从 `-0` 开始编号，同目录下会重名，一个实例清理时会删掉另一个实例正在用的文件，
那个实例的下一次提交就会失败，之后该索引一直写不进去（见下面的排障）。这个问题曾在线上出现过一次。

- 索引被删除时临时目录一并删除；新建索引的准备文件改名为正式索引后，准备阶段的临时目录也会清掉。
- 启动时清理中断遗留的准备文件及其临时目录。
- 这些目录平时是空的，只有内存吃紧时才有文件。磁盘被它占满说明某个查询或写入批次的工作集远大于单个索引上限，
  应优化查询或批次，仅在主机内存有余量时调大上限；不要删除正在使用的临时文件。

**排障：View 水位停滞，日志反复出现“活动索引写入失败 … Duplicate key”**

- 现象：某个 View 的输出水位停住，监控报“数据停止更新”（`dataset:storage_view:…`）；`storage-view` 日志每秒几条
  `storage view 活动索引写入失败 … Constraint Error: Duplicate key "subject_id: …"`，涉及的标的集中在少数几个。
- 找首条：先用 `moox-cli monitor logs --component storage-view --keyword 索引写入失败` 看最早的一条（重要日志保留 30 天，同一位置每分钟只留 10 条）；
  要看完整上下文再到 storage 主机 `grep -a "索引写入失败" /data/moox/storage/current/storage-view/logs/trpc.log*`（只留最近 10MB×5）。如果首条是
  `Failed to commit: Failed to create checkpoint … Could not remove file … duckdb_temp_storage_…tmp: No such file or directory`，
  就是一次提交失败后索引的内存状态与磁盘不一致，后续重试永远撞主键，不会自愈。
- 处理：重启 `storage-view`（`restart.sh --components storage-view`）。数据不会丢，WAL 随启动重放，各 View 中断几秒；
  上游数据集和 Primary 不受影响。
- 确认：重启后日志里不再出现“活动索引写入失败”，该 View 的输出水位追上数据集，监控告警自动恢复。
- 预防：升级到每个索引独立临时目录的版本（含 `index_manager.go` 的 `indexTempDir`），共用目录不再出现。

**排障：已删除的 View 在监控里一直报“数据停止更新”**

- 原因：进程导出的指标序列不会自己消失，删除 View（例如删除因子任务连同它的结果数据集）后，`storage-view` 仍然带着冻结的
  `moox_storage_view_output_*` 序列上报，Monitor 看到它“还在上报、水位一直不动”，永远判迟到。
- 现在：每轮维护（`maintainOnce`）完整列出活动 View 之后，`ViewMetrics.RetainViews` 删除不在活动清单里的 View 的输出水位、到达时间与按标的统计的序列，
  告警随之恢复；旧版本要重启 `storage-view` 才会清掉。

### 6.5 Pebble 块缓存

storage-primary 用 Pebble 保存字段级事实。窗口读取（`ReadTimeSeriesRows`）先在历史索引里选出行键，再对每一行做一次存在性检查、对每一列做一次点查，所以读取成本约等于「行数 × (列数 + 1)」次 `Get`。
Pebble 的块缓存缓存的是解压后的数据块和索引块；缓存装不下热点时，每次 `Get` 都要重新读出并 snappy 解压。

- **大小**：默认取主机内存的 1/32，下限 64MB、上限 2GB，读不到主机内存时 128MB；线上 Storage 主机（15480MB）是 483MB。
  环境变量 `MOOX_STORAGE_BLOCK_CACHE`（正整数加 `KB`/`MB`/`GB`/`TB`）可显式指定，优先于推算。
- **日志**：打开时写 `storage Pebble 块缓存 483MB（来源）`；启动 30 秒后及之后每 5 分钟写一行 `Pebble 块缓存 占用=…MB/…MB 条目=… 近期命中率=… 累计命中率=…`。
  近期命中率长期偏低、占用顶满上限，说明缓存偏小。
- **为什么不能用默认值**：2026-10-14 为两个 1h K 线因子任务做回填，当时的 `storage-node` 进程（现已并入 storage-primary）CPU 被打到 330% 以上，单个窗口读取 15 秒以上并超时重试。CPU profile 里 52% 的时间在 `snappy.decode`，其中 72% 是在解压索引块。
  把块缓存从 8MiB 放大后，同一个补算的 CPU 采样总量约降到原来的十分之一。
- **仍然偏重的地方**：这次事故发生时，回填和预热读的是 Storage 里整个回看窗口，而且逐期重读；现在因子的计算窗口来自因子机本地存储，Storage 只承担增量同步、读回核对和结果写入。Pebble 读取仍没有并发上限，也不区分在线计算和批量回填。启用成员不再自动提交回填作业，需要历史因子值时才手动补算。这些都会在数据量变大后重新放大负载。

## 7. 查询

| 接口 | 用途 |
| --- | --- |
| `DataView.QueryTimeSeriesRows` | 按 View 查询时序行，支持序列、时间范围、字段选择和稳定分页 |
| `DataView.SearchRecordRows` | 在记录 View 中检索 |
| `DataView.GetViewState` | View 当前的索引标识、代次（建成时的日志头部序号，重建会变）、已建列、覆盖范围与跟随变更日志已扫描到的位置 |
| `DataView.WaitViewApplied` | View 在服务端取日志头部，等自己扫描到不小于它时返回（最多 30 秒）；写入返回后调用它，就能确认写入已经在 View 里可查 |
| `PrimaryStore.ReadTimeSeriesRows` | 读取时序事实（所有调用方都由 storage-primary 的 Pebble 库回答，结果一致）：时间区间或每个序列最近 N 根；不指定标的即整个数据集；`column_names` 必填；只用 `page.size` 与 `page.cursor` 顺序翻页，不能跳页（区间页大小 ≤ 2000，最近 N 根页大小 ≤ 20000 且 ≤ 20 万个值）。selector 最多 100 个 |
| `PrimaryStore.ReadRows` | 按精确键读取（至多 1 万个键），只返回存在的行，可按 `attribute_keys` 取行属性 |
| `PrimaryStore.CountTimeSeriesRows` | 按标的统计时间范围内已有的行数（同一时间点多个 series_tag 只计一次），由 storage-primary 在序列索引上扫描键回答，只回传计数；一次至多 2000 个标的。Collector 完整性检查先用它比对根数 |
| `DataView.CountTimeSeriesRows` | 同样的统计，由 active View 的 DuckDB 回答，供看板类查询使用 |

管理台通过 Admin 的 Storage BFF 访问 Metadata 和 DataView。

**错误码**：业务失败一律放在响应的 `ret_info` 里，不返回框架错误。存储层（元数据库、元数据校验、Pebble）返回带类别的错误（`internal/storeerr`），只在 `retinfo.Code` 一处映射，不看错误文字：

| 类别 | 错误码 | 例子 |
| --- | --- | --- |
| 参数错误 | `INVALID_PARAM` | 缺必填字段、不可变字段被修改、标签不合法、周期截止时间已过 |
| 不存在 | `NOT_FOUND` | 数据集、View、字段组不存在，序列快照没有登记 |
| 冲突 | `CONFLICT` | View 或标签重名、修订号不符、同一 commit_id 或完成标记内容不同、字段组非空 |
| 其他 | `INNER_ERR` | 存储故障、元数据缓存没有发布；Factor 只把它当作基础设施错误重试 |

`GetDataset`、`GetView`、`GetSubject`、`GetField`、`GetSpace` 在对象确实不存在时另用 `DATASET_NOT_FOUND`、`VIEW_NOT_FOUND`、`SUBJECT_NOT_FOUND`、`FIELD_NOT_FOUND`、`SPACE_NOT_FOUND`，读取出错按上表返回（调用方据专用码认为对象已经删掉，不能把读取失败混进来）。`GetDatasetPeriodCompleted` 是例外：数据集不存在或已停用时返回 `INNER_ERR`，因为 Factor 把 `NOT_FOUND` 当作“这一期还没算过”，不能用它表示数据集问题。PrimaryStore 读取不存在或已停用的数据集返回 `NOT_FOUND`、`INVALID_PARAM`；写入与完成标记遇到同样情况返回 `INNER_ERR`，写入方稍后重试，不丢掉这次写入。DataView 查询的 `VIEW_NOT_READY`（索引还没准备好、活动索引变了）、`VIEW_COLUMN_NOT_FOUND`（请求的列不在 View 里或有歧义）由 View 服务按哨兵错误判定，同样不看错误文字。

不可变字段等原来落到 `INNER_ERR` 的参数错误现在是 `INVALID_PARAM`：Factor 对账结果数据集遇到它时把因子任务标为未就绪、触发事件按 NAK 重试，等下一轮对账，而不是像以前那样继续计算、写入时再被拒绝。

## 8. 鉴权

- primary、view 两个角色各有必填密钥（`MOOX_STORAGE_PRIMARY_AUTH_SECRET`、`MOOX_STORAGE_VIEW_AUTH_SECRET`），不允许空密钥；
  PrimaryStore 与 DataView 校验请求里的 HMAC，Metadata 不验签，只靠网关的逐方法 ACL。
- 独立[外部接入模块](外部接入.md)接受 `scf-collector`、`factor-engine`、`archive-worker`、`collector-operator`、`moox-skill` 五类外部身份；
  逐方法白名单在 `packages/servicecatalog/catalog.yaml` 的 `principals` 中声明。SCF 只可调用 `CommitTimeSeriesBatch` 与 `UpsertFields`，不再领取 Timer 批次，
  不能维护标签或元数据；这些管理调用由内部 `collector` 身份执行。
- Access 验证外部签名后以内部 `access` 身份重新签名转发；Storage 请求体里的 AppId 只用于服务签名与日志，不参与授权。
- **写入权限只靠网关 ACL**：Metadata 与 PrimaryStore 的写方法（建、改、删数据集与 View、`UpsertFields`、`CommitTimeSeriesBatch`、周期报告等）
  放行给哪些调用方，由 `catalog.yaml` 里读、写分开的 ACL 规则决定；Storage 内部没有任何按业务身份（因子、采集等）的写入判断，也没有数据集级的写入属主。
- access 用 SQLite 记录 nonce 防重放（`data/access/nonces.db`）。

| `reset-metadata` | 系统重置里 Storage 的元数据部分：备份元数据库到 `metadata/reset-backups/`（保留最近 3 份）后清空全部业务定义（空间、数据源、标的与标签、数据集与字段、View），再用 `--seed` 重新导入种子；保留标的修订号（修订号单调递增，调用方靠它判断缓存是否过期）。**必须先暂停 Storage**（`<包根>/pause.sh`；不能用 `stop.sh`，主机守护会把停掉的组件拉起），需要 `--yes`，`--dry-run` 只列行数；每张表必须在清单里归类，schema 新增表漏了清单会拒绝执行。通过 `moox-cli storage reset-metadata` 调用 |
| `delete-view` | 离线删除 `--view <空间>/<视图 ID>` 指定的一个 View 元数据（`--yes`、`--metadata-db`、`--package-root`；`storage-view` 必须已停止）；控制台没有删除视图的入口，下线单个 View 用它，物理索引由 View 清理定时器回收 |

清空全部行数据（含已登记的序列快照）不用维护命令：`<包根>/pause.sh` 暂停 Storage、删除 Pebble 与 View 索引目录后 `<包根>/resume.sh` 恢复，之后必须让 Collector 重新登记，见[部署与运维](../部署与运维.md#清空全部数据重新积累)。

`setup init` 提供业务 seed 导入，但仍包含旧部署假设；原生安装的初始化边界见[部署与运维](../部署与运维.md)。
这些维护命令（`repair-view`、`reset-metadata`、`delete-view`）按原生部署的接口工作；操作机上用同名的 `moox-cli storage <命令>`，它经 SSH 在存储机上执行这些命令并补齐路径参数：
通过包根目录的 `start.sh` / `stop.sh` / `status.sh` / `healthcheck.sh`（转给 `moox-runtime`，不接受位置参数）停启服务和检查状态，
整个 Storage 单元不带参数，单个组件用 `--components`；数据路径按所属组件解析（元数据库和 Pebble 在 `storage-primary`、
View 索引在 `storage-view`），所以 `--package-root` 要指向包根目录（如 `/data/moox/storage/current`），`--storage-conf` 指向 `storage-view` 的配置
（读它的元数据库与 View 索引路径）。`status.sh` / `healthcheck.sh` 输出的是 JSON（按组件给出 `state` 与 `ready`）。
维护命令不调用 Admin，也不连接 EventBus。

## 10. 代码结构

```text
cmd/server            两个角色的进程入口（按 MOOX_STORAGE_ROLE）
cmd/cli               moox-storage-cli
internal/service/metadata      元数据服务与 SQLite 实现、缓存
internal/service/primarystore  写入校验、读取
internal/service/datanode      pebble 存储、outbox 发布、周期账本（运行在 storage-primary 进程内）
internal/service/view          View 构建、维护、跟随变更日志（follow 子包）
internal/service/viewindex     DuckDB / Bleve 索引实现
schema/metadata.sql            元数据表结构
```

DuckDB 需要 CGO；正式的 Linux 版本在本机的 Docker 编译镜像里用 `make build-storage-linux` 构建，环境准备见[构建手册](../构建手册.md)。

## 11. View 访问 Metadata

storage-view 与 Metadata、PrimaryStore 同机部署，两者都**直连**、带服务签名，不经网关 ACL（访问 Metadata 用 View 密钥 `MOOX_STORAGE_VIEW_AUTH_SECRET`，访问 PrimaryStore 用 Primary 密钥 `MOOX_STORAGE_PRIMARY_AUTH_SECRET` 签名）：Metadata 默认目标 `ip://127.0.0.1:20100`（`MOOX_STORAGE_METADATA_TARGET`），
storage-view 只读 View 列表（`ListViews`，列随 View 一起返回），不往元数据写任何状态；这些读方法与其他模块共享、不验签，访问控制靠网关 ACL；PrimaryStore 默认目标 `127.0.0.1:20102`，只用于读历史与跟随变更日志。
storage-view 进程本身不使用网关客户端，服务目录里也不把它登记为任何服务的调用方。storage-view 对外只提供 DataView 一个服务，经网关被其他模块调用；建索引、写索引都在进程内完成，没有对外的索引接口。

Storage 内部的数据面使用角色认证直接调用 tRPC。View 到 PrimaryStore 的历史读取保留五分钟超时。内部 tRPC 客户端和监听显式使用 go-net，避免 Linux SDK 自动选择 tNET。旧 Metadata 目标/协议/网络环境变量、Primary 协议/网络环境变量、`storage.view.storage_rpc` 及无用服务名配置已移除；配置加载拒绝已删除字段、未知网关字段和重复键。当前 Storage 业务监听均为原生 tRPC；原生单元部署已接入按角色分发签名身份与 Storage 凭据。
