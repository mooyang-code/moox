# 存储（Storage）

Storage 是 MooX 的事实存储与查询中心：保存行情、因子结果、系统指标等全部时序与记录数据，
维护空间、标的、标签、数据集等元数据，并为每个数据集提供可重建的查询 View。

代码位置：`modules/storage`。

## 1. 进程与端口

Storage 由同一个二进制按 `MOOX_STORAGE_ROLE` 启动为不同角色：

| 进程 | 角色 | 主要服务与端口 |
| --- | --- | --- |
| `moox-storage-primary` | Metadata + PrimaryStore | Metadata 原生 tRPC `20100`，PrimaryStore 原生 tRPC `20101`、`20102`，DataNode 管理 tRPC `20106`，健康 `20210` |
| `moox-storage-node` | DataNode | DataNodeRuntime tRPC `20107`，健康 `20212` |
| `moox-storage-view` | View | DataView 原生 tRPC `20103`，ViewIndex tRPC `20104`，健康 `20211` |

- **primary**：元数据的增删改查和校验；把写入请求按数据集路由到所属 DataNode。
- **node**：一个固定 `node_id` 的 Pebble 数据目录；负责字段写入、Outbox 事件、采集周期账本、
  过期数据清理。一个节点可以承载多个数据集，但每个数据集只属于一个节点，创建后不可更改。
- **view**：消费 Storage 事件，维护 DuckDB（时序）和 Bleve（记录）索引，提供查询。

SCF 和因子引擎通过独立的[外部接入模块](../../modules/access/README.md)访问，入口为 `moox-access`（见第 8 节）。

原生 `setup deploy-unit --profile storage` 当前要求三个角色同机，内部 RPC 走 loopback；
DataNode ID 固定为 `storage-node-0`，与默认 seed 及 Collector 一致。

系统不做数据集内分片、副本、选主或在线迁移；节点离线只影响它承载的数据集，
View 离线不阻塞写入，未消费的事件留在 JetStream 中。

## 2. 数据模型

### 2.1 元数据

元数据保存在 primary 的 SQLite（`schema/metadata.sql`，schema 版本 15），主要对象：

| 对象 | 表 | 说明 |
| --- | --- | --- |
| Space | `t_spaces` | 业务域：`crypto`、`stockcn`、`stockhk`、`stockus`、`mooxsys` |
| DataSource | `t_data_sources` | 数据来源：数据集可引用的名字，只有 ID、名称、状态与属性；采集的连接配置在 Collector 的源配置里 |
| Subject | `t_subjects` | 标的（交易对、股票、主机等）：ID、名称、时区、状态与属性；`subject_type`、`market`、`currency` 等业务含义是属性键，Storage 不解释 |
| Tag | `t_tags`、`t_subject_tags` | 标的分组：ID、名称、描述、`mode`、`builtin`、成员统计与属性；市场类型、同步来源、同步周期这类业务含义写在属性里（`market_type`、`sync.source`、`sync.cron`、`sync.timezone`，由 Collector 解释），自动标签的成员由 Collector 按这些属性同步 |
| Dataset | `t_datasets` | 数据集：时序（time_series）或记录（record），绑定一个 DataNode 和保留期；时序数据集只有一个规范频率 `freq`，创建后不可修改 |
| FieldGroup / Field | `t_field_groups`、`t_fields` | 数据集字段，只增不删，类型不可改 |
| DatasetColumn | `t_dataset_columns` | 数据集的列定义；来源分三类：`FIELD`（引用字段，身份是 `origin_id`）、`CUSTOM`（数据集自己定义的值列，身份就是列名、不带 `origin_id`，因子 ID、成员键等生产者信息由写入方放在列属性里）、`SYSTEM` |
| View | `t_views`、`t_view_columns` | 面向查询的视图，只索引一个 Dataset；`freq` 由 Storage 按所属 Dataset 填写；由使用方（Collector、factor-mgr）自己创建、扩展与删除 |
| View 运维状态 | `t_view_index_builds`、`t_view_rebuild_logs`、`t_view_period_dataset_states`、`t_view_sync_points` | 索引构建、重建日志、周期就绪状态、同步点 |
| DataNode / Device | `t_data_nodes`、`t_storage_devices` | 节点注册与存储设备 |
| 标的修订号 | `t_space_revisions` | 按空间单调递增的 `subjects_revision`：标的（状态、属性、增删）、标签成员、标签属性、数据集（创建、删除、标的范围）变化时由触发器在同一事务内递增；`GetDataset` 响应带回，调用方用它判断缓存的标的元数据是否过期 |

`t_space_revisions` 与触发器全部 `IF NOT EXISTS`：执行一次 `moox-storage-cli init` 即可补建。runtime 托管的 storage-primary 启动时不执行 init；单元安装由 setup 在候选目录内 init，只换二进制的原生发布要先备份元数据库并执行 init 再换二进制。

数据集创建后为 disabled 状态，需要通过只读的激活检查后显式激活，激活后与 DataNode 的绑定锁定。
Storage 不托管任何默认 View：数据集的 View 由业务模块自己建（Collector 为采集结果建浏览 View，factor-mgr 为因子结果数据集建结果 View），数据集属性、列属性也全部由业务模块自己维护，Storage 不读取、不锁定、不校验业务含义。
`data_source_id` 对所有数据集都可选，填写时校验引用存在。

命名规则见[元数据命名规范](../元数据命名规范.md)。

### 2.2 行身份

```text
时序：space_id + dataset_id + subject_id + freq + data_time(UTC) + series_tag
记录：space_id + dataset_id + record_id + version
```

- `series_tag` 是可选的不透明字符串，空字符串表示默认序列；推荐写成 `venue:binance` 这样的约定，
  Storage 不解析其内容。范围查询中“不设置”表示全部序列，“设置为空”表示只要默认序列。
- `data_time` 统一保存为 UTC、9 位纳秒精度。
- 写入是字段级 Upsert：可以新增、覆盖或补写历史行的某些字段，所有字段都允许缺失。
- 记录写入必须带 `version`；读取时不指定版本则取字节序最大的版本。

### 2.3 物理布局

DataNode 使用 Pebble，key 空间按用途分区：`0x01` 字段、`0x02` 属性、`0x03` 时序历史索引、
`0x04` 序列历史索引，另有 `__outbox/`、`__meta/` 等内部前缀。布局版本为 4，写在数据目录的
版本文件中，版本不符时拒绝启动。

时序数据的物理 key 把规范化的时间桶 `bucket_start` 放在数据集之后，过期清理可以按
`(space, dataset, bucket)` 做有界的 `DeleteRange`（不逐个读取 key），再异步 Compact 回收空间。

### 2.4 保留策略

保留期不由数据集各自声明，而是由 `moox-cli` 从 `moox.toml` 的 `[storage_retention]` 与 `[storage_view]`
渲染为策略 JSON。原生安装向各 Storage 角色的发布目录写入 `config/storage-policy.json`，
`storage.policy_file` 指向角色内副本；primary 与 view 使用同一策略内容，缺失或非法时拒绝启动。
旧平铺部署使用 `<storage_root>/config/storage-policy.json`，不能用该路径推导原生配置位置。

- **保留期与因子回看根数是关联的配置**：因子引擎预载、补算要从 Storage 读回「任务里启用成员的最大回看根数」那么多历史，保留期装不下就读不全。`setup init` / `setup factors` 初始化因子时核对：保留期必须大于最大回看根数，crypto 等 7×24 市场装不下报错并写明至少要调到多少（`storage_retention.spaces.<空间>.<频率>`），股票等交易时段市场按日历估算只给提醒；View 的 `bars` 同理要被保留期装下（`Policy.Coverage`）。改因子表达式的窗口、改保留期、改 View 根数时要一起看。
- 时序数据集的生效保留期按 `(space_id, freq)` 解析：空间配置优先，没有时用全局默认；全局默认覆盖
  全部**标准频率**（30s、1m、5m、15m、30m、1h、4h、1d、1w、1mo）。合成出来的非标准频率（如 45m、2h）没有单独配置时，
  沿用时长不超过它的最大标准档（45m → 30m，2h → 1h，12h → 4h），先看空间覆盖再看默认；也可以在配置里为它单独写一项。
  因此每个时序数据集都有确定的保留期。记录型数据集不过期。
- Metadata 的 `GetDataset`、`ListDatasets` 和 DataNode 列表返回只读的 `retention`（`<n>h` 或
  `forever`）与 `retention_source`（`default`、`space`、`record`）；写接口没有保留字段。
- primary 每小时清理一次：对每个活跃时序数据集计算 `cutoff = now - 保留期` 并按天桶截断，调用
  DataNode 的 `CleanupExpiredBuckets` 删除更早的行与历史索引。实际保留在保留期到多一天之间。
  `forever` 跳过。每次清理记录日志和指标 `moox_storage_dataset_cleanup_cutoff_timestamp_seconds`、
  `moox_storage_dataset_cleanup_duration_seconds`、`moox_storage_dataset_cleanup_failures_total`；
  DataNode 上报 Pebble 磁盘占用 `moox_storage_node_pebble_disk_bytes`。

## 3. 写入路径与事件

```text
调用方 ─► PrimaryStore（一次请求一个数据集；校验数据集、字段、类型）─► 数据集所在的 DataNode
DataNode：锁外编码 KV、构造事件；outboxMu 内查 commit 标记、分配编号，一个 Pebble Batch 写入 字段/属性 + __outbox/<id> + 变更日志 + commit 标记
Outbox Relay：按 ID 顺序同步发布到 EventBus，失败即停止，只删除连续成功的前缀
事件压缩：发布器默认压缩，信封不小于 256B 且压缩后明显变小时以 zstd 字典压缩发布（content type 为 `application/vnd.moox.event+protobuf+zstd`），字典按事件所属空间选择，消费端经 `events.DecodeRaw` 透明解压。因子结果行事件每期约 300KB（压缩后约 190KB）。EventBus 部署在存储机上，storage-node 到 storage-view 的这条管道是同机回环，不再经公网往返；其他主机（因子机、控制机、海外机）仍经公网连接 EventBus，压缩对它们照样有效；新增或更换字典必须分两次发布，先让所有消费端能解码
```

谁能调用哪些写方法只由网关 ACL（`packages/servicecatalog/catalog.yaml`）决定：Storage 内部没有按调用方身份（因子、采集等）的写入判断，请求体里的 AppId 只用于服务签名与日志。
代价是 ACL 管的是方法、不管数据集：有写权限的调用方能写所有数据集，模块写错数据集 ID 时 Storage 不会拦。

DataNode 发布的事件都在 `MOOX_STORAGE` Stream：

| 事件 | 含义 |
| --- | --- |
| `rows.upserted` v2 | 一次写入的变更行和变更字段（不是全量快照），Subject 精确到数据集 |
| `dataset.period.completed` | 某数据集某频率的一期已完成（complete/degraded），统一的周期完成事件；`source` 为 `ledger`（DataNode 按序列快照账本判定，采集与 K 线合成）或 `producer`（写入方自己报告，因子） |
| `dataset.sync_point` | 数据集同步点，用于等待 View 追上某个写入位置 |

## 4. 采集周期协议与周期完成

DataNode 是“采集周期是否完成”的唯一权威，Collector 通过 PrimaryStore 调用：

| 方法 | 作用 |
| --- | --- |
| `EnsureDatasetPeriod` | 首次调用时固化该周期的完整序列快照（`series_snapshot`、hash、数量）和截止时间 |
| `CommitTimeSeriesBatch` | 写入行，返回被接受的序列编号；只有完整回执才算成功 |
| `RecordDatasetPeriodFailures` | 上报失败序列，逐个返回 `recorded`、`already_succeeded` 或 `missed_deadline` |
| `GetDatasetPeriodStatus` | 查询周期状态 |

全部预期序列都成功时 DataNode 提前把周期固化为 `complete`；到达截止时间仍未齐则固化为 `degraded`，两者都是原子完成，并写入
`DatasetPeriodCompleted` 标记（`source=ledger`）；标记里只包含截止前被接受且最终仍未成功的序列。删除或恢复
数据集时，其周期账本和索引一并清理。序列快照里的序列身份只有 `subject_id` 与 `series_tag` 两项（`packages/seriesset`，Collector 与 Storage 共用同一份实现，`series_hash` 因此一致）；`series_tag` 由写入方决定，Storage 不解释。

同属 PrimaryStore 的相关方法：`RegisterSeriesSnapshot`（Collector 对账协程在生效周期之前登记序列快照，`EnsureDatasetPeriod` 据此固化周期）、
`DeleteDatasetRows` / `RestoreDatasetRows`（数据集删除、恢复时清理或恢复行数据）。

### 4.1 周期完成事件

不由账本判定的周期（现在只有因子结果）由写入方用 `ReportDatasetPeriodCompleted` 报告（`source=producer`），`GetDatasetPeriodCompleted` 按 `cause_event_id` 或 `period_time` 查询；DataNode 对应的方法是 `AppendDatasetPeriodCompleted`、`GetDatasetPeriodCompleted`，标记存在 `__period_marker` 索引里。
两种来源写出的是同一个事件 `DatasetPeriodCompleted`，`source` 只说明这一期怎么判定完成的，不是业务分类；消费方按自己绑定的数据集与频率筛选，两种来源都接受。字段：

| 字段 | 说明 |
| --- | --- |
| `dataset_id`、`frequency`、`period_time` | 哪个数据集的哪一期 |
| `status` | `complete` / `degraded` |
| `source` | `ledger`（DataNode 账本判定）/ `producer`（写入方报告） |
| `universe_subject_ids`、`failed_subjects` | 本期应有的标的与失败的标的 |
| `committed_positions` | 本期写入在 Outbox 中的位置，View 据此确认数据已进入索引 |
| `snapshot_ref` | `ledger` 来源时的序列快照引用 |
| `cause_event_id` | `producer` 来源时触发本次计算的事件 ID，用于幂等查询 |
| `completed_at` | 完成时间 |
| `detail_type`、`detail` | 写入方自定义的明细（不透明字节）：Storage 原样保存并透传，不解析 |

**写入幂等**：`UpsertFields` 一次只写一个数据集（请求顶层 `space_id`、`dataset_id`，每行必须一致），可选 `commit_id`：同一数据集内同一
`commit_id` 只生效一次，内容相同返回成功、内容不同返回 `CONFLICT`。commit 标记按数据集存放（`__commit/`），永久有效、随删除数据集清理。
不带 `commit_id` 的写入不去重：消息重投时会再写一次相同的行、多发一条行变更事件，View 重复应用无害。

## 5. 因子结果与同步点

- Factor 用 `UpsertFields`（带 `commit_id`）一次写入一个周期的完整结果行（携带列 + 因子列 + 系统列 `__params`），随后用
  `ReportDatasetPeriodCompleted`（`source=producer`）报告这一期完成；`detail_type` 是 `moox.factor.PeriodDetail.v1`，`detail` 是因子自己定义的 `PeriodDetail`
  （`modules/factor/proto/factor.proto`：每个成员的状态、`spec_hash`、`definition_hash`、`gap_subjects` 等），由因子侧校验（`storageio.ValidatePeriodDetail`），Storage 不解析。
- **因子结果列的契约不在 Storage**：结果数据集的值列用 `CUSTOM` 来源（不带 `origin_id`），`column_kind`、`factor_id`、`member_key`、`member_kind`、`output_name` 等放在列属性里，列名与类型的约定由 factor-mgr 建列时自己保证；
  Storage 只校验通用规则（列名唯一、值类型合法、字段列引用存在）。`__params` 是 `json` 类型的列，JSON 文本由调用方解析，Storage 不解析；
  结果 View 的列集合跟随数据集（含 `__params`），View 照常为它建索引，DuckDB 可用 `json_extract` 查询。
- `AppendDatasetSyncPoint` 在数据集事件流中插入同步点，`WaitViewSyncPoint` 等待 View 消费到该点，
  供需要“写后读”的调用方使用。

## 5.1 行变更日志

> 状态：已实现（因子本地K线存储设计 5.1）。

数据集时序行写入（`UpsertFields`、`CommitTimeSeriesBatch`）在同一个 Pebble 批里追加持久化的变更日志（`__changelog/` 键，序号单调、记录被修改的标的与区间），
保留 7 天，由 outbox relay 顺带清理（记录已清理到的序号）。`ReadDatasetChanges`（PrimaryStore 与 DataNode 都有）按游标（节点、存储、序号）读取，
`from_head` 取当前位点；游标早于已清理的序号时返回 `gap`（断档）。因子机据此在本地时序存储里跟进修正；调用方是 `factor-engine`（服务目录里已授权）。

数据集字段的 `attributes.fill` 声明缺失行的填充规则：`prev`（默认）、`prev_close`、`zero`；Storage 原样保存，由因子机本地存储解释，取值无效时按列名取默认规则。
View 默认保留 10000 根（`view_rows_per_series`），各频率默认保留期要装得下（30s 90h、1m 35d（要装得下默认因子 EMA 的最大回看）、5m 35d、15m 105d、30m 210d、1h 420d、4h 1700d；1d 及以上永久），
单 View 文件容量阈值 `max_view_file_bytes` 默认 4GiB（1 万根的 1m K 线 View 约 1.1GB）。
View 另有按空间 × 频率的最长保留天数 `[storage_view.max_age]`（写法同 `[storage_retention]`：`defaults` 必须覆盖全部标准频率，`spaces.<空间>` 覆盖默认；
默认值恰好装下 1 万根：30s 90h、1m 7d、5m 35d、15m 105d、30m 210d、1h 420d、4h 1700d，1d 及以上永久，股票空间按交易时段放宽）；`setup` 校验 7×24 市场的期限装不下 `view_rows_per_series` 根时报错，交易时段市场只警告。

## 6. View

### 6.1 索引与重建

- 一个 View 只索引一个 Dataset。View 列名就是 Dataset 列名，不带数据集前缀，`origin_id` 与列名相同；
  Metadata 写入 View 列时校验该列是所属 Dataset 的活跃列。按精确 Key 读 Primary 与按时间范围读 View
  使用同一套列名。
- 时序 View 使用 DuckDB 文件，主键为 `(subject_id, freq, data_time, series_tag)`；记录 View 使用 Bleve，
  支持全文检索。
- 每个 View 有 A/B 两份独立索引。触发重建时创建新索引并安装实时双写，从 Primary 回填历史，
  回填只填缺失值、不覆盖实时写入；完成后在 Metadata 中以 CAS 激活新 revision，DataView 原子切换，
  旧索引在宽限期后删除。新索引写入或回填失败只终止本次构建，旧索引继续服务。
- **View 的写入路径**（`viewindex/duckdb/bulk_write.go`）：一批行按携带的字段集合分组，每组两条语句——先对 `view_rows` 里还不存在的键按序列累加 `view_series_counts`，
  再整批 UPSERT；每个列绑定成一个 LIST 参数、用 `unnest` 展开（驱动不支持 LIST 里的 NULL 与 BLOB：NULL 用占位值加布尔掩码，BLOB 用十六进制文本再 `from_hex`）。
  旧实现是每 32 行一条多值 INSERT、每行两轮 SQL，本机实测导入形态 8055 → 93982 行/秒（11.7 倍），实时形态 6177 → 27686 行/秒（4.5 倍）；
  旧实现原样留在 `legacy_write_oracle_test.go` 作对照，`bulk_write_equivalence_test.go` 用同一批输入写两个索引、逐行逐列比较结果。
  **按最长保留天数过滤写入**：所有写入路径（实时事件、补采、重建回填）最后都经 `Service.writeIndex`，写进索引之前先丢弃 `data_time` 早于“当前时间 − `[storage_view.max_age]` 期限”的时序行
  （K 线 View 与因子结果集 View 一样；记录型行、未配置期限的频率、永久保留的频率不过滤）。补采、导入与因子历史重算带来的旧行因此不进 View；主存 Dataset 与因子机本地存储照常保留全部历史。
  丢弃行数记在指标 `moox_storage_view_expired_rows_dropped_total{space,freq}` 和 `storage view 丢弃超过最长保留期的行` 日志里。
  这条过滤只管新写入，已在 View 里的行仍按根数整理，不按天数清；根数窗口之内的旧行（期限恰好装满根数，所以通常没有）只在重建时被回填窗口排除。
  历史导入仍建议只写最近窗口（`moox-cli import --tail-rows`），省得 Storage 读写一遍再丢弃。
- 时序 View 只按根数保留：每个序列保留最近 `view_rows_per_series` 根（默认 10000），超过 ceil(1.2 × N) = 12000 根时
  触发整理；周末和节假日不影响有效根数。根数由 `moox.toml` 的 `[storage_retention] view_rows_per_series` 统一配置。DataView 查询响应的 `retained_rows_per_series` 是活动索引建立时记录的保留根数与当前配置中较小的一个（调大配置要等重建成功才变大；旧索引没有记录时为 0，表示未知）。
- 重建回填不指定标的，用 `ReadTimeSeriesRows(latest_per_series = N)` 按游标逐页读取：DataNode 在序列索引上按
  subject_id、series_tag 顺序逐个序列、从新到旧取最近 N 根，一页最多 2 万行且不超过 20 万个值，同一标的可以跨页。
  耗时只与「序列数 × 根数」有关、与历史长度无关，不依赖数据集是否绑定了标的标签。某一页失败（含超时）时整次重建按
  现有失败处理重试，不静默跳过标的。历史不足目标根数时以现有数据激活。记录型 View（Bleve）不按根数，从活跃索引整体复制。
- **View 的行为由属性声明**，Storage 只读这三个，不认业务标记：
  - `follow_dataset_columns=true`：数据集加列后，View 在维护循环里原地扩展，跟随数据集的列（因子结果 View 用）。扩展完成前到达的行事件按 View 当前的列投影应用，尚未扩展出来的新列直接裁掉，不阻塞消费、不回填；
    新列在 View 里晚生效一两期，需要这几期的值时扩展完成后对那几期重算（行会带上新列）。主库里的值不受影响。
  - `rebuild_source`：`active_then_primary`（默认，先复制活动索引再从主库补）或 `primary`（只从主库历史重建，主库还没有数据时允许先空着；因子结果 View 用）。
  - `maintenance_priority`：维护顺序，整数、越小越先，默认 50（Collector 的浏览 View 为 0，因子结果 View 为 10）。
  因子结果 View 由 factor-mgr 创建与删除（`view_role=factor_result` 只是页面用来找到它的业务标记，Storage 不读）；删除因子结果数据集的顺序是先删 View、再清空行、最后删数据集。
- View 不保存也不返回行属性（因子结果写入本来就不带行属性）；行属性只由 `PrimaryStore.ReadRows` 按 `attribute_keys` 返回。
- 文件超过 `max_view_file_bytes` 时：时序 View 触发容量重建，记录型 View 只告警不截断。
  仅由容量触发的重建要等 View 消费者积压足够小、连续空闲若干次后才开始。
- 每次实际重建或被门禁跳过都记录到 `t_view_rebuild_logs`。

### 6.2 事件消费

View 按数据集消费 `MOOX_STORAGE` 的事件，只有一种消费方式：每个数据集一个动态 durable `view_<12 位数据集哈希>`（`events.StorageViewConsumerName`，名字里不带业务含义）。
不同数据集的消费者并行，同一数据集内按顺序处理。

- 投递参数是全局配置 `storage.view.fetch_batch`、`max_workers`、`max_ack_pending`、`ack_wait_ms`（`config/storage.yaml`），所有数据集共用；前三项默认都是 1，避免同一行的两次更新先后颠倒，导入历史后追平不够快再调大。
- 动态消费者由 View 清单协调器根据活动 View 引用的数据集创建和回收，名称由数据集身份哈希得到，保持稳定，不按空间或数据集做白名单过滤。
  JetStream 消费者的过滤条件不可修改，因此不能用通配消费者跟随新数据集变化。
- 同一数据集的行、标记和同步点进入同一个有序队列，保证行先于标记应用；不同数据集并行。
  连续的行事件在不跨越标记的前提下合并为一次索引写入。
- 写入 Active 失败时保持当前投递并本地退避；Subject、Proto、负载等永久错误执行 `Term`。

### 6.3 就绪事件

View 应用 `DatasetPeriodCompleted` 标记并确认该周期的数据都已进入
索引后，发布 `ViewDataReady`（v2：携带已提交位置、标的全集，并原样透传标记里的 `detail_type`、`detail`）。Strategy 以此作为触发信号：
`detail_type` 是 `moox.factor.PeriodDetail.v1` 时按因子的 `PeriodDetail` 解码，判断每个成员这一期是否可用；是否相关只看事件绑定的 View 与数据集，不再区分完成来源。

就绪事件先进入持久队列；发布失败按有界超时重试，行写入不会因发布失败而回滚。写入围栏记录每个索引
已应用的来源位置，当前按秒批量落盘。行事件可能在围栏落盘前已经 ACK，异常退出会丢失这段进度，
重启后相应就绪事件可能等待同一来源的后续写入；日线或停更数据集等待尤其明显。
该边界与建议见[代码审查](../审查/2026-10-10代码审查.md)。

### 6.4 DuckDB 资源与临时目录

每个时序 View 索引（每个 A/B 槽位）是一个独立的 DuckDB 实例，各自受 `memory_limit` 约束，所以一台主机上的总占用最多是「索引个数 × 单个上限」，不是一个全局上限；**没有进程级的总预算**，索引越多、越大，`moox-storage-view` 越吃内存（见下方“内存占用与硬件要求”）。

**内存上限的默认值**：`moox-storage-view` 启动时按主机内存推算，取 1/16，下限 128MB、上限 2GB。在容器里取 cgroup 限制和物理内存中较小的一个；读不到主机内存（非 Linux 开发机）时用 256MB。
推算结果随主机规格变化，不需要在部署时手工填写：

| 主机内存 | 单个索引上限 | 说明 |
| --- | --- | --- |
| 2GB 及以下 | 128MB | 取下限；应显式配置更小的值或减少 View |
| 4GB | 256MB | |
| 8GB | 512MB | |
| 16GB | 1GB | 线上 Storage 主机（15480MB）约 967MB |
| 32GB 及以上 | 2GB | 取上限 |

- 为什么是 1/16 而不是更小：上限是天花板，不是预留。只有几 MB 的索引不会涨到天花板，主机上的实际占用约等于各索引文件大小之和再加重建时的峰值，
  不是「索引个数 × 上限」。上限应当按能装下最大索引在重建时的工作集来定。
  线上出现过一次：256MB 的上限在重建一个 211MB 的索引（历史回填、激活探测）时被顶满，报 `Out of Memory Error: failed to pin block`。
  索引文件超过 `max_view_file_bytes`（默认 4GiB）才触发容量重建，1 万根的 1m K 线 View 约 1.1GB，重建它需要约 1 到 1.5 倍文件大小的内存，所以上限放到 2GB。
- 线上现状作参照（2026-10-28，重启 1 小时后）：Storage 主机 15.5GB，`storage-view` 打开 36 个索引文件，磁盘合计约 2.7GB（最大的是 crypto 5m K 线 615MB、两个 1m K 线各约 470MB，另有 7 个因子结果集各 120～190MB），
  进程常驻内存约 7.8GB（峰值 8.5GB），其中 Go 堆只有约 60MB，其余全是 DuckDB 原生内存。
- 启动日志会记录生效值和来源，例如 `storage view DuckDB 单个索引内存上限 967MB（主机内存 15480MB 的 1/16，…）`。
- 需要固定某个值时设置环境变量 `MOOX_STORAGE_VIEW_DUCKDB_MEMORY_LIMIT`（正整数加 `KB`/`MB`/`GB`/`TB`），显式配置优先于推算；留空等同未配置。原生部署不需要额外配置。
- 同时可用 `MOOX_STORAGE_VIEW_DUCKDB_THREADS`（1–8，默认 1）和 `MOOX_STORAGE_VIEW_DUCKDB_MAX_OPEN_CONNS`（1–64，默认 4）限制每个索引的线程和连接数。

**内存占用与硬件要求**（新建 View、给 View 加标的、新增因子结果集之前先估算）：

- `storage-view` 的常驻内存主要是 DuckDB 的缓冲池：磁盘上压缩存储，进缓冲池后解压，再加主键 `(subject_id, freq, data_time, series_tag)` 的索引，
  稳态约为**所有索引文件大小之和的 2.5～3 倍**（线上 2.7GB 文件对应约 7.5GB）。DuckDB 没有内存压力时不会把缓冲池还给操作系统，所以重启后一次恢复就会涨到这个水位并停在那里，这不是泄漏。
- 单个 View 的体量 ≈ 标的数 × `view_rows_per_series` 行；线上量级约每行 100～150 字节（磁盘，压缩后）。比如 500 多个标的 × 1 万根的 5m K 线 View 约 600MB 文件、1.5～2GB 常驻。
  每新增一个这样的 View，Storage 主机就要多留这么多内存。
- 峰值另算：重建、历史回填、容量重建期间，最大的索引还要额外约 1～1.5 倍文件大小；因子历史重算若不受 `[storage_view.max_age]` 限制，会把历史行全写进 View（2026-10-28 就是这样把内存涨到 13.6G、拖垮存储机的）。
- **硬件要求**：Storage 主机内存要大于「全部 View 文件之和 × 3 + 最大索引 × 1.5 + Primary / DataNode / EventBus 等进程（约 2GB）」，并留 20% 以上余量。
  当前 15.5GB 的主机只够约 3GB 的 View 文件；超过就要升配、缩小 `view_rows_per_series`、为高频率设更短的 `[storage_view.max_age]`，或减少 View，而不是调大单索引上限。
  不要在 Storage 主机上同时做大批量历史重算或重建多个 View。
- 可观测：`moox_storage_view_expired_rows_dropped_total`（被最长保留期挡掉的行）、用量日志里的“内存合计 / 进程常驻内存”、`moox_storage_view_*` 指标；监控上要给 Storage 主机的内存留告警。

**用量日志**：`moox-storage-view` 启动 30 秒后记录一次，之后每 5 分钟一次，读的是每个索引的 `duckdb_memory()`：

- 汇总行：`storage view DuckDB 资源 索引=17 内存合计=… 溢出临时文件合计=0MB 单个上限=967MB 进程常驻内存=… 内存最多：空间/View/槽位 …MB；…`，列出内存最多的 3 个索引。
- `storage view DuckDB 内存接近上限 index=…`：某个索引内存用到上限的 80% 以上，再大一点的重建或查询就会开始溢出，甚至 OOM。
- `storage view DuckDB 发生磁盘溢出 index=… 溢出=…`：该索引当前有数据写进了临时目录。
- 这两类提示行反复出现，说明上限偏小，应调大 `MOOX_STORAGE_VIEW_DUCKDB_MEMORY_LIMIT`；长期只有汇总行且内存远低于上限，说明有富余，不必调。
- 在容器或内存很小的主机上，对照“进程常驻内存”，确认索引合计加上其他部分没有逼近主机内存。

**临时目录的作用**：DuckDB 的内存超过 `memory_limit` 时不会报错，而是把暂时放不下的中间状态（排序、聚合、Join、检查点前的缓冲）写到 `temp_directory` 里的临时文件，需要时再读回。
它只是易失的工作区，已提交的数据在 `.duckdb` 主文件和 `.wal` 里；进程退出后临时文件没有用处，无人使用时可以直接删除。
临时文件名只包含块大小类别和序号（例如 `duckdb_temp_storage_S32K-0.tmp`），不含数据库名。

**每个索引用自己的临时目录**：目录固定为 `<索引文件>.tmp`（例如 `view_xxx_a.duckdb.tmp`）。
不能让多个索引共用一个目录：各实例的临时文件都从 `-0` 开始编号，同目录下会重名，一个实例清理时会删掉另一个实例正在用的文件，
那个实例的下一次提交就会失败，之后该索引一直写不进去（见下面的排障）。这个问题曾在线上出现过一次。

- 索引被删除（A/B 轮换、重建后的退役）时临时目录一并删除；新建索引的准备文件改名为正式索引后，准备阶段的临时目录也会清掉。
- 启动时清理中断遗留的准备文件及其临时目录。
- 这些目录平时是空的，只有内存吃紧时才有文件。磁盘被它占满说明某个查询或写入批次的工作集远大于单个索引上限，
  应调大上限或优化查询，不要靠清理临时文件。

**排障：View 水位停滞，日志反复出现“活动索引写入失败 … Duplicate key”**

- 现象：某个 View 的输出水位停住，监控报“数据停止更新”（`dataset:storage_view:…`）；`storage-view` 日志每秒几条
  `storage view 活动索引写入失败 … Constraint Error: Duplicate key "subject_id: …"`，涉及的标的集中在少数几个。
- 找首条：`grep -a "活动索引写入失败" storage-view.log | head -1`。如果首条是
  `Failed to commit: Failed to create checkpoint … Could not remove file … duckdb_temp_storage_…tmp: No such file or directory`，
  就是一次提交失败后索引的内存状态与磁盘不一致，后续重试永远撞主键，不会自愈。
- 处理：重启 `storage-view`（`restart.sh --components storage-view`）。数据不会丢，WAL 随启动重放，各 View 中断几秒；
  上游数据集和 Primary 不受影响。
- 确认：重启后日志里不再出现“活动索引写入失败”，该 View 的输出水位追上数据集，监控告警自动恢复。
- 预防：升级到每个索引独立临时目录的版本（含 `index_manager.go` 的 `indexTempDir`），共用目录不再出现。

**排障：已删除的 View 在监控里一直报“数据停止更新”**

- 原因：进程导出的指标序列不会自己消失，删除 View（例如删除因子任务连同它的结果数据集）后，`storage-view` 仍然带着冻结的
  `moox_storage_view_output_*` 序列上报，Monitor 看到它“还在上报、水位一直不动”，永远判迟到。
- 现在：每轮维护（`maintainOnce`）完整列出活动 View 之后，`ViewMetrics.RetainViews` 删除不在活动清单里的 View 的输出水位、到达时间与按标的统计的序列，
  告警随之恢复；旧版本要重启 `storage-view` 才会清掉。

### 6.5 DataNode 的 Pebble 块缓存

DataNode 用 Pebble 保存字段级事实。窗口读取（`ReadTimeSeriesRows`）先在历史索引里选出行键，再对每一行做一次存在性检查、对每一列做一次点查，所以读取成本约等于「行数 × (列数 + 1)」次 `Get`。
Pebble 的块缓存缓存的是解压后的数据块和索引块；缓存装不下热点时，每次 `Get` 都要重新读出并 snappy 解压。

- **大小**：默认取主机内存的 1/32，下限 64MB、上限 2GB，读不到主机内存时 128MB；线上 Storage 主机（15480MB）是 483MB。
  环境变量 `MOOX_STORAGE_NODE_BLOCK_CACHE`（正整数加 `KB`/`MB`/`GB`/`TB`）可显式指定，优先于推算。
- **日志**：打开时写 `storage node Pebble 块缓存 483MB（来源）`；启动 30 秒后及之后每 5 分钟写一行 `Pebble 块缓存 占用=…MB/…MB 条目=… 近期命中率=… 累计命中率=…`。
  近期命中率长期偏低、占用顶满上限，说明缓存偏小。
- **为什么不能用默认值**：2026-10-14 为两个 1h K 线因子任务做回填，`storage-node` 的 CPU 被打到 330% 以上，单个窗口读取 15 秒以上并超时重试。CPU profile 里 52% 的时间在 `snappy.decode`，其中 72% 是在解压索引块。
  把块缓存从 8MiB 放大后，同一个补算的 CPU 采样总量约降到原来的十分之一。
- **仍然偏重的地方**：这次事故发生时，回填和预热读的是 Storage 里整个回看窗口，而且逐期重读；现在因子的计算窗口来自因子机本地存储，Storage 只承担增量同步、读回核对和结果写入。DataNode 的读取仍没有并发上限，也不区分在线计算和批量回填。启用成员不再自动提交回填作业，需要历史因子值时才手动补算。这些都会在数据量变大后重新放大负载。

## 7. 查询

| 接口 | 用途 |
| --- | --- |
| `DataView.QueryTimeSeriesRows` | 按 View 查询时序行，支持序列、时间范围、字段选择和稳定分页 |
| `DataView.SearchRecordRows` | 在记录 View 中检索 |
| `PrimaryStore.ReadTimeSeriesRows` | 读取时序事实（所有调用方都由 DataNode 回答，结果一致）：时间区间或每个序列最近 N 根；不指定标的即整个数据集；`column_names` 必填；只用 `page.size` 与 `page.cursor` 顺序翻页，不能跳页（区间页大小 ≤ 2000，最近 N 根页大小 ≤ 20000 且 ≤ 20 万个值）。selector 最多 100 个 |
| `PrimaryStore.ReadRows` | 按精确键读取（至多 1 万个键），只返回存在的行，可按 `attribute_keys` 取行属性 |
| `PrimaryStore.CountTimeSeriesRows` | 按标的统计时间范围内已有的行数（同一时间点多个 series_tag 只计一次），由 DataNode 在序列索引上扫描键回答，只回传计数；一次至多 2000 个标的。Collector 完整性检查先用它比对根数 |
| `DataView.CountTimeSeriesRows` | 同样的统计，由 active View 的 DuckDB 回答，供看板类查询使用 |

管理台通过 Admin 的 Storage BFF 访问 Metadata 和 DataView。

## 8. 鉴权

- primary、node、view 三个角色各有必填密钥（`MOOX_STORAGE_PRIMARY_AUTH_SECRET` 等），所有内部 RPC
  都校验 HMAC，不允许空密钥或以节点 ID 代替密钥。
- 独立[外部接入模块](外部接入.md)接受 `scf-collector`、`factor-engine`、`archive-worker`、`collector-operator`、`moox-skill` 五类外部身份；
  逐方法白名单在 `packages/servicecatalog/catalog.yaml` 的 `principals` 中声明。SCF 只可执行周期/批次协议与领取 Timer 批次，
  不能维护标签或元数据；这些管理调用由内部 `collector` 身份执行。
- Access 验证外部签名后以内部 `access` 身份重新签名转发；Storage 请求体里的 AppId 只用于服务签名与日志，不参与授权。
- **写入权限只靠网关 ACL**：Metadata 与 PrimaryStore 的写方法（建、改、删数据集与 View、`UpsertFields`、`CommitTimeSeriesBatch`、周期报告、`DeleteDatasetRows` 等）
  放行给哪些调用方，由 `catalog.yaml` 里读、写分开的 ACL 规则决定；Storage 内部没有任何按业务身份（因子、采集等）的写入判断，也没有数据集级的写入属主。
- access 用 SQLite 记录 nonce 防重放（`data/access/nonces.db`）。

## 9. 运维命令

`moox-storage-cli`（随 Storage 部署）：

| 命令 | 作用 |
| --- | --- |
| `init` | 初始化元数据库 |
| `import-seed` | 导入元数据种子 |
| `register-node` | 注册 DataNode |
| `activate-datasets` | 激活数据集 |
| `repair-view` | 默认备份元数据、重置消费者并提高 desired revision，触发 A/B 重建；删除索引需显式选项 |
| `force-rebuild-view` | 删除旧索引、运行时指针和消费者，从可重放事件重新创建 View |
| `reset-metadata` | 系统重置里 Storage 的元数据部分：备份元数据库到 `metadata/reset-backups/`（保留最近 3 份）后清空全部业务定义（空间、数据源、标的与标签、数据集与字段、View 及其构建/同步状态），再用 `--seed` 重新导入种子；保留 DataNode 登记、存储设备、标的修订号（修订号单调递增，调用方靠它判断缓存是否过期）。**必须先停 Storage**，需要 `--yes`，`--dry-run` 只列行数；每张表必须在清单里归类，schema 新增表漏了清单会拒绝执行。通过 `moox-cli storage reset-metadata` 调用 |
| `reset-view-consumers` | 重置 View 消费者；`--reset-all-storage-data --yes` 还会清空全部行数据（含已登记的序列快照），之后必须让 Collector 重新登记，见[部署与运维](../部署与运维.md#清空全部数据重新积累) |
| `retain-views` | 按保留策略整理 View：删除所有不在 `--keep-view` 清单里的 View（清单必须正好 7 个），会波及因子结果视图等业务模块创建的 View，只适合只有固定 7 个 View 的新环境 |
| `delete-view` | 离线删除 `--view <空间>/<视图 ID>` 指定的一个 View 元数据（`--yes`、`--metadata-db`、`--package-root`；`storage-view` 必须已停止）；控制台没有删除视图的入口，下线单个 View 用它，物理索引由 View 清理定时器回收 |
| `purge-dataset-events` | 清理数据集的积压事件 |
| `period-inventory` | 在停机或一致副本上只读盘点采集周期账本 |

`setup init` 提供业务 seed 导入，但仍包含旧部署假设；原生安装的初始化边界见[部署与运维](../部署与运维.md)。
这些维护命令（`repair-view`、`force-rebuild-view`、`reset-view-consumers`、`retain-views`、`delete-view`）按原生部署的接口工作：
通过包根目录的 `start.sh` / `stop.sh` / `status.sh` / `healthcheck.sh`（转给 `moox-runtime`，不接受位置参数）停启服务和检查状态，
整个 Storage 单元不带参数，单个组件用 `--components`；数据路径按所属组件解析（元数据库在 `storage-primary`、Pebble 在 `storage-node`、
View 索引在 `storage-view`），所以 `--package-root` 要指向包根目录（如 `/data/moox/storage/current`），`--storage-conf` 指向 `storage-view` 的配置
（读它的 View 消费参数）。`status.sh` / `healthcheck.sh` 输出的是 JSON（按组件给出 `state` 与 `ready`）。
涉及 EventBus 的操作（查看消费者过滤、删除消费者、清除数据集事件）不需要 EventBus 凭据，也没有 `--credential-file`、`--eventbus-url` 参数：
命令用 `storage-view` 配置里的 `gateway_client` 身份（原生部署在 `<包根>/storage-view/config/storage.yaml`，caller 必须是 `storage-view`）
经网关调用 Admin 的 `InspectEventBus`、`DeleteEventBusConsumers`、`PurgeEventBusSubjects`，由 Admin 用数据库里的管理员令牌执行（见[管理后台](管理后台.md)）。
`--dry-run` 同样走这条路径（`repair-view`、`force-rebuild-view` 在要删消费者时也一样），网关、Admin、EventBus 任何一段不通都会在停止服务、改动本地状态之前报错；`reset-view-consumers` 还会提前检查所有要清除的主题都在 Admin 允许的范围内。网关目录缓存放在 `<组件目录>/var/storage-cli/`，与 storage-view 进程互不干扰。
`reset-view-consumers` 重启后会等所有 View 重建出活动索引；View 有历史数据时重建要几十分钟（线上 19 个 View 约 26 分钟），建议 `--timeout 60m`。等待超时时重置已经提交，命令会明确报“重置已完成、View 仍在后台重建”，不要重复执行。

## 10. 代码结构

```text
cmd/server            三个角色的进程入口（按 MOOX_STORAGE_ROLE）
cmd/cli               moox-storage-cli
internal/service/metadata      元数据服务与 SQLite 实现、缓存
internal/service/primarystore  写入校验与路由、读取
internal/service/datanode      DataNode：pebble 存储、outbox 发布、周期账本
internal/service/view          View 构建、维护、消费者与清单协调
internal/service/viewindex     DuckDB / Bleve 索引实现
schema/metadata.sql            元数据表结构
```

DuckDB 需要 CGO；正式的 Linux 版本在本机的 Docker 编译镜像里用 `make build-storage-linux` 构建，环境准备见[构建手册](../构建手册.md)。

## 11. View 访问 Metadata

storage-view 与 Metadata、PrimaryStore 同机部署，两者都**直连**、带服务签名（View 密钥 `MOOX_STORAGE_VIEW_AUTH_SECRET`），不经网关 ACL：Metadata 默认目标 `ip://127.0.0.1:20100`（`MOOX_STORAGE_METADATA_TARGET`），
回报索引构建状态、写重建日志、View 周期状态和同步点等 storage-view 专用的 Metadata 方法按这个签名认证；读数据集、列等与其他模块共享的读方法不验签，访问控制靠网关 ACL；PrimaryStore 默认目标 `127.0.0.1:20102`，读历史并写路由就绪同步点（`AppendDatasetSyncPoint`）。
只有维护命令（`moox-storage-cli`）调用 Admin 的 EventBus 检查与清理经网关：命令借用 storage-view 的身份，读 `storage.yaml` 里顶层 `gateway_client` 声明的 `caller: storage-view`、Admin 分配的 `key_id`、`key_file`（密钥路径相对模块配置文件；同一部署目录中的 `host-gateway/config/app.yaml` 提供主机 ID、loopback 地址与私有 CA），网关目录缓存见第 9 节。storage-view 进程本身不使用网关客户端。
网关 ACL 里没有 storage-view 访问 Metadata、PrimaryStore 的规则；storage-view 对外提供的 DataView 查询仍经网关被其他模块调用。

Storage 内部的数据面使用角色认证直接调用 tRPC。View 到 PrimaryStore 的历史修复读取保留五分钟超时；主进程到 DataNode、ViewIndex 等内部链路也保持直连。内部 tRPC 客户端和监听显式使用 go-net，避免 Linux SDK 自动选择 tNET。旧 Metadata 目标/协议/网络环境变量、Primary 协议/网络环境变量、`storage.view.storage_rpc` 及无用服务名配置已移除；配置加载拒绝已删除字段、未知网关字段和重复键。当前 Storage 业务监听均为原生 tRPC；原生单元部署已接入按角色分发签名身份与 Storage 凭据。
