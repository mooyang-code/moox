# 归档（Archive）

> 本文描述新的定时归档：**管理端 `moox-archive-mgr`**（阶段 6）和 **worker `moox-archive-worker`**（阶段 7），均在 2026-10-17 实现，尚未部署。前端（阶段 8）尚未实现；
> 完整设计见[数据归档设计](../计划/数据归档设计.md)。旧的事件式实现已在 2026-10-17 删除。

代码位置：`modules/archive`。管理端与 worker 都是纯 Go（关闭 CGO），管理端放在 control 主机；执行读取、暂存和导出的 worker 另外部署在能出站访问 Access 的机器上（本次计划是编译机）。

## 1. 进程与端口

| 服务 | 端口 / 周期 | 说明 |
| --- | --- | --- |
| `ArchiveMgr` | `11406` | 控制台与 `moox-cli` 使用的接口（服务目录 `console_name: archive`，必须带 `X-Space-Id`） |
| `ArchiveWorker` | `11408` | mgr 与 worker 的内部契约，`acl: []`，只有外部身份 `archive-worker` 经 Access 能调用 |
| 健康检查 | `11416` | `/healthz`、`/readyz`、`/metrics` |
| `mgr.trigger.timer` | 每秒（`* * * * * *`），单次超时 900ms | 全局触发器：生成到点任务的运行 |
| `mgr.maintain.timer` | 每分钟第 13 秒，单次超时 50 秒 | 回收过期租约；每小时刷新各任务的保留期与 DataNode、清理运行记录；每天回收 SQLite 空闲页 |

数据目录 `data/archive-mgr/archive.db`（SQLite，`auto_vacuum = INCREMENTAL`）。内部身份 `archive-mgr` 经网关调用 Storage 的 `Metadata.GetDataset`（请求体 AppId 为 `archive`，用 Primary 密钥签名）。

## 2. 数据模型

四张表（`schema/archive.sql`）：`t_archive_tasks`（一个时序数据集最多一个任务）、`t_archive_runs`（定时 / 手动 / 补拉区间的运行）、
`t_archive_partitions`（每个任务每个分区一行，open / exported / final）、`t_archive_workers`（worker 租约与心跳状态）。
时间列统一存 UTC 文本 `YYYY-MM-DD HH:MM:SS.mmm`。已有分区的任务不能删除，只能停用。

## 3. 任务与执行计划

- 执行计划是带秒的 6 段 cron（robfig/cron v1 语法）加 IANA 时区（默认 `Asia/Shanghai`）。保存时展开未来 14 天的计划时刻，取相邻时刻的最小间隔作为执行间隔，**小于 5 分钟拒绝**。
- 开始时间二选一：`immediate`（保存后立刻生成一条 `manual` 运行，之后按计划）或 `at`（从该时刻起按计划，之前的计划时刻不运行）。
- 回补起点可选，必须早于当前时间且不早于「今天 − 线上保留期 + 1 天」；保留期为 `forever` 时不限。
- 分区粒度由频率决定：低于 1d 按空间本地日（`day`），1d、1w、1mo 按「`data_time` + 12 小时」的 UTC 日期归月（`month`）。
- 各空间的默认计划（`PrepareArchiveTask` 返回的推荐值，北京时间）：crypto 1h 以下每小时 `:34:43`、1h 及以上每天 08:34:43；stockcn 17:04:43；stockhk 17:34:43；stockus 06:04:43。
- `PreviewArchiveSchedule` 返回接下来 5 次运行时间、执行间隔、读取区间长度（执行间隔 + 最少回看 + 一根 K 线的最大跨度）、上一个与当前分区的预计导出时间，以及落在避让区间（每分钟 0–25 秒、整点 :58～:04）的提示。

## 4. 运行的生命周期

1. **生成**：全局触发器查询 `status = enabled AND next_run_at <= now` 的任务；已有排队中或运行中的运行时只累加连续跳过次数（不写运行记录），否则生成 `scheduled` 运行并清零；`next_run_at` 推进到当前时刻之后的下一个计划时刻，错过的不补。手动立即运行与补拉区间直接生成 `manual` / `range` 运行，同一任务同时只能有一条排队或运行中的运行。
2. **领取**：worker 的心跳取得活动租约（同一时刻只有一个 worker 活动，旧 worker 停止心跳 45 秒后才能被接管；同一 `worker_id` 的第二个存活实例返回冲突）。活动 worker 每次拉取按计划时刻从早到晚领取，不超过空闲槽数和每个 DataNode 的并发上限；已有分区登记的任务只派给登记的那个 `worker_id`。领取时写 10 分钟的运行租约和随机令牌。
3. **进度与取消**：`ReportArchiveRunProgress` 续租并上报统计；用户取消的运行立即标为 `canceled`，worker 在下次心跳（`cancel_run_ids`）或进度上报（`canceled`）得知并停止，收尾时仍可上报已导出的分区。
4. **完成**：`CompleteArchiveRun` 在一个事务里更新运行状态、分区登记、任务的最近成功时间（定时与手动运行）和定稿边界（只前进不回退）；失败的事务整体回滚。一个分区只允许一个 worker 登记。
5. **租约过期**：维护定时器把租约过期的运行标为 `failed`（原因「worker 失联」）；下一次运行从上一次成功的运行算起重新读，所以不会丢数据。
6. **清理**：成功的定时运行保留 30 天，其余保留 90 天。

## 5. 健康等级

| 条件 | 等级 |
| --- | --- |
| 最近一次成功运行距今超过「线上保留期 − 2 天」（从未成功则按创建时间算）；有无法补齐的区间；有到期运行时活动 worker 离线超过 30 分钟 | 异常 |
| 最近一次运行失败；连续跳过 3 次以上；运行耗时超过执行间隔的一半；有分区到时间超过 2 个执行间隔仍未导出 | 需关注 |
| 其他 | 正常；停用的任务显示为已停用 |

## 6. 接口

`ArchiveMgr`（14 个方法）：`GetArchiveOverview`、`ListArchiveTasks`、`PrepareArchiveTask`、`PreviewArchiveSchedule`、`CreateArchiveTask`、`UpdateArchiveTask`、`DeleteArchiveTask`、
`RunArchiveTaskNow`、`BackfillArchiveRange`、`CancelArchiveRun`、`ListArchiveRuns`、`GetArchiveRun`、`ListArchivePartitions`、`GetArchivePartition`。
调用方 `console`、`moox-cli`；前 4 个以及 4 个查询方法为只读，另外允许 `monitor` 调用。经 Console 的调用以请求头里的空间为准，请求体里的 `space_id` 与之不一致时拒绝；内部调用方（CLI）在请求体里指定空间。

`ArchiveWorker`（4 个方法）：`ArchiveWorkerHeartbeat`、`PullArchiveRun`、`ReportArchiveRunProgress`、`CompleteArchiveRun`。外部身份 `archive-worker` 在 Access 白名单里只有：
`PrimaryStore.ReadTimeSeriesRows`、`Metadata.GetDataset` / `ListDatasetColumns`，以及这 4 个方法。

## 7. 配置（`config/app.yaml`）

`database.path`、`gateway_client`（caller `archive-mgr`）、`run.lease_ttl`（10 分钟）、`worker.takeover_wait`（45 秒）、

**目录内嵌在 Admin、Monitor、各主机 host-gateway 和 Access 中，上线时必须用同一提交一起发布**（做法同发布 A）。构建：`scripts/build/build.sh archive-mgr`。

**部署方式**：archive-mgr 随 control 单元发布，与 factor-mgr 一样由 `moox-runtime` 管理（工作目录 `<发布目录>/archive-mgr/{config,data,logs}`，
同样的密钥投影与网关身份），由主机守护（`moox-runtime watch`）看护，可暂停、随发布回滚。在 `moox.toml` 的 control 放置里加入 `archive-mgr` 即启用。

## 9. worker（`moox-archive-worker`）

代码在 `modules/archive/cmd/worker` 与 `internal/worker/*`，纯 Go（暂存库是 SQLite），`scripts/build/build.sh archive-worker` 可交叉编译 Linux、macOS、Windows 版本。worker 只出站：用外部身份 `archive-worker` 经固定的 Access（`access_address` + `access_id`）调用 `ArchiveWorker` 与 Storage，
不订阅 EventBus，也不监听业务端口（只有本机健康检查 `127.0.0.1:11418`，`worker health` 子命令签名后查询）。

**主循环**（`internal/worker/app`）：每 10 秒心跳（磁盘、暂存库大小、正在执行的运行、是否在维护；返回是否持有活动租约、需要取消的运行、已删除的任务），
有空闲并发槽且租约有效时每 5 秒领取（带上已占用的 DataNode；备用 worker、维护中、磁盘低于 `min_free_bytes` 时不领取）。每个运行在独立协程里执行，每 30 秒上报进度并续租，
结束时上报结果；上报失败退避重试 6 次，mgr 返回冲突（运行已结束或令牌失效）就放弃。续租与进度由独立的定时器负责（读取、导出、定稿、排队期间都续租）。
同一数据集的运行在本地串行；每个分区带「待上报」标记，mgr 确认登记之后才清除，所以上报失败的分区会在后续运行里再次上报（定稿后的统计在定稿时记进暂存库的分区状态）。同一 `worker_id` 的第二个存活实例会收到冲突，不领取。

**一次运行**（`internal/worker/runner`）：
1. 读取区间：`[W − L − S, 本次运行开始)`（`W` 是暂存库里上一次完整成功运行的开始时间；`S` 一根 K 线的最大跨度，1mo 31 天、1w 7 天）；首次运行取回补起点，没有则取「开始 − 执行间隔 − L − S」（算出的起点记在暂存库里，水位前进之前失败重试沿用更早的起点）；补拉区间运行读指定区间且不推进 `W`。
   起点早于线上保留期截止的部分截掉，记为「无法补齐」上报。区间按分区边界切块，逐块、逐页（游标，每页最多 2000 行，失败重试 3 次）读取，不指定标的。
2. 写入暂存区：每页先进临时表，与暂存表按主键比对（`IS DISTINCT FROM`），只写新增和变化的行，同一事务里更新受影响分区的 `last_changed_at`。要写入已定稿分区时，先把原文件按列名读回暂存表并标回 `open`（读回的行不算变化，所以重复读到的行不会触发重写）。
3. 导出：`运行开始 ≥ 分区收盘时间 + L` 且分区需要导出（从未导出，或导出之后又有变化）→ `COPY … TO <文件>.partial`（gzip CSV）→ fsync → rename → fsync 目录 → 计算 sha256 与预览。
4. 定稿：`运行开始 ≥ 分区收盘时间 + L + 暂存保留期` 且没有待导出的变化 → **在同一个暂存库事务里**删除暂存行、标 `final`，并把 `W` 推进到本次运行开始。事务失败时两者都不变，重跑从同一个起点读。
5. 上报：本次涉及的分区（状态、行数、标的数、数据时间范围、文件路径 / 大小 / sha256、列、预览）、运行统计和定稿边界（最早的连续已定稿分区的结束时间）。

**文件**：`<root_dir>/<space>/<yyyy>/<前缀>_<yyyymmdd|yyyymm>.csv`（默认不压缩，`worker.export_formats: [csv.gz]` 可改为压缩），`<root_dir>/<space>/<前缀>_dataset.json`（数据集说明：数据集 ID、中文名、简介、数据来源 ID、标的范围、线上保留期、创建与更新时间，分区方式与时区，文件格式与路径规则，以及每一列的名称、类型、中文名、来源和别名；列定义取自 Storage 的数据集列，数据集信息由 mgr 每小时刷新后随运行下发，内容有变化才重写）。前缀是创建任务时数据集的中文名去掉空白（路径不安全字符换成下划线），为空或与同空间其他任务重名时退回「名称_数据集 ID」或数据集 ID；创建后固定，数据集改名不会改已有文件名；升级前创建的任务由 mgr 的每小时维护补上前缀。`<root_dir>/.state/staging.db`（SQLite，WAL 文件为 `staging.db-wal`）是暂存区与永久保留的分区状态。
每个任务一张 `WITHOUT ROWID` 暂存表，主键 (subject_id, data_time, series_tag)，另有 data_time 索引；所有时间列存 Unix 纳秒整数（Storage 行键保留纳秒）。

**CSV 格式**（RFC 4180，逗号分隔，`\n` 换行）：表头 `data_time,subject_id,series_tag,<值列…>`，按 subject_id、data_time、series_tag 排序；
`data_time` 与时间列为 UTC RFC3339，秒以下保留到纳秒（尾随 0 省略，整秒时为 `2026-10-15T01:00:00Z`）；浮点数为最短可精确往返的写法，整数值带 `.0`，
无穷写作 `+Inf` / `-Inf`（NaN 在暂存库里存为缺失值）；布尔为 `true` / `false`；二进制为标准 base64；缺失值是不带引号的空字段，空字符串写作 `""`，
含逗号、引号、换行或首尾空白的字段加引号。定稿分区被补写时按同样的规则读回，读回的行与原文件逐字段一致。
表头 `data_time,subject_id,series_tag,<值列…>`，`data_time` 为 UTC RFC3339，行按 `subject_id, data_time, series_tag` 排序；空字符串写成 `""`、缺失值为空字段，二者可区分。值列取来源为字段或因子、状态启用的列；系统列与行属性不导出。
日分区按空间时区的本地日切分，月分区按「`data_time` + 12 小时」的 UTC 日期归月（分区在 `data_time` 上的范围是 `[当月 1 日 − 12h, 下月 1 日 − 12h)`）。

**节奏**（`internal/worker/pacing`）：只在每分钟第 25–55 秒发起请求；每小时 :58 到下一小时 :04 之间不发起；同一运行两次请求至少间隔 200ms；所有并发运行共享一个 512KB/s 的令牌桶；
最多 4 个运行并发，同一 DataNode 最多 2 个。避让依赖本机时钟，部署机器必须开启 NTP。
每分钟的秒区间由 `pacing.minute_window` 控制，默认 `true`；设为 `false` 则整分钟都可发请求，整点静默、带宽和请求间隔仍然生效。每次请求发出前都会检查当前时间，落在禁区就等到允许时刻；读取请求不使用网关客户端内部的重试（`gatewayclient.WithoutRetry`），失败由 worker 自己重试，每次重试前同样先检查时间。

**维护**（每天 04:17:43，本机时区）：停止领取并等进行中的运行结束（最多 30 分钟），清理 mgr 通知的已删除任务的暂存表，`PRAGMA wal_checkpoint(TRUNCATE)`，库文件（按 `page_count`、`freelist_count`、`page_size` 计算）超过存活数据的 `rebuild_ratio`（默认 2）倍且不小于 64MB 时用 `VACUUM INTO` 新文件重建，关闭连接后原子替换再重新打开。启动时清理残留的 `.partial` 文件。

**配置**（`config/worker/app.yaml`）：`gateway_client`（`access_address`、`access_id`、`caller: archive-worker`、`key_id`、`key_file`、`compression`）、`storage_auth_file`（Storage Primary 签名密钥，以 AppId `archive` 签名）、`worker`（`worker_id`、`root_dir` 绝对路径、`min_free_bytes`、心跳与领取间隔）、
`staging`（`cache_size` 暂存库页缓存上限，默认 256MB；`rebuild_ratio`）、`pacing`、`health`、`maintenance`。未知项被拒绝。

**构建与部署**：Linux 版必须在 Linux 上构建——`moox-cli setup build-linux --module archive-worker`（在 `compile_host` 上构建并取回）；macOS 可 `scripts/build/build.sh archive-worker`。
`scripts/deploy/deploy-archive-worker.sh --root-dir <归档目录> --access-address … --access-id … --access-key-id … [--binary <预构建二进制>]` 渲染配置与服务定义（Linux 用 systemd 用户服务，macOS 用 launchd）并等待 `worker health` 通过；
凭据（`access-archive-worker.key`、`storage-primary-auth.secret`，0600）放在 `<dir>/secrets`。换机器时把归档目录（含 `.state`）整体拷过去并沿用同一个 `worker_id`。
