# 归档（Archive）

> 本文描述当前源码已实现的定时归档：**管理端 `moox-archive-mgr`** 与 **worker `moox-archive-worker`**；管理端可随 control 部署，worker 可独立部署在因子机。运行状态以部署清单与健康检查为准，本次文档审查没有连接生产环境。
> 管理台一级菜单“数据归档”下有“归档任务”（`/archive/tasks`）与“归档存储”（`/archive/storage`）两页；CSV 导入与清除无法补齐区间只在 `moox-cli archive …` 里。旧的事件式实现已在 2026-10-17 删除。

代码位置：`modules/archive`。管理端与 worker 都是纯 Go（关闭 CGO），管理端放在 control 主机；执行读取、暂存和导出的 worker 另外部署在能出站访问 Access 的机器上（示例拓扑为因子机）。
worker 每次导出分区后再传一份到标准 S3 接口的对象存储（默认是随 archive-worker 部署的内置 SeaweedFS，`moox.toml` 配了 `[archive_object_store]` 时用外部 S3；见[部署与运维](../部署与运维.md)“归档对象存储”），见第 9 节“对象存储副本”；mgr 只登记，不连对象存储。

## 2. 数据模型

四张表（`schema/archive.sql`）：`t_archive_tasks`（一个时序数据集最多一个任务，记着拉取间隔 N 与最近处理过的两个边界）、`t_archive_runs`（复核 / 手动 / 到点拉取 / 补拉区间 / 导入的运行）、
`t_archive_partitions`（每个任务每个分区一行，open / exported / final）、`t_archive_workers`（worker 租约与心跳状态）。
时间列统一存 UTC 文本 `YYYY-MM-DD HH:MM:SS.mmm`。已有分区的任务不能删除，只能停用。

- **远端副本**：分区登记带 `c_remote_key`（相对对象存储 `prefix` 的对象键，不含 endpoint、桶名和前缀，换桶或换前缀不用改库）、`c_remote_sha256`、`c_remote_etag`、`c_remote_uploaded_at`、`c_remote_verified_at`、`c_remote_error`。
  “已复制”的口径（worker 与 mgr 相同）：有文件，且 `c_remote_sha256 = c_file_sha256`、`c_remote_verified_at` 非空。`c_remote_key` 非空而 sha256 不等于文件的，表示远端只有旧版本、新版本待上传。
- 接口里的 `remote_state`（mgr 计算）：`off`（对象存储未启用：有活动 worker 时看它的心跳，没有时看最近一次心跳的那条 worker 记录）、`none`（没有文件）、`verified`（已复制）、`failed`（不是已复制且有错误）、`pending`（其余，待上传）。
- `c_worker_id` 是最近一次登记该分区的 worker，只用于展示与排障；任务不再钉死在某个 worker 上（第 4 节）。
- **目录**：`t_archive_tasks.c_purpose`（`collect` 采集结果、`factor` 因子结果、`data` 其他）与 `c_dir_name` 决定分区目录 `<空间>/<用途>/<目录名>/`，`UNIQUE (c_space_id, c_purpose, c_dir_name)`，建好后不改（规则见第 9 节“目录”）。
- **导入运行**：`t_archive_runs.c_kind` 可取 `import`，此时 `c_import_file`（相对 `<归档根目录>/.import` 的 `<import_id>/<文件名>`）必填（表约束），`c_overwrite` 为 1 表示同键已存在的行以导入文件为准、0 表示只补空缺。
- `t_archive_runs.c_partitions_uploaded` 是运行上传并校验通过的分区数；`t_archive_workers.c_object_store_json` 存心跳带来的对象存储摘要（endpoint、桶、前缀、存储类型、地址风格，不含凭据）。
- **磁盘**：`t_archive_workers` 只存数值，不存“空间不足”标记。`c_disk_total_bytes` 是总量（statfs `Blocks`），`c_disk_used_bytes` 是已用（`Blocks − Bfree`），`c_disk_free_bytes` 是可用（`Bavail`，不含 root 保留空间），`c_min_free_bytes` 是 worker 配置的下限 `worker.min_free_bytes`（默认 5GB）。
  已用 + 可用小于总量，差额是文件系统给 root 的保留空间。可用低于下限时 worker 停止领取新运行、`/readyz` 降级原因为 `disk_insufficient`；归档存储页按同一个数（可用）和同一个下限判断“磁盘空间不足”，与 worker 一致。

## 3. 任务与触发规则

任务不填执行计划，由数据集的时序信息决定什么时候拉取：**mgr 每分钟第 25 秒检查一次，每个任务到了它的拉取边界才生成运行，不到就跳过（不写运行记录）**。代码在 `internal/schedule`（纯函数）与 `store.TriggerDue`。

**任务设置**

- `pull_every_bars`（N，1～1440，默认 1）：每收盘 N 根 K 线拉取一次，且「频率 × N」不超过 1 天（步长再长，到点拉取要读的根数会超出线上保留期、被误记为无法补齐）。1d 及以上每天一次，N 只校验范围、统一存 1。
- `interval_seconds`：复核间隔，由 mgr 按频率填写，低于 1d 为 3600，1d 及以上为 86400，用户不能改。
- 回补起点可选，必须早于当前时间且不早于「今天 − 线上保留期 + 1 天」；保留期为 `forever` 时不限。修改任务时只有改了回补起点才重新校验，没改就保留原值。
  `PrepareArchiveTask` 给出的最早值按当时的时刻算，提交时下界已经后移：早于下界**不到 1 小时**（代码常量 `backfillClampSlack`）的起点夹到下界（向上取整到秒）而不报错，保存与返回的是夹取后的值；差 1 小时以上照旧拒绝。补拉区间（`BackfillArchiveRange`）的起点同理，下发的是夹取后的区间。
- `last_boundary`、`last_review`：最近一次已生成运行的拉取边界与复核边界。新建任务时两者为空；停用后重新启用时两者清空。为空时下一次检查立即复核。
- 分区粒度由频率决定：低于 1d 按空间本地日（`day`）；1d、1w、1mo 按「`data_time` + 12 小时」的 UTC 日期归月（`month`）。

**拉取边界**（≤ 现在的最晚一个）

- 低于 1d（30s、1m、5m、15m、30m、1h、4h…）：步长 = 频率 × N，从 Unix 纪元向下取整（UTC，与 K 线开盘对齐）。
- 1d、1w、1mo：每天一个，与 N 无关。空间配置了本地收盘时刻（`spaces.<空间>.local_close`）时，取最近一个本地收盘时刻，按当地日期构造，跨夏令时也落在当地收盘；没有配置时取 UTC 0 点。
- 股票的日内频率同样按 UTC 对齐，非交易时段也会算出边界，读回来是空的（一次空请求很便宜）；不引入交易日历。周末的日线边界同理。

**复核边界**：低于 1d 为每小时第 34 分（UTC，≤ 现在的最晚一个）；1d 及以上不单独复核，拉取就是复核。

**每次检查**（第 25 秒，一个事务处理全部启用的任务）

1. 当前避让规则有整点窗口（见下文“避让规则”）且现在落在 **:58:00～:04:00**（UTC 分钟 ≥ 58 或 < 4）时整次跳过；没有整点窗口时不跳过。
2. 对每个任务算拉取边界 `B` 与复核边界 `R`：
   - `tickDue`：`last_boundary` 为空，或 `B > last_boundary`；`reviewDue`：`last_review` 为空，或 `R > last_review`。1d 及以上 `reviewDue = tickDue`。
   - 都不到点：跳过，不写记录。
   - 到点但任务已有排队中或运行中的运行：连续跳过次数 + 1，两个边界都不前进，下一次检查再判断。
   - `reviewDue`：生成复核（`scheduled`），`last_review = R`；同时 `tickDue` 时 `last_boundary = B`（复核已覆盖，不再另生成到点拉取）。1d 及以上两个边界都记成 `B`。
   - 只有 `tickDue`：生成到点拉取（`tick`），读 `[起点, 现在)`，`last_boundary = B`。
     起点 = `last_boundary − 2 根`；`last_boundary` 为空或早于 `B − 60 根` 时取 `B − (N + 2) 根`（更早的交给复核）。
     多读 2 根是为了带上刚收盘那根的晚到写入；跳过几次之后，起点仍从上次边界算，跳过的那几根不会漏。
   - 生成运行时连续跳过次数清零。运行的计划时刻（`scheduled_at`）是这次检查的时刻。
3. 判断用「边界比上次记下的晚」，不是「现在恰好等于边界」：mgr 重启、整点窗口、跳过而错过的检查，出了窗口的第一次检查照样触发。

**到点拉取**负责及时：暂存区始终跟到最新一根，分区在「收盘 + L」之后的第一次拉取或复核就能导出；它不推进水位。**复核**负责完整：沿用回看规则读 `[W − L − S, 现在)` 并推进水位 `W`（第 9 节），补上 15 分钟之后才写回的补采；worker 停机或运行失败时，复核从上次成功的 `W` 接上。首次复核从回补起点读起（没有回补起点时从「开始 − 复核间隔 − L − S」读起）。

**例子**（N = 1，时刻为 UTC，除非另注；按有整点窗口的情形，即有 1h 及以上的采集频率，没有时 :58～:03 的边界不顺延，在各自的第 25 秒拉取）

| --- | --- | --- | --- | --- |
| crypto 1m | 每个整分 | 每分钟第 25 秒；:58～:03 的边界合并到 :04:25 | 12:40:25 读 `[12:37, 12:40:25)` | 每小时 :34:25 |
| crypto 1m，N = 5 | 每 5 分钟（:00、:05…） | :05:25、:10:25…；:00 的边界在 :04:25 | 12:45:25 读 `[12:38, 12:45:25)` | 每小时 :34:25 |
| crypto 5m | 每 5 分钟 | 同上 | 12:45:25 读 `[12:30, 12:45:25)` | 每小时 :34:25 |

**预览**：`PrepareArchiveTask` 返回频率、分区粒度、保留期、最早回补起点、推荐的 N（1），以及用途 `purpose`、建议目录名 `suggested_dir_name` 与 `dir_name_conflict`（请求带 `dir_name` 时检查它，否则检查建议值）。`PreviewArchiveSchedule`（`space_id`、`dataset_id`、`pull_every_bars`）返回接下来 5 个拉取时刻（有整点窗口时窗口里的顺延到 :04:25 并去重）、接下来 3 个复核时刻、复核间隔、复核读取区间长度（复核间隔 + L + 一根 K 线的最大跨度），以及上一个与当前分区的预计导出时间（「收盘 + L」之后的第一次拉取或复核）。任务列表的 `next_pull_at` 是下一次拉取时刻（同样顺延），停用的任务为空。预览、`next_pull_at` 与导出时间估算都按当前生效的避让规则计算。

**避让规则**（`internal/schedule/avoid.go` 纯函数，`internal/service/avoidance.go` 刷新）：归档读取要避开采集函数的触发时刻。规则由采集频率推出，不解析 cron、不看执行端（采集函数的 cron 本来就由它服务的最小频率生成，stream 与本地执行端也在收盘那一分钟的第 0 秒触发）。

- 来源：`CollectMgr.GetCollectorStatus(space_id)` 返回的 `functions[].datasets`（“数据集|频率”）。只读**有归档任务的空间**；mgr 配置 `spaces` 段里有、但没有任务的空间不读。
- 每分钟规则：取这些空间生效中的、低于 1h 的频率（分钟数，不足 1 分钟按 1 分钟），**N = 它们与 60 的最大公约数**（3m 与 5m 得 1，只有 5m 得 5，7m 得 1）。触发时刻 T 是 Unix 纪元起分钟数为 N 的倍数的第 0 秒，`[T − 5s, T + 25s)` 不发请求，其余时间可发；N = 1 时就是“每分钟只在第 25～55 秒发”。没有低于 1h 的频率时不限秒。
- 整点窗口：有任何 ≥ 1h 的频率（这些数据集在整点集中收盘）时加 `:58:00～:04:00`；没有时不避让整点。A 股不按交易时段细分。
- 无法识别的频率按最保守处理（每分钟触发，并有整点窗口）。不足 1 分钟的频率（如 30s）只避开整分钟的触发，分钟内其余触发（30s 的第 30 秒）不在避让范围内，依据里注明。
- 刷新：挂在 maintain 定时器上，排在它原有的工作之后；距上次成功满 10 分钟、或有任务的空间变了（例如建了某空间的第一个任务）才读，各空间并行读，合计不超过 20 秒。
  任一空间读取失败时这个空间沿用上一次成功的频率，依据里注明“（读取失败，沿用 MM-DD HH:MM UTC 的结果）”，3 分钟后重试；读取失败不算维护失败。
- 默认值：启动后还没成功读过时用每分钟第 25～55 秒、整点 :58～:04，依据写“未取到采集频率，使用默认值”；部分空间从没读到过时，这些空间按默认值计入。没有任何归档任务时不避让（依据“没有归档任务，不避让”）。规则只在内存里，mgr 重启后从默认值开始。
- 执行：mgr 只按整点窗口跳过检查；每分钟的秒窗口由 worker 执行（mgr 的检查固定在第 25 秒，恰好是 T + 25 秒）。规则随 worker 心跳回包下发（`avoidance`），`GetArchiveOverview` 也返回它（含 `basis` 与 `computed_at`），归档存储页显示生效分钟、秒窗口、整点窗口、依据与计算时间。

## 4. 运行的生命周期

运行类型：`scheduled`（复核）、`manual`（立即运行，读法同复核）、`tick`（到点拉取）、`range`（补拉区间）、`import`（导入 `moox-cli` 上传的本地 CSV，不经 Storage，见第 9 节“CSV 导入”）。`tick` 与 `range` 必须带区间，`import` 必须带导入文件（表约束）。同一任务同时只能有一条排队或运行中的运行；立即运行、补拉区间与导入遇到**排队中的到点拉取**时把它取消（标为 `canceled`，原因“让位给立即运行、补拉区间或导入”，它的区间由之后的复核兜底），遇到运行中的运行或排队中的其他运行仍返回冲突。

1. **生成**：复核与到点拉取只由每分钟的检查生成（第 3 节）；`RunArchiveTaskNow` 生成 `manual`，`BackfillArchiveRange` 生成 `range`，`ImportArchiveFile` 生成 `import`，已有排队或运行中的运行时返回冲突。
2. **领取**：worker 的心跳取得活动租约（同一时刻只有一个 worker 活动，旧 worker 停止心跳 45 秒后才能被接管；同一 `worker_id` 的第二个存活实例返回冲突）。活动 worker 每次拉取按计划时刻从早到晚领取，不超过空闲槽数和每个 DataNode 的并发上限；任务派给任何持有活动租约的 worker（不再钉死在登记分区的 `worker_id` 上，前提是分区登记带远端副本、读回时能从对象存储取回，见第 9 节）。领取时写 10 分钟的运行租约和随机令牌。下发的参数里带运行类型与区间、任务 ID（删除后重建会换新值）、复核间隔、任务最近一次成功复核或手动运行的开始时间（即读取水位），以及该任务的分区登记（含远端字段），worker 本地暂存状态丢失时据此重建（见第 9 节）。
   下发哪些登记：结束时间晚于「本次开始 − 线上保留期」的，加上更早但有文件、还不是已复制的（暂存库重建后它们还要补传）；已复制的旧分区不下发，下发量不随年份增长。
   导入运行例外，下发全部登记：导入写的多是保留期之前的分区，暂存库丢失时要先补齐本地状态，不能把已有文件的分区当成新分区导出。
3. **进度与取消**：`ReportArchiveRunProgress` 续租并上报统计；用户取消的运行立即标为 `canceled`，worker 在下次心跳（`cancel_run_ids`）或进度上报（`canceled`）得知并停止，收尾时仍可上报已导出的分区。
4. **完成**：`CompleteArchiveRun` 在一个事务里更新运行状态、分区登记、定稿边界（只前进不回退）和累积的无法补齐区间；只有成功的复核与手动运行更新任务的最近成功时间并清掉回补起点，**到点拉取、补拉区间与导入都不更新**，也都不推进水位。失败的事务整体回滚。完成上报带上传数（`partitions_uploaded`）。
   导入成功**不自动删除**任务累积的无法补齐区间（区间不带标的，按时间范围自动判断会把真实缺口藏掉）；导入补齐历史缺口后由人确认，用 `ClearArchiveUnrecoverable`（CLI `archive tasks clear-unrecoverable`）删掉整段落在 `[start, end)` 里的区间，返回删掉的条目。
   分区的远端字段按上报值整体替换；open 状态不带文件信息时，文件与远端字段一并沿用已登记的值。**文件大小兜底**：上报的 `file_bytes` 是上报时 stat 的，本地文件不在时为 0，路径与 sha256 都没变时保留已登记的大小。
   **分区登记不许倒退**：已有文件的分区，上报的行数或标的数比已登记的少就整次拒绝——运行记为失败并写明哪个分区从多少降到多少，分区与任务都不动，返回冲突；worker 不清待上报标记，之后每次运行都会再报、再被拒，任务一直显示失败。归档只增不删（读回合并后不会变少），变少只会来自暂存状态丢失后用残缺数据重新导出，需要人工核对原文件。
5. **租约过期**：维护定时器把租约过期的运行标为 `failed`（原因「worker 失联」）；下一次复核从上一次成功的复核算起重新读，所以不会丢数据。
6. **清理**（维护定时器每小时一次）：成功的到点拉取保留 24 小时（1m、N = 1 时每天最多 1440 条），成功的复核保留 30 天，其余（含导入）保留 90 天。
7. **列表**：`ListArchiveRuns` 默认不列成功的到点拉取（排队、运行中、失败、取消的照常列出）；`include_ticks`（CLI `--include-ticks`）列出全部。任务列表的「最近一次运行」包括到点拉取。

## 5. 健康等级

| 条件 | 等级 |
| --- | --- |
| 最近一次成功的复核或手动运行距今超过「线上保留期 − 2 天」（从未成功则按创建时间算）；任务累积过无法补齐的区间；分区登记被拒；有到期运行时活动 worker 离线超过 30 分钟；读不到数据集的线上保留期 | 异常 |
| 最近一次运行（含到点拉取与导入）失败；最近一次复核或手动运行失败（单独判断，之后成功的到点拉取不会把它盖掉）；连续跳过 10 次以上；最近一次复核或手动运行耗时超过复核间隔的一半；有分区到时间（收盘 + L）超过 2 个复核间隔仍未导出 | 需关注 |
| 启用了对象存储时：最早一个不是已复制的分区（有文件）导出超过 72 小时（`remoteErrorAfter`） | 异常 |
| 启用了对象存储时：同上，超过 24 小时（`remoteWarnAfter`） | 需关注 |
| 其他 | 正常；停用的任务显示为已停用 |

每分钟检查一次，复核运行期间到点拉取被跳过几次是常态，所以连续跳过的门槛是 10 次。耗时规则只看复核与手动运行，到点拉取每分钟一条，不参与。

远端副本规则的原因文案：`共 N 个分区还没有已校验的远端副本，最早的 <分区键> 导出已超过 24 小时（3 天）；最近错误：…`。N 是该任务全部未复制分区的数量（含还没满 24 小时的），时长只按最早那个分区算；最近错误取该任务 `c_mtime` 最新的那条。
计时起点是**当前版本**的导出时间，重导出后从新的导出时间重新计；不另设“多久没抽查”的规则：抽查发现远端丢了会重置成待上传，导出时间早，马上就是异常。
规则只在 worker 报告启用了对象存储时生效（判断方式同 `remote_state` 的 `off`）。任务列表同时给出 `remote_verified_count`（已复制的分区数）与 `remote_pending_count`（有文件但不是已复制的，含失败的），没启用时都是 0。Monitor 不用改：规则通过等级生效，原因进 `health_reason`。

mgr 每 30 秒把每个任务的健康等级上报为指标 `moox_archive_task_health{space,dataset}`（0 正常、1 需关注、2 异常、3 已停用）。Monitor 据此生成两类检查：
- **归档任务 `<数据集>`**：异常时告警；需关注只写在原因里，不告警。
- **未归档的数据集**：Storage 里已激活、有限保留期（不是 `forever`）、不在 `mooxsys` 空间的时序数据集没有归档任务时告警。
archive-mgr 没有部署或停止上报（没有新鲜的 worker 在线状态）时两类都不生成，免得把它自身的故障报成“全部未归档”。

对象存储可用性单独成一项：worker 配置了对象存储时每分钟对不存在的键 `<prefix>_probe/absent` 做 HEAD（404 或 200 算可用，连接失败、403、5xx 等算不可用），把最近的失败原因 `probe_error` 与连续不可用的起点 `unavailable_since` 放进心跳的 `ObjectStoreInfo`（`archive overview` 的 `worker.object_store` 可见）。mgr 每 30 秒按最近心跳的 worker 上报 `moox_archive_object_store_state{worker,probe_error}`（0 可用、1 不可用未满 5 分钟、2 超过 5 分钟；没配置对象存储或 2 分钟内没有心跳时不报），Monitor 据此生成检查 **归档对象存储**：2 告警，1 只把原因写上。内置 SeaweedFS 与外部 S3 同样适用；worker 重启后起点重新计。

## 6. 接口

`ArchiveMgr`（18 个方法）：`GetArchiveOverview`、`ListArchiveTasks`、`PrepareArchiveTask`、`PreviewArchiveSchedule`、`CreateArchiveTask`、`UpdateArchiveTask`、`DeleteArchiveTask`、
`RunArchiveTaskNow`、`BackfillArchiveRange`、`CancelArchiveRun`、`ListArchiveRuns`、`GetArchiveRun`、`ListArchivePartitions`、`GetArchivePartition`、`RetireArchiveWorker`（退役不再持有活动租约的 worker 登记）、
`PrepareArchiveImport`（取活动 worker 的归档根目录与新生成的导入 ID、上传目录 `<root>/.import/<import_id>`；没有活动 worker 时报错）、`ImportArchiveFile`（为已上传的文件建一条 `import` 运行）、`ClearArchiveUnrecoverable`（删掉整段落在 `[start, end)` 里的无法补齐区间）。

- 前 14 个调用方 `console`、`moox-cli`；`RetireArchiveWorker` 与三个导入相关方法（`PrepareArchiveImport`、`ImportArchiveFile`、`ClearArchiveUnrecoverable`）只给 `moox-cli`（导入要经 SSH 把文件传到 worker 所在主机）。
- `GetArchiveOverview`、`ListArchiveTasks`、`PrepareArchiveTask`、`PreviewArchiveSchedule` 与 4 个查询方法为只读，另外允许 `monitor` 调用。
- 经 Console 的调用以请求头里的空间为准，请求体里的 `space_id` 与之不一致时拒绝；内部调用方（CLI）在请求体里指定空间。
- `CreateArchiveTask` 带 `dir_name`（为空取建议值），目录名被同空间同用途的其他任务占用时返回冲突“目录名 <名> 已被 <数据集> 使用，请改一个”；`UpdateArchiveTask` 不能改目录名。

`ArchiveWorker`（4 个方法）：`ArchiveWorkerHeartbeat`、`PullArchiveRun`、`ReportArchiveRunProgress`、`CompleteArchiveRun`。心跳上报磁盘总量、已用、可用与下限（`disk_total_bytes`、`disk_used_bytes`、`disk_free_bytes`、`min_free_bytes`），回包带当前避让规则 `avoidance`（`AvoidanceRules`：`every_minutes`、`before_seconds`、`after_seconds`、`hour_quiet_from`/`hour_quiet_until`、`basis`、`computed_at`）。
`RunAssignment` 带任务的 `purpose`、`dir_name`，导入运行另带 `import_file`、`overwrite`。外部身份 `archive-worker` 在 Access 白名单里只有：
`PrimaryStore.ReadTimeSeriesRows`、`Metadata.GetDataset` / `ListDatasetColumns`，以及这 4 个方法。

控制台的分区下载与最新数据预览不走 tRPC：Admin 的两个裸 HTTP 路由 `/api/admin/archive/PartitionDownload`、`/api/admin/archive/RecentRows`（一次性 ticket，操作 `archive_download`、`archive_recent`，资源是 `<space>/<dataset>`，Admin 核对 query 里的 space、dataset 与 ticket 一致）转给 worker 的数据端口，见第 9 节“数据端口”。

## 8. 部署

`archive-mgr` 是服务目录里的可选组件（`required_in_default_profile: false`）。服务目录里登记了组件、外部身份 `archive-worker`、`Metadata.GetDataset` 与 `CollectMgr.GetCollectorStatus` 对 `archive-mgr` 的放行，以及 archive-worker 的 `relay_http` 数据端口；
**目录内嵌在 Admin、Monitor、各主机 host-gateway、Access 与 moox-cli 中，改了目录就必须用同一提交一起发布**，并且先发全部主机的 host-gateway、再发 Admin 与 Monitor（原因见[主机网关](主机网关.md)第 5 节）。构建：`scripts/build/build.sh archive-mgr`。

**部署方式**：archive-mgr 随 control 单元发布，与 factor-mgr 一样由 `moox-runtime` 管理（工作目录 `<发布目录>/archive-mgr/{config,data,logs}`，
同样的密钥投影与网关身份），由主机守护（`moox-runtime watch`）看护，可暂停、随发布回滚。在 `moox.toml` 的 control 部署里加入 `archive-mgr` 即启用。
早期在 control 上单独安装成 systemd 用户服务的做法（`deploy-archive-mgr.sh`）已删除（新项目，旧 `archive.db` 不迁移）。

**全新部署归档**：归档的库结构、目录规则或运行类型变了时不写升级 SQL，也不让新旧两套目录并存，而是清空后按新规则重建任务、从 Storage 线上保留期内回补。前提是要保留的分区都还在 Storage 保留期内（先用 `archive tasks list` 与 `archive partitions list` 核对最早分区）。步骤：

1. 记下当前任务清单（`moox-cli archive tasks list`：数据集、N、回补起点、状态），备份 control 上 archive-mgr 的 `archive.db*` 与 worker 主机上的 `<归档根目录>/.state/staging.db*`。
2. 停 worker：`setup deployment disable --host <worker 主机> --component archive-worker --yes`（不带 `--yes` 只预览），用 `systemctl --user is-active moox-archive-worker` 确认已停。
3. 暂停 archive-mgr：control 上 `moox-runtime pause --plan <发布目录>/runtime.json --components archive-mgr`（必须带 `--plan`；手工 stop 一分钟内会被主机守护拉起），确认进程已退出。进程还在时不要动库文件。
4. 清旧数据：删除 archive-mgr 的 `archive.db`、`archive.db-wal`、`archive.db-shm`；清空 worker 的归档根目录（含 `.state`、`.import`）；用内置 SeaweedFS 时在 `weed shell` 里 `fs.rm -r /buckets/moox-archive/<前缀>/<空间>` 删掉各空间的旧对象并 `fs.ls` 确认（外部 S3 照同样的前缀清理）。
5. 发布新版本：改了服务目录时先发全部主机的 host-gateway，再发 Admin、Monitor 与 control 上其余组件（见[主机网关](主机网关.md)第 5 节）。archive-mgr 处于暂停，换二进制用 `skills/moox/scripts/native-release.sh install … --no-restart`（暂停的组件 restart 会失败且不重新封存），再 `moox-runtime resume --plan <发布目录>/runtime.json --components archive-mgr`，启动时按 `schema/archive.sql` 建新库。
6. `setup deploy-unit --host <worker 主机> --profile archive-worker --release <ID>`，再 `setup deployment enable --host <worker 主机> --component archive-worker --yes`。
7. 按第 1 步的清单重建任务：先 `archive tasks prepare` 核对建议目录名，`archive tasks create --backfill-from <最早要回补的时刻>` 从 Storage 回补。
8. 核对：Monitor 的“未归档的数据集”消失；回补完成后分区路径是新目录、`datasets.csv` 行数与任务数一致、远端副本全部已校验；在归档任务页下载一个分区，`sha256sum` 与响应头 `X-Moox-SHA256` 一致。

## 9. worker（`moox-archive-worker`）

代码在 `modules/archive/cmd/worker` 与 `internal/worker/*`，纯 Go（暂存库是 SQLite）；原生安装使用 Linux systemd 用户服务：它是服务目录里的外部程序组件，登记在因子机的 `[deployments]` 里，用 `moox-cli setup deploy-unit --host factor --profile archive-worker --release <ID>` 安装为 systemd 用户服务（停用与恢复用 `setup deployment enable|disable`，见[部署与运维](../部署与运维.md)的“因子机外部程序”）。worker 离线约 3.5 分钟后 Monitor 推送“归档 worker 在线状态”告警；换机后的旧登记用 `ArchiveMgr.RetireArchiveWorker` 退役。worker 只出站：用外部身份 `archive-worker` 经固定的 Access（`access_address` + `access_id`）调用 `ArchiveWorker` 与 Storage，
不订阅 EventBus，不监听 tRPC 端口；本机只有健康检查 `127.0.0.1:11418`（`worker health` 子命令签名后查询）与数据端口 `127.0.0.1:11428`（见下文“数据端口”）。

**主循环**（`internal/worker/app`）：每 10 秒心跳（磁盘总量、已用、可用与下限，暂存库大小、正在执行的运行、是否在维护、生效的节奏；返回是否持有活动租约、需要取消的运行与避让规则，活动时还带回当前全部任务），
有空闲并发槽且租约有效时每 5 秒领取（带上已占用的 DataNode；备用 worker、维护中、可用空间低于 `min_free_bytes` 时不领取，`/readyz` 原因为 `disk_insufficient`）。每个运行在独立协程里执行，每 30 秒上报进度并续租，
结束时上报结果；上报失败退避重试 6 次，mgr 返回冲突（运行已结束或令牌失效）就放弃。续租与进度由独立的定时器负责（读取、导出、定稿、排队期间都续租）。
同一数据集的运行在本地串行；每个分区带「待上报」标记，mgr 确认登记之后才清除，所以上报失败的分区会在后续运行里再次上报（定稿后的统计在定稿时记进暂存库的分区状态）。同一 `worker_id` 的第二个存活实例会收到冲突，不领取。

**一次运行**（`internal/worker/runner`）：
0. 绑定与重建：任务 ID 与本地记录不同（任务删除后重建）就丢掉该数据集的全部暂存状态。按 mgr 下发的分区登记补齐本地缺的分区状态：登记里有文件的一律按 `final` 恢复（统计、路径、sha256 取登记值），没有文件的不恢复。
1. 读取区间：复核与手动运行读 `[W − L − S, 本次运行开始)`（`W` 是暂存库里上一次完整成功的复核或手动运行的开始时间；`S` 一根 K 线的最大跨度，1mo 31 天、1w 7 天）。本地没有 `W` 但 mgr 下发了任务最近一次成功运行的开始时间时，用它当 `W`，并把起点再前移到登记里最早一个没有文件的 `open` 或 `exported` 分区的开始，让这些分区按线上还在的数据整段重读（暂存库丢失后的重建）。都没有时首次运行取回补起点，再没有则取「开始 − 复核间隔 − L − S」（算出的起点记在暂存库里，水位前进之前失败重试沿用更早的起点）。复核与手动运行再取「续读起点」与它的较晚者；
   **补拉区间（`range`）与到点拉取（`tick`）读下发的 `[range_start, range_end)`，不续读、不写首次起点、不推进 `W`**。
   起点早于线上保留期截止的部分截掉，截掉一根 K 线以上时记为「无法补齐」上报。区间按分区边界切块，逐块、逐页（游标，`pacing.page_rows` 默认 500、上限 2000 行，失败重试 3 次）读取，不指定标的。
2. 写入暂存区：每页先进临时表，与暂存表按主键比对（`IS DISTINCT FROM`），只写新增和变化的行，同一事务里更新受影响分区的 `last_changed_at`。要写入已定稿分区时，先按记录的路径核对 sha256，再把原文件按列名读回暂存表并标为 `exported`（读回的行不算变化，所以重复读到的行不会触发重写）。
3. **每读完一块**就导出、定稿到期的分区（到点拉取也导出，所以分区一到「收盘 + L」之后的第一次拉取就能导出），复核与手动运行把续读起点推到 `min(块结束, 运行开始 − L − S)`；中途失败，下次从续读起点接着读，不必整段重来。
   导出：`运行开始 ≥ 分区收盘时间 + L` 且分区需要导出（从未导出，或导出之后又有变化）→ 从 SQLite 流式读取并由 Go 编码到 `<文件>.partial`（默认 csv.gz），写入时一起算 sha256 → fsync → rename → fsync 目录 → 生成预览，路径记进分区状态。已有记录路径的分区写回原路径（按扩展名沿用原格式）；没有记录而目标文件已存在时拒绝导出，运行失败——防止暂存状态丢失后用残缺数据覆盖完整文件。
   定稿：`运行开始 ≥ 分区收盘时间 + L + 暂存保留期`、没有待导出的变化、文件存在且 sha256 一致 → 每个分区一个事务删除暂存行、标 `final`。
4. 全部读完后单独一个事务把 `W` 推进到本次运行开始（补拉区间与到点拉取不推进），同时清掉首次起点与续读起点。
5. 上报：本次涉及的分区（状态、行数、标的数、数据时间范围、文件路径 / 大小 / sha256、列、预览）、运行统计和定稿边界（最早的连续已定稿分区的结束时间）。

**文件**：`<root_dir>/<space>/<purpose>/<dir_name>/<yyyy>/<yyyymmdd|yyyymm>.csv.gz`（`worker.export_format: csv` 时为不压缩的 `.csv`），`<root_dir>/<space>/<purpose>/<dir_name>/dataset.json`（数据集说明：数据集 ID、中文名、简介、数据来源 ID、标的范围、线上保留期、创建与更新时间，分区方式与时区，文件格式与路径规则，以及每一列的名称、类型、中文名、来源和别名；列定义取自 Storage 的数据集列，数据集信息由 mgr 每小时刷新后随运行下发，内容有变化才重写）。`<root_dir>/.state/staging.db`（SQLite，WAL 文件为 `staging.db-wal`）是暂存区与永久保留的分区状态；`<root_dir>/.import/<import_id>/` 是待导入的文件；`<root_dir>/datasets.csv` 是目录对照表（见下文“目录”）。

**CSV 格式**（RFC 4180，逗号分隔，`\n` 换行）：表头 `data_time,subject_id,series_tag,<值列…>`，按 subject_id、data_time、series_tag 排序；
`data_time` 与时间列为 UTC RFC3339，秒以下保留到纳秒（尾随 0 省略，整秒时为 `2026-10-15T01:00:00Z`）；浮点数为最短可精确往返的十进制写法（绝对值小于 1e21 时不用指数形式），整数值带 `.0`，
无穷写作 `+Inf` / `-Inf`（NaN 在暂存库里存为缺失值）；布尔为 `true` / `false`；二进制为标准 base64；缺失值是不带引号的空字段，空字符串写作 `""`，
含逗号、引号、换行或首尾空白的字段加引号。定稿分区被补写时按同样的规则读回，读回的行与原文件逐字段一致。
值列取来源为字段或因子、状态启用的列；系统列与行属性不导出。
日分区按空间时区的本地日切分，月分区按「`data_time` + 12 小时」的 UTC 日期归月（分区在 `data_time` 上的范围是 `[当月 1 日 − 12h, 下月 1 日 − 12h)`）。

**节奏**（`internal/worker/pacing`）：按 mgr 随心跳下发的避让规则（第 3 节）发起请求：每个触发时刻 T 的 `[T − 5s, T + 25s)` 不发，有整点窗口时 :58 到下一小时 :04 之间不发；
收到规则就替换生效分钟、秒窗口与整点窗口，还没收到过时用 `app.yaml` 的 `pacing.request_seconds`（默认 `[25, 55]`）与 `pacing.hour_quiet`（默认 `["58:00", "04:00"]`）。心跳上报的 `pacing_json` 是生效值。
同一运行两次请求至少间隔 200ms；所有并发运行共享一个 512KB/s 的令牌桶；最多 4 个运行并发，同一 DataNode 最多 2 个。避让依赖本机时钟，部署机器必须开启 NTP。
每分钟的秒窗口由 `pacing.minute_window` 控制，默认 `true`；设为 `false` 则整分钟都可发请求（人工开关，优先于 mgr 下发的规则），整点窗口、带宽和请求间隔仍然生效。导入运行不读 Storage，不受节奏限制。每次请求发出前都会检查当前时间，落在禁区就等到允许时刻；读取请求不使用网关客户端内部的重试（`gatewayclient.WithoutRetry`），失败由 worker 自己重试，每次重试前同样先检查时间。

**维护**（每天 04:17:43，本机时区）：停止领取并等进行中的运行结束（最多 30 分钟），再发一次心跳取当前全部任务，删掉不在列表里（或任务 ID 不同）的数据集的暂存表与状态（取不到列表就跳过这一步），然后 `PRAGMA incremental_vacuum` 回收空闲页（暂存库建库时为 `auto_vacuum = INCREMENTAL`）并 `wal_checkpoint(TRUNCATE)`。启动时清理残留的 `.partial` 文件。

**对象存储副本**（`internal/objectstore`，配置了 `object_store` 才启用）：只用标准 S3 操作——单次 PutObject、HeadObject、GetObject，客户端 `minio-go` v7，代码里没有任何厂商专有接口、请求头或 SDK，换 R2、B2、自建 S3 兼容存储只改配置。
- **导出即上传**：每次导出之后（按块推进时每块一次，全部读完再一次），把本数据集“待上传”的分区（有文件、不是已复制的，跳过还在退避中的）按导出时间逐个上传：
  读一遍本地文件同时算 MD5 与 sha256（sha256 与记录不符就不传，记“本地文件与记录不一致，需要人工核对”）→ 单次 PUT（带 `Content-MD5`，载荷签 `UNSIGNED-PAYLOAD`，不分片、不带 `x-amz-checksum-*`，超过 5GiB 拒绝）→ HEAD 核对大小、ETag 等于本地 MD5 → 记成已复制并置待上报。
  对象键在扩展名前插入 sha256 前 12 位，例如 `crypto/collect/binance-spot-kline-1m/2026/20261107.csv.gz` → `crypto/collect/binance-spot-kline-1m/2026/20261107.3f9a0c1b2d4e.csv.gz`；每个版本一个对象，不覆盖、不删除，键只由内容决定，重复上传写的也是相同内容。
  `Content-Type`：`.csv.gz` 为 `application/gzip`，`.csv` 为 `text/csv; charset=utf-8`，不设 `Content-Encoding`；用户元数据 `sha256`、`dataset`、`partition` 只为人工查看。
- **失败与重试**：上传失败不让运行失败（文件已经在本地），运行消息写“N 个分区上传对象存储失败：<第一条错误>”，分区记下错误、失败次数与下次重试时刻（`min(1h, 1m × 2^(n−1))`）；对象存储一侧失败（网络、权限、校验）后本次运行不再传后面的分区。
  本地文件缺失或与记录不一致只记这一个分区。重导出（sha256 变了）自动回到待上传，失败次数、重试时刻与错误清零，立刻尝试。
  本次运行导出的分区总要尝试；之前遗留的分区从本次运行第一次上传起累计最多传 2 分钟（`backlogUploadBudget`），首次启用或长时间断网后的积压分摊到之后的运行。
  `dataset.json`：本次有分区上传成功、且内容（sha256）与上次上传的不同时，PUT 到 `<space>/<purpose>/<dir_name>/dataset.json` 覆盖旧的；失败只记日志。
- **读回时取回**：读回已定稿分区时，只有“本地文件不存在”和“sha256 不符”两种情况、且远端是当前版本时，从对象存储取回：sha256 不符的本地文件先改名为 `<文件>.bad-<unix 秒>` 保留（不自动删），
  下载到 `<文件>.partial` 边写边算 sha256，相符才 fsync → rename → fsync 目录，再照常读回；运行消息追加“分区 <键> 已从对象存储取回”。权限、读盘等其他错误照旧报错、运行失败，不改名、不取回；
  远端也没有时报错，本地缺文件的提示是“本地文件缺失且没有可用的远端副本”。按 mgr 登记恢复的分区带着远端字段，所以新机器上第一次读到它时就从远端取回。
- **维护抽查**（每天维护时，在对账之后）：按 `remote_verified_at` 从早到晚 HEAD 最多 100 个已复制的分区核对 ETag，通过的更新校验时间；再从通过的里随机 GET 1 个重算 sha256。
  对象不存在或内容不符就清空远端字段、写原因（“远端副本丢失”“远端副本内容不符”），回到待上传，下一次运行从本地重传；HEAD 的 404 没有正文，先用 GET 确认是对象不存在（桶不存在说明配置错了，不算丢失）。网络、权限错误只记日志、不改状态，并结束这次抽查。抽查结果随该数据集下一次运行上报。
  体量（2026-11 按约 7 个任务估，上线时按 `archive tasks list` 的实际任务数与 `total_file_bytes` 重估）：每天新增约 0.2GB（K 线约 35MB/天，因子结果约为它的 4 倍），每年约 2500 个分区，HEAD 约 25 天轮一遍；GET 每天一个分区（17～70MB），外网下行费每月一两元以内。
  暂存库重建后，早于线上保留期的已复制分区不再下发，也就不在本地状态里，不再被维护抽查。
- **配置与凭据**：`object_store` 段（见下）的 `credentials_file` 指向 `<dir>/secrets/archive-object-store.env`（0600，普通文件，只认 `ACCESS_KEY_ID`、`SECRET_ACCESS_KEY` 两行，各一次，不认引号和 `export`，错误信息不回显值）。启动时读一次，不连网探测，换密钥要重新部署并重启。
  HTTP 客户端不读代理环境变量（直连），连接与 TLS 握手各 10 秒、等响应头 60 秒；HEAD 超时 30 秒，PUT、GET 为 60 秒加按 128KiB/s 估算的传输时间，minio-go 一次调用内最多重试 3 次。错误文本截到 500 字符写库。
- **子命令**：`moox-archive-worker check-config --config <文件>` 完整载入并校验配置、读一遍凭据（Storage 签名密钥与对象存储凭据），不连网，部署脚本在替换配置、重启服务之前先跑它；
  `moox-archive-worker objectstore-check --config <文件> [--large]` 只读配置里的 `object_store` 段与凭据，在 `<prefix>_smoke/<主机名>-<时间戳>/` 下冒烟：PUT 1KB 并 HEAD 核对 ETag、看存储类型、GET 校验、改坏请求体必须被拒、（`--large`）单次 PUT 70MB、DELETE 必须被拒、写到前缀之外必须被拒，记录换一种地址风格的 HEAD 结果与预签名下载结果，最后 HEAD 一个不存在的键必须返回 404（没有列举权限时有的 S3 实现回 403，那样维护抽查发现不了远端丢失）；
  `--key <remote_key> --sha256 <hex>` 只下载指定对象比对 sha256（上线验证用）。输出不含凭据。
  “不给删除”挡不住用同一个键再 PUT 覆盖（上传权限本身允许覆盖）；防线是对象键里带内容 sha256 加每天的抽查。

**数据端口**（`internal/worker/dataapi`，`127.0.0.1:11428`）：给管理台下载分区副本、查看最新数据。端口由服务目录 archive-worker 条目的 `relay_http` 决定，固定只听回环地址、不可配，不验签：
外部只能经 control 的中转进入（服务目录只放行调用方 `console`），浏览器的鉴权由 Admin 的一次性 ticket 完成。

- **路径**：管理台 → Admin 裸 HTTP 路由（第 6 节）→ Admin 取拓扑里唯一启用的 archive-worker 部署（部署与所在主机都启用）：在 control 上就直连 `127.0.0.1:11428`，在只出站主机上就用 console 网关客户端 `DialRelay(<主机>, 11428)` 经中转连接。
  **适用范围**：只支持 worker 装在 control 或只出站主机上；装在其他可直达主机上时返回 501“归档执行器所在主机不支持网页下载与预览（只支持 control 与只出站主机）”。没有启用的部署返回 503，多于一条返回 500。
  Admin 原样转发、透传状态码与响应头；预览 15 秒超时，下载不设整体超时（受 Console 服务的超时上限约束），只限等 worker 响应头 90 秒。
- **`GET /v1/partition?space=&dataset=&partition=`**：按本地分区状态找分区，不在本地登记里返回 404“该分区不在当前执行器的登记里”。只下载远端的当前版本（`remote_sha256 = file_sha256` 且已校验），从对象存储流式读出；
  没配对象存储、当前版本还没上传或没校验、对象存储里找不到时返回 409“远端副本未就绪：…”，读取失败返回 502。不下载本地文件，也不做多分区打包。
  响应头 `Content-Type`（`.csv.gz` 为 `application/gzip`）、`Content-Length`、`Content-Disposition: attachment; filename="<目录名>_<分区键>.csv.gz"`、`X-Moox-SHA256`。
  边读边算 sha256，**扣住最后 64KB**，读完核对相符才写出；不符就中断连接（客户端拿到的文件长度不足）并记日志。
  限速：全部下载共享一个令牌桶 `data_api.max_bytes_per_second`（默认 2MB/s，下限 256KB：同时 2 个下载平分带宽，每个下载从对象存储读取的超时按 128KiB/s 估算），与运行的节奏带宽分开计；同时最多 2 个下载，超出返回 429。
- **`GET /v1/recent?space=&dataset=&subject=&before=&limit=`**：查暂存库里某个标的最近的行，按 `data_time` 倒序，`before`（RFC3339，不含）往前翻页，`limit` 默认 200、最多 500；`subject` 必填，最长 256 字节。
  每次请求单独开只读连接、用完关闭，不挡每天维护的 `wal_checkpoint(TRUNCATE)`。列名与类型读该任务的 `dataset.json`（还没生成时返回 409，任务不在本机返回 404）；时间（纳秒）转 RFC3339 UTC、布尔转 `true`/`false`，NULL 与空串区分照 CSV 规则。
  返回 `{columns, rows, staged_until}`，`staged_until` 是扫描水位（暂存库已从 Storage 读到的时刻）。暂存行保留到“收盘 + L + 72 小时”定稿为止，所以至少有最近 3 天。
- 参数都按目录片段规则校验（不能为空、不能含斜杠或以点开头），错误为中文 JSON `{code, msg, success: false}`。

**CSV 导入**（`kind = import`，`internal/worker/runner/importer.go`）：把本地 CSV 作为历史数据直接写进归档，不经 Storage。只接受归档自己的 CSV 格式（见上文“CSV 格式”，表头用 `moox-cli archive import template` 取）。

1. CLI（`moox-cli archive import`，见[命令行工具](命令行工具.md)）本地预检表头：列名属于数据集的值列或三个系统列、不重复，`data_time`、`subject_id` 必须有；`--overwrite` 时必须带齐全部值列（覆盖是整行替换，缺列会清空已有值）。
2. `PrepareArchiveImport` 取活动 worker 的归档根目录与导入 ID；worker 所在主机取 `moox.toml` `[deployments]` 里唯一部署了 `archive-worker` 的主机，经 SSH（与 `deploy-unit` 前提相同）先 `mkdir -p -m 0700 <root>/.import/<import_id>`，再上传成 `import.csv` 或 `import.csv.gz`（0600，只按扩展名取固定文件名，不用本地文件名）。
3. `ImportArchiveFile` 建运行，`import_file` 是 `<import_id>/<文件名>`；worker 只认 `<root>/.import/<import_id>/<文件名>`，两段都按目录片段规则防路径穿越。
4. **series_tag**：先查该任务暂存表的不同取值（取到两个就停），没有暂存行时读最近一个本地分区文件。CSV 没有这一列时，已知取值必须恰好一个，自动补上，否则要求 CSV 带这一列；
   带了这一列且有值时，已知取值只有一个就必须相等，有多个就必须是其中之一；带了列但留空时，已知取值恰好一个就补上，一个都没有就按空串，有多个就算错误。也就是说，数据集有多个 series_tag 时 CSV 必须带这一列并逐行填写。
5. **第一遍校验**（不写库）：流式解析（`.gz` 自动解压；表头可带 UTF-8 BOM，末尾空行忽略，单条记录最长 1MiB）；`data_time` 为 RFC3339 且按频率对齐（1d 以下是 Unix 纪元起频率时长的整数倍，1d 及以上是空间时区的本地零点），必须按 `data_time` 升序（乱序算错误）；`subject_id` 不能为空；数值按列类型能解析；同一 `data_time` 内主键不重复。
   开盘不在整点的小时级数据集（如 A 股 60m）的 `data_time` 对不上这条规则，当前无法导入。
   收集前 20 条带行号的错误，有错就整次失败，运行消息“导入文件有 N 处错误，整份拒绝，什么都没有写入（只列前 20 条）：第 x 行：…；…”，什么都不写。“有一行不对就整份拒绝”只针对这一遍。
6. **第二遍写入**：每 5 万行一块（不拆开同一 `data_time`）写进暂存区，落在已定稿分区时先读回原文件（同复核）。默认**只补空缺**：同键已存在的行以已归档的为准，不写；`--overwrite` 时走比对替换。没有实际写入的分区不更新 `last_changed_at`，不会白白重导出、重传。
   按块推进时就地导出、上传、定稿已经写完的分区（历史分区当场满足“开始 ≥ 收盘 + L + 暂存保留期”），最后照常上报分区。
   这一遍中途失败或被取消时，已写入的块保留，运行消息写明“已写入前 N 行”；用同一份文件不带 `--overwrite` 重新导入即可补齐（已写入的行算“已存在相同”）。不等节奏、不做保留期截断、不写首次起点与续读起点、不推进水位。两遍都每 1 万行或每 30 秒更新进度，由定时器续 10 分钟的运行租约。
7. 运行消息“导入 N 行（新增 a、已存在相同 b、已存在不同 c 未覆盖/已覆盖），涉及 k 个分区”。成功后删除导入目录；失败保留供核对，worker 每天维护时删除超过 7 天的 `.import/*`。
   导入期间任务有一条运行中的运行，到点拉取与复核被跳过，长时间导入时任务可能显示“已连续跳过 N 次”（需关注），属预期，导入结束后的第一次复核会补上。CLI 经 SSH 上传不限速，经慢链路（如海外机、家庭网络）上传大文件时注意占用带宽。
8. 导入补齐历史缺口后，任务累积的无法补齐区间不会自动消失，确认后用 `archive tasks clear-unrecoverable` 清（第 4 节）。

**配置**（`config/worker/app.yaml`）：`gateway_client`（`access_address`、`access_id`、`caller: archive-worker`、`key_id`、`key_file`；压缩由共享客户端管理，没有 `compression` 配置项）、`storage_auth_file`（Storage Primary 签名密钥，以 AppId `archive` 签名）、`worker`（`worker_id`、`root_dir` 绝对路径、`export_format`（`csv.gz` 默认或 `csv`）、`min_free_bytes`、心跳与领取间隔）、
`staging`（`cache_size` 暂存库页缓存上限，默认 256MB）、`pacing`、`health`、`data_api`（只有 `max_bytes_per_second`，默认 2MB、不能小于 256KB；监听地址不可配）、`maintenance`，以及可选的 `object_store`（整段省略表示不使用）：
`endpoint`（主机名[:端口]，不带协议）、`region`（必填，COS 填地域，R2 填 `auto`；非空时不查桶位置，受限的子账号没有这个权限）、`bucket`、`prefix`（默认 `moox-archive/`）、`url_style`（必填 `virtual` 或 `path`，没有默认值：自动判断对 COS 会选路径风格，而 COS 2024 年以后新建的桶只接受虚拟主机风格）、
`use_tls`（默认 true，false 只用于内网自建存储，启动时打警告）、`storage_class`（可选，按 `x-amz-storage-class` 发送，如 `STANDARD_IA`）、`credentials_file`。未知项被拒绝。

**构建与部署**：worker 是纯 Go（关闭 CGO），在本机交叉编译即可：`bash scripts/build/build-linux-local.sh archive-worker` 得到 linux/amd64 版本；本机运行用 `scripts/build/build.sh archive-worker`。环境准备见[构建手册](../构建手册.md)。
`setup deploy-unit --profile archive-worker` 由 CLI 准备参数与凭据并经 SSH 上传，安装脚本 `scripts/deploy/deploy-archive-worker.sh` 把配置渲染到 `app.yaml.new`，用新二进制 `check-config` 校验通过后才替换配置与二进制、重启服务，并等待 `worker health` 通过（校验不过时脚本退出，旧配置、旧二进制和旧进程都不动）；归档根目录取 `moox.toml` 的 `[paths] archive_root`。
凭据（`access-archive-worker.key`、`storage-primary-auth.secret`，0600）放在 `<dir>/secrets`。`moox.toml` 有 `[archive_object_store]` 时，CLI 在读部署登记的同一个网关上从 Admin 读出 `secret_id` 那条密钥（要求提供方 `s3`、已启用），
渲染成 `archive-object-store.env` 一起上传、装进 `<dir>/secrets`，安装参数带 `--object-store-*`；没有这一段时安装参数带 `--builtin-object-store`：安装并启动包里的 SeaweedFS（`moox-seaweedfs`），凭据由机器上生成的密钥派生，`object_store` 指向 `127.0.0.1:11473`（SeaweedFS 没就绪时部署停下，旧配置、旧凭据和旧进程都不动）。准备工作见[部署与运维](../部署与运维.md)的“归档对象存储”。
**换机器**：用内置 SeaweedFS 时它和归档文件在同一台机器、同一块盘，新机器上的是空的，要把归档目录（含 `.state`）和 `<部署根>/seaweedfs` 一起拷过去。用外部 S3 时，新机器沿用或换一个 `worker_id` 都可以，不用拷目录——暂存库按 mgr 登记重建，读到已定稿分区时从对象存储取回（只取被读到的分区，其余分区的本地热副本以后用 `restore` 补）；旧 worker 登记用 `archive worker retire` 退役。
没拷目录时：新 worker 读到已定稿分区会读回失败、运行失败（可见，不丢数据：登记不许倒退，导出也拒绝覆盖已有记录的文件）。
暂存库丢失时 worker 按 mgr 的分区登记和水位重建，不需要人工处理；暂存库和归档文件一起丢（坏盘）时，用外部 S3 就读回时从远端取回；用内置 SeaweedFS 时远端副本在同一块盘上一起丢了，读回已定稿分区会一直失败，只能全新部署归档（第 8 节）。分区登记被拒（行数倒退）时，核对原文件后删掉 `t_archive_partitions` 里对应的行再重跑。
