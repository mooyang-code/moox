# 归档（Archive）

> 本文描述当前源码已实现的定时归档：**管理端 `moox-archive-mgr`** 与 **worker `moox-archive-worker`**；管理端部署在控制机，worker 部署在因子机。
> 管理台一级菜单“数据归档”下有“归档任务”（`/archive/tasks`）与“归档存储”（`/archive/storage`）两页；历史 CSV 导入用 `moox-cli import --target archive`（见[命令行工具](命令行工具.md)）；清除任务累积的无法补齐区间统一通过 `ClearArchiveUnrecoverable`（管理台任务详情“清除这些记录”或 `moox-cli archive tasks clear-unrecoverable`，`--start`/`--end` 同时留空表示清空全部，同时填写表示删除整段落在 `[start, end)` 内的区间）。

代码位置：`modules/archive`。管理端与 worker 都是纯 Go（关闭 CGO），管理端放在 control 主机；执行读取、暂存和导出的 worker 另外部署在能出站访问控制机与存储机 `11003` 的登记主机上（示例拓扑为因子机）。
对象存储为**可选扩展**：未在 `moox.toml` 配置 `[archive_object_store]` 时，worker 仅保留因子机本地带 SHA-256 的 `.csv.gz`（或 `.csv`）归档目录，管理台可直接经 worker 数据端口做路径安全限制与 SHA-256 校验下载；配置了 `[archive_object_store]` 外部 S3（如腾讯云 COS、Cloudflare R2；见[部署与运维](../部署与运维.md)“归档对象存储”）时，worker 才在导出分区后额外上传一份到对象存储并启用读回取回与每日抽查（见第 9 节“对象存储副本”）；mgr 只登记，不连对象存储。

## 2. 数据模型

四张表（`schema/archive.sql`）：`t_archive_tasks`（一个时序数据集最多一个任务；`c_backfill_from` 是归档起点，`NOT NULL`，创建时确定、之后不改也不清空；状态为 `enabled` / `disabled`；记录最近本地跟随结果 `c_last_follow_at`、`c_last_follow_error`、`c_last_follow_message` 与显式重读进度 `c_rescan_from`、`c_rescan_until`；不存 `partition_unit`、`retention`、`meta_json`、`creator`，其中 `partition_unit` 由 `c_freq` 推导，保留期与数据集元数据进 mgr 5 分钟 TTL 内存缓存）、`t_archive_runs`（仅存 `manual` / `range` / `import` 三种一次性运行，`range` 必须带起止时间；状态为 `queued` / `running` / `succeeded` / `failed` / `cancelled`；仅记 `c_subjects_done`，无冗余 `subjects_total` 列）、
`t_archive_partitions`（每个任务每个分区一行，open / exported / final）、`t_archive_workers`（worker 最近一次心跳的状态，只有一行）。
时间列统一存 **Unix 毫秒整数**（`INTEGER NOT NULL`，0 表示没有）。已有分区的任务不能删除，只能停用。

- **远端副本**：分区登记带 `c_remote_key`（相对对象存储 `prefix` 的对象键，不含 endpoint、桶名和前缀，换桶或换前缀不用改库）、`c_remote_sha256`、`c_remote_etag`、`c_remote_uploaded_at`、`c_remote_verified_at`、`c_remote_error`。
  “已复制”的口径（worker 与 mgr 相同）：有文件，且 `c_remote_sha256 = c_file_sha256`、`c_remote_verified_at` 非空。`c_remote_key` 非空而 sha256 不等于文件的，表示远端只有旧版本、新版本待上传。
- 接口里的 `remote_state`（mgr 计算）：`off`（对象存储未启用，看 worker 最近一次心跳的上报；从未心跳时也算未启用）、`none`（没有文件）、`verified`（已复制）、`failed`（不是已复制且有错误）、`pending`（其余，待上传）。
- 分区登记是 worker 本地暂存库丢失后的重建来源（第 9 节“一次运行”第 0 步）；登记和运行都不记是哪个 worker 写的。
- **目录**：`t_archive_tasks.c_purpose`（`collect` 采集结果、`factor` 因子结果、`data` 其他）与 `c_dir_name` 决定分区目录 `<空间>/<用途>/<目录名>/`，`UNIQUE (c_space_id, c_purpose, c_dir_name)`，建好后不改（规则见第 9 节“目录”）。
- **导入运行**：`t_archive_runs.c_kind = 'import'` 的运行不带文件或区间：行由 `moox-cli import` 经 worker 数据端口写来（第 9 节“导入运行”）。
- `t_archive_runs.c_partitions_uploaded` 是运行上传并校验通过的分区数；`t_archive_workers.c_object_store_json` 存心跳带来的对象存储摘要（endpoint、桶、前缀、存储类型、地址风格，不含凭据）。
- **磁盘**：`t_archive_workers` 只存数值，不存“空间不足”标记。`c_disk_total_bytes` 是总量（statfs `Blocks`），`c_disk_used_bytes` 是已用（`Blocks − Bfree`），`c_disk_free_bytes` 是可用（`Bavail`，不含 root 保留空间），`c_min_free_bytes` 是 worker 配置的下限 `worker.min_free_bytes`（默认 5GB）。
  已用 + 可用小于总量，差额是文件系统给 root 的保留空间。可用低于下限时 worker 停止领取新运行、`/readyz` 降级原因为 `disk_insufficient`；归档存储页按同一个数（可用）和同一个下限判断“磁盘空间不足”，与 worker 一致。

## 3. 任务与跟随规则

任务不填执行计划：**worker 自己运行每分钟本地跟随循环**（对齐每分钟第 25 秒，调 `ArchiveWorker.ListFollowTasks` 取当前全部启用、源数据集存在、且没有排队中或运行中一次性运行的任务与完整执行参数），按最久未跟随优先顺序在并发与读 Storage 上限内执行跟随（第 9 节“一次运行”），完成后调 `ArchiveWorker.ReportFollowResult` 按 `task_id` 校验写入任务行（`c_last_follow_at`、`c_last_success_at`、`c_last_follow_error`、`c_last_follow_message`、`c_rescan_from`、`c_rescan_until`、`c_final_until`、`c_unrecoverable_json`）与分区登记，不再在 `t_archive_runs` 写 `follow` 运行记录。不按整点窗口跳过：避让只由 worker 的节奏执行，整点窗口内的跟随只做导出与定稿。代码在 `internal/worker/app/app.go` 与 `internal/worker/runner/follow.go`。
维护定时器每小时从 Storage 刷新各任务的数据集信息时，更新内存缓存并在 Storage 明确返回“数据集不存在”时在任务上记“源数据集不存在”（写独立列 `c_source_missing`，不改变人工启停状态 `c_status`，也不覆盖分区登记被拒原因 `c_blocked_reason`），将其从 `ListFollowTasks` 清单排除，且不算刷新失败（不退回每分钟重试）；网络错误或 Storage 临时不可用时沿用内存缓存、不动任务状态，照常下一分钟重试。后续刷新发现同名数据集重新出现时自动清除标记并恢复跟随。

**自动补齐任务**：维护定时器每分钟从 Storage 读取全部数据集（`Metadata.ListDatasets`，顺带刷新数据集内存缓存），筛选状态为 `active`、时序类型（`time_series`）且保留期有限（非空且不是 `forever`）的数据集，对尚无归档任务的数据集按默认参数自动建任务（建议目录名、默认回补起点「现在 − 线上保留期 + 1 天」、状态 `enabled`），新建采集或因子任务后无需手工再建。
- **删除与停用的区别**：手工**删除**的归档任务会在下一轮维护被重新建出来；不想归档某个数据集就把任务**停用**（`disabled`），停用的任务不会被重建或自动改回启用。
- **补不上时报关注项**：读取 Storage 数据集清单失败，或个别数据集因目录名冲突、频率不支持等建不出任务时，不阻断其他数据集的补齐，并上报关注项 `attention:archive-mgr:task_ensure_failed`（“归档任务自动补齐失败”）；问题解决后自动恢复。

**任务设置**

- 回补起点（归档起点）：创建时确定，之后不改、成功后也不清空。没填时取「现在 − 线上保留期 + 1 天」，首次运行就整段读线上保留期；保留期为 `forever` 时必须填写。填了的必须早于当前时间且不早于「今天 − 线上保留期 + 1 天」。
  `PrepareArchiveTask` 给出的最早值按当时的时刻算，提交时下界已经后移：早于下界**不到 1 小时**（代码常量 `backfillClampSlack`）的起点夹到下界（向上取整到秒）而不报错，保存与返回的是夹取后的值；差 1 小时以上照旧拒绝。补拉区间（`BackfillArchiveRange`）的起点同理，下发的是夹取后的区间。
  补更早的数据用补拉区间（保留期内）或 `moox-cli import --target archive`（保留期外）。
- `UpdateArchiveTask` 只负责启停（`enabled` / `disabled`，重新启用后从原位点继续跟随）；清除无法补齐区间统一经 `ClearArchiveUnrecoverable`。
- 分区粒度由频率动态推导（不落库）：低于 1d 按空间本地日（`day`）；1d、1w、1mo 按「`data_time` + 12 小时」的 UTC 日期归月（`month`）。

**本地跟随与三种运行**

| 方式 / kind | 谁触发 | 做什么 | 推进什么 |
| --- | --- | --- | --- |
| 本地跟随（不写 `t_archive_runs`） | worker 每分钟本地循环 | 一轮：导出定稿 → 读变更日志 → 用剩余预算整段重读 → 再导出定稿，经 `ReportFollowResult` 回写任务行与分区 | 变更日志位点、整段重读进度、最近成功时间、最近跟随时间与错误 |
| `manual` | 用户（管理台“整段重读”、`archive tasks run`） | 重建基线（整段重读线上保留期），再按跟随跑一轮；之后的本地跟随分段读完 | 同本地跟随 |
| `range` | 用户（补拉区间） | 读 `[range_start, range_end)`，按分区块读、每块之后导出定稿 | 不推进位点 |
| `import` | `moox-cli import --target archive`（`StartArchiveImport`） | 占住任务，接收经数据端口写来的批次，结束后统一导出 | 不推进位点 |

**为什么由 worker 本地循环跟随**：只有单个 worker，把每分钟的稳态跟随留在 worker 本地循环后，mgr 不必每任务每天向 SQLite 写 1440 条 `follow` 运行记录，也省去 `trigger.timer`、两档清理与让位取消逻辑；`t_archive_runs` 保持精简，只留需要人工发起与追踪的一次性作业（`manual`、`range`、`import`）。任务重建安全靠 `ReportFollowResult` 校验 `task_id` 兜底，同数据集互斥靠 worker 本地 `acquireDataset` 保证（领到的手动运行等待当轮本地跟随结束并照常续租）。

**重建基线与整段重读**（首次运行、位点断档、暂存库新建、`manual`）

1. 取变更日志头部位点 H（`ReadDatasetChanges(from_head)`，只取位点、不等节奏）。
2. 下界 S = max(归档起点 A, 保留期起点 R)：A = min(暂存库里最早一个分区的开始（含按 mgr 登记补齐的）, 回补起点)；R = 运行开始 − 线上保留期（`forever` 时没有）。早于 A 的写入不读，否则会新建只含改动段、看起来完整的分区（Storage 里那个分区别的数据从没读过）。`[回补起点, 最早分区)` 首次运行已整段读过，之后那里的写入都在变更日志里，读进来的分区与 Storage 一致：先建任务、后补的历史（补采、因子补算、`import --target storage`）因此照样进归档。变更日志跟随的截断用同一个 S。
3. 一个事务里写位点 = H、整段重读进度 `[S, 取到 H 之后的时刻)`（暂存库 `task_state.rescan_from`、`rescan_until`）。先落位点再读数据：H 之后的写入由日志读取覆盖，之前的由整段重读覆盖。
4. 无法补齐（上报 `unrecoverable`，长度不到一根 K 线跨度时不记）：位点断档或暂存库丢失（mgr 下发了最近成功时间）且最近成功早于 R 时记 `[最近成功, R)`；真正的首次运行（没有最近成功）且回补起点早于 R 时记 `[回补起点, R)`。manual 不记。

整段重读按段读：低于 1d 一段到下一个整点（最多 1 小时数据时间，不跨分区），1d 及以上一段是一个分区；每段写进暂存区后把 `rescan_from` 推进到段末。到达 `rescan_until` 所在的那一段时终点取 `2200-01-01`（不设上界），读完两列清空：晚于基线时刻的行也一并读到，不依赖“数据时间不晚于写入时刻”。
**整段重读进行中，导出、上传与定稿只处理结束不晚于 `rescan_from` 的分区**，否则一个日分区会随每段重读被反复导出、读回，并在暂存保留期已过的历史日上定稿成只有半天数据的分区。
整段重读进行中，worker 在 `ReportFollowResult` 与 `CompleteArchiveRun`（`manual`）里以显式字段 `rescan_from`、`rescan_until` 上报当前重读区间，mgr 落入 `t_archive_tasks.c_rescan_from`、`c_rescan_until`（重读完成后清空为 0）；任务列表接口返回 `rescan_from`、`rescan_until`，管理台任务行跟随列与健康判定直接读取这两个字段，不再解析运行消息文本。

耗时（V7 估算，真机验收时回填）：crypto 1m 现货与永续各约 500 个标的、保留 35 天、各约 2500 万行，每行响应约 225 字节，一个数据集约 5.6 GB；带宽 512 KB/s 只在发请求的时间里有效（秒窗口一半、整点窗口去掉 6 分钟），约 230 KB/s，一个数据集约 6.8 小时，两个同时重读共用令牌桶约 13～14 小时。想快可临时调大 worker 的 `pacing.max_bytes_per_second`。

**按标的读**：一页日志的范围先截掉早于 S 的部分，再按分区整理成时间并集 `[最早, 最晚]` 与涉及的标的集合。标的数不超过 100（`ReadTimeSeriesRows` 的 selector 上限）时每个标的带一个 selector（频率取任务频率）读这段时间；超过 100 或日志条目没带标的时读这段时间里的全部标的。补采常常只补一两个标的的一长段，按标的读不会把全部标的的同一段重读一遍；实时写入每分钟涉及全部标的但只有一根，走全部标的。
整理出的范围再按时间先后切段，都不跨分区，每轮读取预算在段的边界检查：读全部标的的按整段重读的粒度切（低于 1d 最多 1 小时，1d 及以上一个分区）；带 selector 的按“标的数 × K 线根数 ≤ 3 万”切（代码常量 `selectorSegmentRows`，与 crypto 1m 读全部标的一小时一段差不多大）：100 个标的的 1m 日分区切成 5 段，20 个以内一个日分区一段，单标的补一长段时不把请求数放大。

**冲突规则**（`store.CreateRun`，manual、range、import 共用）：本任务已有排队中或运行中的 manual、range、import 时返回冲突，错误写明挡住它的运行种类与 run_id；正在 worker 本地执行的跟随不挡新运行的创建，worker 领到后经本地 `acquireDataset` 等待当轮跟随让出数据集（等待期间续租定时器照常续租）。

**读 Storage 的名额**：本地跟随与 `manual`、`range` 共同计入 worker 的 `max_storage_runs`（默认 2；导入运行不占此名额）；worker 调 `PullArchiveRun` 时把本地正在跟随的任务数一并计入 `busy_storage_runs` 与已占并发槽。跟随在整点窗口内提前结束、每轮读满预算（1 分钟，最多再超一段）就结束，并在本地按“最久未跟随优先”轮转、在槽位释放后优先尝试 `pullOnce`，避免长重读饿死其他任务或手动运行。

**避让规则**（常量在 `internal/schedule`，由 worker 的节奏执行）：归档读取要避开采集写入，写死两个窗口，不读采集频率、不随心跳下发。

- 每分钟只在第 25～55 秒（`[25s, 55s)`）读取 Storage：避开采集函数在收盘那一分钟第 0 秒的触发与随后的写入（stream 与本地执行端同样在第 0 秒触发）。
- 每小时 `:58:00～:04:00`（UTC，跨整点）不读取：避开 1h 及以上数据集在整点的集中收盘。A 股不按交易时段细分。
- 每分钟的秒窗口可用 `pacing.minute_window` 关掉（第 9 节“节奏”）。导出与定稿不读 Storage，不受这两个窗口约束。
- 写死只会偏保守：全部空间都只有 5m 等较粗频率时，其余 4 分钟的开头本可以读也不读；没有 1h 及以上频率时，整点窗口也照样避开。

## 4. 运行的生命周期

`t_archive_runs` 只存三种一次性运行：`manual`、`range`（必须带区间，表约束）、`import`。同一任务同时只执行一条运行；冲突规则见第 3 节。

1. **生成**：`RunArchiveTaskNow` 生成 `manual`，`BackfillArchiveRange` 生成 `range`，`StartArchiveImport` 生成 `import`（worker 不在线时报错）。每分钟常规跟随由 worker 本地循环执行，不写运行表。
2. **领取**：部署里只有一个 worker，mgr 不区分是谁来领：worker 每次拉取按计划时刻从早到晚领取，跳过已有运行中运行的任务（同一任务同时只执行一条），不超过空闲槽数和读 Storage 的并发上限 `max_storage_runs`（导入运行不读 Storage 时序数据（只取一次列信息），不占这个名额；仍占一个并发槽；本地跟随同时计入总并发槽与 `busy_storage_runs`）。领取时写 10 分钟的运行租约和随机令牌，之后的进度与完成上报只认这个令牌。
   worker 重启后（新进程、同一身份）第一次心跳成功就能继续领取；重启前领走、没来得及上报的运行等运行租约过期后由维护定时器标为失败（第 5 步），这期间该任务不会再被领取。
   已知情况：不防两个 worker 进程同时运行（部署只装一个）。误启动两个时两者都会领取运行（同一任务仍只有一条在执行），`t_archive_workers` 那一行在两者之间来回变，同一台机器上还会同时写同一个暂存库；发现后停掉多余的那个。
   下发的参数里带运行类型与区间、任务 ID（删除后重建会换新值）、允许迟到、归档起点、任务最近一次成功的跟随或 manual 的开始时间（位点断档时据此判断无法补齐的区间），以及按需同步的分区登记（`ArchivePartition`，含远端字段），worker 本地暂存状态丢失时据此重建（见第 9 节）。
   下发哪些登记：未在 `synced_tasks` 中匹配当前 `task_id`（暂存库新建/丢失或任务重建）时，以及导入运行时，一次性下发该任务的全部已登记分区，保证暂存库重建后超保留期旧分区在纯本地模式下仍可下载且日后启用外部 S3 不漏传。
3. **进度与取消**：`ReportArchiveRunProgress` 续租并上报统计；用户取消的运行立即标为 `cancelled`，worker 在下次心跳（`cancel_run_ids`）或进度上报（`cancelled`）得知并停止，收尾时仍可上报已导出的分区。
4. **完成**：`CompleteArchiveRun`（及本地跟随的 `ReportFollowResult`）在一个事务里更新运行或任务状态、分区登记（`ArchivePartition`）、定稿边界（只前进不回退）、显式重读进度（`rescan_from`/`rescan_until`）和累积的无法补齐区间；只有成功的本地跟随与 `manual` 更新任务的最近成功时间，**补拉区间与导入不更新**。失败的事务整体回滚。完成上报带上传数（`partitions_uploaded`）。
   导入成功**不自动删除**任务累积的无法补齐区间（区间不带标的，按时间范围自动判断会把真实缺口藏掉）；清除入口统一为 `ClearArchiveUnrecoverable`（管理台任务详情“清除这些记录”、CLI `archive tasks clear-unrecoverable`）：`start` 与 `end` 都留空时清空全部，都填写时只删掉整段落在 `[start, end)` 里的区间，返回删掉的条目。
   分区的远端字段按上报值整体替换；open 状态不带文件信息时，文件与远端字段一并沿用已登记的值。**文件大小兜底**：上报的 `file_bytes` 是上报时 stat 的，本地文件不在时为 0，路径与 sha256 都没变时保留已登记的大小。
   **分区登记不许倒退**：已有文件的分区，上报的行数或标的数比已登记的少就整次拒绝——运行或跟随记为失败并写明哪个分区从多少降到多少，分区不动、任务记 `c_blocked_reason`，返回冲突；worker 不清待上报标记，之后每次运行或跟随都会再报、再被拒，任务一直显示异常。归档只增不删（读回合并后不会变少），变少只会来自暂存状态丢失后用残缺数据重新导出，需要人工核对原文件。
5. **租约过期**：维护定时器把租约过期的运行标为 `failed`，原因按 worker 此刻是否在线（2 分钟内有心跳）写：不在线是「worker 失联：租约到期时 worker 已停止心跳」；在线是「租约到期时 worker 仍在心跳，但没有续租这条运行：领取的响应可能没送到 worker（网络超时），或 worker 重启后丢了这条运行」（mgr 已记开始、worker 没收到领取响应时就是这样）。
   位点与重读进度只在读完一个单位之后才推进，下一轮本地跟随接着读，不会丢数据。
6. **清理**（维护定时器每小时一次）：运行表统一按单档 `run.retention`（默认 90 天）清理已结束的运行记录。
7. **列表**：`ListArchiveRuns` 列出全部一次性运行（`manual`、`range`、`import`），不再需要 `include_follow` 参数；任务列表的「最近一次运行」反映最近一次一次性运行，而每分钟本地跟随的最近时间、错误与重读进度直接记在任务行上。

## 5. 健康等级

| 条件 | 等级 |
| --- | --- |
| 最近一次成功的本地跟随或 manual 距今超过「线上保留期 − 2 天」（从未成功则按创建时间算）；任务累积过无法补齐的区间；分区登记被拒；源数据集不存在（此时不再叠加保留期与跟随超时提示）；有到期运行或启用任务等待跟随但 worker 离线超过 30 分钟；读不到数据集的线上保留期 | 异常 |
| 最近一次本地跟随失败（`last_follow_error` 非空）；最近一次一次性运行失败且晚于最近成功跟随；最近一次成功的跟随距今超过 30 分钟（从未成功则按创建时间算，覆盖 worker 卡住、跟随连续失败、名额长期被占）；有分区到时间（收盘 + 允许迟到）超过 1 小时仍未导出（任务的显式重读进度 `rescan_from`/`rescan_until` 非空时不判，那时导出本来就只到重读进度） | 需关注 |
| 启用了对象存储时：最早一个不是已复制的分区（有文件）导出超过 72 小时（`remoteErrorAfter`） | 异常 |
| 启用了对象存储时：同上，超过 24 小时（`remoteWarnAfter`） | 需关注 |
| 其他 | 正常；停用的任务显示为已停用（`disabled`） |

本地跟随每分钟执行一次：失败的补拉区间、导入会被之后的成功跟随覆盖，健康里不再持续告警；这两种由用户发起，命令行与页面当场能看到结果。

远端副本规则的原因文案：`共 N 个分区还没有已校验的远端副本，最早的 <分区键> 导出已超过 24 小时（3 天）；最近错误：…`。N 是该任务全部未复制分区的数量（含还没满 24 小时的），时长只按最早那个分区算；最近错误取该任务 `c_mtime` 最新的那条。
计时起点是**当前版本**的导出时间，重导出后从新的导出时间重新计；不另设“多久没抽查”的规则：抽查发现远端丢了会重置成待上传，导出时间早，马上就是异常。
规则只在 worker 报告启用了对象存储时生效（判断方式同 `remote_state` 的 `off`）。任务列表同时给出 `remote_verified_count`（已复制的分区数）与 `remote_pending_count`（有文件但不是已复制的，含失败的），没启用时都是 0。Monitor 不用改：规则通过等级生效，原因进 `health_reason`。

mgr 每 30 秒按各任务的健康等级上报关注项 `attention:archive-mgr:task_failing`（“归档任务异常”，列出异常的空间/数据集；需关注不告警），
并上报自动补齐任务的失败情况 `attention:archive-mgr:task_ensure_failed`（“归档任务自动补齐失败”，读取 Storage 清单失败或有符合条件的数据集建不出任务时告警，补齐后自动恢复）。worker 离线由 archive-mgr 的关注项 `worker_offline` 告警。

对象存储可用性单独成一项：worker 配置了外部对象存储时每分钟对不存在的键 `<prefix>_probe/absent` 做 HEAD（404 或 200 算可用，连接失败、403、5xx 等算不可用），把最近的失败原因 `probe_error` 与连续不可用的起点 `unavailable_since` 放进心跳的 `ObjectStoreInfo`（`archive overview` 的 `worker.object_store` 可见）。mgr 每 30 秒按最近心跳的 worker 判断，连续不可用超过 5 分钟时上报关注项 `attention:archive-mgr:object_store_down`（detail 带最近一次探测失败原因；没配置对象存储或 2 分钟内没有心跳时不报），Monitor 据此生成检查 **归档对象存储**：2 告警，1 只把原因写上。worker 重启后起点重新计。

## 6. 接口

`ArchiveMgr`（15 个业务方法；**无模块级生命周期暂停**，不实现 `GetLifecycle` / `ControlLifecycle`，不接受 `moox-cli lifecycle --module archive-mgr`，按任务启停即可）：`GetArchiveOverview`、`ListArchiveTasks`、`PrepareArchiveTask`、`CreateArchiveTask`、`UpdateArchiveTask`、`DeleteArchiveTask`、
`RunArchiveTaskNow`（建 manual：整段重读）、`BackfillArchiveRange`、`CancelArchiveRun`、`ListArchiveRuns`、`GetArchiveRun`、`ListArchivePartitions`、`GetArchivePartition`、
`StartArchiveImport`（为 `moox-cli import` 的归档目标建一条导入运行：任务存在、worker 在线（2 分钟内有心跳）才建，返回运行与 `worker_id`（`archive-worker@<主机 ID>`）；冲突时写明挡住它的运行）、`ClearArchiveUnrecoverable`（`start` 与 `end` 都为空时清空全部无法补齐区间，都填写时删掉整段落在 `[start, end)` 里的区间）。

- 接口里的墙钟时刻（运行的 `scheduled_at`、`started_at`、`finished_at`、`lease_until`，任务的 `last_follow_at`、`last_success_at`、`created_at`、`updated_at`，分区的 `last_changed_at`、`exported_at`、`finalized_at`、`remote_uploaded_at`、`remote_verified_at`，worker 的 `last_heartbeat_at` 与对象存储的 `unavailable_since`）是 int64 Unix 毫秒，0 表示没有；分区范围、数据时间、回补起点、`final_until`、`rescan_from`、`rescan_until` 是 `data_time` 口径的 RFC3339 文本。库表里的时间列同样存 Unix 毫秒整数。
- 除 `StartArchiveImport` 只给 `moox-cli` 外，其余 14 个方法（含 `ClearArchiveUnrecoverable`）均向 `console`、`moox-cli` 开放。
- `GetArchiveOverview`、`ListArchiveTasks`、`PrepareArchiveTask` 与 4 个查询方法为只读，另外允许 `monitor` 调用。
- 经 Console 的调用以请求头里的空间为准，请求体里的 `space_id` 与之不一致时拒绝；内部调用方（CLI）在请求体里指定空间。
- `CreateArchiveTask` 带 `dir_name`（为空取建议值）和 `disabled`（建好先停用），目录名被同空间同用途的其他任务占用时返回冲突“目录名 <名> 已被 <数据集> 使用，请改一个”；`UpdateArchiveTask` 只改状态（`enabled` / `disabled`），不能改目录名与回补起点。
- `PrepareArchiveTask` 返回频率、分区粒度、保留期、最早回补起点，以及用途 `purpose`、建议目录名 `suggested_dir_name` 与 `dir_name_conflict`（请求带 `dir_name` 时检查它，否则检查建议值）。

`ArchiveWorker`（6 个方法）：`ArchiveWorkerHeartbeat`、`ListFollowTasks`、`ReportFollowResult`、`PullArchiveRun`、`ReportArchiveRunProgress`、`CompleteArchiveRun`。心跳上报磁盘总量、已用、可用与下限（`disk_total_bytes`、`disk_used_bytes`、`disk_free_bytes`、`min_free_bytes`），回包带需要取消的运行；只有维护对账请求带 `include_tasks = true` 时 mgr 才查询并返回当前全部任务（普通 10 秒心跳不查任务表）。`ListFollowTasks` 与 `PullArchiveRun` 请求携带 `synced_tasks`（worker 本地暂存库已完成分区同步的任务列表含 `task_id`），仅当任务不在该列表或 `task_id` 变化（暂存库新建/丢失或任务重建）时，mgr 才按需下发 `registered_partitions`（`ArchivePartition`）。
`FollowTask` / `RunAssignment` 带任务的 `purpose`、`dir_name`、`allowed_lateness_seconds`、`backfill_from`（归档起点）与 `last_success_at`。调用方 `archive-worker` 在服务目录的调用名单里只有：
`PrimaryStore.ReadTimeSeriesRows` / `ReadDatasetChanges`、`Metadata.GetDataset` / `ListDatasetColumns`，以及这 6 个方法。

控制台的分区下载与最新数据预览不走 tRPC：Admin 的两个裸 HTTP 路由 `/api/admin/archive/PartitionDownload`、`/api/admin/archive/RecentRows`（和别的管理台请求一样按会话 Cookie 鉴权，浏览器同源下载自己带 Cookie，不需要票据）转给 worker 的数据端口，见第 9 节“数据端口”。

## 7. 配置（`config/app.yaml`）

`database.path`、`gateway_client`（caller `archive-mgr`）、`run.lease_ttl`（运行租约，10 分钟）、`run.retention`（`manual`/`range`/`import` 运行记录保留期，默认 90 天，不小于 7 天）、
`allowed_lateness`（分区收盘后再等多久才导出，默认 15 分钟，不能小于 15 分钟）、`staging_retention`（72 小时）。
避让的两个窗口（第 3 节）是代码常量（`internal/schedule`），不进配置。`config/trpc_go.yaml` 只保留 `mgr.maintain.timer`（每分钟第 13 秒），不再有 `mgr.trigger.timer`。
未知配置项会被拒绝。`MOOX_ARCHIVE_DB_PATH` 可覆盖数据库路径。
空间时区与数据集保留期/元数据均由 mgr 从 Storage 元数据（`Metadata.GetSpace`、`Metadata.GetDataset` / `ListDatasets`）读取，并共用 5 分钟 TTL 内存缓存（Storage 临时不可用时沿用旧缓存），与管理台“数据归档 › 归档任务”页天然保持单一事实源（crypto=UTC、stockcn=Asia/Shanghai、stockhk=Asia/Hong_Kong、stockus=America/New_York）。各空间的本地日终时刻与是否全天交易统一从共享包 `packages/barclock` 读取（A 股 15:00、港股 16:10 含收市竞价、美股 16:00，加密货币与未登记空间按全天交易处理）。

## 8. 部署

`archive-mgr` 是服务目录里的可选组件（`moox.toml` 不部署它时不装）。服务目录里登记了组件 `archive-mgr` 与 `archive-worker`、`Metadata.GetDataset` / `Metadata.ListDatasets` 对 `archive-mgr` 的放行，以及 archive-worker 的 `relay_http` 数据端口；
**目录内嵌在 Admin、Monitor、各主机 host-gateway 与 moox-cli 中，改了目录就要让全部主机升到同一提交**：逐台 `setup deploy`，控制机先（见[部署与运维](../部署与运维.md)）。构建：`scripts/build/build.sh archive-mgr`。

**部署方式**：archive-mgr 是控制机上的一个组件，和 factor-mgr 一样由 `setup deploy` 部署成 systemd 用户服务 `moox-archive-mgr`（配置 `<部署根>/config/archive-mgr/`、数据 `<部署根>/data/archive-mgr/`、日志 `<部署根>/logs/archive-mgr/`）。在 `moox.toml` 的 control 部署里加入 `archive-mgr` 即启用。

**全新部署归档**：归档的库结构、目录规则或运行类型变了时不写升级 SQL，也不让新旧两套目录并存，而是清空后按新规则重建任务、从 Storage 线上保留期内回补。前提是要保留的分区都还在 Storage 保留期内（先用 `archive tasks list` 与 `archive partitions list` 核对最早分区）。步骤：

1. 记下当前任务清单（`moox-cli archive tasks list`：数据集、回补起点、状态），备份 control 上 archive-mgr 的 `archive.db*` 与 worker 主机上的 `<归档根目录>/.state/staging.db*`。
2. 停 worker：在 `moox.toml` 的 `[deployments_disabled]` 里写上这台主机的 `archive-worker`，`setup deploy --host <worker 主机> --component archive-worker`，用 `systemctl --user is-active moox-archive-worker` 确认已停。
3. 停掉 archive-mgr：`moox-cli setup stop --host <控制机> --component archive-mgr --yes`，确认进程已退出。进程还在时不要动库文件。
4. 清旧数据：删除 archive-mgr 的 `archive.db`、`archive.db-wal`、`archive.db-shm`；清空 worker 的归档根目录（含 `.state`）；配置了外部 S3 时照同样的前缀清理远端各空间的旧对象。
5. 部署新版本：改了服务目录时逐台 `setup deploy`，控制机先。`setup deploy --host <控制机>` 会按声明把 archive-mgr 重新拉起，启动时按内嵌的 schema 建新库（没有新版本要部署时用 `moox-cli setup start-component --host <控制机> --component archive-mgr --yes`）。
6. 从 `[deployments_disabled]` 删掉 `archive-worker`，`setup deploy --host <worker 主机> --component archive-worker`。
7. 等待维护定时器自动补齐全部有限保留期的时序数据集任务（保留期为 `forever` 或需指定自定义目录名、回补起点的任务，用 `archive tasks prepare` 核对后手工 `archive tasks create`），不需要归档的数据集将对应任务停用；保留期之外的历史用 `moox-cli import --target archive` 导入。
8. 核对：Monitor 中没有 `attention:archive-mgr:task_ensure_failed` 告警；回补完成后分区路径是新目录、`datasets.csv` 行数与任务数一致、远端副本全部已校验；在归档任务页下载一个分区，`sha256sum` 与响应头 `X-Moox-SHA256` 一致。

## 9. worker（`moox-archive-worker`）

代码在 `modules/archive/cmd/worker` 与 `internal/worker/*`，纯 Go（暂存库是 SQLite）；它是服务目录里的外部程序组件，登记在因子机的 `[deployments]` 里，用 `moox-cli setup deploy --host factor` 部署成 systemd 用户服务 `moox-archive-worker`（停用与恢复改 `moox.toml` 的 `[deployments_disabled]` 后部署，见[部署与运维](../部署与运维.md)）。worker 离线约 3.5 分钟后 Monitor 推送“归档 worker 在线状态”告警。mgr 只记最近心跳的那个 worker：换了 `worker_id`（换机器）后旧的一行随新 worker 的第一次心跳删除。worker 只出站：以组件 `archive-worker` 的身份、用因子机的主机密钥直连控制机与存储机的 `11003`，调用 `ArchiveWorker` 与 Storage，
不订阅 EventBus，不监听 tRPC 端口；本机只有健康检查 `127.0.0.1:11418`（`moox-archive-worker health` 子命令查询，不验签）与数据端口 `127.0.0.1:11428`（见下文“数据端口”）。

**主循环**（`internal/worker/app`）：每 10 秒心跳（磁盘总量、已用、可用与下限，暂存库大小、正在执行的运行、是否在维护、生效的节奏；普通心跳只返回需要取消的运行，每日维护对账时才传 `include_tasks=true` 拉取当前全部任务）；每分钟第 25 秒运行本地跟随循环（调 `ListFollowTasks` 拉取可跟随任务，按最久未跟随优先在并发与读 Storage 上限内执行本地跟随，结束后调 `ReportFollowResult` 上报任务状态、显式重读进度与分区登记）；有空闲并发槽时每 5 秒拉取一次性运行（`PullArchiveRun`，启动后第一次心跳成功之后才开始；带上本地跟随与非导入运行合计的 `busy_storage_runs` 与本地已同步分区的 `synced_tasks`，按需拉取 `registered_partitions`；维护中、可用空间低于 `min_free_bytes` 时停止跟随与领取，`/readyz` 原因为 `disk_insufficient`）。每个一次性运行在独立协程里执行，每 30 秒上报进度并续租，结束时上报结果；上报失败退避重试 6 次，mgr 返回冲突（运行已结束、任务 ID 不匹配或令牌失效）或不存在就放弃。续租与进度由独立的定时器负责（等待本地跟随让出数据集、读取、导出、定稿、排队期间都续租）。
同一数据集的执行（本地跟随与手动、补拉、导入运行）经 `acquireDataset` 在本地串行；每个分区带「待上报」标记，mgr 确认登记之后才清除，所以上报失败的分区会在后续跟随或运行里再次上报（定稿后的统计在定稿时记进暂存库的分区状态）。

**一次运行**（`internal/worker/runner`）：
0. 绑定与重建：任务 ID 与本地记录不同（任务删除后重建）就丢掉该数据集的全部暂存状态（含位点与重读进度）。按 mgr 下发的分区登记补齐本地缺的分区状态：登记里有文件的一律按 `final` 恢复（统计、路径、sha256 取登记值），没有文件的不恢复。随后取数据集的列、建暂存表、写 `dataset.json`。
1. **follow / manual**（`follow.go`，T = 运行开始）：
   1. manual 先重建基线（第 3 节），不论位点是否有效。
   2. 先导出、上传、定稿到期的分区（重读进行中只到 `rescan_from`，日志页读了一半时跳过正在读的分区，见第 6 步），不读 Storage，休市时也靠它定稿。
   3. 下一个允许读取的时刻比现在晚 2 分钟以上（落在整点窗口里）时本轮到此结束、记成功，消息“整点窗口内只做导出与定稿”：否则 :58～:04 两个读 Storage 的名额会被等着读的运行占满 6 分钟。
   4. 暂存库 `task_state` 没有位点（首次运行、暂存库新建）就重建基线。
   5. **本轮读取预算**：日志与整段重读共用，按本轮墙钟计：已过 60 秒，或现在不能读（秒窗口已过第 55 秒、或进了整点窗口）就在段（日志页切出的段或重读段）的边界停下，剩下的留给下一轮。**每轮至少读一段**，保证有进展；之后才看预算，所以一轮最多超出预算一段。
   6. 从位点起读一页变更日志（`PrimaryStore.ReadDatasetChanges`，`limit` 2000：按全库日志计数的最多扫描条数，不是本数据集的条数，一页的大小另由 Storage 按字节截断，见存储文档 5.1）→ 按第 3 节“按标的读”整理、切段 → 按时间先后逐段读行、写暂存区 → 一页的段全部写完才把位点推进到这一页的 `next_cursor` → 预算未用完且还有下一页就接着读。
      预算在一页中间用完时，剩下的段和这一页的 `next_cursor` 记在 worker 内存里（不进暂存库），位点不动；下一轮暂存库里的位点仍是这一页的起点、任务 ID 也没变，就不再取这一页、从下一段接着读，中途失败或取消时同样从下一段接着读。manual、断档重建、任务重建会重设位点，记下的段随之作废；worker 重启后内存里的段没了，从位点重读整页（写暂存区按主键比对替换，重读幂等）。
      一页读了一半时，**正在读的那个分区**（剩下的第一段所在的分区）在两轮之间不导出、不定稿，读完才导出：否则一个日分区会随之后每一轮被反复导出、定稿、读回，每次还上传一个新版本（与整段重读只导出到 `rescan_from` 同理）。成功的消息带“变更日志这一页还剩 N 段没读（从 X 起），下一轮接着读”。
      任何一页断档（日志只保留 7 天、worker 停得更久，或存储重建）就重建基线，本轮不再读日志。
   7. 用剩余预算整段重读（`rescan_from` 非空时），每段写完推进进度。
   8. 再导出、上传、定稿一次，生成分区登记上报。
   读日志或读行失败时运行失败，位点与重读进度不动，下一分钟重来；已写进暂存区的行留着。
2. **range**：读下发的 `[range_start, range_end)`，起点早于线上保留期截止的部分截掉（截掉一根 K 线以上时记为「无法补齐」），按分区边界切块，逐块读、每块之后导出定稿；不读变更日志、不动位点。
3. 读行：逐页（游标，`pacing.page_rows` 默认 500、上限 2000 行，失败重试 3 次）读取，带或不带 selector（第 3 节）。
4. 写入暂存区：每页先进临时表，与暂存表按主键比对（`IS DISTINCT FROM`），只写新增和变化的行（同键一律覆盖），同一事务里更新受影响分区的 `last_changed_at`。要写入已定稿分区时，先按记录的路径核对 sha256，再把原文件按列名读回暂存表并标为 `exported`（读回的行不算变化，所以重复读到的行不会触发重写）。
5. 导出：`运行开始 ≥ 分区收盘时间 + 允许迟到` 且分区需要导出（从未导出，或导出之后又有变化）→ 从 SQLite 流式读取并由 Go 编码到 `<文件>.partial`（默认 csv.gz），写入时一起算 sha256 → fsync → rename → fsync 目录 → 生成预览，路径记进分区状态。已有记录路径的分区写回原路径（按扩展名沿用原格式）；没有记录而目标文件已存在时拒绝导出，运行失败——防止暂存状态丢失后用残缺数据覆盖完整文件。
   定稿：`运行开始 ≥ 分区收盘时间 + 允许迟到 + 暂存保留期`、没有待导出的变化、文件存在且 sha256 一致 → 每个分区一个事务删除暂存行、标 `final`。
6. 上报：本次涉及的分区（状态、行数、标的数、数据时间范围、文件路径 / 大小 / sha256、列、预览）、运行统计和定稿边界（最早的连续已定稿分区的结束时间）。

已知情况：调用名单由存储机、控制机的主机网关按内嵌的服务目录算，升级时这两台的网关要和 worker 一起换或先换。

**暂存库 `task_state`**：每个数据集一行，`task_id`、`purpose`、`dir_name`、`meta_remote_sha256`、变更日志位点 `change_store_id`、`change_sequence`，以及整段重读进度 `rescan_from`、`rescan_until`（纳秒，平时为 NULL，只在重读期间有值，表示 `[rescan_from, rescan_until)` 还没读）。暂存库的表结构变了不写迁移：全新部署时停掉 worker，删除 `staging.db`（及 `-wal`、`-shm`）后重启，分区登记从 mgr 重建，位点为空会重建基线、整段重读保留期内的数据（读回已定稿分区比对，多数相同、不重导）。
**文件**：`<root_dir>/<space>/<purpose>/<dir_name>/<yyyy>/<yyyymmdd|yyyymm>.csv.gz`（`worker.export_format: csv` 时为不压缩的 `.csv`），`<root_dir>/<space>/<purpose>/<dir_name>/dataset.json`（数据集说明：数据集 ID、中文名、简介、数据来源 ID、标的范围、线上保留期、创建与更新时间，分区方式与时区，文件格式与路径规则，以及每一列的名称、类型、中文名、来源和别名；列定义取自 Storage 的数据集列，数据集信息由 mgr 每小时刷新后随运行下发，内容有变化才重写）。`<root_dir>/.state/staging.db`（SQLite，WAL 文件为 `staging.db-wal`）是暂存区与永久保留的分区状态；`<root_dir>/datasets.csv` 是目录对照表（见下文“目录”）。
每个任务一张 `WITHOUT ROWID` 暂存表（表名由 space + dataset 决定，与目录名无关），主键 (subject_id, data_time, series_tag)，另有 data_time 索引；所有时间列存 Unix 纳秒整数（Storage 行键保留纳秒）。

**CSV 格式**（RFC 4180，逗号分隔，`\n` 换行）：表头 `data_time,subject_id,series_tag,<值列…>`，按 data_time、subject_id、series_tag 排序；
`data_time` 与时间列为 UTC RFC3339，秒以下保留到纳秒（尾随 0 省略，整秒时为 `2026-10-15T01:00:00Z`）；浮点数为最短可精确往返的十进制写法（绝对值小于 1e21 时不用指数形式），整数值带 `.0`，
无穷写作 `+Inf` / `-Inf`（NaN 在暂存库里存为缺失值）；布尔为 `true` / `false`；二进制为标准 base64；缺失值是不带引号的空字段，空字符串写作 `""`，
含逗号、引号、换行或首尾空白的字段加引号。定稿分区被补写时按同样的规则读回，读回的行与原文件逐字段一致。
值列取来源为字段或因子、状态启用的列；系统列与行属性不导出。
日分区按空间时区的本地日切分，月分区按「`data_time` + 12 小时」的 UTC 日期归月（分区在 `data_time` 上的范围是 `[当月 1 日 − 12h, 下月 1 日 − 12h)`）。

**节奏**（`internal/worker/pacing`）：按第 3 节写死的两个窗口发起请求：每分钟只在第 25～55 秒发，:58 到下一小时 :04 之间不发。心跳上报的 `pacing_json` 是配置里的秒窗口开关、请求间隔、带宽与并发上限。
同一运行两次请求至少间隔 200ms；所有并发运行共享一个 512KB/s 的令牌桶；最多 4 个运行并发（`max_concurrent_runs`），其中读 Storage 的运行（导入除外）最多 2 个（`max_storage_runs`，不超过 `max_concurrent_runs`）。避让依赖本机时钟，部署机器必须开启 NTP。
每分钟的秒窗口由 `pacing.minute_window` 控制，默认 `true`；设为 `false` 则整分钟都可发请求（人工开关），整点窗口、带宽和请求间隔仍然生效。导入运行不读 Storage，不受节奏限制。follow 一轮的读取预算（第 9 节“一次运行”）用 `AllowedAt` 判断现在能不能读，跟着这两个窗口走。每次请求发出前都会检查当前时间，落在禁区就等到允许时刻；读取请求不使用网关客户端内部的重试（`gatewayclient.WithoutRetry`），失败由 worker 自己重试，每次重试前同样先检查时间。

**维护**（每天 04:17:43，本机时区）：停止领取并等进行中的运行结束（最多 30 分钟），再发一次心跳取当前全部任务，删掉不在列表里（或任务 ID 不同）的数据集的暂存表与状态（取不到列表就跳过这一步），然后 `PRAGMA incremental_vacuum` 回收空闲页（暂存库建库时为 `auto_vacuum = INCREMENTAL`）并 `wal_checkpoint(TRUNCATE)`。启动时清理残留的 `.partial` 文件。

**对象存储副本**（`internal/objectstore`，配置了 `object_store` 才启用）：只用标准 S3 操作——单次 PutObject、HeadObject、GetObject，客户端 `minio-go` v7，代码里没有任何厂商专有接口、请求头或 SDK，换 R2、B2、自建 S3 兼容存储只改配置。
- **导出即上传**：每次导出之后（每轮导出定稿时、补拉区间每块之后），把本数据集“待上传”的分区（有文件、不是已复制的，跳过还在退避中的）按导出时间逐个上传：
  读一遍本地文件同时算 MD5 与 sha256（sha256 与记录不符就不传，记“本地文件与记录不一致，需要人工核对”）→ 单次 PUT（带 `Content-MD5`，载荷签 `UNSIGNED-PAYLOAD`，不分片、不带 `x-amz-checksum-*`，超过 5GiB 拒绝）→ HEAD 核对大小、ETag 等于本地 MD5 → 记成已复制并置待上报。
  对象键在扩展名前插入 sha256 前 12 位，例如 `crypto/collect/binance-spot-kline-1m/2026/20261107.csv.gz` → `crypto/collect/binance-spot-kline-1m/2026/20261107.3f9a0c1b2d4e.csv.gz`；每个版本一个对象，不覆盖、不删除，键只由内容决定，重复上传写的也是相同内容。
  `Content-Type`：`.csv.gz` 为 `application/gzip`，`.csv` 为 `text/csv; charset=utf-8`，不设 `Content-Encoding`；用户元数据 `sha256`、`dataset`、`partition` 只为人工查看。
- **失败与重试**：上传失败不让运行失败（文件已经在本地），运行消息写“N 个分区上传对象存储失败：<第一条错误>”，分区记下错误、失败次数与下次重试时刻（`min(1h, 1m × 2^(n−1))`）；对象存储一侧失败（网络、权限、校验）后本次运行不再传后面的分区。
  本地文件缺失或与记录不一致只记这一个分区。重导出（sha256 变了）自动回到待上传，失败次数、重试时刻与错误清零，立刻尝试。
  本次运行导出的分区总要尝试；之前遗留的分区从本次运行第一次上传起累计最多传 2 分钟（`backlogUploadBudget`），首次启用或长时间断网后的积压分摊到之后的运行。
  `dataset.json`：本次有分区上传成功、且内容（sha256）与上次上传的不同时，PUT 到 `<space>/<purpose>/<dir_name>/dataset.json` 覆盖旧的；失败只记日志。
- **读回时取回**：读回已定稿分区时，只有“本地文件不存在”和“sha256 不符”两种情况、且远端是当前版本时，从对象存储取回：sha256 不符的本地文件先改名为 `<文件>.bad-<unix 秒>` 保留（不自动删），
  下载到 `<文件>.partial` 边写边算 sha256，相符才 fsync → rename → fsync 目录，再照常读回；运行消息追加“分区 <键> 已从对象存储取回”。权限、读盘等其他错误照旧报错、运行失败，不改名、不取回；
  远端也没有时报错，本地缺文件的提示是“本地文件缺失且没有可用的远端副本”。按 mgr 登记恢复的分区带着远端字段，所以新机器上第一次读到它时就从远端取回。
- **维护抽查**（每天维护时，在对账之后）：按 `remote_verified_at` 从早到晚 HEAD 最多 100 个已复制的分区核对 ETag，通过的更新校验时间；再从通过的里随机 GET 1 个重算 sha256。
  对象不存在或内容不符就清空远端字段、写原因（“远端副本丢失”“远端副本内容不符”），回到待上传，下一次运行从本地重传；HEAD 的 404 没有正文，先用 GET 确认是对象不存在（桶不存在说明配置错了，不算丢失）。网络、权限错误只记日志、不改状态，并结束这次抽查。抽查结果随该数据集下一次运行上报。
  体量（2026-11 按约 7 个任务估，上线时按 `archive tasks list` 的实际任务数与 `total_file_bytes` 重估）：每天新增约 0.2GB（K 线约 35MB/天，因子结果约为它的 4 倍），每年约 2500 个分区，HEAD 约 25 天轮一遍；GET 每天一个分区（17～70MB），外网下行费每月一两元以内。
  暂存库重建后，早于线上保留期的已复制分区不再下发，也就不在本地状态里，不再被维护抽查。
- **配置与凭据**：`object_store` 段（见下）的 `credentials_file` 指向 `<部署根>/secrets/archive-object-store.env`（0600，普通文件，只认 `ACCESS_KEY_ID`、`SECRET_ACCESS_KEY` 两行，各一次，不认引号和 `export`，错误信息不回显值）。启动时读一次，不连网探测，换密钥要重新部署并重启。
  HTTP 客户端不读代理环境变量（直连），连接与 TLS 握手各 10 秒、等响应头 60 秒；HEAD 超时 30 秒，PUT、GET 为 60 秒加按 128KiB/s 估算的传输时间，minio-go 一次调用内最多重试 3 次。错误文本截到 500 字符写库。
- **子命令**：`moox-archive-worker check-config --config <文件>` 完整载入并校验配置、读一遍凭据（主机签名私钥与对象存储凭据），不连网；
  `moox-archive-worker objectstore-check --config <文件> [--large]` 只读配置里的 `object_store` 段与凭据，在 `<prefix>_smoke/<主机名>-<时间戳>/` 下冒烟：PUT 1KB 并 HEAD 核对 ETag、看存储类型、GET 校验、改坏请求体必须被拒、（`--large`）单次 PUT 70MB、DELETE 必须被拒、写到前缀之外必须被拒，记录换一种地址风格的 HEAD 结果与预签名下载结果，最后 HEAD 一个不存在的键必须返回 404（没有列举权限时有的 S3 实现回 403，那样维护抽查发现不了远端丢失）；
  `--key <remote_key> --sha256 <hex>` 只下载指定对象比对 sha256（上线验证用）。输出不含凭据。
  `moox-archive-worker probe --config <文件> --space <空间> --dataset <数据集> [--span 76m] [--page-rows 2000] [--pages 5]` 用 worker 自己的身份读几页区间数据并打印每页耗时，排查读取慢或超时用，不写任何东西。
  “不给删除”挡不住用同一个键再 PUT 覆盖（上传权限本身允许覆盖）；防线是对象键里带内容 sha256 加每天的抽查。

**数据端口**（`internal/worker/dataapi`，`127.0.0.1:11428`）：给管理台下载分区副本、查看最新数据，给 `moox-cli import` 的归档目标写入批次。端口由服务目录 archive-worker 条目的 `relay_http` 决定，固定只听回环地址、不可配，不验签：
外部只能经 control 的中转（服务目录只放行调用方 `console` 与 `moox-cli`）、SSH 本地转发或 control 本机的 Admin 进入，浏览器的鉴权由 Admin 按会话 Cookie 完成；Admin 只转发两个 GET 路径、非 GET 返回 405，写接口不会经控制台暴露。

- **路径**：管理台 → Admin 裸 HTTP 路由（第 6 节）→ Admin 取拓扑里唯一启用的 archive-worker 部署（部署与所在主机都启用）：在 control 上就直连 `127.0.0.1:11428`，在只出站主机上就用 console 网关客户端 `DialRelay(<主机>, 11428)` 经中转连接。
  **适用范围**：只支持 worker 装在 control 或只出站主机上；装在其他可直达主机上时返回 501“归档执行器所在主机不支持网页下载与预览（只支持 control 与只出站主机）”。没有启用的部署返回 503，多于一条返回 500。
  Admin 透传 worker 的状态码与正文，响应头只透传 `Content-Type`、`Content-Length`、`Content-Disposition`、`X-Moox-SHA256` 4 个，其余不转发；Admin 自己会返回 405（只支持 GET）、502（连不上执行器）、504（等响应超时）。预览 15 秒超时，下载不设整体超时（受 Console 服务的超时上限约束），只限等 worker 响应头 90 秒。
- **`GET /v1/partition?space=&dataset=&partition=`**：按本地分区状态找分区，不在本地登记里返回 404“该分区不在当前执行器的登记里”：
  - **未配置外部对象存储（`Remote == nil`）**：直接读取本地已导出的分区文件（未导出返回 409“本地归档文件未就绪：该分区还没有导出”）；先用 `filepath.IsLocal` 拒绝绝对路径、反斜杠与越界相对路径，再通过 `os.OpenRoot(Files.Root)` 打开归档根目录并校验目标为普通文件（防止路径穿越与符号链接逃逸，磁盘文件不存在返回 409），设 `Content-Length` 后走同一套 `verifiedCopy` 流式校验写出。
  - **配置了外部对象存储（`Remote != nil`）**：下载远端的当前版本（`remote_sha256 = file_sha256` 且已校验），从对象存储流式读出；当前版本还没上传或没校验、对象存储里找不到时返回 409“远端副本未就绪：…”，读取失败返回 502。不做多分区打包。
  响应头 `Content-Type`（`.csv.gz` 为 `application/gzip`）、`Content-Length`、`Content-Disposition: attachment; filename="<目录名>_<分区键>.csv.gz"`、`X-Moox-SHA256`。
  边读边算 sha256，**扣住最后 64KB**，读完核对相符才写出；不符就中断连接（客户端拿到的文件长度不足）并记日志。
  限速：全部下载共享一个令牌桶 `data_api.max_bytes_per_second`（默认 2MB/s，下限 256KB：同时 2 个下载平分带宽，每个下载从对象存储读取的超时按 128KiB/s 估算），与运行的节奏带宽分开计；同时最多 2 个下载，超出返回 429。
- **`GET /v1/recent?space=&dataset=&subject=&before=&limit=`**：查暂存库里某个标的最近的行，按 `data_time` 倒序，`before`（不含）往前翻页。
  校验：`subject` 必填，最长 256 字节，必须是合法 UTF-8，不能含 NUL、回车、换行；`before` 可省略，给了就必须是 RFC3339（可带纳秒）且在 1678～2261 年之间；`limit` 可省略（默认 200），给了就必须是 1～500 的整数；不合规时返回 400。
  每次请求单独开只读连接、用完关闭，不挡每天维护的 `wal_checkpoint(TRUNCATE)`。列名与类型读该任务的 `dataset.json`（还没生成时返回 409，任务不在本机返回 404）；时间（纳秒）转 RFC3339 UTC、布尔转 `true`/`false`，NULL 与空串区分照 CSV 规则。
  返回 `{columns, rows}`。暂存行保留到“收盘 + 允许迟到 + 72 小时”定稿为止，所以至少有最近 3 天；页面按任务的最近成功时间提示“之后写进 Storage 的行可能还没进暂存库”。
- `space`、`dataset`（以及 `/v1/partition` 的 `partition`）按目录片段规则校验（不能为空、不能含斜杠或以点开头），错误为中文 JSON `{code, msg, success: false}`。

- **`POST /v1/import/rows?run=<run_id>`**：请求体是 protobuf 编码的 `storagepb.PrimaryUpsertFieldsReq`（与 moox-cli 写 Storage 的同一种行，上限 8 MiB，超了返回 413），交给正在执行的导入运行写进暂存区，写完返回 `{"added","changed","same"}`。
  运行不存在、不是导入运行、已停止或已收到 finish 时返回 404；worker 可用磁盘低于 `min_free_bytes` 时返回 507；批次不合法（列名不在任务列里、键的空间或数据集不符、频率不符、`data_time` 不能解析或超出纳秒范围、类型不符）整批拒绝、返回 400 和原因。
- **`POST /v1/import/finish?run=<run_id>`**：通知导入运行批次已全部写完，立即返回 202（不等导出）。
- 两个处理器不直接碰暂存库，而是交给 App：按 run_id 找到运行，把批次放进该运行的通道，等运行协程写完回结果。串行就靠“只有运行协程写暂存区”保证，不另加锁。数据端口的读超时 1 分钟（批次经 control 中转上传较慢）。

**导入运行**（`kind = import`，`internal/worker/runner/import.go`）：`moox-cli import --target archive`（见[命令行工具](命令行工具.md)）的写入端，行的解析与校验都在 CLI 一侧（与写 Storage、因子机本地同一套规则）。

1. CLI 第一次写入时调 `StartArchiveImport` 建运行，等它从排队变成运行中（排队超过 3 分钟就取消自己建的运行，报出挡住它的运行）；`worker_id` 的主机必须等于 `moox.toml` `[deployments]` 里唯一部署了 `archive-worker` 的主机，不一致就取消运行并报错。
2. worker 绑定任务、按 mgr 下发的**全部**分区登记补齐本地状态、建暂存表，然后循环收批次：每批按列名把 `TypedValue` 转成暂存值（与读 Storage 同一套规则，`source.Convert`），比对写进暂存区（同键一律覆盖；落在已定稿分区的先读回），每批之后更新进度（行数记 `rows_read`）。
3. 结束条件：收到 finish；或 30 分钟没有收到批次（`importIdleTimeout`，CLI 中途退出时）；或运行被取消。
4. 不论哪种结束，都先导出、上传、定稿全部到期的分区（不受重读进度限制），再上报。finish 结束记成功，消息“导入 n 行（新增 a、已存在相同 b、已存在不同已覆盖 c），涉及 k 个分区”；空闲超时记失败、取消记取消，消息写明“已写入的行已照常导出；用同一条 moox-cli import 命令重跑会按断点跳过已写批次”。
5. 导入运行占住任务：期间 mgr 的 `ListFollowTasks` 自动排除该任务，分钟本地跟随也就不会在两批之间导出半截分区；变更日志保留 7 天，结束后接着读。
6. worker 重启：运行协程退出，租约过期后 mgr 记失败；CLI 写批次得到 404，报错并提示重跑续传；已写的行留在暂存区，由之后的本地跟随导出。
7. **暂存库体积**：导入运行要等结束才导出，暂存库的峰值就是整次导入的行数。实测约 110 字节/行（7 个值列；按列数外推约 40 + 10 × 值列数），导出文件（csv.gz）约 30～40 字节/行。已知最大的一次导入（永续 5m，501 个标的 × 6 万根，约 3000 万行）暂存库约 3.3 GB，加导出文件、WAL 与 `.partial` 峰值约 4.5～5 GB，与 `min_free_bytes`（默认 5 GB）同一量级。
   所以 CLI 预检按“(导入行数 + 时间范围内已登记分区的行数) × (40 + 10 × 值列数) × 1.5”估算（落在已定稿分区的批次会把整个分区读回暂存区；1.5 计入导出文件与 WAL），与 `disk_free_bytes − min_free_bytes` 比较，不够就拒绝并提示按时间拆成几次导入；worker 写接口在磁盘不足时返回 507，兜住估算偏差。500 个标的一年 1m（约 2.6 亿行、暂存约 29 GB）会被挡下，需要拆分。定稿后暂存行删除，但文件要等每天维护的 `incremental_vacuum` 才缩回。
8. 导入补齐历史缺口后，任务累积的无法补齐区间不会自动消失，确认后统一经 `ClearArchiveUnrecoverable`（CLI `archive tasks clear-unrecoverable` 或管理台任务详情“清除这些记录”）按区间或整体清除（第 4 节）。

**配置**（`config/worker/app.yaml`）：`gateway_client`（`caller: archive-worker`、本机的主机签名私钥 `key_file`，以及部署渲染的 `host_id`、`local_address`、`ca_file`；压缩由共享客户端管理，没有 `compression` 配置项）、`worker`（`worker_id`、`root_dir` 绝对路径、`export_format`（`csv.gz` 默认或 `csv`）、`min_free_bytes`、心跳与领取间隔）、
`staging`（`cache_size` 暂存库页缓存上限，默认 256MB）、`pacing`、`health`、`data_api`（只有 `max_bytes_per_second`，默认 2MB、不能小于 256KB；监听地址不可配）、`maintenance`，以及可选的 `object_store`（整段省略表示不使用）：
`endpoint`（主机名[:端口]，不带协议）、`region`（必填，COS 填地域，R2 填 `auto`；非空时不查桶位置，受限的子账号没有这个权限）、`bucket`、`prefix`（默认 `moox-archive/`）、`url_style`（必填 `virtual` 或 `path`，没有默认值：自动判断对 COS 会选路径风格，而 COS 2024 年以后新建的桶只接受虚拟主机风格）、
`use_tls`（默认 true，false 只用于内网自建存储，启动时打警告）、`storage_class`（可选，按 `x-amz-storage-class` 发送，如 `STANDARD_IA`）、`credentials_file`。未知项被拒绝。

**构建与部署**：worker 是纯 Go（关闭 CGO），在本机交叉编译即可：`bash scripts/build/build-linux-local.sh archive-worker` 得到 linux/amd64 版本；本机运行用 `scripts/build/build.sh archive-worker`。环境准备见[构建手册](../构建手册.md)。
`setup deploy --host <worker 主机>` 从模板渲染 `<部署根>/config/archive-worker/app.yaml`（归档目录固定是 `<部署根>/archive`），把凭据写到 `<部署根>/secrets/`，重启服务并等本机 `/readyz` 就绪。
worker 和别的组件一样用所在主机的签名私钥 `secrets/host.key`（0600）、以 `archive-worker` 的身份签名，经本机主机网关取目录，再直连存储机与控制机的 `11003`；Storage 没有调用方密钥，只靠服务端口只监听本机加网关访问控制。`moox.toml` 有 `[archive_object_store]` 时，CLI 从 Admin 读出 `secret_id` 那条密钥（要求提供方 `s3`、已启用），写成 `secrets/archive-object-store.env`，并渲染 `object_store` 段；未配置 `[archive_object_store]` 时省略 `object_store` 段，worker 仅保留本地带 SHA-256 的归档文件并支持管理台直接校验下载。准备工作见[部署与运维](../部署与运维.md)的“归档对象存储（可选）”。
**换机器**：未配置外部 S3 时，归档文件只存在本机磁盘，换机须把整个归档目录（含 `.state`）拷到新机器。配置了外部 S3 时，新机器沿用或换一个 `worker_id` 都可以，不用拷目录——暂存库按 mgr 登记重建，读到已定稿分区时从对象存储取回（只取被读到的分区；批量取回其余分区的命令还没有，见第 11 节）；旧 worker 的那一行随新 worker 的第一次心跳删除。
没拷目录时：新 worker 读到已定稿分区会读回失败、运行失败（可见，不丢数据：登记不许倒退，导出也拒绝覆盖已有记录的文件）。
暂存库丢失时 worker 按 mgr 的分区登记重建、重建基线后整段重读线上保留期，不需要人工处理；暂存库和归档文件一起丢（坏盘）时，配置了外部 S3 就读回时从远端取回，未配置外部 S3 时已定稿分区无远端副本可读回，只能全新部署归档（第 8 节）。分区登记被拒（行数倒退）时，核对原文件后删掉 `t_archive_partitions` 里对应的行再重跑。

## 10. 已知差别

1. **首次运行整段读线上保留期**：crypto 1m 两个任务约 13～14 小时（第 3 节）；期间页面能看到进度（任务行跟随列的 `rescan_from`/`rescan_until`）。
2. **整点窗口 :58～:04 内的 follow 只导出定稿、不读**，这几分钟的写入在 :04 之后的第一轮读到。
3. **读 Storage 名额只有 2 个**：两个任务整段重读或读长积压期间，其它任务的 follow 要排队几分钟（每轮最多超出预算一段，按验收实测速度一段约 4～5 分钟，见第 21 条）；用户发起的长补拉区间会一直占一个名额。
4. **同一分区同一轮里既有全部标的的实时写入、又有少数标的的长段补采时**，退回读全部标的的时间并集，这一轮会读得多。
5. **补拉区间、导入失败会被下一次成功的 follow 盖住**，任务健康里看不出来；这两种都由用户发起，结果当场可见。
6. **导入期间该任务的分钟跟随暂停**，与 Storage 目标一起导入时可能持续几小时；变更日志保留 7 天，结束后接着读。期间任务健康的“最近一次成功的跟随距今超过 30 分钟”会亮需关注，属预期。导入写批次失败（CLI 退出）后，导入运行要等 30 分钟空闲超时才结束，这期间该任务也不跟随。
7. **只写归档、数据时间落在线上保留期内的导入值，以后会被 Storage 的值换回**：Storage 对同一区间的任何写入、或一次整段重读，都会把暂存区比对成 Storage 的版本。归档以 Storage 为准，要改保留期内的值应连 Storage 一起导入。
8. **历史导入一律覆盖同键**，没有“以已归档的为准”。
9. **导入格式是 moox-cli 口径**：1d 按 UTC 零点对齐、拒绝 NaN/Inf、字符串列写不进空字符串、bytes 按原文（归档导出的 base64 文件不能原样再导入）、只支持 1m～1d；`series_tag` 写错的检查只有“非空”，与实时数据是否一致仍要用 `data rows export` 核对。
10. **只写归档时不检查标签范围**，写错标的名会在归档里多出一个标的（摘要会列出不在范围内的标的）。
11. **大导入要拆**：暂存库要装下整次导入，约 110 字节/行（7 个值列），预检按磁盘余量拒绝。
12. **回补起点建好后不能改**，补更早的数据用补拉区间（保留期内）或导入（保留期外）。早于回补起点（且早于最早分区）的写入跟随时不读，也要这样补。
13. **数据集清空重灌后，Storage 里已不存在的旧行会留在归档里**：跟随只把读到的行比对替换进暂存区，不删暂存区或已定稿文件里多出来的行。
14. **整段重读的最后一段不设上界**：最后一段是 `[rescan_until 所在段的起点, 2200-01-01)`，读全部标的。首次重读要十几个小时时，读到最后“现在”已比 `rescan_until` 晚十几个小时，这一段要一次读完这段时间的新数据（crypto 1m 约 40 万行，占名额几分钟）。这是为不依赖“数据时间不晚于写入时刻”有意的选择。
15. **暂存库丢失按位点断档处理**：位点为空但 mgr 有最近成功时间时，上报 `[最近成功, 保留期起点)` 为无法补齐（这段时间里写进 Storage、数据时间早于保留期起点的行已被清掉）。
16. **整段重读的最后一段不受每轮预算限制**：最后一段一次读到底，首次重读或位点断档后的重读快结束时，这一轮会占一个读 Storage 的名额较久（见第 14 条）。
17. **删任务重建后重跑同一条导入命令会全部跳过**：`moox-cli import` 的断点按文件与参数算身份，不含归档任务；任务删掉重建、归档已清空时，同一条命令会认为各批都写过。此时换一个 `--job-db` 或指定新的 `--job-id` 再导入。
18. **整段重读实际耗时可能接近第 3 节估算的两倍**：预算只在段的边界检查，一段（1 小时数据，约 30 秒）在第 55 秒之前开始就会照常读完，段内每页都等秒窗口，于是跨到下一分钟的窗口里；这一轮跨两分钟，下一轮 follow 要等它结束才生成，每分钟的有效读取比估算的半分钟少。真机验收时以实测为准。
19. **一大段变更分很多轮读完，期间这个任务的归档落后、但每轮都成功**：补采、补算一次写进上百万行时（2026-11-26 验收时美股补采重试约 233 万行、因子补算约 110 万行，读取约 100～200 行/秒），总耗时不变，只是不再一轮占着名额读几个小时。“最近一次成功的跟随距今超过 30 分钟”不会因此亮起，积压只在运行消息“变更日志这一页还剩 N 段没读”里看得见。整段重读进行中时同一轮先读日志，长积压读完之前重读进度不动。
20. **读了一半的日志页只记在 worker 内存里**：worker 重启后从位点重读整页，已读的段再读一遍（结果相同）；重启后的第一轮还不知道哪个分区读了一半，可能把它导出一次，读完后再导出一次。
21. **一轮最多超出预算一段，一段要读几分钟**：按验收实测约 100～140 行/秒估算（第 18 条按带宽估算的“一段约 30 秒”是理想情况），带 selector 的段最多约 3 万行（第 3 节“按标的读”），约 4～5 分钟；读全部标的的段与整段重读相同，crypto 1m 约 500 × 60 = 3 万行，也是 4～5 分钟。
    标的很多的数据集读全部标的时一段更大：A 股 1m 约 6000 个标的，一小时一段约 36 万行，约 45～60 分钟，这一轮占一个名额这么久（整段重读同样）。
