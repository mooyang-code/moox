# 事件中心

事件中心（组件 ID `callback-dispatcher`，进程 `moox-callback-dispatcher`，源码 `modules/callbackdispatcher`）是一个通用功能：
从 EventBus 接收系统里发生的变更，你在管理台「事件中心」配置要关注的事件，事件发生时向你自己实现的 HTTP 接口发通知，
或者执行 MooX 自带的处理（系统动作）。第一个系统动作是标的下架时禁止买入、下架前平仓。

下架检测作为事件的生产者放在[采集](采集.md)里：Collector 发现“标的即将下架”就发布事件，由事件中心按规则处理。

## 1. 部署

- 独立部署单元，profile 和组件 ID 都是 `callback-dispatcher`；由 `moox.toml` 的 `[deployments]` 决定装在哪台主机，示例里默认在海外机。
  部署主机必须能访问到你填写的通知地址：接口在国内内网时，把它装到能访问的那台机器上。系统动作只经网关调用 Trade，装在哪台都可以。
- 安装与升级都不动别的单元：`moox-cli setup deploy-unit --host <主机> --profile callback-dispatcher`。
- 端口：RPC `11460`（loopback），健康检查 `11461`，指标上报定时器 `11463`，Prometheus `12965`。
- 自有 SQLite 库 `data/moox_callback_dispatcher.db`，库里有通知验证密钥，文件权限 0600。
- 系统动作经网关调用 Trade，调用方身份是 `callback-dispatcher`（配置里的 `gateway_client`，安装时写入）；网关打不开（没有安装身份、读不到目录）服务就启动失败，不会悄悄退化成“只记录”。
- 全局服务，不分空间：调用方是 `console` 和 `moox-cli`，管理台路径 `/api/admin/callback-dispatcher/<方法>`，不进 Admin 的空间授权。
- 健康检查只看数据库；EventBus 连不上只在详情里显示。服务可以比 EventBus 先启动，每分钟重试连接，连上后自动开始接收。

## 2. 可订阅的事件

目录只放在本服务里（`internal/catalog`），不改事件注册表。第一版开放：

| 事件 | 界面名 | 可限定的范围 |
| --- | --- | --- |
| `event.storage.dataset.period.completed` | 数据集一期完成 | 空间、数据集 |
| `event.storage.view.data.ready` | View 数据就绪 | 空间、View |
| `event.collector.kline.backfilled` | K 线补写 | 空间、数据集 |
| `event.collector.instrument.delist_scheduled` | 标的即将下架 | 交易所、市场、交易所代码 |

限定范围全部来自信封（空间、subject），匹配是通用的，不解析各事件的 payload：同一字段的多个取值是“或”，不同字段之间是“且”，不限定就是全部。
不开放的事件：`MOOX_TRADE` 的策略目标（工作队列，再挂消费者会和 Trade 抢消息）、`dataset.rows.upserted` 和 `dataset.sync_point`（量大且偏内部）、监控事件。
目录里的每个事件必须在注册表里声明过、所属的流不是工作队列，测试会核对，也核对它和 `events.CallbackDispatcherEvents`（EventBus 凭据按它生成权限）是同一批。
以后开放新事件，在目录里加一项并同步 `CallbackDispatcherEvents`。

## 3. 事件规则

一条规则：名称、触发事件、限定范围、动作、启用开关。动作有两种：

- **通知地址**：URL（只允许 http、https，不能内嵌账号密码）。创建时服务生成验证密钥 `whsec_…`，只在创建的返回里完整出现一次，
  之后只显示末 4 位。要换密钥就删掉规则重新新建（只能在管理台）。规则可以勾选“允许内网地址”。
  通知地址本身会出现在规则列表、执行记录和日志里：不要把令牌、密钥放进地址的路径或查询参数，接收方用验证密钥验签即可。
- **系统动作**：第一版只有“卖出策略持有的下架币”，只能用在“标的即将下架”上。它是服务自带的一条系统规则，首次启动时自动创建，
  默认启用；用户可以停用，但不能修改、不能删除，也不能新建系统动作规则（免得重复平仓）。

更新规则只改请求里带了的字段（`--enabled=false` 不会清掉名称和地址）；系统规则只接受启停。删除规则会把它还没结束的执行记录置为已取消。

## 4. 接收与执行

**接收**：每个可订阅事件一个固定的 durable（名字见[事件总线](事件总线.md)），`MaxDeliver` 不限次数：写库失败不能丢事件。
“标的即将下架”用 DeliverAll（流保留 72 小时，第一次上线时能收到 Collector 已经发出的下架，回放无害，同一事件会被去重），其余事件用 DeliverNew。

收到事件后：先用 `events.DecodeRaw` 解码并校验，再用 protojson 把 payload 转成紧凑 JSON（蛇形字段名，int64 按 protojson 约定写成字符串）；
匹配所有启用的规则；在**一个事务里**先往 `t_event_receipts`（主键：事件 ID、规则 ID）插一行——插不进去说明处理过，跳过——再写执行记录。
写库成功才确认消息。匹配不上任何规则的直接确认，不留记录。解码失败的终止，并计入 `moox_callbackdispatcher_event_errors_total`。

- 通知地址：写一条状态为待处理的执行记录。
- 系统动作：按合并键（规则 + 交易所:市场:代码）合并或新建。同一标的已有未结束的记录时，只在下架时间或范围变了才更新它的事件内容并让它立即到期，不新建；
  已结束的记录不再参与合并，同一标的之后的新事件会新建一条。合并键上有一个只覆盖未结束记录的部分唯一索引。

**执行**由独立的工作线程处理，和 JetStream 消费解耦，一条通知失败不会让同批后面的事件一起退避。执行记录的 `c_next_run_at` 是下一次该处理它的时间，
跨天的系统动作靠它推进。进程重启时把停在“执行中”的记录放回待处理（投递是“至少一次”）。处理期间如果有新事件合并进同一条记录，
处理结果不会覆盖新的安排，记录立即重新处理。
领取后不等处理完（慢接口不拖住下一轮），每条规则同时最多处理 2 条，限额在领取的 SQL 里按规则做，积压的规则占不满领取名额。
领取时记下领取时间（`c_claimed_at`），它同时是凭证：写回结果必须对得上。停在“执行中”超过 10 分钟的记录每分钟放回待处理，旧线程迟到的结果写不进来；
一次处理（发通知、系统动作推进一步）的时限是 5 分钟，所以旧线程在被放回前已经被取消。系统动作的处理器单步要远快于这个时限。

### 通知请求

```text
POST <通知地址>
Content-Type: application/json
X-MooX-Event-Id: <事件 ID>
X-MooX-Event: <事件名>
X-MooX-Timestamp: <发送时的毫秒时间戳>
X-MooX-Signature: sha256=<HMAC-SHA256(验证密钥, 时间戳 + "." + 请求体) 的十六进制>

{"event_id":"...","event":"event.collector.instrument.delist_scheduled","version":1,
 "space_id":"mooxsys","subject":"binance:SPOT:FOOUSDT","occurred_at":"2026-11-04T08:00:00Z",
 "rule_id":"...","data":{...payload 的 JSON...}}
```

返回 2xx 算成功。投递语义是“至少一次”，同一事件可能收到多次，请用 `X-MooX-Event-Id` 去重；不保证顺序。验签（Go）：

```go
mac := hmac.New(sha256.New, []byte(secret))
mac.Write([]byte(timestamp + "." + string(body)))
ok := hmac.Equal([]byte("sha256="+hex.EncodeToString(mac.Sum(nil))), []byte(signatureHeader))
```

也应检查时间戳与当前时间相差不大，防止重放。

### 出站防护

通知地址由用户填写，出站请求要防住误配置和 SSRF（`packages/netguard`，出口代理共用同一份）：

- 只允许 http、https；不跟随重定向（3xx 当作配置错误，请直接填最终地址）；不使用环境变量里的代理；每个请求新建连接，不复用。
- 连接超时 3 秒，总超时 10 秒；响应体最多读 64 KB，只记录前 1 KB。
- 解析域名后逐个检查 IP，通过才拨号，并且直接用检查过的 IP 拨号，防止 DNS 重绑定；IPv4、IPv6 都检查。
  回环、链路本地（含云元数据 169.254.169.254）、组播、保留与文档地址一律拒绝，落在内网段里的云元数据地址（阿里云 100.100.100.200、AWS IPv6 fd00:ec2::254）也一律拒绝，勾选“允许内网地址”同样不放行；内网段（10/8、172.16/12、192.168/16、100.64/10、IPv6 ULA）默认拒绝，规则勾选“允许内网地址”才放行。
  被防护拒绝是配置错误，直接失败不重试。
- 不经过出口代理（它只放行交易所），直接出站。

### 重试与告警

- 失败后按 1 分钟、5 分钟、30 分钟、2 小时、6 小时、12 小时重试；重试用完，或从第一次失败起下一次重试会超过 24 小时，执行记录置为失败。
- 返回 4xx（408、429 除外）、3xx、被防护拒绝的不重试，直接失败：多半是配置错了。网络错误、超时、5xx、408、429 重试。
- 重新执行（`RetryEventExecution`）把失败记录放回待处理并清零失败计数，重试间隔从 1 分钟重新开始；尝试编号继续累计。
- 执行记录保留 30 天（可配）。

告警走 Monitor 的“关注项”：服务每 30 秒按库里的状态重新计算并上报 `moox_callbackdispatcher_attention_active{kind,detail}`，重启不丢。

| 种类 | 触发 | 持续到 |
| --- | --- | --- |
| `execution_failed` | 通知类执行记录失败 | 用户重新执行或确认 |
| `delist_detected` | 收到新的“标的即将下架”并且当前有策略持有 | 约 3 分钟：触发一次、恢复一次，相当于一条通知 |
| `action_failed` | 系统动作记录失败（核对时仍有持有）；还没结束的记录里有下架步骤失败或只平了一部分；取消后的善后（解除禁止买入）没做成；下架后核对时留有零头（只报一次） | 用户处理；有失败步骤的在记录结束后恢复，零头约 3 分钟 |

Monitor 把它们汇总成 `event_center_attention:*` 业务检查（见[监控](监控.md)）。

## 5. 系统动作：卖出策略持有的下架币

代码：`internal/action`（注册点与 Trade 客户端接口）、`internal/action/delist`（处理器）、`internal/tradegateway`（经网关调用 Trade 的真实客户端）。

- `Registry`：系统动作到处理器的注册点；`Handler` 的 `Step` 推进一条执行记录一步（用 `NextRunAt` 约定下一次时间），`OnCancel` 在记录已被取消之后善后（解除禁止买入，必须幂等）。
  服务启动时一定注册下架处理器，所以 `ListSubscribableEvents` 返回的 `available_system_actions` 总含“卖出策略持有的下架币”，健康检查详情的 `system_actions` 也列着它；管理台只在读不到事件目录时才提示“无法确认系统动作是否启用”。
- `TradeClient`：事件中心自己的类型描述的 Trade 接口——`BlockInstrument`、`UnblockInstrument`、`ListBlockedInstruments`、`ListInstrumentHolders`、`FlattenInstrument`、`GetOperatorAction`，用（交易所、市场、交易所代码）定位标的。
  Trade 忙（`FlattenInstrumentRsp.busy`，返回码 `CONFLICT`、不带动作）翻译成 `ErrTradeBusy`，稍后再试、不计重试次数；返回码 `INVALID_PARAM` 翻译成 `ErrInvalidRequest`，重试没有用。
  网关客户端用 PB 序列化，枚举直接是 proto 类型。名单的四个接口是全局的，请求不带空间头；`FlattenInstrument` 和 `GetOperatorAction` 按空间，带持有者所在的空间。网关本身不看空间头，只按服务目录里的调用方和方法授权。
  持有者每个执行账户一行，处理器按（空间、组合账户）聚合；响应里没有交易所，取自请求。
- 没有注册处理器的系统动作，工作线程不会领取对应的执行记录，记录停在待处理，注册后立即被处理。
- 下架处理的各轮步骤存在 `t_delist_actions`（唯一键：执行记录、轮次、种类、空间、组合账户），详情接口会返回，管理台抽屉按轮次展示。

### 处理流程

处理器不在内存里留状态：每次 `Step` 都从事件内容（标的、下架时间 T、范围）和已存的步骤推导出现在该做什么，时间只看传进来的 `now`。
所以进程重启、记录卡住后被放回、下架时间被合并更新，都只是用新的输入再推导一次。

| 轮次 | 时间 | 做什么 |
| --- | --- | --- |
| 0 禁止买入 | 一发现就做 | `BlockInstrument`（名单标的“只减不增”）；有非零头持有者时记 `delist_detected` 关注项；Trade 不认识这个标的（`instrument_unknown`）时照常写入名单，直接结束，不查持有者、不发 `delist_detected` |
| 1 平仓 | T−24 小时 | 找持有者，每个（空间、组合账户）一行，各发起一次 `FlattenInstrument`；每 30 秒查一次结果 |
| 2 复查 | T−2 小时 | 再找一次持有者，仍有持有的用新的操作号再平 |
| 3 核对 | T 之后 10 分钟 | 只核对不下单：仍有非零头持有的置为失败并告警；零头列在结果里，告警一次 |

- 每次推进前先用 `ListBlockedInstruments` 确认标的还在名单里。已被手工解除的（误报、交易所改期），停止所有后续步骤，记录置为已取消。
- 轮次之间互不阻挡：第 1 轮还在退避重试时，第 2 轮照常开始。某个组合某一轮用完重试，只让这一行失败，不让整条记录失败；整条记录的成败只在核对时决定，中途的失败靠 `action_failed` 提醒。
- 每一轮到点时，没有持有者也写一行汇总（空间和组合账户为空），页面上能看到这一轮已经做过、查到几个持有者、有没有零头。汇总行最后写：它存在，说明这一轮各组合的行都已存好。
- 到了 T，所有平仓一律停下，没结束的行置为失败，不再下单。“过了下架时间不下单”在每次发起平仓之前都判断，不只在 `Step` 开头判断一次。
  收到事件时已过 T（只可能是手工补录）也照样写入名单，然后直接核对（T+10 分钟之前先等着）。核对晚 10 分钟，是因为交易所到点结算后 Trade 的持仓要等下一次同步才更新。
- 中途改下架时间（事件合并）：下一次推进按新的 T 重新算各轮时间；已经平掉的不会重复平；已存下的平仓说明不变。
- 范围 PAPER_ONLY（演练）：传 `paper_only=true`，处理器自己再过滤一遍返回的持有者，非模拟盘的一律丢掉，不依赖 Trade 守约。测试网组合不处理（Trade 的持有者列表已排除）。

### 平仓的重试

- 操作号由（执行记录、轮次、空间、组合账户）确定地生成，平仓说明（reason）只由合并时不会变的字段生成，建行时存下，之后读回使用。
  所以卡住后被放回的旧线程和新线程即使同时发起，用的也是同一个号、同一个说明，由 Trade 的幂等挡住重复；每一轮的号不同，复查总是换新号。
- 每 30 秒用 `GetOperatorAction` 查一次：`RUNNING` 继续查、不计次数；`COMPLETED` 成功；Trade 查到标的已解除禁止（`unblocked`，响应里或结果 JSON 顶层）而提前结束也算成功，不重试，下一次推进前查名单时记录会被置为已取消。
- `FAILED` 和发起平仓时出错（Trade 不可达）用同一个操作号重试，计一次，按 1、2、4、8、16、30、30…分钟指数退避，最多 10 次，用完这一行失败。
- `PARTIAL`（最近一笔被交易所拒绝、连续 20 笔限价 IOC 一股没成交，或套利底仓的对冲腿下架，原因写在说明里）：同一个操作号再调很快又会得到 `PARTIAL`，重试没有用，所以这一轮这个组合就此结束（状态“只平了一部分”），原因留给用户看，由 T−2 小时的复查换新的操作号再平。
- Trade 忙：30 秒后再试，不计次数。
- 零头（低于交易所最小数量，下不了单）不平，只在汇总行和核对结果里列出。零头不处理是第一版的边界。

### 取消与并发

- `CancelEventExecution` 先原子置为已取消，再调 `OnCancel`。取消并解除禁止的规则按范围分两种：
  - 真实下架（ALL）：尝试过写名单就一律解除，不管同标的的演练有没有结束。Trade 只在解除禁止时才停下清仓，不解除的话已发起的平仓会继续卖；演练下一次推进前查名单发现不在了，会自己停下，代价只是一次模拟盘演练。
  - 演练（PAPER_ONLY）：只解除“自己写进名单的那一条”（禁止买入那一步记下 Trade 返回的 `created`），并且同标的没有未取消的真实下架记录（已结束的也算：结束的真实下架按设计保留名单）。演练没写过名单、名单是别人先写的，或同标的有真实下架，取消和结束都不碰名单。
  - 从没尝试过写名单的记录（还没推进就被取消）不碰名单；Trade 拒绝参数（`INVALID_PARAM`，例如不支持的交易所）说明名单里不会有它，当作没有要解除的。
- 同一标的的“写名单 + 复查记录状态”与 `OnCancel` 的“查别的记录 + 解除”靠进程内的按标的锁串行。锁只包这两段，查持有者、平仓、轮询都不在锁里，取消不会排在 Trade 的慢调用后面。
- 写名单后，处理器先记下“名单已写、是不是自己写的”（这一步状态仍是进行中），再复查记录状态：
  - 已是已取消就补一次解除；补解除失败时记录已不是执行中，`SaveResult` 会丢掉结果，处理器改用 `MarkCleanupPendingIfCanceled` 把“善后未完成”标记重新置 1，用户才看得到“重试善后”；
  - 复查本身失败（读库出错）：记录若其实已取消，同样把标记写回库；记录没取消就什么也不做，下次推进重新写名单（幂等）再复查。
- 服务层做完善后清除“善后未完成”标记时按序号比较（`c_cleanup_seq`，每次置位加一）：善后期间标记被重新置位（Step 写名单后补解除失败），序号变了，标记就不会被吞掉。
- 演练（PAPER_ONLY）记录自己结束（核对成功、核对失败、未知标的直接结束）时同样按上面的规则解除；真实下架结束后名单则保留（标的确实下架了）。
- 标的的写法在入口统一：交易所小写、市场和交易所代码大写、去掉空白。事件校验要求代码是大写，Collector 的手工登记把代码统一成大写再登记，事件中心接收时合并键和 `c_subject_id` 都用统一后的写法，处理器调用 Trade 和比较名单也用它；管理台登记框把代码转成大写。同一个币只落成一个标的，“同标的别的记录”的判断才不会失效。
- `OnCancel` 的 ctx 没有截止时间，处理器调 Trade 自己加 30 秒时限；快速连点两次取消时两路 `OnCancel` 同时执行，靠按标的锁和幂等挡住。
- 每次发起或查询平仓前处理器先确认记录没有被取消；一次 `Step` 的剩余时间不到 45 秒时不再发起新的 Trade 调用，留给下一次推进（单步远小于工作线程给的 5 分钟）。

### 演练

只动模拟盘，不改配置，不向交易所真实下单：

1. 在管理台「事件中心」右上角“手工登记下架”，选标的，先看预览里的持有者，确认只有模拟盘组合持有；
2. 勾选“仅模拟盘”，下架时间设为 3 小时后。系统规则会立刻禁止买入（执行记录详情的“发现后禁止买入”一行成功）；有模拟盘持有者时 Monitor 收到一次 `delist_detected`；
3. 下架前 24 小时已经过了，所以第 1 轮立刻开始平仓；1 小时后（T−2 小时）复查；T+10 分钟核对，记录变为成功（或失败），**演练记录一结束就自动解除禁止**：演练的标的是真实存在、并不会下架的，已结束的记录又不能再取消，不解除的话全局的禁止会一直留着，实盘再也买不了它；只解除演练自己写进名单的那一条，同标的有未取消的真实下架（含已结束的）时不解除。解除失败时记录不结束，1 分钟后重试；
4. 另建一条通知地址规则，指向一个临时的接收地址，确认请求格式和签名，失败时会重试并告警；
5. 想提前结束演练时，在执行记录里点“取消并解除禁止”；演练结束后删掉临时规则。禁止是全局生效的，演练期间实盘组合也不会买这个标的；同标的有真实下架时，演练的取消和结束都不会解除它。

## 6. 接口 `CallbackDispatcherService`

| 方法 | 说明 | 只读 |
| --- | --- | --- |
| `ListSubscribableEvents` | 可订阅事件目录，含界面名和可限定的字段 | 是 |
| `ListEventRules` / `GetEventRule` | 规则列表与详情（含最近一次执行的结果） | 是 |
| `CreateEventRule` / `UpdateEventRule` / `DeleteEventRule` | 增删改；系统规则只能启停 | 否 |
| `TestEventRule` | 用一条示例事件立即发一次（只对通知地址），返回状态码和耗时，不写执行记录 | 否 |
| `ListEventExecutions` / `GetEventExecution` | 执行记录列表（可按规则和状态筛选）与详情（事件内容、每次尝试的状态码耗时响应摘要、下架处理的各轮步骤） | 是 |
| `RetryEventExecution` | 重新执行失败的记录 | 否 |
| `CancelEventExecution` | 取消还没结束的执行：先原子置为已取消，再让处理器善后（下架：解除禁止）；系统动作的记录在同一条 UPDATE 里记下 `c_cleanup_pending`（善后未完成），善后成功后清除；善后失败、请求超时或进程重启时标记仍在：执行记录对外带 `cleanup_pending`，管理台显示“重试善后”，再取消一次只重做善后；关注项算作 `action_failed`；清理旧记录时跳过它 | 否 |
| `AcknowledgeEventExecution` | 确认失败的记录已处理，清除关注项 | 否 |

命令行：`moox-cli event catalog`、`event rules list|get|update|delete|test`、`event executions list|get|retry|cancel|ack`。
**新建规则只能在管理台做**：`CreateEventRule` 的返回里有验证密钥明文，所以没有 `event rules create` 命令，通用的 `gateway call` 也拒绝它，服务目录里它只放行 `console`；
验证密钥只在管理台创建成功的弹窗里显示一次。换密钥也在管理台：删掉规则重新新建。

## 7. 管理台「事件中心」

放在「系统设置」下，两个页签。**事件规则**：列表、新建或编辑（选触发事件 → 按事件给出的字段限定范围 → 填通知地址 → 勾选是否允许内网地址）、
创建后弹窗只显示一次验证密钥并附验签示例、“发一条测试”、系统规则带“系统”标记只能启停。右上角“手工登记下架”：选交易所、市场，填交易所代码和下架时间，
可选“仅模拟盘”；提交前先用 Trade 的 `ListInstrumentHolders` 预览会被平仓的组合，有生产组合时要二次确认；提交调用 Collector 的 `RegisterDelistNotice`（带 crypto 空间头）。
**执行记录**：列表（时间、规则、事件、状态、耗时、失败原因，可筛选）、详情抽屉、重新执行 / 取消 / 确认已处理。

## 8. 数据库

自有 SQLite，表见 `modules/callbackdispatcher/schema/callbackdispatcher.sql`（没有迁移：已有的事件中心库文件是旧 schema，套上新 schema 会在运行时报 `no such column`，要先删掉库文件再启动）：`t_event_rules`、`t_event_receipts`、`t_event_executions`（含 `c_dedupe_key`、`c_next_run_at`、`c_failures`）、
`t_event_attempts`（通知的每次尝试）、`t_delist_actions`。

## 9. 风险与边界

- 来源接口的含义可能和预想不同，所以下架检测用官方样例测试，并保留手工登记兜底。误报时会一发现就禁止买入，平仓要等到 T−24 小时，期间有 `delist_detected` 通知，可以在执行记录里取消（同时解除禁止）。
- 通知地址不可达时，执行记录持续失败并告警；页面上“发一条测试”在保存规则时就能发现问题。
- 第一版不做事件编排、按条件改写事件内容、下架的自动撤销（交易所真撤销下架时靠用户手工取消）、别的系统动作、下架后零头的自动处理（只告警）。
