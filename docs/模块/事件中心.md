# 事件中心

事件中心（组件 ID `callback-dispatcher`，进程 `moox-callback-dispatcher`，源码 `modules/callbackdispatcher`）是一个通用功能：
从 EventBus 接收系统里发生的变更，你在管理台「事件中心」配置要关注的事件，事件发生时向你自己实现的 HTTP 接口发通知，
或者执行 MooX 自带的处理（系统动作）。第一个系统动作是标的下架时禁止买入、下架前平仓。

下架检测作为事件的生产者放在[采集](采集.md)里：Collector 发现“标的即将下架”就发布事件，由事件中心按规则处理。

## 1. 部署

- 独立部署单元，profile 和组件 ID 都是 `callback-dispatcher`；由 `moox.toml` 的 `[deployments]` 决定装在哪台主机，示例里默认在海外机。
  部署主机必须能访问到你填写的通知地址：接口在国内内网时，把它装到能访问的那台机器上。系统动作只经网关调用 Trade，装在哪台都可以。
- 安装与升级都不动别的单元：`moox-cli setup deploy-unit --host <主机> --profile callback-dispatcher`。
- 端口：RPC `11460`（loopback），健康检查 `11461`，指标上报定时器 `11463`，Prometheus `12965`。
- 自有 SQLite 库 `data/moox_callback_dispatcher.db`，库里有通知验证密钥，文件权限 0600。
- 全局服务，不分空间：调用方是 `console` 和 `moox-cli`，管理台路径 `/api/admin/callback-dispatcher/<方法>`，不进 Admin 的空间授权。
- 健康检查只看数据库；EventBus 连不上只在详情里显示。服务可以比 EventBus 先启动，每分钟重试连接，连上后自动开始接收。

## 2. 可订阅的事件

目录只放在本服务里（`internal/catalog`），不改事件注册表。第一版开放：

| 事件 | 界面名 | 可限定的范围 |
| --- | --- | --- |
| `event.storage.dataset.period.completed` | 数据集一期完成 | 空间、数据集 |
| `event.storage.view.data.ready` | View 数据就绪 | 空间、View |
| `event.collector.kline.backfilled` | K 线补写 | 空间、数据集 |
| `event.collector.instrument.delist_scheduled` | 标的即将下架 | 交易所、市场、交易所代码 |

限定范围全部来自信封（空间、subject），匹配是通用的，不解析各事件的 payload：同一字段的多个取值是“或”，不同字段之间是“且”，不限定就是全部。
不开放的事件：`MOOX_TRADE` 的策略目标（工作队列，再挂消费者会和 Trade 抢消息）、`dataset.rows.upserted` 和 `dataset.sync_point`（量大且偏内部）、监控事件。
目录里的每个事件必须在注册表里声明过、所属的流不是工作队列，测试会核对，也核对它和 `events.CallbackDispatcherEvents`（EventBus 凭据按它生成权限）是同一批。
以后开放新事件，在目录里加一项并同步 `CallbackDispatcherEvents`。

## 3. 事件规则

一条规则：名称、触发事件、限定范围、动作、启用开关。动作有两种：

- **通知地址**：URL（只允许 http、https，不能内嵌账号密码）。创建时服务生成验证密钥 `whsec_…`，只在创建的返回里完整出现一次，
  之后只显示末 4 位。要换密钥就删掉规则重新新建（只能在管理台）。规则可以勾选“允许内网地址”。
- **系统动作**：第一版只有“卖出策略持有的下架币”，只能用在“标的即将下架”上。它是服务自带的一条系统规则，首次启动时自动创建，
  默认启用；用户可以停用，但不能修改、不能删除，也不能新建系统动作规则（免得重复平仓）。

更新规则只改请求里带了的字段（`--enabled=false` 不会清掉名称和地址）；系统规则只接受启停。删除规则会把它还没结束的执行记录置为已取消。

## 4. 接收与执行

**接收**：每个可订阅事件一个固定的 durable（名字见[事件总线](事件总线.md)），`MaxDeliver` 不限次数：写库失败不能丢事件。
“标的即将下架”用 DeliverAll（流保留 72 小时，第一次上线时能收到 Collector 已经发出的下架，回放无害，同一事件会被去重），其余事件用 DeliverNew。

收到事件后：先用 `events.DecodeRaw` 解码并校验，再用 protojson 把 payload 转成紧凑 JSON（蛇形字段名，int64 按 protojson 约定写成字符串）；
匹配所有启用的规则；在**一个事务里**先往 `t_event_receipts`（主键：事件 ID、规则 ID）插一行——插不进去说明处理过，跳过——再写执行记录。
写库成功才确认消息。匹配不上任何规则的直接确认，不留记录。解码失败的终止，并计入 `moox_callbackdispatcher_event_errors_total`。

- 通知地址：写一条状态为待处理的执行记录。
- 系统动作：按合并键（规则 + 交易所:市场:代码）合并或新建。同一标的已有未结束的记录时，只在下架时间或范围变了才更新它的事件内容并让它立即到期，不新建；
  已结束的记录不再参与合并，同一标的之后的新事件会新建一条。合并键上有一个只覆盖未结束记录的部分唯一索引。

**执行**由独立的工作线程处理，和 JetStream 消费解耦，一条通知失败不会让同批后面的事件一起退避。执行记录的 `c_next_run_at` 是下一次该处理它的时间，
跨天的系统动作靠它推进。进程重启时把停在“执行中”的记录放回待处理（投递是“至少一次”）。处理期间如果有新事件合并进同一条记录，
处理结果不会覆盖新的安排，记录立即重新处理。

### 通知请求

```text
POST <通知地址>
Content-Type: application/json
X-MooX-Event-Id: <事件 ID>
X-MooX-Event: <事件名>
X-MooX-Timestamp: <发送时的毫秒时间戳>
X-MooX-Signature: sha256=<HMAC-SHA256(验证密钥, 时间戳 + "." + 请求体) 的十六进制>

{"event_id":"...","event":"event.collector.instrument.delist_scheduled","version":1,
 "space_id":"mooxsys","subject":"binance:SPOT:FOOUSDT","occurred_at":"2026-11-04T08:00:00Z",
 "rule_id":"...","data":{...payload 的 JSON...}}
```

返回 2xx 算成功。投递语义是“至少一次”，同一事件可能收到多次，请用 `X-MooX-Event-Id` 去重；不保证顺序。验签（Go）：

```go
mac := hmac.New(sha256.New, []byte(secret))
mac.Write([]byte(timestamp + "." + string(body)))
ok := hmac.Equal([]byte("sha256="+hex.EncodeToString(mac.Sum(nil))), []byte(signatureHeader))
```

也应检查时间戳与当前时间相差不大，防止重放。

### 出站防护

通知地址由用户填写，出站请求要防住误配置和 SSRF（`packages/netguard`，出口代理共用同一份）：

- 只允许 http、https；不跟随重定向（3xx 当作配置错误，请直接填最终地址）；不使用环境变量里的代理；每个请求新建连接，不复用。
- 连接超时 3 秒，总超时 10 秒；响应体最多读 64 KB，只记录前 1 KB。
- 解析域名后逐个检查 IP，通过才拨号，并且直接用检查过的 IP 拨号，防止 DNS 重绑定；IPv4、IPv6 都检查。
  回环、链路本地（含云元数据 169.254.169.254）、组播、保留与文档地址一律拒绝；内网段（10/8、172.16/12、192.168/16、100.64/10、IPv6 ULA）默认拒绝，规则勾选“允许内网地址”才放行。
  被防护拒绝是配置错误，直接失败不重试。
- 不经过出口代理（它只放行交易所），直接出站。

### 重试与告警

- 失败后按 1 分钟、5 分钟、30 分钟、2 小时、6 小时、12 小时重试；重试用完，或从第一次失败起下一次重试会超过 24 小时，执行记录置为失败。
- 返回 4xx（408、429 除外）、3xx、被防护拒绝的不重试，直接失败：多半是配置错了。网络错误、超时、5xx、408、429 重试。
- 重新执行（`RetryEventExecution`）把失败记录放回待处理并清零失败计数，重试间隔从 1 分钟重新开始；尝试编号继续累计。
- 执行记录保留 30 天（可配）。

告警走 Monitor 的“关注项”：服务每 30 秒按库里的状态重新计算并上报 `moox_callbackdispatcher_attention_active{kind,detail}`，重启不丢。

| 种类 | 触发 | 持续到 |
| --- | --- | --- |
| `execution_failed` | 通知类执行记录失败 | 用户重新执行或确认 |
| `delist_detected` | 收到新的“标的即将下架”并且当前有策略持有 | 约 3 分钟：触发一次、恢复一次，相当于一条通知 |
| `action_failed` | 系统动作某一步用完重试、核对失败或有零头 | 用户处理 |

Monitor 把它们汇总成 `event_center_attention:*` 业务检查（见[监控](监控.md)）。

## 5. 系统动作：卖出策略持有的下架币

**本版只落了框架，处理器（任务 C6）依赖交易计划 T27 的 Trade 接口，尚未实现。** 框架在 `internal/action`：

- `Registry`：系统动作到处理器的注册点；`Handler` 的 `Step` 推进一条执行记录一步（用 `NextRunAt` 约定下一次时间），`OnCancel` 在记录已被取消之后善后（解除禁止买入，必须幂等；失败时用户再取消一次重做）。
  处理器写入禁止名单（`BlockInstrument`）之后必须复查记录状态，已经是已取消就补一次解除；同一标的还有别的未结束的真实执行时不能解除（Trade 的名单是全局的，演练的取消不能解除真实下架的禁止）。
- `TradeClient`：事件中心自己的类型描述的 Trade 接口——`BlockInstrument`、`UnblockInstrument`、`ListBlockedInstruments`、`ListInstrumentHolders`、`FlattenInstrument`、`GetOperatorAction`，用（交易所、市场、交易所代码）定位标的；Trade 忙时返回 `ErrTradeBusy`（稍后再试，不计重试次数）。
  C6 写适配器经网关（配置里的 `gateway_client`，调用方 `callback-dispatcher`）调用 Trade。
- 没有注册处理器的系统动作，工作线程不会领取对应的执行记录（按已注册的动作过滤），记录停在待处理，注册后立即被处理，不会丢也不会空转。
- 下架处理的各轮步骤存在 `t_delist_actions`（唯一键：执行记录、轮次、种类、空间、组合账户），详情接口会返回。

设计的处理流程（以下架时间 T 为基准）：一发现就调 `BlockInstrument` 禁止买入（名单标的“只减不增”，可以减仓）；T−24 小时对每个持有的（空间、组合账户）调 `FlattenInstrument` 平仓，
每 30 秒查结果，失败用同一个操作号重试最多 10 次；T−2 小时复查，仍有持有的再平一轮；T 之后只核对不下单；每次推进前用 `ListBlockedInstruments` 确认标的还在名单里，已被手工解除的停止后续步骤；
收到事件时已过 T（只可能是手工补录）也照样写入名单，然后直接核对。测试网组合不处理。

## 6. 接口 `CallbackDispatcherService`

| 方法 | 说明 | 只读 |
| --- | --- | --- |
| `ListSubscribableEvents` | 可订阅事件目录，含界面名和可限定的字段 | 是 |
| `ListEventRules` / `GetEventRule` | 规则列表与详情（含最近一次执行的结果） | 是 |
| `CreateEventRule` / `UpdateEventRule` / `DeleteEventRule` | 增删改；系统规则只能启停 | 否 |
| `TestEventRule` | 用一条示例事件立即发一次（只对通知地址），返回状态码和耗时，不写执行记录 | 否 |
| `ListEventExecutions` / `GetEventExecution` | 执行记录列表（可按规则和状态筛选）与详情（事件内容、每次尝试的状态码耗时响应摘要、下架处理的各轮步骤） | 是 |
| `RetryEventExecution` | 重新执行失败的记录 | 否 |
| `CancelEventExecution` | 取消还没结束的执行：先原子置为已取消，再让处理器善后（下架：解除禁止）；善后失败时记录仍是已取消，再点一次只重做善后 | 否 |
| `AcknowledgeEventExecution` | 确认失败的记录已处理，清除关注项 | 否 |

命令行：`moox-cli event catalog`、`event rules list|get|update|delete|test`、`event executions list|get|retry|cancel|ack`。
**新建规则只能在管理台做**：`CreateEventRule` 的返回里有验证密钥明文，所以没有 `event rules create` 命令，通用的 `gateway call` 也拒绝它，服务目录里它只放行 `console`；
验证密钥只在管理台创建成功的弹窗里显示一次。换密钥也在管理台：删掉规则重新新建。

## 7. 管理台「事件中心」

放在「系统设置」下，两个页签。**事件规则**：列表、新建或编辑（选触发事件 → 按事件给出的字段限定范围 → 填通知地址 → 勾选是否允许内网地址）、
创建后弹窗只显示一次验证密钥并附验签示例、“发一条测试”、系统规则带“系统”标记只能启停。右上角“手工登记下架”：选交易所、市场，填交易所代码和下架时间，
可选“仅模拟盘”；提交前先用 Trade 的 `ListInstrumentHolders` 预览会被平仓的组合，有生产组合时要二次确认；提交调用 Collector 的 `RegisterDelistNotice`（带 crypto 空间头）。
**执行记录**：列表（时间、规则、事件、状态、耗时、失败原因，可筛选）、详情抽屉、重新执行 / 取消 / 确认已处理。

## 8. 数据库

自有 SQLite，表见 `modules/callbackdispatcher/schema/callbackdispatcher.sql`：`t_event_rules`、`t_event_receipts`、`t_event_executions`（含 `c_dedupe_key`、`c_next_run_at`、`c_failures`）、
`t_event_attempts`（通知的每次尝试）、`t_delist_actions`。

## 9. 风险与边界

- 来源接口的含义可能和预想不同，所以下架检测用官方样例测试，并保留手工登记兜底。误报时会一发现就禁止买入，平仓要等到 T−24 小时，期间有 `delist_detected` 通知，可以在执行记录里取消（同时解除禁止）。
- 通知地址不可达时，执行记录持续失败并告警；页面上“发一条测试”在保存规则时就能发现问题。
- 第一版不做事件编排、按条件改写事件内容、下架的自动撤销（交易所真撤销下架时靠用户手工取消）、别的系统动作、下架后零头的自动处理（只告警）。
