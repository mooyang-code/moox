# 主机代理（HostAgent）

`moox-host-agent` 是每台 Linux 主机上的用户级服务，采集本机资源，随每分钟拉取主机策略的那次 RPC 报给 Monitor，
由 Monitor 统一入库和告警。它不保存样本，也不连 EventBus。

代码位置：`modules/hostagent`；快照协议在 `packages/hostmetricpb`。

## 1. 进程与端口

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| `HostAgentMgr` | loopback tRPC `11426` | `GetStatus`、`RunOnce`（服务目录超时 30 秒，响应结果与传输错误分离，不因同时返回非 nil error 丢弃响应体） |
| 健康检查 | `11425` | 只听 127.0.0.1、不验签，供部署的就绪检查与诊断（`moox-cli doctor` 经 SSH）读取；Monitor 不探测，按主机快照判断 host-agent |
| `sample.timer` | 每分钟（启动时立即执行） | 采集一次主机快照，再经本机网关调 Monitor 的 `GetHostPolicy`（带上快照、拉回主机策略），单次超时 30 秒 |

## 2. 采集

- 读取 CPU、内存、文件系统、磁盘 I/O 和网络计数器，算出使用率和速率。
- 读取 `/proc/<pid>/stat`，随快照上报占用最高的进程（`top_processes`）：CPU 前 5 与内存前 5 合并去重，最多 10 个。
  - CPU 是两次采样之间的平均占用，按单核百分比表示，与 `top` 一致（340% 即 3.4 个核）。算法是“进程 CPU 时间的增量 ÷ 整机 CPU 时间的增量 × 核数”；第一次采样、进程在上一次采样时还不存在、PID 被新进程复用时没有 CPU 值。
  - 进程名取可执行文件的文件名（`/proc/<pid>/exe` 指向的路径）；别的用户的进程和内核线程读不到，用内核里的进程名 `comm`（用户进程最多 15 个字符）。`comm` 可以被进程改写（例如 `sshd: user@pts/0`），只取空白之前的第一段；内核线程的名字本身带斜杠（`ksoftirqd/0`），原样保留。两种来源最后都把控制字符换成问号。
    不读 `/proc/<pid>/cmdline`：进程可以改写自己的命令行（sshd、postgres、Node 等），里面可能带参数甚至密钥；而且读它要拿目标进程的内存映射锁，目标进程卡住时会把采集一起卡住。
  - 核数取 `/proc/stat` 里 `cpuN` 的行数。内存是常驻内存（RSS），包含文件映射和共享内存，和整机“已用内存”（按 `MemAvailable` 算）不是一个口径，各进程相加会超过整机已用。
  - 短命的子进程（定时任务、崩溃后反复重启的进程）在两次采样之间就结束了，排行里看不到。`/proc` 挂载了 `hidepid` 时只能看到 HostAgent 同一用户的进程。
  - 这一项读不到不影响其他指标，采集状态里记为 `process` 失败。只有 Monitor 用它（告警正文、告警事件、主机监控详情页），不写入 Storage，也没有历史。
- 每次采集的快照（带 UUIDv7 上报 ID 与采集时间）随同一分钟的 `GetHostPolicy` 报给 Monitor，尽力发送，失败不重试；
  采集失败的那一分钟照常拉策略，只是不带快照。Monitor 先收快照再判断自己的检查评估是否停滞，评估停了快照也照常入库；
  快照不合法或写库失败只在 Monitor 记日志，策略照常返回。
- 定时和手动 `RunOnce` 共用同一把非重入锁，同一时刻只有一次采集。采集由 tRPC 定时器驱动，
  首次或后续采集失败会更新错误状态并等待下一轮；首次成功采集前 `/readyz` 不就绪，上报失败不影响采集就绪。

## 3. 身份

HostAgent 只有一个身份：`config/app.yaml` 的 `host_id`，即 Admin 登记的主机 ID（`t_hosts.c_host_id`），由部署按主机渲染，必填；
不在本机另存身份文件，也没有脱离部署的独立运行模式（`host_id`、`gateway_client`、`host_policy_path` 缺一项就拒绝启动）。
主机快照的 `subject_id` 就是 `host_id`，Monitor 的主机登记、快照历史与主机类检查都以它为键，每台登记主机一行；重装 HostAgent 沿用同一行，不留旧记录。
`host_name` 只用于展示，操作系统 hostname 不参与关联。`host_id` 不在登记里的上报不进入主机监控列表。

## 4. 主机策略同步

HostAgent 还负责把告警渠道带到本机：部署时渲染 `gateway_client`（调用方 `host-agent`）与
`host_policy_path`（`<部署根>/data/host-agent/host-policy.json`），由采样定时器在启动时拉一次、之后每分钟经本机网关调用 Monitor 的 `GetHostPolicy`
（服务目录只允许调用方 `host-agent`；它带着快照写入 Monitor，按上报 ID 去重，标为可重发），拿到全部通知渠道。内容摘要变化时版本号加一并原子写入（0600），
内容不变不重写；拉取失败或返回非法渠道时保留旧文件。指标：`moox_hostagent_host_policy_sync_total{result}`、
`moox_hostagent_host_policy_last_success_timestamp_seconds`、`moox_hostagent_host_policy_version`。
Admin 的证书巡检只读这个文件，控制面不可用时也能直接推送告警。
这两项与 `host_id` 一样必填。打不开网关客户端（例如首装时本机网关还没监听、取不到目录）时进程直接退出，由 systemd 拉起重试。

拉取的结果还是两条直推的依据（`internal/policysync/watch.go`），只在没有部署 Monitor 的主机上推送（按网关目录判断本机是否部署了 `MonitorMgr`）：

- **控制机或 Monitor 不可达**：连续 3 次（约 3 分钟）拉取失败推送一条，之后第一次成功推送恢复。
- **Monitor 反复重启**：`GetHostPolicy` 的响应带 Monitor 的进程启动时间，10 分钟内变了 3 次推送一条，窗口里的变化少于 3 次后推送恢复。Monitor 反复崩溃时每次拉起后都能成功应答几次，光看连续失败发现不了。10 分钟内连续部署控制机三次也会触发这一条，属于误报。

推送渠道取本机主机策略缓存里的渠道（`packages/notification`），至少一个渠道送达就算送达，不经过 Monitor 与 EventBus。每台非控制机各推一条，三台主机就是三条。

Monitor 3 分钟收不到某台主机的快照时，会结合该主机网关的组件上报区分“主机失联”（网关也停报）与“host-agent 停止上报”（网关仍在上报），见[监控](监控.md)第 9 节。

## 5. 部署

Host Agent 是每台主机都有的主机级组件，随 `moox-cli setup deploy --file ./moox.toml --host <主机ID>` 与 HostGateway
一起安装，是 systemd 用户服务 `moox-host-agent`，没有 EventBus 凭据。
`/readyz` 只看采集循环（至少成功采集过一次，且最近一次采集没有出错），**不依赖 Monitor**：控制机或 Monitor 不可达时 HostAgent 仍然就绪，
只是报不出快照；上报错误放在状态接口（`last_report_at`、`last_error`；状态接口里的时刻都是 Unix 毫秒，0 表示还没有）里，报不出快照由 Monitor 的“host-agent 停止上报”告警，或由非控制机直推“控制机或 Monitor 不可达”。
这样远端服务不可用时部署的就绪等待不会卡在它身上。验证时使用 `moox-cli doctor bootstrap --node <主机ID>`；
健康端口只听 127.0.0.1、不验签，远程 `curl` 连不上，要在目标机上请求（doctor 经 SSH 代为请求）。
