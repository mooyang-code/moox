# Strategy 模块架构设计

## 文档定位

本文描述当前 Strategy 模块的架构和边界。详细的 DSL 字段、求值顺序、输入依赖、
生命周期和验收规则以
[MooX 策略执行框架设计](策略执行框架设计.md)为准；实施任务以
[2026-08-29 实施计划](superpowers/plans/2026-08-29-moox-coin-selection-strategy.md)为准。

本文面向个人量化系统，优先选择简单、可读、易维护的方案：固定 Go 流程、Expr 受限表达式、
SQLite 和 JetStream。它不引入通用工作流、分布式锁、Saga 或全局 exactly-once。

> **实现状态（2026-09-06）：** Strategy/Trade 的声明式策略、三表存储、定时/事件触发、目标权重
> 事件和会话校验已在 `feature/mooyang` 分支实现，并通过模块测试、本地 Factor/Storage/Strategy
> E2E、隔离 NATS 的 Strategy→Trade 目标事件 E2E 以及会话代际单元测试。当前联合 E2E 使用内存
> 存储和测试消费者，尚未覆盖真实 Strategy/Trade 进程连接真实执行账户。真实 Factor/Storage
> 外部部署与正式交易环境验证仍需单独授权和运行记录；本文不能作为生产已上线证明。

## 1. 模块边界

```text
Collector / Factor -> 数据、因子和 View ready 事件
Storage            -> 可读行情、因子结果和标的目录
Strategy           -> pool/filter/score/select/signals/weight
                     -> PositionTargets（完整目标权重）
                     -> StrategyResult（快照、后态、投递状态）
                     -> 异步目标权重事件
Trade              -> 权益、数量换算、账户选择、风控、订单和失败恢复
Monitor / UI       -> 分开展示计算、投递、接收、成交和持仓事实
```

Strategy 只输出一个实例对应资金单元的完整 `target_weight` 快照。它不读取账户权益、余额、
实际持仓、订单或成交，不选择执行账户，不访问交易所，也不处理最小下单量、价格精度、合约
乘数、拆单、撤单和补单。Trade 收到权重后才换算绝对数量并执行。

Trade 可以异步发布接受、拒绝、部分成交和执行失败通知，供监控和界面展示；这些通知不作为
Strategy 的决策输入，不推进 `RuleState`，也不触发策略重算。策略的发布重试只负责把同一冻结
消息送到 broker，不构成交易反馈闭环。

定时和事件触发都是唤醒方式：可以只配一种，也可以同时配置，语义为 OR。事件不能携带买卖
指令绕过 DSL；它只提供触发时点和已声明的输入上下文。

## 2. 核心对象和命名

| 对象 | 含义 |
| --- | --- |
| `StrategyDef` | 用户编写的一份 DSL 定义，持久化 `strategy_id`、`strategy_name` 和 `dsl_yaml` |
| `StrategyInstance` | 定义、Space、输入绑定、资金单元和启用状态的运行绑定 |
| `EvaluationInput` | 本期冻结的标的池、行情、因子、时间边界和输入出处 |
| `RuleState` | 每条规则下一期所需的理论状态，不是 Trade 真实持仓 |
| `StrategyResult` | 一次成功求值的历史快照、目标、规则后态和投递状态 |
| `PositionTargets` | 一个实例在一个周期发布的完整目标权重集合 |
| `InstrumentTarget` | `instrument_id` 与有符号 `target_weight` |

`strategy_name` 由 DSL 根字段 `name` 在保存事务中派生，是列表、搜索和排序字段；它不是第二
个编辑来源。DSL 只保留 `dsl_yaml`，不保存 `api_version`、definition hash、revision 或
持久化编译制品。

持久化对象不再叫 `StrategyRunner`，实例主键使用 `instance_id`。代码中实际执行计算的组件
仍可以叫 Runner，但不把实现类名和领域对象混用。一次显式启用产生 `session_id`，替代
`run_id`、`activation_id` 和 `run_generation`；正常进程重启保持会话，停用后重新启用创建新会话。
`command_sequence`、`last_result_id` 不再是实例字段，最近结果按 `(instance_id, session_id,
bar_end_time)` 查询。

策略时间统一使用 `bar_end_time`，表示已闭合 bar 的结束边界。表达式中：

- `bars[0]` 是本次决策使用的已闭合 bar；
- `bars[-1]` 是同一日历下紧邻的上一根有效 bar；
- 第一版只接受常量索引 `0` 和 `-1`，拒绝 `bars[1]`、`bars[-2]` 和动态索引。

`bars[-1]` 不是普通数组“最后一个元素”的语义；读取缺少精确上一周期时整次求值跳过，不能
退化成任意最近记录、上次触发或默认值。

## 3. DSL 结构

规则名由用户自定义，`rules`、`pool`、`filter_before`、`score`、`select`、`signals`、
`weight`、`weight_each`、`side` 和 `filter_after` 才是框架字段。示例：

```yaml
name: strategy_demo

triggers:
  schedule: {cron: "5 * * * *", timezone: UTC}
  event: {name: ViewFactorPeriodReady}

data: {bar: 1h, calendar: crypto_24x7}

rules:
  momentum_selection:
    pool: {udf: spot_symbols, params: {quote_asset: USDT}}
    filter_before: "turnover_20 > 1000000"
    score: "0.6 * pct_rank(return_20) + 0.4 * pct_rank(turnover_20)"
    select: {top: 10}
    weight: 0.60
    filter_after: "return_20 > 0"

  ma_signal:
    pool: [BTC-USDT-SPOT, ETH-USDT-SPOT]
    signals:
      entry: "bars[-1].ma20 <= bars[-1].close && bars[0].ma20 > bars[0].close"
      exit: "bars[-1].ma20 >= bars[-1].close && bars[0].ma20 < bars[0].close"
    weight_each: 0.10
```

固定池、UDF 池和前筛共同定义“本期要计算的集合”；前筛只做评分前初步筛选。`score` 是
数值表达式，不是固定的 `momentum` 算法；`pct_rank` 和 `zscore` 是两个受限的截面标准化
函数。`select.top` 取高分前 N，`select.tail` 取高分排序后的末 N，二者互斥。

不再使用 `components`、`universe`、`pre_filter`、`post_filter`、`bottom`、`kind`、
`method: fixed`、`position` 或 `target.valid_for_bars`。不需要筛选、评分或信号时，直接列池
和 `weight`/`weight_each`；不需要伪造一个“fixed”类型。

`signals` 用于时序规则：旧理论持仓先检查 `exit`，再从候选中加入 `entry`，退出优先；
它不等待 Trade 成交，也不要求把所有分值设成相同。截面规则和时序规则走同一条固定流水线，
区别只在是否维护 `RuleState`。

## 4. 固定处理流程

```text
定时 / 事件
  -> 确定 instance_id + session_id + bar_end_time
  -> 检查本周期是否已有成功结果、恢复当前会话最近 RuleState
  -> 解析 pool，得到稳定、无重复的 instrument_id 集合
  -> 加载本期所需行情、因子和精确历史，冻结输入出处
  -> filter_before
  -> 批量标准化、计算 score
  -> select（可选）
  -> signals / holding（可选）
  -> 分配基础份额，再乘 weight 或使用 weight_each
  -> filter_after（只剔除，不补位、不重新分配）
  -> 合成完整 PositionTargets 和下一期 RuleState
  -> 事务保存 StrategyResult 与初始投递状态
  -> 后台异步发布冻结目标消息给 Trade
```

各规则独立计算，任一必要规则失败，整次不提交部分 FULL。明确成功的空集合才表示完整零
目标；缺数、因子未 ready 或表达式错误不能当成空持仓。每个 `(instance_id, session_id,
bar_end_time)` 最多成功一次，同权重的新周期也会生成新目标。

## 5. 求值引擎和输入

启用实例时解析 DSL、检查字段类型和输入绑定，并在内存编译 Expr；重启后重新编译，不落盘
编译产物。Expr 只访问已声明的行情、Factor 输出、标的元信息和时间上下文，开放纯函数白名单，
拒绝网络、文件、数据库、`now`、随机数和任意动态 UDF。

Pool UDF 是按名称注册的可信函数，输入为 Storage 提供的标的目录快照、时点和参数，输出
规范 `instrument_id` 集合。启用和运行时都校验名称、参数、成员、重复项和大小写规范，不能
把非法返回静默变成空池。

Factor 绑定明确 source View、result View、输出列、频率和 subjects。绑定频率与 `data.bar`
一致，省略时继承该周期；Strategy 读取 Factor 已准备结果，不在模块内重算 MA20 等指标。

同一规则、本期输入和前态应得到确定结果。诊断日志可以记录池规模、原始/标准化评分、排序、
后筛原因和批次贡献，但 Result 只保存恢复、解释和投递所需的最小快照。

## 6. 持久化和异步投递

Strategy 只保留三张业务表；字段详表见执行框架设计第 9 节：

| 表 | 字段摘要 |
| --- | --- |
| `t_strategies` | `strategy_id`、`strategy_name`、`dsl_yaml`、`created_at`、`updated_at` |
| `t_strategy_instances` | `instance_id`、`strategy_id`、`space_id`、`input_bindings_json`、可空 `logical_account_id`、`enabled`、可空 `session_id`、创建/更新时间 |
| `t_strategy_results` | `result_id`、`instance_id`、`session_id`、`bar_end_time`、`valid_until`、`snapshot_json`、`targets_json`、`rule_states_json`、可空 `event_data`、`publish_status`、`created_at` |

不创建 `t_strategy_runners`、`t_strategy_outbox` 或独立规则状态表。`event_data` 与
`publish_status` 直接并入 Result，状态只有 `none`、`pending`、`sent`、`cancelled`：

- `none`：观察模式，无需投递；
- `pending`：等待 broker 确认或重试；
- `sent`：broker 已确认，不表示 Trade 已接受或成交；
- `cancelled`：停止重试，不保证此前从未送达。

一次成功求值在一个 SQLite 事务中写入历史快照、目标、后态和冻结消息。后台发布器只更新
`pending -> sent/cancelled`；新周期成功后取消同一实例、同一会话更早的待发快照。确认丢失
可以使用相同 `result_id` 重投，Trade 以实例、会话、周期和目标内容幂等处理。

## 7. 实例生命周期和恢复

实例未绑定 `logical_account_id` 时为观察模式，仍计算和保存 Result，但不发布 Trade 消息。
一个资金单元同一时刻只能有一个启用的实例发布完整目标。

启用流程：解析 DSL、检查输入和资金单元、生成新 `session_id`，先完成 Trade 授权再开始求值。
停用先持久化 `enabled=false`，停止新的求值和发布，确认 Trade 清理后再清空 session。进程
重启时恢复 `enabled=true + session_id` 的会话；`false + 非空 session_id` 视为未完成控制操作，
只清理旧授权，不自动续启。

旧会话的结果、迟到消息和正在计算的任务必须通过 `session_id` 校验；新会话建立自己的周期
基线，不继承旧会话的高水位。停用不隐含撤单或清仓，实际交易操作由 Trade 管理。

## 8. Strategy 到 Trade 的合同

执行型实例异步发布完整目标权重事件，核心字段为：

```text
target_id = result_id
instance_id
strategy_id
logical_account_id
session_id
bar_end_time
effective_at
valid_until
targets[] { instrument_id, target_weight }
```

Trade 在去重快捷路径之前和接收事务内都校验当前授权身份与有效期，再按同一会话的
`bar_end_time` 接受更晚目标；旧会话、旧周期、过期目标和同周期内容冲突会被拒绝。Trade
再独立读取账户权益、换算数量、选择执行账户、应用精度/最小量和风控。

协议中仍可能保留 `runner_id`、`command_sequence` 等兼容字段，以便旧消息解码和迁移；
新 Strategy 只写入 `instance_id`、`session_id`、`bar_end_time`、`valid_until` 与 `target_weight`。
新校验器不接受依赖旧字段的目标，不能因为协议字段暂时存在就恢复旧语义。

Strategy 只负责“算出目标并可靠发送”；Trade 的执行失败通知可以被 Monitor 展示，但不会
反向修改规则后态，也不会让 Strategy 自行补单或改变目标。

## 9. 历史 Python 契约

旧版 Python `run-once + quantity` 只保留在
[Strategy Python 策略接入手册](策略模块Python策略接入手册.md)中，作为迁移和历史数据解释参考。
它不是新策略接入方式；新增策略必须使用本文引用的声明式 DSL 和 `target_weight` 输出。
不得根据旧手册新增 `api_version`、`entrypoint`、`quantity`、`hold/rebalance` 或 Python
源码执行路径。若需兼容旧策略，必须另行制定迁移和下线计划。
