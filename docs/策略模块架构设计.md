# Strategy 模块架构设计

本文保留 Strategy V1 Python `run-once + quantity` 契约，作为历史迁移参考，不再作为
新实现的规范。当前目标架构、命名和执行边界以
[MooX 选币策略执行框架设计](选币策略执行框架设计.md) 为准；实施步骤见
[MooX 选币策略执行框架实施计划](superpowers/plans/2026-08-29-moox-coin-selection-strategy.md)。

> **迁移提示：** 新 Strategy 使用 `moox.strategy/v2` 声明式 `Manifest`，按周期消费
> `ViewFactorPeriodReady`，输出 FULL `target_weight`。本页中的 Python、`quantity`、
> `RunOnce` 和历史窗口接口不得用于新增策略。

## 模块边界

Strategy 把不可变 Python 策略应用到一个完整历史窗口，保存已接受结果，并向 Trade
发布组合账户的完整目标。Strategy 不读取交易凭据、不选择执行账户、不提交订单，也不
复制 Trade 的订单、成交和持仓事实。

```text
Storage/View 准备完整历史窗口
        -> StrategyEngine 调用 Python
        -> 严格校验输出
        -> 原子提交 StrategyResult + Runner + outbox
        -> LogicalAccountTargetRequested
        -> Trade 动态收敛 LogicalAccount
```

## 核心对象

| 对象 | 含义 |
| --- | --- |
| `Strategy` | 不可变源码、清单和 source hash |
| `StrategyRunner` | Strategy 的一个独立参数、数据和调度实例 |
| `StrategyResult` | 一次校验成功并原子接受的输出 |
| `InstrumentTarget` | 规范化标的及其绝对目标持仓量 `quantity` |
| `LogicalAccount` | Trade 管理的一个组合账户 |

一个 Strategy 可创建多个 Runner。一个执行型 Runner 最多控制一个 LogicalAccount；
观察型 Runner 不关联账户。一个 LogicalAccount 最多有一个 owner Runner，但可以包含
多个同质执行账户。

Strategy 是不可变制品。源码、`manifest_yaml` 或输入契约变化时创建新的
`strategy_id`。切换 Runner 的 Strategy 必须先停用 Runner；切换后保留当前理论目标和
command sequence，清空只与旧制品有关的最近结果和健康字段。

## Python 契约

清单：

```yaml
api_version: moox.strategy/v1
entrypoint: strategy.py:run
input:
  history_bars: 200
```

入口：

```python
def run(context, data, params):
    return {
        "action": "rebalance",
        "targets": [{
            "instrument_id": "BTC-USDT-SPOT",
            "quantity": "0.1",
        }],
        "debug_info": {},
    }
```

Python 是完整历史窗口上的无状态函数。入口恰好三个参数；没有跨轮内部状态或状态迁移
协议。冷却期、连续信号和滚动指标都从清单声明、严格按时间排序且以
`trigger_bar_time` 结束的窗口重新计算。

输出 action 只有：

- `hold`：保留 `current_targets_json`，不增加 sequence，不发事件。
- `rebalance`：用 targets 完整替换理论目标。空列表合法，表示全部归零。

`InstrumentTarget.quantity` 是带符号的绝对目标数量，不是变化量或权重。遗漏旧标的
表示目标归零。完整协议见
[Strategy Python 策略接入手册](策略模块Python策略接入手册.md)。

## 持久化

Strategy 只有四张业务表：

```text
t_strategies
  strategy_id + name
  manifest_yaml + source_code + source_hash
  created_at

t_strategy_runners
  runner_id + strategy_id + space_id
  view_id + frequency + params_json
  logical_account_id + status
  current_targets_json + command_sequence
  last_result_id + last_success_at + last_error
  created_at + updated_at

t_strategy_results
  result_id + runner_id + strategy_id
  trigger_bar_time + namespace + input_hash
  action + output_json + optional command_sequence
  created_at

t_strategy_outbox
  message_id + event_data + created_at
```

`current_targets_json` 是 Runner 最新已接受的理论 FULL 目标，用于 hold、展示和下游
事件，不会传回 Python，也不是账户实际持仓。

StrategyResult 的唯一逻辑触发键是：

```text
(runner_id, strategy_id, namespace, trigger_bar_time)
```

`input_hash` 由 Strategy 身份、完整历史输入、参数、namespace 和触发上下文计算。相同
触发键重试时，相同 hash 返回已有结果，不同 hash 报冲突。失败运行不写
StrategyResult，只更新 Runner `last_error`。

## 原子提交与 Outbox

一次成功提交在同一个 SQLite 事务中：

1. 插入 StrategyResult。
2. 更新 Runner 最近结果与健康字段。
3. 对 `rebalance` 替换 `current_targets_json`。
4. 执行型 Runner 增加 `command_sequence` 并写一条 outbox。

Outbox 独立成表是为了避免“结果已提交但事件丢失”或“事件已发送但结果回滚”。发布器
成功发送 `LogicalAccountTargetRequested` 后删除对应记录；重复投递由 target ID 和
sequence 在 Trade 侧幂等吸收。这是小型事务 outbox，不是通用消息工作流。

事件内容：

```text
target_id = result_id
runner_id
logical_account_id
command_sequence
targets[] InstrumentTarget(instrument_id, quantity)
```

事件不携带执行账户、原生 symbol、资金权重或过期时间。Trade 持久化当前
LogicalAccountTarget，并动态选择执行账户。

## 归属

StrategyRunner 保存 `logical_account_id`，LogicalAccount 保存 `owner_runner_id`。
启用前必须双向一致；Trade 在每条目标命令上重新校验。不同 Runner 不能控制同一组合
账户，单个执行账户也不能同时属于两个启用组合账户。

解除或切换归属时先停用 Runner、暂停组合账户并释放旧 owner。人工操作由 Trade 的
OperatorAction 处理，Strategy 不制造人工订单。

## 运行与恢复

- Python worker 按 `source_hash` 缓存不可变 Strategy。
- Engine 强制输入行数、严格递增时间和最后一行触发时点。
- 输出由 Python SDK 和 Go 双重严格校验。
- Runner 的当前 FULL 目标和 sequence 持久化，进程重启后无需重放策略内部状态。
- outbox 未发布记录在重启后继续发布。
- 组合账户 PAUSED 时 Strategy 仍可接受新结果；Trade 只保存最新目标，不下单。

## 明确不做

- 隐藏的跨轮策略状态和增量输入。
- 多策略共享同一执行账户的资本归属。
- Strategy 内部账户选择、订单执行和 Secret 访问。
- 通用工作流、分布式锁、全局 exactly-once。
- 为已删除的旧模型保留兼容表或转换链。
