# MooX 代码审查报告（2026-07-06）

本报告对 moox 大仓做了一次全量代码与架构审查，覆盖 `modules/storage`（约 3.8 万行）、`modules/admin`（2.2 万行）、`modules/trade`（1.9 万行）、`modules/cloudnode`（1.8 万行）、`modules/collector`（1.3 万行）、`modules/cli`、`packages/cloudruntime`、`web-host`，以及大仓治理、构建部署、测试基建、前端接入等横切关注点。审查以设计文档（架构总览、存储引擎架构、云节点执行平台架构等）为对照基准，每条发现均有代码位置佐证；未能运行验证的结论标注"待确认"。

## 一、执行摘要

**总体判断：设计成熟度明显高于工程落地成熟度（约 7/10 vs 4/10）。**

架构蓝图清晰且代码基本守住了设计边界：go.work 多模块 + proto 优先的跨模块通信、PrimaryStore 唯一写入口 + 事件驱动派生、JetStream 作执行事实源 + SQLite 投影、admin 表驱动网关转发不耦合业务模块——这些核心设计在代码中都有忠实映射，模块边界检查脚本、部署脚本、运行时数据分离等工程化投入是真实的。

但存在三类必须正视的风险：

1. **安全硬伤（P0，可直接利用）**：开放注册默认 ADMIN 角色、SysDeploy 无 RBAC 可篡改转发目标形成 SSRF、SSH 端点绕过 JWT、开发密钥随部署包分发、云账户/交易所密钥明文或弱加密落库。
2. **交易与数据正确性（P0）**：trade 的成交结算链路（`ApplyFills`）实现了但从未被调用、撤单缺必填参数、下单无幂等与超时对账——**当前不宜用于实盘**；collector K 线采集固定拉"最新 5 根"、无断点续采，漏调度即永久缺桶；storage View 重建的构建期增量补偿是空操作。
3. **质量门禁缺失（P1，系统性）**：无 Go 构建/测试 CI，storage 3.8 万行只有 4 个测试文件，release/deploy 产物不完整（缺 web-host 构建链、trade 配置），依赖版本跨模块漂移。

**若只修十件事，按此顺序**：① admin 注册权限与默认角色 → ② SysDeploy RBAC + 转发地址校验 → ③ 生产密钥治理（拒绝默认值启动 + 加密落库）→ ④ trade `ApplyFills` 接线与撤单参数修复 → ⑤ trade 下单幂等 + 超时对账 → ⑥ collector K 线断点续采 → ⑦ cloudnode RUNNING 超时回收 + AckWait/recover_after 对齐 → ⑧ storage View dirty 追踪补实现 → ⑨ 搭建 Go CI（build + test + check-boundaries）→ ⑩ SSH 端点鉴权加固。
