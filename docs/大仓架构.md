# moox 大仓架构

本文记录 moox 作为量化数据存储统一解决方案的大仓结构设计。本文只描述代码组织、模块边界、构建发布，不涉及业务代码实现。

> **状态：第一阶段迁移已完成。** `go.work` 管理多个 Go module，所有模块已迁入 `modules/`，`skills/moox` 和 `scripts/` 已建立，根 `Makefile` 已统一构建入口。Gin 依赖已移除，全部统一为 tRPC 框架。

## 目标

moox 作为唯一大仓，吸收旧 `data-collector`、`factor-calculator` 和 `xData-mini`，将账户/订单相关能力收敛到 `modules/trade`，并将 `data-miner` 中有价值的交易所连接、调度、限频、标的发现能力合并进 collector。

已建立的大仓骨架：

- 使用 `modules/` 承载各业务模块。
- 接受 `go.work + 多 go.mod` 的 workspace 模式。
- 统一命令入口命名，所有二进制使用 `moox-*` 前缀。
- 将原 `internal/data` 类命名收窄为 `internal/storage`。
- 新增 `skills/` 存放 moox 相关 Agent 技能。
- 新增 `scripts/` 存放编译、发布、技能打包脚本。

## 技术决策

### go.work + 多 go.mod

采用 `go.work` 管理多个 Go module，而不是直接合并成单个 `go.mod`。

原因：

- 合并前的 `moox/cli`、`moox/server`、`xData-mini/storage`、`xData-mini/cli`、`data-collector`、`data-miner` 曾是独立 Go module；当前大仓已经按 `modules/*` 和根级 `packages/*` 组织，其中 `data-miner` 不再作为一级模块迁移，而是作为 collector 的内部能力来源。
- 这些来源模块的依赖差异很大，尤其 `xData-mini/storage` 包含 Pebble、DuckDB 等 CGO 依赖。
- 使用多 `go.mod` 可以降低迁移风险，让每个模块保持可独立编译和测试。
- `go.work` 可以在本地开发时消除大量临时 `replace`，同时保留模块边界。

### internal/storage 替代 internal/data

代码中的 `data` 容易被理解为数据文件、样例数据或运行时数据。涉及存储抽象、存储路由、存储引擎封装时，统一使用 `storage`。

当前约定：

| 目录 | 含义 |
| --- | --- |
| `internal/storage` | 存储抽象、存储路由、存储引擎封装 |
| `internal/dataset` | Dataset 领域模型和业务规则 |
| `var/` | 本地运行时数据，例如 db、index、cache、临时文件 |
| `examples/` | 可重建的示例和端到端初始化数据 |

## 运行产物不进入源码树

根目录和各模块下的运行产物、构建产物统一通过 `.gitignore` 排除：

```text
/bin/
/data/
/log/
/logs/
/var/
/release/
/dist/
/modules/*/bin/
/modules/*/data/
/modules/*/log/
/modules/*/logs/
/modules/*/var/
/modules/*/release/
/modules/*/dist/
/modules/*/.cache/
```

源码仓库只保留代码、配置模板、schema、文档、脚本和 examples 示例。真实运行数据应放到云磁盘部署目录，例如远端 `/data/moox/var/<module>`。

## 模块目录规范

每个业务模块优先使用同一套目录语义：

| 目录 | 含义 |
| --- | --- |
| `cmd/` | 可编译二进制入口，优先使用 `server`、`cli`，再按模块运行形态补充短目录名 |
| `internal/` | 模块私有实现，不允许跨模块 import |
| `proto/` | 对外协议和生成代码，是当前允许跨模块引用的主要边界 |
| `schema/` | 模块拥有的数据表定义或元数据定义 |
| `config/` 或 `configs/` | 配置模板，不放本地运行时配置 |
| `docs/` | 模块内设计文档和操作说明 |

关键协议、CLI、Schema 初始化边界和易回归逻辑保留单元测试；端到端数据通过 `examples/` 和运行期服务流程重建。临时验证脚本不沉淀到模块源码。

## 跨模块依赖边界

业务模块不能随意互相 import。当前强制规则：

- 同一模块内可以 import 自己的 `internal/`、`pkg/`、`proto/`。
- 跨模块只能 import 对方 `proto/` 下的生成协议包。
- Admin 是中央管理和浏览器控制面，边界更严格：`modules/admin` 不 import 其他业务模块，包括其他模块的 `proto/*`。Admin 维护 `t_gateway_nodes` 和按节点归属的 `t_service_deployments`，只处理 `/api/admin/*` 与 `/api/gateway-control/*`。
- `modules/gateway` 是每台服务器独立部署的数据面执行器，通过根级 `packages/gatewayauth` 和 `packages/gatewayproxy` 共享稳定协议，只代理本机 loopback 服务，不 import Admin 内部实现。
- 当前正式部署形态是一个中央 Admin 管理多个服务节点。系统不承担动态服务发现、自动摘除、负载均衡、跨节点转发或自动故障转移。
- 稳定共享库放在根级 `packages/`。当前 `packages/commonpb` 承载跨模块公共 proto 类型，`packages/cloudruntime` 承载跨业务复用的 CloudNode JobItem runtime；业务模块不能直接引用其他业务模块的 `internal/` 或 `pkg/`。
- 根级 `packages/` 不能反向 import `modules/*` 业务模块，避免共享库变成隐式业务依赖聚合点。

依赖边界由根脚本检查：

```bash
make check-boundaries
```

## 统一验证入口

根目录是大仓操作入口，模块内 Makefile 可以保留模块自己的细节，但日常命令优先从根目录执行：

```bash
make build
make check-boundaries
make release
make release-matrix
make deploy
```

`make build` 编译当前大仓模块，`make check-boundaries` 检查模块依赖边界，`make release` 生成单平台二进制归档包，`make release-matrix` 生成 Linux、macOS、Windows 的跨平台归档与校验文件，`make deploy` 生成并同步可运行部署目录。推送版本 Tag 后，GitHub Actions 与 CNB 分别发布这些归档。源码检查、构建、发布脚本和 Agent skills 保留在仓库源码树；二进制 release 包不复制整套 `scripts/` 或 `skills/`，避免发布包携带需要源码上下文的开发资产。

## 模块职责

| 模块 | 职责 |
| --- | --- |
| `modules/admin` | 中央控制面、管理台后端、Space、认证、网关节点、系统部署信息与基础运维能力 |
| `modules/gateway` | 节点本机服务网关：路由拉取、HMAC 校验、缓存与 loopback 代理 |
| `modules/cli` | 统一命令行入口，面向用户、脚本和 Agent |
| `modules/storage` | 数据事实面、在线写入、在线查询、异步派生视图、存储引擎适配 |
| `modules/cloudnode` | 云节点、云账户、云函数代码包、异步 JobItem 队列和 SCF 执行状态 |
| `modules/collector` | 采集规则、任务实例、数据源接入、交易所连接、标的发现、采集任务执行（可部署于 SCF） |
| `modules/factor` | 因子服务占位与健康检查；后续承载因子定义、计算和结果写回 |
| `modules/eventbus` | 内嵌 NATS JetStream Broker，声明 Stream/KV 并提供只读管理面；业务 Consumer 由消费服务创建 |
| `modules/hostagent` | Linux CPU、内存、文件系统、磁盘和网络指标采集与 EventBus 发布 |
| `modules/monitor` | 服务探测、指标消费、Storage 投影、告警和监控查询 API |
| `modules/trade` | 订单、成交、交易通道和账户交易操作 |
| `packages/commonpb` | 根级公共 proto 类型包，唯一生成 `trpc.moox.common.*` |
| `packages/events` | EventMessage 外层协议、事件注册表、Subject 渲染和结构化 Payload 编解码 |
| `packages/storagepb` | Storage Dataset 行变更的公共 Payload 类型 |
| `packages/metricspb` | 指标 Payload 类型 |
| `packages/hostmetricpb` | 主机指标 Payload 类型 |
| `packages/jetstream` | NATS 连接、发布、消费、凭据和投递语义共享封装 |
| `packages/cloudruntime` | 根级共享库，承载 CloudNode JobItem runtime，不归任何单一业务模块私有 |
| `packages/gatewayauth` | Gateway 控制面与服务面共享 HMAC 协议和安全客户端 |
| `packages/gatewayproxy` | Gateway 路由快照、校验、哈希、原子路由表和代理规则 |

> 另有 `web/`（Vue 3 前端）和 `web-host/`（Go 静态文件服务器）作为前端工程；`web-host/` 已纳入 `go.work`，只承载静态资源，不代理 `/api/admin`、`/api/service` 或 storage API。

## 公开边缘与安全边界

`deploy/caddy/Caddyfile` 是 HTTP 公开路由契约。中央节点 Caddy 把站点交给 web-host `9528`，把 `/api/admin/*` 和 `/api/gateway-control/*` 交给 Admin `11000`；每台节点 Caddy 都把 `/api/service/*` 交给本机 Gateway `11002`。web-host、Admin、HTTP Gateway、诊断端口和业务服务只绑定 loopback。控制节点另在 `11003` 提供带 Service HMAC 的原生 tRPC Gateway，供 SCF 访问 Storage；Storage 物理监听仍只绑定 loopback。`--no-admin` 节点不创建浏览器站点或控制面路由。

`/api/admin/*` 属于人机控制面，使用 JWT + 每请求会话 HMAC；`/api/gateway-control/*` 使用 control HMAC；`/api/service/*` 属于机器数据面，使用与 control key 分离的 service HMAC。诊断服务位于独立内部监听并使用 health HMAC。Caddy 和私有 CA 由发布脚本自动管理；模块不应自行实现 TLS 终止或把诊断路由加入公开网关。详细架构见[节点服务网关架构](节点服务网关架构.md)。
