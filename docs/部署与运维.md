# 部署与运维

当前代码提供按单元部署的原生 CLI 和 Linux 运行助手。初始化分为 core、主机与业务单元、完整 control；
各阶段独立返回就绪收据。全系统交付范围见[当前实现与文档边界](实现状态.md)。

旧 `setup deploy-control/deploy-storage/deploy-service` 与 `scripts/deploy/deploy-moox.sh` 仍存在，
其外置 Caddy、旧网关字段和目录布局尚未完成收尾，不能用来部署本分支的新架构。

## 1. 拓扑与软件包

主机、组件放置和路径由 `moox.toml` 的 `[hosts.*]`、`[placements]`、`[paths]` 声明，模板为
`moox.toml.example`。软件包与主机不同：同一主机可安装 host 和多个业务单元。

| profile | 包内组件 |
| --- | --- |
| `host` | HostGateway、HostAgent、`moox-runtime` |
| `control` | Console Proxy、web-host、Admin、EventBus、Monitor、Collector、CloudNode、Factor Manager、Strategy |
| `storage` | Storage primary、node、view |
| `access` | Access |
| `egress-proxy` | EgressProxy |
| `trade` | Trade |

实际安装取包内组件与目标主机放置的交集。每台 MooX 主机先具备 host 单元；Factor Engine 在操作员机器
独立安装，SCF 另行发布。Archive 有独立模块和工具，但不在上述原生 profile 中。

纯 Go 程序和前端在本机构建或交叉编译；Storage 三个服务需要 Linux CGO 制品，Storage CLI 仍关闭 CGO。
`setup package` 只收集软件与公开模板，不读 `moox.toml`，也不携带证书、签名密钥、数据库或日志。

## 2. 原生初始化顺序

前提：准备私有 `moox.toml`（0600）、可信 SSH 指纹、Linux 目标主机和所需网络连通性；
目标机需要 Python 供传输预检。Factor Manager 所在主机还需要预先安装 pandas 2.2+（小于 3）和 numpy 2。

以下示例使用模板的 `control`、`storage`、`compute-1` 主机 ID。业务单元必须按实际放置选择，不自动创建云资源或防火墙规则。

```bash
# 本机 CLI 与配置检查
./scripts/build/build.sh cli
./bin/moox-cli setup validate --file ./moox.toml

# 核心控制面：Admin、EventBus、HostGateway、HostAgent；输出 core-ready
./bin/moox-cli setup bootstrap --stage core --file ./moox.toml --source-dir .

# 每台业务主机安装 HostGateway 和 HostAgent
./bin/moox-cli setup deploy-host --file ./moox.toml --source-dir . --host storage
./bin/moox-cli setup deploy-host --file ./moox.toml --source-dir . --host compute-1

# 默认下载到 ./bin，同时构建所需的 Linux Storage CLI
./bin/moox-cli setup build-linux --file ./moox.toml --module storage --source-dir .
./bin/moox-cli setup deploy-unit --file ./moox.toml --source-dir . \
  --host storage --profile storage --binary-dir ./bin
./bin/moox-cli setup deploy-unit --file ./moox.toml --source-dir . --host storage --profile access
./bin/moox-cli setup deploy-unit --file ./moox.toml --source-dir . --host compute-1 --profile egress-proxy

# 完整控制单元；此例显式选择 internal TLS 的首次 CA 创建授权
./bin/moox-cli setup bootstrap --stage control --file ./moox.toml --source-dir . \
  --factor-python /absolute/path/to/python --create-proxy-ca
```

最后一条的 `--create-proxy-ca` 只适用于 `[hosts.control] tls_mode = "internal"`。
公网模式不传此参数；导入已有 internal CA 使用 `--proxy-ca-import-dir` 指向目标机上已停止、带原始信任证明的状态树，
与首次创建互斥。运行状态中已有 CA 时不能靠重试重新生成。

所有阶段使用同一个原始配置和 `--state-dir`（默认 `~/.local/state/moox/setup/<绑定摘要>`）。
SSH 断连并不证明远端已停止；重试复用原请求、制品和持久日志。`*-paused` 表示组件保留了暂停状态，不能当作 ready。

`control-ready` 证明所选控制组件就绪，不代表业务 seed、SCF、Factor Engine、真实行情写入或交易验收完成。
原生 Storage 会建元数据库；业务初始化输入仍在 `config/setup/metadata.yaml`、`collection-tasks.yaml`、
`dataset-health-policy.yaml`。现有 `setup init/apply` 等命令包含旧部署假设，完整初始化流程尚需统一，不能机械接在上述流程后宣称完成。

## 3. 目录与运行助手

默认部署根 `/data/moox`，control 单元根 `/data/moox/prod`，Storage 单元根 `/data/moox/storage`。
单元各有 `releases/<发布ID>` 和 `current`；组件工作目录位于发布内，状态复制后才切换 current，旧发布保留独立快照。

| 位置 | 用途 |
| --- | --- |
| `<部署根>/host/current` | 当前 HostGateway、HostAgent 及运行助手 |
| `<单元根>/current/runtime.json` | 私密运行计划，组件与健康端口来自共享目录 |
| `<发布目录>/secrets/`、`certs/` | 按组件投影的签名身份、EventBus 凭据和证书 |
| `<部署根>/identity/` | 独立于发布的运行身份、Admin 主密钥、MooX CA 与代理 CA 授权材料 |
| `<部署根>/run/maintenance.lock` | 安装、启停、恢复和守护共享的主机锁 |
| `<部署根>/run/paused/`、`pids/`、`draining/` | 暂停标记、进程身份与排空记录 |

以默认 control 根为例，在目标 Linux 主机执行：

```bash
/data/moox/host/current/bin/moox-runtime status --plan /data/moox/prod/current/runtime.json
/data/moox/host/current/bin/moox-runtime pause --plan /data/moox/prod/current/runtime.json --components collector
/data/moox/host/current/bin/moox-runtime resume --plan /data/moox/prod/current/runtime.json --components collector
```

助手支持 start、stop、restart、pause、resume、healthcheck、status。暂停先落盘再停进程，重试和守护保留暂停。
healthcheck 按 `/healthz` 判断进程是否需恢复；`/readyz` 暂不可用不会触发自动重启。
低层 prepare、activate、recover、rollback 由部署编排生产规范请求，不应手写私密请求替代上层部署。

## 4. 网络与信任

| 入口 | 使用方与安全机制 |
| --- | --- |
| HTTPS `9527` | 浏览器 → Console Proxy → Admin/web-host；只代理 `/api/admin/*` 与页面 |
| loopback `11002` | 本机组件和操作员 SSH 隧道；签名 tRPC 与 Directory |
| TLS `11003` | 跨主机签名 tRPC；MooX 私有 CA、目标主机 ID 校验 |
| tRPC `11004` | 外部 Access；SCF、Factor Engine、Skill 各自身份、方法白名单及持久 nonce；该入口本身不提供 TLS |
| TLS `4222` | EventBus；按发布/消费角色鉴权 |

普通业务 RPC 绑定 loopback。原生安装器按组件目录渲染健康监听：未标记 loopback 的健康端口绑定 `0.0.0.0`，
使用 health HMAC；防火墙限制探测来源。Console Proxy `19528`、web-host `19527` 保持回环。
应用实际配置看 `unitinstall/render.go`，不能只根据源码模板判断监听。

三套 CA 分开管理：MooX CA 用于主机网关 TLS，EventBus CA 用于 NATS，Console Proxy 的 internal CA 用于浏览器。
公网代理使用系统信任/ACME；internal 根证书需要由操作员核验并安装信任。代理 CA 不由普通启动隐式创建，
控制阶段持锁消费创建/导入授权；丢失已消费材料时拒绝自动重建。

## 5. 配置发布与凭据

原生部署把配置、身份和软件摘要绑定到一次操作；更换源码、参数或私密环境不能接管旧请求。
服务身份由 Admin 生成，操作员只下载自己的签名身份和公开 CA，服务私钥与 CA 私钥留在目标机。
Storage 的 node、primary、view 角色密钥独立于网关签名，按实际需要分发。

`config plan/publish` 已实现差异检查、保留期缩短确认与失败恢复，但仍操作旧平铺目录、`<root>.maintenance.lock`
和 `start.sh`。原生单元使用发布内的配置及 `<部署根>/run/maintenance.lock`，两者尚未统一；
当前不能用 `config publish` 更新原生安装。配置发布细节见[命令行工具](模块/命令行工具.md#_1-2-配置发布)。

EventBus 角色与 TLS 材料由 Admin CLI ensure/export/rotate 管理；轮换后还须分发到实际客户端、SCF 和外置引擎。
调用方签名轮换允许新旧 KeyID 共存，替代密钥生效后才能 retire 旧密钥；Access 的静态验证文件也需重新分发。

## 6. 数据保留

| 数据 | 当前默认行为 |
| --- | --- |
| 行情与因子事实 | `[storage_retention]` 按空间和频率解析；按天桶清理，实际可能多保留不足一天；record 数据不过期 |
| `mooxsys` 服务指标 | 30s 数据集保留 48 小时 |
| `mooxsys` 主机指标 | 1m 数据集保留 180 天 |
| View 索引 | 每个序列最近 `view_bars` 根，默认 5000；超过 ceil(1.2 × N) 整理 |
| Monitor 检查结果和告警事件 | 默认 14 天；每 6 小时清理 |
| Strategy | 定义版本、会话、结果保留；解释明细默认 90 天；已结束回放默认 90 天且每空间最多 50 个 |
| Admin | 90 天前的登录历史与 SSH 会话由垃圾回收定时器清理 |
| Trade 订单成交、Archive Parquet | 不自动按统一期限删除 |
| EventBus | 各 Stream 独立设置保留时间与容量，见[事件总线](模块/事件总线.md) |

Storage 策略的原生路径是发布内各角色的 `config/storage-policy.json`。缩短保留期会删除超期事实，
需要在发布前核对。SQLite 空闲页和 Pebble 删除标记的磁盘回收还取决于复用或 compaction。
各模块日志 writer 的轮转配置各自生效；旧部署脚本的统一日志轮转和 CLS 预检不等于原生部署已接入相同流程。

## 7. 构建和验证

```bash
make test-docs-architecture check-boundaries
pnpm docs:build
make test-unit-core test-unit-bootstrap test-unit-install test-unit-runtime
make test-console-proxy
make test                 # 工作区 Go 测试与 vet、前端测试和构建
make verify              # CI 的综合检查
```

Go 版本以 `.go-version` 为准；Python 测试依赖安装到隔离环境：
`python -m pip install -r modules/factor/pyworker/requirements.txt`，并让该环境的 `python3` 位于 PATH 前部。

Linux 发布验证另行执行 `test-unit-core-linux`、`test-unit-bootstrap-linux`、`test-unit-install-linux`、
`test-unit-runtime-linux` 及 `test-host-gateway-control-e2e`。这些门禁需要预构建二进制、软件包和隔离的运行环境；
准备要求见 `scripts/test/gates/`。本机测试通过不能替代跨主机和生产业务验收。
