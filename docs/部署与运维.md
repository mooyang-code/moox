# 部署与运维

部署由 `moox-cli setup` 完成：每台主机一个部署根，组件是 systemd 用户服务，`setup deploy` 把一台主机部署成配置描述的样子，`setup install` 按顺序装完整个系统（新安装），`setup update` 按同样的顺序覆盖更新已装好的系统（数据保留），`setup wipe` 卸载（清空全部启用的主机，moox.toml 里停用的主机不碰）；`setup validate` 检测每台主机上各组件是否已部署，据此决定走哪一种。
全系统交付范围见[当前实现与文档边界](实现状态.md)。

## 1. 拓扑与组件包

配置是同一目录里的两份文件，模板为 `moox.toml.example` 与 `moox.secrets.toml.example`：

- `moox.toml`：明文，主机（`[hosts.*]`）、组件放在哪台主机（`[deployments]`）、部署根（`[paths] deploy_root`）和部署时渲染的参数（保留期、出口白名单、日志服务地址等），以及手工调参 `[overrides]`。没有秘密，可以放进自己的私有仓库。
- `moox.secrets.toml`：整份加密（密钥在本机钥匙串）。管理员、腾讯云密钥、交易所密钥、告警渠道是**初始值**：`setup init` 写进管理台一次，只建不改，之后以管理台为准；
  CLS 写入密钥是部署参数，每次部署读出来渲染进各组件的环境文件。

组件、它的二进制与配套命令行、启动参数、配置模板、启动顺序都登记在服务目录（`packages/servicecatalog/catalog.yaml`）。发布时每个组件一个包
（`moox-<组件>_<版本>_linux_amd64.tar.gz`，只有 `bin/` 下的二进制），发布清单 `moox-bundle.json` 的 `components` 列出每个包的摘要；配置模板在产物包的仓库快照里，由 CLI 渲染。

| 主机（示例拓扑） | 组件 |
| --- | --- |
| 每台主机 | `host-gateway`、`host-agent`（自动带上，不写在 `[deployments]` 里）。`[hosts.<ID>]` 写了 `external_entry = true` 的主机，网关另开外部入口 `11004`（见[主机网关](模块/主机网关.md)第 6 节） |
| 控制机 | `admin`（含浏览器入口 9527 与内嵌的管理台页面）、`monitor`、`collector`、`factor-mgr`、`archive-mgr`、`strategy` |
| 存储机 | `storage-primary`、`storage-view`、`eventbus`；网关开外部入口（`external_entry = true`） |
| 海外机 | `trade`、`egress-proxy`、`collector-stream`、`callback-dispatcher`（事件中心；所在主机必须能访问到用户的通知地址） |
| 因子机 | `factor-engine`、`archive-worker`；没配 `[archive_object_store]` 时另有内置对象存储 `seaweedfs` |

- `collector-stream` 写 Storage 经主机网关，按服务目录的访问控制放行，没有要分发的 Storage 密钥。端口：本地执行端 `MarketFetchExecutor` 11450，健康检查 11451；它经主机网关调用 Collector 的 `StreamCollector`（11422）。
- 服务目录新增组件、调用方或方法时，各主机的网关、Admin、Monitor 要是同一版：`setup update`（或逐台 `setup deploy`，控制机先）。路由由各网关按内嵌的服务目录自己算，没升级的网关不认识新组件（忽略并记日志）、不认识新方法（拒绝），其余照常。新组件不需要自己的签名密钥：每台主机一把签名私钥（`secrets/host.key`），本机组件共用，网关按“签名主机上是否部署了这个组件”认调用方。控制机每次部署都会执行 `moox-admin-cli bootstrap`，把 `moox.toml` 里的主机与部署同步进去：新的登记上，已有主机的地址、中文名等跟着更新，启停状态保留。
- 纯 Go 程序和前端在本机构建或交叉编译；Storage 的两个服务（primary、view）需要 Linux CGO 二进制，Storage CLI 仍关闭 CGO。SCF 函数另行发布。

### 主机命名与登记

主机 ID 用英文短名、按角色命名，配一个固定的中文名（`[hosts.<ID>] label`，不写时按 ID 生成；登记到 Admin 的主机表，管理台只显示中文名与 ID、地址），
文档与沟通统一写“中文名（英文 ID）”。只在同一角色有多台时才加序号（如 `overseas-2` → “海外机 2”）。

| 主机 ID | 中文名 | 角色 |
| --- | --- | --- |
| `control` | 控制机 | 控制面：Admin（含管理台）、Monitor、Collector（含云函数管理）、因子管理、归档管理、策略 |
| `storage` | 存储机 | Storage primary/view、EventBus；网关开外部入口 |
| `overseas` | 海外机 | 海外 IP 出口：Trade、EgressProxy、Collector Stream、事件中心（callback-dispatcher），网关开外部入口，建议放在香港 |
| `factor` | 因子机 | 因子引擎与归档 Worker（外部程序），可以在内网（只能出站） |

Admin 的主机表（`t_hosts`）是主机的唯一登记处，也保存控制台终端用的 SSH 端口与用户（凭据在 `t_secrets`，指纹首次连接时固定）。
机器的新增、部署、启停与移除只通过 `moox-cli` 完成，管理台的“主机工作台”与“服务管理”页面只读：

启停与移除只在 `moox.toml` 里声明：`[hosts.<ID>]` 的 `enabled`（不写为启用）和与 `[deployments]` 同形的 `[deployments_disabled]`。
每次 `setup deploy`、`setup update` 都按 `moox.toml` 整份覆盖 Admin 的主机与部署登记（多出的主机与部署删除，签名公钥与 SSH 指纹保留），
并按声明启停 systemd 单元。登记的状态列仍在：Monitor、网关路由、服务目录、归档中转与 doctor 都读它，只是不再有改状态的命令。

| 操作 | 做法 |
| --- | --- |
| 登记并部署主机 | 在 `moox.toml` 加 `[hosts.<ID>]` 与 `[deployments]`，`setup deploy --host <ID>` |
| 停用 / 恢复主机 | `enabled = false` / 删掉它，再 `setup deploy --host <ID>`：停用的主机只留 `host-gateway` 在跑（各网关只认它）；连不上也照常写登记 |
| 停用 / 恢复组件部署 | `[deployments_disabled]` 加上 / 删掉组件，再 `setup deploy --host <ID>`：停用的组件只装文件、单元停掉 |
| 移除主机 | 先 `setup stop` 逐个停掉它的组件，再从 `moox.toml` 删掉它，部署任意一台主机即删除登记 |

已知差别：部署主机 Y 时也会把主机 X 的新状态写进 Admin，各网关的路由随即撤销或恢复；但 X 上的进程要等部署 X 时才按声明启停。
`setup stop` 只是临时停：下次部署会按声明把组件重新拉起，长期停用写进 `[deployments_disabled]`。
没有登记 SSH（或只能出站）的主机，控制台终端与文件管理置灰。Agent 的操作说明见 `skills/moox/references/host-registry.md`。

## 2. 安装顺序

日常安装用一条命令，在产物包目录运行：

```bash
./bin/moox-cli setup install --space-id crypto                       # 只读预检
./bin/moox-cli setup install --space-id crypto --yes                 # 执行
./bin/moox-cli setup install --space-id crypto --yes --wipe <摘要>   # 装过、用户确认彻底清空后
```

前提：两份配置（`config init` 生成）、可信的 SSH 指纹、Linux 目标主机；目标机要有 `python3`、`bash`、`tar`、`flock`；每台主机的部署用户开了 linger（`sudo loginctl enable-linger <用户>`），部署根的上级目录对该用户可写。
`setup validate` 会把没开 linger 的主机列在 `manual_steps` 里，journald 没有持久化（`/var/log/journal` 不存在）列在 `warnings` 里。

`setup install` 依次执行（每一步都可以单独运行，命令在预检输出的 `steps` 里）：

0. 操作身份（`setup operator`）：这台电脑上没有 `~/.config/moox/moox-cli.key` 就生成一把 ed25519 私钥，有就原样复用（重跑不换，否则和控制机上登记的公钥对不上）。
1. 防火墙：放行各主机对外的端口（`setup firewall`）。
2. 控制机先装 `admin`、`host-gateway`、`host-agent`。部署前在控制机上执行 `moox-admin-cli bootstrap`：建库、MooX CA、主密钥、管理员、登记这台电脑的 `moox-cli` 公钥、EventBus 凭据，都是只建不改；全部主机与部署按 `moox.toml` 同步（已有主机的地址等跟着更新，启停状态保留）；控制机的根证书与它的指纹同时记到这台电脑的 `~/.config/moox`。
3. 带 EventBus、Storage 的主机（示例拓扑里是存储机）。
4. `setup init --stage storage`：业务空间、初始秘密、元数据。Collector 启动时要连 Storage 核对内置任务的元数据，所以排在控制机其余组件之前。
5. 控制机其余组件。
6. 其余主机；因子引擎、归档 worker 所在的主机排最后（它们依赖 `factor-mgr`、`archive-mgr` 与 Storage）。
7. 统一等一次全部组件就绪（各台的本机 `/readyz`，最长 5 分钟；被停用的组件不等）。
8. `setup init`：告警渠道、云账户、日志服务、云函数代码包、登录校验，并再核对一遍业务空间与元数据。这些要等 Collector、Monitor 起来，所以排在全部就绪之后。
9. `setup start --space-id <空间>`、`setup verify --space-id <空间>`。

某一步失败就停下（`install_step_failed`，报错里带单独重跑这一步的命令），修好重跑同一条命令：每一步都可以重做，没有变化的组件不重启。预检的 `manual_steps` 不为空时带 `--yes` 会直接拒绝（`manual_steps_required`）。装过的机器不带 `--wipe` 重跑就是接着装完，数据保留；带 `--wipe <预检摘要>` 是卸载后重装。
但重跑会再执行一次 `setup start`：手工停用的内置采集任务与默认因子任务成员会被重新启用，走云函数的空间会重建云函数。已经装好的系统要升级或改配置用 `setup update`（覆盖更新：部署顺序和安装相同，不初始化、不启动空间），不要重跑 `setup install`。

采集任务默认停用，`setup start --space-id <空间>` 才启用（种子里标了 `start: manual` 的任务除外，如两条 A 股日线任务，要用 `collector task update --enabled=true` 显式启用），并导入这个空间的因子任务（`config/setup/factor-tasks.yaml`）、创建默认示例策略；`setup verify --space-id <空间>` 验收真实数据。

**一次部署做的事**（`moox-cli setup deploy --host <主机> [--component a,b]`）：

1. 只读检测目标机：linger 没开就停下并给出要用户执行的命令；读回 `version.json`。
2. 把二进制放到 `<部署根>/bin/`：在产物包目录里，目标机按清单自己下载组件包到 `<部署根>/.staging/<摘要>/`（下载源按实测速度选 CNB、GitHub，每台最多 4 条连接，校验 SHA256；都下载不了时由操作机下载再推送）；
   在源码目录里用 `--binary-dir` 指定本机编译好的 Linux 二进制，只上传和上次部署记录不一样的。
3. 取身份材料：先在目标机上算出现有主机签名私钥的公钥（`moox-host-gateway-cli sign-public-key`，私钥不离开目标机）。控制机执行 `moox-admin-cli bootstrap`；
   其余主机先把登记同步到 Admin（这样网关快照和实际部署一致），再让控制机签发这台主机的身份包与 EventBus 凭据，经 SSH 取回并校验。
   目标机上的私钥和 Admin 登记的公钥一致时不换密钥，身份包里只有重新签发的主机证书与根证书；不一致、没有私钥，或带了 `--rotate-host-key` 时签发新的主机签名私钥（旧的立即作废）。
   签发了新私钥的这次部署按整台部署处理（`--component` 不起作用；全新主机除外，它没有已装的组件，按选中的组件装）：本机每个组件的配置指纹里都有签名公钥，全部按启动顺序重启并写进 `version.json`，主机网关最先重启，脚本等它的本机入口重新开始监听（最多 30 秒）再重启其余组件。
   主机签名密钥换了的话，这次没部署、但已经装着的组件也会被重启。
4. 渲染：每个组件的配置（`config/<组件>/`，路径都是绝对路径）、环境文件（`secrets/env/<组件>.env`）和单元文件；渲染之后应用 `[overrides]`。
5. 打成一个包传到目标机，由内嵌的安装脚本持文件锁（`<部署根>/.deploy.lock`）装好：配置按组件整目录替换，秘密文件逐个写，`daemon-reload`，按启动顺序重启**有变化**的组件，写 `version.json`。
6. 经 SSH 逐个请求本机 `/readyz`，到时限（默认 3 分钟）还没就绪的列出来，退出码非 0。只等这次装的组件。

重跑同一条命令就是再做一遍，没有过程记录，也不要求配置和上次一样。只部署个别组件时，如果服务目录的摘要和目标机 `version.json` 记的不一样，这台主机的 `host-gateway` 会一起升级并重启（路由是网关按内嵌的服务目录算的）。
整台部署时，不再属于这台主机的 `moox-*` 服务会被停掉并删除（数据目录留着）。

**从源码目录部署**（维护者）：

```bash
./scripts/build/build.sh cli
bash scripts/build/build-linux-local.sh --out ./bin-linux <目标>...      # 目标清单见 scripts/release/build-release.sh 的 server_targets
./bin/moox-cli setup validate --file ./moox.toml
./bin/moox-cli setup install --file ./moox.toml --binary-dir ./bin-linux --space-id crypto --yes
./bin/moox-cli setup deploy --file ./moox.toml --binary-dir ./bin-linux --host control --component monitor   # 之后单独发布一个组件
```

维护者发布新版本用 `scripts/release/build-release.sh vX.Y.Z`。清空重装的完整记录见 skill 的 [`references/fresh-deploy.md`](../skills/moox/references/fresh-deploy.md)，Agent 从源码目录部署与升级的流程见 [`references/source-deploy.md`](../skills/moox/references/source-deploy.md)。

补充：

- 管理台只用内部证书（MooX CA 签发）。浏览器信任步骤先经 SSH 从 `<部署根>/secrets/moox-ca.crt` 取回根证书，再在本机安装信任。这一步要本机管理员授权，不阻塞安装：用户在自己的终端运行 `setup trust-browser`；没有终端或安装失败时报 `browser_trust_manual` 并给出完整命令。
  macOS：`sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain ~/.moox/certs/moox-ca-<控制机地址>.crt`。不要清理钥匙串里的这张证书。
- 业务初始化输入在 `config/setup/metadata.yaml`、`collection-tasks.yaml`、`dataset-health-policy.yaml`、`factor-tasks.yaml`。
- `moox.secrets.toml` 里的 `[[exchange_keys]]` 由 `setup init` 写进密钥管理（固定 ID `exchange-<交易所>-<环境>-<名称>`，只建不改：管理台里已有的不覆盖、已删除的不重建）；它只写入、不检测，Trade 装好后逐把运行 `moox-cli trade inspect-credential`（`readonly = true` 的只读密钥不检测）。
- 告警渠道的规则是“Monitor 一个渠道都没有才写入秘密文件里的 `[notification]`”：在管理台把渠道全部删掉之后重跑 `setup init`，会把秘密文件里的渠道写回去；不想要就先把秘密文件里的 Webhook 地址清空。
- Collector 不需要配置空间：采集计划、补采和库维护按本地库的管理集合运行；`collector-stream` 按实例注入 `MOOX_SPACE_ID`。
- 默认采集任务：全新安装时 Collector 启动会把随部署放到 `<部署根>/config/collector/collection-tasks.yaml` 的种子写成默认任务（只在任务表为空时写，固定任务 ID，因子任务的源数据集依赖这些 ID）。
- 因子机：`[hosts.factor]` 写 `reachability = "outbound"`，`[deployments]` 里有 `factor-engine`、`archive-worker`。控制机的 11003 与 EventBus 所在主机的 4222 要在腾讯云防火墙放行（`setup firewall`）。
- 因子任务启用后不需要任何生命周期命令。引擎在计算前检查每个任务（窗口载入、数据覆盖、变更同步等），检查通过就自动开始计算；用 `moox-cli factor task status [--task-id <因子任务 ID>]` 看哪一项没过和处理办法。

### 全新部署与升级的注意点

- **表结构或存储格式变了的版本不写迁移**：发布说明会写明。整体做法是清空重装（`setup wipe` 后 `setup install`）；只涉及一个组件时，停掉它、删掉 `<部署根>/data/<组件>` 再重新部署。
- **全部主机同一版**：服务目录编在每台主机的网关、Admin、Monitor 里，升级时用 `setup update`（或逐台 `setup deploy`，控制机先）；全部做完之前，新方法在还没升级的网关上会被拒绝。
- **腾讯云上的函数不用先删**：Collector 按函数名接管云上的同名函数；符合本空间命名格式、不在计划里的函数在第一次读回后被停掉定时器，不会自动删除，确认后用 `moox-cli collector function delete` 清掉。
- **只清了 Storage、保留了 Collector 库时**（不是整体 `setup wipe`），对正在采集的空间执行 `moox-cli collector fetch-plan reregister --space-id <空间> --yes`（见“清空全部数据重新积累”第 3 步）。
- **操作员身份跟着控制机**：重装的控制机会生成新的 CA 与密钥。`setup wipe` 清空主机后会删掉这台电脑 `~/.config/moox` 下的操作员身份；没用它清空时，部署控制机会报 `operator_trust_failed` 并列出要删的文件。
- **升级后因子水位晚一两分钟**：因子引擎重启后重新载入窗口，载入期间的周期由追赶补算，水位晚一两分钟后补齐，不用处理。
- 装完之后按 skill 的 [`references/fresh-deploy.md`](../skills/moox/references/fresh-deploy.md)“全新部署后的验收”逐项核对。

配置变更通过重新部署生效：改 `moox.toml` 后对受影响的主机执行 `setup deploy --host <主机>`，配置每次都从模板重新渲染。

### 已知差别

下面这些都不影响结果，没有为它们加逻辑：

- Monitor 到 EventBus 的连接反复短断（每次短于 60 秒、间隔小于 5 分钟）时，依赖观测输入的检查会持续冻结，“观测输入”自己也不告警；这段时间只有网关、K 线结果、行情探针与标签检查照常判定（见 `docs/模块/监控.md` 12.2）。
- 首装时每台主机的 `host-gateway` 都会先退出一次再由 systemd 拉起（5 秒后）：没有快照缓存的网关首次拉取快照失败就退出，控制机的是因为 Admin 还没起来；其余主机的公钥刚登记，控制机网关要到下一次快照（约 5 秒）才认它，在那之前它的签名被拒。本机网关还没起来时，同机的 `trade`、`callback-dispatcher`、`collector-stream`、`factor-engine`、`host-agent` 也跟着退出 1～2 次，5～10 秒内都起来。`NRestarts` 为 1～2 属于正常。
- 升级时存储机的 `storage-view` 可能在主库还没监听时退出一次，5 秒后由 systemd 拉起。
- 原地升级（`setup deploy`）时二进制里带提交号，所以即使只改了个别模块的代码，除 `seaweedfs` 外的组件摘要都会变、都会重启。
- 单组件升级（`setup deploy --component <组件>`）后，这台主机 `version.json` 的提交号就是新提交（一台主机只记一个提交号），其余组件其实还是旧二进制；要全部一致就整台部署。
- 升级后因子引擎要重新载入窗口，载入期间的周期由追赶补算：因子水位会晚一两分钟后补齐，策略结果不缺期。
- 安装期间还没启动的空间（没执行 `setup start --space-id <空间>`）可能推一条“标签下没有可用的采集对象”的标签告警，几十秒后自动恢复。
- `host-agent` 打不开网关客户端（首装时本机网关还没监听、取不到目录）时直接退出，由 systemd 拉起重试；它不会带着“主机策略不同步”的状态继续跑。
- 现货与合约的首份采集计划生效时刻可能差几分钟，`setup verify` 默认最长等 10 分钟（`--timeout`）来覆盖这段时间，所以 `setup install` 的最后一步可能要等好几分钟；仍然超时（`factor_not_advancing`）时单独重跑 `setup verify --space-id crypto` 即可。
- `system pause` 要等 Collector 把云函数定时器全部停掉才返回，函数多或还在创建时要等几分钟；`system resume` 补齐暂停区间后放行，耗时随暂停时长与补采量而定。其中最多约 5 分钟是在等缺口巡检：Collector 放行到实时推送接上之间的一两根 K 线在放行时还没到应到时刻，补不了，要等下一次周期性缺口巡检（每 5 分钟一次）建补采作业，因子追赶在这之前停在缺口前。没有为它加放行后的定时重扫。
- 系统暂停或恢复追赶期间（Collector 模块不是运行状态），“K 线结果”“行情探针”两类检查不评估、保持原状态，不出新告警；Monitor 是从 Collector 的上报里得知暂停的，暂停后的头一两分钟内如果已经判出失败，仍可能有个别告警。
- `doctor diagnose` 刚装完时结论是 `INCONCLUSIVE`：磁盘预测历史不足，其余检查通过即可。
- 归档任务只拉建任务之后的变更；建任务之前导进 Storage 的历史数据不会进归档，要进归档用 `moox-cli archive import`。
- 因子机上 `host-gateway` 仍监听 `*:11003`（局域网内）。
- 登记或更换外部身份（`moox-skill`、`scf-collector`）的公钥后，各网关要等下一次拉到快照才认新公钥，最多约 5～10 秒。
- 空间没有启动（`setup start --space-id <空间>` 还没执行）时，它在云上的定时函数会被 Collector 判为计划外并停掉定时器，函数本身留在云上；下次启动这个空间时 Collector 按名字接管。
- `moox-cli collector function list` 把按需创建的补采函数也算进 `drift_count`：补采函数第一次补采时才创建，云上还没有时读回是“不存在”，被记成不一致，不代表采集有问题；已经建出来的补采函数不算。
- Monitor 的评估停滞没有自己的告警标题：启动满 3 分钟后，最近 3 分钟没有一次完整成功的评估（含业务评估整轮失败）时 `GetHostPolicy` 返回失败，由其他主机的 HostAgent 连续 3 次拉取失败后推送“控制机或 Monitor 不可达”，和进程退出、控制机失联是同一条。只有控制机一台主机时没有观测方，评估停滞不会有告警，表现为各项检查的时间不再前进。
- 没配通知渠道时告警只入库、不推送：Monitor 一个渠道都没有时，告警照常生成并显示在管理台与 `doctor alerts` 里，但不会发到任何地方；HostAgent 的直推与证书巡检同样发不出去。安装与部署不要求配渠道，装完要自己补上（管理台“资源与运维 › 监控告警”页的“消息通知设置”）。
- 系统暂停不撤销已收到的目标：Trade 放行后会继续执行暂停前收到、还没收敛且仍在有效期内的目标。
- 系统恢复要求每个启用的实盘账户同步正常才算 Trade 追平：凭证失效但仍启用的账户会让 `system resume` 一直等，要先停用这个账户再恢复。
- 主机签名私钥是本机组件共用的：海外机上任一进程拿着它都能以 trade 的身份向控制机取交易所密钥（Trade 自己就要用）。服务端把经网关来的组件调用方限定在类别 `exchange`，云账号等其他类别取不到；控制机上的进程同机直连 Admin，不受这条限制。
- 因子任务的窗口还没载入完（或检查没通过）时到达的周期不算：算过的任务只记追赶目标，载入完成后由追赶循环补算，这些周期的结果比正常晚到；从没算过的新任务从就绪后的第一条实时事件算起，载入期间的周期用补算作业补。
- 策略实例读不出追赶进度时（绑定快照无法解析、日历换算失败等）不挡系统恢复，只写进策略的追赶说明；这样的实例本来就不求值，放行后要按策略页的跳过原因修好。
- 策略回放与实盘求值用浮点运算，Go 在 arm64 上会把乘加融合成一条指令、在 amd64 上不会：金样覆盖到的路径已用显式转换保证两种架构结果一致，其余路径在不同 CPU 架构下末位可能不同。同一套部署里实盘与回放都在同一台主机上算，互相一致；不要拿另一种架构的机器上算的结果逐位比对。
- 真实 systemd 下的安装、启停和就绪等待没有自动化检查：安装脚本的用例用假的 `systemctl` 核对文件布局与调用顺序，真实行为只靠真机安装验证。

## 3. 目录与服务

每台主机一个部署根（`[paths] deploy_root`，默认 `/data/moox`），属于部署用户、权限 0700：

```text
/data/moox/
  bin/                       本机要用的全部二进制与配套命令行
  config/<组件>/             渲染出的配置，每次部署按组件整目录替换
  secrets/
    host.key                                   主机签名私钥（ed25519），本机全部组件共用；Admin 只登记它的公钥
    moox-ca.crt  host.crt  host.tls.key        MooX CA 根证书、主机证书
    scf-collector.key                          只有控制机：云函数的签名私钥，Collector 发布函数时写进函数环境
    env/<组件>.env                             环境文件（systemd 的 EnvironmentFile）
    eventbus/                                  <角色>.yaml；EventBus 所在主机另有 users.yaml（没有证书：EventBus 用上面的主机证书）
    archive-object-store.env                   归档 worker 的对象存储凭据
    seaweedfs/                                 内置对象存储的访问密钥与 s3.json（目标机生成）
    admin-master.key  pki/                     只有控制机：Admin 主密钥与 MooX CA（bootstrap 生成）
  data/<组件>/               数据，也是组件的工作目录；部署不碰
  logs/<组件>/               tRPC 的文件日志
  archive/  import/          归档文件、导入包（因子机）
  version.json               部署记录：版本、提交、服务目录摘要、部署时间，每个组件的二进制摘要与配置指纹
  .staging/                  下载的组件包（按摘要存放，可以删）
~/.config/systemd/user/moox-<组件>.service
```

存储机、因子机的 `secrets/` 下只有本机的密钥、主机证书、根证书、EventBus 角色文件（存储机另有对象存储等本机凭据）：没有 `moox-cli`、`console` 的签名能力。

单元文件由 CLI 按服务目录渲染（模板 `deploy/systemd/user/moox-component.service.tmpl`）：

```ini
[Unit]
Description=MooX collector
After=moox-host-gateway.service moox-admin.service
StartLimitIntervalSec=0

[Service]
Type=simple
WorkingDirectory=/data/moox/data/collector
EnvironmentFile=/data/moox/secrets/env/collector.env
UnsetEnvironment=HTTP_PROXY HTTPS_PROXY http_proxy https_proxy
ExecStart=/data/moox/bin/moox-collector -config=/data/moox/config/collector/app.yaml -conf=/data/moox/config/collector/trpc_go.yaml
Restart=always
RestartSec=5
TimeoutStopSec=120
UMask=0077
LimitNOFILE=65536

[Install]
WantedBy=default.target
```

- **启动顺序**只用 `After=` 排先后（只写同一台主机上的组件），不等就绪。依赖没起来时组件自己重试，重试不了就退出，由 systemd 5 秒后再拉起。Collector 启动时核对内置任务的元数据，连不上 Storage 时每 5 秒重试，不退出。
- **进程看护**：systemd 只在进程退出时重启（`Restart=always`）；主机重启后靠 linger 开机拉起。卡死但不退出的进程不会被自动重启，由 Monitor 报“停止上报”或“未就绪”。
- **停用与恢复**：长期停用写进 `moox.toml` 的 `[deployments_disabled]`（或主机的 `enabled = false`），部署时只更新文件、单元停掉。`moox-cli setup stop` / `setup start-component`（`systemctl --user disable --now` / `enable --now`）只是临时启停，下次部署按声明重新拉起。
- **环境文件**里有 `MOOX_NODE_ID`、`MOOX_SERVICE_NAME`、`MOOX_INSTANCE_ID`（`<组件>@<主机>`）、EventBus 地址与凭据位置，以及打开了 `logging.cls` 时的写入密钥（只给声明了 `cls` 凭据的组件）。
  启动标识（`MOOX_BOOT_ID`）由进程启动时自己生成，二进制摘要由进程对自己的可执行文件算一次，部署都不注入。
- **日志**：tRPC 的文件日志在 `logs/<组件>/trpc.log`，用它自带的按大小轮转（单个 50MB、保留 5 份、最多 7 天）；标准输出与标准错误（崩溃信息、启动失败的原因）交给 journald。
  `moox-cli setup logs --host <主机> [--component <组件>]` 先读文件日志，没有再读 `journalctl --user -u moox-<组件>`；`--journal` 只读 journald。journald 没有持久化时重启后看不到之前的输出，部署时会提醒。
- **手工调过的配置**写在 `moox.toml` 的 `[overrides."<组件>"."<配置文件名>"]`，每行是 `"键路径" = 值`，渲染之后逐项覆盖，键路径不存在就报错；重新部署不会丢。只支持改已有的单值键，不支持删键和数组元素。
- **主机策略缓存** `<部署根>/data/host-agent/host-policy.json`（0600）：HostAgent 每分钟从 Monitor 拉取告警渠道（`GetHostPolicy`），拉取失败保留旧文件；Admin 的证书巡检读它推送告警，控制面不可用时也能发出去。

在目标主机上直接看：

```bash
systemctl --user list-units 'moox-*'
systemctl --user status moox-collector
journalctl --user -u moox-collector -n 100 --no-pager
curl -s http://127.0.0.1:11412/readyz          # 健康端口只听本机
cat /data/moox/version.json
```

日常不用上机：`moox-cli setup status`、`setup logs`、`setup restart|stop|start-component`、`doctor diagnose --node <主机>` 都经 SSH 代做。

**清空**：`moox-cli setup wipe` 逐台停用并删除全部 `moox-*` 用户服务，杀掉可执行文件在部署根里的全部进程，清空部署根下的内容（保留目录本身），再删掉这台电脑上的操作员身份与缓存的管理台根证书。
归档文件（`archive/`）和内置对象存储的数据（`data/seaweedfs/`）都在部署根下，会一起清掉，预览里单独列出它们的大小；管理台里改过的密钥只在线上有，清空前先在管理台导出。

### 因子机上的组件

`factor-engine` 与 `archive-worker` 是服务目录里的外部程序组件，和其他组件一样由 `setup deploy --host factor` 部署成用户服务，它们是普通调用方：用因子机的主机密钥、以自己的组件 ID 签名，从本机网关取目录，再直连存储机与控制机的 `11003`。

- **因子引擎的内存与窗口**：模板默认回看 50000 根（`window.lookback`）、计算内存 4GiB（`compute.max_memory`）、进程预算不限。配置每次部署都从模板重新渲染，调过的值必须写在 `[overrides."factor-engine"."engine.yaml"]` 里才会保留；
  在因子机上运行 `/data/moox/bin/moox-factor-engine tune --config /data/moox/config/factor-engine/engine.yaml` 看按本机内存给出的建议值。内存装不下一期计算时整期 `factor_memory_budget_exceeded`。
- 引擎重启后各任务要重新载入本地窗口（耗时随标的数与回看根数增长，几百个标的、5 万根回看是分钟级），期间显示“未就绪”，载入完成后自动继续计算；避开整点前后重启。
- 归档对象存储：没有 `[archive_object_store]` 时这台主机多一个内置对象存储组件 `seaweedfs`（见下文“归档对象存储”）；有这一段时，部署从 Admin 读出其中 `secret_id` 指向的密钥，写成 `secrets/archive-object-store.env`（0600），并渲染 worker 的 `object_store` 段。worker 侧的行为见[归档](模块/归档.md)第 9 节。
- 健康检查：健康端口只听本机（因子引擎 11417、归档 Worker 11418），`moox-cli doctor` 经 SSH 在目标机上请求 `/readyz`；离线由 factor-mgr、archive-mgr 按心跳评估并告警（见[监控](模块/监控.md)第 12 节）。
- 因子引擎的 EngineControl 端口 `11423`：策略回放的“因子现算”用，只听 `127.0.0.1`，由因子机的主机网关按服务目录的路由转发（回放的三个方法只给 strategy，生命周期、任务检查与本地写入的方法只给 `moox-cli`；都经 control 中转进入），不在防火墙放行。
- 归档 Worker 的数据端口 `11428`：管理台的分区下载与最新数据预览用，只听 `127.0.0.1`、不验签、不在防火墙放行，外部只能经 control 中转进入（服务目录 `relay_http` 只放行调用方 `console`，见[主机网关](模块/主机网关.md)第 5 节）。
  只支持 worker 装在 control（Admin 直连本机）或只出站主机（经中转）上，装在其他可直达主机上时这两个功能返回“归档执行器所在主机不支持网页下载与预览”。下载限速 `data_api.max_bytes_per_second` 默认 2MB/s，同时最多 2 个。
- 归档的库结构、目录规则或运行类型变了时不写升级 SQL，按“全新部署归档”清空 archive-mgr 的库、worker 的归档目录与对象存储里的旧对象后重建任务、从 Storage 保留期内回补（步骤见[归档](模块/归档.md)第 8 节）。
- 只能出站的主机：`[hosts.<ID>]` 写 `reachability = "outbound"`，`address` 填内网地址（只作身份与证书 SAN）；它的网关主动与 control 网关保持反向连接，
  进入它的连接都经 control 中转（见[主机网关](模块/主机网关.md)第 5 节）。control 的 `11003` 与 EventBus 所在主机的 EventBus 端口需要对公网开放（凭 TLS 与签名认证，不按来源 IP 放行），由 `setup firewall` 放行。

### 归档对象存储

archive-worker 每次导出分区后把文件单次 PUT 到标准 S3 接口的对象存储，代码里没有厂商专有接口，换后端只改配置。
默认用随 archive-worker 一起部署的**内置 SeaweedFS**，什么都不用配；`moox.toml` 写了 `[archive_object_store]` 段时改用外部 S3（腾讯云 COS 的做法见下面 A～G）。

#### 内置 SeaweedFS（默认）

内置对象存储是服务目录里的一个第三方组件 `seaweedfs`（二进制 `weed`，固定版本，版本与官方安装包的 sha256 见 `scripts/build/seaweedfs-sha256.txt`，构建时由 `scripts/build/fetch-seaweedfs.sh` 下载并校验，缓存在 `~/.cache/moox/seaweedfs/`；Apache-2.0）。
它不写在 `[deployments]` 里：装了 `archive-worker` 且没配 `[archive_object_store]` 的主机自动带上它，不登记到 Admin、不签名、不上报。`setup deploy --host <因子机>` 时：

1. `weed` 装到 `<部署根>/bin/`，数据在 `<部署根>/data/seaweedfs/`；
2. 第一次部署时在机器上生成访问密钥 `<部署根>/secrets/seaweedfs/s3-credentials.env`（0600，不打印、不经过 Admin），之后一直沿用；每次部署由它派生 `secrets/seaweedfs/s3.json` 和 worker 的 `secrets/archive-object-store.env`；
3. `s3.json` 只有一个身份 `moox-archive-worker`，不给简单动作，只挂策略：在 `moox-archive/` 前缀下 `PutObject`、`GetObject`，对桶 `ListBucket`。SeaweedFS 的简单动作 `Write` 含删除，所以必须用策略才能“能写不能删”；
4. 用户服务 `moox-seaweedfs` 排在 `moox-archive-worker` 之前启动：所有端口只听 127.0.0.1——master 11470、volume 11471、filer 11472、S3 11473，gRPC 21470～21473；关掉遥测（`-master.telemetry=false`）、Iceberg 与 Lance，日志进 journal（`moox-cli setup logs --host <因子机> --component seaweedfs`）；
5. 等它就绪后建桶 `moox-archive`（已有就跳过），worker 配置的对象存储指向 `127.0.0.1:11473`、path 风格、不用 HTTPS、不设存储类型。

worker 停用（`[deployments_disabled]` 里写上 `archive-worker` 后部署）时 SeaweedFS 照常运行；改用外部 S3 后再部署这台主机，`moox-seaweedfs` 会被停掉并删除服务，数据留着。从源码目录部署时，`--binary-dir` 里除了 `moox-archive-worker` 还要有 `weed`（`build-linux-local.sh` 的 `archive-worker` 目标会带上它）。

**它防什么、不防什么**：和归档文件同盘，只防误删和本地文件损坏，不防整机或整盘故障；要异地副本就换外部 S3。

**冒烟与清理**：在因子机上 `/data/moox/bin/moox-archive-worker objectstore-check --config /data/moox/config/archive-worker/app.yaml --large`，第 1、3～7、10 步要通过（第 6、7 步必须是 403），第 2 步因为没设存储类型跳过，第 8 步（virtual 风格）在回环地址上解析不了是正常的。
冒烟对象没有生命周期规则，用完手工删：`echo "fs.rm -r /buckets/moox-archive/moox-archive/_smoke" | <部署根>/bin/weed -logtostderr=true shell -master=127.0.0.1:11470 -filer=127.0.0.1:11472`。

**健康**：worker 每分钟对一个不存在的键做 HEAD，连不上或被拒就上报不可用；超过 5 分钟 Monitor 推送“归档对象存储”告警（外部 S3 也一样），`archive overview` 的 `worker.object_store` 带着原因。

#### 外部 S3（可选）

以下 A～G 由用户在腾讯云控制台操作；标“核对”的条目以控制台和官方文档为准。

**A. 建桶**（对象存储 → 存储桶列表 → 创建存储桶）

1. 地域：南京（`ap-nanjing`）；名称 `moox-archive`，系统会加上 `-<APPID>`，记下完整桶名（例如 `moox-archive-1250000000`）和 APPID。
2. 访问权限：私有读写。
3. 版本控制：不开（对象键里带 sha256，不依赖版本控制；开了的话不要配“非当前版本 N 天后删除”）。
4. 服务端加密：不开（开了以后 ETag 不一定等于内容 MD5，上传后的核对会一直失败；确实要开，必须在冒烟之前开好，以冒烟第 1 步通过为准）。
5. 不需要配置跨域、防盗链、静态网站。

**B. 生命周期规则**（存储桶 → 基础配置 → 生命周期）：只建一条，作用于前缀 `moox-archive/_smoke/`，上传 1 天后删除（清理冒烟对象）。**不要**建作用于整个 `moox-archive/` 的删除规则。

**C. 存储类型**：配置项 `storage_class = "STANDARD_IA"`（低频，约 0.08 元/GB·月，最少存 30 天，取回 0.02 元/GB），由冒烟第 2 步与控制台对象详情确认生效。不要用归档或深度归档（要先解冻，不适合读回）。
桶级的默认存储类型设置是否存在没能确认（核对）；有的话与配置项二选一。

**D. 写入用的子账号**（访问管理 CAM）

1. 策略 → 新建自定义策略 → 按策略语法创建，名称 `moox-archive-writer`（`<APPID>` 换成实际值，动作名与资源格式按 COS 的 CAM 文档逐条核对）：

   ```json
   {
     "version": "2.0",
     "statement": [
       {
         "effect": "allow",
         "action": ["name/cos:PutObject", "name/cos:GetObject", "name/cos:HeadObject"],
         "resource": ["qcs::cos:ap-nanjing:uid/<APPID>:moox-archive-<APPID>/moox-archive/*"]
       }
     ]
   }
   ```

   只给 `moox-archive/` 前缀；不给删除、ACL、桶配置与列举权限；只用单次 PUT，不需要分片上传的动作。“不给删除”挡不住同键再 PUT 覆盖，真正的防线是对象键里带内容 sha256 加每天的维护抽查。
2. 用户 → 新建用户 → 自定义创建 → “可访问资源并接收消息”，访问方式只勾**编程访问**，用户名 `moox-archive-writer`，关联上面的策略。
3. 完成页记下 SecretId / SecretKey（SecretKey 只显示一次）。不要贴进对话，不要写进 `moox.toml`。

不需要只读子账号：管理台的分区下载由 worker 用上面这把写入密钥从对象存储读出，经 control 中转给浏览器，不用预签名地址。

**E. 录入管理台**：“系统设置 › 密钥管理”新建一条——名称 `归档对象存储（写入）`，分类 `其他`，提供方 `s3`（小写，按 S3 接口而不是按厂商，换后端时只换值），类型 `API 密钥对`，
标识填 SecretId（即 S3 的 Access Key ID），秘钥值填 SecretKey（Secret Access Key）。记下列表里的 `secret_id`。

**F. 填配置**：换上新的 moox-cli 后，在 `moox-cli config edit` 打开的本机配置页里打开“归档对象存储”一组，填对象存储地址 `cos.ap-nanjing.myqcloud.com`、地域 `ap-nanjing`、桶名、前缀 `moox-archive/`、地址风格 `virtual`、HTTPS、存储类型 `STANDARD_IA`、上一步的 `secret_id` 并保存
（`config set` 只能改已有的键，第一次加这一段只能走配置页；之后单个字段可以 `config set archive_object_store.<键>=<值> --yes`）。有多份 `moox.toml`（多套环境）时每份都要填，改完用 `config get archive_object_store` 回读。

**G. 冒烟**（上线之前，用受限的子账号密钥，不用主账号）：本机 `scripts/build/build.sh archive-worker` 编出 worker，在 `~/Documents` 之外写一份只含 `object_store` 段的临时配置和 0600 的临时凭据文件（凭据由用户自己写，不经过对话），
运行 `moox-archive-worker objectstore-check --config <临时配置> --large`：第 1～7 步与第 10 步（HEAD 不存在的键返回 404）必须全部通过，第 8 步（换地址风格）与第 9 步（预签名下载）记下结果补进[归档](模块/归档.md)；到控制台看 `_smoke/` 下的对象是低频存储、自定义元数据里有 sha256；最后删掉临时凭据文件。
上线后在因子机上可用 `/data/moox/bin/moox-archive-worker objectstore-check --config /data/moox/config/archive-worker/app.yaml --key <remote_key> --sha256 <file_sha256>` 核对单个分区。

## 4. 网络与信任

| 入口 | 使用方与安全机制 |
| --- | --- |
| HTTPS `9527` | 浏览器 → Admin 自己监听的入口：管理台页面、根证书下载 `/ca/*` 与 `/api/admin/*`；Host 必须是控制机地址，其余 `/api` 与健康路径一律 404 |
| loopback `11002` | 本机组件取目录（Directory）；操作员 SSH 隧道进来的签名 tRPC。同机组件互调不经它，直连服务的回环端口 |
| TLS `11003` | 跨主机签名 tRPC；MooX 私有 CA、目标主机 ID 校验；同端口按 ALPN 接受出站主机的反向连接（attach 要求带 `ClientAuth` 的网关证书）与签名的中转流 |
| tRPC `11004` | 主机网关的外部入口（只有登记成外部入口的主机监听）；SCF、Skill、采集名单工具各自的身份与方法白名单，nonce 记在网关内存里；该入口本身不提供 TLS |
| TLS `4222` | EventBus；按发布/消费角色鉴权 |

普通业务 RPC 与全部健康端口都绑定 127.0.0.1；健康端口不验签，渲染不改写监听地址（`modules/cli/internal/setup/deploy/render.go`），
契约测试 `packages/servicecatalog/health_loopback_contract_test.go` 逐个组件核对模板。防火墙不放行任何健康端口。
要看某台主机上组件的 `/readyz`，用 `moox-cli doctor`（经 SSH 在目标机上请求本机端口），或 SSH 上去 `curl http://127.0.0.1:<端口>/readyz`。
因子机只能出站，SSH 只有在家里的局域网才连得上，所以它的 doctor 与 `/readyz` 检查只能在局域网里做；
不在局域网时看 Monitor 的上报状态（`moox-cli doctor alerts`）和 `moox-cli host agent status --host factor`。

只有一个 CA：MooX CA 给每台主机签一张主机证书（5 年），主机网关的 11003 和 EventBus 的 4222 都用所在主机的这张证书；
它也给管理台 9527 签网页证书（Admin 自己签，1 年，剩余不足 30 天自动重签）。管理台没有域名，浏览器要信任的就是 MooX CA 根证书，由操作员核验并安装信任。
MooX CA 由离线 bootstrap 创建一次，之后只校验不补建；丢失时拒绝自动重建。

主机证书的 SAN 是主机 ID、`moox.toml` 里登记的对外地址与内网地址，加上回环地址（同机组件经 `127.0.0.1` 连 EventBus）。
`setup deploy --host <主机>` 每次都重新签发这张证书并覆盖 `secrets/host.crt`、`secrets/host.tls.key`，但不会因此重启主机网关和 EventBus，新证书在它们下次重启时生效。
Admin 每天巡检全部主机证书，到期前 90 天起告警。续签的做法：

```bash
moox-cli setup deploy --host <主机>                                   # 签发新证书（再有 5 年）
moox-cli setup restart --host <主机> --component host-gateway --yes   # 主机网关换上新证书
moox-cli setup restart --host <主机> --component eventbus --yes       # 只有 EventBus 所在主机要做；各客户端会自动重连
```

根证书不变，别的主机什么都不用动。主机改了地址也是同样的做法（先改 `moox.toml`）。

## 5. 配置发布与凭据

签名身份分两类：每台主机一把 ed25519 主机签名私钥（`secrets/host.key`），本机全部组件共用，私钥不离开这台主机，Admin 只登记公钥；
部署之外的程序（`moox-cli`、`moox-skill`、`scf-collector`）各有一把自己的私钥，公钥登记在 Admin。
`moox-cli` 的信任根是操作电脑到控制机的 SSH 私钥：能 SSH 上控制机，就能登记一把新的 `moox-cli` 公钥（`setup operator --register`）。
Storage 没有调用方密钥，服务端口只监听本机，访问控制由主机网关按服务目录做。

配置随部署渲染：`moox.toml` 变更后对受影响的主机执行 `setup deploy --host <主机>`；
Primary 保留期缩短会在下一次 Storage 清理时删除超期事实，安装前先确认；View 的 `max_age` 缩短只过滤后续写入，不会立即删除已有索引行。

EventBus 的角色令牌由 Admin CLI ensure/export/rotate 管理；轮换后重新部署 EventBus 所在主机和用到这个角色的主机，新令牌随部署下发。云函数不连 EventBus，没有要同步的凭据。
EventBus 没有自己的证书和 CA：服务端证书就是它所在主机的主机证书，客户端（角色文件里的 `ca_file`）用 `secrets/moox-ca.crt` 校验，认证与主题权限仍按角色令牌。
EventBus 换主机不用轮换任何东西：改 `moox.toml` 后先部署新的 EventBus 所在主机，再逐台部署其余主机（角色文件里的地址跟着换）。broker 的用户表只随 `eventbus` 组件下发，别的组件不带。
调用方签名密钥没有新旧并存：一个身份只有一把公钥，换了之后旧私钥立即作废。

| 要换的 | 做法 | 影响 |
| --- | --- | --- |
| 一台主机的签名密钥（存储机、海外机、因子机） | `moox-cli setup deploy --host <主机> --rotate-host-key` | 这台主机上的组件全部重启；别的主机网关在下一次快照（约 5 秒）认新公钥 |
| 控制机的签名密钥 | 删掉控制机上的 `<部署根>/secrets/host.key`，再 `moox-cli setup deploy --host <控制机>` | 控制机上的组件全部重启 |
| 云函数的密钥（`scf-collector`） | 删掉控制机上的 `<部署根>/secrets/scf-collector.key`，再 `moox-cli setup deploy --host <控制机>` | 新公钥随快照下发，各网关几秒内认到；采集计划的下一轮对账把新私钥写进函数环境，这期间函数的写入会被拒 |
| 操作电脑（`moox-cli`） | 新电脑上放两份配置文件、SSH 私钥、解密密钥，`moox-cli setup operator --register`，再 `moox-cli setup deploy --host <控制机>`（取回根证书） | 原电脑随即不能用，两台电脑不能同时用 |
| `moox-skill` | 先删掉操作电脑上的 `~/.config/moox/moox-skill.key`，再 `moox-cli setup export-skill-config`。私钥固定在这个文件里，已有就复用；只换输出目录是再抄一份同样的配置，不换密钥 | 之前导出的 Skill 配置都不能用 |

`moox-admin-cli keys list` 列出登记着的公钥；它不保存任何签名私钥。

### Storage 主机内存要求

`moox-storage-view` 为每个 DuckDB 索引配置内存预算，但代码没有进程级总预算；这些设置不能作为进程 RSS 的硬上界。
`storage-view` 的常驻内存通常是 View 文件总大小的数倍，首次建索引时还要为最大的那个索引再留一份。
估算时按「View 文件之和的数倍 + 最大索引的一到两倍 + 同机其他进程的实测占用」再留余量，具体倍数以本机实测的 RSS 为准。
这只是量级上的指导，不是源码保证的线性关系或内存上界；新建 View、扩大标的范围或调大 `view_rows_per_series` 之前，须结合实际字段、查询、写入和建索引并发测量，余量不足先升配或缩小 View。
细节与估算方法见 [存储模块](模块/存储.md) 的“内存占用与硬件要求”。

## 6. 数据保留

| 数据 | 当前默认行为 |
| --- | --- |
| 行情与因子事实 | `[storage_retention]` 按空间和频率解析；按天桶清理，实际可能多保留不足一天；record 数据不过期 |
| 主机快照历史 | Monitor 的 SQLite（`t_monitor_host_samples`）保留 7 天，随 Monitor 数据清理删除 |
| View 索引 | 每个序列保留最近 `view_rows_per_series` 根，默认 10000，更旧的行每 2 分钟定时删除一轮（偶数分钟第 10 秒）。`[storage_view.max_age]` 按空间 × 频率过滤早于处理时刻截止点的新写入，等于截止点保留；不主动清理已有旧行，也不保证实际保留 N 根 |
| Monitor 检查结果和告警事件 | 默认 14 天；每 6 小时清理 |
| Monitor 数据链路逐根到达记录 | 7 天（按到达时间）；每 6 小时清理 |
| Strategy | 定义版本、会话、结果保留；解释明细默认 90 天；已结束回放默认 90 天且每空间最多 50 个 |
| Trade 订单与成交 | 模拟账户按账户自己的订单保留天数清理已结束的订单与成交（默认 5 天，0 表示不清理，上限 365 天）；实盘账户不清理 |
| Archive CSV 分区文件 | 不自动删除 |
| EventBus | 各 Stream 独立设置保留时间与容量，见[事件总线](模块/事件总线.md) |

Storage 策略在 `<部署根>/config/storage-primary/storage-policy.json` 与 `config/storage-view/storage-policy.json`，由部署从 `moox.toml` 渲染。缩短 Primary 保留期会在清理时删除超期事实，
需要在发布前核对；缩短 View 的 `max_age` 只影响后续写入，既有旧行可能持续可见，直到 View 重新建索引时被过滤。SQLite 空闲页和 Pebble 删除标记的磁盘回收还取决于复用或 compaction。
日志：各组件的 tRPC 文件日志在 `<部署根>/logs/<组件>/trpc.log`，用它自带的按大小轮转（单个 50MB、保留 5 份、最多 7 天，大小与份数写在各组件的 tRPC 配置模板里）；
标准输出与标准错误（崩溃信息、数据库日志）交给 journald，由 journald 自己的容量上限管理。本机文件日志的轮转不在 `moox.toml` 里配置；`moox.toml` 的 `[logging]` 只管腾讯云日志服务的保留天数与服务日志上报（见下文）。

### 清空全部数据重新积累

整体清空行情与因子数据（例如测试环境换方案）要按下面的顺序做，四步缺一不可：

1. 停止因子引擎（因子机上的 systemd 用户单元 `moox-factor-engine`）：它持有账本文件，还会往 Storage 写结果。
2. **清 Storage**：停掉存储机上的两个 Storage 组件（`moox-cli setup stop --host <存储机> --component storage-view --yes`，再 `storage-primary`），在存储机上删除 Pebble 目录与 View 索引目录
   （`rm -rf /data/moox/data/storage-primary/pebble /data/moox/data/storage-view/view-indexes`），再恢复（`setup start-component`，先 `storage-primary` 后 `storage-view`），用 `setup status` 与 `doctor diagnose --node <存储机>` 确认就绪。
   全部行数据（含已登记的序列快照）都会被清掉，数据集、View、标的等定义保留；View 按空索引重建后跟随新写入。
   Storage 停机期间 Collector、因子引擎的写入会失败几分钟，可能留下短缺口，由自动补采和因子缺口保护处理。
3. **让 Collector 重新登记**：对每个有采集计划的空间执行 `moox-cli collector fetch-plan reregister --space-id <空间> --yes`。
   Pebble 里登记的序列快照在第 2 步被一并清掉，而对账只在数据集标的集合变化时才重新登记，不做这一步实时采集的周期提交会一直被拒绝
   （症状：补采能写入、实时采集不写入）。命令把已生效计划里的数据集标记为“快照未登记”，约 1 分钟内对账生成新计划并登记；
   1m 数据集约 2 分钟后恢复写入，1h 数据集等下一个整点，计划在最后一个整点之后才算生效。同时清掉该空间的补采作业、自动补采水位与历史扫描记录；
   此后检查、自动补采与历史扫描都从新计划的生效周期起算，清库前的计划段不再参与。
   空间里还有未生效的计划时会拒绝，等它生效后重试。
4. **清因子缺口账本并启动引擎**：在因子机上执行 `/data/moox/bin/moox-factor-engine reset-gap-ledger --config /data/moox/config/factor-engine/engine.yaml --yes`（引擎还在运行时拒绝执行），然后启动引擎。
   账本里的待恢复项指向已经不存在的数据，不清的话恢复一直白跑，超过 `gap.give_up_after` 还会告警。

清完之后的预期：停机的几分钟和第 3 步生效前会有一小段缺口；因子任务要等回看窗口积累够才能出完整结果（回看长度由因子自己决定，
1m 因子任务约 1 小时，1h 因子任务可达两天多），期间这些数据集在页面上显示“数据积累中”（降级），但不告警：因子引擎把预热中的运行报告为 `partial`，策略把历史不足（`history_insufficient`）、上游因子被跳过的周期报告为 `partial`，Monitor 的新鲜度检查据此按通过记录。策略的积累期有上限（`min_age_bars` 对应的时长与 72 小时取较大者，再加一小时），超过仍然不足说明不是在积累，回到失败与告警。

### SCF 定时触发采集（Timer 模式）配置

SCF 采集统一使用 Timer 模式：函数的数量、标的分配和定时器由 Collector 的对账协程按任务与标签成员自动创建和维护，运维只需要声明“哪些空间的哪些市场在哪些地域运行”。在 `moox.toml` 里写 `[scf_plan]`（示例见 `moox.toml.example`）：

- **空间与市场**：`[[scf_plan.spaces]]` 的 `markets` 把市场（`spot`、`swap`、`equity`……）映射到运行地域；`package_name`（默认 `moox-collector-<space>-plan`）与 `namespace`（默认 `moox-<space>-plan`）可覆盖。
- **地域网络**：`[scf_plan.regions.<region>]` 分两种。默认是 vpc：给出函数所在 VPC 与子网，函数通过同地域主机的私网地址访问外部入口（主机网关的 `11004`），所以该地域必须有一台配置了 `region` 与 `private_address`、并写了 `external_entry = true` 的主机，入口地址与入口主机 ID 由此自动推导。没有 MooX 主机的地域写 `network = "public"` 和 `entry_host`（不写 VPC 与子网）：函数不绑 VPC，经公网连入口主机的 `11004`，入口主机的安全组要对公网放行这个端口。
- **云账号**：`[scf_plan.cloud_account]`。
- **入口主机**：同地域只有一台带私网地址的入口主机时自动选用；有多台时必须用 `scf_plan.regions.<region>.entry_host` 指定。
- **关闭与移除**：`[scf_plan]` 只管云函数，关闭它不影响推送采集：空间有启用的 K 线任务，Collector 就会生成采集计划。采集方式是 `scf` 的任务要先切到 stream（`moox-cli collector ingest-mode set --ingest stream`），否则对账报 `no SCF region`，已有定时器继续运行。空间不再有启用任务、也没有计划时，Collector 会先把它的函数定时器停用并读回确认再退出。

自动完成的部分：

- `setup deploy --host <控制机>`：渲染 Collector 的 `scf_regions`、`scf_markets`、`scf_plan`。代码包只写**名称**，Collector 每轮解析该名称的最新可用版本；函数环境（空间、外部入口地址、`scf-collector` 的签名私钥、日志服务配置）由 Collector 建函数或改环境时生成，没有要手工维护的环境文件。
- `setup init`：登记云账号、开通日志服务，并为每个空间检查代码包：已有可用版本就沿用，没有则构建上传。失败不阻断初始化，结果在摘要的 `scf_plan` 里。
- **代码升级**：执行 `moox-cli collector function upload --package-name <名称> ...`。Collector 在一分钟内解析到新版本，落后的函数自动升级，不需要改配置或重启。

### 服务日志上报 CLS（可选）

各服务的错误日志总是发给 Monitor，在管理台“日志中心”的“重要日志”页签里看，不需要配置。下面配的是把各服务**警告及以上的日志和关键事件**（进程启动、暂停与恢复等）另外上报到 CLS，方便检索。
Info 级的逐条处理日志默认不上报（量大约是 10 倍，用处小），留在各主机的本机文件里；确实需要时把 `logging.cls.min_level` 改成 `info`。

费用（腾讯云按量计费，单价以腾讯云的 CLS 计费页为准）由四部分组成：

| 计费项 | MooX 的用量 |
| --- | --- |
| 日志主题的分区 | 每个主题 1 个分区，按天收固定费用，每多一个主题多一份 |
| 服务请求次数 | 有日志时各进程定时批量上报，默认级别下很少 |
| 索引流量 | 随上报的日志量，默认级别下很小 |
| 写流量、日志与索引存储 | 随日志量与保留天数（默认 2 天） |

也就是每个日志主题一份很小的固定费用，加上随日志量变化的按量部分；把 `min_level` 调到 `info` 后按量部分约为默认的 10 倍。云函数采集日志用的主题 `moox-application` 是初始化时就开通的，服务日志的主题 `moox-service` 是这里新增的一个。
日志保留天数在 `moox.toml` 的 `[logging] retention_days`（默认 2，初始化页面上可以改），只在创建日志主题时生效；已经建好的主题要到腾讯云控制台改。

1. 创建日志主题：`moox-cli ops tencent cls bootstrap --topic-name moox-service --retention-days 2`（天数与 `[logging] retention_days` 保持一致）。这条命令要用云账号的管理密钥，从环境变量 `TENCENTCLOUD_SECRET_ID` / `TENCENTCLOUD_SECRET_KEY` 读取，或用 `--secret-id`、`--secret-key` 传入；记下输出里的主题 ID。命令输出里的 `writer.host` 是腾讯云内网域名（`<地域>.cls.tencentyun.com`），只有同地域的云主机能用；我们的主机分在不同地域，第 4 步的 `endpoint` 填外网域名 `<地域>.cls.tencentcs.com`。
2. 在腾讯云“访问管理”里新建一个子账号，只授予这个主题的日志上传权限（`cls:pushLog`），给它建一对 API 密钥。**不要用云账号的管理密钥**：这对密钥会下发到每台主机。
3. `moox.toml` 里没有这一段时照 `moox.toml.example` 补上（写入密钥在 `moox.secrets.toml` 的 `[logging.cls]`）。
4. 填值：`moox-cli config set logging.cls.endpoint=<地域>.cls.tencentcs.com --yes`，同样设置 `topic_id`；写入密钥在秘密文件里：`moox-cli config set --file ./moox.secrets.toml logging.cls.writer_secret_id=<值> --yes`、`writer_secret_key` 同理；最后 `logging.cls.enabled=true`。`min_level` 默认 `warn`。这几条 `config set` 一条一条执行，不要写成脚本连着跑：每次写回都会按秒备份原文件，同一秒内两次会撞名。
5. 逐台重新部署（`moox-cli setup deploy --host <主机>`，声明了 `cls` 凭据的组件的环境文件里会多出 `MOOX_LOG_CLS_*`，这些组件会重启）。之后在 CLS 控制台按 `component`、`host`、`level`、`caller` 检索。

上报走明文 HTTP（腾讯云 SDK 写死），日志里不要写密钥和完整的 Webhook 地址。没有启用时服务照常运行，只是没有这一路。上报失败（密钥、主题或权限不对）不影响服务，也不告警：各组件的标准输出（journald，`setup logs --journal`）里每分钟记一行 `logsink: cls 一路发送失败`，进程的 `/metrics` 里 `moox_logsink_dropped_total{path="cls"}` 会增长。启用后要到 CLS 控制台确认日志确实到了。

### 日志服务（CLS）自动开通

SCF 采集函数的日志不会自动投递，排查“某个标的某一分钟为什么没采到”依赖函数主动上报的 CLS 日志，因此开通和下发不需要人工参与：

- **初始化时开通**：配了云函数采集（`[scf_plan]`）时，`moox-cli setup init` 在登记云账号之后，用该账号幂等开通 CLS（服务、日志集 `moox`、主题 `moox-application`），并补齐采集日志字段的键值索引。开通失败不阻断初始化，结果在摘要的 `cls` 里（`status=failed` 时修复权限后重跑即可）。
- **建函数、改环境时下发**：Collector 每次建采集函数或改它的环境时，把上报环境变量（`MOOX_CLS_*`）补进函数环境，首次使用时同样幂等开通；已声明 `MOOX_CLS_ENABLED` 的函数保持不动。这是尽力而为的附加动作：开通失败、补齐后环境超过平台 4KB 上限都只记日志并保持原环境，只换代码、只改定时器不触发它。由 Collector 配置 `cloud.cls` 控制（默认开启）。**建议配置专用的只写凭证**（`cls.writer_secret_id` 与 `cls.writer_secret_key_file`，CAM 子账号只给该主题的日志写入权限）：开通仍用云账号管理密钥，函数环境里只放写入凭证；不配置时退回把管理密钥放进函数环境，并记告警。
- **上报内容**：
  - `market_fetch_item_failure`：失败项，含错误全文、尝试次数、取数耗时。
  - `market_fetch_batch`：批次摘要，含条数、失败数、取数耗时、剩余窗口、已用权重，以及取数项的阶段耗时汇总：`since_close_start_ms`／`since_close_fetch_end_ms`（批次开始、取数结束相对收盘的毫秒数，仅周期提交请求有）、`item_p50/p90/max_ms`（单项取数耗时）、`queue_max_ms`（等并发名额）、`dns_max_ms`、`connect_p90/max_ms`、`tls_p90/max_ms`、`ttfb_p50/p90/max_ms`（写完请求到收到响应首字节，即行情源处理与网络往返）、`attempts_total`、`retried`（尝试次数或 HTTP 请求数大于 1 的项数）、`http_requests`、`conn_new`／`conn_reused`。
  - `market_fetch_item_slow`：单项取数超过 1 秒或重试过的项，每批最多 8 条（最慢的优先），含 `fetch_ms`、`queue_ms`、`attempts`、`http_requests`、`dns_ms`、`connect_ms`、`tls_ms`、`ttfb_ms`、`http_status`、`endpoint`、`remote_addr`、`since_close_start_ms`。正常请求不逐项上报，避免日志量随标的数增长。
  - 失败的 HTTP 尝试：批次摘要带 `fail_total`（失败尝试数）、按原因的 `fail_timeout`／`fail_reset`（对端重置或提前关闭）／`fail_tls`／`fail_dial`／`fail_status`／`fail_other`、按阶段的 `fail_in_connect_phase`（建连前：DNS、拨号、TLS、等连接）／`fail_in_wait_response`（已发出请求没有首字节）／`fail_in_io_phase`、`fail_on_reused_conn`（失败发生在复用的旧连接上，用来判断是否空闲连接已被对端关闭）、`fail_ms_p50`／`fail_ms_max`；偏慢单项的 `attempt_trace` 逐次列出“域名:阶段:原因或状态码:耗时:new 或 reused<空闲毫秒>”，用分号分隔。
  - 取数阶段的更多线索：偏慢单项的 `attempt_trace` 每次请求后接 `|` 明细：`dns`、`c`（TCP 建连）、`t`（TLS）、`w`（发起到请求写完）、`f`（写完到首字节，-1 表示没有首字节）、`ip`（对端地址）、`pop`（CDN 节点 x-amz-cf-pop）、`cache`（x-cache）、`skew`（服务端 Date 与本机收到时刻之差，毫秒）、`body`（非 200 响应体前 100 字节，如 202 的内容）。批次摘要另带函数进程与触发的上下文：`timer_late_ms`（函数入口晚于定时事件计划时间多少）、`entry_to_start_ms`（入口到开始取数，含建立到外部入口的连接与等到收盘后取数时刻）、`proc_age_ms`（进程存活时间，冷启动时很小）、`invocation_seq`（进程内第几次调用）、`num_cpu`、`sched_lag_max_ms`（取数期间调度唤醒最大迟滞，CPU 吃紧时变大）与 `goroutines_max`。
  - `market_fetch_commit`：批次写入 Storage 的 `commit_ms`、行数、数据集数与 `since_close_done_ms`（写入完成相对收盘的毫秒数），写入失败时带 `error`。
  - 字段清单在 `packages/cloudprovider/tencent/cls_fields.go` 统一维护，collector 测试保证上报字段都在索引里。新增字段需要对已有主题补齐键值索引（`moox-cli ops tencent cls bootstrap` 幂等，或 Collector 下次开通时补齐），不补索引字段仍随原始日志保存，但不能按字段检索。
  - 排查整点慢：按 `function` 或市场分组，对比 `since_close_start_ms`、`item_p90_ms`、`connect_p90_ms`、`tls_p90_ms`、`ttfb_p90_ms` 与 `retried`，哪一项在整点前后明显变大，慢就在哪一段。
- **查询**：主题 ID 在初始化摘要里；`moox-cli ops tencent cls resolve` 可查询。检索时间使用毫秒。

## 7. 构建和验证

本机需要装什么、各系统（macOS / Linux / Windows）怎么准备、怎么构建与发布，见[构建手册](构建手册.md)。

```bash
make test-docs-architecture check-boundaries
pnpm docs:build
make test-deployment-packages test-host-deployment test-host-identity-bundles   # 组件包、部署渲染与安装脚本、身份包
make test                 # 工作区 Go 测试与 vet、前端测试和构建、UDF 的 Rust SDK 测试
make verify              # CI 的综合检查
```

PR 上的 CI 把 `make verify` 按耗时拆成并行的作业，由 `verify-pr` 汇总：`verify (core / contracts / storage / web)` 对应 Makefile 里的 `verify-ci-<组>` 目标，
Go 工作区测试单独切成三片（`MOOX_GO_SHARD=<第几片>/3 make test-go`）；只改了 `docs/` 的 PR 只跑文档检查。新增检查时放进 Makefile 的某一组，`make verify` 与各组自动保持一致。
本机的 `make verify` 和自托管运行器的 `verify-trusted` 仍然依次全跑。

Go 版本以 `.go-version` 为准。

安装脚本的用例（`modules/cli/internal/setup/deploy/install_test.go`）要 `flock`，只在 Linux 上执行（macOS 上跳过）：PR 的 CI 在 Linux 运行器上跑它，本机是 macOS 时在 Linux 容器里跑 cli 模块的测试。
`make test-e2e-gates` 起真实进程联调（`scripts/test/gates/run-e2e-gates.sh`）：EventBus 用主机证书的联调、策略到 Trade 的两条跨进程联调（`scripts/test/e2e/test-strategy-trade-event-e2e.sh`：目标经 NATS 进入 Trade 并由模拟盘成交；`test-strategy-trade-gateway-e2e.sh`：策略经目录与主机网关调 Trade）在各系统都跑；真实 Admin 加主机网关的联调要 Linux 的 `127.0.0.2`，只在 Linux 上执行，PR 的 CI 会跑。
本机测试通过不能替代跨主机和生产业务验收。

### 发布新版本

1. `scripts/release/build-release.sh` 构建产物，先发到 GitHub（标记 Pre-release）和 CNB。CNB 用 `scripts/release/cnb-release.py`，中断后重新运行会跳过已传好的附件，结束前按 SHA256 核对全部附件。这一步不标记最新，也不删除旧版本。
2. 新目录、干净的 HOME，用发布产物跑 `config init` 和 `setup install`。`setup verify` 通过、`doctor alerts` 为 HEALTHY 才算通过。
3. 通过后再改 `skills/moox/references/install.md` 的 `VER`，把 GitHub Release 标记为最新，再运行 `cnb-release.py promote <新版本> <旧版本或 none>`。没通过就修好发下一个补丁版本，不覆盖已发布的附件。

当前版本已知装不通时是例外：新版本直接发正式版并切 `VER`，等验收只会让新用户继续遇到已知问题。发布说明要写明还没有完成真机验收。

产物包和 `moox-cli` 的版本必须一致，否则报 `bundle_version_mismatch`。自己改代码重新构建时保留版本号，用文件名和构建提交区分。

升级后如果新版本增加了防火墙规则，运行一次 `moox-cli setup firewall --yes`（逐台 `setup deploy` 升级时不会补规则；`setup update` 和 `setup install` 会）。

### 升级线上组件

用新版本再部署一遍：全部主机用 `moox-cli setup update`（覆盖更新，先预览），单台用 `moox-cli setup deploy --host <主机> [--component <组件>]`，只重启二进制或配置有变化的组件，数据目录不动；回到旧版本就是用旧版本的包再部署一次。
用发布产物升级见 skill 的 `references/install.md`“升级到新版本”，从源码目录构建后部署见 `references/source-deploy.md`。

## 8. 常见故障与处理

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| Collector 日志出现 `RequestLimitExceeded`、`被腾讯云限频`，并反复出现 `collector fetch plan cannot read back` | 腾讯云 SCF 管理接口按「API + 接入地域 + 子账号」限频（`ListTriggers` 等为 20 次/秒）；Collector 已有按接口的进程内令牌桶，仍大量限频说明同一云账号被别的调用方占用，或令牌桶配置过高 | 读 Collector 本地 `/metrics` 的 `moox_collector_tencent_api_throttled_total` 与 `..._wait_seconds` 定位接口；用 Collector 配置的 `cloud.tencent_scf.api_rate_limits` 调低对应接口：写进 `moox.toml` 的 `[overrides."collector"."app.yaml"]` 后 `setup deploy --host <控制机> --component collector`（配置每次部署都从模板重新渲染，直接改目标机上的 `app.yaml` 只能临时用，下次部署会被覆盖）；排查同账号的其他调用方，如手工执行的 CLI 诊断命令。细节见[采集](模块/采集.md)第 10a 节 |
| 监控报“数据停止更新”，只有某个 View 的水位停滞，`storage-view` 日志反复出现“活动索引写入失败 … Duplicate key” | 一次 DuckDB 提交失败后该索引的内存状态与磁盘不一致，不会自愈 | 重启 `storage-view`；详见[存储 §6.4](模块/存储.md) |
| 新建（或启用）因子任务后，`storage-primary` CPU 长时间 300% 以上，引擎日志大量 `factor_read_batch_failed … i/o timeout` | Pebble 块缓存相对数据量偏小：窗口读取逐行逐列点查，缓存装不下时每次都重新解压数据块和索引块。块缓存按主机内存推算（见[存储 §6.5](模块/存储.md)）；启用成员不自动回填历史，补算同时只跑一个作业且读因子机本地存储（见[因子 §4](模块/因子.md)） | 看 `storage-primary` 日志里的 `Pebble 块缓存` 行：命中率长期偏低或占用顶满说明缓存偏小，用 `MOOX_STORAGE_BLOCK_CACHE` 调大；紧急时先停用该因子任务（控制台“计算任务”页或 `SetFactorTaskStatus`），负载立即回落。主机 CPU 持续高于 80% 约 3 分钟会触发主机 CPU 告警 |
| 监控报“collector-stream 心跳已中断”或某数据集连续多个周期缺标的，crypto 实时 K 线停写或大面积缺失 | `collector-stream` 进程挂了、海外机失联，或 WS 连接长时间失败 | 先用 `moox-cli setup status --host <海外机>` 看 `collector-stream` 是否在运行，再看它的日志与 `moox-cli collector ingest-mode get --space-id crypto` 的连接状态。短时间恢复不了就切回 SCF 拉取：分钟第 20～40 秒执行 `moox-cli collector ingest-mode set --space-id crypto --ingest scf --yes`，不用加任何强制开关：进程失联、心跳超时 180 秒后交接计划不等它确认（Collector 刚重启的 180 秒内仍会等）；记下各数据集的生效周期 P，P 之前缺的 K 线由补采补齐（切到 `scf` 后补采走云函数，不依赖已失联的本地执行端）。合约推迟取数的配置（市场参数里 swap 的 `not_before_ms`）一直保留，切回后自动生效。恢复后再切回 `--ingest stream --yes`。切换后因子水位会在缺数据的周期等待补采，补齐后自动追上 |
| 监控报“因子连续水位停滞” | 某任务前面有零提交或缺失超过阈值的周期，补采还没补上（或行情源确实没有） | 用 `moox-cli collector kline check` / `backfill` 补采该范围；补采成功后 Collector 通知因子补齐，水位自动前进。行情源确实没有的标的会在补采时确认，不再计入缺失比例 |
| 只部署了部分组件之后，Monitor 日志每分钟报 `SysDeploy catalog differs from this Monitor release`；新增的方法 `moox-cli` 调不通 | 服务目录（`packages/servicecatalog/catalog.yaml`，增删方法、调整调用名单都算）内嵌在 Admin、Monitor 和各主机的 host-gateway 里：Monitor 要求自己内嵌的目录与 Admin 提供的逐字节一致，不一致就停掉部署同步（新增、停用的部署 Monitor 看不到）；网关按自己内嵌的目录算路由，不认识的方法一律拒绝 | 目录有变化时逐台 `setup deploy`（控制机先），让 Admin、Monitor、每台主机的 host-gateway 是同一个提交 |

重启 Storage 进程的注意点：

- 重启单个进程用 `moox-cli setup restart --host <存储机> --component <storage-primary 或 storage-view> --yes`，不要整体重启。
- 重启 `storage-primary` 会让这一刻的周期提交失败，监控的行情探针可能触发一次几十秒的短告警并自动恢复。
- `storage-primary` 启动时会重放 Pebble 的 WAL（日志里能看到 `replayed N keys`），数据不丢。
- DuckDB 内存上限与临时目录的约定见[存储 §6.4](模块/存储.md)。
- 因子计算引擎不在控制主机上：它运行在`[deployments]` 指定的因子机的 systemd 用户服务 `moox-factor-engine`，更新二进制后用 `systemctl --user restart moox-factor-engine`。
  同一个 `engine_id` 的新进程第一次心跳就顶替旧进程，不用等旧心跳过期；只有另一个 `engine_id` 的引擎在当前引擎心跳还新鲜（45 秒内）时来登记才报 `lease conflict`。新进程起来后依次预热全部因子任务，耗时随标的数与回看根数而定。
  预热完成前到达的周期（通常是 1m 任务的前一两期，或在整点前一两分钟重启时的 1h 那一期）结果按失败标的上报、页面短暂显示“数据积累中”，
  跳过的结果记入跳过账本，由跳过恢复补算（发现后至少等 `gap.settle` 5 分钟，每 `gap.sweep_interval` 5 分钟扫一轮），历史结果不会缺一根（日志 `factor_gap_repaired`）。
- 重启 `factor-mgr` 时如果引擎正好在上报一个补算作业的进度，这次上报会失败，引擎放弃该任务（日志 `factor_recalc_abandoned`）；任务租约（15 分钟）过期后被重新领取、从已上报的进度续跑。
  因为补算作业同时只跑一个，这段时间里其它排队的补算作业也在等待。要避免这种等待，重启管理端前先确认没有 `running` 的补算作业。
- 引擎状态里的任务执行器只包含目录里启用的因子任务；没有因子任务的数据集（例如还没建因子任务的 1h K 线）不出现在“数据预热”里。
