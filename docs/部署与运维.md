# 部署与运维

本文说明 MooX 的部署方式、首次部署、日常发布、暂停与停机切换，以及运维检查。各模块自身的运维细节见对应的模块文档。

## 1. 部署形态

所有部署输入都在仓库根目录的 `moox.toml`（从 `moox.toml.example` 复制，权限 `0600`）。其中 `[hosts.<主机 ID>]`
列出 MooX 主机，`[placements]` 是部署表：每台主机上运行哪些业务组件。主机组件（主机网关、主机采集器）每台主机自动
部署，不用写进部署表。

| 主机 | 部署根目录 | 组件 |
| --- | --- | --- |
| control | `/data/moox/prod` | console-proxy（Caddy）、web-host、admin、eventbus、monitor、collector、cloudnode、factor-mgr、strategy |
| storage | `/data/moox/storage` | storage-primary、storage-node、storage-view、access |
| compute-1（香港） | `/data/moox/compute-1` | trade、access、egress-proxy |
| 操作员机器 | 例如 `~/moox/factor-engine` | Factor Engine（只发起出站连接） |
| 腾讯云 SCF | — | 行情采集函数（Timer 与 Invoke） |

部署根目录默认为 `<paths.deploy_root>/<主机 ID>`，也可以用 `[hosts.<主机 ID>] root` 单独指定。目录结构：

| 路径 | 内容 |
| --- | --- |
| `releases/<版本>/` | 一次发布：`bin/`、各组件的配置（`<组件>/config/`）、组件规格 `runtime/<组件>.env`、运行脚本 |
| `current` | 指向当前发布的符号链接；安装器保留上一个发布用于回滚 |
| `data/<组件>/` | 组件数据（SQLite、Pebble、JetStream、Caddy 证书等），跨发布保留 |
| `logs/<组件>/` | 组件日志，跨发布保留 |
| `run/<组件>.pid`、`run/paused/<组件>` | 进程号与暂停标记 |
| `secrets/` | 调用方密钥、health HMAC、Storage 内部密钥、Admin 加密密钥、EventBus 凭据、`pki/`（仅 control），权限 0600 |
| `certs/` | MooX 私有 CA 证书 `moox-ca.crt` 和主机网关证书 `host-gateway/` |

每个发布根目录下有 `start.sh`、`stop.sh`、`restart.sh`、`status.sh`、`pause.sh`、`resume.sh`、`healthcheck.sh`
（来源是仓库的 `deploy/runtime/`）。组件启动前执行各自的准备步骤，例如用模块 CLI 应用 schema
（`moox-monitor-cli init` 等），所以有 schema 的模块总是和它的 CLI 一起发布。

默认业务配置在 `config/setup/`：

| 文件 | 读取方 | 用途 |
| --- | --- | --- |
| `metadata.yaml` | `moox-cli setup init` | Admin 业务空间和 Storage 元数据（空间 `crypto`、`stockcn` 等，内部空间 `mooxsys`） |
| `collection-tasks.yaml` | Collector 启动前的 `moox-collector-cli init` | 默认采集任务 |
| `dataset-health-policy.yaml` | Monitor | 实时数据集健康阈值 |

## 2. 首次部署

```bash
moox-cli setup validate --file ./moox.toml        # 校验配置、腾讯云凭据和全部主机的 SSH 连接
moox-cli setup trust-host --file ./moox.toml ...  # 核验并记录 SSH 主机指纹（每台主机和编译主机）
moox-cli setup firewall --file ./moox.toml        # 按部署表同步防火墙入站规则（要先于 bootstrap）
moox-cli setup bootstrap --file ./moox.toml       # 空环境首次部署：初始化管理后台并部署全部主机
moox-cli setup apply --file ./moox.toml           # 写入初始用户、云凭据和 SSH 主机
moox-cli setup init --file ./moox.toml            # 导入默认空间、数据集、字段和因子
moox-cli setup trust-browser --file ./moox.toml   # 让本机浏览器信任控制台证书（internal 模式；apply 和 init 也会检查）
```

防火墙要先于 `bootstrap`：其他主机的主机网关要经 control 的 `11003` 取到第一份快照才算就绪，部署命令会等它就绪。

空环境下有三个相互依赖：主机网关需要的证书要由 control 上的 CA 签发；CLI 要经主机网关登记部署，而网关的路由又来自
已登记的部署；登记部署依赖 Admin 运行。所以 `bootstrap` 单独完成初始化：

1. 把 control 的发布装上，暂不启动；
2. 经 SSH 在 control 上离线执行 `moox-admin-cli bootstrap`：执行 `admin.sql` 建表、生成 MooX 私有 CA、按部署表
   写入全部主机和部署（与 `SyncHostPlacements` 同一套校验）、生成全部调用方密钥、为 control 签发主机网关证书；
3. 再次安装 control 的发布（复用二进制，带上签名密钥）并启动；
4. 把 moox-cli 的签名密钥取回操作员机器（`~/.config/moox/caller-moox-cli.key`）；
5. 依次部署其他主机，这时经 SSH 隧道调用 Admin 同步部署记录。

`bootstrap` 可以重复执行：已有的表、CA 和密钥都会复用，不会重建。`--control-only` 只做前 4 步。

`setup init` 也可以重复执行：先补齐防火墙规则；在 Admin 中创建或核对用户、凭据和空间；在 CloudNode 中核对云账户；
经 SSH 隧道创建或核对元数据，并逐个激活数据集。相同资源记为 `unchanged`，字段不一致时报冲突，不会自动覆盖。

## 3. 发布

| 场景 | 方式 |
| --- | --- |
| 一台主机 | `moox-cli setup deploy-host --host <主机>`：主机组件和部署表中的全部业务组件 |
| 一台主机的部分组件 | `deploy-host --host <主机> --components a,b`，其余组件不动 |
| 一个组件 | `moox-cli setup deploy-service --component <组件> [--host <主机>]`：部署了该组件的全部主机（或指定主机） |
| 只改配置 | 部署命令加 `--reuse-binaries`：不上传二进制，复用主机当前发布中的 |
| Storage 保留期等策略 | `moox-cli config plan` 核对差异，`config publish` 发布（见[存储](模块/存储.md)） |
| 回滚 | `moox-cli setup rollback --host <主机>`：切回上一个发布并重启组件 |
| 检查渲染结果 | `moox-cli setup render --host <主机> --out <目录>`：不连接主机 |
| 需要 CGO 的 Linux 二进制 | 在编译主机上构建（Storage、Factor 等），部署命令会自动使用；也可以单独执行 `moox-cli setup build-linux` |
| SCF 采集函数 | `moox-cli collector function package` 构建代码包，`collector function publish submit` 按 fleet 发布，见[采集](模块/采集.md) |
| Factor Engine | `scripts/deploy/deploy-factor-engine.sh`，见[因子](模块/因子.md) |
| 前端 | 在编译主机上构建，再部署 web-host，见[前端](模块/前端.md) |

每次部署一台主机，CLI 依次完成：

1. 按 `moox.toml` 渲染这台主机的发布（配置与组件规格），构建需要的二进制；
2. 在 control 上用 `moox-admin-cli` 取出这台主机要用的调用方密钥、外部调用方密钥集，并重新签发主机网关证书；
3. 调用 `SysDeploy.SyncHostPlacements`，按部署表事务性地同步这台主机在 Admin 中的部署记录（`--no-sync` 跳过，
   用于 Admin 不可用、需要先修复 control 的情况）；页面上设置的启用 / 停用状态保留；
4. 上传发布包，运行安装器：持有维护锁 → 解出发布目录 → 装入密钥和证书 → 生成缺少的本机密钥 → 停止要替换的组件 →
   切换 `current` → 启动组件（暂停的组件不启动）。启动失败时切回上一个发布并重新启动这些组件。

注意：

- 发布包不包含数据、日志；密钥和证书只在安装时装进 `secrets/`、`certs/`，随后从发布目录中删除。
- 组件目录内嵌在 Admin、Monitor、CLI、主机网关和外部接入中，组件目录有变化时这几个组件要一起发布。
- 配置采用严格解析，删除或新增配置项时需要整体发布该服务的配置。

## 4. 启停、暂停与维护锁

```bash
moox-cli setup service status --host storage                       # 查看组件状态
moox-cli setup service restart --host control --components monitor # 重启组件
moox-cli setup pause --host control --components collector,strategy
moox-cli setup resume --host control --components collector,strategy
```

- **暂停**：写入暂停标记 `run/paused/<组件>` 并停止进程。标记放在发布目录之外，重新部署后仍然有效；`start.sh`、
  `healthcheck.sh` 和安装器都不会拉起被暂停的组件，直到执行 `resume`。`service start|restart --force` 忽略暂停标记。
- **健康检查**：安装器在 crontab 中登记每分钟执行一次的 `healthcheck.sh`，它滚动本地日志，拉起停止或连续探测失败的
  组件（暂停的组件不管）。
- **维护锁**：`<部署根目录>.maintenance.lock`。安装器运行期间自己持有，结束时释放；`healthcheck.sh` 在锁被占用时整体
  跳过。需要在主机上做一段较长的手工维护时，操作员在自己的会话中持锁：

  ```bash
  exec 9>/data/moox/prod.maintenance.lock; flock -w 120 9
  ```

  持锁期间执行的部署命令和 `pause`、`resume` 都要加 `--maintenance-lock-held`，否则安装器会等待这把锁。

## 5. 受保护组件与离线恢复

`admin`、`host-gateway`、`console-proxy`、`web-host` 和 control 主机本身受保护：控制台不显示它们的停用开关，
`SetPlacementStatus`、`SetHostStatus` 拒绝停用，`SyncHostPlacements` 拒绝把它们从部署表中移除。

在控制台「资源与运维 → 服务部署」停用的其他组件，15 秒内从各主机网关的路由中消失。控制台或网关异常、无法在页面上
恢复时，经 SSH 在 control 上离线修改数据库，不依赖 Admin 或网关：

```bash
cd /data/moox/prod
current/bin/moox-admin-cli placement set-status --db-path data/admin/admin.db --host <主机> --component <组件> --status enabled
current/bin/moox-admin-cli host set-status --db-path data/admin/admin.db --host <主机> --status enabled
```

下一次快照（15 秒内）会下发新的路由。

## 6. 停机切换

需要所有主机一起停机的升级（例如替换网关、迁移数据目录）按以下做法进行，具体步骤写在对应的执行计划里，例如
[网关与服务部署重构执行计划](计划/网关与服务部署重构执行计划.md)第 13 节：

1. **准备**（不停机）：迁移并校验 `moox.toml`；构建全部二进制；执行 `moox-cli setup export-state` 导出 SCF 函数状态
   和各主机的防火墙规则，回滚时使用。
2. **暂停采集**：在 control 上持锁，`pause` collector 和 strategy，停止操作员机器上的因子引擎。
3. **一致性备份**：服务停止后用 SQLite 备份接口导出数据库，并做 `PRAGMA integrity_check`；打包备份 `certs/`、
   `secrets/`、Caddy 数据和 crontab。
4. **逐台部署**：control 用 `bootstrap --control-only --maintenance-lock-held`（已初始化过的环境用 `deploy-host`），
   其他主机用 `deploy-host --host <主机> --maintenance-lock-held`；每台确认主机网关心跳和路由同步正常后再释放锁。
5. **防火墙与 SCF**：`moox-cli setup firewall --prune` 删除旧规则；按批发布 SCF。
6. **恢复采集**：`resume` collector 和 strategy，观察 30 分钟，确认暂停期间没有新批次。

回滚时三台主机一起回滚：切回上一个发布，放回数据库备份、证书与密钥，按 `export-state` 的记录恢复 SCF 和防火墙。

## 7. HTTPS 与证书

| 证书 | 说明 |
| --- | --- |
| 控制台证书 | 控制台代理（固定版本的 Caddy，只在 control 上）提供 9527。`tls_mode = "public"` 用 Let's Encrypt 短期证书，需要 TCP 80 持续可达以便续期；`internal` 用 Caddy 内置 CA，根证书在 `data/console-proxy/caddy/pki/authorities/local/root.crt`，用 `moox-cli setup trust-browser` 或 `skills/moox/scripts/caddy-ca.sh` 让浏览器信任；`auto`（默认）对私网和回环地址用 `internal`，其余用 `public` |
| MooX 私有 CA | 首次部署时生成，私钥在 control 的 `secrets/pki/`（不放进 `admin.db`，重置 control 数据不会丢失）；有效期 10 年 |
| 主机网关证书 | 每次部署一台主机时重新签发，SAN 包含主机 ID、公网地址和私网地址；有效期 5 年，正常情况下不会过期 |

Admin 的证书巡检定时器检查 MooX 私有 CA、EventBus CA 和各主机网关证书（到期时间来自主机网关的心跳），到期前 90 天告警。

## 8. 凭据

| 凭据 | 生成方式 | 位置 |
| --- | --- | --- |
| 调用方密钥 | `moox-admin-cli bootstrap` 或首次部署引入该调用方时生成，之后复用；主副本加密存放在 Admin 密钥表 | 组件所在主机的 `secrets/caller-<身份>.key`；moox-cli 的在操作员机器 `~/.config/moox/caller-moox-cli.key` |
| 外部调用方密钥 | 同上；SCF 的由 Collector 写进函数环境变量 | 外部接入主机的 `secrets/access-principals.json`；因子引擎的在操作员机器 |
| EventBus CA、各角色 token | 部署 eventbus 时由 `moox-admin-cli eventbus-credentials ensure/export` 自动处理 | token 保存在 Admin 密钥表，导出到 control 的 `secrets/eventbus/`，部署时随组件下发 |
| health HMAC、Storage 内部密钥、Admin 会话与加密密钥 | 安装器在 control 上首次生成，之后复用；部署其他主机时从 control 复制 | `secrets/health-auth.env`、`storage-internal-auth.env`、`admin-jwt.env`、`admin-encryption-key` |
| DataNode 密钥 | 安装器在 Storage 主机上生成 | `secrets/storage-node-auth.env` |
| 云账户、交易所密钥 | 管理台或 `setup apply` | Admin SecretMgr 加密保存 |

`admin-encryption-key` 丢失后已有的密钥表无法解密，所以有 `admin.db` 时安装器拒绝重新生成它。

轮换调用方密钥用 `moox-admin-cli keys rotate --caller <身份>`：新旧密钥同时有效，新密钥随快照下发到各主机网关，
重新部署该调用方后再停用旧 KeyID。轮换外部调用方密钥后要重新部署全部外部接入。轮换 EventBus CA 或 token 后，
需要把新凭据分发到所有客户端（各主机的 HostAgent、Factor Engine、SCF 函数环境）后才算完成。

## 9. 数据保留

| 数据 | 边界 | 说明 |
| --- | --- | --- |
| EventBus Stream | 见[事件总线](模块/事件总线.md) | 按时间和容量淘汰旧消息，不影响已提交的业务事实 |
| 时序数据集 | `moox.toml` `[storage_retention]` 按空间与频率给出，例如 crypto 1m 7 天、1h 365 天、1d 起永久 | Storage 按天桶清理；页面与 Metadata 显示只读的生效保留期和来源 |
| 主机指标数据集 | 180 天 | `mooxsys` 空间 1m 的保留期 |
| 服务指标数据集 | 48 小时 | `mooxsys` 空间 30s 的保留期 |
| View 索引 | 每个序列最近 `view_bars` 根（默认 5000） | 超过 ceil(1.2 × N) 根时整理；A/B 槽位重建后整体删除旧槽位 |
| View 周期状态 | 7 天（`MOOX_STORAGE_VIEW_PERIOD_RETENTION`） | 只清理去重和等待状态 |
| Monitor 检查结果与告警事件 | 14 天 | `data_cleanup` 定时器每 6 小时清理 |
| Archive Parquet | 永久 | 需要规划长期容量 |
| Admin / Strategy / Trade 业务数据 | 不自动删除 | 订单、成交、策略结果等事实不能为了腾磁盘静默删除 |
| 本地日志 `logs/**/*.log` | 每个 50 MiB、保留 5 份（`[local_logs]`） | `healthcheck.sh` 每分钟滚动 |

SQLite 删除后的空闲页、Pebble 删除标记都要等复用或 compaction 才会让磁盘变小，判断清理效果要
看几个周期的趋势。不要用通用目录清理命令删除正在运行的 Pebble、SQLite、DuckDB、Bleve 或
JetStream 文件。

## 10. 日志与 tRPC 插件

- 所有 tRPC 服务的 server filter 链首是 `recovery`，把 handler panic 转为系统错误；指标统一使用
  `plugins.metrics.prometheus`（`enablepush: false`），由各服务的 `metrics` 定时器发布到 EventBus。
- 主机上的组件把日志写到 console，由运行脚本重定向到 `logs/<组件>/stdout.log`。日志中禁止出现凭据、原始请求体、
  JWT 和 HMAC。每个进程都会给默认 logger 追加固定的 `service_name` 属性（组件 ID）。
- SCF 采集函数的日志写入腾讯云 CLS：`moox-cli ops tencent cls prepare` 在 `ap-guangzhou` 查找或创建 Logset `moox`
  与 Topic，发布采集函数时写入函数配置，见[采集](模块/采集.md)。
- 幂等只读 RPC（如 `ReadTimeSeriesRows`）通过 `packages/trpcretry` 最多重试一次；写接口不重试。
- Factor 到 Storage 的客户端启用 `transinfo-blocker` 白名单，只透传 trace 与空间标识。

## 11. 日常检查

| 目的 | 方式 |
| --- | --- |
| 整体健康 | 管理台“资源与运维 → 监控告警”；告警推送到企业微信 / 飞书 |
| 部署与路由 | 管理台“资源与运维 → 服务部署”：每台主机的组件状态、期望与已应用的路由哈希、网关心跳 |
| 主机上的组件 | `moox-cli setup service status --host <主机>`；`moox-cli setup host-diagnostics` 查看磁盘和进程 |
| 诊断部署 | `moox-cli doctor bootstrap`（新部署）、`moox-cli doctor diagnose --node <主机>` |
| 单个进程 | 使用 health HMAC 访问各进程的 `/readyz`（未签名请求返回 401） |
| 主机网关 | `moox-host-gateway-cli snapshot`、`/readyz` 的快照同步时效，见[主机网关](模块/主机网关.md) |
| 采集周期 | `moox-cli collector period-inventory`、管理台“采集任务 → 任务实例” |
| View 进度 | `moox-storage-cli repair-view`、`reconcile-view-consumers` |
| 主机与磁盘 | 管理台“主机工作台 → 主机监控”；`du -sh data/* logs/*` |

## 12. 构建、测试与 CI

```bash
make build          # 构建全部 Go 二进制到 bin/
make test           # Go 与前端测试
make verify         # CI 使用的完整检查：边界、格式、lint、契约、发布、文档构建等
make proto          # 重新生成 Protobuf 代码
```

GitHub Actions：`ci.yml` 在 Pull Request 上做密钥扫描和 `make verify`；`release.yml` 按 tag 构建发布包；
`deploy-docs.yml` 在 main 分支构建 VitePress 文档站点。生产部署只用 `moox-cli setup` 命令，CI 不部署生产。
