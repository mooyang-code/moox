# 部署与运维

本文说明 MooX 的部署方式、初始化流程、日常发布和运维检查。各模块自身的运维细节见对应的模块文档。

## 1. 部署形态

| 位置 | 部署目录 | 进程 |
| --- | --- | --- |
| control 主机 | `/data/moox/prod` | Caddy、web-host、Admin、Gateway、EventBus、CloudNode、Collector、Collector Subject、Factor Manager、Strategy、Monitor、HostAgent |
| storage 主机 | `/data/moox/storage` | storage-primary、storage-node、storage-view、storage-access、Gateway、HostAgent |
| 操作员机器 | 例如 `~/moox/factor-engine` | Factor Engine（只做出站连接） |
| 腾讯云 SCF | — | 行情采集函数（Timer 与 Invoke） |

Trade 和 Archive 默认不部署，按需启用。

`scripts/deploy/deploy-moox.sh` 是整机部署脚本，用 `--profile` 选择组件组合：

| profile | 组件 |
| --- | --- |
| `control` | 控制面全部组件（不含 Storage 与 Archive） |
| `storage` | Storage 四个角色 + Gateway |
| `storage-access` | 只部署 storage-access（例如为某个 SCF 地域单独设置入口） |

也可以用 `--no-<组件>` / `--with-<组件>` 精确增减；`--package-only --archive <zip>` 只打包不发布。
部署目录结构为 `bin/`、`config/`、`data/`、`logs/`、`run/`、`secrets/`、`certs/`，
每个服务的 `start.sh` 会在启动前应用该模块的 schema。

## 2. 首次部署与初始化

所有初始化输入都在仓库根目录的 `moox.toml`（从 `moox.toml.example` 复制，权限 `0600`），
其中包含主机清单、云账户、编译机、SCF 采集配置等。默认业务配置在 `config/setup/`：

| 文件 | 读取方 | 用途 |
| --- | --- | --- |
| `metadata.yaml` | `moox-cli setup init` | Admin 业务空间和 Storage 元数据（空间 `crypto`、`stockcn`，内部空间 `mooxsys`） |
| `service-deployments.yaml` | `moox-admin-cli service-deployments import` | 默认服务目录 |
| `collection-tasks.yaml` | `moox-collector-cli init` | 默认采集任务 |
| `dataset-health-policy.yaml` | Monitor | 实时数据集健康阈值 |

推荐顺序：

```bash
moox-cli setup validate --file ./moox.toml        # 校验配置与 SSH 连接
moox-cli setup trust-host --file ./moox.toml ...  # 核验并记录 SSH 主机指纹
moox-cli setup deploy-control --file ./moox.toml  # 部署控制面，安装受管 Caddy 并验收 HTTPS
moox-cli setup apply --file ./moox.toml           # 写入初始用户、云凭据和主机
moox-cli setup deploy-storage --file ./moox.toml --host storage
moox-cli setup init --file ./moox.toml --config-dir ./config/setup --storage-host storage
```

`setup init` 可重复执行：开放所需防火墙端口；在 Admin 中创建或核对用户、凭据、主机和空间；
在 CloudNode 中核对云账户；通过 Storage 主机的 SSH 隧道创建或核对元数据，并逐个激活数据集。
相同资源记为 `unchanged`，字段不一致时报冲突，不会自动覆盖。

需要清空并重建全部 Storage 数据时使用 `moox-cli setup rebuild-storage`：不带 `--yes` 只做远端
预演；带 `--yes` 时会依次停止写入方、清理 EventBus 消费者、删除 Storage 数据与元数据、重新初始化并验证。

## 3. 发布

| 场景 | 方式 |
| --- | --- |
| 整机更新 | `scripts/deploy/deploy-moox.sh --target <user@host> --dir <部署目录> --profile <profile>` |
| 单个服务 | `scripts/build/package-service.sh` 打包 ZIP，再 `moox-cli setup deploy-service` 发布（上传、解压、回滚、健康检查） |
| 纯 Go 程序（含 Factor Manager/CLI） | 本机设置 `TARGET_GOOS` / `TARGET_GOARCH`，使用 `scripts/build/build.sh` 交叉编译 |
| 需要 CGO 的 Linux 二进制 | `moox-cli setup build-linux` 在编译机上构建（Storage Primary/Node/View/CLI 的 DuckDB 目标） |
| SCF 采集函数 | `moox-cli collector function package` 构建代码包，`collector function publish submit` 按 fleet 发布，见[采集](模块/采集.md) |
| Factor Engine | `scripts/deploy/deploy-factor-engine.sh`，见[因子](模块/因子.md) |
| HostAgent | `skills/moox/scripts/hostagent-deploy.sh`，见[主机代理](模块/主机代理.md) |
| 前端 | 本机上 `pnpm build:prod`，再 `make statik` 并构建 web-host，见[前端](模块/前端.md) |

发布注意：

- 服务包只包含 `bin/`、`config/`、`start.sh`、`stop.sh`、`healthcheck.sh`，不得包含数据、日志、凭据和证书。
- 有 schema 变化的模块要同时发布服务二进制和对应的 CLI（`start.sh` 用 CLI 应用 schema）。
- 配置采用严格解析，删除或新增配置项时需要整体发布该服务的配置。

## 4. HTTPS 与证书

Caddy 是 HTTP/HTTPS 唯一的公网入口，由部署脚本以固定版本安装在部署目录（`bin/caddy`、
`config/caddy/Caddyfile`、`data/caddy`），不依赖系统 Caddy：

- `--tls-mode auto`（默认）：公网 IP/DNS 使用 Let's Encrypt 短期证书，需要 TCP 80 持续可达以便续期；
  私网和回环地址使用 Caddy 内部 CA。
- 内部 CA 模式下根证书在 `certs/caddy/root.crt`，用 `skills/moox/scripts/caddy-ca.sh` 分发；
  后端进程通过 `MOOX_SERVICE_GATEWAY_CA_FILE` 信任它，SCF 使用 `MOOX_SERVICE_GATEWAY_CA_PEM_B64`。
- 每分钟的 `healthcheck.sh` 会检查证书剩余有效期并在 Caddy 异常时拉起。

## 5. 凭据

| 凭据 | 生成方式 | 位置 |
| --- | --- | --- |
| EventBus CA、各角色 token | `moox-admin-cli eventbus-credentials ensure/export/rotate` | token 保存在 Admin 密钥表，导出到 `~/.config/moox/eventbus/<角色>.yaml` |
| 网关控制面 / 服务密钥 | 部署脚本生成 | `secrets/gateway-control.key`、`secrets/gateway-credentials.json`（0600） |
| health HMAC | 部署脚本生成 | `secrets/health-auth.env` |
| Storage 内部签名密钥 | 部署脚本生成 | `secrets/storage-internal-auth.env` |
| 云账户、交易所密钥 | 管理台或 `setup apply` | Admin SecretMgr 加密保存 |

轮换 EventBus CA 或 token 后，需要把新凭据分发到所有客户端（各主机的 HostAgent、Factor Engine、
SCF 函数环境）后才算完成。

## 6. 数据保留

| 数据 | 边界 | 说明 |
| --- | --- | --- |
| EventBus Stream | 见[事件总线](模块/事件总线.md) | 按时间和容量淘汰旧消息，不影响已提交的业务事实 |
| 时序数据集 | `moox.toml` `[storage_retention]` 按空间与频率给出，例如 crypto 1m 7 天、1h 365 天、1d 起永久 | Storage 按天桶清理；页面与 Metadata 显示只读的生效保留期和来源 |
| 主机指标数据集 | 180 天 | `mooxsys` 空间 1m 的保留期 |
| 服务指标数据集 | 48 小时 | `mooxsys` 空间 30s 的保留期 |
| View 索引 | 每个序列最近 `view_bars` 根（默认 5000） | 超过 ceil(1.2 × N) 根时整理；A/B 槽位重建后整体删除旧槽位 |
| View 周期状态 | 7 天（`MOOX_STORAGE_VIEW_PERIOD_RETENTION`） | 只清理去重和等待状态 |
| Monitor 检查结果与告警事件 | 14 天 | `data_cleanup` 定时器每 6 小时清理 |
| Archive Parquet | 永久 | 需要规划长期容量 |
| Admin / Strategy / Trade 业务数据 | 不自动删除 | 订单、成交、策略结果等事实不能为了腾磁盘静默删除 |
| 本地日志 `logs/**/*.log` | 每个 50 MiB、保留 5 份 | `healthcheck.sh` 调用 `moox-log-rotate` 轮转 |

SQLite 删除后的空闲页、Pebble 删除标记都要等复用或 compaction 才会让磁盘变小，判断清理效果要
看几个周期的趋势。不要用通用目录清理命令删除正在运行的 Pebble、SQLite、DuckDB、Bleve 或
JetStream 文件。

## 7. 日志、CLS 与 tRPC 插件

- 所有 tRPC 服务的 server filter 链首是 `recovery`，把 handler panic 转为系统错误；指标统一使用
  `plugins.metrics.prometheus`（`enablepush: false`），由各服务的 `metrics` 定时器发布到 EventBus。
- 本地与测试环境只写 console；生产额外把 warn/error 写入腾讯云 CLS，Factor 的计算流水线写 info。
  日志中禁止出现凭据、原始请求体、JWT 和 HMAC。每个进程都会给默认 logger 追加固定的 `service_name` 属性
  （部署模块名），便于在同一个 Topic 中按服务筛选。
- 启用 CLS 的发布会在发布包同步和停服之前执行预检：`skills/moox/scripts/cls-bootstrap.sh` 通过
  `moox-cli ops tencent cls prepare` 在 `ap-guangzhou` 查找或创建 Logset `moox` 与 Topic
  `moox-application`，把非敏感 ID 写入生成的 `config/resources.env`。配置文件只引用
  `${MOOX_CLS_TOPIC_ID}`、`${MOOX_CLS_SECRET_ID}`、`${MOOX_CLS_SECRET_KEY}` 占位符，写入凭据只保存在目标机
  `secrets/cls.env`（0600）。预检任一步失败都会中止发布。
- 幂等只读 RPC（如 `ReadTimeSeriesRows`）通过 `packages/trpcretry` 最多重试一次；写接口不重试。
- Factor 到 Storage 的客户端启用 `transinfo-blocker` 白名单，只透传 trace 与空间标识。

## 8. 日常检查

| 目的 | 方式 |
| --- | --- |
| 整体健康 | 管理台“运维 → 服务管理 → 健康监控”；告警推送到企业微信 / 飞书 |
| 诊断部署 | `moox-cli doctor bootstrap`（新部署）、`moox-cli doctor diagnose --node <节点>` |
| 单个进程 | 使用 health HMAC 访问各进程的 `/readyz`（未签名请求返回 401） |
| 节点网关路由 | `moox-host-gateway-cli routes`、`/readyz` 的路由同步时效 |
| 采集周期 | `moox-cli collector period-inventory`、管理台“采集任务 → 任务实例” |
| View 进度 | `moox-storage-cli repair-view`、`reconcile-view-consumers` |
| 主机与磁盘 | 管理台“主机工作台 → 主机监控”；`du -sh data/* logs/*` |

## 9. 构建、测试与 CI

```bash
make build          # 构建全部 Go 二进制到 bin/
make test           # Go 与前端测试
make verify         # CI 使用的完整检查：边界、格式、lint、契约、发布、文档构建等
make proto          # 重新生成 Protobuf 代码
```

GitHub Actions：`ci.yml` 在 Pull Request 上做密钥扫描和 `make verify`；`release.yml` 按 tag 构建
发布包并可选部署到生产；`deploy-docs.yml` 在 main 分支构建 VitePress 文档站点。
