# 部署与运维

当前代码提供按单元部署的原生 CLI 和 Linux 运行助手。初始化分为 core、主机与业务单元、完整 control；
各阶段独立返回就绪收据。全系统交付范围见[当前实现与文档边界](实现状态.md)。

## 1. 拓扑与软件包

主机、组件部署和路径由 `moox.toml` 的 `[hosts.*]`、`[deployments]`、`[paths]` 声明，模板为
`moox.toml.example`。软件包与主机不同：同一主机可安装 host 和多个业务单元。

| profile | 包内组件 |
| --- | --- |
| `host` | HostGateway、HostAgent、`moox-runtime` |
| `control` | Console Proxy、web-host、Admin、EventBus、Monitor、Collector、CloudFunction、Factor Manager、Strategy |
| `storage` | Storage primary、node、view |
| `access` | Access |
| `egress-proxy` | EgressProxy |
| `trade` | Trade |
| `collector-stream` | Collector Stream（WS 推送接收与本地执行端） |
| `factor-engine` | 因子引擎（外部程序，systemd 用户服务） |
| `archive-worker` | 归档 Worker（外部程序，systemd 用户服务） |

实际安装取包内组件与目标主机部署的交集。`collector-stream` 默认放在海外机（`moox.toml.example` 的 overseas 部署），用
`moox-cli setup deploy-unit --host <海外机> --profile collector-stream` 部署：写 Storage 沿用 `moox-collector` 应用身份，部署时在本机按 Storage 主密钥派生这一把应用密钥，
以 `MOOX_STORAGE_PRIMARY_AUTH_APP_KEYS_JSON` 注入，主密钥不放到海外机。端口：本地执行端 `MarketFetchExecutor` 11450，健康检查 11451；它经主机网关调用 Collector 的
`StreamCollector`（11422）。服务目录新增组件与路由，发布时 Admin、各主机 host-gateway、Monitor、Access 与 Collector 用同一提交构建、按顺序一起换；线上 Collector 的
`trpc_go.yaml` 是安装时的副本，只换二进制不会带上新的 `StreamCollector` 服务，需要同步配置。
服务目录新增调用方（例如 `collector-stream`、外部身份 `collector-operator`）时，新 Admin 不会在读路径上生成签名密钥：换上新 Admin 之后立即在控制机执行
`bin/moox-admin-cli keys ensure --caller <调用方> --db-path admin/data/admin.db --encryption-key-file /data/moox/identity/admin-master.key`（每个新调用方一次），
否则路由里放行了该调用方的主机（控制机、存储机）的网关快照编译失败，Monitor 报“主机部署读写失败”、网关心跳不再更新（2026-10-21 发布 WS 推送采集时遇到约 3 分钟）。每台 MooX 主机先具备 host 单元；因子引擎与归档 Worker 是因子机上的外部程序，
经 `setup deploy-unit` 以 systemd 用户服务安装（见下文“因子机外部程序”），SCF 另行发布。

纯 Go 程序和前端在本机构建或交叉编译；Storage 三个服务需要 Linux CGO 制品，Storage CLI 仍关闭 CGO。
`setup package` 只收集软件与公开模板，不读 `moox.toml`，也不携带证书、签名密钥、数据库或日志。

### 主机命名与登记

主机 ID 用英文短名、按角色命名，配一个固定的中文名（`[hosts.<ID>] label`，不写时按 ID 生成；登记到 Admin 的主机表，管理台只显示中文名与 ID、地址），
文档与沟通统一写“中文名（英文 ID）”。只在同一角色有多台时才加序号（如 `overseas-2` → “海外机 2”）。

| 主机 ID | 中文名 | 角色 |
| --- | --- | --- |
| `control` | 控制机 | 控制面：Admin、EventBus、Monitor、Collector、CloudFunction、因子管理、策略、控制台 |
| `storage` | 存储机 | Storage primary/node/view 与 Access |
| `overseas` | 海外机 | 海外 IP 出口：Trade、Access、EgressProxy、Collector Stream，建议放在香港 |
| `factor` | 因子机 | 因子引擎与归档 Worker（外部程序），可以在内网（只能出站） |

Admin 的主机表（`t_hosts`）是主机的唯一登记处，也保存控制台终端用的 SSH 端口与用户（凭据在 `t_secrets`，指纹首次连接时固定）。
机器的新增、部署、启停与移除只通过 `moox-cli` 完成，管理台的主机列表、服务部署与数据节点页面只读：

| 操作 | 命令 |
| --- | --- |
| 登记并部署主机 | `setup deploy-host --host <ID>`，随后逐个 `setup deploy-unit --host <ID> --profile <单元>` |
| 同步该主机的完整组件部署 | `setup sync-deployments --host <ID>` |
| 启用 / 停用主机 | `setup host enable\|disable --host <ID>`（先预览，`--yes` 才执行） |
| 启用 / 停用组件部署 | `setup deployment enable\|disable --host <ID> --component <组件>` |
| 移除主机登记 | `setup remove-host --host <ID>`（主机已不在 `moox.toml`；不会停止目标机上的进程） |

外部程序停用时先经 SSH 停掉 systemd 服务并核对已停止，再改登记；停用主机会先逐个停掉它上面启用的外部程序。
没有登记 SSH（或只能出站）的主机，控制台终端与文件管理置灰。Agent 的操作说明见 `skills/moox/references/host-registry.md`。

## 2. 原生初始化顺序

前提：准备私有 `moox.toml`（0600）、可信 SSH 指纹、Linux 目标主机和所需网络连通性；
目标机需要 Python 供传输预检。

以下示例使用模板的 `control`（控制机）、`storage`（存储机）、`overseas`（海外机）主机 ID。业务单元必须按实际部署选择，不自动创建云资源或防火墙规则。

```bash
# 本机 CLI 与配置检查
./scripts/build/build.sh cli
./bin/moox-cli setup validate --file ./moox.toml

# 核心控制面：Admin、EventBus、HostGateway、HostAgent；输出 core-ready
./bin/moox-cli setup bootstrap --stage core --file ./moox.toml --source-dir .

# 每台业务主机安装 HostGateway 和 HostAgent
./bin/moox-cli setup deploy-host --file ./moox.toml --source-dir . --host storage
./bin/moox-cli setup deploy-host --file ./moox.toml --source-dir . --host overseas

# 默认下载到 ./bin，同时构建所需的 Linux Storage CLI
./bin/moox-cli setup build-linux --module storage --source-dir .
./bin/moox-cli setup deploy-unit --file ./moox.toml --source-dir . \
  --host storage --profile storage --binary-dir ./bin
./bin/moox-cli setup deploy-unit --file ./moox.toml --source-dir . --host storage --profile access
./bin/moox-cli setup deploy-unit --file ./moox.toml --source-dir . --host overseas --profile egress-proxy

# 完整控制单元；此例显式选择 internal TLS 的首次 CA 创建授权
./bin/moox-cli setup bootstrap --stage control --file ./moox.toml --source-dir . \
  --create-proxy-ca
```

最后一条的 `--create-proxy-ca` 只适用于 `[hosts.control] tls_mode = "internal"`。
公网模式不传此参数。运行状态中已有 CA 时不能靠重试重新生成。

所有阶段使用同一个原始配置和 `--state-dir`（默认 `~/.local/state/moox/setup/<绑定摘要>`）。
SSH 断连并不证明远端已停止；重试复用原请求、制品和持久日志。`*-paused` 表示组件保留了暂停状态，不能当作 ready。

`control-ready` 证明所选控制组件就绪，不代表业务 seed、SCF、Factor Engine、真实行情写入或交易验收完成。
原生 Storage 会建元数据库；业务初始化输入仍在 `config/setup/metadata.yaml`、`collection-tasks.yaml`、
`dataset-health-policy.yaml`。`setup init` 与 `setup export-skill-config` 经 SSH 只读取原生 storage 单元
`<storage_root>/current/secrets/runtime-storage-primary.json`（0600，unitinstall 生成）里的 Node/Primary/View 角色密钥，密钥不落盘、不打印；
浏览器证书信任步骤先经 SSH 从 `<control_root>/current/console-proxy/certs/caddy/root.crt` 取回内部 CA 根证书，
再在本机安装信任（仅 internal TLS，需要本机管理员授权，非交互终端会失败）。

### 实机验证补充（2026-10-11，三台主机）

用 `moox.toml.example` 的三主机结构在真实主机上完整走过一遍后，需要在 `deploy-unit --profile storage` 与
`bootstrap --stage control` 之间补做下面几步，否则 Monitor、Collector 起不来：

1. 在存储主机用随包的 `moox-storage-cli register-node --metadata-target ip://127.0.0.1:20100 --node-id storage-node-0
   --service-target ip://127.0.0.1:20107` 注册 DataNode（节点 ID 与元数据种子、Collector 默认值一致，原生部署固定为 `storage-node-0`）。
   命令需要环境变量 `MOOX_STORAGE_NODE_AUTH_SECRET`，值取自存储节点进程自己的环境。
2. `setup apply` 写入管理员与云凭据；主机由 `deploy-host` 登记，SSH 登录信息（密码或私钥文件，直达主机才同步）随主机同步给 Admin。
   末尾的本机浏览器 CA 信任步骤从原生 control 单元取根证书，需要本机管理员授权，非交互终端会失败，不影响已写入的数据。
3. `setup metadata-import --storage-host storage --spaces mooxsys` 先导入系统空间，再导入 `crypto,stockcn,stockhk,stockus`；
   随后在存储主机运行 `moox-storage-cli activate-datasets --metadata-target ip://127.0.0.1:20100` 激活数据集。
   Monitor 要求 `mooxsys` 的数据集已激活，Collector 要求业务空间的数据源元数据存在。
4. 执行 `bootstrap --stage control --create-proxy-ca`。控制主机磁盘较小时，每次失败重试会残留约 2.7 GB 的发布目录，先确认空间。
5. 控制台创建业务空间：`setup init` 会修改云防火墙并信任本机浏览器证书，联调时也可以登录控制台（或运行
   `e2e-console -create-spaces`（默认校验证书；internal CA 用 `-ca-file`，一次性联调才用 `-insecure-skip-verify`））通过 `space/CreateSpace` 创建。

配置变更通过新版本安装生效：`setup release build` 构建版本，再用各单元的部署命令加 `--release <版本>` 安装；
同一版本的重试绑定原始配置摘要，只换二进制的原生发布不更新配置。
联调时设置 `MOOX_SETUP_DEBUG_HELPER=1` 可输出目标端助手的失败信息。

验证结果：18 个原生组件在三台主机全部 ready；Console 9527 HTTPS 可达，真实登录后 14 项控制台调用
（auth、space、sysdeploy、storage、collector、monitor、strategy、factor、cloudfunction、trade）全部成功，其中 storage、trade 跨主机经主机网关转发。
未覆盖：SCF 发布与 `scf-collector` 凭据分发、真实行情写入、交易下单。


## 3. 目录与运行助手

默认部署根 `/data/moox`，control 单元根 `/data/moox/prod`，Storage 单元根 `/data/moox/storage`。
单元各有 `releases/<发布ID>` 和 `current`；组件工作目录位于发布内，状态复制后才切换 current，旧发布保留独立快照。

| 位置 | 用途 |
| --- | --- |
| `<部署根>/host/current` | 当前 HostGateway、HostAgent 及运行助手 |
| `<单元根>/current/runtime.json` | 私密运行计划，记录该发布打包时的服务目录摘要；组件与健康端口来自发布自带的 `config/servicecatalog/catalog.yaml` |
| `<发布目录>/secrets/`、`certs/` | 按组件投影的签名身份、EventBus 凭据和证书 |
| `<部署根>/identity/` | 独立于发布的运行身份、Admin 主密钥、MooX CA 与代理 CA 授权材料 |
| `<部署根>/run/maintenance.lock` | 安装、启停、恢复和守护共享的主机锁 |
| `<部署根>/run/paused/`、`pids/`、`draining/` | 暂停标记、进程身份与排空记录 |

以默认 control 根为例，在目标 Linux 主机执行：

```bash
/data/moox/host/current/bin/moox-runtime status --plan /data/moox/prod/current/runtime.json
/data/moox/host/current/bin/moox-runtime pause --plan /data/moox/prod/current/runtime.json --components collector
/data/moox/host/current/bin/moox-runtime resume --plan /data/moox/prod/current/runtime.json --components collector
```

助手支持 start、stop、restart、pause、resume、healthcheck、status。暂停先落盘再停进程，重试和守护保留暂停。
healthcheck 按 `/healthz` 判断进程是否需恢复；`/readyz` 暂不可用不会触发自动重启。
低层 prepare、activate、recover、rollback 由部署编排生产规范请求，不应手写私密请求替代上层部署。

运行助手按发布自带的服务目录管理已安装的发布：目录文件的哈希必须同时等于 `runtime.json` 与包清单
`package-manifest.json` 记录的值，任何一处不符（被改动、缺失、组或其他人可写）都拒绝。候选发布（prepare 与 activate
的新发布）另外要求与助手内嵌的目录一致。这样服务目录变更后升级运行助手时，新助手仍能查询、停止和回滚旧目录打包的
当前或上一发布，再用新目录的发布逐个单元接替；单独替换 `moox-runtime` 二进制而不重新部署各单元，计划仍是旧目录，
但不再因此失败。

### 进程看护

| 部署方式 | 看护 | 进程崩溃后 | 主机重启后 |
| --- | --- | --- | --- |
| 原生单元（control、storage、业务主机上由 `moox-runtime` 管理的全部组件，含 archive-mgr） | 部署用户 crontab 里一条 `# moox-watchdog`，每分钟执行一次 `moox-runtime watch` | 1 分钟内按依赖顺序拉起并推送“自动拉起” | cron 开机自启，第一轮 watch 按依赖顺序拉起全部组件，推送一条“主机重启” |
| 因子机外部程序（因子引擎、archive-worker） | Linux systemd 用户服务（`Restart=always`，开启 `Linger`） | 约 10 秒后由系统拉起 | 开机即启动 |

**安装**：`moox-cli setup deploy-host` 在主机服务就绪后自动安装守护；control 由 bootstrap 部署，安装后执行一次
`moox-cli setup watchdog --file moox.toml`（也可 `--host <名称>` 只处理某台、`--remove` 移除）。它在目标机上执行
`moox-runtime install-watchdog --root <部署根>`：确认 cron 在运行（不在就报错，不改 crontab）、幂等写入条目并删除旧部署器的 `# moox-healthchecks`，
再用 `moox.toml` 的 `[notification]` 写一份主机策略种子（经 SSH 标准输入传输，已有从 Monitor 拉取的策略时不覆盖）。
用 `native-release.sh` 替换 `moox-runtime` 后也要执行一次 `setup watchdog`。

crontab 条目：`flock -n <根>/run/watchdog.lock <根>/host/current/bin/moox-runtime watch --root <根> --log <根>/run/watchdog.log`。
flock 保证上一轮没跑完时不叠加；日志每轮一行 JSON 汇总，10 MiB 轮转、保留 3 份。

**一轮 watch 做什么**：

1. 识别重启边界：内核 boot ID 变化时，上次开机留下的 PID 记录与 `draining` 标记一并清除（PID 可能已被复用）。
2. 遇到持久屏障（`run/installation.json`、`run/bootstrap.json`，即发布或初始化被中断）时不做任何拉起，只推送“需要人工恢复”。
3. 按依赖顺序检查：control 上 Admin → 主机网关 → EventBus → HostAgent → 其余组件；其他主机先 host 单元再业务单元。
   上游没运行时下游本轮跳过；遇到维护锁（发布进行中）整轮跳过；暂停的组件不动。4 分钟软期限后不再开始新的检查。
4. 每个组件执行一次 `healthcheck`：`/healthz` 不通才重启（`/readyz` 不就绪只告警）。10 分钟内自动拉起 3 次进入“持续崩溃”，
   之后每 5 分钟、1 小时后每 30 分钟重试一次，连续正常 10 分钟算恢复。
5. 非 control 主机与 control 主机网关做 TLS 握手（交叉检查），连续约 3 分钟失败推送“control 失联”。
6. 告警直接发给本机主机策略缓存里的全部渠道，状态与台账在 `run/watchdog/`（`state.json`、`peer-control.json`、`<组件>.jsonl`）。

**主机策略缓存** `<部署根>/run/host-policy.json`（0600）：全部告警渠道与守护参数。HostAgent 每 5 分钟从 Monitor 拉取（`GetHostPolicy`），
内容变化时版本号加一；拉取失败保留旧文件。守护参数在 Monitor 配置 `host_policy.watchdog` 里调整（合并窗口、持续崩溃阈值、未就绪告警时长等），
`disabled: true` 是总开关：守护只检查与记录、不拉起不告警。各主机缓存的版本与拉取时间用 `moox-cli config notification` 查看，
单台主机上用 `moox-runtime host-policy-status --root <部署根>` 查看（不显示地址）。

**手工检查一轮**（不拉起、不告警）：

```bash
/data/moox/host/current/bin/moox-runtime watch --root /data/moox --dry-run
```

守护停用或 cron 故障时仍可按依赖顺序手工启动。主机网关要等 Admin 完成同步才就绪，HostAgent 要 EventBus；`start` 会等待就绪，
等不到会停掉进程。所以 control 必须按下面的顺序逐个启动，不能先整体启动 host 单元：

```bash
R=/data/moox/host/current/bin/moox-runtime
$R start --plan /data/moox/prod/current/runtime.json --components admin
$R start --plan /data/moox/host/current/runtime.json --components host-gateway
$R start --plan /data/moox/prod/current/runtime.json --components eventbus
$R start --plan /data/moox/host/current/runtime.json --components host-agent
$R start --plan /data/moox/prod/current/runtime.json
```

其他主机（control 已在运行）先启动 host 单元，再启动本机的业务单元，例如 storage：

```bash
R=/data/moox/host/current/bin/moox-runtime
$R start --plan /data/moox/host/current/runtime.json
$R start --plan /data/moox/storage/current/runtime.json
```

如果某个组件因为上次停止被打断（`run/draining/<组件>`）或发布未完成（`run/installation.json`、`run/bootstrap.json`）而起不来，
不要手工删除这些文件：前者用 `stop --components <组件>` 续停后再启动，后者按发布或 bootstrap 的恢复流程处理。

### 因子机外部程序

`factor-engine` 与 `archive-worker` 是服务目录里的外部程序组件，只支持 Linux，装在因子机（`factor`）上：

```bash
./bin/moox-cli setup release build --release <ID> --source-dir .      # release 里含两个外部程序
./bin/moox-cli setup deploy-unit --file ./moox.toml --source-dir . --host factor --profile factor-engine --release <ID>
./bin/moox-cli setup deploy-unit --file ./moox.toml --source-dir . --host factor --profile archive-worker --release <ID>
```

- 软件包随 release 交付，由 systemd **用户服务**托管（`moox-factor-engine`、`moox-archive-worker`），目标机需开启 linger；
  CLI 准备并上传 Access 地址与外部身份密钥、Storage 鉴权、EventBus 凭据和健康密钥，安装脚本不再自己生成。
- 主机或部署在 Admin 里已停用时，安装只落文件、不启动；停用与恢复见上文“主机命名与登记”。
- 归档根目录取 `moox.toml` 的 `[paths] archive_root`。
- 健康检查：因子机只能出站，Monitor 与 `moox-cli doctor` 经 control 网关的中转端口探测 `/readyz`（因子引擎 11417、归档 Worker 11418），
  离线由 factor-mgr、archive-mgr 按心跳评估并告警（见[监控](模块/监控.md)第 12 节）；换机后的旧 worker 登记用 `ArchiveMgr.RetireArchiveWorker` 退役。
- 只能出站的主机：`[hosts.<ID>]` 写 `reachability = "outbound"`，`address` 填内网地址（只作身份与证书 SAN），按 host 单元部署；它的网关主动与 control 网关保持反向连接，
  进入它的连接都经 control 中转（见[主机网关](模块/主机网关.md)第 5 节）。control 的 `11003` 与 EventBus 端口需要对公网开放（凭 TLS 与签名认证，不按来源 IP 放行）：
  `setup deploy-host` 部署出站主机前会经腾讯云接口自动确认放行，确认不了就停止；`setup firewall` 也会放行。

## 4. 网络与信任

| 入口 | 使用方与安全机制 |
| --- | --- |
| HTTPS `9527` | 浏览器 → Console Proxy → Admin/web-host；只代理 `/api/admin/*` 与页面 |
| loopback `11002` | 本机组件和操作员 SSH 隧道；签名 tRPC 与 Directory |
| TLS `11003` | 跨主机签名 tRPC；MooX 私有 CA、目标主机 ID 校验；同端口按 ALPN 接受出站主机的反向连接（attach 要求带 `ClientAuth` 的网关证书）与签名的中转流 |
| tRPC `11004` | 外部 Access；SCF、Factor Engine、Skill 各自身份、方法白名单及持久 nonce；该入口本身不提供 TLS |
| TLS `4222` | EventBus；按发布/消费角色鉴权 |

普通业务 RPC 绑定 loopback。原生安装器按组件目录渲染健康监听：未标记 loopback 的健康端口绑定 `0.0.0.0`，
使用 health HMAC；防火墙限制探测来源。Console Proxy `19528`、web-host `19527` 保持回环。
应用实际配置看 `unitinstall/render.go`，不能只根据源码模板判断监听。

三套 CA 分开管理：MooX CA 用于主机网关 TLS，EventBus CA 用于 NATS，Console Proxy 的 internal CA 用于浏览器。
公网代理使用系统信任/ACME；internal 根证书需要由操作员核验并安装信任。代理 CA 不由普通启动隐式创建，
控制阶段持锁消费创建/导入授权；丢失已消费材料时拒绝自动重建。

## 5. 配置发布与凭据

原生部署把配置、身份和软件摘要绑定到一次操作；更换源码、参数或私密环境不能接管旧请求。
服务身份由 Admin 生成，操作员只下载自己的签名身份和公开 CA，服务私钥与 CA 私钥留在目标机。
Storage 的 node、primary、view 角色密钥独立于网关签名，按实际需要分发。

配置随单元版本发布：`moox.toml` 变更后用 `setup release build` 构建新版本，再以 `--release` 安装受影响的单元；
保留期缩短会在下一次 Storage 清理时删除数据，安装前先确认。

EventBus 角色与 TLS 材料由 Admin CLI ensure/export/rotate 管理；轮换后还须分发到实际客户端、SCF 和外置引擎。
调用方签名轮换允许新旧 KeyID 共存，替代密钥生效后才能 retire 旧密钥；Access 的静态验证文件也需重新分发。

## 6. 数据保留

| 数据 | 当前默认行为 |
| --- | --- |
| 行情与因子事实 | `[storage_retention]` 按空间和频率解析；按天桶清理，实际可能多保留不足一天；record 数据不过期 |
| `mooxsys` 主机指标 | 1m 数据集保留 7 天 |
| View 索引 | 每个序列最近 `view_rows_per_series` 根，默认 5000；超过 ceil(1.2 × N) 整理 |
| Monitor 检查结果和告警事件 | 默认 14 天；每 6 小时清理 |
| Monitor 数据链路逐根到达记录 | 7 天（按到达时间）；每 6 小时清理 |
| Strategy | 定义版本、会话、结果保留；解释明细默认 90 天；已结束回放默认 90 天且每空间最多 50 个 |
| Trade 订单成交、Archive Parquet | 不自动按统一期限删除 |
| EventBus | 各 Stream 独立设置保留时间与容量，见[事件总线](模块/事件总线.md) |

Storage 策略的原生路径是发布内各角色的 `config/storage-policy.json`。缩短保留期会删除超期事实，
需要在发布前核对。SQLite 空闲页和 Pebble 删除标记的磁盘回收还取决于复用或 compaction。
日志轮转分两层：各模块的框架日志用 trpc 的 file writer 按大小轮转（`<发布目录>/<组件>/logs/trpc.log`，单个 10MB、保留 5 份、最多 7 天，
admin、cloudfunction、eventbus、factor-mgr、collector、monitor、strategy 与 access、egress-proxy、storage、trade 同类，文件名和备份份数略有不同）；
组件的标准输出/错误追加写入 `<部署根>/run/logs/<组件>.log`，没有常驻进程可以实时切割，所以 `moox-runtime` 在每次启动前按大小轮转
（超过 50MB 就轮转，保留 5 份）；运行中它主要是崩溃信息和数据库（GORM）日志，持续报错时仍可能增长，要靠启动前轮转和告警兜底。`moox.toml` 的 `[local_logs]` 只属于旧部署脚本，不影响原生部署。旧部署脚本的统一日志轮转和 CLS 预检不等于原生部署已接入相同流程。

### 系统级重置（`moox-cli system reset`）

整个系统回到「刚部署完、尚未 init」的状态（删除运行数据，`--scope all` 再删业务配置，保留 Admin 的用户/密钥/主机等引导身份层与发布内的配置文件），用 `moox-cli system reset plan` → `apply`，流程和各模块的清单见[暂停恢复与重置设计](计划/暂停恢复与重置设计.md)第 5、6 节和[命令行工具](模块/命令行工具.md)。要点：

- 前提：各模块进程配置了重置专用密钥（`MOOX_HEALTH_RESET_ACCESS_KEY` / `_SECRET_KEY`，与运行时的健康密钥不同），否则重置接口一律拒绝；
- Trade 的实盘账户有持仓或未完成订单时会阻止，重置不撤单也不动交易所；
- Storage、Admin 业务部分是外部步骤，在各自主机上执行并用 `--external-done` 继续；Storage 的 `all` 范围顺序是 `reset-view-consumers --reset-all-storage-data --restart=false` → `reset-metadata` → 启动 Storage → `activate-datasets`；
- 重置后 Collector 要 `fetch-plan reregister`，各模块再按常规流程 init → start → confirm；CloudFunction 与引导身份层默认不动。

#### 线上的手工配置（2026-10-22 演练时做的，重新生成发布目录会丢，要重做）

- **重置专用密钥**：每个模块一把（访问标识 `reset-<模块名>`，密钥是随机生成的），写在各模块的运行时密钥文件里的 `MOOX_HEALTH_RESET_ACCESS_KEY` / `MOOX_HEALTH_RESET_SECRET_KEY`：
  控制机 `/data/moox/prod/current/secrets/runtime-<strategy|collector|monitor|factor-mgr|archive-mgr>.json`、海外机 `/data/moox/trade/current/secrets/runtime-trade.json`、
  因子机 `~/moox/factor-engine/secrets/health-auth.env`。原位追加（保持 600），改前备份在各机 `backups/reset-keys-<日期>/old/`，改完执行 `moox-runtime reseal --unit-root <单元> --yes`（`native-release.sh install` 会顺带做），重启模块生效。
  密钥不入库、不打印；操作机取用的做法见演练助手（经 SSH 读出后只放进环境变量）。
- **Collector 健康端口请求时限**：`collector/config/trpc_go.yaml` 里 `trpc.moox.collector.Health` 的 `timeout` 由 3000 改成 330000（暂停要等 SCF 定时器停用确认，最长 5 分钟）。
- **`moox-admin-cli`、`moox-storage-cli`** 用 `native-release.sh install --name <二进制名> --no-restart` 单独替换（线上旧版没有 `reset-business`，旧版 `reset-view-consumers` 在原生布局下会被自己的路径检查拒绝）。

### 清空全部数据重新积累

整体清空行情与因子数据（例如测试环境换方案）要按下面的顺序做，四步缺一不可：

1. 停止因子引擎（因子机上的 systemd 用户单元 `moox-factor-engine`）：它持有账本文件，还会往 Storage 写结果。
2. **清 Storage**：在 Storage 主机上执行 `moox-cli storage reset-view-consumers --reset-all-storage-data --package-root /data/moox/storage/current --storage-conf /data/moox/storage/current/storage-view/config/storage.yaml --yes`（先加 `--dry-run` 只做预检，不改任何状态）。
   不需要任何 EventBus 凭据：命令用 storage-view 自己的网关身份调用 Admin 的 `InspectEventBus`、`DeleteEventBusConsumers`、`PurgeEventBusSubjects`，
   由 Admin 用数据库里的 EventBus 管理员令牌连接 EventBus 代为执行（EventBus 与 Admin 同机时走本机回环，否则走登记的对外地址）。
   Admin 只放行固定范围：`MOOX_STORAGE` 流、Storage View 的消费者（两个固定的 `storage_view_factor`、`storage_view_misc`，以及按数据集动态创建的 `storage_view_misc_<12 位十六进制>`、`storage_view_factor_<12 位十六进制>`）、数据集事件的确切主题（不接受通配符），所以这个身份不能借此清空别的流或删别的消费者。
   预检会真实走一遍这条路径（网关路由、Admin 连 EventBus、流是否存在），Admin 或 EventBus 不可用时在动手前就报错，不会停了 Storage 才失败。
   它停止 Storage、备份元数据、复位全部 View 的元数据并删除索引、清 `MOOX_STORAGE` 事件流和 Pebble 数据，再重启并等待 View 就绪；
   包括主机指标（`mooxsys`）在内的全部行数据都会被清掉，数据集、View、标的等定义保留。
   **建议加 `--timeout`**：默认只有 5 分钟，命令重启后要等所有 View 重建出活动索引。带 `--reset-all-storage-data` 时 View 是空的，几分钟内就绪；
   不带它（只重置 View，Primary 数据保留）时，每个 View 要从 Primary 回溯每个序列最近的 K 线再写入 DuckDB，线上 19 个 View 实测约 26 分钟，所以有历史数据时用 `--timeout 60m`。
   等待超时不代表重置失败：超时发生在重置提交之后，命令会报“重置已完成……View 仍在后台从 Primary 回溯重建，不需要也不应该重新执行重置”，
   不要重复执行，用包根目录的 `healthcheck.sh` 和元数据库里 `t_views` 的 `c_active_index_id` 观察进度（空值就是还在重建）；Storage 保持运行。
   重置与重建期间 Storage 停机和 View 暂缺，Collector、因子引擎的写入会失败几分钟，可能留下短缺口，由自动补采和因子缺口保护处理。
3. **让 Collector 重新登记**：对每个有采集计划的空间执行 `moox-cli collector fetch-plan reregister --space-id <空间> --yes`。
   Pebble 里登记的序列快照在第 2 步被一并清掉，而对账只在数据集标的集合变化时才重新登记，不做这一步实时采集的周期提交会一直被拒绝
   （症状：补采能写入、实时采集不写入）。命令把已生效计划里的数据集标记为“快照未登记”，约 1 分钟内对账生成新计划并登记；
   1m 数据集约 2 分钟后恢复写入，1h 数据集等下一个整点，计划在最后一个整点之后才算生效。同时清掉该空间的补采作业、自动补采水位与历史扫描记录；
   此后检查、自动补采与历史扫描都从新计划的生效周期起算，清库前的计划段不再参与。
   空间里还有未生效的计划时会拒绝，等它生效后重试。
4. **清因子缺口账本并启动引擎**：`moox-factor-engine reset-gap-ledger --config config/engine.yaml --yes`（引擎还在运行时拒绝执行），然后启动引擎。
   账本里的待恢复项指向已经不存在的数据，不清的话恢复一直白跑，超过 `gap.give_up_after` 还会告警。

清完之后的预期：停机的几分钟和第 3 步生效前会有一小段缺口；因子集要等回看窗口积累够才能出完整结果（回看长度由因子自己决定，
1m 因子集约 1 小时，1h 因子集可达两天多），期间这些数据集在页面上显示“数据积累中”（降级），但不告警：因子引擎把空洞保护、预热中的运行报告为 `partial`，策略把历史不足（`history_insufficient`）、上游因子被跳过的周期报告为 `partial`，Monitor 的新鲜度检查据此按通过记录。策略的积累期有上限（`min_age_bars` 对应的时长与 72 小时取较大者，再加一小时），超过仍然不足说明不是在积累，回到失败与告警。

### SCF 定时触发采集（Timer 模式）配置

SCF 采集统一使用 Timer 模式：函数的数量、标的分配和定时器由 Collector 的对账协程按任务与标签成员自动创建和维护，运维只需要声明“哪些空间的哪些市场在哪些地域运行”。在 `moox.toml` 里写 `[scf_plan]`（示例见 `moox.toml.example`）：

- **空间与市场**：`[[scf_plan.spaces]]` 的 `markets` 把市场（`spot`、`swap`、`equity`……）映射到运行地域；`package_name`（默认 `moox-collector-<space>-plan`）与 `namespace`（默认 `moox-<space>-plan`）可覆盖。
- **地域网络**：`[scf_plan.regions.<region>]` 给出函数所在 VPC 与子网。函数通过同地域主机的私网地址访问 Access，所以该地域必须有一台配置了 `region` 与 `private_address`、并在 `[deployments]` 里带 `access` 组件的主机，Access 的地址与身份由此自动推导。
- **云账号**：`[scf_plan.cloud_account]`。
- **入口主机**：同地域只有一台带私网地址的 access 主机时自动选用；有多台时必须用 `scf_plan.regions.<region>.access_host` 指定。
- **关闭与移除**：从配置里移除某个空间（或关闭 `[scf_plan]`）不是“停止管理”而是“停止采集”：Collector 重启后发现库里有该空间的采集计划、配置里却没有它，会先把它的函数定时器停用并读回确认再退出。重新加回配置后按原计划恢复。

自动完成的部分：

- `setup deploy`：渲染 Collector 的 `scf_regions`、`scf_markets`、`scf_plan`。代码包只写**名称**，Collector 每轮解析该名称的最新可用版本；函数的空间身份与 Storage 应用密钥由 Collector 自己生成（应用密钥由控制机身份里的 Storage 主密钥派生，不落配置文件），日志服务配置由 CloudFunction 创建函数时补齐，所以不再需要手工维护 `scf-plan-env.json`。
- `setup init`：登记云账号、开通日志服务，并为每个空间检查代码包：已有可用版本就沿用，没有则构建上传。失败不阻断初始化，结果在摘要的 `scf_plan` 里。
- **代码升级**：执行 `moox-cli collector function upload --package-name <名称> ...`。Collector 在一分钟内解析到新版本，落后的函数自动升级，不需要改配置或重启。

### 日志服务（CLS）自动开通

SCF 采集函数的日志不会自动投递，排查“某个标的某一分钟为什么没采到”依赖函数主动上报的 CLS 日志，因此开通和下发不需要人工参与：

- **初始化时开通**：`moox-cli setup init` 在登记云账号之后，用该账号幂等开通 CLS（服务、日志集 `moox`、主题 `moox-application`），并补齐采集日志字段的键值索引。开通失败不阻断初始化，结果在摘要的 `cls` 里（`status=failed` 时修复权限后重跑即可）。
- **创建函数时下发**：CloudFunction 在创建采集函数、以及启用定时器的配置更新时，把上报环境变量（`MOOX_CLS_*`）补进函数环境，首次使用时同样幂等开通；已声明 `MOOX_CLS_ENABLED` 的函数保持不动。这是尽力而为的附加动作：开通失败、补齐后环境超过平台 4KB 上限都只记日志并保持原环境，停用定时器的更新从不触发它。由 CloudFunction 配置 `cls:` 控制（默认开启）。**建议配置专用的只写凭证**（`cls.writer_secret_id` 与 `cls.writer_secret_key_file`，CAM 子账号只给该主题的日志写入权限）：开通仍用云账号管理密钥，函数环境里只放写入凭证；不配置时退回把管理密钥放进函数环境，并记告警。
- **上报内容**：
  - `market_fetch_item_failure`：失败项，含错误全文、尝试次数、取数耗时。
  - `market_fetch_batch`：批次摘要，含条数、失败数、取数耗时、剩余窗口、已用权重，以及取数项的阶段耗时汇总：`since_close_start_ms`／`since_close_fetch_end_ms`（批次开始、取数结束相对收盘的毫秒数，仅周期提交请求有）、`item_p50/p90/max_ms`（单项取数耗时）、`queue_max_ms`（等并发名额）、`dns_max_ms`、`connect_p90/max_ms`、`tls_p90/max_ms`、`ttfb_p50/p90/max_ms`（写完请求到收到响应首字节，即行情源处理与网络往返）、`attempts_total`、`retried`（尝试次数或 HTTP 请求数大于 1 的项数）、`http_requests`、`conn_new`／`conn_reused`。
  - `market_fetch_item_slow`：单项取数超过 1 秒或重试过的项，每批最多 8 条（最慢的优先），含 `fetch_ms`、`queue_ms`、`attempts`、`http_requests`、`dns_ms`、`connect_ms`、`tls_ms`、`ttfb_ms`、`http_status`、`endpoint`、`remote_addr`、`since_close_start_ms`。正常请求不逐项上报，避免日志量随标的数增长。
  - 失败的 HTTP 尝试：批次摘要带 `fail_total`（失败尝试数）、按原因的 `fail_timeout`／`fail_reset`（对端重置或提前关闭）／`fail_tls`／`fail_dial`／`fail_status`／`fail_other`、按阶段的 `fail_in_connect_phase`（建连前：DNS、拨号、TLS、等连接）／`fail_in_wait_response`（已发出请求没有首字节）／`fail_in_io_phase`、`fail_on_reused_conn`（失败发生在复用的旧连接上，用来判断是否空闲连接已被对端关闭）、`fail_ms_p50`／`fail_ms_max`；偏慢单项的 `attempt_trace` 逐次列出“域名:阶段:原因或状态码:耗时:new 或 reused<空闲毫秒>”，用分号分隔。
  - 取数阶段的更多线索：偏慢单项的 `attempt_trace` 每次请求后接 `|` 明细：`dns`、`c`（TCP 建连）、`t`（TLS）、`w`（发起到请求写完）、`f`（写完到首字节，-1 表示没有首字节）、`ip`（对端地址）、`pop`（CDN 节点 x-amz-cf-pop）、`cache`（x-cache）、`skew`（服务端 Date 与本机收到时刻之差，毫秒）、`body`（非 200 响应体前 100 字节，如 202 的内容）。批次摘要另带函数进程与触发的上下文：`timer_late_ms`（函数入口晚于定时事件计划时间多少）、`stagger_ms`（函数内错峰等待）、`entry_to_start_ms`（入口到开始取数，含建立到 Access 的连接与错峰）、`proc_age_ms`（进程存活时间，冷启动时很小）、`invocation_seq`（进程内第几次调用）、`num_cpu`、`sched_lag_max_ms`（取数期间调度唤醒最大迟滞，CPU 吃紧时变大）与 `goroutines_max`。
  - 备援相关：批次摘要总是带 `standby_ms`（0 表示这批没有启用备援），启用的批次另有 `standby_fired`／`standby_won`；开关与含义见[采集](模块/采集.md)的“备援请求”。
  - 连接复用：批次摘要总是带 `conn_reuse`（0/1），开关与分组见[采集](模块/采集.md)的“连接复用”。
  - `market_fetch_commit`：批次写入 Storage 的 `commit_ms`、行数、数据集数与 `since_close_done_ms`（写入完成相对收盘的毫秒数），写入失败时带 `error`。
  - 字段清单在 `packages/cloudprovider/tencent/cls_fields.go` 统一维护，collector 测试保证上报字段都在索引里。新增字段需要对已有主题补齐键值索引（`moox-cli tencent ops cls bootstrap` 幂等，或 CloudFunction 下次开通时补齐），不补索引字段仍随原始日志保存，但不能按字段检索。
  - 排查整点慢：按 `function` 或市场分组，对比 `since_close_start_ms`、`item_p90_ms`、`connect_p90_ms`、`tls_p90_ms`、`ttfb_p90_ms` 与 `retried`，哪一项在整点前后明显变大，慢就在哪一段。
- **查询**：主题 ID 在初始化摘要里；`moox-cli tencent ops cls resolve` 可查询。检索时间使用毫秒。

## 7. 构建和验证

本机需要装什么、各系统（macOS / Linux / Windows）怎么准备、怎么构建与发布，见[构建手册](构建手册.md)。

make test-console-proxy
make test                 # 工作区 Go 测试与 vet、前端测试和构建

PR 上的 CI 把 `make verify` 按耗时拆成并行的作业，由 `verify-pr` 汇总：`verify (core / contracts / storage / web)` 对应 Makefile 里的 `verify-ci-<组>` 目标，
Go 工作区测试单独切成三片（`MOOX_GO_SHARD=<第几片>/3 make test-go`）；只改了 `docs/` 的 PR 只跑文档检查。新增检查时放进 Makefile 的某一组，`make verify` 与各组自动保持一致。
本机的 `make verify` 和自托管运行器的 `verify-trusted` 仍然依次全跑。

Go 版本以 `.go-version` 为准。

Linux 发布验证另行执行 `test-unit-core-linux`、`test-unit-bootstrap-linux`、`test-unit-install-linux`、
`test-unit-runtime-linux` 及 `test-host-gateway-control-e2e`。这些门禁需要预构建二进制、软件包和隔离的运行环境；
准备要求见 `scripts/test/gates/`。本机测试通过不能替代跨主机和生产业务验收。

## 8. 常见故障与处理

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| Collector 重启或发布后，监控短暂出现“发布租约被占用”，Collector 日志每分钟报 `collector publish lease is held` | 重启前旧进程提交的批次作业还在 CloudFunction 里执行，它的操作占用（每次续期到当前时间加 6 分钟）挡住了新进程；新进程的持有者 ID 与旧进程不同，必须等占用结束。租约在正常工作，不是故障 | 默认 10 分钟内（`market_health.timer_coordination_lease_grace`）不告警，通常 6 分钟左右自行恢复。超过宽限期出现“发布租约长时间被占用”时：看 CloudFunction 日志里是否有卡住的 `function-job` 作业，以及是否有 CLI 手工发布、补采在运行；不要手工删除 Admin 里的租约或占用记录 |
| CloudFunction 日志出现 `RequestLimitExceeded`、`被腾讯云限频`，Collector 日志反复出现 `cloud readback incomplete` | 腾讯云 SCF 管理接口按「API + 接入地域 + 子账号」限频（`ListTriggers` 等为 20 次/秒）；CloudFunction 已有按接口的进程内令牌桶，仍大量限频说明同一云账号被别的调用方占用，或令牌桶配置过高 | 读 CloudFunction 本地 `/metrics` 的 `moox_cloudfunction_tencent_api_throttled_total` 与 `..._wait_seconds` 定位接口；用 `tencent_scf.api_rate_limits` 调低对应接口（配置不随二进制更新，改前备份、改后重启 CloudFunction）；排查同账号的其他调用方，如手工执行的 CLI 命令 |
| 监控报“数据停止更新”，只有某个 View 的水位停滞，`storage-view` 日志反复出现“活动索引写入失败 … Duplicate key” | 一次 DuckDB 提交失败后该索引的内存状态与磁盘不一致，不会自愈 | 重启 `storage-view`；详见[存储 §6.4](模块/存储.md) |
| 监控显示入库数据集“已 N 小时没有运行”，但 View、因子和策略的水位都是新的 | 入库监控指标只在 `UpsertFields` 路径更新，周期提交路径（`CommitTimeSeriesBatch`）没有上报；已修复，旧版本才会出现 | 升级 `storage-primary`；数据本身不需要处理 |
| 新建（或启用）因子集后，`storage-node` CPU 长时间 300% 以上，引擎日志大量 `factor_read_batch_failed … i/o timeout` | 根因是 Pebble 块缓存只有默认的 8MiB，而 DataNode 数据约 1.6GB：窗口读取逐行逐列点查，每次都重新解压数据块和索引块（profile：`snappy.decode` 占 52%，其中 72% 在解压索引块）。启用成员时又会为每个成员各建一个全量回填任务，负载被放大。已改为按主机内存推算块缓存（见[存储 §6.5](模块/存储.md)），并给回填加了防护：同一因子集只建一个任务、默认只回填最近 5000 期、同时只跑一个补算任务、批量读取并发上限与退避断路（见[因子 §4](模块/因子.md)） | 看 `storage-node` 日志里的 `Pebble 块缓存` 行：命中率长期偏低或占用顶满说明缓存偏小，用 `MOOX_STORAGE_NODE_BLOCK_CACHE` 调大；紧急时先 `SetFactorSetStatus` 停用该因子集，负载立即回落。主机 CPU 持续高于 80% 约 3 分钟会触发主机 CPU 告警 |
| 监控报“collector-stream 心跳已中断”或某数据集连续多个周期缺标的，crypto 实时 K 线停写或大面积缺失 | `collector-stream` 进程挂了、海外机失联，或 WS 连接长时间失败 | 先看海外机守护是否已拉起、`collector-stream` 日志与 `moox-cli collector ingest-mode get --space-id crypto` 的连接状态。短时间恢复不了就切回 SCF 拉取：分钟第 20～40 秒执行 `moox-cli collector ingest-mode set --space-id crypto --mode pull --executor scf --yes`，进程已失联时加 `--force`（交接计划不等失联端确认）；记下各数据集的生效周期 P，P 之前缺的 K 线由补采补齐（此时本地执行端也不可用，补采要用 `scf`）。阶段 1 的合约推迟取数配置一直保留，切回后自动生效。恢复后再切回 `--mode stream --yes`。切换后因子水位会在缺数据的周期等待补采，补齐后自动追上 |
| 监控报“因子连续水位停滞” | 某集合前面有零提交或缺失超过阈值的周期，补采还没补上（或行情源确实没有） | 用 `moox-cli collector kline check` / `backfill` 补采该范围；补采成功后 Collector 通知因子补齐，水位自动前进。行情源确实没有的标的会在补采时确认，不再计入缺失比例 |
| 因子滞后在 1 分钟上下闪动 | 旧口径用“现在 − 上一期开盘时间”，刚算完的因子天然滞后一个周期 | 前端与监控按最近一根已收盘 K 线判断，落后不足 2 根视为已追平 |
| 只发布了部分组件之后，三个主机的“网关心跳”告警同时出现，Monitor 日志每分钟报 `SysDeploy catalog differs from this Monitor release`；新增的 RPC 路由 `moox-cli` 调不通 | 服务目录（`packages/servicecatalog/catalog.yaml`，新增或删除 RPC 路由、调整 ACL 都算）内嵌在 Admin、Monitor 和各主机的 host-gateway 里：Monitor 要求自己内嵌的目录与 Admin 提供的逐字节一致，不一致就停掉部署同步，网关心跳缓存不再刷新（Admin 里的网关心跳其实是新的）；host-gateway 用内嵌目录校验路由快照，目录不一致会拒绝新快照 | 目录有变化时 Admin、Monitor、每台主机的 host-gateway 要用同一个提交一起发布；只想发布 Monitor 等其他组件的代码改动而目录还没有一起发布时，用不含目录改动的目录文件构建，使内嵌目录与线上 Admin 一致 |

重启 Storage 进程的注意点：

- 更新或重启单个进程用 `restart.sh --components <id>`（`storage-primary` / `storage-node` / `storage-view`），不要整体重启。
- 重启 `storage-primary` 或 `storage-node` 会让这一刻的周期提交失败，监控的行情探针可能触发一次几十秒的短告警并自动恢复。
- `storage-node` 启动时会重放 Pebble 的 WAL（日志里能看到 `replayed N keys`），数据不丢。
- DuckDB 内存上限与临时目录的约定见[存储 §6.4](模块/存储.md)。
- 因子计算引擎不在控制主机上：它运行在因子机 `mooyang-X99`（192.168.0.103）的 systemd 用户服务 `moox-factor-engine`，更新二进制后用 `systemctl --user restart moox-factor-engine`。
  管理端租约 TTL 是 45 秒，新进程会在旧租约过期前报 `lease conflict`，约 45 秒后接管；接管后立即主动预热全部因子集（1m 约 45 秒、1h 约 80 秒，依次进行）。
  预热完成前到达的周期（通常是 1m 集合的前一两期，或在整点前一两分钟重启时的 1h 那一期）结果按失败标的上报、页面短暂显示“数据积累中”，
  跳过的结果记入跳过账本，约 5～10 分钟后由跳过恢复补算，历史结果不会缺一根（日志 `factor_gap_repaired`）。
- 重启 `factor-mgr` 时如果引擎正好在上报一个补算任务的进度，这次上报会失败，引擎放弃该任务（日志 `factor_recalc_abandoned`）；任务租约（15 分钟）过期后被重新领取、从已上报的进度续跑。
  因为补算任务同时只跑一个，这段时间里其它排队的补算任务也在等待。要避免这种等待，重启管理端前先确认没有 `running` 的补算任务。
- 引擎状态里的 lane 只包含目录里启用的因子集；没有因子集的数据集（例如还没建因子集的 1h K 线）不再出现在“数据预热”里。
