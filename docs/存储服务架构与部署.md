# Storage 服务架构与部署

本文说明 `modules/storage` 的服务角色、模块关系和部署方式。MooX 平台已经支持一个中央 Admin 管理多个 Gateway 节点，但当前 Storage 运行边界仍是单个存储节点：角色可以同机合并或拆成同机独立进程。下文中的 Storage 多机分片和同角色多实例是目标架构，不属于当前支持范围。

更细的概念定义见 `存储概念与设计意图.md`，元数据表设计见 `存储目标架构与元数据.md`，PB 协议边界见 `协议设计.md`。

## 一句话模型

Storage 使用同一个二进制 `moox-storage`，通过 `storage.roles` 选择本进程启用的运行角色：

```text
primary  负责 Metadata + PrimaryStore API，是唯一公开事实数据读写入口
shard    负责固定 shard_id 的 Pebble 在线事实主存
view     负责 View 物理索引、增量双写、租约维护和 DataView 查询
```

单机标准部署使用独立的 `storage-primary` 与 `storage-view` 进程；`storage-view` 通过 RPC 读取 `Metadata` 与 `PrimaryStore`，并通过 JetStream 接收行变更事件。Archive 属于独立的 `modules/archive` 服务。跨主机和同角色多实例仅作为目标架构保留，当前发布、部署和运维流程不对其作支持承诺。

## 角色与职责

| 角色 | 对外服务 | 本地存储 | 主要职责 |
| --- | --- | --- | --- |
| `primary` | `trpc.moox.storage.Metadata`、`trpc.moox.storage.PrimaryStore`，以及对应 HTTP 服务 | Metadata SQLite；可嵌入 DataShard | 管理元数据，校验 Dataset/Column 契约，解析路由，聚合 DataShard，发布行变更事件 |
| `shard` | 内部 `trpc.moox.storage.DataShard` | Pebble | 保存固定 `shard_id` 的在线事实主存；可嵌入 `primary` 或独立私网部署 |
| `view` | 内部 `trpc.moox.storage.ViewIndex`、`trpc.moox.storage.DataView` | 每 View/槽位独立 DuckDB 文件或 Bleve 目录 | 消费事件、物化 ViewIndex、维护租约并提供派生查询 |

`services/viewindex` 是可独立部署的 owner 服务；`view/search` 是 owner 内部的 Bleve 引擎实现，不直接暴露给用户。

## 代码模块关系

```text
modules/storage/
  cmd/server/             # moox-storage：读取 storage.roles，装配各角色
  cmd/cli/                # moox-storage-cli：初始化 metadata schema，导入 seed
  cmd/bench/              # 本地压测入口
  internal/config/        # storage.yaml 业务配置加载
  internal/rowkey/          # 稳定事实键
  internal/typedvalue/      # 统一列值
  internal/retinfo/         # RPC 返回状态
  internal/service/
    datashard/            # DataShard RPC、Pebble 和 outbox
    primarystore/         # Metadata + PrimaryStore 编排与路由
    metadata/             # Metadata contract、SQLite 和 cache
    dataview/             # DataView 查询
    viewbuilder/          # RowsCommitted 消费和增量物化
    viewindex/            # DuckDB/Bleve 物理 owner 与 RPC
```

`primarystore` 是唯一公开事实数据访问入口；DataShard、ViewBuilder 和 ViewIndex 通过明确的 owner RPC/事件契约协作，不跨边界直接访问其他进程的物理目录。

Storage 服务启动不自动创建 metadata 表。部署脚本会先运行 `moox-storage-cli init --storage-conf ... --schema-path ...`，需要导入示例元数据时再运行 `moox-storage-cli import-seed ...`。

## 数据流

### 写入事实数据

```mermaid
flowchart LR
    C["Collector / SCF / CLI"] --> A["PrimaryStore API"]
    A --> V["Schema Validator"]
    V --> R["PrimaryStoreRoute Resolver"]
    R --> P["PrimaryStore RPC"]
    P --> PB["Pebble"]
    A --> E["RowsCommitted Event"]
    E --> N["NATS / MemoryBus"]
    N --> VB["ViewBuilder"]
    N --> AR["Archive Runtime"]
    VB --> A2["PrimaryStore Read RPC"]
    A2 --> P
    VB --> VI["ViewIndex owner RPC"]
    VI --> D["DuckDB / Bleve"]
    AR --> A3["PrimaryStore Read RPC"]
    A3 --> P
    AR --> PQ["Parquet"]
```

PrimaryStore 是事实数据读写的唯一入口。`view` 和 `archive` 收到事件后，也必须通过 PrimaryStore 回读最新完整事实行；它们不直接理解 PrimaryStore 分片，也不直接访问某个 `ShardTarget`。

### 查询数据

| 查询 | 服务路径 | 存储 |
| --- | --- | --- |
| `ReadTimeSeriesRows` | Client -> PrimaryStore -> PrimaryStore | Pebble |
| `ReadRecordRows` | Client -> PrimaryStore -> PrimaryStore | Pebble |
| `QueryTimeSeriesRows` | Client -> DataView -> ViewIndex owner | DuckDB active slot |
| `SearchRecordRows` | Client -> DataView -> ViewIndex owner | Bleve active slot |

`SearchRecordRows` 属于 DataView 能力。用户不直接调用内部 ViewIndex 服务。

`QueryTimeSeriesRows` 和 `SearchRecordRows` 都只读取 `active_index_id`。旧槽位持续服务到 `ActivateViewIndex` CAS 成功，因此 schema 或容量切换期间没有读空窗。active schema 与指针一起持久化，空索引也能准确校验字段；新字段激活前返回 `VIEW_NOT_READY`。

### 时序视图查询的 limit 与 total_mode

`QueryTimeSeriesRows` 支持两种查询形态：

| 形态 | 参数 | 行为 |
| --- | --- | --- |
| 精确分页 | `page` | 服务端按 `page.page` / `page.size` 返回结果；`page.size` 省略时默认 `25` |
| 预览查询 | `limit` | 服务端最多返回 `limit` 条，并额外探测 1 条设置 `has_more`；默认浏览页传 `limit=1000` |

`total_mode` 控制是否计算精确总数：

| 值 | 行为 |
| --- | --- |
| `AUTO` | 有 `keys`、`time_range` 或 `filters` 时计算总数；无界浏览时跳过总数 |
| `NONE` | 跳过总数 |
| `FORCE_EXACT` | 计算精确总数 |

`page_result.total_state` 表示 `total` 是否可信：

| 值 | 含义 |
| --- | --- |
| `EXACT` | `total` 是精确总数 |
| `SKIPPED` | 服务端为了避免大范围 `COUNT(*)` 没有计算总数，调用方应展示“已加载 N 条”而不是“总数 N 条” |

`limit` 不能与有效 `page.page`、`page.size` 或 `page.cursor` 同时使用。

## 事件总线

写入成功后，PrimaryStore 发布 storage 领域事件：

```text
moox.storage.time_series.rows_committed.v1
moox.storage.record.rows_committed.v1
```

同进程部署可以使用 `eventbus.type: memory`。跨进程部署必须使用 `eventbus.type: nats` 或等价跨进程传输；否则 `view` 和 `archive` 收不到 PrimaryStore 发布的变更事件。

NATS 配置要点：

| 字段 | 说明 |
| --- | --- |
| `eventbus.nats_url` | 所有 storage 进程连接同一个 NATS |
| `eventbus.stream_name` | storage 事件所在 JetStream stream |
| `eventbus.subject_prefix` | subject 前缀，默认 `moox.storage` |
| `eventbus.consumer_name` | 每个角色或副本使用独立 consumer 名，避免 durable 冲突 |
| `eventbus.embedded.enabled` | 只应由一个进程开启；多机部署建议使用独立 NATS |

实时派生消费者处理新产生的行变更事件。历史补仓、断档追数和读模型重建统一通过 view 的 `op=maintain` 完成：schema 变化会用新 buildID 抢占旧构建，活动指针在最终 CAS 前不变；不提供手动重建 RPC，也不依赖事件消费者回放完整历史。

## 单机部署

单机部署把多个角色放进同一个进程。仓库默认 `modules/storage/config/storage.yaml` 使用：

```yaml
storage:
  roles:
    - primary
    - view
  primary:
    service_name: ""
  eventbus:
    type: memory
```

该配置表示：

| 行为 | 说明 |
| --- | --- |
| `primary` 和 `view` 同进程 | ViewBuilder 可以使用进程内 MemoryBus 接收事件 |
| `primary.service_name: ""` | PrimaryStore 自动创建本地 PrimaryStore，并暴露 `trpc.moox.storage.PrimaryStore` |
| Archive | 不属于 `storage.roles`；由独立 `modules/archive` 服务负责 |

Archive 通过 Metadata/PrimaryStore RPC 读取数据，生产环境使用 NATS 接收行变更事件；它不在 `moox-storage` 进程内注册运行角色。

## 多机部署

多机部署把角色拆成独立进程。最常见的拆分是 `primary`、`shard`、`view` 三类 Storage 进程，Archive 另行部署。

### DataShard 节点

DataShard 节点只负责固定 `shard_id` 的 Pebble 主存；PrimaryStore 通过内部 tRPC 调用它。

```yaml
storage:
  roles:
    - shard
  primary:
    shard_id: storage-shard-0
```

要求：

| 项 | 要求 |
| --- | --- |
| tRPC | 暴露 `trpc.moox.storage.DataShard` |
| 本地目录 | 拥有自己的 `devices.pebble_path` |
| 身份 | `primary.shard_id` 固定且不可变 |

多个 DataShard 节点通过 `PrimaryStoreNode` 和 `PrimaryStoreRoute` 做水平分片。

### PrimaryStore 节点

PrimaryStore 节点负责 Metadata 与事实读写入口。

```yaml
storage:
  roles:
    - primary
  primary:
    service_name: trpc.moox.storage.DataShard
  eventbus:
    type: nats
    nats_url: nats://10.0.0.10:4222
```

要求：

| 项 | 要求 |
| --- | --- |
| tRPC/HTTP | 暴露 Metadata 和 PrimaryStore |
| Metadata | 拥有 SQLite 元数据控制面 |
| PrimaryStore | 通过 `primary.service_name` 访问远程 Primary |
| EventBus | 发布行变更事件到 NATS |

### View 节点

生产部署使用一个独立的 `storage-view` 进程，同时承载物理索引 owner、事件物化和 DataView 查询。内部仍使用 ViewIndex Service/LocalClient 保持索引身份、schema fence 和生命周期边界，但不经过本机网络 RPC。

`storage-view` 只读取一个 `config/trpc_go.yaml`。该文件同时包含 tRPC server/client 和 `storage` 业务配置：

```yaml
server:
  service:
    - name: trpc.moox.storage.Health
      port: 20211
      protocol: http_no_protocol
    - name: trpc.moox.storage.DataView.trpc
      port: 20103
      protocol: trpc
    - name: trpc.moox.storage.DataView.http
      port: 20202
      protocol: http
    - name: trpc.moox.storage.ViewIndex
      port: 20104
      protocol: trpc
    - name: trpc.moox.storage.view.timer
      network: "*/30 * * * * *?scheduler=viewBuilderSchedule&startAtOnce=1"
      protocol: timer

storage:
  roles:
    - view
  devices:
    view_root: /data/moox/storage/view-indexes
  eventbus:
    type: jetstream
    nats_url: nats://10.0.0.10:4222
    consumer_name: storage_view
  view:
    metadata_service_name: trpc.moox.storage.Metadata
    primary_store_service_name: trpc.moox.storage.PrimaryStore
    index_service_name: trpc.moox.storage.ViewIndex
```

要求：

| 项 | 要求 |
| --- | --- |
| 配置 | 只有 `storage-view/config/trpc_go.yaml`，不再额外读取业务 YAML |
| ViewIndex | 监听内部 tRPC 20104；进程内唯一拥有 `view_root` |
| Builder | 通过 Metadata/PrimaryStore RPC 回读，订阅 JetStream，通过 LocalClient 写 ViewIndex |
| Query | 暴露 DataView 20103/20202，通过 Metadata RPC 和 LocalClient 查询 |
| Health | 统一使用 20211；进程退出会同时停止 Builder、Query 和 Index |

标准生产只启动一个 `storage-view` 实例。由于 DuckDB/Bleve 物理目录是本地单 owner，不得让多个实例共享同一 `view_root`。生产事件总线必须使用 JetStream，不能使用进程内 memory bus。

View 索引计时器只在 view 注册，参数统一使用 `op=maintain`。一次维护 pass 受 `run_budget`、每轮 View 数和每 View 页数约束；每页成功后持久化 cursor 并续租。owner 在可用磁盘低于配置下限时拒绝新构建。

相关业务配置位于 `storage.view.maintenance`：

```yaml
storage:
  view:
    maintenance:
      enabled: true
      owner_id: ""
      lease_ttl: 90s
      run_budget: 20s
      page_size: 500
      max_entries: 200000
      target_entries: 150000
      max_physical_bytes: 536870912
      min_free_disk_bytes: 1073741824
      min_ready_entries: 1000
      overlap_window: 30m
      allowed_lag: 2m
      remove_grace: 60s
      time_series:
        default_retention_window: 7d
        retention_by_freq:
          1m: 24h
          1h: 90d
          1d: 730d
      record:
        retention_window: 30d
```

`maintenance.enabled=false` 是完整 kill switch。`max_entries` 和 `max_physical_bytes` 是高水位；若保留窗口内数据本身仍超过高水位，系统上报 index pressure 而不会反复重建。物理布局为：

```text
<view_root>/duckdb/<space-hex>/<view-hex>/a.duckdb|b.duckdb
<view_root>/bleve/<space-hex>/<view-hex>/a|b
```

新项目需要清理旧派生格式时运行：

```bash
scripts/reset-storage-view-indexes.sh --root /data/moox/storage --yes
# 旧 metadata schema 也需要重建时追加 --metadata；PrimaryStore 始终保留
```

维护日志和指标统一携带以下字段，便于按一次切换串联控制面、owner 和查询侧：

```text
space_id view_id build_id index_id engine state owner_id
active_entries active_bytes warming_entries warming_bytes
cursor pages_written rows_written source_end coverage_end lag_seconds
switch_reason switch_duration_seconds remove_duration_seconds
```

### Archive 服务（独立模块）

`modules/archive` 负责归档运行时和 Parquet 冷归档，不使用 `storage.roles: [archive]`。

```yaml
archive:
  eventbus:
    type: nats
    nats_url: nats://10.0.0.10:4222
    consumer_name: archive_1
```

要求：

| 项 | 要求 |
| --- | --- |
| timer | 由 `modules/archive` 暴露归档任务入口 |
| Metadata | 通过 Metadata RPC 读取 Dataset、Device、ArchiveFile 元数据 |
| PrimaryStore | 通过 PrimaryStore RPC 回读待归档事实数据 |
| EventBus | 订阅 NATS 行变更事件 |
| 本地目录 | 拥有 Parquet 归档目录 |

当前 Archive 的事件 handler 只做占位 ack。后续归档策略应在 `modules/archive` 内实现，不放到 `view` 角色中。

## 服务部署信息

当前 `t_service_deployments` 默认按 HTTP 入口和 tRPC 入口分别登记。SCF 或其他后台运行时需要与 storage 交互时，应优先读取这些 active 服务部署信息。

每个服务名当前只对应一个入口。例如 `storage-primary` 只能指向一个 PrimaryStore 实例；SysDeploy 不会合并多个实例，也不会根据健康状态执行负载均衡。表中的 `active` 只表示该入口允许被使用。

| 服务名 | 角色 | 默认端口 | 说明 |
| --- | --- | --- | --- |
| `storage-primary` | `primary` | `20200` | Metadata + PrimaryStore HTTP 服务；可嵌入 DataShard |
| `storage-shard` | `shard` | 私网 `20106` | 固定 `shard_id` 的 DataShard tRPC 服务 |
| `storage-view` | `view` | `20202` | DataView + ViewBuilder HTTP 服务 |

K 线等事实写入走 PrimaryStore HTTP/tRPC；View 和独立 Archive 服务内部回读通过 Metadata/PrimaryStore RPC 完成。

远程发布或线上验证优先通过 admin gateway `11000` 调用 DataView 管理接口，例如 `/api/admin/storage/QueryTimeSeriesRows` 和 `/api/admin/storage/SearchRecordRows`。验证请求必须带小页大小或 `limit`，并设置 `total_mode=NONE` 或等价跳过精确总数的参数，避免生产环境无界扫描或大范围 `COUNT(*)`。

## 部署选择

| 场景 | 推荐部署 |
| --- | --- |
| 本地开发 | `roles: [primary, view]`，`primary.service_name: ""`，`eventbus.type: memory` |
| 单机生产或小规模使用 | 独立 `storage-primary` + `storage-view`，使用 JetStream |
| 主存数据量变大 | 拆出一个或多个 `primary` 节点 |
| View 构建影响写入 | 将统一 `storage-view` 部署到独立节点并设置资源限额 |
| 归档任务消耗 IO | 拆出独立 `modules/archive` 服务，并使用 NATS |
| 目标架构：多机部署 | `primary`、`shard`、`view` 和独立 Archive 跨主机部署；当前版本不提供统一部署和运维支持 |

核心约束只有两条：

| 约束 | 原因 |
| --- | --- |
| 跨进程派生必须用 NATS | `memory` 事件总线不能跨进程传播 |
| 派生角色必须通过 PrimaryStore/Metadata RPC 回读 | 派生角色不理解 PrimaryStore 分片，也不绕过 PrimaryStore |
