# 节点服务网关架构

> 状态：已实现。本文描述 MooX 当前运行架构，不是未来规划。

## 1. 架构结论

MooX 将浏览器控制面与机器服务数据面拆开：

- 中央 Admin 负责用户、主机、网关节点、服务实例和路由配置，是唯一控制面。
- 每台服务器运行一个独立 `moox-gateway`，只代理本机 loopback 服务。
- Caddy 是每台服务器唯一公网入口，`/api/service/*` 转发到本机 Gateway。
- Gateway 不读取 Admin 数据库，通过签名控制接口拉取本节点完整路由快照。
- 单实例 Monitor 通过本机 Gateway 暴露有界监控查询；跨节点检查由操作者在目标节点运行 Doctor，不提供 Monitor 互检或流量切换。

该架构支持一个中央控制节点管理多台服务节点，但不提供服务发现、负载均衡、跨节点转发或自动故障转移。

## 2. 总体拓扑

```text
                              中央控制节点
                    +-----------------------------+
 Browser ---------->| Caddy                      |
                    |  /            -> web-host  |
                    |  /api/admin/* -> Admin      |
                    |  /api/gateway-control/*     |
                    |                 -> Admin     |
                    +---------------+-------------+
                                    |
                       路由拉取与状态上报
                                    |
              +---------------------+---------------------+
              |                                           |
   +----------v-----------+                     +---------v------------+
   | 广州服务节点          |                     | 香港服务节点          |
   | Caddy : HTTPS        |                     | Caddy : HTTPS        |
   | /api/service/*       |                     | /api/service/*       |
   |        |             |                     |        |             |
   | Gateway 127.0.0.1    |                     | Gateway 127.0.0.1    |
   | :11002 / :11003 / :11012 |                 | :11002 / :11003 / :11012 |
   |        |             |                     |        |             |
   | 本机 Monitor 等服务   |                     | 本机业务服务          |
   +----------------------+                     +----------------------+
```

中央控制节点也运行自己的 Gateway。单节点部署是同一模型的特例，不会退回由 Admin 代理 `/api/service/*`。

## 3. 组件职责

| 组件 | 职责 | 明确不负责 |
| --- | --- | --- |
| Admin | 管理网关节点和服务实例，编译节点路由，提供控制接口，记录应用状态 | 代理 `/api/service/*`、跨节点转发、服务负载均衡 |
| Node Gateway | 拉取并原子应用本节点路由，校验 service HMAC，代理到本机服务 | 修改路由、直连远端服务、读取 Admin 数据库 |
| Caddy | TLS 终止和公开路径分流 | 业务鉴权、动态服务发现 |
| 本机业务服务 | 提供 tRPC HTTP 接口和本机诊断接口 | 直接暴露公网端口 |
| Monitor | 单实例保存监控事实、告警并提供 `GetDoctorContext` | 对端互检、网关路由切换或服务流量接管 |

## 4. 控制面与路由模型

Admin 使用两类记录维护路由：

- `t_gateway_nodes`：保存稳定 `node_id`、公开地址、启用状态和 Gateway 最近应用状态。
- `t_service_deployments`：保存服务所属 `node_id`、本机协议/地址/端口、`gateway_service_id`、tRPC 路径和是否允许网关暴露。

一条可下发路由必须同时满足：

1. 网关节点状态为启用。
2. 服务实例状态为 `active` 且 `gateway_enabled=true`。
3. 上游协议为 HTTP，地址只能是 `127.0.0.1` 或 `::1`。
4. `gateway_service_id` 在同一节点内唯一。

路由生命周期如下：

```text
管理员保存节点/服务实例
        |
        v
Admin 按 node_id 编译完整路由快照和 route_hash
        |
        v  control HMAC + X-Moox-Target-Node
Gateway 定时拉取（默认 15 秒）
        |
        v
校验全部路由 -> 原子替换内存表 -> 落盘 routes.json -> 上报 applied_route_hash
```

路由表没有草稿、发布版本或回滚历史。配置有误时 Gateway 拒绝整份新快照，继续使用上一份有效路由，管理员直接修正服务管理记录。

## 5. 请求链路

```text
调用方
  -> HTTPS /api/service/{service}/{method}
  -> 节点 Caddy
  -> 127.0.0.1:11002 moox-gateway
  -> service HMAC、时间戳、nonce、target node 校验
  -> 路由匹配
  -> http://127.0.0.1:{port}/{trpc-service}/{method}
  -> 本机业务服务
```

Gateway 保留必要的请求与响应语义，但会过滤 hop-by-hop 和不应向下游透传的鉴权头。请求只能命中当前节点路由，不能借一个节点的 Gateway 访问另一台机器。

## 6. 鉴权与安全边界

- 控制面和服务面都使用 `moox-gateway-auth-v1`，但必须使用不同密钥。
- control key 仅由 Admin 和所有 Gateway 持有；service key 由 Gateway 和授权机器调用方持有。
- 签名绑定 HTTP 方法、路径、body hash、时间戳、nonce 和目标 `node_id`。
- Gateway 使用持久化 nonce 存储防止进程重启后重放。
- HTTPS 通过明确的 CA bundle 校验，不允许跳过证书验证。
- Gateway HTTP 服务端口 `11002`、native tRPC 服务端口 `11003`、诊断端口 `11012` 和所有业务上游端口仅监听 loopback。
- 公网只开放 Caddy HTTPS；诊断路由不会通过 Caddy 暴露。
- 密钥通过权限为 `0600` 的文件安装，不写入 YAML、源码或日志。

## 7. 可用性语义

| 场景 | 行为 |
| --- | --- |
| Gateway 首次启动且 Admin 可用 | 拉取有效快照后 ready |
| Gateway 首次启动且 Admin 不可用、无缓存 | 保持 not ready，不接受业务流量 |
| 已成功运行后 Admin 暂时不可用 | 保持 ready，继续使用最后有效路由并记录同步错误 |
| Admin 下发非法快照 | 拒绝整份快照，保留旧路由 |
| 本机目标服务不可用 | 当前请求失败，不自动转发到其他节点 |
| Monitor 不可用 | `doctor diagnose` 返回 `INCONCLUSIVE` 和 `run_bootstrap`；不自动切换到另一套诊断流程 |

本地 `routes.json` 是恢复缓存，不是人工配置源。Admin 控制面恢复后，Gateway 会继续拉取并收敛到最新配置。

## 8. 部署形态

### 中央控制节点

运行 Caddy、web-host、Admin、Gateway，以及该机器需要的本地业务服务。Admin 只在这里部署。

### 普通服务节点

使用 `--no-admin` 部署 Caddy、Gateway 和本机业务服务。该模式不包含浏览器站点、Admin schema 或 Admin 凭据，Caddy 只公开 `/api/service/*`。

### Monitor 部署边界

V1 只允许一个 Monitor 实例。它依赖 EventBus 指标链路和既有只读历史，不支持 `peer-only` 模式。远程诊断通过现有 SSH 运维入口在目标节点运行 `moox-cli doctor bootstrap|diagnose`，不在 Monitor 内增加 SSH 或跨节点编排。

## 9. 端口与路径

| 端口/路径 | 所有者 | 暴露范围 | 用途 |
| --- | --- | --- | --- |
| HTTPS（部署参数决定） | Caddy | 公网 | 中央站点和各节点公开入口 |
| `/api/admin/*` | 中央 Caddy -> Admin `11000` | 中央节点 | 浏览器控制面 |
| `/api/gateway-control/*` | 中央 Caddy -> Admin `11000` | Gateway 可达 | 路由拉取与状态上报 |
| `/api/service/*` | 节点 Caddy -> Gateway `11002` | 节点公网入口 | 机器服务调用 |
| `127.0.0.1:11002` | Gateway | loopback | HTTP service 代理入口 |
| `127.0.0.1:11003` | Gateway | loopback | native tRPC service 代理入口 |
| `127.0.0.1:11012` | Gateway | loopback | `healthz`、`readyz`、`metrics` |
