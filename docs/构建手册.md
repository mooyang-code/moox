# 构建手册

MooX 的所有二进制都在**你自己的机器上**构建，再发布到线上主机。本手册讲清楚三件事：本机需要装什么、怎么构建、怎么发布；
每件事都按 macOS、Linux、Windows 分别说明，并且写成 Agent 能照着执行的形式，见“[让 Agent 代劳](#让-agent-代劳)”。

## 先看全貌

| 要构建的东西 | 在哪里构建 | 需要 |
| --- | --- | --- |
| 纯 Go 的服务和命令行（绝大多数组件） | 本机用固定版本的 Go **交叉编译**成 `linux/amd64` | Git、固定版本的 Go |
| **Storage**（`storage-primary`、`storage-node`、`storage-view`，依赖 DuckDB，需要 CGO） | 本机的 **Docker 编译镜像**里 | + Docker |
| 前端与 Web Host | 本机用 Node 构建，再嵌进 Web Host 的 Go 二进制 | + Node、pnpm |
| 因子机上的外部程序（因子引擎、归档 worker，只支持 Linux） | 与其他纯 Go 目标一样交叉编译成 `linux/amd64`，随 release 交付 | Git、固定版本的 Go |

没有专用的“编译机”：不需要登录任何远程主机去编译，线上主机只负责运行。

### 哪些系统可以用

| | macOS | Linux | Windows（WSL2，**推荐**） | Windows（Git Bash） |
| --- | --- | --- | --- | --- |
| 构建纯 Go 目标 | ✅ | ✅ | ✅ | ✅ |
| 构建 Storage（Docker） | ✅ colima / Docker Desktop / OrbStack | ✅ Docker Engine | ✅ Docker Desktop + WSL 集成 | ✅ Docker Desktop |
| 构建前端、Web Host | ✅ | ✅ | ✅ | ✅ |
| 推送前本地预检 | ✅ | ✅ | ✅ | ❌ 没有 rsync，请用 WSL |
| 发布到线上主机 | ✅ | ✅ | ✅ | 请用 WSL |

构建脚本是 bash 写的，所以 Windows 上要在 **WSL2 里**运行（Ubuntu 里的行为与 Linux 完全一致）；Git Bash 只适合只构建、不预检不发布的场景。
处理器是 Intel / AMD 还是 Apple 芯片、ARM 都可以：产物固定是 `linux/amd64`，Apple 芯片上的编译镜像用 arm64 的交叉编译器产出它，不需要 x86 模拟。

### 三步上手

```bash
# 1. 检查环境：缺什么、怎么装，一次说清
bash scripts/build/check-build-env.sh --profile all

# 2. 按“修复”一列补齐（见下面各系统一节），重跑第 1 步直到全部通过

# 3. 构建
bash scripts/build/build-linux-local.sh admin monitor collector storage-primary
```

这三步和发布都可以直接交给 Agent，见文末。

## 1. 前置依赖

### 1.1 总表

`check-build-env.sh --profile <场景>` 只检查你要做的事需要的那部分：

| 场景 `--profile` | 用来做什么 | 需要 |
| --- | --- | --- |
| `build` | 构建纯 Go 的 Linux 二进制 | Git、固定版本的 Go、SHA-256 工具 |
| `cgo` | 再加上构建 Storage | + Docker 正在运行，可用内存 ≥ 4 GB |
| `web` | 再加上构建前端与 Web Host | + Node、pnpm |
| `verify` | 推送前本地预检（`scripts/ci/local-verify.sh`） | + make、真正的 `rg`、Python 3、jq、rsync、Node、pnpm |
| `release` | 发布到线上主机 | + Docker、ssh、scp |
| `all` | 以上全部（默认） | — |

各工具的版本要求：

| 工具 | 版本要求 | 说明 |
| --- | --- | --- |
| Go | **与仓库根 `.go-version` 完全一致**（当前 `1.27.2`） | 不接受更新或更旧的版本，也不会联网下载 toolchain；用 `install-go.sh` 装到 `~/.local/go<版本>`，不影响系统里已有的 Go |
| Git | 任意 | 版本信息取自当前提交；发布要求工作区干净 |
| Docker | 能 `docker info`，可用内存 ≥ 4 GB | 只有构建 Storage 和发布用；macOS 优先 colima |
| Node.js | `^20.19.0 \|\| ^22.13.0 \|\| ≥24`，推荐 24 | 低于 22.13 的前端测试会报 `ERR_REQUIRE_ESM` |
| pnpm | 仓库固定 `10.28.2` | 用 corepack 启用 |
| make、rg、jq、rsync、Python 3 | 任意 | 只有本地预检用；`rg` 必须是真正的可执行文件，shell 里的别名或函数不算 |
| ssh、scp | 任意 | 只有发布用；发布只用 SSH 公钥 |

其他条件：

- **磁盘**：预留 10 GB 以上（Docker 镜像和缓存卷、Go 模块与编译缓存、`node_modules`）。
- **网络**：需要能访问 Go 模块代理、npm 仓库和 Docker 基础镜像 `ubuntu:22.04`。国内直连很慢，换镜像的办法见“[国内网络](#国内网络)”。
- **权限**：装系统软件（`sudo`、管理员 PowerShell）需要你自己输入密码，Agent 不会也不应该索取。

### 1.2 macOS

```bash
# 基础工具（Apple 芯片和 Intel 一样）
xcode-select --install                               # git、make
brew install ripgrep jq python node@24 && brew link --overwrite node@24   # 只做 verify / web 时才需要
corepack enable && corepack prepare pnpm@10.28.2 --activate               # pnpm

# 固定版本的 Go：装到 ~/.local/go<版本>，不改动系统里已有的 Go
bash scripts/build/install-go.sh

# Storage 需要 Docker：colima（命令行，免图形界面和许可确认）；已经装了 Docker Desktop 或 OrbStack 就直接用它们
brew install colima docker
colima start --vm-type vz --cpu 4 --memory 8
```

验证：`bash scripts/build/check-build-env.sh --profile all` 全部 `[通过]`。以后每次开机后构建 Storage 前先 `colima start`（`colima status` 看是否在运行）。

### 1.3 Linux（Debian / Ubuntu / RHEL / Fedora / Arch 等）

```bash
# Debian / Ubuntu
sudo apt-get install -y git make curl ripgrep jq rsync python3 openssh-client
# RHEL / Fedora
sudo dnf install -y git make curl ripgrep jq rsync python3 openssh-clients

bash scripts/build/install-go.sh                      # 固定版本的 Go

# Storage 需要 Docker
sudo apt-get install -y docker.io                     # RHEL 系：sudo dnf install -y docker && sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"                       # 重新登录后生效

# Node 24（发行版自带的通常太旧）：用 nvm 或 NodeSource，见 https://nodejs.org/en/download
corepack enable && corepack prepare pnpm@10.28.2 --activate
```

验证同上。`docker info` 提示权限不足时，多半是当前用户还不在 `docker` 组里，重新登录一次。

### 1.4 Windows

分三步：**装 WSL2 → 在 Ubuntu 里按 Linux 准备环境 → 装 Docker Desktop 并打开 WSL 集成**。

```powershell
# 1. 管理员 PowerShell：装 WSL2 和 Ubuntu，装完重启电脑
wsl --install -d Ubuntu

# 2. 可选：先在 PowerShell 里检查 Windows 一侧有没有这些入口，缺什么会给出 winget 命令
powershell -ExecutionPolicy Bypass -File scripts\build\check-build-env.ps1

# 3. Storage 需要 Docker Desktop（WSL2 后端）
winget install --id Docker.DockerDesktop -e
```

然后做这几件事：

1. 打开 Ubuntu（开始菜单里的 “Ubuntu”），按上面 1.3 节（Linux）装依赖。
2. 在 Docker Desktop 的 Settings → Resources → WSL integration 里打开这个 Ubuntu 发行版，然后在 Ubuntu 里确认 `docker info` 能成功。
3. **把仓库克隆到 Ubuntu 的家目录**（`~/moox`），不要放在 `/mnt/c/...` 下：跨文件系统很慢，而且文件权限和换行符会出问题。
4. 防止脚本被改成 Windows 换行：`git config --global core.autocrlf input`，**在克隆之前**设置；已经克隆过的仓库如果脚本报 `\r: command not found`，设置后重新克隆。
5. 运行 `bash scripts/build/check-build-env.sh --profile all`。

备选的 **Git Bash**（`winget install --id Git.Git -e`）也能运行构建脚本和 `install-go.sh`，但没有 rsync，不能做本地预检；发布请用 WSL。

## 2. 构建

### 2.1 构建 Linux 二进制（线上用）

```bash
# 纯 Go 的在本机交叉编译，含 CGO 的（Storage）自动进 Docker；产物默认在 bin/
bash scripts/build/build-linux-local.sh admin monitor collector storage-primary

# 指定输出目录（可以是相对路径）
bash scripts/build/build-linux-local.sh --out /tmp/moox-bin storage
```

- 构建目标就是 `scripts/build/build.sh` 的目标名，脚本按目标自动选择“本机交叉编译”还是“Docker”。不支持 `all`：请逐个写明目标。
- 脚本在 stdout 打印 `BUILT:<文件名>:<sha256>`，进度走 stderr。每次构建先放进独立的临时目录，成功后只把这次产出的文件拷到输出目录（不比较修改时间），没有产物直接报错，所以输出目录里的旧文件不会被当成成果。
- 版本信息取当前提交，也可用 `VERSION`、`GIT_COMMIT` 环境变量覆盖。
- `make build-storage-linux` 等价于构建 `storage`；`moox-cli setup build-linux --module storage` 同样调用这个脚本。

### 2.2 构建目标速查

产物名是 `moox-<目标>`；带“+cli”的目标同时产出对应的 `moox-<目标>-cli`。

| 目标 | 产物 | 说明 |
| --- | --- | --- |
| `cli` | `moox-cli` | 运维命令行；本机自己用时不加 `-linux-local`，见 2.3 |
| `admin`、`monitor`、`collector`、`factor-mgr`、`strategy`、`trade`、`cloudfunction` | 服务 +cli | 纯 Go |
| `eventbus`、`egress-proxy`、`console-proxy`、`access`、`factor-engine`、`archive-mgr` | 服务 | 纯 Go |
| `host-gateway` | `moox-host-gateway`、`-cli`、`moox-runtime` | 每台主机都要装；改了网关 cli 也要装 |
| `hostagent` | `moox-host-agent`、`-cli` | 只支持 Linux（amd64 / arm64） |
| `collector-scf` | `moox-collector-scf` | 只支持 linux/amd64（云函数用） |
| `storage` | `moox-storage-primary`、`-node`、`-view` + `moox-storage-cli` | **CGO，进 Docker** |
| `storage-primary`、`storage-node`、`storage-cgo` | 其中一个或三个 | **CGO，进 Docker**；三个文件是同一份二进制的三个名字 |
| `storage-cli` | `moox-storage-cli` | 纯 Go |
| `web-host` | `moox-web-host` | 先构建前端，见 2.4 |
| `archive-worker` | `moox-archive-worker` | 纯 Go（暂存库是 SQLite），只支持 Linux |

### 2.3 在本机运行的二进制（不是 Linux 版）

```bash
./scripts/build/build.sh cli                       # 当前系统的 moox-cli，产物在 bin/

```

因子引擎和归档 worker 只支持 Linux，由 `setup release build` 打进 release，经 `setup deploy-unit` 安装到因子机，见[部署与运维](部署与运维.md)的“因子机外部程序”一节。

### 2.4 前端与 Web Host

```bash
cd web && pnpm install && pnpm build:prod        # 生成 web/dist
cd ../web-host && make statik && make build-linux   # 内嵌前端，产物 web-host/bin/moox-web-host
```

- 国内网络先设 `GOPROXY=https://mirrors.tencent.com/go,direct`：`make statik` 要 `go run` 一个外部工具，取不到依赖就失败；
  分两条命令执行时，`statik` 失败后 `make build-linux` 仍会成功，打出来的是内嵌**旧前端**的二进制。构建后确认 `git status` 里 `web-host/internal/statik/statik.go` 已被改写。
- 构建会改写 `web-host/internal/statik/statik.go` 与 `web/src/components.d.ts`：发布后 `git checkout --` 还原，**不要提交**。
- 前端开发、测试和页面检查见[前端](模块/前端.md)。

### 2.5 Storage 的编译镜像

第一次构建 Storage 时脚本会自动构建镜像 `moox-linux-cgo-builder:go<版本>-<摘要>`（Ubuntu 22.04 + 固定版本的 Go + gcc），之后复用；
Dockerfile 或 `.go-version` 变了会按新标签重建。选 Ubuntu 22.04 做基础，是为了让产物依赖的 glibc / libstdc++ 版本较低，能在更新的线上系统上运行。
源码和产物都通过 tar 管道进出容器，不依赖主机目录能否被 Docker 挂载（colima 默认只共享 `$HOME`，远程 Docker 完全没有共享），所以输出目录可以放在任何位置。
Go 模块缓存和编译缓存放在 Docker 卷 `moox-go-mod-cache`、`moox-go-build-cache` 里，镜像和缓存都在时，构建 Storage 只要几秒。

升级 `.go-version` 时要同步更新 `scripts/build/docker/go-sha256.txt` 里两条 Linux 安装包的 SHA-256（来源 `https://golang.google.cn/dl/?mode=json`），
`scripts/test/contract/test-build-linux-local.sh` 会检查这一点。

## 3. 发布

构建好的二进制由 `skills/moox/scripts/native-release.sh` 逐台替换到线上主机。**只有你明确要求“发布某某”才发布，并且只发布点名的组件**。
完整规则、服务目录整体发布的顺序和各种陷阱见[原生部署的发布流程](https://github.com/mooyang-code/moox/blob/main/skills/moox/references/native-release.md)，这里只讲怎么上手。

### 3.1 前提

- 在 macOS、Linux 或 WSL 里运行（脚本是 bash + ssh / scp）。
- 本机构建环境通过 `check-build-env.sh --profile release`。
- 改动已提交并推送：脚本拒绝“工作区有未提交改动”和“提交还没推送”，因为线上二进制必须能对应到一个提交。
- 能用 **SSH 公钥**登录目标主机（脚本固定 `BatchMode=yes`、禁用密码登录），部署用户对 `/data/moox` 有写权限。脚本不读取 `moox.toml`，不处理任何账号密码。
- 一次性配置主机地址，写在 `~/.moox-release.env`（不入库，不要提交），模板见 `skills/moox/references/release-hosts.env.example`：

```bash
MOOX_RELEASE_HOST_CONTROL=<用户>@<控制机地址>
MOOX_RELEASE_HOST_STORAGE=<用户>@<存储机地址>
MOOX_RELEASE_HOST_OVERSEAS=<用户>@<海外机地址>
```

配好后先只读验证：

```bash
S=skills/moox/scripts/native-release.sh
$S status --host control      # 各单元组件的状态、就绪与二进制 sha
$S ledger --host control      # 发布台账：谁在什么时候装了哪个提交
```

### 3.2 发一个组件

```bash
S=skills/moox/scripts/native-release.sh

# 1. 构建：在本机构建（含 CGO 的在 Docker 里），产物放到 $TMPDIR/moox-release/<提交>/，并校验 sha
$S build collector

# 2. 安装并重启；输出里的 BACKUP 要记下来，回滚用
$S install --host control --unit prod --file <上一步的 moox-collector> --restart collector

# 3. 核对：组件 ready=True，sha 变成新构建的 sha
$S status --host control

# 出问题时回滚
$S rollback --host control --unit prod --backup <install 输出的 BACKUP> --restart collector
```

`install` 会上传并核对 sha、备份旧二进制、原子替换、重启、再核对重启后的 sha 与就绪状态，任何一步失败都会非零退出。
一次只动一个组件、一台主机，每步看到 `RESULT:...ready=True` 再继续。

### 3.3 组件装在哪里

| 主机 | 单元 `--unit` | 组件 |
| --- | --- | --- |
| 控制机 | `prod` | `admin` `eventbus` `monitor` `collector` `cloudfunction` `factor-mgr` `strategy` `web-host` `console-proxy` |
| 存储机 | `storage` | `storage-primary` `storage-node` `storage-view`（同一份二进制，三个文件名，分别用 `--name` 各装一次） |
| 每台主机 | `host` | `host-gateway`（连 cli 一起装）、`host-agent` |
| 存储机、海外机 | `access` | `access` |
| 海外机 | `trade`、`egress-proxy` | `trade`、`egress-proxy` |
| 因子机 | systemd 用户单元 | `factor-engine`，不走 `native-release.sh`，见发布流程文档 |

### 3.4 发布前要小心的几件事

- **改了 `packages/servicecatalog/catalog.yaml`**（新增删除路由、改 ACL、改方法超时）必须整体发布 `host-gateway admin monitor`，否则三台主机同时出“网关心跳”告警。先运行 `$S catalog-changed --since <上次整体发布的提交>`，退出码 10 表示必须整体发布。
- **配置文件不随二进制更新**：只换二进制不会带上仓库里的配置改动。
- **重启有代价**：Storage 的 primary / node 重启会让周期提交失败片刻；因子引擎重启会丢一个整点周期，要避开整点前后。
- 发布期间 Monitor 短暂出现的告警几分钟内自动恢复就是正常，超过 5 分钟再查。

## 让 Agent 代劳

三类任务各一段提示词，复制给 Agent 即可。Agent 应当先读本手册和（发布时）`skills/moox/references/native-release.md`。

### 搭环境

> 请在这个仓库里搭好 MooX 的构建环境。先读 `docs/构建手册.md`，然后：
> 1. 运行 `bash scripts/build/check-build-env.sh --profile all --json`（Windows 先运行 `scripts\build\check-build-env.ps1`，再进入 WSL，克隆位置和 Docker Desktop 的 WSL 集成按手册 1.4 节）；
> 2. 对 `status` 不是 `ok` 的每一项，执行它的 `fix` 命令；需要管理员密码的命令让我自己在终端里输入，不要索取或记录我的密码；
> 3. 重新运行检查，直到 `ok` 为 `true`；
> 4. 运行 `bash scripts/build/build-linux-local.sh admin` 验证能构建，需要 Storage 时再构建 `storage-primary`；
> 5. 把做过的事和还缺的事告诉我。

### 构建

> 读 `docs/构建手册.md` 的第 2 节，在本机构建 `<目标>`（例如 `admin collector storage-primary`），用 `bash scripts/build/build-linux-local.sh`。构建前先跑 `check-build-env.sh --profile cgo`（含 Storage）或 `--profile build`，有缺项先修好。完成后把每个产物的文件名和 sha256（`BUILT:` 行）告诉我。

### 发布

> 读 `docs/构建手册.md` 第 3 节和 `skills/moox/references/native-release.md`，把 `<组件>` 发布到 `<主机>`。先向我复述：哪些组件、哪些主机、是否涉及服务目录（`catalog-changed`），我确认后再动手。一次只动一个组件、一台主机，每步核对 `ready=True` 与 sha；记下 `BACKUP:` 行，失败就回滚并告诉我。只用 SSH 公钥，不要读取 `moox.toml`。

### Agent 需要遵守的规则

- 检查脚本的 `fix` 字段已按本机系统和包管理器选好命令；没有把握的项给出的是指引而不是命令，照指引处理，不要编造。
- Go 必须装成 `.go-version` 的版本，用 `install-go.sh`，不要用 `brew install go` 或发行版的 Go。
- 安装需要管理员权限的软件前先告诉用户，并由用户输入密码；不要绕过校验（不要 `curl -k`，不要关掉 SHA-256 校验）。
- Docker 在 macOS 上优先 colima；用户已经装了 Docker Desktop 或 OrbStack 就直接用，不要再装一套。
- 国内网络下载慢，先按下面的“国内网络”换镜像，不要反复重试直连。
- 只发布用户点名的组件；不要读取 `moox.toml`，不要把主机地址、公网 IP 写进仓库里的文档或脚本。

## 国内网络

GitHub、Docker Hub 等直连很慢时：

| 场景 | 做法 |
| --- | --- |
| 下载 Go | `install-go.sh` 默认就用官方国内镜像 `golang.google.cn/dl`；可用 `MOOX_GO_DL_BASE` 改 |
| Go 模块 | 构建 Storage 的容器默认用 `https://mirrors.tencent.com/go,direct`，可用 `MOOX_BUILD_GOPROXY` 改；本机构建（含 `make statik`）设 `GOPROXY` |
| npm / pnpm | `pnpm config set registry https://registry.npmmirror.com` |
| 镜像里的 apt | `MOOX_BUILD_APT_MIRROR=http://mirrors.aliyun.com`（中科大、清华的 http 镜像也行）。必须是**不跳转 https** 的 http 镜像：基础镜像里还没有 ca-certificates，https 源取不到索引（软件包有 GPG 签名校验）；腾讯云镜像会强制跳转 https，不能用 |
| Homebrew | 设 `HOMEBREW_API_DOMAIN` 与 `HOMEBREW_BOTTLE_DOMAIN` 指向清华镜像；**镜像在国内时直连比走本机代理快得多**，下载前取消 `HTTPS_PROXY` |
| 拉取 Docker 基础镜像 | Docker Hub 直连不通（域名会被解析到错误地址）。给 Docker 配置可用的 `registry-mirrors`：colima 在 `~/.colima/default/colima.yaml` 的 `docker:` 段写 `registry-mirrors: [https://docker.m.daocloud.io, https://docker.1ms.run]`，再 `colima restart`；Docker Desktop 在 Settings → Docker Engine 里加同样的 `registry-mirrors`；用 `curl -s -o /dev/null -w '%{http_code}' https://<镜像>/v2/` 返回 401 说明镜像可用 |
| colima 虚拟机镜像 | 第一次 `colima start` 会从 GitHub 下载约 330 MB 的镜像；太慢时经 `ghfast.top` 之类的镜像站下载 `colima-core` 发布的 `ubuntu-24.04-minimal-cloudimg-<arch>-docker.raw.gz`，校验 SHA-512 后用 `colima start --disk-image <本地文件>` |
| colima 首次启动很久 | 虚拟机第一次启动要 `apt-get update` 并装 rsync，国内访问 ubuntu 源很慢，会超过 colima 的 10 分钟等待而报 `did not receive an event with the running status`。虚拟机其实还在后台继续：用 `LIMA_HOME=~/.colima/_lima limactl shell colima cloud-init status` 看到 `done` 后，`colima stop -f && colima start` 一次即可，之后启动只要几秒 |
| colima 虚拟机里解析不了域名 | 精简镜像没有 systemd-resolved，`/etc/resolv.conf` 是悬空链接。在 `colima.yaml` 的 `provision:` 里加一段系统脚本，缺失时写入 `nameserver 223.5.5.5`，或进虚拟机手动写一次（`LIMA_HOME=~/.colima/_lima limactl shell colima sudo sh -c 'printf "nameserver 223.5.5.5\n" > /etc/resolv.conf'`） |
| 构建镜像时 apt 失败 | 见上面的 `MOOX_BUILD_APT_MIRROR`；报 `Unable to locate package` 通常是 apt 源取不到索引（https 源没有证书、或镜像把 http 跳转到 https） |
| `docker build` 提示 legacy builder | 装 `docker-buildx`（`brew install docker-buildx`），并在 `~/.docker/config.json` 加 `"cliPluginsExtraDirs": ["/opt/homebrew/lib/docker/cli-plugins"]`；不装也能构建，只是有一条弃用提示 |

## 常见问题

- **`构建没有产出二进制`**：目标名写错，或 Go 版本与 `.go-version` 不一致。先跑 `check-build-env.sh`。
- **`含 CGO 的目标需要 Docker`**：安装并启动 Docker（macOS：`colima start`）；只构建纯 Go 目标时不需要。
- **`Docker 没有在运行`**：macOS 上 `colima status` 看状态；Linux 上 `systemctl status docker`，并确认当前用户在 `docker` 组里；WSL 里确认 Docker Desktop 已启动并打开了本发行版的集成。
- **Go 版本“不符”**：系统里的 Go 不是 `.go-version` 指定的版本。运行 `bash scripts/build/install-go.sh`，构建脚本会自动优先使用 `~/.local/go<版本>/bin`。
- **容器里编 Storage 很慢或内存不足**：给 Docker 至少 4 GB 内存（colima：`colima stop && colima start --memory 8`；Docker Desktop 在 Settings → Resources 里调）。
- **shell 里的 `rg` 不生效**：`rg` 是 shell 函数或别名时，make 和脚本看不到它；装真正的 ripgrep 可执行文件。
- **前端测试报 `ERR_REQUIRE_ESM`**：Node 低于 22.13，升级到 24；`which node` 看一下排在前面的是不是旧版本。
- **脚本报 `\r: command not found`**（Windows）：仓库被改成了 Windows 换行。按 1.4 节设 `core.autocrlf input` 后在 WSL 里重新克隆。
- **发布脚本拒绝执行**：提示“工作区有未提交改动”或“提交还没推送”，先提交并推送；这是为了让线上二进制能对应到一个提交。

## 访问管理台：安装根证书

管理台用控制台代理内置 CA 签发的 HTTPS 证书，每台要访问的电脑和手机都要装一次根证书，否则浏览器会提示不安全，
页面的后台请求也会成片报“无法连接管理台”。入口在登录页底部的“下载并安装根证书”和“秘钥管理”页的“HTTPS 根证书”，弹窗会按设备停在对应页签：

- **电脑**：下载安装包，按其中 `AGENT-INSTALL.md` 的“直接安装”操作（也可以交给 Agent），装好后彻底重启浏览器；初始化管理台的那台机器已自动安装。
- **iPhone / iPad**：用 Safari 下载证书 → “设置 → 通用 → VPN 与设备管理”安装 → **“设置 → 通用 → 关于本机 → 证书信任设置”打开完全信任** → 重新打开 Safari。
- **Android**：用 Chrome 下载证书 → “设置 → 安全 → 加密与凭据 → 安装证书 → CA 证书” → 重新打开 Chrome；Firefox 还要在它自己的设置里打开“使用第三方 CA 证书”。

安装前都要核对 SHA-256 指纹。为什么用 HTTPS、为什么不改成纯 HTTP 或只点“继续前往”，见[控制台代理的访问方式安全考量](模块/控制台代理.md)。
