12. web-host 显式拒绝路径含 `..` 的请求（A21 防御性一行）。

## 批次二：数据与状态正确性

### WP-2.1 trade 交易写路径系统性修复（T1~T8、T12、T13、T17）— 约 5 人日

这是关联最紧的一组，按依赖顺序实施，整包完成后做 sandbox 全链路验证。

涉及：`modules/trade/internal/service/order_exec.go`、`service/sync.go`、`service/dao/{fund_flow,order,trade,balance}.go`、`service/decimal.go`、`rpc/server.go`、`rpc/schedule.go`、`exchange/httpclient/httpclient.go`、`exchange/binance/binance.go`

**步骤 1：撤单/改单参数补全（T2）**
- `CancelOrderExec` / `AmendOrderExec` 查到本地订单后，用 `o.Symbol`、`o.MarketType`、`o.ExchangeOrderID` 构造适配层请求，不再透传原始 req；本地无订单时报错而非盲调交易所。

**步骤 2：下单幂等（T3，按 D3 决策）**
- `PlaceOrderExec` 开头按 `(space_id, client_order_id)` 查重：已存在且非终态→幂等返回现有订单；终态→拒绝（要求换新 ID）。
- `client_order_id` 必填校验前置到 RPC 层。
- 唯一索引冲突的兜底分支保留但逻辑修正：冲突时解冻本次冻结并返回已存在订单。

**步骤 3：余额校验（T5）**
- `dao/fund_flow.go` 的 `adjustFrozen` 在 `delta>0` 时校验 `available >= delta`，不足返回 `ErrInsufficient`（已定义，接上）；同函数对结果负值做防御性拒绝。

**步骤 4：下单事务化（T8）**
- 冻结 + `SaveOrder` 包进同一 SQLite 事务；交易所调用留在事务外。
- 新增启动恢复逻辑：扫描 PENDING 且超过阈值时间的订单，按 client_order_id 查交易所对账（有单→回填 exchange_order_id 置 OPEN；无单→解冻置 REJECTED）。

**步骤 5：超时对账（T4、T11 错误分类部分）**
- `exchange/httpclient` 错误分类：网络超时/5xx 归"结果未知"，4xx 业务错误归"确定失败"（解析 Binance JSON `code`，重点识别 `-2010` 重复单、`-1021` 时间戳）。
- `PlaceOrderExec` 对"结果未知"不再直接 REJECTED+解冻，而是订单置 `UNKNOWN`（或复用 PENDING）并触发按 client_order_id 查单对账（复用步骤 4 的恢复逻辑）。

**步骤 6：成交结算接线（T1、T6、T7）**
- `AppendTrades` 前按 `exchange_order_id` 反查本地订单，建立成交↔订单关联（解决 T7 的 ID 断裂，不强行统一历史 ID 规则）。
- `SyncTrades` 对新增成交调用 `ApplyFills`；`ApplyFills` 内部改为单事务（解冻、流水、成交、订单状态原子提交），去掉所有 `_ =` 吞错（T6）。
- 无法关联到本地订单的成交（外部手工单）只落成交表并打标记，不动冻结。

**步骤 7：余额同步语义（T9）+ 杂项**
- `SyncBalances` 保留全量覆盖但改为"对账模式"：覆盖前对比本地冻结与快照差异超过阈值时告警日志（成交结算接线后差异应收敛）。
- `dao/order.go` `only_open` 集合纳入 PENDING(0)（T17）。
- `rpc/schedule.go` 默认 space 从配置读，同步失败返回 error（T12）。
- `service/decimal.go` 余额路径 `big.Float` 统一替换为 `big.Rat`（与 `order_quantity.go` 一致）（T13）。

验证：Binance testnet/sandbox 全链路——下单→部分成交→撤单→余额对账；构造超时（断网）验证 UNKNOWN 对账路径；重复 client_order_id 验证幂等。

风险：步骤 5 改变了"超时即拒绝"的现有行为，订单会短暂停留在对账中状态，前端订单列表需确认能展示；`ApplyFills` 首次接线建议先在 sandbox 环境灰度。

### WP-2.3 cloudnode 队列状态收敛（N1、N2、N4、N5、N6、N8、N9、N10、N7、N13）— 约 3 人日

涉及：`modules/cloudnode/internal/{rpc/job_item.go,rpc/node.go,rpc/package.go,jobqueue/jetstream_queue.go,projection/*,storage/database.go}`、`config/app.yaml`

1. **RUNNING 超时 reconciler（N1）**：在现有 `EnqueueReconciler` 旁新增 `RunningReconciler`——周期扫描 `c_status=running AND c_recover_at < now`，标记 attempt LOST、状态回 PENDING（未超 MaxDeliver）或 FAILED，残留 `ack_subject` 尝试 Term。
2. **AckWait 对齐 + InProgress 续租（N2，按 D5 决策）**：SCF runtime 执行长任务期间周期调用 `InProgress`（`jetstream_queue.go:149` 已实现底层，需接一个续租 RPC/心跳钩子并在 cloudruntime 执行循环中定时触发），AckWait 设合理值（如 2min）即可，不靠调大配置硬扛崩溃场景；配置加载仍校验 `ack_wait` 与 `recover_after` 关系并告警。（若近期不想动 SCF runtime，回退备选：仅把 `ack_wait_millis` 调至 `recover_after + 120s`。）
3. **Report 顺序调整（N4）**：`ReportJobItemStatus` 改为先 `executionQueue.Ack/Term`，成功后再 `PublishReported`；投影发布失败由 N1 的 reconciler + 迟到 report 幂等兜底（`repository.go:540` 已对重复事件跳过）。
4. **MaxDeliver 死信（N5）**：poll 消费侧检测 `NumDelivered >= MaxDeliver` 时主动 Term 并将 SQLite 状态置 `failed`（原因 `max_deliver_exhausted`）。
