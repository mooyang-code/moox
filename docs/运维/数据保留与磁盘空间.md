# MooX 数据保留与磁盘空间

本文说明 MooX 哪些运行数据会自动清理、保留多久、由谁负责，以及哪些数据会持续增长。目标是让部署者能在磁盘告警发生前判断容量，而不是把“有定时任务”等同于“所有目录都不会增长”。

## 结论

- EventBus、CloudNode 短期任务状态、Monitor 检查历史、Monitor 去重记录、Storage 派生 View 和 Archive 去重回执都有明确的时间或容量边界。
- Storage 主机指标默认保留 48 小时，由有超时、防重入和批次上限的 tRPC Timer 清理。
- Storage 目标使用 Schema v6；每个事实 Dataset 直接绑定一个 DataNode。DataNode 注册、Dataset
  激活和绑定锁定是 Metadata 生命周期，不是磁盘迁移策略。激活后不可在线迁移或再平衡，
  释放空间必须按 Dataset 生命周期显式授权。
- TimeSeries Dataset 按自己的 `keep_duration` 清理旧 bucket；`0` 表示永久保存。
- Archive Parquet v2 按 Subject/`series_tag`/月拆分并长期保留，默认不自动删除。
  接受每个 tag 独立文件产生的小文件；本地归档目录仍需要容量规划或迁移到更大的
  磁盘，COS 副本不会自动替代或删除本地文件。
- Admin、Trade、Strategy 等控制面 SQLite 不执行笼统的“按时间删表”。订单、成交、策略运行和审计事实不能仅为了腾磁盘而静默删除。
- 标准部署把各进程 stdout/stderr 写入 `logs/<module>/stdout.log`，当前没有统一 logrotate。这些文件不在业务数据清理任务的保护范围内，必须纳入主机日志轮转。

## 自动清理矩阵

| 数据 | 当前默认边界 | 执行方式 | 磁盘效果 |
| --- | --- | --- | --- |
| EventBus `MOOX_STORAGE` | 72 小时或 1 GiB | JetStream `limits + DiscardOld` | 达到任一边界后淘汰最旧消息 |
| EventBus `MOOX_METRICS` | 24 小时或 256 MiB | JetStream `limits + DiscardOld` | 指标消息不会无限增长 |
| EventBus `MOOX_CLOUDNODE_EXEC` | 72 小时或 256 MiB | JetStream WorkQueue | 已 ACK 消息移除，未处理消息仍受时间和字节上限约束 |
| EventBus `MOOX_TRADE` | 7 天或 256 MiB | JetStream WorkQueue | Strategy 调仓命令有界；交易事实仍由 Trade 数据库保存 |
| CloudNode active JobItem KV | 48 小时 | JetStream KV TTL | 过期 active 状态自动淘汰 |
| CloudNode JobItem 历史日库 | 正常连续运行时 2 天 | 每日 tRPC Timer | 删除指定过期日库；跨日停机后需检查更老残留 |
| Monitor 检查结果和告警事件 | 14 天 | `monitor.data_cleanup.timer` 每 6 小时执行并在启动时执行 | 控制面检查历史不会长期累积 |
| Monitor 指标消息去重记录 | 7 天 | 同一清理 Timer 每 6 小时删除过期行 | 只清理去重回执，不删除 catalog/latest/rule |
| Storage 主机指标事实 | 48 小时 | Storage PrimaryStore 每小时执行有界 tRPC Timer | 限制四个直接绑定 DataNode 的 Host Dataset 的 Pebble 历史规模 |
| Storage TimeSeries View | 默认 7 天；`moox_service_metrics` 为 3 天；`1m=24h`、`1h=90d`、`1d=730d` | View maintenance 重建并切换 a/b 槽位 | DuckDB 只保存配置窗口，旧槽位排空后删除 |
| Storage Record View | 30 天 | View maintenance 重建并切换 a/b 槽位 | Bleve 只保存配置窗口，旧目录排空后删除 |
| Archive 消息去重回执 | 7 天 | 每次物化维护时清理 | 限制 Archive Pebble journal 中的回执数量 |
| Archive Parquet 事实文件 | 永久 | 不自动删除 | 这是有意设计的长期增长项 |

表中默认值来自当前仓库配置。部署环境修改配置后，应以实际发布目录中的 `config/app.yaml`、`storage.yaml` 和 `trpc_go.yaml` 为准。

“删除过期行”和“操作系统立刻看到文件变小”不是同一件事。SQLite 删除后的空闲页通常先留在数据库内供后续写入复用，没有 `VACUUM` 时文件尺寸可以保持不变；Pebble 的删除也要等待后台 compaction 回收旧 SST 空间。判断清理是否有效时应同时观察有效行数、过期最老时间和数个清理/compaction 周期后的磁盘趋势，不能只看一次 `du`。

## Storage 主机指标清理

主机指标位于 `space_id=moox_system`，按一分钟频率写入：

- `host_resource_v1`
- `host_fs_v1`
- `host_disk_v1`
- `host_net_v1`

`trpc.moox.storage.host_metrics_cleanup.timer` 由 Storage `access` 角色每小时执行一次，删除严格早于 `now - 48h` 的数据。Handler 同步执行，Clone tRPC Context，设置 60 秒超时，并通过进程内原子状态防止重入。

每个数据集单次最多清理 10 批，每批每个解析后的 PrimaryStore target 最多删除 1000 行；遇到空页会提前结束。因此一次运行最多追赶 10000 行/数据集/target，既能处理历史积压，也不会用无界循环冲击在线读写。某个数据集失败时仍继续清理其他数据集，结束后返回汇总错误，并通过 `moox_timer_job_runs_total` 与 `moox_timer_job_duration_seconds` 暴露结果和耗时。删除标记最终依赖 Pebble compaction 回收物理空间。

该 Timer 使用 tRPC `DefaultScheduler`，只保证当前进程内调度；多副本同时运行会各自触发。当前部署应只让一个 `access` 实例承担这项清理，或在扩展到多副本前接入分布式 scheduler。

## Dataset 与 View 的保留约束

TimeSeries Dataset 的 `keep_duration` 决定 Pebble 事实 bucket 的保留窗口；View 的
`keep_duration` 决定可重建索引的查询窗口。两者遵循以下约束：

- Dataset `keep_duration` 必须为 `0`，或不短于所有引用它的 View `keep_duration`。
- `0` 表示永久保存。
- 服务指标 Dataset/View `moox_service_metrics` / `moox_service_metrics_view` 的默认窗口为 72 小时（3 天）；该 Dataset 按 30 秒频率和服务指标序列持续写入，窗口过长会快速放大 DuckDB 索引和查询工作集。
- 创建/更新 View 或缩短 Dataset 窗口时，Metadata 在写入阶段校验约束并拒绝非法配置。
- 过期 bucket 清理不发布业务事件。删除只为回收存储空间；View、Archive 等下游保留的
  副本无需跟随删除。

View maintenance 在 schema、容量或覆盖范围变化时构建非活跃槽位，追平后原子切换；
旧槽位在引用排空和 `remove_grace` 结束后删除。默认还使用 `max_entries=200000`、
`max_physical_bytes=512MiB` 和 `min_free_disk_bytes=1GiB` 作为维护与磁盘准入边界。

## 不会自动删除的数据

以下数据需要显式容量规划：

- `keep_duration=0` 的 Storage Dataset，以及不适用 TimeSeries bucket 清理的资料和业务事实。
- Archive `root_dir` 下按 Subject/`series_tag`/月拆分的 Parquet v2 文件。
- Admin、Trade、Strategy 等模块需要审计或恢复的业务事实。
- 数据库备份、发布包、core dump，以及不受 tRPC file writer 管理的外部日志。
- 标准部署生成的 `logs/<module>/stdout.log` 和 `run/caddy.log`；当前部署脚本只负责重定向，不负责轮转或按日删除。

不能用通用目录清理命令删除正在运行的 Pebble、SQLite、DuckDB、Bleve、JetStream 或 Archive journal 文件。需要释放容量时，应先确认数据所有者和恢复路径，再通过模块 API、数据集生命周期任务或停机迁移处理。

## 日常检查

在部署目录执行：

```bash
du -sh data/* logs/* 2>/dev/null | sort -h
find data/cloudnode/jobs -maxdepth 1 -name '*.db' -print 2>/dev/null | sort
find data/archive -type f -name '*.parquet' 2>/dev/null | wc -l
```

重点关注：

- `data/eventbus/jetstream` 是否接近所在分区容量。
- `data/storage` 中 Pebble 与 View 索引的增长速度是否符合数据写入量。
- `data/archive` 是否按月持续增长，并预留长期容量。
- `data/monitor/monitor.db` 是否在两个 6 小时清理周期后仍持续异常增长。
- CloudNode 历史目录是否只保留短期日库；服务长期停机后重启，应额外检查遗漏的旧日库。
- `logs/*/stdout.log` 和 `run/caddy.log` 是否由 systemd、logrotate 或主机日志平台设置了大小/天数上限。

磁盘使用率超过 70% 时应评估增长趋势，超过 80% 时应扩容或迁移长期数据，不要等到数据库写入失败后再清理。

## 配置来源

- EventBus：`modules/eventbus/config/app.yaml`
- CloudNode：`modules/cloudnode/config/app.yaml` 和 `modules/cloudnode/config/trpc_go.yaml`
- Monitor：`modules/monitor/config/app.yaml`
- Storage：`modules/storage/config/storage.yaml` 和各运行角色的 `trpc_go*.yaml`
- Archive：`modules/archive/config/app.yaml`
