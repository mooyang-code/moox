# MooX 数据保留与磁盘空间

本文说明 MooX 哪些运行数据会自动清理、保留多久、由谁负责，以及哪些数据会持续增长。目标是让部署者能在磁盘告警发生前判断容量，而不是把“有定时任务”等同于“所有目录都不会增长”。

## 结论

- EventBus、CloudNode 短期任务状态、Monitor 检查历史、Monitor 去重记录、Storage 派生 View 和 Archive 去重回执都有明确的时间或容量边界。
- Storage 主机指标已经按时间清理；当前版本默认保留 72 小时。已确定的下一步改造会调整为 48 小时，并把单页清理升级为有超时、防重入和批次上限的 tRPC Timer 任务。
- 行情、因子等 Pebble 事实数据不会被通用清理器删除。删除事实必须由数据集级生命周期策略明确授权。
- Archive Parquet 是长期归档，默认永久保留。本地归档目录仍需要容量规划或迁移到更大的磁盘；COS 副本不会自动替代或删除本地文件。
- Admin、Trade、Strategy 等控制面 SQLite 不执行笼统的“按时间删表”。订单、成交、策略运行和审计事实不能仅为了腾磁盘而静默删除。
- 标准部署把各进程 stdout/stderr 写入 `logs/<module>/stdout.log`，当前没有统一 logrotate。这些文件不在业务数据清理任务的保护范围内，必须纳入主机日志轮转。

## 自动清理矩阵

| 数据 | 当前默认边界 | 执行方式 | 磁盘效果 |
| --- | --- | --- | --- |
| EventBus `MOOX_STORAGE` | 72 小时或 2 GiB | JetStream `limits + DiscardOld` | 达到任一边界后淘汰最旧消息 |
| EventBus `MOOX_METRICS` | 24 小时或 512 MiB | JetStream `limits + DiscardOld` | 指标消息不会无限增长 |
| EventBus `MOOX_CLOUDNODE_EXEC` | 72 小时或 512 MiB | JetStream WorkQueue | 已 ACK 消息移除，未处理消息仍受时间和字节上限约束 |
| EventBus `MOOX_DLQ` | 30 天或 256 MiB | JetStream `limits + DiscardOld` | 异常消息保留较长时间，但仍有硬上限 |
| EventBus `MOOX_TRADE` / `MOOX_STRATEGY` | 7 天或 512 MiB | JetStream `limits + DiscardOld` | 事件流有界；业务事实仍由各模块数据库保存 |
| CloudNode active JobItem KV | 48 小时 | JetStream KV TTL | 过期 active 状态自动淘汰 |
| CloudNode JobItem 历史日库 | 正常连续运行时 2 天 | 每日 tRPC Timer | 删除指定过期日库；跨日停机后需检查更老残留 |
| Monitor 检查结果和告警事件 | 14 天 | 每 6 小时清理一次，启动时先执行 | 控制面检查历史不会长期累积 |
| Monitor 指标消息去重记录 | 7 天 | 记录 TTL；每 6 小时删除过期行 | 只清理去重回执，不删除 catalog/latest/rule |
| Storage 主机指标事实 | 当前 72 小时 | Storage Access 每小时删除过期行 | 限制四个 Host Dataset 的 Pebble 历史规模 |
| Storage TimeSeries View | 默认 7 天；`1m=24h`、`1h=90d`、`1d=730d` | View maintenance 重建并切换 a/b 槽位 | DuckDB 只保存配置窗口，旧槽位排空后删除 |
| Storage Record View | 30 天 | View maintenance 重建并切换 a/b 槽位 | Bleve 只保存配置窗口，旧目录排空后删除 |
| Archive 消息去重回执 | 7 天 | 每次物化维护时清理 | 限制 Archive Pebble journal 中的回执数量 |
| Archive Parquet 事实文件 | 永久 | 不自动删除 | 这是有意设计的长期增长项 |

表中默认值来自当前仓库配置。部署环境修改配置后，应以实际发布目录中的 `config/app.yaml`、`storage.yaml` 和 `trpc_go.yaml` 为准。

“删除过期行”和“操作系统立刻看到文件变小”不是同一件事。SQLite 删除后的空闲页通常先留在数据库内供后续写入复用，没有 `VACUUM` 时文件尺寸可以保持不变；Pebble 的删除也要等待后台 compaction 回收旧 SST 空间。判断清理是否有效时应同时观察有效行数、过期最老时间和数个清理/compaction 周期后的磁盘趋势，不能只看一次 `du`。

## Storage 主机指标清理

主机指标位于 `space_id=moox_system`，按一分钟频率写入：

- `host_resource_v1`
- `host_fs_v1`
- `host_disk_v1`
- `host_net_v1`

当前实现由 Storage `access` 角色每小时执行一次，删除严格早于 `now - 72h` 的数据。每个数据集、每个解析后的 PrimaryStore target 单次最多删除 1000 行，因此删除过程不会用一次大事务冲击在线读写。

当前实现只处理一页。如果积压产生速度持续高于清理速度，磁盘仍可能增长。已批准的改造方案见 [tRPC Timer And Host Metrics Cleanup Implementation Plan](../superpowers/plans/2026-07-17-trpc-timer-and-host-metrics-cleanup.md)：

- Timer 重命名为 `trpc.moox.storage.host_metrics_cleanup.timer`。
- 默认 `max_age` 改为 `48h`。
- 每个数据集单次最多清理 10 批，每批每 target 最多 1000 行；删到空页时提前结束。
- Handler 同步执行，Clone tRPC Context，设置 60 秒超时并防止同进程重入。
- 一个数据集失败不会阻止其他数据集清理，最终返回汇总错误并记录删除量、批次数和失败指标。

在该计划完成前，用户界面和运维判断必须按当前 72 小时、单页清理能力理解，不能提前把 48 小时视为已生效。

## Storage View 与事实数据不是同一保留策略

DuckDB/Bleve View 是可重建的派生读模型。View 的 `retention_window` 只决定查询索引覆盖范围，不会删除 Pebble 中的行情、因子或资料事实。

View maintenance 在 schema、容量或覆盖范围变化时构建非活跃槽位，追平后原子切换；旧槽位在引用排空和 `remove_grace` 结束后删除。默认还使用 `max_entries=200000`、`max_physical_bytes=512MiB` 和 `min_free_disk_bytes=1GiB` 作为维护与磁盘准入边界。

因此：缩短 View 窗口可以降低 DuckDB/Bleve 占用，但不会降低 Pebble 事实主存或 Archive Parquet 的占用。

## 不会自动删除的数据

以下数据需要显式容量规划：

- Storage Pebble 中的通用行情、因子、资料和业务事实。
- Archive `root_dir` 下的 Parquet 月分区文件。
- Admin、Trade、Strategy 等模块需要审计或恢复的业务事实。
- 数据库备份、发布包、core dump，以及不受 tRPC file writer 管理的外部日志。
- 标准部署生成的 `logs/<module>/stdout.log` 和 `run/caddy.log`；当前部署脚本只负责重定向，不负责轮转或按日删除。

不能用通用目录清理命令删除正在运行的 Pebble、SQLite、DuckDB、Bleve、JetStream 或 Archive journal 文件。需要释放容量时，应先确认数据所有者和恢复路径，再通过模块 API、数据集生命周期任务或停机迁移处理。

## 日常检查

在部署目录执行：

```bash
du -sh data/* logs/* 2>/dev/null | sort -h
find data/cloudnode/jobs -maxdepth 1 -name '*.db' -print 2>/dev/null | sort
find data/archive -type f -name '*.parquet' 2>/dev/null | wc -l
```

重点关注：

- `data/eventbus/jetstream` 是否接近所在分区容量。
- `data/storage` 中 Pebble 与 View 索引的增长速度是否符合数据写入量。
- `data/archive` 是否按月持续增长，并预留长期容量。
- `data/monitor/monitor.db` 是否在两个 6 小时清理周期后仍持续异常增长。
- CloudNode 历史目录是否只保留短期日库；服务长期停机后重启，应额外检查遗漏的旧日库。
- `logs/*/stdout.log` 和 `run/caddy.log` 是否由 systemd、logrotate 或主机日志平台设置了大小/天数上限。

磁盘使用率超过 70% 时应评估增长趋势，超过 80% 时应扩容或迁移长期数据，不要等到数据库写入失败后再清理。
