# MooX 总体设计

MooX 是面向个人的一站式量化平台：从行情采集、数据存储、因子计算、策略选股到交易执行，
再到全链路监控，都在同一套系统内完成，并提供 Web 管理台和 `moox-cli` 命令行两种入口。

系统按“单用户、自托管、少量机器”设计：唯一的登录用户拥有全部管理能力，不建设 RBAC；
但登录、会话、服务间请求签名和防重放始终开启，单用户不等于不设防。

## 1. 设计原则

- **事实与派生分离。** 行情、因子结果等事实由 Storage 的 DataNode 持久化；查询用的 View
  索引、监控指标历史都是可以重建的派生数据。
- **事件驱动，消费者自治。** 跨模块的异步协作统一走 EventBus（内嵌 NATS JetStream）。
  EventBus 只声明 Stream，每个消费方自己创建并拥有 Consumer。
- **控制面与数据面分离。** Admin 维护服务目录和路由（控制面）；每台机器上的节点网关只负责
  把已签名的服务请求转发到本机服务（数据面）。控制面故障不影响已缓存路由的数据面。
- **按模块独立部署。** 每个业务模块是一个独立进程，自带 SQLite 或 Pebble 存储，模块之间只通过
  RPC 和事件交互，不共享数据库，也不跨模块引用 `internal` 代码。
- **短时计算放到云函数。** 行情抓取运行在腾讯云 SCF 上，每次触发只执行一批请求，不常驻；
  控制面负责规划、分片和对账。

## 4. 部署拓扑与对外入口

| 位置 | 运行内容 |
| --- | --- |
| control 主机 | Caddy、Admin、Gateway、web-host、EventBus、CloudNode、Collector（含 subject 同步）、Factor Manager、Strategy、Monitor、HostAgent |
| storage 主机 | Storage 的 primary/node/view/access 四个进程、Gateway、HostAgent |
| 腾讯云 SCF | 行情采集函数：crypto 是调度器异步调用的 Invoke 函数池，stockcn 是 Timer 触发的 fleet |
| 操作员机器 | Factor Engine（macOS 用 launchd、Linux 用 systemd 用户服务托管） |

对外开放的端口只有以下几个，其余服务都只监听 `127.0.0.1`：

| 端口 | 所在 | 用途 |
| --- | --- | --- |
| `9527` | control | Caddy HTTPS：管理台页面与 `/api/admin/*`、`/api/gateway-control/*` |
| `11001` | 每台机器 | Caddy HTTPS：`/api/service/*`，转发到本机节点网关 `11002` |
| `11003` | 网关所在机器 | 节点网关的 native tRPC 入口（供 SCF 等签名调用方使用） |
| `11004` | storage | access：因子引擎和按地域配置的 SCF 采集函数访问 Storage 的入口（未配置的地域走 storage 主机网关 `11003`） |
| `4222` | control | EventBus（TLS，按角色凭据鉴权） |

各服务的本地端口见各模块文档；健康检查端口统一提供 `/healthz`、`/readyz`、`/metrics`，
需要独立的 health HMAC 签名，Caddy 对外一律返回 404。

## 5. 核心数据流

### 5.1 行情采集

```text
Collector 规划周期批次
  ├─ crypto：通过 CloudNode InvokeFunction 异步调用 Invoke 函数池，失败换节点重试
  └─ stockcn：写成 TimerPeriodBatch；SCF Timer 到点后 ClaimTimerBatch（经节点网关领取）
  ─► 并发请求行情源（Binance、新浪、腾讯、东方财富、百度、通达信等）
  ─► access（或 storage 主机网关 11003）─► PrimaryStore ─► DataNode：
        EnsureDatasetPeriod（首次固化本周期的序列快照与截止时间）
        CommitTimeSeriesBatch（写入 K 线，逐序列确认）
        RecordDatasetPeriodFailures（上报失败序列）
  ─► 发布 MarketFetchBatchCompleted ─► Collector 更新批次、生成重试
DataNode 到达截止时间 ─► 原子固化 complete/degraded 并写入 CollectorPeriodCompleted 标记
```

DataNode 是“一个采集周期是否完成”的唯一权威。Collector 只在收到 Storage 的逐序列回执后
才认为失败上报已被接受，确认之前一直保持待上报状态并重放。

### 5.2 因子计算

```text
CollectorPeriodCompleted ─► Factor Engine（按计算任务订阅源数据集）
  ─► 读取源数据窗口 ─► Python worker 计算 ─► WriteFactorRows 写入因子结果数据集
  ─► ReportFactorPeriodComputed ─► DataNode 写入 FactorPeriodComputed 标记
Storage View 消费行与标记 ─► 结果 View 就绪后发布 ViewDataReady
```

Factor Manager 在控制机上维护因子定义、计算任务和补算任务；Factor Engine 在操作员机器上
运行，定时拉取任务目录快照并持有引擎租约，管理端不可达时继续用最后一份快照计算。

### 5.3 策略与交易

```text
ViewDataReady（携带各因子的 definition_hash）
  ─► Strategy：按 View 找到全部启用实例 ─► 乱序 / 过期周期直接记 skipped
  ─► 就绪判定：因子缺失、指纹变化、上一根版本未知、因子跳过 ─► skipped（原因）
  ─► 只读绑定的那一个 View：基础集合 U → 各规则的 E / G / A / M
  ─► 纯函数引擎：rank（filter → score → select → weight → filter_after）、signal（exit 优先）
  ─► 组合约束与守门 ─► 一个事务保存结果、解释明细与待投递事件 ─► ACK
  ─► 后台发布 LogicalAccountTargetWeightRequested（完整目标权重，有效期 2 根 bar）
Trade：校验会话与时效 ─► 按组合账户权益换算数量 ─► 逐子单收敛目标
```

Strategy 只输出相对总权益的目标权重，不读取账户和持仓；数量换算、账户选择、精度和风控都在 Trade 完成。
每个处理过的周期都有记录：ok 带目标与逐标的解释，skipped 带原因；连续缺期由 Monitor 的数据集新鲜度告警。

### 5.4 监控

```text
各服务每 30 秒上报 Prometheus 快照 ─► MOOX_OBSERVABILITY ─► Monitor
HostAgent 每分钟上报主机快照       ─┘
Monitor ─► 写入 Storage 的 mooxsys 系统数据集（服务指标、主机指标历史）
        ─► 运行检查：部署探活、指标上报、数据集新鲜度、K 线新鲜度、模块健康、主机在线
        ─► 状态变化时按规则发送企业微信/飞书通知
```

## 6. 事件清单

事件名称、版本、所属 Stream 和负载类型都在 `packages/events` 中以代码声明；
Subject 统一为 `moox.<事件名>.v<版本>.<space>[.<subject>]`。

| 事件 | Stream | 发布方 | 消费方 |
| --- | --- | --- | --- |
| `event.storage.dataset.rows.upserted` v2 | `MOOX_STORAGE` | Storage DataNode（Outbox） | Storage View、Collector、Archive |
| `event.storage.collector.period.completed` | `MOOX_STORAGE` | Storage DataNode | Factor Engine、Storage View |
| `event.storage.dataset.factor_period.computed` | `MOOX_STORAGE` | Storage DataNode | Storage View |
| `event.storage.dataset.sync_point` | `MOOX_STORAGE` | Storage DataNode | Storage View |
| `event.storage.view.data.ready` | `MOOX_STORAGE` | Storage View | Strategy（据 `factors[].definition_hash` 判定因子版本） |

| `event.observability.metrics.snapshot.reported` | `MOOX_OBSERVABILITY` | 各服务 | Monitor |

## 7. 服务调用与安全

| 场景 | 机制 |
| --- | --- |
| 浏览器登录 | 一次性盐值挑战 + bcrypt 密码；登录后签发 24 小时会话，每个管理请求再附带带 nonce 的会话 HMAC |
| 服务之间（经节点网关） | `packages/gatewayauth` 的服务 HMAC：调用方 key、目标节点、请求体摘要和时间戳一起签名，网关校验并防重放 |
| 网关拉取路由 | 独立的 control HMAC，只能访问 `/api/gateway-control/*` |
| 健康检查 | 独立的 health HMAC，与业务密钥分离 |
| Storage 内部 | primary/node/view 各自的必填密钥，DataNode、PrimaryStore、ViewIndex、DataView 全部校验 |
| 外部访问 Storage | access 按调用方（collector、factor-engine）限定可调用的方法，并重新签名后转发 |
| EventBus | TLS + 按角色划分的凭据（如 `storage-eventbus`、`factor-eventbus`、`hostagent-publisher`），由 Admin CLI 生成和轮换 |
| 交易所等外部密钥 | 存放在 Admin 的密钥表中，Trade 按 `secret_id` 单条读取 |

## 8. 数据与存储

| 数据 | 存放位置 |
| --- | --- |
| 行情、因子结果、系统指标等事实 | Storage DataNode（Pebble），按 Dataset 保留期清理 |
| 查询索引 | Storage View（时序用 DuckDB，记录用 Bleve），可随时重建 |
| 元数据（空间、标的、标签、数据集、字段、View、节点） | Storage primary 的 SQLite |
| 各模块控制面状态 | 各自的 SQLite：Admin、Collector、CloudNode、Factor、Strategy、Trade、Monitor |
| 事件 | EventBus JetStream，按 Stream 设置时间和容量上限 |
| 长期归档 | Archive 的按月 Parquet（可同步到 COS） |

初始元数据由 `config/setup/metadata.yaml` 定义，包含 `crypto`、`stockcn`、`stockhk`、
`stockus` 四个市场空间和系统空间 `mooxsys`。采集结果和因子结果的数据集不在这份清单里，
分别由 Collector 和 Factor Manager 随任务自动创建。命名规则见[元数据命名规范](元数据命名规范.md)。

## 9. 代码组织

仓库是 Go Workspace 大仓（`go.work`），代码分布在 `modules/`、`packages/` 和仓库根级运行模块中：

| 目录 | 内容 |
| --- | --- |
| `modules/<模块>` | 业务模块：`cmd/`（进程入口）、`internal/`（实现）、`proto/`（协议与生成代码）、`schema/`（SQLite 表结构）、`config/`（默认配置） |
| `packages/` | 跨模块共享包：协议定义、事件注册表、网关鉴权、JetStream 客户端、健康检查、指标上报等 |
| `web/`、`web-host/` | 管理台前端与静态资源服务 |
| `config/setup/` | 初始化清单：元数据、内置采集任务、数据集健康策略、服务部署 |
| `scripts/` | 构建、部署、发布、检查与契约测试脚本 |
| `deploy/` | Caddy、launchd、systemd 模板 |
| `skills/`、`tools/` | 运维 Agent 技能与 MCP 工具 |
| `examples/` | 示例数据与示例因子 |

依赖边界由脚本强制检查：模块之间不能互相引用 `internal` 包，共享能力必须下沉到

| `./scripts/build/build.sh <模块>` | 构建单个模块的二进制到 `bin/` |
| `make build-storage-linux` | 在 Linux 编译机上构建启用 DuckDB（CGO）的 Storage |
| `make verify` | 提交前的完整检查：依赖边界、格式、lint、Go 测试与 vet、前端测试与构建、文档构建、契约测试 |
| `make release` / `make release-binaries` | 生成发布归档，或只汇总各模块二进制 |
| `./scripts/deploy/deploy-moox.sh` | 生成部署目录并同步到本机或远端（control / storage 等 profile） |
| `moox-cli setup ...` | 初始化控制面、部署 Storage、导入并激活元数据 |

部署和日常运维见[部署与运维](部署与运维.md)。
