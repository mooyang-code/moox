# MooX 总体设计

MooX 是面向个人的一站式量化平台：从行情采集、数据存储、因子计算、策略选股到交易执行，
再到全链路监控，都在同一套系统内完成，并提供 Web 管理台和 `moox-cli` 命令行两种入口。

系统按“单用户、自托管、少量机器”设计：唯一的登录用户拥有全部管理能力，不建设 RBAC；
但登录、会话、服务间请求签名和防重放始终开启，单用户不等于不设防。

## 1. 设计原则

- **事实与派生分离。** 行情、因子结果等事实由 Storage 的 DataNode 持久化；查询用的 View
  索引、监控指标历史都是可以重建的派生数据。
- **事件驱动，消费者自治。** 跨模块的异步协作统一走 EventBus（内嵌 NATS JetStream）。
  EventBus 只声明 Stream，每个消费方自己创建并拥有 Consumer。
- **一个网关，只转发到本机。** 组件、端口、tRPC 服务和 ACL 都写在代码里的组件目录中；Admin 按部署表为每台主机
  编译路由快照（控制面），每台主机上的主机网关只把已签名的请求转发到本机服务（数据面）。控制面故障不影响已缓存
  快照的数据面。
- **外部调用方只有一个入口。** SCF、因子引擎等不运行在 MooX 主机上的调用方只能经外部接入访问，能调用的方法由
  代码里的白名单限定。
- **按模块独立部署。** 每个业务模块是一个独立进程，自带 SQLite 或 Pebble 存储，模块之间只通过
  RPC 和事件交互，不共享数据库，也不跨模块引用 `internal` 代码。
- **短时计算放到云函数。** 行情抓取运行在腾讯云 SCF 上，每次触发只执行一批请求，不常驻；
  控制面负责规划、分片和对账。

## 4. 部署拓扑与对外入口

组件定义在 `packages/servicecatalog` 的组件目录中，组件 ID 是二进制名去掉 `moox-` 前缀。哪个组件部署在哪台主机由
`moox.toml` 的 `[placements]` 决定，CLI 部署主机时把它同步到 Admin 的部署表。主机组件（`host-gateway`、
`host-agent`）每台主机自动部署，不用写进部署表。

| 位置 | 运行内容 |
| --- | --- |
| control 主机 | 控制台代理（Caddy）、web-host、Admin、EventBus、Monitor、Collector、CloudNode、Factor Manager、Strategy，以及主机组件 |
| storage 主机 | storage-primary、storage-node、storage-view、外部接入 `access@storage`，以及主机组件 |
| compute-1（香港） | Trade、出口代理、外部接入 `access@compute-1`，以及主机组件 |
| 腾讯云 SCF | 行情采集函数：crypto 是调度器异步调用的 Invoke 函数池，stockcn 是 Timer 触发的 fleet |
| 操作员机器 | Factor Engine（macOS 用 launchd、Linux 用 systemd 用户服务托管）、moox-cli |

`admin`、`host-gateway`、`console-proxy`、`web-host` 和 control 主机本身受保护：停用它们会切断控制台和恢复入口，
所以接口、页面和部署同步都拒绝停用它们。误停用其他组件时，可以用 `moox-admin-cli placement set-status` 离线恢复。

对外开放的端口只有以下几个。业务服务的 tRPC 端口都只监听 `127.0.0.1`，由本机主机网关转发：

| 端口 | 所在 | 用途 | 开放范围 |
| --- | --- | --- | --- |
| `9527` | control | 控制台代理 HTTPS：管理台页面与 `/api/admin/*` | 公网 |
| `11003` | 每台主机 | 主机网关的跨主机入口，tRPC + TLS（MooX 私有 CA） | 只对 MooX 主机 |
| `11004` | 部署了外部接入的主机 | 外部接入，tRPC 明文 + 签名 | 公网 |
| `4222` | control | EventBus（TLS，按角色凭据鉴权；SCF 直接发布事件） | 公网 |
| 各组件健康端口、`11012` | 各主机 | `/healthz`、`/readyz`、`/metrics`，需要独立的 health HMAC | 只对 control |

主机网关的本机入口 `11002` 只监听 `127.0.0.1`，供本机组件和经 SSH 隧道的 moox-cli 使用。防火墙规则由
`moox-cli setup firewall` 按部署表同步。各组件的端口见各模块文档。

## 5. 核心数据流

### 5.1 行情采集

```text
Collector 规划周期批次
  ├─ crypto：通过 CloudNode InvokeFunction 异步调用 Invoke 函数池，失败换节点重试
  └─ stockcn：写成 TimerPeriodBatch；SCF Timer 到点后经外部接入 ClaimTimerBatch 领取
  ─► 并发请求行情源（Binance、新浪、腾讯、东方财富、百度、通达信等）
  ─► 外部接入（同地域私网，否则 access@storage 公网）─► storage 主机网关 ─► PrimaryStore ─► DataNode：
        EnsureDatasetPeriod（首次固化本周期的序列快照与截止时间）
        CommitTimeSeriesBatch（写入 K 线，逐序列确认）
        RecordDatasetPeriodFailures（上报失败序列）
  ─► 发布 MarketFetchBatchCompleted ─► Collector 更新批次、生成重试
DataNode 到达截止时间 ─► 原子固化 complete/degraded 并写入 CollectorPeriodCompleted 标记
```

DataNode 是“一个采集周期是否完成”的唯一权威。Collector 只在收到 Storage 的逐序列回执后
才认为失败上报已被接受，确认之前一直保持待上报状态并重放。

外部接入地址、实例 ID 和 `scf-collector` 凭据由 Collector 经 CloudNode 写进函数环境变量，代码包里不带地址和凭据。
Collector 自己访问 Binance 时经香港的出口代理，并用出口代理的解析结果为 SCF 生成 DNS 快照。

### 5.2 因子计算

```text
CollectorPeriodCompleted ─► Factor Engine（按计算任务订阅源数据集）
  ─► 经外部接入读取源数据窗口 ─► Python worker 计算 ─► WriteFactorRows 写入因子结果数据集
  ─► ReportFactorPeriodComputed ─► DataNode 写入 FactorPeriodComputed 标记
Storage View 消费行与标记 ─► 结果 View 就绪后发布 ViewDataReady
```

Factor Manager 在控制机上维护因子定义、计算任务和补算任务；Factor Engine 在操作员机器上运行，经外部接入访问
Storage 和 FactorEngine 服务，定时拉取任务目录快照并持有引擎租约，管理端不可达时继续用最后一份快照计算。

### 5.3 策略与交易

```text
ViewDataReady ─► Strategy：确定 (实例, 会话, bar_end_time) ─► 读取行情与因子
  ─► 池 → 前筛 → 评分 → 选择 → 信号 → 权重 → 后筛 ─► 事务保存 StrategyResult
  ─► 后台发布 LogicalAccountTargetWeightRequested（完整目标权重）
Trade：校验会话与时效 ─► 按组合账户权益换算数量 ─► 逐子单收敛目标
```

Strategy 只输出目标权重，不读取账户和持仓；数量换算、账户选择、精度和风控都在 Trade 完成。

### 5.4 监控

```text
各服务每 30 秒上报 Prometheus 快照 ─► MOOX_OBSERVABILITY ─► Monitor
HostAgent 每分钟上报主机快照       ─┘
Monitor ─► 写入 Storage 的 mooxsys 系统数据集（服务指标、主机指标历史）
        ─► 运行检查：每条已启用部署的探活（placement:<主机>:<组件>）、主机网关心跳与快照一致性、
           指标上报、数据集新鲜度、K 线新鲜度、模块健康、主机在线
        ─► 状态变化时按规则发送企业微信/飞书通知
```

## 7. 服务调用与安全

所有跨进程的业务调用都是 tRPC，经 `packages/gatewayclient` 发出，有三种使用方式：

| 方式 | 使用者 | 怎么找到目标 | 传输 |
| --- | --- | --- | --- |
| 内部 | MooX 主机上的组件 | 本机主机网关的服务目录；目标在本机时连 `127.0.0.1:11002`，在其他主机时连 `<主机>:11003` | 跨主机走 TLS，只信任 MooX 私有 CA |
| 外部 | SCF、因子引擎、moox-skill | 配置中固定的外部接入地址和实例 ID `access@<主机>` | 明文 + 签名 |
| 隧道 | moox-cli | 经 SSH 隧道连 control 的 `127.0.0.1:11002` 取目录，再对目标主机建立 SSH 隧道 | SSH |

| 场景 | 机制 |
| --- | --- |
| 浏览器登录 | 一次性盐值挑战 + bcrypt 密码；登录后签发 24 小时会话，每个管理请求再附带带 nonce 的会话 HMAC |
| 浏览器调用业务服务 | 控制台 API 以 `console` 身份经主机网关转发；浏览器能调用哪些方法，看组件目录的 ACL 是否放行 `console` |
| 服务之间 | `packages/gatewayauth` 的服务签名：调用方、KeyID、目标主机、请求体摘要、时间戳和 nonce 一起签名；目标主机网关校验签名和 ACL，并防重放 |
| 调用方密钥 | 每个调用方身份一把密钥（各组件、`admin`、`console`、`host-gateway@<主机>`、`access`、`moox-cli`），主副本加密存放在 Admin 密钥表；主机网关的校验密钥随快照下发 |
| 主机网关拉快照 | 同样使用服务签名，网关控制只接受 `host-gateway@<同一主机>` |
| 外部调用方 | 外部接入校验 `scf-collector`、`factor-engine`、`moox-skill` 的签名；白名单写在组件目录里，不能通过配置放宽 |
| 健康检查 | 独立的 health HMAC，与业务密钥分离 |
| Storage 内部 | primary/node/view 各自的必填密钥，DataNode、PrimaryStore、ViewIndex、DataView 全部校验 |
| EventBus | TLS + 按角色划分的凭据（如 `storage-eventbus`、`factor-eventbus`、`hostagent-publisher`），由 Admin CLI 生成和轮换 |
| 交易所等外部密钥 | 存放在 Admin 的密钥表中，Trade 按 `secret_id` 单条读取；`SecretMgr.GetSecretValue` 只放行内部调用方 |

MooX 私有 CA 在首次部署时生成，私钥只放在 control 的 `secrets/pki/`；每次部署一台主机都会为它的主机网关重新签发
证书。

## 8. 数据与存储

| 数据 | 存放位置 |
| --- | --- |
| 行情、因子结果、系统指标等事实 | Storage DataNode（Pebble），按 Dataset 保留期清理 |
| 查询索引 | Storage View（时序用 DuckDB，记录用 Bleve），可随时重建 |
| 元数据（空间、标的、标签、数据集、字段、View、节点） | Storage primary 的 SQLite |
| 各模块控制面状态 | 各自的 SQLite：Admin（含主机、部署和主机网关状态）、Collector、CloudNode、Factor、Strategy、Trade、Monitor |
| 主机网关快照缓存 | 每台主机的 `data/host-gateway/snapshot.json`，网关控制不可用时继续使用 |
| 事件 | EventBus JetStream，按 Stream 设置时间和容量上限 |
| 长期归档 | Archive 的按月 Parquet（可同步到 COS） |

初始元数据由 `config/setup/metadata.yaml` 定义，包含 `crypto`、`stockcn`、`stockhk`、
`stockus` 四个市场空间和系统空间 `mooxsys`。采集结果和因子结果的数据集不在这份清单里，
分别由 Collector 和 Factor Manager 随任务自动创建。命名规则见[元数据命名规范](元数据命名规范.md)。

## 9. 代码组织

仓库是 Go Workspace 大仓（`go.work`），代码分布在 `modules/`、`packages/` 和仓库根级运行模块中：

| 目录 | 内容 |
| --- | --- |
| `modules/<模块>` | 业务模块：`cmd/`（进程入口）、`internal/`（实现）、`proto/`（协议与生成代码）、`schema/`（SQLite 表结构）、`config/`（默认配置） |
| `packages/` | 跨模块共享包：组件目录、调用方客户端、协议定义、事件注册表、网关鉴权、JetStream 客户端、健康检查、指标上报等 |
| `web/`、`web-host/` | 管理台前端与静态资源服务 |
| `config/setup/` | 初始化清单：元数据、内置采集任务、数据集健康策略 |
| `scripts/` | 构建、发布、检查与契约测试脚本 |
| `deploy/` | 主机运行脚本（`deploy/runtime`：安装、启停、暂停、健康检查），以及因子引擎的 launchd、systemd 模板 |
| `skills/`、`tools/` | 运维 Agent 技能与 MCP 工具 |
| `examples/` | 示例数据与示例因子 |

依赖边界由脚本强制检查：模块之间不能互相引用 `internal` 包，共享能力必须下沉到
`packages/`；事件名称和 Subject 只能在 `packages/events` 中声明。

`go.work` 中的全部 Go 模块：

| 模块路径 | 说明 |
| --- | --- |

## 10. 构建、测试与发布

| 命令 | 作用 |
| --- | --- |
| `./scripts/build/build.sh <模块>` | 构建单个模块的二进制到 `bin/` |
| `make build-storage-linux` | 在 Linux 编译机上构建启用 DuckDB（CGO）的 Storage |
| `make verify` | 提交前的完整检查：依赖边界、格式、lint、Go 测试与 vet、前端测试与构建、文档构建、契约测试 |
| `make release` | 生成发布归档 |
| `moox-cli setup bootstrap` | 空环境首次部署：离线初始化 Admin（建表、CA、调用方密钥、主机与部署），再部署全部主机 |
| `moox-cli setup deploy-host --host <主机>` | 部署一台主机：主机组件和部署表中的业务组件 |
| `moox-cli setup deploy-service --component <组件>` | 在部署了该组件的主机上重新部署它 |
| `moox-cli setup init` | 导入并激活元数据、采集任务和因子 |

部署和日常运维见[部署与运维](部署与运维.md)。
