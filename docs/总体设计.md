# MooX 总体设计

MooX 是面向个人的一站式量化平台：从行情采集、数据存储、因子计算、策略选股到交易执行，
再到全链路监控，都在同一套系统内完成，并提供 Web 管理台和 `moox-cli` 命令行两种入口。

当前能力与部署限制见[实现状态](实现状态.md)，历史重构计划见[计划索引](计划/README.md)。

系统按“单用户、自托管、少量机器”设计：唯一的登录用户拥有全部管理能力，不建设 RBAC；
但登录、会话、服务间请求签名和防重放始终开启，单用户不等于不设防。

## 1. 设计原则

- **事实与派生分离。** 行情、因子结果等事实由 Storage 的 DataNode 持久化；查询用的 View
  索引、监控指标历史都是可以重建的派生数据。
- **事件驱动，消费者自治。** 跨模块的异步协作统一走 EventBus（内嵌 NATS JetStream）。
  EventBus 只声明 Stream，每个消费方自己创建并拥有 Consumer。
- **控制面与数据面分离。** Admin 维护组件目录、主机登记与部署和路由快照（控制面）；每台机器上的主机网关只负责
  把已签名的 tRPC 请求转发到本机服务（数据面）。控制面故障不影响已缓存快照的数据面。
- **按模块独立部署。** 每个业务模块可包含一个或多个独立进程，按职责使用 SQLite 或 Pebble 等存储，模块之间只通过
  RPC 和事件交互，不共享数据库，也不跨模块引用 `internal` 代码。
- **采集执行端与控制面分开。** 行情抓取运行在腾讯云 SCF（每次触发只执行一批请求，不常驻）或海外机上的推送接收端（crypto 的 WS 收盘 K 线）；
  控制面（Collector）负责规划、分片和对账，执行端停机重启不丢计划。
- **每一层都是同一个形状。** “输入数据集 → 任务 → 输出数据集”：采集任务产出 K 线，因子任务产出因子结果，策略实例读因子结果产出目标权重；行情与因子这两层的事实都先写进 Storage，下一层只依赖上一层写下的事实和事件。
- **派生可重建，结构变化靠全新部署。** View 索引、因子结果、监控历史都能重建或补算；项目不写迁移与兼容代码。

## 2. 一条数据的一生：端到端处理流程

一根 K 线从交易所产生，到变成一笔订单，经过六个环节。**行情（①②）和因子结果（③）这两类事实先落到 Storage，计算输入以持久化事实和事件为准；任务目录与参数闭环通过 RPC 协作**；
策略（⑤）的结果、目标权重和下一期参数则在 Strategy 自己的 SQLite 里同一事务保存，再异步发出：实例挂了账户且结果有效时发目标权重给 Trade，策略产出了下一期可变成员参数时投递给 Factor。Monitor 旁路观察每个环节。

```text
行情源 ─①采集─► Storage 事实：K 线 ─②周期完成标记─► ③因子计算 ─► Storage 事实：因子结果 + 系统列 __params
   ─④View 就绪事件─► ⑤策略求值 ─► Strategy 本地事务：结果 + 目标权重 + 下一期参数
                                         ├─（异步，挂了账户且结果有效）─► ⑥ Trade ─► 订单 / 成交
                                         └─（异步，有可变成员参数）─────► Factor：第 T+1 期开算时取用
```

| 环节 | 做什么 | 谁说了算 | 产物 |
| --- | --- | --- | --- |
| ① 采集 | SCF 函数或 `collector-stream` 按采集计划抓取（或接收 WS 推送）收盘 K 线，逐序列提交 | Collector 规划、DataNode 记账 | 数据集里的 K 线行；失败序列上报，缺口由检查与补采修复 |
| ② 周期完成 | 全部预期序列成功时提前固化为 `complete`；到达截止时间仍未齐则固化为 `degraded`，都是 DataNode 原子完成 | **DataNode 是“周期是否完成”的唯一权威** | `DatasetPeriodCompleted` 标记事件（`source=ledger`） |
| ③ 因子计算 | 引擎收到事件，同一源数据集上的**每个启用因子任务同时开算**（任务内串行），按成员的固定参数或策略提交的参数计算 | Factor Manager 维护任务与成员，Engine 计算 | 因子结果数据集的行（因子值 + 每行实际用的参数 `__params`）、`DatasetPeriodCompleted` 标记（`source=producer`，`detail` 带各成员的状态） |
| ④ View 就绪 | Storage View 按当前索引策略应用行与标记（超龄历史行可被过滤），确认该周期数据已进入索引 | Storage View | `ViewDataReady`（原样透传标记里的 `detail_type`、`detail`；因子的明细含各成员的定义指纹与类型） |
| ⑤ 策略 | 只读实例关联的那一个因子任务的结果 View，按 DSL 过滤、打分、选股、配权；同一事务里保存结果与下一期参数 | Strategy | 带逐标的解释的结果；目标权重事件；待投递的下一期参数 |
| ⑥ 交易 | 校验会话与时效，按组合账户权益换算数量，逐子单收敛目标 | Trade | 订单、成交；模拟盘与实盘共用同一套收敛 |

**时间线（2026-10-26 生产实测，5m 周期、501 个标的、5 个因子成员）**：收线 → 采集写完（约 1 秒内）→ 引擎开算到写完约 2.7 秒（载入 0.2、计算 2.05、写出 0.4）→ View 就绪 →
策略结果落库，**收线到策略结果约 4.1～4.8 秒**（这是 `chain_ema20w_5m` 一个实例的一次实测，不是时延保证）。另一个只有单个可变成员的轻量任务（`ftask_swap5m_var`，引擎约 0.5 秒）的观察实例，
其参数在收线后约 3 秒内送达 Factor；参数先随结果落库、再由独立的投递循环异步发送，送达时刻不保证；只要赶在第 T+1 期开算之前送达，第 T+1 期就用上，否则从下一个还没开算的期次起生效。

**出问题时的路径**：缺行由 Collector 的 K 线检查与自动补采补上，补采成功后通知 Factor（`NotifyPeriodsFilled`），引擎沿连续水位从断点往后补算并发布历史结果；
上游当期未到或窗口尚未预载就绪的标的可进入跳过账本，恢复后按账本补算，仍受可用数据与放弃期限限制；本地存储中的缺期按写入填充规则处理。策略的 rank/signal 规则对已持有且满足空洞保护条件的标的发出 `hold=true`，由 Trade 保持当前数量；保护项仍计入缺数比例，tranche 不参与该保护。每一步都留下原因，在 Monitor 与控制台可查。

## 3. 核心概念与设计取舍

### 3.1 核心概念

| 概念 | 含义 |
| --- | --- |
| 空间（Space）/ 数据集（Dataset）/ 标的（Subject） | 业务域（`crypto`、`stockcn`……）、一类数据的存放单元、被采集和计算的对象；一个数据集只属于一个 DataNode |
| 周期与完成标记 | 一个数据集一个频率的一期（如一根 K 线）；完成标记 `DatasetPeriodCompleted` 是下游（因子、View、K 线合成）的触发信号，来源有两种：DataNode 按序列快照与截止时间判定（`ledger`，采集），或写入方自己报告（`producer`，因子） |
| 因子定义 | 全局的表达式（YAML spec），类型、输入列、输出列、回看和可调参数全部由编译推导 |
| 因子任务 | **源数据集 + 频率 → 结果数据集**，由用户创建，可以先于策略运行；一个源数据集可以有多个任务，任务之间完全独立、并行计算、不共享计算 |
| 成员、成员键、列名 | 任务里的一个因子（固定参数，或参数由策略逐期提交的“可变”成员）；成员键与结果列名由“因子 ID + 参数 + 是否可变 + 输出”按规则**推导**，没有别名（`ema__20_50000`、`boll__mid`、`ma__var`） |
| `__params` | 结果数据集的系统列（JSON），记录这一行每个成员**实际用了什么参数**；是参数的唯一历史记录，补算、回放和策略的 `params()` 都读它 |
| 策略实例 | 策略定义 + 一个因子任务 + 可选的组合账户；与任务 1:1、独占且永久（不能改绑任务、不能删除；停用后仍可改定义和账户）；没挂账户的是只计算不下单的观察实例 |
| View | 面向查询的派生索引，可随时重建；策略只读结果数据集的默认 View |
| 生命周期阶段 | 未初始化 → 就绪 → 试运行 → 运行；另有暂停、恢复追赶、重置、故障。实时计算在试运行和运行阶段进行；策略在追赶或处理迟到周期时还可仅推进规则状态。试运行目标带影子标记、Trade 不下单 |

### 3.2 设计取舍

1. **事实与派生分离，派生可重建。** 行情和因子结果是事实，存在 DataNode；View 索引与因子机的本地时序存储可从保留的事实重建；超过 Storage 保留窗口的本地历史需从导入文件或归档恢复，不能只靠当前 Storage 尾部窗口还原。历史因子值不够可发起补算，View 损坏可重建。
2. **“周期完成”只有一个权威。** 上游缺数据、晚到数据、补采都会让一个周期的数据“事后变化”，所以完成与否不由任何消费者猜，而由 DataNode 在截止时间固化并发布；下游据事件工作，错过的靠连续水位追赶。
3. **用因果顺序代替锁。** 参数闭环不依赖分布式锁：策略要提交第 T+1 期的参数，前提是第 T 期因子已经写出，所以引擎开算第 T+1 期时读到的提交值不会超前；同一期失败重试时用本地“进行中记录”里第一次选定的参数，重试不换参数；
   积压追赶时引擎不等策略，晚到的提交从下一个还没开算的期次起生效——不保证每期都用上针对它算出的参数，但保证不超前、不倒退，并且**用了什么都如实记在 `__params` 里**。
4. **任务与实例 1:1，是为了让“参数写入方”唯一。** 可变成员只有一个写入方（关联的实例），不需要冻结记录、快照表和离线补报；任务先于策略存在，历史可以先积累；策略停止不影响因子计算。
5. **名字可推导，用户可预测。** 成员键与列名的规则只有一份实现（Go 的 `packages/factorname`，前端 TS 与它共用测试向量），解析时不需要查定义；创建任务、写策略规则和写 SQL 时看到的是同一个名字。
6. **门禁而不是开关。** 谁能计算、谁能发目标，由生命周期阶段统一门禁：试运行跑完整链路但不下单，运行才下单，暂停不求值、持仓不动。系统级暂停 / 恢复有固定次序（见 7.5）。
7. **计算读本地，写入时保证连续。** 因子机在本地 Pebble 里保存全量序列（没有定时淘汰，显式重置会清空），写入时按频率网格检查连续性：允许 FillGaps 时生成填充行，否则缺期报错；填充行不等同于已采集到真实行情。Storage 主要在增量同步、修正跟进和连续水位核对缺失时被读取，计算窗口不再逐期向它读取。
8. **模块自带存储、只通过 RPC 与事件协作；控制面与数据面分离。** 见第 1 节原则。
9. **单用户、自托管、项目可全新部署。** 不建设 RBAC，但登录、会话、服务间签名和防重放始终开启；不写迁移与兼容代码，结构变化通过清掉旧数据、全新部署解决（因子任务重构就是这样上线的）。

## 4. 系统全景

```text
                         浏览器 / moox-cli
                               │ HTTPS :9527（管理台）
                               ▼
┌──────────────────────── control 主机 ────────────────────────┐
│ moox-console-proxy（内嵌 Caddy）─► moox-web-host（静态资源）  │
│   └────► moox-admin（认证、空间、组件目录、密钥、终端、Setup） │
│ moox-host-gateway（主机网关，tRPC：本机 :11002 / 跨主机 TLS :11003）│
│ moox-cloudfunction   moox-collector                             │
│ moox-factor-mgr  moox-strategy  moox-monitor  moox-archive-mgr │
│ moox-host-agent                                               │
└───────────────────────────────┬──────────────────────────────┘
        ▲ 定时触发/调用          │ 事件、服务调用
        │                        ▼
┌───────┴────────┐    ┌──────────────────── storage 主机 ────────────────────┐
│ 腾讯云 SCF      │───►│ moox-access（外部入口 :11004，按调用方限定方法）    │
│ 行情采集函数    │    │ moox-storage-primary（Metadata + PrimaryStore）      │
└────────────────┘    │ moox-storage-node（Pebble 事实存储 + Outbox）         │
                      │ moox-storage-view（DuckDB/Bleve View + 查询）         │
┌────────────────┐    │ moox-eventbus（NATS JetStream，TLS :4222）            │
│ 因子机 factor   │───►│ moox-host-gateway   moox-host-agent                        │
│ moox-factor-engine（只做出站连接）│    └───────────────────────────────────────────────────────┘
│ moox-archive-worker              │
└────────────────┘

┌─────────────────── 海外机 overseas ───────────────────┐
│ moox-collector-stream：crypto 的 WS 收盘 K 线接收与    │
│   本地执行端 ─► storage 主机的 Access                  │
│ moox-trade：消费 EventBus 的目标权重事件，换算订单并收敛 │
│ moox-access  moox-egress-proxy                         │
│ moox-host-gateway  moox-host-agent                     │
└────────────────────────────────────────────────────────┘
```

海外机（`overseas`）部署 Trade、Access、EgressProxy 与 Collector Stream，并运行 HostGateway、HostAgent；
因子机（`factor`）是只能出站的内网机器，运行因子引擎与归档 Worker（外部程序，同样登记为部署主机）。
具体组件由 `moox.toml` 的 `[deployments]` 决定。上述图说明角色分工，不代表生产运行状态。

**EventBus 放在 storage 主机**：Storage 内部的行变更事件（storage-node 发布、storage-view 消费）占 EventBus 流量的九成以上，
同机之后这条管道不再经公网往返。EventBus 是独立的部署单元（`eventbus` profile），位置由 `[deployments]` 决定，不绑定控制机；
客户端与它同机时连回环地址，否则连它所在主机的对外地址（证书同时覆盖两者）。

## 6. 部署拓扑与对外入口

| 位置 | 运行内容 |
| --- | --- |
| control 主机 | Console Proxy、Admin、HostGateway、web-host、CloudFunction、Collector（含 subject 同步）、Factor Manager、Strategy、Archive Manager、Monitor、HostAgent |
| storage 主机 | Storage 的 primary/node/view 三个进程、EventBus、Access、HostGateway、HostAgent |
| 海外机 overseas（模板） | Trade、Access、EgressProxy、Collector Stream、HostGateway、HostAgent |
| 腾讯云 SCF | pull + scf 采集方式使用 Timer 触发的 fleet；crypto 默认使用海外机的 stream + local |
| 因子机 factor | Factor Engine、Archive Worker（外部程序，原生安装使用 Linux systemd 用户服务） |

业务入口如下。业务 RPC 仅监听回环；健康端口由原生安装器按组件目录另行渲染为回环或 `0.0.0.0`，并使用独立鉴权和网络访问限制：

| 端口 | 所在 | 用途 |
| --- | --- | --- |
| `9527` | control | 控制台代理 HTTPS：管理台页面与 `/api/admin/*`（诊断端口 `19528` 仅回环） |
| `11003` | 每台机器 | 主机网关的跨主机入口，tRPC + TLS，只对 MooX 主机开放；本机入口 `11002` 仅回环 |
| `11004` | 部署了外部接入的主机 | Access：SCF、因子引擎与 Skill 的签名 tRPC 入口 |
| `4222` | EventBus 所在主机（默认 storage） | EventBus（TLS，按角色凭据鉴权） |

新运行链路不提供 `11001` 或主机网关 HTTP `/api/service/*`。旧部署脚本仍有这些配置，不能混用；
可用的 core、host、业务单元及 control 入口见[部署与运维](部署与运维.md)。历史切换方案保留在
[网关与服务部署重构执行计划](计划/网关与服务部署重构执行计划.md)，现场状态须单独确认。

各服务的本地端口见各模块文档；健康检查端口统一提供 `/healthz`、`/readyz`、`/metrics`，
需要独立的 health HMAC 签名；跨机健康端口的防火墙应限制来源。Console Proxy 和 web-host 的诊断仅绑定回环。

所有 tcp + trpc 服务端在 `trpc_go.yaml` 里显式声明 `transport: go-net`，由契约检查
`scripts/test/contract/test-trpc-plugin-config.sh` 调用 `packages/healthz/cmd/trpctransportcheck` 保证。Linux 下 tRPC 默认启用的 tnet 空闲定时器会把每 30～60 秒才复用一次的连接
提前关掉，调用方随后读到 `ReadFrame: EOF`（tRPC 171）。

## 7. 核心数据流

### 7.1 行情采集

```text
Collector 对账协程（每个空间每分钟）：读任务与标签成员 → 算出采集计划 → 登记序列快照 → 下发给执行端
执行端（按数据集绑定的采集方式）：
  · stream + local（crypto 默认）：collector-stream 订阅交易所 WS，收盘 K 线到齐或到截止时按周期提交
  · pull + scf（其余空间）：腾讯云 SCF 函数由 Timer 触发，并发请求行情源（Binance、新浪、腾讯、东方财富、百度、通达信等）
  ─► access（11004，转发到 storage 主机网关）─► PrimaryStore ─► DataNode：
        CommitTimeSeriesBatch（写入 K 线，逐序列确认；首次提交时按已登记的序列快照建立本周期）
K 线重采样任务（kline_resample）：Collector 按源数据集合成更大的周期（含 A 股交易时段）；源数据被补写时发布补写通知，受影响的桶重新合成
失败项上报 CLS；缺口由 K 线检查与补采修复（moox-cli collector kline check / backfill，另有自动补采）
DataNode 到达截止时间 ─► 原子固化 complete/degraded 并写入 DatasetPeriodCompleted 标记（source=ledger）
```

实时采集不依赖 Collector：执行端按计划自行触发或接收、自行写入，Collector 停机只影响计划变更与补采。
DataNode 是“一个采集周期是否完成”的唯一权威；整个周期零提交时不会建立账本或发出完成标记，缺期由补采与因子连续水位读回处理。

### 7.2 因子计算

```text
DatasetPeriodCompleted ─► Factor Engine（按源数据集与频率找到全部启用的因子任务，同时分发给各任务的执行器）
  ─► 取参：固定成员用成员行的参数；可变成员向 FactorMgr 读策略最近一次提交（失败重试复用本地“进行中记录”）
  ─► 从因子机本地时序存储读窗口 ─► 表达式引擎计算 ─► UpsertFields（带 commit_id）写入因子结果数据集（因子值 + __params）
  ─► ReportDatasetPeriodCompleted（detail 为各成员的 PeriodDetail）─► DataNode 写入 DatasetPeriodCompleted 标记（source=producer）─► 清掉进行中记录
Storage View 按索引策略消费行与标记 ─► 结果 View 就绪后发布 ViewDataReady（不保证被 max_age 过滤的历史行可查）
```

Factor Manager 在控制机上维护因子定义、因子任务与成员、补算作业和策略参数提交；Factor Engine 在因子机上运行，
定时拉取任务目录快照并持有引擎租约，管理端不可达时继续用最后一份快照计算。引擎为每个任务保存**连续水位**：
零提交或缺失超过阈值的周期会阻塞水位（不跳期），补采后由通知推进；历史因子值只通过补算作业生成，启用成员不会自动补算。

### 7.3 策略与交易

```text
ViewDataReady（透传因子的周期明细：各成员的定义指纹与类型）
  ─► Strategy：按实例关联的因子任务找到全部启用实例 ─► 乱序周期记 skipped；追赶 / 过期周期在输入就绪且求值成功时推进规则状态，仍记 skipped、不发目标
  ─► 就绪判定：成员缺失、契约变化、上一根版本未知、因子跳过 ─► skipped（原因）
  ─► 只读关联任务的结果 View：基础集合 U → 各规则的 E / G / A / M（规则直接引用结果列名，params() 读 __params）
  ─► 纯函数引擎：rank（filter → score → select → weight → filter_after）、signal（exit 优先）、tranche（参数表、分批持仓与止损止盈）
  ─► 组合约束与守门 ─► 一个事务保存结果、解释明细、下一期可变成员参数与待投递事件 ─► ACK
  ─► 后台发布 LogicalAccountTargetWeightRequested（完整目标权重，有效期 2 根 bar）
  ─► 后台投递下一期参数 SubmitFactorParams（只投当前会话里最新一条未送达的）
Trade：校验会话与时效 ─► 按组合账户权益换算数量 ─► 逐子单收敛目标
```

Strategy 求值输出相对总权益的目标权重，不读取余额、持仓或订单；账户绑定与会话对账会读取 Trade 的组合账户归属信息。数量换算、账户选择、精度和风控都在 Trade 完成，`hold=true` 的目标保持当前数量。
每个处理过的周期都有记录：ok 带目标与逐标的解释，skipped 带原因，其中成功求值的 catchup/expired 记录还保存规则状态；连续缺期由 Monitor 的数据集新鲜度告警。
没挂账户的观察实例只计算、不投递目标。

### 7.4 监控

```text
各服务每 30 秒上报 Prometheus 快照 ─► MOOX_OBSERVABILITY ─► Monitor
HostAgent 每分钟上报主机快照       ─┘
Monitor ─► 服务指标只存最新值（SQLite）；主机指标历史写入 Storage 的 mooxsys 系统数据集
        ─► 运行检查：部署探活、指标上报、数据集新鲜度、K 线新鲜度、模块健康、主机在线
        ─► 状态变化时按规则发送企业微信/飞书通知
```

### 7.5 生命周期、暂停与恢复追赶

`packages/lifecycle` 是各模块共用的状态机：未初始化 → 就绪 → **试运行** → 运行，另有暂停（手动 / 系统 / 自动）、恢复追赶、重置和故障。
模块（Collector、Factor Engine、Strategy、Trade）各自把阶段持久化在数据库旁，对象是因子任务、策略实例；实时计算只在试运行和运行阶段进行；策略在追赶及放行边界内的历史周期输入就绪时仍可求值推进规则状态（不发目标）。
检查失败的对象自动暂停并在恢复后回到原阶段。因子任务自动 init / start / confirm；策略实例自动 init / start，没挂账户的实例随后自动 confirm，挂了账户的由用户 confirm 才开始真实下单。

系统级暂停与恢复由 `packages/sysctl` 编排（`moox-cli system pause|resume`）：**暂停从下游到上游**（Strategy → Trade → Factor Engine → Collector），每个模块真正停下才停下一个；
**恢复先追赶后放行**：行情链路按依赖启动追赶——采集补采完暂停区间，因子才同步并补算；因子追平，策略才开始记录周期并在输入就绪时求值推进规则状态（不发目标）；Trade 与行情链路无关，一开始就追赶。
有副作用的模块（因子、Trade、策略）要等所有模块都追平（栅栏）才放行，放行顺序是 Collector → Factor Engine → Trade → Strategy（Trade 先于策略，保证放行后的第一批目标有地方接收）；
采集没有下单、发目标这类副作用，补齐暂停区间后**自行恢复实时采集、不等栅栏**，否则等待期间的行情又成了新缺口。
编排器自己不持有状态，中途断开再执行一次即按各模块当前状态继续。策略追赶不自动补齐所有历史事件；暂停期间忽略的周期与追赶时未就绪的周期，不能据“追平”状态推断其规则状态均已成功推进。

### 7.6 补算、回放与历史导入

- **补算**：对已有行按其 `__params` 分段重算——原行存在且 `__params` 里有该成员的期次，结果与原值逐位相同；原行不存在、或 `__params` 里没有该成员的期次按默认参数新补，并列在作业结果里。同一时刻只跑一个补算作业，避免打垮 Storage。
- **历史导入**：数据源首次接入时，因子机本地写全量历史、Storage 与 View 只写最近窗口（`moox-cli import`，见 skill 的“初始数据导入”）。
- **逐期回放**：按时间逐期推进历史，每期走实时计算路径算因子、交给策略求值，再由 Trade 的纸面账本撮合；回放绝不产生实际下单。带可变成员的策略用闭环回放，参数只存在回放会话里。

## 9. 服务调用与安全

| 场景 | 机制 |
| --- | --- |
| 浏览器登录 | 一次性盐值挑战 + bcrypt 密码；登录后签发 24 小时会话，每个管理请求再附带带 nonce 的会话 HMAC |
| 服务之间（经主机网关） | `packages/gatewayauth` 的服务 HMAC：调用方 key、目标主机、请求体摘要和时间戳一起签名，网关按原始字节校验并防重放；跨主机连接再叠加 MooX 私有 CA 的 TLS |
| 网关拉取快照 | 主机网关以 `host-gateway@<主机ID>` 身份调用 Admin 的 `GatewayControl`（control 主机直连回环 `11112`，其他主机经 control 的 `11003`），Admin 再次验签并持久化 nonce |
| 健康检查 | 独立的 health HMAC，与业务密钥分离 |
| 谁能写什么 | 写入权限只靠网关 ACL（`packages/servicecatalog/catalog.yaml`）：哪个调用方能调 Storage 的哪个写方法由 ACL 决定，Storage 内部不再按业务身份（因子、采集等）判断某个数据集能不能写 |
| Storage 内部 | primary/node/view 各自的必填密钥，DataNode、PrimaryStore、ViewIndex、DataView 校验服务签名，Metadata 只对 storage-view 专用的方法验签（共享的读方法由网关 ACL 控制访问）；storage-view 直连 Metadata 与 PrimaryStore（读元数据、回报索引构建状态、写同步点），不经网关 ACL；只有 Storage 维护命令借用 storage-view 的身份调用 Admin 的 EventBus 维护时才走网关 |
| 外部访问 Storage | Access 按外部调用方（scf-collector、factor-engine、archive-worker、collector-operator、moox-skill）限定可调用的方法，校验 Admin 分配的 KeyID 与签名，再以 `access` 身份重新签名转发 |
| EventBus | TLS + 按角色划分的凭据（如 `storage-eventbus`、`factor-eventbus`、`hostagent-publisher`），由 Admin CLI 生成和轮换 |
| 交易所等外部密钥 | 存放在 Admin 的密钥表中，Trade 按 `secret_id` 单条读取 |

## 12. 构建、测试与发布

| 命令 | 作用 |
| --- | --- |
| `./scripts/build/build.sh <模块>` | 构建单个模块的二进制到 `bin/` |
| `bash scripts/build/build-linux-local.sh <目标>...` | 在本机构建 linux/amd64 二进制：纯 Go 目标交叉编译，含 CGO 的 Storage 在 Docker 编译镜像里构建；`make build-storage-linux` 等价于构建 Storage |
| `bash scripts/build/check-build-env.sh` | 检查本机构建环境，按系统给出缺项的安装命令；说明见[构建手册](构建手册.md) |
| `make verify` | 提交前的完整检查：依赖边界、格式、lint、Go 测试与 vet、前端测试与构建、文档构建、契约测试 |
| `moox-cli setup release build` | 构建一个版本的全部单元制品，供各部署命令以 `--release` 升级 |
| `moox-cli setup bootstrap --stage core/control` | 核心初始化及完整控制单元部署，返回阶段收据 |
| `moox-cli setup deploy-host/deploy-unit` | 按主机部署登记 host 和业务单元（含因子机外部程序） |

部署和日常运维见[部署与运维](部署与运维.md)。
