# 策略前端管理台设计

## 1. 设计结论

策略前端管理台是**运行观察和运维页面**，不是策略代码开发工具。

V1 明确不提供：

- Python 策略源码输入或在线编辑。
- Git/CI 集成流程。
- 已发布策略版本回滚按钮。
- 在线修改正在运行版本的代码。

策略包由后端导入/发布接口提交。管理台只展示策略的身份、版本、源码 hash、运行状态、决策结果和绩效表现。

策略版本仍然不可变。需要更换策略代码时，由后端导入新版本，再通过新的绑定配置启用；页面只负责查看和运行控制。

## 2. 页面导航

```text
策略管理
├── 运行概览
├── 运行中策略
├── 策略详情
│   ├── 基本信息
│   ├── 运行状态
│   ├── 决策记录
│   ├── 目标与持仓
│   ├── 策略表现
│   ├── 状态与数据
│   └── 错误与审计
└── 策略组合与执行账户
```

“策略版本”是查询维度，不作为独立的在线代码编辑页面。用户从运行中的 Binding 进入详情，而不是从源码文件进入页面。

## 3. 运行概览

### 3.1 页面目标

让值班人员在一个页面判断：当前有哪些策略在运行、是否正常计算、是否产生目标、表现是否异常、是否需要暂停。

### 3.2 顶部摘要

展示以下低基数摘要卡：

| 指标 | 说明 |
| --- | --- |
| 运行中策略 | 当前存在有效 Binding 的策略数 |
| 正常运行 | 最近一个调度周期成功完成的策略数 |
| 延迟策略 | 超过预期调度时间仍未完成的策略数 |
| 异常策略 | 最近运行失败、数据过期或执行状态未知的策略数 |
| Observe/Paper/Live | 按执行模式统计 Binding 数量 |
| 今日策略收益 | 按 `performance_source` 分开汇总，不能混合回测与实盘 |

### 3.3 运行策略表

默认按“异常优先、最近运行时间倒序”排列。

| 列 | 内容 |
| --- | --- |
| 策略 | `strategy_id` 和显示名称 |
| 版本 | `version`、`source_hash` 前 12 位 |
| Binding | Binding ID、Space、View、频率 |
| 模式 | `observe`、`paper`、`live` |
| 状态 | 运行中、已暂停、等待数据、计算失败、执行未知 |
| 最近运行 | 最近触发时间、耗时、结果状态 |
| 数据 | `data_revision`、数据截止时间、数据新鲜度 |
| 目标偏差 | 理论目标与实际持仓的最大偏差 |
| 表现 | 选定区间收益、回撤和净值变化 |
| 操作 | 查看、暂停/恢复、查看错误 |

支持按策略、Space、模式、状态和时间范围筛选；不支持按源码内容搜索。

## 4. 策略详情

### 4.1 基本信息

展示：

- 策略 ID、版本、API 版本、状态。
- `source_hash`、manifest hash、依赖信息。
- 发布时间、发布人、导入时间。
- 当前 Binding、Space、View、频率和参数摘要。
- 当前执行模式和关联账户/模拟账户。

页面不展示源码编辑器。源码 hash 可复制，用于与后端导入记录核对。

### 4.2 运行状态

展示最近一个调度周期的状态时间线：

```text
等待数据 -> 快照生成 -> Python 计算 -> 输出校验 -> 状态提交
                                      -> 目标生成 -> 执行提交/观察完成
```

每一步展示开始时间、结束时间、耗时、状态和错误摘要。需要区分：

- Python 计算失败。
- 输入数据未到齐或已过期。
- 状态 CAS 冲突。
- 目标通过但执行失败。
- Trade 返回未知状态。

执行失败不应被显示成策略计算失败；两者属于不同处理链路。

### 4.3 决策记录

按时间倒序展示每次 StrategyRun：

| 字段 | 说明 |
| --- | --- |
| 触发时间 | `trigger_bar_time` |
| 运行 ID | `run_id` |
| 数据版本 | `data_revision`、输入 hash |
| 状态版本 | 提交前 `state_revision` 和提交后 revision |
| 决策 | `hold` 或 `rebalance` |
| 目标数量 | 目标标的数、权重合计、净/总敞口 |
| 结果 | observed、accepted、failed、superseded |
| 执行 | execution ID、Trade rebalance ID 或 paper fill ID |

支持查看一次运行的目标明细和错误日志，但不允许在页面上重新编辑输入或手工修改输出。

### 4.4 目标与持仓

同屏展示三组数据：

1. 策略理论目标：Python 输出的完整目标权重。
2. 组合目标：多个策略聚合和风控后的目标权重。
3. 实际持仓：Trade 或 Paper 的实际仓位。

表格列包括 `instrument_id`、symbol、目标权重、目标数量、实际数量、偏差、最近价格、更新时间。目标权重和实际仓位必须明确标注数据来源和时间，禁止把理论目标伪装成实际持仓。

### 4.5 策略表现

提供区间选择：今日、近 7 天、近 30 天、运行以来和自定义时间范围。

核心指标：

- 净值曲线和累计收益。
- 区间收益、日收益和年化收益（样本足够时）。
- 最大回撤、回撤持续时间。
- 换手率、费用、成交次数。
- 波动率、胜率和收益/风险比（样本不足时显示“数据不足”）。
- 理论目标与实际持仓偏差。
- 策略运行成功率、平均耗时、超时次数。

每个指标都必须带 `performance_source`：

| 来源 | 计算依据 |
| --- | --- |
| `backtest` | 历史快照和虚拟成交 |
| `observe` | 理论目标与市场价格，不产生交易 |
| `paper` | 模拟成交、费用和持仓 |
| `live` | Trade 实际成交、账本和持仓对账 |

不同来源默认分开展示，不能把回测、Observe、Paper、Live 拼成一条累计收益曲线。

### 4.6 状态与数据

展示：

- 当前状态 JSON 的摘要和大小。
- `state_revision`、最近一次更新运行 ID、更新时间。
- 当前 `data_revision`、快照 hash、数据截止时间。
- 输入列、缺失列、数据行数和快照生成耗时。

默认只展示结构化摘要，不直接展示大块原始 JSON。状态重置属于高风险后端操作，V1 页面不提供删除状态按钮；如确需处理，走受控运维流程并记录原因。

### 4.7 错误与审计

按错误类型聚合：

- 数据缺失/数据过期。
- Python 异常或输出协议错误。
- worker 启动、超时或崩溃。
- 状态冲突。
- 风控拒绝。
- Outbox 积压。
- Paper/Trade 执行失败或未知。

审计记录至少包含操作者、时间、Binding、旧状态、新状态、操作原因和请求 ID。日志页面展示摘要和关联 ID，不把源码或账户敏感信息写入前端日志。

## 5. 运行控制

V1 只提供以下控制：

| 操作 | 作用 | 限制 |
| --- | --- | --- |
| 暂停 Binding | 停止新的策略触发 | 已接受执行意图继续由执行层处理 |
| 恢复 Binding | 重新允许策略运行 | 恢复前检查数据、worker 和执行状态 |
| 切换 Observe/Paper | 改变最终执行端口 | 必须记录操作者和生效时间 |
| 查看执行状态 | 查询 Paper/Trade 结果 | 不在 Strategy 页面直接重试未知订单 |
| 查看新版本 | 查看后端已导入版本 | 页面不提供源码输入或版本回滚 |

Live 模式的启用、账户绑定和资金限制属于单独的执行权限，不与普通策略查看权限合并。

## 6. 前端数据接口

### 6.1 策略运行查询

现有 `StrategyMgr` 需要扩展只读查询接口，建议保持分页和时间范围参数：

```text
ListRunningStrategies
GetStrategyOverview
ListStrategyRuns
GetStrategyRun
ListStrategyTargets
GetStrategyStateSummary
GetStrategyHealth
GetStrategyPerformance
```

运行控制接口：

```text
PauseBinding
ResumeBinding
SetExecutionMode
```

所有接口返回 `request_id`、服务时间和数据时间；性能接口额外返回 `performance_source`、`data_revision` 和指标计算时间。

### 6.2 统一状态返回

```json
{
  "status": "running",
  "mode": "paper",
  "last_run": {
    "run_id": "run-001",
    "trigger_bar_time": "2026-07-11T10:00:00Z",
    "status": "accepted",
    "duration_ms": 38
  },
  "data": {
    "revision": "view-42:00001873",
    "cutoff": "2026-07-11T10:00:00Z",
    "fresh": true
  },
  "health": {
    "worker": "ready",
    "outbox_lag_seconds": 0,
    "last_error": null
  }
}
```

### 6.3 性能接口返回

性能接口必须避免把不同来源混合：

```json
{
  "performance_source": "paper",
  "range": {"from": "2026-07-01", "to": "2026-07-11"},
  "currency": "USDT",
  "nav": 1.0342,
  "return": 0.0342,
  "max_drawdown": -0.012,
  "turnover": 0.42,
  "fees": 12.5,
  "as_of": "2026-07-11T10:05:00Z",
  "data_revision": "paper-ledger:000024"
}
```

没有足够数据时返回 `insufficient_data`，不要返回 0 造成误解；数据延迟时返回 `stale` 和最后更新时间。

## 7. 表设计

### 7.1 设计原则

前端不直接访问数据库，也不创建一套“前端策略表”。策略服务继续作为业务事实源，管理台通过 RPC 查询。表分为三类：

1. **业务事实表**：保存策略定义、Binding、状态、运行、目标和执行事实。
2. **查询辅助表**：保存运行耗时、健康摘要和已计算的绩效点，允许重建，不替代事实表。
3. **审计表**：保存暂停、恢复和模式切换等人工操作。

### 7.2 继续复用的业务事实表

以下表已经属于 Strategy 业务模型，前端只读取其服务层投影：

| 表 | 前端用途 |
| --- | --- |
| `t_strategy_defs` | 策略 ID、版本、API、源码 hash、状态 |
| `t_strategy_bindings` | Space、View、频率、参数和 Binding 状态 |
| `t_strategy_states` | 当前 state revision、最近运行 ID |
| `t_strategy_runs` | 每次策略决策、输入 revision、状态和输出 |
| `t_strategy_run_targets` | 某次运行的策略级目标明细 |
| `t_strategy_groups` / `t_strategy_group_members` | 策略组合及资金比例 |
| `t_strategy_group_targets` | 聚合后的组合目标和目标 hash |
| `t_strategy_execution_bindings` | 账户、执行模式和执行状态 |
| `t_strategy_execution_requests` / `t_strategy_execution_states` | 执行请求、幂等状态和结果 |
| `t_strategy_backtest_jobs` | 回测任务、配置 hash 和产物状态 |

这些表不建议被前端直接拼接查询，统一由 `StrategyMgr` 返回分页、权限过滤和数据时间。

### 7.3 需要新增的查询辅助表

#### `t_strategy_run_metrics`

保存单次运行的耗时和资源摘要，不改变 `t_strategy_runs` 的决策事实：

| 字段 | 说明 |
| --- | --- |
| `c_run_id` | 主键，关联 `t_strategy_runs` |
| `c_queue_delay_ms` | 排队等待时间 |
| `c_snapshot_duration_ms` | 快照生成耗时 |
| `c_compute_duration_ms` | Python 计算耗时 |
| `c_validate_duration_ms` | 输出校验耗时 |
| `c_total_duration_ms` | 总耗时 |
| `c_input_rows` | 输入行数 |
| `c_output_targets` | 输出目标数 |
| `c_worker_id` | worker 逻辑标识，不作为前端高基数筛选项 |
| `c_ctime` | 记录时间 |

主键保证同一个 `run_id` 只写入一次；重试只更新同一条记录。

#### `t_strategy_binding_health`

保存每个 Binding 的最新可重建健康摘要：

| 字段 | 说明 |
| --- | --- |
| `c_binding_id` | 主键 |
| `c_status` | running、paused、waiting_data、failed、unknown |
| `c_mode` | observe、paper、live |
| `c_last_run_id` | 最近一次运行 |
| `c_last_success_at` | 最近成功时间 |
| `c_last_error_type` / `c_last_error_message` | 最近错误摘要 |
| `c_last_data_revision` | 最近输入版本 |
| `c_data_cutoff` | 最近输入截止时间 |
| `c_worker_status` | worker 健康状态 |
| `c_outbox_lag_seconds` | Outbox 延迟 |
| `c_observed_at` | 摘要更新时间 |

该表是缓存，不是新的状态机事实。服务启动或定时任务可以根据运行、执行和 runtime 状态重建它。

### 7.4 绩效表

绩效必须按策略、Binding、执行模式和来源隔离，不能只按策略 ID 汇总。

#### `t_strategy_performance_points`

用于净值曲线和目标偏差图：

| 字段 | 说明 |
| --- | --- |
| `c_binding_id` | Binding |
| `c_performance_source` | backtest、observe、paper、live |
| `c_point_time` | 指标时间 |
| `c_nav` | 归一化净值 |
| `c_cumulative_return` | 累计收益 |
| `c_drawdown` | 当前回撤 |
| `c_gross_exposure` / `c_net_exposure` | 总/净敞口 |
| `c_turnover` | 本时间点换手 |
| `c_fees` | 累计或本点费用，需在协议中固定口径 |
| `c_data_revision` | 数据版本或账本版本 |
| `c_calculated_at` | 计算时间 |

建议主键为 `(c_binding_id, c_performance_source, c_point_time)`，并按时间和来源建立查询索引。

#### `t_strategy_performance_daily`

用于概览卡和区间统计，避免每次打开页面扫描所有曲线点：

| 字段 | 说明 |
| --- | --- |
| `c_binding_id` | Binding |
| `c_performance_source` | 绩效来源 |
| `c_trade_date` | 统计日期 |
| `c_start_nav` / `c_end_nav` | 日初/日末净值 |
| `c_return` | 日收益 |
| `c_max_drawdown` | 日内最大回撤 |
| `c_turnover` | 日换手 |
| `c_fees` | 日费用 |
| `c_win_count` / `c_loss_count` | 胜负次数 |
| `c_sample_count` | 样本数 |
| `c_data_revision` | 计算依据版本 |
| `c_calculated_at` | 计算时间 |

唯一键为 `(c_binding_id, c_performance_source, c_trade_date)`。重算采用同键覆盖，不能产生重复统计日。

### 7.5 审计表 `t_strategy_operation_audits`

记录管理台操作，不记录源码内容：

| 字段 | 说明 |
| --- | --- |
| `c_operation_id` | 主键和幂等键 |
| `c_operator` | 操作者 |
| `c_action` | pause、resume、set_mode、view_sensitive 等 |
| `c_binding_id` | 作用对象 |
| `c_old_value` / `c_new_value` | 脱敏后的状态变化 |
| `c_reason` | 操作原因 |
| `c_request_id` | 请求追踪 ID |
| `c_ctime` | 操作时间 |

操作表只追加，不允许页面删除或修改历史审计记录。

### 7.6 数据保留

- 运行事实、状态和执行关联按业务审计周期保留。
- `t_strategy_performance_points` 可按分钟/小时粒度设置保留期，过期后保留日汇总。
- `t_strategy_performance_daily` 保留周期应长于曲线点。
- 健康摘要只保留当前快照；历史健康变化通过运行事实和审计表追溯。
- 所有查询辅助表都必须能够由事实表、Paper/Trade 账本和回测产物重新生成。

## 8. 权限和交互规则

建议至少分为四类权限：

| 权限 | 允许内容 |
| --- | --- |
| `strategy.viewer` | 查看运行策略、目标、表现和错误 |
| `strategy.operator` | 暂停/恢复 Binding、切换 Observe/Paper |
| `strategy.risk` | 查看 Live 风险、偏差和执行状态 |
| `strategy.admin` | 管理策略绑定和执行配置；仍不能在线编辑源码或回滚版本 |

前端不得缓存账户密钥、完整策略源码或未脱敏交易凭证。高风险操作必须二次确认，确认框显示影响范围、当前模式和生效时间。

## 9. 页面状态和告警

必须明确区分：

- `loading`：正在读取。
- `empty`：没有运行策略或时间范围内没有表现数据。
- `stale`：数据超过新鲜度阈值。
- `partial`：部分执行账户或数据源不可用。
- `error`：查询失败。

告警建议：

- 连续运行失败。
- 策略延迟超过频率预算。
- 输入数据 revision 长时间不更新。
- 目标与实际持仓偏差超过阈值。
- Outbox 或 Trade 执行状态长时间未知。
- Live 实际收益与理论目标收益偏差过大。

## 10. 实施顺序

### Phase 1：只读运行监控

- 运行概览。
- 运行策略列表。
- 策略基本信息、版本 hash、Binding 和 worker 状态。
- 最近运行记录和错误详情。

### Phase 2：目标与表现

- 理论目标、组合目标和实际持仓对比。
- Observe/Paper/Live 分来源绩效。
- 净值、回撤、换手和费用图表。
- 数据 revision 和快照信息。

### Phase 3：受控运行操作

- 暂停/恢复 Binding。
- Observe/Paper 模式切换。
- 风险偏差和执行未知状态告警。
- 审计查询和权限细分。

本阶段不包含源码编辑、Git/CI 集成和版本回滚。

## 11. 当前后端缺口

当前 Strategy 首版已有策略定义、Binding、运行事实、状态和部分执行模型，但完整前端还需要：

1. 分页查询策略、Binding、运行和目标的 RPC。
2. 统一健康状态聚合，包括 Storage、runtime、Outbox 和 Trade。
3. Performance 聚合模型，区分 backtest、observe、paper、live。
4. Paper/Trade 成交、持仓和费用查询接口。
5. Admin Gateway 的策略路由、鉴权和审计接入。

这些接口完成前，前端只能展示已经存在的 StrategyRun 和目标数据，不能自行计算或猜测实盘绩效。
