# 元数据命名规范

本文定义 MooX 中业务身份、事件、配置和代码目录的统一命名规则。新项目不保留历史命名例外；代码、配置、测试数据和文档必须使用本规范。

## 通用规则

- 面向机器识别的标识只使用 ASCII 字符。
- 业务 ID 默认使用小写；普通 ID 使用 `snake_case`，Factor ID 保留因子文件名的大小写组合，事件名称和 NATS Subject 使用 `.` 分层。
- 单词使用完整、稳定且含义明确的英文单词，避免缩写、拼音和同义词混用。
- 名称只描述稳定业务身份，不包含 Provider、部署环境、实例、时间戳或版本号。
- 类型前缀用于容易混淆的跨域标识，例如 View 使用 `view_`、Event 使用 `event.`；Factor ID 直接使用因子文件名主体，不添加前缀。
- 版本和修订信息放在元数据字段、Schema 或配置中，不拼接到稳定业务 ID。
- 第三方接口名称、交易所原始字段和外部协议字段保持其原始命名；本规范只约束 MooX 自有标识。

## Space ID

Space ID 表示业务市场或系统域，使用单个稳定 token，不再使用同一语义的多种写法。

| 含义 | Space ID |
| --- | --- |
| 中国股票市场 | `stockcn` |
| 香港股票市场 | `stockhk` |
| 美国股票市场 | `stockus` |
| 加密货币市场 | `crypto` |
| MooX 系统域 | `mooxsys` |

因此，统一使用 `stockcn`，禁止使用 `stock_cn`、`stock_hk`、`stock_us`、`crypto_market` 和 `moox_system`。市场 Space 使用 `stockcn`、`stockhk`、`stockus` 的紧凑形式，保持同一组市场标识的一致性。

## Dataset ID

Dataset ID 使用：

```text
dataset_<space>_<asset>_<series>
```

示例：

```text
dataset_stockcn_equity_kline
dataset_stockcn_index_kline
dataset_stockcn_bond_kline
dataset_crypto_spot_kline
```

约束如下：

- `dataset_` 必须位于 Dataset ID 最前面，用于和 View、Factor 等标识区分。
- Dataset 表示实际存储的数据集合，默认不在稳定 ID 中携带查询频率；多个频率通过 `freq` 维度共存。
- View 是面向查询的频率契约，因此每个时序频率必须建立独立 View。
- 只有在不同频率需要物理存储隔离、独立保留策略或独立数据源时，Dataset 才允许把频率作为末级 token，例如 `dataset_crypto_spot_kline_1m`。
- Provider 和 source 不进入逻辑 Dataset ID；来源信息放在数据源、规则或运行时字段中。
- `asset` 使用受控词表，例如 `equity`、`index`、`bond`、`spot`、`swap`。
- 同一 Space 下的 Dataset 也必须携带 Space token，例如 `stockhk` 使用
  `dataset_stockhk_equity_kline`，系统域使用 `dataset_mooxsys_service_metrics`。
- Dataset ID 不携带 `_v1`、`_v2` 等版本号；结构或协议版本放在元数据 revision、Schema
  或事件版本字段中。

## View ID

View ID 是稳定的查询业务身份。时序 View 统一使用：

```text
view_<space>_<asset>_kline_<frequency>
```

例如：

| 场景 | View ID |
| --- | --- |
| A 股股票 1 分钟 | `view_stockcn_equity_kline_1m` |
| A 股指数日线 | `view_stockcn_index_kline_1d` |
| A 股可转债 1 分钟 | `view_stockcn_bond_kline_1m` |
| 加密货币现货 1 分钟 | `view_crypto_spot_kline_1m` |

约束如下：

- `view_` 必须位于 View ID 最前面，不再使用结尾的 `_view`。
- `space` 使用稳定的 Space ID；`asset` 使用受控资产类型。
- `frequency` 使用规范短语：`1m`、`5m`、`15m`、`1h`、`1d`、`1w`、`1mo`。月份使用 `1mo`，不使用 `1M`。
- 一个 View 的查询契约只对应一个频率。Dataset 可以支持多个频率，但应为不同频率建立不同 View。
- View 浏览和管理界面必须同时展示 View ID、主 Dataset ID 和 View filter 中解析出的频率，
  不能只展示 Dataset 中文名或省略频率。
- Provider 和 source 不进入 View ID；来源切换不应改变业务查询入口。
- View 的列变化使用 View revision 管理，不把版本号拼到 View ID 中。

因子结果 Dataset 和 View 由 Factor Registry 根据源 View 派生生成。标准命名必须保留
Space、资产类型、K 线频率和 `factor` 角色后缀：

```text
dataset_<space>_<asset>_kline_<frequency>_factor
view_<space>_<asset>_kline_<frequency>_factor
```

例如加密货币现货 1 分钟因子结果为
`dataset_crypto_spot_kline_1m_factor` 和 `view_crypto_spot_kline_1m_factor`。
同一源 View 下的多个因子共享这两个对象，Factor ID 不拼接到对象 ID 中；因子明细由
结果列的 `origin_factor_id` 和绑定元数据表达。Provider 不参与结果对象命名，即使源 View
的主 Dataset 由某个具体交易所提供，也不能生成 `dataset_binance_*` 或 `view_binance_*`
这样的结果对象。标准名称不能使用哈希替代可读字段；仅当用户自定义名称超过长度上限时，
才允许使用稳定哈希作为末尾截断标识。

非时序 View 不拼接频率，统一使用：

```text
view_<space>_<resource>
```

例如：`view_mooxsys_host_resource`、`view_mooxsys_service_metrics`。

## Event Name

Event Name 用于描述领域事件，统一使用 `event.` 前缀，并使用点号分隔层级：

```text
event.<domain>.<resource>.<action>
```

示例：

```text
event.collector.dataset.ready
event.collector.dataset.failed
event.storage.dataset.written
event.factor.view.computed
event.trade.order.created
event.trade.order.filled
```

约束如下：

- `event.` 必须位于名称最前面，不能使用 `event_` 或裸事件名。
- `domain` 表示事件所属业务域，使用模块或领域名称。
- `resource` 表示事件涉及的业务对象。
- `action` 使用过去式或明确状态词，例如 `created`、`updated`、`deleted`、`ready`、`failed`。
- 不把环境、实例、Provider、时间戳和版本号放入 Event Name。
- 事件版本放在 EventMessage 元数据或 Schema 中，不放入名称。

### Event Name、Event Type 与 NATS Subject

- Event Name 是业务语义名称，作为 EventMessage 的稳定类型标识。
- Event Type 如果用于协议或序列化层，应直接复用 Event Name，不另造一套名称。
- NATS Subject 是传输路由名称，可以在 Event Name 后追加受治理的路由维度，例如 Space、Dataset；追加部分仍使用小写点号分隔。
- Subject 的路由维度不能改变事件语义，也不能替代 EventMessage 中的业务字段。
- 事件生产者和消费者必须只使用已登记的事件名称和 Subject，不得临时拼接未声明的主题。

## Factor ID

Factor ID 使用文件名主体本身：

```text
<FactorName>
```

其中 `FactorName` 必须与 `modules/factor/factors` 下对应 Python 因子文件的文件名主体完全一致，去掉 `.py` 后缀，保留原始大小写组合。因子本身是跨市场、跨 Space 复用的通用计算定义，因此 Factor ID 不包含 Space 信息。

例如：

| 因子文件 | Factor ID |
| --- | --- |
| `Bias.py` | `Bias` |
| `BiasQ.py` | `BiasQ` |
| `QuoteVolumeMeanQ.py` | `QuoteVolumeMeanQ` |
| `ZscoreAbsMeanQ.py` | `ZscoreAbsMeanQ` |

因子输出字段使用小写 `snake_case`，字段名应表达业务含义，不携带 Provider、运行环境和实现版本。

因子结果对象仍然属于具体 Space，但它由源 View 派生，而不是由 Provider 专属的源主
Dataset 派生。一个源 View 下的多个因子共享同一结果 Dataset 和 View，因此结果对象 ID
不直接包含单个 Factor ID；由 Factor Registry 的固定规则生成。

## Subject ID 与 Series Tag

- Subject ID 是标的在 Dataset 中的稳定业务标识，优先使用外部市场通用代码，例如 `600000.XSHG`、`BTC-USDT`。
- Subject ID 不强制改写为 MooX 的小写蛇形格式，因为它通常属于外部市场编码。
- Series Tag 用于区分同一 Subject 下的不同数据序列，使用小写 `snake_case`，例如 `default`、`adjusted`。
- Subject、Series Tag 和外部 Symbol 的语义必须分开，不使用多个字段表达同一身份。

## Event Payload、字段和数据库对象

- Go 导出字段使用标准 Go 命名：导出标识使用 `PascalCase`，非导出标识使用 Go 默认的小写或混合写法。
- Protobuf 字段、JSON 字段和数据库列名使用小写 `snake_case`。
- 数据库表名使用 `t_<domain>_<resource>`；主键和公共列使用 `c_<name>`。
- JSON、YAML 和 TOML 配置键使用小写 `snake_case`；环境变量使用大写 `MOOX_<DOMAIN>_<NAME>`。
- 时间字段统一使用带含义的后缀，如 `_at` 表示时间点，`_time` 表示业务时间，`_ms`、`_s` 表示数值单位。
- 布尔字段使用 `is_`、`has_`、`enable_` 或 `allow_` 等明确前缀，避免使用含义不明的 `flag`。

## 服务、模块、目录和脚本

- 顶层业务代码统一放在 `modules/<module>`；公共能力放在 `packages/<package>`。
- Go package 使用小写单词；多个单词直接拼接，例如 `stockcn`，不使用下划线。
- 服务目录使用小写 `snake_case`；服务二进制名称使用小写短横线或下划线，但同一目录内必须保持一致。
- 配置按职责放置：模块专属配置放在 `modules/<module>/config`，需要用户统一干预的配置放在仓库根目录。
- 脚本按职责放在 `scripts/build`、`scripts/check`、`scripts/ci`、`scripts/deploy`、`scripts/deps`、`scripts/marketdata`、`scripts/release`、`scripts/runtime` 和 `scripts/test` 下；不在 `scripts` 根目录堆放业务脚本。
- 脚本文件名使用小写短横线，例如 `verify-event-contracts.sh`；同一类脚本放在同一目录，不保留旧路径兼容包装脚本。

## 初始化配置

`config/setup` 是 `setup init`、Monitor、Admin 和 Collector 共用的仓库内置 seed，不是随手运行的示例。用户可干预的主配置放在仓库根目录 `moox.toml`，其模板为 `moox.toml.example`。

## 禁止事项

- 不新增 `stock_cn`、`stock_hk`、`stock_us`、`crypto_market` 等带下划线的市场 Space ID，也不使用 `moox_system`。
- 不新增尾部带 `_view` 的 View ID；统一使用开头的 `view_`。
- 不新增不带 `event.` 前缀的事件名称。
- 不把 Provider、环境、版本和时间戳嵌入稳定业务 ID。
- 不为旧名称新增兼容别名、转发器或重复配置。
