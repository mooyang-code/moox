# MooX 策略执行框架设计

## 文档状态

本文定义 Strategy 模块的目标架构，修订日期为 2026-09-05，替代《选币策略执行框架设计》。
文中的“执行”指策略定义的求值，不指订单执行。模块继续命名为 Strategy，不再以“选币”限制其能力。

本文已纳入目标持仓边界、组件化 DSL、理论持仓状态及本地 XBX 参考代码的讨论结论。
它是后续设计和实施的依据，不是当前代码已具备这些能力的声明。本轮只修订设计文档，
不实施 DSL、协议、数据库或其他模块的重命名。

[2026-08-29 实施计划](superpowers/plans/2026-08-29-moox-coin-selection-strategy.md)
保留为上一版实施记录。该计划中的单池、无组件、无理论状态、后滤后等权、相同权重不发布等
约束已经失效；其施工步骤和验收项尚未按本文重写，不能直接作为新版实施计划执行。
本轮对该计划只修正因文档改名产生的路径引用，并标注基线已过时。

本文固定以下决策：

- Strategy 只计算该策略的理论目标持仓权重，并可靠发送给 Trade。
- Strategy 不读取真实持仓、账户权益、订单或成交，不根据 Trade 业务反馈推进策略。
- Trade 独立负责权重换算、实际持仓差额、下单、重试、风控和目标过期后的执行政策。
- 一个 StrategyDef 可包含多个单边组件，组件目标在一个 Runner 内合成一个完整目标。
- 多空方向分别声明，不设置隐式的多空反向排序，也不自动归一化组件预算。
- offset 表示并存的理论持有批次；理论状态与交易状态严格分离。
- 每个新的有效决策发布完整目标，即使权重与上一决策相同；同一决策重投仍保持幂等。
- DSL 使用逻辑输入，Runner 绑定物理数据依赖和投递目的地；定义不嵌入交易账户或凭据。
- Factor 保持 FactorDef + Binding 两层，不引入 FactorInstance，不把因子引擎搬入 Strategy。
- 单进程、SQLite、JetStream、Runner 内串行求值即可；不引入分布式工作流或全局 exactly-once。

## 1. 职责与非目标

### 1.1 模块边界

```text
Collector / Factor
  -> 向 Storage 提交数据与完成 marker
Storage
  -> 持久化数据，再通过 outbox 发布 View 可读事件
Strategy
  -> 冻结输入和依赖版本
  -> 按 StrategyDef 计算各组件理论目标
  -> 合成 PositionTargets
  -> 原子保存决策、理论状态和 outbox
Trade
  -> 接收并保存目标
  -> 根据自身资金、价格、持仓和执行政策执行
Monitor / 管理界面
  -> 分别观察 Strategy 计算/投递结果与 Trade 执行结果
```

Strategy 分别记录 `CALCULATED`（目标已计算）和 `PUBLISHED`（消息已获 broker 发布确认），
二者都不表示 Trade 已接受，更不表示已经成交或达到目标仓位。Trade 可以发布接受、拒绝、部分成交和失败事件，
但这些事件不作为 Strategy 求值输入，也不驱动其重试、补单或理论持仓修正。

可靠发布仍是 Strategy 的职责：outbox 在目标有效期内重试发送同一目标，直到获得 broker
确认或到期终止。这属于传输可靠性，不是交易执行反馈闭环；具体到期规则见第 10 节。

### 1.2 不属于 Strategy 的内容

- 真实账户、可用资金、权益、保证金、实际持仓、订单和成交管理。
- 权重到数量的换算、执行账户选择、最小下单量、价格精度和合约乘数处理。
- 网格下单、拆单、追单、撤单、交易所 API 调用及执行失败恢复。
- 根据实际成交收益调整策略预算，或自动用其他组件填补交易失败的仓位。
- 任意 Python/Go 用户脚本、任意网络访问、回测撮合和收益曲线模拟引擎。
- 为兼容旧 DSL 保留两套求值含义，或在运行时猜测旧配置意图。

固定权重、条件目标、排序轮动和基于规则的理论进出场属于本框架；
订单级策略不因为名称中带有“策略”就进入本 DSL。

### 1.3 控制面与运行链路

一个执行型 Runner 对应一个 Trade 资金单元，当前可映射为 LogicalAccount。
同一资金单元同一时刻只能有一个有效的完整目标发布者。多个组件在 Runner 内合成，
不能让多个 Runner 各自发送 FULL 去覆盖同一资金单元。

投递绑定、授权和绑定代次由管理控制面与 Trade 建立，再作为不可变运行参数注入 Runner。
不要求 Strategy 在每次求值前后查询 Trade owner，也不把 Trade 生命周期协调放进求值器。
控制面可复用现有管理入口，不需要因此增加一个独立服务。

停用 Runner 只停止计算和新的目标发布，不隐含撤单或清仓。暂停 Trade 自动化、撤销投递绑定、
清空目标和清仓是不同的管理动作，应显式调用 Trade 的管理能力。撤销或替换绑定必须推进
Trade 侧的绑定代次，使旧 outbox 消息即使延迟到达也无法恢复旧目标。

需要主动消除的隐式行为：

- 选币框架先在准入池评分再前滤，选股框架先前滤再评分。DSL 必须显式声明排名样本集。
- 参考代码先等权再后滤，后滤删除的份额留空；不能改成后滤后自动满仓而仍宣称语义相同。
- 数量、比例、名次区间和百分位区间必须分型，不用数字大小或魔法字符串推断。
- 并列评分可以共享统计名次，但固定数量选择必须有确定的截取规则，不能意外超选。
- 股票交易日、连续市场小时、信号观测时刻和目标生效时刻不能混用。
- 截面排名再做历史差分，不等于各标的独立计算一个普通时序因子。
- 回测中的次日可交易信息不能作为实时策略当时已知的数据；缺失持仓数据也不能隐式触发退出。

仓位管理框架中的收益曲线轮动依赖子策略的理论绩效序列。MooX 可保留该方向，
但必须由独立的研究或绩效数据能力提供输入，不能让 Strategy 调用 Trade 成交结果补齐，
也不能宣称仅增加一段配置就已有收益曲线轮动能力。

## 3. 术语与命名

### 3.1 领域对象

| 对象 | 含义 |
| --- | --- |
| `StrategyDef` | 可发布、不可变、有版本的策略定义 |
| `StrategyComponent` | 定义内部一个单边目标计算组件，不是独立 Runner 或交易账户 |
| `InstrumentPoolRule` | 市场、报价资产、包含/排除名单和最短历史等标的准入规则 |
| `InstrumentPool` | 某时点由规则解析出的规范标的集合 |
| `StrategyRunner` | 绑定某个定义版本、输入依赖和投递目的地的运行实例 |
| `CompiledStrategy` | 针对 Runner 绑定编译的不可变计算计划与依赖清单 |
| `EvaluationInput` | 一次决策的逻辑输入值、标的池和读取版本信息 |
| `TheoryState` | 理论批次、理论入选记录和退出冷却等决策状态 |
| `base_allocation` | 组件内的无量纲基础份额，尚未乘组件预算、批次份额或择时乘数 |
| `component_contribution` | 乘预算、批次份额、方向及择时后的标的贡献，只在合成时计算 |
| `StrategyResult` | 一次成功决策及其输入身份、前后理论状态和解释记录 |
| `PositionTargets` | 目标持仓：该 Runner 对应资金单元的一次完整目标快照，包含决策时点、有效期及标的目标列表 |
| `InstrumentTarget` | 单个标的的目标持仓，由 `instrument_id` 和 `target_weight` 组成 |
| `ReadinessChecker` | 无状态检查本次输入是否可读且完整的组件 |

### 3.2 Spec 与 Def

统一对象含义，不做全仓 `Spec` 到 `Def` 的机械替换。

| 对象语义 | 建议命名 | 说明 |
| --- | --- | --- |
| 可复用、可校验、可发布的定义 | `StrategyDef`、`FactorDef`、`ResampleRuleDef`、`CheckDef` | `Def` 表示定义，而不是本次执行参数 |
| 运行绑定 | `Binding` | 连接定义、物理数据与运行目的地 |
| 一次执行的调用描述 | `Invocation` / `Request` | 当前 Factor 引擎的 `FactorSpec` 更适合 `FactorInvocation` |
| 具体订单意图 | `OrderIntent` / `OrderRequest` | 含数量、价格和归属的 `OrderSpec` 不应叫 `OrderDef` |
| 任务规划结果 | `TaskPlan` / `TaskDraft` | 适用于适配器产出的待执行任务，不冒充可复用定义 |
| 参数、服务配置 | `Params` / `Config` | 不因已有 `Spec` 后缀而改成定义对象 |
| 查询、过滤、排序 | `Query` / `FilterExpr` / `SortRule` | 使用实际用途命名 |

用户 DSL 的根对象统一为 `StrategyDef`；原始 YAML/JSON 文本可称为 manifest，
但不再把 `Manifest`、`StrategySpec` 和 `StrategyDef` 当成三个含义相同的领域对象。
这些命名是后续相关模块修改时的规则，本次不发起全仓重命名。

## 4. 定义、绑定与编译

### 4.1 StrategyDef

```text
strategy_id           稳定逻辑标识
revision              不可变发布版本
name                  用户可读名称
api_version           DSL 语言版本
definition_yaml       原始用户文本
definition_json       校验并规范化后的定义
definition_hash       规范化定义的 hash
created_at
```

同一 `strategy_id + revision` 发布后不可修改。修改规则、参数或名称时发布新 revision，
Runner 固定引用具体版本，不自动追随最新版。语言版本与策略 revision 是不同概念。

本文 DSL 使用 `api_version: moox.strategy/v3`，与当前 `moox.strategy/v2` 的
`kind: coin_selection` 根结构明确区分，不兼容解析旧 DSL，也不表示 v3 已经实现。

### 4.2 Runner 绑定

StrategyDef 只引用逻辑输入，如 `momentum`、`liquidity`、`exposure`。
Runner 将这些输入绑定到具体的行情字段、FactorDef 输出和 enabled Binding。
定义中不出现 `space_id`、物理 View ID、账户 ID、凭据或执行算法。

```text
StrategyRunner
  runner_id
  strategy_id + revision
  space_id
  input_bindings        逻辑输入 -> 数据/因子输出/Binding/View
  delivery_binding      观察模式，或目标资金单元与授权绑定代次
  compiled_artifact
  status                DISABLED | ENABLED
  activation_id         本次启用的理论运行身份
  last_result_id
  command_sequence
```

Factor 仍以 `factor_id` 标识已发布计算定义；参数、输出和源码 hash 必须随依赖冻结。
不引入 FactorInstance，也不允许启用后悄悄替换公式或输出。多输出 Factor 必须明确选择
输出列，不能在运行时猜测。自定义公式先作为 Factor 能力发布，再绑定给 Strategy 使用。

### 4.3 编译职责

编译分为定义校验和绑定编译，不把账户与物理 View 固化进可复用的 StrategyDef。

1. 严格解析 DSL，拒绝未知字段、重复键、未知组件类型和未注册算子。
2. 校验逻辑输入、类型、组件引用、预算、市场方向、日历和调度规则。
3. 解析 Runner 的输入绑定，冻结 FactorDef、输出、Binding、View、schema 和日历版本。
4. 生成每种求值任务所需输入的闭包，包括当前池、理论持仓和择时所需数据。
5. 验证读取快照、历史窗口、截面作用域与运行时算子能力均能满足要求。
6. 生成 `CompiledStrategy`、依赖清单、编译器版本和 artifact hash。

`Compiler.VerifyDependencies` 在启用前及相关运行检查中只复核已经冻结的依赖，
不重新寻找 Binding、不自动换因子，也不根据线上状态修改定义。

当前单 Source View、单 Factor Result View 的实现可作为首阶段能力限制。
需要多 View、多频率或历史截面输入的定义，在对应能力缺失时必须编译失败，
不能选用“最接近”的输入，也不能把部分组件算完后当成完整策略输出。

## 5. DSL 结构

### 5.1 根结构

| 字段 | 作用 |
| --- | --- |
| `api_version`、`kind`、`name` | 语言版本、固定根类型 `StrategyDef` 和名称 |
| `clock` | 日历、基础 bar 粒度与时间锚点 |
| `inputs` | 逻辑输入的类型与作用域 |
| `target` | 完整目标的最早生效时间规则与有效期 |
| `limits` | 理论预算上限，不是交易账户风控 |
| `components` | 以稳定组件 ID 为键的单边组件集合 |
| `timing` | 可选的整个目标组合暴露乘数 |
| `compose` | 组件目标的求和与同标的净额规则 |

组件类型是带标签的联合类型，不是可随意拼接的执行 DAG：

| `kind` | 必需决策配置 | 理论状态 |
| --- | --- | --- |
| `ranked` | `universe`、`schedule`、`holding`、`score`、`select`、`allocation` | replace 基础份额，或多个 cohort |
| `fixed` | `weights` | 固定基础份额；可叠加择时 |
| `entry_exit` | `universe`、`schedule`、`holding`、`score`、`capacity`、`entry`、`exit`、`allocation` | 理论入选集合、进入时点、占用份额和冷却期 |

三类组件均必须声明 `kind`、`side`、`budget`，择时为可选。多头与空头各写一个组件，允许使用不同
标的池、因子、日程和预算；不引入相互覆盖的 `long/short` 两套根字段。
组件不能读取另一组件的“本次结果”形成隐式依赖环；不提供 `long_nums` 等魔法引用。

表中的必需字段不做隐式补全。`ranked` 可选前/后滤；`fixed` 不接受选取、日程或 holding
字段；`entry_exit` 不接受 ranked 的前/后滤和 select 字段。不同 kind 的字段不能混用。
根字段除 `inputs`（默认空）、`limits`（默认总预算上限 1）和 `timing`（默认不缩放）外均必填。

### 5.2 完整示例

下面只演示语言结构，不是交易建议。`<instrument_id>` 是需替换为真实规范 ID 的占位说明，
生产发布时不能接受该占位字符串；逻辑输入必须由 Runner 显式绑定。

```yaml
api_version: moox.strategy/v3
kind: StrategyDef
name: multi_component_demo

clock:
  calendar: crypto_24x7
  bar: 1h
  anchor: "2026-01-01T00:00:00Z"

inputs:
  momentum: {type: number, scope: instrument}
  liquidity: {type: number, scope: instrument}
  exposure: {type: number, scope: portfolio}

target:
  effective: bar_close
  valid_for_bars: 2

limits:
  max_gross_budget: "1"

components:
  rotation:
    kind: ranked
    side: long
    budget: "0.60"
    universe:
      markets: [spot]
      quote_assets: [USDT]
      include: []
      exclude: []
      min_history_bars: 168
    schedule: {every_bars: 24, offsets: [0, 12]}
    holding: {mode: cohorts, duration_bars: 24, budget_split: equal}
    pre_filter:
      all:
        - {input: liquidity, op: gt, value: "0"}
    score:
      method: rank_weighted
      scope: candidates
      factors:
        - {input: momentum, prefer: high, weight: "1"}
    select: {mode: count, value: 8, ties: instrument_id, insufficient: take_available}
    allocation: {method: equal}
    post_filter: {all: [], refill: false, reweight: false}
    timing:
      component: {input: exposure}

  core:
    kind: fixed
    side: long
    budget: "0.20"
    weights:
      "<instrument_id>": "1"

compose: {method: sum, netting: instrument_id}
```

`rotation` 的两个 offset 各分得 0.30 预算，每个批次独立保留 24 个 bar。
若某批次选中 8 个标的，则每个基础份额为 1/8，合成时只乘一次预算得到 0.0375；后滤删除
其中 2 个时，默认其余 6 个仍各贡献 0.0375，而不是重新分到 0.05。
`core` 使用 0.20，剩余预算不自动补给任何组件。

### 5.3 输入类型

- `type` 支持 `number`、`boolean`、`string`。DSL 中 Decimal 数值的词法形式是十进制字符串，
  如 `"0.60"`，schema 显式解码并规范化为 Decimal；这不等于声明了 `string` 类型。
  bar 数、数量、offset 和名次等整数结构字段直接使用 YAML/JSON 整数。
- `scope: instrument` 表示每个标的一份值；`scope: portfolio` 表示该决策的一份标量。
- 比较、排名和乘法必须满足类型约束，不把声明为 `string` 的输入在运行时偷偷转成数值。
- 未配置择时不等于配置的择时输入缺失。前者使用乘数 1，后者是输入不完整。
- 时序、截面及截面历史因子的计算域由 Factor 定义及编译依赖说明，不用相同的
  `scope: instrument` 掩盖其不同的数据需求。

例如 RankDiff 需要“在同一可追溯标的池内排名，再按标的计算历史差分”。提供方必须
声明池定义、池的时点语义、历史长度和数据版本。不能把某个固定池计算的历史排名绑定到
另一个池，并称为该策略自己的排名。该能力不可用时拒绝编译。

## 6. 标的池、数据完整性与时间

### 6.1 标的池解析

每个 `ranked` / `entry_exit` 组件拥有自己的 `InstrumentPoolRule`，可以复用同一份
物理数据，但不要求所有组件共用一个池。固定组件的 `weights` 键必须是规范标的 ID。

```text
候选 = 满足市场、报价资产、include/exclude 等规则的标的
适格 = 在绑定的数据序列上满足历史长度等资格的候选
InstrumentPool = 按 instrument_id 升序规范化的适格集合
```

数据来源与执行市场分开：物理 venue 及其优先级由 Runner 输入绑定决定；
组件选择的是规范市场标的，不替 Trade 选择执行账户。若首选 venue 无历史，不能借用
其他 venue 的历史计数将其判为适格。多 provider 数据必须带 subject/series selector，
不能按同名 instrument 混成一条序列。

历史不足的新上市标的可正常排除。当前池内必需行、列缺失则是数据异常，不能静默缩池。
已有理论持仓不在本次候选池中，不等于自动退出；entry_exit 的数据闭包仍包含理论持仓，
是否退出由显式退出条件决定。缺行或实际不可交易不能代替退出信号。

### 6.2 时间模型

以下概念必须分别记录：

| 概念 | 含义 |
| --- | --- |
| `clock.bar` | 策略基础决策网格，不代表所有因子都只能用该窗口 |
| `clock.calendar` | 连续市场或交易市场的有效 bar/交易日/session 定义 |
| `clock.anchor` | 调度编号和 offset 的确定性起点 |
| `schedule` | 何时产生新选择或执行理论进出场判断 |
| `holding` | 基础目标替换规则或理论批次有效窗口 |
| `as_of` | 本次决策所用观测数据的截止时点，采用闭合 bar 的结束时刻 |
| `information_cutoff` | 本次冻结输入时的可用信息截点 |
| `effective_at` / `valid_until` | 完整目标允许执行的时间区间 |

调度使用日历中的连续有效 bar 编号。编号为 `k`、周期为 `p` 时，
`k mod p` 落入 `offsets` 才为该组件创建新选择。offset 必须唯一且处于 `[0, p)`。
`replace` 仅允许一个 offset；`cohorts` 可有多个 offset，且本版要求
`duration_bars = every_bars`，避免同一 offset 内再叠加多个不明确预算的批次。

普通定期替换必须显式写成以下形式；`holding.mode: replace` 不接受 duration 或 budget_split。
非选取 bar 延续基础份额，仍按根节拍合成并发布目标：

```yaml
schedule: {every_bars: 24, offsets: [0]}
holding: {mode: replace}
```

`cohorts` 必须提供 `duration_bars` 和固定为 `equal` 的 `budget_split`；
`entry_exit` 本版只允许 `schedule: {every_bars: 1, offsets: [0]}`，其
`holding.mode: until_exit` 必须提供正整数 `max_bars` 和非负整数 `cooldown_bars`。

股票的 `1d` 是交易日 bar，不是固定 24 小时；session、午休、节假日及其版本属于日历。
禁止用硬编码 UTC 偏移、次日加 23 小时等规则代替日历映射。

`target.effective` 支持 `bar_close` 和 `next_session_open`；后者只用于有明确 session 的
交易日/session 级基础 bar，不用于把多个盘中 bar 挤到同一次开盘。编译后的日历必须提供
严格递增的生效边界映射 `E(k)`：bar `k` 的目标最早在 `E(k)` 生效，持有 `d` 个 bar 的
批次在 `E(k + d)` 到期。进入年龄和冷却仍按同一决策 bar 序号计算，不使用调用次数。

`valid_for_bars` 必须大于零，bar `k` 的目标默认有效至 `E(k + valid_for_bars)`。
若期间已有确定的批次到期或理论强制退出边界，则将 `valid_until` 截短到最近的该边界，
不能让完整快照声明的有效期跨过已知的目标失效时刻。合成以本次 `effective_at` 为基准，
先排除在该时刻已到期的批次，再纳入在该时刻生效的新批次。

`effective_at` 是最早允许执行的时刻，不要求系统恰在该时刻收到消息；到达后只要处于
`[effective_at, valid_until)` 仍可处理。已过期的历史决策不得改用当前时间延长有效期后重发。

例如周五收盘是 bar `k`，其后周一、周二均为交易日：日线配合 `next_session_open` 时，
`E(k)` 为周一开盘，持有一个 bar 的批次在周二开盘 `E(k + 1)` 到期。遇到休市由日历跳过，
不按自然日相加，也不从周五收盘再计固定 24 小时。

### 6.3 求值触发不等于交易调仓

根求值节拍固定为每个闭合的有效 `clock.bar`，每个 bar 对应一个逻辑期。
组件 `schedule` 只控制该期是否更新组件选择，不控制根决策或发布节拍。
即使全部 ranked 组件本期均无新选择且没有择时，只要仍可合法合成目标，也保存并发布新 FULL。
示例中是每小时产生一个新目标、每 24 小时分别更新各 offset，而不是每 24 小时才发布一次。

相关 View ready 事件使某个决策网格具备可计算条件；时钟可唤醒固定目标、到期检查和
无新因子依赖的任务。外部事件不能直接携带任意买卖命令绕过 DSL；需要它影响策略时，
先作为已声明、带版本和时点的数据输入进入同一计算链路。

不在选择日程时，已有基础目标仍需参与组合，择时也可在新的基础 bar 上调整暴露。
因此不能像旧版一样在发现“不是选取周期”后直接忽略整个 Runner。

`on_change`、`scheduled` 不再作为 Strategy 的交易调仓模式。Strategy 只定义计算时机；
Trade 独立决定按目标变化、定时或实际仓位偏离程度执行。价格变化既不是唯一触发源，
也不意味着 Strategy 应逐笔行情重新选取。

### 6.4 严格读取与失败分类

Storage 的 ready 表示 View 可读，不保证某个 Strategy 的依赖全齐。
Collector/Factor 判定并上报 marker，Storage 在结果可读后通过 outbox 发布事件。
因子结果仍以 `ViewFactorPeriodReady` 为可读依据，不以 Factor 内部计算完成日志替代。

`ReadinessChecker` 无状态地验证本次任务的输入闭包。没有到期选择任务时不要求无关评分列，
但已有理论目标的择时与退出判断所需输入仍必须齐备。任一必要组件输入不全时，
整次决策不提交；不能只发布其他组件，导致 FULL 意外清掉未成功组件。

| 状态 | 行为 |
| --- | --- |
| View 未完成、Storage/SQLite 暂时不可用 | 有界延迟重试，不推进理论状态 |
| View 可读但必要行/列缺失、非有限数、类型错误 | 记录终态失败并 ACK；等待新的有效输入版本 |
| 读取代际已被更新 | 记录 superseded 并 ACK；等待新 ready 或显式重算 |
| 数据完整且明确空选 | 正常计算，必要时输出空 FULL；不是失败 |
| 旧周期晚到或目标已经过期 | 记录原因并 ACK，不倒灌历史目标 |
| 不可恢复的协议/配置错误 | 终态记录并隔离，不让 broker 无限重试 |

输入/readiness 重试必须有次数或事件有效期上限；到达目标有效期后终止该次输入事件处理，不能让缺失旧周期
永久阻塞后续周期。新事件可再次检查同一周期，但仍受代际、输入完整性与目标有效期约束。
多 Runner 共用事件时，分别记录终态进度；只有相关 Runner 均完成处理才标记整条 inbox。

一次输入读取必须冻结 Source/Result View 的 active index ID 和 revision，后续分页携带
对应的 expected 值。发生索引切换或原地修订时不能拼接两个版本。因子事件 provenance、
结果行的 source hash 与编译依赖必须一致；不允许静默截断、多序列重复或旧因子行混入。

观测时间不得晚于 `as_of`，输入必须在 `information_cutoff` 前已经可获得。
尤其不能将事后修订的市场属性、次日停牌/涨停信息伪装为当时已知信息。
若底层不提供历史版本，本框架只保证本次冻结读取的一致性，不宣称可精确重建任意历史时点。

## 7. 组件计算语义

### 7.1 Ranked 流水线

```text
解析准入池与输入
  -> 前置过滤，得到 candidates
  -> 按 score.scope 在 pool 或 candidates 上计算分数
  -> 在 candidates 中稳定排序并选择
  -> 分配本批次无量纲 base_allocation
  -> 后置过滤
  -> 更新 replace 基础目标或对应 cohort
  -> 对当前有效基础目标应用择时
```

`score.scope: pool` 使用前滤之前冻结的池，即使实现先执行前滤也不能改变排名样本；
`candidates` 使用前滤后的集合。两者明确覆盖参考框架不同的评分顺序。

`rank_weighted` 对每个输入使用 `method=min` 排名，再按正数权重加权求和。
评分权重在评分内部归一化，与组件资金预算无关。`prefer: high` 表示值越高越优，
`low` 表示越低越优；两者都将更优值映射为更小名次。最终按 `(score, instrument_id)`
升序排序，空头不会自动翻转该排序含义。

### 7.2 条件表达式

条件使用结构化 `all`、`any`、`not`，不接受字符串 `eval`、用户函数或隐式类型转换。
一个条件节点只能是一个逻辑运算或一个叶子比较。

```yaml
all:
  - {input: liquidity, op: gt, value: "0"}
  - any:
      - {input: momentum, op: gte, value: "0.2"}
      - {input: risk, op: lt, value: "0.1"}
```

`risk` 等被引用输入必须在定义中声明并绑定。比较支持 `eq`、`ne`、`lt`、`lte`、`gt`、`gte`；
布尔和字符串只允许相等/不等比较。缺失值不是 false，非有限数也不能参与比较。
空 `all` 为 true，空 `any` 为 false，未配置过滤等同于空 `all`。

数值叶子可选 `measure: value | rank | percentile`，默认 `value`。
排名和百分位必须额外声明 `scope` 与 `prefer`：前滤只允许 `pool`；后滤允许
`pool`、`candidates`、`selected`。所有同阶段条件使用同一份冻结样本，不能逐条件缩池。
`selected` 是该组件后滤之前的选中集合，不包含其他组件或另一方向。
本版 entry/exit 条件只允许 `measure: value`，不提供隐含的 held 排名作用域。
entry 条件作用于准入池候选，exit 条件逐项作用于理论持仓；所需输入缺失仍使整次决策失败。

统计名次使用 `method=min`，百分位定义为 `(rank - 1) / (N - 1)`，单元素集合为 0。
它表示按 `prefer` 排列后的相对位置，0 最优。该统计百分位不同于下面按排序序号切片的选择规则。

### 7.3 选择与分配

| `select.mode` | 语义 |
| --- | --- |
| `count` | 稳定排序后取前 `value` 个，`value` 为正整数 |
| `fraction` | 取 `floor(N * value)` 个，`value` 在 `(0, 1]`；可配置非负 `min_count`，默认 0 |
| `rank_range` | 按稳定排序序号截取 `[start, end]`，从 1 开始，双端包含 |
| `percentile_range` | 截取序号 `floor(N * start) + 1` 至 `floor(N * end)`，`0 <= start < end <= 1` |
| `all` | 选择全部候选，不提供 `value` |

这里 `N` 是前滤后的候选数量，序号不是共享的统计名次。`ties: instrument_id` 是本版唯一
支持的最终并列策略；未知值拒绝编译。`fraction` 不隐含“至少选一个”。
`insufficient` 支持 `take_available`（默认）和 `skip_decision`；后者使整个 Runner 本次
决策跳过，不产生部分组件输出。完全空的合法池在 `take_available` 下得到空选择。

候选不足按 mode 定义：`count` 为 `N < value`；`rank_range` 为 `N < end`；
`fraction` 先计算 `K = max(floor(N * value), min_count)`，仅当 `N < K` 才不足。
比例计算出 0 且 `min_count = 0` 是合法空选，不是不足。`all` 和合法的百分位区间不产生不足。
`take_available` 对数量取 `min(N, K)`，对名次区间取 `[start, end]` 与 `[1, N]` 的交集；
交集为空就是空选择，不从更前面的名次补足。百分位区间计算出空切片时也得到合法空选择。

`ranked` 本版基础分配采用 `allocation.method: equal`：实际选中 M 个时，各自的
`base_allocation = 1/M`，M 为零时为空。份额此时不含组件预算或批次预算。
后滤默认 `refill: false, reweight: false`，只删除对应份额，幸存份额不变。
`reweight: true` 明确表示对幸存标的重新分配和为 1 的基础份额；无人幸存时仍为空。
本版不支持 `refill: true`，编译时拒绝，避免未定义的候选递补与后滤排名相互影响。

### 7.4 Fixed

`fixed.weights` 的键为规范标的 ID，值就是非负的 `base_allocation`，总和必须等于 1。
方向、预算和择时只在合成 `component_contribution` 时应用，不提前乘入基础状态。不自动归一化错误的固定份额；
需要保留预算时降低 `budget`，需要条件暴露时使用择时。

固定组件不虚构选取日程或 Factor 依赖。每个有效基础 bar 都可重新产生完整决策；
若配置了择时，则等待对应择时输入。现货标的不允许放入 short 组件。

### 7.5 Entry/Exit

该组件维护的是“按规则应持有的标的”，不是交易账户真实持仓。

```yaml
kind: entry_exit
side: short
budget: "0.20"
universe: {markets: [perpetual], quote_assets: [USDT], min_history_bars: 168}
schedule: {every_bars: 1, offsets: [0]}
holding: {mode: until_exit, max_bars: 24, cooldown_bars: 2}
score:
  method: rank_weighted
  scope: pool
  factors: [{input: momentum, prefer: low, weight: "1"}]
capacity: {mode: count, value: 5}
entry: {all: [{input: momentum, op: lt, value: "0"}]}
exit: {any: [{input: momentum, op: gt, value: "0.1"}]}
allocation: {method: equal_slots}
```

以上是嵌入 `components` 的片段，输入、时钟与完整目标策略由根定义提供。
执行顺序固定为：检查退出/到期 → 保留未退出项 → 在未持有、非冷却候选中按分数补空位。
本版仅支持 `capacity.mode: count`，且不叠加 cohorts；不配置 ranked 的后滤。
`score.scope: pool` 使用准入池；`candidates` 使用满足 entry 条件、未持有且不在冷却期的
可补位集合。退出项仍不能在同一 bar 重新进入该集合。

每个位置的 `base_allocation = 1 / capacity`，合成贡献再乘 budget；只持有 3 个而容量为 5 时使用 3/5 预算，
不自动把存量标的补满仓。进入时记下基础 bar 编号；年龄按日历经过的 bar 计算，
不是求值次数。年龄达到 `max_bars` 时退出。

标的在 bar `k` 退出、冷却长度为 `c` 时，最早在 `k + c + 1` 再次进入；
即使 `c = 0` 也不在同一 bar 退出后重入。缺失数据使整次决策失败，不能把缺失当退出。
跳过的周期不虚构补仓；下次成功求值按真实经过的 bar 更新年龄和到期判断。

### 7.6 择时

择时是对基础目标的暴露乘数，不是直接下单动作：

- 根 `timing.portfolio`：整个策略目标的标量乘数。
- 组件 `timing.component`：该组件所有当前有效基础目标的标量乘数。
- 组件 `timing.instrument`：逐标的乘数，作用于该组件已有理论目标。

配置格式均为 `{input: alias}`。标量择时要求 `scope: portfolio`，逐标的择时要求
`scope: instrument`；值必须处于 `[0, 1]`，越界失败，不静默截断。未配置的乘数为 1。
配置后输入缺失则本次决策失败，不默认放行或清零。

择时按基础 bar 求值，不必等到下一选取周期。它不重做选取、不修改 entry/exit 进入时点，
也不将上一次缩放后的权重再次累乘。每次都从仍有效的基础目标重新计算。

## 8. 理论状态与目标合成

### 8.1 状态边界

```text
TheoryState
  activation_id
  components
    replace             最近一次有效选择的 base_allocation
    cohorts             offset、建立 bar、到期 bar、base_allocation
    entry_exit          理论入选项、进入 bar、占用份额、冷却截止 bar
```

不保存实际成交量、真实持仓数量、订单编号或 Trade 回执。
理论状态只由定义、冻结输入和之前的理论状态推导，可以随成功决策一起审计。
状态保存无量纲份额，不保存已乘预算或择时后的贡献；预算只在下一节的合成公式中乘一次。

`replace` 在下次成功选择时替换基础目标，择时归零不删除基础目标。
`cohorts` 每个 offset 独占 `budget / offset_count` 预算，批次有效区间为
`[effective_at, expiry_at)`；旧批次到期后不参与组合，同一 offset 的新批次不得重复建立。
启动时未建立批次的预算留空，不自动补满，也不凭空构造过去的选择。

数据失败不推进状态、不发布新目标、不延长上次目标的有效期。恢复时按当前 bar 清理已到期
批次，但不回填缺失周期的虚构批次。此前投递目标在缺数期间如何处理由 Trade 的过期政策决定。

### 8.2 合成规则

所有预算是相对于该 Runner 对应资金单元的绝对总敞口比例，不是需要归一化的相对分数。
组件预算必须非负；总预算不得超过显式 `limits.max_gross_budget`，省略时上限为 1。
需要超过 1 的理论总预算时必须显式提高上限；Trade 仍独立执行实际风控。

```text
component_contribution(i)
  = direction_sign
    * component_budget
    * batch_share
    * base_allocation(i)
    * component_exposure
    * instrument_exposure(i)

target_weight(i)
  = portfolio_exposure * sum(all active contributions for i)
```

`replace` 和 `fixed` 的 `batch_share` 为 1，cohorts 为 `1 / offset_count`。
entry_exit 的 `base_allocation` 为 `1 / capacity`。后滤删除的份额、尚未建立的批次和
择时缩减的预算都不自动转移给其他标的或组件。

`compose.method: sum`、`netting: instrument_id` 是本版固定规则。同一规范标的上的有符号
目标相加，零净权重可从列表删除。现货和合约是不同 instrument，不能按基础币名抵消。
现货不允许负权重，编译和运行都应检查；组合合成不绕过这条约束。

`gross = sum(abs(net_target_weight))`、`net = sum(net_target_weight)`。
净额后的 gross 可能小于原始组件总预算，必须保留组件贡献用于归因。
不对最终目标强制归一到 1；衍生品的未使用名义预算不等于账户可用现金或保证金。

## 9. PositionTargets 与异步契约

```text
PositionTargets
  target_id
  decision_id
  runner_id
  activation_id
  strategy_id + revision
  compiled_hash
  delivery_binding_id + binding_generation
  capital_scope_id
  command_sequence
  mode = FULL
  as_of
  effective_at
  valid_until
  targets[]: InstrumentTarget
    instrument_id
    target_weight
```

权重采用规范十进制字符串；重复 instrument 必须在发布前合并，列表按 ID 排序。
`FULL` 只覆盖绑定资金单元，不覆盖整个交易账户。未列出的旧标的目标为零，
明确成功的空列表表示该资金单元完整零目标，不能用空列表表达输入失败。

每个新的有效决策保存 Result 并投递 FULL，包括“新周期但权重完全相同”的情况。
不再输出 `hold | rebalance` 来替 Trade 判断是否需要交易。
同一决策因消息重投再次到达，则返回原结果，不增加 sequence，也不新增 outbox。

Trade 对重复 `target_id` 校验请求内容一致性，并独立管理接收和执行幂等。
Trade 必须检查投递绑定代次、单调 sequence、生效区间和资金单元，拒绝过期绑定、旧目标
倒灌及同 ID 不同内容；收到未来生效的目标也不得提前执行。
当前有效目标与待生效目标不能仅按“最后收到的一条”混用。

权重如何根据权益和价格换算数量、何时重新换算、如何保存换算或执行回执，均属于 Trade
的独立设计。Strategy 不要求“同一目标永远只换算一次数量”，也不要求消费该回执。
当前 Trade 的 `TargetReceipt` 可保留为实现事实，但不是 Strategy 推进状态的依据。

本文固定的是领域载荷。现有权重消息若缺少本契约所需的时间、绑定或版本字段，
后续实施必须同步升级生产端、消费端和协议验收，不能假定当前消息已经支持新版语义。
不得复用 quantity 字段表示 weight，也不得只改消息名称而保留旧 hold 语义。

## 10. 幂等、重算与持久化

### 10.1 纯计算内核

```text
Evaluate(CompiledStrategy, EvaluationInput, PreviousTheoryState)
  -> PositionTargetsDraft, NextTheoryState, Explanation
```

内核不访问网络、数据库、账户或进程内时钟；所需时间来自输入的日历 bar 和冻结上下文。
相同定义、输入、前态得到相同结果。Live 与 Paper 使用相同内核，差异只在 Trade。

### 10.2 决策身份与修订

决策逻辑期为 `(runner_id, activation_id, strategy_revision, as_of)`。
结果另带唯一 `decision_id`、`input_hash`、`base_state_hash`、`compiled_hash` 和修订关系。

`input_hash` 覆盖实际参与语义的规范输入值、池成员、日历及因子版本；原始事件 ID
只作来源记录，不改变同一内容的求值身份。View 索引代际和读取 revision 仍需记录并校验，
但不能用无关行的物理修订代替输入内容是否变化的判断。

- 同一逻辑期、相同输入和同一基准前态：返回已有结果，零状态推进。
- 当前最新逻辑期的输入修订：从该期开始前的同一基准前态重算，产生新的不可变 Result 和 FULL。
- 已有更晚成功决策后收到旧期修订：仅记录 late/superseded，不回滚在线状态，不串联重算后续交易目标。
- 未经历的中间周期不自动补算；严格历史重放属于独立研究能力，不是在线 Runner 的隐式行为。

同周期重算不能把本期已经产出的后态再当作前态，否则会重复建立 cohort、重复进入、
重复计龄或重复冷却。每个成功 Result 必须保存可用于本期修订的基准前态。

### 10.3 最小持久化模型

| 表 | 职责 |
| --- | --- |
| `t_strategies` | 不可变 StrategyDef 及版本 |
| `t_strategy_runners` | 输入/投递绑定、编译制品、启用身份、当前结果指针和单调 sequence |
| `t_strategy_results` | 不可变成功结果、输入身份、基准前态、后态、完整目标和解释 |
| `t_strategy_attempts` | 按事件/Runner 记录跳过、失败、过期、无变化重投等处理事实 |
| `t_strategy_inbox` | broker 消息整体处理状态与去重 |
| `t_strategy_outbox` | 同一 target 的可靠发布与传输重试 |

理论状态可直接存为 Result 的结构化字段，由 Runner 当前结果指针定位，不必先增加
一套独立的批次调度服务或逐组件数据库。`last_error` 只是管理界面摘要，不能代替历史失败记录。

一次新成功决策在同一 SQLite 事务中完成：

1. 重读 Runner 启用身份、编译 hash、最新逻辑期和基准前态，拒绝已失效计算。
2. 保存不可变 Result 及前后理论状态。
3. 更新 Runner 当前结果指针和持久单调 `command_sequence`。
4. 为执行型 Runner 保存对应 target 的 outbox；观察型 Runner 只保存结果。
5. 记录本 Runner 的事件处理结果，并在所有相关 Runner 终态时完成 inbox。

失败则整体回滚。输入失败只保存 attempt，不改变当前理论状态、目标、sequence 或 outbox。
观察型 Runner 不产生 Trade 消息，但使用同样的计算、状态和幂等语义。

Runner 内串行计算即可，不引入 worker lease 或分布式锁。outbox 在确认丢失时可重复发布，
但 `target_id` 和内容保持不变。到 `valid_until` 仍未获得 broker 确认时，将该 outbox 标为
`EXPIRED` 并停止重试，保留历史 Result 和传输记录，不修改目标时间或生成替代目标。
`EXPIRED` 只表示本地不再投递；若先前确认丢失，不据此断言 Trade 从未收到消息。
broker 去重不替代本地事务，也不替代 Trade 的消费幂等。sequence 允许存在过期目标造成的空缺，
Trade 检查单调性而不是等待每个连续编号。

停用后重新启用采用新的 `activation_id`，默认重新建立理论状态，不静默恢复旧目标。
历史结果不删除，sequence 不重置；投递绑定代次负责隔离已经失效的旧消息。
自动续接旧理论状态不属于首阶段能力，不能在更换定义或数据绑定后隐式沿用。

### 10.4 审计与重放边界

Result 保存池成员、排除原因、筛选数量、排序结果、基础分配、后滤释放预算、各批次贡献、
择时乘数、净额合成和输入 provenance。失败 attempt 保存缺失项与终态原因。
解释字段不参与权重决策，但不能省略决定结果的规则、输入版本和理论前态身份。

默认不落盘完整行情输入快照或内容寻址的 MarketFrame 制品。
因此“幂等恢复”指已保存结果的重投、理论状态恢复及具备相应输入版本时的确定性重算，
不等于保证从可变 View 重建任意历史行情。精确历史重放需要独立的版本化数据保障。

## 11. 可观测性、安全与验收

### 11.1 可观测性

Strategy 指标至少区分：计算成功、输入失败、过期跳过、幂等重投、目标发布待处理和发布确认。
另记录组件池规模、入选数、活跃批次数、理论总预算、净额 gross/net 与择时暴露。
不得用“published”指标代表交易完成。

日志关联字段包括 `space_id`、`runner_id`、`activation_id`、定义 revision、
`as_of`、`decision_id`、`target_id`、输入 hash 和 trace ID。
管理界面分别展示理论目标与 Trade 的实际执行情况，不用一条 Strategy 状态掩盖二者差异。

### 11.2 安全与确定性

- 严格 schema 校验；版本、未知字段、重复键、算子和不支持能力都在启用前明确拒绝。
- decimal、时间、规范标的 ID 和排序键统一规范化，拒绝 NaN/Inf 和不合法范围。
- 不允许随机排序、依赖 map 遍历顺序、任意脚本或运行时动态拉取未声明数据。
- 单组件求值不修改其他组件前态；组合层只合成声明的目标贡献。
- 输入鉴权沿用 Storage Metadata 与 DataView 的独立身份，不混用 secret，
  不把凭据写入定义、编译制品、日志或前端响应。
- 目标签名、消息身份及投递授权使用现有基础设施，不能由用户 YAML 自行声明权限。

### 11.3 必须覆盖的验收场景

| 类别 | 验收重点 |
| --- | --- |
| 定义与命名 | StrategyDef 发布不可变；物理绑定不污染定义；旧 v2 和未知能力明确拒绝 |
| 排名与过滤 | pool/candidates 差异；同分稳定截取；后滤留空与显式 reweight；不跨组件排名 |
| 选择 | 固定数量、比例取整/最小数、区间边界、空池和候选不足政策 |
| 批次 | offset 均分预算；未建立预算留空；到期移除；同标的合成；E(k)/次交易日开盘与有效期截短 |
| 择时 | 根/组件/标的作用域；非选取日调整；缺失不当作 0 或 1；不重复累乘 |
| Entry/Exit | 先退后进；容量份额不自动补满；年龄按 bar；冷却边界；缺数不退出 |
| 完整性 | 当前池与理论持仓的数据闭包；任一必要组件失败不产生部分 FULL；失败不清仓 |
| 输入版本 | 多 venue 历史不串用；索引切换/修订不混读；Factor provenance 一致；无未来信息 |
| 输出边界 | 新周期同权重仍发布；合法空 FULL；仅覆盖绑定资金单元；Strategy 不依赖执行回执 |
| 幂等与修订 | 重投零副作用；同周期重算使用原前态；旧期晚到不回滚；失败事务不推进状态 |
| 生命周期 | 新启用身份不复活旧目标；sequence 不重置；旧绑定消息失效；停计算不暗含清仓 |
| 传输 | Result/状态/outbox 原子提交；确认丢失重投同 target；过期停止投递但不推断未送达；乱序旧目标拒绝 |

## 12. 能力边界与后续落地

下表用于区分目标架构和实施能力，不是对旧执行计划的补丁，也不表示相关能力已经交付。

| 能力层 | 范围 | 启用条件 |
| --- | --- | --- |
| 基础目标 DSL | StrategyDef、绑定编译、ranked/fixed、多组件、明确预算和 FULL 输出 | schema、算子、输入与跨模块消息契约统一通过验收 |
| 理论批次与择时 | 日历、cohorts、基础目标保存、组件/标的暴露 | 理论状态事务、同周期修订和日历边界通过验收 |
| 理论进出场 | entry_exit、容量、期限、冷却 | 已持有标的数据闭包、缺数政策及确定性状态测试通过验收 |
| 高级输入与组合 | 多 View/频率、截面历史、理论绩效驱动预算 | 相应 Factor/Storage/研究输入能力可证明存在，另行细化其专属 DSL |

同一阶段可先支持有限算子和数据绑定，但必须由编译器明确拒绝未实现部分。
不以“配置可解析”代替“策略语义可执行”，也不以文档存在代替本地测试或真实链路验收。

相对上一版的关键变化：

| 上一版基线 | 本文基线 |
| --- | --- |
| `coin_selection` 固定长短两侧配置 | `StrategyDef` + 单边组件集合 |
| 一个 Runner 一份池和一个选择日程 | 一个 Runner 一份完整策略，各组件可有自己的池和日程 |
| 排名总在前滤之前 | 排名样本集显式声明 |
| 后滤后重新等权 | 先分配后滤，默认保留被剔除预算 |
| 无状态单期权重计算 | 显式输入理论前态的确定性计算 |
| 相同权重 hold、不发事件 | 每个新有效决策发 FULL；仅同一决策重投幂等 |
| Strategy 文档规定 Trade 换算与回执细节 | Strategy 只规定目标契约，Trade 独立设计执行 |
| 一个 Result View 被当成永久语言限制 | 单 View 是当前可实现能力限制，不是 DSL 永久边界 |
| 旧因子覆盖、旧表归档等部署细节混入框架 | 迁移和部署由后续实施计划依据当前代码单独处理 |

后续先按本文更新实施计划与能力清单，再进入代码修改。其他模块的命名、Trade 协议、
数据库变更及运行验收均须在对应实施范围内明确处理，不在本次文档修订中执行。
