# MooX 策略执行框架设计

## 文档状态

本文是 Strategy 模块的目标设计，修订日期为 2026-09-06，汇总截至本轮的讨论结论，
替代《选币策略执行框架设计》。这里的“执行”指计算策略结果，不指执行订单。
本文描述目标合同及当前实现边界；实现仍以实施计划和测试结果为准，未通过验证的能力不得视为已上线。

[2026-08-29 实施计划](superpowers/plans/2026-08-29-moox-coin-selection-strategy.md)
已同步本文的 DSL、状态、触发和验收基线。当前分支已落地核心实现并完成本地验证；Strategy 已在用户授权后
发布到 `moox.toml` 的 `strategy_host`（`106.53.107.122:/data/moox/prod`），发布版本和健康读回证据见实施计划。
这只证明服务已启动，不代表真实交易或实际持仓已经达标。

设计面向个人量化系统：固定处理流程、少量配置、单进程、SQLite、JetStream 即可。
不引入复杂版本管理、通用工作流、分布式锁或全局 exactly-once。

核心决策：

- Strategy 只输出目标持仓权重，并通过异步链路发送给 Trade。
- Trade 独立完成账户权益读取、数量换算、实际持仓比较、下单、风控与失败恢复。
- 一个策略包含多套 `rules`，规则结果在同一实例内合成为一份完整目标。
- 固定流程是标的池、前筛、评分、选择、可选进出场、权重分配、后筛、目标合成。
- 定时触发和事件触发任选其一或同时配置；二者使用相同的周期与去重规则。
- DSL 只保留一份 `dsl_yaml`，没有定义版本、定义 hash 或持久化编译制品。
- 名称由 DSL 的 `name` 派生到 `strategy_name`，便于列表、搜索与排序，不形成第二个编辑来源。
- 保留定义与实例分离；同一份定义可由多个实例独立绑定、启停和计算。
- 只保留定义、实例、结果三张表，结果同时保存冻结消息和投递状态，不另建 outbox 表。
- `RuleState` 只保存计算下一期所需的理论状态，不保存订单、成交或真实持仓。
- 缺数或计算失败不等于空持仓；新周期即使权重不变，也产生新的完整目标。

## 1. 职责边界

### 1.1 模块分工

```text
Collector / Factor -> 数据和因子结果
Storage            -> 可读数据与 View ready 事件
Strategy           -> 按定义计算目标权重 -> Result（后态、冻结消息、投递状态）
Trade              -> 接收目标 -> 换算数量 -> 独立执行
Monitor / 管理界面 -> 分别展示策略计算、消息投递和交易执行状态
```

Strategy 不读取账户权益、余额、实际持仓、订单或成交，不自行选择交易账户、调用交易所，
也不处理最小下单量、价格精度、合约乘数、拆单、撤单和补单。
本文中的“持仓”除非注明，均指策略计算出的理论持仓；币数、股数等实际目标数量由 Trade 换算。

Trade 可以异步发布接受、拒绝、部分成交和执行失败通知，供 Monitor 与管理界面展示。
这些通知不作为 Strategy 的决策输入，不驱动其重新选取、调整理论状态或重试交易。
Strategy 的异步投递重试只负责消息传输，不构成交易反馈闭环。

策略结果已计算、消息获得 broker 确认、Trade 已接收、订单已成交是不同状态。
不能用“已发布”表示已经成交或实际持仓已经达标。

### 1.2 运行归属

一个执行型实例对应一个 `logical_account_id`，代表一个由 Trade 管理的资金单元。
同一资金单元同一时刻只有一个有效的完整目标发布者；多套规则必须先在实例内合成，
不能让多个实例分别发布完整快照、相互覆盖。

实例未绑定资金单元时为观察模式：照常计算、保存结果，但不发布 Trade 消息。
停用实例不等于撤单或清仓；这些操作由 Trade 的独立管理入口显式完成。

## 2. 领域对象与最小状态

### 2.1 术语

| 名称 | 含义 |
| --- | --- |
| `StrategyDef` | 策略定义，持久化用户编写的 DSL |
| `StrategyRule` | `rules` 下的一套独立计算规则，不是另一个实例 |
| `InstrumentPool` | 本期事先确定的计算标的集合 |
| `StrategyInstance` | 将策略定义、输入绑定和投递目的地连接起来的运行实例 |
| `EvaluationInput` | 本期冻结的标的、行情、因子及时间上下文 |
| `RuleState` | 下一期计算所需的理论入选状态或持有批次 |
| `base_weights` | 规则内部尚未乘资金比例和方向的基础份额，通常只是中间值 |
| `rule_weights` | 一套规则经过权重分配和后筛后，对各标的贡献的有符号权重 |
| `StrategyResult` | 一次成功决策的历史快照、后态、目标与投递信息 |
| `PositionTargets` | 一个实例对应资金单元的一次完整目标持仓快照 |
| `InstrumentTarget` | 一项 `instrument_id` 与 `target_weight` |

`TheoryState`、`DecisionState` 统一改为 `RuleState`，表示每条规则的计算状态，
不再使用容易混淆的 Theory 命名，也不表示 Trade 的真实持仓。
原 `base_allocation` 改称 `base_weights`；原 `component_contribution` 随 `rules` 命名
统一称为 `rule_weights`，不再另设一个持久化领域对象或数据表。

其他模块按对象含义命名，不做全仓机械替换：可复用定义使用 `xxxDef`；运行绑定使用
`Binding`；调用参数使用 `Request`、`Invocation`；订单意图使用 `OrderIntent`；
参数和配置使用 `Params`、`Config`。只有确实表示“定义”的 `xxxSpec` 才改为 `xxxDef`。
这些是后续命名规则，本轮不修改其他模块代码。

### 2.2 StrategyDef

```text
strategy_id
strategy_name
dsl_yaml
created_at
updated_at
```

DSL 的 `name` 是名称的唯一编辑来源。保存定义时严格解析 DSL，在同一事务中同步写入
`strategy_name` 与 `dsl_yaml`；列表、搜索和排序直接读取 `strategy_name`。
不允许单独修改数据库名称而不改 DSL，创建/更新接口不提供另一个独立的名称参数。
这是一列派生展示数据，不是第二份定义，也不增加版本管理。
删除 `api_version`、定义 revision、`definition_yaml/json/hash`；不改用另一套
`dsl_version`、`dsl_hash` 或发布版本体系。`dsl_yaml` 是定义的唯一权威文本。

修改 DSL 前必须停用所有引用它的实例；编辑与启用操作在控制面串行校验，
不能在检查通过后又并发启用旧定义。修改后重新校验、启用，并重新建立理论状态。
不支持热更新或静默沿用旧规则的状态。历史 Result 的 `snapshot_json` 保存当时的策略 ID 与 `dsl_yaml` 副本即可，
不需要额外的定义版本表。

### 2.3 StrategyInstance

```text
instance_id
strategy_id
space_id
input_bindings_json
logical_account_id    可空，空表示观察模式
enabled
session_id            稳定停用时可空
created_at
updated_at
```

- `instance_id` 标识稳定的策略实例，创建后不因启停或周期计算而改变。
- `input_bindings` 把逻辑字段绑定到行情字段、FactorDef 输出、Binding 和 View，并提供类型；
  持久化列为 `input_bindings_json`，在内存与 API 中仍是结构化绑定。
- 最小绑定 JSON 形状如下（字段可按实际因子补充）：
  `{"source_view_id":"prices-1h","frequency":"1h","factors":[{"factor_id":"ma20","binding_id":"b-ma20","result_view_id":"factor-ma20","column_name":"ma20"}]}`。
  `source_view_id` 决定行情池，`factors` 决定要读取的 Factor Result View/列；这些绑定随实例冻结，
  不在每次调度时按同名字段猜测。内置 `spot_symbols`/`all_symbols` UDF 只读取 Storage 提供的标的目录快照。
- `session_id` 标识本次启用的运行会话，不是登录会话、DSL 版本或每次求值的任务 ID。
- `result_id` 标识该会话内某一成功周期的结果，和前两个 ID 分别回答“哪个实例、哪段运行、哪次结果”。
- 删除 `last_result_id`：按 `(instance_id, session_id)` 查询 `bar_end_time` 最大的成功 Result。

绑定频率必须与 DSL 的 `data.bar` 相同（分钟使用小写 `m`）；因子绑定未填写频率时继承该周期。
多个规则可以使用不同的固定标的池或 Factor subject 范围，Storage 只对实际规则/标的组合执行严格
完整性检查，不把无关 Factor 交叉要求到其他标的。Pool UDF 启用前检查注册名称和参数，返回的标的
ID按 Storage 目录中的规范值统一大小写，避免同一标的被重复或误过滤。
- 删除 `command_sequence`：在当前已授权的运行身份内，以 `bar_end_time` 比较目标先后。
  前提是每个闭合 bar 最多成功一次，不支持同 bar 修订或盘中多次输出。

持久化对象由 `StrategyRunner` 改称 `StrategyInstance`，原 `runner_id` 改为 `instance_id`，
原 `run_id` / `activation_id` 改为 `session_id`。代码中实际执行计算的组件仍可叫 Runner，
不把对象重命名扩大为对所有执行器或文件路径的机械替换。
删除定义 revision、`compiled_artifact`、编译 hash 和重复的状态枚举，使用 `enabled` 即可。
启用时严格解析 DSL、绑定输入并编译表达式，将结果保存在内存；重启时重新编译。
正常进程重启恢复原 `session_id` 和该次运行已提交的状态；显式停用后重新启用创建新 `session_id`，
从空规则状态开始，历史结果保留。两种恢复路径不能混为一谈。
`session_id` 可以使用 UUID，只比较是否相同，不依赖数值大小或时间顺序。
规则状态来自该实例当前会话最近成功的 Result，不一定来自上一根 bar；历史清理不得删除该恢复点。
例如实例 I1 首次启用为会话 S1，多个计算结果属于 S1；正常重启仍恢复 S1，完成停用后再启用为 S2。
同一 StrategyDef 的多个实例共享定义，但绑定、会话、规则状态和结果互不共享。

Factor 仍使用 FactorDef 与 Binding，不为策略引入 FactorInstance。
运行期间不得悄悄替换因子公式、参数、输出或数据绑定；影响输入含义的修改也走停用、校验、
重新启用流程。UDF 实现和日历语义变化遵守同样规则。
输入来自哪个源、哪个输出列必须明确，不按同名字段猜测。

### 2.4 运行身份与授权

`session_id` 保留原 `run_generation` 必需的隔离作用，统一启用身份和投递绑定身份，前提是控制面与 Trade
共同使用同一授权身份：`logical_account_id -> (instance_id, session_id)`。
它不是由 DSL 任意填写的权限声明。

稳定停用为 `enabled=false, session_id=NULL`；运行中为 `enabled=true, session_id 非空`。
停用先持久化 false，保留旧 session_id 和目的地，停止本地求值与发布；
确认 Trade 已撤销该身份后才清空 session_id。跨资金单元改绑必须完成旧目的地清理后，才覆盖绑定。
启用从稳定停用状态开始，持久化新 session_id、保持 false，确认 Trade 授权后才设为 true。
同一存活控制操作内部重试复用该身份；对已经 enabled 的重复启用请求幂等返回。

为避免增加 pending_action 或控制流程表，`false + 非空 session_id` 在进程重启后统一视为未完成操作，
只取消和清理对应授权，不自动继续启用。清理完成后由用户重新启用，分配新 session_id。
正常重启的 `true + 非空 session_id` 则先确认 Trade 仍授权相同身份，再恢复该会话的状态与求值；
授权不匹配时保持停止并提示处理，不静默重新抢占。观察模式跳过 Trade 授权步骤。
这里主动放弃“未完成启用在崩溃后自动续作”，以少量字段保持恢复行为明确。

Trade 授权行除 owner 身份外，保留一个不透明的 `auth_fence`，仅用于管理操作 CAS，
不进入 DSL、实例或 PositionTargets，不是定义版本。管理入口原子检查 expected-old 身份及 fence，
再设置 desired 发布者；实际状态转换生成新 fence，不使用跨服务时钟比较。
当前已等于 desired 时幂等成功，被其他发布者占用时拒绝，不做无条件覆盖。
撤销/取消后保留新生成、不可复用的空闲 fence，不重置成初始全空状态；
即使 Claim 尚未到达、账户当前空闲，取消也要推进此检查值，阻止迟到 Claim 恢复已取消运行。
Claim/Rebind 重试必须复用原 expected 值，不能读取新值后继续旧命令；空闲检查值不授权交易。
取消不能撤销其他活动身份；已经空闲且 fence 已改变时旧取消只确认结果，不能把值写回或回退。
控制面不能在撤销失败时宣告清理完成；失败保持停用并提示处理，不引入 Saga 或新的协调服务。
旧会话待发结果、迟到消息和正在计算的旧任务都不能越过 session_id 校验。
撤销发布授权不隐含撤销已挂订单或清仓，已有交易动作仍由 Trade 管理。

## 3. DSL

### 3.1 完整示例

下面仅演示配置结构，不是交易建议。`spot_symbols`、因子字段和标的 ID 都是示例，
启用前必须解析为已注册 UDF、已绑定输入及真实规范标的，不能假定示例已在系统中存在。

```yaml
name: strategy_demo

triggers:
  schedule: {cron: "5 * * * *", timezone: UTC}
  event: {name: ViewFactorPeriodReady}

data: {bar: 1h, calendar: crypto_24x7}

rules:
  momentum_selection:
    pool: {udf: spot_symbols}
    filter_before: "turnover_20 > 1000000"
    score: "0.6 * pct_rank(return_20) + 0.4 * pct_rank(turnover_20)"
    select: {top: 10}
    weight: 0.60
    filter_after: "return_20 > 0"

  ma_signal:
    pool: [BTC-USDT-SPOT, ETH-USDT-SPOT]
    signals:
      entry: "bars[0].ma20 > bars[0].close"
      exit: "bars[0].ma20 < bars[0].close"
    weight_each: 0.10
```

`momentum_selection` 和 `ma_signal` 是用户自定义的规则名，不是框架关键字。
名称只用于识别和解释规则，不决定算法。一个策略可以只有一条规则。
示例最多分配 60% 给排序规则，每个信号持仓分配 10%；两个信号均成立时最多合计 80%。
余下比例不自动补给其他规则。

### 3.2 字段规则

根字段只有 `name`、`triggers`、`data`、`rules`，均必填。`rules` 至少包含一条规则。
`triggers.schedule` 与 `triggers.event` 至少配置一项；`data` 明确给出基础 bar 与日历。

| 规则字段 | 含义与默认行为 |
| --- | --- |
| `pool` | 必填，固定标的列表或返回标的集合的 UDF |
| `filter_before` | 评分前初筛，布尔表达式；不写表示不过滤 |
| `score` | 数值评分表达式；不需要排序时可省略 |
| `select` | 可选的分数条件及 `top` / `tail` 选取，配置时必须有 `score` |
| `signals` | 可选的理论进出场规则，配置时同时提供 `entry` 和 `exit` |
| `weight` | 后筛前，在拟持有集合中等分的规则总资金比例 |
| `weight_each` | 每个拟持有标的的资金比例，与 `weight` 二选一且必须提供一项 |
| `side` | `long` 或 `short`，省略默认 `long` |
| `filter_after` | 基础权重分配后终筛，布尔表达式；不写表示不过滤 |
| `holding` | 可选的分批持有配置；普通排序、固定配置和信号规则均不必填写 |

不再使用 `components`、`universe`、`pre_filter`、`post_filter`、`bottom`。
不再声明根或规则 `kind`，也不保留 `ranked/fixed/entry_exit` 三套互斥结构。
删除 `position`、`allocation.method`、`budget` 包装，不要求用户反复声明等权、做多和求和。
不提供 `target`、`compose`、`limits`、三层 `timing` 等额外 DSL 配置。

YAML 字段顺序不改变执行顺序。未知字段、重复键、类型错误和未实现能力在启用前拒绝，
不能忽略旧字段后悄悄执行另一种含义。

### 3.3 固定规则与做空

不需要筛选或信号时，直接列出池和比例即可，不需要 `kind: fixed`：

```yaml
rules:
  fixed_targets:
    pool: [BTC-USDT-SPOT, ETH-USDT-SPOT]
    weight: 0.20
```

该片段每次有效求值都输出两个各占 10% 的目标，不是只运行一次。
需要每个标的固定为 10% 时写 `weight_each: 0.10`；它不是固定币数或股数。
做空规则显式填写 `side: short`，评分和 `top/tail` 含义不自动反转。
现货不允许做空，不能通过其他规则净额抵消来绕过检查。

## 4. 固定处理流程

```text
定时 / 事件通知
  -> 确定实例、session_id 和 bar_end_time，检查周期是否已成功或过时
  -> 加载最近成功结果的 RuleState
  -> 解析各规则 pool，确定本期计算范围
  -> 加载必要行情、因子及历史，冻结本期输入
  -> filter_before，得到初筛集合
  -> 批量标准化并计算 score（可选）
  -> select（可选）
  -> 处理 signals，得到拟持有集合（可选）
  -> 分配基础份额和资金比例
  -> filter_after，只剔除，不补位、不重新分配
  -> 更新理论状态，合成并校验完整 PositionTargets
  -> 同一事务保存 Result、后态、冻结消息及初始投递状态
  -> 异步发布给 Trade
```

这是固定 Go 流水线，不开放步骤重排、规则依赖图或跨规则读取“本次结果”。
各规则独立计算，任一必要规则失败，整次不提交，不能把部分规则当作完整目标发布。
有持有批次时只在对应时点创建新批次，但每次有效触发都清理到期批次并合成当前目标。
有信号时，已有理论持仓的退出判断不依赖它能否通过本期初筛或进入前 N 名。

### 4.1 标的池与前筛

`pool` 是事先可以确定的计算标的集合，统一返回规范 `instrument_id` 集合。
它与基于本期行情、因子结果进行初步筛选的 `filter_before` 是两个阶段。

```yaml
pool:
  udf: spot_symbols
  params: {quote_asset: USDT}
filter_before: "turnover_20 > 1000000 && close > 0"
```

固定列表和 UDF 均输出无重复、按 ID 稳定排序的集合。固定列表允许显式为空；
重复配置、未知标的或 UDF 返回非法 ID 是错误，不静默忽略。
Pool UDF 根据预加载的标的目录、明确的参数和时点确定范围，不依赖尚待该池计算的本期因子，
避免“先算因子才能知道要算哪些标的”的循环。数值筛选放在 `filter_before`。

池可以作为上游因子计算范围的依据，但 Strategy 不因此接管 Factor 计算。
Strategy 从已绑定数据中读取结果，未准备好的必需输入按第 8 节处理。
当前池只控制新进入的资格；信号规则的旧理论持仓即使移出池，仍加载退出和后筛所需数据。

### 4.2 输入与表达式

逻辑字段的类型来自实例输入绑定，不在 DSL 中重复声明一份 `inputs` schema。
首版只支持数值字段，以及框架明确提供的字符串元信息 `instrument_id`；布尔和其他字符串
字段暂不作为可绑定输入，不做任意隐式类型转换。`score` 是选择阶段的保留计算字段，
不能再作为同名物理输入别名。

`filter_before`、`filter_after`、`select.where`、`signals.entry/exit` 必须返回布尔值，
`score` 必须返回有限数值。
后筛可以读取该标的的原始输入；普通当期排序规则也可读取本次 `score`。
配置 `signals` 时，entry、exit 和后筛均不得引用 `score`，启用时直接拒绝，
避免给不在评分集合中的旧持仓伪造分数。score 在信号规则中只用于新进入资格的选择。
分批规则的后筛只在批次建立时执行，可以读取当批分数。

不覆盖原始字段：例如 `return_20` 始终是原始收益率，`pct_rank(return_20)` 是独立临时结果。
评分系数不自动归一化，也不与持仓权重混用。

## 5. 评分、标准化与选择

### 5.1 分数来自表达式

`momentum` 只是示例因子名，常指动量，不是框架内置的某个固定算法。
例如由 Factor 提供以下定义的输出：

```text
return_20(t) = close(t) / close(t - 20 个有效 bar) - 1
```

`score: "return_20"` 直接以该收益率评分；价格从 100 涨到 110 得分为 0.10，
从 100 跌到 95 得分为 -0.05。`score: "0.7 * return_20 + 0.3 * return_60"`
则直接执行加权算式。因子如何计算由 Factor 定义，如何组合为分数由 Strategy 定义。
写下因子名字不会自动创建对应的因子或历史数据。

最终分数越高越靠前。不同量纲或尺度的因子需要在组合时显式处理尺度；
不是所有组合都必须标准化，也不由框架偷偷决定何时标准化。

### 5.2 两个内置标准化函数

统计样本固定为本规则、本期、前筛后的完整候选集合，不提供可切换的 `scope`。
它们是截面变换，不是单个标的沿历史时间做滚动统计。

| 函数 | 本版定义 |
| --- | --- |
| `pct_rank(x)` | 原始值升序排列，名次从 1 开始，取平均名次 r，输出 `(r - 1) / (N - 1)` |
| `zscore(x)` | 输出 `(x - 均值) / 总体标准差`，总体方差分母为 N |

`pct_rank` 值越大越接近 1；同值使用同一平均名次，不能用 ID 打散统计名次。
只有一个标的时返回 0.5，全部相同也返回 0.5。`zscore` 标准差为零时返回 0，
其结果不限于 `[0, 1]`，也不是固定落在 `[-3, 3]`。
合法空候选集合直接得到空选择，不执行统计。必要值缺失或出现 NaN/Inf 时失败，不填零。

例如初筛后有三项：

| 标的 | return_20 | turnover_20 | 收益率 pct_rank | 成交额 pct_rank | 0.6 / 0.4 加权分数 |
| --- | --- | --- | --- | --- | --- |
| A | 0.05 | 10000000 | 0 | 1 | 0.4 |
| B | 0.10 | 2000000 | 0.5 | 0 | 0.3 |
| C | 0.15 | 5000000 | 1 | 0.5 | 0.8 |

对应 `0.6 * pct_rank(return_20) + 0.4 * pct_rank(turnover_20)`，排序为 C、A、B。
希望低值更优时，使用 `1 - pct_rank(volatility_20)` 或 `-zscore(volatility_20)`。
排名方法便于比较位置，但不保留绝对差距；zscore 保留差距，但更易受极端值影响。

初版只允许在 `score` 中调用这两个函数，参数只接输入字段名，不支持任意集合参数或嵌套标准化。
启用时识别表达式依赖；每期先对所需列批量计算一次，再让逐标的表达式读取临时结果。
选取、信号和后筛都不改变这次统计样本，也不在逐标的求值时重复扫描整个集合。
无需新增标准化模块、FactorDef 或持久化表。

Factor 已提供的标准化输出可直接当作普通字段使用，但其样本范围必须明确。
“全市场预计算标准化”与“本规则初筛集合标准化”不是同一含义，不能混称。
历史滚动标准化或截面排名的历史差分仍由具备对应历史数据能力的 Factor 提供。

### 5.3 选择

```yaml
select:
  where: "score >= 0.6"
  top: 10
```

`where` 是可选的分数条件，只读取已计算的 `score`，先筛分数，再排序截取。
`top: N` 取前 N 个，`tail: N` 取后 N 个；两者互斥，N 必须是正整数。
固定按 `(score 降序, instrument_id 升序)` 排列，再执行头部或尾部切片。
同分不扩张数量，候选不足取现有数量，空集合合法。

只配置 `where` 时保留全部满足分数条件的标的。省略 `select` 时保留初筛后的全部标的；
可以计算分数用于解释，但不会隐式截取。空的 `select` 配置拒绝，避免没有实际作用的配置。
不再提供数量/比例混用、百分位区间、补足数量或可配置并列处理模式。
评分后的 `where` 不能倒过来改变标准化样本。

## 6. 仓位分配与后筛

### 6.1 两种写法

`weight` 和 `weight_each` 都是相对于实例对应资金单元的绝对比例，不是需要归一化的分数。
用户可以直接填写 YAML 十进制数值，如 `0.60`；权重字段按十进制解析，输出采用规范十进制字符串。
过滤阈值和评分使用有限数值，不能把浮点评分误当作资金数量或订单精度。

| 配置 | 后筛前的分配 |
| --- | --- |
| `weight: 0.60` | 拟持有 M 个时，每个分配 `0.60 / M`；M 为零时为空 |
| `weight_each: 0.10` | 每个拟持有标的分配 0.10，数量变化不使其他标的的比例改变 |

这里的 M 是本次完成选择、进出场判断后的拟持有数量，不是池大小、配置的 N 或本次新进入数量。
信号规则的 M 包括仍保留的旧持仓。`weight` 会在每个新决策中按当期拟持有集合重新等分；
若不希望其他标的进出影响单标的比例，使用 `weight_each`。

基础份额在等分时为 `1/M`，逐标的固定比例时为 1。普通规则只需临时计算这些份额，
无需建立一个专门的 allocation 对象。分批规则的份额需要保留，见第 7.2 节。

上表是数学表达，实际沿用 Strategy 现有 `internal/quant/decimal.go` 的 18 位定点规则：
权重配置最多 18 位小数，超出拒绝；先按后筛前 ID 升序等分总基础份额 1，余数以 `10^-18`
为单位依次补给前项，得到稳定的 base_weights。分批预算也按 offset 数值升序使用相同等分法。
再以规则比例或批次预算乘基础份额，乘法向零截断到 18 位，截断尾差留空，不事后补齐。
方向最后应用，跨规则求和使用定点加法；序列化去小数尾零、不用指数或分数字符串，零输出 `"0"`。
这复用数值工具，不复用旧求值器的后筛后均分顺序，也不表示 Trade 内部已经采用相同 Decimal。
零候选直接为空，不调用除法；其他除零必须作为错误处理，不沿用数值工具的静默返回零行为。

### 6.2 后筛只做剔除

`filter_after` 在基础权重分配后执行，true 保留，false 删除本规则对该标的的份额。
固定为不补位、不重新分配，不增加 `refill` 或 `reweight` 配置开关。

例如 `weight: 0.60`，选中 10 个，各占 6%；后筛剔除 2 个，剩下 8 个仍各占 6%，
规则实际总权重为 48%。不会从第 11 名补入，也不会将剩余标的增加到各占 7.5%。
这取代此前讨论中“在后筛后的最终集合重新等分”的歧义表述。

前筛决定谁参与竞争；后筛决定已经拟持有的标的是否最终保留。
后筛只作用于当前规则，不否决其他规则对同一标的的持仓。
数据缺失或表达式错误不是 false，不得据此删除持仓或发布部分结果。

### 6.3 合成

每条规则按方向生成 `rule_weights`：做多为正，做空为负；相同规范标的的各规则贡献直接相加。
规范 ID 不同的现货、合约不能按基础币名抵消。净额为零的标的可以从最终列表省略。

规则比例必须大于零且不超过 1。第一版固定总分配上限为 1，不支持 DSL 调大上限。
启用时检查所有规则的权重上界之和不超过 1：weight 规则按声明比例预留；weight_each
规则按最大拟持有数量乘单标的比例预留。普通选取的数量上界取固定池长度、top/tail 数量
中可证明的较小值；无法确定上界时改用 weight，不增加动态容量配置。
未用完或后筛释放的预留比例不借给其他规则；分批规则也按整个 weight 预留。
运行时仍在后筛和跨规则净额之前复核实际拟分配绝对权重之和；违规时失败，
不靠后筛、做空抵消、舍入尾差或隐式缩放使非法分配通过。

`weight_each` 不再额外配置规则自身的总额上限，这是相比原 `method: fixed + budget`
的一项明确简化。未使用的份额不转给其他规则，最终目标也不强制归一到 1。
衍生品的名义权重不等于实际保证金占用，Trade 仍独立执行真实账户风控。

## 7. 理论状态与时序规则

### 7.1 Signals

`signals` 表示按条件维护理论持仓，不需要假装所有分数相同再用 TopN 实现时序策略。
配置它时，前筛与选择只决定新进入资格，不强制已有持仓在每期继续进入前 N 名。
因此信号规则中的 `top: N` 不是总持仓容量上限；需要固定单标的比例时使用 `weight_each`，
总比例仍受第 6.3 节检查。
为避免跨期累计后持续超额，第一版 signals 与 weight_each 组合只接受固定列表 pool，
按整个列表长度预留比例，不用本期入选数或 TopN 冒充总容量。动态 UDF 池的信号规则使用 weight。

每期先对已有理论持仓检查 `exit`，保留未退出项，再从本期候选中加入满足 `entry` 的新项。
同一期已经退出的标的不再次进入；新项同时满足 entry 与 exit 时也不进入，退出优先。
随后分配权重，并对所有拟持有项执行后筛，包括池外仍保留的旧理论持仓。

后筛为 false 的项从下一期 RuleState 中移除，不保留一个“输出为零但仍持有”的隐藏状态。
后筛恢复后必须重新满足 entry 才能进入；本期不再循环补位或重新计算信号。

沿用用户给定方向的条件示例：

```yaml
signals:
  entry: "bars[0].ma20 > bars[0].close"
  exit: "bars[0].ma20 < bars[0].close"
```

MA20 高于收盘价时进入，低于收盘价时退出；相等时保持之前的理论状态，首次为空仓。
这是持续条件，不是“刚发生穿越”。如果需要严格穿越，写成：

```yaml
signals:
  entry: "bars[-1].ma20 <= bars[-1].close && bars[0].ma20 > bars[0].close"
  exit: "bars[-1].ma20 >= bars[-1].close && bars[0].ma20 < bars[0].close"
```

`bars[0]` 是本次决策所用的已闭合 bar，`bars[-1]` 是同一交易日历中紧邻的上一根有效 bar。
它们均包含该周期绑定的行情字段和因子值；`ma20` 是已绑定因子，不由 bars 语法自动计算。
这是一套相对周期视图，不是普通数组的负下标；不会把 `-1` 解释为数组最后一个元素。

第一版只接受常量索引 `0` 和 `-1`，拒绝正索引、`-2` 等更长历史和动态索引。
跨期表达式统一显式写出两期索引，不混写 `prev.x` 或裸字段表示当前期；
普通单期评分、过滤仍可使用 `return_20` 等当前期字段简写。
编译器提取偏移和字段依赖，仅引用 `[0]` 时不强制加载上一期；引用 `[-1]` 时必须加载精确相邻周期，
不能用上次事件、上次成功计算、任意最近数据或当前未收盘 bar 替代。
必要历史缺失时跳过整次决策，不删除相关子条件，不把条件默认改成 true，也不输出零目标。
这些信号维护理论状态，Strategy 不等待 Trade 成交确认后才记录进入。

### 7.2 可选的分批持有

保留此前讨论的 offset 能力，但从普通规则中移走冗余配置，只有需要分批持有时才声明：

```yaml
rules:
  staggered_selection:
    pool: {udf: spot_symbols}
    score: "return_20"
    select: {top: 10}
    weight: 0.60
    filter_after: "return_20 > 0"
    holding: {bars: 24, offsets: [0, 12]}
```

该片段在完整 DSL 的触发与日历下执行。`bars` 同时表示新批次周期和持有长度，
不再分别配置 every_bars、duration_bars 或 budget_split。`offsets` 非空、唯一，
每个整数落在 `[0, bars)`；bars 为正整数。

日历提供从固定锚点计算的有效 bar 序号 k，`k mod bars` 命中某个 offset 时为该 offset
建立新批次。锚点由日历定义，不取进程启动时间。每个 offset 独占 `weight / offset_count`，
上例两个批次各占最多 30%，各保留 24 个有效 bar。未建立批次的预算留空。

第一版 `holding` 只与 `weight` 配合，不能叠加 `weight_each` 或 `signals`。
无 holding 的普通规则在每个有效求值期替换选择；有 holding 时，前筛、评分、选择和后筛
只在新批次建立时执行，存下后筛后保留的基础份额，期间不重新评分或重分配。

每次触发先移除到期批次，再按当期 offset 建立批次，合成所有仍有效的贡献。
持有区间是 `[建立 bar 的结束时点, 第 bars 个后续有效 bar 的结束时点)`。
缺失触发不虚构补建中间批次；恢复时清理已到期项。状态推进按日历，不按触发次数。

若需要按时检查批次到期，应配置足够频率的定时触发；只配事件时，没有事件就不会主动计算
新的退出目标。消息有效期会限制旧批次目标继续执行，但消息过期不等于实际清仓。

### 7.3 RuleState 保存什么

普通无信号、无分批规则不需要跨期选择状态。信号规则只保存最终理论持有 ID 和必要的进入时点；
分批规则保存 offset、建立/到期时点及后筛后保留的 `base_weights`。
在 Result 的 `rule_states_json` 列中按规则名保存各自 `RuleState`；无状态规则不占条目，
整次计算都无跨期状态时保存 `{}`。内存中的结构仍叫 `rule_states`。
恢复时查询当前 `session_id` 最近成功的 Result，不另建理论持仓表或批次调度服务。
不能从合成后的 PositionTargets 反推状态：同一标的可能属于多条规则或多个不同到期批次，
合成和多空抵消都会丢失这些归属信息。

等分批次的 `base_weights` 在创建时为 `1/M`，后筛删除后不重新归一；输出时再乘
`weight / offset_count` 和方向。这样不会在下一期对已经缩小的目标重复乘预算。
`rule_weights` 是合成时的中间结果，可以写入诊断日志，不另建生命周期或表。

状态只随整次成功决策一起提交。失败不改变前态，Trade 的成交与错误通知也不修改它。

## 8. 触发、时间与输入完整性

### 8.1 两种触发

`schedule` 是定时求值，不是定时下单。使用五段 cron 和明确的 timezone；
例如 `5 * * * *` 表示每小时第 5 分钟触发。
`event` 监听已注册事件，不限于价格变化，示例为 `ViewFactorPeriodReady`。
通知必须能确定关联实例、数据范围和闭合数据周期，不能只是无时点的“有变化”。

两种触发是 OR 关系，进入相同的流水线。只配置 schedule、只配置 event 或同时配置均合法。
事件只负责唤醒，不能携带买卖指令绕过 DSL。外部信息如需影响决策，必须先成为带时点的已声明输入。
不再保留 `on_change`、`scheduled` 等策略侧“交易调仓模式”；何时实际交易由 Trade 决定。

若规则依赖 Factor Result View，首版必须配置能携带该因子完成周期和来源的 `event` 触发；
仅有 `schedule` 的实例只允许读取行情源字段。这样可以避免定时唤醒时把尚未完成或无法证明
来源周期的因子结果当成已就绪输入。后续若为 Factor 增加可验证的周期快照协议，再放开因子规则的
schedule-only 配置；这不改变两种触发对普通行情规则的 OR 语义。

### 8.2 bar_end_time 与周期

`data.bar` 是决策时间网格，`data.calendar` 定义有效 bar 和交易日。
股票日线按交易日计算，不是固定 24 小时；所有持有长度和 `bars[-1]` 都使用同一日历。
`bar_end_time` 是决策 bar 的结束时刻，不是触发接收时间、处理时间或 Result 创建时间，
也不能直接把数据源按开盘标记的 K 线时间当作结束时刻。
例如 10:00 至 11:00 的小时 bar，11:05 定时触发、11:07 才处理，`bar_end_time` 仍是 11:00。

Storage/Collector 的 `period_time` 当前表示时序行的 `BarStart`。事件适配器按策略日历将其映射为
结束边界；连续市场按固定频率换算，股票日线按交易日历映射到收盘时刻。定时触发先得到闭合结束边界，
再由 Storage 适配器定位同一交易日的 `BarStart`，不能简单按 24 小时回退。
DSL、Result、Trade 消息只使用结束边界，Storage 查询只使用开始边界，禁止混用。

首版实施范围为 `crypto_24x7` 的固定分钟、小时和日 bar，以及 `cn_stock` 日 bar。
股票分钟会话、多频率混合在具备明确映射前拒绝启用，不把交易日历工具当作完整 K 线日历。

- 定时通知以实际调度唤醒时刻，取当时最近已闭合 bar 的结束时间作为 `bar_end_time`；调度回调
  可能因进程负载稍晚执行，不能读取共享的“下一次计划时间”。
- 事件通知以事件携带的数据周期映射 `bar_end_time`，不能在延迟处理时换成最新周期。
- 读取输入的观测时间不得晚于 `bar_end_time`；不使用未来 bar、事后才能知道的交易状态。
- 进程晚启动不批量追赶所有错过的 cron；下一次定时或事件处理当前有效周期。

不强制每个 bar 求值。只有配置的触发实际发生才会计算；同一 bar 多次触发不表示多个独立决策。
需要逐 bar 检查信号或到期时，用相应频率的 schedule 或可靠的数据事件驱动。

### 8.3 首次成功锁定本期

决策身份固定为 `(instance_id, session_id, bar_end_time)`，触发类型和事件 ID 只用于解释与日志。

- 本期尚无成功结果：可以计算；缺数、暂时不可用或计算失败不占用成功身份。
- 本期已有成功结果：返回原结果，不推进状态、不重新生成待发消息或重置投递状态。
- 本期成功后出现数据修订：不自动重算本期；改变的历史数据可能影响后续周期的因子与结果。
- 已有更晚成功结果时，旧期通知直接跳过，不回滚、不补发旧目标。

因此定时先到但缺数，之后 ready 事件仍可补算同一期；若定时已经成功，事件再到只去重。
这是为简化在线状态作出的取舍，不提供同期修订链、基准前态 hash 或自动历史重放。

### 8.4 输入加载检查

删除独立 `ReadinessChecker` 对象，完整性与一致性检查直接放在输入加载流程中。
Storage 的 ready 只说明 View 可读，不保证某条策略的全部依赖已经齐备。
因子结果以可读的 View 与对应完成信息为准，不能以 Factor 内部“计算完成”日志代替。

输入按实际阶段加载：前筛需要池内相应字段；评分只要求初筛后集合的评分字段；
信号退出与后筛需要旧理论持仓相应字段。无新批次时不要求无关的评分数据。
前筛已剔除标的缺少未使用评分字段，不应导致失败；真正必需的数据缺失不能静默缩池。

同次读取冻结 View 索引身份和读取修订，分页不能拼接不同数据代际。
物理 provider、venue、序列标识和 Factor 输出必须匹配绑定，不能借另一数据源的历史填补缺口。
标的目录未提供明确 `series_tag` 时，若同一标的在本周期返回多条物理序列且该 View 为策略提供字段值，
本次直接判为严格缺数并要求绑定明确序列；仅作为因子完成/行情存在性门槛的 source View 可以保留多序列，
但不把它们合并到策略字段，避免后写序列覆盖先写序列。
保留输入出处和已存在的读取版本信息，不为 Strategy 另造内容 hash 或版本平台。
底层不提供历史快照时，只保证本次冻结读取的一致性，不承诺重建任意历史时点的市场状态。

| 情况 | 行为 |
| --- | --- |
| 数据暂未就绪或 Storage 暂时不可用 | 在原周期与有效期内有界重试；仍失败则记录并结束本次尝试 |
| 必需行列缺失、类型错误、UDF/表达式失败、NaN/Inf | 本次不提交、不发布，记录具体原因；后续触发可重试尚未成功的周期 |
| `bars[-1]` 或所需历史不足 | 跳过，不放宽条件、不把旧持仓当作退出 |
| 分页时索引切换或读取修订变化 | 放弃混合读取，在时效内重新读取或等待后续触发 |
| 通配序列返回多个物理行且策略需要该 View 的字段值 | 严格失败并要求显式 `series_tag`，不得静默覆盖 |
| 明确成功的空池、空选择或全部被后筛剔除 | 按规则正常处理，可以产生完整零目标 |
| 旧期、旧 session_id 或已经超出有效期 | 记录原因并结束，不把历史目标改时间后重发 |

每次重试有次数与时效上限，不让缺数旧周期永久阻塞实例。
没有常驻等待屏障；新的触发是新的尝试，但成功身份仍按第 8.3 节统一去重。

## 9. PositionTargets 与可靠异步

### 9.1 目标契约

```text
PositionTargets
  target_id            固定使用本次 result_id，同时作为事件 ID
  instance_id
  session_id
  strategy_id
  logical_account_id
  bar_end_time
  effective_at
  valid_until
  targets[]
    instrument_id
    target_weight
```

消息固定表示完整快照，不提供增量、hold 或 rebalance 模式。完整范围仅是指定资金单元，
不是整个交易账户；未列出的旧标的目标为零，明确成功的空列表表示完整零目标。
目标列表按规范 ID 排序，重复标的先合成，权重输出规范十进制字符串。
观察模式只在 Result 中保存理论目标草稿，不构造缺少资金单元的投递消息。

每个新成功周期都生成目标，即使权重与上期相同；是否需要下单由 Trade 判断。
Strategy 不要求 Trade 每收到一个目标就交易，也不要求同一目标永远只换算一次数量。
现有协议若不能表达这些信息，后续需同时修改生产端、消费端与验收，本轮不修改协议。

### 9.2 有效期不进入策略 DSL

删除 DSL 中的 `target.valid_for_bars`，但不删除目标时效保护。
框架级运行配置统一提供默认有效长度，初始默认是 2 个 `data.bar`；不在每个实例或规则中重复配置。
设本期为 bar k，默认 `effective_at = bar_end_time`，`valid_until` 为 bar k+2 的结束时点。
清理本期已到期批次后，若仍有持有批次，则取默认截止与这些批次最近到期时点中较早者。
保存目标后时间不再改变，运行配置修改也不追溯延长既有目标。
结果表单独保存 `bar_end_time` 与 `valid_until`，便于周期查询和过滤过期记录；
`effective_at` 固定等于 `bar_end_time`，不另设数据库列，但完整消息内仍携带该字段。
观察模式也保存同样的计算有效截止，只是不构造或发送 Trade 消息。

以连续市场小时 bar 为例，收盘即生效的目标通常两小时后过期。
股票按交易日历映射边界，实际交易时段与开盘执行安排由 Trade 决定；本版不提供
`next_session_open` 等另一套策略生效调度配置。

Trade 在接收目标、重试、补单及使用已保存目标再次发起交易前，都检查
`[effective_at, valid_until)`、授权运行身份和周期顺序；仅首次接收检查时效不够。
过期后不能再凭该目标发起新交易，但过期不是零目标，不自动卖出现有持仓。
已挂订单如何处理属于 Trade；真正退出持仓需要新的有效零目标或显式管理操作。

### 9.3 三表持久化

保留定义与实例分离，支持同一份 DSL 对应多个独立实例；仅将原 outbox 并入结果表。
以下是目标 schema，共 25 个字段，不表示当前数据库已经完成改造。
类型按 SQLite 表示；时间均为 UTC 毫秒，除明确“可空”外均必填。

#### 9.3.1 t_strategies：5 个字段

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `strategy_id` | TEXT | 主键，稳定的策略定义 ID |
| `strategy_name` | TEXT | 由 DSL.name 派生的列表、搜索和排序字段 |
| `dsl_yaml` | TEXT | 当前 DSL 的唯一权威文本 |
| `created_at` | INTEGER | 创建时间 |
| `updated_at` | INTEGER | 最近修改时间 |

保存 DSL 与派生名称必须原子完成；名称不要求代替 ID 作为唯一标识。
所有引用实例停用后才允许修改共享定义，不因只修改名称而增加另一条热更新流程。

#### 9.3.2 t_strategy_instances：9 个字段

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `instance_id` | TEXT | 主键，策略实例身份 |
| `strategy_id` | TEXT | 引用的 StrategyDef |
| `space_id` | TEXT | 数据与资金单元所属空间 |
| `input_bindings_json` | TEXT，JSON | 字段与行情、Factor 输出、Binding 和 View 的绑定 |
| `logical_account_id` | TEXT，可空 | 输出目的地；空表示观察模式 |
| `enabled` | INTEGER | 只允许 0/1，是否启用 |
| `session_id` | TEXT，可空 | 当前运行会话；完成停用清理后为空 |
| `created_at` | INTEGER | 创建时间 |
| `updated_at` | INTEGER | 最近修改时间 |

同一 `(space_id, logical_account_id)` 最多有一个 enabled 的实例，空目的地不参加该约束。
不保存 current_targets、last_result_id、command_sequence；不重复保存 DSL 中的周期和触发配置。
结果列表按 instance_id 查询，恢复前态按 instance_id + session_id 查询，不能只凭策略定义 ID 恢复。

#### 9.3.3 t_strategy_results：11 个字段

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `result_id` | TEXT | 主键，同时作为 target_id 和事件 ID |
| `instance_id` | TEXT | 产生本次结果的实例 |
| `session_id` | TEXT | 本次结果所属运行会话 |
| `bar_end_time` | INTEGER | 决策采用的已闭合 bar 结束时刻 |
| `valid_until` | INTEGER | 冻结的有效截止，用于扫描过期记录 |
| `snapshot_json` | TEXT，JSON | 当时的策略身份、DSL 与输入出处 |
| `targets_json` | TEXT，JSON | 完整目标权重列表；明确成功的零目标写 `[]` |
| `rule_states_json` | TEXT，JSON | 按规则名保存的后态；无状态时写 `{}` |
| `event_data` | BLOB，可空 | 完整冻结的目标事件；观察模式为空 |
| `publish_status` | TEXT | none、pending、sent、cancelled |
| `created_at` | INTEGER | 本次结果实际创建时间 |

`snapshot_json` 固定包含 `strategy_id`、`dsl_yaml`、`inputs`。
inputs 保存本次使用的绑定、Space/View/列/Factor 输出等来源，以及实际冻结的索引和读取修订；
不是完整行情面板，也不是另一份定义版本。无需再设 strategy_id、dsl_yaml 或前结果 ID 的独立列，
历史策略身份和输入不能通过当前实例或当前定义反查。

targets_json 必须由成功计算显式赋值，不以数据库默认 `[]` 掩盖遗漏结果或计算失败。
event_data 冻结事件信封、目的地、策略/实例/会话身份、目标权重及全部时间字段；
其中身份、目标、周期和截止必须与该 Result 一致。与 targets_json 的少量重复是有意保留：
查看结果不必解析消息协议，重投也不必读取已经改变的实例配置。
只有 publish_status 可以更新，其余字段作为计算及投递快照不可变；不增加 updated_at。

唯一约束为 `(instance_id, session_id, bar_end_time)`，同时支持按当前会话倒序查询最新成功结果。
给 pending 记录建立部分索引，不增加重试计数、下次执行时间、租约、inflight 或 published_at。
详细评分过程先写诊断日志，不增加单独的解释表或 details 列。

### 9.4 原子提交与结果内投递

删除独立 `t_strategy_outbox`，不创建 inbox、attempts、规则状态或投递任务表。
异步发送职责仍保留，由一个后台发布循环处理结果表中的待发记录。

同一事件涉及多个实例时分别按成功周期去重；已经成功的不重复计算，其他实例在时效内继续。
输入暂时失败可有界延迟重试，终态原因记录后 ACK，不因某个实例失败而覆盖其他实例结果。

一次成功决策在同一 SQLite 事务中：

1. 复核实例仍 enabled、session_id 未变；查询当前会话最近成功 Result，与求值开始时读取的
   前结果 ID 比较，且没有更晚成功周期。前结果 ID 只是提交校验参数，不写入实例或结果列。
   同时确认当前时间仍早于 valid_until，防止长计算结束后提交已经过期的结果。
2. 本周期尚未成功时，插入带唯一周期键的 Result，一次保存历史快照、后态、目标和投递信息。
   执行型实例保存完整 event_data 和 pending；观察型保存 NULL event_data 和 none。
3. 将同实例、同会话更早周期仍为 pending 的记录改为 cancelled。新 FULL 已替代旧目标，
   不再补投积压的旧快照；历史计算结果保留，其他实例与会话不受影响。

本周期已成功直接返回原 Result，不因为触发来源或临时 result_id 不同而覆盖内容，
也不把 sent/cancelled 重置为 pending。失败整体回滚，不能先存后态再另行创建消息。
单实例串行求值、事务检查与唯一键即可，不使用分布式锁。

| publish_status | 含义 | event_data |
| --- | --- | --- |
| none | 观察结果，无需投递；以后绑定资金单元也不补投 | NULL |
| pending | 等待发送或重试，不能据此判断 broker 从未收到 | 非空 |
| sent | 已获得 broker 确认，不代表 Trade 已接受或成交 | 非空 |
| cancelled | 已停止重试，不保证此前从未送达 | 非空 |

执行型记录只允许 pending -> sent 或 pending -> cancelled；none、sent、cancelled 不重新转为 pending。
单发布循环每轮按 created_at/result_id 取得完整 pending 列表，处理完成后按框架统一间隔等待下一轮。
个人系统首版不做 LIMIT 分批，避免持续失败的首批记录使后续目标一直排不到；本轮新增记录留到下一轮。
逐条发布前复查该行仍为 pending、实例 enabled、会话有效、目标未过期，且没有更晚成功周期；
不能只信本轮开始取得的列表。发送有统一超时。过期、停用、旧会话或被新周期替代的记录
转 cancelled，临时发送失败保持 pending，均继续处理本轮其余记录。
在有效期内始终使用同一 result_id/target_id 和原 event_data 重试；broker 确认后再更新为 sent。
确认丢失或确认后数据库更新失败时仍可能保持 pending，依靠相同消息重投和 Trade 去重恢复。
发送途中停用或产生更新周期时，消息可能已经发出，无法靠本地 cancelled 撤回；
broker 确认只条件更新仍 pending 的记录，不能把 cancelled 改为 sent。
Trade 仍负责授权、时效与已接受周期的校验，不保证其尚未获知新周期时旧目标绝不执行。

清理历史时，保留各实例当前会话最近成功的 Result，不受其投递状态影响；
仍有效的 pending 也不得删除。失效 pending 先终止，再按普通保留规则处理。
不再有独立 outbox 清理流程，也不能删除整个最新结果来表示投递已经完成。

### 9.5 Trade 接收边界

Trade 在去重快捷路径之前先校验资金单元当前授权的 `(instance_id, session_id)` 与有效期，
再在该授权身份内比较 bar_end_time，接收事务中再次复核，不能只在事务外检查：

- 比当前周期新：接受并建立新的当前目标；不等待缺失周期。
- 与当前周期相同：只允许相同 target_id 且规范内容完全一致的重投；其他情况报告冲突。
- 比当前周期旧：拒绝，不因已有 receipt 而恢复旧目标或唤醒执行。

同一 target_id 的任何业务字段变化均属于冲突。可以保留消息内容一致性校验或请求摘要，
这不是已删除的 DSL 定义 hash。新授权 session_id 单独建立周期基线，不继承旧会话的高水位；
旧会话即使携带更晚周期也不能通过授权校验。授权管理的迟到释放请求同样必须匹配旧身份，
不能撤销已切换到的新身份。Trade 自身订单的版本锁不属于本次删除范围。

### 9.6 解释与重放边界

Result 保留恢复和投递所需的最小历史快照、规则后态与完整目标。
各规则池规模、排除原因、原始/标准化评分、排序、基础份额、后筛释放比例和批次贡献
先写结构化诊断日志，不要求每个结果持久化完整评分明细。
日志关联 instance_id、session_id、bar_end_time、result_id/target_id 和 trace ID。

不默认落盘完整行情快照或内容寻址制品。保存结果可支持断点恢复、重复投递和解释，
但没有相应历史数据时，不能宣称可以精确重算任意过去周期。

## 10. 执行引擎与参考借鉴

### 10.1 固定 Go 流程、Expr、少量可信 UDF

采用固定 Go 流水线处理集合、排序、状态和权重，Expr 处理受约束的布尔及数值表达式。
启用时进行类型校验和内存编译，每期复用编译结果；标准化列按当期候选集合批量预计算。
表达式只访问已提供的上下文，不注入任意网络、文件、数据库或下单能力。
编译时禁用 Expr 默认内置函数，再按白名单开放必要的纯函数及本版两个评分变换。
禁止 now、随机数和隐式读取环境等非确定能力；需要时间时使用显式传入的决策上下文。

Pool UDF 采用按名称注册的可信函数，输入是预加载的标的目录快照、时点与参数，
输出是该目录内的规范标的 ID 集合。启用时检查名称和参数，运行时检查返回类型、成员和重复项。
UDF 不随机选池、不读取未声明的最新外部状态、不调用 Trade。
首版不允许在 score/过滤表达式内任意调用其他动态 UDF。

计算内核可概括为：

```text
Evaluate(内存中的已校验规则, EvaluationInput, PreviousRuleState)
  -> PositionTargetsDraft, NextRuleState, Explanation
```

输入加载和投递在内核之外。相同规则、输入和前态得到相同结果，不依赖进程当前时间或 map 遍历顺序。
Live 与 Paper 使用相同计算内核，区别留在 Trade。

## 11. 验收与本轮简化清单

### 11.1 后续实施必须验证的场景

| 类别 | 验收重点 |
| --- | --- |
| DSL | rules 命名；未知字段与重复键拒绝；无版本/hash/旧 kind 分支；编辑前停用所有引用实例；strategy_name 与 DSL.name 原子同步 |
| 标的池 | 固定列表与 UDF 返回同类集合；池与前筛分离；非法 ID/重复项/UDF 错误不当作空池 |
| 评分 | 原始因子、表达式组合、有限数值和类型检查；评分系数不影响资金比例 |
| 标准化 | 初筛后冻结样本；平均名次；单元素/全相同；总体标准差与零方差；后筛不重算样本 |
| 选择 | 高分优先；top/tail 互斥；where 在截取前；同分 ID 稳定；不足取现有、空集合法 |
| 权重 | weight/weight_each 互斥；静态总预算上界；M=7/三个 offset 的 18 位余数与截断；后筛删除余数首项；现货不做空 |
| 后筛 | 60%/10 项剔除 2 项后剩 48%；不补位；不重新分配；只影响本规则 |
| 信号 | 持续条件与穿越不同；相等保持；退出优先；旧持仓独立检查退出；后筛删除后需重新 entry；固定比例仅配固定池 |
| 分批 | 固定日历锚点、offset 独立份额、到期与未建立留空、不虚构补批次、只在建立时后筛 |
| 触发 | 定时/事件均可独立运行；同时启用 OR；定时按实际唤醒时刻映射、事件按事件周期确定 bar_end_time；非每 bar 强制求值 |
| 幂等 | 本期首次成功锁定；失败可重试；同周期修订不重算；旧期不倒灌；正常重启与重新启用不同 |
| 输入 | 分页一致性、多源不混用、按实际阶段检查依赖、bars[-1] 精确相邻 bar、缺数不退出 |
| 完整目标 | 所有必要规则全成功才提交；成功空集为零目标；同权重新周期仍发布；仅覆盖绑定资金单元 |
| 生命周期 | session_id 与 Trade 幂等授权切换；改绑撤销旧目的地；迟到释放不撤销新身份；周期基线按授权隔离 |
| 持久化 | 三表共 25 列；历史快照不读当前绑定；无状态后态为 {}；保留当前会话最新成功结果 |
| 异步 | Result/状态/事件/初始投递状态原子保存；四态不混淆；确认丢失重投；新成功周期取消积压旧目标；连续失败不阻塞其他待发记录；在途取消不冒充撤回 |
| 执行边界 | 接收及再次执行都查时效；过期不清仓；Trade 通知不推进 RuleState |
| 表达式 | 仅开放纯函数白名单；拒绝 now/随机能力；字段与函数依赖在启用时校验；bars 仅允许 0/-1 常量偏移 |

### 11.2 相比旧文档的删减

| 旧设计 | 当前设计 |
| --- | --- |
| 不可变发布版本与 definition_hash/json | 一份可管理编辑的 dsl_yaml，历史结果留副本 |
| api_version、DSL 版本与持久化编译制品 | 单一语言格式，启用时内存编译 |
| components / universe / pre_filter / post_filter / bottom | rules / pool / filter_before / filter_after / tail |
| kind 区分 ranked、fixed、entry_exit | 同一流水线，可选 score/select/signals/holding |
| method/budget/position 包装 | weight 或 weight_each，默认做多 |
| 评分范围、方向、并列和数量不足的多种可配模式 | 初筛后评分，高分优先，稳定截取，不足取现有 |
| 后滤后可重新分配、三层 timing、容量与冷却配置 | 后筛只删除，信号保持最小状态，不提供额外开关 |
| 每个闭合 bar 强制求值 | 只由配置的定时或事件触发 |
| 同期输入 hash 比较与自动修订重算 | 每个运行周期第一次成功后固定结果 |
| 独立 ReadinessChecker 与复杂等待链 | 输入加载时直接检查，有界重试 |
| TheoryState、DecisionState、component_contribution | RuleState、临时 rule_weights |
| StrategyRunner、runner_id、run_id、activation_id | StrategyInstance、instance_id、session_id |
| run_generation、last_result_id、command_sequence | 运行会话隔离；按当前会话查询最近结果，以 bar_end_time 排序 |
| 定义名称每次解析、没有展示字段 | strategy_name 由 DSL.name 同步派生，不独立编辑 |
| 定义/实例/结果/outbox 四表 | 定义/实例/结果三表；结果携带 event_data 与 publish_status |
| Result 独立策略 ID、DSL、前结果指针和详细解释列 | snapshot_json 保存历史身份与 DSL；前态校验不落库；明细先日志 |
| as_of、prev.x | bar_end_time、bars[0].x / bars[-1].x |
| 每个策略单独配置 target 有效期 | 框架统一默认时效，消息仍携带有效边界 |

暂不引入动态脚本发布、任意工作流、规则间依赖、可调杠杆预算、自动历史重放、收益曲线轮动、
复杂择时和完整回测引擎。多 View、多频率等输入能力只有在绑定与读取实现明确支持时才可启用，
不能通过“配置可以解析”假装语义可执行。

本文是 Strategy、Trade、协议、持久化和管理界面的共同合同。后续实现或维护必须同步更新这些
消费链路，不能只删除实例字段而保留依赖旧序号、旧时间或旧状态命名的路径；任何未通过本版验收
的能力都不能在文档或界面中标为已上线。
