## 1. 项目概述

MooX 是一个面向个人开发者的量化金融一站式数据平台，涵盖从多源数据采集、统一存储管理到前端可视化交互的完整技术栈。项目采用 Go Monorepo 架构，通过 `go.work` 管理多个独立 Go Module，配合 Vue 3 前端。当前产品支持由一个中央 Admin 管理多台服务节点：每台服务器部署独立 Gateway，并且只把机器服务请求转发给本机服务。

### 核心能力

| 能力域 | 说明 |
|--------|------|
| 多源数据采集 | 支持交易所（Binance 等）K 线、标的元数据采集，可扩展至行情、舆情等数据源 |
| 统一存储引擎 | 时序数据（K 线）、记录数据（标的信息）的统一存储与查询，支持列级更新 |
| 异步派生视图 | 写入主存后异步构建 OLAP 物化视图（DuckDB）和全文索引（Bleve） |
| 管理控制台 | 单用户登录、服务部署、网关节点、路由状态和运维监控 |
| 节点服务网关 | 每台机器独立接收 `/api/service/*`，校验 HMAC 后只代理本机 loopback 服务 |
| 前端工作台 | 数据浏览、采集器管理、策略配置、运维监控的可视化界面 |

### 当前部署边界

- 面向个人开发者和个人量化站点，优先保证安装、升级、备份和故障定位简单。
- Admin 是唯一中央控制面；普通服务节点可使用 `--no-admin`，但仍必须运行本机 Gateway。
- `t_gateway_nodes` 维护节点身份和路由应用状态；`t_service_deployments` 按 `node_id` 维护服务实例与网关路由来源。
- 当前不支持自动发现、自动摘除、负载均衡、跨节点转发或自动故障转移。需要调整路由时，由部署流程或管理员更新服务管理记录。
- SCF 是由 CloudNode 调度的外部计算运行时，不属于常驻服务多实例部署；它通过 keepalive 获取当前服务地址。
- Monitor 是单实例监控事实存储，不做 Peer/Owner/Lease 或对端互检。手工部署检查和故障诊断由目标节点上的 `moox-cli doctor bootstrap|diagnose` 执行。完整边界见[节点服务网关架构](节点服务网关架构.md)。

## 2. Monorepo 组织结构

项目使用 Go 1.24 + `go.work` 管理 Monorepo。业务服务和独立协议生成模块位于 `modules/`，共享能力位于 `packages/`，前端静态宿主 `web-host` 是仓库根级运行模块；因此 Workspace Module 分布在 `modules/`、`packages/` 和仓库根级运行模块中。下表必须与 `go.work` 保持一一对应。

| `modules/eventbus/proto/eventbusgen` | EventBus proto 生成代码 |

| `packages/healthz` | 健康检查、签名保护和 tRPC 插件 |
| `packages/hostmetricpb` | 主机指标公共消息协议 |
| `packages/jetstream` | NATS 发布、消费、凭据和投递封装 |
| `packages/messagepb` | EventBus 统一消息外层协议 |

### Monorepo 规范

- **跨模块引用**：业务模块间只允许引用对方稳定的 `proto/` 生成模块；通用能力必须下沉到根级 `packages/*`，不得直接 import 对方 `internal/` 实现
- **统一构建入口**：根 `Makefile` 转发至 `scripts/` 下的脚本执行复杂逻辑
- **独立二进制产物**：`bin/` 目录存放各模块编译产物（`moox-admin`、`moox-storage`、`moox-collector` 等）

## 4. 核心模块详解

### 4.1 Admin 模块（管理服务）

**入口**：`modules/admin/cmd/server/main.go`；Schema 初始化入口是 `modules/admin/cmd/cli/main.go`。

Admin 模块是整个系统的**中央管理与浏览器控制面**，承担用户管理、网关节点、服务部署信息、节点路由编译和基础运维职责。Admin 保留 `/api/admin/*` 和 `/api/gateway-control/*`，不再承载 `/api/service/*`。主机指标采集、历史存储和告警属于 Host Agent、Monitor 与 Storage；采集规则、云节点、云账户和云函数代码包业务实现分别位于 `modules/collector` 与 `modules/cloudnode`。

#### 架构分层

```
modules/admin/
├── cmd/
│   ├── server/main.go             # moox-admin：bootstrap.Initialize() + trpc.NewServer()
│   └── cli/main.go                # moox-admin-cli：init admin schema
├── internal/
│   ├── bootstrap/                 # 启动编排（初始化、依赖注入、TRPC 注册）
│   ├── gateway/                   # 浏览器控制面和 Gateway 控制接口
│   ├── service/                   # 业务服务层
│   │   ├── auth/                  # 认证鉴权（JWT + 盐值挑战 + HMAC）
│   │   ├── database/              # 数据库管理（SQLite + GORM）
│   │   ├── sysdeploy/             # 服务部署信息
│   │   └── secret/                # 秘钥管理
│   └── ...
├── proto/                         # Proto 定义（admin/infra/ops/secret/sysdeploy）
│   └── admingen/                  # 生成代码（独立 module）
├── schema/admin.sql               # admin 本地基础表
├── config/                        # 配置文件（gateway.yaml / trpc_go.yaml）
└── docs/                          # 模块文档（已合并到根 docs/admin/）
```

#### TRPC 服务定义

Admin 模块只注册 admin 本地基础服务。采集和云节点协议分别由 `modules/collector/proto` 与 `modules/cloudnode/proto` 持有，并由独立 `moox-collector` 与 `moox-cloudnode` 实现。

| Proto 文件 | 服务 | 核心方法 |
|-----------|------|---------|
| `infra_service.proto` | AuthService | GetLoginSalt, Login, Logout, IssueRawSessionTicket, GetUserInfo, UpdateUserInfo |
| `admin_service.proto` | SpaceMgr | Space 管理 |
| `ops_service.proto` | Dns / Ssh | 运维辅助能力 |
| `secret_service.proto` | SecretMgr | 秘钥管理 |
| `sysdeploy_service.proto` | SysDeploy | 服务部署信息 |

#### 数据库模型

Admin 使用 SQLite + GORM，`schema/admin.sql` 只定义 admin 本地基础表：

- **认证体系**：用户、登录态、登录历史和用户行为。
- **运维能力**：SSH 主机、SSH 会话和秘钥管理。
- **节点与服务部署**：`t_gateway_nodes`、按节点归属的 `t_service_deployments`。

采集规则、任务实例、云账户、云节点、云函数代码包不在 admin schema 中，分别由 `modules/collector/schema/collector.sql` 和 `modules/cloudnode/schema/cloudnode.sql` 管理。

服务启动只打开数据库连接和缓存。部署或本地重建时，先运行 `moox-admin-cli init --db-path ...` 初始化 `schema/admin.sql`，再启动 `moox-admin`。

#### 鉴权机制

1. **浏览器控制面**：登录挑战、JWT/session 和会话 HMAC 防重放。
2. **Gateway 控制面**：Admin 与 Gateway 使用独立 control HMAC key。
3. **机器服务面**：调用方与 Gateway 使用独立 service HMAC key，签名绑定目标节点和 nonce。
4. **本机诊断面**：独立 health HMAC；诊断端口只监听 loopback。

### 4.2 Storage 模块（存储引擎）

**入口**：`modules/storage/cmd/server/main.go`；元数据初始化入口是 `modules/storage/cmd/cli/main.go`。

Storage 模块是系统的**数据面核心**，提供量化金融数据的统一存储与查询能力。

#### 核心设计理念

| 概念 | 说明 |
|------|------|
| **Space** | 顶层命名空间，实现数据隔离 |
| **Dataset** | 数据集，一个 Dataset 只绑定一个 DataSource |
| **DataSource** | 数据源（替代传统 Exchange 概念），描述数据来源 |
| **Subject** | 数据主体（如交易标的），不归属于 DataSource |
| **SubjectSymbol** | 外部代码映射（如 `BINANCE:BTCUSDT` → 统一 Subject） |
| **Factor** | 因子定义，不拆分 Def/Instance |
| **View** | 异步物化只读查询入口 |

#### 架构分层

```
modules/storage/
├── cmd/
│   ├── server/main.go             # moox-storage：按 storage.roles 装配服务角色
│   ├── cli/main.go                # moox-storage-cli：init / import-seed
│   └── bench/main.go              # 本地压测入口
├── internal/
│   ├── rowkey/ typedvalue/ retinfo/ # 真正跨服务复用的基础契约
│   └── service/                   # 按领域垂直组织
│       ├── primarystore/          # Metadata、路由和事实编排
│       ├── datanode/             # Pebble、Sequence 和 Outbox
│       ├── dataview/              # DataView 查询和维护
│       ├── viewbuilder/           # RowsCommitted 消费和物化
│       └── viewindex/              # DuckDB/Bleve ViewIndex
├── proto/                         # 6 个 proto 文件
│   └── storagegen/                # 生成代码（独立 module）
└── docs/                          # 模块文档（已合并到根 docs/storage/）
```

#### 数据模型

Storage 将所有数据统一为**事实行**模型：

```
事实行 = space_id + dataset_id + data_key + version
```

| 数据类型 | Key 前缀 | Key 组成 | Version |
|----------|----------|----------|---------|
| TimeSeries（时序） | `t\|` | `subject \| freq \| dimhash` | `data_time` |
| Record（记录） | `r\|` | `record_id` | `record_version` |

**写入语义**：列级 patch/upsert，NULL 值不覆盖已有数据。

#### 存储引擎分工

```
                    ┌──────────────────────────────────────────────┐
                    │              PrimaryStore Service                   │
                    │       (唯一公开入口 / Facade)                  │
                    └───────┬──────────────┬───────────────────────┘
                            │              │
                    写入 ▼              查询 ▼
                    ┌──────────┐    ┌──────────────────────────┐
                    │  Pebble   │    │    DataView (读模型)      │
                    │ (主存KV)  │    │  ┌────────┐  ┌────────┐ │
                    └─────┬────┘    │  │DuckDB  │  │ Bleve  │ │
                          │         │  │(时序)  │  │(全文)  │ │
                    事件 ▼         │  └────────┘  └────────┘ │
                    ┌──────────┐    └──────────────────────────┘
                    │  EventBus │           ▲
                    │Memory/NATS│           │ 物化构建
                    └─────┬────┘    ┌───────┴───────┐
                          │         │   ViewBuilder     │
                          └────────▶│  (视图构建器)  │
                                    └───────────────┘

    ┌──────────┐                              ┌──────────┐
    │  SQLite  │  (元数据控制面)               │ Parquet  │ (冷归档)
    └──────────┘                              └──────────┘
```

#### CQRS + 异步派生

Storage 采用 **CQRS（命令查询职责分离）** 模式：

- **写模型**：Pebble KV 存储，所有写入通过 PrimaryStore Service 统一入口
- **读模型**：DuckDB 物化视图（时序 OLAP）+ Bleve 全文索引（记录检索）
- **派生流程**：写入 Pebble → 发布事件到 MemoryBus/NATS → ViewBuilder 消费事件 → 通过 PrimaryStore 回读完整行 → 写入派生存储
- **幂等保证**：ViewBuilder 消费幂等，且 PrimaryStore 始终是唯一数据入口

#### 版本化物化视图

采用 **Blue-Green** 模式管理视图版本：

1. `view_version` 递增触发新的持久化 `ViewIndexBuild`
2. `BUILDING/CATCHING_UP` 期间增量同时写 `active_index_id` 与当前 build 的 `index_id`
3. 构建完成后通过 `ActivateViewIndex` CAS 原子切换 `active_index_id`

#### 运行角色

Storage 支持通过 `storage.roles` 配置四种运行角色：

| 角色 | 职责 | 默认部署 |
|------|------|----------|
| `access` | 对外服务，接收读写请求 | 单机模式默认启用 |
| `primary` | Pebble 主存节点 | 分布式模式独立部署 |
| `view` | DataView 查询与 ViewBuilder 异步构建视图 | 单机模式默认启用 |
| `archive` | Parquet 冷归档调度与执行 | 按需启用 |

#### 水平分片

`router.Resolver` 支持多节点 Pebble 分片：
- 精确 `subject_id` 匹配 → 优先路由
- Glob pattern 匹配 → 次优先
- 通配 `*` → 兜底路由

### 4.3 Collector 模块（数据采集器）

**入口**：`modules/collector/cmd/server/main.go`；Schema 初始化入口是 `modules/collector/cmd/cli/main.go`；SCF 运行入口是 `modules/collector/cmd/scf/main.go`。

Collector 是独立部署的采集管理与执行服务。控制面进程负责采集规则、任务实例和 planner，SCF runtime 负责执行云端采集任务。

#### 架构分层

```
modules/collector/
├── cmd/
│   ├── server/                    # moox-collector：CollectMgr 独立服务入口
│   ├── cli/                       # moox-collector-cli：init collector schema
│   └── scf/                       # moox-collector-scf：SCF runtime 入口
├── internal/
│   ├── app/control/               # 控制面启动、配置、依赖发现、数据库
│   ├── app/runtime/               # SCF runtime 配置、鉴权和 URL helper
│   ├── app/runtimeboot/           # SCF runtime 启动装配
│   ├── rpc/                       # CollectMgr RPC 实现
│   ├── planner/                   # 根据规则生成任务实例
│   ├── executor/                  # 执行采集任务
│   ├── taskrunner/                # CloudNode JobItem 到采集任务的适配
│   ├── serverless/                # SCF runtime 事件入口
│   ├── sources/                   # Collector 接口、Binance 采集实现和交易所客户端
│   ├── reporter/                  # 状态与心跳上报
│   ├── model/                     # SCF runtime 事件与心跳模型

└── config/ / configs/             # 控制面配置与 SCF 配置树
```

#### 插件化采集器架构

- **接口定义**：`Collector` 接口定义 `Source()`、`DataType()`、`Collect()`。
- **当前实现**：当前内置 Binance K 线采集；现货标的元数据通过 Binance 适配器写入 Dataset。
- **扩展方式**：新增数据源时补齐 `sources` 执行实现；新增数据类型时补齐 `planner` 展开逻辑、配置文件、元数据 seed 和 SCF 能力上报。

以上描述当前实现。目标架构将采集入口提升为 `stock_cn`、`stock_us`、`crypto_binance`、`crypto_okx` Market Module：用户不选择 Provider；Market Module 在内部组合 Provider、交易日历、符号映射、质量裁决和完整性补洞，并将结果写入 Storage 统一数据集。目标术语、数据流和初始化约定见 [内置市场行情采集架构](内置市场行情采集架构.md)。

#### 配置机制（三层）

1. **静态配置**：启动时从配置文件加载基础参数
2. **控制面配置**：`moox-collector` 持久化采集规则和任务实例，并通过 `moox-cloudnode` 下发 JobItem
3. **运行时配置**：SCF runtime 通过 cloudnode keepalive 获取服务部署信息并维持节点在线状态，任务通过 `PollJobItems` 获取

#### 与其他模块交互

| 交互方向 | 协议 | 说明 |
|----------|------|------|
| 管理台/CLI → Collector 控制面 | Admin 控制面 `/api/admin/collectmgr/*` | 管理采集规则、触发 planner、查询任务实例 |
| Collector 控制面 → CloudNode | CloudNodeMgr HTTP/tRPC JSON | 提交采集 JobItem |
| SCF runtime → Node Gateway | `/api/service/cloudnode/*` + `/api/service/collectmgr/*` | 拉取 JobItem、回报云执行状态和采集任务实例状态 |
| SCF runtime → Storage PrimaryStore/Metadata | Node Service Gateway tRPC | 通过 `storage-primary` 写入 dataset 和 K 线 |
| Collector/SCF → 交易所 | HTTP/REST | DNS 优选 IP 访问交易所 API |

#### SCF 环境适配

- Panic 恢复：SCF 冷启动异常自动恢复
- 同步状态上报：每次采集完成后立即上报
- ServerInfo 动态更新：运行时环境信息动态采集
- K 线闭合处理：根据交易所时间判断 K 线是否闭合
- 并发控制：通过 channel + goroutine 池控制并发采集

目标部署模型中，Collector 控制面负责全局规划、Provider 配额和缺口修复，SCF 只执行有时间与数据量上限的 JobItem。四个内置 Space 复用同一代码包，但分别部署 SCF 函数，并通过 `MOOX_SPACE_ID` 固定执行范围；超出单次预算的任务通过 `continuation_cursor` 续跑。查询和元数据初始化不进入 SCF 链路。

#### DNS 优选机制

```
定时解析域名 → 多 IP 探测 → 延迟排序 → 缓存最优 IP
```

通过自建 DNS 代理优化对交易所 API 的访问成功率，避免 DNS 污染和延迟问题。

### 4.5 Web-Host（前端静态服务）

**路径**：`web-host/`

Web-Host 是一个 Go 编写的**前端静态文件服务器**，将前端 `dist` 通过 statik 嵌入单个二进制文件。它只在 `127.0.0.1:9528` 提供静态内容，不代理 API；Caddy 是公开代理。

#### 架构角色

```
Browser --HTTPS--> EdgeOne --HTTPS--> 中央 Caddy --HTTP loopback--> web-host:9528 or Admin:11000
Backend/SCF --HTTPS + service HMAC--> 节点 Caddy --HTTP loopback--> Gateway:11002
Monitor --health HMAC--> dedicated internal health ports
```

#### 对外暴露

- 中央 Caddy 的 `/`、`/#/*`、静态资源 → web-host `9528`
- 中央 Caddy 的 `/api/admin/*`、`/api/gateway-control/*` → Admin `11000`
- 每台节点 Caddy 的 `/api/service/*` → 本机 Gateway `11002`
- 公开入口上的其他 API 或诊断路由 → `404`

**边界**：浏览器不直连 Admin，后台 service 调用不经过 web-host。EdgeOne 和 Caddy 构成公网边界；web-host、Admin、Gateway、健康检查、metrics 和模块 RPC 均绑定 loopback。

### 4.6 EventBus、Monitor 与 Host Agent

这三个模块构成系统监控数据面：

- `moox-eventbus` 是唯一的 NATS JetStream Broker 所有者，只提供只读管理面，不提供消息发布代理。
- `moox-host-agent` 是 Linux `amd64/arm64` 普通用户进程，从 `/proc`、`/sys` 和 `statfs` 采集 CPU、内存、文件系统、磁盘与网络指标。
- `moox-monitor` 消费主机指标和服务指标，写入 Storage、维护当前快照、执行内存规则快照并向管理台提供查询 API。
- `moox-cli doctor` 在用户显式触发时读取 embedded Manifest、SysDeploy、签名 health/metrics 和 Monitor `GetDoctorContext`，生成版本化报告；它不是守护进程，也不自动恢复。

主机监控链路固定为：

```text
moox-host-agent -> EventBus -> moox-monitor -> Storage
Web -> Admin control plane -> moox-monitor -> current registry / Storage history
```

Host Agent 采用 best-effort 发布，不保存 outbox 或补发旧样本。Monitor 写 Storage 成功后才更新内存快照并确认消息。历史数据统一使用系统级 `space_id=moox_system`，按一分钟粒度保存到四个 Host Dataset，默认保留 48 小时；Storage 通过有超时、防重入和批次上限的 tRPC Timer 清理，Monitor 不删除 Storage 事实。完整设计见[主机监控架构设计](主机监控架构设计.md)，全系统保留矩阵见[数据保留与磁盘空间](运维/数据保留与磁盘空间.md)。

### 后台调度契约

以下运行任务由 tRPC Timer 统一拥有调度频率。除 HostAgent 外，业务 Handler 使用共享 `timerjob.Job` Clone 调用 Context、施加执行超时、同步返回结果并跳过同进程重入；HostAgent 直接复用 Agent 自身的原子 guard，确保手动与定时采样互斥并计入同一 skipped 指标。

| 服务 | 周期 | 超时 | 启动立即执行 |
| --- | --- | --- | --- |
| `trpc.moox.storage.host_metrics_cleanup.timer` | 每小时 | 60s | 是 |
| `trpc.moox.admin.auth_cache_cleanup.timer` | 每 5 分钟 | 60s | 否 |
| `trpc.moox.monitor.data_cleanup.timer` | 每 6 小时 | 120s | 是 |
| `trpc.moox.monitor.check_schedule.timer` | 每 30 秒 | 30s | 是 |
| `trpc.moox.monitor.metric_rule.timer` | 每分钟 | 30s | 是 |
| `trpc.moox.archive.materialize.timer` | 每 10 分钟 | 120s | 是 |
| `trpc.moox.archive.cos_sync.timer` | 每小时 | 300s | 是 |
| `trpc.moox.trade.fill_reconcile.timer` | 每 5 秒 | 5s | 是 |
| `trpc.moox.trade.order_recovery.timer` | 每 15 秒 | 15s | 是 |
| `trpc.moox.gateway.route_refresh.timer` | 每 15 秒 | 10s | 否 |
| `trpc.moox.hostagent.sample.timer` | 每 15 秒 | 30s | 是 |

`startAtOnce=1` 会在 Timer service 启动期间同步执行 Handler；Handler 返回错误会阻止该 service 成功启动。Gateway 已在监听前执行一次允许有效缓存兜底的同步初始化，因此不能再设置 `startAtOnce`。HostAgent 把它作为唯一的立即采样入口，初次采集或发布失败会让启动失败并交由进程 supervisor 重试。两者频率都是部署时静态配置，不支持热更新。

这些 Timer 默认使用 `DefaultScheduler`，只保证当前进程内触发，不提供跨进程互斥。扩展为多副本前必须明确单一 owner 或接入分布式 scheduler，不能把本地 overlap guard 当成集群锁。

### 4.7 Gateway（节点服务网关）

**路径**：`modules/gateway/`

每台服务器运行一个 `moox-gateway`。它从中央 Admin 拉取本节点完整路由快照，校验后原子替换内存路由并保存到本机 `routes.json`，随后只把 `/api/service/{service}/{method}` 转发给路由中声明的 loopback 服务。Admin 临时不可用时，已加载有效快照的 Gateway 继续使用最后路由；无缓存的新节点保持 not ready。

Gateway 与 Admin 分别属于数据面执行器和中央控制面。两者使用独立模块和部署进程，完整设计见[节点服务网关架构](节点服务网关架构.md)。

### 4.8 Factor、Strategy、Trade 与 Archive

- **Factor**：管理因子定义和绑定，按任务调度常驻 Python worker，从 Storage 读取输入并把结果列写回 Storage。Go 负责协议、版本、超时和重试，Python 只负责纯计算。
- **Strategy**：管理策略包、Binding、运行状态、回测、组合目标和绩效查询。Strategy 保持现有独立的 Python worker/业务运行时实现，但其代码可导入 `packages/pyruntime` 的可复用组件；本次 Streaming 只纳入并支持 Factor 的 Python runtime 入口，不把 Strategy 迁移到 Factor 的业务 runtime。通过 Storage 事件唤醒和 Outbox 可靠发布推进状态；标准部署默认启用，RPC 为 `11430`，健康检查为 `11431`。
- **Trade**：账户、订单、成交、账本、仓位和调仓的唯一事实源。Strategy 只保存策略决策和下游关联，不复制 Trade 事实。
- **Archive**：消费 Storage 变更，维护 Journal，把数据写入 Parquet 月分区并可同步 COS；它是冷归档和恢复能力，不替代 Pebble 在线事实主存。

四个模块都是独立进程和独立 Go Module。Admin 只维护部署和路由，不转发或实现这些模块的业务逻辑；浏览器请求经本机 Gateway 访问 active、gateway-enabled 的服务实例。

### 4.9 实时流处理链路

实时行情链路统一为：

```text
Collector
  -> market.kline.closed EventMessage
  -> EventBus / NATS JetStream
  -> streamcalc event-time K 线聚合
  -> Storage DataNode 原子写入 + Outbox
  -> storage.rows.upserted EventMessage
  -> Storage View / Factor / Archive
```

`modules/eventbus` 是独立部署的 NATS/JetStream 基础设施服务，不承载业务 Handler。
业务模块只声明 Stream/Durable 并绑定 EventBus 已创建的 Consumer；Storage View 按
Dataset Subject Lane 并行处理，Backfill 与实时写通过写优先 gate 协调。

MooX 使用相互独立的浏览器控制面和节点服务数据面：

```
Browser -> 中央 Caddy -> /api/admin/* -> Admin :11000
Gateway -> 中央 Caddy -> /api/gateway-control/* -> Admin :11000

Browser/SCF -> Admin Gateway BFF -> Node Gateway native tRPC :11003
Service client --------------------^             |
                                                   +-> Metadata / PrimaryStore / DataView loopback
```

Admin 根据 `t_gateway_nodes` 和 `t_service_deployments` 为每个 `node_id` 编译完整快照。Node Gateway 默认每 15 秒拉取一次，校验 service HMAC、目标节点、时间戳和 nonce 后匹配路由。上游只允许 HTTP loopback 地址，不允许跨节点转发。

通过 `X-Space-Id` HTTP 头实现多空间数据隔离，网关层注入，业务层透明使用。

```
   │ Gateway :11002     │     │ Gateway :11002     │
   │ 本机业务服务        │     │ 本机业务服务        │
   └────────────────────┘     └────────────────────┘
```

Admin 只部署在中央控制节点。每台机器包括中央节点都运行自己的 Gateway；普通节点使用 `--no-admin`，Caddy 只暴露本机 `/api/service/*`。一个物理节点仍可把 Storage、Collector、CloudNode、Monitor、Trade 等模块作为独立进程部署。

### 单节点模式

```
┌───────────────────────────────────────────┐
│ Caddy                                    │
│ web-host + Admin                         │
│ Gateway :11002 / :11012                  │
│ Storage / EventBus / Monitor / 业务模块   │
└───────────────────────────────────────────┘
```

单节点是相同架构的特例。即使 Admin 与业务服务同机，`/api/service/*` 仍经过独立 Gateway，避免形成两套运行模型。

## 8. 安全与鉴权

### 鉴权层级

```
浏览器 ──HTTPS + JWT + request HMAC──▶ 中央 Caddy ──▶ Admin:11000
Gateway ──HTTPS + control HMAC───────▶ 中央 Caddy ──▶ Admin:11000
机器调用方 ──HTTPS + service HMAC────▶ 节点 Caddy ──▶ Gateway:11002
```

| 鉴权方式 | 适用场景 | 机制 |
|----------|----------|------|
| JWT + 会话请求 HMAC | 浏览器 → `/api/admin/*` | 24 小时 session，签名原始 body，时间戳 + nonce 防重放 |
| control HMAC | Gateway → `/api/gateway-control/*` | 独立 control key，绑定目标节点和 nonce |
| service HMAC | 后台服务/SCF → `/api/service/*` | 独立 service key，通过节点 Caddy HTTPS |
| health HMAC | Monitor → 内部诊断端口 | 独立凭据，缺失/重放返回 `401` |

### 数据隔离

- **产品边界**：MooX 是个人单用户系统，唯一登录用户拥有全部管理能力。
- **认证边界**：浏览器请求必须通过登录会话、JWT、请求 HMAC 与 nonce 防重放；后台和诊断面使用各自独立 HMAC。
- **不采用 RBAC**：当前不新增 `SUPER_ADMIN` 角色表、权限表或资源级 ACL。只有出现第二个真实用户后才重新评估。
- **Space 归属**：`X-Space-Id` 用于区分数据空间和路由上下文，不代表已实现多租户安全隔离。

## 10. 构建与发布

### Makefile 命令

| 命令 | 说明 |
|------|------|
| `make build` | 编译所有模块二进制到 `bin/` |
| `make check-boundaries` | 检查模块依赖边界 |
| `make test` | 遍历 Go Workspace 测试和 vet，并测试、构建管理台 |
| `make verify` | 执行边界、后端、前端、文档和发布契约完整验证 |
| `make deploy ARGS="..."` | 部署到目标环境 |
| `make release` | 打包发布 |
| `make proto` | 生成 proto 代码 |
| `make clean` | 清理构建产物 |

### 构建脚本

`scripts/` 目录下存放具体脚本，由 Makefile 调用：

- `build.sh` — 多平台编译（darwin/linux × amd64）
- `deploy-moox.sh` — 部署到远程节点
- `release.sh` — 打包发布产物
- `build-collector-scf-package.sh` — 打包 collector SCF 运行包
- `check-module-boundaries.sh` — 检查模块依赖边界
- 其他运维脚本

### 发布产物

`release/` 目录按平台和架构组织：

```
release/
├── deploy-stage/              # 部署暂存
├── moox-dev-darwin-amd64/     # macOS 开发版
└── moox-dev-linux-amd64/      # Linux 开发版
```
