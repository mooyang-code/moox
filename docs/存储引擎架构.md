# Storage 架构设计

本文描述 storage 模块当前落地的架构。更完整的概念定义、元数据表结构和协议设计见仓库根目录：

- `存储概念与设计意图.md`
- `存储目标架构与元数据.md`
- `协议设计.md`
- `存储服务架构与部署.md`

## 设计目标

storage 服务在同一套元数据与访问入口下，统一承接多种形态的金融数据：

- 在线时序数据：tick、K 线、行情快照。
- 静态结构化数据：公司信息、证券基础资料、交易对资料。
- 动态因子结果：MA20、MA60、RSI14 等。
- 文本数据：公告、新闻、公司简介。
- 冷数据与备份：历史行情归档。

核心原则：**所有数据访问都先进入 Access Service**。Access 按请求语义把请求编排到 PrimaryStore、DataView 和 Archive 等内部能力上。对外协议只暴露 Space/Dataset/Subject/View 等业务概念，不暴露物理表名、分片和具体存储引擎。

## 分层与代码组织

```text
proto/             # tRPC/protobuf 协议定义与生成代码（对外契约）
schema/            # 元数据 SQL 表定义
config/            # 部署配置（trpc_go.yaml 框架配置，storage.yaml 业务配置）
cmd/server/        # moox-storage：装配服务、注册 tRPC service 与 timer
cmd/cli/           # moox-storage-cli：初始化 metadata schema，导入 seed
cmd/bench/         # 本地压测入口
internal/
  config/          # 运行配置加载（RuntimeConfig）
  core/            # 领域抽象与纯业务规则（不依赖具体设备）
    eventbus/      # 业务事件总线抽象和测试用 MemoryBus
    factkey/       # 事实主键/维度编码
    metadata/      # 元数据存储接口（Store / Reader）
    router/        # PrimaryStoreTarget 路由解析器
    schema/        # 写入列契约校验器
    factvalue/     # TypedValue 处理、时间/过滤/排序/分页通用工具
    response/      # RetInfo 构造（统一错误码与响应）
  infra/           # 底层实现
    device/        # 存储设备驱动层
      pebble/      #   在线事实主存（KV，时序/点查）
      duckdb/      #   视图物化结果（OLAP，必须启用 CGO）
      bleve/       #   全文索引
      parquet/     #   冷归档文件
    metadata/
      sqlite/      #   元数据控制面实现
      cache/       #   元数据读快照（snapshotcache）
    eventbus/      # JetStream producer、durable consumer 与 ACK/NAK 控制
  service/         # 可独立部署/调度的服务层
    access/        #   唯一公开数据访问入口
    primary/       #   在线事实主存服务（local / remote client）
    view/          #   DataView 查询、ViewBuilder、DuckDB/Bleve
      builder/     #   行变更事件消费与 View 增量派生
      search/      #   Record View 的 Bleve 索引和搜索
    archive/       #   Parquet 归档服务
```

分层约束：

- `service/access` 是唯一公开入口，负责 tRPC 协议编排、写入校验、路由解析与请求转发。
- `service/primary`、`service/view`、`service/archive` 是内部执行角色，可独立部署，也可在同进程内装配。`service/view/search` 是 view 角色内部能力，不是独立部署服务。
- `infra/device` 是设备驱动层，所有具体存储引擎实现集中于此。
- `core` 与 `infra` 不直接作为服务启动，只作为上层服务依赖的领域抽象和底层实现。

## Runtime Roles

`cmd/server` 由 `storage.roles` 选择本进程启用的运行角色：

| 角色 | 职责 |
| --- | --- |
| `access` | 面向用户的写入和权威读取入口；校验列契约、解析路由、写 PrimaryStore，并发布行变更事件。 |
| `primary` | 拥有 Pebble PrimaryStore RPC；可按路由和配置部署多个 primary 服务。 |
| `view_index` | View 物理索引 owner，唯一拥有 DuckDB/Bleve 路径，提供创建、写入、查询、引用排空和删除 RPC。 |
| `view_builder` | durable 消费行更新，通过 Access 回读并写 ViewIndex；维护 rebuild cursor/lease，追平后原子激活。 |
| `view_query` | 注册 DataView，读取 `active_index_id` 和 schema 后通过 ViewIndex 查询。 |
| `view` | 标准 View 服务角色，在一个进程内组合 `view_index + view_builder + view_query`，内部仍保持 owner、物化和查询边界。 |
| `archive` | 注册 archive timer，消费行变更事件，通过 Metadata/Access RPC 读取元数据和事实数据；后续写 Parquet 冷归档。 |

组合配置 `storage.yaml` 用于本地 `access + view` 开发；标准部署启动 `storage-access` 和 `storage-view` 两个独立进程。`storage-view` 只读取自己的 `storage_view/trpc_go.yaml`，该文件同时包含 tRPC 和 View 业务配置。如果 `access` 角色的 `storage.primary.service_name` 为空，进程也会暴露本地 `PrimaryStoreService`；如果该字段非空，Access 通过远程 PrimaryStore RPC 写读，除非同时显式启用 `primary` 角色。

仓库和标准部署默认使用 `eventbus.type: jetstream`，连接独立 `moox-eventbus`；Storage 进程不内嵌 NATS。`MemoryBus` 只用于单元测试和显式的进程内装配。无论使用哪种实现，派生结果都异步生成，不提供写后立即可查契约。ViewBuilder 配置项包括：

DataView 只随 `view` 角色启动。`access` 角色不打开 DuckDB/Bleve View 存储，避免跨进程部署时与 view builder 争抢 DuckDB 文件锁，也避免 view builder 绕过 AccessService 理解 PrimaryStore 路由。

| 字段 | 含义 |
| --- | --- |
| `view.access_service_name` | View/Archive 回读当前事实行使用的 Access 服务名；留空时使用同进程本地 Access reader。 |
| `view.batch_size` | 单批最多聚合的变更 key 数。 |
| `view.batch_wait_ms` | 未达到批大小时的最长等待时间。 |
| `view.max_workers` | TimeSeries 与 Record 各自的并发处理 worker 数。 |

## 核心概念

| 概念 | 含义 |
| --- | --- |
| Space | 业务命名空间，其下所有概念唯一性都限定在 Space 内 |
| DataSource | 数据来源（交易所、行情接口、文件导入、内部计算） |
| Subject | 数据对象（交易标的、榜单、新闻源、账户等），交易标的只是其中一种 |
| SubjectSymbol | Subject 在某个 DataSource 下的外部代码映射 |
| Dataset | 可写事实数据集，定义一类数据及其列契约，绑定唯一 DataSource |
| DatasetColumn | Dataset 下允许写入/读取的列，可声明 required 等写入契约 |
| Field / Factor | Space 内的字段字典 / 已参数化因子定义，进入 Dataset 即成为 DatasetColumn |
| View | 用户查询入口，也是可异步物化的结果定义；查询不存在的 View 返回 `VIEW_NOT_FOUND` |
| ViewColumn | View 对用户暴露的列 |
| PrimaryStoreNode / Device | 在线主存节点 / 底层存储设备 |
| PrimaryStoreRoute | 在线事实主存的水平切分路由 |
| ArchiveFile | 从 Pebble 归档出来的 Parquet 事实文件记录 |

## 存储组件职责

| 组件 | 角色 | 说明 |
| --- | --- | --- |
| SQLite | 元数据控制面 | 保存全部元数据（Space/DataSource/Subject/Dataset/Field/Factor/View/PrimaryStoreNode/Device/PrimaryStoreRoute/ArchiveFile）。元数据 CRUD 直接读写 SQLite。 |
| snapshotcache | 服务侧元数据读快照 | Access 的校验、路由、Search 列解释等**读路径**使用快照（`infra/metadata/cache`）。CRUD 不在写时更新缓存；启动加载与周期刷新（默认 10s）由 snapshotcache 负责。 |
| Pebble | 在线事实主存 | 由 PrimaryStore 管理，承接事实数据写入；内部按时序 `t|` 与记录 `r|` 两类 key 空间保存，支持低延迟写入、时间范围读取、记录按 `record_id/version` 读取、截面最新读，区间读支持游标分页。 |
| DuckDB | TimeSeries View 结果 | 由 View 管理，按 `view_version` 保存版本化物化结果供 `QueryTimeSeriesRows` 读取；结果表名以 `view_{view_id}` 开头，按 `ViewColumn` 展开为 `dataset_id.column_name` 物理列，并为行键、`subject_id + freq + data_time`、各视图字段建索引；必须使用 `CGO_ENABLED=1` 的真实磁盘 DuckDB 实现。 |
| Bleve | Record View 索引 | 由 Search 管理，按 `view_version` 保存版本化全文索引供 `SearchRecordRows` 读取；索引字段由 ViewColumn 决定。 |
| Parquet | 事实冷备 | 由 Archive 管理，只从 Pebble 事实主存归档，不从 DuckDB 物化结果归档。 |

## 写入链路

```text
AccessService.WriteTimeSeriesRows / WriteRecordRows
  -> schema.Validator        读 metadata cache：校验 Dataset 与列契约
  -> router.Resolver         读 metadata cache：解析 PrimaryStoreTarget（可按 dataset/subject 分组）
  -> service/access          调用 primary.Client（local 或 remote）
  -> Pebble fact store        原子写入事实行与发布 Outbox
  -> primary.OutboxRelay      重试发布 rows_updated 事件到 JetStream
  -> service/view/builder     durable 消费、异步回读并写 DuckDB / Bleve
```

要点：

- **事实行统一模型为 `space_id + dataset_id + data_key + version`**：同一 key 再次写入只替换本次携带的列与 attributes，未携带的旧列保留；写入协议不提供整行删除或范围清空语义，底层不用 `DeleteRange` 做范围清空。
- **时序数据与记录数据对外分开表达**：时序数据必须是固定 `subject_id + freq` 下按 `data_time` 演进的数据，例如 K 线；其逻辑 `data_key=subject_id|freq|dimhash`，`version=data_time`。非固定 `subject_id + freq` 的数据都归为记录数据，即使有时间线（新闻、研报、榜单版本），也通过 `record_id + version` 表达。
- **Pebble 物理 key 空间区分数据形态**：时序使用 `t|space|dataset|data_key|version`，记录使用 `r|space|dataset|data_key|version`。其中时序 `data_key=subject_id|freq|dimhash`，记录 `data_key=record_id`。`TimeRange` 的边界时间统一解析 RFC3339/RFC3339Nano，并归一化为 UTC 固定 9 位纳秒，保证 key 字典序与时间序一致。
- **事实行与发布意图原子提交**：本地 Pebble 写入会在同一 batch 中保存事实行和发布 Outbox；Outbox 超出行数、字节数或年龄上限时写入失败，避免在失去可靠发布能力后继续制造不可追踪差异。JetStream 临时不可用不会丢事件，relay 按退避重试并只删除已确认发布的 Outbox。
- **派生层异步完成**：Search/View/Archive 失败不回滚已经成功的主存事实，但 durable 消息不会被 ACK；重投、View rebuild 和归档任务负责补偿，因此不承诺写后立即可查。
- **跨 target 非原子**：Access 按路由把同一批 rows 分组写入多个 `PrimaryStoreTarget`。`PrimaryStoreTarget` 是内部执行目标，不是事务边界；某 target 失败不回滚已成功 target，且仍会为已成功写入的 rows 发布变更事件，让派生侧追上成功部分。

### 事件总线

- `core/eventbus` 是上层业务事件抽象，定义时序和记录行更新事件以及进程内测试实现。
- `infra/eventbus` 使用共享 `packages/jetstream` 实现生产发布、durable pull consumer、并发上限、in-progress heartbeat、ACK/NAK 和投递指标。
- `service/primary` 的 Outbox relay 发布完整 `MooxMessage`；`service/view/builder` 只在派生完成后确认投递。

行变更事件只携带发生变更的用户侧 key，不要求携带完整行。派生消费者收到事件后，必须**通过 Access 读接口回读最新完整行**再覆盖写入派生结果；消费者不直接请求某个 `PrimaryStoreTarget`，也不理解分片/路由/设备细节，从而保证消费重试幂等、Access 始终是唯一访问入口。

部署形态：

- 生产 `infra/eventbus.SubscriberBus` 分别订阅 `${prefix}.time_series.rows_updated.v1` 与 `${prefix}.record.rows_updated.v1`，使用 `storage_view_builder_time_series_rows_updated_v1` 和 `storage_view_builder_record_rows_updated_v1` 两个 durable，避免不同 subject 共用消费进度。
- JetStream durable 会恢复未确认和离线期间保留的事件；超出 stream retention 的历史补仓、完整断档修复和读模型重建统一通过 View rebuild 完成。
- 事件 subject 统一前缀默认 `moox.storage`，时序行更新默认 `moox.storage.time_series.rows_updated.v1`，记录行更新默认 `moox.storage.record.rows_updated.v1`；stream 使用 `moox.storage.>` 通配。
- ViewBuilder handler 只有在 DuckDB/Bleve 派生写入成功后才返回 success。处理失败会向上传递错误，transport 对消息执行 `Nak` 并由 JetStream 重投；处理时间较长时定期发送 in-progress，避免 `ack_wait` 到期造成并发重复处理。

## 查询链路

```text
ReadTimeSeriesRows : Access -> router -> primary.Client -> Pebble
ReadRecordRows     : Access -> router -> primary.Client -> Pebble
SearchRecordRows   : Access -> Search Service -> Bleve
QueryTimeSeriesRows: DataView -> ViewIndex owner -> DuckDB active_index_id
```

- `ReadTimeSeriesRows` 使用 `TimeSeriesKey + TimeRange` 读取固定 Subject/Freq 下的时序数据。`TimeRange` 是闭区间 `[start_time, end_time]`，两端为空表示无界；时间格式必须是 RFC3339/RFC3339Nano。
- `ReadRecordRows` 使用 `RecordKey + VersionRange` 读取记录数据。`VersionRange` 是闭区间 `[start_version, end_version]`，两端为空表示无界。
- `SearchRecordRows` 查询 Record View 的 active Bleve 索引，不走路由，也不 fan-out 到多个 Pebble 分片；支持全文 `text_query` 与结构化过滤。
- `QueryTimeSeriesRows` 只查询 TimeSeries View 的活动 DuckDB 槽位；没有可用 `active_index_id` 时返回 `VIEW_NOT_FOUND`。`time_range`、`subject_id`、`freq`、filter、sort、limit 与分页下推到 owner 内的 DuckDB。
- `RebuildTimeSeriesView` / `RebuildRecordView` 异步受理并返回 `rebuild_id`，后台按当前 `view_version` 从 PrimaryStore 全量扫描构建新结果；构建期间事件消费者会同时写 active 与 building 结果，确保切换后包含构建期增量。

## 元数据控制面与缓存

- 元数据 CRUD（Create/Update/Get/List）直接读写 SQLite，读自身写入立即一致。
- Access 的**数据面读路径**（路由解析和写入校验）走 snapshotcache 快照，默认每 10s 刷新一次。因此新建路由/列契约后，写读路径可见前存在短暂延迟，运行链路验证时需要等待快照刷新。

## 路由与水平分片

`router.Resolver` 依据 `PrimaryStoreRoute` 把 `space_id + dataset_id + subject_id` 解析为 `PrimaryStoreTarget`。路由可按精确 `subject_id`、`subject_pattern`、哈希规则匹配，并带优先级。`PrimaryStoreTarget` 描述目标节点、引擎与设备表，是内部执行目标，对上层不可见。

Metadata 表结构由 `moox-storage-cli init --storage-conf ... --schema-path ...` 在服务启动前创建；示例元数据由 `moox-storage-cli import-seed ...` 导入。`moox-storage` 服务启动只打开运行配置和存储设备，不执行 schema 迁移。

## 派生与后台调度

`cmd/server` 启动时按 `storage.roles` 装配 Access、PrimaryStore、ViewBuilder 与 View 查询服务，并注册 tRPC timer handler：

| Timer | 调度器 | 行为 |
| --- | --- | --- |
| `trpc.moox.storage.view.timer` | `viewBuilderSchedule` | `op=maintain` 驱动有租约、可续跑的 a/b 槽位构建；成功后 CAS 切换 `active_index_id` |
| `trpc.moox.storage.host_metrics_cleanup.timer` | `DefaultScheduler` | 每小时清理四个 Host Dataset 中严格早于 48 小时的事实；启动时立即执行，单次超时 60 秒 |

说明：

- 使用官方 tRPC timer；cron network 只保留 `scheduler`、`startAtOnce` 和 `holdTime`。业务参数由 bootstrap 绑定或通过业务 API 传入，禁用的任务不写入 service 列表。
- View 构建使用 SQLite 条件更新和 owner lease，多个 builder 只能有一个持有者；崩溃后从持久化 cursor 续跑。失败或构建中的结果不会改变 `active_index_id`，只有 `ActivateViewIndex` 成功后才切读。
- Host 指标清理每数据集最多执行 10 批，每批每个解析后的 PrimaryStore target 最多删除 1000 行，遇到空页提前结束。单个数据集失败不阻断其他数据集，最终返回汇总错误。Handler Clone tRPC Context、同步等待并跳过同进程重入。
- `DefaultScheduler` 只提供单进程调度，不提供跨副本互斥；多副本部署必须指定单一清理 owner 或接入分布式 scheduler。

## 动态字段与因子

Field 和 Factor 都是 Space 内字典：进入 Dataset 统一成为 `DatasetColumn`，进入 View 统一成为 `ViewColumn`。因子参数是 Factor 定义的一部分：

```text
factor_id   = ma20_close
algorithm   = MA
params_json = {"window":20,"price":"close"}
```

新增因子时只新增 Factor 及对应列，不要求在线事实主存改 schema。

## 部署形态

- 单进程开发可显式使用 `roles: [access, view]`、`primary.service_name: ""` 和 `eventbus.type: memory`；`access` 同时暴露本地 `PrimaryStoreService`，组合 view 角色仍异步派生。
- 标准生产部署连接独立 `moox-eventbus`，启动顺序为 `storage-access -> storage-view`。`storage-view` 是 DuckDB/Bleve 物理目录的唯一进程 owner，Builder 和 Query 在进程内通过 LocalClient 访问 ViewIndex owner，并保留与远程 RPC 相同的写入 fence。
- 多机主存可单独启用 `primary`，让 Access 使用远程 `primary.service_name`；Archive 使用独立 `modules/archive` 服务消费事件和写 Parquet/COS。
- 跨进程 ViewBuilder 必须使用 JetStream，不能使用 memory；所有进程连接同一个由 `moox-eventbus` 管理的 NATS，不在 Storage 内嵌 broker。
- 运行配置由 `internal/config.RuntimeConfig` 加载，覆盖角色、元数据路径、各设备目录、primary 服务名、eventbus 类型和 view builder 批处理参数。
