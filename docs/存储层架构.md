# 存储层最终架构

本文是当前 Storage 代码的架构事实源，描述最终的职责边界和数据流。

## 业务 Schema 约束

MooX 面向个人量化交易，Dataset Schema 采用 Append-only 模型：

- 已有字段永不删除。
- 已有字段的 `field_id` 永不修改，也不会被其他字段复用。
- 已有字段的 `value_type` 永不修改。
- 已有字段的 Required 属性永不修改。
- Schema 变更只允许追加 Optional 字段；Required 字段只允许在 Dataset 创建时定义。
- 系统不实现字段删除、类型迁移、新旧字段双读或双写兼容。

Schema 变化不在运行中热更新。Storage 明确拒绝受影响 Dataset 的写入，由用户重新部署 PrimaryStore 和对应事实存储进程。View 使用非活跃 Index 后台重建；旧 Active Index 在切换前持续提供查询，新字段只在 Index 和 View Revision 原子切换后可见。

该业务约束的简化目标和多进程部署设计见 [Storage Dataset 单归属与多进程简化设计](superpowers/specs/2026-07-19-storage-dataset-node-simplification-design.md)。

## 数据流

```text
Browser
  -> Admin Gateway /api/admin/storage/{method}
  -> Node Service Gateway tRPC
  -> Metadata | PrimaryStore | DataView

Go Service
  -> Node Service Gateway tRPC
  -> Metadata | PrimaryStore | DataView

PrimaryStore
  -> DataShard
  -> Pebble + Outbox（同一 Batch）
  -> TimeSeriesRowsCommitted | RecordRowsCommitted
  -> ViewBuilder
  -> RowMapper
  -> ViewIndex.Apply
  -> DuckDB / Bleve

RowsCommitted UPSERT -> Archive Journal / Parquet / COS
RowsCommitted DELETE  -> ViewIndex DELETE
RowsCommitted DELETE  -> Archive ACK（忽略，不删除历史）
```

浏览器不保存 Storage 物理地址，也不能绕过 Admin Gateway。服务间调用者使用独立的 Service HMAC 凭证进入目标节点的 Node Service Gateway；Gateway 依据服务方法和 Caller ACL 选择本机 loopback 上游。Admin Gateway 只负责用户会话、静态方法白名单、JSON BFF 适配和受信转发，不复制 Storage 业务校验。

## 服务归属

| 服务 | 唯一职责 | 持有的状态 |
| --- | --- | --- |
| Metadata | 目录、Schema、View 定义和 Shard 拓扑 | SQLite 与小型目录缓存 |
| PrimaryStore | 事实校验、Merge、路由、跨 Shard 聚合和受控扫描 | 不直接持有 Pebble |
| DataShard | 固定 Shard 身份下的物理事实读写、Sequence 和 Outbox | 一个 Pebble 数据目录 |
| DataView | 活动 View 的公开查询 | 不直接写事实主存 |
| ViewBuilder | RowsCommitted 有序消费、RowMapper、缺行恢复和物化 | 消费进度协调 |
| ViewIndex | View 写入协议及物理索引生命周期 | DuckDB/Bleve 文件和 Checkpoint |
| Archive | 白名单事实的历史归档 | Journal、Parquet 和 COS |

Storage 默认只部署 `storage-primary` 与 `storage-view`。需要容量分片时，可在私网单独部署带固定 `shard_id` 的 DataShard；本计划不实现副本、自动故障转移、迁移、再平衡或跨分片事务。

## 一致性边界

- DataShard 在同一 Pebble Batch 中提交事实行、Outbox 和本 Shard 连续 Sequence；写入未完成前请求失败。
- Outbox 只能删除从队首开始连续发布成功的前缀。失败项及其后继必须保留并重放。
- `TimeSeriesRowsCommitted` 和 `RecordRowsCommitted` 共用该 Shard 的 Sequence Lane，携带完整 Merge 后事实快照。
- ViewBuilder 对同一 Shard 保序、对同一 `ViewRowKey` 串行；ViewIndex 只接受明确的 `MERGE`、`REPLACE`、`DELETE`。
- 稳态 MERGE 只覆盖消息来源 Dataset 拥有的列。目标行缺失时原子批次不推进 Checkpoint，Builder 批量回读全部来源后以完整 `REPLACE` 重试。
- ViewIndex 写入和 Shard Checkpoint 在同一 Apply 中提交，并使用 `ExpectedLastAppliedSequence` CAS；`ViewVersion + ViewSchemaHash` 拒绝过期构建。
- `indexed_from/indexed_to` 使用 UTC RFC3339Nano，分别解释 TimeSeries 的 `data_time` 与 Record 的时间化 `version`；普通增量写入不能自行扩大查询范围。
- View Delete 删除在线 DuckDB/Bleve 行；Archive 忽略 Delete 并保留已归档历史。

## 目录和拓扑限制

事实 Key 只属于一个固定 DataShard。首次写入前 PrimaryStore 锁定 Dataset 的 Shard 拓扑哈希；节点、Hash Pool、权重和路由规则的修改如果会改变既有 Key 的放置位置必须失败。DataShard 验证请求中的 `shard_id`、Space、Dataset 和 Key 一致，不能被调用者通过物理地址、任意 Node 或 Engine 静默绕过。

Metadata 的列表接口使用确定性 SQL 分页；缓存只保存小型目录、Schema 和 Shard 路由，不把持续增长的 ArchiveFile 或构建历史读入全量快照。SQLite 的 `created_at/updated_at` 是唯一时间事实源。

## 磁盘治理

Host Metrics 保留 48 小时，并以每次最多 10 批、每批 1000 条、超时和防重入的清理任务执行。Pebble 通过 Compaction 管理在线事实，DuckDB/Bleve 的 A/B 重建需要额外临时空间，Archive 的 Parquet/COS 按历史保留策略永久保存，三者不能互相冒充清理策略。
