# 存储层最终架构

本文是当前 Storage 代码的架构事实源，描述最终的职责边界和数据流。

## 业务 Schema 约束

MooX 面向个人量化交易，Dataset Schema 采用 Append-only 模型：

- 已有字段永不删除。
- 已有字段的 `field_id` 永不修改，也不会被其他字段复用。
- 已有字段的 `value_type` 永不修改。
- 所有字段都允许缺失；系统不定义 Required 字段。
- Schema 变更只允许追加字段。
- 系统不实现字段删除、类型迁移、新旧字段双读或双写兼容。

Add Field 在 SQLite Commit 和 PrimaryStore DatasetSchema 指针替换后才返回成功；此后新字段立即可写，既不中断已有写入，也不需要重启或重新部署。DataNode 不感知业务 Schema；字段归属和类型只由 PrimaryStore 入口校验。View 使用非活跃 Index 后台重建；旧 Active Index 在切换前持续提供查询，新字段只在 Index 和 View Revision 原子切换后可见。

该业务约束的简化目标和多进程部署设计见 [Storage Dataset 单归属与多进程简化设计](superpowers/specs/2026-07-19-storage-dataset-node-simplification-design.md)。

## 数据流

```text
Browser
  -> Admin Gateway /api/admin/storage/{method}
  -> Metadata | PrimaryStore | DataView

Go Service
  -> direct tRPC + Service HMAC
  -> Metadata | PrimaryStore | DataView

PrimaryStore
  -> Dataset.data_node_id
  -> DataNode
  -> Pebble + Outbox（同一 Batch）
  -> TimeSeriesRowsCommitted | RecordRowsCommitted
  -> ViewBuilder
  -> RowMapper
  -> ViewIndex.Apply
  -> DuckDB / Bleve

RowsCommitted UPSERT -> Archive Journal / Parquet / COS
RowsCommitted DELETE  -> ViewIndex DELETE
RowsCommitted DELETE  -> Archive ACK（忽略，不删除历史）
```

浏览器不保存 Storage 物理地址，也不能绕过 Admin Gateway。Storage 内部进程使用独立 Service HMAC 凭证直接通过 tRPC 调用，不经过 Node Service Gateway。Admin Gateway 只负责用户会话、静态方法白名单、JSON BFF 适配和受信转发，不复制 Storage 业务校验。

## 服务归属

| 服务 | 唯一职责 | 持有的状态 |
| --- | --- | --- |
| Metadata | 目录、Append-only Schema、View 定义和 DataNode 注册 | SQLite |
| PrimaryStore | 字段校验、Dataset 到 DataNode 路由和受控扫描 | 启动时 Routing 与可原子追加的 DatasetSchema |
| DataNode | 固定 Node 身份下的通用事实 Merge、Sequence 和 Outbox | 一个 Pebble 数据目录 |
| DataView | 活动 View 的公开查询 | 不直接写事实主存 |
| ViewBuilder | RowsCommitted 有序消费、RowMapper、缺行恢复和物化 | 消费进度协调 |
| ViewIndex | View 写入协议及物理索引生命周期 | DuckDB/Bleve 文件和 Checkpoint |
| Archive | 白名单事实的历史归档 | Journal、Parquet 和 COS |

Storage 默认运行一个 `storage-primary`、一个 `storage-view` 和一个或多个带固定 `node_id` 的 `storage-node` 进程。它们可以位于同一台机器，也可以把 K 线、因子等 Dataset 按 `data_node_id` 分到不同服务器。每个 Dataset 只有一个 DataNode Owner；系统不实现 Dataset 内分片、副本、自动故障转移或迁移。

## 一致性边界

- DataNode 在同一 Pebble Batch 中提交事实行、Outbox、本 Node 连续 Sequence 和 Dataset `last_committed_sequence`；写入未完成前请求失败。
- Outbox 只能删除从队首开始连续发布成功的前缀。失败项及其后继必须保留并重放。
- `TimeSeriesRowsCommitted` 和 `RecordRowsCommitted` 共用该 DataNode 的 Sequence Lane，携带完整 Merge 后事实快照。
- ViewBuilder 对同一 DataNode 保序、对同一 `ViewRowKey` 串行；ViewIndex 只接受明确的 `MERGE`、`REPLACE`、`DELETE`。
- 稳态 MERGE 只覆盖消息来源 Dataset 拥有的列。目标行缺失时原子批次不推进 Checkpoint，Builder 批量回读全部来源后以完整 `REPLACE` 重试。
- ViewIndex 写入和 `{node_id, dataset_id}` Source Checkpoint 在同一 Apply 中提交，并使用 `ExpectedLastAppliedSequence` CAS；不大于 Checkpoint 的重投只做幂等 ACK，不回写 Index。View Revision 拒绝过期构建。
- `indexed_from/indexed_to` 使用 UTC RFC3339Nano，分别解释 TimeSeries 的 `data_time` 与 Record 的时间化 `version`；普通增量写入不能自行扩大查询范围。
- View Delete 删除在线 DuckDB/Bleve 行；Archive 忽略 Delete 并保留已归档历史。

## Dataset 和 DataNode 边界

Dataset 通过 `data_node_id` 归属一个 DataNode；一个 DataNode 可以承载多个 Dataset。系统不按 Subject、RowKey、时间、Hash Pool 或权重继续分片。Dataset 产生事实数据后，Metadata API 永久拒绝修改 `data_node_id`。MooX 不提供 Dataset 迁移；用户自行停机、复制文件或修改 SQLite 属于系统外操作。

PrimaryStore 是唯一业务字段校验入口。DataNode 不理解 Field 类型，只校验通用 TypedValue 结构、RowKey、Batch/Payload 大小和原子提交边界。Metadata 的列表接口直接使用 SQL 分页，不把 ArchiveFile 或构建历史读入全量缓存；SQLite 的 `created_at/updated_at` 是唯一时间事实源。

## 磁盘治理

Host Metrics 保留 48 小时，并以每次最多 10 批、每批 1000 条、超时和防重入的清理任务执行。Pebble 通过 Compaction 管理在线事实，DuckDB/Bleve 的 A/B 重建需要额外临时空间，Archive 的 Parquet/COS 按历史保留策略永久保存，三者不能互相冒充清理策略。
