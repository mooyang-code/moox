# 因子视图驱动计算设计

> 状态：评审稿（2026-08-07）
> 关联文档：《因子计算模块设计.md》《存储层架构.md》《内置市场行情采集架构.md》

## 1. 背景与动机

当前因子计算的触发链路是**行事件驱动 + 启发式等待**：

1. DataNode outbox 逐批发布 `DatasetRowsUpserted` 行事件；
2. Factor 的 `EventBatcher` 以 2 秒固定窗口批合行事件，猜测"这一批写完了"；
3. 调度器执行前固定 sleep `ViewSettleDelay`（300ms）+ 失败重试 3 次，猜测"视图索引追上了"；
4. 读到数据后对 `[T, T+lookback-1]` 做前向传播重算，防御"任何历史行随时可能被 upsert 修订"。

这套机制的系统性问题：

- **无因果保证**：sleep/重试都是对视图延迟的启发式猜测，慢视图场景下仍会以不完整数据出值（`ErrViewIncomplete` 三次后放弃）；
- **重复计算放大**：每批行事件都触发 `lookback` 长度的前向重算，1m 频率 × lookback=200 的因子每天重复计算量巨大；
- **事件量与价值不匹配**：因子真正关心的是"本周期数据齐了"，却消费了全部行级事件；
- **契约错位**：因子绑定在数据集上，但读路径实际走视图，两侧概念不一致，元数据校验被迫做"视图投影是否覆盖数据集列"的间接推断。

## 2. 设计目标与非目标

### 2.1 目标

- 因子计算只面向**数据视图（View）**，不理解底层数据集；
- 触发链路改为**周期就绪信号驱动**：采集完成 → 数据集周期就绪 → 视图周期就绪 → 因子计算，每一环都是因果信号而非启发式；
- **周期终态语义**：`ready(T)` 发出时，周期 T 的输入数据在视图中已终态且可读，因子每个周期只计算一次（带 lookback 历史上下文）；
- 因子结果"向视图写入"，内部路由到绑定时自动创建并关联的结果数据集；
- 支持多数据集聚合视图的就绪判定（AND 语义，一期即支持）；
- 周期内部分标的采集失败时**超时降级**：宽限期后照常发 ready 并附失败清单，保时效。

### 2.2 非目标

- 不改变 DataNode 写入链路与行事件的既有语义（视图索引仍靠行事件驱动）；
- 不改变因子 Python 执行器与沙箱契约（`lookback`、`input_columns`、`outputs` 结构不变）；
- 一期不做因子级联 DAG（`dataset_role=factor_result` 禁止作为输入源的约束保留）；
- 历史补数（catchup / `moox-cli storage import`）不发周期信号，走既有 `RecalcFactor` RPC 补算。

## 3. 总体设计

### 3.1 三级信号链

```
Collector（采集侧）                Storage（存储侧）                     Factor（因子侧）
─────────────────                ─────────────────                     ────────────────
周期 T 的采集批次全部终态
（含超时降级判定）
  │ ReportDatasetPeriodCollected
  ▼
                            DataNode 将周期 marker 追加到
                            本空间 outbox（与行事件同序）
                              │ DatasetPeriodCollected
                              ▼
                            View 串行消费行事件+marker：
                            行事件先落索引，再登记就绪[T]
                            全部输入数据集到齐？
                              │ ViewPeriodReady(view, T)
                              ▼
                                                                  按 view 匹配 enabled 绑定
                                                                  每 subject：读 [T-lookback+1, T]
                                                                  compute → 写结果数据集
                                                                  推进绑定水位（持久化自愈）
```

**关键不变式**：`ViewPeriodReady(view, T)` 发出时 ⇒ 视图 Active 索引已包含周期 T 的全部输入行。该不变式由两个机制联合保证：

1. **有序 marker**：周期 marker 由 DataNode 经 outbox 追加，与该行事件共用同一 outbox 序列，JetStream 发布顺序即写入顺序（collector 只上报，不直接发事件）；
2. **串行消费**：View 角色单线程按序消费（`Fetch(1)`、`MaxAckPending=1`），处理到 marker 时此前的行事件必然已应用。

### 3.2 周期终态语义与前向传播的删除

`ready(T)` 意味着 T 的输入已终态，而因子输出 `output(T)` 只依赖 `input(≤T)`，因此：

- **正常路径**：每周期只算 `[T, T+1)` 一个 period，读取窗口 `[T-lookback+1, T]` 提供历史上下文；
- **修订路径**：交易所重述历史 bar 或补数覆盖旧周期 T' 时，由采集侧/导入方重新上报 T' 的周期信号，因子对 `[T', min(T'+lookback-1, 已算水位)]` 做范围重算（幂等 upsert 覆盖）。前向传播只存在于修订路径，不再是每次触发的默认行为。

## 4. 事件协议

在 `packages/events/registry.go` 按既有 `declareEvent` 模式新增两个事件，subject 模板沿用 `moox.<name>.v<N>.<space>.<subject>`：

| 事件 | 版本 | Stream | Owner | Subject | 载荷 |
|---|---|---|---|---|---|
| `storage.dataset.period.collected` | v1 | `MOOX_STORAGE` | storage | `<space>.<dataset_id>` | `DatasetPeriodCollected` |
| `storage.view.period.ready` | v1 | `MOOX_STORAGE` | storage | `<space>.<view_id>` | `ViewPeriodReady` |

proto 定义（放入 `packages/storagepb`，与 `DatasetRowsUpserted` 同包）：

```protobuf
// 数据集单周期采集就绪信号。由 DataNode outbox 发布，保证与同数据集
// 行事件的因果顺序：消费者见到本事件时，该周期已提交的行事件必先于它到达。
// 计数类观测信息由采集侧指标承担，事件契约保持最小。
message DatasetPeriodCollected {
  string dataset_id = 1;
  string frequency = 2;
  int64 period_time = 3;                  // 周期起始时刻，UTC epoch 秒，按 frequency 网格对齐
  string status = 4;                      // complete | degraded
  repeated string failed_subjects = 5;    // degraded 时非空
  string source = 6;                      // realtime | manual | restatement
  google.protobuf.Timestamp collected_at = 7;
}

// 视图单周期就绪信号。发出时视图 Active 索引已含该周期全部输入行。
message ViewPeriodReady {
  string view_id = 1;
  string frequency = 2;
  int64 period_time = 3;
  repeated ViewPeriodDatasetReady datasets = 4;
  google.protobuf.Timestamp ready_at = 5;
}

message ViewPeriodDatasetReady {
  string dataset_id = 1;
  string status = 2;                      // complete | degraded
  repeated string failed_subjects = 3;
}
```

设计要点：

- 两个事件的 owner 都登记为 **storage**（发布者是 DataNode/View），collector 不直接持有事件发布权，这是有序 marker 不变式的前提；
- `period_time` 用 int64 epoch 秒而非字符串，避免时区/格式歧义；`frequency` 冗余携带便于消费方快速过滤；
- `DatasetRowsUpserted` 行事件保持不变，Factor 不再订阅它。

## 5. 采集侧：周期就绪追踪

### 5.1 现状复用

Collector 已具备周期对齐调度（`domain/schedule.go` 的 `ScheduleDecision`）、批次状态机（`FetchBatch`：`planned/dispatched/succeeded/partial_failed/failed/timed_out`）、批次完成事件（`MarketFetchBatchCompleted`，逐 item 携带 `subject_id/target_data_time/outcome`）与 deadline 兜底恢复。

### 5.2 周期就绪聚合

新增组件**周期就绪追踪器（PeriodReadinessTracker）**（collector 内部）：

1. 消费 `MarketFetchBatchCompleted`（已有 consumer 位置），按 `(space_id, dataset_id, frequency, period)` 聚合，period 由 item 的 `target_data_time` 对齐到 frequency 网格得出；
2. 每个周期的**预期批次集合**从批次计划表获得（计划时已落库），就绪状态持久化到 collector sqlite（见 §8.3），重启可恢复；
3. 当预期批次全部到达终态：
   - 全部成功 → 以 `complete` 上报；
   - 存在永久失败 → 以 `degraded` 上报，附 `failed_subjects`；
4. **超时降级**：周期收盘价 + 宽限期（`period_ready_grace`，按 frequency 配置，默认 `2×freq`，上限 10m）到达仍未齐，强制以 `degraded` 上报，失败清单 = 未终态批次的标的并集；
5. 上报方式：调用 Storage Access 新 RPC `ReportDatasetPeriodCollected`，由存储侧落 outbox；
6. **迟到修订**：任何对历史周期 T' 的成功写入（重试补采、人工补录）触发对 T' 的再次上报（`source=restatement`），幂等。

### 5.3 补数路径

`BatchKindCatchup` 批次与 `moox-cli storage import` 不进入周期就绪追踪（避免历史逐周期信号打爆链路）。补数完成后由发起方调用因子 `RecalcFactor`（已有 RPC）按范围补算。导入工具在导入结束时自动发起该调用。

## 6. 存储侧：有序 Marker 与视图就绪聚合

### 6.1 ReportDatasetPeriodCollected RPC

Storage Access 新增 RPC：校验 `(space, dataset, freq)` 合法后，向该空间 DataNode 的 outbox 追加一条 **period marker 记录**（outbox 表新增 `c_kind` 列区分 `rows_upserted | period_collected`），publisher 按序发布为 `DatasetPeriodCollected` 事件。因同空间行事件与 marker 走同一 outbox 序列，因果顺序由此保证。

### 6.2 视图就绪聚合（View 角色）

View 角色的串行 consumer 扩展为同时订阅两类事件（行事件 family + `storage.dataset.period.collected` 的相关 subject），处理逻辑：

1. 行事件：维持现状，应用进 DuckDB 索引；
2. `DatasetPeriodCollected(ds, T)`：登记到**视图周期就绪表**（§8.2），键 `(space_id, view_id, period_time)`，记录各输入数据集的到达状态；
3. 当视图的全部**输入数据集**对周期 T 均已到达（此时对应行事件必然已应用，由串行序保证），发布 `ViewPeriodReady(view, T)` 并标记已发，随后清理过期的就绪记录。

关键规则：

- **输入数据集 = `dataset_ids` 中扣除 `dataset_role=factor_result` 的数据集**。因子结果数据集不参与就绪判定，否则"因子写回 → 视图事件 → 就绪判定"形成循环依赖；
- 视图的 `filter_json.freq` 即视图周期网格，`period_time` 非该网格对齐的 collected 事件直接忽略；
- ready 事件可重发（修订路径），消费方幂等；
- 就绪表定期清理：`period_time < now - keep` 且已发 ready 的行删除。

## 7. 因子侧改造

### 7.1 触发：从行事件到就绪信号

- 删除 `EventBatcher`、`factor_calc` 对 `DatasetRowsUpserted` 的订阅；
- 新增 ready consumer：按空间订阅 `storage.view.period.ready`，解码后按 `view_id` 匹配 enabled 绑定，为每个 `(binding, subject)` 生成任务进入分片队列（沿用 `subject → worker` 的串行语义）；
- subject 集合来源：视图内 `series_tag` 去重查询（ready 已保证数据可读），受绑定 `subject_mode/subjects` 过滤；
- 队列去重键从 `(binding, subject, start, end)` 变为 `(binding, subject, period)`。

### 7.2 计算：单周期 + 水位自愈

- **正常路径**：任务范围 `[T, T+1)`，读取窗口 `[T-lookback+1, T]`（视图范围查询，现状能力）；
- **水位自愈**：每个绑定持久化 `c_last_period`（§8.1）。收到 `ready(T)` 时若 `T > last+1`，先补算 `(last, T)` 的缺失周期再算 T——ready 事件丢失或因子服务停机重启后，下一个 ready 自动愈合缺口，不依赖 JetStream 重投；补算跨度超过上限（默认 1440 周期）时截断并告警，引导走 `RecalcFactor`；
- **修订路径**：`ready(T')` 且 `T' ≤ last` 时，按 §3.2 做 `[T', min(T'+lookback-1, last+1)]` 范围重算，幂等覆盖；
- 删除：`ViewSettleDelay`、`EventReadRetry`、`ExpandEndByPeriods`、水位判定与 `ErrViewIncomplete` 重试链。

### 7.3 读写契约：只见视图

- **读**：维持视图范围查询；`input_columns` 语义从"数据集列"改为**视图列名**，绑定校验从"视图投影覆盖数据集列"简化为"视图列存在"；
- **写**：调度器持 `view_id`，内部解析出该视图的因子结果数据集（绑定时创建，见 §9），走既有 `UpsertFields` 写入。因子代码与调度逻辑不出现数据集概念。

### 7.4 保留不变的机制

分片队列与 per-subject 串行、Python 执行器协议、`FactorGate` 并发门禁、启停清理时的 task_id 版本 fencing、`RecalcFactor` 手动补算 RPC。

## 9. 绑定生命周期与视图重建

### 9.1 绑定创建流程

`UpsertBinding(space, view, factor, freq, subject_scope)`：

1. 校验：视图为时序视图（`filter_json.freq` 存在且等于绑定 `freq`）；因子未禁用；`FactorGate` 门禁通过；
2. **结果数据集**：按视图派生 `factor_result__<view_id>`（替代现 `ResultDataset(sourceDataset)` 的按源派生），不存在则创建，`dataset_role=factor_result`，grain 与视图对齐；
3. **列同步**：因子输出列以 `<factor_name>__<output>` 命名登记到结果数据集，并在 `t_view_columns` 登记视图列（`origin_type=dataset_column`，`origin_id=结果数据集`）；
4. **关联视图**：将结果数据集并入 `view.dataset_ids`，`desired_view_revision + 1` → 触发既有 A/B 索引重建；
5. 响应携带视图修订状态，前端据此提示。

### 9.2 重建期间的系统行为

- 重建走既有 A/B 机制：Active 索引继续服务查询，实时事件双写 Active/New；
- **因子计算不阻塞**：结果数据集即刻可写，新周期照常计算，结果行在切换后随索引可见；
- 用户可见性：`t_view_index_builds` 携带构建状态与 `c_backfilled_rows` 进度，网关暴露后前端展示"视图重建中"徽标；
- 因子禁用不触发重建（列保留）；显式解绑触发重建以摘除结果列。

### 9.3 前端绑定页改造

- 绑定页改为**按视图分组**：列出当前空间全部时序视图（`ListViews`），每个视图卡片展示已绑定因子组（状态、lookback、水位进度），卡片内发起绑定/解绑；
- 绑定操作返回视图修订状态时，弹出提示："新增因子将触发视图索引重建，结果列在重建完成前暂不可查"；
- 视图卡片展示 `IndexBuild` 状态（构建中/切换中/就绪）。

## 11. 可靠性与边界场景

| 场景 | 行为 |
|---|---|
| ready 事件丢失 | 绑定水位自愈：下一周期 ready 触发补算缺口 |
| 视图服务重启 | 就绪状态在 sqlite，重启后续算；重启期间到达的事件由 JetStream 重投 |
| 采集 straggler | 宽限期后 degraded 降级，ready 照常发出，失败标的在因子侧按 subject 跳过（读取无数据即跳过） |
| 重复 ready（修订/重投） | 消费幂等：≤水位的周期走修订重算，>水位的正常推进 |
| 交易所重述历史 bar | 采集侧重上报该周期 → 视图重发 ready → 因子修订路径范围重算 |
| 视图重建中收到 ready | 正常计算写结果数据集；查询可见性延迟至索引切换 |
| 多数据集 straggler 放大 | 任一输入源降级后 ready 即发出（降级策略下不存在无限等待）；长期未就绪周期有就绪表可查可告警 |

- `t_factor_bindings` 直接改表（`c_source_dataset` → `c_view_id`），开发库删库重建；
- 既有按数据集派生的 `*_factor` 结果数据集废弃，绑定重建后由视图派生数据集替代；
- 删除 `EventBatcher` 及其配置项，无滚动升级窗口要求。

## 13. 实施任务拆分

1. **事件协议**：`storagepb` 新增两个 proto 消息；`events/registry.go` 注册 + 校验器；
2. **storage**：outbox 增加 `c_kind` 与 period marker 发布；`ReportDatasetPeriodCollected` RPC；View consumer 双订阅 + 视图就绪聚合 + ready 发射；
3. **collector**：PeriodReadinessTracker 聚合（消费批次完成事件、deadline 降级、上报 RPC）；schema 新表；
4. **factor**：schema 变更（绑定视图化 + 水位表）；ready consumer 替换行事件链路；单周期计算 + 水位自愈 + 修订重算；写路径视图化；
5. **registry/metadata_sync**：绑定流程改造（结果数据集派生、列同步、视图关联与修订触发）；
6. **前端**：绑定页按视图分组、重建状态展示与提示；
7. **清理**：删除 `EventBatcher`、settle/retry 配置、`ExpandEndByPeriods` 调用链、废弃的结果数据集派生逻辑；
8. **端到端验证**：K 线采集 → ready → 因子出值 → 视图可查；降级、修订、自愈三类故障注入演练。

## 14. 开放问题

1. **每周期 per-subject 读放大**：500 标的 × 每周期一次范围读，视图查询 QPS 随标的数线性增长。一期按现状接受；二期评估"单查询取全 tag + 内存分组"的 cohort 模式（Scheduler 已预留该演进空间）。
2. **多视图共用同一结果数据集**：当前按视图派生独立结果数据集，简单清晰但数据集数量随视图数增长；若后续视图爆炸再评估合并策略。
3. **跨空间视图**：`t_views` 以 `c_space_id` 归属单空间，跨空间因子（如跨市场价差）需跨空间视图支持，另行立项。
