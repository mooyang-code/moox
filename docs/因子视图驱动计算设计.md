# 因子视图驱动计算设计

> 状态：评审稿 v2（2026-08-07，吸收评审意见：消费顺序与发布可靠性闭环、(binding, subject) 进度模型、视图列契约对齐、item 级就绪明细）
> 关联文档：《因子计算模块设计.md》《存储层架构.md》《内置市场行情采集架构.md》

## 1. 背景与动机

当前因子计算的触发链路是**行事件驱动 + 启发式等待**：

1. DataNode outbox 逐批发布 `DatasetRowsUpserted` 行事件；
2. Factor 的 `EventBatcher` 以 2 秒固定窗口批合行事件，猜测"这一批写完了"；
3. 调度器执行前固定 sleep `ViewSettleDelay`（300ms）+ 失败重试 3 次，猜测"视图索引追上了"；
4. 读到数据后对 `[T, T+lookback-1]` 做前向传播重算，防御"任何历史行随时可能被 upsert 修订"。

这套机制的系统性问题：

- **无因果保证**：sleep/重试都是对视图延迟的启发式猜测，慢视图场景下仍会以不完整数据出值（`ErrViewIncomplete` 三次后放弃）；
- **重复计算放大**：每批行事件都触发 `lookback` 长度的前向重算，1m 频率 × lookback=200 的因子每天重复计算量巨大；
- **事件量与价值不匹配**：因子真正关心的是"本周期数据齐了"，却消费了全部行级事件；
- **契约错位**：因子绑定在数据集上，但读路径实际走视图，两侧概念不一致，元数据校验被迫做"视图投影是否覆盖数据集列"的间接推断。

## 2. 设计目标与非目标

### 2.1 目标

- 因子计算只面向**数据视图（View）**，不理解底层数据集；
- 触发链路改为**周期就绪信号驱动**：采集完成 → 数据集周期就绪 → 视图周期就绪 → 因子计算，每一环都是因果信号而非启发式；
- **周期终态语义**：`ready(T)` 发出时，周期 T 的输入数据在视图中已终态且可读，因子每个周期只计算一次（带 lookback 历史上下文）；
- 因子结果"向视图写入"，内部路由到绑定时自动创建并关联的结果数据集；
- 支持多数据集聚合视图的就绪判定（AND 语义，一期即支持）；
- 周期内部分标的采集失败时**超时降级**：宽限期后照常发 ready 并附失败清单，保时效。

### 2.2 非目标

- 不改变 DataNode 写入链路与行事件的既有语义（视图索引仍靠行事件驱动）；
- 不改变因子 Python 执行器与沙箱契约（`lookback`、`input_columns`、`outputs` 结构不变）；
- 一期不做因子级联 DAG（`dataset_role=factor_result` 禁止作为输入源的约束保留）；
- 历史补数（catchup / `moox-cli storage import`）不发周期信号，走既有 `RecalcFactor` RPC 补算。

## 3. 总体设计

### 3.1 三级信号链

```
Collector（采集侧）                Storage（存储侧）                     Factor（因子侧）
─────────────────                ─────────────────                     ────────────────
周期 T 的采集批次全部终态
（含超时降级判定）
  │ ReportDatasetPeriodCollected
  ▼
                            DataNode 将周期 marker 追加到
                            本空间 outbox（与行事件同序）
                              │ DatasetPeriodCollected
                              ▼
                            View 单 consumer 多 Filter 订阅，
                            按 dataset 串行分发：行先落索引，
                            再事务化登记就绪[T]
                            全部输入数据集到齐？
                              │ ViewPeriodReady(view, T)
                              ▼
                                                                  按 view 匹配 enabled 绑定
                                                                  每 subject：读 [T-lookback+1, T]
                                                                  compute → 写结果数据集
                                                                  推进绑定水位（持久化自愈）
```

**关键不变式**：`ViewPeriodReady(view, T)` 发出时 ⇒ 视图 Active 索引已包含周期 T 的全部输入行。该不变式由三个机制联合保证：

1. **有序 marker**：周期 marker 由 DataNode 经 outbox 追加（Pebble outbox 条目按 ID 有序发布），与该数据集的行事件共用同一发布序列，流内顺序即写入顺序（collector 只上报，不直接发事件）；
2. **同数据集串行**：View 使用**单个 durable consumer + 多 FilterSubject**（行事件族与 marker 族同一消费位点，流内有序），`subjectDispatcher` 的分发键从 NATS subject 改为 **dataset_id**——同数据集的行事件与 marker 进入同一队列串行处理，处理到 marker 时该数据集此前的行事件必然已应用。禁止用两个独立 consumer 再假设事件顺序；
3. **就绪登记事务化**：不同数据集的 marker 分发键不同、可并发处理，对 `(view, period)` 就绪行的读改写必须在单个 sqlite 事务内完成。

### 3.2 周期终态语义与前向传播的删除

`ready(T)` 意味着 T 的输入已终态，而因子输出 `output(T)` 只依赖 `input(≤T)`，因此：

- **正常路径**：每周期只算 `[T, T+1)` 一个 period，读取窗口 `[T-lookback+1, T]` 提供历史上下文；
- **修订路径**：交易所重述历史 bar 或补数覆盖旧周期 T' 时，由采集侧/导入方重新上报 T' 的周期信号，因子对 `[T', min(T'+lookback-1, 已算水位)]` 做范围重算（幂等 upsert 覆盖）。前向传播只存在于修订路径，不再是每次触发的默认行为。

## 4. 事件协议

在 `packages/events/registry.go` 按既有 `declareEvent` 模式新增两个事件，subject 模板沿用 `moox.<name>.v<N>.<space>.<subject>`：

| 事件 | 版本 | Stream | Owner | Subject | 载荷 |
|---|---|---|---|---|---|
| `storage.dataset.period.collected` | v1 | `MOOX_STORAGE` | storage | `<space>.<dataset_id>` | `DatasetPeriodCollected` |
| `storage.view.period.ready` | v1 | `MOOX_STORAGE` | storage | `<space>.<view_id>` | `ViewPeriodReady` |

proto 定义（放入 `packages/storagepb`，与 `DatasetRowsUpserted` 同包）：

```protobuf
// 数据集单周期采集就绪信号。由 DataNode outbox 发布，保证与同数据集
// 行事件的因果顺序：消费者见到本事件时，该周期已提交的行事件必先于它到达。
// 计数类观测信息由采集侧指标承担，事件契约保持最小。
message DatasetPeriodCollected {
  string dataset_id = 1;
  string frequency = 2;
  int64 period_time = 3;                  // 周期起始时刻，UTC epoch 秒，按 frequency 网格对齐
  string status = 4;                      // complete | degraded
  repeated string failed_subjects = 5;    // degraded 时非空
  string source = 6;                      // realtime | manual | restatement
  google.protobuf.Timestamp collected_at = 7;
}

// 视图单周期就绪信号。发出时视图 Active 索引已含该周期全部输入行。
message ViewPeriodReady {
  string view_id = 1;
  string frequency = 2;
  int64 period_time = 3;
  repeated ViewPeriodDatasetReady datasets = 4;
  google.protobuf.Timestamp ready_at = 5;
}

message ViewPeriodDatasetReady {
  string dataset_id = 1;
  string status = 2;                      // complete | degraded
  repeated string failed_subjects = 3;
}
```

设计要点：

- 两个事件的 owner 都登记为 **storage**（发布者是 DataNode/View），collector 不直接持有事件发布权，这是有序 marker 不变式的前提；
- `period_time` 用 int64 epoch 秒而非字符串，避免时区/格式歧义；`frequency` 冗余携带便于消费方快速过滤；
- `DatasetRowsUpserted` 行事件保持不变，Factor 不再订阅它。

## 5. 采集侧：周期就绪追踪

### 5.1 现状复用

Collector 已具备周期对齐调度（`domain/schedule.go` 的 `ScheduleDecision`）、批次状态机（`FetchBatch`：`planned/dispatched/succeeded/partial_failed/failed/timed_out`）、批次完成事件（`MarketFetchBatchCompleted`，逐 item 携带 `subject_id/target_data_time/outcome`）与 deadline 兜底恢复。

### 5.2 周期就绪聚合

新增组件**周期就绪追踪器（PeriodReadinessTracker）**（collector 内部）。聚合粒度是 **`(dataset, freq, period, subject)` 明细**而非批次计数——一个批次可含多个 item、item 自带 `target_data_time`，且重试会产生重复 completion：

1. 消费 `MarketFetchBatchCompleted`（已有 consumer 位置），按 item 展开为 `(dataset, freq, period, subject)` 明细，period 由 item 的 `target_data_time` 按 §5.3 对齐算法得出；重复 completion 按明细幂等去重；
2. 每个周期的**预期 subject 集合**来自调度计划（绑定该 dataset+freq 的 subject 清单，计划时已落库）；明细状态机 `pending → success | failed`，持久化到 collector sqlite（见 §8.3），重启可恢复；
3. 周期内全部预期 subject 到达 `success` → 以 `complete` 上报；存在终态失败 → 以 `degraded` 上报，附 `failed_subjects`；
4. **超时降级**：周期收盘价 + 宽限期（`period_ready_grace`，按 frequency 配置，默认 `2×freq`，上限 10m）到达时仍 `pending` 的 subject 置为 `failed`，按 `degraded` 上报；
5. **状态单调与修订**：已上报周期内 `failed → success`（迟到重试成功，`BatchInvocation` 已有 `LateCompletion` 标记）视为修订，明细 `c_revision + 1` 并以 `source=restatement` 重新上报该周期；`success` 不回退；
6. 上报方式：调用 Storage Access 新 RPC `ReportDatasetPeriodCollected`，由存储侧落 outbox。

### 5.3 周期对齐算法

`period_time = floor(unix_seconds, freq_seconds)`（秒级频率：1m/5m/15m/1h/4h 等）；日及以上日历频率按 UTC 日历对齐。对齐函数与 `domain/schedule.go` 的 `ParseScheduleInterval`/`ScheduleDecision` 共用同一份实现，避免采集调度与就绪判定网格不一致。

### 5.4 补数路径

`BatchKindCatchup` 批次与 `moox-cli storage import` 不进入周期就绪追踪（避免历史逐周期信号打爆链路）。补数完成后由发起方调用因子 `RecalcFactor`（已有 RPC）按范围补算。导入工具在导入结束时自动发起该调用。

## 6. 存储侧：有序 Marker 与视图就绪聚合

### 6.1 ReportDatasetPeriodCollected RPC

Storage Access 新增 RPC：校验 `(space, dataset, freq)` 合法后，向该空间 DataNode 的 outbox 追加一条 **period marker 条目**。注意 DataNode outbox 是 **Pebble KV 条目**（`outbox.Relay` 轮询 `ListOutbox` 发布），并非关系表：需扩展条目模型携带事件类型（`rows_upserted | period_collected`），并放宽 `JetStreamPublisher.validateDatasetEvent`——当前它硬编码只放行 `DatasetRowsUpserted`，需同时接受 `DatasetPeriodCollected`。条目按 outbox ID 有序发布，同数据集的行事件与 marker 由此获得因果顺序。

### 6.2 视图就绪聚合（View 角色）

View 角色的 consumer 改造为**单 durable consumer + 多 FilterSubject**（行事件族与 marker 族挂在同一消费位点，流内有序），`subjectDispatcher` 分发键改为 dataset_id（§3.1 不变式 2）。处理逻辑：

1. 行事件：维持现状，应用进 DuckDB 索引；
2. `DatasetPeriodCollected(ds, T)`：在**单个 sqlite 事务**内对 `(space_id, view_id, period_time)` 就绪行做读改写，登记该输入数据集的到达状态（§8.2）；
3. 当事务内判定视图的全部**输入数据集**对周期 T 均已到达（对应行事件必然已应用，由同数据集串行保证），**先发布 `ViewPeriodReady(view, T)`，发布成功后才将 `c_ready_emitted` 置位**（at-least-once）。进程在发布与置位之间退出时，重启扫描"满足条件但未置位"的就绪行重发——重复 ready 由消费方幂等吸收；不得为了去重改成先置位后发布（at-most-once 会永久丢失最后一个周期）。

关键规则：

- **输入数据集 = `dataset_ids` 中扣除 `dataset_role=factor_result` 的数据集**。因子结果数据集不参与就绪判定，否则"因子写回 → 视图事件 → 就绪判定"形成循环依赖；
- 视图的 `filter_json.freq` 即视图周期网格，`period_time` 非该网格对齐的 collected 事件直接忽略；视图的全部输入数据集必须包含该 freq 的数据（创建视图时校验，绑定因子时复核）；
- ready 事件可重发（修订路径/崩溃重发），消费方幂等；
- 就绪表定期清理：`period_time < now - keep` 且已发 ready 的行删除。

## 7. 因子侧改造

### 7.1 触发：从行事件到就绪信号

- 删除 `EventBatcher`、`factor_calc` 对 `DatasetRowsUpserted` 的订阅；
- 新增 ready consumer：按空间订阅 `storage.view.period.ready`，解码后按 `view_id` 匹配 enabled 绑定，为每个 `(binding, subject)` 生成任务进入分片队列（沿用 `subject → worker` 的串行语义）；
- **任务集合按 `subject_id` 生成**：查询视图内 distinct `subject_id`（ready 已保证数据可读），受绑定 `subject_mode/subjects` 过滤。`series_tag` 是同一 subject 下的序列维度而非任务维度——因子输入为"该 subject 全部 series_tag"的行，`series_tag` 不产生独立任务；
- 队列去重键从 `(binding, subject, start, end)` 变为 `(binding, subject, period)`。

### 7.2 计算：单周期 + 水位自愈

- **正常路径**：任务范围 `[T, T+1)`，读取窗口 `[T-lookback+1, T]`（视图范围查询，现状能力）；
- **进度模型为 `(binding_id, subject_id)` 粒度**（绑定已唯一确定 freq）：任务按 subject 并发执行，绑定级单一水位在"A 成功 B 失败"时推进与否都会出错，故每 subject 独立持久化 `c_last_period`（§8.1）。规则：
  - 下一周期用 `NextPeriod(freq, last)` 计算，不得用 `last+1`（`period_time` 是 epoch 秒）；
  - 以独立初始化标记区分"未初始化"，不得用 0 值兼任；未初始化时以首个 ready 周期为起点，不做历史回补（历史回补走 `RecalcFactor`）；
  - **写回成功后才推进进度**；单 subject 失败只阻塞自身进度，由重试与下一周期自愈；
- **缺口自愈**：收到 `ready(T)` 时若该 subject 存在 `(last, T)` 缺失周期，先补算再算 T——ready 事件丢失或服务停机后由下一周期自动愈合；补算跨度超过上限（默认 1440 周期）时截断并告警，引导走 `RecalcFactor`；
- **修订路径**：`ready(T')` 且 `T' ≤ last` 时，按 §3.2 做 `[T', min(T'+lookback-1, last+1)]` 范围重算，幂等覆盖；
- **degraded 周期**：`failed_subjects` 命中的 subject 本周期输入不完整，跳过计算并**保留上一周期结果**（upsert 语义下旧值自然留存），同时输出指标与日志；同一 subject 连续 degraded 超阈值（默认 3 个周期）触发告警。不得静默跳过而不留可观测痕迹；
- 删除：`ViewSettleDelay`、`EventReadRetry`、`ExpandEndByPeriods`、水位判定与 `ErrViewIncomplete` 重试链。

### 7.3 读写契约：只见视图

- **读**：`ReadTimeSeriesRowsReq` 增加可选 `view_id`——指定后 Storage 直接路由到该视图（不再经 dataset 反查默认视图），`column_names` 直接使用视图列名（停用 `qualifyDatasetColumns` 的 `dataset.column` 拼接）。保持单 RPC 入口与既有鉴权，优于 Factor 直连 `DataView.QueryTimeSeriesRows`。`input_columns` 语义改为**视图列名**，绑定校验简化为"视图列存在"；
- **写**：调度器持 `view_id`，内部解析出该视图的因子结果数据集（绑定时创建，见 §9），走既有 `UpsertFields` 写入；**写回层完成输出列名映射**：Python 原始 output 名 → 结果列 `field_id`（§9.1），不能只改元数据而漏掉写回映射。因子代码与调度逻辑不出现数据集概念；
- **`RecalcFactor` 同步迁移**：入参从 `source_dataset` 改为 `view_id`，与实时路径共用同一读取契约，避免两条路径语义分叉。

### 7.4 保留不变的机制

分片队列与 per-subject 串行、Python 执行器协议、`FactorGate` 并发门禁、启停清理时的 task_id 版本 fencing、`RecalcFactor` 手动补算 RPC。

    c_state TEXT NOT NULL DEFAULT 'pending',
    c_revision INTEGER NOT NULL DEFAULT 0,
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_state IN ('pending', 'success', 'failed')),
    UNIQUE (c_space_id, c_dataset_id, c_frequency, c_period_time, c_subject_id)
);

CREATE INDEX IF NOT EXISTS idx_t_period_readiness_items_period
ON t_period_readiness_items (c_space_id, c_dataset_id, c_frequency, c_period_time, c_state);

## 9. 绑定生命周期与视图重建

### 9.1 绑定创建流程

`UpsertBinding(space, view, factor, freq, subject_scope)`：

1. 校验：视图为时序视图（`filter_json.freq` 存在且等于绑定 `freq`）；因子未禁用；`FactorGate` 门禁通过；
2. **结果数据集**：按视图派生 `factor_result__<view_id>`（替代现 `ResultDataset(sourceDataset)` 的按源派生），不存在则创建，`dataset_role=factor_result`，grain 与视图对齐；
3. **列同步**：因子名统一**小写规范化**——现行 `pythonModuleNamePattern` 允许大写，需在唯一性校验、源码路径、元数据同步三处统一归一化，并拒绝 `Bias`/`bias` 这类大小写变体重名。因子输出列以 `<factor_name>__<output>` 命名登记到结果数据集；视图列遵循现行 `ViewColumn` 契约（`metadata.proto` 要求 `column_name` 与 `origin_id` 一致且必须为 `dataset_id.column_name`），即视图列名 = `<结果数据集>.<factor_name>__<output>`，`origin_type=dataset_column`；
4. **关联视图**：将结果数据集并入 `view.dataset_ids`，`desired_view_revision + 1` → 触发既有 A/B 索引重建；
5. 响应携带视图修订状态，前端据此提示。

### 9.2 重建期间的系统行为

- 重建走既有 A/B 机制：Active 索引继续服务查询，实时事件双写 Active/New；
- **因子计算不阻塞**：结果数据集即刻可写，新周期照常计算，结果行在切换后随索引可见；
- 用户可见性：`t_view_index_builds` 携带构建状态与 `c_backfilled_rows` 进度，网关暴露后前端展示"视图重建中"徽标；
- 因子禁用不触发重建（列保留）；显式解绑触发重建以摘除结果列。**解绑清理策略**：结果列从视图摘除后，结果数据集与历史结果默认**保留**（可按数据集直接查询与审计），确需清除时走 storage 数据集删除的显式操作，不在解绑流程中隐式删数据。

### 9.3 前端绑定页改造

- 绑定页改为**按视图分组**：列出当前空间全部时序视图（`ListViews`），每个视图卡片展示已绑定因子组（状态、lookback、水位进度），卡片内发起绑定/解绑；
- 绑定操作返回视图修订状态时，弹出提示："新增因子将触发视图索引重建，结果列在重建完成前暂不可查"；
- 视图卡片展示 `IndexBuild` 状态（构建中/切换中/就绪）。

## 11. 可靠性与边界场景

| 场景 | 行为 |
|---|---|
| ready 事件丢失 | （binding, subject）进度自愈：下一周期 ready 触发补算缺口 |
| ready 发布与置位之间崩溃 | 先发布后标记（at-least-once），重启扫描未置位行重发；消费方幂等 |
| 视图服务重启 | 就绪状态在 sqlite，重启后续算；重启期间到达的事件由 JetStream 重投 |
| 采集 straggler | 宽限期后 degraded 降级，ready 照常发出；失败 subject 当周期跳过计算并保留旧值（指标+日志可观测，连续 degraded 触发告警） |
| 重复 ready（修订/重投） | 消费幂等：≤进度的周期走修订重算，>进度的正常推进 |
| 交易所重述历史 bar | 采集侧重上报该周期 → 视图重发 ready → 因子修订路径范围重算 |
| 视图重建中收到 ready | 正常计算写结果数据集；查询可见性延迟至索引切换 |
| 多数据集 straggler 放大 | 任一输入源降级后 ready 即发出（降级策略下不存在无限等待）；长期未就绪周期有就绪表可查可告警 |

## 13. 实施任务拆分

落地顺序按四个契约收敛，其余工作挂靠其后：

1. **契约一：周期就绪事件与 DataNode 原子 outbox**。`storagepb` 新增两个 proto 消息、`events/registry.go` 注册与校验器；Pebble outbox 条目扩展事件类型、publisher 放行 `DatasetPeriodCollected`；`ReportDatasetPeriodCollected` RPC；
2. **契约二：View 的 marker 消费与 ready 可靠发布**。单 durable consumer 多 FilterSubject、分发键改为 dataset_id、就绪表事务化、先发布后置位 + 崩溃重发；
3. **契约三：collector 周期就绪追踪**。PeriodReadinessTracker（item 明细状态机、deadline 降级、迟到修订重报）；`t_period_readiness` 两张新表；
4. **契约四：factor 视图化读写与 (binding, subject) 进度**。`ReadTimeSeriesRowsReq` 增加 `view_id`；ready consumer 替换行事件链路；单周期计算 + 缺口自愈 + 修订重算 + degraded 策略；输出列名映射写回；`RecalcFactor` 迁移 view_id；
5. **registry/metadata_sync**：绑定流程改造（视图校验、视图派生结果数据集、视图列契约、修订触发）；因子名小写归一化（含大小写变体重名拒绝）；
6. **storage 附带修复**：`QueryTimeSeriesRows` 的 `complete` 语义区分"覆盖完整但无数据"与"索引未覆盖"（当前空结果直接 false）；
7. **前端**：绑定页按视图分组、重建状态展示与提示；
8. **清理**：删除 `EventBatcher`、settle/retry 配置、`ExpandEndByPeriods` 调用链、废弃的按源数据集派生结果集逻辑；
9. **补数闭环**：`moox-cli storage import` 完成后自动调用 `RecalcFactor`（内部服务 HMAC 凭证；失败记指标与日志，允许手动重试）；
10. **测试**：多数据集乱序、重复 marker、ready 发布失败、View 重启、degraded 后迟到修订、单 subject 失败、空周期（无任何行）、绑定变更与视图重建中的 ready、进度自愈截断。

## 14. 开放问题

1. **每周期 per-subject 读放大**：500 标的 × 每周期一次范围读，视图查询 QPS 随标的数线性增长。一期按现状接受；二期评估"单查询取全 tag + 内存分组"的 cohort 模式（Scheduler 已预留该演进空间）。
2. **多视图共用同一结果数据集**：当前按视图派生独立结果数据集，简单清晰但数据集数量随视图数增长；若后续视图爆炸再评估合并策略。
3. **跨空间视图**：`t_views` 以 `c_space_id` 归属单空间，跨空间因子（如跨市场价差）需跨空间视图支持，另行立项。
