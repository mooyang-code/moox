# 因子视图驱动计算设计

> 状态：评审稿 v6（个人量化简化版）
> 关联文档：《因子计算模块设计.md》《存储层架构.md》《内置市场行情采集架构.md》

## 1. 背景

当前因子计算采用“行事件触发 + 固定等待”的方式：

1. DataNode outbox 发布 `DatasetRowsUpserted`；
2. Factor 的 `EventBatcher` 合并短时间内的行事件；
3. 调度器等待 `ViewSettleDelay`，再尝试从 View 读取；
4. 同一周期多批行事件可能重复触发相同因子。

这种方式不能明确回答两个问题：

- 本周期 K 线是否已经采集完成，并且已经在 Source View 中可读；
- 因子是否已经计算完成，并且结果已经在 Result View 中可读。

本设计增加显式的周期完成事件，把实时链路调整为：

```text
K 线采集任务终态
  -> DatasetPeriodCollected
  -> Source View 确认可读
  -> ViewSourcePeriodReady
  -> Factor 计算并写结果
  -> FactorPeriodComputed
  -> Result View 确认可读
  -> ViewFactorPeriodReady（最终事件）
```

## 2. 设计边界

### 2.1 目标

- Collector 按 `(dataset, frequency, period, subject)` 汇总采集结果；
- Dataset 完成 Marker 与 K 线行写入使用同一个 DataNode outbox，保证先写行、后发完成 Marker；
- Factor 只消费 `ViewSourcePeriodReady`，不再用行事件和固定 sleep 猜测 View 是否追平；
- Factor 结果写入和 `FactorPeriodComputed` 使用同一个结果 DataNode outbox；
- `ViewFactorPeriodReady` 发出时，本周期最新因子结果已经在 Result View 中可读；
- Source View 与 Result View 分离，动态 `series_tag` 不回流污染下一周期输入；
- 保留单实例、SQLite、JetStream、幂等写入和必要恢复，不引入分布式锁、工作流引擎和 Exactly-Once 协议。

### 2.2 简化后的可靠性语义

本设计采用 **latest-wins**：

- 完成事件表示“事件发出时，本周期当前结果已经可读”；
- 完成事件不是历史不可变快照句柄；
- 下游收到旧事件时，如果结果已经被 Recalc 或后续计算覆盖，读取到最新结果是允许的；
- 进程退出可能导致重复计算，结果写入必须可重入；
- 同一周期的迟到 K 线、交易所历史修正和对账差异，统一通过显式 `RecalcFactor` 处理，不在实时链路自动生成 restatement；
- 不保证对每个中间状态产生一次且仅一次的完成事件。

这些取舍适合个人量化系统：实现和运维成本较低，异常时可以通过告警、重试和显式 Recalc 恢复。

### 2.3 非目标

- 一期不做因子级联 DAG；
- 一期不支持跨空间 View；
- 一期不支持横截面 period-scoped 因子，继续使用现有 per-subject Python 因子契约；
- Catchup 和 import 不逐周期广播实时 ready；
- 不保存可供历史精确读取的因子结果快照；
- 不做自动 lookback 前向 restatement，历史变化由调用方明确指定 Recalc 范围。

## 3. 总体架构

### 3.1 四类完成信号

| 信号 | 含义 | 决策方 | 发布方 |
|---|---|---|---|
| `DatasetPeriodCollected` | 数据集本周期所有预期 subject 已进入终态 | Collector | 数据集 DataNode outbox |
| `ViewSourcePeriodReady` | 本周期源数据已在 Source View 中可读 | View | Storage/View |
| `FactorPeriodComputed` | 本周期所有 enabled binding 已终态，结果写入已提交 | Factor | 结果数据集 DataNode outbox |
| `ViewFactorPeriodReady` | 本周期最新因子结果已在 Result View 中可读 | View | Storage/View |

import、catchup 使用 `DatasetSyncPoint` 确认某一批写入已经被 View 消费；由它们触发的 Recalc 必须等待该 SyncPoint。SyncPoint 只表示同步进度，不表示业务周期完成。

### 3.2 完整链路

```text
Collector                         Storage / View                         Factor
─────────                         ──────────────                         ──────
预建周期任务
监听 K 线 DatasetRowsUpserted
更新 subject 状态
全部终态或到达 deadline
  │ ReportDatasetPeriodCollected
  ▼
                                  Primary 按 dataset 路由 DataNode
                                  在同一 outbox 追加完成 Marker
                                    │ DatasetPeriodCollected
                                    ▼
                                  View 串行消费：
                                  先应用此前 K 线行，再处理 Marker
                                  Source View 所有输入 dataset 到齐
                                    │ ViewSourcePeriodReady
                                    └──────────────────────────────────► 查询当前 enabled bindings
                                                                         按 subject 计算因子
                                                                         写入 Result Dataset
                                                                         清理本 binding 消失的旧输出
                                                                         全部任务终态
                                                                         │ ReportFactorPeriodComputed
                                                                         ▼
                                  结果 DataNode 在同一 outbox 追加 Marker
                                    │ FactorPeriodComputed
                                    ▼
                                  Result View 串行消费：
                                  先应用结果行，再处理 Marker
                                    │ ViewFactorPeriodReady
                                    ▼
                                  策略读取当前 Result View
```

### 3.3 必须保留的不变式

1. `DatasetPeriodCollected` 与促成它的 K 线行位于同一个 DataNode outbox，Marker 排在行事件之后；
2. View 的 dataset consumer 一期只运行一个实例，使用显式 ACK 和 Dataset 队列；同一
   Dataset 的 rows、Marker、SyncPoint 串行，不同 Dataset 可并行；
3. View 只有在完成 Marker 之前的行事件成功应用后，才发布 ready；
4. `FactorPeriodComputed` 与本次结果写入位于同一个结果 DataNode outbox，Marker 排在结果行之后；
5. Result View 处理 `FactorPeriodComputed` 时，此前结果行已经应用，因此可以发布最终事件；
6. Source View 不包含 factor-result dataset，Result View 只承载因子输出；
7. 自动创建的 factor-result dataset 只允许 Factor 和 Storage 内部流程写入，避免 manual/import 绕过完成协议。

不再维护 period generation、snapshot hash、read fence、不可变 emission history 和跨代报告链。

## 4. 事件协议

四个完成事件和一个辅助 SyncPoint 都进入 `MOOX_STORAGE` Stream。Collector 和 Factor 通过 Storage RPC 上报完成决定，由对应 DataNode 写入 outbox。

| 事件 | Subject 末级 | 载荷 |
|---|---|---|
| `storage.dataset.period.collected` | `<space>.<dataset_id>` | `DatasetPeriodCollected` |
| `storage.view.source_period.ready` | `<space>.<source_view_id>` | `ViewSourcePeriodReady` |
| `storage.dataset.factor_period.computed` | `<space>.<result_dataset_id>` | `FactorPeriodComputed` |
| `storage.view.factor_period.ready` | `<space>.<result_view_id>` | `ViewFactorPeriodReady` |
| `storage.dataset.sync_point` | `<space>.<dataset_id>` | `DatasetSyncPoint` |

字段编号以最终 proto 评审为准：

`period_time` 统一表示 UTC 周期起始时间的 epoch seconds；Collector 归期、View 聚合和 Factor 目标周期必须复用同一个对齐函数。

```protobuf
message DatasetPeriodCollected {
  string dataset_id = 1;
  string frequency = 2;
  int64 period_time = 3;
  string status = 4;                       // complete | degraded
  repeated string subject_ids = 5;        // 本周期预期 subject
  repeated string failed_subjects = 6;    // deadline 时未完成的 subject
  google.protobuf.Timestamp collected_at = 7;
}

message ViewPeriodDatasetState {
  string dataset_id = 1;
  string status = 2;                       // complete | degraded
  repeated string failed_subjects = 3;
}

message ViewSourcePeriodReady {
  string source_view_id = 1;
  string frequency = 2;
  int64 period_time = 3;
  string status = 4;                       // complete | degraded
  repeated ViewPeriodDatasetState datasets = 5;
  repeated string primary_subjects = 6;
  google.protobuf.Timestamp ready_at = 7;
}

message FactorBindingPeriodState {
  string binding_id = 1;
  string factor_id = 2;
  string status = 3;                       // complete | degraded
  repeated string skipped_subjects = 4;
  repeated string failed_subjects = 5;
}

message FactorPeriodComputed {
  string source_view_id = 1;
  string result_dataset_id = 2;
  string frequency = 3;
  int64 period_time = 4;
  string status = 5;                       // complete | degraded
  repeated FactorBindingPeriodState bindings = 6;
  google.protobuf.Timestamp computed_at = 7;
  string trigger_event_id = 8;             // 用于追踪与重复交接检查
}

message ViewFactorPeriodReady {
  string source_view_id = 1;
  string result_view_id = 2;
  string frequency = 3;
  int64 period_time = 4;
  string status = 5;                       // complete | degraded
  repeated FactorBindingPeriodState bindings = 6;
  google.protobuf.Timestamp ready_at = 7;
}

message DatasetSyncPoint {
  string sync_point_id = 1;                // hash(request_id,dataset_id)
  string request_id = 2;
  string dataset_id = 3;
  string source = 4;                       // import | catchup
}
```

### 4.1 完成与降级

- `complete`：本阶段所有预期任务成功；
- `degraded`：所有预期任务已经终态，但存在 timeout、skip 或 failure；
- `ViewSourcePeriodReady.degraded` 仍可触发 Factor；Factor 跳过没有有效输入的 subject；
- `ViewFactorPeriodReady.degraded` 表示成功任务的最新结果可读，失败和跳过清单包含在事件中；
- failed/skipped task 在上报 Factor Marker 前清理 manifest 中本周期已知的旧输出，避免把旧值误当成本次结果；
- written/cleared row count 属于 Metrics 和日志，不进入公共事件。

### 4.2 幂等

- Dataset 周期完成 Event ID 由 `(space,dataset,frequency,period)` 确定；
- Source View ready Event ID 由 `(space,source_view,frequency,period)` 确定；
- Factor Marker Event ID 由 `(space,result_dataset,trigger_event_id,period)` 确定；
- Result View ready Event ID 由 Factor Marker Event ID 和 Result View ID 确定；
- SyncPoint ID 由 `(request_id,dataset_id)` 确定；
- Source View ready 的 `ready_at` 复用 Dataset Marker 的事件时间，Result View ready 的 `ready_at` 复用 Factor Marker 的事件时间，重投时不重新读取当前时钟；
- repeated ID 列表在生成 payload 前去重并排序；
- RPC 超时重试必须复用原 ID；重复事件允许重复处理，但不能产生不一致的 payload；
- View 和 Factor 的业务写入使用 upsert/clear，重复执行后结果保持一致。

一期同一 dataset 周期只自动报告一次。已经报告 `degraded` 后到达的迟到数据不会生成第二代完成事件，由对账或人工调用 Recalc 修正。

## 5. Collector：周期采集完成

### 5.1 周期任务预建

`PeriodReadinessTracker` 在周期开始时：

1. 从未删除的 `TaskInstance` 按 `(space,dataset,frequency)` 读取预期 subject；
2. 创建 `(dataset,frequency,period)` 父状态；
3. 为每个 subject 创建一个 `pending` item；
4. 记录本周期不可变的任务来源和必需字段；
5. 设置 `deadline_at = period_close + period_ready_grace`。

必须预建周期，不能等第一条 K 线行到达后再创建。否则整次 Timer 没有执行时，deadline worker 无法发现缺失任务。

assignment 在周期中变化时不修改已创建周期，从下一周期生效。

### 5.2 由 K 线行更新状态

Collector 消费 `DatasetRowsUpserted.rows[]`：

1. 从 RowKey 读取 `dataset_id/subject_id/frequency/data_time`；
2. 按 `data_time` 归属周期，不使用事件发布时间；
3. 只接受与预建 TaskInstance/write source 匹配的 Collector 写入；
4. 确认本任务要求的字段已经写入后，把 item 更新为 `success`；
5. 同一 subject/period 的重复行幂等；
6. 一个批次包含多个 `data_time` 时，分别更新对应周期。

内存可以缓存当前周期状态，但 SQLite 是权威状态。必须先提交 SQLite，再 ACK 行事件。

### 5.3 Deadline 与完成上报

- deadline 到达时，把剩余 `pending` item 更新为 `timed_out`；
- 全部成功时状态为 `complete`；
- 存在 `timed_out` 时状态为 `degraded`；
- 第一次进入全部终态时，固定 `collected_at` 和完整 payload，状态更新为 `report_pending`；
- reporter 调用 `ReportDatasetPeriodCollected`；
- RPC 成功后更新为 `reported`；
- RPC 超时使用相同 Event ID 和已保存 payload 重试。

一旦进入 `report_pending/reported`，本周期不再自动改变完成结论。迟到数据仍正常写入 Storage，但是否需要重算由对账任务或用户显式决定。

### 5.4 Collector 最小持久化

```sql
CREATE TABLE IF NOT EXISTS t_period_readiness (
    c_id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    c_space_id TEXT NOT NULL,
    c_dataset_id TEXT NOT NULL,
    c_frequency TEXT NOT NULL,
    c_period_time INTEGER NOT NULL,
    c_deadline_at TEXT NOT NULL,
    c_status TEXT NOT NULL,                 -- pending | complete | degraded
    c_report_state TEXT NOT NULL,           -- waiting | pending | reported
    c_event_id TEXT NOT NULL DEFAULT '',
    c_collected_at TEXT NOT NULL DEFAULT '',
    c_payload_json TEXT NOT NULL DEFAULT '{}',
    UNIQUE (c_space_id, c_dataset_id, c_frequency, c_period_time)
);

CREATE TABLE IF NOT EXISTS t_period_readiness_items (
    c_readiness_id INTEGER NOT NULL,
    c_subject_id TEXT NOT NULL,
    c_state TEXT NOT NULL,                  -- pending | success | timed_out
    c_updated_at TEXT NOT NULL,
    PRIMARY KEY (c_readiness_id, c_subject_id),
    FOREIGN KEY (c_readiness_id) REFERENCES t_period_readiness(c_id)
);
```

具体建表时沿用当前 Collector SQLite migration 方式。`payload_json` 只用于崩溃后重试同一次上报，不保存多代 report history。

## 6. Storage：同 DataNode Outbox Marker

### 6.1 RPC

Storage Primary 新增：

- `ReportDatasetPeriodCollected`；
- `ReportFactorPeriodComputed`；
- `AppendDatasetSyncPoint`；
- `GetFactorPeriodComputed`：按 `(source_view_id,trigger_event_id,period_time)` 查询 Marker 是否已经交接，Primary 通过 Source View 自动结果关系完成路由；
- `WaitViewSyncPoint`：等待指定 View 消费 request 对应的全部 dataset SyncPoint。

三个追加类 RPC 使用同一套简单规则：

1. 校验 space、dataset、调用方和 payload；
2. 按 `(space,dataset)` 路由到 dataset 当前所属 DataNode；
3. DataNode 在与行写相同的 `outboxMu` 下追加 Marker；
4. 使用确定性 Event ID 幂等处理 RPC 重试；
5. 相同 Event ID 但 payload 不同返回冲突错误。

不维护多代 report、report chain 或 target plan；同一周期只保留第一次已上报的状态。

### 6.2 自动结果数据集写入权限

自动创建的结果 dataset 标记为：

```text
dataset_role = factor_result
write_owner = factor
```

Primary 和 DataNode 只允许：

- Factor 写入结果字段和清理旧字段；
- Factor 上报 `FactorPeriodComputed`。

CLI import 和普通 manual upsert 不得直接写自动结果 dataset，避免结果行与完成 Marker 失去顺序关系。

## 7. View：从 Marker 到 Ready

### 7.1 单 Consumer 与 ACK 边界

View 使用一个 durable consumer 订阅：

- dataset row events；
- `DatasetPeriodCollected`；
- `FactorPeriodComputed`；
- `DatasetSyncPoint`。

一期约束：

- 只运行一个活动实例；
- `MaxAckPending=8`，同一 Dataset 仍由 Dataset 队列保证顺序；
- 行事件应用到 Active/Building 成功后 ACK；
- Marker 处理和 ready 发布成功后 ACK；
- 暂时错误保持当前消息未 ACK 并重试，不允许越过失败行处理后续 Marker；
- 永久错误告警并等待人工处理，不额外设计“阻塞队列”状态机。

这是整个简化方案成立的核心：完成 Marker 与此前行事件在同一个有序消费链中处理，因此不需要 `view_period_generations`。

### 7.2 Source View ready

处理 `DatasetPeriodCollected(dataset,T)`：

1. 根据 Active View 元数据找到依赖该 dataset 的 Source View；
2. 幂等保存本 View、本周期、本 dataset 的完成状态；
3. 检查 Source View 配置的所有 periodic input datasets 是否都已经收到完成 Marker；
4. 未到齐则 ACK 当前 Marker，等待其他 dataset；
5. 全部到齐后聚合 status、failed subjects 和 primary subjects；
6. 直接发布 `ViewSourcePeriodReady`；
7. 发布成功后 ACK Marker。

单数据集 Source View 在收到 Marker 后可以直接执行第 5 至第 7 步。

View 不再：

- 维护周期 generation/previous report 链；
- 维护跨代 applied/sealed 状态；
- 计算 snapshot/dependency hash；
- 创建不可变 emission intent；
- 为同一周期生成 initial/restatement 链；
- 通过 Active schema/index fence 阻止 Factor 读取。

发布成功但 ACK 前退出时，Marker 会重投并可能再次发布 ready。Event ID 固定，Factor 重复消费必须可重入。

### 7.3 Result View ready

处理 `FactorPeriodComputed`：

1. 根据结果 dataset 找到自动 Result View；
2. 确认 Result View 当前为 Active；
3. 由于同一 consumer 已经应用 Marker 前面的结果行，直接构造 `ViewFactorPeriodReady`；
4. 发布成功后 ACK Marker。

不重新扫描结果行计算 hash，也不保证旧事件对应的值在以后仍然保留。最终事件的契约是：**发布时当前结果可读；以后读取以 Result View 最新值为准。**

### 7.4 最小 Metadata 状态

多数据集 Source View 需要一张简单聚合表：

```sql
CREATE TABLE IF NOT EXISTS t_view_period_dataset_states (
    c_space_id TEXT NOT NULL,
    c_view_id TEXT NOT NULL,
    c_dataset_id TEXT NOT NULL,
    c_frequency TEXT NOT NULL,
    c_period_time INTEGER NOT NULL,
    c_event_id TEXT NOT NULL,
    c_status TEXT NOT NULL,
    c_subject_ids_json TEXT NOT NULL DEFAULT '[]',
    c_failed_subjects_json TEXT NOT NULL DEFAULT '[]',
    c_updated_at TEXT NOT NULL,
    PRIMARY KEY (c_space_id, c_view_id, c_dataset_id, c_frequency, c_period_time)
);
```

该表只用于等待多个输入 dataset 到齐和事件重投幂等，不保存多代快照。单数据集 View 后续可以直接处理，不依赖该表。

SyncPoint 应用状态使用现有 Metadata 命名风格：

```sql
CREATE TABLE IF NOT EXISTS t_view_sync_points (
    c_space_id TEXT NOT NULL,
    c_view_id TEXT NOT NULL,
    c_dataset_id TEXT NOT NULL,
    c_request_id TEXT NOT NULL,
    c_sync_point_id TEXT NOT NULL,
    c_applied_at TEXT NOT NULL,
    PRIMARY KEY (c_space_id, c_view_id, c_dataset_id, c_request_id)
);
```

物理 DuckDB View 中不新增 `view_period_generations` 或替代表。现有 `view_meta`、`view_columns`、`view_rows` 保持不变。

## 8. Factor：直接消费 Source-ready

### 8.1 消费流程

同一 source View、frequency、period 和 subject 的多个因子共享一次 Python batch 调用；
不同 subject 仍由有界 worker 并行执行。批量响应按 binding 独立校验、写回和记录失败，
因此单因子异常不会丢弃同标的其他因子结果。

这里的 batch 仅是执行优化，不表示因子之间存在依赖关系。所有注册 Factor 都必须能够
仅凭自己的 Source View 输入独立完成计算；复合因子由业务在单个 `compute` 中展开基础
算法，不读取或等待其他 Factor 的结果。Factor 运行时不提供 DAG、拓扑顺序或中间结果
复用，因此同一批次成员可以安全并发并分别失败。

Factor 新 durable 只订阅 `storage.view.source_period.ready`：

1. 收到 `ViewSourcePeriodReady`；
2. 使用 source-ready `EventMessage.ID` 作为 `trigger_event_id`，先调用 `GetFactorPeriodComputed`；已经存在 Marker 时直接 ACK；
3. 查询该 Source View 当前 enabled bindings；
4. 使用事件中的 `primary_subjects` 创建 `(binding,subject)` 任务；
5. 直接读取当前 Active Source View；
6. 执行 Python 因子并写入自动 Result Dataset；
7. 全部任务进入 success/skipped/failed 后，上报 `FactorPeriodComputed`；
8. Storage 确认 Marker 已写入后 ACK source-ready。

Factor 信任 `ViewSourcePeriodReady`，不再验证 source snapshot、dependency hash、Active index ID 或 read fence。若事件到达后 View 已经包含更新数据，Factor 读取并计算最新数据，符合 latest-wins 语义。

绑定前提：Source View 的每个输入 Dataset 都必须由 Collector 以绑定 frequency 持续产生 `DatasetPeriodCollected`。手工导入、只做历史回填或不支持该 frequency 的 Dataset 不会自动产生 source-ready；这类数据必须通过 `DatasetSyncPoint` 等待 View 完成后显式 Recalc。绑定校验会拒绝未激活或不包含该 frequency 的输入 Dataset，避免把这类配置误标为可执行。

一期设置 `MaxAckPending=1`，避免两个周期执行组交错。长任务定期发送 `InProgress` heartbeat。

### 8.2 Binding 和任务状态

每次事件到达时读取当前 enabled bindings，不持久化不可变 binding snapshot：

- binding 已 disabled/unbound：不执行；
- `pending_view` binding 不进入本次任务；
- Source-ready 标记为失败且没有有效输入的 subject 记为 skipped；
- 执行期间发生配置变化：当前任务允许按已读取配置结束，下一周期使用新配置；
- 无 enabled binding：直接 ACK，不产生因子完成事件。

单任务失败沿用现有有限重试。重试耗尽后记入 `failed_subjects`，整个周期为 `degraded`，其余任务继续完成。

### 8.3 结果写入与旧值清理

Source View 和 Result View 必须分离：

- Source View 只包含行情和其他源数据；
- 每个 Source View 自动关联一个 factor-result dataset；
- 每个 factor-result dataset 自动关联一个 Result View；
- Result View filter 必须包含与 Source View 一致的规范化 frequency；
- Factor binding 的 output fields 使用独立 namespace，避免不同因子互相清理。

如果因子输出 RowKey 固定为输入 RowKey，不需要额外 manifest。

如果允许动态 `series_tag`，Factor 内部保留最近窗口的 RowKey manifest：

1. Python 输出先规范化为本次 current RowKeys；
2. `old - current` RowKeys 的本 binding 输出字段写 NULL；
3. current RowKeys 执行 upsert；
4. 写入成功后更新 manifest；
5. written/cleared row count 只记录日志和 Metrics；
6. Recalc 可以通过扫描 Result View 的本 binding 字段修复 manifest 窗口外或异常退出遗留的数据。

task 最终 failed/skipped 时，把 manifest 中该 subject/period 的本 binding 旧输出字段写 NULL，并把这些 RowKeys 从 manifest 移除；clear 成功后才允许上报 Factor Marker。

一期接受极端崩溃点可能留下需 Recalc 清理的动态输出，不为此引入通用 reservation/write-plan 状态机。

最小 manifest：

```sql
CREATE TABLE IF NOT EXISTS t_factor_output_manifests (
    c_binding_id TEXT NOT NULL,
    c_frequency TEXT NOT NULL,
    c_period_time INTEGER NOT NULL,
    c_row_keys_json TEXT NOT NULL DEFAULT '[]',
    c_updated_at TEXT NOT NULL,
    PRIMARY KEY (c_binding_id, c_frequency, c_period_time)
);
```

## 9. Import、Catchup 与 Recalc

### 9.1 DatasetSyncPoint

import/catchup 完成 Storage 写入后：

1. 调用方生成一个稳定 `request_id`；
2. 对每个实际写入的 dataset 调用 `AppendDatasetSyncPoint`；
3. Primary 把 SyncPoint 路由到对应 dataset DataNode；
4. DataNode 在与行写相同的 outbox 中追加 `DatasetSyncPoint`；
5. View 串行应用此前行事件，再记录 SyncPoint 已应用；
6. 调用方通过 `WaitViewSyncPoint(view_id,request_id,dataset_ids)` 等待全部 dataset 到齐；
7. Wait 成功后才启动依赖这批数据的 Recalc。

同一 `request_id` 重试复用原 SyncPoint。这里不再使用 Barrier、Fence、Active triple 或 generation。

### 9.2 Recalc

`RecalcFactor` 与实时任务复用同一个全局 TaskRunner、View read pool 和 Python worker 池：

1. import/catchup 触发时先等待 Source View SyncPoint；
2. 独立 Recalc 直接读取当前 Source View；
3. 调用方明确传入 subject、frequency 和时间范围；
4. Factor 按目标周期逐期计算、写结果并上报 `FactorPeriodComputed`；
5. Result View 处理 Marker 后发布对应 `ViewFactorPeriodReady`；
6. 每个目标周期使用 `hash(request_id,period_time)` 作为 `trigger_event_id`；同一个 request 重试时，已经存在 Factor Marker 的周期直接跳过。

历史周期变化对未来 lookback 的影响范围由 Recalc 调用方明确决定，不在事件消费者中自动扩展。

## 10. View A/B 重建

本文将旧版本笼统的“维护”统一称为“重建检查”。重建检查只负责定期判断
View 是否需要创建新的 B 索引；它不执行通用数据库维护，也不逐行删除 Active View
中的事实数据。文件超限重建失败后的等待称为“超限重建重试间隔”，作用是避免重复启动
昂贵的全量回填，不会暂停 A 的查询和实时写入。

个人单实例采用“旧 View 继续服务、新 View 延迟追平”的简单模型，不需要
`c_build_fence_json`：

1. 当前 Active A 继续提供查询和实时写入；创建非活跃的 Building B；
2. B 从 origin dataset 或当前 Active A 回填历史窗口；
3. B 挂载后，新的行同时写入 A 和 B，Marker 仍以 A 为准发布 ready；
4. 回填只补 B 中缺失字段，不覆盖已经写入的实时值；同一索引的回填和实时写通过一个简单的写入门串行；
5. 回填完成后，只在当前 View 内取得短时互斥锁，等待在途写入完成，再通过 Metadata CAS 激活 B；
6. 切换后新请求只写 B，固定宽限期结束后直接删除旧 A 文件（包括 WAL）。

同一 Dataset 的 rows、period marker 和 sync point 使用同一个 Dataset 队列顺序处理（队列键即
`space_id + dataset_id`，全文统一称为“Dataset 队列键”）。不同 Dataset 仍可并行。
切换不等待整个 durable consumer 的历史 backlog，因此不会因为
其他 Dataset 或旧消息阻塞当前 View。

build 中途退出时，删除本次 Building 并重新完整构建，不恢复复杂游标或证明链。现有 `t_view_index_builds` 的 build ID、state、status、backfilled rows、error 和更新时间足够记录过程。

因此：

- 不新增 `c_build_fence_json`；
- 不新增 `view_period_generations`；
- 不解析 Event ID 作为 outbox 水位；
- 不在业务事件中携带物理 index ID 或 schema hash；
- 接受 B 在构建期间暂时落后于 A，不提供 B 的中间查询；
- 接受显式清空为 `NULL` 的值可能在历史回填时被补回；
- 旧 A 使用固定 grace 后删除，不在 active 索引上逐行删除。

## 11. Binding 生命周期

### 11.1 新建和启用

1. 创建 binding；
2. 确保自动结果 dataset 和 Result View 存在；
3. 把 output fields 加入 Result View desired schema；
4. Result View 新 revision 激活后，把 binding 从 `pending_view` 改为 `enabled`。

Factor 启动和低频定时任务检查 `pending_view` binding 是否已经满足 Source/Result View 字段要求。不计算 dependency hash。

binding enable/disable/unbind 与 realtime/Recalc 共用 Factor 单实例操作门，避免配置变更和结果写入并发，不增加跨服务锁。

### 11.2 Disable 和 Unbind

- disable 先把 binding 置为 disabled，阻止新任务；
- 根据 manifest 清理保留窗口内的旧输出；
- 清理失败时保留操作状态并告警，用户可以重试或执行 Recalc 清理；
- unbind 在清理完成后从 Result View desired schema 移除 output fields；
- Result View 新 revision 激活后删除 binding 和 manifest；
- 自动 Result View 和结果 dataset 默认保留，避免频繁创建和删除。

不为 disable/unbind 引入重建预留、变更门或跨服务事务。

## 12. 配置与运行约束

| 配置/约束 | 默认 | 说明 |
|---|---|---|
| `period_ready_grace` | `2 x frequency`，上限 10m | 周期关闭后的采集等待 |
| `period_item_retention` | 最近 60 个周期 | Collector subject 明细保留 |
| `period_readiness_retention` | 7d | Collector 已上报父状态和固定 payload 保留 |
| `view_period_state_retention` | 7d | 多数据集到齐状态和重复 Marker 去重 |
| `view_sync_point_retention` | 7d | import/catchup 等待和重试 |
| `engine.python_workers` | `100` | 全局数据就绪任务和按需启动 Python 进程的上限 |
| `engine.view_read_workers` | `16` | 不同 period read groups 的最大并行 View 读取数；与 Python 并发独立 |
| `engine.view_read_timeout_ms` | `10000` | 单次 View RPC 超时；临时失败释放槽位并移到队尾重试一次 |
| `factor_manifest_periods` | 覆盖常用 Recalc/lookback 窗口 | 动态 RowKey 清理 |
| Factor source-ready `MaxAckPending` | `1` | 避免执行组交错 |
| View dataset durable `MaxAckPending` | `8` | 通过 Dataset 队列保证行与 Marker 顺序 |
| View consumer replicas | `1` | 个人部署单实例 |
| Factor period ordering | 每个 Factor 实例 `1` 个周期执行组 | realtime 和 Recalc 共用操作门；周期内组合并行 |
| Factor-bound Source View keep | 覆盖 lookback 窗口 | `0` 表示无限；有限值必须不小于绑定 lookback |
| `view_settle_delay` | 删除 | 由完成 Marker 取代 |
| `event_read_retry*` | 删除 | 不再轮询猜测 View 可读性 |

周期内部按严格 identity 合并读取：space、Source View/Dataset、subject、frequency、目标
范围、period 和 trigger 全部相同才共享；lookback 取组内最大值，Python 端按成员 lookback
截取各自窗口。读取列为成员 Factor 输入列的规范化并集；成功后立即进入容量
`2 * python_workers` 的 prepared queue，Python 前按 Factor 投影。该队列满时停止继续预取。
所有读取、计算、清理和写回终态后才能上报
`FactorPeriodComputed`。

实时 Factor durable 使用 `DeliverNewPolicy`、显式 ACK，从当前新到达的 source-ready 开始计算，避免个人部署首次启动时重放全部历史周期造成队列堆积；历史数据重建统一通过显式 Recalc 完成。暂时错误持续重试并告警；对无法自动处理的永久错误，由个人运维决定修复数据、重建 View 或跳过消息。

dataset rebind/migration 作为迁移操作执行：暂停对应 Collector 和 View consumer，完成迁移后从下一周期恢复。禁止促成同一周期完成的行写在旧 DataNode、Marker 却追加到新 DataNode。

## 13. 故障与恢复边界

| 场景 | 简化后的行为 |
|---|---|
| 整次 Timer 未执行 | 周期已预建，deadline 形成 degraded |
| Collector 退出 | SQLite 恢复 item 和 pending report |
| Collector RPC 超时 | 使用固定 Event ID/payload 重试 |
| degraded 后迟到 K 线 | 不自动发第二代事件；需要时显式 Recalc |
| View 行应用失败 | 当前消息不 ACK，后续 Marker 不会越过 |
| View ready 发布后 ACK 前退出 | Marker 重投，可能重复发布同 Event ID |
| Factor 收到重复 source-ready | 先查 Marker；已存在则直接 ACK |
| Factor 部分结果写入后退出 | 重投后重新计算和覆盖；动态残留由 Recalc 修复 |
| Factor Marker 已写但 ACK 前退出 | Marker preflight 命中，不重复计算 |
| 单个因子失败 | 周期为 degraded，成功结果仍产生最终事件 |
| 结果行应用失败 | Result View 不处理后续 Marker，不发最终事件 |
| View A/B build 退出 | 丢弃 Building，从头重建 |
| import 写完但 View 未追平 | SyncPoint 未完成，不启动 Recalc |
| Result View 已被新结果覆盖 | 下游读取最新结果，不保证旧事件快照 |
| EventBus 暂时不可用 | DataNode outbox 或未 ACK Marker 保留重试 |
| manual/import 写自动结果 dataset | Storage 拒绝，统一走 Factor/Recalc |

## 14. 实施顺序

1. 新增四个完成事件、`DatasetSyncPoint` 和 Storage 追加/等待 RPC；
2. Collector 增加周期预建、SQLite item 状态、deadline 和一次性完成上报；
3. View 新 durable 按 Dataset 队列串行处理行、Marker 和 SyncPoint，不同 Dataset 可并行；
4. View 增加最小 dataset 聚合状态并发布 `ViewSourcePeriodReady`；
5. 自动创建独立 factor-result dataset 和 Result View；
6. Factor 改为只消费 source-ready，移除 `EventBatcher`、`ViewSettleDelay` 和 `ErrViewIncomplete` 猜测链；
7. Factor 增加动态 RowKey manifest、结果 clear 和 `FactorPeriodComputed`；
8. Result View 处理 Factor Marker 并发布最终事件；
9. import/catchup 接入 SyncPoint，Recalc 与 realtime 共用全局 TaskRunner；
10. View A/B build 使用 A 权威、B 延迟追平和短时切换锁，不新增复杂构建水位；
11. 补充日志、Metrics、CLI 状态和端到端测试。

重点测试：

- 周期全部成功、部分 subject 超时、整次 Timer 未执行；
- 多条 K 线和完成 Marker 的 outbox 顺序；
- Marker RPC 超时和 EventBus 重复投递；
- 单数据集和多数据集 Source View 聚合；
- Factor 重复消费和进程退出后的 Marker preflight；
- Python 返回零行、动态 tag 从 A 变为 B、从 A 变为空；
- 单个因子失败时的 degraded 最终事件；
- 结果行尚未应用时不得发布最终事件；
- import SyncPoint 完成前不得启动 Recalc；
- realtime 与 Recalc 不得并发写同一个结果 dataset；
- A/B build 期间暂停、积压回放、激活和进程退出重建；
- Source View 不包含 factor-result dataset，动态 tag 不回流输入；
- 非 Factor 调用方不能写自动结果 dataset。

## 15. 后续演进条件

只有出现明确需求和实际问题后，才考虑增加以下能力：

- 多实例 View/Factor；
- 自动 restatement 和 lookback 前向重算；
- 历史不可变结果快照；
- per-dataset 并行消费；
- 跨空间 View；
- 横截面 period-scoped 因子。

这些能力不应提前通过 generation、snapshot hash、read fence、复杂 reservation 或发布状态机进入一期设计。
