# 因子视图驱动计算设计

> 状态：评审稿 v5（2026-08-08，确认采用“同 DataNode outbox 因果 Marker 链”；最终因子完成事件表示结果已在自动管理的 Result View Active 索引中可读）
> 关联文档：《因子计算模块设计.md》《存储层架构.md》《内置市场行情采集架构.md》

## 1. 背景与动机

当前因子计算的触发链路是**行事件驱动 + 启发式等待**：

1. DataNode outbox 逐批发布 `DatasetRowsUpserted` 行事件；
2. Factor 的 `EventBatcher` 用固定时间窗口猜测“本批数据已经写完”；
3. 调度器执行前固定 sleep `ViewSettleDelay`，再以 `ErrViewIncomplete` 做有限重试，猜测“View 已追上”；
4. 每批行事件都可能触发一段 lookback 前向重算。

这套机制存在四个根本问题：

- **没有因果保证**：Factor 与 View 独立消费行事件，Factor 可能先读取到旧索引；
- **重复计算放大**：同一周期的多批行事件会重复触发相同 lookback；
- **业务信号错位**：因子关心的是“本周期输入已经可读”，而不是每一条数据变更；
- **完成语义不清**：结果写入 Storage 成功，不等于结果已经在 View 中可读。

本设计把实时链路改成四段明确的因果屏障：

```text
采集任务终态
  -> 数据集周期采集完成 Marker
  -> View 源数据周期可读
  -> 因子任务终态与结果写入
  -> View 因子结果周期可读（最终事件）
```

## 2. 设计目标与非目标

### 2.1 目标

- Factor 只绑定并读取 View，不理解底层输入数据集；
- Collector 按 `(dataset, freq, period, subject)` 聚合实时采集状态；
- Collector 的完成决定、Storage 行写入、View 可见性之间使用**同 DataNode outbox Marker**建立因果顺序；
- `ViewSourcePeriodReady` 发出时，源数据已经在指定 Active View revision 中可读；
- Factor 对一次 source-ready 事件固定绑定快照，执行该 Source View 的全部 enabled 因子；
- 每个 Source View 自动关联一个以 factor-result dataset 为 primary dataset 的 Result View，动态 `series_tag` 结果不会回流污染下一周期输入；
- `ViewFactorPeriodReady` 是下游唯一的最终完成事件；发出时，所有成功任务实际产生的因子结果行已经在 Result View Active 索引中可读；
- 所有事件按 at-least-once 设计，重复事件通过确定性 ID、状态快照、轻量执行保留与可重入写入处理；
- 采集业务超时或因子计算失败时仍在 deadline 后形成 `degraded` 终态；Storage/EventBus 交付失败则保持未交接并告警，不伪造“结果已可读”；
- 保持个人量化系统的单实例、轻量化边界，不引入分布式锁、通用工作流引擎或 Exactly-Once 协议。

### 2.2 非目标

- 一期不做因子级联 DAG，`dataset_role=factor_result` 的列禁止作为因子输入；
- 一期不支持跨空间 View；
- 一期不支持横截面 period-scoped 因子，继续使用现有 per-subject Python 因子契约；
- 不能发现“根本没有写入 Storage”的交易所静默重述；该类差异仍由对账任务发现并调用 `RecalcFactor`。Collector 已观测到的同状态有效值变化则必须产生 restatement，以闭合 View read fence；
- Catchup 和 `moox-cli storage import` 不逐周期广播实时 ready；
- 不为 Factor 新增完整的 `FactorRun`、durable inbox 或 per-task 调度状态机；但保留一条 source-ready 对应的不可变 binding 快照，以及动态输出 RowKey manifest，两者都是崩溃恢复所需的最小持久化。

## 3. 总体架构

### 3.1 四类完成信号与职责

| 信号 | 业务含义 | 决策方 | 实际发布方 |
|---|---|---|---|
| `DatasetPeriodCollected` | 数据集本周期所有预期 subject 已进入终态 | Collector | 目标 DataNode outbox |
| `ViewSourcePeriodReady` | 本周期源数据已在 Source View Active 索引中可读 | View | Storage/View |
| `FactorPeriodComputed` | 本周期全部绑定因子已终态，结果 upsert 与旧值 clear 已提交 Storage | Factor | 结果数据集 DataNode outbox |
| `ViewFactorPeriodReady` | 成功结果与失败/消失输出的 clear 已在 Result View Active 索引中可读 | View | Storage/View |

Collector 和 Factor 负责做业务聚合；Storage 负责把“完成决定”转换成与数据行同序的 Marker；View 负责确认实际可读性。

Catchup/import 另外使用辅助的 `DatasetWriteBarrier` 事件证明“本次覆盖写已被 View 应用”。它不表示业务周期完成，不进入上述四段实时链。

Source View 与 Result View 必须分离。当前 View 的普通查询按 primary dataset 定义行域，而 Factor 允许 Python 生成新的动态 `series_tag`。若把 factor-result dataset 直接并入 Source View，派生 tag 可能无法物化，或作为缺少源字段的额外行进入下一周期 Factor lookback。独立 Result View 同时保留动态 tag 契约和输入隔离，且每个 Source View 只增加一个自动管理的 Result View。

### 3.2 完整链路

```text
Collector                         Storage / View                         Factor
─────────                         ──────────────                         ──────
预建周期 T expected subjects
监听 DatasetRowsUpserted
按 row.data_time 更新 subject
deadline 后剩余 pending -> timed_out
全部 subject 终态
  │ ReportDatasetPeriodCollected
  ▼
                                  Primary 按 (space,dataset) 路由
                                  到该 dataset 所属 DataNode
                                  同 outboxMu 追加 source marker
                                    │ DatasetPeriodCollected
                                    ▼
                                  View 同 dataset lane：
                                  先应用此前行，再处理 marker
                                  全部 Active 输入 dataset 到齐
                                    │ ViewSourcePeriodReady
                                    └──────────────────────────────────► 固定 enabled binding 快照
                                                                         按 (binding,subject) 计算
                                                                         结果 upsert/旧值 clear 写结果 dataset
                                                                         全部任务终态
                                                                         │ ReportFactorPeriodComputed
                                                                         ▼
                                  结果 dataset 所属 DataNode
                                  同 outboxMu 追加 factor marker
                                    │ FactorPeriodComputed
                                    ▼
                                  Result View 先应用全部结果行，
                                  再处理 marker
                                  校验结果列在其 Active schema 中可读
                                    │ ViewFactorPeriodReady
                                    ▼
                                  策略/下游开始读取本周期结果
```

### 3.3 核心不变式

1. **采集 Marker 保序**：`DatasetPeriodCollected(dataset,T)` 的 outbox ID 大于促成该快照的全部 K 线行事件；
2. **源数据可读**：`ViewSourcePeriodReady(source_view,T)` 发出时，事件携带的 `active_view_revision/schema_hash/index_id` 已成功应用对应源数据 Marker 之前的全部行；这是读取下界，不声称 View 为该事件保留不可变 as-of 快照；
3. **因子 Marker 保序**：`FactorPeriodComputed(source_view,result_view,T)` 的 outbox ID 大于该执行组全部结果 upsert 和旧结果 clear 事件；
4. **最终可读**：`ViewFactorPeriodReady(result_view,T)` 发出时，全部成功因子结果已在事件携带的 Result View Active 索引中可读，本次快照中消失或失败任务的旧字段值已清空；
5. **失败不穿透**：任何行事件永久应用失败后，该 dataset lane 进入 blocked；后续 Marker 不得越过失败行发 ready；
6. **输入/结果隔离**：Source View 永不包含 factor-result dataset；Result View 以 factor-result dataset 为 primary，因子输入也不得引用 factor-result 列；
7. **执行身份稳定**：一个周期的 expected subjects、Active View 契约和 enabled binding/target set 在对应执行阶段内固定；任务实际读到的输入行另外纳入 write plan hash。
8. **结果写入独占**：自动 factor-result dataset 只接受 Factor 服务携带稳定 source ID 的写入；同 result dataset 的 mutation gate 持有到最终 emission 已发布或被判定为内容相同而 coalesced，外部 manual/import 不得插队覆盖。

## 4. 事件协议

四个实时完成事件和一个 import 辅助 barrier 都登记在 `MOOX_STORAGE` Stream，由 Storage 组件实际发布。Collector 和 Factor 通过 RPC 上报决定，不直接跨 Stream 发布完成事件。

| 事件 | Subject 末级 | 载荷 |
|---|---|---|
| `storage.dataset.period.collected` | `<space>.<dataset_id>` | `DatasetPeriodCollected` |
| `storage.view.source_period.ready` | `<space>.<source_view_id>` | `ViewSourcePeriodReady` |
| `storage.dataset.factor_period.computed` | `<space>.<result_dataset_id>` | `FactorPeriodComputed` |
| `storage.view.factor_period.ready` | `<space>.<result_view_id>` | `ViewFactorPeriodReady` |
| `storage.dataset.write_barrier` | `<space>.<dataset_id>` | `DatasetWriteBarrier` |

### 4.1 完成与降级语义

- `complete`：该阶段全部 expected item 成功；
- `degraded`：全部 expected item 已终态，但存在 `timed_out/skipped/failed`；
- 最终事件的 `complete` 保证所有预期因子任务成功，且这些任务实际产生的结果行与对旧 RowKey 的精确清空均可读；因子合法返回零行时 `written_row_count=0`，但仍必须清空 manifest 中本周期的旧输出；
- 最终事件的 `degraded` 保证成功结果可读，失败/跳过任务的已知旧输出已精确清空，缺失项在载荷中完整列出；下游不得把上一快照结果当成本快照结果；
- “全部完成”始终表示**全部进入终态**，不是“全部成功”。

### 4.2 幂等与快照

- 不暴露业务 readiness revision；
- expected subjects、dataset states、binding states 均先排序、规范化，再计算 snapshot hash；
- View ready Event ID 由 `phase/view/freq/period/Active triple/snapshot hash` 确定性生成；同一业务快照在兼容新 Active 重建时得到新的 Event ID，避免被旧 triple 的 cancelled intent 唯一键吞掉；
- 同一 snapshot 的重复 RPC、outbox 重发和 JetStream 重投产生同一 Event ID；
- snapshot 发生有效变化时产生新 Event ID，并按 restatement 重新执行；
- 同一 `(source_view,freq,period,Active triple)` 的首个已发 snapshot 为 `initial`，后续不同 snapshot 为 `restatement` 并指向上一个 Event ID；这个链接只表示计算因果，不引入可变 revision 号；
- 每个新 snapshot 在 Metadata 同一事务内先生成不可变 emission intent，再更新当前信号行；publisher 不直接从可覆盖的 current payload 发事件。
- publisher 标记 current emitted 时必须 CAS 当前 snapshot hash，不能只比较 `state`；CAS 只是当前快照的便捷水位，不决定不可变 emission 历史是否存在。
- 事件业务时间在 emission intent 创建时固定并持久化；同一 Event ID 的重发复用原时间，不在发布时重新调用 `time.Now()`。
- `FactorPeriodComputed` 必须自包含 source/result Active triple、source dependency hash、binding contract hash 与 output field IDs；View 不依赖可能已被 restatement 覆盖或删除的可变 binding 元数据来验证最终可读性。
- Factor 输出先做统一规范化：一个 RowKey 的本 binding 输出字段全部为 NULL 时，该行等价于“本因子无输出”，从 current manifest 移除并走 clear；至少一个字段非 NULL 的 current row 才保留，未返回的其他 output field 规范化为显式 NULL。由此 NULL 物理行与已 clear 的旧行具有相同逻辑语义，不要求 View 区分。
- `FactorBindingPeriodState.output_manifest_hash` 对排序后的 current RowKeys 计算；`output_content_hash` 对这些行的 `(RowKey,sorted(field_id,TypedValue))` 计算，不包含 trigger/input provenance。由于每个 binding 使用独占 output namespace，View 可扫描该 target period 中“任一 output field 非 NULL”的全部行，把查询省略的字段补成 NULL，独立重建两个 hash并核对不存在 manifest 外非 NULL 残留；不需要从 hash 反推 Python preimage。

## 5. Collector：周期采集状态

### 5.1 复用当前能力

当前 Collector 已有：

- 稳定的 `TaskInstance` 与 SCF assignment；
- `DatasetRowsUpserted` durable consumer；
- Storage 行事件到 `TaskInstance` freshness 的 SQLite 更新；
- MarketFetch completion、重试和 deadline 观测。

本设计不再把 `MarketFetchBatchCompleted` 作为实时 readiness 的必要输入。实时 Timer 当前不发布 completion，K 线行事件已经是“Storage 已提交成功”的更强信号。

### 5.2 周期任务预建

`PeriodReadinessTracker` 在每个周期开始前或开始时：

1. 从当前未删除的 `TaskInstance` 按 `(space,dataset,freq)` 读取预期 subject；
2. 固定本周期 `expected_subjects` 与 `expected_hash`；
3. 为每个 item 固定 task ID、expected write source、必需 field IDs 和必需 series-tag cohort；
4. 创建 `(dataset,freq,period)` 父状态及 subject item；
5. 计算 `deadline_at = period_close + period_ready_grace`。

必须预建周期，不能等第一条行事件到达后才创建。否则整次 Timer 未执行时没有任何状态可供 deadline 扫描。

assignment 在周期中发生变化时不修改已创建周期的 expected 快照；新 assignment 从下一周期生效。

`period_time` 统一表示 UTC 周期起始时刻：秒级固定频率按 epoch 秒向下对齐，日及以上频率按 UTC 日历对齐；Collector 调度、行事件归期、View ready 和 Factor 任务必须复用同一套周期函数。

一期要求同一 `(space,dataset,freq,subject)` 只有一个有效 Collector task；预建时发现重复任务必须 fail closed，不能把一个行事件同时算作多个未知任务完成。

### 5.3 由 K 线行事件更新状态

Collector 的 Storage write consumer 对每个 `DatasetRowsUpserted.rows[]`：

1. 从 RowKey 读取 `dataset_id/subject_id/freq/data_time`；
2. 用 `data_time` 对齐 period，不使用事件 envelope 时间；
3. 仅接受 `write_source` 与该周期预建 task/assignment 快照一致的 Collector 写入；manual/import/factor 及未知来源写入不推进实时 readiness；
4. `DatasetRowsUpserted` 是字段 delta，先把本事件的 field/tag 及其值合并到 item 的 observed contract；只有 observed 已覆盖预建 required field/tag contract 时，才计算规范化 required data hash 并执行 `pending|timed_out -> success`；
5. 同一 subject/period 的重复行幂等；
6. 一个 BarLimit 批次写入 T-2/T-1/T 时，分别更新三个实际 `data_time`，不再扩展 `MarketFetchItemResult.affected_periods`。

一期约束：一个 Collector K 线 task 对应一个 `(dataset,subject,freq)`。当前执行器通常一次写完整 K 线，但 tracker 仍按 required/observed contract 验证，不能把“看到任意一行或一个字段”直接解释为整个 subject 成功。若未来一个 subject 需要多个独立采集任务，readiness key 必须增加 task 维度。

### 5.4 状态持久化与内存边界

Collector 周期状态以 SQLite 为准，内存只做当前少量周期的缓存：

1. handler 在 SQLite 事务内更新 item；
2. 同一事务对排序后的 `(subject,state,required_data_hash)` 重算 failed subjects 与当前 snapshot hash；
3. 若全部 item 终态且 hash 尚无 report intent，在该事务中分配严格递增的 `generation`，固定 `collected_at`，以当前最后一条 intent 的 report ID 填 `previous_report_id`，生成完整规范化 payload 与 `report_id = hash(space,dataset,freq,period,generation,snapshot_hash)`，插入不可变 report intent，再把父状态置为 `report_pending`；
4. 事务提交后更新内存缓存并 ACK Storage 行事件；
5. 独立 reporter 对每个 readiness 按 generation 串行扫描 pending intent，前一代未确认时不发送后一代；仅使用已持久化的 report ID/payload 调用 `ReportDatasetPeriodCollected`，RPC 超时重试不得重新取时钟或重建 payload；
6. RPC 成功后把该 intent 置为 reported，并推进父级 reported generation/hash；若期间状态变化，新快照保留为下一代 pending。旧请求即使晚到 DataNode，也会被 compare-and-append 规则判为已应用或 stale，不得覆盖新代。

禁止“只写内存后 ACK”。否则进程在 ACK 后退出会永久丢失本周期状态。

subject 明细只保留短窗口，例如最近 60 个周期；父级摘要按 View/因子补算需要保留更久，避免每分钟 500 subject 长期累计形成无界表。

Collector 启动顺序固定为：恢复 TaskInstance/assignment -> 幂等补建当前周期和最近 recovery window 的缺失周期 -> 启动 deadline worker -> 最后启动 Storage write consumer。consumer 遇到 recovery window 内尚未预建的行事件时 NAK 等待补建，不能直接 ACK；窗口外事件 ACK 并交给显式 Recalc/对账处理。

### 5.5 Deadline 与 restatement

- deadline 到达时仍为 `pending` 的 subject 置为 `timed_out`；
- 全部 `success` 时报告 `complete`；
- 存在 `timed_out` 时报告 `degraded`；
- subject 明细保留窗口内的迟到 K 线允许 `timed_out -> success`，形成新 snapshot，并以 `source=restatement` 再报告；窗口外修正走显式 Recalc；
- `success` 不回退；
- `success -> success` 时，required data hash 不变的幂等重写不发 restatement；hash 变化则更新父 snapshot 并发 restatement。因而 BarLimit 重写相同 K 线不会重算，但已实际改值的历史行不会绕过读 fence。
- generation 1 使用 `source=realtime`，后续有效快照使用 `source=restatement`；该顺序由持久化 report chain 决定，不能用 `collected_at` 或 snapshot hash 比大小。

## 6. Storage：同 DataNode Outbox Marker

### 6.1 追加与查询 RPC

Storage Primary 新增：

- `ReportDatasetPeriodCollected`：Collector 上报源数据集周期终态；
- `ReportFactorPeriodComputed`：Factor 上报结果数据集周期计算终态；
- `AppendDatasetWriteBarrier`：import/catchup 按 dataset 追加与覆盖写同序的 barrier；
- `GetFactorPeriodReports`：Factor 传入 `(space_id,source_view_id,source_ready_event_id)` 查询该 trigger 已追加的全部 target-period Marker；Storage 由 source-view/result-dataset 自动关系路由到结果 DataNode，并结合 Metadata 返回 report ID/payload hash、`target_set_hash`、Marker `handoff_complete` 及每个 report 的 final publication/coalesced 状态；
- `WaitViewFactorPeriodReady`：Factor 按 report IDs 等待每个目标周期进入 final terminal：emission 已 `published`、结果内容与当前已发布快照相同而 `coalesced`，或自动 Result View 契约被显式管理操作废弃而 `superseded`；
- `ListViewSourceReadySnapshots`：Factor 在 restatement 扩展时按 `(source_view_id,freq,period_range)` 读取每个目标周期当前已发的 source-ready Event ID/snapshot/Active triple；
- `WaitViewBarrier`：CLI 按 `(view_id,correlation_id,expected_dataset_ids)` 等待当前 Active View 应用全部 dataset barrier。

三个追加类 RPC 都必须：

1. 校验公共的 `(space,dataset)` 与调用方权限；两个 period report 另外校验 `(freq,period)`，barrier 另外校验 `correlation_id/source`；
2. 按 `(space,dataset)` resolver 找到**该 dataset 当前绑定的 DataNode**；
3. dataset 处于 rebind/migration 中时拒绝追加 Marker；迁移完成后从下一周期重新建立 readiness，避免促成完成的行在旧节点而 Marker 落到新节点；
4. 携带确定性 `report_id/barrier_id` 调用目标 DataNode；
5. DataNode 在与行写相同的 `outboxMu` 下分配下一个 outbox ID；
6. 写入完整 `EventMessage`，并复用 source-event 去重机制处理 RPC 超时重试；Marker report 的 processed-source 记录需同时保存 payload hash，供 preflight 查询；相同 ID 但 payload hash 不同必须拒绝，不能静默返回旧 Marker。

`ReportFactorPeriodComputed` 还必须对 `(source_ready_event_id,period_time)` 做唯一交接约束：同一 trigger 的一个目标周期只能关联一个 report ID。所有 Marker 重复携带规范化 `planned_target_periods/target_set_hash`；Storage 只有在该集合的每个周期都已有同 hash Marker 时才返回 `handoff_complete=true`。该二级索引与 report payload 在同一 DataNode 批次内提交，防止 binding 变更或并发重投产生第二个目标 Marker。

`ReportDatasetPeriodCollected` 另外在 DataNode 批次内维护 `(dataset,freq,period) -> latest generation/report_id`：同 generation/ID/hash 重试幂等成功；仅当 `generation=latest+1` 且 `previous_report_id=latest_report_id` 时追加下一代；generation 更旧返回 stale success，更高但 predecessor 缺失返回可重试错误。这样即使 S2 RPC 先到、S1 的超时请求后到，outbox 中也只能按 S1 -> S2 排列，旧 degraded 不会覆盖新 complete。

自动结果 dataset 设置不可变属性 `dataset_role=factor_result, write_owner=factor`。Primary 只允许 Factor 内部身份携带稳定 `source_event_id` 的字段级 upsert/clear、Factor Marker/Recalc barrier，以及 Storage/View 构建器的 `source=view_build` 内部 barrier；DataNode 再按 dataset 属性和内部调用凭据做防御性校验。CLI import、manual upsert 和其他服务直接写该 dataset 必须拒绝，运维修复统一走 `RecalcFactor`/barrier 协议，避免绕过 `ResultMutationGate` 在 Marker 与最终 PubAck 之间改值。

“该空间任意 DataNode”或由 Primary 直接发布都不满足顺序保证。

### 6.2 Outbox 扩展

DataNode outbox publisher 从只接受 `DatasetRowsUpserted` 扩展为接受受治理的 Storage dataset 事件：

- `DatasetRowsUpserted`；
- `DatasetPeriodCollected`；
- `FactorPeriodComputed`；
- `DatasetWriteBarrier`。

Relay 继续按 outbox ID 单线程发布；任一较早条目发布失败时不得越过它发布后续 Marker。

DataNode 的 processed-source 去重记录同步扩展为保存 payload hash。该规则既用于两个 Marker report，也用于 Factor 的稳定结果写 source ID；重复 ID 且 hash 相同返回幂等成功，hash 不同返回冲突。

## 7. View：两次可读性确认

### 7.1 单 Consumer、同 Dataset Lane

View 使用一个新 durable consumer，通过 `FilterSubjects` 同时订阅行写、采集 Marker、因子 Marker 和 write barrier 四类 dataset 事件。一个 View consumer durable 在个人部署中只允许一个活动实例；一期设置 `MaxAckPending=1`，用全局 head-of-line 换取最简单、可证明的顺序，吞吐确认不足后再设计显式 per-dataset sequence 并放开并发。

`subjectDispatcher` 的串行键必须从完整 NATS subject 改为 `(space_id,dataset_id)`，保证同 dataset 的行与 Marker 进入同一 lane。

不能解析 `EventMessage.event_id` 猜 outbox ID，也不能把 JetStream `StreamSeq` 当成单 dataset 业务水位：带 `source_event_id` 的 Storage 写没有可解析的 outbox 后缀，StreamSeq 又属于整个 Stream。一期的因果性只来自同 DataNode 顺序 outbox、单活动 consumer、`MaxAckPending=1` 和 dataset lane。

处理规则：

- 行事件在 Active/Building 物理索引的同一本地事务中应用数据，并在映射列有实际值变化时推进该 `(origin_dataset,freq,period)` 的 applied generation；二者成功后才 ACK；
- 暂时性本地/Metadata 故障对当前 delivery 持续 `InProgress` 并在 lane 内原地重试，不得 NAK 后继续处理后续消息；进程退出则由同一条未 ACK 消息重投；
- 行事件达到永久失败或重试上限时，先持久化 dataset lane blocked，再 TERM；
- blocked lane 可以继续接收消息，但任何后续 Marker 只能记录“被阻塞”，不得形成 ready；
- 完成权威回填/索引重建并核验成功后，显式清除 blocked，并重新评估保留窗口内已登记的 Marker；满足条件时补发对应 ready。

Marker 的 ACK 边界固定为：Metadata merge 事务已持久化 dataset/factor snapshot 或 blocked 状态后 ACK；Metadata RPC/SQLite 暂时失败时保持当前 delivery 并原地重试；协议永久非法时记录告警后 TERM。不能 NAK 当前消息后越过它处理后续消息，不能只在内存看到 Marker 就 ACK，也不能因 lane blocked 无限保留同一 JetStream delivery。

每个 time-series 物理 View 索引增加 `view_period_generations`，与 `view_rows` 同库：

```sql
CREATE TABLE view_period_generations (
    origin_dataset_id VARCHAR NOT NULL,
    freq VARCHAR NOT NULL,
    period_time BIGINT NOT NULL,
    applied_generation UBIGINT NOT NULL,
    sealed_generation UBIGINT NOT NULL,
    sealed_snapshot_kind VARCHAR NOT NULL,  -- none | source_marker | factor_final | barrier_invalidated
    sealed_snapshot_hash VARCHAR NOT NULL,
    PRIMARY KEY (origin_dataset_id, freq, period_time)
);
```

行 patch 只有在 SQL `IS DISTINCT FROM` 比较确认映射值真正变化时才推进 `applied_generation`，因而 BarLimit 重写相同值不会使周期变 dirty。`DatasetPeriodCollected` 在同 dataset lane 到达后，View 把对应周期的 `sealed_generation` 推进到当前 applied generation，并记录 `source_marker/snapshot_hash`；只有封存成功才参与 source-ready 聚合。任何后续有效值变化都会使 `applied_generation > sealed_generation`，直到 Collector restatement Marker 再次封存。

### 7.2 Metadata 所有权

View 进程不直接打开 metadata SQLite。所有 readiness merge、snapshot CAS 和 blocked 状态通过 Storage Metadata RPC 执行，由 Primary/Metadata repository 持有事务边界。

至少需要六个内部操作：

- `MergeViewSourceDatasetPeriod`；
- `MergeViewFactorPeriod`；
- `SetViewDatasetDeliveryHealth`；
- `ListViewSourceReadySnapshots`；
- `MarkViewBarrierApplied`；
- `GetViewBarrierState`（由 Primary 的 `WaitViewBarrier` 轮询或长轮询封装）。

上述 Marker merge 与 barrier applied 必须在同一个 Metadata SQLite 中追加统一的 `dataset lane ledger`。它的自增 `lane_order` 只表示 View 已处理顺序，不从 Event ID/StreamSeq 推导；同一 event 重投按 Event ID 幂等。Result build 用这张统一 ledger 比较 Factor Marker 与 invalidating barrier 的先后，不能比较分散表各自的自增 ID。

### 7.3 源数据周期可读

处理 `DatasetPeriodCollected(dataset,T)` 时：

1. 先校验 Marker generation 与 `previous_report_id` 链，再把 dataset 当前 Marker 快照持久化到独立 `dataset-period snapshot`；同 generation 重投幂等，较旧 generation 只记审计不覆盖 current，合法下一代覆盖 current snapshot 并保留 emitted 事件记录；
2. 找到 Active schema 中使用该 dataset 的 Source View；
3. 以 Active dependency set 计算 source readiness，不能使用 desired schema；
4. source aggregation row 的唯一键等价于 `(view_id,freq,period,active_view_revision,active_schema_hash,active_index_id)`，同一 Active triple 下的多 dataset Marker 合并到这一行；
5. Active schema 的全部 periodic source dataset Marker 到齐，且所有 lane 健康后，生成规范化 source snapshot；
6. snapshot 与已建 intent 不同时，在同一 Metadata 事务中确定 Event ID/业务时间/完整 payload，按该 signal 之前最新 emission intent 填充 `source=initial|restatement` 和 `supersedes_event_id`，插入 `state=pending` 的不可变 emission 行，再更新 current signal 为 `ready_pending`；
7. publisher 按 emission `c_id` 顺序处理同一 `(view,freq,period,phase,Active triple)` 的 pending intent，不越过旧 intent。发布前获取单实例 per-view `PublishActivationGate` 共享租约，并在租约内复核 intent triple 仍是当前 Active；不匹配时把旧 intent 标为 `cancelled_active_changed`，由 activation reconciler 在新 triple 重建 source/factor signal，不发布旧 payload。匹配时持有租约直到 PubAck 和 emission `published` 提交，`ActivateViewIndex` 只能获取排他租约，因而不能插入“检查后、PubAck 前”。若在 PubAck 后退出，重启会以同 Event ID 重发；current snapshot CAS 失败不删除已发 emission，新 snapshot 仍由后续 pending intent 发布。

Source View 激活新 Active revision 时，Metadata 使用保留窗口内的 dataset-period snapshots 重新评估当前和最近周期。因而旧 revision ready 被 Factor 判 stale 并 ACK 后，新 Active triple 仍会产生对应 ready，不会永久漏掉切换窗口内的 T。

一期的 subject 集合采用 View 的现有主时间轴语义：

- `primary_subjects` 来自 primary dataset 的 expected subjects；
- secondary-only subject 不创建 Factor task；
- primary subject 只有在属于某个必要输入 dataset 的 expected 集合且位于其 failed 集合时，该 binding 才判为 degraded；不属于该 dataset expected 集合表示 not-applicable，不自动算失败；
- Factor 按绑定 input mapping 追溯实际依赖 dataset，不能简单把任意无关 dataset 的失败放大到所有因子。

一期只允许 dataset attribute `readiness_mode=periodic` 的 Collector 管理型 time-series dataset 作为 source-ready 依赖，并要求所有 periodic source 使用与 Source View 相同的 freq。静态维表和其他无周期 Marker 的数据集暂不进入因子 Source View；factor-result dataset 只允许作为自动 Result View 的 primary dataset。

`ViewSourcePeriodReady` 必须携带 `active_view_revision/schema_hash/index_id`。Factor 读取时传入相同 expected active 信息；不匹配则拒绝读取旧/新混合 schema。

`source_dependency_hash` 不直接复用现有 schema hash，而是对以下规范化内容计算：Source View ID、frequency、filter JSON、primary dataset ID、排序后的 ViewColumn origin `(dataset_id,field_id,type)`，以及排序后的 periodic dependency `(dataset_id,readiness_mode,frequency)`。Active revision/index ID 单独用于精确 fencing，不放入 dependency hash，因而契约相同的 A/B 切换可判定为兼容。

该契约必须在索引构建声明时从 desired View 定义一次性快照到 `t_view_index_builds`，`ActivateViewIndex` 再与 active revision/columns/schema hash 同一事务复制到 `t_views.c_active_dependency_contract_json/c_active_dependency_hash`。source-ready 聚合、Factor fencing 和 `BindingReconciler` 只读这份 Active 快照，禁止在发事件时用可变的 desired `dataset_ids/filter_json/t_view_columns` 临时重建 hash。

Building 索引不能只复制旧 Active：首建没有 Active，新增列也不在旧 schema 中；当前逐 RowKey “Building 已存在就整行跳过”的回填还会在 live delta 只写部分字段时漏掉同 RowKey 的其他字段。因此一期把权威回填列为激活前置协议：

1. 为每次构建/恢复创建新的 `build_attempt_id`，注册 Building 后获取现有 `liveGate` 独占租约，排空在途 delivery 并阻止新的 View live apply；
2. 清空本 attempt 的 Building 内容，通过新增的 Storage/DataNode 只读 scan API，按 desired dependency contract 全量枚举 origin datasets，结构化物化全部目标字段、NULL 和 RowKey；禁止因 RowKey 已存在而整行跳过，若采用 merge 必须逐字段合并并保留显式 NULL；
3. scan 期间 Storage 仍可写，这些写对应的行事件停留在 consumer；无论 scan API 使用一致性 snapshot 还是分页读取，任何未反映在 scan 结果中的提交都必须有一条排在后置 build barrier 之前的行事件，并在 gate 释放后应用，因此不要求从字符串 event ID 猜 outbox watermark；
4. scan 完成后释放 gate，继续把 live 行/Marker/barrier 双写 Active/Building；随后为每个 origin dataset 追加 `DatasetWriteBarrier(source=view_build,correlation_id=build_attempt_id,affected_ranges=scanned_ranges)`；
5. 同 DataNode outbox 保证 scan 期间及之前提交但尚未应用的行事件排在 build barrier 前。只有 Building 实际应用全部 build barriers、generation/seal 与 retained Marker/barrier ledger 校验一致，且相关 lane 未 blocked，才持久化 `build_fence` 并允许 READY/Activate；对 Result View 还必须按统一 `dataset lane ledger.c_lane_order` 重放每个保留期的 Factor Marker 与 Recalc/maintenance barrier：最后 seal-affecting 事件是 Marker 时才扫描核对并重建 `factor_final/hash`，最后事件是 mutation barrier 时重建 `barrier_invalidated/空 hash`。普通 build barrier 不改变这个业务 snapshot 状态；
6. `build_fence` 记录 build attempt、dependency contract、每个 dataset build barrier ID、已重放的 ledger high-order，以及 rows/generation/applied-ledger 的规范化 hash。中途退出时废弃未完成 attempt，以新 attempt 清空重扫并追加新 barrier；不能重用已被 outbox 幂等吞掉的旧 barrier，也不能只凭 row count、coverage 或未落库的 cursor 判断完成。

该协议需要替换当前“只从 Active backfill/整行 skip”的实现，而不是仅在 Metadata 补一条完成记录。旧 Active 在 gate 期间仍可提供上一个一致快照，但不会产生新的 ready；这是个人系统可接受的短暂 View 更新停顿。

### 7.4 因子结果周期可读

自动 Result View 处理结果 dataset 的 `FactorPeriodComputed` 时：

1. 同 lane 中此前的全部因子结果行与旧 RowKey 的定向 NULL patch 已经成功应用；
2. 校验 payload 的 `result_view_id` 与 result dataset 的自动管理关系一致，且 Factor Marker 自包含的 source Active triple/dependency contract、calculation input hash 和 binding contract hash 内部一致；Source View 在计算完成后切换不阻断旧 report，因为读阶段已经 expected-active fenced；
3. 校验自动 Result View 当前 Active 仍以该 result dataset 为 primary，并包含该代全部 output fields。正常 A/B 必须保留已预留 binding 的字段；若管理操作违规移除导致旧结果不可读，把 report 标为 `superseded`、不发布 final event 并释放 gate，不能永久 blocked；
4. 在一个 Result View 物理读写事务中扫描每个 binding 的 namespaced fields，重建并核对 output manifest/content hash；再规范化计算 `factor_snapshot_hash = hash(target_period,top_level_status,sorted(binding_id,factor_id,contract_hash,output_field_ids,expected_count,success_count,skipped_subjects,failed_subjects,written_row_count,cleared_row_count,output_manifest_hash,output_content_hash))`。列表先排序，不能使用 proto 到达顺序；该 hash 只排除 trigger/input provenance 和业务时间；
5. 同一物理事务把该 result dataset/target period 的 `sealed_generation` 推进到当前 `applied_generation`，并写入 `sealed_snapshot_kind=factor_final/sealed_snapshot_hash=factor_snapshot_hash` 后提交；三者共同固定本 report 的可读 result generation；
6. Metadata 以 `(result_view,freq,target_period,Active triple)` 查找此前最新已发布的 factor-phase snapshot。完整结果/质量语义相同时把当前 report 标为 `coalesced` 并只保留 Marker 审计；实际变化时创建 factor phase emission intent，可靠发布 `ViewFactorPeriodReady`。

factor emission publisher 在 `PublishActivationGate` 共享租约内再次验证：intent triple 仍是当前 Result Active、本周期 generation 等于 Marker 封存值、当前可读内容 hash 与 payload 相同。不一致时不得发布：兼容 Active 切换取消旧 intent，并在新 triple 重新评估同 Marker；无法恢复可读性的管理型 schema 变更才把 report 收敛为 `superseded`。正常情况下结果值稳定性由延长到 final terminal 的 `ResultMutationGate` 和 factor-result 写 ACL 保证，generation/content 检查是防御性 fail closed。

事件里的 Active triple 表示 **PubAck 时** 提供读取的索引，不承诺永远保持 Active。其后发生兼容 A/B 切换时，权威 build/barrier 协议必须保证同一 factor snapshot 已进入新 Active；下游晚到读取使用 `result_view_id + period + factor_snapshot_hash` 校验当前 View 内容，不把旧 index ID 当永久路由地址。若当前内容已被更新代替，返回 superseded/current snapshot，而不是尝试读取已删除旧索引。

`ViewFactorPeriodReady` 是交易策略和其他下游监听的**最终事件**：

- `complete`：本周期全部预期因子任务成功，且其实际写出的结果行均可从 payload 指定的 Result View 读取，已从 manifest 消失的 RowKey 不再保留本因子的旧字段值；
- `degraded`：所有因子任务已终态，成功结果可读，失败/跳过任务的已知旧字段值已清空，对应清单完整；
- 下游不监听 `FactorPeriodComputed`，该事件只是结果行与最终 ready 之间的内部 Marker。

## 8. Factor：执行组与结果 Marker

### 8.1 Source-ready 消费

Factor 新 consumer 订阅 `storage.view.source_period.ready`：

1. 收到 `source ready Event ID` 后，先调用 `GetFactorPeriodReports`；只有 `handoff_complete=true` 且全部 report 已进入 `published|coalesced|superseded` terminal 才直接 ACK；部分目标周期已有 Marker 时恢复缺失工作，Marker 已齐但 final 未终态时只恢复等待，不再写结果；
2. 在 Factor SQLite 查询该 source-ready 的 group reservation；已存在时必须复用其不可变 binding/target plan，不再以当前 View/binding 替换；如果 Storage 已有部分 Marker 但本地 reservation 缺失，必须 fail closed 并告警，不可猜测剩余 target set；
3. reservation 不存在时，先用 `ListViewSourceReadySnapshots` 校验该 Event ID 仍是 trigger period 最新已发 snapshot，且 Active triple/dependency hash 仍是当前契约；已被新 restatement 取代或 Active 已过期则 ACK，由最新 source-ready 接管；
4. 读取当前 enabled binding，snapshot 包含 binding ID、不可变 factor source 内容或版本化引用及其 hash、lookback、input/output mapping、subject scope，以及 Source/Result View Active triple；
5. `initial(T)` 的 target plan 只包含 T；`restatement(T')` 则对每个 `(binding,subject)` 沿 Source View 实际存在的 data_time 向后扩展，直到 T' 移出该因子 lookback 窗口，并只保留已有 current source-ready snapshot 的目标周期；因而尚未 ready 的未来周期会在正常 initial 路径自然读到修正后历史；
6. 对 target plan 的每个周期固定 target source-ready Event ID 和预期 `(binding,subject)` 集合，规范化后生成 `binding_set_hash`、`planned_target_periods` 与 `target_set_hash`；
7. 在 SQLite 事务内持久化完整 binding/target snapshot，并为每个目标周期计算 `report_id = hash(source_ready_event_id,binding_set_hash,target_period)`；
8. 以 reservation 创建内存执行组，按 target plan 展开 `(target_period,binding,subject)` 任务，跳过 preflight 已有 Marker 的目标周期。

新 binding 在 reservation 创建后不加入本组，从下一次 source-ready 生效；已预留组的重投不因当前 binding 变化而换组。如果预留时没有 enabled binding，记录 `no_work` reservation 后 ACK，不生成结果 Marker；该记录至少保留到 source-ready 事件超出 Stream 与 readiness 保留窗口。

已建 reservation 在第一个 task plan 持久化之前若发现 trigger 已被新 restatement 取代，可将其置为 `superseded` 并 ACK；一旦任何 pending/last plan 或 Marker 已存在，必须按原 reservation 收敛完整交接，后续 restatement 再写新一代。

### 8.2 内存执行组为何可接受

与 Collector 不同，Factor 的全部工作由一条 `ViewSourcePeriodReady` 父消息触发：initial 只有一个 target period，restatement 可有多个。调度与 per-task 进度只放内存，但 binding/target 快照和输出身份必须持久化，并满足：

- 父消息在整组完成、`planned_target_periods` 全部成功追加 `FactorPeriodComputed` Marker，且对应 final 状态全部进入 `published|coalesced|superseded` terminal 前不 ACK；
- 计算期间周期性发送 JetStream in-progress heartbeat；
- 进程退出后父消息重投；先按 source-ready ID 做 report preflight，未完成时从 reservation 重建原执行组；
- Python 契约必须对相同 `canonical_rows_hash`、source hash 和参数产生确定性结果；禁止用墙上时间、未固定随机数或网络响应直接影响输出。同一 source-ready 在首个 plan 固定前可读到更新的已封存输入，因此确定性边界是“相同已持久化 task plan”，不是“同 Event ID 永远对应同一 View as-of 快照”；
- 每个 reservation 在任何计算前固定 `trigger_type`、`trigger_id` 和 `trigger_anchor_at`；realtime 分别使用 `source_ready/Event ID/ready_at`，Recalc 使用 `recalc/recalc_id/首次 reservation 时间`；
- `factor.parent_task_id` 由 trigger type/ID、target period、binding set、binding 和 subject 确定性生成；`factor.computed_at` 使用已持久化的 `trigger_anchor_at`，实时 target 的 `FactorPeriodComputed.computed_at` 也使用该值；真实耗时只进 metrics/log，不进入幂等 payload；
- 每个任务先形成规范化 write plan，再按完整 RowKey 排序并确定性分块；写调用携带 `source_event_id = hash(trigger_type,trigger_id,target_period,binding_set_hash,binding_id,binding_contract_hash,subject_id,plan_hash,operation,chunk_index)`，其中 operation 为 `upsert` 或 `clear`；
- 规范化 write plan 的完整 upsert/clear payload 在首次 Storage 写前以 CAS 记录到 output manifest 的 pending 区；重投直接复用已有 plan，只有“相同 input rows hash 与执行契约却产生不同 plan hash”才 fail closed；并发候选 plan 不同时由 CAS 败的一方丢弃候选并复用胜出 plan，不混写两者；
- 每个 target 的 report ID 和最终 Event ID 都是确定性的；
- 不新增完整 `FactorRun`、持久化 inbox 或分布式锁。

同一 source-ready Event ID 的重复投递在内存中合并；新 snapshot 的 restatement 是新执行组。所有 realtime/Recalc/binding-maintenance 任务对同一 `(binding,subject)` 全局串行，不同 target period 按 data_time 排序；新 restatement 在当前任务运行时设置 dirty，当前任务结束后再执行最新快照。这个串行约束保证 output manifest 每行只需一个 pending plan 槽位。

已有 reservation 的旧 Active 组必须收敛：已保存 pending plan 的任务不再读 Source View，直接恢复该 plan；尚未形成 plan 且原 Active 已不可读的任务记为 `skipped_source_revision_changed`，并精确清空其旧 manifest。该组交接 degraded Marker 并等到 final terminal 后 ACK，新 Active 的 source-ready 随后产生新一代结果。

为防止“G1 已写结果、尚未形成 final terminal，G2/Recalc/解绑清理先覆盖同周期”，一期对每个自动 result dataset 使用单实例 `ResultMutationGate`：

- realtime、Recalc 和 binding maintenance 都必须先持久化 reservation，再按 reservation `c_id` 顺序获取该 result dataset 的 gate；
- gate 按 reservation `c_id` 排队；轮到本组时，realtime 在形成第一个计算/写计划前获取，Recalc 在追加 source barrier 前获取，maintenance 在第一个 clear plan 前获取。它一直保持到 realtime 的全部 target Marker 已追加且 `WaitViewFactorPeriodReady` 返回全部 final terminal，或 Recalc/maintenance 的 result barrier 已应用；unbinding 还要保持到移除字段的新 Result Active 生效。后来组不得插入其结果写；
- Factor 启动时先关闭 Recalc/Binding 变更入口并暂不拉取新 source-ready，扫描未交接 reservation、对照 Storage Marker/barrier 并恢复最旧组；清空恢复队列后才对外服务；
- source-ready durable 额外设置 `MaxAckPending=1`，保证单实例不同时拉取多个父事件；任务内部仍可按 subject 并发。

这是单 Factor 进程内的有序门禁，不是分布式锁。如果以后需要多实例或多组并行，必须先把该 result-dataset generation fence 下沉到 Storage，一期不做。

### 8.3 计算与 degraded

- initial 路径只计算触发周期 T；restatement 路径按 reservation 中的 target plan 计算已受影响的 T'及后续目标期 P，不对每个正常行事件做前向重算；
- 每个目标期 P 的输入为 P 与之前 `lookback-1` 个实际存在的 data_time；只有 T' 仍在该窗口内时，该 `(binding,subject,P)` 才进入 restatement target plan；
- Factor-bound Source View 一期要求 `keep_duration=0`，避免 retention 截断历史后静默产生错误 rolling 值；
- 绑定 input mapping 只允许引用非 factor-result dataset 的列；
- 读到 `ErrViewPeriodDirty` 时不执行 Python，保持父消息 heartbeat 并重查 latest source-ready；若本组尚无任务 plan 且已有更新事件，按 superseded 收敛；若已有部分 plan，已计算任务保留，尚未形成 plan 的任务在更新事件到达后记为 `skipped_source_superseded` 并清空旧 manifest，本组先交接 degraded，新组再交付完整结果；
- 某 subject 在该 binding 的必要输入 dataset 中 degraded 时，不执行 Python，但要对 output manifest 中该周期的旧 RowKey 执行本 binding 输出字段的定向 NULL patch，然后记为 `skipped_degraded`；
- Python 成功后先把全 NULL row 规范化为 absence，再以完整 RowKey 比较 `old_manifest - current_output`；仅对消失 RowKey 清空本 binding 的 namespaced output field IDs，不删整行，也不影响其他因子列；
- clear 复用 Storage 已有的字段级 `TypedValue.null_value`；请求只包含本 binding 输出字段，其他字段和属性省略并保留；
- Python 合法返回零行等价于当前 manifest 为空，因而清空该周期全部旧输出；有限重试耗尽的 `failed` 任务也先执行同样的精确清空，防止下游读到上一次 restatement 的旧值；
- 迟到 source restatement 变为 success 后重新执行受影响 target plan 并写入正常结果；
- Python 执行错误按有限重试收敛为 `failed`；`factor_group_timeout` 到期时取消仍在执行的 Python，将尚未终态任务记为 `failed_timeout`，两者随后都进入上述精确清空；
- Storage upsert/clear/report 失败是交付故障，不能伪装成业务 `degraded`。在结果状态尚未可证明时保持父消息未 ACK 并持续重试/告警，恢复或人工处置后才允许追加 Marker。

这里的零行语义明确覆盖《因子计算模块设计.md》中“空 DataFrame 不清除旧结果”的旧约定。实现阶段必须删除 `WriteFactorPatch` 的零行直接成功分支：即使没有 upsert 行，也要根据 manifest 生成 clear plan、提交 manifest，再进入任务终态；两份文档和运行契约必须在启用新链路前同步。

output manifest 为每个 `(binding,subject)` 保留最近修正窗口内 `period -> sorted RowKeys` 的有界 map，不是每周期一行的运行历史。任务的 pending plan 与 last committed `(trigger type,trigger ID,target period)` 也写在同一行：崩溃在 manifest commit 前发生时重放同一 plan；commit 后、Marker 前发生时由 last task key 直接恢复任务成功计数，不再根据新 manifest 误生成另一个 plan。

### 8.4 全部因子终态与结果写入

执行组按 target period 分组，每个 target expected set 是 reservation 中的 `(binding,subject)` 子集：

- 全部成功：组状态 `complete`；
- 存在 `skipped/failed`：组状态 `degraded`；
- 没有 enabled binding：视为无工作，持久化 `no_work` reservation，不生成结果 Marker 和最终因子 ready；
- 每个成功任务只有在携带稳定 source_event_id 的结果 upsert、旧行 clear 全部返回成功，且 output manifest 已提交后才进入 success；
- 一个 target 的全部任务终态后，调用 `ReportFactorPeriodComputed` 向结果 dataset outbox 追加该目标周期 Marker；payload 携带 trigger/target source-ready ID、target 计算输入 hash、每个 binding 的 output content hash、`source_view_id/result_view_id` 与完整 `planned_target_periods/target_set_hash`；
- 已有 Marker 的 target 不再执行任何结果写；只有 `GetFactorPeriodReports.handoff_complete=true` 且全部 report 进入 `published|coalesced|superseded` terminal 后才释放 gate 并 ACK `ViewSourcePeriodReady` 父消息。Marker handoff 只证明结果写排在 Marker 之前，不能单独释放 gate；否则异步 publisher 可能在下一代覆盖结果后才发布旧 ready。

如果进程在部分结果写入后退出，重投后从 reservation 恢复原 binding/target set，由 pending plan 和稳定 source_event_id 去重已完成写入并继续缺失任务；如果部分或全部 Marker 已追加但父消息 ACK 前退出，按 source-ready ID 的 preflight 只恢复缺失 target，Marker 全部交接后继续等待 final terminal，不能仅凭 Marker 直接 ACK。即使 binding 已变更，也禁止在任一旧 target Marker 后产生该 target 的新结果行事件。

### 8.5 读写与 Recalc

Storage 读协议改为显式二选一：

```protobuf
message ReadTimeSeriesRowsReq {
  oneof source {
    string dataset_id = 8;
    string view_id = 10;
  }
  uint64 expected_active_view_revision = 11;
  string expected_active_schema_hash = 12;
  string expected_active_index_id = 13;
  oneof visibility_fence {
    SourceReadyReadFence source_ready = 14;
    ViewBarrierReadFence write_barrier = 15;
    FactorSnapshotReadFence factor_snapshot = 16;
  }
}

message SourceReadyReadFence {
  string event_id = 1;
  string snapshot_hash = 2;
}

message ViewBarrierReadFence {
  string correlation_id = 1;
  repeated string expected_dataset_ids = 2;
}

message FactorSnapshotReadFence {
  int64 period_time = 1;
  string expected_factor_snapshot_hash = 2;
}

message FactorSnapshotReadState {
  string served_factor_snapshot_hash = 1;
  uint64 served_result_generation = 2;
  string current_snapshot_kind = 3;         // factor_final | barrier_invalidated | none
}
```

Source View 模式下 selector 不再要求 Factor 伪造 primary dataset ID；响应列通过 binding 的 logical-input mapping 转成 Python DataFrame 所需名字。实时任务使用 `SourceReadyReadFence`，View 校验该 emission 已发布、属于同一 View/Active 契约且对应 Marker 已应用；Recalc 使用 `ViewBarrierReadFence`，View 校验当前 Active triple 已应用全部 expected dataset barrier。两者都只是读取下界，不要求 as-of 读；查询在与 `view_rows` 相同的物理读事务中，还必须对本 binding 输入列的全部实际 data_time/origin dataset 验证 `applied_generation == sealed_generation`。任一周期有尚未被 Marker/barrier 封存的新值时返回 `ErrViewPeriodDirty`，禁止 Factor 读到部分新代数据。

响应增加对完整 RowKey、值、NULL 与排序规范化后的 `canonical_rows_hash`。Factor 复算该 hash，并把 `visibility fence identity + target period + canonical_rows_hash + factor source/params/mapping` 放入 task plan hash。`FactorPeriodComputed.calculation_input_hash` 是目标周期全部 task plan hash 的规范化聚合，表示**实际计算输入**，不再把 source-ready 的下界信号误当不可变数据快照。查询可以读到比 fence 更新的**已封存** restatement；这种 latest-sealed 语义以实际 rows hash 定义结果身份。

策略/下游读取 Result View 时使用 `FactorSnapshotReadFence`。View 在与 `view_rows/view_period_generations` 相同的物理读事务中比较 target period 的 generation、`sealed_snapshot_kind` 和 hash；只有 `kind=factor_final` 且期望 hash 匹配才返回完整周期 rows，并在响应附 `FactorSnapshotReadState`。期望 hash 已被下一代替代，或当前只有 Recalc/maintenance barrier 而没有可引用 final snapshot 时，不返回 rows，返回 `ErrFactorSnapshotSuperseded` 及 current kind/hash/generation。该 fenced 读取一期不分页；若单周期超过服务端上限则明确失败，未来要分页必须先提供服务端 snapshot token，不能让客户端跨多个独立事务自行 hash。

实时计算不从 Result View 读取因子输入，因此动态结果 tag 不会进入下一周期输入。

`RecalcFactor`：

- 入参迁移为 `recalc_id/source_view_id/freq/subject_scope/time_range/[factor_id]/[source_barrier_fence]`，同一调用方重试复用 `recalc_id`；
- 首次请求先以 `trigger_type=recalc/trigger_id=recalc_id` 持久化 binding/target reservation、trigger anchor 和 source visibility-fence plan；import/catchup 调用复用传入的已完成 source barrier correlation，独立 Recalc 则固定 `recalc_id:source` 与 Source View 的实际 origin datasets/affected ranges；
- 按 reservation `c_id` 获取与实时任务相同的 `ResultMutationGate` 后，在任何读取前追加/等待 reservation 中的 source barrier，并把 Wait 返回的 Active triple 固定进 fence；不能因历史期没有 source-ready 而无 fence 读取。随后通过同一 per-subject 队列执行；RPC 使用 `SubmitAndWait`，不得绕过队列直接 `Run`；
- 复用实时 write-plan/manifest 协议；对超出 manifest 保留窗口的历史周期，先在 barrier 之后从 Result View 查询“本 binding 输出字段任一非 NULL”的现存 RowKey，再计算精确 clear set；
- 全部结果 upsert/clear 成功后，对结果 dataset 追加 `DatasetWriteBarrier(source=recalc,correlation_id=recalc_id)`，并等待自动 Result View 的当前 Active triple 应用 barrier；该 barrier 封存 generation 时必须把旧 factor final snapshot 标为 `barrier_invalidated`，只有此时才标记 reservation completed 并返回 RPC 成功；
- 不发送实时 `ViewFactorPeriodReady`，但同步成功与方案 B 保持一致：Recalc 结果已在返回的 Result View Active triple 中可读；
- 历史 import 必须先完成 View 可见性 barrier，见第 13 节。

- source phase：`hash(active_view_revision, active_schema_hash, active_index_id)`；同一 Active triple 下的迟到恢复更新同一聚合行并产生新的 current snapshot；
- factor phase：`FactorPeriodComputed.report_id`，把一次明确的实际输入 rows hash、Source View 和因子绑定快照绑定为一个最终结果批次。

## 10. Binding 生命周期与 View 重建

`UpsertBinding(space,source_view,factor,freq,subject_scope,input_mapping)`：

1. 校验 Source View 是 time-series View，freq 一致，且 `keep_duration=0`；
2. 校验 input mapping 的每个 Source ViewColumn 存在；
3. 沿 ViewColumn origin dataset 拒绝 `dataset_role=factor_result`，包括自依赖和 A -> B 隐式因子依赖；
4. 以有界、带 hash 的 `ResultDatasetForView(source_view_id)` 创建结果 dataset，写入不可变的 `dataset_role=factor_result,write_owner=factor`，不能直接使用可能超过 30 字符的 `factor_result__<view_id>`；
5. 以有界、带 hash 的 `ResultViewForSourceView(source_view_id)` 创建 `managed_by=factor` 的自动 Result View，并把结果 dataset 设为其 primary dataset；Metadata 拒绝普通用户/API 直接改该 View schema，只允许 Binding lifecycle 内部操作。该 time-series View 使用与 binding/Source View 相同的规范化 freq，显式写入 canonical `filter_json={"freq":"<freq>"}`，并采用兼容的 grain 与 `keep_duration=0`；Source View 永不加入结果 dataset；
6. 保留 Factor `name` 作为 Python module/display name，不强制修改大小写；每次新建 binding 生成不可复用的 `binding_id/c_output_namespace`，结果 field ID 由该 namespace 与规范化 output name 组成并限制在 Storage 长度内。namespace 在同一 binding 更新/禁用/恢复期间保持稳定，但 unbind 后不得复用；
7. 持久化 logical input -> Source View column 与 raw output -> result field ID 两组 mapping；
8. 一次性把该因子的全部结果列加入结果 dataset 和 Result View desired schema，只触发 Result View 的一次 A/B 重建；
9. binding 先保存为 `pending_view`；
10. 仅当 Source View Active schema 包含全部输入列，且 Result View Active schema 包含结果 dataset 与全部输出列后，切换为 `enabled`。

Factor 内置一个单实例 `BindingReconciler` 负责第 10 步：`UpsertBinding` 完成 schema 请求后立即触发一次，Factor 启动和低频定时扫描再做补偿。它从 Storage 读取 Source/Result 两个 Active triple 与实际 schema，只对 `pending_view|enabled` binding 做双向收敛：契约满足时 CAS `pending_view -> enabled` 并更新两个 enabled revision；任一 Active 契约不再满足时，在创建新 reservation 前 CAS `enabled -> pending_view`。`disabling|disabled|unbinding` 不得被 Reconciler 自动启用。reservation 创建时还要以当次读取的两个 Active triple 复核 binding contract，读写之间发生切换则由后续 expected-active read fence 拒绝，不能只信 Reconciler 的历史状态。这是 Factor 本地对账，不依赖未定义的 View activation 事件，也不新增跨服务工作流。

重建期间：

- 旧 Active 继续服务；
- pending_view binding 不参与 source-ready 执行组；
- Source View 和 Result View 的 Active 契约都满足后，从下一次 source-ready 开始计算；
- Source View 激活时按保留的 dataset-period snapshots 为新 Active triple 重建最近周期 source-ready；新依赖尚未到齐则保持 pending；
- 旧 revision 的 source-ready 到达时按 expected active fencing 判 stale 并 ACK，不跨不兼容 schema 计算；对应新 revision ready 由激活重评估产生；
- Result View 激活时重新评估此前因 schema 不兼容而 blocked 的 Factor Marker；
- `ActivateViewIndex` 与 emission publisher 通过 per-view `PublishActivationGate` 协调；旧 triple 的 pending intent 必须先取消并在新 triple 重建，或先完成 PubAck，禁止在 Active 已切换后才发布旧 triple payload；
- `disable/unbind` 不是同步删除。RPC 首次收到稳定 `operation_id` 时，在同一 Factor SQLite 事务中把 binding CAS 为 `disabling|unbinding` 并创建 `trigger_type=binding_maintenance` 的 reservation；从该状态起不再进入新的 source-ready reservation，但早先 reservation 仍按 `c_id` 顺序收敛；
- maintenance reservation 自包含 binding generation、manifest window、规范化 clear plan 和目标 Result Active contract，使用通用 trigger anchor 与稳定 write source IDs。轮到它时获取同 result dataset 的 `ResultMutationGate`，分块 clear、提交 manifest，再追加 `DatasetWriteBarrier(source=maintenance,correlation_id=operation_id)` 并等待 Result View 当前 Active 应用；进程退出后由启动恢复扫描重放同一 plan/barrier；
- `disable` 只有在 maintenance barrier 完成后才提交 `disabled`。它保留 binding、output namespace、Result View schema 与窗口外历史，后续显式恢复仍是同一代；
- `unbind` 在 clear barrier 完成后从 Result View desired schema 移除该代结果列，并继续持有 gate，直到新 Active 已不含这些字段；最后才删除 binding/manifest 并完成 maintenance reservation。结果 dataset 中超出 manifest 窗口的旧 raw 字段可以保留，但以后重绑必须创建新的 binding generation/field IDs，旧字段不再进入 Result View，因而不会复活；
- maintenance 未到终态时同 `operation_id` 查询/等待原 reservation，不得重复创建；结果 dataset 和自动 Result View 默认保留，显式操作才删除。

## 11. 配置与运行约束

| 配置/约束 | 默认 | 说明 |
|---|---|---|
| `period_ready_grace` | `2 x freq`，上限 10m | 周期关闭后的采集等待 |
| `period_item_retention` | 最近 60 个周期 | Collector subject 明细保留 |
| `view_signal_retention` | `max(Stream MaxAge, 最大 Factor 停机/未 ACK 恢复窗口, period_item_retention + max_enabled_lookback)` | emission history、source snapshot 和 read fence 必须活得不短于可重投事件 |
| `view_barrier_retention` | 不小于 import、View build、Recalc/maintenance 的最长恢复时间 | CLI 与内部 reservation 可重连等待 barrier |
| `dataset_lane_ledger_retention` | 不小于 `max(view_signal_retention,最长 View build 恢复窗口)` | A/B 可恢复每期最后 factor-final/invalidated 状态 |
| `factor_group_timeout` | 按最大因子耗时配置 | 执行组最终降级 deadline |
| `factor_task_max_retry` | 沿用当前有限重试 | 单任务重试 |
| `factor_manifest_periods` | 不小于 `max(period_item_retention,max_enabled_lookback)` | 动态 RowKey 修正与精确清空 |
| `factor_reservation_retention` | 不小于 `view_signal_retention` | 重投复用原 binding 快照 |
| `marker_report_retention` | 不小于 `view_signal_retention` | DataNode generation chain、report preflight 与 final 状态可恢复 |
| Factor source-ready `MaxAckPending` | `1` | 一期避免多父事件交错写结果 |
| View dataset durable `MaxAckPending` | `1` | 一期保证失败 delivery 不被后续 Marker 越过 |
| Result mutation concurrency | 每 result dataset `1` | realtime/Recalc 写到 Marker/barrier 的因果顺序 |
| View consumer replicas | `1` | 单 durable 的活动 View 消费实例 |
| Factor-bound Source View keep | `0` | 一期保证 lookback 历史完整 |
| `view_settle_delay` | 删除 | 由因果 Marker 取代 |
| `event_read_retry*` | 删除 | 正常链路不再靠轮询猜测 |

Collector 行事件、View dataset lane 和 Factor source-ready 三个新 durable 统一使用 `DeliverAllPolicy`、显式 ACK 和 `MaxDeliver=-1`。业务永久错误由本文定义的 blocked/TERM 边界收敛，不依赖 broker 在第五次投递后静默停止恢复；View 暂时故障和 Factor 长任务都持续 in-progress heartbeat。

Retention 必须以时间统一换算，不能把“60 个 1m 周期 + 200 lookback”误当成足以覆盖 72h Stream。只要 JetStream 仍可能重投 source-ready，Metadata 的 source emission/dataset snapshot、Factor reservation，以及 DataNode report generation/preflight 都必须仍可验证；任一层先清理会把可恢复重投变成永久 fail closed。

迁移时使用新 durable name，不就地假设已有 consumer 的 deliver policy 可修改。个人单实例允许一次短暂受控停顿：先创建新 durable，再停止旧 Factor 行触发和旧 View consumer，启动新 View/Collector/Factor consumer 并等待 dataset 行回放追平，最后才启用 Marker 生产者。禁止新旧 Factor 触发同时写结果，也禁止两个 View consumer 并发写同一索引。新 durable 使用 DeliverAll，即使完成事件早于消费进程首次启动，也不会因 `DeliverNewPolicy` 漏掉。

## 12. 可靠性与边界场景

| 场景 | 行为 |
|---|---|
| 整次 Timer 未执行 | 周期已预建；deadline 将所有 pending 置 timed_out 并报告 degraded |
| Collector 更新内存后退出 | SQLite 先提交才 ACK；重启从 SQLite 恢复 |
| Collector report RPC 超时 | 以确定性 report ID 重试；DataNode 去重 |
| Collector report 已追加但响应丢失 | 复用 SQLite 中固定的 collected_at/payload，不因重试时钟变化冲突 |
| 迟到 K 线 | timed_out -> success，产生新 snapshot 和 restatement |
| `success` 后同值重写 | required data hash 不变，不发 restatement |
| `success` 后有效值变化 | Collector 更新 data hash，发 restatement Marker；新 Marker 前 View period 保持 dirty |
| 行事件应用失败并 TERM | 先持久化 lane blocked；后续 Marker 不发 ready |
| View ready 发布后置位前退出 | ready_pending 重发；Event ID 相同 |
| 发布期间 snapshot 改变 | emitted CAS 比较 current hash，旧发布不能吞掉新 snapshot |
| View A/B 重建 | ready 绑定 Active revision；pending binding 等待目标 schema 激活 |
| Factor 运行中退出 | source-ready 父消息未 ACK，重投后从 reservation 恢复原 binding set |
| Factor 部分结果写入后退出 | pending plan 校验确定性，稳定 task source_event_id 去重已写 upsert/clear |
| Factor 完成写入但 Marker 前退出 | manifest 的 last trigger/target 恢复任务终态，不重建不同 clear plan |
| 部分 target Marker 成功、父消息 ACK 前退出 | preflight 只恢复缺失 target；Marker 齐全后继续等待全部 final terminal 才释放 gate/ACK |
| 新一代行已应用但 Marker 尚未到达 | generation 为 dirty，Factor 读取返回 `ErrViewPeriodDirty`，不得读部分新代 |
| restatement 修改 lookback 内历史期 | 按实际 data_time 扩展已 ready target，每个 target 产生新一代最终事件 |
| G1 Marker 已追加但 final publisher 阻塞，G2/Recalc 到达 | `ResultMutationGate` 持有到 G1 final terminal，不允许 G2 覆盖后再发布 G1 ready |
| 相同快照产生不同 Python 结果 | pending plan hash 冲突并 fail closed，不混写两个代际 |
| 动态 tag 从 A 变为 B 或零行 | 写 B 并对 A 的本 binding 字段写 NULL，Marker 在两者之后 |
| unbind 后重绑同一因子 | 创建新 output namespace/field IDs；旧代超窗 raw 值不重新进入 Result View |
| disable/unbind clear 中途退出 | binding 保持 maintenance 状态；启动恢复按稳定 plan/source IDs 重放并等待 result barrier，未完成前不删 binding |
| 单个因子失败 | 有限重试后组进入 degraded，仍追加 Marker并产生最终 degraded ready |
| 结果行应用失败 | 结果 dataset lane blocked，Result View 不发 `ViewFactorPeriodReady` |
| manual/import 直接写自动结果 dataset | Primary/DataNode 按 `write_owner=factor` 拒绝，修复必须走 Recalc/barrier |
| Recalc 结果 Storage 已提交但 View 未应用 | 结果 dataset barrier 未完成，`SubmitAndWait` 不返回成功 |
| 无 enabled binding | source-ready 正常 ACK，不产生因子最终事件 |
| EventBus 长时间不可用 | DataNode outbox 保留 Marker，Relay 不越过失败条目 |
| 事件早于新 consumer 首次启动 | 新 durable 使用 DeliverAll，从 Stream 保留起点回放 |
| 连续超过 5 次进程退出 | `MaxDeliver=-1`，父消息持续重投直到交接或显式永久错误 |

## 13. Catchup、Import 与 Recalc

Catchup/import 不逐周期进入实时 ready 链，但必须解决“Storage 已提交不等于 View 已可读”：

1. import 完成所有 `UpsertFields`；
2. 为本次调用生成并在重试中复用 `correlation_id`，把实际覆盖的频率和周期范围规范化为 `affected_ranges`；对每个受影响 dataset 调用 `AppendDatasetWriteBarrier`，`barrier_id = hash(correlation_id,dataset_id)`；
3. Storage Primary 按 `(space,dataset)` 路由到该 dataset DataNode，DataNode 用行写的同一 `outboxMu` 追加 `DatasetWriteBarrier`；重试的 ID/payload 必须一致；
4. View 在同 dataset lane 先应用 barrier 前全部行，再把完整 barrier 幂等保存到与 View 无关的 `t_dataset_write_barriers`。对每个已接收该 dataset 行事件的 Active/Building 物理索引，在本地事务中按 `affected_ranges` 把对应 period 的 `sealed_generation` 推进到当前 `applied_generation`，然后按该物理 triple 写入 `t_view_barrier_applied`；Metadata 写入成功后才 ACK barrier，暂时失败保持当前 delivery 原地重试，协议永久非法才 TERM；
5. CLI 调用 `WaitViewBarrier(view_id,correlation_id,expected_dataset_ids)`；只有目标 View 的当前 Active triple 已记录全部 expected dataset 才返回成功和该 triple，超时则导入命令失败并允许以同 correlation ID 重试；
6. Active 在等待中切换时，Wait 不得用旧 triple 的 applied 记录返回成功。原 barrier 若已在该 build attempt 的 build barrier 之前由 lane 持久化，权威 full scan 加后置 build barrier 可证明新索引包含其写入，activation reconciler 才能把原 correlation 的 applied ledger 继承到新 triple；原 barrier 若更晚，则必须由 lane 实际双写到 Building。缺少任一证据时不得补记 applied 或让 Wait 成功。**以相同 correlation/barrier ID 重试只返回原 outbox 记录，不会产生新事件，不能把“重追加”当作 Active 切换协议**；
7. barrier 完成后才把 `correlation_id/expected dataset set/Wait 返回的 Active triple` 作为 source visibility fence 传给同步 `RecalcFactor`；若读取时 triple 已变则回到 Wait 重试，不能丢弃 barrier 身份后裸读。

不能只轮询 View 的 coverage/`complete`，因为历史范围原本就可能完整，coverage 无法证明本次覆盖写已经应用。

第 4 步对自动结果 dataset 有额外规则：`source=recalc|maintenance` 的 barrier 在推进 `sealed_generation` 的同一物理事务中写 `sealed_snapshot_kind=barrier_invalidated` 并清空 `sealed_snapshot_hash`，使任何旧 `FactorSnapshotReadFence` 返回 superseded；不能保留旧 H 后返回 barrier 之后的新 rows。`source=view_build` 不直接覆盖 factor snapshot，而是按第 7.3 节从统一 dataset lane ledger 恢复最后 seal-affecting 状态：只有最后事件为 Factor Marker 才是 `factor_final`，最后事件为 Recalc/maintenance barrier 则保持 `barrier_invalidated`。普通 Source View barrier 使用 `source_marker/none` 语义，不参与结果快照读取。

## 14. 实施顺序

1. **事件与 DataNode Marker 契约**：新增四个完成事件和 `DatasetWriteBarrier`、追加/等待 RPC、Collector generation compare-and-append、按 source-ready/report 的 preflight、确定性 ID、outbox publisher 泛化；
2. **Collector 周期追踪**：启动补建、周期预建、Storage row event 按 data_time 与完整 row contract 更新、SQLite 状态、不可变有序 report intents、deadline、restatement；
3. **View 消费顺序、权威 build 与读取 fence**：多 FilterSubjects、DeliverAll/无限投递新 durable、dataset lane、单实例约束、blocked health、DataNode full scan + per-attempt build barrier、逐字段回填、物理 period generation/seal 与 `ErrViewPeriodDirty`；
4. **Storage Metadata 信号状态机**：dataset-period snapshots、source/factor signal merge、不可变 emission history、snapshot hash、ready_pending、CAS emitted；
5. **View source-ready**：Active dependency set、primary subjects、`ViewSourcePeriodReady`；
6. **Factor binding/read 契约**：Source View binding、带 canonical freq 的自动 Result View、input/output mapping、不可复用 output namespace、有界命名、dependency hash、双向 BindingReconciler 和 expected active fencing；
7. **Factor 执行组**：按 source-ready 的 report/final preflight、realtime/Recalc/maintenance 通用 trigger reservation、父消息 heartbeat、确定性 payload、output manifest/零行 clear plan、output content hash、稳定 task write source ID、per-subject fanout、持有到 final terminal 的 ResultMutationGate、degraded 汇总与结果 Marker；同时同步《因子计算模块设计.md》的空结果契约并移除 `WriteFactorPatch` 零行直接返回；
8. **Result View final-ready**：应用结果 Marker、封存 result generation、复核可读内容、可靠发布 `ViewFactorPeriodReady`，并实现 `WaitViewFactorPeriodReady`；
9. **Recalc/import barrier**：`SubmitAndWait`、Result View barrier、barrier retention/activation re-evaluation 与 CLI 等待；
10. **写所有权与清理**：自动结果 dataset 的 Factor-only ACL；删除 `EventBatcher`、settle/retry 链和旧 dataset-bound Factor 逻辑；
11. **前端与可观测性**：pending_view、source/factor 周期状态、blocked lane、degraded 清单；
12. **验证**：模块测试、EventBus/Storage/View/Factor E2E、进程退出重投、A/B 重建和真实 Python 写回。

重点测试矩阵：

- 周期完全无行、部分 subject 缺失、迟到恢复；
- 未预建周期的启动积压、非 Collector write_source、部分字段 delta 均不得假 complete；
- assignment 在周期中变化；
- Marker RPC 超时重试和重复 outbox 发布；
- Collector 首次 report 响应丢失且时钟推进后，必须复用已持久化的 collected_at/payload；
- S1 degraded RPC 延迟、S2 complete 已生成时，DataNode 必须按 generation chain 先追加 S1 再追加 S2；晚到旧代不得覆盖 current；
- `success -> success` 同值重写不 restatement，有效值变化必须 restatement；
- 行事件永久失败后 Marker 不得越过；
- 多数据集 Marker 乱序；
- S2 行已进 View、S2 Marker 未到时，以 S1 source-ready 读取必须返回 `ErrViewPeriodDirty`；行与 generation 的检查/读取并发时只能得到完整 S1 或完整已封存 S2；
- minimum source-ready 读取到更新的已封存数据时，`canonical_rows_hash` 必须进入 task plan，重投复用首个 CAS 成功的 plan；
- snapshot 发布过程中发生 restatement；
- desired/active revision 不一致；
- Factor 已按旧 Source Active 写完并追加 Marker 后 Source 切换，新 contract 不得阻断旧 report final；事件必须保留旧 source triple；
- 自动 Result View 字段被违规移除时旧 report 必须收敛为 `superseded` 并释放 gate，不得永久 blocked；正常 unbind 必须先等 reservation；
- 首次建 View 必须从 origin datasets 权威回填历史；重建时 Building 先收到单字段 live delta，也不得因整行 skip 丢失同 RowKey 的其他字段；
- View build 在 scan、gate 释放、build barrier 和 fence 提交各点退出时，新 attempt 必须清空重扫并以新 barrier 收敛，未证明完整不得 Activate；
- Active 切换后从 dataset snapshots 为新 triple 重建同周期 ready；
- binding pending_view 到 enabled，以及 Active 丢失输入/输出契约后的 enabled 到 pending_view；
- 自动 Result View 创建请求包含规范化 `filter_json.freq`；
- 动态 series_tag 只进入 Result View，不得回流 Source View 输入；
- Factor 中途退出、部分 upsert/clear 已写、manifest 已 commit 但 Marker 未写；
- Marker 已存在且 binding 已变更时，重投仍不得在 Marker 后追加新结果行事件；
- 动态 series_tag 从 `{A}` 变为 `{B}` 和从 `{A}` 变为空集时，A 的本因子字段必须为 NULL；
- 相同 RowKey/status 的因子值从 1 变 2 时 output content hash 必须变化并发布新最终事件；
- Python 合法返回空 DataFrame 时不得走零行快速成功，必须提交 clear plan；
- unbind 超过 manifest 窗口后再绑定同一因子，必须使用新 namespace，旧 raw 字段不得重新可见；
- disable/unbind 分块 clear 任一点退出都必须从 maintenance reservation 恢复；其他 binding 的 realtime/Recalc 不得越过同 result dataset gate；
- 相同已持久化 input rows hash 与执行契约重算出不同值或 RowKey 时，plan hash 必须 fail closed；
- Recalc 重试必须复用 reservation 的 `recalc_id/trigger_anchor_at`，相同 write source ID 不得因墙上时间产生 payload 冲突；
- 没有历史 source-ready 的独立 Recalc 必须先建立并持久化 source barrier read fence，重投复用同一 fence；
- degraded/failed restatement 只清空 manifest 中本 binding 的旧 RowKey，不影响其他因子字段；
- 结果行尚未应用时不得发最终事件；
- 下游收到 H1 final 后若 H2 已覆盖，`FactorSnapshotReadFence(H1)` 必须在单一物理事务内返回 superseded/current H2 且不返回混代 rows；H1 未被覆盖时响应必须回显 H1/generation；
- H1 final 后 Recalc/maintenance 改值并只追加 barrier 时，物理 snapshot kind 必须变为 `barrier_invalidated`；读取 H1 不得返回 barrier 后的新 rows；
- G1 final emission pending 时暂停 publisher，再到达 G2/Recalc；G2 必须被 gate 阻塞，恢复后发布 G1 时 View 仍可读 G1 值；
- Result A 上已建 pending final intent、PubAck 前切换兼容 B 时，activation/publisher gate 必须保证“先发 A 再切换”或“取消 A 并在 B 重建”，不得切换后发布 A；
- 非 Factor 身份对自动结果 dataset 的 manual/import upsert 必须被 Primary 和 DataNode 拒绝；
- import 历史覆盖在 barrier 前不得 Recalc；Active 切换后不得误用旧 triple，同 barrier ID 重试不产生新事件且必须由 activation re-evaluation 收敛；
- restatement 前向扩展的每个 target 都有独立 Marker；两个 trigger 得到相同结果快照时不重复发布最终事件；
- Factor 停机超过旧的 period/lookback 保留值但仍小于 Stream MaxAge 后恢复，source emission、reservation 与 report preflight 仍必须存在；
- 完成事件在 consumer 首次启动前已发布，以及连续超过 5 次崩溃，都必须最终恢复。

## 15. 开放问题

1. **每周期 per-subject 读取放大**：一期沿用 per-subject 任务；二期测量后再评估一次 cohort 查询并在内存分组。
2. **横截面因子**：未来需要独立的 period-scoped binding/task，不复用 per-subject 完成计数。
3. **采集器未观测到的交易所静默重述**：Collector 已收到的 `success` 后有效值变化会自动 restatement；若上游根本没有再次写入 Storage，仍需对账任务发现差异并显式 Recalc。
4. **跨空间 View**：需要新的数据所有权和完成聚合契约，另行设计。
5. **有限 View retention**：一期要求 factor-bound View keep=0；未来若放开，必须先定义可证明的 history completeness。
