## 3. 目标设计

### 3.1 术语

| 术语 | 含义 | 标识 |
| --- | --- | --- |
| 主机 | 纳入 MooX 部署的一台机器，每台主机上恰好运行一个主机网关 | 主机 ID 即主机名（代码中的 `node_id`） |
| 组件 | 一种 MooX 进程 | 组件 ID 为二进制名去掉 `moox-` 前缀 |
| 部署 | 组件与主机的对应关系，带启用状态 | `t_placements` |
| 主机网关 | **系统中唯一的网关**，是一台主机上所有跨进程调用的入口，只转发到本机服务 | `moox-host-gateway`、组件 `host-gateway` |
| 外部接入 | 外部调用方的唯一入口：按调用方限定可调用的方法，再转发给目标主机网关 | `moox-access`、组件 `access` |
| 控制台代理 | 独立 MooX 进程，内嵌 Caddy，只在 control 上为控制台提供 HTTPS | `moox-console-proxy`、组件 `console-proxy` |
| 控制台 API | 管理后台里面向浏览器的 `/api/admin`，负责会话鉴权、限流、空间作用域和请求转发 | `trpc.moox.admin.Console` |
| 网关控制 | 管理后台里的一个服务：向主机网关下发路由快照和服务目录，并接收心跳 | `trpc.moox.admin.GatewayControl` |
| 组件目录 | 写在代码里的组件定义，包括名称、端口、tRPC 服务、ACL、健康检查、外部调用方白名单 | `packages/servicecatalog` |
| 服务目录 | 由组件目录和部署计算出「哪个 tRPC 服务在哪台主机」，随路由快照下发到每台主机网关 | 主机网关本机接口 `Directory` |
| 调用方身份 | 服务签名中的 caller。内部组件使用组件 ID；管理后台有两个身份，内部任务用 `admin`，控制台转发浏览器请求用 `console`；此外还有 `host-gateway@<主机>`、`access`、`moox-cli` | — |
| 受保护组件 | 一旦停用就会切断控制面或恢复入口的组件，不允许停用；control 主机同样受保护 | 组件目录中的 `protected: true` |
| 外部调用方 | 不运行在 MooX 主机上的调用方，只能经外部接入访问 | `scf-collector`、`factor-engine`、`moox-skill` |

以下旧称要从代码、配置、文档和界面中全部清除：节点网关、管理网关、服务网关、service gateway、Storage Gateway、
Trade Gateway、`admin_gateway`、`service_gateway`、`service_gateway_native`、`moox_gateway`、`storage-gateway`、
`storage-access-storage`、调用方 `admin-gateway`、`trpc.moox.gateway.control`。

### 3.2 组件与主机

主机：

| 主机 ID | 公网地址 | 私网地址 | 地域 |
| --- | --- | --- | --- |
| control | 106.53.107.122 | — | 不需要 |
| storage | 146.56.196.204 | 10.206.0.5 | ap-nanjing |
| compute-1 | 43.132.204.177 | 172.19.32.13 | ap-hongkong |

地域和私网地址只有一个用途：让 SCF 就近访问外部接入（见 3.7）。没有部署外部接入的主机不需要填写这两项。

组件的部署范围分三种：
- 「主机」：每台主机自动部署，不能编辑；
- 「control」：只能部署在 control；
- 「任意」：可以部署到任意主机。

| 组件 ID | 名称 | 部署范围 | 副本 | 受保护 | 部署在 |
| --- | --- | --- | --- | --- | --- |
| `host-gateway` | 主机网关 | 主机 | 每台一份 | 是 | 全部主机 |
| `host-agent` | 主机采集器 | 主机 | 每台一份 | 否 | 全部主机 |
| `console-proxy` | 控制台代理 | control | 单份 | 是 | control |
| `web-host` | 控制台前端 | control | 单份 | 是 | control |
| `admin` | 管理后台 | control | 单份 | 是 | control |
| `eventbus` | 消息总线 | control | 单份 | 否 | control |
| `monitor` | 监控服务 | control | 单份 | 否 | control |
| `collector` | 行情采集服务 | 任意 | 单份 | 否 | control |
| `cloudnode` | 云节点服务 | 任意 | 单份 | 否 | control |
| `factor-mgr` | 因子管理服务 | 任意 | 单份 | 否 | control |
| `strategy` | 策略服务 | 任意 | 单份 | 否 | control |
| `archive` | 归档服务 | 任意 | 单份 | 否 | 不部署 |
| `storage-primary` | 存储主服务 | 任意 | 单份 | 否 | storage |
| `storage-node` | 存储数据节点 | 任意 | 单份 | 否 | storage |
| `storage-view` | 存储视图服务 | 任意 | 单份 | 否 | storage |
| `access` | 外部接入 | 任意 | 多份 | 否 | storage、compute-1 |
| `egress-proxy` | 出口代理 | 任意 | 单份 | 否 | compute-1（见 3.13） |
| `trade` | 交易服务 | 任意 | 单份 | 否 | compute-1 |

- 「副本」指所有主机加起来最多能有几条启用的部署。「任意」只表示可以部署到别的主机，不表示可以同时在多处运行。
  第一版只有外部接入允许多份；Collector、FactorMgr、Strategy 等组件本身有租约或状态，只能运行一份。
- 「受保护」的组件一旦停用，控制台和恢复入口就会断开，所以不允许停用（见 3.8）。

不运行在 MooX 主机上的调用方：
- SCF 采集函数：经外部接入访问；
- 操作员机器上的因子引擎和 moox-skill：经外部接入访问；
- moox-cli：经 SSH 隧道访问。

### 3.3 流量与端口

```text
浏览器       ─HTTPS 9527─► 控制台代理（仅 control）─► 控制台前端 / 管理后台（控制台 API）
内部组件     ─本机：tRPC 127.0.0.1:11002 ──────────► 本机主机网关 ─► 本机服务
             ─跨主机：tRPC + TLS <主机>:11003 ─────► 目标主机网关 ─► 本机服务
外部调用方   ─tRPC 明文 + 签名 11004─► 外部接入（就近）─TLS 11003─► 目标主机网关 ─► 本机服务
moox-cli    ─SSH 隧道─► 目标主机 127.0.0.1:11002 ─► 主机网关 ─► 本机服务
主机网关     ─TLS 11003─► control 主机网关 ─► 网关控制（拉快照、报心跳）
```

| 端口 | 位置 | 用途 | 开放范围 |
| --- | --- | --- | --- |
| 9527 | control | 控制台代理：控制台页面与 `/api/admin` | 公网 |
| 19528 | control | 控制台代理的鉴权健康与指标，供同机 Monitor/Doctor/启停脚本使用 | 仅 127.0.0.1 |
| 11003 | 每台主机 | 主机网关的跨主机入口，tRPC + TLS | 只对 MooX 主机开放 |
| 11002 | 每台主机 | 主机网关的本机入口，tRPC 明文，同时提供服务目录 | 仅 127.0.0.1 |
| 11012 | 每台主机 | 主机网关的健康与指标端口（沿用 health HMAC） | 只对 control 开放 |
| 11004 | 部署了外部接入的主机 | 外部接入，tRPC 明文 + 签名 | 公网 |
| 各组件健康端口 | 各主机 | `/healthz`、`/readyz`、`/metrics`（沿用） | 只对 control 开放 |
| 4222 | control | EventBus（不在本次范围） | 不变 |

取消的端口和入口：
- 所有主机上的 11001；
- compute-1 上的 12004；
- 主机网关的 HTTP `/api/service/*`；
- 各组件的 HTTP 业务端口；
- 9527 上的 `/api/gateway-control`。

### 3.4 主机网关（`modules/hostgateway`）

- **监听**：
  - `0.0.0.0:11003`：tRPC + TLS，接收跨主机调用和外部接入转来的请求；
  - `127.0.0.1:11002`：tRPC 明文，供本机调用方使用，也用来查询服务目录；
  - `0.0.0.0:11012`：健康与指标。
- **只转发到本机**：路由来自「部署在本机且已启用」的组件在组件目录中声明的 tRPC 服务，上游固定为
  `127.0.0.1:<目录端口>`。路由键为 tRPC service path 加方法名，不再使用 `gateway_service_id`。
- **鉴权**：校验服务签名（调用方身份、目标主机 ID、请求体摘要、时间戳、nonce）并检查路由 ACL。nonce 持久化和
  重放保护沿用现有实现。用于校验的调用方密钥表随快照下发（见 3.5）。
- **快照**：
  - 每 15 秒向网关控制拉取一次，请求时带上当前哈希，没有变化就不返回内容；
  - 快照包括本机路由、全局服务目录、调用方校验密钥表和版本号；
  - 新快照先整体校验，校验不通过就拒绝，继续使用旧快照；
  - 快照落盘缓存（`routes.json`、`directory.json`），启动时先加载缓存。
- **心跳**：每次拉取时一并上报实例 ID（进程启动时随机生成）、版本、已应用的哈希和最近一次错误。如何区分实例替换与
  冲突，见 3.8。
- **就绪**：最近一次同步成功在 90 秒以内即视为就绪（沿用现有规则）。
- **control 主机的引导**：control 的主机网关内置一条通往本机网关控制（`127.0.0.1:11112`）的静态路由，自己也直接从
  本机拉取快照；其他主机通过 control 的 11003 拉取。空环境下的首次初始化见 3.12 的「首次部署」。
- **删除**：
  - HTTP 入口（`router.go` 中的 `/api/service/*`）；
  - `caller_policy.go`；
  - control HMAC 与 `/api/gateway-control`。
- **改名**：
  - 模块目录 `modules/gateway` 改为 `modules/hostgateway`；
  - 二进制改为 `moox-host-gateway` 和 `moox-host-gateway-cli`；
  - tRPC 服务名改为 `trpc.moox.hostgateway.*`；
  - 指标前缀改为 `host_gateway_`。

### 3.5 TLS、密钥与安全取舍

**证书（全自动，用户无需感知）**

- 需要新建一个 MooX 私有 CA。现有 EventBus 的 CA 签完服务端证书就把私钥丢弃了（见
  `admin/cmd/cli/eventbus_credentials.go` 的 `makeTLSBundle`），无法再签新证书。
- 自动化方式沿用现在 EventBus 凭据的做法：`deploy-moox.sh` 部署 control 时会自动执行
  `moox-admin-cli eventbus-credentials ensure`，用户从不手动运行。证书相关的步骤如下：
  - 首次部署 control 时自动生成 CA，之后每次部署都直接复用；
  - CLI 每次部署某台主机时，都会自动为这台主机的主机网关签发一份新证书并下发。证书的 SAN 包含主机 ID、公网地址和
    私网地址；
  - 有效期：CA 10 年，主机证书 5 年（与 EventBus 一致）。因为每次部署都会换发，正常情况下不会过期。
- 新增的 `moox-admin-cli pki ensure-ca | issue | export-ca` 只供部署脚本内部调用，不对用户开放。
- CA 文件放在 control 的 `secrets/pki/`（权限 0600），不放进 `admin.db`。这样重置 control 数据时不会丢失 CA；否则
  所有主机的证书都要重签（`deploy-moox.sh` 已经为 EventBus 凭据处理过同样的问题）。
- 调用方只信任 MooX 私有 CA。
- Admin 的证书巡检（`trpc.moox.admin.certificates.timer`）改为检查 MooX 私有 CA 和各主机网关证书，到期前 90 天告警，
  作为兜底；同时去掉 `gateway_peer_ca`、`service_gateway_ca` 两项。
  公有证书清单来自 `secrets/pki/ca.crt` 与 `secrets/pki/hosts/<host-id>.crt`，每轮覆盖全部已登记主机，包括停用主机；不读取私钥，不在巡检中生成证书。首次部署时其他主机可能还没有证书，缺失会告警但不阻止 Admin 启动，避免阻断后续签发和部署。`MOOX_ADMIN_PKI_DIR` 与 bootstrap 的 `--pki-dir` 保持一致。
- EventBus 的证书暂不迁到新 CA（不在本次范围）。

**调用方密钥**

- **身份**：每个调用方身份各有一把服务签名密钥，包括：
  - 每个内部组件；
  - 管理后台的 `admin` 和 `console`；
  - 每台主机的 `host-gateway@<主机>`；
  - `access`、`moox-cli`。

  外部调用方（`scf-collector`、`factor-engine`、`moox-skill`）另有自己的密钥，只登记在外部接入上。
- **生成与复用**：在首次部署初始化时，或第一次部署引入某个调用方时生成；之后的部署一律复用，不重新生成。主副本加密
  存放在 Admin 密钥表里。
- **签名密钥的分发**：
  - CLI 部署某个组件时，把它自己的签名密钥下发到所在主机（`secrets/caller-<组件>.key`）；
  - `moox-cli` 的密钥保存在操作员机器上。
- **校验密钥的分发**：
  - 主机网关不再从本地文件读取密钥表，而是从网关控制的快照里拿到「允许调用本机路由的调用方」的校验密钥。
    快照经 TLS 传输，只发给 `host-gateway@<同一主机>`。
  - 需要预先放到主机上的只有主机网关自己的 `host-gateway@<主机>` 密钥，由 CLI 部署主机时下发。
  - 新增一台主机或一个调用方后，其他主机网关在下一次快照（15 秒内）就能识别，不需要逐台重新部署。
- **外部调用方的密钥**：部署外部接入时由 CLI 下发；轮换时需要重新部署外部接入。
- **轮换**：执行 `moox-admin-cli keys rotate --caller <身份>`，步骤如下：
  1. 生成新的 KeyID，新旧两把密钥同时有效；
  2. 新密钥随快照下发到各主机网关；
  3. 重新下发调用方的签名密钥，并重启该组件；
  4. 确认新密钥已经生效后，停用旧 KeyID。

  停用使用 `moox-admin-cli keys retire --caller <身份> --key-id <旧 KeyID> --confirm`。
  旧密钥不会按短宽限期自动失效；每个调用方最多同时保留两把有效密钥，旧密钥未停用时拒绝再次轮换。
  `keys info --caller <身份>` 只显示 KeyID 与状态；`keys export` 只将当前签名密钥写入 0600 文件。
  外部调用方的校验表使用 `keys export-access` 导出，轮换和停用后均须重新部署 Access。

  这样网关和调用方两端任何时候都不会出现不一致。
- **单台重新部署**：复用全部已有密钥，不影响其他主机。

**安全取舍（效率优先）**

| 让步 | 理由 |
| --- | --- |
| 外部接入使用明文传输 | 传输内容是行情和因子数据；签名可以防篡改和防重放；外部调用方调不到任何密钥类接口 |
| 网关拉路由用的 control HMAC 并入服务签名 | 少维护一类密钥；网关控制的路由 ACL 只允许 `host-gateway@*` 调用 |
| 本机调用走 11002 明文 | 该端口只监听 127.0.0.1 |
| 校验密钥随快照下发 | 快照经 TLS 传输，只发给通过身份校验的主机网关，省去逐台分发密钥表 |

**不让步的部分**：读取密钥的接口（`SecretMgr.GetSecretValue`）只对内部调用方开放，跨主机调用必须走 TLS；外部调用方的
白名单写在代码里，不能通过配置放宽。

### 3.6 服务目录与调用方客户端（`packages/gatewayclient`）

- **目录内容**：版本号、`tRPC service path → [主机 ID]` 的映射，以及
  `主机 ID → {公网地址, 私网地址, 地域}` 的映射。由网关控制根据「组件目录 × 已启用的部署」计算，随快照一起下发。
- **两种调用接口**：
  - 对象调用：`Invoke(ctx, servicePath, method, req, rsp)`。按序列化类型（默认 PB）把请求对象序列化，对序列化后的
    字节签名，再发送出去。各组件之间的普通调用都用这个接口。
  - 原始字节转发：`Forward(ctx, servicePath, method, serialization, body) ([]byte, error)`。保留调用方给定的序列化
    类型，直接对 `body` 签名并原样发送，返回原始的响应字节。外部接入转发 PB 请求、控制台透传 JSON 请求，都用这个
    接口。
  - 必须分成两个接口，因为现有的 `NewTRPCClientFilter` 会把请求对象重新序列化一遍：传入原始字节时，PB 会报
    `body not protobuf message`，JSON 会被改写成带 Base64 的 `{"Data":…}`。外部接入现在正是为此单独写了
    `rawGatewayClientFilter`。
  - 两种接口在本机和跨主机场景下都要经过真实的主机网关验证。
- **三种使用方式**：

| 方式 | 使用者 | 目标从哪里来 | 传输 | 需要的配置 |
| --- | --- | --- | --- | --- |
| 内部 | MooX 主机上的组件 | 本机主机网关的 `Directory`。目标在本机时连 `127.0.0.1:11002`，在其他主机时连 `<主机>:11003` | 跨主机走 TLS，校验 MooX 私有 CA | 调用方身份、签名密钥、CA 文件、目录缓存路径（`<数据目录>/gatewayclient/directory.json`） |
| 外部 | SCF、因子引擎、moox-skill | 配置中固定的外部接入地址和实例 ID `access@<主机>`；没有目录 | 明文 + 签名 | 外部调用方身份、签名密钥、外部接入地址、实例 ID |
| 隧道 | moox-cli | 先经 SSH 隧道连 control 的 `127.0.0.1:11002` 取目录，再对目标主机建立 SSH 隧道 | SSH | `moox-cli` 的签名密钥（在操作员机器上）；SSH 连接信息来自 `moox.toml` |
- **选路**：同一服务部署在多台主机上时（目前只有外部接入这样部署），优先选本机，否则按主机 ID 排序取第一台。只读
  方法失败时换下一台重试。
- **各模块配置只保留调用方身份和密钥文件**，目标地址、目标节点全部删除（清单见第 4 节）。

**对调用性能的影响可以忽略**，原因如下：
- 目录查询不在调用路径上：客户端启动时从本机主机网关取一次目录，之后每 15 秒比对一次版本号，有变化才更新，并落盘
  缓存。
- 每次调用只做一次内存查表（从服务找到主机），耗时在纳秒级；而一次网络往返在毫秒级。
- 连接是复用的：客户端对每台目标主机维护长连接，TLS 只在建立连接时握手一次，之后的调用不再握手。
- 跳数不变：本机调用仍是「调用方 → 本机网关 → 服务」；跨主机调用是「调用方 → 目标主机网关 → 服务」，比原来走 11001
  还少了 Caddy 这一跳。
- 异常处理：本机网关暂时不可用时，使用落盘缓存。目标网关返回「服务不在本机」或拒绝连接时，客户端立即刷新目录；
  如果是只读方法，再重试一次。

### 3.7 外部接入（`modules/access`）

- 从 `modules/storage`（`cmd/access`、`internal/accessproxy`）迁出，成为独立模块。二进制名 `moox-access`，环境变量前缀
  `MOOX_ACCESS_`。
- **入站**：监听 `0.0.0.0:11004`，tRPC 明文。外部调用方签名时，目标填外部接入实例 `access@<主机>`。nonce 存在 SQLite
  中（沿用现有实现）。
- **外部调用方白名单**写在组件目录（即代码）里，外部接入和路由编译共用同一份：

| 外部调用方 | 允许调用的方法 |
| --- | --- |
| `scf-collector` | PrimaryStore：`EnsureDatasetPeriod`、`CommitTimeSeriesBatch`、`RecordDatasetPeriodFailures`、`GetDatasetPeriodStatus`；MarketFetchRuntime：`ClaimTimerBatch`。实施时对照 SCF 代码核对。现有 collector 预设中的建表、删表、视图重建等权限不再授予 SCF |
| `factor-engine` | PrimaryStore：`ReadTimeSeriesRows`、`WriteFactorRows`、`ReportFactorPeriodComputed`、`GetFactorPeriodComputed`；Metadata：`GetDataset`、`ListDatasetColumns`、`ListDatasetSubjects`；FactorEngine：`SyncEngineCatalog`、`EngineHeartbeat`、`PullRecalcJob`、`ReportRecalcProgress` |
| `moox-skill` | PrimaryStore：`ReadTimeSeriesRows` |

- **上游转发**：用 `gatewayclient.Forward` 把外部调用方发来的 PB 字节原样转发给目标主机网关（走 TLS），调用方身份为
  `access`，签名针对实际发送的字节。外部调用方的名称放在请求元数据里，用于日志和指标。编译路由时，白名单里涉及的
  方法会自动把 `access` 加入允许的调用方。
- **部署位置**：storage 主机（`access@storage`，ap-nanjing）和 compute-1（`access@compute-1`，ap-hongkong），统一使用
  11004 端口。
- **SCF 怎么选外部接入**：目的是同地域走私网流量，以节省费用。现在按地域选择 Storage 入口的机制（`storage_access_targets`，
  以及同地域走 storage 私网）收敛为一条规则：
  - 与函数同地域的主机上有外部接入时，使用它的私网地址。前提是函数绑定了该主机所在的 VPC，可用现有的
    `moox-cli setup attach-scf-vpc` 完成绑定；
  - 同地域没有外部接入，或函数无法绑定该 VPC 时，使用 `access@storage` 的公网地址；
  - 外部接入地址和其他运行参数一样，由 Collector 经 CloudNode 写进函数的环境变量（替换现在的
    `InvokeStorageRPCGatewayTarget`），SCF 代码包里不带地址和凭据。
- **香港函数池改走私网**：目前香港函数池访问的是 compute-1 的公网地址。SCF 与 compute-1 属于同一个腾讯云账号，所以把
  香港函数池绑定到 compute-1 所在的 VPC，改为访问它的私网地址 `172.19.32.13`。
- **moox-cli 不经过外部接入**：它先通过 SSH 隧道连 control 的 `127.0.0.1:11002` 查服务目录，再按目录对目标主机建立
  SSH 隧道，连接该主机的 `127.0.0.1:11002`。调用方身份为 `moox-cli`。

### 3.8 管理后台：组件目录、主机、部署与网关控制

**组件目录**

组件目录放在 `packages/servicecatalog`，内嵌 `catalog.yaml`；`packages/doctor/components.yaml` 并入其中。示例：

```yaml
version: 1
components:
  - id: storage-primary
    name: 存储主服务
    binary: moox-storage-primary
    scope: any            # host | control | any
    replicas: single      # single | multi
    protected: false      # true 表示不能停用
    health:
      kind: readyz        # readyz | https | none
      port: 20210
      ready_body: '"ready":true'
    services:
      - path: trpc.moox.storage.Metadata
        port: 20100
        console_name: storage
        timeout_ms: 5000
        max_body_bytes: 33554432
        acl:
          - methods: [GetDataset, ListDatasets, ListDatasetColumns]
            callers: [console, collector, factor-mgr, monitor, strategy, storage-view]
          - methods: [DeleteSpace]
            callers: [console, moox-cli]
    doctor:
      role: storage
      dependencies: [eventbus]
      transport: reporter
      recovery_action_ids: [restart_service_manually]
  - id: cloudnode
    name: 云节点服务
    binary: moox-cloudnode
    scope: any
    replicas: single
    protected: false
    health:
      kind: readyz
      port: 11411
    services:
      - path: trpc.moox.cloudnode.CloudNodeMgr
        port: 11401
        console_name: cloudnode
        acl:
          - methods: [ListCloudAccounts, ListFunctionNodes]
            callers: [console, collector]
          - methods: [CollectGarbage]   # 只给 Admin 的每日垃圾回收任务，浏览器调不到
            callers: [admin]
  - id: console-proxy
    name: 控制台代理
    binary: moox-console-proxy
    scope: control
    replicas: single
    protected: true
    health:
      kind: readyz        # health HMAC；仅 control 本机 127.0.0.1
      port: 19528
principals:
  - id: moox-skill
    allow:
      - service: trpc.moox.storage.PrimaryStore
        methods: [ReadTimeSeriesRows]
```

- 目录校验（放进单测和 CI）：
  - 组件 ID 唯一；
  - 同一主机上的端口不冲突；
  - ACL 引用的调用方都已定义；
  - 外部调用方白名单只引用已声明的服务和方法；
  - `scope: control` 的组件只能部署在 control；
  - `replicas: single` 的组件在所有主机中最多只有一条启用的部署；
  - `health.kind` 为 `readyz` 或 `https` 时必须给出端口；
  - 带 `console_name` 的服务至少有一个方法放行 `console`。
- ACL 的判定逻辑由 `servicecatalog` 提供。主机网关和控制台（进程内调用时）共用这一份，确保两边的判定结果一致。
- Admin、Monitor、CLI、主机网关和外部接入都内嵌同一份目录，因此这几个组件必须同版本发布。

**表结构（`modules/admin/schema/admin.sql`）**

删除 `t_gateway_nodes`、`t_service_deployments`，新增下面三张表。主机网关的运行状态由心跳频繁写入，因此和主机配置
分表存放。

```sql
-- 部署主机：主机 ID 即主机名，每台主机恰好一个主机网关
CREATE TABLE IF NOT EXISTS t_hosts (
    c_host_id TEXT NOT NULL PRIMARY KEY,
    c_address TEXT NOT NULL,
    c_private_address TEXT NOT NULL DEFAULT '',
    c_region TEXT NOT NULL DEFAULT '',
    c_status TEXT NOT NULL DEFAULT 'enabled',
    c_description TEXT NOT NULL DEFAULT '',
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_status IN ('enabled', 'disabled')),
    UNIQUE (c_address)
);

CREATE TRIGGER IF NOT EXISTS trg_t_hosts_mtime
AFTER UPDATE ON t_hosts
FOR EACH ROW
WHEN NEW.c_mtime = OLD.c_mtime
BEGIN
    UPDATE t_hosts SET c_mtime = CURRENT_TIMESTAMP WHERE c_host_id = OLD.c_host_id;
END;

-- 部署：哪个组件部署在哪台主机；组件定义见代码中的组件目录
CREATE TABLE IF NOT EXISTS t_placements (
    c_host_id TEXT NOT NULL,
    c_component_id TEXT NOT NULL,
    c_status TEXT NOT NULL DEFAULT 'enabled',
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_status IN ('enabled', 'disabled')),
    FOREIGN KEY (c_host_id) REFERENCES t_hosts (c_host_id),
    PRIMARY KEY (c_host_id, c_component_id)
);

CREATE INDEX IF NOT EXISTS idx_t_placements_component ON t_placements (c_component_id);

CREATE TRIGGER IF NOT EXISTS trg_t_placements_mtime
AFTER UPDATE ON t_placements
FOR EACH ROW
WHEN NEW.c_mtime = OLD.c_mtime
BEGIN
    UPDATE t_placements SET c_mtime = CURRENT_TIMESTAMP
    WHERE c_host_id = OLD.c_host_id AND c_component_id = OLD.c_component_id;
END;

-- 主机网关运行状态：由心跳写入
CREATE TABLE IF NOT EXISTS t_host_gateway_status (
    c_host_id TEXT NOT NULL PRIMARY KEY,
    c_instance_id TEXT NOT NULL DEFAULT '',
    c_version TEXT NOT NULL DEFAULT '',
    c_expected_hash TEXT NOT NULL DEFAULT '',
    c_applied_hash TEXT NOT NULL DEFAULT '',
    c_route_count INTEGER NOT NULL DEFAULT 0,
    c_last_seen_at DATETIME,
    c_last_error TEXT NOT NULL DEFAULT '',
    c_previous_instance_id TEXT NOT NULL DEFAULT '',
    c_replaced_at DATETIME,
    c_conflict_instance_id TEXT NOT NULL DEFAULT '',
    c_conflict_seen_at DATETIME,
    FOREIGN KEY (c_host_id) REFERENCES t_hosts (c_host_id)
);
```

- 主机工作台的 SSH 主机（`t_ssh_host`）与 `t_hosts` 不建外键，只按地址关联，仅用于界面跳转。
- 注册主机时，自动为它创建「主机」范围组件（主机网关、主机采集器）的部署记录；这两条记录不能编辑。
- **实例替换与冲突**：
  - 心跳中的实例 ID 与当前实例不同时，记为「替换」：当前实例记入 `c_previous_instance_id`，并写入 `c_replaced_at`。
    正常重启就是这种情况，不告警。
  - 5 分钟内，若被替换掉的旧实例又上报心跳（即 A→B→A 这样交替），记为「冲突」：写入 `c_conflict_instance_id` 和
    `c_conflict_seen_at`，由 Monitor 告警。
  - 冲突记录在 5 分钟内没有再发生交替就清除。

**协议（`modules/admin/proto/sysdeploy_service.proto`）**

| 服务 | 使用者 | 方法 |
| --- | --- | --- |
| SysDeploy | 管理台 | `GetCatalog`（共享 YAML、SHA-256、明确的 control_host_id）、`ListHosts`、`ListPlacements`、`GetHostRoutes`（编译后的路由、期望与已应用的哈希、网关状态、snapshot_schema_version、compiled_at）、`GetDirectory`；`SetHostStatus`、`SetPlacementStatus`（受保护的组件和 control 主机拒绝停用） |
| SysDeploy | CLI | `SyncHostPlacements`（见下）；`DeleteHost`（主机上仍有业务部署时拒绝；自动维护的主机组件随主机删除） |
| GatewayControl（tRPC 端口 `11112`） | 主机网关 | `PullSnapshot(host_id, current_hash)`：快照包括路由、服务目录和校验密钥表；`ReportStatus(host_id, instance_id, version, applied_hash, error)`。只允许 `host-gateway@<同一主机>` 调用 |

`SyncHostPlacements` 的语义：

- **输入**：
  - 一台主机的信息：ID、地址、私网地址、地域；
  - 这台主机的完整组件列表，来自 `moox.toml` 的部署表。主机组件（主机网关、主机采集器）由系统自动维护，不需要
    写进列表。
- **先整体校验**：
  - 组件在目录中存在；
  - 符合部署范围：control 组件只能在 control；
  - 符合副本数：`single` 组件在所有主机中最多一条；
  - 受保护组件不能从列表中移除，例如不能从 control 的列表里去掉 `admin`。

  任何一项不通过就整体拒绝，不做任何修改。
- **校验通过后，在一个事务里完成**：
  - 写入或更新主机；
  - 补上缺少的部署，新部署默认启用；
  - 删除列表里已经没有的部署；
  - 已有部署的启用状态保持不变。
- **删除部署时不检查引用**：部署之间没有外键，路由和目录会在下一次快照中自动更新。
- **删除主机**：control 主机不能删除。其他主机必须先通过同步清空所有非 `scope: host` 的部署，包括已停用的部署；删除操作在同一事务中移除网关运行状态、两条自动维护的主机部署和主机记录。自动部署不作为“仍有业务部署”的拒绝条件，否则所有已注册主机都无法删除。

删除以下接口：`ListServiceDeployments`、`Get/Create/Update/DeleteServiceDeployment`、`ListActiveServiceDeployments`，
以及网关节点的增删改查。

**删除的旧机制**：
- 代码：`SeedDefaults`、`DefaultDeployments`、`obsoleteDefaultDeploymentNames`、`gatewayDeploymentName`、
  `defaultPublicHost`、`extra_config` 的解析与 `routeExtraConfig`、端口硬编码覆盖；
- 配置与命令：`config/setup/service-deployments.yaml`、`moox-admin-cli service-deployments`。

主机和部署改由 CLI 在部署时登记，Admin 启动时不写任何部署数据。

**控制台 API（`admin/internal/gateway` 改为 `admin/internal/console`）**

- tRPC 服务名 `trpc.moox.gateway.control` 改为 `trpc.moox.admin.Console`，仍监听 11000（HTTP，由控制台代理转发进来）。
- **路由**：`/api/admin/<console_name>/<方法>` 按组件目录映射到对应的 tRPC 服务，请求体按 JSON 序列化，用
  `gatewayclient.Forward` 原样透传。`console_name` 的规则是：单服务组件用组件 ID（如 `collector`、`monitor`），
  管理后台内部的服务用短名（如 `ssh`、`sysdeploy`）。
- **身份与权限**：
  - 控制台以调用方身份 `console` 发起调用，Admin 内部任务（如每日垃圾回收、发布租约校验）使用 `admin`；
  - 浏览器能调用哪些方法，看 ACL 是否放行 `console`，由主机网关统一校验。例如 `CloudNode.CollectGarbage` 只放行
    `admin`，`SecretMgr.GetSecretValue` 也不放行 `console`，所以浏览器都调不到；
  - Trade 的三个归属方法 `ClaimLogicalAccountOwner`、`ReleaseLogicalAccountOwner`、`RebindLogicalAccountOwner` 不放行 `console`，保留 `strategy` 和 `moox-cli` 的权限；
  - 现有的 `isMachineOnlyAdminMethod` 等特殊判断由 ACL 取代，可以删除。
- **管理后台自己的服务**（Auth、Ssh、SpaceMgr、SecretMgr、SysDeploy、Setup、CollectorPublishLease）：
  - 控制台在进程内直接调用，不经过主机网关；
  - 同样按 `console` 的 ACL 校验，判定逻辑与网关共用；
  - 这样控制台访问 SysDeploy、Auth 时不依赖网关路由，即使网关异常，也能在页面上处理。
- **保留不变**：
  - 会话鉴权、请求签名、限流、空间作用域注入，以及交易授权（`TradeSpaceAuthorizer`）；
  - SSH 终端和 SFTP 上传下载的原始处理器（`ssh/WsConnect`、`ssh/SftpUpload`、`ssh/SftpDownload`），继续在控制台
    进程内处理 HTTP/WebSocket，不走 RPC；
  - 存储接口在浏览器侧的方法映射（`console_name: storage`）。
- **删除**：`forwardStorageToNodeGateway`、`forwardTradeConsoleToGateway`，以及 `MOOX_NODE_GATEWAY_*` 环境变量。
- **协议**：Admin 进程内 RPC 服务的协议从 HTTP 改为 tRPC，端口不变；新增 GatewayControl，端口 `11112`。

**受保护组件与恢复**

- 受保护的组件是 `admin`、`host-gateway`、`console-proxy`、`web-host`，control 主机本身也受保护。它们一旦停用，控制台和
  CLI 的入口就会断开，所以：
  - `SetPlacementStatus` 和 `SetHostStatus` 拒绝停用受保护的对象；
  - 页面不显示它们的停用开关；
  - `SyncHostPlacements` 拒绝把它们从部署表中移除。
- 离线恢复命令：
  - `moox-admin-cli placement set-status --db-path <Admin数据库> --control-host-id <control主机ID> --host-id <主机> --component-id <组件> --status enabled`
  - `moox-admin-cli host set-status --db-path <Admin数据库> --control-host-id <control主机ID> --host-id <主机> --status enabled`

  这两条命令经 SSH 在 control 上执行，直接修改数据库，不依赖 Admin 或网关。下一次快照会下发新的路由。用于处理误停用
  或数据异常。
- 执行计划包含一条测试：停用一个非关键组件，再用离线命令恢复。

### 3.9 服务端协议统一

主机网关只转发 tRPC，最直接的做法是让各组件的业务服务都只用 tRPC 协议，删掉 HTTP 业务端口。这样也同时消除了

- 各模块的 `config/trpc_go.yaml`：
  - 业务服务的 `protocol: http` 改为 `trpc`；

  - 只有 HTTP 端口的，把原端口改成 tRPC；
  - 端口以组件目录为准。
- 健康端口（`/healthz`、`/readyz`、`/metrics`）保持 HTTP，不变。
- 控制台 API 用 `gatewayclient.Forward` 按 JSON 序列化透传请求体（Admin 现有的存储 BFF 已经是这样做的）。
- 现在通过 HTTP 访问网关的调用方，全部改为 tRPC：`admin/internal/gateway/forward.go`、`cli/internal/adminclient/`、
  `cli/internal/command/collector.go`、`cloudnode/internal/cloudcredential/resolver.go`、
  `cloudnode/internal/publishlease/client.go`、`collector/internal/app/runtime/auth.go`、

### 3.10 Monitor

- **检查定义**由组件目录和部署生成：每条已启用的部署对应一个检查 `placement:<主机>:<组件>`，探测方式取决于组件目录的
  `health.kind`：
  - `readyz`：带 health HMAC 请求健康端口的 `/readyz`，沿用现有做法；
  - `https`：供目录中未来选择 HTTPS 健康探测的组件使用；显式配置连接地址、SNI/Host 和 CA/系统信任，返回 2xx 或 3xx 即视为正常；当前控制台代理不使用它代替内部 `readyz`；
  - `none`：不生成检查，组件状态显示为「不探测」，不算作「未知」。

  主机网关本身也是每台主机上的一条部署，会被一并探测。这套检查取代现在的 `sysdeploy:*` 检查，也取代
  `monitor/internal/sysdeploy/sync.go` 中基于 doctor manifest 的过滤逻辑。
- **控制台代理**：与 Monitor 都在 control，以 health HMAC 请求 `127.0.0.1:19528/readyz`；发现逻辑不得把这个地址改写成公网主机地址。
  liveness、readiness 与 Admin/web-host 依赖状态分开。HTTPS 页面另生成端到端检查，结果不替代 `placement:control:console-proxy`
  的组件健康：internal 显式加载已验证的 Caddy CA，public 使用系统信任；连接 loopback 时仍校验公开 SNI/Host，不关闭证书校验。
  端到端失败会报告入口或依赖故障，但自愈不能据此重启仍然 live 的代理进程。
- **主机网关状态告警**（数据来自 `GetHostRoutes` 和主机列表），以下情况告警：
  - 已启用的主机超过 2 分钟没有心跳；
  - 同一主机出现网关实例冲突，即两个实例交替上报（规则见 3.8）；
  - 已应用哈希与期望哈希不一致超过 2 分钟。
  Monitor 将最近一次非敏感状态和同一期望快照的不一致起始时间保存到 `t_monitor_gateway_observations`；进程重启或读取失败不重置等待期。发现失败时保留旧事实，未知状态不会生成告警恢复结果；停用/删除主机后停止对应检查。HTTPS 探测策略与原始错误保存在 Monitor schema，服务及 CLI 同时发布；首次切换先一致性备份，再在 CLI 内保留通知渠道配置并离线重建运行库，不迁移旧检查和指标目录。
- **反向对账**：完整组件目录、主机和部署快照与探测定义在同一事务中保存到 Monitor；停用部署和 `health.kind: none` 也保留登记，不以检查是否存在判断登记状态。上报按主机 ID、组件 ID 精确关联，组件指标发布方直接使用目录 ID，不转换旧名称。
  有近期运行指标但没有部署记录的进程单独标为「未登记」；目录要求 Reporter、已登记但没有任何上报记录的部署标为「从未上报」。停用部署保留真实上报事实但停止 Reporter 告警；目录中的外部 principal（如 `scf-collector`）不虚构成主机组件。首次发现未成功时不推断「未登记」，后续发现失败保留完整旧快照。
  未登记的上报经过 EventBus 权限、事件信封和有界指标快照校验后进入目录，删除基于探测定义拒绝上报的入口。探测时间、指标产生时间分别保存；延迟报告不会将停止的进程刷新为在线。清理退役序列和 boot 记录时，为每条仍登记的部署保留最后一次上报，区分「停止上报」和「从未上报」。
- **健康概览 v2**：`modules/monitor/proto/monitor.proto` 中的 `GetHealthOverview` 改为返回结构化数据，不再在后端拼好
  中文卡片：

| 字段 | 内容 |
| --- | --- |
| `summary` | 告警数、需关注数、正常数、未知数，以及独立的组件计数（供首页使用）和未登记进程数 |
| `alerts[]` | 级别；告警对象（类型分为组件、数据集、主机、业务检查，附主机 ID、组件 ID、数据集 ID、频率）；标题；中文原因；原始错误；触发时间；最近检查时间。**主机告警也包含在内** |
| `components[]` | 主机 ID、组件 ID、名称、状态、探测结果（状态、时间、原始错误）、上报状态（实例 ID、版本、最近上报时间）、当前状态的开始时间 |
| `pipeline[]` | 各链路阶段（采集、存储与视图、因子、交易）的状态与明细：数据集、频率、最新水位、落后时长、最近一次成功、原因、原始错误 |
| `business_checks[]` | 业务检查：类型、模块、空间、状态、原因、原始错误、检查时间 |
| `hosts[]` | 主机摘要：显式部署主机 ID、物理 Agent ID、状态、CPU/内存/磁盘及各项可用标志、最近上报时间、网关信号；独立 Agent 不按 hostname 猜测部署关联 |
| `unregistered[]` | 在运行但没有登记的进程 |
| `notification` | 告警推送渠道及其配置状态 |

- 当前状态开始时间由后台采样持久化，仅在实际观察到状态改变时重置；API 请求不写入，观测变化尚未落库时不虚构时间。
- 主机资源用 Host Agent 配置的 `host_id` 显式关联部署，Agent ID 保留物理身份；部署工具必须下发规范 host_id。
- 状态值统一为 `healthy`、`degraded`、`down`、`unknown`、`disabled`、`unchecked`（不探测）六种。
- 名称只从组件目录读取，`alerttext.serviceNames` 也改为读目录。删除 `healthview.serviceName()` 和 `ChineseName()`
  中的模糊匹配，改为按显式字段（组件 ID、检查类型、数据集生产者）分组。
- 后端保留原始错误，另外给出中文摘要。前端删掉 `displayConclusion` 翻译表，只展示后端给的摘要，原始错误可以展开
  查看。

**首次部署（空环境初始化）**

空环境下有三个相互依赖：
- 主机网关需要证书和密钥，CA 却要在部署 control 时才生成；
- CLI 要经主机网关登记部署，而网关的路由又来自已经登记的部署；
- 登记主机依赖 Admin 运行，Admin 又要先装好。

所以首次部署单独做一步初始化（`moox-cli setup bootstrap`），步骤如下：

1. 把主机包和 control 包上传到 control，暂不启动。
2. 经 SSH 在 control 上离线执行 `moox-admin-cli bootstrap`，不依赖任何运行中的服务。它依次完成：
   - 执行 `admin.sql` 建表；
   - 在同一个数据库事务内，按 CLI 从 `moox.toml` 提取的主机与组件清单写入主机和部署（与 `SyncHostPlacements` 同一套校验），再生成全部调用方密钥并存入 Admin 密钥表；主机先登记，才能生成每台主机的 `host-gateway@<host-id>` 密钥；
   - 生成或验证已有 MooX 私有 CA，再提交上述事务；主密钥和 CA 文件是重跑时复用的持久检查点，数据库失败不会发布凭据包；
   - 为 control 签发主机网关证书；
   - 生成 control 的主机网关配置，将证书、配置与 control 所需签名文件一起发布到新的 0700 目录；`moox-cli` 操作员签名文件单独放在该包的 `operator/` 中。
3. 启动 Admin，再启动 control 的主机网关，确认网关已拿到快照并就绪。
4. 启动 EventBus 并验证角色 TLS，再启动 Host Agent；核心阶段只安装 Admin、EventBus 与两个主机组件，完整放置清单仍参与离线登记和身份签发。不能在远端 Storage 就绪前启动依赖它的策略、采集等控制服务。
5. 经已就绪的 Admin/网关和 SSH 隧道部署其余主机及业务单元；确认 Storage、Access、出口代理、交易和计算依赖就绪后，将 control 从核心子集升级为完整放置集合，最后激活 Console Proxy。完整初始化的成功条件仍覆盖全部主机、服务和浏览器链路。

整个初始化可以重复执行：已有的表、CA、密钥都会复用，不会重建。执行计划包含一条「空数据库、无证书、无缓存」的首次
安装验收。

上传后的软件准备由 `moox-runtime extract` 复用独立 `unitpackage` 执行，必须提供生产端摘要、profile 和新目标目录，并按助手所在 Linux 主机的平台校验。全部归档、清单、ELF 与逐文件摘要核对完成后，才将私密暂存目录原子发布，已有目标一律不覆盖。软件准备只解包公开软件与模板，不切换 current、不注入身份或复制数据、不启动进程；此阶段可以在旧版本运行时执行，后续配置、持久状态复制、停止旧实例与激活仍须持有共用维护锁。

身份材料由独立 `unitbundle` 消费，公开清单由 `servicecatalog/hostbundle` 在两端共用。调用方传入当前拓扑、完整放置、已确认的 CA 指纹和期望快照；可信 SSH 的 Admin 响应必须与下载清单相同。逐文件限长、摘要、签名身份、Access 外部验证表、网关配置、证书链/精确 SAN/私钥全部核对后，才发布到新的 0700 私密目录。`PublishServices` 去掉 bootstrap 操作员配置和密钥，服务材料保持规范相对路径；操作员本机安装及软件发布目录中的配置注入仍由安装器完成。`moox-runtime inspect-bundle` 复用相同校验，只输出公开元数据。该阶段不切换 current 或启动服务。

离线命令只接收 `--topology-file` 指定的 0600 JSON 文件（`version: 1`、`control_host_id`、`hosts`），由部署 CLI 生成并上传；不复制或读取原始 `moox.toml`。其余参数为 `--db-path`、`--encryption-key-file`、`--pki-dir`、`--output-dir`。整个初始化用操作系统文件锁串行化；重跑保留已停用状态，保留原主密钥、CA 与调用方 KeyID，并为本次部署重签 control 叶证书。原主密钥丢失且已有加密记录、已有网关密钥却丢失 CA、私密文件损坏或权限不符均拒绝继续，必须恢复原件。数据库和文件系统无法组成一个事务：如果事务已提交而输出阶段失败，从头重跑会复用已提交的身份，再生成完整包；失败的暂存目录会清理。

后续部署先同步目标主机的完整放置，再通过 control 的可信 SSH 执行 `moox-admin-cli host-bundle`。参数为 `--host-id`、`--control-host-id`、`--db-path`、`--encryption-key-file`、`--pki-dir`、`--output-dir`；地址和组件只从现有拓扑读取。命令不创建数据库、schema、主密钥或 CA；为目标主机及其组件生成缺少的调用方密钥并复用已有 KeyID，每次重签该主机叶证书。包含 Access 时同时导出外部验证表及轮换重叠期密钥。普通部署不导出操作员身份；bootstrap 的操作员文件由部署 CLI 单独取回并以 0600 安装在本机。

两种命令共用私密身份包格式：新建 0700 目录、0600 文件，`host-gateway/config/app.yaml` 为规范配置路径，`bundle.json` 保存主机身份、公开 KeyID、期望快照摘要、证书摘要及逐文件 SHA256/长度，清单自身不计入载荷。主密钥和 CA 私钥始终留在 control 持久目录，未完成的暂存包不得交给安装器。主机包与业务包可在不同根目录：业务根通过 `host-gateway` 目录链接访问独立主机包，客户端先解析配置实际位置再解析相对 CA 路径；各组件继续持有自己的签名文件和数据目录。

**暂停服务**

停机切换时，必须保证被暂停的服务在整个切换期间都不会被自动拉起。现在有两个地方会自动拉起服务：
- 安装器部署完会执行 `start.sh`，拉起全部服务；
- 每分钟运行的 `healthcheck.sh` 只在维护锁被占用时跳过，其余时候会重启停止的服务。

做法如下：
- 在部署根目录下设暂停标记 `run/paused/<组件>`。`start.sh`、`healthcheck.sh` 和安装器都识别这个标记，跳过被暂停的
  服务。标记放在发布目录之外，切换发布目录时不会丢失。
- 新增 `moox-cli setup pause --host <主机> --components <组件,...>` 和 `resume`。暂停时写入标记并停止进程；恢复时删除
  标记并启动进程。
- 维护锁的语义：
  - 安装器运行期间自己持有维护锁，结束时释放；
  - 暂停标记与锁无关，会一直有效到执行 `resume`；
  - `healthcheck.sh` 在锁被占用时整体跳过；锁空闲时，也不会拉起被暂停的服务。

启停与守护由 host 软件包中的纯 Go `moox-runtime` 统一执行，业务包不再各自复制等待和强杀逻辑。每个发布目录保存部署器生成的私密 `runtime.json`，只列该单元实际放置的组件、物理发布根和对应环境文件；二进制身份、健康端口与服务目录摘要共用 `servicecatalog`。公共运行状态位于独立的部署根 `run/`：主机身份、维护锁、暂停标记、PID 记录和排空记录都不放入 releases。安装器在已持锁时将同一文件描述符传给助手，配合 `--maintenance-lock-held` 使用，不以布尔值跳过锁核验。

发布准备由独立 `unitinstall` 组合软件包、已验证身份与显式私密配置，持共用维护锁生成按单元裁剪的身份、实际 KeyID、Host Agent 规范主机 ID、运行计划/环境和七个生命周期脚本，再同步并原子发布候选目录。业务发布通过有界目录视图访问同主机、同部署根的主机包。`prepared.json` 记录软件、配置、身份、环境及脚本的完整文件清单，`inspect-release` 在安装切换前验证尚未启动、未复制状态的候选；出现未声明文件、内容/权限变化或非法链接时拒绝。该准备层不切换 current、不复制运行数据、不启停服务。其上的激活层在同一维护锁下停止旧单元、复制并同步独立状态、原子切换 current、按依赖顺序启动；阶段日志与持久安装标记覆盖安装器退出后的恢复窗口，失败恢复旧快照和原运行选择，显式回滚保留升级后的数据在退役目录。暂停标记保持独立，未完成恢复时守护跳过且自动启动拒绝。离线状态由 `seal-state` 绑定新发布与预期旧 current，在停机前和独立复制后验证全部摘要，仅允许显式可变目录；旧快照保持独立，Admin 主密钥、MooX CA 私钥及操作员材料不通过该通道进入发布。真实 CLI 部署、五步 bootstrap 的停止/一致性备份和离线初始化编排、首次 CA 授权的一次性消费与历史 CA 迁移继续由后续阶段接通。

控制主机初始化由目标主机 `unitbootstrap` 编排，私密规范请求只包含共享拓扑、预构建软件和显式运行配置。停机前日志记录 host/control 的旧发布与原运行集合，随后在同一维护锁下停止写入、克隆关闭后的 Admin 状态并执行离线初始化。首次离线数据库、Admin 主密钥和 MooX CA 持久保留，失败重试复用已签发身份。离线子进程继承维护锁，并在父进程死亡时结束；数据库仍有写入者时，新的协调者不能取得锁。host 先以不启动方式激活，为 control 提供固定目录视图；control 导入封存状态后，按 Admin ready、网关有效快照/心跳 ready、EventBus ready 和其余组件的顺序启动。复合日志负责两个单元的共同恢复，单元日志负责各自 current 与快照恢复。成功结果先落盘再清除跨单元保护；已完成发布的重跑只修复相同发布的运行状态，不重复离线初始化。

升级前核对既有 Admin 的实际数据库路径，必须指向发布内已初始化的私密快照源；缺失或位于外部路径时拒绝，不能因此生成新密钥。服务专用启动子进程使用 umask 0077，确保数据库和缓存的新文件可以按私密权限独立复制，避免依赖 SSH 用户的默认 umask。

离线初始化在关闭的 Admin 数据库中事务签发 EventBus 角色和 TLS 身份，随后导出私密材料；重跑复用已有身份，拒绝缺失一半或损坏的 TLS 身份。准备层仅投影每个组件需要的角色、CA 和连接配置，服务端私钥及用户 ACL 仅进入 EventBus。broker 开启鉴权与 TLS，组件配置及环境指向发布内的独立副本，导出目录不成为运行依赖。所有离线签发子进程遵循相同的维护锁继承与父进程死亡约束。

Console Proxy 常规服务配置不包含 CA 初始化权限，serve 只使用已验证的持久基线。首次 internal CA 由目标编排请求 proxy_ca.create 显式授权，历史迁移则以 proxy_ca.import_directory 提供关闭后的规范状态；导入要求原始发布的根证书与指纹，不能从现存私钥自行建立信任。独立离线 initialize-state 只加载 PKI，不开启监听、申请站点证书或安装系统信任。部署根 identity/console-proxy/ 保存私密凭据和初始材料，先持久记录 pending，再同步完整材料并排他原子发布，最后写 ready；未发布生成阶段可以恢复，已消费材料丢失则拒绝重建。候选失败、退役清理及首次 SIGKILL 恢复不改变根身份。升级核对持久身份后复制最新关闭的运行状态，保留 ACME 缓存和已续签的中间证书。public-only 初始化不生成 internal CA，已有历史 CA 继续保留供回滚。原生 CLI 的授权生产和生产历史目录归档仍须接入。

所有共用运行层启动的服务使用稳定的组件/主机实例身份和随机启动标识。HostGateway 的 healthz/readyz 输出标准健康 JSON，包含制品摘要与启动标识；readiness 同时要求最新快照同步、心跳和持久存储可用。status 只读探测就绪状态，探测失败单独报告并保留进程身份。

进程记录包含 Linux start ticks、UID、可执行文件 device/inode 和启动时停止预算，信号使用 pidfd，避免 PID 复用误杀。父子管道屏障保证 PID 记录持久化后才 exec；父进程提前退出使等待子进程收到 EOF，已记录的启动器与最终可执行文件转换可由新助手继续等待或停止。健康探测同时核对制品摘要和本次随机 boot ID。console-proxy 的外层预算从实际配置中的请求排空、引擎停止与清理三项相加，并随旧进程记录；新发布不能缩短旧进程预算。取消停止后持久排空标记保留，守护不拉起；重试停止继续已发送 TERM 的原预算。超过完整预算后再次核验身份，强杀后观察实际退出，再启动替代进程。守护的重启依据是鉴权 liveness，not-ready 不触发重启；认证或返回进程身份不符时停止自动处置并报告错误。

### 3.13 采集对象同步并入 Collector，Binance 经出口代理访问

现状见第 2 节：两份实例都在处理全部自动标签，彼此没有分工；control 连不上 Binance 合约接口，compute-1 访问东方财富
不稳定。根本原因是网络，因此改为「一个实例 + 出口代理」。

**采集对象同步并入 Collector**

- `moox-collector-subject`（`collector/cmd/subject`）只是把 `subjectsync` 的标签同步和属性同步放在一个单独进程里运行。
  单独部署的唯一实际用途，是把它放到能访问 Binance 的 compute-1 上。出口代理解决网络问题后，这个独立进程就没必要了。
- 由 `moox-collector` 中的两个 tRPC 定时器触发，与 Collector 现有的 `schedule`、`dns`、`kline_resample` 定时器写法
  一致。两个定时器都用 `packages/timerjob` 包装，以获得超时控制、重叠时跳过和指标上报，做法与 Monitor、Admin、
  主机网关相同：

| 定时器 | 触发 | 每次做什么 | 超时 |
| --- | --- | --- | --- |
| `trpc.moox.collector.subject_tags.timer` | 每分钟一次，在第 30 秒，与第 0 秒的 `schedule` 错开 | 从 Storage 读出全部自动标签，只同步到期的那些。是否到期由标签自己的 cron 和上次运行时间决定 | 10 分钟 |
| `trpc.moox.collector.subject_attributes.timer` | 每分钟一次，在第 45 秒 | 只执行本分钟内到点的属性同步任务。任务计划写成带时区的 cron（`10 8 * * *`，`Asia/Shanghai`），即北京时间 08:10:45 执行，避开整点的标签同步 | 10 分钟 |

- 为什么标签同步不直接用 cron 定时器：每个标签的同步周期是在管理台「标签」页的「定时更新」里按标签单独设置的，存放在
  Storage 中，没法写死成 tRPC 定时器。所以定时器只负责每分钟检查一次，到期与否由标签自身决定。上次运行时间也存在
  Storage 里，进程重启后不会漏跑。
- 属性同步为什么也是每分钟检查一次，而不是直接写成每天一次的 cron 定时器：tRPC 定时器底层用的是 robfig/cron，按进程
  所在主机的本地时区执行。如果直接写成 `45 10 8 * * *`，在 UTC 主机上会变成北京时间 16:10:45 才执行。
  - 改为每分钟检查后，任务计划自己带时区，执行时间与主机时区无关，也不用设置进程时区（设置进程时区会影响进程里其他
    使用本地时间的代码）。
  - 判断规则无状态：本次触发时间往前一分钟的区间内，只要有该任务的计划时间就执行。
  - 现有两个任务的计划（A 股北京时间 08:00、crypto UTC 00:00）本是同一时刻，统一改为北京时间 08:10。
  - 删除 `AttributeRunner` 里的内存调度（`next` 字段）。错过的运行（例如恰好在这个时间重启）要等到第二天，这一点与现在
    相同。属性变化很慢，影响可以忽略。
- 删除 `subjectsync.Service` 的轮询循环和 `poll_interval` 配置。拉取超时和属性同步任务的列表并入
  `collector/config/app.yaml` 的 `subject_sync` 段。指标并入 Collector 的上报。Collector 启动时照常向 Storage 登记
  支持的数据源（`RegisterSubjectListing`）。
- 只保留一个实例，标签不会再被两个进程抢着写。
- 删除：`cmd/subject`、组件 `collector-subject`、健康端口 11413、`config/subject.yaml`，以及相应的部署脚本和 Monitor
  检查。

**出口代理（组件 `egress-proxy`，二进制 `moox-egress-proxy`，部署在 compute-1）**

- 用途：替 MooX 内部组件访问国内连不上的外部接口，目前只有 Binance 的 REST 接口；出口在香港。
- 形态：独立组件，代码放在新模块 `modules/egressproxy`。不并入其他进程的原因见本节末尾。
- 接口：tRPC 服务 `trpc.moox.egress.Proxy`，tRPC 端口 11440，健康端口 11441，挂在 compute-1 的主机网关后面。
  - 调用方通过 `gatewayclient` 调用，复用主机网关的 TLS、签名和 ACL；
  - 不需要新开公网端口，也不需要另一套代理鉴权；
  - ACL 只允许 `collector` 调用。
- 调用方把要代理的请求（域名、路径、参数等）传给 tRPC，由出口代理发出 HTTPS 请求，再把结果原样返回：

  ```protobuf
  service Proxy {
    rpc Do(DoReq) returns (DoRsp);
    rpc ResolveDomains(ResolveDomainsReq) returns (ResolveDomainsRsp);
  }

  message DoReq {
    string method = 1;               // GET 或 POST
    string host = 2;                 // 目标域名，必须在白名单内，例如 fapi.binance.com
    string path = 3;                 // 例如 /fapi/v1/exchangeInfo
    string query = 4;                // 已编码的查询参数
    map<string, string> headers = 5; // 只转发白名单内的请求头
    bytes body = 6;
    int32 timeout_ms = 7;            // 不超过 60000
  }

  message DoRsp {
    trpc.moox.common.RetInfo ret_info = 1;
    int32 status = 2;                // 目标返回的 HTTP 状态码
    map<string, string> headers = 3;
    bytes body = 4;                  // 已解压，不超过 32MB
  }
  ```

  - 出口代理只发 HTTPS 请求；不在白名单里的域名一律拒绝。
  - 目标返回的 HTTP 错误（如 429、5xx）原样放在 `status` 里返回，由调用方现有的重试逻辑处理；只有代理自身出错时才
    设置 `ret_info`。
  - `ResolveDomains` 从交易服务移过来，现在的实现在 `trade/internal/rpc/dns_resolver.go`，请求和响应结构沿用。它供
    Collector 的 `dns` 定时器生成 SCF 的 DNS 快照。迁移后 Collector 不再依赖交易服务，交易服务删除这部分功能和
    `trade_dns_resolver` 路由。
- Collector 一侧：
  - 给 HTTP 客户端（`collector/internal/httpclient`）增加一个传输层（`http.RoundTripper`）：凡是白名单域名的请求，就把
    `http.Request` 转成 `DoReq` 发给出口代理，再把 `DoRsp` 还原成 `http.Response`。其他请求照常直连。Binance 适配器等
    上层代码都不用改。
  - 必须显式注入，因为现在的传输层不读 `HTTPS_PROXY` 等环境变量。也就是说，compute-1 那个 systemd 服务里配置的代理
    其实从来没有生效过。
- 白名单在 `moox.toml` 的 `[egress_proxy] domains` 中配置，由 CLI 同时渲染给出口代理和 Collector：出口代理据此放行，
  Collector 据此决定哪些请求走代理。
- 访问量：标签每小时同步一次，属性每天同步一次，DNS 快照每 5 分钟刷新一次。经过代理多出来的一次往返可以忽略。
- 出口代理不可用时：
  - Binance 标签同步会失败，按现有机制上报（`ReportTagRunFailure`），由 Monitor 告警；
  - DNS 快照沿用上一次的成功结果；
  - SCF 采集不受影响，因为 SCF 在香港，直接连接 Binance。
- 切换：Collector 经出口代理同步 Binance 标签成功后，再删除 compute-1 上手工安装的 `moox-collector-subject.service`
  和 `/opt/moox/subject/`（见执行计划第 13 节）。
- 为什么做成独立组件，而不是并入其他进程：
  - 出口代理必须运行在香港，Collector 在 control 上，所以它不可能放进 Collector 进程。
  - compute-1 上已有的进程都不合适：

| 并入 | 不合适的原因 |
| --- | --- |
| 主机网关 | 违反「主机网关只转发本机服务」的约束，而且会把慢且容易出错的外部请求放进所有跨主机调用都要经过的关键进程；概念上也会把网关和代理混在一起 |
| 外部接入 | 外部接入负责外部调用方进入 MooX，出口代理负责 MooX 访问外部，两者方向和信任模型相反；而且外部接入还部署在南京，那里不需要出口 |
| 交易服务 | 这正是现在 DNS 解析放在交易服务里的做法，本次要拆开 |

  - 代价只是 compute-1 上多一个很小的进程。部署位置由 `moox.toml` 的部署表决定，以后其他地域需要出口时，加一行即可。

原生主机部署在 core 成功后执行：本机持久保存完成收据、原始运行身份和操作员 CA 绑定，`deploy-host` 经签名 SSH 隧道同步完整放置，再通过控制机的运行中 Admin 导出目标身份。EventBus 导出限定客户端角色与公共 CA，主密钥、CA 签名私钥和 broker 私钥不扩散。导出与目标部署都持久记录原请求；重试复用已签发字节，目标中断先恢复旧快照，已回滚候选保留并换新候选。完成重试修复缺失进程且保留暂停，区分 `host-ready` 和 `host-paused`。这一步只保证 Host Gateway/Host Agent，业务单元、完整 control 与 Console Proxy 仍按本节依赖顺序接续。纯 Go/前端在本机编译；只有需要 CGO 的 Linux 产物交给编译机。
