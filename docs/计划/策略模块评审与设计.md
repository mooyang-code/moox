# 策略模块：现状评审与重新设计

> 状态：设计稿第三版，已吸收两轮评审意见，待编码。
> 范围：`modules/strategy` 及其与 Factor、Storage、Trade、Monitor 的接口。先评审现状，再给出
> "因子计算完成之后策略如何计算"的目标流程，最后给出面向个人量化系统的模块设计。实施步骤见
> [策略模块执行计划](策略模块执行计划.md)。项目尚未上线，不做任何历史兼容。

## 1. 结论摘要

- **架构骨架是对的，应当保留。** Strategy 只读 Storage 的 View、只输出相对权益的目标权重、不接触账户；
  由 `ViewDataReady` 事件驱动；结果按 (实例, 会话, bar_end_time) 幂等；会话 fence 与 outbox 投递完整；
  `bar_end_time` 作为唯一业务时间。这些边界和 Trade 的契约都不需要动。
- **现状按文档示例跑不通。** 四个 P0 缺陷：内置标的池 `spot_symbols` 对 crypto 标的恒为空（会把账户清仓）、
  前端模板的事件名后端不接受、做空保护依赖的 `market` 字段取值与假设不符、策略要求结果行携带因子版本属性而
  全仓库没有任何写入方（Storage 还明确拒绝该属性），引用因子的实例每期在加载阶段失败。
- **缺少个人量化最核心的三件事：** 回放（用历史周期验证策略）、可解释（每个标的为什么被选中或淘汰）、
  换仓控制（排名缓冲区）。没有这三件事，策略只能"上线后看结果"。
- **复杂度与价值倒挂。** 约 1.2 万行代码里有大量兼容旧 Runner、旧 Manifest、旧列名、定时触发和
  "视图世代溯源"的分支；事件处理器从不填充溯源字段，这些分支在生产路径上是死的。每个周期还会对
  每个实例重新编译 DSL 并向 Factor、Storage 各发多个 RPC 做依赖校验。
- **设计方向：** 一个实例绑定一个因子结果 View（它已经携带 OHLCV 和全部因子列）；只有一种触发；
  求值引擎是纯函数（输入一帧数据，输出目标与解释）；回放与实盘走同一条求值路径；每个周期的结果与解释落库；
  删除所有兼容分支。

## 2. 现状评审

### 2.1 当前链路（事实）

```text
Collector 周期完成 ─► DataNode CollectorPeriodCompleted
  ─► Factor Engine：读源数据窗口 ─► Python 计算 ─► WriteFactorRows（携带列 + 因子列）
  ─► ReportFactorPeriodComputed（status、universe_subject_ids、factors[]{status, failed_subjects, source_hash}）
  ─► Storage View 索引完成 ─► ViewDataReady（view_id=结果 View，completion_kind=factor_period.computed，
                                             period_time=bar_start，universe_subject_ids，factors[]）
  ─► Strategy 消费者（durable strategy_view_data_ready_v1）
        遍历本空间全部启用实例 ─► 解析 DSL ─► CompileWithBindings ─► VerifyDependencies（RPC）
        ─► 读源 View 当期行 + 读因子 View 当期行（可选再读上一期）
        ─► 池 → filter_before → score（pct_rank/zscore）→ select → signals/holding → weight → filter_after
        ─► CommitResult（一个事务）─► outbox 发布 LogicalAccountTargetWeightRequested
Trade：校验 (instance_id, session_id)、valid_until、bar_end_time 单调 ─► 权益换算数量 ─► 收敛
```

以 Binance 现货 1h 为例，相关对象的实际身份：

| 对象 | 实际值 |
| --- | --- |
| 采集任务 / 源数据集 / 源 View | `dasftksvjhj2jom4vhe0` / `dataset_dasftksvjhj2jom4vhe0` / `view_dasftksvjhj2jom4vhe0_kline_1h` |
| 因子集 / 结果数据集 / 结果 View | `fset_dasftksvjhj2jom4vhe0_1h` / `dataset_factor_dasftksvjhj2jom4vhe0_1h` / `view_factor_dasftksvjhj2jom4vhe0_1h` |
| 结果 View 的列 | 携带列 `open high low close volume quote_volume trade_num` + 因子列（如 `bias_q_20`，列属性 `origin_factor_id`、`factor_output`） |
| 结果数据集的属性 | `owner_module`、`dataset_role`、`source_dataset_id`、`write_owner`；没有 `market_type` |
| 标的 ID | `BTC-USDT`（现货与合约共用一个标的；`market` = `CRYPTO`，`currency` = `USDT`，属性只有 `base`、`quote`） |
| 行的 series_tag | `venue:binance` |
| 市场类型（现货/合约） | 在**源数据集**属性 `market_type` 上，不在标的上，也没有复制到结果数据集 |
| 因子版本 | `source_hash` 只是源码内容的哈希；参数、回看、输入列不在其中；结果行不携带任何版本属性 |

推论：结果 View 一张表就包含策略需要的全部输入，Strategy 现在同时读源 View 和结果 View 是多余的；
"现货还是合约"由实例绑定的 View 所对应的源数据集决定，策略表达式和标的池都不应从标的属性猜。

## 3. 因子计算完成后的策略计算流程（目标设计）

### 3.1 时间与身份

- Storage 行键和 `ViewDataReady.period_time` 都是 **bar_start**；策略、结果、Trade 使用 **bar_end**。
  crypto：`bar_end = bar_start + bar`；stockcn 日线：`bar_end` 是该交易日 15:00（Asia/Shanghai）。
  换算沿用 `input/calendar.go`，不再接受任何"别名时间"。
- 一次求值的身份是 `(instance_id, session_id, bar_end_time)`，与现状一致。每条结果记录当时的 `dsl_hash`
  与绑定快照，历史解释不受后来修改定义影响。
- 结果有效期 `valid_until = bar_end + 2 根 bar`（现为 4 根）。Trade 在有效期内持续收敛，过期自动失效。

### 3.2 触发、路由与确认

只有一种触发：`ViewDataReady`。

```text
ViewDataReady(space, view_id, period_time, completion_kind, status, universe_subject_ids, factors[])
  ─► 按 (space, view_id) 找到绑定该 View 且已启用的实例；没有 ─► ACK
  ─► 对每个实例顺序执行 3.3 ~ 3.8；一个实例的错误不影响其余实例，错误汇总后再决定 ACK / NAK
  ─► 每个实例都产生了已落库的终态记录（ok 或 skipped）─► ACK
  ─► 任一实例的终态记录没有落库（Storage、EventBus、SQLite 瞬时错误）─► NAK 退避重投，不设投递次数上限
```

- 因子结果 View 的事件要求 `completion_kind = factor_period.computed`；K 线 View 的事件要求
  `completion_kind = collector.period.completed`。实例绑定哪种 View 在启用时就确定了。
- 删除 cron 定时触发。"数据迟迟不到"用 Monitor 的截止告警解决（见 3.8），不是用定时器拿残缺数据求值。
- 消费者的 `MaxDeliver` 设为无限（NATS 的 -1）。求值与读输入的尝试次数由业务在进程内限制（默认 5 次），
  超过后写 `skipped(infra_retry_exhausted)`；只有终态记录落库成功才 ACK，落库失败就继续 NAK 直到数据库可写。
  解码失败与契约错误仍然 TERM。
- `period_time` 早于实例最近一次处理过的周期 ─► 作为乱序记录 `skipped(out_of_order)`。提交时的 CAS 冲突先重读最新
  记录：同一周期已提交 ─► 重复，ACK；已有更新周期 ─► 乱序；否则重新求值一次。

### 3.3 就绪判定

启用实例时已经把 DSL 引用的每一列解析成 `(column, origin_factor_id, definition_hash)` 并固化在实例绑定里。
`definition_hash` 由 Factor 计算，覆盖源码、因子类型、规范化后的参数、回看周期、输入输出列和
`allow_partial_universe`，随 `FactorPeriodState` 进入 `ViewDataReady`（见 4.9）。每个事件到来时只做本地比对：

| 事件中的因子状态 | 处理 |
| --- | --- |
| 实例引用的因子不在 `factors[]` 中，或 `definition_hash` 为空 | 跳过，原因 `factor_missing` |
| `definition_hash` 与固化值不同 | 跳过，原因 `factor_changed`；需要人工重新启用实例以采用新版本 |
| DSL 用到 `bars[-1]`，且上一期记录的 `definition_hash` 与本期不同 | 跳过，原因 `factor_changed`（上一根数据可能属于旧版本） |
| `status = skipped` | 跳过，原因 `factor_skipped`（该周期不会再有新事件，重投无意义） |
| `status = degraded` | 继续；`failed_subjects` 只对引用该因子的规则视为缺数（见 3.4） |
| `status = complete` | 继续 |
| View 事件 `status = degraded` 且无 `factors[]`（K 线 View） | 继续；`failed_scope_ref` 对应的标的视为缺数 |

事件级指纹只证明"这次计算声明的版本"，不证明历史行属于该版本。第一版明确不做行级版本持久化，
也不承诺历史行版本可验证；上一期指纹比对覆盖了 `bars[-1]` 跨版本的情况，重算而不改定义的情况版本不变，接受。

"跳过"是一种被记录的结果（见 3.7），不是错误；连续跳过由 Monitor 告警。

### 3.4 输入装配

- 只读实例绑定的那一个 View。读取时同时固定 `expected_active_index_id` 与 `expected_active_index_revision`，
  任一变化就丢弃已读页面、重新读取完整输入，不混用页面。
- **预期集合 E**：事件 `universe_subject_ids` ∩ 活跃标的 ∩ universe 配置（标签、黑白名单）。
  **年龄剔除 G**：E 中不满足 `min_age_bars` 的标的。
  **可用集合 A(r)**：按规则 r 计算，E − G 中当期有行、规则 r 引用的列都有值、且未被 r 引用的因子标记失败的标的。
  **缺数集合 M(r)** = E − G − A(r)。黑白名单、标签和年龄剔除都不算缺数。
- `min_age_bars` 的语义是"标的在 N 根之前已有数据"，用于剔除新上市标的。实现为每期一次探针查询：
  取 T − (N−1) 根所在的窗口（向前容忍两根），只读 `close` 列，覆盖 E 中全部标的，有行即满足。无状态、无缓存。
  探针查询失败按基础设施错误重试，绝不当作"历史不足"剔除。启用时校验 N 不超过 View 的保留根数。
- 实时读取的 selector 来自数据集当前 active 的标的绑定；回放另行枚举（见 4.5）。
- 每个标的一行，列值为 `Decimal`；空值保留为"缺失"，不补零。同一标的多个 `series_tag` 的行视为配置错误，
  本期跳过，原因 `ambiguous_series`。DSL 用到 `bars[-1]` 时再读上一根（日历感知）。
- 装配结果是一个不可变的 `Frame{bar_end, rows[subject] → {col → value|null}}` 加上 E、G、A(r)、M(r) 四个集合，
  这是求值引擎的唯一输入。回放时同一个 `Frame` 由历史周期装配，引擎代码完全相同。

### 3.5 规则求值

每条规则按下列阶段执行，每个阶段对每个标的只做"通过 / 淘汰（原因）"或打分，所有中间结果保留到解释明细：

```text
E ─► pool ─► filter ─► score ─► select ─► weight ─► filter_after      （type: rank）
       └── pool ─► exit / entry（带理论持仓状态）─► weight           （type: signal）
```

| 阶段 | 语义 |
| --- | --- |
| pool | 规则级，可省略（默认 = E − G）；固定列表；或 `{tags: [...]}`。显式给出时替代 universe 的标签与黑白名单，但仍受"当期有行、未被上游标记失败、满足 `min_age_bars`"约束 |
| filter | 布尔表达式。引用的列在该行缺失 ─► 该标的淘汰，原因 `missing:<col>`，计入 M(r)；上期持有则本期权重为 0 |
| score | 数值表达式。`rank(expr)`、`zscore(expr)` 在**通过 filter 的样本**上计算，参数可以是任意表达式，可嵌套，内层先算；`rank` 同分取平均名次、单样本记 0.5；`zscore` 零方差记 0；排序以 `instrument_id` 打破平局；结果 NaN ─► 淘汰 |
| select | `top N` / `bottom N` / `where`；`buffer B`：上期该规则持有的标的若仍在前 `N + B` 名就保留，空位由新标的按分数补足；`bottom` 下名次按分数升序 |
| weight | `total` 是规则预算上限；`method = equal`（选中标的等分）或 `rank`（选中集合内按名次线性配权，最优 N 份、最差 1 份，方向与 select 一致）；`cap` 是规则内单标的上限，超出部分在规则内按比例分给未达上限的标的，仍分不出去的留现金 |
| filter_after | 只剔除不补位，剔除的权重留现金 |
| signal | `type: signal` 规则：先对旧理论持仓判 `exit`，再对候选判 `entry`，退出优先；持有标的的 `exit` 输入缺失视为退出 |
| holding | `type: rank` 规则的可选分批换仓 `bars/offsets`；与 buffer 互斥；缺数标的从所在批次移除，其份额留作现金，不重新分配 |

表达式实现只保留 compiler 一套：启用时把每个阶段编译成 Expr `Program`，`rank(...)`/`zscore(...)` 在编译期用
AST 改写成预计算变量（`expr.Patch`），运行时先对样本做一次截面预计算，再逐行执行 `Program`。
删除 evaluator 里的正则解析与二次编译。

### 3.6 组合合成与守门

```text
各规则权重相加（做空为负）
  ─► 组合级单标的上限 portfolio.max_weight：超出部分留现金，不跨规则再分配
  ─► gross = Σ|w| 不得超过 portfolio.leverage（默认 1），超过即本期跳过，原因 config_error
  ─► 现金 = 1 − Σw（现货 View 上不允许负权重）
  ─► 守门（按 rank 规则逐条计算）：
        进入 filter 的 |A(r)| < portfolio.min_universe ─► 跳过，原因 universe_too_small
        |M(r)| / |E − G| > portfolio.max_missing（默认 0.2）─► 跳过，原因 too_many_missing
```

- 第一版不做逐标的 `min_delta`，换手控制只靠 `select.buffer`；沿用旧权重会破坏预算约束并阻止强制退出，
  以后若加回来，强制退出必须绕过阈值，且在换仓控制之后重新校验 gross、单标的上限和现金。
- 守门是防止"池被意外清空 ─► 发布空目标 ─► 清仓"的最后一道闸。选择阶段合法地选出 0 个标的
  （例如 `filter_after` 全部剔除）仍然是有效结果，意味着转为现金，页面上要显式标明。`signal` 规则的池是显式的，
  不受 `min_universe` 约束。

### 3.7 结果、解释与投递

一个 SQLite 事务写入：

- `t_strategy_results`：状态 `ok | skipped`、`skip_reason`、`dsl_hash`、目标权重、规则状态（signal / holding / buffer
  的理论持仓）、本期摘要（|E|、|G|、各规则的 |A|、|M|、各阶段数量、gross、net、换手、现金）、输入摘要
  （view、bar_start、事件 ID、各因子 `definition_hash`）。
- `t_strategy_result_items`：E 中每个标的在每条规则下的最终阶段、分数、名次、权重、淘汰原因；缺数、上游失败、
  年龄不足也各有一行，最需要解释的标的不能缺席。数据量按保留天数清理。
- **最近处理周期**与**最近 ok 决策**分开：`skipped` 只推进处理记录，不取消任何 pending 目标，不参与投递时的
  "最新结果"判断；规则状态只从最近 ok 决策恢复；只有新的 ok 决策才替代旧目标。
- 绑定组合账户的 `ok` 结果进入 outbox，事件契约 `LogicalAccountTargetWeightRequested` 不变。

### 3.8 失败语义与可观测

| 情况 | 处理 |
| --- | --- |
| 解码失败、事件契约错误 | TERM |
| Storage / EventBus 瞬时错误 | 进程内重试，超过尝试预算写 `skipped(infra_retry_exhausted)` 后 ACK |
| 终态记录落库失败（SQLite 不可写） | NAK 退避，无投递次数上限，直到落库成功 |
| 提交 CAS 冲突 | 重读最新记录后分类：重复 ACK、乱序记 skipped、否则重新求值一次 |
| DSL / 绑定错误（启用后列被删、View 失效） | `skipped(config_error)`，实例标记 `degraded`，页面提示重新启用 |
| 周期可以求值 | `ok`，指标 `moox_strategy_period_total{instance_id,result="ok"}` |
| 周期不能求值 | `skipped`，指标 `moox_strategy_period_total{instance_id,result="skipped",reason}` |
| 截止告警 | 每个启用实例登记为 Monitor 的期望数据集（间隔 = bar 时长），每期上报一次运行；连续缺期由现有新鲜度检查告警；启用后的首个周期给一个等待宽限 |

### 3.9 伪代码

```go
// 处理一条 ViewDataReady：所有实例都处理，错误汇总，只有全部终态落库才 ACK
func (c *Consumer) handle(ev ViewDataReady) HandlerResult {
    instances := c.store.EnabledInstancesByView(ev.SpaceID, ev.ViewID)
    var retry []error
    for _, inst := range instances {
        barEnd := calendar.BarEnd(inst.Calendar, inst.Bar, ev.PeriodTime)
        if !barEnd.After(inst.LastProcessedBarEnd) {
            retry = appendIfErr(retry, c.store.CommitSkipped(inst, barEnd, "out_of_order", ev))
            continue
        }
        if reason := readiness.Check(inst.Resolved, inst.PreviousFingerprints, ev); reason != "" {
            retry = appendIfErr(retry, c.store.CommitSkipped(inst, barEnd, reason, ev))
            continue
        }
        frame, err := c.input.LoadBar(ctx, inst, ev, barEnd)          // 只读一个 View，固定 index 与 revision
        if err != nil {
            if c.budget.Exhausted(ev.ID, inst.ID) {                    // 进程内尝试预算
                retry = appendIfErr(retry, c.store.CommitSkipped(inst, barEnd, "infra_retry_exhausted", ev))
            } else {
                retry = append(retry, err)
            }
            continue
        }
        decision := engine.Evaluate(inst.Program, frame, inst.LastOkState) // 纯函数
        if err := c.store.CommitDecision(inst, barEnd, decision, ev); err != nil {
            retry = append(retry, c.classifyCommitError(inst, barEnd, err)) // CAS 冲突先重读分类
        }
    }
    if len(retry) > 0 {
        return NAK(backoff, errors.Join(retry...))
    }
    return ACK
}
```

## 4. 策略模块设计（面向个人量化）

### 4.1 设计原则

- **一个人维护得住：** 概念只有定义、实例、结果、回放四个；实例绑定只有三项（定义、View、账户）。
- **因子层做时序，策略层做截面：** 滚动、均线、分位等都写成因子；策略表达式只在当期截面上做过滤、打分、
  排序、配权。这样 Strategy 不需要回看窗口，输入永远是一帧。
- **回放与实盘同一条路径：** 求值引擎是纯函数，实盘喂最新一帧，回放按周期喂历史帧。
- **每个周期都有记录：** 成功有解释，跳过有原因，缺失有告警。
- **先观察，再上账户：** 观察模式与回放是默认工作流，绑定账户是最后一步。
- **不碰账户状态：** 换仓控制只基于本实例的理论目标，真实持仓、余额、精度全部留在 Trade。

### 4.2 领域模型

| 概念 | 内容 |
| --- | --- |
| StrategyDef（定义） | `strategy_id`、名称、DSL 文本、`dsl_hash`。跨空间共享，被启用实例引用时不可修改 |
| StrategyInstance（实例） | 定义 + 空间 + **一个 View** + 可空组合账户 + 启停 + 会话 + 启用时固化的绑定（列解析、因子 `definition_hash`、bar、日历、市场类型） |
| Decision（周期决策） | 一次求值的产物：状态、目标权重、规则状态、摘要、解释明细 |
| Replay（回放） | 对一个定义在一个 View 的历史区间上逐周期求值，产出决策序列与理论绩效 |

会话语义：进程重启恢复原会话与规则状态；重复调用启用是幂等的，不新建会话、不清零状态；
只有显式停用后再启用才产生新会话，规则状态从零开始。

去掉：`EvaluationInput` 的多种变体、`StrategyRunner`、Manifest、Runner 版账户授权接口。

### 4.3 DSL v3

在现有 DSL 上做减法和定向加法，不是另起炉灶：

```yaml
name: binance_spot_momentum_1h
bar: 1h                                 # 可选断言；实际周期由绑定的 View 决定，不一致则启用失败

universe:                               # 省略即 all：事件冻结名单 ∩ 活跃标的
  min_age_bars: 240                     # 240 根之前已有数据才进入候选（剔除新上市）
  exclude_tags: [stablecoins]           # Storage 中维护的手动标签，多个策略共用
  exclude: [BTC-USDT]                   # 也可直接列标的；BTC 由下面的择时规则单独持有

rules:
  - id: long_momentum                   # 稳定标识：规则状态、解释明细按它关联，改了会丢状态
    name: 多头动量选币                   # 可选，只用于展示
    type: rank                          # 固定词表：rank（截面选股）| signal（固定池择时）
    filter: "quote_volume_mean_20 > 2000000 && close > 0"
    score: "0.6 * rank(bias_q_20) + 0.4 * rank(quote_volume_mean_q_20)"
    select: {top: 5, buffer: 2}
    weight: {total: 0.8, method: equal, cap: 0.3}

  - id: btc_trend
    name: BTC 均线趋势跟随
    type: signal
    pool: [BTC-USDT]                    # 显式池替代 universe 的标签与黑白名单
    entry: "bars[-1].close <= bars[-1].ma_20 && bars[0].close > bars[0].ma_20"   # 上穿均线入场
    exit:  "bars[0].close < bars[0].ma_20"                                        # 跌破均线退出
    weight: {total: 0.2}

portfolio:
  leverage: 1
  max_weight: 0.3
  min_universe: 20
  max_missing: 0.2
```

示例依赖的因子：`BiasQ`、`QuoteVolumeMean`、`QuoteVolumeMeanQ` 来自 `modules/factor/factors/catalog.json`
（窗口 20），`ma_20` 来自 `examples/factors/timeseries/ma.py`，以 `windows: [20]` 导入并启用为同一因子集的成员。
文档示例必须能原样保存、启用并产出目标。

规则用列表而不是以规则名作 map key：固定的字段集合便于校验和表单编辑，顺序也随列表保留。`id` 仍然必须稳定，
因为 signal / holding / buffer 的理论持仓状态和解释明细都按 `id` 关联，改 `id` 等于从零开始；`name` 只用于展示。
`type` 显式声明而不是从字段推断：`rank` 要求 `score`、`select`、`weight`，`signal` 要求 `pool`、`entry`、`exit`、`weight`，
字段放错位置在保存时就报错。

标的范围分两层：`universe` 是策略级默认池，省略即 all；规则显式给出 `pool` 时替代 universe 的标签与黑白名单，
但仍受"当期有行、未被上游标记失败、满足 `min_age_bars`"约束。标签直接复用 Storage 的 Tag：手动标签（如 `stablecoins`、
`majors`）在元数据页维护，多个策略共用；自动标签（如 `binance_spot`）由采集侧同步。`tags` 取任一命中。
策略模块已在网关白名单内可调用 `ListTags`、`GetTag`、`ListTagMembers`，不需要新路由。

与现 DSL 的差异：

| 项 | 现状 | v3 |
| --- | --- | --- |
| `triggers` | schedule / event 二选一或同时 | 删除；统一由 View 事件触发 |
| `data.bar`、`data.calendar` | 必填 | `bar` 可选断言；日历由空间决定（crypto → 24x7，stockcn → 交易日历） |
| `rules` | 以用户自定义的规则名作 map key；规则类型由出现的字段推断 | 列表；每条规则 `id`（稳定标识，必填）、`name`（展示，可选）、`type`（固定词表 `rank` / `signal`） |
| 标的池 | 每条规则必填 `pool`（列表或 UDF） | 策略级 `universe`（默认 all，可用 `tags`、`exclude_tags`、`include`、`exclude`、`min_age_bars`）；规则 `pool` 可省略，显式给出时为列表或 `{tags: [...]}`；删除 UDF 机制 |
| `filter_before` | | 改名 `filter`；缺列只淘汰该标的 |
| `pct_rank(x)` / `zscore(x)` | 只接受裸字段 | `rank(expr)` / `zscore(expr)`，参数为任意表达式，可嵌套 |
| `select` | `top/tail/where` | `top/bottom/where`，增加 `buffer` |
| `weight` / `weight_each` | 标量，等权 | 对象：`total`（预算上限）、`method`（`equal` / `rank`）、`cap`；删除 `weight_each`；按分数比例配权延后 |
| `side` | 字符串 | 保留；做空只允许在源数据集 `market_type = swap` 的 View 上，启用时校验 |
| `signals` | 嵌套在规则下的 `signals.entry/exit` | `type: signal` 的规则直接写 `entry` / `exit` |
| `holding` | | 保留，仅 `type: rank` 可用；与 `buffer` 互斥 |
| `portfolio` | 无 | 新增 `leverage`、`max_weight`、`min_universe`、`max_missing` |

### 4.4 实例绑定

创建实例只需要三个输入：定义、View、组合账户（可空）。启用时自动完成：

1. 读取 View：频率、所属数据集、全部列及列属性。因子结果 View 沿数据集属性 `source_dataset_id` 再读一次源数据集，
   取其 `market_type`；K 线 View 直接读自身数据集。市场类型缺失则拒绝启用，不默认现货。
2. 解析 DSL 引用的每个标识符：必须是该 View 的列；因子列记录 `(origin_factor_id, definition_hash)`
   （从 Factor 的 `GetFactor` 读一次），携带列（`open`、`close` 等）不记录指纹。
3. 校验：`bar` 断言、做空与市场类型、`buffer` 与 `holding` 互斥、权重上限、`min_age_bars` 不超过 View 保留根数。
4. 把解析结果固化为 `c_resolved_json`，运行时只与事件里的指纹比对。
5. 绑定账户时认领 Trade 会话（现有握手保留）。

页面上删除手工绑定 JSON，只剩三个选择器；绑定详情以只读表展示。

### 4.5 回放

第一版的回放定位是**基于现有 View 的研究回放**：用来比较策略版本，不承诺复现历史上的实时结果。

- 入参：定义（或未保存的 DSL 文本）、View、`[start, end)`、手续费（bps）。
- 执行：在 Strategy 进程内作为后台任务逐周期运行：装配历史帧 ─► `engine.Evaluate` ─► 记录决策；
  规则状态在内存中跨期传递，从空状态开始。同一时刻只跑一个回放。
- 数据来源只有 View（已决策）：不读 PrimaryStore，不查周期标记。
  - 可回放区间受 View 保留根数限制（默认每序列 5000 根：1h 约 208 天，4h 约 833 天，1d 以实际数据为限）。
    需要更长的小时级回放时调大 `[storage_retention].view_bars`，代价是 DuckDB 文件更大。
  - 按时间范围分页读取整段数据，固定 index 与 revision，在内存中按 bar 切帧，不逐期发起查询。
  - selector 枚举数据集的全部标的绑定（含已停用的），不复用实时的 active 目录；每一期的 E = 该期有行的标的。
    是否存在幸存者偏差取决于绑定是否还在、行是否仍在保留期内、`tags` 是否变过（标签只有当前成员关系），
    回放报告要逐项标注。
  - 因子版本不可验证：结果行不携带版本，回放开始时只核对当前各因子的 `definition_hash` 等于定义解析时的值，
    报告标注"区间内历史行版本未验证"。
  - DSL 用到 `bars[-1]` 时从 `start` 前一根开始读；`min_age_bars` 只能数到 View 保留起点，
    有效回放起点 = 保留起点 + `min_age_bars`。
- 理论账本：回放维护独立的理论持仓（数量）与现金，不读 Trade。每期流程：按当期 `close` 对持仓估值 ─► 求值得到目标权重
  ─► 按当期 `close` 成交到目标（理想化假设，与"bar_end 后成交"不同，要在报告里写明）─► 成交金额计费
  （`fee_bps × 成交额`）─► 换手 = 成交额 / 成交前权益。skipped 的周期持仓与状态原样延续；持有标的当期无价时按最后已知价估值并标注
  "估值陈旧"；标的此后不再有行，则在其首个无价周期按最后已知价清算并标注。
- 绩效：累计收益、年化、最大回撤、平均换手、平均持仓数、跳过周期数；每期记录目标、持仓账本、收益、换手、费用。
- 一致性验收是引擎级的：相同编译结果、相同 Frame、相同 E/G/A/M、相同前序状态 ─► 相同 Decision。
  只有无 buffer、无 holding 的纯 `rank` 策略才能额外要求"回放最后一期等于实时同期结果"。
- 结果写入 `t_strategy_replays` 与 `t_strategy_replay_bars`，页面展示净值曲线、指标和每期持仓。

```sql
    c_summary_json TEXT NOT NULL,
    c_event_data BLOB,
    c_publish_status TEXT NOT NULL DEFAULT 'none',
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_status IN ('ok', 'skipped')),
    CHECK (c_publish_status IN ('none', 'pending', 'sent', 'cancelled')),
    UNIQUE (c_instance_id, c_session_id, c_bar_end_time)
);

CREATE INDEX IF NOT EXISTS idx_t_strategy_results_latest_ok
ON t_strategy_results (c_instance_id, c_session_id, c_bar_end_time)
WHERE c_status = 'ok';

CREATE INDEX IF NOT EXISTS idx_t_strategy_results_pending
ON t_strategy_results (c_ctime, c_result_id)
WHERE c_publish_status = 'pending';

CREATE TABLE IF NOT EXISTS t_strategy_result_items (
    c_result_id TEXT NOT NULL,
    c_rule TEXT NOT NULL,
    c_instrument_id TEXT NOT NULL,
    c_stage TEXT NOT NULL,
    c_score REAL,
    c_rank INTEGER,
    c_weight TEXT,
    c_reason TEXT NOT NULL DEFAULT '',
    PRIMARY KEY (c_result_id, c_rule, c_instrument_id),
    FOREIGN KEY (c_result_id) REFERENCES t_strategy_results (c_result_id) ON DELETE CASCADE
);

CREATE TABLE IF NOT EXISTS t_strategy_replays (
    c_replay_id TEXT NOT NULL PRIMARY KEY,
    c_strategy_id TEXT,
    c_dsl_yaml TEXT NOT NULL,
    c_space_id TEXT NOT NULL,
    c_view_id TEXT NOT NULL,
    c_start_time INTEGER NOT NULL,
    c_end_time INTEGER NOT NULL,
    c_fee_bps REAL NOT NULL DEFAULT 0,
    c_status TEXT NOT NULL,
    c_progress_time INTEGER,
    c_metrics_json TEXT NOT NULL DEFAULT '{}',
    c_error TEXT NOT NULL DEFAULT '',
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_status IN ('pending', 'running', 'done', 'failed', 'cancelled'))
);

CREATE TABLE IF NOT EXISTS t_strategy_replay_bars (
    c_replay_id TEXT NOT NULL,
    c_bar_end_time INTEGER NOT NULL,
    c_status TEXT NOT NULL,
    c_targets_json TEXT NOT NULL,
    c_positions_json TEXT NOT NULL,
    c_summary_json TEXT NOT NULL,
    c_return REAL,
    c_equity REAL,
    c_turnover REAL,
    c_fee REAL,
    PRIMARY KEY (c_replay_id, c_bar_end_time),
    FOREIGN KEY (c_replay_id) REFERENCES t_strategy_replays (c_replay_id) ON DELETE CASCADE
);
```

保留策略：结果主表永久保留（每期一行，很小）；解释明细与回放按天数清理（默认 90 天），由模块自己的
定时任务执行。解释明细每期每规则对 E 中每个标的一行，约 500 个标的、两条规则的小时策略一天 2.4 万行，
90 天约 220 万行，SQLite 可承受，必要时缩短保留天数。

### 4.7 管理接口与页面

`StrategyMgr`：

| 分类 | 方法 |
| --- | --- |
| 定义 | `CreateStrategy`、`UpdateStrategy`、`GetStrategy`、`ListStrategies`、`DeleteStrategy`、`ValidateStrategy`（对一个 View 做列解析并在最新周期试算一次，返回解释，不落库） |
| 实例 | `CreateStrategyInstance`、`UpdateStrategyInstance`、`GetStrategyInstance`、`ListStrategyInstances`、`SetStrategyInstanceEnabled`、`DeleteStrategyInstance` |
| 结果 | `ListStrategyResults`、`GetStrategyResult`（含解释明细）、`ListStrategyTargets` |
| 回放 | `StartReplay`、`GetReplay`、`ListReplays`、`ListReplayBars`、`CancelReplay` |

页面：

- 定义编辑器：模板（与真实标的、因子库一致）、保存前校验、"试算"按钮显示最新周期的解释表。
- 实例：三个选择器创建；详情页展示绑定解析结果、健康状态、最近结果列表。
- 结果：每期一行（状态、目标数、gross、换手、跳过原因）；展开看每个标的的阶段、分数、排名、权重、淘汰原因。
- 回放：发起表单、进度、净值曲线、指标表、每期持仓，以及局限性标注。

### 4.8 代码结构

```text

  cmd/server, cmd/cli
  internal/dsl        解析、校验、编译（合并现 config + compiler；一套表达式引擎）
  internal/engine     纯函数求值：E/G/A/M → rules → portfolio → 守门，输出 Decision 与解释
  internal/input      从一个 View 装配 Frame（实时：一期；回放：区间迭代）、集合划分、年龄探针
  internal/readiness  事件、固化绑定与上一期指纹的比对
  internal/trigger    ViewDataReady 消费、路由、尝试预算、终态落库后 ACK（删除 scheduler、inbox）

  internal/store      SQLite（4.6 的表）
```

### 4.9 对外接口的变化

| 对方 | 变化 |
| --- | --- |
| Factor | 新增 `definition_hash`：由 Factor 在规范化定义上计算（源码 hash、`factor_type`、规范化 `params_json`、`lookback_periods`、`input_columns`、`outputs`、`allow_partial_universe`），写入 `FactorDef` 与周期标记的 `FactorPeriodState`；`source_hash` 保留源码身份含义不变 |

### 4.10 明确不做

- 多周期混合（一个实例只有一个 bar）。
- 组合优化器（均值方差、风险平价）；按分数比例配权（`method: score`）。
- 逐标的 `min_delta` 换仓阈值。
- 行级因子版本持久化与历史行版本验证。
- 实盘持仓、成交反馈到策略规则。
- Python 策略运行时：复杂逻辑写成因子，策略保持声明式。
- 盘口级回测、滑点模型。

## 6. 决策记录

| # | 问题 | 决策 |
| --- | --- | --- |
| 1 | 上期持有、本期因子缺失的标的如何处理 | 清仓：该标的本期不参与计算，目标权重为 0，不沿用上期权重（见 3.3、3.5） |
| 2 | 回放数据来源 | 只用 View，不读 PrimaryStore，策略模块只与 View 打交道；定位为研究回放（见 4.5） |
| 3 | 规则的组织方式 | 列表 + 稳定 `id` + 展示用 `name` + 固定词表 `type`，不再用自定义规则名作 map key（见 4.3） |
| 4 | 标的池 | 默认 all；按 Storage 标签收窄或排除；规则可显式覆盖（见 4.3） |
| 5 | 选择结果为空 | 允许发布空目标（转现金），受 `portfolio.min_universe` 与 `max_missing` 守门；页面显式标注"转为现金" |
| 6 | `max_missing` 的默认值 | 0.2，按预期集合与可用集合的差计算，可在 `portfolio` 中覆盖 |
| 7 | DSL 的 `bar` 断言 | 保留为可选项，避免 1h 策略误绑到 1d View |
| 8 | `type` 词表 | `rank`（截面选股）与 `signal`（固定池择时）；`holding` 作为 `rank` 的可选项 |
| 9 | 因子版本 | Factor 计算完整的 `definition_hash` 随事件下发；策略做事件级校验加上一期指纹比对；不做行级版本持久化，不承诺历史行版本可验证 |
| 10 | 上市年龄 | 字段名 `min_age_bars`，语义"N 根之前已有数据"，每期探针查询实现，无缓存；探针失败按基础设施错误重试 |
| 11 | 换仓控制 | 第一版只有 `select.buffer`，不做 `min_delta`；`portfolio.max_weight` 超出部分留现金 |
| 12 | 权重方法 | 第一版 `equal` 与 `rank`，`score` 延后 |
| 13 | 确认与重试 | 投递次数不设上限；求值尝试在进程内限次后转 skipped；终态记录落库成功后才 ACK；CAS 冲突重读后分类 |
| 14 | 结果与投递 | `skipped` 不取消 pending、不参与最新性判断；规则状态只从最近 ok 决策恢复 |
| 15 | 会话 | 重启恢复原会话与状态；重复启用幂等；显式停用再启用才新建会话并清零状态 |
| 16 | 市场类型来源 | 因子结果 View 沿 `source_dataset_id` 读源数据集属性；缺失拒绝启用 |
