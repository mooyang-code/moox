# 部署修复与安装提速执行计划

执行计划 v5（2026-11-01，尚未编码），基线 `main@edb0b350`（v0.4.3 之后一个只改测试的提交）。
需求来源：[部署流程与skill优化清单](部署流程与skill优化清单.md) 第 14～38 项。本文写怎么做，清单写做什么和为什么。

v2 改为管理台只用内部证书。v3 吸收两份独立审查：补上暂停和重置要用的空间集合、`setup init` 里隐藏的 sudo、验收按拓扑处理、控制机看护；第二批拆开产物包改造，修正元数据并发和 EventBus 材料合并的问题；去掉回收目录和 Storage 单一二进制；目标时间按审查结果放宽。v4 吸收复审：修正验收口径，补上 control 的配置绑定检查和看护回执，把 `staging` 判定提前到 B2，定义清除重跑的摘要规则，处理没有因子机的拓扑；预检通过后下载、清除、防火墙同时进行。v5 吸收第四轮审查：定义 `expected == 0` 和因子、策略的判断来源，定准备阶段的顺序，改用单独的 RPC 触发对账，单元失败后改配置写成限制。

## 1. 背景与目标

2026-11-01 用 v0.4.3 做了一次真实全新安装。部署显示完成，但采集计划和因子任务都是 0，机器时间约 24 分钟，另有约 10 分钟人工等待，中途还清空重装过一次。

目标：

1. 新安装完成后真的有数据：K 线入库、因子前进、默认策略运行。
2. 全新安装约 3 分钟服务就绪，约 5 分钟看到第一根 K 线（目标值，未实跑）。
3. 不要求用户在中途做事：确认一次之后跑到底，装完后再做一次浏览器信任。
4. 修复任何问题都不靠 Agent 上机改数据或翻维护者脚本。

## 2. 决定

| 项目 | 决定 |
| --- | --- |
| 发布节奏 | 分两批。第一批 v0.4.4 修问题并恢复线上，第二批 v0.5.0 提速 |
| 改名 | `core` 改为 `admin`，放在第一批最前面，不留别名 |
| WS 采集 | 不依赖 `[scf_plan]`，空间有启用的 K 线任务就管理 |
| 线上恢复 | 全新重装，不做原地升级。线上没有行情和因子数据，重装还能验证整条安装路径。执行前要用户确认 `setup wipe` |
| 兼容 | 不写状态迁移，旧状态文件不读，旧产物布局不支持 |

| 准备阶段 | 预检通过后，下载、清除、防火墙同时进行 |

## 3. 动手前要确认的事

### 线上全新重装

第一批发布后对四台机器执行 `setup wipe`。清除前再确认一次线上没有要保留的内容：行情和因子为空，但用户可能已经填了交易所密钥或做过设置。

### 线上配置里的因子任务

`setup init` 遇到不存在的源数据集会整体失败。重装前要确认 `moox.toml` 的 `[[factors.tasks]]` 没有指向非默认数据集。Agent 不读这个文件，用 `config get` 或由用户确认。

### T2：WS 采集不依赖云函数开关（清单 14）

| 集合 | 内容 | 用途 |

`setup verify` 的检查：

| 检查 | 数据来源 | 通过条件 | 失败错误码 |
| --- | --- | --- | --- |
| 采集计划 | `GetCollectorStatus` | 有进行中或已生效的计划；计划里有推送或本地执行项时，collector-stream 在线 | `collection_not_started` |
| K 线 | 已启用 K 线任务的数据集，用 `CheckKline` 查最近三期 | `expected > 0` 且缺失比例不超过 5%，输出缺失数 | `kline_not_arrived` |
| 因子 | `ListFactorTasks(status=enabled)` 按 `space_id` 过滤，读 `last_run` | 1m 任务的最后一期在本次运行内前进，且状态不是 `failed`；频率大于 1m 的只查不是 `failed` | `factor_not_advancing` |
| 策略 | `strategy instance list` | `enabled=true` 的实例有 `session_id`，不等第一个结果 | `strategy_not_running` |

每项结果是 `pass`、`wait`、`fail` 或 `skip`，等到超时才算失败，失败时给出原因和下一步。

- **K 线允许少量缺失：** 门控到截止时间就带缺口结算，缺口靠之后补采，要求零缺失可能永远走不完。
- **因子 `degraded` 算通过：** 预热期状态就是 `degraded`，默认 1m 任务约持续 1 小时。
- **本次运行内前进：** 开始时记下基线，在内存里比较。`recent_runs` 没有空间和频率，所以改用任务列表。
- **跳过：** 空间没有启用的 K 线任务时跳过并说明；没有部署 factor-engine 时跳过因子；源数据集不在已启用 K 线任务里的因子任务跳过；没有启用的策略实例时跳过策略。

`expected == 0` 的判定（RPC 不返回原因，所以按下表判断）：

| 情况 | 结果 |
| --- | --- |
| `GetCollectorStatus.datasets` 里没有这个数据集 | `wait` |
| 1m，且现在早于 `effective_from` 加 3 分钟 | `wait` |
| 1m，超过这个时间仍是 0 | `skip`，按休市处理 |
| 频率大于 1m | `skip` |

全新安装时计划已登记、生效周期还没到，`expected` 也是 0，所以不能写成排除法。查最近三期是为了避开每分钟开头的截止时间。

要在第一批实装时看：疑似下架的标的在 `CheckKline` 里仍算缺失，全新安装还没有确认记录，比例超过 5% 时会等到超时。阈值按真实比例再定。

拓扑处理：`next_steps` 从 `[deployments]` 和 `[scf_plan]` 算出能采集的空间：有 collector-stream 就有 crypto，再加 `[scf_plan]` 里的空间，每个空间一条验收。算不出就不加验收步骤，改成一条警告，说明 crypto 任务不会运行。第一批不改任务默认启用。

不用 `data kline get`：它需要 `config/data-access.yaml`，新装的操作电脑没有。不新增因子水位接口，要阻塞原因时再加。

测试：无计划、有计划无数据、数据正常、因子阻塞四种情况；只走云函数的空间不要求 collector-stream；少量缺失能通过；因子 `degraded` 能通过；没有海外机、没有因子机的拓扑。

## 6. 第一批发布和线上恢复

发布：

1. 第一批合入 main，等 main 上的 `verify-trusted` 通过。PR 上的检查不代表 main 通过。
2. 单独提交把 `install.md` 的 `VER` 改为 `v0.4.4`，合入后打 tag 并推送。
3. `scripts/release/build-release.sh v0.4.4 ~/Downloads/moox-release-v0.4.4/dist`。
4. 在 dist 目录运行 `gh release create v0.4.4 --repo mooyang-code/moox --verify-tag --notes-file … ./*`。dist 不是 Git 仓库，要带 `--repo`。
5. `source ~/.zshenv` 后运行：

   ```bash
   python3 ~/Downloads/moox-release-v0.4.0/cnb-release.py v0.4.4 ~/Downloads/moox-release-v0.4.4/dist <发布说明> none <主仓库目录>
   ```

   第 4 个参数传 `none`，不删旧版本。核对 CNB 的 main、tag 和附件哈希，CNB 的 main 一起带上 `edb0b350`。

线上恢复（用户确认后，在部署电脑上执行）：

1. 下载 v0.4.4，把 `moox.toml` 放进 `moox-v0.4.4/` 根目录。
2. 运行 `./bin/moox-cli config migrate --set-factors-enabled true --yes`，删除旧的 `tls_mode` 并打开因子导入。
3. `setup validate`，确认路线和 `setup wipe` 预览，用户确认后清除。v0.4.3 的状态会判 `existing`，走清除没有问题。
4. 按 `next_steps` 跑完，最后 `setup verify --space-id crypto`。
5. 等约 15 分钟后按 `fresh-deploy.md` 手工创建默认策略。第一批示例还带 `min_age_bars: 15`，太早启用会被拒绝。
6. 确认监控检查已恢复，`doctor alerts` 没有长期不消的告警。
7. 用户在自己的终端做一次浏览器信任。重装后 CA 是新的，旧证书要换掉。

验收标准：

- 配置模板不做额外修改就能采到 K 线。
- 全程没有 Agent 手工改数据。
- `setup verify` 全部通过，管理台能看到 K 线、因子和策略结果。
- 控制机有看护，杀掉一个组件后能被拉起。
- 记录每一步的耗时，作为第二批的基线。

### B4：`setup install`（清单 28）

新增 `modules/cli/internal/setup/installflow`，执行函数由 command 层注入，命令在 `command/setup_install.go`。

```bash
moox-cli setup install --space-id crypto
moox-cli setup install --space-id crypto --yes --wipe <预览摘要> [--accept-trade-risk] [--kill-outside]
```

- 不带 `--yes`：只读预检，输出路线、清除范围、防火墙、每台要下载的内容和预计耗时。
- 带 `--yes`：下载、清除（如需要）、防火墙同时进行 → 部署 → 初始化 → 启动 → 配置备份 → 验收。
- 中途失败可以直接重跑，用已有回执跳过完成的步骤。

准备阶段：

1. 预检：扫描主机，检查磁盘，每台实测下载源。下载源不通又没有本机推送的条件时，在动旧程序之前停下。
2. 用户授权后，同时启动下载、清除和防火墙。重装时总耗时取决于最慢的一项，首次安装没有清除。
3. 清除流程不变，和 `setup wipe` 共用：`VerifyUnchanged` → `MarkPending` → 并行清除 → 用 `LocalState{}` 确认 `fresh` → `ClearPending`。
4. 下载失败时按顺序换源、本机推送。这时旧程序可能已经删除，修好网络后重跑即可。这是用速度换来的代价：预检挡住常见失败，用户授权清除时已经接受旧部署不再保留。
5. 清除失败时不进入部署。下载到一半不用中断，已完成的文件重跑时不再下载。
6. 清除和下载都完成后运行 `checkAdminRoute`，由它执行 `ArchiveLocal`、`WriteBinding`。
7. 重跑时路线已是 `fresh` 或 `resume`，就忽略 `--wipe`。

下载脚本的进程是系统 `python3`，不在部署目录内，清除结束进程时不会碰到它。`clear(root)` 保留部署根本身，临时文件放在 `staging` 里。

改动：

- `deployscan.NextSteps` 改为返回结构化步骤（类型、主机、单元、依赖），`setup validate` 继续输出字符串。顺序只有这一个来源。
- 增加 SSH 连接池和共用的网关连接，每阶段只扫描一次，`checkInstallDisk` 合并到预检。清除后必须复查。
- 每步有总超时，维护锁排队没有上限。
- 输出逐行 JSON，Agent 后台运行后读取，只在结束或失败时汇报。

现有命令的副作用都要编排进去：

| 副作用 | 来源 |
| --- | --- |
| 全新安装的 `ArchiveLocal`、`WriteBinding` | `checkAdminRoute`。`ArchiveLocal` 会改名状态目录，下载记录不能先写在里面 |
| `MarkPending`、`ClearPending`、`wipe_trade_risk` | `setup wipe`。标记还在时 `Decide` 返回 `existing` |
| 只能出站主机的 `ensureRelayFirewall` | `setup deploy-host` |
| 看护安装后才 `MarkHostReady` | `setup deploy-host` |
| 控制机看护 | T13 |
| `MarkStep`、`config backup` | `setup init`、`config backup` |

`sync-deployments` 步骤去掉：`DeployUnit` 导出前已经同步。

分步命令保留用于修复。`skills/moox/references/install.md` 改成以 `setup install` 为主线。

测试：每个步骤后中断都能重跑完成；预检拒绝时不改任何东西；范围变化时拒绝清除。

- 公网证书：管理台只用内部证书。
- 回收目录和后台删除：实测删除很慢再加。
- Storage 改用单一二进制：只省约 2 秒，要改 23 处，还失去按进程名区分角色的能力。
- 只重跑失败的主机：清除脚本可重复执行，全部重跑更简单。
- 跨进程的下载进度文件。
- `admin` 阶段一次准备、DNS 异步、组件并行启动：收益小，第一批结束后看实测再定（清单 35、36）。
- 状态复制跳过空洞：缩小 Badger 预分配就够了。
- Storage 批量导入 RPC：分组并发够用。
- zstd、压缩二进制、云镜像。
- 原地升级到 v0.4.4 的状态迁移。
- A 股本地拉取。
