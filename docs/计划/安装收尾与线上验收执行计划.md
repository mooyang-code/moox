## 2. 原则

- 动线上之前必须有用户的明确确认。`setup wipe`、`--clean-functions`、`--kill-outside`、`--accept-trade-risk` 都要单独确认，上一次确认不能沿用。
- Agent 不读 `moox.toml`、状态目录和线上 `secrets/`、`identity/`，配置只用 `config get`。
- 遇到采集或计划问题，不删任务、不改数据库、不用维护者脚本，先看 `collector kline status` 和 `setup verify` 给出的原因。
- 验收发现代码问题时，先修复并发补丁版本，再继续验收。

## 3. 执行顺序

```text
阶段一 发布核对
  → 阶段二 README 和视频
  → 阶段三 文档、帮助文字、测试
  → 阶段四 计划偏差收口（发 v0.5.1）
  → 阶段五 线上重装（用户确认后）
  → 阶段六 第 8 节验收
  → 阶段七 收尾（第 13 版视频、README 耗时、记录）
```

阶段二、三可以并行。阶段四如果动了部署代码，要先发 v0.5.1，线上重装用新版本。

## 7. 阶段四：计划偏差收口

逐项定结论，要改代码的合并成一个 PR，发 v0.5.1。

| 偏差 | 影响 | 建议 |
| --- | --- | --- |
| `setup install` 多次扫描 | 多花几秒 | 不改，看实测，占比超过 10% 再优化 |
| `checkInstallDisk` 只合并了一部分 | 磁盘不够时，清除之后才报错 | **要改**：有旧部署时按清除后的可用空间在预检判断，空机在预检直接拒绝 |
| “空间不够先清除再下载”未实现 | 下载失败不致命，部署时会重下 | 不改，文档写明 |
| `staging` 保留规则 | 本机推送的目录没有 `.release`，不会被清理 | **要改**：`ensureArtifact` 推送后写 `.release` |
| 跨架构构建代码没删 | 只是死代码，源码路径才用得到 | 清理，删除 `host_software.go` 的跨架构分支、`unit.go` 对应逻辑和 `--arch` |

## 8. 阶段五：线上重装

每一步都在部署电脑上执行，开始前要用户确认。

### 确认项

1. 线上没有要保留的数据。
2. `moox.toml` 里的因子任务没有指向非默认数据集。
3. 启动的空间是 `crypto`。
4. 云函数要不要清理，单独决定，默认不清。
5. 是否有实盘账户。预检报 `live` 或 `unreadable` 时要用户再确认。

### 步骤

1. 下载 CLI 和产物包，校验 `SHA256SUMS`，把 `moox.toml` 放进产物包根目录。
2. 运行 `./bin/moox-cli config migrate --set-factors-enabled true --yes`，删除旧的 `tls_mode`。
3. 运行 `./bin/moox-cli setup install --space-id crypto`，把路线、清除范围和下载源可达情况告诉用户。
4. 用户确认后运行 `./bin/moox-cli setup install --space-id crypto --yes --wipe <预检摘要>`，后台运行，记录每个阶段的耗时。
5. 用户在自己的终端做一次浏览器信任。重装后 CA 是新的，旧证书要换掉。
6. 约 15 分钟后确认默认策略有第一个结果。
7. 运行 `doctor alerts`，确认监控恢复，没有长期不消的告警。

### 回退

重装是单向的，清除后不能回到旧部署。失败时修好后重跑同一条命令，已完成的步骤跳过。

## 9. 阶段六：验收

### 9.1 流程验收

| 场景 | 通过标准 | 动线上 |
| --- | --- | --- |
| 有旧部署 + 授权清除 | 全程没有手工改数据，`setup verify` 通过 | 是 |
| 全新安装 | 空机直接走完 | 是，需要先清空 |
| 断网回退 | 断开一台外网或改错下载地址，退回本机推送并装完 | 是 |
| 中途结束再重跑 | 结束 `setup install` 后重跑，能接着完成 | 是 |
| 连续安装 | 至少三次，全部成功 | 是 |

每次清除前都要用户单独确认。

### 9.2 发布后才能验证的项

| 项目 | 验证方法 | 通过标准 |
| --- | --- | --- |
| 真实下载 | 看 `download_finished` 事件和 `sources` 进度 | CNB 和 GitHub 都能下载，四台并行不互相影响 |
| 目标耗时 | 从 `setup install` 的进度算阶段耗时 | 服务就绪 2.5～3.5 分钟，首根 K 线 4.5～5.5 分钟，第一个策略结果约 15 分钟 |
| WS 订阅 | 看首份计划的生效周期和首根 K 线 | 500 多个标的能赶上 30 秒提前量，赶不上就调大提前量 |
| Monitor 告警 | 启用任务到计划生效这段时间看 `doctor alerts` | 不误报；误报就修 `kline_freshness` 的判断 |
| 控制机看护 | 杀掉一个组件 | 能被拉起 |
| 用户操作次数 | 全程记录 | 配置页一次、确认一次、装完信任一次 |

耗时达不到时，看阶段耗时找瓶颈，不为凑数字加复杂度。
