## 1. 范围与原则

**范围**

- Go 模块：
  - 改动：`admin`、`storage`（迁出外部接入）、`collector`、`factor`、`strategy`、`trade`、`cloudnode`、`archive`、`monitor`、
    `cli`、`eventbus`、`hostagent`；
  - 改名：`gateway` 改为 `hostgateway`；
  - 新增：`access`、`egressproxy`、`consoleproxy`。
- 共享包：
  - 新增：`packages/servicecatalog`、`packages/gatewayclient`；
  - 改名：`packages/gatewayproxy` 改为 `packages/gatewayroute`；
  - 调整：`packages/gatewayauth`、`packages/doctor`、`packages/cloudprovider/tencent`。
- 其他：前端 `web/src`；部署相关的 `scripts/deploy`、`scripts/build`、`scripts/lib`、`deploy/caddy`、`scripts/test/contract`；
  `skills/moox`；`docs`。
- 不在范围的内容见设计文档第 5 节。

**原则**

1. **前期只新增**：阶段 A 只新增包和新的协议文件，不删除、也不修改任何已有的公共接口。
2. **纯改名单独提交**：在同一个提交里改完所有引用，包括代码、`go.work`、构建与部署脚本、测试。
3. **换协议、迁调用方、删旧代码放进同一个提交**：
   - 一个服务换协议时，它的全部调用方在同一个提交里迁移；
   - 一个旧的公共接口，在它最后一个调用方完成迁移的那个提交里删除；
   - 新旧两版协议可以在分支上暂时并存，例如 SysDeploy v1 与 v2，但只用于让每个提交都能编译。旧版在最后一个调用方
     迁走时删除。
4. **每个提交都能编译、测试都能通过**：运行时的端到端联调放在阶段 C 的 e2e 测试和阶段 J。
5. **一次上线**：全部工作在 `feature/mooyang` 分支上完成。所有阶段验收通过后，按第 13 节一次性停机切换；在此之前，
   生产环境不部署任何中间版本。外置 Caddy 相关源码在分支联调完成后删除，最终产物重建并验收；线上旧发布包与证书状态
   单独归档，作为第 13 节的回滚材料。
6. **持续检查**：每个阶段结束时跑一遍第 15 节的检查。
7. **Storage 内部调用不变**：Storage 三个角色之间现有的直连调用（DataNode 等内部端口，各自使用角色密钥）保持原样。凡是
   现在经过网关的调用，都改为经过主机网关。
8. **编译位置按 CGO 依赖划分**：只有需要 CGO 的 Linux 目标在 Linux 编译机编译；纯 Go 目标在本机编译或交叉编译，前端也在本机构建。Linux 机器可以运行本机构建的测试和制品，运行验证不等于在远端编译。

### 2.5 配置

**`gatewayclient` 的三种使用方式**（对应设计文档 3.6）

内部组件，以 Collector 为例：

```yaml
gateway_client:
  caller: collector
  key_id: <Admin 分配的公开 KeyID>
  key_file: ../../secrets/caller-collector.key
```

内部组件由 `FileConfig.OpenInternal` 初始化：配置遵循 `<部署目录>/<模块>/config/app.yaml`，共享读取
`<部署目录>/host-gateway/config/app.yaml` 的主机 ID、loopback 地址与 CA，不重复指定网关目标。密钥路径相对模块配置文件；
目录缓存放入模块提供的数据目录下的 `gatewayclient/directory.json`。KeyID 根据 bootstrap 的公开凭据清单填写，
与 caller 独立；读取配置允许留空以支持离线命令，实际连接时必须完整。

外部调用方，以因子引擎的 `engine.yaml` 为例。没有目录，不需要 CA：

```yaml
gateway_client:
  caller: factor-engine
  key_id: <Admin 分配的公开 KeyID>
  key_file: ../secrets/access-factor-engine.key
  access_address: access.example.test:11004
  access_id: access@storage
```

外部进程用 `ExternalFileConfig.OpenExternal` 初始化；外部方式由构造入口确定，无需重复配置 `mode`。
`key_file` 相对实际配置文件解析，或使用绝对路径；签名文件校验复用内部方式的安全约束，缺失或无效即失败，
不会回退到环境凭据或本机主机网关。公开配置校验不打开私密文件，但外部调用必须填写完整 KeyID。

- SCF 不读配置文件，从环境变量 `MOOX_ACCESS_ADDRESS`、`MOOX_ACCESS_ID`、`MOOX_CALLER`、`MOOX_CALLER_KEY_ID`、`MOOX_CALLER_KEY` 取值。这些变量由
  Collector 经 CloudNode 写入。
- moox-cli 用隧道方式：SSH 连接信息取自 `moox.toml`，签名密钥放在 `~/.config/moox/caller-moox-cli.key`。同目录的 0600 `gateway-client.yaml` 记录 `caller: moox-cli`、Admin 分配的 `key_id` 和 `key_file: caller-moox-cli.key`；bootstrap 的 `operator/` 同时导出两个文件，由 G 阶段安装。

### 13.2 维护锁与暂停的做法

- 在每台主机上操作时，操作员在自己的会话里持有该主机的维护锁：
  `exec 9>/data/moox/<prod|storage>.maintenance.lock; flock -w 120 9`。
- 在持锁期间运行的安装器一律加上 `--maintenance-lock-held` 参数。
- 旧版本的 `healthcheck.sh` 不认识暂停标记，只会在维护锁被占用时跳过。所以在新脚本装好之前，必须一直持锁。
- 新脚本装好之后，暂停标记会持续生效，可以释放锁。

## 16. 顺序与依赖

```text
A（只新增的共享包）
├─► B（管理后台：v2 与 v1 并存；B8 同时修改前端服务名）
├─► C（主机网关）
└─► D1（已是 tRPC 的调用方迁移）
          │
B、C ─────┴─► D2（被调用方换协议，连同全部调用方）─► D3（删除旧公共接口）
                                                     │
                                                     ▼
              E（外部接入、出口代理、标的同步）─► F（Monitor，F4 同时提交监控告警页）
                                                     │
              H（H2 服务部署页，必须在 G4 之前合入）──┤
                                                     ▼
                                          G（部署工具；G4 删除 SysDeploy v1）
                                                     │
              I（文档与技能，贯穿全程，J 之前完成）───┤
                                                     ▼
                                          J（本地全链路验证）─► 第 13 节停机切换
```

几条硬性的顺序约束：
- B8 与前端服务名的修改放在同一个提交。
- F4 与监控告警页放在同一个提交。
- H2 必须在 G4 之前合入，因为 G4 会删除 SysDeploy v1。
- D3 在最后一个引用消失时执行。
- E2 必须同时切换外部接入和全部外部调用方。
- G7 按 Console Proxy 子计划推进；源码清理、最终包重建、J9/P7 验证、独立审查与修复回归全部完成后，才进入第 13 节。

## 17. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 一次性切换，改动范围大 | 先做阶段 J 的本地全链路验证；生产上逐台切换，每一步都验证；回滚有逐项清单（13.4 节） |
| 没有测试环境，部署脚本的问题只能在生产上暴露 | 用 G13 的渲染快照、G12 的契约测试、J2 的首次安装验收兜底；逐台切换；可以整体回滚 |
| 空环境或数据重置后无法完成初始化 | 用离线的 `bootstrap` 打破循环依赖，可以重复执行；J2 专门验收这个场景 |
| 误停用控制面后失去恢复入口 | 受保护组件和受保护主机不能停用；管理后台自己的服务走进程内调用；离线恢复命令（J3 验证） |
| 暂停期间服务被自动拉起，产生采集批次 | 暂停标记、`--maintenance-lock-held`，并在新脚本装好之前一直持锁；验收要求切换期间没有新批次 |
| SCF 分批发布中途失败 | 发布前用 `export-state` 记录状态；第二批失败时先重试，再回退第一批；采集保持暂停 |
| WAL 数据库的备份不一致 | 用 SQLite 备份接口导出，并做完整性校验，不直接复制 `.db` 文件 |
| 校验密钥随快照下发，有泄露的可能 | 只经 TLS 发给通过身份校验的主机网关；落盘文件权限为 0600 |
| 新旧协议在分支上并存，旧版删不干净 | 每个旧接口都有明确的删除提交（D3、G4）；旧称扫描兜底 |
| `deploy-moox.sh` 有 6000 多行，改动大 | 按 G11 的条目分步提交，每一步都跑契约测试 |
| 证书过期，或信任配置出错 | 证书由 MooX 私有 CA 签发；Admin 巡检到期时间；Monitor 探测每台主机网关 |
| 服务目录错误，调用发往错误的主机 | 目录带版本号；主机网关拒绝不属于本机的服务；客户端收到错误后立即刷新目录 |
| control 主机网关故障，其他主机拉不到快照 | 其他主机继续使用缓存的路由和密钥；Monitor 告警；网关控制恢复后自动重新同步 |
| 外部接入使用明文 | 只传输行情和因子数据；签名防篡改、防重放；密钥类接口不对外部调用方开放 |
| compute-1 或出口代理故障，Binance 标签停止更新 | 标签同步失败会上报并告警；周期规划和 SCF 采集都不受影响 |

## 18. 不做的事

- 设计文档第 5 节列出的内容。
- 不为旧接口、旧配置键、旧表、旧二进制名保留兼容层。新旧两版只在分支内暂时并存，只为保证每个提交都能编译。
- 运维机器上的 `moox.toml` 一次性迁移，CLI 不读取旧键。
- 属性同步不做持久化：错过的那一次要等到第二天执行，与现在相同。
