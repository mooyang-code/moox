# 数据归档设计

状态：设计稿 v2（2026-10-16），尚未编码。v2 按讨论改为：用户自行设定定时归档任务（执行计划与开始时间），
每次运行拉取每个序列最近 N 根，不同数据集的任务可以并发。实现后以[归档](../模块/归档.md)模块文档为准。

## 0. 设计原则

1. **永久保存，不追时效**：归档只保证线上数据在被保留策略删除之前落到本地，晚一两天可以接受。
2. **不影响采集**：执行计划和运行中的每个请求都避开整点和每分钟开头的写入高峰；并发和带宽都有上限。
   Storage 的 DataNode 读取没有并发保护，限流由归档自己承担。
3. **定时拉取，不订阅事件**：mgr 和 worker 都不订阅 EventBus，任何事件都不会触发归档。何时读由任务的执行计划决定，
   读多快由 worker 的节奏配置决定。
4. **窗口重叠代替复核**：每次拉最近 N 根，N 默认覆盖两个执行间隔，每根数据至少被读两次。
   第二次读时已经过了一个间隔，这期间补采写回的数据会被带上。
5. **本地只增不删**：同一行以最后一次从 Storage 读到的值为准；Storage 因保留期删掉的行在本地保留。
6. **部署目标可配置**：worker 只做出站连接，可以装在任何能访问 Access 的机器上；本次装在编译机。

## 1. 背景

### 1.1 现有实现

`modules/archive` 目前是事件驱动实现：消费 `rows.upserted`，先写本地 Journal，再按月物化为 Parquet，可选同步到 COS；
Storage 元数据中有 `t_archive_files` 及 `RegisterArchiveFile` / `ListArchiveFiles` 用于登记文件。该模块没有部署过，也没有页面。

本设计用定时拉取的实现**整体替换**它（项目不考虑历史兼容）。不保留事件式实现的原因：

- 事件式需要 7×24 小时在线消费，停机超过 JetStream 保留期就会丢数据，因此必须配套 Journal 和去重回执；
- 定时拉取天然幂等，运行失败下次再拉即可；唯一的约束是归档不能中断到线上保留期之外。

### 1.2 约束

| 约束 | 来源 | 对设计的影响 |
| --- | --- | --- |
| 完整历史只在 DataNode | View 每个序列只留最近 `view_bars`（5000）根 | 只能通过 `PrimaryStore.ReadTimeSeriesRows` 读取 |
| 「最近 N 根」一次只能查一个标的 | `latest_per_series` 要求恰好一个 selector，不能带时间范围和翻页，一次返回完整结果 | 每个标的一次请求；标的多的数据集请求次数多（见第 14 节） |
| PrimaryStore 路由超时 5 秒 | 服务目录 `timeout_ms: 5000` | N 设上限 10000，保证单次响应在超时内返回 |
| DataNode 读取代价高、无并发上限 | 每次读取约「行数 ×（列数 + 1）」次点查；2026-10-14 回填把 storage-node 打到 330% | 每个 DataNode 同时读取的任务数有上限，同一任务内串行 |
| 线上保留期短 | 生产保留策略：crypto 1m 保留 7 天，stockcn 1m 保留 45 天，按天桶清理 | 中断时间接近保留期时告警；超出保留期的缺口无法补齐 |
| SCF 写入集中在每分钟开头 | 收盘到批次写完 p50 9.0s、p99 22.5s（[SCF 定时触发采集改造设计](SCF定时触发采集改造设计.md)） | 每分钟第 0–25 秒不发起读取，执行计划的秒数也不能落在这段 |
| 编译机在内网，只能出站 | 与因子引擎相同 | 拆成控制机上的管理端和目标机器上的 worker |

## 2. 总体架构

参照 Factor 的「manager + engine」模式，`modules/archive` 产出两个程序：

| 程序 | 部署位置 | 职责 |
| --- | --- | --- |
| `moox-archive-mgr` | control（原生放置） | 保存任务、运行记录、文件登记和 worker 状态（SQLite）；按执行计划生成运行；`ArchiveMgr` 供控制台和 CLI 调用；`ArchiveWorker` 供 worker 领取运行、上报结果 |
| `moox-archive-worker` | 任意机器，只出站（本次为编译机） | 经 Access 领取运行、读取 Storage、合并写入本地 CSV，并上报进度、结果与心跳 |
| `moox-archive-cli` | 随 mgr / worker | `init`、`status`、`verify`（重新计算 sha256 并与登记值比对）、`reindex`（扫描归档目录，重建文件登记） |

```text
浏览器 ─► Console Proxy ─► Admin 管理网关 ─► archive-mgr（control）
                                              │  ArchiveMgr：任务、运行、文件
                                              │  ArchiveWorker：心跳、领取运行、上报
                                              │  按执行计划计算下次运行；回收过期租约
                                              ▲
                                              │ 出站 tRPC（签名，gzip）
archive-worker（编译机）──► Access 11004 ──────┤
   │  每 10 秒心跳；有空闲并发槽时领取到期的运行  └─► Storage Metadata / PrimaryStore（只读）
   ├─ 每个标的：ReadTimeSeriesRows(latest_per_series = N)，接不上时按时间区间补读
   ├─ 按 UTC 日 / 月与本地文件归并，写 .partial → fsync → rename
   └─ CompleteArchiveRun 上报文件登记与运行统计
```

不放进 Collector：归档会长时间读 Storage、写磁盘，worker 需要部署在磁盘大的机器上；拆开后 Collector 保持轻量，归档出问题不影响采集计划和补采。

## 3. 归档任务

一个归档任务对应一个时序数据集，以 `(space_id, dataset_id)` 标识。界面上按采集任务名选择；数据模型本身不限于采集结果，
因子结果数据集以后只需增加界面入口。

### 3.1 用户设置

| 设置 | 说明 | 默认 |
| --- | --- | --- |
| 数据集 | 采集任务的结果数据集，必须是已激活的时序数据集 | — |
| 执行计划 | 带秒的 6 段 cron 加时区；界面提供「每 N 小时」「每天」「每周」预设，也可直接写 cron | 按空间给出（见 3.3） |
| 开始时间 | 任务从这个时刻起按执行计划运行，之前的计划时刻不运行 | 创建时刻 |
| 每次拉取根数 N | 每个序列（标的 × series_tag）拉最近 N 根，范围 1–10000 | 推荐值见 3.2 |
| 回补起点（可选） | 首次运行时，从这个数据时间补读到最近 N 根之前，补齐历史；不早于「今天 − 线上保留期 + 1 天」 | 不回补，首次只拉最近 N 根 |
| 状态 | 启用 / 停用 | 启用 |

数据集的频率、分区粒度和所在 DataNode 由 mgr 从 Storage 读取，用户不填。

### 3.2 执行计划与 N 的校验

mgr 在创建和修改时校验，界面同时预览接下来 5 次运行时间：

- **避开写入高峰**：cron 的秒字段展开后都必须在 25–54 之间；分钟字段展开后不能包含 58、59、00、01、02、03。
  不满足时拒绝保存，并提示一个就近的合法时刻（如 `08:00:00` 提示改为 `08:04:43`）。
- **间隔不小于 1 小时**：相邻两次运行间隔小于 1 小时的计划拒绝保存。
- **N 的推荐值**：取两个执行间隔内的根数，按空间的交易时长取上界估算：
  - 间隔不到 1 天时，按自然时间计算：`2 × 间隔 / 频率`；
  - 间隔为 1 天及以上时，按每天的根数计算：`2 × 间隔天数 × 每天根数`。1m 的每天根数为 crypto 1440、stockcn 240、
    stockhk 330、stockus 390，其他频率按比例换算。
- **N 偏小时提示**：N 小于 1.2 倍间隔内根数时提示「窗口没有重叠，补采写回的数据可能带不上；断档靠补读接上」，但允许保存。

### 3.3 各空间的默认执行时刻（北京时间）

| 空间 | 默认计划 | 理由 |
| --- | --- | --- |
| crypto | 每天 08:04:43 | 美股已收盘，A 股和港股尚未开盘 |
| stockcn | 每天 17:04:43 | A 股 15:00 收盘，留出 2 小时给自动补采 |
| stockhk | 每天 17:34:43 | 港股 16:10 收盘之后 |
| stockus | 每天 06:04:43 | 美股收盘（北京时间 04:00 / 05:00）之后 |

例：stockcn 1m 每天 17:04:43 运行，N = 480，每次拉到当天和前一个交易日；当天的数据第二天还会再读一次。
crypto 1m 每天 08:04:43 运行，N = 2880，每次拉到过去两个 UTC 日。

## 4. 一次运行做什么

1. 读取数据集元数据（频率、列），调用 `ListHistorySubjects` 取该频率下有过数据的标的，按 `subject_id` 排序。
2. 对每个标的调用 `ReadTimeSeriesRows(latest_per_series = N)`，一次拿到它各个 `series_tag` 最近 N 根。
3. **接续检查**：worker 在本地记录每个序列上次归档到的最新时间 `last_time`。某个序列本次返回了满 N 根，而最早一根晚于
   `last_time`，说明中间可能有缺，就对这个标的按 `(last_time, 最早一根)` 区间补读（`time_range` + `after_key`，每页 2000 行）。
   - 补读区间的起点早于线上保留期截止时，截到截止处，被截掉的部分记为「无法补齐」并上报；
   - 首次运行时，填了回补起点的以它作为 `last_time`，没填的不补读；
   - 返回不足 N 根说明已是该序列的全部历史，不需要补读。
4. 一个标的处理完（含补读）再处理下一个：行按 UTC 日（`1d` 及以上为 UTC 月）分到当次运行的临时分区文件，
   因为标的有序、标的内按时间排序，临时文件天然按 `subject_id, data_time, series_tag` 有序。
5. 所有标的处理完后，逐个分区把临时文件与本地正式文件做流式归并：同键的行用本次读到的值覆盖，本地独有的行保留；
   写 `<文件>.partial`，fsync 后 rename，再 fsync 目录。内存只与单个标的的数据量有关。
6. 更新本地每个序列的 `last_time`，向 mgr 上报本次涉及的每个文件（行数、大小、sha256、列、数据时间范围、预览）和运行统计
   （请求数、读取字节、读取 / 新增 / 变更行数、补读标的数、无法补齐的区间）。

运行中途失败时丢弃临时文件、不更新 `last_time`，正式文件保持原样。下一次运行重新拉最近 N 根，接续检查会补上中间缺的部分，不会丢数据。

## 5. 节奏与并发

### 5.1 运行中的节奏（worker 配置 `pacing`，均可调）

| 规则 | 默认值 | 目的 |
| --- | --- | --- |
| 分钟内避让 | 只在每分钟第 25–55 秒**发起**请求 | SCF 收盘到写完 p99 22.5 秒 |
| 整点避让 | 每小时 :58 到下一小时 :04 之间不发起请求 | 1h K 线收盘、1h 因子计算等整点任务；同在编译机的因子引擎整点后集中读取，避免与它争用同一条公网链路和 Storage 出口带宽 |
| 请求间隔 | 同一运行的两次请求之间至少 200ms | |
| 带宽上限 | `max_bytes_per_second` 默认 512KB/s，所有并发运行共享一个令牌桶（按解压后的响应字节计，压缩后约 0.8 Mbps） | 无论并发多少、请求多快，读取速率都有硬上限 |
| 压缩 | `gateway_client.compression: gzip` | 经公网读取时减少带宽 |
| 磁盘保护 | 可用空间低于 `min_free_bytes`（默认 5GB）时不再领取运行，心跳上报 `disk_low` | 避免写满磁盘 |

运行开始的时刻由执行计划决定（3.2 已保证它不落在高峰），运行持续期间每个请求仍受上表约束。
worker 的避让依赖本机时钟，部署机器必须开启 NTP 同步。

### 5.2 并发

- **不同数据集的任务可以并发**：worker 最多同时执行 `max_concurrent_runs`（默认 4）个运行；
  同一个 DataNode 上同时最多 `max_runs_per_data_node`（默认 2）个。线上只有 `storage-node-0`，所以实际最多 2 个任务同时在读。
- **同一任务内串行**：一次只有一个请求在途；同一任务同时只有一个运行。
- **计划时刻到了但上一次还没结束**：本次计划时刻跳过，记一条 `skipped` 运行；下一次运行靠接续检查补上。
- **worker 离线期间错过的多个计划时刻**合并成一次运行，worker 恢复后立即执行。
- 不同任务写不同目录的文件，并发运行之间没有文件冲突。

## 6. 补写与断档

- **窗口内的补写**：每根数据在约 `N / 间隔内根数` 次运行中都会被读到，最后一次读到它时距离它产生已过了约一个间隔。
  这期间补采写回的数据会被自动带上。
- **窗口外的补写**（例如一周后手动补采了更早的日期）：不会自动带上。界面提供「补拉区间」，对指定时间区间做一次区间读取并归并，
  只要该区间仍在线上保留期内即可。
- **断档**：worker 停机或运行失败导致与上一次接不上时，下一次运行按第 4 节第 3 步对每个序列补读；
  超出线上保留期的部分无法补齐，记录在运行结果里并告警。
- **保留期告警**：任务最近一次成功运行距今超过「线上保留期 − 2 天」时，健康等级升为异常（见第 12 节），提示尽快恢复 worker。
- **局限**：Storage 中已存在的行后来被删除（如管理员删除数据集行）时，本地不会删除，符合永久归档的目的。

## 7. 文件格式与目录

```text
<root_dir>/<space_id>/<dataset_id>/<yyyy>/<dataset_id>_<yyyymmdd>.csv.gz   # 日分区（频率低于 1d）
<root_dir>/<space_id>/<dataset_id>/<yyyy>/<dataset_id>_<yyyymm>.csv.gz     # 月分区（1d 及以上）
<root_dir>/<space_id>/<dataset_id>/_dataset.json                          # 频率、列及类型；列变化时重写
<root_dir>/.state/<space_id>/<dataset_id>.json                            # 每个序列的 last_time
```

- 分区按 UTC 切分。UTC 日与各市场都对得上：A 股和港股交易时段在 UTC 01:30–08:00，美股在 13:30–21:00，币安日线以 UTC 0 点为界。
- 默认 gzip 压缩（worker 配置 `compression: gzip | none`），pandas 和 DuckDB 都能直接读取 `.csv.gz`。
- UTF-8，无 BOM，按 RFC 4180 转义。表头为 `data_time,subject_id,series_tag,<数据集列…>`；行上有 attributes 时，
  最后追加一列 `attributes`（JSON）。频率在数据集内唯一，不写成列。
- `data_time` 为 UTC RFC3339，纳秒为 0 时不输出小数部分（`2026-10-15T01:31:00Z`）；数值输出最短的可往返十进制，不用科学计数法；
  缺失字段输出空串。行按 `subject_id, data_time, series_tag` 排序。
- 数据集只增列。归并时以当前列为准写表头，旧行缺的列留空；文件的列登记在 `c_columns_json`，并同步写入 `_dataset.json`。
- `.state` 与归档文件放在同一目录树下，迁移机器时一起拷走。`.state` 丢失时，`reindex` 从各序列最新的文件中重建。
- 启动时清理残留的 `.partial` 和临时分区文件。

## 8. 管理端与 worker 的协作

- **心跳与 worker 租约**：worker 每 10 秒调用 `ArchiveWorkerHeartbeat`，上报 `worker_id`、进程实例 ID、版本、归档目录、
  磁盘总量与可用量、节奏与并发配置、正在执行的运行。同一时刻只有一个 worker 持有活动租约，旧 worker 停止心跳 45 秒后
  新 worker 才能接管；同一 `worker_id` 的两个进程同时运行时，后来者心跳返回冲突，不领取运行。
- **生成运行**：mgr 为每个启用的任务维护 `c_next_run_at`（开始时间之后执行计划的下一个时刻）。到期时生成一条 `queued` 运行，
  并推进 `c_next_run_at`；任务已有 `queued` / `running` 的运行时，本次记 `skipped`。手动的「立即运行」「补拉区间」同样生成 `queued` 运行。
- **领取**：worker 有空闲并发槽时调用 `PullArchiveRun`，带上已占用的 DataNode。mgr 在一个事务中按计划时刻从早到晚，
  选出不超过 DataNode 并发上限的运行，写入运行租约（默认 10 分钟）后返回任务参数（数据集、频率、列、N、区间、回补起点）。
- **进度**：运行中每 30 秒调用 `ReportArchiveRunProgress`，续租并上报已处理的标的数、请求数和读取字节。
- **完成**：`CompleteArchiveRun` 上报运行统计和本次写入的文件；mgr 在一个事务中更新运行状态、文件登记，以及任务的最近成功时间。
- **租约过期**：mgr 的维护定时器（每分钟）把租约过期的运行标为 `failed`（原因「worker 失联」）；下一次运行靠接续检查补上。
  维护定时器同时每小时调用 `Metadata.GetDataset` 刷新各任务的保留期和 DataNode，并清理 90 天前的运行记录。
- **更换机器**：文件只存在于写它的 worker 上，文件登记记录 `c_worker_id`。换机器时，把归档目录（含 `.state`）整体拷到新机器，
  并沿用同一个 `worker_id`（配置项，默认 `archive-worker@<主机名>`），即可无缝接续。
  如果新机器换了 `worker_id`，界面标出旧文件的存放位置，新运行写到新机器上。

## 9. 表结构

mgr 的 SQLite：`modules/archive/schema/archive.sql`，库文件 `data/archive-mgr/archive.db`。Storage 元数据中不再登记归档文件。

```sql
-- 归档任务：一个时序数据集最多一个任务；频率与分区粒度创建时从数据集固化，保留期与 DataNode 由维护定时器刷新
CREATE TABLE IF NOT EXISTS t_archive_tasks (
    c_id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    c_space_id TEXT NOT NULL,
    c_dataset_id TEXT NOT NULL,
    c_freq TEXT NOT NULL,
    c_partition_unit TEXT NOT NULL,
    c_data_node_id TEXT NOT NULL DEFAULT '',
    c_retention TEXT NOT NULL DEFAULT '',
    c_schedule_cron TEXT NOT NULL,
    c_schedule_tz TEXT NOT NULL DEFAULT 'Asia/Shanghai',
    c_start_at DATETIME NOT NULL,
    c_latest_bars INTEGER NOT NULL,
    c_backfill_from DATETIME,
    c_status TEXT NOT NULL DEFAULT 'enabled',
    c_next_run_at DATETIME,
    c_last_success_at DATETIME,
    c_creator TEXT NOT NULL DEFAULT '',
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_partition_unit IN ('day', 'month')),
    CHECK (c_latest_bars BETWEEN 1 AND 10000),
    CHECK (c_status IN ('enabled', 'paused')),
    UNIQUE (c_space_id, c_dataset_id)
);

CREATE INDEX IF NOT EXISTS idx_t_archive_tasks_due ON t_archive_tasks (c_status, c_next_run_at);

CREATE TRIGGER IF NOT EXISTS trg_t_archive_tasks_mtime
AFTER UPDATE ON t_archive_tasks
FOR EACH ROW
WHEN NEW.c_mtime = OLD.c_mtime
BEGIN
    UPDATE t_archive_tasks SET c_mtime = CURRENT_TIMESTAMP WHERE c_id = OLD.c_id;
END;

-- 归档运行：一次定时、手动或补拉区间的执行；running 期间由租约标识持有的 worker，保留 90 天
CREATE TABLE IF NOT EXISTS t_archive_runs (
    c_id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    c_run_id TEXT NOT NULL,
    c_space_id TEXT NOT NULL,
    c_dataset_id TEXT NOT NULL,
    c_kind TEXT NOT NULL DEFAULT 'scheduled',
    c_range_start DATETIME,
    c_range_end DATETIME,
    c_status TEXT NOT NULL DEFAULT 'queued',
    c_scheduled_at DATETIME NOT NULL,
    c_started_at DATETIME,
    c_finished_at DATETIME,
    c_worker_id TEXT NOT NULL DEFAULT '',
    c_lease_token TEXT NOT NULL DEFAULT '',
    c_lease_until DATETIME,
    c_subjects_total INTEGER NOT NULL DEFAULT 0,
    c_subjects_done INTEGER NOT NULL DEFAULT 0,
    c_catchup_subjects INTEGER NOT NULL DEFAULT 0,
    c_request_count INTEGER NOT NULL DEFAULT 0,
    c_bytes_read INTEGER NOT NULL DEFAULT 0,
    c_rows_read INTEGER NOT NULL DEFAULT 0,
    c_rows_added INTEGER NOT NULL DEFAULT 0,
    c_rows_changed INTEGER NOT NULL DEFAULT 0,
    c_unrecoverable_json TEXT NOT NULL DEFAULT '[]',
    c_message TEXT NOT NULL DEFAULT '',
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_kind IN ('scheduled', 'manual', 'range')),
    CHECK (c_status IN ('queued', 'running', 'succeeded', 'failed', 'skipped', 'canceled')),
    CHECK (c_kind != 'range' OR (c_range_start IS NOT NULL AND c_range_end IS NOT NULL)),
    FOREIGN KEY (c_space_id, c_dataset_id) REFERENCES t_archive_tasks (c_space_id, c_dataset_id) ON DELETE CASCADE,
    UNIQUE (c_run_id)
);

CREATE INDEX IF NOT EXISTS idx_t_archive_runs_task ON t_archive_runs (c_space_id, c_dataset_id, c_scheduled_at);
CREATE INDEX IF NOT EXISTS idx_t_archive_runs_active
ON t_archive_runs (c_status, c_scheduled_at)
WHERE c_status IN ('queued', 'running');
CREATE INDEX IF NOT EXISTS idx_t_archive_runs_retention ON t_archive_runs (c_finished_at);

CREATE TRIGGER IF NOT EXISTS trg_t_archive_runs_mtime
AFTER UPDATE ON t_archive_runs
FOR EACH ROW
WHEN NEW.c_mtime = OLD.c_mtime
BEGIN
    UPDATE t_archive_runs SET c_mtime = CURRENT_TIMESTAMP WHERE c_id = OLD.c_id;
END;

-- 归档文件：每个任务每个 UTC 日（1d 及以上为 UTC 月）一个文件，由运行归并写入；c_worker_id 是文件所在的 worker
CREATE TABLE IF NOT EXISTS t_archive_files (
    c_id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    c_space_id TEXT NOT NULL,
    c_dataset_id TEXT NOT NULL,
    c_partition_key TEXT NOT NULL,
    c_range_start DATETIME NOT NULL,
    c_range_end DATETIME NOT NULL,
    c_worker_id TEXT NOT NULL,
    c_file_path TEXT NOT NULL,
    c_file_bytes INTEGER NOT NULL DEFAULT 0,
    c_file_sha256 TEXT NOT NULL DEFAULT '',
    c_row_count INTEGER NOT NULL DEFAULT 0,

    c_min_data_time DATETIME,
    c_max_data_time DATETIME,

    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_file_bytes >= 0),
    CHECK (c_row_count >= 0),
    CHECK (c_subject_count >= 0),
    CHECK (c_write_count >= 0),
    FOREIGN KEY (c_space_id, c_dataset_id) REFERENCES t_archive_tasks (c_space_id, c_dataset_id),
    UNIQUE (c_space_id, c_dataset_id, c_partition_key)
);

CREATE INDEX IF NOT EXISTS idx_t_archive_files_worker ON t_archive_files (c_worker_id);

CREATE TRIGGER IF NOT EXISTS trg_t_archive_files_mtime
AFTER UPDATE ON t_archive_files
FOR EACH ROW
WHEN NEW.c_mtime = OLD.c_mtime
BEGIN
    UPDATE t_archive_files SET c_mtime = CURRENT_TIMESTAMP WHERE c_id = OLD.c_id;
END;

-- 归档 worker：同一时刻只有一个 worker 持有活动租约（c_lease_until 未过期）；心跳刷新磁盘与正在执行的运行
CREATE TABLE IF NOT EXISTS t_archive_workers (
    c_id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    c_worker_id TEXT NOT NULL,
    c_instance_id TEXT NOT NULL DEFAULT '',
    c_version TEXT NOT NULL DEFAULT '',
    c_root_dir TEXT NOT NULL DEFAULT '',
    c_disk_total_bytes INTEGER NOT NULL DEFAULT 0,
    c_disk_free_bytes INTEGER NOT NULL DEFAULT 0,
    c_pacing_json TEXT NOT NULL DEFAULT '{}',
    c_running_json TEXT NOT NULL DEFAULT '[]',
    c_lease_until DATETIME,
    c_last_heartbeat_at DATETIME,
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_disk_total_bytes >= 0),
    CHECK (c_disk_free_bytes >= 0),
    UNIQUE (c_worker_id)
);

CREATE TRIGGER IF NOT EXISTS trg_t_archive_workers_mtime
AFTER UPDATE ON t_archive_workers
FOR EACH ROW
WHEN NEW.c_mtime = OLD.c_mtime
BEGIN
    UPDATE t_archive_workers SET c_mtime = CURRENT_TIMESTAMP WHERE c_id = OLD.c_id;
END;
```

说明：

- `t_archive_files` 引用任务时不级联删除：已有文件的任务不能删除，只能停用；永久归档不提供删除文件的入口。
- `c_preview` 是表头加前 20 行（不超过 8KB），由 worker 上报。文件在 worker 机器上，控制台无法直接读取。
- `c_unrecoverable_json` 记录超出线上保留期、无法补齐的区间（按序列合并后最多 200 组）。
- mgr 的库丢失时，用 worker 机器上的 `moox-archive-cli reindex` 扫描归档目录重新上报文件登记，已有文件不受影响；任务需要重新创建。

## 10. 接口

### 10.1 `trpc.moox.archive.ArchiveMgr`（mgr，端口 11406）

`console_name: archive`，浏览器路径 `/api/admin/archive/<方法>`；调用方 `console`、`moox-cli`；按请求头注入的 `space_id` 限定范围。

| 方法 | 说明 |
| --- | --- |
| `GetArchiveOverview` | 活动 worker（ID、版本、归档目录、磁盘用量、最后心跳）、节奏与并发配置、正在执行的运行与进度、告警汇总 |
| `ListArchiveTasks` | 当前空间的任务和汇总：执行计划、N、上次运行与结果、下次运行、已归档的数据时间范围、文件数、总行数与字节、健康等级 |
| `PrepareArchiveTask` | 给定数据集，返回频率、分区粒度、线上保留期、最早回补起点、所在 DataNode、推荐的执行计划和 N，以及是否已有任务 |
| `PreviewArchiveSchedule` | 校验执行计划、开始时间和 N，返回接下来 5 次运行时间、校验错误与提示 |
| `CreateArchiveTask` / `UpdateArchiveTask` | 创建、修改任务（执行计划、开始时间、N、回补起点、启停）；保存前按 3.2 校验 |
| `DeleteArchiveTask` | 仅当任务没有文件时允许 |
| `RunArchiveTaskNow` | 立即生成一次运行；运行中仍受避让和带宽限制 |
| `BackfillArchiveRange` | 对指定数据时间区间生成一次补拉运行；区间不能早于线上保留期截止 |
| `CancelArchiveRun` | 取消排队中或运行中的运行；运行中的在下一个请求前停止，丢弃临时文件 |
| `ListArchiveRuns` / `GetArchiveRun` | 运行记录与详情（含无法补齐的区间） |
| `ListArchiveFiles` / `GetArchiveFile` | 按月份列出文件；详情含位置、大小、sha256、行数、标的数、数据时间范围、列、预览、写入次数 |

只读方法：`GetArchiveOverview`、`ListArchiveTasks`、`PrepareArchiveTask`、`PreviewArchiveSchedule`、`ListArchiveRuns`、
`GetArchiveRun`、`ListArchiveFiles`、`GetArchiveFile`。

### 10.2 `trpc.moox.archive.ArchiveWorker`（mgr，端口 11408）

`acl: []`，只经 Access 对外部身份 `archive-worker` 开放（与 `FactorEngine` 一样）。

| 方法 | 说明 |
| --- | --- |
| `ArchiveWorkerHeartbeat` | 心跳与 worker 租约；返回是否为活动 worker，以及需要取消的运行 |
| `PullArchiveRun` | 按空闲并发槽和已占用的 DataNode 领取运行（无可领取时返回空） |
| `ReportArchiveRunProgress` | 续租并上报进度 |
| `CompleteArchiveRun` | 上报运行结果与文件登记 |

### 10.3 Access 白名单与 Storage 调用

新增外部身份 `archive-worker`：

| 服务 | 方法 |
| --- | --- |
| `trpc.moox.storage.PrimaryStore` | `ReadTimeSeriesRows`、`ListHistorySubjects` |
| `trpc.moox.storage.Metadata` | `GetDataset`、`ListDatasetColumns` |
| `trpc.moox.archive.ArchiveWorker` | 全部四个方法 |

- worker 只配置固定的 Access（`access_address` + `access_id`），不使用主机网关配置；Storage 请求体的角色认证与因子引擎相同
  （`storage-primary-auth.secret`），写权限由 Access 白名单拦住，worker 只能调用读方法。
- mgr 以内部身份 `archive-mgr` 经 `gatewayclient` 调用 `Metadata.GetDataset`，读取频率、保留期、DataNode 和激活状态。
- 补读和补拉区间使用 `time_range` + `after_key` 翻页的单标的读取；落地时补一个用例确认该组合的翻页语义。

- **mgr**：加入 control 的原生放置（`[placements] control = [..., "archive-mgr"]`），随 control 单元安装；

## 14. 容量与耗时估算

按以下规模估算，仅用于判断量级：stockcn 1m 约 5000 个标的，crypto 1m 约 500 个；Access 往返每次约 0.4 秒。

| 项 | crypto 1m（每天，N = 2880） | stockcn 1m（每天，N = 480） |
| --- | --- | --- |
| 每次请求数 | 约 500 | 约 5000 |
| 每次读取行数 | 约 144 万 | 约 240 万 |
| 每次耗时 | 约 20 分钟（受 512KB/s 带宽上限约束） | 约 2 小时（受请求次数约束，17:04 开始，19:00 前后结束） |
| 每次下行流量（gzip 后） | 约 60MB | 约 100MB |
| 每年磁盘（gzip 后） | 约 5GB | 约 5GB |

- 窗口重叠使每根数据读两次，读取量是「只读新数据」的两倍，换来不需要复核。
- stockcn 这类标的多的数据集受「一次一个标的」限制。实测耗时不可接受时，可以扩展 Storage 让 `latest_per_series` 接受多个 selector
  （DataNode 按 selector 逐个执行即可），每批 50 个标的可把请求数降到约 100 次；这需要单独发布 Storage，不在第一阶段做。
- 新建任务填回补起点时，首次运行按区间补读：stockcn 1m 补 45 天（约 31 个交易日）约 3700 万行、约 2 万次请求，
  下行约 7GB（解压后），受带宽上限约束约 10 小时完成；补读期间该任务后续的计划时刻记为跳过。

## 17. 已确认与待确认

已确认：

- 定时拉取，整体替换现有事件式 archive 模块；不订阅 EventBus；
- 用户为每个数据集设定定时归档任务（执行计划、开始时间），每次拉每个序列最近 N 根；不同数据集的任务可以并发；
- worker 的部署目标可配置，本次与编译机同机；
- 文件为 gzip 压缩的 CSV，按 UTC 日 / 月分区，本地只增不删；
- 界面入口先只提供采集结果，数据模型按数据集设计。
