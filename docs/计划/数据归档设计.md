# 数据归档设计

状态：设计稿 v1（2026-10-16），已与用户讨论确认方向，尚未编码。实现后以[归档](../模块/归档.md)模块文档为准。

## 0. 设计原则

1. **永久保存，不追时效**：归档只保证线上数据在被保留策略删除之前落到本地，不追求实时，晚一两天可以接受。
2. **不影响采集**：避开整点和每分钟开头的写入高峰，单并发、限速读取。Storage 的 DataNode 读取没有并发保护，限流由归档自己承担。
3. **定时拉取、可重跑**：按分区从 Storage 拉取，同一分区重跑结果逐字节一致；不依赖事件流，停机后补跑即可。
4. **部署目标可配置**：worker 只做出站连接，可以装在任何能访问 Access 的机器上；本次装在编译机。
5. **简单优先**：一个分区一个文件，不建文件表，不做多副本，不在线迁移。

## 1. 背景

### 1.1 现有实现

`modules/archive` 目前是事件驱动实现：消费 `rows.upserted`，先写本地 Journal，再按月物化为 Parquet，可选同步到 COS；
Storage 元数据中有 `t_archive_files` 及 `RegisterArchiveFile` / `ListArchiveFiles` 用于登记文件。该模块没有部署过，也没有页面。

本设计用拉取式实现**整体替换**它（项目不考虑历史兼容）。不保留事件式实现的原因：

- 事件式需要 7×24 小时在线消费，停机超过 JetStream 保留期就会丢数据，因此必须配套 Journal 和去重回执；
- 拉取式天然幂等，任何一天都能重跑，补采写回的数据重跑时自然带上；唯一的约束是归档进度不能落后到保留期之外。

### 1.2 约束

| 约束 | 来源 | 对设计的影响 |
| --- | --- | --- |
| 完整历史只在 DataNode | View 每个序列只留最近 `view_bars`（5000）根 | 只能通过 `PrimaryStore.ReadTimeSeriesRows` 读取 |
| DataNode 读取代价高、无并发上限 | 每次读取约「行数 ×（列数 + 1）」次点查；2026-10-14 回填把 storage-node 打到 330% | 归档单并发、限速，避开写入高峰 |
| 线上保留期短 | 生产保留策略：crypto 1m 保留 7 天，stockcn 1m 保留 45 天，按天桶清理 | 临近删除的分区优先归档并告警，超过保留期的标为过期 |
| SCF 写入集中在每分钟开头 | 收盘到批次写完 p50 9.0s、p99 22.5s（[SCF 定时触发采集改造设计](SCF定时触发采集改造设计.md)） | 每分钟第 0–25 秒不发起读取 |
| 编译机在内网，只能出站 | 与因子引擎相同 | 拆成控制机上的管理端和目标机器上的 worker |

## 2. 总体架构

参照 Factor 的「manager + engine」模式，`modules/archive` 产出两个程序：

| 程序 | 部署位置 | 职责 |
| --- | --- | --- |
| `moox-archive-mgr` | control（原生放置） | 保存任务、分区、执行记录和 worker 状态（SQLite）；`ArchiveMgr` 供控制台和 CLI 调用；`ArchiveWorker` 供 worker 领取工作、上报结果；规划定时器 |
| `moox-archive-worker` | 任意机器，只出站（本次为编译机） | 经 Access 领取分区、读取 Storage、写本地 CSV、复核，并上报结果与心跳 |
| `moox-archive-cli` | 随 mgr / worker | `init`、`status`、`verify`（重新计算 sha256 并与登记值比对）、`reindex`（扫描归档目录，重建分区登记） |

```text
浏览器 ─► Console Proxy ─► Admin 管理网关 ─► archive-mgr（control）
                                              │  ArchiveMgr：任务、分区、记录
                                              │  ArchiveWorker：心跳、领取、上报
                                              │  plan.timer：补分区、判过期、回收租约
                                              ▲
                                              │ 出站 tRPC（签名，gzip）
archive-worker（编译机）──► Access 11004 ──────┤
   │  tick.timer（每 10 分钟，xx:04:43 起）      └─► Storage Metadata / PrimaryStore（只读）
   ├─ PullArchiveWork 领取一个分区
   ├─ ListHistorySubjects → 分批 ReadTimeSeriesRows（after_key 游标）
   ├─ 写 .partial → fsync → rename
   └─ CompleteArchiveWork 上报文件信息
```

不放进 Collector：归档会长时间读 Storage、写磁盘，worker 需要部署在磁盘大的机器上；拆开后 Collector 保持轻量，归档出问题不影响采集计划和补采。

## 3. 归档对象与分区

- **一个归档任务对应一个时序数据集**，以 `(space_id, dataset_id)` 标识。采集是「一个任务一个结果数据集」，界面上按采集任务名选择。
  数据模型本身不限于采集结果，因子结果数据集以后只需增加界面入口。
- **分区按 UTC 切分**：频率低于 `1d` 按 UTC 日，`1d` 及以上按 UTC 月。UTC 日与各市场都对得上：
  A 股和港股交易时段在 UTC 01:30–08:00，美股在 13:30–21:00，币安日线以 UTC 0 点为界。
- **一个分区一个文件**。分区键：日分区 `2026-10-15`，月分区 `2026-10`。
- 任务的起始日期不能早于「今天 − 线上保留期 + 1 天」；月分区的起始日期向下取整到月初。

## 4. 文件格式与目录

```text
<root_dir>/<space_id>/<dataset_id>/<yyyy>/<dataset_id>_<yyyymmdd>.csv.gz   # 日分区
<root_dir>/<space_id>/<dataset_id>/<yyyy>/<dataset_id>_<yyyymm>.csv.gz     # 月分区
<root_dir>/<space_id>/<dataset_id>/_dataset.json                          # 频率、列及类型；列变化时重写
```

- 默认 gzip 压缩（worker 配置 `compression: gzip | none`）。pandas 和 DuckDB 都能直接读取 `.csv.gz`。
- UTF-8，无 BOM，按 RFC 4180 转义。
- 表头为 `data_time,subject_id,series_tag,<数据集列…>`；行上有 attributes 时，最后追加一列 `attributes`（JSON）。
  频率在数据集内唯一，不写成列。
- `data_time` 为 UTC RFC3339，纳秒为 0 时不输出小数部分（`2026-10-15T01:31:00Z`）；数值输出最短的可往返十进制，不用科学计数法；
  缺失字段输出空串。
- 行按 `subject_id, data_time, series_tag` 排序：worker 先对标的排序后分批读取，批内在内存中排序，整个文件因此有序。
  同一分区的数据不变时，重跑产出的文件逐字节相同。
- 数据集只增列：每个文件用写入时的列，表头可能随日期变化；文件的列记录在分区的 `c_columns_json` 中，并同步写入 `_dataset.json`。
- 写入流程：写 `<文件>.partial`，fsync 后 rename 为正式文件，再 fsync 目录，最后上报 mgr。中途崩溃时 `.partial` 在启动时清理，分区按租约过期重做。

## 5. 调度与避让

### 5.1 节奏（worker 配置 `pacing`，均可调）

| 规则 | 默认值 | 目的 |
| --- | --- | --- |
| tick 定时器 | cron `43 4-59/10 * * * *`（xx:04:43、xx:14:43…xx:54:43），`timerjob` 防重叠 | 启动时刻避开整点、整 5 分（SCF 触发）和 Collector 自动补采的 x2:30 / x7:30 槽 |
| 领取窗口 | 每次 tick 只在前 8 分钟内领取新分区；已领取的分区做完为止（单分区上限 50 分钟，超时按失败重试） | 一次只占用一段时间 |
| 分钟内避让 | 只在每分钟第 25–55 秒**发起**请求 | SCF 收盘到写完 p99 22.5 秒 |
| 整点避让 | 每小时 :58 到下一小时 :04 之间不发起请求 | 1h K 线收盘、1h 因子计算等整点任务 |
| 并发与分页 | 单并发；每批 50 个标的，每页 2000 行（`after_key` 游标）；请求间隔至少 200ms | 把 DataNode 的负载限在一个请求以内 |
| 压缩 | `gateway_client.compression: gzip` | 经公网读取时减少带宽 |
| 磁盘保护 | 可用空间低于 `min_free_bytes`（默认 5GB）时停止领取，心跳上报 `disk_low` | 避免写满磁盘 |

worker 的避让依赖本机时钟，部署机器必须开启 NTP 同步。

### 5.2 分区何时到期

分区在 `range_end + 等待时长` 之后才可归档，等待时长默认 24 小时（任务级可调）：

- 给自动补采留出时间，把实时漏采的 K 线补上（自动补采按水位追赶，落后超过 1 小时会告警）；
- 等待时长取整天时，各分区都在 UTC 00:04 前后到期：第 D 天在 D+2 的 UTC 00:04（北京时间 08:04）开始归档，
  此时美股已收盘，A 股和港股尚未开盘，是股票市场最空闲的时段；
- 对 crypto 1m 的 7 天保留期仍有 5 天余量。

考虑过「等 Collector 自动巡检水位越过分区末尾再归档」，这样更准确，但要依赖 Collector 在线。有了第 6 节的复核就不需要这层耦合。

### 5.3 领取优先级

1. **临近删除**：分区起点距离线上删除不足 2 天（见 5.4）；
2. **待复核**；
3. 其余按到期时间从旧到新。

失败后从 10 分钟起指数退避，上限 6 小时，不限次数，直到分区超出保留期被标为 `expired`。

### 5.4 保留期判断

Storage 清理时 `cutoff = now − 保留期`，按天桶截断，早于 `floor_day(cutoff)` 的天桶被删除。据此，对分区起点 `range_start`：

- **已过期**：`range_start < floor_day(now − 保留期)`，Storage 可能已删除部分数据，不再首次归档，也不允许重新归档；
- **临近删除**：`range_start < floor_day(now − 保留期) + 2 天`；
- 保留期为 `forever` 时两者都不成立。

保留期由 mgr 的规划定时器通过 `Metadata.GetDataset` 读取（`retention` 字段），缓存在任务行中。

## 6. 补写与复核

归档之后，补采（手动补采、历史缺口补采确认、`force` 重拉）仍可能写回已归档的日期。

- **每天复核一次**：mgr 把到期的复核分派给持有该文件的 worker。worker 调 `CountTimeSeriesRows`（每批 500 个标的，只返回计数），
  与本地文件中每个标的的去重时间点数比对（同一时间点有多个 `series_tag` 只计一次，与该接口口径一致）。
  **只有 Storage 比文件多时才重新归档**；Storage 比文件少（View 已裁掉旧数据）不算差异。
- **只在 View 覆盖期内复核**：计数由 View 回答，View 每个序列只留最近 `view_bars` 根。mgr 以 `view_bars × 频率` 作为保守的覆盖期
  （crypto 1m 约 3.4 天），分区起点超出覆盖期后不再复核，文件定稿。默认配置下，各频率的覆盖期都短于保留期。
  交易时段市场的实际覆盖期更长（stockcn 1m 约 20 个交易日），按保守值计算只会少做几次复核。
- **重新归档不减行**：新文件行数少于旧文件时，放弃新文件、保留旧文件，记一条 `rejected` 并告警。
  已过期的分区不允许重新归档。
- **局限**：值被改写但行数不变时，复核发现不了。K 线收盘后基本不再变化，可以接受；需要时在界面上手动「重新归档区间」。

## 7. 管理端与 worker 的协作

- **心跳与 worker 租约**：worker 每 10 秒调用 `ArchiveWorkerHeartbeat`，上报 `worker_id`、进程实例 ID、版本、归档目录、
  磁盘总量与可用量、节奏配置和当前进度。同一时刻只有一个 worker 持有活动租约，旧 worker 停止心跳 45 秒后新 worker 才能接管；
  同一 `worker_id` 的两个进程同时运行时，后来者心跳返回冲突、不领取工作。
- **领取**：`PullArchiveWork` 在一个事务中按 5.3 的优先级选出一个分区，写入分区租约（`c_lease_*`，默认 15 分钟），
  返回分区范围、动作（归档 / 复核）和旧文件行数（用于不减行判断）。复核只分派给 `c_worker_id` 与请求方相同的分区。
- **进度**：处理中每 30 秒调用 `ReportArchiveProgress`，续租并上报已处理的标的数和行数。
- **完成**：`CompleteArchiveWork` 上报结果：归档成功（文件路径、字节数、sha256、行数、标的数、列、前 20 行预览）、
  复核结论（一致 / 不一致及差异标的数）、`rejected` 或失败原因。mgr 更新分区并写一条执行记录。
- **租约过期**：mgr 规划定时器把租约过期的分区退回，计一次失败并退避，worker 本地的 `.partial` 在下次启动或重做时清理。
- **更换机器**：文件只存在于写它的 worker 上，分区记录 `c_worker_id`。换机器时，把归档目录整体拷到新机器，并沿用同一个 `worker_id`
  （配置项，默认 `archive-worker@<主机名>`），即可无缝接续。如果新机器换了 `worker_id`，旧机器上的分区不再复核，界面标出存放位置；
  需要时对这些分区手动重新归档，它们会改写到新 worker 上（仍受保留期限制）。

## 8. 表结构

mgr 的 SQLite：`modules/archive/schema/archive.sql`，库文件 `data/archive-mgr/archive.db`。Storage 元数据中不再登记归档文件。

分区的调度用两组字段描述：`c_status` 表示文件状态，`c_next_action` / `c_next_action_at` 表示下一步要做什么、何时可做；
是否正在执行看租约是否有效。

| 事件 | 分区变化 |
| --- | --- |
| 规划生成 | `pending`，`archive`，`range_end + 等待时长` |
| 归档成功 | `archived`，文件字段更新，`c_attempts = 0`；还在覆盖期内时为 `verify`，`now + 1 天`，否则 `none` |
| 归档失败 | 状态不变，`c_attempts + 1`，到期时间按退避推后 |
| 复核一致 | 更新 `c_verified_at`；还在覆盖期内时 `now + 1 天` 再次复核，否则 `none` |
| 复核不一致 | `archive`，`now`（重新归档） |
| 重新归档被拒 | 保留旧文件，`none`，`c_last_error` 记录原因 |
| 手动重新归档 | `archive`，`now`（已过期的拒绝） |
| 超出保留期 | 未归档的 `pending` 变为 `expired`；已归档但待重新归档的改为 `none` |

```sql
-- 归档任务：一个时序数据集最多一个任务；频率与分区粒度创建时从数据集固化，保留期由规划定时器刷新
CREATE TABLE IF NOT EXISTS t_archive_tasks (
    c_id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    c_space_id TEXT NOT NULL,
    c_dataset_id TEXT NOT NULL,
    c_freq TEXT NOT NULL,
    c_partition_unit TEXT NOT NULL,
    c_start_date TEXT NOT NULL,
    c_settle_seconds INTEGER NOT NULL DEFAULT 86400,
    c_retention TEXT NOT NULL DEFAULT '',
    c_status TEXT NOT NULL DEFAULT 'enabled',
    c_creator TEXT NOT NULL DEFAULT '',
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_partition_unit IN ('day', 'month')),
    CHECK (c_settle_seconds >= 0),
    CHECK (c_status IN ('enabled', 'paused')),
    UNIQUE (c_space_id, c_dataset_id)
);

CREATE TRIGGER IF NOT EXISTS trg_t_archive_tasks_mtime
AFTER UPDATE ON t_archive_tasks
FOR EACH ROW
WHEN NEW.c_mtime = OLD.c_mtime
BEGIN
    UPDATE t_archive_tasks SET c_mtime = CURRENT_TIMESTAMP WHERE c_id = OLD.c_id;
END;

-- 归档分区：一个分区一个文件；c_worker_id 是文件所在的 worker，c_lease_* 是正在执行的租约
CREATE TABLE IF NOT EXISTS t_archive_partitions (
    c_id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    c_space_id TEXT NOT NULL,
    c_dataset_id TEXT NOT NULL,
    c_partition_key TEXT NOT NULL,
    c_range_start DATETIME NOT NULL,
    c_range_end DATETIME NOT NULL,
    c_status TEXT NOT NULL DEFAULT 'pending',
    c_next_action TEXT NOT NULL DEFAULT 'archive',
    c_next_action_at DATETIME NOT NULL,
    c_attempts INTEGER NOT NULL DEFAULT 0,
    c_lease_worker_id TEXT NOT NULL DEFAULT '',
    c_lease_token TEXT NOT NULL DEFAULT '',
    c_lease_until DATETIME,
    c_worker_id TEXT NOT NULL DEFAULT '',
    c_file_path TEXT NOT NULL DEFAULT '',
    c_file_bytes INTEGER NOT NULL DEFAULT 0,
    c_file_sha256 TEXT NOT NULL DEFAULT '',
    c_row_count INTEGER NOT NULL DEFAULT 0,
    c_subject_count INTEGER NOT NULL DEFAULT 0,
    c_columns_json TEXT NOT NULL DEFAULT '[]',
    c_preview TEXT NOT NULL DEFAULT '',
    c_archived_at DATETIME,
    c_verified_at DATETIME,
    c_last_error TEXT NOT NULL DEFAULT '',
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_status IN ('pending', 'archived', 'expired')),
    CHECK (c_next_action IN ('archive', 'verify', 'none')),
    CHECK (c_attempts >= 0),
    CHECK (c_file_bytes >= 0),
    CHECK (c_row_count >= 0),
    CHECK (c_subject_count >= 0),
    FOREIGN KEY (c_space_id, c_dataset_id) REFERENCES t_archive_tasks (c_space_id, c_dataset_id) ON DELETE CASCADE,
    UNIQUE (c_space_id, c_dataset_id, c_partition_key)
);

CREATE INDEX IF NOT EXISTS idx_t_archive_partitions_action
ON t_archive_partitions (c_next_action, c_next_action_at)
WHERE c_next_action != 'none';
CREATE INDEX IF NOT EXISTS idx_t_archive_partitions_lease
ON t_archive_partitions (c_lease_until)
WHERE c_lease_until IS NOT NULL;

CREATE TRIGGER IF NOT EXISTS trg_t_archive_partitions_mtime
AFTER UPDATE ON t_archive_partitions
FOR EACH ROW
WHEN NEW.c_mtime = OLD.c_mtime
BEGIN
    UPDATE t_archive_partitions SET c_mtime = CURRENT_TIMESTAMP WHERE c_id = OLD.c_id;
END;

-- 执行记录：每次归档、复核、重新归档一行，保留 30 天
CREATE TABLE IF NOT EXISTS t_archive_runs (
    c_id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    c_space_id TEXT NOT NULL,
    c_dataset_id TEXT NOT NULL,
    c_partition_key TEXT NOT NULL,
    c_worker_id TEXT NOT NULL DEFAULT '',
    c_kind TEXT NOT NULL,
    c_result TEXT NOT NULL,
    c_row_count INTEGER NOT NULL DEFAULT 0,
    c_prev_row_count INTEGER NOT NULL DEFAULT 0,
    c_request_count INTEGER NOT NULL DEFAULT 0,
    c_message TEXT NOT NULL DEFAULT '',
    c_started_at DATETIME NOT NULL,
    c_finished_at DATETIME NOT NULL,
    CHECK (c_kind IN ('archive', 'verify', 'rearchive')),
    CHECK (c_result IN ('success', 'mismatch', 'failed', 'rejected', 'expired'))
);

CREATE INDEX IF NOT EXISTS idx_t_archive_runs_dataset ON t_archive_runs (c_space_id, c_dataset_id, c_started_at);
CREATE INDEX IF NOT EXISTS idx_t_archive_runs_retention ON t_archive_runs (c_started_at);

-- 归档 worker：同一时刻只有一个 worker 持有活动租约（c_lease_until 未过期）；心跳刷新磁盘与进度
CREATE TABLE IF NOT EXISTS t_archive_workers (
    c_id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    c_worker_id TEXT NOT NULL,
    c_instance_id TEXT NOT NULL DEFAULT '',
    c_version TEXT NOT NULL DEFAULT '',
    c_root_dir TEXT NOT NULL DEFAULT '',
    c_disk_total_bytes INTEGER NOT NULL DEFAULT 0,
    c_disk_free_bytes INTEGER NOT NULL DEFAULT 0,
    c_pacing_json TEXT NOT NULL DEFAULT '{}',
    c_progress_json TEXT NOT NULL DEFAULT '{}',
    c_lease_until DATETIME,
    c_last_heartbeat_at DATETIME,
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_disk_total_bytes >= 0),
    CHECK (c_disk_free_bytes >= 0),
    UNIQUE (c_worker_id)
);

CREATE TRIGGER IF NOT EXISTS trg_t_archive_workers_mtime
AFTER UPDATE ON t_archive_workers
FOR EACH ROW
WHEN NEW.c_mtime = OLD.c_mtime
BEGIN
    UPDATE t_archive_workers SET c_mtime = CURRENT_TIMESTAMP WHERE c_id = OLD.c_id;
END;
```

字段说明：

- `c_status` 中不单独设 `failed`：未归档且 `c_attempts > 0` 即「失败重试中」，已归档的分区重新归档失败时旧文件仍有效。
- `c_preview` 是表头加前 20 行（不超过 8KB），由 worker 在完成时上报。文件在 worker 机器上，控制台无法直接读取。
- 归档任务有已归档分区后不能删除，只能停用；永久归档不提供删除文件的入口。
- mgr 的库丢失时，用 worker 机器上的 `moox-archive-cli reindex` 扫描归档目录，重新上报分区登记，已有文件不受影响。

## 9. 接口

### 9.1 `trpc.moox.archive.ArchiveMgr`（mgr，端口 11406）

`console_name: archive`，浏览器路径 `/api/admin/archive/<方法>`；调用方 `console`、`moox-cli`；按请求头注入的 `space_id` 限定范围。

| 方法 | 说明 |
| --- | --- |
| `GetArchiveOverview` | 活动 worker（ID、版本、归档目录、磁盘用量、最后心跳）、节奏配置、正在执行的分区与进度、积压和告警汇总 |
| `ListArchiveTasks` | 当前空间的任务和汇总：已连续归档到哪天、待归档数、失败重试数、临近删除数、已过期数、总行数与字节、下次执行时间、健康等级 |
| `PrepareArchiveTask` | 给定数据集，返回频率、分区粒度、线上保留期、最早可归档日期，以及是否已有任务 |
| `CreateArchiveTask` | 创建任务：只接受已激活的时序数据集，起始日期不早于最早可归档日期 |
| `UpdateArchiveTask` | 启停、调整等待时长；起始日期只能往前挪，且不早于最早可归档日期 |
| `DeleteArchiveTask` | 仅当任务没有已归档分区时允许 |
| `ListArchivePartitions` | 按月份或区间、状态列出分区 |
| `GetArchivePartition` | 分区详情：文件位置、大小、sha256、行数、标的数、列、预览、最近的执行记录 |
| `RearchivePartitions` | 把区间内的分区标为待重新归档；已过期的跳过并在结果中列出。只改调度，真正执行仍走 worker 的避让窗口 |
| `RetryFailedPartitions` | 把失败重试中的分区退避清零，下一次 tick 优先领取 |
| `ListArchiveRuns` | 执行记录，按任务、类型、结果筛选，分页 |

只读方法：`GetArchiveOverview`、`ListArchiveTasks`、`PrepareArchiveTask`、`ListArchivePartitions`、`GetArchivePartition`、`ListArchiveRuns`。

### 9.2 `trpc.moox.archive.ArchiveWorker`（mgr，端口 11408）

`acl: []`，只经 Access 对外部身份 `archive-worker` 开放（与 `FactorEngine` 一样）。

| 方法 | 说明 |
| --- | --- |
| `ArchiveWorkerHeartbeat` | 心跳与 worker 租约；返回是否为活动 worker |
| `PullArchiveWork` | 领取一个分区（无工作时返回空） |
| `ReportArchiveProgress` | 续租并上报进度 |
| `CompleteArchiveWork` | 上报结果 |

### 9.3 Access 白名单与 Storage 调用

新增外部身份 `archive-worker`：

| 服务 | 方法 |
| --- | --- |
| `trpc.moox.storage.PrimaryStore` | `ReadTimeSeriesRows`、`ListHistorySubjects`、`CountTimeSeriesRows` |
| `trpc.moox.storage.Metadata` | `GetDataset`、`ListDatasetColumns` |
| `trpc.moox.archive.ArchiveWorker` | 全部四个方法 |

- worker 只配置固定的 Access（`access_address` + `access_id`），不使用主机网关配置；Storage 请求体的角色认证与因子引擎相同
  （`storage-primary-auth.secret`），写权限由 Access 白名单拦住，worker 只能调用读方法。
- mgr 以内部身份 `archive-mgr` 经 `gatewayclient` 调用 `Metadata.GetDataset`，读取频率、保留期和激活状态。
- 读取方式：先 `ListHistorySubjects` 取该频率下有过数据的标的并排序，每 50 个标的一批，按分区时间范围调用
  `ReadTimeSeriesRows`（多个 selector + `after_key` 翻页）。DataNode 的 `pageHistory` 已支持多 selector，落地时补一个用例，
  确认 `after_key` 与多 selector 组合的语义。

## 10. 前端

### 10.1 菜单与路由

数据采集 → **数据归档**：路径 `/collector/archive`，路由名 `collector-archive`，排在「采集任务」之后。

### 10.2 页面

页面分两个 Tab。

**归档任务**

- 顶部概况条：活动 worker 和在线状态、归档目录、磁盘剩余、下次 tick 时间、正在归档的分区与进度，以及一句避让规则说明
  （「每 10 分钟第 4 分 43 秒起；只在每分钟第 25–55 秒读取，避开整点前后」）。worker 离线或磁盘不足时整条显示告警色。
- 任务表格：

  | 列 | 内容 |
  | --- | --- |
  | 采集任务 | 采集任务名，悬停显示数据集 ID |
  | 频率 / 粒度 | 如 `1m / 按日` |
  | 线上保留 | 如 `7 天`、`永久` |
  | 起始日期 | |
  | 已归档至 | 从起始日期开始连续归档到的最后一个分区 |
  | 待归档 / 失败 / 已过期 | 数量，点击打开详情并按状态筛选 |
  | 文件 | 总行数、总大小 |
  | 下次执行 | |
  | 健康 | 正常 / 需关注 / 异常（规则见第 12 节） |
  | 操作 | 详情、停用 / 启用、删除（仅无已归档分区时可用） |

- 新建任务（对话框）：
  1. 选择采集任务：只列出结果为时序数据集、且尚未建立归档的任务（任务名来自 Collector 的任务列表）；
  2. 调用 `PrepareArchiveTask` 展示「频率 1m，按日分区；线上保留 7 天，最早可归档到 2026-10-10」；
  3. 选择起始日期，默认为最早可归档日期；
  4. 高级选项：等待时长（默认 24 小时）。
- 详情抽屉：
  - 汇总卡片：已归档分区数、总行数、总大小、最近一次归档、最近一次复核；
  - 月历视图：每个分区一格，按状态着色——未到期、待归档、归档中、已归档（复核期内）、已定稿、失败重试中、已过期、无数据（0 行）；
    月分区任务改为按年展示的月格；
  - 点击格子：行数、标的数、文件位置（`worker_id` + 完整路径）、大小、sha256、归档与复核时间、预览、最近执行记录，可「重新归档」；
  - 批量操作：选择日期区间「重新归档」、「重试失败分区」。

**执行记录**

表格：时间、任务、分区、类型（归档 / 复核 / 重新归档）、结果、行数（及与旧文件的差值）、请求数、耗时、说明；按任务、类型、结果筛选。

### 10.3 文件下载

文件在 worker 机器的本地磁盘上，控制台不提供下载：管理网关是 JSON RPC，单个响应有大小上限，且编译机不接受入站连接。

## 12. 监控与告警

mgr 的 `/metrics`：

- 按任务：积压分区数、临近删除数、已过期数、失败重试数、最早到期分区的等待时长；
- worker：最后心跳时间、磁盘可用量；
- 执行：归档、复核、重新归档的次数与结果。

任务健康等级（列表与总览共用）：

| 条件 | 等级 |
| --- | --- |
| 有临近删除或已过期的分区；或有积压时活动 worker 离线超过 30 分钟 | 异常 |
| 最早到期分区等待超过 24 小时；有分区连续失败 3 次以上；有被拒绝的重新归档 | 需关注 |
| 其他 | 正常 |

Monitor 增加两条告警：「归档分区临近删除或已过期」（critical）、「归档积压超过 24 小时或 worker 离线超过 30 分钟」（warning）。

## 13. 部署

- **mgr**：加入 control 的原生放置（`[placements] control = [..., "archive-mgr"]`），随 control 单元安装；
  数据目录 `data/archive-mgr`，只存元数据，占用很小。
- **worker**：新增 `scripts/deploy/deploy-archive-worker.sh`，用法参照 `deploy-factor-engine.sh`，在目标机器上执行：
  `--dir`（安装目录）、`--root-dir`（归档目录）、`--worker-id`、`--access-address`、`--access-id`、`--access-key-id`；
  Linux 用 systemd 用户服务、macOS 用 launchd 托管，并等待 `/readyz`。部署目标由在哪台机器执行脚本决定。
- **本次部署**：worker 装在编译机 `mooyang-X99`（192.168.0.103），与因子引擎同机、共用同一个 Access。
  编译机断电或断网时分区会积压，恢复后自动追赶；只要中断不超过 crypto 1m 的保留期（7 天）就不会丢数据，超过 2 天未归档的分区会先告警。
- 凭据：`moox-admin-cli keys export --caller archive-worker` 生成外部身份密钥，`keys export-access` 重新导出 Access 校验文件并部署 Access；
  mgr 的内部身份 `archive-mgr` 随 control 部署分发。

## 14. 容量与耗时估算

按以下规模估算（仅用于判断量级）：stockcn 1m 约 5000 个标的，crypto 1m 约 500 个，其他频率合计约 50 万行/天。

| 项 | 估算 |
| --- | --- |
| 每日行数 | stockcn 1m 约 120 万，crypto 1m 约 72 万，合计约 240 万 |
| 每日请求数 | 每页 2000 行，约 1200 次 |
| 每日耗时 | 每分钟可用 30 秒，每次请求约 1 秒，约 25 次/分钟，约 50 分钟；从北京时间 08:04 开始，A 股开盘前基本完成 |
| 带宽 | 响应约 200 字节/行，gzip 后读取速率约 0.3 Mbps，每天下行约 100MB |
| 磁盘 | CSV 约 90 字节/行，gzip 后约 1/5：stockcn 1m 每年约 5GB，全部数据每年约 10GB |
| 新建任务补历史 | stockcn 1m 补 45 天约 2.7 万次请求，约一天追平 |
