# 数据归档设计

状态：设计稿 v4（2026-10-16），尚未编码。实现后以[归档](../模块/归档.md)模块文档为准。

演进：

- v2：用户自行设定定时归档任务（执行计划与开始时间），每次运行拉取每个序列最近 N 根，不同数据集的任务可以并发；
- v3：开始时间可选「立即开始」，crypto 等全天交易的空间默认全天按小时备份；Storage 的「最近 N 根」扩展为一次查多个标的；
- v4：最短执行间隔改为 5 分钟，mgr 用一个每秒触发的 trpc timer 作为全局触发器；为了不在短间隔下反复重写当天的文件，
  未封存的数据先进本地暂存区，分区不再变化后才封存为正式文件；第 5 节并入 [Storage 读写路径审查](../审查/2026-10-16-Storage读写路径审查.md)
  中与读取路径相关的修复。

## 0. 设计原则

1. **永久保存，不追时效**：归档只保证线上数据在被保留策略删除之前落到本地，晚一两天可以接受。
2. **不影响采集**：运行中的每个请求都避开整点前后和每分钟开头的写入高峰；并发和带宽都有上限。
   Storage 的 DataNode 读取没有并发保护，限流由归档自己承担。
3. **定时拉取，不订阅事件**：mgr 和 worker 都不订阅 EventBus，任何事件都不会触发归档。何时运行由任务的执行计划和 mgr 的全局触发器决定，
   读多快由 worker 的节奏配置决定。
4. **窗口重叠代替复核**：每次拉最近 N 根，N 至少覆盖两个执行间隔、且至少回看 1 小时。每根数据至少被读两次，
   最后一次被读到时距离它产生至少 1 小时，这期间补采写回的数据会被带上。
5. **正式文件封存后不变**：分区在不会再被定时运行写入之后才写出正式文件，之后只有显式的「补拉区间」会重写它。
6. **本地只增不删**：同一行以最后一次从 Storage 读到的值为准；Storage 因保留期删掉的行在本地保留。
7. **部署目标可配置**：worker 只做出站连接，可以装在任何能访问 Access 的机器上；本次装在编译机。

## 1. 背景

### 1.1 现有实现

`modules/archive` 目前是事件驱动实现：消费 `rows.upserted`，先写本地 Journal，再按月物化为 Parquet，可选同步到 COS；
Storage 元数据中有 `t_archive_files` 及 `RegisterArchiveFile` / `ListArchiveFiles` 用于登记文件。该模块没有部署过，也没有页面。

本设计用定时拉取的实现**整体替换**它（项目不考虑历史兼容）。不保留事件式实现的原因：

- 事件式需要 7×24 小时在线消费，停机超过 JetStream 保留期就会丢数据，因此必须配套 Journal 和去重回执；
- 定时拉取天然幂等，运行失败下次再拉即可；唯一的约束是归档不能中断到线上保留期之外。

也考虑过像因子引擎那样由事件触发，再借助 NATS 的延迟投递避开整点，最终不采用：项目内嵌的 nats-server 是 v2.11.17，
JetStream 原生的延迟投递（`Nats-Schedule`，流需开启 `AllowMsgSchedules`）从 2.12 才提供；2.11 的 `NakWithDelay` 和 `BackOff`
是重试机制，不是调度器；即使有延迟投递，同一时刻到期的大量消息仍会集中触发，读取节奏照样要归档自己控制。

### 1.2 约束

| 约束 | 来源 | 对设计的影响 |
| --- | --- | --- |
| 完整历史只在 DataNode | View 每个序列只留最近 `view_bars`（5000）根 | 只能通过 `PrimaryStore.ReadTimeSeriesRows` 读取 |
| 「最近 N 根」目前一次只能查一个标的 | DataNode 的 `latest_per_series` 要求恰好一个 selector，不能带时间范围和翻页，一次返回完整结果 | 本次扩展为一次最多 100 个标的（第 5 节） |
| PrimaryStore 路由超时 5 秒、请求体上限 32MB | 服务目录 `timeout_ms: 5000`、`max_body_bytes: 33554432` | 单次批量读取限制在 2 万行以内；N 上限 10000 |
| DataNode 读取代价高、无并发上限 | 每行约「列数 + 2」次查找（第 5 节 S-2）；2026-10-14 回填把 storage-node 打到 330% | 每个 DataNode 同时读取的任务数有上限，同一任务内串行；本次同时降低每行的读取代价 |
| 线上保留期短 | 生产保留策略：crypto 1m 保留 7 天，stockcn 1m 保留 45 天，按天桶清理 | 中断时间接近保留期时告警；超出保留期的缺口无法补齐 |
| SCF 写入集中在每分钟开头 | 收盘到批次写完 p50 9.0s、p99 22.5s（[SCF 定时触发采集改造设计](SCF定时触发采集改造设计.md)） | 每分钟第 0–25 秒不发起读取 |
| trpc timer 是静态配置 | 定时器在 `trpc_go.yaml` 中逐个声明，运行时不能按任务动态增加 | mgr 只配一个每秒触发的全局定时器，到点的任务由它逐个触发 |
| 编译机在内网，只能出站 | 与因子引擎相同 | 拆成控制机上的管理端和目标机器上的 worker |

## 2. 总体架构

参照 Factor 的「manager + engine」模式，`modules/archive` 产出两个程序：

| 程序 | 部署位置 | 职责 |
| --- | --- | --- |
| `moox-archive-mgr` | control（原生放置） | 保存任务、运行记录、分区登记和 worker 状态（SQLite）；全局触发器按执行计划生成运行；`ArchiveMgr` 供控制台和 CLI 调用；`ArchiveWorker` 供 worker 领取运行、上报结果 |
| `moox-archive-worker` | 任意机器，只出站（本次为编译机） | 经 Access 领取运行、读取 Storage、写入本地暂存区、封存正式文件，并上报进度、结果与心跳 |
| `moox-archive-cli` | 随 mgr / worker | `init`、`status`、`verify`（重新计算 sha256 并与登记值比对）、`reindex`（扫描归档目录，重建分区登记） |

```text
浏览器 ─► Console Proxy ─► Admin 管理网关 ─► archive-mgr（control）
                                              │  trigger.timer（每秒）：到点的任务生成运行
                                              │  maintain.timer（每分钟）：回收过期租约、刷新数据集信息、清理记录
                                              │  ArchiveMgr：任务、运行、分区
                                              │  ArchiveWorker：心跳、领取运行、上报
                                              ▲
                                              │ 出站 tRPC（签名，gzip）
archive-worker（编译机）──► Access 11004 ──────┤
   │  每 10 秒心跳；有空闲并发槽时每 5 秒领取一次   └─► Storage Metadata / PrimaryStore（只读）
   ├─ 每批标的：ReadTimeSeriesRows(latest_per_series = N, 多个 selector)，接不上时按时间区间补读
   ├─ 逐批写入本地暂存区（SQLite），值没变的行不算写入
   ├─ 不会再被写入的分区封存为 .csv.gz（.partial → fsync → rename）
   └─ CompleteArchiveRun 上报分区登记与运行统计
```

不放进 Collector：归档会长时间读 Storage、写磁盘，worker 需要部署在磁盘大的机器上；拆开后 Collector 保持轻量，归档出问题不影响采集计划和补采。

## 3. 归档任务

一个归档任务对应一个时序数据集，以 `(space_id, dataset_id)` 标识。界面上按采集任务名选择；数据模型本身不限于采集结果，
因子结果数据集以后只需增加界面入口。

### 3.1 用户设置

| 设置 | 说明 | 默认 |
| --- | --- | --- |
| 数据集 | 采集任务的结果数据集，必须是已激活的时序数据集 | — |
| 执行计划 | 带秒的 6 段 cron 加时区；界面提供「每 N 分钟」「每 N 小时」「每天」「每周」预设，也可直接写 cron；最短间隔 5 分钟 | 按空间和频率给出（见 3.3） |
| 开始时间 | 二选一：**立即开始**（保存后马上运行一次，之后按执行计划）；**指定时间**（从该时刻起按执行计划运行，之前的计划时刻不运行） | 立即开始 |
| 每次拉取根数 N | 每个序列（标的 × series_tag）拉最近 N 根，范围 1–10000 | 推荐值见 3.2 |
| 回补起点（可选） | 首次运行时，从这个数据时间补读到最近 N 根之前，补齐历史；不早于「今天 − 线上保留期 + 1 天」 | 不回补，首次只拉最近 N 根 |
| 状态 | 启用 / 停用 | 启用 |

数据集的频率、分区粒度和所在 DataNode 由 mgr 从 Storage 读取，用户不填。

「立即开始」只是立刻生成第一次运行，运行中的每个请求仍受第 6 节的避让与带宽限制，不会因为「立即」而在整点或每分钟开头读取。
任务停用后再启用时，同样可以选择立即运行一次。

### 3.2 执行计划与 N 的校验

mgr 在创建和修改时校验，界面同时预览接下来 5 次运行时间：

- **最短间隔 5 分钟**：相邻两次计划时刻的最小间隔小于 5 分钟时拒绝保存。保存时把这个最小间隔记为任务的执行间隔，
  用于计算 N 的推荐值和封存等待时间。
- **计划时刻不做硬性限制**：运行中的每个请求都受避让窗口约束，所以计划时刻落在避让区间里也不会在高峰读取。
  预览中如果某个计划时刻落在每分钟第 0–25 秒或每小时 :58–:04，提示「实际读取从 HH:MM:25（或 HH:04:25）开始」，并建议一个错开的时刻；
  各空间的默认计划已经错开。
- **N 的推荐值**：`max(2 × B, B + L)`，其中 B 是一个执行间隔内的根数，L 是最少回看时长（mgr 配置，默认 1 小时）内的根数：
  - 间隔不到 1 天时，按自然时间计算 B 和 L：`间隔 / 频率`、`1 小时 / 频率`；
  - 间隔为 1 天及以上时，按每天的根数计算 B：`间隔天数 × 每天根数`。1m 的每天根数为 crypto 1440、stockcn 240、
    stockhk 330、stockus 390，其他频率按比例换算。
- **N 偏小时提示**：N 小于推荐值时提示「回看不足，补采写回的数据可能带不上；断档靠补读接上」，但允许保存。

### 3.3 各空间的默认执行计划（北京时间）

| 空间 | 默认计划 | 理由 |
| --- | --- | --- |
| crypto（频率低于 1h） | 每小时第 34 分 43 秒（`43 34 * * * *`） | 全天交易，全天按小时备份；第 34 分避开整点、半点（30m 及以下 K 线收盘）和整点前后的避让区间 |
| crypto（1h 及以上） | 每天 08:04:43 | 每天新增的根数少，一天一次即可 |
| stockcn | 每天 17:04:43 | A 股 15:00 收盘，留出 2 小时给自动补采 |
| stockhk | 每天 17:34:43 | 港股 16:10 收盘之后 |
| stockus | 每天 06:04:43 | 美股收盘（北京时间 04:00 / 05:00）之后 |

例：

| 任务 | N | 说明 |
| --- | --- | --- |
| crypto 1m，每小时 | `max(120, 60 + 60) = 120` | 每次拉过去 2 小时，每根数据被读两次 |
| crypto 1m，每 5 分钟（`43 4-59/5 * * * *`） | `max(10, 5 + 60) = 65` | 每次拉过去 65 分钟，每根数据约被读 13 次；绝对量仍很小（第 15 节）。:59:43 那次的读取会等到 :04:25 才开始 |
| stockcn 1m，每天 17:04:43 | `max(480, 240 + 60) = 480` | 每次拉到当天和前一个交易日，当天的数据第二天还会再读一次 |

自动补采通常在十几分钟内补上实时漏采，1 小时的回看足够覆盖；Collector 长时间停机造成的晚到补采，用「补拉区间」或调大 N。

## 4. 一次运行做什么

1. 读取数据集元数据（频率、列），调用 `ListHistorySubjects` 取该频率下有过数据的标的，按 `subject_id` 排序后切成批：
   每批标的数 = `min(50, floor(20000 / N))`，保证单次响应不超过 2 万行（如 N = 65 或 120 时 50 个，N = 480 时 41 个，N = 2880 时 6 个）。
2. 每批调用一次 `ReadTimeSeriesRows(latest_per_series = N)`，selector 为这批标的（第 5 节），一次拿到它们各个 `series_tag` 最近 N 根。
3. **丢弃已封存的部分**：定时运行和立即运行中，`data_time` 早于本任务封存边界（第 8.3 节）的行直接丢弃。
   停更的标的每次都会读回同样的旧数据，这样它们不会反复打开早已封存的分区；补拉区间不丢弃。
4. **接续检查**：worker 在本地记录每个序列上次归档到的最新时间 `last_time`。某个序列本次返回了满 N 根，而最早一根晚于
   `last_time`，说明中间可能有缺，需要补读 `(last_time, 最早一根)`。
   - 同一批里需要补读的标的合并读取：时间范围取它们缺口的并集，多个 selector 加 `after_key` 翻页（每页 2000 行），
     再按各自的缺口过滤。补读行数超过 `max_batch_rows`（默认 20 万）时，把时间范围切成几段分别读取；
   - 补读区间的起点早于线上保留期截止时，截到截止处，被截掉的部分记为「无法补齐」并上报；
   - 返回不足 N 根说明已是该序列的全部历史，不需要补读。
5. **写入暂存区**：每批读完（含补读）后，在一个本地事务里写入暂存区并更新这批序列的 `last_time`（第 8.2 节）。
   同键的行值没变时不算写入；新增或变化的行记下所在分区的最近变化时间。
6. **封存**：所有批处理完后，检查本任务处于打开状态的分区，满足封存条件的写出正式文件（第 8.3 节）。
7. 向 mgr 上报本次涉及的每个分区（行数、标的数、数据时间范围、是否封存；封存的再带上文件路径、大小、sha256、列、预览）和运行统计
   （请求数、读取字节、读取 / 新增 / 变更 / 丢弃行数、补读标的数、封存分区数、无法补齐的区间）。

**首次回补**：填了回补起点时，首次运行先按时间分段补齐历史：从回补起点开始每段 1 天，对全部标的读完一段（多个 selector 加 `after_key`）
就写入暂存区并立即封存这一段，再读下一段，所以暂存区不会因为历史回补而膨胀；补到最近 N 根之前后，再按上面的步骤 1–7 执行。

运行中途失败时，已提交的批次留在暂存区，`last_time` 也已推进；下一次运行重新拉最近 N 根，接续检查会补上中间缺的部分，不会丢数据，
也不会产生半写的正式文件。

## 5. Storage 改动（本次实现）

### 5.1 一次查多个标的的「最近 N 根」

`ReadTimeSeriesRows` 的 `latest_per_series` 是给 View 重建用的：要求恰好一个带 `subject_id` 和 `freq` 的 selector，
不能带 `time_range`、`after_key` 或页码，一次完整返回。Primary 只原样转发，限制在 DataNode
（`modules/storage/internal/service/datanode/pebble/history.go` 的 `ReadTimeSeriesRows`）。
按标的逐个请求时，stockcn 1m（约 5000 个标的）每次运行要发 5000 次请求，约 2 小时，大部分时间耗在 Access 往返上。

协议字段不变，只放宽语义，并同步修改 `rows.proto` 中 `latest_per_series` 的注释：

- selector 数量放宽为 1–100 个，每个都必须带 `subject_id` 和 `freq`，`series_tag` 可选（不带表示该标的全部序列）；
- 增加总量上限：`selector 数 × latest_per_series ≤ 20000`，超出返回 `INVALID_PARAM`；
- 仍然不能带 `time_range`、`after_key` 或页码，仍然一次完整返回；
- 返回顺序：按请求中 selector 的顺序，每个序列内从新到旧（与现在单个 selector 的顺序一致），调用方自行排序；
- 实现：对每个 selector 依次调用现有的 `latestPerSeries`，每个之间检查 `ctx`。

View 重建仍然只传一个 selector，不受影响。

### 5.2 同时修复的读取问题

以下两项来自 [Storage 读写路径审查](../审查/2026-10-16-Storage读写路径审查.md)，与 5.1 改的是同一段读取路径，放在同一次改动和发布里：

- **S-1 字段补全分块**：现在只按「键数 × 字段数 ≤ 10 万」分块，没按「键数 ≤ 1 万」分块，一次返回超过 1 万行、列数少于 10 时
  整个读取失败（`read request exceeds key/field limit`）。5.1 的批量读取单次 2 万行，必然触发。改为 `min(10000, 100000 / 字段数)`。
- **S-2 按行前缀扫描取代逐字段点查**：`ReadFieldsWithPresence` 现在每行先建两个迭代器判断存在，再对每个字段各 `Get` 一次；
  同一行的字段在物理上连续。改为整个请求共用一个快照迭代器，键按物理编码排序后，每行 `SeekGE` 行前缀、顺序 `Next` 取字段并得到存在性，
  只有请求了属性或这一行没有字段时才查属性命名空间，最后按原顺序返回。每行从「2 次建迭代器 + F 次点查」降到「1 次定位 + F 次顺序读」，
  因子窗口读取、View 重建、Collector 读行和归档都受益。

审查中的 S-4（出站事件重复读取和校验）也在 DataNode 上、改动小，可以并入同一次发布；S-3（Primary 每个请求复制整份元数据）
涉及 storage-primary，单独做。

### 5.3 测试与发布

- 测试：
  - 多个 selector 的结果与逐个单查的并集一致；一个标的有多个 `series_tag` 时每个序列各取 N 根；
  - 超出数量或总量上限、带时间范围或 `after_key` 时被拒绝；没有数据的标的返回空、不报错；
  - 一次返回 1 万行以上、只请求少量列时读取成功（S-1）；
  - 前缀扫描与原逐字段点查的结果逐行一致，包括只有属性没有字段的行、记录型数据集取最大版本的行（S-2）；
  - 用回填场景做前后对比 benchmark（读取耗时、CPU）。
- 发布：只有 DataNode 的行为变化，只需换 storage-node 的二进制（Linux CGO 构建）。重启时 DataNode 停写几秒，
  选在分钟中段、避开整点执行，期间失败的 SCF 提交由自动补采修复。Storage 先于 worker 发布，worker 不保留逐个标的的读法。

## 6. 节奏、并发与触发

### 6.1 运行中的节奏（worker 配置 `pacing`，均可调）

| 规则 | 默认值 | 目的 |
| --- | --- | --- |
| 分钟内避让 | 只在每分钟第 25–55 秒**发起**请求 | SCF 收盘到写完 p99 22.5 秒 |
| 整点避让 | 每小时 :58 到下一小时 :04 之间不发起请求 | 1h K 线收盘、1h 因子计算等整点任务；同在编译机的因子引擎整点后集中读取，避免与它争用同一条公网链路和 Storage 出口带宽 |
| 请求间隔 | 同一运行的两次请求之间至少 200ms | |
| 带宽上限 | `max_bytes_per_second` 默认 512KB/s，所有并发运行共享一个令牌桶（按解压后的响应字节计，压缩后约 0.8 Mbps） | 无论并发多少、请求多快，读取速率都有硬上限 |
| 压缩 | `gateway_client.compression: gzip` | 经公网读取时减少带宽 |
| 磁盘保护 | 可用空间低于 `min_free_bytes`（默认 5GB）时不再领取运行，心跳上报 `disk_low` | 避免写满磁盘 |

worker 的避让依赖本机时钟，部署机器必须开启 NTP 同步。

### 6.2 并发

- **不同数据集的任务可以并发**：worker 最多同时执行 `max_concurrent_runs`（默认 4）个运行；
  同一个 DataNode 上同时最多 `max_runs_per_data_node`（默认 2）个。线上只有 `storage-node-0`，所以实际最多 2 个任务同时在读。
- **同一任务内串行**：一次只有一个请求在途；同一任务同时只有一个运行。
- **计划时刻到了但上一次还没结束**：跳过这次计划时刻，任务的连续跳过次数加 1（不生成运行记录）；下一次运行靠接续检查补上。
- **worker 离线期间错过的多个计划时刻**合并成一次运行，worker 恢复后立即执行。
- 不同任务写不同目录，并发运行之间没有文件冲突。

### 6.3 全局触发器

trpc timer 只能在 `trpc_go.yaml` 中静态声明，不能为每个任务各建一个。mgr 只配一个每秒触发的定时器：

- `trpc.moox.archive.mgr.trigger.timer`，cron `* * * * * *`，单次超时 900ms，用 `timerjob` 防重叠；
- 每次触发查询 `c_status = 'enabled' AND c_next_run_at <= now` 的任务（走索引，每秒一次查询，开销可以忽略）。
  对每个到点的任务，在一个事务里：已有排队中或运行中的运行时，连续跳过次数加 1；否则生成一条 `scheduled` 运行，并把连续跳过次数清零。
  之后把 `c_next_run_at` 推进到「当前时刻之后」的下一个计划时刻，期间错过的计划时刻不补；
- 每秒触发让计划时刻的误差在 1 秒以内；worker 有空闲并发槽时每 5 秒领取一次，所以运行在计划时刻后 5 秒内开始，
  真正的读取仍按 6.1 的避让规则发起；
- 维护工作放在另一个定时器：`trpc.moox.archive.mgr.maintain.timer`，cron `13 * * * * *`（每分钟第 13 秒）。

## 7. 补写与断档

- **回看窗口内的补写**：每根数据在约 `N / B` 次运行中都会被读到，最后一次读到它时距离它产生至少 1 小时、且至少过了一个执行间隔。
  这期间补采写回的数据会被自动带上。
- **封存之后的补写**（例如一周后手动补采了更早的日期）：定时运行不会再带上。界面提供「补拉区间」：对指定时间区间做一次区间读取，
  涉及的已封存分区重新打开，与原文件归并后重新封存；区间必须仍在线上保留期内。
- **断档**：worker 停机或运行失败导致与上一次接不上时，下一次运行按第 4 节第 4 步对每个序列补读；
  超出线上保留期的部分无法补齐，记录在运行结果里并告警。
- **保留期告警**：任务最近一次成功运行距今超过「线上保留期 − 2 天」时，健康等级升为异常（见第 13 节），提示尽快恢复 worker。
- **局限**：Storage 中已存在的行后来被删除（如管理员删除数据集行）时，本地不会删除，符合永久归档的目的。

## 8. 文件、暂存区与封存

### 8.1 目录

```text
<root_dir>/<space_id>/<dataset_id>/<yyyy>/<dataset_id>_<yyyymmdd>.csv.gz   # 已封存的日分区（频率低于 1d）
<root_dir>/<space_id>/<dataset_id>/<yyyy>/<dataset_id>_<yyyymm>.csv.gz     # 已封存的月分区（1d 及以上）
<root_dir>/<space_id>/<dataset_id>/_dataset.json                          # 频率、列及类型；列变化时重写
<root_dir>/.state/<space_id>/<dataset_id>.db                              # 本任务的暂存区与序列状态（SQLite）
```

- 分区按 UTC 切分。UTC 日与各市场都对得上：A 股和港股交易时段在 UTC 01:30–08:00，美股在 13:30–21:00，币安日线以 UTC 0 点为界。
- 正式文件默认 gzip 压缩（worker 配置 `compression: gzip | none`），pandas 和 DuckDB 都能直接读取 `.csv.gz`。
- UTF-8，无 BOM，按 RFC 4180 转义。表头为 `data_time,subject_id,series_tag,<数据集列…>`；行上有 attributes 时，
  最后追加一列 `attributes`（JSON）。频率在数据集内唯一，不写成列。
- `data_time` 为 UTC RFC3339，纳秒为 0 时不输出小数部分（`2026-10-15T01:31:00Z`）；数值输出最短的可往返十进制，不用科学计数法；
  缺失字段输出空串。行按 `subject_id, data_time, series_tag` 排序。
- 数据集只增列。封存时以当前列为准写表头，旧行缺的列留空；文件的列登记在 `c_columns_json`，并同步写入 `_dataset.json`。
- `.state` 与归档文件放在同一目录树下，迁移机器时一起拷走。
- 启动时清理残留的 `.partial` 文件。

### 8.2 暂存区

每个任务一个本地 SQLite 库（纯 Go 驱动，与项目其他模块一致），表结构放在 `modules/archive/schema/worker_state.sql`：

```sql
-- 每个序列已归档到的最新数据时间，用于接续检查
CREATE TABLE IF NOT EXISTS t_series_state (
    c_subject_id TEXT NOT NULL,
    c_series_tag TEXT NOT NULL,
    c_last_time TEXT NOT NULL,
    PRIMARY KEY (c_subject_id, c_series_tag)
) WITHOUT ROWID;

-- 未封存分区的暂存行：c_values 按列名保存已格式化的值（JSON），封存时按当时的列顺序输出
CREATE TABLE IF NOT EXISTS t_staged_rows (
    c_partition_key TEXT NOT NULL,
    c_subject_id TEXT NOT NULL,
    c_data_time TEXT NOT NULL,
    c_series_tag TEXT NOT NULL,
    c_values TEXT NOT NULL,
    PRIMARY KEY (c_partition_key, c_subject_id, c_data_time, c_series_tag)
) WITHOUT ROWID;

-- 分区状态：open 表示还会被运行写入，sealed 表示已写出正式文件
CREATE TABLE IF NOT EXISTS t_partition_state (
    c_partition_key TEXT NOT NULL,
    c_range_start TEXT NOT NULL,
    c_range_end TEXT NOT NULL,
    c_status TEXT NOT NULL DEFAULT 'open',
    c_last_changed_at TEXT NOT NULL,
    c_file_sha256 TEXT NOT NULL DEFAULT '',
    CHECK (c_status IN ('open', 'sealed')),
    PRIMARY KEY (c_partition_key)
) WITHOUT ROWID;
```

- 写入用 `INSERT ... ON CONFLICT DO UPDATE SET c_values = excluded.c_values WHERE c_values != excluded.c_values`，值没变的行不产生写入；
  新增和变化的行把所在分区的 `c_last_changed_at` 更新为本次运行时间。
- 一批的暂存行与 `t_series_state` 在同一个事务里提交，所以运行可以按批断点续做，不需要临时文件。
- 暂存区只保存打开的分区，按默认配置约为最近 1～3 天的数据（crypto 1m 约 200MB，stockcn 1m 约 700MB）。

### 8.3 封存

- **封存条件**：分区不是当前的 UTC 日（月分区为当前 UTC 月），且本次运行的开始时间不早于
  `分区结束时间 + max(2 × 执行间隔, 执行间隔 + 最少回看时长)`。这个等待与 3.2 中 N 的推荐值对应：此后的定时运行不会再读到这个分区的数据。
  例：crypto 1m 每小时运行时，D 日在 D+1 日 02:00 UTC 之后的第一次运行结束时封存；每 5 分钟运行时在 01:05 UTC 之后；
  stockcn 1m 每天运行时在 D+3 日的那次运行结束时封存。
- **写出文件**：按主键顺序流式读出该分区的暂存行；分区已有正式文件时（被补拉区间重新打开），与原文件流式归并，同键以暂存行为准；
  写 `<文件>.partial`，fsync 后 rename，再 fsync 目录，然后在一个本地事务里删除该分区的暂存行、标记为 `sealed`、记下 sha256。
- **封存边界**：已封存分区中最晚的结束时间，且它之前没有打开的分区（没有数据的日期不产生分区，不影响边界）。
  定时运行丢弃早于它的行（第 4 节第 3 步）。
- **补拉区间**：把涉及的已封存分区标回 `open`，读到的行照常写入暂存区，运行结束时按上面的方式与原文件归并后重新封存，不受封存等待限制。
- **未封存的数据**：暂存区里的数据在控制台上显示为「暂存中」，有行数、标的数和数据时间范围，但没有正式文件；
  封存前只能在 worker 机器上用 `moox-archive-cli export --partition <分区>` 临时导出查看。

## 9. 管理端与 worker 的协作

- **心跳与 worker 租约**：worker 每 10 秒调用 `ArchiveWorkerHeartbeat`，上报 `worker_id`、进程实例 ID、版本、归档目录、
  磁盘总量与可用量、节奏与并发配置、正在执行的运行。同一时刻只有一个 worker 持有活动租约，旧 worker 停止心跳 45 秒后
  新 worker 才能接管；同一 `worker_id` 的两个进程同时运行时，后来者心跳返回冲突，不领取运行。
- **生成运行**：由全局触发器完成（6.3）。手动的「立即运行」「补拉区间」直接生成 `manual` / `range` 运行；
  选「立即开始」的任务在保存（或重新启用）的同一事务里，`c_start_at` 取当前时间，并生成一条 `manual` 运行，之后按执行计划继续。
- **领取**：worker 有空闲并发槽时每 5 秒调用一次 `PullArchiveRun`，带上已占用的 DataNode。mgr 在一个事务中按计划时刻从早到晚，
  选出不超过 DataNode 并发上限的运行，写入运行租约（默认 10 分钟）后返回任务参数（数据集、频率、列、N、执行间隔、最少回看时长、区间、回补起点）。
- **进度**：运行中每 30 秒调用 `ReportArchiveRunProgress`，续租并上报已处理的标的数、请求数和读取字节。
- **完成**：`CompleteArchiveRun` 上报运行统计和本次涉及的分区；mgr 在一个事务中更新运行状态、分区登记、任务的最近成功时间与封存边界。
- **租约过期**：维护定时器把租约过期的运行标为 `failed`（原因「worker 失联」）；已提交的批次留在暂存区，下一次运行靠接续检查补上。
  维护定时器同时每小时调用 `Metadata.GetDataset` 刷新各任务的保留期和 DataNode，并按第 10 节的保留期清理运行记录。
- **更换机器**：文件和暂存区只存在于写它的 worker 上，分区登记记录 `c_worker_id`。换机器时，把归档目录（含 `.state`）整体拷到新机器，
  并沿用同一个 `worker_id`（配置项，默认 `archive-worker@<主机名>`），即可无缝接续。
  如果新机器换了 `worker_id`，界面标出旧文件的存放位置，新运行写到新机器上。

说明：

- `c_interval_seconds` 是执行计划中相邻两次计划时刻的最小间隔，保存时计算，下限 300 秒（5 分钟）。
- 计划时刻撞上未结束的运行时只累加 `c_consecutive_skips`，不写运行记录，避免 5 分钟间隔的任务每天产生几百条跳过记录。
- 运行记录保留期：成功的定时运行 30 天，其余（失败、取消、手动、补拉区间）90 天。5 分钟间隔的任务每天约 288 条，30 天约 8600 条。
- `t_archive_partitions` 引用任务时不级联删除：已有分区的任务不能删除，只能停用；永久归档不提供删除文件的入口。
- `c_preview` 是表头加前 20 行（不超过 8KB），封存时由 worker 上报。文件在 worker 机器上，控制台无法直接读取。
- `c_unrecoverable_json` 记录超出线上保留期、无法补齐的区间（按序列合并后最多 200 组）。
- mgr 的库丢失时，用 worker 机器上的 `moox-archive-cli reindex` 扫描归档目录和暂存区重新上报分区登记，已有文件不受影响；任务需要重新创建。

## 11. 接口

### 11.1 `trpc.moox.archive.ArchiveMgr`（mgr，端口 11406）

`console_name: archive`，浏览器路径 `/api/admin/archive/<方法>`；调用方 `console`、`moox-cli`；按请求头注入的 `space_id` 限定范围。

| 方法 | 说明 |
| --- | --- |
| `GetArchiveOverview` | 活动 worker（ID、版本、归档目录、磁盘用量、最后心跳）、节奏与并发配置、正在执行的运行与进度、告警汇总 |
| `ListArchiveTasks` | 当前空间的任务和汇总：执行计划、N、上次运行与结果、下次运行、已封存与暂存中的数据时间范围、文件数、总行数与字节、健康等级 |
| `PrepareArchiveTask` | 给定数据集，返回频率、分区粒度、线上保留期、最早回补起点、所在 DataNode、推荐的执行计划和 N，以及是否已有任务 |
| `PreviewArchiveSchedule` | 校验执行计划、开始时间和 N，返回接下来 5 次运行时间、执行间隔、推荐的 N、落在避让区间的提示与错误 |
| `CreateArchiveTask` / `UpdateArchiveTask` | 创建、修改任务（执行计划、开始时间、N、回补起点、启停）；保存前按 3.2 校验 |
| `DeleteArchiveTask` | 仅当任务没有分区时允许 |
| `RunArchiveTaskNow` | 立即生成一次运行；运行中仍受避让和带宽限制 |
| `BackfillArchiveRange` | 对指定数据时间区间生成一次补拉运行；区间不能早于线上保留期截止 |
| `CancelArchiveRun` | 取消排队中或运行中的运行；运行中的在下一个请求前停止，已提交的批次留在暂存区 |
| `ListArchiveRuns` / `GetArchiveRun` | 运行记录与详情（含无法补齐的区间） |
| `ListArchivePartitions` / `GetArchivePartition` | 按月份列出分区；详情含状态、位置、大小、sha256、行数、标的数、数据时间范围、列、预览、封存次数 |

只读方法：`GetArchiveOverview`、`ListArchiveTasks`、`PrepareArchiveTask`、`PreviewArchiveSchedule`、`ListArchiveRuns`、
`GetArchiveRun`、`ListArchivePartitions`、`GetArchivePartition`。

### 11.2 `trpc.moox.archive.ArchiveWorker`（mgr，端口 11408）

`acl: []`，只经 Access 对外部身份 `archive-worker` 开放（与 `FactorEngine` 一样）。

| 方法 | 说明 |
| --- | --- |
| `ArchiveWorkerHeartbeat` | 心跳与 worker 租约；返回是否为活动 worker，以及需要取消的运行 |
| `PullArchiveRun` | 按空闲并发槽和已占用的 DataNode 领取运行（无可领取时返回空） |
| `ReportArchiveRunProgress` | 续租并上报进度 |
| `CompleteArchiveRun` | 上报运行结果与分区登记 |

### 11.3 Access 白名单与 Storage 调用

新增外部身份 `archive-worker`：

| 服务 | 方法 |
| --- | --- |
| `trpc.moox.storage.PrimaryStore` | `ReadTimeSeriesRows`、`ListHistorySubjects` |
| `trpc.moox.storage.Metadata` | `GetDataset`、`ListDatasetColumns` |
| `trpc.moox.archive.ArchiveWorker` | 全部四个方法 |

- worker 只配置固定的 Access（`access_address` + `access_id`），不使用主机网关配置；Storage 请求体的角色认证与因子引擎相同
  （`storage-primary-auth.secret`），写权限由 Access 白名单拦住，worker 只能调用读方法。
- mgr 以内部身份 `archive-mgr` 经 `gatewayclient` 调用 `Metadata.GetDataset`，读取频率、保留期、DataNode 和激活状态。
- 最近 N 根按批读取，一次最多 100 个标的（第 5 节）；补读、首次回补和补拉区间使用多个 selector 加 `time_range` + `after_key` 翻页。
  `pageHistory` 按 `data_time, subject, freq, tag` 的顺序返回，顺序由暂存区的主键负责；落地时补一个用例，确认多个 selector 与
  `after_key` 组合的翻页语义。

## 12. 前端

### 12.1 菜单与路由

数据采集 → **数据归档**：路径 `/collector/archive`，路由名 `collector-archive`，排在「采集任务」之后。
同步修改 `static-menu.ts`、`route.ts`、中英文文案（「数据归档」/「data archive」）和 `scripts/check-menu-structure.mjs`。

### 12.2 页面

页面分两个 Tab。

**归档任务**

- 顶部概况条：活动 worker 和在线状态、归档目录、磁盘剩余、正在执行的运行（任务名、标的进度），以及一句节奏说明
  （「只在每分钟第 25–55 秒读取，避开整点前后；最多 2 个任务同时读取，总带宽不超过 512KB/s」）。
  worker 离线或磁盘不足时整条显示告警色。
- 任务表格：

  | 列 | 内容 |
  | --- | --- |
  | 采集任务 | 采集任务名，悬停显示数据集 ID |
  | 频率 / 粒度 | 如 `1m / 按日` |
  | 执行计划 | 翻译成中文（如「每 5 分钟」「每天 08:04:43」），悬停看 cron 和时区 |
  | 每次拉取 | 如「最近 120 根」 |
  | 上次运行 | 时间与结果；运行中显示进度条 |
  | 下次运行 | |
  | 已归档 | 已封存的数据时间范围、文件数、总行数与大小；暂存中的行数 |
  | 线上保留 | 如 `7 天`、`永久` |
  | 健康 | 正常 / 需关注 / 异常（规则见第 13 节） |
  | 操作 | 立即运行、补拉区间、编辑、停用 / 启用、删除（仅无分区时可用） |

- 新建 / 编辑任务（对话框）：
  1. 选择采集任务：只列出结果为时序数据集、且尚未建立归档的任务（任务名来自 Collector 的任务列表）；
  2. 调用 `PrepareArchiveTask`，展示「频率 1m，按日分区；线上保留 7 天，最早可回补到 2026-10-10」，并填入推荐的执行计划和 N；
  3. 执行计划：预设（每 N 分钟 / 每 N 小时 / 每天 / 每周 + 时刻）或 cron；输入时调用 `PreviewArchiveSchedule`，
     实时显示校验结果、接下来 5 次运行时间和落在避让区间的提示，执行计划变化时同步更新推荐的 N；
  4. 开始时间：单选「立即开始」（默认，保存后马上运行一次）或「指定时间」；
  5. 每次拉取根数 N（显示推荐值和「至少覆盖 2 个执行间隔、回看 1 小时」的说明）、回补起点（可选）。
- 停用的任务点「启用」时，同样可以勾选「立即运行一次」。
- 详情抽屉：
  - 汇总卡片：已封存的数据时间范围、文件数、总行数、总大小、暂存中的行数、最近一次成功运行、无法补齐的区间；
  - 月历视图：每天一格（月分区任务按年展示月格），分为暂存中、已封存、无数据三种状态；当天有无法补齐的区间时标红；
  - 点击格子：状态、行数、标的数、数据时间范围；已封存的再显示文件位置（`worker_id` + 完整路径）、大小、sha256、封存次数、预览；
  - 该任务的运行记录列表。

**运行记录**

表格：计划时间、任务、类型（定时 / 手动 / 补拉区间）、状态、耗时、标的进度、请求数、读取字节、读取 / 新增 / 变更 / 丢弃行数、
补读标的数、封存分区数、说明；按任务、类型、状态筛选。有排队中或运行中的记录时每 5 秒刷新，可取消。

### 12.3 文件下载

文件在 worker 机器的本地磁盘上，控制台不提供下载：管理网关是 JSON RPC，单个响应有大小上限，且编译机不接受入站连接。

## 13. 监控与告警

mgr 的 `/metrics`：

- 按任务：最近一次成功运行时间、最近一次运行耗时、连续跳过次数、暂存中的行数、无法补齐的区间数；
- worker：最后心跳时间、磁盘可用量、正在执行的运行数；
- 运行：按类型和结果计数，请求数与读取字节；全局触发器的执行耗时。

任务健康等级（列表与总览共用）：

| 条件 | 等级 |
| --- | --- |
| 最近一次成功运行距今超过「线上保留期 − 2 天」；有无法补齐的区间；有到期运行时活动 worker 离线超过 30 分钟 | 异常 |
| 最近一次运行失败；连续跳过 3 次以上；运行耗时超过执行间隔的一半 | 需关注 |
| 其他 | 正常 |

Monitor 增加两条告警：「归档即将来不及（接近线上保留期）或出现无法补齐的区间」（critical）、
「归档运行失败或 worker 离线超过 30 分钟」（warning）。

### 14.1 worker 配置（`config/app.yaml`，示意）

```yaml
gateway_client:
  access_address: <access 主机>:11004
  access_id: access@<主机ID>
  caller: archive-worker
  key_id: ""                          # Admin 分配
  key_file: ../secrets/access-archive-worker.key
  compression: gzip
storage_auth_file: ../secrets/storage-primary-auth.secret
worker:
  worker_id: archive-worker@mooyang-X99
  root_dir: /data/moox-archive         # 部署时指定
  compression: gzip
  min_free_bytes: 5GB
  heartbeat_interval: 10s
  pull_interval: 5s
pacing:
  request_seconds: [25, 55]            # 每分钟内允许发起请求的秒区间
  hour_quiet: ["58:00", "04:00"]       # 每小时内不发起请求的区间
  request_interval: 200ms
  max_bytes_per_second: 512KB
  max_concurrent_runs: 4
  max_runs_per_data_node: 2
  latest_batch_subjects: 50            # 最近 N 根每批最多标的数（Storage 上限 100）
  latest_batch_rows: 20000             # 每批标的数 × N 的上限（与 Storage 上限一致）
  catchup_page_rows: 2000
  max_batch_rows: 200000               # 一批补读的行数上限，超过时切分时间范围
health:
  addr: 127.0.0.1:11418
```

### 14.2 mgr 配置

`config/app.yaml`：`gateway_client`（caller `archive-mgr`）、数据库路径、运行租约（10 分钟）、worker 接管等待（45 秒）、
运行记录保留（成功的定时运行 30 天，其余 90 天）、执行计划规则（最短间隔 5 分钟、N 上限 10000、最少回看时长 1 小时），
避让区间的提示规则与 worker 的 `pacing` 默认值保持一致。

`config/trpc_go.yaml` 中的两个定时器：

```yaml
- name: trpc.moox.archive.mgr.trigger.timer
  network: "* * * * * *"               # 每秒：触发到点的任务
  protocol: timer
  timeout: 900
- name: trpc.moox.archive.mgr.maintain.timer
  network: "13 * * * * *"              # 每分钟第 13 秒：回收租约、刷新数据集信息、清理记录
  protocol: timer
  timeout: 50000
```

### 14.3 部署

- **mgr**：加入 control 的原生放置（`[placements] control = [..., "archive-mgr"]`），随 control 单元安装；
  数据目录 `data/archive-mgr`，只存元数据，占用很小。
- **worker**：新增 `scripts/deploy/deploy-archive-worker.sh`，用法参照 `deploy-factor-engine.sh`，在目标机器上执行：
  `--dir`（安装目录）、`--root-dir`（归档目录）、`--worker-id`、`--access-address`、`--access-id`、`--access-key-id`；
  Linux 用 systemd 用户服务、macOS 用 launchd 托管，并等待 `/readyz`。部署目标由在哪台机器执行脚本决定。
- **本次部署**：worker 装在编译机 `mooyang-X99`（192.168.0.103），与因子引擎同机、共用同一个 Access。
  编译机断电或断网时，恢复后的第一次运行会自动补读中断期间的数据；中断不超过 crypto 1m 的保留期（7 天）就不会丢数据，
  接近保留期时会先告警。
- 凭据：`moox-admin-cli keys export --caller archive-worker` 生成外部身份密钥，`keys export-access` 重新导出 Access 校验文件并部署 Access；
  mgr 的内部身份 `archive-mgr` 随 control 部署分发。

## 15. 容量与耗时估算

按以下规模估算，仅用于判断量级：stockcn 1m 约 5000 个标的，crypto 1m 约 500 个；Access 往返每次约 0.4 秒；按 S-2 落地后的读取代价。

| 项 | crypto 1m（每小时，N = 120） | crypto 1m（每 5 分钟，N = 65） | stockcn 1m（每天，N = 480） |
| --- | --- | --- | --- |
| 每批标的数 | 50 | 50 | 41 |
| 每次请求数 | 约 10 | 约 10 | 约 120 |
| 每次读取行数 | 约 6 万 | 约 3.3 万 | 约 240 万 |
| 每次耗时 | 约 1 分钟 | 约 20 秒（不撞避让区间时） | 约 35 分钟（受带宽上限约束，17:04 开始，17:40 前后结束） |
| 每天读取行数 | 约 144 万（24 次） | 约 940 万（288 次） | 约 240 万（1 次） |
| 每天下行流量（gzip 后） | 约 60MB | 约 380MB（平均约 35Kbps） | 约 100MB |
| 每年磁盘（gzip 后） | 约 5GB | 约 5GB | 约 5GB |

- 每天新数据 crypto 1m 约 72 万行。每小时运行时每根读 2 次；每 5 分钟运行时为了回看 1 小时，每根约读 13 次。
  后者的绝对量仍很小（DataNode 平均每秒约 110 行），但如果对时效没有要求，每小时运行更省。
- 一次查多个标的之后，stockcn 每次运行的请求数从约 5000 降到约 120，耗时从约 2 小时降到约 35 分钟，瓶颈从 Access 往返变成带宽上限。
- 暂存区让正式文件每个分区只写一次：每 5 分钟运行时，如果每次都重写当天的文件，一天要重写 288 次（每次十几 MB 的解压、归并、压缩）。
- 新建任务填回补起点时，首次运行按天分段补读：stockcn 1m 补 45 天（约 31 个交易日）约 3700 万行、解压后约 7GB，
  受带宽上限约束约 9 小时完成；补读期间该任务后续的计划时刻记为跳过。

## 18. 已确认与待确认

已确认：

- 定时拉取，整体替换现有事件式 archive 模块；不订阅 EventBus；
- 用户为每个数据集设定定时归档任务（执行计划、开始时间），每次拉每个序列最近 N 根；不同数据集的任务可以并发；
- 开始时间可选「立即开始」；crypto 等全天交易的空间默认全天按小时备份；
- 最短执行间隔 5 分钟，mgr 用一个每秒触发的 trpc timer 作为全局触发器；
- Storage 的「最近 N 根」本次扩展为一次查多个标的，并同时修复读取路径的 S-1、S-2；
- worker 的部署目标可配置，本次与编译机同机；
- 文件为 gzip 压缩的 CSV，按 UTC 日 / 月分区，分区不再变化后才封存，本地只增不删；
- 界面入口先只提供采集结果，数据模型按数据集设计。

落地时需确认：

- 多个 selector 加 `time_range` + `after_key` 翻页的语义（补读、首次回补与补拉区间依赖它）；
- S-2 的前后对比 benchmark，以及 S-3 是否单独排期；
- 编译机归档目录所在磁盘的容量。
