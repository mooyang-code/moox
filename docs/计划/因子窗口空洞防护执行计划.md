# 因子窗口空洞防护执行计划

> 状态：设计定稿（已吸收六轮独立评审，恢复部分已按「个人项目、简洁可维护」简化），尚未实现。评审意见的处置见第 7 节。

## 1. 目标与原则

K 线可以延迟，但**因子的回看窗口里不能有空洞**：因子取回看窗口内的行做滚动计算，中间缺了几根时，计算照常给出一个看似正常的数，并一路传到策略和下单。

- 采集侧负责「防」和「补」：自动补采每 5 分钟一轮（见[采集](../模块/采集.md)）。
- 因子侧负责「不信、不算」：窗口有洞，该标的该因子当期不输出结果，按失败标的上报，并用 `gap_subjects` 标明原因。
- 策略侧负责「不因数据故障交易」：空洞缺数的持仓保持不动，不开新仓。
- 补采补上缺口后，自动重算被跳过的周期，只补历史因子，不触发交易。
- 每一次跳过都永久可追溯。
- 无需兼容历史；沿用现有的失败标的口径与重算作业，不新增并行机制。

### 1.1 背景与取舍（给后来的维护者）

**为什么要做**：窗口中间缺了几根，因子照样算出一个看似正常的数，再一路传给策略和下单；整条链路没有任何环节会发现它是错的。K 线空洞有两类来源：采集失败（函数超时、网关超时、行情源故障），以及标的新上市（上市前本来就没有数据，不是空洞）。

**两种处理方式，选了「跳过该标的」**：

| 方式 | 做法 | 结论 |
|---|---|---|
| 跳过 | 这个标的当期按缺数处理，因子、策略、下单照常推进 | 采用 |
| 阻塞 | 整条链路等空洞修复后再继续 | 不采用 |

不采用阻塞的原因：
- 周期整体推进，一个周期约 500 个标的，一个标的的空洞会拖住其余 499 个。
- 修复要等 5～15 分钟（补采 5 分钟一轮，加复查与重算），1 分钟周期里结果早已过期，行情已变，多半不能下单。
- 一个空洞影响此后一整个回看窗口那么多期，阻塞等于把策略挂起几十期。
- 「等一会儿，超时就丢」等价于一开始就跳过。

**跳过要有两道保护，否则跳过本身会造成损失**：
1. 策略把缺数的持仓当作退出（signal 规则）或移除（rank 规则）。因数据故障强制平仓，比少开一次仓更糟，所以空洞缺数必须与其他缺数区别对待，持仓保持不动（见 3.7）。
2. 缓存、预热、补算都会绕开检测。必须覆盖所有读窗口的入口，否则空洞会以普通失败的面目回来，保护失效（见 3.2）。

**零成交分钟不是空洞**：币安现货对零成交的分钟也返回 K 线（开高低收等于前收、成交量 0），冷门币不会因此产生空洞，采集侧不需要合成平 K 线。

## 2. 现状（已核实）

| 项目 | 现状 |
|---|---|
| 窗口读取 | 因子按应有时间区间读取行并过滤，**不检查区间内每个应有点位是否存在**；`pipeline/plan.go` 只依据事件里的 `UpstreamFailed` 排除标的 |
| 滚动因子对不足窗口 | 因子本身不拒绝回看不足，例如 `QuoteVolumeMean.py` 用 `min_periods=1`，窗口缺行时仍输出数值 |
| 失败上报 | 已有「按因子、按标的」失败（`markFactorSubjectFailure`、marker 的 `FailedSubjects`）；失败的因子字段写 NULL、状态失败，源列和其他因子的结果行仍保留 |
| 序列身份 | 同一标的一帧里可含多个 `series_tag`，因子按 `series_tag` 分组计算 |
| 实时窗口缓存 | `pipeline/window_cache.go` 缓存每个标的已读窗口，之后只读最后一根；生产固定开启后台预热（`engine/runtime.go` 的 `BackgroundWarmup: true`），缓存缺失的标的当期被当作预热中标的、当期不读完整窗口；`load.go` 的 `warmup` 直接写缓存，没有窗口检查 |
| 实时与补算窗口 | 实时 `Plan.TargetStart` 是最大回看窗口的起点；补算的 `TargetStart/TargetEnd` 是输出区间 `[start,end)`，`readWindowStart` 另外向前读回看前缀，时间序列因子一次计算整个分块，结果与失败状态没有按周期拆分 |
| 补算的全集 | `recalcexec` 把重算请求里的标的直接当作 `Expected` 全集；截面因子只给一个标的会被当作完整截面 |
| 重算作业 | `Submit` 对相同请求 ID 返回原作业；引擎只领取 `accepted` 和租约过期的 `running`，`failed`/`succeeded` 不会再被领取；作业走到区间终点就报成功，即使结果是 degraded |
| 补算的 marker | 补算模式不写 `FactorPeriodComputed`，只产生 `DatasetRowsUpserted`；同一事件 ID 的 marker 内容不同会冲突，不能改写 |
| 策略对缺数 | 有缺数集合 M(r) 和 `too_many_missing` 守门；单个标的缺数时，signal 规则 exit 输入缺失的持仓按清仓处理，rank 规则延续期间缺数的持仓被移除、份额留作现金；原因只记第一个缺失列 |
| 策略的持仓状态 | `RuleState` 对 signal 和普通 rank 只保存 `Held` 名单，没有各规则上期的贡献权重 |
| Trade | 按「目标权重 × 当前权益 ÷ 价格」换算数量；目标里缺该标的或目标为 0，`nextLaneAction` 会把已有持仓减掉 |
| 采集补采 | 自动补采从扫描水位向前重叠 5 分钟扫；补采后仍缺的单根会被记为「行情源没有」并按成功结束，水位照常推进；水位之外的旧缺口不会被扫到 |
| 周期时钟 | `periodclock.ForSpace` 只支持 `crypto`；`pipeline.periodRange`、`recalcexec.chunkEnd` 还通过固定 `Duration` 推进周期 |
| 零成交 K 线 | 币安现货：2026-10-13 在控制机上取 24 小时成交额最低的 10 个 USDT 交易对各 1000 根 1 分钟线，区间内缺失均为 0，零成交根占 44%～90%。永续接口控制机直连不通，**未验证** |
| Storage 缺口 | 同日现货 1 分钟共约 21.7 万个应有点位只缺 150 个，全部是 00:52Z 这一分钟，是一次采集故障 |

## 3. 设计

### 3.1 检测并跳过（引擎）

- **位置**：读完窗口、合并缓存前缀之后，计算之前。
- **粒度**：因子 × 标的 × 序列（`series_tag`）× 目标周期。对每个因子，取 `clock.Window(t, freq, 该因子回看根数)` 作为目标周期 `t` 的应有时间点，与该序列读到的时间点逐个比较；缺任何一个，该因子对该标的当期失败，字段写 NULL，状态失败，`gap_subjects` 记入该标的。同一标的的多个序列各自比较后再汇总，不能把不同序列的时间点取并集。
- **按因子各自的回看长度判断**：短回看因子不受长回看窗口里的洞影响。
- **窗口头部缺失**：只有同时满足「该标的有上市时间或首根 K 线时间的记录」且「缺失的点位早于它」才按新上市放行；没有依据按空洞处理。（因子本身不拒绝回看不足，不能依赖因子兜底。）
- **目标周期本身**：目标行缺失而上游没有报失败时，同样按空洞处理，不能只依赖上游标记；补算没有上游失败名单，必须自己判断。
- **补算逐周期判断**：对每个输出周期 `t` 检查 `Window(t, freq, L)`。长度为 `L` 的时间序列因子，一个缺口只影响缺口之后的 `L` 个周期，其余周期照常计算并写入；结果和失败状态必须按周期拆分，不能把一次失败放进整个分块的错误里。
- **截面因子**：
  - `AllowPartialUniverse=false`：沿用整因子 `skipped`，不能改成单标的失败。
  - `AllowPartialUniverse=true`：实时时按剔除空洞标的后的全集构造 panel。
  - **恢复时两种都用目标周期冻结的全集**：取该周期 marker 里的 `UniverseSubjectIds`，不用当前标的池，也不用请求里的单标的当伪全集；`false` 的因子恢复时全集必须完整可算，`true` 的因子更新所有受影响标的。
- **已写入的错值与目标键**：若补算时窗口仍有洞，该因子字段写 NULL 失效，不能仅省略字段而留下旧的错值。现有 `Assemble` 只枚举读到的源行，目标源行不存在时无法清掉该键已有的值，所以组装要改成按「应有网格（目标周期 × 已知序列）」枚举，缺失的目标键也写 NULL。**因子可以输出派生的 `series_tag`**（`pipeline/output_test.go`），所以失效范围不能只按源序列枚举：因子失败时，先读出该因子、该标的在目标周期上**已经存在的结果键**，对这些键全部写 NULL，再加上源网格里的键。实时周期首次计算时没有已存在的结果，这一读取是空的，没有额外代价；补算和恢复时这一读取保证旧错值被清掉，不依赖引擎重启后是否还记得输出序列。已存在结果里从未出现过、又不在源网格的键，没有错值可清，不需要处理；因此不再有「已知限制」。

### 3.2 缓存与预热（必须同步处理，否则保护失效）

- 检测发现有洞的标的不写入实时缓存，并清掉它已有的缓存；`Load` 和后台 `warmup` 两个写缓存的入口都要做检查。
- **区分「首次预热」与「空洞恢复」**：恢复期间标的的失败原因保持 `gap`，不能退化成普通预热失败，否则策略看到 `factor_failed` 会按原规则退出。恢复期间短回看因子继续计算，只有窗口含洞的因子跳过。
- **缓存代次**：缓存失效时递增代次，在途的旧预热结果写回前校验代次，防止把被清掉的缓存重新写回。
- 有洞的标的每期多读一次完整窗口，数量少，可以接受；长期有洞的标的变多时改为退避重试。

### 3.3 标记：让下游知道「这是空洞」

- 因子状态新增 `gap_subjects`：失败标的中因窗口空洞失败的那部分子集，仍同时出现在 `failed_subjects` 里。
- **协议**：`modules/factor/proto/factor.proto`、`modules/storage/proto/dataset_markers.proto`、`packages/storagepb/storage_events.proto`；只新增字段。
- **手工转换必须同步**：`storageio.markerToProto`、`BuildFactorPeriodComputedMessage`、DataNode marker 查询的反向转换、`runTracker`、`factorwire`、View 的就绪状态。新增 proto 字段不会自动穿过这些重建对象的代码，要有端到端测试覆盖。
- **marker 里的 `gap_subjects` 是下游读取的就绪事实，不是审计来源**：它不含首次缺失点位、`series_tag`、发现时间，数据集删除时 marker 也会被清掉；审计与恢复用引擎本地的账本（见 3.4）。原 marker 不改写。

### 3.4 恢复：引擎本地账本 + 定时只填充重算

**取舍**：不做 mgr 表、不新增接口、不做作业状态机。恢复完全在引擎进程内完成，复用补算执行器的计算与写入代码，不经过 mgr 的作业队列。引擎是单实例部署（目前就是这样）；多实例同时跑只会重复计算，不会写坏数据（见下文幂等）。

**账本**：引擎每次因空洞跳过，向本地追加文件 `factor-gap-YYYYMM.jsonl`（按月一个文件，永不自动删除）写一行，事件类型：

| 事件 | 含义 | 主要字段 |
|---|---|---|
| `skip` | 因空洞跳过 | 集合、因子、标的、周期、序列、缺失时间点、定义哈希、触发事件 ID、时间 |
| `repaired` | 已补齐并写入 | 集合、因子、标的、周期、时间 |
| `cancelled` | 因子定义已变更或因子、标的已不在范围，不再恢复 | 同上 + 原因 |
| `gave_up` | 超过期限仍补不上 | 同上 |

账本同时是**永久审计**（用 DuckDB 的 `read_json_auto` 或 `jq` 直接分析空洞频率、集中的标的和时段、从发现到补齐的耗时）和**恢复的待办来源**：引擎启动时**回放全部账本文件**（体量很小），重建内存里的待恢复集合：条目以 `(集合, 因子, 标的, 周期, 定义哈希)` 为唯一键，有 `skip`、尚无 `repaired`/`cancelled`/`gave_up` 的算待恢复；其中已超过期限（停机期间超期的也算）的，立即追加 `gave_up` 并告警，不会因为停机而无声消失。末尾被崩溃截断的半行直接忽略；同一条目的重复 `skip` 按唯一键合并。

**定时只填充重算**（引擎每 5 分钟一轮）：

1. 对待恢复条目里「已经过了 5 分钟」的，按集合和标的合并，用小范围读取检查缺失的时间点是否已补上。**先取得集合锁，再校验**定义哈希与范围，避免校验之后定义又变了。
2. 已补上的，在进程内对这些（因子、标的、周期）做重算，**只填充**：窗口检查通过才计算并写入，仍有洞就什么都不写（该键最初跳过时已写成 NULL）。合法的 NULL 输出照常写入。**完成判据是逐「因子、标的、周期」计算成功且写入确认**，不能把整次执行 `err == nil` 或结果 degraded 当作修复成功；确认后追加 `repaired`，从待恢复集合移除。
3. 条目的定义哈希与因子当前定义不同：追加 `cancelled` 并丢弃；这些周期按新定义算出的历史，由定义变更时人工发起的补算负责（现有流程），本机制不接管。
4. 超过 6 小时（可配）仍没补上：追加 `gave_up`，输出告警日志，提示用 `moox-cli collector kline backfill` 手工补采后，再用因子管理 CLI（`moox-factor-mgr-cli`）的 `recalc` 命令手工重算。
5. 区间终点是最后一个待补周期加一个周期（半开区间）；时间序列因子按标的恢复；截面因子用该周期 marker 里冻结的 `UniverseSubjectIds`（通过账本里记的触发事件 ID 读取），不用当前标的池；**marker 读不到**（例如数据集被删）时无法冻结全集，直接记 `gave_up`（原因 `universe_unavailable`），交给人工。

**幂等与并发**：
- 写入的提交 ID 由「集合、因子、标的、周期区间、完整定义哈希、**本批写入内容的摘要**」确定（沿用现有的内容寻址方式）：Storage 对「同 ID、不同请求体」报冲突而不是去重成功，所以 ID 必须随内容变化；内容相同的重复提交由提交回执去重。写入后、追加 `repaired` 前崩溃：重启回放后重做，重算结果相同则回执去重，不同（例如源数据被更正）则按新内容写入，都无害。
- **落盘顺序**：`skip` 先追加并 fsync，再写周期 marker 与确认事件；崩溃后事件重投，同一条目按唯一键合并，不会丢账。
- 填充与实时周期、人工补算共用每个集合的锁（`setlock`），同一集合内不会交错写入；同一进程内没有并行的旧新两次执行，所以不需要租约、attempt 或提交回执查询。
- 「只填充、从不写失效 NULL」限定为空洞失效用的 NULL；失效 NULL 只由实时周期和人工补算写入。
- 残余风险：引擎在写请求在途时被重启，旧请求迟到送达，恰逢源数据被更正。概率极低；写入的仍是由完整窗口算出的值，不会留下 NULL 或空洞。该条目已记 `repaired`、不再轮询，不会被自动覆盖，怀疑时由操作员人工补算。

**只修历史，不触发策略**：恢复只写历史因子行，原 `FactorPeriodComputed` marker 不改写。补算产生的是 `DatasetRowsUpserted`，View 应用它只更新索引，不会创建新的 `ViewDataReady`；新就绪只由 `FactorPeriodComputed` 创建，且已处理的周期有去重，所以已提交的周期不会被重新评估。原就绪事件还没被策略消费时，策略首评可能读到恢复后的值，这是允许的（数据更正确）。

**对补算执行器的改动（`recalcexec`）**：它不依赖 mgr 的作业存储，已有 `Run`/`RunChunk`、锁和回调，可以进程内复用，mgr 的调用集中在 `engine/recalcloop.go`，本地账本回调替代之即可。但有两处必须改：(a) 现有执行计划默认 `WriteCarry=true`，组装会预置失败 NULL，需要新增「只填充」写入策略，不预置失败 NULL；(b) `Outcome` 没有逐周期的完成信息，需要新增逐「因子、标的、周期」的结果，账本据此判断完成。

时延预期（补采正常时）：补采 5 分钟、恢复轮询 5 分钟，缺口出现到因子补齐大致 5～15 分钟。

### 3.5 日志与监控

- 引擎每次跳过除写账本外，输出一行结构化日志 `factor_window_gap set=… factor=… subject=… period=… missing=…`，便于直接 grep。
- 指标：待恢复条目数、每小时跳过数、`gave_up` 数；`gave_up` 或待恢复条目持续增长时告警。
- 账本写失败（磁盘满等）：记错误日志与指标并让引擎健康检查降级，周期推进不受影响；该期缺口仍体现在 marker 的 `gap_subjects` 里供人工核对，但不保证能完整重建。

### 3.6 Collector：因子发现的缺口怎样补上

不新增自动联动。自动补采每 5 分钟一轮，覆盖绝大多数采集失败造成的缺口（见[采集](../模块/采集.md)）。它覆盖不到的情形（水位之外的旧缺口、行情源确实没有、不在计划覆盖内）由 3.4 的 `gave_up` 告警暴露，由操作员手工补采；不改 Collector 的补采入口，不增加来源参数。文档里不再写「空洞只来自采集失败」。

### 3.7 策略与下单：空洞缺数的持仓保持（方案 A：数量不动）

**原则**：因空洞缺数的标的，**已持有的数量不动，未持有的不开新仓**，其他标的照常按规则调仓。

**预算口径与谁来执行**：保持中的标的**不退出总仓位**，它占用的敞口仍计入预算，其余标的在剩余额度内按各自权重调仓。

- 策略在目标里声明总预算 `B`，并为每个保持标的给出预留权重 `r`（取该标的在该规则上期的贡献权重，需要持久化）；其余目标按 `B − r` 分配。
- **最终的预算约束由 Trade 执行**。记号：`R` 是全部保持标的的预留权重之和，`A` 是它们的实际权重之和，均按绝对值（总敞口口径，与策略的 gross 约束一致）汇总；其余正常目标的总敞口 `S ≤ B − R`，且已经过策略的 cap 处理。Trade 取缩放系数：
  - `R < B` 时 `f = min(1, max(0, (B − A) ÷ (B − R)))`，其余目标整体乘以 `f`；
  - `R ≥ B`（预留已用满，其余目标本来就是 0）时不做缩放；
  - **只缩小，不放大**：`A < R`（保持仓位的实际占比低于预留）时 `f > 1`，取 1，多出的额度留作现金，不放大已经落实过 cap 的目标，否则会突破策略设定的上限；
  - `A ≥ B`（保持敞口已用满或超出预算）时 `f = 0`，其余目标按 0 处理，**不会为了回到预算而强制减保持仓位**，并写告警日志。
- 在 `R < B`、`A < B` 时，缩放后 `A + S × f ≤ B` 成立，总敞口不超预算。
- 不这样做，实际占比上涨后偏差不会自动消除，其余标的会按过期的预留权重建仓。

**保持的生效边界**：

- **保持是标的级的**：任一规则因空洞保护某标的，该标的整个数量冻结；其他规则对它的贡献不再生效，也不再被选入，它的占用按实际权重计。
- **订单**：Trade 收到保持目标时，撤销该标的未成交的调仓单，且不再新增；撤单期间已成交的部分接受。「数量不动」指不因新的决策改变，不承诺撤单窗口内的成交也被阻止。
- **整期跳过的情形**：`too_many_missing` 守门或严格截面因子整因子 `skipped` 时，策略整期跳过、不发新目标，保持标记发不出去；此时 Trade 按已有目标继续执行（现有行为，不新增也不声称保持）。文档与验收都按这个口径。

**实现要点**：

- **原因收集**：对规则实际需要的全部输入收集缺失原因，不能只看第一个。**只有全部缺失原因都是空洞（`factor_gap`）才触发保护**；混有独立的无行、值为空、`factor_failed`、`source_failed` 时按原规则处理。
- **空洞造成的 NULL 或无行由空洞证据解释**：现有 `partitionRule` 在读取失败原因之前就对无行直接返回 `no_row`，要改成先检查失败列，空洞造成的无行或 NULL 归因为 `factor_gap`，不能再被当成独立的普通缺失而取消保护。
- **上一根的原因**：`bars[-1]` 的空洞要传递，否则本期窗口已完整、上一根因子仍为空时，会被看成普通缺数而重新触发退出。读取上一期的就绪状态与 `gap_subjects`。
- **状态**：`RuleState` 增加各规则上期对各标的的贡献权重，供冻结使用。
- **signal 规则**：冻结缺口持仓的贡献权重，剩余预算在其余标的中再分配；不判 exit。signal 的持仓只判 exit，仍只检查 exit 引用的列。
- **rank 规则**：覆盖普通 rank、buffer、holding 延续和到期重建。冻结部分预留名额和预算份额，避免正常候选补满后再叠加冻结部分；holding 批次到期重建时冻结部分不丢。
- **多规则合成**：冻结按标的汇总；cap、gross、现金和量化作用于其余标的，不缩放冻结部分。
- **守门**：保护中的标的仍计入缺数比例（`too_many_missing`），不能伪装成可用；解释明细只生成一条记录，标注「空洞保持」。
- **Trade 协议**：目标新增「保持」标记，Trade 对该标的不生成加仓或减仓；**不能靠省略目标实现**（省略会被当作目标 0 而减仓）。已有未成交订单的处理沿用现有逻辑，需在实现时核实。
- **范围外**：退市、移出池的标的是否仍保护，实现前按业务确认，默认不保护。

### 3.8 不做的事

- 不在采集侧合成平 K 线。
- 不做 mgr 的审计表、新接口、作业状态机、attempt 与租约、提交回执查询：恢复在引擎进程内完成。
- 不做 Collector 的自动定向补采联动。
- 不把持仓保护扩展到 `source_failed`、`factor_failed` 等其他原因（见第 6 节）。
- 重算不重写原 marker，不触发策略重新评估已提交的周期。

## 4. 实施顺序

上线门槛是**下游保护就绪**，不能先开检测：否则有持仓的标的会被清仓。

0. **协议与转换**：`gap_subjects` 的 proto、生成代码、全部手工转换，端到端测试。
1. **策略与 Trade**：`factor_gap` 原因、上一根传递、`RuleState` 贡献权重、持仓保持（signal、rank、合成）、Trade 的保持标记与预算缩放；先上线 Trade，再上线策略。
2. **引擎**：窗口检测、缓存与预热处理、组装按应有网格写 NULL、账本与日志、恢复轮询（只填充重算）；先在隔离环境验证，**最后上线并开启**。
3. **验证（开启前）**：在隔离环境注入缺口并走完「跳过 → 补采 → 恢复 → 因子补齐」；生产只做受控演练。生产删单根 K 线目前没有对应接口（`PrimaryDeleteDatasetRowsReq` 只有数据集粒度），演练方法要先确定，暖缓存可能让已删的根仍在缓存里，演练未必触发检测。永续接口的零成交行为在目标环境确认。

部署顺序遵循「消费者先于发布者」：Storage、策略、Trade 先上，引擎最后；**mgr 与 Collector 无改动**。旧中间节点可能丢掉 `gap_subjects`、旧策略仍会退出，所以不能只用「新增字段兼容」判断业务安全。

## 5. 验收矩阵

- 检测：中间缺一根、头部缺失（有无上市依据）、目标行缺失、多 `series_tag` 交错缺失、不同回看长度、`min_periods=1` 因子。
- 补算：逐周期部分恢复、分块前缀与边界、窗口仍有洞时写 NULL 失效、单期请求区间。
- 缓存：预热原因保持、清缓存与在途预热并发写回、`Load` 和 `warmup` 两个入口。
- 截面：`AllowPartialUniverse` 的严格与部分两种、实时与补算。
- 恢复：账本回放重建待恢复集合、写入后追加 `repaired` 前崩溃的幂等重做、超期 `gave_up`、定义变更后 `cancelled`、同一周期多个因子的缺口、只填充不写失效 NULL。
- 策略：signal 权重变化、rank 到期重建、多规则合成、上一根空洞、混合原因、守门比例、实际订单数量（保持标的数量不变）。
- 下游：Primary 写入、View 可读、账本完整、原策略决策不被重写；原就绪事件延迟消费时策略首评读到恢复值。
- 截面恢复使用冻结全集。
- 审计：账本写失败时的降级与告警。
- 组装：目标键缺失写 NULL 清旧值、序列完全消失的限制与告警。
- 保持：跨规则同一标的、空头与超预算、保持敞口 `a ≥ B`、撤单期间成交、守门或严格截面整期跳过时旧目标继续执行、`no_row` 由空洞证据归因。

## 6. 风险与待核实

- **已决定：保护只认 `factor_gap`，不扩展到 `source_failed` 等其他原因**。`source_failed`（目标 K 线缺失，由 Collector 的周期状态声明失败）对有持仓的标的同样会触发退出，危害与空洞相似；但大面积采集故障已有 `too_many_missing` 守门整期跳过，单标的的故障最坏是少持一期、下一期数据恢复即回来；而扩展会把 Collector 的周期状态与因子失败都接进策略的原因判定，混合原因的优先级、持仓保持的触发条件都更复杂。个人项目优先简洁可维护，这个极小概率的损失可以接受。若以后发现实际损失不小，再扩展。
- **持仓保持是交易语义变更**：signal、rank、合成、Trade 四处联动，必须单独设计评审并充分测试，是这份计划里风险最高的部分。
- **贡献权重的持久化口径**：保持标的占用权重取上期贡献，价格漂移的偏差大小需要用回放验证。
- **已有未成交订单**：保持标记下的处理要读 Trade 现有逻辑后确定。
- **账本的存放与备份**：账本在引擎主机本地，按月一个文件、永不自动删除；引擎主机迁移时要带走，并纳入已有的备份范围。
- **A 股**：补交易日历的 `Window` 之外，还要检查周期迭代、补算分块和结束边界，本次不实现。
- **有洞标的的读取开销**：见 3.2。
- **采样证据**：零成交与缺口统计限于已采样的现货范围，不作为全市场保证。
