# 因子窗口空洞防护执行计划

## 1. 目标与原则

K 线可以延迟，但**因子的回看窗口里不能有空洞**：窗口按根数取最近 N 根，中间缺了几根时，因子会用不连续的数据算出看似正常的值，并一路传到策略。

- 采集侧负责「防」和「补」：自动补采已改为每 5 分钟一轮、1 小时窗口、批量读取（见[采集](../模块/采集.md)）。
- 因子侧负责「不信、不算」：窗口有洞就不输出该标的该因子该期的结果，按失败标的上报，策略自然读不到。
- 补采补上缺口后，自动重算被跳过的周期，不靠人工。
- 无需兼容历史，沿用现有的失败标的上报口径和重算作业，不新增并行机制。

## 1.1 背景与取舍（给后来的维护者）

**为什么要做**：因子按「最近 N 根」取回看窗口。窗口中间缺了几根，因子照样算出一个看似正常的数，再一路传给策略和下单；整条链路没有任何环节会发现它是错的。K 线空洞的来源有两类：采集失败（函数超时、网关超时、行情源故障），以及标的新上市（上市前本来就没有数据）。后者不是空洞。

**两种处理方式，选了「跳过该标的」**：

| 方式 | 做法 | 结论 |
|---|---|---|
| 跳过 | 这个标的当期按缺数处理，因子、策略、下单照常推进 | 采用 |
| 阻塞 | 整条链路等空洞修复后再继续 | 不采用 |

不采用阻塞的原因：
- 周期是整体推进的，一个周期约 500 个标的，一个标的的空洞会拖住其余 499 个。
- 修复要等 5～15 分钟（自动补采 5 分钟一轮，加上复查与重算），1 分钟周期里结果早已过期，行情已变，等出来的结果多半不能下单。
- 一个空洞影响此后一整个回看窗口那么多期，阻塞等于把策略挂起几十期。
- 「等一会儿，超时就丢」等价于一开始就跳过。

**空洞必须可见、可追溯**：被跳过不是静默的。每一次因空洞跳过都会（a）在因子结果标记里与其他失败区分开，让下游知道原因，（b）永久记入审计表，供事后分析（见 3.4、3.5）。

**零成交分钟不是空洞**：币安现货对零成交的分钟也返回 K 线（开高低收等于前收、成交量 0），冷门币不会因此产生空洞，所以采集侧不需要合成平 K 线。

## 2. 现状（已核实）

| 项目 | 现状 |
|---|---|
| 窗口连续性检查 | 因子引擎没有；回看窗口按不同 `data_time` 计数，不检查是否连续 |
| 失败上报 | 已有「按因子、按标的」失败（`markFactorSubjectFailure`、marker 的 `FailedSubjects`），策略不使用失败标的的该期 |
| 实时窗口缓存 | `pipeline/window_cache.go` 缓存每个标的已读窗口，之后只读最后一根；缺口补上后，缓存里中间那段仍是旧数据 |
| 重算 | factor-mgr 的 `recalc.Service.Submit(set, factors, subjects, requestID, start, end)`，请求 ID 幂等；引擎经 `PullRecalcJob` 拉取执行 |
| 策略对缺数的处理 | 已有缺数集合 M(r)、`too_many_missing` 守门（大面积缺数整期跳过）；但**单个标的缺数时，signal 规则 exit 输入缺失的持仓按清仓处理，rank 规则延续期间缺数的持仓被移除、份额留作现金**（见 `engine/signal.go`、`engine/rank.go`）。空洞若直接并入缺数，会让有持仓的标的被误清仓 |
| 周期时钟 | `periodclock.ForSpace` 目前只支持 `crypto`，`Window(t, freq, n)` 返回连续的 n 个周期；A 股接入因子时需补日历实现 |
| 冷门币零成交 | 已核实：币安现货接口对零成交的分钟返回开高低收等于前收、成交量为 0 的 K 线（取成交额最低的 10 个 USDT 交易对，各 1000 根 1 分钟线，区间内缺失均为 0，零成交根占 44%～90%）；Storage 里 1 分钟现货共 21.7 万个应有点位只缺 150 个，且全部集中在同一分钟（10-13 00:52Z），是一次采集故障，不是行情源没有 |
| 永续接口 | 控制机直连 fapi 不通（网络不可达），未直接验证；按现货的行为推断，上线前再确认 |

结论：不需要在采集侧合成平 K 线。当前的空洞只来自采集失败，由自动补采修复。

## 3. 设计

### 3.1 检测并跳过（引擎，第一步）

- **位置**：`pipeline` 读完窗口并合并缓存前缀后、计算前。
- **判断**：对每个因子、每个标的，取 `clock.Window(T, freq, 该因子回看根数)` 作为应有时间点，与读到的行对照；窗口内部缺任何一个时间点，该因子对该标的失败，不计算、不写结果。
  - 按因子各自的回看长度判断，短回看因子不受长回看窗口里的洞影响。
  - 只看窗口内部：窗口头部缺失按新上市处理，由因子自己的「回看不足」逻辑处理。
  - 目标周期本身缺失沿用现有的上游失败标的路径，不在这里重复判断。
- **补算也用同一检查**：补算窗口有洞同样跳过，所以补算随时可提交，不会算出错值。
- **缓存**：检查发现有洞的标的不写入实时窗口缓存，并清掉它已有的缓存，下一期重新读完整窗口；没洞时才进缓存。
- **状态**：失败原因标记见 3.4，日志见 3.5；补算作业的备注里带上「窗口空洞」计数，便于排查。

### 3.2 记录、复查、重算（第二步）

状态放 factor-mgr（引擎是远程纯出站进程，库在 mgr），Storage 读取由引擎做，mgr 不新增 Storage 依赖。

1. **上报**：`EngineService` 新增 `ReportGapSkips`，引擎每期把「集合、标的、周期、缺的时间点」批量上报；mgr 写入 `t_factor_gap_skips`（`c_set_id`、`c_subject_id`、`c_period_time`、`c_missing_json`、`c_status`、`c_request_id`、`c_ctime`、`c_mtime`；`(c_set_id, c_subject_id, c_period_time)` 唯一，重复上报只更新缺失列表）。
2. **复查**：引擎每 5 分钟拉取待处理记录（新增 `PullGapSkips`），按集合和标的汇总需要确认的时间点，用小范围读取检查是否已补上。
3. **提交重算**：已补上的，按「集合 + 标的」把最早到最晚被跳过的周期合成一个区间，调用新增的 `ResolveGapSkips`；mgr 用确定的请求 ID（集合、标的、起止周期）调用现有 `Submit` 创建重算作业，并把记录标为已提交。请求 ID 幂等，重复提交不会重复算。
4. **收尾**：重算作业成功后记录标为完成；失败则保留，下一轮继续（重算本身有窗口检查，仍有洞会再次跳过并保持待处理）。
5. **保留**：记录永久保留（见 3.5）。

时延预期：补采 5 分钟一轮、复查 5 分钟一轮，缺口从出现到因子补齐大致 5～15 分钟。

### 3.4 标记：让下游知道「这是空洞」

- 因子状态里新增 `gap_subjects`：失败标的中因窗口空洞失败的那部分子集（仍然同时出现在 `failed_subjects` 里，所以不认识新字段的模块行为不变）。该字段随因子状态进入 Storage 的周期 marker、`FactorPeriodComputed` 事件与 View 的就绪状态，策略读取就绪结果时可以拿到。
- 涉及协议：`modules/factor/proto/factor.proto`、`modules/storage/proto/dataset_markers.proto`、`packages/storagepb/storage_events.proto`，以及对应的转换代码；只新增字段，旧字段含义不变。
- 策略侧把空洞映射为单独的缺数原因 `factor_gap`（与 `factor_failed`、`source_failed` 并列），结果的缺数明细里能看到。

### 3.5 永久审计

- **审计表**：第二步的 `t_factor_gap_skips` 即永久记录，**不做保留期清理**（空洞本身稀少，行很小）。每行记录集合、因子、标的、周期、缺失时间点、首次发现时间、状态（待复查、已提交重算、已完成）、重算请求 ID、完成时间，之后可以直接用 SQL 分析空洞的频率、集中的标的与时段、从发现到补齐的耗时。
- **日志**：引擎每次跳过输出一行结构化日志 `factor_window_gap set=… factor=… subject=… period=… missing=…`，便于在第二步上线前（审计表还不存在时）也能 grep 追溯。第一步先有日志，第二步补表。

### 3.6 策略侧：空洞标的的持仓保持（需要拍板）

问题：按现状，有持仓的标的一旦出现空洞（缺数），会按上面的规则被清仓或移除。因数据故障强制平仓，比少开一次仓更糟。

建议：把 `factor_gap` 与其他缺数区别对待——
- **已持有、因空洞缺数的标的：保持现有持仓**，不判 exit、不从目标里移除；
- **未持有的标的：不开新仓**；
- 其他原因的缺数（无行、值为空、`factor_failed`、`source_failed`）行为不变；
- `too_many_missing` 守门不变。

这需要改 `engine` 的集合划分、`signal`、`rank` 的组合计算，属于交易语义变更，要单独设计和测试，并且**必须在第一步上线之前完成**：否则第一步让空洞变成显式的缺数后，有持仓的标的会被清仓。

### 3.7 不做的事

- 不在采集侧合成平 K 线（冷门币接口已返回零成交 K 线）。
- 不修改策略：失败标的该期本来就不被策略使用。
- 不做引擎内存版的跳过记录：重启会无声丢失，违背目标。

## 4. 实施顺序

0. **前置（策略）**：3.6 的持仓保持，以及 `gap_subjects` 在策略侧的读取与 `factor_gap` 缺数原因。
1. **第一步（引擎）**：窗口连续性检查、按因子失败、缓存处理、`gap_subjects` 标记（协议新增字段）、结构化日志、单测（含「中间缺一根」「头部缺失」「不同回看长度」「补算跳过」「缓存清理」）。上线顺序：先上认识新字段的消费端（Storage、策略），再上引擎。
2. **第二步（mgr + 引擎）**：`t_factor_gap_skips` 表（遵循 schema 格式规范，永久保留）、`ReportGapSkips`/`PullGapSkips`/`ResolveGapSkips` 三个引擎侧接口、引擎复查循环、重算提交；部署顺序按「新增接口先上 mgr，再上引擎」。
3. **第三步（验证）**：在生产人为制造缺口（对一个标的删一根 K 线）观察「跳过 → 补采 → 复查 → 重算 → 因子补齐」全流程；确认永续接口的零成交行为。

## 5. 风险与待核实

- **迟到旧周期的下游处理**：重算会写出旧周期的因子行并产生事件，需先读策略的触发逻辑，确认旧周期事件不会让策略重新评估已提交的周期；上线第二步之前核实。
- **有洞的标的每期多读一次完整窗口**：数量少，可接受；若长期有洞的标的变多，改为按退避间隔重试。
- **A 股**：`periodclock.ForSpace` 只支持 `crypto`；A 股接入因子前需补交易日历的 `Window` 实现，检查逻辑本身与空间无关。
- **跳过期间的因子行**：这些周期在补齐前缺失，策略读到的是「失败标的」，与预热中的行为一致。
