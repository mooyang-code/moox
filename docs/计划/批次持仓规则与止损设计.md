# 批次持仓规则与止损设计

> 状态：设计稿第三版（3.1），已吸收 Codex 两轮设计审查的意见（附录 A、B）。已编码（分支 `feat/tranche`），实现与本稿的差异见附录 C；用户文档见 `docs/模块/策略.md` 的“tranche 规则”“止损止盈”“策略模板”。
>
> 目标：
> 1. 把 F1 的选币与持有方式抽象成通用的规则类型 `tranche`（批次持仓），F1 只是它的一份预设。以后同类策略写配置即可，不用改代码、不用发布。
> 2. 增加通用的**止损与止盈**环节，`rank`、`signal`、`tranche` 三种规则都能用，默认关闭。
> 3. 增加**模板库**：常用的策略骨架存成命名模板，建策略时选模板、填参数即可，不改代码、不发布。
>
> 不变：`rank`、`signal` 规则的模型与现有写法不变，止损止盈对它们只是可选的附加环节。

## 1. 现状

| 规则类型 | 适用 | 状态 | 能否配置出 F1 |
| --- | --- | --- | --- |
| `rank` | 截面打分、选前 N、配权；可选 `buffer` 或 `holding` 分批换仓 | 持有集合；分批换仓的批次 | 不能：权重按当期分数定，没有"每期开一批、按开仓数量持有 h 期" |
| `signal` | 固定池择时，entry / exit | 持有集合 | 不能 |
| `f1` | 与 alphalib F1 逐期一致 | 按排名签名分组的开仓记录 | 是，但各环节写死成 F1 的做法 |

`f1` 规则（`modules/strategy/internal/engine/f1.go`、`modules/strategy/internal/dsl/f1.go`）已经有"子策略模板 + 参数表展开"，
新增 F1 子策略本来就不用改代码；缺的是**环节里的做法不能换**，比如想按固定权重持有、或按 K 线根数计持有期，就得改代码。

## 2. 总体方案

| 层 | 内容 | 新增策略时是否要发布 |
| --- | --- | --- |
| 规则层 | `rank`、`signal`、`tranche` 三种规则类型，止损止盈是三者共用的可选环节。环节的每种做法都做成选项 | 只有需要一种**新机制**时要编码，而且只是给已有环节加一个选项 |
| 配置层 | 策略 DSL（已存库，管理台与 CLI 可改）；`tranche` 沿用参数表展开子策略 | 不用 |
| 模板层 | 命名的 DSL 骨架 + 变量与参数列定义，建策略时生成 DSL（第 6 节）。引擎不感知模板 | 不用 |

打分的灵活性主要来自因子层：任意打分逻辑先写成因子表达式（见 [因子](../模块/因子.md)），规则只负责排名、过滤、选币与持有。

**混用限制**：含 `tranche` 规则的策略只能全部是 `tranche` 规则（沿用 f1 现状，`validateF1Strategy`），不能写 `factor_params`，
整份策略不参与空洞冻结（`frozenSet` 对含 tranche 的策略直接返回空，持有到期只看候选行）。`rank`、`signal` 的混用与冻结规则不变。

## 3. `tranche` 规则

### 3.1 环节与选项

每期按下面的顺序求值。"F1 预设"列是 `preset: f1` 的取值，"通用默认"是不写 `preset` 时的取值。

| 环节 | 选项 | F1 预设 | 通用默认 | 作用层级 |
| --- | --- | --- | --- | --- |
| 1. 候选 | `candidates.require_volume` | `true` | `true` | 规则级（整条规则一个候选集 B） |
| | 名单 `long_white_list` 等 | `[]` | `[]` | 子策略 |
| | `seal999` | `true` | 无此项 | 子策略，全策略必须一致；为真时要求 `universe.min_age_bars ≥ 999` |
| 2. 打分 | `score.method` | `rank_sum` | `rank_sum` | 子策略 |
| | `score.missing` | `median` | `drop` | 子策略 |
| 3. 前置过滤 | `filter_before` | `[]` | `[]` | 子策略 |
| 4. 选币 | `long_coin_num`、`short_coin_num` | `1`、`1` | `1`、`0` | 子策略 |
| | `long_weight`、`short_weight` | `1`、`1` | `1`、`0` | 子策略；某侧权重为 0 时该侧不选币 |
| 5. 后置过滤 | `filter_after` | `[]` | `[]` | 子策略 |
| 6. 开仓 | 每期新开一批 | 固定 | 固定 | — |
| 7. 持有 | `hold_period` | `12` | 必填 | 子策略 |
| | `hold_count` | `candidate_rows` | `bars` | 子策略 |
| 8. 定仓 | `sizing.method` | `quantity` | `weight` | 子策略 |
| | `sizing.scale` | `0.5` | `1` | 子策略 |
| 9. 合成 | `stg_weight` | `1` | `1` | 子策略 |
| 10. 止损止盈 | `stop` | 不开 | 不开 | 子策略，见第 4 节 |

F1 预设的默认值与 `F1StrategyConfig` 相同（`hold_period=12`、`seal999=true`、两侧权重与个数都为 1，见 `dsl/f1.go` 的 `decodeF1Sub`）。
写出的字段覆盖预设；`preset` 只影响没写的字段。通用默认按"对新策略最不意外"来定：只做多、因子空值的标的不靠补中位数入选、持有期等于自然时间。

### 3.2 精确定义（F1 预设必须逐值一致）

以下按现有实现（`engine/f1.go`）写死语义，重构时不得改变：

- **候选集 B**：本期有行且 `close` 非空的标的，按"标的 ID 去掉 `-`"升序排列。`require_volume`：
  - 为真（F1 与通用默认）：还要求 `volume` 非空且 `> 0`；`volume` 为空算缺数，`volume = 0` 记 `idle`（`volume_zero`），既不可用也不算缺数（现有 F1 行为）。
  - 为假：不读 `volume`，有行且 `close` 非空即为候选；没有 `idle` 分类。
- **`score.method: rank_sum`**（F1 的 `cross`）：对因子列表里每个不重复的列，在 B 上求平均名次（`averageRanks`），
  `score.missing: median` 时空值补同期名次中位数（`fillMedian`），`drop` 时空值保持空、该标的本侧不参与选币。
  分数 = Σ（名次 × 权重 × 方向符号），`descending` 为真时符号为负；**是加权求和，不除以权重和**。
  多空因子列表不同时分两遍：先排多头列表的列并算多头分数，再在当前值上（共用的列已经是名次）排空头列表的列并算空头分数。
- **`score.method: raw_sum`**（F1 的 `vertical`）：直接用因子原值加权求和，不排名、不补中位数；`score.missing` 对它只决定空值是否剔除。
- **选币**：在名单与前置过滤之后的样本上按分数排名（`method='first'`，同分按 B 的顺序）：**多头按分数升序取小者，空头按分数降序取大者**
  （`firstRanks(values, !short, pct)`；`descending` 因子的方向已由符号体现）。
  `coin_num ≥ 1` 取名次 ≤ N 的标的，**分母固定为配置的 N**，选不满也不变；`0 < coin_num < 1` 是百分比，分母为实际选中个数。
- **定仓**：一条开仓记录的份额 = `scale × side_weight / h / 分母`。
  `quantity`：开仓时记下开仓 close，本期贡献 = 份额 × 本期 close / 开仓 close（权重随价格变动）；`weight`：本期贡献 = 份额（不随价格变动）。
  做空贡献取负。子策略贡献 × `stg_weight / Σ stg_weight × weight.total` 后合成，组合层截断到 1e-4（`WeightPlaces`）。
- **持有计数**：新记录开仓当期计 1。之后每期先计数、再贡献、最后清理：
  `candidate_rows` 下该标的本期在 B 中才 +1；`bars` 下按 bar 序号算年龄（本期序号 − 开仓序号 + 1）。
  计数超过子策略的 `hold_period` 时该子策略不再从这条记录取权重。
- **去重与状态键**：
  - **排名签名**（同签名的子策略每期只选一次币）包含所有影响候选、排名与选币的字段：`score.method`、`score.missing`、多空因子、名单、
    前置过滤、个数、哪一侧权重大于 0、`stop.price`（第 4.2 节）。`candidates.require_volume` 是规则级，不进签名。
  - **状态键**（StateKey，变化时旧开仓记录不再沿用）覆盖签名与组内全部子策略的全部字段（含 `hold`、`sizing`、`stop`）。
  - **记录删除**：组内每个子策略分别判断这条记录对它是否仍有效（未超过它的持有期、未被它止损），全部失效才删除。
    这替代现有"`Rows ≥` 组内最大 h 即删除"的规则；同组混用两种 `hold.count` 时也成立（记录同时保存 `rows` 与开仓 `bar`）。

### 3.3 DSL 写法

`type: f1` 删除，改为 `type: tranche`。参数表展开与占位符规则不变。FH003 改写后的示意（字段齐全、能通过校验；具体因子与参数以生产 DSL 为准）：

```yaml
name: FH003
bar: 5m
universe: {}
rules:
  - id: fh003
    type: tranche
    preset: f1
    weight: {total: 1}
    tranche:                      # 子策略模板，"{列名}" 取参数表这一行的值
      hold_period: "{h}"
      seal999: false
      long_factors: [{factor: "f1_po__{s}_{l}", descending: true, weight: 1}]
      short_factors: []
      long_weight: 2
      short_weight: 0
      long_coin_num: 1
      short_coin_num: 0
      filter_after:
        - {direction: long, factor: "f1_upper_shadow__{n2}", type: value, op: lte, value: "{p2}"}
      stg_weight: "{w}"
      # stop: {loss: 0.08, cooldown_bars: 12}   # 可选，见第 4 节
    params:
      columns: [h, s, l, n2, p2, w]
      rows:
        - [1, 65, 193, 24, 0.1, 0.0033333333333333335]
portfolio:
  leverage: 2
  max_missing: 1
```

实际改写以生产上 FH002、FH003 现有 DSL 为准，只改 `type`、规则体字段名与 `preset`，其余字段原样保留。

### 3.4 等价性验收

- 黄金用例（`engine/testdata/f1/` 的 13 个用例）与对比测试：DSL 改为 `tranche + preset: f1` 写法，**期望权重不变**，逐值一致。
- 生产等价：回放目前不支持 F1／合约 View（`rpc/replays.go`、`trigger/replay.go`），所以不用回放，改为离线回灌，不保留旧引擎代码：
  1. 重构前，用现有 `f1` 求值对从生产 View 导出的最近 2 天因子结果按 bar 顺序求值，状态逐期接力，把每期的目标权重与**归一化状态**写成本地基准文件（不进仓库）。
  2. 重构后，用 `tranche + preset: f1` 对同一份数据求值，与基准逐期比较。
  3. 归一化状态：忽略组键与状态键的取值（它们哈希了子策略结构，命名变化会改变），把每组的开仓记录展开成
     （签名对应的子策略行号集合, 开仓 bar, 标的, 方向, 开仓 close, 分母, 持有计数, 后置过滤通过位图）的多重集合比较；目标权重要求逐值相等。
- 状态格式：`RuleState.f1` 改名 `RuleState.tranche`，开仓记录增加止损字段，按项目原则不做迁移，上线时重新启用实例（第 7 节）。

## 4. 止损与止盈（三种规则共用，默认关闭）

### 4.1 配置

规则级的可选块，写在 `rank`、`signal` 规则上，或 `tranche` 的子策略模板里（可用参数表占位符）：

```yaml
stop:
  loss: 0.05            # 固定止损：相对入场价不利变动达到 5%
  trailing: 0.08        # 跟踪止损：相对此前最有利价格回撤 8%
  profit: 0.10          # 固定止盈：相对入场价有利变动达到 10%
  price: close          # close（默认）| extreme
  cooldown_bars: 12     # 触发后的冷却根数；默认 0
```

- `loss`、`trailing`、`profit` 至少写一个，可同时写，任一触发即平掉该持仓单位。`loss`、`trailing` 取值 (0, 1)，`profit` 取值 (0, 10]。
- 下文"止损"泛指三种触发。不写 `stop` 时行为与现在完全一致。

### 4.2 价格与取列

| 用途 | `price: close` | `price: extreme`（多头 / 空头） |
| --- | --- | --- |
| 入场价 | 入场当期 `close` | 同左 |
| 固定止损、跟踪止损判断 | 本期 `close` | 本期 `low` / `high` |
| 止盈判断 | 本期 `close` | 本期 `high` / `low` |
| 最有利价格更新 | 本期 `close` | 本期 `high` / `low` |

- **取列**：开了 `stop` 的规则额外读取 `close`（以及 `extreme` 时的 `high`、`low`），作为**可选列**：不进入规则的必需列，
  缺值不算缺数、不触发"持有标的缺数即清仓"。启用实例时校验绑定的 View 有这些列，没有就拒绝启用。
- **无参考价**：本期参考价为空、非有限值或 ≤ 0 时，该单位本期不判止损、不更新最有利价格。入场价缺失时不入场（与现有"无 close 不开仓"一致）。
- **冻结**：被空洞冻结的标的（只 `rank`、`signal`）本期不判止损、不更新最有利价格。
- **tranche 同组同价格口径**：`stop.price` 进入排名签名，同组子策略的价格口径相同，所以记录上共用一个最有利价格是确定的。

### 4.3 求值顺序（每期在规则求值的最前面）

1. **判断**：对每个持仓单位，用本期参考价与入场价判断固定止损、止盈；用本期参考价与**此前**的最有利价格（不含本期）判断跟踪止损。
2. **同期多触发**：止损（固定或跟踪）与止盈同时满足时按止损处理（收盘后无法知道本根先到哪一边，取保守一侧）；明细原因按 `stop_loss` > `trailing_stop` > `take_profit` 取第一个。
3. **处理**：触发的单位按 4.4 节平掉，标的写入冷却表。
4. **更新**：未触发的单位用本期价格更新最有利价格（多头取较高、空头取较低）。

跟踪止损用"此前"的最有利价格，是因为同一根 K 线里高低点的先后未知：多头若先用本根 `high` 抬高峰值，再用本根 `low` 判断，
会把先出现的低点按后出现的高点来判，造成虚假触发。例：多头入场 100，此前最高 110，`trailing: 0.08` → 止损线 101.2；
本根 `high` 115、`low` 102：用此前峰值判断不触发，之后峰值更新为 115（止损线 105.8）。空头对称：此前最低 90，止损线 97.2，本根 `low` 85、`high` 96 不触发，之后谷值更新为 85。

**冷却**：触发当期本规则不得重新入场（不论 `cooldown_bars`）。设触发的 bar 序号为 T，冷却区间是 `[T, T + cooldown_bars]` 闭区间：
`cooldown_bars: 0` 只禁止当期，T+1 起可入场；`1` 禁止 T 与 T+1；`12` 禁止 T～T+12。状态里存冷却截止序号 `T + cooldown_bars`。

### 4.4 各规则的持仓单位与处理

| 规则 | 持仓单位 | 入场价与入场序号 | 触发后 |
| --- | --- | --- | --- |
| `rank`（无 `holding`） | 持有集合里的每个标的 | 进入持有集合那一期的 close 与序号，持有期间调权不改 | 移出持有集合；冷却中不可入选；由后面的名次补位 |
| `rank`（`holding`） | 每个批次里的每个标的 | 该标的**实际进入该批次**那一期的 close 与序号（另存，不用批次的 `EstablishedBar`） | 移出该批次，份额留现金，到该批次下次重建 |
| `signal` | 持有集合里的每个标的 | 入场那一期的 close 与序号 | 等同 exit；冷却中 entry 成立也不入场 |
| `tranche` | 一条开仓记录 × 组内每个子策略 | 开仓 close 与开仓序号（记录本来就有） | 该子策略不再从这条记录取权重；冷却中该子策略不为这个标的的新开仓取权重 |

**rank 补位的位置**：先在完整可用样本上打分、定名次（解释明细的分数与名次不受止损影响），再从选币输入与 `buffer` 的上期持有集合中排除本期触发与冷却中的标的，
按名次补足。`filter_after` 仍是"只剔除不补位、留现金"。

**tranche 按子策略**：共用记录只存与阈值无关的价格（入场价、最有利价格）与一个"已止损子策略"位图（与后置过滤通过位图同样的形式）。
冷却按子策略：冷却中的标的仍参与组内共用的打分、过滤与选币，只是该子策略不为本期在该标的上的新开仓取权重；冷却不影响持有计数。

### 4.5 明细与摘要

- 解释明细保持"每个（规则, 标的）一条"（表主键 `(result_id, rule_id, instrument_id)` 不变）。止损相关的明细在写结果前按规则与标的合并，优先级从高到低：
  1. 本期触发止损、且标的已无权重：阶段 `stopped`，原因 `stop_loss` / `trailing_stop` / `take_profit`；若同一标的本期另有缺数或 `idle` 明细，
     改为这一条，把原原因追加在后面（例如 `stop_loss;missing:exit_factor`）。例如 `signal` 持仓的 exit 因子缺失、而 `close` 已达止损线。
  2. 标的仍有权重（另一批次或另一条开仓记录还持有）：保持 `weighted`，原因追加 `;stopped:<n>`，n 是本期被止损的持仓单位数。
  3. 冷却中本应入选而被排除：阶段 `dropped`，原因 `cooldown`。
  4. 其余照现有规则。
  T2 加入"必需因子缺失、止损价格有效"与"止损且 idle"的测试，验证每个（规则, 标的）只有一条。
- 规则摘要增加 `stop_loss`、`trailing_stop`、`take_profit` 三个计数，计的是**触发的持仓单位数**，不是标的数。

### 4.6 与现有机制的交互

- **守门跳过**：整期跳过时状态不变，止损不推进。
- **追赶期与迟到周期**：这些周期求值并推进状态（#64），止损也照常推进，放行后与连续运行一致。
- **回放**：`rank`、`signal` 的研究回放与闭环回放走同一求值，自动支持止损；`tranche` 回放仍不支持（与 f1 现状相同）。

### 4.7 边界

- 这是**按 K 线收盘判断的理论止损止盈**：止损目标随下一次目标下发，由 Trade 执行。盘中触价需要 Trade 挂条件单，不在本设计范围内。
- 入场价是决策当期的 close，不是实际成交价，差额在实盘里体现为滑点。
- `price: extreme` 更接近盘中触发，但仍在收盘后执行，实际成交价可能比止损线更差。

## 5. 状态

```text
RuleState
  held        []string                    # 不变
  batches     []HoldingBatch              # 批次成员增加实际入场 close 与入场序号、最有利价格
  entries     map[id]{price, bar, peak}   # 新增：rank（无 holding）/ signal 持有标的；只在开了 stop 时记录
  cooldown    map[id]int                  # 新增：冷却截止序号（含）；只在开了 stop 时记录
  tranche     {groups: [...]}             # 由 f1 改名；开仓记录增加 peak（开了 trailing 时）与已止损子策略位图（开了 stop 时）
  tranche_cooldown  map[sub][id]int       # 新增：tranche 按子策略的冷却截止序号
```

不开止损时这些新字段为空，状态大小与现在相同。

## 6. 模板库

### 6.1 模型

模板 = 命名的 DSL 骨架 + 变量定义 + 可选的样例参数行 + 说明。存在策略模块的库里，管理台与 CLI 可增删改，不随代码发布。

```yaml
template_id: f1
name: F1 截面选币（批次持仓）
description: alphalib F1 子策略参数表迁移；参数表每行一个子策略
variables:                       # 单值变量，类型 int / number / string / bool
  - {name: total, type: number, min: 0, max: 10, default: 1, doc: 规则预算}
  - {name: leverage, type: number, min: 0, max: 10, default: 2, doc: 组合杠杆上限}
sample_row: [1, 65, 193, 24, 0.1, 0.0033]   # 保存时试渲染用的一行合法参数；参数列以骨架里的 params.columns 为准
dsl: |                           # 骨架：完整策略 DSL
  name: "{{name}}"
  rules:
    - id: main
      type: tranche
      preset: f1
      weight: {total: "{{total}}"}
      tranche:
        hold_period: "{h}"
        ...
      params:
        columns: [h, s, l, n2, p2, w]
        rows: []                 # 由建策略时上传的参数表填入
  portfolio: {leverage: "{{leverage}}"}
```

- **替换在 YAML 节点上做，不做文本替换**：先把骨架解析成 YAML 树，只替换**值为完整 `"{{变量}}"` 的标量节点**，按声明类型写入（数值保留数值类型，
  字符串写成字符串标量，不会改变 YAML 结构）。键、部分包含 `{{` 的标量、未声明的变量一律拒绝。`name` 是内置变量（策略名）。
- **两种占位符不冲突**：`{{变量}}` 由模板渲染替换；`{列名}`（单花括号）原样保留，交给 tranche 的参数表展开。
  为避免变量值被参数表二次解释，**字符串变量的值禁止包含 `{` 与 `}`**，渲染时拒绝；数值与布尔变量不受影响。测试覆盖值为 `{h}`、`foo{h}` 两种情形。
- **参数列只维护一份**：以骨架里 `params.columns` 为准，模板不另存列定义；列的范围由 DSL 校验与 tranche 字段校验负责。
- 骨架可以是任何规则类型；`rank`、`signal` 模板只用变量，不填参数表。

### 6.2 流程与接口

- **存储**：策略库新增表 `t_strategy_templates`（模板 ID、名称、说明、模板 YAML、修改时间），格式按 `modules/storage/schema/metadata.sql` 规范。
- **接口**：`ListStrategyTemplates`、`GetStrategyTemplate`、`SaveStrategyTemplate`、`DeleteStrategyTemplate`、`RenderStrategyTemplate`。
  - `Save` 时用变量默认值与 `sample_row` 试渲染一次并做完整 DSL 校验，不通过拒绝保存。
  - `Render` 给定变量与参数表，返回生成的 DSL 与校验结果，不落库。骨架含 `params.columns` 时参数表必须非空；不含时（`rank`、`signal` 模板）不接受参数表。
- **建策略**：管理台"从模板新建"——选模板、填变量、上传参数表 CSV（表头与 `params.columns` 一致），预览 DSL，确认后走现有 `CreateStrategy`。
  生成的策略是普通策略定义，与模板脱钩：改模板不影响已有策略。
- **CLI**：`moox-strategy-cli template list|get|save|delete|render`；仓库 `modules/strategy/templates/f1.yaml` 是内置模板，用 `save` 导入。
- **发布影响**：新增 RPC 改了服务目录（`packages/servicecatalog/catalog.yaml`），上线必须走目录变化的整体发布；还要发布 `moox-strategy-cli` 与 `web-host`（第 7 节）。

## 附录 C：实现与本稿的差异

| 项 | 本稿 | 实现 | 原因 |
| --- | --- | --- | --- |
| 选项写法 | `hold.count` | `hold_count`；`score: {method, missing}`、`sizing: {method, scale}`、规则级 `candidates: {require_volume}` | 与 `hold_period` 并列更直观 |
| `score.missing` 对 `raw_sum` | 决定空值是否剔除 | `raw_sum` 下空值总是不参与排名 | 与 F1 `vertical` 一致，`median` 只对名次有意义 |
| T5 因子定义更新 | 新增 `moox-factor-mgr-cli update` | 不新增命令：用 `moox-cli gateway call` 调 FactorMgr 现有的 `UpdateFactor`、`SetTaskMemberStatus` | 现有接口已带全部校验，CLI 走直连库要另建服务对象，没有必要 |
| 模板 CLI | `moox-strategy-cli template list/get/save/delete/render` | `moox-strategy-cli template check/render` 只做本地校验与渲染；保存、删除走 `gateway call` | `moox-strategy-cli` 是本地工具，没有接口客户端 |
| 管理台模板 | 增删改 | 只读列表 +“从模板新建” | 模板很少改，保存与删除用 CLI；页面只做最常用的建策略 |
| 冷却明细 | 冷却中“本应入选而被排除” | 冷却中的全部候选都记 `cooldown` | 判断“本应入选”需要再选一次币，收益小 |
| 入场价缺失 | 不入场 | 照常入场，入场价在下一个有价格的期次补记 | 不改变选币结果，避免止损列缺值影响策略本身 |
| 阈值比较 | 未写 | 按比例比较，达到阈值（含等于，留 1e-12 浮点余量）即触发 | 100 × 0.95 这类乘积会差最后一位 |
