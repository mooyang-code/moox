# 策略读取变慢排查与修复方案

- 日期：2026-10-27（CST）
- 范围：只读排查，生产环境没有做任何改动。采样用的临时脚本和抓包文件已从两台主机删除。
- 关联：`F1策略迁移执行计划.md` 7.1 节中的"chain 对照"。

## 1. 结论

chain（实例 `9c88ee5b-…`）的"当期与上一根行"变慢，原因不在策略代码，也不在 Storage View 的查询。

真正的原因是：存储机（南京）与控制机（广州）之间的跨地域公网链路在突发流量下丢包，TCP 靠重传超时（RTO）指数退避才把数据补齐。

- **为什么从 17:57 开始**：F1 上线后，每个 5 分钟边界后的 2～10 秒里，这条链路上多了两类流量：
  - 三个 FH 任务的因子结果事件，每个约 190 KB（已压缩）。它们从 storage-node 发到控制机上的 EventBus，再投递回存储机上的 storage-view，等于在链路上往返一次；
  - 三个 FH 实例的读取应答，每个 107～193 KB（已压缩）。
- **丢包规律**：
  - 一次 160～300 KB 的突发能完整通过；
  - 紧随其后的 250 ms 内，首发分段丢 20～43%；
  - 被丢的分段重传时又被丢，于是 RTO 按 0.24 → 0.49 → 1.02 秒翻倍。
- **结果**：一次本该 0.2 秒的读取，会被拉长到约 0.5、1.0 或 2.2 秒。这几个档位正好对应 RTO 退避的累加值。
- **谁受害**：哪个实例的应答恰好排在突发后面，哪个就慢。chain 并不总是最慢的：07:55 那期 chain 只用了 219 ms，反而是最先读取的 `5d158293` 用了 1.17 秒。

"就绪等待"的 0.5～1.5 秒由两部分组成：

1. 因子完成事件经同一条链路（控制机 → 存储机）投递给 storage-view 时也遇到丢包。chain 的投递滞后 p50 由 0.38 秒升到 0.72 秒，p90 由 1.01 秒升到 2.67 秒；
2. 策略按事件串行处理所有实例，后到的实例要排在前面实例的处理之后。

修复方案：先看控制台里两台主机的公网带宽（第 4.0 节），再决定以哪一项为主。两项都不改代码，都可以回退。

- **提高公网带宽（第 4.2 节）**：控制台显示任一侧不超过 5 Mbps 时，以这一项为主。
  - 现有数据更倾向于带宽偏小：突发过后只发了 30 KB 也丢了 43%，见 3.3 节。
- **两台主机改用 BBR 拥塞控制（第 4.1 节）**：两侧都不低于 10 Mbps 时，以这一项为主。
  - BBR 会让发送端按速率起搏，不再一次性按线速打出突发；遇到丢包也不会把窗口减半。
  - 带宽小的时候同样值得做，能减少"重传又被丢"的连锁退避。
- **顺手改进（第 4.3 节，不是根因）**：实时读取的页大小改成不小于标的数，每次读取少一次跨机往返。

## 3. 证据

### 3.1 读取路径与逐项排除

调用链如下：

1. strategy `LoadBar`（`modules/strategy/internal/input/frame.go`）；
2. `RPCClient.QueryRows` 分页调用 `QueryTimeSeriesRows`；
3. 本机主机网关 → 公网 → 存储机主机网关（:11003）；
4. storage-view DataView（127.0.0.1:20103）；
5. DuckDB 索引文件。每个 View 一个文件，FH 为 26～35 MB，chain 为 59 MB。

| 假设 | 结论 | 依据 |
|---|---|---|
| 四个实例同时读 View、互相争用（7.1 的推断） | 不成立 | 策略的事件消费是串行的：`jetstream.Runner` 没有开 `Concurrent`，`Handler.Handle` 全程持有 `h.mu`。四个实例的读取在时间上从不重叠，日志里每个读取都在前一个实例处理结束后才开始 |
| 策略侧串行锁 | 存在，但只解释排队 | 它让后到的实例等待，属于"就绪等待"的一部分；它不会让单次读取变慢 |
| DuckDB 连接池（4 个连接）、`threads = 1` | 不是瓶颈 | 卡顿期间，storage-view 对每个请求都在 50～90 ms 内应答（见 3.2 存储机本地一跳）。从来没有出现过 "slow query"（> 1 秒）日志。07:45 边界前后 20 秒的 pprof 里，`QueryTimeSeriesRows` 总共只占 0.61 秒 CPU，而五个实例的读取合计约 5.1 秒 |
| Pebble 读放大 | 不在这条路径上 | 读取只走 storage-view → DuckDB，不碰 storage-node 的 Pebble |
| 主机 CPU | 不是瓶颈 | 07:45 边界采样（每秒一次）：存储机 storage-view 最高 57%，控制机 strategy 最高 35%，两台都是 4 核，负载约 0.2 |
| 新二进制 | 已排除 | 17:50、17:55 两期已跑在新二进制上，读取仍是 0.2 秒 |
| "写入压力"已排除 | 推断不成立 | 17:55 那期，FH001、FH003 的结果在 01:55:38、01:55:48（CST）才进入 storage-view（当时引擎还没修复，compute 要 37～48 秒），chain 的读取在 01:55:05 就结束了。和 chain 读取落在同一时段的只有 FH002 的结果，而且当时 FH 实例还没启用、没有读取。17:56 修复引擎、17:57 启用实例之后，三份结果加三次读取才挤进了同一个 2～10 秒窗口 |

### 3.2 07:50 那期：chain 读取 2.16 秒的逐跳拆分

方法：两台主机在边界附近同时用 `tcpdump` 只抓包头（snaplen 128），两机时钟偏差小于 1 ms。

当期日志：chain 当期行耗时 2.16 秒，就绪等待 3.16 秒。

| 跳 | 第 1 页（500 行） | 第 2 页（1 行） |
|---|---|---|
| 存储机本地：网关 → storage-view :20103 | 05.761 发出请求，70 ms 后应答 107 KB | 07.835 发出请求，51 ms 后应答 |
| 公网：存储机网关 :11003 → 控制机 | 05.832 起发出 37 KB 压缩应答，**1969 ms** 才传完 | 正常 |

公网那一段，chain 连接的逐包情况：

1. 05.832：存储机一次发出 10 个分段，这是 IW10。原因是存储机 `tcp_slow_start_after_idle = 1`，连接空闲 5 分钟后拥塞窗口重置为初始窗口。
2. 控制机只收到第 1 个和第 10 个分段，中间 8 个在网络中丢失。
3. 05.934：快速重传，又丢了。
4. 06.175、06.663、07.679：RTO 重传，前两次又丢了，间隔分别是 241、488、1016 ms。第 4 次才送达。
5. 07.709：确认到达，随后剩余的数据在 3 个 RTT 内补齐。

两台主机网卡的 qdisc 统计都是 `dropped 0`，说明包是在两机之间的网络上丢的。

同一期里，FH001 的 107 KB 应答只用了 244 ms，FH003 的 193 KB 只用了 274 ms。慢不慢不取决于数据量，取决于应答落在突发中的什么位置。

### 3.3 07:55 那期：丢包紧跟在突发之后

把存储机发往控制机的每个首发分段，与控制机在 100 ms 内收到的字节区间对照（已排除 GRO 合并造成的误判），按 250 ms 分桶统计。下表只列出有代表性的桶。

| 发送时刻 | 发送量 | 主要成分 | 首发丢失率 |
|---|---|---|---|
| 02.0～02.5 | 236 KB | 4222（FH002 结果事件发往 EventBus） | 0% |
| 03.0 | 26 KB | 11003（`5d158293` 的读取应答） | **21%**（这一期 5d158293 读取 1.17 秒） |
| 04.2 | 195 KB | 4222 | 0% |
| 05.7 | 163 KB | 11003（FH002 读取应答） | 0% |
| 06.0 | 30 KB | 4222 | **43%** |
| 07.2～07.7 | 299 KB | 4222（FH001 结果事件）、11003 | 0% |
| 08.0～08.7 | 131 KB | 11003（FH001、FH003 读取应答） | **19～32%** |

整个窗口的首发丢失率是 3.0%。控制机 → 存储机方向的规律相同：EventBus 在 02.2、04.5、07.5 分别把约 187 KB 的结果事件投递给 storage-view，之后的桶丢 8～48%，整个窗口 1.4%。

两台主机的流量概况：

- 1 秒滑动峰值：约 3.0～3.6 Mbps；
- 100 ms 峰值：约 10～11 Mbps；
- 存储机出向流量 90% 发往控制机。端口 4222（EventBus）在 18 秒窗口里有 1031 KB，比网关读取应答的 690 KB 还多。

累计重传率（开机以来，`nstat`）：

| 主机 | TcpRetransSegs / TcpOutSegs |
|---|---|
| 存储机 | 1350 万 / 5.06 亿 = 2.7% |
| 控制机 | 2387 万 / 5.18 亿 = 4.6% |

这两个数字对一条健康的链路来说偏高。

规律是：一次突发能通过，紧随其后的分段被成批丢弃，被丢的重传还会接着被丢。这符合令牌桶限速：桶被突发抽空后，要过一段时间才能补满。

06.0 那个桶在突发之后只发了约 30 KB，却丢了 43%：

- 如果限速器每秒补充 10 Mbps 以上的令牌，250 ms 能补回约 300 KB，这 30 KB 不应该丢；
- 所以实际限额更可能只有约 2～3 Mbps（按秒计），或者跨地域路径本身拥塞。

由于两个方向都有丢包，无法仅凭抓包确定限速点在哪一侧，要以控制台为准（4.0）。另外，1 秒峰值 3.0～3.6 Mbps 是被丢包压过之后的数字，真实需求比这更高。

### 3.4 "就绪等待"的拆分（07:50 那期，chain 3.16 秒）

- **K 线至就绪 2.51 秒**：`ReadyAt` 取的是 `factor_period.computed` 事件的发生时间，即 07:50:02.51。
- **storage-view 收到 chain 的完成事件**：07:50:05.3，投递滞后 2.79 秒。
  - 这个事件经 EventBus 从控制机投递到存储机。
  - 同期抓包显示，控制机 → 存储机的 4222 方向在 02.7 和 03.7 各有一次约 190 KB 的突发（FH 结果事件）。02.7～04.5 之间，首发分段丢失 8～19%，chain 的事件正好要在这段时间里投递。
  - 抓包只有包头，无法逐条认出是哪个事件，但时间上吻合。
- **策略开始处理 chain**：05.67，正好是 FH002 处理结束的时刻（05.668），中间因为串行处理排了约 0.3 秒队。

所以这一期的就绪等待主要是事件投递被丢包拖慢，排队只占一小部分。FH003 等实例排在后面，它们的就绪等待主要是排队，而排队时长又随前面实例的读取一起被拉长。

## 4. 修复方案

### 4.0 先确认公网带宽（只读，五分钟）

在腾讯云控制台查看两台实例的"公网带宽上限"和计费方式：

- 存储机：`ins-c73j3usm`，ap-nanjing-3，BF1.LARGE16，包年包月；
- 控制机：`ins-84tx5l36`，ap-guangzhou-4，S5.LARGE4，按量计费。

metadata 里的 `bandwidth-limit-*`（约 1.5～2 Gbps）是内网带宽上限，不能拿来判断公网带宽。

按查到的结果选方案（这一步决定以哪一项为主）：

- **任一侧不超过 5 Mbps**：以 4.2 为主，4.1 作为补充。现有数据（3.3 节）更倾向于这种情况。
- **两侧都不低于 10 Mbps**：限额不是问题，丢包来自 100 ms 级突发或路径拥塞，以 4.1 为主；无效时再做 4.2。

### 4.1 两台主机改用 BBR（不改代码）

**原理**：

- 现在两台主机的拥塞控制都是 `cubic`。`eth0` 实际挂的队列是 `mq` 下的 `pfifo_fast`：`default_qdisc` 虽然是 `fq_codel`，但没有作用到 eth0 已有的队列上。
- 在这种配置下，TCP 按拥塞窗口一次性把分段打出去，比如 IW10 或 190 KB 的事件批，在微秒级时间内全部发出。
- BBR 会要求按速率起搏。网卡队列不是 `fq` 时，内核 4.13 起由 TCP 自己做内部起搏，所以不需要改 qdisc。起搏会把同样的数据摊到几十毫秒里，不容易一下子抽空限速器的令牌桶。
- BBR 不把丢包当作拥塞信号来减半窗口，并且带有针对限速器的长期带宽采样，能减少"重传又被丢"的连锁退避。
- 两台主机的 7.0 内核都带有 `tcp_bbr` 模块（已用 `modinfo` 确认），只是还没有加载。

**做法**：两台主机各执行一次，不需要停服务，也不碰 qdisc。

```bash
sudo modprobe tcp_bbr
echo tcp_bbr | sudo tee /etc/modules-load.d/moox-bbr.conf
echo 'net.ipv4.tcp_congestion_control = bbr' | sudo tee /etc/sysctl.d/90-moox-net.conf
sudo sysctl --system
sysctl net.ipv4.tcp_congestion_control   # 预期输出：bbr
```

**生效范围**：只对新建的连接生效。

- 主机网关连接池里的连接最长存活 30 分钟，会自然换成 BBR。想立即生效，可以避开边界（例如 xx:x2:30），在两台主机上各执行一次 `./restart.sh -components host-gateway`。
- EventBus 的长连接在下次重连时才会换成 BBR。要让结果事件的往返流量也立即受益，可以在同样的时间点重启存储机上的 storage-node 和 storage-view（它们是 EventBus 的客户端）。

**回退**：

```bash
sudo rm /etc/sysctl.d/90-moox-net.conf /etc/modules-load.d/moox-bbr.conf
sudo sysctl -w net.ipv4.tcp_congestion_control=cubic
```

**验收**（改后至少观察 12 期）：

- 策略日志："当期与上一根行"的 p90 降到 0.5 秒以内。对照第 2 节的表；可以沿用 `local/f1/latency.py`，或按本文的 grep 口径统计。
- storage-view 日志：chain 的"因子结果就绪 … 投递滞后" p90 回到 1 秒左右。
- 边界前后 20 秒的 `nstat TcpRetransSegs` 增量明显下降。也可以按 3.3 节的方法在边界抓一次包头，看首发丢失率。

### 4.2 提高公网带宽

以下两种情况，在控制台把带宽较小的一侧调高：

- 4.0 查到任一侧不超过 5 Mbps；
- 4.1 实施后 p90 仍然在 1 秒以上。

两种方式任选：

- 固定带宽，调到至少 10 Mbps，建议 20 Mbps；
- 改为按流量计费，带宽上限设为 50 Mbps 或更高。

边界附近 100 ms 级的需求已经达到 10～17 Mbps（见 3.3 节，入向峰值约 16.8 Mbps）。

费用参考：存储机开机 39 天累计发送 209 GB，约 5.3 GB/天。具体价格以控制台为准。这一步不改代码、不动服务，可以随时调回。

### 4.3 顺手改进（代码，小改动，不是根因）

**问题**：实时读取用的是 `RPCClient` 的默认页大小 500，比 501 个标的少 1。因为 `TotalMode_NONE` 时 Storage 用 `HasMore = returned >= size` 判断还有没有下一页，所以每个实例每期都会多一次跨机往返，外加一次 DuckDB 查询。chain 这次额外往返约 85 ms，占 0.2 秒基线的四成。

**改法**：

- 只改 `modules/strategy/internal/input/client.go` 的 `QueryRows`，把页大小取成 `max(c.pageSize(), 本次预计行数)`。本次预计行数等于选中标的数，读上一根时再乘 2。
- 不改 `pageSize()` 的默认值，因为它还用于 `ListViewColumns`、`ListDatasetSubjects`、`ListSubjects`、`ListTagMembers` 等 Metadata 分页，不应受影响。
- 显式传入了 `query.Limit` 的调用保持原样。
- 补一条单测：501 个标的的读取只发一次请求。

**容量核算**：

- Storage DataView 的页大小没有上限（`queryPage` 不截断）；
- FH003 的 501 行原始应答约 0.8 MB，读两根时约 1.6 MB，远低于 DataView 的 `max_body_bytes`（32 MB）。

**发布**：改动只涉及 strategy，按常规流程替换二进制即可。

### 4.4 不采用的做法

| 做法 | 不采用的原因 |
|---|---|
| 策略改成并发处理实例 | 会让同一时刻的突发叠得更高，丢包更严重。网络问题解决之前不要做 |
| 调整 DuckDB 连接池或 threads | 不是瓶颈，单次查询已经只要 50～90 ms |
| 把 `tcp_slow_start_after_idle` 设为 0 | 空闲连接会直接按大窗口突发，加剧限速丢包 |
| 每条路由调小 `rto_min` | 能缩短退避，但要在每台主机上维护静态路由参数，属于治标；4.1 和 4.2 无效时再考虑 |
| 因子结果不再经控制机上的 EventBus 往返，或用云联网打通两地内网 | 能从根本上减少跨地域流量，但涉及架构或额外的网络费用，对单用户系统来说太重 |

## 5. 附：复现方法（只读）

**策略分段耗时**：在控制机 `strategy/logs/trpc.log` 中匹配"实例 … 周期 … 耗时："，取"当期与上一根行"和"就绪等待"两项。

**storage-view 一侧**：

- `/data/moox/run/logs/storage-view.log` 中的"因子结果就绪 view=… 投递滞后="；
- pprof：`curl http://127.0.0.1:20001/debug/pprof/profile?seconds=20`（回环地址，不需要鉴权）。

**链路丢包**：在边界前 3 秒，两台主机同时运行：

```bash
sudo timeout 18 tcpdump -i any -s 128 -nn -w cap.pcap 'not port 22'
```

然后按以下方法分析：

- 用 `(服务端口, 客户端口, seq)` 把发送端的首发分段与接收端在 100 ms 内收到的字节区间对照；接收端开了 GRO，必须按区间覆盖判断，不能按 seq 起点判断；
- 对照时排除抓包结束前后不完整的部分。
