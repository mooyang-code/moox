## 0. 结论

- **三个策略的共同结构**：在全部永续标的里，每根 5m K 线选出因子值**最大**的 1 个币做多。选出后再做一次**后置过滤**，条件为真就清仓，被清掉的份额留作现金，不补位。每根 K 线都新开一份仓位，每份按开仓时的数量持有 h 根（h 为 1～36），h 份滚动叠加。几百到近两千组参数按权重加权平均，得到最终仓位。
- **原子组件**：选币因子 `Po`、`Mtmstd`，过滤因子 `MaxHightDie`、`MinMax`、`UpperShadow`，三个策略一共用到 100 个（因子, 窗口）成员。
  - 用现有的严格窗口算子能写出这 5 个因子，但上市不久的币会算不出值，F1 却能算出（F1 的 EMA 从第一根开始递推，rolling 用了 `min_periods`）。
  - 所以表达式引擎要新增 5 个"序列开头允许部分窗口"的算子，现有算子和现有因子都不受影响（第 2、3 节）。
- **策略侧**：新增 `type: f1` 规则（第 7 节）。字段与 F1 的 `F1StrategyConfig` 一一对应，覆盖 F1 的全部写法：
  - 多因子加权、截面排名或原值打分、多空两边、按个数或百分比选币；
  - 前置过滤与后置过滤：`value` / `rank` / `pct` 三种类型、10 种比较方式、串联执行、按编号组合逻辑；
  - 黑白名单、999 根封印、持有期与按数量持有、多子策略加权合并。

  可选的参数表把几千个子策略压进一条规则。引擎按"排名签名"去重：签名相同的子策略只算一次排名和选币，状态和明细都做了收敛。
- **不在本次范围内**：合约回放与资金费率采集；长 EMA 补算加速（分块锚定，第 8 节）；参数搜索与打分。

## 1. 已核实的 F1 语义

"左、右因子"按以下理解：左因子是选币（排序）因子，右因子是过滤因子。下表的行号都指 `alphalib-dev/alphalib/contrib/strategy/f1_strategy.py`（简称 S）和 `alphalib/common_utils/f1_utils.py`（简称 U）。

| 编号 | 项 | F1 行为 | 位置 |
|---|---|---|---|
| F1-1 | 候选行 | 每个标的只保留 `volume > 0` 的 K 线；`enable_seal999` 为真时，再去掉该标的全部数据的前 999 行。数据里有 `avg_price` 列时，还要求下一根的 `avg_price` 不为空——这是 F1 回测特有的、用到下一根数据的筛选，实盘没有对应项 | S:88-96 |
| F1-2 | 截面排名的样本 | 每个因子在同一时刻、**全部候选行**上升序排名（并列取平均名次），在黑白名单和过滤之前完成；名次为 NaN 的用同期名次的中位数补上。只有 `cross` 模式这样做，`vertical` 模式直接用原值，不排名、不补。**多空因子列表不同时分两遍原地改写**：先处理多头列表的列，再处理空头列表的列；两边共用的列会被再排一次，第二次排的是第一次的名次（其中包含补上的中位数） | S:139-155 |
| F1-3 | 合成分数 | `分数 = Σ 系数 × 名次（或原值）`，系数 = `descending ? −weight : weight`；多空因子相同时共用一列 | S:139-155 |

| F1-8 | 过滤写法 | 方向 `df1`（多头）或 `df2`（空头）；类型 `value`、`rank`（默认从大到小，`rank_ascending` 可改）、`pct`（固定从小到大）；`rank` 和 `pct` 都用 `method='first'`；比较方式 `lt` `lte` `gt` `gte` `bt` `bte` `nbt` `nbte` `eq` `ne` | U:49-128 |
| F1-9 | 比较的细节 | 用 `between(lo, hi, inclusive)` 实现：比较方式以 e 结尾的是闭区间；`lt`/`lte` 写成 `[-1e100, v]`，`gt`/`gte` 写成 `[v, 1e100]`，是有限边界，不是无穷；`eq` 当作 `bte[v,v]`，`ne` 当作 `nbt[v,v]`；`nb*` 先把开闭取反，再对结果取反。所以 **NaN 在普通比较下为假，在 `nb*` 下为真** | U:72-125 |
| F1-10 | 逻辑组合 | 元组写法 `(条件1, 条件2, …, "1&2|3")`：编号对应条件，按 `&`、`|` 和括号组合，同一组的条件必须是同一个方向 | U:154-189 |

| F1-13 | 按数量持有 | 每份按 `资金 / 开仓 close` 记为数量，本期权重 = Σ 数量 × 本期 close。窗口是该标的**最近 h 个候选行**（按行数，不按日历）。本期没有候选行的标的不出现在结果里，回放时按目标 0 对齐 | S:195-203（数量滚动）；`f1_playback.py:126-148`（回放时补 0 对齐） |

## 2. 选币因子（左因子）

| F1 名称 | 公式（F1 原文） | moox 因子 ID | 写法要点 | 用到的窗口 |
|---|---|---|---|---|
| `Po` | `s = ewm(close, com=n)`，`l = ewm(close, com=3n)`，结果为 `(s − l)/(s + l)` | `f1_po` | 把 `com` 换成 `span`：`short_span = 2n+1`、`long_span = 6n+1`。窗口参数不能写成运算，所以拆成两个参数；长线最多用 5 万根预热；用 `ema_partial`，上市不足 5 万根时从第一根开始递推，和 F1 一样 | 34 个，24～1992 |
| `Mtmstd` | `r = pct_change(close, n)`，结果为 `mean(r, n, min_periods=1) × std(r, n, min_periods=2)` | `f1_mtmstd` | 用 `ts_mean_partial(r, n, 1)` 与 `ts_std_partial(r, n, 2)`，回看 2n，最大 4000 | 28 个，168～1992 |

成员键举例：`Po n=24` 对应 `f1_po__49_145`，`Mtmstd n=768` 对应 `f1_mtmstd__768`。默认值取参数下限，不与参数表里的任何取值重合，所以不会出现省略参数段的成员键。

**新增算子**（`packages/factorexpr`）。现有算子、现有因子和它们的 `definition_hash` 都不变：

| 算子 | 语义 | 回看 |
|---|---|---|
| `ema_partial(x, n, k)` | 同 `ema(x, n, k)`（`k` 为 0 时按容差推导）；区别是窗口里的 NaN **只出现在开头**（序列还没开始）时，从第一个有效值开始递推，相当于 pandas `ewm(adjust=False)` 从序列首根开始算。有效值之后再出现 NaN，结果为 NaN | 同 `ema` |
| `ts_mean_partial(x, n, m)`、`ts_std_partial(x, n, m)`、`ts_min_partial(x, n, m)`、`ts_max_partial(x, n, m)` | 窗口里的 NaN 只出现在开头、并且有效值不少于 m 个时，在有效值上计算，相当于 pandas `rolling(n, min_periods=m)` 作用在从首根开始的序列上；其他情况与严格窗口一致。`ts_std_partial` 要求 m ≥ 2 | 同对应的严格算子 |

- **点纯性仍然成立**：结果只取决于窗口内容，"开头"由数据本身决定，与需求区间、分块方式都无关。实现时内核只看固定窗口、按固定顺序计算，不能改成从需求区间或分块起点开始递推。
- **"窗口开头的 NaN 就是序列开头"这个判断成立的前提**：因子机的本地时序存储写入时保证每个标的在 `[Earliest, Latest]` 上按频率网格连续，交易所缺的周期写成填充行（OHLC 取上一期 close，volume 填 0，带 `is_filled` 标记，见[因子文档"本地时序存储"](../../模块/因子.md)）。所以输入列只会在序列开始之前是 NaN。派生值中途出现 NaN 时（例如除以 0），partial 算子和严格窗口一样输出 NaN，**这一点和 pandas 不同**（pandas 的 `min_periods` 会跳过中途的 NaN）。F1 这 5 个因子的输入（close、high、low、`pct_change(close)`、典型价）中途不会出现 NaN，所以不受影响。T1.0 对开头 NaN、中途 NaN、窗口左缘 NaN 分别测试。
- **填充行**：F1 的数据中心同样会补齐缺失周期（`data_center_zhenyu.py:875-884`：close 沿用上一期、volume 等字段填 0），因子在补齐后的网格上计算，再按 `volume > 0` 选候选。这和 moox"填充行参与因子计算、`volume = 0` 不算候选行"的口径一致。验收时两边用同一份含填充行的数据（执行计划 T0.6、T9.2）。
- **"序列开头"指 moox 里这个标的最早的数据**：标的在 moox 里的历史比上市时间晚（只导入了最近 N 根），并且不足 K 根时，结果会和从更早数据开始算的 F1 不同。现在这 501 个长历史标的都在 5 万根以上，新上市的标的由 WS 从第一根开始采集，所以只影响历史导入不全的个别标的，在 P9 单独统计。

**数值对比**：下表是 v1 草案（严格窗口写法）用 6 万根合成 5m 数据跑出的结果，`factorexpr eval` 与 strategy_share 原版 pandas 逐行对比。改用新算子后，序列开头的出数位置也要和 F1 一致，由执行计划 T1.3 复测。

| 因子 | 相对误差（中位 / 最大） | 符号一致率 | 说明 |
|---|---|---|---|
| Po n=24 | 1.1e-9 / 3.1e-5 | 1.0000 | 截断误差 |
| Po n=1992 | 6.2e-5 / 4.4 | 0.9999 | 长线 EMA（span 11953）只用 5 万根预热，丢掉的起点权重为 2.3e-4。合成数据上 F1 的历史也只有 5～6 万根，这个数字**低估**了与长历史 F1 的偏差；以真实数据上的每期 top1 一致率为准（执行计划 T9.2） |
| Mtmstd n=1992 | 3e-14 / 4e-12 | 1.0000 | 严格窗口从第 3984 根开始出数，F1 从第 1994 根开始（从 1 数）；改用新算子后应同为第 1994 根 |

**实时成本**：截断 EMA 每个点的计算量是 O(K)。按本机 EMA(50000) 的基准（每"标的·根"约 6.4 ns）、501 个标的估算：FH001 的 16 个 Po 约 3.4 秒/期，FH003 的 32 个 Po 约 6.9 秒/期。

## 3. 过滤因子（右因子）

| F1 名称 | 公式 | moox 因子 ID | 用到的窗口 | 用在哪个策略 |
|---|---|---|---|---|
| `MaxHightDie` | `rolling_max((high − close)/close, n)`（名字和 docstring 都写成"回撤"，实际算的是上影线占比的滚动最大值） | `f1_wick_max` | 13 个，3～2016 | FH001 后置：值 ≤ p2 时清仓 |
| `MinMax` | 典型价 `tp = (H+L+C)/3` 在近 n 根里的位置，再减 0.5（rolling 用 `min_periods=1`） | `f1_min_max`，用 `ts_min_partial` / `ts_max_partial`（m = 1） | 12 个，24～2016 | FH002 后置：值 ≥ p2 时清仓 |
| `UpperShadow` | `abs(rolling_max(high, n) − close)/rolling_mean(close, n)` | `f1_upper_shadow` | 13 个，12～2016 | FH003 后置：值 ≤ p2 时清仓 |

- **前置过滤**：FH001～FH003 都没有。官方示例里常见的成交额排名、涨跌幅上限等过滤，`f1` 规则也能完整表达（F1-7～F1-10）。
- **新开 ID**：`f1_min_max` 与现有 `min_max` 的公式相同，但窗口上限从 120 放宽到 2016。这里另开 ID，不改现有因子：改了会变动线上任务的 `definition_hash` 和回看。
- **数值对比**：三个过滤因子与 F1 的相对误差都 ≤ 1e-10。MaxHightDie 和 UpperShadow 在 F1 里也是严格的 `rolling(n)`，两边都从第 n 根开始出数。MinMax 在 F1 里从第 2 根开始出数（第 1 根的区间宽度为 0，结果是 NaN），改用 partial 算子后两边一致。

## 5. F1 与 moox 的差异（`f1` 规则实现后）

| 项 | 结论 |
|---|---|
| 选币、排名样本、补中位数、两遍排名、同分顺序、黑白名单、前后置过滤、按数量持有、合并 | 与 F1 一致（第 7 节逐条对应 F1-1～F1-14） |
| 上市初期 | 用 partial 算子后与 F1 一致。例外是历史导入不全、moox 里不足 K 根的标的（第 2 节） |
| Po 截断 | 长线最多丢掉 2.3e-4 的起点权重；F1 自己的值也取决于数据从哪天开始 |
| 同分顺序与名单 | 按标的 ID 映射到的 F1 symbol 排序，名单也按它转换。映射规则（去掉 `-`）要在真实标的上核对（执行计划 T0.11） |
| seal999 | **近似支持**：F1 去掉每个标的原始数据的前 999 行；moox 用 `universe.min_age_bars: 999`，按日历推算，探针容忍 2 根缺口。没有缺口时首次放行的边界可能差 1 根，有缺口时差得更多。FH001～FH003 都不用它 |
| `avg_price` 筛选 | F1 回测要求下一根 `avg_price` 不为空（F1-1），实盘没有对应项，不还原 |
| 权重精度 | 子策略份额精确累加，组合层截断到 1e-4（`WeightPlaces = 4`），零头留作现金 |
| 合计权重 | 按数量持有会让 Σw 略大于 1（实测最大 1.007），所以转换出的 DSL 把 `portfolio.leverage` 设为 2，只作上限，不缩放 |
| 下架 | moox 不使用未来信息：标的退市或数据消失后，按缺数清掉它的仓位。F1 的回测分数因此偏乐观 |
| `fdiff_n` | 由因子定义表达；f1 规则只引用列，不做差分 |
| 市场 | 本版 f1 规则只用于合约 View；现货 View 在启用时拒绝，因为按数量持有可能让 Σw 超过 1 |

## 7. `f1` 规则设计

### 7.1 DSL

```yaml
name: fh001_po_wick_max
bar: 5m

universe: {}                      # 同 F1：不设标签；seal999 为真时转换脚本写 min_age_bars: 999

rules:
  - id: fh001
    name: FH001 Po + MaxHightDie
    type: f1
    weight: {total: 1}            # 本规则的预算：子策略按 stg_weight 归一化后乘以它（F1-14）
    f1:                           # 子策略模板，字段与 F1StrategyConfig 一一对应
      hold_period: "{h}"
      calc_factor_type: cross     # cross | vertical
      seal999: false
      long_factors:
        - {factor: "f1_po__{s}_{l}", descending: true, weight: 1}
      short_factors: []
      long_weight: 2
      short_weight: 0
      long_coin_num: 1            # 整数是个数；0～1 之间的小数是百分比
      short_coin_num: 0
      long_white_list: []
      long_black_list: []
      short_white_list: []
      short_black_list: []
      filter_before: []
      filter_after:
        - {direction: long, factor: "f1_wick_max__{n2}", type: value, op: lte, value: "{p2}"}
      stg_weight: "{w}"
    params:                       # 可选：参数表，每行展开为一个子策略；省略就只有一个子策略
      columns: [h, s, l, n2, p2, w]
      rows:
        - [1, 65, 193, 24, 0.1, 0.0033333333333333335]
        # …… 共 300 行，由转换脚本从 FH001.py 生成
```

过滤条件的写法：

```yaml
filter_before:
  - {direction: long, factor: quote_volume_sum__24, type: rank, op: lte, value: 60}       # 成交额从大到小前 60
  - {direction: long, factor: close_pct_change_max__24, type: value, op: lte, value: 0.2}
  - {direction: short, factor: funding_rate_min__8, type: pct, op: bt, value: [0.1, 0.9]}
  - logic: "1&(2|3)"            # F1 的元组写法：编号对应 items，同一组必须是同一个方向
    items:
      - {direction: long, factor: a__20, type: value, op: gt, value: 0}
      - {direction: long, factor: b__20, type: rank, op: lte, value: 10, rank_ascending: true}
      - {direction: long, factor: c__20, type: pct, op: gte, value: 0.8}
```

规则：
- **占位符**：`"{名称}"` 取参数表里同名列的值。整个字段只有一个占位符时，按字段类型替换为数值；出现在字符串里（列名）时按十进制原样拼接。不做运算，没有对应列就报错。
- **字段对应**：字段名、默认值和取值范围都与 F1 相同。`direction` 写成 `long` / `short`，F1 的 `df1` / `df2` 也接受。`op` 是 F1 的 10 种比较方式。`type: rank` 时 `value` 必须是整数，`type: pct` 时在 [0, 1] 之间。`bt` / `bte` / `nbt` / `nbte` 的 `value` 是 `[lo, hi]`，并且要求 lo ≤ hi。
- **限制**：
  - 一条 f1 规则最多 5000 行，一份 DSL 里所有 f1 子策略合计最多 10000 个；
  - 每个子策略最多 16 个因子、32 个过滤条件，`hold_period` 为 1～2016；
  - 含参数表的 DSL 整体上限从 64 KiB 放宽到 1 MiB，其他 DSL 保持 64 KiB；
  - 规则的 `weight` 只接受 `total`；f1 规则不能和 `holding`、`buffer`、`select`、`filter`、`score` 写在一起。
- **不混用**：一份 DSL 里只要有 f1 规则，就只能全是 f1 规则，不能再有 rank 或 signal 规则。这样空洞冻结、守门都不会和现有规则交叉；需要组合时，各自建实例。
- **seal999**：同一份 DSL 里所有 f1 子策略的 `seal999` 必须相同。为真时要求 `universe.min_age_bars ≥ 999`，因为年龄判定是策略级的，这是近似支持（第 5 节）。
- **市场**：启用时，绑定的 View 必须是合约；现货 View 直接拒绝。

### 7.2 每期求值（对应 F1-1～F1-14）

1. **候选行 B**（F1-1）：规则的预期集合 E(r) 中，本期有行并且 `volume > 0` 的标的。`close` 或 `volume` 为空的视为没有候选行。
2. **因子排名**（F1-2、F1-3）：
   - `cross`：在 B 上升序平均名次，NaN 用同期名次的中位数补上；
   - `vertical`：直接用原值。
   - 多空因子列表相同时只排一遍。不同时按 F1 分两遍原地改写：先排多头列表的列，再在**当前值**（共用的列此时已经是名次）上排空头列表的列。
   - 第一遍的结果按"列 + 模式"缓存，供签名之间复用；第二遍不进缓存。
3. **按排名签名分组**：签名包括多空因子与系数、`calc_factor_type`、展开后的前置过滤、黑白名单和 `coin_num`。签名相同的子策略只做一次第 4～5 步。
4. **候选与前置过滤**（F1-6～F1-10）：
   - 在 B 上套用黑白名单后，按顺序执行前置过滤。每一步的 `rank` / `pct` 都在上一步留下的样本上计算；逻辑组合先在同一样本上算出各个条件，再组合。
   - 比较一律走 F1-9 的 `between` 语义：`lt`/`gt` 一类用 ±1e100 的有限边界；NaN 在 `nb*` 下为真。
5. **选币**（F1-4、F1-5）：
   - 多头按分数升序、空头按分数降序排名（`method='first'`）；同分时按标的 ID 映射到的 F1 symbol 排序（去掉 `-`，例如 `BTC-USDT` 对应 `BTCUSDT`，映射规则由 T0.11 核对）。
   - 截取：固定个数时取名次 ≤ `coin_num` 的；按百分比时取"名次 / 分数不为 NaN 的个数" ≤ `coin_num` 的。
   - 每个选出的币在本签名下新建一条开仓记录（7.4），记下方向、本期 `close`，以及本期的资金分母：固定个数时是 `coin_num`，按百分比时是本期选中的数量（F1-12）。
6. **后置过滤**（F1-11）：每个子策略在本期本签名选中的样本上计算全部后置条件（`rank` / `pct` 也在选中样本上算），任一条件成立就剔除。结果写进对应开仓记录的通过位图（每个子策略一位，见 7.4）。
7. **配权**（F1-12、F1-13）。每期按下面的顺序处理（对应 F1 的 `rolling(h)`：本期加上此前 h−1 个候选行）：
   1. **计数**：上一期留下的每条开仓记录，如果它的币本期有候选行，`Rows` 加 1；本期新开的记录 `Rows = 1`。
   2. **贡献**：对每个子策略 i、每条通过它后置过滤的记录，只要 `Rows ≤ h_i`，并且该币本期有候选行，就计入 `数量 × 本期 close`。其中 `数量 = 0.5 × side_weight / h_i / 资金分母 / 开仓 close`，空头取负。本期没有候选行的币不计入，但记录保留。
   3. **合成**：规则权重 = `Σ 子策略 stg_weight × 贡献 / Σ stg_weight × weight.total`。全程用精确有理数，只在组合层截断。
   4. **清理**（输出之后）：`Rows ≥ 组内最大的 h`，或者币已不在预期集合里的记录，删除。

   举例：h = 1 时，记录只在开仓那一期有贡献（`Rows = 1 ≤ 1`）。h = 3 时，在开仓那一期和之后两个有候选行的期次有贡献，中间没有候选行的期次跳过、不计数。

### 7.3 守门与缺数

- **集合划分（f1 专用）**：f1 规则不走 `partitionRule` 的"所有引用列都要有值"。缺数集合只包含 E(r) 里本期没有行、`close` 或 `volume` 为空，或 K 线 `source_failed` 的标的。因子列为空**不算缺数**：选币时按 F1-2 补中位数或保持 NaN，过滤时按 F1-9 计算。
- **守门**：`max_missing` 和 `min_universe` 按上面的缺数集合与候选行 B 计算。U 为空时仍然整期 `no_data`。
- **空洞冻结**：因为 f1 规则不和其他规则混用（7.1），含 f1 规则的程序不计算冻结集合，`frozenSet` 直接返回空。持仓到期只看候选行，和 F1 一致。
- **年龄**：沿用策略级 `universe.min_age_bars`（seal999 时为 999，近似）。

### 7.4 状态与明细

**状态**：`RuleState` 新增 `F1` 字段，写进 `c_rule_states_json`。

```go
type F1State struct {
    Groups []F1Group `json:"groups"` // 按排名签名的哈希排序
}
type F1Group struct {
    Key   string   `json:"key"`   // 排名签名的哈希；组内子策略按展开顺序编号
    Picks []F1Pick `json:"picks"` // 仍然有效的开仓记录，按（开仓 bar, 标的）排序
}
type F1Pick struct {
    Bar   int64  `json:"bar"`             // 开仓的 bar 序号
    ID    string `json:"id"`
    Short bool   `json:"short,omitempty"`
    Close string `json:"close"`           // 开仓 close，原样保存
    Denom int    `json:"denom"`           // 资金分母（F1-12）
    Rows  int    `json:"rows"`            // 自开仓以来该币的候选行数（含开仓那一行）
    Pass  string `json:"pass"`            // 组内各子策略的后置过滤是否通过，位图的十六进制
}
```

- **到期按行数**：一条开仓记录对组内第 i 个子策略在 `Rows ≤ h_i` 时有效（按 7.2 第 7 步的顺序，先计数再判断）。输出之后，`Rows ≥ 组内最大的 h`，或者该币已不在预期集合里（退市、移出名单）的记录整条删除。不再按"最近 max(h) 个切片"裁剪，所以中途缺行、`volume = 0` 的币，仓位能像 F1 一样持有过 h 个日历周期。
- **体积**：正常情况下，FH003 有 32 组，每组约 36 条记录，每条约 80 字节，组内约 61 个子策略的位图约 16 个十六进制字符，合计约 100 KB 一期。
  - 几个币先后被选中、又长期没有候选行时，记录会一起保留，所以条数没有严格上限。
  - 256 KB 是**运行目标，不是硬上限**：超过时不截断（截断会改变结果），在结果摘要里写一条说明并记日志，由 T9.5 观察。
  - T3.12 用"多个币轮流长期缺行"的样本测体积。
- **重启**：重启后从上一条 ok 结果的状态继续。DSL 的参数表变了（`dsl_hash` 不同）就是新版本，需要重新启用；新会话的第一期从空状态开始，和 F1 第一份仓位建立时一样。

**明细**：f1 规则不按（子策略, 标的）落库。每个（规则, 标的）最多一条：
- 有权重的币：阶段 `weighted`，写合计权重，`reason` 为 `f1:<持有该币的子策略数>`；
- 本期被选中、但在全部子策略里都被后置过滤剔除的币：阶段 `dropped`，`reason` 为 `f1_filter_after`；
- 上期持有、本期缺数的币：沿用现有原因。

**摘要**：`RuleSummary` 记子策略数、签名数、本期选中的币数和持仓币数。

### 7.5 不支持的场景

- `StartReplay`（View 回放）、闭环回放、`factor_params`（动态调参）遇到 f1 规则时，明确拒绝并给出中文原因。
- 试算（`ValidateStrategy`）可以用：从空状态在最近一期上求一次值。

## 8. 以后再考虑

- **长 EMA 分块锚定**：把递推起点锚定到绝对序号 `⌊t/B⌋·B − K + 1`，这样仍然点纯，补算的均摊成本降到 O(1 + K/B)。它会改变 `ema` / `sma` 的数值（差异在 1e-9 以内），所以要单独设计和评审。补算或闭环回放 1 年的 5m 数据之前，必须先做这一项。
- **合约回放**：采集资金费率；账本加合约模式（负权重、保证金、资金费、最小下单额）；回放报价支持 `next_vwap`；View 回放根数在 `brief` 模式下放宽到 1 年。
