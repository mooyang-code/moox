## 0. 结论

- 加密货币空间改为**常驻进程接收交易所 WebSocket 推送的收盘 K 线**，按周期提交 Storage。REST 返回里没有闭合标志、合约 REST 要到收盘后约 8 秒才是定稿值（第 1.4 节），所以实时只收 WS 推送，**不做 REST 兜底**：截止时还没到的标的（现货、合约一样）统一交给自动补采。SCF 定时拉取的代码和函数保留，默认不启用，只能用命令手动切回（不做自动切换）。**采集方式按数据集绑定**，不再按空间：同一空间里可以一部分数据集走推送、一部分走拉取。
- WS 模式下数据集的截止时间从 15 秒改为 **1m 5 秒、1h 8 秒**（第 5.11 节）：正常周期约 0.5 秒写完，截止只影响"有标的没到"的周期，让它们的完成标记早发出；1h 多给 3 秒，整点 1m 与 1h 同时提交时不再挤在同一个 5 秒窗口里。
- 写成一个**通用的 WS K 线接收框架**：连接管理、订阅、周期闸门、提交、计划同步、观测都与交易所无关；币安是第一个数据源适配器，以后接 OKX 等只需新增适配器。
- 以后把"一个行情源能做什么"收进**统一的行情源目录**：每个数据源×市场注册一次，按实现的接口声明能力——全市场标的列表、REST K 线、WS K 线（第 5.9 节）。标的同步、SCF 取数、stream 接收都从目录取，不再各自写装配开关。**这是独立的重构，不是 WS 上线的前提，排在切换之后做**；WS 只需要标的快照多带一个 `Pair` 字段。stream 进程本身不拉标的列表，标的与 SCF 一样来自 Collector 的采集计划。
- 采集层有一个与采集方式无关的 **K 线数据模型**：推送、SCF 拉取、本地拉取、补采都只产出同样的 K 线批次，经同一个提交器写 Storage（第 5.12 节）。
- **补采不必调 SCF**：拉取与补采的处理函数同时提供云函数入口和本地服务入口，按配置选执行端；`collector-stream` 所在的香港机上跑本地执行端，crypto 的自动补采走它（第 6.7 节）。
- 进程是服务目录里的新组件 `collector-stream`，放在海外机（香港 compute-1）的部署单元里，由 `moox-runtime` 托管。单点可接受，故障时手动切回 SCF；升级只在约定的时间窗口做。停机、重启期间缺的周期由自动补采补齐，下游因子必须等缺口补齐才推进水位（第 7.4、7.5 节）。
- 合约必须订阅**连续合约 K 线**（`<pair>_perpetual@continuousKline_<周期>`），不能用普通 K 线（`<symbol>@kline_<周期>`）：普通 K 线冷门标的要等下一笔成交或 3 秒才收盘，连续合约 K 线固定在收盘后约 0.1 秒收盘，数值一致。
- 标的列表与 SCF 一样来自 Collector 的采集计划；下架的标的由推送侧探测后立即触发标签同步（第 5.10 节）；采集名单干预接口（第 6.6 节）排在切换之后做。
- 实测发现现行 SCF 合约数据**有相当一部分不是定稿值**（成交量、成交额、笔数偏少，收盘价不对）。这个问题与 WS 改造无关，单独先修，见第 8 节。

## 1. 背景与实测

### 1.1 现状

实时采集是"腾讯云定时器每分钟触发 42 个 SCF 函数（现货、合约各 21 个，每个约 25 个标的），函数调 REST 取刚收盘的 K 线，经 Access 用 `CommitTimeSeriesBatch` 提交"。整点币安 REST 接口变慢（约一半请求停住），整点现货 1m 写入完成要 6～7 秒，见[整点取数变慢排查](采集整点取数变慢排查与优化.md)。

| 16:00 整点，中位 | 193 | 6184 | 551 | 2855 |
| 16:00 整点，最后一个标的 | 290 | 6919 | 3043 | 4216 |

连续合约 K 线（第 1.3 节）全量验证（16:59～18:14 UTC，全部 524 个合约标的，1m 73 个周期、1h 2 个周期，含 17:00、18:00 两个整点）：每个周期 524 个标的全部收到定稿（含没有成交的分钟），服务端收盘时间中位 102 毫秒、最大 118 毫秒，本机到达每周期最后一个标的中位 152 毫秒、最大 191 毫秒；1m 38252 根、1h 1048 根与稳定基准 100% 一致。

### 1.4 定稿：哪些值可以进周期提交

以收盘 1 分钟后再取的 REST 历史 K 线为基准（已稳定），16:33～16:36 共 180 个标的的比对：

| 来源 | 现货 | 合约-活跃 | 合约-冷门 |
| --- | --- | --- | --- |
| WS 普通 K 线 `x=true` | 100% | 100% | 100% |
| WS 连续合约 K 线 `x=true` | — | 100% | 100% |
| REST 收盘后 0.6 秒 | 99.2% | 13% | 65% |
| REST 收盘后 1.5 秒 | 99.6% | 31.5% | 73% |
| REST 收盘后 5 秒 | 100% | 86% | 99% |
| 收盘前最后一条未收盘推送 | 91% | 25% | 48% |
| 用逐笔成交（`aggTrade`）自己聚合 | — | 98.3%（跨分钟的成交归属与 K 线不一致） | |

结论：

- 现货与合约的 WS 收盘推送都是定稿值。
- **合约 REST 在收盘后几秒内返回的是未定稿的 K 线**：成交量只会偏少、不会偏多，收盘价也可能不是最后一笔。现货 REST 0.6 秒就基本定稿。
- 收盘前的快照、自己聚合逐笔成交都对不上，不能用来替代收盘推送。

| --- | --- | --- | --- |
| 3 秒 | 100% | 59.3% | 93.9% |
| 8 秒 | 100% | 100% | 100% |
| 12／20／30 秒 | 100% | 100% | 100% |

合约 REST 要到收盘后 5～8 秒之间才定稿（5 秒时活跃标的 86%，8 秒起全部一致；6、7 秒未测），整点与普通分钟一样。

两点补充（10-21 实测与文档核对）：

- **REST 返回里没有闭合标志。** 币安 K 线接口每根返回开盘时间、开高低收、成交量、收盘时间、成交额、笔数、主动买入量／额与一个保留字段；"收盘时间"是固定的开盘时间 + 59999 毫秒，K 线还在变时就已经是这个值。现行 SCF 判断"已收盘"只看本机时间是否晚于它（`sources/binance/kline.go:221`），不代表交易所已经算完。
- **连续合约 K 线的 REST 接口同样慢。** 同时取 `/fapi/v1/klines` 与 `/fapi/v1/continuousKlines`（60 个合约标的、8 分钟）：0.6 秒时活跃标的都约 32%、冷门约 80%，1.5 秒约 70%／92%，3 秒约 89%／97%，两者几乎相同。推送侧的连续合约 K 线约 0.1 秒就定稿，REST 侧没有这个特性，慢在 REST 的数据更新本身。

## 2. 目标与非目标

目标：

1. 加密货币空间 1m、1h 的实时 K 线由 WS 推送采集，现货整点写入完成从 6～7 秒降到 1 秒以内，合约在 1 秒以内；写入的都是定稿值。
2. 框架与交易所无关：新增数据源只写适配器（第 5.2 节的接口），不改连接管理、周期闸门、提交与 Collector。
3. 复用现有采集计划（数据集、标的快照、序号、生效周期）与 Storage 周期协议，不改 Storage。
4. SCF 实时采集保留为备用，系统初始化时默认关闭；加密空间的数据集默认 WS；可以用命令按生效周期在 WS 与 SCF 之间手动切换，不做自动切换。

非目标：

- 不做 WS 进程的多活或自动切换（单点可接受）。
- 不做 REST 兜底：截止前没到的标的一律交给自动补采（第 5.6 节）。
- 不改补采的流程（缺口扫描、分块、复查、缺失判定）：只把"调谁执行"抽成可配置的执行端（第 6.7 节）。
- 不覆盖 A 股（stockcn 仍是 SCF 定时拉取）。
- 不新增数据列；行情来源（WS 推送、SCF 备用或补采）只记在写入来源与指标里。

## 3. 硬约束（来自 Storage 周期协议，不能绕开）

1. **进入周期提交的只能是定稿值。** DataNode 在一个周期的全部序列都提交成功的那一刻就把周期定为 `complete`（`period_progress.go` 的 `finalizePeriodBaseLocked`），之后对该周期的 `CommitTimeSeriesBatch` 只返回回执、**不写行**；过了截止时间也一样。下游（因子、策略）在周期完成事件到达时就读了数据。所以"先写临时值、以后补取覆盖"在周期提交里做不到。事后修正只能走普通写入（`UpsertFields`，与补采同一路径），而且下游已经算过的结果不会自动重算。
2. **截止时间是收盘＋`lateness_s`。** 取值是数据集属性 `allowed_lateness_seconds`：PrimaryStore 每次提交都读这个属性随请求带给 DataNode（`primarystore/period.go` 的 `datasetAllowedLateness`），DataNode 只在周期第一次提交、懒建周期时用它算出截止并固化（`datanode/pebble/period_snapshot.go` 的 `planLazyPeriod`；属性缺失时默认 60 秒），所以改属性只影响之后建立的周期。线上 crypto 的 1m、1h 数据集现在都是 15 秒（空间默认值）。截止前没提交的序列在周期标记里记为失败，由自动补采补齐。**stream 模式改为 1m 5 秒、1h 8 秒，SCF 模式现货保持 15 秒、合约放宽到 20 秒**（第 5.11、8 节）。
3. **同一周期最好只有一个写入方，但短暂双写不会写错数据。** 两个写入方写同一周期，先写全的那个让周期完成，后到的被丢弃；都只写了一部分时两边的行合在一起。两边写的都是定稿值（SCF 按第 8 节推迟到定稿后取数），行构造与写入 ID 规则相同（第 5.5 节），提交是幂等的，结果与单写一致。所以切换仍按生效周期交接（第 6.3 节），但不需要租约、写授权之类的防双写机制。
4. **序列身份不能变。** 行键里的 `series_tag` 是 `venue:binance|market:spot|source:spot_http`（合约为 `swap`／`swap_http`）。WS 写入沿用同一个 `series_tag` 与 `source_id`，否则就是新序列，历史窗口断开。`source_id` 里的 `http` 是历史命名，表示"币安现货 K 线"这个来源，不表示传输方式。

## 4. 总体架构

```text
control 主机
  Collector
    ├─ 计划对账（每空间每分钟）：任务与标签 → 数据集标的快照 → 生效周期 P → Storage 登记快照
    │     ├─ 数据集 ingest=pull   → 下发 SCF 函数环境变量（现状）
    │     └─ 数据集 ingest=stream → 写入 stream 计划版本，等 collector-stream 心跳确认
    ├─ StreamCollector 服务（新）：心跳、拉计划、上报周期统计
    └─ 自动补采：流程不变，按数据集的 executor 调 SCF 补采函数或香港机的本地执行端

海外机 compute-1（香港，overseas 单元）
  collector-stream（新组件，moox-runtime 托管）
    ├─ 计划同步：每 10 秒心跳，计划版本变化时拉取
    ├─ 数据源适配器：binance（现货、合约），以后 okx …
    ├─ 连接管理：分片、订阅、保活、重连、24 小时前主动轮换
    ├─ 周期闸门：按（数据集, 频率, 周期）收集收盘推送；齐了立即提交；不齐时到最晚提交时刻提交已到的，缺的交给补采；截止 1m 5 秒、1h 8 秒
    ├─ 提交：KlineCommitter（与 SCF、补采共用）→ host-gateway → Storage PrimaryStore
    └─ 本地执行端 MarketFetchExecutor：执行补采（以及切回拉取时的定时拉取），与 SCF 函数同一套处理代码
```

与 SCF 相比：取数从"每分钟 42 个函数各自发 25 个 REST 请求"变成"4 条常驻连接被动接收"；写入方从 42 个函数变成 1 个进程；计划、快照、周期协议、补采流程不变。

## 5. 通用框架（`modules/collector/internal/stream`）

### 5.1 分层

| 层 | 职责 | 与交易所有关吗 |
| --- | --- | --- |
| 数据源适配器 `Source` | 连接地址、流命名、订阅／退订报文、解码、保活、限额 | 是，每个交易所×市场一个 |
| 连接管理 `ConnManager` | 按流数分片、拨号、订阅限速、重连退避、主动轮换、差量订阅 | 否 |
| 周期闸门 `PeriodGate` | 按周期收集定稿、判断齐备、触发提交、处理迟到 | 否 |
| 提交 `Committer` | 行构造、周期提交、失败上报 | 否（复用 `marketfetch`） |
| 计划客户端 `PlanClient` | 心跳、拉取计划、上报统计 | 否 |
| 观测 | 指标、日志、健康检查 | 否 |

### 5.2 数据源适配器接口

```go
// Source 是一个交易所的一个市场（例如币安现货、币安 U 本位永续）的 WS K 线来源。
type Source interface {
    // Key 与 marketdata 注册表里的 SourceKey 一致（provider + source_id），用来构造 series_tag。
    Key() marketdata.SourceKey
    MarketType() string
    // Endpoints 按优先级返回连接地址；连接管理按顺序尝试，失败后退避换下一个。
    Endpoints() []string
    // Limits 是连接与订阅的限额。
    Limits() Limits
    // Stream 返回一个（交易所 symbol, 频率）对应的流名；不支持的频率返回 false。
    Stream(symbol string, frequency marketdata.Frequency) (string, bool)
    // Subscribe / Unsubscribe 构造订阅报文；一条报文最多 Limits.StreamsPerMessage 个流。
    Subscribe(streams []string, id int) ([]byte, error)
    Unsubscribe(streams []string, id int) ([]byte, error)
    // Decode 把一条原始消息解成零到多个事件；订阅回执、心跳等控制消息返回 Control 事件。
    Decode(raw []byte, receivedAt time.Time) ([]Event, error)
    // Keepalive 说明保活方式：服务端 ping（回 pong）或客户端定时发送的报文。
    Keepalive() Keepalive
}

type Limits struct {
    StreamsPerConn    int           // 币安 1024，按 1000 用
    StreamsPerMessage int           // 一条订阅报文的流数，币安 100
    MessagesPerSecond int           // 入站限速，币安 5
    MaxConnAge        time.Duration // 交易所强制断开的寿命，币安 24h
    ConnectsPerWindow int           // 建连限速（币安每 IP 5 分钟 300 次），只做保护
}

type Keepalive struct {
    ServerPing  bool          // 收到 ping 回 pong（币安）
    ClientPing  []byte        // 客户端定时发送的报文（例如某些交易所要求发文本 "ping"）
    Interval    time.Duration // 客户端发送间隔
    ReadTimeout time.Duration // 这么久没有任何消息就判定连接失效并重连
}

// Event 是解码后的一条消息。只有 Final 为真的 K 线才进周期闸门。
type Event struct {
    Kind    EventKind // KlineUpdate / KlineFinal / Control / Error
    Symbol  string    // 交易所 symbol（大写）
    Kline   marketdata.NormalizedKline // 已填 ProviderID、SourceID、Frequency、BarStart/BarEnd、OHLCV、成交额、笔数
    EventAt time.Time // 交易所事件时间，用来算服务端延迟
}
```

要点：

- **定稿标志由适配器显式给出**（币安是 `k.x == true`）。闸门只接受 `KlineFinal`，`KlineUpdate` 只用于观测（可选）。
- 适配器只负责"协议"，不做重连、不持有状态（除订阅 ID 生成外），便于用录制的报文做单元测试。
- 一个交易所的不同市场是不同 `Source`（现货、合约分别实现，或同一类型不同参数）。
- 交易所 symbol 与 `subject_id` 的映射沿用采集计划的 `ExchangeSymbol`（例外表优先，否则 crypto 去掉连字符）。

### 5.3 连接管理

- **分片**：一个 `Source` 的全部流（标的 × 频率）按 `StreamsPerConn` 切成若干连接；1m 与 1h 分开连接（1h 的流整点才有定稿，分开便于观察）。币安现货 1m、现货 1h、合约 1m、合约 1h 各一条，共 4 条。
- **订阅**：连接建立后按 `StreamsPerMessage` 分批发送订阅，批间间隔满足 `MessagesPerSecond`；校验每条回执，回执报错的流记入事件并在下次重连时重试。
- **差量订阅**：计划变化时对比新旧流集合，只发退订与新增订阅；某条连接超过上限时新开连接。新计划的生效周期 P 至少在 2 分钟之后（`planLeadTime`），所以**新增的标的拿到计划就订阅**（P 之前收到的定稿不进闸门），**移除的标的等它最后负责的那个周期提交之后再退订**；闸门始终按每个周期生效的那份 copy 判断期望标的。
- **保活与失效判定**：按 `Keepalive` 回 pong 或定时发报文；`ReadTimeout`（默认 60 秒）内收不到任何消息就关闭重连。
- **重连**：指数退避加抖动（1 秒起，最长 30 秒），按 `Endpoints` 轮换；重连后重新订阅全部流。
- **主动轮换**：连接寿命到 `MaxConnAge − 30 分钟`时，在非整点、分钟第 20～40 秒之间新建一条连接、订阅完同一组流、确认收到消息后再关闭旧连接；轮换期间两条连接的事件都交给闸门，闸门按（周期, 标的）去重。这样 24 小时强制断开不会造成缺数。
- **断线期间缺的定稿**：不在连接层补，在截止时记为失败、由自动补采补齐（第 5.4、7.4 节）；所以主动轮换比事后补救更重要。

### 5.4 周期闸门

闸门按（数据集, 频率, 周期）维护一个"待提交周期"，周期的期望标的集合来自计划里该周期生效的那份（`PlanDataset.SelectCopy`，与 SCF 相同）。

```text
收盘时刻 C 到达（定时器主动建立这一期，不等第一条推送）
  ├─ 收到定稿：记入（同一标的重复的定稿忽略，数值不同时记告警）
  ├─ 期望标的全部到齐 → 立即提交（通常 C + 0.1～0.3 秒）
  ├─ 提交时刻：全部到齐，或到达最晚开始提交的时刻 D = C + lateness − 提交预留（默认预留 1 秒：1m 为 C + 4 秒、1h 为 C + 7 秒；预留要容得下同一截止的全部数据集串行提交完，见第 7.3 节）
  │     → 一次 CommitTimeSeriesBatch（每数据集一次，见 5.5）
  │     → 仍缺的标的不另行上报：截止时 DataNode 把没有提交成功的序列记为失败（`periodMarkerSubjects`），自动补采之后会补
  └─ 提交之后才到的定稿：计数（late_after_commit），截止前再增量提交一次：周期仍是 waiting 且未到截止时，再次部分提交会并入成功位图（`datanode/pebble/period_progress.go` 的 `CommitTimeSeriesBatch`；现在 SCF 各函数分别提交同一周期也靠这一点）
```

实现：

1. **并发模型**：每个（数据集, 频率）一个闸门协程，独占自己的状态、不加锁；连接协程解码后把事件投进它的通道。提交由独立的提交协程执行，闸门不阻塞在网络上。
2. **状态**：`pending map[周期开始时间]*periodSlot`；slot 里有该周期生效的计划 copy（期望标的与序号）、按序号存的 K 线数组与已到位图、状态 `collecting | committing | committed`、最后一个到达的时刻。
3. **建立周期**：收盘时刻 C 由定时器建立 slot，所以一条推送都没来的周期也能统计为"零到达"；收到 `BarStart` 晚于当前周期的推送时也就地建立（时钟稍慢的保护）。
4. **收到 `x=true`**：按 `BarStart` 找 slot，用 copy 的交易所符号映射找序号；不在期望集合里的丢弃计数（含 P 之前就已订阅的新标的）；重复的忽略、数值不同告警（轮换期间两条连接靠这个去重）；到齐即把 slot 交给提交协程。
5. **最晚提交时刻 D**：slot 建立时同时挂一个定时器，到 D 还没到齐就提交已到的；一个都没到就不提交，只上报零到达。定时器按本机单调时钟走，机器开 NTP。
6. **提交协程**：一个按截止时间排序的队列，截止早的先发，所以整点 1m 自然排在 1h 之前。提交用 `KlineCommitter`（第 5.12 节），写入 ID 按内容生成；失败按 300 毫秒间隔重试，重试到截止前 200 毫秒为止。
7. **回收**：截止后再保留一个周期就删除 slot；每个频率内存里同时最多 2 个 slot（约 2 × 524 根 K 线）。
8. **计划变化**：每个 slot 只看自己周期的 copy；新计划从 P 起生效，不影响已建立的 slot。
9. **上报**：每个 slot 结束时生成一条统计（到达数、截止时仍缺的标的、最后一个到达的时刻、提交完成时刻、迟到数），交给 `ReportStreamPeriods` 与指标。
10. **测试**：时钟与定时器注入假时钟，提交注入假 Storage；覆盖到齐即提交、D 时提交已到的、零到达、重复去重、跨 P 切换 copy、整点 1m 先于 1h。

- 一个周期一行都没提交成功时 DataNode 不会建立这个周期（周期在第一次提交时才建立），也就没有完成标记；与 SCF 全部函数失败时相同，由自动补采的缺口扫描补齐。
- 1h 与 1m 独立闸门；整点同时有 1m、1h 两个周期。
- 适配器给出的交易所事件时间只用于观测。
- 进程重启时丢弃内存里的待提交周期；重启后第一个完整周期从下一个收盘开始，期间的缺口由自动补采补齐（第 7.4 节）。

### 5.5 提交

- **复用 SCF 的行构造与周期绑定**（即第 5.12 节的 `KlineCommitter`）：把 `KlinePipeline.Execute` 里"由标准化 K 线构造行（`rowFor`）→ 按数据集分组 → `periodCommitForDataset` → `CommitTimeSeriesBatch`"这一段抽成独立的 `KlineCommitter`，SCF 与 stream 共用，保证两边写出的行逐字节一致（字段、`series_tag`、`source_id`、写入 ID 规则）。
- **请求的构造**：stream 进程用计划构造与 SCF 相同的 `PlannedRequest`（`Plan.BuildRequests` 的同一套目标、序号、hash、总数），只是 `Items` 的数据来自推送，而不是 REST。
- **一个周期一个数据集一次提交**：现货 1m 511 行、合约 1m 524 行，每行约 290 字节（压缩前），一次约 150KB。不分片：Storage 与 Collector 对一次提交没有条数上限，网关请求体上限 4MB（`servicecatalog.DefaultMaxBodyBytes`），分片也不减少串行总耗时（第 7.3 节）。
- **写入 ID**：沿用 `WriteIDByContent`，同一内容重试复用同一 ID。
- **写入来源**：`writeSource` 取 `collector-stream`，便于在 Storage 与 Monitor 区分写入方。
- **失败**：提交失败按 300 毫秒间隔重试，重试到截止前 200 毫秒为止（与第 5.4 节相同）；最终失败的标的留给截止判定与补采。

### 5.6 不做 REST 兜底

截止前没到的标的（现货、合约一样）不调 REST 补，截止时由 DataNode 记为失败，自动补采按稳定后的历史 K 线补齐。理由：

- REST 要晚于定稿时间才可信：现货收盘后 3 秒、合约 8 秒（第 1.4 节）。合约 8 秒不早于 1m 5 秒、1h 8 秒的截止，本来就兜不了；现货要在 3～4 秒之间返回，整点 REST 常停 2 秒以上，正好在最需要的时候来不及。
- 普通分钟里 WS 几乎不缺（实测现货、连续合约 K 线全量每个周期都到齐），兜底很少触发，却要多一层取数、一套定稿时间规则和配置。
- 一旦把未定稿的 REST 值提交，周期就完成了，之后到的正确推送也改不了；不兜底就没有这个风险。

上线后看"截止时仍缺的标的数"指标（第 6.5 节）；如果长期明显不为 0，再评估是否给现货加兜底。

### 5.8 接入新数据源（以 OKX 为例）的清单

新数据源只实现 `Source`；REST `KlineFetcher` 用于补采与 SCF 备用，不用于实时兜底。实现前要对照该交易所文档核实以下各项（OKX 的具体协议**未核实**，下面只列需要确认的问题）：

1. 公共行情的 WS 地址，K 线频道属于哪个路由；
2. 订阅报文格式、每条报文与每条连接的频道上限、订阅限速、建连限速；
3. 保活方式（客户端是否要定时发送报文、间隔多少）；
4. K 线推送里**有没有显式的"已收盘"标志**；没有的话怎样判断定稿（例如收到下一根的第一条更新）——这决定能否用于周期提交；
5. 收盘推送相对收盘的延迟分布、冷门标的是否像币安合约那样延迟；
6. REST K 线在收盘后多久定稿（决定 SCF 备用链路的取数时刻），按第 1.4 节的方法实测；
7. 连接寿命与强制断开规则；
8. 标的命名与 `subject_id` 的映射。

上线前用与本次相同的方法（全量订阅、与稳定后的 REST 基准逐条比对、覆盖整点）验收。

### 5.9 统一的行情源目录（标的列表、REST K 线、WS K 线；切换之后做）

**现状。** 能力接口已经统一在 `marketdata`：`MarketProvider`（描述：provider、source_id、域名、状态）、`InstrumentFetcher`（全市场标的快照 `FetchInstrumentSnapshot`）、`KlineFetcher`（REST K 线 `FetchKlines`），币安的 `MarketDataAdapter` 一个类型同时实现后两者，A 股各数据源也按同样接口实现。不统一的是**装配**——"有哪些数据源、怎样构造"写死在三处：

| 用途 | 位置 | 做法 |
| --- | --- | --- |
| 标的同步（自动标签成员、属性维护） | `marketwiring/subject_listers.go` 的 `NewSubjectListers` | 手写币安现货、合约两项，再按 A 股路由配置逐个构造数据源，包成 `subjectsync.Lister` |
| SCF 取数（加密、可转债、指数） | `marketwiring/market_runtime.go` 的 `newMarketProvider` | 按 `marketID`／`instrumentType`／`providerID`／`sourceID` 的 `if/switch` 构造，每条流水线新建一个只有一个数据源的 `Registry` |
| SCF 取数（A 股） | `marketwiring/stock_runtime.go` 的 `newStockCNProviderForSource` | 另一套按 provider 名称的 `switch` |

结果是：同一个数据源在三处各构造一次（HTTP 客户端、配置来源也各不相同：标的同步走出口代理客户端，SCF 走函数内的共享客户端）；新增一个交易所要改三处开关，WS 如果再加一处就是第四处。目前实现了标的快照的只有币安与 A 股的新浪、东方财富、百度（指数、可转债、腾讯、通达信只有 K 线），目录能直接看出每个数据源有哪些能力。

**方案：一个目录，按能力取用。**

```go
// Factory 构造一个数据源实例；Deps 由使用方注入（HTTP 客户端、DNS 路由、配置目录等），
// 同一个数据源在 Collector（标的同步）、SCF（取数）、collector-stream（接收）里用同一个工厂。
type Factory func(Deps) (MarketProvider, error)

type CatalogEntry struct {
    Key        SourceKey      // provider + source_id，例如 binance/swap_http
    MarketID   MarketID       // crypto / stockcn …
    Instrument InstrumentType // spot / swap / equity …
    New        Factory
}

// Catalog 是全部数据源的登记表；每个数据源包在 init 或显式 Register 里登记自己。
type Catalog struct{ entries []CatalogEntry }

func (c *Catalog) Listers(deps Deps) (map[ListerKey]InstrumentFetcher, error) // 实现了 InstrumentFetcher 的
func (c *Catalog) Kline(key SourceKey, deps Deps) (KlineFetcher, error)      // 实现了 KlineFetcher 的
// stream 包里：provider.(stream.Provider) 取得 WS 适配器（stream 依赖 marketdata，反过来不依赖）
```

- **能力由接口决定**：数据源实现了 `InstrumentFetcher` 就能用于标的同步，实现了 `KlineFetcher` 就能用于 SCF 取数与补采，实现了 `stream.Provider`（返回第 5.2 节的 `Source`）就能用于 WS 接收。不需要另写能力清单。
- **一个数据源一处构造**：`NewSubjectListers`、`newMarketProvider`、`newStockCNProviderForSource` 改为从目录取；A 股按路由配置决定启用哪些数据源，仍在工厂里读配置。
- **标的身份一致**：`subject_id` 与交易所 symbol 的映射只在数据源的标的快照里产生（`Instrument.SubjectID`／`ProviderSymbol`），经标签成员进入采集计划（`ExchangeSymbol`、符号例外）；SCF 取数、WS 订阅、补采都用计划里的同一个映射，WS 不另写一套。
- **合约的连续合约 K 线需要 `pair`**：币安合约标的快照已经只保留 `TRADING` 且 `PERPETUAL` 的合约（`binance/client/swap.go`），目前 USDT 永续的 `pair` 与 `symbol` 相同。`Instrument` 增加可选的 `Pair` 字段，由标的快照带出；WS 适配器订阅前校验，`pair` 与 `symbol` 不同的标的按 `pair` 订阅、按 `symbol` 写入。
- **新增交易所（例如 OKX）只加一个包**：实现 `MarketProvider` + `InstrumentFetcher` + `KlineFetcher` + `stream.Provider`，在目录里登记，标的同步、SCF、stream 都能用；不改 `marketwiring`、`subjectsync`、`stream` 框架。

这一步是纯重构，行为不变，**不是 WS 上线的前提**：WS 只需要 `Instrument.Pair`（随币安适配器一起加），目录重构排在切换之后（执行计划阶段 8）。

### 5.10 标的下架（或停牌）而计划还没更新

**会发生什么。** 标的从交易所下架后，要等到下一次自动标签刷新（币安现货每小时第 13 分、永续第 17 分）把它从标签成员里去掉（`ApplyTagSnapshot` 把快照里没有的成员立即置为 inactive，没有逐个标的的防抖），再经过对账（每分钟一轮）和新计划的提前量（2 分钟），计划才不再包含它，最长约 1 小时 3 分钟。这期间每个周期仍期望它：WS 收不到它的定稿，于是这个周期**不会卡住**，而是到截止时间由 DataNode 定为 `degraded`、把它记为失败；因子按降级周期继续计算已到的标的、水位照常前进，缺的标的记入空洞账本（第 7.5 节）；自动补采之后会把它确认为行情源缺失（`t_collector_source_absences`），确认没有数据的不再补算。

截止时间 = 收盘 + 数据集的 `allowed_lateness_seconds`：任务没有指定时按空间默认值，crypto 是 15 秒（`domain.DefaultAllowedLatenessSeconds`；stockcn 90 秒，其他 60 秒），线上 crypto 的 1m、1h 四个数据集都是 15 秒。所以代价是这段时间里**每个周期的完成标记都要等到截止**才出来：SCF 模式收盘后 15 秒，stream 模式是 1m 5 秒、1h 8 秒（第 5.11 节）。

**对策：**

1. **先提交已到的**：闸门到最晚提交时刻 D 就提交已有的标的，不等截止；完成标记仍要等截止，但数据先进库。
2. **尽早发现下架**：
   - 合约：订阅 `!contractInfo`（`/market` 路由，合约上下架、交割时推送，带合约状态），状态离开 `TRADING` 即判定；
   - 现货与合约通用：某标的连续 3 个 1m 周期没有收盘推送时，判定为"疑似下架"（只看 1m，1h 跟随 1m 的判定，否则要等 3 小时）。
3. **立即同步标签**：stream 在 `ReportStreamPeriods` 里带上疑似下架的标的，Collector 收到后立即对相应的自动标签做一次快照同步（等同 `SyncSubjects`，不等 cron）。标签成员按快照直接更新，**不设防抖**；防止"交易所接口偶尔返回不全"由取数内部的重试与校验负责：标的快照请求失败或校验不通过（`ValidateInstrumentSnapshot`：必须完整、按交易所计数一致、不能为空）时在本次同步内退避重试（例如 3 次，间隔 2、4 秒），都失败就保持原成员不变并上报失败，绝不用一份残缺的快照去更新成员。从下架到计划去掉它约 4～5 分钟（3 个周期判定 + 同步 + 不到 1 分钟的对账 + 2 分钟提前量）。
4. **停牌不等于下架**：快照显示仍在交易（或暂停但未下架）时成员不变，按行情源缺失处理，由补采确认。
5. **人工或旁路程序直接干预**（第 6.6 节，切换之后做；在此之前可以手动调 `SyncSubjects`）：知道某个标的要下架（例如交易所提前公告）时，不必等探测，直接把它从采集名单里排除。

### 5.11 stream 模式的截止时间：1m 5 秒、1h 8 秒

WS 收齐全部标的不到 0.3 秒，15 秒的截止只在"有标的没到"时才起作用，却让这种周期的完成标记晚 15 秒。stream 模式把 crypto 1m 数据集的 `allowed_lateness_seconds` 设为 **5 秒**、1h 设为 **8 秒**：

| 项目 | 情况 |
| --- | --- |
| 正常周期 | 不受影响：约 0.3 秒收齐、约 0.5 秒写完，完成标记随最后一次提交立即发出 |
| 有标的没到（下架、个别推送丢失、断线） | 只要这个周期有过提交，完成标记在截止时发出（1m 收盘后 5 秒、1h 8 秒，原来 15 秒），缺的标的由补采补齐 |
| 整个周期一行都没提交（进程停、连接全断） | 周期在第一次提交时才建立，零提交就没有周期、也没有完成标记（与 SCF 全部函数失败时相同），由自动补采的缺口扫描补齐；下游的处理见第 7.5 节 |
| 提交重试 | 1m 约 4 秒、1h 约 7 秒的窗口（提交本身 0.1～0.3 秒），重试间隔 300 毫秒 |
| 整点出站 | 整点 4 个数据集约 664KB：两个 1m 约 330KB 要在 5 秒内发完，两个 1h 在 8 秒内。海外机出带宽标称 1 Mbps，实测秒级峰值约 3.6 Mbps，阶段 0 实测确认；整点先提交 1m、再提交 1h |
| 为什么 1h 是 8 秒 | 1h 对几秒的延迟不敏感；多给 3 秒，整点 1m 与 1h 不再挤在同一个 5 秒窗口里，不需要靠压缩或分片保住 1h |

**SCF 模式仍是 15 秒，合约放宽到 20 秒**（第 8 节）：SCF 合约要到收盘后 8 秒才取数，5 秒来不及。所以截止时间跟着采集方式走，由 Collector 在切换时改（第 6.3 节的 `drain` 步骤）：

- 数据集属性只影响之后建立的周期，而周期在第一次提交时建立。旧执行端最后一个周期（P 的前一根）的第一次提交在收盘 P 之后几百毫秒（stream）到约 9～12 秒（SCF）；新执行端第一个周期（P 那一根）的第一次提交在 P 加一个周期之后。所以改属性的合法区间是（P + 旧模式迟到窗口, P + 一个周期）：前者之后旧周期已不能再建立，后者之前新周期还没建立。`drain` 在**下发最终计划之前**改属性，此时是 `WindowEnd`（P + 旧值）加收尾余量（5 秒），对 1m、1h、两个切换方向都落在区间内（最晚 P + 25 秒），新旧周期各用各自的截止。
- 配置：`stream.lateness_s`（按频率：`1m: 5`、`1h: 8`），SCF 沿用任务或空间默认值（15，合约 20）；任务参数里显式写了 `allowed_lateness_seconds` 的以任务为准、不随模式切换。
- **截止值只有一个计算入口**：现在截止值有两个用处，一是计划内容里的 `PlanDataset.LatenessS`（执行端据此算 `StorageDeadline`，到点就停止取数），二是每次生成新计划时 `EnsureAllowedLateness` 按它回写的 Storage 属性。两处都取期望状态里的同一个值（`plan_desired.go` 现在按"任务值 → 空间默认值"取），改为"任务值 → 数据集当前采集方式的默认值"。只改 Storage 属性会出两种错：SCF 按计划里的旧值提前停止，或者下一份计划把属性改回旧值。交接计划里旧执行端那一份写旧模式的值（`WindowEnd` 也按它算），新执行端那一份直接写新模式的值（它只负责 P 起的周期，这些周期按新值建立），不依赖最终计划及时送达；最终计划都写新值；新建的数据集直接按当前方式取值，不经过 `drain`。

### 5.12 与采集方式无关的 K 线数据模型

采集方式（推送、拉取）和执行端（SCF、本地）不同，但交给 Storage 的数据接口是同一个。采集层按数据类型定义模型，K 线是第一个：

- **数据**：沿用 `marketdata.NormalizedKline`（REST、SCF、A 股已经在用）。其上加一层批次：`KlineBatch{SpaceID, DatasetID, Frequency, Period, Copy, Bars []NormalizedKline, Origin}`，`Copy` 是该周期生效的计划 copy（期望标的、序号、hash），`Origin` 取 `stream | pull | backfill`，只用于写入来源与指标。
- **写入**：`KlineCommitter`（从 `KlinePipeline.Execute` 抽出）提供两个方法：`CommitPeriod(batch)` 走周期提交（实时），`Upsert(batch)` 走普通写入（补采）。行构造、`series_tag`、`source_id`、写入 ID 都只在这里，保证不同来源写出的行逐字节一致。
- **来源**：WS 接收（周期闸门）、SCF 定时拉取、本地定时拉取、补采都只负责产出 `KlineBatch`，不各自写 Storage。
- **其他数据类型**：以后的资金费率、盘口快照等各自定义模型与 Committer，采集方式与执行端这一层不变。

## 6. Collector 侧

### 6.1 采集方式（按数据集绑定）

- **每个数据集一个采集方式** `ingest`：`stream`（WS 推送）或 `pull`（定时拉取）；拉取再配执行端 `executor`：`scf`（云函数）或 `local`（本地执行端，第 6.7 节）。不再按空间绑定：同一空间里可以合约 1m 走推送、现货 1d 走拉取。
- **存储与初值**：运行时的当前值保存在 Collector 库（按数据集一行），由命令切换（第 6.3 节）。新数据集的初值取空间默认值：Collector `app.yaml` 的 `scf_plan.spaces.<空间>.default_ingest`；数据集任务参数里可以显式指定，指定了的以任务为准。
- **系统初始化**（`moox setup init` / `setup deploy` 渲染 Collector 配置时）：加密空间默认 `stream`，A 股默认 `pull`（executor `scf`）；`moox.toml` 的 `[[scf_plan.spaces]]` 可写 `default_ingest` 覆盖。`collector-stream` 默认放进海外机的放置清单。用到 SCF 执行端时仍需要云账号与代码包，所以 `[scf_plan]` 的云账号与地域配置照旧。
- **截止时间跟着数据集的采集方式走**：stream 的数据集 1m 5 秒、1h 8 秒，拉取的数据集按第 5.11 节。

### 6.2 计划

- **期望状态与快照不变**：仍由任务与标签成员算出每个数据集的标的集合、hash、序号与生效周期 P，并在 Storage 登记快照。
- **分配不同**：每个市场只有一个"stream 分配"，包含该市场 `ingest=stream` 的全部数据集与全部标的；（不受每函数 25 个、每函数 200 个、环境变量 4KB 的限制）；SCF 函数的分配只包含 `ingest=pull, executor=scf` 的数据集；仍用 `Plan` 结构（`market`、`datasets[].copies[]` 的 `from`/`hash`/`count`/`subjects[].i`），只是不经过环境变量编码。
- **stream 分配是计划内容里的一种执行端**：在 `FetchPlanContent.Functions` 里与 SCF 函数并列，带执行端类型（`scf`／`stream`／`local`），名称如 `stream-crypto-swap`；过渡计划、最终计划、各份 copy、符号例外都按现有结构记录。这样计划记录仍是"谁在什么时候负责哪些标的"的唯一来源：补采按历史计划解析市场与交易所符号（`klinecheck/backfill.go` 的 `datasetMarket` 遍历 `Functions`）不需要另查别处，只需按执行端类型解析市场与来源，再按数据集的 `executor` 选补采执行端（第 6.7 节）。
- **下发与确认**：`collector-stream` 每 10 秒心跳一次，响应里带最新的计划记录 ID 与阶段；变化时用 `PullStreamPlan` 从计划记录里取自己那几项的计划（过渡或最终），再在心跳里回报已应用的计划记录 ID 与阶段；Collector 看到确认才算这一项下发完成，替代 SCF 的"推环境变量 → 读回核对"。
- 对账器内部把"下发到执行端"抽成接口（SCF 舰队与 stream 各一个实现），计划生成、快照登记、生效周期选择、活动日志共用。

### 6.3 手动切换与交接

只做**手动切换**，不做自动切换：Monitor 告警后由操作员判断、执行命令。切换粒度是数据集，生效周期 P 也按数据集选；方案定了就直接切，不做灰度和上线前比对。

- 命令：`moox-cli collector ingest-mode get --space-id crypto [--dataset <id>]`、`moox-cli collector ingest-mode set --dataset <id>|--space-id <空间> --mode stream|pull [--executor scf|local] [--force] [--yes]`（`--space-id` 表示该空间全部数据集；RPC `SetIngestMode`，只允许 `moox-cli`）。
- **按生效周期交接**：切换时对账器生成一份新计划，按频率各选生效周期 P（与现在选 P 的规则相同，P 距现在至少 3 分钟；P 是 K 线开始时间），对每个数据集：旧执行端的最后一份 copy 从 P 起没有标的，新执行端的 copy 从 P 起包含全部标的。标的集合没变，hash、总数、序号都不变，**不需要重新登记快照**（Storage 只核对该周期应生效的 hash，不关心是哪个执行端写的）。P 之前的周期由旧执行端写，P 及以后由新执行端写。
- **步骤**（阶段记在计划进度里，Collector 重启后按阶段续跑）：
  1. `prepare`：生成计划，选 P。
  2. `switch`：同时给旧执行端下发"P 起为空"、给新执行端下发"P 起全部标的"的计划，等两边确认。提交幂等（第 3 节），两边确认的先后不影响正确性：新端先生效时 P 附近可能短暂双写，结果相同；旧端先停、新端到 P 还没确认时，那几个周期无人写，由补采补齐。
  3. `drain`：旧执行端继续负责 P 之前的周期，它最后一个周期 `[P − 1 个周期, P)` 在 P 收盘，所以等到各数据集的 `P + 旧模式迟到窗口 + 收尾余量` 中最晚的那个时刻（即现有的 `WindowEnd`，按旧值计算），先把数据集的截止时间改成新模式的值（第 5.11 节），再下发最终计划，1h 不需要再多等一个整点；SCF 是旧执行端时，这之后才停用定时器（函数保留，代码包仍随发布升级）。
- 切到 `stream`：要求 `collector-stream` 在线（心跳正常），否则拒绝。
- **极端故障时的 `--force`**：旧执行端已经失联、无法确认时（例如 `collector-stream` 进程卡死、海外机网络异常），操作员确认后加 `--force`，不等旧执行端确认，只等新执行端确认就生效。失联的旧端恢复后如果还按旧计划写，与新端写的是同样的定稿值，不会写错；它下一次心跳就会拿到新计划、停止写入。
- **交接与标的变更分开**：交接计划不包含标的变更。对账发现标的集合有变化时，先按现有规则完成那份计划（登记新快照、生效、收尾），再开始交接；交接进行中出现的标的变化等交接完成后再处理。否则同一个 P 上会出现两份 hash。
- **`--force` 遇到未完成的标的变更计划**：对账器有未完成的计划时只推进那份计划（`PlanReconciler.Reconcile` 发现 `open` 就只调 `advance`），如果那份计划正等着已失联的旧执行端确认，交接就永远进不去。所以 `--force` 同样作用于这份已有计划：不再等失联端确认，按它已登记的 hash 和生效周期把它推进完成，然后立即开始交接。期间失联端负责的周期没人写，由补采补齐。

### 6.4 `StreamCollector` 服务（新）

| 方法 | 调用方 | 作用 |
| --- | --- | --- |
| `StreamHeartbeat` | `collector-stream` | 上报进程实例、已应用的计划版本、各连接状态（流数、最近消息时间、重连次数）；返回最新版本号 |
| `PullStreamPlan` | `collector-stream` | 拉取指定空间与市场的计划 |
| `ReportStreamPeriods` | `collector-stream` | 批量上报每个周期的统计：推送到达数、截止时仍缺的标的数、提交耗时、提交完成相对收盘的时间、迟到数、疑似下架的标的 |

- **不设租约、写授权或写权限到期**：提交幂等（第 3 节），短暂双写不会写错数据。同一空间只部署一个 `collector-stream`（服务目录 `replicas: single`），重启时 `moox-runtime` 先停旧进程再起新进程。stream 进程按计划里的 copy 决定从哪个周期起写哪些标的，计划就是唯一的"授权"。
- 心跳只用于计划同步（版本号与确认）、运行状态与告警。没有观察模式：`collector-stream` 只处理计划里分配给它的数据集，没有分配时只保持心跳。

### 6.5 运行状态与监控

- 运行状态页"函数"区按采集方式显示：`stream` 时显示 collector-stream 实例、连接、最近周期的到达／失败、提交完成时间。
- 指标（Collector 汇总后上报）：`moox_collector_stream_online`、`..._period_final_arrivals_total`、`..._period_missed_total`、`..._commit_done_seconds`（相对收盘）、`..._reconnects_total`。
- Monitor 告警：`collector-stream` 心跳中断超过 3 分钟；连续 3 个周期有失败标的（已判定为疑似下架的标的不计入，避免每次下架都误报）；下游因子水位停滞超过 30 分钟（第 7.5 节）。

### 6.6 采集名单干预接口（新，切换之后做）

> 不是 WS 上线的前提：下架探测（第 5.10 节）与手动 `SyncSubjects` 已经覆盖大部分场景，这一节排在切换之后作为独立任务（执行计划阶段 8）。

自动标签的成员来自交易所快照；需要在快照之外临时去掉某些标的（交易所公告下架、数据异常、人工判断）时，提供一层**排除名单**，叠加在标签成员之上：

| 方法 | 作用 |
| --- | --- |
| `SetSubjectExclusions` | 按空间加入一批排除：`subject_ids`、可选的 `market_type`（不填表示该空间所有市场）、`reason`、可选的 `expires_at`（到期自动失效）；同一标的重复设置时更新原因与到期时间 |
| `ClearSubjectExclusions` | 按空间与标的移除排除 |
| `ListSubjectExclusions` | 列出当前生效的排除（含设置人、原因、设置与到期时间） |

- 存储：Collector 库新表 `t_collector_subject_exclusions`（空间、标的、市场、原因、调用方、设置时间、到期时间）。
- 生效方式：对账计算期望状态时，在"任务 × 标签成员"得出的标的集合上去掉排除的标的（`task_groups.go` 计算分组之后、`BuildDesiredState` 之前）。名单一变，下一轮对账（≤1 分钟）就生成新计划、登记新快照，按 2 分钟提前量生效；SCF 与 stream 走同一套计划，两种采集方式都生效。
- 与交接的关系：排除名单的变化属于标的变更，按第 6.3 节"交接与标的变更分开"处理（交接进行中时等交接完成）。
- 不影响标签本身：排除只作用于采集计划，标签成员、标的属性照常同步；排除解除后标的自动回到计划（从新的生效周期起采集，期间的历史需要时用补采）。
- 调用方：`moox-cli`（`moox-cli collector subjects exclude|unexclude|exclusions`）、控制台，以及旁路程序。旁路程序如果不在部署拓扑里，经 Access 用一个外部身份调用（服务目录新增外部身份，例如 `collector-operator`，只放行这三个方法与 `SyncSubjects`）；在拓扑内的组件用内部身份。所有调用写活动日志（`collector.subject_change`）。
- 旁路程序也可以只调 `SyncSubjects` 让某个标签立即按交易所快照刷新（交易所已经下架的情况），不需要排除。

### 6.7 执行端：SCF 与本地两种部署

拉取（定时拉取与补采）的处理代码只有一份，同时提供两种入口，按数据集的 `executor` 选用：

- **现状**：SCF 入口只是一层壳。`serverless/market_data/handler.go` 的 `HandleRequest` 把 JSON 事件交给 `marketwiring.NewHandler()`；补采侧调用的也已经是接口（`klinecheck/backfill.go` 的 `Invoker.Invoke` 与 `Functions(spaceID).EnsureBackfillFunction`）。
- **云函数入口**：`cloudfunction.Start(handler)`，不变。
- **本地入口**：内部 RPC `MarketFetchExecutor.Invoke`，请求体就是现在的事件 JSON，返回同样的 `model.Response`；先挂在 `collector-stream` 进程里（香港机，直连币安），不另起组件。补采并发大时不能拖慢推送接收，所以本地执行端用独立的并发上限（例如 4）和独立的 HTTP 客户端。
- **补采选执行端**：`Invoker` 按数据集的 `executor` 选实现：`scf` 走现有的 `scfinvoker`（先 `EnsureBackfillFunction`），`local` 直接调本地 RPC（不需要建函数）。分块认领、复查、缺失判定都不变；现有的分块租用保证同一分块不会被两个执行端同时执行。crypto 的数据集默认 `executor: local`。
- **定时拉取**：`ingest=pull, executor=local` 时由本地执行端自己按收盘时刻触发，计划从 `PullStreamPlan` 取（与 stream 分配同一条下发通道），不经过云定时器与环境变量。这条路径用于"手动切回拉取但不想用 SCF"的情况。
- **差异**：云函数天然多实例，本地执行端要自己限并发；本地执行端的配置来自组件配置，不来自函数环境变量；SCF 的代码包照常随发布升级，切回 SCF 时可用。
- **服务目录**：`collector-stream` 组件新增服务 `trpc.moox.collector.MarketFetchExecutor`（`acl` 只放 `collector`）。

## 7. `collector-stream` 组件

### 7.1 部署形态：服务目录组件（选定）

| 方案 | 先例 | 取舍 |
| --- | --- | --- |
| **服务目录组件，放在海外机单元，`moox-runtime` 托管（选定）** | trade、egress-proxy | 和其他组件一样由主机守护拉起、`status.sh` 可见、随发布与回滚；内部身份经本机 host-gateway 调 Collector 与 Storage，不需要 Access 签名和外部密钥 |
| 只出站的外部进程，经 Access 外部身份调用 | archive-worker、factor-engine | 适合放在不受部署管理的机器上；需要单独的部署脚本与 systemd 服务、外部身份密钥，与本场景（固定放在已部署的海外机）不匹配 |

两种都要改服务目录（新组件或外部身份、新服务与权限），**Admin、Monitor、各主机 host-gateway、Access 必须用同一提交一起发布**（见[部署与运维](../部署与运维.md)）。

### 7.2 身份与权限

- 组件 ID `collector-stream`，二进制 `moox-collector-stream`（`modules/collector/cmd/stream`，纯 Go）。
- 调用：Collector 的新服务 `StreamCollector` 三个方法（`acl` 只放 `collector-stream`）；Storage `PrimaryStore.CommitTimeSeriesBatch`（不需要 `RecordDatasetPeriodFailures`，它没有对外 RPC，截止判定已覆盖失败）。
- **Storage 写入身份沿用 SCF 的 `moox-collector`**：网关调用身份是 `collector-stream`，但请求体 `AuthInfo` 的 AppId 必须是 `moox-collector`——Storage 的周期 RPC 只接受 Collector 身份（`primarystore/period.go` 的 `validateCollectorPeriodDataset` 经 `isOwnedAppID` 只认 `collector`／`moox-collector`），用 `collector-stream` 作 AppId 会被拒。写入方仍可经 `writeSource=collector-stream` 区分（第 5.5 节）。
- 凭据注入沿用 SCF 现有机制：`marketstorage.storageAuthInfo` 优先读 `MOOX_STORAGE_PRIMARY_AUTH_APP_KEYS_JSON`（AppId → 应用密钥），Collector 给 SCF 函数下发的就是只含 `moox-collector` 一把派生密钥的这个对象（`bootstrap/fetch_plan_config.go` 的 `builtinPlanEnvironment`）。部署端在 control 上用同样的方式生成这一项，注入海外机的 `collector-stream`（`modules/cli/internal/setup/unitdeploy/unit.go` 的 `unitEnvironment` 目前只给 control 上的几个组件，要加上它），**不把主密钥 `MOOX_STORAGE_PRIMARY_AUTH_SECRET` 放到海外机**，也不新增环境变量。
- 首次安装：部署单元的组件与资源清单（`modules/cli/internal/setup/unitpackage`）要加入 `collector-stream`（二进制、配置模板、运行清单）；`native-release.sh install` 只能替换已有组件的二进制，不能新增组件，首次安装要走部署工具（需要支持向已部署的单元新增组件，或一次单元重新部署）。
- 只监听本机健康检查端口（`/healthz`、`/readyz`、`/metrics`），不对外提供业务端口。

### 7.3 资源与带宽

- 入站：全量 4 条连接约 1.7 Mbps，峰值约 6 Mbps；海外机入站实测 160 Mbps 以上。
- 出站：提交的数据量与现在的 SCF 相同（SCF 也经这台机器的 Access 转发到存储机）。实测每分钟前 10 秒的出站比平时多约 183KB（中位），整点约 664KB；海外机出带宽标称 1 Mbps，实测秒级峰值可到约 3.6 Mbps，现在 SCF 提交耗时 100～200 毫秒。stream 是同一进程在收盘后集中提交，阶段 0 要在海外机上实测一次整点 4 个数据集同时提交的耗时。最坏情况是两个 1m 数据集都没收齐，同时在 D 开始串行提交，所以**两个 1m 串行提交的总耗时必须小于提交预留**（默认 1 秒），1h 同理；实测超过就调大 `commit_reserve_ms`（D 相应提前），而不是靠分片——分片不减少总数据量。1h 截止 8 秒，整点先提交 1m、再提交 1h（见 5.11）。
- CPU 与内存：调研工具约 6% CPU；进程常驻内存预计 100MB 以内。

### 7.4 单点、升级与停机恢复

- **升级时间窗口**：`collector-stream` 只在约定窗口升级：避开整点前后（放在 :02～:10），并在分钟第 20～40 秒执行替换。单副本重启要重新连接、重新订阅（每条连接约 1000 个流，按每秒 5 条报文、每条 100 个流，约 2 秒），正常情况下赶在下一个收盘前就绪、不丢周期；赶不上时最多丢 1 个周期，由补采补齐。"启动到全部订阅完成"的耗时列为验收项。
- **进程退出或重启**：`moox-runtime` 拉起，内存里的待提交周期丢弃，从下一个收盘开始收。
- **停机期间缺的数据**（进程停、机器宕机、WS 全断）：
  - 有过提交的周期：截止时 DataNode 把没到的标的记为失败，周期为 `degraded`，自动补采补齐失败的标的；
  - 零提交的周期：Storage 不建立周期、没有完成标记，由自动补采的缺口扫描按计划发现并补齐（补采读稳定后的历史 K 线，走普通写入）；
  - 自动补采每 5 分钟一个槽，补齐时间取决于停机时长；补齐之后要通知下游，下游因子在补齐之前不推进水位（第 7.5 节）。
- `collector-stream` 进程或 WS 连接长时间失败：Monitor 告警后，操作员执行 `moox-cli collector ingest-mode set --space-id crypto --mode pull --executor scf`（进程已失联时加 `--force`）手动切回 SCF 拉取（第 6.3 节）。这时本地执行端随 `collector-stream` 一起不可用，补采也要用 `scf`。
- 币安推送整体异常但 REST 正常：没有兜底，周期零提交或大面积失败，靠补采补齐；持续时手动切回 SCF（SCF 按定稿时间推迟取数，数据正确但更慢）。
- **海外机整机故障时切回 SCF 也没用**：SCF 函数的 Storage 入口是同地域唯一的 Access，也在这台机器上（`modules/cli/internal/setup/config/scf_plan.go` 选入口、写进函数环境）。整机故障期间两条路都断，只能等机器恢复后由补采补齐；要覆盖这种情况需要另一台香港主机的 Access 与函数入口切换，不在本次范围。

### 7.5 停机缺口与下游因子的连续水位（新增要求）

**要求**：下游因子必须等中间缺口补齐后才推进水位，不允许跳过缺失的周期继续计算，否则会算出错误的因子值。

**现状（2026-10-21 读代码）**：

| 问题 | 现在的行为 | 位置 |
| --- | --- | --- |
| 触发 | 每收到一条周期完成事件算一期；同一集合按到达顺序串行，不检查上一期是否算过 | `modules/factor/internal/trigger/eventconsumer/handler.go`、`trigger/lanes.go` |
| 零提交的周期 | Storage 只在周期有过提交时建立周期、发完成事件；补采走普通写入也不发事件，所以因子永远不会算这一期 | `modules/storage/internal/service/datanode/pebble/period_progress.go` |
| 产出水位 | 取最近算过的一期（`LastPeriodTime`），不是"连续算完的最后一期"，中间缺了照样前进 | `modules/factor/internal/engine/run_tracker.go`、`internal/bootstrap/dataset_observer.go` |
| 降级周期里失败的标的 | 事件带 `FailedSubjects`，`BuildLivePlan` 把它们排除、只算已到的；空洞账本（`RecordGaps`）只记窗口空洞与预热，不记这些标的，补采之后它们的这一期永远不会补算；重放原事件也不行（原事件的 `FailedSubjects` 已过时） | `trigger/eventconsumer/handler.go`、`pipeline/plan.go`、`pipeline/report.go` |
| 窗口空洞检查 | 已实现：计算前检查回看窗口，有洞的写 NULL、记账，补采后"只填充"重算；但仓库 `modules/factor/config/engine.yaml` 默认 `gap.enabled: false`（生产配置以线上为准，待核实），而且设计上是"不阻塞流水线" | `pipeline/gapcheck.go`、`engine/gapfill.go`、[因子窗口空洞防护详细设计](因子窗口空洞防护详细设计.md) 2.8 |

**方案**：

1. **连续水位**：每个因子集合持久化一个 `committed_through`，含义是"这一期及之前已经连续算完"。策略只消费水位以内的结果。
2. **按顺序补算**：收到 T 期事件时，从 `committed_through + 1` 到 T 逐期处理（水位已到 T − 1 时就只处理 T）。每一期计算前都检查前面有没有"还没补到"的无效周期（零提交，或缺失超过阈值，见下）；有就停在这里（事件延迟重投），水位不前进。
   - **缺失阈值**：缺失比例 = 未确认缺失的失败标的数 ÷ 期望标的数（按因子集合的标的取交集，用事件里已有的 `UniverseSubjectIds` 与 `FailedSubjects` 算；已确认下架、停牌的不计入）。超过阈值（按因子集合配置，默认 10%）的周期视为无效，与零提交周期一样阻塞水位，补采把缺失比例补到阈值以下后再算整期。典型场景是一条 WS 连接断了、整个市场没到而另一个市场提交了：周期是 `degraded` 而不是零提交，若照常推进，截面类因子（排名、标准化）会只用剩下的一小部分标的算，结果没有意义。WS 正常时每期缺 0 个，下架时一般缺 1～2 个（不到 1%），10% 能把这两种分开。
   - **当期 T 有标的没到（`degraded`）、缺失在阈值以内不阻塞水位**：先算已到的标的，严格截面因子按现有规则整因子 skipped（`compute.go` 有缺失即跳过）。实时计划把 `UpstreamFailed` 的标的也记进空洞账本（要补的缺陷，见上表），补采补齐后由现有 gapfill 的只填充路径补算这些标的的这一期；T + 1 之后回看窗口里的洞照旧由窗口空洞检查兜住。不能靠重放原事件补算，原事件的 `FailedSubjects` 已过时。
3. **"还没补到"和"确认没有"分开**：下架、停牌、新上市等标的级的"确认没有数据"（补采已记入 `t_collector_source_absences`）不阻塞水位，按现有窗口空洞规则处理；只有"还没补到"才阻塞，否则一个下架标的就能永久卡住整个集合。
4. **补齐通知**：补采补齐一个零提交周期，或 `degraded` 周期里失败的标的之后，发一条"周期已补齐"事件，因子据此解除阻塞或唤醒账本补算；阻塞期间因子也按固定间隔查一次 Storage 作为保底。
5. **上限与告警**：阻塞超过 30 分钟告警，交给人工处理（手动补采、确认缺失），**不自动跳过**。
6. **代价**：停机恢复后，策略要等补采（每 5 分钟一个槽）加补算完成才出新信号，期间按已有目标持仓。

这是因子模块与补采的改动，单独出详细设计与执行计划（执行计划阶段 5a）。WS 切换（阶段 6）之前至少要完成第 1～4 条并打开窗口空洞检查，否则 stream 停机或重启造成的缺口会让因子跳期或算出错值。

## 8. 现行 SCF 合约数据不准的处理（独立于 WS，先做）

1. **立即缓解**：取数推迟到 REST 定稿之后——合约 1m、1h 收盘后约 8 秒才开始取，现货收盘后约 3 秒（第 1.4 节；现货 0.6 秒时 99.3%、线上现货 1m 不一致 2.4%，同样是早取造成的）。现有的 `stagger_base_ms` 不合适：它从函数入口算起（云定时器本身晚 0.4～1 秒），而且按空间生效（现货、合约在同一空间）。所以新增两项：按市场的拉取参数覆盖（`scf_plan.spaces.<空间>.markets.<市场>.fetch`），以及相对收盘的最早取数时刻 `not_before_ms`，合约设 8000、现货设 3000。8 秒起取数，加整点可能的 2～4 秒停住，接近 15 秒的截止时间，所以 SCF 模式下**合约数据集的截止放宽到 20 秒**（现货仍 15 秒；现货、合约是不同的数据集，可以分开设，切换时由 `drain` 步骤一起改）；来不及的标的按失败上报、由补采补齐（补采读的是已稳定的历史 K 线）。代价是写入完成推迟：合约从约 0.6 秒到约 9 秒，现货非整点从约 0.7 秒到约 3.5 秒（整点本来就在 6 秒以上，影响小），策略产出延迟相应增加；正确性优先。WS 上线后这项设置只在切回 SCF 时生效，所以保留，切回 SCF 时数据同样是定稿值。
2. **历史数据修正**：对合约 1m、1h 从最早生效点（10-16）到修复生效时刻做一次 `force` 补采（`moox-cli collector kline backfill --force`），REST 历史 K 线已稳定，重拉即正确；补采走普通写入，不受周期完成的限制。现货 1m 不一致率 2.4%，同样可以一起重拉。
3. **下游**：因子与策略的历史结果是用不准的成交量算的。重拉之后，因子按需提交重算（因子模块的补算任务）；策略的历史结果不回改，只在说明里注明。
4. 修复后用本文第 1.5 节的方法复核一次（Storage View 副本 vs 币安基准）。

| 时钟 | 闸门按香港机时钟算最晚提交时刻，截止由存储机 DataNode 判；1m 只有 5 秒 | 两端开 NTP，心跳上报时钟偏差并监控 |
| 迟到定稿 | 闸门提交后、截止前才到的定稿 | 已核实：周期 waiting 且未到截止时再次部分提交会并入成功位图（`period_progress.go`），截止前增量再提交一次 |
| 升级丢周期 | 单副本重启期间可能丢 1 个周期 | 约定升级窗口（第 7.4 节），靠补采 |
| 适配器解码错误 | 不做影子运行与上线前比对，解码错误（例如大小写键串值）会直接写进已锁定的周期 | 用录制的真实报文做单元测试（含大小写键的回归）；上线后发现就手动切回拉取，并对受影响区间 `--force` 补采 |
| 本地执行端与推送同进程 | 补采并发大时可能拖慢推送接收 | 独立并发上限与 HTTP 客户端；监控闸门的到达延迟 |
| 币安推送行为变化 | 例如连续合约 K 线的收盘时机改变 | 指标里的到达分布与"截止时仍缺的标的数"告警 |
| `source_id` 命名 | `spot_http`／`swap_http` 名不副实 | 本次不改（改了就是新序列）；以后若要改，需要整体重新登记并迁移历史 |

## 11. 取舍记录

- **为什么实时不用 REST**：REST 没有闭合标志，合约要到收盘后约 8 秒才定稿、现货约 3 秒，整点还会停住数秒；周期一旦完成就锁定，早取的不定稿值改不回来。完整对比见[行情获取方式对比](行情获取方式对比：REST拉取与WS推送.md)。
- **为什么合约用连续合约 K 线流**：普通 K 线流冷门标的要等下一笔成交或 3 秒才收盘；连续合约 K 线流全部约 0.1 秒收盘，数值相同。它的 REST 版本没有这个特性，所以不能拿来缩短 REST 的等待。
- **为什么 WS 模式截止 1m 5 秒、1h 8 秒，并且不做 REST 兜底**：正常周期 0.5 秒写完，截止只决定"有标的没到"时完成标记多晚发出；1h 多给 3 秒是为了错开整点出站。合约 REST 8 秒才定稿，现货兜底在整点又来不及，兜底很少起作用，却多一层代码和"把未定稿值写进去"的风险，缺的少数标的统一由补采补齐。
- **为什么不设租约**：提交幂等，两边写的都是定稿值，短暂双写结果相同；单实例由部署保证，切换只做手动，失联时用 `--force`。租约要防的问题不存在，反而带来跨机器对时钟的问题。
- **为什么不用逐笔成交自己聚合 K 线**：实测与官方 K 线的成交量、笔数只有约 95～98% 一致（成交跨分钟的归属规则不同），而且冷门标的仍然无法判断"这一分钟的成交已经全部到达"。
- **为什么不用收盘前最后一条快照**：合约只有 25%～48% 等于定稿。
- **为什么不在 WS 里先写临时值再修正**：周期一旦完成就锁定，下游当时就读走了，事后修正改不了已算出的因子与策略结果（第 3 节）。
- **为什么不放南京**：南京只能连上现货的 `data-stream.binance.vision`，合约连不上。
- **为什么补采改走本地执行端**：香港机直连币安，补采读的是已稳定的历史 K 线，不需要云函数的弹性；处理代码与 SCF 同一份，执行端按配置切换，SCF 仍可随时用。
- **为什么当期降级不阻塞因子水位**：缺的标的只影响它自己（写失败，严格截面因子整因子跳过），不会让别的标的算错，补齐后只填充补算即可；整体阻塞会让一条推送丢失就停住策略一个补采槽（5 分钟以上），下架探测窗口里还会反复卡住。零提交周期、缺失超过阈值（默认 10%）的周期仍阻塞水位：前者无数据可算，后者截面类因子会只用一小部分标的算出没有意义的值。
- **为什么不做影子运行**：连续合约 K 线与现货推送已经全量实测、与基准 100% 一致；提交幂等、可以随时手动切回，影子运行多出的观察模式、本地 JSONL、三方比对脚本不值得。
