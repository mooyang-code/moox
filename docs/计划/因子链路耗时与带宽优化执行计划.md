# 因子链路耗时与带宽优化执行计划

> 状态：待审查，未编码。基线数据取自 2026-10-27 04:10～08:05 UTC 的线上实测（EventBus 已迁到存储机，见 [EventBus迁至存储机设计与执行计划.md](EventBus迁至存储机设计与执行计划.md) 第 7.2 节）。
> 原则：单用户、不过度设计、未上线可全新部署（不写迁移、不设计回退）；**改的是通用能力，不为某一条写入路径或某一类因子加特殊逻辑**；凡是动到计算的改动，结果必须逐位不变。

## 1. 基线

### 1.1 单期耗时（5 分钟周期，从收线边界 B 起算，中位数）

| 实例 | 引擎 load | 引擎 compute | 引擎 write | K线至就绪 | 就绪等待 | 读行 | 求值 | 端到端 |
|---|---|---|---|---|---|---|---|---|
| ma_var_5m | 0.38s | 0.003s | 0.30s | 1.5s | 0.15s | 0.24s | 0.002s | 2.1s |
| chain | 0.31s | 0.79s | 0.54s | 2.3s | 0.34s | 0.23s | 0.002s | 3.0s |
| FH002 | 0.31s | 1.36s | 0.76s | 3.4s | 0.33s | 0.30s | 0.19s | 4.3s |
| FH001 | 0.26s | 3.32s | 0.65s | 5.1s | 0.29s | 0.31s | 0.04s | 5.9s |
| FH003 | 0.31s | 3.89s | 0.79s | 6.0s | 0.38s | 0.27s | 0.48s | 7.2s |

五个任务在 B+0.5～0.8 秒同时开始（采集周期完成事件到达引擎）。FH001、FH003 的关键路径里，引擎计算占一半以上。

### 1.2 引擎计算：时间花在哪里

- 数据在内存里：每个源数据集有常驻的内存窗口（`modules/factor/internal/localdata`），每期只从 Storage 增量拉新到的一根（`load` 阶段）。
- 多核用上了：边界时 3 秒内占用 45～57 核（因子机 88 核），每个边界合计约 158 CPU·秒。
- CPU profile（10 秒，覆盖一个边界）：95% 在 `packages/factorexpr/ops.exactSumOf` → `addPartial`（Shewchuk 精确求和，与 Python `math.fsum` 同一算法），调用方是 `ema_partial` 的 `partialSmoothing`（`ops/partial.go`）。
- 量级：FH003 有 32 个 Po 成员（64 个 EMA 节点），FH001 有 16 个（32 个），每个 EMA 在每个标的上对最多 5 万个加权项做精确求和；每期约 17 亿项，折合约 90 ns 一项。

### 1.3 写入：时间花在存储端

- 引擎每个任务每期只发一次 `WriteFactorRows`（501 行全在一个请求里，`engine.yaml` 的 `write_batch_rows` 默认 1000），再发一次 `ReportFactorPeriodComputed`；跨主机走 zstd 加字典压缩，实测 6.6～8.2 倍。
- 因子机上行带宽不是瓶颈：从因子机上传 3 MB，扣掉 SSH 建连只要零点几秒。
- 存储端服务端耗时（`trpc_ServerFilter_time` 自进程启动的平均）：

| 环节 | 平均 |
|---|---|
| 主库 `PrimaryStore.WriteFactorRows` | 364 ms |
| 其中数据节点 `DataNodeRuntime.WriteFactorRows` | 189 ms |
| 主库 `ReportFactorPeriodComputed` | 35 ms |
| 数据节点 `AppendFactorPeriodComputed` | 31 ms |

- 主库 CPU profile：`WriteFactorRows` 的大部分 CPU 在逐行校验上——`factor_rows.go` 对每一行调用 `validateRow` → `MetadataValidator.ValidateRow`，每次都新建 `datasetSchema`，从元数据快照里线性扫描、解码一遍这个数据集的全部列定义；501 行重复 501 次。`UpsertFields`、`CommitTimeSeriesBatch` 两条路径早已改用批量的 `ValidateRows`（同一数据集只加载一次，`d04a99ca`），因子写入没有跟上；另外它还用 `factorResultColumnNames` 再检查一遍列，与通用校验重复。
- 数据节点 CPU profile：时间在 `prepareFieldsWrite`（合并已有行）与 `buildDatasetRowsUpsertedMessage` / `eventmapper.ToEventRows`（构建行变更事件），另有 Pebble 后台压实。

### 1.4 View 投递滞后（因子结果写完到 View 发出就绪事件）

按 JetStream 入流时间（存储机时钟）与引擎日志逐段对照，35 个样本：

| 段 | p50 | p90 | 内容 |
|---|---|---|---|
| 引擎完成（`ComputedAt`）→ 完成标记入流 | 116 ms | 134 ms | 跨公网上报约 30 ms、数据节点落盘约 31 ms、outbox 轮询（`RelayOptions` 默认 100 ms，写死） |
| 完成标记入流 → 就绪事件入流 | 178 ms | 350 ms | View 先应用本期行事件（一期一条，29～213 KB），再处理完成标记（不到 50 ms） |
| 合计 | 274 ms | 480 ms | |

两台主机 chrony 偏差都小于 1 ms，不是时钟误差。`storage.yaml` 里的 `primary.outbox.*`（8 个键）与 `view.batch_wait_ms` 只被解析、没有任何代码使用，是死配置。

### 1.5 带宽

- 存储机公网出向上限 3 Mbps。开机以来平均出向 0.49 Mbps；边界前后 150 秒平均 0.10 Mbps；按 1 秒统计的峰值 1.85 Mbps，按 0.25 秒统计的瞬时峰值 6.64 Mbps；该边界 15 秒内 TCP 重传 0（4859 段）。当前没有超限。
- 1m 因子任务（`ftask_spot_1m`、`ftask_swap_1m`）无策略使用，已于 06:15 UTC 手动暂停：引擎每分钟写入从压缩后约 230 KB 降到约 20 KB；Monitor 已按任务暂停状态跳过它们的新鲜度检查（`6c388be0`、`86b74eb2`）。

## 2. 优化项

按"收益 / 风险"排序。每项写明现状证据、改法、影响面、验证与预期收益。

### O1 精确舍入求和提速（因子表达式公共底层）

- 现状：`packages/factorexpr/ops/sum.go` 的 `exactSum` / `exactSumOf` 用 Shewchuk 部分和（每加一项都要和已有部分和逐个做 two-sum、按绝对值比较），再由 `roundPartials` 合成正确舍入的结果。调用方是表达式引擎的大部分统计与平滑算子：`ema`（`truncatedSmoothing`）、`ema_partial`（`partialSmoothing`）、`wma`、`ts_mean`、`ts_std`、偏度、峰度、相关、回归、截面均值与标准差等（`ops/stats.go`、`ops/cross.go`、`ops/partial.go`）。
- 改法：换一个更快的"正确舍入精确求和"实现，接口不变。候选是定点超长累加器（把每个 float64 按指数放进一组整数字里累加，最后一次性规约并按"半数取偶"舍入），每项只需几次整数运算、没有随部分和数量增长的循环；同时去掉 `exactSumOf` 每项一次的闭包调用（调用方先把乘积写进复用的缓冲区，再整体求和，或者提供带权重的专用入口）。
- 为什么结果逐位不变：精确和的正确舍入值是唯一的，只取决于参与求和的数的多重集合，与算法和顺序无关；参与求和的每一项（例如 `full[j] * w[j]`）照旧按现在的方式在 float64 上算出。所以：
  - 所有因子值逐位不变，F1 对照、补算"按 `__params` 重算与原值逐位相同"两条约定都保持；
  - `ExprVersion`（`expr/2`）与定义哈希不变，不需要补算、不迁移数据。
- 必须一致的边界：NaN、正负无穷、两个方向的无穷相加、中间结果溢出（部分和溢出后 `math.fsum` 的处理）、负零、次正规数。新实现在这些输入上必须与现实现完全一致。
- 验证：
  1. 差分测试：新旧两种实现在大量随机输入（含各数量级混合、大量相消、全零、全相同、交替符号）与上面的边界输入上逐位比较；加进 `ops` 的测试并保留旧实现作为测试里的参照。
  2. 现有金标测试（`packages/factorexpr/exec/golden_test.go`、`ops` 的参照测试）与 F1 对照（f1-strategy 工作树的 `local/f1/compare.py`，不进仓库）全部通过。
  3. 基准：`BenchmarkLiveEMA50000` 等现有基准前后对比；再用线上 FH003 的成员组合做一个基准。
- 预期：求和本身提速 10～30 倍（估计值，以基准为准）；FH003 compute 3.9 秒降到约 0.2～0.4 秒，FH001 类似，端到端约省 3 秒；每个边界的 CPU 从约 158 CPU·秒降到十几 CPU·秒。
- 影响面：`packages/factorexpr` 被 `modules/factor`（引擎、管理端的预览与回放）和 `modules/cli`（因子转换的离线检查）引用。结果不变，所以发布不需要协调；先发因子引擎。

### O2 主库写入校验统一走批量（通用）

- 现状：见 1.3。三条写入路径各自判断 `s.validate` 是否支持 `ValidateRows`，因子写入没有走批量。
- 改法：在 `primarystore` 里提供一个通用入口（例如 `validateRows(ctx, rows, validator)`）：先对每一行做结构检查（现在 `validateRow` 里与元数据无关的部分：行键、字段、属性非空），再一次性做元数据校验（支持批量就用 `ValidateRows`，不支持才逐行）。`UpsertFields`、`CommitTimeSeriesBatch`、`WriteFactorRows` 三条路径都改用它，删掉各自的类型断言分支。
- 因子写入里的 `factorResultColumnNames` 列检查：通用校验已经要求每个字段是 active 的已登记列；两者的差别是通用校验同时接受列名与 `origin_id`，`factorResultColumnNames` 只接受列名。先核对因子结果数据集的列是否 `origin_id` 与列名一致（或为空）：一致就删掉这段重复检查；不一致说明因子写入确实需要"只接受列名"，那这是数据集层面的规则，应放进通用校验按数据集属性判断，而不是留在因子写入路径里。
- 不改：校验内容一条不少（数据集 active、行键类型、规范频率、字段已登记、值类型）。
- 验证：`primarystore` 现有测试全部通过；补一个测试断言一次写入多行时元数据只加载一次（用计数的假 reader）；补因子写入的错误路径测试（未登记列、类型不符、频率不符仍被拒绝）。
- 预期：每次 FH 写入在主库省约 100～150 ms（按 profile 估计），所有批量写入路径都受益。

### O3 数据节点 outbox 写入即唤醒

- 现状：`modules/storage/cmd/server/main.go` 用 `RelayOptions{}` 创建转发协程，轮询间隔默认 100 ms（`outbox/relay.go`）；每条事件平均多等约 50 ms。行事件、完成标记、采集周期完成事件都走这条路。
- 改法：`pebble.Store` 在一次提交写入了 outbox 条目之后，往一个容量为 1 的通道非阻塞地发信号（合并：已有信号就不再发）；`Relay` 的循环同时等这个信号与原来的定时器，定时器保留作兜底（发布失败的重试、启动时的积压）。完成标记（`AppendFactorPeriodComputed`）等其他写 outbox 的路径同样发信号。
- 不改：发布顺序、失败重试与隔离、清理逻辑；协议与数据都不变。
- 验证：`outbox` 现有测试通过；补一个测试：写入后在远小于轮询间隔的时间内被发布；补一个测试：连续多次提交只触发有限次 flush。
- 预期：每条事件平均省约 50 ms，同时作用于引擎收到采集完成事件、View 收到行事件与完成标记、策略收到就绪事件。

### O4 清理 Storage 死配置

- `storage.yaml`（含各组件的副本与仓库里的 `modules/storage/config/*.yaml`）的 `primary.outbox` 整块（`flush_batch_size`、`flush_max_bytes`、`flush_interval_ms`、`max_rows`、`max_bytes`、`max_age_hours`、`backoff_base_ms`、`backoff_max_ms`）与 `view.batch_wait_ms`：只被 `internal/config/loader.go` 解析和填默认值，没有任何使用方。删掉结构体字段、默认值与配置文件里的键。
- 注意：Storage 的配置是严格解码（`loader.go` 用 `yaml.UnmarshalStrict`），线上副本必须与二进制同时改（先删副本里的键再换二进制没问题；先换二进制、副本里还留着已删除的键会被拒绝启动）；发布时与 O2、O3 一起做，按 [native-release.md](../../skills/moox/references/native-release.md) 的"配置文件不随二进制更新"处理。
- 若 O3 需要可配置的轮询兜底间隔，新增一个真正被使用的键，不复用这些死键。

### O5 引擎增量拉数的读取并行（先测再改）

- 现状：`load` 0.2～0.4 秒。实时周期由 `localdata` 的 `PullStaged` 从 Storage 增量拉本期数据；`storageio` 的读取按每批 100 个标的顺序发请求（501 个标的约 6 次往返，跨公网 RTT 约 30 ms，另加存储端处理）；5 个任务共用同一个源数据集，`loadLiveWindow` 在源上持锁。
- 先测：在 `PullStaged` 里加分段计时（每批往返、存储端耗时、提交到本地、持锁等待），确认 0.3 秒落在哪里。
- 可能的改法（按测量结果选）：同一次拉取内的多批请求有界并发（例如 4 路）；同一源数据集同一周期只拉一次，其他任务直接复用已同步的窗口（如果现在每个任务各拉一次）。
- 预期：约 0.1～0.2 秒，影响所有 5m 任务。

### O6 View 应用行事件耗时排查（先测再改）

- 现状：完成标记入流到就绪事件入流 p50 178 ms、p90 350 ms，主要是 View 先应用本期行事件（同一 View 的消费者按数据集有序、串行处理）；耗时随行事件大小增长（FH003 一期约 213 KB）。
- 先测：边界时对 storage-view 抓 CPU profile，并在行事件应用里加分段计时（解码、写视图索引、提交）。
- 改法待定，原则是不改有序语义、不改 View 的数据与协议。

### O7 数据节点写入耗时排查（先测再改）

- 现状：数据节点处理一次因子写入平均 189 ms；profile 显示在合并已有行与构建行变更事件（含 protobuf 反序列化）上。
- 先测：边界时抓 profile，在 `writeFieldsEventLocked` 里加分段计时；看合并是否在读不需要的旧值、事件构建是否重复编解码。
- 改法待定，原则同 O6。

### O8 策略求值耗时排查（FH003 0.48 秒）

- 现状：FH003 求值 p50 0.48 秒、FH002 0.19 秒，其余实例几毫秒；与规则数量和标的数相关。
- 先测：对 strategy 在边界时抓 profile，确认是 DSL 求值、过滤还是排序。
- 改法待定。

## 3. 不做的方案

| 方案 | 不做的原因 |
|---|---|
| EMA 增量递推（保存上一期状态） | 递推的舍入误差会让结果末几位与现在的精确求和不同，破坏"补算逐位一致"与 F1 对照；引擎重启、K 线空洞、晚到数据修订都要重建状态。O1 不改语义就能拿到大部分收益 |
| 策略缓存上一根行 | 线上五个策略都不引用 `bars[-1]`，只读当期，没有收益 |
| 调 outbox / View 的批量间隔配置 | 这些键是死配置（见 O4），改了没有效果；真正的等待来自写死的轮询间隔，由 O3 处理 |
| 训练按空间的专用压缩字典 | 现在只有通用字典 `default-v1`，压缩比已经 4.5～12 倍，整行压缩后已接近 float64 本身的熵；预计收益 10～25%（未实测），优先级最低，等需要省带宽时再评估 |
| 提升存储机带宽 | 当前按秒统计没有超过 3 Mbps，边界时无重传 |
| 把因子引擎迁到云上 | 写入慢的原因在存储端处理，不在因子机网络 |

## 4. 执行顺序与发布

1. **O1**（只动 `packages/factorexpr`）：编码 → 差分测试、金标、F1 对照、基准 → 发布因子引擎（避开 5 分钟边界：上一期全部算完、距下个边界 3 分钟以上时重启）。管理端、CLI 随下次发布带上即可（结果不变）。
2. **O2 + O3 + O4**（Storage）：一起编码、一起发布。Storage 三个组件同一份二进制；O2 只影响 storage-primary，O3 只影响 storage-node，O4 涉及三个组件的配置副本。按 native-release 的 Storage 规则逐个替换，重启 primary、node 会让当期的周期提交短暂失败，选在两个 5 分钟边界之间。
3. **O5**：先加计时、发布引擎观察几期，再决定改法。
4. **O6、O7、O8**：先抓 profile 和加计时，结论写回本文档，再单独决定是否改。

## 6. 风险

- O1 的边界输入（NaN、无穷、溢出）处理与现实现不一致，会悄悄改变个别因子值：靠差分测试兜住，差分测试不过不发布。
- O2 若因子结果列的 `origin_id` 与列名不一致，直接删掉重复检查会放宽因子写入：先核对再删（见 O2）。
- O3 的信号在高写入量时引起过于频繁的 flush：信号合并、flush 本身批量，测试覆盖。
- O4 线上配置副本与二进制不同步会导致 Storage 拒绝启动：按发布顺序同时换。
