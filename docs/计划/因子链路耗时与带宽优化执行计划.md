# 因子链路耗时与带宽优化执行计划

> 状态：已经过两轮 Codex 审查并修订（见第 7 节）；O1～O8 已编码（分支 `perf/latency-optimizations`），编码结果见第 8 节。基线数据取自 2026-10-27 04:10～08:05 UTC 的线上实测（EventBus 已迁到存储机，见 [EventBus迁至存储机设计与执行计划.md](EventBus迁至存储机设计与执行计划.md) 第 7.2 节）。
> 原则：单用户、不过度设计、未上线可全新部署（不写迁移、不设计回退）；**改的是通用能力，不为某一条写入路径或某一类因子新增特殊逻辑**；凡是动到计算的改动，在实际会出现的输入上结果必须与现在的实现逐位一致；不为不会出现的极端输入（例如累加溢出 float64）增加复杂度。

## 1. 基线

### 1.1 单期耗时（5 分钟周期，从收线边界 B 起算，中位数）

| 实例 | 引擎 load | 引擎 compute | 引擎 write | K线至就绪 | 就绪等待 | 读行 | 求值 | 端到端 |
|---|---|---|---|---|---|---|---|---|
| ma_var_5m | 0.38s | 0.003s | 0.30s | 1.5s | 0.15s | 0.24s | 0.002s | 2.1s |
| chain | 0.31s | 0.79s | 0.54s | 2.3s | 0.34s | 0.23s | 0.002s | 3.0s |
| FH002 | 0.31s | 1.36s | 0.76s | 3.4s | 0.33s | 0.30s | 0.19s | 4.3s |
| FH001 | 0.26s | 3.32s | 0.65s | 5.1s | 0.29s | 0.31s | 0.04s | 5.9s |
| FH003 | 0.31s | 3.89s | 0.79s | 6.0s | 0.38s | 0.27s | 0.48s | 7.2s |

五个任务在 B+0.5～0.8 秒同时开始（采集周期完成事件到达引擎）。FH001、FH003 的关键路径里，引擎计算占一半以上。

### 1.2 引擎计算：时间花在哪里

- 数据在内存里：每个源数据集有常驻的内存窗口（`modules/factor/internal/localdata`），每期只从 Storage 增量拉新到的一根（`load` 阶段）。
- 多核用上了：边界时 3 秒内占用 45～57 核（因子机 88 核），每个边界合计约 158 CPU·秒。
- CPU profile（10 秒，覆盖一个边界）：95% 在 `packages/factorexpr/ops.exactSumOf` → `addPartial`（Shewchuk 部分和），调用方是 `ema_partial` 的 `partialSmoothing`（`ops/partial.go`）。
- 量级：FH003 有 32 个 Po 成员（64 个 EMA 节点），FH001 有 16 个（32 个），每个 EMA 在每个标的上对最多 5 万个加权项求和；每期约 17 亿项，折合约 90 ns 一项。

### 1.3 写入：时间花在存储端

- 引擎每个任务每期只发一次 `WriteFactorRows`（501 行全在一个请求里，`engine.yaml` 的 `write_batch_rows` 默认 1000），再发一次 `ReportFactorPeriodComputed`；跨主机走 zstd 加字典压缩，实测 6.6～8.2 倍。
- 因子机上行带宽不是瓶颈：从因子机上传 3 MB，扣掉 SSH 建连只要零点几秒。
- 存储端服务端耗时（`trpc_ServerFilter_time` 自进程启动的平均）：

| 环节 | 平均 |
|---|---|
| 主库 `PrimaryStore.WriteFactorRows` | 364 ms |
| 其中数据节点 `DataNodeRuntime.WriteFactorRows` | 189 ms |
| 主库 `ReportFactorPeriodComputed` | 35 ms |
| 数据节点 `AppendFactorPeriodComputed` | 31 ms |

- 主库 CPU profile：`WriteFactorRows` 的大部分 CPU 在逐行元数据校验上。`factor_rows.go` 对每一行调用 `validateRow` → `MetadataValidator.ValidateRow`，每次都新建 `datasetSchema`，从元数据快照里线性扫描、解码一遍这个数据集的全部列定义；501 行重复 501 次。批量接口 `ValidateRows`（按数据集只加载一次）已经存在，`UpsertFields`、`CommitTimeSeriesBatch` 在用，因子写入没有用。
- 数据节点 CPU profile：时间在 `prepareFieldsWrite`（编码字段与行索引 KV）与 `buildDatasetRowsUpsertedMessage` / `eventmapper.ToEventRows`（构建行变更事件），另有 Pebble 后台压实。

### 1.4 View 投递滞后（因子结果写完到 View 发出就绪事件）

按 JetStream 入流时间（存储机时钟）与引擎日志逐段对照，35 个样本：

| 段 | p50 | p90 | 内容 |
|---|---|---|---|
| 引擎完成（`ComputedAt`）→ 完成标记入流 | 116 ms | 134 ms | 跨公网上报约 30 ms、数据节点落盘约 31 ms、outbox 轮询（`RelayOptions` 默认 100 ms，写死） |
| 完成标记入流 → 就绪事件入流 | 178 ms | 350 ms | 含 View 消费者排队、应用本期行事件（一期一条，29～213 KB）、持久化围栏、处理完成标记与就绪发布；各段占比待测（O6） |
| 合计 | 274 ms | 480 ms | |

两台主机 chrony 偏差都小于 1 ms，不是时钟误差。`storage.yaml` 里的 `primary.outbox.*`（8 个键）与 `view.batch_wait_ms` 只被解析、没有任何代码使用，是死配置。

### 1.5 带宽

- 存储机公网出向上限 3 Mbps。开机以来平均出向 0.49 Mbps；边界前后 150 秒平均 0.10 Mbps；按 1 秒统计的峰值 1.85 Mbps，按 0.25 秒统计的瞬时峰值 6.64 Mbps；该边界 15 秒内 TCP 重传 0（4859 段）。当前没有超限。
- 1m 因子任务（`ftask_spot_1m`、`ftask_swap_1m`）无策略使用，已于 06:15 UTC 手动暂停：引擎每分钟写入从压缩后约 230 KB 降到约 20 KB；Monitor 已按任务暂停状态跳过它们的新鲜度检查（`6c388be0`、`86b74eb2`）。

## 2. 优化项

按"收益 / 风险"排序。每项写明现状证据、改法、影响面、验证与预期收益。

### O1 精确求和提速（因子表达式公共底层）

- 现状：`packages/factorexpr/ops/sum.go` 的 `exactSum` / `exactSumOf` 用 Shewchuk 部分和（每加一项都要和已有部分和逐个做 two-sum），再由 `roundPartials` 按 CPython `math.fsum` 的末段（含半数取偶修正）合成结果。调用方（全部在 `ops/stats.go`、`ops/cross.go`、`ops/partial.go`，回调都是纯计算）：`ema`（`truncatedSmoothing`）、`ema_partial`（`partialSmoothing`）、`sma`、`ts_decay_linear`、`ts_mean`、`ts_std`、偏度、峰度、相关、回归、截面均值、标准差与 `cs_scale` 等。
- 输入的实际范围（决定设计取舍）：表达式引擎规定任何产生 ±Inf 的运算都记为 NaN（`factorexpr.Finite`，设计 4.4），所以参与求和的每一项只可能是有限值或 NaN；行情数据（价格、成交量、收益率）及其加权、平方，数量级远低于 float64 的上限（约 1.8e308）。
- 改法：
  1. 新实现只处理这两类输入：有限值走新的"精确和正确舍入"实现，候选是定点超长累加器（按指数把每个 float64 放进一组整数字里累加，最后一次性规约并按半数取偶舍入），每项只需几次整数运算，没有随部分和数量增长的循环；遇到 NaN 直接返回 NaN（与现实现相同）。
  2. 不为不会出现的输入增加分支（用户决定，设计以简洁为先）：
     - 中间溢出（各项累加超过约 1.8e308）：现实现会得到 NaN，新实现可能得到正确的有限值或 ±Inf（再被 `Finite` 记为 NaN）。行情数据不会出现。
     - 精确和为 0 时一律返回 `+0`：现实现只在所有项都是 `-0` 时返回 `-0`，这种输入现实中不会出现，且 `-0 == +0`，下游比较、排序不受影响。
     - ±Inf 输入：引擎内不会出现（见上）；单独调用时按 NaN 处理。
  3. 去掉每项一次的闭包调用：调用方先把每一项写进缓冲区，再整体求和（或提供带权重的专用入口）。缓冲区必须按调用独占（同一个算子内核会被多个 worker 并发调用，见 `exec/run.go` 的并行执行），不能放在共享的内核闭包里；保持对 `0..n-1` 逐项求值的次数与顺序。
- 每一项的值不能只凭源码断言不变：Go 规范允许把 `a*b + c` 融合成一次舍入的乘加（FMA），编译器在 arm64 和启用相应指令集的 amd64 上有融合规则。生产的引擎是 linux/amd64、默认 `GOAMD64=v1`（不融合），但改写后的代码仍要在目标架构与构建参数下验证；乘积需要固定舍入的地方显式写成 `float64(a*b)`。
- 结论成立的条件：满足上面的改法、并通过下面的位级差分验证后，在实际会出现的输入（有限值与 NaN、不溢出）上所有因子值与现在逐位一致，F1 对照与补算"按 `__params` 重算与原值逐位相同"的约定都保持，`ExprVersion`（`expr/2`）与定义哈希不变，不需要补算、不迁移数据。验证不过，不发布。
- 验证：
  1. **求和的位级差分**（`Float64bits` 比较，新旧实现并存于测试里）：大量随机有限输入（各数量级混合、大量相消、全零、全相同、交替符号、不同排列、半数取偶的中点、次正规数），以及含 NaN 的输入。不测、也不要求一致的：中间溢出、全为 `-0`。
  2. **每一项的位级差分**：对每个调用方，比较旧回调返回值与新路径写进缓冲区的每一项。
  3. **算子与程序输出的位级差分**：用线上 FH001～FH003、chain 的真实输入冻结一份快照，新旧实现对全部成员输出逐位比较（现有金标测试有容差、F1 对照截断到 1e-4，抓不到位级差异，只作为补充）。
  4. 基准：现有 `BenchmarkLiveEMA50000` 等，加一个 FH003 成员组合的基准；用基准结果确定收益目标。
  5. `go test -race` 覆盖并发调用。
  6. 上线抽查：上线前保存同一期的输入与旧版本结果，上线后用新版本重算该期逐位比较。
- 预期：以基准为准。profile 显示求和占 95%；若求和提速 10 倍，边界 CPU 约 `158×(5% + 95%÷10) ≈ 23` CPU·秒，提速 30 倍约 13 CPU·秒；FH003 compute 预计降到 0.3～0.6 秒。
- 影响面：`packages/factorexpr` 被 `modules/factor`（引擎，管理端的预览与回放）和 `modules/cli`（因子转换的离线检查）引用。结果逐位一致，发布不需要协调；先发因子引擎。

### O2 因子写入改用已有的批量元数据校验（通用能力，不加特殊逻辑）

- 现状（三条路径的顺序与回退各不相同）：
  - `UpsertFields`（`service.go`）：先整批 `ValidateRows`，再逐行做结构检查（`validateRow` 里与元数据无关的部分）；不支持批量时逐行做元数据校验。
  - `CommitTimeSeriesBatch`（`period.go`）：只有整批 `ValidateRows`，没有不支持批量时的逐行回退，也不调用 `validateRow` 的结构检查。
  - `WriteFactorRows`（`factor_rows.go`）：逐行依次检查行身份、字段非空、无行属性、`validateRow`（结构 + 逐行元数据校验）、列名约束（`factorResultColumnNames`）。
- 改法：把"按数据集缓存元数据、逐行检查"的能力做成通用的逐行校验器，例如 `MetadataValidator.Batch(ctx)` 返回一个请求内的校验器，`Check(row)` 按行检查、数据集与列定义按 (space, dataset) 只加载一次；`ValidateRows` 改为用它实现。`WriteFactorRows` 在原来的逐行循环里把 `validateRow` 的元数据部分换成这个校验器，**校验顺序、错误码与错误文本都不变**（仍是逐行、按原顺序报第一处错误），只是不再每行重新加载列定义。
- 不改：
  - 校验内容一条不少：数据集 active、行键类型、规范频率、字段已登记且 active、值类型。
  - 因子写入的列名约束保留原样：它只接受非空列名、不接受 `origin_id`，有测试明确要求（`factor_rows_test.go` 的 `TestWriteFactorRowsDoesNotTreatOriginIDAsColumnName`）；这段检查每个请求只加载一次列清单，不是慢点，也不是这次要改的对象。
  - `UpsertFields`、`CommitTimeSeriesBatch` 的校验顺序与错误行为。两者"有没有逐行回退"的差别只在 validator 不支持批量时出现（生产的 `MetadataValidator` 支持），不在本项范围。
- 验证：`primarystore` 现有测试全部通过；补测试：一次写入多行时列定义只加载一次（计数的假 reader）；因子写入混合错误的请求（不同行各有一种错误）返回的错误与改动前相同；列清单读取失败仍返回 `INNER_ERR`。
- 预期：每次 FH 写入在主库省约 100～150 ms（按 profile 估计，以实测为准）。

### O3 数据节点 outbox 写入即唤醒

- 现状：`modules/storage/cmd/server/main.go` 用 `RelayOptions{}` 创建转发协程，轮询间隔默认 100 ms（`outbox/relay.go`）；每条事件平均多等约 50 ms。行事件、完成标记、采集周期完成事件都走这条路。
- 改法：
  - 写 outbox 的生产路径集中在 `pebble.Store`：`commitFieldsWriteLocked`（行写入）、`AppendDatasetMarker`（含 `AppendFactorPeriodComputed`）与周期完成标记（`period_progress.go`）。在它们共用的 `noteOutboxCommitted` 更新提示**之后**，往一个容量为 1 的通道非阻塞地发信号（已有信号就不再发）。这样提交失败、判重的空操作都不会唤醒。
  - `Relay` 的循环同时等这个信号与原来的定时器，定时器保留作兜底。Relay 启动时本来就会先 flush 一次，加上缓冲的信号，启动前的写入与重启积压都能覆盖。
  - 单次 flush 最多取一批（默认 100 条）：flush 成功且取满一批时，有界地连续排空，期间仍响应停止；发布失败时照旧按 `PollInterval` 退避，不因信号而加速重试。单线程顺序发布的模型不变。
- 不改：发布顺序、失败重试与隔离、清理逻辑；协议与数据都不变。
- 验证：`outbox` 现有测试通过；补测试：提交后在远小于轮询间隔的时间内被发布；提交失败不唤醒；Relay 启动前的提交在启动后被发布；各标记路径都会唤醒；超过一批的积压被连续排空；发布失败时不忙等。
- 预期：单条事件平均省约 50 ms（积压超过一批时另计），同时作用于引擎收到采集完成事件、View 收到行事件与完成标记、策略收到就绪事件。

### O4 清理 Storage 死配置

- `StorageOutbox` 的 8 个字段（`flush_batch_size`、`flush_max_bytes`、`flush_interval_ms`、`max_rows`、`max_bytes`、`max_age_hours`、`backoff_base_ms`、`backoff_max_ms`）与 `StorageView.BatchWaitMS`（`batch_wait_ms`）：在非测试代码里只有 `internal/config/loader.go` 解析和填默认值，没有任何使用方。删掉结构体字段、默认值与配置里的键。
- 涉及的仓库配置：`modules/storage/config/storage.yaml`、`storage.node.yaml`、`storage.primary.yaml`、`storage_view/trpc_go.yaml`（四份都要核对，以 `grep` 结果为准），以及线上三个组件各自的 `config/storage.yaml` 副本。
- 严格解码（`loader.go` 用 `yaml.UnmarshalStrict`）：旧二进制允许副本里先删掉这些键；新二进制读到仍带旧键的副本会拒绝启动。所以发布时**先备份并删除线上副本里的键、校验，再换二进制**，最后按发布手册对手改过配置的单元重新封存清单。
- 若 O3 需要可配置的兜底间隔，新增一个真正被使用的键，不复用这些死键。

### O5 引擎增量拉数（先测再改）

- 现状：`load` 0.2～0.4 秒。实时周期由 `localdata` 的 `loadLiveWindow` 在源数据集的锁内调用 `seriessync.PullStaged`：它已经把待读批次交给 worker 并行读取（`engine.yaml` 的 `sync.workers` 默认 4、每批 100 个标的），底层 `storageio.ReadWindow` 在单次调用里按批顺序翻页。5 个任务共用同一个源数据集，先拿到锁的任务拉到新数据后，后面的任务对已更新的标的跳过网络读取。
- 先测：在 `PullStaged` 里加分段计时——确定待拉标的（`Bounds` 扫描、变更日志链头请求）、批次的实际并发与往返、落本地、窗口更新，以及 `loadLiveWindow` 的锁等待。
- 再决定：是否有重复的往返可以去掉（例如链头请求）、并发度是否合适；没有明显浪费就不改。
- 预期：待测；不按"6 次顺序往返"估算。

### O6 View 处理完成标记前的耗时（先测再改）

- 现状：完成标记入流到就绪事件入流 p50 178 ms、p90 350 ms，耗时随行事件大小增长（FH003 一期约 213 KB）。这段包含消费者排队、行事件应用、持久化围栏与就绪发布；同一 View 的消费者按数据集有序、串行处理。
- 已有观测：行事件慢日志（`view/event_apply.go`，只在 ≥200 ms 时打印）；完成标记的分段日志（`view/period_event_apply.go`，"投递滞后/前置/入队/发布"）。
- 先测：把两类日志按事件关联；补消费者等待、解码与低于 200 ms 的分段观测；边界时抓 storage-view 的 CPU profile。
- 改法待定，原则是不改有序语义、不改 View 的数据与协议。

### O7 数据节点写入耗时（先测再改）

- 现状：数据节点处理一次因子写入平均 189 ms；profile 显示在编码字段与行索引 KV（`prepareFieldsWrite`）与构建行变更事件（含 protobuf 反序列化，`store.go` 的预处理与事件编解码）上。
- 先测：边界时抓 profile，在 `writeFieldsEventLocked` 里加分段计时；看合并是否读了不需要的旧值、事件构建是否重复编解码。
- 改法待定，原则同 O6。

### O8 策略"求值"阶段耗时（先测再改，FH003 0.48 秒）

- 现状：日志里的"求值"计时（`strategy/internal/trigger/handler.go`）从读取上一期结果（`Store.LatestOk`，SQLite）开始，包括规则状态的 JSON 反序列化，最后才是 `engine.Evaluate`。FH003 p50 0.48 秒、FH002 0.19 秒，其余实例几毫秒；仓库里 FH003 规模的引擎基准（`strategy/internal/engine/f1_scale_test.go`）约 25 ms/期，说明大头可能不在 DSL 本身。
- 先测：把"读上一期结果、JSON 反序列化、`Evaluate`"三段分别计时；检查 `LatestOk` 的 SQL 与索引；必要时抓 profile。
- 改法待定。这一项的潜在收益（最多约 0.45 秒）高于 O3、O5，测量应提前做。

## 3. 不做的方案

| 方案 | 不做的原因 |
|---|---|
| EMA 增量递推（保存上一期状态） | 递推的舍入误差会让结果末几位与现在不同，破坏"补算逐位一致"与 F1 对照；引擎重启、K 线空洞、晚到数据修订都要重建状态。O1 不改结果就能拿到大部分收益 |

## 6. 风险

- O1 在实际会出现的输入上与现实现不一致，会悄悄改变个别因子值：靠位级差分（含线上真实输入快照）兜住，差分不过不发布。中间溢出与全 `-0` 两种不会出现的输入按设计不保证一致。
- O1 的缓冲区在并发调用下被共享，会产生错误结果：按调用独占、`-race` 覆盖。
- O1 改写后编译器对乘加的处理与旧代码不同，会改变某些项的末位：按目标架构做每一项的位级差分。
- O2 改变校验顺序或错误码：方案保留逐行顺序，测试覆盖混合错误与读取失败。
- O3 的信号在高写入量时引起过于频繁的 flush：信号合并、flush 本身批量、失败时按原间隔退避，测试覆盖。
- O4 线上配置副本与二进制错位导致 Storage 拒绝启动：先删副本再换二进制。
