### S1 在旧版上清掉旧结果数据（线上写入，旧版仍在运行）

旧版的 factor-mgr / strategy 还在，沿用它们现成的接口，因为清除因子结果需要因子服务的凭据。

1. **预检（只读）**：

2. **停用并删除策略实例**（读取方在前）：
   ```bash
   $CLI gateway call trpc.moox.strategy.StrategyMgr SetStrategyInstanceEnabled --data '{"instance_id":"<ID>","enabled":false}' $F
   $CLI gateway call trpc.moox.strategy.StrategyMgr DeleteStrategyInstance      --data '{"instance_id":"<ID>"}' $F
   ```
   删除实例会释放它的私有因子集，并连同结果数据集一起清掉。
3. **删除剩下的共享因子任务**，按 `ListFactorSets` 里的状态分别处理（`set_id` 即旧任务 ID）：
   - `pending`：用同样的参数再调一次 `CreateFactorSet`，它会接着完成创建、把任务推到 `enabled`，然后按 `enabled` 处理。
   - `enabled`：对每个启用成员 `SetFactorMemberStatus {set_id, member_alias, status:"disabled"}` → 每个成员 `RemoveFactorFromSet {set_id, member_alias}` → `SetFactorSetStatus {set_id, status:"disabled"}` → `DeleteFactorSet {set_id, purge:true}`。
   - `disabled`：停用仍启用的成员 → 移除成员 → `DeleteFactorSet {purge:true}`。
   - `deleting`（上次清理中途失败）：直接再调一次 `DeleteFactorSet {purge:true}` 续做。

旧指标标签换了名，旧序列 24 小时内会让页面报“数据生产端长时间未更新”。要立刻清：控制机持维护锁（用脚本或 `moox-runtime` 的方式，**不要手动 `flock` 再启动组件**），`stop monitor` → 先把待删行导出成 JSON 备份 → 用 `python3` 对 `t_monitor_metric_series` 与 `t_monitor_metric_latest` 按 `c_metric_name GLOB 'moox_factor_set_*'`、`'moox_factor_param_*'`，以及 `c_labels_json GLOB '*"dataset_factor_*'`、`'*"strategy_<旧实例 ID>"*'` 删除（**用 GLOB，不用 LIKE**，LIKE 不区分大小写）→ `start monitor` 并确认进程在运行。

## 5. 验收

按设计第 15 节，分“线上必做”和“由测试覆盖、线上不复现”。

**线上必做**（记录每项结果到执行计划第 12 节）：

| 项 | 做法 | 通过条件 |
| --- | --- | --- |
| 链路耗时 | `chain_ema20w_5m`（5 个成员、501 标的）取连续若干个 5m 周期，逐段列出：收盘 → 采集写完 → Storage 提交 → 因子 load / compute / write → View 就绪 → 策略求值 → 提交 | 总耗时 < 6 s（目标约 4.5～5 s），与设计第 1 节的 8.0 s 对照 |
| 并行分发 | 同一个源数据集上 `ftask_swap5m_chain` 与 `ftask_swap5m_var` 同期开算 | 两个任务同一期的完成时刻相近，不先后排队 |
| 可变参数 | `ma_var_5m` 运行几期后，读结果行 `__params` | 第一期 `ma__var` 的 window 为默认 20，之后各期为策略提交的 10；固定成员的参数每期如实记录 |
| 幂等与拒绝 | 对同一任务重复调用 `BindFactorTask`（同实例）、用另一个实例绑定 | 前者成功，后者被拒绝；`UpdateStrategyInstance` 改任务被拒绝 |
| 补算 | 对已有 `__params` 的一段历史重算 | 与原值逐位相同；只补部分成员时其他成员的 `__params` 不变；原行不存在的期次出现在补算作业的 `default_filled` |
| Storage | 结果数据集注册了 `__params` 列，默认 View 能读回 `json_value` | 能读回，且不被当作因子输出 |
| 命名与可见性 | 控制台加成员预览的列名、`setup factors` 打印的列名、结果数据集实际列名 | 三者一致；任务详情与策略创建页能看到并复制全部列名；DSL 写错列名时报错给出最接近的列名 |
| Monitor | 同一源数据集的两个任务 | 到达链按任务分别展示，各自对应正确的结果数据集；“策略参数投递”检查为正常 |
| 引擎与告警 | 因子 / 策略 / 数据集新鲜度检查 | S7 解除屏蔽后 10 分钟内全部恢复正常 |

**已由单元 / 集成测试覆盖，线上不人为制造**：同一期失败重试与重启复用同一参数、旧请求晚到被拒绝、部分标的提交不退回默认、追赶期间不等策略、factor-mgr 不可达走本地缓存、结果行成功而标记失败后重试。需要线上复现时再单独和你商量。
