# 因子自定义算子（wasm UDF）设计

> 状态：设计稿 v2.3（2026-10-28，尚未编码；已吸收四轮 Codex 审查，处置见第 16 节）。已确认的决策：
> 1. 因子与策略优先用 DSL 表达；DSL 表达不了的**那一步算法**，用 Rust 编写自定义算子（UDF），编译成 wasm 后由系统加载，不需要重新编译、发布引擎；
> 2. UDF 是 DSL 的**时序算子**，在 DSL 层与内置算子组合使用（输入可以是任意 DSL 表达式），UDF 内部不回调系统、不使用系统内置算子；
> 3. 运行时用 wazero（纯 Go，编译模式），只提供 Rust SDK；
> 4. 在本地按锁定的工具链编译，管理端复核 wasm 产物并重跑一致性测试，不在服务端编译；源码留在私有仓库，系统只记录提交号；
> 5. 版本不可变（按 wasm 字节的 sha256 区分），名称指向当前启用的版本；版本哈希并入 `definition_hash`；
> 6. **切换启用版本在因子引擎模块暂停期间进行**：复用现有的无损暂停与恢复追赶，切换后不会有任何计算用旧版本写出结果；
> 7. 单用户系统：不设审批与权限。
>
> 第一期只做因子侧的时序 UDF（第 14 节）。实现之后，以[因子](../模块/因子.md)为准。

## 1. 背景与目标

因子与策略已经全部是声明式的：因子是表达式（[因子表达式引擎详细设计](因子表达式引擎详细设计.md)），策略是 DSL（[策略](../模块/策略.md)），
常见的变更只改配置、不发布。但总有一部分算法写不成表达式：递归滤波（卡尔曼等）、带分支与迭代的状态更新、自定义回归等。
现在遇到这类需求只能给 factorexpr 加算子，也就是改 Go 代码、重新发布因子管理端与引擎。

目标：

- DSL 表达不了的算法，用户（实际是 Agent）用 Rust 写成 UDF，经命令行发布、启用后即可在因子表达式里调用，不改系统代码、不发布服务；
- UDF 与内置算子遵守同一套语义（点纯、回看、空值、确定性），因此空洞检查、预热、补算分块、试算、`definition_hash` 变更检测全部照常工作；
- 代码由 Agent 生成，所以门禁必须自动化、以 wasm 产物为准，不依赖作者自觉；
- UDF 出错（panic、死循环、内存失控）只让这一次计算失败（与现有执行器出错的处理相同），不影响引擎进程与其他任务，也不会被当成空值写出。

### 1.1 方案选型

2026-10-28 用同一批算法做了实测（基准与原生 Go 比较，Apple M4 与因子机 E5-2696 v4 两台机器）：

| 方案 | 相对原生的耗时 | 可中断死循环 | 确定性 | 结论 |
| --- | --- | --- | --- | --- |
| yaegi（解释执行 Go 源码，参考某内容平台的计算框架） | 约 45～75 倍 | 否（循环不可抢占，goroutine 里的 panic 会让进程崩溃） | 否（map 遍历随机、可读时间） | 不用 |
| Starlark | 约 100～200 倍 | 是 | 是 | 太慢，不适合数值计算 |
| wazero 解释模式 | 约 100～250 倍 | 是 | 是 | 不用 |
| Go 官方 wasip1 → wazero 编译模式 | 2.7～4 倍 | 是 | 是 | Go 后端生成的 wasm 较弱 |
| **Rust → wazero 编译模式** | **纯计算 1.3～1.6 倍** | 是 | 是 | **采用** |
| TinyGo → wazero 编译模式 | 与 Rust 相同 | 是 | 是 | 可行，第一期不提供 SDK |

端到端验证：把一个生产中的批次持仓策略（45 个因子成员，其中 32 个是 5 万根回看的长 EMA；1960 个子策略）整体用 Rust 实现成 wasm，
与 Go 实现在同一份 523 个标的的 5m 数据上逐期对拍：400 期、941 万个因子值逐位一致（0 ulp，arm64 与 amd64 上都对拍过），目标权重 0 处不一致；
在两边采用同一算法、同一分区后，每期因子耗时 Go 原生 2.09 秒、Rust wasm 2.87～3.31 秒、TinyGo wasm 2.88～3.29 秒（单线程）。
据此得出两条设计约束：

- **wasm 比原生慢约 1.4～1.8 倍**，瓶颈在 wazero 的代码生成而不是源语言。所以 UDF 只用于 DSL 写不出来的那一步，能用内置算子的部分留在 DSL 里由 Go 原生计算；
- **长回看下数据拷贝不可忽略**（5 万根窗口的 EMA 实验里约占四成）。第一期每次调用拷贝窗口，超长回看的优化放到以后（第 14 节）。

## 2. 非目标

- 不在 UDF 内回调系统或使用内置算子（宿主导入函数）：回看无法静态推导，跨边界拷贝反而更慢；组合在 DSL 层完成（第 4 节）；
- 不在 Rust SDK 里移植内置算子库；
- 第一期不做：截面 UDF、策略 UDF、多输出 UDF、区间实现（一次算一段输出）、通用的回看公式、历史常驻 wasm 内存、删除版本；
- 不在服务端编译，不维护构建环境，不在系统里存源码；
- 不做多用户隔离、审批与权限；
- 不做对外开放的 UDF 市场或跨系统分发。

## 3. 总体结构

```text
私有 UDF 仓库（git，不进 moox 仓库）
  └─ moox-cli udf build     本地：clippy → cargo build（锁定工具链）→ 模块检查 → 一致性测试 → 打包 .udfpkg（记录提交号）
  └─ moox-cli udf publish   上传到 FactorMgr：复核模块、重跑一致性测试并比对结果摘要，存为不可变版本（未启用）
  └─ moox-cli udf preview   用未启用的版本在真实数据上试算（PreviewFactor）
  └─ moox-cli udf activate  因子引擎模块暂停期间切换；先给出影响清单

FactorMgr（control）
  t_factor_udfs / t_factor_udf_versions；每个因子定义带一份 UDF 绑定（名称 → 版本哈希）
  目录快照、补算任务携带绑定与模块元数据；GetUdfModule 按哈希提供 wasm 字节

FactorEngine
  应用目录前按哈希拉取、校验、编译模块（失败则不应用新目录并重试）
  每个模块哈希一个实例池；factorexpr 运行到 UDF 节点时，把窗口拷进实例内存、调用、读回结果
```

新增共享包 `packages/factorudf`：元数据定义与校验、回看公式求值、wasm 模块检查、wazero 加载与调用、实例池、一致性测试。
命令行、FactorMgr、FactorEngine 共用同一份代码，本地门禁与服务端复核的结论因此一致。

## 4. DSL 写法、编译与版本绑定

### 4.1 调用语法

UDF 在表达式里写成 `udf.<名称>(<序列输入>..., <参数>...)`，与内置算子用命名空间区分：

```yaml
params:
  n: {type: int, min: 2, max: 200, default: 20}
  m: {type: int, min: 2, max: 200, default: 60}
let:
  trend: ema(close, n)                          # 内置算子，Go 原生计算
  vol: ts_std(pct_change(close), m)             # 内置算子
output: cs_rank(udf.kalman_trend(trend / vol, 20, 0.1))   # UDF 只做 DSL 写不出来的那一步；截面在外层组合
```

- 序列输入可以是任意数值表达式（列、`let` 中间量、内置算子的结果），个数与顺序由 UDF 元数据声明；
- 参数必须是常量或因子参数名（参数槽），与内置算子的整数、数值参数一致，取值范围由 UDF 元数据声明并在编译时检查；
- 截面计算写在 UDF 外层（例如 `cs_rank(udf.xxx(...))`），时序 UDF 一次只看到一个标的。

expr-lang 把 `udf.kalman_trend(...)` 解析成调用节点，调用对象是成员访问（左侧标识符 `udf`、右侧字符串 `kalman_trend`），已验证。
factorexpr 现在拒绝成员访问（`syntax.go` 的语法白名单），函数名只能是标识符（`check.go` 的 `lowerCall`）。两处都改为额外接受这一种形式：
作为调用对象、左侧是标识符 `udf`、右侧是 UDF 名称；其余成员访问仍然拒绝。

### 4.2 回看

回看公式只允许两种形式，保证窗口长度随参数单调不减：

- 整数常量 `b`，或
- `a*<整数参数>+b`，`a`、`b` 为非负整数常量（例如 `4*n`、`n+1`）。

由此：

- 窗口长度 L 的最小值、最大值在参数范围的端点取得，现有 `worstBackShift` 只枚举端点的做法仍然成立；
- 发布时检查：参数取下限时 L ≥ 1，取上限时 L 不超过因子回看的整体上限（与内置算子共用），计算过程不会溢出；
- UDF 节点的 `Back = L − 1`、`Shift = 0`；集合回看、需求区间（`actualExtent` 按实际参数值）、SDK 交给用户函数的窗口长度都用同一个 L；
- UDF 节点参与公共子表达式消除与运行时去重：版本哈希、输入、参数相同才是同一节点。

更一般的公式（多个参数、非单调）放到以后，届时需要做保守的区间求值。

### 4.3 版本绑定

每个因子定义带一份**UDF 绑定**：它引用的每个 UDF 名称 → 版本哈希。绑定决定了编译用哪个版本，必须随定义一起走完整条链路：

| 环节 | 做法 |
| --- | --- |
| 管理端 | 读取定义时按 `t_factor_udfs` 的启用版本解析出绑定；`ValidateFactorSpec`、`PreviewFactor` 的 `udf_versions` 是请求级覆盖，只作用于本次请求 |
| 传输 | `factorwire` 的定义与目录快照、补算任务都携带绑定，以及被引用模块的元数据 |
| 引擎 | 本地持久化的目录快照保存绑定；编译入口接收绑定，不自行查找“当前版本”；补算作业（含重启后续跑）始终用领取时随作业下发的绑定 |
| 编译缓存 | `domain.CompileDefinition` 的缓存、流水线按 `factor_id + spec` 的编译缓存，键都加上绑定（切换版本时 spec 不变，否则会命中旧版本） |
| 编译失败 | `definition_hash` 的备用值（`naming.go` 在编译失败时使用）也包含绑定，不同版本编译失败时身份不同 |

### 4.4 定义哈希

规范程序文本里 UDF 节点写成 `udf.<名称>@<版本哈希>(...)`。`definition_hash` 的算法不变（`domain/naming.go`：
`definition-v2`、expr 语义版本、规范程序文本、`allow_partial_universe`），所以：

- 切换 UDF 版本 = 引用它的因子定义的 `definition_hash` 改变：目录快照哈希（`enginehub.CatalogHash` 含成员的 `spec_hash` 与 `definition_hash`）随之变化，
  引擎重新编译；策略按现有机制进入 `skipped(factor_changed)`、需要重新启用；
- 切换版本不改变因子定义原文，所以 `spec_hash` 不变（也就是 Storage 周期标记里的 `source_hash` 不变），这不影响上面的变更检测；
- 说明与示例不在 wasm 字节里（7.3），只改说明不产生新版本，不影响任何定义。

## 5. 语义契约

UDF 与内置时序算子遵守同一套规则（[因子表达式引擎详细设计](因子表达式引擎详细设计.md)第 4、5 节）。能由 SDK 强制的都由 SDK 强制，
其余由一致性测试做回归检查（第 8 节）。点纯性主要由 SDK 的结构保证：用户只写逐点函数，只能看到当前窗口。

| 规则 | 内容 | 保证方式 |
| --- | --- | --- |
| 点纯 | t 的输出只取决于 `[t−L+1, t]` 窗口的内容；不跨调用保留状态 | SDK 只把当前窗口交给用户函数；禁用全局可变状态（6.3）；分块、换序与未来数据扰动测试 |
| 回看如实 | 读窗口之外的数据即错误 | SDK 的窗口视图越界即 panic；回看外塞垃圾测试 |
| 空值（默认严格） | 任一输入的窗口内有 NaN 时输出 NaN，不调用用户函数 | SDK 强制 |
| 空值（声明 `relaxed`） | 每个输入的 NaN 只能出现在窗口开头（序列还没开始），否则输出 NaN；各输入从**同一时间偏移**裁出共同有效段（起点取各输入首个有效值中最晚的一个），有效段短于元数据的 `min_valid`（默认 1）或为空时输出 NaN，不调用用户函数 | SDK 强制；单输入时与 `*_relaxed` 算子一致 |
| 有限性 | 输出只能是有限值或 NaN，±Inf 记为 NaN | SDK 转换，宿主再规范化 NaN 的位模式 |
| NaN 不可观察 | wasm 规范允许运算产生的 NaN 的符号与负载不确定，所以业务结果不得依赖 NaN 的符号或位模式 | 禁用 `to_bits`、`copysign`、`is_sign_negative` 等（6.3） |
| 确定性 | 同一 wasm 在支持的 wazero 版本、arm64 与 amd64 上逐位相同 | 禁用清单；两实例对拍；本地与服务端的结果摘要比对（8.3） |
| 失败 | panic 即 abort（wasm trap）；超时、超内存同样是失败；失败不产生 NaN | SDK 设定 `panic = "abort"`；宿主见第 11 节 |

## 6. Rust 工程约定

### 6.1 仓库与目录

UDF 源码放在用户自己的私有 git 仓库，不进 moox 仓库（与用户策略、用户因子同一原则）。`moox-cli udf new` 生成如下骨架：

```text
my-udfs/
  rust-toolchain.toml        # 锁定 Rust 版本与 wasm32-unknown-unknown 目标
  clippy.toml                # 禁用 API 清单（6.3）
  Cargo.toml                 # workspace；[profile.release] opt-level=3, lto=true, codegen-units=1, panic="abort"
  AGENTS.md                  # 给 Agent 的编写规范（本节与第 5、8 节的摘要）
  udfs/
    kalman_trend/            # 一个 crate 一个 UDF：一个模块、一个版本哈希
      Cargo.toml             # crate-type = ["cdylib", "rlib"]；依赖只允许 moox-udf（锁定版本）与本仓库的 path 依赖
      udf.toml               # 说明与示例（doc、example），不进 wasm，改它不产生新版本
      src/lib.rs
      tests/fixtures/        # 对拍样本：输入 CSV、参数与期望输出（可由 pandas 等参考实现生成）
```

`moox-cli udf build` 在包里记录仓库的提交号；`publish` 要求工作区干净（没有未提交的改动），这样系统里的每个版本都能对应到私有仓库的一次提交。

### 6.2 命名与数值

- 名称：`^[a-z][a-z0-9_]{0,47}$`，全局唯一；在 DSL 里写成 `udf.<名称>`；
- 只用 f64，NaN 表示空值；整数参数以 i64 交给用户函数，在宿主与 wasm 之间以 f64 精确传递（取值范围远小于 2^53）；
- 用户函数直接返回 f64，没有错误通道；无法计算时返回 NaN，不可能出现的情况才 panic。

### 6.3 禁用清单

由 `clippy.toml` 的 `disallowed-methods`、`disallowed-types`、`disallowed-macros` 与 `#![forbid(unsafe_code)]` 落实，`moox-cli udf build` 以 `-D warnings` 执行：

- `f64::mul_add` 等融合乘加；
- `f64::to_bits` / `from_bits`、`copysign`、`is_sign_negative` / `is_sign_positive`（NaN 不可观察，见第 5 节）；
- `std::time`、随机数、线程与同步原语、`std::env`、文件与网络；
- 跨调用状态：`thread_local!` 与可变全局状态（`static` 里的 `Cell`、`RefCell`、`OnceCell`、原子类型、`Mutex` 等）；clippy 覆盖不全的情况由点纯测试兜底；
- `HashMap` / `HashSet` 的遍历（只做查找可以；需要有序遍历用 `BTreeMap`）；
- 浮点归约的顺序必须固定（不用并行迭代器）；
- 依赖只有 `moox-udf` 与本仓库的 path 依赖。`f64::exp`、`ln` 等数学函数会编进 wasm，跨平台一致，可以使用。

### 6.4 编写原则（写进模板的 AGENTS.md）

- 能用内置算子表达的部分写在 DSL 里，作为 UDF 的输入；UDF 只做 DSL 写不出来的那一步；
- 优先写朴素循环：实测手工展开、多路累加在 wazero 下反而变慢；
- 热路径不分配内存；不默认使用精确求和，确实需要逐位一致的累加语义时再说明；
- 说明与示例写在 crate 的 `udf.toml` 里（`doc`、`example`），控制台与 `ListFactorFunctions` 展示它们。

## 7. SDK 设计

SDK 位于 moox 仓库 `sdk/rust/`：`moox-udf`（运行时）与 `moox-udf-macros`（过程宏），模板位于 `sdk/rust/template/`。
SDK 的职责是让用户只写算法：ABI、内存、批量循环、空值规则、元数据都由宏生成。

### 7.1 用户代码

```rust
use moox_udf::prelude::*;

#[udf(
    name = "kalman_trend",
    inputs = [x],                                  // 序列输入，按位置对应 DSL 的实参
    params = { n: int(2..=500), q: float(0.0..=1.0) },
    lookback = "4*n",                              // 只允许常量或 a*整数参数+b（4.2）
    nan = "strict",                                // 默认 strict；可选 relaxed，并可设 min_valid（第 5 节）
)]
fn kalman_trend(x: &Window, p: &KalmanTrendParams) -> f64 {
    // x 是以 t 结尾、长度为 4*n 的窗口（relaxed 时是共同有效段）
    // p.n: i64，p.q: f64 —— 参数结构体由宏按 params 生成
    ...
}
```

- 多个序列输入写成 `inputs = [x, y]`，函数签名对应 `fn f(x: &Window, y: &Window, p: &P) -> f64`，各窗口时间对齐、长度相同；
- `Window` 提供 `len()`、`get(i)`（0 为最老）、`last()`、`iter()`、`as_slice()`，越界即 panic；
- 宏在编译期检查：名称合法、参数名与回看公式一致、回看公式符合 4.2 的形式。

### 7.2 元数据

宏把**影响计算的元数据**写进 wasm 的自定义段 `moox.udf`（JSON），宿主不执行代码即可读取（wazero 支持读取自定义段）：

```json
{
  "abi": 1,
  "sdk": "0.1.0",
  "name": "kalman_trend",
  "kind": "series",
  "inputs": ["x"],
  "params": [
    {"name": "n", "type": "int", "min": 2, "max": 500},
    {"name": "q", "type": "float", "min": 0, "max": 1}
  ],
  "lookback": "4*n",
  "nan": "strict",
  "min_valid": 1
}
```

- 自定义段只放上面这些语义字段，它们随 wasm 字节进入版本哈希；
- 说明与示例来自 crate 的 `udf.toml`，由 `moox-cli udf build` 和自定义段合并成包里的 `manifest.json`，存进数据库供展示，不进 wasm、不进版本哈希。
  同一哈希再次上传时只更新说明与示例。

### 7.3 ABI 契约

只有一个 ABI 版本号，宿主只接受当前版本。按项目原则不做兼容：ABI 升级时全部 UDF 用新 SDK 重编、重新发布（单用户场景下数量很少）。
宏生成以下导出，签名必须完全一致，用户不直接接触：

| 导出 | 签名 | 说明 |
| --- | --- | --- |
| `memory` | 线性内存 | 唯一的内存，不共享 |
| `moox_udf_abi` | `() -> i32` | ABI 版本 |
| `moox_udf_reserve` | `(i32 bytes) -> i32` | 返回实例暂存区的起始偏移，至少 `bytes` 字节、8 字节对齐；失败（长度溢出、内存不足）返回 0。暂存区跨调用复用，下一次 `reserve` 后旧内容作废 |
| `moox_udf_eval` | `(i32 series, i32 in_len, i32 out_len, i32 params, i32 inputs, i32 out) -> i32` | 计算一批序列，三个指针都在暂存区内；返回 0 成功、1 参数越界、2 窗口长度不一致，其他值与 trap 都是失败 |

内存布局与索引：

- 偏移是 u32，数值是小端 IEEE-754 f64；
- `inputs` 按 `[输入][序列][in_len]` 排列，`params` 按 `[序列][参数]` 排列，`out` 按 `[序列][out_len]` 排列；
- 参数按元数据里的声明顺序排列，整数参数以 f64 精确传入。factorexpr 的节点把整数参数与数值参数分开保存（`ir.go` 的 `Ints` / `Floats`），由宿主按元数据顺序重新映射；
- `in_len = out_len + L − 1`；`out[s][j]` 对应以 `inputs[k][s][j + L − 1]` 结尾的窗口，即 `inputs[k][s][j .. j + L − 1]`；
- SDK 对每个序列按参数算出 L，与 `in_len − out_len + 1` 不一致时返回 2；SDK 生成的循环写满每个输出位置；
- wazero 的 `Memory.Read` 返回的是借用视图，guest 内存可能在任何一次调用中增长，所以宿主每次调用后都重新取视图，不跨调用缓存。

### 7.4 本地开发

`moox_udf::testing` 在原生环境下运行用户函数与 fixtures，便于调试与单元测试；门禁以 wasm 产物为准（第 8 节），原生测试只是辅助。

## 8. 门禁

本地（`moox-cli udf build`）与服务端（`PublishUdf`）执行同一套检查，代码都在 `packages/factorudf`。
源码检查只能在本地执行（服务端没有工具链），**安全不依赖源码检查**：沙箱与下面的模块检查、执行时限制都直接作用于 wasm 产物；
一致性测试是有限样本上的回归门禁，点纯性主要靠 SDK 的结构保证。

### 8.1 源码检查（只在本地）

- `cargo clippy --locked -- -D warnings`（含 6.3 的禁用清单），用户 crate `#![forbid(unsafe_code)]`；
- `cargo build --release --locked --target wasm32-unknown-unknown`。

### 8.2 模块检查（本地与服务端）

- **没有任何导入**：纯计算，不开 WASI；
- **没有 start 函数**：实例化时不执行任何用户代码；
- 特性只允许 wasm 2.0（wazero 的 `CoreFeaturesV2`：符号扩展、可变全局、多返回值、非陷入的浮点转整数、批量内存、引用类型、SIMD），
  Rust 的 `wasm32-unknown-unknown` 默认产物就在这个范围内；线程与原子操作、共享内存、relaxed-simd、memory64、尾调用、异常处理、GC 一律拒绝
  （运行时只开 `CoreFeaturesV2`，用到其他特性的模块编译即失败）；
- 恰好一个内存且不共享，声明的初始页数不超过上限；表不超过一个、元素数不超过上限；
- 导出与 7.3 的签名完全一致、ABI 版本等于当前版本；
- 元数据存在且合法：名称、参数范围、回看公式符合 4.2 并通过端点检查、`nan` 与 `min_valid` 取值合法；
- 模块不超过 1.5 MiB（实测 Rust UDF 的产物在 100 KiB 以内）。

### 8.3 一致性测试（本地与服务端）

宿主用固定种子生成合成数据：若干条随机游走序列，外加开头 NaN、中途 NaN、常数序列、量级跨度很大的序列，多输入时各输入的开头 NaN 长度不同；
参数取声明范围的下限、上限与若干中间值。

| 测试 | 通过条件 |
| --- | --- |
| 分块与点纯 | 同一段输出按不同分块大小、不同起点调用，结果逐位相同 |
| 批次组合与换序 | 同一序列放进不同的批次、换到批次内不同的位置，结果逐位相同 |
| 未来数据扰动 | 改动 t 之后的数据，t 及之前的输出不变 |
| 回看 | 把窗口之外的历史换成随机值或 NaN，输出不变 |
| 空值 | 严格模式下窗口含 NaN 的点输出 NaN；`relaxed` 模式下按第 5 节的共同有效段规则计算 |
| 有限性 | 输出没有 ±Inf |
| 确定性 | 两个新实例、各跑两次，逐位相同 |
| fixtures 对拍 | 与 `tests/fixtures` 的期望输出一致（默认逐位，可在 fixtures 里放宽到相对误差 1e-12） |
| 资源 | 在执行时限制（11 节）之下全部完成；报告记录每个输出点的平均耗时与实例峰值内存 |

- fixtures（输入、参数、期望输出与误差设置）规范化后随包上传，服务端与本地跑的是完全相同的一套测试；
- 测试报告（JSON）包含全部测试输出的摘要（sha256）。服务端重跑后比对摘要：本地一般是 arm64（Mac）、服务端与因子机是 amd64，
  摘要不一致即拒绝，跨架构的确定性因此每次发布都会被检查；
- 失败项带输入摘要与最小复现参数，Agent 可以据此迭代修改；
- 资源统计只用于报告与调参，真正的限制是执行时的截止时间与内存上限（11 节）。

## 9. 发布链路

| 命令 | 行为 |
| --- | --- |
| `moox-cli udf new <名称>` | 生成 6.1 的骨架（首次在空目录生成 workspace，之后只添加 crate） |
| `moox-cli udf build [<名称>]` | 8.1～8.3 全部检查，产出 `dist/<名称>-<sha256>.udfpkg` |
| `moox-cli udf publish <udfpkg>` | 要求私有仓库工作区干净；上传到 FactorMgr，服务端复核 8.2、8.3 并比对摘要，通过后存为不可变版本（未启用）；同一哈希重复上传只更新说明与示例 |
| `moox-cli udf preview <名称>@<哈希> --spec <因子定义> --task <因子任务> ...` | 用未启用的版本走 `PreviewFactor` 在真实数据上试算 |
| `moox-cli udf activate <名称>@<哈希> [--dry-run]` | 给出影响清单与前提检查结果（10.3）；前提都满足才切换 |
| `moox-cli udf list` / `show <名称>` | 版本、启用状态、元数据、服务端报告、提交号、引用关系、各引擎的就绪状态 |

- `.udfpkg` 是一个 tar：`module.wasm`、`manifest.json`（自定义段的语义字段加 `udf.toml` 的说明，语义字段必须与自定义段一致；另含仓库与提交号）、
  `fixtures/`（规范化的对拍样本，不超过 256 KiB）、`report.json`（本地门禁报告，服务端只用其中的摘要做比对）；
- 大小：整包不超过 2 MiB。命令行的管理调用经网关走 JSON，二进制按 base64 编码约放大 4/3，2 MiB 的包编码后约 2.7 MiB，加上 JSON 包装仍在
  FactorMgr 现有的 4 MiB 消息上限之内；命令行发送前再检查完整序列化后的请求体大小；
- 切换版本的完整步骤：`activate --dry-run` 查看影响 → 暂停因子引擎模块（等在途收敛）→ 取消列出的已领取补算作业 → `activate`
  → 恢复因子引擎（追赶：应用新目录、准备模块、用新版本补算暂停期间的周期，全部完成才放行）→ 相关策略实例重新启用；需要更早的历史一致时显式补算。
  暂停只需几秒到几分钟，恢复时补算的周期很少；
- 新 UDF 的首次 `activate` 没有引用方，直接生效；之后才能在因子定义里引用它；
- 回滚就是 `activate` 指回旧版本；版本一直保留，第一期不提供删除；
- moox skill 增加 UDF 的发布流程说明，Agent 发布 UDF 走这套命令，不直接调接口。

## 10. 管理端

### 10.1 数据库

```sql
-- 自定义算子（wasm UDF）：名称指向当前启用的版本，空串表示还没有启用
CREATE TABLE IF NOT EXISTS t_factor_udfs (
    c_name TEXT NOT NULL PRIMARY KEY,
    c_active_hash TEXT NOT NULL DEFAULT '',
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 自定义算子的版本：不可变，主键是 wasm 字节的 sha256；c_manifest 含说明与示例（可随重复上传更新），c_source_ref 是私有仓库与提交号
CREATE TABLE IF NOT EXISTS t_factor_udf_versions (
    c_hash TEXT NOT NULL PRIMARY KEY,
    c_name TEXT NOT NULL,
    c_manifest TEXT NOT NULL,
    c_wasm BLOB NOT NULL,
    c_source_ref TEXT NOT NULL,
    c_sdk_version TEXT NOT NULL,
    c_toolchain TEXT NOT NULL,
    c_report TEXT NOT NULL,
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (c_name) REFERENCES t_factor_udfs (c_name) ON DELETE RESTRICT
);

CREATE INDEX IF NOT EXISTS idx_t_factor_udf_versions_name ON t_factor_udf_versions (c_name, c_ctime);
```

`c_active_hash` 非空时必须是该名称的一个版本，由管理端在事务内校验。被因子定义引用的 UDF 不能把 `c_active_hash` 清空。

### 10.2 接口（`modules/factor/proto/factor.proto`）

| 方法 | 作用 | 只读 |
| --- | --- | --- |
| `PublishUdf` | 上传 `.udfpkg`，复核并存为版本（未启用），返回哈希与服务端报告 | 否 |
| `ListUdfs` / `GetUdf` | 名称、启用版本、版本列表、元数据、报告、提交号、引用关系、各引擎上报的就绪状态 | 是 |
| `ActivateUdf` | 切换启用版本；`dry_run` 只返回影响清单 | 否 |
| `GetUdfModule` | 引擎按哈希拉取 wasm 字节（与 `SyncEngineCatalog` 同属引擎接口） | 是 |

- `ValidateFactorSpec`、`PreviewFactor` 增加可选的 `udf_versions`（名称 → 哈希），请求级覆盖，用于在未启用的版本上校验与试算；
- `ListFactorFunctions` 返回已启用的 UDF；`EngineHeartbeat` 增加各模块哈希的就绪状态（11 节）；
- 服务目录 `packages/servicecatalog/catalog.yaml`：新方法加入方法列表、只读方法列表、控制台路由与管理接口的调用方 ACL；
  `GetUdfModule` 加入 `principals.factor-engine.allow`；
- 内嵌服务目录的组件必须用同一提交构建并一起发布：Admin、control 主机网关、Monitor、Access，以及经 `gatewayclient` 做本地检查的调用方（命令行、FactorEngine）。

### 10.3 切换启用版本

成员校验沿用 `UpdateFactor` 修改被引用定义的规则（`catalog/service.go`）；为保证切换之后没有任何计算还在用旧版本写结果，切换在因子引擎模块暂停期间进行。

**锁协议**：管理端增加一把全局的 UDF 锁（单用户，不需要按名称细分）。所有会改变 UDF 引用关系或启用版本的入口都先取这把锁，
再按现有顺序取定义锁、任务锁：`PublishUdf`、`ActivateUdf`，以及新旧原文中任一方引用了 UDF 的 `CreateFactor`、`UpdateFactor`。
绑定解析与最终的编译校验都在锁内完成，引用清单在提交之前不会变化。

**切换在因子引擎模块暂停期间进行。** 在系统运行中“热切换”需要处理的竞态太多：目录同步是定时的、正在计算的那一期与补算分块会继续写出、
补算提交可能在检查之后入库。现有的模块暂停（`packages/lifecycle`，见[暂停恢复与重置设计](暂停恢复与重置设计.md)）正好提供需要的保证：
门禁关闭后因子引擎的三条写结果路径（实时计算、补算作业、追赶推进）都停下；恢复时先追赶、全部追平才放行。

**前置改动**（对普通的暂停恢复同样是缺陷，第一期一并修复）：

1. **在途收敛与证据**：因子引擎目前没有实现生命周期的 `Quiesce` 钩子（只有 Trade、Collector 实现了），而 `lifecycle` 先置为 `paused` 再调用
   `Quiesce`，收敛超时后仍是 `paused`。所以要补上 `Quiesce`（等待在途的实时计算、补算分块、追赶推进结束），并上报“本次暂停已收敛”的证据
   （暂停开始时间与收敛完成时间）；只有 `paused` 不算收敛；
2. **补算领取并入暂停门禁**：现在补算循环只检查目录已加载与租约，暂停期间仍会领取作业。改为暂停期间不领取，收敛时等待在途的领取与当前分块结束；
3. **追赶的执行门禁**：现在进入恢复追赶就允许推进水位与后台补算，可能先用旧目录写出结果。改为追赶在任何写入之前，先确认引擎已应用管理端当前的目录
   （心跳的 `CatalogInSync`）且引用的模块全部就绪；不满足时追赶不执行、上报原因。

**补算作业的版本**：作业在**领取时**才解析绑定并随作业下发，之后（含重启续跑）始终用这份绑定（4.3）。所以已提交、未领取（`accepted`）的作业
在切换后会用新版本执行；只有已领取（`running`）的作业可能跨版本，切换前要求没有这类作业。补算的提交入口因此不需要加 UDF 锁。

**步骤**：

1. 找出引用该名称的因子定义 → 包含这些定义的成员的因子任务 → 关联这些任务的策略实例；
2. 前提一：**因子引擎模块已暂停且本次暂停已收敛**（以引擎上报的收敛证据为准），提交事务前再复查一次。切换期间不得恢复引擎，
   也不得对单个任务强制追赶：单用户按第 9 节的步骤顺序操作即可，不另设互斥；
3. 前提二：**受影响任务没有已领取（`running`）的补算作业**，否则拒绝并列出作业（可用 `CancelRecalcJob` 取消；引擎暂停期间不会领取新作业）；
4. 用新版本重新编译每个引用它的定义，并对每个任务重新做成员校验（成员保存的参数仍在新的参数范围内等），规则同 `UpdateFactor`；任何一项不通过就拒绝；
5. 报告每个定义新旧的 `definition_hash`、回看与输入列；回看变长时列出受影响的任务，检查源数据的保留期能否覆盖新回看，
   并提示引擎侧的 `window.lookback`、`window.max_memory`、`memory.total_budget`、`compute.max_memory` 也要装得下。

`dry_run` 时到此为止，返回影响清单与每个前提的检查结果。执行时在同一事务里改 `c_active_hash`；之后读取这些定义得到新的绑定。
恢复因子引擎后的追赶见 11.1。

## 11. 引擎

### 11.1 模块就绪与目录应用

现有的 `CatalogCache.Apply` 即使有定义编译失败也会安装新快照并记下快照哈希，之后同步返回“未变化”，不会重发。模块的拉取与编译因此必须放在使用定义之前。
引擎有三个入口会拿到带绑定的定义，都走同一个“按绑定准备模块”的函数：

- **准备模块**：本地按内容寻址的目录（`<数据目录>/udf/<哈希>.wasm`）没有就调 `GetUdfModule` 拉取，校验 sha256，再用 wazero 编译
  （编译缓存放在 `<数据目录>/udf/cache/`，每个版本在每台机器上只编译一次）；
- **目录同步**：新快照引用的模块全部就绪才应用快照、记下快照哈希；任何一个失败就不应用，按退避在下一次同步时重试；
- **恢复追赶**：追赶在推进水位、执行后台补算这些写入之前，先确认已应用管理端当前的目录（心跳的 `CatalogInSync`）且引用的模块全部就绪
  （10.3 前置改动第 3 条）。模块准备失败时追赶不执行任何写入、上报原因，门禁不放行，不会拿旧快照、旧版本计算；就绪后用新版本补算暂停期间的周期，再放行；
- **启动恢复**（`CatalogCache.Load`）：模块正常情况下已在本地；缺失且拉取失败时，引用它的任务记为不可执行并上报原因，按退避重试，就绪后恢复；
- **补算领取**：领取后先准备作业绑定的模块；失败时作业报告为失败并写明原因，不写任何分块，由用户重新发起。

心跳上报每个模块哈希的状态（就绪 / 拉取失败 / 编译失败及原因），`udf show` 与控制台展示。于是“管理端已切换”“引擎已就绪”“已放行计算”是三个可以分别看到的状态。

只有目录同步这个入口会在模块准备失败时继续用旧快照；切换总在引擎暂停时进行、恢复时由追赶把关，所以切换之后不会出现“旧快照、旧版本仍在计算”。

### 11.2 实例池与执行

- 每个模块哈希一个实例池：计算时借出、用完归还；池的大小不超过 `compute.workers`；空闲超过一段时间的实例关闭；
- factorexpr 的执行器每次运行临时创建 goroutine（`exec/run.go` 的 `parallel`），没有固定的 worker 身份，所以按借还管理，而不是按 worker 绑定；
- **分批**：同一批序列的 L 必须相同，宿主先按参数取值分组；再按字节预算拆批，
  每批序列数 = `floor(批字节上限 / (8 × (输入个数 × in_len + 参数个数 + out_len)))`，计算时检查乘加溢出；
  结果为 0（单条序列都放不下）时按失败处理并提示调整上限；
- **执行时限制**：实例化与每一次 guest 调用（包括 `reserve`、`abi`）都在带截止时间的上下文里执行，配合 wazero 的 `WithCloseOnContextDone` 中断死循环；
  实例的线性内存不超过上限（`WithMemoryLimitPages`）；超时、trap、内存超限后丢弃该实例；
- 默认值（可配置）：每次调用 10 秒、每个实例 512 MiB、每批 64 MiB。

### 11.3 内存预算

- 实例跨调用保留，它保留的线性内存计入引擎的常驻预算（`memory.total_budget`），按池中实例数 × 实例峰值估算；
- 每次调用拷入拷出的缓冲计入本次运行的计算预算（`compute.max_memory`），运行结束即释放；
- 管理端的试算沿用现有的 256 MiB 上限，发布测试另有自己的上限，都与引擎分开计算。

### 11.4 失败语义

现有的时序内核 `ops.SeriesKernel` 没有错误返回，执行器出错时本次运行的全部成员失败（`pipeline/compute.go`）。UDF 节点遵循同一语义：

- UDF 调用失败（trap、超时、内存超限、返回非 0）时，UDF 内核把错误交给执行器，`exec.Run` 返回错误，本次运行的成员全部记失败；
  factorexpr 需要为 UDF 节点增加这条错误通道（内置内核不受影响）；
- **不填 NaN**：失败若写成 NaN，会被 `fill_nan` 一类算子吞掉或当成正常空值写出，截面算子也会把它当作缺值继续排名，结果看似正常却是错的；
- 失败在因子侧按现有的运行失败记录与上报，策略侧照常看到该期因子失败；
- 指标：`factor_udf_call_seconds{udf}`、`factor_udf_failures_total{udf,reason}`、`factor_udf_copy_bytes_total{udf}`、`factor_udf_module_state{udf,hash}`。

## 12. 控制台

因子定义页增加“自定义算子”：列表（名称、启用版本、更新时间、被引用次数）、详情（元数据、版本列表、服务端测试报告、提交号、引用关系、各引擎的就绪状态）、
切换版本（先展示影响清单与前提检查结果）。因子定义编辑器的补全与校验通过 `ListFactorFunctions` 自动包含 UDF。

## 13. 安全与隔离

| 风险 | 措施 |
| --- | --- |
| 访问文件、网络、时间 | 模块不得有任何导入；wasm 本身没有这些能力 |
| 实例化时执行代码 | 不允许 start 函数；实例化也有截止时间 |
| 死循环 | 每次 guest 调用都有截止时间，经上下文取消中断 |
| 内存失控 | 实例线性内存上限；内存与表的声明大小上限；批字节上限 |
| panic 拖垮引擎 | panic 即 abort，宿主只看到 trap，按运行失败处理 |
| 失败被当成空值 | 失败走错误通道，不写 NaN |
| 结果不确定 | 禁用清单（含 NaN 位模式）+ 两实例对拍 + 本地与服务端的跨架构摘要比对；宿主规范化输出的 NaN |
| 版本被悄悄替换 | 版本不可变、以 wasm 哈希为身份并进入 `definition_hash`；切换只能经 `ActivateUdf`，且在因子引擎暂停、在途收敛后进行 |
| 源码与产物不对应 | 本地编译的局限：记录私有仓库的提交号并要求发布时工作区干净；需要可复现构建时再引入服务端构建（第 14 节） |

## 14. 分期

**第一期**：时序 UDF（单输出、严格或 relaxed 空值、受限的回看公式）；Rust SDK 与模板；`packages/factorudf`；命令行；管理端两张表、接口、切换规则；
factorexpr 的 `udf.` 调用、版本绑定与错误通道；因子引擎的三项前置改动（`Quiesce` 与收敛证据、补算领取并入暂停门禁、追赶的执行门禁，见 10.3）；引擎的模块就绪、实例池、执行时限制与失败语义；控制台列表与详情；moox skill 与[因子](../模块/因子.md)文档。

**以后视需要再做**：

- 区间实现（一次算一段输出，适合递归算法）：需要强制的逐点入口做对拍，并定义区间模式下的空值与失败规则；
- 更一般的回看公式：保守的区间求值；
- 截面 UDF：样本按标的键排序、并列规则由宿主固定；
- 多输出 UDF；
- 历史常驻 wasm 内存、每期只传新值：针对超长回看，需要处理补数据导致的缓存失效；
- 策略 UDF：纯函数（本期行、上期状态、参数）→（分数或权重、原因、新状态），状态由引擎序列化保存，守门、缺数、组合约束、解释明细仍由框架负责；
- 删除版本：删除条件要包含在途与恢复所需的引用；
- 服务端可复现构建与源码归档；
- TinyGo SDK（实测性能与 Rust 相同）。

## 15. 待定问题

1. UDF 回看的上限：沿用因子回看的整体上限，还是对 UDF 另设更小的上限以控制每次调用的拷贝量；
2. 执行时限制与预算的默认值（调用截止时间、实例内存、批字节）需要在实现时用几个典型 UDF 实测后确定；
3. CI 需要安装 Rust 工具链来构建 SDK、模板与示例 UDF，并让 SDK 测试进入 `make test`；
4. 切换版本要先暂停、再恢复因子引擎；是否给 `udf activate` 加一个自动完成“暂停 → 切换 → 恢复”的选项，等实际用过再定。
