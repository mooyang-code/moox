# 统一数据集执行计划

- 日期：2026-11-04
- 状态：v3 定稿，经三轮独立审查没有大、中问题，可以开始编码（见第 7 节）
- 基线：main 7ad72502
- 来源：用户 2026-11-04 决定，现货、永续两种组织方式都要支持，由用户自己选：
  - **分开**：现货、永续各一个数据集，各一个因子任务、一个 View，策略汇合两边（策略计划 3.2 方式 A）；
  - **统一**：同一个数据集里同时放同一标的的现货、永续两条序列，用存储行键里已有的 `series_tag` 区分，只要一个因子任务、一个 View。用户看到的标的名仍是 `BTC-USDT`。
- 关联：`docs/计划/策略多市场与策略池执行计划.md`（下称“策略计划”）3.2.2 的方式 B 和任务 S1.8 依赖本计划
- 约束：单用户，不过度设计；统一数据集一律新建（从零采集或导入），不改造已有的分开数据集，也不允许已有任务在单市场和多市场之间切换

## 1. 目标

1. 一个采集任务可以同时挂现货、永续两个标签，写进同一个数据集，两条序列靠 `series_tag` 区分、互不覆盖。
2. 采集的周期账本、补采、完整性检查、K 线合成都能正确处理“一个数据集多条市场序列”。
3. 因子在统一数据集上照常计算：
   - 时序算子逐条序列算；
   - 截面算子按市场分组；
   - 期望全集、缺失、跳过、失败都按（标的、市场）判断，一个市场的缺数、失败、延迟不连累另一个。
4. 策略能直接用统一数据集上的一个因子任务做五种市场模式（策略计划 3.2.2）。
5. 导入、回放、管理台、命令行、监控都能识别市场序列。

不做：

- 跨市场因子（基差、溢价）：截面按序列分组，写不出“同一个币现货减永续”的表达式。
- 改造已有的分开数据集。
- 闭环回放支持多市场。

## 3. 设计

### 3.1 统一数据集的识别

- **tag 取值**：沿用生产上现有的值（2.1）：现货 `venue:binance|market:spot|source:spot_http`，永续 `venue:binance|market:swap|source:swap_http`。不改成字面的 SPOT、SWAP，以免监控探针、命令行配置、`MOOX_MARKET_FETCH_SERIES_TAG`、合成配置、管理台的精确查询都要连带修改。导入页输入框占位文字里的裸写 `venue:binance`（`web/.../data/import/index.vue:67`）改成实际取值。
- **tag 到市场**：在 `packages` 下新增 `SeriesTagMarket(tag)`：按 `market:` 段解析，没有这一段的视为现货；返回小写的 `spot`、`swap`，与标签的 `market_type`、策略的 `resolve.go:349` 一致。因子、策略、命令行、管理台都用它，不另存映射。生成 tag 的正向逻辑依赖采集模块的 `DefaultSourceID`，留在 collector，不移出来。单测用生产的实际取值。
- **数据集属性**：统一数据集的 `market_type` 写成 `multi`。采集建数据集时：
  - 两个标签的 `sync.source` 相同、市场不同 → `market_type = multi`，`data_source_id` 保留；
  - 两个标签的 `sync.source` 不同 → 建任务时拒绝。
- **每个市场的标的与活跃状态**：来自数据集挂的标签加上标签的 `market_type`。现货标签下的标的属于现货序列，永续标签下的属于永续序列。

### 3.2 用户怎么选

- **建采集任务**：
  - 选了现货、永续两个标签，就是统一数据集（一个任务）；
  - 想分开，就建两个任务，各挂一个标签。

  不另存一个“组织方式”字段。管理台在用户同时选了两个市场时给出提示：“合并为一个数据集”，还是“按市场拆成两个任务”。选后者，页面就一次建两个任务。
- **已有任务不能在单市场和多市场之间切换**：`Ensure` 只补属性（`result.go:579-584`），切换会留下半旧的数据集。编辑时拒绝跨市场增删标签，提示新建任务。
- **建因子任务**：源是统一数据集，结果也就是统一数据集。
- **建策略实例**：二选一：
  - 方式 A：绑两个任务（现货、永续各一个），汇合求值；
  - 方式 B：绑一个统一数据集上的任务。

### 3.5 因子

**期望全集与缺失按序列**：

- 期望序列全集来自 `universe_series`，三条计算路径都要拿到：
  - **实时计算**：从源数据集周期完成事件的 `universe_series` 读。
  - **空洞恢复**：现在通过 `storageio/marker.go:72` 读因子自己结果数据集的 marker 里冻结的全集（`engine/gapfill.go:443`）。因子写自己的周期完成标记时也带上 `universe_series`（`storageio/marker.go:129`），Storage 复制 marker 字段时保存它（`datanode/marker.go:65`），恢复时改读它。
  - **人工补算**：现在取 `selection.Subjects`（`recalcexec/executor.go:561`），改读同一份 marker 里的 `universe_series`。
- 截面的严格全集按（标的、tag）判断缺失（`compute.go:44-46`）。不允许部分全集的截面因子，只在**缺失的那个 tag** 上跳过，另一个 tag 照常算（`compute.go:68`）。

**成员状态的汇总规则**：`FactorPeriodState.status` 只有一个值，规则写死如下：

- 全部 tag 都跳过，才记 `skipped`；
- 只有部分 tag 跳过，记 `degraded`，并在新字段 `skipped_series_tags` 里列出跳过的 tag，这些 tag 的序列在结果里写 NULL；
- 读这个状态的地方要逐一按新规则处理：
  - 策略的就绪判断（`readiness.go:124-140`）：`degraded` 加 `skipped_series_tags`，只让对应市场不可用；
  - 预热完成判断（`engine/lifecycle.go:308`）：`degraded` 算作已完成；
  - 状态迁移（`run_tracker.go:156`）；
  - 结果组装（`pipeline/assemble.go:175`）：只删跳过的 tag 的参数、写 NULL，不动整个成员。

**失败与空洞按序列**：

- `FactorPeriodState` 新增 `failed_series`、`gap_series`、`skipped_series_tags`，每项是（标的、tag）或 tag（`factor.proto:109-117`）。
- 生成处同步修改：`period_detail.go:41-57`、`run_tracker.go:149-160`、`gapledger/ledger.go:43、87`。
- 原有的按标的字段保留现在的口径，单市场任务不受影响。

**结果与预检**：

- 一个 tag 失败，只把这条序列的行写成 NULL（`assemble.go:185-194`）。
- 结果项的键加 tag（`types.go:154`）。
- 内存预检按序列数估算（`compute.go:282`）。

**就绪与同步**：

- `Bounds` 按 tag 分开返回（`seriesstore/store.go:331-345`）。
- 就绪判断（`localdata.go:736-750`）和增量同步（`seriessync/sync.go:243`）按每条序列各自的最新时间。
- 期望序列来自 `universe_series`：新上永续的币，从它第一次出现在 `universe_series` 里算起。

**参数**：仍按标的取值，两个市场共用一组参数（`assemble.go:369-380`）。

### 3.6 策略

见策略计划 3.2.2。下面几处由策略计划负责，本计划只提供依赖：

- 就绪判断读因子明细的 `failed_series`、`gap_series`、`skipped_series_tags`，按（标的、市场）判断（`readiness.go:124-140`）。
- 读取不带 tag 的 selector，读全量后在内存里用 `SeriesTagMarket` 换成市场，再按 DSL 的 `market` 过滤。
- 歧义判断：统一数据集上，同一标的出现能换成市场的不同 tag 是正常的；换不出市场的 tag 才算歧义（`frame.go:247`、`range.go:476`）。研究回放也走 `range.go`。
- 活跃状态和标的全集按市场：标签成员加 `market_type`（`client.go:211-275`）。
- 年龄探针按（标的、市场）记录，`t_strategy_age_passed` 的主键加市场（`sets.go:232-246`）。

### 3.7 导入、回放、管理台、命令行、监控

- **导入**：
  - 整段替换只删文件里出现的（标的、tag）序列（`runner/runner.go:461`）；
  - 导入包清单的 tag 可以按文件分别指定（`import_pack.go:42`）。

  这样现货、永续可以分两次导入。
- **研究回放**：走策略的 `range.go`，随策略计划 S1.8 和 S2 一起处理。闭环回放（`ValueAt`）在策略侧本来就拒绝多市场，这里确认会被拒绝即可。
- **管理台**：
  - 视图浏览页的 tag 列用 `SeriesTagMarket` 显示成“现货”“永续”，行详情显示市场；
  - 数据集信息显示“统一数据集（现货、永续）”；
  - 采集任务页按 3.2 提示。一次建两个任务时，第二个失败就保留第一个，并提示用户补建。
- “禁止跨市场改标签”由后端的更新任务接口拦截，不只靠前端。
- **命令行**：查 K 线用 `--market spot|swap` 选序列（`data_kline.go:104-115`）。

## 5. 风险

1. **两个市场互相等待**：两个市场共用一份快照，一个周期要等两边都提交或到截止时间。一边的标的变化，也会让两个市场的函数一起重新下发。所以统一数据集上只用现货的策略，也会被永续拖慢。只用一个市场的用户应选“分开”的方式，管理台提示里写明这一点。
2. **按标的折叠的遗漏**：调研列出的折叠点可能不全。U6 的验收要用“永续晚到、现货正常”“永续缺一个币”两个真实场景跑一遍。
3. **数据量翻倍**：统一数据集里每个币两条序列，View 行数和存储占用都翻倍，删旧行的耗时也会增加。V2 要记录 View 大小和删旧行耗时。
4. **跨市场因子写不出来**：截面按 tag 分组。需要基差这类因子时，另做设计。

## 6. 不做

1. 跨市场因子（基差、溢价）。
2. 改造已有的分开数据集，以及已有任务在单市场和多市场之间切换。
3. 闭环回放支持多市场。
4. View 就绪事件的序列字段：策略不读它。
