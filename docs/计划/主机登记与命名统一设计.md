# 主机登记与命名统一设计

设计稿 v7.1（2026-10-24，决策已确认，尚未编码）。实现后以[部署与运维](../部署与运维.md)、[管理后台](../模块/管理后台.md)、[监控](../模块/监控.md)、[前端](../模块/前端.md)为准。

## 1. 原则与目标

原则：
- 只有一个超级用户，登录即拥有全部权限，不设计角色、成员、多用户。
- 个人量化系统，能用简单办法就不引入机制。
- 项目未上线，表结构直接改 `schema/*.sql`，上线时全新部署，不写数据迁移，也不设计平滑回退。

目标：
1. 服务拓扑能看到内网因子机，以及它上面跑的因子引擎和归档 worker。
2. 主机列表、主机监控只展示登记的机器，显示中文名和 IP。
3. 统一主机的职责与命名；代码和界面统一用“部署”一个词。
4. **机器的新增、部署、启停、移除一律通过 moox skill（`moox-cli`）完成；控制台只展示，并提示用 moox skill 操作。**
5. 精简 Admin 库，删除重复和无人使用的表、字段与接口。

## 2. 现状（2026-10-24，生产只读与代码核对）

- **三套主机登记互不约束**：
  - 部署主机：Admin `t_hosts`、`t_placements`，由 CLI 按 `moox.toml` 同步；
  - SSH 主机：`t_ssh_host`，只在初始化时写入当时的主机，之后靠控制台手工增删；
  - 主机采集器：Monitor `t_monitor_host_agents`，`agent_id` 是随机 4 位身份，`host_id` 是部署主机 ID。
- **生产数据**：只有 control、storage、overseas 三台，库里没有多余的行；`compute-1` 已改名为 `overseas`。overseas 没有 SSH 记录，因为它是 `deploy-host` 后加入的，这条路径不写 SSH。
- **页面“脏数据”的原因**：
  - 前端把采集器的 `agent_id` 当成主机 IP 去和 SSH 记录配对（`toHostMetrics`）；
  - 按名字配对也失败：`control` 对不上操作系统主机名 `VM-12-13-ubuntu`；
  - 结果主机列表显示 5 行，主机监控显示 5 张卡。
- **因子机**：
  - 192.168.0.103 在家庭网络里，只能出站，以 systemd 用户服务运行 `moox-factor-engine`、`moox-archive-worker`，两者都以外部身份经 Access 访问系统；
  - 反向连接和“192 登记为主机”的代码已经完成（主机守护计划 D10、D17），但一直没有登记。
  - 两个程序的健康端口分别是 11417、11418。11417 上还挂着导入、生命周期、回放路由，它们同样要求健康 HMAC，这和其他模块一致。
  - 安装脚本给两个程序随机生成健康密钥，所以 Monitor 探测不了它们。
- **命名**：同一个概念，代码里叫 placement，界面上叫“部署”；中文名借用 `t_hosts.c_description` 存放。
- **Admin 库 14 张表里**：
  - `t_space_members` 是空表，只被成员鉴权读取，没有写入方；
  - `t_ssh_session`、`t_login_history` 只写不读；
  - 用户表的昵称、邮箱、头像全为空；
  - 密钥表的“最后使用”两列从未写入。

## 3. 设计决策

| 编号 | 决策 |
| --- | --- |
| D1 | `t_hosts` 是唯一的主机登记，主机只来自 `moox.toml` 的 `[hosts.*]`，只经 `moox-cli` 写入 |
| D2 | 机器的新增、部署、启停、移除，以及外部程序的退役，只经 moox skill（`moox-cli`）。控制台只读：去掉这些按钮，服务目录里对应写接口的 `console` 调用方也一并去掉。终端连接、文件管理保留 |
| D3 | 主机 ID 用小写英文角色名，中文名由角色决定；同一角色有多台时加序号（`overseas-2` / 海外机 2） |
| D4 | 因子机 `factor` 按只能出站的主机登记，部署完整的 host 单元 |
| D5 | `factor-engine`、`archive-worker` 作为“外部程序组件”进服务目录，部署在 `factor` 上；访问系统仍用同名外部身份经 Access；它们不能出现在内部 ACL 里 |
| D6 | 外部程序的部署健康由 Monitor 经中转探测各自的健康端口（`readyz`）；健康签名改用系统健康密钥；中转许可在 `monitor` 之外再放行 `moox-cli`；引擎的健康端口不拆分 |
| D7 | 部署记录表示期望状态。部署和升级时也遵守停用状态：主机或部署停用时，安装但不启动 |
| D8 | 启停命令修改登记状态；对外部程序，CLI 同时经 SSH 操作它的 systemd 服务并核对结果 |
| D9 | “placement”全链路改名为“部署（deployment）”，表名改为 `t_deployments`。Storage、Trade、腾讯云 SDK 和前端组件属性里含义不同的 placement 不改 |
| D10 | SSH 并入主机登记：端口、用户名、指纹成为 `t_hosts` 的列，密码或私钥存进 `t_secrets`（ID 为 `ssh-host-<主机ID>`）。只有 `moox.toml` 里配了密码或私钥文件的直达主机，才会同步给控制台；没配的主机和只能出站的主机，控制台都置灰。指纹按“地址 + 端口”管理，这两项变化时清空。终端外观存在浏览器本地 |
| D11 | **单用户**：删除 `t_space_members` 和所有按角色、成员的鉴权，登录即拥有全部权限；用户表只保留登录需要的字段；删除 `UpdateUserInfo` |
| D12 | **日志**：不再记录 SSH 会话，删除 `t_ssh_session`；成功登录写一条活动日志 `auth.login`，删除 `t_login_history`；活动日志允许不属于任何空间（全局），活动页增加“全局”选项 |
| D13 | 删除密钥表的“最后使用”两列，包括协议、接口映射和前端里的相关字段 |
| D14 | 初始化（`ApplySetup`）不再处理主机。SSH 信息统一由部署同步写入，离线 bootstrap 的写入链也包括在内 |
| D15 | 主机监控按采集器上报的 `host_id` 关联登记主机，只展示登记主机；同一主机有多个采集器时，取最近上报的一个。Monitor 后端的主机汇总与失联告警也用同一规则 |
| D16 | 因子引擎和 archive-worker 暂时只支持 Linux，删除两者在 macOS / Windows 上的安装方式与服务代码 |
| D17 | 存储节点的编辑和删除改为只读，CLI 新增 `storage node update`、`storage node delete` |
| D18 | SCF 云函数与代码包管理不在本次范围内 |
| D19 | 上线方式是全新部署：删除线上全部数据，按初始化流程重建，不写迁移命令，也不设计回退 |

## 4. 设计

### 4.1 主机职责与命名

| 主机 ID | 中文名 | 职责 | 业务组件 | 可达性 |
| --- | --- | --- | --- | --- |
| `control` | 控制机 | 控制面与业务调度 | console-proxy、web-host、admin、eventbus、monitor、collector、cloudfunction、factor-mgr、strategy、archive-mgr | 直达 |
| `storage` | 存储机 | 数据面；国内 SCF 写入入口 | storage-primary、storage-node、storage-view、access | 直达 |
| `overseas` | 海外机 | 海外 IP 出口：交易、WS 行情、香港 SCF 写入入口 | trade、collector-stream、egress-proxy、access | 直达 |
| `factor` | 因子机 | 离线计算：因子计算、数据归档导出；可以在内网，必须是 Linux | factor-engine、archive-worker | 只能出站 |

每台主机都有 host-gateway、host-agent，由代码补齐。新增角色时，先改本表与[部署与运维](../部署与运维.md)第 1 节。

### 4.2 Admin 数据模型（直接修改 `schema/admin.sql`）

| 表 | 结果 |
| --- | --- |
| `t_hosts` | 增加 `c_label`（中文名）、`c_ssh_port`（`0` 表示控制台不能 SSH）、`c_ssh_user`、`c_ssh_fingerprint`；`c_description` 只放补充说明 |
| `t_deployments` | 原 `t_placements` 改名，结构不变 |
| `t_host_gateway_status` | 不变（网关心跳频繁写入，与配置表分开） |
| `t_secrets` | 新增 `ssh` 分类记录（`ssh-host-<主机ID>`，类型为 `password` 或 `ssh_key`；`c_key_id` 存用户名）；删除 `c_last_used_at`、`c_last_used_by` |
| `t_activity_logs` | 新增类别 `auth.login`；`c_space_id` 为空表示全局事件 |
| `t_users` | 只保留 `c_user_id`、`c_username`、`c_password_hash`、最后登录时间与 IP、创建与修改时间，删除角色、状态、昵称、邮箱、头像等列 |
| `t_spaces`、`t_collector_publish_leases`、`t_collector_publish_operations` | 不变 |
| 删除 | `t_ssh_host`、`t_ssh_host_key`、`t_ssh_session`、`t_login_history`、`t_space_members` |

**接口**：
- SysDeploy：
  - `ListPlacements` / `SetPlacementStatus` / `SyncHostPlacements` / `ComponentPlacement` 改名为 `ListDeployments` / `SetDeploymentStatus` / `SyncHostDeployments` / `Deployment`；
  - `DeploymentHost` 增加 `label`、`ssh_port`、`ssh_user`（不含凭据），控制台的主机列表直接用 `ListHosts`；
  - `SyncHostDeployments` 请求可以携带 SSH 凭据。Admin 在同一事务里写 `t_hosts` 的 SSH 列和 `t_secrets`；没带凭据时，把该主机的 SSH 置空。凭据不进日志和错误信息。
- `ops.Ssh`：
  - 删除主机的增删改查接口；
  - `CreateSession` 改用字符串 `host_id`：Admin 从 `t_hosts` 和 `t_secrets` 取连接信息，首次连接时把指纹写回 `t_hosts`；
  - 连接建立后仍用 `session_id` 定位会话，一次性 ticket 与所有者校验保持不变。
- 密钥管理：`ssh-host-` 前缀的记录和网关密钥一样由系统维护，控制台看不到，也改不了。
- 删除：`ListSpaceMembers`、`UpdateUserInfo`，以及 `UpdateLastUsed` 这个 DAO 方法。

**鉴权**（D11）：
- `AuthorizeSpaceRequest` 只检查空间存在且启用，不再看角色和成员；
- 控制台、发布租约、活动日志里按角色的判断全部删除（`console/console.go`、`console/resolver.go`、`space`、`publishlease`、`activitylog`，以及 `cmd/cli/admin_user.go`）。

**删除部署主机**（SysDeploy `DeleteHost`）在一个事务里依次删除：
1. `t_secrets` 里该主机的 `ssh-host-` 记录；
2. `t_host_gateway_status`；
3. `t_deployments`；
4. `t_hosts`。

提交后关闭该主机在内存里的终端和 SFTP 会话。创建会话、写回指纹、同步 SSH 信息和删除主机都持有同一把按主机的锁，所以旧连接不会把旧指纹写回已经改过地址的主机。

**登录日志**：登录成功后，由 auth 服务经本地的活动日志写入器记一条 `auth.login`（用户名、IP、UA）；失败不记录，仍沿用现有的尝试计数。
活动日志查询允许空 `space_id`，表示全局；活动页增加“全局”选项。业务重置照常清空活动日志。

### 4.3 外部程序组件

**服务目录**（`packages/servicecatalog/catalog.yaml`，字段名实现时定）：

```yaml
- id: factor-engine
  name: 因子引擎
  binary: moox-factor-engine
  scope: any
  replicas: single
  protected: false
  external_program: true
  health: { kind: readyz, port: 11417, ready_body: '"ready":true' }
  doctor: { role: factor-engine, transport: health_only, supervisor: systemd_user, unit: moox-factor-engine }
- id: archive-worker            # 同上，健康端口 11418，unit 为 moox-archive-worker
```

- **校验**：外部程序组件必须有同名外部身份，不声明 `services`、`ports`，也不出现在任何 `acl.callers` 里。
  只有这种组件允许和外部身份同名。
- **健康**：
  - Monitor 已经支持只能出站主机上 `readyz` 组件的中转探测，不用新增逻辑；不要设置 `health.loopback`。
  - 健康端口的中转许可，在 `monitor` 之外再放行 `moox-cli`（`routes.go` 的许可生成与 `ValidRelay`、网关侧校验）。
  - `deploy-unit` 用 core state 里的 `runtimeIdentity` 渲染系统健康密钥，安装脚本不再自己生成。
- **Doctor**：
  - `supervisor`、`unit` 两个字段要同时加在 `servicecatalog.Doctor`（严格解析）和 `packages/doctor` 的投影上。
  - CLI 诊断对 `systemd_user` 组件经 SSH 检查 `is-enabled`、`is-active` 和 linger，健康检查经中转进行。
- **安装**：
  - `setup deploy-unit --host factor --profile factor-engine|archive-worker`（沿用现有的 `--profile` 参数）从指定 release 取制品，经 SSH 执行安装脚本，核对 linger，再经中转等待 `/readyz`。
  - 主机或部署是停用状态时，加 `--no-start` 并 `systemctl --user disable`。
  - release 打包清单要加入两个程序。
  - 安装脚本只保留 Linux 分支。

### 4.4 配置与 CLI

- `moox.toml`：

  ```toml
  [hosts.factor]
  label = "因子机"
  address = "192.168.0.103"     # 只用作身份与证书 SAN
  reachability = "outbound"
  ssh = { port = 22, username = "mooyang" }   # 只供 CLI 在内网部署

  [deployments]                 # 原 [placements]
  control = ["console-proxy", "web-host", "admin", "eventbus", "monitor", "collector", "cloudfunction", "factor-mgr", "strategy", "archive-mgr"]
  storage = ["storage-primary", "storage-node", "storage-view", "access"]
  overseas = ["trade", "access", "egress-proxy", "collector-stream"]
  factor = ["factor-engine", "archive-worker"]
  ```

  删除 `[factor_engine]` 和 `Manifest.Hosts` 里的因子机特例。直达主机的 `ssh` 里，配了 `password` 或私钥文件，才会同步给控制台。
- `config migrate`：把 `[placements]` 改名为 `[deployments]`，把 `[factor_engine]` 转成 `[hosts.factor]` 和两个部署，`local` 取值直接报错。配置向导同步修改：生成新格式，删除 local 模式，只接受 Linux。
- 命令：
  - `sync-deployments`（原 `sync-placements`）携带 `label` 和 SSH 信息，`deploy-host` 同样携带。离线 bootstrap 写入主机的链路（`unitbootstrap` 到 `admin/cmd/cli/bootstrap.go` 的 `SyncHosts`）也写入 control 的 SSH 信息。
  - `setup host enable|disable`、`setup deployment enable|disable`：先预览，加 `--yes` 才执行。
    - 外部程序停用时，先 `stop` 加 `disable`，再改登记；启用时先改登记，再 `enable` 加 `start`，并等待 `/readyz`。
    - 主机停用前，先停掉它上面的外部程序；主机停用时，拒绝启用其上的部署。
  - `storage node update|delete`、`archive worker retire`。
- `ApplySetup` / `GetSetupStatus` 删除主机部分；`remove-host` 不再单独清理 SSH。

### 4.5 Monitor

- 不新增探测逻辑。
- 改名范围：
  - 包 `internal/placement`；
  - 检查 ID 前缀与检查来源值 `placement`；
  - 部署快照的 JSON 字段（`domain/topology.go`）；
  - 配置键 `placement`（严格解析）及其生成端（CLI 的 `unitdeploy/control.go`）；
  - tRPC 定时服务名（`trpc_go.yaml`、`service_runtime.go`）；
  - 健康视图、告警关联、Reporter 归属与清理保护里的同名字段（4.7）。
- **主机汇总按登记主机**：健康视图现在每个采集器输出一台主机、各自生成失联告警（`internal/healthview/hosts.go`）。改为每台登记主机只取最近上报的那个采集器，参与汇总和失联告警；同一主机的其他采集器不再告警。
- 全新部署后，Monitor 库是新建的，不需要处理旧数据。
- 测试要覆盖“启动后第二次定时同步正常”，避免定时服务名只改了一边。

### 4.6 控制台

统一提示：

> 主机与部署由 moox skill 维护。在 Claude Code 中告诉 moox skill 要做的事，或运行 `moox-cli setup …`。

| --- | --- |

## 5. 上线：全新部署

1. **本地**：用新版 CLI 执行 `config migrate`，把 `moox.toml` 转成新格式；需要控制台 SSH 的主机，补上密码或私钥文件。
2. **构建**：同一提交构建 release（`setup release build`），包含两个外部程序。
3. **清空线上环境**：
   - 停止 control、storage、overseas 的守护与全部单元，删除部署目录（`/data/moox`）；
   - 在 192 上停止并删除两个外部程序的服务与安装目录；
   - 清理云上由系统创建的 SCF 函数与触发器，避免重新初始化后出现重复；
   - 在本机删除 CLI 的部署状态目录和操作员身份目录，或者改用全新的空目录，之后所有命令都用这一组目录。
     否则 bootstrap 会复用旧制品（`unitdeploy/software.go`），已安装的操作员身份也会因为绑定旧 CA 而被拒绝（`unitbundle/operator.go`）。
4. **全新初始化**（按[部署与运维](../部署与运维.md)第 2 节的原生初始化顺序，操作者需在内网）：
   1. `setup validate`；
   2. `bootstrap --stage core`；
   3. 对 storage、overseas、factor 执行 `deploy-host`；
   4. 对 storage、access、egress-proxy、trade、collector-stream 执行 `deploy-unit`；
   5. `bootstrap --stage control`；
   6. `setup init`；
   7. 最后对 factor-engine、archive-worker 执行 `deploy-unit`。两个外部程序依赖 control 上的 factor-mgr、archive-mgr、EventBus 与 Access：
      archive-worker 要等 archive-mgr 确认心跳后才就绪（`archive/cmd/worker/main.go`），提前部署会卡在就绪等待；
   8. 按现有流程导入因子、空间元数据等业务配置。

   以上部署命令都带 `--release <ID>`。
5. **验收**：
   - 主机列表与主机监控只有四台主机，显示中文名和 IP；
   - 服务拓扑出现 factor 列，两个外部程序的部署健康为正常；
   - 控制台能打开三台直达主机的终端，factor 置灰；
   - 部署页没有启停按钮；
   - 活动日志的“全局”里能看到登录记录。

如需撤回，用旧版本按同样的流程重新部署。

## 7. 风险

- **反向连接第一次上生产**：192 的出口 IP 会变，会话断开期间 factor 的部署探测失败；失联判断以 host-agent 的上报为准，并且已有“主机网关反向连接”告警。
- **全新部署会清空行情、因子、策略等全部线上数据**：这是已确认的取舍（D19）。因子引擎重装后需要重新预热和补算。
- **紧急启停需要 CLI 环境**：外部程序的启停还要求操作者在内网。
