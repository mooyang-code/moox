# 主机登记与命名统一设计

设计稿 v4（2026-10-24，决策已确认，尚未编码）。实现后以[部署与运维](../部署与运维.md)、[管理后台](../模块/管理后台.md)、[监控](../模块/监控.md)、[前端](../模块/前端.md)为准。

- **v2**：确认原第 8 节的全部待定事项，补全各阶段的改动位置。
- **v3**：吸收一轮 Codex 审查（14 条意见加 2 个待确认项）。
  - 外部程序的健康改为经中转探测各自的健康端口，不再新增 doctor transport；健康签名改用系统健康密钥。
  - 区分“登记状态”和“进程启停”：停用外部程序时，CLI 同时停掉它的 systemd 服务。
  - 只能出站的主机在控制台上终端、文件管理置灰，也不写 SSH 记录。
  - 归档 worker 的退役移到 CLI。
  - 补上 SSH 记录删除事务、Admin 表迁移、发布版本与目录一致性、配置向导、删除清单、采集器 ID 规则。
  - 引擎的导入写入接口与健康端口分开，避免中转许可连带打开写入接口。
- **v4**：吸收 Codex 第二轮审查。第一轮的 16 项中，11 项已解决，其余在本版补齐；另有 12 项新意见，加 2 个待确认项。
  - 初始化的 Apply / Status 只针对直达主机；
  - 健康端口的中转许可放行 `moox-cli`；
  - 主机停用时不能启用外部程序，主机级启停逐个程序返回结果；
  - 删除主机的事务保留放置清理，并关闭内存中的 SSH 会话；
  - 迁移处理孤儿引用、保留自增高水位；
  - 引擎的全部非健康接口（导入、生命周期、回放）都移出 11417；
  - 本地配置转换前移，外部程序进入 release 制品；
  - 分两种情况写回退；
  - 补全 `servicehost` 的删除范围；
  - 自启动诊断分别检查 enabled、active 和 linger；
  - Doctor 字段的解析链写进清单。

## 1. 目标

1. 服务拓扑要能看到内网因子机，以及它上面跑的因子引擎（登记信息和部署信息都要有）。
2. 主机列表、主机监控只展示系统登记的机器，显示中文名和 IP，去掉现在的重复行和看不懂的标识。
3. 统一主机的职责与命名。
4. **机器的新增、部署、启停、移除一律通过 moox skill（`moox-cli`）完成；控制台只展示，在相应位置提示用 moox skill 操作。**

## 2. 现状核查（2026-10-24，生产只读与代码核对）

### 2.1 三套主机登记

| 登记 | 表 | 谁写入 | 用在哪 |
| --- | --- | --- | --- |
| 部署主机 | Admin `t_hosts`、`t_placements` | `moox-cli setup` 按 `moox.toml` 的 `[hosts.*]`、`[placements]` 同步（`SyncHostPlacements`） | 服务部署页、网关路由、服务拓扑 |
| SSH 主机 | Admin `t_ssh_host`（整数主键 `c_id`；`t_ssh_host_key.c_host_id`、`t_ssh_session.c_host_id` 引用它，但没有声明外键） | `setup init`（`ApplySetup` 的 `ensureHost`，`c_creator = setup`）只在初始化时写入当时的主机；之后只能在控制台手工增改删；`setup remove-host` 在删除部署主机**之后**按名字删除 SSH 记录 | 主机列表、终端、文件管理 |
| 主机采集器 | Monitor `t_monitor_host_agents`（`c_agent_id` 唯一，`c_host_id` 不唯一） | 各主机 host-agent 上报：`c_agent_id` 是随机 4 位身份，`c_host_id` 是安装器注入的部署主机 ID | 主机监控（历史曲线按 `agent_id` 查询） |

三套之间没有外键。前端用“地址相同”或“名字唯一相同”去猜它们的对应关系。

### 2.5 因子机与两个外部程序

- 192.168.0.103 在家庭网络里，只能出站。上面以 systemd 用户服务运行 `moox-factor-engine` 和 `moox-archive-worker`，已开启 linger（主机守护计划 2.1 的核查）。
- 两项前置能力已在[主机守护与告警高可用执行计划](主机守护与告警高可用执行计划.md)里编码完成：D10（192 按完整 host 单元登记）和 D17（反向连接）。
  但“登记 192”这一步运维操作一直没有执行。
- 两个程序都以外部身份经 Access 访问系统（`factor-engine`、`archive-worker` 都是 principal），不在服务目录的组件里。
  服务目录校验禁止组件 ID 与外部身份同名（`packages/servicecatalog/validate.go`）。
  Admin 也拒绝把外部身份放进内部验签密钥集合（`modules/admin/internal/service/keys/store.go`）。
- 两个程序都有本机健康端口：引擎 `trpc.moox.factor.Health` 监听 `127.0.0.1:11417`，worker `/readyz` 监听 `127.0.0.1:11418`。
  但安装脚本给它们**随机生成**健康签名密钥（`deploy-factor-engine.sh` 的 `health-auth.env`），Monitor 用的是系统健康密钥（`HealthAuthConfig`），所以现在探测不了。
- Monitor 对只能出站主机上 `readyz` 组件的探测已经支持经 control 中转：`internal/placement/sync.go` 生成合成主机名，中转许可自动包含该主机上已放置组件的健康端口。
- 在线状态的业务检查 `worker_presence:<程序>` 用于告警：管理端停止上报、或没有任务时都判为通过，也不核对程序跑在哪台主机上。它不适合当部署健康用。
- 现有启停接口（`SetHostStatus`、`SetPlacementStatus`）只改数据库；Access 只核对外部身份白名单，不看放置状态。所以只改登记状态停不住外部程序。
- Admin 的 SSH 终端、SFTP 直接拨 `地址:端口`（`ssh/conn/ssh_conn.go`）；反向连接只中转网关端口和健康端口。所以控制台连不到只能出站的主机。
  CLI 部署（`deploy-host`、`deploy-unit`）同样直接 SSH，操作者必须在内网里。
- `moox.toml` 用 `[factor_engine] host = "<主机>|local"` 指定引擎所在机器；`Manifest.Hosts` 对“因子计算机没有放置时不算部署主机”有特例；
  配置向导（`modules/cli/internal/configinit`）也生成 `[factor_engine]`，并把因子机排除在部署拓扑外。

## 3. 设计决策

| 编号 | 决策 | 原因 |
| --- | --- | --- |
| D1 | Admin `t_hosts` 是唯一的主机登记；主机只来自 `moox.toml` 的 `[hosts.*]`，只经 `moox-cli` 写入 | 三套登记各管各的是这次问题的根源 |
| D2 | 机器新增、部署、启停、移除、外部程序退役只经 moox skill（`moox-cli`）。控制台只展示，在操作位置给出提示和对应命令；服务目录里这些写接口去掉 `console` 调用方。终端连接、文件管理属于“使用机器”，保留 | 用户要求；部署要预检、确认和记录，放在 skill 里统一处理；只删按钮不收 ACL，控制台仍能直接发请求 |
| D3 | 主机 ID 用小写英文角色名，中文名由角色决定；同角色多台时加序号（`overseas-2` / 海外机 2）。职责见 4.1 | 现有约定已经是这样，这次定为唯一规则 |
| D4 | 因子机 `factor` 登记为部署主机，可达性为只能出站，按完整 host 单元部署 | 沿用主机守护计划的 D10、D17 |
| D5 | `factor-engine`、`archive-worker` 作为“外部程序组件”进服务目录，放置在 `factor`。访问系统仍用同名外部身份经 Access，鉴权路径不变；它们不能出现在任何内部 ACL 的调用方里 | 部署记录完整，拓扑、部署页、监控按放置展示；不让同名带来内部身份混用 |
| D6 | 外部程序的部署健康 = Monitor 经中转探测它的健康端口（`health.kind: readyz`、doctor transport `health_only`），健康签名用系统健康密钥 | 直接反映进程是否就绪；复用现有探测与 doctor 契约，不新增 transport；在线状态检查继续只用于告警 |
| D7 | 放置表示**期望部署**。放置写入后组件还没装好时，页面按探测结果显示（异常 / 未知），不另设“未安装”状态 | 与现有 `deploy-host` 先同步放置再安装的流程一致 |
| D8 | 区分登记状态与进程启停：主机、组件的启停命令改登记状态；对外部程序，CLI 还要经 SSH 停止或启动它的 systemd 服务并核对结果 | 外部程序不经网关路由，只改登记状态停不住它 |
| D9 | `t_hosts` 增加 `c_label`（中文名），`c_description` 只放补充说明 | 中文名是展示主键，不该借用说明字段 |
| D10 | SSH 记录与登记主机一一对应：`t_ssh_host` 增加 `c_host_id`（唯一、外键指向 `t_hosts`、主机删除时级联）。由 CLI 写入，删除部署主机时在同一事务里清理。只能出站的主机不写 SSH 记录，初始化的写入、检查与计数也都只针对直达主机；控制台的终端、文件管理对它置灰 | 主机列表只能是登记的主机；控制台连不到内网主机 |
| D11 | 主机监控按采集器上报的 `host_id` 关联登记主机，只展示登记主机；同一主机有多个采集器时取最近上报的一个，其余提示为旧记录 | 去掉按地址、名字猜测配对 |
| D12 | 因子引擎和 archive-worker 暂时只支持 Linux，只运行在登记的主机上；删除 `[factor_engine]` 配置、两程序的 macOS launchd 与 Windows 安装、服务代码；共享包的 Windows 实现保留 | 用户决定；“只展示登记的机器”要求运行中的程序都落在登记主机上 |
| D13 | 存储节点的编辑、删除改为只读，CLI 新增 `moox-cli storage node update` 与 `moox-cli storage node delete` | 数据节点属于部署拓扑 |
| D14 | SCF 云函数与代码包管理不在本次范围内，控制台照旧可以操作 | 属于采集业务配置，以后再单独讨论 |

## 4. 详细设计

### 4.1 主机职责与命名

| 主机 ID | 中文名 | 职责 | 业务组件 | 可达性 |
| --- | --- | --- | --- | --- |
| `control` | 控制机 | 控制面与业务调度：控制台入口、管理后台、消息总线、监控，以及采集、云函数、因子管理、策略、归档管理 | console-proxy、web-host、admin、eventbus、monitor、collector、cloudfunction、factor-mgr、strategy、archive-mgr | 直达，不能是只能出站 |
| `storage` | 存储机 | 数据面；国内 SCF 写入入口 | storage-primary、storage-node、storage-view、access | 直达 |
| `overseas` | 海外机 | 海外 IP 出口：交易、WS 行情、香港 SCF 写入入口 | trade、collector-stream、egress-proxy、access | 直达 |
| `factor` | 因子机 | 离线计算：因子计算、数据归档导出；可以在内网，必须是 Linux | factor-engine、archive-worker | 只能出站 |

- 每台主机都有 host-gateway、host-agent，由代码补齐，不写在 `[placements]` 里。
- 中文名由角色固定（`moox-cli config migrate` 已经会补 `label`）。新增角色要先改本表与[部署与运维](../部署与运维.md)第 1 节。
- 主机 ID 写进了网关证书、身份包、部署目录、守护 crontab 和告警规则，改 ID 等于重新登记（现有的 `config migrate --rename-host` 加 `remove-host` 流程）。

### 4.2 服务目录：外部程序组件

`packages/servicecatalog/catalog.yaml` 新增两个组件（字段名实现时定）：

```yaml
- id: factor-engine
  name: 因子引擎
  binary: moox-factor-engine
  scope: any
  replicas: single
  protected: false
  external_program: true        # 外部程序组件：以同名外部身份经 Access 访问系统
  health:
    kind: readyz
    port: 11417
    ready_body: '"ready":true'  # 实现时按引擎 /readyz 的实际响应确定
  doctor:
    role: factor-engine
    transport: health_only
    supervisor: systemd_user    # 进程由 systemd 用户服务托管，不归 moox-runtime 看护
    unit: moox-factor-engine
- id: archive-worker            # 同上，health.port 11418，unit moox-archive-worker
```

**校验**（`validate.go`）。外部程序组件必须满足：
- 有同名的外部身份；
- 不声明 `services`、`ports`；
- 不出现在任何服务 `acl.callers` 里，权限仍只声明在 `principals[].allow`。

只有外部程序组件允许和外部身份同名；普通组件的规则不变。

测试覆盖：
- 校验拒绝：外部程序组件出现在内部 ACL 里、缺少同名外部身份、声明了 services 时都拒绝；
- 路由：调用方里只出现 access；
- 内部验签密钥集合里不含外部身份（`keys/store.go`），快照生成不受影响。

**健康**（D6）：
- Monitor 不需要改探测逻辑：放置在只能出站主机上的 `readyz` 组件，会自动经中转探测 `127.0.0.1:<端口>`，中转许可自动放行该健康端口（`routes.go` 从启用的放置收集 `Health.Port`）。
  不要设置 `health.loopback: true`：这个字段会把探测指向 Monitor 本机。
- **中转许可放行 CLI**：健康端口的许可调用方现在固定只有 `monitor`（`routes.go` 生成许可、`ValidRelay` 校验）。
  CLI 部署、启用和诊断都要经中转等待 `/readyz`，所以只能出站主机上的健康端口许可改为 `monitor` 与 `moox-cli`。许可生成、校验和网关快照测试同步修改；CLI 不借用 Monitor 身份。
- 两个程序的健康签名改用系统健康密钥：`deploy-unit` 从原始 core state 的 `runtimeIdentity`（`unitdeploy/host.go` 强制读取）取 `HealthAccessKey`、`HealthSecret`，
  渲染成 `secrets/health-auth.env`，和其他单元同源（`unitdeploy/unit.go` 的 `unitEnvironment`，Monitor 也从这组变量读取 `HealthAuthConfig`）。安装脚本不再自己生成密钥。
- 引擎 `/readyz` 返回 `healthz.Response{Ready: …}`，`ready_body: '"ready":true'` 可以直接使用。
- “因子引擎在线状态”“归档 worker 在线状态”两项业务检查保持原语义，继续用于告警。
- **引擎的健康端口只留健康接口**：11417 现在挂着三组业务路由（`engine/runtime.go` 的 `factorhealth.Register`）：
  - 导入服务的本地写入（`/v1/series/...`）；
  - 生命周期命令（命令、追赶、重置）；
  - 回放（open / step / close）。

  中转许可打开 11417 后，这些接口都会被经中转的连接触达。所以把全部非健康接口移到一个单独的回环“控制端口”（实现时分配，不进服务目录、不进中转许可），11417 只保留 `/healthz`、`/readyz`、`/metrics`。改动范围：
  - 监听注册与 `config/trpc_go.engine.yaml`；
  - 使用默认地址的四个入口：CLI 导入（`cli/internal/command/import.go`）、独立 importer（`importer/cmd/importer/main.go`）、生命周期命令（`cli/internal/command/lifecycle.go`）、回放命令（`packages/seriesreplay/command/command.go`）；
  - 共享客户端（`packages/seriesimport/engineclient`、`target/factor.go`），以及帮助文案和文档。

  测试：11417 上不提供任何业务路径；新端口的业务正常，且不进中转许可；`moox-factor-engine health` 仍用 11417。

**Doctor 契约**：
- **解析链**：YAML 由 `servicecatalog.Doctor` 接收，并开启了 `KnownFields(true)`（`catalog.go`）；`packages/doctor` 先调这个解析器再投影字段（`manifest.go`）。
  所以 `supervisor`（默认 `moox_runtime`，可选 `systemd_user`）和 `unit` 要同时加在源类型和投影上，并补默认值与组合校验：
  `systemd_user` 必须带 `unit`，`moox_runtime` 不能带 `unit`。transport 枚举不变，Monitor 只随公共包更新并验证清单加载，不新增分支。
- **CLI 诊断**（`modules/cli/internal/doctor`）在操作端运行，对 `systemd_user` 组件经 SSH 在目标主机上检查（操作者要在内网）：
  - 自启动：分别检查 `systemctl --user is-enabled <unit>`、`is-active <unit>` 和 linger，三项都满足才通过；“active 但 disabled”判为失败；
  - 路径：按目标主机上的安装目录（`~/moox/<程序>`）检查；
  - 健康：经中转拨号，用 `moox-cli` 身份。
- 测试：新目录下其他主机的诊断不受影响；自启动三项检查分别给出反例。

**安装**：
- 沿用 systemd 用户服务，不纳入 `moox-runtime` 看护（与主机守护计划 4.6 一致）。
- `setup deploy-unit --host factor --component factor-engine|archive-worker` 经 SSH 把二进制、配置和密钥传到目标主机，执行安装脚本；之后核对 linger 已开启，并经中转等待 `/readyz` 通过。
- 安装脚本只保留 Linux 分支，接受 CLI 传入的健康密钥文件，不再在操作者本机直接运行。
- **进入 release 制品**：现在的 release 与单元安装包按固定清单打包（`unitdeploy/release.go`、`unitpackage/package.go`），不会因为目录新增组件就自动包含这两个程序。
  所以要在清单里加入两个外部程序：二进制、安装脚本、systemd 模板和配置模板，并写进 manifest，带摘要和 CPU 架构校验。
  `deploy-unit --release <ID>` 只从指定 release 取制品，回退时指定旧 release 重装。

### 4.3 配置、CLI 与配置向导

- `moox.toml`：

  ```toml
  [hosts.factor]
  label = "因子机"
  address = "192.168.0.103"     # 只用作身份与证书 SAN，不要求可达
  reachability = "outbound"
  ssh = { port = 22, username = "mooyang" }   # 只供 CLI 在内网部署使用

  [placements]
  factor = ["factor-engine", "archive-worker"]
  ```

  删除 `[factor_engine]`（包括 `local` 取值），引擎所在主机由放置推导；删除 `Manifest.Hosts` 里的因子机特例，每台 `[hosts.*]` 都是部署主机。
- **配置向导**（`internal/configinit`）同步修改：
  - 涉及 request、render、editor、页面、角色说明和操作系统探测（`probe.go`）；
  - 生成 `[hosts.factor]`（只能出站）和两个放置；
  - 删除 local 模式，操作系统探测只接受 Linux。
- **启停命令**（D8；先预览，加 `--yes` 才执行；都是幂等的，失败后重复执行即可）：
  - `setup placement disable --host <ID> --component <组件>`：对外部程序先经 SSH `systemctl --user stop` 加 `disable`，核对已停止后再改登记状态。
    停止失败就不改登记状态，并报告原因；进程已停止但登记写入失败时，报告“进程已停止、登记未更新”。
  - `setup placement enable …`：所属主机是停用状态时拒绝执行，提示先启用主机。
    外部程序先改登记状态，再 `enable` 加 `start`，并经中转等到 `/readyz` 通过；启动失败时报告“已登记启用但进程未就绪”。
  - `setup host disable --host <ID>`：
    - 先逐个停止该主机上所有放置为启用的外部程序，逐个程序返回结果；
    - 全部停止成功后才把主机改为停用（撤销路由与探测，和现在的语义相同）；有程序停止失败时，主机保持启用，并列出失败的程序；
    - 放置状态不动，保留“哪些程序本来是启用的”。
  - `setup host enable --host <ID>`：先把主机改为启用，再只启动放置为启用的外部程序（之前单独停用的保持停用），逐个程序返回结果。
  - 普通组件仍只改登记状态。它们没有路由就无法被调用，进程仍由部署工具管理。
- **SSH 记录**：
  - `setup init`、`deploy-host`、`sync-placements` 为直达主机写入或更新 SSH 记录（按 `c_host_id` 关联），只能出站的主机跳过；
  - **初始化一致性**：CLI 发给 Admin 的 `ApplySetup` 与 `GetSetupStatus` 请求现在都带全部 `OtherHosts()`（`setup/client/client.go`），服务端逐个检查 SSH 记录，缺了就报未完成（`setup/impl.go`）。
    改为两个请求只带直达主机，写入、检查与计数用同一个集合（`SetupHost` 协议不用增加可达性字段）。补端到端用例：初始化配置里已经包含只能出站的 factor；
  - 删除由 Admin 在删除部署主机的事务里完成（4.4），CLI 不再单独删除。
  - 认证方式衔接[秘密管理与初始化录入设计](秘密管理与初始化录入设计.md)（SSH 只用密钥）；在那份设计实施前，沿用现在的密码加密存储。
- **其他新命令**：
  - `moox-cli storage node update|delete`，复用 `setup_storage.go` 的 Storage 代理；
  - `moox-cli archive worker retire --worker <ID>`，调用 `RetireArchiveWorker`。
- moox skill（`skills/moox/SKILL.md` 与 references）补充主机登记、启停、移除、外部程序安装与退役的流程，作为唯一的操作入口。

### 4.4 Admin

- `t_hosts` 增加 `c_label TEXT NOT NULL DEFAULT ''`。`SyncHostPlacementsReq` 与 `DeploymentHost` 增加 `label`；`c_description` 保留为补充说明。
- `t_ssh_host`：
  - 保留整数主键 `c_id`、凭据密文及其他列，会话表、指纹表的整数引用不变；
  - 增加 `c_host_id TEXT NOT NULL`，加 `UNIQUE (c_host_id)` 和 `FOREIGN KEY (c_host_id) REFERENCES t_hosts (c_host_id) ON DELETE CASCADE`；
  - 删除 `c_space_id`（主机不分空间）；
  - 终端外观列先保留，以后单独清理，不和这次迁移混在一起。
- **删除部署主机**（SysDeploy `DeleteHost`）在一个事务里依次删除：
  - 该主机 SSH 记录对应的 `t_ssh_host_key` 和 `t_ssh_session`；
  - `t_ssh_host`（外键级联兜底）；
  - `t_host_gateway_status`；
  - `t_placements`（包括自动补齐的 host-gateway、host-agent；该表的外键不级联，现有实现已经先删放置）；
  - `t_hosts`。

  事务提交后关闭这条 SSH 记录在内存里的全部终端和 SFTP 会话（`ssh/conn/session_manager.go`）。
  创建会话时在会话管理器的锁内重新确认 SSH 记录还在，避免和删除主机并发。`remove-host` 的客户端不再单独删除 SSH 记录。
- `ops.Ssh`：`CreateHost`、`UpdateHost`、`DeleteHost` 在服务目录里只放行 `moox-cli`，服务端改为按 `host_id` 写入；`ListHosts`、`GetHost`、会话与 SFTP 接口照旧对 console 开放。
- **生产库迁移**：Admin 只执行 `CREATE TABLE IF NOT EXISTS`，不自动升级，所以新增 `moox-admin-cli migrate host-registry` 子命令。
  - 前置检查：Admin 已停止（持有维护锁）；先在线备份（`VACUUM INTO`）。
  - 在一个事务里：
    - `t_hosts` 用 `ALTER TABLE ADD COLUMN c_label`，从 `c_description` 回填后清空 `c_description`；
    - `t_ssh_host` 用“建新表、复制、删旧表、改名”的方式重建，保留 `c_id`，按 `c_name` 等于主机 ID 回填 `c_host_id`；
    - 对应不上任何主机的记录不迁移，在迁移报告里逐条列出（生产预计没有）；它们的 `t_ssh_host_key`、`t_ssh_session` 行在同一事务里删除；
    - 保留 `sqlite_sequence` 里 `t_ssh_host` 的自增高水位，避免新记录复用旧 ID、让残留引用指向别的主机。
  - 提交前检查：`PRAGMA foreign_key_check`；`t_ssh_host_key`、`t_ssh_session` 对 `t_ssh_host` 的反连接孤儿检查（这两张表没有声明外键，`foreign_key_check` 查不出来）；行数核对。
  - 可以重复执行：已迁移的库直接通过。
  - 回滚：Admin 停止后恢复备份文件，再启动旧版本。

## 5. 生产迁移（每一步需确认）

0. **本地准备**：
   - 备份 `moox.toml`，用新版 CLI 转换：删除 `[factor_engine]`，加入 `[hosts.factor]` 和两个放置，补 `label`；
   - 执行解析预检（`setup validate`）。新版解析器拒绝 `[factor_engine]`，而 `release build` 要先加载配置确定状态目录，所以转换必须在构建之前做。
   - 这一步只改本地文件，远端同步仍在第 3 步。
1. **构建版本**：同一提交构建本次 release（`setup release build`），包含两个外部程序的制品（4.2）；之后所有部署命令都显式带 `--release <ID>`。
   服务目录变化要求 Admin 与 Monitor 内置的目录摘要完全一致（`monitor/internal/placement/source.go`），安装包里的目录摘要也必须与 CLI 一致（`unitpackage/inspect.go`）。
2. **整体发布**（顺序同主机守护计划阶段 7 与 native-release 流程）：
   - 停 Admin，执行 `moox-admin-cli migrate host-registry`（4.4）；
   - 依次换上新版 Admin、Monitor（两者之间 Monitor 会短暂报“目录不一致”，属预期）；
   - 再发布其余目录消费者：三台主机的 host-gateway、两台 Access，以及 Storage、Trade、Strategy、Collector、CloudFunction、factor-mgr、archive-mgr、collector-stream、host-agent；
   - 核对三台网关的快照摘要与 Admin 一致，Monitor 的部署同步恢复正常。
3. **同步现有主机**：用第 0 步转换好的 `moox.toml`，对 control、storage、overseas 执行 `sync-placements`，写入 `label`，补齐 overseas 的 SSH 记录。
4. **登记因子机**（操作者需在内网）：
   - `setup deploy-host --host factor --release <ID>` 安装 host 单元（会先确认 control 的 11003 与 EventBus 端口对公网放行），检查反向连接会话在线；这是 D17 第一次在生产使用。
   - 放置随 `deploy-host` 写入后，两个组件在安装完成前会显示异常，告警属预期，尽快执行下一步。
   - `setup deploy-unit --host factor --component factor-engine --release <ID>`，以及 `--component archive-worker`：沿用现有安装目录，换成系统健康密钥并重启服务。
     本地 K 线库与水位保留，不需要重建历史；但重启后引擎要重新载入内存窗口，这期间的实时周期会跳过、之后补算。
   - 验收：两个组件的部署健康为正常；因子“预载完成”，跳过的周期已补算；“因子引擎在线状态”“归档 worker 在线状态”都通过。
5. **发布前端**，核对主机列表、主机监控、服务部署、拓扑。
6. **文档与 skill 清理**：删除 2.4 列出的过时 `compute-1` 说明，完成 4.7 的文档部分。

## 7. 风险与回退

- **反向连接第一次上生产**：192 的出口 IP 会变，会话断开会让因子机的部署探测失败。失联判断仍以 host-agent 经 EventBus 的上报为准，并已有“主机网关反向连接”告警。
- **回退因子机登记**（操作者在内网）：
  1. 停掉 factor 上的守护与 host 单元（`setup watchdog` 移除、`stop`）。
  2. 从 `moox.toml` 删除 `[hosts.factor]` 和对应放置。
  3. `setup remove-host --host factor` 先预览，确认后加 `--yes`。
  4. 两个外部程序的 systemd 服务保留运行：它们经 Access 访问，不依赖登记。这时它们暂时处于未登记状态，只作临时过渡。
- **回退整体发布**，分两种情况：
  - **迁移事务失败**（第 2 步还没换上任何新版本）：事务回滚，库保持原样，旧版本照常运行，不需要别的操作。
  - **新版消费者已经发布**：只恢复 Admin 不够。新版 Monitor 会拒绝旧 Admin 的目录（`placement/source.go`），新版网关也会拒绝旧快照里 console 的写接口授权（`hostgateway/internal/snapshot/snapshot.go`）。所以要成套恢复：
    1. 停 Admin，恢复迁移前的数据库备份；
    2. 按 native-release 的回滚流程，把 Admin、Monitor、三台 host-gateway、两台 Access，以及第 2 步发布过的其余目录消费者切回上一个 release；
    3. 恢复本地 `moox.toml` 备份，CLI 改用旧版本；
    4. 验收：Admin 与 Monitor 的目录摘要一致，三台网关应用的快照摘要与 Admin 一致，部署探测恢复正常。
- **控制台去掉启停**：紧急停用组件需要 CLI 环境，而外部程序的启停要求在内网。可以接受，因为启停本来就需要确认影响面。
- **目录变更要求整体发布**：Admin 与 Monitor 切换期间有一小段观测中断，安排在维护窗口内。
