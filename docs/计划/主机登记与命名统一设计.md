## 1. 目标

1. 服务拓扑要能看到内网因子机，以及它上面跑的因子引擎（登记信息和部署信息都要有）。
2. 主机列表、主机监控只展示系统登记的机器，显示中文名和 IP，去掉现在的重复行和看不懂的标识。
3. 统一主机的职责与命名。
4. **机器的新增、部署、启停、移除一律通过 moox skill（`moox-cli`）完成；控制台只展示，在相应位置提示用 moox skill 操作。**
5. 精简 Admin 库：去掉重复和无人使用的表、字段与接口；代码与界面统一用“部署”一个词。

## 2. 现状核查（2026-10-24，生产只读与代码核对）

### 2.1 三套主机登记

| 登记 | 表 | 谁写入 | 用在哪 |
| --- | --- | --- | --- |
| 部署主机 | Admin `t_hosts`、`t_placements` | `moox-cli setup` 按 `moox.toml` 的 `[hosts.*]`、`[placements]` 同步（`SyncHostPlacements`） | 服务部署页、网关路由、服务拓扑 |
| SSH 主机 | Admin `t_ssh_host`（整数主键；`t_ssh_host_key`、`t_ssh_session` 用整数引用它，没有声明外键） | `setup init`（`ApplySetup` 的 `ensureHost`）只在初始化时写入当时的主机；之后只能在控制台手工增改删；`setup remove-host` 在删除部署主机之后按名字删除 | 主机列表、终端、文件管理 |
| 主机采集器 | Monitor `t_monitor_host_agents`（`c_agent_id` 唯一，`c_host_id` 不唯一） | 各主机 host-agent 上报：`c_agent_id` 是随机 4 位身份，`c_host_id` 是安装器注入的部署主机 ID | 主机监控（历史曲线按 `agent_id` 查询） |

三套之间没有外键，前端用“地址相同”或“名字唯一相同”去猜它们的对应关系。

### 2.3 页面上的“脏数据”从哪来

- `toHostMetrics` 把采集器的 `agent_id` 同时填进了 `host_id` 和 `address`（`web/src/api/modules/host-monitor.ts`），所以按地址和 SSH 记录配对永远失败。
- 按名字配对也配不上：SSH 记录叫 `control`，采集器上报的是操作系统主机名 `VM-12-13-ubuntu`。
- 结果是 3 个采集器和 2 条 SSH 记录全都“未匹配”：
  - 主机列表显示 5 行，其中 3 行的名字是 `VM-xx-ubuntu`、地址是 `pwU2` 这类 ID；
  - 主机监控显示 5 张卡，其中 2 张是“未监控”。
- 采集器其实已经上报了部署主机 ID（`HostAgentInfo.host_id`），前端没有用它来配对。

### 2.4 命名

- 命名约定已经写在[部署与运维](../部署与运维.md)第 1 节：control 控制机、storage 存储机、overseas 海外机、factor 因子机。
- 生产已经按约定改名，但仓库里还有残留：`docs/部署与运维.md` 第 46 行起、`skills/moox/references/native-release.md` 第 25 行、若干测试夹具与历史计划文档里仍写着 `compute-1`。
- 中文名借用 `t_hosts.c_description` 存储（CLI 的 `Description: host.Label`），字段语义不清。
- 同一个概念在代码里叫 placement（`t_placements`、`ComponentPlacement`、`sync-placements`），在界面上叫“部署”（“部署状态”、Monitor 的“部署探测”），每次都要换算。

### 2.5 因子机与两个外部程序

- **机器**：192.168.0.103 在家庭网络里，只能出站。上面以 systemd 用户服务运行 `moox-factor-engine` 和 `moox-archive-worker`，已开启 linger。
- **前置能力**：[主机守护与告警高可用执行计划](主机守护与告警高可用执行计划.md)里的 D10（192 按完整 host 单元登记）和 D17（反向连接）都已编码完成，但“登记 192”这一步运维操作一直没有执行。
- **身份**：两个程序都以外部身份（principal）经 Access 访问系统，不在服务目录的组件里。
  - 服务目录校验禁止组件 ID 与外部身份同名（`packages/servicecatalog/validate.go`）；
  - Admin 拒绝把外部身份放进内部验签密钥集合（`keys/store.go`）。
- **健康端口**：引擎 `127.0.0.1:11417`，worker `127.0.0.1:11418`。
  - 引擎的 11417 上还挂着导入、生命周期、回放路由，它们和健康接口一样要求健康 HMAC（`modules/factor/internal/health/server.go` 用 `healthz.WrapFromEnv` 包装整个 mux），重置还要单独的重置密钥。这和策略、Trade、采集把生命周期接口挂在健康端口上的做法一致（`moox-cli system` 就是这样调用的）。
  - 安装脚本给两个程序随机生成健康密钥，而 Monitor 用的是系统健康密钥，所以 Monitor 现在探测不了它们。
- **中转探测**：Monitor 对只能出站主机上的 `readyz` 组件，已经支持经 control 中转探测（`internal/placement/sync.go`）；中转许可也已自动包含该主机上已部署组件的健康端口，只是调用方目前固定只有 `monitor`。
- **在线状态检查**：`worker_presence:<程序>` 用于告警。管理端停止上报、或者没有任务时，它都判为通过，所以不适合当部署健康用。
- **启停**：启停接口只改数据库；Access 只核对外部身份白名单，不看部署状态。
- **SSH 可达性**：Admin 的 SSH 终端直接拨 `地址:端口`，反向连接不中转 SSH；CLI 部署同样直接 SSH，操作者必须在内网。
- **配置**：`moox.toml` 用 `[factor_engine]` 指定引擎所在机器。`Manifest.Hosts` 对因子机有特例；配置向导与 `config migrate` 也还生成或保留 `[factor_engine]`。

## 3. 设计决策

| 编号 | 决策 | 原因 |
| --- | --- | --- |
| D1 | Admin `t_hosts` 是唯一的主机登记；主机只来自 `moox.toml` 的 `[hosts.*]`，只经 `moox-cli` 写入 | 多套登记各管各的是这次问题的根源 |
| D2 | 机器新增、部署、启停、移除、外部程序退役只经 moox skill（`moox-cli`）。控制台只展示，在操作位置给出提示和对应命令；服务目录里这些写接口去掉 `console` 调用方。终端连接、文件管理属于“使用机器”，保留 | 用户要求；部署要预检、确认和记录；只删按钮不收 ACL，控制台仍能直接发请求 |
| D3 | 主机 ID 用小写英文角色名，中文名由角色决定；同角色多台时加序号（`overseas-2` / 海外机 2）。职责见 4.1 | 现有约定已经是这样，这次定为唯一规则 |
| D4 | 因子机 `factor` 登记为部署主机，可达性为只能出站，按完整 host 单元部署 | 沿用主机守护计划的 D10、D17 |
| D5 | `factor-engine`、`archive-worker` 作为“外部程序组件”进服务目录，部署在 `factor`。访问系统仍用同名外部身份经 Access，鉴权路径不变；它们不能出现在任何内部 ACL 的调用方里 | 部署记录完整；不让同名带来内部身份混用 |
| D6 | 外部程序的部署健康 = Monitor 经中转探测健康端口（`health.kind: readyz`、doctor transport `health_only`），健康签名用系统健康密钥。引擎健康端口上的业务路由不拆分 | 复用现有探测与 doctor 契约；业务路由已受健康 HMAC 保护，与其他模块一致 |
| D7 | 部署表示**期望部署**。部署写入后组件还没装好时，页面按探测结果显示，不另设“未安装”状态 | 与 `deploy-host` 先同步部署、再安装的流程一致 |
| D8 | 区分登记状态与进程启停：启停命令改登记状态；对外部程序，CLI 还要经 SSH 操作它的 systemd 服务并核对结果；部署和升级也遵守停用状态 | 外部程序不经网关路由，只改登记状态停不住它 |
| D9 | `t_hosts` 增加 `c_label`（中文名），`c_description` 只放补充说明 | 中文名是展示主键 |
| D10 | **SSH 并入主机登记**：端口、用户名、主机指纹成为 `t_hosts` 的列，密码或私钥存进 `t_secrets`（`ssh` 分类，ID 为 `ssh-host-<主机ID>`）；删除 `t_ssh_host`、`t_ssh_host_key`；终端字体、颜色等个人偏好改存在浏览器本地。SSH 信息只经 CLI 的部署同步写入；只能出站的主机没有 SSH，控制台置灰 | SSH 已经和登记主机一一对应，单独成表只会带来外键、级联、孤儿和锁的问题 |
| D11 | 主机监控按采集器上报的 `host_id` 关联登记主机，只展示登记主机；同一主机有多个采集器时取最近上报的一个 | 去掉按地址、名字猜测配对 |
| D12 | 因子引擎和 archive-worker 暂时只支持 Linux，只运行在登记的主机上；删除 `[factor_engine]` 配置、两程序的 macOS launchd 与 Windows 安装及服务代码；共享包的 Windows 实现保留 | 用户决定 |
| D13 | 存储节点的编辑、删除改为只读，CLI 新增 `moox-cli storage node update` 与 `moox-cli storage node delete` | 数据节点属于部署拓扑 |
| D14 | SCF 云函数与代码包管理不在本次范围内 | 属于采集业务配置，以后单独讨论 |
| D15 | **“placement”全链路改名为“部署（deployment）”**：`t_placements` → `t_deployments`，协议、服务目录、网关、Monitor、CLI、`moox.toml`、前端统一改名（4.8）。Storage、Trade 里同名但含义不同的词（视图放置、下单）不改 | 代码和界面用同一个词；这次本来就要改表结构、协议并整体发布，项目不要求兼容旧名字 |
| D16 | `t_ssh_session`、`t_login_history` 并入 `t_activity_logs`，类别为 `ssh.session`、`auth.login`，这两个类别保留 90 天，其余类别仍永久保存 | 两张表只写不读，本身就是事件记录 |
| D17 | 删除无用的表、字段和接口：`t_space_members` 与 `ListSpaceMembers`；`t_users` 的昵称、邮箱、头像与 `UpdateUserInfo`；`t_secrets` 的 `c_last_used_at` / `c_last_used_by`、`UpdateLastUsed` 及查询用不到的索引 | 没有写入方或调用方 |
| D18 | 初始化（`ApplySetup` / `GetSetupStatus`）不再处理主机：SSH 信息统一由部署同步（`SyncHostDeployments`）写入 | 主机已由部署流程登记；顺带消除“初始化要求每台主机都有 SSH 记录”的问题 |

## 4. 详细设计

### 4.1 主机职责与命名

| 主机 ID | 中文名 | 职责 | 业务组件 | 可达性 |
| --- | --- | --- | --- | --- |
| `control` | 控制机 | 控制面与业务调度：控制台入口、管理后台、消息总线、监控，以及采集、云函数、因子管理、策略、归档管理 | console-proxy、web-host、admin、eventbus、monitor、collector、cloudfunction、factor-mgr、strategy、archive-mgr | 直达，不能是只能出站 |
| `storage` | 存储机 | 数据面；国内 SCF 写入入口 | storage-primary、storage-node、storage-view、access | 直达 |
| `overseas` | 海外机 | 海外 IP 出口：交易、WS 行情、香港 SCF 写入入口 | trade、collector-stream、egress-proxy、access | 直达 |
| `factor` | 因子机 | 离线计算：因子计算、数据归档导出；可以在内网，必须是 Linux | factor-engine、archive-worker | 只能出站 |

- 每台主机都有 host-gateway、host-agent，由代码补齐，不写在 `[deployments]` 里。
- 中文名由角色固定（`moox-cli config migrate` 已经会补 `label`）。新增角色要先改本表与[部署与运维](../部署与运维.md)第 1 节。
- 主机 ID 写进了网关证书、身份包、部署目录、守护 crontab 和告警规则，改 ID 等于重新登记（现有的 `config migrate --rename-host` 加 `remove-host` 流程）。

### 4.2 服务目录：外部程序组件

`packages/servicecatalog/catalog.yaml` 新增两个组件（字段名实现时定）：

```yaml
- id: factor-engine
  name: 因子引擎
  binary: moox-factor-engine
  scope: any
  replicas: single
  protected: false
  external_program: true        # 外部程序组件：以同名外部身份经 Access 访问系统
  health:
    kind: readyz
    port: 11417
    ready_body: '"ready":true'
  doctor:
    role: factor-engine
    transport: health_only
    supervisor: systemd_user    # 进程由 systemd 用户服务托管，不归 moox-runtime 看护
    unit: moox-factor-engine
- id: archive-worker            # 同上，health.port 11418，unit moox-archive-worker
```

**校验**（`validate.go`）。外部程序组件必须满足：
- 有同名的外部身份；
- 不声明 `services`、`ports`；
- 不出现在任何服务的 `acl.callers` 里，权限仍只声明在 `principals[].allow`。

只有外部程序组件允许和外部身份同名。测试覆盖校验拒绝、路由（调用方里只出现 access）、内部验签密钥集合不含外部身份。

**健康**（D6）：
- Monitor 不改探测逻辑：只能出站主机上的 `readyz` 组件，自动经中转探测 `127.0.0.1:<端口>`。不设 `health.loopback: true`，否则探测会指向 Monitor 本机。
- **中转许可放行 CLI**：只能出站主机上启用部署的健康端口，许可调用方由固定的 `monitor` 改为 `monitor` 与 `moox-cli`（`routes.go` 的许可生成与 `ValidRelay`），网关快照测试同步；CLI 不借用 Monitor 身份。
- **健康签名**：`deploy-unit` 从原始 core state 的 `runtimeIdentity`（`unitdeploy/host.go`）取 `HealthAccessKey`、`HealthSecret`，渲染成 `secrets/health-auth.env`，与其他单元同源（`unitdeploy/unit.go`，Monitor 的 `HealthAuthConfig` 也读这组变量）。安装脚本不再自己生成。
- **业务路由**：11417 上的导入、生命周期、回放路由保持不动（2.5）。持有系统健康密钥的运维入口（CLI 的 `system`、`import` 等）可以经中转操作引擎，与其他模块一致。
- “因子引擎在线状态”“归档 worker 在线状态”两项业务检查保持原语义，继续用于告警。

**Doctor 契约**：
- **解析链**：YAML 由 `servicecatalog.Doctor` 接收，开启了 `KnownFields(true)`（`catalog.go`）；`packages/doctor` 先调这个解析器再投影（`manifest.go`）。
  `supervisor`（默认 `moox_runtime`，可选 `systemd_user`）和 `unit` 要同时加在源类型和投影上：`systemd_user` 必须带 `unit`，`moox_runtime` 不能带。transport 枚举不变，Monitor 只随公共包更新。
- **CLI 诊断**在操作端运行，对 `systemd_user` 组件经 SSH 在目标主机上检查（操作者要在内网）：
  - 自启动：分别检查 `is-enabled`、`is-active` 和 linger，三项都满足才通过，“active 但 disabled”判为失败；
  - 路径：按目标主机上的安装目录（`~/moox/<程序>`）检查；
  - 健康：经中转拨号，用 `moox-cli` 身份。

**安装**：
- 沿用 systemd 用户服务，不纳入 `moox-runtime` 看护（与主机守护计划 4.6 一致）。
- `setup deploy-unit --host factor --component factor-engine|archive-worker`：经 SSH 把二进制、配置和密钥传到目标主机，执行安装脚本；核对 linger，经中转等待 `/readyz` 通过。安装脚本只保留 Linux 分支，接受 CLI 传入的健康密钥文件。
- **遵守停用状态**：主机或该部署是停用状态时，安装脚本带 `--no-start`（已有参数）运行并 `systemctl --user disable`，跳过就绪等待，输出“已安装、保持停用”。
- **进入 release 制品**：release 与安装包按固定清单打包（`unitdeploy/release.go`、`unitpackage/package.go`），清单要加入两个程序的二进制、安装脚本、systemd 模板和配置模板，写进 manifest，带摘要和 CPU 架构校验。`deploy-unit --release <ID>` 只从指定 release 取制品。
- **跨目录的回退要用匹配的 CLI**：安装包的目录摘要必须等于当前 CLI（`unitpackage/inspect.go`），这条校验保留。本次是两个程序第一次进入 release，首次迁移的回退靠第 5 节第 4 步的现状备份。

  - `setup host disable --host <ID>`：逐个对启用部署的外部程序执行 `stop` 加 `disable`，逐个返回结果；全部成功后才把主机改为停用，否则主机保持启用并列出失败的程序。部署状态不动。
  - `setup host enable --host <ID>`：先启用主机，再只对启用部署的外部程序执行 `enable` 加 `start`。
  - 普通组件仍只改登记状态。
- **其他新命令**：`moox-cli storage node update|delete`（复用 `setup_storage.go` 的 Storage 代理）；`moox-cli archive worker retire --worker <ID>`。
- moox skill（`skills/moox/SKILL.md` 与 references）补充主机登记、启停、移除、外部程序安装与退役、Admin 迁移的流程，作为唯一的操作入口。

**删除部署主机**（SysDeploy `DeleteHost`）在一个事务里依次删除：
1. `t_secrets` 的 `ssh-host-<主机ID>`；
2. `t_host_gateway_status`；
3. `t_deployments`（包括自动补齐的 host-gateway、host-agent；外键不级联）；
4. `t_hosts`。

事务提交后关闭该主机在内存里的全部终端和 SFTP 会话（`ssh/conn/session_manager.go`）。
**串行**：创建会话时在按主机的锁内确认主机仍有 SSH 信息、注册会话；`DeleteHost` 持同一把锁完成删除并关闭会话。
指纹写回是 `UPDATE t_hosts`，主机被删除后影响 0 行；会话日志进入活动日志，不引用主机表，所以库里不会留下孤儿。`remove-host` 的客户端不再单独清理 SSH。

**生产库迁移**：新增 `moox-admin-cli migrate host-registry`（Admin 只执行 `CREATE TABLE IF NOT EXISTS`，不自动升级）。
- 前置：Admin 已停止（持有维护锁）；先在线备份（`VACUUM INTO`）。
- 在一个事务里：
  1. `t_hosts`：`ADD COLUMN` 新增四列；从 `c_description` 回填 `c_label` 后清空 `c_description`。
  2. `t_placements` 改名为 `t_deployments`，重建对应的索引与触发器。
  3. SSH：`t_ssh_host` 中 `c_name` 等于主机 ID 的记录，端口、用户写入 `t_hosts`；密文原样写入 `t_secrets` 的 `ssh-host-<主机ID>`（两者同一把主密钥）。`t_ssh_host_key` 的指纹写入 `c_ssh_fingerprint`。对应不上主机的记录不迁移，在报告里列出（生产预计没有）。
  4. `t_login_history` 逐行转成活动日志 `auth.login`（生产 52 行）；`t_ssh_session` 同理转成 `ssh.session`（生产 0 行）。
  5. 删除 `t_ssh_host`、`t_ssh_host_key`、`t_ssh_session`、`t_login_history`、`t_space_members`。
  6. `t_users`、`t_secrets` 删除列和多余索引（`ALTER TABLE DROP COLUMN`，先删依赖的索引）。
- 提交前检查：`PRAGMA foreign_key_check`、`PRAGMA integrity_check`、各表行数核对（主机 3、部署 24、SSH 密钥 2、活动日志增加 52）。

## 5. 生产迁移（每一步需确认）

0. **本地准备**：
   - 用新版 CLI 执行 `config migrate`（先预览、再加 `--yes`；会先备份加密配置）：`[placements]` 改为 `[deployments]`，`[factor_engine]` 转成 `[hosts.factor]` 和两个部署，补 `label`；转换后的严格解析就是本地预检。
   - 新版解析器拒绝旧配置，而 `release build` 要先加载配置确定状态目录，所以转换必须在构建之前做。
   - 不在这一步执行 `setup validate`（它会 SSH 全部主机，包括 factor），改到第 4 步在内网执行。
1. **构建版本**：同一提交构建本次 release（`setup release build`），包含两个外部程序的制品；之后所有部署命令都显式带 `--release <ID>`。
   Admin 与 Monitor 内置的目录摘要必须完全一致（`monitor/internal/placement/source.go`），安装包里的目录摘要也必须与 CLI 一致（`unitpackage/inspect.go`）。
2. **整体发布**（顺序同主机守护计划阶段 7 与 native-release 流程）：
   - 停 Admin，执行 `moox-admin-cli migrate host-registry`（4.4）；
   - 依次换上新版 Admin、Monitor（两者之间 Monitor 会短暂报“目录不一致”；Monitor 换新后按新 ID 重建部署检查，旧检查与其活动告警被清理，属预期）；
   - 再发布其余目录消费者：三台主机的 host-gateway、两台 Access，以及 Storage、Trade、Strategy、Collector、CloudFunction、factor-mgr、archive-mgr、collector-stream、host-agent；
   - 核对三台网关的快照摘要与 Admin 一致，Monitor 的部署同步恢复正常；删除 Monitor 里旧 `placement:` 前缀的序列。
3. **同步现有主机**：对 control、storage、overseas 执行 `sync-deployments`，写入 `label` 与 SSH 信息；overseas 由此第一次有了 SSH。
4. **登记因子机**（操作者需在内网）：
   - 先执行 `setup validate`，确认包括 factor 在内的全部主机 SSH 可达。
   - **备份两个外部程序的现状**：在 192 上打包 `~/moox/factor-engine`、`~/moox/archive-worker` 的 `bin/`、`config/`、`secrets/`（含旧的 `health-auth.env`），以及 `~/.config/systemd/user/` 下的两个 unit 文件。数据目录不动，也不打包。
   - `setup deploy-host --host factor --release <ID>`：安装 host 单元（会先确认 control 的 11003 与 EventBus 端口对公网放行），检查反向连接会话在线（D17 第一次在生产使用）。部署随之写入，两个组件在安装完成前显示异常，属预期。

## 7. 风险与回退

- **反向连接第一次上生产**：192 的出口 IP 会变，会话断开会让因子机的部署探测失败。失联判断仍以 host-agent 经 EventBus 的上报为准，并已有“主机网关反向连接”告警。
- **Monitor 检查 ID 改名**：旧检查连同活动告警被清理，新检查从“未知”开始；切换期间这些组件短暂没有告警覆盖，安排在维护窗口内。
- **回退因子机登记**（操作者在内网）：
  1. 停掉 factor 上的守护与 host 单元（`setup watchdog` 移除、`stop`）。
  2. 从 `moox.toml` 删除 `[hosts.factor]` 和对应部署。
  3. `setup remove-host --host factor` 先预览，确认后加 `--yes`。
  4. 两个外部程序的 systemd 服务保留运行：它们经 Access 访问，不依赖登记，只作临时过渡。
- **回退整体发布**：按实际完成到第几步，逆序恢复。
  - **迁移事务失败**（第 2 步刚停 Admin，库已回滚）：启动旧 Admin、退出维护状态。如果放弃本次窗口，恢复第 0 步备份的 `moox.toml`，CLI 改回旧版本。
  - **迁移已提交，消费者还没替换**：旧 Admin 读不了新表结构，停 Admin，恢复迁移前的数据库备份，启动旧 Admin，再处理本地配置和 CLI（同上）。
  - **新版消费者已经发布**：只恢复 Admin 不够，新版 Monitor 会拒绝旧 Admin 的目录（`placement/source.go`），新版网关也会拒绝旧快照的授权（`hostgateway/internal/snapshot/snapshot.go`）。按以下顺序逆序恢复，跳过还没执行的步骤：
    1. 第 5 步已完成：web-host 切回上一个 release。
    2. 第 4 步已完成：先按上面“回退因子机登记”撤销 factor；再用第 4 步的备份恢复两个外部程序（停服务，还原 `bin/`、`config/`、`secrets/` 和 unit 文件，`daemon-reload` 后启动），它们回到旧的随机健康密钥。
    3. 第 3 步写入的内容都在 Admin 库里，随下一项的数据库恢复一起回到原样。
    4. 第 2 步：停 Admin，恢复迁移前的数据库备份；按 native-release 的回滚流程，把 Admin、Monitor、三台 host-gateway、两台 Access 和其余目录消费者切回上一个 release。Monitor 会按旧的 `placement:` ID 重建检查。
    5. 第 0 步：恢复本地 `moox.toml` 备份，CLI 改用旧版本（跨目录的回退必须用匹配的 CLI）。
    6. 验收：Admin 与 Monitor 的目录摘要一致；三台网关应用的快照摘要与 Admin 一致；部署探测恢复正常；两项在线状态检查通过。
- **控制台去掉启停与 SSH 编辑**：紧急停用组件、修改 SSH 信息都需要 CLI 环境，外部程序的启停还要求在内网。可以接受。
