# 主机登记与命名统一设计

设计稿 v2（2026-10-24，决策已确认，尚未编码）。实现后以[部署与运维](../部署与运维.md)、[管理后台](../模块/管理后台.md)、[监控](../模块/监控.md)、[前端](../模块/前端.md)为准。

v2 变更：第 8 节待确认事项全部定下。因子引擎和 archive-worker 暂时只支持 Linux，并且都登记到 `factor`；
存储节点的编辑、删除改为只读，移到 CLI；SCF 云函数不在本次范围内。第 6 节补全各阶段的改动位置。

## 1. 目标

1. 服务拓扑要能看到内网因子机，以及它上面跑的因子引擎（登记信息和部署信息都要有）。
2. 主机列表、主机监控只展示系统登记的机器，显示中文名和 IP，去掉现在的重复行和看不懂的标识。
3. 统一主机的职责与命名。
4. **机器的新增、部署、启停、移除一律通过 moox skill（`moox-cli`）完成；控制台只展示，在相应位置提示用 moox skill 操作。**

已拍板的方向：因子机登记为部署主机、`factor-engine` 进服务目录；海外机主机 ID 用 `overseas`；SSH 与主机监控都只认登记的主机。

## 2. 现状核查（2026-10-24，生产只读）

### 2.1 三套主机登记

| 登记 | 表 | 谁写入 | 用在哪 |
| --- | --- | --- | --- |
| 部署主机 | Admin `t_hosts`、`t_placements` | `moox-cli setup` 按 `moox.toml` 的 `[hosts.*]`、`[placements]` 同步（`SyncHostPlacements`） | 服务部署页、网关路由、服务拓扑 |
| SSH 主机 | Admin `t_ssh_host` | `setup init`（`ApplySetup` 的 `ensureHost`，`c_creator = setup`）只在初始化时写入当时的主机；之后只能在控制台手工增改删；`setup remove-host` 删除同名记录 | 主机列表、终端、文件管理 |
| 主机采集器 | Monitor `t_monitor_host_agents` | 各主机 host-agent 上报，`c_agent_id` 是随机 4 位身份，`c_host_id` 是安装器注入的部署主机 ID | 主机监控 |

三套之间没有外键。前端用“地址相同”或“名字唯一相同”去猜它们的对应关系。

### 2.3 页面上的“脏数据”从哪来

- `toHostMetrics` 把采集器的 `agent_id` 填进了 `address`（`web/src/api/modules/host-monitor.ts`）。于是按地址和 SSH 记录配对时永远失败。

- 结果是 3 个采集器全部“未匹配”，2 条 SSH 记录也“未匹配”：
  - 主机列表显示 5 行（`mergeHostWorkbenchRows` 加 `monitorOnlyHosts`），其中 3 行的名字是 `VM-xx-ubuntu`、地址是 `pwU2` 这类 ID；
  - 主机监控显示 5 张卡，其中 2 张是“未监控”。
- 采集器其实已经上报了部署主机 ID（`HostAgentInfo.host_id`），前端只在定位链接时用到它（`deployment_host_id`），没有用来配对。

### 2.4 命名

- 命名约定已经写在[部署与运维](../部署与运维.md)第 1 节：control 控制机、storage 存储机、overseas 海外机、factor 因子机。
- 生产已经按约定改名，但仓库里还有残留：
  - `docs/部署与运维.md` 第 46 行起仍写着“生产海外机的主机 ID 目前仍是 `compute-1`”，并附了改名步骤；
  - `skills/moox/references/native-release.md` 第 25 行同样过时；
  - 若干测试夹具和历史计划文档里还有 `compute-1`。
- 中文名借用 `t_hosts.c_description` 存储（CLI 的 `Description: host.Label`），字段语义不清。

### 2.5 因子机

- 192.168.0.103 在家庭网络里，只能出站。上面以 systemd 用户服务运行 `moox-factor-engine` 和 `moox-archive-worker`。
- 两项前置能力在[主机守护与告警高可用执行计划](主机守护与告警高可用执行计划.md)里都已编码完成：
  - D10：192 按完整 host 单元部署并登记为主机；
  - D17：只能出站的主机经 control 网关反向连接中转。

  但“登记 192”这一步运维操作一直没有执行，生产的 `t_hosts` 里没有它。
- 因子引擎以外部身份 `factor-engine`（principal）经 Access 访问 Storage 和 FactorMgr，不在服务目录的组件里。
  服务目录校验禁止组件 ID 与外部身份同名（`packages/servicecatalog/validate.go`），所以不能直接加一个同名组件。
- 引擎自己不上报指标。在线状态由 factor-mgr 按心跳评估，Monitor 据此生成业务检查 `worker_presence:factor-engine`（因子引擎在线状态）。
- `moox.toml` 用 `[factor_engine] host = "<主机>|local"` 指定引擎所在机器。按现在的规则，这台机器没有放置组件时不算部署主机（`Manifest.Hosts`）。

## 3. 设计决策

| 编号 | 决策 | 原因 |
| --- | --- | --- |
| D1 | Admin `t_hosts` 是唯一的主机登记；主机只来自 `moox.toml` 的 `[hosts.*]`，只经 `moox-cli` 写入 | 三套登记各管各的是这次问题的根源 |
| D2 | 机器新增、部署、启停、移除只经 moox skill（`moox-cli`）。控制台只展示，在操作位置给出提示和对应命令。终端连接、文件管理属于“使用机器”，保留 | 用户要求；部署是有状态、需要预检与回退的过程，放在 skill 里能统一走预检、确认和记录 |
| D3 | 主机 ID 用小写英文角色名，中文名由角色决定；同角色多台时加序号（`overseas-2` / 海外机 2）。职责见 4.1 | 现有约定已经是这样，这次把它定为唯一规则，并补上职责 |
| D4 | 因子机 `factor` 登记为部署主机，可达性为只能出站，按完整 host 单元部署（host-gateway、host-agent、守护） | 沿用主机守护计划的 D10、D17，代码已经就绪 |
| D5 | `factor-engine` 进服务目录，作为“外部程序组件”放置在 `factor` 上；它访问系统仍用外部身份 `factor-engine` 经 Access，鉴权路径不变 | 部署记录完整，拓扑、部署页、监控都能按放置展示；不改引擎的调用链路 |
| D6 | `t_hosts` 增加 `c_label`（中文名），`c_description` 只放补充说明 | 中文名是展示主键，不该借用说明字段 |
| D7 | SSH 连接信息和登记主机一一对应：`t_ssh_host` 增加 `c_host_id`（唯一），由 CLI 写入、更新、删除；`ops.Ssh` 的增改删接口只允许 `moox-cli` 调用 | 主机列表只能是登记的主机；修复后加入的主机没有 SSH 记录的问题 |
| D8 | 主机监控按采集器上报的 `host_id` 关联登记主机；只展示登记主机，未登记的采集器只显示数量提示 | 去掉按地址、名字猜测配对 |
| D9 | 服务部署页去掉启停按钮；CLI 新增主机与组件的启用、停用命令 | 落实 D2 |
| D10 | 因子引擎和 archive-worker 暂时只支持 Linux，只运行在登记的主机上（`factor`），都作为外部程序组件进服务目录。删除 `[factor_engine]` 配置、macOS launchd 与 Windows 的安装路径 | 用户决定；“只展示登记的机器”要求所有运行中的程序都落在登记主机上，没登记的运维机不再是合法的部署位置 |
| D11 | 存储节点的编辑、删除改为只读，CLI 新增 `moox-cli storage node update` 与 `moox-cli storage node delete` | 数据节点属于部署拓扑，按 D2 处理 |
| D12 | SCF 云函数与代码包管理不在本次范围内，控制台照旧可以操作 | 属于采集业务配置，以后再单独讨论 |

## 4. 详细设计

### 4.1 主机职责与命名

| 主机 ID | 中文名 | 职责 | 业务组件 | 可达性 |
| --- | --- | --- | --- | --- |
| `control` | 控制机 | 控制面与业务调度：控制台入口、管理后台、消息总线、监控，以及采集、云函数、因子管理、策略、归档管理 | console-proxy、web-host、admin、eventbus、monitor、collector、cloudfunction、factor-mgr、strategy、archive-mgr | 直达，不能是只能出站 |
| `storage` | 存储机 | 数据面；国内 SCF 写入入口 | storage-primary、storage-node、storage-view、access | 直达 |
| `overseas` | 海外机 | 海外 IP 出口：交易、WS 行情、香港 SCF 写入入口 | trade、collector-stream、egress-proxy、access | 直达 |
| `factor` | 因子机 | 离线计算：因子计算、数据归档导出；可以在内网，必须是 Linux | factor-engine、archive-worker | 只能出站 |

- 每台主机都有 host-gateway、host-agent，由代码补齐，不写在 `[placements]` 里。
- 中文名由角色固定，`moox-cli config migrate` 已经会补 `label`。新增角色要先改本表与[部署与运维](../部署与运维.md)第 1 节。
- 主机 ID 写进了网关证书、身份包、部署目录、守护 crontab 和告警规则，改 ID 等于重新登记（现有的 `config migrate --rename-host` 加 `remove-host` 流程）。

### 4.2 服务目录：外部程序组件

`packages/servicecatalog/catalog.yaml` 新增：

```yaml
- id: factor-engine
  name: 因子引擎
  binary: moox-factor-engine
  scope: any
  replicas: single
  protected: false
  external_principal: true   # 字段名实现时定
  health:
    kind: none
  doctor:
    role: factor-engine
    transport: presence      # 新增：健康取自管理端的在线状态检查
```

- **校验**（`validate.go`）：声明 `external_principal: true` 的组件，必须有同名的外部身份，且不得声明 `services`、`ports`。
  只有这种组件允许和外部身份同名。它也不会作为网关调用方编进路由（路由编译本来就只看 `services`，storage-node 已有先例）。
- **健康**：`health.kind: none` 表示 Monitor 不主动探测。只能出站的主机虽然可以经中转探测，但引擎没有健康端口对外。
  doctor 新增 transport `presence`，Monitor 把该放置的组件健康映射为 `worker_presence:factor-engine` 的结果：
  在线为正常，离线为异常，“不需要”为不探测。部署页和拓扑因此能显示因子引擎的真实状态。
- **部署方式**：沿用现在的 systemd 用户服务（不纳入 `moox-runtime` 的看护，与主机守护计划 4.6 一致）。
  `setup deploy-unit --host factor --component factor-engine` 经 SSH 在目标主机上执行安装脚本，安装成功后写入放置。
  脚本只保留 Linux 分支，不再在操作者本机上直接运行。
- **archive-worker 同批处理**：同样的组件定义（`id: archive-worker`、`binary: moox-archive-worker`、`doctor.transport: presence`），
  健康取自 `worker_presence:archive-worker`，放置在 `factor`，由 `deploy-unit --component archive-worker` 安装。
- **只支持 Linux（D10）**，删除以下内容：
  - `deploy/launchd/com.moox.factor-engine.plist.tmpl`、`deploy/launchd/com.moox.archive-worker.plist.tmpl`；
  - `scripts/deploy/deploy-factor-engine.ps1`、`scripts/deploy/deploy-archive-worker.ps1`；
  - 两个 bash 脚本里的 `Darwin` 分支；
  - 引擎与 worker 的 Windows 服务子命令（`service stop|start|uninstall`）；
  - 主机守护计划阶段 11 为 Windows 加的平台分支，Linux 上的权限检查保持不变。

  [因子](../模块/因子.md)、[归档](../模块/归档.md)的运维章节同步改写。

### 4.3 配置与 CLI

- `moox.toml`：

  ```toml
  [hosts.factor]
  label = "因子机"
  address = "192.168.0.103"     # 只用作身份与证书 SAN，不要求可达
  reachability = "outbound"
  ssh = { port = 22, username = "mooyang" }

  [placements]
  factor = ["factor-engine", "archive-worker"]
  ```

  删除 `[factor_engine]`（包括 `local` 取值）：引擎所在主机由放置推导。`Manifest.Hosts` 里“因子计算机没有放置时不算部署主机”的特例随之删除，
  每台 `[hosts.*]` 都是部署主机。
- 新增命令（都先预览，加 `--yes` 才执行，和 `remove-host` 一致）：
  - `moox-cli setup host enable|disable --host <ID>`
  - `moox-cli setup placement enable|disable --host <ID> --component <组件>`
- SSH 记录同步：`setup init`、`deploy-host`、`sync-placements` 写入或更新该主机的 SSH 记录（按 `c_host_id` 关联），`remove-host` 删除。
  认证方式衔接[秘密管理与初始化录入设计](秘密管理与初始化录入设计.md)（SSH 只用密钥）；在那份设计实施前，沿用现在的密码加密存储。
- moox skill（`skills/moox/SKILL.md` 与 references）补充主机登记、启停、移除、SSH 同步的操作流程，作为唯一的操作入口。

### 4.4 Admin

- `t_hosts`：`c_description` 改为 `c_label TEXT NOT NULL DEFAULT ''`（中文名）加 `c_description TEXT NOT NULL DEFAULT ''`（补充说明）。
  `SyncHostPlacementsReq` 与 `DeploymentHost` 增加 `label`。
- `t_ssh_host`：增加 `c_host_id TEXT NOT NULL`，加上 `UNIQUE (c_host_id)` 和指向 `t_hosts (c_host_id)` 的外键；删除 `c_space_id`（主机不分空间）。
  `c_name` 保留为终端标题，写入时取中文名。
- `ops.Ssh`：
  - `CreateHost`、`UpdateHost`、`DeleteHost` 在服务目录里只放行 `moox-cli`；
  - `ListHosts`、`GetHost`、会话与 SFTP 接口照旧对 console 开放；
  - 终端外观（字体、颜色）属于个人偏好，不再存进 SSH 记录，改存在浏览器本地。
- 生产库加列：按 Admin 现有的 schema 变更方式执行。项目不考虑兼容，但已有数据要迁移：2 条 SSH 记录按名字回填 `c_host_id`，`c_description` 回填到 `c_label`。

### 4.5 Monitor

- 新 doctor transport `presence`：把对应组件的放置健康取自 `worker_presence:<组件>` 检查。
  已有的“因子引擎在线状态”业务检查保留，作为告警来源；部署健康不再报“暂无健康观测”。
- 只能出站主机的部署探测、反向连接检查已在主机守护计划阶段 7 实现，这次不改。
- `ListHostAgents` 不变：未登记的采集器仍然返回，由页面过滤。服务端过滤会让“有采集器在上报但没登记”这件事彻底看不见。

### 4.6 控制台

统一的只读提示：

> 主机与部署由 moox skill 维护。在 Claude Code 中告诉 moox skill 要做的事，或直接运行 `moox-cli setup …`。

| 页面 | 改动 |
| --- | --- |
| 服务部署 · 服务 | 去掉启用、停用按钮，保留状态标签；页头放只读提示，组件详情抽屉给出对应的 CLI 命令 |
| 服务部署 · 服务拓扑 | `factor` 作为普通主机列出现；因子引擎、archive-worker 节点落在 factor 列，按 `presence` 健康着色；数据流向的“因子”步骤跟着落到该列；外部程序组件不再出现在外部节点里（同名外部身份按放置的组件显示） |
| 主机列表 | 行来自 `t_hosts`：中文名、主机 ID、公网 IP / 内网 IP、地域、可达性、采集器状态；操作只剩“终端”“文件管理”；去掉新增、编辑、删除和“仅监控”行；没有 SSH 记录的主机显示“未配置 SSH，请用 moox skill 同步” |
| 主机监控 | 只展示登记主机，按采集器的 `host_id` 关联；卡片标题为中文名，副标题为主机 ID 和 IP；登记了但没有上报的主机显示“未上报”；有未登记的采集器时只显示一行“有 N 个未登记的采集器”；链接参数统一为 `host_id`（去掉 `agent_id`，首页链接同步改） |
| 存储节点 | 去掉编辑、删除，只读加提示（D11） |

前端删除 `mergeHostWorkbenchRows`、`buildHostMonitorRows` 里按地址、名字猜测配对的逻辑，以及 `toHostMetrics` 把 `agent_id` 当地址的写法。

## 5. 生产迁移（每一步需确认）

1. 发布 Admin（新列、SSH 接口权限）、Monitor（`presence`）、全部服务目录消费者（新组件字段；目录消费者严格拒绝未知字段，要先全部发布）。Admin 库按 4.4 迁移。
2. `moox.toml` 按 4.3 修改。用 `sync-placements` 给 control、storage、overseas 补写 `label` 和 SSH 记录，overseas 因此得到第一条 SSH 记录。
3. 登记因子机：
   - 先确认 control 的 11003 与 EventBus 端口对公网放行（`deploy-host` 会自动确认）；
   - `setup deploy-host --host factor` 安装 host 单元，检查反向连接会话在线（这是 D17 第一次在生产使用）；
   - `setup deploy-unit --host factor --component factor-engine` 和 `--component archive-worker` 用脚本重装两个程序并写入放置。
     沿用现有安装目录（`~/moox/factor-engine` 等），引擎的本地 K 线库与水位保留，不需要重新预热；

## 7. 风险与回退

- **反向连接第一次上生产**：192 的出口 IP 会变，会话断开会让因子机的部署探测失败。失联判断仍以 host-agent 经 EventBus 的上报为准，并已有“主机网关反向连接”告警。
  回退：`setup remove-host --host factor` 撤销登记，引擎继续以 systemd 用户服务运行，访问路径（Access）不受影响。
- **控制台去掉启停**：紧急停用组件要有 CLI 环境。可以接受，因为启停本来就需要确认影响面。
- **目录字段升级**：新字段要求全部目录消费者先发布，顺序同主机守护计划阶段 7。
