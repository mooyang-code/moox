# 采集整点取数变慢：排查记录与优化点

日期：2026-10-20。起因：策略 1m 实例在整点的“产出延迟”（结果落库时间 − K 线结束时间）约 10~12 秒，非整点约 5~6 秒。
本文记录已证实的结论、尚未证实的部分和待做的优化，不是当前能力说明；采集链路的当前行为见[采集](../模块/采集.md)。

## 1. 已证实的结论

- 策略自身整点与非整点一样快（读取约 0.4 秒、求值与提交几十毫秒），处理量相同（1m 视图，约 511 个标的），小时 K 线不进策略。
- 多出来的约 5 秒在上游：现货 1m 的“周期采集完成”事件整点比平时晚约 5 秒，因子计算（约 0.8 秒）、视图刷新、策略依次被顺延。
- 采集函数（现货、合约各 21 个，地域 ap-hongkong）整点的 1m 批次：开始晚约 1 秒（Timer 触发到开始取数，整点约 2.4 秒、平时 1.2~1.6 秒），取数耗时现货约 4.9 秒（平时 0.3~1.0 秒）、合约约 2.0 秒（平时 0.3~0.9 秒）。
- 整点约一半的 1m 请求第一次尝试停住，换端点或重试后才成功（25 项里重试 13 项，HTTP 请求 51 个对 25 个）；排队、DNS、写 Storage（约 60 毫秒）与平时一致，建连与 TLS 只多几十毫秒。
- 1h 在同一函数里排在 1m 之后，几乎不重试，不拖累 1m。行情源首字节随“整点程度”上升（:01 约 57 毫秒，:05 约 480 毫秒，:30 约 650 毫秒，整点约 720 毫秒）。

数据来源：CLS 里的 `market_fetch_batch`、`market_fetch_item_slow`、`market_fetch_commit`（字段见[部署与运维](../部署与运维.md)的 CLS 一节），以及策略日志的分段耗时。

## 2. 逐次请求证据（2026-10-20 10:00 UTC 整点，失败尝试上报上线后的第一个整点）

- 现货 1m：第一个端点（`data-api.binance.vision`）的请求在 1200 毫秒处超时（阶段 `wait_response`，原因 `deadline`）的有 112 次；之后依次换 `api.binance.com`（又有 62 次在 1200 毫秒超时）、`api1`（约 600 毫秒）、`api2`（约 200 毫秒），最后一次尝试才成功，成功请求自身只要约 0.7～0.9 秒。常见序列：先超时再换下一个端点成功 50 次，两次超时后成功 29 次，三到四次超时后成功 34 次。**1200 毫秒正是 `endpointAttemptContext` 的单端点最短尝试时间 `minEndpointAttempt`**，整点行情源响应在 1 秒上下，被这个上限反复截断、重发，累计 3.7～4.9 秒。
- 合约 1m：`fapi.binance.com` 的新连接请求同样在 1200 毫秒超时，随后 `fapi1`～`fapi4` 各在约 175 毫秒返回 HTTP 202（被当作失败），最后在一条**复用的已有连接**上 59 毫秒返回 200，合计约 1.97 秒。说明整点新连接上的第一个请求久不响应，而已建立的连接响应很快。
- 失败全部是 `deadline`（等响应阶段），没有重置、拨号、TLS 错误；Storage 写入仍是 60～70 毫秒。
- 备援（`standby_ms=800`，一半函数）没有改善：现货 1m 中位 3705 毫秒对 3728 毫秒，备援触发 282 次只赢了 59 次——备援请求也受同一个 1200 毫秒上限，且备用端点同样慢。该逻辑现称“备援请求”（`standby_*`，默认关闭）并保留，随 3 秒单端点上限重新提供。

## 3. 结论与下一步

整点慢的直接原因是单端点最短尝试时间（1.2 秒）低于整点行情源的响应时间，导致“超时 → 换端点 → 再超时”的级联，而不是并发量或我们这一侧的资源。候选改法（都要先小范围对比再全量）：

1. 把首个端点的最短尝试时间加长到约 2.5 秒（预算允许时），让 1～2 秒才响应的请求在一次尝试内成功；
2. 合约：整点新连接首个请求久不响应而已有连接很快，评估在函数启动时预热并复用连接；
3. HTTP 202 目前被当作失败，需要确认它在币安合约接口上的含义后再决定是否重试同一端点；
4. 备援请求改名保留、默认关闭；单端点最短尝试时间改为 3 秒后，用新增的逐次请求明细（阶段耗时、CDN 节点、响应头、202 响应体）与函数进程指标（定时事件迟到、错峰、调度迟滞）继续定位整点延迟。

## 3.5 2026-10-20 12:00 UTC 整点（3 秒超时、新日志）

- 现货 1m：定时事件比计划晚 1.09 秒（平时 0.39 秒），函数内错峰 0.73 秒，取数 4.29 秒（平时 0.26 秒）。排队、DNS、写 Storage、调度迟滞与平时一致。
- 第一次请求发给 `api.binance.com`（对端 18.65.0.122，香港 CloudFront），TLS 与请求写出都很快（3～260 毫秒），然后一个字节都收不到，等满 3 秒超时；重发发生在**复用的连接**上，1.4～2.3 秒成功（`x-cache: Miss from cloudfront`，节点 HKG61-P1）。所有成功的重试都在复用连接上，失败的都在新建连接上。
- 3 秒的单端点上限等于整次尝试的预算，第一个端点占满后直接进入下一次尝试，仍从 `api.binance.com` 开始，没有真正换到 `api-gcp`。
- 合约同样：对 `fapi.binance.com` 的第一次请求停住，落点是快照固定的 54.230.70.114／.42，成功响应节点是 HKG1-P1。

## 3.6 2026-10-20 14:00 UTC 整点三组对比（错峰 0～0.5 秒，每组约 3 成函数）

| 组 | 现货 1m 取数中位 | 合约 1m 取数中位 | 普通分钟（14:01／14:02）现货 1m 取数 |
| --- | --- | --- | --- |
| 对照 | 3.72 秒 | 1.66 秒 | 0.27～0.33 秒 |
| 备援（1000 毫秒） | 3.72 秒（触发 55 次、获胜 21 次） | 1.08 秒（触发 11 次、获胜 11 次） | — |
| 连接复用 | 4.03 秒 | 1.91 秒 | 0.07～0.17 秒 |

- 连接复用在普通分钟里有效：新建连接几乎为 0，握手耗时（TLS）消失，批次取数从约 0.3 秒降到 0.07～0.17 秒；但整点现货 1m 完全没有改善——**复用（空闲 60 秒）的连接上第一次请求同样停住 2 秒**，说明整点停住与连接新旧无关。
- 备援对合约有效：单端点（`fapi.binance.com`）第二个请求每次都先返回（11/11），取数中位 1.66→1.08 秒；对现货无效，备援请求也落在同一段停住里。
- 整点现货 1m 的重试占比随批次开始偏移上升：开始于收盘后 0.5～1 秒约 0.10，1～1.5 秒 0.23，1.5～2 秒 0.36，2 秒以后约 0.50（10:00～14:00 五个整点合计，样本 88 个）。**开始得越早停住越少**，所以缩短错峰、减少定时事件迟到都有帮助。

## 4. 优化点清单

| 项目 | 说明 | 状态 |
| --- | --- | --- |
| 补报失败尝试的错误类型、阶段与连接是否复用 | 只对重试过的项上报，量级不变；用来确认第一次尝试为什么停住 | 已上线，结论见第 2 节 |
| 备援请求 | 超过阈值未返回就并发再发一个，先成功的为准；`scf_plan.fetch` 的 `standby_ms`／`standby_percent`／`standby_hour_only` 控制，默认关闭；线上试过无改善（当时单端点上限 1.2 秒），3 秒版后可重试 | 已保留，待再试 |
| 币安端点收敛为 3 个不同出口 | 现货 `api.binance.com`（CloudFront）、`api-gcp.binance.com`（Google Cloud）、`data-api.binance.vision`（AWS 东京直连）；合约只保留 `fapi.binance.com`（fapi1～4 是重定向通配域名）。香港实测前两者建连约 2 毫秒、首字节约 110 毫秒，data-api 约 250 毫秒，原来排第一的 data-api 反而最慢 | 随下一次函数包发布 |
| DNS 快照与香港本地解析不一致 | 快照里 `fapi.binance.com` 是 54.230.70.x，而香港主机本地解析是 18.65.14.x；整点停住的请求几乎都落在快照固定的少数 IP 上。可对比关闭币安的快照固定、改用函数所在地域的本地解析 | 待评估 |
| 单端点最短尝试时间 1.2 秒 → 2 秒 → 3 秒 → 2 秒 | `minEndpointAttempt` 先改 2 秒（10:17 UTC 上线），12:00 整点 3 秒版取数中位 4.29 秒，比 2 秒版更差（停住的请求等多久都不返回，重发在复用连接上 1.4～2.3 秒成功），所以回到 2 秒 | 2 秒版随下一次发布 |
| 跨调用复用连接 | 进程内共享 HTTP 客户端，上一分钟留下的空闲连接下一分钟直接用；`conn_reuse`／`conn_reuse_percent` 控制 | 已上线 30%：普通分钟取数 0.3→0.1 秒，整点无改善；可全量 |
| 连接预热与复用（原思路） | 每个函数每分钟启动一次，25 个请求同时发出，几乎每个请求都新建连接（`conn_new` ≈ 请求数、`conn_reused` ≈ 0），每个请求都付一次 TCP 建连（现货约 59 毫秒）与 TLS 握手（现货约 190~300 毫秒、合约约 125~320 毫秒）。可在并发取数前先用一条请求预热连接，或让同一函数的后续请求复用已建好的连接。这与整点变慢无关（整点只比平时多几十毫秒），但每个批次都能省约 0.2~0.4 秒 | 未开始 |
| Timer 触发到开始取数整点晚约 1 秒 | 触发由云厂商完成，函数内的错峰（0~1.5 秒）是确定性延迟；可评估整点是否缩小错峰窗口 | 未开始 |
