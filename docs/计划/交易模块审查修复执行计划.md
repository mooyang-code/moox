## 1. 结论

生产现在只跑模拟盘，下面的问题都没有影响到它。但交易所私有接口从来没在真实账户上跑过，有两处一上实盘就会出错：

1. 币安现货私有流的订单事件，每一条都解析失败。
2. U 本位合约 REST 补拉的成交，方向全部变成卖。

另外有五处在模拟盘上也可能碰到：

- 对一个组合清仓，会动到另一个组合。
- 停用的执行账户移不出组合。
- 现货清仓因为零头空转 30 分钟。
- 同一组合同时跑两个清仓，会互相撤对方的子单。
- 清仓锁忙时，前端看到内部错误。

现有测试用的样例都是手写或删减过的，这些问题因此没被测出来。所以这次修复的前提是：先把测试样例换成官方原文，确认测试在当前 main 上失败，再动手修。

修复分四个阶段：

| 阶段 | 内容 | 影响范围 |
| --- | --- | --- |
| A | 交易所适配：私有流解析、成交方向、OKX 推送、状态码、签名、重连退避、OKX 权益、限频细节 | 只影响实盘，实盘启用前必须完成 |

## 3. 设计要点

### 3.1 私有流按精确键取值

结构体解码一定会走大小写不敏感的回落。改成先解到 `map[string]json.RawMessage`（键按原样保留），再按精确键取值：

- 新增 `exchange/binance/fields.go`，提供 `exactFields(raw) (fields, error)` 和取值方法：
  - `str(key)`、`number(key)`、`int64(key)`（数字和字符串形式的数字都接受）、`bool(key)`、`object(key)`、`array(key)`。
  - JSON `null` 按缺键处理。官方 NEW 样例就带 `"N": null`，不这样处理又会每条都解析失败。
  - 可选键缺失时返回零值；必填键用 `required(key)` 取，缺失时报带键名的错误。必填键：现货订单事件的 `e`、`s`、`i`、`x`、`X`；合约 `o` 对象的 `s`、`i`、`x`、`X`。
  - 类型不对时，返回带键名的错误。
- 先按 `e` 分派事件类型，再取对应字段。外层不能统一把 `o`、`a` 当对象取：在 executionReport 里，`o` 是字符串 `"LIMIT"`，`a` 是数字。
- 私有流的四类负载全部改用它：外层信封、现货 executionReport、合约 ORDER_TRADE_UPDATE 的 `o`、现货 outboundAccountPosition 和合约 ACCOUNT_UPDATE。合约事件按字段集看目前没撞键（还要 A0 用原文确认），也一并改，以后加字段不会再踩坑。
- 删除 `privateOrderFields` 结构体，现货和合约分别写一个从字段构造 `orderPayload` 的函数：
  - 现货的客户端单号：只在 `x = CANCELED` 且 `C` 非空时用 `C`，其他情况一律用 `c`。撤单事件里 `c` 是撤单请求自己的单号，`C` 才是原单号；不这样处理，撤单事件会被当成外部订单导入，并暂停组合账户。改单（`x = REPLACED`）时 `c` 才是新单号，所以不能写成“`C` 非空就用 `C`”。
  - 现货 `x = TRADE_PREVENTION` 时，订单状态按 `X` 映射，见 3.4。
  - 限价取 `p`，补上 WS 订单事件丢失限价的问题；否则外部限价单导入时会报“没有价格”。创建时间取 `O`。
  - `E` 兼容数字和字符串。新版 listenKeyExpired 事件的 `E` 是字符串，现在会解析失败，导致到不了 `errListenKeyExpired` 分支。
- REST 响应都是驼峰长键，目前没有撞键，继续用结构体解码，但测试改用官方原文（A0）。

### 3.2 合约 REST 成交方向

`tradePayload` 增加三个字段：`Side`（`side`）、`Buyer`（`buyer`）、`Maker`（`maker`）。

- 永续：方向取 `side`，只接受 BUY/SELL，否则按拒绝处理；吃单还是挂单取 `maker`。
- 现货：继续用 `isBuyer`、`isMaker`。
- 不能只改 json 标签，否则现货会坏。

### 3.3 OKX 只按事件推送

`privateChannels()` 给 account 和 positions 两个频道加上 `"extraParams": "{\"updateInterval\": \"0\"}"`，按 OKX 文档要求写成 JSON 字符串。orders 频道本来就只按事件推送，不用改。

### 3.4 订单状态和错误码

- `mapOrderStatus`：`EXPIRED_IN_MATCH` 映射为 Expired，部分成交的情况由成交入账补齐，和 EXPIRED 一致。
- 币安错误码：`-1006`、`-1007` 归为结果未知，走查询恢复。

### 3.5 签名追加在末尾

- `httpclient.Request` 增加 `RawQuery string`。非空时原样使用，`Query` 被忽略。
- 币安 `signedRequest` 的做法：先算 `encoded := values.Encode()`（含 timestamp、recvWindow），再拼成 `encoded + "&signature=" + hex(hmac(encoded))`，作为 `RawQuery` 发送。这样签名串和发送串是同一份字节。
- WS API 订阅签名的规则是按键排序，保持不变。

### 3.6 重连退避复位

`runSession` 记录每次 `Run` 的开始时间。会话连续运行超过 1 分钟后才断开的，下一次等待从 `RetryMin` 重新开始；连续快速失败的，仍按翻倍退避，上限 30 秒。

### 3.7 OKX 权益取结算币

REST 的 `GetAccountSnapshot` 和私有流的 account 推送（`okx/account_events.go:356`）共用同一个函数，从 `balanceEnvelope` 构造快照。权益不再用 `totalEq`：

- 永续的 `Equity` 取结算币那一项的 `eq`。REST 快照没有结算币明细时为 0，由权益解析报“组合账户权益为 0”。
- 只改 REST 不够。推送带 `Present.Equity`，同步时会覆盖快照（`accountsync/service.go:1470`）；A3 改完以后每笔成交都会推送 account，修好的值马上就会被盖回 `totalEq`。
- 推送里的 `Present.Equity` 改成和 `AvailableFunds` 一样，只有带结算币明细时才置 true。OKX 的事件推送只带发生变化的币种，一条只含 BTC 的推送如果也置 true，就会把权益写成 0。账户权益采样不看是否就绪（`equity/service.go:129`），会记下这个 0；换手告警也读它（`attention.go:229`）。
- 现货权益本来就由受管资产估值算出，不受影响。

### 3.8 一个执行账户只属于一个组合（B1）

- 表约束：把部分唯一索引 `ux_enabled_physical_account_membership`（`WHERE c_enabled = 1`）换成全量唯一索引 `ux_logical_account_members_trading_account ON t_logical_account_members (c_space_id, c_trading_account_id)`，同时删掉已经多余的 `idx_logical_account_members_account`。
- 归属检查：`AddMember` 的第一步就检查这个执行账户是否已属于其他组合，属于就返回业务错误“执行账户已属于组合 X，先从该组合移除”。
  - 必须放在同步和持仓检查之前。现在的顺序是先同步、查持仓，最后才写入（`logicalaccount/service.go:142-165`），用户会先看到“需要接管持仓”或同步失败这类无关的错误。
  - `PutLogicalAccountMember` 在事务里再查一次，作为兜底；用户不会直接看到唯一约束冲突。
- 关闭模拟账户（`store/paper_simulation.go:64`）现在只删启用成员，改为删除该账户的全部成员关系。否则留下的停用成员会让这个组合每次清仓都同步失败，一直运行满 30 分钟。
  - 加锁也要跟着改。现在按启用成员找组合加锁（`papersimulation/service.go:133`），账户只是停用成员时，只拿到执行账户锁就删了成员关系。改为用 B2 新增的“按执行账户查任意成员关系”找到组合，再加成员变更锁。
- 按旧模型写的测试一起改：
  - `store/logical_account_test.go:44-58` 断言可以在另一个组合加停用成员，改为断言被拒绝；
  - `operator/service_test.go:437` 的 “move member” 场景改为先移除、再加入。
- 不改的地方：
  - 清仓仍包含停用成员。约束改了以后，停用成员只可能属于本组合，清仓它是对的。
  - `FindLogicalAccountByTradingAccount` 仍只认启用成员。
  - 同步锁范围、人工下单撤单、各 RPC 读路径，第一轮审查已核对过，不用改。
- 选这个方案而不是“清仓时跳过别的组合的单”，是因为模型更简单，撤单、持仓查询、移除检查等各处都不用再分辨归属。代价是想把账户换到别的组合，必须先移除；移除本来就要求无持仓，不增加操作负担。

### 3.9 停用执行账户前检查组合成员（B2）

`account.Service.Update` 把账户从启用改为停用时，如果它还在任何组合里（启用或停用成员都算），返回业务错误“先把执行账户移出组合账户再停用”。模拟盘账户本来就不允许改状态，这条只影响实盘账户。

### 3.10 清仓结束条件（B3）

**零头只针对现货。** 现货受管资产按**总量**（不是可用余额）判断：

- 按步长取整后低于最小数量，或者按最新价低于最小名义金额，就算零头，下不了单。
- 零头不算剩余，不阻止“完成”。清仓结果里另列 `Dust`，供用户查看。
- 总量不是零头、只是可用余额不够（还被锁在挂单里），归入可重试。如果按可用余额判零头，余额还没释放时会误报“完成”。

**零头规则由一个函数统一判断。** 新增包 `internal/application/exposure`，提供“选标的 + 判零头”：

- 选标的的规则统一用清仓现在的口径：基础资产匹配、计价资产等于结算资产、在结算资产下可交易。
- 现在移除成员（`memberHasManagedExposure`，`logicalaccount/service.go:602-615`）按基础资产取最后一个标的、只比最小数量，和清仓的口径不一致。改为调用同一个函数。
- 移除成员要给 `logicalaccount.Service` 接上报价来源（bootstrap 里已有 `ExchangePriceSource`）。拿不到报价时只比较最小数量。

**永续不按名义金额判断。** 清仓平仓单用 reduceOnly，币安不查最小名义金额；目标执行器的全平也是这样（`executor.go:978`）。永续只有数量不符合交易所规则时才算终结原因。

**剩余原因分两类，没有列为终结的一律可重试：**

| 类别 | 原因 | 处理 |
| --- | --- | --- |
| 终结 | 无可交易标的；永续数量不符合交易所规则；清仓子单**零成交**就被拒单、撤销或过期（同一单号重试只会得到同样结果）；`Orders.Place` 返回的永久校验错误（`IsPermanentValidationError`），但 `ErrInsufficientFunds` 除外；不支持的市场类型；不在交易时段 | 本账户本轮直接结束为“部分完成”，不再重试 |
| 可重试 | 其他所有情况，包括：等待余额确认、报价失败、子单在途、本轮刚下成功、同步失败、账户错误、现货可用余额不够、`ErrInsufficientFunds`（预留不足时也返回它，`order/service.go:199`）、`ErrReduceOnly`（持仓投影可能滞后）、部分成交后被撤销或过期的子单，以及兜底原因 “position remains after final sync” | 照旧重试 |

部分成交的子单要按可重试处理，原因是子单单号由数量算出（`flatten.go:946`）。部分成交后，持仓同步到最新时，下一轮会按新数量生成新单号；还没同步到时会撞上同一个单号，这时不能当作终结。

- `reasons` 从 `map[string]string` 改为带类别的结构。
- **每轮单独记本轮的错误。** 现在每轮开头只清空 `result.Error`（`flatten.go:325`），`cause` 在同一次运行里一直累加；外层又按 `!submissionBusinessError(cause)` 决定是否重试（`flatten.go:152`）。不改的话，第一轮“子单在途”留下的旧错误，会让只剩终结原因的动作仍停在运行中。改法：
  - 本轮的错误和分类单独存放，跨轮只保留用于展示的错误文本；
  - 外层是否重试，按各账户最后一轮的分类决定。
- `flattenAccount` 每轮结束时，剩余全部是终结原因、且本轮没有可重试错误，就立即返回“部分完成”。整个动作也随之变成“部分完成”，不再等 30 分钟。
- 30 分钟兜底保留，用于账户一直异常的情况。

**顺带去掉一次多余的轻量同步：** 没有要撤的单时，`syncAfterCancel` 会紧接着第一次同步再做一次轻量同步。没撤单就跳过。

### 3.11 清仓入口：并发与锁忙（B4）

- **同一组合只允许一个运行中的清仓。** 发起清仓时，如果这个组合已有另一个运行中的 FLATTEN 动作，直接返回那个动作，不新建。否则两个清仓会互相撤对方的子单。
  - 要查两次。锁前先查一次：运行中的清仓多半正持着锁，只在锁内查的话，新请求只会拿到“组合账户正忙”。锁内建动作的事务里再查一次，防止两个请求同时通过检查。
  - 请求的动作本身已存在且在运行中时（工作线程恢复时用原动作号调入，`operator/service.go:410`），跳过这个检查。否则遗留下来的两个运行中动作会互相返回对方，永远不推进。
  - 前端按返回的 `action_id` 轮询（`index.vue:891`），返回另一个动作没有问题。
- **拿锁用短超时，并从总预算里扣除。** 组合账户锁用 2～3 秒的超时去拿，现在是整个预算都用来等锁（`flatten.go:65-85`）。8 秒总预算不变，等锁用掉的时间从里面扣除，保证加上收尾不超过网关的 10 秒调用超时（`flatten.go:989`）。锁是轮询抢占（`context_lock.go:36`），目标执行器一整轮都持锁（`executor.go:156`），所以 1 秒太短，实盘下容易报“正忙”。
- **锁被占用时：**

| 动作状态 | 返回 |
| --- | --- |
| 新动作 | 业务错误“组合账户正忙，稍后再发起清仓” |
| 运行中 | 当前动作，错误为 nil。前端看到“运行中”，由工作线程继续；与人工下单一致（`service.go:191`） |
| 部分完成、失败 | 业务错误“组合账户正忙，稍后再发起清仓”，不再返回假成功 |

### 3.12 换手率告警（D 决策 1，需要你定）

- 主机上没有 `sqlite3` 命令行，读写库用 `python3` 的 `sqlite3` 模块。
- 每分钟有 `moox-runtime watch` 看门狗，会拉起停掉的服务。

启动时的表结构检查会逐条比较索引 SQL，所以已有库要在换二进制之前改好索引。旧进程只在启动时检查，运行中改索引不影响它。但改完之后、换二进制之前，旧进程一旦被看门狗重启，就会因表结构不符而启动失败。所以改库之后要紧接着发布，不要隔开。

1. 备份数据库到 `/data/moox/trade/db-backup-<时间>/`。用 `sqlite3` 模块的 backup 接口，不要直接 cp 正在写的文件。
2. 检查重复成员，结果必须为空。不为空就停下来问用户，由用户决定移除哪个：

   ```sql
   SELECT c_space_id, c_trading_account_id, COUNT(*)
   FROM t_logical_account_members
   GROUP BY c_space_id, c_trading_account_id
   HAVING COUNT(*) > 1;
   ```

3. Trade 运行中，用 `python3` 执行下面三条语句：

   ```sql
   CREATE UNIQUE INDEX IF NOT EXISTS ux_logical_account_members_trading_account
   ON t_logical_account_members (c_space_id, c_trading_account_id);
   DROP INDEX IF EXISTS ux_enabled_physical_account_membership;
   DROP INDEX IF EXISTS idx_logical_account_members_account;
   ```

   - **建索引语句直接从新的 `schema/logical_account.sql` 拷贝，不要手敲。** 表结构检查只合并连续空白、去掉引号、统一小写（`store.go:292-296`），`t (a)` 和 `t(a)` 不相等。SQLite 存的索引 SQL 不含 `IF NOT EXISTS`，这一点不影响比较。
   - Python 的 `sqlite3` 默认不给 DDL 开事务。连接时用 `isolation_level=None`，三条语句外面显式包上 `BEGIN IMMEDIATE; … COMMIT;`，并设置 `busy_timeout`，避免和 Trade 的写入冲突。
4. 紧接着用 native-release 发布新 Trade 二进制。native-release 不接受未推送的提交，要先推送分支。
5. 用 `current/status.sh` 和 Trade 日志确认表结构检查通过、服务正常，再做 D4。
6. **回滚不恢复备份库**：恢复会丢掉发布之后的订单、成交和权益点。步骤：
   1. 用 `current/pause.sh` 停掉 Trade。暂停状态会记下来，看门狗不会把它拉起来。
   2. 执行反向语句：重建 `ux_enabled_physical_account_membership` 和 `idx_logical_account_members_account`（从旧版 schema 拷贝），删除 `ux_logical_account_members_trading_account`。
   3. 用 `install -m 0755` 把 `binary-backup-trade-*` 里的旧二进制换回。resume 会校验二进制是属主一致、权限 0755 的普通文件（`unitruntime/runtime.go:379`）。
   4. 用 `current/resume.sh` 启动。

   第 1 步的备份只在库损坏时才用。

## 7. 风险

- **精确键解析改动面大**：私有流的四类负载全部改写，字段映射容易错。缓解办法是 A0 先用官方原文样例锁住预期，D2 审查逐个对照，D5 用测试网录到的原文再核对一次。
- **B1 改约束会挡住现有用法**：生产只有一个模拟组合，第 5 节第 2 步先查重。以后要把账户换到别的组合，必须先移除。
- **B3 终结原因分错，会让本该重试的清仓提前结束**：结束时剩余持仓和原因都写进结果，用户可以重新发起。审查时重点看分类表。
- **A8 的边界**：非下单请求被限频后不再暂停下单，但下单请求自己仍会被 OKX 拒、并触发暂停，不会放大请求量。
