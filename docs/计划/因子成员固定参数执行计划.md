# 因子成员固定参数执行计划

2026-10-25 · v3（已吸收第一轮 Codex 审查，未编码） · 分支 `feat/initial-import`

## 1. 目的与范围

现有设计里，一个因子定义常常要同时算多组参数（EMA20 与 EMA50、预热 0 与预热 5 万），但参数只能由策略实例的专属任务逐期提交，
**非策略专属的因子计算任务（页面上的“计算任务”，内部叫共享因子集）的成员永远用定义的默认参数**。要在这类任务里算 `ema(close, 20, 50000)`，
只能新建一个把参数写进表达式的因子（`Ema20Warmup50000`）：参数混进了因子名，每多一组参数就多一个定义，结果里也看不到参数。

另外，建任务时还要选“对象范围”（`all` / `include` 一组标的），而标的范围其实已经由源数据集决定；新建任务后还要在因子机手动 `lifecycle init / start / confirm`，
不做就一直是“未初始化”，不计算（2026-10-25 实际踩到）。

本计划做三件事，让“因子计算任务”成为唯一的用户概念：

> 因子计算任务 = 一个源数据集（决定标的、频率） + 一组成员（因子 + 固定参数 + 别名）

1. **成员带固定参数**，同一个因子定义可以用不同参数、不同别名在一个任务里出现多次；别名由参数自动生成。
2. **去掉任务的对象范围**：任务的标的就是源数据集当前的标的。
3. **所有任务自动推进生命周期**，不再手动 init / start / confirm。

不在本计划内：不引入“内置因子 / 自定义因子”的区分，不做按数据集自动绑定；回看仍按参数范围的最大组合推导（引擎按最大需求加载本地窗口，公共计算逻辑不变）。

## 2. 术语

| 说法 | 含义 |
| --- | --- |
| 因子计算任务 | 页面“计算任务”，内部 `FactorSet`；本计划不改内部名字 |
| 成员 | 任务里的一个因子，身份是 `(任务, 别名)` |
| 固定参数 | 加成员时给定、之后不变的参数值 |
| 策略实例专属任务 | 策略实例启用时自动建的任务（`owner_instance_id` 非空），参数由该实例逐期提交；是引擎内部的一类任务，不是用户要学的概念 |

## 3. 决策

| # | 决策 | 理由 |
| --- | --- | --- |
| 1 | 成员新增**固定参数**：加成员时给出，之后不可改；要换参数就删除后重加（别名随参数变） | 别名与结果列名由参数决定，参数不可变才能保证列的含义不变，也免去“改参数”的冻结与历史问题 |
| 2 | 别名默认由系统生成：**全部参数等于默认值 → 沿用因子 ID；否则 `因子ID_参数1_参数2…`**，按定义声明的顺序写全部参数值 | 同一组参数总是同一个别名；全默认时现有列名（`ema`、`macd_dif`）不变 |
| 3 | 别名可在加成员时手改，**成员启用后不可改**；字符与长度沿用现有规则（字母、数字、下划线，无连续下划线，别名最长 32 字符，`别名_输出名` 结果列最长 64 字符）；自动生成的别名超长或与已有别名冲突时，提示手填 | 别名决定结果列名；不放宽现有限制 |
| 4 | 同一任务内，**同一因子 + 同一组参数只能有一个成员** | 避免重复计算 |
| 5 | **参数列只在策略实例专属任务写入**；非专属任务不写 | 固定参数的任务里，参数列每行都一样，没有信息量；专属任务的参数逐期变化，列才有记录价值（按用户“参数列不用”理解，见第 11 节） |
| 6 | 去掉任务的对象范围：删除 `subject_mode`、`subjects` 与只改范围的 `UpdateFactorSet`；任务的标的 = 源数据集当前的标的，标的增减沿用现有行为 | 范围已体现在源数据集里 |
| 7 | 所有任务由引擎自动 `init`、`start`；**非专属任务另外在满足第 9 节判据后自动 `confirm` 进入运行**；专属任务保持现状（不自动 confirm） | 专属任务的预热阶段有“策略对预热实例发影子目标”的语义，不动；非专属任务没有策略依赖，预热与运行只是显示阶段不同 |
| 8 | 删除 `Ema20Warmup50000` 因子与成员，改为 `Ema` + `span=20, warmup=50000`（别名 `Ema_20_50000`）；`Ema50000` 暂保留 | 项目未上线，线上数据直接删除重建，不写迁移 |
| 9 | 因子定义命名约定：只描述算法，不带参数值 | 参数属于成员，不属于定义 |

数值参数写进别名的规范：先把有限 `float64` 按 `strconv.FormatFloat(v, 'f', -1, 64)` 写成十进制（不出现指数；`-0` 按 `0`；整数不带小数点），再把 `.` 换成 `p`、`-` 换成 `n`（`0.5` → `0p5`，`-1` → `n1`）。服务端与前端用同一份测试向量。
下划线拼接不保证全局无歧义（因子 `A_1` 的参数 `2` 与因子 `A` 的参数 `1, 2` 都能生成 `A_1_2`）：同一任务内别名本来就唯一，冲突时第二个提示手填别名即可，不加编码。

## 4. 数据模型

- `t_factor_set_members` 新增 `c_params TEXT NOT NULL DEFAULT '{}'`：参数名 → 数值的规范 JSON（键有序），**保存加成员时的完整参数值**（定义没有参数的存 `{}`）。“是否全默认”只在创建时用于生成别名；之后定义的默认值再变，成员的固定值也不变（避免同一别名、同一列跨期含义漂移）。
- 唯一性：应用层校验“同任务同因子同参数”；SQL 层加唯一索引 `(c_set_id, c_factor_id, c_params)`。`store/database.go` 的严格列清单同步。
- `t_factor_sets` 删除 `c_subject_mode`、`c_subjects_json`。
- 领域层：`domain.MemberDef` 增加 `Params`（完整参数）与 `TrackParams`（是否写参数列）。**`TrackParams` 由所属任务的 `owner_instance_id` 派生**（非空为真）：`SetMember.Def()` 现在拿不到任务，改为带任务所有者参数的构造；已有的所有 `MemberDef` 构造点（`catalog/reconcile.go`、`rpc/convert.go`、`enginehub/snapshot.go`、`pipeline/compute.go` 等）逐一审计；
  `domain.DefaultSnapshot(def)` 改为 `domain.MemberSnapshot(member)`，快照取成员固定参数。
- **成员契约指纹**：周期标记里的 `definition_hash` 由“定义指纹”改为“定义指纹 + 成员完整参数的规范串”的哈希，让策略的版本核对（`strategy/internal/readiness`）能识别“同一别名、不同参数”；参数为空的成员指纹不变。
- 别名生成：`domain.DeriveMemberAlias(def, params)` 是服务端权威实现；前端实现同一规则，两边用同一份测试向量（放 `modules/factor/testdata/alias_vectors.json`，前端测试读取）。

## 5. 协议（`proto/factor.proto`）

- `AddFactorToSetReq` 增加 `map<string, double> params = 4`；`member_alias` 为空时按第 3 节规则生成（不再取定义 ID）。
- `FactorMember` 增加 `map<string, double> params`（完整参数，只读，派生）；`param_columns` 在非专属任务为空。
- `FactorUsage` 增加 `params_summary`（如 `span=20, warmup=50000`，全默认为空）。
- `FactorSet` 删除 `subject_mode`、`subjects`；`CreateFactorSetReq` 随之不再带；`EnsureInstanceFactorSetReq` 里的 `subject_mode`、`subjects` 一并删除（策略调用方、管理端 RPC 转换、`catalog/instance.go` 同步）；删除 `UpdateFactorSetReq/Rsp` 与 RPC `UpdateFactorSet`。
- 引擎目录（`SyncEngineCatalog`）的成员带 `params`，**目录指纹（`enginehub/snapshot.go` 的 `CatalogHash`）纳入成员完整参数**，否则同一别名删除重加换参数后，引擎会因 `not_modified` 继续用旧目录；任务不再带 `subject_mode`、`subjects`。
- 服务目录（`packages/servicecatalog/catalog.yaml`）去掉 `UpdateFactorSet`，路由数与快照测试同步；这是目录变化，**Admin、Monitor、三台 host-gateway 要整体发布**（`native-release.md` 的“服务目录变化”流程）。

## 6. 校验

加成员时：参数名必须是定义声明的；类型（整型必须是整数）与范围按定义校验；联合约束成立；别名合法且在任务内唯一；同因子同参数不重复。
定义被更新（`UpdateFactor`）时，除了现有“成员须先停用”，还要校验所有成员保存的固定参数仍然合法（参数名仍声明、类型与范围仍成立），不合法的拒绝并列出成员。
同一别名在结果数据集里已有列时，不允许以不同的完整参数重建成员（避免策略把新参数产生的同名列当成旧因子继续读）；要换参数请换别名。

## 7. 冻结与计算

- 非专属任务的冻结来源仍是“默认”，但默认快照改为成员快照：`engine/params.go`、`pipeline/compute.go`、`catalog/params.go`、`engine/replay.go`、`engine/runonce.go` 里五处 `DefaultSnapshot(member.Factor)` 改为 `MemberSnapshot(member)`。
- `params_digest` 用成员快照计算；周期标记里的 `params_source` 仍为 `default`。
- 专属任务不变：成员固定参数为空，参数仍由策略逐期提交，参数列照常写入。
- **回放**（`engine/replay.go` 的 `params()`）：非专属任务拒绝请求里的逐期参数覆盖，只用成员固定值；专属任务保持现有请求语义。
- 结果列：`OutputColumn` 规则不变（别名等于因子 ID 时就是输出名，否则 `别名_输出名`）；`ParamColumns()` 在 `TrackParams` 为假时返回空，
  列对齐（`catalog/reconcile.go`、`catalog/service.go`）随之不含参数列。**组装（`pipeline/assemble.go` 的 `planParams`/`memberParamColumns`）与回放帧（`engine/replay.go`）当前按 `ParamNames()` 的下标访问 `ParamColumns()`，`TrackParams` 为假时必须整体跳过参数列的组装与注入**（参数计算仍用完整快照），否则越界。分别测实时、补算、回放。
- 回看不变：成员回看仍按定义的参数范围取最大组合（不按成员固定参数缩小）。
- **冻结区间**：固定参数值不会变，但冻结记录按“快照 + 来源”分段，离线沿用等情况仍可能出现多段；补算按冻结记录分段的现有行为不变，不承诺“只有一段”。

## 8. 去掉对象范围

所有用到 `SubjectMode` / `Subjects` / `InScope` 的地方，统一改为“任务的标的 = 源数据集当前的标的”：

| 位置 | 改动 |
| --- | --- |
| `domain/types.go` | 删除 `SubjectModeAll/Include`、`FactorSet.SubjectMode/Subjects`、`InScope`（范围判断改为“标的在源数据集里”由调用方的标的列表决定） |
| `engine/preload.go`、`pipeline/plan.go`、`trigger/eventconsumer/continuity.go`、`engine/recalcloop.go` | 本地窗口共享键只用源数据集；预加载标的取源数据集全部标的；实时计算、连续水位继续使用**该期事件的全集**；缺口修复继续读冻结全集 |

| `preview/preview.go`、`domain/validate.go`（`ValidateSnapshot` 的范围参数） | 试算与参数覆盖需要校验标的时同上，查询源数据集成员 |

| `cli/internal/command/setup_factors.go`、`cli/internal/setup/config/config.go`、`moox.toml.example`、`factor/cmd/cli/commands.go`（含 `purge-dataset` 之外的建任务命令） | 配置与命令行去掉范围字段 |

标的随源数据集的标签增减，沿用引擎现有的“标的进出”处理，不加新机制。

## 9. 自动推进生命周期

- `engine/lifecycle.go` 的 `autoStartSet`：由“有拥有者的集合”改为“目录里的全部启用任务”，每个生命周期周期（`lifecycle.interval`，默认 30 秒）自动 `init`（未初始化）与 `start`（就绪）；检查没过的下一轮再推进，手动暂停、恢复追赶、重置中的不动（与现状一致）。
- 非专属任务自动 `confirm` 的判据（全部满足才确认）：任务有启用成员且有期望标的；进入预热**之后**有一个周期的所有成员都 `complete`、无预热中与失败标的，且结果与周期标记都已成功写入；确认瞬间复查阶段仍是预热。
  证据持久化：在 `lifecycle.json` 的对象状态里记录“预热后首个完整周期时间”，引擎重启后从这里恢复，不依赖内存里的最近运行摘要（`engine/run_tracker.go` 重启即清空）。专属任务不变。
- `AutoAdvance`（`packages/lifecycle/query.go`）只处理未初始化与就绪；手动暂停、恢复追赶、重置中的对象不会被它推进，保持。
- 保留 `lifecycle init/start/confirm` 命令，供人工排障。
- skill `initial-import.md` 第 12 步里“手动走 lifecycle”的一段改为“自动推进：新任务在引擎同步目录并预加载完成后进入预热，下一个源数据周期之后出结果并转为运行；用 `lifecycle status` 查看”；`因子.md` 同步。

## 11. 需要确认

1. **“参数列不用”的含义**：按“非专属任务不写参数列，只有策略实例专属任务写”处理。若你的意思只是“不要按别名展开成 `Ema_20_50000__span`，已有的 `Ema__span` 仍保留”，则决策 5 与第 7 节最后一条改为“非专属成员的参数列仍按 `别名__参数名` 写”，其余不变。
2. 自动 `confirm` 的触发条件（第一个预热周期完整算完且无失败标的）是否合适。
3. `Ema` 的 `span` 上限是否放开使 `Ema50000` 也并入 `Ema`：放开会让“不设预热”的通常方式回看超过引擎上限，建议另议，本次不做。

## 12. 上线（未上线，不写迁移）

仓库的 `factor.db` 严格匹配当前表结构，旧库会被拒绝，所以走“先删任务、再改库、再发布、按新模型重建”：

1. **清理现有任务**（在旧版本还在运行时）：通过 `DeleteFactorSet`（`purge=true`）删除线上 3 个任务（两个 1m、一个 5m）及其结果数据集，删除要作废的因子定义（`Ema20Warmup50000`）。`purge-dataset` 不能删仍被任务引用的结果数据集，所以先删任务。
2. **停相关进程**：因子引擎、策略实例涉及的 strategy 无需停，但新旧协议不能混用，所以下面第 3 步的组件要尽快连续替换。
3. **发布顺序**（沿用 `native-release.md` 的“服务目录变化”流程）：三台 host-gateway **及其 CLI**（存储机、海外机、控制机）→ Admin → Monitor（Admin 与 Monitor 连着装）→ factor-mgr（含 CLI）→ 因子引擎 → strategy → web-host（需重新生成内嵌静态文件）。控制机网关装完起不来时，按该文档的办法拉起。操作机 `moox-cli` 最后。
4. **改库**：停 factor-mgr 后对 `factor.db` 手工执行一次结构调整（先备份；不进代码）：成员表加 `c_params` 与唯一索引，任务表删范围两列；同时确认引擎本地状态里与已删任务相关的部分（`lifecycle.json`、参数状态文件、缺口账本）随任务删除被清理，残留的手工清除。
5. **重建**：用 `moox-cli setup factors`（TOML）按新模型建 3 个任务；5m 任务含成员 `Ema`（默认）与 `Ema`（`span=20, warmup=50000`，别名自动生成 `Ema_20_50000`）、`Ema50000` 等。
6. **验收**（分开验收，不用统一 30 秒）：
   - 新建任务后不做任何手动命令，引擎同步目录并预加载完成后自动进入预热；
   - 下一个源数据周期收盘后出结果，第一个完整周期后自动转为运行；
   - 5m 任务出现 `Ema_20_50000_ema`，数值与旧 `Ema20Warmup50000` 在同一期一致（上线前先记下旧列的一期数值作对照）；
