## 1. 目标

1. 新增独立服务，组件 ID `callback-dispatcher`，模块名 `callbackdispatcher`。组件 ID 不带 event，免得和事件总线 `eventbus` 混淆。界面上叫「事件中心」。
2. 用户在事件中心配置**事件规则**：当某类事件发生、并且落在限定范围内时，执行一个动作。动作有两种：
   - **通知地址**：向用户自己实现的 HTTP 接口发 POST；
   - **系统动作**：MooX 自带的处理。第一版只有一个：“卖出策略持有的下架币”。
3. 每次执行都有**执行记录**。失败会自动重试，用完重试次数后告警，可以在页面上重新执行。
4. 下架检测作为事件生产者，放在采集模块 Collector 里，发布新事件“标的即将下架”。

不做：事件编排（多个动作串成流程）、按条件改写事件内容、向 EventBus 反写事件。

## 2. 现状

**EventBus**（NATS JetStream）：

- 事件在 `packages/events/registry.go:66-93` 里声明，现有 8 个：
  - `MOOX_OBSERVABILITY`：两个监控事件；
  - `MOOX_STORAGE`：`dataset.rows.upserted`、`dataset.period.completed`、`view.data.ready`、`dataset.sync_point`；
  - `MOOX_COLLECTOR`：`collector.kline.backfilled`；
  - `MOOX_TRADE`：`trade.target.weight_requested`。
- 信封有 event_id、名称、版本、空间、subject、发生时间、payload（`eventpb/event_message.proto:12-20`）。payload 是确定性 proto 二进制，信封 ≥256 字节时做 zstd 压缩。消费端必须先用 `events.DecodeRaw`（`decode.go:28-80`）解压并校验，仓库里没有现成的 payload 转 JSON。
- 消费：用 `events.NewConsumer` 和 `jetstream.Runner`，处理结果映射成 ACK、RETRY、TERM（`runner.go:17-27`）。
  - 一个 durable 只能绑一个流，消费多个流就是每个流一个 durable（先例：Collector 合成，`resample/eventconsumer/consumers.go:132-148`）。
  - 已存在的 durable 不能放宽过滤主题（`jetstream/consumer.go:351-356`）。
- `MOOX_TRADE` 是工作队列（`eventbus/config/app.yaml:62-73`），再挂消费者会和 Trade 抢消息，**不能开放订阅**。
- 新的消费者要在三处配置：凭据角色（`admin/cmd/cli/eventbus_credentials.go:35-36、401-451`）、组件到角色的映射，以及写入 app.yaml 的投影（`unitinstall/eventbus.go:31-53、282-297`）。
- 发布端：Collector 有 EventBus 发布身份和发件箱（`collector/schema/collector.sql:356-368` 的 `t_collector_event_outbox`，`resample/notify.go:153-180`），NATS 去重窗口 2 分钟。

**采集侧的下架相关**：

- collector-stream 没接入 EventBus，也没有数据库。它发现“疑似下架”（连续 3 个周期没有收盘推送，`stream/delist.go`）时，经网关报给 Collector（`rpc/stream_collector.go:141-206`），再由 Collector 同步标签。
- Collector 经出口代理访问币安：出口代理的域名白名单只有币安（`egressproxy/config/app.yaml:2-4`）。Collector 有币安客户端（`sources/binance/client`，`GetExchangeInfo` 在 `spot.go:103`、`swap.go:100`），没有 OKX 源。
- 这些都是下架**发生之后**的检测；交易所公告是**提前**通知，两者不重叠。

**出站请求**：仓库里没有面向任意用户地址的出站防护。告警 Webhook 只允许企业微信、飞书的域名（`packages/notification/channel.go:41-50`）；出口代理有解析后逐个 IP 校验再拨号的代码（`egressproxy/internal/proxy/dial.go:12-41`），可以提成共享包（4.3）。

## 3. 事件与规则

### 3.1 可订阅事件目录

**目录只放在本服务里**，不改事件注册表，也不改 EventBus 的 `ListEvents`。只为了展示就在注册表加标记、改 proto 不值得，界面名和可限定的字段本来就要在本服务里写。本服务加一条测试，断言目录里每个事件都在注册表里声明过，而且所属的流不是工作队列。

第一版开放的事件：

| 事件 | 界面名 | 可限定的范围（都从信封取） |
| --- | --- | --- |
| `event.storage.dataset.period.completed` | 数据集一期完成 | 空间、数据集（subject） |
| `event.storage.view.data.ready` | View 数据就绪 | 空间、View（subject） |
| `event.collector.kline.backfilled` | K 线补写 | 空间、数据集（subject） |
| `event.collector.instrument.delist_scheduled`（新增） | 标的即将下架 | 交易所、市场、交易所代码（subject 的三段） |

- 可限定的范围全部来自信封的 `space_id`、`subject_id`，规则匹配是通用的，不用解析各事件的 payload。前三个事件的 subject 已核对：分别是 dataset_id、view_id、dataset_id（`events/validation.go:193、242`）。
- 不开放的事件：
  - `MOOX_TRADE` 的策略目标：它是工作队列；
  - `dataset.rows.upserted`、`dataset.sync_point`：量大，而且偏内部；
  - 两个监控事件。
- 以后开放新事件，只需要在本服务的目录里加一行。

### 3.2 新事件：标的即将下架

- 名称 `event.collector.instrument.delist_scheduled`，版本 1，流 `MOOX_COLLECTOR`，owner `collector`。
- payload 新增 proto `InstrumentDelistScheduled`：交易所、市场（SPOT/SWAP）、交易所代码、下架时间、来源（`BINANCE_SPOT_SCHEDULE`、`BINANCE_SWAP_EXCHANGE_INFO`、`OKX_SWAP_INSTRUMENTS`、`MANUAL`）、首次发现时间、范围（ALL / PAPER_ONLY，后者只用于演练）。
- payload 的 proto 和已有的 Collector 事件 `CollectorKlineBackfilled` 放在同一个包（`storagepb`）。
- 信封：
  - subject 用“交易所:市场:代码”；
  - 空间用现有系统事件的 `mooxsys`（信封只要求空间不为空，`message.go:115`；先例见 hostagent 的 `jetstream.go:58`）；
  - event_id 由（交易所、市场、代码、下架时间）确定性生成，同一条下架重复发布时，NATS 会在 2 分钟窗口内去重。
- 校验函数断言 payload 类型，并核对 subject 一致。
- 注册：
  - `registry.go` 加声明，`events_test.go` 的清单同步修改；
  - `eventbus/config/app.yaml:76` 里 `MOOX_COLLECTOR` 的 subjects 加上 `moox.event.collector.instrument.delist_scheduled.v1.>`。EventBus 启动时要求每个注册事件恰好被一个流覆盖（`config_validation.go:108-129`）；它启动时会对流执行 UpdateStream（`registry/registry.go:171`），加 subject 不需要迁移。

### 3.3 事件规则

一条规则：

| 字段 | 说明 |
| --- | --- |
| 名称 | 用户起的名字 |
| 触发事件 | 从可订阅目录里选一个 |
| 限定范围 | 按 3.1 表里可限定的字段做等值匹配，空表示不限；可以多选，例如交易所只限币安 |
| 动作 | 通知地址，或系统动作 |
| 通知地址 | URL（只允许 http、https），以及一个验证密钥（服务生成，只在创建时完整显示一次） |
| 系统动作 | 第一版只有“卖出策略持有的下架币”，只能用在“标的即将下架”上：一发现就禁止买入，下架前 24 小时平仓。用户不能新建系统动作规则，只有服务自带的那一条，免得重复平仓 |
| 启用 | 开关 |

- 规则存在服务自己的库里（`t_event_rules`）。
- 服务首次启动时，自动建一条系统规则：“标的即将下架时，卖出策略持有的这个币”，默认启用。用户可以停用，但不能删除。

## 4. 投递

### 4.1 消费与落库

**消费**：

- 每个可订阅事件一个固定的 durable（`events.ConsumerConfig.Event` 已经支持按事件建），开放新事件就加一个，不用改已有 durable 的过滤主题。
- 命名：NATS 的 durable 名不能含点号，所以名字是 `callback_dispatcher_` 加上去掉 `event.` 前缀、点换成下划线的事件名，再加 `_v<版本>`，例如 `callback_dispatcher_collector_instrument_delist_scheduled_v1`。
- 这张 durable 名表在本服务和 EventBus 凭据生成（`eventbus_credentials.go`）里各写一份，两边由测试核对一致。
- MaxDeliver 设成不限次数：写库失败不能丢事件。
- 投递策略：
  - “标的即将下架”用 DeliverAll。流保留 72 小时，第一次上线时能收到 Collector 已经发出的下架；回放也无害，同一事件会被去重。
  - 其余事件用 DeliverNew，第一次上线时不回放历史通知。

**落库**：

1. 收到事件，先用 `DecodeRaw` 解码，再用 protojson 把 payload 转成 JSON。
2. 匹配所有启用的规则。匹配上的规则：
   - **去重**：先往 `t_event_receipts`（主键：event_id、规则 ID）插一行。插不进去，说明这条事件已经处理过，直接跳过。通知地址和系统动作都用这张表去重。
   - **通知地址**：写一条执行记录（`t_event_executions`），状态 PENDING。
   - **系统动作**：按 `c_dedupe_key`（规则 + 交易所:市场:代码）**合并或新建**。同一个标的已经有未结束的执行记录时，只更新它的下架时间，不新建。`c_dedupe_key` 上有一个排除终态的部分唯一索引。新建或更新后，把 `c_next_run_at` 设为现在，让工作线程立即处理（4.4 的 `delist_detected` 在工作线程里判断，不放在消费路径上，免得 Trade 不可达时消息反复重投）。
3. 写库成功才 ACK。匹配不上任何规则的直接 ACK，不留记录。解码失败的 TERM，并计入告警计数。

**执行**：执行记录由独立的工作线程处理，和 JetStream 的消费解耦，一条通知失败不会让同批后面的事件一起退避（`runner.go:197-208` 的问题）。跨天的系统动作用 `c_next_run_at` 记下一次该推进的时间，工作线程按这个时间取任务。

### 4.2 通知地址的请求格式

```text
POST <通知地址>
Content-Type: application/json
X-MooX-Event-Id: <event_id>
X-MooX-Event: <事件名>
X-MooX-Timestamp: <发送时的毫秒时间戳>
X-MooX-Signature: sha256=<HMAC-SHA256(验证密钥, 时间戳 + "." + 请求体)>

{"event_id": "...", "event": "event.collector.instrument.delist_scheduled", "version": 1,
 "space_id": "...", "subject": "...", "occurred_at": "2026-11-04T08:00:00Z",
 "rule_id": "...", "data": { ...payload 的 JSON... }}
```

- 返回 2xx 算成功，其余都算失败。
- 投递语义是“至少一次”，同一事件可能收到多次，回调方用 `X-MooX-Event-Id` 去重。不保证顺序。
- 管理台的说明页给出验签示例（几行代码）。

### 4.3 出站防护

通知地址是用户填的，出站请求要防住误配置和 SSRF：

- **协议与跳转**：只允许 http、https，不跟随重定向。`Transport.Proxy` 设为 nil，不用环境变量里的代理。
- **超时与大小**：连接超时 3 秒，总超时 10 秒；响应体最多读 64 KB，只记录前 1 KB。
- **地址限制**：解析域名后逐个 IP 检查，通过才拨号，并且直接用解析出的 IP 拨号，防止 DNS 重绑定。IPv4、IPv6 都要检查。
  - 一律拒绝：回环、链路本地（含云元数据 169.254.169.254）、组播。
  - 默认拒绝内网段（10/8、172.16/12、192.168/16、100.64/10，以及 IPv6 的 ULA）。规则可以单独勾选“允许内网地址”，用于用户自己的内网服务。
- **代码复用**：出口代理已有同样的逻辑（`egressproxy/internal/proxy/dial.go:12-41`、`resolver/address.go:10`），但在 internal 包里，不能直接引用。把它提到共享包 `packages/netguard`，出口代理也改用它，避免两份代码。
- 不经过出口代理（它只放行交易所），直接出站。所以部署主机要能访问用户的地址，见 7.4。

### 4.4 重试与告警

- 失败后按 1 分钟、5 分钟、30 分钟、2 小时、6 小时、12 小时重试，从第一次失败起超过 24 小时就停，执行记录置 FAILED。
- 返回 4xx 的（408、429 除外）不重试，直接 FAILED：多半是配置错了，重试也没用。
- 告警走 Monitor 的“关注项”（照 Trade 的 `telemetry/attention.go:66-100`），指标是 `moox_callbackdispatcher_attention_active`，分三类：

| 种类 | 触发 | 持续到 |
| --- | --- | --- |
| `execution_failed` | 有执行记录置为 FAILED | 用户在页面上重新执行或确认 |
| `delist_detected` | 收到新的“标的即将下架”，并且用只读的 `ListInstrumentHolders` 查到当前有策略持有 | 约 3 分钟：触发一次、恢复一次，相当于一条通知 |
| `action_failed` | 系统动作某一步用完重试、核对失败或有零头（第 5 节） | 用户处理 |

  关注项每轮从库里的状态重新算出，重启不丢。Monitor 要为本服务新写一个汇总函数（现有汇总只读 Trade 的指标，`overview.go:1089、1107`），还要在上报白名单里放行这个指标（`report/monitored_metrics.go:92`）、`business_freshness.go:289、305`、`overview.go:1724、1738`，以及 skill 的 `monitor-attention.md`。
- 执行记录保留 30 天。

## 5. 系统动作：卖出策略持有的下架币

这一节沿用原《事件处理中心执行计划》v4 第 3.4 节的流程，只是触发方式改成“由规则触发”。所需的 Trade 接口见交易计划 4.7，调用方从原来的 event-center 改为 callback-dispatcher。

**动作状态**：下架处理要跨越一天以上，不能像通知那样一次完成。每条执行记录对应一个下架事件，处理过程中的轮次和步骤存在 `t_delist_actions` 里，字段沿用原计划的动作表：轮次、种类（BLOCK、FLATTEN、VERIFY）、空间、组合账户、交易所、Trade 操作号、状态、尝试次数、结果、错误，唯一键是（执行记录、轮次、种类、空间、组合账户）。

记下架时间为 T，流程如下：

1. **一发现就禁止买入**（用户 11-04 决定）：收到事件后立即调 `BlockInstrument`，不等 T − 24 小时。这样策略在下架前这段时间不会新买入这个币。收到事件时已经过了 T（只可能是手工补录），也照样写入名单，然后直接跳到第 7 步核对，不下单。
2. **未知标的**：Trade 不认识这个标的（没有开通对应市场的账户）时，`BlockInstrument` 照常写入名单，`ListInstrumentHolders` 返回空列表。这种情况直接结束，也不发 `delist_detected`；名单照样保留，以后开通这个市场的账户也不会买入它。
3. **等平仓时机**：禁止之后等到 T − 24 小时再平仓。从发现到 T − 24 小时之间，名单标的“只减不增”（交易计划 4.7）：策略不能加仓，但可以照常减仓、卖出；下架前 24 小时再把剩下的统一平掉。
4. **找持有者**：调 `ListInstrumentHolders`，范围是 PAPER_ONLY 时传 `paper_only=true`；零头不算持有。
5. **平仓**（第 1 轮，T − 24 小时）：对每个（空间、组合账户）调 `FlattenInstrument`。
   - reason 在建动作时生成并存下，重试用存下的值。
   - 每 30 秒用 `GetOperatorAction` 查一次结果：RUNNING 继续查、不计次数；COMPLETED 算成功；FAILED、PARTIAL 用同一个操作号重试，计一次。
   - Trade 返回“忙”时稍后再试，不计次数。
   - 计数的重试最多 10 次，按指数退避；用完置 FAILED，记 `action_failed`。
6. **复查**（第 2 轮，T − 2 小时）：再找一次持有者。仍有持有的，发起第 2 轮平仓，用新的操作号。
7. **核对**：T 之后只核对、不下单。仍有非零头持有的，记一条 VERIFY 失败并告警；零头列在结果里，告警一次。
8. **禁止之后每次推进前先查名单**：第 1 步 `BlockInstrument` 成功之后，每次推进前都用 `ListBlockedInstruments` 确认这个标的还在名单里。已被手工解除的（比如误报或交易所改期很久），停止所有后续步骤，执行记录置为“已取消”。
9. 轮次之间互不阻挡；到了 T，所有平仓重试一律停下。

测试网组合不处理。

**同一标的的去重**：事件可能被多个来源报告，下架时间也可能改。按 4.1 的 `c_dedupe_key` 合并：
- 新事件的下架时间不同时，更新这条记录的 T，按新时间重新算复查和核对的时刻（`c_next_run_at`），已存下的 reason 不变；
- 已结束的记录，同一个 event_id 不再新建。

## 6. 下架检测（采集模块 Collector）

### 6.1 放在 Collector，而不是 collector-stream

上一轮讨论时说放在 collector-stream，摸清现状后改放 Collector：

- collector-stream 没有数据库，也没接入 EventBus，去重和“不丢”都得自己做；
- Collector 有 EventBus 发布身份和发件箱，已经经出口代理访问币安；
- 现有的“疑似下架”也是由 collector-stream 报给 Collector 处理的。

**前提改动：把 EventBus 连接和发件箱中继提到 Collector 级。**

现状是中继挂在 K 线合成下面：

- 只有 `kline_resample.enabled`（`bootstrap.go:447`）并且配置了 `kline_resample.event_bus`（`resample.go:95`）时才创建；
- 中继为空时 Flush 直接返回 nil（`notify.go:69-71`），下架事件会静默积压；
- EventBus 连不上时，靠合成的每分钟定时器重试（`resample.go:93-124`）；发布器是从合成消费者的连接上取出来的（`consumers.go:178`）。

改法：

- **共享连接**：配置改成顶层 `event_bus`。Collector 级维护一个共享连接，自己每分钟重试，不依赖 EventBus 先启动。
- **中继独立**：中继有自己的循环，不依赖合成。`NoticePublisher` 拆成两部分：“封存合成通知”留在合成，“中继发布”归 Collector 级。合成的 `eventconsumer.Start` 改成接收已有连接。
- **同版本发布**：Collector 的配置是严格解码（`bootstrap/config.go:185`）。所以包里的 app.yaml、`unitinstall/eventbus.go:284` 写配置的分支、Collector 二进制，三者必须同一个版本发布。

### 6.2 来源

每个来源每 10 分钟轮询一次：

| 来源 | 接口 | 说明 |
| --- | --- | --- |
| 币安现货 | `GET /sapi/v1/spot/delist-schedule` | 行情数据类：请求头带 `X-MBX-APIKEY`，不要签名，权重 100。用专用只读 Key，见下 |
| 币安 U 本位合约 | `GET /fapi/v1/exchangeInfo` | 单独写解码，不复用 `GetExchangeInfo`：它会过滤掉非 TRADING 的合约（`swap.go:136`），结构里也没有 `deliveryDate`、`contractStatus`（`types.go:143-151`）。哪些字段值算下架，按官方文档定 |
| OKX 永续 | `GET /api/v5/public/instruments?instType=SWAP` 的 `expTime` | Collector 没有 OKX 源，只写这一个公开请求 |
| 手工登记 | Collector 新增 RPC `RegisterDelistNotice` | 事件中心页面调用，用于补漏报和演练 |

- 只保留 USDT 计价的现货和 U 本位永续；接口来源忽略下架时间已过的条目，手工登记可以补录过去的时间。
- 每个接口的字段和取值，实现前按官方文档核对，并录成样例测试。

**出口代理要改两处**：Collector 经出口代理访问交易所。

- **请求头**：请求头有两层白名单，都只放行 Accept、Accept-Language、Content-Type、User-Agent（Collector 侧 `egress_transport.go:115-120`，代理侧 `proxy.go:68`），`X-MBX-APIKEY` 会被丢掉。
  - 改成两层都只对 `api.binance.com` 放行这个头，两侧的日志都不记录它。
  - 币安客户端（`client.go:170-174`）也要加上带请求头的入口。
  - 同步修改《出口代理》文档。
- **域名**：OKX 的域名要同时加进 Collector 的 `egress_proxy.domains`（Collector `app.yaml:61`）和出口代理的白名单。只改代理一边不够：Collector 只把命中自己名单的请求交给代理，其余直连（`egress_transport.go:84`）。

**币安现货的只读 Key**：

- 用户在币安建一把只开“读取”权限的 API Key，写进 moox.toml 的 `[[exchange_keys]]`，设 `readonly = true`、`name = "readonly"`。`setup apply` 把它写进 SecretMgr，固定 ID 是 `exchange-binance-production-readonly`（交易计划 4.2）。只能走这条路，管理台新建的密钥 ID 是随机的。这个来源因此依赖交易计划 T5c。
- 交易计划 T5c 的“apply 后检测”要跳过 `readonly = true` 的密钥，它不是交易账户用的。
- Collector 只读这一个 ID，只用 `key_id`。
- **SecretMgr 新增专用方法** `GetReadonlyExchangeKey(exchange)`：只返回 `exchange-<exchange>-production-readonly` 的 `key_id`，不返回 Secret。服务目录只给 collector 放行这个方法，不给它 `GetSecretValue`。
  - 不能在 `GetSecretValue` 里按调用方限定：网关转发时会丢掉所有 `x-moox-` 开头的元数据（`hostgateway/internal/router/upstream.go:46-50`），SecretMgr 看不到调用方是谁。
  - 用专用方法，沿用现有的“按方法授权”，网关不用改，Collector 也拿不到 Trade 的交易密钥。
- 读不到这个 ID 时，币安现货来源本轮跳过，记一条关注项；下一轮继续尝试，不会永久停用。

### 6.3 去重、发布与告警

- 新表 `t_collector_delist_notices`：（交易所、市场、代码、下架时间）唯一。同一条再次被报告时，只更新“最后报告时间”，不再发布。
- 新出现的条目写进发件箱 `t_collector_event_outbox`，由 6.1 提到 Collector 级的中继发布，不丢。
- 下架时间变了，就是一条新条目，发布新事件。事件中心按第 5 节合并。
- **不做自动撤销**：条目从接口里消失，可能是下架时间改了，也可能是下架已经完成，没法可靠地判断交易所是否撤销了下架。误报靠 24 小时提前量、`delist_detected` 告警、手工取消兜底；Trade 侧还有“解除禁止就停”。
- **来源失败告警**：Collector 也照 Trade 的写法上报关注项，指标是 `moox_collector_attention_active`，种类有 `delist_source_failed`（某个来源连续 3 次失败）和 `delist_readonly_key_missing`。Monitor 的汇总函数和事件中心的一起写（C8）。不用模块健康检查：那是固定注册表（`packages/report/module_health_checks.go:20-30`），表达不了这些原因。

## 8. 管理台「事件中心」

**事件规则**：

  - 通知地址：每次尝试的状态码、耗时、响应摘要；

## 11. 风险

1. **漏报、误报**：来源接口的含义可能和预想不同，所以必须用官方样例测试，并保留手工登记兜底。误报时会一发现就禁止买入，但平仓要等到 T − 24 小时，中间有 `delist_detected` 通知，可以在执行记录里取消（同时解除禁止）。
2. **通知地址不可达**：部署主机访问不到用户的地址时，执行记录会持续失败并告警。页面上的“发一条测试”在保存规则时就能发现问题。
3. **出站滥用**：通知地址由用户填写，靠 4.3 的防护兜底。默认禁止内网地址。
4. **EventBus 凭据变更**：新增消费者要重新生成并下发凭据，漏一处服务就起不来。按第 10 节的顺序发布，C2 的验收要覆盖“全新安装能连上 EventBus”。
5. **交易所真撤销下架**：第一版不做自动撤销。交易所真撤销时，要靠用户在执行记录里手工取消，否则到 T − 24 小时会照常禁止买入并平仓。`delist_detected` 告警会提前提醒你。
