# v0.5.1 安装反馈优化方案

日期：2026-11-01
依据：用户反馈 `~/Downloads/moox反馈.md`、附件 `moox-v0.5.1-install-feedback-2026-11-02.zip`（补丁和测试摘录）
前置文档：[安装收尾与线上验收执行计划](安装收尾与线上验收执行计划.md)

## 1. 结论

- 反馈的 4 个主要问题全部属实，代码里都能对上。其中 3 个会挡住所有新用户：新电脑过不了 SSH 配置页；`setup install` 必定崩溃；Host Agent 在 EventBus 装好之前会退出。
- v0.5.1 不能直接完成全新安装。用户是改了代码才装成功的。
- 根本原因不在单个 bug：`setup install` 发布前没有用真实依赖在真机上跑通过。测试全部注入假依赖，真机验收排在了发布之后。这次用户反馈就是那次被推迟的验收。
- 反馈之外还查出 3 个问题：同样的启动定时器问题还在另外 7 个定时器上；已经装好的用户不会自动补上防火墙规则；CNB 上的 v0.5.1 只有 7 个附件，缺 11 个。
- 建议发 v0.5.2 一次修完。发布流程改成先真机装通，再把安装文档指向新版本。线上重装不再用 v0.5.1。

## 3. 为什么发布前没发现

| 漏洞 | 这次漏掉了什么 |
| --- | --- |
| 安装测试注入的是假依赖 | 假依赖把两个回调都填上了，真实入口没填，所以测试全过，真机崩溃 |
| SSH 配置页的测试用假探测 | 真实的 `Dial` 从没在空 HOME 下跑过；维护者的电脑上指纹文件早就存在 |
| 真机验收排在发布之后 | 阶段五、六等线上重装才做，v0.5.0 和 v0.5.1 都先发布了 |
| 长期运行的线上环境掩盖了启动顺序问题 | 线上 EventBus 一直在，Host Agent 从没在它不在时启动过 |
| 同一件事有两套算法 | Monitor 按完整拓扑探测，防火墙只看用户声明的组件 |
| `setup verify` 只查数据 | 告警还有 4 条 critical，安装已经报 `installed` |
| 文档命令靠人工核对 | 上一轮的完成标准只核对了 `setup` 子命令 |
| 发布核对看错了退出码 | CNB 脚本打印 `cnb=1`，外层任务退出码是 0 |

下面每一项都分两部分：这次的修复，以及防止同类问题再出现的检查。

## 4. 方案

### P0：必须进 v0.5.2

#### 4.1 依赖补全集中到一处

**问题。** `bootstrapAdmin`、`bootstrapControl` 的默认值写在 `newSetupBootstrapCommand` 里，只改了它自己的副本。`setup install` 拿到的是另一份，两个字段都是空的。

**修复。** 不照补丁只加两行。把散落在各子命令里的默认值全部移进 `defaultSetupDeps`，`completeSetupDeps` 用一个地方补全，原处的判空删掉。涉及 `setup_bootstrap.go`、`setup_install.go`、`setup_deploy_host.go`、`setup_deploy_unit.go`、`setup_release.go`、`setup_restart.go`、`setup_logs.go`、`setup_wipe.go`。

**防复发。** 用反射写一个测试：`completeSetupDeps(setupDeps{})` 之后，`setupDeps` 的所有函数字段都不能为空。以后加字段忘了给默认值，测试直接失败。

#### 4.2 启动时立即执行的定时器不能因为错误退出

**问题。** 定时器库在 `startAtOnce` 时把第一次执行的错误返回给 `ListenAndServe`，服务随之退出；之后的周期只记日志。

```text
配置了 startAtOnce 的定时器：
  hostagent 采样
  monitor   metrics、data_cleanup、check_schedule、host_silence
  archive   metrics
  factor    metrics
  strategy  metrics
```

`report.Handler` 连不上 EventBus 时返回错误，`timerjob.Job.Handle` 也原样返回错误。所以其余 7 个定时器有同样的风险。新安装时它们排在 EventBus 之后，暂时碰不到；但 EventBus 所在主机不可用时重启这些服务，它们会反复退出。

安装顺序不用改：EventBus 单元依赖主机单元里的 `moox-runtime`，主机单元必须在前。要改的是服务对依赖未就绪的容忍度。

**修复。** 在 `packages/timerjob` 加一个包装函数：执行失败时记录警告和指标，向定时器返回 nil。8 处注册都改用它。Host Agent 的健康状态逻辑按补丁保留：EventBus 不可用时进程运行、`/readyz` 返回 200；必需的采集失败时 `/readyz` 返回 503。

**防复发。** 在 `scripts/check/` 加一项检查：配置了 `startAtOnce` 的定时器服务，注册时必须走这个包装函数。

#### 4.3 防火墙规则和 Monitor 探测目标用同一份拓扑

**问题。** `healthProbeFirewallRules` 遍历 `manifest.Deployments`，只有用户声明的业务组件。Host Gateway 和 Host Agent 是 `Manifest.Topology()` 自动补入的，Monitor 按完整拓扑探测，防火墙却没放行。

**修复。**

1. 采用补丁，改为遍历 `manifest.Topology().Deployments`。
2. 现在 `Topology()` 和目录加载失败时都 `return nil`，等于悄悄少放行规则。改成把错误传出去。
3. 已经装好的用户：`setup_install.go:140` 在 upgrade 路线没有待办时直接返回 `installed`，不会补新规则。发布说明写明运行 `setup firewall --yes`。

**防复发。** 加对照测试：在直连、同地域私网、出站三类主机的拓扑上，算出 Monitor 走公网探测的每个目标，逐一确认有对应的放行规则。

其余用到 `Deployments` 的地方已逐个看过：`deployscan.hostPorts` 单独处理了主机服务，`adminRequest` 等几处本来就只要业务组件，不用改。

#### 4.4 SSH 指纹库首次使用

**问题。** `Dial` 用 `create=false` 检查指纹文件，文件不存在时返回 `ErrHostKeyStoreInvalid`。`Login` 把这个错误报成“连不上”，页面到不了指纹确认那一步，而创建文件的 `TrustHost` 排在后面。

**修复。**

1. `Dial` 改成指纹文件不存在就创建空文件（目录 0700、文件 0600）。空文件里没有任何可信主机，未知主机照样要用户确认，安全性不变。
2. `Login`、`Authorize` 遇到 `ErrHostKeyStoreInvalid` 时，用 `Trust` 里那条可重置的提示。
3. “连不上”只留给 `ErrUnreachable`，其他错误显示真实原因。

**防复发。** 现有的 `setup/ssh/client_test.go` 已有测试 SSH 服务器。加端到端测试：空 HOME 下用真实的 `systemProber` 走完“未知主机 → 确认指纹 → 登录”。再覆盖文件权限不对、文件损坏两种情况。

#### 4.5 文档和提示里的命令

**问题。** `collector kline status` 不存在。`status`、`fetch-plan` 直接挂在 `collector` 下（`collector_kline.go:180`）。

**修复。** 改成 `collector status --space-id <空间>`：

| 文件 | 行 |
| --- | --- |
| `skills/moox/SKILL.md` | 73 |
| `skills/moox/references/install.md` | 203、266、267 |
| `skills/moox/references/fresh-deploy.md` | 102 |
| `modules/cli/internal/command/setup_verify.go` | 82 |
| `modules/cli/internal/command/collector_subjects.go` | 32 |
| `modules/collector/internal/rpc/ingest_mode.go` | 102 |

**防复发。** 加测试：从 `skills/`、`docs/`、README 和 CLI 错误提示里抽出 `moox-cli ...` 命令，用 `rootCmd.Find` 解析，解析不到就失败。

#### 4.6 安装验收加上 Monitor 健康检查

**问题。** 这次 `setup verify` 通过了，同时还有 4 条 critical 告警。用户要自己多跑一次 `doctor alerts` 才知道。

**修复。** `verify.Input` 增加 Monitor 总览，`Evaluate` 增加 `monitor` 检查，数据来源和 `doctor alerts` 相同（`GetHealthOverview`）。

| 状态 | 处理 |
| --- | --- |
| 没有 critical | 通过 |
| 有 critical，还在验收时限内 | 等待，给首轮探测和新数据留时间 |
| 到时限还有 critical | 失败，列出主机、组件和端口 |
| 远程健康检查超时 | 提示运行 `setup firewall --yes` |

这一项是其他问题的兜底：只要组件在反复退出、端口没放行或探测失败，安装都不会报 `installed`。

风险：误报会把成功的安装判成失败。上线前要在真机上看一遍时限（目前 6 分钟）够不够，只有 critical 才判失败。

### P0：发布流程

#### 4.7 先真机装通，再改安装文档

```text
构建产物
  → 发到 GitHub（标记 Pre-release）和 CNB
  → 核对附件数量和哈希
  → 新目录、干净 HOME，用发布产物跑 config init 和 setup install
  → setup verify 通过，doctor alerts 为 HEALTHY
  → 把 install.md 的 VER 改成新版本，GitHub 标记为最新
```

这样即使真机验收失败，用户照文档拿到的还是上一个版本。失败时修好发下一个补丁版本，不覆盖已发布的附件。

CNB 发布脚本也要改。这次失败的原因是 `curl: (16) Error in the HTTP2 framing layer`，脚本只传一次，没有重试。

1. 把 `~/Downloads/moox-release-v0.4.0/cnb-release.py` 移进 `scripts/release/`，确认里面没有令牌。
2. 上传改用 `--http1.1 --retry 5 --retry-all-errors`。
3. 结束前读取 CNB 上的附件，按 `SHA256SUMS` 比对数量和哈希，不齐就返回非零。

v0.5.1 不再补传。它装不通，补齐附件没有意义，用 v0.5.2 替代。发 v0.5.2 时在 GitHub 的 v0.5.1 Release 上加一条已知问题，CNB main 同时同步（现在还停在 `972d3e61`，缺 #103）。

### P1：小改动，随 v0.5.2 一起做

#### 4.8 部署目录不可写

报错里直接给出可以运行的命令：

```text
sudo install -d -o <SSH 用户> -g <SSH 用户组> -m 0755 /data/moox
```

不自动执行 sudo，由用户决定。`install.md` 的前置条件里说明自定义根目录的权限要求。

#### 4.9 Host Agent 就绪后再看一次

反馈里海外机先报告就绪，随后才退出。4.2 修好后这个具体问题就没了，但“就绪过一次”仍然不等于稳定。`deploy-host` 判定就绪后，隔几秒再确认一次进程号没变。先在真机上量耗时，增加的时间不超过 15 秒才做；否则由 4.6 兜底。

#### 4.10 新安装预热提示

`insufficient_closed_bars` 只改告警文字，说明新装后几分钟内属于正常现象。4.6 里把它算作等待。不给 Monitor 加“安装中”状态。

### P2：只写文档或小修

| 事项 | 处理 |
| --- | --- |
| 版本绑定 | 在部署文档里说明：产物包和 CLI 版本必须一致，改代码自行构建时保留版本号，用文件名和构建提交区分 |
| 来源提交 | `cleanCommit` 有 `.git` 时走 Git 检查，只有在产物包目录（没有 `.git`）才读 `moox-bundle.json` |
| SSH 登录方式 | SSH 配置页说明自定义密钥要用 `ssh -i ~/.ssh/moox_ed25519`，普通 `ssh` 询问密码不代表公钥没装上 |
| 路线 resume 变 upgrade | 不改 |

| 步骤 | 内容 | 产出 |

| 2 | 新 Agent 做代码审查，修完合并 | main |
| 3 | 4.7 的 CNB 脚本改造 | 随 PR 或单独 PR |
| 4 | 发 v0.5.2（Pre-release），核对 GitHub 和 CNB 的 18 个附件 | Release |
| 5 | 新目录、干净 HOME 跑配置页；线上重装（用户确认清除后） | 真机结果和各阶段耗时 |

| 8 | 接原计划阶段六的流程验收 | 验收记录 |

线上是四台主机，有只能出站的因子机；反馈是三台，没有因子机。两边合起来覆盖了主要拓扑。

## 7. 完成标准

- 一台新电脑、干净的 HOME，按 `install.md` 走完，不需要改代码、手工建文件或手工补防火墙。
- `setup install` 返回 `installed` 时，这个空间和各组件、主机没有 critical 问题，验收连续两轮通过。
- 第 4 节的每条防复发检查都进 CI，并确认在修复前的代码上会失败。
- CNB 和 GitHub 的附件数量、哈希一致，脚本结果可信。

## 8. 决定不做

| 事项 | 原因 |
| --- | --- |
| CI 里用容器搭完整的多机安装 | 依赖腾讯云接口，要做假云服务，投入大；4.1～4.6 的检查加一次真机安装已覆盖这次的问题 |
| 调整安装顺序 | EventBus 依赖主机单元，顺序本身没错 |
| 自动执行 sudo 创建部署目录 | 改服务器权限应由用户决定 |
| Monitor 增加“安装中”状态 | 为几分钟的预热加状态，不值得 |
| 放宽版本绑定 | 正常用户碰不到，放宽反而可能混用版本 |
