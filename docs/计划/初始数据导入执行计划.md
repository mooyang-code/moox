# 初始数据导入执行计划

2026-10-25 · v1（待 Codex 审查） · 分支 `perf/storage-write-path`（基于 `feat/swap-history-ema50000`）

## 0. 目的

**初始数据导入**是指：一个数据源（空间 + 数据集 + 频率）第一次接入时，把用户提供的历史 K 线一次性灌进系统，让因子从第一期起就有完整的长回看，而不是上线后再等实时数据慢慢积累。典型场景是 EMA(50000) 这类需要 5 万根历史的因子：5m 要 173 天、1m 要 34 天，等实时积累不现实。

这件事要同时满足四点：

1. **快**：几百个标的、几千万行，小时级以内导完并追平实时，而不是半天。
2. **不扰动线上**：导入期间实时采集、因子、策略照常运行，Storage 与 View 不被打出数小时的积压。
3. **只导数据**：导入不触发历史因子与策略结果的计算，不推送告警；需要历史结果时由人手动补算。
4. **可校验**：导完能确认每个标的的边界与行数和文件一致，与实时数据无缝衔接。

## 1. 背景：2026-10-25 第一次实操的问题

把 `crypto-binance-swap-candle-moox` 的 5m 合约历史（501 个标的 × 最近 6 万根，约 3000 万行）导入线上，用的是现有 `moox-cli import --target storage,factor`：

| 问题 | 实测 |
| --- | --- |
| 导入慢 | 约 3 小时 20 分；Storage 主机（4 核）被打满（primary 约 190%、node 约 100%、view 约 100% CPU），并发 4 路与 8 路几乎同速 |
| View 积压 | 5m K 线 View 约 1100 行/秒，3000 万行要 8 小时以上；期间实时 5m 周期被积压挡住，策略只能跳过过期周期 |
| 白写 | View 每序列只保留 1 万根，导入的 6 万根全部写进 View 再等重建丢弃（约 83% 无用功） |
| 误触发计算 | 启用策略实例时自动提交 5000 期因子补算，又往 Storage 写了约 250 万行结果，进一步加重 View 积压 |
| 告警刷屏 | 积压期间 Monitor 对 5m View、策略结果持续推送 critical 告警 |
| 保留期 | 为装下 6 万根，把 5m 保留期从 35d 临时调到 240d |

而因子机本地存储只写 6 万行只要 4.7 秒（Storage 要 24 秒），并且 6 路并行几乎线性加速。网络也不是瓶颈：Mac 到存储机实测 4.4 MB/s，导入只用了不到 0.3 MB/s。

## 2. 已确认的决定

| # | 决定 |
| --- | --- |
| 1 | **两层写入**：因子机本地存储写全量历史并永久保留；Storage 与 View 只写最近 **W = 6000** 根（View 窗口 1 万根，之后由实时写入逐步补满） |
| 2 | 导入包由用户按第 3 节的格式整理；每个文件**最后一根早于“现在 − 2 天”**（N = 2），缺口（最后一根到现在）不超过 30 天，由采集补采接上 |
| 3 | 校验只比**边界与行数**（因子机本地、Storage 窗口），不做内容对账 |
| 4 | 流程写成 **skill 里的手动步骤**（`skills/moox/references/initial-import.md`），由 Agent 按步骤执行，不新增编排命令 |
| 5 | 导入包与 `moox-cli` 用 **rsync** 传到因子机，在因子机本机执行导入；并发数按目标机器的核数与内存在导入前计算 |
| 6 | 导入期间开启 **Monitor 全局告警屏蔽**（一段时间，到期自动恢复），只停推送、不停评估与记录 |
| 7 | **历史因子默认不补算**：启用因子成员（含策略实例的私有因子集）不再自动提交补算，需要时用 `recalc` 手动指定范围 |
| 8 | 策略实例启用时的 `min_age_bars` 检查**改看源 K 线 View**，不看私有因子结果 View（后者在不补算时刚启用为空） |
| 9 | Storage 写入路径的 **Node 与 View 优化本期完成**（第 6 节），并以基准测试量化 |
| 10 | 5m 保留期**恢复默认 35d**：Storage 只需装下 W 根（6000 根 5m ≈ 20.8 天） |

### 关于“在存储机本机写入”

讨论中提过把导入包和 CLI 也传到存储机、在本机写 Storage。实测网络不是瓶颈，Storage 侧的耗时全部在 Primary 校验、Node 写 Pebble 与 View 写 DuckDB，与写入位置无关；另外 `moox-cli import` 的 Storage 目标经操作员 SSH 网关写入，需要 `moox.toml`（加密）与 Storage 角色签名，放到存储机上要新增一套本机写入身份。因此本期 **Storage 窗口仍从操作机写**（W = 6000 时约 300 万行），只把因子机本地导入放到因子机本机。

## 3. 导入包格式

```text
import-pack/
  manifest.json
  <freq>/<SUBJECT>.csv          例如 5m/BTC-USDT.csv；文件名（去掉 .csv）即标的 ID
```

**CSV**

- UTF-8、无 BOM、LF 换行，首行为表头：`data_time` 加数据集的**全部字段**（如 `open,high,low,close,volume,quote_volume,trade_num`）。
- `data_time` 为 K 线开盘时间，UTC RFC3339（例如 `2026-01-01T00:00:00Z`），严格升序、无重复、对齐频率网格。
- 数值按字段类型（double / int）书写；序列内部允许缺周期，因子机本地按字段的 `fill` 规则填成带标记的填充行（`--allow-missing`），Storage 不写填充行。

**manifest.json**

```json
{
  "space_id": "crypto",
  "dataset_id": "dataset_dbelsl2vka4d2219crv0",
  "freq": "5m",
  "series_tag": "venue:binance|market:swap|source:swap_http",
  "files": [
    {"subject_id": "BTC-USDT", "file": "5m/BTC-USDT.csv", "rows": 60000,
     "first_utc": "2026-03-25T16:00:00Z", "last_utc": "2026-10-19T23:55:00Z", "sha256": "…"}
  ]
}
```

`series_tag` 必须与实时采集写入的完全一致（同一序列的历史与增量才会接成一条），预检用目标数据集已有的行核对。

**硬约束（预检强制）**

1. 每个文件 `last_utc` < 现在 − 2 天；`现在 − last_utc` ≤ 30 天。
2. 行数 ≥ 该数据源的回看数量 N（因子机 `window.lookback` 或 `lookback_overrides`）。
3. 标的必须已在数据集的标签里（不在的直接报错，不静默跳过）。
4. 字段与类型和数据集严格一致；`sha256`、行数、首尾时间与文件一致。

## 4. 操作流程（写入 skill）

前置：数据集与采集任务已建好（K 线数据集由采集任务创建）、标签成员已就绪、实时采集已在写入。

1. **预检**（操作机）：`moox-cli import --manifest-pack <包> --dry-run`，按第 3 节逐项检查，输出每个标的的行数、首尾时间、到现在的缺口天数和预计耗时。
2. **屏蔽告警**：`moox-cli monitor mute --for 3h --reason 初始数据导入`。
3. **补缺口**（操作机）：`moox-cli collector kline backfill --force --dataset-id <数据集> --from <文件末根 + 1 期> --to <实时起点>`，等作业全部成功（失败分块用 `backfill-retry`），用 `collector kline check` 确认区间齐全。
4. **因子机本地全量**：
   - `rsync -a import-pack/ moox-cli-linux 因子机:<导入目录>/`；
   - 在因子机上算并发：`P = clamp(核数 ÷ 2, 2, 32)`，再按“可用内存 ÷ 0.5 GiB”取下限；
   - 先单标的试跑记录耗时，再 `xargs -P $P` 逐文件执行 `moox-cli import --target factor --allow-missing --series-tag <tag> --path <文件>`（引擎地址 `127.0.0.1:11417`，鉴权密钥取自本机 `secrets/health-auth.env`，不需要 `moox.toml`）。
5. **Storage 窗口**（操作机，可与第 4 步同时进行）：`moox-cli import --target storage --tail-rows 6000 ...`，逐文件执行；Storage 写入在 DataNode 内串行，操作机并发 2～4 即可。
6. **校验**：
   - 因子机本地：每个标的的本地最早、最晚时间与 manifest 一致，`最晚` 之后由同步器从 Storage 接上（补采段）；
   - Storage：每个标的在 `[文件倒数第 6000 根, 现在]` 内的行数 = 6000 + 补采行数 + 实时行数；
   - View：滞后为零（Monitor 该 View 恢复正常）。
7. **解除屏蔽**：`moox-cli monitor unmute`（到期也会自动解除）；解除时若仍有未恢复的告警，Monitor 补发一条汇总。
8. **启用**：建因子集或策略实例。启用不再自动补算，因子从启用那一期开始计算；需要历史因子值时用 `moox-factor-mgr-cli recalc` 指定范围。

## 5. 功能改动

### 5.1 导入命令（`modules/cli/internal/command/import.go`、`packages/seriesimport`）

- `--tail-rows N`：每个文件只取最后 N 行（只对 storage 目标生效；同时写 storage 与 factor 时 factor 仍取全量，storage 取尾部）。
- `--manifest-pack <目录>`：按 manifest 读取空间、数据集、频率、`series_tag` 与文件清单，并做第 3 节的硬约束检查；`--dry-run` 只做检查。
- 去掉 `import_retention.go` 的“早于保留期”警告逻辑对 factor 目标的误报（只在 storage 目标且未用 `--tail-rows` 时检查）。

### 5.2 Monitor 全局告警屏蔽（`modules/monitor`）

- 表 `t_monitor_mutes`（单行：开始、结束、原因、操作者），按 `schema/*.sql` 规范直接加；最长 24 小时。
- 推送出口：`alerting/evaluator.go` 的告警通知、`hostmetrics/alerts.go` 的主机指标告警、`bootstrap/host_presence.go` 的主机失联通知，三处在发送前检查屏蔽；屏蔽期间事件照常记录，标记“已屏蔽”。
- 到期或解除时，汇总仍未恢复的告警补发一条。
- 接口 `SetMute` / `ClearMute` / `GetMute`；CLI `moox-cli monitor mute --for <时长> --reason <原因>`、`moox-cli monitor unmute`；首页显示“告警已屏蔽至 HH:MM”。
- 不在范围：Admin 证书检查、主机守护（`moox-runtime watch`）的直推告警。

### 5.3 历史因子默认不补算（`modules/factor`）

- `catalog/service.go`：启用成员时不再自动提交 `factor-enable-` 补算（删除 `DefaultMaxBackfillPeriods` 与相关合并逻辑）；`SetFactorMemberStatusRsp.backfill_job` 一并删除。
- 手动补算 `recalc` 不变。
- 文档：`docs/模块/因子.md` 的“启用成员会原子提交一次补算”改为“启用不补算”。

### 5.4 策略启用检查（`modules/strategy/internal/input/resolve.go`）

- `checkAgeCoverage` 对声明了 `factors` 的实例改用 `source_view_id`（K 线 View）的覆盖范围判断 `min_age_bars`。
- 因子值从启用那一期开始才有；启用后的前几期，策略对缺因子值的标的按现有缺数规则处理（`max_missing` 守门）。

### 5.5 保留期

- 线上 Storage 三个角色的 `storage-policy.json` 与本机 `moox.toml` 的 `defaults."5m"` 恢复为 35d（840h）。
- 注意：恢复后，本次已导入 Storage 的 35 天之前的 5m 行会在下一次清理时删除，这是预期结果（因子机本地仍保留全量）。

## 6. Storage 写入路径优化

### 6.1 实测（本机 Apple M4，按导入形态复现，基准默认跳过、设环境变量运行）

| 环节 | 改法 | 改前 | 改后 | 状态 |
| --- | --- | --- | --- | --- |
| View 写入，导入形态（每批 4000 行，表里已有 300 万行） | 每列整体绑定成一个 LIST 参数、`unnest` 展开，一批两条 SQL（先按新键累加计数，再整批 UPSERT） | 8205 行/秒 | 94741 行/秒（11.5 倍） | 原型在 `viewindex/duckdb/import_write_bench_test.go` |
| View 写入，实时形态（每批 500 个标的各一行） | 同上 | 6331 行/秒 | 28823 行/秒（4.5 倍） | 同上 |
| Primary 逐行元数据校验（1000 行请求，元数据 2000～10000 条） | 每个请求按 (space, dataset) 只查一次 | 每请求 39～109 ms | 0.03～0.16 ms | 已实现（`primarystore/metadata_validator.go`） |
| DataNode 写入（每请求 1000 行 × 7 字段，带事件，同步落盘） | KV 编码、事件构造与校验挪到 `outboxMu` 之外 | 2.8 万行/秒，并发 1/4/8 无差别 | 4～8 并发约 3.5 万行/秒（+25%） | 已实现（`datanode/pebble/store.go`） |
| DataNode 组提交（锁内只应用、锁外等 fsync） | `ApplyNoSyncWait` + `SyncWait` | — | 无收益 | 已撤掉：瓶颈在 Pebble 压缩与 GC；且“未落盘先可见”会让中继和变更跟进读到可能丢失的写入 |

**换算到线上（估算，待上线实测）**：线上 View 实测约 1100 行/秒，是本机现状的约 1/7.5；按同比例改后约 1.2 万行/秒，W = 6000 时 300 万行的 View 消化从约 45 分钟降到 4～5 分钟。线上导入时每个 1000 行请求约 0.4 秒，逐行校验在本机就占 39～109 ms，线上占比更高，去掉后 Storage 写入预计提速明显，具体倍数待实测。

### 6.2 为什么不去掉锁、不把 View 改成并行

- **DataNode `outboxMu`**：outbox 事件编号与变更日志序号必须按提交顺序连续——事件中继按编号顺序发布，因子引擎的变更跟进按序号游标读取；编号 N+1 先于 N 提交，读者会越过 N 造成漏读。所以锁保留，锁内只剩分配编号、绑定事件、写变更日志与提交。
- **View 同一数据集串行**：同一行的多次更新要按事件顺序应用；周期的“数据就绪”通知必须在该期全部行之后；每个 View 是一个 DuckDB 文件，并发写同一文件会冲突。先把单线程的每行成本降下来，收益确定、改动小；按标的分区并行改动大、风险高，本期不做。

### 6.3 View 正式实现要补齐的部分

原型只覆盖了导入形态的 double/int 列与实时写入（LiveWrite）语义。正式实现在 `viewindex/duckdb/index_manager.go` 的 `Write` 中替换 `ensureSeriesRowsAndCounts` 与每 32 行一条的 UPSERT：

- 全部字段类型的 LIST 绑定：string、int、double、bool、time、json、bytes；NULL 值。
- 回填模式（Backfill）的 `COALESCE(view_rows.x, excluded.x)` 只补空值语义。
- 内部属性列 `__moox_attributes` 的 JSON 合并（实时与回填两种方向）。
- `batch.RowWrites` 已按键合并（`collapseRowWrites`）的前提下，同批无重复键；保留现有“重复键约束错误时逐行重试”的兜底。
- 计数：只对新键累加 `view_series_counts`（与现状 `RETURNING` 的结果一致）。
- `view_meta` 的 `indexed_from` / `indexed_to` 维护不变；DuckDB 参数个数与单条语句大小上限下的分批（按行数上限切批）。
- 测试：现有 `index_manager_test.go`、`series_window_test.go` 等全部通过；新增新旧实现对同一批输入（新键、已存在键、混合、回填、含 NULL、含属性）写出完全相同表内容的对照测试。

### 6.4 可选（本期视时间）

- 事件构造去掉 protojson 往返（`eventmapper.ToEventRows`）：profile 中占 DataNode 写入 CPU 的一大块，未单独量化。
- View 追赶期间把 K 线数据集消费者的 `fetch_batch` 从 4 调大（如 16），同时调大 `max_ack_pending`。

## 10. 请审查重点关注

1. 两层写入下，因子机本地（全量）与 Storage（尾部 6000 根）的衔接是否会被同步器误判：`Follow` / `Pull` / `reconcile` 只比对“本地范围 ∩ Storage 现存范围”，Storage 早于窗口的部分为空，本地早于 Storage 最早一根的历史是否一定不受影响。
