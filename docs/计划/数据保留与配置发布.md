# 数据保留策略与配置发布：执行计划

> 状态：待评审，尚未编码。
> 范围：Dataset 原始数据按「空间 × 频率」保留、View 按 bar 数保留、每个 Dataset 只有一个频率、
> 新增 `moox-cli config` 配置发布命令。项目尚未上线，不做任何历史兼容。

## 1. 已确认的决策

| # | 决策 |
| --- | --- |
| 1 | 在线量化系统，不需要长期数据；不部署 Archive，过期数据直接删除 |
| 2 | 每个时序 Dataset 只有一个频率 |
| 3 | 保留期按「空间 × 频率」配置：全局默认表 + 空间覆盖；Dataset 和 View 上不再保存保留字段 |
| 4 | 配置写在 `moox.toml`，由 `moox-cli` 渲染并分发到各主机的模块配置文件 |
| 5 | View 只按 bar 数保留：每个序列保留最近 5000 根，超过 6000 根时整理 |
| 6 | 保留期取值见第 3.3 节（stockcn 1m 45 天，stockhk/stockus 1m 30 天，mooxsys 30s 48 小时） |

## 2. 现状与问题

| 问题 | 位置 |
| --- | --- |
| Dataset 只有一个 `keep_duration`，`0` 表示永久；Collector 任务未设置时默认 `0`，crypto 全部永久保留 | `collector/internal/planner/taskresult/result.go`、`storage/cmd/server/main.go`（`cleanupDatasets` 跳过 `0`） |
| 一个 Dataset 可以有多个频率（`freqs`），共用一个保留期；stockhk/stockus 种子把 1m/1d/1w/1M 放在一起 | `storage/proto/metadata.proto`（`repeated string freqs`）、`config/setup/metadata.yaml` |
| 频率名不统一：任务配置的 `1H` 被原样写入 Dataset，月线用 `1M`，与命名规范的 `1h`、`1mo` 不符 | `config/setup/collection-tasks.yaml`、`collector/internal/marketdata/frequency.go` |
| View 同时有时间型保留（`keep_duration`、`rebuild_lookback`）和 bar 数保留（`rebuild_lookback_periods`、`max_periods_per_series`），另有 `system_monitor` 和逐 View 覆盖 | `storage/internal/service/view/maintenance.go`、`moox.toml [storage_view]` |
| View 的频率写在 `filter_json.freq`，与 Dataset 的频率重复 | `storage/internal/service/catalog/metadata_space_view.go` |
| `moox.toml` 中的配置只在打包部署时注入（例如 `MOOX_STORAGE_VIEW_MAINTENANCE_POLICY_B64` → `maintenance.json`），修改配置必须重新部署 | `cli/internal/setup/deploy/deploy.go`、`scripts/deploy/deploy-moox.sh` |
| 清理时先逐个遍历过期 key 统计桶数（只用于返回值），过期数据越多越慢 | `storage/internal/service/datanode/pebble/cleanup.go` |
| 回填时每个标的读完全部历史（翻页到底，且每页都扫描整个序列），历史越长越慢 | `storage/internal/service/view/build.go`、`datanode/pebble/history.go` |

已有可复用的能力：Storage 主进程每小时执行一次过期清理（`runCleanupLoop` → DataNode
`CleanupExpiredBuckets`），按天分桶用 DeleteRange 删除并立即压缩该范围，磁盘空间会回收；
`moox-cli` 已有 SSH 客户端、主机指纹信任库、按角色划分的主机配置（control/storage/view/strategy/other）
和 Collector、Trade 运行配置的渲染函数。

## 3. 目标设计

### 3.1 频率规范

新增共享包 `packages/frequency`，Storage、Collector、Factor、CLI 共用；前端 `web/src` 同步一份常量。

- 规范频率：`30s`、`1m`、`5m`、`15m`、`30m`、`1h`、`4h`、`1d`、`1w`、`1mo`。
- `Parse` 接受常见别名并返回规范值：`1H`/`60m` → `1h`，`1M`（月）→ `1mo`，`1D` → `1d`。
- 提供每根 bar 的时长（`1mo` 按自然月，无固定时长）。
- Storage 只接受规范频率，非规范值直接拒绝；别名转换只在输入边界（任务配置、CLI、页面）做。
- 交易所接口的写法（例如 Binance 月线 `1M`）只留在采集源适配层。

### 3.2 每个 Dataset 一个频率

- `Dataset.freqs`（repeated）改为 `Dataset.freq`（string，时序 Dataset 必填）。`t_datasets.c_freqs_json`
  改为 `c_freq`。
- 记录型（record）Dataset 不受保留策略约束，`freq` 可以为空。现有的 `quarter` 是描述性取值，保留不动。
- View 的频率由所属 Dataset 决定，去掉 `filter_json.freq`。View ID 中的频率后缀保留不变。
- 命名规范同步修改：时序 Dataset 的 ID 携带频率。
  - 种子 Dataset 按频率拆分，例如 `dataset_stockhk_equity_kline_1m`、`dataset_stockhk_equity_kline_1d`。
  - 采集任务结果 `dataset_<task_id>` 不变，一个任务本来就只有一个频率。

### 3.3 保留策略配置

`moox.toml` 新增 `[storage_retention]`，取代 `[storage_view]` 中的 `rebuild_lookback_periods`、
`max_periods_per_series`、`system_monitor` 和 `views`：

```toml
[storage_retention]
view_bars = 5000                # 每个序列 View 保留最近 N 根；超过 ceil(1.2 × N) 根时整理

# 7×24 小时交易的空间（crypto 等，以及没有单独配置的新空间）
[storage_retention.defaults]
"30s" = "48h"
"1m"  = "7d"
"5m"  = "30d"
"15m" = "90d"
"30m" = "180d"
"1h"  = "365d"
"4h"  = "1095d"
"1d"  = "forever"
"1w"  = "forever"
"1mo" = "forever"

[storage_retention.spaces.stockcn]
"1m"  = "45d"
"5m"  = "240d"
"15m" = "730d"
"30m" = "forever"
"1h"  = "forever"
"4h"  = "forever"

[storage_retention.spaces.stockhk]
"1m"  = "30d"
"5m"  = "240d"
"15m" = "730d"
"30m" = "forever"
"1h"  = "forever"
"4h"  = "forever"

[storage_retention.spaces.stockus]
"1m"  = "30d"
"5m"  = "240d"
"15m" = "730d"
"30m" = "forever"
"1h"  = "forever"
"4h"  = "forever"

[storage_retention.spaces.mooxsys]
"30s" = "48h"
"1m"  = "180d"
```

规则：

- 生效保留期按频率逐项解析：空间覆盖优先，没有时用全局默认。全局默认必须覆盖 3.1 节的全部规范频率，
  否则校验失败，因此任何 Dataset 都有确定的保留期。
- 取值格式：`<n>h`、`<n>d` 或 `forever`。CLI 解析后渲染为 Go 时长（`168h`）或 `forever`。
- 覆盖校验：保留期必须不小于 `view_bars` 根 bar 所需的时长。
  - 7×24 空间精确计算，不满足则报错。
  - 有交易时段的空间按每日交易分钟近似（A 股按交易日历和 240 分钟，港股 330 分钟，美股 390 分钟），
    节假日会有误差，不满足只告警。
- 当前取值的覆盖情况：

| 空间 / 频率 | 保留期 | 约可覆盖 bar 数 | View 需要 |
| --- | --- | --- | --- |
| crypto 1m | 7 天 | 10,080 | 5,000 |
| crypto 1h | 365 天 | 8,760 | 5,000 |
| stockcn 1m | 45 天 | ~7,400（约 31 个交易日） | 5,000 |
| stockhk 1m | 30 天 | ~6,900 | 5,000 |
| stockus 1m | 30 天 | ~8,200 | 5,000 |
| stock 5m | 240 天 | ~7,900 | 5,000 |
| stock 15m | 730 天 | ~7,800 | 5,000 |
| mooxsys 30s | 48 小时 | 5,760 | 5,000 |

### 3.4 Storage 策略文件与清理

- `moox-cli` 把 `[storage_retention]` 和 `[storage_view]` 中剩余的维护参数（检查间隔、
  `max_view_file_bytes`）渲染为 Storage 主机上的一个文件：`<storage_root>/config/storage-policy.json`。
  `storage.yaml` 的 `maintenance_policy_file` 改名为 `policy_file`，`maintenance.json` 删除。

```json
{
  "retention": {
    "defaults": {"30s": "48h", "1m": "168h", "1d": "forever"},
    "spaces": {"stockcn": {"1m": "1080h"}}
  },
  "view": {
    "bars": 5000,
    "trim_bars": 6000,
    "maintenance_check_interval": "1m",
    "capacity_check_interval": "1h",
    "capacity_check_jitter": "1h",
    "max_view_file_bytes": 1073741824
  }
}
```

- storage-primary 和 storage-view 启动时都加载并校验该文件，非法则拒绝启动。
- 清理循环（storage-primary，每小时）对每个活跃时序 Dataset 按 `(space_id, freq)` 解析生效保留期：
  `forever` 跳过；否则 `cutoff = now - 保留期`，按天桶截断后删除。实际保留期在 N 到 N+1 天之间。
- 去掉清理前逐个遍历过期 key 统计桶数的扫描，直接 DeleteRange 后压缩。
- 每次清理按 Dataset 记录日志和指标：cutoff、删除的范围、耗时；Pebble 磁盘占用上报 Monitor。
- Metadata 接口（`GetDataset`、`ListDatasets`、`DatasetSummary`）返回只读的 `retention`（生效保留期）
  和 `retention_source`（`default` / `space`），供 Collector、Factor 和页面使用；写接口不再接受保留字段。

### 3.5 View 只按 bar 数保留

- 删除 `View.keep_duration`（proto、`t_views.c_keep_duration`、页面）、storage-view 的时间型
  `rebuild_lookback`、`system_monitor` 特例和逐 View 覆盖。
- 重建目标为每个序列最近 `view.bars` 根；容量整理阈值为 `view.trim_bars`。
- 回填只读需要的窗口：
  - DataNode 按序列历史索引（subject, freq, tag, time）在每个 tag 内倒序读到目标根数就停止，
    然后跳到下一个 tag；
  - 回填循环某个标的读满目标根数后不再翻页。
  - 耗时与历史长度无关，只与「标的数 × 目标根数」有关。
- 记录型 View（Bleve）不按 bar，全量重建；记录型 Dataset 本身也不过期。

### 3.6 依赖保留期的模块

| 模块 | 现状 | 改为 |
| --- | --- | --- |
| Collector 采集任务 | `result_config.keep_duration` 写入 Dataset | 删除该字段（proto、页面、默认值），保留期由 Storage 策略决定 |
| Collector 重采样 | `kline_resample.target_keep_duration` 写入目标 Dataset 和 View；用源 Dataset 保留期判断回补窗口 | 删除 `target_keep_duration`；回补窗口校验读取源 Dataset 的只读 `retention` |
| Factor | 结果 Dataset 复制源 Dataset 的保留期；按结果保留期计算回补窗口；对账比较保留期 | 不再设置和比较；需要窗口时读取只读 `retention` |
| CLI 元数据导入 / setup | 种子与 mooxsys Dataset 带 `keep_duration` | 删除字段；种子按单频率重写 |
| 前端 | 采集任务表单可填保留期；存储页面显示保留期 | 删除输入；Dataset 详情只读显示生效保留期和来源 |

### 3.7 配置发布命令 `moox-cli config`

用户修改 `moox.toml` 后，由 Agent（或用户）执行：

```bash
moox-cli config plan    --file ./moox.toml                # 渲染并对比，不做任何修改
moox-cli config publish --file ./moox.toml --yes          # 写入、重启受影响的服务并验证
```

设计要点：

1. **发布目标注册表**。每个目标描述：
   - 主机角色；
   - 文件路径（相对部署根目录）；
   - 渲染函数（输入快照和远端当前文件，输出新文件）；
   - 受影响的服务；
   - 是否含敏感信息。

   第一批目标：

   | 目标 | 主机 | 文件 | 重启服务 |
   | --- | --- | --- | --- |
   | Storage 策略 | storage_host | `config/storage-policy.json` | storage-primary、storage-view |
   | Collector 运行配置 | control_host | `collector/config/app.yaml` 中由 `moox.toml` 派生的段落 | collector |
   | Trade DNS 解析 | DNS 解析所在节点 | `trade/config/...` | trade |

   之后由 `moox.toml` 派生的配置都通过新增目标接入，不再各自走部署脚本。

2. **一条渲染路径**。`deploy-storage`、`deploy-service` 复用同一批渲染函数生成配置；
   部署脚本不再通过环境变量注入并自行写文件（删除 `MOOX_STORAGE_VIEW_MAINTENANCE_POLICY_B64`）。
3. **plan**：
   - 加载并校验 `moox.toml`；
   - 通过 SSH 下载各目标的远端文件，渲染并对比；
   - 输出 JSON：主机、文件、状态（未变 / 变更 / 远端缺失）、变更的键、需要重启的服务、告警。
   - 告警包括：保留期缩短（会立即删除数据）、覆盖校验告警、远端文件被手工改动（与上次发布不一致）。
   - 含敏感信息的文件只输出键名，不输出值。
4. **publish**：
   - 只处理有变更的目标，按主机顺序执行。
   - 每台主机的步骤：
     1. 取得 `<root>.maintenance.lock`，与部署、healthcheck 互斥；
     2. 写临时文件；
     3. 把当前文件保存为 `<file>.last`，只保留一份，每次覆盖，不会累积；
     4. 原子替换；
     5. 重启受影响的服务；
     6. 等待就绪探针。
   - 任一步失败：用 `<file>.last` 恢复并重启，报告失败并停止后续主机。
   - 重复执行是幂等的，未变更的目标不会触发重启。
5. **安全**：
   - 保留期缩短需要额外加 `--allow-retention-shrink`；
   - 不输出密码和密钥；
   - 只连接已信任指纹的主机；
   - `--only <target>` 可以只发布指定目标。
6. **Agent 使用**：skill 文档说明标准流程——修改 `moox.toml` → `config plan` → 向用户展示变更和告警 →
   用户确认后 `config publish --yes`（缩短保留期时再加确认参数）。
7. `moox-cli setup validate` 同时执行保留策略校验。

## 6. 生产迁移

不做兼容，按以下顺序一次完成：

1. **备份与停写**：在 Storage 主机取得维护锁，备份元数据库（迁移完成并验证后删除备份）。
2. **元数据迁移**（离线脚本，Storage 停止期间执行）：
   - 已有单频率的 Dataset：`freqs[0]` 写入 `freq`，删除保留字段。
   - crypto 1h 两个 Dataset（频率由 `1H` 改为 `1h`）：Primary 行键中带有频率，无法原地改名。
     做法是删除这两个 Dataset 的 Primary 数据并重建 View，再把采集任务改为 `1h`，由实时采集重新累积。
     现有约 1.5 天的 1h 数据会丢失。
   - stockcn/stockhk/stockus 多频率种子 Dataset（目前均无数据）：删除后按单频率重新导入。
   - 其余 View 的列结构不变，不需要重建索引。
3. **部署新版本**：Storage、Collector、Factor、CLI、web-host。
4. **发布配置**：在 `moox.toml` 写入 `[storage_retention]`、删减 `[storage_view]`，执行 `moox-cli config plan`
   核对后 `config publish --yes`。本次没有缩短任何保留期：crypto 数据只有约 2 天，mooxsys 30s 由 24 小时
   改为 48 小时，不会删除数据。
5. **验证**（第 7 节）通过后删除备份。

- `moox-cli config plan` 在没有修改时输出「全部未变」；修改一个保留期后只显示对应条目，
  缩短时没有确认参数会被拒绝。

## 8. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 缩短保留期会立即删除数据，无法恢复 | plan 明确列出；publish 需要 `--allow-retention-shrink` |
| 发布到错误的主机或文件 | 目标由 `moox.toml` 的主机角色推导；plan 先列出主机与文件；只连接已信任指纹的主机 |
| 发布中途失败 | 每台主机单独替换并验证，失败用 `<file>.last` 恢复；后续主机不执行；重跑幂等 |
| 主机上手工修改的配置被覆盖 | plan 标出与上次发布不一致的文件；以 `moox.toml` 为唯一来源 |
| 有交易时段的市场覆盖计算不精确 | 只告警；取值已留余量 |
| crypto 1h 数据因频率改名丢失 | 已知且接受，约 1.5 天 |

## 9. 不在本次范围

View 重建加速另行处理（详见 View 重建耗时分析）：

1. 非因子 View 不读取因子溯源属性（kline View 约快 25%）；
2. 空 Dataset 跳过逐标的遍历；
3. DataNode 按行一次读取全部字段；
4. 按标的并发回填。

本计划的 P4 只包含「回填只读目标窗口」。
