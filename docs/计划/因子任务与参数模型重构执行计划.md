# 因子任务与参数模型重构执行计划

执行计划 v2.1（2026-10-26，尚未编码；v2 已过 Codex 复审，5 条意见见第 13a 节）。依据：[因子任务与参数模型重构设计](因子任务与参数模型重构设计.md)定稿（D1~D17、S1~S13），下文简称「设计」。
本计划只把设计拆成可以逐项执行、逐项验收的任务，不另做设计决策。遇到与设计不一致的地方，先改设计，再改本计划。

- **v1**：按设计拆成 12 个阶段、29 个任务。
- **v2**：吸收 Codex 审查（13 条问题、4 条与代码不符，见第 13 节）。
  - **提交边界**：
    - v1 的阶段 5~7（成员、参数、任务与绑定）互相依赖，拆开提交会编译不过，合并为一个「模型切换」阶段；
    - 阶段 1 的后端与前端改名合成一次提交；
    - 表达式规格与因子库合并；CLI 配置结构与 `setup factors`、迁移命令合并；
    - 每次提交都执行 `make test-go`。
  - **纠正**：策略实例在**第一次启用**时才绑定任务，创建时只保存任务 ID（设计 8.1）。
  - **补充任务**：
    - 周期标记的 Storage 侧协议与转换；
    - 补算作业记录「按默认参数新补的期次」；
    - 生命周期门禁（本地序列够不够预热、任务至少一个成员）；
    - 闭环回放；
    - 提交滞后告警的接线；
    - Monitor 按任务选择到达链；
    - 漏列的策略、CLI、前端文件。
  - **重写**：各阶段的残留检查，改用精确符号，并列出允许保留的命中。
  - **上线**：阶段 10 开始前，先写一份按主机填写的操作清单交用户确认。

## 0. 约定

- **原则**：只有一个超级用户，个人系统，不过度设计；项目未上线，表结构直接改 `schema/*.sql`，上线全新部署，不写迁移和回退。
- **分支**：从当前的 `feat/initial-import` 新建 `feat/factor-task-model`，阶段 1~9 都在这个分支上完成。
- **提交**：
  - **每次提交后，整个仓库都必须能编译，并通过 `make test-go`**（它会对 `go.work` 里的每个模块执行 `go test` 和 `go vet`）。改了前端的提交，还要在编译机上跑前端测试。
  - 能单独提交的任务就单独提交，提交信息写明任务编号。
  - 阶段 5「模型切换」的任务互相依赖：成员模型、参数接口、删除私有因子集、两侧 schema 和协议，必须一起改才能编译。所以这个阶段按任务顺序逐项编码、逐项自测，**等全阶段都能编译后再提交**，可以是一次提交，也可以是几次，但每次都必须满足上一条。提交信息列出包含的任务编号。
  - 中间提交只要求能编译、测试通过，**不要求行为完整**。整体行为以阶段 9 的全量验收为准。
- **协议**：修改 `.proto` 后执行 `make proto`，生成代码和改动一起提交。`make proto-check` 要求工作区干净，所以在**提交之后**再跑。
- **schema**：遵守 AGENTS.md 的「数据库 Schema 格式规范」。每个 schema 文件都要能单独载入空 SQLite 库，并通过 `git diff --check`。
- **前端**：测试与构建在编译机 `192.168.0.103:~/moox-web` 上执行（rsync 后跑 vitest、vue-tsc、vite build）。
- **构建**：不要在模块目录里不带 `-o` 执行 `go build ./cmd/x`，否则二进制会被 `git add` 提交进去。
- **清理**：涉及的文件顺手删掉死代码、只为旧行为存在的分支，以及过时的注释和测试（AGENTS.md「代码清理原则」）。
- **残留检查**：每个阶段末尾的 `rg` 检查一律用 `rg -n -F '<精确符号>'`，按单个符号逐条检查，并在计划里列出**允许保留的命中**。不使用含 `\b`、`\.` 的正则，避免在 shell 引号里转义出错。
- **上线前暂停**：阶段 9 的 Codex 代码审查处理完后**暂停**，等用户确认，再执行阶段 10。

## 3. 阶段 2：命名公共包

### T2.1 Go 包 `packages/factorname`

- **新建** `packages/factorname`。和 `packages/factorexpr` 一样，它有自己的 `go.mod`，并登记进 `go.work`；使用它的模块（factor、strategy、cli、monitor）在各自的 `go.mod` 里加依赖。
- **提供设计 5.1、5.2、5.5~5.7 需要的全部函数**：
  - 校验名字：因子 ID、输出名、参数名，以及输出名的附加约束（不是 `var`、不匹配值的语法、不等于因子 ID）；
  - 格式化参数值：`FormatFloat('f', -1)`，`.` 写成 `p`，`-` 写成 `n`；
  - 拼成员键：参数全为默认值时省略参数段，可变成员为 `<因子ID>__var`；
  - 拼列名：单输出因子没有输出段；
  - 解析列名：按 `__` 切成「因子 ID、固定或可变、参数段、输出名」，重新格式化后与原文比对，不一致判为非法；
  - 规范 JSON：`__params` 与 `factor_params`，键按字典序，数字用 JSON 数字，不带空白；
  - ID：`ftask_<后缀>`、`dataset_factor_<后缀>`、`view_factor_<后缀>` 的生成与反解，8 位随机后缀，自定后缀的校验（不超过 35 个字符）；
  - 长度上限。
- **测试向量** `packages/factorname/testdata/vectors.json` 覆盖：默认参数；小数；负数；`5e-324` 与 `1.7976931348623157e308`；可变成员；单输出与多输出；非法名字；两段式列名的判定；非规范写法 `01`、`1p0`。

## 5. 阶段 4：Storage 列契约

### T4.1 按 `column_kind` 分两类校验因子列

- **按类型分开校验**（`modules/storage/internal/service/catalog/metadata_catalog.go:597-612`）：
  - `output`：必须有 `factor_id`、`member_key`、`output_name`、`member_kind` 四个属性，值类型为 `double`；列名必须等于 `member_key`、`output_name` 按规则拼出的字符串。Storage 只比较字符串，不引用公共包。
  - `params`：列名必须是 `__params`，值类型为 `json`，每个结果数据集恰好一列。
- **View 列校验**（`catalog/validate.go:90-108,169-180`）：`isFactorViewColumn` 改用新属性，只把 `column_kind=output` 当作因子输出。默认 View 的列集合要包含 `__params`。
- **展示名**：重写 `validateColumnDisplayName`。它现在要求展示名等于 `factor_output`，改为：
  - 输出列：取「定义的中文名」，多输出时再加上输出名；
  - `__params`：取「因子参数」。
- **注释**：`metadata.proto:135` 和 `metadata.proto:376` 的旧注释改掉，然后 `make proto`。
- **测试**：
  - 两类列都能注册，属性缺失或不匹配时被拒绝；
  - 第二个 `params` 列被拒绝；
  - 默认 View 包含 `__params`，能写入并读回 `json_value`；
  - 展示名的新规则。

**阶段 4 验收**：`make test-go` 通过；在 `modules/storage` 范围内，`rg -n -F 'origin_factor_id'`、`rg -n -F 'factor_output'` 都没有命中。

### T5.4 参数提交、读取与告警

- `catalog/params.go`：
  - **`SubmitFactorParams`**：保留现有的 `request_id` 字段（`factor.proto:463`），重新定义它的幂等语义，并调整请求结构。在一个事务里依次完成：
