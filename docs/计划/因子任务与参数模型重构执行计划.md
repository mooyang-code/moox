# 因子任务与参数模型重构执行计划

执行计划 v1（2026-10-25，尚未编码）。依据：[因子任务与参数模型重构设计](因子任务与参数模型重构设计.md)定稿，含 D1~D17、S1~S13，下文简称「设计」。
本计划只把设计拆成可以逐项执行、逐项验收的任务，不另做设计决策。遇到与设计不一致的地方，先改设计，再改本计划。

## 0. 约定

- **原则**：只有一个超级用户，个人系统，不过度设计；项目未上线，表结构直接改 `schema/*.sql`，上线全新部署，不写迁移和回退。
- **分支**：从当前的 `feat/initial-import` 新建 `feat/factor-task-model`，阶段 1~11 都在这个分支上完成。
  - 每完成一个任务（`T*.*`）就跑它的测试并单独提交，提交信息写明任务编号。
  - **每次提交后，整个仓库都必须能编译、测试通过。**
  - 阶段 5~7 的任务互相牵连：协议、因子模块、策略模块要一起改才能编译。所以这几个阶段允许把相邻任务合成一次提交，但不能留下编译不过的中间状态。
  - 中间提交只要求能编译、测试通过，**不要求行为完整**，例如阶段 5 结束时私有因子集仍然存在。整体行为以阶段 11 的全量验收为准。
- **Go 测试**：仓库根目录和 `packages/` 都不是 Go 模块，不能用 `go test ./packages/...`。单个模块在它自己的目录里执行 `go test ./...`；全量测试执行 `make test-go`。
- **协议**：修改 `.proto` 后执行 `make proto`，把生成代码和改动一起提交。`make proto-check` 要求工作区干净，所以在**提交之后**再跑。
- **schema**：遵守 AGENTS.md 的「数据库 Schema 格式规范」。改完每个 schema 文件都要能单独载入空 SQLite 库，并通过 `git diff --check`。
- **前端**：测试与构建在编译机 `192.168.0.103:~/moox-web` 上执行（rsync 后跑 vitest、vue-tsc、vite build）。
- **构建**：不要在模块目录里不带 `-o` 执行 `go build ./cmd/x`，否则二进制会被 `git add` 提交进去。
- **清理**：涉及的文件顺手删掉死代码、只为旧行为存在的分支，以及过时的注释和测试（AGENTS.md「代码清理原则」）。
- **上线前暂停**：阶段 11 的 Codex 代码审查处理完后**暂停**，等用户确认再执行阶段 12。

## 3. 阶段 2：命名公共包

### T2.1 Go 包 `packages/factorname`

- **新建** `packages/factorname`，提供设计 5.1、5.2、5.5、5.6、5.7 所需的全部函数：
  - 名字校验：因子 ID、输出名、参数名，以及输出名的附加约束（不是 `var`、不匹配值的语法、不等于因子 ID）；
  - 参数值格式化：`FormatFloat('f', -1)`，`.` → `p`，`-` → `n`；
  - 拼成员键：参数全为默认值时省略参数段，可变成员是 `<因子ID>__var`；
  - 拼列名：单输出因子没有输出段；
  - **解析列名**：按 `__` 切成「因子 ID、固定或可变、参数段、输出名」，然后重新格式化与原文比对，不一致就判为非法；
  - `__params`、`factor_params` 的规范 JSON：键按字典序，JSON 数字，没有空白；
  - ID 生成与反解：`ftask_<后缀>`、`dataset_factor_<后缀>`、`view_factor_<后缀>`，8 位随机后缀，用户自定后缀的校验（不超过 35 个字符）；
  - 长度上限：因子 ID 24 个字符、输出名和参数名 16 个字符、成员键 44 个字符、列名 64 个字符。
- **测试向量** `packages/factorname/testdata/vectors.json`：覆盖默认参数、小数、负数、极小和极大的浮点数（`5e-324`、`1.7976931348623157e308`）、可变成员、单输出与多输出、非法名字，以及「两段式列名是参数段还是输出名」的判定和非规范写法（`01`、`1p0`）。
- `packages/factorname` 是独立的 Go 模块，和 `packages/factorexpr` 一样有自己的 `go.mod`，并登记进 `go.work`。`make test-go` 会按 `go.work` 逐个模块测试。
  使用它的模块（factor、strategy、cli、monitor）各自在 `go.mod` 里加依赖。
- **测试**：在 `packages/factorname` 目录下执行 `go test ./...`。

### T2.2 TS 实现 `web/src/utils/factor-name.ts`

- 功能与 T2.1 一一对应。vitest 直接读取 `packages/factorname/testdata/vectors.json`，要求每一条结果都一致。
- **测试**：编译机上跑 vitest。

**阶段 2 验收**：Go 与 TS 读同一份测试向量，全部通过。这个阶段还没有调用方。

## 4. 阶段 3：表达式规格与因子库

### T3.1 `factorexpr` 支持单数 `output`

- `packages/factorexpr/spec.go`：
  - 接受 `output: <表达式>`，输出名默认等于因子 ID；`output` 与 `outputs` 只能写一个；
  - `outputs` 至少要有两项；
  - 输出名、参数名、`let` 名的校验改为调用 `factorname`；输出名额外检查不是 `var`、不匹配值的语法。
- 「输出名不能等于因子 ID」在因子定义的校验里做，即 `modules/factor/internal/domain/validate.go`，同样调用 `factorname`。
- `domain/validate.go` 里的 `factorIDPattern`、`resultColumnPattern` 改为调用公共包。
- **测试**：factorexpr 的单测覆盖单输出、多输出、二者同时写、多输出只有一项、非法输出名；factor 模块的定义校验测试。

### T3.2 因子库与示例改写

- `modules/factor/factors/common.yaml`、`xbx.yaml`：
  - 因子 ID 全部改为小写（`Ema` → `ema`、`ZscoreAbsMeanQ` → `zscore_abs_mean_q` 等）；
  - 单输出因子改用 `output`；
  - `boll` 的输出改为 `mid`、`up`、`low`、`pctb`，`macd` 的输出改为 `dif`、`dea`、`hist`；
  - `atr` 拆成 `atr` 和 `atr_pct` 两个因子。
- `examples/factors`：删除 `ma`（与因子库重名）、`sma`、`ema50000`，其余按同样的规则改写。
- 所有引用旧因子 ID 的测试、fixture、示例和 `factorlib` 一并改掉。
- **测试**：factor 模块全量测试；因子库载入测试（每个定义都能编译，回看与原来一致）。

**阶段 3 验收**：因子库里没有大写的因子 ID，没有带因子前缀的输出名，所有定义都能编译通过。

## 5. 阶段 4：Storage 列契约

### T4.1 按 `column_kind` 分两类校验因子列

- `modules/storage/internal/service/catalog/metadata_catalog.go:597-612`：因子结果数据集里的 `FACTOR` 列按 `column_kind` 分开校验：
  - `output`：必须带 `factor_id`、`member_key`、`output_name`、`member_kind`，值类型为 `double`。列名要与 `member_key`、`output_name` 拼出的结果一致；Storage 只做字符串比较，不引用公共包。
  - `params`：列名必须是 `__params`，值类型为 `json`，每个结果数据集恰好一列。
- `catalog/validate.go:90-108,169-180`：View 列校验与 `isFactorViewColumn` 改用新属性，只把 `column_kind=output` 当作因子输出。默认 View 的列集合包含 `__params`。
- 展示名按 `validateColumnDisplayName` 的规则：输出列用「定义中文名」，多输出时再加输出名；`__params` 用「因子参数」。
- `metadata.proto:135` 更新注释，`make proto`。
- **测试**：storage 模块测试，覆盖：注册输出列和参数列；属性缺失或不匹配时被拒绝；第二个 `params` 列被拒绝；默认 View 包含 `__params`；写入并读回 `json_value`。

**阶段 4 验收**：Storage 能注册并读写 `__params`。旧的 `origin_factor_id`、`factor_output` 在 Storage 里不再出现。

## 6. 阶段 5：成员与列

这一阶段要改协议和策略模块，按约定可以把相邻任务合成一次提交。

### T5.1 成员表与成员模型

- `modules/factor/schema/factor.sql`：`t_factor_task_members` 按设计 9.1 重写。去掉 `c_member_alias` 和 `c_carry_alert_periods`，增加 `c_member_key`、`c_kind`、`c_params`；同一因子最多一个可变成员，用部分唯一索引约束；`mtime` 触发器按列限定。
  运行状态列在阶段 6 加入。
- `domain/types.go`：`TaskMember` 增加 `Key`、`Kind`、`Params`，删除 `Alias`、`OutputColumn` / `ParamColumn` / `ParamColumns`、`FixedParams()` 这些分支；列名一律由 `factorname` 推导。
- `store/members.go`：读写新的列。`domain/member_params.go` 里的 `DeriveMemberAlias`、`FormatParamValue`，以及 `CheckSharedMemberParams` 删除。
- **测试**：store 测试；schema 载入空库测试。

### T5.2 加成员、结果列注册与定义修改限制

- `catalog/service.go`：
  - `AddTaskMember(任务, 因子 ID, 类型, 参数)`：补齐完整参数，由 `factorname` 推导成员键和列名；成员键冲突、列名与非因子列重名时拒绝；
  - 重新加入同一个成员键时，核对旧列元数据里的 `factor_params`、`member_kind`，不一致就拒绝（设计 5.3）；
  - 注册输出列时写入新属性，任务创建时注册 `__params` 列（设计 5.5）。
- `catalog/reconcile.go:179`：列兼容判断改用 `member_key`、`output_name`、`member_kind`。
- `UpdateFactor`：被引用的定义不能增删参数，不能改参数的类型、顺序和默认值，也不能增删、改名或重排输出；改范围时，新范围要包含现有成员的参数（设计 5.4）。
- 协议：`AddTaskMember` 返回成员键和列名列表（设计 5.7）；删除 `member_alias` 字段，`make proto`。
- **测试**：加固定成员和可变成员、冲突、重新加入时核对参数、定义修改的每一条限制。

### T5.3 计算、组装与写入 `__params`

- `pipeline/compute.go`、`plan.go`：重建成员时保留 `Key`、`Kind`、`Params`，删除参数列相关的逻辑。
- `pipeline/assemble.go`：每行写因子值，并写规范化的 `__params`，JSON 由公共包生成。写入时用 `storageio` 的 `JSONText`。
- `engine/replay.go`、`runonce.go`、`preview/preview.go`、`enginehub/snapshot.go`：同样不再有参数列，改用成员键。
- 周期标记（`pipeline/report.go`、`packages/storagepb/storage_events.proto`、`packages/events/validation.go`）：按成员记录 `member_key`、`factor_id`、`definition_hash`、`member_kind`；删除 `params_source`、`params_digest`。
- 自动确认的证据与成员契约哈希（`engine/lifecycle.go`）：契约哈希 = 定义哈希 + 成员类型 + 固定参数（设计 7.2、7.3）。
- **测试**：同一行写出的 `__params` 与因子值一致，同一期重算时逐位相同；回放、诊断运行、试算都不再有参数列；周期标记的新字段；契约哈希随成员变化。

### T5.4 补算合并 `__params`

- `recalc/service.go`、`recalcexec/executor.go`：
  - 按期读取原行的 `__params`，取出这个成员的参数来重算；
  - 写回时只替换本次重算成功的成员键，其余保留；
  - 原行不存在、或 `__params` 里没有这个成员时：固定成员用 `c_params`，可变成员用默认参数，并把这些期次记进补算作业的结果（设计 7.4）。
- **测试**：只补算部分成员时，其他成员的记录不变；原行存在时重算逐位相同；缺行的期次被列出。

### T5.5 策略侧适配列名

- `modules/strategy/internal/input/resolve.go`、`readiness`：列解析只认 `column_kind=output`，删除 `column_kind=param` 和 `<别名>__<参数名>` 的读取。就绪检查改为比较成员契约哈希。
- 私有因子集在阶段 7 才删除，这一阶段的私有集成员按 DSL 生成：出现在 `factor_params` 里的因子为可变成员，其余为固定成员。这只是中间状态。
- **测试**：strategy 模块测试（解析、就绪检查、回放）。

**阶段 5 验收**：没有任何地方还在使用别名和参数列；`rg -n 'member_alias|MemberAlias|ParamColumn|column_kind.*param\b' modules packages` 只剩 `column_kind=params` 一处。

## 7. 阶段 6：参数提交与取值

### T6.1 成员运行状态列，以及 factor-mgr 的提交与读取

- `factor.sql`：
  - 成员表加入 `c_last_submitted_params`、`c_last_submitted_period`、`c_last_request_id`、`c_last_submitted_at`，以及设计 9.1 的 CHECK 约束；
  - 删除 `t_factor_param_requests`、`t_factor_param_snapshots`、`t_factor_param_freezes`、`t_factor_param_frozen_periods`。
- `catalog/params.go`、`store/params.go`：
  - `SubmitFactorParams`：校验、目标期不倒退、`request_id` 幂等、按标的合并，全部在一个事务里完成（设计 6.2）；
  - `GetFactorParams(task_id)`：只读接口（设计 6.3）。
- 协议：删除 `FreezeFactorParams`、`ReportOfflineFreezes`、`ListParamIntervals`；`SubmitFactorParams` 增加 `request_id`。同步修改 `catalog.yaml`，`make proto`。
- 提交滞后告警：可变成员的 `c_last_submitted_period` 落后引擎当前期次超过 `factor.params.stale_alert_periods`（默认 10）期时告警。
- **测试**：乱序请求被拒绝；同一个请求 ID 重复提交按幂等成功；同期不同请求 ID 被拒绝；按标的合并；提交校验的每一条规则。

### T6.2 引擎本地参数缓存

- 新的 `data/engine/param_cache.json` 存两样东西：
  - 每个任务的进行中记录：期次和选定的参数；
  - 最近一次读到的提交值。
- 开算一期时：
  1. 有这一期的进行中记录，就直接用；
  2. 没有，就读提交值（读不到时用缓存）、按规则取值，写进行中记录，落盘后再开始计算；
  3. **周期完成标记写成功后**才清掉进行中记录；
  4. 重启时发现某期有进行中记录、但标记已经存在，就只清除记录（设计 6.3~6.5）。
- 读到的 `c_last_submitted_period > t` 时，改用缓存里的值并告警。
- 删除 `engine/params.go` 的冻结与离线补报，以及 `data/engine/params.json` 及其读写代码。
- **测试**：
  - 同一期重试、写出前重启：用的都是第一次开算时的参数；
  - 结果行写成功、标记写失败后重试：参数不变；
  - factor-mgr 不可达时用缓存，恢复后用最新的合并结果；
  - 读到超前的提交时告警并用缓存值；
  - 积压追赶时不等策略。

### T6.3 策略投递并入结果表
