# 主机守护与告警高可用执行计划

> 状态：执行计划 v3（2026-10-18，尚未编码）。依据 2026-10-18 的讨论与线上只读核查；v2 吸收了一轮 Codex 审查（12 条，均已核实处理）；
> v3 加入（并吸收第二轮 Codex 审查 11 条）：服务器统一由 `moox-runtime` 管理（archive-mgr 并入 control 单元）、运维机外部程序的离线告警与 Windows 支持、
> archive-worker 暂存从 DuckDB 换成纯 Go SQLite（新项目，归档旧数据直接删除、不迁移）、服务器重启后的恢复过程。
> 实现后以[部署与运维](../部署与运维.md)、[监控](../模块/监控.md)、[主机代理](../模块/主机代理.md)、[归档](../模块/归档.md)为准。

## 1. 目标

1. **进程看护**：每台主机上由 `moox-runtime` 管理的组件，崩溃后自动拉起，主机重启后自动启动；不误拉有意暂停的组件，不和发布、重启抢操作。
2. **拉起告警**：每次自动拉起都推送企业微信（或飞书），写明主机、组件、原因、结果和崩溃线索；反复崩溃时退避并升级告警，不刷屏。
3. **告警配置单一来源**：告警渠道只在一处维护（Monitor 的通知渠道），各主机自动拿到最新值；在控制台或 `moox.toml` 修改后，全部主机在约 5 分钟内生效，不需要重新部署。
4. **没有监控盲区**：任何一台主机失联都有人告警，包括运行 Monitor 的 control 自己，以及目前没有登记成主机的因子引擎机器。
5. **一种管理模式**：服务器上 `/data/moox` 部署体系内的全部组件统一由 `moox-runtime` 管理、cron 触发守护，包括目前单独装成 systemd 服务的 archive-mgr；
   服务器重启后全部自动恢复。
6. **外部程序跨平台**：运维机上的外部程序（因子引擎、archive-worker）支持 Linux、macOS、Windows，用各系统自带的服务管理开机自启和崩溃重启，
   离线时 Monitor 直接告警。

非目标：不引入新的常驻进程，不把外部程序纳入 `moox-runtime`（它们不在部署体系内，还要支持 macOS、Windows），不做多 Monitor 实例选主。

| --- | --- | --- | --- |
| 192（编译机）：`moox-factor-engine`、`moox-archive-worker` | systemd 用户服务，`Restart=always`，`Linger=yes`，已 `enable` | 10 秒后自动拉起 | 自动启动（2026-10-18 10:58:39 开机，10:58:47 引擎已启动） |
| control：admin、host-gateway、monitor、eventbus、collector、strategy、factor-mgr、cloudnode、web-host、console-proxy、host-agent | `moox-runtime start` 拉起后父进程为 1，**无 systemd、无 crontab、无定时器** | **不会拉起** | **不会启动** |
| control：`moox-archive-mgr` | systemd 用户服务（`scripts/deploy/deploy-archive-mgr.sh` 单独安装在 `/data/moox/prod/archive`）。它是服务目录里的正式组件（`scope: any`），当初因为生产 runtime 内嵌的服务目录不认识新组件才没进 control 单元 | 自动拉起 | 自动启动 |
| storage（access、host、storage 三个单元）、compute-1（access、egress-proxy、host、trade 四个单元） | 与 control 相同：父进程为 1，无 systemd、无 crontab（阶段 0 已核实） | **不会拉起** | **不会启动** |

control 自 2026-09-25 起没有重启过，所以问题还没暴露。

**缺口的来历**：旧部署器每台主机装有一条 `# moox-healthchecks` crontab，每分钟遍历各包的 `healthcheck.sh`
（`modules/cli/internal/setup/deploy/deploy.go` 的 `install_healthcheck_cron`）。切换到原生部署时，
[网关与服务部署重构执行计划](网关与服务部署重构执行计划.md)第 13 节先删除了这条 crontab，防止旧脚本误拉进程；之后原生部署没有补装定时调用。

**现成的守护能力**：`moox-runtime healthcheck`（各包 `healthcheck.sh` 调用的就是它）已经是完整的单次守护检查，
见 `modules/cli/internal/setup/unitruntime/runtime.go` 的 `healthcheck`：

- 有暂停标记（`run/paused/<组件>`）或停止中标记（`run/draining/<组件>`）时不动；
- PID 记录不存在或进程已不在时直接启动；
- 进程在但带签名的 `/healthz` 失败时，先按预算停止再启动；`/readyz` 未就绪不触发重启；
- 与安装器、启停共用维护锁（`run/maintenance.lock`），锁被占用时整体跳过；存在 `run/bootstrap.json` 或 `run/installation.json`
  （bootstrap、发布未完成的持久屏障，跨重启保留）时整体跳过；
- 用 pidfd + 可执行文件 inode + start ticks 核对进程身份，不会认错或误杀。

**会让组件一直起不来的边界问题**（读代码确认）：

1. PID 记录指向的 PID 在重启后被别的进程复用时，身份核对返回 `errIdentity`，`healthcheck` 报错且**不拉起**。
2. 停止过程中被中断（包括关机，也包括调用方超时取消了 `stop`）留下的 `run/draining/<组件>` 会一直保留，按设计守护不得重启，该组件**一直不会被拉起**
   （`runtime_linux_test.go` 有测试明确覆盖“取消后保留标记”）。
3. 发布或 bootstrap 中断留下的 `run/installation.json` / `run/bootstrap.json` 会让整机的 `healthcheck` 一直跳过；这两个屏障有恢复流程，不能按开机时间直接删除。
4. **启动有依赖顺序**：主机网关要等 Admin 完成同步才就绪，HostAgent 要 EventBus；`start` 会等待就绪，超时会停掉进程。
   bootstrap 的恢复流程按 `admin → host-gateway → eventbus → host-agent → 其余组件` 跨单元启动（`unitbootstrap/recover.go` 的 `startStages`）。
   按单元逐个执行 `healthcheck`（先 host 单元）在 control 冷启动时会卡在等待网关就绪上。

### 2.2 告警链路

| 能力 | 现状 |
| --- | --- |
| 组件不可用 | Monitor 按部署对各组件做 HTTP/TCP 探测，失败 3 次告警（严重）；只告警，不拉起 |
| 主机失联 | HostAgent 每分钟经 EventBus 上报快照，Monitor 3 分钟收不到即推送“主机 X · 失联”，恢复后推送“已恢复在线” |
| 主机网关 | 每台主机网关的心跳、实例冲突、路由同步合成 `gateway:<主机>:status` 一条检查 |
| 数据中断 | 采集、存储、视图、因子、策略的数据集新鲜度与 K 线新鲜度检查 |
| 推送 | Monitor 发往 `t_monitor_notification_channels` 中的全部渠道；持续未恢复每 5 分钟提醒一次 |
| 证书到期 | Admin 证书巡检已实现，能读 `MOOX_NOTIFICATION_WEBHOOK_URL` 直接推送；但原生部署只给 Monitor 注入通知变量（`unitdeploy/unit.go`，测试明确要求 Admin 不含），生产 `runtime-admin.json` 也没有，**目前只记录不推送** |
| Monitor 自身失效 | Monitor 检查结果写库失败时不会执行告警回调（`scheduler.go`），而 `/healthz` 仍返回存活，进程不会被判为故障 |

Monitor 已登记的主机（`t_monitor_host_agents` 与 `t_monitor_gateway_observations`）：control、storage、compute-1，均在线。

### 2.3 告警链路的缺口

| 编号 | 缺口 | 影响 |
| --- | --- | --- |
| G1 | control、storage、compute-1 上由 `moox-runtime` 管理的组件都没有看护（阶段 0 已核实） | 崩溃后只告警不恢复；主机重启后整机业务停摆 |
| G2 | 重启后的两个边界问题（2.1 末尾） | 即使补上定时调用，重启后也可能有组件起不来 |
| G3 | 告警地址有多份副本：Monitor 库（控制台可改）、Monitor 环境变量（种子）、`moox.toml`；Admin 没有地址 | 改 `moox.toml` 不会同步到 Monitor（只在首次建库时写入）；证书到期告警发不出去 |
| G4 | control 失联无人告警：Monitor、EventBus、推送都在 control 上 | 最严重的故障反而没有告警。文档提到的“SCF 哨兵”在代码中不存在，11409 只是在防火墙上对公网开放，没有调用方 |
| G5 | 192 没有登记成主机 | 机器失联只能从“因子数据不新鲜”间接发现，看不出是机器问题 |
| G6 | host-agent 进程停止会被报成“主机失联” | 告警原因不准，排查方向错误 |
| G7 | 主机失联、组件拉起等告警没有在生产演练过 | 链路是否真的能送达未经证实 |
| G8 | Monitor 进程活着但评估或写库停滞 | 所有 Monitor 侧告警静默失效，进程和网关看起来都正常 |
| G9 | 主机资源告警的阈值按“每 15 秒采样”设计（`default_alerts.go` 的注释与次数），HostAgent 实际每分钟采样一次 | CPU、内存告警要约 12、20 分钟才触发，而不是设计的 3、5 分钟 |
| G10 | archive-mgr 在 control 上单独用 systemd 管理，与其他组件不是一种模式 | 暂停、发布、回滚、拉起告警都要单独处理 |
| G11 | 因子引擎、archive-worker 离线只能间接发现（数据不新鲜、归档停滞），虽然它们一直向 factor-mgr、archive-mgr 发心跳 | 告警慢，看不出是外部程序停了 |
| G12 | 外部程序不能在 Windows 上运行：因子引擎的集合锁用 Linux 的 `flock`（`modules/factor/internal/setlock/locks.go`），archive-worker 依赖 DuckDB 必须用 cgo 编译；安装脚本只有 bash | 只能部署在 Linux、macOS 上 |

## 3. 设计决策

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| D1 | 复用 `moox-runtime healthcheck` 的判断，不写按进程名 `ps | grep` 的守护脚本 | 按名字判断分不清新旧版本和暂停中的组件，`kill -9` 同名进程有误杀风险，还会和发布、`restart.sh` 抢操作 |
| D2 | 定时方式用 crontab，每台主机一条，带标记 `# moox-watchdog` | 用户选定；不依赖 systemd 用户会话；与旧方案一致；开机后 cron 每分钟运行，最多 1 分钟即拉起，不需要 `@reboot` |
| D3 | 新增 `moox-runtime watch` 子命令遍历本机全部单元，而不是在 crontab 里写 shell 循环 | 台账、退避、告警合并需要状态与测试；纯 Go，可在 Linux 内核门禁里测 |
| D4 | 服务器上统一由 `moox-runtime` 管理、cron 触发守护，archive-mgr 并入 control 单元；运维机上的外部程序（因子引擎、archive-worker）用系统自带的服务管理（Linux systemd、macOS launchd、Windows 服务），不纳入 watch | 统一的是管理者而不是定时器：`moox-runtime` 已实现暂停、维护锁、健康检查重启、停止预算、发布回滚，改用 systemd 要重写这一层并给每个程序接看门狗；外部程序不在部署体系内且要支持 macOS、Windows，用系统服务最自然 |
| D5 | 守护直接推送企业微信 / 飞书，不经过 Monitor | 挂掉的可能正是 Monitor 或 EventBus；共享的 `notification` 包已支持直接发送（Admin 证书巡检用的就是它） |
| D6 | 告警渠道的唯一来源是 Monitor 的通知渠道；`moox.toml` 的 `[notification]` 只作初始化种子 | 控制台已能增删和测试，支持多个渠道 |
| D7 | 主机通过 host-agent 拉取“主机策略”并缓存到本机文件，`moox-runtime` 只读文件 | `moox-runtime` 的设计原则是不联网、不持有网关凭据；host-agent 已常驻每台主机 |
| D8 | 不用 EventBus 推送告警配置 | 要让告警密钥进入消息流并单独收紧权限；EventBus 本身也在 control 上 |
| D9 | control 失联由其他主机交叉检查：与 control 主机网关做 TLS 握手，用 MooX 私有 CA 校验证书 | 每台主机都有私有 CA；不需要分发 control 的健康密钥；只依赖网络与 control 的网关进程 |
| D10 | 192 按完整 host 单元部署（host-gateway + host-agent）并登记为主机 | Admin 登记主机会自动添加全部 host 范围组件，拓扑校验要求它们存在（`sysdeploy/topology.go`、`servicecatalog/routes.go`）；只装 host-agent 会留下不存在的网关部署而持续告警，策略拉取也没有本机网关可走 |
| D11 | watch 按跨单元依赖顺序检查，与 bootstrap 恢复顺序一致 | 冷启动时网关依赖 Admin、HostAgent 依赖 EventBus |
| D12 | 不改 PID 记录结构；在 `run/boot.json` 单独记下内核 boot ID，变了即说明重启过，清理全部进程记录与停止中标记；没有 `boot.json` 时（新版本第一次运行）退回按 `StartedAt` 早于开机时间至少 1 分钟判断 | 旧版 runtime 按严格模式解析记录（`DisallowUnknownFields`），加字段后回滚旧版会失去启停能力；只靠 `StartedAt` 与开机时间比较，在开机后时钟被校准回拨时会把正在运行的进程误判为残留、拉起第二份 |
| D13 | 外部程序离线由各自的管理端判定并上报模块健康检查，Monitor 据此告警 | 心跳已经存在（`EngineHeartbeat`、`ArchiveWorkerHeartbeat`），复用 Monitor 已有的“模块健康”来源，不新增通道 |
| D14 | archive-worker 暂存从 DuckDB 换成纯 Go SQLite（与 archive 模块已依赖的 `glebarez/sqlite` 一致） | DuckDB 在这里只做主键暂存、状态表、按时间段排序导出 CSV，没有用到列存分析；纯 Go 后不需要 cgo，三个系统都能直接交叉编译 |
| D15 | 新项目，归档旧数据不迁移：切换时删除 archive-mgr 的 `archive.db`、worker 的归档目录（CSV 与 `.state/`），从头开始归档；导出 CSV 的格式不需要与 DuckDB 的输出兼容 | 用户确认旧数据可以直接删除，省去迁移命令与格式兼容测试 |
| D16 | 因子引擎、archive-worker 支持 Windows：补 Windows 文件锁、接入 Windows 服务、提供 PowerShell 安装脚本 | 两个程序都是纯计算或纯 IO 的外部程序，放在哪种机器上都一样 |
| D17 | 只能出站的主机（192 及以后的运维机）经主机网关反向连接接入：出站主机的网关主动与 control 网关保持长连接，进入它的连接都经 control 中转 | 家庭网络 NAT 且出口 IP 会变；SSH 反向隧道与 control 自身端口冲突、网关目标无法改；WireGuard 引入系统级依赖与第二套身份；反向连接沿用现有 TLS 与签名、端到端加密、跨平台、不需要 root |

**借鉴的外部脚本做法**（参考 trpc 的 `monitor.sh` / `start.sh` / `stop.sh`）：
进程消失时扫描最近日志里的 `panic:`、`fatal error:`、`SIGSEGV` 并限频；每种处置给出明确的原因分类；记录检查与启动历史；
cron 层用 `flock -n` 保证同一时刻只有一轮在跑。不借鉴：按进程名判断与 `kill -9`、`pid.conf`、`curl` 拉取配置。

## 4. 详细设计

### 4.1 `moox-runtime watch`

```text
moox-runtime watch --root /data/moox [--dry-run]
```

每轮流程：

1. **枚举单元**：`<root>/*/current/runtime.json`（跳过 `.next`、`.previous`、`.failed`），按主机身份 `run/host.json` 校验，不跨主机。
2. **持久屏障**：存在 `run/bootstrap.json` 或 `run/installation.json` 时整轮跳过，结果记为 `skipped_bootstrap` / `skipped_installation`，
   并按 4.3 推送“需要人工恢复”（附对应的恢复命令）；不自动删除这两个文件。
3. **上次开机的残留**（解决 G2 的 1、2）：
   - 内核 boot ID 与 `run/boot.json` 记录的不同：全部 PID 记录与 `draining` 标记都属于上次开机，删除后按“已停止”处理，不再走身份核对，告警里注明“停止过程被关机打断”（D12）。
     这一步由运行助手在每次操作持锁后执行（`Result.boot_recovered` 列出清理掉的残留），watch、`healthcheck.sh` 与人工操作都会触发。
   - 本次开机内留下的 `draining`（例如人工 `stop` 被打断）：不自动清除，推送“需要人工处理”，附 `moox-runtime stop --components <组件>` 续停命令。
   - `paused` 标记保持不动（这是用户的意图）。
4. **按依赖顺序逐组件检查**（D11）：先 `admin`、`host-gateway`、`eventbus`、`host-agent`（各自所在单元），再按各单元 `runtime.json` 的顺序检查其余组件；
   依赖组件本轮没能就绪时，依赖它的组件本轮跳过（记 `skipped_dependency`），下一轮再试。
   调用与 `healthcheck` 相同的逻辑，返回结构化结果：`healthy`、`started`（原来没在运行）、`restarted`（健康检查失败后重启）、`start_failed`、
   `not_ready`（进程活着但 `/readyz` 持续失败）、`skipped_paused`、`skipped_draining`、`skipped_locked`、`skipped_dependency`、`identity_error`。
5. **崩溃线索**：结果为 `started` 或 `restarted` 时，读取该组件日志末尾 1000 行，提取最后 3 条匹配 `panic:|fatal error:|runtime error:|SIGSEGV|SIGABRT|\[PANIC\]` 的行，
   以及进程退出码（能取到时）；同一组件 60 秒内只扫描一次。
6. **台账**：每次非 `healthy` 的结果追加到 `run/watchdog/<组件>.jsonl`（时间、结果、原因、耗时、线索摘要），保留最近 30 天，随 runtime 的日志轮转清理。
7. **持续崩溃与退避**：按“自动拉起次数”统计，不只看启动失败——组件启动成功后又崩溃，每轮都能“拉起成功”，只数失败永远累计不到。
   同一组件 10 分钟内被自动拉起（`started` / `restarted`）或拉起失败合计 3 次，进入“持续崩溃”：之后每 5 分钟才尝试一次，连续 1 小时仍在崩溃改为每 30 分钟一次。
   连续稳定运行 10 分钟（期间每轮都是 `healthy`）才判定恢复并清零。状态保存在 `run/watchdog/state.json`。
8. **未就绪告警**（解决 G8 的一部分）：进程活着但 `/readyz` 连续 5 分钟失败的组件，不重启（遵守 runtime 的约定），推送“组件持续未就绪”。
   Monitor 的 `/readyz` 增加“最近一次评估完成时间”判断：超过 3 分钟没有完成评估即返回未就绪，这样 Monitor 写库或调度停滞时，control 上的 watch 会直接推送告警。
9. **告警**：见 4.3。
10. **输出**：一行 JSON 汇总写到 stdout（cron 重定向到 `run/watchdog.log`），包括每个组件的结果与耗时。

维护锁被占用时整轮跳过并记录一行；单个组件出错不影响其他组件。
**没有整轮硬超时**：硬超时会取消正在执行的 `stop`，留下 draining 标记反而让组件永远起不来。改为“软期限”：一轮开始 4 分钟后不再开始新的组件检查，
已经开始的启停按 runtime 自己的完整预算执行完；cron 那一层的 `flock -n` 保证下一分钟不会叠加新一轮。

### 4.2 crontab

每台主机、部署用户各一条：

```cron
* * * * * PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin flock -n /data/moox/run/watchdog.lock /data/moox/host/current/bin/moox-runtime watch --root /data/moox >>/data/moox/run/watchdog.log 2>&1 # moox-watchdog
```

- **安装时机**：host 单元安装或激活时写入（`moox-runtime` 随 host 包装到每台主机）。按标记替换，幂等；写入后用 `crontab -l` 校验。
- **前置检查**：cron 守护进程不存在或不在运行时安装失败并报错，不静默跳过。
- **卸载**：卸载 host 单元时删除这一行。
- **旧条目**：发现旧的 `# moox-healthchecks` 条目时一并删除（原生部署不再使用它）。
- **日志**：`run/watchdog.log` 纳入 runtime 现有的日志轮转。

### 4.3 拉起告警

**渠道**：读取本机主机策略缓存（4.4）里的全部渠道，用共享的 `notification` 包发送（企业微信、飞书都支持）；
至少一个渠道送达即视为送达。推送失败只写日志，不影响拉起，也不重试。缓存缺失或没有渠道时，在日志里记录“没有可用的告警渠道”。

**消息**（示例）：

```text
【MooX 自动拉起】control · strategy · 已恢复
原因：进程不存在（上次运行 3 小时 12 分）
结果：拉起成功，健康检查通过（耗时 4.1 秒）
崩溃线索：panic: runtime error: index out of range [3] with length 3
近 1 小时自动拉起：1 次
时间：2026-10-18 14:03:12（北京时间）
```

**防刷屏**：

| 场景 | 规则 |
| --- | --- |
| 同一组件短时间多次拉起 | 10 分钟内最多一条，多出的次数合并进下一条 |
| 进入持续崩溃 | 立即发一条“持续崩溃，已降低拉起频率”（严重） |
| 持续崩溃后恢复 | 发一条“已恢复” |
| 主机重启后首轮拉起多个组件 | 合并为一条“主机重启，已拉起 N 个组件：…”（附开机时间） |
| `identity_error`、`start_failed`、`not_ready`、持久屏障与残留标记需要人工 | 每种问题每 30 分钟最多一条 |

### 4.4 主机策略缓存与告警配置单一来源

**文件**：`<root>/run/host-policy.json`，0600，原子替换（写临时文件后 rename）。

```json
{
  "version": 7,
  "content_hash": "sha256:…",
  "source": "monitor",
  "fetched_at": "2026-10-18T06:00:05Z",
  "notification_channels": [{"type": "wecom", "webhook_url": "https://qyapi.weixin.qq.com/…"}],
  "watchdog": {"enabled": true, "merge_window": "10m", "crash_loop_failures": 3, "crash_loop_window": "10m", "crash_loop_retry": "5m"}
}
```

**拉取**：host-agent 启动时拉一次，之后每 5 分钟经本机主机网关调用 Monitor 新增的只读方法 `GetHostPolicy`
（服务目录新增调用方 `host-agent`，只读）；内容哈希变化才重写文件。拉取失败保留旧文件并记日志、上报指标。

**种子**：部署 host 单元时，部署工具用 `moox.toml` 的 `[notification]` 写一份 `source: "seed"` 的初始文件，保证首次拉取之前也能告警；
已有更新的 `source: "monitor"` 文件时不覆盖。

**修改路径**：

| 修改方式 | 生效过程 |
| --- | --- |
| 控制台「消息通知设置」增删渠道 | Monitor 库更新 → 各主机 host-agent 下次拉取（≤ 5 分钟）→ 缓存更新 |
| 修改 `moox.toml` 的 `[notification]` | `moox-cli config plan` 显示与 Monitor 现有渠道的差异 → 用户确认后 `config publish` 调用 `AddNotificationChannel` / `DeleteNotificationChannel` 写入 Monitor（moox-cli 已是这两个方法的合法调用方）→ 同上 |
| 需要立即生效 | `moox-cli config publish` 完成后通过 SSH 在各主机触发 host-agent 立即拉取（`moox-runtime` 不参与） |

`config plan` 同时列出各主机缓存的 `version` 与 `fetched_at`，可以看出哪台主机还没追上。

**接通证书告警**：Admin 证书巡检改为每次巡检时读取本机 `host-policy.json` 的最新渠道（取代从未在原生部署中注入的 `MOOX_NOTIFICATION_*` 环境变量，相关读取代码一并删除），
这样证书到期告警第一次真正能推送出去。Monitor 保持“只在首次建库时读取种子”不变。

### 4.5 control 交叉检查（解决 G4）

- storage、compute-1 上的 `watch` 每轮额外检查 control：与 control 主机网关的跨主机 TLS 入口建立连接并完成握手，用本机的 MooX 私有 CA 校验证书与主机名（5 秒超时）。
- 连续 3 分钟失败，用本机缓存的渠道推送“control 失联（由 storage 观测）”（严重）；恢复后推送“control 已恢复（由 storage 观测）”。状态保存在 `run/watchdog/peer-control.json`。
- 两台主机都会发送，同一件事最多两条，消息里写明观测方。
- 只有 control 的网关进程挂了而主机还在时也会触发；这种情况 control 自己的 watch 会在 1 分钟内把网关拉起，通常不会达到 3 分钟。
- TLS 握手只能证明 control 的网关入口活着，不能证明 Monitor 在正常评估；后者由 control 上 watch 的未就绪告警覆盖（4.1 第 8 步）。
  control 主机还在但 watch 自己也坏了（例如 cron 停了）的组合仍是盲区，由外部兜底覆盖。
- 可选兜底：在腾讯云配置云拨测探测控制台 9527，作为不依赖本系统的外部检查（运维配置，不在代码范围内）。

### 4.6 192 登记为主机：主机网关反向连接（解决 G5）

按完整 host 单元部署（host-gateway + host-agent + `moox-runtime` 与 watch 的 crontab），在 Admin 登记主机（D10）。与其他主机一样，
由 watch 看护，HostAgent 经本机网关拉取主机策略。192 原有的因子引擎、archive-worker 仍是 systemd 用户服务，不纳入 watch。

**问题**（2026-10-18 核实，见 9.2）：192 在家庭网络里，只有 NAT 后的内网地址，出口公网 IP 会变；control 连不进 192，192 能出站。
现有体系默认“所有主机互相可直达”：调用方的网关客户端直接连目标主机的 `Address:11003`（`gatewayclient.endpoint`），
Monitor 直接探测各主机的健康端口；主机材料包把 `control.target` 固定为“control 公网地址:11003”，安装器逐字核对。
曾考虑过的 SSH 反向隧道不可行：control 自己的网关、HostAgent 健康端口监听在所有地址上，反向转发绑不上；网关目标也无法指向本地转发。
按来源 IP 放行安全组解决不了动态 IP；WireGuard 覆盖网络能解决，但会引入系统级新依赖（工具包、root、Windows 客户端）和第二套身份体系。

**决定（D17）**：给主机网关加“反向连接”（relay）。只能出站的主机（以下称“出站主机”）的网关主动与 control 网关保持一条长连接，
所有要进入出站主机的连接都经 control 网关中转、顺着这条连接送达。不引入新组件，沿用 MooX CA 与调用方签名，Linux / macOS / Windows 一致，不需要 root。

**设计**：

1. **主机可达性**：主机增加属性 `reachability = "direct" | "outbound"`（默认 `direct`）。来源依次是 `moox.toml` 的 `[[hosts]]`、
   Admin 主机登记（新列）、服务目录拓扑 `servicecatalog.Host`、编译后的目录 `DirectoryHost.Relay`（出站主机填 control 的主机 ID，其他为空）。
   校验：control 不能是出站主机；出站主机的 `Address` 只作身份与证书 SAN 用，不要求可达（192 填它的内网地址 `192.168.0.103`）。
2. **会话建立（出站主机 → control）**：出站主机的网关按 `control.target`（control 公网地址:11003，与其他主机相同）发起 TLS。
   **11003 在 listener 层按 ALPN 分流**：`moox-relay-attach`、`moox-relay-open` 两种协议独占连接，不带这两个 ALPN 的连接照旧交给 tRPC 子 listener
   （tRPC 处理器接管不了 socket，不能在普通 RPC 方法里升级连接）。普通 RPC、交叉检查、打开流都不提交客户端证书，只有 attach 强制双向 TLS：
   现有主机网关证书只有 `ServerAuth` 用途，所以 Admin 要给出站主机的网关签发含 `ClientAuth` 的证书（材料包与安装器的证书校验随之更新），
   attach 时提交；control 用 MooX CA 校验，证书 SAN 必须等于一台已登记、已启用、`reachability=outbound` 的主机，只有 `ServerAuth` 的证书不能 attach；
   再用该主机的 `host-gateway@<主机>` 凭据签名一次“attach”请求（沿用现有签名、nonce 防重放）。通过后这条连接切换为多路复用会话
   （纯 Go 库，候选 `hashicorp/yamux`，实现时定），每台出站主机同一时刻只保留最新的一个会话（按网关实例 ID，新的接替旧的）。
   断开后指数退避重连（1 秒起，最长 30 秒），出口 IP 变化只表现为一次重连。会话每 15 秒心跳，45 秒无响应即判断开。
3. **建立中转流（调用方 → control → 出站主机）**：要连接出站主机的一方（调用方网关客户端、Monitor 探测）先以 ALPN `moox-relay-open` 与 control 网关建 TLS，
   在连接开头发送一个有长度上限的签名“打开流”前导：目标主机、目标端口。control 网关校验：
   - 签名有效（调用方凭据，`TargetNode` 为 control，nonce 防重放），调用方在服务目录的中转 ACL 里；
   - 目标主机是出站主机且会话在线；
   - 目标端口在允许清单里：该主机网关的跨主机端口 11003，以及服务目录中放置在该主机上的组件的健康端口（只有 Monitor 能打开健康端口）。
   通过后在会话上开一条流，出站主机的网关把流接到本机 `127.0.0.1:<端口>`，之后双向透传字节。
4. **安全边界**：经中转的 RPC 仍由调用方与出站主机网关之间做 TLS（`ServerName` 为目标主机 ID），每个请求仍带调用方签名，最终授权仍由目标主机网关按路由 ACL 判断；
   control 网关只转发字节、读不到明文。**但 control 不是不可信的中转**：调用方签名是 HMAC（对称），Admin 会把验证用的原始密钥下发给各网关，
   control 网关本来就持有能调用 192 上服务的调用方（Monitor、moox-cli 等）的密钥，理论上可以自行签出请求。control 是整个系统的信任根（Admin、CA 都在它上面），
   本设计把 control 网关明确定为可信认证方，端到端 TLS 只保证传输机密性，不作为“control 无法伪造”的保证。
   要消除这一能力需要把业务签名改为非对称签名，属于独立的大改动，不在本计划内。健康探测走 HMAC 健康认证（与现在相同），外层在两段 TLS 之内。
5. **调用方改动**：`gatewayclient` 用自定义的连接池拨号器完成“与 control 建 TLS（`moox-relay-open`）→ 发打开流前导 → 在流上与目标做 TLS”，
   返回最终的 `net.Conn` 交给 tRPC；连接池按目标主机与 TLS 身份隔离，业务签名的 `TargetNode` 仍是目标主机，只读重试与目录刷新语义不变。
   操作端 CLI 走 SSH 隧道模式（`Mode == Tunnel`），它的分支要同样处理：经隧道到 control 后再打开中转流，而不是去 SSH 直连出站主机。
   Monitor 的部署探测对出站主机同样经中转拨号。直达主机的路径完全不变。
6. **control 的 11003 对公网开放**：与已经对公网开放的 EventBus 4222 一样，凭 TLS 与签名认证，不按来源 IP 放行；出站主机的 IP 怎么变都不需要改安全组。
   同时给 11003 加连接保护：未完成握手与认证的连接 10 秒超时，单个来源 IP 的并发连接上限，中转流总数与每会话流数上限。
7. **可观测性与告警**：control 网关在心跳状态里上报各出站主机会话（是否在线、建立时间、重连次数、活动流数），Monitor 增加
   “主机网关反向连接 · <主机>”检查：会话断开 3 分钟告警（严重），恢复后通知。会话断开时出站主机的部署探测会一起失败，
   失联判断仍以 HostAgent 经 EventBus 的上报为准（4222 直连，不经中转），因此能区分“反向连接断开”与“主机宕机”，告警正文写明检查方法。
   出站主机上的守护交叉检查（4.5）照常进行（它本来就是出站连接）。
8. **Windows 运维机**：网关与反向连接都是纯 Go，以后 Windows 运维机加入时同样以出站主机接入。

**审查**（2026-10-18）：Codex 两轮审查。第一轮 7 条（发布范围遗漏目录消费者、HMAC 下 control 可伪造、证书缺 ClientAuth、tRPC 无法接管 socket、Admin 新列无迁移、
部署复用首次初始化软件、stop 会被守护拉起）均已吸收进本节与阶段 7；第二轮判定 7 条全部解决，未发现新的重大问题。

**不做的事**：不改直达主机之间的调用路径；不让 control 网关解密或改写中转内容；不在出站主机上开放任何入站端口。

### 4.7 区分“主机失联”与“host-agent 停止”（解决 G6）

Monitor 的失联告警附带该主机网关心跳的状态：

- host-agent 静默且网关心跳也停 → “主机失联”（严重）；
- 只有 host-agent 静默 → “host-agent 停止上报”（警告），正文提示守护应在 1 分钟内拉起。



### 4.8 服务器重启后的恢复过程

1. 系统启动 cron（各主机的 cron 必须是开机自启，阶段 0 逐台确认；control 已确认 `enabled`、`active`，`/data` 在根分区）。用户 crontab 不需要登录就会执行。
2. 开机后的下一个整分钟，第一轮 `watch` 开始：上次开机的 PID 记录与 `draining` 标记按 4.1 第 3 步处理；`flock` 是内核锁，重启后自然释放。
3. 按依赖顺序启动：control 上 Admin → 主机网关 → EventBus → HostAgent → 其余组件；其他主机先 host 单元再业务单元。上游没就绪时下游本轮跳过，下一分钟再试。
4. 全部就绪后推送一条“主机重启，已拉起 N 个组件”。

| 场景 | 预计恢复时间 |
| --- | --- |
| storage、compute-1 单独重启（control 正常） | 开机后 1～2 分钟 |
| control 重启 | 几分钟（按顺序等 Admin、网关、EventBus 就绪）；期间其他主机发出“control 失联”，恢复后发“已恢复” |
| 多台同时重启 | 其他主机的网关要等 control 的 Admin 就绪，每分钟重试，control 恢复后跟着恢复 |

有意不自动恢复的情况（推送告警并附处理命令）：用户暂停的组件；重启时正在发布或初始化（`installation.json`、`bootstrap.json`）。
运维机上的外部程序由系统服务开机自启（192 于 2026-10-18 10:58 重启时，引擎 8 秒后恢复）。

### 4.9 archive-mgr 并入 control 单元（解决 G10）

- 生产 control、host 单元打包的服务目录都不包含 archive-mgr（2026-10-18 核实：两个发布都是 10-11 打包，之后只替换过二进制）。
  因此要按当前服务目录**整体重新发布 host 与 control 单元**（服务目录变化必须整体发布的既有规则），把 archive-mgr 加进 control 单元的运行计划：
  工作目录 `<发布目录>/archive-mgr/{config,data,logs}`，与 factor-mgr 相同的密钥投影与网关身份。这次整体发布与阶段 4 的 host 单元发布合并进行。
- 删除 `scripts/deploy/deploy-archive-mgr.sh` 及其 systemd 单元模板。
- **切换顺序**（旧 mgr 占用 11406、11408、11416 等端口，安装器只停止旧运行计划里的组件，不会停止单独的 systemd 服务；不先停掉旧服务，新 control 激活会因端口冲突整体回退）：
  1. 停止 192 上的旧 worker；
  2. `systemctl --user stop` 并 `disable` control 上的 `moox-archive-mgr.service`，确认上述端口已释放；
  3. 激活新 control 单元（含 archive-mgr，从空库开始，按 D15 不迁移旧 `archive.db`）；
  4. 删除旧的单元文件与 `/data/moox/prod/archive`、192 上的归档目录；
  5. 部署新 worker，在控制台重建归档任务。
- **回退**：回滚 control 单元到上一版本后，旧版本不含 archive-mgr；如需恢复旧的独立服务，用旧版本的 `deploy-archive-mgr.sh` 重新安装（从空库开始），否则归档暂停。
- 之后 archive-mgr 和其他组件一样由 watch 看护、可暂停、随发布回滚。

### 4.10 外部程序离线告警（解决 G11）

**判定对象**（与租约分开）：
- 因子引擎：引擎租约只有 45 秒（`enginehub.DefaultEngineLeaseTTL`），离线两分钟时早已不持有租约，所以不能按“持有租约的引擎”筛选；
  改为“最近一次被接受心跳的引擎”是否在 2 分钟内有心跳。最近心跳目前只在 factor-mgr 内存里，需要持久化到 factor-mgr 的库（引擎 ID、最后心跳时间、主机名），
  管理端重启后仍能判定“引擎一直没回来”。存在启用的因子集才要求有引擎在线。
- 归档 worker：worker 登记是心跳自动产生的持久记录，租约过期不会删除，换机后旧记录还在；所以不检查“每个登记过的 worker”，
  而是按当前单活动 worker 的模型检查“是否有一个 worker 在 2 分钟内有心跳”。存在启用的归档任务才要求有 worker 在线；
  在控制台增加 worker 记录的退役操作，清理不再使用的旧登记。

**告警链路**（现有“模块健康”只按最近成功、失败的运行时间判断，原因文本固定，不能直接表达“离线”，archive-mgr 也还没有接入指标定时上报，需要补齐）：
- 两个管理端各增加一个每 30 秒的评估：得出“在线 / 离线 / 不需要”三种状态，以及最后心跳时间、机器标识；
- 通过 `packages/report` 上报一个专门的状态指标（archive-mgr 首次接入定时指标上报）；
- Monitor 新增对应的检查类型：状态为离线时失败，原因写明机器与最后心跳时间；“不需要”时视为通过，删除全部任务后已有的告警随之恢复；
- 告警时间：2 分钟无心跳 + 最长 30 秒评估与上报延迟 + 60 秒外部检查宽限，约 3.5 分钟内告警。

### 4.11 archive-worker 暂存改用纯 Go SQLite（解决 G12 的一半）

- `internal/worker/staging` 的实现从 DuckDB 换成 SQLite（`glebarez/sqlite`，与 archive-mgr 相同，纯 Go）：
  - 每个任务一张 `WITHOUT ROWID` 暂存表，主键 (subject_id, data_time, series_tag)，另建 `data_time` 索引供按分区导出；
  - **时间精度**：Storage 行键保留纳秒，worker 按 `RFC3339Nano` 解析，所以 `data_time` 存 **Unix 纳秒整数**（int64 可表示到 2262 年），不能降为毫秒，
    否则同一标的、同一序列相差不到 1 毫秒的两行会互相覆盖；导出与读回保持同样精度；
  - **时间列的存取要重写，不能照搬**：DuckDB 把 TIMESTAMP 直接扫描成 `time.Time` / `sql.NullTime`（临时表统计、`MIN/MAX(data_time)`、状态表的各时间列），
    SQLite 没有这种类型，`CREATE TABLE … AS SELECT` 也不保留列类型。所有时间列统一用纳秒整数，NULL 用 SQL NULL，绑定与扫描集中在一组转换函数里；
    覆盖临时表、状态表、聚合结果与 CSV 读回；
  - 任务状态、分区状态两张表保留业务语义、重写存取（SQLite 支持 `INSERT OR REPLACE`、`ON CONFLICT … DO UPDATE`）；
  - 列信息从 `information_schema` 改为 `pragma table_info`；
  - 导出 CSV、读回 CSV 改用 Go 的 `encoding/csv` + `compress/gzip` 流式实现，替代 DuckDB 的 `COPY … TO` 与 `read_csv`；
  - **维护流程**：`CHECKPOINT` 改为 `PRAGMA wal_checkpoint(TRUNCATE)`；库大小统计从 DuckDB 的 `PRAGMA database_size` 改为 `page_count`、`freelist_count` 与 `page_size`；
    压缩从 `COPY FROM DATABASE` 改为 `VACUUM INTO` 新文件 → 关闭连接 → 原子替换 → 重新打开；
  - **文件大小**：SQLite 的 WAL 文件是 `<库>-wal`（DuckDB 是 `.wal`），`FileBytes` 与心跳上报的暂存库大小按新文件名统计；
  - 内存上限从 DuckDB 的 `memory_limit` 改为 SQLite 的 `cache_size`；
  - 写入继续“先进临时表、按主键比对只写变化行”，比对改用 SQLite 的 `IS NOT`。
- 暂存库文件改名为 `<root_dir>/.state/staging.db`。导出文件的路径与命名规则不变，CSV 的具体格式按新实现确定（D15，不要求与旧输出一致），写进[归档](../模块/归档.md)。
- 去掉 cgo 后，`build.sh archive-worker` 可在任意平台交叉编译，删除 `moox-cli setup build-linux --module archive-worker` 这条“必须在 Linux 上构建”的要求。
- 切换（D15）：与 4.9 的切换顺序合并执行（先停旧 worker 与旧 mgr，再激活新 control，最后删除旧数据、部署新 worker、重建任务）。

### 4.12 运维机外部程序支持 Windows（解决 G12 的另一半）

- **因子引擎的集合锁**：`internal/setlock` 拆成 `locks_unix.go`（`flock`）与 `locks_windows.go`（`LockFileEx` / `UnlockFileEx`，`golang.org/x/sys/windows`），语义不变：非阻塞加锁、失败重试、退出释放。
- **Windows 服务**：两个程序在 Windows 上作为服务运行，接入 `golang.org/x/sys/windows/svc`：收到停止请求时走与 SIGTERM 相同的优雅退出；
  服务恢复策略设为失败后 10 秒重启；开机自动启动（延迟启动）。程序提供 `service install|uninstall|start|stop` 子命令，避免依赖第三方服务包装器。
- **安装脚本**：新增 `scripts/deploy/deploy-factor-engine.ps1`、`deploy-archive-worker.ps1`，与现有 bash 脚本做相同的事：渲染配置、放置密钥、注册服务、等待 `health` 通过。
  默认安装到 `%LOCALAPPDATA%\moox\<程序>`，不放在“文档”等受保护目录。
- **私密文件权限**：Linux 上靠 `Mode().Perm() == 0600` 判断，Windows 的文件模式表示不了这个，ACL 正确也会被拒绝。需要统一成按平台检查
  （Unix 看 0600，Windows 看 ACL 只允许当前用户访问、不含 Everyone、Users 等组）：
  - 网关签名密钥：`packages/gatewayauth/secret_file_windows.go` 已有 Windows 实现，核对语义；
  - **EventBus 凭据**：`packages/jetstream/credentials.go` 无条件要求 0600，因子引擎读取 `factor-eventbus.yaml` 时会被拒绝、消费者起不来，必须改成平台检查；
  - 其他启动时读取的私密文件（health 认证、Access 密钥）逐一核对。
- **目录同步**：archive-worker 写分区文件与 `_dataset.json` 后对目录 `fsync`（`export.go` 的 `syncDir`），Windows 不支持，错误会让任务失败。
  拆成平台实现，Windows 上跳过目录同步（仓库已有同样做法：`modules/admin/internal/privatefiles/sync_windows.go`）。
- **磁盘余量**：`internal/worker/app/disk_other.go` 在非 Unix 平台始终返回错误，Windows 上心跳一直上报零容量，`min_free_bytes` 的停止领取保护也失效。
  补 Windows 实现（`GetDiskFreeSpaceEx`）。
- **构建**：`build.sh` 增加 `windows/amd64` 目标；CI 增加两个程序的 Windows 交叉编译检查。

### 阶段 7a：单元升级能力（反向连接与 archive-mgr 并入的前置）

**现状**（2026-10-18 核实）：
- 目标端已经支持新发布：`moox-runtime deploy` 收到新请求（新软件包）会准备新候选、停旧进程、独立复制状态、激活，失败自动恢复；
  `moox-runtime bootstrap` 在上次已完成、请求不同的情况下重新捕获 control 上的 host 与 control 单元，复制 Admin 数据，
  离线重签材料（沿用 CA 与 KeyID），准备、激活并按依赖顺序启动，失败恢复旧发布。
- 卡住的是操作员侧：软件只取首次初始化的 `core-software.json`；每个单元只有一条 `operation.json`，control 只有一个 `control-operation.json`，
  重试必须与首次请求逐字一致；`bootstrap --stage control` 还会把 Storage 与出口单元当作依赖重新部署。
- 生产的私有部署状态在操作员机器的 `~/moox-state`（runtime 身份、core/control 收据、各主机与业务单元的操作记录、导出材料）。

**设计**：

1. **版本制品与身份分开**：状态目录里身份类文件（`runtime-identity.json`、core/control 收据、导出材料、操作员 pin）保持不动；
   软件按版本放在 `releases/<版本 ID>/`，`release.json` 记录来源提交、目标架构、各单元软件包（host、control、access、egress-proxy、trade，
   有 Storage CGO 二进制时加 storage）的摘要与清单、运行助手及其摘要。
   新命令 `moox-cli setup release build --release <ID>`：要求工作区干净，在本机关闭 CGO 构建纯 Go 组件与前端（Storage 用 `--storage-binary-dir`），
   打包并独立校验后原子写入；同一 ID 已存在且内容一致时直接复用，不一致拒绝。读取时与 `core-software.json` 相同的独立校验。
2. **按版本记录操作**：`setup deploy-host`、`setup deploy-unit` 增加 `--release <ID>`。带版本时操作记录放在
   `<单元状态>/releases/<ID>/operation.json`，使用该版本的软件包与助手，每个版本操作各自导出一次材料（反映当前拓扑与服务目录），
   重试同一版本时要求与该版本首次请求一致（沿用现有重试语义）。不带 `--release` 时行为不变（修复首次安装的发布）。
   新主机（例如 192）直接用 `--release` 部署，不再依赖首次初始化的软件。
3. **control 升级**：`setup bootstrap --stage control --release <ID>` 用该版本的 host 与 control 软件包、按当前 `moox.toml` 重新生成环境与 control 配置覆盖，
   请求绑定记在 `control-operations/<ID>.json`（每个版本一条，替代单一绑定），目标端走 `moox-runtime bootstrap` 的再执行路径；
   带版本时不再顺带部署 Storage 与出口单元，只核验它们已有操作记录。成功后更新 `control-ready.json`（记录版本 ID）。
   **代价**：control 升级会停止并按顺序重启 control 上的 host 与 control 两个单元（Admin → 网关 → EventBus → HostAgent → 其余），
   期间 control 上的服务短暂不可用；目标端设置 bootstrap 屏障，守护这段时间不会插手。
4. **发布顺序**（服务目录变化时）：其他主机的 host 单元（网关）→ control 升级（同时更新 control 上的网关、Admin、Monitor 等）→ 其他主机的业务单元。
   不变化时可只升级相关单元。每一步由用户确认。
5. **与现行二进制替换的关系**：`native-release.sh` 的二进制替换继续用于小改动；需要更新运行计划、配置、身份投影或新增组件时用版本升级。
   版本升级生成的新发布里二进制与配置都来自版本制品，之前手工替换的二进制与手工修改的配置会被新版本覆盖（发布前核对手工改动是否已进仓库）。

**测试**：版本制品构建、读取、篡改检测与重复构建；带版本的操作记录路径、重试一致性与不同版本互不影响；control 升级的请求绑定与不顺带部署依赖；
命令参数。Linux 门禁：用“旧初始化状态＋新版本”部署一台新主机、升级一个已安装的业务单元、升级 control。

### 阶段 7：192 登记与失联原因区分

失联原因区分（4.7）与资源告警对齐（G9）已在 2026-10-18 完成并上线。192 接入改为主机网关反向连接（4.6、D17），分为以下几块。

**前置条件：单元升级能力**，见下面的“阶段 7a”。

- **服务目录与拓扑**（服务目录变化，须整体发布）：`servicecatalog.Host.Reachability`、`DirectoryHost.Relay`、校验规则；
  新增中转 ACL（可打开中转流的调用方：服务目录里能调用出站主机上任一服务的调用方，以及 Monitor 的健康探测）；编译后的 control 快照带上出站主机及其允许的端口清单。
  **`Relay` 进入目录哈希**：调用方按自己认识的字段重算目录哈希，旧客户端会拒绝含新字段的目录、没有缓存时起不来，
  所以目录 protobuf、转换、缓存校验一并修改，并且**全部目录消费者**（HostAgent、Access、Storage、Trade、Strategy、Collector、CloudNode、factor-mgr、Monitor、Admin、操作端 CLI、
  运维机上的因子引擎与 archive-worker 等用网关客户端的程序）都要重编并发布，完成后才登记第一台出站主机。
- **配置与 Admin**：`moox.toml` 的 `[[hosts]]` 增加 `reachability`；Admin 主机登记增加 `c_reachability` 列（默认 `direct`，带枚举约束）与 SysDeploy 接口字段、控制台展示；
  拓扑投影与放置同步带上该字段；出站主机的网关证书增加 `ClientAuth` 用途，材料包与安装器的证书校验更新（`control.target` 仍是 control 公网地址:11003）。
  **Admin 没有自动迁移**（只执行 `CREATE TABLE IF NOT EXISTS`），生产库要在启用新 Admin 前显式变更：在线备份 → 加列 → 核验现有主机都是 `direct`。
- **主机网关**：
  - control 侧：11003 在 listener 层按 ALPN 分流（attach、打开流独占连接，其余交给 tRPC 子 listener）；双向 TLS 校验出站主机证书、签名与登记状态；会话表（每主机一个、新替旧）；
    流的端口清单校验与字节透传；连接保护（握手超时、单 IP 并发、流数上限）；会话状态写进网关心跳。
  - 出站主机侧：会话拨号、attach、心跳、退避重连；收到流时只连本机允许的端口。
  - 多路复用库选型（候选 `hashicorp/yamux`，纯 Go）在实现时确定并写进记录。
- **网关客户端**：自定义连接池拨号器，遇到 `Relay` 时经 control 打开流再做端到端 TLS，返回最终连接；覆盖 CLI 的 SSH 隧道模式；只读请求的重试、目录刷新语义不变。
- **Monitor**：出站主机的部署探测经中转拨号；新增反向连接检查（会话断开 3 分钟告警）；告警正文区分“反向连接断开”与“主机宕机”。

## 6. 风险与回退

| 风险 | 应对 |
| --- | --- |
| 守护在发布过程中误拉进程 | 复用维护锁与暂停、停止中标记；发布流程本就持锁 |
| 持续崩溃时守护反复拉起拖垮主机 | 退避（4.1 第 6 步）；持续崩溃升级告警由人处理 |
| 告警风暴 | 合并窗口、主机重启合并、按问题类型限频 |
| 缓存里的 webhook 泄露 | 文件 0600、只在部署用户可读目录；不写日志、不进命令行参数 |
| 守护本身出错导致大量误操作 | 先上线阶段 2 的只记录模式，在测试机与 compute-1 观察一段时间后再开启拉起 |
| cron 守护进程缺失 | 安装时检查并报错 |
| archive-worker 换存储后行为变化 | 现有测试全部迁移到 SQLite 上通过，并补导出、读回、压缩的往返测试；切换时从空数据开始（D15），不存在新旧数据混用 |
| Windows 上的行为差异（文件锁、路径、服务停止） | 只在 Windows 实机验收通过后才在 Windows 上部署；Linux、macOS 的行为不受影响 |

**回退**：默认回退只删除各主机的 `# moox-watchdog` 条目来停用守护（组件进程不受影响），保留新版 `moox-runtime`。
因为不改 PID 记录结构（D12），必要时也可以按既有发布流程把 host 单元回滚到上一版本，旧版 runtime 仍能读取记录并启停组件；回滚前先停用守护。
阶段 5 回退时 Admin 恢复为不推送证书告警（即现状），`GetHostPolicy` 与缓存文件保留不影响其他功能。
archive-mgr 并入与 archive-worker 换存储按 D15 不保留旧数据，回退即重新部署上一版本并从空数据开始，不做数据回退。

### 9.2 192 的网络条件

- 192 只有家庭网络的内网地址 `192.168.0.103/24`（网关 192.168.0.1），没有公网地址；control 到 `192.168.0.103` 的 TCP 连接超时（22 端口也不通）。
- 192 上的程序都是出站访问（因子引擎、archive-worker 经 storage 的 Access），因此目前运行正常。
- 按完整 host 单元部署后，Monitor 会从 control 探测 192 上主机网关与 HostAgent 的健康端口，在网络打通前会持续报“服务不可用”。
  最初选择了第 1 种（反向隧道），发布前核实不可行，改为主机网关反向连接（4.6、D17）。核实到的前提：192 到 control 的 22 端口可达；192 上还没有到 control 的免密登录与主机指纹；
  control 的 sshd 是默认配置（`GatewayPorts no`、允许 TCP 转发），control 私网地址 10.1.12.13。可选方式：
  1. **192 主动建立到 control 的反向隧道**（SSH `-R` 或 WireGuard），把 192 的健康端口与网关跨主机端口映射到 control 的私网侧，Admin 中登记的访问地址指向隧道端；
     不需要改家庭路由器，但隧道本身要纳入看护（192 上的 systemd 服务）。
  2. **家庭路由器做端口映射**到 192，并在云安全组里只放行 control 的出口地址；需要家庭宽带有固定公网 IP 或动态域名。
  3. **组网**（WireGuard 等）把 192 接入云上的私有网络，Admin 中登记 192 的组网地址。

### 9.3 发布影响面与耗时

- 计划 4.4 新增的 Monitor 方法属于服务目录变更：Admin、全部主机网关、Monitor 同一提交构建、同批替换（既有规则）。
  阶段 4（各主机 host 单元整体重新发布）与阶段 8（control 单元整体重新发布）本来就要按当前服务目录重新打包，服务目录变更并入这两次发布，不单独再发一次。
- 现有台账（`/data/moox/run/release-ledger.log`）显示单个组件替换并重启约 3～4 秒；整体激活需停止全部组件、复制状态、逐个等待就绪，
  control 有 9 个组件（并入后 10 个），按此估计整体激活在 1～2 分钟量级。实际耗时在第一次整体发布时记录，之后据此安排窗口。

### 9.4 HostAgent 采样对齐

每次采样是每台主机一条 EventBus 消息与一次 Monitor 写 `mooxsys` 的 `UpsertFields`，改为每 15 秒的负载可以忽略；
但视图每个序列只保留最近 5000 根，主机指标历史会缩短到约 21 小时。结论：保持每分钟采样，调整告警的连续次数（见阶段 7）。

### 阶段 10：archive-worker 暂存改用 SQLite（2026-10-18 完成）

- `internal/worker/staging` 改用纯 Go SQLite（`glebarez/go-sqlite`，单连接，WAL、`synchronous=NORMAL`、`cache_size` 由配置给出）：
  每个任务一张 `WITHOUT ROWID` 暂存表加 data_time 索引；任务状态与分区状态两张表也是 `WITHOUT ROWID`；
  所有时间列（行键、分区范围、各状态时间、统计的最小 / 最大时间、水位、首次起点）统一存 Unix 纳秒整数，转换集中在 `nanos` / `fromNanos` / `nullNanos` / `scanNanos`；
  布尔存 0/1；写入值按列类型转换（`bindValue`），比对改用 `IS NOT`；列信息用 `pragma_table_info`、暂存表清单用 `sqlite_master`。
- 导出与读回：新文件 `csvio.go` 自带最小的 RFC 4180 读写（`encoding/csv` 读不出字段是否带引号，无法区分缺失值与空字符串），
  流式写出 gzip / 未压缩 CSV、流式按批读回；格式写进 `docs/模块/归档.md`（时间保留纳秒，浮点最短可往返且整数值带 `.0`，二进制 base64）。
  NaN 在 SQLite 里存为缺失值（已在文档与测试中注明）。
- 维护：`PRAGMA wal_checkpoint(TRUNCATE)`；大小按 `page_count`、`freelist_count`、`page_size` 计算；压缩用 `VACUUM INTO` 新文件 → 关闭 → 原子替换 → 重新打开，
  同时清理 `-wal` / `-shm`；`FileBytes` 统计 `<库>-wal`。删除 DuckDB 临时目录及其清理（`TempDir`、`CleanTemp`）。
- 配置：`staging.memory_limit` 与 `staging.threads` 改为 `staging.cache_size`（默认 256MB，不小于 1MB）；暂存库改名 `.state/staging.db`。
- 去掉 cgo：go.mod 不再依赖 DuckDB；`build.sh archive-worker` 以 `CGO_ENABLED=0` 构建，`linux/amd64`、`linux/arm64`、`darwin/arm64`、`windows/amd64` 交叉编译均通过；
  `moox-cli setup build-linux` 与 `build-storage-linux.sh` 不再接受 archive-worker；部署脚本改为纯 Go 构建。
- 测试：原有暂存测试全部改为 SQLite 后通过（只写变化行、批内去重、大批量、加列、导出排序与空串 / 缺失值、定稿原子性、读回不触发重写、删除、重开、压缩、待上报、首次起点、实例绑定）；
  新增纳秒键不互相覆盖并在 CSV 中保留、全部列类型经导出—定稿—读回逐字段一致、损坏文件读回报错且不留下半个分区。

### 阶段 11：运维机外部程序支持 Windows（2026-10-18 代码完成，实机验证待以后）

- 私密文件：`packages/security.CheckPrivateFile`——普通文件、不是符号链接、只有当前用户能访问；Unix 看 0600，
  Windows 读 DACL（只允许当前用户、SYSTEM、Administrators 的允许项，没有 DACL 或出现其他账户 / 组即拒绝，报错里给出 icacls 修复命令）。
  EventBus 凭据（`jetstream.LoadCredentialFile`，因子引擎读 `factor-eventbus.yaml`）与签名密钥（`gatewayauth.ReadSigningSecret`，Access 密钥与 Storage 鉴权密钥）改用它；
  此前 Windows 上签名密钥完全不检查、EventBus 凭据一律拒绝。服务器侧的网关凭据注册表等不在运维机上读取，未改。
- 因子引擎集合锁：`setlock` 的文件锁拆成 `filelock_unix.go`（flock）与 `filelock_windows.go`（`LockFileEx` 锁第一个字节，`LOCKFILE_FAIL_IMMEDIATELY`），语义不变。
- archive-worker：目录 fsync 拆成平台实现（Windows 跳过）；磁盘余量补 Windows 实现（`GetDiskFreeSpaceEx`，可用量按当前用户配额）。
- Windows 服务：新共享包 `packages/servicehost`（`golang.org/x/sys/windows/svc`）。两个程序新增 `service install|uninstall|start|stop` 子命令：
  开机延迟自动启动，异常退出（含非零退出码）10 秒后重启；服务收到停止 / 关机请求时取消 ctx，走与 SIGTERM 相同的优雅退出（引擎调用 tRPC `Server.Close`），
  最多等 60 秒；服务进程把工作目录切到 `<安装目录>`（`bin` 的上一级）。Linux / macOS 上 `service` 子命令报错并提示用 systemd / launchd 脚本。
- 安装脚本：`scripts/deploy/deploy-factor-engine.ps1`、`deploy-archive-worker.ps1`（管理员运行）——默认装到 `%LOCALAPPDATA%\moox\<程序>`，拒绝“文档”目录；
  渲染与 bash 脚本相同的配置；密钥目录与文件收紧为只允许当前用户与 SYSTEM（服务以 LocalSystem 运行）；生成健康检查凭据并写进服务的环境变量；注册并启动服务、等待 `health` 通过。
  `TARGET_GOOS=windows TARGET_GOARCH=amd64 scripts/build/build.sh factor-engine|archive-worker` 产出 `.exe`。
- CI：`.github/workflows/ci.yml` 新增 `windows-external` 作业（`windows-latest`）：运行 security（含 Everyone 可读被拒、收紧后通过）、servicehost、
  因子引擎集合锁与入口、archive-worker 全部 worker 包与入口的测试，jetstream 做 Windows 编译检查，并用 PowerShell 解析器检查两个脚本的语法。
  jetstream 的 0600 测试在 Windows 上跳过（ACL 由 security 的 Windows 测试覆盖）。
- 本机验证：两个程序 `GOOS=windows` 编译与 `go vet` 通过；Unix 上全部相关测试通过。CI 结果要等推送后看；
  作为服务安装、开机自启、被结束后 10 秒内拉起、实际计算一期，按用户决定以后在 Windows 实机上验证。
- 推送：本阶段改了 `.github/workflows/ci.yml`，钥匙串令牌缺 `workflow` 权限，经终端面板用用户的令牌推送（已推送）。
