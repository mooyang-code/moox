# 主机守护与告警高可用执行计划

> 状态：执行计划 v2（2026-10-18，尚未编码）。依据 2026-10-18 的讨论与线上只读核查；v2 吸收了一轮 Codex 审查（12 条，均已核实处理）。
> 实现后以[部署与运维](../部署与运维.md)、[监控](../模块/监控.md)、[主机代理](../模块/主机代理.md)为准。

## 1. 目标

1. **进程看护**：每台主机上由 `moox-runtime` 管理的组件，崩溃后自动拉起，主机重启后自动启动；不误拉有意暂停的组件，不和发布、重启抢操作。
2. **拉起告警**：每次自动拉起都推送企业微信（或飞书），写明主机、组件、原因、结果和崩溃线索；反复崩溃时退避并升级告警，不刷屏。
3. **告警配置单一来源**：告警渠道只在一处维护（Monitor 的通知渠道），各主机自动拿到最新值；在控制台或 `moox.toml` 修改后，全部主机在约 5 分钟内生效，不需要重新部署。
4. **没有监控盲区**：任何一台主机失联都有人告警，包括运行 Monitor 的 control 自己，以及目前没有登记成主机的因子引擎机器。

非目标：不引入新的常驻进程，不改变 systemd 已管理服务（因子引擎、归档）的看护方式，不做多 Monitor 实例选主。

## 2. 现状核查（2026-10-18，只读）

### 2.1 进程看护

| 主机 / 组件 | 看护方式 | 崩溃后 | 主机重启后 |
| --- | --- | --- | --- |
| 192（编译机）：`moox-factor-engine`、`moox-archive-worker` | systemd 用户服务，`Restart=always`，`Linger=yes`，已 `enable` | 10 秒后自动拉起 | 自动启动（2026-10-18 10:58:39 开机，10:58:47 引擎已启动） |
| control：admin、host-gateway、monitor、eventbus、collector、strategy、factor-mgr、cloudnode、web-host、console-proxy、host-agent | `moox-runtime start` 拉起后父进程为 1，**无 systemd、无 crontab、无定时器** | **不会拉起** | **不会启动** |
| control：`moox-archive-mgr` | systemd 用户服务 | 自动拉起 | 自动启动 |
| storage、compute-1 | 与 control 同一套原生部署，推断相同 | 待阶段 0 核实 | 待阶段 0 核实 |

control 自 2026-09-25 起没有重启过，所以问题还没暴露。

**缺口的来历**：旧部署器每台主机装有一条 `# moox-healthchecks` crontab，每分钟遍历各包的 `healthcheck.sh`
（`modules/cli/internal/setup/deploy/deploy.go` 的 `install_healthcheck_cron`）。切换到原生部署时，
[网关与服务部署重构执行计划](网关与服务部署重构执行计划.md)第 13 节先删除了这条 crontab，防止旧脚本误拉进程；之后原生部署没有补装定时调用。

**现成的守护能力**：`moox-runtime healthcheck`（各包 `healthcheck.sh` 调用的就是它）已经是完整的单次守护检查，
见 `modules/cli/internal/setup/unitruntime/runtime.go` 的 `healthcheck`：

- 有暂停标记（`run/paused/<组件>`）或停止中标记（`run/draining/<组件>`）时不动；
- PID 记录不存在或进程已不在时直接启动；
- 进程在但带签名的 `/healthz` 失败时，先按预算停止再启动；`/readyz` 未就绪不触发重启；
- 与安装器、启停共用维护锁（`run/maintenance.lock`），锁被占用时整体跳过；存在 `run/bootstrap.json` 或 `run/installation.json`
  （bootstrap、发布未完成的持久屏障，跨重启保留）时整体跳过；
- 用 pidfd + 可执行文件 inode + start ticks 核对进程身份，不会认错或误杀。

**会让组件一直起不来的边界问题**（读代码确认）：

1. PID 记录指向的 PID 在重启后被别的进程复用时，身份核对返回 `errIdentity`，`healthcheck` 报错且**不拉起**。
2. 停止过程中被中断（包括关机，也包括调用方超时取消了 `stop`）留下的 `run/draining/<组件>` 会一直保留，按设计守护不得重启，该组件**一直不会被拉起**
   （`runtime_linux_test.go` 有测试明确覆盖“取消后保留标记”）。
3. 发布或 bootstrap 中断留下的 `run/installation.json` / `run/bootstrap.json` 会让整机的 `healthcheck` 一直跳过；这两个屏障有恢复流程，不能按开机时间直接删除。
4. **启动有依赖顺序**：主机网关要等 Admin 完成同步才就绪，HostAgent 要 EventBus；`start` 会等待就绪，超时会停掉进程。
   bootstrap 的恢复流程按 `admin → host-gateway → eventbus → host-agent → 其余组件` 跨单元启动（`unitbootstrap/recover.go` 的 `startStages`）。
   按单元逐个执行 `healthcheck`（先 host 单元）在 control 冷启动时会卡在等待网关就绪上。

### 2.2 告警链路

| 能力 | 现状 |
| --- | --- |
| 组件不可用 | Monitor 按部署对各组件做 HTTP/TCP 探测，失败 3 次告警（严重）；只告警，不拉起 |
| 主机失联 | HostAgent 每分钟经 EventBus 上报快照，Monitor 3 分钟收不到即推送“主机 X · 失联”，恢复后推送“已恢复在线” |
| 主机网关 | 每台主机网关的心跳、实例冲突、路由同步合成 `gateway:<主机>:status` 一条检查 |
| 数据中断 | 采集、存储、视图、因子、策略的数据集新鲜度与 K 线新鲜度检查 |
| 推送 | Monitor 发往 `t_monitor_notification_channels` 中的全部渠道；持续未恢复每 5 分钟提醒一次 |
| 证书到期 | Admin 证书巡检已实现，能读 `MOOX_NOTIFICATION_WEBHOOK_URL` 直接推送；但原生部署只给 Monitor 注入通知变量（`unitdeploy/unit.go`，测试明确要求 Admin 不含），生产 `runtime-admin.json` 也没有，**目前只记录不推送** |
| Monitor 自身失效 | Monitor 检查结果写库失败时不会执行告警回调（`scheduler.go`），而 `/healthz` 仍返回存活，进程不会被判为故障 |

Monitor 已登记的主机（`t_monitor_host_agents` 与 `t_monitor_gateway_observations`）：control、storage、compute-1，均在线。

### 2.3 告警链路的缺口

| 编号 | 缺口 | 影响 |
| --- | --- | --- |
| G1 | control（以及推断的 storage、compute-1）上的组件没有看护 | 崩溃后只告警不恢复；主机重启后整机业务停摆 |
| G2 | 重启后的两个边界问题（2.1 末尾） | 即使补上定时调用，重启后也可能有组件起不来 |
| G3 | 告警地址有多份副本：Monitor 库（控制台可改）、Monitor 环境变量（种子）、`moox.toml`；Admin 没有地址 | 改 `moox.toml` 不会同步到 Monitor（只在首次建库时写入）；证书到期告警发不出去 |
| G4 | control 失联无人告警：Monitor、EventBus、推送都在 control 上 | 最严重的故障反而没有告警。文档提到的“SCF 哨兵”在代码中不存在，11409 只是在防火墙上对公网开放，没有调用方 |
| G5 | 192 没有登记成主机 | 机器失联只能从“因子数据不新鲜”间接发现，看不出是机器问题 |
| G6 | host-agent 进程停止会被报成“主机失联” | 告警原因不准，排查方向错误 |
| G7 | 主机失联、组件拉起等告警没有在生产演练过 | 链路是否真的能送达未经证实 |
| G8 | Monitor 进程活着但评估或写库停滞 | 所有 Monitor 侧告警静默失效，进程和网关看起来都正常 |
| G9 | 主机资源告警的阈值按“每 15 秒采样”设计（`default_alerts.go` 的注释与次数），HostAgent 实际每分钟采样一次 | CPU、内存告警要约 12、20 分钟才触发，而不是设计的 3、5 分钟 |

## 3. 设计决策

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| D1 | 复用 `moox-runtime healthcheck` 的判断，不写按进程名 `ps | grep` 的守护脚本 | 按名字判断分不清新旧版本和暂停中的组件，`kill -9` 同名进程有误杀风险，还会和发布、`restart.sh` 抢操作 |
| D2 | 定时方式用 crontab，每台主机一条，带标记 `# moox-watchdog` | 用户选定；不依赖 systemd 用户会话；与旧方案一致；开机后 cron 每分钟运行，最多 1 分钟即拉起，不需要 `@reboot` |
| D3 | 新增 `moox-runtime watch` 子命令遍历本机全部单元，而不是在 crontab 里写 shell 循环 | 台账、退避、告警合并需要状态与测试；纯 Go，可在 Linux 内核门禁里测 |
| D4 | 已由 systemd 管理的服务（因子引擎、归档）不纳入 watch | 两套看护会互相打架；systemd 已提供自动拉起 |
| D5 | 守护直接推送企业微信 / 飞书，不经过 Monitor | 挂掉的可能正是 Monitor 或 EventBus；共享的 `notification` 包已支持直接发送（Admin 证书巡检用的就是它） |
| D6 | 告警渠道的唯一来源是 Monitor 的通知渠道；`moox.toml` 的 `[notification]` 只作初始化种子 | 控制台已能增删和测试，支持多个渠道 |
| D7 | 主机通过 host-agent 拉取“主机策略”并缓存到本机文件，`moox-runtime` 只读文件 | `moox-runtime` 的设计原则是不联网、不持有网关凭据；host-agent 已常驻每台主机 |
| D8 | 不用 EventBus 推送告警配置 | 要让告警密钥进入消息流并单独收紧权限；EventBus 本身也在 control 上 |
| D9 | control 失联由其他主机交叉检查：与 control 主机网关做 TLS 握手，用 MooX 私有 CA 校验证书 | 每台主机都有私有 CA；不需要分发 control 的健康密钥；只依赖网络与 control 的网关进程 |
| D10 | 192 按完整 host 单元部署（host-gateway + host-agent）并登记为主机 | Admin 登记主机会自动添加全部 host 范围组件，拓扑校验要求它们存在（`sysdeploy/topology.go`、`servicecatalog/routes.go`）；只装 host-agent 会留下不存在的网关部署而持续告警，策略拉取也没有本机网关可走 |
| D11 | watch 按跨单元依赖顺序检查，与 bootstrap 恢复顺序一致 | 冷启动时网关依赖 Admin、HostAgent 依赖 EventBus |
| D12 | 不改 PID 记录结构，用记录已有的 `StartedAt` 与本次开机时间比较识别上次开机的记录 | 旧版 runtime 按严格模式解析记录（`DisallowUnknownFields`），加字段后回滚旧版会失去启停能力 |

**借鉴的外部脚本做法**（参考 trpc 的 `monitor.sh` / `start.sh` / `stop.sh`）：
进程消失时扫描最近日志里的 `panic:`、`fatal error:`、`SIGSEGV` 并限频；每种处置给出明确的原因分类；记录检查与启动历史；
cron 层用 `flock -n` 保证同一时刻只有一轮在跑。不借鉴：按进程名判断与 `kill -9`、`pid.conf`、`curl` 拉取配置。

## 4. 详细设计

### 4.1 `moox-runtime watch`

```text
moox-runtime watch --root /data/moox [--dry-run]
```

每轮流程：

1. **枚举单元**：`<root>/*/current/runtime.json`（跳过 `.next`、`.previous`、`.failed`），按主机身份 `run/host.json` 校验，不跨主机。
2. **持久屏障**：存在 `run/bootstrap.json` 或 `run/installation.json` 时整轮跳过，结果记为 `skipped_bootstrap` / `skipped_installation`，
   并按 4.3 推送“需要人工恢复”（附对应的恢复命令）；不自动删除这两个文件。
3. **上次开机的残留**（解决 G2 的 1、2）：
   - PID 记录的 `StartedAt` 早于本次开机时间（`/proc/stat` 的 `btime`）：是上次开机的记录，删除后按“已停止”处理，不再走身份核对。不改记录结构（D12）。
   - `draining` 标记的时间早于本次开机：进程必然已不在，清除标记并按“已停止”处理，告警里注明“停止过程被关机打断”。
   - 本次开机内留下的 `draining`（例如人工 `stop` 被打断）：不自动清除，推送“需要人工处理”，附 `moox-runtime stop --components <组件>` 续停命令。
   - `paused` 标记保持不动（这是用户的意图）。
4. **按依赖顺序逐组件检查**（D11）：先 `admin`、`host-gateway`、`eventbus`、`host-agent`（各自所在单元），再按各单元 `runtime.json` 的顺序检查其余组件；
   依赖组件本轮没能就绪时，依赖它的组件本轮跳过（记 `skipped_dependency`），下一轮再试。
   调用与 `healthcheck` 相同的逻辑，返回结构化结果：`healthy`、`started`（原来没在运行）、`restarted`（健康检查失败后重启）、`start_failed`、
   `not_ready`（进程活着但 `/readyz` 持续失败）、`skipped_paused`、`skipped_draining`、`skipped_locked`、`skipped_dependency`、`identity_error`。
5. **崩溃线索**：结果为 `started` 或 `restarted` 时，读取该组件日志末尾 1000 行，提取最后 3 条匹配 `panic:|fatal error:|runtime error:|SIGSEGV|SIGABRT|\[PANIC\]` 的行，
   以及进程退出码（能取到时）；同一组件 60 秒内只扫描一次。
6. **台账**：每次非 `healthy` 的结果追加到 `run/watchdog/<组件>.jsonl`（时间、结果、原因、耗时、线索摘要），保留最近 30 天，随 runtime 的日志轮转清理。
7. **持续崩溃与退避**：按“自动拉起次数”统计，不只看启动失败——组件启动成功后又崩溃，每轮都能“拉起成功”，只数失败永远累计不到。
   同一组件 10 分钟内被自动拉起（`started` / `restarted`）或拉起失败合计 3 次，进入“持续崩溃”：之后每 5 分钟才尝试一次，连续 1 小时仍在崩溃改为每 30 分钟一次。
   连续稳定运行 10 分钟（期间每轮都是 `healthy`）才判定恢复并清零。状态保存在 `run/watchdog/state.json`。
8. **未就绪告警**（解决 G8 的一部分）：进程活着但 `/readyz` 连续 5 分钟失败的组件，不重启（遵守 runtime 的约定），推送“组件持续未就绪”。
   Monitor 的 `/readyz` 增加“最近一次评估完成时间”判断：超过 3 分钟没有完成评估即返回未就绪，这样 Monitor 写库或调度停滞时，control 上的 watch 会直接推送告警。
9. **告警**：见 4.3。
10. **输出**：一行 JSON 汇总写到 stdout（cron 重定向到 `run/watchdog.log`），包括每个组件的结果与耗时。

维护锁被占用时整轮跳过并记录一行；单个组件出错不影响其他组件。
**没有整轮硬超时**：硬超时会取消正在执行的 `stop`，留下 draining 标记反而让组件永远起不来。改为“软期限”：一轮开始 4 分钟后不再开始新的组件检查，
已经开始的启停按 runtime 自己的完整预算执行完；cron 那一层的 `flock -n` 保证下一分钟不会叠加新一轮。

### 4.2 crontab

每台主机、部署用户各一条：

```cron
* * * * * PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin flock -n /data/moox/run/watchdog.lock /data/moox/host/current/bin/moox-runtime watch --root /data/moox >>/data/moox/run/watchdog.log 2>&1 # moox-watchdog
```

- **安装时机**：host 单元安装或激活时写入（`moox-runtime` 随 host 包装到每台主机）。按标记替换，幂等；写入后用 `crontab -l` 校验。
- **前置检查**：cron 守护进程不存在或不在运行时安装失败并报错，不静默跳过。
- **卸载**：卸载 host 单元时删除这一行。
- **旧条目**：发现旧的 `# moox-healthchecks` 条目时一并删除（原生部署不再使用它）。
- **日志**：`run/watchdog.log` 纳入 runtime 现有的日志轮转。

### 4.3 拉起告警

**渠道**：读取本机主机策略缓存（4.4）里的全部渠道，用共享的 `notification` 包发送（企业微信、飞书都支持）；
至少一个渠道送达即视为送达。推送失败只写日志，不影响拉起，也不重试。缓存缺失或没有渠道时，在日志里记录“没有可用的告警渠道”。

**消息**（示例）：

```text
【MooX 自动拉起】control · strategy · 已恢复
原因：进程不存在（上次运行 3 小时 12 分）
结果：拉起成功，健康检查通过（耗时 4.1 秒）
崩溃线索：panic: runtime error: index out of range [3] with length 3
近 1 小时自动拉起：1 次
时间：2026-10-18 14:03:12（北京时间）
```

**防刷屏**：

| 场景 | 规则 |
| --- | --- |
| 同一组件短时间多次拉起 | 10 分钟内最多一条，多出的次数合并进下一条 |
| 进入持续崩溃 | 立即发一条“持续崩溃，已降低拉起频率”（严重） |
| 持续崩溃后恢复 | 发一条“已恢复” |
| 主机重启后首轮拉起多个组件 | 合并为一条“主机重启，已拉起 N 个组件：…”（附开机时间） |
| `identity_error`、`start_failed`、`not_ready`、持久屏障与残留标记需要人工 | 每种问题每 30 分钟最多一条 |

### 4.4 主机策略缓存与告警配置单一来源

**文件**：`<root>/run/host-policy.json`，0600，原子替换（写临时文件后 rename）。

```json
{
  "version": 7,
  "content_hash": "sha256:…",
  "source": "monitor",
  "fetched_at": "2026-10-18T06:00:05Z",
  "notification_channels": [{"type": "wecom", "webhook_url": "https://qyapi.weixin.qq.com/…"}],
  "watchdog": {"enabled": true, "merge_window": "10m", "crash_loop_failures": 3, "crash_loop_window": "10m", "crash_loop_retry": "5m"}
}
```

**拉取**：host-agent 启动时拉一次，之后每 5 分钟经本机主机网关调用 Monitor 新增的只读方法 `GetHostPolicy`
（服务目录新增调用方 `host-agent`，只读）；内容哈希变化才重写文件。拉取失败保留旧文件并记日志、上报指标。

**种子**：部署 host 单元时，部署工具用 `moox.toml` 的 `[notification]` 写一份 `source: "seed"` 的初始文件，保证首次拉取之前也能告警；
已有更新的 `source: "monitor"` 文件时不覆盖。

**修改路径**：

| 修改方式 | 生效过程 |
| --- | --- |
| 控制台「消息通知设置」增删渠道 | Monitor 库更新 → 各主机 host-agent 下次拉取（≤ 5 分钟）→ 缓存更新 |
| 修改 `moox.toml` 的 `[notification]` | `moox-cli config plan` 显示与 Monitor 现有渠道的差异 → 用户确认后 `config publish` 调用 `AddNotificationChannel` / `DeleteNotificationChannel` 写入 Monitor（moox-cli 已是这两个方法的合法调用方）→ 同上 |
| 需要立即生效 | `moox-cli config publish` 完成后通过 SSH 在各主机触发 host-agent 立即拉取（`moox-runtime` 不参与） |

`config plan` 同时列出各主机缓存的 `version` 与 `fetched_at`，可以看出哪台主机还没追上。

**接通证书告警**：Admin 证书巡检改为每次巡检时读取本机 `host-policy.json` 的最新渠道（取代从未在原生部署中注入的 `MOOX_NOTIFICATION_*` 环境变量，相关读取代码一并删除），
这样证书到期告警第一次真正能推送出去。Monitor 保持“只在首次建库时读取种子”不变。

### 4.5 control 交叉检查（解决 G4）

- storage、compute-1 上的 `watch` 每轮额外检查 control：与 control 主机网关的跨主机 TLS 入口建立连接并完成握手，用本机的 MooX 私有 CA 校验证书与主机名（5 秒超时）。
- 连续 3 分钟失败，用本机缓存的渠道推送“control 失联（由 storage 观测）”（严重）；恢复后推送“control 已恢复（由 storage 观测）”。状态保存在 `run/watchdog/peer-control.json`。
- 两台主机都会发送，同一件事最多两条，消息里写明观测方。
- 只有 control 的网关进程挂了而主机还在时也会触发；这种情况 control 自己的 watch 会在 1 分钟内把网关拉起，通常不会达到 3 分钟。
- TLS 握手只能证明 control 的网关入口活着，不能证明 Monitor 在正常评估；后者由 control 上 watch 的未就绪告警覆盖（4.1 第 8 步）。
  control 主机还在但 watch 自己也坏了（例如 cron 停了）的组合仍是盲区，由外部兜底覆盖。
- 可选兜底：在腾讯云配置云拨测探测控制台 9527，作为不依赖本系统的外部检查（运维配置，不在代码范围内）。

### 4.6 192 登记为主机（解决 G5）

按完整 host 单元部署（host-gateway + host-agent + `moox-runtime` 与 watch 的 crontab），在 Admin 登记主机（D10）。与其他主机一样，
由 watch 看护，HostAgent 经本机网关拉取主机策略。192 原有的因子引擎、archive-worker 仍是 systemd 用户服务，不纳入 watch。

阶段 0 需要确认 192 的网络条件：192 在内网（192.168.0.103），Monitor 按部署探测健康端口、跨主机 TLS 调用都需要 control 能访问到 192 的相应端口。
如果做不到，有两个选择，阶段 0 结束时由用户决定：
- 为 192 打通 control 到它的访问（隧道或端口映射）；
- 在服务目录里增加“出站专用主机”的形态：只要求 host-agent 与网关出站，Monitor 不对它做入站探测，失联只按 HostAgent 与网关心跳判断。这是服务目录变更，需要单独设计。

### 4.7 区分“主机失联”与“host-agent 停止”（解决 G6）

Monitor 的失联告警附带该主机网关心跳的状态：

- host-agent 静默且网关心跳也停 → “主机失联”（严重）；
- 只有 host-agent 静默 → “host-agent 停止上报”（警告），正文提示守护应在 1 分钟内拉起。

若 192 最终采用“出站专用主机”形态，仍有网关心跳可用，判断方式相同。

## 5. 阶段

每个阶段单独提交，阶段内的测试通过才进入下一阶段。

### 阶段 0：只读核查

- storage、compute-1 的看护现状（与 2.1 同样的盘点）；各主机 cron 是否安装并运行；部署用户能否写 crontab。
- 192 的网络条件：control 能否访问 192 的健康端口与网关跨主机端口（4.6）。
- control 冷启动演练的条件：用哪台机器演练 control 整机重启（生产 control 重启影响全部业务，需用户安排时间）。
- Monitor 新增方法的服务目录变更影响面：需要 Admin、全部主机网关、Monitor 同批发布（服务目录变更的既有规则）。

验收：本计划第 2 节的“待核实”项全部有结论，必要时修订本计划。

### 阶段 1：runtime 重启边界

- `record()` 用 `StartedAt` 与开机时间识别上次开机的记录（不改记录结构）；上次开机遗留的 `draining` 标记的处理（4.1 第 3 步）。
- `healthcheck` 与 `watch` 都使用这套判断，人工执行 `healthcheck.sh` 也能在重启后拉起。
- 测试：Linux 内核门禁新增“PID 被复用”“上次开机遗留 draining”“本次开机遗留 draining 不清除”三个场景；确认旧版 runtime 仍能读取新版写出的记录。

验收：在测试机上伪造上次开机的记录与标记，`healthcheck` 能拉起组件。

### 阶段 2：`watch` 子命令（只记录不告警）

- 单元枚举、持久屏障、依赖顺序、结构化结果、崩溃线索、台账、持续崩溃判定、未就绪判定、软期限、汇总输出。
- Monitor 的 `/readyz` 加入评估停滞判断（4.1 第 8 步）。
- 测试：用合成组件覆盖各结果分支；“启动成功后立即崩溃”能在 3 次内进入持续崩溃；软期限到期时正在执行的停止不被取消、不留 draining；
  依赖未就绪时下游跳过；维护锁占用、持久屏障存在时整轮跳过；单组件失败不影响其他组件。

验收：在测试机上 `watch --dry-run` 输出与实际状态一致；杀掉合成组件后一轮内拉起并写入台账；按冷启动顺序能把一套停掉的单元全部拉起。

### 阶段 3：拉起告警与本机缓存读取

- 读取 `host-policy.json`、消息模板、合并与退避规则、推送失败处理；部署时写入种子文件。
- 测试：用假渠道验证每种场景的消息内容与条数（含主机重启合并、持续崩溃升级与恢复）。

验收：测试机上杀掉组件，测试群收到一条“已恢复”；连续杀 3 次进入持续崩溃并收到升级告警。

### 阶段 4：crontab 接入部署

- host 单元安装、激活写入 crontab，卸载删除；cron 不可用时报错；清理旧 `# moox-healthchecks` 条目；日志轮转。
- 测试：契约测试覆盖幂等写入、替换、删除与 cron 缺失报错（用 `MOOX_CRONTAB_COMMAND` 替身，沿用旧部署器的做法）。

验收：在测试机上部署后 `crontab -l` 只有一条 `# moox-watchdog`；重复部署不产生重复条目。

### 阶段 5：告警配置单一来源

- Monitor 新增 `GetHostPolicy`（服务目录：调用方 `host-agent`，只读）；host-agent 定时拉取并原子写入缓存，上报拉取状态指标。
- Admin 证书巡检每次巡检时读取缓存中的最新渠道，删除不再使用的通知环境变量读取。
- `moox-cli config plan/publish` 新增“通知渠道”目标：比较 `moox.toml` 与 Monitor，确认后写入；列出各主机缓存版本；可选立即刷新。
- 测试：Monitor 方法与权限测试；host-agent 拉取、哈希不变不重写、失败保留旧文件；`config` 命令的计划与发布测试。

验收：在控制台修改渠道，5 分钟内各主机缓存更新，下一次拉起告警发往新地址；`config plan` 能显示 `moox.toml` 与 Monitor 的差异；
用一张即将过期的测试证书触发巡检，证书到期告警实际送达。

### 阶段 6：control 交叉检查

- 非 control 主机的 `watch` 增加对 control 网关的 TLS 握手检查、3 分钟判定、恢复通知与状态持久化。
- 测试：用本地 TLS 服务模拟可达、证书不符、不可达三种情况。

验收：测试环境中阻断到 control 网关的连接 3 分钟，收到“control 失联”；恢复后收到“已恢复”。

### 阶段 7：192 登记与失联原因区分

- 192 按阶段 0 的结论部署（完整 host 单元，或“出站专用主机”形态的单独设计与实现）并登记；Monitor 失联告警附带网关心跳状态并区分两种标题（4.7）。
- 对齐资源告警（G9）：HostAgent 采样改为每 15 秒一次（与阈值设计一致），或保持每分钟采样并把 CPU、内存的连续次数改为 3、5；
  选哪一种看采样量对 EventBus 与 `mooxsys` 存储的压力，阶段 0 顺带评估。
- 测试：Monitor 失联判定的单元测试覆盖两种组合。

验收：192 出现在 Monitor 主机列表；停止某台主机的 host-agent 收到“host-agent 停止上报”而不是“主机失联”。

### 阶段 9：发布与演练

**发布顺序**：

1. 阶段 5 涉及服务目录变更：Admin、全部主机网关、Monitor 同批发布（与既有规则相同），随后发布 host-agent。
2. 各主机的 host 单元（含新的 `moox-runtime` 与 crontab），先 compute-1、再 storage、最后 control。
3. 192 按阶段 7 的方式部署 host 单元。

**演练**（会真实推送告警，逐项征得用户同意后执行）：

| 演练 | 期望 |
| --- | --- |
| compute-1 上 `kill` 一个组件 | 1 分钟内拉起，收到“自动拉起 · 已恢复” |
| 暂停一个组件后等待 3 分钟 | 不被拉起，不告警 |
| compute-1 整机重启 | 开机后数分钟内全部组件就绪，收到一条“主机重启，已拉起 N 个组件” |
| control 整机冷启动（在用户安排的窗口） | 按依赖顺序全部拉起；期间其他主机发出“control 失联”，恢复后发“已恢复” |
| 发布中途中断（测试机） | watch 推送“需要人工恢复”并附恢复命令，不擅自删除屏障 |
| 停止 compute-1 的 host-agent 4 分钟 | 守护在 1 分钟内拉起；若先停守护再停 host-agent，收到“host-agent 停止上报” |
| 在控制台把渠道改到测试群 | 5 分钟内各主机缓存更新，下一次演练告警发到测试群；演练后改回 |
| 阻断 storage、compute-1 到 control 网关 3 分钟（防火墙规则） | 收到两条“control 失联”及恢复通知 |

## 6. 风险与回退

| 风险 | 应对 |
| --- | --- |
| 守护在发布过程中误拉进程 | 复用维护锁与暂停、停止中标记；发布流程本就持锁 |
| 持续崩溃时守护反复拉起拖垮主机 | 退避（4.1 第 6 步）；持续崩溃升级告警由人处理 |
| 告警风暴 | 合并窗口、主机重启合并、按问题类型限频 |
| 缓存里的 webhook 泄露 | 文件 0600、只在部署用户可读目录；不写日志、不进命令行参数 |
| 守护本身出错导致大量误操作 | 先上线阶段 2 的只记录模式，在测试机与 compute-1 观察一段时间后再开启拉起 |
| cron 守护进程缺失 | 安装时检查并报错 |

**回退**：默认回退只删除各主机的 `# moox-watchdog` 条目来停用守护（组件进程不受影响），保留新版 `moox-runtime`。
因为不改 PID 记录结构（D12），必要时也可以按既有发布流程把 host 单元回滚到上一版本，旧版 runtime 仍能读取记录并启停组件；回滚前先停用守护。
阶段 5 回退时 Admin 恢复为不推送证书告警（即现状），`GetHostPolicy` 与缓存文件保留不影响其他功能。
