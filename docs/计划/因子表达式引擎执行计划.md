# 因子表达式引擎执行计划

> 状态：执行计划 v3（尚未编码；已随设计稿 v3 吸收三轮 Codex 审查，第三轮确认可以进入编码）。设计依据见[因子表达式引擎详细设计](因子表达式引擎详细设计.md)（下称“设计”）。
> 约束：Python 因子执行链路直接删除、不过渡；窗口不满严格输出 NaN；允许浮点末位误差；项目无需兼容历史。

## 1. 总体顺序

```text
阶段 1 表达式包：语法与编译 ─┐
阶段 2 表达式包：算子与执行 ─┴─► 阶段 3 一致性验收（在现有代码上与 Python 并排计算，线上只读）
                                   │  ← 闸门：不通过不进入阶段 4
                                   ▼
                     阶段 4 管理端与接口 ─┐
                     阶段 5 引擎接入 ─────┴─► 阶段 6 删除 Python ─► 阶段 8 文档 ─► 阶段 9 发布与切换
                                            阶段 7 控制台 ────────┘
```

- 阶段 1、2 只新增 `packages/factorexpr`，不影响现有代码，可以独立合入。
- **阶段 3 是闸门**：在现有代码（Python 计算路径还在）上新增 `compare`，让旧的 Python 计算与新引擎读同一份线上窗口、同时计算并对比（设计 12.2）。没有通过验收，不改动管理端与引擎，更不删除 Python。
- 阶段 4、5 改动因子模块，必须一起合入（领域模型和接口变了，mgr 与引擎要同时换）。阶段 5 删除旧的 Python 计算路径（`compare` 的 Python 基准模式随之删除），阶段 6 删除其余 Python 文件、部署与 CI。
- 阶段 7（控制台）可以与阶段 6 并行；阶段 9 需要阶段 4～8 全部完成。
- 每个阶段完成时：`go test` 通过、`git diff --check` 干净，按仓库规范带路径提交（共享工作目录，先看 `git diff --cached`）。

## 2. 阶段 1：表达式包——语法与编译

**新增** `packages/factorexpr`（独立 Go 模块，加入 `go.work`；依赖 `github.com/expr-lang/expr v1.17.8`、`gopkg.in/yaml.v3`）。

| 文件 | 内容 |
|---|---|
| `spec.go` | 用 `yaml.Node` 按顺序解析 `params` / `let` / `outputs`；拒绝未知键、重复键、多文档、锚点与别名；长度限制（设计 3.3） |
| `expand.go` | 列表参数的笛卡尔积展开；列名模板 `{param}` 校验（整数、每个列表参数都必须出现、展开后 ≤ 64 个输出且不重名） |
| `syntax.go` | `parser.ParseWithConfig` + `DisableAllBuiltins`；节点白名单（设计 4.1）；表达式长度与节点数限制；错误位置换算到“字段 + 行列” |
| `names.go` | 名称解析：`let` → `params` → 算子注册表 → 输入列；重名、保留列、函数名误用检查 |
| `types.go`、`check.go` | 四种类型（数值序列、布尔序列、数值常量、布尔常量）；常量折叠；算子签名与参数范围检查（窗口必须是 1～5000 的整数常量等） |
| `ir.go` | 规范表达式树：`let` 内联，节点规范键（用于 CSE 与哈希） |
| `lookback.go` | 回看推导（设计 6.2）；递归算子的 K 值计算；上限 5000 |
| `meta.go` | 派生 `input_columns`、`outputs`、`lookback_periods`、`factor_type`；规范程序文本；`ExprVersion` 常量（初始 `expr/1`） |
| `program.go` | 集合程序：多个因子合并成一个 DAG，按规范键去重；拓扑排序；每个节点的最后使用者（供缓冲区回收） |
| `need.go` | 需求区间的自顶向下传播（设计 6.4） |
| `registry.go` | 算子注册表的结构（名称、签名、参数范围、回看规则、内核与参考实现的接口、中文文档、示例）；本阶段先登记签名与回看规则，内核在阶段 2 补齐 |
| `errors.go` | 中文诊断：类型、字段路径、行列、原因 |

**测试**
- spec 解析：合法与非法文档各类用例（顺序、重复键、未知键、锚点、超长）。
- 展开：单参数、多参数笛卡尔积、模板缺参数、重名、超过 64 个。
- 语法白名单：每一种被拒绝的节点各一例，错误信息为中文并且带位置。
- 名称与类型：隐式转换、函数名当变量、`let` 前向引用、常量窗口检查、常量输出被拒绝。
- 回看：设计 6.2 表中 11 个因子的推导值逐一断言；`ema`、`sma` 的 K 值；嵌套 `delay`；超过 5000 被拒绝。
- 哈希：改注释、改格式、改 `let` 名，哈希不变；改窗口、改输出名、改 `allow_partial_universe`、改语义版本，哈希变化。
- CSE：两个因子共用 `ts_mean(close, 20)` 时，DAG 中只有一个节点。
- 需求区间：实时（只要最后一行）与补算（分块区间）下各节点的区间断言。

**验收**：`cd packages/factorexpr && go test ./... && GOWORK=off go test -race ./...` 通过；现有 11 个因子的 spec 全部能编译，派生元数据与生产库一致（回看、输入列、输出列）。

## 3. 阶段 2：表达式包——算子与执行

| 文件 | 内容 |
|---|---|
| `ops/elementwise.go` | 逐元素算子；±Inf 一律记为 NaN；三值逻辑（设计 4.4） |
| `ops/rolling.go` | `ts_sum/mean/var/std/zscore`、`ts_product`、`ts_count`：满足点纯性（设计 5.1），窗口 ≤ 256 时逐点按固定顺序直接计算，更大的窗口用按绝对周期序号对齐的 64 周期分块合并（Chan 公式）；常数窗口精确返回均值与 0 方差；`ts_min/max` 用单调队列 |
| `ops/rolling_order.go` | `ts_rank`、`ts_quantile/median`、`ts_argmax/argmin`：逐点扫描自己的窗口 |
| `ops/rolling_moment.go` | `ts_skew`、`ts_kurt`、`ts_corr`、`ts_cov`、`ts_slope/rsquare/resi`、`ts_decay_linear`：与 `rolling.go` 相同的点纯实现方式 |
| `ops/recursive.go` | `ema`、`sma`：截断到 K 根的固定加权和（设计第 5 节），权重向量编译期算好；不依赖需求区间起点 |
| `ops/shift.go` | `delay`、`delta`、`pct_change` |
| `ops/cross.go` | `cs_rank`、`cs_zscore`、`cs_demean`、`cs_scale`，按 `(时刻, series_tag)` 分组，排除 NaN |
| `ops/reference.go` | 每个算子的朴素参考实现（只用于测试） |
| `exec/panel.go` | 面板：时间网格、序列（按标的、标签排序）、序列优先的列存储；构建接口接收“时间网格 + 每条序列的行”，不依赖因子模块的类型 |
| `exec/buffers.go` | 缓冲池；每个节点的缓冲区按它自己的需求区间分配（设计 7.2），按最后使用者回收；计算阶段的峰值估算（面板 + 同时存活的缓冲区之和），供阶段 5 的完整生命周期估算使用 |
| `exec/run.go` | 按拓扑顺序执行；按序列 / 按时间点分块并行；每个节点开始前检查 `ctx`；集合级 `recover` |
| `exec/result.go` | 列式结果（设计 7.4）：每个输出列一个“序列 × 目标时刻”的 float64 数组，外加有源行的位置掩码 |
| `functions.go` | 导出注册表文档，供 `ListFactorFunctions` 使用 |
| `testdata/golden/` | pandas 锚点（JSON）、生成脚本与 README（写明 pandas 版本；CI 不运行脚本） |
| `bench_test.go` | 基准：11 个因子的实时一期、补算一个分块；合成的 300 个因子（参照 Alpha101 的结构生成）；300 个 `ts_mean(close, 1440) + i` 的实时一期（长窗口共享节点 + 大量不同输出） |

**测试**
- 每个算子：与参考实现的模糊对照（`go test -fuzz`，CI 跑固定的种子语料）；覆盖 NaN 分布、并列值、常数序列、极端量级、不同需求区间起点。
- pandas 锚点：每个算子逐一比对，相对误差 ≤ 1e−12（锚点数据量小，可以要求更严）。
- 严格窗口：窗口内有一个 NaN，输出为 NaN；NaN 离开窗口之后恢复正常。
- 网格空洞：在网格上挖掉一行，受影响的目标行为 NaN，不受影响的行与完整数据时逐位相同。
- 截面：分组按标签隔离；NaN 被排除；单样本时 `cs_rank` 为 1.0、`cs_zscore` 为 NaN。
- 确定性：同一输入在 1、2、8 个工作线程下逐位相同。
- 点纯性（设计 5.1、12.1）：同一个点在“单独计算 / 与其他因子共享节点”“不同需求区间起点”“不同分块边界”“只算最后一行 / 算整段”下逐位相同；必须包含 Codex 审查给出的反例：`x[0]=-1, x[1]=1, x[2..208]=0` 时，`where(ema(x,20) > 0, 1, 0)` 单独计算与和 `delay(ema(x,20), 1)` 一起计算的结果相同。
- 常数窗口：`ts_std` 精确为 0，`ts_zscore` 为 NaN，`close / ts_mean(close, n)` 精确为 1。
- 大窗口（> 256）的分块实现与参考实现对照，并验证分块边界随绝对周期序号对齐。
- 内存：计算阶段的峰值估算与实际缓冲区占用一致；300 个 `ts_mean(close, 1440) + i` 的实时一期，输出缓冲只占“序列数 × 1”。

**验收**：测试与 `-race` 通过；基准在 Mac 上达到设计 7.7 的目标（阶段 3 再在 192 上复测）。

## 4. 阶段 3：一致性验收（闸门）

### 4.1 在现有代码上实现 `compare`

此时管理端与引擎都还是现有代码，Python 计算路径完整可用。

| 文件 | 改动 |
|---|---|
| `modules/factor/factors/*.yaml` | 新增 YAML 因子库：现有 11 个因子按设计 6.2 的表达式改写，`factor_id` 与输出列名不变（旧的 `.py` 与 `catalog.json` 暂时保留，阶段 6 删除） |
| `modules/factor/go.mod` | 依赖 `packages/factorexpr` |
| `modules/factor/internal/engine/compare.go`（新增） | 设计 12.2 的 Python 基准模式：读取 `--set-file`（旧格式 `catalog.json`，用现有的目录快照解码）与 `--library`；旧源码落盘到 `--work-dir`（复用 `internal/artifacts`）；启动 `--python-workers` 个 Python 进程（复用 `pyexec`）；按补算的分块与读取节流构造计划，调用现有 `Runner.Load`（`GapSink` 置空）与 `Runner.Compute` 得到基准；同一份 `LoadResult` 构建面板交给 `factorexpr`；逐键比较并输出 JSON 摘要 |
| `modules/factor/cmd/engine/main.go` | 新增 `compare` 子命令（只读：不调用组装、写入、上报，不同步目录，不访问 mgr） |

**测试**
- 用内存中的假 Store 与小型 Python 因子，覆盖设计 12.2 的全部分类：两边一致、末位误差、离散跳变、窗口内有空洞、新上市头部、常数窗口、Python 侧失败。
- 确认 `compare` 不调用 Store 的任何写方法、不写引擎状态目录（假 Store 对写方法直接判失败）。

### 4.2 线上只读核对

在 192 上运行，不影响正在运行的旧引擎：

1. 交叉编译 Linux amd64 的引擎（CGO=0），连同 YAML 因子库拷贝到 192 的临时目录（例如 `~/tmp-factor-compare/`），不替换正在运行的二进制。
2. 输入：
   - `--config`：直接使用现有的 `~/moox/factor-engine/config/engine.yaml`（此时配置解析器仍是旧的，凭据、`python.bin`、`worker_path` 都有效）；
   - `--set-file`：复制 `data/engine/catalog.json`；
   - `--library`：YAML 因子库；`--work-dir`：临时目录；`--python-workers 4`。
   - 运行环境与 systemd 服务单元保持一致（`deploy/systemd/user/moox-factor-engine.service.tmpl`）：Python worker 继承当前 shell 的环境，要显式设置 `MOOX_PYTHON_RUNTIME_PATH=$HOME/moox/factor-engine/python-runtime`（否则 `worker.py` 会按源码仓库的目录结构找 `moox_pyruntime` 而导入失败），并清掉 `HTTP_PROXY`、`HTTPS_PROXY`、`http_proxy`、`https_proxy`（192 上开着代理软件，服务单元里同样清掉了）。例如：

     ```bash
     env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy \
       MOOX_PYTHON_RUNTIME_PATH="$HOME/moox/factor-engine/python-runtime" \
       ./moox-factor-engine compare --config "$HOME/moox/factor-engine/config/engine.yaml" \
         --set-file ./catalog.json --library ./factors --work-dir ./work --python-workers 4 \
         --set <set_id> --start <RFC3339> --end <RFC3339>
     ```
   - 正式核对前先对一个标的、一小段区间试跑，确认 Python worker 握手成功、两边都有结果。
3. 对 4 个因子集分别核对最近 3 天：1m 集合 `--start now-72h`，1h 集合同样取 72 期以上。读取走补算的节流参数，避开整点前后几分钟，分集合依次执行，减轻对 Storage 的压力。
4. 按设计 12.2 的五条标准判定；输出的 JSON 摘要存档到本文第 12 节。
5. 在 192 上复测 `packages/factorexpr` 的基准，确认设计 7.7 的性能指标。
6. 完成后删除临时目录。不通过时，回到阶段 2 修正内核或补充锚点，再次核对；**不进入阶段 4**。

## 10. 阶段 9：发布与切换

### 10.1 发布范围

同一提交构建：`moox-factor-mgr`、`moox-factor-mgr-cli`、`moox-factor-engine`、`moox-admin`、control 主机网关、`moox-monitor`（服务目录变化，三者必须一起换）、`web-host`（控制台）。本机 `moox-cli` 也要重建（内嵌服务目录）。

### 10.2 切换前检查

1. 192 上引擎的 `factor_gap_pending` 为 0；mgr 里没有 `running` 的补算任务。
2. 列出引用因子的策略实例（切换后要重新启用）。
3. 备份：192 上整个 `~/moox/factor-engine` 目录（含 `bin`、`venv`、`pyworker`、`config`、`data`）打包；control 主机上的 `factor.db`；各组件旧二进制按现有发布流程备份，**包括旧版 `moox-factor-mgr-cli`**（回滚后补算要用它）。

### 10.3 切换步骤（选在整点后 :02～:10 开始）

1. **停引擎**：192 上 `systemctl --user stop moox-factor-engine`。
2. **mgr 迁移**：停 `factor-mgr`；用新的 `moox-factor-mgr-cli migrate-expr --library <因子库目录>` 迁移 `factor.db`（命令会自动备份）。
3. **换服务目录相关组件**：按现有流程依次重启 Admin、control 网关、Monitor；在 Monitor 库的 `t_monitor_gateway_observations` 中确认 control 的 route_count 与 expected/applied hash 一致。
4. **换 mgr 与 mgr-cli**：替换二进制，删除 `config/app.yaml` 中的 `python:` 段，启动后用 `GetStatus` 确认正常。
5. **换引擎**：替换二进制；编辑 `config/engine.yaml`，删除 `python:` 段（必要时加 `compute:` 段）；删除 `data/engine/catalog.json` 与 `data/engine/factors/`；启动。
6. **换控制台**：`web-host`。
7. **验证**：
   - `/readyz` 正常；`ps` 下没有 Python 子进程；引擎线程数 ≤ 150；
   - 下一个 1m 周期起各集合完成，`factor_period_duration_seconds{stage="compute"}` 明显下降；
   - 下一个整点 1h 集合完成；Monitor 因子环节正常；
   - 抽查切换前后几期的因子值数量级连续；对切换后写入的几期运行 `compare --baseline stored`，除运行摘要中已标明失败、预热或空洞的键外，差异应为零；
   - `GetStatus` 中引擎与 mgr 的 `expr_version` 一致。
8. **重新启用策略实例**：逐个重新启用 10.2 列出的实例，确认下一期不再报 `skipped(factor_changed)`。
9. **清理**：观察 3 天无异常后，删除 192 上的旧 `venv`、`pyworker` 与备份包，以及 control 上的 `factor.db` 备份与旧版二进制。

### 10.4 回滚

回滚时区分**程序与配置**（可以整体还原）和**运行账本**（`data/gap`，不能还原，见设计 13.3）：

1. 停引擎与 mgr；
2. **导出新账本中的待恢复条目**：用 `jq`（或 DuckDB 的 `read_json_auto`）从 `data/gap/factor-gap-*.jsonl` 中找出有 `skip`、但没有 `repaired` / `cancelled` / `gave_up` 的条目，按（集合、因子、标的、周期区间）汇总，保存到回滚记录；
3. 还原 `factor.db` 备份；
4. 还原 mgr、**mgr-cli**、Admin、网关、Monitor、web-host 的旧二进制与旧配置；引擎从备份包中**只还原 `bin`、`venv`、`pyworker`、`config`**，`data/gap` 保留当前内容（审计记录完整；旧引擎回放时会把新哈希的条目记为 `cancelled`），删除 `data/engine/catalog.json` 让旧引擎重新同步；
5. 按 Admin → 网关 → Monitor → mgr → 引擎的顺序重启；
6. 对第 2 步导出的区间，用**旧版** `moox-factor-mgr-cli recalc`（配合旧配置与还原后的 `factor.db`）手工补算，并核对这些键已写入有效值；
7. 重新启用策略实例（哈希变回旧值，同样会触发 `factor_changed`）。

切换后到回滚前**已经写入**的因子结果，与旧实现只有末位差异，不需要重算；需要处理的只是第 2 步导出的待恢复区间。

## 11. 风险与应对

| 风险 | 应对 |
|---|---|
| 阶段 3 验收不通过 | 不改动管理端与引擎，不删除 Python；按分类统计定位到具体算子，修正内核或补充锚点后重新核对 |
| `compare` 的读取与 Python 计算给 Storage、192 带来压力 | 使用补算的读取节流参数；只启动 4 个 Python 进程；避开整点；分集合依次执行 |
| 服务目录变化导致网关、Monitor 告警 | 按 10.3 第 3 步的顺序发布并核对观测表 |
| 引擎配置的严格加载拒绝旧的 `python:` 段 | 10.3 第 5 步先改配置再启动；部署脚本同步更新 |
| 切换时还有待恢复的空洞 | 10.2 第 1 步检查；必要时切换后手工补算 |
| 回滚丢失切换后新增的待恢复条目 | 10.4 第 2 步先导出、第 4 步保留 `data/gap`、第 6 步用旧版 CLI 手工补算 |
| 递归算子、大窗口实现不满足点纯性 | 阶段 2 的点纯性测试（含 Codex 给出的 EMA 反例）与阶段 5 的三条路径一致性测试是合入前提 |
| 策略实例忘记重新启用 | 10.2 第 2 步先列清单，10.3 第 8 步逐个核对 |
| 与[Storage 读接口收敛](Storage读接口收敛与数据归档执行计划.md)同时改动 `storageio` 与 `pipeline/load.go` | 两者都尚未编码；谁先合入，另一方在开工前基于新代码重新核对读取路径。本计划的读取只经过现有 `Load` 接口，不新增 Storage 调用 |
