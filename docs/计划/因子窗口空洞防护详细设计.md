# 因子窗口空洞防护详细设计

> 状态：详细设计，尚未实现。上位文档：[因子窗口空洞防护执行计划](因子窗口空洞防护执行计划.md)（背景、取舍、评审记录）；本文只写「怎么改」。
> 范围：协议与转换、因子引擎（检测、缓存、组装、账本、恢复轮询）、策略引擎（持仓保持）、Trade（保持标记）。mgr 与 Collector 无改动。

## 0. 与执行计划的差异（读代码后的简化）

详细设计读完代码后，有几处比计划更简单，已按「个人项目、简洁可维护」取舍，需要你确认（标 ★ 的会改变计划里的口径）：

| # | 差异 | 原因 |
|---|---|---|
| ★1 | **Trade 不做预算缩放**，预算预留完全在策略侧完成 | 空洞的持续时间很短（见 2.3：缺口一补齐，下一期窗口就完整，保持随之结束），价格漂移很小；保持结束后的下一期策略按完整预算重新配权，偏差自然消除。现货账户里多出的那点敞口最坏表现是个别目标 `blocked`（余额不足），不会清仓。计划 3.7 里 Trade 的 `(B−A)/(B−R)` 缩放因此取消 |
| ★2 | **不预留名额，不持久化各规则的贡献权重**；预留取上期组合级目标权重（`State.Targets`，现成字段） | `RuleState` 不用改；rank 规则多出一个持仓名额，下一期自然回落 |
| ★3 | **不读「已存在的结果键」去失效派生 `series_tag`** | 实时周期首次计算没有旧结果；只有「手工补算且窗口有洞」才可能碰到旧的派生键错值，概率极低。保留为已知限制 |
| 4 | **「上一根缺失」的保护规则改为：已持有的标的，当期输入完整、只缺上一根（`bars[-1]`）时保持** | 不需要把上一期的 `gap_subjects` 传给策略；对已持有标的这种缺失本来就不该触发清仓 |
| 5 | 提交 ID 含内容摘要**已经满足**：`storageio.CommitID` 对整批行做规范化哈希 | 无需改动 |
| 6 | 缓存不再需要「代次」：把检查放进缓存的写入口 `store`，写入的窗口一定无洞；有洞的标的标记 `dirty`，下期在本期内整窗口读取，不进入后台预热 | 比计划 3.2 更简单，同时覆盖 `Load` 和 `warmup` 两个入口 |
| 7 | 恢复不单独做「复查缺失点位」，直接尝试填充：填充本身做窗口检查，仍有洞就什么都不写 | 少一次读取和一段代码 |

## 2. 因子引擎

### 2.1 总览

```
读窗口(Load) ──► 窗口检查(checkGaps) ──► 计算(Compute) ──► 组装(Assemble，按检查结果过滤) ──► 写入(Write)
                       │                                          │
                       └──► 账本 skip（先 fsync）                  └──► Outcome.Items（逐项结果）
实时周期结束写 marker（含 gap_subjects）
恢复轮询（每 5 分钟）：账本待恢复项 ──► 进程内 RunChunk(FillOnly) ──► 逐项写入确认 ──► 账本 repaired
```

新增代码集中在 `modules/factor/internal/pipeline/`（`gapcheck.go`）、`.../engine/`（`gapledger.go`、`gapfill.go`），其余是小改动。

### 2.2 窗口检查 `pipeline/gapcheck.go`

**输入**：`Plan`、`LoadResult.Frames`（每个标的一帧，含 `data_time`、`series_tag` 列）。
**输出**：`GapReport`，只记有洞的组合：

```go
// GapReport 记录有洞的 (因子, 标的, 目标周期)；没有洞的组合不出现。
type GapReport struct {
    entries map[gapKey][]time.Time // 缺失的时间点（已去掉头部新上市部分）
}
type gapKey struct {
    FactorID string
    Subject  string
    Period   time.Time // 目标周期 t（该周期的 data_time）
}
func (g GapReport) Invalid(factorID, subject string, period time.Time) bool
func (g GapReport) Subjects(factorID string, period time.Time) []string // 该因子该周期有洞的标的
```

**算法**（对每个有帧的标的）：

1. 把帧里的行按 `series_tag` 分组，得到每个序列已有时间点集合 `present[tag]`。窗口内没有任何行的标的没有序列：它本来就是上游缺失或预热，沿用现有路径，不在这里判定。
2. 目标周期列表 `targets`：实时只有一个（`planTarget`）；补算是 `periodRange(TargetStart, TargetEnd)`。
3. 对每个因子 `f`（回看 `L = f.LookbackPeriods`），目标周期 `t` 的应有时间点是 `clock.Window(t, freq, L)`。
4. 对每个序列，把所有目标周期的应有时间点并成一个网格 `[最早窗口起点, 最晚目标]`，求出缺失时间点的**有序列表** `missing`。补算时一个标的一个序列只扫一遍网格，每个 `(因子, 目标周期)` 用二分查找 `missing` 里是否有落在 `[t−(L−1)Δ, t]` 的点，避免补算块里 `O(因子 × 周期 × L)` 的重复比较。
5. **头部缺失**：`missing` 非空时，用 `firstBar(subject)`（见下）去掉早于首根 K 线的点；剩余仍非空才算有洞。
6. **目标周期本身缺失**：某序列在 `t` 缺失，同样算有洞（`t` 在应有时间点里）。上游已报失败的标的不进入 `Available`，不会走到这里。
7. 同一标的的各序列分别比较，任一序列有洞，该 `(因子, 标的, t)` 就记为有洞。

**`firstBar(subject)`**：新增 `storageio.Store.FirstBar(ctx, spaceID, datasetID, subject, freq) (time.Time, bool, error)`，用 `ReadTimeSeriesRows`、升序、取 1 行实现；`Runner` 内存缓存结果（首根 K 线不会变），**不缓存错误**。读取出错时按「不是新上市」处理（保守，当作空洞），下期重试，并记日志。只有 `missing` 非空且最早已有行晚于窗口起点时才会调用，新上市标的很少，开销可忽略。

**性能**：实时周期 500 标的 × 13 因子 × 一个目标，每个因子比较 `L` 个点，最坏约百万次整数比较，毫秒级。

### 2.3 缓存与预热 `pipeline/window_cache.go`

**不变量**：缓存里的窗口一定无洞。

- `liveWindowCache.store(plan, frames)` 对每个标的先用 2.2 的检查（用该集合最大回看 `maxLookback` 的窗口、目标取 `plan.PeriodTime`）：
  - 无洞：照旧合并进缓存；
  - 有洞：**不写入缓存**，并在 `set.dirty` 里标记该标的（缓存里已有的窗口保留不动，不会被使用，见下）。
- `plan()` 里，`dirty` 的标的**不走「覆盖」分支，也不进预热**，直接 `reads[subject] = subjectRead{start: plan.TargetStart}`：本期内整窗口读取，不用前缀。这样有洞的标的每期多读一次完整窗口，数量很少，可以接受。
- 整窗口读取后再经 `store` 检查：无洞则清除 `dirty` 并写缓存；有洞继续 `dirty`。
- 后台 `warmup` 同样调用 `store`，被拒绝写入的标的进入 `dirty`，退出预热队列（由实时周期整窗口读取接管）。
- 因为所有写缓存的入口都经过 `store`，在途的旧预热结果也只可能写入无洞窗口，不需要缓存代次。

**为什么保持标记不会退化成 `factor_failed`**：`dirty` 的标的不进预热，所以不会出现在 `WarmingSubjects` 里被当作普通失败；它每期都有帧，由检查决定是否 `gap`。

**持续时间**：空洞一旦补齐，下一期整窗口读取就是完整的，立即恢复正常，不必等回看窗口滑过空洞。所以保持（第 3 节）通常只持续「补采到位」所需的几分钟。

### 2.4 计算与组装

**`Plan` 新增**：`FillOnly bool`。`recalcexec.Selection` 新增同名字段，`recalcexec.plan()` 传入并在 `FillOnly` 时令 `WriteCarry=false`。

**Run 流程**（`pipeline/report.go` 的 `Run`）：

```
loaded := Load(plan)
gaps   := checkGaps(plan, loaded)            // 新增；FillOnly 与否都做
computation := Compute(plan, loaded, gaps)   // 签名加 gaps
rows, report := Assemble(plan, loaded, computation, gaps) // 返回值加逐项报告
recordGaps(plan, gaps)                       // 账本 skip，先 fsync；FillOnly 不记
Write(rows)
Report(...)                                  // 实时模式写 marker，里面带 gap_subjects
```

**Compute（`pipeline/compute.go`）**：

- 时间序列因子：Python 调用不变（一次一个标的、该标的所有时间序列因子），空洞过滤放到组装阶段。
- 截面因子（实时单目标 / 补算按目标周期逐个）：
  - `AllowPartialUniverse=false`：该周期只要有标的在该因子上有洞，该周期整因子 `skipped`（实时与现有的「缺失标的 > 0」口径一致，状态 `skipped`，不发任务）；补算则只跳过这些周期，其余周期照常。
  - `AllowPartialUniverse=true`：该周期的 panel 和 `available_subjects` 里**去掉有洞的标的**，用剩下的计算；有洞标的当期结果为 NULL。panel 过滤实现为 `panelIndex.slice`、`buildPanelFrame` 增加「排除标的」参数。
- `FactorState` 的 `FailedSubjects` 并入有洞标的，`GapSubjects` 记录它们；`Status` 沿用 `degraded`（严格截面为 `skipped`）。

**Assemble（`pipeline/assemble.go`）**：

- 应用因子值时（`applyFactorValues` 调用前）：`gaps.Invalid(factor, subject, at)` 为真则跳过，该因子字段保持 NULL（默认值）。**不要走现有的「标的级失败」`markFactorSubjectFailure`**，它会把整个补算块里该标的该因子的所有周期都清成 NULL；空洞是周期级的。
- `FillOnly`：初始 `fields` 不放因子列（而不是放 nil）；计算失败、无效值、有洞都**不写该因子列**；跳过「标的级失败清 NULL」那一段；字段全空的行不输出。这样填充只会写入由完整窗口算出的值。
- 新增 `AssembleReport`，逐 `(因子, 标的, 周期)` 记录 `written`（该键该因子列已取得有效值）、`gap`（有洞）、`failed`（计算错误、无效值、该周期没有源行）。

**Run 把 `AssembleReport` 与写入结果合并成 `Outcome.Items`**：写入成功后 `written` 才算确认；写入失败整块按 `failed`。

**目标键缺失**：目标源行不存在时没有结果键可写。这是 3.1 里提到的限制（见 0 的第 ★3 条），记日志和指标 `factor_gap_target_missing_total`，不处理。

### 2.5 账本 `engine/gapledger.go`

**文件**：`<ledger_dir>/factor-gap-YYYYMM.jsonl`，按 UTC 月份，永不自动删除。

**行格式**：

```json
{"event":"skip","at":"2026-10-14T06:05:07Z","set":"fset_x","subject":"BTC-USDT","period":"2026-10-14T06:04:00Z",
 "factors":[{"id":"bias_20","hash":"sha256:…"}],"missing":["2026-10-14T05:58:00Z"],"tags":[""],"trigger":"evt-…"}
{"event":"repaired","at":"…","set":"fset_x","subject":"BTC-USDT","period":"…","factors":[{"id":"bias_20","hash":"…"}]}
{"event":"cancelled","…","reason":"definition_changed"}
{"event":"gave_up","…","reason":"timeout|universe_unavailable"}
```

**待恢复键**：`(set, subject, period, factorID)`，值带定义哈希、首次发现时间、触发事件 ID、缺失点位。

**写入**：`Append(lines []line)` 在互斥锁下，一次 `Write` 一整批，再 `Sync()`。打开文件时若末尾不是 `\n` 先补一个换行（防崩溃留下的半行）。实时周期里，`recordGaps` 在 marker 写入之前调用，失败只记日志和指标并让健康检查降级，不影响周期。

**回放**：启动时读取全部账本文件（体量很小），按时间顺序应用事件：`skip` 加入（同键重复则合并，保留最早发现时间）；`repaired`/`cancelled`/`gave_up` 移除。忽略无法解析的行（含末尾半行），记计数。回放后对已超过 `give_up_after` 的待恢复项追加 `gave_up` 并告警，停机期间超期的也不会无声消失。

**对外**：`Pending() []entry`、`MarkRepaired`、`MarkCancelled`、`MarkGaveUp`，都内部追加并更新内存集合。

### 2.6 恢复轮询 `engine/gapfill.go`

```go
type gapFiller struct {
    ledger   *gapLedger
    sets     SetSource      // 按 set_id 取 domain.EngineSet（来自引擎 catalog）
    source   SourceDataset  // DatasetColumns
    exec     ChunkRunner    // recalcexec.Executor.RunChunk
    store    UniverseSource // 读 marker 的 UniverseSubjectIds（GetFactorPeriodComputed）
    interval, settle, giveUp time.Duration
}
```

每 `interval`（默认 5 分钟）一轮：

1. 取 `ledger.Pending()`，丢掉发现时间距今不足 `settle`（5 分钟）的；超过 `giveUp`（6 小时）的追加 `gave_up` 并 `WARN`，提示手工补采与手工补算。
2. 按 `(set, subject)` 分组，每轮最多处理 `max_groups`（默认 20）组，串行。
3. 取 `EngineSet`：集合已不存在或已停用 → `cancelled(set_gone)`。逐因子比较账本里的定义哈希与当前定义，不同 → `cancelled(definition_changed)`；因子已不在集合里 → `cancelled(factor_removed)`。
4. 时间序列因子：`Selection{Set, Factors: 该组涉及的因子, Subjects: [subject], Columns, FillOnly: true}`，`RunChunk(selection, minPeriod, maxPeriod+Δ)`。`RunChunk` 内部取集合锁（`setlock`，与实时周期、人工补算互斥），**锁取得后**才会读窗口和计算，所以定义校验在锁内的 `Run` 里再做一次（取得锁后重新取 `EngineSet`，哈希变了就放弃该组，下轮按 3 处理）。
5. 截面因子：用账本里的 `trigger`（`trigger_event_id`）读该周期 marker 的 `UniverseSubjectIds`，`Subjects` 取这份冻结全集，对该周期单独 `RunChunk`；marker 读不到 → `gave_up(universe_unavailable)`。`AllowPartialUniverse=false` 的因子，全集中仍有洞则该周期 `gap`，保持待恢复。
6. 按 `Outcome.Items`：该组涉及的 `(因子, 标的, 周期)` 里状态为 `written` 的，追加 `repaired`；`gap`、`failed` 保持待恢复，下轮再试。

**重启安全**：写入后、追加 `repaired` 前崩溃，重启回放得到同样的待恢复项，重做一次：结果相同则 Storage 的提交回执去重（`CommitID` 含内容），不同（源数据被更正）则按新内容写入，都无害。

### 2.7 配置与指标

`modules/factor` 引擎配置新增：

```yaml
gap:
  enabled: false            # 默认关；下游（Storage、策略、Trade）全部就绪后才打开
  ledger_dir: ./data/gap    # 账本目录，纳入备份
```

## 3. 策略引擎

### 3.1 输入侧

- `readiness.Check`：对 `degraded` 的因子，除了 `FailedByFactor[factorID]`，另取 `GapByFactor[factorID] = state.GetGapSubjects()`（去重排序），放入 `Result`。
- `input/frame.go` 的 `failedColumns`：遍历 `FailedByFactor` 时，若标的在 `GapByFactor[factorID]` 里，原因取新常量 `engine.FailedGap = "factor_gap"`，否则 `FailedFactor`。`View` 级的 `FailedSubjects`（`source_failed`）不变。

### 3.2 求值：冻结集合

在 `engine/evaluate.go` 的第一遍之前新增 `freeze.go`：

```go
// frozenSet 返回因空洞缺数、需要保持持仓的标的。
func frozenSet(program *dsl.Program, frame Frame, previous State) map[string]struct{}
```

**候选**：`previous.State.Targets` 里权重非零的标的（策略当前理论上持有的）。

**对每条规则、每个候选标的**（且标的在该规则的预期集合里、没被年龄剔除）：按 `partitionRule` 同样的口径取检查列（signal 规则的已持仓标的只看 exit 引用的列），收集**全部**缺失原因，分类：

| 缺失情形 | 分类 |
|---|---|
| 列在 `FailedColumns` 里且原因是 `factor_gap` | `gap` |
| 无行，但检查列上有 `factor_gap` 证据 | `gap`（先查失败证据，再判无行） |
| 当期列全部齐全，只缺上一根（`bars[-1]`）的列，且没有失败证据 | `prevonly` |
| 其他（`factor_failed`、`source_failed`、无行无证据、值缺失无证据） | `other` |

**标的被冻结，当且仅当**：所有规则里都没有 `other`，且至少有一条规则的分类是 `gap` 或 `prevonly`。有 `other` 就完全按现有逻辑处理（保持不扩展到 `source_failed`、`factor_failed`）。

### 3.3 集合划分与规则求值的改动

`ruleSets` 新增 `frozen map[string]string`（标的 → `gap_hold`）。

- **`partitionRule`**：冻结标的既不进 `available` 也不进 `missing`，记入 `frozen`；解释明细（`items`）新增阶段 `StageHeld = "held"`，原因 `gap_hold`。
- **守门**：`guard` 的缺数计数用 `len(missing) + len(frozen)`，保护中的标的仍计入 `too_many_missing`，不能伪装成可用。
- **signal**（`evaluateSignal`）：`previous.Held` 里的冻结标的**不判 exit、不参与平分**，但加入 `result.state.Held`，保证状态里仍记着它在持有。
- **rank（普通与 buffer）**：冻结标的不在 `ordered` 里，`selectWithBuffer` 会忽略（已核实）；`result.state.Held` 把上期持有的冻结标的补回去，保住下期的缓冲资格。
- **holding**：`evaluateHolding` 里延续批次的过滤用 `availableSet`，改成「可用 ∪ 冻结」，冻结标的的基准权重继续留在批次里；这样保持结束后它仍在批次里，不被误卖。
- **合成**：规则产出的 `contributions` 里**删除冻结标的**（它们由下面的保持目标代替）。

### 3.4 组合：预算预留与保持目标

`applyPortfolio` 新增参数 `frozen map[string]struct{}`，流程：

1. 照现在先量化非冻结标的（`quantizeTargets`）。
2. 预留 `R = Σ |previous.Targets[id]|`（冻结标的上期组合级目标权重，保留符号用于目标，预算用绝对值）。
3. 预算上限 `B = portfolio.Leverage`；现货取 `min(Leverage, 1)`。
4. 非冻结标的的总敞口 `G`。若 `G + R > B`：缩放系数 `f = max(0, (B − R) / G)`（`G = 0` 时不缩放），**只缩小**；每个非冻结目标乘以 `f` 后再向零截断，为零的剔除，重算 gross、net。`R ≥ B` 时非冻结全部为 0。
5. 追加保持目标：`Target{InstrumentID: id, Weight: previous.Targets[id], Hold: true}`，计入 gross、net（供现有的 leverage、现货净值检查）。
6. 现有检查（`gross > Leverage` 报错、现货 `net > 1` 报错）照常作用于「缩放后的非冻结 + 保持」。因为 `R` 已预留，只要上期合法，这里不会误触发。
7. `State.Targets` 写入时包含保持标的（保持它的预留权重，下一期仍可读到），`turnover` 因保持标的权重不变而不增加。

**`Target` 新增 `Hold bool`**。

### 3.5 结果与事件

- `trigger/convert.go`：`TargetJSON` 新增 `Hold bool \`json:"hold,omitempty"\``；`EncodeTargets` 带上；`MarshalTargetEvent` 把 `Hold` 写入 `InstrumentWeightTarget.Hold`（4.1）。
- `store` 里 `TargetsJSON` 是 JSON，无需改表。
- 结果页（`web/src/views/strategy`）：目标表对 `hold` 的行加「保持」标签；解释明细阶段 `held` 加中文名「保持（数据空洞）」。可延后，不影响交易。
- 摘要 `Summary.Notes` 追加一条「N 个标的因数据空洞保持持仓：…」，便于排查。

### 3.6 边界

- 候选只含上期组合级目标非零的标的：没持仓的标的不会因空洞被「保持」，只是缺数、不开新仓（现有行为）。
- 整期被守门跳过（`too_many_missing`、`universe_too_small`）或严格截面整因子 `skipped` 时，策略不发新目标，保持标记发不出去；Trade 按已有目标继续执行（现有行为），文档与测试按此口径。
- 退市、移出标签的标的不在预期集合里，不会被冻结，行为不变（`notExpected` 明细）。

## 4. Trade

### 4.1 协议

`packages/tradeeventpb`：`InstrumentWeightTarget` 新增 `bool hold = 3;`，重新生成。

### 4.2 解析 `application/target/weight_resolver.go`

- `canonicalWeights`：`orderedWeight` 加 `Hold bool`，**纳入请求哈希**（`payload.Targets`），否则同样权重但 hold 不同的请求会被当作同一个。
- `validateWeightRisk`：保持标的的权重照常计入单标的和总敞口检查（它是预留的真实敞口）。
- `Resolve` 循环：`Hold` 为真的标的**跳过报价与数量换算**，输出 `store.InstrumentTarget{InstrumentID, Hold: true}`（`Quantity` 为空）。全部为保持标的时不需要权益快照，但仍走原有的「非空目标」路径，不当作清仓。

### 4.3 存储 `infra/store/target.go`

`InstrumentTarget` 新增 `Hold bool \`json:"hold,omitempty"\``，`Quantity` 在 `Hold` 时可为空。目标记录是 JSON，无需改表。

### 4.4 执行 `application/target/executor.go`

- `desiredTarget` 新增 `Hold bool`；`desiredTargets` 对 `Hold` 的条目不解析 `Quantity`。
- `nextLaneAction` 开头：`if desired.Hold { return laneAction{}, true, "", nil }`，即该标的视为已完成，**既不加仓也不减仓**。`laneIDs` 里该标的照常存在（它有持仓），但不会产生动作。
- 旧目标遗留的未成交订单：现有逻辑在新目标到达时会撤销属于旧目标的订单（`current.OwnerID != target.TargetID → stopOrder`），保持标的没有新单，所以这些订单撤销后不会补发。撤单窗口内已成交的部分接受，「数量不动」的含义是「不因新决策改变」。
- `blockedExposures`、过期、暂停等其他流程不变。

### 4.5 查询与界面

目标记录的展示（`LogicalAccountTargetRecord.Targets`）对 `Hold` 的行显示「保持」；没有数量时不报错。

## 5. 测试清单

**因子引擎**
- 检查：中间缺一根、目标周期缺失、头部缺失（有 / 无首根 K 线依据、`FirstBar` 出错保守判空洞）、多 `series_tag` 一序列有洞、不同回看长度（短回看不受影响）、补算块内一个洞只影响其后 `L` 个周期、二分查找边界。
- 缓存：有洞不写缓存且标记 `dirty`；`dirty` 标的下期整窗口读取、不进预热；补齐后清除；`Load` 与 `warmup` 两个入口；`min_periods=1` 的因子在有洞时不输出数值。
- 组装：有洞周期因子列为 NULL、其余周期不受影响；`FillOnly` 不写 NULL、不写 carry 列、字段全空的行不输出；`AssembleReport` 三种状态。
- 截面：严格模式有洞整周期 `skipped`；部分模式 panel 排除有洞标的；补算按周期。
- 账本：写入顺序（先 `skip` 后 marker）、半行忽略、回放重建、超期追加 `gave_up`、重复 `skip` 合并、磁盘写失败降级。
- 恢复：成功填充追加 `repaired`；仍有洞保持待恢复；定义变更 `cancelled`；写入后崩溃重做幂等；与实时周期、人工补算共用集合锁；截面 marker 读不到 `gave_up`。

**协议**：端到端 `gap_subjects` 从引擎一路到策略（1.2 的测试）。

**策略**
- 冻结判定：只缺 `gap` / 只缺上一根 / 混有 `other` / 无行但有 gap 证据 / 多规则一条有 `other`。
- signal：冻结标的不判 exit、留在 `Held`；其余平分；预留缩放后总敞口不超预算。
- rank：普通、buffer（冻结标的不抢缓冲）、holding（批次保留冻结标的权重）。
- 组合：`R ≥ B`、`G + R ≤ B` 不缩放、缩放后截断为零、现货 `net` 检查、`State.Targets` 保留保持标的、`turnover`。
- 守门：冻结计入缺数比例；整期跳过时没有保持目标。
- 明细：`held / gap_hold` 一条记录，不重复。

**Trade**：`hold` 纳入请求哈希；`Resolve` 跳过换算；`Converge` 对保持标的不下单；新目标撤销旧订单后保持标的无新单；全部保持不被当作清仓。

**回放验证**：用策略回放（`docs/模块/策略.md` 第 10 节）对一段含人为空洞的历史数据，对比「有 / 无保护」的权重与成交差异。

## 6. 实施与上线步骤

1. **协议与转换**（1 节）：Storage、策略、因子引擎都要升级，生成代码、转换、端到端测试。
2. **Trade**（4 节）：先上线。旧策略不发 `hold`，行为不变。
3. **策略**（3 节）：上线后，没有 `gap_subjects` 时 `GapByFactor` 为空，行为不变。
4. **因子引擎**（2 节）：部署二进制，`gap.enabled=false`；在隔离环境把 `enabled` 打开，注入缺口走完「跳过 → 补采 → 恢复 → 补齐」；确认永续接口的零成交行为；然后生产打开。
5. 部署顺序遵循「消费者先于发布者」：Storage → Trade → 策略 → 因子引擎。引擎开关最后打开。

**生产演练**：目前没有删除单标的单根 K 线的接口（`PrimaryDeleteDatasetRowsReq` 只有数据集粒度）。演练方法在隔离环境里用测试数据集注入；生产只用「停掉某个标的一个周期的采集」这类自然缺口观察，不做人为删除。
