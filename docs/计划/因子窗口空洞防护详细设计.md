# 因子窗口空洞防护详细设计

> 状态：详细设计，尚未实现。上位文档：[因子窗口空洞防护执行计划](因子窗口空洞防护执行计划.md)（背景、取舍、评审记录）；本文只写「怎么改」。
> 范围：协议与转换、因子引擎（检测、缓存、组装、账本、恢复轮询）、策略引擎（持仓保持）、Trade（保持标记）。mgr 与 Collector 无改动。

## 0. 与执行计划的差异（读代码后的简化）

详细设计读完代码后，有几处比计划更简单，已按「个人项目、简洁可维护」取舍，需要你确认（标 ★ 的会改变计划里的口径）：

| # | 差异 | 原因 |
|---|---|---|
| ★1 | **Trade 不做预算缩放**，预算预留完全在策略侧完成 | 价格漂移带来的偏差有限：现货账户里多出的那点敞口最坏表现是个别目标 `blocked`（余额不足），不会清仓；保持结束后的下一期按完整预算重新配权。**注意**：保持的持续时间并不保证只有几分钟（自动补采不保证补齐，`gave_up` 也不会解除实时保持，直到空洞滑出回看窗口或被人工处理），所以要加「保持时长」告警指标，并在验证里覆盖长时间保持与价格漂移（见 5） |
| ★2 | **不预留名额，不持久化各规则的贡献权重**；预留取上期组合级目标权重（`State.Targets`，现成字段） | `RuleState` 不用改；rank 规则多出一个持仓名额，下一期自然回落 |
| ★3 | **不读「已存在的结果键」去失效派生 `series_tag`**；但**目标源行缺失**的情形要处理：非 `FillOnly` 模式按「已知源 `series_tag` × 目标周期」生成失效 NULL 行（`WriteFactorRows` 接收显式 RowKey，允许只写因子字段） | 派生键只在「手工补算且窗口有洞」时才可能有旧错值，概率极低，保留为已知限制；源序列的目标键缺失不能漏 |
| 4 | **「上一根缺失」的保护规则改为：已持有的标的，当期输入完整、只缺上一根（`bars[-1]`）时保持** | 不需要把上一期的 `gap_subjects` 传给策略；对已持有标的这种缺失本来就不该触发清仓 |
| 5 | 提交 ID 已含内容摘要（`storageio.CommitID`）；**但相同内容的提交回执已存在时 Storage 直接返回成功、不再写字段**，所以**补算的所有写入、以及含失效 NULL 的实时批次，一律使用每次执行唯一的提交 ID**（2.6），否则「修复 → 被人工补算再次写 NULL → 恢复算出同样的值」等路径会被回执吞掉 | 评审发现 |
| 6 | 缓存不再需要「代次」：把检查放进缓存的写入口 `store`，写入的窗口一定无洞；有洞的标的标记 `dirty`，下期在本期内整窗口读取，不进入后台预热 | 比计划 3.2 更简单，同时覆盖 `Load` 和 `warmup` 两个入口 |
| 7 | 恢复不单独做「复查缺失点位」，直接尝试填充：填充本身做窗口检查，仍有洞就什么都不写 | 少一次读取和一段代码 |
| 8 | `firstBar` 直接复用 `storageio.Client.EarliestPeriod`（已有，按批取升序最早一行，带列和有界时间范围） | 不新增存储读取接口 |
| 9 | holding 规则：含冻结成员的批次**延后重建**（见 3.3） | 比「在新批次里保留冻结份额」简单，且保持 `BaseWeights` 总和合法 |
| 10 | 截面因子的账本待办只在实时周期记录；手工补算的截面空洞只记日志 | 手工补算的 `Plan` 没有触发事件 ID，取不到冻结全集 |
| 11 | `prevonly`（已持有标的当期完整、只缺上一根）的保护**不依赖 `gap_subjects`**，策略升级后立即生效，是独立的行为变化 | 对已持有标的这种缺失本来就不该清仓；需要单独验收（见 5、6） |

## 2. 因子引擎

### 2.1 总览

```
读窗口(Load) ──► 窗口检查(checkGaps) ──► 计算(Compute) ──► 组装(Assemble，按检查结果过滤) ──► 写入(Write)
                       │                                          │
                       └──► 账本 skip（先 fsync）                  └──► Outcome.Items（逐项结果）
实时周期结束写 marker（含 gap_subjects）
恢复轮询（每 5 分钟）：账本待恢复项 ──► 进程内 RunChunk(FillOnly) ──► 逐项写入确认 ──► 账本 repaired
```

新增代码集中在 `modules/factor/internal/pipeline/`（`gapcheck.go`）、`.../engine/`（`gapledger.go`、`gapfill.go`），其余是小改动。

### 2.2 窗口检查 `pipeline/gapcheck.go`

**输入**：`Plan`、`LoadResult.Frames`（每个标的一帧，含 `data_time`、`series_tag` 列）。
**输出**：`GapReport`，只记有洞的组合：

```go
// GapReport 记录有洞的 (因子, 标的, 目标周期)；没有洞的组合不出现。
type GapReport struct {
    entries map[gapKey][]time.Time // 缺失的时间点（已去掉头部新上市部分）
}
type gapKey struct {
    FactorID string
    Subject  string
    Period   time.Time // 目标周期 t（该周期的 data_time）
}
func (g GapReport) Invalid(factorID, subject string, period time.Time) bool
func (g GapReport) Subjects(factorID string, period time.Time) []string // 该因子该周期有洞的标的
```

**算法**（对每个有帧的标的）：

1. 把帧里的行按 `series_tag` 分组，得到每个序列已有时间点集合 `present[tag]`。
   - **空帧**（读取成功但窗口内没有任何行，`Load` 会创建这样的空帧并仍把标的放进 `Available`）：调用 `firstBar(subject)`；有记录且早于窗口结束，说明它存在过、窗口内全缺，按**整个窗口缺失**处理（序列 `tag=""`），对所有因子记为有洞；没有任何记录（从未有过数据）沿用现有路径，不在这里判定。这样严格截面不会把窗口内全缺的标的当作完整全集的一员。
2. 目标周期列表 `targets`：实时只有一个（`planTarget`）；补算是 `periodRange(TargetStart, TargetEnd)`。
3. 对每个因子 `f`（回看 `L = f.LookbackPeriods`），目标周期 `t` 的应有时间点是 `clock.Window(t, freq, L)`。
4. 对每个序列，把所有目标周期的应有时间点并成一个网格 `[最早窗口起点, 最晚目标]`，求出缺失时间点的**有序列表** `missing`。补算时一个标的一个序列只扫一遍网格，每个 `(因子, 目标周期)` 用二分查找 `missing` 里是否有落在 `[t−(L−1)Δ, t]` 的点，避免补算块里 `O(因子 × 周期 × L)` 的重复比较。
5. **头部缺失**：`missing` 非空时，用 `firstBar(subject)`（见下）去掉早于首根 K 线的点；剩余仍非空才算有洞。
6. **目标周期本身缺失**：某序列在 `t` 缺失，同样算有洞（`t` 在应有时间点里）。上游已报失败的标的不进入 `Available`，不会走到这里。
7. 同一标的的各序列分别比较，任一序列有洞，该 `(因子, 标的, t)` 就记为有洞。

**`firstBar(subject)`**：直接复用 `storageio.Client.EarliestPeriod(ctx, spaceID, datasetID, freq, []string{subject}, []string{"close"})`（升序、带列和有界时间范围，是 `validateFactorHistoryRead` 要求的查询形式）；`Runner` 内存缓存结果（首根 K 线不会变），**不缓存错误**。读取出错时按「不是新上市」处理（保守，当作空洞），下期重试，并记日志。只有 `missing` 非空且最早已有行晚于窗口起点、或空帧时才会调用，新上市标的很少，开销可忽略。**调用必须在缓存互斥锁之外。**

**性能**：实时周期 500 标的 × 13 因子 × 一个目标，每个因子比较 `L` 个点，最坏约百万次整数比较，毫秒级。

### 2.3 缓存与预热 `pipeline/window_cache.go`

**不变量**：缓存里的窗口一定无洞。

- `liveWindowCache.store(plan, frames)` 对每个标的先用 2.2 的检查（用该集合最大回看 `maxLookback` 的窗口、目标取 `plan.PeriodTime`）：
  - 无洞：照旧合并进缓存；
  - 有洞：**不写入缓存**，并在 `set.dirty` 里标记该标的（缓存里已有的窗口保留不动，不会被使用，见下）。
- `plan()` 里，`dirty` 的标的**不走「覆盖」分支，也不进预热**，直接 `reads[subject] = subjectRead{start: plan.TargetStart}`：本期内整窗口读取，不用前缀。这样有洞的标的每期多读一次完整窗口，数量很少，可以接受。
- 整窗口读取后再经 `store` 检查：无洞则清除 `dirty` 并写缓存；有洞继续 `dirty`。
- 后台 `warmup` 同样调用 `store`，被拒绝写入的标的进入 `dirty`，退出预热队列（由实时周期整窗口读取接管）。
- 因为所有写缓存的入口都经过 `store`，在途的旧预热结果也只可能写入无洞窗口，不需要缓存代次。
- **并发细节**：标记 `dirty` 时同时清掉该标的的 `pending`（`nextWarmup/finishWarmup` 不再处理它）；较旧的预热结果（窗口结束时间早于已记录的 `dirty` 时刻）不得凭旧窗口解除较新的 `dirty`；检查里的 `firstBar` 在缓存互斥锁外调用。

**为什么保持标记不会退化成 `factor_failed`**：`dirty` 的标的不进预热，所以不会出现在 `WarmingSubjects` 里被当作普通失败；它每期都有帧，由检查决定是否 `gap`。

**持续时间**：空洞一旦补齐，下一期整窗口读取就是完整的，立即恢复正常，不必等回看窗口滑过空洞。所以保持（第 3 节）通常只持续「补采到位」所需的几分钟。

### 2.4 计算与组装

**`Plan` 新增**：`FillOnly bool`。`recalcexec.Selection` 新增同名字段，`recalcexec.plan()` 传入并在 `FillOnly` 时令 `WriteCarry=false`。

**Run 流程**（`pipeline/report.go` 的 `Run`）：

```
loaded := Load(plan)
gaps   := checkGaps(plan, loaded)            // 新增；FillOnly 与否都做
computation := Compute(plan, loaded, gaps)   // 签名加 gaps
rows, report := Assemble(plan, loaded, computation, gaps) // 返回值加逐项报告
recordGaps(plan, gaps)                       // 账本 skip，先 fsync；FillOnly 不记
Write(rows)
Report(...)                                  // 实时模式写 marker，里面带 gap_subjects
```

**Compute（`pipeline/compute.go`）**：

- 时间序列因子：Python 调用不变（一次一个标的、该标的所有时间序列因子），空洞过滤放到组装阶段。
- 截面因子（实时单目标 / 补算按目标周期逐个）：
  - `AllowPartialUniverse=false`：该周期只要有标的在该因子上有洞，该周期整因子 `skipped`（实时与现有的「缺失标的 > 0」口径一致，状态 `skipped`，不发任务）；补算则只跳过这些周期，其余周期照常。
  - `AllowPartialUniverse=true`：该周期的 panel 和 `available_subjects` 里**去掉有洞的标的**，用剩下的计算；有洞标的当期结果为 NULL。panel 过滤实现为 `panelIndex.slice`、`buildPanelFrame` 增加「排除标的」参数。
- `FactorState` 的 `FailedSubjects` 并入有洞标的，`GapSubjects` 记录它们；`Status` 沿用 `degraded`（严格截面为 `skipped`）。

**Compute 保留逐周期失败证据**：截面因子的结果现在统一聚合在 `Results[factorID][""]`，补算时截面调用失败还会把 `item.Err` 清掉、失败名单是整块的标的集合，无法推出各周期的结果。新增 `Computation.CrossPeriods map[factorID]map[periodUnix]periodOutcome`（`skipped`/`gap`/`failed`/`ok`），每个 `(截面因子, 目标周期)` 任务写一条；时间序列因子沿用按标的的结果，逐周期状态由 `AssembleReport` 从输出行得到。验证同一块里「有洞、执行失败、成功」三个周期互不清空。

**Assemble（`pipeline/assemble.go`）**：

- 应用因子值时（`applyFactorValues` 调用前）：`gaps.Invalid(factor, subject, at)` 为真则跳过，该因子字段保持 NULL（默认值）。**不要走现有的「标的级失败」`markFactorSubjectFailure`**，它会把整个补算块里该标的该因子的所有周期都清成 NULL；空洞是周期级的。
- **目标源行缺失**（非 `FillOnly`）：对每个已知源序列 × 目标周期，**已知源序列**取本窗口帧里出现过的 `series_tag`；**空帧**（2.2 判为有洞、但帧里没有任何行）取窗口缓存里该标的最近一次见过的 `series_tag` 集合，缓存里也没有就用空串 `""`（K 线数据集的默认序列）。若没有源行且该因子在这个周期无效（有洞或目标缺失），生成一行只含因子列、值为 NULL 的失效行，清掉可能存在的旧值。
- **`FillOnly` 要覆盖 `applyFactorValues` 本身**：新建结果行（派生 `series_tag`）时不再预置因子列为 nil；无效数值分支不写 nil；源行的初始 `fields` 不放因子列；跳过「标的级失败清 NULL」；字段全空的行不输出。语义区分：
  - **合法 NULL**（Python 返回 `None`，或 `NaN`/`Inf` 经 `normalizeNumeric` 转成 NULL，这与实时路径在窗口完整时的行为一致）：写入并确认；
  - **执行错误、非数值类型、结果列不合法、该周期没有源行**：不写，记 `failed`；
  - **有洞**：不写，记 `gap`。
- 新增 `AssembleReport`，逐 `(因子, 标的, 周期)` 记录 `written` / `gap` / `failed`。

**Run 把 `AssembleReport` 与写入结果合并成 `Outcome.Items`**：写入成功后 `written` 才算确认；写入失败整块按 `failed`。

**已知限制**：因子输出的派生 `series_tag`（只出现在截面因子的结果里）在窗口有洞时不会被失效；只在「手工补算且窗口有洞」时可能留下旧错值，记日志和指标 `factor_gap_derived_key_total`。

### 2.5 账本 `engine/gapledger.go`

**文件**：`<ledger_dir>/factor-gap-YYYYMM.jsonl`，按 UTC 月份，永不自动删除。

**行格式**：

```json
{"event":"skip","at":"2026-10-14T06:05:07Z","set":"fset_x","subject":"BTC-USDT","period":"2026-10-14T06:04:00Z",
 "factors":[{"id":"bias_20","hash":"sha256:…"}],"missing":["2026-10-14T05:58:00Z"],"tags":[""],"trigger":"evt-…"}
{"event":"repaired","at":"…","set":"fset_x","subject":"BTC-USDT","period":"…","factors":[{"id":"bias_20","hash":"…"}]}
{"event":"cancelled","…","reason":"definition_changed"}
{"event":"gave_up","…","reason":"timeout|universe_unavailable"}
```

**待恢复键**：`(set, subject, period, factorID, 定义哈希)`，值带 **`skipID`**、首次发现时间、触发事件 ID、缺失点位与序列。**每一条 `skip` 行都带一个新生成的随机 64 位十六进制 `skipID`**；回放时同键重复的 `skip` 取**最后一条的 `skipID`**、最早的发现时间。因此条目无论是已终结后再次失效，还是**尚未终结（例如写入成功但 `repaired` 还没落盘）时又被人工补算再次写 NULL**，只要再次产生 `skip`，`skipID` 就会变。`repaired`/`cancelled`/`gave_up` 都按这个完整键精确匹配，所以旧定义的待办被取消时不会误伤同键的新定义待办。`GapReport` 的条目因此要保留缺失序列（`tags`），账本才能如实填写。截面因子只在实时周期记待办（带 `trigger`）；手工补算的截面空洞只记日志。

**写入**：`Append(lines []line)` 在互斥锁下，一次 `Write` 一整批，再 `Sync()`。打开文件时若末尾不是 `\n` 先补一个换行（防崩溃留下的半行）。实时周期里，`recordGaps` 在 marker 写入之前调用，失败只记日志和指标并让健康检查降级，不影响周期。

**回放**：启动时读取全部账本文件（体量很小），按时间顺序应用事件：`skip` 加入（同键重复则合并：`skipID` 取最后一条，发现时间取最早）；`repaired`/`cancelled`/`gave_up` 移除。忽略无法解析的行（含末尾半行），记计数。回放后对已超过 `give_up_after` 的待恢复项追加 `gave_up` 并告警，停机期间超期的也不会无声消失。

**对外**：`Pending() []entry`、`MarkRepaired`、`MarkCancelled`、`MarkGaveUp`，都内部追加并更新内存集合。

### 2.6 恢复轮询 `engine/gapfill.go`

```go
type gapFiller struct {
    ledger   *gapLedger
    hub      SetHub          // Hub.Snapshot：只含启用的集合
    source   SourceDataset   // DatasetColumns
    exec     ChunkRunner     // 新增 RunChunkWith
    markers  UniverseSource  // 读 marker 的 UniverseSubjectIds（GetFactorPeriodComputed）
    interval, settle, giveUp time.Duration
    maxSpan  int             // 每个组一次最多处理的周期数
}
```

**`recalcexec` 的改动**：`RunChunk` 取得锁之后直接用固定的 `Selection`，没有锁内刷新机制，不能满足「锁取得后再校验定义」。新增：

```go
// RunChunkWith 先取集合锁，再调用 source 重新取得集合、因子、标的与源列，最后运行。
func (e *Executor) RunChunkWith(ctx context.Context, source SelectionSource, start, end time.Time) (pipeline.Outcome, error)
```

**待办在锁内重读**：`Pending()` 在锁外取的只是「这一组大概有哪些待办」的快照；`RunChunkWith` 的 `source` 回调在**取得集合锁之后**重新读取这一组当前的待办（剔除已终结的、用最新的 `skipID` 构造盐），之后才计算与写入。取快照之后、取得锁之前发生的再次失效（人工补算持锁追加了新的 `skip`）因此一定会被看到。`repaired` 按「完整键 + 本次使用的 `skipID`」精确匹配：期间 `skipID` 已变的条目不会被这次确认移除，留待下一轮。

`RunChunkWith` 另带一个 `after func(pipeline.Outcome)` 回调，**在集合锁内、`Run` 返回之后立即调用**，恢复在回调里追加 `repaired`：写入与 `repaired` 确认处于同一把集合锁内，锁释放后的新失效（实时周期或人工补算，二者的 `skip` 也是在各自持锁时追加）不会被旧的确认移除。`Selection` 新增 `FillOnly`、`CommitSalt string`，`plan()` 传入 Plan 并在 `FillOnly` 时令 `WriteCarry=false`。`Columns` 仍读取源数据集的列（计算输入需要），`WriteCarry=false` 只影响写入。恢复使用与实时同一个 `Runtime.locks`，并遵循引擎的 `active()`（租约丢失时不运行）。

每 `interval`（默认 5 分钟）一轮：

1. 取 `ledger.Pending()`，丢掉发现时间距今不足 `settle`（5 分钟）的；超过 `giveUp`（6 小时）的追加 `gave_up` 并 `WARN`，提示手工补采与手工补算。
2. 按 `(set, subject)` 分组，每轮最多处理 `max_groups`（默认 20）组，串行；每组一次最多 `maxSpan`（默认 60）个周期，更长的下轮继续，避免长时间占住集合锁。
3. `RunChunkWith` 的 `source` 回调在锁内：从 `Hub.Snapshot` 取集合。**集合不在快照里（目录尚未加载、结果表未就绪）：本轮跳过等待，不记 `cancelled`**；只有集合明确不再启用才 `cancelled(set_gone)`。逐因子比较账本里的定义哈希与当前定义：不同 → `cancelled(definition_changed)`；因子已不在集合里 → `cancelled(factor_removed)`；这两种该组不再运行。
4. 时间序列因子：`Selection{Set, Factors: 该组涉及的因子, Subjects: [subject], Columns, FillOnly: true, CommitSalt}`，运行 `[minPeriod, maxPeriod+Δ)`。
5. 截面因子：用账本里的 `trigger` 读该周期 marker 的 `UniverseSubjectIds`，`Subjects` 取这份冻结全集，对该周期单独运行；marker 读不到 → `gave_up(universe_unavailable)`。`AllowPartialUniverse=true` 时更新所有受影响标的；`false` 的因子全集中仍有洞则该周期 `gap`，保持待恢复。
6. 按 `Outcome.Items`：该组涉及的 `(因子, 标的, 周期)` 里状态为 `written` 的追加 `repaired`；`gap`、`failed` 保持待恢复，下轮再试。

**提交 ID 的盐（补算一律加每次执行唯一的盐）**：Storage 对「同提交 ID、同内容」直接返回成功而不再写字段，这会把「期望重写」的写入吞掉：修复后被写 NULL 再恢复、NULL 之后恢复写值再被写同样的失效 NULL、普通补算写 A → 有洞补算写 NULL → 补齐后普通补算重写相同的 A、账本落盘失败或崩溃后重启复用旧回执，都是同一类问题。与其逐条论证，不如规定：

- **补算模式（`ModeRecalc`）的所有写入——人工补算和 `FillOnly` 填充，无论有无空洞——`CommitSalt` 取该次执行生成的随机 64 位十六进制**，混入 `storageio.CommitID`；
- **实时周期**：保持现有的内容寻址去重；仅当该批次包含空洞失效 NULL 时同样加每次执行唯一的盐。实时周期在 marker 写入后即确认（`Handler` 看到 marker 就不再重做），不会在补算写入之后再被重投，所以普通实时批次不会撞上旧回执；
- 代价：补算因崩溃或重试被重做时会多写一次相同内容（字段级 upsert，值相同），无害；补算本来就是低频、小范围的；
- `skipID` 因此不再承担提交去重的职责，只用于 `repaired` 的精确匹配（见上）。
- **已接受的残余风险**：实时写入 A 成功、marker 落盘前崩溃，此时恰好有人工补算对同一周期因空洞写入 NULL，随后实时事件重投、算出相同的 A，被旧回执吞掉，字段停留在 NULL 而 marker 已确认。需要「实时周期未完成 + 崩溃 + 人工补算同一周期 + 补算时仍有空洞」同时发生，概率可忽略；运维约定：人工补算不要覆盖正在进行的最新周期；发现时用人工补算（加盐）重写即可。若以后要彻底消除，可让所有因子结果写入都加每次执行唯一的盐（放弃实时重投的写入去重，值相同的重写无害）。

**重启安全**：写入后、追加 `repaired` 前崩溃，重启回放得到同样的待恢复项，重做一次；提交 ID 每次执行唯一，所以一定会重写，相同内容的重写无害。

### 2.7 配置与指标

`modules/factor` 引擎配置新增：

```yaml
gap:
  enabled: false            # 默认关；下游（Storage、策略、Trade）全部就绪后才打开
  ledger_dir: ./data/gap    # 账本目录，纳入备份
  sweep_interval: 5m
  settle: 5m
  give_up_after: 6h
  max_groups_per_sweep: 20
```

`enabled=false` 时：不检查、不写账本、不恢复，行为与现状完全一致（二进制可以先部署）。

指标：`factor_gap_skipped_total{set}`、`factor_gap_pending`、`factor_gap_repaired_total`、`factor_gap_gave_up_total`、`factor_gap_ledger_errors_total`、`factor_gap_target_missing_total`。`gave_up` 增长或 `pending` 持续不降时告警。

### 2.8 整期大面积缺失：告警，由人工介入

某个周期里大比例标的同时缺失（采集故障、网关故障），不是「个别标的的空洞」，不应该靠自动跳过和恢复悄悄消化，要明确告警让人看到。分工：

- **不阻塞流水线**：因子引擎仍按正常流程完成周期、写 marker（状态 `degraded`），否则下游无法区分「没算」和「算了但大量缺失」；策略由已有的守门接管：缺数占比超过 `portfolio.max_missing`（默认 0.2）整期 `skipped(too_many_missing)`，不产生目标、不下单，Trade 沿用已有目标直到它过期。
- **引擎告警**：新增配置 `gap.mass_ratio`（默认 0.2，与策略默认值一致）。一个周期里「有洞的标的数 ÷ 预期标的数」≥ 该比例时，引擎输出 `ERROR factor_gap_mass set=… period=… ratio=… gap=… expected=…`，并增加指标 `factor_gap_mass_total{set}`，由监控告警规则（`docs/模块/监控.md`）接入通知。上游已报失败的标的（`UpstreamFailed`）也计入分子，因为「整期采集失败」往往表现为上游失败而不是窗口空洞。
- **策略告警**：已有的跳过指标按原因计数；新增规则：同一实例连续 3 期 `skipped(too_many_missing)` 或 `skipped(no_data)` 告警。
- **恢复**：大面积缺失时账本照常记录（每个标的一条），补采补齐后由恢复轮询逐个填充；人工介入的意义是尽快补采和确认数据源，而不是替代恢复。
- 阈值与连续期数都可配，默认值先按上面设，运行一段时间后按实际告警噪声调整。

## 3. 策略引擎

### 3.1 输入侧

- `readiness.Check`：对 `degraded` 的因子，除了 `FailedByFactor[factorID]`，另取 `GapByFactor[factorID] = state.GetGapSubjects()`（去重排序），放入 `Result`。
- `input/frame.go` 的 `failedColumns`：遍历 `FailedByFactor` 时，若标的在 `GapByFactor[factorID]` 里，原因取新常量 `engine.FailedGap = "factor_gap"`，否则 `FailedFactor`。`View` 级的 `FailedSubjects`（`source_failed`）不变。

### 3.2 求值：冻结集合

在 `engine/evaluate.go` 的第一遍之前新增 `freeze.go`：

```go
// frozenSet 返回因空洞缺数、需要保持持仓的标的。
func frozenSet(program *dsl.Program, frame Frame, previous State) map[string]struct{}
```

**候选**：`previous.State.Targets` 里权重非零的标的（策略当前理论上持有的）。

**对每条规则、每个候选标的**（且标的在该规则的预期集合里、没被年龄剔除），按与 `partitionRule` **同一个函数**收集缺失原因：把现有 `missingReason`（只返回首个原因）重构为 `missingReasons(...) []reason`，返回每一列的原因；`partitionRule` 取第一个，冻结判定取全部。检查列的口径（signal 已持仓只看 exit 引用的列、年龄豁免）也共用。

| 逐列的缺失情形 | 分类 |
|---|---|
| 该列在 `FailedColumns` 里且原因是 `factor_gap` | `gap` |
| 标的没有行：逐列看，该列有 `factor_gap` 证据则 `gap`，**没有证据的必需列记 `other`** | `gap` / `other` |
| 当期列全部齐全，只缺上一根（`bars[-1]`）的列，且没有失败证据 | `prevonly` |
| 其他（`factor_failed`、`source_failed`、值缺失且无证据） | `other` |

**标的被冻结，当且仅当**：所有规则里都没有 `other`，且至少有一条规则的分类是 `gap` 或 `prevonly`。有 `other` 就完全按现有逻辑处理（保持不扩展到 `source_failed`、`factor_failed`）。

### 3.3 集合划分与规则求值的改动

`ruleSets` 新增 `frozen map[string]string`（标的 → `gap_hold`）。

- **`partitionRule`**：冻结标的既不进 `available` 也不进 `missing`，记入 `frozen`；解释明细（`items`）新增阶段 `StageHeld = "held"`，原因 `gap_hold`。
- **守门**：`guard` 的缺数计数用 `len(missing) + len(frozen)`，保护中的标的仍计入 `too_many_missing`，不能伪装成可用。
- **signal**（`evaluateSignal`）：`previous.Held` 里的冻结标的**不判 exit、不参与平分**，但加入 `result.state.Held`，保证状态里仍记着它在持有。
- **rank（普通与 buffer）**：冻结标的不在 `ordered` 里，`selectWithBuffer` 会忽略（已核实）；`result.state.Held` 把上期持有的冻结标的补回去，保住下期的缓冲资格。
- **holding**：
  - `evaluateHolding` 里延续批次的过滤用 `availableSet`，改成「可用 ∪ 冻结」，冻结标的的基准权重继续留在批次里；保持结束后它仍在批次里，不被误卖。
  - **含冻结成员的批次延后重建**：`holdingRebuilds` 返回的待重建 offset 里，凡是旧批次包含冻结成员的，本期不重建（批次继续延续）。保持解除后，现有的「已满 bars 根却没能按时重建的批次在之后第一根 ok bar 补建」逻辑会把它补建，建仓序号仍按 offset 对齐。这样不会出现「到期重建丢弃旧批次、冻结成员身份消失、保持结束后被卖」，也不需要在新批次里保留冻结份额。延后期间**不得推进该批次的 `EstablishedBar`**（原值保留，补建条件 `barIndex − EstablishedBar ≥ bars` 才会持续成立）。冻结成员不进入配权、cap 再分配，也不再生成 `weighted` 明细。
- **合成**：规则产出的 `contributions` 里**删除冻结标的**（它们由下面的保持目标代替）。

### 3.4 组合：预算预留与保持目标

`applyPortfolio` 新增参数 `frozen map[string]struct{}`，流程：

1. 照现在先量化非冻结标的（`quantizeTargets`）。
2. 预留 `R = Σ |previous.Targets[id]|`（冻结标的上期组合级目标权重，保留符号用于目标，预算用绝对值）。
3. 预算上限 `B = portfolio.Leverage`；现货取 `min(Leverage, 1)`。
4. 非冻结标的的总敞口 `G`。若 `G + R > B`：缩放系数 `f = max(0, (B − R) / G)`（`G = 0` 时不缩放），**只缩小**；每个非冻结目标乘以 `f` 后再向零截断，为零的剔除，重算 gross、net。`R ≥ B` 时非冻结全部为 0。
5. 追加保持目标：`Target{InstrumentID: id, Weight: previous.Targets[id], Hold: true}`，计入 gross、net（供现有的 leverage、现货净值检查）。
6. 现有检查（`gross > Leverage` 报错、现货 `net > 1` 报错）照常作用于「缩放后的非冻结 + 保持」。因为 `R` 已预留，只要上期合法，这里不会误触发。
7. `State.Targets` 写入时包含保持标的（保持它的预留权重，下一期仍可读到），`turnover` 因保持标的权重不变而不增加。

**`Target` 新增 `Hold bool`**。

### 3.5 结果与事件

- `trigger/convert.go`：`TargetJSON` 新增 `Hold bool \`json:"hold,omitempty"\``；`EncodeTargets` 带上；`MarshalTargetEvent` 把 `Hold` 写入 `InstrumentWeightTarget.Hold`（4.1）。
- `store` 里 `TargetsJSON` 是 JSON，无需改表。
- 结果页（`web/src/views/strategy`）：目标表对 `hold` 的行加「保持」标签；解释明细阶段 `held` 加中文名「保持（数据空洞）」。可延后，不影响交易。
- 摘要 `Summary.Notes` 追加一条「N 个标的因数据空洞保持持仓：…」，便于排查。

### 3.6 边界

- 候选只含上期组合级目标非零的标的：没持仓的标的不会因空洞被「保持」，只是缺数、不开新仓（现有行为）。
- 整期被守门跳过（`too_many_missing`、`universe_too_small`）或严格截面整因子 `skipped` 时，策略不发新目标，保持标记发不出去；Trade 按已有目标继续执行（现有行为），文档与测试按此口径。
- 退市、移出标签的标的不在预期集合里，不会被冻结，行为不变（`notExpected` 明细）。
- **保持没有时长上限**：空洞补不上时，保持会持续到空洞滑出回看窗口或人工处理。新增指标 `strategy_gap_hold_periods{instance}` 和日志，保持超过 `N` 期（可配，默认 30）告警；价格漂移引起的敞口偏差靠告警兜底，不做自动退出。

### 4.4 执行 `application/target/executor.go`

- `desiredTarget` 新增 `Hold bool`；`desiredTargets` 对 `Hold` 的条目不解析 `Quantity`。
- `nextLaneAction` 开头：`if desired.Hold { return laneAction{}, true, "", nil }`，即该标的视为已完成，**既不加仓也不减仓**。`laneIDs` 里该标的照常存在（它有持仓），但不会产生动作。
- 旧目标遗留的未成交订单：现有逻辑在新目标到达时会撤销属于旧目标的订单（`current.OwnerID != target.TargetID → stopOrder`），保持标的没有新单，所以这些订单撤销后不会补发。撤单窗口内已成交的部分接受，「数量不动」的含义是「不因新决策改变」。
- `blockedExposures`、过期、暂停等其他流程不变。

**保持保证成立的条件**（写入文档，不作为缺陷）：
- 目标未过期。`Converge` 在过期检查之后才撤旧单，`stopOrder` 也检查有效期；过期清理只处理本目标的 `PENDING` 单。过期的目标不会下单，也不会撤销旧单，所以过期时「不动」仍成立，但旧目标的在途订单可能继续成交。
- 账户内没有「无法映射的持仓」（`loadMembers`/`blockedExposures`）：这类持仓会让整个账户 `blocked`，与是否保持无关，沿用现有行为。
- 逻辑账户处于 `ACTIVE` 且归属本实例会话；否则 `Converge` 本来就暂停。

- 截面：严格模式有洞整周期 `skipped`；部分模式 panel 排除有洞标的；补算按周期。
- 缓存：旧预热迟到不解除较新的 `dirty`、读取失败仍保留 `dirty`、`dirty` 恢复后再次覆盖读取；账本：写入顺序（先 `skip` 后 marker）、半行忽略、回放重建、超期追加 `gave_up`、重复 `skip` 合并、磁盘写失败降级。
- 恢复：「修复成功 → 人工补算再次写 NULL → 恢复算出相同值」仍能写入（提交 ID 盐）；另覆盖「写入成功但 `repaired` 未落盘即崩溃或追加失败 → 人工补算再次写 NULL → 重启恢复」仍会重写（每次执行的提交 ID 唯一）；「NULL 写入 → 恢复写值 → 再次写同样的失效 NULL」不被旧回执吞掉；账本追加或 `Sync` 失败时进程内 `skipID` 仍更新；「取待办快照后、取得锁前再次失效」的交错路径（锁内重读、`repaired` 不移除已变更 `skipID` 的条目）；`repaired` 在集合锁内追加；冻结全集与部分截面更新全部受影响标的；Primary 与 View 可读且**不产生新的 `ViewDataReady`**；成功填充追加 `repaired`；仍有洞保持待恢复；定义变更 `cancelled`；写入后崩溃重做幂等；与实时周期、人工补算共用集合锁；截面 marker 读不到 `gave_up`。

**协议**：端到端 `gap_subjects` 从引擎一路到策略（1.2 的测试）。

**策略**
- 冻结判定：只缺 `gap` / 只缺上一根（`prevonly`，含「不依赖 `gap_subjects` 即生效」的独立验收）/ 混有 `other` / 无行时逐列证据（有证据的列归 `gap`，无证据的必需列归 `other`）/ 多规则一条有 `other`。
- signal：冻结标的不判 exit、留在 `Held`；其余平分；预留缩放后总敞口不超预算。
- rank：普通、buffer（冻结标的不抢缓冲）、holding（批次保留冻结标的权重；含冻结成员的批次延后重建，解除后补建；连续保持跨越多个重建点）。
- 组合：`R ≥ B`、`G + R ≤ B` 不缩放、缩放后截断为零、现货 `net` 检查、`State.Targets` 保留保持标的、`turnover`。
- 守门：冻结计入缺数比例；整期跳过时没有保持目标。
- 明细：`held / gap_hold` 一条记录，不重复。

**Trade**：`hold` 纳入请求哈希；`Resolve` 跳过换算；落库链路逐个位置（编码、解码、现货受理、回执、查询协议）都能读写 hold 并重启读回；混合目标、重复消费；`Converge` 对保持标的不下单；新目标撤销旧订单后保持标的无新单；全部保持不被当作清仓；目标过期时的行为。

**回放与场景测试**：现有回放（`strategy/internal/replay/runner.go`）把目标转成权重 map、丢掉 `Hold`，`Ledger.Step` 对有价格的持仓继续按权重买卖，且回放的 `Frame` 不带 `FailedColumns`，**不能直接验证数量保持**。因此：(a) 引擎层用合成 `Frame`（带 `FailedColumns` 的 `factor_gap`、`prevonly`、混合原因）做场景测试；(b) 回放扩展：`Runner` 保留 `Hold`，`Ledger.Step` 对保持标的只估值、不调数量，并允许注入 gap 证据；之后才能做「有 / 无保护」的成交对比。
**长时间保持**：覆盖连续多期保持、价格单边漂移 10% 时的敞口、保持跨越 holding 重建点（批次延后重建）、保持解除后正常延续。

## 6. 实施与上线步骤

1. **协议与转换**（1 节）：Storage、策略、因子引擎都要升级，生成代码、转换、端到端测试。
2. **Trade**（4 节）：先上线。旧策略不发 `hold`，行为不变。
3. **策略**（3 节）：上线后没有 `gap_subjects` 时 `GapByFactor` 为空，`factor_gap` 路径不触发；**但 `prevonly` 保护不依赖 `gap_subjects`，策略一升级就生效**：已持有标的当期完整、只缺上一根时保持持仓（以前会按缺数处理）。这是独立的行为变化，需要单独验收，并在升级说明里写明。
4. **因子引擎**（2 节）：部署二进制，`gap.enabled=false`；在隔离环境把 `enabled` 打开，注入缺口走完「跳过 → 补采 → 恢复 → 补齐」；确认永续接口的零成交行为；然后生产打开。
5. 部署顺序遵循「消费者先于发布者」：Storage → Trade → 策略 → 因子引擎。引擎开关最后打开。

**生产演练**：目前没有删除单标的单根 K 线的接口（`PrimaryDeleteDatasetRowsReq` 只有数据集粒度）。演练方法在隔离环境里用测试数据集注入；生产只用「停掉某个标的一个周期的采集」这类自然缺口观察，不做人为删除。
