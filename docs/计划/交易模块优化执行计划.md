## 1. 背景与目标

审查发现四类问题：

- 策略目标可能到不了执行环节：策略发 `BTC-USDT`，Trade 内部是 `BTC-USDT-SWAP`，两边没有转换；被拒绝的目标没有任何页面痕迹。
- 实盘适配没有经过真实响应验证：Binance 合约一有持仓就同步失败，拒单会每秒重试。
- 大标的池撑不住：每次完整同步按标的逐个请求，活动订单查询实际读取全部历史订单，账户同步全程持有全局锁。
- 前端看不到失败原因：业务错误不提示，状态文案和后端对不上，阻塞原因和拒单原因都不展示。

本计划完成后要达到：

1. 真实格式的策略目标能走通，Binance、OKX 测试网上带持仓的账户能保持就绪，并完成开仓、调仓、清仓全流程。
2. 单个账户、单个订单的异常不会卡住其他账户，也不会让组合账户永久无法恢复。
3. 拒单不再循环；目标能正确区分“已完成”和“真的执行不了”。
4. 所有失败原因在页面上能看到，并且是中文。
5. 实测 50 个标的换仓的耗时，目标是 2 分钟内完成；达不到时另立计划，不阻塞本计划发布。
6. 组合账户可以在页面上完整配置和查看，并能用模拟盘验证。
7. 以后接入 A 股、港美股下单时，只需新增适配器、加一处注册和一个 proto 枚举值，`application`、`runtime` 不用改。

## 2. 当前模型

### 2.1 账户关系

```text
策略定义 ──1:N── 策略实例 ──1:0或1── 组合账户 ──1:N── 执行账户
```

| 关系 | 规则 | 依据 |
| --- | --- | --- |
| 策略定义和实例 | 一个定义可建多个实例，分别绑定不同组合账户 | `t_strategy_instances` |
| 实例和组合账户 | 一个启用的实例最多绑定一个组合账户，也可以不绑定（仅计算） | `ux_logical_account_owner_instance` |
| 组合账户和实例 | 同时只归属一个实例的当前会话 | `ux_t_strategy_instances_account`、`auth_fence` |
| 组合账户和执行账户 | 可有多个成员，可跨交易所；成员的模拟/实盘模式、市场、结算资产、运行环境必须相同 | `PutLogicalAccountMember` |
| 执行账户和组合账户 | 最多属于一个启用的组合账户 | `ux_enabled_physical_account_membership` |

策略只输出“占组合账户总权益的比例”。Trade 把成员权益加总，算出每个标的的总目标数量。目标不按比例分到各账户：减仓优先选持仓最大的账户，加仓按成员优先级依次使用，资金不足时换下一个账户。

成员可以使用不同的密钥。每个执行账户绑定自己的 `credential_secret_id`，各自运行私有流和同步，所以下面这些都支持：

- 同一交易所的两个独立账户。
- 同一交易所的主账户和子账户，或多个子账户，各用自己的密钥。
- Binance 账户加 OKX 账户。

前提是每个成员对应不同的交易所账户。同一个交易所账户录入两次（同一把密钥，或同一账户的两把密钥）不支持：两个会话看到同一批订单，会互相当成外部订单而暂停。同一把密钥由 T30 拦截；两把不同密钥系统不做检测，靠页面和文档提示，发生时组合账户会被暂停，问题能直接暴露。

### 2.2 目标来源

Strategy 通过事件 `event.trade.target.weight_requested` 发送组合账户的完整目标权重。Trade 校验归属和有效期，用权益和报价换算成数量并写入回执，再由执行器逐笔下单收敛。没列出的标的目标为 0，空列表表示全部清仓。每个组合账户只保留最新目标。

交易对范围由上游决定：采集标签 → 数据集标的 → 因子任务 → 策略 `universe`、`pool` → 目标里的标的。Trade 不再单独配置一份列表。

上游的标的 ID 不带市场后缀（`BTC-USDT`），Trade 内部带后缀（`BTC-USDT-SPOT`、`BTC-USDT-SWAP`）。转换统一在 Trade 完成，见 T37。

### 2.3 目标过期

有效期为 2 根 bar。超时的结果已经会被丢弃，本计划不改这条规则：

| 环节 | 处理 |
| --- | --- |
| Strategy 求值或提交时已过期 | 不发目标，记 `skipped(expired)`，规则状态继续推进 |
| Strategy 待投递时已过期 | 取消投递 |
| Trade 收到时已过期 | 丢弃 |
| Trade 暂停期间到达 | 延迟重投，恢复后未过期就接收，过期就丢弃 |
| 执行到一半过期 | 目标置为 `EXPIRED`，不再下新单，未发出的子单释放资金 |

丢弃是安全的，因为下一期的完整目标会覆盖上一期没完成的部分。需要解决的是可见性：过期后持仓停在中间状态，如果策略之后没有新目标，这部分持仓会一直留着；规则状态继续推进时，理论状态也可能和实际持仓不一致。这两点由 T26、T28 处理。

### 2.4 组合账户支持情况

| 能力 | 后端 | 前端 | 处理 |
| --- | --- | --- | --- |
| 建组合账户、加减成员 | 支持，含一致性校验 | 支持 | T9 让失败可见 |
| 跨账户收敛、平仓、换成员 | 支持，有单元和 e2e 测试 | 不涉及 | T35 补故障场景和测试网验证 |
| 权益合并与资金曲线 | 支持 | 支持 | 无 |
| 逐账户清仓 | 支持 | 支持 | T23 修预算 |
| 修改成员优先级和启用状态 | 重新调用添加接口可覆盖 | 没有入口 | T32 |
| 成员详情（名称、交易所、状态、资金） | 执行账户接口已有 | 只显示账户编号 | T32 |
| 组合账户的持仓和订单 | 支持 | 只能按执行账户看 | T33 |
| 组合账户的成交 | `ListFills` 只能按执行账户查 | 无 | T33 |
| 模拟盘组合 | 成员不可变，无法组合 | 可以新建模拟组合账户，但加不了成员 | T31 |
| 策略绑定组合账户 | 绑定时校验归属，不校验市场 | 下拉框列出全部账户，含自主下单账户 | T37、T34 |
| 绑定后的运行状态 | 新账户默认暂停，绑定不会自动恢复 | 实例页没有提示 | T34 |
| 不同密钥的账户组合 | 支持 | 支持 | T35 补同交易所双账户测试 |
| 同一交易所账户录入两次 | 没有校验 | 无 | T30 拦截同一密钥，两把密钥靠提示 |
| 现货和合约混合 | 不支持，成员市场必须相同 | 不支持 | 本计划不做 |

结论：后端主流程支持多账户合并，前端和模拟盘还不完整。

### 2.5 场所抽象现状

采集模块已经有成熟的抽象：`marketdata` 按市场、产品、提供方注册（`sources/catalog`），提供方用 `ProviderDescriptor` 声明能力，A 股和加密货币共用一条流水线。Trade 也有 `ExecutionAdapter` 和 `Registry`，但还不够：

| 现状 | 问题 |
| --- | --- |
| 行情、参考价、订单查询是可选接口，核心流程用类型断言取，失败就报错（`order/service.go:807`、`target/price.go:30`、`equity/service.go:165` 等） | 哪些能力必须实现，看接口看不出来 |
| `Exchange.Valid()`、`bootstrap.registerBuiltins`、`ResolveExecutionCapabilities` 写死两家交易所和全部订单类型 | 新增场所要改核心代码 |
| 现货、合约的差异散落在 14 个文件的 `MarketTypeSpot`、`MarketTypeSwap` 判断里 | 股票要逐处加分支 |
| 会话强制要求私有流（`session.go:111`） | 很多券商接口没有推送 |
| `Credential` 固定为 API Key、Secret、Passphrase | 券商常用账号和网关地址 |
| 没有交易时段的概念；减仓上限取余额总量，不看可用量 | 股票收盘后会一直尝试下单，T+1 冻结的股票也会尝试卖出 |
| `Binance`、`OKX` 适配器本身 | 已经隔离得比较好，不用大改 |

## 7. 阶段 1：实盘可用，不再卡死

### T37 标的 ID 标准化

问题：采集和策略的标的 ID 是 `BTC-USDT`（`collector/internal/sources/crypto/subject.go:19`），Trade 从交易所加载的是 `BTC-USDT-SPOT`、`BTC-USDT-SWAP`（`CanonicalInstrumentID`），目标发布和接收路径上没有转换，而 Trade 按 ID 精确匹配。成员就绪时，策略目标会因 “no enabled member supports instrument” 被直接丢弃（[target.go:174](../../modules/trade/internal/eventconsumer/target.go)）。测试没有发现，是因为 e2e 测试数据把 Trade 标的 ID 写成了 `BTC-USDT`，而适配器测试断言的是带后缀的格式。

  - 去除首尾空格，转成大写。
  - `BASE-QUOTE`：补上市场后缀。
  - `BASE-QUOTE-SPOT`、`BASE-QUOTE-SWAP`：后缀与账户市场一致就原样返回，不一致就报错。

验收：

### T4 拒单不再循环

问题：交易所明确拒单后，[executor.go:829](../../modules/trade/internal/application/target/executor.go) 只返回错误，下一秒用新的客户端订单号重下，一直持续到目标过期。

规则：同一目标、同一标的、同一执行账户，出现过**已调用交易所**的 `REJECTED` 子单后，本目标不再向这个账户下单。还有其他成员就换下一个；都不可用就把该标的写入 `blocked_targets`，原因取订单的 `reject_reason`。下一个目标自然重试，不做冷却。

本地校验失败同样写 `REJECTED`，但它们在持仓或资金刷新后可以恢复，所以不计入：查询条件要求 `c_submitted_at > 0`，不需要加字段。

改动：

- `store` 增加按 `target_id` 查询已拒绝子单的方法，使用现有索引 `idx_trade_orders_logical_owner_state`。
- `placeAction` 过滤候选成员。减仓候选从一个扩为全部同向持仓成员，按持仓大小排序。
- `Submit` 返回的订单状态为 `Rejected` 时，按候选失败处理，不再作为错误向上返回。`Converge` 里待提交订单的分支同样处理。
- `Place` 返回 `permanentValidationError` 时也按候选失败处理，否则仍是每秒报错。
- `terminalize` 写默认原因“交易所拒单”，异步拒单也有原因。
- Binance `-1015` 归为限流；`-1021` 归为不确定错误，实现前确认 HTTP 状态。

验收：

- 测试桩持续拒单时，一个目标在单账户上只产生一笔拒绝订单，目标状态为 `BLOCKED`，原因可读。
- 多成员时自动换下一个成员，减仓同样可以换。
- 本地资金不足后再次满足条件时，同一目标能继续下单。

### T38 降低已阻塞和已收敛目标的重算频率

问题：工作线程每秒重算 `BLOCKED` 和 `CONVERGED` 目标（[target_worker.go:197](../../modules/trade/internal/runtime/target_worker.go)）。资金不足的标的每次都先请求一次报价，50 个标的阻塞时约 50 次请求每秒，有被交易所限频的风险。`CONVERGED` 目标每次也要读全量标的表。

改动：定时器只处理 `PENDING`、`CONVERGING`。`BLOCKED`、`CONVERGED` 只在 `Wake`（账户事实变化）时重算，每次同步都会唤醒，至少每 30 秒一次。`WakeTarget`（新目标）不变。

验收：`BLOCKED` 目标在账户事实没有变化时不发起报价请求；资金到账同步后能继续下单；已收敛目标在手工改仓后的下一次同步能发现差额。

### T6 账户同步不阻塞其他账户，失败不断开会话

问题一：[service.go:108](../../modules/trade/internal/application/accountsync/service.go) 持有全局成员锁期间调用 REST，一个账户慢，所有账户的成交入账都要排队。只在拿到账户锁后释放成员锁不够：同组账户 B 持着成员锁等执行锁时，其他组合账户仍要排队。

改动：同步路径完全不拿成员锁，抽出 `lockSyncScope`，在 `SyncAccount`、`ApplySnapshot`、`ApplyFill`、`ApplyOrder` 中统一使用，沿用 `lockCurrentLogicalAccount` 的做法：

1. 无锁读取组合账户 ID。
2. 拿执行锁和账户锁。
3. 复核归属，不一致就释放后重试，最多 4 次。

成员变更同时持有执行锁和账户锁，所以复核通过后归属不会变化。全局成员锁只留给成员变更。

问题二：周期同步的任何 REST 错误都会断开私有流并全量重启（[session.go:291](../../modules/trade/internal/runtime/session.go)）。

改动：同步失败时记录错误、保持未就绪，下一轮重试。只有私有流结束才重启会话。

验收：

- A、B 同组且 A 的 REST 阻塞时，不同组账户 C 的同步和成交入账正常完成；B 排队等待属预期。
- 成员变更的并发测试继续通过。
- REST 临时失败时私有流不断开，恢复后账户回到就绪。

### T7 撤单和异常订单都有退出路径

问题：撤单失败后操作永远停在 `RUNNING`（[cancel.go:232](../../modules/trade/internal/application/operator/cancel.go)），恢复自动执行又要求没有运行中的操作。本地活动、交易所已查不到的订单也会一直卡住新目标。

改动：

- 本地为 `OPEN`、`PARTIALLY_FILLED`、`CANCELING`、`CANCEL_UNKNOWN` 的订单，不在挂单列表、交易所明确返回不存在，且 `max(c_submitted_at, c_ctime)` 已超过 5 分钟，才按已撤销处理并写入同步告警。迟到成交仍可入账（领域模型已支持）。

验收：

- 撤单持续失败时，5 分钟后组合账户可以恢复；清仓持续失败时，30 分钟后可以恢复，并能看到剩余持仓。

- 外部挂单没有客户端订单号、接口返回 404、OKX 返回空数组时，都不得判为已撤销。

## 9. 阶段 3：收敛与同步模型

### T14 完成判定按交易规则

问题：目标数量保留 18 位小数，判定完成要求完全相等，正常收敛也会变成 `BLOCKED`。

规则，在计算出标的的剩余量之后按顺序判断。这里的成员指全部启用成员，不受 T4 的拒单过滤影响：

1. 剩余量在全部成员上取整后都为 0：已完成。
2. 剩余量在所有成员上都达不到最小数量或最小名义金额：
   - 目标为 0，或该标的已有同向持仓：已完成，剩余量无法下单。
   - 从空仓开新仓就达不到最小量：`BLOCKED`，这才是需要人看的情况。
3. 有成员能下单，但被 T4 排除后没有候选：`BLOCKED`，原因取拒单原因，不能算完成。

配套改动：

- 减仓改为逐成员尝试，某成员步长粗取整为 0 时换下一个。
- 反向零头下不了单时跳过这个成员，继续判断加仓；全部成员都下不了才 `BLOCKED`。
- 合约全平的 reduce-only 订单只查最小数量，不查最小名义金额。需要 T8 在测试网确认。

现货减仓后残留的零碎数量按第 2 条算完成。股票不足一手的余量同样按第 2 条算完成。

完成判定按 `Total` 算。持仓够但可卖量不足（比如 T+1 冻结）下不了单时不算完成，状态为 `BLOCKED`，原因写“可卖量不足”。

验收：常规调仓结束状态为 `CONVERGED`；`TestTargetExecutorRecordsBelowMinimumBlockedTarget` 保留；`TestTargetExecutorRecordsBlockedRemainingDelta` 要改，全平不再查最小名义金额，应该下单而不是 `BLOCKED`；新增测试覆盖步长 0.001 和 0.01 的双成员、一成员被拒而另一成员达不到最小量（必须是 `BLOCKED`）、反向零头加目标持仓、T41 假券商不足一手的余量。

### T16 同步只拉需要的标的

问题：每次同步都按全部标的拉成交，501 个标的就是 501 次请求，而且每笔成交后都要同步一次。

做法：不分两种同步模式，每轮同步拉成交的标的改为下面五项的并集：

1. 活动订单涉及的标的。
2. 有成交缺口的订单涉及的标的。
3. 持仓快照数量与本地不一致的标的。
4. 现货里余额与上一份快照不同的资产对应的标的。现货没有本地持仓表，只能和上一份快照比。
5. 轮转批次：全集的十分之一，每轮换下一批，30 秒一轮时 5 分钟走完一圈。

全集指 `syncSymbols` 的结果：有成交游标、有持仓的标的，以及现货持有资产对应的交易对。T21 删除 `sync_symbols` 后不再包含手填列表。

会话启动和控制台手动同步拉全集。账户、持仓、挂单每轮都读。

不用“5 分钟内订单涉及的标的”：换仓时它就是全部换仓标的，同步反而最慢，而 `Submit` 后的同步只有 3 秒预算。已结束且成交齐全的订单不需要再拉。

接入前的历史成交：T18、T21 之后，标的第一次进入拉取范围往往是 MooX 第一次在它上面下单之后。这时没有成交游标，会从头拉全部历史，接入前的手工成交或重建 Trade 库之前的成交都会被算成外部成交，组合账户在调仓中途被暂停。已用测试复现。

规则：

- `applySnapshot` 开头过滤：早于执行账户创建时间的成交只推进游标，不入账，也不算外部成交。这些成交的结果已经包含在余额和持仓快照里。过滤要排在 `batchQuantities` 和 `positionDeleteBefore` 之前，否则持仓删除边界会被拉回到最老的成交。
- 账户创建前下的挂单在创建时可能已部分成交，这部分成交被过滤后，累计成交缺口永远补不上，账户会一直未就绪。所以 `importExternalOrder` 导入“交易所下单时间早于账户创建时间”的订单时，把“交易所累计成交量减去本批未过滤的该订单成交量”作为本地成交量的起点，同时带上均价，后续新成交在此基础上累加，订单也能正常走到 `FILLED`。成交先于订单处理，不减掉本批成交会重复入账，报 “Fill exceeds order quantity”。
- 账户创建之后的真实外部成交仍然暂停。`binance.go:690` 的注释和相关测试同步修改。

其他改动：

- `syncSymbols` 增加范围参数，并与 `sessionSymbols` 合并成一个函数。
- `ensureOneWayMode`、`ensureSingleAssetMode` 只在会话启动时检查。

验收：500 个标的配置下，换仓期间每轮 `userTrades` 请求不超过“上述 1～4 项 + 轮转批次”；未入账的手工成交一轮内被发现；有成交缺口的账户不必等待一整圈就能恢复；接入前手工交易过的标的，策略首次下单后组合账户不被暂停，账户创建之后的外部成交仍然暂停；接入前部分成交的挂单，后续成交完或撤单后账户能回到就绪。

### T17 余额确认使用实际读取时间

问题：Binance 合约的快照时间取资产 `updateTime`，是最后变更时间。余额没变的成交（比如零手续费）之后，快照时间追不上成交时间，账户一直未就绪。私有更新用事件时间，而 REST 用 `updateTime`，后者更早时快照还会被判为旧数据。

改动：

- `Snapshot` 增加 `AccountReadAt`，由 `syncAccountLocked` 和 `session.go` 在读取账户快照前记录本地时间。适配器不动。
- `applySnapshot` 判断快照新旧、清除待确认水位时用 `AccountReadAt`，`SnapshotSourceTime` 也写它。
- 读取顺序不变，持仓删除边界 `positionDeleteBefore` 继续用原来的时间，否则会误删刚开的持仓。
- 账户读取之后才发生的成交，时间晚于 `AccountReadAt`，这轮不清除水位，下一轮同步自然覆盖。
- `ApplyAccountSnapshot` 收到旧于已存时间的私有更新时，不合并余额，但仍抬高水位并关闭准入。
- 本地时钟偏慢时，下一轮同步自然修正。

验收：余额未变化的成交之后，下一轮同步恢复就绪；成交释放预留到快照确认之前，准入保持关闭；持仓读取后到账户读取前到达新开仓成交时，同步结束持仓行仍在。

### 重建 Trade 库的步骤

阶段 1A 和阶段 4 改了表结构，新版本启动时会比对表结构，不一致就拒绝启动，`reset` 也不改表结构，所以只能删库文件。删库会清掉执行账户、组合账户、成员和成交游标，组合账户 ID 由服务端生成，无法沿用，Strategy 实例还指向旧 ID。按下面的顺序做：

1. 停用绑定了组合账户的策略实例。
2. 记下执行账户、组合账户、成员优先级和杠杆配置。
3. 实盘账户平仓、撤单。不平仓的话，第 6 步要走“接管已有敞口”。
4. 停止 Trade，删除库文件，发布新版本。
5. 重建执行账户和杠杆配置。阶段 1A 在 T18 之前，实盘没有 `"*"` 回退，要逐标的设置。
6. 重建组合账户和成员。
7. 把策略实例改绑到新的组合账户 ID，重新启用。页面没有改绑入口，用命令行 `strategy instance update`，这是整体替换：`--strategy-id` 必填，漏掉 `--logical-account-id` 实例会变成仅计算。
8. 确认账户就绪后，人工恢复自动执行。

如果跳过第 7 步，实例启用会失败（Trade 返回账户不存在），持仓留在交易所却收不到平仓目标。
