# 因子本地时序存储、导入与回放设计

2026-10-21 · v5（按讨论结论重写） · 基于 `feat/ws-market-stream`（3ec89780）

## 0. 已确认的决定

| # | 决定 |
| --- | --- |
| 1 | 因子机本地用 Pebble 持久化时序数据（不限于 K 线）；实时计算、水位追赶、补算、重算都从本地读，Storage 只用于补增量和修正 |
| 2 | 本地数据**永不删除**；不做每日全量核对；不抽公共 Pebble 包；不做应用层压缩，开启 Pebble 自带的块压缩 |
| 3 | 内存保留按列存储的**滑动窗口**；初始化时估算窗口内存给用户参考；`compute.max_memory` 按探测到的内存自适应 |
| 4 | 本地组件用通用命名 `series*`：`seriesstore`、`serieswindow`、`seriessync` |
| 5 | 本地写入**只有一种语义：整段替换**。导入的数据必须带数据集的全部字段 |
| 6 | 本地数据**写入时保证连续、没有空洞**，每个标的的本地数据就是 `[Earliest, Latest]` 连续的一段，相信 `Latest`。标的首根就是本地最早一根 |
| 7 | 交易所本身缺的周期写成**缺失行**，按字段的填充规则（`prev` / `prev_close` / `zero`）填充并带「已填充」标记；不设长缺口上限；填充只发生在本地，不写回 Storage |
| 8 | 数据导入独立成 **`modules/importer`**，并入现有 `moox-cli storage import`；格式解析独立成 **`packages/seriesformat`**，CSV 是第一种格式 |
| 9 | 逐期回放独立成 **`modules/replay`**；回放不产生实际下单，只走纸上交易；每次回放创建专用 PAPER 账户和独立策略会话 |
| 10 | 回放默认按下一根 K 线开盘价成交（可选本期收盘价）；回放不走生产事件总线 |
| 11 | Storage 是近期数据的权威，本地靠 Storage 行变更序号持久化同步；导入的历史不受 Storage 保留期约束 |
| 12 | 变更日志断档（离线太久、Storage 节点更换）不自动处理：自检判为未就绪，由用户执行对账命令 |
| 13 | **系统生命周期**：模块和对象（因子集合、策略实例）两级都有状态；所有模块就绪后由用户启动，先预热（真实数据、不真实下单），用户确认后才进入运行；首页按颜色展示 |
| 14 | 重启后通过该模块的启动前检查就直接回到原阶段；运行中出故障**只停受影响的部分**；策略实例暂停 = 不发新目标、持仓不动 |
| 15 | 本期一个数据源（space + dataset + freq）对应一个因子集合；频率限 1m–1d 固定频率，不做 3m、周线、月线 |
| 16 | 5 万根主要用于 1m；View 默认保留根数从 5000 改为 **1 万**，初始化时可设置 |
| 17 | 所有时间统一用 UTC：块边界、文件时间列、命令参数、日志、回放时钟 |

## 1. 背景

- 预期规模：每个标的回看最多约 5 万根 1m K 线，1000 多个标的，单次计算约 5000 万行。
- 现状：因子引擎每期从 Storage 经网络读取，只在进程内存里缓存实时窗口（`pipeline/window_cache.go`）。
  - 缓存用 `[][]any` 按行存储，每格约 48 字节（`pipeline/memory.go:16-18`），这个规模下放不下；
  - 重启要整窗口重新预热；
  - 补算、重算（`ModeRecalc`）每次从 Storage 读整窗口（`pipeline/load.go:48-56`）。
- 现有的修正通知 `PeriodsFilled` 只在内存里暂存（`rpc/filled_inbox.go`，10 分钟过期、最多 1000 条、取出即清空），丢了靠追赶循环重新从 Storage 读回。改成全部读本地后这层兜底消失，需要 Storage 提供可补读的变更日志（第 5.1 节）。

## 2. 总体结构

```
  数据文件（因子机磁盘）
        │
   modules/importer ── packages/seriesformat（csv …）
        │ 写入目标            │
        ▼                    ▼
  因子引擎本地写入接口      Storage（权威）
        │                    │ 变更日志 / 区间读取
 ┌──────┼──────── 因子引擎进程 ┼──────────────────────────┐
 │      ▼                    ▼                           │
 │  seriesstore（Pebble，永久） ◄── seriessync            │
 │      │ 启动加载 / 每期追加                              │
 │      ▼                                                 │
 │  serieswindow（内存列式窗口，读租约）  ◄── 内存准入      │
 │      │                                                 │
 │  pipeline（实时 / 追赶 / 补算 / 重算）   回放计算接口     │
 └──────┼─────────────────────────────────────┼──────────┘
        ▼                                     ▲ 按期计算
  Storage 结果写回                      modules/replay
                                       │ 策略回放求值 → Trade（专用 PAPER）
```

| 位置 | 组件 | 职责 |
| --- | --- | --- |
| `modules/factor/internal/` | `seriesstore` | 本地磁盘存储，Pebble 只出现在这里 |
| | `serieswindow` | 内存列式窗口，提供读租约 |
| | `seriessync` | 从 Storage 增量同步、修正重拉、对账 |
| | 内存准入器 | 计算、回放、窗口换代向它申请内存预留 |
| `modules/importer` | 导入服务 | 读文件、解析校验、写到一个或多个写入目标 |
| `modules/replay` | 回放编排 | 回放会话、周期记录、调用因子 / 策略 / Trade |
| `packages/seriesformat` | 格式解析 | 统一 `Decoder` 接口与各格式实现，以及与格式无关的校验 |

Pebble 同一目录只允许一个进程打开，所以本地存储只能由因子引擎进程持有：导入服务通过因子引擎的本地写入接口写入，回放服务通过因子引擎的回放计算接口取因子。本地存储不能独立成服务，否则又回到每期经网络读取整窗口。

## 3. 本地存储 seriesstore

### 3.1 接口

```go
type Store interface {
    // ReadRange 返回 [start, end) 内各标的的列式数据，按 data_time 排序。
    // 一次调用在同一个 Pebble 快照上读，各标的版本一致。
    ReadRange(ctx context.Context, src Source, subjects []string, start, end time.Time) (map[string]*Columns, error)
    // WriteRange 用 rows 完整替换标的在 [from, to) 内的数据。rows 必须带数据集全部字段，
    // 写入前做连续性检查（第 3.3 节），缺的周期按填充规则写成缺失行（第 3.4 节）。
    WriteRange(ctx context.Context, src Source, subject string, from, to time.Time, rows *Columns, opts WriteOptions) error
    // Latest / Earliest 返回标的本地最新、最早一根的时间；本地数据在两者之间连续。
    Latest(src Source, subject string) (time.Time, bool, error)
    Earliest(src Source, subject string) (time.Time, bool, error)
}

type Source struct{ SpaceID, DatasetID, Freq string }
// Columns: Times []int64（UTC 秒）、SeriesTags、按字段名的列（带类型描述和空值位图）、每行的「已填充」标记。
// WriteOptions: SyncCursor（同步位点，随写入原子提交）、RecalcPending（要随写入记录的失效区间）、AllowMissing（导入时允许中间缺期）。
```

- **原子边界**：一次 `WriteRange`（或同步器把本期所有标的合成的一批）在一个 Pebble batch 里同时提交块、`m/latest`、`m/earliest`、同步位点和失效重算待办。崩溃后不会出现「块已写、位点没动」或「数据改了、重算待办丢了」。
- 不提供删除接口：本地永不删除。

### 3.2 数据布局

- **key**：`k/{space}/{dataset}/{freq}/{subject}/{blockStart 大端 int64 UTC 秒}`。各段是系统内标识符，写入前做字符校验，不需要转义编码。
- **块跨度**按频率固定，每块几十到几百行：

  | 频率 | 块跨度（UTC 对齐） | 每块行数 |
  | --- | --- | --- |
  | 1m | 1 小时 | 60 |
  | 5m | 6 小时 | 72 |
  | 15m / 30m | 1 天 | 48–96 |
  | 1h | 1 周 | 168 |
  | 4h | 1 个月 | ~180 |
  | 1d | 1 年 | ≤ 366 |

- **块内按列编码**：
  - 头部：行数、schema 版本、列名与类型表（数据集全部字段）；
  - 时间列：int64 UTC 秒；行身份是 `(data_time, series_tag)`，同一时间可以有多个 series_tag；
  - `series_tag`：块内字典；
  - 「已填充」位图：每行一位；
  - 数值列：float64 / int64 + 空值位图；其他类型（字符串、BOOL、TIME、JSON）：长度前缀字节；
  - 不做应用层压缩，Pebble 用默认块压缩。
- **存数据集全部字段**。数据集加字段后，新块带新 schema 版本，旧块里该字段读出为空；要补齐旧数据就重新导入或由同步器重拉对应区间。
- **元数据 key**：
  - `m/layout`：布局版本，不一致时自检失败；
  - `m/latest/…`、`m/earliest/…`：每个标的本地最新、最早时间；
  - `m/sync/{src}`：同步位点（Storage 变更游标，第 5.1 节）；
  - `m/recalc_pending/{src}`：待提交的失效重算区间（第 5.3 节）。

### 3.3 连续性约束

本地每个标的的数据始终是 `[Earliest, Latest]` 上按频率网格**连续**的一段（有交易时段的市场按 `packages/marketcalendar` 的交易日历取网格），所以：

- 「本地同步到哪里了」只看 `Latest`；
- 标的的首根就是本地 `Earliest`，早于它的周期视为上市前（`pipeline/gapcheck.go` 的头部缺失规则改为读本地 `Earliest`；导入更早的数据让 `Earliest` 前移时，清掉首根缓存即可）。

`WriteRange` 的检查：

1. 写入的这段本身在网格上连续；中间缺期时，来自同步器的写入按第 3.4 节写成缺失行，来自导入的写入只有带 `AllowMissing` 才写成缺失行，否则拒绝并列出缺的周期；
2. 写入区间必须与本地已有数据相接或重叠：接在 `Latest` 之后、接在 `Earliest` 之前（导入更早的历史），或者覆盖已有区间（修正）；与本地数据之间留出空档就拒绝。本地还没有该标的时，第一次写入不受这一条限制。

### 3.4 缺失行与填充

交易所宕机、维护等时段本身就没有数据，Storage 里也没有。为了保持连续，这些周期写成**缺失行**：

- **何时写**：只有当某个周期**之后**已经有真实数据时，才把它判定为缺失并写成缺失行。本期数据还没到（采集延迟）不写，`Latest` 不前进，这个标的本期按现有规则算失败、进跳过账本；下一期数据到了而这一期仍没有，才写成缺失行。所以策略决策时用到的本期数据一定是真实的。
- **怎么填**：按数据集字段定义上的填充规则（新增字段属性 `fill`）：

  | 规则 | 含义 | 典型字段 |
  | --- | --- | --- |
  | `prev`（默认） | 取上一期该字段的值 | 资金费率、持仓量等状态类字段 |
  | `prev_close` | 取上一期的 close | open / high / low / close |
  | `zero` | 填 0 | volume、成交额、成交笔数 |

  不设长缺口上限，缺多少期就填多少期。
- **标记**：每行带「已填充」标记，表达式执行器里暴露成一列 `is_filled`，因子需要排除填充值时可以用它；默认把填充值当正常值参与计算。
- **只在本地**：填充行不写回 Storage，Storage 保持原始数据。之后采集器补齐了真实数据，Storage 产生变更，同步器整段替换，填充行被真实值覆盖，并生成失效重算待办（第 5.3 节）。
- **填充随前值联动**：填充值依赖前一期的值，所以任何 `WriteRange` 写完后，如果紧跟其后是一段连续的填充行，要按新的前值重新生成这段填充行。例如 t1、t2 原本都按 t0 填充，补回 t1 的真实值后，t2 要改按 t1 填充。实际改变的区间延伸到这段填充行的末尾，窗口覆盖和失效重算都按延伸后的区间处理。

### 3.5 读写实测（2026-10-21）

环境：云端 4 核容器，Pebble v1.1.5，1000 标的 × 5 万根 1m，7 个数值字段。测试代码在会话临时目录，可按需放进仓库的 `tools/`。

| 项 | 块方案（采用） | 对照：每根一个 KV |
| --- | --- | --- |
| 全量导入 5000 万行 | 34s，约 145 万行/秒 | 64s，约 78 万行/秒 |
| 每期追加 1000 根（一批，同步落盘） | 平均 33ms，最慢 104ms | 平均 15ms |
| 读 1000 × 1 万根 | 1.4–2.9s | 2.0–3.2s |
| 读 1000 × 5 万根 | 5.6–6.0s | 7.9–8.1s |
| 磁盘 | 2.8GB | 2.8GB |

结论：

- 追加的读改写每期只要几十毫秒，不是瓶颈。实时写入量是每分钟约 2000 根，离上限差三四个数量级。现有的 WS 采集写主存也是「每个数据集每期一次批量提交」（`collector/internal/stream/commit.go`），是同一种模式。
- **瓶颈是每期整窗口重读**（5 万根约 6 秒），所以引入第 4 节的内存滑动窗口。磁盘存储只在启动、回放开始、修正重拉和超出窗口的补算时读取。

### 3.6 容量

- 本地磁盘：实测约 56 字节/行。crypto 1m 现货加合约（约 2000 个序列）存 5 万根约 5.6GB。因子机剩余 1.7T，不需要清理。
- Pebble 块缓存 512MB，可配置，计入进程内存预算（第 4.4 节）。

## 4. 内存滑动窗口 serieswindow

### 4.1 结构

- **单位**：每个数据源一份窗口；本期一个数据源只对应一个启用的因子集合（现有 `factor.sql:16` 的唯一约束 `(space, dataset, freq)`）。
- **长度**：该集合内各因子的最大回看根数。
- **序列与时间网格**：按 `(subject, series_tag)` 分序列；时间轴按频率对齐成固定网格。本地数据连续，所以窗口内没有缺行，只有「值为 NULL」和「已填充」两种标记。这正是表达式执行器面板输入（`packages/factorexpr/exec/panel.go`）要求的布局。
- **存储**：每个序列每个字段一个定长数组（float64 或 int64），另有时间数组和已填充位图。容量 = 窗口长度 + 余量 H（默认 2 个块跨度的行数），环形写入；窗口提供支持环形偏移的**访问层**，表达式执行器通过它读取，不每期重新铺平整个窗口。
- **读租约**：
  - 计算前 `Acquire(endPeriod)`，返回的视图只包含 `endPeriod` 及之前的 L 根，持有期间这一范围内的数据不变；
  - 追加只写余量，不影响已有租约；余量用尽或修正覆盖已有区间时，复制成新一代数组再原子切换，旧一代等租约释放后回收；
  - 同时存活的代数最多 2 代，已有 2 代时新的换代排队；换代前先向准入器预留新一代内存。
- **提交与锁**：网络读取和文件解析在锁外完成；向窗口提交只在切换一代的瞬间持有数据源锁；实时周期的同步和计算优先于导入。
- **生命周期**：引擎启动时从 `seriesstore` 加载（5 万根约 6 秒）；每个实时周期由同步器写盘后追加；修正重拉后覆盖对应区间。回放使用独立的回放窗口（第 7 节）。

### 4.2 内存估算

公式：**标的数 × 窗口根数 × (数值字段数 + 1) × 8 字节 × 1.1**，再加余量 H 和换代副本（最坏接近再多一份窗口，复制前向准入器预留）。crypto K 线 7 个字段，约每行 70 字节：

| 序列数 | 1 万根 | 5 万根 |
| --- | --- | --- |
| 1000（如现货 1m） | ~0.7GB | ~3.5GB |
| 2000（现货 + 合约 1m） | ~1.4GB | ~7GB |
| 再加 1h 两个数据集 | +~1.4GB | +~7GB |

- **初始化时**：探测因子机内存（已有，`cli/internal/configinit/probe.go:142`）；按「计划启用的数据集 × 预计标的数 × 窗口根数（默认 1 万）」给出窗口内存估算，和建议的内存配置一起展示（第 8 节）。
- **运行时**：状态页显示每个数据源窗口的实际占用；新启用的集合会让窗口内存超过 `window.max_memory` 时拒绝启用，并给出明确原因。

### 4.3 对计算侧的影响

窗口是列式的，pipeline 的读取和表达式执行器的输入改成列式，跳过 `storageio.Frame`（`[][]any`）。这是本期必做：每期把 5000 万格转成 `[][]any`，本身就要十几 GB 内存和数秒 CPU。

- **数值字段**：通过窗口访问层直接构建面板；INT 转 float64、BOOL 按 0/1 的类型转换固定在窗口层。
- **携带列（非数值）**：只取目标周期的那几行，仍按行处理。
- **内存预算**（`pipeline/memory.go`）：去掉「读取帧」一项，窗口常驻内存按第 4.4 节统一计入；补算、重算、回放预热从磁盘读区间时的列式读取缓冲保留。

### 4.4 进程级内存准入

`compute.max_memory` 只限制**单次**计算，而不同集合的计算可以并行（`trigger/lanes.go` 每个集合一条车道）。所以引入进程级预算：

- `memory.total_budget = 总内存 × 60%`，常驻部分（实时窗口 + Pebble 块缓存）先扣除；
- 计算、回放窗口、窗口换代在开始前向准入器**预留**内存，预留不到就排队，超时拒绝并给出原因；
- 实时周期的计算优先级最高，回放、重算让路。

## 5. 同步 seriessync

### 5.1 Storage 变更日志（前置工作）

本地靠 Storage 的行变更序号得知修正。现有 Storage 没有可补读的行变更接口：`source_sequence`（`storagepb/storage_events.proto`）只在 `(source_node_id, source_store_id)` 内可比较，来自 outbox；事件发布确认后 relay 会删除 outbox 记录（`datanode/outbox/relay.go`）；事件流只保留 72 小时 / 8GiB，也没有按序号读取的 RPC。需要在 Storage 侧新增：

- **持久化变更日志**：记录数据集、标的、时间区间、变更序号；与行写入在同一个 Pebble batch 里提交；保留期默认 7 天；
- **读取接口**：游标身份是 `(source_node_id, source_store_id, sequence)`，`ReadChanges(after_cursor, limit)` 分页读取；
- **断档检测**：游标早于日志保留起点、或游标身份对不上（Storage 节点更换）时返回「断档」。

`PeriodsFilled` 通知保留，只作为「有变更了，尽快读」的提示，丢了不影响正确性。

### 5.2 同步动作

| 时机 | 动作 |
| --- | --- |
| 每个实时周期，计算前 | 对本期标的，从 `Latest` 拉到本期末，`WriteRange` 写盘（本期所有标的一批提交），再追加到窗口。正常每个标的只拉 1 根；缺期按第 3.4 节处理 |
| 引擎启动 | 从 `Latest` 拉到当前，补停机缺口；读 `m/sync` 之后的变更；然后加载窗口 |
| 每次心跳、收到 `PeriodsFilled` | 读 `m/sync` 之后的变更，对变更区间重拉并 `WriteRange` 覆盖本地和窗口，失效重算待办与同步位点同批提交；之后才唤醒水位推进和补算（调整 `onFilled` 的顺序） |
| 本地没有某个标的（新上市、新数据集） | 从 Storage 拉「最大回看根数」的数据，一次性写入 |
| 读到「断档」 | 不自动处理：引擎自检判该数据源未就绪（第 6 节），受影响的集合暂停，提示用户执行对账命令 |

- **Storage 保留期**：同步器只用 Storage 保留期内的数据替换本地；保留期之外的本地数据不动，Storage 返回空结果也不当作删除。
- 导入服务写 Storage 产生的变更，同步器读到后会重拉同一区间，得到的是同样的数据，不需要特殊处理。
- 同一数据源的同步写入和导入写入按数据源互斥提交。

**对账命令**（`moox-cli factor series reconcile --source <space/dataset/freq>`）：

1. 取 Storage 变更日志当前游标 `C0`；
2. 对「本地数据范围 ∩ Storage 保留期」逐标的重拉并 `WriteRange`；
3. 补读 `C0` 之后的变更并应用，然后把 `C0` 之后的最新游标写入 `m/sync`。

Storage 每个分页 RPC 各自新建快照（`pebble/rows_read.go`），全量扫描不来自同一快照，所以基线游标要先取、扫描后再补读，不能取扫描结束时的序号。对账完成后自检通过，受影响的集合自动恢复。

### 5.3 数据修正后的重算

修改 `[from, to)` 内的数据，会影响其后所有仍然包含这些数据的回看窗口：

- 失效范围是 `[from, to + (L−1)×周期)`，截断到已经计算过的范围；截面因子（依赖标的全集的）扩展到相关全部标的；
- 触发来源：同步器的修正覆盖了已经算过的区间（包括填充行被真实数据替换）、导入带 `--recalc`、导入更早的历史让 `Earliest` 前移（此前按「上市前」算的区间，失效范围从新的 `Earliest` 起算）；
- 失效区间作为待办 `m/recalc_pending/{src}`，与数据同批提交；后台用稳定的 `request_id` 幂等提交区间重算任务（`recalc.Service.Submit`），提交成功后清除待办；
- 重算完成前，受影响区间的因子值是旧值，状态页显示「待重算区间」。

## 6. 系统生命周期与状态

### 6.1 状态

模块和对象（因子集合、策略实例）都有状态，含义一致：

| 状态 | 颜色 | 含义 |
| --- | --- | --- |
| 未初始化 | 灰 | 刚部署，配置或初始化未完成 |
| 未就绪 | 红 | 启动前检查有失败项，列出原因和处理命令（如「本地数据不足，请导入 xxx」「变更日志断档，请执行对账」） |
| 就绪 | 蓝 | 检查全部通过，等待用户启动 |
| 预热 | 黄 | 用真实数据跑完整链路，不真实下单 |
| 运行 | 绿 | 用户确认预热结果后进入 |
| 暂停 | 橙 | 受上游故障影响自动暂停，或用户手动暂停 |
| 故障 | 红 | 运行中出现自身无法恢复的错误 |

**系统状态**分两个维度，首页同时展示：

- **健康面**：由各模块状态推导，任何一个模块未就绪或故障，系统标红，并列出模块和原因；
- **运行阶段**：就绪 → 预热 → 运行，只由用户命令推进，不会自动跳。

首页的展示形如「运行中 · 降级（因子引擎：crypto/spot_1m 变更日志断档）」。模块状态里汇总它管理的对象状态；新增一个因子集合或策略实例时，只有它自己走一遍「就绪 → 预热 → 确认运行」，不影响已经在运行的部分。

### 6.2 模块要提供的能力

每个模块都提供下面这些接口（RPC）和对应的命令行：

| 能力 | 说明 |
| --- | --- |
| `check` | 启动前检查，复用 `packages/doctor` 的检查框架（PASS / WARN / FAIL / BLOCKED 和依赖关系） |
| `init` | 执行该模块的初始化动作 |
| `status` | 返回模块状态、各对象状态和未就绪原因 |
| `start` / `confirm` / `pause` / `resume` | 推进或改变阶段；可作用于整个模块或单个对象 |

- 每个模块在自己的存储里**持久化**自己和对象的当前阶段；`packages/healthz` 现有的 `State` 只有一个就绪布尔值，要扩展成上面的状态。
- 状态由 monitor 汇总（现有 `monitor/internal/healthview`），首页展示。

因子引擎的启动前检查：本地存储布局版本；每个启用集合的数据源本地数据就绪（下一条）；变更日志没有断档；窗口内存与总预算放得下。

**本地数据就绪**的判断：对集合标的全集里的每个标的，本地连续数据满足以下之一：

- 根数 ≥ 最大回看根数；
- 本地 `Earliest` 等于 Storage 的首根，说明是在 Storage 保留期内上市、Storage 有多少本地就有多少的新标的。

并且 `Latest` 已同步到当前。不满足时给出缺数据的标的和区间，提示导入。

### 6.3 启动、预热与运行

1. 所有模块就绪后，用户点击启动（或执行启动命令），系统进入**预热**：因子正常计算，策略正常求值，Trade 对预热中的策略实例走**影子模式**：用实时报价完成目标换算，记录将要下的单（影子订单），不预留资金、不下单。
2. 首页展示预热指标：每期耗时、缺数标的数、因子覆盖率、影子订单。
3. 用户确认后进入**运行**。

Trade 的影子模式是新增能力。

### 6.4 重启与故障

- **重启**：每个模块重启后先跑启动前检查，通过就回到重启前的阶段（运行或预热），首页提示「已自动恢复」；不通过就进入未就绪，受影响的对象按下一条暂停。
- **只停受影响的部分**：按依赖链向下传：数据源 → 因子集合 → 策略实例。例如某个数据源断档，只暂停用它的因子集合和用这些集合的策略实例，其他照常。
- **策略实例暂停** = 不发新目标、持仓不动，并告警，由人决定是否手动平仓。不能用空目标表示暂停：Trade 把空的 FULL 目标解释为清仓（`trade/internal/application/target/weight_resolver.go`）。
- **恢复**：受影响的部分重新通过检查后，自动回到暂停前的阶段。期间漏掉的周期由现有追赶机制补算因子；这些过期周期不会成交，Trade 入口会按 `valid_until` 拒绝过期目标（`trade/internal/eventconsumer/target.go`）。

## 7. 导入 importer

### 7.1 部署与写入目标

- `modules/importer` 是常驻服务，部署在数据文件所在的机器上（通常是因子机），任务由 `moox-cli import` 下发，进度在命令行和首页查看。
- 文件放到该机器的导入目录（例如 `/data/moox/import/`），用户自己放，或由 Claude 用 scp 上传；导入命令只传路径。
- **写入目标**可以选一个或多个：
  - `storage`：写入 Storage（行写入接口），并入现有 `moox-cli storage import` 的能力；
  - `factor`：通过因子引擎的本地写入接口调 `WriteRange`。
- 任务状态和断点存在 importer 自己的 SQLite 里。`WriteRange` 是整段替换、天然幂等，每个目标每批写完记一次断点；失败重试就是原样重写这一批。
- 引擎处于未就绪状态时仍接受本地写入，这正是「先导入、再就绪」的流程。

### 7.2 格式与校验（packages/seriesformat）

- **格式层**：统一的 `Decoder` 接口，按批输出列式行，按格式名注册。`csv` 是第一个实现，以后加 parquet、jsonl、交易所历史数据包等，只是多一个实现。有界流式读取，不整文件累积。
- **校验层**（与格式无关，所有格式共用）：
  - 字段名与数据集注册的字段一致，**必须带全部字段**；外加时间列 `data_time`，可选 `series_tag`（或用 `--series-tag` 统一指定）；
  - 时间按 UTC 解析：没有时区的视为 UTC，带时区的转换为 UTC；
  - 连续性：文件内按网格连续；有缺期时默认拒绝并列出缺的周期，带 `--allow-missing` 时写入本地为缺失行（按填充规则），写入 Storage 时跳过这些周期；
  - 标的必须已在数据集的标签范围内（与现有 storage import 一致，不在范围内就拒绝）。
- CSV 约定：一个文件对应一个标的，文件名即标的 ID（也可以用 `--subject` 指定）。

### 7.3 命令

```
moox-cli import --format csv --space crypto --dataset <dataset> --freq 1m \
  --dir /data/moox/import/spot_1m/ [--target storage,factor] [--allow-missing] [--recalc]
```

- `--target` 默认两者都写；
- `--recalc` 时，写入因子本地的数据按第 5.3 节生成失效待办，提交区间重算，得到历史因子值。

## 8. 内存配置自适应

- 初始化探测到总内存 M、估算出常驻内存（窗口 W + Pebble 块缓存 C）后：
  - `memory.total_budget = M × 60%`；
  - `compute.max_memory = max(1GiB, (total_budget − W − C) × 50% ÷ 并行计算数)`，并行计算数取计划启用的集合数与 CPU 核数中的较小值；
  - 都写入 `engine.yaml`，用户可以修改。
- 初始化界面展示 M、W、C、总预算和建议值；`W + C` 超过总预算的 2/3，或 `total_budget − W − C < 1GiB` 时警告。

## 9. 逐期回放 replay

### 9.1 目标与边界

- 按时间顺序逐期推进历史数据，每期走实时计算路径算出因子，交给策略求值，再由 Trade 在专用 PAPER 账户里撮合，得到接近实盘时序的模拟结果。
- **回放绝不产生实际下单**；不进入生产事件总线，不影响连续水位、监控新鲜度和实盘策略实例。
- `modules/replay` 负责编排；因子引擎只提供回放计算接口，回放窗口仍在因子进程内（要读本地存储）。

### 9.2 各模块接口

| 模块 | 接口 / 改动 |
| --- | --- |
| 因子引擎 | `ReplayOpen(session, set, from)`：按预热区间加载回放窗口（会话开始时取快照，运行中不随修正更新），向准入器预留内存；`ReplayStep(session, t)`：计算第 t 期并返回因子帧；`ReplayClose(session)` |
| 策略 | 新增回放求值接口：入参是 `replay_id`、实例、周期和完整回放输入（见 9.4），复用现有求值引擎（`strategy/internal/engine`），**只返回本期决策**（目标权重或跳过），不直接发事件 |
| Trade：回放会话 | 每次回放创建专用 PAPER 账户和策略会话，初始资金与配置快照固定，结束后保留结果、可清理 |
| Trade：回放推进命令（新增 `ReplayAdvance`） | 每期必达：`replay_id`、周期、回放时钟、回放报价、决策（`UPDATE_TARGET` 内含目标权重 / `SKIP`）。`SKIP` 不改动目标，只撮合遗留挂单。同步返回本期确认 |
| Trade：执行上下文 | 会话级 `{replay_id, clock, quotes}`：入口的 `valid_until` 校验（`eventconsumer/target.go`）用回放时钟；权重换算（`application/target/weight_resolver.go`）的权益和参考价取自回放会话与回放报价；资金预留、`PaperExecutionPrice`、撮合（`execution/reservation_policy.go`、`execution/paper/pricing.go`、`matcher.go`）都用回放报价，缺价时报错、不回退实时报价；撮合只处理本会话的挂单 |
| Trade：订单、成交 | 记录 `replay_id` |
| 因子集合事件、水位 | 不变，回放不发 `FactorPeriodComputed` 等生产事件 |

### 9.3 流程

```
moox-cli replay start --set <因子集合> --instance <策略实例> \
  --from 2026-01-01T00:00:00Z --to 2026-02-01T00:00:00Z [--write-factors]
```

1. **校验**：本地数据覆盖回放区间及预热区间，并且**包含 `to` 之后的一根**（用于下一根开盘成交）。
2. **建立会话**：回放服务分配 `replay_id`，让 Trade 创建专用 PAPER 账户和会话；调用因子引擎 `ReplayOpen`：
   - 预热起点 = `from − max(L_f − 1 + k, 年龄检查根数) × 周期`，L_f 是因子最大回看根数，k 是策略引用因子列的上一根深度（如 `bars[-1]` 为 1）；
   - 第一个正式周期之前，先算出并缓存策略需要的上一期因子值；
   - 会话固定策略版本和因子定义版本。
3. **逐期推进**，对周期 t：
   1. 调 `ReplayStep` 取因子帧；
   2. 调策略回放求值，得到决策；
   3. 持久化周期记录（9.5）；
   4. 向 Trade 发 `ReplayAdvance`，等确认；
   5. 带 `--write-factors` 时写因子结果（与区间重算的写法相同，不发周期完成事件）；
   6. 本期所有阶段完成后推进下一期。挂单留到后续周期继续撮合，不等全部成交。
4. 支持暂停、继续、取消；进度、当前周期、每期耗时在回放服务里查询。

回放报价默认取下一根的开盘价，模拟「本期收盘决策、下期开盘成交」；可选本期收盘价。时间语义：K 线起点是 `data_time`，决策时刻是 `data_time + 周期`，成交时刻是下一根开盘（与决策时刻同一刻）。

### 9.4 策略回放输入契约

回放求值的入参与现有求值一致，构建逻辑复用 `strategy/internal/engine/frame.go` 和研究回放（`strategy/internal/replay/runner.go`）：

- 本期因子帧，以及策略需要的上一根数据；
- `Universe` / `Expected` / `AgedOut`、失败列、市场类型、周期序号；
- 前序规则状态（持有批次等），按 `replay_id` 独立保存，不读写实盘实例的状态。

### 9.5 周期记录与恢复

- 回放服务在自己的 SQLite 里按 `(replay_id, period)` 保存周期记录：本期决策、下一期策略状态、待发送的 `ReplayAdvance`、`--write-factors` 时的待写因子行和批次标识，以及各阶段完成标记（策略状态已保存、Trade 已确认、因子已写入）。同一期重复执行返回同一条记录，不重新求值。
- 重启后按完成标记补齐缺的阶段：Trade 未确认就原样重发命令（先向 Trade 查询该期状态），策略状态和因子行按记录原样补写；全部完成后才推进。

### 9.6 与区间重算、策略研究回放的关系

| 需求 | 用法 |
| --- | --- |
| 只要历史因子值 | 导入 + 区间重算（`--recalc`），比逐期回放快几个数量级 |
| 要按实盘时序验证策略与成交 | 逐期回放 |
| 快速比较策略版本 | 现有策略研究回放（`strategy/internal/replay`，读取 View，区间受 View 保留根数限制） |

### 9.7 速度估算

内存窗口下每期的读取成本接近零，耗时主要在计算、跨模块调用和撮合往返。如果每期 0.1–1 秒，回放一个月的 1m（约 4.3 万期）需要 1–12 小时。实施时按真实因子集合实测，再决定是否在回放里批量预计算因子、只逐期执行策略和撮合。

## 11. 故障处理

| 情况 | 处理 |
| --- | --- |
| 本地目录损坏、布局版本不符 | 自检失败、未就绪。人工删目录后重新导入，或由同步器按回看窗口从 Storage 拉取 |
| 本地数据不足 | 自检失败、未就绪，列出缺数据的标的和区间，提示导入 |
| 同步器拉取失败、本期数据未到 | 本期按现有规则：该标的算失败，进入跳过账本，之后补算 |
| 交易所本身缺数据 | 之后的周期有数据时，写成缺失行并按填充规则填充（第 3.4 节） |
| 修正通知丢失、引擎离线 | 下次心跳或启动时从同步位点继续读变更日志 |
| 变更日志断档 | 该数据源未就绪，受影响的集合和策略实例暂停；用户执行对账命令后自动恢复 |
| 内存预留不到 | 任务排队，超时拒绝并给出原因；实时周期的计算优先 |
| 上游故障 | 只暂停依赖链上受影响的对象，策略实例不发新目标、持仓不动 |
| 回放中服务重启 | 按周期记录的完成标记补齐后继续 |
| 回放订单指向非本会话账户 | Trade 拒绝并告警 |

## 12. 配置

因子引擎 `engine.yaml`：

```yaml
seriesstore:
  dir: ./data/seriesstore
  block_cache: 512MiB
window:
  max_memory: 4GiB              # 初始化按探测结果写入
  headroom_blocks: 2            # 环形窗口余量（块跨度数）
memory:
  total_budget: 12GiB           # 初始化按 总内存 × 60% 写入
compute:
  max_memory: 1GiB              # 初始化按第 8 节公式写入，是单次计算上限
```

importer：

```yaml
import:
  dir: /data/moox/import        # 数据文件放置目录
  batch_rows: 10000             # 每批写入行数
  storage_workers: 2
```

## 13. 实施阶段

| # | 阶段 | 内容 |
| --- | --- | --- |
| 1 | seriesstore | 块编码与解码、`ReadRange` / `WriteRange` / `Latest` / `Earliest`、连续性检查、缺失行与填充规则、已填充标记、原子提交；数据集字段 `fill` 属性；单元测试；带元数据 key 重测写入性能 |
| 2 | serieswindow、列式计算与内存准入 | 环形窗口（读租约、换代）；pipeline 与表达式执行器改为列式输入，暴露 `is_filled`；`gapcheck` 首根改读本地 `Earliest`；进程级内存准入；`liveWindowCache` 和后台预热先保留 |
| 3 | Storage 变更日志与 seriessync | **前置**：Storage 持久化变更日志、读取接口、断档检测；然后实时增量、启动补缺、新标的拉取、变更同步、失效重算待办、对账命令；完成后删除 `liveWindowCache` 与后台预热 |
| 4 | importer | `packages/seriesformat`（`Decoder` 接口、csv 实现、通用校验）；`modules/importer` 服务、写入目标（storage / factor）、断点；`moox-cli import`，替换 `moox-cli storage import`；`--recalc` |
| 5 | 生命周期与状态 | `packages/healthz` 状态扩展；各模块的 `check` / `init` / `status` / `start` / `confirm` / `pause` / `resume`；阶段持久化与重启恢复；依赖链暂停；monitor 汇总与首页展示；Trade 影子模式与预热指标 |
| 6 | 初始化与配置 | 窗口内存估算与内存配置自适应；`DefaultViewBars` 改为 1 万、各频率默认保留期（含 30s）、单 View 容量阈值；相关文档同步 |
| 6a | **实时闭环验证（阶段 1–6 上线门槛）** | 引擎重启、历史修正、缺失行填充与之后被真实数据替换、导入与实时并发、断档与对账、内存准入拒绝、上游故障只停受影响部分；与 Storage 抽样比对一致 |
| 7 | 逐期回放 | Trade：回放会话与专用 PAPER 账户、执行上下文、`ReplayAdvance`；策略：回放求值接口与输入契约；因子：`ReplayOpen` / `ReplayStep` / `ReplayClose`；`modules/replay`：编排、周期记录与恢复、`moox-cli replay`。短周期（几十期）的一致性与重启恢复测试在本阶段完成 |
| 8 | 部署验证 | 导入真实数据；测 1m 实时周期耗时、窗口内存、磁盘；一次一个月的 1m 回放（性能验收） |

阶段 1–6 加 6a 通过后可以先上线；阶段 7 依赖 1–5。阶段 5 涉及所有模块，可以和阶段 2–4 并行推进。
