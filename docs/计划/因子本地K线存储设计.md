# 因子本地 K 线存储与回放设计

2026-10-21 · v4（按 Codex 评审修订，已定稿） · 基于 `feat/ws-market-stream`（3ec89780）

## 0. 已确认的决定

| # | 决定 |
| --- | --- |
| 1 | 因子机本地用 Pebble 持久化 K 线；实时计算、水位追赶、补算、重算都从本地读，Storage 只用于补增量和修正 |
| 2 | 本地数据**永不删除**；不做每日全量核对；不抽公共 Pebble 包 |
| 3 | 不做应用层压缩，开启 Pebble 自带的块压缩 |
| 4 | 内存保留按列存储的**滑动窗口**；初始化时估算窗口内存给用户参考 |
| 5 | 历史数据通过 **CSV 导入**，同时写本地存储和 Storage；文件先放到因子机指定目录（用户自己放，或由 Claude 上传），导入时给路径 |
| 6 | CSV 列名与系统里注册的字段名一致 |
| 7 | **逐期回放本期要做**：回放不产生实际下单，只走纸上交易；消息体加回放标记 |
| 8 | `compute.max_memory` 按初始化时探测到的因子机内存自适应 |
| 9 | 5 万根主要用于 1m；View 默认保留根数从 5000 改为 **1 万**，初始化时可设置 |
| 10 | 所有时间统一用 UTC：块边界、CSV 时间列、命令参数、日志、回放时钟 |
| 11 | 回放默认按下一根 K 线开盘价成交（可选本期收盘价） |
| 12 | 回放不走生产事件总线：引擎直接调用策略回放求值接口，只在发往 Trade 的目标权重消息里带 `replay_id`、回放时钟与回放报价 |

评审后新增的设计约束（第 3–6、9 节展开）：

| # | 约束 |
| --- | --- |
| 13 | 本地写入分 `MergeRows`（合并）和 `ReplaceRange`（完整替换）两种语义，CSV 默认合并，只有来自 Storage 的完整快照才替换 |
| 14 | 本地 `Latest` 只表示最大时间，不代表完整；完整性由「覆盖区间」元数据表达 |
| 15 | 窗口读取走带结束周期的读租约，计算期间看到的是同一版本数据 |

| 17 | 源数据被修正后，重算范围向后扩展到受影响的回看窗口 |
| 18 | 回放的报价、时钟贯穿 Trade 的目标校验、权重换算、资金预留、撮合；每次回放使用独立会话，按 `(replay_id, period)` 幂等 |
| 19 | Storage 是近期数据的权威，本地靠 Storage 行变更序号持久化同步；导入的历史不受 Storage 保留期约束（2026-10-21 确认） |
| 20 | 每次回放创建专用 PAPER 账户和独立策略会话（2026-10-21 确认） |
| 21 | 本期一个数据源对应一个因子集合，频率限 1m–1d 固定频率，不做 3m、周线、月线（2026-10-21 确认） |

## 1. 背景

- 预期规模：每个标的回看最多约 5 万根 1m K 线，1000 多个标的，单次计算约 5000 万行。
- 现状：因子引擎每期从 Storage 经网络读取，只在进程内存里缓存实时窗口（`pipeline/window_cache.go`）。
  - 缓存用 `[][]any` 按行存储，每格约 48 字节（`pipeline/memory.go:16-18`），这个规模下放不下；
  - 重启要整窗口重新预热；
  - 补算、重算（`ModeRecalc`）每次从 Storage 读整窗口（`pipeline/load.go:48-56`）。
- 现有补算兜底：补齐通知 `PeriodsFilled` 只在内存里暂存（`rpc/filled_inbox.go`，10 分钟过期、最多 1000 条、取出即清空），丢了靠追赶循环重新从 Storage 读回。改成全部读本地后这层兜底消失，需要在本方案里补上（第 5.1 节）。

## 2. 总体结构

```
 CSV（因子机磁盘）                         Storage（权威）
     │ moox-cli factor kline import            ▲    │ 增量 / 修正重拉
     ▼                                         │    ▼
 ┌─────────────── 因子引擎进程 ───────────────────────────────┐
 │ 导入器 ──► klinestore（Pebble，磁盘，永久） ◄── klinesync    │
 │   └─后台分批写 Storage        │ 启动加载 / 每期追加           │
 │                               ▼                             │
 │            klinewindow（内存列式窗口，读租约）                │
 │                               │                             │
 │        pipeline（实时 / 追赶 / 补算 / 重算）   回放驱动        │
 │             ▲ 进程级内存准入 ▲                               │
 └───────────────────────────────┼───────────────────┼─────────┘
                                 ▼                   ▼ 回放帧（replay_id）
                         Storage 结果写回      策略回放求值 ─► Trade（回放专用 PAPER 会话）
```

`modules/factor/internal/` 下新增 5 个组件：

| 组件 | 职责 |
| --- | --- |
| `klinestore` | 本地磁盘存储，Pebble 只出现在这里 |
| `klinewindow` | 内存列式窗口，提供读租约 |
| `klinesync` | 从 Storage 增量拉取、修正后重拉 |
| `klineimport` | CSV 导入 |
| `replay` | 逐期回放驱动 |

另需一个进程级的内存准入器（第 4.4 节），放在 `pipeline` 旁边，计算、回放、导入、窗口扩容都向它申请预留。

Pebble 同一目录只允许一个进程打开，所以导入和回放都在引擎进程内执行，命令行只负责下发任务、查询进度。

## 3. 本地磁盘存储 klinestore

### 3.1 接口

```go
type Store interface {
    // ReadRange 返回 [start, end) 内各标的的列式数据，按 data_time 排序。
    // 一次调用在同一个 Pebble 快照上读，各标的版本一致。
    ReadRange(ctx context.Context, src Source, subjects []string, start, end time.Time) (map[string]*Columns, error)
    // MergeRows 按 (data_time, series_tag) 合并：行不存在则新增；行存在则只覆盖 rows 里「提供了」的字段，
    // 其余字段保持不变。新 K 线追加和 CSV 导入用它。
    MergeRows(ctx context.Context, src Source, subject string, rows *Columns, cur SyncCursor) error
    // ReplaceRange 用 rows 完整替换标的在 [from, to) 内的数据，区间内 rows 没有的行被删除。
    // 只用于来自 Storage 的完整快照（修正重拉）。
    ReplaceRange(ctx context.Context, src Source, subject string, from, to time.Time, rows *Columns, cur SyncCursor) error
    // Latest / Earliest 返回标的本地最新、最早一根的时间（只是本地数据的边界，不代表区间完整）。
    Latest(src Source, subject string) (time.Time, bool, error)
    Earliest(src Source, subject string) (time.Time, bool, error)
    // Coverage 返回标的已确认的覆盖区间及其状态（第 3.2 节）。
    Coverage(src Source, subject string) ([]CoverSpan, error)
}

type Source struct{ SpaceID, DatasetID, Freq string }
// Columns: Times []int64（UTC 秒）、SeriesTags、按字段名的列。每列带类型描述、
//   「提供」标记（该列这次是否带了值）和空值位图（带了但值为 NULL），三者区分：未提供 ≠ 显式 NULL ≠ 空字符串。
// SyncCursor: 调用方给出的同步位点（Storage 变更序号或导入断点），随写入原子提交，可为空。
```

- **原子边界**：每个写方法在一个 Pebble batch 里同时提交块、`m/latest`、`m/earliest`、覆盖区间和 `SyncCursor`。崩溃后不会出现「块已写、位点没动」或相反的状态。同步器每期对本期所有标的合并成一批提交，对应第 3.3 节的「一批同步落盘」。
- 不提供删除接口：本地永不删除。`ReplaceRange` 是唯一会让数据变少的操作，且只能由 Storage 的完整快照触发。

### 3.2 数据布局

- **key**：`k/{space}/{dataset}/{freq}/{subject}/{blockStart 大端 int64 UTC 秒}`。各段是系统内标识符，写入前做字符校验，不需要转义编码。
- **块跨度**按频率固定，每块几十到几百行：

  | 频率 | 块跨度（UTC 对齐） | 每块行数 |
  | --- | --- | --- |
  | 1m | 1 小时 | 60 |
  | 5m | 6 小时 | 72 |
  | 15m / 30m | 1 天 | 48–96 |
  | 1h | 1 周 | 168 |
  | 4h | 1 个月 | ~180 |
  | 1d | 1 年 | ≤ 366 |

  频率集合以第 4.5 节确定的本期支持范围为准。

- **块内按列编码**：
  - 头部：行数、schema 版本、列名与类型表（数据集全部字段）；
  - 时间列：int64 UTC 秒；行身份是 `(data_time, series_tag)`，同一时间可以有多个 series_tag；
  - `series_tag`：块内字典；
  - 每列：类型描述 + 「提供」标记 + 空值位图；数值列 float64 / int64；
  - 其他类型（字符串、BOOL、TIME、JSON）：长度前缀字节；读出到计算时的类型转换（INT→float64、BOOL、非数值空值）在第 4.3 节固定。
  - 不做应用层压缩，Pebble 用默认块压缩。
- **存数据集全部字段**，同一数据集的多个因子集合共用一份。数据集加字段后：
  - 新写入的块带新 schema 版本；旧块里该字段读出为「未提供」；
  - 同一个块里新旧行混合时，写入该块的读改写会把块升级到新 schema 版本；
  - 新字段的历史数据通过重新导入或重拉补齐，覆盖区间（见下）按字段记录起点，依赖新字段的因子只能在字段覆盖区间内计算。
- **元数据 key**：
  - `m/layout`：布局版本，不一致时拒绝启动；
  - `m/latest/…`、`m/earliest/…`：每个标的本地最新、最早时间；
  - `m/cover/{src}/{subject}`：**覆盖区间**列表，每段带状态：`present`（已同步到本地）、`checked_empty`（已向 Storage 查询过，结果为空）、`stale`（断档后待校验，不得用于计算）。区间之外就是「未同步」；
  - `m/exist/{src}/{subject}`：首根存在性证据，只前移不后移（第 5.3 节）；
  - `m/recalc_pending/{src}`：待提交的失效重算区间（第 5.4 节）；
  - `m/sync/{src}`：同步位点（Storage 变更序号，见第 5.1 节）；
  - `m/import/{taskID}`：导入断点与待上传 Storage 的批次；
  - `m/replay/{replayID}`：回放进度。

### 3.3 读写实测（2026-10-21）

环境：云端 4 核容器，Pebble v1.1.5，1000 标的 × 5 万根 1m，7 个数值字段。测试代码在会话临时目录，可按需放进仓库的 `tools/`。

| 项 | 块方案（采用） | 对照：每根一个 KV |
| --- | --- | --- |
| 全量导入 5000 万行 | 34s，约 145 万行/秒 | 64s，约 78 万行/秒 |
| 每期追加 1000 根（一批，同步落盘） | 平均 33ms，最慢 104ms | 平均 15ms |
| 读 1000 × 1 万根 | 1.4–2.9s | 2.0–3.2s |
| 读 1000 × 5 万根 | 5.6–6.0s | 7.9–8.1s |
| 磁盘 | 2.8GB | 2.8GB |

结论：

- 追加的读改写每期只要几十毫秒，不是瓶颈。实时写入量是每分钟约 2000 根，离上限差三四个数量级。现有的 WS 采集写主存也是「每个数据集每期一次批量提交」（`collector/internal/stream/commit.go`），是同一种模式。
- **瓶颈是每期整窗口重读**（5 万根约 6 秒），所以引入第 4 节的内存滑动窗口。磁盘存储只在启动、回放开始、修正重拉和超出窗口的补算时读取。
- 实测的写入没有包含覆盖区间与同步位点的元数据 key，阶段 1 要带上这些 key 重测一次。

### 3.4 容量

- 本地磁盘：实测约 56 字节/行。crypto 1m 现货加合约（约 2000 个序列）存 5 万根约 5.6GB。因子机剩余 1.7T，不需要清理。
- Pebble 块缓存 512MB，可配置，计入进程内存预算（第 4.4 节）。

## 4. 内存滑动窗口 klinewindow

### 4.1 结构

- **单位**：每个「数据源（space + dataset + freq）」一份窗口。每个数据源只对应一个启用的因子集合（见第 4.5 节）。
- **长度**：该集合内各因子的最大回看根数。
- **序列与时间网格**：窗口按 `(subject, series_tag)` 分序列，每个序列一个 `Series`；时间轴按频率对齐成固定网格，缺期用「行存在」位图标记，不靠时间戳比较推断。表达式执行器的面板输入（`packages/factorexpr/exec/panel.go`）要求按序列分列、时间网格对齐、区分缺行与 NULL，窗口直接提供这种布局。
- **存储**：每个序列每个字段一个定长数组（float64 或 int64），另有一个时间数组。数组容量 = 窗口长度 + 余量 H（默认 2 个块跨度的行数），以环形方式写入：
  - 每期追加一根，写到余量里，最旧的一根自然移出可见范围；
  - 环形数组绕回后不是连续的时间切片，所以窗口提供支持环形偏移的**访问层**（按序列、按字段、按时间下标取连续视图），表达式执行器的输入通过它读取，不每期重新铺平整个窗口。
- **读租约**：
  - 计算前 `Acquire(endPeriod)`，返回的视图只包含 `endPeriod` 及之前的 L 根，持有期间这一范围内的数据不会变化；
  - 追加只写余量，不影响已有租约的可见范围；余量用尽需要整理时，复制成新一代数组再原子切换，旧一代等租约释放后回收；同一个窗口同时存活的代数最多 2 代（当前代 + 一个仍被租约占用的旧代），已有 2 代时新的换代请求排队；换代前必须先预留新一代的内存，预留成功才开始复制；
  - 修正重拉、导入要覆盖窗口里已有区间时，同样复制新一代再原子切换，不原地改；
  - 租约持有者不会看到同一次计算里混用的两个版本。
- **提交与锁**：网络读取和 CSV 解析在锁外完成；向窗口提交按有界批次进行，每个批次只在「切换一代」的瞬间持有数据源锁。实时周期的同步和计算优先于导入和回放，导入不会长期占住数据源。
- **生命周期**：
  - 引擎启动时从 `klinestore` 加载（5 万根约 6 秒），加载完成前集合状态为「窗口加载中」；
  - 每个实时周期由同步器写盘后追加；
  - 修正重拉后，覆盖窗口里对应的区间；
  - 回放用独立的窗口（第 6 节），不影响实时窗口。

### 4.2 内存估算

公式：**标的数 × 窗口根数 × (数值字段数 + 1) × 8 字节 × 1.1**，再加上余量 H 和**换代副本**：计算持有租约期间，多标的的修正或导入会同时保留这些标的的旧数组，最坏接近再多一份窗口（与上表同量级，如 1000 序列 × 5 万根约再加 3.5GB）。换代副本在复制前向准入器预留（第 4.4 节）。crypto K 线 7 个字段，约每行 70 字节：

| 序列数 | 1 万根 | 5 万根 |
| --- | --- | --- |
| 1000（如现货 1m） | ~0.7GB | ~3.5GB |
| 2000（现货 + 合约 1m） | ~1.4GB | ~7GB |
| 再加 1h 两个数据集 | +~1.4GB | +~7GB |

- **初始化时**：
  - 探测因子机内存（已有，`cli/internal/configinit/probe.go:142`）；
  - 按「计划启用的数据集 × 预计标的数 × 窗口根数（默认 1 万）」给出窗口内存估算，和建议的 `compute.max_memory` 一起展示；
  - 窗口 + Pebble 块缓存超过总内存的 40% 时提示调小窗口根数（口径见第 7 节）。
- **运行时**：
  - 状态页显示每个数据源窗口的实际占用；
  - 新启用的集合如果会让窗口内存超过上限（`window.max_memory`，初始化时写入），就拒绝启用，并给出明确原因。

### 4.3 对计算侧的影响

窗口是列式的，pipeline 的读取和表达式执行器的输入要随之改成列式，跳过 `storageio.Frame`（`[][]any`）。这原本是 v2 里「单独评审」的第 7 步，现在成为本期必做：每期把 5000 万格转成 `[][]any`，本身就要十几 GB 内存和数秒 CPU。

- **数值字段**：通过窗口访问层直接构建面板。
- **类型转换**（固定在窗口层，不在表达式层各自处理）：INT 转 float64 参与计算；BOOL 按 0/1；数值列的「未提供」与 NULL 在面板里都是缺失；缺行在面板里是缺期，与有行但值为 NULL 区分开。
- **携带列（非数值）**：只取目标周期的那几行，仍按行处理。
- **内存预算**（`pipeline/memory.go`）：去掉「读取帧」那一项，窗口常驻内存按第 4.4 节统一计入。**但**补算、重算、回放预热从磁盘读区间时仍有列式读取缓冲，这一项保留，按读取的行数估算。

### 4.4 进程级内存准入

`compute.max_memory` 现在只限制**单次**计算，不同集合的计算可以并行（`trigger/lanes.go` 每个集合一条车道）。新增窗口、回放窗口、导入缓冲和 Pebble 缓存后，各任务各自通过检查，加起来仍可能超过进程可用内存。因此：

- 引入进程级内存预算 `B`，常驻部分先扣除：`B = 总内存 × 60%`；常驻 = 实时窗口 + Pebble 块缓存 + 导入缓冲上限。
- 计算、回放（回放窗口 + 每期计算）、导入、窗口扩容和**窗口换代**（新一代缓冲）在启动前向准入器**预留**内存，预留量按各自的估算（计算沿用现有的预算估算；回放窗口按 4.2 公式；导入按批次大小）。预留不到则排队等待，等待超时或永远预留不到时拒绝并给出明确原因。
- 实时周期的计算预留优先级最高，回放、导入、重算让路。
- `compute.max_memory` 保留，含义不变（单次计算上限）；新增 `memory.total_budget`（初始化时按探测结果写入），准入器按它判断。

### 4.5 本期支持范围

- 一个数据源（space + dataset + freq）对应一个启用的因子集合。现有 `factor.sql:16` 的唯一约束 `(space, dataset, freq)` 和 `engine/catalog.go` 的事件定位只返回一个集合，本期保持这个约束，不做「多个集合共用一份窗口」。同一数据集不同回看根数的需求，通过同一集合内的因子各自声明回看根数满足，窗口长度取最大值。
- 频率：本期支持因子时钟已支持的固定频率（1m、5m、15m、30m、1h、4h、1d），与系统规范一致；`3m`、周线、月线本期不做（它们需要先改日历推进，不在本期范围）。

> 如果以后要做多集合共用或周月线，需要把 schema、事件分发、补齐广播和日历推进列为独立任务。

## 5. 同步与导入

### 5.1 同步器 klinesync

**权威与同步位点**：

- Storage 是近期数据的权威，本地是它的持久化副本。本地不再靠「内存里的补齐通知」得知修正，而是靠 Storage 的**行变更序号**：同步器记录自己已处理到的序号（`m/sync/{src}`，随块一起原子提交）；每次心跳、启动时从该序号继续读变更；变更落到本地并提交后才推进序号，并向管理服务确认。
- `PeriodsFilled` 仍然保留，只作为「有变更了，赶紧读」的提示，丢了不影响正确性。
- 本地没有变更序号可用的老区间（例如导入的历史）不受 Storage 的保留期约束，见 5.2。

**前置工作（Storage 侧，阶段 3 之前必须完成）**：现有 Storage 没有可补读的行变更接口。`source_sequence`（`storagepb/storage_events.proto`）只在 `(source_node_id, source_store_id)` 内可比较，来自 outbox；事件发布确认后 relay 会删除 outbox 记录（`datanode/outbox/relay.go`）；事件流只保留 72 小时 / 8GiB，也没有按序号读取的 RPC。需要新增：

- 持久化变更日志：至少覆盖 K 线数据集，记录数据集、标的、时间区间、变更序号；保留期不少于本地允许的最长离线时间（默认 7 天）；
- 读取协议：游标的完整身份是 `(source_node_id, source_store_id, sequence)`；`ReadChanges(after_cursor, limit)` 分页读取；
- 断档检测：游标早于日志保留起点、或身份变化（Storage 节点更换）时，返回「断档」；
- 写入原子性：Storage 的行写入与变更日志记录在同一个 Pebble batch 里提交，不会出现「行已改、日志没有」；
- 断档处理（重建基线游标）：
  1. 先取日志当前已提交游标 `C0`；
  2. 对「本地覆盖区间 ∩ Storage 仍保留区间」做全量重拉对账（`ReplaceRange`，按标的分批）。范围不能只取当前因子的回看窗口：本地永久保留历史，补算和回放都会读到，更早区间在断档期间发生的修正同样要补上。Storage 每个分页 RPC 各自新建快照（`pebble/rows_read.go`），整个扫描并不来自同一快照，所以不能把扫描结束时的最新序号当基线；
  3. 全部对账完成后，再补读 `C0` 之后的变更并应用，才发布新基线游标；
  4. 对账期间，尚未对账的覆盖区间在 `m/cover` 里标 `stale`（待校验），不得用于计算（按第 5.3 节的「未同步」处理）。按「最近回看窗口优先、较早历史后台继续」分区放行：最近窗口扫描完成后，先补读该范围内 `C0` 到某个确定游标 `C1` 之间的变更并应用，再解除该范围的 `stale`，实时计算即可恢复；此后已放行范围继续按增量同步（从 `C1` 起读变更）维护，较早历史在后台继续对账。扫描期间的修正在放行前补齐，计算不会看到混合版本。所有区间脱离 `stale` 之前，不发布新基线游标。保留期之外的本地数据不动。

在这些完成之前，第 9 节「漏通知不影响正确性」不成立，阶段 3 以它为前置。

| 时机 | 动作 |
| --- | --- |
| 每个实时周期，计算前 | 对本期标的，从 `Latest` 拉到本期末，`MergeRows` 写盘（同一批提交），再追加到窗口。正常每个标的只拉 1 根。`Latest` 只决定从哪里开始拉；是否完整由覆盖区间决定 |
| 引擎启动 | 对启用集合的数据源，先对照覆盖区间检查「回看窗口需要的区间」是否都是 `present` 或 `checked_empty`，缺的部分补拉；再从 `Latest` 拉到当前，补停机缺口；然后读 `m/sync` 之后的变更；最后加载窗口 |
| 读到修正变更 | 对变更区间重拉并 `ReplaceRange`（只对 Storage 仍保留的区间），覆盖窗口；本地提交成功后才推进同步位点、才唤醒水位推进和补算（调整 `onFilled` 的顺序） |
| 本地没有某个标的（新上市、新数据集） | 从 Storage 拉「最大回看根数」的窗口，一次性完成，写入覆盖区间 |

同一数据源的同步、导入、修正重拉按数据源互斥提交，网络读取在锁外进行（第 4.1 节）。

### 5.2 CSV 导入

**文件准备**：CSV 放到因子机的指定目录（例如 `/data/moox/import/`），用户自己放，或由 Claude 用 scp 上传。导入命令只传路径，文件内容不再经过网络。

**格式**：

- 一个文件对应一个标的，文件名即标的 ID（也可以用 `--subject` 指定）；
- 列名与数据集注册的字段名一致，外加时间列 `data_time`；
- 时间按 UTC 解析：没有时区的时间视为 UTC，带时区的统一转换为 UTC；
- 可选 `series_tag` 列，或用 `--series-tag` 统一指定；
- **空单元格表示「不提供该字段」**，与现有 `moox-cli storage import` 一致（该行该字段保持原值）；CSV 里不出现的列同样是未提供。CSV 无法表达显式 NULL。

**命令**：

```
moox-cli factor kline import --space crypto --dataset <dataset> --freq 1m \
  --dir /data/moox/import/spot_1m/ [--storage=true] [--recalc]
```

**引擎处理**：

1. **解析与校验**。复用现有 `moox-cli storage import` 的字段校验逻辑（`cli/internal/command/storage_import.go`），抽成公共包 `packages/klinecsv`，改为**有界流式读取**（按批次回调），不再整文件累积 protobuf 行。标的必须已在数据集的标签范围内（与现有 storage import 一致，不在范围内就拒绝，不自动绑定），这个检查在本地发布前完成。
2. 按块 `MergeRows` 写本地，写入同时把区间记入 `m/cover`（`present`）。
3. `--storage=true`（默认）时，把同样的行后台分批写入 Storage（`UpsertFields`，字段更新语义，与本地合并语义一致）。本地写完即可开始计算；Storage 的写入进度单独显示。
4. **本地块、待上传批次、导入断点在同一个 Pebble batch 里原子提交**；上传内容固定，失败可原样重试，重跑幂等。
5. 带 `--recalc` 时，导入完成后按第 5.4 节的失效范围提交区间重算，得到历史因子值。

**Storage 保留期的边界**：Storage 的 View 只保留最近 1 万根，导入的一个月以前的历史不会长期留在 Storage 的 View 里。因此：

- 修正重拉（`ReplaceRange`）只允许用于 Storage 仍保留的区间；
- 重拉得到空结果、或区间落在保留期之外，一律不当作「删除」，本地数据保持不变；
- 待上传 Storage 但尚未完成的区间，修正重拉跳过它们（以本地待上传内容为准），避免旧值覆盖刚导入的数据。

### 5.3 就绪与可计算性

集合要计算第 t 期，对每个标的、每个因子，需要回看区间 `[t − (L−1)×周期, t]`。区间内的每个周期属于下列状态之一：

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| 有数据 | 本地有这根 K 线 | 正常计算 |
| 上市前 | 早于该标的的首根存在性证据（复用 `pipeline/gapcheck.go` 的头部缺失规则，不算空洞） | 按现有规则，不足回看根数的因子值为空 |
| 已查询为空 | 已向 Storage 查询过该区间，结果为空（覆盖区间 `checked_empty`） | 只说明查询过，避免重复拉取，**不**单独表示允许计算：是否合法取决于上一行「上市前」的存在性证据，上市后的缺期仍按真实空洞处理 |
| 真实空洞 | 晚于首根、Storage 也没有 | 进入跳过账本，之后补算（现有机制） |
| 未同步 | 本地还没有拉取过，或处于 `stale`（断档后待校验） | 见下 |

- **整个数据源首次载入时**（启动补缺、CSV 导入还没跑完）：集合状态为「本地数据未就绪」，不计算、不跳期，连续水位停住；载入完成后水位从停住的地方自动追赶（`engine/catchup.go`）。
- **运行中个别标的未同步**（新上市、新数据集中的新标的、同步失败）：按现有规则，读不到的标的算失败，进入跳过账本，不停住整个集合。这样「未就绪」和「同步失败」的边界是：前者只发生在数据源整体首次载入，后者是单个标的的运行期问题。
- **首根存在性证据**：`gapcheck` 现在用的 `storageio.EarliestPeriod` 只是 Storage 主存当前剩余数据的第一行，保留期清理会让它不断后移，回放较早的导入历史时，窗口头部漏掉的数据会被误判为「上市前」。因此本地持久化 `m/exist/{src}/{subject}` 作为存在性证据：取同步时 Storage 首根与本地最早一根中**更早**的一个，只前移、不后移，导入更早数据后更新。证据带版本号，前移时版本加一；`gapcheck` 现有的 `firstBarCache` 把已找到的首根永久缓存（依据是首根不会变），要改为按证据版本读取，证据前移后缓存失效，不能沿用旧首根。前移后，新旧首根之间原本被当作「上市前」的缺期变成真实空洞，需要按第 5.4 节重新检查并重算。这是工程上能证明的「该标的至少从这时起就有数据」，局限是：CSV 的起点晚于真实上市时间时，起点之前的区间会被当作上市前，需要更早数据时重新导入即可。
- **扩大回看、增加字段、增加标的**时，都会在覆盖区间里留下新的「未同步」段，触发相应补载，并重新做窗口内存的准入检查（第 4.4 节）。

### 5.4 数据修正后的失效范围

修改 `[from, to)` 内的 K 线，会影响其后所有仍然包含这些 K 线的回看窗口。因此：

- 对固定频率、回看 L 根的因子，失效范围是 `[from, to + (L−1)×周期)`，再截断到已经计算过的范围；
- 截面因子（依赖标的全集的）还要扩展到相关的全部标的；
- 触发来源有两类：CSV 导入带 `--recalc`；修正重拉覆盖了已经算出过因子值的区间。两者都**提交一个区间重算任务**（`recalc.Service.Submit`），不是只唤醒缺口恢复。现有缺口恢复只处理跳过账本里的待办，不会覆盖已经成功算过的旧结果。
- **首根证据前移**也是一种数据修正：失效范围是 `[新首根, 旧首根 + (L−1)×周期)`，因为这段范围内的因子值此前是按「上市前 / 短历史」算出的；同样生成失效待办。
- **待办与源数据原子提交**：失效区间作为待办 `m/recalc_pending/{src}`，与块、覆盖区间、同步游标放在同一个 Pebble batch 提交；后台用稳定的 `request_id`（由数据源、区间、游标生成）幂等提交重算任务，提交成功后清除待办。这样提交前后任何一步失败或重启，待办都在。CSV 的 `--recalc` 同样处理。
- 重算任务完成前，受影响区间的因子值是旧值；状态页显示「待重算区间」。

## 6. 逐期回放

### 6.1 目标与边界

- 按时间顺序逐期推进历史 K 线，每期走实时计算路径算出因子，交给策略求值，再由 Trade 在 **PAPER 账户**里撮合，得到接近实盘时序的模拟结果。
- **回放绝不产生实际下单**。
- 回放不进入生产事件总线，不影响连续水位、监控新鲜度和实盘策略实例。
- 隔离不能只靠「账户是 PAPER」：复用已有 PAPER 账户会共享资金、持仓、挂单和目标序列，Trade 的撮合扫描目前也没有回放隔离。所以每次回放使用**独立的回放会话**，见 6.3。

### 6.2 流程

```
moox-cli factor replay start --set <因子集合> --instance <策略实例> \
  --from 2026-01-01T00:00:00Z --to 2026-02-01T00:00:00Z [--write-factors]
```

1. 校验：
   - 策略实例绑定的逻辑账户必须全部是 PAPER 账户，否则拒绝并为本次回放创建专用 PAPER 账户（独立资金、持仓、挂单和策略会话，初始资金与配置快照在会话里固定，结束后保留结果、可清理）；
   - 区间内的 K 线在本地已就绪（先导入），并且**包含 `to` 之后的一根**（用于下一根开盘成交）；
   - 向内存准入器预留回放窗口和计算内存。
2. 引擎建立回放会话（`replay_id`）和独立的回放窗口：
   - 从 `klinestore` 加载预热区间的 K 线，起点 = `from − max(L_f − 1 + k, 年龄检查根数) × 周期`，其中 L_f 是因子最大回看根数，k 是策略引用因子列的上一根深度（如 `bars[-1]` 为 1）；
   - 在第一个正式周期之前，先计算并缓存策略需要的上一期因子值（研究回放是直接读已存好的列值，逐期回放没有这份数据，必须自己算）；
   - 会话固定当时的策略版本和因子定义版本，运行中修改配置不影响本次回放。
3. 回放驱动逐期推进，对周期 t：
   1. 窗口追加 t 这一根，计算因子；
   2. 调用策略的回放求值接口，传入完整的回放输入（见下）；接口复用现有求值引擎，**只返回本期决策**（产出目标权重，或「跳过」及原因），不直接发 Trade 事件；
   3. 回放驱动向 Trade 发**回放推进命令**（`ReplayAdvance`，每期必达），携带 `replay_id`、周期、回放时钟、本期回放报价，以及决策：`UPDATE_TARGET`（内含带 `replay_id` 的 `LogicalAccountTargetWeightRequested`）或 `SKIP`；
   4. Trade 在回放会话里按回放报价和回放时钟处理：`UPDATE_TARGET` 换算并下单；`SKIP` 不改动目标，只撮合遗留挂单。处理完成并落盘后**确认本期**（包括策略跳过、没有订单的周期）；
   5. 本期所有必要阶段（Trade 确认、策略状态落盘、启用 `--write-factors` 时的因子写入）都完成并记入周期记录后，才推进下一期，保证严格按时序。挂单留到后续周期继续撮合，**不等全部成交才推进**。
4. 带 `--write-factors` 时，同时把回放算出的因子结果写入结果数据集（与区间重算的写法相同，不发周期完成事件）。
5. 进度、当前周期、每期耗时记在 `m/replay/{replayID}`，支持暂停、继续、取消。

**策略回放输入契约**：回放求值接口的入参不是「只有本期因子值」，而是与现有求值一致的完整帧，构建逻辑复用 `strategy/internal/engine/frame.go` 和研究回放（`strategy/internal/replay/runner.go`）已有的处理：

- 本期因子帧，以及策略需要的上一根数据；
- `Universe` / `Expected` / `AgedOut`（标的全集、期望到齐集合、年龄检查剔除集合）、失败列、市场类型、周期序号；
- 前序规则状态（持有批次等），按 `replay_id` 独立持久化，不读写实盘实例的状态。

### 6.3 消息与接口改动

| 位置 | 改动 |
| --- | --- |
| `tradeeventpb.LogicalAccountTargetWeightRequested` | 新增 `replay_id`、`replay_time`（回放时钟，UTC）、`replay_quotes`（本期各标的的回放报价） |
| 策略 RPC | 新增回放求值接口：入参是 `replay_id`、实例、周期和上述完整回放输入，复用现有求值引擎，返回本期决策（目标权重或跳过），不直接发事件 |
| Trade 回放推进命令（新增 `ReplayAdvance`） | 每期必达：`replay_id`、周期、回放时钟、回放报价、决策（`UPDATE_TARGET` / `SKIP`）。区分「跳过」与「空目标」：Trade 把空的 FULL 目标解释为清仓（`weight_resolver.go`），所以跳过不能用空目标表示。同步返回本期确认 |
| Trade 入口（`eventconsumer/target.go`） | `replay_id` 不为空时，目标账户必须是回放会话内的 PAPER 账户，否则拒绝并告警（双重保险：策略侧已校验一次）；**`valid_until` 等时间校验用 `replay_time`，不用墙上时间**，否则历史目标会被判过期 |
| Trade 权重换算（`application/target/weight_resolver.go`） | 权益估值和参考价格取自回放会话与 `replay_quotes`，不查实时权益和实时报价 |
| Trade 资金预留与撮合（`execution/reservation_policy.go`、`execution/paper/pricing.go`、`matcher.go`） | 预留价、`PaperExecutionPrice`、撮合价格都用回放报价；**缺价时直接报错，不回退实时报价**；撮合扫描只处理当前回放会话自己的挂单 |
| Trade 订单、成交 | 记录 `replay_id`，便于查询与清理 |
| 因子集合事件、水位 | 不变。回放不走 `FactorPeriodComputed` 等生产事件，不需要所有消费者都去过滤回放标记 |

**执行上下文**：Trade 里定义一个会话级的回放执行上下文 `{replay_id, clock, quotes}`，目标校验、权重换算、估值、资金预留、撮合都只通过它拿时间和价格，实盘路径用实时实现，回放路径用回放实现。时间语义固定为：K 线起点是 `data_time`，决策时刻是该 K 线结束（`data_time + 周期`），成交时刻是下一根的开盘（决策时刻同一刻）。

回放报价默认取下一根 K 线的开盘价，模拟「本期收盘决策、下期开盘成交」；可选本期收盘价。区间最后一期需要 `to` 之后的一根开盘价，所以第 6.2 节要求本地包含这一根。

**周期幂等与恢复**：

- 每期以 `(replay_id, period)` 为幂等键。因子机在 Trade 已成交、本地尚未保存进度时重启是正常窗口，所以恢复时**先向 Trade 查询该期的完成状态**，不能只凭 `m/replay` 里记录的进度判断。Trade 的确认只代表 Trade 阶段完成：Trade 未完成就按周期记录里的命令原样重发；Trade 已完成也不能直接跳期，还要按下面周期记录的完成标记补齐策略状态和因子写入，所有必要阶段都完成后才持久化「本期完成」并推进。
- 「本期确认」表示本期的执行结果和账户状态已落盘，而不是消息已接收。
- **周期记录**：因子机按 `(replay_id, period)` 持久化 `m/replay/{replayID}/period/{t}`，包含本期决策、下一期策略状态、待发送的 `ReplayAdvance` 命令，启用 `--write-factors` 时还有**待写的因子结果行及稳定的批次标识**（恢复时原样补写，不重新计算：重算时本地 K 线可能已被同步修正或 CSV 覆盖，会和已执行决策所用的因子不一致，固定因子定义版本也固定不了输入数据），以及各阶段完成标记（策略状态已落盘、Trade 已确认、因子已写入）。回放窗口在会话开始时取快照，运行期间不随修正更新。同一期重复求值返回同一条记录，不重新求值。
- **提交顺序**：先持久化周期记录（决策 + 下一期策略状态 + 命令），再发 `ReplayAdvance`，再写因子，最后推进到下一期。恢复时按完成标记分别补齐缺的阶段（向 Trade 对账确认、补写策略状态、补写因子），全部完成后才推进。

### 6.4 与区间重算、策略研究回放的关系

| 需求 | 用法 |
| --- | --- |
| 只要历史因子值 | CSV 导入 + 区间重算（`--recalc`）。按分块共享窗口，比逐期回放快几个数量级 |
| 要按实盘时序验证策略与成交 | 逐期回放 |
| 快速比较策略版本 | 现有策略研究回放（`strategy/internal/replay`，读取 View，区间受 View 保留根数限制） |

### 6.5 速度估算

内存窗口下每期的读取成本接近零，耗时主要在计算和撮合往返。如果每期 0.1–1 秒，回放一个月的 1m（约 4.3 万期）需要 1–12 小时。实施时按真实因子集合实测，再决定是否在回放里批量预计算因子、只逐期执行策略和撮合。

## 7. max_memory 自适应

- 初始化探测到因子机总内存 M、估算出常驻内存（窗口 W + Pebble 块缓存 C）之后：
  - 进程总预算 `memory.total_budget = M × 60%`；
  - `compute.max_memory = max(1GiB, (total_budget − W − C) × 50% ÷ 并行计算数)`，并行计算数取计划启用的集合数与 CPU 核数中的较小值；
  - 都写入 `engine.yaml`，用户可以修改。
- 初始化界面同时展示 M、W、C、总预算和建议值。`W + C` 超过总预算的 2/3，或 `total_budget − W − C < 1GiB` 时给出警告。
- 单次计算的预留以 `compute.max_memory` 为上限；并发总量由第 4.4 节的准入器控制，不靠这个公式保证。

## 8. View 保留根数与 Storage 容量

### 8.1 改动

- `packages/storagepolicy/policy.go:32` 的 `DefaultViewBars` 从 5000 改为 10000；初始化表单已有这一项（`cli/internal/configinit/editform.go:48`）。
- 默认保留期要能装下 1 万根，否则配置校验报错（`storagepolicy.Coverage`）。**遍历全部默认频率和各空间的覆盖值逐个校验**：

  | 频率 | 现在 | 改为 |
  | --- | --- | --- |
  | 30s | 48h | 90h |
  | 1m | 7d | 8d |
  | 5m | 30d | 35d |
  | 15m | 90d | 105d |
  | 30m | 180d | 210d |
  | 1h | 365d | 420d |
  | 4h | 1095d | 1700d |

  `30s` 现在只能覆盖 5760 根，不改会让初始化校验失败。1d 及以上本来是 Forever，不动。有交易时段的市场只会给出警告，按需调整。同步更新 `moox.toml.example`，以及 `docs/计划/策略模块评审与设计.md` 4.5 节里「默认 5000 根」的描述。
- **单 View 文件容量阈值**：`MaxViewFileBytes` 默认 1GiB（`storage/internal/service/view/maintenance.go` 的容量重建判断）。按下面实测的每行大小，1 万根的 1m K 线 View 约 1.1GB，会超过阈值，触发「达到容量上限、重建只保留最新」的循环。需要同步调大该阈值（或按 View 调整），并实测重建后的大小。

## 9. 一致性与故障处理

| 情况 | 处理 |
| --- | --- |
| 本地目录损坏、布局版本不符 | 拒绝启动。人工删目录后重启，然后重新导入，或由同步器按回看窗口从 Storage 拉取 |
| 同步器拉取失败 | 本期按现有规则：读不到的标的算失败，进入跳过账本，之后补算 |
| 补齐通知丢失、引擎离线、管理服务重启 | 同步位点之后的变更在下次心跳或启动时读到（依赖第 5.1 节的 Storage 变更日志），本地提交后才推进位点；离线超过日志保留期则走断档重建 |
| 导入时本地已完成、Storage 未写完 | 计算照常进行；Storage 写入从断点续传，状态显示未完成；这段区间的修正重拉被跳过，不会用旧值覆盖 |
| 本地与 Storage 不一致 | 由变更同步重拉修正，失效重算待办与同步位点原子提交，再按第 5.4 节的范围幂等提交重算 |
| 变更日志断档（离线超过保留期、Storage 节点更换） | 取 `C0`，对「本地覆盖区间 ∩ Storage 保留区间」全量对账，对账完成并补读 `C0` 之后的变更后才发布新基线；对账期间未校验的区间标 `stale`，不参与计算 |
| 历史数据超出 Storage 保留期 | 重拉不触碰保留期之外的本地数据；空结果不当作删除 |
| 内存预留不到 | 任务排队，超时拒绝并给出原因；实时周期的计算优先 |
| 回放中引擎重启 | 回放会话暂停；继续时先对账 Trade 侧最后一期的完成状态，再按 `(replay_id, period)` 幂等推进 |
| 回放订单指向非 PAPER 账户或非本会话账户 | 策略和 Trade 两处都拒绝，并告警 |
