## 0. 已确认的决定

| # | 决定 |
| --- | --- |
| 1 | 因子机本地用 Pebble 持久化时序数据（不限于 K 线）；实时计算、水位追赶、补算、重算都从本地读，Storage 只用于补增量和修正 |
| 2 | 本地数据**永不删除**；不做每日全量核对；不抽公共 Pebble 包；不做应用层压缩，开启 Pebble 自带的块压缩 |
| 3 | 内存保留按列存储的**滑动窗口**；初始化时估算窗口内存给用户参考；`compute.max_memory` 按探测到的内存自适应 |
| 4 | 本地组件用通用命名 `series*`：`seriesstore`、`serieswindow`、`seriessync` |
| 5 | 本地写入**只有一种语义：整段替换**。导入的数据必须带数据集的全部字段 |
| 6 | 本地数据**写入时保证连续、没有空洞**，每个标的的本地数据就是 `[Earliest, Latest]` 连续的一段，相信 `Latest`。标的首根就是本地最早一根 |
| 7 | 交易所本身缺的周期写成**缺失行**，按字段的填充规则（`prev` / `prev_close` / `zero`）填充并带「已填充」标记；不设长缺口上限；填充只发生在本地，不写回 Storage |
| 8 | 数据导入独立成 **`modules/importer`**（独立二进制，编排在 `packages/seriesimport`），并入 `moox-cli import`，替换现有 `moox-cli storage import`；格式解析独立成 **`packages/seriesformat`**，CSV 是第一种格式 |
| 9 | 逐期回放独立成 **`modules/replay`**（独立二进制，编排在 `packages/seriesreplay`，与 `moox-cli replay` 共用）；回放不产生实际下单，只走纸上交易；每次回放在 Trade 里建立**独立的纸面账本会话**（见 9.2），规则状态按 `replay_id` 独立保存 |
| 10 | 回放默认按下一根 K 线开盘价成交（可选本期收盘价）；回放不走生产事件总线 |
| 11 | Storage 是近期数据的权威，本地靠 Storage 行变更序号持久化同步；导入的历史不受 Storage 保留期约束 |
| 12 | 变更日志断档（离线太久、Storage 节点更换）不自动处理：自检判为未就绪，由用户执行对账命令 |
| 13 | **系统生命周期**：模块和对象（因子集合、策略实例）两级都有状态；所有模块就绪后由用户启动，先预热（真实数据、不真实下单），用户确认后才进入运行；首页按颜色展示 |
| 14 | 重启后通过该模块的启动前检查就直接回到原阶段；运行中出故障**只停受影响的部分**；策略实例暂停 = 不发新目标、持仓不动 |
| 15 | 本期一个数据源（space + dataset + freq）对应一个因子集合；频率限 1m–1d 固定频率，不做 3m、周线、月线 |
| 16 | 5 万根主要用于 1m；View 默认保留根数从 5000 改为 **1 万**，初始化时可设置 |
| 17 | 所有时间统一用 UTC：块边界、文件时间列、命令参数、日志、回放时钟 |
| 18 | 标的被移出集合后，实时计算、变更同步、窗口都不再处理它；标的列表变化自动重新准备窗口，不需要重启引擎。本地数据按「永不删除」保留，不提供清理命令（2026-10-22） |
| 19 | 长缺口只提示不阻断：连续填充超过 24 小时（日线为 3 期）的标的列在状态页（2026-10-22） |
| 20 | 导入与实时共用数据源锁，不做实时优先队列，只加锁等待指标；读租约不加超时，只加持有时长指标（2026-10-22） |
| 21 | 初始化设置回看数量 N 时，按「序列数 × N」估算窗口内存并与 `window.max_memory` 比较，超过则警告并要求调整；启用集合时仍按实际规模拒绝（2026-10-22，取代先前「不做」的结论，因为 N 现在由用户设置） |
| 22 | 变更跟进（`Follow`）改造：用链头位置 H0 跳过已被拉取反映的变更、必须重拉时按批请求；**仍然持有数据源锁**，让同一数据源的拉取、跟进、导入从取数到提交串行，靠请求数大幅减少来缩短持锁时间（2026-10-22，依据 15.2 的线上实测；最初设想的「锁外取数」经复核会漏掉修正，已去掉） |
| 23 | **回看数量 N**：初始化时由用户设置，全局默认 1 万，数据源可覆盖；窗口长度固定为 N；表达式的回看上限（`MaxLookback` 限制整个表达式的回看，`MaxWindow` 限制单个函数的窗口参数，现在都是固定的 5000）改为随数据源的 N，条件是 `Lookback ≤ N`（`Lookback` 已经是包含当期的所需行数），包内另留一个 10 万的绝对上限（2026-10-22） |
| 24 | **启动加载**：引擎启动时把每个标的 N 根 K 线从本地加载进内存；本地没有则从主存取，取到后先更新内存、再异步落盘；本地和主存都没有任何数据的标的**严格失败**；新上市（主存有它的全部数据但不足 N 根）通过；"失败"的含义是该数据源进入「未就绪」、拒绝 `init` 和 `start` 并报错提示导入或移除，**进程不退出**（2026-10-22） |
| 25 | **实时尾部并行落盘**：窗口追加后立即触发计算，同时写盘，下一期开始前确认上一期已落盘，不做长队列；导入历史、修正覆盖、缺失行填充和失效重算待办仍同步写（2026-10-22） |
| 26 | **（已撤销）订阅行事件直接应用**：因子引擎不订阅 `DatasetRowsUpserted` 来改本地数据，本地数据只由拉取和变更跟进更新。撤销原因：事件迟到或重复会用旧值覆盖新值，事件只带本次修改的行、整段替换会损坏同一周期的其他 `series_tag`，要安全应用就得引入每行版本等一整套机制，而它能省的只是每期约 6 个读取请求。「采集完成后只拉缺的标的」本来就是现状（`Pull` 按每个标的本地最新位置决定从哪里拉）（2026-10-22） |
| 27 | **Storage 字段改名（独立推进）**：事件 `DatasetRowsUpserted` 的 `source_node_id`、`source_store_id`、`source_sequence` 和变更日志游标 `DatasetChangeCursor` 的 `source_node_id`、`source_store_id` 改为 `node_id`、`store_id`、`sequence`，与 `CommittedPosition` 一致。纯改名，不改语义，不依赖其他改动，项目未上线不考虑兼容。原先设想的「序号统一、`prev_sequence` 链、store 身份轮换」随决定 26 一并撤销（2026-10-22） |

## 1. 背景

- 预期规模：每个标的回看最多约 5 万根 1m K 线，1000 多个标的，单次计算约 5000 万行。
- 现状：因子引擎每期从 Storage 经网络读取，只在进程内存里缓存实时窗口（`pipeline/window_cache.go`）。
  - 缓存用 `[][]any` 按行存储，每格约 48 字节（`pipeline/memory.go:16-18`），这个规模下放不下；
  - 重启要整窗口重新预热；
  - 补算、重算（`ModeRecalc`）每次从 Storage 读整窗口（`pipeline/load.go:48-56`）。
- 现有的修正通知 `PeriodsFilled` 只在内存里暂存（`rpc/filled_inbox.go`，10 分钟过期、最多 1000 条、取出即清空），丢了靠追赶循环重新从 Storage 读回。改成全部读本地后这层兜底消失，需要 Storage 提供可补读的变更日志（第 5.1 节）。

## 2. 总体结构

```
  数据文件（因子机磁盘）
        │
   modules/importer ── packages/seriesformat（csv …）
   （编排 packages/seriesimport）
        │ 写入目标            │
        ▼                    ▼
  因子引擎本地写入接口      Storage（权威）
        │                    │ 变更日志 / 区间读取
 ┌──────┼──────── 因子引擎进程 ┼──────────────────────────┐
 │      ▼                    ▼                           │
 │  seriesstore（Pebble，永久） ◄── seriessync            │
 │      │ 启动加载 / 每期追加                              │
 │      ▼                                                 │
 │  serieswindow（内存列式窗口，读租约）  ◄── 内存准入      │
 │      │                                                 │
 │  pipeline（实时 / 追赶 / 补算 / 重算）   回放计算接口     │
 └──────┼─────────────────────────────────────┼──────────┘
        ▼                                     ▲ 按期计算
  Storage 结果写回                      modules/replay（编排 packages/seriesreplay）
                                       │ 策略回放求值 → Trade（纸面账本会话）
```

| 位置 | 组件 | 职责 |
| --- | --- | --- |
| `modules/factor/internal/` | `seriesstore` | 本地磁盘存储，Pebble 只出现在这里 |
| | `serieswindow` | 内存列式窗口，提供读租约 |
| | `seriessync` | 从 Storage 增量同步、修正重拉、对账 |
| | 内存准入器 | 计算、回放窗口向它申请内存预留 |
| `modules/importer` + `packages/seriesimport` | 导入服务 | 读文件、解析校验、写到一个或多个写入目标，断点续传 |
| `modules/replay` + `packages/seriesreplay` | 回放编排 | 回放会话、周期记录、调用因子 / 策略 / Trade |
| `packages/seriesformat` | 格式解析 | 统一 `Decoder` 接口与各格式实现，以及与格式无关的校验 |
| `packages/lifecycle` | 生命周期 | 模块与对象的状态、启动前检查、命令（第 6 节） |

Pebble 同一目录只允许一个进程打开，所以本地存储只能由因子引擎进程持有：导入服务通过因子引擎的本地写入接口写入，回放服务通过因子引擎的回放计算接口取因子。本地存储不能独立成服务，否则又回到每期经网络读取整窗口。

## 3. 本地存储 seriesstore

### 3.1 接口

```go
type Store interface {
    // ReadRange 返回 [start, end) 内各标的的列式数据，按 data_time 排序。
    // 一次调用在同一个 Pebble 快照上读，各标的版本一致。
    ReadRange(ctx context.Context, src Source, subjects []string, start, end time.Time) (map[string]*Columns, error)
    // WriteRange 用 rows 完整替换标的在 [from, to) 内的数据。rows 必须带数据集全部字段，
    // 写入前做连续性检查（第 3.3 节），缺的周期按填充规则写成缺失行（第 3.4 节）。
    WriteRange(ctx context.Context, src Source, subject string, from, to time.Time, rows *Columns, opts WriteOptions) error
    // Latest / Earliest 返回标的本地最新、最早一根的时间；本地数据在两者之间连续。
    Latest(src Source, subject string) (time.Time, bool, error)
    Earliest(src Source, subject string) (time.Time, bool, error)
}

type Source struct{ SpaceID, DatasetID, Freq string }
// Columns: Times []int64（UTC 秒）、SeriesTags、按字段名的列（带类型描述和空值位图）、每行的「已填充」标记。
// WriteOptions: SyncCursor（同步位点，随写入原子提交）、RecalcPending（要随写入记录的失效区间）、AllowMissing（导入时允许中间缺期）。
```

- **原子边界**：一次 `WriteRange`（或同步器把本期所有标的合成的一批）在一个 Pebble batch 里同时提交块、`m/latest`、`m/earliest`、同步位点和失效重算待办。崩溃后不会出现「块已写、位点没动」或「数据改了、重算待办丢了」。
- 不提供删除接口：本地永不删除。

### 3.2 数据布局

- **key**：`k/{space}/{dataset}/{freq}/{subject}/{blockStart 大端 int64 UTC 秒}`。各段是系统内标识符，写入前做字符校验，不需要转义编码。
- **块跨度**按频率固定，每块几十到几百行：

  | 频率 | 块跨度（UTC 对齐） | 每块行数 |
  | --- | --- | --- |
  | 1m | 1 小时 | 60 |
  | 5m | 6 小时 | 72 |
  | 15m / 30m | 1 天 | 48–96 |
  | 1h | 1 周 | 168 |
  | 4h | 1 个月 | ~180 |
  | 1d | 1 年 | ≤ 366 |

- **块内按列编码**：
  - 头部：行数、schema 版本、列名与类型表（数据集全部字段）；
  - 时间列：int64 UTC 秒；行身份是 `(data_time, series_tag)`，同一时间可以有多个 series_tag；
  - `series_tag`：块内字典；
  - 「已填充」位图：每行一位；
  - 数值列：float64 / int64 + 空值位图；其他类型（字符串、BOOL、TIME、JSON）：长度前缀字节；
  - 不做应用层压缩，Pebble 用默认块压缩。
- **存数据集全部字段**。数据集加字段后，新块带新 schema 版本，旧块里该字段读出为空；要补齐旧数据就重新导入或由同步器重拉对应区间。
- **元数据 key**：
  - `m/layout`：布局版本，不一致时自检失败；
  - `m/latest/…`、`m/earliest/…`：每个标的本地最新、最早时间；
  - `m/sync/{src}`：同步位点（Storage 变更游标，第 5.1 节）；
  - `m/recalc_pending/{src}`：待提交的失效重算区间（第 5.3 节）。

### 3.3 连续性约束

本地每个标的的数据始终是 `[Earliest, Latest]` 上按频率网格**连续**的一段（有交易时段的市场按 `packages/marketcalendar` 的交易日历取网格），所以：

- 「本地同步到哪里了」只看 `Latest`；
- 标的的首根就是本地 `Earliest`，早于它的周期视为上市前（`pipeline/gapcheck.go` 的头部缺失规则改为读本地 `Earliest`；导入更早的数据让 `Earliest` 前移时，清掉首根缓存即可）。

`WriteRange` 的检查：

1. 写入的这段本身在网格上连续；中间缺期时，来自同步器的写入按第 3.4 节写成缺失行，来自导入的写入只有带 `AllowMissing` 才写成缺失行，否则拒绝并列出缺的周期；
2. 写入区间必须与本地已有数据相接或重叠：接在 `Latest` 之后、接在 `Earliest` 之前（导入更早的历史），或者覆盖已有区间（修正）；与本地数据之间留出空档就拒绝。本地还没有该标的时，第一次写入不受这一条限制。

### 3.4 缺失行与填充

交易所宕机、维护等时段本身就没有数据，Storage 里也没有。为了保持连续，这些周期写成**缺失行**：

- **何时写**：只有当某个周期**之后**已经有真实数据时，才把它判定为缺失并写成缺失行。本期数据还没到（采集延迟）不写，`Latest` 不前进，这个标的本期按现有规则算失败、进跳过账本；下一期数据到了而这一期仍没有，才写成缺失行。所以策略决策时用到的本期数据一定是真实的。
- **怎么填**：按数据集字段定义上的填充规则（新增字段属性 `fill`）：

  | 规则 | 含义 | 典型字段 |
  | --- | --- | --- |
  | `prev`（默认） | 取上一期该字段的值 | 资金费率、持仓量等状态类字段 |
  | `prev_close` | 取上一期的 close | open / high / low / close |
  | `zero` | 填 0 | volume、成交额、成交笔数 |

  不设长缺口上限，缺多少期就填多少期。但长缺口不能无人察觉：几天的缺口会填出一段零成交量、零波动的数据并参与计算。所以要提示「长时间没有数据的标的」（日线数据集按 3 期，否则每次缺一天都会触发），只提示不阻断：交易所停机产生的填充是合法的，阻断会让该标的整个停摆。阈值按墙钟时间而不是根数，因为按块跨度行数在低频上几乎不会触发（1h 是 168 期，1d 是 366 期）。因子要排除这类数据时用 `is_filled`。因为缺失行只在之后有真实数据时才写，仍在持续的缺口不会表现为窗口结尾的填充行，所以提示分两类：窗口里已经填充的缺口（连续填充超过阈值，填充值仍参与计算，直到滚出窗口），以及最新一根距今超过阈值的标的（到现在还没有新数据）。已实现为集合检查里的「长缺口」警告项（`localdata.LongGaps`，不阻断计算）。
- **标记**：每行带「已填充」标记，表达式执行器里暴露成一列 `is_filled`，因子需要排除填充值时可以用它；默认把填充值当正常值参与计算。
- **只在本地**：填充行不写回 Storage，Storage 保持原始数据。之后采集器补齐了真实数据，Storage 产生变更，同步器整段替换，填充行被真实值覆盖，并生成失效重算待办（第 5.3 节）。
- **填充随前值联动**：填充值依赖前一期的值，所以任何 `WriteRange` 写完后，如果紧跟其后是一段连续的填充行，要按新的前值重新生成这段填充行。例如 t1、t2 原本都按 t0 填充，补回 t1 的真实值后，t2 要改按 t1 填充。实际改变的区间延伸到这段填充行的末尾，窗口覆盖和失效重算都按延伸后的区间处理。

### 3.5 读写实测（2026-10-21）

环境：云端 4 核容器，Pebble v1.1.5，1000 标的 × 5 万根 1m，7 个数值字段。测试代码在会话临时目录，可按需放进仓库的 `tools/`。

| 项 | 块方案（采用） | 对照：每根一个 KV |
| --- | --- | --- |
| 全量导入 5000 万行 | 34s，约 145 万行/秒 | 64s，约 78 万行/秒 |
| 每期追加 1000 根（一批，同步落盘） | 平均 33ms，最慢 104ms | 平均 15ms |
| 读 1000 × 1 万根 | 1.4–2.9s | 2.0–3.2s |
| 读 1000 × 5 万根 | 5.6–6.0s | 7.9–8.1s |
| 磁盘 | 2.8GB | 2.8GB |

结论：

- 追加的读改写每期只要几十毫秒，不是瓶颈。实时写入量是每分钟约 2000 根，离上限差三四个数量级。现有的 WS 采集写主存也是「每个数据集每期一次批量提交」（`collector/internal/stream/commit.go`），是同一种模式。
- **瓶颈是每期整窗口重读**（5 万根约 6 秒），所以引入第 4 节的内存滑动窗口。磁盘存储只在启动、回放开始、修正重拉和超出窗口的补算时读取。

### 3.6 容量

- 本地磁盘：实测约 56 字节/行。crypto 1m 现货加合约（约 2000 个序列）存 5 万根约 5.6GB。因子机剩余 1.7T，不需要清理。
- Pebble 块缓存 512MB，可配置，计入进程内存预算（第 4.4 节）。

## 4. 内存滑动窗口 serieswindow

### 4.1 结构

- **单位**：每个数据源一份窗口；本期一个数据源只对应一个启用的因子集合（现有 `factor.sql:16` 的唯一约束 `(space, dataset, freq)`）。
- **长度**：数据源的回看数量 N（决定 23，默认 1 万）。窗口长度固定为 N，不随集合里的因子变化，新增因子不用重载窗口；所有因子的回看（`Lookback`，已包含当期）都不得超过 N。已实现：`localdata.Config.Lookback` 取数据源的 N，没有配置时才取集合内因子的最大回看。
- **序列与时间网格**：按 `(subject, series_tag)` 分序列；时间轴按频率对齐成固定网格。本地数据连续，所以窗口内没有缺行，只有「值为 NULL」和「已填充」两种标记。这正是表达式执行器面板输入（`packages/factorexpr/exec/panel.go`）要求的布局。
- **存储**：每个序列每个数值字段一个定长数组（float64 或 int64 统一按 8 字节），另有已填充标记（每行 1 字节）。**不存时间数组**：本地数据连续，行的时间由窗口末尾时间和步长推出。容量 = 窗口长度 + 余量 H（默认取窗口长度的 1/4，至少 16 根；配置项 `window.headroom`，单位是根数），环形写入；窗口提供支持环形偏移的**访问层**，表达式执行器通过它读取，不每期重新铺平整个窗口。
- **读租约**：
  - 计算前 `Acquire(endPeriod)`，返回的视图只包含 `endPeriod` 及之前的 L 根，持有期间这一范围内的数据不变；
  - 租约只是加锁时抓取各序列的数组切片头，之后无锁读取，不会阻塞追加和换代；
  - 追加只写余量，不影响已有租约；余量用尽或修正覆盖已有区间时，该序列复制成新一代数组再切换，旧一代留给仍持有租约的读者，之后由 GC 回收；
  - 换代按序列进行，不设代数上限，也不向准入器预留（当前实现如此）。一次租约会同时引用所有被请求序列的数组，这些序列在租约期间陆续换代时，旧副本都要留到租约释放，最坏接近多出一份整窗口。因此**租约只能覆盖单次计算，不得跨期持有**，并且进程内存预算要给这部分留余量（总预算只取总内存的 60%，其余部分就是余量）；旧副本不计入准入的常驻量。**不给租约加超时**：旧副本是被读者持有的引用留住的，让租约「过期」并不能释放内存；防护靠上述约定，外加一个指标——最老租约的持有时长，超过一个计算周期就告警（已实现）。
- **提交与锁**：同一数据源的实时同步（含从 Storage 拉取）、本地窗口读取和导入写入共用一把数据源互斥锁，彼此串行；导入写入在持锁期间整批写盘并重新载入受影响标的的窗口。当前**没有实时优先的提交队列**，大批量导入会让同数据源的实时同步等待，所以导入要分批（`--batch-rows`，每批持锁时间受它限制），并尽量避开整点计算时段。**本期不做实时优先队列**：正常流程是「先导入、再就绪」，导入与实时重叠只出现在运行中带 `--recalc` 补历史的时候。改为加一个指标——实时同步等数据源锁的耗时，超过 1 秒告警（已实现）；真的观察到影响再做实时优先。
  - **持锁但要短**（决定 22）：拉取、变更跟进、导入写入从取数到提交整段串行，由数据源锁保证。不能把取数挪到锁外再提交：拉取读到值 A 还没提交时 Storage 把它改成 B，跟进会把「本地尾部之后」的变更留给拉取，拉取随后提交 A、位点却越过 B，B 就永久丢了。15.2 里的几十秒等待是因为跟进持锁期间发了上千次顺序请求，不是持锁本身；按 5.2 的规则把跟进的请求数降到个位数后，持锁时间在秒以内。上线后用等锁耗时指标验证。
- **生命周期**：引擎启动时从 `seriesstore` 加载（5 万根约 6 秒）；每个实时周期先把新数据追加进窗口并触发计算，写盘与计算并行（决定 25）；修正重拉后覆盖对应区间。回放使用独立的回放窗口（第 9 节）。

### 4.2 内存估算

公式（与 `serieswindow.BytesPerSeries` 一致）：**序列数 × (窗口根数 + 余量 H) × (数值字段数 × 8 + 1) 字节**。窗口根数就是回看数量 N，下表按 1 万 / 5 万两档给出量级；余量 H 默认取窗口长度的 1/4，所以实际占用约为「窗口根数 × 每行字节数」的 1.25 倍，下表已计入；读租约期间换代的旧副本不在内（见 4.1）。crypto K 线 7 个数值字段，每行 57 字节：

| 序列数 | 1 万根 | 5 万根 |
| --- | --- | --- |
| 1000（如现货 1m） | ~0.7GB | ~3.6GB |
| 2000（现货 + 合约 1m） | ~1.4GB | ~7.1GB |
| 再加 1h 两个数据集（序列数同上） | +~1.4GB | +~7.1GB |

- **初始化时**：探测因子机内存（已有，`cli/internal/configinit/probe.go:142`）；设置回看数量 N 时（第 8.1 节），按「计划启用的数据集 × 预计标的数 × N」给出窗口内存估算，和建议的内存配置一起展示，超过 `window.max_memory` 时警告并要求调整（决定 21）。已实现：`moox-factor-engine tune --series <序列总数> [--fields <数值字段数>]` 按 `window.lookback` 估算并与建议的窗口上限比较，超过则警告（第 8.1 节）；启用集合时引擎仍按实际规模和 `window.max_memory` 比较，放不下就拒绝并给出原因。
- **运行时**：状态页显示每个数据源窗口的实际占用；新启用的集合会让窗口内存超过 `window.max_memory` 时拒绝启用，并给出明确原因。

### 4.3 对计算侧的影响

窗口是列式的，pipeline 的读取和表达式执行器的输入改成列式，跳过 `storageio.Frame`（`[][]any`）。这是本期必做：每期把 5000 万格转成 `[][]any`，本身就要十几 GB 内存和数秒 CPU。

- **数值字段**：通过窗口访问层直接构建面板；INT 转 float64、BOOL 按 0/1 的类型转换固定在窗口层。
- **携带列（非数值）**：只取目标周期的那几行，仍按行处理。
- **内存预算**（`pipeline/memory.go`）：去掉「读取帧」一项，窗口常驻内存按第 4.4 节统一计入；补算、重算、回放预热从磁盘读区间时的列式读取缓冲保留。

### 4.4 进程级内存准入

`compute.max_memory` 只限制**单次**计算，而不同集合的计算可以并行（`trigger/lanes.go` 每个集合一条车道）。所以引入进程级预算：

- `memory.total_budget = 总内存 × 60%`，常驻部分（实时窗口 + Pebble 块缓存）先扣除；
- 计算、回放窗口在开始前向准入器**预留**内存，预留不到就排队，超时拒绝并给出原因（实时窗口的换代副本不预留，见 4.1）；
- 实时周期的计算优先级最高，回放、重算让路。

## 5. 同步 seriessync

### 5.1 Storage 变更日志

本地靠 Storage 的行变更得知修正。Storage 已经实现了持久化变更日志和读取接口 `ReadDatasetChanges`（`datanode/pebble/changelog.go`），本期**不需要改动它的行为**，只做决定 27 的字段改名：

- **变更日志**：时间序列行写入时，在同一个 Pebble batch 里为每个数据集分组追加一条记录（数据集、标的、频率、时间范围、变更序号）；保留期默认 7 天。
- **读取接口**：游标是 `(node_id, store_id, sequence)`（改名后），分页读取。返回的下一个游标是**扫描位点**（扫到了整个 store 的哪一条），不是该数据集最后一条变更的序号；基线游标（`from_head`）同样是整个 store 的头部位置。引擎的 `m/sync/{src}` 存的就是这个位点，含义是「序号不超过它的变更都已处理」。
- **断档检测**：游标早于日志保留起点、或游标身份对不上（Storage 节点或 store 更换）时返回「断档」，走对账命令。
- **变更日志序号与事件序号**：变更日志用自己的计数器，事件（`DatasetRowsUpserted`）的序号来自 outbox 计数器，两者独立。因为引擎不用事件改本地数据（决定 26 已撤销），不需要把它们合并。
- **单游标的前提**：Storage 把一个数据集解析到唯一的 DataNode（`primarystore.rangeNode` 按 `(space, dataset)` 路由），变更日志也在这个节点上，所以每个数据源只需要一个位点。数据集迁移到别的节点、或将来拆成多个 store，身份就对不上，按断档处理；真要支持跨 store 分片，位点要改成游标集合。

**字段改名**（决定 27，已实现，提交 `489d03b5`，字段编号不变，二进制兼容）：涉及 `storage_events.proto`、`data_node.proto`、`outbox_message.go`、`view/data_ready.go`、`events/validation.go`、`changelog.go`、因子引擎的 `storageio/changes.go` 及对应测试。纯改名，一次提交完成，不改任何语义。

`PeriodsFilled` 通知保留，只作为「有变更了，尽快读」的提示，丢了不影响正确性。

### 5.2 同步动作

| 时机 | 动作 |
| --- | --- |
| 每个实时周期，收到采集完成事件后、计算前 | 对本期标的，从各自本地的 `Latest` 拉到本期末（`Pull` 按每个标的本地最新位置分组，已经有本期这根的标的不会再拉；采集完成事件里的 `failed_subjects` 是本期采集失败的标的，显式排除、不去拉），`WriteRange` 写盘（本期所有标的一批提交，与计算并行，决定 25），再追加到窗口。正常每个标的只拉 1 根；缺期按第 3.4 节处理 |
| 引擎启动（决定 24） | 先把每个标的 N 根从本地存储加载进窗口；本地没有或不足 N 根的，从 Storage 取，取到后先更新内存、再异步落盘（它是主存的副本，丢了可重取）；从 `Latest` 拉到当前补停机缺口，读 `m/sync` 之后的变更。本地和主存都没有任何数据的标的，该数据源进入「未就绪」，进程不退出（第 6.2 节） |
| 每次心跳（默认每 30 秒）、收到 `PeriodsFilled` | 读 `m/sync` 之后的变更，对变更区间按下面「变更跟进的规则」判断是否需要重拉，需要的重拉并 `WriteRange` 覆盖本地和窗口，失效重算待办与同步位点同批提交；之后才唤醒水位推进和补算（调整 `onFilled` 的顺序） |
| 本地没有某个标的（新上市、新数据集） | 从 Storage 拉 N 根（回看数量，8.1）的数据，一次性写入 |
| 读到「断档」 | 不自动处理：引擎自检判该数据源未就绪（第 6 节），受影响的集合暂停，提示用户执行对账命令 |

- **变更跟进的规则**（决定 22，已实现，待线上验证）：Storage 的变更日志记录每一次时间序列行写入，包括采集器每期写入的新 K 线，而这些新 K 线通常已经被「每个实时周期的拉取」写进本地。如果跟进对每条变更都比对性重拉，就是白做（15.2 的长尾就是这样来的）。规则如下：
  1. **跳过已经反映的变更。** 每次拉取前先取该数据集的链头位置 H0（`ReadDatasetChanges` 的 `from_head`，现有接口）：拉取到的行至少反映了序号 ≤ H0 的全部变更。拉取时记住（标的，周期，H0），保留最近一段时间。跟进读到的变更若序号 ≤ H0 且区间落在拉取覆盖的范围内，视为已反映，不重拉；序号 > H0 的变更可能是拉取之后才发生的修正（例如同一周期先拉到 A、随后被改成 B），必须重拉比对。**不能只凭「近期拉过这个标的和周期」跳过**，否则会漏掉后续修正。
  2. **必须重拉时按批请求。** 同一标的集合的多个区间合并，按每批最多 100 个标的（`sync.batch_subjects`）发请求，并发度沿用 `sync.workers`；各标的的「Storage 最早时间」在一次跟进内缓存，不再逐个标的先查最早时间再读窗口。目标是把一次跟进的请求数从与标的数成正比降到个位数。
  3. **仍然持有数据源锁**（见 4.1）：拉取、跟进、导入从取数到提交整段串行。靠规则 1、2 把持锁时间降到秒以内，不引入锁外取数和提交前复核。
  4. 判断依据是 15.2 的线上实测。实施前先在跟进里加耗时日志确认根因，实施后用同样口径复测。
- **Storage 保留期**：同步器只用 Storage 保留期内的数据替换本地；保留期之外的本地数据不动，Storage 返回空结果也不当作删除。
- 导入服务写 Storage 产生的变更，同步器读到后会重拉同一区间，得到的是同样的数据，不需要特殊处理。
- 同一数据源的同步写入和导入写入按数据源互斥提交。

**对账命令**（`moox-cli factor series reconcile --source <space/dataset/freq>`）：

1. 取 Storage 变更日志当前游标 `C0`；
2. 对「本地数据范围 ∩ Storage 保留期」逐标的重拉并 `WriteRange`；
3. 补读 `C0` 之后的变更并应用，然后把 `C0` 之后的最新游标写入 `m/sync`。

Storage 每个分页 RPC 各自新建快照（`pebble/rows_read.go`），全量扫描不来自同一快照，所以基线游标要先取、扫描后再补读，不能取扫描结束时的序号。对账完成后自检通过，受影响的集合自动恢复。

### 5.3 数据修正后的重算

修改 `[from, to)` 内的数据，会影响其后所有仍然包含这些数据的回看窗口：

- 失效范围是 `[from, to + (L−1)×周期)`，截断到已经计算过的范围；截面因子（依赖标的全集的）扩展到相关全部标的；
- 触发来源：同步器的修正覆盖了已经算过的区间（包括填充行被真实数据替换）、导入带 `--recalc`、导入更早的历史让 `Earliest` 前移（此前按「上市前」算的区间，失效范围从新的 `Earliest` 起算）；
- 失效区间作为待办 `m/recalc_pending/{src}`，与数据同批提交；后台用稳定的 `request_id` 幂等提交区间重算任务（`recalc.Service.Submit`），提交成功后清除待办；
- 重算完成前，受影响区间的因子值是旧值，状态页显示「待重算区间」。

## 6. 系统生命周期与状态

### 6.1 状态

模块和对象（因子集合、策略实例）都有状态，含义一致：

| 状态 | 颜色 | 含义 |
| --- | --- | --- |
| 未初始化 | 灰 | 刚部署，配置或初始化未完成 |
| 未就绪 | 红 | 启动前检查有失败项，列出原因和处理命令（如「本地数据不足，请导入 xxx」「变更日志断档，请执行对账」） |
| 就绪 | 蓝 | 检查全部通过，等待用户启动 |
| 预热 | 黄 | 用真实数据跑完整链路，不真实下单 |
| 运行 | 绿 | 用户确认预热结果后进入 |
| 暂停 | 橙 | 受上游故障影响自动暂停，或用户手动暂停 |
| 故障 | 红 | 运行中出现自身无法恢复的错误 |

**系统状态**分两个维度，首页同时展示：

- **健康面**：由各模块状态推导，任何一个模块未就绪或故障，系统标红，并列出模块和原因；
- **运行阶段**：就绪 → 预热 → 运行，只由用户命令推进，不会自动跳。

首页的展示形如「运行中 · 降级（因子引擎：crypto/spot_1m 变更日志断档）」。模块状态里汇总它管理的对象状态；新增一个因子集合或策略实例时，只有它自己走一遍「就绪 → 预热 → 确认运行」，不影响已经在运行的部分。

### 6.2 模块要提供的能力

每个模块都提供下面这些接口和对应的命令行（实现为挂在各模块**健康端口**上的 HTTP 接口 `/v1/lifecycle/status|command`，签名鉴权，命令行是 `moox-cli lifecycle ...`，见第 15 节）：

| 能力 | 说明 |
| --- | --- |
| `check` | 启动前检查（PASS / WARN / FAIL，失败项带处理办法；实现为 `packages/lifecycle` 的 `Check`，没有复用 `packages/doctor`） |
| `init` | 执行该模块的初始化动作 |
| `status` | 返回模块状态、各对象状态和未就绪原因 |
| `start` / `confirm` / `pause` / `resume` | 推进或改变阶段；可作用于整个模块或单个对象 |

- 每个模块在自己的存储里**持久化**自己和对象的当前阶段（因子引擎 `data/engine/lifecycle.json`、策略与 Trade 在数据库旁的 `lifecycle.json`）；`packages/healthz` 的 `State` 保持就绪布尔值不变，生命周期快照放在 `/healthz` 响应的 `details.lifecycle`。
- 状态由 monitor 汇总（`monitor/internal/healthview`），首页展示。

因子引擎的启动前检查：本地存储布局版本；每个启用集合的数据源本地数据就绪（下面「本地数据就绪」）；变更日志没有断档；窗口内存与总预算放得下。

**本地数据就绪**的判断（`localdata.Coverage`）：对集合标的全集里**本地已有数据**的每个标的，满足以下之一：

- 根数 ≥ 回看数量 N；
- 本地 `Earliest` 就是 Storage 的首根，并且同时满足两个前提：数据源是 7×24 市场（目前因子引擎只支持 crypto），N 不超过该数据集保留期能容纳的根数（保留期 ÷ 周期）。满足时 Storage 有多少本地就有多少，说明是在保留期内新上市的标的。前提不满足时 Storage 的首根可能是被保留期截断的，不能据此认定是新上市：N 超过保留期容量时一律不豁免；有交易时段的市场按日历桶清理，首根同样可能是截断造成的，本期不适用豁免。不豁免时不足 N 根就保持未就绪，由用户导入。已实现（`localdata.newListingExempt`，保留期取自数据集信息 `GetDataset`）。

不满足的列出缺数据的标的和区间，检查失败并提示导入。完全没有本地数据的标的，先从 Storage 取 N 根；Storage 也没有任何数据时，该标的**检查失败**（决定 24）：列出标的，提示导入，或把它从集合的标的列表里移除。无法核对（访问 Storage 出错）时只给警告，不判失败。已实现：`Prepare` 返回 `NoDataError`，数据源未就绪，生命周期检查给出「本地数据」失败项和处理命令（导入或从集合移除）。

**「失败」的含义**：数据源进入「未就绪」，拒绝 `init` 和 `start`，报明确错误和处理命令；引擎进程不退出。原因是 Pebble 同一目录只允许一个进程打开，导入要走引擎的本地写入接口（7.1），进程一退出用户就没法导入。新上市的标的（上面第二条）不算失败。

**`Latest` 是否追到当前不是就绪条件。** 启动时同步器把本地补到最新已收盘的一根，个别标的拉取失败只记为同步失败，按 11 节「本期数据未到」处理（进跳过账本）；只有**全部**标的都失败才算启动失败。原因是下架、长期停牌的标的永远追不上当前，把它当就绪条件会让整个数据源一直未就绪。这类标的的处理办法是**把它从集合的标的列表里移除**（`UpdateSetSubjects`）。**移除后的目标行为**（决定 18）：

- 实时计算按新列表过滤标的（目录刷新后已是如此）；
- 变更同步按集合标的过滤，已移除标的在 Storage 里的历史修正不再写入本地、不再触发窗口重载；
- 集合的标的列表变化时，自动重新准备该数据源的窗口和覆盖检查，不需要重启引擎；
- 已移除标的的本地数据保留（永不删除），不再加载进窗口，也不提供清理命令。

**已实现**：只列出标的的集合（`subject_mode=include`）的标的列表变化后，预载按「回看、标的列表指纹」判断重新准备，窗口释放被移出的标的（`Window.Retain`）；变更跟进按集合标的过滤（`Spec.Subjects`）。「全部标的」的集合不过滤，标的清单来自数据集，由重启或 `init` 刷新。

### 6.3 启动、预热与运行

1. 所有模块就绪后，用户点击启动（或执行启动命令），系统进入**预热**：因子正常计算，策略正常求值，Trade 对预热中的策略实例走**影子模式**：用实时报价完成目标换算，记录将要下的单（影子订单），不预留资金、不下单。
2. 首页展示预热指标：每期耗时、缺数标的数、因子覆盖率、影子订单。
3. 用户确认后进入**运行**。

Trade 的影子模式是新增能力。

### 6.4 重启与故障

- **重启**：每个模块重启后先跑启动前检查，通过就回到重启前的阶段（运行或预热），首页提示「已自动恢复」；不通过就进入未就绪，受影响的对象按下一条暂停。
- **只停受影响的部分**：按依赖链向下传：数据源 → 因子集合 → 策略实例。例如某个数据源断档，只暂停用它的因子集合和用这些集合的策略实例，其他照常。实现上数据源 → 因子集合是显式的（集合检查失败自动暂停）；因子集合 → 策略实例靠「没有新的因子事件就没有新目标」隐式停下，策略侧自己的检查只管实例自身，因为引擎不能被策略反向访问。
- **策略实例暂停** = 不发新目标、持仓不动，并告警，由人决定是否手动平仓。不能用空目标表示暂停：Trade 把空的 FULL 目标解释为清仓（`trade/internal/application/target/weight_resolver.go`）。
- **恢复**：受影响的部分重新通过检查后，自动回到暂停前的阶段。期间漏掉的周期由现有追赶机制补算因子；这些过期周期不会成交，Trade 入口会按 `valid_until` 拒绝过期目标（`trade/internal/eventconsumer/target.go`）。

## 7. 导入 importer

### 7.1 部署与写入目标

- 导入不是常驻服务：`moox-cli import` 与独立二进制 `moox-importer`（`run` / `status` / `version`，`modules/importer`）共用 `packages/seriesimport`，在执行命令的那台机器上同步运行，读这台机器上的文件，进度和结果由命令输出。
- 写 Storage 经操作员 SSH 网关（`--manifest` 部署配置、`--storage-auth-file` 鉴权文件）；写因子本地存储经引擎健康端口上的本地写入接口（`--engine`，可以是 SSH 隧道的本地端口）。数据文件放在执行机器上，导入命令传 `--path`。
- **写入目标**可以选一个或多个：
  - `storage`：写入 Storage（行写入接口），并入现有 `moox-cli storage import` 的能力；
  - `factor`：通过因子引擎的本地写入接口调 `WriteRange`。
- 任务状态和断点存在 SQLite 断点库里（`--job-db`，默认 `./importer.db`；同一请求重跑自动续传，也可以用 `--job` 指定任务 ID）。`WriteRange` 是整段替换、天然幂等，每个目标每批写完记一次断点；失败重试就是原样重写这一批。
- 引擎处于未就绪状态时仍接受本地写入，这正是「先导入、再就绪」的流程。

### 7.2 格式与校验（packages/seriesformat）

- **格式层**：统一的 `Decoder` 接口，按批输出列式行，按格式名注册。`csv` 是第一个实现，以后加 parquet、jsonl、交易所历史数据包等，只是多一个实现。有界流式读取，不整文件累积。
- **校验层**（与格式无关，所有格式共用）：
  - 字段名与数据集注册的字段一致，**必须带全部字段**；外加时间列 `data_time`，可选 `series_tag`（或用 `--series-tag` 统一指定）；
  - 时间按 UTC 解析：没有时区的视为 UTC，带时区的转换为 UTC；
  - 连续性：文件内按网格连续；有缺期时默认拒绝并列出缺的周期，带 `--allow-missing` 时写入本地为缺失行（按填充规则），写入 Storage 时跳过这些周期；
  - 标的必须已在数据集的标签范围内（与现有 storage import 一致，不在范围内就拒绝）。
- CSV 约定：一个文件对应一个标的，文件名即标的 ID（也可以用 `--subject` 指定）。

### 7.3 命令

```
moox-cli import --format csv --space crypto --dataset <dataset> --freq 1m \
  --path /data/moox/import/spot_1m/ [--target storage,factor] [--allow-missing] [--recalc] [--batch-rows 10000]
```

- `--target` 默认两者都写；
- `--recalc` 时，写入因子本地的数据按第 5.3 节生成失效待办，提交区间重算，得到历史因子值。

## 8. 回看数量与内存配置

### 8.1 回看数量 N

- **设置**：初始化时由用户设置全局默认 N（默认 1 万），可对单个数据源覆盖（例如 1d 数据集 500 就够，1 万根是 27 年）。写入引擎配置的 `window.lookback` 与 `window.lookback_overrides`（第 12 节）。
- **与因子的关系**：窗口长度就是 N。因子创建、更新、启用时校验 `Lookback ≤ N`（`Lookback` 是表达式包含当期的所需行数，例如 `ts_mean(close, 500)` 恰好需要 500 根，`ema(close, 20)` 按截断容差需要 208 根），不满足就拒绝并提示调大 N。表达式的 `MaxLookback`（整个表达式的回看）和 `MaxWindow`（单个函数的窗口参数）现在是固定的 5000，改成由调用方按数据源的 N 传入，两者各自校验，包内只留一个 10 万的绝对上限；校验因此从编译期常量挪到因子目录里，按该因子所属数据源的 N 比较。
- **改 N**：调小时，若已有因子的回看超过新 N，拒绝并列出这些因子；调大时，数据源在本地数据补够之前处于「未就绪」，可以用 `backfill --bars N` 补，或导入。
- **自动补数的限制**：从 Storage 自动补只能补到该数据集保留期能容纳的根数（保留期 ÷ 周期，由 `storagepolicy` 的 `Retention` 决定，主存的保留范围与 View 根数不同，View 要求被保留期覆盖）。默认保留期已按 1 万根配置（第 10.1 节）；N 超过它时，超出的部分只能靠导入，并且「新上市」豁免对该数据源不生效（见 6.2）。设置 N 时读取保留期并校验、提示这一点。
- **内存估算与校验**（决定 21）：按「序列数 × (N + 余量) × (数值字段数 × 8 + 1)」展示窗口内存，和 `window.max_memory` 比较，超过则警告；例如 2000 个序列、N = 1 万约 1.4GB，N = 5 万约 7.1GB。
- 已实现：窗口长度取 N；`MaxLookback`、`MaxWindow` 提到包内绝对上限 10 万（单个函数的窗口参数不超过 N 已被 `Lookback ≤ N` 隐含，不再单独参数化）；`Lookback ≤ N` 由引擎在准备数据源和集合检查时校验（N 在引擎配置里，因子管理端读不到它，所以不在创建因子时校验），超限的集合检查失败并列出因子。配置见第 12 节。

### 8.2 内存配置

- 探测到总内存 M 后，设窗口常驻 W、Pebble 块缓存 C：
  - `memory.total_budget = M × 60%`；
  - `window.max_memory`（即 W）`= max(0, 总预算 − C) × 40%`，是窗口内存的**预算上限**，不读取序列数或因子定义；
  - `compute.max_memory = max(1GiB, (total_budget − W − C) × 50% ÷ 并行计算数)`，并行计算数取计划启用的集合数与 CPU 核数中的较小值；
  - 都写入引擎的 `engine.yaml`，用户可以修改。
- **入口**：引擎的配置在引擎所在机器上，`moox-cli` 初始化时写不进去，所以由 `moox-factor-engine tune [--write]` 按本机内存给出建议并写入；`moox-cli` 的因子机探测报告只展示内存预算。
- 展示 M、W、C、总预算和建议值；`W + C` 超过总预算的 2/3，或 `total_budget − W − C < 1GiB` 时警告。

## 9. 逐期回放 replay

### 9.1 目标与边界

- 按时间顺序逐期推进历史数据，每期走实时计算路径算出因子，交给策略求值，再由 Trade 在独立的纸面账本里撮合，得到接近实盘时序的模拟结果。
- **回放绝不产生实际下单**；不进入生产事件总线，不影响连续水位、监控新鲜度和实盘策略实例。
- 编排由 `packages/seriesreplay` 负责，`moox-replay`（`modules/replay`）与 `moox-cli replay` 共用；因子引擎、策略、Trade 的回放接口都挂在各自的健康端口上（HTTP `/v1/replay/*`，沿用签名鉴权）。因子引擎只提供回放计算接口，回放窗口仍在因子进程内（要读本地存储）。

### 9.2 各模块接口

| 模块 | 接口 / 改动 |
| --- | --- |
| 因子引擎 | `ReplayOpen(session, set, from)`：按预热区间加载回放窗口（会话开始时取快照，运行中不随修正更新），向准入器预留内存；`ReplayStep(session, t)`：计算第 t 期并返回因子帧；`ReplayClose(session)` |
| 策略 | 新增回放求值接口：入参是 `replay_id`、实例、周期和完整回放输入（见 9.4），复用现有求值引擎（`strategy/internal/engine`），**只返回本期决策**（目标权重或跳过），不直接发事件 |
| Trade：回放会话 | 每次回放建立一个**纸面账本会话**（`t_replay_sessions`），初始资金、费率、滑点固定，结束后保留结果、可清理 |
| Trade：回放推进命令（新增 `ReplayAdvance`） | 每期必达：`replay_id`、周期（决策时刻毫秒）、回放报价（估值价与成交价）、决策（`UPDATE_TARGET` 带完整目标集合 / `SKIP`）。`SKIP` 不改动目标，只按回放报价估值。同步返回本期确认；按 `(replay_id, period)` 幂等 |
| Trade：账本撮合 | 估值与成交都用回放报价，缺价时报错、不回退实时报价；先卖后买，买单受可用现金限制；只做多现货；不接触实盘账户、订单、预留与执行器（实盘的执行链路绑定墙钟与交易所适配器，回放账本自成一体，保证回放绝不下单、不影响实盘） |
| Trade：订单、成交 | 记录在 `t_replay_orders`（带 `replay_id`），周期结果在 `t_replay_periods` |
| 因子集合事件、水位 | 不变，回放不发 `FactorPeriodComputed` 等生产事件 |

### 9.3 流程

```
moox-cli replay start --set <因子集合> --instance <策略实例> \
  --from 2026-01-01T00:00:00Z --to 2026-02-01T00:00:00Z [--write-factors]
```

1. **校验**：本地数据覆盖回放区间及预热区间，并且**包含 `to` 之后的一根**（用于下一根开盘成交）。
2. **建立会话**：回放服务分配 `replay_id`，让 Trade 创建纸面账本会话；调用因子引擎 `ReplayOpen`：
   - 预热起点 = `from − (L_f − 1 + k) × 周期`，L_f 是因子最大回看根数，k 是策略引用因子列的上一根深度（如 `bars[-1]` 为 1）；标的年龄要求另按本地首根校验，不并入预热根数；
   - 第一个正式周期之前，先算出并缓存策略需要的上一期因子值；
   - 会话固定策略版本和因子定义版本。
3. **逐期推进**，对周期 t：
   1. 调 `ReplayStep` 取因子帧；
   2. 调策略回放求值，得到决策；
   3. 持久化周期记录（9.5）；
   4. 向 Trade 发 `ReplayAdvance`，等确认；
   5. 带 `--write-factors` 时写因子结果（与区间重算的写法相同，不发周期完成事件）；
   6. 本期所有阶段完成后推进下一期。纸面账本**没有跨期挂单**：每期只在 `UPDATE_TARGET` 时按目标调仓，资金不足的订单当期记为部分成交或拒绝，剩余量不保留，下一期按新目标重新调仓；`SKIP` 只估值。
4. 支持暂停、继续、取消；进度、当前周期、每期耗时在回放服务里查询。

回放报价默认取下一根的开盘价，模拟「本期收盘决策、下期开盘成交」；可选本期收盘价。时间语义：K 线起点是 `data_time`，决策时刻是 `data_time + 周期`，成交时刻是下一根开盘（与决策时刻同一刻）。

### 9.4 策略回放输入契约

回放求值的入参与现有求值一致，构建逻辑复用 `strategy/internal/engine/frame.go` 和研究回放（`strategy/internal/replay/runner.go`）：

- 本期因子帧，以及策略需要的上一根数据；
- `Universe` / `Expected` / `AgedOut`、失败列、市场类型、周期序号；
- 前序规则状态（持有批次等），按 `replay_id` 独立保存，不读写实盘实例的状态。

### 9.5 周期记录与恢复

- 回放服务在自己的 SQLite 里按 `(replay_id, period)` 保存周期记录：本期决策、下一期策略状态、待发送的 `ReplayAdvance`，以及各阶段完成标记（Trade 已确认、因子已写入、本期完成）。同一期重复执行返回同一条记录，不重新求值。因子行**不落库**：`--write-factors` 恢复时重新向引擎取该期因子再写。
- 重启后按完成标记补齐缺的阶段：Trade 未确认就原样重发命令（Trade 按 `(replay_id, period)` 幂等），因子未写入就重新取该期因子再写；全部完成后才推进。边界：每次续跑（回放进程重启也算）都会重新调用 `ReplayOpen`，关闭旧会话并按当时的本地存储快照重建回放窗口；若首次快照之后历史数据被修正，补写的因子值可能与当时决策所用的不同。需要严格一致时重新开始回放。

### 9.6 与区间重算、策略研究回放的关系

| 需求 | 用法 |
| --- | --- |
| 只要历史因子值 | 导入 + 区间重算（`--recalc`），比逐期回放快几个数量级 |
| 要按实盘时序验证策略与成交 | 逐期回放 |
| 快速比较策略版本 | 现有策略研究回放（`strategy/internal/replay`，读取 View，区间受 View 保留根数限制） |

### 9.7 速度估算

内存窗口下每期的读取成本接近零，耗时主要在计算、跨模块调用和撮合往返。如果每期 0.1–1 秒，回放一个月的 1m（约 4.3 万期）需要 1–12 小时。实施时按真实因子集合实测，再决定是否在回放里批量预计算因子、只逐期执行策略和撮合。

## 11. 故障处理

| 情况 | 处理 |
| --- | --- |
| 本地目录损坏、布局版本不符 | 自检失败、未就绪。人工删目录后重新导入，或由同步器按回看窗口从 Storage 拉取 |
| 本地数据不足 | 自检失败、未就绪，列出缺数据的标的和区间，提示导入 |
| 本地和主存都没有任何数据的标的 | 数据源未就绪、进程不退出，拒绝 `init` 和 `start`；列出标的，提示导入或把它从集合的标的列表里移除（决定 24） |
| 同步器拉取失败、本期数据未到 | 本期按现有规则：该标的算失败，进入跳过账本，之后补算 |
| 交易所本身缺数据 | 之后的周期有数据时，写成缺失行并按填充规则填充（第 3.4 节） |
| 修正通知丢失、引擎离线 | 下次心跳或启动时从同步位点继续读变更日志 |
| 变更日志断档 | 该数据源未就绪，受影响的集合和策略实例暂停；用户执行对账命令后自动恢复 |
| 内存预留不到 | 任务排队，超时拒绝并给出原因；实时周期的计算优先 |
| 上游故障 | 只暂停依赖链上受影响的对象，策略实例不发新目标、持仓不动 |
| 回放中服务重启 | 按周期记录的完成标记补齐后继续 |
| 回放推进命令发给已结束的会话 | 已完成周期的原样重发按幂等返回原结果；新周期推进被拒绝（冲突）。`replay_id` 不存在同样报错。回放账本与实盘账户、订单、预留互不相通，回放不可能产生实际下单 |

## 12. 配置

因子引擎 `engine.yaml`：

```yaml
seriesstore:
  dir: ./data/seriesstore
  block_cache: 512MiB
window:
  lookback: 10000               # 回看数量 N 的全局默认（决定 23）
  lookback_overrides: {}        # 按数据源覆盖，键为 space/dataset/freq
  max_memory: 4GiB              # 初始化按探测结果写入
  headroom: 0                   # 每个序列的环形余量（根数），0 = 窗口长度的 1/4（至少 16）
memory:
  total_budget: 12GiB           # 初始化按 总内存 × 60% 写入
compute:
  max_memory: 1GiB              # 初始化按第 8 节公式写入，是单次计算上限
```

导入没有常驻配置，参数都是命令行：`--path`（文件或目录，可重复）、`--batch-rows`（每批行数，默认 10000；不会拆开同一个时间点，同一时间点的行较多时批次会略超过该值）、`--engine`、`--job-db`、`--manifest`、`--storage-auth-file` 等，见 7.3。

方法：只读取 X99 上因子引擎日志里每期的 `factor_period_done`（含 `load` / `compute` / `assemble` / `write` / `report` 各阶段耗时），取 10-21 起两个 1m 集合（现货、永续，约 516 / 524 个标的）的 5521 个实时周期；「实时」指日志时间紧跟周期结束，追赶周期不计。

**稳态各阶段**（`load` 不超过 5 秒的 4563 个周期）：

| 阶段 | 中位数 | 占比 |
| --- | --- | --- |
| 写结果到 Storage（`write`） | 约 430ms | 46.5% |
| 读取（`load`，含拉取） | 约 230ms | 35.7% |
| 上报（`report`） | — | 6.8% |
| 因子计算（`compute`） | 约 63ms | 6.4% |
| 组装（`assemble`） | — | 2.9% |

整个周期中位数约 850ms。结论：

- 因子计算只占 6%，EMA 这类递推因子用「保存递推状态」来省计算量不值得做；要优化每期耗时，该看的是写结果和读取。
- 整点（与 1h 集合同时触发）的 `load` 中位数与其他分钟相同（226ms 对 231ms），只有 p95 更长（2.8 秒对 0.69 秒，整点样本仅 78 个）。每个集合每期约 6 个读取请求（每请求最多 100 个标的，4 个并发），并发拉取本身不是瓶颈。订阅行消息（`DatasetRowsUpserted`）直接改本地数据的做法已评估后撤销（决定 26）：收益只是每期省这几个请求，却要引入一整套机制才能保证正确。

**`load` 长尾**（10-22）：

| 指标 | 数值 |
| --- | --- |
| `load` 超过 5 秒的实时周期 | 958 个，占 17% |
| `load` p95 / 最大 | 约 38 秒 / 47 秒 |
| 两个 1m 集合同一周期都慢 / 只有一个慢 | 1 次 / 956 次 |
| 出现时段 | 10-22 03:00–14:xx 与 16:26 以后，每小时约 50 个；10-21 基本没有；15:05–16:20 恢复正常 |

慢周期里 `compute`、`write` 正常，只有 `load` 在等，等待时长在 0–47 秒间大致均匀。

**推断的原因**（未直接证实）：变更跟进 `followSource` 在持有数据源锁期间调用 `Follow`；`Follow` 对变更日志里每个标的的每个区间调用 `refetch`，每次先查 Storage 最早时间、再读窗口，共两次顺序请求，516 个标的约 1000 次请求，按每次 20–40ms 算为 20–45 秒；计算前读取要拿同一把锁，于是被堵住。两个集合基本不同时慢，符合跟进逐个集合轮流进行。变更日志记录每一次行写入，本期新 K 线先被拉取写入本地，随后落在本地范围内，被当作需要比对的变更再拉一遍。没有解释的两点：为什么 10-22 03:00 才开始，以及 15:05–16:20 为什么恢复。改造方案见 5.2「变更跟进的规则」。
