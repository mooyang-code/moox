# 行情获取方式对比：REST 拉取与 WS 推送

> 参考文档（2026-10-20）。写给以后维护采集模块的人：K 线"怎么拿"有两种方式，各有什么特点，我们为什么这样取舍，改动前要注意什么。
> 结论来自同日在香港、南京主机上的实测与线上数据核对；方案细节见 [WS 行情推送采集设计](WS行情推送采集设计.md)，现行 SCF 链路见[采集](../模块/采集.md)。

## 0. 一句话结论

**实时 K 线用 WS 推送，REST 只用在"已经稳定的数据"上**（补采、历史、标的列表、现货的少量兜底，以及推迟到定稿之后才取的 SCF 备用链路）。原因是：REST 返回里没有"这根 K 线已闭合"的标志，币安合约 REST 要到收盘后约 8 秒才是定稿值；而 WS 推送带显式的闭合标志，收盘后约 0.1～0.3 秒就到，整点也不变慢。

## 1. 两种方式在我们系统里是什么

| | REST 主动拉取 | WS 推送 |
| --- | --- | --- |
| 怎么拿 | 收盘后发 HTTP 请求取 K 线（币安 `/api/v3/klines`、`/fapi/v1/klines`） | 建立常驻连接、订阅 K 线流，交易所在 K 线更新与收盘时推过来 |
| 我们的执行端 | SCF 函数：腾讯云定时器每分钟触发，42 个函数各取约 25 个标的 | `collector-stream`：海外机上一个常驻进程，4 条连接收全部约 1035 个标的 |
| 现在用在哪 | 实时采集（现行）、补采、历史扫描、标的列表、SCF 备用 | 实时采集（设计中，加密空间默认） |

## 2. 特点对比

| 维度 | REST 拉取 | WS 推送 |
| --- | --- | --- |
| **是否知道"已闭合"** | 不知道。返回字段是开盘时间、开高低收、成交量、收盘时间、成交额、笔数、主动买入量／额；其中"收盘时间"是固定的开盘时间 + 59999 毫秒，K 线还在变时就已经是这个值。只能靠"本机时间过了收盘时间"推断，这不代表交易所已经算完 | 知道。推送里 `k.x == true` 就是这根 K 线的最终值 |
| **收盘后多久是定稿值** | 现货：0.6 秒约 99.3%，1.5 秒约 99.9%，3 秒起 100%。合约：0.6 秒活跃标的只有 13～32%，3 秒约 60～89%，5 秒约 86～88%，**8 秒起 100%**。连续合约 K 线的 REST 接口（`/fapi/v1/continuousKlines`）与普通接口一样慢 | 现货收盘推送全部在收盘后 250 毫秒内（服务端时间），本机全部到齐约 0.15～0.3 秒。合约见下一行 |
| **合约的收盘推送** | — | 普通 K 线流（`<symbol>@kline_1m`）：新一分钟有成交的标的在第一笔成交时收盘，3 秒内没成交的固定等到 3 秒才收盘（约 27% 的推送）。**连续合约 K 线流**（`<pair>_perpetual@continuousKline_1m`）：所有标的固定在约 0.1 秒收盘，数值相同 |
| **整点表现** | 整点前后币安 REST 明显变慢，约一半请求停住数秒；整点现货 1m 写入完成要 6～7 秒 | 不受影响；整点全部到齐仍在 0.3 秒内 |
| **不定稿的值长什么样** | 只会"偏少"：成交量、成交额、笔数少了收盘前最后一些成交，收盘价可能不是最后一笔；开盘价、最高最低价基本对 | 不会出现（只接受 `x=true`） |
| **历史数据** | 能取任意历史，收盘 1 分钟以后的都已稳定 | 只有订阅之后的实时数据，断线期间的拿不到 |
| **资源** | 每分钟每个标的一次请求，受交易所请求权重限制；SCF 按调用计费，无常驻资源 | 4 条连接，入站平均约 1.7 Mbps，CPU 约 6%（2 核）；不消耗请求权重 |
| **失败模式** | 单次请求失败可重试、换端点；整点停住要靠备援请求、更早发出 | 断线（含交易所每 24 小时强制断开）期间收不到；要重连、重新订阅、提前轮换连接 |
| **运维形态** | 无状态，云函数天然多实例 | 常驻进程，单点；要监控在线、连接与到达情况 |
| **网络** | 国内主机只能用 `data-api.binance.vision`（现货） | 国内主机只能连 `data-stream.binance.vision`（现货），合约连不上；只能放在海外机 |
| **判断"全部标的到齐"** | 每个请求各自返回，取齐就是齐 | 交易所没有"本根 K 线全部推完"的汇总消息，只能按标的逐个计数 |

## 3. 这次排查里证实的关键事实

1. **线上合约数据有相当一部分不是定稿值。** 现行 SCF 在收盘后约 0.5～0.8 秒取合约 REST、每分钟只取 1 根，之后不会回补。与收盘 1 分钟后的稳定值比对，合约 1m 不一致：10-18 为 26%、10-19 为 36%、10-20 为 55%（当天把错峰降到 1 毫秒、复用连接，取得更早）。现货 1m 约 2.4%。
2. **Storage 的周期一旦完成就锁定。** 一个周期全部序列提交成功的那一刻，DataNode 就把周期定为完成；之后对它的周期提交只返回回执、不写行，下游在完成事件到达时就读走了数据。所以不能"先写一个早取的值，过几秒再覆盖"——进入周期提交的必须是定稿值。事后修正只能走补采（普通写入），已经算出的因子与策略结果不会自动重算。
3. **替代判断方法都不可靠：**
   - 等 REST 里出现下一根 K 线：BTCUSDT 新一根约 3 秒就出现，上一根要到约 8 秒才全部定稿；
   - 隔一会儿取两次、数值不变就算定稿：冷门标的几秒没有新成交时两次也一样，但可能仍缺数据；
   - 用逐笔成交（`aggTrade`）自己聚合：与官方 K 线的成交量、笔数只有约 95～98% 一致（跨分钟成交的归属规则不同）；
   - 用收盘前最后一条未闭合推送：合约只有 25～50% 等于定稿。
4. **合约普通 K 线流的 3 秒** 是交易所侧的收盘机制（服务端事件时间就是收盘后 3000 毫秒，网络传输只有约 33 毫秒），换机器、换地址都绕不开；换成连续合约 K 线流就没有这个问题。

## 4. 我们的取舍

| 场景 | 选择 | 理由 |
| --- | --- | --- |
| 加密货币实时 K 线 | **WS 推送**（`collector-stream`），现货订阅普通 K 线流，合约订阅连续合约 K 线流 | 唯一能在收盘后 1 秒内拿到定稿值的方式；整点不变慢 |
| 现货推送没到的少数标的 | 收盘后 3 秒起用 REST 兜底，REST 须在收盘后 4 秒前返回、5 秒截止前写完 | 现货 REST 3 秒起已定稿；整点来不及就交给补采 |
| 合约推送没到的少数标的 | **不用 REST 兜底**，交给补采 | 合约 REST 8 秒才定稿，晚于 WS 模式 5 秒的截止；连续合约 K 线全量实测 75 分钟没有缺过 |
| 周期截止时间 | WS 模式 5 秒，SCF 模式 15 秒，随采集方式切换 | WS 正常 0.5 秒写完，截止只影响"有标的没到"的周期；SCF 合约要等 8 秒才取数，需要 15 秒 |
| SCF 实时采集 | 保留为备用，默认不启用；启用时现货收盘后 3 秒、合约 8 秒才取数 | 推迟到定稿之后，切回 SCF 时数据同样正确，代价是更慢 |
| 补采、历史扫描 | REST | 历史 K 线已稳定，REST 能取任意区间、可并发 |
| 全市场标的列表 | REST（交易所规则接口，经统一的行情源目录） | 低频（每小时），不需要推送 |
| A 股 | REST（SCF） | 数据源没有可用的推送；分钟线没有定稿问题的实测前不改 |

## 5. 改动前要注意的事

1. **不要缩短 REST 的取数等待。** 合约 REST 收盘后 8 秒、现货 3 秒以内取到的值都可能不是定稿，一旦进入周期提交就改不回来。要缩短，先按第 6 节的方法实测。
2. **合约不要改回普通 K 线流。** 冷门标的会固定晚 3 秒收盘。
3. **只认显式的闭合标志。** 新接的数据源如果推送里没有闭合标志，不能直接用于周期提交，先想清楚怎样判断定稿。
4. **`series_tag` 不随传输方式变。** WS 与 SCF 写同一个 `series_tag`（`source:spot_http`／`swap_http`，`http` 是历史命名），改了就成了新序列，历史窗口断开。
5. **同一周期只能有一个写入方。** WS 与 SCF 之间切换必须按生效周期交接，见设计第 6.3 节。
6. **解析币安推送注意大小写键。** `data` 里同时有 `e`／`E`、`t`／`T`、`v`／`V`、`q`／`Q`、`l`／`L`，Go 的 `encoding/json` 对字段名大小写不敏感，结构体必须为每种大小写都声明字段，否则数值会串。
7. **WS 连接会被定期强制断开**（币安 24 小时），要在断开前主动轮换，避免缺数。
8. **整点前后币安 REST 会变慢**，REST 链路的超时、重试、错峰都要按整点设计，见[整点取数变慢排查](采集整点取数变慢排查与优化.md)。

## 6. 怎样验证一个数据源（可复现的方法）

新接交易所或怀疑行为变化时，按这套方法验证，覆盖至少一个整点：

1. **基准**：收盘 1 分钟以后再用 REST 取的历史 K 线（已稳定）。比对字段：开、高、低、收、成交量、成交额、笔数，逐字节相等才算一致。
2. **REST 定稿时间**：每分钟在收盘后若干时刻（例如 0.6、1.5、3、5、8、12 秒）对同一批标的取 REST，分别与基准比对，找出全部一致的最早时刻。样本要包含活跃与冷门标的——活跃标的收盘前成交多，反而更晚定稿。
3. **推送时效与完整性**：全量订阅，记录每个标的每根 K 线的闭合推送的服务端事件时间与本机收到时间；检查每个周期是否每个标的都有闭合推送（包括没有成交的分钟），统计每周期最后一个标的的到达时间。
4. **推送数值**：闭合推送的数值与基准比对，应 100% 一致。
5. **线上核对**：Storage View 的 DuckDB 文件不能直接打开（服务进程占用），在存储主机上低优先级复制到临时目录再导出，用完删除；与基准逐条比对。

2026-10-20 的调研工具（`wsresearch`，Go）与分析脚本没有放进仓库；需要时按上面的方法重写即可。
