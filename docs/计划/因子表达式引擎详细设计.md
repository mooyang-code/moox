# 因子表达式引擎详细设计

> 状态：设计稿 v3（尚未编码；已吸收三轮 Codex 审查，处置见第 16 节，第三轮确认可以进入编码）。已确认的决策：
> 1. 因子改用声明式表达式定义，由 Go 在引擎进程内计算；
> 2. 窗口不满时严格输出 NaN（写入为 null）；
> 3. Python 因子执行链路**直接删除，不设过渡期**；
> 4. 语法采用 WorldQuant BRAIN / Alpha101 风格，解析器复用策略 DSL 已在用的 expr-lang；
> 5. 允许新旧结果在浮点末位上存在误差。
>
> 实施顺序、改动文件与验收见[执行计划](因子表达式引擎执行计划.md)。实现之后，以[因子](../模块/因子.md)为准。

## 1. 背景与目标

### 1.1 现状（2026-10-17 实测）

因子引擎运行在编译机 192.168.0.103（88 个逻辑核）上，每个因子是一个 Python 文件，通过 `packages/pyruntime` 的常驻进程池执行。

| 项目 | 实测 | 原因 |
|---|---|---|
| Python 进程 | 64 个 | `python.workers` 未配置，`autoPythonWorkers` 取 min(64, 核数 × 3/4) |
| 线程 | 每个进程 64 个，合计约 4100（全机 7140） | numpy 自带的 scipy-openblas 按核数开线程池（`MAX_THREADS=64`）；因子不调用 BLAS，63 个线程每个累计只用了 0.12s CPU |
| 内存 | worker 合计 RSS 约 5GB | 64 份 pandas/numpy |
| 单次请求 | 1 个标的 × 11 个因子 × 58 行：单进程 65ms CPU；64 个进程并发时约 109ms | 一半以上是框架开销（JSON 编解码、构造 DataFrame、校验、deepcopy、逐行编码）；其余是 pandas 每次调用的固定开销（`groupby().transform(lambda …)` 对每一组都回调一次 Python） |
| 每期计算 | 500 个标的约 30～55 CPU 秒；每到整分钟，64 个进程同时满载约 0.7 秒 | 时序因子每个标的调用一次 |
| 1m 集合每期各阶段耗时 | 读取约 1.5s，计算约 0.64s，写入约 0.4s | 时延的大头在读存储 |

同样数据（500 标的 × 11 因子 × 58 行）的基准测试：

| 实现 | CPU 时间 |
|---|---|
| 现有逐标的请求（192） | 32.6s |
| pandas 批量（全部标的拼成一个 DataFrame 调用一次，192） | 2.4s |
| Go 朴素实现（Mac 单线程，未做任何优化） | 0.031s（同一台 Mac 上 pandas 为 6.74s，约快 200 倍） |

生产因子库（control 主机 `factor.db`，2026-10-17 只读查询）：11 个时序因子，全部是“滚动窗口 + 逐元素运算”；4 个因子集（2 个 1m、2 个 1h），44 个启用成员；**没有截面因子**。

### 1.2 目标

- 因子用声明式表达式定义，在引擎进程内用 Go 计算。删除 Python worker、`packages/pyruntime`、venv 以及 pandas/numpy 依赖。
- 支撑上百种因子：在 192 上，一个 1m 集合 500 个标的 × 300 个因子，每期计算阶段不超过 0.5 秒；引擎不再有子进程。
- 回看长度、输入列、因子类型（时序 / 截面）全部由表达式静态推导，不再手填。
- 与现有 pandas 实现相比，正常数据上连续值的相对误差不超过 1e-9（判定口径见第 12 节）。
- 周期流水线（读取、空洞检查、预热、组装、写入、周期标记、补算、跳过恢复）的外部契约不变。

### 1.3 非目标

- 不在 Go 里重写 pandas，不支持执行任意代码。
- 不做增量流式计算：1m、1h 周期在缓存的窗口上无状态重算只要毫秒级。
- 不做行业 / 板块中性化（目前没有分类数据）、不做因子自动挖掘、不做跨因子的共享宏（见 15 节）。
- 不改 Storage 与策略的协议。Storage 周期标记里的 `source_hash` 字段原样保留，改填定义文本的哈希（见 9.3）。

### 1.4 业界参考与取舍

| 体系 | 做法 | 本设计借鉴 |
|---|---|---|
| WorldQuant Alpha101 / BRAIN Fast Expression | `rank(ts_corr(close, volume, 10))`；算子分为时序 `ts_*`、截面、分组三类 | 算子命名与分类、小写函数式语法 |
| 国泰君安 Alpha191 | 公式写法，补充 `SMA(x,n,m)`、`DECAYLINEAR`、`REGBETA` 等 | 补充国内研究常用的算子 |
| 微软 Qlib | 因子库是一张“名字 → 表达式字符串”的表（Alpha158）；表达式树上的每个算子自己报告需要的回看（`get_extended_window_size`）；滚动用 pandas，回归类用 Cython | **因子库即数据**；**回看由算子树推导** |
| DolphinDB 响应式状态引擎 | 把表达式拆成有状态 / 无状态子算子，逐条增量计算，批流一体 | 只适用于逐笔、秒级场景，本期不做；算子接口不排斥以后加增量实现 |
| Polars 表达式 | 列式计算，整个面板一次算完，公共子表达式只算一次 | **列式执行**、**公共子表达式消除** |

这些体系的共同点：因子是一门小语言里的表达式；算子库是一组固定的、经过充分测试的向量化原语；回看、依赖和合法性都靠静态分析得到。

## 2. 总体结构

```text
                        packages/factorexpr（纯 Go，无 CGO）
                ┌──────────────────────────────────────────────┐
  定义文本 ───► │ spec：YAML 解析、参数展开、规范化             │
                │ syntax：expr-lang 语法树白名单、名称解析       │
                │ compile：类型检查、回看推导、类型推导、DAG     │
                │ ops：算子注册表（签名、回看规则、内核、参考实现、文档）│
                │ exec：面板、需求区间、缓冲区、并行执行          │
                └──────────────────────────────────────────────┘
                  ▲ 编译、校验、试算                ▲ 编译集合程序、按期执行
     moox-factor-mgr / mgr-cli                 moox-factor-engine（pipeline.Compute）
```

- `packages/factorexpr` 是一个独立的 Go 模块（加入 `go.work`），只依赖 expr-lang（版本与 `modules/strategy` 保持一致，目前是 v1.17.8）和标准库，不依赖因子模块的内部包。
- 管理端用它编译和校验定义、推导元数据、做试算；引擎用它把一个因子集的全部启用因子编译成一个程序，每期执行一次。
- 两端使用同一份代码，**必须同版本发布**（见 9.3 的语义版本）。

## 3. 因子定义

### 3.1 定义文本

定义文本（下称 spec）是一份 YAML 文档，只描述计算本身：

```yaml
params:                  # 可选：命名常量
  window: 20
let:                     # 可选：有序的中间量，后面的可以引用前面的
  tp: (high + low + close) / 3
  m: ts_mean(tp, window)
outputs:                 # 必填：输出列名 → 表达式
  cci: (tp - m) / (0.015 * ts_mean(abs(tp - m), window))
```

| 字段 | 规则 |
|---|---|
| `params` | 名称 → 数值或数值列表。数值是整数或有限小数；列表表示展开（3.2）。名称匹配 `^[a-z][a-z0-9_]{0,31}$` |
| `let` | 有序映射：名称 → 表达式。只能引用在它之前定义的 `let`、`params` 和输入列，不允许递归。名称规则同 `params` |
| `outputs` | 有序映射：输出列名 → 表达式，至少 1 个。列名匹配 `^[A-Za-z_][A-Za-z0-9_]*$`，不能是保留列（`subject_id`、`freq`、`data_time`、`series_tag`），展开后不能重名 |
| 其他键 | 拒绝。YAML 里出现重复键、多个文档、锚点或别名同样拒绝（与 `engine.yaml` 的严格加载口径一致） |

用 YAML 映射承载 `let` 与 `outputs`，是为了和策略 DSL 保持同样的书写习惯；解析时必须按文档里出现的顺序读取（使用 `yaml.v3` 的 `yaml.Node`，不能先解到 Go 的 map 再遍历）。

不属于计算本身的属性放在定义的其他字段里，不进 spec：`factor_id`（身份）、`name`（展示名）、`allow_partial_universe`（截面全集策略，3.4）。

### 3.2 参数展开

参数写成列表时，按列表做笛卡尔积展开，输出列名用 `{参数名}` 占位：

```yaml
params:
  window: [5, 10, 20]
outputs:
  bias_q_{window}: ts_rank(close / ts_mean(close, window) - 1, window)
```

展开为 `bias_q_5`、`bias_q_10`、`bias_q_20` 三个输出。规则如下：
- 出现在列名模板里的参数必须是整数，按十进制格式化；
- 每个列表参数都必须出现在每一个输出列名模板里，保证展开后不重名；
- 展开后的输出总数不超过 64 个；
- 现有 Python 因子的 `windows` / `output_names` 写法由展开取代。

### 3.3 限制

| 项 | 上限 |
|---|---|
| spec 文本 | 64 KiB |
| 单条表达式原文 | 4096 个字符 |
| 单条表达式的语法节点 | 512 个 |
| 单个因子编译后的节点（展开、内联之后，去重之前） | 4096 个 |
| 参数个数 | 16 个 |
| 窗口参数 | 1～5000 |
| 推导出的回看 | ≤ 5000 个周期（见 6.2） |

### 3.4 因子类型与 `allow_partial_universe`

- 因子类型由编译推导：任一输出用到截面算子（`cs_*`），就是 `cross_section`，否则是 `timeseries`。`factor_type` 不再由用户填写，在接口中只读返回。
- `allow_partial_universe` 仍由用户填写，只对截面因子有效（时序因子填 true 时拒绝），语义保持不变：false 表示本期全集不完整就整因子跳过；true 表示剔除不可用的标的后照常计算。

## 4. 表达式语言

### 4.1 语法

表达式用 expr-lang 解析。与策略 DSL 一样禁用全部内置函数（`conf` 中 `DisableAllBuiltins`），这样所有函数调用都解析成 `CallNode`，由因子编译器自己解析名称。语法树节点按白名单检查：

| 允许 | 说明 |
|---|---|
| `IntegerNode`、`FloatNode` | 数字字面量 |
| `BoolNode` | `true` / `false` |
| `IdentifierNode` | 输入列、`let`、`params` |
| `UnaryNode` | `-`、`+`、`!`、`not` |
| `BinaryNode` | `+ - * / % **`，`== != < <= > >=`，`&& || and or` |
| `ConditionalNode` | `c ? a : b`，等价于 `where(c, a, b)` |
| `CallNode` | 调用方是标识符、并且在算子注册表中登记过的函数 |

其余节点（字符串、数组、映射、成员访问、`in`、`matches`、`??`、`..`、管道、闭包、`let` 表达式、`nil` 等）一律拒绝，报错时给出中文原因和出错位置（行、列）。

### 4.2 名称解析

依次在 `let`、`params`、算子注册表中查找；都找不到的标识符视为**输入列**。规则：
- `let` 与 `params` 不能重名，也不能和算子名或保留列重名；
- 函数名只能出现在调用位置，标识符不能被当作函数调用；
- 输入列名必须匹配列名规则；保留列不能作为输入。

定义本身不绑定数据集，所以编译时不知道有哪些源列。把因子加入因子集时（`ValidateMembership`）再检查三件事：推导出的输入列都存在于源数据集；它们都是数值类型；`let` / `params` 的名称没有和源列重名，避免读者误会。

### 4.3 类型

| 类型 | 来源 |
|---|---|
| 数值序列 | 输入列、算术运算、数值算子 |
| 布尔序列 | 比较、逻辑运算、`is_nan` |
| 数值常量 | 字面量、数值参数、只含常量的算术（编译期折叠） |
| 布尔常量 | `true` / `false` |

- 没有隐式转换：数值不能用在需要布尔的位置，反之亦然。布尔值转数值要显式写 `where(c, 1, 0)`。
- 窗口、位移、分位等参数必须是编译期常量，并且满足各算子的取值范围（第 5 节）。这是能推导回看的前提，Qlib 和 BRAIN 也是这么做的。
- 每个输出必须是数值序列，并且至少依赖一个输入列（常量输出没有意义，拒绝）。

### 4.4 空值与非有限值

统一的空值语义（不同于 pandas 的地方用 ★ 标出）：

1. 输入里的 null 读成 NaN；面板时间网格上缺失的行，其各列也是 NaN（7.1）。
2. 算术与逐元素函数：任一输入为 NaN 则结果为 NaN。
3. ★ **任何运算或算子产生 ±Inf 时，结果一律记为 NaN**，例如 `x / 0`、`log(0)`、溢出。pandas 会让 Inf 继续参与后续运算（例如 Inf 参与排名），本设计认为结果没有定义。
4. ★ 比较与逻辑运算采用三值逻辑：任一操作数为 NaN，结果是“布尔 NaN”；`where` 的条件为布尔 NaN 时，结果为 NaN。numpy 中 `NaN > 0` 为 false。
5. ★ **严格窗口**：时序算子的窗口内只要有一个 NaN，结果就是 NaN，不存在 `min_periods`。
6. 截面算子排除本截面里输入为 NaN 的标的，只在其余标的上计算（与 pandas 的 `groupby().rank()` 一致）。
7. `fill_nan`、`is_nan` 是仅有的两个能“吸收”NaN 的入口，由用户显式使用。
8. 写入时 NaN 为 null，与现有契约一致。

第 3、4、5 条是有意的语义收紧。因为回看是推导出来的（6.2），目标行用到的所有中间值都来自完整窗口，所以**在数据完整时，这三条不影响目标行的结果**。只有以下情况会与旧结果不同：

| 场景 | 旧（pandas） | 新 |
|---|---|---|
| 新上市标的的头几期 | `min_periods=1`，照样出数 | null |
| 窗口内有缺失的 K 线 | 按“最近 N 行”计算，跨过空洞 | null（另由空洞检查上报为 `gap_subjects`） |
| 分母为 0 等退化窗口（例如价格连续 20 根不变时 `ts_std` 为 0） | 可能出现 Inf，并带着 Inf 参与排名后得到一个数 | null |

### 4.5 截面分组

截面算子按 `(data_time, series_tag)` 分组：同一时刻、同一序列标签的全部标的构成一个截面。不同 `series_tag`（例如不同交易所）不会混在同一个截面里排名。截面的成员是本期可用的标的（与现有 `available_subjects` 同口径），再排除输入为 NaN 的标的。

## 5. 算子库

记号：`L(x)` 表示 x 在时刻 t 有效所需的行数（见 6.2）；`n` 为窗口。每个算子在注册表里登记签名、参数范围、回看规则、内核、朴素参考实现和中文文档。控制台的补全和函数说明从注册表生成（9.5）。

**逐元素**（回看取各参数的最大值）

| 算子 | 语义 |
|---|---|
| `+ - * / % **` | 算术；`**` 的底数为负且指数非整数时为 NaN |
| `abs sign sqrt exp log` | `log(x≤0)`、`sqrt(x<0)` 为 NaN |
| `power(x, y)`、`signed_power(x, e)` | `signed_power = sign(x) · |x|^e` |
| `max(a, b)`、`min(a, b)` | 二元取大 / 取小，NaN 传播（不同于 `np.fmax`） |
| `clip(x, lo, hi)` | 截断到 [lo, hi] |
| `where(c, a, b)` | 条件选择（4.4 第 4 条） |
| `fill_nan(x, v)`、`is_nan(x)` | 显式处理 NaN |

**时序**（每条序列独立计算，窗口为当期及之前共 n 个网格点）

| 算子 | 回看 | 语义（pandas 参照，均为严格窗口） |
|---|---|---|
| `delay(x, k)` | L(x)+k | `shift(k)`，k ≥ 1 |
| `delta(x, k)` | L(x)+k | `x - shift(k)` |
| `pct_change(x, k=1)` | L(x)+k | `x / shift(k) - 1`，分母为 0 时为 NaN |
| `ts_sum` `ts_mean` `ts_min` `ts_max` `ts_product`（x, n） | L(x)+n−1 | `rolling(n)` 对应的聚合 |
| `ts_std` `ts_var`（x, n） | L(x)+n−1 | ddof=1，n ≥ 2 |
| `ts_zscore(x, n)` | L(x)+n−1 | `(x − ts_mean) / ts_std`，标准差为 0 时为 NaN |
| `ts_rank(x, n)` | L(x)+n−1 | `rolling(n).rank(pct=True)`：当期值在窗口内的百分位，并列取平均名次 |
| `ts_quantile(x, n, q)`、`ts_median(x, n)` | L(x)+n−1 | `rolling(n).quantile(q)`，线性插值，0 ≤ q ≤ 1 |
| `ts_skew` / `ts_kurt`（x, n） | L(x)+n−1 | pandas 的无偏偏度（n ≥ 3）与超额峰度（n ≥ 4） |
| `ts_argmax` / `ts_argmin`（x, n） | L(x)+n−1 | 极值距今的根数（0 表示当期）；并列取最早的一根（`n − 1 − np.argmax`） |
| `ts_corr` / `ts_cov`（x, y, n） | max(L(x),L(y))+n−1 | `rolling(n).corr/cov`，cov 取 ddof=1；任一方标准差为 0 时 corr 为 NaN |
| `ts_decay_linear(x, n)` | L(x)+n−1 | 线性衰减加权，最新一根权重为 n，最老一根为 1 |
| `ts_count(c, n)` | L(c)+n−1 | 窗口内条件为真的个数 |
| `ts_slope` / `ts_rsquare` / `ts_resi`（y, n） | L(y)+n−1 | 对时间序号 1..n 做最小二乘：斜率、R²、当期残差（Qlib 口径），n ≥ 2 |
| `ema(x, n)` | L(x)+K−1 | 截断到 K 根的 `ewm(span=n, adjust=False)`，α = 2/(n+1)，见下文 |
| `sma(x, n, m)` | L(x)+K−1 | 国君 SMA，截断到 K 根的 `ewm(alpha=m/n, adjust=False)`，0 < m < n |

**递归算子按固定长度截断**：`ema` 与 `sma` 本来的记忆是无限长的，结果取决于递推从哪里开始。本设计把它们定义成**每个时刻只看自己最近 K 根的固定窗口算子**：

```text
K   = ⌈ln(1e−9) / ln(1 − α)⌉            （ema(x, 20) 时 K = 208；sma(x, 20, 1) 时 K = 405）
y_t = 在 [t−K+1, t] 上以 x_{t−K+1} 为初值递推得到的值
    = (1−α)^(K−1) · x_{t−K+1} + Σ_{j=0}^{K−2} α(1−α)^j · x_{t−j}
```

- 窗口内有 NaN 时结果为 NaN（严格窗口）。
- 同一时刻的值不随需求区间、补算分块、是否与其他因子共享而变化（满足下面的“点纯”要求）。实现按上面的加权和计算，每点 O(K)。
- 与 pandas（从全部历史开始递推）相比，差异来自被截掉的部分，其权重不超过 1e−9。

**截面**（每个 `(data_time, series_tag)` 截面独立计算，回看为 L(x)）

| 算子 | 语义 |
|---|---|
| `cs_rank(x)` | 截面百分位 `rank(pct=True, method="average")`，即名次 / 有效样本数 |
| `cs_zscore(x)` | `(x − mean) / std`（ddof=1）；样本数少于 2 或标准差为 0 时为 NaN |
| `cs_demean(x)` | `x − mean` |
| `cs_scale(x)` | `x / sum(|x|)`；分母为 0 时为 NaN |

`cs_rank` 采用 pandas 口径（单样本为 1.0），与策略 DSL 的 `rank`（单样本为 0.5）不同，在函数文档里写明。

### 5.1 点纯性（硬性要求）

**任何算子在时刻 t 的输出，只能由它在 t 时窗口内的输入决定，并且按固定的顺序计算**，与以下因素无关：需求区间从哪里开始（6.4）、补算怎样分块、节点是否被别的因子共享、跳过恢复只算了哪几个因子、工作线程数。

理由：同一个因子会在不同的上下文中计算——实时周期计算整个集合，跳过恢复（`FillOnly`）只计算相关的因子，补算按分块计算，共享子表达式会改变节点的需求区间。如果结果依赖上下文，会出现两类问题：
1. 离散算子翻转：例如 `where(ema(x, 20) > 0, 1, 0)`，如果 EMA 的递推起点随共享关系变化，接近 0 的值可能在一个上下文里是正数、在另一个上下文里是负数；`ts_rank` 遇到本应相等的值时，也可能因为末位不同而改变名次。
2. 同一份输入、同一个定义，算出的结果不能稳定复现，验收与排查都无从下手。

因此，**不允许使用跨点延续状态的滑动累加器**（它的舍入误差取决于从哪里开始累加）。

### 5.2 数值实现要点

- **求和类**（`ts_sum`、`ts_mean`、`ts_var`、`ts_std`、`ts_zscore`、`ts_corr`、`ts_cov`、`ts_skew`、`ts_kurt`、`ts_slope` 等）：
  - 窗口不超过 256 时，每个输出点在自己的窗口上从最老到最新直接计算（求和用 Kahan 补偿；方差、协方差用两遍法：先求均值，再累加离差）；
  - 窗口更大时，按**绝对周期序号**对齐、每 64 个周期切一块：块内的部分和（计数、均值、离差平方和）按固定顺序算好，窗口值 = 头部零散段 + 中间完整块（按 Chan 的合并公式依次合并）+ 尾部零散段。块边界只取决于绝对时间，不取决于需求区间，所以仍然是点纯的；每点的代价约 O(w/64 + 64)。
- **常数窗口**：窗口内的值全部相同时，均值直接取这个值，方差、标准差取精确的 0（与 pandas 的处理一致）。否则舍入会让常数窗口的标准差变成 1e−17 这样的极小正数，`(x − m) / s` 就会得到一个看似正常的数，而不是 NaN（价格连续不变在冷门币的 1 分钟线上很常见）。
- `ts_min` / `ts_max` 用单调队列：极值是精确的，与起算位置无关，满足点纯。
- `ts_rank`、`ts_quantile`、`ts_median`、`ts_argmax`、`ts_argmin`、`ts_count`、`ts_decay_linear`：每个输出点直接扫描自己的窗口。
- `ema` / `sma`：按截断后的加权和计算，权重向量在编译期按 (α, K) 算好，所有点共用。
- 每个内核都有一份按定义直接计算的朴素参考实现，用于模糊测试（12.1）。

## 6. 编译

### 6.1 流程

```text
spec ──► YAML 解析 ──► 参数展开 ──► 每条表达式解析、白名单检查
     ──► 名称解析、let 内联、常量折叠、类型检查
     ──► 规范化的表达式树（每个输出一棵）
     ──► 推导：输入列、回看、因子类型
     ──► 规范文本（用于 definition_hash，9.3）
```

集合程序：引擎把一个因子集里全部启用因子的表达式树合并成一个 DAG。节点按规范键（算子名 + 子节点的规范键 + 常量参数）做哈希合并，**相同子树只计算一次**（例如 Bias、BiasQ、ZscoreAbsMeanQ 共用的 `ts_mean(close, 20)`）。截面节点同样可以共享，因为它的值不依赖于是哪个因子在用它（7.3）。

### 6.2 回看推导

对每个节点自底向上计算 L：输入列为 1；常量为 0（不构成约束）；逐元素运算取各参数的最大值；其他算子按第 5 节的规则。因子的回看 = 各输出 L 的最大值（至少为 1）。用现有 11 个因子核对，推导结果与 catalog 里手填的值全部一致：

| 因子 | 表达式（window = 20） | 推导 | 手填 |
|---|---|---|---|
| Bias | `close / ts_mean(close, w)` | 1+19 = 20 | 20 |
| BiasQ | `ts_rank(close / ts_mean(close, w) - 1, w)` | 20+19 = 39 | 39 |
| Cci | `(tp - m) / (0.015 * ts_mean(abs(tp - m), w))` | 20+19 = 39 | 39 |
| MinMax | `(tp - ts_min(tp, w)) / (ts_max(tp, w) - ts_min(tp, w)) - 0.5` | 20 | 20 |
| QuoteVolumeMean | `ts_mean(quote_volume, w)` | 20 | 20 |
| QuoteVolumeMeanQ | `ts_rank(ts_mean(quote_volume, w), w)` | 39 | 39 |
| VolumeMeanQ | `ts_rank(ts_mean(volume, w), w)` | 39 | 39 |
| ZfAbsMean | `ts_rank(ts_mean(where(pct_change(tp) > 0, amp, 0), w), w)` | 2+19+19 = 40 | 40 |
| ZfMeanQ | `ts_rank(ts_mean(amp, w), w)` | 39 | 39 |
| ZfStd | `ts_std(where(pct_change(close) > 0, amp, -amp), w)` | 2+19 = 21 | 21 |
| ZscoreAbsMeanQ | `ts_rank(ts_mean(abs((close - m) / s), w), w)` | 20+19+19 = 58 | 58 |

（`tp = (high + low + close) / 3`，`amp = (high - low) / open`，`m`、`s` 为 `close` 的 20 期均值与标准差。）

回看超过 5000 时拒绝。引擎从 PrimaryStore 读窗口，不受 View 保留行数的限制；设上限是为了约束预热和补算的读取量（每个标的每次预热都要读满一个回看窗口），5000 也与时序 View 默认保留的根数一致，再长的窗口算出的结果在 View 里也没有对应的历史可供策略回看。

### 6.3 推导出的元数据

| 元数据 | 推导方式 |
|---|---|
| `input_columns` | 所有被解析为输入列的标识符，去重排序 |
| `outputs` | 展开后的输出列名，保持 spec 中的顺序 |
| `lookback_periods` | 6.2 |
| `factor_type` | 3.4 |

这些元数据不落库，与 `definition_hash` 一样在读取时由编译派生。管理端与引擎各自编译，结果一致（同版本）。

### 6.4 需求区间

计算前先自顶向下传播每个节点“需要哪些行”：输出节点需要目标行 `[s, e]`；时序算子把自己的需求区间向前扩展 n−1（`delay` 扩展 k，递归算子扩展 K−1）后传给子节点；逐元素与截面算子原样传递；同一节点被多处引用时取并集。

执行时，每个节点只在自己的需求区间上计算。实时周期只需要最后一行，所以每个节点的工作量正比于窗口长度，而不是整个回看窗口；补算的需求区间是“分块的目标区间 + 前置回看”。实时与补算共用这一套机制，不需要两条代码路径。

需求区间只决定**算哪些点**，不影响任何一个点的值：由于全部算子都满足点纯性（5.1），同一个点无论在哪个需求区间里算，结果都逐位相同。

### 6.5 诊断信息

编译错误一律给出中文原因，以及定位：`outputs.cci` 或 `let.tp`，加上表达式内的行、列。管理端在保存时就返回这些错误（9.4），不需要等到引擎运行。

## 7. 执行

### 7.1 面板

由 `pipeline.Load` 读到的各标的窗口（`storageio.Frame`）构建列式面板：

- **时间网格**：用周期时钟生成，实时周期为 `clock.Window(target, freq, 集合回看)`；补算为“分块起点前的回看 + 分块目标区间”。只支持连续周期日历（目前仅 `crypto`），与现状一致。
- **序列**：每个 (标的, `series_tag`) 是一条序列，按 (标的, 标签) 排序，结果与工作线程数无关。
- **列**：集合内全部因子的输入列的并集，每列一个 float64 数组，按序列优先排列（同一序列的值连续存放），长度 = 序列数 × 网格长度。
- 源行里的 null、网格上缺失的行都是 NaN；非数值值在构建时报错，该集合本期按计算失败处理（入成员时已校验列类型，正常情况下不会出现）。

在网格上计算，“最近 n 根”就是“最近 n 个周期”，与现有“回看周期按不同的 `data_time` 计数”的口径一致；缺失的 K 线天然变成 NaN，经严格窗口传播到受影响的输出。所以，即使空洞检查关闭，也不会把跨过空洞的窗口算成一个看似正常的数。

### 7.2 求值

- 按 DAG 的拓扑顺序逐节点计算。一个节点处理完全部序列后，再进入下一个节点。
- **缓冲区**：每个节点的结果数组**按它自己的需求区间分配**（序列数 × 需求区间长度），而不是按整个面板。实时周期里输出节点的需求区间只有目标时刻一行，即使集合回看很长，大量输出节点也只占“序列数 × 1”；只有被长窗口算子引用的中间节点才需要长缓冲区。缓冲区取自缓冲池；编译时算出每个节点的最后一个使用者，用完立即归还；输出节点的缓冲区保留到取结果之后。
- **并行**：时序节点和逐元素节点按序列分块，截面节点按时间点分块，分给固定的 `compute.workers` 个 goroutine（默认 min(4, 核数)）。
- **确定性**：每个输出值只由一个 goroutine 按固定顺序计算，没有跨块的并行归约；再加上点纯性（5.1），同一个 (因子, 标的, 周期) 的值与工作线程数、调度、集合里还有哪些因子、补算分块、实时还是恢复都无关，逐位相同。实时周期写入的提交 ID 是内容摘要，重投时需要逐位相同才能去重，因此确定性是硬性要求。
- **取消**：每个节点开始前检查 `ctx`，周期预算超时后尽快停止。

### 7.3 截面算子、全集与空洞

- 截面的成员是本期 `available` 的标的：预热中、上游失败、读取失败的标的不进入面板（与现状一致）。
- 截面算子跳过输入为 NaN 的标的。由于空洞会让受影响窗口上的值变成 NaN，一个标的在某个截面时刻 τ 是否参与，只取决于**这个节点的输入在 τ 时是否完整**，与是哪个因子、哪个目标周期在使用它无关。因此截面节点可以跨因子共享，补算时也可以一次算出全部目标周期。
- 与旧实现的差异：旧实现对“允许部分全集”的截面因子，把在该因子整个回看窗口内有空洞的标的，从这个目标周期的整块面板中剔除；新实现只在该标的输入确实不完整的那些截面时刻剔除它。新口径只用完整的数据参与排名，更准确。生产目前没有截面因子，不影响现有结果。
- 因子级的判断保持不变，仍在流水线里完成：严格截面因子（`allow_partial_universe=false`）本期全集不完整、或有标的有空洞时，整因子跳过（实时）或该周期跳过（补算）；空洞标的的结果按失败处理，并记入 `gap_subjects`。

### 7.4 结果

执行器返回**列式结果**，不再转换成 Python 时代逐行的 `[][]any`：每个输出列一个 float64 数组，覆盖“序列 × 目标时刻”，外加一份有源行的位置掩码。组装直接按 (序列, 目标时刻) 读取这些数组：只在网格上**有源行**的目标时刻产生结果（与现在“结果行以源行为准”的口径一致）；目标时刻缺源行的情况由现有的空洞失效逻辑处理（读出已有结果键并写 null）。

新实现的输出键恒等于源行的 `(data_time, series_tag)`，**不再支持因子输出派生的 `series_tag`**（Python 契约允许，但生产因子没有用到），组装中相应的分支一并删除。

### 7.5 内存

实时周期、补算和跳过恢复使用同一套估算。实时周期只有一个目标时刻，且缓冲区按需求区间分配（7.2），正常规模下只有几十 MB；但长窗口（例如 `ts_mean(close, 1440)`）的中间节点仍要“序列数 × 1440”的缓冲区，所以实时周期同样做预检。

一个分块（实时周期视为只有 1 个目标周期的分块）的峰值内存按**完整的生命周期**估算，而不只是计算阶段：

| 阶段 | 估算 |
|---|---|
| 读取 | 源窗口（`storageio.Frame` 的行式数据）：序列数 × (分块周期数 + 回看) × 输入与携带列数 × 每格的实测开销 |
| 计算 | 面板（序列数 × 网格长度 × 输入列数 × 8 字节）+ 任一时刻同时存活的节点缓冲区之和（每个节点为序列数 × 自己的需求区间长度 × 8 字节，按拓扑顺序与最后使用者精确计算） |
| 结果 | 列式输出：序列数 × 分块周期数 × 输出列数 × 8 字节 |
| 组装与写入 | 待写入的行与字段：序列数 × 分块周期数 × (输出列数 + 携带列数) × 每个字段的实测开销 |

- **在读取之前**决定分块大小：取配置的 `recalc.chunk_periods` 与“估算峰值不超过 `compute.max_memory`（默认 1GiB）的最大周期数”中较小的一个，并在日志中记录调整后的分块大小。上表的“每格开销”在执行计划阶段 5（引擎接入）用基准实测后写成常量，带一定余量。
- 输出列很多的集合，分块会相应变小。例如 300 个输出、500 个标的时，每块大约几十个周期；补算变慢，但内存有上界。
- 只算 1 个周期仍然超限时，补算任务以资源错误失败（错误信息写明估算值与上限），不会尝试执行；实时周期则该集合本期按计算失败上报，并输出 ERROR 日志。正常规模下不会出现，出现时说明集合里的因子需要拆分。
- 验收检查真实的内存峰值（`runtime/metrics` 采样或基准测试中的 `MemStats`），不只核对估算公式。

### 7.6 错误

- 引擎侧编译失败（理论上只在 mgr 与引擎版本不一致时出现）：该因子本期对全部标的失败，错误原因写入运行摘要；其他因子不受影响。
- 内核 panic：在集合级 `recover`，该集合本期全部因子按计算失败处理（与现在 Python 批次崩溃的处理一致），并输出 ERROR 日志。正常情况下不应出现，由模糊测试保证。

### 7.7 性能指标

| 场景（在 192 上测量） | 目标 |
|---|---|
| 1m 集合，500 标的 × 现有 11 个因子，实时一期的计算阶段 | ≤ 20ms |
| 500 标的 × 合成的 300 个因子（参照 Alpha101 的结构混合），实时一期 | ≤ 500ms |
| 补算一个分块（500 期 × 500 标的 × 11 个因子） | ≤ 2s |
| 引擎进程线程数 | ≤ 150，没有子进程 |

`packages/factorexpr` 内放基准测试，执行计划中的验收会在 192 上复测。

- `name` 不再是 Python 模块名，放宽为展示名：1～64 个字符，不含控制字符，首尾无空白。
- `ValidateMembership`：在现有检查之上，增加输入列必须是数值类型（Storage 列元数据的 `ValueType`），以及 `let` / `params` 名称不能和源列重名。
- 删除 `catalog.SourceChecker` 与 `pyexec.ValidateSource*`：编译就是校验，管理端不再启动任何子进程。

### 9.3 definition_hash 与语义版本

```text
definition_hash = sha256("definition-v2" \0 expr 语义版本 \0 规范程序文本 \0 allow_partial_universe)
```

- **规范程序文本**：参数展开、`let` 内联、常量折叠之后，按输出顺序写出的“输出名 = 规范表达式”。只改注释、格式或 `let` 变量名不会改变哈希；凡是影响计算结果的改动都会改变哈希。输入列、回看、类型都是程序的函数，自然包含在内。
- **expr 语义版本**（例如 `expr/1`）：任何算子的语义发生变化（包括修正数值行为）时递增。版本变化会让全部因子的哈希变化，策略据此识别“因子变了”（`skipped(factor_changed)`）。只做性能优化、不改变结果时不递增。
- 管理端与引擎各自计算哈希。版本不一致时，引擎上报的哈希与管理端不同，策略会跳过并提示重新启用。这是安全的失败方式，但会造成中断，所以**管理端与引擎必须同版本发布**。
- Storage 标记与事件中的 `FactorPeriodState.source_hash` 字段保留，改填 `spec_hash`，不改 Storage 协议（[Storage 去业务耦合设计](Storage去业务耦合设计.md)以后会整体调整这部分）。

### 9.4 接口（`modules/factor/proto/factor.proto`）

- `FactorDef`：删除 `source_code`、`source_hash`、`params_json`；新增 `spec`、`spec_hash`；`factor_type`、`input_columns`、`outputs`、`lookback_periods`、`definition_hash` 改为只读的派生字段（写请求中忽略）。`ListFactors` 的 `include_source` 改名为 `include_spec`。
- 字段编号：`factor_id`（1）、`definition_hash`（15）等保留的字段不改编号，新增字段使用新的编号。策略模块（`modules/strategy/internal/input/client.go`）通过 `GetFactor` 只读取这两个字段，因此不需要随因子模块一起发布。
- `FactorPeriodState`（心跳）：`source_hash` 改名为 `spec_hash`。
- `EngineStatus`：见第 8 节。
- 新增三个方法：

## 12. 数值一致性与验证

Python 直接删除、不并行运行，因此一致性必须在删除前离线验证完毕。

### 12.1 算子级

- **参考实现对照**：每个算子的高效内核都要和朴素参考实现做随机对照（Go 原生模糊测试），覆盖随机长度、随机窗口、NaN 分布、并列值、常数序列、极大极小量级，以及不同的需求区间起点。
- **pandas 锚点**：为每个算子生成一小组 pandas 计算的期望值（JSON），固化 ddof、并列名次、分位插值、偏度峰度的偏差修正、`ewm(adjust=False)` 等口径。生成脚本作为开发工具放在 `packages/factorexpr/testdata/golden/` 下（README 写明 pandas 版本）；CI 只读取已提交的 JSON，不需要 Python。
- **确定性**：同一输入在 1、2、8 个工作线程下的结果逐位相同。
- **点纯性**（5.1）：同一个点的值在以下各种上下文中逐位相同——单独计算与和其他因子共享节点计算；不同的需求区间起点；不同的补算分块边界；实时（只算最后一行）与补算（算整段）。递归算子、求和类算子的大窗口分块实现必须单独覆盖。

### 12.2 因子级（与 Python 并排计算）

Python 删除前，必须用线上真实数据证明新实现与现有 pandas 因子一致。**基准不取线上已经写入的结果，而是让现有的 Python 计算路径与新引擎读同一份窗口、同时计算**，原因是已写入的结果无法可靠地证明来源：
- 已写入的 null 可能来自计算失败、预算超时或预热中跳过（`pipeline/assemble.go` 先预置 NULL，`compute.go` 超时也走这条路径）；
- 补算会覆盖已有结果，却不更新周期标记（`pipeline/report.go`），标记里的失败名单与定义哈希不能证明当前的值是谁写的；
- 读取周期标记必须提供 `trigger_event_id`，它包含采集事件载荷的哈希，无法从集合与周期时间推导，Storage 也没有按时间范围列出标记的接口。

**工具**：只读子命令 `moox-factor-engine compare`，**在现有代码上实现**（执行计划阶段 3），此时 Python 计算路径（`pyexec`、旧的 `pipeline.Compute`）都还在：

| 输入 | 来源 |
|---|---|
| 配置 | 现有的 `config/engine.yaml`，原样使用（此时配置解析器仍是旧的，`python:` 段有效） |
| 因子集与旧定义 | `--set-file <文件>`：引擎目录快照 `data/engine/catalog.json` 的副本，其中有因子集、启用成员与 Python 源码 |
| 新定义 | `--library <目录>`：YAML 因子库，按 `factor_id` 对应 |
| 区间与范围 | `--start`、`--end`，可选 `--factors`、`--subjects`；`--python-workers`（默认 4） |
| 临时目录 | `--work-dir`：旧源码落盘与输出摘要的位置，不使用引擎的状态目录 |

执行过程（按补算的分块与读取节流）：
1. 对每个分块构造与补算相同的计划，调用现有的 `Runner.Load` 读窗口（只读；`GapSink` 置空，不记账本）；
2. 同一份 `LoadResult`：一份交给现有的 `Runner.Compute`（Python 进程池，只启动 `--python-workers` 个）得到基准，一份构建面板交给 `factorexpr` 得到新结果；
3. 逐个 (因子, 标的, 周期, 标签) 比较。不调用组装、写入、上报，不同步目录，不访问 mgr，不写 Storage。

**输出**：两边都有值时的相对误差分布（最大值、p99.9）；离散跳变（`ts_rank` 等相差至少 1/n）的个数；“旧有值、新为 null”与“旧为 null、新有值”的个数，并按原因归类（窗口内有空洞、新上市头部、分母为 0 或常数窗口、其他）；Python 侧计算失败的个数与原因。

**验收标准**（4 个因子集，每个至少核对最近 3 天）：
1. Python 侧计算失败为 0；如有，逐个说明原因（例如超时），排除后不影响其余判定；
2. 两边都有值时，连续值相对误差 ≤ 1e−9（分母取 max(|旧值|, 1e−12)）；
3. 离散跳变比例 ≤ 1e−4，并且抽查确认都是由浮点末位误差引起的并列翻转；
4. “旧有值、新为 null”全部能归入 4.4 列出的三种场景；
5. “旧为 null、新有值”的个数为 0。

**Python 删除之后**：引擎接入新执行器时（执行计划阶段 5），`compare` 的 Python 基准模式随旧计算路径一起删除，保留“与已写入结果对比”的诊断模式（`--baseline stored`）。它不作为验收依据，只用来排查：例如切换后核对新引擎写入的几期，以及以后修改算子实现时对比新旧结果；报告中的差异需要结合当期运行摘要（失败、预热、空洞）判断。

### 12.3 流水线级

- 现有 `pipeline` 测试（周期端到端、补算、空洞、预热、恢复）全部改用新的执行器后通过。
- 新增截面因子的端到端测试：部分全集、严格全集、带空洞，以及补算多周期。
- 同一 (因子, 标的, 周期) 经实时周期、补算（不同分块）、跳过恢复（`FillOnly`，只算相关因子）三条路径写出的值逐位相同。
- 内存：补算用 7.5 的方式估算并调整分块后，实测峰值不超过 `compute.max_memory`；实时周期在“共享的长窗口节点 + 大量不同输出”（例如 300 个 `ts_mean(close, 1440) + i`）下，实测峰值与按需求区间分配的估算一致。

## 13. 迁移与切换

### 13.1 现有因子

现有 11 个因子按 6.2 表中的表达式改写成 YAML，**`factor_id` 与输出列名保持不变**。这样结果数据集的列（`origin_id = factor_id`）、View 的列，以及策略 DSL 引用的列名都不受影响。`definition_hash` 会变化，因此：
- 引用了这些因子的策略实例会在下一期报 `skipped(factor_changed)`，切换后需要逐个重新启用；
- 不需要重算历史：差异只在浮点末位，以及 4.4 列出的场景。

### 13.2 数据库迁移

`moox-factor-mgr-cli` 新增一次性命令 `migrate-expr --library <目录>`，在 mgr 停止时执行，按 SQLite 官方的“重建表”步骤进行：

1. 迁移前自动把数据库文件复制为 `factor.db.bak-<时间>`；
2. 在事务开始**之前**执行 `PRAGMA foreign_keys = OFF`（SQLite 不允许在事务内切换这个开关）；
3. 开始事务，建新表 `t_factor_defs_v2`；
4. 对旧表的每一行，在因子库中按 `factor_id` 找到对应的 spec 并编译。要求展开后的输出列与旧行完全一致，推导出的回看与旧值一致（作为健全性检查）；任何一行找不到 spec 或不一致，就回滚并中止；
5. 写入新表，删除旧表，把新表改名为 `t_factor_defs`；
6. 执行 `PRAGMA foreign_key_check`，确认成员表的外键全部能对上，然后提交；最后恢复 `PRAGMA foreign_keys = ON`；
7. 再次运行就是空操作：检测到已经是新表结构时直接退出。

成员、因子集、补算任务等不变。迁移不经过 API，所以不会触发“启用成员即补算”的回填。

### 13.3 切换时的注意事项

- 跳过账本：未完成的待恢复条目带着旧的 `definition_hash`，新引擎回放时会按“定义已变更”记为 `cancelled`。切换前确认 `factor_gap_pending` 为 0；不为 0 时，等它恢复完再切换，或者切换后对这些区间手工补算。
- 补算任务：切换前确认没有 `running` 的补算任务。
- 引擎本地状态：删除 `data/engine/catalog.json`（旧格式的快照）与 `data/engine/factors/`（旧的源码落盘目录），新引擎启动后立即从 mgr 同步。
- 引擎重启时间：按惯例放在整点后 :02～:10，避开 1h 集合的整点。
- 发布顺序与回滚步骤见执行计划。回滚依赖切换前备份的旧二进制、旧 venv 安装目录与 `factor.db` 备份，这些备份在验证完成前不删除。
- **回滚时区分程序与运行账本**：切换后新引擎首次预热、遇到空洞，会在 `data/gap` 中记下新的待恢复条目（带新的 `definition_hash`）。回滚时只还原程序、venv 和配置，`data/gap` 保留当前内容（审计记录完整）；旧引擎回放时会把这些新哈希的条目记为 `cancelled`，所以回滚前要先把它们导出（集合、因子、标的、周期区间），回滚后用**旧版** `moox-factor-mgr-cli recalc` 手工补算这些区间并核对结果（`recalc` 会读取本地配置并直接打开 `factor.db`，新版 CLI 不接受旧配置与旧表结构，所以旧版 CLI 也要随回滚一起还原）。新引擎已经写入的结果与旧实现只有末位差异，不需要重算。

## 14. 风险与取舍

| 风险 | 影响 | 应对 |
|---|---|---|
| 数值口径与 pandas 有细微差别（并列、ddof、插值、Inf） | 新旧结果不一致 | 12.1 的锚点固化口径；12.2 按线上真实数据验收；Inf 等有意的差异在 4.4 中列明 |
| 离散算子放大末位误差 | 个别 `ts_rank` 结果相差一档 | 验收时单独统计离散跳变；常数窗口精确处理（5.2），保证本应相等的值严格相等 |
| 结果依赖计算上下文（共享、分块、需求区间） | 同一定义在不同路径下算出不同的值，离散算子翻转 | 点纯性作为硬性要求（5.1），递归算子按固定长度截断，禁止跨点的滑动累加器；12.1、12.3 覆盖各种上下文 |
| 补算的行式组装占用过多内存 | 输出很多的集合在补算时内存失控 | 列式结果；按完整生命周期估算、读取前决定分块；最小分块仍超限时以资源错误失败（7.5） |
| 表达能力不足（个别因子写不进 DSL） | 需要扩展算子 | 新增算子只需在注册表登记内核、参考实现、锚点和文档；没有 Python 兜底，这是已确认的取舍 |
| 管理端与引擎版本不一致 | 引擎编译失败，或哈希不同导致策略跳过 | 同版本发布；引擎在心跳中上报自己的 expr 语义版本，管理端在状态中显示不一致 |
| 递归算子的回看变长（`ema`、`sma` 需要两三百期） | 预热读取量变大 | 只影响用到这些算子的集合；窗口缓存只增量读取；回看上限 5000 |
| 严格窗口让新上市标的在回看期内的因子值为 null | 策略把它们当作缺数；若策略的 `min_age_bars` 小于因子回看，可能计入 `max_missing` | 在因子与策略文档中写明“`min_age_bars` 应不小于所引用因子的回看”；控制台的因子详情展示回看 |
| 截面口径从“按目标周期剔除”改为“按截面时刻剔除” | 部分全集截面因子的结果与旧实现不同 | 生产没有截面因子；新口径更准确，并在因子文档中写明 |

## 15. 以后再考虑

- **跨因子共享宏**（全局复用 `tp`、`amp` 等）：宏的变化会让引用它的全部因子的哈希一起变化，需要把宏纳入哈希与版本管理，本期不做。同一集合内相同的子表达式已经由 CSE 自动共享。
- **分组中性化**（`group_neutralize` 等）：等有了板块 / 分类数据再加。
- **增量计算**：只有在秒级或逐笔场景下才需要。
- **因子挖掘**：表达式树天然可以作为遗传规划的基因，本期不做。
- **存储写入宽度**：因子增长到几百个后，每期 `WriteFactorRows` 的数据量和结果 View 的列数都会成倍增加，需要和存储一起评估是否按主题拆分因子集。读取不受影响。
- **空洞检查开关**：网格上的严格窗口已经能在数值上挡住空洞，`gap.enabled` 以后可以考虑固定开启并删除这个开关。
