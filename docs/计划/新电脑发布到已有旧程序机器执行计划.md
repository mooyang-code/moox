# 新电脑发布到已有旧程序机器执行计划

执行计划 v5（2026-10-31，尚未编码），基线 `feat/init-page-polish2@8a199907`（还没合入 main）。
这个分支也改了 `skills/moox/references/install.md`，应先合并它，再从 main 开新分支。
v4 按实际场景收窄范围：第一版只做“彻底清空后全新发布”这条主线，接管推迟到第二版，修复现有生产移出本计划。
v5 吸收独立审查：补强 `setup wipe` 的删除保护、停止方式和重跑，细化 `route` 判定，云函数第一版交给用户清理，重新分批上线 skill 改动。

## 1. 背景与目标

场景：用户在**一台新电脑**的 Agent 里，通过 skill 把 MooX 发布到目标机器，而**目标机器上有旧程序在跑**。
新电脑的特点是本机什么都没有：没有 `moox.toml`、状态目录、操作员身份和 `~/.moox-release.env`，也不一定和因子机在同一网络。

2026-10-31 用 v0.4.1 实际走了一次：`setup validate` 全绿，Agent 按空机安装，到 `setup bootstrap` 才发现机器上已有部署。
将近一半的过程都在排查和绕路：目录权限报错没有路径，远端拒绝却提示重试，Agent 为了查原因去读线上密钥、手动执行远端程序、翻产物包源码，最后用脚本逐组件替换。

目标：

1. 发布前就知道每台机器的实际情况，不靠失败来发现。
2. 用户同意后，一次做完“彻底清空 + 全新发布”，全程用这次的新设置。
3. 常见失败都有明确原因和下一步，同一个错误不反复重试。
4. Agent 不需要读线上密钥、手动执行远端程序或翻源码。

## 2. 决定

| 项目 | 决定 |
| --- | --- |
| 第一版主线 | 新电脑 + 已有旧部署 + 用户同意彻底清空 + 全新发布 |
| 彻底清空 | 删除 `moox.toml` 列出的主机上 MooX 的全部程序、数据和服务项，包括部署根内全部内容、`import`、归档目录和外部程序目录，不保留任何旧数据 |
| 不动的内容 | 部署根和预览列出的目录之外的文件；不在 `moox.toml` 里的主机 |
| 配置来源 | 全部用这次 `config init` 的新设置，不继承旧部署的配置、账号或身份 |
| 确认方式 | 只问一次，问题里写明主机、丢失内容和防火墙放行；同意后不再逐步确认。范围变大或发现实盘持仓时才重新询问 |
| 进程处理 | 部署根内的进程可以终止；部署根之外的进程只报告，不杀 |
| 云函数 | 第一版不由 CLI 清理，提醒用户到腾讯云控制台删除；自动清理放第二版 |
| 因子机不可达 | 只有“换到同一网络”一条路，不做“先不配、以后加回” |
| 操作机系统 | 第一版只支持 macOS 和 Linux |
| 保留数据 | 第一版走 `config restore`，并如实说明还不能做的事；`setup adopt` 放第二版 |
| 检测入口 | 扩展 `setup validate` 命令，不新增命令，也不改 `setup apply` 的校验路径 |
| 目录权限 | CLI 自动收紧自己的本机私有目录，报错带路径 |
| 远端失败 | 区分“SSH 断开”和“远端明确失败”，只有前者提示重试 |
| 身份安全 | 不放宽“不能替换已有部署身份”的规则 |
| 验证方式 | 不准备测试机，用自动化测试覆盖，第一次真实使用靠预览把关 |
| 现有生产 | 不在本计划内处理，也不对它执行 `setup wipe`，除非用户明确要求 |

## 3. 发布流程

```text
下载产物
  → 问用户：目标机器上有旧部署吗？要保留数据吗？
      要保留 → config restore（第 A7 节）
      不保留或不清楚 → config init → setup validate
                         route=fresh    → 确认部署计划 → 全新安装
                         route=resume   → 继续这台电脑上次没做完的首次安装，不询问清空
                         route=existing → setup wipe 预览 → 询问是否彻底清空
                                            同意 → setup wipe --yes --expect <摘要> → 全新安装 → 验收
                                            不同意 → 新 moox.toml 改名 → config restore
                         route=upgrade  → 询问是否彻底清空；不同意则按原电脑流程升级
                         route=blocked  → 说明原因，停下
```

要不要保留数据必须在填配置之前问：

- `config restore` 依赖旧管理台还在运行，清空之后就回不去了；
- 它不覆盖已有 `moox.toml`，所以用户中途改主意时要先把新文件改名；
- 用新配置升级旧部署走不通：CLI 会用 `moox.toml` 里的管理员账号登录（`command/setup.go:809`），新填的密码和旧部署可能不同。

## 5. 第 A 阶段：改 skill

分两批上线：

| 批次 | 内容 | 时机 |

第二批上线前，Agent 检测到旧部署时停下告诉用户，不手工清除。

### A1. 安全边界

`skills/moox/SKILL.md` 的“安全边界”增加：

- 不读取、不打印 `~/.local/state/moox/setup/`（请求文件含 SSH 私钥）、线上 `secrets/` 和 `identity/`；
- 不手工写入或恢复 `runtime-identity.json`、`core-ready.json`；
- 不在目标机器上手动执行 `moox-runtime bootstrap`；
- 不手工执行 `rm` 清除部署，只用 `setup wipe`（第二批）；
- 遇到这些情况就停下，带着现状和选项问用户。

**验收**：这次记录里的越界操作都能在 skill 里找到明确禁止条款。

### A2. 发布流程与询问

`skills/moox/references/install.md` 按第 3 节调整：下载后先问是否保留数据，`setup validate` 之后按 `route` 分流。

`route` 是 `existing` 或 `upgrade` 时，先跑 `setup wipe` 取预览，再这样问用户，不能只问“要覆盖吗”：

> 检测到这些机器上已经部署了 MooX：`<主机、IP、版本>`。
> 要彻底清空吗？清空会删除这些机器上全部旧程序和旧数据（K 线、因子、策略、任务、归档、历史导入包、交易记录、管理台账号与操作记录、管理台里保存的交易所密钥等、配置备份），然后用你刚填的初始化设置重新发布 `<版本>`，并在腾讯云防火墙放行 `<端口摘要>`。删除后无法恢复，配置备份也会一起删除。
> `<配置之外还有这些旧机器：……，不会被清理，上面的旧程序会继续运行>`
> 如果旧部署启用过云函数采集，请你到腾讯云控制台删除 `moox-fetch-plan-` 开头的函数；不删会继续运行并产生费用，以后启用云函数时同名函数也会创建失败。
> 不清空就保留全部数据，这次不发布新程序，改走恢复配置。

用户同意后执行 `setup wipe --yes --expect <摘要>`，再走全新安装，中途不再确认。

### A3. 报错速查表

扩充 `install.md` 的“常见问题”。

第一批（现版本成立）：

| 现象 | 含义 | 处理 |
| --- | --- | --- |
| `private material directory ownership or permissions are invalid` | 本机私有目录权限不对 | 检查 `~/.config/moox` 和状态目录，告诉用户需要收紧到 700 |
| `bootstrap observation failed` | SSH 断开，或远端明确拒绝 | 重试一次；仍失败时跟用户确认后，单次设置 `MOOX_SETUP_DEBUG_HELPER=1` 看原因，不手动上机执行 |
| `unit deployment requires the original core state directory…` | 这台电脑没有部署状态 | 目标机可能已有部署，停下问用户 |
| `unit deployment requires its original operator bootstrap pin` | 这台电脑没有操作员身份 | 同上 |
| `full control requires its original completed core receipt` | 本机没有安装记录 | 同上 |
| `existing deployment lacks its persistent runtime identity binding` | 旧部署缺少身份绑定 | 同上 |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | 系统 `known_hosts` 有旧记录，或机器确实换了 | 先跑 `setup validate`；通过说明 MooX 记录的指纹没变，不自己删记录，向用户说明 |

第二批（随 v0.4.2，同时删掉 `MOOX_SETUP_DEBUG_HELPER` 的用法，第一批的“停下问用户”改为“回到 `setup validate`”）：

| 现象 | 含义 | 处理 |
| --- | --- | --- |
| `route=blocked` | 属主或权限不符、端口被占用或有部署目录之外的旧进程 | 按输出的原因处理，不要继续安装 |
| `ssh_unreachable` 且是因子机 | 这台电脑和因子机不在同一网络 | 换到同一网络后重新运行 |
| `bootstrap observation failed` | SSH 断开（B2 之后的含义） | 用同样的参数重试一次 |
| 远端拒绝的错误码 | 机器不是空机 | CLI 会给出下一步，按提示处理 |

### A4. 排查规则

写进 `SKILL.md` 的“几条容易踩的规则”：

- 同一个错误重试一次还失败就停，不再重试；
- 先查速查表和诊断命令，不把产物包源码当主要排查手段；
- 路线走不通时停下问用户，不要自己绕路。

### A5. 部署计划一次确认

现在 `SKILL.md` 要求每条部署命令都先给用户确认，来回太多。改成把整条部署计划（主机、单元、顺序、防火墙放行内容）一次确认，确认后执行 `setup firewall --yes` 和各部署命令，过程中只在计划变化或失败时再问。

现在 `install.md:111` 的 `setup firewall` 没带 `--yes`，只预览不放行，一起改掉。用户同意彻底清空时，清除、防火墙和后续部署都算在这次确认内。

### A6. 下载失败自动切源

`install.md` 的下载片段：`curl` 加连接超时、重试和 `-C -` 断点续传，测速选中的源失败时自动换另一个。
先在 macOS 和 Linux 试跑。

### A7. 保留数据时怎么做

`install.md` 增加一节，第一版写清楚现状，不做承诺：

- 前提：旧管理台能打开，旧部署做过 `config backup`，并且知道**初始**管理员密码；
- 运行 `config restore` 取回配置；
- 取回后 `setup validate`、`setup firewall`、`config backup` 这类只靠 SSH、云密钥或管理台登录的命令有密钥就能用；`doctor`、`deploy-*` 依赖操作员身份和本机状态，仍不可用；SSH 密钥路径也要重新核对；
- 需要升级时优先回到原来部署的电脑操作；
- 原电脑已不可用时，告诉用户这种情况第一版不支持，等第二版的 `setup adopt`，或者选择彻底清空。

`native-release.md` 注明它面向维护者，不带配置改动，也不恢复 CLI 能力。

### A8. 配置完成的话术

`config init` 结束后，Agent 要立即告诉用户：配置已保存，页面可以关，之后不用重填。

### A9. 操作机系统

`install.md` 第 0 节改为第一版操作机只支持 macOS 和 Linux，用户用 Windows 时提前说明，不要走到部署才失败。

## 6. 第 B 阶段：改 CLI

### B1. 本机目录权限

- `unitdeploy/core.go` 的 `privateRoot`：目录属主是当前用户、不是符号链接、没有组和其他人写权限时，收紧到 0700；
- 其他情况不动目录，报错带路径和修复命令；
- `fsutil.OpenPhysicalRoot` 只改报错文案，不改校验，因为它也在远端使用；
- 配套测试：755 自动收紧、组可写拒绝、属主不符拒绝、符号链接拒绝。

**验收**：`~/.config/moox` 为 755 时 `setup bootstrap` 自动通过。

### B2. 远端失败给明确原因

- 给 `unitbootstrap` 现有的固定错误加稳定错误码，`moox-runtime` 失败时输出一行固定格式（只含错误码，不含动态内容）；
- CLI 只识别白名单内的错误码，配中文原因和下一步后显示，不开调试开关也能看到；
- 覆盖 `core.go:296`、`host.go:312`、`host.go:453`、`control.go:255`、`remote.go:105`、`external.go:164`；
- 用 `*ssh.ExitError` 区分：远端非零退出时带这个错误类型，连接断开时没有（`setup/ssh/client.go:550-554`）；
- 只有真正的 SSH 断开才提示重试，错误码之外的输出继续隐藏。

**验收**：故意制造 `narrow` 和身份不一致两种失败，CLI 直接显示原因和下一步，输出不含密钥。

### B3. `setup validate` 报告实际情况

**改动位置**：只在 `setup validate` 命令里增加部署检测，`setup apply` 调用的 `deps.validate` 不变。`SSHChecker` 只返回错误，要新增能读取结果的接口。

**只读**：检测不能建目录、不能生成密钥。比较身份哈希时不走 `loadIdentity`、`privateRoot`（它们会写文件），改成只读读取已有文件；文件不存在就算没有本机状态。

每台主机检测：

| 检测 | 方法 | 结果 |
| --- | --- | --- |
| 部署状态 | 见下面的 `empty` 定义 | `empty`、`installed`，已装时带发布 ID |
| 属主与权限 | 部署根属主等于 SSH 用户，`mode & 022 == 0`，复用 `targetFiles` 的规则；部署根不存在时上级目录要可写；部署根内有不属于 SSH 用户的文件时报告 | 不符就 `blocked` |
| 部署目录外的旧进程 | 读 `/proc/*/exe`，不用命令行匹配（会匹配到检测命令和 `~/moox-web`）。读不到 `exe` 的 `moox-` 进程按部署目录外处理 | 有就 `blocked` |
| 端口 | 端口来自 `servicecatalog` 的 `componentPorts`（要导出）、`manifest.EventBus.Port` 和 `[deployments]`；用 python3 读 `/proc`，不依赖 `ss` | 被非 MooX 程序占用就 `blocked` |

`empty` 的定义：部署根不存在或没有内容，**并且**没有 `# moox-watchdog` 的 crontab 行、没有两个外部程序的服务文件、`archive_root` 为空。半清的机器不算空机。

`route` 的判定按顺序：

| 值 | 条件 | Agent 怎么做 |
| --- | --- | --- |
| `blocked` | 有上表的阻塞项 | 说明原因，停下 |
| `existing` | 本机有 `wipe` 未完成标记（B4） | 重新运行 `setup wipe` |
| `fresh` | 全部主机都是 `empty` | 全新安装 |
| `resume` | 已有部署，本机身份哈希匹配，没有 `control-ready.json` | 继续这台电脑上次没做完的首次安装，不询问清空 |
| `upgrade` | 已有部署，哈希匹配，并且有 `core-ready.json`、操作员 pin 和 `units/*/*/operation.json` | 询问清空；不同意则升级 |
| `existing` | 其余已有部署的情况，新电脑都是这种 | 询问清空 |

`blocked` 时命令退出码非 0，其余为 0。

`setup bootstrap --stage core` 动手打包和上传前读取同样的判断：

- `fresh` 或 `resume` 才继续，其余立即停止并提示回到 `setup validate`；
- `fresh` 且本机有上次遗留的状态目录时，先改名为 `.bak-<时间>` 再继续，避免复用旧软件。

**验收**：测试覆盖全空机、全部已装、部分已装、半清的机器、首装做到一半、本机状态匹配但缺部署记录、哈希不一致、属主不同、部署目录外有进程、端口被占，并确认检测过程不产生任何文件。

### B4. 彻底清空：`setup wipe`

新增 `moox-cli setup wipe`。不带 `--yes` 只预览；执行时要求 `--yes --expect <摘要>`，摘要和当前预览不一致就拒绝，这也能防止跳过预览。

**预览内容**：

- 主机、发布 ID、各目录占用；
- 部署根顶层条目，标出不认识的条目；
- 外部程序的实际目录（读服务文件的 `ExecStart` 和 `WorkingDirectory`）；
- 归档的实际目录（读 `archive-worker/config/app.yaml` 的 `worker.root_dir`），和新配置不同时一并列出；
- 控制机 `t_hosts` 里有、但这次配置没有的旧机器。读取方式在编码时确定，优先用控制机上已部署的工具；读不到时标明“未能读取”，不阻塞；
- 范围摘要，由主机、路径和发布 ID 算出。

重跑时范围只会变小，变小不重新询问；范围变大才重新询问。

**删除保护**，`deploy_root` 和其他要清的目录都要通过，`fsutil.ValidateUnitRoots` 不算删除保护：

- 拒绝 `/`、`/data`、`/home`、`/root`、`/etc`、`/usr`、`/var`、`/opt`，以及 `$HOME` 和它的上级目录；
- 部署根必须能看到 MooX 标记（`run/host.json`、`host/current`、`identity`、`bootstrap` 之一）；半清重跑时靠未完成标记放行，且主机地址和部署根都要和标记里的一致；
- 部署根之外的目录必须有 MooX 自己的文件才清除：外部程序目录要有 `bin/moox-factor-engine` 或 `bin/moox-archive-worker`，归档目录要有 `.state`。没有标记的目录不计入残留，只列在 `skipped_dirs` 里；
- 外部目录只认服务文件的 `WorkingDirectory`，不从 `ExecStart` 推断；符号链接、部署根的上级、系统目录的子目录和 `$HOME` 下的点目录都拒绝；
- 嵌套挂载点清空内容、保留目录；
- 删除内容不跟随符号链接到目录外。

**清除前全部检查**，任一项不过就停止，**一台都不动**：

- `setup validate` 的结果不是 `blocked`，所有主机 SSH 可达；
- 产物包能用：用 `unitpackage.Package` 按全部 profile 试打包到临时目录，和正式部署走同一条路径；
- Trade 没有实盘账户、持仓或未完成订单：`t_trading_accounts.c_execution_mode='LIVE'`、持仓表、`t_trade_orders.c_state` 的未完成状态。Trade 单元不存在算没有；文件存在但读不出就停下问用户。用户明确同意后，用 `--accept-trade-risk` 继续；
- 删除保护全部通过。

**执行**：开始时在 `~/.config/moox/wipe-pending.json` 写未完成标记。主机顺序沿用 `fresh-deploy.md`：因子机 → 海外机 → 控制机 → 存储机。每台：

1. 用纯 crontab 操作删掉 `# moox-watchdog` 行，不依赖 `moox-runtime`；
2. 等 `run/watchdog.lock` 释放，防止正在运行的那轮看护把组件拉起来；
3. 有服务文件的主机：先读出目录，再停止、禁用、删除服务文件，执行 `systemctl --user daemon-reload`。没有这两个服务时不访问用户级 systemd；
4. 各单元有脚本就先 `pause` 再 `stop`，脚本缺失或失败不中止；
5. 按 `/proc/*/exe` 找部署根和外部程序目录内的进程（包括 `releases/bootstrap-*` 候选目录，路径末尾的 `(deleted)` 要去掉），先 TERM，超时后 KILL，确认没有残留；
6. 保留部署根目录本身（否则要 sudo 重建），删除里面的全部内容，**包括因子机的 `import`**；
7. 清空预览列出的外部程序目录和归档目录；
8. 再查一次，部署根之外还有 `moox-` 进程就停下报告，不杀。

全部主机完成后：

9. 本机移走操作员身份文件（`gateway-client.yaml`、`gateway-bootstrap.json`、`moox-ca.crt`、`caller-moox-cli.key`）到 `~/.config/moox/.bak-<时间>/`；`config.key`、`known_hosts` 留在原处，否则 `moox.toml` 解不开、指纹要重新确认；
10. 本机状态目录改名为 `.bak-<时间>`，不删除；
11. `moox.toml` 不动；
12. 最后删除未完成标记。

可重复执行：中途失败后再跑一次会接着清，标记不删 `route` 就保持 `existing`。完成后 `setup validate` 必须返回 `route=fresh`。
`du` 和删除都要给足超时，SSH 不会替它们兜底。`setup wipe` 不提供保留选项。所有远端操作都由 CLI 执行，不给 Agent 暴露自由拼接的 `rm` 命令。

不需要处理的：云防火墙和 CLS 可以重复初始化（`setup_firewall.go:23-27`、`packages/cloudprovider/tencent/cls.go:106`，防火墙实现编码时再确认）；浏览器 CA 由 `setup init` 刷新（`setup.go:1021-1026`）。

`skills/moox/references/fresh-deploy.md`、`host-registry.md`“全新部署”改为使用这个命令；`command-index.md`、`docs/模块/命令行工具.md` 同步。

**验收**：一台不可达时不清除任何主机；实盘持仓时拒绝，`--accept-trade-risk` 后继续；摘要不符时拒绝；系统目录和家目录被拒绝；没有 MooX 标记时拒绝；中断后重跑不被 Trade 检查和 `stop.sh` 卡住；清除后部署根和归档目录都为空、服务文件已删除、`config.key` 和 `known_hosts` 还在、预览之外的文件不受影响。

## 7. 验证

每个阶段都跑 `go test ./modules/cli/...`、交叉编译、`git diff --check`。

| 用例 | 期望 |
| --- | --- |
| 新电脑 + 全空机 | `route=fresh`，不询问清空，全新安装完成 |
| 新电脑 + 已有部署，同意清空 | `setup wipe` 后 `route=fresh`，安装到 `*-ready`，能用新管理员账号登录，中途不再确认 |
| 新电脑 + 已有部署，不同意清空 | 不清除任何东西，走 `config restore`，如实说明限制 |
| 用户开头就说要保留数据 | 不走 `config init`，直接 `config restore` |
| 首装中途失败后重跑 | `route=resume`，不询问清空，继续安装 |
| 清除中途断开 | `route=existing`，再跑一次接着清，之后才能安装 |
| 空机 + 本机有上次遗留的状态 | 安装前归档旧状态，不复用旧软件 |
| 没有钥匙串的机器 | 清除后 `moox.toml` 仍能解开 |
| SSH 用户和旧部署不同 | `route=blocked`，不清除 |
| 配置之外还有旧机器 | 预览列出，询问时提醒，不清理 |
| 因子机不可达 | `setup validate` 失败，提示换到同一网络，不清除任何主机 |
| 部署目录外有旧进程，或端口被占 | `route=blocked` |
| 有实盘持仓 | `setup wipe` 拒绝，重新询问用户 |
| `deploy_root` 配成家目录 | `setup wipe` 拒绝 |
| `~/.config/moox` 为 755 | 自动收紧，不打断流程 |
| 远端拒绝 | 直接显示原因和下一步，不提示重试 |
| 选中的下载源失败 | 自动换另一个源 |

个人项目不单独准备测试机。上面的用例用自动化测试覆盖：SSH 用现有的假客户端，清除逻辑在临时目录里跑，确认只删该删的内容。
第一次真实使用就是实机验收：先看 `setup wipe` 的预览，确认主机和范围无误再执行；发现问题修在下一个版本。不用现有生产做这个验收。

## 10. 风险

| 风险 | 处理 |
| --- | --- |
| 用户没读清就同意清空，数据无法恢复 | 询问必须列出主机和丢失内容；执行要带预览摘要 |
| 用户看了预览才发现配错机器 | 预览列出 IP 和发布 ID；不带 `--yes` 不做任何改动 |
| `deploy_root` 配错，删到系统目录 | 删除保护拒绝系统目录、家目录和没有 MooX 标记的目录 |
| 部署根里混有用户自己的文件 | 部署根内全部删除，预览标出不认识的条目，由用户看预览决定 |
| 清除后新版本装失败，线上空着 | 清除前试打包并检查全部主机；失败时状态是 `route=fresh` 或 `resume`，修好后接着安装 |
| 清除途中断开，主机停在半清状态 | 未完成标记 + 可重复执行，清完才继续安装 |
| 用户不去清理旧云函数 | 询问里写明费用和以后的同名冲突；新配置默认不启用 SCF，第一版主线不受影响 |
| 配置之外的旧机器继续运行 | 预览和询问里提醒，清理由用户决定；连不上新系统时可能产生报错 |
| 部署用户不同，权限不够 | `blocked`，第一版不用 sudo 代删，由用户改用原用户 |
| 部署根是挂载点时 `lost+found` 删不掉 | 编码时确认，必要时跳过这一项 |
| 历史导入包重新下载很贵 | 询问里写明会删除；要留就选不清空 |
| 手工配置随清除丢失 | 询问里写明数据不保留；`moox.toml` 之外的改动要重新做 |
| `~/.config/moox` 为 755 的来源未查明 | B1 让它不再阻塞，不继续追查 |
| 不做实机测试，`setup wipe` 第一次真实运行就是用户的机器 | 预览先行、清除前全部检查、可重复执行；发布说明注明这是新功能 |

## 11. 不做的事

- 第一版不做 `setup adopt`，也不随 `config backup` 备份本机状态；
- 第一版不由 CLI 清理云函数；
- 第一版不支持 Windows 操作机；
- 不放宽“不能替换已有部署身份”的规则；
- 不做“只清程序、保留数据”的半清空，也不做保留部分数据的选项；
- 不在没有询问用户的情况下清除任何部署；
- 不做单台清除（`setup wipe --host`）；
- 不做“先不配因子机，以后加回”；
- 不杀部署根和外部程序目录之外的进程；
- 不用 sudo 代删其他用户的部署；
- 不清理不在 `moox.toml` 里的主机；
- 不新增单独的检测命令；
- 不处理现有生产的遗留项，另开任务。
