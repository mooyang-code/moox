# 因子连续水位详细设计

> 依据 [WS 行情推送采集设计](WS行情推送采集设计.md) 第 7.5 节与[执行计划](WS行情推送采集执行计划.md) 阶段 5a。只写实现要点；要求本身的理由见设计。

## 1. 现状要点（2026-10-21 读代码）

- 因子引擎（外部进程，经 Access 调用）按 `CollectorPeriodCompleted` 事件逐期计算：`trigger/eventconsumer/handler.go` 收到 T 就算 T，不检查 T 之前的周期；同一集合按通道串行。
- 零提交的周期没有事件，引擎永远不会算它；降级周期里失败的标的（`FailedSubjects`）只是被排除，没有记进空洞账本，补采之后不会补算。
- JetStream 消费者 `MaxDeliver=-1`、`MaxAckPending=16`：如果用"NAK 重投"来阻塞，长时间阻塞的事件会占满待确认名额，拖住所有集合。
- `CollectorPeriodCompleted` 还被 Storage View 消费（据此发 ViewDataReady 给策略），不能拿它当"补齐通知"再发一遍。

## 2. 方案

### 2.1 持久化的连续水位

- 引擎在空洞账本目录旁保存 `factor-watermarks.json`：每个集合一项 `{set_id, space_id, dataset_id, freq, committed_through, target, universe, blocked_since}`，原子写（临时文件 + rename）。
- `committed_through`（W）：这一期及之前已经连续算完。`target`：已知的最新收盘周期（收到的事件里最大的 T）。`universe`：最近一次事件的期望标的（用于读回判断前面的周期）。
- 第一次见到某个集合（没有记录）时 W 取 T − 一个周期：只从上线那一刻起保证连续，不回头补历史（历史用补算任务）。

### 2.2 推进（事件与追赶共用）

收到 T 的事件：`target = max(target, T)`，记下事件的 universe 与 FailedSubjects，然后在该集合的通道里执行 `advance`：

```text
for p = W + 一个周期; p <= target; p += 一个周期:
    info(p) = p == T ? 事件里的 universe 与失败标的 : 读回 Storage（见 2.3）
    缺失 = info.失败标的 − 已确认缺失（2.5）
    if 缺失 / 期望 > 阈值 or 零提交（期望全部缺失）:
        blocked_since 记首次阻塞时刻；停在这里，W 不前进；return
    计算 p（BuildLivePlan，UpstreamFailed = 缺失），把缺失的标的记进空洞账本（reason=upstream_failed）
    W = p；清 blocked_since；持久化
```

- 事件处理完一律 ACK（只有基础设施错误才重投）：阻塞靠本地状态续推，不占 JetStream 的待确认名额。
- 一次最多推进 30 期，剩下的交给追赶循环，避免一次占住通道太久。
- 读回得到的周期用合成的触发事件 ID `catchup:<set_id>:<period>`，周期 marker 与正常周期一样上报（策略照常消费，且只会看到连续的结果）。
- 当期 T 降级且缺失在阈值以内：先算已到的标的，缺失的标的记进账本，补采补齐后由 gapfill 的"只填充"路径补算；严格截面因子沿用现有规则（有缺失整因子 skipped）。

### 2.3 读回判断（保底）

`readback(p)`：用 `ReadWindow` 读期望标的在 `[p, p+周期)` 的一列（集合第一个因子的第一个输入列），有行的算到达，其余为缺失。只用于 W 与 T 之间没有事件可用的周期（零提交、或者事件在阻塞期间已经 ACK）。

### 2.4 追赶循环与补齐通知

- 引擎起一个循环：每 10 秒（`watermark.poll_interval`）对 `target > W` 的集合在其通道里执行一次 `advance`；这就是"阻塞期间按固定间隔查 Storage 保底"。
- 补齐通知：Collector 的补采作业成功后调因子管理服务新增的 `FactorMgr.NotifyPeriodsFilled(space_id, dataset_id, frequency, from, to, absent_subjects)`（服务目录只放行 `collector`）；因子管理服务按数据集暂存（有上限、10 分钟过期），在引擎心跳响应里带回给持有租约的引擎。引擎收到后立即对相应集合执行 `advance`，并唤醒 gapfill；该集合 `from～to` 里 reason=upstream_failed 的待办不再等 Settle。

### 2.5 "还没补到"与"确认没有"

- 补齐通知里的 `absent_subjects` 是补采已确认行情源没有的标的（`t_collector_source_absences`），引擎记在内存里（按集合、周期范围，30 分钟过期），计算缺失比例时扣除，不阻塞水位，也不记账本。
- 没有通知时，下架、停牌的少数标的本来就在 10% 阈值以内，不会阻塞。

### 2.6 阈值与告警

- 阈值：引擎配置 `watermark.max_missing_ratio`（默认 0.1），`watermark.set_ratios` 按集合 ID 覆盖。
- 心跳状态增加阻塞的集合（`blocked_since`、W、target）；因子管理服务导出 `moox_factor_set_watermark_blocked_since_timestamp_seconds`，Monitor 增加"因子水位停滞超过 30 分钟"检查（不自动跳过，交人工：手动补采、确认缺失）。

### 2.7 窗口空洞检查

`gap.enabled` 在生产已于 2026-10-13 打开（见记忆与因子窗口空洞防护详细设计第 8 节），本阶段只核对线上配置。

## 3. 改动清单

| 模块 | 改动 |
| --- | --- |
| factor 引擎 | `engine/watermark.go`（状态文件、advance、追赶循环、读回、已确认缺失）、`eventconsumer/handler.go` 改为先记 target 再 advance、`pipeline` 支持 upstream_failed 记账、gapfill 按通知放行、心跳带阻塞状态、配置 `watermark` 段 |
| factor-mgr | `NotifyPeriodsFilled` RPC、心跳响应带补齐通知、阻塞指标 |
| collector | 补采作业成功后通知因子管理服务（失败只记日志） |
| servicecatalog | `FactorMgr.NotifyPeriodsFilled` 放行 `collector` |
| monitor | 因子水位停滞 > 30 分钟检查；`packages/report` 放行阻塞指标 |

## 4. 测试

- 连续：W=t0，收到 t0+3 的事件，t0+1、t0+2 读回齐全 → 依次算 t0+1、t0+2、t0+3，W=t0+3。
- 零提交阻塞：t0+1 读回全部缺失 → 只记 target，W 不动，blocked_since 有值；之后读回齐全（或收到补齐通知）→ 按顺序补算，W 追上。
- 降级在阈值内：缺 1/50 → 照常算，缺的标的记账本 reason=upstream_failed，W 前进。
- 降级超阈值：缺 10/50 → 阻塞；补到 2/50 后整期计算，W 前进。
- 已确认缺失不计入比例。
- 重启：状态文件恢复 W 与 target，追赶继续。
- 不会用缺根的窗口算出值：阻塞期间不调用计算。
