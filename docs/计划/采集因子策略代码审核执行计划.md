# 采集 / 因子 / 策略 代码审核执行计划

日期：2026-10-12　基线：`moox` 仓库 `feature/mooyang` 分支（其余三个目录为 worktree，不在本次范围）

## 1. 目标与原则

- 目标：审查"数据采集""因子计算""策略模块"的前后端代码，找出值得优化的点，并纠正文档与代码不一致之处。
- 定位：个人量化系统。**不追求小概率可靠性问题**（极端崩溃窗口、多副本一致性、过度重试等），设计保持简洁；
  只保留"会导致数据错误 / 策略误触发 / 明显性能或维护负担"的结论。
- 协作方式：Claude 与 Codex 逐条讨论，**每条结论双方一致才进入最终清单**；分歧项单列并写明各自理由，交用户裁决。
- 项目原则沿用 `AGENTS.md`：无需兼容历史，可直接删除死代码、冗余适配层。

## 3. Codex 配置

- 模型：`gpt-6-astra`（模型缓存中的 GPT6 Astra），推理强度 `xhigh`。
  注意 `~/.codex/config.toml` 默认是 `gpt-6.1-sol`，因此每次调用显式传 `-m gpt-6-astra -c model_reasoning_effort=xhigh`。
- 模式：`codex exec`，只读沙箱（`-s read-only`），工作目录为 `moox`，不让 Codex 改代码。
- 多轮讨论：首轮记录会话 id，后续用 `codex exec resume <id>` 续聊，保证上下文连续。
- 调用示例：

```bash
codex exec -m gpt-6-astra -c model_reasoning_effort=xhigh -s read-only -C . "<审查提示词>"
```

## 4. 执行步骤

### 阶段 0：准备（Claude）
1. 通读三个模块的文档与 README，整理"文档声称的行为清单"，作为后续对齐基准。
2. 运行现有测试与静态检查拿基线：`go vet`、`go test ./...`（三个模块）、前端 `vitest`、`eslint`、`tsc --noEmit`，记录已有失败，避免误判为新问题。
3. 统计热点：文件行数最大、圈复杂度高、重复代码多的包，用来排审查优先级。

### 阶段 1：独立初审（并行）
- Claude 与 Codex **各自独立**审查，互不看对方结论，避免锚定。按 6 个单元切分：
  1. 采集后端　2. 采集前端　3. 因子后端　4. 因子前端　5. 策略后端　6. 策略前端
- 统一审查维度：
  - 正确性：数据口径、时间/频率/交易日历、复权与对齐、因子与策略的数据就绪依赖。
  - 简化：死代码、过度抽象、重复实现、可合并的包与配置项。
  - 性能：明显的全量扫描、重复读取、不必要的序列化（仅在有依据时提出）。
  - 前后端契约：接口字段、枚举、错误码、分页与前端类型是否一致。
  - 文档对齐：文档描述与代码实际行为的差异。
- 每条发现统一格式：`编号 | 位置(文件:行) | 问题 | 影响 | 建议 | 严重度(高/中/低) | 是否属于"个人系统可忽略"`。

### 阶段 2：交叉讨论（Claude ⇄ Codex）
1. 合并两份初审，去重，形成候选清单。
2. 逐条交给 Codex 复核：Claude 对 Codex 的发现回到代码验证，Codex 对 Claude 的发现同样验证；对每条给出 同意 / 反对 / 修改建议。
3. 反对项最多讨论 2 轮；仍不一致的记为"分歧项"，写明双方依据。
4. 过滤规则：属于"小概率可靠性"或需要显著增加复杂度的建议，默认剔除，除非双方都认为收益明显。

### 阶段 3：形成共识清单
- 输出 `docs/审查/2026-10-12-采集因子策略审查.md`，结构：
  1. 共识结论（按优先级排序，含位置、原因、建议）
  2. 文档与代码不对齐清单
  3. 被剔除项及理由（说明为何对个人系统不值得做）
  4. 分歧项（如有）
- 此文档提交用户确认后，才进入改动。

### 阶段 4：落地（需用户确认清单后执行）
1. 文档类：直接修正 `docs/模块/*.md`、`docs/实现状态.md` 等不一致描述。
2. 代码类：按优先级小步修改，每项改动让 Codex 复核 diff；改动范围限定在共识清单内。
3. 验证：相关 Go 测试、Python worker 测试、前端 vitest / eslint / tsc 全部通过；schema 变更按 `AGENTS.md` 规范校验。
4. 会话结束按 `AGENTS.md` 要求，把所有改动提交到 Git（`feature/mooyang`）。
