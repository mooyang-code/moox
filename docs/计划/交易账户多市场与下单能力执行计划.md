## 1. 目标

1. 一把交易所密钥只对应一个执行账户，这个账户可以同时做现货和 U 本位永续。
2. 支持三种账户：币安统一账户（组合保证金）、币安普通账户（现货、合约两个钱包）、OKX 统一账户。账户类型和 API 权限在录入密钥和建账户时自动检测，不靠手填。
3. 策略目标里每个标的自带市场，交易按标的所属市场下单。同一个币的现货仓和合约仓各自独立，不互相抵消。
4. 补齐 qronos 已有的下单能力：调仓阈值、分市场最小下单额、单币每小时上限、拆单、伪市价单与递增滑点重试、挂单比例、BNB 抵扣与补买、小额资产兑 BNB、多稳定币调平、保证金币、套利底仓、钱包划转、下架清仓、保证金率监控。
5. 前端按已评审的交互原型改版（https://claude.ai/artifact/6FJHTiXrgFZjTVVzfMLd8y ，四轮意见见原型「设计说明 / 评审记录」）。

不在本计划：分钟偏移（用户决定先不做）；选币与市场模式、策略池（在策略计划里）。

## 3. 与策略模块的契约（两份计划共用）

`packages/tradeeventpb/trade_events.proto` 的 `InstrumentWeightTarget` 加一个字段：

```protobuf
message InstrumentWeightTarget {
  string instrument_id = 1;   // 标的，采集和策略的写法：BTC-USDT；股票是原始代码
  string target_weight = 2;
  bool hold = 3;
  string market_type = 4;     // SPOT | SWAP | STOCK，必填
}
```

- 同一个 `instrument_id` 可以以 SPOT、SWAP 各出现一次；同一（标的，市场）重复出现仍拒绝。
- Trade 用 `exchange.NormalizeInstrumentID(instrument_id, market_type)` 得到内部 ID（`BTC-USDT-SPOT` / `BTC-USDT-SWAP`），不再按组合市场补后缀。
- `market_type` 缺失或不在组合的可交易市场里（4.1）：整份目标按 `invalid_contract` 拒绝。
- 现货负权重仍是永久拒绝（weight_resolver.go:159）；策略侧保证空头只输出 SWAP。
- 目标里出现组合的排除资产（BNB 保留、稳定币保证金、保证金币、底仓，见 4.5）时，**只跳过这一项并告警**，其余照常执行，不拒绝整份目标。同一个组合、同一个资产每天只告警一次，避免每期刷屏。
- 删除同一 proto 里“13 曾是已删除的 runner_id”这类兼容注释。
- 改动要过 `make test-event-contracts`。

**发布耦合**：交易 T2 删掉组合的 `market_type`，Strategy 的 `tradeowner/client.go:157、233-247` 读这个字段，属于编译期依赖。所以交易阶段 1 的 A 批（第 6 节）与策略计划 S1 必须在同一个分支合入、同一次发布。

## 4. 设计

### 4.1 账户模型

**执行账户**（`t_trading_accounts`）：

- 删 `c_market_type`，新增 `c_markets`：逗号分隔的有序集合。加密货币账户取 SPOT、SWAP 的子集；股票账户保持现状，只有 STOCK。
- 新增 `c_account_mode`：只用于加密货币实盘账户，取 `BINANCE_PORTFOLIO_MARGIN`、`BINANCE_STANDARD`、`OKX_UNIFIED`；模拟盘和股票为空串。只由检测写入，用户不能改。
- 新增 `c_inspection_json`：最近一次检测的结果，含权限、OKX acctLv、持仓模式、检测时间、阻断项。
- `c_snapshot_json` 改成“权益 + 各钱包余额”：
  ```text
  equity, available_funds, used_margin, maintenance_margin, unrealized_pnl, exchange_equity,
  wallets: [{wallet: SPOT|FUTURES|MARGIN|UNIFIED, updated_at, balances: [{asset, total, available, locked, borrowed}]}]
  ```
  `equity` 按 4.6 的统一公式计算；`exchange_equity` 是交易所给的总权益，只用于展示核对。
- 钱包与市场的对应：普通账户 SPOT → SPOT 钱包，SWAP → FUTURES 钱包；统一账户 SPOT → MARGIN 钱包，SWAP → UNIFIED；OKX 两个市场都是 UNIFIED。
- `c_leverage_settings_json` 只对 SWAP 生效，键改成内部标的 ID。
- `c_fill_cursors_json` 的键改成“市场:交易所代码”。
- 一把密钥（交易所 + 环境 + 密钥 ID）全局只能有一个启用的执行账户：删掉 `Descriptor.UnifiedAccount`，`rejectDuplicateCredential` 改成无条件冲突，并在表上加唯一部分索引兜底。
- SWAP 一律全仓。币安普通账户允许多资产模式（保证金币需要），删掉 `ensureSingleAssetMode`，模式写进检测结果。

**组合账户**（`t_logical_accounts`）：

- 删 `c_market_type` 及其 CHECK。成员同质性只要求执行模式、环境、结算资产一致。
- 新增 `c_order_settings_json`（4.4）和 `c_fund_settings_json`（4.5）。
- “可交易市场”不存储，由启用成员已开通市场的并集算出，`LogicalAccount` 消息新增只读字段 `markets`。Strategy 启用实例时用它代替现在 `checkMarket` 的精确匹配：策略要输出的市场必须都在 `markets` 里。成员变动后某市场不再可交易，Trade 收到含该市场的目标按 `invalid_contract` 拒绝并告警。

**订单、成交、持仓**：

- `t_trading_positions` 和墓碑表主键加 `c_market_type`。
- `t_trade_orders` 的交易所订单号唯一索引、`t_order_fills` 的成交唯一约束都加 `c_market_type`；`canonicalFillID` 改成“账户:市场:代码:成交号”。
- 订单归属新增 `SYSTEM`，用于 BNB 补买、稳定币调平（4.5）。
- `t_operator_actions` 的动作类型 CHECK 新增 `REDUCE`（按比例减仓）和 `DELIST_FLATTEN`（单标的下架清仓），见 4.7。
- `CreateOrder` 改成校验“订单市场 ∈ 账户已开通市场”（fact.go:443、1294）。

**代码层的键**：新增值类型 `exchange.SymbolKey{Market, Symbol}`，替换所有以交易所代码做键的 map、集合、缓存和查询参数（第 2 节列出的各处），靠编译器把用到的地方找全。Order、Fill、Position、AssetBalance 加 `Market`，AssetBalance 加 `Wallet`。

**标的**：`t_trade_instruments` 本来就按（交易所、环境、市场、代码）存，不变。会话按账户已开通的每个市场各加载一份；`persistInstruments` 改成接受账户已开通的任一市场。

**一次定稿的 DDL**：阶段 1 的 T2、T3 包含本计划需要的全部表结构：

- 上面各列与约束；
- 订单的 `c_attempt`（4.4）；
- 划转表（4.5）；
- 下架名单表（4.7）；
- SYSTEM 归属；
- REDUCE、DELIST_FLATTEN 两种动作。

后续阶段只加代码。

### 4.2 账户检测

新增两个 RPC：

- `InspectExchangeCredential(exchange, environment, credential_secret_id)`：只读，不落库，供录入密钥和建账户前预览。
- `ReinspectTradingAccount(trading_account_id)`：对已有账户重新检测，结果写回 `c_account_mode`、`c_inspection_json`。

**判别方法**（生产环境）：

| 项 | 币安 | OKX |
| --- | --- | --- |
| 权限 | `GET /sapi/v1/account/apiRestrictions` | `GET /api/v5/account/config` 的 `perm`、`ip` |
| 账户类型 | 见下 | `acctLv`：2、3、4 → 统一账户；1（现货模式）→ 只能做 SPOT |
| 持仓模式 | 合约必须单向 | `posMode` 必须 `net_mode` |

币安账户类型的判别：

1. `/papi/v1/account` 调通 → 统一账户。
2. papi 不通、`/fapi/v3/account` 调通 → 普通账户（现有代码用的就是 fapi v3，binance.go:411）。
3. 两者都返回鉴权或权限类错误，且 `enableFutures=true`：按“疑似统一账户、密钥建于开通统一账户之前”处理，记为阻断项。币安文档说明开通组合保证金后 fapi 不可用，所以这种情况不能简单判成普通账户。

**传输错误不下结论**：超时、限频、5xx 这类错误，只说明这次没检测成，不代表账户有问题。这时保留上次的检测结果，不触发阻断，下一小时再试；连续失败 6 次再告警。只有鉴权、权限类的错误码才参与判别。具体是哪些错误码，要在实现前用官方文档核对并录成样例；分类沿用现有的 `exchange` 错误分类。

**阻断项**：任一出现就不能建账户；已有账户的会话停止下单、暂停所在组合并告警。

1. 有提现权限（币安 `enableWithdrawals`，OKX `perm` 含 withdraw）。
2. 判别方法第 3 种情况。
3. 普通账户同时开通了 SPOT 和 SWAP，但没有万向划转权限（`permitsUniversalTransfer`）。
4. 合约是双向持仓。
5. OKX acctLv=1 却开通了 SWAP。

**测试网**：币安测试网没有 sapi 和 papi，现货和合约测试网是两套域名、两把密钥。测试网账户跳过权限与类型检测，记为 `BINANCE_STANDARD`，且一个测试网账户只能开通一个市场。OKX 模拟盘照常检测。

**检测时机**：

1. 管理台「系统设置 / 秘钥管理」录入或编辑交易所密钥时，“测试连接”按钮调用 `InspectExchangeCredential`，弹窗显示结果。
2. `CreateTradingAccount` 必须先检测通过。
3. `UpdateTradingAccount` 换了密钥：必须重新检测通过才保存。
4. 会话每小时调用一次复查逻辑。账户模式变了或出现阻断项时，停止下单、暂停组合、告警；在管理台点“重新检测”通过后才能恢复。

不自动修改交易所的账户设置，例如不开联合保证金、不切持仓模式（qronos 会自动改）。唯一例外是 4.5 的 BNB 抵扣开关，它由用户在资金设置里显式开启。

**config init 录入页录交易所密钥**（用户 11-04 确认）：

- **录入**：moox.toml 新增 `[[exchange_keys]]` 数组段，随整个文件加密。字段：
  - `name`：只允许 `[a-z0-9-]`，在 validate 里查重；
  - `exchange`：小写 binance、okx；
  - `environment`：production、testnet；
  - `api_key`、`secret_key`、`passphrase`（OKX）：用这三个字段名，`config get` 才会自动打码（access.go:23）；
  - `readonly`：可选，默认 false。只读 Key 设为 true（例如 Collector 检测币安现货下架用的那把），它不能用来建执行账户，apply 后也不做交易账户检测。
- **要改的地方**：
  - `modules/cli/internal/setup/config` 的 `Manifest` 加字段（遇到未知键会报错，config.go:502）。
  - `moox.toml.example` 与录入页嵌入的示例里只放注释掉的样例，否则占位密钥会被 apply 进 SecretMgr。两份示例要保持一致。
  - 录入页（page.html）在“管理员与告警”之后加一步“交易所密钥”，可以不填。没配海外机（Trade 所在的主机）时隐藏这一步。
  - 渲染时 `setKey` 要求示例里已有这个键（tomledit.go:98-104），`tomledit` 也只认 `[段]`、不认数组段（tomledit.go:9-28）。所以整段的增删改，用 migrate.go 的 `splitBlocks`（389）整块替换。
  - 「修改配置」页（editor.html、editform.go）和 reveal 的 switch（editor.go:238-256）按序号支持新字段。
- **写入 SecretMgr**：扩展 `ApplySetup`（setup_service.proto:30），把每个 `[[exchange_keys]]` 写成 category=exchange、provider 为小写交易所名、secret_type=api_key 的密钥。固定 ID 为 `exchange-<交易所>-<环境>-<名称>`（三段一律小写，例如 Collector 检测币安现货下架用的 `exchange-binance-production-readonly`），passphrase 放进 extra_config（值只能是字符串，Trade 按 `map[string]string` 解析，bootstrap.go:509）。
  - **只建不改**：库里有这个 ID 时，不管内容是否相同都不覆盖，在结果里注明“已存在，以管理台为准”，也不算冲突。存在性检查要连已软删除的行一起看（现有检查只看未删除的行，impl.go:228）：用户在管理台删掉的密钥（比如已作废或泄露）不会被重新建出来，提示“已在管理台删除，未重建”。唯一索引是（c_secret_id, c_is_deleted）（admin.sql:175），同一个 ID 也不能被第二次软删除。否则下次 setup init 会把管理台改过的密钥改回去，还会绕开“换密钥必须重新检测”。这和 `tencent-default` 的“内容不同就报冲突”不一样，交易所密钥单独处理，不进整体冲突判断。
  - 同步修改 `GetSetupStatus`、`Inspect`，以及 `expectedResult` 和 `Inspect` 里写死的 `Secrets: 1`（impl.go:84、116-121）。
  - moox.toml 里删掉的密钥不会从 SecretMgr 自动删除，避免误删正在用的账户，由管理台手工删除。
- **检测在海外机上做**：录入页在你本机运行，交易所密钥通常绑定了海外机的 IP，币安的万向划转权限一般也要求绑定 IP，本机检测多半通不过，判断也不准。所以录入页不做本机检测，只提示“部署完成后，在海外机上检测这把密钥”。
  - `setup apply` 写入密钥后，如果 Trade 已经部署，CLI 经网关调 Trade 的 `InspectExchangeCredential`（moox-cli 本来就在 Trade 的 acl 里），逐个打印检测结果和阻断项。`readonly = true` 的密钥跳过检测。
  - Trade 还没部署时，提示部署后执行 `moox-cli trade inspect-credential`，或在管理台检测。全新安装时 `setup apply` 排在 Trade 部署之前（部署与运维.md:146），所以 skill 的 `fresh-deploy.md` 要在 Trade 部署之后加一步 `trade inspect-credential`。
  - 这样检测只有 Trade 里一份实现，不新建公共包。

### 4.4 目标执行与下单设置

**换算**（weight_resolver）：

- 换算用的权益 = 4.6 的统一权益 + 目标里尚未受管的现货资产市值（沿用现有的 `unmanagedTargetValue`，weight_resolver.go:148、193，不加会多卖一截）− 权益 × 资金预留比例 − max(0, BNB 保留金额 − 当前 BNB 市值)。BNB 本身不计入权益，所以只扣还差的部分，买到位后不再扣。
- qronos 那串没有说明的 ÷1.001、×0.95、×0.97 不照搬，统一成“资金预留比例”这一个可配项。
- 数量 = 权益 × 权重 ÷ 价格。现货和合约各自独立换算，各自取本市场的报价。
- 组合有多个执行账户时，先按市场筛出开通了该市场的成员，再沿用现有按优先级分配的逻辑。
- 删掉 `store/target.go:144` 按组合市场的做空校验，改成按标的市场：只有 SWAP 能为负。

**下单设置**：存在组合的 `c_order_settings_json` 里，管理台「执行账户与设置」可改，从下一份目标开始生效。

| 设置 | 含义 | 默认 |
| --- | --- | --- |
| 调仓阈值模式 | `TARGET_RATIO`：差额不超过目标数量 × r 就不调（现有行为）；`POSITION_RATIO`：调仓金额低于当前持仓金额 × r 就不调；`EQUITY_RATIO`：低于权益 × r 就不调；`ALWAYS`：每期都调。建仓（当前为 0）和清仓（目标为 0）不受限制 | `TARGET_RATIO`，r = 5%，等于现状 |
| 最小下单额（现货、合约） | 低于 max(交易所最小名义, 配置值) 的子单不下；合约减仓、清仓例外 | 现货 10，合约 5 |
| 单币每小时上限（现货、合约） | 每个标的每个自然小时累计下单金额的上限，可用 `*` 设默认值，超出部分留到下一小时；从 `t_trade_orders` 聚合，不加表 | 不限 |
| 单笔上限 | 拆单时每笔的名义金额上限，替换进程级常量 `MaxChildNotional` | 100000 |
| 拆单随机化 | 每笔金额在上限的 50%～100% 之间随机 | 关 |
| 批间隔 | 批与批之间等待的秒数 | 1 秒 |
| 下单方式 | `MARKET` 市价单；`PSEUDO_MARKET` 伪市价单 | `PSEUDO_MARKET` |
| 伪市价滑点 | 首次相对参考价偏移 s，每次重试再加 s，直到上限 | s = 1.5%，上限 6%，最多 4 次 |
| 挂单比例 | 加仓、减仓、调仓的名义金额中，按此比例改成挂单；建仓、清仓不挂单 | 0 |
| 挂单寿命 | 挂单最多保留多久；到期撤单，剩余量重新计入差额 | 到下一份目标到达为止 |

**执行阶段**：每份目标按下面的顺序执行。

1. **撤旧单**：撤掉不属于本目标的 TARGET 子单（现有逻辑，executor.go:299-306）。上一份目标留下的挂单也在这一步撤掉，不带进新目标的差额。
2. **减仓**：现货卖单、合约减仓单。
3. **合约加仓。**
4. **普通账户划转**（4.5）：划转完成后，等现货钱包快照的时间晚于划转完成时间，再进入下一阶段。
5. **现货买入。**
6. **普通账户归集。**

统一账户和 OKX 跳过第 4、6 阶段。第 4 阶段的一个例外见 4.3。

**阶段不单独存储**：每次 Converge 从当前状态推出该做哪一阶段：

- 还有待减仓的标的 → 第 2 阶段；
- 没有了、还有待合约加仓的 → 第 3 阶段；
- 再看本目标在划转表里有没有已完成的划转，决定第 4、5、6 阶段。

只有划转需要持久化，靠划转表就够了，不加 `c_phase` 列。

**与现有收敛状态的衔接**：

- **不卡阶段**：被阻塞（executor.go:503-510）、被每小时上限顺延、或伪市价重试用尽“未到位”的标的，都不卡住阶段推进。这些标的在本阶段视为已处理，进入下一阶段。
- **最后阶段才定终态**：只有第 6 阶段（或统一账户、OKX 的第 5 阶段）处理完，才按现有规则把目标置为 BLOCKED 或 CONVERGED。中间阶段一律保持 CONVERGING，定时器（target_worker.go:195-197）会继续扫。
- **只剩挂单时**：目标定为 CONVERGED，不再每秒扫描重算，`RetryAfter` 设成距 `valid_until` 的剩余时间。之后有三种情况：
  - 挂单成交：成交事件会唤醒目标重算。现有路径已经支持：实盘经 `accountsync/service.go:676` 的 `wakeTargets`，模拟盘经 `paper/matcher.go:366、471`。
  - 下一份目标到达：在第 1 阶段撤掉旧挂单。
  - 一直没有成交，也没有新目标：到 `valid_until` 时被唤醒，走过期分支（`executor.go:176-193`），在这里补上“撤掉本目标的挂单”。
- **有顺延时**：本目标有标的被每小时上限顺延时，目标也定为 CONVERGED，`RetryAfter` 设到下一个整点，到时继续下顺延的部分。同时还有挂单的，取两个唤醒时间里较早的那个。重启后定时唤醒会丢，但启动时会全量扫描一次，不影响结果。

**每个阶段内部**：

- 按单笔上限拆单；每批每个标的最多一片；批间等待批间隔。
- 每批开头重新取报价，下一批按最新持仓重算差额，不像 qronos 那样一次算定。
- 不做跨阶段的卖买配对：阶段顺序已经保证先卖后买。

**伪市价单**：

- 限价 + IOC，价格 = 参考价 ×（1 ± s），按价格精度取整。
- 部分成交时，只按剩余数量补单，价格按新的滑点重新计算。现货卖出不超过可卖余额。
- 重试次数记在订单表的 `c_attempt` 列，client order id 带上次数，防止重复。
- 结果不明时，先按 client order id 查单，确认没成交再重下。复用现有幂等逻辑（order/service.go:103-125）。
- 用满次数仍没成交完：该标的在本份目标里记为“未到位”，告警一次，不再重试，等下一份目标重算。

**挂单**：

- 限价 + GTC，买单挂买一价，卖单挂卖一价。
- 挑选：每轮按每个方向的金额预算挑选，每个标的每轮最多一片。用“组合 ID + 目标 ID”做随机种子，结果可复现。
- **挂单不阻塞**：两处在途检查（executor.go:340-366 和 `waitingOnChildren` 1739-1785）都排除本目标的挂单。算差额时，把挂单的剩余量当作“已在路上”从差额中扣掉，避免再下一笔吃单造成超买。
- 到期撤单后，剩余量重新计入差额。

**单币每小时上限**：从 `t_trade_orders` 按（组合、内部标的 ID、提交时间所在的自然小时）汇总已提交子单的名义金额。

### 4.5 资金设置

存在组合的 `c_fund_settings_json` 里：

| 设置 | 含义 | 适用 |
| --- | --- | --- |
| 资金预留比例 | 换算目标时从权益里扣掉的比例 | 全部 |
| BNB 抵扣 | 开关；会话启动和设置变更时调用 4.3 的抵扣接口，现货、合约一起设 | 币安 |
| BNB 保留金额 N | BNB 市值低于 N − 10 时市价补买到 N。普通账户的分配：做现货就现货、合约钱包各一半，否则全放合约钱包 | 币安 |
| 小额兑 BNB | 每隔 D 天（默认 15），把非目标、非排除、低于 5U 的现货零头兑成 BNB；上次兑换时间记在账户的检测结果里 | 币安 |
| 多稳定币保证金 | 稳定币及目标比例（必须含 USDT，比例和为 1）。每小时检查一次，偏离目标超过 5% 时在稳定币交易对上调平：买入用买一价限价单，到下一次检查还没成交就撤掉；卖出用 IOC | 币安统一账户 |
| 保证金币 | {资产: 配置的固定 U 值}，按配置值计入权益（第 9 节待确认 2） | 统一账户；普通账户须先手工划到合约钱包 |
| 套利底仓 | 资产列表；这些币的现货和对应永续都不参与策略持仓，按净值计入权益；非空时组合只做合约 | 统一账户 |

**系统单**：

- BNB 补买和稳定币调平下的单，归属是 `SYSTEM`。
- 执行器的在途检查忽略 SYSTEM 单，它们不会暂停组合，也不会被当成本目标的子单。
- SYSTEM 单的成交不让资产变成受管（4.6）。
- 开启 BNB 保留时，BNB 现货标的属于排除资产。策略目标里出现它时，按第 3 节只跳过这一项并告警，避免策略和补买互相打架。
- 稳定币保证金、保证金币、底仓同理。

**普通账户钱包划转**：

- USDT 平时放在合约钱包。
- 第 4 阶段的划转金额 = max(0, 现货买单名义总额 × 1.02 − 现货钱包可用 USDT)，并且不超过合约钱包可划额度 × 0.99。划转前现查两边余额，不用缓存。
- 额度不足：告警，并按可用资金等比缩小现货买单，不让交易所报余额不足。
- 第 6 阶段归集：现货钱包只留 BNB 补买所需的金额和 1U。现货钱包多出来的 USDT 低于归集阈值时不划，阈值取 max(100U, 权益 × 1%)，避免 1 分钟级策略每期来回划转。
- 划转记录写进新表 `t_trade_wallet_transfers`，每条带目标 ID 和方向（划到现货、归集回合约），第 4、6 阶段的推导靠这两列区分。先写一条 PENDING 记录（带本地引用号），成功后写交易所流水号。超时则按时间窗口和金额查交易所的划转记录，确认没到账才重试。
- 如果实现前核对发现划转接口支持客户端流水号，就改用它，省掉按时间窗口对账。
- `ListAccountLedger` 把这张表里的划转合并进返回结果。资金流水仍然即查、不落库。

**统一账户**不划转。保证金币和底仓放在统一账户的杠杆钱包里，由交易所统一计算保证金。

### 4.6 权益与受管资产

**统一权益公式**（每个执行账户）：

```text
权益 = 结算资产在各钱包的净额（含负债为负）
     + 永续未实现盈亏（不含底仓对冲腿）
     + 受管现货的市值
     + 保证金币的配置值
     + 底仓净值（底仓现货市值 + 底仓对冲腿的未实现盈亏）
```

- 不使用交易所给的总权益（OKX totalEq、币安 totalMarginBalance、papi accountEquity）。多资产模式和统一账户会把保证金币、其他币折算进去，和上面的项重复。`exchange_equity` 只用于展示核对。
- 每个余额字段都取**不含未实现盈亏**的口径，未实现盈亏只从持仓接口取一次。

各账户模式的字段对应如下。字段名要在实现前按官方样例核对，口径不能变：

| 账户模式 | 结算资产净额 | 永续未实现盈亏 | 现货数量 |
| --- | --- | --- | --- |
| 币安普通账户 | 合约钱包 `walletBalance`（`/fapi/v3/account` 的 assets）+ 现货钱包 `free + locked`（`/api/v3/account`） | `/fapi/v3/positionRisk` 的 `unRealizedProfit` 之和 | 现货钱包 `free + locked` |
| 币安统一账户 | `/papi/v1/balance`：杠杆钱包资产 − 借款 − 利息 + UM 钱包余额 | `/papi/v1/um/positionRisk` 的未实现盈亏之和 | 杠杆钱包资产 − 借款 |
| OKX 统一账户 | `/api/v5/account/balance` 的 `cashBal`（不是含未实现盈亏的 `eq`；现在用 `eq`，okx.go:441） | `/api/v5/account/positions` 的 `upl` 之和 | `cashBal` |
| 模拟盘 | 现有的本地余额 | 现有的本地计算 | 现有的本地余额 |
- 组合权益 = 成员权益之和。权益采样（equity worker）和界面展示用同一个公式。

**受管资产**：沿用现有定义（`infra/store/managed.go`），只做三处修改：

1. 取 BaseAsset 时只看 SPOT 标的。SWAP 标的不让 BTC 这种基础资产变成受管现货。
2. 统计“MooX 有成交”的标的时只算 TARGET、OPERATOR 单，SYSTEM 单不算（现在就是这样，补测试锁住）。
3. 结果减去排除项：BNB（开启 BNB 保留时）、稳定币保证金、保证金币、底仓。

受管但不在目标里的现货仍按目标 0 处理，和现在一样。用户自己放在账户里、MooX 从没交易过的币不受管，不会被卖。

**余额确认水位**：`consumer/fill.go:212-230` 的待余额确认水位和 `accountsync/service.go:545-548` 的快照新鲜度判断，都改成按钱包。合约成交只推进 FUTURES/UNIFIED 钱包的水位，不会让现货钱包一直“不就绪”。

**资金预留**（order/validator.go）：按订单市场对应的钱包取可用余额。普通账户的两个钱包分开算，统一账户和 OKX 用同一个钱包。

### 4.7 风控

**下架处理**：见 `docs/计划/事件中心执行计划.md`（用户 11-04 决定）。下架检测由采集模块 Collector 负责，并发布“标的即将下架”事件；决定何时动手、找出持有者，由事件中心的系统动作“卖出策略持有的下架币”负责。Trade 只提供执行用的接口。

**下架名单**：

- 名单是全局的，不分空间：下架是交易所层面的事实。
- 表 `t_trade_blocked_instruments` 的键是（交易所、市场、交易所代码），另存内部标的 ID、base_asset、原因、来源事件 ID、写入时间，随 T2 一次定稿。内部标的 ID 和 base_asset 只用于展示和审计，匹配一律在使用时查标的表。
- 写入时能从标的表查到的，就记下内部标的 ID 和 base_asset；查不到的留空（见下面的“未知标的”）。标的表只增改、不删行（session.go:650-683），标的下架后也查得到。

**接口**：面向事件中心的接口都用（交易所、市场、交易所代码）定位标的。币安下架计划只给 `FOOUSDT` 这样的交易所代码，由 Trade 按标的表换算成内部 ID。

| 接口 | 说明 | 调用方 |
| --- | --- | --- |
| `BlockInstrument(exchange, market_type, exchange_symbol, reason, event_id)` | 写入下架名单 | callback-dispatcher |
| `UnblockInstrument(exchange, market_type, exchange_symbol)` | 解除禁止 | callback-dispatcher、console |
| `ListBlockedInstruments()` | 列出名单，只读 | callback-dispatcher、console |
| `ListInstrumentHolders(exchange, market_type, exchange_symbol, paper_only)` | 跨空间列出持有该标的的（空间、组合账户、执行账户、数量、是否零头）。只算策略持有：现货必须是受管资产（4.6）且余额大于 0，永续持仓不为 0；只看该交易所的执行账户；不在组合里的执行账户不算；测试网不算。`paper_only` 只返回模拟盘。只读 | callback-dispatcher、console（事件中心手工登记前的预览） |
| `FlattenInstrument(action_id, logical_account_id, exchange, market_type, exchange_symbol, reason)` | 在调用时带的空间里，对该组合中属于这个交易所的成员发起单标的 `DELIST_FLATTEN`，返回操作 ID | callback-dispatcher |
| `GetOperatorAction` | 现有接口，事件中心用来查平仓结果 | 在原有调用方之外加上 callback-dispatcher |

- **未知标的**：标的表只由已有账户的会话写入，每个会话只写自己账户的交易所和市场（session.go:650-683）。用户没开通的市场里的标的，在标的表里查不到。这时：
  - `BlockInstrument` 照常写入名单，内部 ID 留空，返回“Trade 无此标的”的标记，不算失败；
  - `ListInstrumentHolders` 返回空列表和同样的标记，不算失败。
  - 名单的匹配不依赖写入时存下的内部 ID 和 base_asset，而是在使用时查标的表，所以以后才开通这个市场的账户也能匹配上。
- **全局方法**：名单的三个方法和 `ListInstrumentHolders` 是全局的，Trade 的 RPC 层对它们免除空间检查（rpc/account.go:240）。管理台照常带上空间头，Trade 忽略即可。
- **按空间的方法**：`FlattenInstrument` 和 `GetOperatorAction` 仍按空间调用，用 `ListInstrumentHolders` 返回的空间。
- **服务目录**：`ListBlockedInstruments`、`ListInstrumentHolders` 放进 read_only_methods；`FlattenInstrument` 照同类方法配上 `method_timeouts_ms`（catalog.yaml:1864-1867）。

**名单标的“只减不增”**（用户 11-04 决定“一发现下架就先禁止买入”）：从写入名单到下架，这段时间可能长达一周。名单只禁止买入，不禁止卖出：

- **标的还能交易时**：目标里的这一项改成“只减不增”。
  - 多头：目标数量 = min(目标, 当前持仓)，不低于 0；
  - 永续空头：|目标| ≤ |当前持仓|，方向不变；
  - 反向开仓的部分去掉。

  策略主动减仓、卖出照常执行，加仓的部分被截掉，并按第 3 节每天告警一次（只在确实截掉了买入时才告警）。受管持仓不在目标里的，照常按目标 0 卖出（隐式目标 0）。下架前 24 小时，事件中心再用 `DELIST_FLATTEN` 显式平掉剩下的。
- **标的已经不能交易时**（下架后，标的状态不再是 TRADING）：整项跳过，不买也不卖。

“只减不增”要在下面三处生效。任何一处不改，下架后组合都会一直卡在 BLOCKED：

1. **接收目标**（eventconsumer/target.go:410-418）：现在目标里有一项不受支持（非保持）就整份拒绝。名单里已经不能交易的标的，改成只跳过这一项。
2. **隐式目标 0**（executor.go:742-763 的 `laneIDs`）：还能交易时照常进入，按目标 0 卖出；已经不能交易时不进入。
3. **阻塞判断**（executor.go:566-568、600-608、632-639、310-334）：找不到可交易标的的受管余额和持仓，现在会记为 blocked，进而把整份目标置为 BLOCKED。名单里的不再记 blocked，下架后剩下的零头也不会卡住组合。匹配方式：
   - 永续持仓按（交易所、SWAP、交易所代码）匹配；
   - 现货余额按 base_asset 匹配，而且只匹配 SPOT 的名单条目，避免永续下架把同名的现货余额也豁免掉。

“只减不增”的截断放在 weight_resolver 把权重换成数量之后、执行器算差额之前，按每个执行账户的当前持仓截断。

**`DELIST_FLATTEN`** 复用清仓的执行框架，按伪市价单（滑点 3%）卖掉或平掉，和现有清仓有下面几处不同：

- **不暂停组合**：不改组合的自动执行状态（现有清仓会先置 PAUSED，flatten.go:196-201）。
- **只看这一个标的**：请求里写明标的，清仓框架的每一步都只看它，包括撤单与撤单确认（`hasCancelableOrders`、`confirmAccountCancellations`，flatten.go:589、644-672）、恢复子单（546）、剩余计算（`remainingForAccount`，988）、平仓循环和完成判断（516-520）。现有清仓每一步都按整个账户算；下架清仓不暂停组合，执行器照常持有别的标的、也有挂单，不收窄就会每轮记 PARTIAL，永远完不成。
- **互斥**：同一组合里，不同标的的 `DELIST_FLATTEN` 不互相判为冲突（同一公告常常一次下架好几个币）。它们都要拿组合锁（flatten.go:170），实际是排队执行，后来的返回“忙”。遇到整组 `FLATTEN` 或 `REDUCE` 正在运行，或拿不到组合锁（flatten.go:170），返回“忙”，事件中心稍后再试，不计入重试次数。反过来，发起整组 `FLATTEN` 或 `REDUCE` 时，现有检查（flatten.go:185、311）只看 FLATTEN，要扩展成也把运行中的 `DELIST_FLATTEN` 算作忙。
- **重启恢复**：`ResumeOperatorAction`（operator/service.go:395-430）和工作线程恢复动作的入口（service.go:408）现在只认 FLATTEN、MANUAL_ORDER、CANCEL_ORDER、SUBMIT_ORDER，要加上 `DELIST_FLATTEN` 和 `REDUCE`。否则重启后这两类动作停在 RUNNING，还会挡住恢复自动执行（logicalaccount/service.go:411-419）。
- **幂等**：沿用现有规则。同一个 `action_id` 要求组合、类型、reason、请求内容完全一致，否则返回冲突（operator/service.go:998-1004）；已完成的直接返回旧结果（flatten.go:147-149）；FAILED、PARTIAL 用同一个号再调会重新执行（flatten.go:209-212）。reason 由事件中心在创建动作时生成并存下，重试时原样使用，保证同一个号的请求一致；复查是新的一轮，用新的 `action_id`。
- **不算冲突**：执行器的冲突判断（executor.go:286-297）里，属于 `DELIST_FLATTEN` 动作的 OPERATOR 单不算冲突，不暂停组合。`DELIST_FLATTEN` 运行期间，执行器跳过这个标的，不和它同时下单。
- **解除禁止就停**：`DELIST_FLATTEN` 每一轮都先查下架名单，发现已经解除（误报被取消），就撤掉本动作的订单并结束。动作记为 COMPLETED，结果里带“已解除禁止”的标记，不记 FAILED 或 PARTIAL，免得事件中心按规则重试。否则执行器恢复买入、清仓继续卖，会来回成交。

`REDUCE` 本来就要暂停组合、撤全部订单，保持现有行为。

统一账户只做合约时同样生效（qronos 在这种情况下跳过，是个漏洞）。

**保证金率监控**：

- 普通账户：合约钱包权益 ÷ 合约持仓名义 ≤ 阈值（默认 0.5）时触发。
- 统一账户：uniMMR 低于阈值（默认 1.5）时触发。
- 动作：暂停组合，发起 `REDUCE` 人工操作，把现货和合约同比例减仓（默认 10%）；普通账户再把现货钱包的 USDT 归集回合约钱包。前后都告警。
- `REDUCE` 复用清仓的操作记录和执行框架：清仓就是比例为 100% 的减仓。用户确认安全后手动恢复组合。
- 清仓按“剩余为 0”逐轮重算（flatten.go:432-516），按比例减仓不能这样做，否则每次重试都会再减一次。所以发起 `REDUCE` 时，就把每个标的的目标数量写进请求，之后各轮都收敛到这个数量。

## 6. 依赖与顺序

- 阶段 1A 与策略计划 S1 同一分支、同一次发布（第 3 节的编译期依赖）。1A 只需要模拟盘链路就能联调：行情由 T4 的公共行情接口提供，1A 期间不开放实盘建账户。真实交易所接入（1B）随后单独发布。
- 1A 内部：T2、T3 先做；T4 先于 T10～T12。
- 1B 内部：T5 先于 T6、T7；T7（统一账户）是用户实盘的前提，优先于 T6。
- 阶段 2～4 可以在阶段 1 之后分批发布，依赖只有 T14 → T15～T20、T22 → T23～T26。
- T27 是事件中心 C6 的前提。T27 的服务目录 acl 要引用 callback-dispatcher，服务目录会拒绝未知的调用方（validate.go:144），所以 T27 依赖事件中心 C2 先登记组件；T5c 的“apply 后检测”依赖 T5 的 `InspectExchangeCredential`。

## 7. 风险

1. **同名交易所代码**：币安现货和合约都叫 `BTCUSDT`，任何漏加市场的键都会串数据。T3 用 `SymbolKey` 类型配合编译器找全，并用同名样例覆盖所有表和缓存。
2. **统一账户没有测试网**：papi 的真实行为只能靠官方样例和用户本人小额验证。
3. **划转没有幂等键**：网络超时可能重复划转，靠本地记录加查询对账兜底。
4. **普通账户两路私有流**：任一路断开都会漏成交。断线期间不下新单，恢复并补拉成交后才继续。
5. **改动面大**：约 100 处按账户市场的判断都要改成按标的市场，靠 T3、T10、T12 的混合持仓测试兜住。
6. **阶段化执行**：阶段从当前状态和划转表推出，重启后要能接着走。T11 要覆盖“阶段中途重启”和“划转刚完成就重启”的用例。

## 8. 不做

1. 分钟偏移。
2. 借币、现货做空、币本位合约、期权、交割合约。
3. 自动修改交易所的账户设置，例如开联合保证金、切持仓模式。唯一例外是用户在资金设置里显式开启的 BNB 抵扣开关。
4. 下架检测（移到采集模块 Collector，见事件中心计划第 6 节）；抓取交易所公告网页。
5. 提现和跨账户划转。
6. 资金流水落库。
