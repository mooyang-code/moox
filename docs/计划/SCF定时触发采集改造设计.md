# SCF 定时触发采集改造设计

状态：设计稿 v2（2026-10-11），尚未编码。已吸收独立评审的四轮意见，结论为可进入实施计划（见第 17 节）；实施前仍需按第 15 节确认未决事项。

## 1. 背景与目标

### 1.1 现状

crypto 空间当前由 Collector 每分钟规划采集批次，通过 CloudNode 以异步 Invoke 调用香港的 80 个 SCF 函数；函数抓取币安 K 线，经 Access 写入 Storage，并向 EventBus 发布批次完成事件。stockcn 已有一套“定时触发 + 向 Collector 领取批次”的实现，但从未上线。

2026-10-11 修复函数环境后的基线（759 个 1m 批次，**批次完成口径**）：

| 指标 | p50 | p90 | p99 |
| --- | --- | --- | --- |
| K 线收盘到批次完成 | 9.0s | 17.2s | 22.5s |
| 批次派发到完成 | 2.4s | 4.9s | 7.5s |

收盘到派发约 6.6s，全部消耗在 Collector 的规划与派发排队。此外：

- Collector 的 SQLite 每分钟写入数万行（每周期、每标的的实例与批次条目），是性能热点。
- 函数环境（EventBus CA、调用方密钥、Storage 应用密钥、Access 地址）在重新部署后整体失效，函数全部失败，需要手工刷新 80 个函数。
- 周期完成与降级的裁决早已在 Storage DataNode 完成（见 `docs/模块/存储.md`“周期”章节）；Collector 只在规划时登记周期。

### 1.2 目标

1. crypto 与 stockcn 统一：由腾讯云定时器触发函数，Collector 不再派发任务，也不再用 Invoke 重试。
2. 实时链路不依赖 Collector：函数持有分配缓存，并向 Storage 解析权威版本后直接提交。
3. crypto：收盘到 Storage 接受，周期口径 p99 不超过 8 秒（口径见第 11 节）；stockcn 不适用该目标。
4. 提供手动与自动的 K 线完整性检查、补采能力。
5. 去掉函数侧 EventBus 依赖；去掉自建服务端 TLS（主机网关 11003、EventBus 4222），只保留浏览器到 Console 的证书；同时补齐去 TLS 后必需的最小认证与完整性措施（第 8 节）。

### 1.3 非目标

- 不做新旧并存的兼容层：项目尚未上线，旧调度、旧表、旧页面直接删除。第 14.2 节的“回滚窗口内暂留旧表”只是发布期的保险，窗口结束后物理删除。
- 标的变更不要求实时生效。
- 不保证 SCF 到 Access 链路的保密性（明文 tRPC 加签名，已接受）。
- v1 不做 Storage 自主生成周期、追加式序列索引、分布式限流服务。

## 2. 已确认的决策

| # | 决策 |
| --- | --- |
| 1 | 两个空间统一为 Timer 模式；Invoke 仅用于非实时的修复与运维 |
| 2 | 分配（gzip 加 base64）写入函数环境变量，**作为缓存**；权威版本与工作清单在 Storage |
| 3 | 每函数标的数可配置；合约默认 40，现货默认 30，首批灰度约 20；容量校验不通过仍拒绝部署 |
| 4 | 现货放南京（`data-api.binance.vision`，经南京内网 Access 写入），合约放香港 |
| 5 | 标的变更不要求实时：标签同步后在固定窗口计算新分配，成员变更全量重发 |
| 6 | 失败时 Collector 不干预；手动检查、手动补采是一等功能；Collector 另做有界自动补采 |
| 7 | 函数不再连 EventBus；诊断走 CLS、Storage 指标和 Monitor |
| 8 | 主机网关 11003 与 EventBus 4222 去掉自建 TLS；仅浏览器到 Console 保留证书 |
| 9 | 云防火墙白名单由 CLI 在 `setup init` 的防火墙对账中配置，并集成到 moox-skill |
| 10 | 延迟验收：crypto 收盘到 Storage 接受 p99 ≤ 8s；拉行情目标 ≤ 3s |
| 11 | 接受 SCF 到 Access 链路明文，接受 NATS 令牌被冒用的**角色权限内**风险 |

## 3. 总体架构

```text
Collector：计算分配 → Storage PreparePlan → 分发分片到函数环境 → 读回校验
           → Storage ActivatePlan（CAS，激活与占位覆盖校验同一串行裁决）→ 持续预登记周期占位
           → 检查与补采（非实时）
SCF 函数：定时触发 → ResolveFunctionWork 取得本次应执行的数据集、频率与版本
           → 拉取目标 K 线 → 按版本提交 Storage
Storage：  持久化版本与激活记录 → 绑定周期成员 → 裁决 complete/degraded
           → 生成 CollectorPeriodCompleted → 受理修复写入
Monitor：  读 Storage 与 View 状态；inventory 持久化，不依赖 Collector 在线
```

Collector 宕机只影响：发布变更、预登记保障、检查与补采；不影响已激活计划下的实时采集。

## 4. 核心概念

| 对象 | 内容 | 变化时机 |
| --- | --- | --- |
| 计划（稳定 ID） | 一个空间下某数据源的采集计划：数据集、频率、允许迟到时间的策略版本 | 创建、停用、策略修改 |
| 序列版本 | 数据集的全部序列、稠密全局索引、`series_hash`、成员有效范围 | 标的或序列定义变化 |
| 分配版本 | 哪个函数负责哪些序列，以及抓取与写入目标 | 扩缩容、迁移、成员变化 |
| 周期实例 | 键为 `(space_id, dataset_id, frequency, period_time)`；绑定的版本、截止时间、成功位图、终态 | 每个有效周期 |

约束：

- 版本一经创建不可变。成员不变而归属变化时，`series_hash` 可能不变，所以 Storage 必须同时校验分配版本，阻止旧归属写入。
- 全局稠密 `series_index` 随成员变更重排，所以任何成员变化都全量重发该数据集的所有函数；v1 不做追加式索引。
- 一个周期一旦绑定版本，成员、索引、截止时间都不再修改。
- “周期时间 P”一律指目标 K 线的开始时间（`period_time`），不得与 Timer 触发时刻混用。
- **共享抓取**：多个任务共用同一标的的一次抓取时，可共用原始 bar，但每个目标数据集的 `series_index`、版本、截止时间和提交回执**各自独立**，不能用一份全局索引解释所有目标。

## 5. Storage 设计

### 5.1 计划版本与激活

- **PreparePlan**：持久化不可变版本（序列版本、分配版本、抓取与写入目标）。返回版本号。
- **ActivatePlan**：以 CAS 方式声明“版本 V 自周期 P 起生效”。CAS 的前置值是该计划**最近一次已提交的激活记录**，不是“当前墙钟下活跃的版本”。激活不得修改已开始或已冻结的周期；激活时校验新计划在 P 之后已有足够的预登记占位覆盖，**首次激活（新增数据集或频率）必须与占位登记同属一个串行裁决，发布器崩溃不能留下无占位的已激活计划**。幂等，带发布操作 ID；结果不明时调用方先查询，不得猜测失败。
- **DeactivatePlan**：停用计划时，尚未开始的占位明确撤销，已开始的周期按原规则裁决。
- **GetPlan**：按版本读取内容与激活状态，用于函数回源补取分片和管理台展示。

版本记录与周期绑定由数据集所属 DataNode 串行裁决，沿用现有 Primary 周期 RPC 的 `space_id + dataset_id` 路由。

### 5.2 函数工作解析：`ResolveFunctionWork`

**问题**：若只按数据集解析版本，热实例持旧环境时不会知道新增了数据集或频率，也就不会去查询，“缺版本回源”无从发现新增工作。环境是缓存，不能让缓存决定“哪些工作值得向权威查询”。

**设计**：函数每次触发先调用 `ResolveFunctionWork(function_id, scheduled_at, manifest_digest)`：

- 输入：函数标识、计划触发时间、函数已持有的分配摘要。
- 输出：本次应执行的（数据集、频率、目标周期）列表，每项带生效版本、截止时间和函数在该版本下的分片；摘要命中的项只返回版本与截止时间。
- 没有工作时返回 `no_work`；函数在新版本中被撤销分配时同样返回 `no_work`。
- 对尚未登记的周期按“版本引用”登记并绑定成员，不再要求函数上传整库快照。
- Storage 无法解析版本时，函数不得擅自使用旧版本执行新周期。
- 缓存只允许缓存不可变的版本内容与已冻结的具体周期映射，不缓存笼统的“当前版本”。

单数据集的解析语义是 `ResolveFunctionWork` 的内部步骤，不单独暴露。检查与补采只使用 5.6 的只读状态查询，**不得调用会登记周期的解析路径**。

### 5.3 周期预登记（占位）

- Collector 周期性（默认每小时）预登记未来 N 小时的周期**占位**：保存周期键、**稳定计划 ID**与**截止时间策略版本**，**不绑定成员版本**，所以不会阻塞之后的版本切换。
- 截止时间由策略版本确定，首次函数请求不得自行决定；策略修改只影响尚未登记的周期，已登记占位的截止时间保持不变。
- 到允许绑定的边界后，由首次解析或 Storage 的 deadline worker 根据历史激活记录绑定版本；禁止提前解析而冻结未来周期。
- 所有函数都未触发时，deadline worker 仍从占位生成零完成度的 `degraded`。
- 超过预登记 horizon 的 Collector 故障窗口可以接受，但承诺要明确：可能没有按时产生 `degraded`，恢复后识别为“当时未登记”，不补造看似按时完成的历史记录。Storage 暴露预登记覆盖水位，Monitor 在 horizon 耗尽前告警，告警不依赖 Collector 存活。

### 5.4 截止时间

`deadline = 该根 K 线收盘时间 + 数据集允许迟到时间`（`allowed_lateness` 按策略版本，crypto 与 stockcn 分别配置）。旧的“调度时刻加约 12 分 25 秒”（含多轮派发与重试预算）作废。

- 实时结果：截止时缺失即 `degraded`，因子及时继续。
- 最终完整性：之后仍允许修复，但原始终态不变，不把“后来补齐”伪装成“当时按时完成”。
- 8 秒是延迟目标（SLO），`allowed_lateness` 是决定 degraded 的业务参数，两者分别设定。

### 5.5 修复：`RepairTimeSeriesBatch`

- 默认只补缺失；覆盖已有行必须显式 `force`。
- 按每行所属历史周期校验版本、序列身份和时间范围，不得按当前分配解释历史。
- 原始 `complete/degraded` 及截止时完成情况保持不变；单独更新“当前覆盖情况”，并原子保存行、覆盖进度、写入回执及行变更 outbox。
- 不再次发送原始周期完成事件。
- 跨版本的历史抓取结果在提交时按历史绑定拆分。
- **未登记周期的修复**：根据历史激活记录建立修复用元数据，记 `original_registration=missing`，更新当前覆盖，不补发原始完成事件，不伪造截止时完成情况。
- **过保留期**：禁止自动修复；如需恢复只能走显式的历史导入。版本、回执与去重记录的保留期至少覆盖允许的事件重试期与修复窗口。
- 修复后“缺口归零”限定为数据源仍提供、且应当存在的数据；停牌、超出数据源保留期等必须有终止原因，不得无限自动补采。

### 5.6 状态查询扩展

`GetDatasetPeriodStatus` 只需要周期键，不应要求检查器先提供正确的 hash/count；返回：

```text
registration_state       已登记 / 占位 / 未登记 / 过保留期
original_status          waiting / complete / degraded
cutoff_progress          截止时的成功数与 missing_series_indexes
current_progress         当前的成功数与 missing_series_indexes
series_version / assignment_version
deadline_at / observed_at
retention_watermark
```

- `missing_series_indexes` 是期望集合减成功位图，**不是**显式失败列表（未触发的序列同样缺失）。
- 提供有界的周期列表，避免页面或检查器逐分钟 RPC。
- 只读：检查不得为了检查而创建周期。未登记周期的 `original_status` 与 `cutoff_progress` 返回“未知/不存在”，不得伪装成 `waiting` 或零完成。

### 5.7 幂等标识（三层）

| 标识 | 含义 | 规则 |
| --- | --- | --- |
| 逻辑批次 ID | 汇总同一周期的工作 | 由周期、版本、函数分片、频率决定 |
| 写入 ID | 一个内容固定的提交分块 | **同 ID 不同内容必须被拒绝**（存载荷摘要比对），不是文档约定；新子集、新分块、强制重拉使用新写入 ID |
| 尝试 ID | 一次实际执行 | 仅用于诊断，不能替代持久化写入去重 |

现有 Storage 按 `source_event_id + space + dataset` 去重整组写入，且调用方在缺少同步点时回退到批次 ID；改造后必须按上表拆开。

## 6. 函数设计

### 6.1 触发与执行

1. 定时器触发。**周期由事件的计划时间决定**；现有 `timerNow()` 在时间解析失败时回退到 `time.Now()`，这与“不得冒充当前周期”冲突，新路径必须**拒绝缺失或非法的时间**。事件 `Time` 字段的实际语义（延迟投递、重试时是否保持原计划时间）需要通过实验确认。
2. 调用 `ResolveFunctionWork` 取得本次工作与版本。
3. 拉取目标 bar（实时路径只拉目标那一根，保持 `RequirePeriodCommit` 语义）。
4. 按版本与历史绑定提交 Storage；Storage 拒绝版本不符的写入；**未完成权威解析之前禁止提交**。
5. 结构化日志写 CLS，统一带周期、版本、函数、逻辑批次、写入、尝试 ID。

**解析与抓取只有条件并行**：缓存命中且最终解析结果一致时，预取的行情可复用；版本变化后仅复用抓取身份完全一致的结果；新分片、新频率、变更的数据源仍须解析后再抓取。切换或缓存缺失时按“解析后抓取”的串行路径验收，并行收益不作为预算的固定前提。

正确性依赖持久化幂等与版本校验，不依赖进程锁、热实例缓存或“同一个函数只有一个实例”。重复触发、丢触发、函数并发实例都按正常情况处理。

### 6.2 环境变量

- 分配表（分片、数据源、市场、频率、`series_tag`、输出字段、目标数据集、全局索引、例外 symbol）gzip 加 base64 放进**一个**环境变量，保存 current 与可选 next 两份版本。
- crypto 的交易所 symbol 由标的 ID 去连字符推导，只存例外。
- 实测压缩后每标的约 4 到 6 字节；单函数 40 个标的远小于 SCF 环境变量 4096 字节上限（含约 1.5KB 基础环境）。预算校验按完整最终值计算（current 与 next、写入绑定、全局索引、DNS、凭据、字段名、base64 膨胀），复用现有校验。
- 定位是**缓存**：SCF 官方没有“更新 Active 后所有热实例立即刷新环境”的保证，所以版本与工作清单以 Storage 为准。
- 不再包含 EventBus 凭据与 CA；保留 Access 地址、调用方身份与密钥、Storage 应用密钥、DNS 路由、限流参数。
- **内存不是环境参数**：它是 SCF 的部署配置，由部署 API 设置；`node.go` 当前把行情 Timer 函数内存硬编码为 64MB，需要解除并作为实验参数。

### 6.3 错误返回与重试

现有 handler 多处返回 `Success:false, nil`，SCF 不会据此重试。需要定义明确的可重试错误返回方式；异步重试次数、事件保留期、死信与告警显式配置，避免默认两次重试和最长六小时积压与当前采集争抢资源。

### 6.4 cron 与错峰

- 按函数服务的频率集合生成：只有 1h 的函数不必每分钟触发。一个函数服务多频率时，执行与写入按“数据集加频率”分组，整点重叠负载要单独校验。
- 腾讯云 cron 的秒字段只支持整数，错峰实现为“整数秒触发 + 函数内确定性延迟（由函数标识哈希得到）”，并把实际触发迟到与人为错峰分开计量。

## 7. Collector 设计

### 7.1 分配计算

- 在标签同步后的固定安静窗口计算；新标的放入最空的函数，下架标的留空位，不洗牌，减少数据搬迁。
- 一个函数服务多个任务时，每函数标的数取较小值。
- 每函数标的数是任务（数据集）级参数，校验见第 10 节；超限配置直接拒绝并说明原因。

### 7.2 发布状态机

1. 持久化新版本（Storage PreparePlan）。
2. 准备新函数、分发 next 到所有受影响函数，读回校验配置与代码版本。
3. 更新触发器 cron：**旧 cron 必须覆盖边界前的工作，新 cron 必须覆盖边界后的工作**，不能只原子切换分片。
4. 在 Storage ActivatePlan（CAS，周期 P 之后，提前量默认 5 分钟）。
5. 把 next 提升为 current，清理已撤销的触发器（缓存整理，失败不影响正确性）。

规则：**激活提交前继续旧版本；提交后所有执行服从已提交记录；提交结果不明时先查询。**

发布记录包含前置版本、目标版本、边界、完整函数清单、每个分片摘要、部署确认及操作 ID。配置更新、代码发布、DNS 更新、密钥轮换、触发器变更纳入同一发布互斥与版本校验；新压缩字段加入 CloudNode managed-key 白名单。

**密钥轮换**不能只靠环境更新：热实例持旧密钥时，连 Storage 回源都无法完成。必须有**双密钥接受窗口**（Access 与主机网关同时接受新旧密钥）、实例更新验证和旧密钥退役条件。

### 7.3 检查与补采

**检查** `moox-cli collector kline check`：按历史版本、交易日历和 `[from,to)` 生成应有（序列 × 时间点），对比 Storage 的 `cutoff_progress` 与 `current_progress`；输出机器可读结果（版本、数据集、频率、序号、缺失时间段、原因、检查时间），连续缺口合并显示。可选深度检查：读取物理行验证 OHLCV 字段齐全。

**补采** `moox-cli collector kline backfill`：

- 默认消费检查结果，执行前再次验证缺口；按序列与连续时间段分块；单次每序列至多 1000 根。
- 复用现有历史批次形态（catchup/gap_repair：一个 item、1 到 1000 根）和抓取、过滤、标准化流程，写入走 `RepairTimeSeriesBatch`。
- 持久化运维作业、分块、写入 ID、进度和取消状态，支持中断恢复。
- **并发上限指实际并发执行的实例数**：异步重试会让同一个函数名产生多个执行实例，所以使用专用补采函数池，或持久化租约/执行许可；仅限制 Invoke 提交数不够。
- 以 Storage 写入回执与缺口复查关闭作业；异步 Invoke 返回成功只代表请求被接受。
- 实时与补采使用独立资源预算；补采权重也要计入（合约 `limit=1000` 权重为 5）。
- `--force` 使用新的写入身份，并明确是否触发因子重算。

**自动补采**：定时扫描已过 deadline 的周期，持久化扫描水位并保留重叠窗口；Collector 恢复后追赶停机区间。每轮行数、请求权重、并发和每日预算有上限，不得挤占实时采集。修复完成不意味着历史因子自动重算，因子重算保持独立的显式操作。

### 7.4 清理

直接行情采集链路上删除：`ClaimTimerBatch`、`MarketFetchRuntime` 服务（proto、生成代码、RPC 注册、tRPC 配置、服务目录、Access 权限）、`t_collector_timer_period_batches`、调度器的派发与重试、每地域保留的 Invoke 辅助函数、`timer_function_count` 历史字段名、`StorageWriteConsumer` 对 `task_instances` 的更新、完成事件消费者与函数批次完成事件发布、指标 EventBus reporter；以及避免继续每周期复制全量 `PeriodSeriesSnapshot`（改为不可变版本复用）。

**必须保留**：`kline_resample` 的 Runner、本地 readiness 与 inventory 分支所用的 `task_instances`；清理只针对直接行情采集，重采样要保留或另做完整替代。

## 8. 去 TLS 与认证、完整性

### 8.1 范围与影响面

“去 TLS”限定为**MooX 自建服务端 TLS**：主机网关 11003、EventBus 4222。保留：Console 9527 的 HTTPS、第三方 HTTPS 客户端信任（出口代理访问币安等）、SSH 主机密钥校验。

| 范围 | 必要调整 |
| --- | --- |
| `gatewayclient` | 内部模式不再强制 `CAFile`，远程端点与连接池不再启用 TLS；配置加载、端点构造、连接池隔离与测试一起调整 |
| hostgateway | 远程 listener 不再强制 TLS 材料；`hostgatewayconfig`、`LoadIdentity` 重构；持久 nonce 保留 |
| 网关控制面 | 控制面客户端独立持有 TLS 连接池，不会随普通 gatewayclient 自动改好 |
| unitinstall / unitbundle / unitbootstrap | 去掉证书校验与 EventBus 非 TLS 拒绝；身份包格式、注入、收据、bootstrap、恢复流程同步修改 |
| Admin PKI | 清理自建内部 PKI、host bundle 签发与相关 CLI；**签名密钥管理与 Console 证书管理保留** |
| EventBus 服务与公共客户端 | 服务配置校验与 jetstream 客户端当前都拒绝远程明文，需同步修改；broker、内部管理客户端、广告地址、凭据文件一起改 |
| EventBus 凭据生命周期 | 删除证书部分，保留角色令牌、ACL、权限隔离与轮换；不得因此重置 JetStream 数据与消费者 |
| Monitor / HostAgent | HostAgent 发布器去掉显式 CA；Monitor 的 Console 页面 HTTPS 探针保留，不能全局删除 CA 字段 |
| Access → 主机网关 | 验证请求与响应保护、连接复用、压缩、路由保持正确 |
| egress proxy | 内部 tRPC 随网关改造；代理访问第三方的 HTTPS 与证书校验保留 |
| moox-cli | 现有隧道经 SSH 转发到目标 `127.0.0.1:11002`，不依赖 11003 TLS，无需改动 |
| 脚本与运行配置 | deploy、watchdog、SCF 打包、环境校验、示例配置中的 `tls://` 与 CA 要求同步清理 |

### 8.2 去 TLS 后必须补的最小措施

用户接受“明文 + 防火墙白名单”，但评审指出以下三项属于**让现有认证仍然成立的前提**，成本低，纳入设计：

1. **网关快照中的验签密钥不得明文下发。** 主机网关从 Admin 拉取的快照（`GatewayVerificationKey.secret`）包含实际 HMAC 密钥，明文传输等于任何嗅探者都能伪造任意调用方。方案：快照中的密钥用**每主机密封密钥**（AES-GCM；该密钥在主机 bootstrap 时仅经已验证主机身份的 SSH 加密通道一次性安装）加密；密封密钥随主机身份轮换。契约：明确密封密钥在 Admin、主机及备份中的保管；GCM nonce 不重复，AAD 绑定主机、密钥身份与版本；轮换可恢复）。（长期可改为非对称签名、快照只含公钥，作为后续演进，不在 v1。）
2. **授权相关元数据必须进入签名。** 当前客户端先签名、后附加 `X-Space-Id / X-User-Id / X-User-Role`，明文下可被篡改。这些参与授权与数据隔离的上下文与编码类型要纳入签名，或由已认证身份重新推导。
3. **响应要有完整性保护。请求与响应 MAC 使用不同的域标识或派生密钥，覆盖控制面及 Access 两跳，校验失败不得降级接受。** 当前响应没有应用层签名，版本解析、写入回执、查询结果都可能被篡改。用同一调用方密钥对“请求 nonce、目标身份、状态码、响应摘要”做 MAC，错误响应同样覆盖；客户端校验失败按网络错误处理。

另需明确：

- Storage `AuthInfo.app_key` 目前放在请求体中，长期凭据以可复用原文跨明文链路传输。v1 记录为已知风险；后续应改为由网关已认证的调用方身份授权，去掉请求体中的 app_key（单独立项）。
- NATS 令牌不受网关 HMAC 与 nonce 保护，被获取后攻击者可在可达 broker 时行使该角色权限（包括 Storage 角色发布周期完成事件）。接受的是**角色权限内的冒用风险**；若仍要求“可信完成事实只来自 Storage”，对关键事件增加独立生产者签名，或消费前向 Storage 核验（列为后续项）。
- 防火墙白名单限制连接来源，不能防止合法路径上的嗅探与篡改。

### 8.3 防火墙白名单（CLI 与 skill）

- `setup init` **已经调用**防火墙配置并拒绝 partial 结果；本次是扩展现有对账，不是新增接入。
- 现有 `EnsureFirewallRule` 主要是查重后添加，不会收窄旧宽规则。扩展为按来源对账：
  - 11003、4222：仅放行放置清单中各主机的公网与私网地址；
  - 11004（Access）：保持公网（SCF 来源地址不固定，无法白名单），南京 SCF 走私网地址；
  - 9527：公网；11012 健康端口：仅对 control 放行。
- 对账需覆盖：关联安全组中的重叠规则、端口范围、IPv6 宽规则，不能只删除一条精确的 `0.0.0.0/0:11003`；输出差异；规则条数上限纳入检查。

## 9. 压缩

压缩是两跳，分别启用、分别测量：

1. SCF → Access：由函数环境 `MOOX_GATEWAY_COMPRESSION=gzip` 控制（已实现）。
2. Access → 主机网关：由 Access 自己的 `gateway_client.compression` 控制。香港 compute-1 的 Access 已启用 gzip；南京存储主机上的 Access 与主机网关同机，走回环，不压缩。

## 10. 容量设计

### 10.1 限流参数化

现有拉取管线有两层并发与一层速率限制：`FeedGuard`（默认 5 请求/秒、burst 5、并发 1）、流水线 `Request.Concurrency`（默认 5）、HTTP 连接并发。它们是代码保守默认，不是币安的限制。以下都要做成环境参数并按数据源下发：FeedGuard 的 rps、burst、并发，流水线并发，请求超时。**内存由部署 API 设置**（见 6.2）。

币安限制按**出口 IP**汇总：现货 6000 权重/分钟（K 线权重 2）；合约 2400 权重/分钟（`limit<100` 权重 1，100 到 499 为 2，500 到 1000 为 5）。分别核算：现货约 506×2=1012/6000，合约约 525×1=525/2400；还要计入其他频率、重试、补采，不能把两者相加当成同一个限额池。

- FeedGuard 是进程内限流，不是出口 IP 级限流，多个函数会叠加；先给同一出口的各函数静态分配保守预算。
- 币安域名尝试循环可能在一次 guard 调用内发出多个 HTTP 请求，一个令牌不等于一个物理请求；容量计算的 `q` 是物理请求数，含重试、备用域名与多频率重合。
- 腾讯云不保证“每个函数独立出口 IP”：同账号同地域同子网的函数可能共用网关或 EIP。南京上线前必须确认公网路径（SCF 公共出口还是 VPC 的 NAT）、不同函数与冷热实例实际出口 IP、NAT 的 EIP 池与连接容量。
- 必须遵守 429 与 `Retry-After`；418 不能通过切换域名绕过；记录 `X-MBX-USED-WEIGHT-*`。

### 10.2 容量公式与默认值

```text
C有效     = min(流水线并发, FeedGuard 并发, 实际连接并发)
并发耗时  = 冷连接 + ceil(q / C有效) × L(p95)
限速耗时  = max(0, q − burst) / rps + 最后一个请求耗时
拉取时间 ≈ max(并发耗时, 限速耗时)
```

单请求 p95 不能直接推导批次 p99；以完整批次耗时分布在 canary 中校准。若沿用 `rps=5, burst=5`，40 个请求仅等待令牌就要约 7 秒，所以**必须同时提高速率**，使限速耗时不成为瓶颈。建议初始参数（均待 canary 校准）：

| | 香港合约（`fapi.binance.com`） | 南京现货（`data-api.binance.vision`） |
| --- | --- | --- |
| 请求延迟 p50（已测） | 72 到 83ms | 233 到 373ms |
| 假设 p95 / 冷连接 | 200ms / 0.4s | 450ms / 1.0s |
| 并发 | 6 | 10 |
| rps / burst | 20 / 10 | 15 / 10 |
| 默认 n | 40 | 30 |
| 并发耗时 | 0.4 + ceil(40/6)×0.2 = 1.8s | 1.0 + ceil(30/10)×0.45 = 2.35s |
| 限速耗时 | (40−10)/20 + 0.2 = 1.7s | (30−10)/15 + 0.45 ≈ 1.8s |
| 函数数 | 约 14 | 约 17 |

上式只是**初筛估算，不是保守上界**：现有 FeedGuard 先占并发槽再等令牌，两者会耦合（例如南京现货首批 10 个请求各经历 1s 冷连接，理想模型也可能约 2.57s）。部署准入采用联合排队估算加实测裕量，并以冷热实例、多频率重合、重试和实际两跳链路验证整批耗时、周期 p99 与峰值内存，不能仅凭公式 ≤ 3s 放行。

Collector 的容量校验同时检查：上式拉取时间 ≤ 3s、环境预算、函数 60 秒预算（扣除 Storage 提交与指标预留）、数据源上限（TDX 实测安全值 40，不套用 30/40）、重试次数与多频率重合。校验不通过则拒绝部署，不以默认值掩盖。首批灰度约 20，每次只调整一个主要容量参数。

### 10.3 其他容量事实

- 1Mbps 的 compute-1：提交 gzip 后每分钟约 46KB，独占发送约 0.37 秒；真正要关心的是集中到达的突发与竞争流量，不能据此认定“不是瓶颈”。实时最新周期优先于历史修复，补采走独立预算。
- 并发提升到 6 到 10 时重点观测：HTTP Transport 复用与连接上限、TLS 握手、峰值 RSS 与 GC、429 后同出口其他函数是否继续请求。
- Storage 压测未覆盖 Access 路径，也不能外推为两倍以上规模的保证；需要在真实链路上重测。

## 11. 延迟预算与口径

**范围**：8 秒目标只适用于 crypto。stockcn 的默认错峰从第 5 秒开始、窗口 35 秒，且有 settle delay，不纳入统一的 8 秒预算。

**口径**：

- “Storage 接受”指**行与覆盖进度持久化成功**，不是 RPC 返回成功，也不是异步 Invoke 的 ACK。
- 同时记录两个指标：序列写入延迟，以及**周期最后一个应有序列的接受时间**（单函数 p99 ≤ 8s 不代表整个数据集周期 p99 ≤ 8s，函数越多最后完成者的尾延迟越大）。
- 缺失、超时、未触发必须进入覆盖率统计，不能只对成功样本计算 p99。
- 现有 22.5s 是批次完成口径，不能直接当作新口径的基线；canary 阶段先在同一数据集、频率和统计口径下测出新口径基线，再对照。

预算（p99，串行路径）：

| 环节 | 预算 |
| --- | --- |
| 触发错峰（整数秒触发 + 函数内确定性延迟，收盘后才拉） | ≤ 1.5s |
| 启动 + `ResolveFunctionWork`（含首次周期绑定） | ≤ 1.0s（压测中 Ensure 通常 0.13 到 0.5s，偶有 2 到 3s，预算尚无实测支撑） |
| 拉行情 | ≤ 3s（设计目标 2.5s） |
| 提交（经 Access） | ≤ 1.5s |
| 余量 | 约 1s |
| 合计 | 约 8s |

最可能破预算的环节：南京现货整批抓取（延迟高、冷连接、并发与令牌等待）、冷启动与首次解析、香港 Access→Storage 提交排队（1Mbps 与其他流量）、首次周期绑定的偶发慢请求。因此 8 秒目前是**正式门槛，不是已证明的容量结论**，以 canary 实测为准。

| 2 Storage 修复与查询 | `RepairTimeSeriesBatch`、持久化回执、status 扩展、保留水位、有界周期列表 | 修复原子更新行与当前覆盖，原始终态不变，重复写入不重复生效，未登记周期可合法修复 |
| 3 函数与 CloudNode | Timer 自主解析工作，保留目标 bar，支持历史修复；移除 EventBus 强制项；限流、并发参数与内存部署；更新环境白名单、权限、打包、触发器配置；严格 Timer 时间 | 无 EventBus 配置仍可采集，旧环境可发现新增工作并补取分片，错误版本零落盘 |

### 14.2 验收条件

- **正确性**：错误版本、错误分片、未收盘 bar 零落盘；重复触发不重复产生有效写入；同写入 ID 不同内容被拒绝；零错误版本接受、零虚假 complete、零静默丢失；每个应有周期都可解释为 waiting、complete、degraded 或明确未登记。
- **工作发现**：热实例持旧环境时，新增数据集或频率仍被 `ResolveFunctionWork` 发现并执行。
- **登记保障**：全部函数不触发时，已预登记周期按时 `degraded`；首次激活后发布器崩溃不留无占位的已激活计划；超过 horizon 后能明确识别未登记。
- **修复**：部分失败、提交成功但响应丢失、Collector 重启、跨版本补采、未登记周期修复均可恢复；修复后当前缺口归零（限定数据源仍提供的数据），原终态不变。
- **安全**：快照密钥不以明文出现在网络上；篡改的元数据与响应被拒绝；非法 Timer 时间被拒绝。
- **依赖隔离**：阻断函数到 Collector 与 EventBus 的网络，实时采集仍成功；Monitor 不因 inventory 刷新失败而停止所有检查，两者同时重启后检查仍继续。
- **故障演练**：发布一半崩溃、Collector 离线、Storage 写入丢 ACK、重复 Timer、旧事件跨版本重放、连续漏触发、补采取消后恢复、密钥轮换期间热实例仍持旧密钥。
- **容量**：确认实际出口拓扑；记录请求权重、429/418、执行分位数、峰值内存、提交耗时；两跳压缩分别测量。
- **延迟**：crypto 周期口径（最后一个应有序列的接受时间）p99 ≤ 8s，同时记录序列口径；缺失与超时计入。
- **覆盖时段**：crypto 至少跨多次整点、多频率重合、冷启动与一整天；stockcn 覆盖开盘、午休、收盘及非交易日。

### 14.3 灰度与回滚

- 灰度要用不相交的 ownership 范围或隔离 canary；从一个生产数据集切出少量标的时，周期 expectation 仍是该数据集的完整 universe，不能分别按“灰度集合”和“剩余集合”初始化同一周期。“绝不同时采集”按同一序列同一周期解释；若要求整个空间任一时刻只有一种方式，则不做生产小流量混合灰度，先用隔离 canary，再整空间交接。
- **回滚包**（不能只依赖 git tag `prod-baseline-20261009`）：旧代码包、环境与触发器清单、控制数据库快照、旧分配版本、明确的交接周期，以及**主机单元、EventBus 配置、凭据格式和防火墙状态**。回滚顺序：停止新入口并隔离新版本 → 排空或过期处理在途事件 → 恢复旧运行状态 → 从新的交接边界恢复采集 → 检查并补齐切换窗口。
- 不覆盖已写入的新行情数据；已提交的历史激活记录不改回去；旧表物理删除放在回滚窗口结束之后。

## 15. 风险与未决事项

| 风险 | 缓解 |
| --- | --- |
| 币安限流按出口 IP 汇总，南京出口可能共用 | 实测出口拓扑，按出口求和分配预算，记录权重响应头 |
| 8 秒目标预算偏紧、证据不足 | 错峰窗口 1.5s，canary 先测同口径基线，连接复用，启动与解析路径单独计量 |
| Storage 改动面大，且有数据一致性风险 | 阶段 1、2 先独立验证，重放与崩溃测试优先 |
| 去 TLS 后明文链路可被嗅探与篡改 | 防火墙白名单 + 第 8.2 节三项最小措施；`app_key` 明文、NATS 令牌冒用为已知风险 |
| Collector 宕机超过预登记 horizon | 暴露覆盖水位并告警；恢复后识别“未登记”并合法修复 |
| 公共交易日历 2026-12-31 到期 | 部署检查与告警 |
| 热实例持旧环境或旧密钥 | `ResolveFunctionWork` 回源；密钥双窗口 |

未决（实施前需确认）：

1. 密封与 MAC 契约（8.2）：密钥保管、nonce 与 AAD、域分离、轮换恢复、校验失败不降级；
2. 南京真实网络与权限：确认 `access@storage` 已部署、私网路由与来源地址正确，新增 RPC 授权到位，测出公网出口 IP、NAT 容量与共享权重预算；
3. 容量准入标准：10.2 为初筛估算，以实测整批耗时、周期 p99 与峰值内存为准；
4. 阶段 0 的生产切换顺序：与旧 SCF 的 EventBus TLS 依赖退出协调；
5. 周期与查询契约：实测 Timer 事件 `Time` 在延迟与重试时的语义；检查路径只读；未登记周期返回未知；
6. 因子重算的触发方式（v1 为显式操作）；是否在后续把快照密钥改为非对称签名。

## 17. 评审记录

2026-10-11 与独立评审（codex，`gpt-6-astra`，xhigh）四轮讨论，核实了代码与腾讯云、币安官方文档。对本设计产生实质影响的结论：

1. 直接行情的周期完成由 Storage DataNode 裁决，Collector 不应重新成为权威。
2. 函数无法独立构造完整周期快照，版本必须放 Storage；`next + effective_at` 不是原子协议，改为 prepared 加 CAS 激活。
3. “多拉 3 根自愈”在现有 `RequirePeriodCommit` 与周期终态语义下不成立，改为集中检查加修复接口。
4. FeedGuard 默认 5 请求/秒、并发 1，50 标的不现实；容量公式必须计入令牌等待，并同时参数化速率、burst、两层并发。
5. 预登记不能冻结成员版本，否则会阻塞版本切换，改为占位；占位需绑定稳定计划与截止时间策略版本。
6. 腾讯云不保证函数独立出口 IP，限流需按出口汇总。
7. 取消函数 EventBus 时需同步处理指标 reporter、监控规则、环境校验与打包脚本。
8. 只按数据集解析版本无法让热实例发现新增数据集，增加 `ResolveFunctionWork`。
9. 去 TLS 后，网关快照中的 HMAC 密钥、未签名的授权元数据、无签名的响应是三项必须补的最小措施；去 TLS 应作为独立基础设施阶段。
10. 并行抓取与解析只有条件成立；非法 Timer 时间不得回退当前时间；补采并发要限制实际执行实例；密钥轮换需要双密钥窗口。
11. 第四轮（v2 核对）：评审结论为“同意，可进入实施计划”，无主架构分歧；对密封密钥、南京私网 Access、容量参数三项自选方案均同意，并要求把容量公式限定为初筛估算、阶段 0 生产切换与旧 SCF 依赖协调、检查路径只读等写入契约（已纳入）。
