# SCF 定时触发采集改造设计

状态：v3 简化版（2026-10-11），独立评审结论“同意，可进入实施计划”，尚未编码。第 13 节记录了从 v1 到 v3 的演进与取舍，想了解“为什么这样设计”请先读第 0 节和第 13 节。

## 0. 设计原则

MooX 是**个人量化项目**。本设计按以下原则取舍：

1. **简单优先**：能用现有机制解决的，不新增概念；能接受的代价，不为它引入复杂协议。
2. **实时链路不依赖 Collector**：Collector 停机时，K 线照常采集和入库。
3. **小概率事件简单处理**：标的变更、任务变更是小概率事件，不追求无缝切换；切换瞬间少量周期记为 `degraded`，由补采修复即可。
4. **失败不在线干预**：函数失败不由 Collector 即时重试；缺口由检查与补采统一修复。
5. **不为证书付出可用性**：只有浏览器到 Console 使用证书，其他链路不用 TLS，避免证书过期、重建、分发遗漏导致整体故障。

## 1. 背景

### 1.1 现状

crypto 空间当前由 Collector 每分钟规划采集批次，通过 CloudNode 以异步 Invoke 调用香港的 80 个 SCF 函数；函数抓取币安 K 线，经 Access 写入 Storage，并向 EventBus 发布批次完成事件。stockcn 已有一套“定时触发 + 向 Collector 领取批次”的实现，但从未上线。

2026-10-11 修复函数环境后的基线（759 个 1m 批次，批次完成口径）：

| 指标 | p50 | p90 | p99 |
| --- | --- | --- | --- |
| K 线收盘到批次完成 | 9.0s | 17.2s | 22.5s |
| 批次派发到完成 | 2.4s | 4.9s | 7.5s |

### 1.2 问题

- **派发排队**：收盘到派发约 6.6s，全部消耗在 Collector 的规划与派发排队，函数实际执行只占 2～3 秒。
- **Collector 写放大**：SQLite 每分钟写入数万行（每周期、每标的的实例与批次条目），是性能热点。
- **环境脆弱**：重新部署后 EventBus CA、调用方密钥、Storage 应用密钥、Access 地址全部变化，线上函数全部失败，需要手工刷新 80 个函数。根因之一是函数依赖 EventBus（需要 CA 与凭据）。
- **Collector 是实时单点**：Collector 一停，采集就停。

## 2. 目标与非目标

**目标**

1. crypto 与 stockcn 统一为“腾讯云定时器触发函数，函数按环境变量里的任务自行采集并提交 Storage”。Collector 不再派发，也不再用 Invoke 重试。
2. 实时链路不依赖 Collector。
3. crypto：收盘到 Storage 接受，p99 ≤ 8 秒。
4. 提供手动与自动的 K 线完整性检查和补采。
5. 函数不再连接 EventBus；去掉主机网关 11003 与 EventBus 4222 的 TLS。

**非目标**

- 不做新旧兼容层：项目尚未上线，旧调度、旧表、旧页面直接删除。
- 不追求标的变更的无缝切换。
- 不做精确的出口 IP 核算：假设每个 SCF 函数的出口 IP 不同。
- 不做 SCF 到 Access 链路的加密（明文 tRPC 加签名）。

## 3. 总体方案

```text
Collector（每个空间一个协程，每分钟第 10 秒对账）
  读任务 + 读标签成员 → 计算每个数据集的标的集合 hash 与函数分配
  ├─ 没变化：什么都不做
  └─ 有变化：选生效周期 P → Storage 登记快照并在生效表追加“从 P 起用新 hash”
             → 并行更新函数环境变量（新旧两份都带生效起点）→ 失败的下一分钟重试

SCF 函数（腾讯云定时器触发）
  读环境变量 → 按目标周期时间为每个数据集选出生效的那份 → 拉取刚收盘的 K 线
  → 经同地域 Access（私网）提交 Storage，带上所选那份的 hash

Storage
  提交时周期不存在 → 查生效表确认 hash 正是该周期应生效的 → 按 hash 找快照 → 自动建立周期
  → 照旧裁决 complete/degraded → 发 CollectorPeriodCompleted
```

职责边界：

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| SCF 函数 | 按环境变量抓取与提交 | 不知道“数据集规则”，不连 EventBus，不登记周期 |
| Collector | 计算分配、选生效周期、登记快照、下发环境、检查与补采 | 不派发、不重试、不汇总周期完成 |
| Storage | 保存快照与生效表、建立周期、裁决完成、发完成事件 | 不懂标的规则与交易日历 |

## 4. SCF 函数

### 4.1 工作项与环境变量

函数**与数据集解耦**：它只看“抓哪个市场的哪些标的、哪个频率”，以及“结果写到哪些数据集”。一个函数只服务一个市场（现货与合约分开）。

```text
函数环境（压缩前示意）
  市场: binance 现货
  数据集段:
    (数据集 D1, 1m): [                                   按生效起点排序；平时 1 份，变更期间 2 份
      { 生效起点: 2026-10-11T12:00Z, hash: H1, 标的总数: 506, 本函数的标的→序号: {...} },
      { 生效起点: 2026-10-15T08:32Z, hash: H2, 标的总数: 507, 本函数的标的→序号: {...} },
    ]
    (数据集 D2, 1h): [ { 生效起点: ..., hash: ..., ... } ]
```

- **每份是完整的一套**：生效起点、hash、整个数据集的标的总数、本函数负责的标的及其序号。标的增删后排序会让许多标的序号整体移动，所以两份的序号各自独立，不能混用。
- **选份规则**：对每个数据集，取“生效起点 ≤ 目标周期时间”的那几份中起点最晚的一份；**没有任何一份的起点 ≤ 目标周期时，跳过该数据集**（不能因为只有一份就总是选它）。生效起点和周期时间都指 K 线的**开始时间**：目标周期恰好等于 P 时选新份。例如 1h 数据集 P=13:00，新份第一次用于 13:00 开始、14:00 收盘的那根，即 14:00 那次触发；日线同理。
- 这些“生效起点 + hash”正是 Storage 生效表（5.1）中对应的行，由 Collector 在同一轮对账中先写 Storage、再下发环境，两边一致。

- **合并同类请求**：函数在每次触发时，把各数据集选中那份里的标的按“标的 + 频率”合并，同一标的同一频率只抓一次，再分别写入各个目标数据集（各用各的序号与 hash）。新增任务时若标的已在抓，只是多了一个数据集段，不增加请求。
- 现货与合约是不同市场的不同标的，分配到不同函数（通常也在不同地域）。
- 一个标的同时有 1m 和 1h 时，是两个抓取单元（币安按周期返回 K 线），但放在同一个函数里，1h 只在整点那次触发时执行。
- 整个结构 gzip 后 base64，放进**一个**环境变量。crypto 的交易所 symbol 由标的 ID 去连字符推导，只存例外。实测压缩后每个标的约 4～6 字节，每份额外的生效起点、hash、总数约 100 字节；单函数 50 个标的、变更期间两份同时存在，也远小于 SCF 环境变量 4096 字节上限（含约 1.5KB 基础环境）。预算按完整最终值（变更期间的两份）校验，复用现有的环境大小校验。
- 环境变量里**不再有 EventBus 凭据与 CA**；保留 Access 私网地址、调用方身份与密钥、Storage 应用密钥、DNS 路由、限流参数。

### 4.2 执行流程

1. 定时器触发，**周期由事件的计划时间决定**。现有 `timerNow()` 在时间解析失败时回退到当前时间（`handler.go:125`），新路径改为拒绝缺失或非法时间，避免延迟投递的旧事件冒充当前周期。
2. 确定本次到期的频率（1m 每分钟，1h 只在整点），算出各自的**目标周期时间**（刚收盘那根 K 线的开始时间）。
3. 对每个到期的数据集，按目标周期时间选出生效的那份（4.1 的选份规则）；把选中各份的标的按“标的 + 频率”合并去重。
4. 拉取刚收盘的那一根 K 线（实时路径只拉目标那一根）。
5. 按数据集拆分，每个数据集一次 `CommitTimeSeriesBatch`，带上**所选那份**的 `series_hash`、`expected_count` 和序号。
6. 结构化日志写 CLS，带周期、函数、数据集、hash。

函数**不再调用 `EnsureDatasetPeriod`**，每次触发少一次往返。

**函数内截止时间**：环境中带各数据集的允许迟到时间，函数据此计算“收盘 + 允许迟到时间 − 3 秒”作为本次执行的内部截止（crypto 即收盘后约 12 秒）。到点后停止 HTTP 重试（现有最多 4 次），立即提交已拿到的结果；未拿到的标的不再提交，交给补采。避免重试做完时已过截止时间而白做。

### 4.3 不连 EventBus

- 去掉批次完成事件的发布与函数指标的 EventBus reporter；环境校验（`scf_environment.go`）与打包脚本不再要求 EventBus 参数和 CA。
- 诊断改走：CLS 结构化日志、SCF 自带的调用/错误/超时指标、Storage 的提交与周期指标。
- 现有 handler 多处返回 `Success:false, nil`，SCF 不会据此重试。新路径明确：业务失败不依赖 SCF 重试，异步重试次数设为 0、事件保留期设短，避免旧事件积压与当前采集争抢；缺口交给补采。

### 4.4 定时与错峰

- 腾讯云 cron 的秒字段只支持整数。每分钟第 0～1 秒触发，函数内按函数标识哈希做 0～1.5 秒的确定性延迟，实现错峰。实际触发迟到与人为错峰分开计量。
- 只服务 1h 任务的函数用整点 cron，不必每分钟触发。

### 4.5 限流参数

- 函数内有一个**令牌桶限流器**（`FeedGuard`）：桶容量为 burst，每秒补充 rps 个令牌，每发一个请求消耗一个，桶空了就等。现有默认 rps=5、burst=5、并发 1 是保守值，不是币安的限制；按默认值，50 个请求光等令牌就要约 9 秒。
- rps、burst、FeedGuard 并发、流水线并发（`Request.Concurrency`，默认 5）、请求超时都改成环境参数，按数据源下发。
- 遵守 429 与 `Retry-After` 退避；418 不能通过切换域名绕过。

## 5. Storage

### 5.1 新增 `RegisterSeriesSnapshot`

**作用**：把一个数据集的完整标的列表交给 Storage 保存一份，以后用 hash 引用；同时声明这个 hash 从哪个周期起生效。Storage 建立周期时需要知道完整列表（决定完成位图长度、序号对应哪个标的、周期完成事件里列出缺失标的），而函数只有 hash 和自己负责的几十个标的，所以由 Collector 事先交一份。

| 步骤 | 内容 |
| --- | --- |
| 输入 | 空间、数据集、频率、完整标的列表（排好序）、生效周期 P |
| 校验 | 数据集存在且未删除；列表无重复且按规范排序；**Storage 自己重新计算 hash**，不信任调用方；数量不超过周期规模上限；新增的 P 对齐该频率的 K 线边界、晚于 Storage 当前时间，且该数据集该频率在 P 及之后还没有建立任何周期（不能改写过去） |
| 保存 | 快照以 `(空间, 数据集, 频率, hash)` 为键持久化；在该数据集该频率的**生效表**追加一行“从 P 起 → hash”。快照与生效记录在同一个持久化批次中保存 |
| 并发 | 与 `CommitTimeSeriesBatch` **共用 DataNode 现有的周期锁**（`period_progress.go:240`），“检查 P 之后没有周期”与“追加生效记录”在锁内一次完成，不会在两者之间被建出旧 hash 的周期 |
| 幂等 | `(空间, 数据集, 频率, P)` 唯一。同 P、同 hash 的重试**先返回成功**，即使 P 已经过去、周期已经建立；同 P、不同 hash 拒绝。真正新增的 P 必须**严格晚于**最后一个已登记的起点，不能插入已有时间线的中间 |
| 时间判断 | “当前时间”由 Storage 在锁内判断；Collector 的时钟只用于提出 P。只有因“P 已不在未来”被**明确拒绝**时 Collector 才重新选 P；结果不明（超时、断连）时重放原请求，由幂等规则恢复 |
| 清理 | **v1 不清理**。快照很少（一年几份），而低频任务、长假或长时间故障后，仍被函数使用的快照可能既不被近期周期引用、也不是“最近登记”，自动清理会导致持续拒写 |

只给 Collector 使用，与现有周期接口一样按数据集路由到所属 DataNode。

**生效表**：每个“数据集 + 频率”一张，只追加、不修改，一年只有几行：

```text
(数据集 D1, 1m)：
  从周期 2026-10-11 12:00 起 → H1
  从周期 2026-10-15 08:32 起 → H2
```

粒度是“数据集 + 频率”，不是每条时间序列：一个 hash 代表该数据集在该频率下的全部标的，每个标的的时间序列只是快照中的一个序号。现有数据集本身按频率区分，所以实际上是每个数据集一个 hash。

**允许迟到时间是数据集属性**：作为数据集的属性 `allowed_lateness_seconds` 保存在 Storage 元数据中，用现有的数据集更新接口设置（Collector 在创建或更新任务的结果数据集时写入），不新增接口，也不放进快照（同一标的集合可能先后用过不同的迟到时间）。Primary 转发提交请求时本来就会查数据集元数据，由它把该值带给 DataNode；属性缺失时按 60 秒处理并告警。它只用于新建的周期，已建立周期的截止时间不变。

取值（数据集级参数，可调）：

| 空间 | 频率 | 允许迟到时间 | 依据 |
| --- | --- | --- | --- |
| crypto | 1m、1h | 15 秒 | 实测正常执行从收盘到提交完成约 2～4 秒，p99 目标 8 秒，留约一倍余量 |
| stockcn | 1m | 90 秒（初值） | 有 settle delay，错峰窗口从第 5 秒到第 40 秒；实施 stockcn 时按实测调整 |

取值的影响只在出问题时体现：所有标的按时到齐时周期立即 complete，与该值无关；慢于截止时间的提交被拒绝，相关标的记为缺失、周期 `degraded`，由自动补采补回。值越小，因子在有缺失时等待越短；值越大，被拒绝的迟到提交越少。canary 中统计“因迟到被拒”的比例，超过约 0.1% 时把 crypto 调到 30 秒。

**hash 的计算必须在 Collector 和 Storage 之间完全一致**：规范序列键沿用现有定义（provider、sourceID、marketType、标的 ID、series_tag，见 `domain/task_series.go:30`），排序后生成稠密序号与 hash；把实现抽到共享包，两边共用。快照条目因此要带齐这五项。

### 5.2 提交时自动建立周期

修改现有 `CommitTimeSeriesBatch`，不给 SCF 新增接口。注意不能只改“周期不存在就报错”的那个分支（`period_progress.go:252`）：现有代码在它之前先读取周期期望（`period_progress.go:244`），周期不存在时已经出错返回。改为在 DataNode 已持有的周期锁内：

1. **先判断周期是否存在**。存在则按现有逻辑校验 hash 并提交。
2. 不存在时，先查生效表：该周期时间应生效的 hash 必须等于提交带来的 hash，否则拒绝（报“hash 与生效表不符”，旧环境函数在此被明确拒绝，而不会抢先用旧快照建立周期）；再按 `(空间, 数据集, 频率, hash)` 加载快照，找不到则拒绝并报“快照未登记”。
3. 计算截止时间 = `frequency.BarEnd(周期时间)` + 允许迟到时间（用共享的周期计算，月线等不能直接加固定时长），由 Storage 按自己的时钟判断；`now >= deadline` 时拒绝本次提交，不建立周期，迟到的数据交给补采。
4. 在内存中构造周期期望，用快照完成**逐行身份校验**（`period_progress.go:927` 的校验需要快照，不能只在生成完成事件时才查快照）。
5. 在**首次行写入的同一个原子批次**中保存：周期记录（`series_hash`、`expected_count`、`deadline`、`status=waiting`）、完成位图、waiting 与截止时间索引（否则后台截止 worker 找不到这个周期）、行数据与行变更事件。
6. 不要在持锁时调用同样会加锁的 `EnsureDatasetPeriod`。

并发提交时第一个建立周期，后续提交拿到锁后看到周期已存在，只校验 hash；hash 不一致按现有逻辑拒绝。

**周期只存 hash 引用**，不再像现在那样每个周期复制一份完整标的列表（现有 `EnsureDatasetPeriod` 每周期写入 `series_snapshot` JSON，500 多个标的每分钟一份）。逐行校验、生成完成事件、列出缺失标的时都按 hash 查回快照。

### 5.3 周期裁决不变

complete/degraded 的裁决、截止时间 worker、`CollectorPeriodCompleted` 的生成沿用现有 DataNode 逻辑（`docs/模块/存储.md`“周期”章节），因子与 View 的消费方式不变。

**一处必须修改**：现有 `periodMarkerSubjects`（`period_progress.go:1096`）只把“显式失败位已设置、成功位未设置”的标的列为失败。新模型中函数不再上报失败（漏触发、未提交的标的根本没有失败位），会出现 `degraded` 但缺失列表为空。改为截止裁决时直接用“快照全集减成功位图”生成缺失列表。

`EnsureDatasetPeriod` 不再由 SCF 或 Collector 的实时路径调用；没有其他调用方后删除。

### 5.4 写入幂等

Storage 按 `source_event_id + space + dataset` 去重，相同来源 ID 的整组写入直接跳过（`store.go:260`）。同一周期、同一函数的两次执行内容可能不同（第一次只抓到 A，重复触发时抓到 A 和 B），如果写入 ID 只由（周期、函数、数据集）决定，第二次的 B 会被跳过。所以：

- 写入 ID = （周期、函数、数据集、本次规范化提交内容的摘要）。完全相同的 RPC 重试复用同一个 ID；内容不同就换 ID。
- 保留现有的 `AcceptedSeriesIndexes` 检查，不能把 RPC 成功当成全部行都被接受。
- 补采使用独立的写入 ID。现有调用方在缺少同步点时回退到批次 ID（`kline_pipeline.go:671`），改造时一并调整。

## 6. Collector

### 6.1 每个空间一个对账协程

```text
Collector 进程
 └─ 空间管理器（每分钟检查一次空间列表）
     ├─ crypto 协程：每分钟第 10 秒对账
     ├─ stockcn 协程：每分钟第 10 秒对账
     └─ 新建空间 → 启动协程；删除或停用空间 → 停止协程
```

每轮对账：

```text
0. Collector 启动后的第一轮：全量读回云端实际函数与定时器，不把重启前的内存状态当作“已生效”
1. 若本空间有未生效的“采集计划”（pending/applying）：本轮先续跑它（重试失败的下发、推进收尾），新的变化合并为最新期望，等它生效后再处理
2. 计算期望状态：读本地采集任务 + 向 Storage 查各标签当前成员（每个空间一次）
   → 每个数据集的标的集合 hash、每个函数的工作项、应退役的函数
3. 每小时一次（放在提前返回之前）：全量读回所有函数的配置与定时器，发现被手工改动则补推
4. 只有“没有未生效的采集计划，且期望与已生效状态一致”时才提前结束（绝大多数分钟）
5. 否则开始一次新变更：
     ① 为每个标的集合有变化的数据集选生效周期 P：不早于“当前时间 + 2 分钟”的第一个 K 线边界
        （1m 数据集通常是第 M+2 分钟；1h 数据集是至少 2 分钟之后的下一个整点）
     ② 在 Collector 库中先保存本空间唯一的一份未生效“采集计划”（表 `t_collector_fetch_plans`）：各数据集各自的 P 与 hash、
        每个受影响函数的完整目标环境、各函数确认状态
     ③ 登记新快照并在生效表追加“从 P 起 → 新 hash”（必须先于下发）
     ④ 并行更新受影响函数的环境变量（同时带旧份与新份，各自带生效起点），读回确认；
        退役函数此时**不停用**（它们的旧份在旧周期提交窗口内仍可能需要）
     ⑤ 等本轮全部下发结束，更新记录中的确认状态，下一分钟（第 1 步）重试失败的
     ⑥ 收尾：旧份保留到“各数据集的 P + 允许迟到时间”之后（在此之前旧周期仍可能合法提交），
        期间 cron 覆盖新旧两份需要的频率；之后去掉旧份、调整 cron、停用退役函数（沿用现有
        assignment.go:509 为未使用函数生成 Enabled:false 的行为）；全部完成后把采集计划标记为已生效（applied）
```

**采集计划**是变更的唯一依据，**每个空间同一时间只有一份未生效的计划**；最近一份已生效的计划就是“已生效状态”：

- 重试和 Collector 重启都继续这一条，**不重新选 P**；登记响应丢失时重放原请求（5.1 的幂等规则保证安全）。只读回云端配置无法发现“已写入 Storage 生效表、但还没下发”的变更，所以必须先落这条记录再登记。
- 一个函数可能同时服务多个数据集。按空间只保留一条记录，所有数据集的变更一起计算出每个函数的完整目标环境，避免“A 数据集的旧记录重试时，把 B 数据集已更新的环境覆盖回旧配置”。
- 计划未生效期间出现的新变化，合并为最新期望，等这份计划生效后作为下一次变更处理。这样环境里每个数据集最多同时有新旧两份。

实施时的约束：

1. 第 5 步的实际条件是“**没有未生效的计划**且期望与已生效不一致”；第 1 步续跑后计划仍未生效时，本轮不新建计划。
2. 重启恢复、每小时配置纠偏，都以采集计划**当前阶段的目标配置**为准，不能用新的期望覆盖正在执行的计划。
3. 一个函数服务多个数据集时，要等它所有旧工作项的保留窗口都结束后才能退役。
4. 收尾操作也持久化进度、可重试；环境清理、cron 调整、退役停用全部确认成功后才把计划标记为已生效。

**空间停用或删除**：先停用该空间所有函数的定时器（失败则下一分钟重试），确认成功后才退出该空间的协程。只停协程不会停掉云端的定时器。

**为什么只用定时对账**：标签同步照旧每小时写 Storage，任务增删改照旧写 Collector 的库；对账只读取这两处的结果，不需要任何事件或回调，也不与其他逻辑耦合。控制台手改标签、上次下发失败等情况，都会在下一分钟被发现。

**每个空间独立**：自己的定时与防重叠（沿用 `timerjob`，上一轮未结束则本空间本轮跳过）、自己的状态、超时与错误、带空间 ID 的日志与指标。一个空间卡住不影响其他空间。

**共享资源**：

| 资源 | 处理 |
| --- | --- |
| SQLite 单连接 | 对账每分钟只读一次任务表，写入只在有变化时发生，量很小 |
| 腾讯云 SCF API | 设全局并发上限（如同时最多 20 个配置更新），各空间共用，避免触发云 API 限频 |
| Storage 网关客户端 | 各空间共用，支持并发 |
| 进程退出 | 先取消并等待所有空间协程，再关闭客户端和数据库 |

**时效**：1m 数据集的标的变化约 2～3 分钟后生效（P 至少在 2 分钟后）；1h 数据集最迟到下一个整点。下发失败的函数在 P 之后被拒，相关序列记为 `degraded`，由补采修复。

### 6.2 分配规则

- 分配单位是“市场 + 标的 + 频率”，与数据集无关；写入目标随工作项下发。
- 每函数标的数是任务级参数：现货与合约默认都是 50，canary 直接用 50；同一函数服务多个任务时取较小值；容量校验不通过则拒绝部署（见 8.1）。
- 标的变更时直接按最新标的重新计算分配、全量更新该空间所有函数的环境，不追求“只动少数函数”。

### 6.3 SCF 部署与地域

- **地域白名单**：每个空间（crypto 的现货和合约分别）配置自己的 SCF 地域列表。stockcn 默认是存储主机所在地域（南京），用户可改，例如用户在广州有服务器，就配置广州。
- **约束**：每个配置的地域都必须有一台同地域、部署了 Access 的服务器。函数绑定该服务器所在的 VPC，访问 Access 的私网地址。地域没有同地域 Access 主机时拒绝部署。`moox.toml` 的 `region_blacklist` 改为显式 `regions`；Access 地址由放置清单推导，删除手写的 `storage_access_targets` 等路由。
- **VPC 与公网**：函数绑定 VPC 后还必须能访问币安等数据源。部署前检查“绑定 VPC + 开启公网访问”能否同时生效；**不能时只报告给用户，不自动创建 NAT 网关**（会产生费用）。
- **数据源可达性**：用现有 `probe-egress` 检查各地域能否访问对应数据源（例如南京访问不了币安合约），结果给用户看，不自动改地域。
- **内存**：内存是 SCF 部署配置，不是环境变量；`node.go:681` 当前把行情函数内存硬编码为 64MB，改为可配置。
- **cron**：按函数服务的频率集合生成。

### 6.4 检查与补采

- **检查** `moox-cli collector kline check`：按任务、标的集合、交易日历和时间窗口生成“应有的（标的 × 时间点）”，直接读取 Storage 中的行，输出缺口（数据集、频率、标的、缺失时间段），连续缺口合并显示。个人规模下读行足够（24 小时约 150 万行）。
- **补采** `moox-cli collector kline backfill`：默认补检查出的缺口，也可指定范围强制重拉；复用现有历史批次形态（catchup/gap_repair：一个标的、1～1000 根）与抓取流程，由 Collector 用 Invoke 触发函数执行，函数把行直接写入 Storage（为 `scf-collector` 补充写行权限）。这是 Invoke 唯一保留的用途，不在实时路径上。
- **自动补采**：同一个对账协程中低频执行（如每小时），检查最近若干小时的缺口并有界补采；每轮行数、并发、请求权重有上限，不挤占实时采集。
- **已知代价**：补采只补数据，不改变已终结周期的 `degraded` 状态（它代表“当时没有按时完成”）。`UpsertFields` 会持久化行变更事件，View 会写入补来的行，不会因为周期是 degraded 而忽略；因子订阅的是周期完成事件，补行**不会**自动触发重算，因子历史重算保持手动。

### 6.5 清理

删除（仅限直接行情采集链路）：调度器的规划、派发与重试；`ClaimTimerBatch`、`MarketFetchRuntime` 服务（proto、生成代码、RPC 注册、配置、服务目录、Access 权限）；`t_collector_timer_period_batches`；逐周期逐标的的实例与批次条目写入、`PeriodSeriesSnapshot` 的逐周期复制；`StorageWriteConsumer` 对实例表的更新；批次完成事件消费者；每地域保留的 Invoke 辅助函数；`timer_function_count` 历史字段名；`EnsureDatasetPeriod`（无调用方后）。

保留：`kline_resample` 的 Runner、本地 readiness 与 inventory 分支所用的 `task_instances`，以及标签同步、属性同步。

## 7. 网络与安全

### 7.1 私网路径

| 地域 | 路径 |
| --- | --- |
| 南京（存储主机所在） | SCF → 存储主机 Access 私网地址（`10.206.0.5:11004`）→ 本机主机网关 → Storage |
| 香港 | SCF → compute-1 Access 私网地址（`172.19.32.13:11004`）→ 经公网转发到南京 Storage 主机网关 |
| 其他地域（如用户的广州服务器） | SCF → 同地域服务器 Access 私网地址 → 经公网转发到 Storage |

所有 SCF 到存储的请求都走同地域私网；只有 Access 到主存储这一跳可能走公网。新增 Storage 方法（`RegisterSeriesSnapshot` 只给 Collector；SCF 写行权限）需加入服务目录与 Access 的方法白名单。

### 7.2 两跳压缩

1. SCF → Access：函数环境 `MOOX_GATEWAY_COMPRESSION=gzip`（已实现）。
2. Access → 主存储：Access 的 `gateway_client.compression`。香港 compute-1 已启用 gzip；与存储同机的 Access 走回环，不压缩。

### 7.3 去 TLS

范围限定为 **MooX 自建的服务端 TLS**：主机网关 11003、EventBus 4222。保留：Console 9527 的 HTTPS、第三方 HTTPS（出口代理访问币安等）、SSH 主机密钥校验。

| 范围 | 调整 |
| --- | --- |
| `gatewayclient` | 内部模式不再强制 `CAFile`，远程端点不再启用 TLS |
| hostgateway | 远程 listener 不再要求 TLS 材料；`hostgatewayconfig`、`LoadIdentity` 重构；持久 nonce 保留 |
| 网关控制面 | 控制面客户端独立持有 TLS 连接池，需单独修改 |
| unitinstall / unitbundle / unitbootstrap | 去掉证书校验与 EventBus 非 TLS 拒绝；身份包、bootstrap、恢复流程同步修改 |
| Admin PKI | 清理自建内部 PKI 与 host bundle 签发；签名密钥管理与 Console 证书管理保留 |
| EventBus 服务与客户端 | 服务配置校验、jetstream 客户端不再拒绝远程明文；保留角色令牌、ACL 与轮换；不重置 JetStream 数据 |
| Monitor / HostAgent | HostAgent 去掉显式 CA；Monitor 对 Console 的 HTTPS 探针保留 |
| egress proxy | 内部 tRPC 随网关改造；访问第三方的 HTTPS 保留 |
| moox-cli | 隧道经 SSH 转发到 `127.0.0.1:11002`，不受影响 |
| 脚本与配置 | deploy、watchdog、SCF 打包、环境校验、示例配置中的 `tls://` 与 CA 要求一并清理 |

**切换顺序**：旧 SCF 的环境校验强制要求 EventBus TLS，而新的 4222 白名单只放行主机。所以去 TLS 的生产切换放在**所有 SCF 迁到新函数（不再连 EventBus）之后**（见第 11 节）。

### 7.4 防火墙白名单（CLI 与 skill）

- `setup init` 已经调用防火墙配置并拒绝 partial 结果（`setup_init.go:122`）；本次扩展现有对账能力：
  - 11003、4222：只放行放置清单中各主机的公网与私网地址；
  - 11004（Access）：保持开放（SCF 走私网，来源地址不固定）；
  - 9527：公网；11012 健康端口：只对 control 放行。
- 现有 `EnsureFirewallRule` 只做查重后添加，需扩展为收窄已有宽规则，覆盖安全组重叠规则、端口范围与 IPv6 宽规则，并输出差异。
- 集成到 `skills/moox`：SKILL.md 优先指引 `moox-cli setup firewall`，`tencent_lighthouse_firewall.py` 只作为单条规则的辅助工具。

### 7.5 已接受的风险与后续加固

已接受（个人项目、来源已白名单）：SCF 到 Access、主机之间的链路明文；NATS 令牌被嗅探后可在角色权限内冒用；Storage `AuthInfo.app_key` 明文出现在请求体中。

**后续加固项**（不阻塞本次实施）：

1. 主机网关从 Admin 拉取的快照里含 HMAC 验签密钥（`GatewayVerificationKey.secret`），明文传输时可被嗅探后伪造调用方；可用每主机密封密钥加密，或改为非对称签名。
2. `X-Space-Id`、`X-User-Id`、`X-User-Role` 在签名之后才附加（`gatewayclient/client.go:346`），应纳入签名。
3. 响应没有应用层签名，可增加响应 MAC。
4. 去掉请求体中的 `app_key`，改由网关已认证的调用方身份授权。

## 8. 容量与延迟

### 8.1 每函数标的数

时间估算（初筛用，部署准入以实测为准）：

```text
C有效     = min(流水线并发, FeedGuard 并发, 实际连接并发)
并发耗时  = 冷连接 + ceil(n / C有效) × 单请求延迟 p95
限速耗时  = max(0, n − burst) / rps + 最后一个请求耗时
拉取时间 ≈ max(并发耗时, 限速耗时)，目标 ≤ 3s
```

2026-10-11 实测（临时 SCF，绑定同地域 VPC 并开启公网，真实交易对，连接在热实例中跨调用复用）：

| | 香港合约（`fapi.binance.com`） | 南京现货（`data-api.binance.vision`） |
| --- | --- | --- |
| 单请求（复用连接） | p50 57ms、p95 约 60ms，偶有 160～360ms | p50 76ms、p95 79ms |
| 新建连接 | 460～660ms | 550～820ms |
| 整批实测 | 40 个、并发 6：冷 1.1s，热 0.4s（偶有 0.6～1.0s）；40 个、并发 10：热 0.24s | 30 个、并发 10：冷 1.06s，热 0.24s；40 个、并发 10：热 0.32s |

据此确定默认参数：

| | 香港合约 | 南京现货 |
| --- | --- | --- |
| 每函数标的数 | 50 | 50 |
| 并发 / rps / burst | 10 / 50 / 50 | 10 / 50 / 50 |
| 估算整批（热 / 冷） | 约 0.3s / 约 1.0s | 约 0.4s / 约 1.3s |
| 整点 1m 与 1h 同时到期（100 个请求，热） | 约 0.6s | 约 0.8s |
| 函数数（全量） | 约 11 | 约 11 |

- 早期按“南京单请求约 300ms”估算是因为那次测量包含了 TLS 建连；连接复用后只有约 76ms。
- rps 与 burst 必须同时放开到 50，否则限流器本身会成为瓶颈（rps 20、burst 10 时 50 个请求光等令牌就要约 2 秒）。
- 币安限流按出口 IP 每分钟计权重（现货 6000，K 线权重 2；合约 2400，`limit<100` 权重 1）。每函数每分钟：现货 100、合约 50 权重；即使同一子网的函数共用出口 IP，全量合计也只有现货 1012/6000、合约 525/2400。
- 代价：一个函数故障影响这一分钟的 50 个标的（约 10%），由补采修复。
- 64MB 内存足够 50 个小响应，canary 中确认峰值。
- TDX（stockcn）沿用实测安全值 40，不套用上表。
- compute-1 只有 1Mbps 出口，香港合约提交 gzip 后每分钟约几十 KB，需关注集中到达的突发；实时提交优先于补采。

### 8.2 延迟预算（仅 crypto）

口径：**收盘到 Storage 接受**，指行与完成位图持久化成功，不是 RPC 返回；同时记录序列口径与“周期最后一个应有序列”的接受时间；缺失与超时计入统计。

| 环节 | 预算（p99） |
| --- | --- |
| 触发与错峰 | ≤ 1.5s |
| 启动 | ≤ 0.5s |
| 拉行情 | ≤ 3s（实测热实例 0.3～0.4s，冷启动约 1.1s） |
| 提交（含首次建立周期） | ≤ 1.5s |
| 余量 | 约 1.5s |
| 合计 | ≤ 8s |

去掉了派发排队（约 6.6s）和每次触发的周期登记往返。拉行情实测远低于预算，最可能超预算的是香港经 compute-1 的提交排队。stockcn 有自己的 settle delay 与错峰窗口，不适用 8 秒目标。

## 9. 前端与监控

管理台“采集实例”页改为三块：

1. **分配**：各函数的地域、标的、数据集 hash、最近一次下发时间与结果。
2. **标的变更日志**：什么时候标的列表变了、新增和移除了哪些标的、从哪个周期起生效、何时完成生效（来自下面的活动日志）。
3. **补采**：作业、进度、失败原因。

管理台不展示周期列表，Storage 也不为此新增接口。

**活动日志（全局模块）**：新增一个全局、永久保存的“活动日志”，任何模块都可以写入需要展示给用户的事件，标的变更是第一个使用者。

- 由 Admin 持有（控制面数据库中的一张表），提供“批量追加”和“按空间、来源、类别、关联对象、时间范围分页查询”两个接口；按幂等键去重，重试不会重复记录；不做清理。
- 每条日志包含：空间（全局事件为空）、来源模块、类别、级别、一句话标题、JSON 详情、关联对象 ID、时间。
- Collector 在新建采集计划时写一条“标的变更”日志（各数据集新增与移除的标的、旧 hash 与新 hash、生效周期），计划生效时再写一条“已生效”日志；写入失败下一分钟随对账重试。
- 管理台：采集任务页内嵌按类别过滤的变更日志列表，另提供一个全局的活动日志页。

需要同步修改的后端：`GetTaskResultInventory` 的最近终态改从 Storage 查询；`PeriodStorageReconciler` 替换为新的状态来源；Monitor 在 Collector 不可用时保留最后一次有效的 inventory 继续检查（持久化，两者同时重启后仍可用），并单独告警控制面数据过期；Monitor 中读取旧 assignment 与 coordination 指标的规则改为读对账状态；stockcn feed 健康检查不再依赖函数经 EventBus 上报的指标。

新增监控：周期没有任何提交、触发迟到、hash 不一致被拒、对账下发失败、实际缺口、补采积压、429 响应、函数内存峰值。

## 10. stockcn

- 保留交易日历、午休、停牌、数据源无数据语义、收盘尾段补采。函数按日历决定是否执行，Storage 只为有提交的周期建立记录，因此 Storage 不需要懂交易日历。
- 公共日历 `packages/marketcalendar` 当前覆盖到 2026-12-31，作为部署检查与告警项。
- 保留自己的 settle delay 与错峰窗口；TDX 每函数 40 个标的。
- 默认放在存储主机所在地域（南京），可配置到其他有 Access 主机的地域。南京约 170 个 stockcn 函数加约 11 个现货函数，腾讯云每地域 5 个命名空间、每个 50 个函数，放得下但需核对并发额度。
- stockcn 函数从未上线，没有迁移成本；在 crypto 稳定后实施。

## 11. 实施阶段与验收

| 阶段 | 工作 | 通过条件 |
| --- | --- | --- |
| 1 Storage | `RegisterSeriesSnapshot` 与生效表；`CommitTimeSeriesBatch` 自动建立周期（含生效表校验、截止时间与迟到拒绝）；周期只存 hash；缺失列表改为全集减成功位图；hash 计算抽到共享包 | 并发提交只建立一次周期；与生效表不符的 hash 被拒；快照未登记被拒；过截止时间被拒；不能登记过去的生效周期 |

| 8 去 TLS 与防火墙 | 第 7.3、7.4 节，全部服务统一改造 | 所有链路在无 TLS 下正常；防火墙差异输出正确 |

**验收**

- 正确性：hash 不一致、未收盘 bar 零落盘；重复触发不产生重复有效写入；周期按时 complete 或 degraded。
- 依赖隔离：停掉 Collector，实时采集与入库照常。
- 标的变更：变更后约 2 分钟内生效；过渡期只有少量周期 degraded，补采后数据补齐。
- 容量：无持续 429，峰值内存在配置之内，整批拉取 ≤ 3s。
- 延迟：crypto 收盘到 Storage 接受 p99 ≤ 8s。
- 补采：手动检查能发现人为制造的缺口，补采后检查通过。
- 迟到：因迟到被拒的提交比例 ≤ 0.1%（crypto，允许迟到 15 秒）。

**交接与回滚**：新旧方式按**目标周期**交接——选定 K 线开始时间 T，旧链路负责 `< T` 的周期，新链路负责 `≥ T`，同一数据集同一周期只由一种方式采集。迁移期间用任务级的临时归属参数让旧调度与新对账互斥。保留旧 Invoke 函数、旧代码包、函数环境与触发器清单、Collector 数据库快照；会破坏回退能力的清理（旧接口、权限、EventBus 流、旧函数）在七天回退窗口结束后才执行。回退同样按目标周期交接。

## 12. 代价汇总

| 简化 | 代价 | 为什么可以接受 |
| --- | --- | --- |
| Storage 不做计划版本，只用 hash + 只追加的生效表 | 下发失败的函数在生效周期后被拒，少量周期 degraded；标的变更约 2～3 分钟（1h 为下一个整点）后生效 | 标的变更是小概率事件，补采可修复；周期判为 complete 时一定按正确的标的集合 |
| 周期在首次提交时建立 | 整分钟所有函数都失败时，没有该周期记录，也没有 degraded 事件 | Monitor 新鲜度告警与完整性检查能发现，补采补齐数据 |
| 补采只写行，不改周期状态 | 已终结周期保持 degraded | 它如实表示“当时没按时完成”；数据本身已补齐 |
| Collector 每分钟对账而非事件驱动 | 变更最迟 1～2 分钟生效，每分钟一次轻量计算 | 不耦合其他逻辑，覆盖所有变化来源 |
| 不做出口 IP 核算 | 若实际多函数共用出口，可能遇到 429 | canary 中观察 429，再调整 |
| 只走同地域私网 | SCF 只能放在有 Access 主机的地域 | 用户可在需要的地域部署 Access |
| 去 TLS | 链路明文 | 个人项目、来源已白名单，换取不再因证书导致整体故障 |

## 13. 设计演进与取舍

这一节记录我们考虑过、又放弃的方案，以及放弃的原因，便于以后理解设计意图。

### 13.1 v1：分配写进环境变量

最初的设想：分配写进函数环境变量，函数完全不依赖 Collector；Collector 汇总批次完成事件、发周期完成事件；函数每次多拉 3 根 K 线实现自愈；每函数默认 50 个标的。

评审后发现：

- 周期完成本来就由 Storage DataNode 裁决，不需要 Collector 汇总。
- Storage 建立周期需要整个数据集的完整标的列表，而函数只有自己的分片，无法自己登记周期。
- 实时路径只写目标 bar，Storage 不会因为多拉的历史行更新历史周期，周期终结后也不再接受写入，“多拉 3 根”在现有语义下不成立。
- 函数内令牌桶默认 5 请求/秒、并发 1，50 个标的光等令牌就要约 9 秒。

### 13.2 v2：Storage 做计划版本

为解决上述问题，v2 引入了一套完整协议：Storage 保存不可变的计划版本、CAS 激活、`ResolveFunctionWork`（函数每次触发向 Storage 解析本次工作）、未来周期占位、专用修复接口、截止时与当前两套进度、出口 IP 汇总核算、去 TLS 后的三项安全措施。独立评审认为 v2 正确完整，可进入实施。

### 13.3 v3：按个人项目简化

v2 正确但过于复杂，与“个人量化项目”的定位不匹配。v3 的关键取舍：

1. **用 hash 加生效表代替版本系统**：`series_hash` 本身就能唯一代表一个标的集合，Storage 现有逻辑已在提交时校验 hash。只要 Storage 能按 hash 查到完整列表、并知道每个周期该用哪个 hash，周期就能在首次提交时自动建立。新增的只有 `RegisterSeriesSnapshot` 一个接口和一张只追加的生效表，没有 CAS、激活、占位。
2. **放弃“提前登记周期”**：曾考虑由 Collector 提前若干小时登记周期，以容忍 Collector 宕机；但已登记周期的快照不可修改，会与标的变更冲突。改为“快照登记一次、周期首次提交时建立”后，既不依赖 Collector，也没有冲突。
3. **放弃 `ResolveFunctionWork`**：它解决的是“热实例拿着旧环境”的问题，代价是每次触发多一次 Storage 往返，不值得放在热路径上。但如果只靠“谁先提交按谁的 hash 建周期”，旧环境的函数抢先提交会用旧快照建立新周期，整个周期按旧集合判定（新增标的不在期望里，周期却可能判为 complete），新环境的函数反而被拒，而且没有任何报错。评审中比较了三种处理：Storage 记生效表（甲）、变更时停用定时器再恢复（乙）、只做事后检查告警（丙）。用户选择甲：Storage 只多一张只追加的生效表，函数与 Storage 用同一个生效周期 P 切换，旧环境函数被明确拒绝，周期完成判定始终正确。
4. **只用每分钟定时对账**：标签同步、任务变更、控制台手改都没有现成的事件；与其给每个来源加回调，不如每分钟按空间对账一次，只读取结果，不与其他逻辑耦合。
5. **分配与数据集解耦**：函数只看“市场 + 标的 + 频率”，写入目标随任务下发，同类请求自然合并。
6. **补采只写行**：不新增修复接口，接受已终结周期保持 degraded。
7. **不做出口 IP 核算**：假设每个函数出口 IP 不同，用 canary 中的 429 观察兜底。
8. **只走同地域私网**：SCF 必须放在有同地域 Access 主机的地域，地域可配置；VPC 加公网访问不可用时只报告，不自动开 NAT。
9. **安全措施降为后续加固**：快照密钥加密、元数据入签名、响应 MAC 不阻塞实施。
10. **函数不连 EventBus**：这次重新部署后函数全部失败的根因之一就是 EventBus CA 变化，去掉这个依赖比维护它更简单。

## 14. 前置实验结果与未决事项

### 14.1 前置实验（2026-10-11，临时 SCF，已删除）

| 问题 | 结论 |
| --- | --- |
| SCF 能否同时“绑定 VPC + 开启公网访问” | **能**。南京绑定存储主机 VPC、香港绑定 compute-1 VPC，均只开 SCF 公网访问（不用 EIP、不用 NAT）。南京：Access 私网 `10.206.0.5:11004` 3～9ms，`data-api.binance.vision` 通，`api`/`fapi.binance.com` 不可达（与之前结论一致）；香港：Access 私网 `172.19.32.13:11004` 1～8ms，`fapi`、`api.binance.com`、`data-api` 都通 |
| 更新环境变量后，下一次触发是否用新环境 | **是**。配置更新约 6～8 秒到 Active；之后的第一次调用就落在新实例上，旧热实例不再使用；更新进行中的调用也拿到新值，没有失败。定时触发实测：15:27:26 更新，15:28:00 的触发即在新实例上使用新值。分钟内第 10 秒开始下发、下一分钟生效的做法成立 |
| 单请求延迟、冷连接、整批耗时 | 见 8.1 实测表；50 个标的热实例 0.3～0.4 秒、冷启动约 1.1～1.3 秒拉完 |
| Timer 事件 `Time` 在重试时的语义 | 函数失败后平台默认重试 2 次、间隔 60 秒，**重试事件的 `Time` 保持最初的计划时间**。默认异步配置：事件保留 6 小时，被限流（错误码 432）的事件无限重试、间隔 60 秒。所以用 `Time` 确定周期是对的，同时必须按 4.3 把异步重试设为 0、缩短保留期 |
| Timer 在函数仍在运行（并发占满）时的行为 | 单并发、每次运行 90 秒的函数，12 分钟里只有偶数分钟的触发被执行，奇数分钟的触发**没有被延迟执行，也没有带着旧时间晚到**，等同于被跳过。所以函数必须远在一分钟内结束（实测 1～2 秒），并避免把并发配额压得太低 |

### 14.2 未决事项

1. canary 中确认：50 个标的的峰值内存、端到端延迟（收盘到 Storage 接受）、429 是否出现、因迟到被拒的比例。
2. stockcn 允许迟到时间（初值 90 秒）在实施 stockcn 时按实测确定。
