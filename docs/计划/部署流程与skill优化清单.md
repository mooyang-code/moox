# 部署流程与 skill 优化清单

目标：任何用户在任何拓扑、任何机器状态下用 skill 部署时，都能走通主流程；出问题时能看清原因、知道下一步，不把机器弄得更糟；在此基础上把安装时间压到最短。
范围：针对问题类型，不绑定某个版本或某几台机器。

| 轮次 | 编号 | 内容 | 状态 |
| --- | --- | --- | --- |
| 第二轮第一批 | 14～24、37、38 | 新装就能采到数据，恢复线上 | 待实现 |
| 第二轮第二批 | 25～34 | 安装提速、并行清除、默认示例 | 待实现 |
| 可选 | 35～36 | 收益小，不排期 | 暂不做 |
| 第一轮 | 1～13 | 默认路径、失败可见、重试安全、现状判断 | 已实现，随 #94 发布 |

执行步骤见 [部署修复与安装提速执行计划](部署修复与安装提速执行计划.md)。

分工原则：**判断和动作放进 CLI，skill 只管流程和跟用户沟通。** skill 不写具体案例，只写通用规则；能由 CLI 判断的事，不让 Agent 推理。

已定的决策：

- 发布分两批，第一批先让新安装和线上都能采到数据。
- `core` 改名为 `admin`，不留别名。
- 线上全新重装，不做原地升级：线上没有行情和因子数据，重装还能验证整条安装路径。
- 管理台只用内部证书，不询问用户，删除公网证书相关代码和 `tls_mode` 配置项。
- 目标机并行自己下载，发布产物按部署单元分包。
- 默认策略是合约 1m 数据的 MA5/MA10 双均线，用于展示，不挂账户；去掉 `min_age_bars`，安装时直接启用，前约 10 分钟自动跳过。
- 旧部署在用户授权后并行清除全部遗留，同步删除，回收目录第一版不做。
- 预检通过后，下载、清除、防火墙同时进行。
- Storage 保留三个二进制：改成一个只省约 2 秒，还失去按进程名区分角色的能力。

## 第一批：新装就能采到数据，恢复线上

14. **WS 采集不依赖云函数开关**
    - 问题：Collector 只为 `scf_markets` 里的空间启动对账。`[scf_plan]` 关闭时部署会删掉这一项，对账静默不启动，没有采集计划，collector-stream 拿不到任务。`config init` 生成的配置默认关闭，所以新装必现。
    - 改法：空间里有已启用的 K 线任务就管理，不再看 `scf_markets`；`[scf_plan]` 只管云函数。管理器每轮重新计算空间，启用任务不用重启。分开“管理集合”和“运行集合”：暂停、恢复、重置用管理集合，里面要包含暂停的空间，否则暂停开关清不掉。拉取加云函数的数据集缺地域时，明确报错。
    - 文档：写实：关闭 `[scf_plan]` 不影响推送采集；拉取加云函数的数据集要先切到 stream。
    - 验证：集成测试在没有云函数地域、云函数接口返回错误的条件下，crypto 计划走到 applied 并下发出推送项；没有云账号时不能每轮对账都记失败；重置后第一次 init 能解除暂停。

15. **首份计划等执行端在线**
    - 问题：解耦后 Collector 一启动就会建计划并选生效周期，而 collector-stream 要在 control 之后才部署，开头会缺一段 K 线。
    - 改法：新计划要给 collector-stream 下发推送项、而它不在线时，本轮不建计划，状态里说明在等它。不影响已有计划，也不影响 `--force` 切回拉取。
    - 验证：单元测试覆盖不在线不建计划、上线后下一轮建计划、切回拉取不受影响。

16. **验收看真实数据**
    - 问题：`collector status` 没有计划时仍返回 `level: ok`；`next_steps` 为空就算完成，装好了一根 K 线都没有也判成功。
    - 改法：有已启用任务却没有生效计划时，`collector status` 报错并说明原因；增加验收命令，每个已启用数据集写入最近几期收盘 K 线（缺失不超过 5%）、1m 因子任务前进（`degraded` 算通过）才算通过，并作为 `next_steps` 的最后一步。计划已登记但第一根还没收盘时算等待，不能算通过。按拓扑处理：没有因子机时因子检查跳过；空间没有启用任务时跳过；没有海外机也没配云函数时不加验收，给出警告。
    - 验证：验收等到超时才算失败，开头没有计划或没有数据时算等待；只走云函数的空间不要求 collector-stream；没有海外机、没有因子机的拓扑不会永远走不完。

17. **默认因子导入打开**
    - 问题：模板写的是 `[factors] enabled = false`，文档却说默认运行两个 1m 因子任务，实际任务数是 0。
    - 改法：两份模板默认打开，文档写实。生成配置时，有因子机且有海外机才打开，否则会长期告警。Collector 启动时已同步创建源数据集，导入顺序不用改。
    - 验证：在产物包路径上实跑一次，确认 `source_dir` 能读到因子库。

18. **只保留内部证书**
    - 问题：`auto` 遇到公网 IP 走公网证书，到第 12 步才失败。管理台地址只会是 IP，这条分支用不到。
    - 改法：管理台固定用内部证书，用户不用选择。删除 `tls_mode` 配置项、CLI 里的证书模式判断、Console Proxy 的 ACME 分支、80 端口防火墙规则和 `--create-proxy-ca`；首次安装自动创建 CA，已有 CA 不替换。`config migrate` 删除旧配置里的 `tls_mode`。
    - 验证：全新安装不需要证书相关参数；防火墙规则不含 80 端口；旧配置迁移后能解析。

19. **改配置不用清空重装**
    - 问题：第 11 项绑定整份配置摘要，`control-operation.json` 又绑定第一次请求，改通知、保留期这类不影响部署拓扑的字段也要全部重来。这是第一轮改得过严造成的。
    - 改法：绑定只覆盖主机、地址、内网地址、路径、部署拓扑和管理员信息；首次 control 增加这个绑定检查；control 没成功过时允许换新请求；control 前检查 Storage、出口代理改成看 `ready.json`，不再重跑部署。已部署单元的保留期和出口配置，改完要发新版本才生效，`setup validate` 给出提醒和命令。
    - 限制：Storage、出口单元部署失败后，不支持改这两类配置再重试，要换回原值或走清除。
    - 验证：安装中途改通知或 Collector 配置后重跑 control 能通过；改主机地址、管理员密码后 control 报错。

20. **Badger 空文件不再拖慢发布**
    - 问题：Admin 的 Badger 真实数据约 2.7MB，却预分配 2GB 的 `.vlog` 和 128MB 的 `.mem`。部署把稀疏文件复制成实心 2.2GB，再计算哈希、落盘、复制第二轮，每次 control 部署多花约 56 秒，还留下 2.2GB 残留。
    - 改法：缩小 `ValueLogFileSize` 和 `MemTableSize`，Admin 退出时关闭 Badger；host-gateway 的 nonce 库同样处理。里面有登录会话和防重放记录，继续随状态复制。线上全新重装后没有 2GB 旧文件，复制逻辑不用改。
    - 验证：在打开状态下量目录表观大小低于 64MB；发布目录到 admin 启动的空档降到几秒。

21. **SFTP 上传改成并发写入**
    - 问题：SFTP 用默认选项，每发 32KB 等一次确认，实测只有线路能力的七分之一到三分之一。
    - 改法：改用 `ReadFromWithConcurrency`，不依赖库对读取器大小的判断。本地开发构建和目标机下载失败时的兜底都走这条路。
    - 验证：上传速度接近 SSH 管道直传；中途失败不留下校验不过的文件。

22. **证书信任不阻塞安装**
    - 问题：`setup init` 有两处调用浏览器信任（开头和登录校验），Agent 环境没有 sudo 时后面全部卡住；`install.md` 给的是 login 钥匙串命令，脚本查的是 System 钥匙串。
    - 改法：两处都去掉，登录校验只取回证书；信任放进 `manual_steps`，不放 `next_steps`；修正命令。这一步要用户电脑的管理员授权，安装结果写明命令；不做时管理台能打开，但浏览器有安全提示。

23. **报错和文档说真实原因**
    - 问题：`ingest-mode set`、`fetch-plan reregister`、`subjects sync` 的提示把 Agent 引向错误方向；`fresh-deploy.md` 关于默认运行内容和任务写入的说法与实际不符；`doctor bootstrap` 在产物包目录读不到目录文件，报假失败；`doctor diagnose` 在操作机上全部跳过。
    - 改法：文案直接说缺什么；文档按实际行为修正；`doctor bootstrap` 改用内嵌目录；`doctor diagnose` 在操作机上说明要到哪里查。

24. **单组件重启和 skill 规则**
    - 问题：重启一个组件要重发整个管理台，Agent 还翻到维护者脚本；采集没起来时删了全部任务，再用 `host exec` 补种。
    - CLI：增加 `setup restart --host <主机> --component <组件>`。
    - skill：采集或计划有问题时，不删任务、不用 `host exec` 改数据库、不用维护者脚本；先看 CLI 给出的原因，走不通就停下来汇报。

37. **`core` 改名为 `admin`**
    - 问题：`core` 看不出这一步的作用，错误提示也难懂。
    - 改法：`--stage core` 改 `--stage admin`，相关状态、错误码、类型和文档一起改，共 161 处，不留别名。放在第一批最前面单独提交。
    - 验证：旧名字搜不到；线上全新重装，不做状态迁移。

38. **控制机看护**
    - 问题：看护只在部署其他主机时安装，`next_steps` 又跳过控制机，所以全新安装的控制机没有看护，组件崩溃后没人拉起。
    - 改法：`setup bootstrap --stage control` 成功后安装控制机看护，幂等，装好再写完成记录，否则看护失败后再也补不上。
    - 验证：杀掉一个组件后能被拉起；重复运行不重复写入；看护安装失败时重跑能补上。

## 第二批：安装提速

25. **按部署单元发布**
    - 问题：448MB 产物包里所有机器的程序混在一起，用户本机要下载，再上传给目标机。
    - 改法：发布时用 `setup package` 打好 10 个单元包。单元是安装、校验和回滚的最小单位，带程序、配置模板、schema、脚本和文件清单，不按单个二进制拆。`moox-bundle.json` 写入各单元的包摘要和文件哈希，并核对与 CLI 版本一致。`moox-collector-scf` 单独发布，启用云函数时才下载。`moox-runtime` 从 host 包取出，不再单独传。
    - 顺序：先增加单元包，等目标机下载做完，再让 `moox-bundle` 去掉二进制（约 12MB），保证每一步合入后都能安装。
    - 信任：`SHA256SUMS` 校验产物包，产物包里的清单校验各单元，强度和现在相同。

26. **目标机并行下载**
    - 问题：传输占安装时间一半以上，还受用户本机上行带宽限制。
    - 改法：CLI 按 `[deployments]` 算出每台要哪些单元，通过 SSH 并行下发下载任务。每台用一小段下载实测 CNB 和 GitHub，选更快的源，不能只看状态码；每台最多 4 条连接，失败的分段重试，校验 SHA256 后才改名和执行。两个源都不通时，由本机下载这一个单元再用 SFTP 推过去。
    - 本机依赖：软件包校验、`moox-runtime`、control 配置模板、版本记录、云函数包都改成不依赖本机二进制。先定义远端软件记录，再逐处替换。配置模板从产物包读，按清单哈希核对。
    - 目标机：下载目录 `staging` 只保留当前版和上一版，不算遗留：清除时保留，路线判定和清除摘要都不计入。预检读真实可用空间。
    - 入口：分步命令在路线和前提检查之后按需下载，`setup install` 在准备阶段统一下载。
    - 共用：安装和升级走同一套，升级时限速，避免挤占海外机的实时采集。
    - 验证：两个源都不通、下载中断、哈希不对、磁盘不足四种情况都有测试。

27. **证书材料一次传完**
    - 问题：每个单元 22～27 个小文件，逐个走两次 python 校验加 SFTP，累计约 3.9 分钟。
    - 改法：主机身份每台只导出一次，EventBus 客户端角色取并集，打成一个包通过一条 SSH 连接传完，到目标机一次校验。EventBus server 材料只属于 eventbus 单元，继续单独导出。部署成功后清理目标机上的材料目录。

28. **`setup install` 一条命令装完**
    - 问题：Agent 要逐步运行 19 条命令，每步重新连接、扫描、导出。
    - 改法：预检后一次确认，一个进程跑完，复用连接，每阶段只扫描一次。中途失败可以直接重跑。现有命令的副作用（本机状态归档、只能出站主机的防火墙、看护、完成记录、配置备份）都要编排进去。步骤顺序继续只有一个来源，分步命令保留用于修复。输出逐行进度，Agent 后台运行，不用多轮对话。
    - 验证：在每个步骤后中断都能重跑完成。

29. **按依赖并行部署**
    - 改法：不同主机并行，同一主机靠维护锁排队（锁是排队等待，不是立即失败）。多个单元导出身份时会在控制机上排队。
    - 依赖顺序：admin → 其他主机的主机服务 → EventBus、Storage、Access、出口代理 → 元数据 → 管理台 → 初始化 → collector-stream、Trade、因子引擎、归档 Worker → 验收。
    - 验证：用假主机验证依赖顺序；真实环境连续安装多次，确认没有并发竞争。

30. **元数据分组并发**
    - 问题：382 项逐条调用，`--stage storage` 和完整初始化各跑一遍，累计约 2 分钟。
    - 改法：不同类资源按依赖顺序执行。字段分组先写父再写子；列按 View 和数据集分组，组内串行，因为新列排序依赖写入顺序。现在每列都翻页查一遍，改成每组查一次。`init-storage.json` 记下种子摘要，一致且业务空间还在时跳过第二遍的导入和核对，激活每次都跑。先不加 Storage 批量接口。

31. **防火墙批量写入**
    - 问题：18～19 条规则逐条调用云接口，安装时跑两次。
    - 改法：每台主机解析和读取各一次，缺的规则一次写入，各台并行。批量后重跑很便宜，初始化继续跑一次，不加回执。

32. **并行清除旧部署**
    - 现状：`wipe.py` 已是下发脚本且可以重复执行，但逐台串行、先优雅停止，不清云函数。
    - 改法：
      - 全部主机并行，一台失败不影响其他台，失败时全部重跑（脚本可重复执行）。整机清空时数据都要删，不再需要先下游后上游。
      - 删掉看护和外部服务后，循环结束进程直到目录内没有进程，不走优雅停止。同步删除，实测很慢再考虑回收目录。
      - 清空、防火墙、部署合并成一次确认。预检先实测下载源和磁盘，通过后下载、清除、防火墙同时进行。重装时总耗时取决于最慢的一项；代价是下载中途失败时旧程序已删除，要换源、本机推送或修好网络后重跑。
      - 磁盘放不下新版本时，这台先清除再下载。
      - 预检改用并行扫描，保持主机顺序；不再试打包，改为核对下载哈希。
      - 中断后重跑：未完成标记存原摘要和每台的完整范围，范围变大时拒绝。
    - 范围：

      | 遗留项 | 处理 |
      | --- | --- |
      | 部署根、外部目录、systemd 服务、定时看护 | 授权后清除 |
      | 部署根之外的 moox 进程 | 预览列出，用 `--kill-outside` 确认后才结束 |
      | 腾讯云 `moox-fetch-plan-` 函数 | 单独的任务和参数，预览单独一行，单独确认 |
      | 防火墙规则、日志服务 | 保留 |
      | 本机旧状态 | 归档 |
      | 不在 `moox.toml` 里的主机 | 只列出，不碰 |

    - 保留：实盘账户检查和系统目录保护不变。
    - 验证：一台中途失败后重跑；家目录下的配置残留再盘点一遍。

33. **第一根 K 线提前**
    - 问题：对账每分钟一轮，生效周期至少提前 2 分钟，验收要等第一根 K 线收盘。
    - 改法：全部任务启用后调一次新 RPC 触发对账，避免把任务拆成两份计划；全部是推送或本地执行项的首份计划，提前量改成 30 秒，重选周期沿用这个提前量。
    - 验证：实测 500 多个标的的 WS 订阅能在生效周期之前完成。

34. **选空间和默认示例**
    - 选空间：安装开始时问，安装最后执行。放到开始才能预检：crypto 要海外机、collector-stream 和出口代理；A 股没有推送路径，collector-stream 的空间写死为 crypto，所以必须先配好 `[scf_plan]`，否则预检拒绝。四个空间的元数据照常导入，选择只决定启用哪些任务。
    - 启动：提供可单独运行的 `setup start --space-id <空间>`，重跑不重复创建。crypto 依次启用采集任务、确认因子任务已导入、用固定 ID 创建并启用默认策略。任务已被用户实例绑定时，跳过示例并说明。
    - 默认策略：继续用 `examples/strategies/dual_ma_swap_1m.yaml`，去掉 `min_age_bars`，绑定 `ftask_swap_1m`，不挂账户。用户想在这个任务上跑自己的策略时，停掉示例，用 `strategy instance update` 改绑。
    - 因子机：没有因子机时跳过因子和默认策略，并说明原因。
    - 告警：去掉 `min_age_bars` 后，前几根缺数会记 `too_many_missing` 并告警。改成本次会话还没有成功结果时算积累中，有单独的短上限，第一次成功后恢复原样。
    - 验证：前约 10 分钟的跳过不告警，长期缺数仍告警；验收只等 K 线和因子，并告诉用户大约何时出现第一个策略结果。

## 可选，暂不排期

35. **admin 阶段一次准备，control 不再停 Admin**：修完第 20 项后控制面中断还剩约 25 秒，省下这部分要改带恢复日志的发布流程，风险大于收益。

36. **Collector 的 DNS 刷新改异步、组件并行启动**：启动序列共约 13 秒，其中 DNS 约 7 秒，合计约省 10 秒。

## 不做

- 换 zstd 压缩、压缩二进制：下载变快后只省几秒。
- 云镜像：绑定云厂商，用户环境也各不相同。
- 回收目录和后台删除：实测删除很慢再加。
- Storage 改用单一二进制：只省约 2 秒，要改 23 处。

# 第一轮（已完成）

## 一、默认路径必须走得通

新用户都会走这条路，这里有问题就是人人必现。

1. **配置依赖完整性检查**
   - 问题：默认配置可能缺组件，部署到一半才以“未就绪”的形式暴露。
   - CLI：`setup validate` 检查所有授权服务都有对应部署，缺什么报什么，并给出修正命令。
   - 验证：单元测试对 `config init` 能生成的每种拓扑（有无海外机、有无因子机）都跑一遍。

2. **安装顺序只有一个来源**
   - 问题：`install.md` 和 `fresh-deploy.md` 各写一套顺序，慢慢走样，就绪条件依赖的数据被排到了后面。Agent 还要自己推算计划，拓扑不同时容易错。
   - CLI：`setup validate` 输出 `next_steps`，按当前拓扑和已完成的步骤给出接下来的命令；元数据导入放到依赖它的服务之前（`setup init --stage storage`）。
   - skill：不再写死步骤表，照 `next_steps` 执行。
   - 规则：组件的就绪条件不能依赖排在它之后的步骤。

3. **每个阶段先查前提**
   - 问题：前提不满足时，要等上传、启动、超时后才失败，或者报一个不相干的错误。
   - CLI：`core` 未完成、元数据未激活、磁盘不足等，在阶段开始时就报出来，直接说缺哪一步。

## 二、失败时要看得清原因

不管环境出什么问题，用户和 Agent 都要拿到事实，不用靠猜。

4. **区分“连接断了”和“目标机失败”**
   - 问题：目标机明确失败也可能显示成 `observation failed`，Agent 按断线处理，反复重试。
   - CLI：两种情况用不同的错误，文案不混用；错误码要能从目标机带回来。

5. **未就绪要说出没就绪的项**
   - 问题：所有组件超时都只报 `did not become ready`，看起来像“启动即退出”。
   - CLI：只走白名单，输出值为 `false` 的字段名、缺少的服务名；进程已退出和一直没就绪分开报；端口冲突这类已知情况转成错误码。目标机原始输出继续隐藏，防止泄露。

6. **统一的只读日志入口**
   - 问题：skill 不让 Agent 上机，详细输出又要反复授权，回滚后的日志也不好找。
   - CLI：增加 `moox-cli setup logs --host <主机> --component <组件>`，只读，能看到失败回滚的发布目录里的日志。

7. **错误码和处理办法同步**
   - 问题：新增错误码后，文档可能没有对应处理办法，Agent 只能自己想。
   - 验证：测试确保每个错误码都有 CLI 说明，并在 `install.md` 的处理表里有一行。

## 三、重试和残留不能让情况变糟

8. **启动前查端口**
   - 问题：上次失败的残留或其他程序占着端口，新进程起不来。只在部署前查一次不够，冲突可能发生在部署中途。
   - CLI：持维护锁时，启动每个组件前查占用者。本部署目录内的残留核对身份后停掉并留日志；其他程序立刻失败，报端口和程序名。

9. **重试前确认上次已结束**
   - 问题：断线后再次运行，可能和目标机上还没结束的操作重叠。
   - CLI：`setup validate` 显示上次尝试的状态；SSH 断开后读目标机状态，等结束后报告结果，或提示可以安全重跑。
   - 不做断线后接着观察：要把目标机程序改成后台运行，改动大，收益不够。

10. **失败要自己收拾，磁盘要提前看**
    - 问题：每次失败都留下发布目录和离线包，小磁盘机器几次重试就接近写满。
    - CLI：回滚后删除失败的发布目录，保留当前版和上一版；`setup validate` 报告可用磁盘，不够时阻止继续。

## 四、对机器现状的判断要准

用户可能换电脑、换目录、换配置、换版本，部署也可能在任何一步中断。

11. **路线判定核对配置和版本**
    - 问题：状态目录只按控制机和部署根生成，换了配置或版本仍判为可继续，后面才报错。
    - CLI：记录生成状态时的配置摘要和版本，不一致时不判 `resume`，提示本机有旧配置可复用，或走清除。
    - 后续：整份配置都绑定过严，第 19 项收窄。

12. **清除覆盖本机全部相关状态**
    - 问题：`setup wipe` 留下的本机文件（比如旧 CA）会挡住后续全新安装。
    - CLI：列清本机状态，清除时一起归档；验证清除后能从头走完 `next_steps`，不被本机残留挡住。

## 五、skill 通用规则

13. **更新 `skills/moox/SKILL.md` 和 `references/install.md`**
    - 下结论要有证据：没看到日志或错误码，不说“产物有问题”，不建议回退版本。
    - 重试前必须说明这次改变了什么；什么都没变就不重试。只有 CLI 明确说连接断开才重跑。
    - Agent 不手工 `kill`、不上机 `stop`，不用重启机器解决部署问题。
    - 端口占用按占用者处理：非 MooX 程序问用户；旧部署按路线处理；失败残留由 CLI 清理。
    - 排查顺序固定：CLI 给出的原因 → `setup logs` → 停下来向用户汇报事实和选项。
    - 删除和重启这类操作前，用户看到的是事实和影响，不是猜测的原因。
    - 向用户汇报时说清停在哪一步、已确认的事实、还不确定的地方。
