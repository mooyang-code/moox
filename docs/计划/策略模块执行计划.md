# 策略模块重建：执行计划

> 状态：待评审，尚未编码。
> 依据：[策略模块评审与设计](策略模块评审与设计.md)（以下简称"设计文档"）。本文只写怎么做：改哪些文件、
> 按什么顺序、每一步怎么验收。项目尚未上线，不做任何历史兼容，旧数据库文件直接删除。

## 1. 已确认的决策

| # | 决策 |
| --- | --- |
| 1 | 实例只绑定一个 View（因子结果 View 或 K 线 View）；只由 `ViewDataReady` 触发；删除 cron 定时触发 |
| 2 | 规则用列表组织：`id`（稳定标识）、`name`（展示）、`type`（固定词表 `rank` / `signal`） |
| 3 | 标的池：默认 all；`universe` 可按 Storage 标签收窄或排除；规则可用 `pool` 显式覆盖；删除 UDF 机制 |
| 4 | 上期持有、本期缺数的标的：本期不参与计算，权重 0（清仓） |
| 5 | 选择结果为空允许发布空目标（转现金）；`portfolio.min_universe` 与 `max_missing`（默认 0.2）守门 |
| 6 | 回放只读 View，不读 PrimaryStore，不查周期标记 |
| 7 | DSL 保留可选的 `bar` 断言 |
| 8 | 每个周期都落库：`ok` 带解释明细，`skipped` 带原因 |
| 9 | Trade 事件契约不变；`valid_until` 从 4 根 bar 改为 2 根 |

## 2. 范围与原则

- 范围：`modules/strategy` 全部、`modules/strategy/proto`、`web/src` 的策略页面与 API、Admin 服务目录中的策略
  网关白名单、`docs/模块/策略.md`、部署脚本中与策略配置相关的部分。
- 不在范围：Trade、Factor、Storage 的代码；`packages/tradeeventpb` 与 `packages/events` 的事件契约。
- 原则：核心包整体重写，可移植的部分按文件移植；每个子步骤结束时仓库可编译、测试通过；阶段之间可独立合入，
  但阶段 B 完成前不部署新版本。

### 3.3 协议

重写 `proto/strategy.proto`。保留契约测试要求的消息与方法名（`Strategy`、`StrategyResult`、`InstrumentTarget`、
`StrategyInstance` 与既有 11 个 rpc），不出现 `Binding`、`StrategyRun`、`StrategyState`、`Performance`、
`target_quantity` 等被禁止的符号。

```protobuf
message Strategy {
  string strategy_id = 1;
  string name = 2;
  string dsl_yaml = 3;
  string dsl_hash = 4;
  string created_at = 5;
  string updated_at = 6;
}

message StrategyInstance {
  string instance_id = 1;
  string strategy_id = 2;
  string space_id = 3;
  string view_id = 4;

  string session_id = 7;
  // 启用时固化的解析结果（只读）：bar、日历、市场类型、每列的 origin_factor_id 与 source_hash
  string resolved_json = 8;
  string health = 9;                     // ok | degraded
  string created_at = 10;
  string updated_at = 11;
}

message InstrumentTarget {
  string instrument_id = 1;
  string target_weight = 2;
}

message StrategyResult {
  string result_id = 1;
  string instance_id = 2;
  string session_id = 3;
  string bar_end_time = 4;
  string valid_until = 5;
  string status = 6;                     // ok | skipped
  string skip_reason = 7;
  repeated InstrumentTarget targets = 8;
  string summary_json = 9;               // universe 数、各阶段数量、gross、net、换手、现金
  string input_json = 10;                // view_id、bar_start、事件 ID、因子 hash
  string rule_states_json = 11;
  string publish_status = 12;            // none | pending | sent | cancelled
  string created_at = 13;
}

message StrategyResultItem {
  string rule_id = 1;
  string instrument_id = 2;
  string stage = 3;                      // universe | filtered | scored | selected | weighted | dropped
  string score = 4;
  int32 rank = 5;
  string weight = 6;
  string reason = 7;
}

message ValidateStrategyReq {
  string dsl_yaml = 1;
  string view_id = 2;                    // 可选；给出时做列解析并在最新周期试算
}
message ValidateStrategyRsp {
  common.RetInfo ret_info = 1;
  repeated string diagnostics = 2;
  string resolved_json = 3;
  StrategyResult trial = 4;              // 试算结果，不落库
  repeated StrategyResultItem trial_items = 5;
}

message Replay {
  string replay_id = 1;
  string strategy_id = 2;
  string dsl_yaml = 3;
  string space_id = 4;
  string view_id = 5;
  string start_time = 6;
  string end_time = 7;
  double fee_bps = 8;
  string status = 9;                     // pending | running | done | failed | cancelled
  string progress_time = 10;
  string metrics_json = 11;              // 累计收益、年化、最大回撤、换手、平均持仓数、因子版本
  string error = 12;
  string created_at = 13;
  string updated_at = 14;
}

message ReplayBar {
  string bar_end_time = 1;
  string status = 2;
  repeated InstrumentTarget targets = 3;
  string summary_json = 4;
  double bar_return = 5;
  double equity = 6;
}

service StrategyMgr {
  rpc CreateStrategy(...);  rpc UpdateStrategy(...);  rpc GetStrategy(...);  rpc ListStrategies(...);
  rpc DeleteStrategy(...);  rpc ValidateStrategy(ValidateStrategyReq) returns (ValidateStrategyRsp);
  rpc CreateStrategyInstance(...);  rpc UpdateStrategyInstance(...);  rpc GetStrategyInstance(...);
  rpc ListStrategyInstances(...);  rpc SetStrategyInstanceEnabled(...);  rpc DeleteStrategyInstance(...);
```

### B1 `internal/dsl`

| 文件 | 内容 |
| --- | --- |
| `types.go` | `Strategy{Name, Bar, Universe, Rules []Rule, Portfolio}`、`Universe{Tags, ExcludeTags, Include, Exclude, MinBars}`、`Rule{ID, Name, Type, Pool, Filter, Score, Select{Top, Bottom, Where, Buffer}, Weight{Total, Method, Cap}, Side, FilterAfter, Entry, Exit, Holding{Bars, Offsets}}`、`Portfolio{Leverage, MinUniverse, MaxMissing, Rebalance{MinDelta}}` |

| `program.go` | `Program{Rules []CompiledRule, Columns []string, UsesPreviousBar bool}`，供 engine 与 input 共用 |

测试：解析与校验表格测试（含设计文档 4.3 的完整示例必须通过）；编译依赖提取测试；`rank(-bias_q_20 * close)` 这类表达式参数测试；错误信息包含规则 `id` 与阶段名。

```text
B1 dsl ─► B2 engine ─► B3 store ─► B4 input ─► B5 readiness ─► B6 trigger ─► B7 rpc/bootstrap ─► B8 收尾
```

## 11. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 因子结果 View 缺少某个携带列（例如采集任务输出字段变化） | 启用时解析列，缺列直接报错；运行时列缺失记为 `config_error` 跳过并标记实例 `degraded` |
| 解释明细使数据库增长（每期每规则每标的一行） | 只写进入 filter 阶段之后的标的；按天清理；`t_strategy_result_items` 主键即索引 |
| 回放占用 CPU 与 Storage 查询 | 单工作协程；分段读取；可取消 |
| `rows_per_series` 的 500000 单元上限 | `min_bars` 统计按标的分批，每批不超过 `500000 / (min_bars × 5)` 个标的 |
| 调大 `view_bars` 后 DuckDB 文件增大 | 只在需要长回放时调整，并观察 `max_view_file_bytes` 触发的容量重建 |
| 并行会话同时改动仓库 | 每个阶段单独分支与提交，提交只包含本阶段文件 |
