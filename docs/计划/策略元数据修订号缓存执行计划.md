# 策略元数据修订号缓存执行计划

状态：待实施（仅计划，尚未编码）。

## 1. 背景与目标

策略每个周期（1m）都要为所在 View 重新读取一批元数据：数据集的标的绑定、标的详情、标签、标签成员。
Strategy 在 control 主机，Storage 在另一台主机，这些读取每次是 5～6 次顺序的公网往返（`ListDatasetSubjects`
会分页读绑定，再按 200 个一批读标的详情）。元数据极少变化，却占了每期读取时间的大头，并且在公网抖动时
造成 `读取输入失败`，一期被跳过后下一期还会因 `previous_version_unknown` 连带跳过。

目标：元数据没有变化时，标的绑定、标的详情、标签、标签成员这四类读取每个周期只多一次很小的"修订号"查询；元数据变化时当期立刻重读。
`GetView`/`ListViewColumns`（以及设置了 `min_age_bars` 时的覆盖统计）仍每期读取，不在本次范围内。
行数据（K 线与因子结果）仍然每期现读、不缓存，因此与周期始终对齐。

非目标：不做通用元数据缓存框架；不改 View 行读取；不追求多实例一致性（Strategy 单实例）。

## 2. 方案总览

```text
Storage：subjects_revision（按 space 单调递增，由触发器在同一事务里递增）
         GetDataset 的响应新增字段 subjects_revision（Metadata RPC 本来就直读 SQLite）
Strategy：进程级缓存 {space → revision, 绑定/详情/标签/成员}
         LoadBar 取得 View 后，按 view.DatasetID 查一次 revision；一致则复用，不一致则整体清空重读
```

关键设计选择：

1. **修订号放在 `GetDatasetRsp`，不新增 RPC。** 新增 RPC 要改服务目录（方法清单、ACL、路由数与快照哈希），
   并重发所有主机的网关快照；加字段只需要重新发布 Storage。
2. **按 space 计数，而不是按数据集。** 标的、标签成员的变化是 space 级的，数据集的标的范围由标签推导；
   space 级计数最简单，代价只是别的数据集的标的变化也会让缓存失效一次，可以接受。
3. **触发器递增，而不是在每条写路径里手工递增。** 触发器与变更在同一事务，覆盖所有写路径（Collector 同步
   标签成员、CLI、控制台编辑），不会漏。

## 3. Storage 改动

### 3.1 Schema（`modules/storage/schema/metadata.sql`）

新增一张表和一组触发器，全部 `IF NOT EXISTS`；**不提升 `schema_version`**（13 保持不变）。原因：版本不一致时
Storage 要求清库重建，生产元数据不能清。`InitSchema` 会在已有库上重放整份 schema SQL，新表和触发器因此能
通过 `moox-storage-cli init` 补上，不影响已有数据。

```sql
-- 标的与标签成员的修订号：按空间单调递增，供调用方判断缓存是否过期
CREATE TABLE IF NOT EXISTS t_space_revisions (
    c_space_id TEXT NOT NULL PRIMARY KEY,
    c_subjects_revision INTEGER NOT NULL DEFAULT 0
);
```

触发器（命名 `trg_subjects_revision_*`，每个动作一次 `INSERT ... ON CONFLICT DO UPDATE SET c_subjects_revision =
c_subjects_revision + 1`），格式遵守项目 schema 规范。需要覆盖：

| 表 | 事件 | 说明 |
| --- | --- | --- |
| `t_subjects` | INSERT、DELETE、`UPDATE OF c_status, c_attrs_json, c_subject_type, c_market` | 标的新增、删除、状态与属性变化 |
| `t_subject_tags` | INSERT、DELETE、`UPDATE OF c_status` | 标签成员变化（Collector 每小时同步） |
| `t_tags` | `UPDATE OF c_market_type`、DELETE | 标签详情里策略用到 `market_type` |
| `t_datasets` | INSERT、DELETE、`UPDATE OF c_subject_tags_json` | 数据集标的范围变化；同 ID 删除重建且范围不同也必须失效（缓存键是 space+dataset） |

注意点：

- **`UPDATE OF` 必须列出具体列、排除 `c_mtime`**：每张表都有 `trg_*_mtime` 触发器，会在更新后再
  `UPDATE ... SET c_mtime`，若按整行 `AFTER UPDATE` 触发会重复递增甚至自触发。
- `t_tags` 的 `c_last_run_at` 等同步状态更新不应递增，所以只监听 `c_market_type`。
- 标的/成员批量同步时每行递增一次，次数多但无害；修订号只比较是否相等。
- 种子导入、`init` 重放 schema 不会触发（`IF NOT EXISTS`），空库修订号为 0 也合法。
- 同步更新 schema 单元测试里的契约断言（`metadata_schema_version_test.go`、`metadata_seed_contract_test.go` 如有
  表清单断言）。

### 3.2 读取与 RPC

- `modules/storage/proto/metadata.proto`：`GetDatasetRsp` 新增 `uint64 subjects_revision = 3;` 并重新生成
  `storagegen`（`make` 目标按仓库现有方式）。
- 元数据读接口新增 `SubjectsRevision(ctx, spaceID) (uint64, error)`：
  `SELECT c_subjects_revision FROM t_space_revisions WHERE c_space_id = ?`，无行返回 0。
  - SQLite 实现放在 `internal/service/metadata/sqlite`。
  - 实际 Metadata RPC 的装配（`cmd/server/main.go`、`catalog/service.go`）把 SQLite store 直接作为 `s.metadata`，
    `GetDataset`、`ListSubjects`、`ListDatasetSubjects`、`GetTag`、`ListTagMembers` 都直读 SQLite，不经快照缓存
    （`cache/store.go` 的快照读取不在这条路径上），所以修订号与这些数据天然一致。快照包装若因满足接口需要补方法，
    只做透传；View 的 `gatewayMetadataClient` 没有实现该接口，不需要改。
- `internal/service/catalog/metadata_catalog.go` 的 `GetDataset`：取到数据集后再调一次 `SubjectsRevision`，
  填入响应；该查询失败时返回错误，不静默返回 0。

## 4. Strategy 改动

位置：`modules/strategy/internal/input/cache.go`（目前的 `eventClient` 事件内缓存）。

- 把标的绑定 `subjects`、标签成员 `members`、标签详情 `tags` 三个 map 从"每事件一份"改成**进程级**，
  放进一个带互斥锁的小结构，并记录当前 `(spaceID → revision, loadedAt)`。
- **查询位置**：`ForEvent()` 本身没有 ctx、View 参数，也不返回错误，且 Handler 在实例求值之前就调用它，
  不能在这里查询。改为在 `LoadBar` 已取得并验证当前 View 之后，首次需要元数据时按 `view.DatasetID` 调一次
  `GetDataset` 取 `subjects_revision`，同一事件内复用结果；查询错误从 `LoadBar` 返回，走既有的读取失败计数、
  预算耗尽后落库为 `skipped` 的路径，不要在 `Handle` 里提前返回（消费者 `MaxDeliver=-1`，会无限重投）。
  空间级计数不需要追溯源数据集，查 View 的数据集即可。
  - 与缓存的 revision 相等 → 复用缓存；
  - 不相等或缓存为空 → 清空这三个 map，登记新 revision，再按需重读。
- 先读修订号、再读数据：期间若有变化，缓存里是旧数据但 revision 也是旧的，下个事件比较不等就会重读，方向安全。
- 并发：`Handler.Handle` 持锁串行处理事件，只有一个 Handler，进程级缓存由实时 Loader 持有即可，加一把互斥锁保护
  map，不需要 singleflight。
- 不设 TTL：写路径由触发器全覆盖，Metadata 读取直连 SQLite，不存在快照滞后，TTL 只会掩盖遗漏。
- `View`、覆盖统计 `coverage`、行查询保持现状（每事件现读或不缓存），不属于本次改动。
- `RPCClient.GetDataset` 已存在，需要把响应里的 `subjects_revision` 带出来（`DatasetInfo` 增加字段）。
- 回放（`replay`）使用的 Loader 不走事件缓存，保持不变。

## 5. 测试

Storage：

- schema：在**有数据的版本 13 旧库**上连续执行两次 `init` 不报错、数据不变；新表、触发器存在；对 `t_subjects`/`t_subject_tags`/`t_tags`/`t_datasets` 的各类写入递增修订号，
  仅更新 `c_mtime`、`t_tags.c_last_run_at` 不递增；同一事务回滚时修订号不变。
- 服务：`GetDataset` 响应带 `subjects_revision`，标的变化后值增加；缓存包装不缓存该值。

Strategy：

- 修订号不变时第二个事件不再调用 `ListDatasetSubjects`/`ListSubjects`/`GetTag`/`ListTagMembers`（计数断言）。
- 修订号变化后重读并更新缓存；`GetDataset` 失败时该事件按现有的读取失败路径处理，不使用缓存。
- 真实集合变化：停用标的、修改 `series_tag`、删除 DSL 引用的标签、同 ID 删除重建数据集且标的范围改变，缓存都被正确失效。
- Handler：修订号查询失败时仍消耗既有读取预算并最终记录 `skipped`，不无限重投。
- 现有 `input` 包测试全部保持通过。

## 6. 发布顺序

1. 本地 `go test` 通过：storage 相关包、strategy `./...`、servicecatalog（本次不改目录，哈希不应变化）。
2. 在 Storage 主机：先用新的 `moox-storage-cli` 执行 `init`（带 `--schema-path`）补建表与触发器，再替换 storage
   二进制并重启。顺序要点：`t_space_revisions` 表不存在时新二进制的 `GetDataset` 会报错，所以必须先 init；
   旧二进制不认新表和新字段，先 init 对它无影响。Storage 二进制含 CGO，在编译机（192.168.0.103）上构建。
3. 校验：对种子 space 手工改一个标的状态，`gateway call ... GetDataset` 看到 `subjects_revision` 增加。
4. 在 control 主机发布 strategy 二进制（`swap_comp.sh`），观察日志里该实例每个周期不再有标的绑定读取，
   且最近若干周期结果都是 `ok`。
5. 回滚：顺序是**先 Strategy、后 Storage**。新 Strategy 不能搭配旧 Storage：旧 Storage 不返回该字段，客户端读到 0，
   而 0 是合法修订号，之后元数据变化也一直是 0，缓存不会失效。Storage 的新表与触发器保留即可，旧二进制不受影响。

修复后重新跑测试，再做一次小范围复核即可，不循环。

## 9. 风险与待确认

- **触发器遗漏的写路径**：触发器在库内，任何写路径（含原生 SQL、批量导入）都会触发；同值 UPDATE 也可能递增，只是多一次失效。
- **空间级粒度**：别的数据集的标的变化也会让一次缓存失效，换来实现简单，不做细分。
- **`moox-storage-cli init` 在已有库上重放**：已确认 `InitSchema` 先校验版本再整体执行 schema，新对象均为
  `IF NOT EXISTS`；`scripts/runtime/storage-start.sh` 启动时已经会执行 init，部署时同步更新 SQL 文件并确认初始化的是服务实际使用的库。

## 10. 实施结果（2026-10-13）

- 已按计划实现并部署：Storage（`t_space_revisions` + 11 个触发器、`GetDataset` 带回 `subjects_revision`）、Strategy（`MetaCache` 跨周期缓存，`LoadBar` 取得 View 后先校验修订号）。
- 部署顺序：备份元数据库 → 用新 `moox-storage-cli init` 补建表与触发器（11 个触发器就绪）→ 换 `moox-storage-primary` 并重启 → 换 `moox-strategy` 并重启。线上 `GetDataset` 已返回 `subjects_revision`。
- Codex 审查结论：可以部署，无实现缺陷；两处测试盲点（缓存测试绕过 `LoadBar`、成员触发器与旧库补建未单独验证）已补测试。
- 上线后连续周期结果均为 `ok`。未单独测量每期读取耗时的前后差值；标的元数据读取次数由单元测试断言（修订号不变时第二个事件不再读取）。
- 注意：storage-primary 的启动脚本（runtime 托管）不再执行 `init`，以后改 schema 需要手工在 Storage 主机执行 `moox-storage-cli init --storage-conf=config/storage.yaml --schema-path=schema/metadata.sql`（在 `storage-primary` 目录下）。
