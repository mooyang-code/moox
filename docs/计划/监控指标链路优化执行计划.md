# 监控指标链路优化执行计划

> 状态：v1，2026-10-20。阶段 1（服务指标停写 Storage）已编码、测试通过，**尚未发布**；阶段 2～6 尚未编码。
> 来源：对 VictoriaMetrics（下称 VM）的调研，以及 2026-10-20 对生产 control、storage 主机的只读核查。

## 1. 结论与取舍

**VM 不作为核心组件引入。** 它能替代的只有“指标时序历史存储”这一层，而我们这一层恰好没有读取方（见 2.3）；
告警、采集两层与我们的设计不匹配：

| 层 | VM 的做法 | 我们的做法 | 结论 |
| --- | --- | --- | --- |
| 采集 | vmagent 抓取 `/metrics` | 服务推送有界快照到 NATS，水位前进 1 秒内补报 | 不换：SCF 函数无法被抓取，补报机制是链路时延的基础 |
| 存储 | 单二进制 TSDB，PromQL 查询 | 最新值存 SQLite；主机历史存 Storage | 暂不引入，满足第 3.6 节条件再作为可选历史存储 |
| 告警 | vmalert：PromQL + `for`，通知只能经 Alertmanager | Go 代码评估：交易日历、上报确认迟到、拓扑对账、多渠道送达 | 不换：业务语义写不成 PromQL，告警状态已持久化在 SQLite |
| 到达记录 | 无对应 | SQLite 逐根记录 | 不变 |

**借鉴的是 VM 的几条设计**，按收益排序落到下面的阶段里：

| 借鉴点 | VM 对应能力 | 落地阶段 |
| --- | --- | --- |
| 历史数据要有读取方才值得存 | 单一保留期，按需存储 | 阶段 1、2：下线没人读的服务指标历史 |
| 新序列速率限制 | `-storage.maxHourlySeries` / `-storage.maxDailySeries` | 阶段 3 |
| 入库丢弃要可见 | `vm_rows_invalid_total` 等自监控指标 | 阶段 4 |
| 长期历史与临时查询 | `-retentionPeriod` + MetricsQL | 阶段 6（按需）：VM 作为可选历史存储 |

**原则**（沿用项目约定）：无需兼容历史；不新增并行机制；监控不能因为自身依赖（Storage）故障而失明。

## 2. 现状（已核实，2026-10-20 生产只读）

### 2.1 链路与体量

```text
各服务（30 秒 + 水位补报）──zstd 字典──► NATS MOOX_OBSERVABILITY（24h，磁盘 24 MB）
                                          │
                                          ▼
                                       Monitor ──► SQLite：目录、最新值（t_monitor_metric_latest）
                                          │
          （阶段 1 之前）UpsertFields，经网关（zstd 字典）
                                          ▼
                       storage-primary ─► Pebble（storage-node，全部数据 4.1 GB）
                                          │ 行事件（zstd 字典）
                                          ▼
                       NATS MOOX_STORAGE（72h，磁盘 185 MB，含行情、因子）
                                          │ durable storage_view_metrics（system_metrics 分区，4 worker）
                                          ▼
                       storage-view ─► DuckDB view_mooxsys_service_metrics（440 MB）
```

| 指标 | 数值 | 来源 |
| --- | --- | --- |
| 服务指标快照 | 约 2100 份/小时（0.6 份/秒） | `t_monitor_metric_ingest_messages` 最近 1 小时 |
| 活跃序列 | 246（目录共 483，含 24 小时内未清理的旧实例） | `t_monitor_metric_latest` |
| 写入 Storage 的行 | 约 3 万行/小时（246 × 120 次），48 小时约 140 万行 | 估算 |
| 服务指标 View 索引 | 440 MB，占全部 View 索引 2.9 GB 的 15%，与 1 分钟 K 线视图（530 MB）相当 | `du` |
| Storage 主机 | 4 核 15 GB；负载 0.35～0.7；storage-view 平均占 0.48 核、常驻 1.4 GB | `ps` / `top` |

**对系统的影响**：主机整体不紧张，但服务指标是一份**没有读取方的数据**，却占了 Storage 写入、一条独立的 View 消费分区、
15% 的 View 索引和一部分 MOOX_STORAGE 的磁盘。View 的 CPU 中服务指标占多少没有单独计量，这里不给数字。

### 2.2 链路压缩

系统内部传输已统一用 wirecompress（zstd + 训练字典，按空间绑定字典），2026-10-19 随 `53b3c40a` 发布，设计与实测见
[统一压缩算法（zstd 字典）执行计划](统一压缩算法（zstd字典）执行计划.md)。本计划涉及的链路都已覆盖：

| 链路 | 压缩 | 说明 |
| --- | --- | --- |
| 服务 / HostAgent → NATS（指标、主机快照） | wirecompress | 事件信封由发布器默认压缩（≥256 B 且压缩后至少小 10%），快照内层 gzip 已删除；Monitor 经 `DecodeRaw` 透明解压 |
| Monitor → Storage（经主机网关 11003） | wirecompress | 跨主机的 tRPC 帧恒定压缩，不再有 `gateway_client.compression` 开关 |
| Storage → View（MOOX_STORAGE 行事件） | wirecompress | 发布器压缩，实测约 8 倍（发布日实测） |
| NATS 客户端连接、JetStream 落盘 | 否 | 有意不开：信封已压缩，再叠一层连接层或 S2 流压缩没有收益 |

计划里有意不纳入的位置（统一压缩计划第 1 节）：浏览器流量、`.csv.gz` / `tar.gz` 文件格式、出口代理访问交易所的外部 HTTP、
通达信协议、Prometheus 抓取。

### 2.3 服务指标历史没有读取方

全仓搜索 `dataset_mooxsys_service_metrics` / `view_mooxsys_service_metrics`：除了写入、种子、配置与测试，没有任何读取代码。
概览、告警、Doctor 都只读 SQLite 的最新值。同时它带来三处耦合：

1. **入库被 Storage 卡住**：原流程先写 Storage 再提交 SQLite，Storage 写失败时整份快照重试，服务指标最新值停止更新，
   进而影响 Reporter 状态和数据集新鲜度判断——监控在 Storage 出问题时恰好失明。
2. **就绪依赖表结构**：Monitor 的 `/readyz` 要求服务指标数据集元数据校验通过。
3. **自己告自己**：服务指标数据集不在新鲜度检查的排除名单里（只排除了主机数据集），停写后会被判为数据中断。

### 2.4 基数

Storage View 对每个视图上报最多 200 条“落后标的”（`moox_storage_view_output_lagging_subject_data_time_seconds`，带 `subject_id` 标签）。
2026-10-19 服务指标视图自身就上报过 214 条这类序列——服务指标的序列在 View 里落后，又变成新的服务指标被写回去。
Monitor 入口只有单份快照的上限（`DefaultMaxSamples` 100000、`DefaultMaxMetricFamilies` 2000），没有“新序列速率”的限制。

### 3.3 阶段 3：指标基数保护

借鉴 `-storage.maxHourlySeries` / `-storage.maxDailySeries`：**已有序列照常更新，只拦新序列**，超限时可见、可告警。

- **入口限额**：`modules/monitor/internal/metrics/message_store.go` 在 `CommitIngest` 写目录前统计本小时、本日新出现的序列数；
  超过限额的新序列样本丢弃（快照的其余样本照常入库，消息仍确认，不重投）。默认每小时 300、每天 1000（现状目录 483 条、活跃 246 条），
  配置项 `metrics.max_new_series_per_hour`、`metrics.max_new_series_per_day`。
- **自监控**：`moox_monitor_metrics_series_limit_current{window}`、`moox_monitor_metrics_series_limit_max{window}`、
  `moox_monitor_metrics_series_dropped_total{service}`；Doctor 上下文带上被丢弃最多的服务与指标名。
- **告警**：新增一条 warning 级检查 `metrics_ingest:series_limit`，当前值超过上限 90% 或本小时有丢弃即告警，文案由 `internal/alerttext` 生成。
- **生产者侧**：核对 Monitor 实际读取几条“落后标的”序列（K 线新鲜度告警最多列 `max_subjects_per_alert` = 20 个标的），
  若只用前 20 条，把 `ViewLaggingSubjectsReported` 由 200 降到 20，单个视图最多少 180 条序列。用途核对清楚之前不改。
- **测试**：限额内全部入库；超限时旧序列继续更新、新序列被丢且计数；跨小时窗口重置；重复投递不重复计数。

### 3.4 阶段 4：入库丢弃可见

借鉴 `vm_rows_invalid_total`：现有 `moox_monitor_metrics_ingest_total{result}` 只分 success / error / rejected，看不出丢在哪一步。

- `FilterHealthSamples` 按白名单静默丢弃的样本计入 `moox_monitor_metrics_samples_filtered_total{service}`。
  生产者改了指标名、白名单没跟上时，现在完全看不出来。
- `rejected` 细分原因：`checksum`、`limit_exceeded`、`parse`、`space`，写入 `moox_monitor_metrics_ingest_total{result,reason}`。
- Doctor 上下文给出每个服务最近一次被拒的原因与时间。
- 只加计数与诊断字段，不新增告警（阶段 3 的告警已覆盖基数失控）。

### 3.5 阶段 5：不做（已被统一压缩覆盖）

原计划给 JetStream 流加 S2 压缩。统一压缩（wirecompress）已在发布器层压缩事件信封，流里存的就是 zstd 字节，
再叠 S2 没有收益，且统一压缩计划明确不开 NATS 连接层压缩。本阶段取消。

### 3.6 阶段 6（按需）：VM 作为可选的长期历史存储

**触发条件**（满足任一再立项）：

- 需要保留几个月的主机、服务指标做容量规划（现在主机历史只有 7 天，磁盘预测只看 7 天）；
- 排障时需要临时查询白名单之外的指标；
- 主机指标历史本身成为 Storage 的负担。

**方案草图**：control 主机部署单节点 VM（只监听 loopback，`-retentionPeriod=90d`）；Monitor 在提交 SQLite 之后异步、尽力而为地把样本推到
`/api/v1/import/prometheus`，失败只计数，不影响入库与告警；查询经控制台代理接 Grafana。告警、到达记录、拓扑对账仍留在 Monitor。
立项时另写设计，评估备份（`vmbackup`）、鉴权（vmauth 或只走网关）与部署工具接入。

## 4. 不做的事

- **不用 vmalert 替换告警**：交易日历、上报确认迟到、拓扑与网关信号合并、多渠道送达规则都无法用 PromQL 表达；
  告警状态和事件已在 SQLite 持久化，比 `ALERTS_FOR_STATE` 重启恢复更可靠。
- **不用 vmagent 抓取**：推送加补报是链路时延的前提，SCF 函数也无法被抓取。
- **不把到达记录搬进时序库**：它是事件记录，要做按链路、按日期的关系查询。
- **不恢复服务指标历史写 Storage**：真有历史需求，走阶段 6。

## 5. 风险与回滚

| 风险 | 处理 |
| --- | --- |
| 生产 Monitor 配置未删 `metrics.storage` 段，新版本启动失败 | 发布步骤第 2 步；失败时 `status.sh` 立即可见，放回旧二进制即可 |
| 阶段 2 先发代码后删 durable，旧 durable 无法用工具删除 | 发布顺序写死：先删视图、数据集与 durable，再发代码 |
| 阶段 3 限额过低误丢新上线服务的指标 | 限额按现状的 2 倍以上设置；丢弃有计数和告警；配置可调 |

## 6. 验收总表

| 阶段 | 验收 |

| 1 | 服务指标入库不再调用 Storage；Storage 不可用时最新值照常更新；`mooxsys` 不出现在新鲜度检查与数据链路 |
| 2 | 生产没有 `view_mooxsys_service_metrics`、`storage_view_metrics`；View 索引减少约 440 MB；storage-view 正常 |
