# 因子任务与参数模型重构设计

状态：**定稿**（2026-10-25，v4 吸收第三轮审查后定稿，尚未编码）。第 4 节 D1~D15 是与用户逐条讨论确认的核心规则（D6 的落点在写文档时由行属性改为声明列，见 5.5；
v2 增加 D13~D15：命名风格、单输出与多输出、命名公共包；v3 吸收第一轮 Codex 审查，见第 17 节；v4 吸收第二轮复审并去掉跨任务公共计算与 `c_started_through`，见第 18 节；第三轮审查与定稿见第 19 节）；
其余实现细节是写文档时补充的，集中列在第 13 节（S1~S13），用户已确认全部按建议执行，正文中对应处标注「补充项 Sn」。项目尚未上线，不考虑兼容、迁移与成本，
一切以设计合理为准；实现后以[因子](../模块/因子.md)、[策略](../模块/策略.md)为准。本设计取代
[因子成员固定参数执行计划](因子成员固定参数执行计划.md)中的别名与参数列规则，以及[因子动态调参执行计划](因子动态调参执行计划.md)中的
私有因子集、参数快照与冻结记录。

## 1. 背景

2026-10-25 在生产环境给策略 `chain_ema20w_5m` 测了全链路耗时：一根 5m K线从收盘到策略提交完成共 **8.0 s**。

| 区间（相对收盘） | 环节 | 耗时 |
| --- | --- | --- |
| 0 → 0.95 s | 采集、入库、采集完成事件送达引擎 | 0.95 s |
| 0.95 → 4.34 s | 共享任务「采集结果 · 5m」计算（13 个默认因子加 `Ema_20_50000`，501 个标的） | 3.39 s |
| 4.34 → 4.50 s | 共享任务结束到私有因子集开算 | 0.16 s |
| 4.50 → 7.10 s | 策略私有因子集计算（5 个因子，含 5 万根预热） | 2.60 s |
| 7.10 → 7.64 s | 私有结果写入，View 发出「结果就绪」 | 0.54 s |
| 7.64 → 8.00 s | 策略读取、求值、提交 | 0.36 s |

暴露出两类问题。

**性能**

- **重复计算。** 策略声明的 5 个因子，共享任务早已算过；私有因子集又算一遍，多花约 3.3 s。
- **串行分发。** 同一源数据集上的多个集合本来互不依赖，但 `eventconsumer/handler.go` 逐个调用 `lanes.Do`，
  而 `Do` 会等这个集合算完才返回。所以私有集合要等共享任务算完才能开始。

**模型复杂**

- 「共享任务 / 私有因子集」两种任务。
- 成员别名，以及别名与列名的推导规则。
- 只有私有集合才写的参数列 `<别名>__<参数名>`。
- 共享成员的固定参数校验。
- 参数侧：四张参数表（请求、快照、冻结区间、冻结期次）、离线冻结与补报，以及策略侧的投递 outbox。

上一轮代码审查里的阻断和高优先级问题，多数出在这些分支的交界处。

## 2. 原则

1. 每一层都是同一个形状：**输入数据集 → 任务 → 输出数据集**。
2. 一个概念只在一个地方定义：配置在成员表，运行时提交在成员表的运行状态列，历史事实在结果行。
3. 能由规则推导的不存储，比如列名；能由因果顺序保证的不加锁、不登记，比如参数生效的期次。
4. 各任务完全独立：只算自己的成员，任务之间并行，不做跨任务的公共计算。

## 3. 分层模型

```text
采集数据集 ─┬─ 因子任务 A ──► 因子结果数据集 A ──(1:1)── 策略实例 1 ──► 策略结果
           └─ 因子任务 B ──► 因子结果数据集 B ──(1:1)── 策略实例 2 ──► 策略结果
   ▲
引擎本地序列（与源数据集一一对应，是它的超集：保留更长的历史，供预热）
```

- **采集数据集**是原始数据的源头，一类数据放在一个数据集里。
- **因子任务**关联一个源数据集和一个频率，产出一个因子结果数据集。一个源数据集可以有多个因子任务。
- **策略实例**关联且只能关联一个因子任务，独占且永久，基于它的结果数据集求值。策略结果仍存在策略模块的 SQLite 里，这次不搬进 Storage。
- 「数据集」（dataset）的概念与 ID 规则保持不变；「任务」只指因子计算任务；「策略实例」不改名。

## 4. 决策

| # | 决策 |
| --- | --- |
| D1 | 去掉「共享任务 / 私有因子集」的区分，因子任务只有一种，由用户创建（控制台或 `moox.toml`），可以先于策略运行以积累历史 |
| D2 | 一个因子结果只能被一个策略实例关联，独占、永久。策略实例只能启用或停止，不能删除，也就没有「解除关联」 |
| D3 | 策略停止只影响策略层，因子任务照常计算，由用户手动停止 |
| D4 | 成员分**固定值**与**可变值**。固定值的参数在加成员时写定；可变值由关联的策略逐期提交 |
| D5 | 不再使用成员别名。成员键与列名由「因子 ID + 参数 + 是否可变 + 输出」推导（规则见 5.1）；同一因子在一个任务里最多一个可变成员，需要多个可变值就注册多个因子（例如 `ma_fast`、`ma_slow`） |
| D6 | 不再使用参数列。每个结果数据集有一个隐藏的系统列 `__params`（JSON），每行记录这一行所有成员实际用的参数，固定参数也冗余记录。这是参数的唯一历史记录 |
| D7 | 可变成员的默认参数写在成员行里。策略每期把下一期的参数写进成员行的运行状态列 `c_last_submitted_*`：只有一格，按标的合并，目标期不能倒退，不保留提交历史。引擎在本地记下每一期第一次开算时选定的参数，重试和重启都复用它；晚到的提交从下一期起生效；从未提交过的标的用默认值（见 6，v4 定稿） |
| D8 | 删除四张参数表、离线冻结与补报、`FreezeFactorParams` / `ReportOfflineFreezes` / `ListParamIntervals`；成员的 `c_carry_alert_periods` 一并删除 |
| D9 | 因子任务启用时，检查引擎本地序列是否覆盖最长的回看与预热，不补算；策略启用时只检查关联的任务在运行，且需要的列都存在 |
| D10 | 同一事件下的多个任务并行计算、各自写出；每个任务只算自己的成员，不做跨任务的公共计算，暂不考虑重复计算（v4） |
| D11 | 改名：set 改为 task（`t_factor_tasks`、`ftask_…` 等，见第 11 节）；中文「因子集」「集合」统一为「因子任务」，「补算任务」改为「补算作业」 |
| D12 | 策略侧的 `t_strategy_param_submissions` 并入 `t_strategy_results`，只投递最新一条还没送达的参数 |
| D13 | 因子 ID、输出名、参数名全部小写，名字内部用单下划线；成员键与列名的段与段之间用双下划线（`ema__20_50000`、`boll__mid`、`ma_fast__var`），解析不需要查定义（5.1） |
| D14 | 单输出因子没有输出名，列名就是成员键；只有共用参数的因子才用多输出，输出名不能等于因子 ID，也不带因子前缀（5.2） |
| D15 | 成员键、列名、ID 的拼接、解析与校验集中到公共包 `packages/factorname`，前端用一份对应的 TS 实现，两边共用同一份测试向量（5.6） |

## 5. 成员与列

### 5.1 命名风格

因子 ID、输出名、参数名一律**小写，名字内部用单下划线分词**；名字与名字之间（段与段之间）用**双下划线**分隔。

```text
名字（因子ID / 输出名 / 参数名）： ^[a-z][a-z0-9]*(_[a-z0-9]+)*$   不能连续下划线，不能以下划线开头或结尾
成员键 = 因子ID [ "__" 参数段 ]
参数段 = "var" | 值 { "_" 值 }        值 = n?[0-9]+(p[0-9]+)?    （按定义声明的参数顺序，只写值不写参数名）
列名   = 成员键 [ "__" 输出名 ]        单输出因子没有输出段（见 5.2）
```

| 成员 | 成员键 | 列名 |
| --- | --- | --- |
| `ema`，参数全为默认值 | `ema` | `ema` |
| `ema`，span=20、warmup=50000 | `ema__20_50000` | `ema__20_50000` |
| `boll`，参数全为默认值（输出 mid/up/low/pctb） | `boll` | `boll__mid`、`boll__up`、`boll__low`、`boll__pctb` |
| `boll`，window=30 | `boll__30` | `boll__30__mid` 等 |
| `ma_fast`，可变 | `ma_fast__var` | `ma_fast__var` |
| `macd`，参数全为默认值 | `macd` | `macd__dif`、`macd__dea`、`macd__hist` |

- **为什么全部小写。** DuckDB 的列名不区分大小写，只差大小写的名字（比如现在因子库里的 `Ma` 和示例里的 `ma`）在查询时会撞上。
  另外，系统里的 Storage ID、分类 ID、输出名、参数名本来就是小写，因子 ID 也统一成小写后，就少了一条例外规则。
- **为什么段与段之间用双下划线。** 因子 ID 和输出名里本身就有下划线（`ma_fast`、`bias_q`），用单下划线分隔时，光看列名分不清因子 ID 到哪里结束。
  这一条取代了讨论初期定的「因子名_参数1_参数2」。
- **解析不需要查定义。** 按 `__` 切开：第一段是因子 ID；有两段时，第二段是 `var` 或者能匹配值的语法，就是参数段，否则是输出名；
  有三段时，依次是参数段和输出名；超过三段视为非法。为此有一条约束：输出名不能是 `var`，也不能匹配值的语法，比如 `n5`。
  把参数段的值对应到参数名，靠的是定义里参数的声明顺序，所以被引用的定义不能增删参数（见 5.4）。
- 值的格式化沿用[因子成员固定参数执行计划](因子成员固定参数执行计划.md)第 3 节：`FormatFloat('f', -1)`，`.` 写成 `p`，`-` 写成 `n`。
- **只接受规范形式。** 值的语法本身也能匹配 `01`、`1p0` 这类等价写法。所以公共包解析后，要把结果重新格式化一遍和原文比对，不一致就判为非法。
  名字（因子 ID 等）也一样，只接受上面的小写语法；`domain/validate.go`、`factorexpr/spec.go` 里现有的正则改为调用公共包。
- **列名只能还原「列名里有的信息」。** 例如默认成员的键 `ema` 能解析出「固定、参数全为默认值」，但具体参数值要查列元数据的 `factor_params`，或者查定义。
- 长度上限：因子 ID 24 个字符，输出名和参数名 16 个字符，成员键 44 个字符，列名 64 个字符。
- 冲突：成员键是成员表的主键，同一个任务里键重复的成员直接拒绝。
  比如因子 `ema_20` 的默认成员，和 `ema` 在 span=20 时的成员，按上面的语法分别是 `ema_20` 与 `ema__20`，不会撞上。
  列名如果和结果数据集里已有的非因子列重名（比如因子 ID 叫 `close`），加成员时拒绝。`__params` 以下划线开头，不可能和任何成员列重名。
- 固定成员的参数一旦写定就不能改。要换参数，就加一个新成员，键也随之不同。

### 5.2 输出

输出名定义在因子定义的表达式规格里，也就是 `t_factor_defs.c_spec`，这是唯一的定义来源。
`FactorDef.Outputs` 是编译 `spec` 时推导出来的，按书写顺序排列，不落库。加成员时，factor-mgr 按 `Outputs` 逐个拼出列名并注册结果列，
同时把 `output_name` 复制进列元数据；引擎每期按同样的顺序写值。

| 因子类型 | 规格写法 | 输出名 | 列名 |
| --- | --- | --- | --- |
| 单输出 | `output: <表达式>` | 不写，默认等于因子 ID | 成员键 |
| 多输出 | `outputs: {<输出名>: <表达式>, …}` | 必须写；不能等于因子 ID，也不要带因子前缀（写 `mid`，不写 `boll_mid`） | `成员键__输出名` |

```yaml
- factor_id: ema
  spec: |
    params:
      span: {type: int, min: 2, max: 4825, default: 20}
      warmup: {type: int, min: 0, max: 50000, default: 0}
    output: ema(close, span, warmup)

- factor_id: boll
  spec: |
    params: {window: {type: int, min: 2, max: 120, default: 20}}
    let:
      m: ts_mean(close, window)
      band: 2 * ts_std(close, window)
    outputs:
      mid: m
      up: m + band
      low: m - band
      pctb: (close - (m - band)) / (2 * band)
```

- 单数写法 `output` 目前解析器还不支持，`packages/factorexpr/spec.go` 只接受 `outputs`，所以这是必须做的规格改动。
- `factorexpr` 编译时检查：`output` 与 `outputs` 只能写一个；多输出至少要有两个输出；输出名符合 5.1 的名字语法，不是 `var`，不能匹配值的语法，也不能等于因子 ID。
  因子 ID 在规格之外，所以「输出名不能等于因子 ID」这一条由因子定义的校验来做，用的是公共包里的同一个函数。
- 只有确实共用同一组参数的因子才用多输出。拆开以后，每个成员的参数都得手动保持一致，可变时还要分别提交，而这种一致性无处校验。
  引擎在同一期里会合并公共子表达式，所以把不共用参数的输出拆成独立因子，并不会多算。
- 因子库按这个规则调整：
  - 所有因子 ID 改成小写，比如 `Ema` 改为 `ema`，`ZscoreAbsMeanQ` 改为 `zscore_abs_mean_q`。
  - `atr` 拆成 `atr` 和 `atr_pct` 两个单输出因子。
  - `boll` 的输出改为 `mid`、`up`、`low`、`pctb`；`macd` 的输出改为 `dif`、`dea`、`hist`。
  - 其余因子改为单输出写法。
  - 清理示例里重名或冗余的因子：`ma`（与因子库的 `ma` 重名）、`sma`、`ema50000`。
  - 中文名仍放在定义的 `name` 和列元数据的 `display_name` 里，不受影响。

### 5.3 成员移除与重新加入

- 移除成员时，结果数据集里的列保留，不再写入，页面上也不再显示。
- 再次加入同一个成员键时，沿用原来的列。被引用的定义连默认值也不能改（5.4），所以同一个键必然对应同一组参数。
  作为兜底，重新加入时还要核对旧列元数据里的 `factor_params`、`member_kind` 和本次的是否一致，不一致就拒绝。
- 列元数据（`DatasetColumn`，`origin_type=FACTOR`）回答「这一列是什么」。`attributes` 是 `map<string,string>`，记录：
  `factor_id`、`member_key`、`member_kind`（`fixed` / `var`）、`output_name`（单输出因子为因子 ID）、`column_kind=output`、`category_id`，
  以及 `factor_params`（固定成员的完整参数，规范 JSON 字符串；可变成员没有这一项）和 `definition_hash`。
  替换现有的 `member_alias`、`origin_factor_id`、`factor_output` 三项。

### 5.4 被引用定义的修改限制

被任务引用的因子定义，**不允许增删参数，不允许改参数的类型、声明顺序和默认值，也不允许增删、改名或重排输出**。要改这些，就新建一个定义。
- 列名和成员键依赖参数的顺序与输出的列表，这些一变，已有的列就对不上了。
- 默认值也不能改（v3 收紧，第一轮审查问题 5）：成员键省略了全为默认值的参数段，默认值一变，同一个键 `ema` 就会对应另一组参数。
- 允许修改表达式本身（比如公式）和参数的范围。改表达式会改变定义哈希，但不会改变列。
  改范围时，新范围必须包含所有引用它的成员现有的固定参数和默认参数，否则拒绝。

这样就不会再出现上一轮审查的问题 1：共享成员的固定参数，因为定义增删参数而变得不完整。

### 5.5 系统列 `__params`

- 每个因子结果数据集在创建时声明一列 `__params`：值类型为 `json`，`origin_type=FACTOR`，`origin_id=__params`，列属性 `column_kind=params`，展示名「因子参数」。
  不能用 `origin_type=SYSTEM`：它表示 `subject_id`、`data_time`、`freq` 这类键列，View 会把 `SYSTEM` 来源的列当作「不是数据集列」（`catalog/validate.go` 的 `isDatasetViewColumn`）。
- **Storage 必须改**（第一轮审查问题 1）。现在 `metadata_catalog.go:597-612` 把因子结果数据集里所有 `FACTOR` 列都当作输出列，
  要求带 `origin_factor_id`、`factor_output`，且后者等于列名；`catalog/validate.go:90-108,169-180` 的 View 列校验也依赖这两个旧属性。改为按 `column_kind` 分两类校验：
  - `output`：必须带 `factor_id`、`member_key`、`output_name`、`member_kind`，值类型为 `double`。列名必须和 `member_key`、`output_name` 拼出的结果一致，Storage 只做字符串比较，不引用公共包。
  - `params`：列名必须是 `__params`，值类型为 `json`，每个结果数据集恰好一列。
  - 默认 View 的列集合包含 `__params`；`isFactorViewColumn` 只把 `column_kind=output` 当作因子输出。
  - 展示名沿用 Storage 现有的 `validateColumnDisplayName` 规则：输出列的展示名取「定义中文名」，多输出时再加上输出名，比如「布林带·mid」；`__params` 的展示名是「因子参数」。
  - 因子侧 `catalog/reconcile.go:179` 现在用 `origin_factor_id`、`factor_output` 判断已有列是否兼容，要改为用 `member_key`、`output_name`、`member_kind`；
    `metadata.proto:135` 里关于旧显示名契约的注释一并更新（第二轮审查问题 8）。
- Storage 只存取 JSON 文本，不解析、不组装 map。读取时返回 `{field_id: "__params", value: {json_value: "…"}}`，由调用方自己解析。
  写入时必须用 JSON 值（`storageio` 的 `JSONText`，编码成 `json_value`）；如果写成普通字符串，会因为类型不符被拒绝。
- **不使用 Storage 的行属性。** 讨论时原打算放进行属性 `__moox_attributes`；写文档时核实：因子结果写入本来就拒绝行属性（`primarystore/factor_rows.go:64`），
  [Storage 读接口收敛设计](Storage读接口收敛设计.md)与[存储](../模块/存储.md)也规定 View 不保存、不返回行属性。所以改为声明一列普通字段：
  View 照常给它建索引，DuckDB 能用 `json_extract` 查询，也不用改 Storage 的行属性规则。
- 现在由因子模块注册的**因子输出列**都是 `double`（`catalog/service.go:674-697`），结果数据集里另外还有源数据列。
  Storage 本身已经支持 JSON 类型，相关代码包括：`primarystore/metadata_validator.go:188-248` 校验 JSON，`factor/internal/storageio/write.go:90-154` 能编码 `JsonValue`，
  DuckDB 索引的建列与读取在 `viewindex/duckdb/index_manager.go:732-754,820-835,1415-1429`。要改的只有上面列出的列契约。
- 内容：以成员键为键，只记录这一行实际用的参数，包括固定成员。输出名之类每列固定不变的信息只放在列元数据里，不进 `__params`。

  ```json
  {"boll": {"window": 20},
   "ema__20_50000": {"span": 20, "warmup": 50000},
   "ma_fast__var": {"window": 5},
   "rsi": {"window": 14}}
  ```

- 规范化：
  - 两层键都按字典序排列，不带空白。
  - 数字写成 JSON 数字，例如 `-1.5`、`50000`，用 `strconv.FormatFloat(v, 'f', -1, 64)` 的十进制写法。这和成员键里的 `n1p5` 是两回事。
  - 同一期重算时，这一列必须与因子值一样逐位相同，因为实时写入的提交 ID 依赖它。
- **部分成员补算时要合并**（第一轮审查问题 2）。补算可以只选部分成员（`recalcexec/executor.go:170-180`），而 Storage 会把 `__params` 当作一个完整字段整体覆盖。
  所以补算先读出原行的 `__params`，只替换这次重算成功的成员键，其余键保留后再写回。同一任务的「读、合并、写」由任务 lane 串行执行。
  原行不存在时，只记录这次实际计算的成员。
- 读取：Storage 不隐藏这一列，有人点名读或读全部列时照常返回。页面和导出按列属性 `column_kind=params` 自己隐藏；
  补算、回放、策略就绪检查和用户的 DuckDB 查询显式点名读取。
- 组合查询示例：

  ```sql
  -- 固定值：参数已经在列名里，直接比较
  WHERE ma__60 > 100 AND close > 200
  -- 可变值：按这一行实际用的参数筛选
  WHERE json_extract("__params", '$.ma_fast__var.window')::INT = 20 AND ma_fast__var > 100 AND close > 200
  ```

## 6. 参数的提交与取值

### 6.1 三处存储

| 存储 | 位置 | 内容 | 写入方 | 读取方 |
| --- | --- | --- | --- | --- |
| 成员配置列 `c_params` | factor-mgr 的 `factor.db`，经目录同步缓存到引擎本地（`data/engine/catalog.json`） | 固定参数；可变成员的默认参数 | 用户（加成员时） | 引擎（读本地缓存） |
| 成员运行状态列 `c_last_submitted_*` | 同一张成员表 | 可变成员每个标的最近一次提交的参数（按标的合并），以及最近一次被接受的目标期、请求 ID 和提交时间 | 关联的策略实例，经 `SubmitFactorParams` | 引擎开算一期时读一次 |
| 引擎本地参数缓存 `data/engine/param_cache.json` | 因子机 | 每个任务的「进行中记录」（正在算的那一期及其选定的参数），以及最近一次从 factor-mgr 读到的提交值 | 引擎 | 引擎（重试、重启、factor-mgr 连不上时） |
| 结果行 `__params` | Storage 因子结果数据集 | 这一行实际用的参数 | 引擎，与因子值一起写入 | 补算、回放、策略、用户查询 |

**设计演变**（v4 定稿）：
- v2 只保留「最近一次提交」一格。
- 第一轮审查指出两个问题：同一期失败重试会用上晚到的提交（问题 4），乱序到达的旧请求会把参数改回去（问题 3）。v3 为此改成「当前值 + 待生效值」两格，并加了任务级的 `c_started_through`。
- 第二轮审查又发现两格的状态转移在离线、空槽、整份替换等情况下都有漏洞。
- v4 回到一格，改由引擎在本地记下「每一期第一次开算时选定的参数」来保证重试不换参数，`c_started_through` 和两格一并删除。

### 6.2 提交：`SubmitFactorParams(task_id, member_key, target_period, request_id, 各标的参数)`

factor-mgr 在一个 SQLite 事务里依次处理：

1. **校验**：只接受这个任务的关联实例的提交；成员必须是可变成员；参数名必须是定义声明过的，且在范围内；标的必须在源数据集当前的标的里。
2. **单调与幂等**：
   - `target_period < c_last_submitted_period`：说明是乱序到达的旧请求，拒绝。
   - 目标期相等时：`request_id` 与 `c_last_request_id` 相同，按幂等直接成功；不同则拒绝。
3. **按标的合并**：本次提交带了的标的，覆盖它在 `c_last_submitted_params` 里的值；没带的标的保留原值。一个标的一旦提交过，就不会因为某一次没带它而退回默认参数。
4. **写入**：更新 `c_last_submitted_params`、`c_last_submitted_period`、`c_last_request_id`、`c_last_submitted_at`。

### 6.3 取值：引擎开算第 t 期

1. **查进行中记录**：如果本地缓存里这个任务有第 t 期的进行中记录，说明这一期已经开算过、还没写出成功，比如失败重试或引擎重启。此时直接使用记录里的参数，不再去 factor-mgr 取。
2. **否则读提交值**：调用 `GetFactorParams(task_id)`，读这个任务各可变成员的 `c_last_submitted_*`；任务没有可变成员时不调用。
   factor-mgr 连不上时，改用本地缓存里最近一次读到的提交值。
3. **逐个成员、逐个标的取值**：

   ```text
   固定成员 → c_params
   可变成员 → 这个标的在 c_last_submitted_params 里 ？ 提交值 : c_params（默认参数）
   ```

   固定成员和可变成员走同一个取值函数，只是固定成员没有提交。
4. **写进行中记录**：把第 t 期选定的参数写进 `param_cache.json`，落盘后再开始计算。
   - 这一期要等**周期完成标记写成功**之后，才清掉这份记录，并把读到的提交值留作「最近一次读到的值」。只写完结果行还不够：如果结果行成功、标记失败，重试必须仍用同一份参数（第三轮审查问题 2）。
   - 引擎重启后发现某一期有进行中记录，但这一期的周期标记已经存在，说明这一期其实已经完成，只补做清除。

每个任务的 lane 按期次串行，所以一个任务同时最多只有一期在进行中，记录很小。

**为什么一格就够、不会用到「未来」的参数。** 策略要提交第 t+1 期的参数，前提是第 t 期的因子已经写出。所以引擎读参数准备算第 t 期时，库里任何一次被接受的提交，目标期都不会超过 t。
如果读到的 `c_last_submitted_period > t`，说明有地方出了错：引擎改用本地缓存里最近一次读到的值，并告警。

### 6.4 时间线（5m，第 t 期 = 16:35~16:40）

```text
16:40:00  第 t 期 K线收盘
16:40:01  引擎开算第 t 期：没有进行中记录 → GetFactorParams → 取值 → 写进行中记录 → 计算 → 写结果行 t（因子值 + __params）
          → 写周期完成标记 → 清掉记录
16:40:08  策略算完第 t 期 → SubmitFactorParams(任务, ma_fast__var, 目标期 t+1, request_id = 结果 ID)
          → factor-mgr 按标的合并进 c_last_submitted_params
16:45:01  引擎开算第 t+1 期：读到目标期 t+1 的提交值，使用新参数
```

### 6.5 边界

- **同一期重试、引擎重启**：都用进行中记录里的参数，与第一次开算时相同，结果逐位相同。
  如果记录文件被人为删掉，重试时会重新读提交值，可能用上较新的值；这种情况罕见，实际用了什么都会记在 `__params` 里。
- **晚到**：第 t+1 期已经开算后，「目标期 t+1」的提交才到。第 t+1 期用的是进行中记录里的旧值，新值从 t+2 起生效，`__params` 会如实记录。
- **积压后追赶**：引擎按期次依次计算，算完一期就接着算下一期，**不等策略的提交**（第三轮审查问题 1）。
  - 策略的求值和投递是异步的，所以追赶期间第 t+1 期常常会先读到旧值，策略对 t+1 的提交就按「晚到」处理，从下一个还没开算的期次起生效。
  - 所以追赶期间**不保证**每一期都用上策略针对这一期算出的参数，只保证：不会读到超前的提交（策略要等因子写出才会提交），参数不会倒退，每期实际用的参数都如实记在 `__params` 里。
  - 不让因子层等策略，和 D3「策略停止不影响因子层」的思路一致；追赶本来就是异常情况，按当时能拿到的最新参数计算即可。
- **策略停止**：不再有新提交，`c_last_submitted_params` 一直保留，也就是一直沿用最后一次的参数。
- **关联之前，或某个标的从未提交过**：用默认参数。
- **factor-mgr 暂时连不上**：
  - 引擎用本地缓存里最近一次读到的提交值继续算，不阻塞计算；实际用的参数照样写进 `__params`，事后不需要补报。引擎重启后也能接着用这份缓存（补充项 S6）。
  - 这期间策略如果还能提交，多次提交在 factor-mgr 里按标的合并。恢复后，引擎下一期读到的是**最新的合并结果**，中间被覆盖的值不再追补。
  - 这个缓存文件不是事实来源，删了只会让离线期间退回默认参数。
- **提交滞后告警**：关联实例在运行，可变成员的 `c_last_submitted_period` 落后引擎当前期次超过 N 期时告警。N 用全局配置 `factor.params.stale_alert_periods`，默认 10（补充项 S7）。

## 7. 计算

### 7.1 分发

- 一个周期事件到达后，引擎找出这个源数据集上所有启用的任务，**同时**交给各自的 lane。
  - 现在 `eventconsumer/handler.go` 是逐个调用 `lanes.Do`、等它返回才处理下一个任务，要改为并发调用，等所有任务都返回后再决定这条事件是确认（ACK）还是重投。
  - 每个任务的 lane 仍按期次串行。
- **各任务只算自己的成员，不做跨任务的公共计算。** 两个任务里有相同成员时，就各算一遍，暂不考虑重复计算。
  v2、v3 设计过的「当期节点缓存」在 v4 删掉：它只省 CPU，不缩短链路耗时，但带来了复用条件和并发等待两方面的风险（第一轮审查问题 6、7，第二轮问题 6、7）。
- 任务内部的公共子表达式消除保持现状。
- 引擎本地序列本来就按源数据集只存一份（`data/seriesstore`），不变。
- **失败隔离**：某个任务的成员算失败，只影响这个任务的这一期；其他任务照常写出。
  某个任务因为基础设施错误需要重投事件时，已经写出的任务靠「同一触发事件的周期标记已存在」跳过，这是现有机制。

### 7.2 生命周期

- 任务启用后，由引擎自动执行 init、start、confirm，沿用现有的自动推进逻辑。
- 预热：本地序列的长度要覆盖成员里最长的「回看 + 预热」。可变成员按参数范围的上限计算。
  - 长度不够时，任务停在预热阶段，页面提示「本地序列不足，需要导入历史」。不补算。
  - 长度够了，就转为运行。
- 自动确认的证据要和当期成员的内容绑定。证据由成员键、定义哈希、成员类型和固定参数共同决定；成员一变化，证据就失效。

### 7.3 周期标记

- 周期完成标记按成员记录 `member_key`、`factor_id`、`definition_hash`、`member_kind`。
- 删除 `params_source`、`params_digest`：实际用的参数已经写在 `__params` 里。
- 「成员契约哈希」= `definition_hash` + `member_kind` + 固定参数（可变成员不含参数）。策略启用时把它固化进绑定，就绪检查按它比较。
  定义哈希本身保持原有语义（只看定义），缺口账本与修复继续用定义哈希。

### 7.4 补算、回放与试算

- **补算**：按期读取已有行 `__params` 里这个成员的参数来重算，写回时按 5.5 合并 `__params`。补算作业仍然按单个任务执行，不参与缓存。
  - **一致性只对原行存在、且 `__params` 里有这个成员的期次作保证**：重算结果与原值逐位相同（第一轮审查问题 9）。
  - 原行不存在、或者 `__params` 里没有这个成员时，固定成员用 `c_params`，可变成员用默认参数，算出来的是**新补的值**，不能保证和当时的实时结果一致，因为删除参数表以后，那一期提交过的参数已经无从还原。
    补算作业的结果里要列出这些按默认参数新补的期次。
- **回放**：调参策略要按期交替执行：先算因子，再跑策略，再写回参数，然后进入下一期。参数只存在回放会话的内存里，不写成员行。
  第 t 期用的就是回放第 t-1 期算出的参数。闭环回放的结果是一次新的模拟，不等同于已有的实时历史。
  `packages/seriesreplay/runner.go:68-85` 现在限制调参回放把结果写回结果数据集，这个限制保留，不在本设计里放开。
- **试算 / 诊断运行**：固定成员用 `c_params`，可变成员用默认参数，或者用请求里显式给出的参数。

## 8. 策略侧

### 8.1 关联

- 策略实例的 `c_view_id` 改为 `c_factor_task_id`；读取的 View 就是这个任务结果数据集的默认 View `view_factor_<后缀>`，由命名规则推导。
- **独占的唯一事实来源在因子侧**：`t_factor_tasks.c_bound_instance_id` 为可空的唯一列。
  - 策略第一次启用实例时调用 `BindFactorTask(task_id, instance_id)` 写入。这个调用是幂等的：同一个实例重复调用直接成功，换一个实例则拒绝。
  - 写入后不能改，也不能清空。
- **策略侧也禁止改绑**（第一轮审查问题 10）。现在 `UpdateStrategyInstance` 允许停用后修改 View（`strategy/internal/rpc/instances.go:123-158`）。
  改造后，更新接口和数据库更新路径都不允许修改 `c_factor_task_id`；它只在创建实例时写入一次。实例停用后再启用，只校验原来的关联。
- 策略启用检查：任务已关联本实例、任务在运行、DSL 引用的列都存在，以及可变成员和 `factor_params` 一一对应。

### 8.2 DSL

关联哪个因子任务在创建实例时选，不写在 DSL 里（S2）：DSL 描述策略逻辑，可以被多个实例复用。

```yaml
factor_params:                          # 只能针对任务里的可变成员，键是成员键
  ma_fast__var:
    window: {default: "5", per_subject: "5 + rank(vol) * 10"}
rules:
  - filter: "ema__20_50000 > 0 && close > ema__20_50000 && rsi < 70 && close > boll__mid && ma_fast__var > close"
```

- 删除 `factors` 段：策略不再创建因子，也没有局部别名。规则直接写列名。
- 规则需要读可变成员这一期实际用的参数时，写成 `params("ma_fast__var", "window")`。这个函数从 `__params` 取值，代替原来的 `<别名>__<参数名>`。
- DSL 校验和列解析用公共包 `factorname`：引用的列名必须合法，并且能在关联任务的列元数据里找到。列解析只把 `column_kind=output` 的列当作因子值。
- **`params()` 不能只改 DSL**（第一轮审查问题 8）。现在策略读取数据时只把数值列放进 `map[string]float64`（`input/client.go:377-415`），
  实时查询的列集合来自 DSL 里的数值列（`input/frame.go:165-173,217-226`），回放也一样（`replay/runner.go:267-271`），而 `engine/frame.go:11-16` 里没有放 JSON 的地方。改造包括：
  - DSL 用到 `params()` 时，实时求值和回放都显式读取 `__params` 列。
  - 逐行保留 `json_value`，解析成「成员键 → 参数名 → 值」后放进帧里。
  - 表达式求值时，`params(成员键, 参数名)` 从帧里取值。
  - 校验：成员键必须是关联任务里的成员，参数名必须是定义声明过的。某一行缺这个值时，返回 NaN，和缺数的处理一致。
- `factor_params` 里的 `default` 是策略**提交**的值；成员行的默认参数是策略关联之前、或从未提交时**引擎用**的值。两者独立。

### 8.3 参数投递

- `t_strategy_results` 增加两列：`c_next_params_json`（这一期算出的下一期参数，没有可变成员时为空）和 `c_params_delivered_at`。参数和结果在同一个事务里写入。
- 投递循环只投「这个实例**当前会话**里最新一条、还没送达」的结果；更早的未送达记录直接跳过，因为被覆盖了也没有意义。
  重试采用退避，送达后写入 `c_params_delivered_at`。
- 每次提交带上 `request_id`，取结果 ID；目标期取这条结果对应的下一期。由于 factor-mgr 只接受目标期不减的提交（6.2），即使重试的旧请求晚于新请求到达，也会被拒绝，参数不会倒退。
  被拒绝的旧请求标为已处理，不再重试。
- 实例停用时，当前会话里还没送达的结果不再投递；重新启用会开一个新会话，从新会话的第一条结果开始提交。
- 删除 `t_strategy_param_submissions`，以及 pending、accepted、too_late 等状态。

### 8.4 其他

- 外显设置 `t_strategy_display_settings` 保留，作用对象由「私有因子集的成员」改为「关联任务的成员」，按成员键匹配。
  结果页现在只有在 `owner_instance_id` 存在时才读外显设置（`web/src/views/factor/results/index.vue:220-233`），要改为按任务的 `bound_instance_id` 读取。
- 删除实例相关：删除 `DeleteInstance` 接口、`c_deleted_at` 列和控制台的删除按钮，实例只有启用和停止两种操作（补充项 S4）。

    c_task_id TEXT NOT NULL PRIMARY KEY,
    c_space_id TEXT NOT NULL,

    UNIQUE (c_bound_instance_id),

);

CREATE INDEX IF NOT EXISTS idx_t_factor_tasks_source ON t_factor_tasks (c_space_id, c_source_dataset_id, c_freq, c_status);

CREATE TABLE IF NOT EXISTS t_factor_task_members (
    c_task_id TEXT NOT NULL,
    c_member_key TEXT NOT NULL,
    c_factor_id TEXT NOT NULL,
    c_kind TEXT NOT NULL,
    c_status TEXT NOT NULL DEFAULT 'disabled',
    -- 固定参数，或可变成员的默认参数：加成员时的完整参数（规范 JSON），之后不变
    c_params TEXT NOT NULL,
    -- 以下是可变成员的运行状态（见 6.2），不属于配置：目录同步、目录指纹、成员变化检测都不看它们，也不更新 c_mtime
    -- 各标的最近一次提交的参数（按标的合并的规范 JSON），以及最近一次被接受的目标期（Unix 秒）、请求 ID、提交时间
    c_last_submitted_params TEXT NOT NULL DEFAULT '{}',

    c_last_submitted_at DATETIME,
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (c_task_id, c_member_key),
    CHECK (c_kind IN ('fixed', 'var')),
    CHECK (c_kind = 'var' OR (c_last_submitted_period = 0 AND c_last_submitted_params = '{}' AND c_last_request_id = '' AND c_last_submitted_at IS NULL)),
    CHECK (c_status IN ('enabled', 'disabled')),
    FOREIGN KEY (c_task_id) REFERENCES t_factor_tasks (c_task_id),
    FOREIGN KEY (c_factor_id) REFERENCES t_factor_defs (c_factor_id) ON DELETE RESTRICT
);

CREATE INDEX IF NOT EXISTS idx_t_factor_task_members_factor ON t_factor_task_members (c_factor_id);
CREATE UNIQUE INDEX IF NOT EXISTS ux_t_factor_task_members_var
ON t_factor_task_members (c_task_id, c_factor_id)
WHERE c_kind = 'var';

### 9.2 ID

- 任务 ID：`ftask_<后缀>`。结果数据集为 `dataset_factor_<后缀>`，默认 View 为 `view_factor_<后缀>`。
- 后缀不能再由「源数据集 + 频率」推导，因为一个源数据集可以有多个任务。
  - 控制台创建时，生成 8 位小写字母加数字的随机后缀。
  - `moox.toml` 里由用户写定后缀，这样 `setup factors` 可以重复执行。
  - 后缀只允许小写字母、数字和下划线，最长 35 个字符，保证 `dataset_factor_` 加后缀不超过 Storage 的 50 个字符上限。
- 任务另有一个展示名 `c_name`，由用户填写，**直接**用作 Storage 结果数据集的展示名，不截取（第一轮审查问题 14）。
  所以 `c_name` 要满足 Storage 对数据集名称的要求：含汉字、不超过 10 个字（`storage/internal/service/catalog/validate.go:74-87`），并在空间内唯一（`storage/schema/metadata.sql:76`）。
  创建任务时先按这些规则校验；`UNIQUE (c_space_id, c_name)` 在因子侧再兜底一次。

## 15. 验收

- **链路耗时**：对一个单策略、5 个因子、501 个标的的 5m 任务，从 K 线收盘到策略提交完成，目标约 4.5~5 s，要求低于 6 s。逐段列出耗时，与第 1 节对照。
- **并行分发**：同一个源数据集的两个任务同时开算，不再先后排队；其中一个任务故意失败时，另一个照常写出。
- **可变参数**：
  - 第 t 期提交的参数在 t+1 期生效。
  - 人为延迟投递时，t+1 期沿用旧值，t+2 期生效。
  - 同一期失败重试、写出前引擎重启：用的参数都与第一次开算时相同，即使重试前有新提交到达。
  - 人为让旧请求晚于新请求到达：旧请求被拒绝，参数不倒退；同一个 `request_id` 重复提交按幂等成功。
  - 某次提交只带了部分标的：没带的标的继续用它们上一次提交的值，不退回默认参数。
  - 积压追赶：引擎不等策略，晚到的提交从下一个还没开算的期次起生效；参数不倒退，`__params` 与每期实际用的参数一致。
  - factor-mgr 不可达期间，按本地缓存计算；恢复后从下一期起使用最新的合并结果。
  - 结果行写成功、周期标记写失败后重试：用的仍是第一次开算时的参数；重启时发现标记已存在，只清除进行中记录。
  - 策略停止后一直沿用最后一次提交的值；重新启用后，从新会话开始提交。
  - `__params` 每一期都如实记录实际用的参数。
- **补算**：
  - 对原行存在且 `__params` 完整的一段历史重算，结果与原值逐位相同。把 `__params` 里的参数改成默认值后重算，结果应当不同，以此证明补算确实读了 `__params`。
  - 只补算部分成员时，其他成员在 `__params` 里的记录不变。
  - 原行不存在的期次按默认参数补出，并列在补算作业的结果里。
- **Storage**：结果数据集能注册 `__params` 列，默认 View 包含这一列并能读回 `json_value`；`params` 类型的列不会被当作因子输出。
- **策略**：用到 `params()` 的规则在实时求值和回放里都能取到值；更新实例时不能修改关联的任务。
- **独占**：已关联的任务再被另一个实例关联时被拒绝；停止的实例重新启用后无缝接续。
- **约束**：被引用的定义不能增删参数或输出；同一任务里同一因子不能有两个可变成员；成员键或列名冲突时拒绝加成员。
- **命名**：
  - Go 与 TS 读同一份 `vectors.json`，每一条结果都一致；非规范的参数段（如 `01`、`1p0`）被拒绝。
  - 线上所有因子列都能被公共包解析出列名里含有的信息（因子 ID、固定或可变、参数段、输出名），并与列元数据一致。完整参数值以列元数据的 `factor_params` 为准。
  - 因子库里不再有大写的因子 ID，也不再有带因子前缀的输出名。
- **Monitor**：同一个源数据集有两个任务时，到达链按任务分别展示，各自对应正确的结果数据集。
- **schema**：所有 schema 文件都能逐个载入空 SQLite 数据库，`git diff --check` 通过。
