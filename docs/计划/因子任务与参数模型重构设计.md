# 因子任务与参数模型重构设计

状态：设计稿 v1（2026-10-25，决策已与用户逐条讨论确认，尚未编码，待 Codex 审查）。项目尚未上线，不考虑兼容、迁移与成本，
一切以设计合理为准；实现后以[因子](../模块/因子.md)、[策略](../模块/策略.md)为准。本设计取代
[因子成员固定参数执行计划](因子成员固定参数执行计划.md)中的别名与参数列规则，以及[因子动态调参执行计划](因子动态调参执行计划.md)中的
私有因子集、参数快照与冻结记录。

## 1. 背景

2026-10-25 在生产环境给策略 `chain_ema20w_5m` 测了全链路耗时：一根 5m K线从收盘到策略提交完成共 **8.0 s**。

| 区间（相对收盘） | 环节 | 耗时 |
| --- | --- | --- |
| 0 → 0.95 s | 采集、入库、采集完成事件送达引擎 | 0.95 s |
| 0.95 → 4.34 s | 共享任务「采集结果 · 5m」计算（13 个默认因子加 `Ema_20_50000`，501 个标的） | 3.39 s |
| 4.34 → 4.50 s | 共享任务结束到私有因子集开算 | 0.16 s |
| 4.50 → 7.10 s | 策略私有因子集计算（5 个因子，含 5 万根预热） | 2.60 s |
| 7.10 → 7.64 s | 私有结果写入，View 发出「结果就绪」 | 0.54 s |
| 7.64 → 8.00 s | 策略读取、求值、提交 | 0.36 s |

暴露出两类问题。

**性能**

- **重复计算。** 策略声明的 5 个因子，共享任务早已算过；私有因子集又算一遍，多花约 3.3 s。
- **串行分发。** 同一源数据集上的多个集合本来互不依赖，但 `eventconsumer/handler.go` 逐个调用 `lanes.Do`，
  而 `Do` 会等这个集合算完才返回。所以私有集合要等共享任务算完才能开始。

**模型复杂**

- 「共享任务 / 私有因子集」两种任务。
- 成员别名，以及别名与列名的推导规则。
- 只有私有集合才写的参数列 `<别名>__<参数名>`。
- 共享成员的固定参数校验。
- 参数侧：四张参数表（请求、快照、冻结区间、冻结期次）、离线冻结与补报，以及策略侧的投递 outbox。

上一轮代码审查里的阻断和高优先级问题，多数出在这些分支的交界处。

## 2. 原则

1. 每一层都是同一个形状：**输入数据集 → 任务 → 输出数据集**。
2. 一个概念只在一个地方定义：配置在成员表，运行时提交在成员表的运行状态列，历史事实在结果行。
3. 能由规则推导的不存储，比如列名；能由因果顺序保证的不加锁、不登记，比如参数生效的期次。
4. 合并计算只是底层优化，逻辑上各任务完全独立。

## 3. 分层模型

```text
采集数据集 ─┬─ 因子任务 A ──► 因子结果数据集 A ──(1:1)── 策略实例 1 ──► 策略结果
           └─ 因子任务 B ──► 因子结果数据集 B ──(1:1)── 策略实例 2 ──► 策略结果
   ▲
引擎本地序列（与源数据集一一对应，是它的超集：保留更长的历史，供预热）
```

- **采集数据集**是原始数据的源头，一类数据放在一个数据集里。
- **因子任务**关联一个源数据集和一个频率，产出一个因子结果数据集。一个源数据集可以有多个因子任务。
- **策略实例**关联且只能关联一个因子任务，独占且永久，基于它的结果数据集求值。策略结果仍存在策略模块的 SQLite 里，这次不搬进 Storage。
- 「数据集」（dataset）的概念与 ID 规则保持不变；「任务」只指因子计算任务；「策略实例」不改名。

## 4. 决策

| # | 决策 |
| --- | --- |
| D1 | 去掉「共享任务 / 私有因子集」的区分，因子任务只有一种，由用户创建（控制台或 `moox.toml`），可以先于策略运行以积累历史 |
| D2 | 一个因子结果只能被一个策略实例关联，独占、永久。策略实例只能启用或停止，不能删除，也就没有「解除关联」 |
| D3 | 策略停止只影响策略层，因子任务照常计算，由用户手动停止 |
| D4 | 成员分**固定值**与**可变值**。固定值的参数在加成员时写定；可变值由关联的策略逐期提交 |
| D5 | 不再使用成员别名。成员键与列名由「因子 ID + 参数 + 是否可变」推导；同一因子在一个任务里最多一个可变成员，需要多个可变值就注册多个因子（例如 `ma_fast`、`ma_slow`） |
| D6 | 不再使用参数列。每个结果数据集有一个隐藏的系统列 `__params`（JSON），每行记录这一行所有成员实际用的参数，固定参数也冗余记录。这是参数的唯一历史记录 |
| D7 | 可变成员的默认参数写在成员行里。策略每期把下一期的参数写进成员行的运行状态列，只保留最近一次提交；引擎开算时，提交的目标期不晚于当期就用提交值，否则用默认值 |
| D8 | 删除四张参数表、离线冻结与补报、`FreezeFactorParams` / `ReportOfflineFreezes` / `ListParamIntervals`；成员的 `c_carry_alert_periods` 一并删除 |
| D9 | 因子任务启用时，检查引擎本地序列是否覆盖最长的回看与预热，不补算；策略启用时只检查关联的任务在运行，且需要的列都存在 |
| D10 | 同一事件下的多个任务并行计算、各自写出；底层用当期节点缓存去重，同一个节点只算一次 |
| D11 | 改名：set 改为 task（`t_factor_tasks`、`ftask_…` 等，见第 11 节）；中文「因子集」「集合」统一为「因子任务」，「补算任务」改为「补算作业」 |
| D12 | 策略侧的 `t_strategy_param_submissions` 并入 `t_strategy_results`，只投递最新一条还没送达的参数 |

## 5. 成员与列

### 5.1 成员键与列名

| 成员 | 成员键 | 列名 | 例子 |
| --- | --- | --- | --- |
| 固定值，参数全为默认值 | `<因子ID>` | `<输出名>` | `Rsi` → `rsi`；`Boll` → `boll_mid` 等 |
| 固定值，有非默认参数 | `<因子ID>_<参数1>_<参数2>…`（按定义声明的参数顺序） | `<成员键>_<输出名>` | `Ema_20_50000` → `Ema_20_50000_ema` |
| 可变值 | `<因子ID>_var` | `<成员键>_<输出名>` | `ma_fast_var` → `ma_fast_var_ma` |

- 参数值按[因子成员固定参数执行计划](因子成员固定参数执行计划.md)第 3 节的格式化规则写进成员键：
  `FormatFloat('f', -1)`，`.` 写成 `p`，`-` 写成 `n`，成员键最长 32 个字符，列名最长 64 个字符。规则沿用，共享测试向量 `testdata/alias_vectors.json` 改名为 `member_key_vectors.json`。
- 参数都是数值，固定成员的键不会以 `_var` 结尾。但成员键或列名仍可能撞上：比如因子 `Ema_20` 的默认成员，和 `Ema` 在 `span=20` 时的成员，键都是 `Ema_20`；两个默认成员的输出名也可能相同。遇到这种冲突，加成员时一律拒绝，并提示具体冲突在哪。
- 固定成员的参数一旦写定就不能改。要换参数，就加一个新成员（键也随之不同）。

### 5.2 成员移除与重新加入

- 移除成员时，结果数据集里的列保留，不再写入，页面上也不再显示。
- 再次加入同一个成员键时，直接沿用原来的列。固定成员的键由参数唯一决定，所以同一个键必然对应同一组参数，不需要比对历史参数。
- 列属性里记录 `origin_factor_id`、`member_key`、`member_kind`（`fixed` / `var`）、固定参数和定义哈希。

### 5.3 定义的参数声明

被任务引用的因子定义，**不允许增加、删除参数，也不允许改参数的类型**。要改，就新建一个定义。
允许修改参数的范围和默认值，但已加入的固定成员保存的是完整参数，不跟着变。可变成员的默认参数在加成员时写进成员行，同样不跟着变。
这样就不会再出现上一轮审查的问题 1：共享成员的固定参数因为定义增删参数而变得不完整。

### 5.4 系统列 `__params`

- 每个因子结果数据集在创建时声明一列 `__params`：值类型为 `json`，列属性 `column_kind=system`。
- **不使用 Storage 的行属性。** 因子结果写入本来就拒绝行属性（`primarystore/factor_rows.go:64`），
  [Storage 读接口收敛设计](Storage读接口收敛设计.md)也规定 View 不保存、不返回行属性。`__params` 是一列声明过的普通字段，View 照常给它建索引，DuckDB 也能用 `json_extract` 查询。
- 内容：以成员键为键，记录这一行实际用的参数，包括固定成员。

  ```json
  {"Ema_20_50000": {"span": 20, "warmup": 50000},
   "Rsi": {"window": 14},
   "ma_fast_var": {"window": 5}}
  ```

- 规范化：键按字典序排列，数值格式与成员键的格式化规则一致，不带空白。同一期重算时，这一列必须与因子值一样逐位相同，因为实时写入的提交 ID 依赖它。
- 读取：页面、导出和普通查询默认过滤掉 `column_kind=system` 的列；补算、回放、策略就绪检查和用户的 DuckDB 查询要显式点名读取。
- 组合查询示例：

  ```sql
  -- 固定值：参数已经在列名里，直接比较
  WHERE Ma_20_ma > 100 AND close > 200
  -- 可变值：按这一行实际用的参数筛选
  WHERE json_extract("__params", '$.ma_fast_var.window')::INT = 20 AND ma_fast_var_ma > 100 AND close > 200
  ```

## 6. 参数的提交与取值

### 6.1 三处存储

| 存储 | 位置 | 内容 | 写入方 | 读取方 |
| --- | --- | --- | --- | --- |
| 成员配置列 `c_params` | factor-mgr 的 `factor.db`，经目录同步缓存到引擎本地（`data/engine/catalog.json`） | 固定参数；可变成员的默认参数 | 用户（加成员时） | 引擎（读本地缓存） |
| 成员运行状态列 `c_last_submitted_*` | 同一张成员表 | 可变成员最近一次提交的参数，按标的分开 | 关联的策略实例，经 `SubmitFactorParams` | 引擎每期开算前读一次 |
| 结果行 `__params` | Storage 因子结果数据集 | 这一行实际用的参数 | 引擎，与因子值一起写入 | 补算、回放、策略、用户查询 |

### 6.2 取值规则

引擎计算第 t 期时，对每个成员、每个标的：

```text
固定成员 → c_params
可变成员 → c_last_submitted_period ≤ t 且这个标的在 c_last_submitted_params 里 ？ 提交值 : c_params（默认参数）
```

固定成员和可变成员走同一个取值函数，只是固定成员没有提交。

### 6.3 时间线（5m，第 t 期 = 16:35~16:40）

```text
16:40:00  第 t 期 K线收盘
16:40:01  引擎开算第 t 期：读本地目录缓存（c_params），调 GetFactorParams 读这个任务可变成员的 c_last_submitted_*，
          按 6.2 取值 → 计算 → 写结果行 t（因子值 + __params）
16:40:08  策略算完第 t 期 → SubmitFactorParams(任务, ma_fast_var, 目标期 t+1, 各标的参数)
          → factor-mgr 覆盖成员行的 c_last_submitted_*
16:45:01  引擎开算第 t+1 期：目标期 t+1 ≤ t+1，使用提交值
```

### 6.4 边界

- **只保留最近一次提交就够了。** 策略要提交第 t+1 期的参数，必须先等第 t 期的因子算完，所以引擎在第 t+1 期读到的，不可能是给更晚期次的值。
- **晚到。** 引擎开算第 t+1 期时提交还没到，就用上一次提交的值，也就是沿用；晚到的值从 t+2 起生效。
  不登记「已冻结到哪一期」，也不拒绝晚到的提交；实际用了什么，都记在 `__params` 里。
- **策略停止。** 运行状态列不再更新，一直沿用最后一次提交的值。
- **关联之前，或某个标的从未提交过。** 用默认参数。
- **factor-mgr 暂时连不上。** 引擎用内存里最近一次读到的提交值继续算，不阻塞计算；实际用的参数照样写进 `__params`，事后不需要补报。
  引擎重启后，如果 factor-mgr 也连不上，就用默认参数，并告警。
- **提交校验。** 只接受这个任务的关联实例的提交；成员必须是可变成员；参数名必须是定义声明过的，且在范围内；标的必须在源数据集当前的标的里。
- **提交滞后告警。** 关联实例在运行，而可变成员的 `c_last_submitted_period` 落后当期超过 N 期时告警。N 用全局配置 `factor.params.stale_alert_periods`，默认 10。

## 7. 计算

### 7.1 分发与去重

- 一个周期事件到达后，引擎找出这个源数据集上所有启用的任务，**同时**交给各自的 lane。每个任务的 lane 仍按期次串行。
- **当期节点缓存**：键为「源数据集 + 频率 + 期次 + 节点结构摘要 + 参数向量摘要」，截面节点的键还要加上标的范围摘要。
  - 节点已经算完，直接取结果。
  - 节点正在被别的任务计算，就等它算完再取结果，不重复计算。
  - 这一期所有任务都结束后，清空缓存。
- 每个任务只等自己本来就要算的节点，所以不会比不合并时更慢。可变成员的参数向量各不相同，不会被错误合并。
- **失败隔离**：某个任务的成员算失败，只影响这个任务的这一期。共享节点算失败时，用到它的所有任务都按失败处理，各自重试。
- 引擎本地序列本来就按源数据集只存一份（`data/seriesstore`），不变。

### 7.2 生命周期

- 任务启用后，由引擎自动执行 init、start、confirm，沿用现有的自动推进逻辑。
- 预热：本地序列的长度要覆盖成员里最长的「回看 + 预热」。可变成员按参数范围的上限计算。
  - 长度不够时，任务停在预热阶段，页面提示「本地序列不足，需要导入历史」。不补算。
  - 长度够了，就转为运行。
- 自动确认的证据要和当期成员的内容绑定。证据由成员键、定义哈希、成员类型和固定参数共同决定；成员一变化，证据就失效。

### 7.3 周期标记

- 周期完成标记按成员记录 `member_key`、`factor_id`、`definition_hash`、`member_kind`。
- 删除 `params_source`、`params_digest`：实际用的参数已经写在 `__params` 里。
- 「成员契约哈希」= `definition_hash` + `member_kind` + 固定参数（可变成员不含参数）。策略启用时把它固化进绑定，就绪检查按它比较。
  定义哈希本身保持原有语义（只看定义），缺口账本与修复继续用定义哈希。

### 7.4 补算、回放与试算

- **补算**：按期读取已有行 `__params` 里这个成员的参数来重算。行不存在或没有这个成员时：固定成员用 `c_params`，可变成员用默认参数。
  补算作业仍然按单个任务执行，不参与合并。
- **回放**：调参策略要按期交替执行：先算因子，再跑策略，再写回参数，然后进入下一期。参数只存在回放会话的内存里，不写成员行。
  第 t 期用的就是回放第 t-1 期算出的参数。
- **试算 / 诊断运行**：固定成员用 `c_params`，可变成员用默认参数，或者用请求里显式给出的参数。

## 8. 策略侧

### 8.1 关联

- 策略实例的 `c_view_id` 改为 `c_factor_task_id`；读取的 View 就是这个任务结果数据集的默认 View `view_factor_<后缀>`，由命名规则推导。
- **独占的唯一事实来源在因子侧**：`t_factor_tasks.c_bound_instance_id` 为可空的唯一列。
  - 策略第一次启用实例时调用 `BindFactorTask(task_id, instance_id)` 写入。这个调用是幂等的：同一个实例重复调用直接成功，换一个实例则拒绝。
  - 写入后不能改，也不能清空。
- 策略启用检查：任务已关联本实例、任务在运行、DSL 引用的列都存在，以及可变成员和 `factor_params` 一一对应。

### 8.2 DSL

```yaml
factor_task: ftask_swap5m_chain        # 关联的因子任务；也可以在创建实例时指定，这一点见第 13 节
factor_params:                          # 只能针对任务里的可变成员，键是成员键
  ma_fast_var:
    window: {default: "5", per_subject: "5 + rank(vol) * 10"}
rules:
  - filter: "Ema_20_50000_ema > 0 && close > Ema_20_50000_ema && rsi < 70 && ma_fast_var_ma > close"
```

- 删除 `factors` 段：策略不再创建因子，也没有局部别名。规则直接写列名。
- 规则需要读可变成员这一期实际用的参数时，写成 `params("ma_fast_var", "window")`。这个函数从 `__params` 取值，代替原来的 `<别名>__<参数名>`。
- `factor_params` 里的 `default` 是策略**提交**的值；成员行的默认参数是策略关联之前、或从未提交时**引擎用**的值。两者独立。

### 8.3 参数投递

- `t_strategy_results` 增加两列：`c_next_params_json`（这一期算出的下一期参数，没有可变成员时为空）和 `c_params_delivered_at`。参数和结果在同一个事务里写入。
- 投递循环只投「这个实例最新一条、还没送达」的结果；更早的未送达记录直接跳过，因为被覆盖了也没有意义。重试采用退避，送达后写入 `c_params_delivered_at`。
- 删除 `t_strategy_param_submissions`，以及 pending、accepted、too_late 等状态。

### 8.4 其他

- 外显设置 `t_strategy_display_settings` 保留，作用对象由「私有因子集的成员」改为「关联任务的成员」，按成员键匹配。
- 删除实例相关：删除 `DeleteInstance` 接口、`c_deleted_at` 列和控制台的删除按钮，实例只有启用和停止两种操作。

## 9. 数据模型

### 9.1 `factor.db`（从 10 张表减到 6 张）

| 表 | 变化 |
| --- | --- |
| `t_factor_defs` | 不变 |
| `t_factor_categories` | 不变 |
| `t_factor_tasks` | 由 `t_factor_sets` 改名；删除 `c_owner_instance_id`，增加 `c_bound_instance_id`；状态去掉 `deleting` |
| `t_factor_task_members` | 由 `t_factor_set_members` 改名并重写，见下 |
| `t_factor_recalc_jobs` | `c_set_id` 改为 `c_task_id`，中文改叫「补算作业」 |
| `t_factor_engine_heartbeat` | 不变 |
| 删除 | `t_factor_param_requests`、`t_factor_param_snapshots`、`t_factor_param_freezes`、`t_factor_param_frozen_periods` |

```sql
CREATE TABLE IF NOT EXISTS t_factor_tasks (
    c_task_id TEXT NOT NULL PRIMARY KEY,
    c_space_id TEXT NOT NULL,
    c_name TEXT NOT NULL,
    c_source_dataset_id TEXT NOT NULL,
    c_freq TEXT NOT NULL,
    c_result_dataset_id TEXT NOT NULL,
    -- 关联的策略实例：独占、永久，写入后不能修改或清空
    c_bound_instance_id TEXT,
    c_status TEXT NOT NULL DEFAULT 'pending',
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (c_status IN ('pending', 'enabled', 'disabled')),
    UNIQUE (c_result_dataset_id),
    UNIQUE (c_bound_instance_id)
);

CREATE INDEX IF NOT EXISTS idx_t_factor_tasks_source ON t_factor_tasks (c_space_id, c_source_dataset_id, c_freq, c_status);

CREATE TABLE IF NOT EXISTS t_factor_task_members (
    c_task_id TEXT NOT NULL,
    c_member_key TEXT NOT NULL,
    c_factor_id TEXT NOT NULL,
    c_kind TEXT NOT NULL,
    c_status TEXT NOT NULL DEFAULT 'disabled',
    -- 固定参数，或可变成员的默认参数：加成员时的完整参数（规范 JSON），之后不变
    c_params TEXT NOT NULL,
    -- 以下三列是可变成员的运行状态，不属于配置：目录同步、目录指纹、成员变化检测都不看它们，提交时也不更新 c_mtime
    c_last_submitted_period INTEGER NOT NULL DEFAULT 0,
    c_last_submitted_params TEXT NOT NULL DEFAULT '{}',
    c_last_submitted_at DATETIME,
    c_ctime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    c_mtime DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (c_task_id, c_member_key),
    CHECK (c_kind IN ('fixed', 'var')),
    CHECK (c_kind = 'var' OR (c_last_submitted_period = 0 AND c_last_submitted_params = '{}' AND c_last_submitted_at IS NULL)),
    CHECK (c_status IN ('enabled', 'disabled')),
    FOREIGN KEY (c_task_id) REFERENCES t_factor_tasks (c_task_id),
    FOREIGN KEY (c_factor_id) REFERENCES t_factor_defs (c_factor_id) ON DELETE RESTRICT
);

CREATE INDEX IF NOT EXISTS idx_t_factor_task_members_factor ON t_factor_task_members (c_factor_id);
CREATE UNIQUE INDEX IF NOT EXISTS ux_t_factor_task_members_var
ON t_factor_task_members (c_task_id, c_factor_id)
WHERE c_kind = 'var';
```

`mtime` 触发器沿用现有写法。提交参数的 UPDATE 不改 `c_mtime`，所以触发器的条件 `NEW.c_mtime = OLD.c_mtime` 必须排除只改运行状态列的更新，
做法是按列限定触发：`AFTER UPDATE OF c_factor_id, c_kind, c_status, c_params`。

### 9.2 ID

- 任务 ID：`ftask_<后缀>`。结果数据集为 `dataset_factor_<后缀>`，默认 View 为 `view_factor_<后缀>`。
- 后缀不能再由「源数据集 + 频率」推导，因为一个源数据集可以有多个任务。
  - 控制台创建时，生成 8 位小写字母加数字的随机后缀。
  - `moox.toml` 里由用户写定后缀，这样 `setup factors` 可以重复执行。
  - 后缀只允许小写字母、数字和下划线，最长 35 个字符，保证 `dataset_factor_` 加后缀不超过 Storage 的 50 个字符上限。
- 任务另有一个展示名 `c_name`，Storage 结果数据集的展示名取它的前 10 个字符；空间内重名时拒绝创建。

### 9.3 `strategy.db`

- `t_strategy_instances`：`c_view_id` 改为 `c_factor_task_id`，删除 `c_deleted_at`，并把 `idx_t_strategy_instances_view` 改成按任务建索引。
- `t_strategy_results`：增加 `c_next_params_json`、`c_params_delivered_at`。
- 删除 `t_strategy_param_submissions`。

## 12. 配置、CLI 与控制台

**`moox.toml`**

```toml

source_dataset_id = "dataset_dbev64ivka4d2219dbag"
```

- **`setup factors`**：按 `id` 查找或创建任务，按推导出的成员键查找或加入成员，并逐项报告「已存在 / 新建 / 冲突」。
  配置里已经去掉的成员只报告，不自动移除。
- **控制台「因子任务」页**：
  - 新建任务：选源数据集和频率，填展示名。
  - 加成员：选因子，再选固定（填参数，预览成员键和列名）或可变。
  - 详情：显示关联的策略实例（只读）；可变成员显示最近一次提交的期次和时间。

## 13. 需要确认

1. 不需要因子的策略，比如只用 K 线的策略，还能不能直接绑定 K 线 View？建议**不能**：一律关联因子任务（任务至少有一个成员），保持「策略只读因子结果」的单一模式。
2. `factor_task` 写在 DSL 里，还是创建实例时选？建议**创建实例时选**。DSL 描述策略逻辑，可以被多个实例复用；任务是实例级的绑定。启用时校验 DSL 引用的列都存在。
3. 结果数据集里是否需要冗余源数据列，比如 `close`？现在策略和组合查询读的是结果数据集的默认 View。编码前要核对这个 View 是否已经把源数据列合进来；如果没有，要在 View 定义里补上。

5. 按第 15 节验收。

## 15. 验收

- **链路耗时**：对一个单策略、5 个因子、501 个标的的 5m 任务，从 K 线收盘到策略提交完成，目标约 4.5~5 s，要求低于 6 s。逐段列出耗时，与第 1 节对照。
- **合并计算**：两个任务共有一个成员时，引擎日志能看到节点缓存命中；两个任务的这一列逐位相同；两个任务的开算时间相同，不再先后排队。
- **可变参数**：
  - 第 t 期提交的参数在 t+1 期生效。
  - 人为延迟投递时，t+1 期沿用旧值，t+2 期生效。
  - 策略停止后一直沿用最后一次提交的值。
  - `__params` 每一期都如实记录实际用的参数。
- **补算**：按 `__params` 重算历史一段，结果与原值逐位相同；把 `__params` 里的参数改成默认值后重算，结果应当不同（反证补算确实读了 `__params`）。
- **独占**：已关联的任务再被另一个实例关联时被拒绝；停止的实例重新启用后无缝接续。
- **约束**：被引用的定义不能增删参数；同一任务里同一因子不能有两个可变成员；成员键或列名冲突时拒绝加成员。
- **schema**：所有 schema 文件都能逐个载入空 SQLite 数据库，`git diff --check` 通过。
