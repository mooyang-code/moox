# 模块与系统的暂停/恢复、重置设计

2026-10-21 · v4（阶段 1～4 已实现并部分上线，完成情况对照见第 15 节；已吸收第一轮 Codex 审查的 12 条意见，见第 13 节；已确认：恢复先追赶补采、全部就绪后再放行；状态编排独立成 `modules/sysctl`，`moox-cli` 只作入口；第 11 节取舍按推荐方案确认） · 基于 `main`（611f4b55）

## 0. 要解决的问题与结论

用户需求：每个模块和整个系统都要有 **暂停/恢复**、**重置**（删除全部配置和 DB 表数据，回到原始默认设置）的功能和状态。

现状：

- `packages/lifecycle` 已有 `pause` / `resume`，但只有因子引擎（对象是因子集合）、策略（对象是策略实例）、Trade（模块级）三个模块接入；
  只能暂停预热或运行中的对象，看不出是谁、为什么暂停；自动暂停和手动暂停共用一个字段，系统没有统一的暂停动作。
- Collector 有按采集计划的暂停表（`t_collector_fetch_plan_pauses`），Monitor 没有暂停；其余模块只有进程级的 `moox-runtime pause`（暂停标记加停进程，守护不会拉起）。
- 重置没有统一入口，只有零散命令：`storage reset-view-consumers --reset-all-storage-data`、`collector fetch-plan reregister`、`moox-factor-engine reset-gap-ledger`、
  各模块 `*-cli init`，而且[部署与运维](../部署与运维.md)“清空全部数据重新积累”要靠运维人员按四步手工串起来，漏一步就留下脏状态。

结论（本设计的主线）：

1. **暂停是无损、可逆的门禁**：不删任何数据、不改任何配置，暂停期间各模块继续做不会产生副作用的维护。
   **恢复是两段式，不是一键放开**：先“恢复追赶”——把暂停期间缺失的时序数据补采、增量进入各模块（Collector 补采 → Storage → 因子本地存储与因子补算 → 策略输入就绪 → Trade 对账），
   **所有模块都追平并 ready 之后**，才统一放行，回到暂停前的可执行阶段（运行/预热）。追赶期间任何模块都不下单、不发新目标（第 1.4 节、第 2.2 节）。
2. **重置是有损、不可逆的动作**：必须先暂停、先出计划（dry-run）、再凭计划令牌执行，先备份、分步写日志、可断点续做；重置完成后模块回到“未初始化”，要重新走 init → start → confirm，**不会自动运行**。
3. **“全部配置和数据”不包括引导身份层**：Admin 的用户、密钥、主机与放置、SSH、PKI、`moox.toml`、发布制品是进入和管理系统的前提，清掉它们就没有人能再执行 init。
   这一层的重置等于重新 bootstrap，不放进“重置”命令（第 5.4 节说明）。这是对原话的一处收窄，请用户确认。
4. **系统级动作由独立编排模块 `modules/sysctl` 统一做**（入口 `moox-cli system pause|resume|reset`），按依赖顺序逐模块调用各模块自己的接口；模块只负责本模块的暂停与重置，不互相调用（第 8.1 节）。

## 1. 术语与状态

### 1.1 阶段（在现有 7 个阶段上加 3 个）

| 阶段 | 颜色 | 含义 | 来源 |
| --- | --- | --- | --- |
| uninitialized | 灰 | 刚部署，或重置完成后尚未 init | 现有 |
| not_ready / ready / warming / running / fault | 红/蓝/黄/绿/红 | 现有语义不变 | 现有 |
| paused | 橙 | 暂停，附带 **暂停详情**（第 1.2 节） | 现有，扩展 |
| **resuming** | 青 | 恢复追赶中：暂停期间缺失的数据正在补采、增量进入；**不计算、不下单**，带进度（第 1.4 节） | 新增 |
| **resetting** | 紫 | 重置进行中；不接受除 `reset-status` 外的任何命令，不参与门禁 | 新增 |
| **reset_failed** | 红 | 重置某一步失败；模块保持停用，只允许 `reset-apply` 续做或 `reset-abort`（见第 5.3 节） | 新增 |

重置成功后阶段直接回到 `uninitialized`，没有单独的“已重置”阶段；“刚被重置过”记在 `last_reset`（时间、操作者、计划摘要），首页用它显示“已重置·待初始化”。

### 1.2 暂停详情（`pause` 字段）

现有 `AutoPaused bool` 和 `Resume Stage` 合并扩展为：

```json
{
  "kind": "manual | auto | system",
  "reason": "手动暂停：切换行情源",
  "by": "yangyulei@…（Admin 用户）| cli:<主机> | monitor:auto",
  "since": "2026-10-21T10:00:00Z",
  "resume_to": "running",
  "expires_at": null
}
```

- **manual**：用户对该模块/对象下的暂停。**只有用户 resume 才会恢复**，检查通过也不自动恢复。
- **auto**：检查失败触发的自动暂停（现有行为不变）：检查重新通过自动恢复。
- **system**：系统级暂停动作带下来的。系统 resume 只恢复 `kind=system` 的暂停，**不动用户先前单独手动暂停的对象**（否则“系统恢复”会悄悄放开用户特意停着的策略实例）。
  同一对象已有 manual 暂停时，系统暂停不覆盖它（保持 manual），系统恢复也不碰它。
- `expires_at`：可选，到期自动恢复（适合“暂停一小时”）；到期前不自动恢复，到期后仍要检查通过。v1 先不做，字段预留。

允许暂停的阶段从“预热/运行”放宽到 **ready、warming、running**（ready 暂停后恢复回到 ready）。not_ready / uninitialized / fault 不需要暂停：本来就不计算。

### 1.3 有效阶段与对象阶段分开

模块自身暂停时，下属对象的阶段**保持原样**（现有 `Allowed()` 已是这样：自身暂停则整体不计算），不逐个改成 paused，所以模块恢复后所有对象原地继续，无需逐个恢复。
状态接口同时返回 `stage`（对象自身）和 `effective`（考虑模块暂停后的结果），首页显示 effective。

### 1.3.1 模块门禁矩阵与控制意图（`hold`）

现有 `Allowed(ref)` 只检查模块自身是否 `paused/fault`，再看对象是否 active；`Refresh()` 会在模块第一次检查时把自身自动初始化。新增阶段后必须改成显式矩阵，否则 `resuming`、`resetting`、`reset_failed`、重置后的 `uninitialized` 会绕过门禁：

模块暂停时对象阶段保持原样（第 1.3 节），所以追赶门禁不能要求“对象也是 `resuming`”，而是按**模块阶段 × 对象阶段 × 是否参与本次恢复**判定。对象有一个持久化标记 `catchup_member`：模块进入 `resuming` 时，把暂停前处于 warming / running 且**未被 manual 暂停**的对象标记为参与者；单独恢复对象时，该对象自己进入 `resuming` 并成为参与者。

| 模块自身阶段 | 实时门禁 `Allowed` | 追赶门禁 `CatchupAllowed`（只写历史数据） | 说明 |
| --- | --- | --- | --- |
| warming / running | 看对象是否 active | 对象阶段为 `resuming`（单对象恢复） | 正常；单个对象追赶不影响其他对象 |
| paused（含 `hold=system_pause`） | 否 | **仅**对象阶段为 `resuming` 的对象（对象级 `resume --force` 的例外，第 1.5 节） | 例外只放行该对象，不放开整个模块 |
| fault | 否 | 否 | |
| **resuming** | 否 | `catchup_member` 的对象；manual 暂停的对象继续排除 | 系统/模块恢复的追赶期 |
| **resetting / reset_failed** | 否 | 否 | 重置期，只接受 reset 接口 |
| uninitialized / not_ready / ready | 否 | 否 | 不再沿用“本来就不计算”的隐含假设，一律显式拒绝 |

对象的实时门禁在模块门禁为真时才看对象自身阶段。放行（`release`）时清除 `catchup_member`，对象回到暂停前的阶段。

**控制意图 `hold` 持久化在 `lifecycle.json`**，不依赖阶段推导：`hold = system_pause | post_reset | none`。
- `system_pause`：系统暂停时写入。即使模块自身检查失败（`not_ready`），也必须能建立这个门禁（先写 `hold`，再推进阶段）。
- `post_reset`：重置完成后写入，**`Refresh()` 在 `hold=post_reset` 时不得自动初始化模块自身**，必须用户 `init` 后才清除。`reset-abort` 只把阶段置为 uninitialized 并保持 `hold=post_reset`，**不释放尚未清理完的对象**（对象清理未完成的，journal 记录里仍标为待清理，继续阻断）。

### 1.4 恢复是两段式：追赶 → 放行

`resume` 不再直接回到暂停前的阶段，而是：

```
paused ──resume──▶ resuming（追赶：补采、增量进入、补算、对账；不计算不下单）
                      │ 本模块追平 + 检查通过 → 标记 caught_up
                      ▼
                  等待放行（仍是 resuming，进度 100%，“已追平，待放行”）
                      │ 放行（release）
                      ▼
                  回到 resume_to（running / warming / ready）
```

- **追平标准由各模块自己定义**（第 2.2 节），统一表达为 `catchup`：`{since, target, done, total, caught_up, blocked_by}`。`since` 是暂停时间，`target` 是追赶目标（“最新已完成周期”，追赶期间目标会随时间前移，所以追平指在放行那一刻无缺口）。
- **放行（release）单个对象/模块**：单独 resume 一个模块时，追平且检查通过后**自动放行**（只依赖它的上游已 ready，上游不 ready 则等待，状态显示 `blocked_by`）。
- **系统级放行是一道栅栏**：系统 resume 时，所有参与模块都追平（`caught_up`）之前，**谁也不放行**；全部追平后，编排器按上游到下游的顺序放行（第 2.1 节）。这就是“所有模块 ready 之后再改为正常可执行状态”。
- **放行前再核一次**：放行瞬间重新检查每个模块“无缺口、检查无 FAIL”（沿用现有 `Passed()` 语义：WARN 不挡路；例如策略实例的健康异常刻意返回 WARN，因为它只能靠成功求值恢复，写成阻断会循环等待）；追赶耗时较长时，目标周期已前移，会再追一轮，直到连续一次检查在放行点无缺口。
- 追赶不会被误判成故障：`resuming` 中，该模块及其下游的“新鲜度/缺口”告警按预期处理（与 `paused` 相同）；追赶超过阈值（默认按暂停时长的 2 倍与 30 分钟取大者）仍未追平，发一条“恢复追赶超时”告警，但**不自动放行、不自动回到暂停**，由用户决定继续等或 `resume --release-partial`（第 2.1 节）。
- 自动暂停（检查失败触发）的自动恢复走同一条路径：检查通过 → `resuming`（暂停很短、没有缺口时追赶瞬间完成）→ 自动放行。重启后的恢复同理。
- 暂停后进程重启：`paused_since` 与暂停详情落在 `lifecycle.json`，重启后仍是 paused，不丢追赶起点。

### 1.5 命令冲突规则

| 场景 | 规则 |
| --- | --- |
| 系统暂停期间，对单个对象执行 `resume` | 拒绝并提示“系统暂停中，请 `system resume`”；`--force` 允许（只恢复该对象，且仍要走追赶；用于紧急情况，写审计） |
| 对象已 manual 暂停，再执行系统暂停 / 系统恢复 | 保持 manual，系统暂停不覆盖、系统恢复不触碰（第 1.2 节） |
| `resuming` 中再执行 `pause` | 回到 `paused`，**`paused_since` 保持最早的那次**（已补进来的数据保留，下次追赶从最早起点重新核对，已补的部分很快通过） |
| `resuming` 中进程重启 | 回到 `paused`（追赶是进程内任务，不跨重启续做），`paused_since` 不变；重启后再 `resume` 即可 |
| 上游模块未 ready 时下游 `resume` | 进入 `resuming` 并显示 `blocked_by`，上游追平后自动开始追赶 |
| 暂停期间新建对象（新因子集合、新策略实例） | 可以创建并走 `init`；`start` 之后因模块暂停不会计算，随模块一起经历追赶与放行 |
| `resetting` 期间 | 不接受 `pause` / `resume` / `release`，只接受 `reset/status`、`reset/abort` |
| 重置前的暂停 | 重置要求模块处于 `paused`（或 `uninitialized`）；`resuming` 中要先 `pause` |

## 2. 暂停/恢复：每个模块暂停时到底停什么

原则：**暂停只停“会产生外部可见副作用的动作”**（下单、写结果、发采集请求、发告警），**继续做保持状态新鲜的内部维护**，这样恢复是瞬时的。

| 模块 | 暂停对象的粒度 | 暂停时停什么 | 暂停时继续什么 | 恢复时 |
| --- | --- | --- | --- | --- |
| 因子引擎 | 因子集合、模块 | 停止**全部三类**写结果的路径：实时计算、失效重算/缺口恢复/重算作业（现有 `active()` 只查目录与租约，必须并入生命周期门禁）、追赶推进（现有 `Advance()` 与实时事件共用同一个 gate） | 不要求保持窗口新鲜；暂停期间的事件在连续水位目标更新之前被 ACK 也没关系，恢复时由追赶显式补建（第 2.2 节） | 追赶：显式建立目标周期与标的集合，Pull 尾部增量，补算暂停期间错过的周期（第 2.2 节），放行后才恢复实时计算与发布 |
| 因子管理 | 模块 | 拒绝新建/修改因子集合与重算作业 | 只读查询 | 无需追赶，随放行恢复 |
| 策略 | 策略实例、模块 | 不再产生新目标（触发门禁转 Off） | 状态保留，**已有目标和持仓不动** | 追赶：等输入因子追平、历史充足；**不为暂停期间的周期补发目标**；放行后只对放行后的周期出目标 |
| Trade | 模块 | 关闭**两个入口**：接收新目标（回执“系统暂停”）和订单执行（`TargetWorker.runOnce`、`executor` 的拆单/提交/撤单路径加生命周期门禁），并等待**在途提交结束**才算 paused；**不主动撤单、不平仓**，也不复用逻辑账户的 `AutomationPaused`（它会撤单） | 回报、成交、持仓的消费与对账继续；暂停前未收敛的目标保持原状，放行时按过期处理，不继续下单（第 2.2 节） | 追赶：与交易所对账暂停期间的成交、订单、余额、持仓；对账无差异才算追平 |
| Collector | 采集计划、模块 | 停止发起采集（SCF 定时器、collector-stream 订阅）；暂停确认要等**远端定时器已禁用、订阅已停止、在途任务已结束**，不能只确认数据库开关写入 | 登记与对账、已有任务的状态展示 | 追赶（**恢复模式**，第 9 节）：对暂停区间 `[paused_since, 现在]` 补采全部数据集（第 2.2 节）；放行后恢复实时采集 |
| Monitor | 模块 | 停止**发出告警**（静默），不停探测与指标入库 | 探测、入库、首页聚合 | 最后一个放行；放行后恢复告警，静默期间的状态变化补一条汇总，不逐条补发 |
| Archive | 模块 | 停止调度新的归档运行 | 已在运行的作业跑完 | 无需追赶，随放行恢复 |
| Storage、EventBus、Admin、HostGateway、Access、HostAgent、ConsoleProxy、EgressProxy、CloudNode | — | **不提供业务暂停**：它们是被暂停模块的依赖，也是重置的执行通道，停了反而卡住恢复与重置 | — | 不参与恢复阶段；但 Storage 的 View 消费积压为 0 是追平的判断条件之一（第 2.2 节） |

注：

- 暂停的“继续做什么”必须在实现前逐模块对代码核实（尤其因子引擎暂停时本地同步是否仍跑、Collector 暂停是否会被自动补采重新拉起）；核实结果写回本表。
- **Trade 暂停不清仓**是刻意的：暂停是“别再动”，不是“平掉”。需要清仓是独立的运维动作，不挂在暂停上。
- 暂停和恢复追赶期间（`paused`、`resuming`）Monitor 把该模块及其依赖的“新鲜度/缺口”检查按预期处理，不告警（视为预期状态，类似现有的 `partial` 处理）。

### 2.1 系统级暂停/恢复

`moox-cli system pause [--reason …]`：按**下游到上游**的顺序逐个暂停（先停会下单的，再停会产生数据的）：

```
策略 → Trade → 因子引擎 → 因子管理 → Collector → Archive → Monitor（最后，静默告警）
```

每步等该模块返回 `paused` 再下一步，某步失败**不回滚**已暂停的部分（暂停无损），报告停在哪里，重复执行幂等。

`moox-cli system resume`：分**追赶**和**放行**两段，中间有一道栅栏（第 1.4 节）。只恢复 `kind=system` 的暂停。

1. **追赶段（按上游到下游启动，可并行推进）**：
   `Collector → 因子管理 → 因子引擎 → 策略 → Trade → Archive → Monitor` 依次下达 `resume`，各模块进入 `resuming`。
   下游模块在上游未追平前不会白跑：它的追赶目标依赖上游（例如因子引擎等 Collector 补采写入 Storage 后才能同步和补算），状态显示 `blocked_by: collector`，上游追平后自动开始。
2. **栅栏**：编排器轮询各模块 `catchup`，**全部 `caught_up` 才进入放行段**；任何一个模块未追平（含被依赖阻塞、检查失败）就继续等待，并在 `system status` 里逐模块显示进度与阻塞原因。
3. **放行段（按上游到下游逐个放行，每步确认）**：
   `Collector → 因子管理 → 因子引擎 → Archive → Trade → 策略 → Monitor`。
   Trade 先于策略放行，保证策略放行后产生的第一批目标有地方接收；Monitor 最后，等业务都回到可执行状态再恢复告警，避免恢复瞬间一串噪声。
   放行前每个模块再核一次“无缺口、检查无 FAIL（WARN 不挡路）”，不满足则该模块回到追赶，放行暂停在这一步，已放行的上游保持运行（它们本来就是追平的）。
4. **超时与例外**：追赶超过阈值只告警，不自动放行；用户可以
   - 继续等待；
   - `system resume --release-partial`：明确放行已追平的模块、保持未追平的模块处于追赶（命令会先列出哪些模块未追平、放行后的后果，要求 `--yes`）；
   - `system pause` 回到暂停（追赶中的模块直接回到 paused，已补进来的数据保留）。
   没有“跳过追赶直接放行”的选项：数据没补齐就放行，下游会在缺口上计算；确实无法补采的区间（行情源已不提供）见第 2.2 节的“不可补区间”处理。

系统暂停时 Storage、EventBus、Admin 等基础设施保持运行。

### 2.2 各模块的追赶内容与“追平”标准

| 模块 | 追赶做什么 | 追平标准（`caught_up`） |
| --- | --- | --- |
| Collector | 暂停时记 `paused_since`（每个数据集的最后已完成周期为起点）；恢复时对每个数据集创建补采作业，区间 `[paused_since, 最新已完成周期]`，复用现有 K 线补采（`collector kline backfill`）与历史扫描；补采按现有限频与分块执行 | 所有数据集在暂停区间内无缺口：缺失周期要么补采写入 Storage，要么已被登记为**行情源缺失**（`t_collector_source_absences`，即源头确实没有，例如停牌、行情源保留期之外）。后者按缺失行填充规则处理，不阻塞追平，但追平报告里列出数量 |
| Storage | 被动接收补采写入，View 消费并建索引 | 不单独判断；用于判定别人的追平：目标区间的数据已落盘，View 消费积压为 0 |
| 因子引擎 | ① 进入追赶时**显式建立**连续水位目标（暂停区间内的每个已完成周期 × 当前标的集合），不等下一条实时事件；② 本地 K 线同步：已有范围的修正走 `Follow()`，**新增尾部必须 `Pull()`**（`Follow()` 只修正已有范围）；③ 窗口连续性检查通过（无空洞）；④ 对暂停区间的每个周期补算因子并发布历史结果，使用追赶门禁（第 1.3.1 节），结果事件带“历史”标记（第 2.2.1 节），不触发任何下游交易 | 每个因子集合的水位追到“最新已完成周期”，变更日志无断档，窗口无空洞，补算结果已写入 Storage |
| 策略 | 等其输入因子集合追平；检查历史充足（`min_age_bars`）、输入就绪（现有 readiness）；重建需要的内部状态（回放服务内的规则状态按需） | 实例的全部输入因子追平、readiness 通过，、**放行边界前一周期的版本记录已补齐**（`bars[-1]` 类策略必需），且**策略自己的消费者积压为 0**（用 JetStream 消费者信息判断，不能用 Storage View 积压代替）。**不补发**暂停期间任何周期的目标 |
| Trade | 与交易所对账：拉取暂停期间的成交、订单状态、余额、持仓，写入账本；消费积压的回报事件；纸面账户按已落盘行情补记权益点；放行时把暂停前未收敛的目标置为过期 | 账本与交易所无差异（或差异已被对账规则解释并记录），事件积压为 0，无在途提交 |
| 因子管理、Archive、Monitor | 无数据追赶 | 立即 `caught_up` |

要点：

- **补采是基础**：下游全都等 Collector。Collector 追不平，整个系统不放行。暂停越久、数据集越多，追赶越慢，所以暂停时间会显示在首页，`system resume` 开始前会估算补采量（周期数 × 标的数）并展示。
- **变更日志断档（暂停超过保留期 7 天，或 Storage 身份变化）**：增量同步返回断档并把数据源置为 blocked，重复追赶不会修复，等待超时也解决不了。流程：追赶检测到 blocked → `system resume` 在开始前的预估里提示“需要离线维护因子引擎”并要求 `--allow-engine-restart` → 停引擎 → `reconcile`（已有范围对账）与 `backfill`（向更早历史扩展）→ 重建同步基线 → 尾部 `Pull()` → 启动引擎 → 补算。`reconcile` 与 `backfill` 分别处理不同问题，不能互相替代。v1 由 sysctl 经 SSH 调引擎主机的 systemd 用户单元与现有命令完成；不允许时报告阻塞原因，由人工处理。
- **休市区间**：非交易时段暂停，补采区间里没有应有的 K 线，追赶瞬间完成；日历取自 `marketcalendar`，不会把休市当作缺口。
- **不可补区间（持久事实，三方统一判据）**：行情源保留期之外或确实缺失的区间，Collector 登记在 `t_collector_source_absences`（持久，带数据集、标的和周期区间）。现有因子侧只依赖内存里的缺失通知，30 分钟后过期，会把这些周期重新判成无行，导致永远过不了栅栏。因此：
  - Collector 的追赶接口 `catchup` 同时返回区间内的**源缺失事实清单**（`unfillable`），追平标准是“每个周期要么已写入，要么落在持久缺失事实里”；
  - 因子追赶显式**查询**这份持久清单（不依赖内存通知）：本地窗口按填充规则补齐并带标记，对该标的该周期的因子结果记为跳过（`partial`），不计入缺口；
  - 策略对这些周期同样按 `partial` 处理；
  - 系统不因此卡住，追平报告和首页显示“暂停区间含 N 个不可补周期”。
  Collector 不会向 Storage 写填充行，这一点以代码为准。
- **暂停区间不丢**：追赶起点记在 `paused_since`，不依赖进程不重启；如果暂停期间发生过 Collector 的重新登记或计划变更，起点取更早者。
- **追赶中新周期不断产生**：追赶目标随时间前移。放行前最后一次核对时才算数（第 1.4 节）；实时周期从放行点才开始被采集和计算，放行点之前尚未补完的最近一两个周期由追赶最后一轮兜底，避免放行后第一个周期出现缺口。
- **追赶中的副作用边界**：只允许写入**历史数据**（K 线、因子历史结果）；不下单、不发策略目标、不发告警。边界由协议保证，见第 2.2.1 节，不依赖消息到达的先后。

### 2.2.1 “历史结果不触发交易”的协议保证（策略放行边界）

仅靠“策略处于 `resuming` 不求值”不够：现有策略按**处理时**的门禁决定是否求值，系统恢复时延迟到达的历史事件可能在策略放行后才被消费；单独恢复因子引擎时下游策略可能一直在运行。最近的历史周期还可能落在两根 bar 的有效期内，产生目标并被已放行的 Trade 接收。所以：

1. **历史标记**：追赶期间因子引擎发布的结果事件携带 `catchup=true` 与 `release_period`（追赶目标周期）。
2. **策略放行边界**：每个策略实例持久化 `release_boundary`（实例放行时刻之后**第一个收盘的周期**）。策略对任何事件，**无论何时到达、重投多少次**，只要周期 < `release_boundary`（或带 `catchup=true`）就**不求值、不发目标**。
   但这些历史事件**要用来维护可信版本记录**：现有策略暂停时直接返回、不保存周期记录，而引用 `bars[-1]` 因子列的策略需要恰好上一周期的可信因子指纹，缺失会返回 `previous_version_unknown`，恢复后第一个周期仍被跳过或卡住栅栏。所以历史事件只写周期记录（因子指纹、版本），不求值、不发布；追赶阶段必须补齐**放行边界前一周期**的记录，策略的 `caught_up` 以此为条件之一。
3. 边界只在放行时更新；单独恢复因子引擎（策略一直在运行）时，历史标记保证策略忽略这批事件，不依赖策略自己的暂停。
4. 验证覆盖：单独恢复因子、历史消息延迟到放行之后、消息重投、放行点附近的周期，以及引用 `bars[-1]` 因子列的策略恢复后第一个周期能正常出目标（见第 10 节）。

## 3. 系统状态汇总

`monitor/internal/healthview/system.go` 的 `HealthSystem` 增加：

| 字段 | 说明 |
| --- | --- |
| `phase` 新取值 | `paused`（所有可暂停模块都 paused）、`partially_paused`（部分暂停）、`resuming`（恢复追赶中，含“已追平待放行”）、`resetting`、`reset_pending_init`（已重置，存在 uninitialized 模块） |
| `catchup_summary` | 追赶中的模块数、已追平数、最慢模块与阻塞原因、已追赶/总周期数、预计剩余（按已完成速度估算）、不可补周期数 |
| `pause_summary` | 暂停的模块/对象数、其中 manual / auto / system 各多少、最早暂停时间 |
| `last_reset` | 最近一次系统重置的时间与操作者 |

首页展示形如：「已暂停 · 系统暂停（切换行情源）· 5 个模块」「恢复中 · 追赶 3/5 个模块 · Collector 补采 62%（剩余约 8 分钟）」「恢复中 · 已全部追平，待放行」「部分暂停 · 策略实例 A 手动暂停」「重置中 · 因子引擎」「已重置 · 待初始化 4 个模块」。

健康面规则：`resuming` 不算降级（是预期的过渡状态，超时才变成告警）；manual / system 暂停**不算降级**（是用户意图，显示橙色但健康），auto 暂停仍按现有逻辑算降级；resetting 不算降级但不可操作；reset_failed 算故障（红）。
`HealthLifecycle` 的 `compact` 里每个对象带 `pause.kind`，Monitor 据此区分。

## 4. 重置的语义

### 4.1 “原始默认设置”指什么

= **刚完成部署、尚未 init 时的状态**，由三个来源决定：

1. 模块内嵌的建表 SQL（`modules/*/schema/*.sql`）：重置后表结构与新部署一致；
2. 随发布走的种子与默认值：`config/setup/*.yaml`（`metadata.yaml`、`collection-tasks.yaml`、`dataset-health-policy.yaml`）、因子库 `modules/factor/factors`、`packages/storagepolicy.Default()`；
3. 发布内的配置文件（`config/*.yaml`、`storage-policy.json` 等）——**这些文件不被重置删除**：它们是部署输入（由 `moox.toml` 渲染或随版本安装），属于“部署”而不是“运行时状态”。
   重置不会把被运维手改的文件悄悄改回去；要回到发布原样，是重新安装当前发布（`native-release.sh install` / `setup release`）的事，写进重置报告的提示里。

这样“重置”和“部署”的边界清楚：**部署管文件，重置管状态（DB 表、本地数据、生命周期文件、事件流）**。

### 4.2 三个层级（重置命令的 `--scope`）

| 层级 | 清什么 | 默认 |
| --- | --- | --- |
| `data` | 运行数据：K 线与因子结果、订单/成交/权益、回放结果、告警历史、指标、作业与水位、本地时序存储、事件流 | |
| `config` | 业务配置：因子集合与定义、策略定义与实例、采集任务与计划、告警规则与渠道、空间与数据集定义、View、摄取方式、生命周期文件 | |
| `all` | `data` + `config`，然后重新导入种子 | **默认** |

`data` 单独重置（保留配置重新积累）等价于现有“清空全部数据重新积累”流程的自动化；`config` 单独重置要求同时清掉依赖它的数据，
所以实际上 `config` 会被提升为 `all`，v1 只开放 `data` 与 `all` 两档。

## 5. 每个模块的重置契约

### 5.1 通用契约

每个参与重置的模块提供三个接口（挂在健康端口 `/v1/lifecycle/reset/*`，与现有生命周期路由同一鉴权与前缀路由）：

| 接口 | 作用 |
| --- | --- |
| `reset/plan` | **只读**。返回将要做的每一步：删哪些表（含行数）、哪些文件（含字节数）、保留什么、种子来源、需要的前置条件（例如必须已暂停、引擎进程必须停止）、`plan_digest`（计划内容的哈希）和 `reset_token`（绑定该哈希，10 分钟有效，单次使用） |
| `reset/apply` | 带首次授权 `reset_token` + `scope`（或续做时带 `operation_id`）。校验：模块已暂停（或自身为 uninitialized）、令牌有效且**稳定计划摘要**未变；兑换成持久化的 `operation_id`；进入 `resetting`；按步骤执行并逐步落盘日志 |
| `reset/status` | 当前步骤、已完成步骤、失败原因；`resetting` 与 `reset_failed` 时都能查 |

执行规则：

- **模块进程内执行**，在 `resetting` 阶段独占模块（缓存、连接池、Pebble 单进程锁都由本进程管理，外部删文件会留下脏缓存）。例外是 Storage 的 Pebble 与事件流，复用现有外部流程（第 5.2 节）。**因子引擎也走进程内模型**：重置阶段引擎进程**不停**，控制端口（由引擎进程提供）保持可用，只停业务任务、释放租约、关闭 Pebble，重置后重新打开；只有 `reconcile` / `backfill` 这类现有的离线命令才需要停进程（第 2.2 节断档流程），属于单独的“离线维护”，不与重置混用。
- **步骤幂等、有日志**：`<数据目录>/reset-journal.json` 记录 `operation_id`、稳定计划摘要、步骤列表与完成情况；进程在中途崩溃，重启后模块直接进入 `reset_failed`（带“已完成 n/m 步”），用 `reset/apply --operation-id` 续做，不重新开始、不会半途重置两遍。
- **先备份再删除**：SQLite 用在线备份（`VACUUM INTO`）写到 `<数据目录>/reset-backups/<时间戳>/`，配置类文件和生命周期文件一并拷入；保留最近 3 份。时序大数据（Pebble、Parquet）**默认不备份**（体积大、可重新积累），计划里明示“不备份：xxx（N GB）”，可用 `--backup-bulk` 要求备份。
- **删表方式**：删除全部业务表行（按外键顺序，单事务），不删表结构、不删 `schema_meta`；之后调用该模块已有的 `init` / 种子导入把默认数据写回。不采用“删库文件重建”，避免丢失 SQLite 的 pragma、权限与句柄问题。
- **结束状态**：成功后阶段为 `uninitialized`；检查/初始化由用户按常规流程做。重置本身**不自动 init、不自动 start**。
- **审计**：开始、每步、结束、失败都写模块日志和 Admin 的活动日志（`t_activity_logs`），含操作者、范围、计划摘要；结束时经 Monitor 渠道发一条通知。

| **Storage** | 全部行数据（Pebble）、`MOOX_STORAGE` 事件流、各 View 的消费者与索引；元数据中的数据集/View/标的/空间定义（仅 `all`） | 建表、DataNode 登记 | `import-seed` + `activate-datasets` 导入默认空间、数据集、字段、View；**策略文件 `storage-policy.json` 不动**（属于部署输入）。**执行方式**：`data` 范围复用 `moox-cli storage reset-view-consumers --reset-all-storage-data`（停 Storage、备份元数据、清 Pebble 与事件流、重启并等 View 重建），**该命令保留数据集/View 等定义，只复位 `t_views` 并删除构建与同步状态**，由编排器调用。**`all` 范围现有工具不够**：种子导入是 Upsert，不会删除自定义定义，所以需新增 `storage reset-metadata`（备份后删除全部定义表行，再 `import-seed`）；事件资源（`MOOX_STORAGE` 流、各数据集主题、各 View 的动态消费者）要整理成清单，并扩展 Admin 的 EventBus 受限接口白名单覆盖清单里的全部对象（现仅放行 Storage View 的流、消费者和确切的数据集主题） |
| **EventBus** | JetStream 的流与消费者数据 | 管理员令牌（在 Admin） | 各模块 init 时重新创建自己的流与消费者；与 Storage 的 `MOOX_STORAGE` 流一并通过 Admin 的受限接口清 |
| **Admin** | 业务空间及成员（默认空间除外）、用户操作记录、活动日志、采集发布租约与操作、SCF/云节点发布记录 | **用户、登录历史、密钥 `t_secrets`、主机与放置、SSH 主机/密钥/会话、主机网关状态、PKI、`admin-master.key`** | 默认空间由 `setup init` 重建 |
| **CloudNode** | 默认**不重置**：它登记的是腾讯云上真实存在的 SCF 函数与账号，只清库会留下无人管理的云资源并继续计费 | — | 需要时单独 `--include cloudnode`，计划里先列出远端资源清单，用户逐项确认 |
| **Access、HostGateway、HostAgent、ConsoleProxy、EgressProxy** | 无业务状态；`access/nonces.db` 是防重放缓存，不重置 | 全部 | 无 |

### 5.3 失败与中止

- `reset_failed` 下可 `reset/apply`（凭 `operation_id`）续做，或 `reset/abort`：
  abort **不撤销已做的步骤**，只把模块置为 `uninitialized` 并保留备份路径，由用户决定按备份恢复还是重新 init。
  明确告知“已删除的不会回来”，不假装有回滚。
- 备份恢复 v1 只给**手工步骤**（备份目录里是完整 SQLite 文件与配置，停模块、替换文件、`moox-runtime reseal` 如需），不做 `restore` 命令；等第一次真实需要后再决定值不值得做。

### 5.4 为什么引导身份层不在“重置”里

Admin 的用户、`t_secrets`（交易所与云厂商密钥）、主机与放置、SSH 与 PKI，以及 `moox.toml`、发布制品，决定“谁能进来、能连哪些机器”。
这些被清掉后，重置自己就无法继续（后续 init 需要 Admin 登录、网关路由、密钥）。所以：

- 系统重置到“`setup bootstrap` 之后、`setup init` 之前”的状态，**这就是原始默认**；
- 想连引导层也清掉（换环境/重装），是重新 bootstrap（`setup bootstrap` + `setup apply`），属于部署动作；文档里写明，不提供“一键全删”。

## 6. 系统级重置编排

`moox-cli system reset [--scope all|data] [--include cloudnode] [--backup-bulk]`，分两段：

### 6.1 `system reset plan`（只读）

1. 连接每个模块：不可达、正处于 `resetting`/`reset_failed` 或有发布/维护锁（`run/maintenance.lock`、`installation.json`）时直接拒绝。
2. **危险项预检**：
   - Trade：存在**非纸面**账户有未平持仓或未完成订单（实盘）→ 拒绝并列出；重置只清本地账本，**交易所上的仓位不会因此消失**，不允许留下“账本空白但真有仓位”的状态。**plan 阶段的预检只是提示**：plan 到 apply 之间可能新增仓位，所以阶段 1 里 Trade 暂停（订单执行入口已关闭、在途提交已结束）**之后**，必须向交易所重新核验订单、成交、持仓，**实盘持仓不为零，或有未完成订单（含无法确认状态的订单），都拒绝**，不由重置去撤单——需要用户先自行处理；两项都确认为零才继续。暂停会等在途提交结束但不撤单，所以未成交的限价单必须在复核里拦住，否则清空账本后订单仍可能在交易所成交。
   - 因子引擎的控制端口可达（重置在进程内做）；archive-worker 与进行中的导入作业（`moox-importer` / `moox-cli import`）需要先排空或取消。导入断点库（默认在操作机 `./importer.db`）记录目标的**重置代次**，代次不一致时拒绝续传并要求 `--restart`，避免重跑同一导入因旧断点被整体跳过。
   - 磁盘空间足够放备份。
   - 有进行中的 Collector 补采作业、归档运行、回放会话：列出并要求先取消或加 `--force-cancel`。
3. 汇总每个模块的 `reset/plan`，得到整个系统的 `system_plan_digest` 和 `system_reset_token`（10 分钟有效，仅用于**发起**）；输出人类可读报告：每个模块删什么、多大、备份到哪、不备份什么、哪些保留。

### 6.2 `system reset apply --token <令牌> --yes`

生产环境（`moox.toml` 的 `[system] env = "production"`，默认视为 production）额外要求 `--confirm-name <系统名>`：必须逐字输入系统名，防止在错误环境误执行。

执行阶段（编排器写 `system-reset-journal.json`，可断点续做）：

| 阶段 | 动作 |
| --- | --- |
| 0 | 校验令牌并兑换成持久化的系统 `operation_id`，再为每个模块派生模块 `operation_id`（模块不再各自校验令牌，避免第 11 分钟开始的操作在模块步骤上因令牌过期失败）；写日志，向 Monitor 声明“系统重置中”（抑制告警，首页显示重置中） |
| 1 | `system pause`（第 2.1 节）；停 archive-worker；取消进行中的导入作业。因子引擎**不停进程** |
| 2 | 各模块备份 |
| 3 | **下游到上游**重置：策略 → Trade → 因子引擎 → 因子管理 → Collector → Archive → Storage 与 EventBus（外部流程，其间 Storage 停机几分钟）→ Monitor → Admin 业务部分 |
| 4 | **上游到下游**写回默认：Admin 默认空间 → Storage `import-seed` / `activate-datasets` → Collector 种子与 `fetch-plan reregister` → 因子管理导入因子库 → Monitor 默认规则与渠道 |
| 5 | 各模块 `check`；系统进入 `reset_pending_init`；报告列出“还需要你做的下一步”（init 各模块 → 配置因子集合/策略实例 → start → confirm） |

顺序理由：先清下游，避免上游清空时下游仍在读写；写回时先上游，保证下游 init 时依赖已存在。
Collector 的重新登记必须在 Storage 清空**之后**（现有运维文档第 3 步的原因：Pebble 里的序列快照被清了）。

中途失败：停在失败步，系统显示“重置失败：<模块>/<步骤>”，其余模块保持已暂停；`system reset apply --operation-id` 续做（令牌过期不影响续做，续做校验的是身份、范围和步骤）。不自动回滚。

### 6.3 单模块重置

`moox-cli lifecycle reset-plan|reset-apply|reset-status --kind … --endpoint …` 允许只重置一个模块（例如只重置策略）。
单模块重置只做该模块的 `reset/*`，**不管下游依赖**：例如单独重置因子管理会让策略实例引用的因子集合消失，计划里要列出“被依赖的对象”并要求 `--force`。
系统级重置才保证一致。

## 7. 安全措施汇总

| 措施 | 作用 |
| --- | --- |
| 必须先暂停（系统重置由编排器代做） | 避免边写边删 |
| plan → token → apply 两步 | 不会一条命令误删；令牌（10 分钟）只用于发起并绑定**稳定计划摘要**（删除范围、配置版本、前置条件），行数、字节数等统计值单独展示、不进摘要；发起后换成持久化 `operation_id` 续做 |
| 生产环境需输入系统名 | 防止在错误环境执行 |
| 仅 CLI（命令行）能重置；首页只提供暂停/恢复按钮 | 重置是低频、高风险动作，不放在一次点击能触发的位置 |
| 实盘持仓/未完成订单预检 | 防止本地账本与交易所脱节 |
| CloudNode、引导身份层默认排除 | 防止留下孤儿云资源或把自己锁在门外 |
| 备份 + 保留 3 份 | 手工恢复的依据 |
| 审计日志 + 通知 | 谁在什么时候重置了什么 |
| 重置专用鉴权范围 | 权限由**服务端**的密钥→权限映射决定（不接受客户端自称的 `scope`）：`reset` 权限只映射给运维 CLI 用的密钥，策略/Trade 的运行时密钥不能触发重置。与首次暴露 `reset/*` 接口**同一阶段**完成（阶段 3），不能先开接口后补鉴权 |

## 8.1 状态控制逻辑放在哪里：两层，编排独立成模块

| 层 | 放哪里 | 负责 | 不负责 |
| --- | --- | --- | --- |
| 模块内状态机 | `packages/lifecycle`（各模块进程内，现有） | 本模块/对象的阶段、门禁（`Allowed`）、暂停详情、追赶进度、本模块重置的步骤与日志 | 不知道别的模块 |
| **系统编排** | **新模块 `modules/sysctl`**（二进制 `moox-sysctl`，库在 `modules/sysctl/internal`） | 模块依赖顺序、系统暂停/恢复（追赶栅栏、放行顺序）、系统重置的计划/令牌/阶段日志/续做、危险项预检、汇总状态 | 不持有业务状态：模块的阶段以各模块自己为准 |
| 操作入口 | `moox-cli system …` 与 `moox-cli lifecycle …` | 参数解析、输出、确认交互（令牌、系统名）；**只是薄入口**，调用 `modules/sysctl` | 不写任何编排逻辑 |

要点：

- **编排不放进 `moox-cli` 的命令代码里**：命令行里堆编排会让逻辑难测、难复用；放进 `modules/sysctl` 后，`moox-cli system …` 与独立二进制 `moox-sysctl` 用同一份实现（与 `modules/importer`、`modules/replay` 的做法一致：独立模块加 CLI 嵌入），将来首页按钮（阶段 5）也调用同一份。
- **编排器基本无状态**：阶段以模块自己持久化的 `lifecycle.json` 为准，所以 `system pause|resume` 是**幂等、可重复执行**的——命令行中途断开、笔记本关机，再执行一次就按各模块当前状态继续（追赶可能耗时很长，不依赖某个进程一直在线）。只有系统重置需要自己的阶段日志（`system-reset-journal.json`，放在操作机的状态目录），用于续做。
- **v1 不做常驻服务**：模块的健康端口只在各主机本机监听，经现有 SSH 隧道与主机网关访问（和 `moox-cli lifecycle`、回放工具相同的方式）；常驻服务要新增网关路由、鉴权范围和跨主机密钥分发，等需要首页按钮时（阶段 5）再把同一份实现包成服务，不改编排逻辑。
- **跨主机访问 v1 明确采用运维 SSH 隧道**：现有 lifecycle 客户端直连 `endpoint`，网关对健康端口的中转目前只放行 Monitor，不能直接供 sysctl 使用；常驻服务化时才需要新增网关路由。
- 鉴权：编排器按模块取各自的健康密钥（策略/Trade 共用，因子引擎独立），`reset` 权限由服务端密钥映射决定，见第 7 节。

## 9. 需要新接入生命周期的模块

重置和暂停统一挂在 `packages/lifecycle` 上，所以 **Collector、因子管理、Monitor、Archive、Admin（业务部分）** 要接入模块级生命周期（只有模块自身，没有对象，像 Trade 那样）：

- Collector 的对象可以是“采集计划”。**不能把现有 `t_collector_fetch_plan_pauses` 直接映射成对象的 paused**：保持该暂停开关时补采 `Tick()` 直接返回，空间也退出计划管理器的运行集合；清除开关则同时恢复定时器和流采集。直接映射会在“补采跑不起来”和“栅栏之前提前恢复实时采集”之间二选一。
  所以给采集计划增加独立的**三态**：`paused`（全停）、`recovering`（**恢复模式**：补采调度与所需管理协程运行，实时定时器与订阅保持关闭）、`running`；`resuming` 对应 `recovering`，放行时才切到 `running`，由 `t_collector_fetch_plan_pauses` 增加模式列承载；
- 因子管理（factor-mgr）此前没有接入生命周期，也在这次接入范围内（模块级）；
- Storage 的重置继续走现有外部流程，但**状态**（resetting / uninitialized）要被编排器写入一个模块级记录里，首页才能显示；v1 由编排器代写 Storage 的 `lifecycle.json`，不让 Storage 进程内承担。

## 10. 分阶段落地

| 阶段 | 内容 | 验证 |
| --- | --- | --- |
| 1 | `packages/lifecycle` 暂停详情（kind / reason / by / since）、`resuming` / `resetting` / `reset_failed` 阶段、`effective`、门禁矩阵与 `hold`（第 1.3.1 节）；放宽可暂停阶段；既有三个模块适配（含：因子引擎三类写结果路径并入门禁、Trade 订单执行入口加门禁并等在途提交结束）；Monitor 汇总与首页显示 | 单测（状态机全部转换、system 与 manual 互不覆盖、`hold=post_reset` 时 `Refresh()` 不自动初始化、自身检查失败也能建立系统暂停门禁）；**交易时段内**分别验证：① 暂停 **Trade 模块**，已有待执行目标不再下单、在途提交结束后才进入 paused、持仓/订单不被动；② 暂停**策略实例**，不再生成新目标（已有目标不受影响）→ 首页橙色且不降级 → 恢复 |

| 3 | 重置通用契约（plan / token → `operation_id` / journal / 备份 / 续做）+ 服务端 `reset` 权限映射 + 策略、Trade、因子管理、因子引擎（进程内）、Collector、Monitor、Archive（含 worker 暂存库）的重置 | 每个模块单测删表与种子；**每个破坏性步骤之后中断进程再续做**；本地一次完整重置→重新 init 的演练 |
| 4 | Storage / EventBus 外部流程接入编排器（含新增 `storage reset-metadata`、事件资源清单与 Admin 白名单扩展、导入断点的重置代次）；`moox-cli system reset`；Admin 业务部分；文档与运维手册；安全措施（令牌、系统名、实盘预检、`reset` 鉴权范围） | **在测试数据上**线上整体重置一遍：重置前造假数据（K 线、因子结果、策略实例、纸面账户订单），重置后逐模块核对为空/默认，再完整 init → start → confirm 跑通 |

## 11. 取舍（2026-10-21 用户已按推荐方案确认）

0. **恢复必须先追赶再放行**：追赶超时只告警不自动放行；唯一的例外是 `--release-partial`，需要显式加 `--yes`。追赶期间**不为暂停期间的周期补发策略目标**（只补数据、不补交易）。
1. **引导身份层保留**（Admin 用户、密钥、主机、SSH、PKI、`moox.toml`）：这是对“删除所有配置”的收窄，理由见第 5.4 节。
2. **配置文件不被重置**（发布内的 `config/*.yaml`、`storage-policy.json`）：重置管状态，部署管文件。
3. **CloudNode 默认不重置**（避免留下孤儿云函数），需要时单独加参数。
4. **Trade 暂停不撤单不平仓**；实盘有持仓时拒绝重置。
5. **重置完成后不自动运行**，回到未初始化，需要重新走 init → start → confirm。
6. **重置只在命令行触发**，首页 v1 只放暂停/恢复。
7. 大体积时序数据（Pebble、Parquet）默认不备份。

## 12. 不做的事

- 不做重置的自动回滚（删了就是删了，靠备份手工恢复）。
- 不做“跨环境配置导出导入”（那是 `config backup/restore` 的职责）。
- 不在暂停里加撤单、平仓、强制停进程等副作用；这些是单独的运维动作。
- 不改 Storage 的 Pebble 单进程模型，也不为了重置让 Storage 在线擦除。

### 阶段 1（2026-10-21，分支 `feat/pause-resume-stage1`）

已实现：`packages/lifecycle`（暂停详情、`resuming` / `resetting` / `reset_failed` 阶段、`hold`、门禁矩阵、`resume` 两段式与 `release`、`/v1/lifecycle/catchup`、`Hooks.Catchup` 与 `Hooks.Quiesce`）；

策略暴露 catchup 路由；Monitor 汇总与首页显示新状态；`moox-cli lifecycle` 增强。

与设计不同或补充的地方：

- **门禁矩阵（第 1.3.1 节）更正**：模块自身为 `ready` 时**放行**实时计算。因子引擎和策略的模块自身一直停在就绪，对象在跑；只有自身未初始化、未就绪、暂停、恢复追赶、重置、故障或带控制意图时才不放行。
- **Trade 用 `Halted` 而不是 `Allowed`**：被有意停下（暂停、恢复追赶、重置、重置失败、故障、带控制意图）才关闭目标接收与执行；就绪检查抖动（单个账户会话断开、EventBus 短暂不可用）不应让 Trade 停止接收目标，被拒绝的目标是 TERM，不会重投。
- **暂停后等待在途操作**用通用的 `Hooks.Quiesce`：暂停先提交（门禁立刻关闭），再等在途操作结束，超时返回「已暂停，但在途操作没有结束」，对象仍是暂停。
- **推迟到阶段 2**：策略的历史标记与放行边界（需要因子结果事件加字段）、各模块真正的追赶逻辑（Collector 补采恢复模式、因子 `Pull()` 与历史补算、Trade 对账、断档后的离线维护）、放行时把暂停前未收敛的目标置为过期、`modules/sysctl` 与 `moox-cli system …`。目前没有 `Catchup` 钩子的模块恢复时立即视为追平，行为与阶段 1 之前一致。
- **验证**：生命周期包、Trade、因子相关包、Monitor、命令行、前端首页的单测与类型检查通过；`make -k verify` 唯一失败项是本机缺 PyYAML 的 SCF 打包契约（与本改动无关）。线上的交易时段暂停恢复演练待阶段 2 的追赶逻辑完成后做。

### 线上演练发现并修复的问题（2026-10-22）

第一次线上演练（暂停约 10 分钟后 `system resume`）：采集的补采 40 分钟仍未追平。原因：恢复模式下实时采集关闭，追赶目标却跟着当前时间走；补采速度（每个标的至少一个分块，一个作业 1040 个分块约 30 分钟）赶不上缺口的增长，每个作业跑完又出现新缺口，永远追不平，行情新鲜度告警一直在。修复：

- 采集的追赶目标固定为恢复开始的时刻（`Backfiller.Catchup(since, to)`）；
- 采集只拉取和写入行情，没有副作用，**追平后自行放行**、恢复实时采集，不等栅栏（`sysctl.selfReleasing`）；有副作用的因子、Trade、策略仍然等栅栏。第 2.1 节的「所有模块追平后再放行」据此修正为：除采集外的模块。

### 阶段 2（分支 `feat/pause-resume-stage2`）：恢复追赶与系统级暂停/恢复

已实现：

- **Collector**：模块级生命周期（暂停开关 + 恢复模式 + 暂停区间补采 + 放行）；`klinecheck.Backfiller.Catchup` 对暂停区间提交补采作业并判定追平，`Quiesce` 等在途分块结束。
- **因子引擎**：集合级 `Catchup` 钩子——后台同步本地数据（`Prepare` = Follow + Pull 尾部 + 重载窗口，每次恢复一次）→ `Continuity.NoteTarget` 显式建立追赶目标 → 唤醒现有追赶循环（追赶门禁下补算历史周期）→ 水位追到目标且无阻塞才算追平；变更日志断档时报告阻塞原因。
- **策略**：`ModeCatchup`（追赶期间到达的因子完成事件按 `skipped(catchup)` 记录周期与因子指纹，不求值、不发目标，保证放行后第一个周期有相邻记录）；放行边界 = 控制器记录的放行时间，BarEnd 不晚于它的周期无论何时到达、重投都只记录；追赶进度 = 已处理到最新已收盘的 bar。
- **Trade**：`Catchup` 钩子——每个启用实盘账户的最近一次交易所对账在 2 分钟内、已就绪、无错误、余额已确认，并且没有目标在收敛。
- **系统级编排**：`packages/sysctl` + `moox-cli system status|pause|resume`——暂停下游到上游；恢复按依赖启动追赶（采集 → 因子 → 策略，Trade 一开始就追赶）、栅栏、按上游到下游放行（Trade 先于策略）；幂等；手动暂停的模块不参与；超时不自动放行，`--release-partial --yes` 放行已追平的。
- **Monitor**：`collector` 纳入有生命周期接口的模块（探测不到时系统汇总标红）。

与设计不同或补充的地方：

- **编排落在 `packages/sysctl`，没有新建 `modules/sysctl` 二进制**：第 8.1 节的分层不变（编排逻辑独立于命令行代码，命令行只是薄入口），沿用 `packages/seriesreplay` 的做法；常驻服务化（阶段 5）时再决定是否拆成模块。
- **Collector 的恢复模式只在进程内存**，没有给暂停表加列：追赶中重启回到暂停，再 resume 即可，避免为一个可重来的状态改库结构。
- **策略放行边界用控制器记录的放行时间（`ReleasedAt`），没有给因子结果事件加「历史标记」字段**：因子结果经 Storage 的 `ViewDataReady` 到达策略，加标记要改 Storage 事件。边界规则覆盖系统恢复；**单独恢复因子引擎而策略一直在运行**时，历史事件只受现有的有效期（2 根）限制——运维上应使用 `system pause|resume`（会先暂停策略）；这是已知缺口，列入后续。
- **Trade 放行时不强制过期暂停前未收敛的目标**，按各自有效期自然过期（有效期很短，且重复执行目标是幂等收敛）。
- **因子管理（factor-mgr）和 Archive 没有接入生命周期**：它们没有数据要追赶，暂停语义（拒绝新建/修改）留到阶段 3 与重置一起做。
- **离线维护（变更日志断档）只报告、不自动执行**：追赶报告 `变更日志断档`，需要人工按 `moox-factor-engine reconcile / backfill` 处理；自动化（`--allow-engine-restart`）列入后续。

未覆盖（待线上演练）：交易时段内的真实暂停恢复、Collector 对云函数补采的端到端、因子引擎在真实 Storage 上的追赶耗时。

### 阶段 3（分支 `feat/reset-stage3`）：单模块重置

已实现：

- **通用框架（`packages/lifecycle/reset*.go`）**：`Hooks.Reset` 提供计划与步骤；`plan` 只读，返回步骤、保留项、说明、统计、阻止条件、稳定摘要与一次性令牌（10 分钟）；`apply` 要求模块已暂停（或未初始化），立刻返回，步骤在后台执行，每步写入 `reset-journal.json`；失败进入 `reset_failed`，凭 `operation_id` 续做（已完成的步骤跳过，令牌过期无关）或 `abort`（保持「重置后等待初始化」）；成功后模块回到未初始化并带 `post_reset` 门禁，记录 `LastReset`，第一次 `init` 触发 `AfterReset`。令牌绑定摘要（不含统计），计划变化则作废；令牌在前置条件通过后才消耗。
- **服务端权限**：健康端口鉴权支持第二对密钥（`MOOX_HEALTH_RESET_ACCESS_KEY / SECRET_KEY`），用它签名的请求带 `reset` 权限；`plan / apply / abort` 需要该权限，`status` 不需要；没配置时重置接口一律拒绝。运行时的健康密钥没有 reset 权限。
- **表分类测试**：每个 `t_` 表必须归类（运行数据 / 业务配置 / 状态 / 引导数据），有未归类的表时 `plan` 报阻止条件，新增表漏了清单会在单测里失败。
- **各模块**（范围 `data` 清运行数据保留配置，`all` 再清业务配置）：

| 模块 | 步骤 | 阻止条件 / 特别处理 |
| --- | --- | --- |
| 策略 | 备份 → 清表 | 重置后实例回到未初始化 |
| Trade | 向交易所重新核验实盘敞口 → 备份 → 清表 | 实盘账户有持仓或未完成订单时阻止；敞口核验在 apply 内再做一次 |
| 因子管理 | 备份 → 清表 | — |
| 因子引擎 | 备份水位/空洞账本/目录缓存 → 丢弃内存 → 清空本地时序存储 → 清水位 → 清空洞账本 →（`all`）清目录缓存 | 预载受生命周期门禁约束，重置后不自动预载 |
| Collector | 核验 SCF 定时器已停用 → 等在途补采结束 → 备份 → 清表 | 第一步核验定时器已停用（否则删采集计划会让定时器成为孤儿），最多等 2 分钟，没停用则失败、不删任何东西；**不放进 plan 的阻止项**：plan 时模块还在运行，定时器必然没停用，会永远发不出令牌（线上 plan 验证时发现）；暂停开关保持到重置后第一次 `init` |
| Monitor | 备份 → 清表 | 保留通知渠道；暂停 = 告警静默 |
| Archive | 核验没有进行中的运行 → 备份 → 清表 | 有排队或执行中的运行时阻止 |

- **命令行**：`moox-cli lifecycle reset-plan --scope data|all`、`reset-apply --scope … --token … --yes`（或 `--operation-id … --yes` 续做；默认 `--wait`，逐步打印进度）、`reset-status`、`reset-abort --yes`；用重置专用密钥签名，缺少时给出明确提示，不回退到运行时密钥。
- **其他**：因子管理与 Archive 本阶段接入生命周期（暂停拒绝修改类接口 / 跳过定时触发与维护）；Monitor 系统阶段汇总不再被没有对象的就绪模块拉低。

验证：框架单测覆盖令牌（过期、复用、摘要变化）、每步之后中断再续做、abort、权限；每个模块单测造数据后重置并核对为空/保留；CLI 单测走完整流程、失败续做与权限拒绝。

未做（阶段 4）：`moox-cli system reset`（跨模块编排、系统名确认、`operation_id` 系统日志）、Storage `reset-metadata`、EventBus 资源清理与 Admin 白名单、Admin 业务部分重置。线上要使用重置，需要先在各模块进程配置重置专用密钥并发布这一版。

### 阶段 4（分支 `feat/reset-stage4`）：系统级重置

已实现：

- **编排（`packages/sysctl/reset.go`）**：`PlanReset` 逐个模块取重置计划（模块处于 `resetting` / `reset_failed`、读不到状态、没有重置接口都作为阻止条件），汇总阻止条件、系统摘要和 10 分钟的一次性令牌，计划与令牌写到状态目录；`ApplyReset` 校验令牌与（生产环境的）系统名，令牌立即作废，写系统日志 `journal.json`，先系统暂停（Monitor 最先，告警静默），再按顺序逐个重置，每步落盘。顺序：策略 → Trade → 因子引擎 → 因子管理 → 采集 → 归档 →〔Storage〕→ Monitor →〔Admin 业务部分〕。
- **令牌与长耗时**：模块重置前**重新取该模块的计划**，摘要和 plan 时一致才用新令牌发起，所以系统令牌只管「发起」，后面的模块不会因令牌过期失败；摘要变了（表结构、配置变了）就停在那个模块并要求重新 plan；Trade 的敞口核验在模块 apply 内再做一次（plan 只是提示）。
- **续做**：失败或中断后 `apply --operation-id <系统重置 ID>`：已完成的步骤跳过，进行中的步骤凭模块的 `operation_id` 查状态（完成就记完成，失败就让模块续做，不重做），不自动回滚。
- **外部步骤**：Storage（行数据、事件流、View 消费者；`all` 再加元数据）与 Admin 业务部分要在各自主机上执行，编排器没有登录那些主机的能力，所以停在那一步并列出命令，`--external-done <名字>` 标记后继续。命令随范围不同，随计划保存，续做时以计划为准。
- **Storage `reset-metadata`**：备份元数据库后清空全部业务定义并重新导入种子；保留 DataNode 登记、存储设备、标的修订号（单调递增，策略等调用方靠它判断缓存是否过期，不能回退）；必须先停 Storage；每张表要归类，新增表漏了清单会拒绝。`all` 范围顺序：`reset-view-consumers --reset-all-storage-data --restart=false` → `reset-metadata` → 启动 → `activate-datasets`。
- **Admin `reset-business`**：清活动日志、采集发布租约/操作，`all` 再清业务空间及成员；保留引导身份层（用户、登录历史、密钥、主机与放置、SSH、主机网关状态）和默认空间 `mooxsys`；先备份；不依赖 Admin 进程是否运行。
- **命令行**：`moox-cli system reset plan|apply|status`，`moox-cli storage reset-metadata`，`moox-admin-cli reset-business`。

与设计不同或补充的地方：

- **Admin 默认空间保留，而不是删了让 `setup init` 重建**：`setup init` 通过 Admin RPC 创建空间，没有确认它会重建成员关系，删了可能让管理员看不到默认空间；保留默认空间及其成员是安全的，`setup init` 对它是幂等的。
- **活动日志在 Admin 重置里被清空**，但库里的重置记录仍在各模块日志与系统日志 `journal.json` 里；没有在重置之后往活动日志补一行（Admin 业务部分是离线 CLI，不走 RPC），列入后续。
- **EventBus 资源不单独做**：Storage 的事件流、View 消费者、数据集主题仍由 `reset-view-consumers`（经 Admin 受限接口）清理，没有扩展 Admin 的白名单；其他模块自己创建的流/消费者在各模块 `init` 时重新创建。
- **没有「向 Monitor 声明系统重置中」**：Monitor 本身在重置前暂停（告警静默），重置期间首页显示各模块的 `resetting`；系统阶段的汇总显示留待后续。
- **archive-worker 暂存库**作为人工外部步骤 `archive-worker`（排在 Archive 之后、Storage 之前）：停 worker、删 `.state/staging.db`（否则重建同名任务会沿用旧水位），并提示已归档文件默认不动；**导入作业与导入断点的重置代次没有做**，计划里只把「Archive 有排队或执行中的运行」作为阻止项，需要时人工取消导入、用 `--restart` 重跑。
- **响应丢失与放弃**：模块接受重置后后台继续执行，若 apply 的响应丢了（隧道断开、进程被中断），续做时凭「本次系统重置开始之后的模块操作」认领它（运行中、失败或已完成都行），不新建也不重做；apply 校验当前环境、系统名与 plan 时一致，测试环境的令牌不能在生产配置下使用；计划变化无法续做时 `moox-cli system reset abort --yes` 放弃（只标记日志，不撤销已做的步骤、不动各模块），之后可重新 plan。
- **暂时性阻止条件有界等待**：系统暂停刚结束时 Collector 的 SCF 定时器还没确认停用，模块重置前的新计划会带这类阻止项；编排器在 3 分钟内（`BlockerWait`）轮询，消失就继续，超时才失败。计划摘要不含统计值，且各模块的步骤与说明不随运行状态变化，所以运行中 plan、暂停后核对不会误报「计划不一致」。

验证：编排单测（完整流程与顺序、生产环境系统名、令牌一次性与过期、失败后续做且已完成的模块不重做、计划漂移停在对应模块、阻止条件不发令牌、自动外部步骤、缺重置接口）；`moox-cli system reset` 端到端（命令行 → 编排器 → 模块 HTTP → 控制器，停在外部步骤再继续）；Storage、Admin 的表分类与清理单测。**线上尚未演练**：需要先配置各模块的重置专用密钥并发布本版本，演练建议在测试数据上做（造数据 → 重置 → 逐模块核对 → 重新 init）。

线上整体重置演练（2026-10-22，`--scope data`）暴露的两个问题：

- **新版命令行的暂停请求带零值 `expires_at`，被旧版模块严格解析拒绝（HTTP 400）**：`time.Time` 的 `omitempty` 对零值不生效。改用 `omitzero`（PR #36）。
- **策略库 1.8 GB，重置的备份占满了唯一的数据库连接，健康检查排不上队，守护进程把正在重置的策略重启了**：各模块的库把连接池限制为 1 条，`VACUUM INTO` 备份（以及统计行数、清表）会长时间占着它，`/readyz` 里的 `SELECT 1` 超时，`moox-runtime watch` 判定未就绪后重启进程，重置被「重启中断」。修复：备份、统计、清表都另开一条专用连接（SQLite 是 WAL，读写互不阻塞），文件路径由各模块在重置时登记（应用连接可能正被占着，没法向它查询路径）；有测试覆盖「应用连接被占着时备份/统计/清表仍能完成」。
- **`reset-view-consumers --reset-all-storage-data` 在原生部署布局下被自己的路径安全检查拒绝，且是在清完事件流之后**：安全检查只认 `<包根>/data/...`，原生部署的 Pebble 在 `<包根>/storage-node/var/storage/pebble`，于是 Storage 已停、View 元数据已复位、事件流已清空，才报 `refusing to delete unsafe Primary path`，留下半个重置（Pebble 数据没删，Storage 随后被守护进程拉起，View 重新从 Primary 回溯重建）。修复：校验同时认两种布局，并且提前到停服务之前（`--dry-run` 也能发现）。重新执行同一命令即可完成（命令是可重入的）。
